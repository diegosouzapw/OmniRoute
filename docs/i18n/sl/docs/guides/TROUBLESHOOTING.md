## Kratek pregled

**Ste novi v OmniRoute?** Začnite tukaj — s tem boste rešili 90 % težav:

| Prikaže se                       | Kaj to pomeni                                 | Kaj storiti                                                                                        |
| -------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| "Povezave ni mogoče vzpostaviti" | OmniRoute se ne izvaja                        | Zaženite `omniroute` ali `docker restart omniroute`                                                |
| "Neveljaven ključ API"           | Vaš ključ je napačen ali je potekel           | Znova kopirajte ključ s spletnega mesta ponudnika                                                  |
| "Omejitev hitrosti je presežena" | Pošiljate preveč zahtev                       | Počakajte 1 minuto ali uporabite `model: "auto"` za samodejni preklop                              |
| "Kvota je presežena"             | Porabili ste svojo brezplačno/plačljivo kvoto | Povežite več ponudnikov ali uporabite brezplačne ponudnike (Kiro, Pollinations)                    |
| "Počasni odzivi"                 | Ponudnik je zaseden ali zelo oddaljen         | Uporabite `model: "auto/fast"` ali povežite hitrejšega ponudnika (Groq, Cerebras)                  |
| "Uporabljen je napačen ponudnik" | `auto` je izbral drugega ponudnika            | To je običajno! `auto` izbere najboljšega. Določenega ponudnika vsilite z `model: "openai/gpt-4o"` |
| "502 Neustrezen prehod"          | Ponudnik ne deluje                            | Počakajte in poskusite znova ali uporabite `model: "auto"` za preklop med ponudniki                |
| "401 Nepooblaščeno"              | Vaše poverilnice so napačne                   | Preverite svoj ključ API ali se znova overite z OAuth                                              |
| "omniroute ni prepoznan"         | V Windows PATH manjkajo globalni moduli node  | Dodajte globalno predpono npm v Windows PATH. Poiščite jo z `npm config get prefix`.               |
| "429 Preveč zahtev"              | Dosežena je omejitev hitrosti                 | Počakajte 1 minuto ali povežite več ponudnikov                                                     |

**Težava še vedno ni odpravljena?** Spodaj si oglejte [podrobno odpravljanje težav](#podrobno-odpravljanje-težav) ali vprašajte na [Discordu](https://discord.gg/U47eFqAXCn).

### Omejevanje hitrosti pri brezplačnih ponudnikih (429 / 400 / 401)

**Simptom**: Pri uporabi `model: "auto"` z brezplačnimi ponudniki oziroma ponudniki brez preverjanja pristnosti (opencode, auggie itd.) namesto odgovorov občasno prejmete `HTTP 429`, `400` ali `401`. Zahteve uspejo, če isti poziv nekaj trenutkov pozneje pošljete znova, vendar se avtomatizacija (opravila cron, agenti, skripti) prekine že ob prvi napaki.

**Osnovni vzrok**: Seštevajo se trije neodvisni načini odpovedi:

1. **Ponudnikova omejitev hitrosti (`429`)**: Brezplačne ravni lahko uveljavljajo kvoto za posamezno časovno okno. Sunek vzporednih klicev jo izčrpa, zato je naslednja zahteva zavrnjena, dokler se časovno okno ne ponastavi.
2. **Nedelujoč model v neposrednem posredovanju (`400`/`401`)**: Nabori `auto/*` lahko vključujejo modele za neposredno posredovanje iz `opencode`, ki so registrirani v katalogu, vendar nimajo veljavnih poverilnic (npr. `oc/north-mini-code-free` → `401`). Samodejni usmerjevalnik poskusi enega od njih in ne uspe, napaka pa se razširi, še preden se sproži preklop.
3. **Ojačanje zaradi sočasnosti (`429` pod obremenitvijo)**: Ko več sej agentov ali opravil cron hkrati dostopa do `auto`, skupna hitrost zahtev preseže obremenitev, ki jo brezplačni ponudniki dopuščajo, zato so legitimni klici označeni kot zloraba.

**Preverjen popravek (po poročilih skupnosti, 2026-08-10)**: prilagodite tri spremenljivke okolja, da bodo rotacija, sočasnost in preklop prestregli nestabilnost brezplačne ravni, namesto da bi se proces zaradi nje prekinil:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ob 400/401 preklopi na drug model/ponudnika (preskoči nedelujoče modele za neposredno posredovanje)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # izrecna zgornja meja sprejema zahtev z veliko obremenitvijo (privzeto ni nastavljena: ni omejitve števila zahtev, glejte opombo spodaj)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # daljše omejeno čakanje na zmogljivost za veliko obremenitev namesto takojšnje ponovljive napake 503
```

Te spremenljivke nastavite v okolju procesa OmniRoute (demona, npr. prek datoteke plist LaunchAgent ali `systemctl edit`), nato znova zaženite OmniRoute. Zastavica za rotacijo ima največji učinek: kritično napako pretvori v pregleden ponovni poskus pri delujočem ponudniku v naboru.

**Opomba**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` omejuje število zahtev z veliko obremenitvijo — zahtev z dolgim kontekstom — ki se izvajajo hkrati; ta meja je vstopna pregrada, ne ponudnikova omejitev hitrosti. **Posodobitev glede razpršitve napak #503:** ta spremenljivka privzeto ni več nastavljena (zdaj se upošteva le, če je izrecno konfigurirana, kot zgoraj) — sprejem zahtev z veliko obremenitvijo namesto tega omejuje samodejno izračunan bajtni proračun (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), ki se prilagaja dejanski omejitvi pomnilnika gostitelja. Zato bi morala nova uvedba brez nastavljanja te spremenljivke prejeti precej manj zavrnitev `503 chat_admission_busy`; njena izrecna nastavitev še vedno deluje natančno tako, kot je dokumentirano. Izrecne preglasitve bajtnega proračuna so omejene na 8 MiB–2 GiB. Napaka `413 body_exceeds_budget` ni prehodna: povečajte ta bajtni proračun, zmanjšajte `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ali povečajte omejitev pomnilnika procesa. Razbremenitev `inflight_bytes_budget` pomeni začasno tekmovanje za vire in jo je mogoče znova poskusiti. Omejevanje hitrosti za posameznega ponudnika (`open-sse/services/rateLimitManager.ts`) ločeno upravljajo `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` in `RATE_LIMIT_AUTO_ENABLE` — glejte `.env.example`.

**Kako preveriti, ali popravek deluje**: dvakrat v hitrem zaporedju zaženite svojega agenta/opravilo cron in potrdite, da sta oba zagona uspešna. Pred popravkom drugi zagon običajno vrne napako `429`/`401`. Po popravku se neuspešni poskusi (če do njih pride) samodejno ponovijo in klic se dokonča. Prav tako lahko izvedete `curl /monitoring/health` ter pri povezavah ponudnikov spremljate polje `rateLimitedUntil` in polje `circuitBreakers.providerBreakers[].state` za prizadete ponudnike — stanje je lahko `CLOSED`, `DEGRADED`, `OPEN` ali `HALF_OPEN` (glejte `src/shared/utils/circuitBreaker.ts`), ponudnik, pri katerem se napake ponavljajo, pa bo prešel iz stanja `CLOSED → DEGRADED → OPEN`, preden bo časovno okno za ponastavitev omogočilo preizkusni klic (`HALF_OPEN`).

**Če se napaka 429 še vedno pojavlja**: aktivni račun pri tem ponudniku je dejansko izčrpal svojo _kvoto_ (ne le omejitve hitrosti). Na nadzorni plošči OmniRoute v razdelku Providers → Accounts dodajte drugi račun za istega ponudnika ali vključite drugega brezplačnega ponudnika (npr. `routeway`, `auggie`). Rotacija pomaga le pri prehodnih napakah omejitve hitrosti oziroma napakah 400/401; popolna izčrpanost kvote zahteva dodatne poverilnice ali drugega ponudnika.

**Če se pri modelih za vid (`auto/vision`, `bazaarlink/*`) pojavlja napaka 403**: povezani račun nima plačljivega paketa, ki vključuje vid, ali pa ključ API nima zadostnih dovoljenj. Na nadzorni plošči ponudnika preverite, ali obseg ključa vključuje vid/večmodalnost, ali pa povežite račun s plačljivim paketom in ga ohranite kot cilj za vid.

## Opozorila pri npm install (ERESOLVE / peer / deprecated)

Ko zaženete `npm install -g omniroute`, se lahko prikaže množica opozoril, kot so `npm warn ERESOLVE`, obvestila o vrstniških odvisnostih in sporočila `deprecated`. **Ta opozorila so pričakovana in neškodljiva.** Namestitev je uspela, če je v izpisu prikazano `added <N> packages`.

Če želite skriti opozorila o razreševanju vrstniških odvisnosti, uporabite podprto obliko namestitve OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` skrije samo opozorila `ERESOLVE` in obvestila o vrstniških odvisnostih. Obvestila o opuščenih paketih ostanejo vidna, ker izvirajo iz prehodnih paketov drugih ponudnikov; ne pomenijo, da namestitev ni uspela.

Opozorila povzročajo zastareli razponi vrstniških odvisnosti v paketih drugih ponudnikov, ki niso pod nadzorom OmniRoute:

1. **`marked-terminal` zahteva `marked >=1 <16`, najden pa je bil `marked@18`** — v praksi deluje brez težav; razpon vrstniške odvisnosti v izvornem paketu je le zastarel.
2. **`deprecated prebuild-install@7.1.3`** — prehodni pomožni program za pridobivanje izvornih binarnih datotek. Ne uporablja se
   za namestitev pripete transportne vezave `wreq-js` in ne pomeni, da nastavitev transporta ponudnika
   spletnih piškotkov ni uspela.

**Ukrepanje ni potrebno** — opozoril ni mogoče popolnoma skriti brez razvejanja izvornih paketov.

## Gemini Web in Playwright Chromium

Če zahteva Gemini Web vrne `503` s sporočilom, da Playwright Chromium
ni nameščen, je paket npm prisoten, manjka pa binarna datoteka brskalnika.
Playwright namenoma ločuje prenose brskalnikov od namestitve paketov npm,
zato je ta odziv pričakovan, dokler brskalnik ni nameščen.

Pri globalni namestitvi npm namestite Chromium iz imenika paketa OmniRoute,
da bo predpomnilnik brskalnika pripadal isti namestitvi Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Po namestitvi znova zaženite OmniRoute in nato ponovno poskusite z zahtevo Gemini Web. Če
OmniRoute izvajate iz slike Docker, uporabite sliko `-web` (ali cilj gradnje `runner-web`),
ki vključuje Chromium in njegove odvisnosti; osnovna slika jih
ne vključuje.

## Lažno pozitivna zaznavanja protivirusnih programov

<a name="antivirus-false-positives"></a>

### Avast/AVG premakne `README.md` v karanteno zaradi `MD:HttpRequest-inf[Susp]`

**To je lažno pozitivno zaznavanje. Nič ni okuženo in ukrepanje ni potrebno.**

Avast in AVG uporabljata hevristiko, ki označi datoteke z navadnim besedilom/Markdownom, ki vsebujejo veliko
povezav, podobnih zahtevam HTTP. Datoteka `README.md` projekta OmniRoute je vključena v paket npm (navedena je
v `package.json` → `files`), zato se pri globalni namestitvi znajde v `node_modules/omniroute/README.md` — vsebuje pa
približno 15 primerov `http://localhost:20128/...` (končne točke MCP HTTP/SSE, naslov URL A2A `.well-known`
in izseke `curl`). Takšna gostota povezav zadostuje za sprožitev hevristike.

Če se je to začelo dogajati šele pred kratkim: vrsta datoteke se ni spremenila. V datoteki README je bila razširjena
tabela končnih točk (dodani so bili MCP HTTP + SSE + A2A) in dodanih je bilo več primerov `curl`, zaradi česar
je bila presežena mejna vrednost.

Datoteka je nedejavna dokumentacija brez kakršne koli izvršljive vsebine. Lahko jo varno obnovite
iz karantene.

**Kaj storiti:**

1. **Ustavite obvestila** — namestitveni imenik izključite iz pregledovanja protivirusnega programa
   (Avast: Settings → Exceptions) tako, da dodate svojo globalno pot `node_modules` in/ali
   podatkovni imenik OmniRoute (`~/.omniroute/`).
2. **Prijavite lažno pozitivno zaznavanje** — <https://www.avast.com/false-positive-file-form.php>
   in priložite datoteko `README.md` iz karantene. To je rešitev, ki pomaga vsem, saj gre za
   pretiran odziv ponudnikove hevristike na besedilno datoteko.

**Zakaj tega ne »popravimo« na naši strani:** vsi primeri uporabljajo `http://localhost`, za
localhost pa protokola `https` ni mogoče uporabljati brez zapletov s samopodpisanimi potrdili. Spreminjanje dokumentacije
z namenom izogibanja hevristiki enega ponudnika bi škodovalo vsem bralcem samo zato, da bi zadostili programu za pregledovanje z napako.

### Kaspersky namizno aplikacijo označi kot `PDM:Trojan.Win32.Generic`

**To je lažno pozitivno zaznavanje vedenjske hevristike. Nič ni okuženo.** Predpona
`PDM:` pri programu Kaspersky pomeni, da ocena izvira iz njegovega modula Proactive Defense Module (System Watcher),
ki presoja, kaj namestitveni program _počne_, namesto da bi ga primerjal z znano zlonamerno programsko opremo. Ko
se zaznavanje sproži, Kaspersky »razveljavi« celotno namestitev — izbriše datoteke, ki jih je že
zapisal — zato aplikacija na koncu ne deluje ali manjka.

Datoteke, ki jih označi, so standardni deli navedenih odprtokodnih odvisnosti, priloženih
namizni aplikaciji, na primer:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` in
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), knjižnica za avtomatizacijo
  brskalnika, ki se uporablja za prijavo ponudnika znotraj aplikacije in klepet prek brskalnika.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — pripeta izvorna vezava `wreq-js`, ki se uporablja za HTTP z brskalniškim prstnim odtisom pri ponudnikih,
  ki uporabljajo spletne piškotke (`<arch>` je `x64` ali `arm64`).

**Zakaj se sproži:** namestitveni program za Windows **še ni podpisan s kodo**, zato nepodpisan namestitveni program NSIS
nima nobenega ugleda, vedenjske hevristike pa delujejo z največjo agresivnostjo. Skupaj
s priloženo izvorno knjižnico DLL in stotinami datotek `.js`, zapisanih v
`%LOCALAPPDATA%\Programs\OmniRoute` (vključno z imeniki paketov s priponami zgoščene vrednosti iz
samostojne graditve Next.js), to zadostuje za sprožitev hevristike. Podpisovanje kode je načrtovano;
dokler ne bo uvedeno, se lahko to ponovi ob novih izdajah.

**Kaj storiti:**

1. **Najprej preverite preneseno datoteko** (s tem izključite možnost, da je bila datoteka spremenjena). Z vsako izdajo je objavljena
   datoteka `latest.yml`, katere polje `sha512` (base64) velja za namestitveni program
   `OmniRoute.Setup.<version>.exe`. V PowerShellu v mapi z namestitvenim programom zaženite:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Izhod se mora ujemati z `latest.yml` → `sha512`. Če se ne ujema, izbrišite datoteko in
   jo znova prenesite samo s [strani izdaj na GitHubu](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Obnovite + izključite** — razveljavljene elemente obnovite iz karantene in dodajte izključitev
   za `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   nato znova izvedite namestitev.
3. **Prijavite lažno pozitivno zaznavanje** — <https://opentip.kaspersky.com/>. Poročila uporabnikov o
   lažno pozitivnih zaznavanjih dejansko pospešijo dodajanje na seznam dovoljenih datotek.

## Združljivost z Node.js

<a name="nodejs-compatibility"></a>

### Stran za prijavo se sesuje ali prikaže napako »Module self-registration«

**Vzrok:** Uporabljate različico Node.js zunaj najnižje odobrene varne različice izvajalnega okolja OmniRoute. Najpogostejši primer je uporaba starejše različice popravka Node 22 ali 24, ki je nižja od zahtevane varnostno popravljene različice OmniRoute.

**Simptomi:**

- Stran za prijavo prikaže prazen zaslon ali napako strežnika
- Konzola prikaže `Error: Module did not self-register` ali podobne napake izvornih povezav
- Stran za prijavo prikaže **oranžno opozorilno pasico** z vašo različico Node, če izvajalno okolje ni v skladu s podprtim varnostnim pravilnikom

**Rešitev:**

1. Namestite podprto izdajo Node.js LTS (priporočeno: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Preverite svojo različico: `node --version` mora prikazati `v24.0.0` ali novejšo različico iz veje 24.x LTS
3. Znova namestite OmniRoute: `npm install -g omniroute`
4. Znova zaženite: `omniroute`

> **Podprte varne različice:** `>=22.22.2 <23` ali `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) in Node.js 26 sta v celoti podprta.

### npm v11+: `better-sqlite3` ni nameščen (modula ni mogoče najti)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Vzrok:** npm v11 (priložen Node.js 24+) privzeto blokira namestitvene skripte za izbirne
odvisnosti. Ker je `better-sqlite3` naveden v `optionalDependencies`
in zahteva izvorno prevajanje (`node-gyp rebuild`), ga npm brez opozorila preskoči.

**Simptomi:**

- Strežnik se ob zagonu sesuje z napako `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` prikaže »No such file or directory«
- `npm ls better-sqlite3` prikaže `(empty)`

**Rešitev:**

1. Odobrite namestitvene skripte in znova izvedite namestitev:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Ali pa vnaprej prevedeni paket namestite ročno:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Preverite, ali deluje: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / »slice is not valid mach-o file«

<a name="macos-native-module-rebuild"></a>

**Vzrok:** Po globalni namestitvi z `npm install -g omniroute` je bila izvorna binarna datoteka `better-sqlite3` znotraj paketa morda prevedena za drugo arhitekturo ali ABI Node.js od tistega, ki se izvaja lokalno. To je pogosto v sistemu macOS (tako na Apple Silicon kot na Intel), kadar se vnaprej prevedena binarna datoteka ne ujema z vašim okoljem.

**Simptomi:**

- Strežnik ob zagonu takoj odpove z napako `dlopen`
- Napaka vsebuje `slice is not valid mach-o file`
- Celoten primer:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Rešitev — znova prevedite za svoje lokalno okolje (vrnitev na starejšo različico Node.js ni potrebna):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Opomba:** S tem znova prevedete izvorno povezavo za svojo lokalno različico Node.js in arhitekturo procesorja ter odpravite neujemanje binarnih datotek. Uradno podprto območje izvajalnega okolja je **`>=22.22.2 <23` ali `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` v `src/shared/utils/nodeRuntimeSupport.ts`, usklajeno s poljem `engines` v `package.json`). Node.js 24.x LTS (Krypton) in Node.js 26 sta v celoti podprta z `better-sqlite3` v12.x.

## Težave s posredniškim strežnikom

<a name="proxy-issues"></a>

### Preverjanje ponudnika prikaže »fetch failed«

**Vzrok:** Končna točka za preverjanje ključa API (`POST /api/providers/validate`) je prej obšla konfiguracijo posredniškega strežnika, kar je povzročalo napake v okoljih, ki zahtevajo usmerjanje prek posredniškega strežnika.

**Popravek (v3.5.5+):** To je zdaj popravljeno. Preverjanje ponudnika poteka prek `runWithProxyContext` in samodejno upošteva nastavitve posredniškega strežnika na ravni ponudnika ter globalne nastavitve.

### Preverjanje veljavnosti žetona ne uspe z napako »fetch failed«

**Vzrok:** Osveževanje žetonov OAuth v ozadju ni razreševalo konfiguracije posredniškega strežnika za vsako povezavo posebej.

**Popravek (v3.5.5+):** Razporejevalnik preverjanja veljavnosti žetonov zdaj pred poskusom osvežitve razreši konfiguracijo posredniškega strežnika za vsako povezavo posebej. Posodobite na v3.5.5+.

### Posredniški strežnik SOCKS5 vrne »invalid onRequestStart method«

**Vzrok:** V Node.js 22 razpošiljevalnik undici@8 ni združljiv z Nodeovo vgrajeno implementacijo `fetch()`.

**Popravek (v3.5.5+):** OmniRoute zdaj uporablja lastno funkcijo `fetch()` paketa undici, kadar je aktiven razpošiljevalnik posredniškega strežnika, kar zagotavlja dosledno delovanje. Posodobite na v3.5.5+.

### Posredniški strežnik MITM v WSL: namizne aplikacije v gostiteljskem sistemu Windows niso prestrežene

**Vzrok:** Posredniški strežnik MITM in njegovo potrdilo CA se namestita v okolje, v katerem se izvaja OmniRoute. Pri WSL je to okolje gostujoči sistem Linux, medtem ko se namizne aplikacije z umetno inteligenco (Kiro, Trae, Copilot, Zed, …) izvajajo v gostiteljskem sistemu Windows. Aplikacije v gostiteljskem sistemu ne zaupajo shrambi potrdil gostujočega sistema in prometa ne usmerjajo prek sistemskega posredniškega strežnika gostujočega sistema, zato prestrezanje namiznih aplikacij tam ne deluje.

**Priporočilo:** OmniRoute zaženite neposredno v istem operacijskem sistemu kot namizne aplikacije, ki jih želite prestrezati (Windows za aplikacije Windows; enako velja za macOS/Linux). Če OmniRoute ohranite znotraj WSL in ciljate aplikacije v gostiteljskem sistemu, morate ustvarjenemu potrdilu CA ročno zaupati v gostiteljskem sistemu Windows ter omrežne nastavitve oziroma nastavitve posredniškega strežnika vsake gostiteljske aplikacije usmeriti na končno točko posredniškega strežnika WSL — to je nepodprta in nezanesljiva nastavitev.

## Težave z oblakom

### Napake pri sinhronizaciji z oblakom

1. Preverite, ali `BASE_URL` kaže na vaš delujoči primerek (npr. `http://localhost:20128`)
2. Preverite, ali `CLOUD_URL` kaže na vašo končno točko v oblaku (npr. `https://omniroute.dev`)

1. Ustvarite nov ključ na lokalni nadzorni plošči (`/api/keys`)
2. Zaženite sinhronizacijo z oblakom: Omogoči oblak → Sinhroniziraj zdaj
3. Stari oziroma nesinhronizirani ključi lahko v oblaku še vedno vrnejo `401`

## Težave z okoljem Docker

### Docker IPv6 / Ponastavitev povezave

<a name="docker-ipv6"></a>

**Simptomi:** `curl http://localhost:20128/v1/models` vrne `curl: (56) Recv failure: Connection reset by peer`. Nadzorna plošča in končne točke brez preverjanja pristnosti delujejo, končne točke s preverjanjem pristnosti pa ne — videti je kot težava s preverjanjem pristnosti, vendar ni.

**Vzrok:** `docker run -p 20128:20128` objavi vrata tako na `0.0.0.0` (IPv4) kot na `::` (IPv6), vendar proces znotraj vsebnika posluša samo na IPv4. Na gostiteljih, kjer se `localhost` najprej razreši v `::1`, povezava prispe na objavljena vrata IPv6, za katerimi ni poslušalca → povezava se ponastavi.

**Popravek:**

1. **Hitra diagnostika:** Zaženite `curl -4 http://localhost:20128/v1/models`. Če z možnostjo `-4` deluje, brez nje pa ne, gre za neujemanje vezave IPv6.
2. **Trajni popravek:** Izrecno izvedite vezavo na IPv4 tako, da v ukazu `docker run` uporabite `-p 127.0.0.1:20128:20128`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   To vsili vezavo IPv4 in hkrati prepreči izpostavitev posredniškega strežnika na vseh vmesnikih gostitelja.

## Odpravljanje napak

### Omogočanje dnevniških datotek

V datoteki `.env` nastavite `APP_LOG_TO_FILE=true`. Dnevniki aplikacije se zapisujejo v `logs/`.
Artefakti zahtev se shranjujejo v `${DATA_DIR}/call_logs/`, ko je v nastavitvah omogočen cevovod dnevnika klicev.
Ko je zajemanje cevovoda omogočeno, nastavite `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`, da izpustite
vsebine pretočnih kosov, ali prilagodite `CALL_LOG_PIPELINE_MAX_SIZE_KB`, da spremenite omejitev velikosti artefaktov v KB.

### Preverjanje zdravja ponudnika

```bash
# Nadzorna plošča zdravja
http://localhost:20128/dashboard/health

# Preverjanje zdravja API-ja
curl http://localhost:20128/api/monitoring/health
```

### Shramba izvajalnega okolja

- Glavno stanje: `${DATA_DIR}/storage.sqlite` (ponudniki, kombinacije, vzdevki, ključi, nastavitve)
- Uporaba: tabele SQLite v `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + izbirno `${DATA_DIR}/call_logs/`
- Dnevniki aplikacije: `<repo>/logs/...` (ko je `APP_LOG_TO_FILE=true`)
- Artefakti dnevnika klicev: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, ko je omogočen cevovod dnevnika klicev

Dejanje **Počisti zgodovino** na strani Dnevniki zahtev izbriše `call_logs`, starejše
`request_detail_logs` in lokalni imenik artefaktov `${DATA_DIR}/call_logs/`.

### Pogoste težave s formati

- **Oznake razmišljanja se ne prikažejo** — Preverite, ali ciljni ponudnik podpira razmišljanje, in preverite nastavitev proračuna za razmišljanje
- **Klici orodij se izgubijo** — Nekateri prevodi formatov lahko odstranijo nepodprta polja; preverite v načinu Preizkusno okolje
- **Sistemski poziv manjka** — Claude in Gemini sistemske pozive obravnavata različno; preverite rezultat prevoda
- **SDK vrne neobdelan niz namesto predmeta** — Odpravljeno v v1.x; čistilnik odgovorov odstrani nestandardna polja (`x_groq`, `usage_breakdown` itd.), ki povzročajo napake pri preverjanju veljavnosti Pydantic v OpenAI SDK. Če se težava še vedno pojavlja v v3.x+, prijavite težavo.
- **GLM/ERNIE zavrne vlogo `system`** — Odpravljeno v v1.x; normalizator vlog samodejno združi sistemska sporočila z uporabniškimi sporočili pri nezdružljivih modelih. Če se težava še vedno pojavlja v v3.x+, prijavite težavo.
- **Vloga `developer` ni prepoznana** — Odpravljeno v v1.x; pri ponudnikih, ki niso OpenAI, se samodejno pretvori v `system`. Če se težava še vedno pojavlja v v3.x+, prijavite težavo.
- **`json_schema` ne deluje z Gemini** — Odpravljeno v v1.x; `response_format` se zdaj pretvori v Geminijeva `responseMimeType` + `responseSchema`. Če se težava še vedno pojavlja v v3.x+, prijavite težavo.

## Nastavitve odpornosti

### Samodejno omejevanje hitrosti se ne sproži

- Samodejno omejevanje hitrosti velja samo za ponudnike s ključi API (ne za OAuth/naročnine)
- Preverite, ali je v **Nastavitve → Odpornost → Profili ponudnikov** omogočeno samodejno omejevanje hitrosti
- Preverite, ali ponudnik vrača kode stanja `429` ali glave `Retry-After`

### Prilagajanje eksponentnega čakanja

Profili ponudnikov podpirajo te nastavitve:

- **Osnovna zakasnitev** — začetni čas čakanja po prvi napaki (privzeto: 1s)
- **Največja zakasnitev** — zgornja meja časa čakanja (privzeto: 30s)
- **Množitelj** — za koliko se poveča zakasnitev ob vsaki zaporedni napaki (privzeto: 2x)

### Preprečevanje stampeda zahtev

Ko veliko sočasnih zahtev doseže ponudnika z omejeno hitrostjo, OmniRoute uporabi mutex in samodejno omejevanje hitrosti, da zahteve serializira ter prepreči verižno pojavljanje napak. To se za ponudnike s ključi API izvede samodejno.

### Zahteve za klepet ne uspejo z 503 / chat_admission_busy

**Simptomi:**

- Končna točka za dokončanja klepeta vrne ponovljiv odgovor `503`, katerega koda napake je
  `chat_admission_busy`.
- Odgovor vključuje `Retry-After`. Od #12135 dalje je vrednost izpeljana iz opažene
  zasedenosti — uporabi se večja izmed okna `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`, kolikor je zahteva že
  čakala, in časa, kolikor so bile trenutne zahtevne rezervacije zadržane — zaokrožena navzgor na cele
  sekunde in omejena na 60. Pri nedejavnih vratih ohrani zgodovinske spodnje meje: 2 sekundi na
  poti, ki temelji na bajtih, in 1 sekundo na poti, ki temelji na strukturi (ta vključuje tudi
  `reason: "structure_limit"`).
- To se lahko zgodi, medtem ko se drug zahteven klepet ali dolgotrajen pretočni odgovor še vedno
  izvaja.

Telo odgovora poti, ki temelji na bajtih, je:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Odgovor, ki temelji na strukturi, uporablja isto vrsto in kodo ter sporočilo
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
in `reason: "structure_limit"`.
Pri privzetih pragovih je zahteva strukturno zahtevna, če ima vsaj `200` sporočil,
vsaj `64` orodij ali vsaj `32,000` ocenjenih žetonov oziroma kadar omejeno ocenjevanje strukture
izčrpa svoje omejitve `10,000` obiskanih vozlišč ali globine `12`.

**Vzrok:** To je namerno razbremenjevanje znotraj OmniRoute in ne napaka ponudnika v višjem toku.
Vsak proces uporablja lokalno varovalo procesa, da rezervira omejeno zmogljivost za zahtevne zahteve, preden zadrži
in razčleni veliko telo zahteve. Zahtevna rezervacija ostane zadržana celotno življenjsko dobo odgovora SSE.

**Razvejanje napak #503:** pred tem popravkom je varovalo omejevalo sočasnost na fiksno ŠTEVILO zahtev
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, privzeto `1`) ne glede na pomnilnik gostitelja, zato se je
razvejanje programskih agentov (več podagentov/CLI-jev, telesa redno > 256 KB) sesulo na učinkovito
sočasnost ~1 in pri povsem običajni obremenitvi vračalo napake 503. Varovalo se zdaj samodejno prilagaja: upravlja
ga samodejno izpeljan BAJTNI proračun za sprejem (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), določen glede na
dejansko omejitev pomnilnika procesa, poleg tega pa upošteva sprotni signal obremenitve virov — zato
zavrne zahteve samo, kadar je gostitelj dejansko pod pomnilniškim pritiskom, in ne zgolj zato, ker je hkrati
prispela več kot ena zahtevna zahteva. Stara omejitev števila (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) se
še vedno upošteva, vendar samo, če jo izrecno nastavite.

Ko je zmogljivost zasedena, zahtevna zahteva najprej čaka največ
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (privzeto `2000`, `0` onemogoči čakanje), da se mesto sprosti,
preden odgovori s ponovljivim `503`. Omejeno čakanje obstaja zato, da odjemalci v slogu agentov
(OpenCode, Claude Code, Cursor), ki sočasno razvejajo zahtevne podzahteve, serializirajo naval
namesto da bi porabili ves svoj proračun ponovnih poskusov za takojšnje zavrnitve in odpovedali sredi opravila.
Trenutna zasedenost zahtevnih rezervacij, razrešeni bajtni proračun in trenutna resnost pritiska so
prikazani na `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — to preverite, preden spremenite katero koli spremenljivko okolja.
Nastavitve → Odpornost → Čakalna vrsta zahtev → Sočasne zahteve tega ne nadzoruje; ta nastavitev
upravlja ločen mehanizem čakalne vrste zahtev ponudnika.

**Rešitev:**

1. Najprej poskusite znova. Odjemalci morajo upoštevati `Retry-After` in uporabiti čakanje namesto takojšnje
   ponovitve zahteve.
2. Pred kakršnim koli prilagajanjem preverite `/api/monitoring/health` → `chatAdmission`. `countCapEnabled:
false` in velikodušen `maxInflightBytes` pomenita, da samodejno izpeljani proračun že opravlja svoje
   delo; `pressureSeverity` z vrednostjo `high`/`critical` pomeni, da gostitelju dejansko primanjkuje pomnilnika —
   tega ni mogoče odpraviti s spremenljivko okolja za sprejem, temveč je potrebnega več pomnilnika RAM ali manjša delovna obremenitev.
3. Samo če `/api/monitoring/health` pokaže, da je samodejno izpeljani proračun dejansko premajhen za
   vašega gostitelja (kar je redko — že se prilagaja od vsebnikov do fizičnih strežnikov), ga neposredno preglasite z
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, namesto da se vrnete na podedovano omejitev števila zahtev.

Za uradne nastavitve sprejema glejte [referenco spremenljivk okolja](../reference/ENVIRONMENT.md#4-security--authentication).

## Izbirna taksonomija napak RAG / LLM (16 težav)

Nekateri uporabniki OmniRoute prehod postavijo pred sklade RAG ali agentske sklade. V takšnih postavitvah je pogosto mogoče opaziti nenavaden vzorec: OmniRoute je videti zdrav (ponudniki delujejo, profili usmerjanja so v redu, ni opozoril o omejitvah hitrosti), vendar je končni odgovor kljub temu napačen.

V praksi ti incidenti običajno izvirajo iz nadaljnjega cevovoda RAG in ne iz samega prehoda.

Če želite skupno izrazje za opisovanje teh napak, lahko uporabite WFGY ProblemMap, zunanji besedilni vir z licenco MIT, ki opredeljuje šestnajst ponavljajočih se vzorcev napak RAG / LLM. Na visoki ravni zajema:

- odmik pri pridobivanju in porušene meje konteksta
- prazne ali zastarele indekse in vektorske shrambe
- neskladje med vdelavami in semantiko
- težave pri sestavljanju pozivov in s kontekstnim oknom
- sesutje logike in pretirano samozavestne odgovore
- napake v dolgih verigah in pri usklajevanju agentov
- odmik pomnilnika in vlog pri več agentih
- težave z vrstnim redom uvajanja in inicializacije

Zamisel je preprosta:

1. Ko preiskujete slab odgovor, zajemite:
   - uporabniško nalogo in zahtevo
   - kombinacijo poti ali ponudnikov v OmniRoute
   - ves kontekst RAG, uporabljen v nadaljnji obdelavi (pridobljeni dokumenti, klici orodij itd.)
2. Incident preslikajte na eno ali dve številki WFGY ProblemMap (`No.1` … `No.16`).
3. Številko shranite na lastno nadzorno ploščo, v operativni priročnik ali sistem za spremljanje incidentov poleg dnevnikov OmniRoute.
4. Na ustrezni strani WFGY preverite, ali morate spremeniti svoj sklad RAG, mehanizem za pridobivanje ali strategijo usmerjanja.

Celotno besedilo in konkretna navodila so na voljo tukaj (licenca MIT, samo besedilo):

[README za WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Ta razdelek lahko prezrete, če za OmniRoute ne izvajate cevovodov RAG ali agentskih cevovodov.

## Znane težave v3.8.0

Težave, značilne za izdajo v3.8.0, in njihove trenutne rešitve. Če bo popravek vključen v poznejši popravek različice, bo vnos posodobljen ali odstranjen.

### Napake pri preverjanju pristnosti Devin CLI

**Simptomi:**

- »Devin CLI ni bil najden« ali »preverjanje pristnosti ni uspelo« pri priklicu orodij, ki uporabljajo Devin
- Preverjanje izvajalnega okolja CLI sporoči `installed=false`

**Vzroki:**

- `CLI_DEVIN_BIN` kaže na pot, ki ne obstaja
- Devin CLI ni nameščen na gostitelju

**Rešitev:**

1. Namestite Devin CLI za svojo platformo
2. V `.env` nastavite `CLI_DEVIN_BIN=/usr/local/bin/devin` (ali dejansko pot)
3. Znova zaženite OmniRoute in ponovno izvedite preizkus v **Nadzorna plošča → Orodja CLI**

### Obdobje ohlajanja modela je obtičalo (ročna ponastavitev)

**Simptomi:**

- Model ostane naveden kot model v obdobju ohlajanja tudi po poteku časa
- Zahteve pri kombiniranem usmerjanju še vedno preskočijo model, čeprav je časovni žig že v preteklosti

**Ročna ponastavitev:**

- **Nadzorna plošča:** **Nastavitve → Obdobja ohlajanja modelov** → na kartici zadevnega modela kliknite **Znova omogoči**
- **API:** `DELETE /api/resilience/model-cooldowns` z glavami za skrbniško preverjanje pristnosti

### Povezava s ponudnikom Command Code ne uspe z napako 403

**Simptomi:**

- Napaka 403 pri preskušanju povezave s ponudnikom Command Code
- Kartica ponudnika po novem dodajanju prikazuje »nepooblaščeno«

**Vzrok:** Potek OAuth se ni dokončal (povratni klic ni bil prejet ali žeton ni bil trajno shranjen).

**Rešitev:**

- Izvedite `omniroute providers` iz CLI, da znova sprožite potek OAuth, ali
- Znova izvedite OAuth v **Nadzorna plošča → Ponudniki → Command Code → Znova vzpostavi povezavo**

### ModelScope vrača agresivna obdobja ohlajanja 429

**Simptomi:**

- Zelo kratka ali takojšnja obdobja ohlajanja v ModelScope po majhnem sunku zahtev
- Kombinirano usmerjanje preskoči ModelScope prej, kot je pričakovano

**Vzrok:** ModelScope oddaja glave `Retry-After`, značilne za ponudnika. v3.8.0 vključuje namensko obravnavo teh glav, zato jih starejše različice napačno razumejo kot splošne namige glede omejitve hitrosti.

**Rešitev:**

- Prepričajte se, da uporabljate v3.8.0 ali novejšo različico
- Preverite, ali je preklopnik `useUpstream429BreakerHints` omogočen v **Nastavitve → Odpornost**

### OMNIROUTE_WS_BRIDGE_SECRET manjka v produkcijskem okolju

**Simptomi:**

- Napaka 401 pri vsaki zahtevi mostu WebSocket za Codex/Responses, ko se izvaja na oddaljenem produkcijskem gostitelju
- Rokovanje mostu WebSocket se konča takoj po vzpostavitvi povezave

**Vzrok:** Okoljska spremenljivka `OMNIROUTE_WS_BRIDGE_SECRET` manjka v produkcijskem okolju.

**Rešitev:**

1. Ustvarite naključno skrivnost: `openssl rand -hex 32`
2. Nastavite `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` v okolju produkcijskega strežnika (in v vsakem odjemalcu, ki komunicira z mostom)
3. Znova zaženite OmniRoute

### Responses API: način v ozadju degradiran na sinhronega

**Simptomi:**

- Zabeleženo opozorilo: `background mode degraded to synchronous`
- Zahteva z `background: true` vrne običajen sinhroni odgovor namesto ročice opravila v ozadju

**Vzrok:** v3.8.0 namenoma degradira `background: true` v Responses API na sinhrono izvajanje, pri tem pa izda opozorilo. Popolno asinhrono izvajanje v ozadju je načrtovano za prihodnjo izdajo.

**Rešitev:**

- Prilagodite odjemalca tako, da kliče brez `background`, ali
- Počakajte na poznejšo izdajo s popolnim asinhronim načinom v ozadju (spremljajte dnevnik sprememb)

## Počasen zagon / časovna omejitev pripravljenosti

Če CLI izpiše `⚠ Strežnik se ni odzval v 60 s`, vendar strežnik dejansko
deluje, je časovna omejitev preverjanja pripravljenosti za vaše okolje prekratka.

To se pogosto zgodi v sistemu Windows (protivirusna programska oprema, nadzorniki datotečnega sistema) ali vsebnikih
z velikimi obremenitvami ob zagonu.

**Rešitev — podaljšajte časovno omejitev:**

```bash
# Prek okoljske spremenljivke (velja tudi pri naslednjih zagonih):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minute
omniroute serve

# Prek zastavice CLI (enkratno):
omniroute serve --ready-timeout 180000
```

Privzeta vrednost je 60 000 ms (60 s). Opozorilo je zgolj informativno; strežnik
se še naprej zaganja v ozadju in bo dosegljiv, ko bo zagon končan.

Za vse podrobnosti o `OMNIROUTE_READY_TIMEOUT_MS` glejte
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
