Les relais (Vercel, Deno, Cloudflare) mettent fin à la connexion en amont sur un
backend sans serveur afin qu’OmniRoute puisse faire sortir le trafic depuis une région stable tout en conservant
la clé d’API du fournisseur côté serveur. Ce document décrit les deux modes de défaillance
rencontrés par les opérateurs en production, ainsi que les procédures de récupération fournies par OmniRoute pour
chacun d’eux.

## Stockage de l’authentification des relais

Lorsque vous déployez un relais depuis **Paramètres → Pool de proxys → Déployer un relais**, le
processus de déploiement stocke le jeton d’authentification du relais dans le champ JSON `notes` du proxy :

- Si `STORAGE_ENCRYPTION_KEY` est définie, le jeton est enregistré sous la forme `relayAuthEnc`
  (chiffré avec AES au repos).
- Sinon, il est enregistré en texte brut dans `relayAuth`.

Lors d’une requête, `extractRelayAuth(notes)` renvoie la forme présente,
de sorte que le relais continue de fonctionner après les redémarrages.

## Mode de défaillance 1 — jeton indéchiffrable après la rotation de la clé

**Symptôme :** les relais qui fonctionnaient auparavant renvoient désormais des erreurs
`401`/d’authentification en amont après une rotation de
`STORAGE_ENCRYPTION_KEY` dans l’environnement ou le gestionnaire de secrets. Le blob `relayAuthEnc` stocké ne peut plus être
déchiffré ; `extractRelayAuth` renvoie donc une chaîne vide et le relais n’envoie
aucune authentification.

**Récupération — réparation sur place (sans redéploiement) :**

1. Ouvrez **Paramètres → Pool de proxys**.
2. Les lignes de relais dont l’authentification est absente affichent un badge jaune `authentification manquante` et un
   bouton **Réparer**.
3. Cliquez sur **Réparer**. OmniRoute appelle
   `POST /api/settings/proxies/[id]/repair-relay`, qui :
   - déchiffre `relayAuthEnc` avec la clé **actuelle**,
   - réécrit la valeur `relayAuth` en texte brut dans `notes`,
   - renvoie `{ repaired: true, mode: "recovered" }`.

Le relais reprend son service sans qu’il soit nécessaire de saisir à nouveau les identifiants de déploiement.

Cela ne fonctionne que si la valeur actuelle de `STORAGE_ENCRYPTION_KEY` peut encore déchiffrer le
blob. Si vous avez effectué la rotation de la clé **sans** migration, le blob est
irrécupérable.

## Mode de défaillance 2 — jeton irrécupérable (ancienne clé supprimée après rotation)

**Symptôme :** vous avez cliqué sur **Réparer** et obtenu
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Récupération — redéploiement :**

Le jeton stocké ne peut pas être récupéré avec la clé actuelle. Redéployez le relais
depuis la même fenêtre modale que celle utilisée initialement (menu **Déployer un relais** → Vercel / Deno
/ Cloudflare). Le processus de déploiement enregistre un nouveau jeton (chiffré avec la clé actuelle)
et le badge `authentification manquante` de la ligne disparaît.

Dans l’interface utilisateur, le bouton **Réparer** ouvre lui-même la fenêtre modale de redéploiement lorsque le
jeton est irrécupérable, de sorte que vous n’avez jamais à la rechercher manuellement.

## Mode de défaillance 3 — relais joignable mais défaillant

**Symptôme :** le test du proxy (bouton `speed`) indique que le relais est opérationnel, mais les requêtes
échouent toujours par intermittence.

Vérifiez les en-têtes d’identification du relais renvoyés par la sonde de test automatique d’OmniRoute
(voir **Paramètres → Pool de proxys** et les compteurs `relayTested` / `relayAlive`) :

- `x-relay-url` — indique quel backend de relais a répondu.
- `x-relay-mode` — `ts` | `bifrost` | `auto` pour cette requête.
- `x-relay-attempts` — indique combien de sauts de relais ont été tentés avant la réussite.
- `x-relay-fallback` — vaut `true` lorsque la requête a basculé du backend préféré
  vers le relais TypeScript.

Un taux élevé de `x-relay-fallback` associé à une faible valeur de `relayAlive` signifie que le backend
sidecar est défaillant ; vous devez soit le réparer, soit définir la stratégie du backend de relais
sur `ts` (voir `RELAY_BACKEND_STRATEGY.md`).

## Référence de l’API

| Méthode | Chemin                                    | Corps                   | Réussite                                                                                                                                          | Échec                                                                                        |
| ------- | ----------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `POST`  | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` après nouvelle dérivation ; `200 { repaired: false, mode: "noop" }` si le texte brut est déjà présent | `409 { mode: "redeploy" }` irrécupérable ; `400` type autre qu’un relais ; `404` introuvable |

La route de liste `GET /api/settings/proxies` ajoute à chaque élément une propriété
`relayInfo: { isRelay, authMissing, repairMode }` ne contenant aucun secret, afin que le tableau de bord
puisse afficher l’option de réparation sans jamais exposer le jeton.
