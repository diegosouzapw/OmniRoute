`open-sse/config/providerPluginManifest.ts` définit le contrat de plugin de
fournisseur compatible JSON. `open-sse/config/providerPluginManifestRegistry.ts`
lie ce contrat au registre actuel des fournisseurs pour les sidecars tels que
Bifrost, CLIProxyAPI ou un futur routeur Go/Rust. Le registre TypeScript reste la
source de vérité, mais les sidecars peuvent consommer le manifeste sans importer
le code des exécuteurs, les valeurs OAuth par défaut, les en-têtes ou l’état de
l’environnement du processus.

Le même manifeste est disponible via HTTP à l’adresse
`GET /api/v1/provider-plugin-manifest` pour les sidecars qui s’exécutent hors
processus.

OmniRoute communique cette URL à Bifrost et CLIProxyAPI via l’en-tête de requête
`X-OmniRoute-Provider-Manifest-Url`. Définissez
`OMNIROUTE_PROVIDER_MANIFEST_URL` lorsque le sidecar nécessite une URL publique
ou une URL du réseau de conteneurs plutôt que l’origine de la requête locale.

## Actualisation du manifeste

Le point de terminaison HTTP renvoie `Cache-Control: public, max-age=60` et un
`ETag` fort. Un sidecar doit conserver le dernier manifeste validé et envoyer
son ETag dans `If-None-Match` lors de l’actualisation. Une réponse
`304 Not Modified` ne contient aucun corps ; le sidecar conserve son manifeste
mis en cache. Si aucun manifeste validé n’est disponible en cache, le sidecar
doit émettre une requête sans condition au lieu d’accepter une réponse `304`.

## Objectif

Faire évoluer les métadonnées des fournisseurs vers un contrat de plugin afin
que le chemin critique des requêtes puisse à terme être pris en charge par un
sidecar à plus faible latence, tandis qu’OmniRoute conserve la route TypeScript
comme point d’application des politiques et solution de repli. Le manifeste est
additif : il ne modifie pas à lui seul le routage des requêtes.

## Contrat

Le manifeste contient :

- l’identifiant et l’alias du fournisseur
- le format en amont et le nom de l’exécuteur
- le type d’authentification, l’en-tête d’authentification et le préfixe
  d’authentification facultatif
- les métadonnées statiques du point de terminaison
- l’éligibilité au sidecar et les raisons explicites pour lesquelles un
  fournisseur doit rester sur le chemin TS
- les métadonnées de modèle compatibles JSON, telles que la longueur du
  contexte, les indicateurs de vision/raisonnement et les paramètres non pris
  en charge
- les balises de capacité, notamment `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` et `usage-supported`

Le manifeste exclut intentionnellement :

- les secrets clients OAuth et les valeurs secrètes par défaut
- la résolution de l’environnement à l’exécution
- les en-têtes de requête et les assistants d’identifiants publics
- les générateurs d’URL dynamiques
- les fonctions d’exécution
- les mécanismes internes du pool de sessions

## Balises de capacité

`capabilities` est un tableau trié de balises dérivées de l’entrée du registre. Les
intégrateurs doivent le considérer comme la réponse lisible par machine à la question
« que peut faire ce fournisseur ? », plutôt que de relire les sources TypeScript.

| Balise               | Signification                                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `apikey`             | Accepte une clé API (`authType` vaut `apikey` ou `optional`).                                   |
| `oauth`              | Utilise un flux OAuth ou de session.                                                            |
| `responses`          | Expose une URL de base pour l’API Responses d’OpenAI.                                           |
| `passthrough-models` | Sert les modèles directement depuis l’amont au lieu d’un catalogue statique.                    |
| `custom-executor`    | Exécute un exécuteur non standard et reste donc sur le chemin TypeScript.                       |
| `sidecar-candidate`  | Reflète `sidecar.eligible` — peut être envisagé sans risque pour l’importation dans le sidecar. |
| `usage-fetch`        | Dispose d’un récupérateur d’utilisation ou de quota configuré (`getUsageForProvider`).          |
| `usage-supported`    | L’API d’utilisation accepte ce fournisseur (`isSupportedUsageConnection`).                      |

`usage-fetch` sert uniquement à la découverte. Cette balise indique qu’OmniRoute sait
comment lire l’utilisation du fournisseur ; elle n’active pas la récupération, ne modifie
pas la sémantique des quotas et n’implique pas que le widget de quota du Dashboard soit
activé pour le fournisseur — ce widget est contrôlé séparément par
`USAGE_SUPPORTED_PROVIDERS`. La source de vérité est `USAGE_FETCHER_PROVIDERS` dans
`open-sse/services/usage/fetcherProviders.ts`.

Cette liste est indexée par les chaînes acceptées par le répartiteur d’utilisation ; elle
combine donc des identifiants canoniques et des alias, et comporte légèrement plus
d’éléments que le nombre de fournisseurs balisés : les entrées qui ne correspondent pas à
des fournisseurs de chat dans le registre du manifeste (par exemple le fournisseur de
recherche `firecrawl` et le fournisseur ACP `amazon-q`) n’ont aucune entrée de manifeste
à baliser.

`usage-supported` indique si les routes d’utilisation du serveur et du Dashboard acceptent
une connexion pour le fournisseur. Cette balise reflète `isSupportedUsageConnection()`
(`src/lib/usage/providerLimits.ts`) et `supportsProviderQuota()`
(`src/shared/utils/providerQuotaVisibility.ts`), toutes deux contrôlées par
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Contrairement
à `usage-fetch`, elle est émise uniquement pour l’identifiant du fournisseur — le contrôle
à l’exécution utilise `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` sans résolution
d’alias, le manifeste conserve donc la même règle. Les deux balises ont des périmètres
différents : 3 fournisseurs portent uniquement `usage-fetch` (`opencode`,
`opencode-zen`, `xai`) et 1 porte uniquement `usage-supported`
(`xiaomi-mimo-token-plan`) ; l’une n’implique donc pas l’autre.

## Utilisation des sidecars

Les sidecars doivent considérer `sidecar.eligible` comme un indicateur prudent de candidature, et non comme une décision de routage inconditionnelle. La première cible d’importation doit être constituée des fournisseurs utilisant une clé d’API, des endpoints statiques et l’exécuteur par défaut. Les fournisseurs dotés d’exécuteurs web personnalisés, de flux OAuth/de session, de générateurs d’URL dynamiques ou d’une configuration de pool restent sur le chemin de repli TypeScript jusqu’à ce qu’un sidecar implémente un comportement équivalent et que la télémétrie démontre la parité.

Phases de migration suggérées :

1. Générer et valider le manifeste des plugins de fournisseurs à partir du registre TS.
2. Permettre à Bifrost ou à CLIProxyAPI d’importer le manifeste pour les fournisseurs utilisant une clé d’API et des endpoints statiques.
3. Router les fournisseurs éligibles via le sidecar derrière `OMNIROUTE_RELAY_BACKEND`, tout en conservant le chemin de repli TS activé.
4. Ne promouvoir les fournisseurs que lorsque le taux de réussite, la latence p99, le comportement du streaming et la gestion des paramètres non pris en charge correspondent au chemin TS.
5. Ajouter des plugins natifs du sidecar pour les exécuteurs personnalisés, une famille de fournisseurs à la fois.

## Pourquoi ne pas intégrer directement les fournisseurs dans Next

Le frontend Next ne doit pas prendre en charge l’exécution des fournisseurs. Il doit appeler la frontière de l’API. Le backend peut alors décider d’utiliser l’exécuteur TypeScript, Bifrost, CLIProxyAPI ou un futur sidecar natif. Cela permet de centraliser la signature des requêtes, les vérifications de liste d’autorisation, la politique de base de données et le comportement de repli avant toute délégation à un sidecar.
