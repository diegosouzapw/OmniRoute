## Vue d’ensemble

Toutes les routes de l’API de gestion d’OmniRoute sont classées dans l’un des trois niveaux de protection. Cette classification est statique, définie dans `src/server/authz/routeGuard.ts`, et évaluée avant l’exécution de toute autre branche d’authentification.

## Niveaux

### Niveau 1 — LOCAL_ONLY

**Appliqué par :** `isLocalOnlyPath(path)` → vérification de l'hôte de bouclage
**Contournement :** Aucun par défaut. Exception étroite pour les chemins dans
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` lorsque la requête contient une clé API valide
avec la portée `manage` (voir [Exception de portée manage](#manage-scope-carve-out)).

Ces routes génèrent des processus enfants ou exécutent du code à l'exécution. Les exposer au
trafic non-loopback permettrait à un attaquant ayant obtenu un JWT valide (par exemple,
via un tunnel Cloudflared/Ngrok) de déclencher la génération de processus — une classe de CVE
connue ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ce qu'est GHSA-fhh6-4qxv-rpqj (la classe d'attaque) :** un serveur de gestion/agent
expose un point de terminaison qui lance un sous-processus (`npm install`, `node`, un navigateur,
un proxy, `git`, `tar`, …). Si ce point de terminaison est accessible depuis l'extérieur de l'hôte — parce que
l'opérateur a placé OmniRoute derrière un tunnel nginx/Cloudflare/Tailscale et qu'un JWT
a fuité, ou que l'authentification a été mal configurée — l'attaquant transforme "appeler une API" en "exécuter une
commande sur l'hôte" (exécution de code à distance). OmniRoute résout ce problème en imposant une
**vérification inconditionnelle de l'hôte de bouclage, avant toute vérification d'authentification**, sur chaque
route capable de générer des processus : un jeton ayant fui via un tunnel ne peut toujours pas atteindre la génération.

**L'ensemble complet LOCAL_ONLY.** La source faisant autorité est
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` dans
`src/server/authz/routeGuard.ts` ; le tableau ci-dessous reflète l'état actuel. La
porte `check-route-guard-membership` énumère chaque `route.ts` sous les
préfixes capables de générer des processus et fait échouer la CI si l'un d'eux n'est pas classé comme local-only.

#### Exemption de portée de gestion

Un sous-ensemble de chemins LOCAL_ONLY PEUT également être accédé depuis une adresse non-loopback si et seulement si la requête contient un `Authorization: Bearer <api-key>` dont les métadonnées incluent la portée `manage` (ou `admin`). L'exemption est explicitement contrôlée par chemin via `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` afin que la valeur par défaut pour tout nouveau chemin LOCAL_ONLY reste en strict-loopback. Les requêtes non authentifiées et les requêtes avec des clés sans portée de gestion sont toujours rejetées avec `403 LOCAL_ONLY`.

Aujourd'hui, le seul préfixe contournable est `/api/mcp/`. `/api/cli-tools/runtime/` et `/api/services/` sont intentionnellement exclus car ils peuvent lancer des sous-processus arbitraires (`npm install`, `node`), ce qui correspond exactement à la classe de CVE que le niveau LOCAL_ONLY vise à prévenir.

**#7895 — Portée étroite `mcp:connect` :** l'exemption `/api/mcp/` accepte ÉGALEMENT une clé Bearer détenant la portée étroite `mcp:connect` (`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), vérifiée via `hasMcpConnectOrManageScope()` dans `src/server/authz/policies/management.ts`. Ceci est limité à `/api/mcp/` UNIQUEMENT — `mcp:connect` n'accorde rien sur aucune autre route de gestion (y compris tout autre préfixe de contournement LOCAL_ONLY, si jamais un était ajouté), et il est délibérément exclu de `MANAGEMENT_API_KEY_SCOPES`. Une clé détenant `manage`/`admin` passe toujours l'exemption exactement comme avant ; `mcp:connect` est une alternative à privilèges réduits pour les appelants distants uniquement MCP qui ne devraient pas avoir besoin d'un accès de gestion étendu.

| Requête                                          | Chemin                     | Résultat                     |
| :----------------------------------------------- | :------------------------- | :--------------------------- |
| Non-loopback, pas de Bearer                      | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Non-loopback, Bearer avec portée `manage`        | `/api/mcp/*`               | Autorisé                     |
| Non-loopback, Bearer avec portée `mcp:connect`   | `/api/mcp/*`               | Autorisé                     |
| Non-loopback, Bearer sans `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY               |
| Non-loopback, Bearer avec portée `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Non-loopback, Bearer avec portée `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY               |
| Loopback, avec/sans Bearer                       | tout LOCAL_ONLY            | Autorisé (le contrôle passe) |

#### Guide de l'opérateur et audit

Si vous exécutez OmniRoute derrière un proxy inverse ou un tunnel (nginx, Caddy, Cloudflare Tunnel, Tailscale, Ngrok), la vérification loopback protège toujours les routes capables de lancer des processus ci-dessus — une requête dont l'adresse client n'est pas loopback est rejetée avec `403 LOCAL_ONLY` **avant l'exécution de l'authentification**, de sorte qu'un JWT divulgué ne peut pas atteindre un lancement de processus. Deux responsabilités de l'opérateur demeurent :

- **Ne "réparez" pas une erreur 403 en falsifiant l'IP client en loopback.** Définir `X-Forwarded-For: 127.0.0.1`, ou un proxy qui réécrit l'adresse source en loopback, rouvre exactement la classe de RCE que ce niveau ferme. Exposez le tableau de bord/API via le proxy — jamais les routes capables de lancer des processus.
- **Maintenez le contournement de la portée de gestion minimal.** Seul `/api/mcp/` est contournable, et uniquement avec une clé API de portée `manage`. Les `SPAWN_CAPABLE_PREFIXES` ne peuvent jamais être ajoutés à la liste de contournement — le schéma zod les rejette et `isLocalOnlyBypassableByManageScope` les refuse à l'exécution (défense en profondeur), ce qui est ce que le tableau de bord entend par "ne peut pas être rendu contournable". Les routes capables de lancer des processus à segment dynamique et à chemin statique sous `/api/providers/` (par exemple `/login`, `/refresh-cursor`) sont couvertes par le compagnon basé sur des expressions régulières `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` dans `src/shared/constants/spawnCapablePrefixes.ts`, et non par le tableau plat `SPAWN_CAPABLE_PREFIXES` — le tableau plat devrait couvrir l'intégralité du préfixe `/api/providers/` pour les intercepter, élargissant excessivement une arborescence de routes que les tableaux de bord distants utilisent légitimement pour le CRUD des fournisseurs.

**Audit d'accès** — pour vérifier que rien d'extérieur à l'hôte n'atteint ces routes :

- Ouvrez l'**Inventaire des autorisations** sur `/dashboard/settings/security` : il affiche la liste des préfixes LOCAL_ONLY en direct, quels préfixes sont contournables, et l'ensemble des éléments capables d'être générés à la compilation ("ne peuvent pas être rendus contournables").
- Recherchez dans les journaux de votre proxy inverse / d'accès les préfixes ci-dessus associés à une adresse client non-loopback. Tout résultat qui a renvoyé `200` au lieu de `403 LOCAL_ONLY` signifie que le proxy masque la véritable adresse IP du client — corrigez le proxy.
- Un `403 LOCAL_ONLY` dans les journaux d'OmniRoute pour l'un de ces chemins signifie que la protection fonctionne comme prévu, et non une erreur à supprimer.

### Niveau 2 — ALWAYS_PROTECTED

**Appliqué par :** `isAlwaysProtectedPath(path)` → ignore le contournement `requireLogin=false`
**Contournement :** Aucun lorsque `requireLogin=false` ; JWT toujours requis

Ces routes sont destructrices ou irréversibles. Les autoriser dans une installation "sans mot de passe" signifierait que n'importe qui sur le même réseau local pourrait effacer la base de données ou arrêter le processus du serveur.

| Chemin                                    | Raison                                                                      |
| :---------------------------------------- | :-------------------------------------------------------------------------- |
| `/api/shutdown`                           | Termine le processus du serveur                                             |
| `/api/settings/database`                  | Exportation, importation et effacement de la base de données                |
| `/api/db-backups`                         | Accès aux archives de sauvegarde complète de la base de données             |
| `/api/settings/export-json`               | Exporte le blob de paramètres complet (y compris les secrets)               |
| `/api/settings/import-json`               | Remplace le blob de paramètres complet                                      |
| `/api/providers/health-autopilot/actions` | Exécute les actions de remédiation de l'autopilote                          |
| `/api/settings/obsidian`                  | Crée des identifiants WebDAV réutilisables pour toute racine de coffre-fort |

**Réponse en cas de violation :** `401 Authentification requise`

`/api/settings/obsidian` couvre son enfant `/webdav` : `POST` pointe le service de fichiers WebDAV — servi par la couche Node personnalisée avant Next.js, en dehors de ce pipeline — vers une racine choisie par l'appelant et renvoie des identifiants Basic fraîchement créés, `DELETE` les fait pivoter, et le `POST` parent stocke le jeton de l'API REST d'Obsidian. GHSA-62vw n'a masqué que la révélation du mot de passe `GET` ; l'émission était toujours au niveau "fail-open" (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` refuse en outre un coffre-fort qui est, se trouve à l'intérieur, ou contient le répertoire de données.

### Le démarrage d'une nouvelle installation est en boucle locale uniquement — par pair réel, pas par `Host`

Sans mot de passe de gestion configuré (et sans `INITIAL_PASSWORD`), `isAuthRequired()` dans `src/shared/utils/apiAuth.ts` maintient le démarrage anonyme ouvert **uniquement pour les pairs en boucle locale**. La boucle locale est décidée à partir des signaux de pair de confiance, dans l'ordre : le pair TCP réel estampillé par jeton (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ce que la politique voit), le verdict `AUTHZ_HEADER_PEER_LOCALITY` propre au pipeline (ce que les gestionnaires de route voient, fiable uniquement tant que `OMNIROUTE_PEER_STAMP_TOKEN` est défini), ou un pair de socket réel pour les appelants directs. `Host` / `nextUrl.hostname` ne sont jamais consultés, et l'écriture du premier mot de passe (`POST /api/settings/require-login`) est soumise à la même contrainte plutôt que d'être ouverte à chaque pair réseau (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmet explicitement son propre verdict `peerContext`, de sorte que les en-têtes de la requête ORIGINALE (avant suppression) ne le décident jamais.

### Niveau 3 — GESTION (par défaut)

Toutes les autres routes de gestion. Authentification requise sauf si `requireLogin=false` est configuré. Les jetons CLI peuvent authentifier ces routes (boucle locale + HMAC valide).

## Ordre d’évaluation

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → poursuivre
     → hors loopback, Bearer avec portée manage
        ET isLocalOnlyBypassableByManageScope    → autoriser (management_key)
     → sinon                                     → rejeter avec 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → autoriser (system)
  3. hasValidCliToken(headers)?
     → autoriser (cli) [loopback + vérification HMAC avec timingSafeEqual]
  4. isAlwaysProtectedPath(path) ou requireLogin=true?
     → isDashboardSessionAuthenticated?
        → autoriser (dashboard_session)
     → Bearer avec portée manage sur un chemin non contournable ?
        → autoriser (management_key)
     → rejeter avec 401/403
  5. requireLogin=false?
     → autoriser (anonymous)
```

La branche avec portée manage de l’étape 1 est le seul chemin authentifié pouvant satisfaire une route
LOCAL_ONLY ; le mode d’échec du backend d’authentification renvoie 503 (et non 403), afin qu’une
base de données expirée ne soit pas silencieusement rétrogradée en « refus ».

## Ajout d’une nouvelle route capable de lancer des processus

1. Ajoutez le préfixe du chemin à `LOCAL_ONLY_API_PREFIXES` dans
   `src/server/authz/routeGuard.ts`
2. Ajoutez un test dans `tests/unit/authz/routeGuard.test.ts` vérifiant que
   `isLocalOnlyPath()` renvoie true pour le nouveau préfixe
3. **Ne sautez jamais cette étape** — consultez la règle absolue nº 15 dans `CLAUDE.md`
4. Décidez : cette route doit-elle ÉGALEMENT figurer dans `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ?
   La réponse par défaut est **non**. N’y consentez que lorsque la route peut être exposée en toute sécurité à un
   détenteur de la portée manage (c.-à-d. qu’elle ne lance PAS de code arbitraire contrôlé par l’utilisateur).

## Ajout d’un chemin contournable avec la portée manage

1. Vérifiez que la route n’exécute pas de code ou de commandes fournis par l’utilisateur. Si c’est
   le cas, arrêtez-vous — cette exception n’est pas l’outil approprié.
2. Ajoutez le préfixe à `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` dans
   `src/server/authz/routeGuard.ts`
3. Ajoutez une couverture dans `tests/unit/authz/management-policy.test.ts` pour les quatre
   formes de requêtes : sans Bearer (403), Bearer avec portée manage (autorisation), Bearer sans portée manage
   (403), ainsi que la régression par préfixe vérifiant que `/api/cli-tools/runtime/*` reste
   strictement limité au loopback, même avec un Bearer doté de la portée manage.

## Documentation des niveaux de sécurité dans OpenAPI

Lors de l’ajout d’une nouvelle route à `docs/openapi.yaml`, appliquez l’extension
fournisseur correspondante si la route est classifiée par `routeGuard.ts` :

| Classification de routeGuard.ts               | Annotation YAML                | Application                                             |
| --------------------------------------------- | ------------------------------ | ------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                     | `x-loopback-only: true`        | Blocage inconditionnel hors loopback                    |
| `ALWAYS_PROTECTED_API_PATHS`                  | `x-always-protected: true`     | Authentification requise même avec `requireLogin=false` |
| Route interne d’administration/débogage       | `x-internal: true`             | Masquée de /dashboard/api-endpoints par défaut          |
| Aucune (publique / authentification standard) | (aucune annotation nécessaire) | Accès standard contrôlé par `requireLogin`              |

### Validation

Deux scripts garantissent la cohérence entre les annotations YAML et `routeGuard.ts` :

- `scripts/check/check-openapi-coverage.mjs` — échoue si la couverture est < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — échoue si les annotations `x-loopback-only` ou
  `x-always-protected` divergent des constantes définies à la compilation

Les deux scripts s’exécutent dans le hook de précommit et dans la CI.

### Règle relative aux faux positifs

Si `x-always-protected` ou `x-loopback-only` est annoté sur une route qui ne figure PAS dans
la constante de `routeGuard.ts`, le script de couverture échoue. La correction consiste toujours à aligner le
YAML sur ce que `routeGuard.ts` applique réellement — et non à ajouter des routes à `routeGuard.ts`
sans également implémenter la logique d’application.
