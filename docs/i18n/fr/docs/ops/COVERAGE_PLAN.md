## Référence

Il existe plusieurs chiffres de couverture selon la manière dont le rapport est calculé. Pour la planification, un seul d’entre eux est utile.

| Métrique              | Périmètre                                         | Instructions / Lignes | Branches | Fonctions | Remarques                                                       |
| --------------------- | ------------------------------------------------- | --------------------: | -------: | --------: | --------------------------------------------------------------- |
| Historique            | Ancien `npm run test:coverage`                    |                79.42% |   75.15% |    67.94% | Surévalué : compte les fichiers de test et exclut `open-sse`    |
| Diagnostic            | Sources uniquement, hors tests et hors `open-sse` |                68.16% |   63.55% |    64.06% | Utile uniquement pour isoler `src/**`                           |
| Référence recommandée | Sources uniquement, hors tests et avec `open-sse` |                82.58% |   75.22% |    84.23% | Il s’agit de la référence à améliorer pour l’ensemble du projet |

La référence recommandée est le chiffre à optimiser.

## Règles

- Les objectifs de couverture s’appliquent aux fichiers sources, pas à `tests/**`.
- `open-sse/**` fait partie du produit et doit rester inclus dans le périmètre.
- Le nouveau code ne doit pas réduire la couverture dans les zones modifiées.
- Privilégier les tests du comportement et des résultats des branches plutôt que les détails d’implémentation.
- Privilégier les bases de données SQLite temporaires et les petites données de test plutôt que les mocks étendus pour `src/lib/db/**`.

## Ensemble actuel de commandes

- `npm run test:coverage`
  - Contrôle principal de la couverture des sources pour la suite de tests unitaires
  - Génère `text-summary`, `html`, `json-summary` et `lcov`
- `npm run coverage:report`
  - Rapport détaillé fichier par fichier à partir de la dernière exécution
- `npm run test:coverage:legacy`
  - Uniquement destiné aux comparaisons historiques

## Politique de progression par paliers

Mettez à jour les seuils de `npm run test:coverage` uniquement lorsque le projet dépasse réellement le palier suivant avec une marge confortable.

**Seuil actuel :** `npm run test:coverage` impose **60 instructions / 60 lignes / 60 fonctions / 60 branches** (la métrique a été recalculée lors de la phase 6A.1 des contrôles qualité — la valeur de référence précédente de 82,58 % était artificiellement élevée, car elle comptabilisait les fichiers de test et excluait `open-sse`). La commande `test:coverage:legacy` conserve l’ancienne métrique 50/50/50 à des fins de comparaison historique.

Pour effectuer des vérifications ponctuelles des seuils sur le dernier rapport, utilisez :

```bash
node scripts/check/test-report-summary.mjs --threshold 75
```

Séquence de progression recommandée (l’ordre est `instructions-lignes / branches / fonctions`) :

1. 55/60/55
2. 60/62/58
3. 65/64/62
4. 70/66/66
5. 75/70/72 <-- seuil actuel (75/70/75)
6. 80/75/78

Le prochain objectif de progression est `80/75/78`, une fois que la couverture des branches se maintient au-dessus de 78 % pendant deux exécutions consécutives.

## Lacune connue

La commande de couverture actuelle mesure la suite principale de tests unitaires Node et inclut le code source qu’elle atteint, notamment `open-sse`. Elle ne fusionne pas encore la couverture Vitest dans un rapport unifié. Cette fusion méritera d’être effectuée ultérieurement, mais elle ne constitue pas un obstacle au démarrage de la progression de 60 % vers 80 %.
