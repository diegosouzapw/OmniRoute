Utilisez ce guide pour choisir la boucle de développement fiable la plus courte pour une pull request. Il ne
remplace pas les documents d’architecture et de sécurité propres à chaque domaine liés ci-dessous ; il relie chaque type
de modification courant à ses contrats, ses vérifications ciblées et sa couverture CI.

## Le parcours suivi par chaque modification

1. **Choisissez la branche de base avant toute modification.** Identifiez la branche `release/v*` active la plus récente et créez votre branche à partir
   de sa pointe. Ciblez cette branche, et non `main`. Si un gel de version est en cours, ne ciblez pas la branche
   gelée ; utilisez le prochain cycle actif décrit dans
   [Modèle de branches et de versions](BRANCHING_MODEL.md).
2. **Nommez les contrats.** Identifiez chaque catalogue, schéma, artefact généré, API publique ou interface
   utilisateur affecté par la modification. Le tableau ci-dessous indique l’ensemble de départ minimal.
3. **Écrivez ou mettez à jour des tests ciblés.** Les modifications du code de production dans `src/`, `open-sse/`, `electron/` ou
   `bin/` nécessitent un test automatisé dans la même PR. Exécutez les fichiers de test les plus restreints qui valident
   le comportement, puis les contrôles ciblés indiqués.
4. **Laissez la CI exécuter la matrice complète.** L’ensemble des segments de tests unitaires, Vitest, le seuil progressif de couverture et
   le build de production sont exécutés sur la PR. N’exécutez localement une suite étendue que lorsqu’un échec ciblé indique
   un impact plus large ou lorsque la modification couvre plusieurs sous-systèmes.
5. **Réconciliez les modifications avant la revue.** Récupérez la branche de base active, examinez ses nouveaux commits ainsi que votre diff par rapport
   à celle-ci, puis rebasez ou fusionnez la branche de base conformément au workflow des contributeurs. Résolvez les conflits de fichiers
   générés et de catalogues depuis leur source, régénérez-les, réexécutez la boucle ciblée et confirmez que la
   PR cible toujours la branche de version active.
6. **Consignez les preuves.** Dans le modèle de PR, indiquez les commandes exécutées, chaque fichier de test ajouté ou modifié,
   les migrations ou feature flags, ainsi que toute validation réservée à la CI encore en attente.

## Parcours recommandés par type de modification

Les commandes ci-dessous constituent les vérifications ciblées minimales, et non une autorisation d’omettre un test couvrant directement le
comportement que vous avez modifié.

### Fournisseur

**Contrats**

- Définition du fournisseur dans `src/shared/constants/providers/` et sa composition dans
  `src/shared/constants/providers.ts`.
- Modèles et capacités dans `open-sse/config/providerRegistry.ts` ou dans les fichiers de registre qui en ont été extraits.
- Sélection de l’exécuteur/du traducteur, configuration OAuth ou par clé d’API, ressources du tableau de bord et référence
  fournisseur générée, le cas échéant.
- Les identifiants publics doivent utiliser `resolvePublicCred()` ; les réponses d’erreur doivent utiliser les fonctions d’assistance partagées
  de nettoyage des erreurs. Consultez `docs/security/PUBLIC_CREDS.md` (git ; non compilé dans `/docs`) et
  [Nettoyage des erreurs](../security/ERROR_SANITIZATION.md).

**Boucle ciblée**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # lorsque le catalogue change ; commitez le diff généré
npm run lint
```

Testez également chaque famille de requêtes affectée : chat, Responses, images, embeddings, audio ou vidéo.
Examinez les différences des catalogues générés et des fichiers de référence comme des modifications de contrat ; ne les acceptez pas aveuglément.

### Routage

**Contrats**

- Valeurs publiques des stratégies et métadonnées de l’interface utilisateur dans `src/shared/constants/routingStrategies.ts`.
- Répartition et ordre sous `open-sse/services/combo.ts` et `open-sse/services/combo/`.
- Schémas des combinaisons, persistance, état de résilience, capacités des modèles et contrôles d’API/d’interface utilisateur.
- [Moteur Auto-Combo](../routing/AUTO-COMBO.md) et documentation sur la résilience lorsque le comportement change.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # modifications de stratégie ou de répartition
npm run check:known-symbols      # modifications de l’enregistrement des stratégies
npm run lint
```

Utilisez localement des tests déterministes avec services en amont simulés. Les tests rapides de combinaisons réelles nécessitent des identifiants et sont
manuels ; ils ne remplacent pas la CI.

### UI / UX

**Contrats**

- Route/page Next.js et limites des composants partagés sous `src/app/` et
  `src/shared/components/`.
- Formes des réponses d’API, états de chargement/vide/erreur, comportement au clavier et avec un lecteur d’écran,
  mise en page adaptative, thèmes et extension des locales.
- Chaînes sources en anglais de l’interface utilisateur dans `src/i18n/messages/en.json` ; ne codez pas en dur de nouveau texte destiné aux utilisateurs.

**Boucle ciblée**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Exécutez l’application pour les modifications d’interaction ou visuelles et vérifiez les fenêtres d’affichage étroites comme larges. La CI exécute le
build de production et les suites plus larges ; le comportement visuel nécessite toujours un composant ciblé, un test Playwright
ou une vérification manuelle documentée adaptée à la modification.

### i18n

**Contrats**

- `src/i18n/messages/en.json` est la source de l’interface utilisateur ; `config/i18n.json` est la source des locales.
- Les catalogues de la CLI sont conservés séparément sous `bin/cli/locales/`.
- Préservez exactement les paramètres substituables et les balises ICU. Ne traduisez pas les noms de produits/fournisseurs/modèles,
  les noms de protocoles et d’en-têtes, les commandes, les identifiants de code/JSON, les URL, les variables d’environnement ni
  les termes protégés tels que `OmniRoute`, `OAuth`, `MCP` et `A2A`. La liste source actuelle est
  `scripts/i18n/glossary/protected-terms.json`.

**Boucle ciblée**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # lorsque les chaînes/catalogues de la CLI changent
npm run lint
```

Il s’agit de recommandations pour le système existant, et non d’une invitation à étendre ses outils ou son modèle de clés.
Maintenez les correctifs i18n strictement ciblés pendant la conception du système de remplacement. N’exécutez pas de commandes de traduction
faisant appel à des services externes, sauf si la tâche exige explicitement des traductions générées et
que vous avez examiné le diff qui en résulte.

### CLI

**Contrats**

- Commandes et options publiques dans `bin/cli/`, commandes d’API générées, codes de sortie, stdout/stderr et
  structures de sortie JSON, comportement de la configuration/de l’environnement et fichiers empaquetés.
- Les chaînes de l’interface CLI destinées aux utilisateurs doivent utiliser la couche i18n de la CLI et maintenir les catalogues `en`/`pt-BR` alignés.
- Conserver Node comme environnement d’exécution pris en charge ainsi que le contrat du binaire publié.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # modifications de la CLI générée/regroupée
npm run check:pack-policy     # modifications de la surface du paquet
npm run lint
```

Utilisez la commande exacte dans un répertoire de données temporaire lorsque le comportement dépend de l’analyse, des fichiers ou du code
de sortie. La CI effectue les vérifications plus larges des artefacts du paquet et de l’écosystème.

### Base de données

**Contrats**

- Modules de domaine sous `src/lib/db/` ; importez directement les modules spécifiques (l’ancienne couche de réexportation `localDb.ts` a été supprimée).
- Migrations SQL numérotées et idempotentes sous `src/lib/db/migrations/`, sécurité des transactions, comportement de
  mise à niveau, index et chaque appelant affecté par le schéma.
- Les routes et les gestionnaires n’exécutent jamais directement de SQL brut.

**Boucle ciblée**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Lors de l’ajout d’une migration, testez à la fois une nouvelle base de données et la mise à niveau depuis le schéma précédent. Les tests de base de données
doivent fermer les handles et appeler `resetDbInstance()` pendant le nettoyage. Exécutez `npm run test:bun:db` uniquement lorsque
le chemin de l’adaptateur Bun sans garantie absolue change ; Node reste la référence.

### Build / déploiement

**Contrats**

- Manifestes et fichier de verrouillage racine et des workspaces, `scripts/build/`, assemblage standalone de Next.js, contenu du paquet `dist/`,
  métadonnées de plateforme Electron, workflows de CI et sentinelles de déploiement.
- Les plages de versions Node prises en charge et l’utilisation autorisée de Bun dans `CLAUDE.md` doivent rester intactes.
- Les artefacts de build restent non suivis ; les politiques relatives aux dépendances, aux licences, aux workflows et aux paquets s’appliquent.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # modifications des dépendances ou du fichier de verrouillage
npm run check:pack-policy      # modifications de la surface du paquet publié
npm run lint
```

Utilisez `npm run build` localement uniquement lorsque la modification affecte la compilation, l’assemblage standalone, les ressources
ou le regroupement pour l’exécution. Utilisez `npm run build:release` uniquement pour la validation de release/déploiement. Le build de la CI constitue
le signal multiplateforme final ; les modifications Electron propres à une plateforme nécessitent le build ciblé correspondant
ou une preuve issue d’un test de smoke.

## Boucle locale et CI

| À exécuter localement pour chaque correctif                                                                                        | La CI fournit une vue d’ensemble                                                           |
| ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Tests directs du comportement et contrôles de catégorie ci-dessus                                                                  | Suite complète de tests unitaires partitionnée et tests en série                           |
| `npm run lint`                                                                                                                     | Suites Vitest et seuils progressifs de couverture/qualité                                  |
| Vérification des types ou build uniquement si le contrat concerné l’exige                                                          | Build de production, sécurité, documentation, dépendances et contrôles de politique des PR |
| Interactions manuelles/vérifications en conditions réelles uniquement lorsque l’automatisation ne peut pas prouver le comportement | Vérifications d’intégration inter-jobs et de plateformes configurées par le workflow       |

Une boucle ciblée au vert constitue une preuve concernant le contrat modifié, et non la garantie que les vérifications CI sans rapport
réussiront. Inversement, ne faites pas attendre chaque modification locale jusqu’à l’exécution de la matrice complète du dépôt.

## Liste de contrôle de réconciliation

Avant de demander une revue :

- Confirmez que la base de la PR est toujours la branche `release/v*` active la plus élevée.
- Récupérez cette base et examinez les commits intégrés depuis la création de votre branche.
- Examinez `git diff <active-base>...HEAD` afin de repérer les modifications accidentelles ou générées.
- Résolvez les conflits de catalogue et de documents générés en mettant à jour la source et en régénérant la sortie.
- Réexécutez chaque test/contrôle ciblé répertorié dans la description de la PR après la réconciliation.
- N’affaiblissez jamais les assertions et ne supprimez jamais les tests requis uniquement pour vous adapter à une base qui a évolué.

Pour les règles relatives au gel des versions et au changement de cible, consultez
[Modèle de création de branches et de publication](BRANCHING_MODEL.md). Pour l’inventaire complet de la CI, consultez
[Référence des contrôles qualité](../architecture/QUALITY_GATES.md).
