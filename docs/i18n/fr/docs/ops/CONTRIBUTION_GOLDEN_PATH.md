Utilisez ce guide pour choisir la boucle de développement fiable la plus courte pour une pull request. Il ne
remplace pas les documents d’architecture et de sécurité propres à chaque domaine, dont les liens figurent
ci-dessous ; il associe chaque type de modification courant à ses contrats, à ses vérifications ciblées et à sa couverture CI.

## Le parcours suivi par chaque modification

1. **Choisissez la branche de base avant toute modification.** Recherchez la branche `release/v*` active la plus récente et créez votre branche à partir
   de son dernier commit. Ciblez cette branche, et non `main`. Si un gel de version est en cours, ne ciblez pas la branche
   gelée ; utilisez le prochain cycle actif décrit dans
   [Modèle de gestion des branches et des versions](BRANCHING_MODEL.md).
2. **Nommez les contrats.** Identifiez chaque catalogue, schéma, artefact généré, API publique ou interface
   utilisateur affecté par la modification. Le tableau ci-dessous fournit l’ensemble initial minimal.
3. **Écrivez ou mettez à jour des tests ciblés.** Les modifications de production dans `src/`, `open-sse/`, `electron/` ou
   `bin/` nécessitent un test automatisé dans la même PR. Exécutez les fichiers de test minimaux qui démontrent
   le comportement, puis les contrôles ciblés indiqués.
4. **Laissez la CI exécuter la matrice étendue.** L’ensemble des partitions de tests unitaires, Vitest, le seuil progressif de couverture et
   le build de production s’exécutent sur la PR. N’exécutez une suite étendue localement que lorsqu’un échec ciblé indique
   un impact plus large ou lorsque la modification couvre plusieurs sous-systèmes.
5. **Réconciliez les changements avant la revue.** Récupérez la branche de base active, examinez ses nouveaux commits ainsi que votre diff par rapport
   à celle-ci, puis rebasez ou fusionnez la branche de base conformément au workflow des contributeurs. Résolvez les conflits de fichiers générés
   et de catalogues à partir de leur source, régénérez-les, réexécutez la boucle ciblée et confirmez que la
   PR cible toujours la branche de version active.
6. **Consignez les preuves.** Dans le modèle de PR, indiquez les commandes exécutées, chaque fichier de test ajouté ou modifié,
   les migrations ou feature flags, ainsi que toute validation réservée à la CI qui reste en attente.

## Parcours recommandés par type de modification

Les commandes ci-dessous constituent les vérifications ciblées minimales ; elles ne dispensent pas d’exécuter un test couvrant directement le
comportement que vous avez modifié.

### Fournisseur

**Contrats**

- Définition du fournisseur dans `src/shared/constants/providers/` et sa composition dans
  `src/shared/constants/providers.ts`.
- Modèles et fonctionnalités dans `open-sse/config/providerRegistry.ts` ou dans les fichiers de registre qui en ont été extraits.
- Sélection de l’exécuteur/du traducteur, configuration OAuth ou par clé d’API, ressources du tableau de bord et référence
  générée du fournisseur, le cas échéant.
- Les identifiants publics doivent utiliser `resolvePublicCred()` ; les réponses d’erreur doivent utiliser les utilitaires partagés
  d’assainissement des erreurs. Consultez `docs/security/PUBLIC_CREDS.md` (git ; non compilé dans `/docs`) et
  [Assainissement des erreurs](../security/ERROR_SANITIZATION.md).

**Boucle ciblée**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # lorsque le catalogue change ; validez le diff généré
npm run lint
```

Testez également chaque famille de requêtes affectée : chat, Responses, images, embeddings, audio ou vidéo.
Examinez les diffs générés des catalogues et des références comme des modifications de contrat ; ne les acceptez pas aveuglément.

### Routage

**Contrats**

- Valeurs publiques des stratégies et métadonnées de l’interface utilisateur dans `src/shared/constants/routingStrategies.ts`.
- Répartition et ordre d’exécution dans `open-sse/services/combo.ts` et `open-sse/services/combo/`.
- Schémas des combos, persistance, état de résilience, fonctionnalités des modèles et contrôles d’API/d’interface utilisateur.
- [Moteur Auto-Combo](../routing/AUTO-COMBO.md) et documentation sur la résilience lorsque le comportement change.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # modifications de stratégie ou de répartition
npm run check:known-symbols      # modifications de l’enregistrement des stratégies
npm run lint
```

Utilisez localement des tests déterministes avec des services en amont simulés. Les tests smoke de combos en conditions réelles nécessitent des identifiants et sont
manuels ; ils ne remplacent pas la CI.

### UI / UX

**Contrats**

- Limites des routes/pages Next.js et des composants partagés dans `src/app/` et
  `src/shared/components/`.
- Structures des réponses d’API, états de chargement/vide/erreur, comportement au clavier et avec les lecteurs d’écran,
  mise en page responsive, thèmes et extension des locales.
- Chaînes sources anglaises de l’interface utilisateur dans `src/i18n/messages/en.json` ; ne codez pas en dur de nouveau texte destiné aux utilisateurs.

**Boucle ciblée**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Exécutez l’application pour les modifications d’interaction ou d’apparence et vérifiez les viewports étroits comme larges. La CI exécute le
build de production et les suites plus étendues ; le comportement visuel nécessite néanmoins un composant ciblé, Playwright,
ou une vérification manuelle documentée adaptée à la modification.

### i18n

**Contrats**

- `src/i18n/messages/en.json` est la source de l’interface utilisateur ; `config/i18n.json` est la source des locales.
- Les catalogues de la CLI se trouvent séparément dans `bin/cli/locales/`.
- Préservez exactement les placeholders et les balises ICU. Ne traduisez pas les noms de produits/fournisseurs/modèles,
  les noms de protocoles et d’en-têtes, les commandes, les identifiants de code/JSON, les URL, les variables d’environnement ni
  les termes protégés tels que `OmniRoute`, `OAuth`, `MCP` et `A2A`. La liste source actuelle est
  `scripts/i18n/glossary/protected-terms.json`.

**Boucle ciblée**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # lorsque les chaînes/catalogues de la CLI changent
npm run lint
```

Il s’agit de recommandations pour le système existant, et non d’une invitation à étendre ses outils ou son modèle de clés.
Limitez les correctifs i18n à des changements chirurgicaux pendant la conception du système de remplacement. N’exécutez pas de commandes de traduction
qui appellent des services externes, sauf si la tâche exige explicitement des traductions générées et
si vous avez examiné le diff produit.

### CLI

**Contrats**

- Commandes publiques et options dans `bin/cli/`, commandes d’API générées, codes de sortie, stdout/stderr et
  structures de sortie JSON, comportement de la configuration/de l’environnement et fichiers inclus dans le paquet.
- Les chaînes de la CLI destinées aux utilisateurs doivent utiliser la couche i18n de la CLI et maintenir les catalogues `en`/`pt-BR` alignés.
- Préserver Node comme environnement d’exécution pris en charge ainsi que le contrat du binaire publié.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # modifications de la CLI générée/regroupée
npm run check:pack-policy     # modifications de la surface du paquet
npm run lint
```

Utilisez la commande exacte dans un répertoire de données temporaire lorsque le comportement dépend de l’analyse syntaxique, des fichiers ou du code
de sortie. La CI effectue les vérifications plus larges des artefacts de paquet et de l’écosystème.

### Base de données

**Contrats**

- Modules de domaine sous `src/lib/db/` ; importez directement les modules spécifiques (l’ancienne couche de réexportation `localDb.ts` a été supprimée).
- Migrations SQL numérotées et idempotentes sous `src/lib/db/migrations/`, sécurité des transactions, comportement lors des mises à niveau,
  index et chaque appelant affecté par le schéma.
- Les routes et les gestionnaires n’exécutent jamais directement de SQL brut.

**Boucle ciblée**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Lors de l’ajout d’une migration, testez à la fois une nouvelle base de données et une mise à niveau depuis le schéma précédent. Les tests de base de données
doivent fermer les handles et appeler `resetDbInstance()` pendant le nettoyage. Exécutez `npm run test:bun:db` uniquement lorsque
le chemin de l’adaptateur Bun en mode best effort change ; Node reste la référence.

### Build / déploiement

**Contrats**

- Manifestes et fichier de verrouillage à la racine et dans les espaces de travail, `scripts/build/`, assemblage autonome Next.js, contenu du paquet `dist/`,
  métadonnées de plateforme Electron, workflows de CI et sentinelles de déploiement.
- Les plages de versions Node prises en charge et l’utilisation de Bun figurant sur la liste d’autorisation dans `CLAUDE.md` doivent rester intactes.
- Les artefacts de build restent non suivis ; les politiques relatives aux dépendances, aux licences, aux workflows et aux paquets s’appliquent.

**Boucle ciblée**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # modifications des dépendances ou du fichier de verrouillage
npm run check:pack-policy      # modifications de la surface du paquet publié
npm run lint
```

Utilisez `npm run build` localement uniquement lorsque la modification affecte la compilation, l’assemblage autonome, les ressources
ou le regroupement à l’exécution. Utilisez `npm run build:release` uniquement pour la validation d’une version/d’un déploiement. Le build de la CI constitue
le signal multiplateforme final ; les modifications Electron spécifiques à une plateforme nécessitent le build ciblé correspondant
ou des résultats de smoke tests.

## Boucle locale de candidats

Les tests du code source ne peuvent pas prouver que l’artefact empaqueté démarre correctement : les listes de fichiers à empaqueter, les dépendances élaguées et les binaires natifs n’échouent qu’une fois l’archive tar installée et démarrée. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) constitue la partie locale du flux construire une fois / valider / promouvoir de la
RFC #8084 : il construit un candidat, valide cet artefact précis, le promeut en renommant des
répertoires et le restaure à son état précédent lorsque l’emplacement promu échoue à son contrôle d’intégrité.

```bash
npm run dev:candidate -- run --dry-run --json  # afficher le plan sans rien modifier
npm run dev:candidate -- run                   # construire + valider + promouvoir, restauration automatique
npm run dev:candidate -- build                 # npm pack + installation dans _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # démarrer sur un port libre, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # permuter current et previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # réutiliser une archive tar créée ailleurs (CI)
```

- **Construire une seule fois.** `build` empaquette l’arborescence actuelle (il a besoin de `dist/server.js`, exécutez donc
  d’abord `npm run build:release`) ou copie `--from-tarball`, puis installe l’archive tar dans un
  préfixe npm isolé, car l’archive tar ne contient aucun `node_modules`. L’identifiant est le sha court de `HEAD`
  (`-dirty` lorsque l’arborescence comporte des modifications locales) ou `tgz-<sha256>` pour une archive tar. Un identifiant propre déjà
  construit est réutilisé au lieu d’être reconstruit ; transmettez `--force` pour le reconstruire.
- **Valider le paquet, pas le code source.** `validate` démarre la CLI installée
  (`serve --port <free port>`) avec un nouveau `DATA_DIR=<candidate>/data`, des secrets factices, tandis que les variables
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` et `INITIAL_PASSWORD` de l’opérateur sont supprimées de
  l’environnement, afin de vérifier la configuration sans clé sur boucle locale d’une nouvelle installation. Il attend que
  `GET /api/health` renvoie 200, exige que `GET /v1/models` renvoie 200, arrête le groupe de processus
  et enregistre le verdict dans `validation.json` avec le hachage de l’archive tar.
- **Promouvoir le même artefact.** `promote` refuse un candidat qui ne dispose pas d’une validation réussie pour le
  hachage de son archive tar actuelle. L’emplacement actif par défaut est `_artifacts/candidate/current` ; `--target <dir>`
  sélectionne un autre répertoire sur le même système de fichiers, et son emplacement précédent est `<dir>.previous`.
  Chaque renommage est atomique, et un échec en cours d’opération annule les renommages déjà effectués.
- **Restaurer l’état précédent.** `run` valide de nouveau l’emplacement promu et permute `current` et `previous` en sens inverse lorsque
  ce contrôle échoue. Un candidat qui échoue à la première validation n’est jamais promu.

Tout est écrit sous le répertoire `_artifacts/candidate/`, ignoré par git ; une installation OmniRoute
existante et son répertoire de données ne sont jamais modifiés. La CLI promue est
`_artifacts/candidate/current/prefix/bin/omniroute` ; démarrez-la avec votre propre `DATA_DIR` lorsque vous
l’utilisez. Codes de sortie : `0` réussite, `1` échec de la validation ou de la promotion, `2` erreur d’utilisation ou build manquant.

## Boucle locale ou CI

| À exécuter localement pour chaque correctif                                                               | La CI fournit un signal global                                                       |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Tests directs du comportement et contrôles de catégorie ci-dessus                                         | Suite complète de tests unitaires partitionnée et tests en série                     |
| `npm run lint`                                                                                            | Suites Vitest et seuils progressifs de couverture/qualité                            |
| Vérification des types ou build uniquement si le contrat concerné l’exige                                 | Build de production, sécurité, documentation, dépendances et règles de PR            |
| Interactions manuelles/tests en direct uniquement si l’automatisation ne peut pas valider le comportement | Vérifications d’intégration inter-jobs et de plateformes configurées par le workflow |

Une boucle ciblée réussie constitue une preuve concernant le contrat modifié, et non la garantie que des vérifications CI sans rapport
réussiront. Inversement, n’obligez pas chaque modification locale à attendre la matrice complète du dépôt.

## Liste de contrôle de réconciliation

Avant de demander une revue :

- Confirmez que la base de la PR est toujours la branche `release/v*` active la plus élevée.
- Récupérez cette base et examinez les commits intégrés depuis la création de votre branche.
- Examinez `git diff <active-base>...HEAD` afin de détecter toute modification accidentelle ou générée.
- Résolvez les conflits dans les catalogues et les documents générés en mettant à jour la source et en régénérant la sortie.
- Réexécutez chaque test/contrôle ciblé indiqué dans la description de la PR après la réconciliation.
- N’affaiblissez jamais les assertions et ne supprimez jamais les tests requis dans le seul but de vous aligner sur une base qui a évolué.

Pour les règles de gel des versions et de reciblage, consultez
[Modèle de branches et de versions](BRANCHING_MODEL.md). Pour l’inventaire complet de la CI, consultez
[Référence des contrôles qualité](../architecture/QUALITY_GATES.md).
