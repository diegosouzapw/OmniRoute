> 選擇性啟用，預設關閉（`settings.freeAccessPolicy !== "strict"` 會讓每個 `auto/*`
> 候選池維持位元組完全相同）。這是 `hidePaidModels`
> （`open-sse/services/autoCombo/paidModelFilter.ts`，#6512）更嚴格的同類功能，適用於需要嚴格
> 保證不會產生任何增量金錢支出，而不只是「文件記載為免費」的營運者。

## 為什麼需要此功能，以及為什麼僅使用 `hidePaidModels` 還不夠

`hidePaidModels` 回答的是「此模型目前在 `FREE_MODEL_BUDGETS` 中是否被歸類為免費？」——
這是在某個時間點的目錄事實，透過 `isFreeModel()`/`providerHasFreeModels()`
（`src/shared/utils/freeModels.ts`）檢查。它完全沒有處理兩項實際風險：

1. `recurring-*`/`one-time-initial` 免費方案的額度可能已經**用盡**——目錄
   仍將該模型列為免費，但其背後的帳戶已沒有任何剩餘額度。
2. 超出免費方案額度不一定會被強制停止。某些提供者明確記載永遠無法
   綁定付款方式（「不需要信用卡」）；其他提供者則未加說明，另有少數提供者會在超出
   免費額度後自動計費。

`hidePaidModels` 無法區分這些情況——它原本就不是為此設計。STRICT_ZERO_COST 正好新增
這兩項檢查，針對每個候選項目，在類別／層級排序**之前**且在
分派**之前**進行評估——絕不會等到請求已經送出後才檢查。

## 候選項目分類

針對池中的每個候選項目（`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`，
緊接在 `filterPaidOnlyCandidates` 之後）：

1. **完全不在 `FREE_MODEL_BUDGETS` 中** → 排除。這涵蓋真正的付費模型，以及
   OmniRoute 尚未分類的任何提供者／模型——新的候選項目預設為排除，而非納入。
2. **`freeType: "keyless"`** → 立即通過，**但僅限於確實
   經由免驗證路徑進入的候選項目**（`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`，
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`）。該候選項目沒有任何憑證，
   因此針對它發出的請求永遠不可能被計費——不需要也不可能進行執行階段檢查。
   透過**真實** DB 連線取得的相同目錄 `keyless` 提供者／模型
   （`connectionId` 是實際的連線 ID，或候選項目帶有
   `allowedConnectionIds`）**不會**獲得這項捷徑——`keyless` 中繼資料專門描述
   免驗證路徑，而不是一般意義上的提供者，且絕不會授權真實的
   已驗證帳戶。此類候選項目會和其他候選項目一樣繼續進入檢查 3，除非目錄項目另外帶有
   `hardStopGuaranteed: true`，否則將被排除（真實的
   `keyless` 項目絕不會有此設定——該捷徑是它們唯一的安全通過途徑）。
3. **任何其他 `freeType`**（`recurring-daily`、`recurring-monthly`、`recurring-credit`、
   `recurring-uncapped`、`one-time-initial`，以及此模組未特別處理的任何未來類型）
   → 僅在**全部**符合下列條件時才會通過：
   - 目錄項目上已設定 `hardStopGuaranteed: true`（`FreeModelBudget.hardStopGuaranteed`、
     `open-sse/config/freeModelCatalog.ts`）——這是關於提供者自行發布之條款的
     **人工精選、手動設定事實**（例如明確聲稱「不需要信用卡」），絕不會從
     `freeType` 或即時 API 回應推導而來。未設定（`undefined`）和 `false` 都會被視為
     「不保證」。
   - `USAGE_FETCHER_PROVIDERS` 中存在該提供者的用量配接器
     （`open-sse/services/usage.ts`）——這是已支援配額儀表板和
     `getUsageForProvider()` 的相同登錄檔。沒有配接器 → 永久排除，直到新增配接器為止。
   - 針對**目前實際評估的特定連線**，其即時快取 `FreeAccessState` 為
     `status: "SAFE"`、已在
     `settings.autoRefreshProviderQuotaInterval` 之內完成檢查（預設 180 秒——使用既有
     設定，而非新增數值），且回報的 `remainingFreeAllowance` 高於一個較小的安全邊際。
4. **`freeType: "discontinued"`** → 一律排除。

## 連線安全性（逐連線驗證，絕非逐候選項目）

自動組合池中的候選項目不一定只繫結至單一連線。「邏輯」候選項目
（`connectionId: null`）會帶有 `allowedConnectionIds` 允許清單，其中包含一或多個可處理該請求的實際
提供者連線／帳戶；實際使用的帳戶會在稍後的分派階段，由 `open-sse/services/combo/autoStrategy.ts`
決定（將 `allowedConnectionIds` 與其自身的連線選擇邏輯取交集，約位於第 315-331 行）。

STRICT_ZERO_COST 會**逐一**驗證該允許清單中每個連線的免費存取狀態
（`strictZeroCostFilter.ts` 中的 `evaluateCandidateConnections()`），並將
`allowedConnectionIds` 改寫為恰好僅包含回傳 `SAFE` 的子集——絕不保留完整的
原始清單，也絕不任意選擇其中單一成員。具體而言：

- 帳戶 A 為 `SAFE`、帳戶 B 為 `UNKNOWN`／額度耗盡／需付費 → 僅 A 仍可供選擇。
- 所有帳戶皆為 `UNKNOWN` → 完全捨棄該候選項目（安全集合為空）。
- 若單一連線候選項目（直接設定 `connectionId`，沒有允許清單）驗證失敗，則會
  直接捨棄，絕不會以空的 `allowedConnectionIds` 回傳。

由於 `autoStrategy.ts` 在選擇要分派至哪個連線之前，就已將 `allowedConnectionIds`
強制執行為硬性允許清單，因此將其改寫為已驗證為 `SAFE` 的子集，足以保證分派時實際使用的
連線必定是此篩選器親自驗證過的連線——絕不會是同一候選項目上的其他未經驗證帳戶。迴歸證明請參閱
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts`
（無金鑰繞過案例 A/B/C、多帳戶案例 1-5）。

`自動探索`：若明天發布的提供者／模型具備正確的中繼資料（存在於
目錄中、具有用量配接器，且 `hardStopGuaranteed: true`），則 OmniRoute 一得知它就能立即使用——
無須修改程式碼、無須新增允許清單項目，也無須編輯此模組。從目錄移除的項目也會以相同方式消失。迴歸證明請參閱
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts`（透過
可注入的固定測試資料，而非修改實際目錄）。

## 配額快取（`open-sse/services/autoCombo/freeAccessQuota.ts`）

重複使用 `getUsageForProvider()`——不建立第二套配額系統。其前方設有一個短效、位於記憶體中、
生命週期與處理程序相同的快取（TTL 等於預設的
`autoRefreshProviderQuotaInterval`），因此即使請求速率達到 Telegram 規模，也不會對每個請求中的
每個候選項目都觸發即時的計費 API 呼叫。讀取為同步操作：快取未命中時會回傳
`undefined`（→ 排除，採失敗關閉策略），並在背景啟動重新整理，以供_下一次_讀取使用——
候選池建置路徑中的任何操作都不會等待網路呼叫。

當連線因任何原因失敗時，`src/sse/services/auth.ts::markAccountUnavailable()` 會立即呼叫
`invalidateFreeAccessState(provider, connectionId)`，因此下一次建置候選池時會讀到乾淨的快取未命中，
而非過期的 `SAFE` 項目——在收到 402/403／配額耗盡回應後，無須等待 TTL 到期。

## ToS 防護機制（獨立於經濟安全性）

`excludeTosAvoid`（預設為 `false`）會移除所有經整理後 `tos` 判定
（`FreeModelBudget.tos`）為 `"avoid"` 的候選項目——它會重複使用 `hidePaidModels` 的同層文件
（`docs/reference/FREE_TIERS.md`）已填入的相同欄位。此機制刻意與
`freeAccessPolicy` 分開：候選項目在經濟層面可以是 `SAFE`，但仍可能因
合約因素在此遭到排除；或者即使已啟用 `freeAccessPolicy: "strict"`，只要關閉此防護機制，候選項目仍會保留。

## 查看防護機制排除了哪些項目

`GET /v1/auto-combo/{channel}/candidates` 會列出所有候選項目，包括此防護機制
會阻止派送的項目，而且每個項目都帶有 `freeAccessExclusion`——符合防護條件時為
`null`，否則為排除原因。此清單只負責回報，絕不執行排除。關閉此政策後，
所有項目的該欄位都會是 `null`，且不會產生任何成本。

| `freeAccessExclusion`  | 代表意義                                                                                          | 處理方式                                                                           |
| :--------------------- | :------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------- |
| `not-in-catalog`       | 提供者／模型組合不存在於 `FREE_MODEL_BUDGETS` 中。                                                | 新增經整理的項目，或接受新組合一開始即遭排除——這是刻意的設計。                     |
| `regime-not-free`      | 已收錄於目錄，但其 `freeType` 並非提供免費存取權的類型（例如已終止的方案）。                      | 無需修正。該模型需要付費。                                                         |
| `no-hard-stop`         | 屬於免費方案，但 `hardStopGuaranteed` 並非 `true`，因此超出額度後可能會在未提示的情況下開始計費。 | 驗證提供者的條款，並在註解中附上來源後設定此旗標——絕不可只是為了擴充目錄而設定。   |
| `contradictory-noauth` | 無須驗證的候選項目，其目錄項目卻不是 `keyless`。遇到不一致的中繼資料時採取故障關閉。              | 修正目錄項目；這兩項事實彼此矛盾。                                                 |
| `exhausted`            | 最新讀數顯示額度已用盡。                                                                          | 等待重設。此問題會自行解決。                                                       |
| `state-unknown`        | 沒有配額讀數，或讀數過舊而無法信任。                                                              | 前往檢查：提供者可能未註冊用量配接器，或配額擷取作業失敗。                         |
| `no-connection`        | 候選項目完全沒有可供檢查的帳戶。                                                                  | 這不是配額問題：候選項目建立時沒有連線，因此從未進行查詢。請檢查候選池的組裝方式。 |

最後兩者特別值得加以區分。已用盡的額度會自行重設；若讀數始終沒有出現，
表示查詢本身出了問題，而在此之前，兩者從外部看起來完全相同——候選項目只會直接消失。

**仍有一項缺口，而且這是刻意保留的。** `excludeTosAvoid` 仍會在建立清單前移除候選項目，
因此經整理後標記為 `tos: "avoid"` 的模型會直接消失，且不會提供原因——這與本節剛針對
零成本防護機制解決的不可見問題相同。若也要填補這項缺口，就必須決定 ToS 排除項目應回報什麼，
而這是獨立於經濟安全性的另一項問題；本頁會明確指出此缺口，而不是假裝它不存在。

若要離線比較前後差異，`npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` 仍可針對
執行中執行個體的候選項目輸出運作；它會讀取每個候選項目的真實 `connectionId`，因此也會
測試連線安全性路徑。無金鑰候選項目必須使用合成的無驗證 `connectionId`，絕不能使用真實連線。
目前內建的無金鑰自動路徑是 OpenCode Free；確切候選項目數量仍取決於即時模型探索結果，
應在目標部署環境中實際測量，而不是從較舊的執行結果複製。`recurring-*` 候選項目只有在
同時具備已註冊的用量配接器和 `hardStopGuaranteed: true` 時才會通過；中繼資料不完整時仍採取故障關閉。

當 `excludeTosAvoid: true` 時，所有經整理後標記為 `tos: "avoid"` 的候選項目都會遭到移除。OpenCode Free
目前帶有此判定，因此啟用該防護機制可能會清空部署環境中剩餘的無金鑰候選池。
這是啟用 ToS 防護機制時預期會有的取捨，並非錯誤：正因如此，此防護機制的預設值才是 `false`
（請參閱上方的「ToS 防護機制」）。

## 啟用

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

這兩項新設定的預設值皆為此功能推出前的值（`"off"` / `false`）——若兩者皆未啟用，
則不會變更任何現有的 `auto/*` 路由行為。
