使用本指南，為提取要求選擇最小且可靠的開發迴圈。本指南不會取代下方連結的特定領域架構與安全性文件；它會將每種常見的變更類型連結至其契約、聚焦檢查及 CI 涵蓋範圍。

## 每項變更都遵循的流程

1. **編輯前先選擇基底。** 找出版本最高且仍在使用中的 `release/v*` 分支，並從其最新提交建立分支。以該分支為目標，而非 `main`。如果目前處於版本凍結期，請勿以已凍結的分支為目標；請使用
   [分支與發布模型](BRANCHING_MODEL.md)中所述的下一個有效週期。
2. **列出契約。** 識別變更會影響的每個目錄、結構描述、產生的成品、公開 API 或使用者介面。下表提供最低限度的起始集合。
3. **撰寫或更新聚焦測試。** 對 `src/`、`open-sse/`、`electron/` 或
   `bin/` 的正式環境程式碼變更，必須在同一個 PR 中加入自動化測試。請先執行能證明相關行為的最小測試檔案集合，再執行列出的聚焦閘門。
4. **讓 CI 執行廣泛的矩陣。** 完整的單元測試分片、Vitest、覆蓋率棘輪檢查及正式環境建置會在 PR 上執行。只有當聚焦測試失敗顯示可能存在更廣泛的影響，或變更橫跨多個子系統時，才需要在本機執行廣泛的測試套件。
5. **在審查前完成同步。** 擷取使用中的基底分支，檢查其新提交以及您的分支與它之間的差異，然後依照貢獻者工作流程，將基底分支重定基底或合併至您的分支。從來源解決產生檔案與目錄的衝突、重新產生這些檔案、再次執行聚焦迴圈，並確認 PR 仍以使用中的發布分支為目標。
6. **記錄證據。** 在 PR 範本中列出執行過的命令、新增或變更的每個測試檔案、遷移或功能旗標，以及任何仍待 CI 驗證的項目。

## 依變更類型劃分的黃金路徑

以下命令是最低限度的聚焦檢查，並不代表可以略過直接涵蓋您所變更行為的測試。

### 提供者

**契約**

- `src/shared/constants/providers/` 中的提供者定義，以及其在
  `src/shared/constants/providers.ts` 中的組合。
- `open-sse/config/providerRegistry.ts` 或其拆分登錄檔案中的模型與能力。
- 執行器／轉譯器選擇、OAuth 或 API 金鑰設定、儀表板資產，以及適用時產生的提供者參考資料。
- 公開憑證必須使用 `resolvePublicCred()`；錯誤回應必須使用共用的已清理錯誤輔助函式。請參閱 `docs/security/PUBLIC_CREDS.md`（位於 git 中；不會編譯至 `/docs`）及
  [錯誤清理](../security/ERROR_SANITIZATION.md)。

**聚焦迴圈**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # 當目錄變更時；提交產生的差異
npm run lint
```

也請測試每個受影響的要求系列：聊天、Responses、圖像、嵌入、音訊或影片。請將產生的目錄與黃金檔案差異視為契約變更進行審查；不要盲目接受。

### 路由

**契約**

- `src/shared/constants/routingStrategies.ts` 中的公開策略值與 UI 中繼資料。
- `open-sse/services/combo.ts` 與 `open-sse/services/combo/` 下的分派及排序。
- 組合結構描述、持久性、韌性狀態、模型能力，以及 API／UI 控制項。
- 行為變更時，請參閱[自動組合引擎](../routing/AUTO-COMBO.md)與韌性文件。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # 策略或分派變更
npm run check:known-symbols      # 策略註冊變更
npm run lint
```

請在本機使用具決定性的模擬上游測試。即時組合冒煙測試需要憑證，且必須手動執行，不能作為 CI 的替代方案。

### UI / UX

**契約**

- `src/app/` 與 `src/shared/components/` 下的 Next.js 路由／頁面及共用元件邊界。
- API 回應形狀、載入／空白／錯誤狀態、鍵盤與螢幕閱讀器行為、回應式版面配置、主題，以及語系擴充。
- `src/i18n/messages/en.json` 中的英文 UI 來源字串；請勿將新的使用者可見文案寫死在程式碼中。

**聚焦迴圈**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

若有互動或視覺變更，請執行應用程式，並同時檢查窄版與寬版視窗。CI 會執行正式環境建置及更廣泛的測試套件；視覺行為仍需依變更性質，透過聚焦元件測試、Playwright 或有文件記錄的手動檢查進行驗證。

### i18n

**契約**

- `src/i18n/messages/en.json` 是 UI 來源；`config/i18n.json` 是語系來源。
- CLI 目錄另存於 `bin/cli/locales/` 下。
- 完整保留 ICU 預留位置與標籤。請勿翻譯產品／提供者／模型名稱、通訊協定與標頭名稱、命令、程式碼／JSON 識別碼、URL、環境變數，或 `OmniRoute`、`OAuth`、`MCP` 和 `A2A` 等受保護詞彙。目前的來源清單為
  `scripts/i18n/glossary/protected-terms.json`。

**聚焦迴圈**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # 當 CLI 字串／目錄變更時
npm run lint
```

這是現有系統的指引，並非擴充其工具或鍵值模型的邀請。在替代系統設計期間，請讓 i18n 修補保持精準且範圍有限。除非工作明確要求產生翻譯，且您已審查產生的差異，否則請勿執行會呼叫外部服務的翻譯命令。

### CLI

**契約**

- `bin/cli/` 中的公開命令與旗標、產生的 API 命令、結束代碼、stdout/stderr 與
  JSON 輸出結構、設定／環境行為，以及套件中包含的檔案。
- CLI 面向使用者的字串必須使用 CLI i18n 層，並保持 `en`/`pt-BR` 語系目錄同步。
- 保留 Node 作為受支援的執行環境，並維持已發布的二進位契約。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 產生／封裝的 CLI 變更
npm run check:pack-policy     # 套件公開介面變更
npm run lint
```

當行為取決於剖析、檔案或結束狀態時，請在暫存資料目錄中使用確切的命令。CI 會執行更廣泛的套件成品與生態系統檢查。

### 資料庫

**契約**

- `src/lib/db/` 下的領域模組；直接匯入特定模組（舊的 `localDb.ts` 重新匯出層已移除）。
- `src/lib/db/migrations/` 下具編號且可重複執行的 SQL 遷移、交易安全性、升級
  行為、索引，以及所有受結構描述影響的呼叫端。
- 路由與處理常式絕不可直接執行原始 SQL。

**聚焦迴圈**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

新增遷移時，請同時測試全新資料庫，以及從前一版結構描述升級。資料庫測試必須關閉控制代碼，並在清理期間呼叫 `resetDbInstance()`。僅在盡力而為的 Bun 配接器路徑變更時執行 `npm run test:bun:db`；Node 仍是權威執行環境。

### 建置／部署

**契約**

- 根目錄與工作區的資訊清單／鎖定檔、`scripts/build/`、Next.js 獨立組裝、`dist/`
  套件內容、Electron 平台中繼資料、CI 工作流程，以及部署哨兵。
- 必須維持受支援的 Node 版本範圍，以及 `CLAUDE.md` 中列入允許清單的 Bun 使用方式。
- 建置成品維持不受版本控制追蹤；相依套件、授權、工作流程與套件政策均適用。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 相依套件或鎖定檔變更
npm run check:pack-policy      # 已發布套件的公開介面變更
npm run lint
```

僅當變更影響編譯、獨立組裝、資產或執行階段封裝時，才在本機使用 `npm run build`。僅將 `npm run build:release` 用於發布／部署驗證。CI 的建置是最終的跨平台判定依據；特定平台的 Electron 變更需要相應的聚焦建置或煙霧測試證據。

## 本機候選版本迴圈

原始碼測試無法證明封裝後的成品能夠啟動：封裝清單、裁剪後的相依套件及原生二進位檔，只有在 tarball 安裝並啟動後才會暴露問題。`npm run dev:candidate`
（`scripts/dev/candidate.mjs`）是 RFC #8084 所述「建置一次／驗證／升級」流程的本機端：它會建置一個候選版本、驗證該確切成品、透過目錄重新命名將其升級，並在升級後的槽位未通過健康檢查時將其回復。

```bash
npm run dev:candidate -- run --dry-run --json  # 顯示計畫，不變更任何內容
npm run dev:candidate -- run                   # 建置 + 驗證 + 升級，自動回復
npm run dev:candidate -- build                 # npm pack + 安裝至 _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # 在可用連接埠上啟動，檢查 /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current，current → previous
npm run dev:candidate -- rollback              # 交換 current 與 previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # 重複使用在其他地方（CI）建置的 tarball
```

- **只建置一次。** `build` 會封裝目前的原始碼樹（它需要 `dist/server.js`，因此請先執行
  `npm run build:release`），或複製 `--from-tarball`，然後將 tarball 安裝至隔離的 npm prefix，因為 tarball 不包含 `node_modules`。ID 是簡短的 `HEAD`
  sha（當原始碼樹含有本機變更時會加上 `-dirty`），若為 tarball，則是 `tgz-<sha256>`。若乾淨的 ID 已完成建置，系統會直接重複使用而不會重新建置；傳入 `--force` 可強制重新建置。
- **驗證套件，而非原始碼。** `validate` 會使用全新的 `DATA_DIR=<candidate>/data`、假的密鑰來啟動已安裝的 CLI
  （`serve --port <free port>`），並從環境中移除操作人員的 `OMNIROUTE_API_KEY`、`STORAGE_ENCRYPTION_KEY` 及 `INITIAL_PASSWORD`，藉此檢查全新安裝在無金鑰情況下的回送介面安全態勢。它會等待
  `GET /api/health` 傳回 200，要求 `GET /v1/models` 傳回 200，停止處理程序群組，並將判定結果連同 tarball 雜湊記錄於 `validation.json`。
- **升級同一個成品。** 如果候選版本沒有針對其目前 tarball 雜湊的通過驗證，`promote` 將拒絕該候選版本。預設的作用中槽位是 `_artifacts/candidate/current`；`--target <dir>`
  可選取同一檔案系統上的其他目錄，而其前一個槽位則為 `<dir>.previous`。每次重新命名都是不可分割的操作；若過程中發生失敗，已執行的重新命名將依序反向還原。
- **回復。** `run` 會再次驗證升級後的槽位；若該檢查失敗，便會將 `current` 與 `previous` 交換回來。未通過第一次驗證的候選版本絕不會被升級。

所有內容都會寫入已被 git 忽略的 `_artifacts/candidate/`；現有的 OmniRoute 安裝及其資料目錄絕不會被修改。升級後的 CLI 位於
`_artifacts/candidate/current/prefix/bin/omniroute`；使用時，請以您自己的 `DATA_DIR` 啟動它。結束代碼：`0` 表示成功，`1` 表示驗證或升級失敗，`2` 表示用法錯誤或缺少建置。

## 本機迴圈與 CI 的比較

| 每個修補程式在本機執行                               | CI 提供廣泛的訊號                                |
| ---------------------------------------------------- | ------------------------------------------------ |
| 上述的直接行為測試與類別閘門                         | 分片的完整單元測試套件與序列測試                 |
| `npm run lint`                                       | Vitest 測試套件與覆蓋率／品質的漸進式門檻        |
| 僅在受影響的契約有要求時進行類型檢查或建置           | 正式環境建置、安全性、文件、相依性與 PR 政策閘門 |
| 僅在自動化無法證明該行為時，才進行手動互動／即時檢查 | 由工作流程設定的跨作業整合與平台檢查             |

聚焦迴圈通過代表受變更契約已有相關證據，但不表示不相關的 CI 檢查
都會通過。反之，也不要讓每次本機編輯都等待完整的儲存庫矩陣。

## 協調檢查清單

請在要求審查前：

- 確認 PR 的基底仍是目前最高版本的有效 `release/v*` 分支。
- 擷取該基底，並檢視您建立分支後新增的提交。
- 檢視 `git diff <active-base>...HEAD`，確認沒有意外或由產生程序造成的大量變更。
- 更新來源並重新產生輸出，以解決目錄與產生文件的衝突。
- 協調完成後，重新執行 PR 描述中列出的每項聚焦測試／閘門。
- 絕不可只是為了配合已變動的基底，而弱化斷言或移除必要的測試。

關於發布凍結與重新設定目標的規則，請參閱
[分支與發布模型](BRANCHING_MODEL.md)。如需完整的 CI 清單，請參閱
[品質閘門參考資料](../architecture/QUALITY_GATES.md)。
