使用本指南，為拉取請求選擇最小且可靠的開發迴圈。本指南不會取代下方連結的各領域專屬架構與安全性文件；它會將每種常見的變更類型連結至其契約、重點檢查及 CI 涵蓋範圍。

## 每項變更都會遵循的路徑

1. **在編輯前選擇基底。** 找出最高版本且仍在使用中的 `release/v*` 分支，並從其最新提交建立分支。以該分支為目標，而非 `main`。如果目前處於版本凍結期，請勿以已凍結的分支為目標；請使用
   [分支與發布模型](BRANCHING_MODEL.md)中所述的下一個有效週期。
2. **列出契約。** 找出變更會影響的每個目錄、結構描述、產生的成品、公開 API 或使用者介面。下表提供最低限度的起始集合。
3. **撰寫或更新重點測試。** 對 `src/`、`open-sse/`、`electron/` 或
   `bin/` 中正式環境程式碼的變更，必須在同一個 PR 中包含自動化測試。先執行可證明該行為的最小測試檔案集合，再執行列出的重點關卡。
4. **讓 CI 執行廣泛的矩陣。** 完整的單元測試分片、Vitest、涵蓋率棘輪檢查，以及正式環境建置都會在 PR 上執行。只有當重點測試失敗顯示可能有更廣泛的影響，或變更橫跨多個子系統時，才在本機執行廣泛的測試套件。
5. **在審查前完成同步。** 擷取目前有效的基底分支，檢查其新提交以及您的變更與它之間的差異，然後依照貢獻者工作流程對基底進行 rebase 或 merge。請從來源解決產生檔案與目錄的衝突、重新產生檔案、再次執行重點迴圈，並確認 PR 仍以目前有效的發布分支為目標。
6. **記錄證據。** 在 PR 範本中列出已執行的命令、所有新增或變更的測試檔案、遷移或功能旗標，以及任何仍待執行且只能在 CI 中完成的驗證。

## 依變更類型區分的黃金路徑

下列命令是最低限度的重點檢查，並不表示可以略過直接涵蓋您所變更行為的測試。

### 提供者

**契約**

- `src/shared/constants/providers/` 中的提供者定義，以及它在
  `src/shared/constants/providers.ts` 中的組合方式。
- `open-sse/config/providerRegistry.ts` 或其拆分出的登錄檔案中的模型與功能。
- 適用時的執行器／轉譯器選擇、OAuth 或 API 金鑰設定、儀表板資產，以及產生的提供者參考文件。
- 公開憑證必須使用 `resolvePublicCred()`；錯誤回應必須使用共用的已清理錯誤輔助函式。請參閱 `docs/security/PUBLIC_CREDS.md`（位於 git 中；不會編譯至 `/docs`）以及
  [錯誤清理](../security/ERROR_SANITIZATION.md)。

**重點迴圈**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # 當目錄變更時執行；提交產生的差異
npm run lint
```

也請測試每個受影響的請求類別：聊天、Responses、圖片、嵌入、音訊或影片。將產生的目錄與黃金檔差異視為契約變更進行審查；不要盲目接受它們。

### 路由

**契約**

- `src/shared/constants/routingStrategies.ts` 中的公開策略值與 UI 中繼資料。
- `open-sse/services/combo.ts` 與 `open-sse/services/combo/` 下的分派與排序。
- Combo 結構描述、持久化、韌性狀態、模型功能，以及 API/UI 控制項。
- 行為變更時，請參閱[自動 Combo 引擎](../routing/AUTO-COMBO.md)與韌性文件。

**重點迴圈**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # 策略或分派變更
npm run check:known-symbols      # 策略註冊變更
npm run lint
```

在本機使用具確定性的模擬上游測試。即時 Combo 冒煙測試需要憑證且須手動執行，不能取代 CI。

### UI / UX

**契約**

- `src/app/` 與 `src/shared/components/` 下的 Next.js 路由／頁面及共用元件邊界。
- API 回應形狀、載入／空白／錯誤狀態、鍵盤與螢幕閱讀器行為、回應式版面配置、主題設定，以及語系擴充。
- `src/i18n/messages/en.json` 中的英文 UI 來源字串；不要將新的使用者可見文案寫死在程式碼中。

**重點迴圈**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

若是互動或視覺變更，請執行應用程式，並檢查窄版與寬版檢視區。CI 會執行正式環境建置與更廣泛的測試套件；視覺行為仍需使用適合該變更的重點元件測試、Playwright 測試，或有文件記錄的手動檢查。

### i18n

**契約**

- `src/i18n/messages/en.json` 是 UI 來源；`config/i18n.json` 是語系來源。
- CLI 目錄另行存放於 `bin/cli/locales/` 下。
- 請完整保留 ICU 預留位置與標籤。不要翻譯產品／提供者／模型名稱、通訊協定與標頭名稱、命令、程式碼／JSON 識別碼、URL、環境變數，或 `OmniRoute`、`OAuth`、`MCP` 和 `A2A` 等受保護詞彙。目前的來源清單是
  `scripts/i18n/glossary/protected-terms.json`。

**重點迴圈**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # 當 CLI 字串／目錄變更時執行
npm run lint
```

這是現有系統的指引，並非擴充其工具或鍵值模型的邀請。在替代系統的設計期間，請讓 i18n 修補保持精準且範圍有限。除非任務明確要求產生翻譯，而且您已審查產生的差異，否則不要執行會呼叫外部服務的翻譯命令。

### CLI

**契約**

- `bin/cli/` 中的公開命令與旗標、產生的 API 命令、結束代碼、stdout/stderr 與
  JSON 輸出格式、設定／環境行為，以及封裝的檔案。
- CLI 面向使用者的字串必須使用 CLI i18n 層，並保持 `en`/`pt-BR` 目錄一致。
- 保持 Node 作為受支援的執行環境，並維持已發布的二進位檔契約。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # 產生／封裝的 CLI 變更
npm run check:pack-policy     # 套件公開介面變更
npm run lint
```

當行為取決於剖析、檔案或結束狀態時，請在暫存資料目錄中使用完全相同的命令。CI 會執行更廣泛的套件成品與生態系統檢查。

### 資料庫

**契約**

- `src/lib/db/` 下的領域模組；直接匯入特定模組（舊的 `localDb.ts` 重新匯出層已移除）。
- `src/lib/db/migrations/` 下具編號且具冪等性的 SQL 遷移、交易安全性、升級
  行為、索引，以及所有受綱要影響的呼叫端。
- 路由與處理常式絕不直接執行原始 SQL。

**聚焦迴圈**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

新增遷移時，請同時測試全新資料庫與從前一版綱要升級。資料庫測試必須關閉控制代碼，並在清理期間呼叫 `resetDbInstance()`。只有在盡力支援的 Bun 介面卡路徑發生變更時，才執行 `npm run test:bun:db`；Node 仍是權威基準。

### 建置／部署

**契約**

- 根目錄與工作區的資訊清單／鎖定檔、`scripts/build/`、Next.js 獨立組裝、`dist/`
  套件內容、Electron 平台中繼資料、CI 工作流程，以及部署哨兵。
- 受支援的 Node 版本範圍及 `CLAUDE.md` 中允許清單內的 Bun 用法必須保持不變。
- 建置成品維持不受追蹤；相依套件、授權、工作流程與套件政策皆適用。

**聚焦迴圈**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # 相依套件或鎖定檔變更
npm run check:pack-policy      # 已發布套件的公開介面變更
npm run lint
```

只有當變更會影響編譯、獨立組裝、資產或執行階段封裝時，才在本機使用 `npm run build`。僅將 `npm run build:release` 用於發行／部署驗證。CI 的建置是最終的跨平台判定依據；平台特定的 Electron 變更需要對應的聚焦建置或冒煙測試證據。

## 本機迴圈與 CI 的比較

| 每個修補在本機執行                                 | CI 提供廣泛的訊號                                |
| -------------------------------------------------- | ------------------------------------------------ |
| 上述的直接行為測試與類別閘門                       | 分片的完整單元測試套件與循序測試                 |
| `npm run lint`                                     | Vitest 測試套件與覆蓋率／品質漸進門檻            |
| 僅在受影響的契約有要求時才執行類型檢查或建置       | 正式環境建置、安全性、文件、相依性與 PR 政策閘門 |
| 僅在自動化無法驗證行為時，才進行手動互動／即時檢查 | 由工作流程設定的跨工作整合與平台檢查             |

聚焦迴圈顯示綠燈，是關於已變更契約的證據，並不代表不相關的 CI 檢查
必然會通過。反之，也不要讓每次本機編輯都必須等待完整的儲存庫測試矩陣。

## 協調檢查清單

在請求審查之前：

- 確認 PR 的基底仍是最高版本且活躍的 `release/v*` 分支。
- 擷取該基底，並審查自您建立分支後新增的提交。
- 檢查 `git diff <active-base>...HEAD`，確認是否有意外或由產生程序造成的大量變更。
- 更新來源並重新產生輸出，以解決目錄與產生文件的衝突。
- 協調完成後，重新執行 PR 說明中列出的每項聚焦測試／閘門。
- 絕不可僅為了配合已移動的基底而弱化斷言或移除必要測試。

如需發行凍結與重新設定目標的規則，請參閱
[分支與發行模型](BRANCHING_MODEL.md)。如需完整的 CI 清單，請參閱
[品質閘門參考](../architecture/QUALITY_GATES.md)。
