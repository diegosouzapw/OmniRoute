## 詳細疑難排解

---

### 免費提供者的速率限制（429 / 400 / 401）

**症狀**：搭配免費／無須驗證的提供者（opencode、auggie 等）使用 `model: "auto"` 時，您會間歇性收到 `HTTP 429`、`400` 或 `401`，而非正常回答。稍後使用相同提示詞重試時，請求會成功，但自動化作業（cron 工作、代理程式、指令碼）會在第一次失敗時中斷。

**根本原因**：三種獨立的失敗模式會疊加發生：

1. **提供者速率限制（`429`）**：免費方案可能會針對每個時間區段強制執行配額。突發的大量平行呼叫會耗盡配額，因此後續請求會遭到拒絕，直到時間區段重設為止。
2. **直通模式中的故障模型（`400`/`401`）**：`auto/*` 集區可能包含來自 `opencode` 的直通模型；這些模型雖已登錄於目錄中，卻沒有有效的認證資訊（例如 `oc/north-mini-code-free` → `401`）。自動路由器會嘗試其中一個模型，但該模型失敗後，錯誤會在備援機制啟動前就向外傳播。
3. **並行放大效應（負載下出現 `429`）**：當多個代理程式／cron 工作階段同時呼叫 `auto` 時，彙總請求速率會超過免費提供者可容許的範圍，導致合法呼叫被標記為濫用。

**已驗證的修正方式（社群回報，2026-08-10）**：調整三個環境變數，讓輪替、並行控制與備援機制吸收免費方案的不穩定狀況，而不是因此失敗：

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 遇到 400/401 時切換至其他模型／提供者（略過故障的直通模型）
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # 明確設定重量級請求的准入上限（預設未設定：無請求數量上限，請參閱下方註記）
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # 將有限的等待時間提高至超過慢速上游的 RATE_LIMIT_MAX_WAIT_MS 預設值
```

請在 OmniRoute 程序的環境中設定這些變數（常駐程式，例如透過 LaunchAgent plist 或 `systemctl edit`），然後重新啟動 OmniRoute。輪替旗標是單一效益最高的調整項目：它能將硬性失敗轉換為對集區內健康提供者的透明重試。

**註記**：`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` 會限制可同時執行的重量級（長上下文）請求數量；此限制是准入閘門，而不是提供者速率限制器。**#503-fanout 更新：**此變數不再預設設定（現在只有在明確設定時才會生效，如上所示）——重量級請求的准入改由自動衍生的位元組預算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`）管控；該預算會根據主機的實際記憶體上限自動調整，因此全新部署即使完全不設定此變數，也應該會大幅減少 `503 chat_admission_busy` 拒絕；在此明確設定仍會完全依照文件所述運作。明確指定的位元組預算覆寫值會被限制在 8 MiB–2 GiB 之間。`413 body_exceeds_budget` 並非暫時性問題：請提高該位元組預算、降低 `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`，或提高程序的記憶體上限。`inflight_bytes_budget` 卸載是暫時性的資源爭用，仍可重試。各提供者的速率限制（`open-sse/services/rateLimitManager.ts`）則由 `RATE_LIMIT_MAX_WAIT_MS`、`RATE_LIMIT_MAX_QUEUE_DEPTH` 與 `RATE_LIMIT_AUTO_ENABLE` 分別控制——請參閱 `.env.example`。

**如何驗證修正是否生效**：快速連續執行兩次代理程式／cron，並確認兩次都成功。修正前，第二次執行通常會拋出 `429`／`401`。修正後，系統會自動重試失敗的請求（若有），並完成呼叫。你也可以執行 `curl /monitoring/health`，觀察提供者連線上的 `rateLimitedUntil` 欄位，以及受影響提供者的 `circuitBreakers.providerBreakers[].state`——狀態會是 `CLOSED`、`DEGRADED`、`OPEN` 或 `HALF_OPEN` 之一（請參閱 `src/shared/utils/circuitBreaker.ts`）；持續失敗的提供者會依序從 `CLOSED → DEGRADED → OPEN` 切換，直到重設時間窗允許探測請求通過（`HALF_OPEN`）。

**如果仍然看到 429**：該提供者目前使用中的帳戶確實已耗盡其_配額_（而不只是觸及速率限制）。請在 OmniRoute 儀表板 → Providers → Accounts 中，為同一提供者新增第二個帳戶，或混用另一個免費提供者（例如 `routeway`、`auggie`）。輪替機制只對暫時性的速率限制／400／401 有幫助；若配額已完全耗盡，則需要第二組憑證或改用其他提供者。

**如果在視覺模型（`auto/vision`、`bazaarlink/*`）上看到 403**：已連線的帳戶沒有包含視覺功能的付費方案，或 API 金鑰的權限不足。請在提供者儀表板中確認金鑰的權限範圍包含視覺／多模態功能，或連線至付費方案帳戶，並將其保留為視覺模型的目標帳戶。

## npm install 警告（ERESOLVE / peer / deprecated）

執行 `npm install -g omniroute` 時，您可能會看到大量警告，例如 `npm warn ERESOLVE`、對等依賴項通知及 `deprecated` 訊息。**這些都是預期中的情況，並且不會造成影響。** 如果輸出中出現 `added <N> packages`，即表示安裝成功。

若要隱藏對等依賴項解析警告，請使用 OmniRoute 支援的安裝方式：

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` 只會隱藏 `ERESOLVE` 和對等依賴項通知。棄用通知仍會顯示，因為它們來自遞移的第三方套件；這些通知並不表示安裝失敗。

這些警告來自 OmniRoute 無法控制的第三方套件中過時的對等依賴項版本範圍：

1. **`marked-terminal` 要求 `marked >=1 <16`，但找到的是 `marked@18`** — 實際使用時運作正常；只是上游的對等依賴項版本範圍已過時。
2. **`deprecated prebuild-install@7.1.3`** — 這是遞移依賴的原生二進位檔擷取輔助工具。它不會
   用於安裝已固定版本的 `wreq-js` 傳輸繫結，也不表示 Web Cookie
   提供者的傳輸設定失敗。

**無需採取任何動作** — 除非分支上游套件，否則無法完全消除這些警告。

## npm 安裝指令碼遭封鎖警告（全域安裝）

<a name="npm-install-scripts-blocked-warning-global-install"></a>

執行 `npm install -g omniroute` 時，較新的 npm 版本（v11+ 和 v12+）預設會封鎖套件生命週期指令碼，並顯示安裝指令碼警告：

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### 可以忽略此警告嗎？

**可以部分忽略，但不建議在不執行指令碼的情況下運作。** OmniRoute 內含平穩的備援機制：如果無法從獨立套件組合載入原生 `better-sqlite3` 繫結，應用程式會依序改用其他驅動程式，例如 `node:sqlite` 或 `sql.js`（請參閱 [SQLite 執行階段解析](../ops/SQLITE_RUNTIME.md)）。伺服器仍可啟動，但使用 `sql.js` 之類的 WASM 備援方案時，會停用 SQLite WAL（預寫式記錄）模式，並增加記憶體與磁碟同步負擔。

### 實際需要哪些指令碼？

並非所有遭封鎖的指令碼都是執行 OmniRoute 所必需的：

- **必要（`omniroute`、`better-sqlite3`）：** OmniRoute 從 Next.js 獨立應用程式套件組合（`dist/`）執行。安裝期間，npm 會在頂層 `node_modules/better-sqlite3/` 中下載或編譯主機專用的原生 SQLite 驅動程式。接著，OmniRoute 的 `postinstall` 指令碼（`scripts/build/postinstall.mjs`）會驗證這些主機專用的二進位檔，並將其複製到 `dist/node_modules/`，讓獨立伺服器可以存取它們。如果 `omniroute` 的 postinstall 指令碼遭到封鎖，便會略過此複製步驟。
- **選用／遞移（`keytar`、`@parcel/watcher`、`@swc/core`、`protobufjs`、`esbuild`）：** 這些是建置輔助工具、監看工具或系統鑰匙圈公用程式。允許執行這些指令碼可避免建置警告，但核心路由功能不需要它們。
- **排除（`onnxruntime-node`）：** 這是用於本機 AI 嵌入的選用依賴項，OmniRoute 的執行**不需要**它。其 postinstall 指令碼會從 NuGet 下載約 300MB 的 CUDA 資源；除非您明確打算在支援的硬體上使用本機 ONNX 加速，否則請勿將它加入允許清單。

### 建議的修正方式

若要在全域安裝期間允許執行必要的安裝指令碼並消除警告，請針對 OmniRoute 及其原生依賴項傳入 `--allow-scripts`：

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

或者，若要為您使用者帳戶下的所有全域安裝永久設定此選項：

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### 驗證您的安裝

安裝後，請執行內建診斷工具，確認原生繫結及執行階段環境均正常：

```bash
omniroute doctor
```

## 防毒軟體誤判

<a name="antivirus-false-positives"></a>

### Avast/AVG 以 `MD:HttpRequest-inf[Susp]` 隔離 `README.md`

**這是誤判。沒有任何檔案受到感染，也不需要採取任何動作。**

Avast 和 AVG 會執行一項啟發式檢測，將包含大量看似 HTTP 請求連結的純文字/Markdown 檔案標記出來。OmniRoute 的 `README.md` 包含在 npm 套件中（它列於 `package.json` → `files`），因此進行全域安裝時，該檔案會位於 `node_modules/omniroute/README.md`，而且其中包含約 15 個 `http://localhost:20128/...` 範例（MCP HTTP/SSE 端點、A2A `.well-known` URL，以及 `curl` 程式碼片段）。如此高的連結密度足以觸發該啟發式檢測。

如果這個問題最近才開始出現：檔案的性質並未改變。README 擴充了端點表格（新增了 MCP HTTP + SSE + A2A）以及更多 `curl` 範例，使其超過了觸發門檻。

此檔案只是靜態文件，完全不含任何可執行內容。您可以放心地將它從隔離區還原。

**處理方式：**

1. **停止通知** — 在防毒軟體中排除安裝目錄（Avast：設定 → 例外），加入您的全域 `node_modules` 路徑及/或 OmniRoute 資料目錄（`~/.omniroute/`）。
2. **回報誤判** — <https://www.avast.com/false-positive-file-form.php>，並附上遭隔離的 `README.md`。這才是對所有人都有幫助的解決方式，因為問題在於提供者的啟發式檢測對文字檔反應過度。

**為什麼我們不從自身這一側「修正」問題：**所有範例都是 `http://localhost`，而 localhost 若沒有自簽憑證所帶來的麻煩，就無法使用 `https`。為了規避單一提供者的啟發式檢測而竄改文件，等於為了迎合掃描器的錯誤而損害所有讀者的使用體驗。

### Kaspersky 將桌面應用程式標記為 `PDM:Trojan.Win32.Generic`

**這是行為啟發式檢測造成的誤判。沒有任何檔案受到感染。** Kaspersky 的 `PDM:` 前綴表示判定來自其主動防禦模組（System Watcher）；該模組會根據安裝程式的實際_行為_進行判斷，而非比對已知惡意軟體。觸發時，Kaspersky 會「復原」整個安裝程序，刪除它先前已寫入的檔案，因此最終會導致應用程式損壞或遺失。

它標記的檔案是桌面應用程式所封裝、已宣告之開放原始碼相依套件的標準組成部分，例如：

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` 和
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)，用於應用程式內提供者登入和瀏覽器支援聊天功能的瀏覽器自動化程式庫。
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — 固定版本的 `wreq-js` 原生繫結，用於在採用網頁 Cookie 的提供者上執行帶有瀏覽器指紋的 HTTP 請求（`<arch>` 為 `x64` 或 `arm64`）。

**觸發原因：**Windows 安裝程式**尚未經過程式碼簽署**，因此未簽署的 NSIS 安裝程式信譽為零，行為啟發式檢測會以最高強度執行。再加上封裝的原生 DLL，以及寫入 `%LOCALAPPDATA%\Programs\OmniRoute` 下的數百個 `.js` 檔案（包括 Next.js 獨立建置所產生、名稱帶有雜湊值後綴的套件目錄），這些因素已足以觸發啟發式檢測。我們已規劃進行程式碼簽署；在完成之前，新版本仍可能重複發生此問題。

**處理方式：**

1. **先驗證您下載的檔案**（排除檔案遭竄改的可能性）。每個版本都會發布 `latest.yml`，其中的 `sha512` 欄位（base64）涵蓋 `OmniRoute.Setup.<version>.exe` 安裝程式。在 PowerShell 中，於包含安裝程式的資料夾執行：
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   輸出必須與 `latest.yml` → `sha512` 相符。如果不相符，請刪除該檔案，並僅從 [GitHub 發行頁面](https://github.com/diegosouzapw/OmniRoute/releases)重新下載。
2. **還原 + 排除** — 從隔離區還原遭復原的項目，並為 `%LOCALAPPDATA%\Programs\OmniRoute` 新增排除項目（Kaspersky → 設定 → 威脅與排除項目），然後重新安裝。
3. **回報誤判** — <https://opentip.kaspersky.com/>。使用者提交的誤判回報確實能加快加入允許清單的速度。

## Node.js 相容性

<a name="nodejs-compatibility"></a>

### 登入頁面當機或顯示「Module self-registration」錯誤

**原因：** 您執行的 Node.js 版本不符合 OmniRoute 核准的安全執行環境最低版本要求。最常見的情況是執行較舊的 Node 22 或 24 修補版本，低於 OmniRoute 要求的安全修補最低版本。

**症狀：**

- 登入頁面顯示空白畫面或伺服器錯誤
- 主控台顯示 `Error: Module did not self-register` 或類似的原生繫結錯誤
- 如果執行環境不符合支援的安全性政策，登入頁面會顯示包含您 Node 版本的**橘色警告橫幅**

**修正方式：**

1. 安裝受支援的 Node.js LTS 版本（建議：Node.js 24.x）：
   ```bash
   nvm install 24
   nvm use 24
   ```
2. 驗證您的版本：`node --version` 應在 24.x LTS 系列中顯示 `v24.0.0` 或更新版本
3. 重新安裝 OmniRoute：`npm install -g omniroute`
4. 重新啟動：`omniroute`

> **受支援的安全版本：** `>=22.22.2 <23` 或 `>=24.0.0 <27`。完整支援 Node.js 24.x LTS (Krypton) 和 Node.js 26。

### npm v11+：未安裝 `better-sqlite3`（Cannot find module）

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**原因：** npm v11（隨 Node.js 24+ 提供）預設會封鎖選用相依套件的安裝指令碼。由於 `better-sqlite3` 列在 `optionalDependencies` 中，且需要進行原生編譯（`node-gyp rebuild`），npm 會在不顯示訊息的情況下略過它。

**症狀：**

- 伺服器啟動時因 `Cannot find module 'better-sqlite3'` 而當機
- `ls node_modules/better-sqlite3` 顯示「No such file or directory」
- `npm ls better-sqlite3` 顯示 `(empty)`

**修正方式：**

1. 核准安裝指令碼並重新安裝：
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. 或手動安裝預先建置的套件：
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. 驗證其能否正常運作：`node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS：`dlopen` /「slice is not valid mach-o file」

<a name="macos-native-module-rebuild"></a>

**原因：** 全域執行 `npm install -g omniroute` 後，套件內的 `better-sqlite3` 原生二進位檔可能是針對與本機執行環境不同的架構或 Node.js ABI 所編譯。當預先建置的二進位檔與您的環境不相符時，這種情況在 macOS（包括 Apple Silicon 和 Intel）上很常見。

**症狀：**

- 伺服器啟動時立即因 `dlopen` 錯誤而失敗
- 錯誤包含 `slice is not valid mach-o file`
- 完整範例：

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**修正方式 — 針對您的本機環境重新建置（不需要降級 Node.js）：**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **注意：** 這會根據您的本機 Node.js 版本和 CPU 架構重新編譯原生繫結，從而解決二進位檔不相符的問題。官方支援的執行環境範圍為 **`>=22.22.2 <23` 或 `>=24.0.0 <27`**（`src/shared/utils/nodeRuntimeSupport.ts` 中的 `SUPPORTED_NODE_RANGE`，並與 `package.json` 的 `engines` 欄位保持一致）。完整支援 Node.js 24.x LTS (Krypton) 和 Node.js 26 搭配 `better-sqlite3` v12.x。

## Proxy 問題

<a name="proxy-issues"></a>

### 提供者驗證顯示「fetch failed」

**原因：** API 金鑰驗證端點 (`POST /api/providers/validate`) 先前會略過 Proxy 設定，導致在需要透過 Proxy 路由的環境中發生失敗。

**修正（v3.5.5+）：** 此問題現已修正。提供者驗證會透過 `runWithProxyContext` 路由，自動採用提供者層級與全域 Proxy 設定。

### Token 健康狀態檢查因「fetch failed」而失敗

**原因：** 背景 OAuth Token 重新整理未依各連線解析 Proxy 設定。

**修正（v3.5.5+）：** Token 健康狀態檢查排程器現在會在嘗試重新整理前，依各連線解析 Proxy 設定。請更新至 v3.5.5+。

### SOCKS5 Proxy 傳回「invalid onRequestStart method」

**原因：** 在 Node.js 22 上，undici@8 dispatcher 與 Node 內建的 `fetch()` 實作不相容。

**修正（v3.5.5+）：** 當 Proxy dispatcher 啟用時，OmniRoute 現在會使用 undici 自有的 `fetch()` 函式，以確保行為一致。請更新至 v3.5.5+。

### WSL 下的 MITM Proxy：Windows 主機上的桌面應用程式未被攔截

**原因：** MITM Proxy 及其 CA 憑證會安裝到 OmniRoute 執行所在的環境。在 WSL 下，該環境是 Linux 客體，而 AI 桌面應用程式（Kiro、Trae、Copilot、Zed，……）則執行於 Windows 主機上。主機應用程式不信任客體的憑證存放區，也不會透過客體的系統 Proxy 路由，因此無法對桌面應用程式進行攔截。

**建議：** 請在與欲攔截之桌面應用程式相同的作業系統上原生執行 OmniRoute（Windows 應用程式使用 Windows；macOS/Linux 亦同）。若將 OmniRoute 保留在 WSL 中並以主機應用程式為目標，則必須在 Windows 主機上手動信任產生的 CA 憑證，並將每個主機應用程式的網路／Proxy 設定指向 WSL Proxy 端點——此設定方式不受支援且容易失效。

## 提供者問題

### 「Language model did not provide messages」

**原因：** 提供者配額已用盡。

**修正：**

1. 檢查儀表板的配額追蹤器
2. 使用具有備援層級的組合
3. 切換至較便宜／免費的層級

### 速率限制

**原因：** 訂閱配額已用盡。

**修正：**

- 新增備援：`cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- 使用 GLM/MiniMax 作為低成本備援

### OAuth Token 已過期

OmniRoute 會自動重新整理 Token。如果問題持續發生：

1. 儀表板 → 提供者 → 重新連線
2. 刪除並重新新增提供者連線

### Kiro 多帳號：第二個帳號會使第一個帳號失效

**原因：** Kiro 的後端會針對每個 OIDC 用戶端註冊強制限制只能有一個作用中的工作階段。
當兩個帳號共用相同的已註冊用戶端（v3.8.0 之前匯入的連線）時，
重新整理其中一個帳號的 Token 會使另一個帳號的重新整理 Token 失效。

**修正（v3.8.0+）：** 重新匯入受影響的連線。
從 v3.8.0 開始，透過**匯入 Token**、
**Google/GitHub 社群登入**或**自動匯入**建立的每個新 Kiro 連線，都會自動註冊各自
專用的 OIDC 用戶端。因此，連線會完全隔離，重新整理其中一個
帳號不會影響任何其他帳號。

在 v3.8.0 _之前_匯入的連線不包含個別連線專用的用戶端
註冊。這些連線會繼續使用共用的社群驗證重新整理端點。
若要達成隔離，請從「儀表板 → 提供者」刪除舊連線，然後透過
上述三種匯入流程中的任一種重新新增。

如需完整詳細資訊，以及並列新增兩個 Kiro 帳號的逐步操作說明，
請參閱 [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md)。

## Docker 問題

### Docker IPv6／連線重設

<a name="docker-ipv6"></a>

**症狀：** `curl http://localhost:20128/v1/models` 傳回 `curl: (56) Recv failure: Connection reset by peer`。儀表板和未驗證的端點可正常運作，但需要驗證的端點會失敗——看起來像是驗證問題，但實際上並不是。

**原因：** `docker run -p 20128:20128` 會同時發佈至 `0.0.0.0`（IPv4）和 `::`（IPv6），但容器內的程序只監聽 IPv4。在 `localhost` 優先解析為 `::1` 的主機上，連線會進入已發佈的 IPv6 連接埠，但其後方沒有監聽程式 → 連線遭到重設。

**修正方式：**

1. **快速診斷：** 執行 `curl -4 http://localhost:20128/v1/models`。如果加上 `-4` 後可以運作，但未加時失敗，表示您遇到了 IPv6 繫結不相符的問題。
2. **永久修正：** 在 `docker run` 命令中使用 `-p 127.0.0.1:20128:20128`，明確繫結至 IPv4：
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   這會強制使用 IPv4 繫結，也可避免將代理伺服器暴露於主機的所有介面上。

## 韌性設定

### 自動速率限制未觸發

- 自動速率限制僅適用於 API 金鑰提供者（不適用於 OAuth／訂閱）
- 確認 **設定 → 韌性 → 提供者設定檔** 已啟用自動速率限制
- 檢查提供者是否傳回 `429` 狀態碼或 `Retry-After` 標頭

### 調整指數退避

提供者設定檔支援下列設定：

- **基礎延遲** — 第一次失敗後的初始等待時間（預設：1 秒）
- **最大延遲** — 等待時間上限（預設：30 秒）
- **倍數** — 每次連續失敗後延遲時間的增加倍數（預設：2 倍）

### 防止驚群效應

當大量並行請求觸及受速率限制的提供者時，OmniRoute 會使用互斥鎖與自動速率限制來將請求序列化，並防止連鎖失敗。對 API 金鑰提供者而言，此機制會自動運作。

### 聊天請求因 503 / chat_admission_busy 而失敗

**症狀：**

- 聊天補全端點傳回可重試的 `503` 回應，其錯誤代碼為
  `chat_admission_busy`。
- 回應包含 `Retry-After`。自 #12135 起，其值會根據觀察到的
  佔用情況推算而得——取請求已等待的 `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` 時間窗
  與目前重量級租約已持有時間兩者中的較大值——向上取整為整秒，
  並以 60 秒為上限。當閘門閒置時，仍會維持既有的下限：以位元組為基礎的路徑為 2 秒，
  以結構為基礎的路徑為 1 秒（後者也會包含
  `reason: "structure_limit"`）。
- 當另一個重量級聊天或長時間執行的串流回應仍在進行中時，
  可能會發生此情況。

以位元組為基礎的回應本文如下：

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

以結構為基礎的回應使用相同的類型與代碼，其訊息為
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
並包含 `reason: "structure_limit"`。
在預設閾值下，當請求至少有 `200` 則訊息、
至少 `64` 個工具、至少 `32,000` 個估算權杖，或有界結構估算
耗盡其 `10,000` 個已造訪節點或深度 `12` 的界限時，即視為結構上重量級的請求。

**原因：** 這是 OmniRoute 內部刻意執行的負載卸除，而非上游提供者故障。
每個處理程序都會使用處理程序本機防護機制，在保留並剖析大型請求本文之前，
預留有限的重量級容量。在 SSE 回應的整個生命週期內，重量級租約都會維持占用。

**#503 扇出：** 在此修正之前，無論主機記憶體多寡，防護機制都會以固定的請求數量
（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`，預設為 `1`）限制並行處理，因此程式設計代理程式的
扇出（多個子代理程式／CLI，本文通常 > 256 KB）會讓有效並行數降至約 1，
並在完全正常的負載下收到 503。防護機制現在會自我調整：其閘控依據為自動推算的擷取
位元組預算（`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`），該預算會根據處理程序的實際記憶體上限
決定大小，並且也會參考即時資源壓力訊號——因此，只有當主機確實面臨記憶體壓力時
才會卸除負載，而不會僅因同時收到一個以上的重量級請求就這麼做。舊版數量上限
（`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`）仍會生效，但前提是您明確設定它。

當容量忙碌時，重量級請求會先等待最多
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`（預設為 `RATE_LIMIT_MAX_WAIT_MS`；`0` 會停用等待），等候釋出空位，
然後才會回覆可重試的 `503`。此有界等待機制可讓以代理程式方式運作的用戶端
（OpenCode、Claude Code、Cursor）在並行扇出重量級子請求時將突發流量序列化，
而不是因立即遭拒而耗盡所有重試額度，並在工作進行到一半時失敗。
目前的重量級租約佔用情況、解析後的位元組預算，以及即時壓力嚴重程度，
均顯示於 `GET /api/monitoring/health` → `chatAdmission`（`inflightBytes`、`maxInflightBytes`、
`budgetSource`、`pressureSeverity`、`countCapEnabled`）——在調整任何環境變數前，請先檢查這些資訊。
設定 → 韌性 → 請求佇列 → 並行請求不會控制此機制；該設定
管理的是另一套提供者請求佇列機制。

**修正方法：**

1. 先重試。用戶端應遵循 `Retry-After` 並使用退避機制，而非立即
   重複傳送請求。
2. 調整任何項目之前，先檢查 `/api/monitoring/health` → `chatAdmission`。`countCapEnabled:
false` 且 `maxInflightBytes` 充足，表示自動推算的預算已正常
   發揮作用；若 `pressureSeverity` 為 `high`/`critical`，表示主機確實記憶體不足——
   這無法透過准入環境變數修正，而是需要更多 RAM 或較小的工作負載。
3. 僅當 `/api/monitoring/health` 顯示自動推算的預算對您的主機而言確實過小時
   （這很少見——它已可從容器擴展至裸機），才應直接使用
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` 覆寫，而不要退回使用舊版的請求數量上限。

如需具權威性的准入設定，請參閱[環境變數參考資料](../reference/ENVIRONMENT.md#4-security--authentication)。

## 選用的 RAG / LLM 失敗分類（16 個問題）

部分 OmniRoute 使用者會將閘道置於 RAG 或代理堆疊前方。在這類設定中，經常會看到一種奇怪的情況：OmniRoute 看起來運作正常（提供者在線、路由設定檔正常、沒有速率限制警示），但最終答案仍然是錯誤的。

實務上，這類事件通常源自下游 RAG 管線，而不是閘道本身。

如果你希望使用一套共通詞彙來描述這些失敗，可以使用 WFGY ProblemMap。這是一份採用 MIT 授權的外部文字資源，定義了十六種反覆出現的 RAG / LLM 失敗模式。概括而言，其涵蓋：

- 檢索偏移與上下文邊界破損
- 空白或過期的索引與向量儲存庫
- 嵌入與語意不相符
- 提示組裝與上下文視窗問題
- 邏輯崩潰與過度自信的答案
- 長鏈與代理協調失敗
- 多代理記憶與角色偏移
- 部署與啟動順序問題

概念很簡單：

1. 調查不良回應時，請記錄：
   - 使用者任務與請求
   - OmniRoute 中的路由或提供者組合
   - 下游使用的任何 RAG 上下文（檢索到的文件、工具呼叫等）
2. 將事件對應至一或兩個 WFGY ProblemMap 編號（`No.1` … `No.16`）。
3. 在你自己的儀表板、操作手冊或事件追蹤器中，將該編號與 OmniRoute 日誌一併儲存。
4. 使用對應的 WFGY 頁面來判斷是否需要變更 RAG 堆疊、檢索器或路由策略。

完整內容與具體操作方式請參閱此處（MIT 授權，純文字）：

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

如果你未在 OmniRoute 後方執行 RAG 或代理管線，可以忽略本節。

## v3.8.0 已知問題

v3.8.0 版本特有的問題及其目前的因應措施。如果修正已包含在後續修補版本中，相關項目將會更新或移除。

### Devin CLI 驗證失敗

**症狀：**

- 呼叫由 Devin 支援的工具時，出現「找不到 Devin CLI」或「驗證失敗」
- CLI 執行階段檢查回報 `installed=false`

**原因：**

- `CLI_DEVIN_BIN` 指向不存在的路徑
- 主機上未安裝 Devin CLI

**修正方式：**

1. 安裝適用於你平台的 Devin CLI
2. 在 `.env` 中設定 `CLI_DEVIN_BIN=/usr/local/bin/devin`（或實際路徑）
3. 重新啟動 OmniRoute，並從 **儀表板 → CLI 工具**重新測試

### 模型冷卻卡住（手動重設）

**症狀：**

- 即使到期時間已過，模型仍列於冷卻狀態
- 儘管時間戳記已是過去時間，組合路由仍會略過該模型

**手動重設：**

- **儀表板：** **設定 → 模型冷卻** → 在受影響的卡片上按一下**重新啟用**
- **API：** 使用管理驗證標頭傳送 `DELETE /api/resilience/model-cooldowns`

### Command Code 提供者連線失敗並回傳 403

**症狀：**

- 測試 Command Code 提供者連線時收到 403
- 新增後，提供者卡片顯示「未授權」

**原因：** OAuth 流程未完成（未收到回呼或權杖未持久化）。

**修正方式：**

- 從 CLI 執行 `omniroute providers` 以重新觸發 OAuth 流程，或
- 從**儀表板 → 提供者 → Command Code → 重新連線**再次執行 OAuth

### ModelScope 回傳過於激進的 429 冷卻

**症狀：**

- 在短暫的請求突發後，ModelScope 上出現非常短暫或立即生效的冷卻
- 組合路由比預期更早略過 ModelScope

**原因：** ModelScope 會發出提供者特定的 `Retry-After` 標頭。v3.8.0 內建了這些標頭的專用處理機制，因此較舊版本會將其誤讀為一般速率限制提示。

**修正方式：**

- 確認你使用的是 v3.8.0 或更新版本
- 確認已在**設定 → 韌性**下啟用 `useUpstream429BreakerHints` 切換開關

### 正式環境中缺少 OMNIROUTE_WS_BRIDGE_SECRET

**症狀：**

- 在遠端正式環境主機上執行時，每個 Codex/Responses WebSocket 橋接請求都收到 401
- WebSocket 橋接交握在連線後立即關閉

**原因：** 正式環境中缺少 `OMNIROUTE_WS_BRIDGE_SECRET` 環境變數。

**修正方式：**

1. 產生隨機密鑰：`openssl rand -hex 32`
2. 在正式環境伺服器的環境中設定 `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>`（以及任何與橋接通訊的用戶端）
3. 重新啟動 OmniRoute

### Responses API：背景模式降級為同步模式

**症狀：**

- 記錄警告：`background mode degraded to synchronous`
- `background: true` 請求回傳一般同步回應，而不是背景工作控制代碼

**原因：** v3.8.0 會刻意將 Responses API 上的 `background: true` 降級為同步執行，同時發出警告。完整的非同步背景執行是未來的交付項目。

**修正方式：**

- 調整用戶端，使其呼叫時不使用 `background`，或
- 等待提供完整非同步背景模式的後續版本（追蹤變更日誌）

## 啟動緩慢 / 就緒逾時

如果 CLI 顯示 `⚠ Server did not respond within 60s`，但伺服器實際上仍可正常運作，表示就緒探測的時間上限對您的環境而言太短。

這種情況常見於 Windows（防毒軟體、檔案系統監看程式），或啟動工作負載較重的容器。

**修正方式 — 提高時間上限：**

```bash
# 透過環境變數（在多次啟動之間持續有效）：
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 分鐘
omniroute serve

# 透過 CLI 旗標（單次有效）：
omniroute serve --ready-timeout 180000
```

預設值為 60 000 毫秒（60 秒）。此警告僅供參考；伺服器會繼續在背景啟動，並在啟動完成後可供存取。

如需 `OMNIROUTE_READY_TIMEOUT_MS` 的完整詳細資訊，請參閱 [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)。
