`open-sse/config/providerPluginManifest.ts` 定義 JSON 安全的提供者
外掛契約。`open-sse/config/providerPluginManifestRegistry.ts` 會將該
契約繫結至目前的提供者註冊表，供 Bifrost、
CLIProxyAPI 或未來的 Go/Rust 路由器等 sidecar 使用。TypeScript 註冊表仍是
唯一真實來源，但 sidecar 無須匯入執行器程式碼、OAuth 預設值、標頭或處理程序環境狀態，
即可使用資訊清單。

對於程序外執行的 sidecar，也可透過 HTTP
`GET /api/v1/provider-plugin-manifest` 取得相同的資訊清單。

OmniRoute 會透過 `X-OmniRoute-Provider-Manifest-Url` 要求標頭，
向 Bifrost 和 CLIProxyAPI 公告該 URL。當 sidecar 需要使用公開或容器
網路 URL，而非本機要求來源時，請設定
`OMNIROUTE_PROVIDER_MANIFEST_URL`。

## 重新整理資訊清單

HTTP 端點會傳回 `Cache-Control: public, max-age=60` 和強式
`ETag`。sidecar 應保留最後一份已驗證的資訊清單，並在重新整理時透過
`If-None-Match` 傳送其 ETag。`304 Not Modified` 回應沒有本文；
sidecar 會繼續使用其快取的資訊清單。如果不存在已驗證的快取資訊清單，
sidecar 必須發出無條件要求，而非接受 `304`。

## 目標

將提供者中繼資料逐步移向外掛契約，使低延遲 sidecar 最終能接管
高頻要求路徑，同時 OmniRoute 保留 TypeScript 路由作為政策閘道與後援。
此資訊清單是附加性的：它本身不會變更要求路由。

## 契約

資訊清單包含：

- 提供者 id 與別名
- 上游格式與執行器名稱
- 驗證類型、驗證標頭，以及選用的驗證前綴
- 靜態端點中繼資料
- sidecar 適用資格，以及提供者應保留在 TS 路徑上的明確原因
- JSON 安全的模型中繼資料，例如上下文長度、視覺／推理旗標，以及
  不支援的參數
- 能力標籤，包括 `apikey`、`oauth`、`custom-executor`、
  `passthrough-models`、`responses`、`sidecar-candidate`、`usage-fetch` 和 `usage-supported`

資訊清單刻意排除：

- OAuth 用戶端密鑰與預設密鑰值
- 執行階段環境解析
- 要求標頭與公開憑證輔助程式
- 動態 URL 建構器
- 執行器函式
- 工作階段集區內部實作

## 能力標籤

`capabilities` 是由註冊表項目衍生並排序的標籤陣列。整合者應將其視為
「此提供者能做什麼」的機器可讀答案，而不是重新閱讀 TypeScript 原始碼。

| 標籤                 | 意義                                                    |
| -------------------- | ------------------------------------------------------- |
| `apikey`             | 接受 API 金鑰（`authType` 為 `apikey` 或 `optional`）。 |
| `oauth`              | 使用 OAuth 或工作階段流程。                             |
| `responses`          | 公開 OpenAI Responses API 基礎 URL。                    |
| `passthrough-models` | 直接提供上游模型，而非使用靜態目錄。                    |
| `custom-executor`    | 執行非預設執行器，因此會保留在 TypeScript 路徑上。      |
| `sidecar-candidate`  | 對應 `sidecar.eligible` — 可安全地考慮匯入 sidecar。    |
| `usage-fetch`        | 已連接用量或配額擷取器（`getUsageForProvider`）。       |
| `usage-supported`    | 用量 API 接受此提供者（`isSupportedUsageConnection`）。 |

`usage-fetch` 僅供探索使用。它表示 OmniRoute 知道如何讀取該提供者的用量；
它不會啟用擷取、變更配額語意，也不表示已為該提供者啟用儀表板配額小工具——
該小工具由 `USAGE_SUPPORTED_PROVIDERS` 另行控管。唯一真實來源是
`open-sse/services/usage/fetcherProviders.ts` 中的 `USAGE_FETCHER_PROVIDERS`。

該清單以用量分派器接受的字串為索引鍵，因此混合了標準 id 與別名，
且略長於已加上標籤的提供者數量：資訊清單註冊表中並非聊天提供者的項目
（例如 `firecrawl` 搜尋提供者和 `amazon-q` ACP 提供者）
沒有可加上標籤的資訊清單項目。

`usage-supported` 表示伺服器和儀表板用量路由是否接受該提供者的連線。
它對應 `isSupportedUsageConnection()`（`src/lib/usage/providerLimits.ts`）
和 `supportsProviderQuota()`（`src/shared/utils/providerQuotaVisibility.ts`），
兩者皆由 `USAGE_SUPPORTED_PROVIDERS`
（`open-sse/services/usage/supportedProviders.ts`）控管。與
`usage-fetch` 不同，它只會根據提供者 id 發出——執行階段防護會執行
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)`，且不解析別名，因此資訊清單
會維持相同規則。這兩個標籤的涵蓋範圍不同：有 3 個提供者只有
`usage-fetch`（`opencode`、`opencode-zen`、`xai`），另有 1 個提供者只有
`usage-supported`（`xiaomi-mimo-token-plan`），因此其中一個並不代表另一個。

## Sidecar 使用方式

Sidecar 應將 `sidecar.eligible` 視為保守的候選訊號，而非無條件的路由決策。第一批匯入目標應為使用預設執行器，且採用 API 金鑰與靜態端點的提供者。使用自訂 Web 執行器、OAuth／工作階段流程、動態 URL 建構器或資源池設定的提供者，應繼續使用 TypeScript 備援路徑，直到 Sidecar 實作等效行為，且遙測資料證明兩者具有同等表現為止。

建議的遷移階段：

1. 從 TS 登錄檔產生並驗證提供者外掛程式資訊清單。
2. 讓 Bifrost 或 CLIProxyAPI 能夠為採用 API 金鑰／靜態端點的提供者匯入該資訊清單。
3. 在 `OMNIROUTE_RELAY_BACKEND` 的控管下，透過 Sidecar 路由符合資格的提供者，同時保持啟用 TS 備援。
4. 只有在成功率、p99 延遲、串流行為及不支援參數的處理方式皆與 TS 路徑一致時，才升級提供者。
5. 逐一針對各提供者系列，為自訂執行器新增 Sidecar 原生外掛程式。

## 為何不直接將提供者嵌入 Next

Next 前端不應負責執行提供者邏輯，而應呼叫 API 邊界。接著，後端可以決定要使用 TypeScript 執行器、Bifrost、CLIProxyAPI，或未來的原生 Sidecar。如此可在交由任何 Sidecar 處理之前，集中管理請求簽署、允許清單檢查、DB 政策及備援行為。
