無需 IDE 工作階段，即可將 Cursor 置於 OmniRoute 後方的兩種方式：

1. **`cursor-api` 提供者**（卡片「Cursor API」，別名 `cua`）：使用 API 金鑰的
   提供者，保存 Cursor 使用者 API 金鑰（`crsr_…`，於
   `https://cursor.com/dashboard/api` 產生）。任何 OmniRoute 用戶端都能透過
   `/v1/chat/completions`，以 `cursor-api/<model>` 或
   `cua/<model>` 存取 Cursor 模型，並套用一般的配額、後援與記錄層。IDE
   提供者（`cursor`，OAuth/IDE 工作階段）維持不變。
2. **Cursor CLI 直通代理**：將 Cursor CLI（`agent`）指向 OmniRoute，使 CLI
   發出的每個 RPC 都使用 OmniRoute API 金鑰進行驗證，並以 `cursor-api`
   連線的憑證轉送至 Cursor，同時記錄於 Logs 頁面。

## 為何需要交換金鑰

`api2.cursor.sh` 會拒絕將原始 `crsr_…` 金鑰作為 Bearer 權杖（401）。Cursor
CLI 會先將金鑰 POST 至 `/auth/exchange_user_api_key`，並取得一個一小時後
到期的工作階段 JWT；傳回的 `refreshToken` 具有相同的 `exp`，因此重新整理
實際上就是再次交換金鑰。
`open-sse/services/cursorApiKeyAuth.ts` 會執行該交換、為每個金鑰快取一個
工作階段權杖、在到期前五分鐘重新交換，並在 Cursor 回應 401 時捨棄快取的
權杖。`CursorExecutor` 會在為 `cursor-api` 連線開啟上游串流前立即呼叫它。

## `cursor-api` 提供者

登錄檔：`open-sse/config/providers/registry/cursor/index.ts`
（`cursor_apiProvider`、`authType: "apikey"`，並具有與 `cursor` 相同的
`format`、`baseUrl` 和 `models`）。目錄卡片：
`src/shared/constants/providers/apikey/specialty-media.ts`。執行器對應表：
`open-sse/executors/index.ts`（`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`）。

控制台：Providers → Cursor API → Add API key。

REST：

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

接著：

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

注意事項：

- `cursor-api` 的模型清單來自靜態 Cursor 登錄檔（與 IDE 提供者後援使用的
  清單相同）；OmniRoute 主機無需安裝 `cursor-agent`。
- `POST /api/providers/{id}/refresh-cursor` 僅適用於 `cursor` IDE 提供者；
  `cursor-api` 連線沒有需要續期的 IDE 工作階段。

## Cursor CLI 直通代理

路由：`src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`。前綴 `/api/cursor-cli/` 已登錄於
`src/shared/constants/publicApiRoutes.ts`，因為處理常式會自行強制執行驗證：

| 路徑                                                                                                                      | CLI 應提供的驗證             | OmniRoute 的處理方式                                                                                                            |
| ------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                        | `Bearer <OmniRoute API key>` | 驗證金鑰、簽發一個 1 小時的 HS256 JWT（使用 `JWT_SECRET` 簽署），然後將其傳回                                                   |
| 所有其他路徑（`/aiserver.v1.*`、`/agent.v1.AgentService/RunSSE`、`/aiserver.v1.BidiService/BidiAppend`、`/v1/traces`、…） | `Bearer <that JWT>`          | 驗證簽發者／受眾／到期時間、選取作用中的 `cursor-api` 連線、將 Authorization 標頭替換為交換所得的 Cursor 權杖，並將回覆串流傳回 |

CLI 會從收到的任何權杖中解碼 `exp`，因此若交給它不透明權杖，它幾乎會在每次
請求前重新交換；簽發的 JWT 可避免此情況。OmniRoute 回傳 401 時，CLI 會再次
執行交換。

### 設定

1. 建立 OmniRoute API 金鑰（控制台 → API keys）以及一個 `cursor-api`
   連線。
2. 指示 CLI 對代理程式串流使用 HTTP/1.1。於
   `~/.cursor/cli-config.json` 中：

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   若未如此設定，CLI 會透過 HTTP/2，向另行設定的代理程式主機開啟代理程式
   回合，而只有控制平面 RPC 會經過該端點。

3. 對 OmniRoute 執行 CLI：

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

每個躍點都會出現在 Logs 中，提供者為 `cursor-api`、請求類型為
`cursor-cli`、路徑為 `/api/cursor-cli/<rpc>`，並歸屬於 OmniRoute API 金鑰
及處理該請求的連線。

### 失敗模式

| 情況                                           | 對 CLI 的回應                                   |
| ---------------------------------------------- | ----------------------------------------------- |
| 未知的 OmniRoute 金鑰且 `REQUIRE_API_KEY=true` | 交換時回傳 401 `unauthenticated`                |
| `REQUIRE_API_KEY=false`                        | 匿名工作階段（與 `/v1/*` 的行為一致）           |
| 已過期／外部／遭竄改的工作階段 JWT             | 401，CLI 會重新交換                             |
| OmniRoute API 金鑰在交換後遭撤銷               | 下一次 RPC 時回傳 401                           |
| 沒有作用中的 `cursor-api` 連線                 | 503 `unavailable`                               |
| Cursor 拒絕連線的金鑰                          | 401 `unauthenticated`，已快取的工作階段會被刪除 |
| 上游無法連線                                   | 502 `unavailable`（已清理的訊息）               |
| 未設定 `JWT_SECRET`                            | 交換時回傳 503                                  |
