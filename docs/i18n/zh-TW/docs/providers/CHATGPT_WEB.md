`chatgpt-web-codex`（別名 `cgpt-codex`）透過已驗證的 ChatGPT 瀏覽器工作階段橋接 Codex Responses 輪次。它獨立於已停用的共用 `chatgpt-web` 提供者，並使用位於 `open-sse/vendor/codex-chatgpt-web/`、包含 MIT 聲明的實作；該實作已更新至上游 v4.0.7 提交 `b59d7dc51b84fb1f465ff1d00f5207f3b2b4a494`。

## 共用提供者停用

先前的共用提供者 ID `chatgpt-web` 和 `cgpt-web` 已不再隨附，因為其 pre-key／工作量證明實作的來源無法釐清。對任一 ID 的明確請求（包括以斜線為前綴的模型 ID 和持久化別名）都會在發出任何上游請求之前，以 HTTP `410` 和代碼 **PROVIDER_RETIRED** 採取封閉式失敗。

遷移 `168_retire_chatgpt_web.sql` 會將相符的提供者連線標記為已停用，並使其有效的工作階段租約失效。它會保留連線歷程和 API 金鑰允許清單；但不會將替代存取權新增至允許清單。此次停用不會比對到 Codex 提供者及其連線。

## 先決條件

- 已登入 ChatGPT 工作階段的完整 Cookie 標頭；
- Chrome 或 Chromium，以及供 npm、systemd 和 PM2 安裝使用的圖形工作階段或 Xvfb 顯示環境；
- 使用 Docker `web` 設定檔時，需要 `docker-compose.yml` 中的內部 Chromium 服務；
- OpenAI `tunnel-client` v0.0.13，以及用於本機 Codex 工具的 ChatGPT 自訂連接器。

只有工具輪次需要通道。當通道和連接器皆已設定時，列出的每個路由（包括 `pro`）都可以使用相同、與輪次繫結的本機工具功能。

## 儀表板設定

1. 開啟 **ChatGPT Web (Codex)** 提供者並新增連線。
2. 貼上完整的 ChatGPT Cookie 標頭、通道 ID、執行階段金鑰和自訂連接器名稱。新的工具功能設定必須使用新建立且名稱完全為 `OmniRoute Codex v2` 的連接器，並將 Authentication 設為 None、Permissions 設為 Allow all actions。
3. 執行連線檢查。OmniRoute 會開啟由瀏覽器支援的 Temporary Chat，並偵測該帳戶是否可使用 Sol 和 Pro。
4. 儲存連線。OmniRoute 會以已驗證的 Playwright 儲存狀態取代貼上的 Cookie，並透過加密憑證抽象層將其與執行階段金鑰一同儲存。

成功儲存後，原始 Cookie 不會被保留。工作階段過期時，請開啟連線、貼上新的完整 Cookie 標頭，然後重新執行檢查。編輯對話方塊中的診斷狀態會分別回報瀏覽器、儲存狀態、登入、Temporary Chat、通道、連接器及工具往返測試的狀態。

> 切勿提交真實的 Cookie、執行階段金鑰、儲存狀態或功能權杖。測試和
> 文件中的值一律必須使用預留位置。

## 模型和組合

固定的模型路由如下：

- `chatgpt-web-codex/luna` — GPT-5.6 Luna，低推理強度
- `chatgpt-web-codex/think` — GPT-5.6 Luna，中等推理強度
- `chatgpt-web-codex/instant`
- `chatgpt-web-codex/medium`
- `chatgpt-web-codex/high`
- `chatgpt-web-codex/extra-high`
- `chatgpt-web-codex/pro`

如同其他模型，將其中一個加入組合即可。Codex 應用程式會將組合名稱作為 `model` 傳送至一般的 Responses 端點 `/v1/responses`；不存在獨立的 Codex 端點或模式切換。

Free／Go 帳戶會提供 Luna 路由。支援 Sol 的帳戶會提供 Instant 至 High，而支援 Pro 的帳戶還會提供 Extra High 和 Pro。每個路由都有固定的後端模型和推理強度；若明確指定了與其衝突的 Responses 推理強度，系統會採取封閉式失敗，而不是悄然變更所選的瀏覽器模式。

請勿重新命名或重複使用較舊的 `Codex Native` 或 `OmniRoute Codex` 連接器。ChatGPT 會依連接器身分快取公用 MCP 合約，而更新後的橋接器使用新的直接輪次權杖合約。執行階段會拒絕這些舊版身分，並要求使用新的 `OmniRoute Codex v2` 連接器。

## 安全性模型

- 原生路徑需要 Responses 請求、可辨識的 Codex 用戶端，以及相符的執行緒與回合識別資訊。
- 工作區、沙箱、核准原則及工具目錄皆來自原生 Codex shell；自由格式的提示文字無權決定這些設定。
- ChatGPT 每個回合只會收到短效能力權杖。MCP 代理程式僅接受 Codex 在該回合中提供的工具。
- 自動確認 **僅允許一次** 只會將工具請求傳回 Codex。只有 Codex 能決定是否核准及執行。
- 在第一次輸出之前，組合可回退至另一個相容的目標。輸出開始後，提供者、模型、連線及瀏覽器回合會保持固定，直到該回合完成。
- Cookie、執行階段金鑰、儲存狀態及能力權杖不會出現在提供者的回應或請求日誌中。

## 無顯示器的 VPS 與 Docker

對於 npm、systemd 及 PM2 安裝，OmniRoute 會偵測常見的 Chrome 與 Chromium 路徑。或者，也可以設定 `CHATGPT_WEB_CODEX_CHROME_PATH`。執行階段回合刻意使用有介面的 Chrome，因為 ChatGPT 會拒絕真正的無頭瀏覽器形式。因此，無顯示器的主機必須透過私有 Xvfb 顯示器執行 OmniRoute；僅設定 Chrome 路徑並不會提供顯示器。

Docker `web` 設定檔會在內部 Compose 網路上啟動 `chatgpt-web-codex-browser`。輔助容器會在 Xvfb 內執行有介面的 Chrome，因此不需要實體顯示器。其 CDP 連接埠不會發布至主機。受保護的瀏覽器設定檔磁碟區與 OmniRoute 資料磁碟區彼此分離，且瀏覽器會獲得足夠的共用記憶體。內部 CDP Proxy 僅監聽 Compose 網路內的連接埠 `9223`；Chrome 在輔助容器中仍只繫結至回送介面。

`DATA_DIR` 下的監督程式租約可防止多個 OmniRoute 程序同時擁有相同的通道與代理程式狀態。doctor 會回報衝突。

## 互動式復原

自動化 Docker 路徑沒有主機可見的視窗，但 Chrome 本身會在私有 Xvfb 顯示器內以有介面模式執行。當 ChatGPT 要求互動式登入或驗證時，可使用現有的 VNC 瀏覽器基礎架構進行復原。瀏覽器 UI 與 CDP 必須只能透過回送介面、經驗證的管理連線或 SSH 通道存取；正常運作期間，noVNC 會維持停用。

## WebSocket 回退機制

當組合包含 ChatGPT Web (Codex) 時，Responses WebSocket 橋接器會在連線至上游之前請求 HTTP/SSE 回退。之後，傳輸會透過 `/v1/responses` 進行。
