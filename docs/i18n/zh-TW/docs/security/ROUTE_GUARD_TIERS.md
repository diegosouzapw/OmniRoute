## 概述

所有 OmniRoute 管理 API 路由均歸類為三種保護層級之一。分類是靜態的，定義於 `src/server/authz/routeGuard.ts`，並會在執行任何其他驗證分支之前進行評估。

## 層級

### 層級 1 — LOCAL_ONLY

**強制執行方式：** `isLocalOnlyPath(path)` → 回環主機檢查  
**繞過方式：** 預設無法繞過。若請求攜帶具有 `manage` 範圍的有效 API 金鑰，則 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路徑可適用範圍有限的例外（請參閱[管理範圍例外](#manage-scope-carve-out)）。

這些路由會產生子程序或執行執行階段程式碼。若將其暴露給非回環流量，取得有效 JWT 的攻擊者（例如透過 Cloudflared/Ngrok 通道）便能觸發程序產生——這是一種已知的 CVE 類型（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 的內容（攻擊類型）：** 管理／代理程式伺服器公開了一個可啟動子程序（`npm install`、`node`、瀏覽器、代理伺服器、`git`、`tar` 等）的端點。若該端點可從主機外部存取——例如操作人員將 OmniRoute 放在 nginx/Cloudflare/Tailscale 通道之後，而 JWT 發生洩漏，或驗證設定錯誤——攻擊者便能將「呼叫 API」轉變成「在主機上執行命令」（遠端程式碼執行）。OmniRoute 透過對每個可產生程序的路由，**無條件地在任何驗證檢查之前強制執行回環主機檢查**來防堵此問題：透過通道洩漏的權杖仍無法存取程序產生功能。

**完整的 LOCAL_ONLY 集合。** 權威來源是 `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`；下表反映目前的狀態。`check-route-guard-membership` 閘門會列舉可產生程序之前綴下的每個 `route.ts`，若其中任何一個未歸類為僅限本機，CI 就會失敗。

#### 管理範圍例外

僅當請求帶有 `Authorization: Bearer <api-key>`，且其
中繼資料包含 `manage` 範圍（或 `admin`）時，部分 LOCAL_ONLY 路徑才可以
從非回送位址存取。此例外透過 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
針對各路徑明確啟用，因此任何新的 LOCAL_ONLY 路徑預設仍會嚴格限制為回送位址。
未驗證的請求，以及使用不含管理範圍金鑰的請求，仍會遭到拒絕並回傳
`403 LOCAL_ONLY`。

目前唯一可略過此限制的前綴是 `/api/mcp/`。`/api/cli-tools/runtime/` 和
`/api/services/` 被刻意排除，因為它們可以啟動任意
子程序（`npm install`、`node`），這正是
LOCAL_ONLY 層旨在防止的 CVE 類別。

**#7895 — `mcp:connect` 窄範圍：** `/api/mcp/` 例外也接受
持有窄範圍 `mcp:connect` 的 Bearer 金鑰
（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`），並透過
`src/server/authz/policies/management.ts` 中的 `hasMcpConnectOrManageScope()`
進行檢查。此範圍**僅**適用於 `/api/mcp/` — `mcp:connect` 不會授予任何其他
管理路由的權限（包括未來可能新增的其他任何 LOCAL_ONLY 例外前綴），而且它被刻意排除在
`MANAGEMENT_API_KEY_SCOPES` 之外。持有 `manage`/`admin` 的金鑰仍會
與先前完全相同地通過此例外；對於只需遠端呼叫 MCP，而不應需要廣泛管理存取權的呼叫端，
`mcp:connect` 是權限較低的替代方案。

| 請求                                         | 路徑                       | 結果             |
| -------------------------------------------- | -------------------------- | ---------------- |
| 非回送、無 Bearer                            | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非回送、Bearer 具有 `manage` 範圍            | `/api/mcp/*`               | 允許             |
| 非回送、Bearer 具有 `mcp:connect` 範圍       | `/api/mcp/*`               | 允許             |
| 非回送、Bearer 不具有 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非回送、Bearer 具有 `mcp:connect` 範圍       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非回送、Bearer 具有 `manage` 範圍            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 回送、具有或不具有任何 Bearer                | 任何 LOCAL_ONLY            | 允許（閘門通過） |

#### 營運人員指南與稽核

若您在反向代理或通道（nginx、Caddy、Cloudflare
Tunnel、Tailscale、Ngrok）後方執行 OmniRoute，回送檢查仍會保護上述可啟動程序的
路由 — 客戶端位址非回送位址的請求會在
**執行驗證之前**遭到拒絕並回傳 `403 LOCAL_ONLY`，因此即使 JWT 洩漏，也無法觸發程序啟動。
營運人員仍有兩項責任：

- **請勿透過將客戶端 IP 偽造成回送位址來「修正」403。** 設定
  `X-Forwarded-For: 127.0.0.1`，或使用會將來源位址改寫為
  回送位址的代理，會重新引入此層所封鎖的 RCE 類別。請透過代理公開
  儀表板/API — 絕對不要公開可啟動程序的路由。
- **將管理範圍例外維持在最低限度。** 只有 `/api/mcp/` 可以略過限制，而且
  必須使用具有 `manage` 範圍的 API 金鑰。`SPAWN_CAPABLE_PREFIXES` 永遠不能
  新增至例外清單 — zod 結構描述會拒絕它們，而且
  `isLocalOnlyBypassableByManageScope` 會在執行階段拒絕它們（縱深防禦），
  這就是儀表板所稱「無法設為可略過」的含義。`/api/providers/` 下具有動態區段
  及靜態路徑的可啟動程序路由（例如 `/login`、
  `/refresh-cursor`），由
  `src/shared/constants/spawnCapablePrefixes.ts` 中基於正規表示式的
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套機制涵蓋，而不是由扁平的
  `SPAWN_CAPABLE_PREFIXES` 陣列涵蓋 — 若要用扁平陣列捕捉這些路由，就必須涵蓋
  整個 `/api/providers/` 前綴，這會使路由樹的限制範圍過於寬泛，而遠端儀表板合理地需要使用該路由樹來進行提供者 CRUD。

**存取稽核** — 若要確認沒有任何主機外部來源正在存取這些路由：

- 在 `/dashboard/settings/security` 開啟 **授權清單**：其中會顯示即時的 LOCAL_ONLY 前綴清單、哪些前綴可被繞過，以及編譯時確定的具程序啟動能力（「不可設為可繞過」）集合。
- 在反向代理／存取日誌中搜尋上述前綴，並確認是否與非回送位址的用戶端位址同時出現。任何這類請求若傳回 `200` 而非 `403 LOCAL_ONLY`，就表示代理正在遮蔽真實的用戶端 IP——請修正代理設定。
- OmniRoute 日誌中若針對其中一個路徑出現 `403 LOCAL_ONLY`，代表防護機制正按預期運作，並非應被抑制的錯誤。

### 第 2 級 — ALWAYS_PROTECTED

**強制執行者：** `isAlwaysProtectedPath(path)` → 略過 `requireLogin=false` 的繞過機制
**繞過方式：** `requireLogin=false` 時仍無法繞過；一律需要 JWT

這些路由具有破壞性，或其操作不可逆。若允許在「無密碼」安裝環境中使用這些路由，就代表同一區域網路上的任何人都能清除資料庫或終止伺服器程序。

| 路徑                                      | 原因                                               |
| ----------------------------------------- | -------------------------------------------------- |
| `/api/shutdown`                           | 終止伺服器程序                                     |
| `/api/settings/database`                  | 匯出、匯入及清除資料庫                             |
| `/api/db-backups`                         | 存取完整的資料庫備份封存檔                         |
| `/api/settings/export-json`               | 匯出完整的設定資料（包括機密資訊）                 |
| `/api/settings/import-json`               | 取代完整的設定資料                                 |
| `/api/providers/health-autopilot/actions` | 執行自動駕駛修復動作                               |
| `/api/settings/obsidian`                  | 為任何保存庫根目錄核發可重複使用的 WebDAV 認證資訊 |

**違規時的回應：** `401 Authentication required`

`/api/settings/obsidian` 也涵蓋其 `/webdav` 子項：`POST` 會將 WebDAV 檔案服務——由自訂 Node 層在 Next.js 之前提供，因此位於此管線之外——指向呼叫者選擇的根目錄，並回傳新核發的 Basic 認證資訊；`DELETE` 會輪替這些認證資訊，而父層的 `POST` 則會儲存 Obsidian REST API 權杖。GHSA-62vw 只遮蔽了 `GET` 洩露密碼的問題；認證資訊的核發仍處於失效開放層級（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 還會拒絕本身即為資料目錄、位於資料目錄內，或包含資料目錄的保存庫。

### 全新安裝的初始設定僅限回送介面——依據真實對等端，而非 `Host`

若未設定管理密碼（且沒有 `INITIAL_PASSWORD`），`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` 只會對回送對等端開放匿名初始設定。是否為回送位址會依序根據下列受信任的對等端訊號判定：經權杖戳記的真實 TCP 對等端（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，亦即原則實際看到的資訊）、管線自身的 `AUTHZ_HEADER_PEER_LOCALITY` 判定結果（亦即路由處理常式看到的資訊，且僅在已設定 `OMNIROUTE_PEER_STAMP_TOKEN` 時受信任），或直接呼叫者的真實通訊端對等端。系統絕不會查閱 `Host` / `nextUrl.hostname`，且首次密碼寫入（`POST /api/settings/require-login`）也受相同限制，而非對每個網路對等端開放（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 會明確向下傳遞其自身的 `peerContext` 判定結果，因此 ORIGINAL（剝除前）請求的標頭永遠不會影響此判定。

### 第 3 級 — MANAGEMENT（預設）

所有其他管理路由。除非已設定 `requireLogin=false`，否則需要驗證身分。CLI 權杖可驗證這些路由（回送位址 + 有效的 HMAC）。

## 評估順序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → 繼續執行
     → 非 loopback、具 manage 範圍的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允許 (management_key)
     → 否則                                      → 拒絕 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允許 (system)
  3. hasValidCliToken(headers)?
     → 允許 (cli) [loopback + timingSafeEqual HMAC 檢查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允許 (dashboard_session)
     → 在不可繞過路徑上具 manage 範圍的 Bearer？
        → 允許 (management_key)
     → 拒絕 401/403
  5. requireLogin=false?
     → 允許 (anonymous)
```

步驟 1 的 manage 範圍分支，是唯一能滿足 LOCAL_ONLY 路由的已驗證路徑；驗證後端失敗時會傳回 503（而非 403），因此過期的 DB 不會在無提示的情況下降級為「拒絕」。

## 新增可啟動程序的路由

1. 將路徑前綴新增至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中新增測試，斷言
   `isLocalOnlyPath()` 對新前綴傳回 true
3. **絕不可略過此步驟** — 請參閱 `CLAUDE.md` 中的硬性規則 #15
4. 決定：此路由是否也應納入 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   預設答案為**否**。僅當該路由能安全地公開給 manage 範圍持有者時，才選擇加入（亦即不會啟動任意由使用者控制的程式碼）。

## 新增可由 manage 範圍繞過的路徑

1. 確認該路由不會執行使用者提供的程式碼或命令。如果會，請停止 — 此例外機制並不適用。
2. 將前綴附加至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中，針對所有四種請求形式新增測試涵蓋：無 Bearer（403）、manage Bearer（允許）、非 manage Bearer（403），以及每個前綴的迴歸測試，確保 `/api/cli-tools/runtime/*` 即使帶有 manage Bearer，仍嚴格限制為 loopback。

## 在 OpenAPI 中記錄安全層級

將新路由新增至 `docs/openapi.yaml` 時，若該路由由 `routeGuard.ts` 分類，請套用對應的提供者擴充欄位：

| routeGuard.ts 分類           | YAML 註記                  | 強制執行方式                          |
| ---------------------------- | -------------------------- | ------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 無條件封鎖來自非 loopback 的請求      |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 仍要求驗證  |
| 內部管理員／偵錯路由         | `x-internal: true`         | 預設不顯示於 /dashboard/api-endpoints |
| 無（公開／標準驗證）         | （不需要註記）             | 由標準 `requireLogin` 控制的存取      |

### 驗證

有兩個指令碼會強制確保 YAML 註記與 `routeGuard.ts` 之間的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 若涵蓋率低於 99%，則執行失敗
- `scripts/check/check-openapi-security-tiers.mjs` — 若 `x-loopback-only` 或
  `x-always-protected` 註記與編譯期常數不一致，則執行失敗

這兩個指令碼都會在 pre-commit hook 和 CI 中執行。

### 誤判規則

若某個路由標有 `x-always-protected` 或 `x-loopback-only`，但未列於
`routeGuard.ts` 常數中，涵蓋率指令碼將會失敗。修正方式一律是讓 YAML 與
`routeGuard.ts` 實際強制執行的內容保持一致，而不是在尚未實作強制執行邏輯的情況下，逕自將路由新增至 `routeGuard.ts`。
