## 1. 服務實際規格（官方文件，經交叉核對）

- 基礎 URL：`https://api.anysearch.com`（REST）+ `POST /mcp`（MCP、JSON-RPC 2.0）。
- `POST /v1/search` - 參數：`query`（必填）、`max_results`（1-10，預設為 10）、`tag`（使用 `{domain}.{sub_domain}` 進行垂直領域路由）、`zone`（cn/intl）、`language`、`params`（結構化垂直領域欄位）、`format`（json/markdown）。
- `GET /v1/sub-domains?domain=...` - 功能目錄，不計入配額。
- `POST /v1/extract` - 擷取／提取 `{url, title, content}`；嚴格的 JSON 請求本文，大小上限為 16 KiB。
- `POST /v1/auth/email/register` - 單次呼叫註冊，傳回一次性明文金鑰 `as_sk_...`。
- 驗證：可選的 `Authorization: Bearer <as_sk_...>`；匿名存取會降級為每 IP 限制，並消耗每日免費配額；無效金鑰會傳回 401/403，且不會靜默回退至匿名模式。
- 免費方案：每天 1000 次請求，每個金鑰 20 QPS。付費方案：尚未定價（即將推出）。
- 回應封裝：成功時為 `{code: 0, message: "success", request_id, data}`；失敗時為 `{code: -1, message}`。驗證／配額錯誤不包含結構化的 `error_code`（以訊息文字作為判斷依據）；擷取專屬錯誤則包含 `error_code`（`invalid_extract_url`、`extract_failed`）。429 回應不含 `Retry-After` 標頭。

## 3. 決策（皆於 2026-08-26 達成）

1. **路由策略：`fallbackOnly`。** 理由：成本為 0 的免費提供者絕不能在自動成本路由中占據主導地位；明確選取與容錯移轉後返回不受影響。先例：已合併的 xquik 項目。
2. **範圍：v1 中透過 `POST /v1/extract` 提供 webSearch + webFetch。** 與 tavily/exa 雙重能力的心智模型一致。垂直領域介面（`tag`、`sub-domains`、`batch_search`）不在範圍內——目前尚無用於垂直領域參數的 IR。
3. **配額顯示：`freeMonthlyQuota: 0`**（xquik 風格的保守顯示）。實際額度（每日 1000 個請求、每日重設）改由 UI 目錄中的 `authHint` 文案說明。理由：配額顯示必須符合重設語意；將每日上限換算成每月等值（30000）會形成 UI 無法兌現的錯誤承諾。
4. **searchTypes：僅 `["web"]`。** 沒有公開證據顯示 AnySearch API 提供新聞／圖片垂直搜尋；整合未記載垂直搜尋功能之 API 的閘道（例如 Google Custom Search）只會公開網頁搜尋，而不會暗中將新聞搜尋對應至網頁搜尋。
5. **金鑰策略：**可不使用金鑰；無效金鑰會傳回 401/403，且絕不會在未告知的情況下降級為匿名模式（與上游合約一致）。
6. **刻意排除項目：**`FETCH_BACKEND_TO_PROVIDER` / `FetchInterceptionBackend`（聊天攔截仍使用 firecrawl/jina/tavily）；`ANONYMOUS_CAPABLE_WEB_FETCH_PROVIDERS`（匿名遠端端點會依每個出口 IP 共用一個受 IP 限制的資源池，因此無金鑰 extract 須由使用者選擇啟用，而非自動路由候選項目）；`QUOTA_STATUS_PROVIDERS`（AnySearch 透過 429／封裝回應表示配額狀態，而非 402/403 狀態）。
