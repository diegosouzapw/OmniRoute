## Referensi Cepat

**Baru menggunakan OmniRoute?** Mulai di sini — solusi berikut mengatasi 90% masalah:

| Yang Anda lihat                 | Artinya                                     | Yang harus dilakukan                                                                             |
| ------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| "Tidak dapat terhubung"         | OmniRoute tidak berjalan                    | Jalankan `omniroute` atau `docker restart omniroute`                                             |
| "Kunci API tidak valid"         | Kunci Anda salah atau kedaluwarsa           | Salin ulang kunci dari situs web penyedia                                                        |
| "Batas laju terlampaui"         | Anda mengirim terlalu banyak permintaan     | Tunggu 1 menit, atau gunakan `model: "auto"` untuk fallback otomatis                             |
| "Kuota terlampaui"              | Kuota gratis/berbayar Anda telah habis      | Hubungkan lebih banyak penyedia, atau gunakan penyedia gratis (Kiro, Pollinations)               |
| "Respons lambat"                | Penyedia sedang sibuk atau berada jauh      | Gunakan `model: "auto/fast"` atau hubungkan penyedia yang lebih cepat (Groq, Cerebras)           |
| "Penyedia yang digunakan salah" | `auto` memilih penyedia yang berbeda        | Itu normal! `auto` memilih yang terbaik. Paksa penyedia tertentu dengan `model: "openai/gpt-4o"` |
| "502 Bad Gateway"               | Penyedia sedang tidak beroperasi            | Tunggu dan coba lagi, atau gunakan `model: "auto"` untuk beralih penyedia                        |
| "401 Unauthorized"              | Kredensial Anda salah                       | Periksa kunci API Anda atau lakukan autentikasi ulang dengan OAuth                               |
| "omniroute tidak dikenali"      | PATH Windows tidak memuat modul node global | Tambahkan prefiks global npm Anda ke PATH Windows. Temukan dengan `npm config get prefix`.       |
| "429 Too Many Requests"         | Terkena pembatasan laju                     | Tunggu 1 menit, atau hubungkan lebih banyak penyedia                                             |

**Masih mengalami masalah?** Lihat [pemecahan masalah terperinci](#detailed-troubleshooting) di bawah ini, atau tanyakan di [Discord](https://discord.gg/U47eFqAXCn).

### Pembatasan Laju pada Penyedia Gratis (429 / 400 / 401)

**Gejala**: Saat menggunakan `model: "auto"` dengan penyedia gratis/tanpa autentikasi (opencode, auggie, dll.), Anda sesekali mendapatkan `HTTP 429`, `400`, atau `401`, bukan jawaban. Permintaan berhasil jika prompt yang sama dicoba kembali beberapa saat kemudian, tetapi otomatisasi (cron job, agen, skrip) berhenti saat kegagalan pertama terjadi.

**Penyebab utama**: Tiga mode kegagalan independen terjadi secara bersamaan:

1. **Batas laju penyedia (`429`)**: Tingkat gratis dapat menerapkan kuota per jendela waktu. Lonjakan panggilan paralel menghabiskan kuota tersebut, sehingga permintaan berikutnya ditolak sampai jendela waktu direset.
2. **Model bermasalah dalam passthrough (`400`/`401`)**: Pool `auto/*` dapat menyertakan model passthrough dari `opencode` yang terdaftar di katalog tetapi tidak memiliki kredensial aktif (misalnya `oc/north-mini-code-free` → `401`). Auto-router mencoba salah satunya, gagal, dan galat diteruskan sebelum fallback dijalankan.
3. **Amplifikasi konkurensi (`429` saat beban tinggi)**: Ketika beberapa sesi agen/cron mengakses `auto` secara bersamaan, laju permintaan gabungan melebihi kemampuan penyedia gratis, sehingga panggilan yang sah ditandai sebagai penyalahgunaan.

**Perbaikan terverifikasi (dilaporkan komunitas, 2026-08-10)**: sesuaikan tiga variabel lingkungan agar rotasi, konkurensi, dan fallback menangani ketidakstabilan tingkat gratis, alih-alih gagal karenanya:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # beralih ke model/penyedia lain pada 400/401 (melewati model passthrough yang bermasalah)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # batas penerimaan eksplisit untuk permintaan berat (secara default tidak ditetapkan: tanpa batas jumlah permintaan, lihat catatan di bawah)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # waktu tunggu terbatas yang lebih lama untuk kapasitas permintaan berat, alih-alih langsung menghasilkan 503 yang dapat dicoba kembali
```

Tetapkan variabel tersebut di lingkungan proses OmniRoute (daemon, misalnya melalui plist LaunchAgent atau `systemctl edit`), lalu mulai ulang OmniRoute. Flag rotasi adalah pengaturan tunggal dengan dampak terbesar: pengaturan ini mengubah kegagalan total menjadi percobaan ulang transparan pada penyedia yang sehat dalam pool.

**Catatan**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` membatasi jumlah permintaan berat — dengan konteks panjang — yang berjalan secara bersamaan; batas tersebut merupakan gerbang penerimaan, bukan pembatas laju penyedia. **Pembaruan #503-fanout:** variabel ini tidak lagi ditetapkan secara default (sekarang hanya berlaku jika dikonfigurasi secara eksplisit, seperti di atas) — sebagai gantinya, penerimaan permintaan berat dibatasi oleh anggaran byte yang diturunkan secara otomatis (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dan menyesuaikan diri berdasarkan batas memori aktual host, sehingga deployment baru seharusnya mengalami jauh lebih sedikit penolakan `503 chat_admission_busy` tanpa perlu menetapkan variabel ini sama sekali; menetapkannya secara eksplisit di sini tetap berfungsi persis seperti yang didokumentasikan. Penggantian eksplisit untuk anggaran byte dibatasi dalam rentang 8 MiB–2 GiB. `413 body_exceeds_budget` bukan kondisi sementara: tingkatkan anggaran byte tersebut, turunkan `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, atau tingkatkan batas memori proses. Pelepasan beban `inflight_bytes_budget` merupakan kontensi sementara dan tetap dapat dicoba kembali. Pembatasan laju per penyedia (`open-sse/services/rateLimitManager.ts`) diatur secara terpisah oleh `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, dan `RATE_LIMIT_AUTO_ENABLE` — lihat `.env.example`.

**Cara memverifikasi bahwa perbaikan berhasil**: jalankan agen/cron Anda dua kali secara berurutan dalam waktu singkat dan pastikan keduanya berhasil. Sebelum perbaikan, proses kedua biasanya menghasilkan `429`/`401`. Setelah perbaikan, kegagalan (jika ada) dicoba ulang secara transparan dan panggilan selesai. Anda juga dapat menjalankan `curl /monitoring/health` dan memantau kolom `rateLimitedUntil` pada koneksi penyedia serta `circuitBreakers.providerBreakers[].state` untuk penyedia yang terdampak — statusnya adalah salah satu dari `CLOSED`, `DEGRADED`, `OPEN`, atau `HALF_OPEN` (lihat `src/shared/utils/circuitBreaker.ts`), dan penyedia yang terus mengalami kegagalan akan berubah dari `CLOSED → DEGRADED → OPEN` sebelum jendela pengaturan ulang mengizinkan sebuah pemeriksaan (`HALF_OPEN`).

**Jika Anda masih melihat 429**: akun aktif untuk penyedia tersebut benar-benar telah kehabisan _kuota_ (bukan sekadar terkena pembatasan laju). Tambahkan akun kedua untuk penyedia yang sama di dasbor OmniRoute → Providers → Accounts, atau sertakan penyedia gratis lainnya (misalnya `routeway`, `auggie`). Rotasi hanya membantu mengatasi pembatasan laju sementara/400/401; kehabisan kuota sepenuhnya memerlukan kredensial kedua atau penyedia lain.

**Jika Anda melihat 403 pada model visi (`auto/vision`, `bazaarlink/*`)**: akun yang terhubung tidak memiliki paket berbayar yang mencakup visi, atau kunci API tidak memiliki izin yang memadai. Verifikasi di dasbor penyedia bahwa cakupan kunci mencakup visi/multimodal, atau hubungkan akun tingkat berbayar dan tetap gunakan akun tersebut sebagai target visi.

## Peringatan npm install (ERESOLVE / peer / deprecated)

Saat menjalankan `npm install -g omniroute`, Anda mungkin melihat banyak peringatan seperti `npm warn ERESOLVE`, pemberitahuan dependensi peer, dan pesan `deprecated`. **Hal ini wajar dan tidak berbahaya.** Instalasi Anda berhasil jika melihat `added <N> packages` pada output.

Untuk menyembunyikan peringatan resolusi dependensi peer, gunakan format instalasi yang didukung OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` hanya menyembunyikan `ERESOLVE` dan pemberitahuan dependensi peer. Pemberitahuan penghentian dukungan tetap terlihat karena berasal dari paket pihak ketiga transitif; pemberitahuan tersebut tidak menunjukkan bahwa instalasi gagal.

Peringatan tersebut berasal dari rentang dependensi peer usang pada paket pihak ketiga yang tidak dikendalikan OmniRoute:

1. **`marked-terminal` memerlukan `marked >=1 <16`, tetapi yang ditemukan adalah `marked@18`** — dalam praktiknya tetap berfungsi dengan baik; rentang peer upstream tersebut sudah usang.
2. **`deprecated prebuild-install@7.1.3`** — helper pengambilan biner native transitif. Paket ini tidak
   digunakan untuk menginstal binding transport `wreq-js` yang versinya telah ditetapkan dan tidak menunjukkan bahwa
   penyiapan transport penyedia web-cookie gagal.

**Tidak ada tindakan yang diperlukan** — peringatan tersebut tidak dapat disembunyikan sepenuhnya tanpa melakukan fork pada paket upstream.

## Gemini Web dan Playwright Chromium

Jika permintaan Gemini Web mengembalikan `503` dengan pesan bahwa Playwright Chromium
belum diinstal, paket npm sudah tersedia, tetapi biner browser belum ada.
Playwright sengaja memisahkan unduhan browser dari instalasi paket npm,
sehingga respons ini wajar sampai browser diinstal.

Untuk instalasi npm global, instal Chromium dari direktori paket OmniRoute
agar cache browser menjadi bagian dari instalasi Playwright yang sama:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Mulai ulang OmniRoute setelah instalasi, lalu coba kembali permintaan Gemini Web. Jika Anda
menjalankan OmniRoute dari image Docker, gunakan image `-web` (atau target build `runner-web`),
yang menyertakan Chromium beserta dependensinya; image dasar
tidak menyertakannya.

## Perbaikan Cepat

| Masalah                                                    | Solusi                                                                                                                                                                       |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Login pertama tidak berfungsi                              | Atur `INITIAL_PASSWORD` di `.env` (tidak ada nilai default yang ditulis langsung dalam kode)                                                                                 |
| Dasbor terbuka pada port yang salah                        | Atur `PORT=20128` dan `NEXT_PUBLIC_BASE_URL=http://localhost:20128`                                                                                                          |
| Tidak ada log yang ditulis ke disk                         | Atur `APP_LOG_TO_FILE=true` dan pastikan perekaman log panggilan diaktifkan                                                                                                  |
| EACCES: izin ditolak                                       | Atur `DATA_DIR=/path/to/writable/dir` untuk mengganti `~/.omniroute`                                                                                                         |
| Strategi perutean tidak tersimpan                          | Perbarui ke rilis v3.x terbaru (perbaikan skema Zod untuk persistensi pengaturan telah dirilis pada versi sebelumnya)                                                        |
| Login crash / halaman kosong                               | Periksa versi Node.js — lihat [Kompatibilitas Node.js](#nodejs-compatibility) di bawah                                                                                       |
| `dlopen` / `slice is not valid mach-o file` (macOS)        | Jalankan `cd $(npm root -g)/omniroute/app && npm rebuild better-sqlite3 && omniroute` — lihat [build ulang modul native macOS](#macos-native-module-rebuild) di bawah        |
| Proxy "fetch failed"                                       | Pastikan konfigurasi proxy diatur pada tingkat yang benar — lihat [Masalah Proxy](#proxy-issues) di bawah                                                                    |
| Docker `curl: (56) Recv failure: Connection reset by peer` | Bind port Docker Anda mungkin mengarah ke IPv6. Gunakan `-p 127.0.0.1:20128:20128` untuk memaksa IPv4, atau uji dengan `curl -4`. Lihat [IPv6 Docker](#docker-ipv6) di bawah |
| Antivirus mengarantina `README.md`                         | Positif palsu — lihat [Positif palsu antivirus](#antivirus-false-positives) di bawah                                                                                         |
| Kaspersky menandai aplikasi Desktop sebagai Trojan         | Positif palsu berbasis perilaku pada penginstal yang tidak ditandatangani — lihat [Positif palsu antivirus](#antivirus-false-positives) di bawah                             |

## Positif Palsu Antivirus

<a name="antivirus-false-positives"></a>

### Avast/AVG mengarantina `README.md` dengan `MD:HttpRequest-inf[Susp]`

**Ini adalah positif palsu. Tidak ada yang terinfeksi, dan tidak diperlukan tindakan apa pun.**

Avast dan AVG menjalankan heuristik yang menandai file teks biasa/Markdown yang berisi banyak
tautan yang tampak seperti permintaan HTTP. `README.md` OmniRoute disertakan di dalam paket npm (file ini
tercantum dalam `package.json` → `files`), sehingga pada instalasi global file tersebut ditempatkan di
`node_modules/omniroute/README.md` — dan berisi sekitar 15 contoh `http://localhost:20128/...` (endpoint
HTTP/SSE MCP, URL `.well-known` A2A, dan cuplikan `curl`). Kepadatan tautan tersebut
cukup untuk memicu heuristik.

Jika hal ini baru mulai terjadi belakangan ini: jenis file tersebut tidak berubah. Tabel endpoint di README
bertambah (HTTP MCP + SSE + A2A ditambahkan), begitu pula contoh `curl`, sehingga
jumlahnya melewati ambang batas.

File tersebut hanyalah dokumentasi pasif tanpa konten yang dapat dieksekusi. Anda dapat memulihkannya
dari karantina dengan aman.

**Yang harus dilakukan:**

1. **Hentikan notifikasi** — kecualikan direktori instalasi di antivirus Anda
   (Avast: Settings → Exceptions), dengan menambahkan jalur global `node_modules` dan/atau
   direktori data OmniRoute (`~/.omniroute/`).
2. **Laporkan positif palsu** — <https://www.avast.com/false-positive-file-form.php>,
   dengan melampirkan `README.md` yang dikarantina. Ini adalah perbaikan yang membantu semua orang karena
   heuristik vendor bereaksi berlebihan terhadap sebuah file teks.

**Mengapa kami tidak "memperbaiki" ini dari sisi kami:** semua contoh menggunakan `http://localhost`, dan
localhost tidak dapat menggunakan `https` tanpa kerumitan sertifikat yang ditandatangani sendiri. Mengubah dokumentasi secara tidak wajar demi
menghindari heuristik satu vendor akan merugikan setiap pembaca hanya untuk mengakomodasi bug pemindai.

### Kaspersky menandai aplikasi Desktop sebagai `PDM:Trojan.Win32.Generic`

**Ini adalah positif palsu dari heuristik perilaku. Tidak ada yang terinfeksi.** Awalan
`PDM:` dari Kaspersky berarti keputusan berasal dari Proactive Defense Module (System Watcher),
yang menilai apa yang _dilakukan_ penginstal, bukan mencocokkannya dengan malware yang telah diketahui. Saat
terpicu, Kaspersky "mengembalikan" seluruh instalasi — menghapus file yang telah
ditulis — sehingga aplikasi menjadi rusak atau hilang.

File yang ditandai merupakan bagian standar dari dependensi sumber terbuka yang dideklarasikan dan disertakan bersama
aplikasi desktop, misalnya:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` dan
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), pustaka otomatisasi browser
  yang digunakan untuk login penyedia di dalam aplikasi dan obrolan berbasis browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — binding native `wreq-js` yang versinya dikunci dan digunakan untuk HTTP dengan sidik jari browser pada penyedia
  berbasis cookie web (`<arch>` adalah `x64` atau `arm64`).

**Mengapa ini terpicu:** penginstal Windows **belum ditandatangani dengan kode**, sehingga penginstal NSIS
yang tidak ditandatangani tidak memiliki reputasi dan heuristik perilaku berjalan dengan agresivitas maksimum. Ditambah
dengan DLL native yang disertakan dan ratusan file `.js` yang ditulis di bawah
`%LOCALAPPDATA%\Programs\OmniRoute` (termasuk direktori paket dengan akhiran hash dari build
standalone Next.js), hal tersebut cukup untuk memicu heuristik. Penandatanganan kode telah direncanakan;
hingga diterapkan, masalah ini dapat berulang pada rilis baru.

**Yang harus dilakukan:**

1. **Verifikasi unduhan Anda terlebih dahulu** (untuk memastikan file tidak dimodifikasi). Setiap rilis menerbitkan
   `latest.yml`, yang kolom `sha512`-nya (base64) mencakup penginstal
   `OmniRoute.Setup.<version>.exe`. Di PowerShell, dari folder yang berisi penginstal:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Output harus cocok dengan `latest.yml` → `sha512`. Jika tidak cocok, hapus file tersebut dan
   unduh ulang hanya dari [halaman rilis GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Pulihkan + kecualikan** — pulihkan item yang dibatalkan dari karantina dan tambahkan pengecualian
   untuk `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   lalu instal ulang.
3. **Laporkan positif palsu** — <https://opentip.kaspersky.com/>. Laporan positif palsu
   yang dikirimkan pengguna benar-benar mempercepat proses penambahan ke daftar yang diizinkan.

## Kompatibilitas Node.js

<a name="nodejs-compatibility"></a>

### Halaman login mengalami crash atau menampilkan kesalahan "Module self-registration"

**Penyebab:** Anda menjalankan versi Node.js di luar batas minimum runtime aman yang disetujui OmniRoute. Kasus yang paling umum adalah menjalankan Node 22 atau 24 dengan tingkat patch lama yang berada di bawah batas minimum keamanan yang telah ditambal dan diwajibkan oleh OmniRoute.

**Gejala:**

- Halaman login menampilkan layar kosong atau kesalahan server
- Konsol menampilkan `Error: Module did not self-register` atau kesalahan binding native serupa
- Halaman login menampilkan **banner peringatan berwarna oranye** beserta versi Node Anda jika runtime berada di luar kebijakan aman yang didukung

**Perbaikan:**

1. Instal rilis Node.js LTS yang didukung (disarankan: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifikasi versi Anda: `node --version` harus menampilkan `v24.0.0` atau yang lebih baru pada lini LTS 24.x
3. Instal ulang OmniRoute: `npm install -g omniroute`
4. Mulai ulang: `omniroute`

> **Versi aman yang didukung:** `>=22.22.2 <23` atau `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) dan Node.js 26 didukung sepenuhnya.

### npm v11+: `better-sqlite3` tidak terinstal (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Penyebab:** npm v11 (disertakan dengan Node.js 24+) secara default memblokir skrip instalasi untuk dependensi
opsional. Karena `better-sqlite3` tercantum dalam `optionalDependencies`
dan memerlukan kompilasi native (`node-gyp rebuild`), npm melewatinya tanpa pemberitahuan.

**Gejala:**

- Server mengalami crash saat dimulai dengan pesan `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` menampilkan "No such file or directory"
- `npm ls better-sqlite3` menampilkan `(empty)`

**Perbaikan:**

1. Setujui skrip instalasi dan instal ulang:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Atau instal hasil build siap pakai secara manual:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifikasi bahwa ini berfungsi: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Penyebab:** Setelah menjalankan `npm install -g omniroute` secara global, biner native `better-sqlite3` di dalam paket mungkin telah dikompilasi untuk arsitektur atau ABI Node.js yang berbeda dari yang berjalan secara lokal. Hal ini umum terjadi di macOS (baik Apple Silicon maupun Intel) ketika biner siap pakai tidak cocok dengan lingkungan Anda.

**Gejala:**

- Server langsung gagal saat dimulai dengan kesalahan `dlopen`
- Kesalahan berisi `slice is not valid mach-o file`
- Contoh lengkap:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Perbaikan — build ulang untuk lingkungan lokal Anda (tidak perlu menurunkan versi Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Catatan:** Tindakan ini mengompilasi ulang binding native terhadap versi Node.js dan arsitektur CPU lokal Anda, sehingga menyelesaikan ketidakcocokan biner. Rentang runtime yang didukung secara resmi adalah **`>=22.22.2 <23` atau `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` dalam `src/shared/utils/nodeRuntimeSupport.ts`, selaras dengan kolom `engines` pada `package.json`). Node.js 24.x LTS (Krypton) dan Node.js 26 didukung sepenuhnya dengan `better-sqlite3` v12.x.

## Masalah Proxy

<a name="proxy-issues"></a>

### Validasi penyedia menampilkan "fetch failed"

**Penyebab:** Endpoint validasi kunci API (`POST /api/providers/validate`) sebelumnya melewati konfigurasi proxy, sehingga menyebabkan kegagalan di lingkungan yang memerlukan perutean melalui proxy.

**Perbaikan (v3.5.5+):** Masalah ini kini telah diperbaiki. Validasi penyedia dirutekan melalui `runWithProxyContext`, sehingga secara otomatis mengikuti pengaturan proxy pada tingkat penyedia dan global.

### Pemeriksaan kesehatan token gagal dengan "fetch failed"

**Penyebab:** Penyegaran token OAuth di latar belakang tidak menentukan konfigurasi proxy untuk setiap koneksi.

**Perbaikan (v3.5.5+):** Penjadwal pemeriksaan kesehatan token kini menentukan konfigurasi proxy untuk setiap koneksi sebelum mencoba melakukan penyegaran. Perbarui ke v3.5.5+.

### Proxy SOCKS5 mengembalikan "invalid onRequestStart method"

**Penyebab:** Pada Node.js 22, dispatcher undici@8 tidak kompatibel dengan implementasi `fetch()` bawaan Node.

**Perbaikan (v3.5.5+):** OmniRoute kini menggunakan fungsi `fetch()` milik undici saat dispatcher proxy aktif, sehingga memastikan perilaku yang konsisten. Perbarui ke v3.5.5+.

### Proxy MITM di WSL: aplikasi desktop pada host Windows tidak diintersepsi

**Penyebab:** Proxy MITM dan sertifikat CA-nya dipasang di lingkungan tempat OmniRoute berjalan. Pada WSL, lingkungan tersebut adalah guest Linux, sedangkan aplikasi desktop AI (Kiro, Trae, Copilot, Zed, …) berjalan pada host Windows. Aplikasi host tidak memercayai penyimpanan sertifikat milik guest dan tidak merutekan lalu lintas melalui proxy sistem guest, sehingga intersepsi desktop tidak berjalan di sana.

**Rekomendasi:** Jalankan OmniRoute secara native pada OS yang sama dengan aplikasi desktop yang ingin Anda intersepsi (Windows untuk aplikasi Windows; demikian juga untuk macOS/Linux). Menjalankan OmniRoute di dalam WSL sambil menargetkan aplikasi host mengharuskan Anda memercayai sertifikat CA yang dihasilkan secara manual pada host Windows dan mengarahkan pengaturan jaringan/proxy setiap aplikasi host ke endpoint proxy WSL — konfigurasi yang tidak didukung dan rentan bermasalah.

## Masalah Penyedia

### "Language model did not provide messages"

**Penyebab:** Kuota penyedia telah habis.

**Perbaikan:**

1. Periksa pelacak kuota di dasbor
2. Gunakan kombinasi dengan tingkatan fallback
3. Beralih ke tingkatan yang lebih murah/gratis

### Pembatasan Laju

**Penyebab:** Kuota langganan telah habis.

**Perbaikan:**

- Tambahkan fallback: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Gunakan GLM/MiniMax sebagai cadangan murah

### Token OAuth Kedaluwarsa

OmniRoute menyegarkan token secara otomatis. Jika masalah berlanjut:

1. Dasbor → Penyedia → Hubungkan Kembali
2. Hapus lalu tambahkan kembali koneksi penyedia

### Multi-akun Kiro: akun kedua membatalkan akun pertama

**Penyebab:** Backend Kiro memberlakukan satu sesi aktif untuk setiap pendaftaran klien OIDC.
Ketika dua akun menggunakan klien terdaftar yang sama (koneksi yang diimpor sebelum v3.8.0),
penyegaran token salah satu akun akan membatalkan token penyegaran akun lainnya.

**Perbaikan (v3.8.0+):** Impor ulang koneksi yang terdampak.
Mulai v3.8.0, setiap koneksi Kiro baru yang dibuat melalui **Impor Token**,
**login sosial Google/GitHub**, atau **Impor Otomatis** secara otomatis mendaftarkan klien
OIDC khususnya sendiri. Dengan demikian, koneksi tersebut sepenuhnya terisolasi dan
penyegaran satu akun tidak memengaruhi akun lainnya.

Koneksi yang diimpor _sebelum_ v3.8.0 tidak memiliki pendaftaran klien per koneksi.
Koneksi tersebut tetap menggunakan endpoint penyegaran autentikasi sosial bersama.
Untuk memperoleh isolasi, hapus koneksi lama dari Dasbor → Penyedia lalu tambahkan kembali
melalui salah satu dari tiga alur impor.

Untuk detail lengkap dan petunjuk langkah demi langkah dalam menambahkan dua akun Kiro secara berdampingan,
lihat [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Masalah Cloud

### Kesalahan Sinkronisasi Cloud

1. Pastikan `BASE_URL` mengarah ke instans yang sedang berjalan (misalnya, `http://localhost:20128`)
2. Pastikan `CLOUD_URL` mengarah ke endpoint cloud Anda (misalnya, `https://omniroute.dev`)
3. Pastikan nilai `NEXT_PUBLIC_*` selaras dengan nilai sisi server

### Cloud `stream=false` Menghasilkan 500

**Gejala:** `Unexpected token 'd'...` pada endpoint cloud untuk panggilan non-streaming.

**Penyebab:** Upstream mengembalikan payload SSE sementara klien mengharapkan JSON.

**Solusi sementara:** Gunakan `stream=true` untuk panggilan langsung ke cloud. Runtime lokal menyertakan fallback SSE→JSON.

### Cloud Menyatakan Terhubung tetapi "Invalid API key"

1. Buat kunci baru dari dasbor lokal (`/api/keys`)
2. Jalankan sinkronisasi cloud: Aktifkan Cloud → Sinkronkan Sekarang
3. Kunci lama/belum disinkronkan masih dapat menghasilkan `401` di cloud

## Masalah Docker

### IPv6 Docker / Koneksi Direset

<a name="docker-ipv6"></a>

**Gejala:** `curl http://localhost:20128/v1/models` menghasilkan `curl: (56) Recv failure: Connection reset by peer`. Dasbor dan endpoint tanpa autentikasi berfungsi, tetapi endpoint yang memerlukan autentikasi gagal — ini tampak seperti masalah autentikasi, tetapi sebenarnya bukan.

**Penyebab:** `docker run -p 20128:20128` memublikasikan pada `0.0.0.0` (IPv4) dan `::` (IPv6), tetapi proses di dalam kontainer hanya mendengarkan pada IPv4. Pada host tempat `localhost` di-resolve ke `::1` terlebih dahulu, koneksi masuk ke port IPv6 yang dipublikasikan tanpa listener di belakangnya → koneksi direset.

**Perbaikan:**

1. **Diagnostik cepat:** Jalankan `curl -4 http://localhost:20128/v1/models`. Jika berfungsi dengan `-4` tetapi gagal tanpanya, terdapat ketidakcocokan binding IPv6.
2. **Perbaikan permanen:** Bind ke IPv4 secara eksplisit dengan menggunakan `-p 127.0.0.1:20128:20128` dalam perintah `docker run` Anda:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Ini memaksa binding IPv4 dan juga mencegah proxy terekspos pada semua antarmuka host.

## Masalah Circuit Breaker

### Penyedia terjebak dalam status OPEN

Ketika circuit breaker suatu penyedia berada dalam status OPEN, permintaan akan diblokir hingga waktu tunggu berakhir.

**Perbaikan:**

1. Buka **Dasbor → Pengaturan → Ketahanan**
2. Periksa kartu circuit breaker untuk penyedia yang terdampak
3. Klik **Reset Semua** untuk menghapus semua breaker, atau tunggu hingga waktu tunggu berakhir
4. Pastikan penyedia benar-benar tersedia sebelum melakukan reset

### Penyedia terus memicu circuit breaker

Jika penyedia berulang kali memasuki status OPEN:

1. Periksa pola kegagalan di **Dasbor → Kesehatan → Kesehatan Penyedia**
2. Buka **Pengaturan → Ketahanan → Profil Penyedia** dan tingkatkan ambang batas kegagalan
3. Periksa apakah penyedia telah mengubah batas API atau mewajibkan autentikasi ulang
4. Tinjau telemetri latensi — latensi tinggi dapat menyebabkan kegagalan akibat waktu habis

## Debugging Penerjemah

Gunakan **Dasbor → Penerjemah** untuk men-debug masalah penerjemahan format:

| Mode                 | Kapan Digunakan                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Playground**       | Bandingkan format input/output secara berdampingan — tempel permintaan yang gagal untuk melihat hasil terjemahannya |
| **Penguji Obrolan**  | Kirim pesan langsung dan periksa payload permintaan/respons lengkap, termasuk header                                |
| **Test Bench**       | Jalankan pengujian batch pada berbagai kombinasi format untuk menemukan terjemahan yang bermasalah                  |
| **Monitor Langsung** | Pantau alur permintaan secara real-time untuk menemukan masalah penerjemahan yang terjadi sesekali                  |

### Masalah format umum

- **Tag penalaran tidak muncul** — Periksa apakah penyedia target mendukung penalaran dan pengaturan anggaran penalaran
- **Pemanggilan alat hilang** — Beberapa penerjemahan format mungkin menghapus kolom yang tidak didukung; verifikasi dalam mode Playground
- **Prompt sistem tidak ada** — Claude dan Gemini menangani prompt sistem secara berbeda; periksa output terjemahan
- **SDK mengembalikan string mentah alih-alih objek** — Telah diatasi di v1.x; pembersih respons menghapus kolom nonstandar (`x_groq`, `usage_breakdown`, dll.) yang menyebabkan kegagalan validasi Pydantic pada SDK OpenAI. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan sebagai issue.
- **GLM/ERNIE menolak peran `system`** — Telah diatasi di v1.x; penormal peran secara otomatis menggabungkan pesan sistem ke dalam pesan pengguna untuk model yang tidak kompatibel. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan sebagai issue.
- **Peran `developer` tidak dikenali** — Telah diatasi di v1.x; secara otomatis dikonversi menjadi `system` untuk penyedia selain OpenAI. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan sebagai issue.
- **`json_schema` tidak berfungsi dengan Gemini** — Telah diatasi di v1.x; `response_format` kini dikonversi menjadi `responseMimeType` + `responseSchema` milik Gemini. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan sebagai issue.

## Pengaturan Ketahanan

### Pembatasan laju otomatis tidak terpicu

- Pembatasan laju otomatis hanya berlaku untuk penyedia kunci API (bukan OAuth/langganan)
- Pastikan **Settings → Resilience → Provider Profiles** telah mengaktifkan pembatasan laju otomatis
- Periksa apakah penyedia mengembalikan kode status `429` atau header `Retry-After`

### Menyetel backoff eksponensial

Profil penyedia mendukung pengaturan berikut:

- **Base delay** — Waktu tunggu awal setelah kegagalan pertama (default: 1s)
- **Max delay** — Batas maksimum waktu tunggu (default: 30s)
- **Multiplier** — Besarnya peningkatan waktu tunggu untuk setiap kegagalan berturut-turut (default: 2x)

### Pencegahan thundering herd

Ketika banyak permintaan serentak mengakses penyedia yang dibatasi lajunya, OmniRoute menggunakan mutex + pembatasan laju otomatis untuk menserialisasi permintaan dan mencegah kegagalan berantai. Ini dilakukan secara otomatis untuk penyedia kunci API.

### Permintaan chat gagal dengan 503 / chat_admission_busy

**Gejala:**

- Endpoint penyelesaian chat mengembalikan respons `503` yang dapat dicoba ulang dengan kode kesalahan
  `chat_admission_busy`.
- Respons menyertakan `Retry-After`. Sejak #12135, nilainya diperoleh dari okupansi yang diamati
  — nilai yang lebih besar antara jendela `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` yang telah digunakan
  permintaan untuk menunggu dan lamanya lease kelas berat saat ini telah dipegang — dibulatkan ke
  atas menjadi detik penuh dan dibatasi maksimal 60. Pada gate yang sedang tidak aktif, nilai ini
  mempertahankan batas minimum historis: 2 detik pada jalur berbasis byte, 1 detik pada jalur
  berbasis struktur (yang juga menyertakan `reason: "structure_limit"`).
- Hal ini dapat terjadi ketika chat kelas berat lain atau respons streaming yang berjalan lama
  masih berlangsung.

Isi respons berbasis byte adalah:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Respons berbasis struktur menggunakan jenis dan kode yang sama, dengan pesan
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
dan `reason: "structure_limit"`.
Pada ambang batas default, suatu permintaan dianggap berat secara struktural jika memiliki setidaknya `200` pesan,
setidaknya `64` alat, atau setidaknya `32,000` token perkiraan, atau ketika estimasi struktur berbatas
mencapai batas `10,000` node yang dikunjungi atau kedalaman `12`.

**Penyebab:** Ini adalah pengurangan beban yang disengaja di dalam OmniRoute, bukan kegagalan penyedia upstream.
Setiap proses menggunakan guard lokal proses untuk mencadangkan kapasitas kelas berat yang terbatas sebelum menahan
dan mengurai isi permintaan yang besar. Lease kelas berat tetap dipegang selama masa aktif respons SSE.

**#503-fanout:** sebelum perbaikan ini, guard membatasi konkurensi pada JUMLAH permintaan tetap
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default `1`) tanpa mempertimbangkan memori host, sehingga fan-out
agen pemrograman (beberapa subagen/CLI, dengan isi yang biasanya > 256 KB) turun menjadi konkurensi efektif
~1 dan menghasilkan 503 di bawah beban yang sepenuhnya normal. Guard kini menyesuaikan diri secara otomatis:
guard dikendalikan oleh anggaran BYTE penyerapan yang diturunkan secara otomatis
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dan ditentukan berdasarkan batas memori aktual proses, serta
mempertimbangkan sinyal tekanan sumber daya secara langsung — sehingga guard hanya mengurangi beban ketika
host benar-benar mengalami tekanan memori, bukan sekadar karena lebih dari satu permintaan berat tiba
bersamaan. Batas jumlah lama (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) tetap dipatuhi, tetapi hanya jika
Anda menetapkannya secara eksplisit.

Ketika kapasitas sedang sibuk, permintaan kelas berat terlebih dahulu menunggu hingga
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default `2000`, `0` menonaktifkan waktu tunggu) agar suatu slot tersedia
sebelum mengembalikan `503` yang dapat dicoba ulang. Waktu tunggu terbatas ini disediakan agar klien bergaya agen
(OpenCode, Claude Code, Cursor) yang melakukan fan-out subpermintaan berat secara bersamaan menserialisasi lonjakan
tersebut, alih-alih menghabiskan seluruh anggaran percobaan ulang mereka akibat penolakan langsung dan berhenti
di tengah tugas. Okupansi lease kelas berat saat ini, anggaran byte yang telah ditentukan, dan tingkat tekanan
langsung ditampilkan di `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — periksa nilai-nilai ini sebelum mengubah env var apa pun.
Settings → Resilience → Request Queue → Concurrent Requests tidak mengendalikan hal ini; pengaturan tersebut
mengatur mekanisme antrean permintaan penyedia yang terpisah.

**Perbaikan:**

1. Coba ulang terlebih dahulu. Klien harus mematuhi `Retry-After` dan menggunakan backoff, bukan langsung
   mengulangi permintaan.
2. Periksa `/api/monitoring/health` → `chatAdmission` sebelum menyetel apa pun. `countCapEnabled:
false` dan `maxInflightBytes` yang memadai berarti anggaran yang diturunkan secara otomatis sudah menjalankan
   fungsinya; `pressureSeverity` bernilai `high`/`critical` berarti host benar-benar kekurangan memori —
   hal tersebut tidak dapat diperbaiki dengan env var admission, tetapi memerlukan RAM yang lebih besar atau beban kerja yang lebih kecil.
3. Hanya jika `/api/monitoring/health` menunjukkan bahwa anggaran yang diturunkan secara otomatis benar-benar terlalu kecil untuk
   host Anda (jarang terjadi — anggaran ini sudah diskalakan dari container hingga bare-metal), timpa secara langsung dengan
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, alih-alih kembali menggunakan batas jumlah permintaan lama.

Lihat [referensi variabel lingkungan](../reference/ENVIRONMENT.md#4-security--authentication)
untuk pengaturan admission yang berlaku secara resmi.

## Taksonomi kegagalan RAG / LLM opsional (16 masalah)

Sebagian pengguna OmniRoute menempatkan gateway di depan stack RAG atau agen. Dalam konfigurasi tersebut, pola yang aneh sering terlihat: OmniRoute tampak sehat (penyedia aktif, profil perutean baik, tidak ada peringatan batas laju), tetapi jawaban akhirnya tetap salah.

Dalam praktiknya, insiden ini biasanya berasal dari pipeline RAG hilir, bukan dari gateway itu sendiri.

Jika Anda menginginkan kosakata bersama untuk menjelaskan kegagalan tersebut, Anda dapat menggunakan WFGY ProblemMap, sumber daya teks eksternal berlisensi MIT yang mendefinisikan enam belas pola kegagalan RAG / LLM yang berulang. Secara umum, cakupannya meliputi:

- penyimpangan pengambilan dan batas konteks yang rusak
- indeks serta penyimpanan vektor yang kosong atau usang
- ketidakcocokan embedding dengan semantik
- masalah penyusunan prompt dan jendela konteks
- keruntuhan logika dan jawaban yang terlalu percaya diri
- kegagalan rantai panjang dan koordinasi agen
- penyimpangan memori dan peran multi-agen
- masalah urutan deployment dan bootstrap

Idenya sederhana:

1. Saat menyelidiki respons yang buruk, catat:
   - tugas dan permintaan pengguna
   - kombinasi rute atau penyedia di OmniRoute
   - konteks RAG apa pun yang digunakan di hilir (dokumen yang diambil, pemanggilan alat, dan sebagainya)
2. Petakan insiden ke satu atau dua nomor WFGY ProblemMap (`No.1` … `No.16`).
3. Simpan nomor tersebut di dasbor, runbook, atau pelacak insiden Anda sendiri di samping log OmniRoute.
4. Gunakan halaman WFGY yang sesuai untuk menentukan apakah Anda perlu mengubah stack RAG, retriever, atau strategi perutean.

Teks lengkap dan resep konkret tersedia di sini (lisensi MIT, hanya teks):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Anda dapat mengabaikan bagian ini jika tidak menjalankan pipeline RAG atau agen di belakang OmniRoute.

## Masalah Umum v3.8.0

Masalah yang khusus untuk rilis v3.8.0 dan solusi sementaranya saat ini. Jika perbaikan tersedia dalam patch berikutnya, entri akan diperbarui atau dihapus.

### Kegagalan autentikasi Devin CLI

**Gejala:**

- "Devin CLI tidak ditemukan" atau "autentikasi gagal" saat memanggil alat yang didukung Devin
- Pemeriksaan runtime CLI melaporkan `installed=false`

**Penyebab:**

- `CLI_DEVIN_BIN` mengarah ke lokasi yang tidak ada
- Devin CLI tidak terinstal pada host

**Perbaikan:**

1. Instal Devin CLI untuk platform Anda
2. Atur `CLI_DEVIN_BIN=/usr/local/bin/devin` (atau lokasi sebenarnya) di `.env`
3. Mulai ulang OmniRoute dan lakukan pengujian kembali dari **Dasbor → Alat CLI**

### Cooldown model macet (reset manual)

**Gejala:**

- Model tetap tercantum dalam cooldown bahkan setelah waktu kedaluwarsa berlalu
- Permintaan masih melewati model dalam perutean kombinasi meskipun timestamp sudah berada di masa lalu

**Reset manual:**

- **Dasbor:** **Pengaturan → Cooldown Model** → klik **Aktifkan kembali** pada kartu yang terdampak
- **API:** `DELETE /api/resilience/model-cooldowns` dengan header autentikasi manajemen

### Koneksi penyedia Command Code gagal dengan 403

**Gejala:**

- 403 saat menguji koneksi penyedia Command Code
- Kartu penyedia menampilkan "tidak diotorisasi" setelah baru ditambahkan

**Penyebab:** Alur OAuth tidak selesai (callback tidak diterima atau token tidak dipertahankan).

**Perbaikan:**

- Jalankan `omniroute providers` dari CLI untuk memicu ulang alur OAuth, atau
- Jalankan ulang OAuth dari **Dasbor → Penyedia → Command Code → Hubungkan kembali**

### ModelScope menghasilkan cooldown 429 yang agresif

**Gejala:**

- Cooldown yang sangat singkat atau langsung terjadi pada ModelScope setelah sejumlah kecil permintaan secara beruntun
- Perutean kombinasi melewati ModelScope lebih awal daripada yang diperkirakan

**Penyebab:** ModelScope mengirimkan header `Retry-After` khusus penyedia. v3.8.0 menyediakan penanganan khusus untuk header tersebut, sehingga versi lama salah membacanya sebagai petunjuk batas laju generik.

**Perbaikan:**

- Pastikan Anda menggunakan v3.8.0 atau yang lebih baru
- Pastikan toggle `useUpstream429BreakerHints` diaktifkan pada **Pengaturan → Ketahanan**

### OMNIROUTE_WS_BRIDGE_SECRET tidak ada di lingkungan produksi

**Gejala:**

- 401 pada setiap permintaan bridge WebSocket Codex/Responses saat berjalan pada host produksi jarak jauh
- Handshake bridge WebSocket langsung ditutup setelah terhubung

**Penyebab:** Variabel env `OMNIROUTE_WS_BRIDGE_SECRET` tidak ada di lingkungan produksi.

**Perbaikan:**

1. Buat secret acak: `openssl rand -hex 32`
2. Atur `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` di env server produksi (dan klien apa pun yang berkomunikasi dengan bridge)
3. Mulai ulang OmniRoute

### Responses API: mode latar belakang diturunkan menjadi sinkron

**Gejala:**

- Peringatan dicatat: `background mode degraded to synchronous`
- Permintaan `background: true` mengembalikan respons sinkron normal, bukan handle tugas latar belakang

**Penyebab:** v3.8.0 sengaja menurunkan `background: true` pada Responses API menjadi eksekusi sinkron sembari mengeluarkan peringatan. Eksekusi latar belakang asinkron penuh akan disediakan pada masa mendatang.

**Perbaikan:**

- Sesuaikan klien agar melakukan pemanggilan tanpa `background`, atau
- Tunggu rilis berikutnya yang menyediakan mode latar belakang asinkron penuh (pantau changelog)

## Startup Lambat / Waktu Tunggu Kesiapan Habis

Jika CLI menampilkan `⚠ Server did not respond within 60s`, tetapi server
sebenarnya berfungsi, batas waktu probe kesiapan terlalu singkat untuk lingkungan Anda.

Hal ini umumnya terjadi di Windows (antivirus, pemantau sistem berkas) atau container
dengan beban kerja startup yang berat.

**Solusi — tingkatkan batas waktu:**

```bash
# Melalui variabel lingkungan (berlaku pada setiap startup):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 menit
omniroute serve

# Melalui flag CLI (sekali pakai):
omniroute serve --ready-timeout 180000
```

Nilai default adalah 60.000 ms (60 dtk). Peringatan tersebut hanya bersifat informatif; server
tetap melakukan startup di latar belakang dan akan dapat diakses setelah proses boot selesai.

Lihat [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) untuk detail
lengkap tentang `OMNIROUTE_READY_TIMEOUT_MS`.
