### Pembatasan Laju pada Penyedia Gratis (429 / 400 / 401)

**Gejala**: Saat menggunakan `model: "auto"` dengan penyedia gratis/tanpa autentikasi (opencode, auggie, dll.), Anda sesekali mendapatkan `HTTP 429`, `400`, atau `401` alih-alih jawaban. Permintaan berhasil saat prompt yang sama dicoba kembali beberapa saat kemudian, tetapi otomatisasi (cron job, agen, skrip) terhenti pada kegagalan pertama.

**Penyebab utama**: Tiga mode kegagalan independen terjadi secara bersamaan:

1. **Batas laju penyedia (`429`)**: Tingkat gratis dapat memberlakukan kuota per jendela waktu. Rentetan panggilan paralel menghabiskannya, sehingga permintaan berikutnya ditolak hingga jendela tersebut direset.
2. **Model rusak dalam passthrough (`400`/`401`)**: Pool `auto/*` dapat menyertakan model passthrough dari `opencode` yang terdaftar dalam katalog tetapi tidak memiliki kredensial aktif (misalnya `oc/north-mini-code-free` → `401`). Auto-router mencoba salah satunya, gagal, dan galat diteruskan sebelum fallback sempat dijalankan.
3. **Amplifikasi konkurensi (`429` saat beban tinggi)**: Ketika beberapa sesi agen/cron mengakses `auto` secara bersamaan, laju permintaan gabungan melampaui batas yang dapat ditoleransi penyedia gratis, sehingga panggilan yang sah ditandai sebagai penyalahgunaan.

**Perbaikan terverifikasi (dilaporkan komunitas, 2026-08-10)**: sesuaikan tiga variabel lingkungan agar rotasi, konkurensi, dan fallback dapat menangani fluktuasi tingkat gratis alih-alih gagal karenanya:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # beralih ke model/penyedia lain saat 400/401 (melewati model passthrough yang rusak)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # batas penerimaan eksplisit untuk beban berat (secara default tidak disetel: tidak ada batas jumlah permintaan, lihat catatan di bawah)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # tingkatkan waktu tunggu terbatas melampaui nilai default RATE_LIMIT_MAX_WAIT_MS untuk upstream yang lambat
```

Tetapkan variabel ini di lingkungan proses OmniRoute (daemon, misalnya melalui plist LaunchAgent atau `systemctl edit`), lalu mulai ulang OmniRoute. Flag rotasi adalah pengungkit tunggal yang paling berdampak: flag ini mengubah kegagalan total menjadi percobaan ulang transparan menggunakan penyedia yang sehat di dalam pool.

**Catatan**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` membatasi jumlah permintaan berat — berkonteks panjang — yang berjalan sekaligus; batas tersebut merupakan gerbang penerimaan, bukan pembatas laju penyedia. **Pembaruan #503-fanout:** variabel ini tidak lagi disetel secara default (sekarang hanya berlaku jika dikonfigurasi secara eksplisit, seperti di atas) — penerimaan beban berat kini dibatasi oleh anggaran byte yang diturunkan secara otomatis (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dan menyesuaikan skalanya berdasarkan batas memori aktual host, sehingga deployment baru seharusnya mengalami jauh lebih sedikit penolakan `503 chat_admission_busy` tanpa perlu menyetel variabel ini sama sekali; menyetelnya secara eksplisit di sini tetap berfungsi persis seperti yang didokumentasikan. Override anggaran byte eksplisit dibatasi ke rentang 8 MiB–2 GiB. `413 body_exceeds_budget` bukanlah kondisi sementara: tingkatkan anggaran byte tersebut, turunkan `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, atau tingkatkan batas memori proses. Pelepasan `inflight_bytes_budget` merupakan kontensi sementara dan tetap dapat dicoba ulang. Pembatasan laju per penyedia (`open-sse/services/rateLimitManager.ts`) diatur secara terpisah oleh `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, dan `RATE_LIMIT_AUTO_ENABLE` — lihat `.env.example`.

**Cara memverifikasi bahwa perbaikan berhasil**: jalankan agen/cron Anda dua kali secara berurutan dalam waktu singkat dan pastikan keduanya berhasil. Sebelum perbaikan, proses kedua biasanya menghasilkan `429`/`401`. Setelah perbaikan, kegagalan (jika ada) dicoba ulang secara transparan dan panggilan selesai. Anda juga dapat menjalankan `curl /monitoring/health` dan memantau bidang `rateLimitedUntil` pada koneksi penyedia serta `circuitBreakers.providerBreakers[].state` untuk penyedia yang terdampak — statusnya dapat berupa `CLOSED`, `DEGRADED`, `OPEN`, atau `HALF_OPEN` (lihat `src/shared/utils/circuitBreaker.ts`), dan penyedia yang terus mengalami kegagalan akan beralih dari `CLOSED → DEGRADED → OPEN` sebelum jendela pengaturan ulang mengizinkan sebuah probe (`HALF_OPEN`).

**Jika Anda masih melihat 429**: akun aktif untuk penyedia tersebut benar-benar telah menghabiskan _kuota_-nya (bukan sekadar terkena pembatasan laju). Tambahkan akun kedua untuk penyedia yang sama di dasbor OmniRoute → Providers → Accounts, atau gunakan penyedia gratis lain sebagai kombinasi (misalnya `routeway`, `auggie`). Rotasi hanya membantu mengatasi pembatasan laju sementara/400/401; kehabisan kuota secara mutlak memerlukan kredensial kedua atau penyedia lain.

**Jika Anda melihat 403 pada model visi (`auto/vision`, `bazaarlink/*`)**: akun yang terhubung tidak memiliki paket berbayar yang mencakup visi, atau kunci API tidak memiliki izin yang memadai. Verifikasikan di dasbor penyedia bahwa cakupan kunci mencakup visi/multimodal, atau hubungkan akun tingkat berbayar dan pertahankan akun tersebut sebagai target visi.

## Peringatan npm install (ERESOLVE / peer / deprecated)

Saat menjalankan `npm install -g omniroute`, Anda mungkin melihat banyak peringatan seperti `npm warn ERESOLVE`, pemberitahuan dependensi peer, dan pesan `deprecated`. **Hal ini sudah diperkirakan dan tidak berbahaya.** Instalasi Anda berhasil jika melihat `added <N> packages` dalam output.

Untuk menyembunyikan peringatan resolusi dependensi peer, gunakan format instalasi yang didukung OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` hanya menyembunyikan `ERESOLVE` dan pemberitahuan dependensi peer. Pemberitahuan penghentian dukungan tetap terlihat karena berasal dari paket pihak ketiga transitif; pemberitahuan tersebut tidak menunjukkan bahwa instalasi gagal.

Peringatan tersebut berasal dari rentang dependensi peer usang dalam paket pihak ketiga yang tidak dikendalikan oleh OmniRoute:

1. **`marked-terminal` memerlukan `marked >=1 <16`, tetapi yang ditemukan adalah `marked@18`** — dalam praktiknya tetap berfungsi dengan baik; rentang peer upstream tersebut hanya sudah usang.
2. **`deprecated prebuild-install@7.1.3`** — helper pengambilan biner native transitif. Paket ini tidak
   digunakan untuk menginstal binding transport `wreq-js` yang dikunci versinya dan tidak menunjukkan bahwa
   penyiapan transport penyedia web-cookie gagal.

**Tidak diperlukan tindakan apa pun** — peringatan tersebut tidak dapat disembunyikan sepenuhnya tanpa melakukan fork terhadap paket upstream.

## Peringatan Pemblokiran Skrip npm install (instalasi global)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Saat menjalankan `npm install -g omniroute`, versi npm yang lebih baru (v11+ dan v12+) secara default memblokir skrip siklus hidup paket dan menampilkan peringatan skrip instalasi:

```
npm warn install-scripts 7 paket memiliki skrip instalasi yang diblokir karena tidak tercakup oleh allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Apakah peringatan ini dapat diabaikan?

**Sebagian, tetapi menjalankannya tanpa skrip tidak disarankan.** OmniRoute menyediakan fallback yang aman: jika binding native `better-sqlite3` tidak dapat dimuat dari bundel mandiri, aplikasi akan beralih menggunakan driver alternatif seperti `node:sqlite` atau `sql.js` (lihat [Resolusi Runtime SQLite](../ops/SQLITE_RUNTIME.md)). Server tetap dapat dijalankan, tetapi penggunaan fallback WASM seperti `sql.js` menonaktifkan mode WAL (Write-Ahead Logging) SQLite serta meningkatkan overhead memori dan sinkronisasi disk.

### Skrip mana yang benar-benar diperlukan?

Tidak semua skrip yang diblokir diperlukan untuk menjalankan OmniRoute:

- **Esensial (`omniroute`, `better-sqlite3`):** OmniRoute dijalankan dari bundel aplikasi mandiri Next.js (`dist/`). Selama instalasi, npm mengunduh atau mengompilasi driver SQLite native khusus host di `node_modules/better-sqlite3/` tingkat teratas. Skrip `postinstall` OmniRoute (`scripts/build/postinstall.mjs`) kemudian memverifikasi dan menyalin biner khusus host tersebut ke `dist/node_modules/` agar server mandiri dapat mengaksesnya. Jika skrip postinstall `omniroute` diblokir, langkah penyalinan ini akan dilewati.
- **Opsional/transitif (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Paket-paket ini merupakan helper build, alat watcher, atau utilitas keychain sistem. Mengizinkannya akan mencegah peringatan build, tetapi paket-paket tersebut tidak diperlukan untuk fungsionalitas perutean inti.
- **Dikecualikan (`onnxruntime-node`):** Dependensi opsional untuk embedding AI lokal dan **tidak** diperlukan agar OmniRoute dapat dijalankan. Skrip postinstall-nya mengunduh aset CUDA sebesar ~300MB dari NuGet; jangan sertakan dalam daftar yang diizinkan kecuali Anda memang bermaksud menggunakan akselerasi ONNX lokal pada perangkat keras yang didukung.

### Perbaikan yang disarankan

Untuk mengizinkan skrip instalasi yang diperlukan selama instalasi global dan menyembunyikan peringatan, teruskan `--allow-scripts` untuk OmniRoute dan dependensi native-nya:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Sebagai alternatif, untuk mengonfigurasi hal ini secara permanen bagi semua instalasi global pada akun pengguna Anda:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Verifikasi instalasi Anda

Setelah instalasi, jalankan alat diagnostik bawaan untuk memastikan bahwa binding native dan lingkungan runtime berfungsi dengan baik:

```bash
omniroute doctor
```

## Positif Palsu Antivirus

<a name="antivirus-false-positives"></a>

### Avast/AVG mengarantina `README.md` dengan `MD:HttpRequest-inf[Susp]`

**Ini adalah positif palsu. Tidak ada yang terinfeksi, dan tidak diperlukan tindakan apa pun.**

Avast dan AVG menjalankan heuristik yang menandai file teks biasa/Markdown yang berisi banyak
tautan yang tampak seperti permintaan HTTP. `README.md` milik OmniRoute disertakan di dalam paket npm (file ini
tercantum di `package.json` → `files`), sehingga pada instalasi global file tersebut ditempatkan di
`node_modules/omniroute/README.md` — dan berisi sekitar 15 contoh `http://localhost:20128/...` (endpoint
HTTP/SSE MCP, URL `.well-known` A2A, dan cuplikan `curl`). Kepadatan tautan tersebut
cukup untuk memicu heuristik.

Jika masalah ini baru muncul belakangan: jenis file tersebut tidak berubah. README memperluas
tabel endpoint-nya (HTTP MCP + SSE + A2A ditambahkan) dan menambahkan lebih banyak contoh `curl`, sehingga
melewati ambang batas.

File tersebut hanyalah dokumentasi pasif tanpa konten yang dapat dieksekusi. Anda dapat memulihkannya
dari karantina dengan aman.

**Yang harus dilakukan:**

1. **Hentikan notifikasi** — kecualikan direktori instalasi di antivirus Anda
   (Avast: Settings → Exceptions), dengan menambahkan jalur `node_modules` global Anda dan/atau
   direktori data OmniRoute (`~/.omniroute/`).
2. **Laporkan positif palsu tersebut** — <https://www.avast.com/false-positive-file-form.php>,
   dengan melampirkan `README.md` yang dikarantina. Inilah perbaikan yang membantu semua orang, karena
   heuristik vendor bereaksi berlebihan terhadap file teks.

**Mengapa kami tidak "memperbaiki" ini dari sisi kami:** semua contoh menggunakan `http://localhost`, dan
localhost tidak dapat menggunakan `https` tanpa kerumitan sertifikat yang ditandatangani sendiri. Mengubah dokumentasi secara tidak wajar untuk
menghindari heuristik satu vendor akan merugikan setiap pembaca hanya demi mengakomodasi bug pemindai.

### Kaspersky menandai aplikasi Desktop sebagai `PDM:Trojan.Win32.Generic`

**Ini adalah positif palsu dari heuristik perilaku. Tidak ada yang terinfeksi.** Prefiks
`PDM:` milik Kaspersky berarti keputusan tersebut berasal dari Proactive Defense Module (System Watcher),
yang menilai apa yang _dilakukan_ penginstal, bukan mencocokkannya dengan malware yang dikenal. Ketika
terpicu, Kaspersky "mengembalikan" seluruh instalasi — menghapus file yang telah
ditulis — sehingga aplikasi menjadi rusak atau hilang.

File yang ditandainya merupakan bagian standar dari dependensi sumber terbuka yang dideklarasikan dan dibundel dengan
aplikasi desktop, misalnya:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` dan
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), pustaka otomatisasi browser
  yang digunakan untuk login penyedia dalam aplikasi dan chat berbasis browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — binding native `wreq-js` yang versinya dikunci dan digunakan untuk HTTP dengan sidik jari browser pada penyedia
  berbasis cookie web (`<arch>` adalah `x64` atau `arm64`).

**Mengapa ini terpicu:** penginstal Windows **belum ditandatangani secara digital**, sehingga penginstal NSIS
yang tidak ditandatangani tidak memiliki reputasi dan heuristik perilaku berjalan dengan tingkat agresivitas maksimum. Jika
digabungkan dengan DLL native yang dibundel dan ratusan file `.js` yang ditulis di bawah
`%LOCALAPPDATA%\Programs\OmniRoute` (termasuk direktori paket dengan akhiran hash dari build
standalone Next.js), kondisi tersebut cukup untuk memicu heuristik. Penandatanganan kode telah direncanakan;
hingga diterapkan, rilis baru dapat kembali mengalami hal ini.

**Yang harus dilakukan:**

1. **Verifikasi unduhan Anda terlebih dahulu** (untuk memastikan file tidak dimodifikasi). Setiap rilis menyediakan
   `latest.yml`, yang bidang `sha512`-nya (base64) mencakup penginstal
   `OmniRoute.Setup.<version>.exe`. Di PowerShell, dari folder yang berisi penginstal:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Output harus cocok dengan `latest.yml` → `sha512`. Jika tidak cocok, hapus file tersebut dan
   unduh ulang hanya dari [halaman rilis GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Pulihkan + kecualikan** — pulihkan item yang dikembalikan dari karantina dan tambahkan pengecualian
   untuk `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   lalu instal ulang.
3. **Laporkan positif palsu tersebut** — <https://opentip.kaspersky.com/>. Laporan FP yang
   dikirimkan pengguna benar-benar mempercepat proses penambahan ke daftar aman.

## Kompatibilitas Node.js

<a name="nodejs-compatibility"></a>

### Halaman login mengalami crash atau menampilkan kesalahan "Module self-registration"

**Penyebab:** Anda menjalankan versi Node.js di luar batas minimum runtime aman yang disetujui OmniRoute. Kasus yang paling umum adalah menjalankan versi patch Node 22 atau 24 yang lebih lama dan berada di bawah batas minimum keamanan dengan patch yang diwajibkan OmniRoute.

**Gejala:**

- Halaman login menampilkan layar kosong atau kesalahan server
- Konsol menampilkan `Error: Module did not self-register` atau kesalahan native binding serupa
- Halaman login menampilkan **banner peringatan berwarna oranye** dengan versi Node Anda jika runtime berada di luar kebijakan aman yang didukung

**Perbaikan:**

1. Instal rilis Node.js LTS yang didukung (disarankan: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifikasi versi Anda: `node --version` harus menampilkan `v24.0.0` atau yang lebih baru pada lini LTS 24.x
3. Instal ulang OmniRoute: `npm install -g omniroute`
4. Mulai ulang: `omniroute`

> **Versi aman yang didukung:** `>=22.22.2 <23` atau `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) dan Node.js 26 didukung sepenuhnya.

### npm v11+: `better-sqlite3` tidak terinstal (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Penyebab:** npm v11 (disertakan bersama Node.js 24+) secara default memblokir skrip instalasi untuk dependensi
opsional. Karena `better-sqlite3` tercantum dalam `optionalDependencies`
dan memerlukan kompilasi native (`node-gyp rebuild`), npm melewatinya tanpa pemberitahuan.

**Gejala:**

- Server mengalami crash saat dimulai dengan `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` menampilkan "No such file or directory"
- `npm ls better-sqlite3` menampilkan `(empty)`

**Perbaikan:**

1. Setujui skrip instalasi dan instal ulang:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Atau instal paket bawaan secara manual:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifikasi bahwa paket berfungsi: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Penyebab:** Setelah menjalankan `npm install -g omniroute` secara global, binary native `better-sqlite3` di dalam paket mungkin telah dikompilasi untuk arsitektur atau ABI Node.js yang berbeda dari yang berjalan secara lokal. Hal ini umum terjadi di macOS (baik Apple Silicon maupun Intel) ketika binary bawaan tidak cocok dengan lingkungan Anda.

**Gejala:**

- Server langsung gagal saat dimulai dengan kesalahan `dlopen`
- Kesalahan memuat `slice is not valid mach-o file`
- Contoh lengkap:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Perbaikan — kompilasi ulang untuk lingkungan lokal Anda (tidak perlu menurunkan versi Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Catatan:** Tindakan ini mengompilasi ulang native binding terhadap versi Node.js dan arsitektur CPU lokal Anda, sehingga mengatasi ketidakcocokan binary. Rentang runtime yang didukung secara resmi adalah **`>=22.22.2 <23` atau `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` dalam `src/shared/utils/nodeRuntimeSupport.ts`, diselaraskan dengan bidang `engines` pada `package.json`). Node.js 24.x LTS (Krypton) dan Node.js 26 didukung sepenuhnya dengan `better-sqlite3` v12.x.

## Masalah Proxy

<a name="proxy-issues"></a>

### Validasi penyedia menampilkan "fetch failed"

**Penyebab:** Endpoint validasi kunci API (`POST /api/providers/validate`) sebelumnya melewati konfigurasi proxy, sehingga menyebabkan kegagalan di lingkungan yang memerlukan perutean melalui proxy.

**Perbaikan (v3.5.5+):** Masalah ini sekarang telah diperbaiki. Validasi penyedia dirutekan melalui `runWithProxyContext`, sehingga secara otomatis mengikuti pengaturan proxy tingkat penyedia dan global.

### Pemeriksaan kesehatan token gagal dengan "fetch failed"

**Penyebab:** Penyegaran token OAuth di latar belakang tidak menentukan konfigurasi proxy untuk setiap koneksi.

**Perbaikan (v3.5.5+):** Penjadwal pemeriksaan kesehatan token kini menentukan konfigurasi proxy untuk setiap koneksi sebelum mencoba melakukan penyegaran. Perbarui ke v3.5.5+.

### Proxy SOCKS5 menampilkan "invalid onRequestStart method"

**Penyebab:** Pada Node.js 22, dispatcher undici@8 tidak kompatibel dengan implementasi bawaan `fetch()` milik Node.

**Perbaikan (v3.5.5+):** OmniRoute kini menggunakan fungsi `fetch()` milik undici sendiri saat dispatcher proxy aktif, sehingga memastikan perilaku yang konsisten. Perbarui ke v3.5.5+.

### Proxy MITM di WSL: aplikasi desktop pada host Windows tidak dicegat

**Penyebab:** Proxy MITM dan sertifikat CA-nya dipasang di lingkungan tempat OmniRoute berjalan. Di WSL, lingkungan tersebut adalah guest Linux, sedangkan aplikasi desktop AI (Kiro, Trae, Copilot, Zed, …) berjalan pada host Windows. Aplikasi host tidak memercayai penyimpanan sertifikat milik guest dan tidak merutekan koneksi melalui proxy sistem milik guest, sehingga pencegatan desktop tidak berjalan di sana.

**Rekomendasi:** Jalankan OmniRoute secara native pada OS yang sama dengan aplikasi desktop yang ingin Anda cegat (Windows untuk aplikasi Windows; demikian pula untuk macOS/Linux). Menjalankan OmniRoute di dalam WSL sambil menargetkan aplikasi host mengharuskan Anda memercayai sertifikat CA yang dihasilkan secara manual pada host Windows dan mengarahkan pengaturan jaringan/proxy setiap aplikasi host ke endpoint proxy WSL — konfigurasi yang tidak didukung dan rentan bermasalah.

## Masalah Penyedia

### "Language model did not provide messages"

**Penyebab:** Kuota penyedia telah habis.

**Perbaikan:**

1. Periksa pelacak kuota di dasbor
2. Gunakan kombinasi dengan tingkat fallback
3. Beralih ke tingkat yang lebih murah/gratis

### Pembatasan Laju

**Penyebab:** Kuota langganan telah habis.

**Perbaikan:**

- Tambahkan fallback: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Gunakan GLM/MiniMax sebagai cadangan murah

### Token OAuth Kedaluwarsa

OmniRoute menyegarkan token secara otomatis. Jika masalah berlanjut:

1. Dasbor → Penyedia → Hubungkan Kembali
2. Hapus lalu tambahkan kembali koneksi penyedia

### Multi-akun Kiro: akun kedua membuat akun pertama tidak valid

**Penyebab:** Backend Kiro memberlakukan satu sesi aktif untuk setiap pendaftaran klien OIDC.
Saat dua akun berbagi klien terdaftar yang sama (koneksi yang diimpor sebelum v3.8.0),
penyegaran token salah satu akun membuat token penyegaran akun lainnya tidak valid.

**Perbaikan (v3.8.0+):** Impor ulang koneksi yang terdampak.
Mulai v3.8.0, setiap koneksi Kiro baru yang dibuat melalui **Impor Token**,
**login sosial Google/GitHub**, atau **Impor Otomatis** secara otomatis mendaftarkan
klien OIDC khususnya sendiri. Dengan demikian, koneksi sepenuhnya terisolasi dan penyegaran satu
akun tidak berdampak pada akun lainnya.

Koneksi yang diimpor _sebelum_ v3.8.0 tidak memiliki pendaftaran klien
per koneksi. Koneksi tersebut tetap menggunakan endpoint penyegaran autentikasi sosial bersama.
Untuk mendapatkan isolasi, hapus koneksi lama dari Dasbor → Penyedia lalu tambahkan kembali
melalui salah satu dari tiga alur impor.

Untuk detail lengkap dan petunjuk langkah demi langkah guna menambahkan dua akun Kiro secara berdampingan,
lihat [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Masalah Cloud

### Kesalahan Sinkronisasi Cloud

1. Pastikan `BASE_URL` mengarah ke instans yang sedang berjalan (misalnya, `http://localhost:20128`)
2. Pastikan `CLOUD_URL` mengarah ke endpoint cloud Anda (misalnya, `https://omniroute.dev`)
3. Pastikan nilai `NEXT_PUBLIC_*` tetap selaras dengan nilai sisi server

### Cloud `stream=false` Menghasilkan 500

**Gejala:** `Unexpected token 'd'...` pada endpoint cloud untuk panggilan non-streaming.

**Penyebab:** Upstream mengembalikan payload SSE sementara klien mengharapkan JSON.

**Solusi sementara:** Gunakan `stream=true` untuk panggilan langsung ke cloud. Runtime lokal menyertakan fallback SSE→JSON.

### Cloud Menyatakan Terhubung tetapi "Invalid API key"

1. Buat kunci baru dari dasbor lokal (`/api/keys`)
2. Jalankan sinkronisasi cloud: Aktifkan Cloud → Sinkronkan Sekarang
3. Kunci lama/belum disinkronkan masih dapat menghasilkan `401` di cloud

## Masalah Docker

### IPv6 Docker / Koneksi Direset

<a name="docker-ipv6"></a>

**Gejala:** `curl http://localhost:20128/v1/models` menghasilkan `curl: (56) Recv failure: Connection reset by peer`. Dasbor dan endpoint tanpa autentikasi berfungsi, tetapi endpoint terautentikasi gagal — ini terlihat seperti masalah autentikasi, padahal bukan.

**Penyebab:** `docker run -p 20128:20128` memublikasikan pada `0.0.0.0` (IPv4) dan `::` (IPv6), tetapi proses di dalam kontainer hanya mendengarkan pada IPv4. Pada host tempat `localhost` di-resolve ke `::1` terlebih dahulu, koneksi masuk ke port IPv6 yang dipublikasikan tanpa listener di belakangnya → koneksi direset.

**Perbaikan:**

1. **Diagnostik cepat:** Jalankan `curl -4 http://localhost:20128/v1/models`. Jika berfungsi dengan `-4` tetapi gagal tanpanya, terdapat ketidakcocokan binding IPv6.
2. **Perbaikan permanen:** Bind ke IPv4 secara eksplisit dengan menggunakan `-p 127.0.0.1:20128:20128` dalam perintah `docker run` Anda:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Ini memaksa binding IPv4 dan juga mencegah proxy terekspos pada semua antarmuka host.

---

## Debugging

### Aktifkan File Log

Atur `APP_LOG_TO_FILE=true` dalam file `.env` Anda. Log aplikasi ditulis di dalam `logs/`.
Artefak permintaan disimpan di dalam `${DATA_DIR}/call_logs/` saat pipeline log panggilan
diaktifkan dalam pengaturan.
Saat perekaman pipeline diaktifkan, atur `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` untuk menghilangkan
payload potongan stream, atau sesuaikan `CALL_LOG_PIPELINE_MAX_SIZE_KB` untuk mengubah batas artefak dalam KB.

http://localhost:20128/dashboard/health

# Pemeriksaan kondisi API

## Masalah Circuit Breaker

### Penyedia terjebak dalam status OPEN

Saat circuit breaker penyedia berstatus OPEN, permintaan akan diblokir hingga masa tunggu berakhir.

**Perbaikan:**

1. Buka **Dasbor → Pengaturan → Ketahanan**
2. Periksa kartu circuit breaker untuk penyedia yang terdampak
3. Klik **Atur Ulang Semua** untuk menghapus semua breaker, atau tunggu hingga masa tunggu berakhir
4. Pastikan penyedia benar-benar tersedia sebelum melakukan pengaturan ulang

### Penyedia terus memicu circuit breaker

Jika penyedia berulang kali memasuki status OPEN:

1. Periksa pola kegagalan di **Dasbor → Kesehatan → Kesehatan Penyedia**
2. Buka **Pengaturan → Ketahanan → Profil Penyedia** dan tingkatkan ambang batas kegagalan
3. Periksa apakah penyedia telah mengubah batas API atau mewajibkan autentikasi ulang
4. Tinjau telemetri latensi — latensi tinggi dapat menyebabkan kegagalan akibat waktu tunggu habis

## Masalah Transkripsi Audio

### Kesalahan "Model tidak didukung"

- Gunakan ID model yang segmen pertamanya merupakan penyedia yang kredensialnya Anda miliki (`openai/whisper-1`, `openrouter/deepgram/nova-3`). `deepgram/nova-3` saja memerlukan kunci native Deepgram.
- Pastikan penyedia telah terhubung di **Dasbor → Penyedia**

### Transkripsi kosong atau gagal

- Periksa format audio yang didukung: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- Pastikan ukuran file masih dalam batas penyedia (biasanya < 25MB)
- Periksa validitas kunci API penyedia pada kartu penyedia

## Debugging Penerjemah

Gunakan **Dasbor → Penerjemah** untuk men-debug masalah penerjemahan format:

| Mode                 | Waktu Penggunaan                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Playground**       | Bandingkan format input/output secara berdampingan — tempel permintaan yang gagal untuk melihat terjemahannya |
| **Penguji Chat**     | Kirim pesan secara langsung dan periksa payload permintaan/respons lengkap, termasuk header                   |
| **Bangku Uji**       | Jalankan pengujian batch pada berbagai kombinasi format untuk menemukan terjemahan yang rusak                 |
| **Monitor Langsung** | Pantau alur permintaan secara real-time untuk menemukan masalah penerjemahan yang terjadi sesekali            |

### Masalah format yang umum

- **Tag thinking tidak muncul** — Periksa apakah penyedia target mendukung thinking dan periksa pengaturan anggaran thinking
- **Pemanggilan alat hilang** — Beberapa penerjemahan format mungkin menghapus bidang yang tidak didukung; verifikasi dalam mode Playground
- **Prompt sistem tidak ada** — Claude dan Gemini menangani prompt sistem secara berbeda; periksa output terjemahan
- **SDK mengembalikan string mentah, bukan objek** — Telah diselesaikan dalam v1.x; sanitizer respons menghapus bidang nonstandar (`x_groq`, `usage_breakdown`, dll.) yang menyebabkan kegagalan validasi Pydantic pada SDK OpenAI. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan masalah.
- **GLM/ERNIE menolak peran `system`** — Telah diselesaikan dalam v1.x; normalizer peran secara otomatis menggabungkan pesan sistem ke dalam pesan pengguna untuk model yang tidak kompatibel. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan masalah.
- **Peran `developer` tidak dikenali** — Telah diselesaikan dalam v1.x; secara otomatis dikonversi menjadi `system` untuk penyedia selain OpenAI. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan masalah.
- **`json_schema` tidak berfungsi dengan Gemini** — Telah diselesaikan dalam v1.x; `response_format` kini dikonversi menjadi `responseMimeType` + `responseSchema` milik Gemini. Jika Anda masih mengalami masalah ini pada v3.x+, silakan laporkan masalah.

## Pengaturan Ketahanan

### Pembatasan laju otomatis tidak terpicu

- Pembatasan laju otomatis hanya berlaku untuk penyedia kunci API (bukan OAuth/langganan)
- Pastikan **Pengaturan → Ketahanan → Profil Penyedia** telah mengaktifkan pembatasan laju otomatis
- Periksa apakah penyedia mengembalikan kode status `429` atau header `Retry-After`

### Menyetel backoff eksponensial

Profil penyedia mendukung pengaturan berikut:

- **Penundaan dasar** — Waktu tunggu awal setelah kegagalan pertama (default: 1 detik)
- **Penundaan maksimum** — Batas maksimum waktu tunggu (default: 30 detik)
- **Pengali** — Besarnya peningkatan waktu tunggu per kegagalan berturut-turut (default: 2x)

### Pencegahan thundering herd

Saat banyak permintaan bersamaan mengakses penyedia yang dikenai pembatasan laju, OmniRoute menggunakan mutex + pembatasan laju otomatis untuk menserialkan permintaan dan mencegah kegagalan berantai. Ini dilakukan secara otomatis untuk penyedia kunci API.

### Permintaan chat gagal dengan 503 / chat_admission_busy

**Gejala:**

- Endpoint penyelesaian chat mengembalikan respons `503` yang dapat dicoba ulang dengan kode kesalahan
  `chat_admission_busy`.
- Respons menyertakan `Retry-After`. Sejak #12135, nilainya diturunkan dari okupansi yang teramati
  — nilai yang lebih besar antara jendela `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` yang telah digunakan
  permintaan untuk menunggu dan lamanya lease heavyweight saat ini telah dipertahankan — dibulatkan
  ke atas menjadi detik penuh dan dibatasi hingga 60. Pada gate yang menganggur, nilai minimum
  historis tetap dipertahankan: 2 detik pada jalur berbasis byte, 1 detik pada jalur berbasis
  struktur (yang juga menyertakan `reason: "structure_limit"`).
- Hal ini dapat terjadi ketika chat heavyweight lain atau respons streaming yang berjalan lama
  masih berlangsung.

Isi respons berbasis byte adalah:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Respons berbasis struktur menggunakan jenis dan kode yang sama, dengan pesan
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
dan `reason: "structure_limit"`.
Pada ambang batas default, permintaan dianggap berat secara struktural jika memiliki setidaknya
`200` pesan, setidaknya `64` alat, atau setidaknya `32,000` token perkiraan, atau ketika estimasi
struktur terbatas mencapai batasnya, yaitu `10,000` node yang dikunjungi atau kedalaman `12`.

**Penyebab:** Ini adalah pengurangan beban yang disengaja di dalam OmniRoute, bukan kegagalan
penyedia upstream. Setiap proses menggunakan guard lokal proses untuk mencadangkan kapasitas
heavyweight yang terbatas sebelum mempertahankan dan mengurai isi permintaan yang besar. Lease
heavyweight tetap dipertahankan selama masa aktif respons SSE.

**Fan-out #503:** sebelum perbaikan ini, guard membatasi konkurensi pada JUMLAH permintaan tetap
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default `1`) tanpa mempertimbangkan memori host, sehingga
fan-out agen pengodean (beberapa subagen/CLI, dengan isi yang secara rutin > 256 KB) turun menjadi
konkurensi efektif sekitar 1 dan menghasilkan 503 dalam beban yang sepenuhnya normal. Kini guard
menyesuaikan diri secara otomatis: guard dikendalikan oleh anggaran BYTE penyerapan yang diturunkan
secara otomatis (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dan ditentukan berdasarkan batas memori nyata
proses, serta memeriksa sinyal tekanan sumber daya langsung — sehingga guard hanya mengurangi beban
ketika host benar-benar mengalami tekanan memori, bukan sekadar karena lebih dari satu permintaan
berat tiba secara bersamaan. Batas jumlah lama (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) masih
dipatuhi, tetapi hanya jika Anda menetapkannya secara eksplisit.

Saat kapasitas sibuk, permintaan heavyweight terlebih dahulu menunggu hingga
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default-nya `RATE_LIMIT_MAX_WAIT_MS`; `0` menonaktifkan waktu tunggu) agar slot tersedia
sebelum memberikan respons `503` yang dapat dicoba ulang. Waktu tunggu terbatas ini tersedia agar
klien bergaya agen (OpenCode, Claude Code, Cursor) yang melakukan fan-out subpermintaan berat secara
bersamaan dapat menserialkan lonjakan tersebut, alih-alih menghabiskan seluruh anggaran percobaan
ulangnya pada penolakan langsung dan gagal di tengah tugas. Okupansi lease heavyweight saat ini,
anggaran byte yang telah ditentukan, dan tingkat keparahan tekanan langsung ditampilkan di
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — periksa nilai-nilai ini sebelum mengubah
variabel lingkungan apa pun. Pengaturan → Ketahanan → Antrean Permintaan → Permintaan Bersamaan
tidak mengendalikan hal ini; pengaturan tersebut mengatur mekanisme antrean permintaan penyedia
yang terpisah.

**Perbaikan:**

1. Coba ulang terlebih dahulu. Klien harus mematuhi `Retry-After` dan menggunakan backoff, alih-alih
   langsung mengulangi permintaan.
2. Periksa `/api/monitoring/health` → `chatAdmission` sebelum menyetel apa pun. `countCapEnabled:
false` dan `maxInflightBytes` yang besar berarti anggaran yang diturunkan secara otomatis sudah
   berfungsi sebagaimana mestinya; `pressureSeverity` sebesar `high`/`critical` berarti host
   benar-benar kekurangan memori — hal itu tidak dapat diperbaiki dengan variabel lingkungan
   admission, tetapi memerlukan lebih banyak RAM atau beban kerja yang lebih kecil.
3. Hanya jika `/api/monitoring/health` menunjukkan bahwa anggaran yang diturunkan secara otomatis
   benar-benar terlalu kecil untuk host Anda (jarang terjadi — anggaran tersebut sudah diskalakan
   dari container hingga bare-metal), timpa secara langsung dengan
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, alih-alih kembali menggunakan batas jumlah permintaan lama.

Lihat [referensi variabel lingkungan](../reference/ENVIRONMENT.md#4-security--authentication)
untuk pengaturan admission yang bersifat otoritatif.

## Taksonomi kegagalan RAG / LLM opsional (16 masalah)

Sebagian pengguna OmniRoute menempatkan gateway di depan tumpukan RAG atau agen. Dalam konfigurasi tersebut, pola yang aneh sering terlihat: OmniRoute tampak sehat (penyedia aktif, profil perutean baik, tidak ada peringatan batas laju), tetapi jawaban akhirnya tetap salah.

Dalam praktiknya, insiden ini biasanya berasal dari pipeline RAG hilir, bukan dari gateway itu sendiri.

Jika Anda menginginkan kosakata bersama untuk menjelaskan kegagalan tersebut, Anda dapat menggunakan WFGY ProblemMap, sebuah sumber teks eksternal berlisensi MIT yang mendefinisikan enam belas pola kegagalan RAG / LLM yang berulang. Secara umum, sumber tersebut mencakup:

- penyimpangan pengambilan dan batas konteks yang rusak
- indeks dan penyimpanan vektor yang kosong atau kedaluwarsa
- ketidakcocokan embedding dengan semantik
- masalah penyusunan prompt dan jendela konteks
- keruntuhan logika dan jawaban yang terlalu percaya diri
- kegagalan rantai panjang dan koordinasi agen
- penyimpangan memori dan peran multiagen
- masalah urutan deployment dan bootstrap

Gagasannya sederhana:

1. Saat menyelidiki respons yang buruk, catat:
   - tugas dan permintaan pengguna
   - rute atau kombinasi penyedia di OmniRoute
   - konteks RAG apa pun yang digunakan di hilir (dokumen yang diambil, pemanggilan alat, dan sebagainya)
2. Petakan insiden ke satu atau dua nomor WFGY ProblemMap (`No.1` … `No.16`).
3. Simpan nomor tersebut di dashboard, runbook, atau pelacak insiden Anda sendiri di samping log OmniRoute.
4. Gunakan halaman WFGY yang sesuai untuk menentukan apakah Anda perlu mengubah tumpukan RAG, retriever, atau strategi perutean Anda.

Teks lengkap dan resep konkret tersedia di sini (lisensi MIT, hanya teks):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Anda dapat mengabaikan bagian ini jika Anda tidak menjalankan pipeline RAG atau agen di belakang OmniRoute.

## Masalah Umum v3.8.0

Masalah yang spesifik untuk rilis v3.8.0 dan solusi sementara yang tersedia saat ini. Jika perbaikan tersedia dalam patch berikutnya, entri ini akan diperbarui atau dihapus.

### Kegagalan autentikasi Devin CLI

**Gejala:**

- "Devin CLI tidak ditemukan" atau "autentikasi gagal" saat memanggil alat yang didukung Devin
- Pemeriksaan runtime CLI melaporkan `installed=false`

**Penyebab:**

- `CLI_DEVIN_BIN` menunjuk ke path yang tidak ada
- Devin CLI tidak terinstal pada host

**Perbaikan:**

1. Instal Devin CLI untuk platform Anda
2. Atur `CLI_DEVIN_BIN=/usr/local/bin/devin` (atau path yang sebenarnya) di `.env`
3. Mulai ulang OmniRoute dan uji kembali dari **Dashboard → Alat CLI**

### Cooldown model macet (reset manual)

**Gejala:**

- Sebuah model tetap tercantum dalam cooldown bahkan setelah waktu kedaluwarsanya berlalu
- Permintaan masih melewati model tersebut dalam perutean kombinasi meskipun timestamp-nya sudah berlalu

**Reset manual:**

- **Dashboard:** **Pengaturan → Cooldown Model** → klik **Aktifkan kembali** pada kartu yang terdampak
- **API:** `DELETE /api/resilience/model-cooldowns` dengan header autentikasi manajemen

### Koneksi penyedia Command Code gagal dengan 403

**Gejala:**

- 403 saat menguji koneksi penyedia Command Code
- Kartu penyedia menampilkan "tidak diotorisasi" setelah baru ditambahkan

**Penyebab:** Alur OAuth tidak selesai (callback tidak diterima atau token tidak disimpan).

**Perbaikan:**

- Jalankan `omniroute providers` dari CLI untuk memicu ulang alur OAuth, atau
- Jalankan ulang OAuth dari **Dashboard → Penyedia → Command Code → Hubungkan kembali**

### ModelScope mengembalikan cooldown 429 yang agresif

**Gejala:**

- Cooldown yang sangat singkat atau langsung diterapkan pada ModelScope setelah sejumlah kecil permintaan dalam waktu singkat
- Perutean kombinasi melewati ModelScope lebih awal dari yang diperkirakan

**Penyebab:** ModelScope mengirimkan header `Retry-After` khusus penyedia. v3.8.0 menyertakan penanganan khusus untuk header tersebut, sehingga versi yang lebih lama salah membacanya sebagai petunjuk batas laju generik.

**Perbaikan:**

- Pastikan Anda menggunakan v3.8.0 atau versi yang lebih baru
- Pastikan pengalih `useUpstream429BreakerHints` diaktifkan di **Pengaturan → Ketahanan**

### OMNIROUTE_WS_BRIDGE_SECRET tidak tersedia dalam produksi

**Gejala:**

- 401 pada setiap permintaan bridge WebSocket Codex/Responses saat dijalankan pada host produksi jarak jauh
- Handshake bridge WebSocket langsung ditutup setelah terhubung

**Penyebab:** Variabel lingkungan `OMNIROUTE_WS_BRIDGE_SECRET` tidak tersedia di lingkungan produksi.

**Perbaikan:**

1. Buat secret acak: `openssl rand -hex 32`
2. Atur `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` di lingkungan server produksi (dan setiap klien yang berkomunikasi dengan bridge)
3. Mulai ulang OmniRoute

### Responses API: mode latar belakang diturunkan menjadi sinkron

**Gejala:**

- Peringatan dicatat: `background mode degraded to synchronous`
- Permintaan `background: true` mengembalikan respons sinkron normal, bukan handle tugas latar belakang

**Penyebab:** v3.8.0 secara sengaja menurunkan `background: true` pada Responses API menjadi eksekusi sinkron sambil mengeluarkan peringatan. Eksekusi latar belakang asinkron penuh merupakan fitur yang akan tersedia mendatang.

**Perbaikan:**

- Sesuaikan klien agar melakukan pemanggilan tanpa `background`, atau
- Tunggu rilis berikutnya yang menyediakan mode latar belakang asinkron penuh (pantau changelog)

## Startup Lambat / Timeout Kesiapan

Jika CLI menampilkan `⚠ Server did not respond within 60s`, tetapi server
sebenarnya berfungsi, batas waktu pemeriksaan kesiapan terlalu singkat untuk lingkungan Anda.

Hal ini umumnya terjadi di Windows (antivirus, pemantau filesystem) atau container
dengan beban kerja startup yang berat.

**Perbaikan — tingkatkan batas waktu:**

```bash
# Melalui variabel lingkungan (berlaku untuk setiap kali startup):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 menit
omniroute serve

# Melalui flag CLI (sekali pakai):
omniroute serve --ready-timeout 180000
```

Nilai default adalah 60.000 milidetik (60 detik). Peringatan ini hanya bersifat informatif; server
akan terus memulai di latar belakang dan dapat diakses setelah proses boot selesai.

Lihat [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) untuk detail
lengkap tentang `OMNIROUTE_READY_TIMEOUT_MS`.
