## Referensi Cepat

**Baru menggunakan OmniRoute?** Mulai dari sini — solusi berikut mengatasi 90% masalah:

| Yang Anda lihat                 | Artinya                                   | Yang harus dilakukan                                                                             |
| ------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------ |
| "Tidak dapat terhubung"         | OmniRoute tidak berjalan                  | Jalankan `omniroute` atau `docker restart omniroute`                                             |
| "Kunci API tidak valid"         | Kunci Anda salah atau sudah kedaluwarsa   | Salin ulang kunci dari situs web penyedia                                                        |
| "Batas laju terlampaui"         | Anda mengirim terlalu banyak permintaan   | Tunggu 1 menit, atau gunakan `model: "auto"` untuk fallback otomatis                             |
| "Kuota terlampaui"              | Kuota gratis/berbayar Anda telah habis    | Hubungkan lebih banyak penyedia, atau gunakan penyedia gratis (Kiro, Pollinations)               |
| "Respons lambat"                | Penyedia sedang sibuk atau lokasinya jauh | Gunakan `model: "auto/fast"` atau hubungkan penyedia yang lebih cepat (Groq, Cerebras)           |
| "Penyedia yang digunakan salah" | `auto` memilih penyedia lain              | Itu normal! `auto` memilih yang terbaik. Paksa penyedia tertentu dengan `model: "openai/gpt-4o"` |

| "401 Unauthorized"              | Kredensial Anda salah                     | Periksa kunci API Anda atau lakukan autentikasi ulang dengan OAuth                               |
| "429 Too Many Requests"         | Terkena pembatasan laju                   | Tunggu 1 menit, atau hubungkan lebih banyak penyedia                                             |

### Pembatasan Laju pada Penyedia Gratis (429 / 400 / 401)

**Gejala**: Saat menggunakan `model: "auto"` dengan penyedia gratis/tanpa autentikasi (opencode, auggie, dan lainnya), Anda sesekali mendapatkan `HTTP 429`, `400`, atau `401`, bukan jawaban. Permintaan berhasil saat prompt yang sama dicoba lagi beberapa saat kemudian, tetapi otomatisasi (tugas cron, agen, skrip) gagal pada kegagalan pertama.

**Penyebab utama**: Tiga mode kegagalan independen terjadi secara bersamaan:

1. **Batas laju penyedia (`429`)**: Tingkat layanan gratis dapat memberlakukan kuota per jendela waktu. Lonjakan panggilan paralel menghabiskan kuota tersebut, sehingga permintaan berikutnya ditolak hingga jendela diatur ulang.
2. **Model rusak dalam passthrough (`400`/`401`)**: Pool `auto/*` dapat menyertakan model passthrough dari `opencode` yang terdaftar dalam katalog tetapi tidak memiliki kredensial aktif (misalnya `oc/north-mini-code-free` → `401`). Auto-router mencoba salah satunya, gagal, dan galat diteruskan sebelum fallback sempat dijalankan.
3. **Amplifikasi konkurensi (`429` saat beban tinggi)**: Saat beberapa sesi agen/cron mengakses `auto` secara bersamaan, laju permintaan gabungan melampaui batas yang dapat ditoleransi penyedia gratis, sehingga panggilan yang sah ditandai sebagai penyalahgunaan.

**Perbaikan terverifikasi (dilaporkan komunitas, 2026-08-10)**: sesuaikan tiga variabel lingkungan agar rotasi, konkurensi, dan fallback menyerap gejolak tingkat layanan gratis alih-alih gagal karenanya:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # beralih ke model/penyedia lain saat terjadi 400/401 (melewati model passthrough yang rusak)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # batas penerimaan eksplisit untuk beban berat (secara default tidak ditetapkan: tanpa batas jumlah permintaan, lihat catatan di bawah)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # waktu tunggu terbatas yang lebih lama untuk kapasitas beban berat, bukan 503 langsung yang dapat dicoba ulang
```

Tetapkan variabel tersebut di lingkungan proses OmniRoute (daemon, misalnya melalui plist LaunchAgent atau `systemctl edit`), lalu mulai ulang OmniRoute. Flag rotasi adalah pengungkit tunggal dengan dampak terbesar: flag ini mengubah kegagalan total menjadi percobaan ulang transparan terhadap penyedia yang sehat dalam pool.

**Catatan**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` membatasi jumlah permintaan beban berat — berkonteks panjang — yang berjalan sekaligus; batas tersebut merupakan gerbang penerimaan, bukan pembatas laju penyedia. **Pembaruan #503-fanout:** variabel ini tidak lagi ditetapkan secara default (sekarang hanya berlaku jika dikonfigurasi secara eksplisit, seperti di atas) — penerimaan beban berat kini dibatasi oleh anggaran byte yang diturunkan secara otomatis (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) dan menyesuaikan diri berdasarkan batas memori aktual host, sehingga deployment baru seharusnya mengalami jauh lebih sedikit penolakan `503 chat_admission_busy` tanpa perlu menetapkan variabel ini sama sekali; menetapkannya secara eksplisit di sini tetap berfungsi persis seperti yang didokumentasikan. Penimpaan anggaran byte eksplisit dibatasi ke rentang 8 MiB–2 GiB. `413 body_exceeds_budget` bukanlah kondisi sementara: tingkatkan anggaran byte tersebut, turunkan `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, atau tingkatkan batas memori proses. Pelepasan `inflight_bytes_budget` merupakan perebutan sumber daya sementara dan tetap dapat dicoba ulang. Pembatasan laju per penyedia (`open-sse/services/rateLimitManager.ts`) diatur secara terpisah oleh `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, dan `RATE_LIMIT_AUTO_ENABLE` — lihat `.env.example`.

**Cara memverifikasi bahwa perbaikan berhasil**: jalankan agen/cron Anda dua kali secara berurutan dalam waktu singkat dan pastikan keduanya berhasil. Sebelum perbaikan, proses kedua biasanya menghasilkan `429`/`401`. Setelah perbaikan, kegagalan (jika ada) dicoba ulang secara transparan dan panggilan selesai. Anda juga dapat menjalankan `curl /monitoring/health` serta mengamati bidang `rateLimitedUntil` pada koneksi penyedia dan `circuitBreakers.providerBreakers[].state` untuk penyedia yang terdampak — statusnya adalah salah satu dari `CLOSED`, `DEGRADED`, `OPEN`, atau `HALF_OPEN` (lihat `src/shared/utils/circuitBreaker.ts`), dan penyedia yang terus mengalami kegagalan akan beralih dari `CLOSED → DEGRADED → OPEN` sebelum jendela pengaturan ulang mengizinkan probe melewatinya (`HALF_OPEN`).

**Jika Anda masih melihat 429**: akun aktif untuk penyedia tersebut benar-benar telah menghabiskan _kuota_-nya (bukan sekadar batas laju). Tambahkan akun kedua untuk penyedia yang sama di dasbor OmniRoute → Providers → Accounts, atau gunakan juga penyedia gratis lain (misalnya `routeway`, `auggie`). Rotasi hanya membantu untuk kesalahan laju/400/401 yang bersifat sementara; kuota yang benar-benar habis memerlukan kredensial kedua atau penyedia lain.

**Jika Anda melihat 403 pada model visi (`auto/vision`, `bazaarlink/*`)**: akun yang terhubung tidak memiliki paket berbayar yang mencakup visi, atau kunci API memiliki izin yang tidak memadai. Pastikan di dasbor penyedia bahwa cakupan kunci mencakup visi/multimodal, atau hubungkan akun paket berbayar dan tetap gunakan akun tersebut sebagai target visi.

## Peringatan npm install (ERESOLVE / peer / deprecated)

Saat menjalankan `npm install -g omniroute`, Anda mungkin melihat banyak peringatan seperti `npm warn ERESOLVE`, pemberitahuan dependensi peer, dan pesan `deprecated`. **Hal ini wajar dan tidak berbahaya.** Instalasi berhasil jika Anda melihat `added <N> packages` dalam output.

Untuk menyembunyikan peringatan resolusi dependensi peer, gunakan format instalasi yang didukung OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` hanya menyembunyikan `ERESOLVE` dan pemberitahuan dependensi peer. Pemberitahuan penghentian dukungan tetap terlihat karena berasal dari paket pihak ketiga transitif; pemberitahuan tersebut tidak menunjukkan bahwa instalasi gagal.

Peringatan tersebut berasal dari rentang dependensi peer usang dalam paket pihak ketiga yang tidak dikendalikan OmniRoute:

1. **`marked-terminal` memerlukan `marked >=1 <16`, tetapi menemukan `marked@18`** — dalam praktiknya tetap berfungsi dengan baik; rentang peer upstream tersebut hanya sudah usang.
2. **`deprecated prebuild-install@7.1.3`** — pembantu pengambilan biner native transitif. Paket ini tidak
   digunakan untuk menginstal binding transport `wreq-js` yang versinya dikunci dan tidak menunjukkan bahwa penyiapan transport
   penyedia web-cookie gagal.

**Tidak diperlukan tindakan apa pun** — peringatan tersebut tidak dapat disembunyikan sepenuhnya tanpa melakukan fork pada paket upstream.

| Masalah                                                    | Solusi                                                                                                                                                                       |

## Positif Palsu Antivirus

<a name="antivirus-false-positives"></a>

### Avast/AVG mengarantina `README.md` dengan `MD:HttpRequest-inf[Susp]`

**Ini adalah positif palsu. Tidak ada yang terinfeksi dan tidak diperlukan tindakan apa pun.**

Avast dan AVG menjalankan heuristik yang menandai file teks biasa/Markdown yang berisi banyak
tautan yang menyerupai permintaan HTTP. `README.md` OmniRoute disertakan di dalam paket npm (file ini
tercantum di `package.json` → `files`), sehingga berada di `node_modules/omniroute/README.md` saat
instalasi global — dan berisi sekitar 15 contoh `http://localhost:20128/...` (endpoint HTTP/SSE
MCP, URL `.well-known` A2A, dan cuplikan `curl`). Kepadatan tautan tersebut cukup untuk
memicu heuristik.

Jika hal ini baru mulai terjadi belakangan ini: jenis file tersebut tidak berubah. README memperluas
tabel endpoint-nya (HTTP MCP + SSE + A2A ditambahkan) dan menambahkan lebih banyak contoh `curl`, yang membuatnya
melewati ambang batas.

File tersebut merupakan dokumentasi pasif tanpa konten yang dapat dieksekusi. Anda dapat memulihkannya
dari karantina dengan aman.

**Yang harus dilakukan:**

1. **Hentikan notifikasi** — kecualikan direktori instalasi di antivirus Anda
   (Avast: Settings → Exceptions), dengan menambahkan jalur `node_modules` global dan/atau
   direktori data OmniRoute (`~/.omniroute/`).
2. **Laporkan positif palsu** — <https://www.avast.com/false-positive-file-form.php>,
   dengan melampirkan `README.md` yang dikarantina. Ini adalah perbaikan yang membantu semua orang karena
   heuristik vendor bereaksi secara berlebihan terhadap file teks.

**Mengapa kami tidak "memperbaiki" hal ini dari sisi kami:** semua contoh menggunakan `http://localhost`, dan
localhost tidak dapat menggunakan `https` tanpa kerumitan sertifikat yang ditandatangani sendiri. Mengubah dokumentasi
secara tidak semestinya demi menghindari heuristik satu vendor akan merugikan setiap pembaca hanya untuk mengakomodasi bug pemindai.

### Kaspersky menandai aplikasi Desktop sebagai `PDM:Trojan.Win32.Generic`

**Ini adalah positif palsu dari heuristik perilaku. Tidak ada yang terinfeksi.** Awalan
`PDM:` Kaspersky berarti keputusan tersebut berasal dari Proactive Defense Module (System Watcher),
yang menilai apa yang _dilakukan_ penginstal alih-alih mencocokkannya dengan malware yang dikenal. Ketika
terpicu, Kaspersky "mengembalikan" seluruh instalasi — menghapus file yang telah
ditulis — sehingga aplikasi akhirnya rusak atau hilang.

File yang ditandai adalah bagian standar dari dependensi sumber terbuka yang dideklarasikan dan dibundel dengan
aplikasi desktop, misalnya:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` dan
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), pustaka otomatisasi browser
  yang digunakan untuk login penyedia di dalam aplikasi dan obrolan berbasis browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — binding native `wreq-js` yang versinya dikunci, yang digunakan untuk HTTP dengan sidik jari browser pada penyedia
  berbasis cookie web (`<arch>` adalah `x64` atau `arm64`).

**Mengapa ini terpicu:** penginstal Windows **belum ditandatangani secara digital**, sehingga penginstal NSIS
yang tidak ditandatangani tidak memiliki reputasi dan heuristik perilaku berjalan dengan tingkat agresivitas maksimum. Jika digabungkan
dengan DLL native yang dibundel dan ratusan file `.js` yang ditulis di bawah
`%LOCALAPPDATA%\Programs\OmniRoute` (termasuk direktori paket dengan akhiran hash dari build
mandiri Next.js), hal tersebut cukup untuk memicu heuristik. Penandatanganan kode telah direncanakan;
hingga diterapkan, rilis baru dapat kembali mengalami hal ini.

**Yang harus dilakukan:**

1. **Verifikasi unduhan Anda terlebih dahulu** (untuk memastikan file tidak dimodifikasi). Setiap rilis menerbitkan
   `latest.yml`, dengan bidang `sha512` (base64) yang mencakup penginstal
   `OmniRoute.Setup.<version>.exe`. Di PowerShell, dari folder yang berisi penginstal:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Output harus cocok dengan `latest.yml` → `sha512`. Jika tidak cocok, hapus file tersebut dan
   unduh kembali hanya dari [halaman rilis GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Pulihkan + kecualikan** — pulihkan item yang dikembalikan dari karantina dan tambahkan pengecualian
   untuk `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   lalu instal ulang.
3. **Laporkan positif palsu** — <https://opentip.kaspersky.com/>. Laporan positif palsu
   yang dikirimkan pengguna benar-benar mempercepat proses penambahan ke daftar yang diizinkan.

## Kompatibilitas Node.js

<a name="nodejs-compatibility"></a>

### Halaman login mengalami crash atau menampilkan kesalahan "Module self-registration"

**Penyebab:** Anda menjalankan versi Node.js di luar batas minimum runtime aman yang disetujui OmniRoute. Kasus yang paling umum adalah penggunaan tingkat patch Node 22 atau 24 lama yang berada di bawah batas keamanan dengan patch yang diwajibkan OmniRoute.

**Gejala:**

- Halaman login menampilkan layar kosong atau kesalahan server
- Konsol menampilkan `Error: Module did not self-register` atau kesalahan binding native serupa
- Halaman login menampilkan **banner peringatan berwarna oranye** beserta versi Node Anda jika runtime berada di luar kebijakan aman yang didukung

**Perbaikan:**

1. Instal rilis LTS Node.js yang didukung (disarankan: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verifikasi versi Anda: `node --version` harus menampilkan `v24.0.0` atau yang lebih baru pada lini LTS 24.x
3. Instal ulang OmniRoute: `npm install -g omniroute`
4. Mulai ulang: `omniroute`

> **Versi aman yang didukung:** `>=22.22.2 <23` atau `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) dan Node.js 26 didukung sepenuhnya.

### npm v11+: `better-sqlite3` tidak terinstal (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Penyebab:** npm v11 (disertakan dengan Node.js 24+) secara default memblokir skrip instalasi untuk dependensi
opsional. Karena `better-sqlite3` tercantum dalam `optionalDependencies`
dan memerlukan kompilasi native (`node-gyp rebuild`), npm melewatinya tanpa pemberitahuan.

**Gejala:**

- Server mengalami crash saat dimulai dengan pesan `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` menampilkan "No such file or directory"
- `npm ls better-sqlite3` menampilkan `(empty)`

**Perbaikan:**

1. Setujui skrip instalasi dan instal ulang:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Atau instal versi bawaan yang telah dikompilasi secara manual:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verifikasi bahwa instalasi berfungsi: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Penyebab:** Setelah menjalankan `npm install -g omniroute` secara global, biner native `better-sqlite3` di dalam paket mungkin telah dikompilasi untuk arsitektur atau ABI Node.js yang berbeda dari yang dijalankan secara lokal. Hal ini umum terjadi pada macOS (baik Apple Silicon maupun Intel) ketika biner yang telah dikompilasi sebelumnya tidak cocok dengan lingkungan Anda.

**Gejala:**

- Server langsung gagal saat dimulai dengan kesalahan `dlopen`
- Pesan kesalahan berisi `slice is not valid mach-o file`
- Contoh lengkap:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Perbaikan — kompilasi ulang untuk lingkungan lokal Anda (tidak perlu menurunkan versi Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Catatan:** Langkah ini mengompilasi ulang binding native berdasarkan versi Node.js dan arsitektur CPU lokal Anda, sehingga mengatasi ketidakcocokan biner. Rentang runtime yang didukung secara resmi adalah **`>=22.22.2 <23` atau `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` dalam `src/shared/utils/nodeRuntimeSupport.ts`, selaras dengan bidang `engines` dalam `package.json`). Node.js 24.x LTS (Krypton) dan Node.js 26 didukung sepenuhnya dengan `better-sqlite3` v12.x.

## Masalah Proxy

<a name="proxy-issues"></a>

### Validasi provider menampilkan "fetch failed"

**Penyebab:** Endpoint validasi kunci API (`POST /api/providers/validate`) sebelumnya melewati konfigurasi proxy, sehingga menyebabkan kegagalan di lingkungan yang mengharuskan perutean melalui proxy.

**Perbaikan (v3.5.5+):** Masalah ini sekarang telah diperbaiki. Validasi provider dirutekan melalui `runWithProxyContext`, dengan otomatis mematuhi pengaturan proxy tingkat provider dan global.

### Pemeriksaan kesehatan token gagal dengan "fetch failed"

**Penyebab:** Penyegaran token OAuth di latar belakang tidak menyelesaikan konfigurasi proxy untuk setiap koneksi.

**Perbaikan (v3.5.5+):** Penjadwal pemeriksaan kesehatan token kini menyelesaikan konfigurasi proxy untuk setiap koneksi sebelum mencoba penyegaran. Perbarui ke v3.5.5+.

### Proxy SOCKS5 menampilkan "invalid onRequestStart method"

**Penyebab:** Pada Node.js 22, dispatcher undici@8 tidak kompatibel dengan implementasi `fetch()` bawaan Node.

**Perbaikan (v3.5.5+):** OmniRoute kini menggunakan fungsi `fetch()` milik undici saat dispatcher proxy aktif, sehingga memastikan perilaku yang konsisten. Perbarui ke v3.5.5+.

### Proxy MITM di WSL: aplikasi desktop pada host Windows tidak dicegat

**Penyebab:** Proxy MITM dan sertifikat CA-nya dipasang di lingkungan tempat OmniRoute berjalan. Pada WSL, lingkungan tersebut adalah guest Linux, sedangkan aplikasi desktop AI (Kiro, Trae, Copilot, Zed, …) berjalan pada host Windows. Aplikasi host tidak memercayai penyimpanan sertifikat milik guest dan tidak merutekan lalu lintas melalui proxy sistem guest, sehingga pencegatan desktop tidak aktif di sana.

**Rekomendasi:** Jalankan OmniRoute secara native pada OS yang sama dengan aplikasi desktop yang ingin Anda cegat (Windows untuk aplikasi Windows; demikian pula untuk macOS/Linux). Menjalankan OmniRoute di dalam WSL sambil menargetkan aplikasi host mengharuskan Anda memercayai sertifikat CA yang dihasilkan secara manual pada host Windows dan mengarahkan pengaturan jaringan/proxy setiap aplikasi host ke endpoint proxy WSL — konfigurasi yang tidak didukung dan rentan bermasalah.

**Perbaikan:**

2. Gunakan kombinasi dengan tingkat fallback

OmniRoute menyegarkan token secara otomatis. Jika masalah berlanjut:

1. Dashboard → Provider → Hubungkan Kembali
2. Hapus lalu tambahkan kembali koneksi provider

### Multi-akun Kiro: akun kedua membuat akun pertama tidak valid

**Penyebab:** Backend Kiro memberlakukan satu sesi aktif untuk setiap pendaftaran klien OIDC.
Ketika dua akun menggunakan klien terdaftar yang sama (koneksi yang diimpor sebelum v3.8.0),
penyegaran token salah satu akun membuat token penyegaran akun lainnya tidak valid.

**Perbaikan (v3.8.0+):** Impor ulang koneksi yang terdampak.
Mulai v3.8.0, setiap koneksi Kiro baru yang dibuat melalui **Impor Token**,
**login sosial Google/GitHub**, atau **Impor Otomatis** secara otomatis mendaftarkan klien
OIDC khususnya sendiri. Dengan demikian, koneksi tersebut sepenuhnya terisolasi dan penyegaran
satu akun tidak berdampak pada akun lainnya.

Koneksi yang diimpor _sebelum_ v3.8.0 tidak memiliki pendaftaran klien per koneksi.
Koneksi tersebut tetap menggunakan endpoint penyegaran autentikasi sosial bersama.
Untuk mendapatkan isolasi, hapus koneksi lama dari Dashboard → Provider dan tambahkan kembali
melalui salah satu dari tiga alur impor.

Untuk detail lengkap dan petunjuk langkah demi langkah guna menambahkan dua akun Kiro secara berdampingan,
lihat [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Masalah Cloud

### Kesalahan Sinkronisasi Cloud

1. Pastikan `BASE_URL` mengarah ke instans yang sedang berjalan (misalnya, `http://localhost:20128`)
2. Pastikan `CLOUD_URL` mengarah ke endpoint cloud Anda (misalnya, `https://omniroute.dev`)

**Penyebab:** Upstream mengembalikan payload SSE sementara klien mengharapkan JSON.

2. Jalankan sinkronisasi cloud: Aktifkan Cloud → Sinkronkan Sekarang
3. Kunci lama/belum disinkronkan masih dapat menghasilkan `401` di cloud

## Masalah Docker

### IPv6 Docker / Pengaturan Ulang Koneksi

<a name="docker-ipv6"></a>

**Gejala:** `curl http://localhost:20128/v1/models` menghasilkan `curl: (56) Recv failure: Connection reset by peer`. Dasbor dan endpoint tanpa autentikasi berfungsi, tetapi endpoint yang memerlukan autentikasi gagal — ini tampak seperti masalah autentikasi, padahal bukan.

**Penyebab:** `docker run -p 20128:20128` memublikasikan pada `0.0.0.0` (IPv4) dan `::` (IPv6), tetapi proses di dalam kontainer hanya mendengarkan pada IPv4. Pada host tempat `localhost` di-resolve ke `::1` terlebih dahulu, koneksi masuk ke port IPv6 yang dipublikasikan tanpa listener di belakangnya → koneksi diatur ulang.

**Perbaikan:**

1. **Diagnosis cepat:** Jalankan `curl -4 http://localhost:20128/v1/models`. Jika berfungsi dengan `-4` tetapi gagal tanpanya, terdapat ketidakcocokan bind IPv6.
2. **Perbaikan permanen:** Bind ke IPv4 secara eksplisit dengan menggunakan `-p 127.0.0.1:20128:20128` dalam perintah `docker run` Anda:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Tindakan ini memaksa bind IPv4 dan juga mencegah proxy diekspos pada semua antarmuka host.

## Pengaturan Ketahanan

### Pembatasan laju otomatis tidak terpicu

- Pembatasan laju otomatis hanya berlaku untuk penyedia kunci API (bukan OAuth/langganan)
- Pastikan **Settings → Resilience → Provider Profiles** mengaktifkan pembatasan laju otomatis
- Periksa apakah penyedia mengembalikan kode status `429` atau header `Retry-After`

### Menyesuaikan backoff eksponensial

Profil penyedia mendukung pengaturan berikut:

- **Penundaan dasar** — Waktu tunggu awal setelah kegagalan pertama (default: 1s)
- **Penundaan maksimum** — Batas maksimum waktu tunggu (default: 30s)
- **Pengali** — Besarnya peningkatan penundaan untuk setiap kegagalan berturut-turut (default: 2x)

### Pencegahan thundering herd

Ketika banyak permintaan bersamaan mengakses penyedia yang dibatasi lajunya, OmniRoute menggunakan mutex + pembatasan laju otomatis untuk menserialkan permintaan dan mencegah kegagalan berantai. Ini berlangsung secara otomatis untuk penyedia kunci API.

### Permintaan chat gagal dengan 503 / chat_admission_busy

**Gejala:**

- Endpoint penyelesaian chat mengembalikan respons `503` yang dapat dicoba ulang dengan kode kesalahan
  `chat_admission_busy`.
- Respons menyertakan `Retry-After`. Sejak #12135, nilainya diturunkan dari okupansi yang diamati
  — nilai yang lebih besar antara jendela `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` yang telah dijalani
  permintaan dan lamanya lease kelas berat saat ini telah ditahan — dibulatkan ke atas menjadi
  detik penuh dan dibatasi hingga 60. Pada gerbang yang tidak aktif, nilai minimum historis tetap
  dipertahankan: 2 detik pada jalur berbasis byte, 1 detik pada jalur berbasis struktur (yang juga
  menyertakan `reason: "structure_limit"`).
- Hal ini dapat terjadi saat chat kelas berat lain atau respons streaming yang berjalan lama masih
  berlangsung.

Isi respons berbasis byte adalah:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Respons berbasis struktur menggunakan tipe dan kode yang sama, dengan pesan
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
dan `reason: "structure_limit"`.
Pada ambang batas default, permintaan dianggap berat secara struktural jika memiliki setidaknya `200` pesan,
setidaknya `64` alat, atau setidaknya `32,000` token yang diperkirakan, atau ketika estimasi struktur
terbatas mencapai batasnya, yaitu `10,000` node yang dikunjungi atau kedalaman `12`.

**Penyebab:** Ini merupakan pelepasan beban yang disengaja di dalam OmniRoute, bukan kegagalan penyedia upstream.
Setiap proses menggunakan pengaman lokal proses untuk mencadangkan kapasitas kelas berat yang terbatas sebelum
menyimpan dan mengurai isi permintaan yang besar. Lease kelas berat tetap ditahan selama masa aktif respons
SSE.

**#503-fanout:** sebelum perbaikan ini, pengaman membatasi konkurensi pada JUMLAH permintaan tetap
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default `1`) tanpa mempertimbangkan memori host, sehingga fan-out
agen pemrograman (beberapa subagen/CLI, dengan isi yang secara rutin > 256 KB) menurunkan konkurensi
efektif menjadi ~1 dan menghasilkan 503 pada beban yang sepenuhnya normal. Pengaman kini menyesuaikan
diri secara otomatis: pengaman dibatasi oleh anggaran BYTE penyerapan yang diturunkan secara otomatis
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), yang ukurannya ditentukan berdasarkan batas memori aktual proses,
dan juga mempertimbangkan sinyal tekanan sumber daya secara langsung — sehingga pengaman hanya melepaskan
beban ketika host benar-benar mengalami tekanan memori, bukan hanya karena lebih dari satu permintaan
berat tiba secara bersamaan. Batas jumlah lama (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) tetap dipatuhi,
tetapi hanya jika Anda menetapkannya secara eksplisit.

Ketika kapasitas sedang sibuk, permintaan kelas berat terlebih dahulu menunggu hingga
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default `2000`, `0` menonaktifkan waktu tunggu) agar slot tersedia
sebelum mengembalikan `503` yang dapat dicoba ulang. Waktu tunggu terbatas ini tersedia agar klien
bergaya agen (OpenCode, Claude Code, Cursor) yang melakukan fan-out terhadap subpermintaan berat secara
bersamaan dapat menserialkan lonjakan, alih-alih menghabiskan seluruh anggaran percobaan ulang pada
penolakan langsung dan berhenti di tengah tugas.
Okupansi lease kelas berat saat ini, anggaran byte yang telah ditentukan, dan tingkat keparahan tekanan
secara langsung ditampilkan di `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`,
`maxInflightBytes`, `budgetSource`, `pressureSeverity`, `countCapEnabled`) — periksa semua ini sebelum
mengubah variabel lingkungan apa pun.
Settings → Resilience → Request Queue → Concurrent Requests tidak mengendalikan hal ini; pengaturan
tersebut mengatur mekanisme antrean permintaan penyedia yang terpisah.

**Perbaikan:**

1. Coba ulang terlebih dahulu. Klien harus mematuhi `Retry-After` dan menggunakan backoff, bukan langsung
   mengulangi permintaan.
2. Periksa `/api/monitoring/health` → `chatAdmission` sebelum menyesuaikan apa pun. `countCapEnabled:
false` dan `maxInflightBytes` yang besar berarti anggaran yang diturunkan secara otomatis sudah
   berfungsi sebagaimana mestinya; `pressureSeverity` bernilai `high`/`critical` berarti host benar-benar
   kekurangan memori — hal tersebut tidak dapat diperbaiki dengan variabel lingkungan penerimaan,
   melainkan membutuhkan lebih banyak RAM atau beban kerja yang lebih kecil.
3. Hanya jika `/api/monitoring/health` menunjukkan bahwa anggaran yang diturunkan secara otomatis
   benar-benar terlalu kecil untuk host Anda (jarang terjadi — anggaran tersebut sudah diskalakan dari
   container hingga bare-metal), timpa secara langsung dengan `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`
   daripada kembali menggunakan batas jumlah permintaan lama.

Lihat [referensi variabel lingkungan](../reference/ENVIRONMENT.md#4-security--authentication)
untuk pengaturan penerimaan yang resmi.

## Taksonomi kegagalan RAG / LLM opsional (16 masalah)

Sebagian pengguna OmniRoute menempatkan gateway di depan tumpukan RAG atau agen. Dalam konfigurasi tersebut, pola yang aneh sering terlihat: OmniRoute tampak sehat (penyedia aktif, profil perutean berfungsi, tidak ada peringatan batas laju), tetapi jawaban akhirnya tetap salah.

Dalam praktiknya, insiden ini biasanya berasal dari pipeline RAG hilir, bukan dari gateway itu sendiri.

Jika Anda menginginkan kosakata bersama untuk menjelaskan kegagalan tersebut, Anda dapat menggunakan WFGY ProblemMap, sebuah sumber daya teks eksternal berlisensi MIT yang mendefinisikan enam belas pola kegagalan RAG / LLM yang berulang. Secara garis besar, sumber daya ini mencakup:

- penyimpangan pengambilan dan batas konteks yang rusak
- indeks dan penyimpanan vektor yang kosong atau usang
- ketidakcocokan embedding dengan semantik
- masalah penyusunan prompt dan jendela konteks
- keruntuhan logika dan jawaban yang terlalu percaya diri
- kegagalan rantai panjang dan koordinasi agen
- penyimpangan memori dan peran multiagen
- masalah urutan deployment dan bootstrap

Idenya sederhana:

1. Saat menyelidiki respons yang buruk, catat:
   - tugas dan permintaan pengguna
   - kombinasi rute atau penyedia di OmniRoute
   - konteks RAG apa pun yang digunakan di hilir (dokumen yang diambil, pemanggilan alat, dan sebagainya)
2. Petakan insiden ke satu atau dua nomor WFGY ProblemMap (`No.1` … `No.16`).
3. Simpan nomor tersebut di dashboard, runbook, atau pelacak insiden Anda sendiri di samping log OmniRoute.
4. Gunakan halaman WFGY yang sesuai untuk menentukan apakah Anda perlu mengubah tumpukan RAG, retriever, atau strategi perutean.

Teks lengkap dan panduan konkret tersedia di sini (lisensi MIT, hanya teks):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Anda dapat mengabaikan bagian ini jika tidak menjalankan pipeline RAG atau agen di belakang OmniRoute.

## Masalah yang Diketahui pada v3.8.0

Masalah yang khusus untuk rilis v3.8.0 dan solusi sementara yang tersedia saat ini. Jika perbaikan tersedia dalam patch berikutnya, entri tersebut akan diperbarui atau dihapus.

### Kegagalan autentikasi Devin CLI

**Gejala:**

- "Devin CLI tidak ditemukan" atau "autentikasi gagal" saat memanggil alat yang didukung Devin
- Pemeriksaan runtime CLI melaporkan `installed=false`

**Penyebab:**

- `CLI_DEVIN_BIN` mengarah ke path yang tidak ada
- Devin CLI tidak terinstal pada host

**Perbaikan:**

1. Instal Devin CLI untuk platform Anda
2. Tetapkan `CLI_DEVIN_BIN=/usr/local/bin/devin` (atau path yang sebenarnya) di `.env`
3. Mulai ulang OmniRoute dan uji kembali dari **Dashboard → CLI Tools**

### Cooldown model macet (reset manual)

**Gejala:**

- Sebuah model tetap tercantum dalam cooldown bahkan setelah waktu kedaluwarsanya berlalu
- Permintaan masih melewati model tersebut dalam perutean kombinasi meskipun timestamp-nya sudah berlalu

**Reset manual:**

- **Dashboard:** **Settings → Model Cooldowns** → klik **Re-enable** pada kartu yang terdampak
- **API:** `DELETE /api/resilience/model-cooldowns` dengan header autentikasi pengelolaan

### Koneksi penyedia Command Code gagal dengan 403

**Gejala:**

- 403 saat menguji koneksi penyedia Command Code
- Kartu penyedia menampilkan "tidak diotorisasi" setelah baru ditambahkan

**Penyebab:** Alur OAuth tidak selesai (callback tidak diterima atau token tidak disimpan).

**Perbaikan:**

- Jalankan `omniroute providers` dari CLI untuk memicu ulang alur OAuth, atau
- Jalankan ulang OAuth dari **Dashboard → Providers → Command Code → Reconnect**

### ModelScope menghasilkan cooldown 429 yang agresif

**Gejala:**

- Cooldown yang sangat singkat atau langsung aktif pada ModelScope setelah lonjakan kecil permintaan
- Perutean kombinasi melewati ModelScope lebih awal dari yang diperkirakan

**Penyebab:** ModelScope mengirimkan header `Retry-After` khusus penyedia. v3.8.0 menyertakan penanganan khusus untuk header tersebut, sehingga versi yang lebih lama salah membacanya sebagai petunjuk batas laju umum.

**Perbaikan:**

- Pastikan Anda menggunakan v3.8.0 atau versi yang lebih baru
- Pastikan opsi `useUpstream429BreakerHints` diaktifkan di **Settings → Resilience**

### OMNIROUTE_WS_BRIDGE_SECRET tidak ada di lingkungan produksi

**Gejala:**

- 401 pada setiap permintaan bridge WebSocket Codex/Responses saat dijalankan pada host produksi jarak jauh
- Handshake bridge WebSocket langsung ditutup setelah tersambung

**Penyebab:** Variabel lingkungan `OMNIROUTE_WS_BRIDGE_SECRET` tidak ada di lingkungan produksi.

**Perbaikan:**

1. Buat secret acak: `openssl rand -hex 32`
2. Tetapkan `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` di lingkungan server produksi (dan setiap klien yang berkomunikasi dengan bridge)
3. Mulai ulang OmniRoute

### Responses API: mode latar belakang diturunkan menjadi sinkron

**Gejala:**

- Peringatan dicatat: `background mode degraded to synchronous`
- Permintaan `background: true` mengembalikan respons sinkron normal, bukan handle pekerjaan latar belakang

**Penyebab:** v3.8.0 secara sengaja menurunkan `background: true` pada Responses API menjadi eksekusi sinkron sambil mengeluarkan peringatan. Eksekusi latar belakang asinkron penuh akan tersedia pada masa mendatang.

**Perbaikan:**

- Sesuaikan klien agar melakukan pemanggilan tanpa `background`, atau
- Tunggu rilis berikutnya yang menyediakan mode latar belakang asinkron penuh (pantau changelog)

## Startup Lambat / Waktu Tunggu Kesiapan Habis

Jika CLI menampilkan `⚠ Server did not respond within 60s`, tetapi server
sebenarnya berfungsi, batas waktu pemeriksaan kesiapan terlalu singkat untuk lingkungan Anda.

Hal ini umumnya terjadi di Windows (antivirus, pemantau sistem file) atau container
dengan beban kerja startup yang berat.

**Solusi — naikkan batas waktu:**

```bash
# Melalui variabel lingkungan (berlaku untuk setiap startup):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 menit
omniroute serve

# Melalui flag CLI (satu kali):
omniroute serve --ready-timeout 180000
```

Nilai default adalah 60.000 md (60 dtk). Peringatan ini hanya bersifat informatif; server
terus melakukan startup di latar belakang dan akan dapat diakses setelah proses boot selesai.

Lihat [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) untuk detail
lengkap tentang `OMNIROUTE_READY_TIMEOUT_MS`.
