Relay (Vercel, Deno, Cloudflare) mengakhiri koneksi upstream pada backend
serverless sehingga OmniRoute dapat mengirimkan lalu lintas keluar dari wilayah yang stabil sambil menjaga
kunci API penyedia tetap berada di sisi server. Dokumen ini membahas dua mode kegagalan
yang ditemui operator dalam produksi serta jalur pemulihan yang disediakan OmniRoute
untuk masing-masing mode.

## Cara autentikasi relay disimpan

Saat Anda menerapkan relay dari **Settings → Proxy Pool → Deploy Relay**, alur
penerapan menyimpan token autentikasi relay dalam kolom JSON `notes` milik proxy:

- Jika `STORAGE_ENCRYPTION_KEY` ditetapkan, token ditulis sebagai `relayAuthEnc`
  (dienkripsi dengan AES saat disimpan).
- Jika tidak, token ditulis sebagai teks biasa `relayAuth`.

Pada saat permintaan, `extractRelayAuth(notes)` mengembalikan bentuk mana pun yang tersedia,
sehingga relay tetap berfungsi setelah dimulai ulang.

## Mode kegagalan 1 — token tidak dapat didekripsi setelah rotasi kunci

**Gejala:** relay yang sebelumnya berfungsi kini mengembalikan kesalahan upstream `401`/autentikasi
setelah rotasi `STORAGE_ENCRYPTION_KEY` di lingkungan atau pengelola rahasia.
Blob `relayAuthEnc` yang tersimpan tidak lagi dapat didekripsi, sehingga
`extractRelayAuth` mengembalikan string kosong dan relay tidak mengirimkan
autentikasi.

**Pemulihan — perbaiki langsung (tanpa penerapan ulang):**

1. Buka **Settings → Proxy Pool**.
2. Baris relay yang autentikasinya tidak tersedia menampilkan lencana kuning `auth missing` dan tombol
   **Repair**.
3. Klik **Repair**. OmniRoute memanggil
   `POST /api/settings/proxies/[id]/repair-relay`, yang:
   - mendekripsi `relayAuthEnc` dengan kunci **saat ini**,
   - menulis kembali `relayAuth` dalam bentuk teks biasa ke `notes`,
   - mengembalikan `{ repaired: true, mode: "recovered" }`.

Relay kembali melayani tanpa perlu memasukkan ulang kredensial penerapan apa pun.

Cara ini hanya berfungsi jika `STORAGE_ENCRYPTION_KEY` saat ini masih dapat mendekripsi
blob tersebut. Jika Anda merotasi kunci **tanpa** migrasi, blob tersebut tidak dapat
dipulihkan.

## Mode kegagalan 2 — token tidak dapat dipulihkan (kunci lama tidak lagi tersedia)

**Gejala:** Anda mengeklik **Repair** dan mendapatkan
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Pemulihan — terapkan ulang:**

Token yang tersimpan tidak dapat dipulihkan dengan kunci saat ini. Terapkan ulang relay
dari modal yang sama seperti yang Anda gunakan sebelumnya (menu **Deploy Relay** → Vercel / Deno
/ Cloudflare). Alur penerapan menulis token baru (dienkripsi dengan kunci saat ini)
dan lencana `auth missing` pada baris tersebut akan hilang.

Di UI, tombol **Repair** akan membuka modal penerapan ulang ketika token
tidak dapat dipulihkan, sehingga Anda tidak perlu mencarinya secara manual.

## Mode kegagalan 3 — relay dapat dijangkau tetapi tidak sehat

**Gejala:** pengujian proxy (tombol `speed`) menunjukkan bahwa relay aktif, tetapi permintaan
masih sesekali gagal.

Periksa header kesadaran relay yang dikembalikan oleh probe pengujian otomatis OmniRoute
(lihat **Settings → Proxy Pool** dan penghitung `relayTested` / `relayAlive`):

- `x-relay-url` — backend relay yang merespons.
- `x-relay-mode` — `ts` | `bifrost` | `auto` untuk permintaan tersebut.
- `x-relay-attempts` — jumlah lompatan relay yang dicoba sebelum berhasil.
- `x-relay-fallback` — `true` ketika permintaan beralih dari backend pilihan
  ke relay TypeScript.

Tingkat `x-relay-fallback` yang tinggi dengan `relayAlive` yang rendah berarti backend
sidecar tidak sehat dan Anda harus memperbaikinya atau mengganti strategi backend relay
ke `ts` (lihat `RELAY_BACKEND_STRATEGY.md`).

## Referensi API

| Metode | Jalur                                     | Isi                     | Berhasil                                                                                                                                      | Gagal                                                                                             |
| ------ | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` ketika diturunkan ulang; `200 { repaired: false, mode: "noop" }` ketika teks biasa sudah tersedia | `409 { mode: "redeploy" }` tidak dapat dipulihkan; `400` bukan jenis relay; `404` tidak ditemukan |

Rute daftar `GET /api/settings/proxies` menambahkan
`relayInfo: { isRelay, authMissing, repairMode }` yang bebas rahasia ke setiap item agar dasbor
dapat merender opsi perbaikan tanpa pernah mengekspos token.
