`open-sse/config/providerPluginManifest.ts` mendefinisikan kontrak plugin penyedia yang aman untuk JSON. `open-sse/config/providerPluginManifestRegistry.ts` mengikat kontrak tersebut ke registri penyedia saat ini untuk sidecar seperti Bifrost, CLIProxyAPI, atau router Go/Rust di masa mendatang. Registri TypeScript tetap menjadi sumber kebenaran, tetapi sidecar dapat menggunakan manifes tanpa mengimpor kode eksekutor, nilai default OAuth, header, atau status lingkungan proses.

Manifes yang sama tersedia melalui HTTP di
`GET /api/v1/provider-plugin-manifest` untuk sidecar yang berjalan di luar proses.

OmniRoute menginformasikan URL tersebut kepada Bifrost dan CLIProxyAPI melalui header permintaan `X-OmniRoute-Provider-Manifest-Url`. Atur `OMNIROUTE_PROVIDER_MANIFEST_URL` ketika sidecar memerlukan URL publik atau URL jaringan kontainer, bukan origin permintaan lokal.

## Memperbarui Manifes

Endpoint HTTP mengembalikan `Cache-Control: public, max-age=60` dan `ETag` yang kuat. Sidecar sebaiknya menyimpan manifes terakhir yang telah divalidasi dan mengirimkan ETag-nya dalam `If-None-Match` saat memperbarui. Respons `304 Not Modified` tidak memiliki isi; sidecar mempertahankan manifes yang tersimpan dalam cache. Jika tidak ada manifes cache yang telah divalidasi, sidecar harus mengirimkan permintaan tanpa syarat alih-alih menerima `304`.

## Tujuan

Mengalihkan metadata penyedia menuju kontrak plugin agar jalur permintaan utama pada akhirnya dapat dikelola oleh sidecar dengan latensi lebih rendah, sementara OmniRoute mempertahankan rute TypeScript sebagai gerbang kebijakan dan fallback. Manifes ini bersifat aditif: manifes tidak mengubah perutean permintaan dengan sendirinya.

## Kontrak

Manifes berisi:

- ID dan alias penyedia
- format upstream dan nama eksekutor
- jenis autentikasi, header autentikasi, dan prefiks autentikasi opsional
- metadata endpoint statis
- kelayakan sidecar dan alasan eksplisit ketika penyedia harus tetap berada di TS
- metadata model yang aman untuk JSON, seperti panjang konteks, flag visi/penalaran, dan parameter yang tidak didukung
- tag kapabilitas yang mencakup `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, dan `usage-supported`

Manifes sengaja tidak menyertakan:

- rahasia klien OAuth dan nilai rahasia default
- resolusi lingkungan runtime
- header permintaan dan helper kredensial publik
- pembuat URL dinamis
- fungsi eksekutor
- internal kumpulan sesi

## Tag Kapabilitas

`capabilities` adalah array tag terurut yang diperoleh dari entri registri. Integrator sebaiknya memperlakukannya sebagai jawaban yang dapat dibaca mesin untuk pertanyaan "apa yang dapat dilakukan penyedia ini", alih-alih membaca ulang sumber TypeScript.

| Tag                  | Arti                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `apikey`             | Menerima kunci API (`authType` adalah `apikey` atau `optional`).                                |
| `oauth`              | Menggunakan alur OAuth atau sesi.                                                               |
| `responses`          | Menyediakan URL dasar OpenAI Responses API.                                                     |
| `passthrough-models` | Menyajikan model langsung dari upstream, bukan katalog statis.                                  |
| `custom-executor`    | Menjalankan eksekutor non-default sehingga tetap berada di jalur TypeScript.                    |
| `sidecar-candidate`  | Mencerminkan `sidecar.eligible` — aman dipertimbangkan untuk diimpor oleh sidecar.              |
| `usage-fetch`        | Memiliki pengambil data penggunaan atau kuota yang telah dikonfigurasi (`getUsageForProvider`). |
| `usage-supported`    | API penggunaan menerima penyedia ini (`isSupportedUsageConnection`).                            |

`usage-fetch` hanya untuk penemuan. Tag ini melaporkan bahwa OmniRoute mengetahui cara membaca penggunaan untuk penyedia tersebut; tag ini tidak mengaktifkan pengambilan data, mengubah semantik kuota, atau menyiratkan bahwa widget kuota Dashboard diaktifkan untuk penyedia tersebut — widget itu dikendalikan secara terpisah oleh `USAGE_SUPPORTED_PROVIDERS`. Sumber kebenarannya adalah `USAGE_FETCHER_PROVIDERS` di `open-sse/services/usage/fetcherProviders.ts`.

Daftar tersebut menggunakan string yang diterima oleh dispatcher penggunaan sebagai kunci, sehingga mencampurkan ID kanonis dengan alias dan sedikit lebih panjang daripada jumlah penyedia yang diberi tag: entri yang bukan penyedia chat dalam registri manifes (misalnya penyedia pencarian `firecrawl` dan penyedia ACP `amazon-q`) tidak memiliki entri manifes yang dapat diberi tag.

`usage-supported` menunjukkan apakah rute penggunaan server dan Dashboard menerima koneksi untuk penyedia tersebut. Tag ini mencerminkan `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`) dan `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), yang keduanya dikendalikan oleh `USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Tidak seperti `usage-fetch`, tag ini hanya diterbitkan pada ID penyedia — pemeriksaan runtime menjalankan `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` tanpa resolusi alias, sehingga manifes mempertahankan aturan yang sama. Kedua tag tersebut memiliki cakupan berbeda: 3 penyedia hanya memiliki `usage-fetch` (`opencode`, `opencode-zen`, `xai`) dan 1 penyedia hanya memiliki `usage-supported` (`xiaomi-mimo-token-plan`), sehingga keberadaan salah satunya tidak menyiratkan keberadaan yang lain.

## Penggunaan Sidecar

Sidecar harus memperlakukan `sidecar.eligible` sebagai sinyal kandidat yang konservatif, bukan sebagai keputusan perutean tanpa syarat. Target impor pertama sebaiknya berupa penyedia berbasis API key dan endpoint statis yang menggunakan eksekutor default. Penyedia dengan eksekutor web khusus, alur OAuth/sesi, pembuat URL dinamis, atau konfigurasi pool tetap menggunakan jalur fallback TypeScript hingga sidecar mengimplementasikan perilaku yang setara dan telemetri membuktikan paritas.

Tahapan migrasi yang disarankan:

1. Buat dan validasi manifes plugin penyedia dari registri TS.
2. Ajarkan Bifrost atau CLIProxyAPI untuk mengimpor manifes bagi penyedia berbasis API key/endpoint statis.
3. Rutekan penyedia yang memenuhi syarat melalui sidecar di balik `OMNIROUTE_RELAY_BACKEND` sambil tetap mengaktifkan fallback TS.
4. Promosikan penyedia hanya ketika tingkat keberhasilan, latensi p99, perilaku streaming, dan penanganan parameter yang tidak didukung sesuai dengan jalur TS.
5. Tambahkan plugin native sidecar untuk eksekutor khusus, satu keluarga penyedia pada satu waktu.

## Mengapa Tidak Menyematkan Penyedia Secara Langsung di Next

Frontend Next tidak seharusnya menangani eksekusi penyedia. Frontend harus memanggil batas API. Backend kemudian dapat memutuskan apakah akan menggunakan eksekutor TypeScript, Bifrost, CLIProxyAPI, atau sidecar native di masa mendatang. Pendekatan ini menjaga penandatanganan permintaan, pemeriksaan allowlist, kebijakan DB, dan perilaku fallback tetap terpusat sebelum penyerahan apa pun ke sidecar.
