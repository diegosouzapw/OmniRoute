Dekripsi transparan TPROXY adalah **mode penangkapan ke-5** OmniRoute untuk stack MITM
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Mode ini mencegat dan **mendekripsi** lalu lintas HTTPS keluar lokal di Linux
menggunakan TPROXY kernel + perutean berbasis kebijakan — **tanpa** memalsukan `/etc/hosts` dan
**tanpa** mengubah pengaturan proksi sistem pada seluruh OS. Mode ini cocok untuk lingkungan headless
(tidak ada perubahan DNS yang perlu dibersihkan) dan aturan firewall otomatis dihapus saat reboot.

Tidak seperti mode penangkapan lainnya, TPROXY tidak memerlukan penyiapan per host: mode ini secara transparan
mencegat host tujuan **apa pun** pada port target, menghentikan TLS dengan
sertifikat leaf yang diterbitkannya secara langsung untuk setiap hostname SNI, menangkap pertukaran data
yang telah didekripsi, lalu mengenkripsi ulang permintaan ke tujuan asli.

> **Khusus Linux, khusus root, dan harus diaktifkan secara eksplisit.** Mode ini memerlukan Linux, addon native
> yang dibuat dengan toolchain C, dan kapabilitas **CAP_NET_ADMIN** (biasanya root). Aksesnya dibatasi
> melalui API AgentBridge khusus loopback dan dinonaktifkan secara default. CA
> MITM tepercaya yang dapat menandatangani host apa pun merupakan kapabilitas yang sangat kuat — lihat [§6 Keamanan](#6-security).

**Sumber:** `src/mitm/tproxy/`
**Rute API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Tombol dasbor:** Traffic Inspector → toolbar mode penangkapan → **"Dekripsi TPROXY"** ⚠
**Lihat juga:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Apa itu dan kapan menggunakannya

Keempat mode penangkapan lainnya masing-masing memiliki keterbatasan:

| Mode                  | Cara lalu lintas diarahkan                             | Keterbatasan                                         |
| --------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| AgentBridge           | Pemalsuan DNS `/etc/hosts` untuk sekumpulan host tetap | hanya host agen IDE yang terdaftar                   |
| Host Kustom           | Pemalsuan DNS `/etc/hosts` per host                    | satu entri per host; perlu sudo untuk mengedit hosts |
| HTTP_PROXY            | Env `HTTP_PROXY`/`HTTPS_PROXY`                         | hanya aplikasi yang mematuhi variabel env            |
| Proksi seluruh sistem | Pengaturan proksi OS                                   | mengubah status global; perlu dikembalikan           |

Dekripsi transparan TPROXY mengarahkan lalu lintas pada lapisan **kernel**. Mode ini
menandai koneksi TCP keluar lokal baru menuju port target (default `443`) dalam
rantai `mangle OUTPUT`, sebuah `ip rule` mengalihkan paket yang ditandai ke pengiriman lokal,
dan saat masuk kembali, target `TPROXY` pada `mangle PREROUTING` menyerahkannya kepada listener
**IP_TRANSPARENT** — yang kemudian menghentikan TLS dan menangkap plaintext.

Gunakan mode ini saat Anda ingin menangkap dan mendekripsi lalu lintas dari proses yang:

- berkomunikasi dengan host yang tidak didaftarkan oleh AgentBridge, dan
- tidak mematuhi `HTTP_PROXY`, dan
- tidak ingin Anda ganggu dengan perubahan proksi seluruh sistem.

Karena intersepsi terjadi di kernel, proses asal **tidak memerlukan
perubahan konfigurasi** — tetapi proses tersebut harus memercayai CA dinamis yang dipasang
OmniRoute (lihat [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Persyaratan

| Persyaratan      | Detail                                                                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**           | Hanya Linux — **IP_TRANSPARENT** adalah opsi socket yang hanya tersedia di Linux. Loader mengembalikan "unavailable" pada semua platform lainnya.           |
| **Hak akses**    | Kapabilitas **CAP_NET_ADMIN** untuk membuat socket transparan dan menerapkan aturan `iptables`/`ip` — dalam praktiknya, jalankan sebagai root.              |
| **Addon native** | Addon N-API kecil (`src/mitm/tproxy/native/transparent.c`) harus dibangun atau disertakan sebagai prebuild. Lihat [§3](#3-the-native-ip_transparent-addon). |
| **Modul kernel** | `iptables` dengan dukungan pencocokan `TPROXY`, `mangle`, dan `mark` (divalidasi terhadap kernel 6.8.0).                                                    |

**Degradasi secara aman:** jika ada persyaratan yang tidak terpenuhi (bukan Linux, tidak ada toolchain,
addon belum dibangun), loader addon (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
mengembalikan `null` alih-alih melemparkan error. Status mode penangkapan kemudian melaporkan
`available: false`, tombol pengalih dasbor **dinonaktifkan** dengan tooltip
"Pendekripsian TPROXY memerlukan Linux + root + addon native", dan bagian lain dari
OmniRoute tetap berfungsi.

## §3 Addon native IP_TRANSPARENT

Modul `net` Node tidak dapat menjalankan `setsockopt(IP_TRANSPARENT)` _sebelum_ `bind()`, padahal
hal tersebut diperlukan oleh TPROXY (jika tidak, kernel akan membuang paket yang dialihkan). Addon
(`src/mitm/tproxy/native/transparent.c`, dibangun melalui `binding.gyp`) adalah modul N-API kecil
yang mengekspos tiga fungsi, yang digunakan melalui `transparentSocket.ts`:

| Fungsi addon                          | Operasi socket                                                                                      | Digunakan untuk                                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, mengembalikan fd mentah | listener penangkapan transparan (Node mengadopsi fd melalui `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** pada fd yang sudah ada                                                     | anti-loop (menandai socket milik proksi sendiri)                                     |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **sebelum** `connect()` non-blocking, mengembalikan fd                     | penerusan upstream yang dienkripsi ulang (SYN membawa tanda tersebut)                |

Tujuan asli dibaca dari `socket.localAddress`/`localPort` — TPROXY
mempertahankannya, sehingga tidak diperlukan pencarian **SO_ORIGINAL_DST**/NAT.

### Membangun addon

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Saat `npm run build`, `scripts/build/build-tproxy-native.mjs` menjalankan `node-gyp
rebuild`. Proses ini **hanya untuk Linux dan tidak bersifat fatal** — toolchain yang tidak tersedia hanya menyebabkan
  mode penangkapan tidak tersedia.
- `assembleStandalone.mjs` menyalin `build/Release/transparent.node` ke dalam
  bundel standalone; `transparentSocket.ts` menemukannya baik secara relatif terhadap modul maupun
  relatif terhadap cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` dan `prebuilds/` diabaikan oleh git — binari tersebut **dibangun, tidak pernah
  di-commit**.

Loader memeriksa, berdasarkan urutan prioritas:
`native/build/Release/transparent.node`, lalu `native/prebuilds/transparent.node`
(keduanya relatif terhadap modul dan di bawah `<cwd>/src/mitm/tproxy/`).

## §4 CA dinamis per-SNI dan penginstal trust store

> **Pembaruan #6684:** server statis AgentBridge (`src/mitm/server.cjs`) kini
> menggunakan pola arsitektur CA/leaf yang sama ini, bukan satu leaf statis
> yang ditandatangani sendiri. Server tersebut menggunakan instans CA yang **berbeda**
> (`src/mitm/cert/rootCa.ts`, disimpan di `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> dan memasangnya pada slot trust store `omniroute-mitm.crt` yang sudah ada
> (menggantikan leaf tunggal lama di sana — tidak diperlukan pembersihan dual-trust),
> serta tetap sepenuhnya terpisah dari slot `omniroute-tproxy-ca.crt` milik TPROXY
> di bawah ini. Instalasi baru AgentBridge mendapatkan model CA secara otomatis;
> instalasi yang sudah memercayai leaf statis lama akan tetap menggunakannya hingga
> operator memilih untuk beralih melalui `MITM_ROOT_CA_ENABLED=true` (lihat
> `src/mitm/cert/migration.ts`) — CA MITM tepercaya yang dapat menandatangani leaf
> untuk **host mana pun** jauh lebih berkuasa daripada leaf fixed-SAN lama, sehingga
> peralihan ini tidak pernah dilakukan secara diam-diam untuk instalasi yang sudah
> memercayainya.

Secara historis, sertifikat MITM statis AgentBridge hanya berfungsi karena
AgentBridge melakukan spoofing DNS terhadap kumpulan host yang **tetap** (kini
disatukan dengan model di bawah). TPROXY mencegat host **arbitrer**, sehingga
listener-nya harus menyajikan leaf yang valid untuk SNI apa pun yang diminta
klien — persyaratan yang sama kini juga berlaku bagi AgentBridge untuk seluruh
kumpulan `MITM_TOOL_HOSTS` (9 entri alat), bukan hanya 4 host antigravity.

### CA dinamis (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` menjalankan CA lokal (dibangun di atas dependensi `selfsigned`) yang:

- Menghasilkan CA berumur panjang melalui `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  masa berlaku 10 tahun, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA 2048-bit / SHA-256).
- Menerbitkan **satu leaf per nama host SNI sesuai permintaan** melalui `issueLeafCert()`
  (masa berlaku 1 tahun, `subjectAltName` = host SNI) dan menyimpan satu
  `tls.SecureContext` dalam cache untuk setiap nama host.
- Mengekspos `createSNICallback()` untuk server yang melakukan terminasi TLS (lihat [§5](#5-how-decrypt-and-capture-work)).
- Dapat dibuat dengan `existingCa` agar CA tetap stabil saat dimulai ulang
  (sehingga trust store tidak perlu dipasang ulang).

Kunci privat CA **tidak pernah meninggalkan mesin**.

### Penginstal trust store (`src/mitm/tproxy/caTrust.ts`)

Klien yang dicegat harus memercayai CA dinamis, sehingga memulai mode penangkapan
akan memasang sertifikat CA ke trust store OS pada **slot khusus** —
`omniroute-tproxy-ca.crt` (konstanta `TPROXY_CA_CERT_NAME`) — yang tetap terpisah
dari slot sertifikat MITM statis (`omniroute-mitm.crt`) agar keduanya tidak pernah
saling menimpa.

`installTproxyCa(caPem, sudoPassword?)` mendeteksi direktori anchor distro
(dengan urutan: gaya Debian terlebih dahulu) dan menjalankan perintah penyegaran
yang sesuai:

| Direktori anchor                            | Perintah penyegaran      |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Proses instalasi menempatkan sementara PEM ke file sementara, lalu secara
istimewa menjalankan `mkdir -p` pada direktori anchor, menyalin file sementara
ke dalamnya dengan `cp`, dan menjalankan perintah penyegaran. `uninstallTproxyCa()`
hanya menghapus slot khusus tersebut (tanpa menyentuh sertifikat MITM statis)
dan melakukan penyegaran — tidak melakukan apa pun pada sistem selain Linux.

Semua perintah berhak istimewa dijalankan melalui `execFileWithPassword`
(`src/mitm/systemCommands.ts`) — `spawn` dengan **array argumen, tanpa shell,
tanpa interpolasi string** (Aturan Ketat #13). Ketika proses berjalan sebagai
root (misalnya pada VPS), target dijalankan secara langsung dan kata sandi tidak
diperlukan; pada desktop non-root, `sudoPassword` diteruskan melalui `sudo -S`
pada stdin.

> `sudoPassword` milik desktop diberikan dalam body POST untuk mengotorisasi
> instalasi trust store; nilai tersebut sepenuhnya diabaikan ketika proses
> berjalan sebagai root.

## §5 Cara kerja dekripsi dan penangkapan

Pipeline (semuanya berada di bawah `src/mitm/tproxy/`):

```
aplikasi lokal  ──TCP/443──▶  mangle OUTPUT menandai koneksi (fwmark)
                               ip rule → tabel rute lokal → lo
                               mangle PREROUTING TPROXY → listener IP_TRANSPARENT (port 8443)
                                   │  captureMode.ts: membaca tujuan asli dari socket.localAddress
                                   ▼
                               tlsCapture.ts:
                                 1. Mengakhiri TLS KLIEN dengan leaf per-SNI (dynamicCert)
                                 2. http.Server internal mengurai plaintext yang telah didekripsi
                                 3. menangkap → globalTrafficBuffer.push() dengan source: "tproxy"
                                    (sanitizeHeaders + maskSecret diterapkan)
                                 4. meneruskan dengan enkripsi ULANG ke tujuan asli
                                    melalui socket bertanda bypass (connectMarked, anti-loop)
                                   │
                                   ▼
                               upstream asli (api.example.com)
```

- **Terminasi TLS** (`createTlsCaptureServer`): membungkus socket mentah yang
  dicegat dalam `tls.TLSSocket` sisi server menggunakan callback SNI milik CA
  dinamis, lalu menyerahkan stream yang telah didekripsi ke `http.Server` internal
  (trik terminasi MITM standar). Masa aktif socket dibatasi oleh
  `MITM_IDLE_TIMEOUT_MS` agar tunnel yang macet tidak menghabiskan deskriptor file.
- **Penangkapan** (`handleDecryptedRequest`): memasukkan `InterceptedRequest`
  dengan `source: "tproxy"`, status awal `"in-flight"`, header yang diproses
  melalui `sanitizeHeaders()`, dan body melalui `maskSecret()` sebelum masuk ke
  buffer. Entri tersebut kemudian diperbarui dengan respons, ukuran, dan latensi.
- **Penerusan dengan enkripsi ulang** (`createForward` / `realForward`):
  mengenkripsi ulang ke tujuan asli. `rejectUnauthorized` secara default bernilai
  **`true`** (aman secara default) — sertifikat upstream diverifikasi terhadap
  SNI/Host yang diminta klien, sehingga proxy menolak hal yang sama persis seperti
  yang akan ditolak oleh klien asli.

### Anti-loop (SO_MARK)

Karena aturan menandai koneksi keluar lokal yang baru, penerusan terenkripsi ulang
milik proxy **sendiri** biasanya akan dicegat kembali — menyebabkan loop tanpa
akhir. Jalur penerusan mencegah hal ini dengan tanda bypass pada socket
(**SO_MARK**):

- `realForward` membuka socket upstream melalui
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539`
  — yang menetapkan **SO_MARK** **sebelum** `connect()`, sehingga SYN penerusan
  membawa tanda bypass.
- Aturan `mangle OUTPUT` mengecualikan koneksi yang sudah membawa tanda bypass
  (`-m mark ! --mark <bypassMark>`), sehingga penerusan proxy **tidak** ditandai
  ulang dan tidak masuk kembali ke TPROXY.

> Catatan implementasi: socket bertanda bypass harus dipasang pada
> `createConnection` milik agent (`https.request({ createConnection })` secara
> diam-diam diabaikan ketika agent tersedia), atau penerusan akan membuka socket
> tanpa tanda dan loop akan kembali terjadi. Ini adalah perbaikan anti-loop yang
> telah divalidasi melalui e2e.

## §6 Keamanan

| Kontrol                                     | Detail                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API khusus loopback**                     | `/api/tools/agent-bridge/tproxy` tercakup dalam prefiks `/api/tools/agent-bridge/` di `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Penerapan loopback berjalan **sebelum** autentikasi (Aturan Keras #15 + #17) — JWT yang bocor melalui tunnel tidak dapat memulai penangkapan TPROXY, yang menerapkan aturan `iptables` dan memasang CA trust store melalui proses turunan. |
| **Slot CA khusus**                          | CA dinamis dipasang ke `omniroute-tproxy-ca.crt`, tanpa pernah menimpa sertifikat MITM statis.                                                                                                                                                                                                                                                                                                 |
| **Kunci CA tidak pernah meninggalkan host** | `DynamicCertStore` menyimpan kunci CA di memori; kunci tersebut tidak diekspor.                                                                                                                                                                                                                                                                                                                |
| **Penyamaran rahasia**                      | `maskSecret()` pada isi permintaan/respons dan `sanitizeHeaders()` pada header dijalankan **sebelum** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                            |
| **Tanpa interpolasi shell**                 | Semua perintah `iptables`/`ip`/trust store dijalankan melalui `execFile`/`execFileWithPassword` dengan array argumen (Aturan Keras #13).                                                                                                                                                                                                                                                       |
| **Verifikasi sertifikat upstream**          | Penerusan yang dienkripsi ulang memverifikasi sertifikat upstream secara default (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                 |
| **Sanitasi kesalahan**                      | Respons kesalahan rute diproses melalui `sanitizeErrorMessage()` (Aturan Keras #12).                                                                                                                                                                                                                                                                                                           |

**CA MITM merupakan kapabilitas yang sangat kuat.** CA yang dipercaya oleh OS dan dapat menandatangani untuk host mana pun
berarti segala sesuatu yang dicegat OmniRoute dapat didekripsi. Penggunaannya dibatasi pada
mode penangkapan TPROXY khusus lokal yang eksplisit, dinonaktifkan secara default, dan entri
trust store dihapus saat Anda menghentikan mode tersebut.

## §7 Penerapan / pengembalian firewall secara transaksional

Crash tidak boleh meninggalkan aturan `mangle` atau rute usang. Pembuat perintah
(`src/mitm/tproxy/commands.ts`) dan pengeksekusi (`src/mitm/tproxy/setup.ts`) menjamin
bahwa **revert merupakan kebalikan persis dari apply, dalam urutan terbalik**.

`applyTproxy(cfg)` menjalankan perintah apply secara berurutan; jika terjadi **kegagalan apa pun**, fungsi ini menjalankan
`revertTproxy(cfg)` penuh dengan upaya terbaik, lalu melempar ulang galat — sehingga firewall
diterapkan sepenuhnya atau dikembalikan sepenuhnya, tidak pernah hanya diterapkan sebagian. `revertTproxy(cfg)` menjalankan
perintah kebalikan dalam urutan terbalik dan mengabaikan kegagalan (idempoten — aman untuk dipanggil
tanpa syarat, misalnya dari pembersihan `repairMitm()` milik AgentBridge).

`validateTproxyConfig(cfg)` dijalankan sebelum perintah apa pun: port harus berada dalam rentang `1–65535`,
`mark`/`routeTable`/`bypassMark` harus berupa bilangan bulat positif, dan `bypassMark` harus
berbeda dari `mark` (anti-loop).

### Perintah apply (secara berurutan)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Revert menghapus semuanya dalam urutan terbalik: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Resep ini berbasis **OUTPUT** karena kasus penggunaan MITM adalah lalu lintas keluar
> _lokal_ (aplikasi pada host yang sama), yang tidak terlihat oleh TPROXY hanya dengan
> `PREROUTING` — `PREROUTING` hanya melihat lalu lintas yang diteruskan. Rantai `OUTPUT` menandai koneksi
> lokal baru, `ip rule` merutekannya kembali ke pengiriman lokal (`lo`), lalu
> `PREROUTING` menetapkannya ke listener transparan.

## §8 Konfigurasi

Permintaan mulai (`POST /api/tools/agent-bridge/tproxy`) menerima bidang-bidang berikut,
yang divalidasi oleh `StartTproxyBodySchema` (`tproxy/route.ts`). Semuanya bersifat opsional
dan akan menggunakan nilai default masing-masing:

| Bidang           | Tipe               | Default  | Catatan                                                                                                                            |
| ---------------- | ------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Port TCP tujuan yang akan diintersepsi secara transparan                                                                           |
| **mark**         | int (≥1)           | `0x2333` | Tanda firewall yang ditetapkan pada `OUTPUT`, dicocokkan oleh `ip rule` + `PREROUTING`                                             |
| **onPort**       | int (1–65535)      | `8443`   | Port yang diikat oleh listener transparan (**IP_TRANSPARENT**)                                                                     |
| **routeTable**   | int (≥1)           | `233`    | ID tabel perutean berbasis kebijakan yang menyimpan rute `local 0.0.0.0/0`                                                         |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Tanda soket bypass (**SO_MARK**) yang ditetapkan proksi pada koneksi upstream-nya sendiri; dikecualikan dalam `OUTPUT` (anti-loop) |
| **sudoPassword** | string             | —        | Hanya desktop non-root: mengotorisasi pemasangan trust store; diabaikan saat berjalan sebagai root                                 |

Tidak ada **variabel lingkungan** untuk TPROXY — seluruh konfigurasi dilakukan melalui
body POST atau nilai default di atas.

## §9 Mengaktifkan dari Traffic Inspector

1. Buka **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).
2. Di bilah alat mode pengambilan, temukan tombol **"TPROXY Decrypt"** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Jika tombol tersebut **dinonaktifkan** dengan tooltip "Dekripsi TPROXY memerlukan Linux + root +
     addon native", addon native tidak tersedia di host ini (bukan Linux,
     tidak ada toolchain, atau addon belum dibangun). Lihat [§2](#2-requirements) dan [§3](#3-the-native-ip_transparent-addon).
3. Klik tombol tersebut. Tindakan ini memanggil `POST /api/tools/agent-bridge/tproxy` melalui
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), yang:
   membuat CA dinamis, membuka listener transparan, menerapkan aturan firewall,
   dan memasang CA di penyimpanan kepercayaan OS.
4. Saat berjalan, toggle berubah menjadi kuning kecokelatan dan menampilkan jumlah intersepsi langsung
   (`· <interceptCount>`). Permintaan yang diintersepsi muncul dalam daftar permintaan dengan
   `source: "tproxy"`.
5. Klik lagi untuk menghentikan — `DELETE /api/tools/agent-bridge/tproxy` melalui
   `stopTproxyCaptureMode()` menutup listener, menghapus pemasangan CA, dan mengembalikan
   aturan firewall.

Status mode pengambilan (berjalan / tersedia / jumlah intersepsi / port listener) berasal
dari `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` di
`src/mitm/tproxy/captureManager.ts`). Hanya **satu** sesi TPROXY yang berjalan dalam satu waktu —
memulai sesi kedua akan ditolak dengan "Mode pengambilan TPROXY sudah berjalan".

## §10 Pemecahan masalah

### Toggle dinonaktifkan

Addon native tidak dapat dimuat. Pastikan: Anda menggunakan Linux, telah membangun addon
(`npm run build:native:tproxy`), dan proses dapat memuat `transparent.node`.
`isTransparentSocketAvailable()` mengendalikan toggle; `GET /api/tools/agent-bridge/tproxy`
mengembalikan `available: false` ketika addon tidak ada.

### Tidak ada yang diambil

- Pastikan proses yang diintersepsi benar-benar terhubung ke `dport` yang dikonfigurasi
  (nilai default `443`).
- Pastikan proses memercayai CA dinamis. CA dipasang sebagai
  `omniroute-tproxy-ca.crt`; aplikasi dengan penyimpanan kepercayaan sendiri (Firefox/Chrome NSS)
  mungkin juga perlu menambahkan sertifikat tersebut di sana.
- Jalankan pengujian mandiri **Diagnose** AgentBridge (lihat
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) untuk pemeriksaan kepercayaan sertifikat /
  kesehatan server.

### Aturan firewall yang tertinggal setelah crash

`revertTproxy()` adalah kebalikan persis dari penerapan dan bersifat idempoten. Menghentikan
mode akan mengembalikan aturan; jika OmniRoute dihentikan secara paksa di tengah sesi, gunakan tindakan
**Repair** AgentBridge (`POST /api/tools/agent-bridge/repair`) untuk membatalkan status sistem
yang tertinggal (spoof DNS, CA root, proksi sistem). Aturan `mangle` dan rute TPROXY juga
dibersihkan secara otomatis saat reboot.

### Loop tak terbatas / proksi mengintersepsi penerusannya sendiri

Ini adalah kasus anti-loop. Pastikan `bypassMark` berbeda dari `mark` (validasi
menerapkan ketentuan ini) dan penerusan menggunakan `connectMarked` (seperti yang dilakukan di `realForward`).
Lihat [§5 Anti-loop](#anti-loop-so_mark).
