## npm Trusted Publishing (zadano od v3.8.51) — pripremljeno na zahtjev, izravno kao pričuvna opcija

`npm-publish.yml` prema zadanim postavkama objavljuje putem **npm Trusted Publishing (OIDC)**: posao
`stage-npm` (koji se izvodi na GitHubovu hostiranom izvršitelju) razmjenjuje GitHubov id-token za kratkotrajnu npm
vjerodajnicu za to pokretanje — bez dugotrajnog npm tokena u tajnama repozitorija, bez upita za 2FA, uz priložen dokaz o podrijetlu.
To je zaobilazni mehanizam koji npm sada odobrava jer se tokeni koji preskaču 2FA povlače iz upotrebe;
njime se vraća potpuno automatski tijek koji je projekt imao do v3.8.48, uz zadržavanje
jamstva WS1.3 (procurjeli token ne može samostalno objavljivati — token ne postoji).

**Jednokratno postavljanje (vlasnik):** npmjs.com → paket `omniroute` → Settings → _Trusted
Publisher_ → GitHub: vlasnik `diegosouzapw`, repozitorij `OmniRoute`, tijek rada `npm-publish.yml`
(okruženje: nijedno). Dok to ne postoji, automatski korak ne uspijeva uz `ENEEDAUTH`:
ponovno ga pokrenite s `publish_mode=staged` (u nastavku) ili `direct`.

### Pripremljeno objavljivanje (na zahtjev — `publish_mode=staged`)

Tijek rada npm-publish više ne objavljuje izravno: pokreće zapakiranu tarball arhivu
(`check:pack-boot`), a zatim izvršava `npm stage publish` — točno ti bajtovi smještaju se u
registar, ali ih **nije moguće instalirati** dok ih vlasnik ne odobri. Ljudska 2FA provjera premještena je
NAKON dokaza, a ne prije njega.

**Tijek za vlasnika nakon što tijek rada postane zelen:**

1. `npm stage list omniroute` — pronađite ID pripremljenog izdanja (ispisuje se i u sažetku tijeka rada).
2. Provjerite pripremljene bajtove (preporučeno): `npm stage download <id>`, zatim instalirajte
   preuzetu tarball arhivu u privremeni prefiks i pokrenite je (`npm run check:pack-boot` automatizira
   istu provjeru paketiranja→instaliranja→pokretanja u CI-ju).
3. `npm stage approve <id>` — 2FA upit JEST objavljivanje. `npm stage reject <id>` odbacuje pripremljeno izdanje.
4. Zaštitna provjera nakon objavljivanja: provjeravatelj nakon objavljivanja (WS1.4 iz plana za v3.8.49) instalira
   objavljenu verziju iz javnog registra u čistom spremniku i pokreće je.

**Pričuvna opcija za hitne slučajeve:** `workflow_dispatch` s `publish_mode=direct` vraća
naslijeđeni neposredni `npm publish` (upotrijebite samo ako priprema ne funkcionira ispravno; zabilježite razlog).

**Jednokratno sigurnosno ojačavanje (vlasnik, npmjs.com):** konfigurirajte Trusted Publisher za
`omniroute` u načinu rada samo s pripremom kako procurjeli dugotrajni token ne bi mogao izvršiti `npm publish`
izravno niotkuda — CI može samo pripremiti izdanje; objaviti ga može samo vlasnik putem 2FA.

**Postupak za neispravne artefakte (nepromijenjen):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
kao zadana reakcija (traje nekoliko minuta, povratno je); `npm unpublish` samo unutar razdoblja od 72 sata i ako nema ovisnih paketa
te nikada kao prvi potez. Docker: nikada nemojte ponovno zapisivati oznaku verzije — vraćanje je
preusmjeravanje oznake `latest` na posljednji ispravan sažetak.

**Docker Hub `latest` (obavezno pri svakom stabilnom SemVer objavljivanju):** tijek rada
`docker-publish` mora označiti **i** `X.Y.Z` **i**, kada
`should-promote-latest.sh` potvrdi da je to najviši stabilni SemVer, `:latest`
s **istim sažetkom**. Nakon posla: sažetak oznake `latest` na Hubu mora biti jednak sažetku novog
SemVer izdanja, a `last_updated` mora biti ažuriran. Nemojte ostaviti `:latest` na starijoj
izgradnji dok bilješke o izdanju govore o ispravcima koji postoje samo u gitu. Compose
primjeri za brzi početak koriste `:latest`; GitOps bi trebao nastaviti prikvačivati `X.Y.Z`. Pogledajte
[Kanali Docker izdanja](../guides/DOCKER_GUIDE.md#release-channels) i #10317.

## Ubrzana staza za hitne ispravke (oznaka `hotfix`)

PR s oznakom `hotfix` preskače opsežnu CI matricu (E2E s 9 segmenata, prag
pokrivenosti, quality-gate, quality-extended) i zadržava brze provjere s jakim signalom: izgradnju,
segmente jediničnih testova, integracijske testove, vitest, lint/provjeru tipova, docs-sync, `check:pack-artifact`
i provjeru pokretanja iz tarballa (`check:pack-boot`). Cilj: zelen status za ≤15 min umjesto ~33 min.

**Pravila ulaska — sva četiri uvjeta su obvezna (po uzoru na hitne staze projekata Chromium/VS Code/Node):**

1. **Ozbiljnost**: produkcija ne radi — objavljeni artefakt ruši se pri pokretanju /
   sigurnosna ispravka / pogođen je svaki korisnik izdanja. „Važno” ne znači „ne radi”.
2. **Ovlaštenje**: samo vlasnik repozitorija primjenjuje oznaku `hotfix`. Oznaka JEST
   odobrenje — nikad je nemojte samostalno primijeniti na PR kampanje.
3. **Dokazi**: tijelo PR-a sadrži poveznicu na prethodno potpuno zeleno opsežno izvođenje (skup testova
   koji bi preskočeni poslovi ponovno provjerili) te test same ispravke koji prvo ne prolazi, a zatim prolazi.
4. **Opseg**: isključivo cherry-pick — minimalna ispravka, bez refaktoriranja i usputnih promjena.

Preskočena površina pokrivenosti/pragova ponovno se provjerava pri sljedećem potpunom izvođenju na
grani izdanja (kontinuirano zeleno izdanje) — staza preskače ČEKANJE, nikad provjeru valjanosti.
Promjene samo u testovima (sve datoteke pod `tests/`, nijedna pod `tests/e2e/`) automatski preskaču E2E
matricu, bez ikakve oznake.

### Hookovi (provjereni Huskyjem)

Husky hookovi nalaze se u `.husky/` i automatski se pokreću tijekom git operacija.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** brze determinističke provjere — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (aktivirano 2026-06-13). Namjerno izostavlja `test:unit` (sporo; pokriveno CI poslom `test-unit`).
  - Ručno pokrenite `npm run test:unit` prije slanja grana izdanja.

Ako hook ne uspije: ispravite temeljni problem, nemojte ga zaobići opcijom `--no-verify`.

### Raspored međuverzije

Repozitorij upotrebljava tri različita izlazna direktorija — nikada ih nemojte pomiješati:

| Direktorij | Svrha                                                              | Prati se?            |
| ---------- | ------------------------------------------------------------------ | -------------------- |
| `src/`     | Izvorni kod aplikacije (TypeScript / TSX)                          | Da                   |
| `.build/`  | Međurezultati međuverzije — izlaz naredbe `next build` (`distDir`) | Ne (ignorira ga git) |
| `dist/`    | Isporučivi npm paket — sastavlja ga `assembleStandalone`           | Ne (ignorira ga git) |

> **Napomena za operatera:** direktorij slike na udaljenom VPS-u ostaje `/usr/lib/node_modules/omniroute/app/`.
> Premješten je samo izlaz međuverzije **unutar repozitorija** (`app/` → `dist/`). Vještine za implementaciju putem rsynca
> sinkroniziraju sadržaj direktorija `dist/` s udaljenim direktorijem `app/` — promjene putanje na VPS-u nisu potrebne.

**Tijek jedne međuverzije:**

```
npm run build:release
  └─ rm -rf .build dist          (čišćenje)
  └─ next build → .build/next/   (međurezultati)
  └─ assembleStandalone          (kopira samostalni paket + statičke datoteke + javne datoteke + izvorne module → dist/)
  └─ writes dist/BUILD_SHA       (HEAD kontrolna oznaka)
```

NEMOJTE pokretati `npm run build`, a zatim zasebno `npm run build:cli` za implementaciju — upotrijebite
`npm run build:release`, koji u jednoj naredbi obavlja čistu ponovnu izgradnju i stvara kontrolnu oznaku.

Nakon v3.8.59 sljedeća je verzija 3.9.0, a njezin vrh postaje polazište dviju dugotrajnih grana:
`stable/v3` (v3 LTS linija, npm `latest`) i `develop` (v4, podignuta na 4.0.0, npm
`nightly`). Model grana/kanala, prosljeđivanje promjena i oznake opisani su u
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md); plan se nalazi u dokumentu [ROADMAP](../../ROADMAP.md) (3. faza). Izdvajanje se izvodi jednom;
3.8.58 uvježbava ga od početka do kraja na račvanju, a 3.8.59 završava s
[GO/NO-GO kontrolnim popisom](./LTS_GO_NO_GO.md).

### Probno izvođenje (samo za čitanje, sigurno u svakom trenutku)

```bash
npm run release:dry-run-lts-cut                       # stvarno izdvajanje: 3.9.0 iz HEAD, prethodna oznaka v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # prikvači izvorni commit
```

`scripts/release/dry-run-lts-cut.mjs` ne izvršava ništa: čita git i `gh` te ispisuje
cijeli slijed — preduvjete (izvor se može razriješiti, prethodna oznaka postoji, `package.json`
ima ciljnu verziju, otvoren je problem `release-freeze`, nema otvorenog problema
`Release branch not green` na postojećoj grani izdanja — za granu koja ne postoji prijavljuje
se `?` nepoznato, nikada zeleno — konfiguriran je Mergifyjev red čekanja `release` (G11:
`queue_rules`, `checks_timeout`, oznaka `queue`), skup pravila `release/*` i dalje blokira
brisanje i prisilno slanje, a `stable/v3` i `develop` još ne postoje), dva koraka za grane,
koji se okidači neaktivnih tijekova rada i uvjeti `if:` aktiviraju (a koji ostaju blokirani
varijablom repozitorija ili prikvačeni na kanonski repozitorij), očekivane dist-oznake
(`latest` → 3.9.0, `next` i `nightly` prazne) i vraćanje promjena. Izlaz `0` =
`RESULT: READY`, `1` = blokirajući preduvjet nije ispunjen (`✗`), `2` = pogreška pri uporabi.
`--advisory <id,...>` spušta provjeru na upozorenje (`!`) bez njezina skrivanja.

Pokrenite probno izvođenje stvarnog izdvajanja dok je zamrzavanje izdanja 3.9.0 još uvijek
aktivno — grane se stvaraju nakon oznake i prije nego što faza 12c ukine zamrzavanje.
