`open-sse/config/providerPluginManifest.ts` definira ugovor pružateljskog
dodatka siguran za JSON. `open-sse/config/providerPluginManifestRegistry.ts` povezuje taj
ugovor s trenutačnim registrom pružatelja za pomoćne procese kao što su Bifrost,
CLIProxyAPI ili budući Go/Rust usmjerivač. TypeScript registar ostaje
izvor istine, ali pomoćni procesi mogu koristiti manifest bez uvoza
koda izvršitelja, zadanih OAuth vrijednosti, zaglavlja ili stanja okruženja procesa.

Isti manifest dostupan je putem HTTP-a na
`GET /api/v1/provider-plugin-manifest` za pomoćne procese koji se izvode izvan glavnog procesa.

OmniRoute oglašava taj URL Bifrostu i CLIProxyAPI-ju putem
zaglavlja zahtjeva `X-OmniRoute-Provider-Manifest-Url`. Postavite
`OMNIROUTE_PROVIDER_MANIFEST_URL` kada pomoćni proces treba javni URL ili URL
kontejnerske mreže umjesto lokalnog izvora zahtjeva.

## Osvježavanje manifesta

HTTP krajnja točka vraća `Cache-Control: public, max-age=60` i jaki
`ETag`. Pomoćni proces trebao bi zadržati posljednji provjereni manifest i slati njegov ETag
u `If-None-Match` pri osvježavanju. Odgovor `304 Not Modified` nema tijelo;
pomoćni proces zadržava svoj predmemorirani manifest. Ako ne postoji provjereni predmemorirani manifest,
pomoćni proces mora poslati bezuvjetni zahtjev umjesto prihvaćanja odgovora `304`.

## Cilj

Premjestiti metapodatke pružatelja prema ugovoru dodatka kako bi kritičnim putem zahtjeva
u konačnici mogao upravljati pomoćni proces niže latencije, dok OmniRoute zadržava
TypeScript rutu kao kontrolnu točku pravila i pričuvno rješenje. Manifest je aditivan: sam
po sebi ne mijenja usmjeravanje zahtjeva.

## Ugovor

Manifest sadrži:

- ID i alias pružatelja
- izvorni format i naziv izvršitelja
- vrstu autentifikacije, autentifikacijsko zaglavlje i neobavezni autentifikacijski prefiks
- statičke metapodatke krajnje točke
- podobnost za pomoćni proces i izričite razloge zbog kojih bi pružatelj trebao ostati na TS-u
- metapodatke modela sigurne za JSON, kao što su duljina konteksta, oznake za vid/zaključivanje i
  nepodržani parametri
- oznake mogućnosti, uključujući `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` i `usage-supported`

Manifest namjerno isključuje:

- OAuth klijentske tajne i zadane tajne vrijednosti
- razrješavanje okruženja tijekom izvođenja
- zaglavlja zahtjeva i javne pomoćne funkcije za vjerodajnice
- dinamičke graditelje URL-ova
- funkcije izvršitelja
- interne pojedinosti spremišta sesija

## Oznake mogućnosti

`capabilities` je sortirani niz oznaka izvedenih iz stavke registra. Integratori
bi ga trebali smatrati strojno čitljivim odgovorom na pitanje „što ovaj pružatelj može učiniti” umjesto
ponovnog čitanja TypeScript izvornog koda.

| Oznaka               | Značenje                                                                         |
| -------------------- | -------------------------------------------------------------------------------- |
| `apikey`             | Prihvaća API ključ (`authType` je `apikey` ili `optional`).                      |
| `oauth`              | Koristi OAuth ili tok sesije.                                                    |
| `responses`          | Izlaže osnovni URL za OpenAI Responses API.                                      |
| `passthrough-models` | Poslužuje modele izravno iz izvornog sustava umjesto iz statičkog kataloga.      |
| `custom-executor`    | Pokreće izvršitelj koji nije zadani, pa ostaje na TypeScript putu.               |
| `sidecar-candidate`  | Odražava `sidecar.eligible` — siguran za razmatranje pri uvozu u pomoćni proces. |
| `usage-fetch`        | Ima povezani dohvatitelj upotrebe ili kvote (`getUsageForProvider`).             |
| `usage-supported`    | API za upotrebu prihvaća ovog pružatelja (`isSupportedUsageConnection`).         |

`usage-fetch` služi samo za otkrivanje. Izvještava da OmniRoute zna čitati podatke o upotrebi za
pružatelja; ne aktivira dohvaćanje, ne mijenja semantiku kvota niti podrazumijeva da je
widget kvote na nadzornoj ploči omogućen za pružatelja — taj widget zasebno kontrolira
`USAGE_SUPPORTED_PROVIDERS`. Izvor istine je `USAGE_FETCHER_PROVIDERS` u
`open-sse/services/usage/fetcherProviders.ts`.

Taj je popis indeksiran nizovima koje dispečer upotrebe prihvaća, pa kombinira kanonske ID-ove
s aliasima i nešto je dulji od broja označenih pružatelja: stavke koje
nisu pružatelji razgovora u registru manifesta (primjerice pružatelj pretraživanja `firecrawl`
i ACP pružatelj `amazon-q`) nemaju stavku manifesta koja bi se mogla označiti.

`usage-supported` odgovara na pitanje prihvaćaju li poslužiteljske rute i rute upotrebe na nadzornoj ploči vezu
za pružatelja. Odražava `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
i `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), a obje kontrolira
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Za razliku od
`usage-fetch`, emitira se samo na temelju ID-a pružatelja — zaštita tijekom izvođenja poziva
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` bez razrješavanja aliasa, pa manifest
zadržava isto pravilo. Dvije oznake imaju različite opsege: 3 pružatelja nose samo
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), a 1 nosi samo
`usage-supported` (`xiaomi-mimo-token-plan`), pa jedna ne podrazumijeva drugu.

## Upotreba pomoćnog procesa

Pomoćni procesi trebaju tretirati `sidecar.eligible` kao konzervativan signal da je pružatelj kandidat, a ne kao bezuvjetnu odluku o usmjeravanju. Prvi cilj uvoza trebali bi biti pružatelji koji koriste API ključ i statičku krajnju točku te zadani izvršitelj. Pružatelji s prilagođenim web-izvršiteljima, OAuth/tokovima sesija, dinamičkim graditeljima URL-ova ili konfiguracijom skupa ostaju na rezervnom TypeScript putu sve dok pomoćni proces ne implementira ekvivalentno ponašanje, a telemetrija ne potvrdi jednakovrijednost.

Predložene faze migracije:

1. Generirati i validirati manifest dodataka pružatelja iz TS registra.
2. Omogućiti Bifrostu ili CLIProxyAPI-ju uvoz manifesta za pružatelje s API ključem i statičkom krajnjom točkom.
3. Usmjeriti prikladne pružatelje kroz pomoćni proces iza `OMNIROUTE_RELAY_BACKEND`, uz zadržavanje omogućenog rezervnog TS puta.
4. Promovirati pružatelje samo kada su stopa uspješnosti, latencija p99, ponašanje strujanja i obrada nepodržanih parametara usklađeni s TS putem.
5. Dodavati dodatke izvorne za pomoćni proces za prilagođene izvršitelje, jednu po jednu obitelj pružatelja.

## Zašto pružatelje ne ugraditi izravno u Next

Next sučelje ne bi trebalo biti zaduženo za izvršavanje pružatelja. Trebalo bi pozivati API granicu. Pozadinski sustav zatim može odlučiti hoće li upotrijebiti TypeScript izvršitelj, Bifrost, CLIProxyAPI ili budući izvorni pomoćni proces. Time se potpisivanje zahtjeva, provjere popisa dopuštenih stavki, pravila baze podataka i rezervno ponašanje centraliziraju prije predaje bilo kojem pomoćnom procesu.
