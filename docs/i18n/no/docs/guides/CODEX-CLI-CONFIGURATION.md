> **TOML er det eneste formatet som fungerer.** Moderne Codex leser utelukkende
> `~/.codex/config.toml` (verifisert mot codex-cli 0.147.0: `codex --help`
> dokumenterer at overstyringer med `-c/--config` «lastes fra
> `~/.codex/config.toml`»). Den gamle `~/.codex/config.yaml` tilhørte den eldre
> npm-CLI-en og ignoreres uten varsel. Dashboard-generatoren
> (`/api/cli-tools/apply`, verktøyet `codex`) skriver TOML med en konservativ
> sammenslåing — eksisterende nøkler og andre leverandørblokker bevares,
> API-nøkkelen forblir i `OMNIROUTE_API_KEY` (aldri i filen), og en gjenværende
> eldre `config.yaml` rapporteres som en migreringsmerknad uten å bli endret.

## Klar-til-innliming config.toml

Erstatt `<YOUR_HOST>` og `<YOUR_KEY>` med dine verdier:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # lagringsgrense i historikken per verktøykall

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc eller ~/.zshrc — faktisk nøkkelverdi, aldri i config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex inkludert i ChatGPT-appen

Hvis du installerte Codex gjennom ChatGPT-skrivebordsappen, kan `codex`-binærfilen
bare finnes inne i app-pakken og ennå ikke være tilgjengelig i skallets `PATH`.
Legg til ressurskatalogen i skallets oppstartsfil:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Åpne et nytt skall, og verifiser deretter:

```bash
command -v codex
codex --version
```

### Lokal OmniRoute uten autentisering: En plassholdernøkkel er tilstrekkelig

Codex validerer at miljøvariabelen angitt av `env_key` finnes
**før** den første forespørselen forlater CLI-en. Hvis den **lokale**
OmniRoute-instansen din ikke krever autentisering, fungerer enhver ikke-tom
plassholder:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Bruk i stedet en ekte nøkkel når OmniRoute-serveren din er beskyttet eller ekstern.

> **Vanlige vertsalternativer**
>
> | Tilgang         | URL                           |
> | --------------- | ----------------------------- |
> | Lokalt nettverk | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | Tilbakekobling  | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — hvorfor det fungerer for alle modeller

Codex CLI avviklet `wire_api = "chat"` (Chat Completions) i februar 2026 og **krever** nå `wire_api = "responses"` (OpenAI Responses API). Hvis `wire_api = "chat"` angis, krasjer programmet umiddelbart ved oppstart fra og med v0.138.

Mange leverandører, inkludert GLM og Kimi, tilbyr fortsatt bare et Chat Completions-endepunkt. DeepSeek V4 tilbyr nå både et innebygd Responses API og et Anthropic-kompatibelt endepunkt. OmniRoute bruker Responses som standard og lar hver DeepSeek-tilkobling velge Anthropic-kompatibilitet.

**OmniRoute løser dette transparent:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute velger leverandørens innebygde protokoll og oversetter ved behov
    → POST /responses (DeepSeek V4) eller /chat/completions (Mistral / GLM / Kimi / andre)
```

Du trenger aldri en separat oversettelsesproxy når du bruker OmniRoute. **Alle modeller bruker `wire_api = "responses"`** — OmniRoute håndterer resten.

> **`wire_api` er standardverdien** — feltets standardverdi er `"responses"` og det kan utelates helt fra `config.toml`. Angi det bare eksplisitt hvis du dokumenterer hensikten.

## Kontekstvindu og komprimering

### Felt for tokenkonfigurasjon

| Felt                             | Beskrivelse                                                                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `model_context_window`           | Totalt tokenbudsjett for den aktive modellen. Angi modellens oppgitte grense.                                                                                                                                |
| `model_auto_compact_token_limit` | Terskel som utløser automatisk komprimering av historikken. **Maksimum: 90 % av `model_context_window`** — verdier over 90 % ignoreres uten varsel.                                                          |
| `tool_output_token_limit`        | Grense for antall tokens som lagres per verktøykallresultat i historikken. Forhindrer at ett stort verktøysvar fyller vinduet. **Dette er ikke maksimal utdata** — det er en lagringsgrense for historikken. |
| `compact_prompt`                 | Innebygd overstyring av systemledeteksten som brukes under komprimering (v0.138+).                                                                                                                           |

> **Merknad om `model_max_output_tokens`**: Dette feltet er **ikke en del av konfigurasjonsskjemaet til Codex CLI** (det finnes ikke i Codex-kodebasen for Rust). Det ignoreres uten varsel hvis det angis. Ikke stol på det — bruk `tool_output_token_limit` til å kontrollere hvor mye verktøyutdata som lagres i historikken.

## Resonneringsinnsats

Styrer hvor mye modellen «tenker» før den svarer.

| Verdi    | Brukes til                                         |
| -------- | -------------------------------------------------- |
| `none`   | Ingen resonnering — direkte svar                   |
| `low`    | Trivielle oppgaver (endre navn, formatere)         |
| `medium` | **Serverstandard** når det ikke er angitt          |
| `high`   | Oppgaver på mellomnivå (refaktorering, feilsøking) |
| `xhigh`  | Arkitektur, grundig analyse, komplekse problemer   |

```bash
# Overstyring per kjøring
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Angi også et **sammendrag** av resonneringen, slik at Desktop kan vise tanketekst (ikke bare krypterte blokker):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # eller ultra når det støttes
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute-tenkebudsjett (serverinnstilling)

På OmniRoute-verten må **Settings → AI → Thinking Budget** være satt til **`passthrough`** for at Codex-innsats/sammendrag skal nå oppstrømstjenesten. Modusen **`auto` fjerner** alle `reasoning`- / `reasoning_effort`-felter fra klienten og vil tømme tankepanelene selv når Codex er riktig konfigurert.

Fullstendig veiledning: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Komprimering og ledetekstbuffer er uavhengige og fortsetter å fungere med `passthrough`.

## Profiler — navngitte konfigurasjoner per modell/arbeidsflyt

Med profiler kan du bytte modell + kontekstvindu med ett enkelt flagg. Hver profil er en flat
`~/.codex/<name>.config.toml` som legges oppå den grunnleggende `config.toml`.

> **Navneregel (Codex CLI v0.137+):** filen må være `~/.codex/<name>.config.toml` — **uten prefikset `profile-`**.
> CLI-en løser `-p kimi-k27` til `~/.codex/kimi-k27.config.toml`. Hvis filen ikke blir funnet, brukes standardinnstillingen uten varsel.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # rask, rimelig
```

### Innsatsprofiler (samme modell, ulik innsats)

```bash
codex -p low      # cx/gpt-5.5, innsats=low
codex -p medium   # cx/gpt-5.5, innsats=medium
codex -p high     # cx/gpt-5.5, innsats=high
codex -p xhigh    # cx/gpt-5.5, innsats=xhigh (standard)
codex -p chat     # cx/gpt-5.5, ingen innsats angitt (serverstandard)
```

## Generere profiler automatisk med `omniroute setup-codex`

Hvis du kjører OmniRoute på en VPS, kan du generere profilfiler automatisk fra den aktive modellkatalogen:

```bash
# Fra en VPS (bruker lokal OmniRoute på port 20128)
omniroute setup-codex

# Fra hvilken som helst maskin — pek mot VPS-en din
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Forhåndsvis uten å skrive filer
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Generer bare GLM- og Kimi-profiler
omniroute setup-codex --only glm,kimi

# Skriv til en egendefinert katalog
omniroute setup-codex --codex-home /path/to/.codex
```

Kommandoen henter `/v1/models`, bruker finjusterte profiler for kjente modeller, faller tilbake på katalogmetadata for andre kompatible tekstmodeller og skriver `~/.codex/<name>.config.toml` for hver av dem. Idempotent — trygg å kjøre på nytt.

OmniRoute kan også **synkronisere automatisk** de samme profilfilene etter at et vellykket leverandørsøk eller en import av modeller endrer den aktive katalogen. Dette er **valgfritt og deaktivert som standard**: slå det på fra **CLI Code-kontrollpanelet** ("Automatisk synkronisering av CLI-profiler" → Codex), eller angi `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (det respekterer også `CLI_ALLOW_CONFIG_WRITES`, som er aktivert som standard). Når dette er aktivert, skriver det bare separate `~/.codex/*.config.toml`-profilfiler. Det endrer aldri den aktive eller standardvalgte `~/.codex/config.toml`, Codex-lb-innstillinger, autentisering eller leverandørvalg.

## Starte Codex med `omniroute launch-codex`

Utfører en helsesjekk av OmniRoute-instansen din før Codex startes:

```bash
# Start mot lokal OmniRoute (standardport 20128)
omniroute launch-codex

# Start med en bestemt profil
omniroute launch-codex --profile kimi-k27

# Start mot en ekstern VPS
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# Send ekstra argumenter til codex
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex er også et mål for de to generiske manifeststyrte inngangspunktene
(`bin/cli/cli-manifest.mjs`):

## Langvarige oppgaver

To standardinnstillinger i OmniRoute kan i det stille sabotere Codex CLI-økter som varer i flere timer. Ingen av dem er en Codex CLI-innstilling — begge ligger på OmniRoute-siden. Brukere som migrerer en konfigurasjon fra oppstrøms-proxyer som låser kontoer og deaktiverer tidsavbrudd ved inaktivitet, støter ofte på begge og konkluderer med at OmniRoute «ikke kan opprettholde en lang økt».

| Symptom                                                                                  | Sannsynlig årsak                                                                  | Innstilling              |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------ |
| Økten fortsetter å bytte konto / kontinuiteten i ledetekstbufferen går tapt mellom turer | TTL for økttilhørighet er `0` (deaktivert)                                        | `sessionAffinityTtlMs`   |
| Tilkoblingen brytes midt i resonneringen uten noen melding til klienten                  | Vakthunden for inaktiv strøm ble utløst etter 10 minutter uten oppstrømsdatablokk | `STREAM_IDLE_TIMEOUT_MS` |

Relaterte diskusjoner: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (avbrudd i lange oppgaver), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (hvorfor tilhørighet er deaktivert som standard). Sporing: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Økttilhørighet — lås én samtale til én konto

**Standard:** `sessionAffinityTtlMs = 0` (deaktivert).

**Hvor den angis**

- Kontrollpanel → **Innstillinger → Ruting** → **Økttilhørighet** → **TTL for tilhørighet (sekunder)** (`ComboDefaultsTab`)
- Eller oppdater innstillingene med PATCH og `sessionAffinityTtlMs` i **millisekunder** (Zod-område `0`–`86_400_000`, dvs. opptil 24 timer)

> Omdøpt i #7274 fra den Codex-spesifikke `codexSessionAffinityTtlMs`. Den eldre nøkkelen godtas fortsatt som et skrivebeskyttet alias; nye konfigurasjoner bør bruke `sessionAffinityTtlMs`. Tilhørighet gjelder nå for **alle** leverandører når TTL-en er høyere enn `0`, ikke bare Codex — se [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Økttilhørighet.

**Hva som slutter å fungere når verdien forblir 0**

Hver tur i en Codex-samtale med flere turer rutes uavhengig av den aktive kombinasjonsstrategien og kan havne på en **annen konto for hver tur**. Dette bryter kontinuiteten i oppstrømsøkten / ledetekstbufferen. OmniRoute bruker bare Codex-øktshoder (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) og brødtekstfelt som `prompt_cache_key` / `session_id` når TTL-en er større enn `0` (`extractSessionAffinityKey` i `src/sse/services/auth.ts`).

**Anbefalt for én oppgave som varer i flere timer**

Sett TTL-en **høyere enn oppgavens forventede faktiske varighet** (maksimum i brukergrensesnittet er **86400 sekunder** = 24 timer):

| Forventet oppgavelengde | TTL for tilhørighet (brukergrensesnitt, sekunder) | `sessionAffinityTtlMs` |
| ----------------------- | ------------------------------------------------- | ---------------------- |
| Noen få timer           | `14400` (4 t)                                     | `14400000`             |
| Over natten / ~12 t     | `43200` (12 t)                                    | `43200000`             |
| Et helt døgn            | `86400` (24 t, maksimum)                          | `86400000`             |

Aktivering er et bevisst valg: Deaktivering av tilhørighet favoriserer lastbalansering på tvers av kontoer, mens aktivering favoriserer kontinuitet for én lang agentøkt. Denne veiledningen endrer **ikke** standardinnstillingen — operatører som kjører lange Codex-oppgaver, må aktivere den selv.

### 2. Tidsavbrudd ved inaktiv strøm — ikke avbryt stille resonneringsturer

**Standard:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minutter). Den arver fra `REQUEST_TIMEOUT_MS` når den ikke er angitt; den delte grunnverdien er også 600000. Se [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Tidsavbrudd.

**Hva som slutter å fungere med standardinnstillingen**

En Codex-resonnerings-/verktøyrunde som er stille i mer enn 10 minutter uten **noen reell oppstrømsdatablokk**, tvangslukkes av SSE-tomgangsvakten (`open-sse/utils/stream.ts`). Klienten opplever ofte bare at forbindelsen brytes — i tråd med «stoppet automatisk uten noe varsel».

Viktig detalj: OmniRoutes syntetiske SSE-**hjerteslag nullstiller ikke** tomgangsklokken. Bare en reell oppstrømsdatablokk oppdaterer `lastChunkTime`. En stille modell som fortsatt «tenker», ser identisk ut som en fastlåst oppstrømstilkobling fra vaktens perspektiv.

Relatert inaktivitet for Undici-responskroppen: `FETCH_BODY_TIMEOUT_MS` (har også den samme standardverdien på 10 minutter; `0` deaktiverer den). Ved strømming dekker `FETCH_TIMEOUT_MS` bare tilkoblingsoppsett / de første headerne — når strømmen er aktiv, styres fastlåste tilstander av `STREAM_IDLE_TIMEOUT_MS` og `FETCH_BODY_TIMEOUT_MS`.

**Anbefalt for én enkelt oppgave som varer i flere timer**

I prosessmiljøet til OmniRoute (`.env` / compose / systemd):

```bash
# Deaktiver avbruddsgrensene for strømmetomgang og inaktiv responskropp ved lange resonneringsrunder
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Eller øk dem til mer enn det lengste stille intervallet du forventer (verdiene er i millisekunder):

```bash
# Eksempel: tillat opptil 2 timers stillhet mellom oppstrømsdatablokker
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Start OmniRoute på nytt etter at disse miljøvariablene er endret.

### Konkret oppskrift — Codex-oppgave over flere timer

1. **Fest kontoen:** Kontrollpanel → Innstillinger → Ruting → Økttilhørighet → Tilhørighets-TTL = `43200` (12 t) eller `86400` (maks. 24 t).
2. **Øk / deaktiver tomgangsgrensene** i OmniRoutes miljø:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Behold den vanlige Codex-`config.toml` (`wire_api = "responses"`, riktig `base_url`, `OMNIROUTE_API_KEY`) — det finnes ingen innstillinger på Codex-siden for tilhørighet/tomgang som styrer disse to virkemåtene.
4. Start OmniRoute på nytt, og start deretter den langvarige Codex-oppgaven.

### Beslutning om standardverdier (#7287)

| Innstilling              | Levert standardverdi | Endre i denne veiledningen?                                                                                        |
| ------------------------ | -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `sessionAffinityTtlMs`   | `0` (av)             | **Nei** — forblir valgfritt (lastbalansering kontra kontinuitet; se diskusjon #5718)                               |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min)    | **Nei** — forblir 10 minutter for generell trafikk; operatører med lange Codex-oppgaver øker eller deaktiverer den |

Å endre en av standardverdiene globalt ville endre virkemåten for alle klienter på en instans, ikke bare Codex. Dokumenter innstillingene; la standardverdiene være uendret frem til en uttrykkelig operatørbeslutning sier noe annet.

### Diagnostisering av tomgangsavbrudd

Når tomgangsvakten utløses, logger OmniRoute en linje med følgende format:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Søk med grep etter `Idle timeout: no data from` (eller koden `stream_idle_timeout` / feilnavnet `StreamIdleTimeoutError`). Leverandørsegmentet er det OmniRoute brukte for den aktuelle forespørselen (`codex`, en annen leverandør-ID eller `provider` hvis den er ukjent) — det er ikke alltid den bokstavelige strengen `codex`.

## Feilsøking

**`Error: wire_api = "chat" støttes ikke lenger`**
Fjern `wire_api = "chat"` fra konfigurasjonen. Angi `wire_api = "responses"`, eller utelat feltet (standardverdien har vært `"responses"` siden v0.138).

**`Error: model not found`**
Kontroller at modellen finnes i OmniRoute med riktig prefiks. Bruk `omniroute models list`, eller åpne `/dashboard/providers/<provider>`.

**`Authentication error`**
Bekreft at `OMNIROUTE_API_KEY` er eksportert: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex kontrollerer at miljøvariabelen finnes før den første forespørselen sendes. Eksporter
en reell nøkkel for beskyttede servere, eller en ikke-tom plassholder som
`OMNIROUTE_API_KEY=local` når din **lokale** OmniRoute-instans ikke
krever autentisering. Start skallet på nytt hvis du la den til i `~/.bashrc` eller `~/.zshrc`.

**`Connection refused`**
Kontroller at OmniRoute kjører, og at verten/porten i `base_url` er riktig for nettverket ditt (lokalt kontra Tailscale kontra VPS).

**Økten krasjer nær kontekstgrensen**
Angi `model_context_window` og `model_auto_compact_token_limit` eksplisitt. Se tabellen over kontekstvinduer ovenfor.

**Komprimering utløses for sent**
Senk `model_auto_compact_token_limit` til 80–85 % av vinduet. Angi aldri en verdi over 90 %.

**Profilen lastes ikke inn (`-p <name>` ignoreres uten varsel)**
Bekreft at filen finnes på `~/.codex/<name>.config.toml` (uten prefikset `profile-`). Kjør `ls ~/.codex/*.config.toml`.

**Langvarig Codex-oppgave avbrytes under kjøring / bytter konto mellom runder**
Se [Langvarige oppgaver](#long-running-tasks). Aktiver økttilknytning (TTL som er lengre enn oppgaven), og øk eller deaktiver `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Søk i OmniRoute-loggene med grep etter `Idle timeout: no data from`.
