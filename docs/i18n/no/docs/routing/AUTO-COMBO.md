## Automatisk ruting uten konfigurasjon (`auto/`-prefiks)

> **NYTT:** Ingen opprettelse av kombinasjoner er nødvendig. Bruk `auto/`-prefikset direkte i en hvilken som helst klient.

### Raske eksempler

| Modell-ID      | Variant   | Virkemåte                                                                      |
| -------------- | --------- | ------------------------------------------------------------------------------ |
| `auto`         | standard  | Alle tilkoblede leverandører, LKGP-strategi, balanserte vekter                 |
| `auto/coding`  | koding    | Kvalitetsorienterte vekter, egnet for kodegenerering                           |
| `auto/fast`    | rask      | Vektet utvalg med lav ventetid                                                 |
| `auto/cheap`   | billig    | Kostnadsoptimalisert ruting (laveste kostnad først)                            |
| `auto/offline` | frakoblet | Foretrekker leverandører med høyest tilgjengelig kvote                         |
| `auto/smart`   | smart     | Kvalitetsorientert + høyere utforskningsgrad (10 %) for bedre modelloppdagelse |
| `auto/lkgp`    | lkgp      | Eksplisitt LKGP (samme som standardvarianten `auto`)                           |
| `auto/chaos`   | kaos      | Feilinjiseringsvekter for testing av robusthet (kaosteknikk)                   |

### Sammensetning av kategori × nivå (`auto/<category>:<tier>`)

OpenRouter-lignende suffikser skiller **hvilken type rute** (kategori) fra **hvordan den skal optimaliseres** (nivå), slik at du fritt kan kombinere dem (#4235 fase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Kategorier** (filtrerer kandidatpoolen etter funksjonalitet): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` beholder modeller med støtte for bilder; `reasoning` beholder modeller for resonnering/tenkning.
- **Nivåer** (velger poengvekter/poolfilter): `fast` (rask levering) · `cheap` (alias `floor`, kostnadsbesparende) · `reliable` (tilstand for sikringsmekanisme + stabil ventetid) · `free` / `pro` (filtrerer poolen etter modellnivå via `classifyTier` — gratisnivå kontra premiumnivå).

| Eksempel               | Løses til                                                       |
| ---------------------- | --------------------------------------------------------------- |
| `auto/coding:fast`     | kodepool, vekter for lav ventetid                               |
| `auto/coding:cheap`    | kodepool, kostnadsoptimalisert (alias `auto/coding:floor`)      |
| `auto/reasoning:pro`   | kun modeller for resonnering/tenkning, premiumnivå              |
| `auto/vision`          | modeller med støtte for bilder (intet nivå → balanserte vekter) |
| `auto/multimodal:free` | modeller med multimodal støtte, kun gratisnivå                  |

Enhver gyldig `auto/<category>[:<tier>]` løses ved behov; et kuratert delsett annonseres i `/v1/models` og kontrollpanelet (`AUTO_SUFFIX_VARIANTS` i `open-sse/services/autoCombo/builtinCatalog.ts`). Filtreringen er **fail-open** — hvis ingen tilkoblede modeller samsvarer med en begrensning, brukes hele poolen slik at rutingen aldri slutter å fungere. Kjernen for poengberegning (`combo.ts`) er uendret; kategori-/nivåfilteret brukes i `buildAutoCandidates`.

> **Direkte modellinformasjon:** egnetheten for automatisk ruting baseres på direkte **Arena ELO**-rangeringer + nivådata fra **models.dev** når flagget `ARENA_ELO_SYNC_ENABLED` er aktivert (ellers brukes det statiske egnethetskartet som reserve).

**Slik bruker du det:**

```bash
# Et hvilket som helst IDE- eller CLI-verktøy som støtter OpenAI-formatet
Base URL: http://localhost:20128/v1
API Key:  <din-endepunktnøkkel>

# Angi modellen slik i koden/konfigurasjonen:
model: "auto"                 # balansert standardvalg
model: "auto/coding"          # best for kodeoppgaver
model: "auto/fast"            # raskest tilgjengelig
model: "auto/cheap"           # billigst per token
```

**Dette skjer:**

1. OmniRoute oppdager `auto/`-prefikset i `src/sse/handlers/chat.ts`
2. Henter alle **aktive leverandørtilkoblinger** fra databasen
3. Filtrerer til dem som har gyldig legitimasjon (API-nøkkel eller OAuth-token)
4. Fastsetter modellen per tilkobling (`connection.defaultModel` eller leverandørens første modell)
5. Bygger en **virtuell kombinasjon** i minnet (lagres ikke i databasen)
6. Ruter ved hjelp av vektprofilen til den valgte varianten + LKGP-strategien

**Viktige egenskaper:**

- ✅ **Alltid aktiv:** Ingen bryter, opprettelse av kombinasjon eller konfigurasjon er nødvendig
- ✅ **Dynamisk:** Gjenspeiler automatisk leverandørene som er tilkoblet for øyeblikket
- ✅ **Øktstilhørighet:** LKGP sørger for at den sist vellykkede leverandøren prioriteres
- ✅ **Støtte for flere kontoer:** Hver leverandørtilkobling blir en separat kandidat
- ✅ **Ingen databaseskriving:** Den virtuelle kombinasjonen finnes bare for forespørselen, uten kostnader knyttet til vedvarende lagring

### Kandidatkontroll per nøkkel (#7819, nivå 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = suffikset etter `auto/`, eller
den bokstavelige verdien `auto` for basiskanalen) er et **skrivebeskyttet** endepunkt som viser den
gjeldende kandidatpoolen til en `auto/*`-kanal, supplert med direkte informasjon om tilgjengelighet, ved å gjenbruke
eksisterende robusthetsavlesninger (aldri rå `state` fra sikringsmekanismen):

- leverandørens sikringsmekanisme — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- nedkjøling av tilkobling — `rateLimitedUntil` / `testStatus` i den løste
  `provider_connections`-raden
- modellsperring — `isModelLocked(provider, connectionId, model)`

Hver kandidat inneholder også denne API-nøkkelens `excluded`-flagg. Ekskluderinger lagres
per API-nøkkel (`auto_candidate_overrides`-tabellen, migrering `128`) — OmniRoute er
enkeltleietaker uten noen `users`-tabell, så `apiKeyId` er den nærmeste reelle identiteten
per anroper — og håndheves ved kandidatpoolens kontrollpunkt i
`open-sse/services/autoCombo/virtualFactory.ts` via den rene, enhetstestede
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Filteret er **fail-open**: En manglende apiKeyId/kanal eller en mislykket databaseoppslag lar begge
poolen forbli ufiltrert, slik at en operatør uten konfigurerte overstyringer får en ruting som er
byte-for-byte identisk med før denne funksjonen.

**Utsatt til en oppfølgingssak:** vekter per kandidat + eksplisitt rekkefølge (nivå 3
— mates inn i de eksisterende vektede/prioriterte strategiforløpene) og låsing til en bestemt
`combo.ts`-strategi per `auto/*`-kanal (nivå 4). Se planen i #7819 for det åpne
spørsmålet om overstyringer bør forbli per API-nøkkel eller bli globale, gitt
én-leietaker-modellen.

**Bak kulissene:**

```txt
Forespørsel: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts oppdager prefikset
   ↓
createVirtualAutoCombo('coding') → candidatePool fra aktive tilkoblinger
   ↓
handleComboChat (samme motor som lagrede kombinasjoner)
   ↓
Automatisk poengberegning velger beste leverandør/modell per forespørsel
```

**Implementasjonsfiler:**

| Fil                                                       | Formål                                                |
| --------------------------------------------------------- | ----------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Prefiksparser (`parseAutoPrefix`)                     |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Oppretter virtuelle `AutoComboConfig`-objekter        |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Testtilkobling for simulering av leverandørregisteret |
| `src/sse/handlers/chat.ts`                                | Integrasjon: kortslutning for auto-prefiks            |
| `src/shared/constants/providers.ts`                       | Systemoppføringen `SYSTEM_PROVIDERS.auto`             |

## Kombinasjonsnavn som samsvarer med en reell modell-ID

En kombinasjon der `name` er identisk med en ren modell-ID (f.eks. en kombinasjon med navnet
`gpt-5.5`), er et **tilsiktet og støttet mønster**, ikke en feil: Det er
mekanismen for reservetilbydere per modell-ID som er dokumentert i
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Fordi kombinasjoner
slås opp før rene modell-ID-er
(`getComboForModel()` i `src/sse/services/model.ts`), rutes en forespørsel om den rene
ID-en `gpt-5.5` gjennom kombinasjonens mål (f.eks.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) i stedet for direkte til
én enkelt tilbyder — dette gjenbruker prioriteten der kombinasjonen behandles før omskriving, som ble laget for
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227), og er
regresjonstestet av `tests/unit/responses-combo-resolution-3227.test.ts` og
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Oppretting eller endring av navnet på en kombinasjon til et navn som skjuler en reell modell-ID, blir
**aldri avvist** — det ville ødelegge denne dokumenterte arbeidsflyten. I stedet
legger `POST /api/combos` og `PUT /api/combos/[id]` (#8530) til et ikke-blokkerende
`warning`-felt i svaret når det (nye) navnet kolliderer med en reell
modell-ID:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Ved oppstart logger `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) også en énlinjes `[STARTUP]`-advarsel
som lister opp alle eksisterende kombinasjoner som skjuler en modell-ID, slik at operatører som
gjør dette ved et uhell (i stedet for med hensikt, som beskrevet i #6940), får et varsel.
Hjelpefunksjonen for registrering finnes i `src/lib/combos/modelNameCollision.ts`.

## Kalle en egendefinert kombinasjon fra en klient

Lagrede kombinasjoner (Innstillinger → Kombinasjoner) brukes bare når klienten sender kombinasjonens **nøyaktige navn** i `model`-feltet — det finnes ingen omtrentlig eller delvis samsvaring av kombinasjonsnavnet, og prefikset `auto/` er ikke involvert. Oppslagsrekkefølge (`getComboForModel()` i `src/sse/services/model.ts`):

1. nøyaktig samsvar med kombinasjonsnavnet (`model: "my-combo"`),
2. `combo/<name>`-prefiks (`model: "combo/my-combo"`),
3. glob-tilordninger fra modell til kombinasjon (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

To vanlige fallgruver:

- **`auto` bruker ikke kombinasjonene dine.** `auto`/`auto/*` bygger sitt eget konfigurasjonsfrie utvalg av kandidater og bruker bare lagrede kombinasjoner hvis en kombinasjon bokstavelig talt heter `auto` (anbefales ikke). For å rute gjennom en kombinasjon må du sende det nøyaktige navnet — ikke `auto`.
- **`openrouter/auto` er et reelt, betalt OpenRouter-produkt** («Auto Best Available»), ikke et OmniRoute-alias. Det er den eneste statiske modelloppføringen i OpenRouter-registeret (`open-sse/config/providers/registry/openrouter/index.ts`) og faktureres separat. Bruk Innstillinger → Ruting → Skjul betalte modeller for å utelate det fra `auto`-utvalg.

Se [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) og [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) for den opprinnelige forvirringen som dette dokumenterer.

## Slik fungerer det (lagrede Auto-Combo-kombinasjoner)

Auto-Combo-motoren velger dynamisk den beste leverandøren/modellen for hver forespørsel ved hjelp av en **poengfunksjon med 16 faktorer** (definert i `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Standardvektene summeres til `1.0`; egendefinerte vekter normaliseres på nytt av `normalizeScoringWeights()`. To av de seksten — `cacheAffinity` og `resetWindowAffinity` — har en standardvekt på `0`; `reliability` har `0` i `DEFAULT_WEIGHTS`, men `0.03` i generiske pakker og `0.04` i `reliability-first`, mens `quality` har `0.02` i pakker (`0.03` i `quality-first`): De beregnes fortsatt for hver kandidat, og `cacheAffinity` styrer deduplisering av promptbufferen utenfor poengberegningen. Faktorene med standardvekt null påvirker dermed ikke resultatet som standard, mens de gjør det i pakkene.

![Auto-Combo-poengberegning med 16 faktorer](../diagrams/exported/auto-combo-scoring.svg)

> Kilde: [diagrams/auto-combo-scoring.mmd](../diagrams/auto-combo-scoring.mmd) (generer på nytt via `npm run docs:render-diagrams`). Filnavnet er historisk; kildefilen og det gjengitte diagrammet viser alle de 16 faktorene som er deklarert i `DEFAULT_WEIGHTS`.

| Faktor                | Standardvekt | Beskrivelse                                                                                                                                                                                                                                |
| :-------------------- | :----------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quota`               | 0.1429       | Gjenværende kvote / margin til hastighetsbegrensning [0..1]                                                                                                                                                                                |
| `health`              | 0.1605       | Helsetilstandspoeng fra kretsbryteren (CLOSED=1.0, HALF_OPEN=0.5, OPEN=0.0)                                                                                                                                                                |
| `costInv`             | 0.1429       | Invers **blandet** kostnad (60 % pris for inndata-tokener + 40 % pris for utdata-tokener, normalisert) — billigere = høyere poengsum                                                                                                       |
| `latencyInv`          | 0.1143       | Invers p95-latens normalisert mot kandidatgruppen — raskere = høyere poengsum                                                                                                                                                              |
| `taskFit`             | 0.0762       | Egnethet for oppgavetype (koding, gjennomgang, planlegging, analyse, feilsøking, dokumentasjon)                                                                                                                                            |
| `stability`           | 0.0476       | Variansbasert stabilitet fra standardavviket i latens — en kandidat med sterkt varierende svartid får lavere poengsum                                                                                                                      |
| `tierPriority`        | 0.0476       | Prioritet for kontonivå — Ultra=1.0, Pro=0.67, Standard=0.33, Free=0.0                                                                                                                                                                     |
| `tierAffinity`        | 0.0476       | Samsvar mellom kandidatens nivå og nivået som anbefales i manifestet                                                                                                                                                                       |
| `specificityMatch`    | 0.0476       | Samsvar mellom forespørselens spesifisitet (hint i manifestet) og modellnivået                                                                                                                                                             |
| `contextAffinity`     | 0.0476       | Samsvar mellom forespørselens behov for kontekstvindu og modellens kontekstvindu                                                                                                                                                           |
| `sessionAvailability` | 0.0476       | Tilgjengelighet av OAuth-økten for kandidattilkoblingen i denne økten (`getOAuthSessionAvailability()`; tilkoblinger uten OAuth får poengsummen 1.0)                                                                                       |
| `connectionDensity`   | 0.0476       | Fordeler belastningen på tvers av tilkoblinger fra samme leverandør (motvirker konsentrasjon)                                                                                                                                              |
| `cacheAffinity`       | 0.00         | Rendezvous-hash-affinitet mot tilkoblingen som mest sannsynlig allerede inneholder denne forespørselens prefiks i promptbufferen (`open-sse/services/combo/promptCacheAffinity.ts`); deaktivert som standard (#8008)                       |
| `resetWindowAffinity` | 0.00         | Vekting mot tilkoblinger med et gunstig vindu for tilbakestilling av kvoten (deaktivert som standard)                                                                                                                                      |
| `quality`             | 0.03         | Tilbakemeldingsdrevet signal for utdatakvalitet fra kvalitetsmåleren for rutingshendelser; kandidater uten observasjoner får en nøytral verdi på 0.5                                                                                       |
| `reliability`         | 0.00         | Observert andel vellykkede forespørsler, `1 - failureRate`, basert på 24 timers brukshistorikk med en nedre grense på ti målinger (ellers brukes sanntidsmålinger); kandidater uten observasjoner får verdien 1.0. Deaktivert som standard |

**Sum:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0`, som deklarert i `DEFAULT_WEIGHTS`; brukerkonfigurerte vekter normaliseres på nytt til en fordeling av `normalizeScoringWeights()` før poengberegningen.

### Semantikk for `weighted`

`weighted` er en **proporsjonal tilfeldig trekning per forespørsel**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ikke en utjevner:

- Hver forespørsel trekker **ett** trinn med sannsynligheten `weight / totalWeight`; de gjenværende trinnene
  sorteres etter synkende vekt som reservekjede for den aktuelle forespørselen.
- Et trinn med vekt `0` (eller manglende vekt) blir **aldri trukket** så lenge et annet trinn har en
  vekt > 0 — det kan bare fungere som reserve etter at det trukne trinnet mislykkes. Bare når **alle**
  vektene er 0, blir valget uniformt.
- Trinn der alle målene er utilgjengelige — leverandørens kretsbryter er `OPEN`, forbindelsen
  er i nedkjølingsperiode, modellen er sperret — fjernes fra trekningen før den gjennomføres
  (`open-sse/services/combo/targetResolution.ts`), slik at ett enkelt friskt trinn midlertidig kan
  vinne hver forespørsel.
- `stickyWeightedLimit` (kombinasjonskonfigurasjon, standardverdi `1` = av) låser det trukne trinnet i så mange
  påfølgende vellykkede forsøk før det trekkes på nytt.

Bruk `round-robin` for streng rotasjon; like vekter med `weighted` gir statistisk — ikke
streng — balanse.

## Fusjonsstrategi

`fusion` er den eneste strategien som **ikke** velger ett enkelt mål. Den sender forespørselen
til **alle panelmodellene parallelt**, og deretter sammenfatter en konfigurerbar **dommermodell**
ett endelig svar fra alle panelsvarene. Portert fra oppstrømsprosjektet `decolua/9router`
(OpenRouters Fusion-design); implementasjonen finnes i `open-sse/services/fusion.ts`.

Slik fungerer det:

0. **Forbikobling for verktøybruk** — en forespørsel som inneholder en ikke-tom `tools`-matrise der
   `tool_choice` ikke uttrykkelig er satt til `"none"`, hopper over panelet helt: den rutes direkte til
   én enkelt modell (den konfigurerte dommeren eller `panel[0]`), med `tools`/`tool_choice`
   videresendt uendret. Panelmedlemmene har ikke tilgang til verktøy, og dommerens
   sammenfattingsinstruks fraråder generering av verktøykall, slik at agentbaserte klienter og klienter
   som bruker verktøykall, får en reell avgjørelse om verktøykall i stedet for sammenfattet prosa (#6771).
1. **Utsending** (bare forespørsler uten verktøy) — forespørselen sendes til alle panelmodellene
   samtidig, med strømming tvangsdeaktivert og verktøy fjernet (dommeren trenger fullstendig
   prosa for å kunne sammenfatte).
2. **Innsamling med quorumfrist** — så snart `minPanel` svar har ankommet, starter en kort
   fristtidsmåler for etternølerne, og deretter fortsetter fusjonen med det som er samlet inn.
   Dette begrenser hvor mye den tregeste modellen påvirker den totale responstiden, innenfor en absolutt tidsavbruddsgrense.
3. **Dommersammenfatting** — panelsvarene anonymiseres (`Source 1`, `Source 2`, … — slik at
   dommeren vurderer innholdet, ikke modellmerket) og overleveres til dommeren, som analyserer
   konsensus / motsetninger / delvis dekning / unik innsikt / blindsoner, og deretter
   skriver **ett** autoritativt svar. Dommerkallet beholder klientens opprinnelige
   `stream`-flagg og verktøy, slik at strømming og etterfølgende verktøybruk fortsatt fungerer.
4. **Robust degradering** — 0 panelsvar → `503`; nøyaktig 1 gjenværende svar → dette svaret
   returneres direkte (ingenting å sammenfatte); et panel med én modell svarer direkte.

Et panelmedlem kan også være et `combo-ref`-trinn (`{kind: "combo-ref", comboName: "..."}`) som refererer
til en annen kombinasjon — det løses som **én svart boks-panelstemme** (en fullstendig rekursiv videresending til
den refererte kombinasjonen, ikke en utsending til kombinasjonens egne mål), med den samme dybde-/syklusbeskyttelsen
som alle andre strategier som bruker combo-ref, allerede benytter (#6764).

Konfigureres i kombinasjonens `config`-blob (ingen skjemamigrering — den gjenbruker den eksisterende

| :--------------------------------------- | :------- | :----------------- | :---------------------------------------------------------------------------------------------- |

| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`            | Absolutt grense som hindrer at én fastlåst modell forsinker forespørselen                       |

## Virtuell Auto-Combo-fabrikk

Auto Combo-motoren krever ikke forhåndsdefinerte kombinasjoner. I stedet bygger `open-sse/services/autoCombo/virtualFactory.ts` kandidater fortløpende:

1. Henter `getProviderConnections({ isActive: true })` (alle aktiverte tilkoblinger)
2. Filtrerer til dem med gyldig legitimasjon (API-nøkkel eller et OAuth-token som ikke er utløpt, via `hasUsableOAuthToken()`)
3. Kryssrefererer med `getProviderRegistry()` for modelltilgjengelighet og priser
4. Bygger en `VirtualAutoComboCandidate` for hver tuppel `(provider, model, connection)`
5. Velger `connection.defaultModel` (eller den første modellen i registeret) som mål for videresending
6. Poengsetter hver kandidat ved hjelp av `scorePool()` med 16 faktorer og variantens vektpakke
7. Returnerer den resulterende minnebaserte `AutoComboConfig` til `handleComboChat()` — lagres aldri i databasen

Dette betyr at **tillegg av en ny leverandør med `auto/*` aktivert automatisk utvider kandidatpoolen** — ingen manuell redigering av kombinasjoner er nødvendig. Den virtuelle kombinasjonen bygges på nytt for hver forespørsel, slik at nylig tilføyde tilkoblinger eller tilkoblinger som nylig har blitt friske, tas i bruk umiddelbart.

## Selvhelbreding

- **Midlertidig ekskludering**: Poengsum < 0.2 → ekskludert i 5 min (progressiv tilbakekobling, maks. 30 min)
- **Bevissthet om effektbryter**: OPEN → automatisk ekskludert; HALF_OPEN → testforespørsler
- **Hendelsesmodus**: >50 % OPEN → deaktiver utforsking, maksimer stabiliteten
- **Gjenoppretting etter nedkjøling**: Etter ekskludering er den første forespørselen en «test» med redusert tidsavbrudd

## Bandit-utforsking

5 % av forespørslene (konfigurerbart) rutes til tilfeldige leverandører for utforsking. Deaktivert i hendelsesmodus.

## API

Det finnes **ikke noe dedikert `POST /api/combos/auto`-endepunkt** — Auto-Combo brukes på to måter:

1. **Uten konfigurasjon (anbefalt):** Send en hvilken som helst forespørsel om chatfullføring med `model: "auto"` eller `model: "auto/<variant>"`. Den virtuelle fabrikken bygger kombinasjonen for hver forespørsel — ingen lagring eller API-kall er nødvendig.

2. **Lagret kombinasjon med `strategy: "auto"`:** Opprett en vanlig kombinasjon via `POST /api/combos`, og angi `strategy: "auto"` sammen med `config.auto.weights` / `config.auto.candidatePool`. Den samme poengsettingsmotoren brukes; kombinasjonen lagres i `combos` og kan gjenbrukes etter ID.

For oppdagelse viser `GET /api/combos/auto` alle varianter med den beregnede kandidatpoolen samt `context_length` / `max_output_tokens` — MAKSIMUM på tvers av vinduene i kandidatpoolen. Klienter (f.eks. opencode-programtillegget) må annonsere disse verdiene i stedet for `0`: En kontekst på null deaktiverer opencodes automatiske komprimering fullstendig, slik at økter vokser helt til gatewayens tømming av historikken ødelegger konteksten. MAKSIMUM er trygt å annonsere fordi Auto-Combos forhåndsfilter for kontekst ruter overdimensjonerte forespørsler til kandidater med store vinduer.

# Lagret automatisk kombinasjon via det vanlige kombinasjonsendepunktet

### Strategier for automatisk ruting

Lagrede kombinasjoner med `strategy: "auto"` kan angi `config.routerStrategy` (eller eldre
`config.auto.routerStrategy`) til én av følgende:

- `rules` — standard vektet poengsetting
- `score` — velger den høyeste konfigurerte vektede poengsummen. Ved helt lik poengsum bevares den konfigurerte
  kandidatrekkefølgen; den eksisterende `explorationRate` gjør utvalg fra hele den rangerte poolen.
- `cost` / `eco` — rimeligste friske leverandør
- `latency` / `fast` — laveste p95-latens med straff for lav pålitelighet
- `sla-aware` / `sla` — foretrekker kandidater som oppfyller SLO-er for p95-latens, feilrate og valgfrie
  kostnader
- `lkgp` — sist kjente fungerende leverandør først

### Ruterstrategier i detalj

Auto-Combo-motoren tilbyr 6 utskiftbare **RouterStrategy**-implementasjoner som
du kan bytte mellom via `config.routerStrategy` (eller den eldre `config.auto.routerStrategy`).
Hver strategi velger én leverandør fra kandidatpoolen basert på en `RoutingContext`
(oppgavetype, verktøy-/synshint, tokenestimat, valgfri SLA-policy og valgfri
sist kjente fungerende leverandør).

#### 1. `rules` (standard) — vektet poengsetting med 16 faktorer

Pakker inn den eksisterende poengsettingsmotoren. Filtrerer bort kandidater med
effektbryteren satt til `OPEN`, kjører deretter `scorePool()` med gjeldende oppgavetype og `getTaskFitness()`,
og velger leverandøren med høyest poengsum.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Når den bør brukes**: Standard. Bruk den når du ønsker en balansert avveining mellom alle signalene.

**Alias**: `rules` (ingen alias)

---

#### 2. `cost` / `eco` — rimeligste friske leverandør

Sorterer kandidatpoolen etter `costPer1MTokens` (stigende) og velger den rimeligste.
Filtrerer først bort kandidater med `OPEN`.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Når den bør brukes**: Kostnadssensitive arbeidsbelastninger, satsvis behandling eller bakgrunnsjobber.

**Alias**: `cost`, `eco`

---

#### 3. `latency` / `fast` — laveste p95-latens med straff for lav pålitelighet

Sorterer etter `p95LatencyMs + (errorRate * 1000)`. Straffen for feilrate sikrer at
upålitelige leverandører rangeres lavere, selv om den nominelle latensen deres er lav.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Når den bør brukes**: Latensfølsomme arbeidsbelastninger som sanntidschat, autofullføring eller
interaktive kodeassistenter.

**Aliaser**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — overholdelse av SLO-er for latens/feil/kostnad

Poengberegner hver kandidat basert på hvor godt den oppfyller den konfigurerte SLO-policyen:

| Faktor           | Vekt | Formel                                               |
| ---------------- | ---- | ---------------------------------------------------- |
| Latenspoeng      | 35%  | `threshold / max(value, ε)`                          |
| Feilpoeng        | 35%  | `threshold / max(value, ε)`                          |
| Tilstandspoeng   | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)    |
| Kostnadspoeng    | 10%  | `threshold / max(value, ε)` eller invers normalisert |
| Stabilitetspoeng | 5%   | invers normalisert standardavvik for latens          |

Når `hardConstraints: true`, sorteres kandidatene primært etter **bruddpoeng**
(hvor mye de overskrider en SLO), og deretter etter samlet poengsum. Ellers brukes bare
den samlede poengsummen.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... beregner poeng for hver kandidat mot policyen: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA-felter** (angis i kombinasjonskonfigurasjonen):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Når den bør brukes**: Produksjonsarbeidsbelastninger med strenge budsjetter for latens, feilrate eller kostnad.

**Aliaser**: `sla-aware`, `sla`

#### 5. `lkgp` — sist kjente gode leverandør først

Prøver den **sist kjente gode leverandøren** først (hvis angitt), og faller deretter tilbake til
`rules`-strategien. Nyttig for øktfasthet — samme leverandør håndterer
oppfølgingsforespørsler i en samtale.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fall tilbake til rules-strategien
    return getStrategy("rules").select(pool, context);
  }
}
```

**Når den bør brukes**: Samtaler med flere meldingsrunder der du ønsker at samme leverandør skal håndtere
oppfølgingsforespørsler (f.eks. for hurtigbufring, kontekstkontinuitet eller konsekvent prising).

**Alias**: `lkgp` (ingen alias)

### Egendefinerte ruterstrategier

Du kan registrere din egen implementasjon av `RouterStrategy` via det offentlige API-et:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Ruterlogikken din her
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

Bruk den deretter:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## Oppsummering av Auto-varianter

Når vi inkluderer den rene `auto` (standard) samt de 6 `AutoVariant`-verdiene som er deklarert i `autoPrefix.ts`, finnes det **7 modell-ID-er som kan startes**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` selv inneholder 6 verdier; det 7. alternativet er «ingen variant» — ren `auto` — som håndteres av `parseAutoPrefix()` som `variant: undefined`.)

## Hvordan nivåer passer inn i Auto-Combo

Poengfunksjonen med 16 faktorer (`open-sse/services/autoCombo/scoring.ts`) behandler nivåtilhørighet som to signaler: `tierPriority` (0.0476) og `tierAffinity` (0.0476). Se den kanoniske [tabellen over poengfaktorer](#how-it-works-persisted-auto-combos) ovenfor for hele settet med `DEFAULT_WEIGHTS` — overstyringene per pakke (ship-fast/cost-saver/quality-first/offline-friendly) er oppført i tabellen «Vektprofiler per pakke».

Nivået alene tvinger **ikke** Nivå 1 til å komme først — hvis ventetiden for Nivå 1 er dårlig eller forholdet mellom kostnad og kvalitet er suboptimalt, vinner Nivå 2. For å fremtvinge nivårekkefølge bruker du kombinasjonsstrategien `priority` og ordner leverandørene etter nivå.

For å gi Nivå 1 (abonnement) en sterk preferanse øker du vekten for `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Se `docs/marketing/TIERS.md` for nivådefinisjoner og klassifisering av leverandører.

## Testing og dekning

### Deterministisk matrise for rutingsbeslutninger (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` beviser rutings**beslutningen** for alle de 19 offentlige strategiene ende-til-ende gjennom den virkelige kombinasjonsflyten med en simulert oppstrømsleverandør. Dekningen inkluderer:

- Alle de 19 `ROUTING_STRATEGY_VALUES`-strategiene (ordnet, vektet, kostnad, kontekst, fusjon, …).
- `quota-share` (intern) ende-til-ende: DRR-rettferdighet + nedprioritering ved metning via det virkelige `selectQuotaShareTarget`-grensesnittet (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`).
- `context-relay`-dekning for universell overlevering på tvers av alle antall mål.

Denne testpakken kjøres i CI (`test:integration`-jobben) med `--test-concurrency=1` og `--test-force-exit`, slik at den er deterministisk og ikke krever aktive tilgangsopplysninger.

### Betinget direkte røykprøve (IKKE i CI — virkelige leverandører)

| Kommando                               | Hva den gjør                                                                                             |
| :------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Virkelig ruting i prosessen med `RUN_COMBO_LIVE=1`; tar et øyeblikksbilde av en aktiv OmniRoute-database |
| `npm run test:combo:live:vps`          | HTTP-kall mot en aktiv OmniRoute-server (angi `COMBO_LIVE_BASE_URL`)                                     |

Disse røykprøvene tester den virkelige kommunikasjonsflyten (kombinasjon → leverandør → fullføring). De er med hensikt utelatt fra CI fordi de krever aktive tilgangsopplysninger og VPS-tilgang.
