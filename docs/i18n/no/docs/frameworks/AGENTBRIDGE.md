AgentBridge er OmniRoutes MITM-proxy (Man-in-the-Middle), som fanger opp HTTPS-trafikk fra AI-agenter i IDE-er og omdirigerer den gjennom OmniRoutes enhetlige rutingmotor. Den støtter **10 IDE-agenter** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code og Trae (under utredning) — noe som gjør OmniRoute til MITM-proxyen med markedets bredeste dekning for AI-baserte kodeassistenter.

**Plassering i kontrollpanelet:** `/dashboard/tools/agent-bridge`
**Sidepanelgruppe:** Verktøy (etter Cloud Agents)
**Se også:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — overvåk all oppfanget trafikk i sanntid; `docs/security/MITM-TPROXY-DECRYPT.md` (git; ikke kompilert inn i `/docs`) — Linux-modusen for transparent dekryptering og oppfanging med TPROXY, styrt av ruten `/api/tools/agent-bridge/tproxy`.

## §1 Oversikt

### Hva er AgentBridge?

Når en IDE-agent (f.eks. GitHub Copilot, Cursor eller Claude Code) foretar et API-kall, kobler den seg direkte til den eksterne AI-leverandøren (OpenAI, Anthropic osv.). AgentBridge fanger opp denne forbindelsen transparent på TLS-nivå — uten at det kreves noen konfigurasjonsendringer i agenten — og skriver om forespørselen slik at den går gjennom OmniRoute.

Dette betyr at du kan:

- **Omdirigere enhver agent til enhver leverandør**: Kommuniserer Copilot med OpenAI? Omdiriger den til Anthropic Claude, Gemini eller en hvilken som helst av OmniRoutes 352 leverandører.
- **Bruke modelltilordninger**: `gemini-3-flash` → `claude-sonnet-4.7` transparent på håndteringsnivå.
- **Observere all agenttrafikk**: Hver oppfangede forespørsel publiseres i [Traffic Inspector](./TRAFFIC_INSPECTOR.md).
- **Bruke OmniRoutes robusthetsfunksjoner**: Kombinasjonsruting, kretsbrytere, reserveløsninger og kostnadssporing fungerer også for trafikk fra IDE-agenter.

## §2 Arkitektur

### 2.1 Komponentoversikt

```
IDE-agent (VS Code / Cursor / osv.)
    │  HTTPS (port 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS-omdirigering
    │
    ▼
src/mitm/server.cjs  (port 443, CJS-underprosess)
    │  løser mål basert på Host-headerens SNI
    │  genererer TLS-sertifikat per SNI signert av AgentBridge-CA-en
    ├── Treff i omgåelseslisten? → TCP-videresending (ingen dekryptering)
    ├── Mål treffes? → fetch → OmniRoute-ruter (port 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() på forespørselens innhold/headere
    │               ├── TrafficBuffer.push() — publiserer til Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── Ingen treff? → TCP-videresending (ingen dekryptering)
```

### 2.2 MITM-server (`src/mitm/server.cjs`)

Den sentrale MITM-serveren kjører som en Node.js CJS-underprosess (for å unngå å omskrive den eksisterende CJS-kodebasen). Den:

- Lytter på port 443 (krever privilegier eller `authbind`/`setcap`)
- Mottar CONNECT-tunneler fra operativsystemet (via DNS-omdirigering i `/etc/hosts`)
- Genererer TLS-sertifikater per SNI signert av AgentBridge-CA-en (`DATA_DIR/mitm/ca.crt`)
- Finner målagenten basert på Host-headeren via registeret `targets/index.ts`
- Sender videre til TypeScript-håndteringslaget via HTTP til `http://127.0.0.1:20128`

`TARGET_HOSTS` lastes fra `DATA_DIR/mitm/targets.json` (skrevet av `targets/index.ts` ved oppstart), noe som muliggjør dynamiske oppdateringer uten å starte CJS-serveren på nytt.

> **Rot-CA-modell (#6684).** Beskrivelsen ovenfor av sertifikater per SNI signert av en CA
> er den persistente rot-CA-modellen som ble lagt til i #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, som gjenbruker CA-/leaf-kryptografien som allerede er
> utprøvd for TPROXY i `src/mitm/tproxy/dynamicCert.ts`) — den erstatter det
> eldre statiske, selvsignerte leaf-sertifikatet (`src/mitm/cert/generate.ts`, fortsatt
> begrenset til bare antigravity-verter) som indikeres av et enkelt `server.crt`/`server.key`-par
> på disken. **Migreringsatferd**: En ny installasjon (uten tidligere
> `server.crt`) får rot-CA-modellen automatisk. En installasjon som allerede
> stolte på det gamle statiske leaf-sertifikatet, fortsetter å bruke det frem til operatøren angir
> `MITM_ROOT_CA_ENABLED=true` og starter broen på nytt (`src/mitm/cert/migration.ts`
> er den rene beslutningsfunksjonen — en betrodd MITM-CA som kan signere et leaf-sertifikat for
> **enhver** vert, er vesentlig kraftigere enn det gamle leaf-sertifikatet med fast SAN, så
> byttet skjer aldri i det stille for en installasjon som allerede er klarert). CA-sertifikatet installeres
> i samme `omniroute-mitm.crt`-plass i klareringslageret som det gamle leaf-sertifikatet brukte
> (`cert/install.ts::installCaCert`) — ingen opprydding av dobbel klarering er nødvendig.

### 2.3 Grunnhåndtering (`src/mitm/handlers/base.ts`)

Alle agenthåndterere utvider `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Beskyttede hjelpefunksjoner: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Hver håndterer kaller `hookBufferStart()` før videresending og `hookBufferUpdate()` når den er ferdig. Disse legger `InterceptedRequest`-oppføringer inn i `globalTrafficBuffer` (se [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Målregister (`src/mitm/targets/`)

Hver agent har en deklarativ målfil:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Registeret (`targets/index.ts`) eksporterer `ALL_TARGETS` og genererer `DATA_DIR/mitm/targets.json` ved oppstart.

### 2.5 Videresending og omgåelsesliste (`src/mitm/passthrough.ts`)

**Omgåelsesliste** (kontrolleres først og har forrang fremfor måltreff):

- Standardmønstre: bankverter, `.gov.`, OAuth-/SSO-leverandører (Okta, Auth0), osv.
- Brukermønstre: lagret i databasetabellen `agent_bridge_bypass`
- Omgåtte verter mottar en transparent TCP-tunnel — TLS dekrypteres **aldri**

**Standard videresending** (ingen måltreff og ikke i omgåelseslisten):

- Mottar også en TCP-tunnel — forbindelser brytes aldri
- Hindrer AgentBridge i å forstyrre generell HTTPS-trafikk i systemet

Rutingsrekkefølge:

```
omgåelsesliste → måltreff → videresending
```

### 2.6 Oppstrøms CA-sertifikat (`src/mitm/upstreamTrust.ts`)

For bedriftsnettverk med en egendefinert CA:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Når den er angitt, konfigureres den globale dispatcheren til `undici` med det ekstra CA-sertifikatet, slik at AgentBridge kan nå oppstrømsleverandører gjennom bedriftens proxyer for TLS-terminering.

### 2.7 Maskering av hemmeligheter (`src/mitm/maskSecrets.ts`)

Den uavhengige clean-room-skanneren brukes på forespørselsinnhold og legitimasjonsheadere
**før** de havner i Traffic Inspector-bufferen eller en logg. Den utfører én enkelt lineær gjennomgang:

- Tokener med prefiksene `sk-` / `ak-` / `pk-` (OpenAI-/Anthropic-stil)
- RFC 6750-legitimasjon av typen `Authorization: Bearer <token>`, med prioritet for hele tokenet
- Generiske, lange, ugjennomsiktige tokener (≥40 tegn), inkludert former med punktum og utfylling

`sanitizeHeaders()` konverterer beholdte navn til små bokstaver, slår sammen matriseverdier deterministisk, fjerner den
delte blokkeringslisten for hop-by-hop-/innrammingsheadere (inkludert proxy-autentisering), maskerer `cookie` og
`set-cookie` fullstendig og delegerer legitimasjonsverdier til skanneren.

## §3 Oppsett

### 3.1 Start/stopp MITM-serveren

Bruk AgentBridge-serverkortet på `/dashboard/tools/agent-bridge`:

| Handling                     | Beskrivelse                                                                             |
| ---------------------------- | --------------------------------------------------------------------------------------- |
| Start server                 | Starter `src/mitm/server.cjs` på port 443                                               |
| Stopp server                 | Avslutter underprosessen på en kontrollert måte                                         |
| Start server på nytt         | Stopper og starter serveren (tar i bruk endringer i målkonfigurasjonen)                 |
| Klarer sertifikatet          | Installerer `DATA_DIR/mitm/ca.crt` i operativsystemets klarerte sertifikatlager         |
| Last ned sertifikatet        | Laster ned `ca.crt` for manuell installasjon                                            |
| Generer sertifikatet på nytt | Oppretter et nytt CA-nøkkelpar (alle eksisterende sertifikater per agent blir ugyldige) |

### 3.2 Klarer sertifikatet

AgentBridge CA-sertifikatet må være klarert av operativsystemet før IDE-er godtar MITM-tilkoblingen.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Nøkkelring):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Du kan også bruke knappen «Klarer sertifikatet» i kontrollpanelet (den kjører riktig kommando for operativsystemet ditt, med en sudo-forespørsel om nødvendig).

#### Electron-baserte IDE-er ignorerer operativsystemets klarerte sertifikatlager (`NODE_EXTRA_CA_CERTS`)

Enkelte IDE-er — særlig **Antigravity IDE** og andre apper basert på Electron / VS Code — leveres med
sin egen Node.js-kjøretid som **ikke bruker operativsystemets klarerte sertifikatlager** for utgående
`fetch`/HTTPS. Det er tilstrekkelig å klarere CA-en på OS-/NSS-nivå for IDE-ens innebygde **bakende**
(f.eks. en Go-språkserver som bruker operativsystemets CA-pakke), men **Electron-grensesnittet** vil
fortsatt mislykkes med TLS — dette vises som at appen er _logget ut_ eller viser en _«tilkoblingsfeil»_,
selv om MITM-loggen viser at bakendens oppstartskall returnerer `200`. To trinn er
nødvendige, og begge er viktige:

1. Pek kjøretiden eksplisitt til CA-en:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Start IDE-en fra dette skallet.** Hvis den startes fra skrivebordsikonet / Dock / Start-menyen,
   arver den **ikke** skallvariablene, og `~/.config/environment.d/*.conf` trer først i kraft etter
   en ny grafisk innlogging. Avslutt IDE-en helt først — Electrons singleton-lås gjør at en ny
   oppstart bare fokuserer den eksisterende prosessen, og det nye miljøet ignoreres.

Trinnet ovenfor for klarering i operativsystemet + NSS er fortsatt nødvendig (Chromium-nettverksstakken som brukes av enkelte
autentiseringsflyter, leser NSS-lageret per bruker og har sine egne statiske pins for `*.googleapis.com` som en
lokalt klarert CA overstyrer). `NODE_EXTRA_CA_CERTS` dekker i tillegg Node-banen for `fetch`.

### 3.3 DNS-ruting

For hver agent du vil avskjære, må API-verten(e) dens løses til `127.0.0.1`. AgentBridge administrerer oppføringer i `/etc/hosts` automatisk når du slår DNS av eller på for en agent i oppsettsveiviseren.

Eksempel på `/etc/hosts`-oppføringer for GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Modelltilordning

Bruk modelltilordningstabellen i hvert agentkort til å definere kilde → mål-tilordninger:

| Kildemodell (agentens opprinnelige) | Målmodell (OmniRoute) |
| ----------------------------------- | --------------------- |
| `gpt-4o`                            | `claude-sonnet-4.7`   |
| `*` (jokertegn)                     | `claude-haiku-4.7`    |

Jokertegnet `*` tilordner enhver ukjent modell til det angitte målet. Lagres i tabellen `agent_bridge_mappings`.

> **Tips — finn agentens faktiske modell-ID-er.** En IDE kan sende modellnavn som avviker fra
> etikettene i brukergrensesnittet, og som endres mellom hovedversjoner. **Antigravity 2** sender for eksempel
> `gemini-3.1-pro-low`, `gemini-pro-agent` og `gemini-3.1-flash-lite` over forbindelsen — ikke
> `gemini-2.5-pro`, som vises i eldre dokumentasjon. Send én chatmelding uten en samsvarende tilordning: MITM
> logger den nøyaktige innkommende `model:`-verdien og videresender forespørselen. Tilordne denne bokstavelige verdien, så blir
> den neste forespørselen avskåret og rutet til målet ditt.

### 3.5 Risikovarsel

AgentBridge avskjærer legitimasjon (OAuth-tokener, API-nøkler) som IDE-en bruker til å autentisere seg mot oppstrømsleverandører. Disse blir **maskert før logging** (se §2.7), men er synlige for OmniRoutes MITM-lag. Første aktivering av hver agent viser et risikovarsel i et modalt vindu som kan lukkes.

### 3.6 Vedlikehold og diagnostikk

Kontrollpanelet viser et kort for **vedlikehold og diagnostikk** (`AgentBridgeMaintenanceCard`, i `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) som gjør operative MITM-ruter som tidligere ikke hadde noe brukergrensesnitt, tilgjengelige. Undertittelen er: _«Selvtest innhentingsflyten, fjern gjenværende systemtilstand og flytt oppsettet ditt mellom maskiner.»_ Klienthjelperne for kortet ligger i `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Knapp                       | Rute                                   | Hva den gjør                                                                                                                                                                                            |
| --------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Diagnostiser**            | `GET /api/tools/agent-bridge/diagnose` | Kjører selvtesten for opptakspipelinen og viser en rapport for hver kontroll (✓/✗ + utbedringstips).                                                                                                    |
| **Reparer**                 | `POST /api/tools/agent-bridge/repair`  | Tilbakestiller foreldreløs MITM-systemtilstand (DNS-forfalskningsoppføringer, rot-CA, systemproxy) etter et krasj eller SIGKILL. Idempotent — rapporterer «Ingenting å reparere» når tilstanden er ren. |
| **Fjern CA**                | `DELETE /api/tools/agent-bridge/cert`  | Fjerner tilliten til og sletter MITM-rot-CA-en fra operativsystemets tillitslager (eksplisitt, idempotent). Vises bare når CA-en er klarert; krever en innebygd «Fjern CA?»-bekreftelse.                |
| **Eksporter konfigurasjon** | `GET /api/tools/agent-bridge/config`   | Laster ned den portable konfigurasjons-JSON-en (se §3.7).                                                                                                                                               |
| **Importer konfigurasjon**  | `POST /api/tools/agent-bridge/config`  | Laster opp en tidligere eksportert konfigurasjons-JSON (se §3.7).                                                                                                                                       |

**Diagnostikkontroller** (`summarizeDiagnostics()` i `src/mitm/inspector/diagnostics.ts`). Ruten kjører den effektfulle testen for hver kontroll og mater de boolske verdiene inn i den rene oppsummeringsfunksjonen. Én samlet `healthy`-vurdering samt et tips for hver feil returneres:

| Kontrollnavn       | Hva den verifiserer                                        | Tips ved feil                                                                                                                                   |
| ------------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM-serverprosessen er aktiv                              | «MITM-serveren kjører ikke. Start den fra AgentBridge-fanen.»                                                                                   |
| `server-reachable` | MITM-serveren godtar tilkoblinger på porten sin (TCP-test) | «MITM-serveren godtar ikke tilkoblinger på porten sin. Kontroller at porten er ledig, og at du har rettigheter til å binde den.»                |
| `cert-exists`      | MITM-sertifikatet er generert på disken                    | «Det er ennå ikke generert noe MITM-sertifikat. Generer et fra AgentBridge-fanen.»                                                              |
| `cert-trusted`     | MITM-rot-CA-en finnes i operativsystemets tillitslager     | «MITM-rot-CA-en er ikke klarert av operativsystemets tillitslager, så TLS-avskjæring vil mislykkes. Klarer sertifikatet fra AgentBridge-fanen.» |
| `dns-configured`   | Målvertsnavn er forfalsket i `/etc/hosts`                  | «Målvertsnavn er ikke forfalsket i /etc/hosts, så trafikken når aldri proxyen. Aktiver DNS for agenten(e) du vil fange opp.»                    |

**Banner for foreldreløs tilstand:** Når siden oppdager tilstand som er etterlatt etter et krasj (DNS-forfalskning / CA / systemproxy), viser kortet et gult banner — _«En tidligere økt etterlot systemtilstand (DNS-forfalskning, CA eller systemproxy). Kjør Reparer for å rydde opp.»_ — og fremhever **Reparer**-knappen. `Repair` er applikasjonslagets motstykke til ProxyBridges `--cleanup`-flagg (det delegerer til `repairMitm()` i `src/mitm/manager.ts`).

> MITM-rot-CA-en forblir installert på tvers av stopp/start for å unngå gjentatte sudo-
> forespørsler (samme virkemåte som mitmproxy/Charles), så fjerning av den er en eksplisitt
> **Fjern CA**-handling i stedet for noe som skjer automatisk ved stopp.

### 3.7 Import/eksport av portabel konfigurasjon

AgentBridge kan serialisere den **operatørjusterbare** tilstanden til en versjonert JSON-blokk, slik at et oppsett kan replikeres på tvers av maskiner. Serialiseringsfunksjonen er `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), validert av `AgentBridgeConfigSchema`.

Eksporten inneholder nøyaktig tre deler (innebygde standardverdier eksporteres med hensikt **IKKE**, slik at import aldri dupliserer dem eller kommer i konflikt med dem):

| Felt             | Kilde                                                               | Merknader                                                                 |
| ---------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `bypassPatterns` | brukerdefinerte omgåelsesmønstre (`agent_bridge_bypass`)            | standardmønstre for banker/myndigheter/okta er utelatt                    |
| `customHosts`    | egendefinerte verter i Traffic Inspector (`inspector_custom_hosts`) | hver: `{ host, kind: "llm"\|"app"\|"custom", label? }`                    |
| `agentMappings`  | modelltilordninger per agent (`agent_bridge_mappings`)              | `{ [agentId]: [{ source, target }] }` for hver agent som har tilordninger |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Importvirkemåte** (`POST /api/tools/agent-bridge/config`): Omgåelsesmønstre og tilordninger per agent **erstattes i sin helhet**; egendefinerte verter legges til **idempotent** (`INSERT OR IGNORE`). Responsen rapporterer hvor mange av hver type som ble brukt:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Dette er **IKKE** med i konfigurasjonen: serverens kjørestatus, sertifikatbaner, DNS-status per agent, banen til den overordnede CA-en og TPROXY-innstillinger – dette er verts-/kjøretidstilstand, ikke portable innstillinger.

## §5 Sikkerhet

### Anvendte absolutte regler

| Regel                             | Anvendelse                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | Alle behandlerfeil renses før svar eller innføring i bufferen                                   |
| **#13** Overføring av skallmiljø  | Endringer i `/etc/hosts` bruker alternativet `env` — ingen strenginterpolering av baner         |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/agent-bridge/` er LOCAL_ONLY + SPAWN_CAPABLE — loopback håndheves før autentisering |

### Omgåelsesliste for sensitive verter

Omgåelseslisten sikrer at finansinstitusjoner, OAuth-/SSO-leverandører og andre sensitive verter **aldri dekrypteres**. TLS-trafikken deres passerer gjennom som en transparent TCP-tunnel — OmniRoute ser aldri klarteksten.

Standardmønstrene for omgåelse inkluderer:

- `*.bank.*`, `*.gov.*` (finans/offentlig sektor)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identitet)
- `*.apple.com`, `*.icloud.com` (Apple-systemtjenester)

Omgåelsesmønstre som brukeren legger til, lagres i tabellen `agent_bridge_bypass` og har forrang over alt annet.

### Maskering av hemmeligheter

`maskSecrets()` fra `src/mitm/maskSecrets.ts` brukes:

- På hver forespørselskropp før `TrafficBuffer.push()`
- På hver HTTP-header før logging eller kringkasting

Mønstre: tokener med prefiksene `sk-`/`ak-`/`pk-`, `Bearer`-tokener og generiske tokener med ≥40 tegn.

### Oppstrøms CA-sertifikat

Når `AGENTBRIDGE_UPSTREAM_CA_CERT` er angitt, leses filen ved oppstart. Hvis banen finnes, men filen ikke kan leses, logger AgentBridge en tydelig feil og nekter å starte (forhindrer stille TLS-feil i bedriftsmiljøer).

### Kjente begrensninger

- **Port 443 krever privilegier**: På Linux trenger AgentBridge `setcap 'cap_net_bind_service=+ep'` på Node-binærfilen, eller må kjøres via `authbind`. Oppsettsveiviseren viser operativsystemspesifikke instruksjoner.
- **IDE-en må startes på nytt**: Etter DNS-omdirigering må IDE-en startes på nytt for at den nye vertsoppløsningen skal tre i kraft.
- **Hardkodede OAuth-tokener**: Enkelte agenter (Kiro, Antigravity) lagrer OAuth-oppdateringstokener lokalt. Disse er transparente for AgentBridge — den ser Bearer-tokenet i hver forespørsel, og dette maskeres før logging.
- **Electron-grensesnitt trenger `NODE_EXTRA_CA_CERTS`**: IDE-er hvis grensesnitt kjører på en medfølgende Node-/Electron-kjøretid, ignorerer operativsystemets/NSS-ens klareringslager og må startes fra et skall der `NODE_EXTRA_CA_CERTS` er angitt (se §3.2). Symptom når dette mangler: IDE-backend autentiseres (MITM viser `200`-svar), men brukergrensesnittet forblir avlogget.
- **Flere installasjoner av samme IDE er uavhengige**: En systeminstallasjon (f.eks. `/usr/share/antigravity/antigravity`) og en brukerlokal «Full»-installasjon (f.eks. `~/AntigravityIDE_Full/antigravity-ide`) er separate prosesser med egne kjøretidsmiljøer — hver av dem må startes på nytt med CA-en injisert. Finn ut hvilken som kjører, ved hjelp av banen til binærfilen før omstart.
- **Identiteten angis av agentens systemprompt, ikke av den rutede modellen**: Når du tilordner en agents modell til en annen leverandør, hevder svaret fortsatt agentens opprinnelige identitet (f.eks. svarer Antigravity «Jeg drives av Gemini») fordi IDE-en injiserer dette i systemprompten. Bekreft den faktiske backend-tjenesten i `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), ikke ved å spørre modellen hvem den er.

## §6 Feilsøking

### Konflikt på port 443

Hvis en annen prosess allerede lytter på port 443 (webserver, VPN osv.):

```bash
lsof -i :443          # finn prosessen
sudo fuser -k 443/tcp  # tvangsavslutt (bruk med forsiktighet)
```

Alternativt kan du konfigurere en ikke-privilegert port i AgentBridge-innstillingene og sette opp omdirigeringsregler for `iptables` / `pf`.

### Sertifikatet er ikke klarert

Hvis IDE-en viser TLS-feil etter at AgentBridge er startet:

1. Kontroller at sertifikatet ble installert: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) eller `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Enkelte apper har sitt eget klareringslager (Firefox, Chrome på Linux). Kjør «Klarer sertifikat» på nytt, og kontroller det NSS-/Firefox-spesifikke sertifikatlageret.
3. Start IDE-en på nytt etter klareringen — aktive TLS-økter bruker den gamle klareringstilstanden.

### IDE-en er logget ut / viser «tilkoblingsfeil» til tross for en klarert CA

Symptom: Etter omdirigering av DNS og klarering av CA-en åpnes en Electron-basert IDE (f.eks. Antigravity)
som **utlogget** eller viser en autentiserings-/tilkoblingsfeil, selv om MITM-loggen viser at
oppstartskallene (`loadCodeAssist`, `fetchAvailableModels`, …) returnerer `200`.

Årsak: IDE-ens **medfølgende Node/Electron-kjøremiljø ignorerer operativsystemets klareringslager**. Den innebygde
bakenden (en Go-språkserver) klarerer operativsystemets CA og autentiserer, men Electron-brukergrensesnittet
gjør ikke det — derfor tror brukergrensesnittet at det er frakoblet.

Løsning (begge trinn): Eksporter `NODE_EXTRA_CA_CERTS=<ca.crt>` **og start IDE-en på nytt fra dette
skallet**, ikke fra skrivebordsikonet. Avslutt først IDE-en helt — Electrons singleton-lås innebærer
at en ny oppstart bare fokuserer på den eksisterende prosessen, og det nye miljøet ignoreres. Se §3.2.
Dette samsvarer med en åpen oppstrømsrapport der en frittstående agent fungerer gjennom en MITM, mens IDE-
varianten mislykkes med samme oppsett.

### DNS er ikke videreformidlet

Kontroller at `/etc/hosts` ble oppdatert:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Tøm DNS-hurtigbufferen:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE-en blir ikke oppdaget

Automatisk oppdagelse bruker vanlige installasjonsbaner. Hvis oppdagelsen mislykkes selv om IDE-en er installert:

- Kontroller om den binære IDE-filen ligger på en ikke-standard plassering
- Oppsettsveiviseren fungerer fortsatt — mislykket oppdagelse betyr bare at merket ikke viser installasjonsbanen

### Behandlerfeil (oppstrømsinnhenting mislykkes)

Hvis AgentBridge avskjærer forespørsler, men alle forespørsler mislykkes:

1. Kontroller at minst én leverandør er tilkoblet på `/dashboard/providers`
2. Kontroller OmniRoute-serverloggene: `APP_LOG_LEVEL=debug` i `.env`
3. Kontroller at `OMNIROUTE_BASE_URL` peker til riktig ruterendepunkt (standard: `http://127.0.0.1:20128`)

## §8 Veikart

### Undersøkelse av Trae

Trae er en relativt ny AI-kodingsassistent. Før en handler implementeres:

1. Identifiser binærfilen/utvidelsen i markedsplassene for VS Code / JetBrains eller som en frittstående app
2. Registrer trafikk med mitmproxy for å finne API-verter og endepunktstrukturer
3. Fastslå autentiseringsmekanismen
4. Vurder om man bør gå videre eller ikke, basert på bruksvilkårene og hvor lett API-et kan identifiseres

Frem til undersøkelsen er fullført, viser Trae-kortet i kontrollpanelet et «Under utredning»-merke med en «Rapporter gjennomførbarhet»-lenke. Handler-plassholderen i `src/mitm/handlers/trae.ts` kaster en strukturert `Not yet implemented`-feil.

### Agenter i etterslepet (MITM kreves — ingen støtte for egendefinert basis-URL)

Følgende verktøy støtter ikke egendefinerte basis-URL-er i sine nåværende versjoner, noe som gjør MITM til den eneste mulige avskjæringsmetoden. Vurdering av gjennomførbarhet gjenstår:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — separat fra Kiro IDE)
- **Cowork** (Anthropic desktop)

Merk: GitHub Copilot CLI ≥v1.0.19 støtter `COPILOT_PROVIDER_BASE_URL` — bruk direkte konfigurasjon i stedet for MITM for dette verktøyet.
