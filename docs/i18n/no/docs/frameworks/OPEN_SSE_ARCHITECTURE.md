> **Kort fortalt**: `open-sse/` er kjernemotoren for strømming som driver alle LLM-forespørsler i OmniRoute. Den inneholder rundt 1 400 filer som implementerer forespørselspipelinen, eksekveringsmoduler, tjenester, MCP-serveren og oversettelseslaget. Denne veiledningen forklarer hvordan delene henger sammen.

**Kilde:** `open-sse/` (arbeidsområdepakke, rundt 1 440 `.ts`-filer som ikke er testfiler)

## Hvorfor en separat arbeidsområdepakke?

`open-sse/` er et **frittstående arbeidsområde** i OmniRoute-monorepoet av flere grunner:

1. **Gjenbrukbarhet** — `open-sse` publiseres som `@omniroute/open-sse` på npm, slik at andre prosjekter kan bruke den uavhengig
2. **Tydelige grenser** — strømmemotoren er frikoblet fra det OmniRoute-spesifikke UI-/database-laget
3. **Ytelse** — motoren har ingen Next.js-avhengigheter, noe som gir raskere kaldstarter i CLI- og serverløse kontekster
4. **Versjonering** — `open-sse` kan lanseres etter sin egen tidsplan

```json
// package.json
"workspaces": ["open-sse"]
```

## Forespørselspipelinen

Alle LLM-forespørsler går gjennom en **pipeline med fem trinn**:

```
                              ┌──────────────┐
   HTTP-forespørsel            │  1. RUT      │   kombinasjonsoppløsning, modellvalg
   (Next.js-rute)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. OVERSETT │   formatkonvertering (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. UTFØR    │   leverandøreksekvering, HTTP, nytt forsøk, kretsbryter
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STRØM    │   SSE-transformering, mottrykk
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. REGISTRER│   bruksregistrering, kallogg, feilklassifisering
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP-respons (SSE eller JSON)
```

### Trinn 1: Ruting (services/combo.ts)

**Inngangspunkt**: `handleComboChat()` i `services/combo.ts`

Oppløser forespørselen til en konkret `(provider, model, account, credentials)`-tuppel:

- Slå opp kombinasjonen etter ID (eller bygg en virtuell kombinasjon for `auto/*`-modeller)
- Bruk rutingstrategien (prioritet, vektet, round-robin osv.)
- Filtrer bort leverandører som ikke er friske (kretsbryter)
- Velg det neste levedyktige målet

For `auto/*`-modeller gjør dette trinnet også følgende:

- Kjører algoritmen for **poengberegning med 16 faktorer** (`services/autoCombo/`)
- Velger et `provider+model`-par basert på helse, kostnad, latens osv.

### Trinn 2: Oversettelse (translator/)

Hvis kildeformatet (f.eks. OpenAI) er forskjellig fra målformatet (f.eks. Claude), blir forespørselen **oversatt**:

- Systemprompt → systemmelding
- Verktøydefinisjoner → leverandørspesifikt verktøyformat
- Parametere for resonnering/tenkning → leverandørspesifikke ekvivalenter
- Normalisering av meldingsroller (`developer` → `system` for andre enn OpenAI)

`translator/index.ts` eksponerer:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Trinn 3: Utførelse (executors/)

**Inngangspunkt**: `getExecutor(providerId).execute(request, options)`

Alle leverandører bruker `DefaultExecutor` (`executors/default.ts`) via reservemekanismen i `getExecutor()`-fabrikken. Eksekveringsmodulen:

- Bygger oppstrøms-URL-en (`buildUrl()`)
- Legger til leverandørspesifikke headere (`buildHeaders()`)
- Transformerer forespørselskroppen (`transformRequest()`)
- Sender HTTP-forespørselen med nye forsøk og eksponentiell tilbakeventing
- Håndterer autentiseringsoppdatering ved behov (OAuth-leverandører)

Alle eksekveringsmoduler utvider `BaseExecutor` (`executors/base.ts`, 1170 kodelinjer), som tilbyr:

- Felles logikk for nye forsøk
- Proxy-integrasjon
- Kretsbryterintegrasjon
- Kroker for bruksregistrering

### Trinn 4: Strømming (utils/stream.ts)

For strømmesvar returnerer eksekveringsmodulen en **ReadableStream**. Håndtereren:

- Sender data gjennom en SSE-transformering (`createSSETransformStreamWithLogger`)
- Bruker heartbeat-signaler for å oppdage døde forbindelser
- Håndterer frakobling av klienten på en kontrollert måte (`pipeWithDisconnect`)
- Transformer SSE → JSON for klienter uten strømmestøtte

For svar uten strømming returnerer eksekveringsmodulen et tolket JSON-objekt som sendes videre uendret.

### Trinn 5: Registrering (services/usage.ts)

Etter svaret (vellykket eller mislykket) registreres bruken:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` fra svaret
- `cost_usd` beregnet fra prisdata
- `latency_ms`, `status`, `error_class` ved feil
- Lagres i tabellen `usage_history`

Artefakter fra kalloggen (hvis aktivert) skrives til `${DATA_DIR}/call_logs/`.

## Dypdykk i nøkkelfiler

### chatCore.ts (5977 linjer)

Den **viktigste forespørselshåndtereren**. Til tross for størrelsen har den en tydelig struktur:

```ts
// Pseudostrukturen til chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autentisering + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validering av innholdet
  const body = await parseRequestBody(request);

  // 3. Formatgjenkjenning + oversettelse
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Kombinasjonsruting
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Fortsett til neste mål
    }
  }

  // 5. Reserveløsning for nødstilfeller
  return await emergencyFallback(body);
}
```

Til tross for at den er én enorm funksjon, er den organisert i **kommenterte seksjoner** som tilsvarer prosessen med fem trinn.

### combo.ts (4456 kodelinjer)

**Rutingmotoren** som løser opp en kombinasjon til en ordnet liste med mål.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Støtter **19 rutingstrategier** (se `src/shared/constants/routingStrategies.ts`):

| Strategi            | Virkemåte                                                                       |
| ------------------- | ------------------------------------------------------------------------------- |
| `priority`          | Ordnet liste med første mål først                                               |
| `weighted`          | Sannsynlighetsbasert etter vekten til hvert mål                                 |
| `round-robin`       | Gå gjennom målene i rekkefølge                                                  |
| `context-relay`     | Overfør kontekst mellom mål                                                     |
| `fill-first`        | Fyll kvoten før du går videre til neste                                         |
| `p2c`               | Velg den beste av to alternativer                                               |
| `random`            | Uniformt tilfeldig                                                              |
| `least-used`        | Velg målet med færrest nylige brukstilfeller                                    |
| `cost-optimized`    | Billigste friske mål først                                                      |
| `reset-aware`       | Tar hensyn til leverandørens tilbakestillingsvinduer                            |
| `reset-window`      | Ruting basert på tilbakestillingsvinduer                                        |
| `headroom`          | Størst gjenværende kvotemargin først                                            |
| `strict-random`     | Virkelig uniformt (ingen kvalitetsvekting)                                      |
| `auto`              | Bruk poengberegning med 16 faktorer (`autoCombo/`)                              |
| `lkgp`              | Sist kjente fungerende leverandør først                                         |
| `context-optimized` | Best for forespørsler med lang kontekst                                         |
| `fusion`            | Send parallelt til et panel, og syntetiser deretter via en dommer (`fusion.ts`) |

## Eksekverere (75+ filer)

Én fil per leverandør. Alle utvider `BaseExecutor` og overstyrer det som er forskjellig.

### Vanlige mønstre

Leverandører løses via `getExecutor(providerId)`, som returnerer den konfigurerte eksekvereren. OpenAI/Anthropic-kompatible leverandører bruker `DefaultExecutor` (`executors/default.ts`). Leverandørspesifikk oppførsel (basis-URL, autentiseringshoder, API-versjon) konfigureres i `open-sse/config/providers/`, mens transformasjoner av forespørselskroppen håndteres i `open-sse/translator/`.

**Egendefinert URL** angis via leverandørkonfigurasjonen:

```ts
// Leverandørkonfigurasjon i open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Egendefinert autentisering** håndteres gjennom autentiseringskonfigurasjonen i leverandørregisteret (API-nøkkel, OAuth, hodeprofiler).

Transformasjoner av **egendefinert forespørselskropp** (f.eks. at Anthropic skiller `system` fra `messages`) registreres per leverandør i `open-sse/translator/`.

````

### Eksekvererfabrikken

`executors/index.ts` eksporterer `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Oppslag går gjennom `ExecutorRegistry` (`executors/registry.ts`): hver spesialiserte eksekverer deklareres i den innebygde tabellen i `executors/index.ts` og registreres via `registerExecutor(alias, instance)` når modulen lastes inn. `getExecutor()` slår opp i registeret og faller tilbake til en mellomlagret `DefaultExecutor` for alle leverandører uten en spesialisert oppføring. Den fullstendige tilordningen alias → eksekverer beskrives av gulltesten `tests/unit/executor-map-golden.test.ts`.

## Oversettere

Oversett mellom **3 formater**: OpenAI, Anthropic, Gemini samt det nye Responses API.

### Når oversettelse skjer

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Vanlige oversettelser:

- `OpenAI → Anthropic`: separat `system`-felt, `x-api-key`-header
- `OpenAI → Gemini`: `contents` i stedet for `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input`-matrise, tilstand via `previous_response_id`

### Håndterte spesialtilfeller

- `developer`-rolle → `system` for andre enn OpenAI
- `system`-rolle → slått sammen med den første brukermeldingen for GLM/ERNIE
- `json_schema` → Geminis `responseMimeType` + `responseSchema`
- `tools` → leverandørspesifikt verktøyformat
- Parametere for tenking (o1, Claude) → leverandørspesifikke ekvivalenter

## MCP-server

`open-sse/mcp-server/` implementerer **Model Context Protocol**-serveren:

- **110 verktøy** (leverandøradministrasjon, kombinasjoner, minne, hurtigbuffer, komprimering, proxy, ferdigheter, spillifisering, programtillegg, Notion, Obsidian, lokalt korpus)
- **3 transporter**: stdio, SSE, strømbar HTTP
- **33 omfang** for finmasket autorisasjon

### Verktøyregistrering

Verktøy registreres som frittstående filer i `open-sse/mcp-server/tools/`, der hver fil eksporterer et navn, et skjema, en håndterer og et omfang:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transporter

```ts
// stdio (CLI-bruk)
startMcpStdio(server);

// SSE (HTTP-basert strømming)
startMcpSse(server, port);

// Strømbar HTTP (moderne MCP)
startMcpStreamable(server, port);
```

### Autorisasjon

Hvert verktøykall går gjennom omfangskontroller (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Transformatorer

`open-sse/transformer/` konverterer mellom formatene **Chat Completions** og **Responses API**.

### Hvorfor en separat transformator?

Responses API er OpenAIs nye format med **tilstandsfulle samtaler** (`previous_response_id`). Når en klient sender en Responses-forespørsel, gjør OmniRoute følgende:

1. Konverterer Responses → Chat Completions internt
2. Sender til leverandøren (enhver leverandør som støtter Chat Completions)
3. Konverterer svaret tilbake til Responses-format
4. Strømmer det konverterte svaret til klienten

Transformatoren (`transformer/responsesTransformer.ts`) tilbyr:

```ts
createResponsesApiTransformStream(): TransformStream
```

Dette håndterer:

- `response.output_item.added`-hendelser
- `response.output_text.delta`-hendelser
- `response.completed`-hendelsen
- Tilordning av verktøykall (`function_call` ↔ `tool_calls`)

## Konfigurasjon

`open-sse/config/` inneholder konfigurasjonslaget:

| Fil                           | Formål                                                      |
| ----------------------------- | ----------------------------------------------------------- |
| `providerRegistry.ts`         | Register over chatmodeller i katalogen med 352 leverandører |
| `providerModels.ts`           | Modellaliaser, formattilordning                             |
| `constants.ts`                | Tidsavbrudd, grenser, statuskoder                           |
| `defaultThinkingSignature.ts` | Standard tenkesignatur for Claude                           |
| `modelStrip.ts` (i tjenester) | Feltfjerning per leverandør                                 |

### Skjema for leverandørregister

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod-validering ved modulinnlasting sikrer at alle leverandørkonfigurasjoner er gyldige.

## Ytelsesbegrensninger

Rutingmotoren har strenge ytelsesbudsjetter:

| Operasjon                                       | Mål   | Måling                      |
| ----------------------------------------------- | ----- | --------------------------- |
| Kombinasjonsoppløsning                          | <10ms | For 50 mål                  |
| Frekvensgrensekontroll                          | <1ms  | Tokenbøtte i minnet         |
| Reserveløsning for modellfamilie                | <5ms  | Bufrede familiedefinisjoner |
| Distribuering av forespørselsruting             | <2ms  | Kritisk kjørebane           |
| **Ingen blokkerende I/O i kritisk rutingsbane** | —     | Alt asynkront               |

## Antimønstre

❌ **Synkrone databasekall i `combo.ts`** — forhåndsberegn og mellomlagre
❌ **Logikk for nye forsøk i behandlere** — bruk `retry()` fra robusthetstjenesten
❌ **Direkte tilgang til leverandørkonfigurasjon** — bruk aksessorene i `providerRegistry`
❌ **Hardkodede reservekjeder** — definer dem i `modelFamilyFallback.ts`
❌ **Tilstandsendringer på tvers av samtidige forespørsler** — bruk kun forespørselsavgrenset kontekst

## Legge til en ny komponent

### Legge til en ny tjeneste

1. Opprett `open-sse/services/[serviceName].ts` med et avgrenset ansvarsområde
2. Eksporter hovedbehandlerfunksjonen og eventuelle konstanter
3. Legg til enhetstester i `tests/unit/services/[serviceName].test.mjs`
4. Integrer den i forespørselskjeden i `handlers/chatCore.ts` (hvis den er rutingsrelatert)
5. Oppdater rutingslogikken i `combo.ts` hvis tjenesten påvirker målutvelgelsen
6. Dokumenter den i denne filen

### Legge til en ny eksekutor

1. Opprett `open-sse/executors/[provider].ts` som utvider `BaseExecutor`
2. Registrer den i `config/providerRegistry.ts`
3. Legg den til i fabrikken i `executors/index.ts`
4. Legg til enhetstester for eksekutoren
5. Dokumenter den i `docs/architecture/ARCHITECTURE.md`

### Legge til et nytt MCP-verktøy

1. Opprett eller oppdater `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definer et Zod-skjema for inndata
3. Registrer verktøyet i `mcp-server/index.ts`
4. Legg det til i tilgangsmatrisen i `mcp-server/auth/`
5. Legg til enhetstester
