OpenAI-ಹೊಂದಾಣಿಕೆಯ ಬ್ಯಾಕೆಂಡ್ ಆಗಿ OmniRoute ಅನ್ನು ಸೂಚಿಸುವ Codex CLI ಬಳಸುವ ಸಂಪೂರ್ಣ ಮಾರ್ಗದರ್ಶಿ.

---

> **TOML ಮಾತ್ರ ಪರಿಣಾಮಕಾರಿ ಸ್ವರೂಪವಾಗಿದೆ.** ಆಧುನಿಕ Codex ಪ್ರತ್ಯೇಕವಾಗಿ `~/.codex/config.toml`
> ಅನ್ನು ಓದುತ್ತದೆ (codex-cli 0.147.0 ವಿರುದ್ಧ ಪರಿಶೀಲಿಸಲಾಗಿದೆ: `codex --help`, "`~/.codex/config.toml` ನಿಂದ ಲೋಡ್ ಮಾಡಲಾದ"
> ಸಂರಚನೆಯನ್ನು `-c/--config` ಅತಿಕ್ರಮಿಸುತ್ತದೆ ಎಂದು ದಾಖಲಿಸುತ್ತದೆ). ಹಳೆಯ
> `~/.codex/config.yaml`, ಪರಂಪರೆಯ npm CLI ಗೆ ಸೇರಿದ್ದಾಗಿದ್ದು, ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ.
> ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಜನರೇಟರ್ (`/api/cli-tools/apply`, ಸಾಧನ `codex`) ಸಂಯಮಿತ ವಿಲೀನದೊಂದಿಗೆ TOML ಅನ್ನು ಬರೆಯುತ್ತದೆ —
> ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕೀಲಿಗಳು ಮತ್ತು ಇತರ ಪೂರೈಕೆದಾರ ಬ್ಲಾಕ್ಗಳನ್ನು ಉಳಿಸಲಾಗುತ್ತದೆ,
> API ಕೀಲಿಯು `OMNIROUTE_API_KEY` ನಲ್ಲಿಯೇ ಇರುತ್ತದೆ (ಫೈಲ್ನಲ್ಲಿ ಎಂದಿಗೂ ಅಲ್ಲ), ಮತ್ತು ಉಳಿದಿರುವ ಪರಂಪರೆಯ
> `config.yaml` ಅನ್ನು ಮುಟ್ಟದೆಯೇ ವಲಸೆ ಟಿಪ್ಪಣಿಯಾಗಿ ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ.

## ನೇರವಾಗಿ ಅಂಟಿಸಲು ಸಿದ್ಧವಾಗಿರುವ config.toml

`<YOUR_HOST>` ಮತ್ತು `<YOUR_KEY>` ಅನ್ನು ನಿಮ್ಮ ಮೌಲ್ಯಗಳಿಂದ ಬದಲಾಯಿಸಿ:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ಪ್ರತಿ ಸಾಧನ ಕರೆಗೆ ಇತಿಹಾಸ ಸಂಗ್ರಹಣೆಯ ಮಿತಿ

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc ಅಥವಾ ~/.zshrc — ನೈಜ ಕೀಲಿಯ ಮೌಲ್ಯ, config.toml ನಲ್ಲಿ ಎಂದಿಗೂ ಅಲ್ಲ
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT ಆ್ಯಪ್ನೊಳಗೆ ಸಂಯೋಜಿಸಲಾದ Codex

ನೀವು ChatGPT ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ ಮೂಲಕ Codex ಅನ್ನು ಸ್ಥಾಪಿಸಿದ್ದರೆ, `codex` ಬೈನರಿಯು
ಆ್ಯಪ್ ಬಂಡಲ್ನೊಳಗೆ ಮಾತ್ರ ಇರಬಹುದು ಮತ್ತು ಇನ್ನೂ ನಿಮ್ಮ ಶೆಲ್ `PATH` ನಲ್ಲಿ ಇಲ್ಲದಿರಬಹುದು. ಸಂಪನ್ಮೂಲಗಳ
ಡೈರೆಕ್ಟರಿಯನ್ನು ನಿಮ್ಮ ಶೆಲ್ ಪ್ರಾರಂಭಿಕ ಫೈಲ್ಗೆ ಸೇರಿಸಿ:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

ಹೊಸ ಶೆಲ್ ತೆರೆಯಿರಿ, ನಂತರ ಪರಿಶೀಲಿಸಿ:

```bash
command -v codex
codex --version
```

### ದೃಢೀಕರಣ ಅಗತ್ಯವಿಲ್ಲದ ಸ್ಥಳೀಯ OmniRoute: ತಾತ್ಕಾಲಿಕ ಕೀಲಿಯೇ ಸಾಕು

ಮೊದಲ ವಿನಂತಿಯು CLI ಯಿಂದ ಹೊರಹೋಗುವ **ಮೊದಲೇ**, `env_key` ಹೆಸರಿಸುವ ಪರಿಸರ ಚರವು ಅಸ್ತಿತ್ವದಲ್ಲಿದೆಯೇ
ಎಂಬುದನ್ನು Codex ಪರಿಶೀಲಿಸುತ್ತದೆ. ನಿಮ್ಮ **ಸ್ಥಳೀಯ** OmniRoute
ನಿದರ್ಶನಕ್ಕೆ ದೃಢೀಕರಣದ ಅಗತ್ಯವಿಲ್ಲದಿದ್ದರೆ, ಖಾಲಿಯಲ್ಲದ ಯಾವುದೇ ತಾತ್ಕಾಲಿಕ ಮೌಲ್ಯ ಸಾಕಾಗುತ್ತದೆ:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

ನಿಮ್ಮ OmniRoute ಸರ್ವರ್ ಸಂರಕ್ಷಿತವಾಗಿದ್ದರೆ ಅಥವಾ ದೂರಸ್ಥವಾಗಿದ್ದರೆ, ಬದಲಿಗೆ ನೈಜ ಕೀಲಿಯನ್ನು ಬಳಸಿ.

> **ಸಾಮಾನ್ಯ ಹೋಸ್ಟ್ ಆಯ್ಕೆಗಳು**
>
> | ಪ್ರವೇಶ           | URL                           |
> | ---------------- | ----------------------------- |
> | ಸ್ಥಳೀಯ ನೆಟ್ವರ್ಕ್ | `http://192.168.0.1:20128/v1` |
> | Tailscale        | `http://100.x.x.x:20128/v1`   |
> | ಲೂಪ್ಬ್ಯಾಕ್       | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — ಇದು ಎಲ್ಲಾ ಮಾದರಿಗಳಿಗೆ ಏಕೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ

Codex CLI ಫೆಬ್ರವರಿ 2026ರಲ್ಲಿ `wire_api = "chat"` (Chat Completions) ಅನ್ನು ಬಳಕೆಯಿಂದ ಹಿಂತೆಗೆದುಕೊಂಡಿತು ಮತ್ತು ಈಗ `wire_api = "responses"` (OpenAI Responses API) ಅನ್ನು **ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ**. v0.138 ರಿಂದ `wire_api = "chat"` ಹೊಂದಿಸುವುದರಿಂದ ಪ್ರಾರಂಭದಲ್ಲೇ ತಕ್ಷಣ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ.

GLM ಮತ್ತು Kimi ಸೇರಿದಂತೆ ಅನೇಕ ಪೂರೈಕೆದಾರರು ಇನ್ನೂ Chat Completions ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಮಾತ್ರ ಒದಗಿಸುತ್ತಾರೆ. DeepSeek V4 ಈಗ Anthropic-ಹೊಂದಾಣಿಕೆಯ ಎಂಡ್ಪಾಯಿಂಟ್ ಜೊತೆಗೆ ಸ್ಥಳೀಯ Responses API ಅನ್ನೂ ಒದಗಿಸುತ್ತದೆ; OmniRoute ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ Responses ಅನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು DeepSeek ಸಂಪರ್ಕಕ್ಕೂ Anthropic ಹೊಂದಾಣಿಕೆಯನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಅವಕಾಶ ನೀಡುತ್ತದೆ.

**OmniRoute ಇದನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ಪರಿಹರಿಸುತ್ತದೆ:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute ಪೂರೈಕೆದಾರರ ಸ್ಥಳೀಯ ಪ್ರೋಟೋಕಾಲ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ ಮತ್ತು ಅಗತ್ಯವಿದ್ದಾಗ ಅನುವಾದಿಸುತ್ತದೆ
    → POST /responses (DeepSeek V4) ಅಥವಾ /chat/completions (Mistral / GLM / Kimi / ಇತರರು)
```

OmniRoute ಬಳಸುವಾಗ ನಿಮಗೆ ಎಂದಿಗೂ ಪ್ರತ್ಯೇಕ ಅನುವಾದ ಪ್ರಾಕ್ಸಿಯ ಅಗತ್ಯವಿಲ್ಲ. **ಎಲ್ಲಾ ಮಾದರಿಗಳೂ `wire_api = "responses"` ಅನ್ನು ಬಳಸುತ್ತವೆ** — ಉಳಿದದ್ದನ್ನು OmniRoute ನಿರ್ವಹಿಸುತ್ತದೆ.

> **`wire_api` ಪೂರ್ವನಿಯೋಜಿತವಾಗಿದೆ** — ಈ ಕ್ಷೇತ್ರವು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ `"responses"` ಮೌಲ್ಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ ಮತ್ತು ಇದನ್ನು `config.toml` ನಿಂದ ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡಬಹುದು. ನಿಮ್ಮ ಉದ್ದೇಶವನ್ನು ದಾಖಲಿಸುತ್ತಿದ್ದರೆ ಮಾತ್ರ ಇದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸಿ.

## ಸಂದರ್ಭ ವಿಂಡೋ ಮತ್ತು ಸಂಕ್ಷೇಪಣೆ

### ಟೋಕನ್ ಸಂರಚನಾ ಕ್ಷೇತ್ರಗಳು

| ಕ್ಷೇತ್ರ                          | ವಿವರಣೆ                                                                                                                                                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | ಸಕ್ರಿಯ ಮಾದರಿಯ ಒಟ್ಟು ಟೋಕನ್ ಮಿತಿ. ಮಾದರಿಗಾಗಿ ಪ್ರಕಟಿಸಲಾದ ಮಿತಿಗೆ ಹೊಂದಿಸಿ.                                                                                                                                              |
| `model_auto_compact_token_limit` | ಸ್ವಯಂಚಾಲಿತ ಇತಿಹಾಸ ಸಂಕ್ಷೇಪಣೆಯನ್ನು ಪ್ರಚೋದಿಸುವ ಮಿತಿ. **ಗರಿಷ್ಠ: `model_context_window`ನ 90%** — 90%ಗಿಂತ ಹೆಚ್ಚಿನ ಮೌಲ್ಯಗಳನ್ನು ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ.                                                  |
| `tool_output_token_limit`        | ಪ್ರತಿ ಉಪಕರಣ ಕರೆದಾಗಿನ ಔಟ್ಪುಟ್ಗಾಗಿ ಇತಿಹಾಸದಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುವ ಟೋಕನ್ಗಳ ಗರಿಷ್ಠ ಮಿತಿ. ಒಂದೇ ದೊಡ್ಡ ಉಪಕರಣ ಪ್ರತಿಕ್ರಿಯೆಯು ವಿಂಡೋವನ್ನು ತುಂಬುವುದನ್ನು ತಡೆಯುತ್ತದೆ. **ಇದು ಗರಿಷ್ಠ ಔಟ್ಪುಟ್ ಅಲ್ಲ** — ಇದು ಇತಿಹಾಸ ಸಂಗ್ರಹಣೆಯ ಮಿತಿಯಾಗಿದೆ. |
| `compact_prompt`                 | ಸಂಕ್ಷೇಪಣೆಯ ಸಮಯದಲ್ಲಿ ಬಳಸಲಾಗುವ ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ಗಾಗಿ ಇನ್ಲೈನ್ ಅತಿಕ್ರಮಣ (v0.138+).                                                                                                                                    |

> **`model_max_output_tokens` ಕುರಿತು ಟಿಪ್ಪಣಿ**: ಈ ಕ್ಷೇತ್ರವು **Codex CLI ಸಂರಚನಾ ಸ್ಕೀಮಾದ ಭಾಗವಲ್ಲ** (Codex Rust ಕೋಡ್ಬೇಸ್ನಲ್ಲಿ ಇಲ್ಲ). ಇದನ್ನು ಹೊಂದಿಸಿದರೆ ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ. ಇದನ್ನು ಅವಲಂಬಿಸಬೇಡಿ — ಇತಿಹಾಸದಲ್ಲಿ ಎಷ್ಟು ಉಪಕರಣ ಔಟ್ಪುಟ್ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ ಎಂಬುದನ್ನು ನಿಯಂತ್ರಿಸಲು `tool_output_token_limit` ಬಳಸಿ.

## ತಾರ್ಕಿಕ ಪ್ರಯತ್ನ

ಪ್ರತಿಕ್ರಿಯಿಸುವ ಮೊದಲು ಮಾದರಿಯು ಎಷ್ಟು "ಯೋಚಿಸಬೇಕು" ಎಂಬುದನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.

| ಮೌಲ್ಯ    | ಇದಕ್ಕಾಗಿ ಬಳಸಿ                                      |
| -------- | -------------------------------------------------- |
| `none`   | ತಾರ್ಕಿಕ ಪ್ರಕ್ರಿಯೆ ಇಲ್ಲ — ನೇರ ಪ್ರತಿಕ್ರಿಯೆ           |
| `low`    | ಸರಳ ಕಾರ್ಯಗಳು (ಮರುಹೆಸರಿಸುವಿಕೆ, ಫಾರ್ಮ್ಯಾಟ್ ಮಾಡುವುದು) |
| `medium` | ನಿರ್ದಿಷ್ಟಪಡಿಸದಿದ್ದಾಗ **ಸರ್ವರ್ ಡೀಫಾಲ್ಟ್**           |
| `high`   | ಮಧ್ಯಮ ಹಂತದ ಕಾರ್ಯಗಳು (ರಿಫ್ಯಾಕ್ಟರಿಂಗ್, ಡೀಬಗ್)        |
| `xhigh`  | ಆರ್ಕಿಟೆಕ್ಚರ್, ಆಳವಾದ ವಿಶ್ಲೇಷಣೆ, ಸಂಕೀರ್ಣ ಸಮಸ್ಯೆಗಳು   |

```bash
# ಪ್ರತಿ ಚಾಲನೆಗೆ ಅತಿಕ್ರಮಣ
codex -c model_reasoning_effort=low "ಚರ x ಅನ್ನು count ಎಂದು ಮರುಹೆಸರಿಸಿ"
codex -c model_reasoning_effort=xhigh "auth ಮಾಡ್ಯೂಲ್ ಅನ್ನು ವಿನ್ಯಾಸಗೊಳಿಸಿ"
```

Desktop ಕೇವಲ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ಬ್ಲಾಬ್ಗಳನ್ನಷ್ಟೇ ಅಲ್ಲದೆ ಯೋಚನಾ ಪಠ್ಯವನ್ನೂ ಪ್ರದರ್ಶಿಸಲು, ತಾರ್ಕಿಕ **ಸಾರಾಂಶ**ವನ್ನೂ ಹೊಂದಿಸಿ:

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # ಅಥವಾ ಬೆಂಬಲಿತವಾಗಿರುವಾಗ ultra
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute ಯೋಚನಾ ಬಜೆಟ್ (ಸರ್ವರ್ ಸೆಟ್ಟಿಂಗ್)

OmniRoute ಹೋಸ್ಟ್ನಲ್ಲಿ, Codex ಪ್ರಯತ್ನ/ಸಾರಾಂಶವು ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ತಲುಪಲು **Settings → AI → Thinking Budget** ಅನ್ನು **`passthrough`** ಆಗಿ ಹೊಂದಿಸಿರಬೇಕು. **`auto` ಮೋಡ್** ಎಲ್ಲಾ ಕ್ಲೈಂಟ್ `reasoning` / `reasoning_effort` ಕ್ಷೇತ್ರಗಳನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ ಮತ್ತು Codex ಅನ್ನು ಸರಿಯಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ್ದರೂ ಯೋಚನಾ ಪ್ಯಾನೆಲ್ಗಳನ್ನು ಖಾಲಿ ಮಾಡುತ್ತದೆ.

ಸಂಪೂರ್ಣ ಮಾರ್ಗದರ್ಶಿ: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

ಸಂಕುಚನ ಮತ್ತು ಪ್ರಾಂಪ್ಟ್ ಕ್ಯಾಶ್ ಸ್ವತಂತ್ರವಾಗಿದ್ದು, `passthrough` ಅಡಿಯಲ್ಲಿಯೂ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ.

## ಪ್ರೊಫೈಲ್ಗಳು — ಪ್ರತಿ ಮಾದರಿ/ಕಾರ್ಯಪ್ರವಾಹಕ್ಕೆ ಹೆಸರಿಸಲಾದ ಕಾನ್ಫಿಗರೇಶನ್ಗಳು

ಪ್ರೊಫೈಲ್ಗಳು ಒಂದೇ ಫ್ಲ್ಯಾಗ್ನೊಂದಿಗೆ ಮಾದರಿ + ಕಾಂಟೆಕ್ಸ್ಟ್ ವಿಂಡೋವನ್ನು ಬದಲಾಯಿಸಲು ನಿಮಗೆ ಅವಕಾಶ ನೀಡುತ್ತವೆ. ಪ್ರತಿ ಪ್ರೊಫೈಲ್ ಒಂದು ಸಮತಟ್ಟಾದ
`~/.codex/<name>.config.toml` ಫೈಲ್ ಆಗಿದ್ದು, ಮೂಲ `config.toml` ಮೇಲೆ ಓವರ್ಲೇ ಆಗುತ್ತದೆ.

> **ಹೆಸರಿಸುವ ನಿಯಮ (Codex CLI v0.137+):** ಫೈಲ್ `~/.codex/<name>.config.toml` ಆಗಿಯೇ ಇರಬೇಕು — **`profile-` ಪೂರ್ವಪ್ರತ್ಯಯ ಇರಬಾರದು**.
> CLI `-p kimi-k27` → `~/.codex/kimi-k27.config.toml` ಎಂದು ಪರಿಹರಿಸುತ್ತದೆ. ಫೈಲ್ ಕಂಡುಬರದಿದ್ದರೆ, ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.

```bash
codex --profile kimi-k27 "ಈ ಕೋಡ್ಬೇಸ್ನ 10k ಸಾಲುಗಳನ್ನು ವಿಶ್ಲೇಷಿಸಿ"
codex -p glm52 "ಆರ್ಕಿಟೆಕ್ಚರ್ ಪರಿಶೀಲನೆ"
codex --profile deepseek-flash "ಚರವನ್ನು ಮರುಹೆಸರಿಸಿ"   # ವೇಗ, ಕಡಿಮೆ ವೆಚ್ಚ
```

## `omniroute setup-codex` ಮೂಲಕ ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ರಚಿಸುವುದು

ನೀವು OmniRoute ಅನ್ನು VPS ನಲ್ಲಿ ಚಲಾಯಿಸುತ್ತಿದ್ದರೆ, ಲೈವ್ ಮಾಡೆಲ್ ಕ್ಯಾಟಲಾಗ್ನಿಂದ ಪ್ರೊಫೈಲ್ ಫೈಲ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ರಚಿಸಬಹುದು:

```bash
# VPS ನಿಂದ (ಪೋರ್ಟ್ 20128 ರಲ್ಲಿರುವ ಸ್ಥಳೀಯ OmniRoute ಅನ್ನು ಬಳಸುತ್ತದೆ)
omniroute setup-codex

# ಯಾವುದೇ ಯಂತ್ರದಿಂದ — ನಿಮ್ಮ VPS ಅನ್ನು ಸೂಚಿಸಿ
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# ಫೈಲ್ಗಳನ್ನು ಬರೆಯದೆ ಪೂರ್ವವೀಕ್ಷಿಸಿ
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# GLM ಮತ್ತು Kimi ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಮಾತ್ರ ರಚಿಸಿ
omniroute setup-codex --only glm,kimi

# ಕಸ್ಟಮ್ ಡೈರೆಕ್ಟರಿಗೆ ಬರೆಯಿರಿ
omniroute setup-codex --codex-home /path/to/.codex
```

ಈ ಕಮಾಂಡ್ `/v1/models` ಅನ್ನು ಪಡೆಯುತ್ತದೆ, ತಿಳಿದಿರುವ ಮಾಡೆಲ್ಗಳಿಗೆ ಟ್ಯೂನ್ ಮಾಡಿದ ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ, ಇತರ ಹೊಂದಾಣಿಕೆಯ ಪಠ್ಯ ಮಾಡೆಲ್ಗಳಿಗೆ ಕ್ಯಾಟಲಾಗ್ ಮೆಟಾಡೇಟಾವನ್ನು ಪರ್ಯಾಯವಾಗಿ ಬಳಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದಕ್ಕೂ `~/.codex/<name>.config.toml` ಅನ್ನು ಬರೆಯುತ್ತದೆ. ಇದು ಐಡೆಂಪೊಟೆಂಟ್ ಆಗಿರುವುದರಿಂದ ಮರುಚಾಲನೆ ಮಾಡುವುದು ಸುರಕ್ಷಿತವಾಗಿದೆ.

ಯಶಸ್ವಿ ಪ್ರೊವೈಡರ್ ಮಾಡೆಲ್ ಅನ್ವೇಷಣೆ/ಆಮದು ಲೈವ್ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಬದಲಾಯಿಸಿದ ನಂತರ OmniRoute ಇದೇ ಪ್ರೊಫೈಲ್ ಫೈಲ್ಗಳನ್ನು **ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸಿಂಕ್** ಮಾಡಬಹುದು. ಇದು **ಆಯ್ಕೆಮಾಡಿ ಸಕ್ರಿಯಗೊಳಿಸಬೇಕಾದ ವೈಶಿಷ್ಟ್ಯವಾಗಿದ್ದು, ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಆಫ್ ಆಗಿರುತ್ತದೆ**: ಇದನ್ನು **CLI Code ಡ್ಯಾಶ್ಬೋರ್ಡ್**ನಿಂದ ("CLI profile auto-sync" → Codex) ಟಾಗಲ್ ಮಾಡಿ, ಅಥವಾ `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` ಅನ್ನು ಹೊಂದಿಸಿ (ಇದು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಆನ್ ಆಗಿರುವ `CLI_ALLOW_CONFIG_WRITES` ಅನ್ನೂ ಗೌರವಿಸುತ್ತದೆ). ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಇದು ಪ್ರತ್ಯೇಕ `~/.codex/*.config.toml` ಪ್ರೊಫೈಲ್ ಫೈಲ್ಗಳನ್ನು ಮಾತ್ರ ಬರೆಯುತ್ತದೆ; ಸಕ್ರಿಯ/ಪೂರ್ವನಿಯೋಜಿತ `~/.codex/config.toml`, Codex-lb ಸೆಟ್ಟಿಂಗ್ಗಳು, ದೃಢೀಕರಣ ಅಥವಾ ಪ್ರೊವೈಡರ್ ಆಯ್ಕೆಯನ್ನು ಎಂದಿಗೂ ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

## `omniroute launch-codex` ಮೂಲಕ Codex ಅನ್ನು ಪ್ರಾರಂಭಿಸುವುದು

```bash

omniroute launch-codex

# ನಿರ್ದಿಷ್ಟ ಪ್ರೊಫೈಲ್ನೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಿ
omniroute launch-codex --profile kimi-k27

omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# codex ಗೆ ಹೆಚ್ಚುವರಿ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳನ್ನು ರವಾನಿಸಿ
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex, ಎರಡು ಸಾರ್ವತ್ರಿಕ ಮ್ಯಾನಿಫೆಸ್ಟ್-ಚಾಲಿತ ಪ್ರವೇಶ ಬಿಂದುಗಳಿಗೂ ಗುರಿಯಾಗಿದೆ
(`bin/cli/cli-manifest.mjs`):

```bash
# ಸಂವಾದಾತ್ಮಕ ಮಾಡೆಲ್ ಪಿಕರ್ → ~/.codex/<name>.config.toml ಅನ್ನು ಬರೆಯುತ್ತದೆ (TOML, env_key)

omniroute run codex
```

## ದೀರ್ಘಾವಧಿಯ ಕಾರ್ಯಗಳು

ಎರಡು OmniRoute ಡೀಫಾಲ್ಟ್ಗಳು ಹಲವು ಗಂಟೆಗಳ Codex CLI ಸೆಷನ್ಗಳನ್ನು ಸದ್ದಿಲ್ಲದೆ ಹಾಳುಮಾಡಬಹುದು. ಎರಡೂ Codex CLI ಸೆಟ್ಟಿಂಗ್ಗಳಲ್ಲ — ಎರಡೂ OmniRoute ಬದಿಯಲ್ಲಿವೆ. ಖಾತೆಗಳನ್ನು ಪಿನ್ ಮಾಡುವ ಮತ್ತು ನಿಷ್ಕ್ರಿಯತೆಯ ಕಡಿತಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರಾಕ್ಸಿಗಳಿಂದ ಸಂರಚನೆಯನ್ನು ವರ್ಗಾಯಿಸುವ ಬಳಕೆದಾರರು ಸಾಮಾನ್ಯವಾಗಿ ಎರಡೂ ಸಮಸ್ಯೆಗಳನ್ನು ಎದುರಿಸಿ, OmniRoute “ದೀರ್ಘ ಸೆಷನ್ ಅನ್ನು ನಿರ್ವಹಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ” ಎಂದು ತೀರ್ಮಾನಿಸುತ್ತಾರೆ.

| ಲಕ್ಷಣ                                                                                            | ಸಂಭವನೀಯ ಕಾರಣ                                                                | ನಿಯಂತ್ರಣ                 |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | ------------------------ |
| ಸೆಷನ್ ಖಾತೆಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತಲೇ ಇರುತ್ತದೆ / ಟರ್ನ್ಗಳ ನಡುವೆ ಪ್ರಾಂಪ್ಟ್-ಕ್ಯಾಶ್ ನಿರಂತರತೆ ಕಳೆದುಹೋಗುತ್ತದೆ | ಸೆಷನ್ ಅಫಿನಿಟಿ TTL `0` ಆಗಿದೆ (ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ)                          | `sessionAffinityTtlMs`   |
| ಕ್ಲೈಂಟ್ಗೆ ಗೋಚರಿಸುವ ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ತಾರ್ಕಿಕ ಪ್ರಕ್ರಿಯೆಯ ಮಧ್ಯದಲ್ಲೇ ಸಂಪರ್ಕ ಕಡಿತಗೊಳ್ಳುತ್ತದೆ       | ಅಪ್ಸ್ಟ್ರೀಮ್ ಚಂಕ್ ಇಲ್ಲದೆ 10 ನಿಮಿಷಗಳ ನಂತರ ಸ್ಟ್ರೀಮ್ ಐಡಲ್ ವಾಚ್ಡಾಗ್ ಸಕ್ರಿಯವಾಯಿತು | `STREAM_IDLE_TIMEOUT_MS` |

ಸಂಬಂಧಿತ ಚರ್ಚೆಗಳು: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (ದೀರ್ಘ ಕಾರ್ಯದ ಸಂಪರ್ಕ ಕಡಿತಗಳು), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (ಅಫಿನಿಟಿ ಡೀಫಾಲ್ಟ್ ಆಗಿ ಏಕೆ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ). ಟ್ರ್ಯಾಕಿಂಗ್: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. ಸೆಷನ್ ಅಫಿನಿಟಿ — ಒಂದು ಸಂಭಾಷಣೆಯನ್ನು ಒಂದು ಖಾತೆಗೆ ಪಿನ್ ಮಾಡಿ

**ಡೀಫಾಲ್ಟ್:** `sessionAffinityTtlMs = 0` (ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ).

**ಇದನ್ನು ಎಲ್ಲಿ ಹೊಂದಿಸಬೇಕು**

- ಡ್ಯಾಶ್ಬೋರ್ಡ್ → **ಸೆಟ್ಟಿಂಗ್ಗಳು → ರೂಟಿಂಗ್** → **ಸೆಷನ್ ಅಫಿನಿಟಿ** → **ಅಫಿನಿಟಿ TTL (ಸೆಕೆಂಡುಗಳು)** (`ComboDefaultsTab`)
- ಅಥವಾ **ಮಿಲಿಸೆಕೆಂಡುಗಳಲ್ಲಿ** `sessionAffinityTtlMs` ಜೊತೆಗೆ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು PATCH ಮಾಡಿ (Zod ವ್ಯಾಪ್ತಿ `0`–`86_400_000`, ಅಂದರೆ 24 ಗಂಟೆಗಳವರೆಗೆ)

> #7274 ರಲ್ಲಿ Codex-ಮಾತ್ರದ `codexSessionAffinityTtlMs` ನಿಂದ ಮರುಹೆಸರಿಸಲಾಗಿದೆ. ಹಳೆಯ ಕೀ ಅನ್ನು ಇನ್ನೂ ಓದಲು-ಮಾತ್ರದ ಅಲಿಯಾಸ್ ಆಗಿ ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; ಹೊಸ ಸಂರಚನೆಗಳು `sessionAffinityTtlMs` ಅನ್ನು ಬಳಸಬೇಕು. TTL `0` ಕ್ಕಿಂತ ಹೆಚ್ಚಾದ ನಂತರ ಅಫಿನಿಟಿ ಈಗ Codex ಗೆ ಮಾತ್ರವಲ್ಲದೆ **ಯಾವುದೇ** ಪ್ರೊವೈಡರ್ಗೆ ಅನ್ವಯಿಸುತ್ತದೆ — [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → ಸೆಷನ್ ಅಫಿನಿಟಿ ನೋಡಿ.

**ಇದು 0 ಆಗಿಯೇ ಉಳಿದಾಗ ಏನು ಹಾಳಾಗುತ್ತದೆ**

ಬಹು-ಟರ್ನ್ Codex ಸಂಭಾಷಣೆಯ ಪ್ರತಿಯೊಂದು ಟರ್ನ್ ಅನ್ನು ಸಕ್ರಿಯ ಕಾಂಬೊ ತಂತ್ರದ ಮೂಲಕ ಸ್ವತಂತ್ರವಾಗಿ ರೂಟ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಅದು **ಪ್ರತಿ ಟರ್ನ್ಗೆ ಬೇರೆ ಖಾತೆ** ತಲುಪಬಹುದು. ಇದು ಅಪ್ಸ್ಟ್ರೀಮ್ ಸೆಷನ್ / ಪ್ರಾಂಪ್ಟ್-ಕ್ಯಾಶ್ ನಿರಂತರತೆಯನ್ನು ಹಾಳುಮಾಡುತ್ತದೆ. TTL `0` ಕ್ಕಿಂತ ಹೆಚ್ಚಿದ್ದಾಗ ಮಾತ್ರ OmniRoute, Codex ಸೆಷನ್ ಹೆಡರ್ಗಳು (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) ಮತ್ತು `prompt_cache_key` / `session_id` ನಂತಹ ಬಾಡಿ ಕ್ಷೇತ್ರಗಳನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ (`src/sse/services/auth.ts` ನಲ್ಲಿನ `extractSessionAffinityKey`).

**ಬಹು ಗಂಟೆಗಳ ಏಕೈಕ ಕಾರ್ಯಕ್ಕೆ ಶಿಫಾರಸು**

ಕಾರ್ಯದ ನಿರೀಕ್ಷಿತ ವಾಲ್-ಕ್ಲಾಕ್ ಅವಧಿಗಿಂತ **ಹೆಚ್ಚಿಗೆ TTL ಅನ್ನು ಹೊಂದಿಸಿ** (UI ಗರಿಷ್ಠವು **86400 ಸೆಕೆಂಡುಗಳು** = 24 ಗಂಟೆಗಳು):

| ನಿರೀಕ್ಷಿತ ಕಾರ್ಯದ ಅವಧಿ | ಅಫಿನಿಟಿ TTL (UI, ಸೆಕೆಂಡುಗಳು) | `sessionAffinityTtlMs` |
| --------------------- | ---------------------------- | ---------------------- |
| ಕೆಲವು ಗಂಟೆಗಳು         | `14400` (4ಗಂ)                | `14400000`             |
| ರಾತ್ರಿಯಿಡೀ / ~12ಗಂ    | `43200` (12ಗಂ)               | `43200000`             |
| ಪೂರ್ಣ ದಿನ             | `86400` (24ಗಂ, ಗರಿಷ್ಠ)       | `86400000`             |

ಆಯ್ಕೆಮಾಡಿ ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದೆ: ಅಫಿನಿಟಿಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು ಖಾತೆಗಳಾದ್ಯಂತ ಲೋಡ್-ಬ್ಯಾಲೆನ್ಸಿಂಗ್ಗೆ ಅನುಕೂಲ ಮಾಡುತ್ತದೆ; ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದು ಒಂದು ದೀರ್ಘ ಏಜೆಂಟ್ ಸೆಷನ್ನ ನಿರಂತರತೆಗೆ ಅನುಕೂಲ ಮಾಡುತ್ತದೆ. ಈ ಮಾರ್ಗದರ್ಶಿ ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ — ದೀರ್ಘ Codex ಕಾರ್ಯಗಳನ್ನು ನಡೆಸುವ ನಿರ್ವಾಹಕರು ಸ್ವತಃ ಇದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಬೇಕು.

### 2. ಸ್ಟ್ರೀಮ್ ಐಡಲ್ ಟೈಮ್ಔಟ್ — ಮೌನವಾದ ತಾರ್ಕಿಕ ಟರ್ನ್ಗಳನ್ನು ಕೊನೆಗೊಳಿಸಬೇಡಿ

**ಡೀಫಾಲ್ಟ್:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 ನಿಮಿಷಗಳು). ಹೊಂದಿಸದಿದ್ದಾಗ ಇದು `REQUEST_TIMEOUT_MS` ನಿಂದ ಮೌಲ್ಯವನ್ನು ಪಡೆದುಕೊಳ್ಳುತ್ತದೆ; ಹಂಚಿದ ಮೂಲ ಮೌಲ್ಯವೂ 600000 ಆಗಿದೆ. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → ಟೈಮ್ಔಟ್ಗಳು ನೋಡಿ.

**ಡೀಫಾಲ್ಟ್ನಲ್ಲಿ ಏನು ಹಾಳಾಗುತ್ತದೆ**

10 ನಿಮಿಷಗಳಿಗಿಂತ ಹೆಚ್ಚು ಕಾಲ **ಯಾವುದೇ ನೈಜ ಅಪ್ಸ್ಟ್ರೀಮ್ ಚಂಕ್ ಇಲ್ಲದೆ** ಮೌನವಾಗಿರುವ Codex reasoning / tool turn ಅನ್ನು SSE idle watchdog (`open-sse/utils/stream.ts`) ಬಲವಂತವಾಗಿ ಮುಚ್ಚುತ್ತದೆ. ಕ್ಲೈಂಟ್ಗೆ ಸಾಮಾನ್ಯವಾಗಿ ಯಾವುದೇ ವಿವರವಿಲ್ಲದೆ ಸಂಪರ್ಕ ಕಡಿತಗೊಂಡಂತೆ ಕಾಣುತ್ತದೆ — ಇದು “ಯಾವುದೇ ಅಧಿಸೂಚನೆ ಇಲ್ಲದೆ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನಿಂತಿತು” ಎಂಬುದಕ್ಕೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ.

ನಿರ್ಣಾಯಕ ವಿವರ: OmniRouteನ ಸಂಶ್ಲೇಷಿತ SSE **heartbeat idle ಗಡಿಯಾರವನ್ನು ಮರುಹೊಂದಿಸುವುದಿಲ್ಲ**. ನೈಜ ಅಪ್ಸ್ಟ್ರೀಮ್ body chunk ಮಾತ್ರ `lastChunkTime` ಅನ್ನು ನವೀಕರಿಸುತ್ತದೆ. ಇನ್ನೂ “ಯೋಚಿಸುತ್ತಿರುವ” ಮೌನ ಮಾದರಿಯು watchdog ದೃಷ್ಟಿಯಲ್ಲಿ ಸ್ಥಗಿತಗೊಂಡ ಅಪ್ಸ್ಟ್ರೀಮ್ನಂತೆಯೇ ಕಾಣುತ್ತದೆ.

ಸಂಬಂಧಿತ Undici body ನಿಷ್ಕ್ರಿಯತೆ: `FETCH_BODY_TIMEOUT_MS` (ಇದೂ ಅದೇ 10-ನಿಮಿಷದ ಮೂಲಮಟ್ಟಕ್ಕೆ ಡೀಫಾಲ್ಟ್ ಆಗಿರುತ್ತದೆ; `0` ಅದನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ). ಸ್ಟ್ರೀಮಿಂಗ್ಗಾಗಿ, `FETCH_TIMEOUT_MS` ಸಂಪರ್ಕ ಸ್ಥಾಪನೆ / ಮೊದಲ ಹೆಡರ್ಗಳನ್ನು ಮಾತ್ರ ಒಳಗೊಳ್ಳುತ್ತದೆ — ಸ್ಟ್ರೀಮ್ ಸಕ್ರಿಯವಾದ ನಂತರ, ಸ್ಥಗಿತಗಳನ್ನು `STREAM_IDLE_TIMEOUT_MS` ಮತ್ತು `FETCH_BODY_TIMEOUT_MS` ನಿಯಂತ್ರಿಸುತ್ತವೆ.

**ಹಲವು ಗಂಟೆಗಳ ಒಂದೇ ಕಾರ್ಯಕ್ಕಾಗಿ ಶಿಫಾರಸು**

OmniRoute ಪ್ರಕ್ರಿಯೆಯ ಪರಿಸರದಲ್ಲಿ (`.env` / compose / systemd):

```bash
# ದೀರ್ಘ reasoning turnಗಳಿಗಾಗಿ stream idle + body ನಿಷ್ಕ್ರಿಯತೆಯ ಕಡಿತ ಮಿತಿಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿ
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

ಅಥವಾ ನೀವು ನಿರೀಕ್ಷಿಸುವ ಅತಿ ದೀರ್ಘ ಮೌನದ ಅಂತರಕ್ಕಿಂತ ಹೆಚ್ಚಿನ ಮೌಲ್ಯಗಳಿಗೆ ಅವುಗಳನ್ನು ಹೆಚ್ಚಿಸಿ (ಮೌಲ್ಯಗಳು ಮಿಲಿಸೆಕೆಂಡ್ಗಳಲ್ಲಿ ಇರುತ್ತವೆ):

```bash
# ಉದಾಹರಣೆ: ಅಪ್ಸ್ಟ್ರೀಮ್ ಚಂಕ್ಗಳ ನಡುವೆ ಗರಿಷ್ಠ 2 ಗಂಟೆಗಳ ಮೌನವನ್ನು ಅನುಮತಿಸಿ
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ಈ env vars ಬದಲಾಯಿಸಿದ ನಂತರ OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ.

### ನಿರ್ದಿಷ್ಟ ವಿಧಾನ — ಹಲವು ಗಂಟೆಗಳ Codex ಕಾರ್ಯ

1. **ಖಾತೆಯನ್ನು ಪಿನ್ ಮಾಡಿ:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) ಅಥವಾ `86400` (ಗರಿಷ್ಠ 24h).
2. OmniRoute ಪರಿಸರದಲ್ಲಿ **idle ಕಡಿತ ಮಿತಿಗಳನ್ನು ಹೆಚ್ಚಿಸಿ / ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿ**:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. ಸಾಮಾನ್ಯ Codex `config.toml` ಅನ್ನು (`wire_api = "responses"`, ಸರಿಯಾದ `base_url`, `OMNIROUTE_API_KEY`) ಹಾಗೆಯೇ ಇರಿಸಿ — ಈ ಎರಡು ವರ್ತನೆಗಳಿಗಾಗಿ Codex ಬದಿಯಲ್ಲಿ affinity/idle ನಿಯಂತ್ರಣಗಳಿಲ್ಲ.
4. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ, ನಂತರ ದೀರ್ಘ Codex ಕಾರ್ಯವನ್ನು ಪ್ರಾರಂಭಿಸಿ.

| `sessionAffinityTtlMs`   | `0` (ಆಫ್)           | **ಇಲ್ಲ** — opt-in ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ (load-balancing ವಿರುದ್ಧ continuity; Discussion #5718 ನೋಡಿ)                                                 |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 ನಿಮಿಷ) | **ಇಲ್ಲ** — ಸಾಮಾನ್ಯ ಟ್ರಾಫಿಕ್ಗಾಗಿ 10 ನಿಮಿಷಗಳಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ; ದೀರ್ಘ Codex ಕಾರ್ಯಾಚರಣೆ ನಡೆಸುವವರು ಅದನ್ನು ಹೆಚ್ಚಿಸುತ್ತಾರೆ ಅಥವಾ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತಾರೆ |

ಯಾವುದೇ ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಜಾಗತಿಕವಾಗಿ ಬದಲಾಯಿಸುವುದರಿಂದ ಕೇವಲ Codex ಮಾತ್ರವಲ್ಲದೆ, ಆ instanceನ ಪ್ರತಿಯೊಂದು ಕ್ಲೈಂಟ್ನ ವರ್ತನೆಯೂ ಬದಲಾಗುತ್ತದೆ. ನಿಯಂತ್ರಣಗಳನ್ನು ದಾಖಲಿಸಿ; ಸ್ಪಷ್ಟವಾದ ಆಪರೇಟರ್ ನಿರ್ಧಾರವು ಬೇರೆ ರೀತಿಯಲ್ಲಿ ಸೂಚಿಸುವವರೆಗೆ ಡೀಫಾಲ್ಟ್ಗಳನ್ನು ಹಾಗೆಯೇ ಬಿಡಿ.

### Idle ಕಡಿತಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುವುದು

Idle watchdog ಸಕ್ರಿಯವಾದಾಗ, OmniRoute ಈ ಸ್ವರೂಪದ ಸಾಲನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

`Idle timeout: no data from` ಗಾಗಿ grep ಮಾಡಿ (ಅಥವಾ `stream_idle_timeout` ಕೋಡ್ / `StreamIdleTimeoutError` ದೋಷದ ಹೆಸರು). Provider segment ಎಂದರೆ ಆ ವಿನಂತಿಗಾಗಿ OmniRoute ಬಳಸಿದ ಮೌಲ್ಯ (`codex`, ಮತ್ತೊಂದು provider id, ಅಥವಾ ತಿಳಿದಿಲ್ಲದಿದ್ದರೆ `provider`) — ಅದು ಯಾವಾಗಲೂ ಅಕ್ಷರಶಃ `codex` ಆಗಿರುವುದಿಲ್ಲ.

---

## ಸಮಸ್ಯೆ ಪರಿಹಾರ

**`Error: wire_api = "chat" is no longer supported`**
ನಿಮ್ಮ ಸಂರಚನೆಯಿಂದ `wire_api = "chat"` ಅನ್ನು ತೆಗೆದುಹಾಕಿ. `wire_api = "responses"` ಎಂದು ಹೊಂದಿಸಿ ಅಥವಾ ಆ ಕ್ಷೇತ್ರವನ್ನು ಬಿಟ್ಟುಬಿಡಿ (v0.138 ರಿಂದ ಡೀಫಾಲ್ಟ್ ಆಗಿ `"responses"` ಬಳಸಲಾಗುತ್ತದೆ).

**`Error: model not found`**
ಸರಿಯಾದ ಪೂರ್ವಪ್ರತ್ಯಯದೊಂದಿಗೆ ಆ ಮಾಡೆಲ್ OmniRoute ನಲ್ಲಿ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ. `omniroute models list` ಬಳಸಿ ಅಥವಾ `/dashboard/providers/<provider>` ತೆರೆಯಿರಿ.

**`Authentication error`**
`OMNIROUTE_API_KEY` ಅನ್ನು ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡಲಾಗಿದೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
ಮೊದಲ ವಿನಂತಿಯನ್ನು ಮಾಡುವ ಮೊದಲು env var ಅಸ್ತಿತ್ವದಲ್ಲಿದೆಯೇ ಎಂದು Codex ಪರಿಶೀಲಿಸುತ್ತದೆ. ಸಂರಕ್ಷಿತ ಸರ್ವರ್ಗಳಿಗಾಗಿ
ನೈಜ ಕೀಲಿಯನ್ನು ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡಿ ಅಥವಾ ನಿಮ್ಮ **ಸ್ಥಳೀಯ** OmniRoute ನಿದರ್ಶನಕ್ಕೆ
ದೃಢೀಕರಣದ ಅಗತ್ಯವಿಲ್ಲದಿದ್ದರೆ `OMNIROUTE_API_KEY=local` ನಂತಹ ಖಾಲಿಯಲ್ಲದ ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ ಬಳಸಿ.
ನೀವು ಅದನ್ನು `~/.bashrc` ಅಥವಾ `~/.zshrc` ಗೆ ಸೇರಿಸಿದ್ದರೆ ಶೆಲ್ ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ.

**`Connection refused`**
OmniRoute ಚಾಲನೆಯಲ್ಲಿದೆಯೇ ಮತ್ತು `base_url` ಹೋಸ್ಟ್/ಪೋರ್ಟ್ ನಿಮ್ಮ ನೆಟ್ವರ್ಕ್ಗೆ (ಸ್ಥಳೀಯ vs Tailscale vs VPS) ಸರಿಯಾಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ.

**ಸಂದರ್ಭದ ಮಿತಿಯ ಸಮೀಪ ಸೆಷನ್ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ**
`model_context_window` ಮತ್ತು `model_auto_compact_token_limit` ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸಿ. ಮೇಲಿನ ಸಂದರ್ಭ ವಿಂಡೋ ಕೋಷ್ಟಕವನ್ನು ನೋಡಿ.

**ಕಾಂಪ್ಯಾಕ್ಷನ್ ತುಂಬಾ ತಡವಾಗಿ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ**
`model_auto_compact_token_limit` ಅನ್ನು ವಿಂಡೋದ 80–85% ಗೆ ಇಳಿಸಿ. ಅದನ್ನು ಎಂದಿಗೂ 90% ಕ್ಕಿಂತ ಹೆಚ್ಚಾಗಿ ಹೊಂದಿಸಬೇಡಿ.

**ಪ್ರೊಫೈಲ್ ಲೋಡ್ ಆಗುತ್ತಿಲ್ಲ (`-p <name>` ಅನ್ನು ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ)**
ಫೈಲ್ `~/.codex/<name>.config.toml` ನಲ್ಲಿ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ (`profile-` ಪೂರ್ವಪ್ರತ್ಯಯ ಇರಬಾರದು). `ls ~/.codex/*.config.toml` ಚಲಾಯಿಸಿ.

**ದೀರ್ಘ Codex ಕಾರ್ಯವು ಚಾಲನೆಯ ಮಧ್ಯದಲ್ಲಿ ಕಡಿತಗೊಳ್ಳುತ್ತದೆ / ತಿರುವುಗಳ ನಡುವೆ ಖಾತೆಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ**
[ದೀರ್ಘಕಾಲ ಚಾಲನೆಯಲ್ಲಿರುವ ಕಾರ್ಯಗಳು](#long-running-tasks) ನೋಡಿ. ಸೆಷನ್ ಅಫಿನಿಟಿಯನ್ನು (ಕಾರ್ಯದ ಅವಧಿಗಿಂತ ಹೆಚ್ಚಿನ TTL) ಸಕ್ರಿಯಗೊಳಿಸಿ ಮತ್ತು `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` ಅನ್ನು ಹೆಚ್ಚಿಸಿ ಅಥವಾ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿ. `Idle timeout: no data from` ಗಾಗಿ OmniRoute ಲಾಗ್ಗಳಲ್ಲಿ grep ಮಾಡಿ.
