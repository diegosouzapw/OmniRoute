ಈ ಮಾರ್ಗದರ್ಶಿಯು OmniRouteಗೆ Kiro (AWS-ಹೋಸ್ಟ್ ಮಾಡಿದ AI ಕೋಡಿಂಗ್ ಸಹಾಯಕ) ಖಾತೆಗಳನ್ನು ಸೇರಿಸುವುದನ್ನು ವಿವರಿಸುತ್ತದೆ,
ವಿಶೇಷವಾಗಿ ಸೆಷನ್ ಸಂಘರ್ಷಗಳಿಲ್ಲದೆ ಏಕಕಾಲದಲ್ಲಿ ಹಲವು ಖಾತೆಗಳನ್ನು ಚಲಾಯಿಸುವುದರ ಮೇಲೆ ಗಮನಹರಿಸುತ್ತದೆ.

---

## ಹಿನ್ನೆಲೆ: Kiro ಖಾತೆಗಳು ಏಕೆ ಸಂಘರ್ಷಿಸಬಹುದು

ಸಕ್ರಿಯ ಸೆಷನ್ಗಳನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡಲು Kiroನ ಬ್ಯಾಕ್ಎಂಡ್ AWS SSO OIDC ಕ್ಲೈಂಟ್ ನೋಂದಣಿಗಳನ್ನು ಬಳಸುತ್ತದೆ.
ಮುಖ್ಯ ನಿರ್ಬಂಧ: **ಪ್ರತಿಯೊಂದು OIDC ಕ್ಲೈಂಟ್ ನೋಂದಣಿಯು ಒಂದೇ ಸಮಯದಲ್ಲಿ ಕೇವಲ ಒಂದು ಸಕ್ರಿಯ
ಸೆಷನ್ ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ**. ಅದೇ ನೋಂದಾಯಿತ ಕ್ಲೈಂಟ್ ಬಳಸಿ ಎರಡನೇ ಸಾಧನ ಅಥವಾ ಬಳಕೆದಾರರು ದೃಢೀಕರಿಸಿದಾಗ,
ಬ್ಯಾಕ್ಎಂಡ್ ಮೊದಲ ಖಾತೆಯ ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ.

ಮತ್ತೊಂದು Kiro ಖಾತೆಯು ಈಗಾಗಲೇ ಸೈನ್ ಇನ್ ಆಗಿರುವ ಯಂತ್ರದಲ್ಲಿ `kiro-cli login` ಚಲಾಯಿಸಿದಾಗ
ಸಮಸ್ಯೆಗಳನ್ನು ಉಂಟುಮಾಡುವ ಕಾರ್ಯವಿಧಾನವೂ ಇದೇ ಆಗಿದೆ — ಹೊಸ ಲಾಗಿನ್ ಮೊದಲ ಖಾತೆಯ ಟೋಕನ್ ಅನ್ನು
ಹಿಂಪಡೆಯುತ್ತದೆ.

## OmniRoute ಇದನ್ನು ಹೇಗೆ ಪರಿಹರಿಸುತ್ತದೆ (v3.8.0+)

v3.8.0ರಿಂದ ಪ್ರಾರಂಭಿಸಿ, ಪ್ರತಿಯೊಂದು Kiro ಸಂಪರ್ಕದ ಆಮದು ಸಮಯದಲ್ಲಿ OmniRoute
`registerClient()` (AWS SSO OIDC) ಅನ್ನು ಕರೆಮಾಡುತ್ತದೆ. ಇದು ಪ್ರತಿಯೊಂದು OmniRoute ಸಂಪರ್ಕಕ್ಕೂ ತನ್ನದೇ ಆದ ಮೀಸಲಾದ OIDC
ಕ್ಲೈಂಟ್ ನೋಂದಣಿಯನ್ನು ಒದಗಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಕ್ಲೈಂಟ್ ನೋಂದಣಿಯೂ ಸ್ವತಂತ್ರವಾಗಿರುವುದರಿಂದ, ಒಂದು ಖಾತೆಯನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವುದು ಅಥವಾ
ಮರು-ದೃಢೀಕರಿಸುವುದು ಬೇರೆ ಯಾವುದೇ ಖಾತೆಯ ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

ಈ ಪ್ರತ್ಯೇಕತೆಯು ರಿಫ್ರೆಶ್-ಟೋಕನ್ ಆಮದು ವಿಧಾನಗಳಿಗೆ ಅನ್ವಯಿಸುತ್ತದೆ ಮತ್ತು API-ಕೀ ದೃಢೀಕರಣವು
OIDC ರಿಫ್ರೆಶ್ ಸೆಷನ್ಗಳನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ತಪ್ಪಿಸುತ್ತದೆ:

| ಆಮದು ವಿಧಾನ                                              | ಪ್ರತ್ಯೇಕತೆಯ ಸ್ಥಿತಿ                                                                                                |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC ಸಾಧನ-ಕೋಡ್ ಹರಿವು                    | ಸಾಧನ-ಕೋಡ್ ಹರಿವನ್ನು ಪರಿಚಯಿಸಿದಾಗಿನಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ                                                              |
| **ಟೋಕನ್ ಆಮದು** (ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅನ್ನು ಕೈಯಾರೆ ಅಂಟಿಸುವುದು) | v3.8.0ರಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ                                                                                       |
| **Google / GitHub ಸಾಮಾಜಿಕ ಲಾಗಿನ್**                      | v3.8.0ರಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ                                                                                       |
| **ಸ್ವಯಂ-ಆಮದು** (kiro-cli SQLite)                        | v3.8.0ರಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ (SQLite ಮಾರ್ಗವು ಈಗಾಗಲೇ ಪ್ರತ್ಯೇಕವಾಗಿತ್ತು; SSO-ಕ್ಯಾಶ್ ಫಾಲ್ಬ್ಯಾಕ್ ಕೂಡ ಈಗ ಪ್ರತ್ಯೇಕವಾಗಿದೆ) |
| **API ಕೀ** (ದೀರ್ಘಾವಧಿಯ CodeWhisperer ಕೀ)                | ರಿಫ್ರೆಶ್ ಸೆಷನ್ ಇಲ್ಲ; ಕೀಲಿಯನ್ನು ಮೌಲ್ಯೀಕರಿಸಿ ಬೇರರ್ ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಆಗಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ                              |

## v3.8.0ಕ್ಕಿಂತ ಮೊದಲು ರಚಿಸಲಾದ ಸಂಪರ್ಕಗಳಿಗಾಗಿ ವಲಸೆ ಸೂಚನೆ

v3.8.0ಕ್ಕಿಂತ ಮೊದಲು ಆಮದು ಮಾಡಲಾದ ಸಂಪರ್ಕಗಳಲ್ಲಿ `providerSpecificData`ಯಲ್ಲಿ
ಮೀಸಲಾದ OIDC ಕ್ಲೈಂಟ್ ನೋಂದಣಿ ಸಂಗ್ರಹವಾಗಿರುವುದಿಲ್ಲ. ಈ ಸಂಪರ್ಕಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ, ಆದರೆ ಹಂಚಿದ
ಸಾಮಾಜಿಕ-ದೃಢೀಕರಣ ರಿಫ್ರೆಶ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಳಸುತ್ತವೆ; ಅಂದರೆ ಅಂತಹ ಎರಡು ಸಂಪರ್ಕಗಳು ಇನ್ನೂ ಪರಸ್ಪರದ
ಟೋಕನ್ಗಳನ್ನು ಅಮಾನ್ಯಗೊಳಿಸಬಹುದು.

**ಪ್ರತ್ಯೇಕತೆಯನ್ನು ಪಡೆಯಲು:** **Dashboard → Providers**ನಿಂದ ಹಳೆಯ ಸಂಪರ್ಕವನ್ನು ಅಳಿಸಿ ಮತ್ತು
ಬೆಂಬಲಿತ ಆಮದು ಹರಿವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ ಬಳಸಿ ಅದನ್ನು ಮರು-ಆಮದು ಮಾಡಿ. ಹೊಸದಾಗಿ ರಚಿಸಲಾದ ಎಲ್ಲ ಸಂಪರ್ಕಗಳು
ತಮ್ಮದೇ ಆದ ಕ್ಲೈಂಟ್ ನೋಂದಣಿಯನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪಡೆಯುತ್ತವೆ.

## ಎರಡು Kiro ಖಾತೆಗಳನ್ನು ಅಕ್ಕಪಕ್ಕದಲ್ಲಿ ಸೇರಿಸುವುದು

### ಪೂರ್ವಾಪೇಕ್ಷಿತಗಳು

- OmniRoute v3.8.0 ಅಥವಾ ನಂತರದ ಆವೃತ್ತಿ.
- ಕಾರ್ಯನಿರ್ವಹಿಸುವ Kiro ಖಾತೆ (ಇಮೇಲ್ + ಪಾಸ್ವರ್ಡ್, Google, ಅಥವಾ GitHub ಲಾಗಿನ್).
- ಐಚ್ಛಿಕವಾಗಿ ಎರಡನೇ Kiro ಖಾತೆ.

### ಹಂತ 1: ಮೊದಲ ಖಾತೆಯನ್ನು ಆಮದು ಮಾಡಿ

1. **Dashboard → Providers → Add Provider → Kiro** ತೆರೆಯಿರಿ.
2. ಇವುಗಳಲ್ಲಿ ಒಂದನ್ನು ಆಯ್ಕೆಮಾಡಿ:
   - **ಟೋಕನ್ ಆಮದು** — `aorAAAAAG`ನಿಂದ ಪ್ರಾರಂಭವಾಗುವ ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅನ್ನು ಅಂಟಿಸಿ.
   - **API ಕೀ** — ದೀರ್ಘಾವಧಿಯ Kiro / CodeWhisperer API ಕೀಲಿಯನ್ನು ಅಂಟಿಸಿ.
   - **Google / GitHub ಲಾಗಿನ್** — ಬ್ರೌಸರ್ನಲ್ಲಿ OAuth ಹರಿವನ್ನು ಪೂರ್ಣಗೊಳಿಸಿ.
   - **ಸ್ವಯಂ-ಆಮದು** — ಬಟನ್ ಕ್ಲಿಕ್ ಮಾಡಿ; OmniRoute ಸ್ಥಳೀಯ kiro-cli ಡೇಟಾಬೇಸ್ ಅಥವಾ
     `~/.aws/sso/cache`ನಿಂದ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳನ್ನು ಓದುತ್ತದೆ.
3. ಸಂಪರ್ಕವನ್ನು ಉಳಿಸಲಾಗುತ್ತದೆ. ರಿಫ್ರೆಶ್-ಟೋಕನ್ ಹರಿವುಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮೀಸಲಾದ
   OIDC ಕ್ಲೈಂಟ್ ಅನ್ನು ನೋಂದಾಯಿಸುತ್ತವೆ. API-ಕೀ ಹರಿವುಗಳು AWSನೊಂದಿಗೆ ಕೀಲಿಯನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತವೆ ಮತ್ತು ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುವುದಿಲ್ಲ.

### ಹಂತ 2: ಎರಡನೇ ಖಾತೆಯನ್ನು ಆಮದು ಮಾಡಿ

ಎರಡನೇ ಖಾತೆಗಾಗಿ ಹಂತ 1 ಅನ್ನು ಪುನರಾವರ್ತಿಸಿ. ಪ್ರತಿಯೊಂದು ಆಮದು ಪ್ರತ್ಯೇಕ OIDC
ಕ್ಲೈಂಟ್ ನೋಂದಣಿಯನ್ನು ರಚಿಸುವುದರಿಂದ, ಎರಡೂ ಸಂಪರ್ಕಗಳು ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತವೆ.

### ಹಂತ 3: ಎರಡೂ ಸಂಪರ್ಕಗಳು ಸಕ್ರಿಯವಾಗಿವೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ

1. **Dashboard → Providers** — ಎರಡೂ Kiro ಸಂಪರ್ಕಗಳು **ಸಕ್ರಿಯ** ಸ್ಥಿತಿಯನ್ನು ತೋರಿಸಬೇಕು.
2. **Dashboard → Health** — ಎರಡೂ ಸಂಪರ್ಕಗಳು ತಮ್ಮ ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಯನ್ನು ಪಾಸ್ ಮಾಡಬೇಕು.

### ಹಂತ 4: ಖಾತೆಗಳ ನಡುವೆ ರೂಟ್ ಮಾಡಲು ಕಾಂಬೊ ಬಳಸಿ

ಲೋಡ್-ಬ್ಯಾಲೆನ್ಸ್ ಮಾಡಲು ಅಥವಾ ಅವುಗಳ ನಡುವೆ ಫಾಲ್ಬ್ಯಾಕ್ ಮಾಡಲು ಎರಡೂ ಸಂಪರ್ಕಗಳನ್ನು ಗುರಿಗಳಾಗಿ ಹೊಂದಿರುವ ಕಾಂಬೊವನ್ನು ರಚಿಸಿ:

```
kiro/kiro-dev → kiro/kiro-pro
```

ಕಾಂಬೊ ಕಾನ್ಫಿಗರೇಶನ್ಗಾಗಿ [FEATURES.md](./FEATURES.md) ಮತ್ತು ರೂಟಿಂಗ್ ದಸ್ತಾವೇಜನ್ನು ನೋಡಿ.

## ಎಂಟರ್ಪ್ರೈಸ್ / IDC ಬಳಕೆದಾರರು

AWS IAM Identity Center (IDC) ಖಾತೆಗಳಿಗಾಗಿ, **Dashboard → Providers → Kiro → Device Code** ನಲ್ಲಿರುವ **AWS Builder ID / IDC device-code**
ಪ್ರವಾಹವನ್ನು ಬಳಸಿ. device-code ಪ್ರವಾಹವು
ಯಾವಾಗಲೂ ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತದೆ. ಈ ಸಂಪರ್ಕಗಳನ್ನು ಮರು-ಆಮದು ಮಾಡುವ ಅಗತ್ಯವಿಲ್ಲ.

ಡೀಫಾಲ್ಟ್ ಅಲ್ಲದ AWS ಪ್ರದೇಶದಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಎಂಟರ್ಪ್ರೈಸ್ ಬಳಕೆದಾರರು Import Token API ಮೂಲಕ
ಆಮದು ಮಾಡುವಾಗ ಪ್ರದೇಶವನ್ನು ನಿರ್ದಿಷ್ಟಪಡಿಸಬಹುದು:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

`region` ಕ್ಷೇತ್ರವನ್ನು ಬಿಟ್ಟರೆ, ಅದು ಡೀಫಾಲ್ಟ್ ಆಗಿ `us-east-1` ಅನ್ನು ಬಳಸುತ್ತದೆ.

## API-ಕೀ ಆಮದು ಪ್ರವಾಹ

API-ಕೀ ದೃಢೀಕರಣವು ದೀರ್ಘಾವಧಿಯ Kiro / AWS CodeWhisperer bearer ರುಜುವಾತುಗಳಿಗಾಗಿ ಆಗಿದೆ. ಇದು
OAuth refresh ಅನ್ನು ಬಳಸುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಹಂಚಿಕೊಂಡ OIDC session ಅಮಾನ್ಯೀಕರಣವನ್ನು ತಪ್ಪಿಸುತ್ತದೆ.

### ಡ್ಯಾಶ್ಬೋರ್ಡ್

1. **Dashboard -> Providers -> Kiro** ತೆರೆಯಿರಿ.
2. **API Key** ಆಯ್ಕೆಮಾಡಿ.
3. API ಕೀ ಮತ್ತು ಐಚ್ಛಿಕ AWS ಪ್ರದೇಶವನ್ನು ಅಂಟಿಸಿ (ಡೀಫಾಲ್ಟ್ ಆಗಿ `us-east-1`).
4. OmniRoute ಕೀಯನ್ನು ಮೌಲ್ಯೀಕರಿಸಿ ಸಂಪರ್ಕವನ್ನು ಉಳಿಸುತ್ತದೆ.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### ಆಂತರಿಕ ಒಪ್ಪಂದ

API route, `KiroService.validateApiKey()` ಅನ್ನು ಕರೆದು ಕೀಯನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; ಇದು
ಪ್ರದೇಶಕ್ಕೆ ಹೊಂದುವ CodeWhisperer/Amazon Q endpoint ವಿರುದ್ಧ `ListAvailableProfiles` ಅನ್ನು
ಬಳಸಿ, `profileArn` ಅನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ.

ಉಳಿಸಲಾದ ಸಂಪರ್ಕವು ಇದನ್ನು ಬಳಸುತ್ತದೆ:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

ಚಾಲನಾ ಸಮಯದಲ್ಲಿ, `KiroExecutor.buildHeaders()` ಕೀಯನ್ನು
`Authorization: Bearer <key>` ರೂಪದಲ್ಲಿ ಕಳುಹಿಸುತ್ತದೆ ಮತ್ತು `tokentype: API_KEY` ಅನ್ನು ಸೇರಿಸುತ್ತದೆ. Quota/profile ಕರೆಗಳು
ಅದೇ ಗುರುತನ್ನು ಬಳಸುತ್ತವೆ, ಇದರಿಂದ AWS ಆ bearer ಅನ್ನು OIDC ಅಥವಾ social access token ಬದಲಿಗೆ
ದೀರ್ಘಾವಧಿಯ API ಕೀ ಎಂದು ಪರಿಗಣಿಸುತ್ತದೆ.

## OIDC ಕ್ಲೈಂಟ್ ಅವಧಿ ಮುಕ್ತಾಯ

AWS SSO OIDC public clients ಸಾಮಾನ್ಯವಾಗಿ 90 ದಿನಗಳ ನಂತರ
ಅವಧಿ ಮುಗಿಯುತ್ತವೆ (`clientSecretExpiresAt`). ವೀಕ್ಷಣಾ ಸೌಲಭ್ಯಕ್ಕಾಗಿ OmniRoute ಈ timestamp ಅನ್ನು `providerSpecificData`
ನಲ್ಲಿ ಸಂಗ್ರಹಿಸುತ್ತದೆ. ಸುಮಾರು 90 ದಿನಗಳ ನಂತರ ಸಂಪರ್ಕವು refresh ಆಗುವುದನ್ನು ನಿಲ್ಲಿಸಿದರೆ, ಹೊಸ OIDC client registration ಪಡೆಯಲು
ಸಂಪರ್ಕವನ್ನು ಮರು-ಆಮದು ಮಾಡಿ. ಅವಧಿ ಮುಗಿದಾಗ ಸ್ವಯಂಚಾಲಿತ ಮರು-ನೋಂದಣಿಯನ್ನು
ಭವಿಷ್ಯದ ಸುಧಾರಣೆಯಾಗಿ ಗುರುತಿಸಲಾಗಿದೆ.

API-ಕೀ ಸಂಪರ್ಕಗಳು AWS SSO OIDC ಮೂಲಕ refresh ಆಗದಿರುವುದರಿಂದ ಅವುಗಳಿಗೆ OIDC client expiry
ಇರುವುದಿಲ್ಲ.

## ಸಮಸ್ಯೆ ಪರಿಹಾರ

### ಎರಡನೇ ಖಾತೆಯು ಪದೇಪದೇ ಲಾಗ್ ಔಟ್ ಆಗುತ್ತಿದೆ

- **Dashboard → Providers** ನಲ್ಲಿ ಎರಡೂ ಸಂಪರ್ಕಗಳನ್ನು ಪರಿಶೀಲಿಸಿ ಮತ್ತು ಪ್ರತಿಯೊಂದರ raw JSON ನಲ್ಲಿ ಶೂನ್ಯವಲ್ಲದ
  `clientId` ಕಾಣಿಸುತ್ತಿದೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ (ಮಾಹಿತಿ ಐಕಾನ್ ಮೂಲಕ ನೋಡಬಹುದು). ಯಾವುದಾದರೂ ಸಂಪರ್ಕದಲ್ಲಿ
  `clientId` ಇಲ್ಲದಿದ್ದರೆ, ಅದನ್ನು v3.8.0 ಗಿಂತ ಮೊದಲು ಆಮದು ಮಾಡಲಾಗಿದೆ — ಅದನ್ನು ಮರು-ಆಮದು ಮಾಡಿ.

### "Token validation failed" ದೋಷದೊಂದಿಗೆ ಆಮದು ವಿಫಲವಾಗುತ್ತದೆ

- refresh token `aorAAAAAG` ನೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುವುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ.
- OmniRoute `https://oidc.us-east-1.amazonaws.com` ಅನ್ನು (ಅಥವಾ ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ
  ಪ್ರದೇಶವನ್ನು) ತಲುಪಬಲ್ಲದು ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ. ನೀವು corporate proxy ಹಿಂದೆ ಇದ್ದರೆ,
  **Dashboard → Settings → Proxies** ನಲ್ಲಿ provider-level proxy ಹೊಂದಿಸಿ.

### API-ಕೀ ಆಮದು ವಿಫಲವಾಗುತ್ತದೆ

- ಕೀಯು Kiro / CodeWhisperer API ಕೀ ಆಗಿದೆಯೇ ಹೊರತು refresh token ಅಲ್ಲ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ.
- AWS ಪ್ರದೇಶವು ಕೀ/ಖಾತೆಗೆ ಹೊಂದುತ್ತದೆ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ. `us-east-1` ಡೀಫಾಲ್ಟ್ ಆಗಿದೆ.
- ಕೀಯು `ListAvailableProfiles` ಅನ್ನು ಕರೆಯಲು ಸಮರ್ಥವಾಗಿರಬೇಕು; ಇಲ್ಲವಾದರೆ ಅಗತ್ಯವಿರುವ
  `profileArn` ಅನ್ನು OmniRoute ನಿರ್ಧರಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಇತರ ಸಮಸ್ಯೆಗಳಿಗಾಗಿ, ಮುಖ್ಯ [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) ಅನ್ನು ನೋಡಿ.
