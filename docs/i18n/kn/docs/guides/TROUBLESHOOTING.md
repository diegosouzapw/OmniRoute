## ವಿವರವಾದ ದೋಷನಿವಾರಣೆ

---

### ಉಚಿತ ಪೂರೈಕೆದಾರರಲ್ಲಿ ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆ (429 / 400 / 401)

**ಲಕ್ಷಣ**: ಉಚಿತ/ದೃಢೀಕರಣವಿಲ್ಲದ ಪೂರೈಕೆದಾರರೊಂದಿಗೆ (opencode, auggie, ಇತ್ಯಾದಿ) `model: "auto"` ಬಳಸುವಾಗ, ಉತ್ತರಗಳ ಬದಲಿಗೆ ಆಗಾಗ್ಗೆ `HTTP 429`, `400`, ಅಥವಾ `401` ದೊರೆಯುತ್ತದೆ. ಕೆಲವು ಕ್ಷಣಗಳ ನಂತರ ಅದೇ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಿದಾಗ ವಿನಂತಿಗಳು ಯಶಸ್ವಿಯಾಗುತ್ತವೆ, ಆದರೆ ಸ್ವಯಂಚಾಲಿತ ವ್ಯವಸ್ಥೆ (cron ಕಾರ್ಯಗಳು, ಏಜೆಂಟ್ಗಳು, ಸ್ಕ್ರಿಪ್ಟ್ಗಳು) ಮೊದಲ ವೈಫಲ್ಯದಲ್ಲೇ ಸ್ಥಗಿತಗೊಳ್ಳುತ್ತದೆ.

**ಮೂಲ ಕಾರಣ**: ಸ್ವತಂತ್ರವಾದ ಮೂರು ವೈಫಲ್ಯ ವಿಧಾನಗಳು ಒಟ್ಟುಗೂಡುತ್ತವೆ:

1. **ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿ (`429`)**: ಉಚಿತ ಶ್ರೇಣಿಗಳು ಪ್ರತಿ ಕಾಲಾವಧಿಗೆ ಕೋಟಾವನ್ನು ಜಾರಿಗೊಳಿಸಬಹುದು. ಸಮಾನಾಂತರ ಕರೆಗಳ ಹಠಾತ್ ಹೆಚ್ಚಳವು ಅದನ್ನು ಖಾಲಿಗೊಳಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಕಾಲಾವಧಿ ಮರುಹೊಂದುವವರೆಗೆ ಮುಂದಿನ ವಿನಂತಿಯನ್ನು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ.
2. **ಪಾಸ್ಥ್ರೂನಲ್ಲಿರುವ ದೋಷಪೂರಿತ ಮಾದರಿ (`400`/`401`)**: `auto/*` ಪೂಲ್ಗಳಲ್ಲಿ `opencode` ನಿಂದ ಪಾಸ್ಥ್ರೂ ಮಾದರಿಗಳು ಇರಬಹುದು; ಅವು ಕ್ಯಾಟಲಾಗ್ನಲ್ಲಿ ನೋಂದಾಯಿಸಲ್ಪಟ್ಟಿದ್ದರೂ ಸಕ್ರಿಯ ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ (ಉದಾ. `oc/north-mini-code-free` → `401`). ಸ್ವಯಂ-ರೂಟರ್ ಒಂದನ್ನು ಪ್ರಯತ್ನಿಸಿ, ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಫಾಲ್ಬ್ಯಾಕ್ ಪ್ರಾರಂಭವಾಗುವ ಮೊದಲು ದೋಷವು ಮುಂದಕ್ಕೆ ಪ್ರಸಾರವಾಗುತ್ತದೆ.
3. **ಏಕಕಾಲಿಕತೆಯ ವರ್ಧನೆ (ಲೋಡ್ನಡಿ `429`)**: ಅನೇಕ ಏಜೆಂಟ್/cron ಸೆಷನ್ಗಳು ಒಂದೇ ಸಮಯದಲ್ಲಿ `auto` ಅನ್ನು ಬಳಸಿದಾಗ, ಒಟ್ಟಾರೆ ವಿನಂತಿ ದರವು ಉಚಿತ ಪೂರೈಕೆದಾರರು ಸಹಿಸಬಲ್ಲ ಮಿತಿಯನ್ನು ಮೀರುತ್ತದೆ; ಇದರಿಂದ ನ್ಯಾಯಸಮ್ಮತ ಕರೆಗಳನ್ನೂ ದುರುಪಯೋಗವೆಂದು ಗುರುತಿಸಲಾಗುತ್ತದೆ.

**ಪರಿಶೀಲಿತ ಪರಿಹಾರ (ಸಮುದಾಯದಿಂದ ವರದಿಯಾದದ್ದು, 2026-08-10)**: ಉಚಿತ ಶ್ರೇಣಿಯ ಏರಿಳಿತದಿಂದ ವಿಫಲಗೊಳ್ಳುವ ಬದಲು, ರೊಟೇಶನ್, ಏಕಕಾಲಿಕತೆ ಮತ್ತು ಫಾಲ್ಬ್ಯಾಕ್ ಅದನ್ನು ನಿಭಾಯಿಸುವಂತೆ ಮೂರು ಪರಿಸರ ವೇರಿಯಬಲ್ಗಳನ್ನು ಹೊಂದಿಸಿ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ಬಂದಾಗ ಮತ್ತೊಂದು ಮಾದರಿ/ಪೂರೈಕೆದಾರರಿಗೆ ಬದಲಿಸಿ (ದೋಷಪೂರಿತ ಪಾಸ್ಥ್ರೂ ಮಾದರಿಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ಹೆವಿವೇಯ್ಟ್ ಪ್ರವೇಶಕ್ಕೆ ಸ್ಪಷ್ಟ ಗರಿಷ್ಠ ಮಿತಿ (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಹೊಂದಿಸಿಲ್ಲ: ವಿನಂತಿ-ಎಣಿಕೆ ಮಿತಿಯಿಲ್ಲ, ಕೆಳಗಿನ ಟಿಪ್ಪಣಿ ನೋಡಿ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ತಕ್ಷಣದ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ 503 ಬದಲಿಗೆ ಹೆವಿವೇಯ್ಟ್ ಸಾಮರ್ಥ್ಯಕ್ಕಾಗಿ ಹೆಚ್ಚು ಸಮಯದ ಮಿತಿಗೊಳಿಸಿದ ಕಾಯುವಿಕೆ
```

ಇವುಗಳನ್ನು OmniRoute ಪ್ರಕ್ರಿಯೆಯ ಪರಿಸರದಲ್ಲಿ ಹೊಂದಿಸಿ (ಡೀಮನ್ನಲ್ಲಿ, ಉದಾ. LaunchAgent plist ಅಥವಾ `systemctl edit` ಮೂಲಕ), ನಂತರ OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ. ರೊಟೇಶನ್ ಫ್ಲ್ಯಾಗ್ ಅತ್ಯಧಿಕ ಪರಿಣಾಮ ಬೀರುವ ಏಕೈಕ ನಿಯಂತ್ರಣವಾಗಿದೆ: ಇದು ಗಂಭೀರ ವೈಫಲ್ಯವನ್ನು ಪೂಲ್ನಲ್ಲಿರುವ ಆರೋಗ್ಯಕರ ಪೂರೈಕೆದಾರರ ವಿರುದ್ಧ ಪಾರದರ್ಶಕ ಮರುಪ್ರಯತ್ನವಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ.

**ಟಿಪ್ಪಣಿ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ಒಂದೇ ಸಮಯದಲ್ಲಿ ಎಷ್ಟು ಹೆವಿವೇಯ್ಟ್ — ದೀರ್ಘ-ಸಂದರ್ಭದ — ವಿನಂತಿಗಳು ಚಲಿಸುತ್ತವೆ ಎಂಬುದನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ; ಈ ಮಿತಿಯು ಪ್ರವೇಶ ದ್ವಾರವೇ ಹೊರತು ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆಯಲ್ಲ. **#503-fanout ನವೀಕರಣ:** ಈ ವೇರಿಯಬಲ್ ಅನ್ನು ಇನ್ನು ಮುಂದೆ ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಹೊಂದಿಸಲಾಗುವುದಿಲ್ಲ (ಈಗ ಮೇಲೆ ತೋರಿಸಿದಂತೆ ಸ್ಪಷ್ಟವಾಗಿ ಸಂರಚಿಸಿದಾಗ ಮಾತ್ರ ಇದು ಅನ್ವಯಿಸುತ್ತದೆ) — ಬದಲಿಗೆ ಹೆವಿವೇಯ್ಟ್ ಪ್ರವೇಶವನ್ನು ಸ್ವಯಂ-ನಿರ್ಧರಿತ ಬೈಟ್ ಬಜೆಟ್ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ನಿಯಂತ್ರಿಸುತ್ತದೆ; ಇದು ಹೋಸ್ಟ್ನ ನೈಜ ಮೆಮೊರಿ ಗರಿಷ್ಠ ಮಿತಿಗೆ ಅನುಗುಣವಾಗಿ ಸ್ವತಃ ಸ್ಕೇಲ್ ಆಗುತ್ತದೆ. ಆದ್ದರಿಂದ ಹೊಸ ನಿಯೋಜನೆಯು ಈ ವೇರಿಯಬಲ್ ಅನ್ನು ಹೊಂದಿಸದೆಯೇ ಬಹಳ ಕಡಿಮೆ `503 chat_admission_busy` ನಿರಾಕರಣೆಗಳನ್ನು ಕಾಣಬೇಕು; ಇದನ್ನು ಇಲ್ಲಿ ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸುವುದೂ ದಾಖಲಿಸಿದಂತೆಯೇ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ. ಸ್ಪಷ್ಟ ಬೈಟ್-ಬಜೆಟ್ ಓವರ್ರೈಡ್ಗಳನ್ನು 8 MiB–2 GiB ನಡುವೆ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ. `413 body_exceeds_budget` ತಾತ್ಕಾಲಿಕವಲ್ಲ: ಆ ಬೈಟ್ ಬಜೆಟ್ ಅನ್ನು ಹೆಚ್ಚಿಸಿ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ಅನ್ನು ಕಡಿಮೆ ಮಾಡಿ, ಅಥವಾ ಪ್ರಕ್ರಿಯೆಯ ಮೆಮೊರಿ ಗರಿಷ್ಠ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ. `inflight_bytes_budget` ಶೆಡ್ ತಾತ್ಕಾಲಿಕ ಸಂಪನ್ಮೂಲ ಸ್ಪರ್ಧೆಯಾಗಿದ್ದು, ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ಪ್ರತಿ-ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆಯನ್ನು (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ಮತ್ತು `RATE_LIMIT_AUTO_ENABLE` ಪ್ರತ್ಯೇಕವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತವೆ — `.env.example` ನೋಡಿ.

**ಇದು ಕೆಲಸ ಮಾಡಿದೆ ಎಂದು ಪರಿಶೀಲಿಸುವುದು ಹೇಗೆ**: ನಿಮ್ಮ ಏಜೆಂಟ್/cron ಅನ್ನು ತ್ವರಿತವಾಗಿ ಸತತವಾಗಿ ಎರಡು ಬಾರಿ ಚಲಾಯಿಸಿ ಮತ್ತು ಎರಡೂ ಯಶಸ್ವಿಯಾಗುತ್ತವೆ ಎಂದು ದೃಢಪಡಿಸಿ. ಪರಿಹಾರಕ್ಕೂ ಮೊದಲು, ಎರಡನೇ ಚಾಲನೆಯು ಸಾಮಾನ್ಯವಾಗಿ `429`/`401` ಅನ್ನು ಎಸೆಯುತ್ತದೆ. ಪರಿಹಾರದ ನಂತರ, ವೈಫಲ್ಯಗಳನ್ನು (ಇದ್ದರೆ) ಪಾರದರ್ಶಕವಾಗಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಕರೆ ಪೂರ್ಣಗೊಳ್ಳುತ್ತದೆ. ನೀವು `curl /monitoring/health` ಅನ್ನು ಚಲಾಯಿಸಿ, ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕಗಳಲ್ಲಿನ `rateLimitedUntil` ಕ್ಷೇತ್ರ ಮತ್ತು ಬಾಧಿತ ಪೂರೈಕೆದಾರರ `circuitBreakers.providerBreakers[].state` ಅನ್ನು ಸಹ ಗಮನಿಸಬಹುದು — ಸ್ಥಿತಿಯು `CLOSED`, `DEGRADED`, `OPEN`, ಅಥವಾ `HALF_OPEN` ಗಳಲ್ಲಿ ಒಂದಾಗಿರುತ್ತದೆ (`src/shared/utils/circuitBreaker.ts` ನೋಡಿ), ಮತ್ತು ನಿರಂತರವಾಗಿ ವಿಫಲಗೊಳ್ಳುವ ಪೂರೈಕೆದಾರರು ಮರುಹೊಂದಿಸುವ ಕಾಲಾವಧಿಯು ಪರಿಶೀಲನಾ ವಿನಂತಿಯನ್ನು ಅನುಮತಿಸುವ ಮೊದಲು `CLOSED → DEGRADED → OPEN` ಗೆ ಬದಲಾಗುತ್ತಾರೆ (`HALF_OPEN`).

**ನೀವು ಇನ್ನೂ 429 ಅನ್ನು ನೋಡುತ್ತಿದ್ದರೆ**: ಆ provider ಗಾಗಿ ಸಕ್ರಿಯ account ತನ್ನ _quota_ ಅನ್ನು ನಿಜವಾಗಿಯೂ ಸಂಪೂರ್ಣವಾಗಿ ಬಳಸಿಕೊಂಡಿದೆ (ಕೇವಲ rate ಅಲ್ಲ). OmniRoute dashboard → Providers → Accounts ನಲ್ಲಿ ಅದೇ provider ಗಾಗಿ ಎರಡನೇ account ಅನ್ನು ಸೇರಿಸಿ, ಅಥವಾ ಮತ್ತೊಂದು ಉಚಿತ provider ಅನ್ನು (ಉದಾ. `routeway`, `auggie`) ಮಿಶ್ರವಾಗಿ ಬಳಸಿ. Rotation ತಾತ್ಕಾಲಿಕ rate/400/401 ಸಮಸ್ಯೆಗಳಿಗೆ ಮಾತ್ರ ಸಹಾಯ ಮಾಡುತ್ತದೆ; quota ಸಂಪೂರ್ಣವಾಗಿ ಖಾಲಿಯಾಗಿದ್ದರೆ ಎರಡನೇ credential ಅಥವಾ ಬೇರೆ provider ಅಗತ್ಯವಿರುತ್ತದೆ.

**vision models (`auto/vision`, `bazaarlink/*`) ನಲ್ಲಿ 403 ಕಂಡುಬಂದರೆ**: ಸಂಪರ್ಕಿತ account ನಲ್ಲಿ vision ಒಳಗೊಂಡಿರುವ paid plan ಇಲ್ಲ, ಅಥವಾ API key ಗೆ ಸಾಕಷ್ಟು permissions ಇಲ್ಲ. key scope ನಲ್ಲಿ vision/multimodal ಸೇರಿದೆ ಎಂಬುದನ್ನು provider dashboard ನಲ್ಲಿ ಪರಿಶೀಲಿಸಿ, ಅಥವಾ paid tier account ಅನ್ನು ಸಂಪರ್ಕಿಸಿ ಮತ್ತು ಅದನ್ನು vision target ಆಗಿ ಇರಿಸಿ.

## npm install ಎಚ್ಚರಿಕೆಗಳು (ERESOLVE / peer / deprecated)

ನೀವು `npm install -g omniroute` ಅನ್ನು ರನ್ ಮಾಡಿದಾಗ, `npm warn ERESOLVE`, peer-dependency ಸೂಚನೆಗಳು ಮತ್ತು `deprecated` ಸಂದೇಶಗಳಂತಹ ಎಚ್ಚರಿಕೆಗಳ ದೊಡ್ಡ ಪಟ್ಟಿಯನ್ನು ನೋಡಬಹುದು. **ಇವು ನಿರೀಕ್ಷಿತವಾಗಿದ್ದು, ಹಾನಿಕಾರಕವಲ್ಲ.** ಔಟ್ಪುಟ್ನಲ್ಲಿ `added <N> packages` ಕಾಣಿಸಿಕೊಂಡರೆ ನಿಮ್ಮ ಇನ್ಸ್ಟಾಲೇಶನ್ ಯಶಸ್ವಿಯಾಗಿದೆ.

peer-dependency ಪರಿಹಾರದ ಎಚ್ಚರಿಕೆಗಳನ್ನು ತಡೆಹಿಡಿಯಲು, OmniRoute ಬೆಂಬಲಿಸುವ ಇನ್ಸ್ಟಾಲ್ ಸ್ವರೂಪವನ್ನು ಬಳಸಿ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ಕೇವಲ `ERESOLVE` ಮತ್ತು peer-dependency ಸೂಚನೆಗಳನ್ನು ತಡೆಹಿಡಿಯುತ್ತದೆ. ಬಳಕೆಯಲ್ಲಿಲ್ಲದಿರುವಿಕೆ ಕುರಿತ ಸೂಚನೆಗಳು ಗೋಚರಿಸುತ್ತಲೇ ಇರುತ್ತವೆ, ಏಕೆಂದರೆ ಅವು ಪರೋಕ್ಷವಾದ ಮೂರನೇ-ಪಕ್ಷದ ಪ್ಯಾಕೇಜ್ಗಳಿಂದ ಬರುತ್ತವೆ; ಇವು ಇನ್ಸ್ಟಾಲೇಶನ್ ವಿಫಲವಾಗಿದೆ ಎಂದು ಸೂಚಿಸುವುದಿಲ್ಲ.

ಈ ಎಚ್ಚರಿಕೆಗಳು OmniRoute ನಿಯಂತ್ರಿಸದ ಮೂರನೇ-ಪಕ್ಷದ ಪ್ಯಾಕೇಜ್ಗಳಲ್ಲಿನ ಹಳೆಯ peer-dependency ಶ್ರೇಣಿಗಳಿಂದ ಬರುತ್ತವೆ:

1. **`marked-terminal` ಗೆ `marked >=1 <16` ಬೇಕಾಗಿದೆ, ಆದರೆ `marked@18` ಕಂಡುಬಂದಿದೆ** — ಪ್ರಾಯೋಗಿಕವಾಗಿ ಇದು ಸರಿಯಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ; upstream peer ಶ್ರೇಣಿ ಕೇವಲ ಹಳೆಯದಾಗಿದೆ.
2. **`deprecated prebuild-install@7.1.3`** — ಪರೋಕ್ಷವಾದ native-binary ಪಡೆಯುವ ಸಹಾಯಕ. ಪಿನ್ ಮಾಡಲಾದ `wreq-js` transport binding ಅನ್ನು ಇನ್ಸ್ಟಾಲ್ ಮಾಡಲು ಇದನ್ನು
   ಬಳಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು web-cookie provider transport ಸೆಟಪ್ ವಿಫಲವಾಗಿದೆ ಎಂದು ಇದು ಸೂಚಿಸುವುದಿಲ್ಲ.

**ಯಾವುದೇ ಕ್ರಮದ ಅಗತ್ಯವಿಲ್ಲ** — upstream ಪ್ಯಾಕೇಜ್ಗಳನ್ನು fork ಮಾಡದೆ ಈ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಿಶ್ಶಬ್ದಗೊಳಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಆಂಟಿವೈರಸ್ನ ತಪ್ಪು ಪಾಸಿಟಿವ್ಗಳು

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md` ಅನ್ನು `MD:HttpRequest-inf[Susp]` ಎಂದು ಕ್ವಾರಂಟೈನ್ ಮಾಡುತ್ತದೆ

**ಇದು ತಪ್ಪು ಪಾಸಿಟಿವ್ ಆಗಿದೆ. ಯಾವುದೂ ಸೋಂಕಿಗೆ ಒಳಗಾಗಿಲ್ಲ ಮತ್ತು ಯಾವುದೇ ಕ್ರಮದ ಅಗತ್ಯವಿಲ್ಲ.**

ಹಲವಾರು HTTP ವಿನಂತಿಗಳಂತೆ ಕಾಣುವ ಲಿಂಕ್ಗಳನ್ನು ಹೊಂದಿರುವ ಸರಳ ಪಠ್ಯ/Markdown ಫೈಲ್ಗಳನ್ನು ಗುರುತಿಸುವ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು Avast ಮತ್ತು AVG ಚಲಾಯಿಸುತ್ತವೆ. OmniRouteನ `README.md`, npm ಪ್ಯಾಕೇಜ್ನೊಳಗೆ ವಿತರಿಸಲ್ಪಡುತ್ತದೆ (ಅದನ್ನು `package.json` → `files` ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾಗಿದೆ), ಆದ್ದರಿಂದ ಜಾಗತಿಕ ಸ್ಥಾಪನೆಯ ಸಂದರ್ಭದಲ್ಲಿ ಅದು `node_modules/omniroute/README.md` ನಲ್ಲಿ ಇರಿಸಲ್ಪಡುತ್ತದೆ — ಮತ್ತು ಅದು ಸುಮಾರು 15 `http://localhost:20128/...` ಉದಾಹರಣೆಗಳನ್ನು ಹೊಂದಿದೆ (MCP HTTP/SSE ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು, A2A `.well-known` URL ಮತ್ತು `curl` ತುಣುಕುಗಳು). ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸಲು ಆ ಲಿಂಕ್ ಸಾಂದ್ರತೆಯೇ ಸಾಕಾಗುತ್ತದೆ.

ಇದು ಇತ್ತೀಚೆಗಷ್ಟೇ ಪ್ರಾರಂಭವಾಗಿದ್ದರೆ: ಫೈಲ್ನ ಸ್ವರೂಪ ಬದಲಾಗಿಲ್ಲ. README ಯ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳ ಕೋಷ್ಟಕವು ವಿಸ್ತರಿಸಿದೆ (MCP HTTP + SSE + A2A ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ) ಮತ್ತು ಹೆಚ್ಚಿನ `curl` ಉದಾಹರಣೆಗಳನ್ನು ಸೇರಿಸಲಾಗಿದೆ; ಇದರಿಂದ ಅದು ಮಿತಿಯನ್ನು ಮೀರಿದೆ.

ಈ ಫೈಲ್ ಯಾವುದೇ ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದ ವಿಷಯವಿಲ್ಲದ ನಿಷ್ಕ್ರಿಯ ದಸ್ತಾವೇಜಾಗಿದೆ. ನೀವು ಅದನ್ನು ಕ್ವಾರಂಟೈನ್ನಿಂದ ಸುರಕ್ಷಿತವಾಗಿ ಮರುಸ್ಥಾಪಿಸಬಹುದು.

**ಏನು ಮಾಡಬೇಕು:**

1. **ಅಧಿಸೂಚನೆಗಳನ್ನು ನಿಲ್ಲಿಸಿ** — ನಿಮ್ಮ ಆಂಟಿವೈರಸ್ನಲ್ಲಿ ಸ್ಥಾಪನಾ ಡೈರೆಕ್ಟರಿಯನ್ನು ಹೊರತುಪಡಿಸಿ
   (Avast: Settings → Exceptions), ನಿಮ್ಮ ಜಾಗತಿಕ `node_modules` ಪಥ ಮತ್ತು/ಅಥವಾ
   OmniRoute ಡೇಟಾ ಡೈರೆಕ್ಟರಿ (`~/.omniroute/`) ಅನ್ನು ಸೇರಿಸಿ.
2. **ತಪ್ಪು ಪಾಸಿಟಿವ್ ಕುರಿತು ವರದಿ ಮಾಡಿ** — <https://www.avast.com/false-positive-file-form.php>,
   ಕ್ವಾರಂಟೈನ್ ಮಾಡಲಾದ `README.md` ಅನ್ನು ಲಗತ್ತಿಸಿ. ಪಠ್ಯ ಫೈಲ್ಗೆ ಮಾರಾಟಗಾರರ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅತಿಯಾಗಿ ಪ್ರತಿಕ್ರಿಯಿಸುತ್ತಿರುವುದರಿಂದ, ಇದೇ ಎಲ್ಲರಿಗೂ ಸಹಾಯ ಮಾಡುವ ಪರಿಹಾರವಾಗಿದೆ.

**ನಮ್ಮ ಕಡೆಯಿಂದ ಇದನ್ನು ಏಕೆ "ಸರಿಪಡಿಸುವುದಿಲ್ಲ":** ಎಲ್ಲ ಉದಾಹರಣೆಗಳೂ `http://localhost` ಆಗಿವೆ ಮತ್ತು ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ ಪ್ರಮಾಣಪತ್ರದ ತೊಂದರೆಯಿಲ್ಲದೆ localhost ಅನ್ನು `https` ಆಗಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಒಬ್ಬ ಮಾರಾಟಗಾರರ ಹ್ಯೂರಿಸ್ಟಿಕ್ನಿಂದ ತಪ್ಪಿಸಿಕೊಳ್ಳಲು ದಸ್ತಾವೇಜನ್ನು ವಿರೂಪಗೊಳಿಸುವುದು, ಸ್ಕ್ಯಾನರ್ ದೋಷವನ್ನು ತೃಪ್ತಿಪಡಿಸುವುದಕ್ಕಾಗಿ ಪ್ರತಿಯೊಬ್ಬ ಓದುಗರಿಗೂ ತೊಂದರೆ ಉಂಟುಮಾಡುತ್ತದೆ.

### Kaspersky, Desktop ಆ್ಯಪ್ ಅನ್ನು `PDM:Trojan.Win32.Generic` ಎಂದು ಗುರುತಿಸುತ್ತದೆ

**ಇದು ವರ್ತನೆ ಆಧಾರಿತ ಹ್ಯೂರಿಸ್ಟಿಕ್ನಿಂದ ಉಂಟಾದ ತಪ್ಪು ಪಾಸಿಟಿವ್. ಯಾವುದೂ ಸೋಂಕಿಗೆ ಒಳಗಾಗಿಲ್ಲ.** Kaspersky ಯ `PDM:` ಪೂರ್ವಪ್ರತ್ಯಯವು, ತಿಳಿದಿರುವ ಮಾಲ್ವೇರ್ಗೆ ಹೋಲಿಸುವ ಬದಲು ಸ್ಥಾಪಕವು _ಏನು ಮಾಡುತ್ತದೆ_ ಎಂಬುದನ್ನು ನಿರ್ಣಯಿಸುವ ಅದರ Proactive Defense Module (System Watcher) ನಿಂದ ತೀರ್ಪು ಬಂದಿದೆ ಎಂಬುದನ್ನು ಸೂಚಿಸುತ್ತದೆ. ಇದು ಪ್ರಚೋದಿತವಾದಾಗ, Kaspersky ಸಂಪೂರ್ಣ ಸ್ಥಾಪನೆಯನ್ನು "ರೋಲ್ ಬ್ಯಾಕ್" ಮಾಡುತ್ತದೆ — ಅದು ಈಗಾಗಲೇ ಬರೆದಿದ್ದ ಫೈಲ್ಗಳನ್ನು ಅಳಿಸುತ್ತದೆ — ಆದ್ದರಿಂದ ಆ್ಯಪ್ ಹಾಳಾಗುತ್ತದೆ ಅಥವಾ ಕಾಣೆಯಾಗುತ್ತದೆ.

ಅದು ಗುರುತಿಸುವ ಫೈಲ್ಗಳು Desktop ಆ್ಯಪ್ನೊಂದಿಗೆ ಬಂಡಲ್ ಮಾಡಲಾದ, ಘೋಷಿತ ಮುಕ್ತ-ಮೂಲ ಅವಲಂಬನೆಗಳ ಪ್ರಮಾಣಿತ ಭಾಗಗಳಾಗಿವೆ, ಉದಾಹರಣೆಗೆ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ಮತ್ತು
  `workerProcessEntry.js` — ಆ್ಯಪ್ನೊಳಗಿನ ಪೂರೈಕೆದಾರರ ಲಾಗಿನ್ ಮತ್ತು ಬ್ರೌಸರ್-ಬೆಂಬಲಿತ ಚಾಟ್ಗಾಗಿ ಬಳಸುವ ಬ್ರೌಸರ್-ಸ್ವಯಂಚಾಲನಾ ಲೈಬ್ರರಿಯಾದ [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ವೆಬ್-ಕುಕೀ ಪೂರೈಕೆದಾರರಿಗಾಗಿ ಬ್ರೌಸರ್-ಫಿಂಗರ್ಪ್ರಿಂಟ್ ಮಾಡಲಾದ HTTP ಗೆ ಬಳಸುವ, ನಿರ್ದಿಷ್ಟ ಆವೃತ್ತಿಗೆ ಸ್ಥಿರಗೊಳಿಸಲಾದ `wreq-js` ನೆಟಿವ್ ಬೈಂಡಿಂಗ್ (`<arch>` ಎಂಬುದು `x64` ಅಥವಾ `arm64` ಆಗಿರುತ್ತದೆ).

**ಇದು ಏಕೆ ಪ್ರಚೋದಿತವಾಗುತ್ತದೆ:** Windows ಸ್ಥಾಪಕವು **ಇನ್ನೂ ಕೋಡ್-ಸಹಿ ಮಾಡಲ್ಪಟ್ಟಿಲ್ಲ**, ಆದ್ದರಿಂದ ಸಹಿ ಮಾಡದ NSIS ಸ್ಥಾಪಕವು ಯಾವುದೇ ವಿಶ್ವಾಸಾರ್ಹತೆಯನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ ಮತ್ತು ವರ್ತನೆ ಆಧಾರಿತ ಹ್ಯೂರಿಸ್ಟಿಕ್ಗಳು ಗರಿಷ್ಠ ಆಕ್ರಮಣಶೀಲತೆಯೊಂದಿಗೆ ಚಲಿಸುತ್ತವೆ. ಇದರೊಂದಿಗೆ ಬಂಡಲ್ ಮಾಡಲಾದ ನೆಟಿವ್ DLL ಮತ್ತು `%LOCALAPPDATA%\Programs\OmniRoute` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾದ ನೂರಾರು `.js` ಫೈಲ್ಗಳು (Next.js standalone ಬಿಲ್ಡ್ನ ಹ್ಯಾಶ್-ಪ್ರತ್ಯಯವುಳ್ಳ ಪ್ಯಾಕೇಜ್ ಡೈರೆಕ್ಟರಿಗಳನ್ನು ಒಳಗೊಂಡಂತೆ) ಸೇರಿಕೊಂಡಾಗ, ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸಲು ಅದು ಸಾಕಾಗುತ್ತದೆ. ಕೋಡ್ ಸಹಿ ಮಾಡುವುದನ್ನು ಯೋಜಿಸಲಾಗಿದೆ; ಅದು ಜಾರಿಯಾಗುವವರೆಗೆ ಹೊಸ ಬಿಡುಗಡೆಗಳಲ್ಲಿ ಇದು ಮರುಕಳಿಸಬಹುದು.

**ಏನು ಮಾಡಬೇಕು:**

1. **ಮೊದಲು ನಿಮ್ಮ ಡೌನ್ಲೋಡ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ** (ಫೈಲ್ ತಿರುಚಲ್ಪಟ್ಟಿರುವ ಸಾಧ್ಯತೆಯನ್ನು ತಳ್ಳಿಹಾಕುತ್ತದೆ). ಪ್ರತಿಯೊಂದು ಬಿಡುಗಡೆಯೂ `latest.yml` ಅನ್ನು ಪ್ರಕಟಿಸುತ್ತದೆ; ಅದರ `sha512` ಕ್ಷೇತ್ರವು (base64) `OmniRoute.Setup.<version>.exe` ಸ್ಥಾಪಕವನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. PowerShell ನಲ್ಲಿ, ಸ್ಥಾಪಕವನ್ನು ಹೊಂದಿರುವ ಫೋಲ್ಡರ್ನಿಂದ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ಔಟ್ಪುಟ್ `latest.yml` → `sha512` ಗೆ ಹೊಂದಿಕೆಯಾಗಬೇಕು. ಹೊಂದಿಕೆಯಾಗದಿದ್ದರೆ, ಫೈಲ್ ಅನ್ನು ಅಳಿಸಿ ಮತ್ತು [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) ನಿಂದ ಮಾತ್ರ ಪುನಃ ಡೌನ್ಲೋಡ್ ಮಾಡಿ.
2. **ಮರುಸ್ಥಾಪಿಸಿ + ಹೊರತುಪಡಿಸಿ** — ಕ್ವಾರಂಟೈನ್ನಿಂದ ರೋಲ್ ಬ್ಯಾಕ್ ಮಾಡಲಾದ ಅಂಶಗಳನ್ನು ಮರುಸ್ಥಾಪಿಸಿ ಮತ್ತು
   `%LOCALAPPDATA%\Programs\OmniRoute` ಗಾಗಿ ಹೊರತುಪಡಿಸುವಿಕೆಯನ್ನು ಸೇರಿಸಿ (Kaspersky → Settings → Threats and Exclusions),
   ನಂತರ ಮರುಸ್ಥಾಪನೆ ಮಾಡಿ.
3. **ತಪ್ಪು ಪಾಸಿಟಿವ್ ಕುರಿತು ವರದಿ ಮಾಡಿ** — <https://opentip.kaspersky.com/>. ಬಳಕೆದಾರರು ಸಲ್ಲಿಸುವ FP
   ವರದಿಗಳು ಅನುಮತಿ ಪಟ್ಟಿಗೆ ಸೇರಿಸುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ನಿಜವಾಗಿಯೂ ವೇಗಗೊಳಿಸುತ್ತವೆ.

## Node.js ಹೊಂದಾಣಿಕೆ

<a name="nodejs-compatibility"></a>

### ಲಾಗಿನ್ ಪುಟ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ ಅಥವಾ "Module self-registration" ದೋಷವನ್ನು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** ನೀವು OmniRoute ಅನುಮೋದಿಸಿದ ಸುರಕ್ಷಿತ ರನ್ಟೈಮ್ ಕನಿಷ್ಠ ಮಿತಿಯ ಹೊರಗಿನ Node.js ಆವೃತ್ತಿಯನ್ನು ಚಲಾಯಿಸುತ್ತಿದ್ದೀರಿ. OmniRoute ಅಗತ್ಯಪಡಿಸುವ ಭದ್ರತಾ ಪ್ಯಾಚ್ನ ಕನಿಷ್ಠ ಮಿತಿಗಿಂತ ಕೆಳಗಿರುವ ಹಳೆಯ Node 22 ಅಥವಾ 24 ಪ್ಯಾಚ್ ಮಟ್ಟವನ್ನು ಬಳಸುವುದು ಅತ್ಯಂತ ಸಾಮಾನ್ಯ ಸಂದರ್ಭವಾಗಿದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಲಾಗಿನ್ ಪುಟವು ಖಾಲಿ ಪರದೆ ಅಥವಾ ಸರ್ವರ್ ದೋಷವನ್ನು ತೋರಿಸುತ್ತದೆ
- ಕನ್ಸೋಲ್ನಲ್ಲಿ `Error: Module did not self-register` ಅಥವಾ ಅಂತಹುದೇ ನೇಟಿವ್ ಬೈಂಡಿಂಗ್ ದೋಷಗಳು ಕಾಣಿಸುತ್ತವೆ
- ರನ್ಟೈಮ್ ಬೆಂಬಲಿತ ಸುರಕ್ಷಿತ ನೀತಿಯ ಹೊರಗಿದ್ದರೆ, ಲಾಗಿನ್ ಪುಟವು ನಿಮ್ಮ Node ಆವೃತ್ತಿಯೊಂದಿಗೆ **ಕಿತ್ತಳೆ ಬಣ್ಣದ ಎಚ್ಚರಿಕೆ ಬ್ಯಾನರ್** ಅನ್ನು ತೋರಿಸುತ್ತದೆ

**ಪರಿಹಾರ:**

1. ಬೆಂಬಲಿತ Node.js LTS ಬಿಡುಗಡೆಯನ್ನು ಸ್ಥಾಪಿಸಿ (ಶಿಫಾರಸು: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ನಿಮ್ಮ ಆವೃತ್ತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ: `node --version` ಎಂಬುದು 24.x LTS ಶ್ರೇಣಿಯಲ್ಲಿ `v24.0.0` ಅಥವಾ ಅದಕ್ಕಿಂತ ಹೊಸದನ್ನು ತೋರಿಸಬೇಕು
3. OmniRoute ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ: `npm install -g omniroute`
4. ಮರುಪ್ರಾರಂಭಿಸಿ: `omniroute`

> **ಬೆಂಬಲಿತ ಸುರಕ್ಷಿತ ಆವೃತ್ತಿಗಳು:** `>=22.22.2 <23` ಅಥವಾ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ಮತ್ತು Node.js 26 ಸಂಪೂರ್ಣವಾಗಿ ಬೆಂಬಲಿತವಾಗಿವೆ.

### npm v11+: `better-sqlite3` ಸ್ಥಾಪನೆಯಾಗಿಲ್ಲ (ಮಾಡ್ಯೂಲ್ ಕಂಡುಬಂದಿಲ್ಲ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ಕಾರಣ:** npm v11 (Node.js 24+ ಜೊತೆಗೆ ಒದಗಿಸಲಾಗುತ್ತದೆ) ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಐಚ್ಛಿಕ
ಡಿಪೆಂಡೆನ್ಸಿಗಳ ಸ್ಥಾಪನಾ ಸ್ಕ್ರಿಪ್ಟ್ಗಳನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ. `better-sqlite3` ಅನ್ನು `optionalDependencies`
ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಿರುವುದರಿಂದ ಮತ್ತು ಅದಕ್ಕೆ ನೇಟಿವ್ ಕಂಪೈಲೇಶನ್ (`node-gyp rebuild`) ಅಗತ್ಯವಿರುವುದರಿಂದ, npm ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಸರ್ವರ್ ಪ್ರಾರಂಭವಾಗುವಾಗ `Cannot find module 'better-sqlite3'` ದೋಷದೊಂದಿಗೆ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ
- `ls node_modules/better-sqlite3` ಎಂಬುದು "No such file or directory" ಎಂದು ತೋರಿಸುತ್ತದೆ
- `npm ls better-sqlite3` ಎಂಬುದು `(empty)` ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಪರಿಹಾರ:**

1. ಸ್ಥಾಪನಾ ಸ್ಕ್ರಿಪ್ಟ್ಗಳನ್ನು ಅನುಮೋದಿಸಿ ಮತ್ತು ಮರುಸ್ಥಾಪಿಸಿ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ಅಥವಾ ಪೂರ್ವನಿರ್ಮಿತ ಪ್ಯಾಕೇಜ್ ಅನ್ನು ಕೈಯಾರೆ ಸ್ಥಾಪಿಸಿ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ಅದು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ಕಾರಣ:** ಜಾಗತಿಕ `npm install -g omniroute` ನಂತರ, ಪ್ಯಾಕೇಜ್ನೊಳಗಿನ `better-sqlite3` ನೇಟಿವ್ ಬೈನರಿಯನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಾಲನೆಯಲ್ಲಿರುವುದಕ್ಕಿಂತ ವಿಭಿನ್ನ ಆರ್ಕಿಟೆಕ್ಚರ್ ಅಥವಾ Node.js ABI ಗಾಗಿ ಕಂಪೈಲ್ ಮಾಡಿರಬಹುದು. ಪೂರ್ವನಿರ್ಮಿತ ಬೈನರಿ ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಹೊಂದಿಕೆಯಾಗದಿದ್ದಾಗ, macOS ನಲ್ಲಿ (Apple Silicon ಮತ್ತು Intel ಎರಡರಲ್ಲೂ) ಇದು ಸಾಮಾನ್ಯವಾಗಿದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಸರ್ವರ್ ಪ್ರಾರಂಭವಾಗುವಾಗಲೇ `dlopen` ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- ದೋಷವು `slice is not valid mach-o file` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ
- ಸಂಪೂರ್ಣ ಉದಾಹರಣೆ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ಪರಿಹಾರ — ನಿಮ್ಮ ಸ್ಥಳೀಯ ಪರಿಸರಕ್ಕಾಗಿ ಮರುನಿರ್ಮಿಸಿ (Node.js ಆವೃತ್ತಿಯನ್ನು ಕೆಳಗಿಳಿಸುವ ಅಗತ್ಯವಿಲ್ಲ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ಸೂಚನೆ:** ಇದು ನಿಮ್ಮ ಸ್ಥಳೀಯ Node.js ಆವೃತ್ತಿ ಮತ್ತು CPU ಆರ್ಕಿಟೆಕ್ಚರ್ಗೆ ಹೊಂದುವಂತೆ ನೇಟಿವ್ ಬೈಂಡಿಂಗ್ ಅನ್ನು ಮರುಕಂಪೈಲ್ ಮಾಡಿ, ಬೈನರಿ ಅಸಾಮರಸ್ಯವನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. ಅಧಿಕೃತವಾಗಿ ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ಶ್ರೇಣಿಯು **`>=22.22.2 <23` ಅಥವಾ `>=24.0.0 <27`** ಆಗಿದೆ (`src/shared/utils/nodeRuntimeSupport.ts` ನಲ್ಲಿರುವ `SUPPORTED_NODE_RANGE`, `package.json` ನ `engines` ಕ್ಷೇತ್ರದೊಂದಿಗೆ ಹೊಂದಿಸಲಾಗಿದೆ). Node.js 24.x LTS (Krypton) ಮತ್ತು Node.js 26 ಅನ್ನು `better-sqlite3` v12.x ಜೊತೆಗೆ ಸಂಪೂರ್ಣವಾಗಿ ಬೆಂಬಲಿಸಲಾಗುತ್ತದೆ.

## ಪ್ರಾಕ್ಸಿ ಸಮಸ್ಯೆಗಳು

<a name="proxy-issues"></a>

### ಪೂರೈಕೆದಾರರ ಮೌಲ್ಯೀಕರಣವು "fetch failed" ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** API ಕೀ ಮೌಲ್ಯೀಕರಣ ಎಂಡ್ಪಾಯಿಂಟ್ (`POST /api/providers/validate`) ಈ ಹಿಂದೆ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಉಪೇಕ್ಷಿಸುತ್ತಿತ್ತು, ಇದರಿಂದ ಪ್ರಾಕ್ಸಿ ರೂಟಿಂಗ್ ಅಗತ್ಯವಿರುವ ಪರಿಸರಗಳಲ್ಲಿ ವೈಫಲ್ಯಗಳು ಉಂಟಾಗುತ್ತಿದ್ದವು.

**ಪರಿಹಾರ (v3.5.5+):** ಇದನ್ನು ಈಗ ಸರಿಪಡಿಸಲಾಗಿದೆ. ಪೂರೈಕೆದಾರರ ಮೌಲ್ಯೀಕರಣವು `runWithProxyContext` ಮೂಲಕ ರೂಟ್ ಆಗುತ್ತದೆ ಮತ್ತು ಪೂರೈಕೆದಾರ-ಮಟ್ಟದ ಹಾಗೂ ಜಾಗತಿಕ ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪಾಲಿಸುತ್ತದೆ.

### ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಯು "fetch failed" ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

**ಕಾರಣ:** ಹಿನ್ನೆಲೆಯ OAuth ಟೋಕನ್ ನವೀಕರಣವು ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೂ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸುತ್ತಿರಲಿಲ್ಲ.

**ಪರಿಹಾರ (v3.5.5+):** ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನಾ ಶೆಡ್ಯೂಲರ್ ಈಗ ನವೀಕರಣವನ್ನು ಪ್ರಯತ್ನಿಸುವ ಮೊದಲು ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೂ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. v3.5.5+ ಗೆ ನವೀಕರಿಸಿ.

### SOCKS5 ಪ್ರಾಕ್ಸಿಯು "invalid onRequestStart method" ದೋಷವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಕಾರಣ:** Node.js 22 ನಲ್ಲಿ, undici@8 ಡಿಸ್ಪ್ಯಾಚರ್ Node ನ ಅಂತರ್ನಿರ್ಮಿತ `fetch()` ಅನುಷ್ಠಾನದೊಂದಿಗೆ ಹೊಂದಾಣಿಕೆಯಾಗುವುದಿಲ್ಲ.

**ಪರಿಹಾರ (v3.5.5+):** ಪ್ರಾಕ್ಸಿ ಡಿಸ್ಪ್ಯಾಚರ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ OmniRoute ಈಗ undici ಯ ಸ್ವಂತ `fetch()` ಫಂಕ್ಷನ್ ಅನ್ನು ಬಳಸುತ್ತದೆ, ಇದು ಸ್ಥಿರವಾದ ನಡವಳಿಕೆಯನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ. v3.5.5+ ಗೆ ನವೀಕರಿಸಿ.

### WSL ಅಡಿಯಲ್ಲಿ MITM ಪ್ರಾಕ್ಸಿ: Windows ಹೋಸ್ಟ್ನಲ್ಲಿರುವ ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳನ್ನು ಪ್ರತಿಬಂಧಿಸಲಾಗುತ್ತಿಲ್ಲ

**ಕಾರಣ:** MITM ಪ್ರಾಕ್ಸಿ ಮತ್ತು ಅದರ CA ಪ್ರಮಾಣಪತ್ರವು OmniRoute ಚಾಲನೆಯಾಗುವ ಪರಿಸರದಲ್ಲಿ ಸ್ಥಾಪನೆಯಾಗುತ್ತವೆ. WSL ಅಡಿಯಲ್ಲಿ ಆ ಪರಿಸರವು Linux ಗೆಸ್ಟ್ ಆಗಿರುತ್ತದೆ, ಆದರೆ AI ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳು (Kiro, Trae, Copilot, Zed, …) Windows ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಾಲನೆಯಾಗುತ್ತವೆ. ಹೋಸ್ಟ್ ಆ್ಯಪ್ಗಳು ಗೆಸ್ಟ್ನ ಪ್ರಮಾಣಪತ್ರ ಸ್ಟೋರ್ ಅನ್ನು ನಂಬುವುದಿಲ್ಲ ಮತ್ತು ಗೆಸ್ಟ್ನ ಸಿಸ್ಟಮ್ ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ರೂಟ್ ಆಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಅಲ್ಲಿ ಡೆಸ್ಕ್ಟಾಪ್ ಪ್ರತಿಬಂಧವು ಸಕ್ರಿಯವಾಗುವುದಿಲ್ಲ.

**ಶಿಫಾರಸು:** ನೀವು ಪ್ರತಿಬಂಧಿಸಲು ಬಯಸುವ ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳು ಇರುವ ಅದೇ OS ನಲ್ಲಿ OmniRoute ಅನ್ನು ನೇಟಿವ್ ಆಗಿ ಚಲಾಯಿಸಿ (Windows ಆ್ಯಪ್ಗಳಿಗೆ Windows; macOS/Linux ಗೂ ಇದೇ ಅನ್ವಯಿಸುತ್ತದೆ). ಹೋಸ್ಟ್ ಆ್ಯಪ್ಗಳನ್ನು ಗುರಿಯಾಗಿಸಿಕೊಂಡು OmniRoute ಅನ್ನು WSL ಒಳಗೆ ಇಟ್ಟುಕೊಳ್ಳಲು, ರಚಿಸಲಾದ CA ಪ್ರಮಾಣಪತ್ರವನ್ನು Windows ಹೋಸ್ಟ್ನಲ್ಲಿ ಕೈಯಾರೆ ವಿಶ್ವಾಸಾರ್ಹಗೊಳಿಸಬೇಕು ಮತ್ತು ಪ್ರತಿಯೊಂದು ಹೋಸ್ಟ್ ಆ್ಯಪ್ನ ನೆಟ್ವರ್ಕ್/ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು WSL ಪ್ರಾಕ್ಸಿ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ನಿರ್ದೇಶಿಸಬೇಕು — ಇದು ಬೆಂಬಲಿಸದ, ಸುಲಭವಾಗಿ ಮುರಿಯಬಹುದಾದ ಸಂರಚನೆಯಾಗಿದೆ.

## ಪೂರೈಕೆದಾರರ ಸಮಸ್ಯೆಗಳು

### "Language model did not provide messages"

**ಕಾರಣ:** ಪೂರೈಕೆದಾರರ ಕೋಟಾ ಮುಗಿದಿದೆ.

**ಪರಿಹಾರ:**

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ ಕೋಟಾ ಟ್ರ್ಯಾಕರ್ ಪರಿಶೀಲಿಸಿ
2. ಫಾಲ್ಬ್ಯಾಕ್ ಹಂತಗಳನ್ನು ಹೊಂದಿರುವ ಕಾಂಬೊ ಬಳಸಿ
3. ಕಡಿಮೆ ವೆಚ್ಚದ/ಉಚಿತ ಹಂತಕ್ಕೆ ಬದಲಿಸಿ

### ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆ

**ಕಾರಣ:** ಚಂದಾದಾರಿಕೆಯ ಕೋಟಾ ಮುಗಿದಿದೆ.

**ಪರಿಹಾರ:**

- ಫಾಲ್ಬ್ಯಾಕ್ ಸೇರಿಸಿ: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- ಕಡಿಮೆ ವೆಚ್ಚದ ಬ್ಯಾಕಪ್ ಆಗಿ GLM/MiniMax ಬಳಸಿ

### OAuth ಟೋಕನ್ ಅವಧಿ ಮುಗಿದಿದೆ

OmniRoute ಟೋಕನ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನವೀಕರಿಸುತ್ತದೆ. ಸಮಸ್ಯೆಗಳು ಮುಂದುವರಿದರೆ:

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರ → ಮರುಸಂಪರ್ಕಿಸಿ
2. ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವನ್ನು ಅಳಿಸಿ ಮತ್ತು ಮರುಸೇರಿಸಿ

### Kiro ಬಹು-ಖಾತೆ: ಎರಡನೇ ಖಾತೆಯು ಮೊದಲನೆಯದನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ

**ಕಾರಣ:** Kiro ನ ಬ್ಯಾಕೆಂಡ್ ಪ್ರತಿ OIDC ಕ್ಲೈಂಟ್ ನೋಂದಣಿಗೆ ಒಂದೇ ಸಕ್ರಿಯ ಸೆಷನ್ ಅನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ.
ಎರಡು ಖಾತೆಗಳು ಒಂದೇ ನೋಂದಾಯಿತ ಕ್ಲೈಂಟ್ ಅನ್ನು ಹಂಚಿಕೊಂಡಾಗ (v3.8.0 ಗಿಂತ ಮೊದಲು ಆಮದು ಮಾಡಲಾದ ಸಂಪರ್ಕಗಳು),
ಒಂದು ಖಾತೆಯ ಟೋಕನ್ ಅನ್ನು ನವೀಕರಿಸುವುದು ಮತ್ತೊಂದು ಖಾತೆಯ ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ.

**ಪರಿಹಾರ (v3.8.0+):** ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಸಂಪರ್ಕಗಳನ್ನು ಮರು-ಆಮದು ಮಾಡಿ.
v3.8.0 ರಿಂದ ಪ್ರಾರಂಭಿಸಿ, **ಟೋಕನ್ ಆಮದು**, **Google/GitHub ಸಾಮಾಜಿಕ ಲಾಗಿನ್**, ಅಥವಾ **ಸ್ವಯಂ-ಆಮದು** ಮೂಲಕ ರಚಿಸಲಾದ ಪ್ರತಿಯೊಂದು ಹೊಸ Kiro ಸಂಪರ್ಕವು ತನ್ನದೇ ಆದ
ಮೀಸಲಾದ OIDC ಕ್ಲೈಂಟ್ ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನೋಂದಾಯಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಸಂಪರ್ಕವು ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತದೆ ಮತ್ತು ಒಂದು
ಖಾತೆಯನ್ನು ನವೀಕರಿಸುವುದರಿಂದ ಬೇರೆ ಯಾವುದೇ ಖಾತೆಯ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

v3.8.0 ಕ್ಕಿಂತ _ಮೊದಲು_ ಆಮದು ಮಾಡಲಾದ ಸಂಪರ್ಕಗಳು ಪ್ರತಿ-ಸಂಪರ್ಕದ ಕ್ಲೈಂಟ್
ನೋಂದಣಿಯನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ. ಆ ಸಂಪರ್ಕಗಳು ಹಂಚಿಕೆಯ ಸಾಮಾಜಿಕ-ದೃಢೀಕರಣ ರಿಫ್ರೆಶ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಳಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ.
ಪ್ರತ್ಯೇಕತೆಯನ್ನು ಪಡೆಯಲು, ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು ವಿಭಾಗದಿಂದ ಹಳೆಯ ಸಂಪರ್ಕವನ್ನು ಅಳಿಸಿ ಮತ್ತು
ಮೂರು ಆಮದು ಪ್ರಕ್ರಿಯೆಗಳಲ್ಲಿ ಯಾವುದಾದರೂ ಒಂದರ ಮೂಲಕ ಅದನ್ನು ಮರುಸೇರಿಸಿ.

ಎರಡು Kiro ಖಾತೆಗಳನ್ನು ಅಕ್ಕಪಕ್ಕದಲ್ಲಿ ಸೇರಿಸುವ ಸಂಪೂರ್ಣ ವಿವರಗಳು ಮತ್ತು ಹಂತ-ಹಂತದ ಸೂಚನೆಗಳಿಗಾಗಿ,
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) ನೋಡಿ.

## ಕ್ಲೌಡ್ ಸಮಸ್ಯೆಗಳು

### ಕ್ಲೌಡ್ ಸಿಂಕ್ ದೋಷಗಳು

1. `BASE_URL` ನಿಮ್ಮ ಚಾಲನೆಯಲ್ಲಿರುವ ಇನ್ಸ್ಟೆನ್ಸ್ಗೆ ಸೂಚಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (ಉದಾ., `http://localhost:20128`)
2. `CLOUD_URL` ನಿಮ್ಮ ಕ್ಲೌಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಸೂಚಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (ಉದಾ., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ಮೌಲ್ಯಗಳನ್ನು ಸರ್ವರ್-ಸೈಡ್ ಮೌಲ್ಯಗಳೊಂದಿಗೆ ಹೊಂದಾಣಿಕೆಯಲ್ಲಿ ಇರಿಸಿ

### ಕ್ಲೌಡ್ನಲ್ಲಿ `stream=false` ಬಳಸಿದಾಗ 500 ಮರಳುತ್ತದೆ

**ಲಕ್ಷಣ:** ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದ ಕರೆಗಳಿಗೆ ಕ್ಲೌಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ನಲ್ಲಿ `Unexpected token 'd'...` ಕಾಣಿಸುತ್ತದೆ.

**ಕಾರಣ:** ಕ್ಲೈಂಟ್ JSON ನಿರೀಕ್ಷಿಸುತ್ತಿರುವಾಗ ಅಪ್ಸ್ಟ್ರೀಮ್ SSE ಪೇಲೋಡ್ ಅನ್ನು ಮರಳಿಸುತ್ತದೆ.

**ಪರಿಹಾರೋಪಾಯ:** ಕ್ಲೌಡ್ಗೆ ನೇರ ಕರೆಗಳಿಗಾಗಿ `stream=true` ಬಳಸಿ. ಸ್ಥಳೀಯ ರನ್ಟೈಮ್ SSE→JSON ಫಾಲ್ಬ್ಯಾಕ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ.

### ಕ್ಲೌಡ್ ಸಂಪರ್ಕಗೊಂಡಿದೆ ಎಂದು ತೋರಿಸಿದರೂ "Invalid API key" ಎನ್ನುತ್ತದೆ

1. ಸ್ಥಳೀಯ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ಹೊಸ ಕೀಲಿಯನ್ನು ರಚಿಸಿ (`/api/keys`)
2. ಕ್ಲೌಡ್ ಸಿಂಕ್ ಅನ್ನು ಚಲಾಯಿಸಿ: Cloud ಸಕ್ರಿಯಗೊಳಿಸಿ → Sync Now
3. ಹಳೆಯ/ಸಿಂಕ್ ಆಗದ ಕೀಲಿಗಳು ಕ್ಲೌಡ್ನಲ್ಲಿ ಇನ್ನೂ `401` ಅನ್ನು ಮರಳಿಸಬಹುದು

## Docker ಸಮಸ್ಯೆಗಳು

### Docker IPv6 / ಸಂಪರ್ಕ ಮರುಹೊಂದಿಕೆ

<a name="docker-ipv6"></a>

**ಲಕ್ಷಣಗಳು:** `curl http://localhost:20128/v1/models` ಅನ್ನು ಚಲಾಯಿಸಿದಾಗ `curl: (56) Recv failure: Connection reset by peer` ಮರಳುತ್ತದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಮತ್ತು ದೃಢೀಕರಣ ಅಗತ್ಯವಿಲ್ಲದ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ, ಆದರೆ ದೃಢೀಕೃತ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು ವಿಫಲವಾಗುತ್ತವೆ — ಇದು ದೃಢೀಕರಣ ಸಮಸ್ಯೆಯಂತೆ ಕಾಣಿಸಿದರೂ ವಾಸ್ತವವಾಗಿ ಹಾಗಲ್ಲ.

**ಕಾರಣ:** `docker run -p 20128:20128` ಎರಡೂ `0.0.0.0` (IPv4) ಮತ್ತು `::` (IPv6) ನಲ್ಲಿ ಪ್ರಕಟಿಸುತ್ತದೆ, ಆದರೆ ಕಂಟೇನರ್ನೊಳಗಿನ ಪ್ರಕ್ರಿಯೆಯು IPv4 ನಲ್ಲಿ ಮಾತ್ರ ಆಲಿಸುತ್ತದೆ. `localhost` ಮೊದಲು `::1` ಗೆ ಪರಿಹಾರವಾಗುವ ಹೋಸ್ಟ್ಗಳಲ್ಲಿ, ಸಂಪರ್ಕವು ಅದರ ಹಿಂದೆ ಯಾವುದೇ ಲಿಸನರ್ ಇಲ್ಲದ IPv6 ಪ್ರಕಟಿತ ಪೋರ್ಟ್ಗೆ ತಲುಪುತ್ತದೆ → ಸಂಪರ್ಕ ಮರುಹೊಂದಿಕೆಯಾಗುತ್ತದೆ.

**ಸರಿಪಡಿಸುವಿಕೆ:**

1. **ತ್ವರಿತ ರೋಗನಿರ್ಣಯ:** `curl -4 http://localhost:20128/v1/models` ಅನ್ನು ಚಲಾಯಿಸಿ. ಇದು `-4` ಜೊತೆಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸಿ, ಅದಿಲ್ಲದೆ ವಿಫಲವಾದರೆ, ನಿಮ್ಮಲ್ಲಿ IPv6 ಬೈಂಡ್ ಹೊಂದಾಣಿಕೆಯಿಲ್ಲ.
2. **ಶಾಶ್ವತ ಸರಿಪಡಿಸುವಿಕೆ:** ನಿಮ್ಮ `docker run` ಕಮಾಂಡ್ನಲ್ಲಿ `-p 127.0.0.1:20128:20128` ಬಳಸುವ ಮೂಲಕ ಸ್ಪಷ್ಟವಾಗಿ IPv4 ಗೆ ಬೈಂಡ್ ಮಾಡಿ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ಇದು IPv4 ಬೈಂಡ್ ಅನ್ನು ಒತ್ತಾಯಿಸುತ್ತದೆ ಮತ್ತು ಎಲ್ಲಾ ಹೋಸ್ಟ್ ಇಂಟರ್ಫೇಸ್ಗಳಲ್ಲಿ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದನ್ನೂ ತಪ್ಪಿಸುತ್ತದೆ.

### CLI ಉಪಕರಣ ಸ್ಥಾಪನೆಯಾಗಿಲ್ಲ ಎಂದು ತೋರಿಸುತ್ತದೆ

1. ರನ್ಟೈಮ್ ಫೀಲ್ಡ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. ಪೋರ್ಟಬಲ್ ಮೋಡ್ಗಾಗಿ: `runner-cli` ಇಮೇಜ್ ಟಾರ್ಗೆಟ್ ಬಳಸಿ (CLIಗಳು ಬಂಡಲ್ ಆಗಿವೆ)
3. ಹೋಸ್ಟ್ ಮೌಂಟ್ ಮೋಡ್ಗಾಗಿ: `CLI_EXTRA_PATHS` ಅನ್ನು ಹೊಂದಿಸಿ ಮತ್ತು ಹೋಸ್ಟ್ bin ಡೈರೆಕ್ಟರಿಯನ್ನು ಓದಲು-ಮಾತ್ರವಾಗಿ ಮೌಂಟ್ ಮಾಡಿ
4. `installed=true` ಮತ್ತು `runnable=false` ಆಗಿದ್ದರೆ: ಬೈನರಿ ಕಂಡುಬಂದಿದೆ, ಆದರೆ ಹೆಲ್ತ್ಚೆಕ್ ವಿಫಲವಾಗಿದೆ

## ದೋಷನಿವಾರಣೆ

### ಲಾಗ್ ಫೈಲ್ಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ

ನಿಮ್ಮ `.env` ಫೈಲ್ನಲ್ಲಿ `APP_LOG_TO_FILE=true` ಅನ್ನು ಹೊಂದಿಸಿ. ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್ಗಳನ್ನು `logs/` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ.
ಸೆಟ್ಟಿಂಗ್ಗಳಲ್ಲಿ ಕಾಲ್ ಲಾಗ್ ಪೈಪ್ಲೈನ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ ವಿನಂತಿ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳನ್ನು `${DATA_DIR}/call_logs/` ಅಡಿಯಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ.
ಪೈಪ್ಲೈನ್ ಕ್ಯಾಪ್ಚರ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ, ಸ್ಟ್ರೀಮ್ ಚಂಕ್ ಪೇಲೋಡ್ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಲು `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ಅನ್ನು ಹೊಂದಿಸಿ, ಅಥವಾ KB ಯಲ್ಲಿ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಮಿತಿಯನ್ನು ಬದಲಾಯಿಸಲು `CALL_LOG_PIPELINE_MAX_SIZE_KB` ಅನ್ನು ಸರಿಹೊಂದಿಸಿ.

### ಪೂರೈಕೆದಾರರ ಸ್ಥಿತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ

```bash
# ಸ್ಥಿತಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್
http://localhost:20128/dashboard/health

# API ಸ್ಥಿತಿ ಪರಿಶೀಲನೆ
curl http://localhost:20128/api/monitoring/health
```

### ರನ್ಟೈಮ್ ಸಂಗ್ರಹಣೆ

- ಮುಖ್ಯ ಸ್ಥಿತಿ: `${DATA_DIR}/storage.sqlite` (ಪೂರೈಕೆದಾರರು, ಕಾಂಬೊಗಳು, ಅಲಿಯಾಸ್ಗಳು, ಕೀಲಿಗಳು, ಸೆಟ್ಟಿಂಗ್ಗಳು)
- ಬಳಕೆ: `storage.sqlite` ನಲ್ಲಿನ SQLite ಟೇಬಲ್ಗಳು (`usage_history`, `call_logs`, `proxy_logs`) + ಐಚ್ಛಿಕ `${DATA_DIR}/call_logs/`
- ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್ಗಳು: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ಆಗಿರುವಾಗ)
- ಕಾಲ್ ಲಾಗ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು: ಕಾಲ್ ಲಾಗ್ ಪೈಪ್ಲೈನ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs ಪುಟದ **Clean history** ಕ್ರಿಯೆಯು `call_logs`, ಹಳೆಯ
`request_detail_logs`, ಮತ್ತು ಸ್ಥಳೀಯ `${DATA_DIR}/call_logs/` ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಡೈರೆಕ್ಟರಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.

## ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಸಮಸ್ಯೆಗಳು

### ಪೂರೈಕೆದಾರರು OPEN ಸ್ಥಿತಿಯಲ್ಲಿ ಸಿಲುಕಿದ್ದಾರೆ

ಪೂರೈಕೆದಾರರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ OPEN ಆಗಿರುವಾಗ, ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ವಿನಂತಿಗಳನ್ನು ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ**ಕ್ಕೆ ಹೋಗಿ
2. ಸಮಸ್ಯೆಗೊಳಗಾದ ಪೂರೈಕೆದಾರರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಕಾರ್ಡ್ ಪರಿಶೀಲಿಸಿ
3. ಎಲ್ಲಾ ಬ್ರೇಕರ್ಗಳನ್ನು ತೆರವುಗೊಳಿಸಲು **ಎಲ್ಲವನ್ನೂ ಮರುಹೊಂದಿಸಿ** ಕ್ಲಿಕ್ ಮಾಡಿ ಅಥವಾ ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ಕಾಯಿರಿ
4. ಮರುಹೊಂದಿಸುವ ಮೊದಲು ಪೂರೈಕೆದಾರರು ನಿಜವಾಗಿಯೂ ಲಭ್ಯವಿದ್ದಾರೆಯೇ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ

### ಪೂರೈಕೆದಾರರು ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಅನ್ನು ಪದೇಪದೇ ಟ್ರಿಗರ್ ಮಾಡುತ್ತಿದ್ದಾರೆ

ಪೂರೈಕೆದಾರರು ಪದೇಪದೇ OPEN ಸ್ಥಿತಿಗೆ ಪ್ರವೇಶಿಸಿದರೆ:

1. ವೈಫಲ್ಯದ ಮಾದರಿಗಾಗಿ **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಆರೋಗ್ಯ → ಪೂರೈಕೆದಾರರ ಆರೋಗ್ಯ** ಪರಿಶೀಲಿಸಿ
2. **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು**ಗೆ ಹೋಗಿ ಮತ್ತು ವೈಫಲ್ಯದ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ
3. ಪೂರೈಕೆದಾರರು API ಮಿತಿಗಳನ್ನು ಬದಲಾಯಿಸಿದ್ದಾರೆಯೇ ಅಥವಾ ಮರು-ದೃಢೀಕರಣದ ಅಗತ್ಯವಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ
4. ಲೇಟೆನ್ಸಿ ಟೆಲಿಮೆಟ್ರಿಯನ್ನು ಪರಿಶೀಲಿಸಿ — ಹೆಚ್ಚಿನ ಲೇಟೆನ್ಸಿಯು ಕಾಲಾವಧಿ ಮೀರುವಿಕೆಯಿಂದ ಉಂಟಾಗುವ ವೈಫಲ್ಯಗಳಿಗೆ ಕಾರಣವಾಗಬಹುದು

## ಆಡಿಯೊ ಲಿಪ್ಯಂತರ ಸಮಸ್ಯೆಗಳು

### "ಬೆಂಬಲವಿಲ್ಲದ ಮಾದರಿ" ದೋಷ

- ಮೊದಲ ವಿಭಾಗವು ನೀವು ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವ ಪೂರೈಕೆದಾರರಾಗಿರುವ model id ಅನ್ನು ಬಳಸಿ (`openai/whisper-1`, `openrouter/deepgram/nova-3`). ಕೇವಲ `deepgram/nova-3` ಬಳಸಲು ಸ್ಥಳೀಯ Deepgram ಕೀ ಅಗತ್ಯವಿದೆ.
- **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು**ನಲ್ಲಿ ಪೂರೈಕೆದಾರರು ಸಂಪರ್ಕಗೊಂಡಿರುವುದನ್ನು ಪರಿಶೀಲಿಸಿ

### ಲಿಪ್ಯಂತರವು ಖಾಲಿಯಾಗಿ ಮರಳುತ್ತದೆ ಅಥವಾ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

- ಬೆಂಬಲಿತ ಆಡಿಯೊ ಸ್ವರೂಪಗಳನ್ನು ಪರಿಶೀಲಿಸಿ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ಫೈಲ್ ಗಾತ್ರವು ಪೂರೈಕೆದಾರರ ಮಿತಿಗಳೊಳಗೆ ಇರುವುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ (ಸಾಮಾನ್ಯವಾಗಿ < 25MB)
- ಪೂರೈಕೆದಾರರ ಕಾರ್ಡ್ನಲ್ಲಿ ಪೂರೈಕೆದಾರರ API ಕೀ ಮಾನ್ಯವಾಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ

## ಅನುವಾದಕದ ದೋಷನಿವಾರಣೆ

ಸ್ವರೂಪ ಅನುವಾದದ ಸಮಸ್ಯೆಗಳನ್ನು ದೋಷನಿವಾರಣೆ ಮಾಡಲು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಅನುವಾದಕ** ಬಳಸಿ:

| ಮೋಡ್             | ಯಾವಾಗ ಬಳಸಬೇಕು                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **ಪ್ಲೇಗ್ರೌಂಡ್**  | ಇನ್ಪುಟ್/ಔಟ್ಪುಟ್ ಸ್ವರೂಪಗಳನ್ನು ಅಕ್ಕಪಕ್ಕದಲ್ಲಿ ಹೋಲಿಸಿ — ಅದು ಹೇಗೆ ಅನುವಾದಗೊಳ್ಳುತ್ತದೆ ಎಂಬುದನ್ನು ನೋಡಲು ವಿಫಲವಾದ ವಿನಂತಿಯನ್ನು ಅಂಟಿಸಿ |
| **ಚಾಟ್ ಪರೀಕ್ಷಕ** | ಲೈವ್ ಸಂದೇಶಗಳನ್ನು ಕಳುಹಿಸಿ ಮತ್ತು ಹೆಡರ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಸಂಪೂರ್ಣ ವಿನಂತಿ/ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ                    |
| **ಟೆಸ್ಟ್ ಬೆಂಚ್** | ಯಾವ ಅನುವಾದಗಳು ದೋಷಪೂರಿತವಾಗಿವೆ ಎಂಬುದನ್ನು ಕಂಡುಹಿಡಿಯಲು ಸ್ವರೂಪ ಸಂಯೋಜನೆಗಳಾದ್ಯಂತ ಬ್ಯಾಚ್ ಪರೀಕ್ಷೆಗಳನ್ನು ಚಲಾಯಿಸಿ                    |
| **ಲೈವ್ ಮಾನಿಟರ್** | ಮಧ್ಯಂತರ ಅನುವಾದ ಸಮಸ್ಯೆಗಳನ್ನು ಪತ್ತೆಹಚ್ಚಲು ನೈಜ-ಸಮಯದ ವಿನಂತಿ ಹರಿವನ್ನು ವೀಕ್ಷಿಸಿ                                                 |

### ಸಾಮಾನ್ಯ ಸ್ವರೂಪದ ಸಮಸ್ಯೆಗಳು

- **ಚಿಂತನಾ ಟ್ಯಾಗ್ಗಳು ಕಾಣಿಸುತ್ತಿಲ್ಲ** — ಗುರಿ ಪೂರೈಕೆದಾರರು ಚಿಂತನೆಯನ್ನು ಬೆಂಬಲಿಸುತ್ತಾರೆಯೇ ಮತ್ತು ಚಿಂತನಾ ಬಜೆಟ್ ಸೆಟ್ಟಿಂಗ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ
- **ಟೂಲ್ ಕಾಲ್ಗಳು ಕಣ್ಮರೆಯಾಗುತ್ತಿವೆ** — ಕೆಲವು ಸ್ವರೂಪ ಅನುವಾದಗಳು ಬೆಂಬಲವಿಲ್ಲದ ಫೀಲ್ಡ್ಗಳನ್ನು ತೆಗೆದುಹಾಕಬಹುದು; ಪ್ಲೇಗ್ರೌಂಡ್ ಮೋಡ್ನಲ್ಲಿ ಪರಿಶೀಲಿಸಿ
- **ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ ಕಾಣೆಯಾಗಿದೆ** — Claude ಮತ್ತು Gemini ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ವಿಭಿನ್ನವಾಗಿ ನಿರ್ವಹಿಸುತ್ತವೆ; ಅನುವಾದದ ಔಟ್ಪುಟ್ ಪರಿಶೀಲಿಸಿ
- **SDK ಆಬ್ಜೆಕ್ಟ್ ಬದಲಿಗೆ ಕಚ್ಚಾ ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು ಮರಳಿಸುತ್ತದೆ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; OpenAI SDK Pydantic ಮೌಲ್ಯೀಕರಣ ವೈಫಲ್ಯಗಳಿಗೆ ಕಾರಣವಾಗುವ ಪ್ರಮಾಣಿತವಲ್ಲದ ಫೀಲ್ಡ್ಗಳನ್ನು (`x_groq`, `usage_breakdown`, ಇತ್ಯಾದಿ) ಪ್ರತಿಕ್ರಿಯೆ ಸ್ಯಾನಿಟೈಸರ್ ತೆಗೆದುಹಾಕುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ಇದು ಕಾಣಿಸಿದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ವರದಿ ಮಾಡಿ.
- **GLM/ERNIE `system` ಪಾತ್ರವನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; ಹೊಂದಾಣಿಕೆಯಾಗದ ಮಾದರಿಗಳಿಗಾಗಿ ಪಾತ್ರ ನಾರ್ಮಲೈಸರ್ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸಿಸ್ಟಮ್ ಸಂದೇಶಗಳನ್ನು ಬಳಕೆದಾರರ ಸಂದೇಶಗಳೊಂದಿಗೆ ವಿಲೀನಗೊಳಿಸುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ಇದು ಕಾಣಿಸಿದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ವರದಿ ಮಾಡಿ.
- **`developer` ಪಾತ್ರವನ್ನು ಗುರುತಿಸಲಾಗಿಲ್ಲ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; OpenAI ಅಲ್ಲದ ಪೂರೈಕೆದಾರರಿಗಾಗಿ ಸ್ವಯಂಚಾಲಿತವಾಗಿ `system`ಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ಇದು ಕಾಣಿಸಿದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ವರದಿ ಮಾಡಿ.
- **Gemini ಜೊತೆಗೆ `json_schema` ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿಲ್ಲ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; `response_format` ಅನ್ನು ಈಗ Geminiಯ `responseMimeType` + `responseSchema`ಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ಇದು ಕಾಣಿಸಿದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ವರದಿ ಮಾಡಿ.

## ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವದ ಸೆಟ್ಟಿಂಗ್ಗಳು

### ಸ್ವಯಂಚಾಲಿತ ದರ-ಮಿತಿ ಸಕ್ರಿಯವಾಗುತ್ತಿಲ್ಲ

- ಸ್ವಯಂಚಾಲಿತ ದರ-ಮಿತಿಯು API ಕೀ ಪೂರೈಕೆದಾರರಿಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ (OAuth/ಚಂದಾದಾರಿಕೆಗೆ ಅಲ್ಲ)
- **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು** ನಲ್ಲಿ ಸ್ವಯಂಚಾಲಿತ ದರ-ಮಿತಿ ಸಕ್ರಿಯವಾಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ
- ಪೂರೈಕೆದಾರರು `429` ಸ್ಥಿತಿ ಕೋಡ್ಗಳು ಅಥವಾ `Retry-After` ಹೆಡರ್ಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತಾರೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ

### ಘಾತೀಯ ಬ್ಯಾಕ್ಆಫ್ ಅನ್ನು ಹೊಂದಿಸುವುದು

ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು ಈ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತವೆ:

- **ಮೂಲ ವಿಳಂಬ** — ಮೊದಲ ವೈಫಲ್ಯದ ನಂತರದ ಆರಂಭಿಕ ಕಾಯುವ ಸಮಯ (ಡೀಫಾಲ್ಟ್: 1s)
- **ಗರಿಷ್ಠ ವಿಳಂಬ** — ಕಾಯುವ ಸಮಯದ ಗರಿಷ್ಠ ಮಿತಿ (ಡೀಫಾಲ್ಟ್: 30s)
- **ಗುಣಕ** — ಪ್ರತಿ ಸತತ ವೈಫಲ್ಯಕ್ಕೆ ವಿಳಂಬವನ್ನು ಎಷ್ಟು ಹೆಚ್ಚಿಸಬೇಕು (ಡೀಫಾಲ್ಟ್: 2x)

### ಥಂಡರಿಂಗ್ ಹರ್ಡ್ ತಡೆಗಟ್ಟುವಿಕೆ

ದರ-ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರೈಕೆದಾರರಿಗೆ ಅನೇಕ ಸಮಕಾಲೀನ ವಿನಂತಿಗಳು ಬಂದಾಗ, ವಿನಂತಿಗಳನ್ನು ಸರಣೀಕರಿಸಲು ಮತ್ತು ಸರಣಿ ವೈಫಲ್ಯಗಳನ್ನು ತಡೆಯಲು OmniRoute ಮ್ಯೂಟೆಕ್ಸ್ + ಸ್ವಯಂಚಾಲಿತ ದರ-ಮಿತಿಯನ್ನು ಬಳಸುತ್ತದೆ. API ಕೀ ಪೂರೈಕೆದಾರರಿಗೆ ಇದು ಸ್ವಯಂಚಾಲಿತವಾಗಿದೆ.

### ಚಾಟ್ ವಿನಂತಿಗಳು 503 / chat_admission_busy ನೊಂದಿಗೆ ವಿಫಲವಾಗುತ್ತವೆ

**ಲಕ್ಷಣಗಳು:**

- ಚಾಟ್ ಪೂರ್ಣಗೊಳಿಸುವಿಕೆ ಎಂಡ್ಪಾಯಿಂಟ್ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ; ಅದರ ದೋಷ ಕೋಡ್
  `chat_admission_busy` ಆಗಿರುತ್ತದೆ.
- ಪ್ರತಿಕ್ರಿಯೆಯು `Retry-After` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ. #12135 ರಿಂದ, ಅದರ ಮೌಲ್ಯವನ್ನು ಗಮನಿಸಲಾದ
  ಆಕ್ಯುಪೆನ್ಸಿಯಿಂದ ಪಡೆಯಲಾಗುತ್ತದೆ — ವಿನಂತಿಯು ಈಗಾಗಲೇ ಕಾಯ್ದಿರುವ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  ಕಾಲಾವಧಿ ಮತ್ತು ಪ್ರಸ್ತುತ ಹೆವಿವೇಟ್ ಲೀಸ್ಗಳನ್ನು ಹಿಡಿದಿಟ್ಟಿರುವ ಸಮಯ, ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದನ್ನು ತೆಗೆದುಕೊಂಡು — ಪೂರ್ಣ
  ಸೆಕೆಂಡ್ಗಳಿಗೆ ಮೇಲಕ್ಕೆ ಪೂರ್ಣಾಂಕಗೊಳಿಸಿ, ಗರಿಷ್ಠ 60ಕ್ಕೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ. ನಿಷ್ಕ್ರಿಯ ಗೇಟ್ನಲ್ಲಿ ಇದು ಹಿಂದಿನ ಕನಿಷ್ಠ
  ಮಿತಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ: ಬೈಟ್-ಆಧಾರಿತ ಪಥದಲ್ಲಿ 2 ಸೆಕೆಂಡ್ಗಳು, ರಚನೆ-ಆಧಾರಿತ ಪಥದಲ್ಲಿ 1 ಸೆಕೆಂಡ್
  (ಇದು `reason: "structure_limit"` ಅನ್ನೂ ಒಳಗೊಂಡಿರುತ್ತದೆ).
- ಮತ್ತೊಂದು ಹೆವಿವೇಟ್ ಚಾಟ್ ಅಥವಾ ದೀರ್ಘಕಾಲ ಚಾಲನೆಯಲ್ಲಿರುವ ಸ್ಟ್ರೀಮಿಂಗ್ ಪ್ರತಿಕ್ರಿಯೆ ಇನ್ನೂ
  ಪ್ರಗತಿಯಲ್ಲಿರುವಾಗ ಇದು ಸಂಭವಿಸಬಹುದು.

ಬೈಟ್-ಆಧಾರಿತ ಪ್ರತಿಕ್ರಿಯೆಯ ಬಾಡಿ ಹೀಗಿದೆ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ರಚನೆ-ಆಧಾರಿತ ಪ್ರತಿಕ್ರಿಯೆಯು ಅದೇ ಪ್ರಕಾರ ಮತ್ತು ಕೋಡ್ ಅನ್ನು ಬಳಸುತ್ತದೆ; ಅದರ ಸಂದೇಶ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ಆಗಿದ್ದು, `reason: "structure_limit"` ಅನ್ನೂ ಒಳಗೊಂಡಿರುತ್ತದೆ.
ಡೀಫಾಲ್ಟ್ ಮಿತಿಗಳಲ್ಲಿ, ವಿನಂತಿಯು ಕನಿಷ್ಠ `200` ಸಂದೇಶಗಳು, ಕನಿಷ್ಠ `64` ಪರಿಕರಗಳು ಅಥವಾ ಕನಿಷ್ಠ `32,000`
ಅಂದಾಜು ಟೋಕನ್ಗಳನ್ನು ಹೊಂದಿದ್ದರೆ, ಅಥವಾ ಮಿತಿಗೊಳಿಸಿದ ರಚನಾ ಅಂದಾಜು ಪ್ರಕ್ರಿಯೆಯು ಭೇಟಿ ನೀಡಿದ `10,000`
ನೋಡ್ಗಳ ಮಿತಿ ಅಥವಾ `12` ಆಳದ ಮಿತಿಯನ್ನು ತಲುಪಿದರೆ, ಅದನ್ನು ರಚನಾತ್ಮಕವಾಗಿ ಭಾರವಾದ ವಿನಂತಿ ಎಂದು ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ.

**ಕಾರಣ:** ಇದು OmniRoute ಒಳಗಿನ ಉದ್ದೇಶಪೂರ್ವಕ ಲೋಡ್ ಕಡಿತವಾಗಿದೆ, ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ವೈಫಲ್ಯವಲ್ಲ.
ದೊಡ್ಡ ವಿನಂತಿಯ ಬಾಡಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುವ ಮತ್ತು ಪಾರ್ಸ್ ಮಾಡುವ ಮೊದಲು, ಸೀಮಿತ ಹೆವಿವೇಟ್ ಸಾಮರ್ಥ್ಯವನ್ನು ಕಾಯ್ದಿರಿಸಲು
ಪ್ರತಿ ಪ್ರಕ್ರಿಯೆಯೂ ಪ್ರಕ್ರಿಯೆ-ಸ್ಥಳೀಯ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. SSE ಪ್ರತಿಕ್ರಿಯೆಯ ಸಂಪೂರ್ಣ ಜೀವಿತಾವಧಿಯವರೆಗೆ
ಹೆವಿವೇಟ್ ಲೀಸ್ ಹಿಡಿದಿಡಲಾಗುತ್ತದೆ.

**#503-ಫ್ಯಾನ್-ಔಟ್:** ಈ ಪರಿಹಾರಕ್ಕೂ ಮೊದಲು, ಹೋಸ್ಟ್ ಮೆಮೊರಿಯನ್ನು ಪರಿಗಣಿಸದೆ ಗಾರ್ಡ್ ಸಮಕಾಲೀನತೆಯನ್ನು
ನಿಗದಿತ ವಿನಂತಿಗಳ COUNTಗೆ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ಡೀಫಾಲ್ಟ್ `1`) ಮಿತಿಗೊಳಿಸುತ್ತಿತ್ತು.
ಆದ್ದರಿಂದ ಕೋಡಿಂಗ್-ಏಜೆಂಟ್ ಫ್ಯಾನ್-ಔಟ್ (ಬಹು ಉಪ-ಏಜೆಂಟ್ಗಳು/CLIಗಳು, ಸಾಮಾನ್ಯವಾಗಿ > 256 KB ಗಾತ್ರದ ಬಾಡಿಗಳು)
ಪರಿಣಾಮಕಾರಿ ಸಮಕಾಲೀನತೆಯನ್ನು ~1ಕ್ಕೆ ಕುಗ್ಗಿಸಿ, ಸಂಪೂರ್ಣವಾಗಿ ಸಾಮಾನ್ಯವಾದ ಲೋಡ್ನಲ್ಲಿಯೇ 503 ದೋಷಗಳನ್ನು ಉಂಟುಮಾಡುತ್ತಿತ್ತು.
ಈಗ ಗಾರ್ಡ್ ಸ್ವಯಂ-ಹೊಂದಾಣಿಕೆ ಮಾಡಿಕೊಳ್ಳುತ್ತದೆ: ಪ್ರಕ್ರಿಯೆಯ ನೈಜ ಮೆಮೊರಿ ಮಿತಿಯಿಂದ ಗಾತ್ರ ನಿರ್ಧರಿಸಲಾದ,
ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಲೆಕ್ಕಿಸಲಾದ ಇನ್ಜೆಸ್ಟ್ BYTE ಬಜೆಟ್ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ಅದನ್ನು
ನಿಯಂತ್ರಿಸುತ್ತದೆ; ಜೊತೆಗೆ, ಅದು ಲೈವ್ ಸಂಪನ್ಮೂಲ-ಒತ್ತಡದ ಸಂಕೇತವನ್ನೂ ಪರಿಶೀಲಿಸುತ್ತದೆ — ಹೀಗಾಗಿ ಒಂದೇ ಸಮಯದಲ್ಲಿ
ಒಂದಕ್ಕಿಂತ ಹೆಚ್ಚು ಭಾರವಾದ ವಿನಂತಿಗಳು ಬಂದಿವೆ ಎಂಬ ಕಾರಣಕ್ಕೆ ಮಾತ್ರವಲ್ಲ, ಹೋಸ್ಟ್ ನಿಜವಾಗಿಯೂ ಮೆಮೊರಿ ಒತ್ತಡದಲ್ಲಿದ್ದಾಗ
ಮಾತ್ರ ಅದು ಲೋಡ್ ಕಡಿತಗೊಳಿಸುತ್ತದೆ. ಹಳೆಯ ಎಣಿಕೆ ಮಿತಿ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ಅನ್ನು
ಇನ್ನೂ ಗೌರವಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ನೀವು ಅದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸಿದರೆ ಮಾತ್ರ.

ಸಾಮರ್ಥ್ಯವು ಕಾರ್ಯನಿರತವಾಗಿರುವಾಗ, ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಪ್ರತಿಕ್ರಿಯಿಸುವ ಮೊದಲು ಸ್ಲಾಟ್ ಖಾಲಿಯಾಗಲು
ಹೆವಿವೇಟ್ ವಿನಂತಿಯು ಮೊದಲು `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ವರೆಗೆ (ಡೀಫಾಲ್ಟ್ `2000`,
`0` ಕಾಯುವಿಕೆಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ) ಕಾಯುತ್ತದೆ. ಈ ಮಿತಿಗೊಳಿಸಿದ ಕಾಯುವಿಕೆ ಇರುವುದರಿಂದ, ಭಾರವಾದ
ಉಪ-ವಿನಂತಿಗಳನ್ನು ಸಮಕಾಲೀನವಾಗಿ ಫ್ಯಾನ್-ಔಟ್ ಮಾಡುವ ಏಜೆಂಟ್-ಶೈಲಿಯ ಕ್ಲೈಂಟ್ಗಳು
(OpenCode, Claude Code, Cursor) ತಕ್ಷಣದ ನಿರಾಕರಣೆಗಳಿಗೆ ತಮ್ಮ ಸಂಪೂರ್ಣ ಮರುಪ್ರಯತ್ನ ಬಜೆಟ್ ಅನ್ನು ವ್ಯಯಿಸಿ
ಕಾರ್ಯದ ಮಧ್ಯದಲ್ಲೇ ವಿಫಲಗೊಳ್ಳುವ ಬದಲು, ಆ ವಿನಂತಿಗಳ ಸ್ಫೋಟವನ್ನು ಸರಣೀಕರಿಸಬಹುದು.
ಪ್ರಸ್ತುತ ಹೆವಿವೇಟ್ ಲೀಸ್ ಆಕ್ಯುಪೆನ್ಸಿ, ನಿರ್ಧರಿಸಲಾದ ಬೈಟ್ ಬಜೆಟ್ ಮತ್ತು ಲೈವ್ ಒತ್ತಡದ ತೀವ್ರತೆಯನ್ನು
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ನಲ್ಲಿ ತೋರಿಸಲಾಗುತ್ತದೆ — ಯಾವುದೇ env var ಅನ್ನು
ಬದಲಾಯಿಸುವ ಮೊದಲು ಇವುಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ವಿನಂತಿ ಕ್ಯೂ → ಸಮಕಾಲೀನ ವಿನಂತಿಗಳು ಇದನ್ನು ನಿಯಂತ್ರಿಸುವುದಿಲ್ಲ; ಆ ಸೆಟ್ಟಿಂಗ್
ಪ್ರತ್ಯೇಕ ಪೂರೈಕೆದಾರ ವಿನಂತಿ-ಕ್ಯೂ ಕಾರ್ಯವಿಧಾನವನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. ಮೊದಲು ಮರುಪ್ರಯತ್ನಿಸಿ. ಕ್ಲೈಂಟ್ಗಳು ವಿನಂತಿಯನ್ನು ತಕ್ಷಣವೇ ಪುನರಾವರ್ತಿಸುವ ಬದಲು `Retry-After` ಅನ್ನು
   ಗೌರವಿಸಿ ಬ್ಯಾಕ್ಆಫ್ ಬಳಸಬೇಕು.
2. ಯಾವುದನ್ನಾದರೂ ಹೊಂದಿಸುವ ಮೊದಲು `/api/monitoring/health` → `chatAdmission` ಅನ್ನು ಪರಿಶೀಲಿಸಿ. `countCapEnabled:
false` ಮತ್ತು ಉದಾರವಾದ `maxInflightBytes` ಎಂದರೆ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಲೆಕ್ಕಿಸಲಾದ ಬಜೆಟ್ ಈಗಾಗಲೇ ತನ್ನ
   ಕೆಲಸವನ್ನು ಮಾಡುತ್ತಿದೆ; `high`/`critical` ಮೌಲ್ಯದ `pressureSeverity` ಎಂದರೆ ಹೋಸ್ಟ್ನಲ್ಲಿ ನಿಜವಾಗಿಯೂ
   ಮೆಮೊರಿ ಕೊರತೆಯಿದೆ — ಇದನ್ನು ಅಡ್ಮಿಷನ್ env var ಮೂಲಕ ಸರಿಪಡಿಸಲಾಗುವುದಿಲ್ಲ; ಇದಕ್ಕೆ ಹೆಚ್ಚಿನ RAM ಅಥವಾ
   ಕಡಿಮೆ ಕಾರ್ಯಭಾರ ಅಗತ್ಯವಿದೆ.
3. `/api/monitoring/health` ನಲ್ಲಿ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಲೆಕ್ಕಿಸಲಾದ ಬಜೆಟ್ ನಿಮ್ಮ ಹೋಸ್ಟ್ಗೆ ನಿಜವಾಗಿಯೂ ತುಂಬಾ
   ಚಿಕ್ಕದಾಗಿದೆ ಎಂದು ತೋರಿಸಿದರೆ ಮಾತ್ರ (ಇದು ಅಪರೂಪ — ಕಂಟೇನರ್ನಿಂದ ಬೇರ್-ಮೆಟಲ್ವರೆಗೆ ಈಗಾಗಲೇ ಸ್ಕೇಲ್ ಆಗುತ್ತದೆ),
   ಹಳೆಯ ವಿನಂತಿ-ಎಣಿಕೆ ಮಿತಿಗೆ ಹಿಂದಿರುಗುವ ಬದಲು `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ಮೂಲಕ ಅದನ್ನು
   ನೇರವಾಗಿ ಓವರ್ರೈಡ್ ಮಾಡಿ.

ಅಧಿಕೃತ ಅಡ್ಮಿಷನ್ ಸೆಟ್ಟಿಂಗ್ಗಳಿಗಾಗಿ [ಪರಿಸರ-ಚರ ಉಲ್ಲೇಖ](../reference/ENVIRONMENT.md#4-security--authentication)
ವನ್ನು ನೋಡಿ.

## ಐಚ್ಛಿಕ RAG / LLM ವೈಫಲ್ಯ ವರ್ಗೀಕರಣ (16 ಸಮಸ್ಯೆಗಳು)

ಕೆಲವು OmniRoute ಬಳಕೆದಾರರು ಗೇಟ್ವೇಯನ್ನು RAG ಅಥವಾ ಏಜೆಂಟ್ ಸ್ಟ್ಯಾಕ್ಗಳ ಮುಂಭಾಗದಲ್ಲಿ ಇರಿಸುತ್ತಾರೆ. ಅಂತಹ ಸೆಟಪ್ಗಳಲ್ಲಿ ವಿಚಿತ್ರ ಮಾದರಿಯೊಂದು ಸಾಮಾನ್ಯವಾಗಿ ಕಾಣಿಸುತ್ತದೆ: OmniRoute ಆರೋಗ್ಯಕರವಾಗಿ ಕಾಣುತ್ತದೆ (ಪೂರೈಕೆದಾರರು ಲಭ್ಯವಿದ್ದಾರೆ, ರೂಟಿಂಗ್ ಪ್ರೊಫೈಲ್ಗಳು ಸರಿಯಾಗಿವೆ, ದರ ಮಿತಿ ಎಚ್ಚರಿಕೆಗಳಿಲ್ಲ), ಆದರೆ ಅಂತಿಮ ಉತ್ತರವು ಇನ್ನೂ ತಪ್ಪಾಗಿರುತ್ತದೆ.

ಪ್ರಾಯೋಗಿಕವಾಗಿ, ಈ ಘಟನೆಗಳು ಸಾಮಾನ್ಯವಾಗಿ ಗೇಟ್ವೇಯಿಂದಲೇ ಉಂಟಾಗದೆ, ನಂತರದ RAG ಪೈಪ್ಲೈನ್ನಿಂದ ಉಂಟಾಗುತ್ತವೆ.

ಆ ವೈಫಲ್ಯಗಳನ್ನು ವಿವರಿಸಲು ನಿಮಗೆ ಸಾಮಾನ್ಯ ಪದಸಂಪತ್ತು ಬೇಕಿದ್ದರೆ, ಹದಿನಾರು ಪುನರಾವರ್ತಿತ RAG / LLM ವೈಫಲ್ಯ ಮಾದರಿಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುವ, MIT ಪರವಾನಗಿಯ ಬಾಹ್ಯ ಪಠ್ಯ ಸಂಪನ್ಮೂಲವಾದ WFGY ProblemMap ಅನ್ನು ನೀವು ಬಳಸಬಹುದು. ಉನ್ನತ ಮಟ್ಟದಲ್ಲಿ ಇದು ಇವುಗಳನ್ನು ಒಳಗೊಂಡಿದೆ:

- ರಿಟ್ರೀವಲ್ ವಿಚಲನ ಮತ್ತು ಮುರಿದ ಸಂದರ್ಭ ಗಡಿಗಳು
- ಖಾಲಿ ಅಥವಾ ಹಳೆಯದಾದ ಸೂಚಿಕೆಗಳು ಮತ್ತು ವೆಕ್ಟರ್ ಸ್ಟೋರ್ಗಳು
- ಎಂಬೆಡ್ಡಿಂಗ್ ಮತ್ತು ಅರ್ಥಸಂಬಂಧಿ ಹೊಂದಾಣಿಕೆಯ ನಡುವಿನ ವ್ಯತ್ಯಾಸ
- ಪ್ರಾಂಪ್ಟ್ ಸಂಯೋಜನೆ ಮತ್ತು ಸಂದರ್ಭ ವಿಂಡೋ ಸಮಸ್ಯೆಗಳು
- ತಾರ್ಕಿಕ ಕುಸಿತ ಮತ್ತು ಅತಿಯಾದ ಆತ್ಮವಿಶ್ವಾಸದ ಉತ್ತರಗಳು
- ದೀರ್ಘ ಸರಣಿ ಮತ್ತು ಏಜೆಂಟ್ ಸಮನ್ವಯ ವೈಫಲ್ಯಗಳು
- ಬಹು-ಏಜೆಂಟ್ ಮೆಮೊರಿ ಮತ್ತು ಪಾತ್ರ ವಿಚಲನ
- ನಿಯೋಜನೆ ಮತ್ತು ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಕ್ರಮದ ಸಮಸ್ಯೆಗಳು

ಕಲ್ಪನೆ ಸರಳವಾಗಿದೆ:

1. ಕೆಟ್ಟ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ತನಿಖೆ ಮಾಡುವಾಗ, ಇವುಗಳನ್ನು ದಾಖಲಿಸಿ:
   - ಬಳಕೆದಾರರ ಕಾರ್ಯ ಮತ್ತು ವಿನಂತಿ
   - OmniRoute ನಲ್ಲಿನ ರೂಟ್ ಅಥವಾ ಪೂರೈಕೆದಾರರ ಸಂಯೋಜನೆ
   - ನಂತರದ ಹಂತದಲ್ಲಿ ಬಳಸಲಾದ ಯಾವುದೇ RAG ಸಂದರ್ಭ (ಹಿಂಪಡೆಯಲಾದ ಡಾಕ್ಯುಮೆಂಟ್ಗಳು, ಟೂಲ್ ಕರೆಗಳು ಇತ್ಯಾದಿ)
2. ಘಟನೆಯನ್ನು ಒಂದು ಅಥವಾ ಎರಡು WFGY ProblemMap ಸಂಖ್ಯೆಗಳಿಗೆ (`No.1` … `No.16`) ಮ್ಯಾಪ್ ಮಾಡಿ.
3. OmniRoute ಲಾಗ್ಗಳ ಪಕ್ಕದಲ್ಲಿ, ನಿಮ್ಮದೇ ಡ್ಯಾಶ್ಬೋರ್ಡ್, ರನ್ಬುಕ್ ಅಥವಾ ಘಟನೆ ಟ್ರ್ಯಾಕರ್ನಲ್ಲಿ ಆ ಸಂಖ್ಯೆಯನ್ನು ಸಂಗ್ರಹಿಸಿ.
4. ನಿಮ್ಮ RAG ಸ್ಟ್ಯಾಕ್, ರಿಟ್ರೀವರ್ ಅಥವಾ ರೂಟಿಂಗ್ ತಂತ್ರವನ್ನು ಬದಲಾಯಿಸಬೇಕೇ ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸಲು ಸಂಬಂಧಿತ WFGY ಪುಟವನ್ನು ಬಳಸಿ.

ಸಂಪೂರ್ಣ ಪಠ್ಯ ಮತ್ತು ಸ್ಪಷ್ಟ ವಿಧಾನಗಳು ಇಲ್ಲಿ ಲಭ್ಯವಿವೆ (MIT ಪರವಾನಗಿ, ಪಠ್ಯ ಮಾತ್ರ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute ಹಿಂದೆ ನೀವು RAG ಅಥವಾ ಏಜೆಂಟ್ ಪೈಪ್ಲೈನ್ಗಳನ್ನು ಚಲಾಯಿಸದಿದ್ದರೆ, ಈ ವಿಭಾಗವನ್ನು ನಿರ್ಲಕ್ಷಿಸಬಹುದು.

## v3.8.0 ತಿಳಿದಿರುವ ಸಮಸ್ಯೆಗಳು

v3.8.0 ಬಿಡುಗಡೆಗೆ ನಿರ್ದಿಷ್ಟವಾದ ಸಮಸ್ಯೆಗಳು ಮತ್ತು ಅವುಗಳ ಪ್ರಸ್ತುತ ಪರಿಹಾರೋಪಾಯಗಳು. ನಂತರದ ಪ್ಯಾಚ್ನಲ್ಲಿ ಸರಿಪಡಿಸುವಿಕೆ ಬಂದರೆ, ಈ ನಮೂದನ್ನು ನವೀಕರಿಸಲಾಗುತ್ತದೆ ಅಥವಾ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ.

### Devin CLI ದೃಢೀಕರಣ ವೈಫಲ್ಯಗಳು

**ಲಕ್ಷಣಗಳು:**

- Devin-ಆಧಾರಿತ ಟೂಲ್ಗಳನ್ನು ಆಹ್ವಾನಿಸುವಾಗ "Devin CLI ಕಂಡುಬಂದಿಲ್ಲ" ಅಥವಾ "ದೃಢೀಕರಣ ವಿಫಲವಾಗಿದೆ"
- CLI ರನ್ಟೈಮ್ ಪರಿಶೀಲನೆಯು `installed=false` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ

**ಕಾರಣಗಳು:**

- `CLI_DEVIN_BIN` ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದ ಪಥವನ್ನು ಸೂಚಿಸುತ್ತದೆ
- ಹೋಸ್ಟ್ನಲ್ಲಿ Devin CLI ಸ್ಥಾಪಿಸಲಾಗಿಲ್ಲ

**ಸರಿಪಡಿಸುವಿಕೆ:**

1. ನಿಮ್ಮ ಪ್ಲಾಟ್ಫಾರ್ಮ್ಗಾಗಿ Devin CLI ಅನ್ನು ಸ್ಥಾಪಿಸಿ
2. `.env` ನಲ್ಲಿ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ಅಥವಾ ನಿಜವಾದ ಪಥ) ಹೊಂದಿಸಿ
3. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ ಮತ್ತು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → CLI ಟೂಲ್ಗಳು** ನಿಂದ ಮರುಪರೀಕ್ಷಿಸಿ

### ಮಾಡೆಲ್ ಕೂಲ್ಡೌನ್ ಸ್ಥಗಿತಗೊಂಡಿದೆ (ಹಸ್ತಚಾಲಿತ ಮರುಹೊಂದಿಕೆ)

**ಲಕ್ಷಣಗಳು:**

- ಅವಧಿ ಮುಗಿದ ಸಮಯ ಕಳೆದ ನಂತರವೂ ಮಾಡೆಲ್ ಕೂಲ್ಡೌನ್ನಲ್ಲಿದೆ ಎಂದು ಪಟ್ಟಿಮಾಡಲಾಗುತ್ತದೆ
- ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಹಿಂದಿನ ಸಮಯದಲ್ಲಿದ್ದರೂ ಸಂಯೋಜಿತ ರೂಟಿಂಗ್ನಲ್ಲಿನ ವಿನಂತಿಗಳು ಇನ್ನೂ ಮಾಡೆಲ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತವೆ

**ಹಸ್ತಚಾಲಿತ ಮರುಹೊಂದಿಕೆ:**

- **ಡ್ಯಾಶ್ಬೋರ್ಡ್:** **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಮಾಡೆಲ್ ಕೂಲ್ಡೌನ್ಗಳು** → ಬಾಧಿತ ಕಾರ್ಡ್ನಲ್ಲಿ **ಮರು-ಸಕ್ರಿಯಗೊಳಿಸಿ** ಕ್ಲಿಕ್ ಮಾಡಿ
- **API:** ನಿರ್ವಹಣಾ ದೃಢೀಕರಣ ಹೆಡರ್ಗಳೊಂದಿಗೆ `DELETE /api/resilience/model-cooldowns`

### Command Code ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕವು 403 ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

**ಲಕ್ಷಣಗಳು:**

- Command Code ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸುವಾಗ 403
- ಹೊಸದಾಗಿ ಸೇರಿಸಿದ ನಂತರ ಪೂರೈಕೆದಾರ ಕಾರ್ಡ್ "ಅನಧಿಕೃತ" ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** OAuth ಹರಿವು ಪೂರ್ಣಗೊಂಡಿಲ್ಲ (ಕಾಲ್ಬ್ಯಾಕ್ ಸ್ವೀಕರಿಸಲಾಗಿಲ್ಲ ಅಥವಾ ಟೋಕನ್ ಉಳಿಸಲಾಗಿಲ್ಲ).

**ಸರಿಪಡಿಸುವಿಕೆ:**

- OAuth ಹರಿವನ್ನು ಪುನಃ ಪ್ರಚೋದಿಸಲು CLI ನಿಂದ `omniroute providers` ಚಲಾಯಿಸಿ, ಅಥವಾ
- **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು → Command Code → ಮರುಸಂಪರ್ಕಿಸಿ** ಮೂಲಕ OAuth ಅನ್ನು ಪುನಃ ಚಲಾಯಿಸಿ

### ModelScope ತೀವ್ರವಾದ 429 ಕೂಲ್ಡೌನ್ಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಲಕ್ಷಣಗಳು:**

- ಸಣ್ಣ ಪ್ರಮಾಣದ ವಿನಂತಿಗಳ ಹಠಾತ್ ಹೆಚ್ಚಳದ ನಂತರ ModelScope ನಲ್ಲಿ ಅತ್ಯಂತ ಕಡಿಮೆ ಅವಧಿಯ ಅಥವಾ ತಕ್ಷಣದ ಕೂಲ್ಡೌನ್ಗಳು
- ಸಂಯೋಜಿತ ರೂಟಿಂಗ್ ನಿರೀಕ್ಷೆಗಿಂತ ಮುಂಚೆಯೇ ModelScope ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ

**ಕಾರಣ:** ModelScope ಪೂರೈಕೆದಾರ-ನಿರ್ದಿಷ್ಟ `Retry-After` ಹೆಡರ್ಗಳನ್ನು ಹೊರಸೂಸುತ್ತದೆ. v3.8.0 ಆ ಹೆಡರ್ಗಳಿಗಾಗಿ ವಿಶೇಷ ನಿರ್ವಹಣೆಯನ್ನು ಒದಗಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಹಳೆಯ ಆವೃತ್ತಿಗಳು ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ದರ-ಮಿತಿ ಸೂಚನೆಗಳೆಂದು ತಪ್ಪಾಗಿ ಅರ್ಥೈಸುತ್ತವೆ.

**ಸರಿಪಡಿಸುವಿಕೆ:**

- ನೀವು v3.8.0 ಅಥವಾ ನಂತರದ ಆವೃತ್ತಿಯಲ್ಲಿದ್ದೀರಿ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ
- **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ** ಅಡಿಯಲ್ಲಿ `useUpstream429BreakerHints` ಟಾಗಲ್ ಸಕ್ರಿಯವಾಗಿದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ

### ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ OMNIROUTE_WS_BRIDGE_SECRET ಕಾಣೆಯಾಗಿದೆ

**ಲಕ್ಷಣಗಳು:**

- ದೂರಸ್ಥ ಉತ್ಪಾದನಾ ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಲಾಯಿಸುವಾಗ ಪ್ರತಿ Codex/Responses WebSocket ಬ್ರಿಡ್ಜ್ ವಿನಂತಿಗೂ 401
- ಸಂಪರ್ಕಿಸಿದ ತಕ್ಷಣ WebSocket ಬ್ರಿಡ್ಜ್ ಹ್ಯಾಂಡ್ಶೇಕ್ ಮುಚ್ಚುತ್ತದೆ

**ಕಾರಣ:** ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ `OMNIROUTE_WS_BRIDGE_SECRET` ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ ಕಾಣೆಯಾಗಿದೆ.

**ಸರಿಪಡಿಸುವಿಕೆ:**

1. ಯಾದೃಚ್ಛಿಕ ರಹಸ್ಯವನ್ನು ರಚಿಸಿ: `openssl rand -hex 32`
2. ಉತ್ಪಾದನಾ ಸರ್ವರ್ ಪರಿಸರದಲ್ಲಿ (ಮತ್ತು ಬ್ರಿಡ್ಜ್ನೊಂದಿಗೆ ಸಂವಹನ ಮಾಡುವ ಯಾವುದೇ ಕ್ಲೈಂಟ್ನಲ್ಲೂ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ಹೊಂದಿಸಿ
3. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ

### Responses API: ಹಿನ್ನೆಲೆ ಮೋಡ್ ಸಿಂಕ್ರೋನಸ್ಗೆ ಕೆಳಮಟ್ಟಕ್ಕಿಳಿಸಲಾಗಿದೆ

**ಲಕ್ಷಣಗಳು:**

- ಲಾಗ್ ಮಾಡಲಾದ ಎಚ್ಚರಿಕೆ: `background mode degraded to synchronous`
- `background: true` ವಿನಂತಿಯು ಹಿನ್ನೆಲೆ ಜಾಬ್ ಹ್ಯಾಂಡಲ್ ಬದಲಿಗೆ ಸಾಮಾನ್ಯ ಸಿಂಕ್ರೋನಸ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಕಾರಣ:** v3.8.0 ಎಚ್ಚರಿಕೆಯನ್ನು ಹೊರಸೂಸುತ್ತಲೇ Responses API ಯಲ್ಲಿನ `background: true` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಸಿಂಕ್ರೋನಸ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಗೆ ಕೆಳಮಟ್ಟಕ್ಕಿಳಿಸುತ್ತದೆ. ಸಂಪೂರ್ಣ ಅಸಿಂಕ್ರೋನಸ್ ಹಿನ್ನೆಲೆ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯು ಭವಿಷ್ಯದಲ್ಲಿ ಒದಗಿಸಲಾಗುವ ವೈಶಿಷ್ಟ್ಯವಾಗಿದೆ.

**ಸರಿಪಡಿಸುವಿಕೆ:**

- `background` ಇಲ್ಲದೆ ಕರೆ ಮಾಡುವಂತೆ ಕ್ಲೈಂಟ್ ಅನ್ನು ಹೊಂದಿಸಿ, ಅಥವಾ
- ಸಂಪೂರ್ಣ ಅಸಿಂಕ್ರೋನಸ್ ಹಿನ್ನೆಲೆ ಮೋಡ್ ಒದಗಿಸುವ ನಂತರದ ಬಿಡುಗಡೆಗಾಗಿ ಕಾಯಿರಿ (ಬದಲಾವಣೆ ದಾಖಲೆಯನ್ನು ಗಮನಿಸಿ)

## ನಿಧಾನ ಪ್ರಾರಂಭ / ಸಿದ್ಧತಾ ಕಾಲಮಿತಿ

CLI `⚠ ಸರ್ವರ್ 60s ಒಳಗೆ ಪ್ರತಿಕ್ರಿಯಿಸಲಿಲ್ಲ` ಎಂದು ಮುದ್ರಿಸಿದರೂ ಸರ್ವರ್ ವಾಸ್ತವವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದ್ದರೆ, ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಸಿದ್ಧತಾ ಪರಿಶೀಲನೆಯ ಸಮಯ ಮಿತಿ ತುಂಬಾ ಕಡಿಮೆಯಾಗಿದೆ.

ಇದು ಸಾಮಾನ್ಯವಾಗಿ Windowsನಲ್ಲಿ (ಆಂಟಿವೈರಸ್, ಫೈಲ್ಸಿಸ್ಟಮ್ ವೀಕ್ಷಕಗಳು) ಅಥವಾ ಪ್ರಾರಂಭದ ಸಮಯದಲ್ಲಿ ಹೆಚ್ಚಿನ ಕಾರ್ಯಭಾರವಿರುವ ಕಂಟೇನರ್ಗಳಲ್ಲಿ ಸಂಭವಿಸುತ್ತದೆ.

**ಪರಿಹಾರ — ಸಮಯ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ:**

```bash
# ಪರಿಸರ ಚರದ ಮೂಲಕ (ಪ್ರಾರಂಭಗಳಾದ್ಯಂತ ಉಳಿಯುತ್ತದೆ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ನಿಮಿಷಗಳು
omniroute serve

# CLI ಫ್ಲ್ಯಾಗ್ ಮೂಲಕ (ಒಂದು ಬಾರಿ ಮಾತ್ರ):
omniroute serve --ready-timeout 180000
```

ಡೀಫಾಲ್ಟ್ ಮಿತಿ 60 000 ms (60 s) ಆಗಿದೆ. ಈ ಎಚ್ಚರಿಕೆಯು ಕೇವಲ ಮಾಹಿತಿಗಾಗಿ; ಸರ್ವರ್ ಹಿನ್ನೆಲೆಯಲ್ಲಿ ಪ್ರಾರಂಭವಾಗುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತದೆ ಮತ್ತು ಬೂಟ್ ಪೂರ್ಣಗೊಂಡ ನಂತರ ಅದನ್ನು ಪ್ರವೇಶಿಸಬಹುದು.

`OMNIROUTE_READY_TIMEOUT_MS` ಕುರಿತ ಸಂಪೂರ್ಣ ವಿವರಗಳಿಗಾಗಿ [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ನೋಡಿ.
