## ವಿವರವಾದ ಸಮಸ್ಯೆ ನಿವಾರಣೆ

---

### ಉಚಿತ ಪೂರೈಕೆದಾರರಲ್ಲಿನ ದರ ಮಿತಿ (429 / 400 / 401)

**ಲಕ್ಷಣ**: ಉಚಿತ/ದೃಢೀಕರಣವಿಲ್ಲದ ಪೂರೈಕೆದಾರರೊಂದಿಗೆ (opencode, auggie, ಇತ್ಯಾದಿ) `model: "auto"` ಬಳಸುವಾಗ, ಉತ್ತರಗಳ ಬದಲಿಗೆ ಮಧ್ಯಂತರವಾಗಿ `HTTP 429`, `400`, ಅಥವಾ `401` ದೊರೆಯುತ್ತದೆ. ಸ್ವಲ್ಪ ಸಮಯದ ನಂತರ ಅದೇ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಿದಾಗ ವಿನಂತಿಗಳು ಯಶಸ್ವಿಯಾಗುತ್ತವೆ, ಆದರೆ ಸ್ವಯಂಚಾಲಿತ ವ್ಯವಸ್ಥೆಯು (cron ಜಾಬ್ಗಳು, ಏಜೆಂಟ್ಗಳು, ಸ್ಕ್ರಿಪ್ಟ್ಗಳು) ಮೊದಲ ವೈಫಲ್ಯದಲ್ಲೇ ಸ್ಥಗಿತಗೊಳ್ಳುತ್ತದೆ.

**ಮೂಲ ಕಾರಣ**: ಮೂರು ಸ್ವತಂತ್ರ ವೈಫಲ್ಯ ವಿಧಾನಗಳು ಒಟ್ಟುಗೂಡುತ್ತವೆ:

1. **ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿ (`429`)**: ಉಚಿತ ಹಂತಗಳು ಪ್ರತಿ ಸಮಯ-ವಿಂಡೋಗೆ ಕೋಟಾವನ್ನು ಜಾರಿಗೊಳಿಸಬಹುದು. ಸಮಾಂತರ ಕರೆಗಳ ದಿಢೀರ್ ಹೆಚ್ಚಳವು ಅದನ್ನು ಖಾಲಿ ಮಾಡುತ್ತದೆ, ಆದ್ದರಿಂದ ವಿಂಡೋ ಮರುಹೊಂದುವವರೆಗೆ ಮುಂದಿನ ವಿನಂತಿಯನ್ನು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ.
2. **ಪಾಸ್ಥ್ರೂದಲ್ಲಿನ ದೋಷಪೂರಿತ ಮಾಡೆಲ್ (`400`/`401`)**: `auto/*` ಪೂಲ್ಗಳು `opencode`ನಿಂದ ಪಾಸ್ಥ್ರೂ ಮಾಡೆಲ್ಗಳನ್ನು ಒಳಗೊಂಡಿರಬಹುದು; ಅವು ಕ್ಯಾಟಲಾಗ್ನಲ್ಲಿ ನೋಂದಾಯಿಸಲ್ಪಟ್ಟಿದ್ದರೂ ಸಕ್ರಿಯ ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ (ಉದಾ. `oc/north-mini-code-free` → `401`). ಸ್ವಯಂ-ರೂಟರ್ ಒಂದನ್ನು ಪ್ರಯತ್ನಿಸುತ್ತದೆ, ಅದು ವಿಫಲವಾಗುತ್ತದೆ ಮತ್ತು ಪರ್ಯಾಯ ವ್ಯವಸ್ಥೆ ಸಕ್ರಿಯವಾಗುವ ಮೊದಲೇ ದೋಷವು ಮುಂದಕ್ಕೆ ಪ್ರಸಾರವಾಗುತ್ತದೆ.
3. **ಸಮಕಾಲೀನತೆಯ ವೃದ್ಧಿ (ಲೋಡ್ನಡಿ `429`)**: ಅನೇಕ ಏಜೆಂಟ್/cron ಸೆಷನ್ಗಳು ಒಂದೇ ಸಮಯದಲ್ಲಿ `auto` ಅನ್ನು ಬಳಸಿದಾಗ, ಒಟ್ಟಾರೆ ವಿನಂತಿ ದರವು ಉಚಿತ ಪೂರೈಕೆದಾರರು ಸಹಿಸಬಹುದಾದ ಮಟ್ಟವನ್ನು ಮೀರುತ್ತದೆ; ಇದರಿಂದ ನ್ಯಾಯಸಮ್ಮತ ಕರೆಗಳನ್ನೂ ದುರುಪಯೋಗವೆಂದು ಗುರುತಿಸಲಾಗುತ್ತದೆ.

**ಪರಿಶೀಲಿಸಲಾದ ಪರಿಹಾರ (ಸಮುದಾಯದಿಂದ ವರದಿಯಾದದ್ದು, 2026-08-10)**: ರೋಟೇಶನ್, ಸಮಕಾಲೀನತೆ ಮತ್ತು ಪರ್ಯಾಯ ವ್ಯವಸ್ಥೆಗಳು ಉಚಿತ-ಹಂತದ ಏರಿಳಿತಗಳಿಂದ ಸ್ಥಗಿತಗೊಳ್ಳುವ ಬದಲು ಅವುಗಳನ್ನು ನಿಭಾಯಿಸುವಂತೆ ಮೂರು ಪರಿಸರ ಚರಗಳನ್ನು ಹೊಂದಿಸಿ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ಬಂದಾಗ ಮತ್ತೊಂದು ಮಾಡೆಲ್/ಪೂರೈಕೆದಾರರಿಗೆ ಬದಲಿಸಿ (ದೋಷಪೂರಿತ ಪಾಸ್ಥ್ರೂ ಮಾಡೆಲ್ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ಹೆವಿವೇಟ್ ಪ್ರವೇಶಕ್ಕೆ ಸ್ಪಷ್ಟ ಗರಿಷ್ಠ ಮಿತಿ (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಹೊಂದಿಸಲಾಗಿಲ್ಲ: ವಿನಂತಿ-ಎಣಿಕೆ ಮಿತಿಯಿಲ್ಲ, ಕೆಳಗಿನ ಟಿಪ್ಪಣಿ ನೋಡಿ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ತಕ್ಷಣದ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ 503 ಬದಲಿಗೆ ಹೆವಿವೇಟ್ ಸಾಮರ್ಥ್ಯಕ್ಕಾಗಿ ದೀರ್ಘವಾದ ಸೀಮಿತ ಕಾಯುವಿಕೆ
```

ಇವುಗಳನ್ನು OmniRoute ಪ್ರಕ್ರಿಯೆಯ ಪರಿಸರದಲ್ಲಿ (ಡೀಮನ್ನಲ್ಲಿ, ಉದಾ. LaunchAgent plist ಅಥವಾ `systemctl edit` ಮೂಲಕ) ಹೊಂದಿಸಿ, ನಂತರ OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ. ರೋಟೇಶನ್ ಫ್ಲ್ಯಾಗ್ ಅತ್ಯಂತ ಪರಿಣಾಮಕಾರಿ ಏಕೈಕ ಸಾಧನವಾಗಿದೆ: ಇದು ಕಠಿಣ ವೈಫಲ್ಯವನ್ನು ಪೂಲ್ನಲ್ಲಿರುವ ಆರೋಗ್ಯಕರ ಪೂರೈಕೆದಾರರ ವಿರುದ್ಧದ ಪಾರದರ್ಶಕ ಮರುಪ್ರಯತ್ನವಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ.

**ಟಿಪ್ಪಣಿ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ಒಂದೇ ಸಮಯದಲ್ಲಿ ಎಷ್ಟು ಹೆವಿವೇಟ್ — ದೀರ್ಘ-ಸಂದರ್ಭದ — ವಿನಂತಿಗಳು ರನ್ ಆಗುತ್ತವೆ ಎಂಬುದನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ; ಈ ಮಿತಿಯು ಪ್ರವೇಶ ಗೇಟ್ ಆಗಿದ್ದು, ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆಯಲ್ಲ. **#503-ಫ್ಯಾನ್ಔಟ್ ನವೀಕರಣ:** ಈ var ಅನ್ನು ಇನ್ನು ಮುಂದೆ ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಹೊಂದಿಸಲಾಗುವುದಿಲ್ಲ (ಮೇಲೆ ತೋರಿಸಿದಂತೆ ಸ್ಪಷ್ಟವಾಗಿ ಸಂರಚಿಸಿದಾಗ ಮಾತ್ರ ಈಗ ಇದು ಅನ್ವಯಿಸುತ್ತದೆ) — ಬದಲಾಗಿ ಹೆವಿವೇಟ್ ಪ್ರವೇಶವನ್ನು ಸ್ವಯಂ-ವ್ಯುತ್ಪನ್ನ ಬೈಟ್ ಬಜೆಟ್ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ಮೂಲಕ ನಿಯಂತ್ರಿಸಲಾಗುತ್ತದೆ; ಅದು ಹೋಸ್ಟ್ನ ನೈಜ ಮೆಮೊರಿ ಮಿತಿಗೆ ಅನುಗುಣವಾಗಿ ಸ್ವತಃ ಸ್ಕೇಲ್ ಆಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಹೊಸ ನಿಯೋಜನೆಯು ಈ var ಅನ್ನು ಹೊಂದಿಸದೆಯೇ ಬಹಳ ಕಡಿಮೆ `503 chat_admission_busy` ನಿರಾಕರಣೆಗಳನ್ನು ಕಾಣಬೇಕು; ಇಲ್ಲಿ ಇದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸುವುದು ಇನ್ನೂ ದಾಖಲಿಸಿದಂತೆಯೇ ನಿಖರವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ. ಸ್ಪಷ್ಟ ಬೈಟ್-ಬಜೆಟ್ ಅತಿಕ್ರಮಣಗಳನ್ನು 8 MiB–2 GiBಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗುತ್ತದೆ. `413 body_exceeds_budget` ತಾತ್ಕಾಲಿಕವಲ್ಲ: ಆ ಬೈಟ್ ಬಜೆಟ್ ಅನ್ನು ಹೆಚ್ಚಿಸಿ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ಅನ್ನು ಕಡಿಮೆ ಮಾಡಿ, ಅಥವಾ ಪ್ರಕ್ರಿಯೆಯ ಮೆಮೊರಿ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ. `inflight_bytes_budget` ಶೆಡ್ ತಾತ್ಕಾಲಿಕ ಸಂಪನ್ಮೂಲ ಪೈಪೋಟಿಯಾಗಿದ್ದು, ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ಪ್ರತಿ-ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆಯನ್ನು (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ಮತ್ತು `RATE_LIMIT_AUTO_ENABLE` ಮೂಲಕ ಪ್ರತ್ಯೇಕವಾಗಿ ನಿಯಂತ್ರಿಸಲಾಗುತ್ತದೆ — `.env.example` ನೋಡಿ.

**ಇದು ಕೆಲಸ ಮಾಡಿದೆ ಎಂದು ಪರಿಶೀಲಿಸುವುದು ಹೇಗೆ**: ನಿಮ್ಮ agent/cron ಅನ್ನು ತ್ವರಿತವಾಗಿ ಸತತ ಎರಡು ಬಾರಿ ಚಲಾಯಿಸಿ ಮತ್ತು ಎರಡೂ ಯಶಸ್ವಿಯಾಗುತ್ತವೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ. ಸರಿಪಡಿಸುವ ಮೊದಲು, ಎರಡನೇ ಚಾಲನೆಯು ಸಾಮಾನ್ಯವಾಗಿ `429`/`401` ದೋಷವನ್ನು ನೀಡುತ್ತದೆ. ಸರಿಪಡಿಸಿದ ನಂತರ, ವೈಫಲ್ಯಗಳಿದ್ದರೆ ಅವುಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಕರೆ ಪೂರ್ಣಗೊಳ್ಳುತ್ತದೆ. ನೀವು `curl /monitoring/health` ಅನ್ನು ಸಹ ಚಲಾಯಿಸಬಹುದು ಮತ್ತು provider ಸಂಪರ್ಕಗಳಲ್ಲಿನ `rateLimitedUntil` ಕ್ಷೇತ್ರ ಹಾಗೂ ಪರಿಣಾಮಕ್ಕೊಳಗಾದ providerಗಳಿಗಾಗಿ `circuitBreakers.providerBreakers[].state` ಅನ್ನು ಗಮನಿಸಬಹುದು — ಸ್ಥಿತಿಯು `CLOSED`, `DEGRADED`, `OPEN`, ಅಥವಾ `HALF_OPEN` ಇವುಗಳಲ್ಲಿ ಒಂದಾಗಿರುತ್ತದೆ (`src/shared/utils/circuitBreaker.ts` ನೋಡಿ), ಮತ್ತು ನಿರಂತರವಾಗಿ ವಿಫಲವಾಗುವ provider, ಮರುಹೊಂದಿಸುವ ಅವಧಿಯು ಪ್ರಾಯೋಗಿಕ ಕರೆಗೆ ಅವಕಾಶ ನೀಡುವ (`HALF_OPEN`) ಮೊದಲು `CLOSED → DEGRADED → OPEN` ಗೆ ಬದಲಾಗುತ್ತದೆ.

**ನೀವು ಇನ್ನೂ 429 ಅನ್ನು ನೋಡುತ್ತಿದ್ದರೆ**: ಆ providerಗಾಗಿ ಸಕ್ರಿಯ ಖಾತೆಯು ನಿಜವಾಗಿಯೂ ತನ್ನ _quota_ ಅನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಳಸಿದೆ (ಕೇವಲ rate ಅಲ್ಲ). OmniRoute dashboard → Providers → Accounts ನಲ್ಲಿ ಅದೇ providerಗಾಗಿ ಎರಡನೇ ಖಾತೆಯನ್ನು ಸೇರಿಸಿ, ಅಥವಾ ಮತ್ತೊಂದು ಉಚಿತ provider ಅನ್ನು (ಉದಾ. `routeway`, `auggie`) ಜೊತೆಗೆ ಬಳಸಿ. Rotation ತಾತ್ಕಾಲಿಕ rate/400/401 ಸಮಸ್ಯೆಗಳಿಗೆ ಮಾತ್ರ ಸಹಾಯ ಮಾಡುತ್ತದೆ; quota ಸಂಪೂರ್ಣವಾಗಿ ಖಾಲಿಯಾಗಿದ್ದರೆ ಎರಡನೇ credential ಅಥವಾ ಬೇರೊಂದು provider ಅಗತ್ಯವಿರುತ್ತದೆ.

**vision models (`auto/vision`, `bazaarlink/*`) ನಲ್ಲಿ 403 ಕಂಡುಬಂದರೆ**: ಸಂಪರ್ಕಿತ ಖಾತೆಯಲ್ಲಿ vision ಅನ್ನು ಒಳಗೊಂಡಿರುವ paid plan ಇಲ್ಲ, ಅಥವಾ API key ಸಾಕಷ್ಟು permissions ಹೊಂದಿಲ್ಲ. key scope ನಲ್ಲಿ vision/multimodal ಒಳಗೊಂಡಿದೆ ಎಂಬುದನ್ನು provider dashboard ನಲ್ಲಿ ಪರಿಶೀಲಿಸಿ, ಅಥವಾ paid tier ಖಾತೆಯನ್ನು ಸಂಪರ್ಕಿಸಿ ಮತ್ತು ಅದನ್ನು vision target ಆಗಿಯೇ ಇರಿಸಿ.

## npm install ಎಚ್ಚರಿಕೆಗಳು (ERESOLVE / peer / deprecated)

ನೀವು `npm install -g omniroute` ಅನ್ನು ಚಲಾಯಿಸಿದಾಗ, `npm warn ERESOLVE`, peer-dependency ಸೂಚನೆಗಳು ಮತ್ತು `deprecated` ಸಂದೇಶಗಳಂತಹ ಅನೇಕ ಎಚ್ಚರಿಕೆಗಳು ಕಾಣಿಸಬಹುದು. **ಇವು ನಿರೀಕ್ಷಿತವಾಗಿದ್ದು ಹಾನಿಕರವಲ್ಲ.** ಔಟ್ಪುಟ್ನಲ್ಲಿ `added <N> packages` ಎಂದು ಕಂಡುಬಂದರೆ ನಿಮ್ಮ ಸ್ಥಾಪನೆ ಯಶಸ್ವಿಯಾಗಿದೆ.

peer-dependency ಪರಿಹಾರದ ಎಚ್ಚರಿಕೆಗಳನ್ನು ನಿಗ್ರಹಿಸಲು, OmniRoute ಬೆಂಬಲಿಸುವ ಸ್ಥಾಪನಾ ವಿಧಾನವನ್ನು ಬಳಸಿ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` ಕೇವಲ `ERESOLVE` ಮತ್ತು peer-dependency ಸೂಚನೆಗಳನ್ನು ನಿಗ್ರಹಿಸುತ್ತದೆ. ಬಳಕೆಯಿಂದ ಹಿಂತೆಗೆದುಕೊಳ್ಳುವಿಕೆ ಕುರಿತ ಸೂಚನೆಗಳು ಇನ್ನೂ ಗೋಚರಿಸುತ್ತವೆ, ಏಕೆಂದರೆ ಅವು ಪರೋಕ್ಷ third-party packages ನಿಂದ ಬರುತ್ತವೆ; ಅವು ಸ್ಥಾಪನೆ ವಿಫಲವಾಗಿದೆ ಎಂಬುದನ್ನು ಸೂಚಿಸುವುದಿಲ್ಲ.

OmniRoute ನಿಯಂತ್ರಿಸದ third-party packages ನಲ್ಲಿರುವ ಹಳೆಯ peer-dependency ಶ್ರೇಣಿಗಳಿಂದ ಈ ಎಚ್ಚರಿಕೆಗಳು ಬರುತ್ತವೆ:

1. **`marked-terminal` ಗೆ `marked >=1 <16` ಬೇಕಾಗಿದೆ, ಆದರೆ `marked@18` ಕಂಡುಬಂದಿದೆ** — ಪ್ರಾಯೋಗಿಕವಾಗಿ ಸರಿಯಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ; upstream peer ಶ್ರೇಣಿಯು ಕೇವಲ ಹಳೆಯದಾಗಿದೆ.
2. **`deprecated prebuild-install@7.1.3`** — ಪರೋಕ್ಷ native-binary ಪಡೆಯುವ ಸಹಾಯಕ. ಇದನ್ನು ಪಿನ್ ಮಾಡಲಾದ `wreq-js` transport binding ಅನ್ನು ಸ್ಥಾಪಿಸಲು
   ಬಳಸುವುದಿಲ್ಲ ಮತ್ತು web-cookie provider transport ಸೆಟಪ್ ವಿಫಲವಾಗಿದೆ ಎಂಬುದನ್ನೂ ಇದು ಸೂಚಿಸುವುದಿಲ್ಲ.

**ಯಾವುದೇ ಕ್ರಮದ ಅಗತ್ಯವಿಲ್ಲ** — upstream packages ಅನ್ನು fork ಮಾಡದೆ ಈ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಿಶ್ಶಬ್ದಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ.

## Gemini Web ಮತ್ತು Playwright Chromium

Gemini Web ವಿನಂತಿಯು Playwright Chromium ಸ್ಥಾಪಿಸಲಾಗಿಲ್ಲ ಎಂಬ ಸಂದೇಶದೊಂದಿಗೆ `503` ಅನ್ನು ಹಿಂದಿರುಗಿಸಿದರೆ,
npm package ಇದೆ, ಆದರೆ browser binary ಕಾಣೆಯಾಗಿದೆ ಎಂದರ್ಥ.
Playwright ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ browser downloads ಅನ್ನು npm package
ಸ್ಥಾಪನೆಯಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿರಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ browser ಸ್ಥಾಪಿಸುವವರೆಗೆ ಈ ಪ್ರತಿಕ್ರಿಯೆ ನಿರೀಕ್ಷಿತವಾಗಿದೆ.

ಜಾಗತಿಕ npm ಸ್ಥಾಪನೆಗಾಗಿ, OmniRoute package ನ
ಡೈರೆಕ್ಟರಿಯಿಂದ Chromium ಅನ್ನು ಸ್ಥಾಪಿಸಿ, ಇದರಿಂದ browser cache ಅದೇ Playwright ಸ್ಥಾಪನೆಗೆ ಸೇರಿರುತ್ತದೆ:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ಸ್ಥಾಪನೆಯ ನಂತರ OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ, ಬಳಿಕ Gemini Web ವಿನಂತಿಯನ್ನು ಪುನಃ ಪ್ರಯತ್ನಿಸಿ. ನೀವು
Docker image ನಿಂದ OmniRoute ಅನ್ನು ಚಲಾಯಿಸುತ್ತಿದ್ದರೆ, Chromium ಮತ್ತು ಅದರ dependencies ಅನ್ನು ಒಳಗೊಂಡಿರುವ `-web` image (ಅಥವಾ `runner-web`
build target) ಅನ್ನು ಬಳಸಿ; base image ಅವುಗಳನ್ನು
ಒಳಗೊಂಡಿರುವುದಿಲ್ಲ.

## ಆಂಟಿವೈರಸ್ನ ತಪ್ಪು ಪಾಸಿಟಿವ್ಗಳು

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md` ಅನ್ನು `MD:HttpRequest-inf[Susp]` ಎಂದು ಕ್ವಾರಂಟೈನ್ ಮಾಡುತ್ತದೆ

**ಇದು ತಪ್ಪು ಪಾಸಿಟಿವ್ ಆಗಿದೆ. ಯಾವುದೂ ಸೋಂಕಿತವಾಗಿಲ್ಲ ಮತ್ತು ಯಾವುದೇ ಕ್ರಮದ ಅಗತ್ಯವಿಲ್ಲ.**

ಹಲವಾರು HTTP ವಿನಂತಿಗಳಂತೆ ಕಾಣುವ ಲಿಂಕ್ಗಳನ್ನು ಹೊಂದಿರುವ ಸರಳ-ಪಠ್ಯ/Markdown ಫೈಲ್ಗಳನ್ನು ಗುರುತಿಸುವ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು Avast ಮತ್ತು AVG ಚಲಾಯಿಸುತ್ತವೆ. OmniRoute ನ `README.md`, npm ಪ್ಯಾಕೇಜ್ನೊಳಗೆ ಬರುತ್ತದೆ (ಇದನ್ನು `package.json` → `files` ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾಗಿದೆ), ಆದ್ದರಿಂದ ಜಾಗತಿಕ ಇನ್ಸ್ಟಾಲ್ನಲ್ಲಿ ಅದು `node_modules/omniroute/README.md` ಗೆ ಸೇರುತ್ತದೆ — ಮತ್ತು ಅದರಲ್ಲಿ ಸುಮಾರು 15 `http://localhost:20128/...` ಉದಾಹರಣೆಗಳಿವೆ (MCP HTTP/SSE ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು, A2A `.well-known` URL ಮತ್ತು `curl` ತುಣುಕುಗಳು). ಅಷ್ಟು ಪ್ರಮಾಣದ ಲಿಂಕ್ ಸಾಂದ್ರತೆಯು ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಕಾಗುತ್ತದೆ.

ಇದು ಇತ್ತೀಚೆಗೆ ಮಾತ್ರ ಪ್ರಾರಂಭವಾಗಿದ್ದರೆ: ಫೈಲ್ನ ಸ್ವರೂಪ ಬದಲಾಗಿಲ್ಲ. README ಯ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳ ಕೋಷ್ಟಕ ವಿಸ್ತರಿಸಿದೆ (MCP HTTP + SSE + A2A ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ) ಮತ್ತು ಹೆಚ್ಚಿನ `curl` ಉದಾಹರಣೆಗಳನ್ನು ಸೇರಿಸಲಾಗಿದೆ; ಇದರಿಂದ ಅದು ಮಿತಿಯನ್ನು ಮೀರಿದೆ.

ಈ ಫೈಲ್ ಯಾವುದೇ ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದ ವಿಷಯವಿಲ್ಲದ ನಿಷ್ಕ್ರಿಯ ದಸ್ತಾವೇಜು. ನೀವು ಅದನ್ನು ಕ್ವಾರಂಟೈನ್ನಿಂದ ಸುರಕ್ಷಿತವಾಗಿ ಮರುಸ್ಥಾಪಿಸಬಹುದು.

**ಏನು ಮಾಡಬೇಕು:**

1. **ಅಧಿಸೂಚನೆಗಳನ್ನು ನಿಲ್ಲಿಸಿ** — ನಿಮ್ಮ ಆಂಟಿವೈರಸ್ನಲ್ಲಿ ಇನ್ಸ್ಟಾಲ್ ಡೈರೆಕ್ಟರಿಯನ್ನು ಹೊರತುಪಡಿಸಿ
   (Avast: Settings → Exceptions), ನಿಮ್ಮ ಜಾಗತಿಕ `node_modules` ಪಥ ಮತ್ತು/ಅಥವಾ
   OmniRoute ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯನ್ನು (`~/.omniroute/`) ಸೇರಿಸಿ.
2. **ತಪ್ಪು ಪಾಸಿಟಿವ್ ಅನ್ನು ವರದಿ ಮಾಡಿ** — <https://www.avast.com/false-positive-file-form.php>,
   ಕ್ವಾರಂಟೈನ್ ಮಾಡಲಾದ `README.md` ಅನ್ನು ಲಗತ್ತಿಸಿ. ಪಠ್ಯ ಫೈಲ್ಗೆ ಮಾರಾಟಗಾರರ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅತಿಯಾಗಿ ಪ್ರತಿಕ್ರಿಯಿಸುತ್ತಿರುವುದರಿಂದ, ಎಲ್ಲರಿಗೂ ಸಹಾಯ ಮಾಡುವ ಪರಿಹಾರ ಇದೇ ಆಗಿದೆ.

**ನಾವು ಇದನ್ನು ನಮ್ಮ ಕಡೆಯಿಂದ ಏಕೆ "ಸರಿಪಡಿಸುವುದಿಲ್ಲ":** ಎಲ್ಲಾ ಉದಾಹರಣೆಗಳೂ `http://localhost` ಆಗಿವೆ ಮತ್ತು ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ ಪ್ರಮಾಣಪತ್ರದ ತೊಂದರೆಯಿಲ್ಲದೆ localhost ಅನ್ನು `https` ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಒಬ್ಬ ಮಾರಾಟಗಾರರ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು ತಪ್ಪಿಸಲು ದಸ್ತಾವೇಜುಗಳನ್ನು ವಿರೂಪಗೊಳಿಸುವುದರಿಂದ, ಸ್ಕ್ಯಾನರ್ ದೋಷವನ್ನು ತೃಪ್ತಿಪಡಿಸಲು ಪ್ರತಿಯೊಬ್ಬ ಓದುಗರಿಗೂ ತೊಂದರೆಯಾಗುತ್ತದೆ.

### Kaspersky ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ ಅನ್ನು `PDM:Trojan.Win32.Generic` ಎಂದು ಗುರುತಿಸುತ್ತದೆ

**ಇದು ವರ್ತನಾ ಹ್ಯೂರಿಸ್ಟಿಕ್ನಿಂದ ಉಂಟಾದ ತಪ್ಪು ಪಾಸಿಟಿವ್ ಆಗಿದೆ. ಯಾವುದೂ ಸೋಂಕಿತವಾಗಿಲ್ಲ.** Kaspersky ಯ `PDM:` ಪೂರ್ವಪ್ರತ್ಯಯ ಎಂದರೆ, ತೀರ್ಪು ಅದರ Proactive Defense Module (System Watcher) ನಿಂದ ಬಂದಿದೆ; ಇದು ತಿಳಿದಿರುವ ಮಾಲ್ವೇರ್ಗೆ ಹೋಲಿಸುವ ಬದಲು ಇನ್ಸ್ಟಾಲರ್ ಏನು _ಮಾಡುತ್ತದೆ_ ಎಂಬುದನ್ನು ನಿರ್ಣಯಿಸುತ್ತದೆ. ಇದು ಪ್ರಚೋದಿತವಾದಾಗ, Kaspersky ಸಂಪೂರ್ಣ ಇನ್ಸ್ಟಾಲೇಶನ್ ಅನ್ನು "ಹಿಂದಕ್ಕೆ ತಿರುಗಿಸುತ್ತದೆ" — ಈಗಾಗಲೇ ಬರೆದಿದ್ದ ಫೈಲ್ಗಳನ್ನು ಅಳಿಸುತ್ತದೆ — ಆದ್ದರಿಂದ ಆ್ಯಪ್ ಹಾಳಾಗುತ್ತದೆ ಅಥವಾ ಕಾಣೆಯಾಗುತ್ತದೆ.

ಇದು ಗುರುತಿಸುವ ಫೈಲ್ಗಳು ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ನೊಂದಿಗೆ ಬಂಡಲ್ ಮಾಡಲಾದ, ಘೋಷಿತ ಮುಕ್ತ-ಮೂಲ ಅವಲಂಬನೆಗಳ ಪ್ರಮಾಣಿತ ಭಾಗಗಳಾಗಿವೆ, ಉದಾಹರಣೆಗೆ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ಮತ್ತು
  `workerProcessEntry.js` — ಆ್ಯಪ್ನೊಳಗಿನ ಪೂರೈಕೆದಾರರ ಲಾಗಿನ್ ಮತ್ತು ಬ್ರೌಸರ್-ಆಧಾರಿತ ಚಾಟ್ಗಾಗಿ ಬಳಸಲಾಗುವ ಬ್ರೌಸರ್-ಸ್ವಯಂಚಾಲನಾ ಲೈಬ್ರರಿಯಾದ [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ವೆಬ್-ಕುಕಿ ಪೂರೈಕೆದಾರರಲ್ಲಿ ಬ್ರೌಸರ್-ಫಿಂಗರ್ಪ್ರಿಂಟ್ ಮಾಡಿದ HTTP ಗಾಗಿ ಬಳಸಲಾಗುವ, ನಿಗದಿತ `wreq-js` ನೇಟಿವ್ ಬೈಂಡಿಂಗ್ (`<arch>` ಎಂಬುದು `x64` ಅಥವಾ `arm64` ಆಗಿರುತ್ತದೆ).

**ಇದು ಏಕೆ ಪ್ರಚೋದಿತವಾಗುತ್ತದೆ:** Windows ಇನ್ಸ್ಟಾಲರ್ಗೆ **ಇನ್ನೂ ಕೋಡ್ ಸಹಿ ಮಾಡಲಾಗಿಲ್ಲ**, ಆದ್ದರಿಂದ ಸಹಿ ಮಾಡದ NSIS ಇನ್ಸ್ಟಾಲರ್ಗೆ ಯಾವುದೇ ಪ್ರತಿಷ್ಠೆ ಇರುವುದಿಲ್ಲ ಮತ್ತು ವರ್ತನಾ ಹ್ಯೂರಿಸ್ಟಿಕ್ಗಳು ಗರಿಷ್ಠ ಆಕ್ರಮಣಶೀಲತೆಯಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ. ಬಂಡಲ್ ಮಾಡಲಾದ ನೇಟಿವ್ DLL ಮತ್ತು `%LOCALAPPDATA%\Programs\OmniRoute` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾಗುವ ನೂರಾರು `.js` ಫೈಲ್ಗಳೊಂದಿಗೆ (Next.js ಸ್ವತಂತ್ರ ಬಿಲ್ಡ್ನ ಹ್ಯಾಶ್-ಪ್ರತ್ಯಯ ಹೊಂದಿರುವ ಪ್ಯಾಕೇಜ್ ಡೈರೆಕ್ಟರಿಗಳೂ ಸೇರಿ), ಇದು ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಕಾಗುತ್ತದೆ. ಕೋಡ್ ಸಹಿ ಮಾಡುವುದನ್ನು ಯೋಜಿಸಲಾಗಿದೆ; ಅದು ಜಾರಿಗೆ ಬರುವವರೆಗೆ ಹೊಸ ಬಿಡುಗಡೆಗಳಲ್ಲಿ ಇದು ಪುನರಾವರ್ತಿಸಬಹುದು.

**ಏನು ಮಾಡಬೇಕು:**

1. **ಮೊದಲು ನಿಮ್ಮ ಡೌನ್ಲೋಡ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ** (ಇದು ತಿರುಚಲಾದ ಫೈಲ್ನ ಸಾಧ್ಯತೆಯನ್ನು ತಳ್ಳಿಹಾಕುತ್ತದೆ). ಪ್ರತಿ ಬಿಡುಗಡೆಯೂ `latest.yml` ಅನ್ನು ಪ್ರಕಟಿಸುತ್ತದೆ; ಅದರ `sha512` ಕ್ಷೇತ್ರವು (base64) `OmniRoute.Setup.<version>.exe` ಇನ್ಸ್ಟಾಲರ್ ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. PowerShell ನಲ್ಲಿ, ಇನ್ಸ್ಟಾಲರ್ ಇರುವ ಫೋಲ್ಡರ್ನಿಂದ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ಔಟ್ಪುಟ್ `latest.yml` → `sha512` ಗೆ ಹೊಂದಿಕೆಯಾಗಬೇಕು. ಹೊಂದಿಕೆಯಾಗದಿದ್ದರೆ, ಫೈಲ್ ಅನ್ನು ಅಳಿಸಿ ಮತ್ತು [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) ನಿಂದ ಮಾತ್ರ ಮರು-ಡೌನ್ಲೋಡ್ ಮಾಡಿ.
2. **ಮರುಸ್ಥಾಪಿಸಿ + ಹೊರತುಪಡಿಸಿ** — ಹಿಂದಕ್ಕೆ ತಿರುಗಿಸಲಾದ ಐಟಂಗಳನ್ನು ಕ್ವಾರಂಟೈನ್ನಿಂದ ಮರುಸ್ಥಾಪಿಸಿ ಮತ್ತು
   `%LOCALAPPDATA%\Programs\OmniRoute` ಗಾಗಿ ಹೊರತುಪಡಿಸುವಿಕೆಯನ್ನು ಸೇರಿಸಿ (Kaspersky → Settings → Threats and Exclusions),
   ನಂತರ ಮರುಸ್ಥಾಪನೆ ಮಾಡಿ.
3. **ತಪ್ಪು ಪಾಸಿಟಿವ್ ಅನ್ನು ವರದಿ ಮಾಡಿ** — <https://opentip.kaspersky.com/>. ಬಳಕೆದಾರರು ಸಲ್ಲಿಸುವ ತಪ್ಪು ಪಾಸಿಟಿವ್ ವರದಿಗಳು ಅನುಮತಿ ಪಟ್ಟಿಗೆ ಸೇರಿಸುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ನಿಜವಾಗಿಯೂ ವೇಗಗೊಳಿಸುತ್ತವೆ.

## Node.js ಹೊಂದಾಣಿಕೆ

<a name="nodejs-compatibility"></a>

### ಲಾಗಿನ್ ಪುಟ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ ಅಥವಾ "Module self-registration" ದೋಷವನ್ನು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** ನೀವು OmniRoute ಅನುಮೋದಿಸಿದ ಸುರಕ್ಷಿತ ರನ್ಟೈಮ್ನ ಕನಿಷ್ಠ ಮಿತಿಯ ಹೊರಗಿನ Node.js ಆವೃತ್ತಿಯನ್ನು ಚಾಲನೆ ಮಾಡುತ್ತಿದ್ದೀರಿ. OmniRoute ಅಗತ್ಯಪಡಿಸುವ ಭದ್ರತಾ ಪ್ಯಾಚ್ನ ಕನಿಷ್ಠ ಮಿತಿಗಿಂತ ಕೆಳಗಿರುವ ಹಳೆಯ Node 22 ಅಥವಾ 24 ಪ್ಯಾಚ್ ಮಟ್ಟವನ್ನು ಚಾಲನೆ ಮಾಡುವುದು ಅತ್ಯಂತ ಸಾಮಾನ್ಯ ಸಂದರ್ಭವಾಗಿದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಲಾಗಿನ್ ಪುಟವು ಖಾಲಿ ಪರದೆ ಅಥವಾ ಸರ್ವರ್ ದೋಷವನ್ನು ತೋರಿಸುತ್ತದೆ
- ಕನ್ಸೋಲ್ನಲ್ಲಿ `Error: Module did not self-register` ಅಥವಾ ಅದೇ ರೀತಿಯ ನೇಟಿವ್ ಬೈಂಡಿಂಗ್ ದೋಷಗಳು ಕಾಣಿಸುತ್ತವೆ
- ರನ್ಟೈಮ್ ಬೆಂಬಲಿತ ಸುರಕ್ಷತಾ ನೀತಿಯ ಹೊರಗಿದ್ದರೆ, ಲಾಗಿನ್ ಪುಟವು ನಿಮ್ಮ Node ಆವೃತ್ತಿಯೊಂದಿಗೆ **ಕಿತ್ತಳೆ ಬಣ್ಣದ ಎಚ್ಚರಿಕೆ ಬ್ಯಾನರ್** ಅನ್ನು ತೋರಿಸುತ್ತದೆ

**ಪರಿಹಾರ:**

1. ಬೆಂಬಲಿತ Node.js LTS ಬಿಡುಗಡೆಯನ್ನು ಸ್ಥಾಪಿಸಿ (ಶಿಫಾರಸು: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ನಿಮ್ಮ ಆವೃತ್ತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ: `node --version` ಎಂಬುದು 24.x LTS ಶ್ರೇಣಿಯಲ್ಲಿ `v24.0.0` ಅಥವಾ ಅದಕ್ಕಿಂತ ಹೊಸ ಆವೃತ್ತಿಯನ್ನು ತೋರಿಸಬೇಕು
3. OmniRoute ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ: `npm install -g omniroute`
4. ಮರುಪ್ರಾರಂಭಿಸಿ: `omniroute`

> **ಬೆಂಬಲಿತ ಸುರಕ್ಷಿತ ಆವೃತ್ತಿಗಳು:** `>=22.22.2 <23` ಅಥವಾ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ಮತ್ತು Node.js 26 ಸಂಪೂರ್ಣವಾಗಿ ಬೆಂಬಲಿತವಾಗಿವೆ.

### npm v11+: `better-sqlite3` ಸ್ಥಾಪನೆಯಾಗಿಲ್ಲ (ಮಾಡ್ಯೂಲ್ ಕಂಡುಬಂದಿಲ್ಲ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ಕಾರಣ:** npm v11 (Node.js 24+ ಜೊತೆಗೆ ಒದಗಿಸಲಾಗುತ್ತದೆ) ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಐಚ್ಛಿಕ
ಅವಲಂಬನೆಗಳ ಸ್ಥಾಪನಾ ಸ್ಕ್ರಿಪ್ಟ್ಗಳನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ. `better-sqlite3` ಅನ್ನು `optionalDependencies`
ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಿರುವುದರಿಂದ ಮತ್ತು ಅದಕ್ಕೆ ನೇಟಿವ್ ಕಂಪೈಲೇಶನ್ (`node-gyp rebuild`) ಅಗತ್ಯವಿರುವುದರಿಂದ, npm ಯಾವುದೇ ಸೂಚನೆ ನೀಡದೆ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಪ್ರಾರಂಭಿಸುವಾಗ `Cannot find module 'better-sqlite3'` ದೋಷದೊಂದಿಗೆ ಸರ್ವರ್ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ
- `ls node_modules/better-sqlite3` ಎಂಬುದು "No such file or directory" ಎಂದು ತೋರಿಸುತ್ತದೆ
- `npm ls better-sqlite3` ಎಂಬುದು `(empty)` ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಪರಿಹಾರ:**

1. ಸ್ಥಾಪನಾ ಸ್ಕ್ರಿಪ್ಟ್ಗಳನ್ನು ಅನುಮೋದಿಸಿ ಮತ್ತು ಮರುಸ್ಥಾಪಿಸಿ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ಅಥವಾ ಪೂರ್ವನಿರ್ಮಿತ ಪ್ಯಾಕೇಜ್ ಅನ್ನು ಕೈಯಾರೆ ಸ್ಥಾಪಿಸಿ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ಅದು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ಕಾರಣ:** ಜಾಗತಿಕ `npm install -g omniroute` ನಂತರ, ಪ್ಯಾಕೇಜ್ನೊಳಗಿನ `better-sqlite3` ನೇಟಿವ್ ಬೈನರಿಯನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಾಲನೆಯಲ್ಲಿರುವುದಕ್ಕಿಂತ ಭಿನ್ನವಾದ ಆರ್ಕಿಟೆಕ್ಚರ್ ಅಥವಾ Node.js ABI ಗಾಗಿ ಕಂಪೈಲ್ ಮಾಡಿರಬಹುದು. ಪೂರ್ವನಿರ್ಮಿತ ಬೈನರಿ ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಹೊಂದಿಕೆಯಾಗದಿದ್ದಾಗ macOSನಲ್ಲಿ (Apple Silicon ಮತ್ತು Intel ಎರಡರಲ್ಲೂ) ಇದು ಸಾಮಾನ್ಯವಾಗಿದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಪ್ರಾರಂಭಿಸಿದ ತಕ್ಷಣವೇ `dlopen` ದೋಷದೊಂದಿಗೆ ಸರ್ವರ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- ದೋಷವು `slice is not valid mach-o file` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ
- ಸಂಪೂರ್ಣ ಉದಾಹರಣೆ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ಪರಿಹಾರ — ನಿಮ್ಮ ಸ್ಥಳೀಯ ಪರಿಸರಕ್ಕಾಗಿ ಮರುನಿರ್ಮಿಸಿ (Node.js ಆವೃತ್ತಿಯನ್ನು ಕೆಳಗಿಳಿಸುವ ಅಗತ್ಯವಿಲ್ಲ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ಗಮನಿಸಿ:** ಇದು ನಿಮ್ಮ ಸ್ಥಳೀಯ Node.js ಆವೃತ್ತಿ ಮತ್ತು CPU ಆರ್ಕಿಟೆಕ್ಚರ್ಗೆ ಅನುಗುಣವಾಗಿ ನೇಟಿವ್ ಬೈಂಡಿಂಗ್ ಅನ್ನು ಮರುಕಂಪೈಲ್ ಮಾಡಿ, ಬೈನರಿ ಅಸಾಮರಸ್ಯವನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. ಅಧಿಕೃತವಾಗಿ ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ಶ್ರೇಣಿಯು **`>=22.22.2 <23` ಅಥವಾ `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts` ನಲ್ಲಿರುವ `SUPPORTED_NODE_RANGE`, `package.json` ನ `engines` ಕ್ಷೇತ್ರದೊಂದಿಗೆ ಹೊಂದಿಸಲಾಗಿದೆ). Node.js 24.x LTS (Krypton) ಮತ್ತು Node.js 26 ಅನ್ನು `better-sqlite3` v12.x ಜೊತೆಗೆ ಸಂಪೂರ್ಣವಾಗಿ ಬೆಂಬಲಿಸಲಾಗುತ್ತದೆ.

## ಪ್ರಾಕ್ಸಿ ಸಮಸ್ಯೆಗಳು

<a name="proxy-issues"></a>

### ಪೂರೈಕೆದಾರರ ಪರಿಶೀಲನೆಯು "fetch failed" ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** API ಕೀ ಪರಿಶೀಲನಾ ಎಂಡ್ಪಾಯಿಂಟ್ (`POST /api/providers/validate`) ಈ ಹಿಂದೆ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಬಳಸದೇ ಇದ್ದುದರಿಂದ, ಪ್ರಾಕ್ಸಿ ರೂಟಿಂಗ್ ಅಗತ್ಯವಿರುವ ಪರಿಸರಗಳಲ್ಲಿ ವೈಫಲ್ಯಗಳು ಉಂಟಾಗುತ್ತಿದ್ದವು.

**ಪರಿಹಾರ (v3.5.5+):** ಇದನ್ನು ಈಗ ಸರಿಪಡಿಸಲಾಗಿದೆ. ಪೂರೈಕೆದಾರರ ಪರಿಶೀಲನೆಯು `runWithProxyContext` ಮೂಲಕ ರೂಟ್ ಆಗುತ್ತದೆ ಮತ್ತು ಪೂರೈಕೆದಾರ-ಮಟ್ಟದ ಹಾಗೂ ಜಾಗತಿಕ ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಗೌರವಿಸುತ್ತದೆ.

### ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಯು "fetch failed" ದೋಷದೊಂದಿಗೆ ವಿಫಲವಾಗುತ್ತದೆ

**ಕಾರಣ:** ಹಿನ್ನೆಲೆಯ OAuth ಟೋಕನ್ ರಿಫ್ರೆಶ್ ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸುತ್ತಿರಲಿಲ್ಲ.

**ಪರಿಹಾರ (v3.5.5+):** ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನಾ ಶೆಡ್ಯೂಲರ್ ಈಗ ರಿಫ್ರೆಶ್ ಮಾಡಲು ಪ್ರಯತ್ನಿಸುವ ಮೊದಲು ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. v3.5.5+ ಗೆ ನವೀಕರಿಸಿ.

### SOCKS5 ಪ್ರಾಕ್ಸಿಯು "invalid onRequestStart method" ದೋಷವನ್ನು ನೀಡುತ್ತದೆ

**ಕಾರಣ:** Node.js 22 ನಲ್ಲಿ, undici@8 ಡಿಸ್ಪ್ಯಾಚರ್ Node ನ ಅಂತರ್ನಿರ್ಮಿತ `fetch()` ಅನುಷ್ಠಾನದೊಂದಿಗೆ ಹೊಂದಾಣಿಕೆಯಾಗುವುದಿಲ್ಲ.

**ಪರಿಹಾರ (v3.5.5+):** ಪ್ರಾಕ್ಸಿ ಡಿಸ್ಪ್ಯಾಚರ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ OmniRoute ಈಗ undici ಯ ಸ್ವಂತ `fetch()` ಫಂಕ್ಷನ್ ಅನ್ನು ಬಳಸುತ್ತದೆ, ಇದರಿಂದ ಸ್ಥಿರವಾದ ವರ್ತನೆ ಖಚಿತವಾಗುತ್ತದೆ. v3.5.5+ ಗೆ ನವೀಕರಿಸಿ.

### WSL ಅಡಿಯಲ್ಲಿನ MITM ಪ್ರಾಕ್ಸಿ: Windows ಹೋಸ್ಟ್ನಲ್ಲಿರುವ ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳನ್ನು ಪ್ರತಿಬಂಧಿಸಲಾಗುವುದಿಲ್ಲ

**ಕಾರಣ:** OmniRoute ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಪರಿಸರದಲ್ಲಿಯೇ MITM ಪ್ರಾಕ್ಸಿ ಮತ್ತು ಅದರ CA ಪ್ರಮಾಣಪತ್ರ ಸ್ಥಾಪನೆಯಾಗುತ್ತವೆ. WSL ಅಡಿಯಲ್ಲಿ ಆ ಪರಿಸರವು Linux ಗೆಸ್ಟ್ ಆಗಿರುತ್ತದೆ, ಆದರೆ AI ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳು (Kiro, Trae, Copilot, Zed, …) Windows ಹೋಸ್ಟ್ನಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ. ಹೋಸ್ಟ್ ಆ್ಯಪ್ಗಳು ಗೆಸ್ಟ್ನ ಪ್ರಮಾಣಪತ್ರ ಸಂಗ್ರಹವನ್ನು ನಂಬುವುದಿಲ್ಲ ಮತ್ತು ಗೆಸ್ಟ್ನ ಸಿಸ್ಟಮ್ ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ರೂಟ್ ಆಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಅಲ್ಲಿ ಡೆಸ್ಕ್ಟಾಪ್ ಪ್ರತಿಬಂಧವು ಕಾರ್ಯನಿರ್ವಹಿಸುವುದಿಲ್ಲ.

**ಶಿಫಾರಸು:** ನೀವು ಪ್ರತಿಬಂಧಿಸಲು ಬಯಸುವ ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಅದೇ OS ನಲ್ಲಿ OmniRoute ಅನ್ನು ನೇಟಿವ್ ಆಗಿ ಚಲಾಯಿಸಿ (Windows ಆ್ಯಪ್ಗಳಿಗೆ Windows; macOS/Linux ಗೂ ಇದೇ ಅನ್ವಯಿಸುತ್ತದೆ). ಹೋಸ್ಟ್ ಆ್ಯಪ್ಗಳನ್ನು ಗುರಿಯಾಗಿಸಿಕೊಂಡು OmniRoute ಅನ್ನು WSL ಒಳಗೇ ಇರಿಸುವುದಾದರೆ, ರಚಿಸಲಾದ CA ಪ್ರಮಾಣಪತ್ರವನ್ನು Windows ಹೋಸ್ಟ್ನಲ್ಲಿ ಹಸ್ತಚಾಲಿತವಾಗಿ ವಿಶ್ವಾಸಾರ್ಹಗೊಳಿಸಬೇಕು ಮತ್ತು ಪ್ರತಿ ಹೋಸ್ಟ್ ಆ್ಯಪ್ನ ನೆಟ್ವರ್ಕ್/ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು WSL ಪ್ರಾಕ್ಸಿ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಸೂಚಿಸಬೇಕು — ಇದು ಬೆಂಬಲಿಸದ, ಸುಲಭವಾಗಿ ವಿಫಲವಾಗಬಹುದಾದ ಸಂರಚನೆಯಾಗಿದೆ.

## ಪೂರೈಕೆದಾರರ ಸಮಸ್ಯೆಗಳು

### "Language model did not provide messages"

**ಕಾರಣ:** ಪೂರೈಕೆದಾರರ ಕೋಟಾ ಮುಗಿದಿದೆ.

**ಪರಿಹಾರ:**

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ ಕೋಟಾ ಟ್ರ್ಯಾಕರ್ ಪರಿಶೀಲಿಸಿ
2. ಫಾಲ್ಬ್ಯಾಕ್ ಹಂತಗಳಿರುವ ಕಾಂಬೊ ಬಳಸಿ
3. ಅಗ್ಗದ/ಉಚಿತ ಹಂತಕ್ಕೆ ಬದಲಿಸಿ

### ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆ

**ಕಾರಣ:** ಚಂದಾದಾರಿಕೆಯ ಕೋಟಾ ಮುಗಿದಿದೆ.

**ಪರಿಹಾರ:**

- ಫಾಲ್ಬ್ಯಾಕ್ ಸೇರಿಸಿ: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- ಅಗ್ಗದ ಬ್ಯಾಕಪ್ ಆಗಿ GLM/MiniMax ಬಳಸಿ

### OAuth ಟೋಕನ್ ಅವಧಿ ಮುಗಿದಿದೆ

OmniRoute ಟೋಕನ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ರಿಫ್ರೆಶ್ ಮಾಡುತ್ತದೆ. ಸಮಸ್ಯೆಗಳು ಮುಂದುವರಿದರೆ:

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರ → ಮರುಸಂಪರ್ಕಿಸಿ
2. ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವನ್ನು ಅಳಿಸಿ ಮತ್ತು ಮರುಸೇರಿಸಿ

### Kiro ಬಹು-ಖಾತೆ: ಎರಡನೇ ಖಾತೆಯು ಮೊದಲನೆಯದನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ

**ಕಾರಣ:** Kiro ನ ಬ್ಯಾಕೆಂಡ್ ಪ್ರತಿ OIDC ಕ್ಲೈಂಟ್ ನೋಂದಣಿಗೆ ಒಂದೇ ಸಕ್ರಿಯ ಸೆಷನ್ ಅನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ.
ಎರಡು ಖಾತೆಗಳು ಒಂದೇ ನೋಂದಾಯಿತ ಕ್ಲೈಂಟ್ ಅನ್ನು ಹಂಚಿಕೊಂಡಾಗ (v3.8.0 ಕ್ಕಿಂತ ಮೊದಲು ಆಮದು ಮಾಡಲಾದ ಸಂಪರ್ಕಗಳು),
ಒಂದು ಖಾತೆಯ ಟೋಕನ್ ಅನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವುದರಿಂದ ಇನ್ನೊಂದರ ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅಮಾನ್ಯವಾಗುತ್ತದೆ.

**ಪರಿಹಾರ (v3.8.0+):** ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಸಂಪರ್ಕಗಳನ್ನು ಮರು-ಆಮದು ಮಾಡಿ.
v3.8.0 ರಿಂದ ಪ್ರಾರಂಭಿಸಿ, **ಟೋಕನ್ ಆಮದು**, **Google/GitHub ಸಾಮಾಜಿಕ ಲಾಗಿನ್**,
ಅಥವಾ **ಸ್ವಯಂ-ಆಮದು** ಮೂಲಕ ರಚಿಸಲಾದ ಪ್ರತಿಯೊಂದು ಹೊಸ Kiro ಸಂಪರ್ಕವೂ ತನ್ನದೇ ಆದ
ಮೀಸಲಾದ OIDC ಕ್ಲೈಂಟ್ ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನೋಂದಾಯಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಸಂಪರ್ಕವು ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತದೆ ಮತ್ತು ಒಂದು
ಖಾತೆಯನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವುದರಿಂದ ಯಾವುದೇ ಇತರ ಖಾತೆಯ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

v3.8.0 ಕ್ಕಿಂತ _ಮೊದಲು_ ಆಮದು ಮಾಡಲಾದ ಸಂಪರ್ಕಗಳು ಪ್ರತಿ-ಸಂಪರ್ಕದ ಕ್ಲೈಂಟ್
ನೋಂದಣಿಯನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ. ಆ ಸಂಪರ್ಕಗಳು ಹಂಚಿಕೆಯ ಸಾಮಾಜಿಕ-ದೃಢೀಕರಣ ರಿಫ್ರೆಶ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಳಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ.

## ಕ್ಲೌಡ್ ಸಮಸ್ಯೆಗಳು

### ಕ್ಲೌಡ್ ಸಿಂಕ್ ದೋಷಗಳು

1. `BASE_URL` ನಿಮ್ಮ ಚಾಲನೆಯಲ್ಲಿರುವ ಇನ್ಸ್ಟಾನ್ಸ್ಗೆ ಸೂಚಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (ಉದಾ., `http://localhost:20128`)
2. `CLOUD_URL` ನಿಮ್ಮ ಕ್ಲೌಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಸೂಚಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (ಉದಾ., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ಮೌಲ್ಯಗಳನ್ನು ಸರ್ವರ್-ಸೈಡ್ ಮೌಲ್ಯಗಳೊಂದಿಗೆ ಹೊಂದಾಣಿಕೆಯಲ್ಲಿ ಇರಿಸಿ

### ಕ್ಲೌಡ್ನಲ್ಲಿ `stream=false` 500 ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ

**ಲಕ್ಷಣ:** ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದ ಕರೆಗಳಿಗೆ ಕ್ಲೌಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ನಲ್ಲಿ `Unexpected token 'd'...`.

**ಕಾರಣ:** ಕ್ಲೈಂಟ್ JSON ಅನ್ನು ನಿರೀಕ್ಷಿಸುತ್ತಿರುವಾಗ ಅಪ್ಸ್ಟ್ರೀಮ್ SSE ಪೇಲೋಡ್ ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.

**ತಾತ್ಕಾಲಿಕ ಪರಿಹಾರ:** ಕ್ಲೌಡ್ಗೆ ನೇರ ಕರೆಗಳಿಗಾಗಿ `stream=true` ಬಳಸಿ. ಸ್ಥಳೀಯ ರನ್ಟೈಮ್ SSE→JSON ಪರ್ಯಾಯ ವ್ಯವಸ್ಥೆಯನ್ನು ಒಳಗೊಂಡಿದೆ.

### ಕ್ಲೌಡ್ ಸಂಪರ್ಕಗೊಂಡಿದೆ ಎಂದು ಹೇಳುತ್ತದೆ, ಆದರೆ "ಅಮಾನ್ಯ API ಕೀ"

1. ಸ್ಥಳೀಯ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ಹೊಸ ಕೀಯನ್ನು ರಚಿಸಿ (`/api/keys`)
2. ಕ್ಲೌಡ್ ಸಿಂಕ್ ಅನ್ನು ರನ್ ಮಾಡಿ: ಕ್ಲೌಡ್ ಸಕ್ರಿಯಗೊಳಿಸಿ → ಈಗ ಸಿಂಕ್ ಮಾಡಿ
3. ಹಳೆಯ/ಸಿಂಕ್ ಮಾಡದ ಕೀಗಳು ಇನ್ನೂ ಕ್ಲೌಡ್ನಲ್ಲಿ `401` ಅನ್ನು ಹಿಂತಿರುಗಿಸಬಹುದು

## Docker ಸಮಸ್ಯೆಗಳು

### Docker IPv6 / ಸಂಪರ್ಕ ಮರುಹೊಂದಿಕೆ

<a name="docker-ipv6"></a>

**ಲಕ್ಷಣಗಳು:** `curl http://localhost:20128/v1/models` ಆಜ್ಞೆಯು `curl: (56) Recv failure: Connection reset by peer` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಮತ್ತು ದೃಢೀಕರಣವಿಲ್ಲದ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ, ಆದರೆ ದೃಢೀಕೃತ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು ವಿಫಲವಾಗುತ್ತವೆ — ಇದು ದೃಢೀಕರಣದ ಸಮಸ್ಯೆಯಂತೆ ಕಾಣುತ್ತದೆ, ಆದರೆ ಹಾಗಲ್ಲ.

**ಕಾರಣ:** `docker run -p 20128:20128` ಎರಡೂ `0.0.0.0` (IPv4) ಮತ್ತು `::` (IPv6) ಮೇಲೆ ಪ್ರಕಟಿಸುತ್ತದೆ, ಆದರೆ ಕಂಟೈನರ್ನೊಳಗಿನ ಪ್ರಕ್ರಿಯೆಯು IPv4 ಮೇಲೆ ಮಾತ್ರ ಆಲಿಸುತ್ತದೆ. `localhost` ಮೊದಲು `::1` ಗೆ ರೆಸಾಲ್ವ್ ಆಗುವ ಹೋಸ್ಟ್ಗಳಲ್ಲಿ, ಸಂಪರ್ಕವು ಅದರ ಹಿಂದೆ ಯಾವುದೇ ಲಿಸನರ್ ಇಲ್ಲದ IPv6 ಪ್ರಕಟಿತ ಪೋರ್ಟ್ಗೆ ತಲುಪುತ್ತದೆ → ಸಂಪರ್ಕ ಮರುಹೊಂದಿಕೆಯಾಗುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. **ತ್ವರಿತ ರೋಗನಿರ್ಣಯ:** `curl -4 http://localhost:20128/v1/models` ಅನ್ನು ರನ್ ಮಾಡಿ. ಇದು `-4` ಜೊತೆಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸಿ, ಅದಿಲ್ಲದೆ ವಿಫಲವಾದರೆ, ನೀವು IPv6 ಬೈಂಡ್ ಅಸಂಗತತೆಯನ್ನು ಹೊಂದಿದ್ದೀರಿ.
2. **ಶಾಶ್ವತ ಪರಿಹಾರ:** ನಿಮ್ಮ `docker run` ಆಜ್ಞೆಯಲ್ಲಿ `-p 127.0.0.1:20128:20128` ಬಳಸುವ ಮೂಲಕ IPv4 ಗೆ ಸ್ಪಷ್ಟವಾಗಿ ಬೈಂಡ್ ಮಾಡಿ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ಇದು IPv4 ಬೈಂಡ್ ಅನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಎಲ್ಲಾ ಹೋಸ್ಟ್ ಇಂಟರ್ಫೇಸ್ಗಳಲ್ಲಿ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದನ್ನೂ ತಪ್ಪಿಸುತ್ತದೆ.

### CLI ಉಪಕರಣವು ಸ್ಥಾಪಿತವಾಗಿಲ್ಲ ಎಂದು ತೋರಿಸುತ್ತದೆ

1. ರನ್ಟೈಮ್ ಫೀಲ್ಡ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. ಪೋರ್ಟಬಲ್ ಮೋಡ್ಗಾಗಿ: `runner-cli` ಇಮೇಜ್ ಟಾರ್ಗೆಟ್ ಬಳಸಿ (CLI ಗಳು ಬಂಡಲ್ ಆಗಿವೆ)
3. ಹೋಸ್ಟ್ ಮೌಂಟ್ ಮೋಡ್ಗಾಗಿ: `CLI_EXTRA_PATHS` ಅನ್ನು ಹೊಂದಿಸಿ ಮತ್ತು ಹೋಸ್ಟ್ bin ಡೈರೆಕ್ಟರಿಯನ್ನು ಓದಲು-ಮಾತ್ರವಾಗಿ ಮೌಂಟ್ ಮಾಡಿ
4. `installed=true` ಮತ್ತು `runnable=false` ಆಗಿದ್ದರೆ: ಬೈನರಿ ಕಂಡುಬಂದಿದೆ, ಆದರೆ ಹೆಲ್ತ್ಚೆಕ್ನಲ್ಲಿ ವಿಫಲವಾಗಿದೆ

### ಹೆಚ್ಚಿನ ವೆಚ್ಚಗಳು

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಬಳಕೆಯಲ್ಲಿ ಬಳಕೆಯ ಅಂಕಿಅಂಶಗಳನ್ನು ಪರಿಶೀಲಿಸಿ
2. ಪ್ರಾಥಮಿಕ ಮಾಡೆಲ್ ಅನ್ನು GLM/MiniMax ಗೆ ಬದಲಾಯಿಸಿ
3. ನಿರ್ಣಾಯಕವಲ್ಲದ ಕಾರ್ಯಗಳಿಗೆ ಉಚಿತ ಟಿಯರ್ (Qoder, Kiro) ಬಳಸಿ
4. ಪ್ರತಿ API ಕೀಗೆ ವೆಚ್ಚದ ಬಜೆಟ್ಗಳನ್ನು ಹೊಂದಿಸಿ: ಡ್ಯಾಶ್ಬೋರ್ಡ್ → API ಕೀಗಳು → ಬಜೆಟ್

## ಡೀಬಗಿಂಗ್

### ಲಾಗ್ ಫೈಲ್ಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ

ನಿಮ್ಮ `.env` ಫೈಲ್ನಲ್ಲಿ `APP_LOG_TO_FILE=true` ಅನ್ನು ಹೊಂದಿಸಿ. ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್ಗಳನ್ನು `logs/` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ.
ಸೆಟ್ಟಿಂಗ್ಗಳಲ್ಲಿ ಕಾಲ್ ಲಾಗ್ ಪೈಪ್ಲೈನ್ ಸಕ್ರಿಯಗೊಂಡಿರುವಾಗ ವಿನಂತಿಯ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳನ್ನು `${DATA_DIR}/call_logs/` ಅಡಿಯಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ.
ಪೈಪ್ಲೈನ್ ಕ್ಯಾಪ್ಚರ್ ಸಕ್ರಿಯಗೊಂಡಿರುವಾಗ, ಸ್ಟ್ರೀಮ್ ಚಂಕ್ ಪೇಲೋಡ್ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಲು `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ಅನ್ನು ಹೊಂದಿಸಿ ಅಥವಾ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ನ ಗರಿಷ್ಠ ಮಿತಿಯನ್ನು KB ಯಲ್ಲಿ ಬದಲಾಯಿಸಲು `CALL_LOG_PIPELINE_MAX_SIZE_KB` ಅನ್ನು ಹೊಂದಿಸಿ.

### ಪ್ರೊವೈಡರ್ನ ಸ್ಥಿತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ

```bash
# ಸ್ಥಿತಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್
http://localhost:20128/dashboard/health

# API ಸ್ಥಿತಿ ಪರಿಶೀಲನೆ
curl http://localhost:20128/api/monitoring/health
```

### ರನ್ಟೈಮ್ ಸಂಗ್ರಹಣೆ

- ಮುಖ್ಯ ಸ್ಥಿತಿ: `${DATA_DIR}/storage.sqlite` (ಪ್ರೊವೈಡರ್ಗಳು, ಕಾಂಬೊಗಳು, ಅಲಿಯಾಸ್ಗಳು, ಕೀಗಳು, ಸೆಟ್ಟಿಂಗ್ಗಳು)
- ಬಳಕೆ: `storage.sqlite` ನಲ್ಲಿನ SQLite ಟೇಬಲ್ಗಳು (`usage_history`, `call_logs`, `proxy_logs`) + ಐಚ್ಛಿಕ `${DATA_DIR}/call_logs/`
- ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್ಗಳು: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ಆಗಿರುವಾಗ)
- ಕಾಲ್ ಲಾಗ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು: ಕಾಲ್ ಲಾಗ್ ಪೈಪ್ಲೈನ್ ಸಕ್ರಿಯಗೊಂಡಿರುವಾಗ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

ವಿನಂತಿ ಲಾಗ್ಗಳ ಪುಟದ **ಇತಿಹಾಸವನ್ನು ತೆರವುಗೊಳಿಸಿ** ಕ್ರಿಯೆಯು `call_logs`, ಹಳೆಯ
`request_detail_logs` ಮತ್ತು ಸ್ಥಳೀಯ `${DATA_DIR}/call_logs/` ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಡೈರೆಕ್ಟರಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.

## ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಸಮಸ್ಯೆಗಳು

### ಪೂರೈಕೆದಾರರು OPEN ಸ್ಥಿತಿಯಲ್ಲೇ ಸಿಲುಕಿದ್ದಾರೆ

ಪೂರೈಕೆದಾರರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ OPEN ಆಗಿರುವಾಗ, ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ವಿನಂತಿಗಳನ್ನು ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ**ಕ್ಕೆ ಹೋಗಿ
2. ಸಮಸ್ಯೆಗೆ ಒಳಗಾದ ಪೂರೈಕೆದಾರರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಕಾರ್ಡ್ ಪರಿಶೀಲಿಸಿ
3. ಎಲ್ಲಾ ಬ್ರೇಕರ್ಗಳನ್ನು ತೆರವುಗೊಳಿಸಲು **ಎಲ್ಲವನ್ನೂ ಮರುಹೊಂದಿಸಿ** ಕ್ಲಿಕ್ ಮಾಡಿ ಅಥವಾ ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ಕಾಯಿರಿ
4. ಮರುಹೊಂದಿಸುವ ಮೊದಲು ಪೂರೈಕೆದಾರರು ನಿಜವಾಗಿಯೂ ಲಭ್ಯವಿದ್ದಾರೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ

### ಪೂರೈಕೆದಾರರು ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಅನ್ನು ಪದೇಪದೇ ಟ್ರಿಗರ್ ಮಾಡುತ್ತಿದ್ದಾರೆ

ಪೂರೈಕೆದಾರರು ಪದೇಪದೇ OPEN ಸ್ಥಿತಿಯನ್ನು ಪ್ರವೇಶಿಸಿದರೆ:

1. ವೈಫಲ್ಯದ ಮಾದರಿಗಾಗಿ **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಆರೋಗ್ಯ → ಪೂರೈಕೆದಾರರ ಆರೋಗ್ಯ** ಪರಿಶೀಲಿಸಿ
2. **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು**ಗೆ ಹೋಗಿ ವೈಫಲ್ಯದ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ
3. ಪೂರೈಕೆದಾರರು API ಮಿತಿಗಳನ್ನು ಬದಲಾಯಿಸಿದ್ದಾರೆಯೇ ಅಥವಾ ಮರು-ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ
4. ಲೇಟೆನ್ಸಿ ಟೆಲಿಮೆಟ್ರಿಯನ್ನು ಪರಿಶೀಲಿಸಿ — ಹೆಚ್ಚಿನ ಲೇಟೆನ್ಸಿಯು ಕಾಲಾವಧಿ ಮೀರುವಿಕೆ ಆಧಾರಿತ ವೈಫಲ್ಯಗಳಿಗೆ ಕಾರಣವಾಗಬಹುದು

## ಆಡಿಯೊ ಪ್ರತಿಲೇಖನ ಸಮಸ್ಯೆಗಳು

### "ಬೆಂಬಲಿಸದ ಮಾದರಿ" ದೋಷ

- ಮೊದಲ ವಿಭಾಗವು ನೀವು ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವ ಪೂರೈಕೆದಾರರಾಗಿರುವ ಮಾದರಿ id ಅನ್ನು ಬಳಸಿ (`openai/whisper-1`, `openrouter/deepgram/nova-3`). ಕೇವಲ `deepgram/nova-3` ಅನ್ನು ಬಳಸಲು ಸ್ಥಳೀಯ Deepgram ಕೀ ಅಗತ್ಯವಿದೆ.
- ಪೂರೈಕೆದಾರರು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು**ನಲ್ಲಿ ಸಂಪರ್ಕಗೊಂಡಿರುವುದನ್ನು ಪರಿಶೀಲಿಸಿ

### ಪ್ರತಿಲೇಖನವು ಖಾಲಿಯಾಗಿ ಮರಳುತ್ತದೆ ಅಥವಾ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

- ಬೆಂಬಲಿತ ಆಡಿಯೊ ಸ್ವರೂಪಗಳನ್ನು ಪರಿಶೀಲಿಸಿ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ಫೈಲ್ ಗಾತ್ರವು ಪೂರೈಕೆದಾರರ ಮಿತಿಯೊಳಗಿದೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ (ಸಾಮಾನ್ಯವಾಗಿ < 25MB)
- ಪೂರೈಕೆದಾರರ ಕಾರ್ಡ್ನಲ್ಲಿ ಪೂರೈಕೆದಾರರ API ಕೀ ಮಾನ್ಯತೆಯನ್ನು ಪರಿಶೀಲಿಸಿ

## ಅನುವಾದಕ ದೋಷನಿವಾರಣೆ

ಸ್ವರೂಪ ಅನುವಾದದ ಸಮಸ್ಯೆಗಳನ್ನು ದೋಷನಿವಾರಣೆ ಮಾಡಲು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಅನುವಾದಕ** ಬಳಸಿ:

| ಮೋಡ್             | ಯಾವಾಗ ಬಳಸಬೇಕು                                                                                                           |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **ಪ್ಲೇಗ್ರೌಂಡ್**  | ಇನ್ಪುಟ್/ಔಟ್ಪುಟ್ ಸ್ವರೂಪಗಳನ್ನು ಅಕ್ಕಪಕ್ಕದಲ್ಲಿ ಹೋಲಿಸಿ — ಅನುವಾದವು ಹೇಗೆ ನಡೆಯುತ್ತದೆ ಎಂಬುದನ್ನು ನೋಡಲು ವಿಫಲವಾದ ವಿನಂತಿಯನ್ನು ಅಂಟಿಸಿ |
| **ಚಾಟ್ ಟೆಸ್ಟರ್** | ಲೈವ್ ಸಂದೇಶಗಳನ್ನು ಕಳುಹಿಸಿ ಮತ್ತು ಹೆಡರ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಸಂಪೂರ್ಣ ವಿನಂತಿ/ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ                  |
| **ಟೆಸ್ಟ್ ಬೆಂಚ್** | ಯಾವ ಅನುವಾದಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿಲ್ಲ ಎಂಬುದನ್ನು ಕಂಡುಹಿಡಿಯಲು ಸ್ವರೂಪ ಸಂಯೋಜನೆಗಳಾದ್ಯಂತ ಬ್ಯಾಚ್ ಪರೀಕ್ಷೆಗಳನ್ನು ಚಲಾಯಿಸಿ           |
| **ಲೈವ್ ಮಾನಿಟರ್** | ಆಗಾಗ್ಗೆ ಸಂಭವಿಸುವ ಅನುವಾದ ಸಮಸ್ಯೆಗಳನ್ನು ಪತ್ತೆಹಚ್ಚಲು ನೈಜ-ಸಮಯದ ವಿನಂತಿ ಹರಿವನ್ನು ವೀಕ್ಷಿಸಿ                                      |

### ಸಾಮಾನ್ಯ ಸ್ವರೂಪ ಸಮಸ್ಯೆಗಳು

- **ಥಿಂಕಿಂಗ್ ಟ್ಯಾಗ್ಗಳು ಕಾಣಿಸುತ್ತಿಲ್ಲ** — ಗುರಿ ಪೂರೈಕೆದಾರರು ಥಿಂಕಿಂಗ್ ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತಾರೆಯೇ ಮತ್ತು ಥಿಂಕಿಂಗ್ ಬಜೆಟ್ ಸೆಟ್ಟಿಂಗ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ
- **ಟೂಲ್ ಕಾಲ್ಗಳು ಕಳೆದುಹೋಗುತ್ತಿವೆ** — ಕೆಲವು ಸ್ವರೂಪ ಅನುವಾದಗಳು ಬೆಂಬಲಿಸದ ಕ್ಷೇತ್ರಗಳನ್ನು ತೆಗೆದುಹಾಕಬಹುದು; ಪ್ಲೇಗ್ರೌಂಡ್ ಮೋಡ್ನಲ್ಲಿ ಪರಿಶೀಲಿಸಿ
- **ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ ಕಾಣೆಯಾಗಿದೆ** — Claude ಮತ್ತು Gemini ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ವಿಭಿನ್ನವಾಗಿ ನಿರ್ವಹಿಸುತ್ತವೆ; ಅನುವಾದದ ಔಟ್ಪುಟ್ ಪರಿಶೀಲಿಸಿ
- **SDK ಆಬ್ಜೆಕ್ಟ್ ಬದಲಿಗೆ ಕಚ್ಚಾ ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು ಮರಳಿಸುತ್ತದೆ** — v1.xನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; OpenAI SDK Pydantic ಮೌಲ್ಯೀಕರಣ ವೈಫಲ್ಯಗಳಿಗೆ ಕಾರಣವಾಗುವ ಪ್ರಮಾಣಿತವಲ್ಲದ ಕ್ಷೇತ್ರಗಳನ್ನು (`x_groq`, `usage_breakdown`, ಇತ್ಯಾದಿ) ಪ್ರತಿಕ್ರಿಯೆ ಸ್ಯಾನಿಟೈಸರ್ ತೆಗೆದುಹಾಕುತ್ತದೆ. v3.x+ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ಸಲ್ಲಿಸಿ.
- **GLM/ERNIE `system` ಪಾತ್ರವನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ** — v1.xನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; ಹೊಂದಿಕೆಯಾಗದ ಮಾದರಿಗಳಿಗಾಗಿ ರೋಲ್ ನಾರ್ಮಲೈಸರ್ ಸಿಸ್ಟಮ್ ಸಂದೇಶಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಬಳಕೆದಾರರ ಸಂದೇಶಗಳೊಂದಿಗೆ ವಿಲೀನಗೊಳಿಸುತ್ತದೆ. v3.x+ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ಸಲ್ಲಿಸಿ.
- **`developer` ಪಾತ್ರವನ್ನು ಗುರುತಿಸಲಾಗುತ್ತಿಲ್ಲ** — v1.xನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; OpenAI ಅಲ್ಲದ ಪೂರೈಕೆದಾರರಿಗೆ ಸ್ವಯಂಚಾಲಿತವಾಗಿ `system`ಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ. v3.x+ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ಸಲ್ಲಿಸಿ.
- **Gemini ಜೊತೆಗೆ `json_schema` ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿಲ್ಲ** — v1.xನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; `response_format` ಅನ್ನು ಈಗ Geminiಯ `responseMimeType` + `responseSchema`ಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ. v3.x+ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯನ್ನು ಸಲ್ಲಿಸಿ.

## ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವದ ಸೆಟ್ಟಿಂಗ್ಗಳು

### ಸ್ವಯಂ ದರ-ಮಿತಿ ಪ್ರಚೋದನೆಯಾಗುತ್ತಿಲ್ಲ

- ಸ್ವಯಂ ದರ-ಮಿತಿಯು API ಕೀ ಪೂರೈಕೆದಾರರಿಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ (OAuth/ಚಂದಾದಾರಿಕೆಗೆ ಅಲ್ಲ)
- **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು** ನಲ್ಲಿ ಸ್ವಯಂ ದರ-ಮಿತಿಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ
- ಪೂರೈಕೆದಾರರು `429` ಸ್ಥಿತಿ ಕೋಡ್ಗಳು ಅಥವಾ `Retry-After` ಹೆಡರ್ಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತಾರೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ

### ಘಾತೀಯ ಬ್ಯಾಕ್ಆಫ್ ಹೊಂದಿಸುವಿಕೆ

ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು ಈ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತವೆ:

- **ಮೂಲ ವಿಳಂಬ** — ಮೊದಲ ವೈಫಲ್ಯದ ನಂತರದ ಆರಂಭಿಕ ಕಾಯುವ ಸಮಯ (ಡೀಫಾಲ್ಟ್: 1s)
- **ಗರಿಷ್ಠ ವಿಳಂಬ** — ಕಾಯುವ ಸಮಯದ ಗರಿಷ್ಠ ಮಿತಿ (ಡೀಫಾಲ್ಟ್: 30s)
- **ಗುಣಕ** — ಪ್ರತಿ ಅನುಕ್ರಮ ವೈಫಲ್ಯಕ್ಕೆ ವಿಳಂಬವನ್ನು ಎಷ್ಟು ಹೆಚ್ಚಿಸಬೇಕು (ಡೀಫಾಲ್ಟ್: 2x)

### ಥಂಡರಿಂಗ್ ಹರ್ಡ್ ತಡೆಗಟ್ಟುವಿಕೆ

ಅನೇಕ ಸಮಕಾಲೀನ ವಿನಂತಿಗಳು ದರ-ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರೈಕೆದಾರರನ್ನು ತಲುಪಿದಾಗ, ವಿನಂತಿಗಳನ್ನು ಅನುಕ್ರಮಗೊಳಿಸಲು ಮತ್ತು ಸರಣಿ ವೈಫಲ್ಯಗಳನ್ನು ತಡೆಯಲು OmniRoute ಮ್ಯೂಟೆಕ್ಸ್ + ಸ್ವಯಂ ದರ-ಮಿತಿಯನ್ನು ಬಳಸುತ್ತದೆ. API ಕೀ ಪೂರೈಕೆದಾರರಿಗೆ ಇದು ಸ್ವಯಂಚಾಲಿತವಾಗಿರುತ್ತದೆ.

### ಚಾಟ್ ವಿನಂತಿಗಳು 503 / chat_admission_busy ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ

**ಲಕ್ಷಣಗಳು:**

- ಚಾಟ್ ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳ ಎಂಡ್ಪಾಯಿಂಟ್ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ; ಅದರ ದೋಷ ಕೋಡ್
  `chat_admission_busy` ಆಗಿರುತ್ತದೆ.
- ಪ್ರತಿಕ್ರಿಯೆಯು `Retry-After` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ. #12135 ರಿಂದ, ಅದರ ಮೌಲ್ಯವನ್ನು ಗಮನಿಸಲಾದ
  ಆಕ್ಯುಪೆನ್ಸಿಯಿಂದ ಪಡೆಯಲಾಗುತ್ತದೆ — ವಿನಂತಿಯು ಈಗಾಗಲೇ ಕಾಯ್ದಿರುವ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  ವಿಂಡೋ ಮತ್ತು ಪ್ರಸ್ತುತ ಹೆವಿವೇಟ್ ಲೀಸ್ಗಳನ್ನು ಹಿಡಿದಿಟ್ಟಿರುವ ಸಮಯದಲ್ಲಿ ದೊಡ್ಡದಾದುದನ್ನು ತೆಗೆದುಕೊಂಡು — ಪೂರ್ಣ
  ಸೆಕೆಂಡ್ಗಳಿಗೆ ಮೇಲ್ಮುಖವಾಗಿ ಪೂರ್ಣಾಂಕಗೊಳಿಸಿ, 60ಕ್ಕೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ. ನಿಷ್ಕ್ರಿಯ ಗೇಟ್ನಲ್ಲಿ ಇದು ಐತಿಹಾಸಿಕ
  ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ: ಬೈಟ್-ಆಧಾರಿತ ಪಥದಲ್ಲಿ 2 ಸೆಕೆಂಡ್ಗಳು, ರಚನೆ-ಆಧಾರಿತ ಪಥದಲ್ಲಿ 1 ಸೆಕೆಂಡ್
  (ಇದು `reason: "structure_limit"` ಅನ್ನೂ ಒಳಗೊಂಡಿರುತ್ತದೆ).
- ಮತ್ತೊಂದು ಹೆವಿವೇಟ್ ಚಾಟ್ ಅಥವಾ ದೀರ್ಘಕಾಲ ಚಾಲನೆಯಲ್ಲಿರುವ ಸ್ಟ್ರೀಮಿಂಗ್ ಪ್ರತಿಕ್ರಿಯೆ ಇನ್ನೂ
  ಪ್ರಗತಿಯಲ್ಲಿರುವಾಗ ಇದು ಸಂಭವಿಸಬಹುದು.

ಬೈಟ್-ಆಧಾರಿತ ಪ್ರತಿಕ್ರಿಯೆಯ ಬಾಡಿ ಹೀಗಿದೆ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ರಚನೆ-ಆಧಾರಿತ ಪ್ರತಿಕ್ರಿಯೆಯು ಅದೇ ಪ್ರಕಾರ ಮತ್ತು ಕೋಡ್ ಅನ್ನು ಬಳಸುತ್ತದೆ; ಅದರ ಸಂದೇಶ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ಮತ್ತು `reason: "structure_limit"` ಆಗಿರುತ್ತದೆ.
ಡೀಫಾಲ್ಟ್ ಮಿತಿಗಳಲ್ಲಿ, ವಿನಂತಿಯು ಕನಿಷ್ಠ `200` ಸಂದೇಶಗಳು, ಕನಿಷ್ಠ `64` ಪರಿಕರಗಳು, ಅಥವಾ ಕನಿಷ್ಠ
`32,000` ಅಂದಾಜು ಟೋಕನ್ಗಳನ್ನು ಹೊಂದಿದ್ದರೆ, ಅಥವಾ ಮಿತಿಗೊಳಿಸಲಾದ ರಚನಾ ಅಂದಾಜು `10,000` ಭೇಟಿ ನೀಡಿದ
ನೋಡ್ಗಳ ಅಥವಾ `12` ಆಳದ ತನ್ನ ಮಿತಿಗಳನ್ನು ಮುಗಿಸಿದರೆ, ಅದು ರಚನಾತ್ಮಕವಾಗಿ ಭಾರವಾದದ್ದಾಗಿರುತ್ತದೆ.

**ಕಾರಣ:** ಇದು OmniRoute ಒಳಗಿನ ಉದ್ದೇಶಪೂರ್ವಕ ಲೋಡ್ ಶೆಡ್ಡಿಂಗ್ ಆಗಿದ್ದು, ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ವೈಫಲ್ಯವಲ್ಲ.
ಪ್ರತಿ ಪ್ರಕ್ರಿಯೆಯು ದೊಡ್ಡ ವಿನಂತಿಯ ಬಾಡಿಯನ್ನು ಉಳಿಸಿಕೊಂಡು ಪಾರ್ಸ್ ಮಾಡುವ ಮೊದಲು ಸೀಮಿತ ಹೆವಿವೇಟ್ ಸಾಮರ್ಥ್ಯವನ್ನು
ಕಾಯ್ದಿರಿಸಲು ಪ್ರಕ್ರಿಯೆ-ಸ್ಥಳೀಯ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. SSE ಪ್ರತಿಕ್ರಿಯೆಯ ಸಂಪೂರ್ಣ ಜೀವಿತಾವಧಿಯವರೆಗೆ
ಹೆವಿವೇಟ್ ಲೀಸ್ ಹಿಡಿದಿಡಲಾಗುತ್ತದೆ.

**#503-ಫ್ಯಾನ್ಔಟ್:** ಈ ಪರಿಹಾರಕ್ಕೂ ಮೊದಲು, ಹೋಸ್ಟ್ ಮೆಮೊರಿಯನ್ನು ಲೆಕ್ಕಿಸದೆ ಗಾರ್ಡ್ ಸಮಕಾಲಿಕತೆಯನ್ನು
ನಿಶ್ಚಿತ ವಿನಂತಿ COUNTಗೆ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ಡೀಫಾಲ್ಟ್ `1`) ಮಿತಿಗೊಳಿಸುತ್ತಿತ್ತು;
ಆದ್ದರಿಂದ ಕೋಡಿಂಗ್-ಏಜೆಂಟ್ ಫ್ಯಾನ್ಔಟ್ (ಬಹು ಉಪಏಜೆಂಟ್ಗಳು/CLIಗಳು, ಸಾಮಾನ್ಯವಾಗಿ > 256 KB ಬಾಡಿಗಳು)
ಪರಿಣಾಮಕಾರಿ ಸಮಕಾಲಿಕತೆಯನ್ನು ~1ಕ್ಕೆ ಕುಗ್ಗಿಸಿತು ಮತ್ತು ಸಂಪೂರ್ಣವಾಗಿ ಸಾಮಾನ್ಯವಾದ ಲೋಡ್ನಲ್ಲೂ 503 ದೋಷಗಳನ್ನು
ಉಂಟುಮಾಡಿತು. ಈಗ ಗಾರ್ಡ್ ಸ್ವಯಂ-ಹೊಂದಾಣಿಕೆಯಾಗುತ್ತದೆ: ಪ್ರಕ್ರಿಯೆಯ ನೈಜ ಮೆಮೊರಿ ಮಿತಿಯಿಂದ ಗಾತ್ರ ನಿರ್ಧರಿಸಲಾದ,
ಸ್ವಯಂ-ಪಡೆದ ಇನ್ಜೆಸ್ಟ್ BYTE ಬಜೆಟ್ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ಅದನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ;
ಜೊತೆಗೆ ಅದು ನೇರ ಸಂಪನ್ಮೂಲ-ಒತ್ತಡದ ಸಂಕೇತವನ್ನೂ ಪರಿಶೀಲಿಸುತ್ತದೆ — ಹೀಗಾಗಿ ಒಂದಕ್ಕಿಂತ ಹೆಚ್ಚು ಭಾರವಾದ ವಿನಂತಿಗಳು
ಒಂದೇ ಸಮಯದಲ್ಲಿ ಬಂದವು ಎಂಬ ಕಾರಣಕ್ಕೆ ಮಾತ್ರವಲ್ಲದೆ, ಹೋಸ್ಟ್ ನಿಜವಾಗಿಯೂ ಮೆಮೊರಿ ಒತ್ತಡದಲ್ಲಿರುವಾಗ ಮಾತ್ರ ಅದು
ಲೋಡ್ ಅನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ. ಹಳೆಯ ಎಣಿಕೆ ಮಿತಿ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ಇನ್ನೂ
ಗೌರವಿಸಲ್ಪಡುತ್ತದೆ, ಆದರೆ ನೀವು ಅದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸಿದರೆ ಮಾತ್ರ.

ಸಾಮರ್ಥ್ಯವು ಕಾರ್ಯನಿರತವಾಗಿರುವಾಗ, ಹೆವಿವೇಟ್ ವಿನಂತಿಯು ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಅನ್ನು ಉತ್ತರಿಸುವ ಮೊದಲು,
ಒಂದು ಸ್ಲಾಟ್ ಖಾಲಿಯಾಗುವುದಕ್ಕಾಗಿ ಮೊದಲಿಗೆ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ವರೆಗೆ (ಡೀಫಾಲ್ಟ್
`2000`, `0` ಕಾಯುವಿಕೆಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ) ಕಾಯುತ್ತದೆ. ಭಾರವಾದ ಉಪ-ವಿನಂತಿಗಳನ್ನು ಸಮಕಾಲೀನವಾಗಿ
ಫ್ಯಾನ್ಔಟ್ ಮಾಡುವ ಏಜೆಂಟ್-ಶೈಲಿಯ ಕ್ಲೈಂಟ್ಗಳು (OpenCode, Claude Code, Cursor), ತಕ್ಷಣದ ನಿರಾಕರಣೆಗಳಲ್ಲಿ
ತಮ್ಮ ಸಂಪೂರ್ಣ ಮರುಪ್ರಯತ್ನ ಬಜೆಟ್ ಅನ್ನು ವ್ಯರ್ಥಮಾಡಿ ಕಾರ್ಯದ ಮಧ್ಯದಲ್ಲೇ ವಿಫಲಗೊಳ್ಳುವ ಬದಲು, ಆ ದಟ್ಟಣೆಯನ್ನು
ಅನುಕ್ರಮಗೊಳಿಸಲು ಈ ಮಿತಿಗೊಳಿಸಲಾದ ಕಾಯುವಿಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ.
ಪ್ರಸ್ತುತ ಹೆವಿವೇಟ್ ಲೀಸ್ ಆಕ್ಯುಪೆನ್ಸಿ, ನಿರ್ಧರಿಸಲಾದ ಬೈಟ್ ಬಜೆಟ್ ಮತ್ತು ನೇರ ಒತ್ತಡದ ತೀವ್ರತೆಯನ್ನು
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ನಲ್ಲಿ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ — ಯಾವುದೇ env var
ಅನ್ನು ಬದಲಿಸುವ ಮೊದಲು ಇವುಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ವಿನಂತಿ ಸರತಿ → ಸಮಕಾಲೀನ ವಿನಂತಿಗಳು ಇದನ್ನು ನಿಯಂತ್ರಿಸುವುದಿಲ್ಲ; ಆ
ಸೆಟ್ಟಿಂಗ್ ಪ್ರತ್ಯೇಕ ಪೂರೈಕೆದಾರ ವಿನಂತಿ-ಸರತಿ ಕಾರ್ಯವಿಧಾನವನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. ಮೊದಲು ಮರುಪ್ರಯತ್ನಿಸಿ. ಕ್ಲೈಂಟ್ಗಳು ವಿನಂತಿಯನ್ನು ತಕ್ಷಣವೇ ಪುನರಾವರ್ತಿಸುವ ಬದಲು `Retry-After` ಅನ್ನು
   ಪಾಲಿಸಬೇಕು ಮತ್ತು ಬ್ಯಾಕ್ಆಫ್ ಅನ್ನು ಬಳಸಬೇಕು.
2. ಏನನ್ನಾದರೂ ಹೊಂದಿಸುವ ಮೊದಲು `/api/monitoring/health` → `chatAdmission` ಅನ್ನು ಪರಿಶೀಲಿಸಿ. `countCapEnabled:
false` ಮತ್ತು ಉದಾರವಾದ `maxInflightBytes` ಎಂದರೆ ಸ್ವಯಂ-ಪಡೆದ ಬಜೆಟ್ ಈಗಾಗಲೇ ತನ್ನ
   ಕೆಲಸವನ್ನು ಮಾಡುತ್ತಿದೆ; `high`/`critical` `pressureSeverity` ಎಂದರೆ ಹೋಸ್ಟ್ನಲ್ಲಿ ನಿಜವಾಗಿಯೂ ಮೆಮೊರಿ
   ಕೊರತೆಯಿದೆ — ಇದನ್ನು ಅಡ್ಮಿಷನ್ env var ಮೂಲಕ ಸರಿಪಡಿಸಲಾಗುವುದಿಲ್ಲ; ಇದಕ್ಕೆ ಹೆಚ್ಚಿನ RAM ಅಥವಾ ಸಣ್ಣ
   ಕಾರ್ಯಭಾರ ಬೇಕಾಗುತ್ತದೆ.
3. `/api/monitoring/health` ನಿಮ್ಮ ಹೋಸ್ಟ್ಗೆ ಸ್ವಯಂ-ಪಡೆದ ಬಜೆಟ್ ನಿಜವಾಗಿಯೂ ತುಂಬಾ ಚಿಕ್ಕದಾಗಿದೆ ಎಂದು
   ತೋರಿಸಿದರೆ ಮಾತ್ರ (ಅಪರೂಪ — ಇದು ಈಗಾಗಲೇ ಕಂಟೇನರ್ನಿಂದ ಬೇರ್-ಮೆಟಲ್ವರೆಗೆ ಸ್ಕೇಲ್ ಆಗುತ್ತದೆ), ಹಳೆಯ
   ವಿನಂತಿ-ಎಣಿಕೆ ಮಿತಿಗೆ ಹಿಂತಿರುಗುವ ಬದಲು `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ಮೂಲಕ ಅದನ್ನು ನೇರವಾಗಿ
   ಓವರ್ರೈಡ್ ಮಾಡಿ.

ಅಧಿಕೃತ ಅಡ್ಮಿಷನ್ ಸೆಟ್ಟಿಂಗ್ಗಳಿಗಾಗಿ [ಪರಿಸರ-ಚರ ಉಲ್ಲೇಖ](../reference/ENVIRONMENT.md#4-security--authentication)
ವನ್ನು ನೋಡಿ.

## ಐಚ್ಛಿಕ RAG / LLM ವೈಫಲ್ಯ ವರ್ಗೀಕರಣ (16 ಸಮಸ್ಯೆಗಳು)

ಕೆಲವು OmniRoute ಬಳಕೆದಾರರು ಗೇಟ್ವೇಯನ್ನು RAG ಅಥವಾ ಏಜೆಂಟ್ ಸ್ಟ್ಯಾಕ್ಗಳ ಮುಂಭಾಗದಲ್ಲಿ ಇರಿಸುತ್ತಾರೆ. ಅಂತಹ ಸಂರಚನೆಗಳಲ್ಲಿ ಒಂದು ವಿಚಿತ್ರ ಮಾದರಿ ಸಾಮಾನ್ಯವಾಗಿ ಕಾಣಿಸುತ್ತದೆ: OmniRoute ಆರೋಗ್ಯಕರವಾಗಿ ಕಾಣುತ್ತದೆ (ಪೂರೈಕೆದಾರರು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದ್ದಾರೆ, ರೂಟಿಂಗ್ ಪ್ರೊಫೈಲ್ಗಳು ಸರಿಯಾಗಿವೆ, ದರ ಮಿತಿ ಎಚ್ಚರಿಕೆಗಳಿಲ್ಲ), ಆದರೆ ಅಂತಿಮ ಉತ್ತರವು ಇನ್ನೂ ತಪ್ಪಾಗಿರುತ್ತದೆ.

ಪ್ರಾಯೋಗಿಕವಾಗಿ, ಈ ಘಟನೆಗಳು ಸಾಮಾನ್ಯವಾಗಿ ಗೇಟ್ವೇಯಿಂದಲೇ ಅಲ್ಲದೆ, ನಂತರದ ಹಂತದ RAG ಪೈಪ್ಲೈನ್ನಿಂದ ಉಂಟಾಗುತ್ತವೆ.

ಆ ವೈಫಲ್ಯಗಳನ್ನು ವಿವರಿಸಲು ನಿಮಗೆ ಸಾಮಾನ್ಯ ಪದಸಂಪತ್ತು ಬೇಕಿದ್ದರೆ, WFGY ProblemMap ಅನ್ನು ಬಳಸಬಹುದು. ಇದು ಪುನರಾವರ್ತಿತವಾಗುವ ಹದಿನಾರು RAG / LLM ವೈಫಲ್ಯ ಮಾದರಿಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುವ, MIT ಪರವಾನಗಿಯ ಅಡಿಯಲ್ಲಿ ಲಭ್ಯವಿರುವ ಬಾಹ್ಯ ಪಠ್ಯ ಸಂಪನ್ಮೂಲವಾಗಿದೆ. ಉನ್ನತ ಮಟ್ಟದಲ್ಲಿ ಇದು ಈ ವಿಷಯಗಳನ್ನು ಒಳಗೊಂಡಿದೆ:

- ಮರುಪಡೆಯುವಿಕೆಯ ವಿಚಲನ ಮತ್ತು ಮುರಿದ ಸಂದರ್ಭ ಗಡಿಗಳು
- ಖಾಲಿ ಅಥವಾ ಹಳೆಯ ಸೂಚ್ಯಂಕಗಳು ಮತ್ತು ವೆಕ್ಟರ್ ಸ್ಟೋರ್ಗಳು
- ಎಂಬೆಡ್ಡಿಂಗ್ ಮತ್ತು ಅರ್ಥಸಂಬಂಧದ ನಡುವಿನ ಅಸಾಮರಸ್ಯ
- ಪ್ರಾಂಪ್ಟ್ ಸಂಯೋಜನೆ ಮತ್ತು ಸಂದರ್ಭ ವಿಂಡೋ ಸಮಸ್ಯೆಗಳು
- ತಾರ್ಕಿಕ ಕುಸಿತ ಮತ್ತು ಅತಿಯಾದ ಆತ್ಮವಿಶ್ವಾಸದ ಉತ್ತರಗಳು
- ದೀರ್ಘ ಸರಪಳಿ ಮತ್ತು ಏಜೆಂಟ್ ಸಮನ್ವಯ ವೈಫಲ್ಯಗಳು
- ಬಹು-ಏಜೆಂಟ್ ಮೆಮೊರಿ ಮತ್ತು ಪಾತ್ರ ವಿಚಲನ
- ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ ಮತ್ತು ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಕ್ರಮದ ಸಮಸ್ಯೆಗಳು

ಕಲ್ಪನೆ ಸರಳವಾಗಿದೆ:

1. ತಪ್ಪಾದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ತನಿಖೆ ಮಾಡುವಾಗ, ಇವುಗಳನ್ನು ದಾಖಲಿಸಿ:
   - ಬಳಕೆದಾರರ ಕಾರ್ಯ ಮತ್ತು ವಿನಂತಿ
   - OmniRoute ನಲ್ಲಿನ ರೂಟ್ ಅಥವಾ ಪೂರೈಕೆದಾರರ ಸಂಯೋಜನೆ
   - ನಂತರದ ಹಂತದಲ್ಲಿ ಬಳಸಲಾದ ಯಾವುದೇ RAG ಸಂದರ್ಭ (ಮರುಪಡೆಯಲಾದ ದಾಖಲೆಗಳು, ಟೂಲ್ ಕಾಲ್ಗಳು ಇತ್ಯಾದಿ)
2. ಘಟನೆಯನ್ನು ಒಂದು ಅಥವಾ ಎರಡು WFGY ProblemMap ಸಂಖ್ಯೆಗಳೊಂದಿಗೆ (`No.1` … `No.16`) ನಕ್ಷೆಗೊಳಿಸಿ.
3. OmniRoute ಲಾಗ್ಗಳ ಪಕ್ಕದಲ್ಲಿ, ನಿಮ್ಮದೇ ಡ್ಯಾಶ್ಬೋರ್ಡ್, ರನ್ಬುಕ್ ಅಥವಾ ಘಟನೆ ಟ್ರ್ಯಾಕರ್ನಲ್ಲಿ ಆ ಸಂಖ್ಯೆಯನ್ನು ಸಂಗ್ರಹಿಸಿ.
4. ನಿಮ್ಮ RAG ಸ್ಟ್ಯಾಕ್, ರಿಟ್ರೀವರ್ ಅಥವಾ ರೂಟಿಂಗ್ ತಂತ್ರವನ್ನು ಬದಲಾಯಿಸಬೇಕೇ ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸಲು ಸಂಬಂಧಿತ WFGY ಪುಟವನ್ನು ಬಳಸಿ.

ಸಂಪೂರ್ಣ ಪಠ್ಯ ಮತ್ತು ನಿರ್ದಿಷ್ಟ ಪರಿಹಾರ ವಿಧಾನಗಳು ಇಲ್ಲಿ ಲಭ್ಯವಿವೆ (MIT ಪರವಾನಗಿ, ಪಠ್ಯ ಮಾತ್ರ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute ಹಿಂದೆ ನೀವು RAG ಅಥವಾ ಏಜೆಂಟ್ ಪೈಪ್ಲೈನ್ಗಳನ್ನು ಚಲಾಯಿಸದಿದ್ದರೆ, ಈ ವಿಭಾಗವನ್ನು ನಿರ್ಲಕ್ಷಿಸಬಹುದು.

### Devin CLI ದೃಢೀಕರಣ ವೈಫಲ್ಯಗಳು

- CLI ರನ್ಟೈಮ್ ಪರಿಶೀಲನೆಯು `installed=false` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ

**ಕಾರಣಗಳು:**

- `CLI_DEVIN_BIN` ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದ ಪಥವನ್ನು ಸೂಚಿಸುತ್ತದೆ
- ಹೋಸ್ಟ್ನಲ್ಲಿ Devin CLI ಸ್ಥಾಪಿಸಲಾಗಿಲ್ಲ

**ಪರಿಹಾರ:**

1. ನಿಮ್ಮ ಪ್ಲಾಟ್ಫಾರ್ಮ್ಗಾಗಿ Devin CLI ಅನ್ನು ಸ್ಥಾಪಿಸಿ
2. `.env` ನಲ್ಲಿ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ಅಥವಾ ನೈಜ ಪಥ) ಹೊಂದಿಸಿ
3. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ ಮತ್ತು **Dashboard → CLI Tools** ನಿಂದ ಮರುಪರೀಕ್ಷಿಸಿ

### ಮಾಡೆಲ್ ಕೂಲ್ಡೌನ್ ಸ್ಥಗಿತಗೊಂಡಿದೆ (ಹಸ್ತಚಾಲಿತ ಮರುಹೊಂದಿಕೆ)

**ಲಕ್ಷಣಗಳು:**

- ಅವಧಿ ಮುಗಿಯುವ ಸಮಯ ಕಳೆದ ನಂತರವೂ ಮಾಡೆಲ್ ಒಂದು ಕೂಲ್ಡೌನ್ನಲ್ಲಿರುವಂತೆ ಪಟ್ಟಿಯಲ್ಲಿ ಉಳಿಯುತ್ತದೆ
- ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಹಿಂದಿನ ಸಮಯದಲ್ಲಿದ್ದರೂ, ಸಂಯೋಜಿತ ರೂಟಿಂಗ್ನಲ್ಲಿ ವಿನಂತಿಗಳು ಮಾಡೆಲ್ ಅನ್ನು ಇನ್ನೂ ಬಿಟ್ಟುಬಿಡುತ್ತವೆ

**ಹಸ್ತಚಾಲಿತ ಮರುಹೊಂದಿಕೆ:**

- **ಡ್ಯಾಶ್ಬೋರ್ಡ್:** **Settings → Model Cooldowns** → ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಕಾರ್ಡ್ನಲ್ಲಿ **Re-enable** ಕ್ಲಿಕ್ ಮಾಡಿ
- **API:** ನಿರ್ವಹಣಾ ದೃಢೀಕರಣ ಹೆಡರ್ಗಳೊಂದಿಗೆ `DELETE /api/resilience/model-cooldowns`

### Command Code ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವು 403 ನೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

**ಲಕ್ಷಣಗಳು:**

- Command Code ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸುವಾಗ 403
- ಹೊಸದಾಗಿ ಸೇರಿಸಿದ ನಂತರ ಪೂರೈಕೆದಾರರ ಕಾರ್ಡ್ "unauthorized" ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** OAuth ಪ್ರಕ್ರಿಯೆ ಪೂರ್ಣಗೊಂಡಿಲ್ಲ (ಕಾಲ್ಬ್ಯಾಕ್ ಸ್ವೀಕರಿಸಲಾಗಿಲ್ಲ ಅಥವಾ ಟೋಕನ್ ಉಳಿಸಲಾಗಿಲ್ಲ).

**ಪರಿಹಾರ:**

- OAuth ಪ್ರಕ್ರಿಯೆಯನ್ನು ಮತ್ತೆ ಪ್ರಚೋದಿಸಲು CLI ನಿಂದ `omniroute providers` ಚಲಾಯಿಸಿ, ಅಥವಾ
- **Dashboard → Providers → Command Code → Reconnect** ನಿಂದ OAuth ಅನ್ನು ಮತ್ತೆ ಚಲಾಯಿಸಿ

### ModelScope ಅತಿಯಾದ 429 ಕೂಲ್ಡೌನ್ಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಲಕ್ಷಣಗಳು:**

- ಸಣ್ಣ ಪ್ರಮಾಣದ ವಿನಂತಿಗಳ ನಂತರ ModelScope ನಲ್ಲಿ ಬಹಳ ಕಡಿಮೆ ಅವಧಿಯ ಅಥವಾ ತಕ್ಷಣದ ಕೂಲ್ಡೌನ್ಗಳು
- ಸಂಯೋಜಿತ ರೂಟಿಂಗ್ ನಿರೀಕ್ಷೆಗಿಂತ ಮೊದಲೇ ModelScope ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ

**ಕಾರಣ:** ModelScope ಪೂರೈಕೆದಾರ-ನಿರ್ದಿಷ್ಟ `Retry-After` ಹೆಡರ್ಗಳನ್ನು ಹೊರಸೂಸುತ್ತದೆ. v3.8.0 ಆ ಹೆಡರ್ಗಳಿಗಾಗಿ ಮೀಸಲಾದ ನಿರ್ವಹಣೆಯನ್ನು ಒಳಗೊಂಡಿದೆ; ಆದ್ದರಿಂದ ಹಳೆಯ ಆವೃತ್ತಿಗಳು ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ದರ-ಮಿತಿ ಸೂಚನೆಗಳಾಗಿ ತಪ್ಪಾಗಿ ಅರ್ಥೈಸುತ್ತವೆ.

**ಪರಿಹಾರ:**

- ನೀವು v3.8.0 ಅಥವಾ ನಂತರದ ಆವೃತ್ತಿಯಲ್ಲಿದ್ದೀರಿ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ
- **Settings → Resilience** ಅಡಿಯಲ್ಲಿ `useUpstream429BreakerHints` ಟಾಗಲ್ ಸಕ್ರಿಯವಾಗಿದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ

### ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ OMNIROUTE_WS_BRIDGE_SECRET ಕಾಣೆಯಾಗಿದೆ

**ಲಕ್ಷಣಗಳು:**

- ದೂರಸ್ಥ ಉತ್ಪಾದನಾ ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಲಾಯಿಸುವಾಗ ಪ್ರತಿಯೊಂದು Codex/Responses WebSocket ಬ್ರಿಡ್ಜ್ ವಿನಂತಿಗೂ 401
- ಸಂಪರ್ಕಗೊಂಡ ತಕ್ಷಣ WebSocket ಬ್ರಿಡ್ಜ್ ಹ್ಯಾಂಡ್ಶೇಕ್ ಮುಚ್ಚುತ್ತದೆ

**ಕಾರಣ:** ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ `OMNIROUTE_WS_BRIDGE_SECRET` ಪರಿಸರ ಚರಾಂಶವು ಕಾಣೆಯಾಗಿದೆ.

**ಪರಿಹಾರ:**

1. ಯಾದೃಚ್ಛಿಕ ರಹಸ್ಯವನ್ನು ರಚಿಸಿ: `openssl rand -hex 32`
2. ಉತ್ಪಾದನಾ ಸರ್ವರ್ ಪರಿಸರದಲ್ಲಿ (ಮತ್ತು ಬ್ರಿಡ್ಜ್ನೊಂದಿಗೆ ಸಂವಹನ ನಡೆಸುವ ಯಾವುದೇ ಕ್ಲೈಂಟ್ನಲ್ಲಿ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ಹೊಂದಿಸಿ
3. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ

### Responses API: ಹಿನ್ನೆಲೆ ಮೋಡ್ ಅನ್ನು ಸಿಂಕ್ರೊನಸ್ ಮೋಡ್ಗೆ ಇಳಿಸಲಾಗಿದೆ

**ಲಕ್ಷಣಗಳು:**

- ಲಾಗ್ ಮಾಡಲಾದ ಎಚ್ಚರಿಕೆ: `background mode degraded to synchronous`
- `background: true` ವಿನಂತಿಯು ಹಿನ್ನೆಲೆ ಜಾಬ್ ಹ್ಯಾಂಡಲ್ ಬದಲಿಗೆ ಸಾಮಾನ್ಯ ಸಿಂಕ್ರೊನಸ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಕಾರಣ:** v3.8.0 ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ Responses API ಯಲ್ಲಿನ `background: true` ಅನ್ನು ಎಚ್ಚರಿಕೆಯನ್ನು ಹೊರಸೂಸುತ್ತಾ ಸಿಂಕ್ರೊನಸ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಗೆ ಇಳಿಸುತ್ತದೆ. ಸಂಪೂರ್ಣ ಅಸಿಂಕ್ರೊನಸ್ ಹಿನ್ನೆಲೆ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯು ಭವಿಷ್ಯದಲ್ಲಿ ಒದಗಿಸಲಾಗುವ ವೈಶಿಷ್ಟ್ಯವಾಗಿದೆ.

**ಪರಿಹಾರ:**

- `background` ಇಲ್ಲದೆ ಕರೆ ಮಾಡುವಂತೆ ಕ್ಲೈಂಟ್ ಅನ್ನು ಹೊಂದಿಸಿ, ಅಥವಾ
- ಸಂಪೂರ್ಣ ಅಸಿಂಕ್ರೊನಸ್ ಹಿನ್ನೆಲೆ ಮೋಡ್ ಒಳಗೊಂಡಿರುವ ನಂತರದ ಬಿಡುಗಡೆಗಾಗಿ ಕಾಯಿರಿ (ಬದಲಾವಣೆಗಳ ದಾಖಲೆಯನ್ನು ಅನುಸರಿಸಿ)

## ನಿಧಾನ ಪ್ರಾರಂಭ / ಸಿದ್ಧತಾ ಕಾಲಮಿತಿ

CLI `⚠ Server did not respond within 60s` ಎಂದು ಮುದ್ರಿಸಿದರೂ ಸರ್ವರ್ ವಾಸ್ತವವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದ್ದರೆ, ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಸಿದ್ಧತಾ ಪರಿಶೀಲನೆಯ ಸಮಯ ಮಿತಿ ತುಂಬಾ ಕಡಿಮೆಯಾಗಿದೆ.

ಇದು ಸಾಮಾನ್ಯವಾಗಿ Windowsನಲ್ಲಿ (ಆಂಟಿವೈರಸ್, ಫೈಲ್ಸಿಸ್ಟಮ್ ವೀಕ್ಷಕಗಳು) ಅಥವಾ ಪ್ರಾರಂಭದ ವೇಳೆ ಹೆಚ್ಚಿನ ಕಾರ್ಯಭಾರವಿರುವ ಕಂಟೇನರ್ಗಳಲ್ಲಿ ಸಂಭವಿಸುತ್ತದೆ.

**ಪರಿಹಾರ — ಸಮಯ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ:**

```bash
# ಪರಿಸರ ಚರದ ಮೂಲಕ (ಪ್ರಾರಂಭಗಳಾದ್ಯಂತ ಉಳಿಯುತ್ತದೆ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ನಿಮಿಷಗಳು
omniroute serve

# CLI ಫ್ಲ್ಯಾಗ್ ಮೂಲಕ (ಒಂದು ಬಾರಿಗೆ):
omniroute serve --ready-timeout 180000
```

ಡೀಫಾಲ್ಟ್ ಮಿತಿ 60 000 ms (60 s) ಆಗಿದೆ. ಎಚ್ಚರಿಕೆಯು ಮಾಹಿತಿಗಾಗಿ ಮಾತ್ರ; ಸರ್ವರ್ ಹಿನ್ನೆಲೆಯಲ್ಲಿ ಪ್ರಾರಂಭವಾಗುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತದೆ ಮತ್ತು ಬೂಟ್ ಪೂರ್ಣಗೊಂಡ ನಂತರ ಅದನ್ನು ತಲುಪಬಹುದು.

`OMNIROUTE_READY_TIMEOUT_MS` ಕುರಿತ ಸಂಪೂರ್ಣ ವಿವರಗಳಿಗಾಗಿ [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ನೋಡಿ.
