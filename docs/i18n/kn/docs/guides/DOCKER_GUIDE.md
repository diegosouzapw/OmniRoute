## ತ್ವರಿತ ಚಾಲನೆ

> **ಒಂದೇ ಕಮಾಂಡ್ನಲ್ಲಿ ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಬೇಕೇ?**
> [ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾರ್ಗದರ್ಶಿ](../getting-started/SELF_HOST_GUIDE.md) ನೋಡಿ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ಪ್ರಕಟಿತ ಇಮೇಜ್ +
> Redis, ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮಾತ್ರ ಸೀಮಿತ, ಪ್ರೊಫೈಲ್ ಆಯ್ಕೆ ಇಲ್ಲ). ಕೆಳಗಿನ ತ್ವರಿತ ಚಾಲನೆಯು
> ಈಗಾಗಲೇ ಬೇರೆಡೆ Redis ಚಾಲನೆ ಮಾಡುತ್ತಿರುವ ಬಳಕೆದಾರರಿಗಾಗಿ ಇರುವ ಏಕ-ಕಂಟೇನರ್ ವಿಧಾನವಾಗಿದೆ.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## ಪರಿಸರ ಫೈಲ್ನೊಂದಿಗೆ

```bash

  --name omniroute \

```

## Docker Compose

```bash
# ಮೂಲ ಪ್ರೊಫೈಲ್ (CLI ಪರಿಕರಗಳಿಲ್ಲ)
docker compose --profile base up -d

# CLI ಪ್ರೊಫೈಲ್ (Claude Code, Codex, OpenClaw ಅಂತರ್ನಿರ್ಮಿತ)
docker compose --profile cli up -d

# ಹೋಸ್ಟ್ ಪ್ರೊಫೈಲ್ (ಪ್ರಾಥಮಿಕವಾಗಿ Linux ಗಾಗಿ; ಹೋಸ್ಟ್ CLI ಬೈನರಿಗಳನ್ನು ಓದಲು-ಮಾತ್ರವಾಗಿ ಮೌಂಟ್ ಮಾಡುತ್ತದೆ)
docker compose --profile host up -d

# ವೆಬ್ ಪ್ರೊಫೈಲ್ (ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರಿಗಾಗಿ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI ಸೈಡ್ಕಾರ್ ಅನ್ನು ಸಂಯೋಜಿಸಿ
docker compose --profile cli --profile cliproxyapi up -d
```

## ಲಭ್ಯವಿರುವ ಪ್ರೊಫೈಲ್ಗಳು

ಮುಖ್ಯ ನಿಯೋಜನಾ ವಿನ್ಯಾಸಗಳಿಗಾಗಿ OmniRoute Compose ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಹೊಂದುವಂತಹದನ್ನು ಆಯ್ಕೆಮಾಡಿ.

| ಪ್ರೊಫೈಲ್          | ಸೇವೆ             | ಯಾವಾಗ ಬಳಸಬೇಕು                                                                                                                                                 | ಕಮಾಂಡ್                                       |
| ----------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ಡೀಫಾಲ್ಟ್) | `omniroute-base` | ಹೆಡ್ಲೆಸ್ ಸರ್ವರ್ / ಕನಿಷ್ಠ ರನ್ಟೈಮ್, ಯಾವುದೇ ಪೂರೈಕೆದಾರ CLIಗಳನ್ನು ಒಳಗೊಂಡಿಲ್ಲ                                                                                       | `docker compose --profile base up -d`        |
| `cli`             | `omniroute-cli`  | `omniroute providers/setup/doctor` ಮತ್ತು ಒಳಗೊಂಡಿರುವ CLIಗಳನ್ನು (Codex, Claude Code, Droid, OpenClaw) ಕರೆಯುವ ಏಜೆಂಟ್-ಆಧಾರಿತ ಕಾರ್ಯಪ್ರವಾಹಗಳು                       | `docker compose --profile cli up -d`         |
| `host`            | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` ಮುಂತಾದವುಗಳನ್ನು ಓದಲು-ಮಾತ್ರವಾಗಿ ಮೌಂಟ್ ಮಾಡುವ ಮೂಲಕ ಹೋಸ್ಟ್ CLIಗಳಿಗೆ `network_mode`-ರೀತಿಯ ಪ್ರವೇಶವನ್ನು ಬಯಸುವ Linux ಹೋಸ್ಟ್ಗಳು | `docker compose --profile host up -d`        |
| `cliproxyapi`     | `cliproxyapi`    | ಅಪ್ಸ್ಟ್ರೀಮ್ CLI ಪ್ರಾಕ್ಸಿಗಾಗಿ `8317` ಪೋರ್ಟ್ನಲ್ಲಿ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ಸೈಡ್ಕಾರ್ ಅನ್ನು ಚಾಲನೆ ಮಾಡಿ                         | `docker compose --profile cliproxyapi up -d` |
| `web`             | `omniroute-web`  | ಬ್ರೌಸರ್ ಅಗತ್ಯವಿರುವ ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರು: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ಅನ್ನು ಬಿಲ್ಡ್ ಮಾಡುತ್ತದೆ, Chromium ಒಳಗೊಂಡಿದೆ)           | `docker compose --profile web up -d`         |

> ಹಲವು ಪ್ರೊಫೈಲ್ಗಳನ್ನು ಸಂಯೋಜಿಸಬಹುದು: `docker compose --profile cli --profile cliproxyapi up -d`.

## OmniRoute Docker ನಲ್ಲಿ ಚಾಲನೆಯಲ್ಲಿರುವಾಗ ಹೋಸ್ಟ್ CLI ಪರಿಕರಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುವುದು

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ
**ಕಾನ್ಫಿಗ್ ಉಳಿಸಿ** ಬಟನ್ಗಳು `~/.codex/*.config.toml` ನಂತಹ ಫೈಲ್ಗಳನ್ನು ಬರೆಯುತ್ತವೆ. ಆ ಪಥಗಳು
CLI ನಿಜವಾಗಿಯೂ ಚಾಲನೆಯಾಗುವ ಯಂತ್ರದಲ್ಲಿ ಮಾತ್ರ ಅರ್ಥಪೂರ್ಣವಾಗಿರುತ್ತವೆ. ಅವುಗಳನ್ನು
ಕಂಟೇನರ್ನೊಳಗೆ ಚಲಾಯಿಸಿದರೆ, ಬರವಣಿಗೆಯು ಕಂಟೇನರ್ನ ಸ್ವಂತ ಹೋಮ್ಗೆ (`/home/node` —
ಇಮೇಜ್ `USER node` ಆಗಿ ಚಾಲನೆಯಾಗುತ್ತದೆ) ಹೋಗುತ್ತದೆ; ಯಾವುದೇ ಹೋಸ್ಟ್ CLI ಅದನ್ನು ಎಂದಿಗೂ ಓದುವುದಿಲ್ಲ ಮತ್ತು
ಕಂಟೇನರ್ ಅನ್ನು ಮರುರಚಿಸಿದ ಕ್ಷಣದಲ್ಲೇ ಅದು ಅಳಿಸಿಹೋಗುತ್ತದೆ.

OmniRoute ಇದನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ ಮತ್ತು ನೀವು ಬಳಸಲಾಗದ ಯಶಸ್ಸನ್ನು ವರದಿ ಮಾಡುವ ಬದಲು
ಸೂಚನೆಗಳೊಂದಿಗೆ ಬರವಣಿಗೆಯನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ: CLI `2` ನೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ ಮತ್ತು API
`containerEphemeralTarget: true` ಜೊತೆಗೆ `422` ಎಂದು ಉತ್ತರಿಸುತ್ತದೆ.

### ಶಿಫಾರಸು ಮಾಡಲಾಗಿದೆ: CLI ಅನ್ನು ಹೋಸ್ಟ್ನಲ್ಲಿ ಮತ್ತು OmniRoute ಅನ್ನು Docker ನಲ್ಲಿ ಚಲಾಯಿಸಿ

ಕಂಟೇನರ್ API ಅನ್ನು ಒದಗಿಸುತ್ತದೆ; CLI ನಿಮ್ಮ ಹೋಸ್ಟ್ ಪರಿಕರಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುತ್ತದೆ.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLI ಅನ್ನು ಕಂಟೇನರ್ಗೆ ಸಂಪರ್ಕಿಸಿ
omniroute setup-codex                      # ನಿಮ್ಮ ಹೋಸ್ಟ್ನ ನಿಜವಾದ ~/.codex ಗೆ ಬರೆಯುತ್ತದೆ
```

Codex, Claude Code, Cursor ಅಥವಾ ಅಂತಹುದೇ ಪರಿಕರಗಳು ನಿಮ್ಮ
ಲ್ಯಾಪ್ಟಾಪ್ನಲ್ಲಿ ಚಾಲನೆಯಾಗುವಾಗ ಇದು ಸರಿಯಾದ ಆಯ್ಕೆ — ಸಾಮಾನ್ಯ ಸೆಟಪ್ ಇದೇ ಆಗಿದೆ.

### ಪರ್ಯಾಯ: ಹೋಸ್ಟ್ ಕಾನ್ಫಿಗ್ ಡೈರೆಕ್ಟರಿಗಳನ್ನು bind-mount ಮಾಡಿ (`host` ಪ್ರೊಫೈಲ್)

ಕಂಟೇನರ್ ಸ್ವತಃ ನಿಮ್ಮ ಹೋಸ್ಟ್ ಕಾನ್ಫಿಗ್ಗೆ ಬರೆಯಬೇಕೆಂದು ನೀವು ಬಯಸಿದರೆ,
ಡೈರೆಕ್ಟರಿಗಳನ್ನು ಮೌಂಟ್ ಮಾಡಿ ಮತ್ತು `CLI_CONFIG_HOME` ಅನ್ನು ಮೌಂಟ್ ರೂಟ್ಗೆ ನಿರ್ದೇಶಿಸಿ. `host` ಪ್ರೊಫೈಲ್
ಈಗಾಗಲೇ ಇದನ್ನು ಮಾಡುತ್ತದೆ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

bind mount ಪಥವನ್ನು ವಿಶ್ವಾಸಾರ್ಹವಾಗಿಸುತ್ತದೆ: OmniRoute
`/proc/self/mountinfo` ಅನ್ನು ಓದುತ್ತದೆ ಮತ್ತು ಮೌಂಟ್ ಮಾಡಿದ ಪಥಗಳಿಗೆ (ಹಾಗೂ ಅವುಗಳ
ಚೈಲ್ಡ್ ಡೈರೆಕ್ಟರಿಗಳು ಮೌಂಟ್ ಆಗಿರುವ ಡೈರೆಕ್ಟರಿಗಳಿಗೆ—ಮೇಲಿನ `/host-home` ರಚನೆಯು ನಿಖರವಾಗಿ ಇದೇ ಆಗಿದೆ) ಬರೆಯಲು ಅನುಮತಿಸುತ್ತದೆ,
ಆದರೆ ಮೌಂಟ್ ಮಾಡದ ಪಥಗಳಿಗೆ ಬರೆಯುವುದನ್ನು ಇನ್ನೂ ನಿರಾಕರಿಸುತ್ತದೆ.

### ತುರ್ತು ಪರ್ಯಾಯ: ಕಂಟೇನರ್ನ ಸ್ವಂತ CLI ಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿ (ಮಿತವಾಗಿ ಬಳಸಿ)

CLI ಗಳು ನಿಜವಾಗಿಯೂ ಕಂಟೇನರ್ನೊಳಗೇ ಇರುವಾಗ (`cli` ಪ್ರೊಫೈಲ್), ಬರವಣಿಗೆಯು
ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿರುತ್ತದೆ. ಯಾವುದೇ `setup-*` ಕಮಾಂಡ್ಗೆ `--allow-container-write` ಅನ್ನು ಪಾಸ್ ಮಾಡಿ ಅಥವಾ
ಸರ್ವರ್ಗಾಗಿ `OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ಅನ್ನು ಹೊಂದಿಸಿ. ಬರವಣಿಗೆಯು ಮುಂದುವರಿಯುತ್ತದೆ,
ಆದರೆ ಅದು ಕಂಟೇನರ್ ಉಳಿಯುವ ಅವಧಿಗಿಂತ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯುವುದಿಲ್ಲ ಎಂಬ ಎಚ್ಚರಿಕೆಯನ್ನು ನೀಡಲಾಗುತ್ತದೆ.

> **ಭದ್ರತಾ ಎಚ್ಚರಿಕೆ — `cli` ಪ್ರೊಫೈಲ್ + `docker.sock` ಮೌಂಟ್.**
> ಕಂಟೇನರ್ನೊಳಗಿನ ಸ್ವಯಂ-ಅಪ್ಡೇಟರ್ ಹೋಸ್ಟ್ ಡೀಮನ್ನಿಂದ ಸ್ಟ್ಯಾಕ್ ಅನ್ನು ಮರುರಚಿಸಲು ಸಾಧ್ಯವಾಗುವಂತೆ
> `cli` ಪ್ರೊಫೈಲ್ `/var/run/docker.sock` ಅನ್ನು bind-mount ಮಾಡುತ್ತದೆ
> (`src/lib/system/autoUpdate.ts` ಆ ಸಾಕೆಟ್ಗಾಗಿ ಪರಿಶೀಲಿಸುತ್ತದೆ ಮತ್ತು ಅದು
> ಇಲ್ಲದಿದ್ದಾಗ Docker ಪಥವನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ). ಆ ಸಾಕೆಟ್ **ಹೋಸ್ಟ್-root ವಿಶ್ವಾಸದ
> ಗಡಿ** ಆಗಿದೆ: ಅದನ್ನು ತಲುಪಬಲ್ಲ ಯಾವುದಾದರೂ ಹೋಸ್ಟ್ Docker ಡೀಮನ್ ಅನ್ನು
> root ಆಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ — ಅದು ಹೋಸ್ಟ್ನಲ್ಲಿರುವ ಯಾವುದೇ ಕಂಟೇನರ್ ಅನ್ನು ರಚಿಸಬಹುದು, ಪರಿಶೀಲಿಸಬಹುದು,
> ನಿಲ್ಲಿಸಬಹುದು ಮತ್ತು ತೆಗೆದುಹಾಕಬಹುದು. ಪರಿಣಾಮಗಳು:
>
> 1. **`cli` ಪ್ರೊಫೈಲ್ನ ಪೋರ್ಟ್ ಅನ್ನು ಎಂದಿಗೂ ನೆಟ್ವರ್ಕ್ಗೆ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.** ಅದನ್ನು
>    `127.0.0.1` ನಲ್ಲಿ ಪ್ರಕಟಿಸಿ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LAN ಮೂಲಕ ತಲುಪಬಹುದಾದ `cli` ಪ್ರೊಫೈಲ್ ಯಾವುದೇ ಡ್ಯಾಶ್ಬೋರ್ಡ್-ಮಟ್ಟದ RCE ಅನ್ನು
>    ಸಂಪೂರ್ಣ ಹೋಸ್ಟ್ ರಾಜಿಗೆ ಪರಿವರ್ತಿಸುತ್ತದೆ.
> 2. **ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಹೋಸ್ಟ್ ಡೈರೆಕ್ಟರಿಗಳನ್ನು `cli` ಪ್ರೊಫೈಲ್ಗೆ bind ಮಾಡಬೇಡಿ.**
>    Docker ಸಾಕೆಟ್ ಜೊತೆಗೆ ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಮೌಂಟ್ ಇದ್ದರೆ, ಅದು ಕಂಟೇನರ್ಗೆ ನಿಮ್ಮ
>    ಫೈಲ್ಸಿಸ್ಟಮ್ ಮತ್ತು ಹೋಸ್ಟ್ ಕಾನ್ಫಿಗ್ಗೆ ಸಂಪೂರ್ಣ ಓದು/ಬರಹ ಪ್ರವೇಶವನ್ನು ನೀಡುತ್ತದೆ. ಪರಿಕರವು
>    ಪ್ರಾಜೆಕ್ಟ್ ಅನ್ನು ನೋಡಬೇಕಾದರೆ, ಅದನ್ನು CLI ಬೈನರಿಯೊಂದಿಗೆ ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಿ — ಅದನ್ನು
>    `cli` ಕಂಟೇನರ್ನೊಳಗೆ ಮೌಂಟ್ ಮಾಡಬೇಡಿ.
>
> ನಿಮಗೆ ಕಂಟೇನರ್ನೊಳಗಿನ ಸ್ವಯಂ-ಅಪ್ಡೇಟ್ ಅಗತ್ಯವಿಲ್ಲದಿದ್ದರೆ, `cli` ಪ್ರೊಫೈಲ್ ಅನ್ನು ಆಫ್ ಆಗಿಯೇ ಇರಿಸಿ
> (`COMPOSE_PROFILES=core,redis` ಅಥವಾ ಇನ್ನೂ ಚಿಕ್ಕದಾಗಿ). ಇತರ ಪ್ರೊಫೈಲ್ಗಳು
> Docker ಸಾಕೆಟ್ ಅನ್ನು ಮೌಂಟ್ ಮಾಡುವುದಿಲ್ಲ.
>
> MITM ಗೆ ಸಂಬಂಧಿಸಿದ ಬೆದರಿಕೆ ಮಾದರಿಗಾಗಿ `docs/security/MITM-TPROXY-DECRYPT.md` ಅನ್ನು ನೋಡಿ (git; `/docs` ಒಳಗೆ ಕಂಪೈಲ್ ಮಾಡಲಾಗಿಲ್ಲ)
> ಮತ್ತು `codex`/`claude-code`/`droid`/`openclaw` ಬೈನರಿ ಮೂಲ ಸರಪಳಿಗಾಗಿ
> `docs/security/SUPPLY_CHAIN.md` ಅನ್ನು ನೋಡಿ.

## Redis ಸೈಡ್ಕಾರ್

ವಿತರಿತ ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಹಂಚಿಕೆಯ ಕ್ಯಾಶ್ಗೆ ಬೆಂಬಲ ನೀಡಲು OmniRoute, Redis ಅನ್ನು ಅವಲಂಬಿಸಿದೆ. `redis` ಸೇವೆಯನ್ನು `docker-compose.yml` ನಲ್ಲಿ **ಯಾವಾಗಲೂ ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿರುತ್ತದೆ** (ಇದಕ್ಕೆ ಯಾವುದೇ ಪ್ರೊಫೈಲ್ ಗೇಟ್ ಇಲ್ಲ) ಮತ್ತು ಬೇರೆ ಯಾವುದೇ ಪ್ರೊಫೈಲ್ನೊಂದಿಗೆ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ.

| ವಿವರ                     | ಮೌಲ್ಯ                                        |
| ------------------------ | -------------------------------------------- |
| ಇಮೇಜ್                    | `redis:7-alpine`                             |
| ಕಂಟೇನರ್ ಹೆಸರು            | `omniroute-redis`                            |
| ಆಂತರಿಕ ಪೋರ್ಟ್            | `6379`                                       |
| ಹೋಸ್ಟ್ ಪೋರ್ಟ್ (ಓವರ್ರೈಡ್) | `REDIS_PORT` (ಡೀಫಾಲ್ಟ್ ಆಗಿ `6379`)           |
| ಹೋಸ್ಟ್ ಬೈಂಡ್ (ಓವರ್ರೈಡ್)  | `REDIS_BIND_HOST` (ಡೀಫಾಲ್ಟ್ ಆಗಿ `127.0.0.1`) |
| ವಾಲ್ಯೂಮ್                 | `omniroute-redis-data` → `/data`             |
| ಆರೋಗ್ಯ ತಪಾಸಣೆ            | `redis-cli ping` (10s ಮಧ್ಯಂತರ)               |

ಸಂಬಂಧಿತ ಪರಿಸರ ಚರಗಳು:

- `REDIS_URL` — ಆ್ಯಪ್ಗೆ ಸೇರಿಸಲಾದ ಸಂಪರ್ಕ ಸ್ಟ್ರಿಂಗ್ (ಡೀಫಾಲ್ಟ್ ಆಗಿ `redis://redis:6379`).
- `REDIS_PORT` — Redis ಕಂಟೇನರ್ಗಾಗಿ ಹೋಸ್ಟ್-ಭಾಗದ ಪೋರ್ಟ್ ಮ್ಯಾಪಿಂಗ್.
- `REDIS_BIND_HOST` — ಪೋರ್ಟ್ ಪ್ರಕಟಿಸಲಾಗುವ ಹೋಸ್ಟ್ ಇಂಟರ್ಫೇಸ್. ಡೀಫಾಲ್ಟ್ ಆಗಿ `127.0.0.1`.

> **ಡೀಫಾಲ್ಟ್ ಆಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಏಕೆ:** ಸೈಡ್ಕಾರ್ `requirepass` ಇಲ್ಲದೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ ಮತ್ತು ಆ್ಯಪ್
> ಕಂಟೇನರ್ಗಳು compose ನೆಟ್ವರ್ಕ್ (`redis:6379`) ಮೂಲಕ ಅದನ್ನು ತಲುಪುತ್ತವೆ — ಪ್ರಕಟಿತ ಪೋರ್ಟ್
> ಹೋಸ್ಟ್-ಭಾಗದ ಪರಿಕರಗಳಿಗಾಗಿ ಮಾತ್ರ (`redis-cli`, ಸ್ಥಳೀಯ `npm run dev`) ಇರುತ್ತದೆ. ಅದನ್ನು
> `0.0.0.0` ನಲ್ಲಿ ಪ್ರಕಟಿಸಿದರೆ, ದೃಢೀಕರಣವಿಲ್ಲದ Redis ನಿಮ್ಮ LANನಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು ಹೋಸ್ಟ್ಗೂ ಬಹಿರಂಗಗೊಳ್ಳುತ್ತದೆ. ನೀವು
> `REDIS_BIND_HOST=0.0.0.0` ಹೊಂದಿಸಿದರೆ, ಸೇವೆಯ `command:` ಗೆ `--requirepass` ಅನ್ನೂ ಸೇರಿಸಿ.

**Redis ಅನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದನ್ನು** ಶಿಫಾರಸು ಮಾಡುವುದಿಲ್ಲ (ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆ ಇನ್-ಮೆಮೊರಿ ಪರ್ಯಾಯಕ್ಕೆ ಕುಸಿಯುತ್ತದೆ). ಹಾಗೆ ಮಾಡಲೇಬೇಕಾದರೆ, `docker-compose.yml` ನಲ್ಲಿರುವ `redis:` ಸೇವಾ ಬ್ಲಾಕ್ ಅನ್ನು ತೆಗೆದುಹಾಕಿ/ಕಾಮೆಂಟ್ ಮಾಡಿ ಅಥವಾ ಅದನ್ನು ಶೂನ್ಯಕ್ಕೆ ಸ್ಕೇಲ್ ಮಾಡಿ:

```bash
docker compose up -d --scale redis=0
```

## ಪ್ರೊಡಕ್ಷನ್ Compose

ಡೆವ್ ಜೊತೆಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಪ್ರತ್ಯೇಕ ಪ್ರೊಡಕ್ಷನ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಾಗಿ `docker-compose.prod.yml` ಬಳಸಿ.

| ವಿವರ                         | ಮೌಲ್ಯ                                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| ಫೈಲ್                         | `docker-compose.prod.yml`                                                                    |
| ಡೀಫಾಲ್ಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪೋರ್ಟ್ | `PROD_DASHBOARD_PORT=20130` (ಆಂತರಿಕ `${DASHBOARD_PORT:-20128}` ಗೆ ಮ್ಯಾಪ್ ಮಾಡಲಾಗಿದೆ)          |
| ಡೀಫಾಲ್ಟ್ API ಪೋರ್ಟ್          | `PROD_API_PORT=20131`                                                                        |
| ಇಮೇಜ್                        | `omniroute:prod` (`runner-cli` ಟಾರ್ಗೆಟ್ನಿಂದ ನಿರ್ಮಿಸಲಾಗಿದೆ)                                   |
| Redis ಕಂಟೇನರ್                | `omniroute-redis-prod` (`redis:8.6.2`, ಮೀಸಲಾದ `redis-prod-data` ವಾಲ್ಯೂಮ್)                    |
| ಡೇಟಾ ವಾಲ್ಯೂಮ್                | `omniroute-prod-data` (ಹೆಸರಿಸಲಾದದ್ದು, ಮರುನಿರ್ಮಾಣಗಳಾದ್ಯಂತ ಉಳಿಸಲಾಗುತ್ತದೆ)                      |
| ಆರೋಗ್ಯ ತಪಾಸಣೆಗಳು             | `node healthcheck.mjs` + `redis-cli ping`, Redis ಆರೋಗ್ಯದ ಆಧಾರದ ಮೇಲೆ ಗೇಟ್ ಮಾಡಲಾದ `depends_on` |

ಬಳಸುವ ವಿಧಾನ:

```bash
# ಪ್ರೊಡಕ್ಷನ್ ಸ್ಟ್ಯಾಕ್ ಅನ್ನು ನಿರ್ಮಿಸಿ ಮತ್ತು ಪ್ರಾರಂಭಿಸಿ
docker compose -f docker-compose.prod.yml up -d --build

# ಲಾಗ್ಗಳನ್ನು ನಿರಂತರವಾಗಿ ವೀಕ್ಷಿಸಿ
docker compose -f docker-compose.prod.yml logs -f

# ಸ್ಥಗಿತಗೊಳಿಸಿ (ವಾಲ್ಯೂಮ್ಗಳನ್ನು ಉಳಿಸಿ)
docker compose -f docker-compose.prod.yml down
```

ಪ್ರೊಡ್ ಸ್ಟ್ಯಾಕ್ ಡೆವ್ compose ಜೊತೆಗೆ ಸಮಾನಾಂತರವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ (ಕಂಟೇನರ್ ಹೆಸರುಗಳು, ಪೋರ್ಟ್ಗಳು ಮತ್ತು ವಾಲ್ಯೂಮ್ಗಳು ವಿಭಿನ್ನವಾಗಿವೆ), ಆದ್ದರಿಂದ ಪ್ರೊಡಕ್ಷನ್ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿರುವಾಗಲೇ ನೀವು ಸ್ಥಳೀಯವಾಗಿ ಪುನರಾವರ್ತಿತ ಅಭಿವೃದ್ಧಿಯನ್ನು ಮುಂದುವರಿಸಬಹುದು.

## Dockerfile ಹಂತಗಳು

ರೆಪೊಸಿಟರಿಯು ಬಹು-ಹಂತದ Dockerfile (`Dockerfile`) ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ನಾಲ್ಕು ಹಂತಗಳನ್ನು ಲಭ್ಯಗೊಳಿಸಲಾಗಿದೆ; ನಿಮ್ಮ ಬಳಕೆಯ ಸಂದರ್ಭಕ್ಕೆ ಸರಿಯಾದ `target` ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ.

| ಹಂತ           | ಮೂಲ ಇಮೇಜ್             | ಉದ್ದೇಶ                                                                                                                                                                                                                                                                                                              |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ಅವಲಂಬನೆಗಳನ್ನು ಸ್ಥಾಪಿಸುತ್ತದೆ (`npm ci --legacy-peer-deps`) ಮತ್ತು `npm run build` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ Turbopack — ಕೆಳಗಿನ ನಿರ್ಮಾಣ-ಸಮಯದ ಸಂಪನ್ಮೂಲಗಳನ್ನು ನೋಡಿ)                                                                                                                                           |
| `runner-base` | `node:26-trixie-slim` | Next.js ಸ್ವತಂತ್ರ ಔಟ್ಪುಟ್ನೊಂದಿಗೆ ಪ್ರೊಡಕ್ಷನ್ ರನ್ಟೈಮ್. **ಯಾವುದೇ ಪೂರೈಕೆದಾರ CLIಗಳನ್ನು ಸೇರಿಸಲಾಗಿಲ್ಲ.**                                                                                                                                                                                                                    |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ಮತ್ತು ಜಾಗತಿಕ CLIಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`. **ಏಜೆಂಟಿಕ್ ಕಾರ್ಯಪ್ರವಾಹಗಳಿಗಾಗಿ ಇದನ್ನು ಆಯ್ಕೆಮಾಡಿ.**                                                                                                                       |
| `runner-web`  | `runner-base`         | ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರಗಳಿಗಾಗಿ Playwright + Chromium ಬ್ರೌಸರ್ (`--with-deps`) ಅನ್ನು ಸೇರಿಸುತ್ತದೆ: `gemini-web`, `claude-web`, `claude-turnstile`. **ಆ ಪೂರೈಕೆದಾರಗಳನ್ನು ಬಳಸುವಾಗ ಇದನ್ನು ಆಯ್ಕೆಮಾಡಿ** — ಇದು ಇಲ್ಲದಿದ್ದರೆ ಸಾಮಾನ್ಯ ಇಮೇಜ್ ವಿನಂತಿಯ ಸಮಯದಲ್ಲಿ ವಿಫಲವಾಗುತ್ತದೆ (ಬಿಡುಗಡೆ ಚಾನೆಲ್ಗಳ ಅಡಿಯಲ್ಲಿರುವ `-web` ಟಿಪ್ಪಣಿಯನ್ನು ನೋಡಿ). |

ನಿರ್ದಿಷ್ಟ target ಅನ್ನು ಹಸ್ತಚಾಲಿತವಾಗಿ ನಿರ್ಮಿಸಿ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ನಿರ್ಮಾಣ-ಸಮಯದ ಸಂಪನ್ಮೂಲಗಳು

ಮೂರು build argಗಳು `builder` ಹಂತದ ಸಂಪನ್ಮೂಲ ವೆಚ್ಚವನ್ನು ನಿಯಂತ್ರಿಸುತ್ತವೆ. ಅವು ನಿರ್ಮಾಣ-ಸಮಯಕ್ಕೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತವೆ —
`OMNIROUTE_MEMORY_MB` (ಕೆಳಗೆ) ಪ್ರತ್ಯೇಕ ರನ್ಟೈಮ್ ನಿಯಂತ್ರಣವಾಗಿದೆ.

| Build arg                   | ಪೂರ್ವನಿಯೋಜಿತ | ಪರಿಣಾಮ                                                                                                            |
| --------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`          | `0` webpack ಬಳಸಿ ನಿರ್ಮಿಸುತ್ತದೆ: ಕಡಿಮೆ ಗರಿಷ್ಠ ಮೆಮೊರಿ, ನಿಧಾನ. `1` Turbopack ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ.                |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`       | ಪ್ರಾರಂಭಿಸಲಾದ `next build` ಗಾಗಿ V8 heap ಮಿತಿ (`--max-old-space-size`).                                             |
| `OMNIROUTE_BUILD_WORKERS`   | `2`          | `CIRCLE_NODE_TOTAL` ಗೆ ಮೌಲ್ಯವನ್ನು ಒದಗಿಸುತ್ತದೆ; ಪುಟ-ಡೇಟಾ ಸಂಗ್ರಹಣೆಗಾಗಿ Next `workers = N - 1` ಅನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ. |

ದೊಡ್ಡ builder ನಲ್ಲಿ ಹೆಚ್ಚಿಸಬೇಕಾದದ್ದು `OMNIROUTE_BUILD_WORKERS`; ಹಾಗೆಯೇ ಸಂಪನ್ಮೂಲ-ನಿರ್ಬಂಧಿತ build ಒಂದು `✓ Compiled successfully` ಎಂಬುದರ **ನಂತರ** ಸ್ಥಗಿತಗೊಂಡರೆ ಮೊದಲು ಅನುಮಾನಿಸಬೇಕಾದದ್ದೂ ಇದೇ. ಪ್ರತಿಯೊಂದು
ಪುಟ-ಡೇಟಾ worker ತನ್ನದೇ ಪ್ರಕ್ರಿಯೆಯಾಗಿರುತ್ತದೆ ಮತ್ತು ಮೂಲ `next build` ಕೂಡ
ಪ್ರತ್ಯೇಕ ಪ್ರಕ್ರಿಯೆಯಾಗಿದೆ; ನೈಜ VPS ಪುನರುತ್ಪಾದನೆಯಲ್ಲಿ (issue #7518), `NODE_OPTIONS`
heap flag ನಿಂದ ಸ್ವತಂತ್ರವಾಗಿ ಪ್ರತಿಯೊಂದು ಪ್ರಕ್ರಿಯೆಯ ಗರಿಷ್ಠ RSS ~4.5 GB ಎಂದು
ಅಳೆಯಲಾಯಿತು (Turbopack, V8 heap ನ ಹೊರಗಿನ native/Rust ಮೆಮೊರಿಯಲ್ಲಿ ಕಂಪೈಲ್
ಮಾಡುತ್ತದೆ). `2` ಎಂಬ ಪೂರ್ವನಿಯೋಜಿತ ಮೌಲ್ಯವು (→ 1 worker, ಒಟ್ಟು 2
ಪ್ರಕ್ರಿಯೆಗಳು) ಪ್ರಕಟಣೆ pipeline ಬಳಸುವ 16 GB / 4 vCPU GitHub-hosted runnerಗಳಿಗೆ
ಹೊಂದುವಂತೆ ನಿಗದಿಪಡಿಸಲಾಗಿದೆ. `8` ನಲ್ಲಿ (→ 7 workers) ಆ runner ನ ಮೆಮೊರಿ ಮುಗಿದು,
buildkit ಹಂತವು `ResourceExhausted: ... cannot allocate memory` ದೋಷದೊಂದಿಗೆ
ವಿಫಲವಾಯಿತು; ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಯ RSS ಅನ್ನು ಊಹಿಸುವ ಬದಲು ನೇರವಾಗಿ ಅಳೆದಾಗ `3`
(→ 2 workers) ಕೂಡ ಸಾಕಾಗಲಿಲ್ಲ. `tests/unit/docker-build-memory-budget.test.ts`
ಅಳತೆ ಮಾಡಿದ ಮೌಲ್ಯವನ್ನು ಆಧರಿಸಿ ಲೆಕ್ಕಾಚಾರ ಮಾಡುತ್ತದೆ ಮತ್ತು ಯಾವುದಾದರೂ ನಿಯಂತ್ರಣವು
runner ಸಾಮರ್ಥ್ಯವನ್ನು ಮೀರಿದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

Turbopack, V8 heap ನ **ಹೊರಗೆ** ಇರುವ native Rust ಮೆಮೊರಿಯಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡುತ್ತದೆ,
ಆದ್ದರಿಂದ `OMNIROUTE_BUILD_MEMORY_MB` ಅದಕ್ಕೆ ಮಿತಿ ವಿಧಿಸುವುದಿಲ್ಲ. ಮೆಮೊರಿ ಮಿತಿಯಿರುವ
host ನಲ್ಲಿ build ಅನ್ನು ಯಾವುದೇ ದೋಷ ಪಠ್ಯವಿಲ್ಲದೆ OOM killer, SIGKILL ಮಾಡುತ್ತದೆ —
ಅದು `Creating an optimized production build` ಮಧ್ಯದಲ್ಲಿಯೇ ನಿಂತುಬಿಡುತ್ತದೆ; ಇದರಿಂದ
ಮೆಮೊರಿ ಕೊರತೆಯ ಬದಲು ಪ್ರಕ್ರಿಯೆ ಸ್ಥಗಿತಗೊಂಡಂತೆ ಕಾಣುತ್ತದೆ. ಆದ್ದರಿಂದ `npm run dev` /
`npm run build` ಗಿಂತ ಭಿನ್ನವಾಗಿ `Dockerfile`, webpack
(`OMNIROUTE_USE_TURBOPACK=0`) ಅನ್ನು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಬಳಸುತ್ತದೆ; ಅಲ್ಲಿ Turbopack
ಕೋಡ್ನ ಪೂರ್ವನಿಯೋಜಿತ ಆಯ್ಕೆಯಾಗಿದೆ: ಯಾವುದೇ build argಗಳಿಲ್ಲದ ಸಾಮಾನ್ಯ
`docker build .` (Railway ಮತ್ತು ಇತರ one-click hostಗಳು ಚಲಾಯಿಸುವುದು) ಮೆಮೊರಿ
ಮಿತಿಯ builder ನಲ್ಲಿ ಮೌನವಾಗಿ ಸ್ಥಗಿತಗೊಳ್ಳಬಾರದು. ಪ್ರಕಟಿತ ಇಮೇಜ್ಗಳು ಈಗಾಗಲೇ
`docker-publish.yml` ನಲ್ಲಿ `OMNIROUTE_USE_TURBOPACK=0` ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ
ಒದಗಿಸುತ್ತವೆ. ಸಾಕಷ್ಟು RAM ಇರುವ builder ನಲ್ಲಿ ವೇಗವಾದ build ಗಾಗಿ Turbopack ಅನ್ನು
ಸಕ್ರಿಯಗೊಳಿಸಿ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ, ಆದ್ದರಿಂದ `next build` ಒಂದು ಮೂಲ
ಪ್ರಕ್ರಿಯೆ **ಮತ್ತು** ಒಂದು worker ಪ್ರಕ್ರಿಯೆಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ ಹಾಗೂ ಪ್ರತಿಯೊಂದೂ
`OMNIROUTE_BUILD_MEMORY_MB` ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಪಾಲಿಸುತ್ತದೆ. container ಮಿತಿಯನ್ನು
ಆ ಮೌಲ್ಯದ ಸುಮಾರು ಎರಡು ಪಟ್ಟಿಗಿಂತ ಹೆಚ್ಚಾಗಿ ನಿಗದಿಪಡಿಸಿ, ಒಂದೇ ಪಟ್ಟಿಗಲ್ಲ.

ಈ tree ನಲ್ಲಿ ಅಳೆಯಲಾಗಿದೆ (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| Bundler   | Container ಮಿತಿ | ಫಲಿತಾಂಶ                               |
| --------- | -------------- | ------------------------------------- |
| Turbopack | 8 GiB / 16 GiB | ಎರಡರಲ್ಲಿಯೂ ಮೌನವಾಗಿ OOM-killed         |
| webpack   | 8 GiB          | build worker SIGKILLed                |
| webpack   | 12 GiB         | ಯಶಸ್ವಿಯಾಯಿತು, ಗರಿಷ್ಠ 11.1 GiB ತಲುಪಿತು |

### ರನ್ಟೈಮ್ ಪೂರ್ವನಿಯೋಜಿತಗಳು

`runner-base` export ಮಾಡುವ ಪೂರ್ವನಿಯೋಜಿತಗಳು: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Docker ನಲ್ಲಿನ ಮೆಮೊರಿ ವರ್ತನೆ:

- ಇಮೇಜ್ `OMNIROUTE_MEMORY_MB=1024` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ ಮತ್ತು ಅದರಿಂದ `NODE_OPTIONS=--max-old-space-size=1024` ಅನ್ನು ಪಡೆಯುತ್ತದೆ.
- ನೈಜ ಸರ್ವರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಸ್ವತಂತ್ರ ಲಾಂಚರ್ ಪ್ರಾರಂಭಿಸುತ್ತದೆ; ಅದು `OMNIROUTE_MEMORY_MB` ಅನ್ನು ಓದಿ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ಅನ್ನು ಸೇರಿಸುತ್ತದೆ.
- ಪುನರಾವರ್ತಿತ `--max-old-space-size` ಮೌಲ್ಯಗಳಲ್ಲಿ ಕೊನೆಯದನ್ನು Node ಬಳಸುತ್ತದೆ, ಆದ್ದರಿಂದ `OMNIROUTE_MEMORY_MB` ಅನ್ನು ಹೊಂದಿಸುವುದು ಪರಿಣಾಮಕಾರಿ Docker ಹೀಪ್ ಮಿತಿಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.
- ಇಮೇಜ್ ಯಾವಾಗಲೂ ಇದನ್ನು ಹೊಂದಿಸುವುದರಿಂದ, ಲಾಂಚರ್ನ ಸ್ವಂತ RAM-ಆಧಾರಿತ ಪರ್ಯಾಯವು Docker ಅಡಿಯಲ್ಲಿ ಎಂದಿಗೂ ಅನ್ವಯಿಸುವುದಿಲ್ಲ. ಕಾರ್ಯಭಾರಕ್ಕೆ ಅನುಗುಣವಾಗಿ ಅದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೆಚ್ಚಿಸಿ (ಕೆಳಗಿನ ಕೋಷ್ಟಕ). ಕೋಡಿಂಗ್-ಏಜೆಂಟ್ `/v1/responses` ಗಾಗಿ `2048` ಇನ್ನೂ ತುಂಬಾ ಚಿಕ್ಕದಾಗಿದೆ.

### ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ಗಳಿಗೆ ರನ್ಟೈಮ್ RAM

1 GiB Docker ಡೀಫಾಲ್ಟ್ ಡ್ಯಾಶ್ಬೋರ್ಡ್/ಹಗುರ ಚಾಟ್ಗೆ ಬೇಕಾದ ಕನಿಷ್ಠ ಮಿತಿಯಾಗಿದೆ, ಪ್ರೊಡಕ್ಷನ್ ಗಾತ್ರವಲ್ಲ. ದೀರ್ಘವಾದ `POST /v1/responses` ಬಾಡಿಗಳು (ನೂರಾರು ಸಂದೇಶಗಳು, ಹತ್ತಾರು ಪರಿಕರಗಳು) ಸಂಕುಚನದ ಸಮಯದಲ್ಲಿ ಅನೇಕ ಇನ್-ಮೆಮೊರಿ ಗ್ರಾಫ್ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಒಂದಕ್ಕೊಂದು ಅತಿಕ್ರಮಿಸುವ ~3 MiB / ~750k-ಟೋಕನ್ನ ಎರಡು ವಿನಂತಿಗಳು **12 GiB** ಓಲ್ಡ್-ಸ್ಪೇಸ್ನಲ್ಲಿ V8 ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಿವೆ (`FATAL ERROR: Reached heap limit`) ಮತ್ತು 16 GiB cgroup OOM ಮಿತಿಯನ್ನೂ ತಲುಪಿವೆ. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ನೋಡಿ.

**cgroup `--memory` ಅನ್ನು ಹೀಪ್ಗಿಂತ ಹೆಚ್ಚಿನದಾಗಿ ನಿಗದಿಪಡಿಸಿ** — ನೆಟಿವ್ ಬಫರ್ಗಳು, SQLite ಮತ್ತು ಸಂಕುಚನದ ಮಧ್ಯಂತರ ಡೇಟಾ V8 ಹೊರಗೆ ಇರುತ್ತವೆ.

| ಕಾರ್ಯಭಾರ                                       | `OMNIROUTE_MEMORY_MB`       | ಕಂಟೇನರ್ / cgroup            | ಟಿಪ್ಪಣಿಗಳು                                                                                                                       |
| ---------------------------------------------- | --------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| ಡ್ಯಾಶ್ಬೋರ್ಡ್, ಒಂದು ಹಗುರ ಚಾಟ್                   | `1024` (ಇಮೇಜ್ ಡೀಫಾಲ್ಟ್)     | ≥2 GiB                      |                                                                                                                                  |
| ಒಂದು ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ (Claude/Codex/Grok)        | `8192`                      | ≥10 GiB                     | ಸಾಮಾನ್ಯ ಏಕ-ಸೆಷನ್ `/v1/responses`                                                                                                 |
| ಏಕಕಾಲೀನ ಎರಡು ದೀರ್ಘ `/v1/responses`             | `10240`–`12288`             | ≥12–16 GiB                  | ~12 GiB ಹೀಪ್ನಲ್ಲಿ V8 ಸ್ಥಗಿತವನ್ನು ಅಳೆಯಲಾಗಿದೆ                                                                                      |
| ಏಕಕಾಲೀನ ಮೂರು ಅಥವಾ ಹೆಚ್ಚಿನ ದೀರ್ಘ ಕಾಂಟೆಕ್ಸ್ಟ್ಗಳು | ಒಂದೇ ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿ ಮಾಡಬೇಡಿ | ಅನುಕ್ರಮಗೊಳಿಸಿ / ಹೆಚ್ಚಿನ RAM | ಡೀಫಾಲ್ಟ್ ಹೆವಿವೇಯ್ಟ್ ಪ್ರವೇಶ ಮಿತಿ ಒಂದೇ ಚಾಲ್ತಿಯಲ್ಲಿರುವ ವಿನಂತಿಯಾಗಿದೆ; RAM ಇಲ್ಲದೆ ಅದನ್ನು ಹೆಚ್ಚಿಸುವುದು ಸ್ಥಗಿತವನ್ನು ಮತ್ತೆ ಉಂಟುಮಾಡುತ್ತದೆ |

ಬೇರ್ ಮೆಟಲ್ನಲ್ಲಿ `omniroute serve`, `OMNIROUTE_MEMORY_MB` ಅನ್ನು **ಹೊಂದಿಸದೇ ಇದ್ದಾಗ** RAMನ ~35% ಗೆ (ಮಿತಿ `[512, 4096]`) ಹೊಂದಿಸುತ್ತದೆ. Docker ಯಾವಾಗಲೂ `1024` ಅನ್ನು ಹೊಂದಿಸುವುದರಿಂದ, ಅಧಿಕೃತ ಇಮೇಜ್ನಲ್ಲಿ ಆ ಮಾಪನಾಂಕ ನಿರ್ಣಯ ಎಂದಿಗೂ ನಡೆಯುವುದಿಲ್ಲ.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ಉಪಮಾರ್ಗದಲ್ಲಿ ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ (Traefik / nginx)

Next.js `basePath` ಅನ್ನು ಸ್ವತಂತ್ರ ಬಂಡಲ್ನಲ್ಲಿ ಕಂಪೈಲ್ ಮಾಡಲಾಗುತ್ತದೆ. OmniRoute ಅಪ್ಲಿಕೇಶನ್ನ ರೂಟ್ನಲ್ಲಿರುವ ಸೆಂಟಿನಲ್ ಫೈಲ್ನಲ್ಲಿ ಬಿಲ್ಡ್ ಸಮಯದಲ್ಲಿ ಸೇರಿಸಲಾದ ಮೌಲ್ಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ (`npm run build` ಸಮಯದಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ; `scripts/docker/ensure-docker-base-path.mjs` ಮೂಲಕ ಓದಲಾಗುತ್ತದೆ) ಮತ್ತು ಕಂಟೇನರ್ ಪ್ರಾರಂಭವಾದಾಗ ಅದನ್ನು `OMNIROUTE_BASE_PATH` ಜೊತೆಗೆ ಹೋಲಿಸುತ್ತದೆ. ಅವು ಭಿನ್ನವಾಗಿದ್ದು, ಇಮೇಜ್ ಅನ್ನು ಡೊಮೇನ್ ರೂಟ್ಗಾಗಿ ಬಿಲ್ಡ್ ಮಾಡಿದ್ದರೆ, `node dev/run-standalone.mjs` ರನ್ ಆಗುವ ಮೊದಲು ಎಂಟ್ರಿಪಾಯಿಂಟ್ ಸ್ವತಂತ್ರ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳು, ಎಂಬೆಡ್ ಮಾಡಲಾದ `basePath`/`assetPrefix` ಲಿಟರಲ್ಗಳು (Next 16 SSR ಅಸೆಟ್ URL ಗಳನ್ನು `assetPrefix` ಒಂದರಿಂದಲೇ ರೆಂಡರ್ ಮಾಡುತ್ತದೆ — ಪ್ಯಾಚರ್ ಉಪಮಾರ್ಗವನ್ನು ಅದರಲ್ಲಿಯೂ ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ), ಬಿಲ್ಡ್ನಲ್ಲಿ ಸೇರಿಸಲಾದ `/_next/static` ಅಸೆಟ್ URL ಗಳು (ಕ್ಲೈಂಟ್-ರೆಫರೆನ್ಸ್ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳು, ಮೀಡಿಯಾ ಆಮದುಗಳು, ಪೂರ್ವ-ರೆಂಡರ್ ಮಾಡಿದ ದೋಷ ಪುಟಗಳು) ಮತ್ತು ಕ್ಲೈಂಟ್ `process.env` ಶಿಮ್ ಅನ್ನು ಮರುಬರೆಯುತ್ತದೆ.

### Compose ಬಿಲ್ಡ್ (ಶಿಫಾರಸು ಮಾಡಲಾಗಿದೆ)

ಇಮೇಜ್ ಮತ್ತು ರನ್ಟೈಮ್ ಹೊಂದಾಣಿಕೆಯಾಗುವಂತೆ `.env` ನಲ್ಲಿ ಎರಡೂ ಚರಗಳನ್ನು ಹೊಂದಿಸಿ, ನಂತರ ಮರುಬಿಲ್ಡ್ ಮಾಡಿ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH` ಅನ್ನು Docker ಬಿಲ್ಡ್-ಆರ್ಗ್ ಆಗಿಯೂ ರನ್ಟೈಮ್ ಪರಿಸರ ಚರವಾಗಿಯೂ ಫಾರ್ವರ್ಡ್ ಮಾಡುತ್ತದೆ.

### ಪೂರ್ವ-ಬಿಲ್ಡ್ ಮಾಡಿದ ರೂಟ್ ಇಮೇಜ್ + ರನ್ಟೈಮ್ ಉಪಮಾರ್ಗ

ಪ್ರಕಟಿಸಲಾದ `diegosouzapw/omniroute:*` ಇಮೇಜ್ಗಳನ್ನು ಡೊಮೇನ್ ರೂಟ್ಗಾಗಿ ಬಿಲ್ಡ್ ಮಾಡಲಾಗಿದೆ. ಆದರೂ ನೀವು ರನ್ಟೈಮ್ನಲ್ಲಿ `OMNIROUTE_BASE_PATH` ಅನ್ನು ಹೊಂದಿಸಬಹುದು; ಕಂಟೇನರ್ ಪ್ರಾರಂಭದ ವೇಳೆ ಬಂಡಲ್ ಅನ್ನು ಒಮ್ಮೆ ಪ್ಯಾಚ್ ಮಾಡುತ್ತದೆ. ಅದನ್ನು ಹೊಂದಾಣಿಕೆಯ ಸಾರ್ವಜನಿಕ ಮೂಲದೊಂದಿಗೆ ಜೋಡಿಸಿ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

**ಸಂಪೂರ್ಣ** ಬಾಹ್ಯ ಮಾರ್ಗವನ್ನು ಫಾರ್ವರ್ಡ್ ಮಾಡುವಂತೆ ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿಯನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿ (ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ತೆಗೆದುಹಾಕಬೇಡಿ). Traefik, `StripPrefix` ಇಲ್ಲದೆ `PathPrefix(`/omniroute`)` ಅನ್ನು ಕಂಟೇನರ್ಗೆ ರೂಟ್ ಮಾಡಬೇಕು, ಇದರಿಂದ Next.js `/omniroute/...` ಅನ್ನು ಸ್ವೀಕರಿಸಿ `/omniroute/_next/...` ನಿಂದ ಅಸೆಟ್ಗಳನ್ನು ಪೂರೈಸುತ್ತದೆ.

Docker ಹೆಲ್ತ್ಚೆಕ್, ಸಕ್ರಿಯ `OMNIROUTE_BASE_PATH` ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿರುವ ಹಗುರವಾದ `/healthz` ಲೈಫ್ಸೈಕಲ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಪರೀಕ್ಷಿಸುತ್ತದೆ. ಮಾನವ/ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಸ್ಗಾಗಿ `/api/monitoring/health` ಲಭ್ಯವಾಗಿಯೇ ಇರುತ್ತದೆ; ಕಂಟೇನರ್ HEALTHCHECK ಅನ್ನು ಮತ್ತೆ ಅದರತ್ತ ತೋರಿಸಲು (ಉದಾಹರಣೆಗೆ, ಆಳವಾದ ಆರೋಗ್ಯ ಜಾರಿಗಾಗಿ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ಅನ್ನು ಹೊಂದಿಸಿ. ಆ ಮಾರ್ಗವು **ಆಳವಾದ** ಪರಿಶೀಲನೆಯಾಗಿದೆ (DB + ಮಾನಿಟರಿಂಗ್ ಸಾರಾಂಶ) — ನೀವು ಅದನ್ನು ಮತ್ತೆ ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡರೆ Docker ನ ವಿರಳವಾದ `HEALTHCHECK` ಗೆ ಸೂಕ್ತವಾಗಿದೆ, ಆದರೆ Kubernetes `livenessProbe` ಮಧ್ಯಂತರಗಳಿಗೆ **ಸೂಕ್ತವಲ್ಲ**.

ಆರ್ಕೆಸ್ಟ್ರೇಟರ್ಗಳಿಗಾಗಿ (Kubernetes, Nomad, ಇತ್ಯಾದಿ):

| ಪ್ರೋಬ್                 | ಆದ್ಯತೆ ನೀಡಿ                                                              | ತಪ್ಪಿಸಿ                                                                   |
| ---------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| ಲೈವ್ನೆಸ್               | HTTP `GET /livez`, ಅಥವಾ ಮುಖ್ಯ ಪೋರ್ಟ್ನಲ್ಲಿ TCP (`PORT`, ಡೀಫಾಲ್ಟ್ `20128`) | ಲೈವ್ನೆಸ್ ಆಗಿ `/api/monitoring/health`                                     |
| ರೆಡಿನೆಸ್               | HTTP `GET /healthz`                                                      | ಈವೆಂಟ್-ಲೂಪ್ ಕಾರ್ಯನಿರತವಾಗಿರುವುದನ್ನು ಸ್ಥಗಿತವೆಂದು ಪರಿಗಣಿಸುವ ಕಡಿಮೆ ಟೈಮ್ಔಟ್ಗಳು |
| ಆಳವಾದ / ಬ್ಲ್ಯಾಕ್ಬಾಕ್ಸ್ | `/api/monitoring/health`                                                 | —                                                                         |

`/healthz` ಪ್ರಕ್ರಿಯೆಯ ಲೈಫ್ಸೈಕಲ್ ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ (`ok` / `starting` / `stopping`). `/livez` ಪ್ರಕ್ರಿಯೆಯು ಚಾಲನೆಯಲ್ಲಿದೆಯೇ ಎಂಬುದನ್ನು ಮಾತ್ರ ಪರಿಶೀಲಿಸುತ್ತದೆ (ಹ್ಯಾಂಡ್ಲರ್ ರನ್ ಆಗಬಹುದಾದಾಗಲೆಲ್ಲಾ 200; ಇದು ರೆಡಿನೆಸ್ಗಾಗಿ ಕಾಯುವುದಿಲ್ಲ). ಇವೆರಡೂ ಇನ್ನೂ ವಿನಂತಿ ನಿರ್ವಹಣೆಯಂತೆಯೇ ಅದೇ Node ಈವೆಂಟ್ ಲೂಪ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತವೆ, ಆದ್ದರಿಂದ CPU-ಆಧಾರಿತ ಕ್ಯಾಟಲಾಗ್ ಅಥವಾ ಕಂಪ್ರೆಷನ್ ಕೆಲಸವು ಅವುಗಳನ್ನು ವಿಳಂಬಗೊಳಿಸಬಹುದು — ಕಾರ್ಯನಿರತ ≠ ಸ್ಥಗಿತ. HTTP ಪ್ರೋಬ್ಗಳು ಟೈಮ್ ಔಟ್ ಆದರೆ TCP ಲೈವ್ನೆಸ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ. ಸಂಪೂರ್ಣ ಪ್ರೋಬ್ ಮಾರ್ಗದರ್ಶನ:
[ಮಾನಿಟರಿಂಗ್ ಮಾರ್ಗದರ್ಶಿ — Kubernetes ಪ್ರೋಬ್ ಶಿಫಾರಸುಗಳು](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Caddy ಜೊತೆಗೆ Docker Compose (HTTPS Auto-TLS)

Caddyಯ ಸ್ವಯಂಚಾಲಿತ SSL ಒದಗಿಸುವಿಕೆಯನ್ನು ಬಳಸಿಕೊಂಡು OmniRoute ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ಬಹಿರಂಗಪಡಿಸಬಹುದು. ನಿಮ್ಮ ಡೊಮೇನ್ನ DNS A ದಾಖಲೆಯು ನಿಮ್ಮ ಸರ್ವರ್ನ IPಗೆ ಸೂಚಿಸುತ್ತಿದೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ.

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth ಕಾಲ್ಬ್ಯಾಕ್ಗಳು, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಲಿಂಕ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ ಸಾರ್ವಜನಿಕ URLಗಳಿಗಾಗಿ ಬ್ರೌಸರ್ ಎದುರಿಸುವ ಮೂಲ.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ನಿಗದಿತ ಕಾರ್ಯಗಳು / ಸ್ವಯಂ-ಫೆಚ್ಗಳಿಗಾಗಿ ಆಂತರಿಕ ಸರ್ವರ್-ಟು-ಸರ್ವರ್ URL.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

ಅಪ್ಸ್ಟ್ರೀಮ್ ಕಂಟೇನರ್ಗಾಗಿ Caddy ಪ್ರಮಾಣಿತ ಫಾರ್ವರ್ಡಿಂಗ್ ಹೆಡರ್ಗಳನ್ನು ಹೊಂದಿಸುತ್ತದೆ. OAuth ಕಾಲ್ಬ್ಯಾಕ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ ಸಾರ್ವಜನಿಕ
ಲಿಂಕ್ಗಳಿಗೆ OmniRoute `NEXT_PUBLIC_BASE_URL` ಅನ್ನು ಅಧಿಕೃತ ಸಾರ್ವಜನಿಕ ಮೂಲವಾಗಿ ಬಳಸುತ್ತದೆ;
ದೃಢೀಕೃತ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಬರಹಗಳು ಸೆಷನ್ಗೆ ಬದ್ಧವಾದ CSRF ರಕ್ಷಣೆಯೊಂದಿಗೆ ಅದೇ ಮೂಲದ ವಿನಂತಿಗಳನ್ನು
ಬಳಸುತ್ತವೆ. ಸ್ಪಷ್ಟ ಸಂರಚನೆಯ ಬದಲಿಗೆ ವಿಶ್ವಾಸಾರ್ಹ ಫಾರ್ವರ್ಡ್ ಮಾಡಿದ ಹೆಡರ್ಗಳಿಂದ ಸಾರ್ವಜನಿಕ ಮೂಲವನ್ನು
OmniRoute ಪಡೆದುಕೊಳ್ಳಬೇಕೆಂದು ನೀವು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಬಯಸುವ ಸುಧಾರಿತ ನಿಯೋಜನೆಗಳಿಗೆ ಮಾತ್ರ
`OMNIROUTE_TRUST_PROXY` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ.

## Cloudflare Quick Tunnel

Docker ನಿಯೋಜನೆಗಳ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಬೆಂಬಲವು `Dashboard → Endpoints`ನಲ್ಲಿ ಒಂದು-ಕ್ಲಿಕ್ **Cloudflare Quick Tunnel** ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಮೊದಲ ಬಾರಿಗೆ ಸಕ್ರಿಯಗೊಳಿಸಿದಾಗ, ಅಗತ್ಯವಿದ್ದರೆ ಮಾತ್ರ `cloudflared` ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ, ನಿಮ್ಮ ಪ್ರಸ್ತುತ `/v1` ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ತಾತ್ಕಾಲಿಕ ಟನಲ್ ಅನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತದೆ ಮತ್ತು ರಚಿಸಲಾದ `https://*.trycloudflare.com/v1` URL ಅನ್ನು ನಿಮ್ಮ ಸಾಮಾನ್ಯ ಸಾರ್ವಜನಿಕ URLನ ನೇರವಾಗಿ ಕೆಳಗೆ ತೋರಿಸುತ್ತದೆ.

ಸಕ್ರಿಯ ಟನಲ್ ಸ್ಥಿತಿಯನ್ನು ಬದಲಾಯಿಸದೆಯೇ ಎಂಡ್ಪಾಯಿಂಟ್ ಟನಲ್ ಫಲಕಗಳನ್ನು (Cloudflare, Tailscale, ngrok) `Settings → Appearance`ನಿಂದ ತೋರಿಸಬಹುದು ಅಥವಾ ಮರೆಮಾಡಬಹುದು.

### ಟನಲ್ ಟಿಪ್ಪಣಿಗಳು

- Quick Tunnel URLಗಳು ತಾತ್ಕಾಲಿಕವಾಗಿದ್ದು, ಪ್ರತಿ ಮರುಪ್ರಾರಂಭದ ನಂತರವೂ ಬದಲಾಗುತ್ತವೆ.
- OmniRoute ಅಥವಾ ಕಂಟೇನರ್ ಮರುಪ್ರಾರಂಭದ ನಂತರ Quick Tunnelಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮರುಸ್ಥಾಪನೆಯಾಗುವುದಿಲ್ಲ. ಅಗತ್ಯವಿದ್ದಾಗ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ ಅವುಗಳನ್ನು ಪುನಃ ಸಕ್ರಿಯಗೊಳಿಸಿ.
- ನಿರ್ವಹಿಸಲಾದ ಸ್ಥಾಪನೆಯು ಪ್ರಸ್ತುತ `x64` / `arm64`ನಲ್ಲಿನ Linux, macOS ಮತ್ತು Windows ಅನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ.
- ನಿರ್ಬಂಧಿತ ಕಂಟೇನರ್ ಪರಿಸರಗಳಲ್ಲಿ ಗದ್ದಲದ QUIC UDP ಬಫರ್ ಎಚ್ಚರಿಕೆಗಳನ್ನು ತಪ್ಪಿಸಲು, ನಿರ್ವಹಿಸಲಾದ Quick Tunnelಗಳು ಡೀಫಾಲ್ಟ್ ಆಗಿ HTTP/2 ಸಾರಿಗೆಯನ್ನು ಬಳಸುತ್ತವೆ. ನಿಮಗೆ ಬೇರೊಂದು ಸಾರಿಗೆ ಬೇಕಿದ್ದರೆ `CLOUDFLARED_PROTOCOL=quic` ಅಥವಾ `auto` ಹೊಂದಿಸಿ.
- Docker ಇಮೇಜ್ಗಳು ಸಿಸ್ಟಮ್ CA ರೂಟ್ಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತವೆ ಮತ್ತು ಅವುಗಳನ್ನು ನಿರ್ವಹಿಸಲಾದ `cloudflared`ಗೆ ರವಾನಿಸುತ್ತವೆ; ಇದರಿಂದ ಕಂಟೇನರ್ನೊಳಗೆ ಟನಲ್ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಆಗುವಾಗ TLS ವಿಶ್ವಾಸ ವೈಫಲ್ಯಗಳು ತಪ್ಪುತ್ತವೆ.
- OmniRoute ಡೌನ್ಲೋಡ್ ಮಾಡುವ ಬದಲಿಗೆ ಈಗಾಗಲೇ ಇರುವ ಬೈನರಿಯನ್ನು ಬಳಸಬೇಕೆಂದು ನೀವು ಬಯಸಿದರೆ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ಹೊಂದಿಸಿ.

## ಇಮೇಜ್ ಟ್ಯಾಗ್ಗಳು

| ಇಮೇಜ್                    | ಟ್ಯಾಗ್   | ಗಾತ್ರ  | ವಿವರಣೆ                                               |
| ------------------------ | -------- | ------ | ---------------------------------------------------- |
| `diegosouzapw/omniroute` | `latest` | ~250MB | ಅತ್ಯುನ್ನತ **ಪ್ರಕಟಿತ** ಸ್ಥಿರ SemVer (git `main` ಅಲ್ಲ) |
| `diegosouzapw/omniroute` | `3.8.0`  | ~250MB | GitOpsಗಾಗಿ ಈ ವರ್ಗದ ಟ್ಯಾಗ್ ಅನ್ನು ಸ್ಥಿರಗೊಳಿಸಿ          |

ಬಹು-ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಮ್ಯಾನಿಫೆಸ್ಟ್: `linux/amd64` + `linux/arm64` ನೇಟಿವ್ (Apple Silicon, AWS Graviton, Raspberry Pi). Docker ಹೊಂದಾಣಿಕೆಯಾಗುವ ಆರ್ಕಿಟೆಕ್ಚರ್ ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಆಯ್ಕೆಮಾಡುತ್ತದೆ; ARM ಹೋಸ್ಟ್ಗಳಲ್ಲಿ AMD64 ಎಮ್ಯುಲೇಶನ್ ಅನ್ನು ಬಲವಂತಗೊಳಿಸಬೇಕಾದರೆ `--platform linux/amd64` ಅನ್ನು ರವಾನಿಸಿ.

### ಬಿಡುಗಡೆ ಚಾನಲ್ಗಳು

ಸ್ಥಿರ ಬಿಡುಗಡೆಗಳು, ಸಕ್ರಿಯ ಬಿಡುಗಡೆ-ಬ್ರಾಂಚ್ ಪರೀಕ್ಷೆ ಮತ್ತು ಅಭಿವೃದ್ಧಿ ಬಿಲ್ಡ್ಗಳಿಗಾಗಿ OmniRoute ಪ್ರತ್ಯೇಕ Docker ಚಾನಲ್ಗಳನ್ನು ಪ್ರಕಟಿಸುತ್ತದೆ.

| ಚಾನಲ್                           | ಮೂಲ                                    | ಬದಲಾಯಿಸುವಿಕೆ                     | ಶಿಫಾರಸು ಮಾಡಿದ ಬಳಕೆ                                                                                                                  |
| ------------------------------- | -------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `:<version>` / `:<version>-web` | ಸಹಿ ಮಾಡಿದ/ಆವೃತ್ತಿಗೊಳಿಸಿದ ಬಿಡುಗಡೆ       | ಬದಲಾಯಿಸಲಾಗದ                      | ನಿಖರವಾದ ಬಿಡುಗಡೆಯನ್ನು ಸ್ಥಿರಗೊಳಿಸುವ ಪ್ರೊಡಕ್ಷನ್ ನಿಯೋಜನೆಗಳು                                                                             |
| `:latest` / `:latest-web`       | ಅತ್ಯುನ್ನತ **ಪ್ರಕಟಿತ** ಸ್ಥಿರ SemVer     | ಬದಲಾಯಿಸಬಹುದಾದ ಸ್ಥಿರ ಸೂಚಕ         | SemVer ಪ್ರಕಟಣೆ ಕಾರ್ಯದ **ನಂತರ** ಸ್ಥಿರ ಬಿಡುಗಡೆಗಳನ್ನು ಅನುಸರಿಸುತ್ತದೆ — `main` ಅಥವಾ ಬಿಡುಗಡೆಯಾಗದ `release/v*` ಕಮಿಟ್ಗಳನ್ನು ಅನುಸರಿಸುವುದಿಲ್ಲ |
| `:next` / `:next-web`           | ಪ್ರಸ್ತುತ ಡೀಫಾಲ್ಟ್ `release/v*` ಬ್ರಾಂಚ್ | ಬದಲಾಯಿಸಬಹುದಾದ ಪೂರ್ವ-ಬಿಡುಗಡೆ ಸೂಚಕ | ಸಕ್ರಿಯ ಬಿಡುಗಡೆ ಬ್ರಾಂಚ್ಗೆ ಸೇರಿಸಲಾದ, ಆದರೆ ಇನ್ನೂ ಸ್ಥಿರ ಬಿಡುಗಡೆಯಲ್ಲಿಲ್ಲದ ಪರಿಹಾರಗಳನ್ನು ಪರೀಕ್ಷಿಸುವುದು                                     |
| `:main` / `:main-web`           | `main` ಬ್ರಾಂಚ್                         | ಬದಲಾಯಿಸಬಹುದಾದ ಅಭಿವೃದ್ಧಿ ಸೂಚಕ     | ಅಭಿವೃದ್ಧಿ ಮತ್ತು ಏಕೀಕರಣ ಪರೀಕ್ಷೆಗೆ ಮಾತ್ರ                                                                                              |

#### ವೆಬ್-ಸೆಷನ್ ಪೂರೈಕೆದಾರರು: `-web` ಇಮೇಜ್ಗಳು

ಮೇಲಿನ ಪ್ರತಿಯೊಂದು ಚಾನಲ್ಗೂ `-web` ಟ್ಯಾಗ್ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ಸಹ ಇದೆ. ಇದನ್ನು `runner-web` ಹಂತದಿಂದ ನಿರ್ಮಿಸಲಾಗುತ್ತದೆ — ಅದೇ ಇಮೇಜ್ ಜೊತೆಗೆ Playwright ಮತ್ತು Chromium ಬ್ರೌಸರ್. ಸಾಮಾನ್ಯ ಇಮೇಜ್ Chromium **ಇಲ್ಲದೆ** ಬರುತ್ತದೆ; `gemini-web`, `claude-web` ಮತ್ತು `claude-turnstile`ಗೆ ಅದು ಅಗತ್ಯವಿದೆ.

ವೈಫಲ್ಯವು ಪ್ರಾರಂಭದ ಸಮಯದಲ್ಲಿ ಸಂಭವಿಸುವುದಿಲ್ಲ, ಬದಲಿಗೆ ಮುಂದೂಡಲ್ಪಡುತ್ತದೆ: ಆ ಪೂರೈಕೆದಾರರು ತಮ್ಮ ಮಾದರಿಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತಾರೆ ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಸಂಪರ್ಕಗೊಂಡಂತೆ ಕಾಣಿಸುತ್ತಾರೆ; ಮೊದಲ ವಿನಂತಿ ಮಾತ್ರ ಈ ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

```
[500]: ಬಾಹ್ಯ ಮಾಡ್ಯೂಲ್ playwright ಅನ್ನು ಲೋಡ್ ಮಾಡಲು ವಿಫಲವಾಗಿದೆ: ದೋಷ: ಮಾಡ್ಯೂಲ್ ಕಂಡುಬಂದಿಲ್ಲ
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ನೀವು ಆ ಪೂರೈಕೆದಾರರನ್ನು ಬಳಸುತ್ತಿದ್ದರೆ, ನೀವು ಈಗಾಗಲೇ ಬಳಸುತ್ತಿರುವ ಚಾನಲ್ನ `-web` ಟ್ಯಾಗ್ ಅನ್ನು ಪುಲ್ ಮಾಡಿ — ಬೇರೆ ಯಾವುದೂ ಬದಲಾಗುವುದಿಲ್ಲ. npm/CLI ಸ್ಥಾಪನೆಯಲ್ಲಿ (Docker ಇಮೇಜ್ ಇಲ್ಲದೆ), ಇದಕ್ಕೆ ಸಮಾನವಾದ ಕಾಣೆಯಾದ ಭಾಗವು ಬ್ರೌಸರ್ ಬೈನರಿಯಾಗಿದೆ: ಹೋಸ್ಟ್ನಲ್ಲಿ `npx playwright install chromium` ಅನ್ನು ರನ್ ಮಾಡಿ.

#### ಪೂರ್ವ-ಬಿಡುಗಡೆ ಚಾನಲ್ ಬಳಸುವುದು

ಪ್ರಸ್ತುತ ಡೀಫಾಲ್ಟ್ `release/v*` ಶಾಖೆಗೆ ಪ್ರತಿ push ಮಾಡಿದಾಗಲೂ `next` ಚಾನಲ್ ಅನ್ನು ಮರುನಿರ್ಮಿಸಲಾಗುತ್ತದೆ ಮತ್ತು AMD64 ಹಾಗೂ ARM64 ಎರಡಕ್ಕೂ ಪ್ರಕಟಿಸಲಾಗುತ್ತದೆ. ಹಳೆಯ ನಿರ್ವಹಣಾ ಶಾಖೆಗಳು ಅದನ್ನು ತಿದ್ದಿಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮುಂದಿನ ಸ್ಥಿರ tag ರಚಿಸುವುದಕ್ಕೂ ಮೊದಲು ಸಕ್ರಿಯ release ಶಾಖೆಗೆ merge ಮಾಡಲಾದ ಪರಿಹಾರಗಳಿಗಾಗಿ ಈ ಚಾನಲ್ pull ಮಾಡಬಹುದಾದ image ಅನ್ನು ಒದಗಿಸುತ್ತದೆ.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ಗಾಗಿ, ಆಯ್ಕೆಮಾಡಿದ profile ಬಳಸುವ image tag ಅನ್ನು ಅತಿಕ್ರಮಿಸಿ, ನಂತರ service ಅನ್ನು pull ಮಾಡಿ ಮರುಸೃಷ್ಟಿಸಿ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ಸುರಕ್ಷತೆ ಮತ್ತು ಹಿಂದಿರುಗಿಸುವಿಕೆ

`next` ಒಂದು ಬದಲಾಗುತ್ತಲೇ ಇರುವ ಪೂರ್ವ-ಬಿಡುಗಡೆ ಚಾನಲ್ ಆಗಿದೆ. ಸಕ್ರಿಯ release ಶಾಖೆಗೆ ಯಾವುದೇ push ಮಾಡಿದಾಗ ಇದು ಬದಲಾಗಬಹುದು ಮತ್ತು ಇದನ್ನು **production ಬಳಕೆಗಾಗಿ ಬೆಂಬಲಿಸಲಾಗುವುದಿಲ್ಲ**. ನಿರ್ದಿಷ್ಟ build ಅನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡುವಾಗ image digest ಅನ್ನು pin ಮಾಡಿ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ಪರೀಕ್ಷಿಸುವ ಮೊದಲು, OmniRoute data volume ಅಥವಾ bind-mounted data directory ಅನ್ನು backup ಮಾಡಿ. ಹಿಂದಿರುಗಿಸಲು, ಈ ಹಿಂದೆ ಬಳಸಿದ ಸ್ಥಿರ version ಅಥವಾ digest ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ ಮತ್ತು container ಅನ್ನು ಮರುಸೃಷ್ಟಿಸಿ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

release ಶಾಖೆಯ build ಎಂದಿಗೂ `latest` ಅನ್ನು ಬದಲಾಯಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ; ಅರ್ಹವಾದ ಸ್ಥಿರ semantic version ಮಾತ್ರ ಸ್ಥಿರ pointer ಅನ್ನು ಮುನ್ನಡೆಸಬಹುದು. `next` images, release image ಪರಿಶೀಲನೆ ಮತ್ತು CRITICAL ದುರ್ಬಲತೆಗಳನ್ನು ನಿರ್ಬಂಧಿಸುವ gate ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

**`latest` ಎಂಬುದು git ನಲ್ಲಿನ ನವೀನತೆಗೆ ಖಾತರಿಯಲ್ಲ.** `main` ಅಥವಾ ಸಕ್ರಿಯ `release/v*` ಶಾಖೆಯಲ್ಲಿ merge ಮಾಡಲಾದ ಪರಿಹಾರಗಳು, ಸ್ಥಿರ SemVer image ಅನ್ನು ಪ್ರಕಟಿಸಿ publish job `:latest` ಅನ್ನು ಮುನ್ನಡೆಸುವವರೆಗೆ (ಆ SemVer ನಂತೆಯೇ ಅದೇ digest) `:latest` ನಲ್ಲಿ ಇರುವುದಿಲ್ಲ. GitHub ನಲ್ಲಿ ಪರಿಹಾರವು ಈಗಾಗಲೇ ಕಾಣಿಸುತ್ತಿದ್ದರೂ `latest` ಸ್ಥಗಿತಗೊಂಡಂತೆ ಕಂಡುಬಂದರೆ, release ಶಾಖೆಯನ್ನು ಪರೀಕ್ಷಿಸಲು `:next` ಅನ್ನು pull ಮಾಡಿ ಅಥವಾ SemVer tag ಗಾಗಿ ಕಾಯಿರಿ.

| ನಿಮಗೆ ಬೇಕಾಗಿರುವುದು                                                                           | ಬಳಸಿ                                              |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| ಬದಲಾಗಬಾರದ GitOps / production                                                                | `:X.Y.Z` ಅನ್ನು pin ಮಾಡಿ (ಅಥವಾ image digest ಅನ್ನು) |
| ಪ್ರಕಟಿತ ಸ್ಥಿರ ಬಿಡುಗಡೆಗಳನ್ನು ಅನುಸರಿಸಿ ಮತ್ತು ಪ್ರತಿ ಬಿಡುಗಡೆಯಲ್ಲೂ ಮರುಸೃಷ್ಟಿಸುವುದನ್ನು ಒಪ್ಪಿಕೊಳ್ಳಿ | `:latest`                                         |
| ಬಿಡುಗಡೆಯಾಗದ `release/v*` commits ಅನ್ನು ಪರೀಕ್ಷಿಸಿ                                             | `:next` (production ಗಾಗಿ ಅಲ್ಲ)                    |
| `main` ಅನ್ನು ಪರೀಕ್ಷಿಸಿ                                                                       | `:main` (production ಗಾಗಿ ಅಲ್ಲ)                    |

## ಲಭ್ಯತೆ: ಡೀಫಾಲ್ಟ್ SQLite ಏಕ-ಪ್ರತಿರೂಪವಾಗಿದೆ

ಪ್ರಮಾಣಿತ Docker / Kubernetes OmniRoute ವಿನ್ಯಾಸವು **ಒಂದು Node ಪ್ರಕ್ರಿಯೆ + ಒಂದು SQLite ರೈಟರ್** ಆಗಿದೆ. ಈ ಟೊಪಾಲಜಿಯಲ್ಲಿ ಹೆಚ್ಚಿನ ಲಭ್ಯತೆ **ಬೆಂಬಲಿತವಾಗಿಲ್ಲ**.

| ನಿರ್ಬಂಧ                                   | ಪರಿಣಾಮ                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಏಕ ರೈಟರ್                                  | ಒಂದೇ SQLite ಫೈಲ್ ವಿರುದ್ಧ ಹಲವಾರು ಪ್ರತಿರೂಪಗಳನ್ನು **ಚಲಾಯಿಸಬೇಡಿ**. ಅದು DB ಅನ್ನು ಹಾಳುಮಾಡುತ್ತದೆ.                                                                                                                                                                                                                                                                        |
| ಮರುರಚನೆ / ಮರುಪ್ರಾರಂಭ / HEALTHCHECK ಸ್ಥಗಿತ | ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿರುವ SSE, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್ಗಳು ಮತ್ತು ಇನ್-ಮೆಮೊರಿ ಸ್ಥಿತಿಯ **ಸಂಪೂರ್ಣ ಸ್ಥಗಿತ**. ಸಂಪರ್ಕಿತ ಪ್ರತಿಯೊಂದು ಕ್ಲೈಂಟ್ನ ಸಂಪರ್ಕ ಕಡಿತಗೊಳ್ಳುತ್ತದೆ. ಎಂಡ್ಪಾಯಿಂಟ್ ಖಾಲಿಯಾಗಿರುವ ಅವಧಿಯಲ್ಲಿ ಹೊಸ ವಿನಂತಿಗಳು OmniRoute JSON ಬದಲಿಗೆ ರಿವರ್ಸ್-ಪ್ರಾಕ್ಸಿ **`502 Bad Gateway: Unknown error`** ಪಡೆಯುತ್ತವೆ — ಕ್ಲೈಂಟ್ಗಳು ಇದನ್ನು ಪೂರೈಕೆದಾರರ ವೈಫಲ್ಯದಿಂದ ಪ್ರತ್ಯೇಕಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ (#11015). |
| `/healthz` ನಂತೆಯೇ ಅದೇ ಈವೆಂಟ್ ಲೂಪ್         | ಕಾರ್ಯನಿರತ ಕ್ಯಾಟಲಾಗ್ ಅಥವಾ ಕಂಪ್ರೆಷನ್ ಟಿಕ್ ಪ್ರೋಬ್ಗಳನ್ನು ವಿಳಂಬಗೊಳಿಸಬಹುದು; ಆಗ ಕಡಿಮೆ ಟೈಮ್ಔಟ್ **ಏಕೈಕ** ಪ್ರತಿರೂಪವನ್ನು ಮರುಪ್ರಾರಂಭಿಸುತ್ತದೆ.                                                                                                                                                                                                                                 |

**ಪ್ರೋಬ್ ಮ್ಯಾಟ್ರಿಕ್ಸ್** ([Kubernetes ಪ್ರೋಬ್ ಶಿಫಾರಸುಗಳು](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations) ಸಹ ನೋಡಿ):

| ಪ್ರೋಬ್        | ಗುರಿ                                                             | ಬಳಸಬೇಡಿ                                                                   |
| ------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------- |
| ಲೈವ್ನೆಸ್      | `PORT` ನಲ್ಲಿ TCP (ಡೀಫಾಲ್ಟ್ `20128`), ಅಥವಾ ಸಾಫ್ಟ್ HTTP `/healthz` | `/api/monitoring/health`                                                  |
| ರೆಡಿನೆಸ್      | HTTP `GET /healthz`                                              | ಈವೆಂಟ್ ಲೂಪ್ ಕಾರ್ಯನಿರತವಾಗಿರುವುದನ್ನು ಸ್ಥಗಿತವೆಂದು ಪರಿಗಣಿಸುವ ಕಡಿಮೆ ಟೈಮ್ಔಟ್ಗಳು |
| ಡೀಪ್ / ಮಾನವರು | `/api/monitoring/health`                                         | ಸ್ವಯಂಚಾಲಿತ kubelet ಲೈವ್ನೆಸ್                                               |

**ಅಪ್ಗ್ರೇಡ್ಗಳು:** ಪ್ರತಿಯೊಂದು ಸೆಷನ್ನ ಸಂಪರ್ಕ ಕಡಿತಗೊಳ್ಳುತ್ತದೆ ಎಂದು ನಿರೀಕ್ಷಿಸಿ. ಸಾಧ್ಯವಾದರೆ ಕ್ಲೈಂಟ್ಗಳನ್ನು ಡ್ರೇನ್ ಮಾಡಿ; ಡೀಫಾಲ್ಟ್ SQLite ನಲ್ಲಿ ರೋಲಿಂಗ್ ಅಪ್ಡೇಟ್ ಇಲ್ಲ. Compose `restart: unless-stopped` ಜೊತೆಗೆ Docker `HEALTHCHECK` ಕೂಡ ಕಂಟೇನರ್ Unhealthy ಆದಾಗ ಏಕೈಕ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ — ಪರಿಣಾಮದ ವ್ಯಾಪ್ತಿಯೂ ಅದೇ ಆಗಿರುತ್ತದೆ.

**ಏಕ ಪ್ರತಿರೂಪಕ್ಕಾಗಿ** Kubernetes ಸ್ನಿಪೆಟ್ (Recreate ಅಗತ್ಯವಿದೆ; ಒಂದೇ SQLite ಫೈಲ್ ವಿರುದ್ಧ `replicas` ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸಬೇಡಿ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` ಸ್ಲೀಪ್ SIGTERM ಗೆ ಮೊದಲು Service ಎಂಡ್ಪಾಯಿಂಟ್ಗಳನ್ನು ತೆಗೆದುಹಾಕಲು kube ಗೆ ಅವಕಾಶ ನೀಡುತ್ತದೆ; ಹೀಗಾಗಿ **ಹೊಸ** ಟ್ರಾಫಿಕ್ ಸ್ಥಗಿತಗೊಳ್ಳುತ್ತಿರುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ತಲುಪುವುದು ನಿಲ್ಲುತ್ತದೆ. ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿರುವ `/v1/responses` SSE ಅನ್ನು ಹೆವಿವೇಯ್ಟ್ ಅಡ್ಮಿಷನ್ ಲೀಸ್ಗಳ ಮೂಲಕ `SHUTDOWN_TIMEOUT_MS` ವರೆಗೆ (ಡೀಫಾಲ್ಟ್ 30s) ಡ್ರೇನ್ ಮಾಡಲಾಗುತ್ತದೆ (#11015). ಇನ್ನೂ ಪ್ರಕ್ರಿಯೆಯನ್ನು ತಲುಪುವ ಹೊಸ ವಿನಂತಿಗಳು `503` + `Retry-After: 5` ಪಡೆಯುತ್ತವೆ. ಬದಲಿ ಪ್ರತಿರೂಪ Ready ಆಗುವವರೆಗಿನ Recreate ಖಾಲಿ-ಎಂಡ್ಪಾಯಿಂಟ್ ಅಂತರವು ಸಂಪೂರ್ಣ ಸ್ಥಗಿತವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ — ಅದು SQLite ಟೊಪಾಲಜಿ, ಪ್ರೋಬ್ನ ತಪ್ಪು ಕಾನ್ಫಿಗರೇಶನ್ ಅಲ್ಲ.

ಬಾಹ್ಯ Postgres / ಮಲ್ಟಿ-ರೈಟರ್ HA ಒಂದು ದಾಖಲಿಸಲಾದ ಪ್ರಮಾಣಿತ ಮಾರ್ಗ **ಅಲ್ಲ**. ನಿಮಗೆ HA ಅಗತ್ಯವಿದ್ದರೆ, ಏಕ ಪ್ರತಿರೂಪವನ್ನೇ ಇರಿಸಿಕೊಳ್ಳಿ ಅಥವಾ ಪ್ರಾಜೆಕ್ಟ್ ಪ್ರತ್ಯೇಕವಾಗಿ ಪರೀಕ್ಷಿಸಿ ದಾಖಲಿಸಿರುವ ಟೊಪಾಲಜಿಯನ್ನು ಚಲಾಯಿಸಿ. Postgres/MySQL ಕೆಲಸವು [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ರಲ್ಲಿದೆ. ಅದು ಬಿಡುಗಡೆಯಾಗುವವರೆಗೆ, **ದೊಡ್ಡ** `/v1/responses` ಸಾಮರ್ಥ್ಯವನ್ನು ಹೆಚ್ಚಿಸಲು ಬೆಂಬಲಿತವಾದ ಏಕೈಕ ವಿಧಾನವೆಂದರೆ N ಸ್ವತಂತ್ರ ಪ್ರಕ್ರಿಯೆಗಳು (ಮುಂದಿನ ವಿಭಾಗ), ಒಂದೇ ವಾಲ್ಯೂಮ್ನಲ್ಲಿ `replicas > 1` ಅಲ್ಲ.

## ಸ್ಕೇಲ್-ಔಟ್: N ಸ್ವತಂತ್ರ ಪ್ರಕ್ರಿಯೆಗಳು

ಒಂದು Node ಪ್ರಕ್ರಿಯೆಯು **ಒಂದು V8 ಹೀಪ್** ಆಗಿದೆ. ಪರಸ್ಪರ ಅತಿಕ್ರಮಿಸುವ ಎರಡು ~3 MiB / ~750k-ಟೋಕನ್ ಕೋಡಿಂಗ್-ಏಜೆಂಟ್ `POST /v1/responses` (RTK + Caveman) ವಿನಂತಿಗಳು ~12 Gi ತಲುಪಿದಾಗ ಆ ಹೀಪ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತವೆ (`FATAL ERROR: Reached heap limit`) ಮತ್ತು 16 Gi cgroup ನಲ್ಲಿ OOM ಉಂಟುಮಾಡಬಹುದು. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ನೋಡಿ. ಆ ಮಾಪನವು **ಮೆಮೊರಿ-ಬಜೆಟ್** ಎಚ್ಚರಿಕೆಯಾಗಿದೆ; ಏಕಕಾಲೀನ ದೀರ್ಘ `/v1/responses` ವಿನಂತಿಗಳಿಗೆ ಉತ್ಪನ್ನದ ಗರಿಷ್ಠ ಮಿತಿ ಎರಡು ಎಂದಲ್ಲ. ಹೆವಿವೇಟ್ ಚಾಟ್ ಪ್ರವೇಶವನ್ನು, ಅದೇ V8/cgroup ಮಿತಿಯಿಂದ ಗಾತ್ರವನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನಿರ್ಧರಿಸುವ ಇನ್ಜೆಸ್ಟ್ ಬೈಟ್ ಬಜೆಟ್ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ನಿಯಂತ್ರಿಸುತ್ತದೆ — ಈಗಾಗಲೇ ಗಾತ್ರ ನಿಗದಿಪಡಿಸಿದ ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿ ಅದನ್ನು ಮೇಲ್ಮುಖವಾಗಿ ಅತಿಕ್ರಮಿಸುವುದು (ಅಥವಾ ಹಳೆಯ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ವಿನಂತಿ-ಎಣಿಕೆ ಮಿತಿಯನ್ನು ಹೊಂದಿಸುವುದು) ಮತ್ತೆ ಸ್ಥಗಿತವನ್ನು ಉಂಟುಮಾಡುತ್ತದೆ. ಸಣ್ಣ ಚಾಟ್ಗಳು, `/healthz`, `/v1/models`, ಮತ್ತು MCP ಆ ಮಿತಿಯಲ್ಲಿ **ಸೇರುವುದಿಲ್ಲ**.

### ಏಕ-ಪ್ರಕ್ರಿಯೆ: ಎರಡಕ್ಕಿಂತ ಹೆಚ್ಚು ದೀರ್ಘ `/v1/responses`

ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪಿ ಇನ್ಫ್ಲೈಟ್-ಬೈಟ್ ಬಜೆಟ್ನಲ್ಲಿ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ಇನ್ನೂ ಸ್ಥಳವಿದ್ದರೆ, **ಆರೋಗ್ಯಕರ** ಪ್ರಕ್ರಿಯೆಯು (`OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO` ಗಿಂತ ಕೆಳಗಿನ ಹೀಪ್, ಡೀಫಾಲ್ಟ್ `0.75`) ಎರಡಕ್ಕಿಂತ ಹೆಚ್ಚು ಏಕಕಾಲೀನ ದೀರ್ಘ `POST /v1/responses` ವಿನಂತಿಗಳನ್ನು ಚಲಾಯಿಸ**ಬಹುದು**. `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (ಡೀಫಾಲ್ಟ್ 256 KiB) ಅಥವಾ ಅದಕ್ಕಿಂತ ಹೆಚ್ಚಿನ ಗಾತ್ರದ ಬಾಡಿಗಳು, ರಚನೆ-ಭಾರಿತ ವಿನಂತಿಗಳಂತೆಯೇ ಅದೇ ಹೆವಿವೇಟ್ ಲೀಸ್ ಅನ್ನು ಪಡೆಯುತ್ತವೆ ಮತ್ತು ಅದೇ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` ವಿನಾಯಿತಿಯನ್ನು (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ಬಳಸುತ್ತವೆ. ಏಕಕಾಲೀನವಾಗಿ ಹತ್ತಾರು ದೀರ್ಘ SSE ಕ್ಲೈಂಟ್ಗಳನ್ನು ಚಲಾಯಿಸುವುದು (ಆಪರೇಟರ್ಗಳಿಗೆ ಸಾಮಾನ್ಯವಾಗಿ 40–50 ಅಗತ್ಯವಿರುತ್ತದೆ) ಒಂದು **ಮೆಮೊರಿ-ಬಜೆಟ್** ಪ್ರಶ್ನೆಯಾಗಿದೆ — ಹೀಪ್ + ಪ್ರಾಥಮಿಕ/ಹೆಡ್ರೂಮ್ ಸ್ಲಾಟ್ಗಳು + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ಗೆ ತಕ್ಕಂತೆ ಗಾತ್ರ ನಿಗದಿಪಡಿಸಿ — ಇದು ಉತ್ಪನ್ನದ ಕಠಿಣ “ಗರಿಷ್ಠ 2” ಮಿತಿಯಲ್ಲ. ಒತ್ತಡದಲ್ಲಿರುವ ಹೀಪ್ ಇನ್ನೂ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಮೂಲಕ ಲೋಡ್ ಅನ್ನು ತಗ್ಗಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ #7849 ಮರುಕಳಿಸುವುದಿಲ್ಲ.

**ಹೀಪ್ಗಳನ್ನು ಗುಣಿಸಲು** (ಸ್ವತಂತ್ರ V8 old-spaces) **ಪ್ರಸ್ತುತ**:

| ಮಾಡಿ                                                                                                                                                                  | ಮಾಡಬೇಡಿ                                                              |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **N ಕಂಟೇನರ್ಗಳು/ಪಾಡ್ಗಳನ್ನು** ಚಲಾಯಿಸಿ, ಪ್ರತಿಯೊಂದಕ್ಕೂ ಅದರ **ಸ್ವಂತ** `DATA_DIR` / ವಾಲ್ಯೂಮ್ ಇರಲಿ                                                                           | ಒಂದೇ SQLite ಫೈಲ್ಗಾಗಿ `replicas > 1` ಹೊಂದಿಸಬೇಡಿ                       |
| ಹೀಪ್ / ಇನ್ಫ್ಲೈಟ್-ಬೈಟ್ ಬಜೆಟ್ನಿಂದ ಹೆವಿ ಇನ್-ಫ್ಲೈಟ್ + ಆರೋಗ್ಯಕರ-ಹೆಡ್ರೂಮ್ ಗಾತ್ರವನ್ನು ನಿರ್ಧರಿಸಿ; 1–2 ಎಂಬುದು ಸಂಪ್ರದಾಯಬದ್ಧ #7849 ಡೀಫಾಲ್ಟ್ ಮಾತ್ರ, ಉತ್ಪನ್ನದ ಕಠಿಣ ಗರಿಷ್ಠ ಮಿತಿಯಲ್ಲ | ಒಂದು ಪ್ರಕ್ರಿಯೆಗೆ 8× RAM ಮತ್ತು ಮಿತಿಯಿಲ್ಲದ ಎಣಿಕೆ ಮಿತಿಯನ್ನು ನೀಡಬೇಡಿ     |
| ಐಚ್ಛಿಕ: **ಹಂಚಿಕೊಂಡ ಕೋಟಾ ಕೌಂಟರ್ಗಳಿಗಾಗಿ** `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                          | Redis ಅನ್ನು ಹಂಚಿಕೊಂಡ SQLite ಎಂದು ಪರಿಗಣಿಸಬೇಡಿ — ಅದು ಹಾಗಲ್ಲ            |
| ಪ್ರತಿ ಇನ್ಸ್ಟೆನ್ಸ್ಗೆ ಪ್ರೊವೈಡರ್ ರಹಸ್ಯಗಳನ್ನು ನಕಲಿಸಿ (ಅಥವಾ ವಿಭಜಿತ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳನ್ನು ಒಪ್ಪಿಕೊಳ್ಳಿ)                                                                         | ಇನ್ಸ್ಟೆನ್ಸ್ಗಳಾದ್ಯಂತ ಒಂದೇ ಡ್ಯಾಶ್ಬೋರ್ಡ್ / ಒಂದೇ ಕಾಲ್-ಲಾಗ್ ನಿರೀಕ್ಷಿಸಬೇಡಿ |
| ಯಾವುದೇ ಲೋಡ್ ಬ್ಯಾಲೆನ್ಸರ್ ಅನ್ನು ಮುಂಭಾಗದಲ್ಲಿ ಇರಿಸಿ; API ಕೀ ಅಥವಾ ಸೆಷನ್ ಆಧಾರಿತ ಸ್ಟಿಕ್ಕಿನೆಸ್ ಸಾಕಾಗುತ್ತದೆ                                                                    | ಮಾರಾಟಗಾರ-ನಿರ್ದಿಷ್ಟ ಗಾತ್ರ-ಅರಿವಿನ ಮಿಡಲ್ವೇರ್ ಅಗತ್ಯವೆಂದು ಭಾವಿಸಬೇಡಿ       |

ಹಾರ್ಡ್ವೇರ್: ಪ್ರತಿ ಇನ್ಸ್ಟೆನ್ಸ್ನ ಏಕಕಾಲೀನ ದೀರ್ಘ `/v1/responses` ಸಾಮರ್ಥ್ಯವು ಒಂದು **ಮೆಮೊರಿ-ಬಜೆಟ್** ಪ್ರಶ್ನೆಯಾಗಿದೆ (ಹೀಪ್ + ಇನ್ಫ್ಲೈಟ್-ಬೈಟ್ / #10110). `N` ಸ್ವತಂತ್ರ `DATA_DIR`ಗಳು ಇನ್ನೂ ಹೀಪ್ಗಳನ್ನು ಗುಣಿಸುತ್ತವೆ: ಹೋಸ್ಟ್ RAM, `N × cgroup` ಅನ್ನು ನಿಭಾಯಿಸಬೇಕು; “N=8 ಇರುವ ಒಂದು 16 Gi ಪಾಡ್” ಅನ್ನು ಅಲ್ಲ. ಒಂದೇ SQLite ಫೈಲ್ನಲ್ಲಿ ಎಂದಿಗೂ `replicas > 1` ಬಳಸಬೇಡಿ.

Compose ಮಾದರಿ (ಎರಡು ಹೀಪ್ಗಳು, ಎರಡು ವಾಲ್ಯೂಮ್ಗಳು — `deploy.replicas: 2` ಅಲ್ಲ):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

ಇನ್-ಪ್ರೊಸೆಸ್ ಸಾಂದ್ರತೆ (HTTP ಐಸೊಲೇಟ್ನಿಂದ ಹೊರಗಿರುವ ಕಂಪ್ರೆಷನ್) ಕುರಿತು [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023) ನೋಡಿ. ಹಂಚಿಕೊಂಡ ದೀರ್ಘಕಾಲಿಕ ಸ್ಥಿತಿಯ ಮೇಲಿನ ಒಂದು ತಾರ್ಕಿಕ ಕ್ಲಸ್ಟರ್ ಕುರಿತು [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075) ನೋಡಿ.

## Docker ಒಳಗಿನ Gemini ಪ್ರಾದೇಶಿಕ ದೋಷಗಳು

Google AI Studio / Gemini API, FAILED_PRECONDITION ಜೊತೆಗೆ HTTP 400 ಮತ್ತು
`User location is not supported for the API use.` ಅನ್ನು ಹಿಂತಿರುಗಿಸಬಹುದು. ಹೋಸ್ಟ್ನಲ್ಲಿ ವಿನಂತಿ ಯಶಸ್ವಿಯಾಗುವುದರಿಂದ
ಕಂಟೇನರ್ ಅದೇ ಔಟ್ಬೌಂಡ್ ಮಾರ್ಗವನ್ನು ಬಳಸುತ್ತದೆ ಎಂದು ಸಾಬೀತಾಗುವುದಿಲ್ಲ. DNS ಕ್ರಮ,
IPv4/IPv6 ಸಂಪರ್ಕ, VPN ರೂಟಿಂಗ್ ಮತ್ತು ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಪ್ರಾಕ್ಸಿಗಳು ಭಿನ್ನವಾಗಿರಬಹುದು.
[Google ಬೆಂಬಲಿಸುವ ಪ್ರದೇಶಗಳು](https://ai.google.dev/gemini-api/docs/available-regions)
ಹಾಗೂ ನಿಜವಾದ ಸಂಪರ್ಕ ಮಾರ್ಗವನ್ನು ಪರಿಶೀಲಿಸಿ; ಈ ದೋಷವೊಂದೇ API ಕೀ ಅಮಾನ್ಯವಾಗಿದೆ ಎಂದು ಸೂಚಿಸುವುದಿಲ್ಲ.

### ಸಂಪರ್ಕ-ನಿರ್ದಿಷ್ಟ ಪ್ರಾಕ್ಸಿಗೆ ಆದ್ಯತೆ ನೀಡಿ

ಪರಿಣಾಮಿತ Gemini ಸಂಪರ್ಕಕ್ಕಾಗಿ OmniRoute ನ [ಪ್ರತಿ-ಸಂಪರ್ಕದ ಪ್ರಾಕ್ಸಿ ಕಾನ್ಫಿಗರೇಶನ್](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ಅನ್ನು ಬಳಸಿ, ನಂತರ ಅದೇ ಮಾದರಿಯೊಂದಿಗೆ **ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸಿ** ಮತ್ತು ಒಂದು ಸಣ್ಣ ವಿನಂತಿಯನ್ನು
ಮತ್ತೆ ಪ್ರಯತ್ನಿಸಿ. ಇದರಿಂದ ರೂಟಿಂಗ್ ಬದಲಾವಣೆಯು ಆ ಸಂಪರ್ಕಕ್ಕೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿರುತ್ತದೆ. ಪ್ರಾಕ್ಸಿಯನ್ನು
ಕಂಟೇನರ್ನಿಂದ ತಲುಪಬಹುದು ಮತ್ತು ಸಂಪರ್ಕವು ನಿಜವಾಗಿಯೂ ಅದನ್ನೇ ಆಯ್ಕೆಮಾಡುತ್ತದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ.
ಮಾರ್ಗವನ್ನು ಬದಲಾಯಿಸುವುದರಿಂದ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರಾದೇಶಿಕ ಅರ್ಹತೆ ಖಚಿತವಾಗುವುದಿಲ್ಲ.

### ಹೋಸ್ಟ್ ಮತ್ತು ಕಂಟೇನರ್ ನೆಟ್ವರ್ಕಿಂಗ್ ಅನ್ನು ಹೋಲಿಸಿ

ದೃಢೀಕರಿಸಲಾದ ಫಲಿತಾಂಶಗಳನ್ನು ಹೋಲಿಸುವಾಗ ಕೀ, ಮಾದರಿ ಮತ್ತು ವಿನಂತಿಯನ್ನು ಒಂದೇ ರೀತಿಯಲ್ಲಿ ಇರಿಸಿ;
ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು, ಪ್ರಾಕ್ಸಿ ಪಾಸ್ವರ್ಡ್ಗಳು ಅಥವಾ ಸಂಪೂರ್ಣ ದೃಢೀಕರಣ ಹೆಡರ್ಗಳನ್ನು ಸಮಸ್ಯೆಯೊಂದರಲ್ಲಿ
ಎಂದಿಗೂ ಅಂಟಿಸಬೇಡಿ. ಮೊದಲು OS ರಿಸಾಲ್ವರ್ ಯಾವ ವಿಳಾಸ ಕುಟುಂಬಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ ಎಂಬುದನ್ನು,
ಹೋಸ್ಟ್ನಲ್ಲಿ ಮತ್ತು ಕಂಟೇನರ್ ಒಳಗೆ ಒಂದೇ ಕಮಾಂಡ್ ಬಳಸಿ ಪರಿಶೀಲಿಸಿ:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute` ಅನ್ನು ನೀವು ಚಲಾಯಿಸುವ ಸೇವೆಯ ಹೆಸರಿನಿಂದ ಬದಲಾಯಿಸಿ (ಉದಾಹರಣೆಗೆ, `omniroute-web`).
ಈ ಕಮಾಂಡ್ಗಳು ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು ಅಥವಾ IP ವಿಳಾಸಗಳಿಲ್ಲದೆ ವಿಳಾಸ ಕುಟುಂಬಗಳನ್ನು ಮುದ್ರಿಸುತ್ತವೆ.
ಹಿಂತಿರುಗಿಸಲಾದ `6` ಕೇವಲ IPv6 DNS ಫಲಿತಾಂಶವನ್ನು ತೋರಿಸುತ್ತದೆ: ಅದು ಬಳಸಬಹುದಾದ IPv6 ಮಾರ್ಗ
ಅಥವಾ API ಪ್ರವೇಶವನ್ನು ಸಾಬೀತುಪಡಿಸುವುದಿಲ್ಲ. `curl` ಸ್ಥಾಪಿತವಾಗಿರುವಲ್ಲಿ, ಎರಡೂ ಪರಿಸರಗಳಲ್ಲಿ
`curl -4 -I https://generativelanguage.googleapis.com` ಅನ್ನು
`curl -6 -I https://generativelanguage.googleapis.com` ಜೊತೆಗೆ ಹೋಲಿಸಿ.
HTTP ಪ್ರತಿಕ್ರಿಯೆಯು ದೃಢೀಕರಣವಿಲ್ಲದ ದೋಷವಾಗಿದ್ದರೂ ಸಹ, ಆ ಪ್ರೋಬ್ಗೆ ಸಂಪರ್ಕವಿದೆ ಎಂದು
ಸಾಬೀತುಪಡಿಸುತ್ತದೆ; ದೃಢೀಕರಿಸಲಾದ ಮಾದರಿ ವಿನಂತಿಯು ಮಾತ್ರ Gemini ಅರ್ಹತೆಯನ್ನು ಪರೀಕ್ಷಿಸುತ್ತದೆ.

### ಹೋಸ್ಟ್-ಮಟ್ಟದ ಪರ್ಯಾಯ: ಕಾರ್ಯನಿರ್ವಹಿಸುವ IPv6 ಮತ್ತು ರಿಸಾಲ್ವರ್ ನೀತಿ

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) ರ ವರದಿಗಾರರು
ತಮ್ಮ ಪರಿಸರದಲ್ಲಿ ಕಂಟೇನರ್ IPv6 ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ ಮತ್ತು glibc ವಿಳಾಸ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸುವ ಮೂಲಕ
ಪ್ರವೇಶವನ್ನು ಮರುಸ್ಥಾಪಿಸಿದರು. ಇದನ್ನು ಪರಿಸರ-ನಿರ್ದಿಷ್ಟ ಪರ್ಯಾಯವಾಗಿ ಪರಿಗಣಿಸಿ. ರಿಸಾಲ್ವರ್ ಆದ್ಯತೆಗಳನ್ನು
ಸರಿಹೊಂದಿಸುವ ಮೊದಲು ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಹೋಸ್ಟ್ IPv6, ಕಂಟೇನರ್ ಎಗ್ರೆಸ್/ರೂಟಿಂಗ್ ಮತ್ತು ಫೈರ್ವಾಲ್
ನಿಯಮಗಳನ್ನು ದೃಢೀಕರಿಸಿ. ಖಾಸಗಿ ULA ವಿಳಾಸವೊಂದೇ ಸಾರ್ವಜನಿಕ IPv6 ಸಂಪರ್ಕವನ್ನು ಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

ಈಗಾಗಲೇ Compose ನ ಡೀಫಾಲ್ಟ್ ನೆಟ್ವರ್ಕ್ಗೆ ಲಗತ್ತಿಸಲಾದ ಸೇವೆಗಳಿಗಾಗಿ, ಈ ತುಣುಕು ಆ ನೆಟ್ವರ್ಕ್ನಲ್ಲಿ
IPv6 ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ; ನಿಮ್ಮ ಸೇವೆ, ಪೋರ್ಟ್ಗಳು, ವಾಲ್ಯೂಮ್ಗಳು ಮತ್ತು ಕಾನ್ಫಿಗರೇಶನ್ನ
ಉಳಿದ ಭಾಗವನ್ನು ಹಾಗೆಯೇ ಉಳಿಸಿಕೊಳ್ಳಿ:

```yaml
networks:
  default:
    enable_ipv6: true
```

ಹೆಸರಿಸಲಾದ ನೆಟ್ವರ್ಕ್ಗಾಗಿ, ಸೇವೆಯು ನಿಜವಾಗಿ ಸೇರುವ ನೆಟ್ವರ್ಕ್ನಲ್ಲಿ ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ.
Docker ಒಂದು ULA ಸಬ್ನೆಟ್ ಅನ್ನು ಹಂಚಿಕೆ ಮಾಡಬಹುದು; ನಿಮ್ಮ ನೆಟ್ವರ್ಕ್ಗೆ ಅಗತ್ಯವಿದ್ದಾಗ ಮಾತ್ರ
ಸ್ಪಷ್ಟವಾದ, ಅತಿಕ್ರಮಿಸದ ಸಬ್ನೆಟ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ. [Docker IPv6 ನೆಟ್ವರ್ಕಿಂಗ್](https://docs.docker.com/engine/daemon/ipv6/)
ಮತ್ತು [Compose ನೆಟ್ವರ್ಕ್ ಆಯ್ಕೆಗಳು](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ನೋಡಿ.

**glibc-ಆಧಾರಿತ ಇಮೇಜ್ನಲ್ಲಿ**, `/etc/gai.conf` ವಿಳಾಸ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸಬಹುದು. ಪ್ರಸ್ತುತ
ರೆಪೊಸಿಟರಿಯ Dockerfile Debian ಅನ್ನು ಬಳಸುತ್ತದೆ; ಕಸ್ಟಮ್ musl-ಆಧಾರಿತ ಇಮೇಜ್ಗಳು ಈ ಕಾರ್ಯವಿಧಾನವನ್ನು
ಹಂಚಿಕೊಳ್ಳುವುದಿಲ್ಲ. ವರದಿ ಮಾಡಲಾದ ಹೊಂದಾಣಿಕೆಯು ULA ಲೇಬಲ್ ಅನ್ನು `label fc00::/7 6` ನಿಂದ
`label fc00::/7 1` ಗೆ ಬದಲಾಯಿಸುತ್ತದೆ. ಇಮೇಜ್ನ ಸಂಪೂರ್ಣ ನೀತಿ ಕೋಷ್ಟಕದಿಂದ ಪ್ರಾರಂಭಿಸಿ ಮತ್ತು ಅದರ
ಇತರ ನಮೂದುಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ: `label` ಅಥವಾ `precedence` ನಮೂದನ್ನು ಸೇರಿಸುವುದರಿಂದ ಆ ಡೀಫಾಲ್ಟ್
ಕೋಷ್ಟಕ ಬದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಬದಲಾಯಿಸಲಾದ ಸಾಲನ್ನು ಮಾತ್ರ ಹೊಂದಿರುವ ಫೈಲ್ ಸಾಕಾಗುವುದಿಲ್ಲ.
[glibc ಕಾನ್ಫಿಗರೇಶನ್ ಉಲ್ಲೇಖ](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ಆ ಶಬ್ದಾರ್ಥಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಪರಿಶೀಲಿಸಲಾದ ಫೈಲ್ ಅನ್ನು `/etc/gai.conf` ನಲ್ಲಿ ಓದಲು-ಮಾತ್ರವಾಗಿ
ಬೈಂಡ್-ಮೌಂಟ್ ಮಾಡಿ ಮತ್ತು ಅದನ್ನು ಅನ್ವಯಿಸಲು ಸೇವೆಯನ್ನು ಮರುರಚಿಸಿ.

ಇದು **ಆ ಕಂಟೇನರ್ನಲ್ಲಿನ ಎಲ್ಲಾ ಔಟ್ಬೌಂಡ್ ಟ್ರಾಫಿಕ್ಗೆ** OS ವಿಳಾಸ ಆಯ್ಕೆಯನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
ಇದು ಪ್ರತಿಯೊಂದು ಅಪ್ಲಿಕೇಶನ್ IPv6 ಅನ್ನು ಆಯ್ಕೆಮಾಡುವಂತೆ ಒತ್ತಾಯಿಸುವುದಿಲ್ಲ: Node ನ DNS ಕ್ರಮ ಮತ್ತು
ಸಂಪರ್ಕ ಆಯ್ಕೆಯೂ ಮುಖ್ಯವಾಗುತ್ತದೆ. ವಿಶೇಷವಾಗಿ, `--dns-result-order=ipv4first` IPv4 ಗೆ ಆದ್ಯತೆ
ನೀಡುತ್ತದೆ ಮತ್ತು IPv4-ಮಾತ್ರದ ವೈಫಲ್ಯಕ್ಕೆ ಪರಿಹಾರವಲ್ಲ. [Node DNS ಕ್ರಮ](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ನೋಡಿ.

ಯಾವುದೇ ಹೋಸ್ಟ್-ಮಟ್ಟದ ಬದಲಾವಣೆಯ ನಂತರ Gemini ಮತ್ತು ನಿಮ್ಮ ಇತರ ಪೂರೈಕೆದಾರರನ್ನು ಮರುಪರೀಕ್ಷಿಸಿ.
ಹಿಂದಕ್ಕೆ ಮರಳಿಸಲು, ಕಸ್ಟಮ್ `gai.conf` ಮೌಂಟ್ ಅನ್ನು ತೆಗೆದುಹಾಕಿ, ಹಿಂದಿನ ನೆಟ್ವರ್ಕ್
ಕಾನ್ಫಿಗರೇಶನ್ ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ ಮತ್ತು ನಿರ್ವಹಣಾ ಅವಧಿಯಲ್ಲಿ ಪರಿಣಾಮಿತ ಸೇವೆ/ನೆಟ್ವರ್ಕ್ ಅನ್ನು
ಮರುರಚಿಸಿ. ನೆಟ್ವರ್ಕ್ ಅನ್ನು ಮರುರಚಿಸುವುದರಿಂದ ಅದಕ್ಕೆ ಲಗತ್ತಿಸಲಾದ ಇತರ ಕಂಟೇನರ್ಗಳಿಗೆ ಅಡಚಣೆ
ಉಂಟಾಗಬಹುದು; ಶಾಶ್ವತ ಡೇಟಾ ವಾಲ್ಯೂಮ್ ಅನ್ನು ಅಳಿಸಬೇಡಿ.

## ಪ್ರಮುಖ ಟಿಪ್ಪಣಿಗಳು

- **SQLite WAL ಮೋಡ್:** OmniRoute ಇತ್ತೀಚಿನ ಬದಲಾವಣೆಗಳನ್ನು `storage.sqlite` ಗೆ ಚೆಕ್ಪಾಯಿಂಟ್ ಮಾಡಲು ಸಾಧ್ಯವಾಗುವಂತೆ `docker stop` ಪೂರ್ಣಗೊಳ್ಳಲು ಅವಕಾಶ ನೀಡಬೇಕು. ಜೊತೆಗೆ ನೀಡಲಾದ Compose ಫೈಲ್ಗಳು ಈಗಾಗಲೇ 40s ನಿಲುಗಡೆ ಗ್ರೇಸ್ ಅವಧಿಯನ್ನು ಹೊಂದಿಸಿವೆ. ನೀವು ಇಮೇಜ್ ಅನ್ನು ನೇರವಾಗಿ ರನ್ ಮಾಡಿದರೆ, `--stop-timeout 40` ಅನ್ನು ಹಾಗೆಯೇ ಇರಿಸಿ.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ನಿಯಮಿತ/ಬರೆಯುವಿಕೆ-ಪೂರ್ವ ಬ್ಯಾಕಪ್ಗಳನ್ನು ಬಾಹ್ಯವಾಗಿ ನಿರ್ವಹಿಸಲಾಗುತ್ತಿದ್ದರೆ, ಇದನ್ನು `true` ಗೆ ಹೊಂದಿಸಿ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಡೇಟಾಬೇಸ್ ಮೈಗ್ರೇಶನ್ಗಳಿಗೆ ಇನ್ನೂ ಅವುಗಳದೇ ಆದ ದೀರ್ಘಕಾಲಿಕ ಸುರಕ್ಷತಾ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಮತ್ತು ಸಾಮೂಹಿಕ-ಮೈಗ್ರೇಶನ್ ರಕ್ಷಣೆಯ ಅಗತ್ಯವಿರುತ್ತದೆ.
- **ಡೇಟಾ ಸ್ಥಿರತೆ:** ಕಂಟೇನರ್ ಮರುಪ್ರಾರಂಭಗಳ ನಡುವೆಯೂ ನಿಮ್ಮ ಡೇಟಾಬೇಸ್, ಕೀಗಳು ಮತ್ತು ಸಂರಚನೆಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲು ಯಾವಾಗಲೂ `/app/data` ಗೆ ವಾಲ್ಯೂಮ್ ಅನ್ನು ಮೌಂಟ್ ಮಾಡಿ.
- **ಪೋರ್ಟ್ ಸಂರಚನೆ:** ಡೀಫಾಲ್ಟ್ `20128` ಪೋರ್ಟ್ ಅನ್ನು ಬದಲಾಯಿಸಲು `PORT` ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ ಅನ್ನು ಓವರ್ರೈಡ್ ಮಾಡಿ.
