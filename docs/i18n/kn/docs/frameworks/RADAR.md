## ಸಾರ್ವಜನಿಕ ಪ್ರಕಟಣೆ ರೀಡರ್

ಸಾಮಾನ್ಯ ಪ್ರಕಟಣೆ ರೀಡರ್, Radar ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ನಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ Home ಮತ್ತು
Changelog ವೀಕ್ಷಕವು ಸರಳ `GET` ಮೂಲಕ ರೆಪೊಸಿಟರಿಯ ಸಾರ್ವಜನಿಕ `news.json` ಅನ್ನು
`NEWS_JSON_URL` ನಿಂದ ಪಡೆಯುತ್ತವೆ (`src/shared/utils/releaseNotes.ts`). ಅವು ಯಾವುದೇ Radar ಸೆಟ್ಟಿಂಗ್, ಪ್ರಾಂಪ್ಟ್, ಪ್ರೊವೈಡರ್
ಕಾನ್ಫಿಗರೇಶನ್, ಬಳಕೆಯ ದಾಖಲೆ ಅಥವಾ ಸ್ಥಳೀಯ ವಜಾಗೊಳಿಸುವಿಕೆಯ ಸ್ಥಿತಿಯನ್ನು ಕಳುಹಿಸುವುದಿಲ್ಲ.

`news.json`, `parseNewsPayload()` ಮೂಲಕ ಅಳವಡಿಸಲಾದ ಮುಚ್ಚಿದ v2 ಸ್ಕೀಮಾವನ್ನು ಬಳಸುತ್ತದೆ:

- `schemaVersion: 2` ಮತ್ತು ಮಿತಿಗೊಳಿಸಲಾದ `items[]` ಸಂಗ್ರಹ;
- ಸ್ಥಿರವಾದ, ಅನನ್ಯ ಪ್ರಕಟಣೆ `id` ಮೌಲ್ಯಗಳು;
- ಸ್ಪಷ್ಟವಾದ `active` ಮತ್ತು ISO `publishedAt` ಫೀಲ್ಡ್ಗಳು;
- ಐಚ್ಛಿಕ ಸ್ಥಳೀಕೃತ ಪಠ್ಯದೊಂದಿಗೆ ಕಡ್ಡಾಯ ಇಂಗ್ಲಿಷ್ ಪಠ್ಯ;
- ಐಚ್ಛಿಕ, ಕ್ರೆಡೆನ್ಷಿಯಲ್-ರಹಿತ HTTPS ಲಿಂಕ್ಗಳು ಮತ್ತು ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿರುವ ಐಕಾನ್;
- ಹೊಸದಾಗಿ ಸಕ್ರಿಯವಾಗಿರುವುದಕ್ಕೆ ಮೊದಲ ಆದ್ಯತೆಯ ಆಯ್ಕೆ, ಇಂಗ್ಲಿಷ್ಗೆ ಲೊಕೇಲ್ ಫಾಲ್ಬ್ಯಾಕ್ ಮತ್ತು ಪ್ರತಿ-ID ಸ್ಥಳೀಯ ವಜಾಗೊಳಿಸುವಿಕೆ.

ಹಳೆಯ ಫೋರ್ಕ್ಗಳು Changelog ವೀಕ್ಷಣೆಯನ್ನು ಹಾಳುಮಾಡದೆ ಮೈಗ್ರೇಟ್ ಆಗಲು, ಪಾರ್ಸರ್ ಹಿಂದಿನ ಏಕವಚನ
`{ active, title, message, ... }` ಸ್ವರೂಪವನ್ನು ತಾತ್ಕಾಲಿಕವಾಗಿ ಸ್ವೀಕರಿಸುತ್ತದೆ. ಅಮಾನ್ಯ ಫೀಡ್ಗಳು ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತವೆ. Radar ಪ್ರಾರಂಭ
ನಮೂದು `active: false` ಜೊತೆಗೆ ರವಾನೆಯಾಗುತ್ತದೆ; ಅದನ್ನು `true` ಗೆ ಬದಲಿಸುವುದು ಮರ್ಜ್ ನಂತರದ, ಡಿಪ್ಲಾಯ್ ನಂತರದ
ಪ್ರತ್ಯೇಕ ಬಿಡುಗಡೆ ಕ್ರಿಯೆಯಾಗಿದ್ದು, `RADAR_ENABLED` ಅಥವಾ ಸ್ವತಂತ್ರ ಫೀಡ್-ಸಿಂಕ್ ಆಯ್ಕೆಯನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ.

## ಫ್ಲ್ಯಾಗ್: `RADAR_ENABLED` (ಡೀಫಾಲ್ಟ್ ಆಗಿ ಆಫ್)

Radar ಅನ್ನು `RADAR_ENABLED` ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ ಮೂಲಕ ಆರಂಭದಿಂದ ಅಂತ್ಯದವರೆಗೆ ನಿಯಂತ್ರಿಸಲಾಗಿದೆ
(`src/shared/constants/featureFlagDefinitions.ts`, ವರ್ಗ `policies`,
`defaultValue: "false"`).

**ಫ್ಲ್ಯಾಗ್ ಆಫ್ ಆಗಿರುವಾಗ, ಈ ಮೇಲ್ಮೈ ಅಸ್ತಿತ್ವದಲ್ಲೇ ಇರುವುದಿಲ್ಲ:**

- ಸ್ಥಳೀಯ ಮಾಡೆಲ್-ಸ್ಥಿತಿ ಓದುವಿಕೆಗಳು ಮತ್ತು ಬರೆಯುವಿಕೆಗಳು ಸೇರಿದಂತೆ ಎಲ್ಲಾ `/api/radar/*` ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು,
  ಯಾವುದೇ Radar ಮಾಡ್ಯೂಲ್ ಅನ್ನು ಸ್ಪರ್ಶಿಸುವ ಮೊದಲು `404` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ.
- ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸ್ಕ್ರೀನ್ಗಳು (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`)
  `notFound()` ಅನ್ನು ರೆಂಡರ್ ಮಾಡುತ್ತವೆ.
- `getRadarCatalog()` (`src/lib/radar/index.ts`) ಯಾವುದೇ ಬದಲಾವಣೆ ಮಾಡದ ಬೇಸ್ಲೈನ್ ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ —
  ಅದೇ ನಮೂದುಗಳ ಸಂಖ್ಯೆ, ಅದೇ ಮೌಲ್ಯಗಳು, ಪ್ರತಿ ನಮೂದಿಗೂ `origin: "baseline"` ಟ್ಯಾಗ್ — ಮತ್ತು ಎಂದಿಗೂ
  ಫೀಡ್ ಕ್ಯಾಶ್ ಅನ್ನು ಓದುವುದಿಲ್ಲ.
- ಯಾವುದೇ Radar ನೆಟ್ವರ್ಕ್ ಕರೆ ಎಂದಿಗೂ ನಡೆಯುವುದಿಲ್ಲ; ಪ್ರತಿ ಸಿಂಕ್ ಮಾಡ್ಯೂಲ್ `fetch` ಅನ್ನು ಸ್ಪರ್ಶಿಸುವ
  ಮೊದಲು `{ status: "disabled" }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.

ಇದು ಕಟ್ಟುನಿಟ್ಟಾದ ಸೂಪರ್ಸೆಟ್ ಗೇಟ್ ಆಗಿದೆ: ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಆನ್ ಮಾಡುವುದರಿಂದ _ಸ್ಕ್ರೀನ್ಗಳು_ ಮಾತ್ರ
ಅನ್ಲಾಕ್ ಆಗುತ್ತವೆ, ಬೇರೇನೂ ಅಲ್ಲ. ಇದು ಡೇಟಾವನ್ನು ಅಪ್ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ, ಹಿನ್ನೆಲೆ ಸಿಂಕ್ ಅನ್ನು ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ ಮತ್ತು
ರೂಟಿಂಗ್ ಅಥವಾ ಮಾಡೆಲ್ ಆಯ್ಕೆಯನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ — ಕೆಳಗಿನ ಪ್ರತ್ಯೇಕ ಆಯ್ಕೆಯನ್ನು ನೋಡಿ.

## ಡೇಟಾ ಸಿಂಕ್ ಒಂದು ಪ್ರತ್ಯೇಕ ಆಯ್ಕೆ — ಗೌಪ್ಯತೆಯ ಭರವಸೆ

`RADAR_ENABLED` ಅನ್ನು ಆನ್ ಮಾಡುವುದರಿಂದ UI ಮಾತ್ರ ಅನ್ಲಾಕ್ ಆಗುತ್ತದೆ. ಫೀಡ್ ಅನ್ನು ಸಿಂಕ್ ಮಾಡಲು
`radar_settings.opt_in` ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುವ ಎರಡನೇ, ಸ್ವತಂತ್ರ ಆಯ್ಕೆಯ ಅಗತ್ಯವಿದೆ (`src/lib/db/radar.ts`,
ಮೈಗ್ರೇಶನ್ `136_radar_cache_settings.sql`). ಯಾವುದೇ ನೆಟ್ವರ್ಕ್ ಕರೆ ಮಾಡುವ ಮೊದಲು `syncRadar()` ಫ್ಲ್ಯಾಗ್
_ಮತ್ತು_ ಆಯ್ಕೆ ಎರಡನ್ನೂ ಪರಿಶೀಲಿಸುತ್ತದೆ:

```
Flag off      → { status: "disabled" }   — no network call
Opt-in false  → { status: "opt_out" }    — no network call
```

ಎರಡೂ ಆನ್ ಆಗಿರುವಾಗ, ಸಿಂಕ್ ಪಥವು ಹೀಗಿರುತ್ತದೆ:

1. `x-omniroute-radar-schema: 2` ಮತ್ತು ಐಚ್ಛಿಕ `Authorization: Bearer <supporter key>`
   ಹೆಡರ್ನೊಂದಿಗೆ `GET <feed base URL>/v1/catalog/latest` (ಕೆಳಗೆ ನೋಡಿ). ಸ್ಕೀಮಾ ಹೆಡರ್ ಇಲ್ಲದಿದ್ದಾಗ ಸರ್ವರ್ಗಳು
   ಪ್ರತ್ಯೇಕವಾಗಿ ಸಹಿ ಮಾಡಲಾದ v1 ಪರಿವರ್ತನಾ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗೆ ಡೀಫಾಲ್ಟ್ ಆಗುತ್ತವೆ, ಆದ್ದರಿಂದ ಹಿಂದೆ ಇನ್ಸ್ಟಾಲ್ ಮಾಡಲಾದ
   ಕ್ಲೈಂಟ್ಗಳು ಅಪ್ಡೇಟ್ಗಳನ್ನು ಪಡೆಯುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ.
2. ಇದು ಕೇವಲ ಡೌನ್ಲೋಡ್ ಮಾಡುವ ಅಪ್ಲಿಕೇಶನ್ ಫ್ಲೋ ಆಗಿದೆ, ಆದರೂ ಇದು HTTPS ವಿನಂತಿಯೇ ಆಗಿರುತ್ತದೆ. ಹೋಸ್ಟ್ ಮಾಡಿದ
   ಮೂಲಸೌಕರ್ಯವು ಮೂಲ IP ಮುಂತಾದ ಸಾಮಾನ್ಯ ಸಂಪರ್ಕ ಮೆಟಾಡೇಟಾವನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ. ಸಪೋರ್ಟರ್
   ಕೀ ಕಾನ್ಫಿಗರ್ ಆಗಿರುವಾಗ, ಅರ್ಹತೆಯನ್ನು ನಿರ್ಧರಿಸಲು ಸೇವೆಗೆ ಸಾಧ್ಯವಾಗುವಂತೆ ಸಿಂಕ್ ಆ ಕೀಯನ್ನು Bearer ಹೆಡರ್ನಲ್ಲಿಯೂ
   ಕಳುಹಿಸುತ್ತದೆ. ಮೇಲಿನ ಸಾಕ್ಷ್ಯದ ಮಿತಿಯಲ್ಲಿ ಗುರುತಿಸಲಾದ ನಿಖರ ಖಾಸಗಿ-ಸರ್ವರ್ ರಿವಿಷನ್ನಲ್ಲಿ,
   ಫೀಡ್-ವಿನಂತಿ ಲೆಕ್ಕಪತ್ರವು ಕೀ ಹ್ಯಾಶ್ಗಳು, ಒಟ್ಟು ಬಳಕೆ ಮತ್ತು ಹಸ್ತಚಾಲಿತ ದುರುಪಯೋಗ ಪರಿಶೀಲನೆಗಾಗಿ IP ಯ
   ಪ್ರತಿದಿನ ಬದಲಾಗುವ ಸಂಕ್ಷಿಪ್ತ HMAC ಅನ್ನು ಬಳಸುತ್ತದೆ; ಆ ಟೇಬಲ್ಗಳು ಕೀ ಅಥವಾ IP ಯನ್ನು ಮೂಲ ಸ್ವರೂಪದಲ್ಲಿ
   ಉಳಿಸಿಕೊಳ್ಳುವುದಿಲ್ಲ. ಮೂಲಸೌಕರ್ಯ ಪ್ರವೇಶ ಲಾಗ್ಗಳು ಮತ್ತು ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ವಿತರಣಾ ಔಟ್ಬಾಕ್ಸ್ ಪ್ರತ್ಯೇಕ ಕಾರ್ಯಾಚರಣಾ
   ಮಿತಿಗಳಾಗಿವೆ.
3. OmniRoute ಎಂದಿಗೂ ಪ್ರಾಂಪ್ಟ್ಗಳು, ಪ್ರತಿಕ್ರಿಯೆಗಳು, ಸಂಭಾಷಣೆಗಳು, ಪ್ರೊವೈಡರ್ ಕ್ರೆಡೆನ್ಷಿಯಲ್ಗಳು, ಮಾಡೆಲ್ ಟ್ರಾಫಿಕ್,
   ಅಪ್ಟೈಮ್, ಲೇಟೆನ್ಸಿ ಅಥವಾ ಸ್ಥಳೀಯ ಪ್ರೊವೈಡರ್ ಕಾನ್ಫಿಗರೇಶನ್ ಅನ್ನು Radar ಸೇವೆಗೆ ಕಳುಹಿಸುವುದಿಲ್ಲ.
4. ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಪರಿಶೀಲಿಸಿ, ಮೌಲ್ಯೀಕರಿಸಿ ಮತ್ತು ಸ್ಥಳೀಯವಾಗಿ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ (
   [ಭದ್ರತಾ ಮಾದರಿ](#security-model) ನೋಡಿ). Radar ನಿಖರವಾಗಿ ನಾಲ್ಕು ಸರ್ವರ್-ಸೈಡ್ ನೆಟ್ವರ್ಕ್ ಪಥಗಳನ್ನು ಹೊಂದಿದೆ:
   ಕ್ಯಾಟಲಾಗ್ಗಾಗಿ `syncRadar()`, ರೆಫರಲ್ಗಳಿಗಾಗಿ `syncRadarReferrals()` ಮತ್ತು
   ಸಪೋರ್ಟರ್ಗಳಿಗೆ ಮಾತ್ರ ಲಭ್ಯವಿರುವ ಆಫರ್ಗಳು ಹಾಗೂ Intel ಗಾಗಿ `syncRadarOffers()` / `syncRadarIntel()`.

**ಸಪೋರ್ಟರ್ ಕೀ** ಎಂಬುದು ಐಚ್ಛಿಕ Bearer ಟೋಕನ್ (`radar_settings.supporter_key`) ಆಗಿದ್ದು,
ಯಾವ ಟಿಯರ್ ಅನ್ನು ಒದಗಿಸಬೇಕು ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸಲು ಫೀಡ್ ಸೇವೆಗೆ ಅವಕಾಶ ನೀಡುತ್ತದೆ (
[ಟಿಯರ್ಗಳು](#tiers-community-and-live) ನೋಡಿ). ಅದು:

- ಪ್ರೊವೈಡರ್ ಕ್ರೆಡೆನ್ಷಿಯಲ್ಗಳಿಗೆ ಬಳಸುವ ಅದೇ AES-256-GCM `encrypt()`/`decrypt()`
  ಸಹಾಯಕಗಳೊಂದಿಗೆ (`src/lib/db/encryption.ts`) **ನಿಷ್ಕ್ರಿಯ ಸ್ಥಿತಿಯಲ್ಲಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ**.
- `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) ಮೂಲಕ ಹೊಂದಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
  **ಎಂದಿಗೂ ಮರಳಿ ಪ್ರದರ್ಶಿಸಲಾಗುವುದಿಲ್ಲ** — ಪ್ರತಿಕ್ರಿಯೆಯು ಮರೆಮಾಚಿದ ರೂಪವನ್ನು (`omr_****abcd`) ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
- ಅದನ್ನು ಬದಲಿಸುವುದು ಅಥವಾ ತೆರವುಗೊಳಿಸುವುದು ಕ್ಯಾಟಲಾಗ್, ರೆಫರಲ್ಗಳು, ಆಫರ್ಗಳು ಮತ್ತು Intel ಕ್ಯಾಶ್ಗಳನ್ನು ಏಕಕಾಲಿಕವಾಗಿ ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ. ಮುಂದಿನ
  ಸಿಂಕ್/ಓದುವಿಕೆ ಹೊಸ ಅರ್ಹತೆಯನ್ನು ಸರ್ವರ್-ಸೈಡ್ನಲ್ಲಿ ನಿರ್ಧರಿಸುತ್ತದೆ; ಕೀಯನ್ನು ಉಳಿಸುವುದರಿಂದ ಸ್ವತಃ
  ನೆಟ್ವರ್ಕ್ ವಿನಂತಿ ನಡೆಯುವುದಿಲ್ಲ ಅಥವಾ ಒಮ್ಮೆ ಮಾತ್ರ ಬಳಸಬಹುದಾದ ಆಕ್ಟಿವೇಶನ್ ಕೀ ಬಳಕೆಯಾಗುವುದಿಲ್ಲ.
- ಸಿಂಕ್ GET ನಲ್ಲಿ Bearer ಟೋಕನ್ ಆಗಿ ಫೀಡ್ ಸೇವೆಗೆ ಕಳುಹಿಸಲಾಗುತ್ತದೆ — ಕೀ ಕುರಿತು ಬೇರೆ ಯಾವುದೂ
  ಕ್ಲೈಂಟ್ನಿಂದ ಹೊರಹೋಗುವುದಿಲ್ಲ.

ಹಸ್ತಚಾಲಿತ ಅನುದಾನಗಳು ಪ್ರಸ್ತುತ ಅವಧಿ ಮುಕ್ತಾಯದಿಂದ ಮುಂದಕ್ಕೆ ಸಂಗ್ರಹಗೊಳ್ಳುತ್ತವೆ; ಜೀವಮಾನ ಪ್ರವೇಶವು ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತದೆ. ಶ್ರೇಯಾಂಕದ ಬದಲಾವಣೆಯು
ಈಗಾಗಲೇ ನೀಡಲಾದ ಸಮಯವನ್ನು ಪೂರ್ವಾನ್ವಯವಾಗಿ ಎಂದಿಗೂ ಹಿಂಪಡೆಯುವುದಿಲ್ಲ ಅಥವಾ ಕಡಿಮೆ ಮಾಡುವುದಿಲ್ಲ.

ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಪರವಾನಗಿ ವೈಯಕ್ತಿಕವಾಗಿದ್ದು, ಬಳಕೆದಾರರಿಗೆ ತೋರಿಸಲಾಗುವ ನಿಯಮವು ಒಂದು ಸಮಯದಲ್ಲಿ ಒಂದು ಸಕ್ರಿಯ ಸ್ಥಾಪನೆ ಮಾತ್ರ ಎಂಬುದಾಗಿದೆ. ಈ
ಬಿಡುಗಡೆಯು ಹಾರ್ಡ್ವೇರ್ ಲಾಕ್ ಇದೆ ಎಂದು **ಹೇಳುವುದಿಲ್ಲ**: OSS ಸಿಂಕ್ ಹಾರ್ಡ್ವೇರ್ನ fingerprint ಮಾಡುವುದಿಲ್ಲ ಅಥವಾ
ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕ್ ಸಾಧನ ಲೀಸ್ ಅನ್ನು ನಿರ್ವಹಿಸುವುದಿಲ್ಲ. ಮೇಲೆ ಪರಿಶೀಲಿಸಲಾದ ಖಾಸಗಿ-ಸರ್ವರ್ revisionನಲ್ಲಿ, ಅನುಷ್ಠಾನಗೊಳಿಸಲಾದ ಜಾರಿ ವ್ಯವಸ್ಥೆಯು
ಅರ್ಹತೆಯ ಪರಿಶೀಲನೆ ಮತ್ತು ಅದೇ ಲೈವ್ ಕೀ 24 ಗಂಟೆಗಳೊಳಗೆ ನಾಲ್ಕನೇ ವಿಭಿನ್ನ IPಯಿಂದ ಕಂಡುಬಂದಾಗ ಹಸ್ತಚಾಲಿತ ಪರಿಶೀಲನೆಯ ಸಂಕೇತವನ್ನು ಒಳಗೊಂಡಿದೆ.
ಆ ಸಂಕೇತವು ಕೀಯನ್ನು ಎಂದಿಗೂ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ ಅಥವಾ ಹಿಂಪಡೆಯುವುದಿಲ್ಲ. ಮರುಪಡೆಯುವಿಕೆ
ಕಳೆದುಹೋದ ಕೀಯನ್ನು ಹಿಂಪಡೆದು ಬದಲಾಯಿಸುತ್ತದೆ ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅವಧಿ ಮುಕ್ತಾಯವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ; ಅದು
ಖರೀದಿಸಿದ ಅಥವಾ ಅನುದಾನವಾಗಿ ನೀಡಿದ ಅವಧಿಯನ್ನು ಮರುಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ.

ಲೈವ್ ಆಫರ್ಗಳನ್ನು ಹಸ್ತಚಾಲಿತವಾಗಿ ಆಯ್ಕೆಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಅವು ಬದಲಾಗಬಹುದು ಅಥವಾ ಅವಧಿ ಮುಗಿಯಬಹುದು. ಆಯ್ಕೆಗೆ ಸಮ್ಮತಿಸುವ ಪರದೆಯು ನಿಖರವಾದ
ಗೌಪ್ಯತಾ ಗಡಿಯನ್ನೂ ತಿಳಿಸುತ್ತದೆ: ಸಹಿ ಮಾಡಿದ ಕ್ಯಾಟಲಾಗ್/referral metadata ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ; ಮಾನ್ಯವಾದ ಕೀ ಹೆಚ್ಚುವರಿಯಾಗಿ
ಸಹಿ ಮಾಡಿದ ಆಫರ್ಗಳು ಮತ್ತು Intel ಅನ್ನು ಅನ್ಲಾಕ್ ಮಾಡುತ್ತದೆ; Bearer ಕೀ ಮತ್ತು ಸಾಮಾನ್ಯ ಸಂಪರ್ಕ metadata ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಸೇವೆಯನ್ನು ತಲುಪುತ್ತವೆ;
promptಗಳು, responseಗಳು, conversationಗಳು, provider credentialಗಳು, model traffic, uptime, latency ಮತ್ತು ಸ್ಥಳೀಯ
provider configuration ತಲುಪುವುದಿಲ್ಲ.

## ಬೆಂಬಲಿಗ ಕೀಲಿಯನ್ನು ಪಡೆಯುವುದು

ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಪರದೆ (`/dashboard/radar`) ಬೆಂಬಲಿಗ ಕೀಲಿಯನ್ನು **ಪಡೆಯಲು** ಎರಡು ಪ್ರಕ್ರಿಯೆಗಳಿಗೆ ಲಿಂಕ್ ಮಾಡುತ್ತದೆ. OSS ರೆಪೊ ಸ್ವತಃ ಎಂದಿಗೂ ಕೀಲಿಯನ್ನು ನೀಡುವುದಿಲ್ಲ, ಪಾವತಿ ಕೋಡ್ ಅನ್ನು ಎಂದಿಗೂ ಚಲಾಯಿಸುವುದಿಲ್ಲ ಮತ್ತು **ಬೆಲೆಯನ್ನು ಎಂದಿಗೂ ತಿಳಿಸುವುದಿಲ್ಲ** — ಬೆಲೆಯನ್ನು ಈ ರೆಪೊದಲ್ಲಿ ಅಲ್ಲ, ಸಂಪೂರ್ಣವಾಗಿ ಗಮ್ಯ ಪುಟಗಳಲ್ಲಿ ನಿರ್ಧರಿಸಿ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ (ವಿನ್ಯಾಸ ನಿರ್ಧಾರ D14).

- **"ನಾನು ಕೊಡುಗೆದಾರ"** — `RADAR_CONTRIBUTOR_CLAIM_URL` ಅನ್ನು ತೆರೆಯುತ್ತದೆ (ಡೀಫಾಲ್ಟ್
  `https://radar.omniroute.online/auth/github`); ಇದು ಖಾಸಗಿ Radar ಸರ್ವರ್ನಲ್ಲಿ ಹೋಸ್ಟ್ ಮಾಡಲಾದ GitHub OAuth ಕ್ಲೇಮ್ ಪ್ರಕ್ರಿಯೆಯಾಗಿದೆ. ಇದು ಇತ್ತೀಚಿನ ಪೂರ್ಣಗೊಂಡ ವಾರದ ಶ್ರೇಯಾಂಕವನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ: ಅಗ್ರ 10 ಮಂದಿಗೆ 365 ದಿನಗಳು
  ಮತ್ತು 11–100 ಸ್ಥಾನಗಳಲ್ಲಿರುವವರಿಗೆ 90 ದಿನಗಳು ದೊರೆಯುತ್ತವೆ. ಅಗ್ರ 100ರ ಹೊರಗೆ, PR ಸಂಖ್ಯೆಯು ಎಂದಿಗೂ ಪ್ರವೇಶವನ್ನು ನೀಡುವುದಿಲ್ಲ; ಬದಲಿಗೆ ಪ್ರಕ್ರಿಯೆಯು ಪ್ರತ್ಯೇಕವಾದ ಸ್ಟಾರ್ + ಫಾಲೋ ಏಕ-ಬಳಕೆಯ ಹಂತವನ್ನು
  ಪರಿಶೀಲಿಸುತ್ತದೆ.
- **"ಯೋಜನೆಯನ್ನು ಬೆಂಬಲಿಸಿ"** — `RADAR_SUPPORTER_PLANS_URL` ಅನ್ನು ತೆರೆಯುತ್ತದೆ (ಡೀಫಾಲ್ಟ್
  `https://radar.omniroute.online/planos`); ಇದು ಒಂದು-ಬಾರಿಯ 6-ತಿಂಗಳ, 1-ವರ್ಷದ ಮತ್ತು
  ಜೀವಮಾನ ಆಯ್ಕೆಗಳಿಗಾಗಿ ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಪುಟವಾಗಿದೆ. OSS ಪುಟವು ಇನ್ನೂ ಯಾವುದೇ ಹಣಕಾಸಿನ ಮೌಲ್ಯವನ್ನು ಪ್ರದರ್ಶಿಸುವುದಿಲ್ಲ.

ಎರಡೂ URLಗಳನ್ನು ಸರ್ವರ್-ಬದಿಯಲ್ಲಿ ಪರಿಹರಿಸಲಾಗುತ್ತದೆ (`src/lib/radar/links.ts`, `RADAR_FEED_URL` ನಂತೆಯೇ ಅದೇ env-ಓವರ್ರೈಡ್
ಮಾದರಿ) ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
`GET /api/radar/settings` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೂಲಕ (`contributorClaimUrl`, `supporterPlansUrl`) ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗೆ ರಿಲೇ ಮಾಡಲಾಗುತ್ತದೆ — ಕ್ಲೈಂಟ್
ಕಾಂಪೊನೆಂಟ್ ಎಂದಿಗೂ ಸ್ವತಃ `process.env` ಅನ್ನು ಓದುವುದಿಲ್ಲ.

| ----------------------------- | ------------------------------------------------------------------------------------------------------- |

### ಕಳೆದುಹೋದ ಬೆಂಬಲಿಗ ಕೀಲಿಯನ್ನು ಮರುಪಡೆಯುವುದು

ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಸೇವೆಯ ಮರುಪಡೆಯುವಿಕೆ ಪ್ರವೇಶ ಬಿಂದು `https://radar.omniroute.online/recover` ಆಗಿದೆ; ಯೋಜನೆಗಳ ಪುಟದಿಂದಲೂ ಇದಕ್ಕೆ
ಲಿಂಕ್ ಮಾಡಲಾಗಿದೆ. ಸ್ಥಳೀಯ ಸ್ಥಾಪನೆಯು ಖರೀದಿದಾರರ/ಕೊಡುಗೆದಾರರ ಇ-ಮೇಲ್ ಅನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ ಮತ್ತು ಅದರ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ಸೆಟ್ಟಿಂಗ್ಗಳಿಂದ ಮೂಲ ಕೀಲಿಯನ್ನು ಪುನರ್ರಚಿಸಲು ಸಾಧ್ಯವಿಲ್ಲವಾದ್ದರಿಂದ, ಮರುಪಡೆಯುವಿಕೆಯು ಸಂಪೂರ್ಣವಾಗಿ OSS ಕ್ಲೈಂಟ್ನ
ಹೊರಗೇ ಉಳಿಯುತ್ತದೆ.

1. ಕೀಲಿಗೆ ಸಂಬಂಧಿಸಿದ ಇ-ಮೇಲ್ ಅನ್ನು ಸಲ್ಲಿಸಿ. ಮರುಪಡೆಯಬಹುದಾದ ಪರವಾನಗಿ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದರೂ ಇಲ್ಲದಿದ್ದರೂ ಸೇವೆಯು ಒಂದೇ ಸ್ವೀಕೃತ ಪುಟವನ್ನು
   ಹಿಂದಿರುಗಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಫಾರ್ಮ್ ಖಾತೆಗಳನ್ನು ಪಟ್ಟಿಮಾಡುವುದಿಲ್ಲ.
2. ಅರ್ಹವಾಗಿದ್ದರೆ, ವಿತರಣಾ ವರ್ಕರ್ ಅಲ್ಪಾವಧಿಯ, ಒಂದು-ಬಾರಿಯ ಬಳಕೆಯ ಲಿಂಕ್ ಅನ್ನು ಕಳುಹಿಸುತ್ತದೆ. ಅದನ್ನು ತೆರೆಯುವುದರಿಂದ ತಕ್ಷಣವೇ
   ಟೋಕನ್ ಅನ್ನು ತಾತ್ಕಾಲಿಕ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ `HttpOnly`/`Secure` ಕುಕೀಗೆ ವರ್ಗಾಯಿಸಿ, ಸ್ವಚ್ಛವಾದ
   `/recover` URL ಗೆ ಮರುನಿರ್ದೇಶಿಸಲಾಗುತ್ತದೆ; ಪುಟವು ಯಾವುದೇ ಟೋಕನ್, ಇ-ಮೇಲ್, ಹಳೆಯ ಕೀಲಿ ಅಥವಾ ಬದಲಿ ಕೀಲಿಯನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ.
3. ರದ್ದತಿಯನ್ನು ದೃಢೀಕರಿಸಿ. ಖಾಸಗಿ ಸೇವೆಯು ಹಿಂದಿನ ಕೀಲಿಯನ್ನು ರದ್ದುಗೊಳಿಸಿ, ಅದೇ ಯೋಜನೆ/ಅವಧಿ ಮುಕ್ತಾಯದೊಂದಿಗೆ
   ಬದಲಿಯನ್ನು ರಚಿಸಿ, ಒಂದೇ ಟ್ರಾನ್ಸಾಕ್ಷನ್ನಲ್ಲಿ ಅದನ್ನು ಇ-ಮೇಲ್ಗಾಗಿ ಸರದಿಗೆ ಸೇರಿಸುತ್ತದೆ. ಬದಲಿ ಕೀಲಿಯನ್ನು ಎಂದಿಗೂ
   ಬ್ರೌಸರ್ಗೆ ಹಿಂದಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ.
4. ಬದಲಿ ಕೀಲಿಯನ್ನು `/dashboard/radar` ನಲ್ಲಿ ಅಂಟಿಸಿ. ಹಳೆಯ ಕೀಲಿಯು ಈಗ `community` ಗೆ ಇಳಿಯಬೇಕು;
   ಬದಲಿ ಕೀಲಿಯು ಪರಿಶೀಲಿಸಿದ `live` ಸಿಂಕ್ ಅನ್ನು ಉತ್ಪಾದಿಸಬೇಕು. ಅದೇ ಮರುಪಡೆಯುವಿಕೆ ಲಿಂಕ್ ಅನ್ನು ಮರುತೆರೆಯುವುದು
   ಸಾಮಾನ್ಯ ಅಮಾನ್ಯ/ಅವಧಿ-ಮೀರಿದ ಪ್ರತಿಕ್ರಿಯೆಯೊಂದಿಗೆ ವಿಫಲವಾಗಬೇಕು.

ಹೋಸ್ಟ್ ಮಾಡಲಾದ ಮರುಪಡೆಯುವಿಕೆ ರೂಟ್ ಮತ್ತು ಮೇಲ್ ವರ್ಕರ್ ಕೋಡ್ನಲ್ಲಿ ಇದ್ದರೂ, ನಿರ್ದಿಷ್ಟ
ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ನಲ್ಲಿ ಅವು ಲಭ್ಯವಿಲ್ಲದಿರಬಹುದು. ಸರ್ವರ್ ಅನ್ನು ಡಿಪ್ಲಾಯ್ ಮಾಡುವವರೆಗೆ, ನಿಯಂತ್ರಿತ ಸ್ವೀಕರಿಸುವವರೊಂದಿಗೆ ವಿತರಣಾ
ಪೂರೈಕೆದಾರರನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡುವವರೆಗೆ ಮತ್ತು ಸಂಪೂರ್ಣ ಒಂದು-ಬಾರಿಯ ಬಳಕೆಯ ಲಿಂಕ್ ಅನ್ನು ಪರೀಕ್ಷಿಸುವವರೆಗೆ ಈ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರೊಡಕ್ಷನ್ಗೆ ಸಿದ್ಧವಾಗಿದೆ ಎಂದು ಪರಿಗಣಿಸಬೇಡಿ.

ಸಂದರ್ಶಕರೊಬ್ಬರು ಕೀಲಿಯನ್ನು (`omr_` + 40 ಹೆಕ್ಸ್ ಅಕ್ಷರಗಳು) ಪಡೆದ ನಂತರ, ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಪರದೆಯು
(`src/app/(dashboard)/dashboard/radar/page.tsx`) ಪ್ರಾಥಮಿಕ ಮಾರ್ಗವಾಗಿ ಕೀಲಿಯನ್ನು ಅಂಟಿಸುವ ಇನ್ಪುಟ್ ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ:
ಕೀಲಿಯನ್ನು ಅಂಟಿಸಿ ಸಲ್ಲಿಸಿದಾಗ, ಒಂದೇ ಕರೆಯಲ್ಲಿ `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`) ಕಳುಹಿಸಲಾಗುತ್ತದೆ — ಕೀಲಿಯನ್ನು ಅಂಟಿಸುವುದು ಅದನ್ನು ಹೊಂದಿಸುವುದರ ಜೊತೆಗೆ ಭಾಗವಹಿಸುವಿಕೆಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ,
ಪರದೆಯನ್ನು ಅನ್ಲಾಕ್ ಮಾಡುತ್ತದೆ. ಫಾರ್ಮ್ಯಾಟ್ ಅನ್ನು (`omr_` + 40 ಹೆಕ್ಸ್ ಅಕ್ಷರಗಳು) ಮೊದಲು ಕ್ಲೈಂಟ್-ಬದಿಯಲ್ಲಿ
ಹಂಚಿಕೆಯ `isValidSupporterKeyFormat()` ಸಹಾಯಕದೊಂದಿಗೆ (`src/lib/radar/supporterKey.ts`)
UX ಅನುಕೂಲಕ್ಕಾಗಿ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ; ಯಾವುದೇ ಸಂದರ್ಭದಲ್ಲೂ ಸರ್ವರ್ನ Zod ಸ್ಕೀಮಾವೇ ಅಧಿಕೃತ ಪರಿಶೀಲನೆಯಾಗಿದೆ. ಒಮ್ಮೆ
ಕೀಲಿಯನ್ನು ಹೊಂದಿಸಿದ ನಂತರ, ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಪರದೆಯು ಖಾಲಿ ಇನ್ಪುಟ್ ಬದಲಿಗೆ ಮರೆಮಾಚಿದ ರೂಪವನ್ನು (`GET /api/radar/settings` ನಿಂದ `supporterKeyMasked`) ತೋರಿಸುತ್ತದೆ ಮತ್ತು
ಹೊಸ ಕೀಲಿಯನ್ನು ಅಂಟಿಸಲು "ಕೀಲಿಯನ್ನು ಬದಲಿಸಿ" ನಿಯಂತ್ರಣವನ್ನು ಒದಗಿಸುತ್ತದೆ — ಮೂಲ ಕೀಲಿಯನ್ನು ಎಂದಿಗೂ ಮತ್ತೆ ಪ್ರದರ್ಶಿಸಲಾಗುವುದಿಲ್ಲ. ಮೇಲಿನ ಎರಡು ಕ್ಲೇಮ್/ಯೋಜನೆಗಳ ಬಟನ್ಗಳು
ಮೊದಲಿಗೆ ಕೀಲಿಯನ್ನು _ಪಡೆಯುವ_ ಮಾರ್ಗವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ; ಈಗಾಗಲೇ ಕೀಲಿಯನ್ನು ಹೊಂದಿರುವ ಆಪರೇಟರ್
ಅದನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವ ಸ್ಥಳವೇ ಈ ಇನ್ಪುಟ್.

### ಆರಂಭದಿಂದ ಅಂತ್ಯದವರೆಗಿನ ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಮಾರ್ಗದರ್ಶಿತ ಸೆಟಪ್

ಖಾಸಗಿ ಫೀಡ್ ಸೇವೆ ಮತ್ತು ಈ OSS ಕ್ಲೈಂಟ್ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಕಿರಿದಾದ ಗಡಿಯನ್ನು ಹೊಂದಿವೆ: ಸೇವೆಯು
ಬೆಂಬಲಿಗ ಕೀಲಿಯನ್ನು ನೀಡುತ್ತದೆ ಮತ್ತು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; ಇದೇ ವೇಳೆ ಸ್ಥಳೀಯ OmniRoute ಸ್ಥಾಪನೆಯು ಕೀಲಿಯನ್ನು ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ,
ಸಹಿ ಮಾಡಿದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳನ್ನು ಸರ್ವರ್-ಬದಿಯಲ್ಲಿ ಸಿಂಕ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಪೂರೈಕೆದಾರರ ಸೆಟಪ್ಗೆ ಮಾರ್ಗದರ್ಶನ ನೀಡುತ್ತದೆ. ಸಹಾಯಿತ ಮೌಲ್ಯೀಕರಣದ ಕ್ರಮ ಹೀಗಿದೆ:

1. ಕೊಡುಗೆದಾರರ ಕ್ಲೈಮ್, plans/checkout, ಮರುಪಡೆಯುವಿಕೆ ಪ್ರಕ್ರಿಯೆ ಅಥವಾ ಅಧಿಕೃತ ಖಾಸಗಿ ಸರ್ವರ್ ಆಪರೇಟರ್ನಿಂದ ಹೊಸದಾಗಿ ನೀಡಲಾದ ಅಥವಾ ಮರುಪಡೆಯಲಾದ ಕೀಲಿಯನ್ನು ಪಡೆಯಿರಿ. ಕಚ್ಚಾ ಕೀಲಿಯನ್ನು ಲಾಗ್ಗಳು, ಸ್ಕ್ರೀನ್ಶಾಟ್ಗಳು, ಸಮಸ್ಯೆಯ ಕಾಮೆಂಟ್ಗಳು ಅಥವಾ ಕಮಾಂಡ್-ಲೈನ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳಲ್ಲಿ ಅಂಟಿಸಬೇಡಿ.
2. ಸ್ಥಳೀಯ OmniRoute ಸ್ಥಾಪನೆಯಲ್ಲಿ `RADAR_ENABLED` ವೈಶಿಷ್ಟ್ಯ ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ. ಇದು UI ಅನ್ನು ಲಭ್ಯವಾಗಿಸುತ್ತದೆ, ಆದರೆ ಪ್ರತ್ಯೇಕ ಆಯ್ಕೆಯನ್ನು ಉಳಿಸುವವರೆಗೆ ನೆಟ್ವರ್ಕ್ನಲ್ಲಿ ನಿಷ್ಕ್ರಿಯವಾಗಿಯೇ ಇರುತ್ತದೆ.
3. `/dashboard/radar` ತೆರೆಯಿರಿ, ಕೀಲಿಯನ್ನು ಅಂಟಿಸಿ ಮತ್ತು ಸಕ್ರಿಯಗೊಳಿಸಿ. ಬ್ರೌಸರ್ `{ optIn: true, supporterKey }` ಜೊತೆಗೆ ಒಂದು ಸ್ಥಳೀಯ
   `POST /api/radar/settings` ಅನ್ನು ಕಳುಹಿಸುತ್ತದೆ; ಕೀಲಿಯನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು
   ಪ್ರತಿಕ್ರಿಯೆಯು `omr_****<last4>` ಅನ್ನು ಮಾತ್ರ ಒಳಗೊಂಡಿರುತ್ತದೆ.
4. ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಪರದೆಯಲ್ಲಿ ಕ್ಯಾಟಲಾಗ್ ಸಿಂಕ್ ಪೂರ್ಣಗೊಳ್ಳಲು ಬಿಡಿ ಅಥವಾ **ಈಗ ಸಿಂಕ್ ಮಾಡಿ** ಆಯ್ಕೆಮಾಡಿ. ಪುಟವು
   `live`, ಫೀಡ್ ಆವೃತ್ತಿ ಮತ್ತು ಪಡೆಯಲಾದ ಸಮಯವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ. ದೃಢೀಕೃತ ಸ್ಥಳೀಯ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಗಾಗಿ,
   `GET /api/radar/status` ಕೀಲಿಯನ್ನು ಹಿಂತಿರುಗಿಸದೆಯೇ ಆಯ್ಕೆ/ಕೀಲಿಯ ಅಸ್ತಿತ್ವ ಮತ್ತು ನಾಲ್ಕು ಕ್ಯಾಶ್ ಸ್ಥಿತಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.
   `POST /api/radar/sync-all` ಕ್ಯಾಟಲಾಗ್, ರೆಫರಲ್ಗಳು, ಆಫರ್ಗಳು ಮತ್ತು Intel ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ರಿಫ್ರೆಶ್ ಮಾಡಬಹುದು.
5. `/dashboard/radar/setup?provider=<provider>` ತೆರೆಯಿರಿ. ಪೂರೈಕೆದಾರರು ನಿರ್ವಹಿಸುವ ಕ್ರೆಡೆನ್ಶಿಯಲ್ URL ಅನ್ನು ಅನುಸರಿಸಿ,
   **API ಕೀ ಸೇರಿಸಿ** ಆಯ್ಕೆಮಾಡಿ, ನೈಜ ಪೂರೈಕೆದಾರ ಫಾರ್ಮ್ ಮೂಲಕ ಉಳಿಸಿ, ಮಾರ್ಗದರ್ಶಿಗೆ ಹಿಂತಿರುಗಿ ಮತ್ತು
   **ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸಿ** ಅನ್ನು ಚಲಾಯಿಸಿ. ಮಾರ್ಗದರ್ಶಿಯು ಸಾಮಾನ್ಯ `/api/providers` ಮತ್ತು
   `/api/providers/<connection-id>/test` ರೂಟ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ; ಅದು ಸಮಾನಾಂತರ Radar ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಅನ್ನು ರಚಿಸುವುದಿಲ್ಲ.
6. ಕನಿಷ್ಠ ಎರಡು ಹೊಂದಾಣಿಕೆಯ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳು ಸಕ್ರಿಯವಾದ ನಂತರ `/dashboard/radar/combos` ತೆರೆಯಿರಿ.
   ಸೂಚಿಸಲಾದ ಕುಟುಂಬವನ್ನು ಪರಿಶೀಲಿಸಿ ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕಾಂಬೊ API ಮೂಲಕ ಕಾಂಬೊವನ್ನು ರಚಿಸಿ. ಆಫರ್ಗಳು ಮತ್ತು
   Intel ಪ್ರತ್ಯೇಕವಾದ, ಲೈವ್ಗೆ ಮಾತ್ರ ಸೀಮಿತವಾದ ಸಹಿ ಮಾಡಿದ ಕ್ಯಾಶ್ಗಳಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ ಮತ್ತು ಅವುಗಳ ಮೀಸಲಾದ Radar ಪುಟಗಳಲ್ಲಿ ಅವುಗಳನ್ನು ಪರಿಶೀಲಿಸಬಹುದು.
7. `/dashboard/radar` ಮತ್ತು ಸೆಟಪ್ ಪುಟವನ್ನು ಮರುಲೋಡ್ ಮಾಡಿ. ಆಯ್ಕೆ, ಮರೆಮಾಡಿದ-ಕೀಲಿಯ ಸ್ಥಿತಿ, ಪರಿಶೀಲಿಸಲಾದ ಕ್ಯಾಶ್, ಉಳಿಸಲಾದ
   ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕ ಮತ್ತು ಪರೀಕ್ಷಾ ಕ್ರಿಯೆಯು ಮರುಲೋಡ್ನ ನಂತರವೂ ಉಳಿಯಬೇಕು. ಕಚ್ಚಾ ಕೀ ಮತ್ತು ಪೂರೈಕೆದಾರರ ಕ್ರೆಡೆನ್ಶಿಯಲ್
   ಇನ್ನು ಮುಂದೆ ಗೋಚರಿಸದಿರುವಾಗ ಮಾತ್ರ ಸಾಕ್ಷ್ಯವನ್ನು ಸೆರೆಹಿಡಿಯಿರಿ.

ಕೀಲಿಯನ್ನು ಉಳಿಸುವುದಷ್ಟೇ ಲೈವ್ ಅರ್ಹತೆಯ ಪುರಾವೆಯಲ್ಲ. ಪುರಾವೆಯು ಖಾಸಗಿ ಸೇವೆಯ
`GET /v1/license/check` ಫಲಿತಾಂಶ, OSS ಕ್ಯಾಟಲಾಗ್ ಒದಗಿಸುವ `live` ಶ್ರೇಣಿ, ಪರಿಶೀಲಿಸಲಾದ ಸಹಿ ಮಾಡಿದ
ಕ್ಯಾಶ್ ಮತ್ತು ನೈಜ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕ/ಪರೀಕ್ಷಾ ಪ್ರಕ್ರಿಯೆಯ ಸಂಯೋಜನೆಯಾಗಿದೆ. ಅಮಾನ್ಯವಾದ, ಅವಧಿ ಮುಗಿದ ಅಥವಾ ಹಿಂಪಡೆಯಲಾದ ಕೀಲಿಯು
ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಸುರಕ್ಷಿತವಾಗಿ `community` ಗೆ ಇಳಿಸುತ್ತದೆ; ಅದನ್ನು ಯಶಸ್ವಿ ಲೈವ್-ಕೀ ಪರಿಶೀಲನೆ ಎಂದು ವರದಿ ಮಾಡಬಾರದು.

### ಖಾಸಗಿ ನಿರ್ವಾಹಕ-ಫಲಕದ ಲಿಂಕ್

`RADAR_ADMIN_URL` ಐಚ್ಛಿಕವಾಗಿ ವೆಚ್ಚಗಳ ಸೈಡ್ಬಾರ್ ವಿಭಾಗದಲ್ಲಿನ ಬಳಕೆದಾರರಿಗೆ ಗೋಚರಿಸುವ
Radar ಐಟಂನ ತಕ್ಷಣವೇ **Radar Admin ↗** ಅನ್ನು ಸೇರಿಸುತ್ತದೆ. ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಇದಕ್ಕೆ ಯಾವುದೇ ಡೀಫಾಲ್ಟ್ ಇಲ್ಲ: ವೇರಿಯೇಬಲ್
ಹೊಂದಿಸದಿದ್ದಾಗ ಅಥವಾ ಅಮಾನ್ಯವಾಗಿದ್ದಾಗ, ಸ್ಥಿರ ಸೈಡ್ಬಾರ್, ಕಮಾಂಡ್ ಪ್ಯಾಲೆಟ್ ಮತ್ತು ಸೈಡ್ಬಾರ್-ಕಸ್ಟಮೈಸೇಶನ್ ಪರದೆಯು ಯಾವುದೇ
ನಿರ್ವಾಹಕ ಐಟಂ ಅಥವಾ ಖಾಸಗಿ URL ಅನ್ನು ಒಳಗೊಂಡಿರುವುದಿಲ್ಲ.

ಮೌಲ್ಯವನ್ನು ಸರ್ವರ್ ಬದಿಯಲ್ಲಿ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ನಿರ್ವಹಣಾ-ದೃಢೀಕೃತ
`GET /api/settings` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೂಲಕ ದೃಢೀಕೃತ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್ಗೆ ಮಾತ್ರ ಅಥವಾ ಸ್ಥಳೀಯ ಲಾಗಿನ್-ರಹಿತ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಸಮಯದಲ್ಲಿ ವಿಶ್ವಾಸಾರ್ಹ
ಲೂಪ್ಬ್ಯಾಕ್ ಮಾಲೀಕರಿಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ. CLI, ಆಂತರಿಕ-ಸೇವೆ ಮತ್ತು manage-scope API-ಕೀ
ದೃಢೀಕರಣವು ಅದನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಬಾಹ್ಯ ಲಿಂಕ್ ಅನ್ನು ಪ್ರದರ್ಶಿಸುವ ಮೊದಲು ಬ್ರೌಸರ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮತ್ತೊಮ್ಮೆ ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ
ಮತ್ತು ಆ ಲಿಂಕ್ `noopener noreferrer` ಜೊತೆಗೆ ತೆರೆಯುತ್ತದೆ.

ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳಿಲ್ಲದ HTTPS ಟನಲ್/tailnet URL ಅನ್ನು ಬಳಸಿ. `http://127.0.0.1:9351` ನಂತಹ ಲೂಪ್ಬ್ಯಾಕ್ SSH
ಫಾರ್ವರ್ಡ್ಗೆ ಮಾತ್ರ ಸರಳ HTTP ಅನ್ನು ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; ಇತರ ಸ್ಕೀಮ್ಗಳು, ಎಂಬೆಡ್ ಮಾಡಿದ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು, ತಪ್ಪಾಗಿ ರೂಪಿಸಲಾದ URLಗಳು ಮತ್ತು
ರಿಮೋಟ್ HTTP ಗಮ್ಯಸ್ಥಾನಗಳು ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲವಾಗುತ್ತವೆ ಮತ್ತು ನ್ಯಾವಿಗೇಶನ್ ಅನ್ನು ನಿಷ್ಕ್ರಿಯವಾಗಿರಿಸುತ್ತವೆ.

## ಭದ್ರತಾ ಮಾದರಿ

### ನಿಖರ ಬೈಟ್ಗಳ ಮೇಲಿನ Ed25519 ಸಹಿ

ಫೀಡ್ ಪೇಲೋಡ್ ಅನ್ನು Ed25519 ಮೂಲಕ ಸಹಿ ಮಾಡಲಾಗಿದೆ. `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) ವೈರ್ ಮೂಲಕ ಸ್ವೀಕರಿಸಿದ **ನಿಖರ ಪ್ರತಿಕ್ರಿಯೆ ಬೈಟ್ಗಳ** ಮೇಲಿನ
ಸಹಿಯನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ — ಪರಿಶೀಲನೆಗೂ ಮೊದಲು ಪೇಲೋಡ್ ಅನ್ನು ಎಂದಿಗೂ ಮರು-ಸೀರಿಯಲೈಸ್
ಮಾಡಲಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಬೈಟ್ಗೆ-ಬೈಟ್ ಮರು-ಎನ್ಕೋಡಿಂಗ್ ಸಹಿ ಪರಿಶೀಲನೆಯನ್ನು ಮೌನವಾಗಿ
ಅಮಾನ್ಯಗೊಳಿಸಲು ಅಥವಾ ಬೈಪಾಸ್ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪರಿಶೀಲನೆ ವಿಫಲವಾದರೆ
(`invalid_signature`), ಪೇಲೋಡ್ ಅನ್ನು ಪಾರ್ಸ್ ಮಾಡುವ ಅಥವಾ ಕ್ಯಾಶ್ ಮಾಡುವ ಮೊದಲೇ ಸಿಂಕ್
ಸ್ಥಗಿತಗೊಳ್ಳುತ್ತದೆ.

### ಪಿನ್ ಮಾಡಿದ ಸಾರ್ವಜನಿಕ ಕೀಲಿ + ರೊಟೇಶನ್

ಪರಿಶೀಲಿಸುವ ಸಾರ್ವಜನಿಕ ಕೀಲಿಯನ್ನು `src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`) ನಲ್ಲಿ ಪಿನ್ ಮಾಡಲಾಗಿದೆ. ಇದು ಒಂದು ಅರೆ ಆಗಿರುವುದರಿಂದ,
ರೊಟೇಶನ್ಗೆ ಮುಂಚಿತವಾಗಿ ಹೊಸ ಕೀಲಿಯನ್ನು ಆರಂಭದಲ್ಲಿ ಸೇರಿಸಬಹುದು; ಇದೇ ವೇಳೆ ಹಿಂದಿನ ಕೀಲಿಯಿಂದ
ಸಹಿ ಮಾಡಲಾದ ಹಳೆಯ ಕ್ಯಾಶ್ ಮಾಡಿದ ಫೀಡ್ಗಳು ಮರು-ಸಿಂಕ್ ಆಗುವವರೆಗೆ ಮಾನ್ಯವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.

### ಫೋರ್ಕ್ಗಳಿಗೆ ಅನುಕೂಲಕರವಾದ env ಓವರ್ರೈಡ್ಗಳು

ಎರಡು env vars ಫೋರ್ಕ್ಗಳು ಮತ್ತು ಸ್ವಯಂ-ಹೋಸ್ಟರ್ಗಳು ಕ್ಲೈಂಟ್ ಅನ್ನು ಡೀಫಾಲ್ಟ್ OmniRoute
ಸೇವೆಯ ಬದಲು ತಮ್ಮದೇ ಫೀಡ್ಗೆ ನಿರ್ದೇಶಿಸಲು ಅನುವು ಮಾಡಿಕೊಡುತ್ತವೆ — ಕೆಳಗಿನ
[ಫೀಡ್ ಅನ್ನು ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡುವುದು ಹೇಗೆ](#how-to-self-host-a-feed) ನೋಡಿ:

| Var                 | ಉದ್ದೇಶ                                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | ಫೀಡ್ನ ಮೂಲ URL ಅನ್ನು ಓವರ್ರೈಡ್ ಮಾಡುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `https://radar.omniroute.online`).                                                |
| `RADAR_FEED_PUBKEY` | ಪಿನ್ ಮಾಡಿದ ಸಾರ್ವಜನಿಕ ಕೀಲಿಯನ್ನು ಓವರ್ರೈಡ್ ಮಾಡುತ್ತದೆ (base64-DER SPKI ಅಥವಾ PEM), ಅಂತರ್ನಿರ್ಮಿತ ಅರೆಯನ್ನು ಈ ಏಕೈಕ ಕೀಲಿಯಿಂದ ಬದಲಾಯಿಸುತ್ತದೆ. |

### ಕನಿಷ್ಠ ಆವೃತ್ತಿ ಮಿತಿ

ಡೌನ್ಲೋಡ್ ಮಾಡಿದ ಫೀಡ್ನ `version`, ಪ್ರಸ್ತುತ ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಆವೃತ್ತಿಗಿಂತ ಕಟ್ಟುನಿಟ್ಟಾಗಿ
ಹೊಸದಾಗಿರದಿದ್ದರೆ `syncRadar()` ಅದನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ (`compareVersions()`,
ಚುಕ್ಕೆಗಳಿಂದ ಬೇರ್ಪಡಿಸಿದ `YYYY.MM.DD.n` ಹೋಲಿಕೆ) — `{ status: "stale" }`. ಇದರಿಂದ
ಹಾನಿಗೊಳಗಾದ ಅಥವಾ ತಪ್ಪಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಫೀಡ್ ಎಂಡ್ಪಾಯಿಂಟ್, ಕ್ಲೈಂಟ್ ಅನ್ನು ಹಳೆಯದಾದ,
ಬೇರೆ ರೀತಿಯಲ್ಲಿ ಸಹಿ ಮಾಡಲಾದ ಪೇಲೋಡ್ಗೆ ಹಿಂದಿರುಗಿಸುವುದನ್ನು ತಡೆಯುತ್ತದೆ.

### ಎರಡು ದಿನಾಂಕಗಳು ಮತ್ತು ಎರಡನ್ನೂ ಏಕೆ ಉಳಿಸಲಾಗಿದೆ

ಕ್ಯಾಶ್ ಮಾಡಿದ ಫೀಡ್ ಎರಡು ವಿಭಿನ್ನ ದಿನಾಂಕಗಳನ್ನು ಹೊಂದಿರುತ್ತದೆ ಮತ್ತು ಅವುಗಳ ನಡುವಿನ ಗೊಂದಲವನ್ನು
ತಪ್ಪಿಸುವುದಕ್ಕಾಗಿಯೇ ಎರಡನ್ನೂ ಉಳಿಸಲಾಗಿದೆ:

| ಫೀಲ್ಡ್        | ಎಲ್ಲಿಂದ ಬರುತ್ತದೆ     | ಯಾವುದಕ್ಕೆ ಉತ್ತರಿಸುತ್ತದೆ                        |
| ------------- | -------------------- | ---------------------------------------------- |
| `generatedAt` | ಸಹಿ ಮಾಡಲಾದ ಫೀಡ್ ಬಾಡಿ | **ಡೇಟಾ** ಎಷ್ಟು ಹಳೆಯದು                          |
| `fetchedAt`   | ಈ ಇನ್ಸ್ಟಾಲ್ನ ಗಡಿಯಾರ  | ಈ ಇನ್ಸ್ಟಾಲ್ ಅದನ್ನು **ಡೌನ್ಲೋಡ್** ಮಾಡಿದ್ದು ಯಾವಾಗ |

ಕೆಲವೇ ನಿಮಿಷಗಳ ಹಿಂದೆ ಪಡೆಯಲಾದ ಫೀಡ್ ವಾರಗಳಷ್ಟು ಹಳೆಯ ಅಂಕಿ-ಅಂಶಗಳನ್ನು ಹೊಂದಿರಬಹುದು,
ಆದ್ದರಿಂದ `fetchedAt` ಮಾತ್ರದಿಂದ ಓವರ್ಲೇ ಅದು ಆಧರಿಸಿರುವ ಬೇಸ್ಲೈನ್ಗಿಂತ ಹೊಸದಾಗಿದೆಯೇ
ಎಂಬುದನ್ನು ಆಪರೇಟರ್ಗೆ ತಿಳಿಯಲು ಸಾಧ್ಯವಿಲ್ಲ. ಎರಡನ್ನೂ `radar_feed_cache` ನಲ್ಲಿ
ಉಳಿಸಲಾಗುತ್ತದೆ, `getRadarCatalog().meta` ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ ಮತ್ತು `GET
/api/radar/status` ಮೂಲಕ ಪ್ರತ್ಯೇಕವಾಗಿ ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ. `generated_at` ಕಾಲಮ್
ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು (ಮೈಗ್ರೇಶನ್ 163) ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಸಾಲನ್ನು `null` ಎಂದು ಓದಲಾಗುತ್ತದೆ
— ಪಡೆಯಲಾದ ಸಮಯವನ್ನು ಬಳಸಿಕೊಳ್ಳುವ ಬದಲು, ತಿಳಿದಿಲ್ಲದ್ದು ತಿಳಿದಿಲ್ಲದಂತೆಯೇ ಉಳಿಯುತ್ತದೆ.
ಮೈಗ್ರೇಶನ್ 142 ರಿಂದ `radar_referrals_cache` ತನ್ನದೇ ಆದ `generated_at` ಅನ್ನು
ಉಳಿಸಿಕೊಂಡಿದೆ.

ಮೇಲಿನ ಕನಿಷ್ಠ ಆವೃತ್ತಿ ಮಿತಿಯು `version` ಅನ್ನು ಹೋಲಿಸುತ್ತದೆ, ಯಾವುದೇ ದಿನಾಂಕವನ್ನಲ್ಲ.

ಎರಡು ಅಂತರಗಳು ಉಳಿದಿವೆ ಮತ್ತು ಎರಡೂ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿವೆ: ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಇನ್ನೂ `Last fetched`
ಅನ್ನು ಮಾತ್ರ ತೋರಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅಲ್ಲಿ ಬಿಲ್ಡ್ ದಿನಾಂಕವನ್ನು ತೋರಿಸಲು ಹೊಸ ಲೇಬಲ್
(ಮತ್ತು ಅದರ 41 ಲೋಕೇಲ್ ನಮೂದುಗಳು) ಅಗತ್ಯವಿದೆ; ಹಾಗೆಯೇ ಆಫರ್ಗಳು ಮತ್ತು ಇಂಟೆಲ್ ಕ್ಯಾಶ್ಗಳು
ಅವುಗಳ ಫೀಡ್ ಸ್ಕೀಮಾಗಳು ಬಿಲ್ಡ್ ದಿನಾಂಕವನ್ನು ಹೊಂದಿದ್ದರೂ ಅದನ್ನು ಉಳಿಸುವುದಿಲ್ಲ — ಆದ್ದರಿಂದ
`GET /api/radar/status`, "ತಿಳಿದಿಲ್ಲ" ಎಂದು ಅರ್ಥವಾಗಬಹುದಾದ `null` ಅನ್ನು ವರದಿ ಮಾಡುವ
ಬದಲು, ಆ ಎರಡು ಫೀಲ್ಡ್ಗಳಿಗೆ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

### ಸ್ಕೀಮಾ ಮೌಲ್ಯೀಕರಣ

ಡೌನ್ಲೋಡ್ ಮಾಡಿದ ಬೈಟ್ಗಳನ್ನು ಸಹಿ ಪರಿಶೀಲನೆಯ **ನಂತರ** `RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`, ಒಂದು Zod ಸ್ಕೀಮಾ) ವಿರುದ್ಧ ಪಾರ್ಸ್ ಮಾಡಿ ಮೌಲ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ.
ಸ್ಕೀಮಾ ಹೊಂದಿಕೆಯಾಗದಿದ್ದರೆ `{ status: "invalid_schema" }` ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
ಕ್ಯಾಶ್ ಅನ್ನು ಮುಟ್ಟಲಾಗುವುದಿಲ್ಲ. ಪ್ರತಿ ಓದುವಿಕೆಯಲ್ಲೂ (`getRadarCatalog()`) ಕ್ಯಾಶ್ ಮಾಡಿದ
ಪೇಲೋಡ್ ಅನ್ನು ರಕ್ಷಣಾತ್ಮಕವಾಗಿ ಮತ್ತೆ ಮೌಲ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ — ಹಾಳಾದ ಅಥವಾ ಕೈಯಿಂದ
ಸಂಪಾದಿಸಲಾದ ಕ್ಯಾಶ್ ಸಾಲನ್ನು ನೀಡುವ ಬದಲು ಬೇಸ್ಲೈನ್ಗೆ ಫಾಲ್ಬ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತದೆ.

### ಪ್ರತಿಕ್ರಿಯೆ ಗಾತ್ರದ ಮಿತಿ (10 MB)

`syncRadar()` ಫೀಡ್ ಪ್ರತಿಕ್ರಿಯೆ ಬಾಡಿಗೆ **10 MB ಕಠಿಣ ಮಿತಿಯನ್ನು** ಜಾರಿಗೊಳಿಸುತ್ತದೆ —
ಸಹಿ ಮಾಡಲಾದ ಫೀಡ್ KB-ಮಟ್ಟದ JSON ಡಾಕ್ಯುಮೆಂಟ್ ಆಗಿರುವುದರಿಂದ, ಇದಕ್ಕಿಂತ ಹೆಚ್ಚಿನ ಗಾತ್ರವು
ಮಾನ್ಯ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಸೂಚಿಸುವುದಿಲ್ಲ; ಬದಲಾಗಿ ತಪ್ಪಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಅಥವಾ ದುರುದ್ದೇಶಪೂರಿತ
`RADAR_FEED_URL` (ಅಥವಾ ಅಸಂಬದ್ಧ ಡೇಟಾವನ್ನು ನೀಡುತ್ತಿರುವ ಅಪ್ಸ್ಟ್ರೀಮ್) ಅನ್ನು ಸೂಚಿಸುತ್ತದೆ.
ಈ ಜಾರಿಗೊಳಿಸುವಿಕೆಯು ಎರಡು ಪದರಗಳನ್ನು ಹೊಂದಿದೆ:

1. ಹೆಡರ್ ಈಗಾಗಲೇ ಮಿತಿಗಿಂತ ಹೆಚ್ಚಿನ ಮೌಲ್ಯವನ್ನು ಘೋಷಿಸಿದಾಗ, `Content-Length`
   ಪ್ರೀಫ್ಲೈಟ್ ಪರಿಶೀಲನೆಯು ಬಾಡಿಯನ್ನು ಓದುವುದನ್ನೇ ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.
2. ಬಾಡಿಯನ್ನು ಓದುವಾಗ ಚಾಲನೆಯಲ್ಲಿರುವ ಒಟ್ಟು ಗಾತ್ರದ ಪರಿಶೀಲನೆಯು `Content-Length`
   ಇಲ್ಲದಿದ್ದರೂ ಅಥವಾ ನಿಜವಾದ ಗಾತ್ರವನ್ನು ಕಡಿಮೆ ತೋರಿಸಿದರೂ ಮಿತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ —
   ಹೆಡರ್ ಒಂದನ್ನೇ ಎಂದಿಗೂ ನಂಬಲಾಗುವುದಿಲ್ಲ. ಸಂಗ್ರಹಿಸಿದ ಚಂಕ್ಗಳನ್ನು ಒಟ್ಟುಗೂಡಿಸುವುದರಿಂದ
   ನಂತರದ Ed25519 ಸಹಿ ಪರಿಶೀಲನೆಗೆ ಅಗತ್ಯವಿರುವ ನಿಖರ ಬೈಟ್ಗಳು ಸಂರಕ್ಷಿಸಲ್ಪಡುತ್ತವೆ.

ಮಿತಿಯನ್ನು ಮೀರಿದರೆ `{ status: "too_large" }` ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಕ್ಯಾಶ್ ಅನ್ನು
ಮುಟ್ಟಲಾಗುವುದಿಲ್ಲ; ಇದು ಇತರ ಪ್ರತಿಯೊಂದು ಸಿಂಕ್ ವೈಫಲ್ಯದಂತೆಯೇ ವಿನಾಶಕಾರಿಯಲ್ಲದ ಮಾದರಿಯನ್ನು
ಅನುಸರಿಸುತ್ತದೆ (`invalid_signature`, `invalid_schema`, `stale`).

## ಶ್ರೇಣಿಗಳು: `community` ಮತ್ತು `live`

ಫೀಡ್ ಸ್ಕೀಮಾ `tier: "community" | "live"` ಕ್ಷೇತ್ರವನ್ನು ಹೊಂದಿರುತ್ತದೆ; ಇದನ್ನು ವಿನಂತಿಯ ಆಧಾರದ ಮೇಲೆ (ಬೆಂಬಲಿಗರ ಕೀ ಇರುವಿಕೆ ಮತ್ತು ಅದರ ಮಾನ್ಯತೆ) ಫೀಡ್ ಸೇವೆಯು **ಸರ್ವರ್-ಸೈಡ್ನಲ್ಲಿ** ನಿರ್ಧರಿಸುತ್ತದೆ
— ಕ್ಲೈಂಟ್ ತನ್ನ ಸ್ವಂತ ಶ್ರೇಣಿಯನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

- **`community`** — ಅತ್ಯಂತ ಇತ್ತೀಚಿನ ಡೇಟಾಕ್ಕಿಂತ ಸರಿಸುಮಾರು 30 ದಿನ ವಿಳಂಬವಾಗಿರುವ ಉಚಿತ ಕ್ಯಾಟಲಾಗ್.
  ದೃಢೀಕರಣವಿಲ್ಲದ ಅಥವಾ ಅಮಾನ್ಯ ಕೀ ಹೊಂದಿರುವ ವಿನಂತಿಗೆ ಇದು ದೊರೆಯುತ್ತದೆ.
- **`live`** — ಮಾನ್ಯ ಬೆಂಬಲಿಗರ ಕೀ ಹೊಂದಿರುವ ವಿನಂತಿಗಳಿಗೆ ಒದಗಿಸಲಾಗುವ ಅತ್ಯಂತ ಇತ್ತೀಚಿನ ಕ್ಯಾಟಲಾಗ್.

**ಅಮಾನ್ಯ ಅಥವಾ ಅವಧಿ ಮುಗಿದ ಬೆಂಬಲಿಗರ ಕೀ `community` ಗೆ ಇಳಿಯುತ್ತದೆ — ಅದು ಎಂದಿಗೂ
ದೋಷವಲ್ಲ.** ಸಿಂಕ್ ಪಥವು ಸಹಿ/ಸ್ಕೀಮಾ/ಆವೃತ್ತಿ ವೈಫಲ್ಯಗಳನ್ನು (ಎಲ್ಲವೂ
ಚೇತರಿಸಿಕೊಳ್ಳಬಹುದಾದವು, ಎಲ್ಲವೂ ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಸ್ಥಿತಿಗೆ ಮಾರಕವಲ್ಲದವು) ಯಶಸ್ವಿ `{ status:
"updated", version, tier }` ನಿಂದ ಮಾತ್ರ ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ. ಕ್ಲೈಂಟ್ ನಿರ್ವಹಿಸಬೇಕಾದ
ಯಾವುದೇ ಶ್ರೇಣಿ-ನಿರ್ದಿಷ್ಟ ದೋಷ ಪಥವಿಲ್ಲ.

### ಒದಗಿಸಲಾದ ಶ್ರೇಣಿಯು ಪ್ರತಿಕ್ರಿಯೆ ಹೆಡರ್ನಿಂದ ಬರುತ್ತದೆ, ಸಹಿ ಮಾಡಲಾದ ಬಾಡಿಯಿಂದಲ್ಲ

ಸಹಿ ಮಾಡಲಾದ ಫೀಡ್ **ಬಾಡಿ**ಯ `tier` ಕ್ಷೇತ್ರವು ಯಾವಾಗಲೂ `"live"` ಆಗಿರುತ್ತದೆ — ಫೀಡ್ ಸೇವೆಯು
**ಪ್ರತಿ ಆವೃತ್ತಿಗೆ ಎರಡು ಸಹಿ ಮಾಡಲಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳನ್ನು** ಕಳುಹಿಸುತ್ತದೆ: live ಪ್ರಸ್ತುತ ಅಭಿಯಾನಗಳನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ ಮತ್ತು community
ಅವುಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗೂ ಅದರದೇ ನಿಖರ ಬೈಟ್ಗಳ ಮೇಲೆ ಸಹಿ ಮಾಡಲಾಗುತ್ತದೆ. ಬಾಡಿ ಇನ್ನೂ
ಅರ್ಹತಾ ನಿರ್ಧಾರದ ಮೂಲವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುವುದಿಲ್ಲ; ವಿನಂತಿಗೆ ವಾಸ್ತವವಾಗಿ ಆಯ್ಕೆ ಮಾಡಲಾದ ಶ್ರೇಣಿಯನ್ನು
**`x-omniroute-feed-tier` ಪ್ರತಿಕ್ರಿಯೆ ಹೆಡರ್ನಲ್ಲಿ** ಸಾಗಿಸಲಾಗುತ್ತದೆ, ಇದನ್ನು ವಿನಂತಿಯ
`Authorization` ಕೀಯಿಂದ ಸರ್ವರ್-ಸೈಡ್ನಲ್ಲಿ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ.

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) ಕ್ಲೈಂಟ್ ನಂಬಬೇಕಾದ
ಶ್ರೇಣಿಯನ್ನು ನಿರ್ಧರಿಸುವ ಏಕೈಕ ಸ್ಥಳವಾಗಿದೆ:

1. `x-omniroute-feed-tier` ಅನ್ನು `RadarTierSchema` (Zod) ಮೂಲಕ ಪಾರ್ಸ್ ಮಾಡಿ — ಹೆಡರ್ ಇಲ್ಲದಿದ್ದರೆ, ಅಥವಾ
   ಅದರ ಮೌಲ್ಯವು ನಿಖರವಾಗಿ `"community"` ಅಥವಾ `"live"` ಆಗಿರದಿದ್ದರೆ, ಅದನ್ನು **ಇಲ್ಲವೆಂದು
   ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ** (ಇದ್ದಂತೆಯೇ ಕ್ಯಾಶ್/UI ಒಳಗೆ ಎಂದಿಗೂ ನಂಬಲಾಗುವುದಿಲ್ಲ; ಹೆಡರ್ಗಿಂತ ಹಿಂದಿನ ಹಳೆಯ ಫೀಡ್
   ಸರ್ವರ್ಗಳನ್ನೂ ಇದು ಒಳಗೊಳ್ಳುತ್ತದೆ).
2. ಹಂತ 1 ಏನನ್ನೂ ನೀಡದಿದ್ದಾಗ ಮಾತ್ರ ಸಹಿ ಮಾಡಲಾದ ಬಾಡಿಯ `tier` ಕ್ಷೇತ್ರಕ್ಕೆ (ಯಾವಾಗಲೂ `"live"`) ಹಿಂತಿರುಗಿ.
3. ನಿರ್ಧರಿಸಲಾದ ಶ್ರೇಣಿಯನ್ನೇ ಕ್ಯಾಶ್ ಮಾಡಿ `{ status: "updated",
version, tier }` ಎಂದು ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ — ಡ್ಯಾಶ್ಬೋರ್ಡ್ ತೋರಿಸುವುದು ಈ ಮೌಲ್ಯವನ್ನೇ ಹೊರತು ಕಚ್ಚಾ ಬಾಡಿ
   ಕ್ಷೇತ್ರವನ್ನಲ್ಲ.

## ಓದುವ-ಸಮಯದ ಓವರ್ಲೇ ವಿಲೀನ ನಿಯಮಗಳು

`applyFeed()` (`src/lib/radar/applyFeed.ts`) ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಫೀಡ್ ಅನ್ನು
ಸ್ಥಿರ ಬೇಸ್ಲೈನ್ನ **ಮೇಲೆ**, `getRadarCatalog()` ಒಳಗೆ **ಓದುವ ಸಮಯದಲ್ಲಿ** ವಿಲೀನಗೊಳಿಸುತ್ತದೆ. ಬೇಸ್ಲೈನ್ ಅರೇ
(`FREE_MODEL_BUDGETS`) ಅನ್ನು ಎಂದಿಗೂ ಬದಲಾಯಿಸಲಾಗುವುದಿಲ್ಲ — ಪ್ರತಿ ಕರೆಯಲ್ಲೂ ಹೊಸದಾಗಿ `MergedEntry[]` ಅನ್ನು ಲೆಕ್ಕಹಾಕಲಾಗುತ್ತದೆ.

ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ನಾಲ್ಕು ನಿಯಮಗಳು:

1. **ಫೀಡ್ ಎಂದಿಗೂ ಸ್ಥಳೀಯ ಓವರ್ರೈಡ್ ಅನ್ನು ತಿದ್ದಿಬರೆಯುವುದಿಲ್ಲ.** ಪ್ರತಿ-ಕ್ಷೇತ್ರಕ್ಕೆ: ಆಪರೇಟರ್ ಒಂದು ಎಂಟ್ರಿಯ
   ಕ್ಷೇತ್ರವನ್ನು ಕಸ್ಟಮೈಸ್ ಮಾಡಿದ್ದರೆ (`localOverrides` ಮ್ಯಾಪ್, `provider:modelId` ಕೀ ಆಧಾರಿತ),
   ಆ ನಿರ್ದಿಷ್ಟ ಕ್ಷೇತ್ರಕ್ಕಾಗಿ ಫೀಡ್ನ ಮೌಲ್ಯವನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ — ಆಪರೇಟರ್ನ ಮೌಲ್ಯವೇ ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತದೆ.
2. **`enabled: false` ಎಂಟ್ರಿಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಅದರ ಮೂಲವನ್ನೂ ದಾಖಲಿಸುತ್ತದೆ.** ಒಂದು ಎಂಟ್ರಿಯನ್ನು
   ಆಫ್ ಮಾಡುವ ಫೀಡ್ ಎಂಟ್ರಿಯು ವಿಲೀನಗೊಂಡ ಫಲಿತಾಂಶದಲ್ಲಿ `enabled: false` ಮತ್ತು `disabledBy: "radar"` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ,
   ಹೀಗಾಗಿ ಒಂದು ಎಂಟ್ರಿ ಲಭ್ಯದಿಂದ ನಿಷ್ಕ್ರಿಯಗೊಂಡದ್ದು _ಏಕೆ_ ಎಂಬುದನ್ನು UI ವಿವರಿಸಬಹುದು.
3. **ಫೀಡ್ನಲ್ಲಿ ಇಲ್ಲದ, ಬಳಕೆದಾರರು ಸೇರಿಸಿದ ಎಂಟ್ರಿ ಯಾವುದೇ ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಉಳಿಯುತ್ತದೆ.** ಕೇವಲ
   ಬೇಸ್ಲೈನ್ನಲ್ಲಿ ಇರುವ (ಅಥವಾ ಸ್ಥಳೀಯವಾಗಿ ಸೇರಿಸಲಾದ) ಮತ್ತು ಅದಕ್ಕೆ ಹೊಂದುವ ಫೀಡ್
   ಎಂಟ್ರಿ ಇಲ್ಲದ ಎಂಟ್ರಿಗಳು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಮುಂದುವರಿಯುತ್ತವೆ.
4. **ಟೂಂಬ್ಸ್ಟೋನ್ ಮಾಡಲಾದ ಎಂಟ್ರಿಯನ್ನು ಎಂದಿಗೂ ಪುನರುಜ್ಜೀವನಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ.** ಆಪರೇಟರ್ ಸ್ಪಷ್ಟವಾಗಿ ಒಂದು
   ಎಂಟ್ರಿಯನ್ನು ಅಳಿಸಿದ್ದರೆ (`tombstones` ಸೆಟ್), ನಂತರದ ಆವೃತ್ತಿಯಲ್ಲಿ ಫೀಡ್ ಆ `provider:modelId` ಅನ್ನು
   ಮರುಸೇರಿಸಿದರೂ ಅದು ಮತ್ತೆ ಬರುವುದಿಲ್ಲ.

ಸಂಪಾದಿಸಬಹುದಾದ ಕ್ಷೇತ್ರಗಳು ಮತ್ತು ಟೂಂಬ್ಸ್ಟೋನ್ಗಳನ್ನು
`radar_local_model_state` ನಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ (ಮೈಗ್ರೇಶನ್ `153_radar_local_model_state.sql`). ಸಾರ್ವಜನಿಕ DB
ಅಡಾಪ್ಟರ್ (`src/lib/db/radar.ts`) ಆ ಸಾಲುಗಳನ್ನು `applyFeed()` ಬಳಸುವ `localOverrides` ಮ್ಯಾಪ್ ಮತ್ತು
`tombstones` ಸೆಟ್ ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ; ಪ್ರೊಡಕ್ಷನ್ `getRadarCatalog()` ಫ್ಲ್ಯಾಗ್, ಕ್ಯಾಶ್ ಮತ್ತು ಸ್ಕೀಮಾ
ಗೇಟ್ಗಳನ್ನು ದಾಟಿದ ನಂತರ ಆ ಸ್ಥಿತಿಯನ್ನು ಲೋಡ್ ಮಾಡುತ್ತದೆ. `displayName` ಮತ್ತು `enabled` ಮಾತ್ರ
ಆಪರೇಟರ್ನಿಂದ ಸಂಪಾದಿಸಬಹುದಾದವು. ಪೂರೈಕೆದಾರ/ಮಾದರಿ ಗುರುತು, ಫೀಡ್ ಮೂಲ, ಕೋಟಾ, ಸಾಮರ್ಥ್ಯಗಳು, ToS,
ಮತ್ತು ಸೆಟಪ್ ಡೇಟಾವನ್ನು ಈ ಮೇಲ್ಮೈ ಮೂಲಕ ಬರೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಡ್ಯಾಶ್ಬೋರ್ಡ್ ನಾಲ್ಕು ಸ್ಥಳೀಯ ಕ್ರಿಯೆಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

- **ಸಂಪಾದಿಸಿ** ಸ್ಥಳೀಯ ಪ್ರದರ್ಶನ ಹೆಸರು ಮತ್ತು ಸಕ್ರಿಯಗೊಳಿಸಿದ ಸ್ಥಿತಿಯನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.
- **ಸ್ಥಳೀಯ ಬದಲಾವಣೆಗಳನ್ನು ಮರುಹೊಂದಿಸಿ** ಟೂಂಬ್ಸ್ಟೋನ್ ಅನ್ನು ಬದಲಾಯಿಸದೆ ಸಂಪಾದಿಸಬಹುದಾದ ಎರಡೂ ಕ್ಷೇತ್ರಗಳನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.
- **ಮರೆಮಾಡಿ** ಟೂಂಬ್ಸ್ಟೋನ್ ಅನ್ನು ರಚಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ನಂತರದ ಫೀಡ್ ಅಪ್ಡೇಟ್ಗಳು ಸಾಲನ್ನು ಮರುರಚಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.
- **ಮರುಸ್ಥಾಪಿಸಿ** ಟೂಂಬ್ಸ್ಟೋನ್ ಅನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ; ಪ್ರತ್ಯೇಕವಾಗಿ ಉಳಿಸಲಾದ ಯಾವುದೇ ಓವರ್ರೈಡ್ ಜಾರಿಯಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ.

ಫೀಡ್ನ `enabled: false` ಸುರಕ್ಷತಾ ಅಪವಾದವಾಗಿ ಉಳಿಯುತ್ತದೆ: ಇದು ಹಳೆಯದಾದ ಸ್ಥಳೀಯ
`enabled: true` ಗಿಂತ ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತದೆ, ವಿಲೀನಗೊಂಡ ಎಂಟ್ರಿಯನ್ನು ನಿಷ್ಕ್ರಿಯವಾಗಿಯೇ ಇರಿಸುತ್ತದೆ ಮತ್ತು `disabledBy: "radar"` ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ.

ಕ್ಯಾಟಲಾಗ್ ಪ್ರಕಟಣೆಗಳು `schemaVersion: 2` ಅನ್ನು ಬಳಸುತ್ತವೆ. `contextWindow` ಹಾಗೂ `tools`, `vision`, ಮತ್ತು
`thinking` ಪ್ರತಿಯೊಂದೂ ಸ್ವತಂತ್ರವಾಗಿ `number | null` / `boolean | null` ಆಗಿರುತ್ತವೆ: `null` ಎಂದರೆ ತಿಳಿದಿಲ್ಲ ಎಂದರ್ಥ, ಆದರೆ
`false` ಎಂದರೆ ಸಾಮರ್ಥ್ಯ ಇಲ್ಲವೆಂದು D16-ದೃಢೀಕರಿಸಿದ ಅಧಿಕೃತ ಪೂರೈಕೆದಾರ ಮೂಲವು ಸ್ಪಷ್ಟವಾಗಿ ಹೇಳುತ್ತದೆ ಎಂದರ್ಥ.
ಆಂತರಿಕ OmniRoute ರಿಜಿಸ್ಟ್ರಿ/ಮಾದರಿ-ಸ್ಪೆಕ್ ಫ್ಲ್ಯಾಗ್ಗಳನ್ನು ಎಂದಿಗೂ ನೇರವಾಗಿ ಫೀಡ್ ವಾಸ್ತವಾಂಶಗಳನ್ನಾಗಿ ಬಡ್ತಿ ನೀಡಲಾಗುವುದಿಲ್ಲ. ಕ್ಲೈಂಟ್
ಇನ್ನೂ v1 ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಳನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ; ಹಳೆಯ ಬಿಲ್ಡರ್ ಅನುಪಸ್ಥಿತಿಯ ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ ಆಗಿ `false` ಅನ್ನು ಬಳಸಿದ್ದರಿಂದ, v1 `false` ಅನ್ನು
ತಿಳಿದಿಲ್ಲ ಎಂದು ಸಾಮಾನ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ, ಆದರೆ v1 `true` ವಾಸ್ತವಿಕವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ತಿಳಿದಿಲ್ಲದ ಸ್ಕೀಮಾ ಆವೃತ್ತಿಗಳು ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ ಮತ್ತು
ಕೊನೆಯ ಮಾನ್ಯ ಕ್ಯಾಶ್ ಲಭ್ಯವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ. null ಅಲ್ಲದ ಕಾಂಟೆಕ್ಸ್ಟ್/ಸಾಮರ್ಥ್ಯವನ್ನು ಹೊಂದಿರುವ ಪ್ರತಿ v2 ಮಾದರಿಯೂ
ರುಜುವಾತು-ಮುಕ್ತ HTTPS `metadataEvidenceUrls[]` ಅನ್ನು ಹೊಂದಿರಬೇಕು; ಇಲ್ಲದಿದ್ದರೆ ಸ್ಕೀಮಾ ಮೌಲ್ಯೀಕರಣವು ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಕ್ಯಾಶ್ ಅನ್ನು
ಬದಲಾಯಿಸಲಾಗುವುದಿಲ್ಲ. ಕ್ಯಾಟಲಾಗ್ ಟೇಬಲ್ ಎಲ್ಲಾ ಮೂರು ಸ್ಥಿತಿಗಳನ್ನು `✓`, `✕`, ಮತ್ತು `?` ರೂಪದಲ್ಲಿ ತೋರಿಸುತ್ತದೆ.

### ಮಾರ್ಗದರ್ಶಿತ ಕಾಂಬೊಗಳು ಮತ್ತು MCP ಪ್ರವೇಶ

ದೃಢೀಕರಿಸಲಾದ `familyId` ಮೌಲ್ಯಗಳು ಓದುವ-ಸಮಯದ ಓವರ್ಲೇಯಲ್ಲಿ ಉಳಿದುಕೊಂಡು ಶುದ್ಧ
`buildRadarComboSuggestions()` ಮಾಡ್ಯೂಲ್ಗೆ (`src/lib/radar/comboSuggestions.ts`) ಚಾಲನೆ ನೀಡುತ್ತವೆ. ಕನಿಷ್ಠ ಎರಡು ವಿಭಿನ್ನ
ಪೂರೈಕೆದಾರರು ಸಕ್ರಿಯ ಸಂಪರ್ಕಗಳನ್ನು ಹೊಂದಿದ್ದು, ನಿಖರವಾಗಿ ಕ್ಯುರೇಟ್ ಮಾಡಲಾದ ಮಾದರಿ ID ಅನ್ನು ಒದಗಿಸಿದಾಗ ಮಾತ್ರ ಒಂದು ಕುಟುಂಬವನ್ನು ಸೂಚಿಸಲಾಗುತ್ತದೆ.
ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಮಾದರಿಗಳು, ನಿಷ್ಕ್ರಿಯ ಪೂರೈಕೆದಾರರು, ಕಾಣೆಯಾದ ಮಾದರಿ IDಗಳು, ಒಂದೇ ಸದಸ್ಯದ ಕುಟುಂಬಗಳು ಮತ್ತು ಅಸ್ಪಷ್ಟ
ಅಲಿಯಾಸ್/ಪ್ರಿಫಿಕ್ಸ್ ಹೊಂದಾಣಿಕೆಗಳು ಸುರಕ್ಷಿತವಾಗಿ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ. ಸಲಹೆಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ `priority` ತಂತ್ರವನ್ನು ಬಳಸುತ್ತವೆ ಮತ್ತು
ಅತಿದೊಡ್ಡ ಮರುಕಳಿಸುವ ಮಾಸಿಕ ಬಜೆಟ್ ಅನ್ನು ಮೊದಲು ಕ್ರಮಗೊಳಿಸುತ್ತವೆ; UI ಅವುಗಳನ್ನು `POST /api/combos` ಮೂಲಕ ಮಾತ್ರ ರಚಿಸುತ್ತದೆ.

ಮಾರ್ಗದರ್ಶಿತ UI `/dashboard/radar/combos` ನಲ್ಲಿ ಲಭ್ಯವಿದೆ. ಇದು ಸ್ಥಳೀಯ
`GET /api/radar/catalog` ಮತ್ತು `GET /api/combos/builder/options` ಎಂಡ್ಪಾಯಿಂಟ್ಗಳನ್ನು ಮಾತ್ರ ಓದುತ್ತದೆ. ಇದು ಎಂದಿಗೂ Radar ಸಿಂಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸುವುದಿಲ್ಲ,
ಪೂರೈಕೆದಾರರ ರುಜುವಾತುಗಳನ್ನು ಓದುವುದಿಲ್ಲ ಅಥವಾ ಕಾಂಬೊ ಡೇಟಾಬೇಸ್ಗೆ ನೇರವಾಗಿ ಬರೆಯುವುದಿಲ್ಲ.

MCP ಕ್ಲೈಂಟ್ಗಳು ಅದೇ ಸ್ಥಳೀಯ ಪ್ರೊಜೆಕ್ಷನ್ ಅನ್ನು `omniroute_radar_catalog` (`read:radar`) ಮೂಲಕ ಓದಬಹುದು. ಐಚ್ಛಿಕ
`provider`, `familyId`, ಮತ್ತು `enabledOnly` ಫಿಲ್ಟರ್ಗಳನ್ನು ಒಂದು ಸ್ಥಳೀಯ
`GET /api/radar/catalog` ಓದುವಿಕೆಯ ನಂತರ ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ. ಇದರ ನಿರ್ಬಂಧಿತ ಔಟ್ಪುಟ್ನಲ್ಲಿ ಕ್ಯಾಟಲಾಗ್ ಮೆಟಾಡೇಟಾ ಜೊತೆಗೆ ಪೂರೈಕೆದಾರ/ಮಾದರಿ,
ಪ್ರದರ್ಶನ ಹೆಸರು, `familyId`, ಕೋಟಾ, ಸಾಮರ್ಥ್ಯಗಳು, ಸಕ್ರಿಯ ಸ್ಥಿತಿ, ಮೂಲ ಮತ್ತು `disabledBy` ಸೇರಿರುತ್ತವೆ; ಸೆಟಪ್ URLಗಳು,
ಹಂತಗಳು, ಸಂಪರ್ಕಗಳು, ಇ-ಮೇಲ್ ವಿಳಾಸಗಳು, ಕೀಗಳು ಮತ್ತು ರೆಫರಲ್ ಡೇಟಾವನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ. ಈ ಉಪಕರಣವು
ಓದಲು ಮಾತ್ರ ಮೀಸಲಾಗಿದ್ದು, ಎಂದಿಗೂ `/api/radar/sync` ಅನ್ನು ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ.

### ಮೂಲೋತ್ಪತ್ತಿ ಗುರುತುಗಳು

ವಿಲೀನಗೊಂಡ ಪ್ರತಿಯೊಂದು ನಮೂದು UI ಬ್ಯಾಡ್ಜ್ ಆಗಿ ಪ್ರದರ್ಶಿಸುವ `origin` ಫೀಲ್ಡ್ ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ:

- `"baseline"` — ಸ್ಥಿರ ಬಿಡುಗಡೆ ಕ್ಯಾಟಲಾಗ್ನಿಂದ ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲದೆ ಉಳಿದಿದೆ.
- `"radar"` — ಒಂದು ಅಥವಾ ಹೆಚ್ಚಿನ ಫೀಲ್ಡ್ಗಳನ್ನು ಫೀಡ್ನಿಂದ ರಿಫ್ರೆಶ್ ಮಾಡಲಾಗಿದೆ.
- `"local"` — ಆಪರೇಟರ್ ಈ ನಮೂದಿನಲ್ಲಿ ಕನಿಷ್ಠ ಒಂದು ಸ್ಥಳೀಯ ಓವರ್ರೈಡ್ ಹೊಂದಿದ್ದಾರೆ (ಫೀಡ್ ಏನು ಹೇಳಿದರೂ,
  ನಿಯಮ 1 ರ ಪ್ರಕಾರ ಸ್ಥಳೀಯ ಓವರ್ರೈಡ್ಗಳೇ ಯಾವಾಗಲೂ ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತವೆ).

**ಕಠಿಣ ನಿಯಮ: ಈ ರೂಟ್ಗಳು ಎಂದಿಗೂ ಫೀಡ್ ಸೇವೆಯನ್ನು ಪ್ರಾಕ್ಸಿ ಮಾಡುವುದಿಲ್ಲ.** ಬ್ರೌಸರ್ ಯಾವಾಗಲೂ
ಸ್ಥಳೀಯ OmniRoute ಸರ್ವರ್ನೊಂದಿಗೆ ಮಾತ್ರ ಸಂವಹನ ನಡೆಸುತ್ತದೆ. Radar ಸೇವೆಯನ್ನು ಸಂಪರ್ಕಿಸುವ ನಾಲ್ಕು ಮಾಡ್ಯೂಲ್ಗಳು
`src/lib/radar/sync.ts` (ಕ್ಯಾಟಲಾಗ್), `src/lib/radar/referralsSync.ts` (ರೆಫರಲ್ಗಳು), ಮತ್ತು
`src/lib/radar/offersSync.ts` (ಆಫರ್ಗಳು), ಜೊತೆಗೆ `src/lib/radar/intelSync.ts` (Intel); ಇವೆಲ್ಲವೂ
ಸರ್ವರ್ ಬದಿಯಲ್ಲಿ ಚಲಿಸುತ್ತವೆ, ಕ್ಲೈಂಟ್ ಬದಿಯಲ್ಲಿ ಎಂದಿಗೂ ಅಲ್ಲ. ಇದು
ಫೀಡ್ URL ಮತ್ತು ಯಾವುದೇ ಬೆಂಬಲಿಗರ ಕೀ ಅನ್ನು ಕ್ಲೈಂಟ್ಗೆ ಗೋಚರಿಸುವ ನೆಟ್ವರ್ಕ್ ಟ್ರಾಫಿಕ್ನಿಂದ ಸಂಪೂರ್ಣವಾಗಿ ಹೊರಗಿಡುತ್ತದೆ.

`RADAR_ENABLED` ಆಫ್ ಆಗಿರುವಾಗ ಎಲ್ಲಾ Radar ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು `404` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ (ಮೇಲಿನ
[ಫ್ಲ್ಯಾಗ್](#flag-radar_enabled-default-off) ನೋಡಿ), ಮತ್ತು ರೆಪೊ-ವ್ಯಾಪಿ ದೋಷ-ಸ್ಯಾನಿಟೈಸೇಶನ್ ನಿಯಮದ ಪ್ರಕಾರ
(`docs/security/ERROR_SANITIZATION.md`) ರೂಟ್ ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು
`buildErrorBody()`/`sanitizeErrorMessage()` ಮೂಲಕ ಕಳುಹಿಸುತ್ತವೆ.

### ದೃಢೀಕರಣ

ಎಲ್ಲಾ Radar ಎಂಡ್ಪಾಯಿಂಟ್ಗಳಿಗೆ `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) ಮೂಲಕ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ — ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್ ಕುಕಿ ಅಥವಾ ನಿರ್ವಹಣೆ-ವ್ಯಾಪ್ತಿಯ
API ಕೀ; ಇದು ಉಳಿದ `/api/settings/*` ಅನ್ನು ರಕ್ಷಿಸುವ ಅದೇ ಗೇಟ್ ಆಗಿದೆ. ಫ್ಲ್ಯಾಗ್-ಆಫ್
`404` ಪರಿಶೀಲನೆಯು ಯಾವಾಗಲೂ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗಿಂತ **ಮೊದಲು** ಚಲಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ `RADAR_ENABLED`
ಆಫ್ ಆಗಿರುವ ಇನ್ಸ್ಟಾಲ್ ಬೈಟ್-ಮಟ್ಟದಲ್ಲಿ ಒಂದೇ ರೀತಿಯಾಗಿ ಉಳಿಯುತ್ತದೆ (ಮೇಲ್ಮೈ ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲವೆಂದು ತಿಳಿಯಲು ಮಾತ್ರ ದೃಢೀಕರಣ ಪ್ರಾಂಪ್ಟ್ ಇಲ್ಲ);
ಫ್ಲ್ಯಾಗ್ ಆನ್ ಆದ ನಂತರ, ಯಾವುದೇ DB ಓದು ಅಥವಾ
ಬರಹಕ್ಕೂ ಮೊದಲು ದೃಢೀಕರಿಸದ ವಿನಂತಿಗೆ `401` ದೊರೆಯುತ್ತದೆ. ದೃಢೀಕರಣ ಸ್ಥಿತಿ ಏನೇ ಇರಲಿ,
`GET /api/radar/settings` ಕಚ್ಚಾ ಬೆಂಬಲಿಗರ ಕೀ ಅನ್ನು ಎಂದಿಗೂ ಹಿಂತಿರುಗಿಸುವುದಿಲ್ಲ —
ಮಾಸ್ಕ್ ಮಾಡಿದ ರೂಪ ಮತ್ತು `hasSupporterKey` ಬೂಲಿಯನ್ ಅನ್ನು ಮಾತ್ರ ಹಿಂತಿರುಗಿಸುತ್ತದೆ.

## ಬೆಂಬಲಿಗರ ಕೊಡುಗೆಗಳು

ಕೊಡುಗೆಗಳು ತಮ್ಮದೇ ಸಹಿ ಮಾಡಿದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್, `GET /v1/offers/latest`, ಅನ್ನು ಬಳಸುತ್ತವೆ ಮತ್ತು ಕ್ಯಾಟಲಾಗ್ ಅಥವಾ
ರೆಫರಲ್ಗಳ ಕ್ಯಾಶ್ ಅನ್ನು ಎಂದಿಗೂ ಹಂಚಿಕೊಳ್ಳುವುದಿಲ್ಲ. ಸರ್ವರ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಮಾನ್ಯವಾದ ಸಕ್ರಿಯ ಬೆಂಬಲಿಗರ Bearer ಕೀ ಅಗತ್ಯವಿದೆ;
ಸಮುದಾಯ ಆಧಾರಿತ ಪರ್ಯಾಯ ವ್ಯವಸ್ಥೆ ಇಲ್ಲ. ಆದ್ದರಿಂದ ವೈಶಿಷ್ಟ್ಯ ಫ್ಲ್ಯಾಗ್ ಆಫ್ ಆಗಿದ್ದರೆ, ಆಪರೇಟರ್ ಆಯ್ಕೆಮಾಡಿ ಸೇರಿರದಿದ್ದರೆ,
ಅಥವಾ ಯಾವುದೇ ಬೆಂಬಲಿಗರ ಕೀ ಕಾನ್ಫಿಗರ್ ಆಗಿರದಿದ್ದರೆ `syncRadarOffers()` ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶಿಸುವ ಮೊದಲೇ ನಿಲ್ಲುತ್ತದೆ.

GET ಯಶಸ್ವಿಯಾದ ನಂತರ, ಕ್ಲೈಂಟ್ ನಿಖರವಾದ ಪ್ರತಿಕ್ರಿಯೆ ಬೈಟ್ಗಳ ಮೇಲಿನ Ed25519 ಸಹಿಯನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ,
`RadarOffersFeedSchema` ಅನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ, ಸಹಿ ಮಾಡಿದ ಬಾಡಿ ಮತ್ತು
`x-omniroute-feed-tier` ಹೆಡರ್ ಎರಡೂ `live` ಎಂದು ಸೂಚಿಸುವುದನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ, ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಹೊಸದಾದ ಡಾಟ್ಗಳಿಂದ
ಬೇರ್ಪಡಿಸಿದ ಆವೃತ್ತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಆನಂತರವೇ `radar_offers_cache` ಅನ್ನು ಅಟಾಮಿಕ್ ಆಗಿ
ಬದಲಾಯಿಸುತ್ತದೆ (ಮೈಗ್ರೇಶನ್ `144_radar_offers_cache.sql`). ಇತರ ಫೀಡ್ಗಳು ಬಳಸುವ ಅದೇ 10 MB
ಹೆಡರ್-ಜೊತೆಗೆ-ಸ್ಟ್ರೀಮ್ ಮಿತಿ ಇಲ್ಲಿಗೂ ಅನ್ವಯಿಸುತ್ತದೆ. ಸಹಿ, ಸ್ಕೀಮಾ, ಟಿಯರ್, ರೀಪ್ಲೇ, ಗಾತ್ರ, HTTP
ಮತ್ತು ನೆಟ್ವರ್ಕ್ ವೈಫಲ್ಯಗಳೆಲ್ಲವೂ ಕೊನೆಯದಾಗಿ ಪರಿಶೀಲಿಸಿದ ಕ್ಯಾಶ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.

ಮುಚ್ಚಿದ ಕೊಡುಗೆ ಸ್ವರೂಪವು ಹೋಲಿಸಬಹುದಾದ ಮೂರು ಪ್ರಯೋಜನ ಪ್ರಕಾರಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ: ಬೇಸಿಸ್ ಪಾಯಿಂಟ್ಗಳಲ್ಲಿನ ಶೇಕಡಾವಾರು,
ಕರೆನ್ಸಿಯ ಸಣ್ಣ ಘಟಕಗಳಲ್ಲಿನ ಕ್ರೆಡಿಟ್, ಅಥವಾ ಪ್ರಯೋಗದ ದಿನಗಳು. ಪಾಲುದಾರರ ಕೊಡುಗೆಯು ಅದೇ-ಪ್ರಕಾರದ ಸಾರ್ವಜನಿಕ ಬೇಸ್ಲೈನ್ ಅನ್ನು
ಒಳಗೊಂಡಿರಬೇಕು ಮತ್ತು ಅದರ ಪ್ರಯೋಜನವು ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಹೆಚ್ಚಿನದಾಗಿರಬೇಕು; ಅಧಿಕೃತ ಕೊಡುಗೆಗಳಿಗೆ ಪಾಲುದಾರ ಬೇಸ್ಲೈನ್ ಇರುವುದಿಲ್ಲ.
URLಗಳು ಕ್ರೆಡೆನ್ಷಿಯಲ್-ರಹಿತ HTTPS ಆಗಿರಬೇಕು. `getRadarOffers()` ಕ್ಯಾಶ್ ಮಾಡಿದ ಪೇಲೋಡ್ ಅನ್ನು ಮುನ್ನೆಚ್ಚರಿಕೆಯಿಂದ
ಮರುಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಸ್ಥಳೀಯ ಓದುವಿಕೆಯಲ್ಲೂ ಅವಧಿ ಮುಗಿದ ನಮೂದುಗಳನ್ನು ಫಿಲ್ಟರ್ ಮಾಡುತ್ತದೆ;
`/dashboard/radar/offers` ರೆಂಡರ್ ಮಾಡುವ ಮೊದಲು ಅವಧಿ ಮುಗಿದವುಗಳನ್ನು ಮತ್ತೊಮ್ಮೆ ಫಿಲ್ಟರ್ ಮಾಡುತ್ತದೆ,
ಲಭ್ಯವಿದ್ದಾಗ ಪೋರ್ಚುಗೀಸ್ ಪಠ್ಯವನ್ನು ಹಾಗೂ ಪರ್ಯಾಯವಾಗಿ ಇಂಗ್ಲಿಷ್ ಪಠ್ಯವನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು ಪಾಲುದಾರರ ಕೊಡುಗೆಗಳಿಗೆ
ಸ್ಪಷ್ಟವಾಗಿ ಲೇಬಲ್ ಹಾಕುತ್ತದೆ.

ಬ್ರೌಸರ್ ಸ್ಥಳೀಯ ರೂಟ್ಗಳನ್ನು ಮಾತ್ರ ಕರೆಯುತ್ತದೆ: ಅದು ಮರೆಮಾಚಿದ ಸೆಟ್ಟಿಂಗ್ಗಳ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಅನ್ನು ಓದುತ್ತದೆ,
ಸರ್ವರ್-ಭಾಗದಲ್ಲಿ ರಿಫ್ರೆಶ್ ಮಾಡಲು `POST /api/radar/offers/sync` ಅನ್ನು ವಿನಂತಿಸುತ್ತದೆ, ನಂತರ
`GET /api/radar/offers` ಅನ್ನು ಓದುತ್ತದೆ. ಕೀ ಇಲ್ಲದಿದ್ದರೆ, ಫೀಡ್ ವಿನಂತಿಯನ್ನು ಪ್ರಯತ್ನಿಸುವ ಬದಲು ಅದು ಈಗಿರುವ
ಕೊಡುಗೆದಾರ/ಬೆಂಬಲ ಲಿಂಕ್ಗಳನ್ನು ತೋರಿಸುತ್ತದೆ. ಬಾಹ್ಯ ಕೊಡುಗೆ ಲಿಂಕ್ಗಳು `noopener noreferrer` ಜೊತೆಗೆ ಹೊಸ ಟ್ಯಾಬ್ನಲ್ಲಿ
ತೆರೆಯುತ್ತವೆ. ಈ ಬಿಡುಗಡೆಯಲ್ಲಿ ಯಾವುದೇ `radar_offers` MCP ಟೂಲ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸಲಾಗಿಲ್ಲ.

## Radar Intel, ಬೆಂಬಲಿಗರ ಬ್ಯಾಡ್ಜ್ ಮತ್ತು CLI

Intel ಎಂಬುದು `GET /v1/intel/latest` ನಲ್ಲಿರುವ ಸಹಿ ಮಾಡಿದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿದೆ. ಮುಚ್ಚಿದ
`RadarIntelFeedSchema`, ದೃಢೀಕರಿಸಿದ ಹೋಲಿಕೆಗಳಿಂದ ಖಾಸಗಿ ಕ್ಯುರೇಟರ್ ಪಡೆದ Radar-ಸ್ವಾಮ್ಯದ ELO ಶ್ರೇಯಾಂಕಗಳು ಮತ್ತು
ಸಹಿ ಮಾಡಿದ ಕ್ಯಾಟಲಾಗ್ ಸ್ನ್ಯಾಪ್ಶಾಟ್ಗಳಿಂದ ಪಡೆದ ವಾಸ್ತವಿಕ ಕ್ಯಾಟಲಾಗ್ ವಯಸ್ಸು/ಎಣಿಕೆಯ ವ್ಯತ್ಯಾಸಗಳನ್ನು ಮಾತ್ರ
ಸ್ವೀಕರಿಸುತ್ತದೆ. ವಿಧಾನವನ್ನು ಆರಂಭಿಕ ರೇಟಿಂಗ್ 1000 ಮತ್ತು K=32 ಎಂದು ನಿಗದಿಪಡಿಸಲಾಗಿದೆ. ಯಾವುದೇ ಹೋಲಿಕೆಯನ್ನು
ದೃಢೀಕರಿಸದಿದ್ದಾಗ ಖಾಲಿ ಶ್ರೇಯಾಂಕವು ಮಾನ್ಯವಾಗಿರುತ್ತದೆ; ಕ್ಲೈಂಟ್ ಎಂದಿಗೂ ಒಂದನ್ನು ಕೃತಕವಾಗಿ ರಚಿಸುವುದಿಲ್ಲ.

`syncRadarIntel()` ಕೊಡುಗೆಗಳಂತೆಯೇ ಅದೇ ಸರ್ವರ್-ಭಾಗದ Bearer, 30-ಸೆಕೆಂಡ್ ಕಾಲಮಿತಿ, 10 MiB ಸ್ಟ್ರೀಮ್ ಮಿತಿ,
ನಿಖರ-ಬೈಟ್ Ed25519 ಪರಿಶೀಲನೆ, ಕಟ್ಟುನಿಟ್ಟಾದ ಸ್ಕೀಮಾ, `live` ಬಾಡಿ/ಹೆಡರ್ ಅಗತ್ಯ, ಆವೃತ್ತಿ ಕನಿಷ್ಠ ಮಿತಿ ಮತ್ತು
ಕೊನೆಯ-ಉತ್ತಮ-ಕ್ಯಾಶ್ ಸಂರಕ್ಷಣೆಯನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ. ಪರಿಶೀಲಿಸಿದ ಸಕ್ರಿಯ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಅನ್ನು ಉಳಿಸಿದ ನಂತರ, ಕ್ಲೈಂಟ್
`radar:<sha256(supporter key)>` ಅನ್ನು ಪಡೆಯುತ್ತದೆ, ಆ ಏಕಮುಖ ಗುರುತನ್ನು ಮಾತ್ರ ಸಂಗ್ರಹಿಸುತ್ತದೆ ಮತ್ತು ಮೀಸಲಾದ
`radar_supporter` ಗುರುತಿಸುವಿಕೆ ಈವೆಂಟ್ ಅನ್ನು ಹೊರಸೂಸುತ್ತದೆ. ಅದರ `radar-supporter` ಬ್ಯಾಡ್ಜ್ ಐಡೆಂಪೊಟೆಂಟ್ ಆಗಿದ್ದು
ಶೂನ್ಯ XP ನೀಡುತ್ತದೆ; ಅದು ಎಂದಿಗೂ ಲೀಡರ್ಬೋರ್ಡ್ಗಳನ್ನು ನವೀಕರಿಸುವುದಿಲ್ಲ ಅಥವಾ `token_share` ಅನ್ನು ಮರುಬಳಸುವುದಿಲ್ಲ.
`/dashboard/radar/intel` ಪರಿಶೀಲಿಸಿದ ಸ್ಥಳೀಯ ಕ್ಯಾಶ್ ಮೆಟಾಡೇಟಾದಿಂದ ಮಾತ್ರ ಬ್ಯಾಡ್ಜ್ ಅನ್ನು ರೆಂಡರ್ ಮಾಡುತ್ತದೆ.

CLI `omniroute radar status` ಮತ್ತು `omniroute radar sync` ಅನ್ನು ಒದಗಿಸುತ್ತದೆ. ಎರಡೂ ಸ್ಥಳೀಯ OmniRoute API
ಜೊತೆಗೆ ಮಾತ್ರ ಸಂವಹನ ನಡೆಸುತ್ತವೆ. `status` ಓದಲು-ಮಾತ್ರದ `GET /api/radar/status` ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ;
`sync` ಒಂದು `POST /api/radar/sync-all` ಅನ್ನು ಕಳುಹಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಫೀಡ್ಗೆ ಫಲಿತಾಂಶವನ್ನು ಮುದ್ರಿಸುತ್ತದೆ.
ಯಾವುದೇ ಕಮಾಂಡ್ ಬೆಂಬಲಿಗರ ಕೀ ಅನ್ನು ಓದುವುದಿಲ್ಲ, ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ ಅಥವಾ ಮುದ್ರಿಸುವುದಿಲ್ಲ ಮತ್ತು ಯಾವುದೂ Radar ಸೇವೆಯನ್ನು
ನೇರವಾಗಿ ಸಂಪರ್ಕಿಸುವುದಿಲ್ಲ.

## ರೆಫರಲ್ ಲಿಂಕ್ಗಳು (ಉಚಿತ ಕ್ರೆಡಿಟ್ಗಳು)

ರೆಫರಲ್ ಲಿಂಕ್ಗಳನ್ನು ಕ್ಯಾಟಲಾಗ್ ಫೀಡ್ನಿಂದ ಪ್ರತ್ಯೇಕವಾದ **ಸ್ವತಂತ್ರ, ಯಾವಾಗಲೂ-ಪ್ರಸ್ತುತವಾಗಿರುವ** ಫೀಡ್ —
`GET /v1/referrals/latest` — ಮೂಲಕ ಒದಗಿಸಲಾಗುತ್ತದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕ: ಸಮುದಾಯ ಶ್ರೇಣಿಯ
ಕ್ಯಾಟಲಾಗ್ ಫೀಡ್ 30 ದಿನಗಳಷ್ಟು ಹಳೆಯದಾಗಿರಬಹುದಾದ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಆಗಿರುವುದರಿಂದ, ಅದರಿಂದ
ಹೊರತೆಗೆಯಲಾದ ರೆಫರಲ್ ಲಿಂಕ್ ಸರ್ವರ್ನ ನಿಜವಾದ ಲಿಂಕ್ ಪಟ್ಟಿಗಿಂತ ಅಷ್ಟೇ ಅವಧಿಯಷ್ಟು ಹಿಂದೆ
ಉಳಿಯುತ್ತಿತ್ತು (ಹೊಸದಾಗಿ ಸೇರಿಸಲಾದ ರೆಫರಲ್ ಉಚಿತ/ಸಮುದಾಯ ಬಳಕೆದಾರರನ್ನು ತಲುಪಲು ಒಂದು
ತಿಂಗಳವರೆಗೂ ಹಿಡಿಯಬಹುದಿತ್ತು). ರೆಫರಲ್ಗಳ ಫೀಡ್ ತನ್ನದೇ ಆದ, ಬಹಳ ಕಡಿಮೆ ಅವಧಿಯ
ಆವರ್ತನದಲ್ಲಿ ಸಿಂಕ್ ಆಗುವ ಮೂಲಕ ಆ ವಿಳಂಬವನ್ನು ನಿವಾರಿಸುತ್ತದೆ.

```ts
// GET /v1/referrals/latest ಪ್ರತಿಕ್ರಿಯೆಯ ಬಾಡಿ (Ed25519-ಸಹಿ ಮಾಡಲಾಗಿದೆ, ಕ್ಯಾಟಲಾಗ್
// ಫೀಡ್ನಲ್ಲಿರುವ ಅದೇ ಪಿನ್ ಮಾಡಿದ ಕೀ):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — ನಿರ್ಣಾಯಕ: ಎಲ್ಲಾ ರೆಫರಲ್ ಲಿಂಕ್ಗಳಲ್ಲಿನ max(updatedAt),
                                  // ಆದ್ದರಿಂದ ಒಂದೇ ರೀತಿಯ ಎರಡು ವಿನಂತಿಗಳು ನಿಖರವಾಗಿ ಅದೇ
                                  // ಸಹಿ ಮಾಡಿದ ಬೈಟ್ಗಳು/ಸಹಿಯನ್ನು ಉತ್ಪಾದಿಸುತ್ತವೆ
  referrals: {
    fixed: RadarReferral[],      // ದೃಢೀಕರಣವಿಲ್ಲದ/ಸಮುದಾಯ ಶ್ರೇಣಿಯನ್ನೂ ಒಳಗೊಂಡಂತೆ ಪ್ರತಿ ಶ್ರೇಣಿಯಲ್ಲಿಯೂ ಇರುತ್ತದೆ
    campaigns: RadarReferral[],  // ಮಾನ್ಯವಾದ ಸಕ್ರಿಯ (ಬೆಂಬಲಿಗ) Bearer ಕೀಗಾಗಿ ಮಾತ್ರ ಭರ್ತಿ
                                  // ಮಾಡಲಾಗುತ್ತದೆ; ದೃಢೀಕರಣವಿಲ್ಲದ/ಅವಧಿ-ಮೀರಿದ-ಕೀ ವಿನಂತಿಗಳು [] ಪಡೆಯುತ್ತವೆ
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

ಕ್ಯಾಟಲಾಗ್ ಫೀಡ್ಗಿಂತ ಭಿನ್ನವಾಗಿ, ಈ ಬಾಡಿಯು ಯಾವುದೇ `tier` ಕ್ಷೇತ್ರವನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ —
`Authorization` ಕೀಯ ಆಧಾರದ ಮೇಲೆ ಪ್ರತಿ ವಿನಂತಿಗೆ ಏನನ್ನು ಸೇರಿಸಬೇಕೆಂದು ಸರ್ವರ್
ನಿರ್ಧರಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಒದಗಿಸಲಾದ ಶ್ರೇಣಿಗೆ `x-omniroute-feed-tier` ಪ್ರತಿಕ್ರಿಯೆ
ಹೆಡರ್ ಮಾತ್ರವೇ ಏಕೈಕ ಮೂಲವಾಗಿದೆ (`referralsSync.ts::syncRadarReferrals`); ಗೈರುಹಾಜರಾದ/
ಗುರುತಿಸಲಾಗದ ಹೆಡರ್ ಕನಿಷ್ಠ ಸವಲತ್ತುಗಳ ಊಹೆಯಾದ `"community"`ಗೆ ಇಳಿಕೆಯಾಗುತ್ತದೆ.
`RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) ಸಂಪೂರ್ಣ ಬಾಡಿಯನ್ನು
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ ಮತ್ತು `feedSchema.ts`ನಿಂದ ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡಲಾದ ಅದೇ ಪ್ರತಿ-ರೆಫರಲ್
`RadarReferralSchema` ಅನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ, ಹೀಗಾಗಿ ಎರಡೂ ಫೀಡ್ಗಳು ಪ್ರತ್ಯೇಕ
ರೆಫರಲ್ಗಳನ್ನು ಒಂದೇ ರೀತಿಯಲ್ಲಿ ಮೌಲ್ಯೀಕರಿಸುತ್ತವೆ. ಪ್ರತಿಯೊಂದು `RadarReferral.url`
`https://` ಆಗಿರಬೇಕು — `http://` url ಸ್ಕೀಮಾ ಮೌಲ್ಯೀಕರಣದಲ್ಲಿ ವಿಫಲವಾಗುತ್ತದೆ.

`RadarFeedSchema` (`feedSchema.ts`)ನಲ್ಲಿರುವ ಹಳೆಯ ಕ್ಯಾಟಲಾಗ್-ಒಳಸೇರಿತ `referrals`
ಕ್ಷೇತ್ರವನ್ನು ಈಗಾಗಲೇ ಕ್ಯಾಶ್ ಮಾಡಲಾದ ಕ್ಯಾಟಲಾಗ್ ಫೀಡ್ಗಳೊಂದಿಗೆ ಹಿಮ್ಮುಖ-ಹೊಂದಾಣಿಕೆಗಾಗಿ
ಉಳಿಸಲಾಗಿದೆ, ಆದರೆ `getRadarReferrals()` ಇನ್ನು ಅದನ್ನು ಓದುವುದಿಲ್ಲ — ಕೆಳಗಿನ
[ಆಕ್ಸೆಸರ್](#accessor) ನೋಡಿ.

### ಸಿಂಕ್

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) ರೆಫರಲ್ಗಳಿಗಾಗಿ ನೆಟ್ವರ್ಕ್
ಅನ್ನು ಸ್ಪರ್ಶಿಸುವ ಏಕೈಕ ಮಾಡ್ಯೂಲ್ ಆಗಿದ್ದು, `syncRadar()`ನ ಒಪ್ಪಂದವನ್ನು ನಿಖರವಾಗಿ
ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ: ಫ್ಲ್ಯಾಗ್ ಆಫ್ → `disabled`; ಆಯ್ಕೆ-ಸಮ್ಮತಿ false → `opt_out`;
`${RADAR_FEED_URL}/v1/referrals/latest` ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ (ಕ್ಯಾಟಲಾಗ್ನಂತೆಯೇ
ಅದೇ `RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` ಫೋರ್ಕ್ ಓವರ್ರೈಡ್ಗಳು), ನಿಖರವಾದ ಪ್ರತಿಕ್ರಿಯೆ
ಬೈಟ್ಗಳ ಮೇಲಿನ Ed25519 ಸಹಿಯನ್ನು (`verifyFeedBytes`) ಪರಿಶೀಲಿಸುತ್ತದೆ,
`RadarReferralsFeedSchema` ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ ಮತ್ತು `radar_referrals_cache`
ಟೇಬಲ್ಗೆ (ಮೈಗ್ರೇಷನ್ `142_radar_referrals_cache.sql`) ಕ್ಯಾಶ್ ಮಾಡುತ್ತದೆ — ಇದು
ಕ್ಯಾಟಲಾಗ್ನ `radar_feed_cache`ನಿಂದ ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾದ ಟೇಬಲ್ ಆಗಿದೆ. 10 MB
ಪ್ರತಿಕ್ರಿಯೆ ಮಿತಿ ಮತ್ತು `generatedAt` ಕನಿಷ್ಠ ಮಿತಿ ಕ್ಯಾಶ್ ಮಾಡಿರುವುದಕ್ಕಿಂತ ಹಳೆಯದಾದ
ಒಳಬರುವ ಫೀಡ್ ಅನ್ನು ತಿರಸ್ಕರಿಸಿ, ಹಳೆಯ ಸಹಿ ಮಾಡಿದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ನ ಮರುಪ್ರಸಾರದಿಂದ
ರಕ್ಷಿಸುತ್ತವೆ. ಸಮಾನ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ: ಸರ್ವರ್ ಸಮುದಾಯ ಮತ್ತು ಸಕ್ರಿಯ
ರೆಫರಲ್ ರೂಪಾಂತರಗಳಿಗೆ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಒಂದೇ ನಿರ್ಣಾಯಕ `generatedAt` ಅನ್ನು ನೀಡುತ್ತದೆ,
ಹೀಗಾಗಿ ಆಧಾರವಾಗಿರುವ ಲಿಂಕ್ ಸೆಟ್ ಬದಲಾಗದಿದ್ದರೂ ಬೆಂಬಲಿಗ-ಕೀ ಬದಲಾವಣೆಯ ನಂತರ ಸಹಿ ಮಾಡಿದ
ಪೇಲೋಡ್ ಮತ್ತು ಒದಗಿಸಲಾದ ಶ್ರೇಣಿ ಬದಲಾಗಬಹುದು. ಇದು ಎಂದಿಗೂ ಥ್ರೋ ಮಾಡುವುದಿಲ್ಲ — ಯಾವಾಗಲೂ
ಸ್ಥಿತಿ ಆಬ್ಜೆಕ್ಟ್ ಅನ್ನು ಮರಳಿಸುತ್ತದೆ; `reason`ನಲ್ಲಿನ ದೋಷಗಳು ಎಂದಿಗೂ ಸ್ಟ್ಯಾಕ್ ಟ್ರೇಸ್
ಅನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ.

ಎರಡು ಟ್ರಿಗರ್ಗಳು ರೆಫರಲ್ಗಳ ಕ್ಯಾಶ್ ಅನ್ನು ಸಿದ್ಧ ಸ್ಥಿತಿಯಲ್ಲಿಡುತ್ತವೆ ಮತ್ತು ಎರಡೂ
ಕ್ಯಾಟಲಾಗ್ನ ಸ್ವಂತ 24h ಆವರ್ತನದಿಂದ ಸ್ವತಂತ್ರವಾಗಿವೆ:

- **ಓದುವಾಗ-ಸಿಂಕ್** — ಕ್ಯಾಶ್ ಇಲ್ಲದಿರುವಾಗ ಅಥವಾ `REFERRALS_STALE_MS`ಗಿಂತ ಹಳೆಯದಿರುವಾಗ
  (1h, `shouldSyncReferralsOnRead()`), ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಒದಗಿಸುವ ಮೊದಲು
  `GET /api/radar/referrals` ಸ್ವತಃ `syncRadarReferrals()` ಅನ್ನು ಇನ್ಲೈನ್ನಲ್ಲಿ
  ಕರೆಯುತ್ತದೆ. ಯಾವುದೇ ಹಿನ್ನೆಲೆ ಟೈಮರ್ಗಾಗಿ ಕಾಯದೆ, ಮುಂದಿನ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಲೋಡ್ನಲ್ಲೇ
  ಸ್ಥಿರ ಲಿಂಕ್ಗಳನ್ನು "ಯಾವಾಗಲೂ ಪ್ರಸ್ತುತ"ವಾಗಿಸುವುದು ಇದೇ.
- **ಶೆಡ್ಯೂಲರ್ ಸೈಡ್-ಸಿಂಕ್** — `radarSchedulerTick()` (`scheduler.ts`) ಕ್ಯಾಟಲಾಗ್ಗೆ
  ಬಳಸಲಾಗುವ ಅದೇ ಗಂಟೆಗೊಮ್ಮೆ ಟಿಕ್ನಲ್ಲಿ ರೆಫರಲ್ಗಳ ಹಳತಾಗಿರುವಿಕೆಯನ್ನು ಸ್ವತಂತ್ರವಾಗಿ
  ಮೌಲ್ಯಮಾಪನ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸಮಯವಾದಾಗ `syncRadarReferrals()` ಅನ್ನು ಕರೆಯುತ್ತದೆ.
  ಆ ಟಿಕ್ನಲ್ಲಿ ಕ್ಯಾಟಲಾಗ್ನ ಸ್ವಂತ ಸಮಯ ಬಂದಿದೆಯೇ ಎಂಬುದನ್ನು ಲೆಕ್ಕಿಸದೆ ಇದು ರನ್ ಆಗುತ್ತದೆ
  ಮತ್ತು `RadarTickResult`ನ ಆಕಾರದ ಮೇಲೆ ಎಂದಿಗೂ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ (ಅತ್ಯುತ್ತಮ-ಪ್ರಯತ್ನದ
  ಪಾರ್ಶ್ವ ಪರಿಣಾಮ ಮಾತ್ರ, ದೋಷವಾದಾಗ ನುಂಗಲಾಗುತ್ತದೆ).

### ಆಕ್ಸೆಸರ್

`src/lib/radar/index.ts` ಎರಡು ಓದಲು-ಮಾತ್ರವಾದ ಆಕ್ಸೆಸರ್ಗಳನ್ನು ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡುತ್ತದೆ,
ಇವೆರಡೂ ಎಂದಿಗೂ ಥ್ರೋ ಮಾಡುವುದಿಲ್ಲ (`getRadarCatalog()`ನಂತೆಯೇ ಅದೇ ರಕ್ಷಣಾತ್ಮಕ ಒಪ್ಪಂದ —
ಫ್ಲ್ಯಾಗ್ ಆಫ್, ಕ್ಯಾಶ್ ಇಲ್ಲದಿರುವುದು ಅಥವಾ ದೋಷಪೂರಿತ ಕ್ಯಾಶ್ ಮಾಡಿದ ಪೇಲೋಡ್ ಇವೆಲ್ಲವೂ ದೋಷದ
ಬದಲು ಖಾಲಿ ಆಕಾರಕ್ಕೆ ಪರಿಹಾರಗೊಳ್ಳುತ್ತವೆ):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  `radar_referrals_cache`ನಿಂದ (`getRadarReferralsCache()` ಮೂಲಕ) ಓದುತ್ತದೆ ಮತ್ತು
  `RadarReferralsFeedSchema` ಮೂಲಕ ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ — ಕ್ಯಾಟಲಾಗ್ ಕ್ಯಾಶ್ ಮೂಲಕ **ಅಲ್ಲ**.
- `getDefaultReferralFor(provider)` → ಆ ಪೂರೈಕೆದಾರನಿಗೆ `isDefault: true` ಹೊಂದಿರುವ
  `fixed` ರೆಫರಲ್, ಅಥವಾ `null`. ಇದು `fixed` ಅನ್ನು ಮಾತ್ರ ನೋಡುತ್ತದೆ — ಅಭಿಯಾನವನ್ನು
  ಪೂರೈಕೆದಾರನ "ಡೀಫಾಲ್ಟ್" ಲಿಂಕ್ ಆಗಿ ಎಂದಿಗೂ ಬಳಸಲಾಗುವುದಿಲ್ಲ.

ನಿಜವಾದ "ಪೂರೈಕೆದಾರನಿಗೆ ಯಾವ ರೆಫರಲ್ ಡೀಫಾಲ್ಟ್ ಆಗಿದೆ" ಎಂಬ ನಿಯಮವು
`findDefaultReferral()` (`src/lib/radar/referrals.ts`)ನಲ್ಲಿದೆ; ಇದು **ಯಾವುದೇ DB
ಇಂಪೋರ್ಟ್ ಹೊಂದಿರದ** ಸಣ್ಣ ಶುದ್ಧ ಫಂಕ್ಷನ್ — ಇದನ್ನು `"use client"` ಕಾಂಪೊನೆಂಟ್ಗೆ
ಸುರಕ್ಷಿತವಾಗಿ ಇಂಪೋರ್ಟ್ ಮಾಡಬಹುದು. `getRadarReferrals`/`getDefaultReferralFor`
(`index.ts`ನಲ್ಲಿ) `@/lib/db/radar` ಅನ್ನು ಒಳಗೆ ತರುತ್ತವೆ ಮತ್ತು ಆದ್ದರಿಂದ ಸರ್ವರ್ನಲ್ಲಿ
ಮಾತ್ರ ಉಳಿಯುತ್ತವೆ; ಬ್ರೌಸರ್ಗೆ `better-sqlite3` ಅನ್ನು ಬಂಡಲ್ ಮಾಡುವುದನ್ನು ತಪ್ಪಿಸಲು
ಪೂರೈಕೆದಾರರ ಡ್ಯಾಶ್ಬೋರ್ಡ್ `index.ts` ಬದಲು `referrals.ts` ಅನ್ನು ನೇರವಾಗಿ ಇಂಪೋರ್ಟ್
ಮಾಡುತ್ತದೆ (ಕೆಳಗೆ ನೋಡಿ).

### `GET /api/radar/referrals`

ಇತರ ಪ್ರತಿಯೊಂದು Radar ಮಾರ್ಗದಂತೆಯೇ ನಿಖರವಾದ ಅದೇ ಗೇಟ್ ಕ್ರಮವನ್ನು ಅನುಸರಿಸುತ್ತದೆ: `RADAR_ENABLED` ಆಫ್ →
`404` (ಮೊದಲು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ, ಬೈಟ್ಗೆ-ಬೈಟ್ ಒಂದೇ ರೀತಿಯ ಜಡತ್ವ); ದೃಢೀಕರಿಸದ ಬಳಕೆದಾರ → `401`; ಇಲ್ಲದಿದ್ದರೆ
ಹಳೆಯದಾಗಿರುವಾಗ ಓದುವಿಕೆಯೊಂದಿಗೆ ಸಿಂಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸುತ್ತದೆ (ಮೇಲೆ ನೋಡಿ), ನಂತರ
`{ fixed, campaigns, tier }` ಜೊತೆಗೆ `200` — `tier` ನೇರವಾಗಿ (ಬಹುಶಃ ಈಗಷ್ಟೇ ರಿಫ್ರೆಶ್ ಮಾಡಿದ)
ಕ್ಯಾಶ್ ಸಾಲಿನಿಂದ ಬರುತ್ತದೆ ಮತ್ತು ಸಂಪೂರ್ಣವಾಗಿ ಮಾಹಿತಿಗಾಗಿ ಮಾತ್ರ (ಕೆಳಗಿನ UI ಯ ಸೌಮ್ಯ ಅಪ್ಸೆಲ್ ಪಠ್ಯವನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ). ಫೀಡ್
ಸರ್ವರ್ಗೆ ಎಂದಿಗೂ ನೇರವಾಗಿ ಪ್ರಾಕ್ಸಿ ಮಾಡುವುದಿಲ್ಲ — ಮಾರ್ಗದ ಸ್ವಂತ ಮೂಲವು ಯಾವುದೇ `fetch(` ಕರೆಯನ್ನು ಹೊಂದಿಲ್ಲ;
ನೆಟ್ವರ್ಕ್ ಯಾವಾಗಲೂ `syncRadarReferrals()` ಒಳಗೆ ಮಾತ್ರ ಸಂಭವಿಸುತ್ತದೆ, ಇದು `/api/radar/catalog` ನಂತೆಯೇ
ಸ್ಥಳೀಯ-ಕ್ಯಾಶ್-ಮಾತ್ರ ತತ್ವವಾಗಿದೆ.

### ಡ್ಯಾಶ್ಬೋರ್ಡ್ UI — `/dashboard/radar` ನಲ್ಲಿನ "ಉಚಿತ ಕ್ರೆಡಿಟ್ಗಳು" ಟ್ಯಾಬ್

ಹೊಸ ಮಾರ್ಗದ ಬದಲು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ Radar ಪುಟವನ್ನು (`src/app/(dashboard)/dashboard/radar/page.tsx`)
ಎರಡನೇ ಟ್ಯಾಬ್ ಆಗಿ ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ — ಪುಟವು ಈಗಾಗಲೇ ಪಡೆಯುವ ಡೇಟಾದ ಬದಲಾವಣೆಯಾಗಿರುವ ವೈಶಿಷ್ಟ್ಯಕ್ಕೆ
ಕಡಿಮೆ ರೂಟಿಂಗ್/i18n ವ್ಯಾಪ್ತಿ. ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡ ನಂತರ, ಟ್ಯಾಬ್ ಪಟ್ಟಿ
**ಕ್ಯಾಟಲಾಗ್** (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕೋಷ್ಟಕ) ಮತ್ತು **ಉಚಿತ ಕ್ರೆಡಿಟ್ಗಳು** ಅನ್ನು ಒದಗಿಸುತ್ತದೆ:

- ಸ್ಥಿರ ಲಿಂಕ್ಗಳನ್ನು ಪೂರೈಕೆದಾರರ ಪ್ರಕಾರ ಗುಂಪು ಮಾಡಲಾಗುತ್ತದೆ, ಪ್ರತಿಯೊಂದೂ `requiredAction` ಅನ್ನು (ಇದ್ದಾಗ)
  ಮತ್ತು ರೆಫರಲ್ URL ಗೆ `target="_blank" rel="noopener noreferrer"` ಬಟನ್ ಅನ್ನು ತೋರಿಸುತ್ತದೆ.
- ಅಭಿಯಾನಗಳು ಅದನ್ನೇ ತೋರಿಸುತ್ತವೆ, ಜೊತೆಗೆ `validUntil` ಇದ್ದಾಗ ಅದನ್ನೂ ತೋರಿಸುತ್ತವೆ.
- `campaigns` ಖಾಲಿಯಾಗಿರುವಾಗ **ಮತ್ತು** ಒದಗಿಸಲಾದ ಟಿಯರ್ `community` ಆಗಿರುವಾಗ, UI
  ಒಂದು ಸಂಕ್ಷಿಪ್ತ ಅಪ್ಸೆಲ್ ಟಿಪ್ಪಣಿಯನ್ನು ತೋರಿಸುತ್ತದೆ ("ಸೀಮಿತ-ಅವಧಿಯ ಅಭಿಯಾನಗಳು ಬೆಂಬಲಿಗರಿಗಾಗಿ ಇರುವ ಹೆಚ್ಚುವರಿ ಸೌಲಭ್ಯ") — ಇದು
  ಸ್ಥಿರ ಲಿಂಕ್ಗಳ ಪಟ್ಟಿಯನ್ನು **ಎಂದಿಗೂ** ಮರೆಮಾಡುವುದಿಲ್ಲ ಅಥವಾ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಪ್ರತಿ ಟಿಯರ್ಗೂ ಸಂಪೂರ್ಣವಾಗಿ ಭರ್ತಿಯಾಗಿಯೇ ಇರುತ್ತದೆ.
  ಅಪ್ಸೆಲ್ ಕೇವಲ ಸೌಮ್ಯ ಸಂದೇಶ ಮಾತ್ರ, ಎಂದಿಗೂ ತಡೆಯಲ್ಲ.

### ಪೂರೈಕೆದಾರರ ಹೆಸರಿನ ಮೇಲಿನ ರೆಫರಲ್ ಲಿಂಕ್ (ಪೂರೈಕೆದಾರರ ಡ್ಯಾಶ್ಬೋರ್ಡ್)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
ಈಗಾಗಲೇ ಪೂರೈಕೆದಾರರ ಹೆಸರನ್ನು `providerInfo.website` ಇದ್ದಾಗ ಅದಕ್ಕೆ ಲಿಂಕ್ ಮಾಡಿತ್ತು, ಜೊತೆಗೆ
ಆದಾಯೀಕರಿಸಿದ ಲಿಂಕ್ಗೆ ಒಂದು ಪೂರ್ವನಿದರ್ಶನವಿತ್ತು: Kimi (Moonshot AI) ಪಾಲುದಾರ-ಲಿಂಕ್ ಟಿಪ್ಪಣಿ
(`providers.kimiPartnerLinkNote` i18n ಕೀ). ಹೊಸ ಕೀ ಪರಿಚಯಿಸುವ ಬದಲು D28
Radar ಡೀಫಾಲ್ಟ್ ರೆಫರಲ್ಗಳಿಗೆ ನಿಖರವಾಗಿ ಅದೇ ವಿವೇಚನಾಯುಕ್ತ-ಟಿಪ್ಪಣಿ ಮಾದರಿಯನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ.

ವಿನ್ಯಾಸದಂತೆಯೇ ಸಡಿಲ ಜೋಡಣೆ:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  ಒಂದು **ಶುದ್ಧ** ಫಂಕ್ಷನ್ — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — `@/lib/radar` ಅಥವಾ `@/lib/db/*` ಮೇಲೆ ಯಾವುದೇ ಅವಲಂಬನೆ ಇಲ್ಲ. ಒಟ್ಟಾರೆಯಾಗಿ `providerPageUtils.ts`
  ಆ ಆಮದುಗಳಿಂದ ಮುಕ್ತವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ (`tests/unit/provider-header-referral-link.test.ts` ಮೂಲಕ
  ದೃಢೀಕರಿಸಲಾಗಿದೆ).
- `ProviderDetailPageClient.tsx` (`"use client"` ಕಾಂಪೊನೆಂಟ್) Radar ಡೇಟಾವನ್ನು ಪಡೆಯಲು ಅನುಮತಿಸಲಾದ
  ಏಕೈಕ ಸ್ಥಳ — Radar ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪುಟವೇ ಬಳಸುವ ಅದೇ ಸ್ಥಳೀಯ-ಮಾರ್ಗ
  ಮಾದರಿಯಾದ `fetch("/api/radar/referrals")` ಮೂಲಕ — ಮತ್ತು ಅದು DB-ಮುಕ್ತ
  `src/lib/radar/referrals.ts` ನಿಂದ `findDefaultReferral()` ಬಳಸಿ ಕ್ಲೈಂಟ್ ಬದಿಯಲ್ಲಿ ಡೀಫಾಲ್ಟ್ ರೆಫರಲ್ ಅನ್ನು ಲೆಕ್ಕಿಸುತ್ತದೆ.
- `RADAR_ENABLED` ಆಫ್ ಆಗಿರುವಾಗ, ಫೆಚ್ 404 ನೀಡುತ್ತದೆ, `referralUrl` `null` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ, ಮತ್ತು
  `resolveProviderHeaderLink()` ಸ್ಥಿರ ಕ್ಯಾಟಲಾಗ್ `website` ಅನ್ನು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಹಿಂದಿರುಗಿಸುತ್ತದೆ — ಈ
  ವೈಶಿಷ್ಟ್ಯ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲಿನಂತೆಯೇ ಪೂರೈಕೆದಾರರ ಪುಟವು ಬೈಟ್ಗೆ-ಬೈಟ್ ಒಂದೇ ಆಗಿರುತ್ತದೆ. ಇನ್ನೂ
  ಕ್ಯಾಶ್ ಇಲ್ಲದಿದ್ದಾಗ ಅಥವಾ ಆ ನಿರ್ದಿಷ್ಟ ಪೂರೈಕೆದಾರರಿಗೆ ಡೀಫಾಲ್ಟ್ ರೆಫರಲ್ ಇಲ್ಲದಿದ್ದಾಗಲೂ ಇದೇ ಫಲಿತಾಂಶ.
- ಡೀಫಾಲ್ಟ್ ರೆಫರಲ್ ಅನ್ವಯಿಸಿದಾಗ, `ProviderPageHeader` `isReferralLink` ಅನ್ನು ಸ್ವೀಕರಿಸಿ
  Kimi ಪಾಲುದಾರ ಲಿಂಕ್ನಂತೆಯೇ ಅದೇ ವಿವೇಚನಾಯುಕ್ತ ಟಿಪ್ಪಣಿ/ಟೂಲ್ಟಿಪ್ ಅನ್ನು ತೋರಿಸುತ್ತದೆ (`providers.kimiPartnerLinkNote`
  ಕೀಯನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ) — ಎಂದಿಗೂ ಹೊಸ, ಪ್ರತ್ಯೇಕ ದೃಶ್ಯ ವಿನ್ಯಾಸವಲ್ಲ.

## ಫೀಡ್ ಅನ್ನು ಸ್ವತಃ ಹೋಸ್ಟ್ ಮಾಡುವುದು ಹೇಗೆ

ಕ್ಯಾಟಲಾಗ್ನ ಮೇಲೆ ಸಂಪೂರ್ಣ ನಿಯಂತ್ರಣವನ್ನು ಬಯಸುವ ಫೋರ್ಕ್ ಅಥವಾ ಸ್ವಯಂ-ಹೋಸ್ಟರ್, ಕ್ಲೈಂಟ್ ಕೋಡ್ ಅನ್ನು
ಬದಲಾಯಿಸದೆಯೇ ತಮ್ಮದೇ ಫೀಡ್ ಸೇವೆಯನ್ನು ಚಲಾಯಿಸಬಹುದು:

1. `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) ಅನ್ನು ಪೂರೈಸುವ JSON ಬಾಡಿಯನ್ನು
   ಹಿಂತಿರುಗಿಸುವ `GET /v1/catalog/latest` ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಒದಗಿಸಿ — ಉನ್ನತ-ಹಂತದ `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks`, ಮತ್ತು `totals`. `x-omniroute-radar-schema: 2` ಅನ್ನು ಗೌರವಿಸಿ; ಪರಿವರ್ತನೆಗೆ ಹೊಂದಿಕೆಯಾಗುವ ಸರ್ವರ್,
   ಅದಿಲ್ಲದ ವಿನಂತಿಗಳಿಗೆ ಪ್ರತ್ಯೇಕವಾಗಿ ಸಹಿ ಮಾಡಲಾದ v1 ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಅನ್ನು ಡೀಫಾಲ್ಟ್ ಆಗಿ ನೀಡಬೇಕು.
2. ನಿಖರವಾದ ಪ್ರತಿಕ್ರಿಯೆ ಬೈಟ್ಗಳಿಗೆ Ed25519 ಕೀ ಜೋಡಿಯಿಂದ ಸಹಿ ಮಾಡಿ ಮತ್ತು base64
   ಸಹಿಯನ್ನು `x-omniroute-feed-signature` ಪ್ರತಿಕ್ರಿಯೆ ಹೆಡರ್ನಲ್ಲಿ ಹಿಂತಿರುಗಿಸಿ.
3. `RADAR_FEED_URL` ಅನ್ನು ಹೊಸ ಬೇಸ್ URL ಗೆ ಮತ್ತು `RADAR_FEED_PUBKEY` ಅನ್ನು ಅದಕ್ಕೆ ಹೊಂದುವ
   ಸಾರ್ವಜನಿಕ ಕೀಗೆ (base64-DER SPKI ಅಥವಾ PEM) ಹೊಂದಿಸಿ —
   [ಪರಿಸರ ವೇರಿಯಬಲ್ ಉಲ್ಲೇಖ](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting) ನೋಡಿ.
4. `RADAR_ENABLED` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ ಮತ್ತು `POST /api/radar/settings`
   (`{ optIn: true }`) ಮೂಲಕ ಆಯ್ಕೆಮಾಡಿ.

ಬೇರೆ ಯಾವುದೇ ಕೋಡ್ ಬದಲಾವಣೆಗಳ ಅಗತ್ಯವಿಲ್ಲ — `verifyFeedBytes()` ಓವರ್ರೈಡ್ ಅನ್ನು
ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಬಳಸಿಕೊಳ್ಳುತ್ತದೆ (`src/lib/radar/pinnedKeys.ts` ನಲ್ಲಿರುವ `getFeedPublicKeys()`), ಮತ್ತು ಆವೃತ್ತಿ
ಹೋಲಿಕೆ, ಸ್ಕೀಮಾ ಮೌಲ್ಯೀಕರಣ ಹಾಗೂ ವಿಲೀನ ನಿಯಮಗಳು ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ ಫೀಡ್ಗೂ ಒಂದೇ ರೀತಿಯಲ್ಲಿ
ಅನ್ವಯಿಸುತ್ತವೆ.

ರೆಫರಲ್ ಲಿಂಕ್ಗಳು (ಮೇಲಿನ [ರೆಫರಲ್ ಲಿಂಕ್ಗಳು (ಉಚಿತ ಕ್ರೆಡಿಟ್ಗಳು)](#referral-links-free-credits)
ನೋಡಿ) ಪ್ರತ್ಯೇಕವಾದ, ಐಚ್ಛಿಕ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿವೆ: ಕೇವಲ `/v1/catalog/latest` ಅನ್ನು ಒದಗಿಸುವ ಫೋರ್ಕ್
ಸಹ ಸಂಪೂರ್ಣವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ — `/v1/referrals/latest` ನಿಂದ `404` ಬಂದಾಗ
`syncRadarReferrals()` `{ status: "error" }` ಗೆ ಹಿಮ್ಮೆಟ್ಟುತ್ತದೆ ಮತ್ತು ಕ್ಯಾಶ್ ಖಾಲಿಯಾಗಿಯೇ
ಉಳಿಯುತ್ತದೆ, ಆದ್ದರಿಂದ ಪುಟದ ಉಳಿದ ಭಾಗವು ವಿಫಲವಾಗುವ ಬದಲು `GET /api/radar/referrals`,
`{ fixed: [], campaigns: [], tier: null }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತದೆ.
ರೆಫರಲ್ ಲಿಂಕ್ಗಳನ್ನೂ ನೀಡಲು, `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) ಅನ್ನು ಪೂರೈಸುವ `GET /v1/referrals/latest` ಅನ್ನು ಒದಗಿಸಿ
ಮತ್ತು ಕ್ಯಾಟಲಾಗ್ ಫೀಡ್ಗೆ ಬಳಸಿದ ಅದೇ Ed25519 ಕೀ ಜೋಡಿಯಿಂದ ಅದಕ್ಕೆ ಸಹಿ ಮಾಡಿ.

ಬೆಂಬಲಿಗರ ಆಫರ್ಗಳು ಮತ್ತೊಂದು ಐಚ್ಛಿಕ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿವೆ. ಅವುಗಳನ್ನು ಒದಗಿಸಲು, ಮುಚ್ಚಿದ
`RadarOffersFeedSchema` (`src/lib/radar/offersFeedSchema.ts`) ನೊಂದಿಗೆ
`GET /v1/offers/latest` ಅನ್ನು ಅಳವಡಿಸಿ, ಸಕ್ರಿಯ ಎಂಟೈಟಲ್ಮೆಂಟ್ ಅನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸಿ,
`x-omniroute-feed-tier: live` ಅನ್ನು ಹಿಂತಿರುಗಿಸಿ ಮತ್ತು ಅದೇ ಕೀಯಿಂದ ನಿಖರವಾದ ಬೈಟ್ಗಳಿಗೆ ಸಹಿ ಮಾಡಿ.
ಈ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುವ ಫೋರ್ಕ್ನಲ್ಲಿ ಕ್ಯಾಟಲಾಗ್/ರೆಫರಲ್ಗಳ ವರ್ತನೆ ಬದಲಾಗುವುದಿಲ್ಲ; ಆಫರ್
ರಿಫ್ರೆಶ್ ವಿನಾಶಕಾರಿಯಲ್ಲದ ರೀತಿಯಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಕೊನೆಯದಾಗಿ ಪರಿಶೀಲಿಸಲಾದ ಸ್ಥಳೀಯ ಆಫರ್
ಕ್ಯಾಶ್ ಲಭ್ಯವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ.

Intel ಕೂಡ ಇದೇ ರೀತಿಯಲ್ಲಿ ಐಚ್ಛಿಕವಾಗಿದೆ. ಸ್ವಯಂ-ಹೋಸ್ಟರ್ `RadarIntelFeedSchema`
(`src/lib/radar/intelFeedSchema.ts`) ಬಳಸಿ `GET /v1/intel/latest` ಅನ್ನು ಒದಗಿಸಬಹುದು,
ಸಕ್ರಿಯ ಎಂಟೈಟಲ್ಮೆಂಟ್ ಅನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸಬಹುದು, `x-omniroute-feed-tier: live` ಅನ್ನು ಹಿಂತಿರುಗಿಸಬಹುದು
ಮತ್ತು ಹಂಚಿಕೊಂಡ Ed25519 ಕೀಯಿಂದ ನಿಖರವಾದ ಬೈಟ್ಗಳಿಗೆ ಸಹಿ ಮಾಡಬಹುದು. ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಟ್ಟರೆ
ಕ್ಯಾಟಲಾಗ್, ರೆಫರಲ್ಗಳು ಮತ್ತು ಆಫರ್ಗಳು ಬದಲಾಗುವುದಿಲ್ಲ; Intel ರಿಫ್ರೆಶ್ ಕೊನೆಯದಾಗಿ ಪರಿಶೀಲಿಸಲಾದ ಯಾವುದೇ
ಸ್ಥಳೀಯ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.
