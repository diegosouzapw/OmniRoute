ರಿಲೇಗಳು (Vercel, Deno, Cloudflare) ಸರ್ವರ್ಲೆಸ್ ಬ್ಯಾಕೆಂಡ್ನಲ್ಲಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ಸಂಪರ್ಕವನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತವೆ; ಇದರಿಂದ ಪೂರೈಕೆದಾರರ API ಕೀಲಿಯನ್ನು ಸರ್ವರ್-ಸೈಡ್ನಲ್ಲೇ ಇರಿಸಿಕೊಂಡು OmniRoute ಸ್ಥಿರ ಪ್ರದೇಶದಿಂದ ಹೊರಹೋಗಬಹುದು. ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ ಆಪರೇಟರ್ಗಳು ಎದುರಿಸುವ ಎರಡು ವೈಫಲ್ಯ ವಿಧಾನಗಳು ಮತ್ತು ಪ್ರತಿಯೊಂದಕ್ಕೂ OmniRoute ಒದಗಿಸುವ ಮರುಪಡೆಯುವಿಕೆ ಮಾರ್ಗಗಳನ್ನು ಈ ದಸ್ತಾವೇಜು ವಿವರಿಸುತ್ತದೆ.

## ರಿಲೇ ದೃಢೀಕರಣವನ್ನು ಹೇಗೆ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ

ನೀವು **Settings → Proxy Pool → Deploy Relay** ಮೂಲಕ ರಿಲೇ ಅನ್ನು ನಿಯೋಜಿಸಿದಾಗ, ನಿಯೋಜನೆ ಪ್ರಕ್ರಿಯೆಯು ರಿಲೇಯ ದೃಢೀಕರಣ ಟೋಕನ್ ಅನ್ನು ಪ್ರಾಕ್ಸಿಯ `notes` JSON ಕ್ಷೇತ್ರದಲ್ಲಿ ಸಂಗ್ರಹಿಸುತ್ತದೆ:

- `STORAGE_ENCRYPTION_KEY` ಹೊಂದಿಸಿದ್ದರೆ, ಟೋಕನ್ ಅನ್ನು `relayAuthEnc` ಆಗಿ ಬರೆಯಲಾಗುತ್ತದೆ
  (ಸಂಗ್ರಹದಲ್ಲಿರುವಾಗ AES ಮೂಲಕ ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ).
- ಇಲ್ಲವಾದರೆ, ಅದನ್ನು ಸರಳ ಪಠ್ಯ `relayAuth` ಆಗಿ ಬರೆಯಲಾಗುತ್ತದೆ.

ವಿನಂತಿಯ ಸಮಯದಲ್ಲಿ `extractRelayAuth(notes)` ಲಭ್ಯವಿರುವ ಯಾವುದೇ ರೂಪವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ,
ಆದ್ದರಿಂದ ಮರುಪ್ರಾರಂಭಗಳ ನಂತರವೂ ರಿಲೇ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿರುತ್ತದೆ.

## ವೈಫಲ್ಯ ವಿಧಾನ 1 — ಕೀ ಬದಲಾವಣೆಯ ನಂತರ ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗದ ಟೋಕನ್

**ಲಕ್ಷಣ:** ಹಿಂದೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದ್ದ ರಿಲೇಗಳು ಈಗ ಪರಿಸರ ಅಥವಾ ಸೀಕ್ರೆಟ್-ಮ್ಯಾನೇಜರ್ನಲ್ಲಿ
`STORAGE_ENCRYPTION_KEY` ಬದಲಿಸಿದ ನಂತರ ಅಪ್ಸ್ಟ್ರೀಮ್ `401`/ದೃಢೀಕರಣ ದೋಷಗಳನ್ನು
ಹಿಂದಿರುಗಿಸುತ್ತವೆ. ಸಂಗ್ರಹಿಸಲಾದ `relayAuthEnc` ಬ್ಲಾಬ್ ಅನ್ನು ಇನ್ನು ಮುಂದೆ
ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲು ಸಾಧ್ಯವಾಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ `extractRelayAuth` ಖಾಲಿ ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು
ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಮತ್ತು ರಿಲೇ ಯಾವುದೇ ದೃಢೀಕರಣ ಮಾಹಿತಿಯನ್ನು ಕಳುಹಿಸುವುದಿಲ್ಲ.

**ಮರುಪಡೆಯುವಿಕೆ — ಅದೇ ಸ್ಥಳದಲ್ಲಿ ದುರಸ್ತಿ (ಮರುನಿಯೋಜನೆ ಬೇಡ):**

1. **Settings → Proxy Pool** ತೆರೆಯಿರಿ.
2. ದೃಢೀಕರಣ ಕಾಣೆಯಾಗಿರುವ ರಿಲೇ ಸಾಲುಗಳಲ್ಲಿ ಹಳದಿ `auth missing` ಬ್ಯಾಡ್ಜ್ ಮತ್ತು
   **Repair** ಬಟನ್ ಕಾಣಿಸುತ್ತದೆ.
3. **Repair** ಕ್ಲಿಕ್ ಮಾಡಿ. OmniRoute
   `POST /api/settings/proxies/[id]/repair-relay` ಅನ್ನು ಕರೆಮಾಡುತ್ತದೆ, ಇದು:
   - **ಪ್ರಸ್ತುತ** ಕೀಲಿಯಿಂದ `relayAuthEnc` ಅನ್ನು ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ,
   - ಸರಳ ಪಠ್ಯದ `relayAuth` ಅನ್ನು ಮತ್ತೆ `notes` ಗೆ ಬರೆಯುತ್ತದೆ,
   - `{ repaired: true, mode: "recovered" }` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

ಯಾವುದೇ ನಿಯೋಜನೆ ರುಜುವಾತುಗಳನ್ನು ಮರುನಮೂದಿಸದೆಯೇ ರಿಲೇ ಮತ್ತೆ ಸೇವೆ ಒದಗಿಸಲು ಪ್ರಾರಂಭಿಸುತ್ತದೆ.

ಪ್ರಸ್ತುತ `STORAGE_ENCRYPTION_KEY` ಇನ್ನೂ ಬ್ಲಾಬ್ ಅನ್ನು ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲು ಸಾಧ್ಯವಾದರೆ ಮಾತ್ರ ಇದು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.
ನೀವು ವಲಸೆ ಪ್ರಕ್ರಿಯೆ **ಇಲ್ಲದೆ** ಕೀಲಿಯನ್ನು ಬದಲಿಸಿದ್ದರೆ, ಬ್ಲಾಬ್ ಅನ್ನು
ಮರುಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ವೈಫಲ್ಯ ವಿಧಾನ 2 — ಮರುಪಡೆಯಲಾಗದ ಟೋಕನ್ (ಹಳೆಯ ಕೀ ಇನ್ನು ಲಭ್ಯವಿಲ್ಲ)

**ಲಕ್ಷಣ:** ನೀವು **Repair** ಕ್ಲಿಕ್ ಮಾಡಿದಾಗ
`{ repaired: false, mode: "redeploy", status: 409 }` ದೊರಕಿದೆ.

**ಮರುಪಡೆಯುವಿಕೆ — ಮರುನಿಯೋಜನೆ:**

ಪ್ರಸ್ತುತ ಕೀಲಿಯನ್ನು ಬಳಸಿ ಸಂಗ್ರಹಿಸಲಾದ ಟೋಕನ್ ಅನ್ನು ಮರುಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. ನೀವು ಮೂಲತಃ ಬಳಸಿದ
ಅದೇ ಮೋಡಲ್ನಿಂದ ರಿಲೇ ಅನ್ನು ಮರುನಿಯೋಜಿಸಿ (**Deploy Relay** ಮೆನು → Vercel / Deno
/ Cloudflare). ನಿಯೋಜನೆ ಪ್ರಕ್ರಿಯೆಯು ಹೊಸ ಟೋಕನ್ ಅನ್ನು ಬರೆಯುತ್ತದೆ (ಪ್ರಸ್ತುತ ಕೀಲಿಯಿಂದ
ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ) ಮತ್ತು ಸಾಲಿನ `auth missing` ಬ್ಯಾಡ್ಜ್ ತೆರವಾಗುತ್ತದೆ.

ಟೋಕನ್ ಅನ್ನು ಮರುಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲದಿದ್ದಾಗ UI ಯಲ್ಲಿನ **Repair** ಬಟನ್ ಸ್ವತಃ
ಮರುನಿಯೋಜನೆ ಮೋಡಲ್ ಅನ್ನು ತೆರೆಯುತ್ತದೆ, ಆದ್ದರಿಂದ ನೀವು ಅದನ್ನು ಕೈಯಾರೆ ಹುಡುಕಬೇಕಾಗಿಲ್ಲ.

## ವೈಫಲ್ಯ ವಿಧಾನ 3 — ರಿಲೇ ತಲುಪಬಹುದಾಗಿದೆ ಆದರೆ ಅನಾರೋಗ್ಯಕರವಾಗಿದೆ

**ಲಕ್ಷಣ:** ಪ್ರಾಕ್ಸಿ ಪರೀಕ್ಷೆಯು (`speed` ಬಟನ್) ರಿಲೇ ಚಾಲನೆಯಲ್ಲಿದೆ ಎಂದು ತೋರಿಸುತ್ತದೆ, ಆದರೆ ವಿನಂತಿಗಳು
ಇನ್ನೂ ಮಧ್ಯಂತರವಾಗಿ ವಿಫಲವಾಗುತ್ತವೆ.

OmniRoute ನ ಸ್ವಯಂ-ಪರೀಕ್ಷಾ ಪ್ರೋಬ್ ಹಿಂದಿರುಗಿಸುವ ರಿಲೇ ಅರಿವು ಹೆಡರ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ
(**Settings → Proxy Pool** ಮತ್ತು `relayTested` / `relayAlive` ಕೌಂಟರ್ಗಳನ್ನು ನೋಡಿ):

- `x-relay-url` — ಯಾವ ರಿಲೇ ಬ್ಯಾಕೆಂಡ್ ಪ್ರತಿಕ್ರಿಯಿಸಿತು.
- `x-relay-mode` — ಆ ವಿನಂತಿಗೆ `ts` | `bifrost` | `auto`.
- `x-relay-attempts` — ಯಶಸ್ಸು ದೊರೆಯುವ ಮೊದಲು ಎಷ್ಟು ರಿಲೇ ಹಾಪ್ಗಳನ್ನು ಪ್ರಯತ್ನಿಸಲಾಯಿತು.
- `x-relay-fallback` — ವಿನಂತಿಯು ಆದ್ಯತೆಯ ಬ್ಯಾಕೆಂಡ್ನಿಂದ TypeScript ರಿಲೇಗೆ
  ಫಾಲ್ಬ್ಯಾಕ್ ಆದಾಗ `true`.

ಕಡಿಮೆ `relayAlive` ಜೊತೆಗೆ ಹೆಚ್ಚಿನ `x-relay-fallback` ದರ ಇದ್ದರೆ, ಸೈಡ್ಕಾರ್
ಬ್ಯಾಕೆಂಡ್ ಅನಾರೋಗ್ಯಕರವಾಗಿದೆ ಎಂದರ್ಥ; ನೀವು ಅದನ್ನು ಸರಿಪಡಿಸಬೇಕು ಅಥವಾ ರಿಲೇ ಬ್ಯಾಕೆಂಡ್
ತಂತ್ರವನ್ನು `ts` ಗೆ ಬದಲಿಸಬೇಕು (`RELAY_BACKEND_STRATEGY.md` ನೋಡಿ).

## API ಉಲ್ಲೇಖ

| ವಿಧಾನ  | ಮಾರ್ಗ                                     | ಬಾಡಿ                    | ಯಶಸ್ಸು                                                                                                                    | ವೈಫಲ್ಯ                                                                                          |
| ------ | ----------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | ಮರು-ಪಡೆಯಲಾದಾಗ `200 { repaired: true, mode: "recovered" }`; ಸರಳ ಪಠ್ಯ ಈಗಾಗಲೇ ಇದ್ದಾಗ `200 { repaired: false, mode: "noop" }` | ಮರುಪಡೆಯಲಾಗದಿದ್ದಾಗ `409 { mode: "redeploy" }`; ರಿಲೇ ಪ್ರಕಾರವಲ್ಲದಿದ್ದರೆ `400`; ಕಂಡುಬರದಿದ್ದರೆ `404` |

ಪಟ್ಟಿ ಮಾರ್ಗ `GET /api/settings/proxies` ಪ್ರತಿ ಐಟಂಗೆ ರಹಸ್ಯ-ಮುಕ್ತ
`relayInfo: { isRelay, authMissing, repairMode }` ಅನ್ನು ಸೇರಿಸುತ್ತದೆ, ಇದರಿಂದ ಡ್ಯಾಶ್ಬೋರ್ಡ್
ಟೋಕನ್ ಅನ್ನು ಎಂದಿಗೂ ಬಹಿರಂಗಪಡಿಸದೆ ದುರಸ್ತಿ ಆಯ್ಕೆಯನ್ನು ಪ್ರದರ್ಶಿಸಬಹುದು.
