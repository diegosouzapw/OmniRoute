`open-sse/config/providerPluginManifest.ts` JSON-ಸುರಕ್ಷಿತ provider
plugin ಒಪ್ಪಂದವನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. `open-sse/config/providerPluginManifestRegistry.ts` ಆ
ಒಪ್ಪಂದವನ್ನು Bifrost, CLIProxyAPI ಅಥವಾ ಭವಿಷ್ಯದ Go/Rust routerನಂತಹ sidecarಗಳಿಗಾಗಿ
ಪ್ರಸ್ತುತ provider registryಗೆ ಜೋಡಿಸುತ್ತದೆ. TypeScript registry ಅಧಿಕೃತ
ಮೂಲವಾಗಿ ಉಳಿಯುತ್ತದೆ, ಆದರೆ sidecarಗಳು executor code, OAuth defaultಗಳು, headerಗಳು
ಅಥವಾ process environment state ಅನ್ನು import ಮಾಡದೆಯೇ manifest ಅನ್ನು ಬಳಸಬಹುದು.

processನ ಹೊರಗೆ ಚಲಿಸುವ sidecarಗಳಿಗಾಗಿ ಇದೇ manifest
`GET /api/v1/provider-plugin-manifest` ಮೂಲಕ HTTPಯಲ್ಲಿಯೂ ಲಭ್ಯವಿದೆ.

OmniRoute, `X-OmniRoute-Provider-Manifest-Url` request header ಮೂಲಕ ಆ URL ಅನ್ನು
Bifrost ಮತ್ತು CLIProxyAPIಗೆ ತಿಳಿಸುತ್ತದೆ. sidecarಗೆ ಸ್ಥಳೀಯ request origin ಬದಲಾಗಿ
ಸಾರ್ವಜನಿಕ ಅಥವಾ container network URL ಅಗತ್ಯವಿದ್ದಾಗ
`OMNIROUTE_PROVIDER_MANIFEST_URL` ಅನ್ನು ಹೊಂದಿಸಿ.

## Manifest ಅನ್ನು Refresh ಮಾಡುವುದು

HTTP endpoint `Cache-Control: public, max-age=60` ಮತ್ತು ಬಲವಾದ
`ETag` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. sidecar ಕೊನೆಯದಾಗಿ ಮೌಲ್ಯೀಕರಿಸಿದ manifest ಅನ್ನು ಉಳಿಸಿಕೊಂಡು,
refresh ಮಾಡುವಾಗ ಅದರ ETag ಅನ್ನು `If-None-Match`ನಲ್ಲಿ ಕಳುಹಿಸಬೇಕು. `304 Not Modified`
responseಗೆ body ಇರುವುದಿಲ್ಲ; sidecar ತನ್ನ cached manifest ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ.
ಮೌಲ್ಯೀಕರಿಸಿದ cached manifest ಯಾವುದೂ ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದಿದ್ದರೆ, sidecar `304` ಅನ್ನು
ಸ್ವೀಕರಿಸುವ ಬದಲು unconditional request ಅನ್ನು ಕಳುಹಿಸಬೇಕು.

## ಗುರಿ

provider metadataವನ್ನು plugin ಒಪ್ಪಂದದತ್ತ ವರ್ಗಾಯಿಸುವುದು, ಇದರಿಂದ ಅಂತಿಮವಾಗಿ ಕಡಿಮೆ
latencyಯ sidecar ಬಿಸಿ request path ಅನ್ನು ನಿರ್ವಹಿಸಬಹುದು ಮತ್ತು OmniRoute,
TypeScript route ಅನ್ನು policy gate ಮತ್ತು fallback ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳಬಹುದು. manifest
ಸಂಯೋಜನಾತ್ಮಕವಾಗಿದೆ: ಅದು ಸ್ವತಃ request routing ಅನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

## ಒಪ್ಪಂದ

manifest ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒಳಗೊಂಡಿದೆ:

- provider id ಮತ್ತು alias
- upstream format ಮತ್ತು executor ಹೆಸರು
- auth type, auth header ಮತ್ತು ಐಚ್ಛಿಕ auth prefix
- ಸ್ಥಿರ endpoint metadata
- sidecar ಅರ್ಹತೆ ಮತ್ತು provider TSನಲ್ಲೇ ಉಳಿಯಬೇಕಾದಾಗ ಅದಕ್ಕೆ ಸ್ಪಷ್ಟ ಕಾರಣಗಳು
- context length, vision/reasoning flagಗಳು ಮತ್ತು ಬೆಂಬಲಿಸದ paramಗಳಂತಹ
  JSON-ಸುರಕ್ಷಿತ model metadata
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` ಮತ್ತು `usage-supported` ಸೇರಿದಂತೆ capability tagಗಳು

manifest ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಹೊರತುಪಡಿಸುತ್ತದೆ:

- OAuth client secretಗಳು ಮತ್ತು default secret valueಗಳು
- runtime environment resolution
- request headerಗಳು ಮತ್ತು public credential helperಗಳು
- dynamic URL builderಗಳು
- executor functionಗಳು
- session pool ಆಂತರಿಕ ವಿವರಗಳು

## Capability Tagಗಳು

`capabilities` ಎಂಬುದು registry entryಯಿಂದ ಪಡೆಯಲಾದ tagಗಳ ವಿಂಗಡಿಸಿದ array ಆಗಿದೆ. Integratorಗಳು
TypeScript sourceಗಳನ್ನು ಪುನಃ ಓದುವ ಬದಲು, "ಈ provider ಏನು ಮಾಡಬಲ್ಲದು" ಎಂಬುದಕ್ಕೆ
machine-readable ಉತ್ತರವಾಗಿ ಇದನ್ನು ಪರಿಗಣಿಸಬೇಕು.

| Tag                  | ಅರ್ಥ                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `apikey`             | API key ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`authType` ಎಂಬುದು `apikey` ಅಥವಾ `optional`).                |
| `oauth`              | OAuth ಅಥವಾ session flow ಅನ್ನು ಬಳಸುತ್ತದೆ.                                                  |
| `responses`          | OpenAI Responses-API base URL ಅನ್ನು ಒದಗಿಸುತ್ತದೆ.                                          |
| `passthrough-models` | ಸ್ಥಿರ catalog ಬದಲಾಗಿ upstreamನಿಂದ ನೇರವಾಗಿ modelಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ.                        |
| `custom-executor`    | default ಅಲ್ಲದ executor ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಇದು TypeScript pathನಲ್ಲೇ ಉಳಿಯುತ್ತದೆ.  |
| `sidecar-candidate`  | `sidecar.eligible` ಅನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ — sidecar importಗಾಗಿ ಪರಿಗಣಿಸಲು ಸುರಕ್ಷಿತವಾಗಿದೆ. |
| `usage-fetch`        | ಸಂಯೋಜಿಸಲಾದ usage ಅಥವಾ quota fetcher (`getUsageForProvider`) ಹೊಂದಿದೆ.                      |
| `usage-supported`    | usage API ಈ provider ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`isSupportedUsageConnection`).                 |

`usage-fetch` ಕೇವಲ ಅನ್ವೇಷಣೆಗಾಗಿ. providerಗಾಗಿ usage ಅನ್ನು ಹೇಗೆ ಓದಬೇಕು ಎಂಬುದು OmniRouteಗೆ
ತಿಳಿದಿದೆ ಎಂದು ಇದು ವರದಿ ಮಾಡುತ್ತದೆ; ಇದು fetching ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದಿಲ್ಲ, quota semantics ಅನ್ನು
ಬದಲಾಯಿಸುವುದಿಲ್ಲ ಅಥವಾ providerಗಾಗಿ Dashboard quota widget ಸಕ್ರಿಯವಾಗಿದೆ ಎಂದು ಸೂಚಿಸುವುದಿಲ್ಲ —
ಆ widget ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ `USAGE_SUPPORTED_PROVIDERS` ಮೂಲಕ gate ಮಾಡಲಾಗುತ್ತದೆ. ಅಧಿಕೃತ ಮೂಲವು
`open-sse/services/usage/fetcherProviders.ts`ನಲ್ಲಿರುವ `USAGE_FETCHER_PROVIDERS` ಆಗಿದೆ.

ಆ ಪಟ್ಟಿಯನ್ನು usage dispatcher ಸ್ವೀಕರಿಸುವ stringಗಳ ಆಧಾರದಲ್ಲಿ key ಮಾಡಲಾಗಿದೆ, ಆದ್ದರಿಂದ ಅದು canonical idಗಳನ್ನು
aliasಗಳೊಂದಿಗೆ ಮಿಶ್ರಗೊಳಿಸುತ್ತದೆ ಮತ್ತು tagged providerಗಳ ಸಂಖ್ಯೆಗಿಂತ ಸ್ವಲ್ಪ ಉದ್ದವಾಗಿದೆ: manifest registryಯಲ್ಲಿ
chat providerಗಳಲ್ಲದ entryಗಳಿಗೆ (ಉದಾಹರಣೆಗೆ `firecrawl` search provider
ಮತ್ತು `amazon-q` ACP provider) tag ಮಾಡಲು ಯಾವುದೇ manifest entry ಇಲ್ಲ.

`usage-supported`, server ಮತ್ತು Dashboard usage routeಗಳು providerಗಾಗಿ connection ಅನ್ನು
ಸ್ವೀಕರಿಸುತ್ತವೆಯೇ ಎಂಬುದಕ್ಕೆ ಉತ್ತರಿಸುತ್ತದೆ. ಇದು `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
ಮತ್ತು `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) ಅನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ; ಎರಡನ್ನೂ
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) ಮೂಲಕ gate ಮಾಡಲಾಗಿದೆ.
`usage-fetch`ಗಿಂತ ಭಿನ್ನವಾಗಿ, ಇದನ್ನು provider id ಮೇಲಷ್ಟೇ ಹೊರಸೂಸಲಾಗುತ್ತದೆ — runtime guard ಯಾವುದೇ alias
resolution ಇಲ್ಲದೆ `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ manifest
ಅದೇ ನಿಯಮವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ. ಈ ಎರಡು tagಗಳು ವಿಭಿನ್ನ ವ್ಯಾಪ್ತಿಗಳನ್ನು ಹೊಂದಿವೆ: 3 providerಗಳು
`usage-fetch` ಅನ್ನು ಮಾತ್ರ (`opencode`, `opencode-zen`, `xai`) ಹೊಂದಿವೆ ಮತ್ತು 1 provider
`usage-supported` ಅನ್ನು ಮಾತ್ರ (`xiaomi-mimo-token-plan`) ಹೊಂದಿದೆ, ಆದ್ದರಿಂದ ಒಂದು ಇನ್ನೊಂದನ್ನು ಸೂಚಿಸುವುದಿಲ್ಲ.

## Sidecar ಬಳಕೆ

Sidecarಗಳು `sidecar.eligible` ಅನ್ನು ಷರತ್ತುರಹಿತ routing ನಿರ್ಧಾರವಾಗಿ ಪರಿಗಣಿಸದೆ, ಸಂಪ್ರದಾಯಬದ್ಧ ಅಭ್ಯರ್ಥಿ ಸಂಕೇತವಾಗಿ ಪರಿಗಣಿಸಬೇಕು. ಮೊದಲ import ಗುರಿಯು default executor ಬಳಸುವ API-key, static-endpoint providerಗಳಾಗಿರಬೇಕು. ಸಮಾನವಾದ ನಡವಳಿಕೆಯನ್ನು sidecar ಕಾರ್ಯಗತಗೊಳಿಸುವವರೆಗೆ ಮತ್ತು telemetry ಸಮಾನತೆಯನ್ನು ಸಾಬೀತುಪಡಿಸುವವರೆಗೆ custom web executorಗಳು, OAuth/session flowಗಳು, dynamic URL builderಗಳು ಅಥವಾ pool config ಹೊಂದಿರುವ providerಗಳು TypeScript fallback ಪಥದಲ್ಲಿಯೇ ಉಳಿಯಬೇಕು.

ಸೂಚಿಸಲಾದ migration ಹಂತಗಳು:

1. TS registryಯಿಂದ provider plugin manifest ಅನ್ನು ರಚಿಸಿ ಮತ್ತು ಮೌಲ್ಯೀಕರಿಸಿ.
2. API-key/static providerಗಳಿಗಾಗಿ manifest ಅನ್ನು import ಮಾಡಲು Bifrost ಅಥವಾ CLIProxyAPIಗೆ ಕಲಿಸಿ.
3. TS fallback ಅನ್ನು ಸಕ್ರಿಯವಾಗಿರಿಸಿಕೊಂಡೇ `OMNIROUTE_RELAY_BACKEND` ಹಿಂದೆ ಇರುವ sidecar ಮೂಲಕ ಅರ್ಹ providerಗಳನ್ನು route ಮಾಡಿ.
4. ಯಶಸ್ಸಿನ ಪ್ರಮಾಣ, p99 latency, streaming ನಡವಳಿಕೆ ಮತ್ತು ಬೆಂಬಲಿಸದ parameterಗಳ ನಿರ್ವಹಣೆ TS ಪಥಕ್ಕೆ ಹೊಂದಿಕೆಯಾದಾಗ ಮಾತ್ರ providerಗಳನ್ನು ಉತ್ತೇಜಿಸಿ.
5. ಪ್ರತಿ ಬಾರಿ ಒಂದು provider familyಗಾಗಿ custom executorಗಳಿಗೆ sidecar-native pluginಗಳನ್ನು ಸೇರಿಸಿ.

## Providerಗಳನ್ನು ನೇರವಾಗಿ Nextನಲ್ಲಿ ಏಕೆ Embed ಮಾಡಬಾರದು

Next frontend provider execution ಅನ್ನು ನಿರ್ವಹಿಸಬಾರದು. ಅದು API boundary ಅನ್ನು ಕರೆಯಬೇಕು. ನಂತರ backend, TypeScript executor, Bifrost, CLIProxyAPI ಅಥವಾ ಭವಿಷ್ಯದ native sidecar ಅನ್ನು ಬಳಸಬೇಕೆ ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸಬಹುದು. ಇದರಿಂದ ಯಾವುದೇ sidecar handoffಗೆ ಮೊದಲು request signing, allowlist ತಪಾಸಣೆಗಳು, DB policy ಮತ್ತು fallback ನಡವಳಿಕೆ ಕೇಂದ್ರೀಕೃತವಾಗಿರುತ್ತವೆ.
