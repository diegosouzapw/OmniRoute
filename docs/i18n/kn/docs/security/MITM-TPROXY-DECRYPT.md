TPROXY ಪಾರದರ್ಶಕ ಡೀಕ್ರಿಪ್ಟ್ ಎನ್ನುವುದು OmniRoute ನ
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM ಸ್ಟ್ಯಾಕ್ಗಾಗಿ ಇರುವ **5ನೇ ಕ್ಯಾಪ್ಚರ್ ಮೋಡ್** ಆಗಿದೆ. ಇದು Linux ನಲ್ಲಿ kernel TPROXY + policy routing ಬಳಸಿ ಸ್ಥಳೀಯವಾಗಿ ಹೊರಹೋಗುವ HTTPS ಟ್ರಾಫಿಕ್ ಅನ್ನು ಪ್ರತಿಬಂಧಿಸಿ **ಡೀಕ್ರಿಪ್ಟ್** ಮಾಡುತ್ತದೆ — `/etc/hosts` ಅನ್ನು ಸ್ಪೂಫ್ ಮಾಡದೆ ಮತ್ತು OS-ವ್ಯಾಪಿ system-proxy ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಮಾರ್ಪಡಿಸದೆ. ಇದು ಹೆಡ್ಲೆಸ್ ಬಳಕೆಗೆ ಸೂಕ್ತವಾಗಿದೆ
(ಸ್ವಚ್ಛಗೊಳಿಸಬೇಕಾದ DNS ಬದಲಾವಣೆಗಳಿಲ್ಲ) ಮತ್ತು ರೀಬೂಟ್ ಆದಾಗ ಫೈರ್ವಾಲ್ ನಿಯಮಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ತೆರವುಗೊಳ್ಳುತ್ತವೆ.

ಇತರ ಕ್ಯಾಪ್ಚರ್ ಮೋಡ್ಗಳಿಗಿಂತ ಭಿನ್ನವಾಗಿ, TPROXY ಗೆ ಪ್ರತಿ ಹೋಸ್ಟ್ಗೆ ಪ್ರತ್ಯೇಕ ಸೆಟಪ್ ಅಗತ್ಯವಿಲ್ಲ: ಇದು ಗುರಿ ಪೋರ್ಟ್ನಲ್ಲಿರುವ **ಯಾವುದೇ** ಗಮ್ಯಸ್ಥಾನ ಹೋಸ್ಟ್ಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ಪ್ರತಿಬಂಧಿಸುತ್ತದೆ, ಪ್ರತಿ SNI ಹೋಸ್ಟ್ಹೆಸರಿಗಾಗಿ ತಕ್ಷಣವೇ ರಚಿಸುವ ಲೀಫ್ ಪ್ರಮಾಣಪತ್ರದೊಂದಿಗೆ TLS ಅನ್ನು ಅಂತ್ಯಗೊಳಿಸುತ್ತದೆ, ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ವಿನಿಮಯವನ್ನು ಸೆರೆಹಿಡಿಯುತ್ತದೆ ಮತ್ತು ಮೂಲ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ವಿನಂತಿಯನ್ನು ಮರು-ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ.

> **Linux ನಲ್ಲಿ ಮಾತ್ರ, root ಗೆ ಮಾತ್ರ, ಆಯ್ಕೆಯ ಮೇರೆಗೆ.** ಈ ಮೋಡ್ಗೆ Linux, C ಟೂಲ್ಚೈನ್ನೊಂದಿಗೆ ನಿರ್ಮಿಸಲಾದ ನೇಟಿವ್ addon ಮತ್ತು **CAP_NET_ADMIN** ಸಾಮರ್ಥ್ಯ (ಸಾಮಾನ್ಯವಾಗಿ root) ಅಗತ್ಯವಿದೆ. ಇದನ್ನು loopback-only AgentBridge API ಯ ಹಿಂದೆ ನಿರ್ಬಂಧಿಸಲಾಗಿದೆ ಮತ್ತು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ. ಯಾವುದೇ ಹೋಸ್ಟ್ಗೆ ಸಹಿ ಮಾಡಬಲ್ಲ ವಿಶ್ವಾಸಾರ್ಹ MITM CA ಒಂದು ಪ್ರಬಲ ಸಾಮರ್ಥ್ಯವಾಗಿದೆ — [§6 ಭದ್ರತೆ](#6-security) ನೋಡಿ.

**ಮೂಲ:** `src/mitm/tproxy/`
**API ಮಾರ್ಗ:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಟಾಗಲ್:** Traffic Inspector → ಕ್ಯಾಪ್ಚರ್-ಮೋಡ್ಗಳ ಟೂಲ್ಬಾರ್ → **"TPROXY ಡೀಕ್ರಿಪ್ಟ್"** ⚠

## §1 ಇದು ಏನು ಮತ್ತು ಯಾವಾಗ ಬಳಸಬೇಕು

ಇತರ ನಾಲ್ಕು ಕ್ಯಾಪ್ಚರ್ ಮೋಡ್ಗಳಲ್ಲಿ ಪ್ರತಿಯೊಂದಕ್ಕೂ ಒಂದು ಮಿತಿ ಇದೆ:

| ಮೋಡ್                    | ಟ್ರಾಫಿಕ್ ಅನ್ನು ಹೇಗೆ ನಿರ್ದೇಶಿಸಲಾಗುತ್ತದೆ      | ಮಿತಿ                                                     |
| ----------------------- | ------------------------------------------- | -------------------------------------------------------- |
| AgentBridge             | ನಿಗದಿತ ಹೋಸ್ಟ್ ಸಮೂಹದ `/etc/hosts` DNS ಸ್ಪೂಫ್ | ನೋಂದಾಯಿತ IDE-agent ಹೋಸ್ಟ್ಗಳು ಮಾತ್ರ                       |
| ಕಸ್ಟಮ್ ಹೋಸ್ಟ್ಗಳು        | ಪ್ರತಿ ಹೋಸ್ಟ್ಗೆ `/etc/hosts` DNS ಸ್ಪೂಫ್      | ಪ್ರತಿ ಹೋಸ್ಟ್ಗೆ ಒಂದು ನಮೂದು; hosts ಸಂಪಾದಿಸಲು sudo          |
| HTTP_PROXY              | `HTTP_PROXY`/`HTTPS_PROXY` env              | env var ಅನ್ನು ಗೌರವಿಸುವ ಆ್ಯಪ್ಗಳು ಮಾತ್ರ                    |
| ಸಿಸ್ಟಮ್-ವ್ಯಾಪಿ ಪ್ರಾಕ್ಸಿ | OS ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳು                    | ಜಾಗತಿಕ ಸ್ಥಿತಿಯನ್ನು ಮಾರ್ಪಡಿಸುತ್ತದೆ; ಹಿಂತಿರುಗಿಸುವಿಕೆ ಅಗತ್ಯ |

ಬದಲಾಗಿ, TPROXY ಪಾರದರ್ಶಕ ಡೀಕ್ರಿಪ್ಟ್ ಟ್ರಾಫಿಕ್ ಅನ್ನು **kernel** ಲೇಯರ್ನಲ್ಲಿ ನಿರ್ದೇಶಿಸುತ್ತದೆ. ಇದು `mangle OUTPUT` ಚೈನ್ನಲ್ಲಿ ಗುರಿ ಪೋರ್ಟ್ಗೆ (ಪೂರ್ವನಿಯೋಜಿತ `443`) ಹೊಸ ಸ್ಥಳೀಯ ಹೊರಹೋಗುವ TCP ಸಂಪರ್ಕಗಳನ್ನು ಗುರುತು ಮಾಡುತ್ತದೆ, ಒಂದು `ip rule` ಗುರುತು ಮಾಡಲಾದ ಪ್ಯಾಕೆಟ್ಗಳನ್ನು ಸ್ಥಳೀಯ ವಿತರಣೆಗೆ ಮರುಮಾರ್ಗಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಮರು-ಪ್ರವೇಶದ ವೇಳೆ `mangle PREROUTING` ನ `TPROXY` ಗುರಿಯು ಅವುಗಳನ್ನು **IP_TRANSPARENT** listener ಗೆ ಹಸ್ತಾಂತರಿಸುತ್ತದೆ — ಅದು ನಂತರ TLS ಅನ್ನು ಅಂತ್ಯಗೊಳಿಸಿ plaintext ಅನ್ನು ಸೆರೆಹಿಡಿಯುತ್ತದೆ.

ಈ ಕೆಳಗಿನ ಗುಣಗಳನ್ನು ಹೊಂದಿರುವ ಪ್ರಕ್ರಿಯೆಯಿಂದ ಟ್ರಾಫಿಕ್ ಅನ್ನು ಸೆರೆಹಿಡಿದು ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಲು ಬಯಸಿದಾಗ ಇದನ್ನು ಬಳಸಿ:

- AgentBridge ನೋಂದಾಯಿಸದ ಹೋಸ್ಟ್ನೊಂದಿಗೆ ಸಂವಹನ ನಡೆಸುತ್ತದೆ, ಮತ್ತು
- `HTTP_PROXY` ಅನ್ನು ಗೌರವಿಸುವುದಿಲ್ಲ, ಮತ್ತು
- ಸಿಸ್ಟಮ್-ವ್ಯಾಪಿ ಪ್ರಾಕ್ಸಿ ಬದಲಾವಣೆಯಿಂದ ಅದನ್ನು ಅಸ್ತವ್ಯಸ್ತಗೊಳಿಸಲು ನೀವು ಬಯಸುವುದಿಲ್ಲ.

ಪ್ರತಿಬಂಧಿಸುವಿಕೆಯು kernel ನಲ್ಲಿ ನಡೆಯುವುದರಿಂದ, ಮೂಲ ಪ್ರಕ್ರಿಯೆಗೆ **ಯಾವುದೇ ಸಂರಚನಾ ಬದಲಾವಣೆ** ಅಗತ್ಯವಿಲ್ಲ — ಆದರೆ ಪ್ರಕ್ರಿಯೆಯು OmniRoute ಸ್ಥಾಪಿಸುವ ಡೈನಾಮಿಕ್ CA ಅನ್ನು ವಿಶ್ವಾಸಿಸಬೇಕು ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) ನೋಡಿ).

## §2 ಅಗತ್ಯತೆಗಳು

| ಅಗತ್ಯತೆ            | ವಿವರ                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **OS**             | Linux ಮಾತ್ರ — **IP_TRANSPARENT** ಎಂಬುದು Linuxಗೆ ಮಾತ್ರ ಸೀಮಿತವಾದ socket ಆಯ್ಕೆಯಾಗಿದೆ. ಇತರ ಎಲ್ಲ ಪ್ಲಾಟ್ಫಾರ್ಮ್ಗಳಲ್ಲಿ loader "ಲಭ್ಯವಿಲ್ಲ" ಎಂದು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.           |
| **ಅಧಿಕಾರ**         | transparent socket ರಚಿಸಲು ಮತ್ತು `iptables`/`ip` ನಿಯಮಗಳನ್ನು ಅನ್ವಯಿಸಲು **CAP_NET_ADMIN** capability ಅಗತ್ಯ — ಪ್ರಾಯೋಗಿಕವಾಗಿ, root ಆಗಿ ಚಲಾಯಿಸಿ.                         |
| **Native addon**   | ಒಂದು ಸಣ್ಣ N-API addon (`src/mitm/tproxy/native/transparent.c`) ಅನ್ನು build ಮಾಡಿರಬೇಕು ಅಥವಾ prebuild ಆಗಿ ಒದಗಿಸಿರಬೇಕು. [§3](#3-the-native-ip_transparent-addon) ನೋಡಿ. |
| **Kernel modules** | `TPROXY`, `mangle`, ಮತ್ತು `mark` match ಬೆಂಬಲದೊಂದಿಗೆ `iptables` (kernel 6.8.0 ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸಲಾಗಿದೆ).                                                            |

**ಸಮರ್ಪಕ ಹಿಂಜರಿಕೆ:** ಯಾವುದೇ ಅಗತ್ಯತೆ ಪೂರೈಸದಿದ್ದರೆ (Linux ಅಲ್ಲದಿರುವುದು, toolchain ಇಲ್ಲದಿರುವುದು,
addon build ಆಗದಿರುವುದು), addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exception ಎಸೆಯುವ ಬದಲು `null` ಹಿಂತಿರುಗಿಸುತ್ತದೆ. ನಂತರ capture-mode ಸ್ಥಿತಿಯು
`available: false` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ, dashboard toggle ಅನ್ನು
"TPROXY decryptಗೆ Linux + root + native addon ಅಗತ್ಯವಿದೆ" ಎಂಬ tooltipನೊಂದಿಗೆ
**ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗುತ್ತದೆ**, ಮತ್ತು OmniRouteನ ಉಳಿದ ಭಾಗವು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಲೇ ಇರುತ್ತದೆ.

## §3 Native IP_TRANSPARENT addon

Nodeನ `net` module, `bind()` ಮಾಡುವುದಕ್ಕೆ _ಮೊದಲು_ `setsockopt(IP_TRANSPARENT)` ಅನ್ನು
ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ; TPROXYಗೆ ಇದು ಅಗತ್ಯವಾಗಿದೆ (ಇಲ್ಲದಿದ್ದರೆ kernel ಮರುನಿರ್ದೇಶಿಸಲಾದ packetಗಳನ್ನು ಕೈಬಿಡುತ್ತದೆ). ಈ addon
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` ಮೂಲಕ build ಮಾಡಲಾಗಿದೆ) ಮೂರು functionಗಳನ್ನು
ಒದಗಿಸುವ ಒಂದು ಸಣ್ಣ N-API module ಆಗಿದ್ದು, ಅವುಗಳನ್ನು `transparentSocket.ts` ಮೂಲಕ ಬಳಸಲಾಗುತ್ತದೆ:

| Addon function                        | Socket ಕಾರ್ಯ                                                                                              | ಬಳಕೆ                                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`; raw fd ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ | transparent capture listener (Node, `server.listen({ fd })` ಮೂಲಕ fd ಅನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳುತ್ತದೆ) |
| `setSocketMark(fd, mark)`             | ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ fd ಮೇಲೆ `setsockopt` **SO_MARK**                                                         | anti-loop (proxyಯ ಸ್ವಂತ socketಗಳಿಗೆ mark ಹಾಕಲು)                                               |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()`ಗೆ **ಮೊದಲು** `socket()` + **SO_MARK**; fd ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ                  | ಮರು-encrypt ಮಾಡಿದ upstream forward (SYN mark ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ)                              |

ಮೂಲ destination ಅನ್ನು `socket.localAddress`/`localPort` ನಿಂದ ಓದಲಾಗುತ್ತದೆ — TPROXY
ಅದನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ **SO_ORIGINAL_DST**/NAT lookup ಅಗತ್ಯವಿಲ್ಲ.

### Addon ಅನ್ನು build ಮಾಡುವುದು

```bash
npm run build:native:tproxy      # src/mitm/tproxy/nativeಗೆ cd ಮಾಡಿ ಮತ್ತು node-gyp rebuild ಚಲಾಯಿಸಿ
                                 # -> native/build/Release/transparent.node
```

- `npm run build` ಸಮಯದಲ್ಲಿ, `scripts/build/build-tproxy-native.mjs` ಎಂಬುದು `node-gyp
rebuild` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇದು **Linuxಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿದೆ ಮತ್ತು ವೈಫಲ್ಯವು ಮಾರಕವಲ್ಲ** — toolchain ಇಲ್ಲದಿದ್ದರೆ
  capture mode ಲಭ್ಯವಿಲ್ಲದಂತಾಗುತ್ತದೆ.
- `assembleStandalone.mjs`, `build/Release/transparent.node` ಅನ್ನು
  standalone bundleಗೆ ನಕಲಿಸುತ್ತದೆ; `transparentSocket.ts` ಅದನ್ನು module-relative ಮತ್ತು
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) ಎರಡೂ ರೀತಿಯಲ್ಲಿ resolve ಮಾಡುತ್ತದೆ.
- `build/` ಮತ್ತು `prebuilds/` ಅನ್ನು git ನಿರ್ಲಕ್ಷಿಸುತ್ತದೆ — binary ಅನ್ನು **build ಮಾಡಲಾಗುತ್ತದೆ,
  ಎಂದಿಗೂ commit ಮಾಡಲಾಗುವುದಿಲ್ಲ**.

Loader ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ಇವುಗಳನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ:
`native/build/Release/transparent.node`, ನಂತರ `native/prebuilds/transparent.node`
(ಎರಡೂ module-relative ಮತ್ತು `<cwd>/src/mitm/tproxy/` ಅಡಿಯಲ್ಲಿ).

## §4 ಪ್ರತಿ-SNI ಡೈನಾಮಿಕ್ CA ಮತ್ತು ಟ್ರಸ್ಟ್-ಸ್ಟೋರ್ ಇನ್ಸ್ಟಾಲರ್

> **#6684 ಅಪ್ಡೇಟ್:** AgentBridge ಸ್ಥಿರ ಸರ್ವರ್ (`src/mitm/server.cjs`) ಈಗ
> ಒಂದೇ ಸ್ಥಿರ ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ ಲೀಫ್ ಬದಲಿಗೆ ಇದೇ CA/ಲೀಫ್ ಆರ್ಕಿಟೆಕ್ಚರ್ ಮಾದರಿಯನ್ನು
> ಹಂಚಿಕೊಳ್ಳುತ್ತದೆ. ಇದು ಒಂದು **ಪ್ರತ್ಯೇಕ** CA ಇನ್ಸ್ಟನ್ಸ್
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt` ನಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ)
> ಬಳಸುತ್ತದೆ ಮತ್ತು ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ `omniroute-mitm.crt` ಟ್ರಸ್ಟ್-ಸ್ಟೋರ್ ಸ್ಲಾಟ್ನಲ್ಲಿ
> ಇನ್ಸ್ಟಾಲ್ ಆಗುತ್ತದೆ (ಅಲ್ಲಿದ್ದ ಹಳೆಯ ಏಕೈಕ ಲೀಫ್ ಅನ್ನು ಬದಲಿಸುತ್ತದೆ — ದ್ವಂದ್ವ-ಟ್ರಸ್ಟ್
> ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ ಅಗತ್ಯವಿಲ್ಲ), ಹಾಗೂ ಕೆಳಗಿನ TPROXY-ಯ ಸ್ವಂತ
> `omniroute-tproxy-ca.crt` ಸ್ಲಾಟ್ನಿಂದ ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಇಡಲಾಗುತ್ತದೆ.
> ಹೊಸ AgentBridge ಇನ್ಸ್ಟಾಲೇಶನ್ಗಳು CA ಮಾದರಿಯನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪಡೆಯುತ್ತವೆ;
> ಈಗಾಗಲೇ ಹಳೆಯ ಸ್ಥಿರ ಲೀಫ್ ಅನ್ನು ನಂಬಿರುವ ಇನ್ಸ್ಟಾಲೇಶನ್ನಲ್ಲಿ ಆಪರೇಟರ್
> `MITM_ROOT_CA_ENABLED=true` ಮೂಲಕ ಆಯ್ಕೆಮಾಡುವವರೆಗೂ ಅದನ್ನೇ ಬಳಸಲಾಗುತ್ತದೆ
> (`src/mitm/cert/migration.ts` ನೋಡಿ) — **ಯಾವುದೇ** ಹೋಸ್ಟ್ಗಾಗಿ ಲೀಫ್ಗೆ ಸಹಿ ಮಾಡಬಲ್ಲ
> ವಿಶ್ವಾಸಾರ್ಹ MITM CA ಹಳೆಯ ಸ್ಥಿರ-SAN ಲೀಫ್ಗಿಂತ ಗಣನೀಯವಾಗಿ ಹೆಚ್ಚು ಶಕ್ತಿಶಾಲಿಯಾಗಿದೆ,
> ಆದ್ದರಿಂದ ಈಗಾಗಲೇ ವಿಶ್ವಾಸಾರ್ಹವಾಗಿರುವ ಇನ್ಸ್ಟಾಲೇಶನ್ನಲ್ಲಿ ಈ ಬದಲಾವಣೆ ಎಂದಿಗೂ
> ಮೌನವಾಗಿ ನಡೆಯುವುದಿಲ್ಲ.

ಐತಿಹಾಸಿಕವಾಗಿ, ಸ್ಥಿರ AgentBridge MITM ಪ್ರಮಾಣಪತ್ರವು AgentBridge ಒಂದು **ನಿಶ್ಚಿತ**
ಹೋಸ್ಟ್ ಸಮೂಹಕ್ಕಾಗಿ DNS-ಸ್ಪೂಫಿಂಗ್ ಮಾಡುವುದರಿಂದ ಮಾತ್ರ ಕೆಲಸ ಮಾಡುತ್ತಿತ್ತು (ಈಗ ಅದನ್ನು
ಕೆಳಗಿನ ಮಾದರಿಯೊಂದಿಗೆ ಏಕೀಕರಿಸಲಾಗಿದೆ). TPROXY **ಯಾವುದೇ** ಹೋಸ್ಟ್ಗಳನ್ನು
ತಡೆಹಿಡಿಯುತ್ತದೆ, ಆದ್ದರಿಂದ ಕ್ಲೈಂಟ್ ವಿನಂತಿಸುವ ಯಾವುದೇ SNI ಗಾಗಿ ಅದರ ಲಿಸನರ್ ಮಾನ್ಯವಾದ
ಲೀಫ್ ಅನ್ನು ಪ್ರಸ್ತುತಪಡಿಸಬೇಕು — ಕೇವಲ 4 antigravity ಹೋಸ್ಟ್ಗಳ ಬದಲಿಗೆ ಸಂಪೂರ್ಣ
`MITM_TOOL_HOSTS` ಸಮೂಹಕ್ಕೆ (9 ಟೂಲ್ ನಮೂದುಗಳು) ಈಗ AgentBridge ಹೊಂದಿರುವ ಅದೇ
ಅವಶ್ಯಕತೆ.

### ಡೈನಾಮಿಕ್ CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`, `selfsigned` ಡಿಪೆಂಡೆನ್ಸಿ ಮೇಲೆ ನಿರ್ಮಿಸಲಾದ ಸ್ಥಳೀಯ CA ಅನ್ನು
ಚಲಾಯಿಸುತ್ತದೆ, ಅದು:

- `generateMitmCa()` ಮೂಲಕ ದೀರ್ಘಾವಧಿಯ CA ಅನ್ನು ರಚಿಸುತ್ತದೆ (CN `"OmniRoute MITM CA"`,
  10 ವರ್ಷಗಳ ಮಾನ್ಯತೆ, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bit RSA / SHA-256).
- `issueLeafCert()` ಮೂಲಕ **ಪ್ರತಿ SNI ಹೋಸ್ಟ್ನೇಮ್ಗೆ ಬೇಡಿಕೆಯ ಮೇರೆಗೆ ಲೀಫ್**
  ನೀಡುತ್ತದೆ (1 ವರ್ಷದ ಮಾನ್ಯತೆ, `subjectAltName` = SNI ಹೋಸ್ಟ್) ಮತ್ತು ಪ್ರತಿ
  ಹೋಸ್ಟ್ನೇಮ್ಗೆ ಒಂದು `tls.SecureContext` ಅನ್ನು ಕ್ಯಾಶ್ ಮಾಡುತ್ತದೆ.
- TLS ಅನ್ನು ಅಂತ್ಯಗೊಳಿಸುವ ಸರ್ವರ್ಗಾಗಿ `createSNICallback()` ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
  ([§5](#5-how-decrypt-and-capture-work) ನೋಡಿ).
- ಮರುಪ್ರಾರಂಭಗಳ ನಡುವೆಯೂ CA ಸ್ಥಿರವಾಗಿರಲು `existingCa` ಜೊತೆಗೆ ರಚಿಸಬಹುದು
  (ಆದ್ದರಿಂದ ಟ್ರಸ್ಟ್ ಸ್ಟೋರ್ ಅನ್ನು ಮರು-ಇನ್ಸ್ಟಾಲ್ ಮಾಡುವ ಅಗತ್ಯವಿಲ್ಲ).

CA ಖಾಸಗಿ ಕೀಲಿ **ಎಂದಿಗೂ ಯಂತ್ರವನ್ನು ಬಿಟ್ಟು ಹೊರಹೋಗುವುದಿಲ್ಲ**.

### ಟ್ರಸ್ಟ್-ಸ್ಟೋರ್ ಇನ್ಸ್ಟಾಲರ್ (`src/mitm/tproxy/caTrust.ts`)

ತಡೆಹಿಡಿಯಲಾದ ಕ್ಲೈಂಟ್ ಡೈನಾಮಿಕ್ CA ಅನ್ನು ನಂಬಬೇಕು, ಆದ್ದರಿಂದ ಕ್ಯಾಪ್ಚರ್ ಮೋಡ್ ಅನ್ನು
ಪ್ರಾರಂಭಿಸುವಾಗ CA ಪ್ರಮಾಣಪತ್ರವನ್ನು OS ಟ್ರಸ್ಟ್ ಸ್ಟೋರ್ನಲ್ಲಿ ಒಂದು **ಮೀಸಲಾದ
ಸ್ಲಾಟ್** ಅಡಿಯಲ್ಲಿ ಇನ್ಸ್ಟಾಲ್ ಮಾಡಲಾಗುತ್ತದೆ — `omniroute-tproxy-ca.crt`
(ಸ್ಥಿರಾಂಕ `TPROXY_CA_CERT_NAME`) — ಎರಡೂ ಪರಸ್ಪರ ಮೇಲ್ಬರೆಯದಂತೆ ಇದನ್ನು ಸ್ಥಿರ
MITM ಪ್ರಮಾಣಪತ್ರದ ಸ್ಲಾಟ್ನಿಂದ (`omniroute-mitm.crt`) ಪ್ರತ್ಯೇಕವಾಗಿ ಇಡಲಾಗುತ್ತದೆ.

`installTproxyCa(caPem, sudoPassword?)` ಡಿಸ್ಟ್ರೋದ ಆಂಕರ್ ಡೈರೆಕ್ಟರಿಯನ್ನು
ಪತ್ತೆಮಾಡುತ್ತದೆ (ಕ್ರಮವಾಗಿ: ಮೊದಲು Debian-ಶೈಲಿ) ಮತ್ತು ಅದಕ್ಕೆ ಹೊಂದುವ ರಿಫ್ರೆಶ್
ಕಮಾಂಡ್ ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ:

| ಆಂಕರ್ ಡೈರೆಕ್ಟರಿ                             | ರಿಫ್ರೆಶ್ ಕಮಾಂಡ್          |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ಇನ್ಸ್ಟಾಲೇಶನ್ PEM ಅನ್ನು ತಾತ್ಕಾಲಿಕ ಫೈಲ್ಗೆ ಸ್ಟೇಜ್ ಮಾಡುತ್ತದೆ, ನಂತರ
(ವಿಶೇಷಾಧಿಕಾರದೊಂದಿಗೆ) ಆಂಕರ್ ಡೈರೆಕ್ಟರಿಯಲ್ಲಿ `mkdir -p` ಚಲಾಯಿಸಿ, ಸ್ಟೇಜ್ ಮಾಡಿದ
ಫೈಲ್ ಅನ್ನು ಅದಕ್ಕೆ `cp` ಮಾಡುತ್ತದೆ ಮತ್ತು ರಿಫ್ರೆಶ್ ಕಮಾಂಡ್ ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ.
`uninstallTproxyCa()` ಮೀಸಲಾದ ಸ್ಲಾಟ್ ಅನ್ನು ಮಾತ್ರ ತೆಗೆದುಹಾಕುತ್ತದೆ (ಸ್ಥಿರ MITM
ಪ್ರಮಾಣಪತ್ರವನ್ನು ಹಾಗೆಯೇ ಬಿಡುತ್ತದೆ) ಮತ್ತು ರಿಫ್ರೆಶ್ ಮಾಡುತ್ತದೆ — Linux ಅಲ್ಲದ
ವ್ಯವಸ್ಥೆಗಳಲ್ಲಿ ಇದು ಯಾವುದೇ ಕಾರ್ಯಾಚರಣೆ ಮಾಡುವುದಿಲ್ಲ.

ಎಲ್ಲಾ ವಿಶೇಷಾಧಿಕಾರದ ಕಮಾಂಡ್ಗಳು `execFileWithPassword`
(`src/mitm/systemCommands.ts`) ಮೂಲಕ ಚಲಿಸುತ್ತವೆ — **ಆರ್ಗ್ಯುಮೆಂಟ್ ಅರೇಗಳೊಂದಿಗೆ,
ಶೆಲ್ ಇಲ್ಲದೆ, ಸ್ಟ್ರಿಂಗ್ ಇಂಟರ್ಪೊಲೇಶನ್ ಇಲ್ಲದೆ** `spawn` ಬಳಸಲಾಗುತ್ತದೆ
(ಕಠಿಣ ನಿಯಮ #13). ಪ್ರಕ್ರಿಯೆಯು root ಆಗಿರುವಾಗ (ಉದಾ. VPS), ಗುರಿ ನೇರವಾಗಿ
ಚಲಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ ಪಾಸ್ವರ್ಡ್ ಅಗತ್ಯವಿಲ್ಲ; root ಅಲ್ಲದ ಡೆಸ್ಕ್ಟಾಪ್ನಲ್ಲಿ
`sudoPassword` ಅನ್ನು stdin ಮೂಲಕ `sudo -S` ಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ.

> ಟ್ರಸ್ಟ್-ಸ್ಟೋರ್ ಇನ್ಸ್ಟಾಲೇಶನ್ಗೆ ಅನುಮತಿ ನೀಡಲು ಡೆಸ್ಕ್ಟಾಪ್ನ `sudoPassword`
> ಅನ್ನು POST ಬಾಡಿಯಲ್ಲಿ ಒದಗಿಸಲಾಗುತ್ತದೆ; ಪ್ರಕ್ರಿಯೆಯು root ಆಗಿದ್ದರೆ ಅದನ್ನು
> ಸಂಪೂರ್ಣವಾಗಿ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ.

## §5 ಡೀಕ್ರಿಪ್ಟ್ ಮತ್ತು ಕ್ಯಾಪ್ಚರ್ ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ

ಪೈಪ್ಲೈನ್ (ಎಲ್ಲವೂ `src/mitm/tproxy/` ಅಡಿಯಲ್ಲಿ):

```
ಸ್ಥಳೀಯ app  ──TCP/443──▶  mangle OUTPUT ಸಂಪರ್ಕವನ್ನು ಗುರುತಿಸುತ್ತದೆ (fwmark)
                          ip rule → ಸ್ಥಳೀಯ route table → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT listener (port 8443)
                              │  captureMode.ts: socket.localAddress ನಿಂದ ಮೂಲ ಗಮ್ಯಸ್ಥಾನವನ್ನು ಓದುತ್ತದೆ
                              ▼
                          tlsCapture.ts:
                            1. ಪ್ರತಿ-SNI leaf (dynamicCert) ಬಳಸಿ CLIENT ನ TLS ಅನ್ನು ಅಂತ್ಯಗೊಳಿಸುತ್ತದೆ
                            2. ಆಂತರಿಕ http.Server ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿದ plaintext ಅನ್ನು ಪಾರ್ಸ್ ಮಾಡುತ್ತದೆ
                            3. capture → source: "tproxy" ಜೊತೆಗೆ globalTrafficBuffer.push()
                               (sanitizeHeaders + maskSecret ಅನ್ವಯಿಸಲಾಗಿದೆ)
                            4. bypass ಗುರುತು ಹಾಕಿದ socket ಮೂಲಕ (connectMarked, anti-loop)
                               ಮೂಲ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ ಮರು-ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿ ಫಾರ್ವರ್ಡ್ ಮಾಡುತ್ತದೆ
                              │
                              ▼
                          ಮೂಲ upstream (api.example.com)
```

- **TLS ಅಂತ್ಯಗೊಳಿಸುವಿಕೆ** (`createTlsCaptureServer`): dynamic CA ಯ SNI callback ಬಳಸಿ ಕಚ್ಚಾ ಪ್ರತಿಬಂಧಿತ
  socket ಅನ್ನು server-side `tls.TLSSocket` ನಲ್ಲಿ ಸುತ್ತಿ, ನಂತರ ಡೀಕ್ರಿಪ್ಟ್ ಮಾಡಿದ stream ಅನ್ನು ಆಂತರಿಕ
  `http.Server` ಗೆ ಹಸ್ತಾಂತರಿಸುತ್ತದೆ (ಪ್ರಮಾಣಿತ MITM ಅಂತ್ಯಗೊಳಿಸುವ ತಂತ್ರ). ಸ್ಥಗಿತಗೊಂಡ tunnel
  file descriptor ಗಳನ್ನು ಖಾಲಿ ಮಾಡದಂತೆ socket ಜೀವಿತಾವಧಿಗಳನ್ನು `MITM_IDLE_TIMEOUT_MS` ಮೂಲಕ
  ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ.
- **ಕ್ಯಾಪ್ಚರ್** (`handleDecryptedRequest`): `source: "tproxy"` ಜೊತೆಗೆ ಒಂದು `InterceptedRequest`
  ಅನ್ನು ಸೇರಿಸುತ್ತದೆ; ಆರಂಭಿಕ ಸ್ಥಿತಿ `"in-flight"` ಆಗಿರುತ್ತದೆ ಮತ್ತು buffer ಅನ್ನು ಪ್ರವೇಶಿಸುವ ಮೊದಲು
  headers ಅನ್ನು `sanitizeHeaders()` ಹಾಗೂ bodies ಅನ್ನು `maskSecret()` ಮೂಲಕ ಸಂಸ್ಕರಿಸಲಾಗುತ್ತದೆ.
  ನಂತರ entry ಯನ್ನು response, ಗಾತ್ರಗಳು ಮತ್ತು latency ಯೊಂದಿಗೆ ನವೀಕರಿಸಲಾಗುತ್ತದೆ.
- **ಮರು-ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ ಫಾರ್ವರ್ಡ್** (`createForward` / `realForward`): ಮೂಲ ಗಮ್ಯಸ್ಥಾನಕ್ಕೆ
  ಮರು-ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡುತ್ತದೆ. `rejectUnauthorized` ನ ಪೂರ್ವನಿಯೋಜಿತ ಮೌಲ್ಯ **`true`** ಆಗಿದೆ
  (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಸುರಕ್ಷಿತ) — client ವಿನಂತಿಸಿದ SNI/Host ವಿರುದ್ಧ upstream cert ಅನ್ನು
  ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ; ಆದ್ದರಿಂದ ಮೂಲ client ತಿರಸ್ಕರಿಸುತ್ತಿದ್ದುದನ್ನೇ proxy ಸಹ ತಿರಸ್ಕರಿಸುತ್ತದೆ.

### ಆಂಟಿ-ಲೂಪ್ (SO_MARK)

ನಿಯಮಗಳು ಹೊಸ ಸ್ಥಳೀಯ outbound ಸಂಪರ್ಕಗಳನ್ನು ಗುರುತಿಸುವುದರಿಂದ, proxy ಯ **ಸ್ವಂತ**
ಮರು-ಎನ್ಕ್ರಿಪ್ಟ್ ಮಾಡಿದ forward ಸಾಮಾನ್ಯವಾಗಿ ಮತ್ತೆ ಪ್ರತಿಬಂಧಿಸಲ್ಪಡುತ್ತದೆ — ಇದು ಅನಂತ ಲೂಪ್ಗೆ
ಕಾರಣವಾಗುತ್ತದೆ. forward path, bypass socket ಗುರುತು (**SO_MARK**) ಬಳಸಿ ಇದರಿಂದ ರಕ್ಷಿಸಿಕೊಳ್ಳುತ್ತದೆ:

- `realForward`, `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` ಮೂಲಕ ತನ್ನ upstream socket ಅನ್ನು ತೆರೆಯುತ್ತದೆ
  — `DEFAULT_BYPASS_MARK = 0x539` — ಇದು `connect()` ಗಿಂತ **ಮೊದಲು** **SO_MARK** ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ;
  ಆದ್ದರಿಂದ forward ನ SYN bypass ಗುರುತನ್ನು ಹೊತ್ತಿರುತ್ತದೆ.
- `mangle OUTPUT` ನಿಯಮವು ಈಗಾಗಲೇ bypass ಗುರುತನ್ನು ಹೊಂದಿರುವ ಸಂಪರ್ಕಗಳನ್ನು ಹೊರತುಪಡಿಸುತ್ತದೆ
  (`-m mark ! --mark <bypassMark>`); ಆದ್ದರಿಂದ proxy ಯ forward ಅನ್ನು ಮರು-ಗುರುತಿಸಲಾಗುವುದಿಲ್ಲ
  ಮತ್ತು ಅದು TPROXY ಗೆ ಮರು-ಪ್ರವೇಶಿಸುವುದಿಲ್ಲ.

> ಅನುಷ್ಠಾನ ಸೂಚನೆ: bypass ಗುರುತು ಹಾಕಿದ socket ಅನ್ನು agent ನ
> `createConnection` ನಲ್ಲಿ ಸ್ಥಾಪಿಸಬೇಕು (`https.request({ createConnection })` ಅನ್ನು agent
> ಇದ್ದಾಗ ಯಾವುದೇ ಸೂಚನೆ ಇಲ್ಲದೆ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ); ಇಲ್ಲವಾದರೆ forward ಗುರುತು ಹಾಕದ socket ಅನ್ನು
> ತೆರೆಯುತ್ತದೆ ಮತ್ತು ಲೂಪ್ ಮರಳುತ್ತದೆ. ಇದು e2e ಮೂಲಕ ದೃಢೀಕರಿಸಲಾದ ಆಂಟಿ-ಲೂಪ್ ಪರಿಹಾರವಾಗಿದೆ.

## §7 ಟ್ರಾನ್ಸಾಕ್ಷನಲ್ ಫೈರ್ವಾಲ್ ಅನ್ವಯ / ಹಿಂತೆಗೆತ

ಕ್ರ್ಯಾಶ್ ಸಂಭವಿಸಿದಾಗ ಯಾವುದೇ `mangle` ನಿಯಮ ಅಥವಾ ಹಳತಾದ ರೂಟ್ ಉಳಿಯಬಾರದು. ಕಮಾಂಡ್ ಬಿಲ್ಡರ್
(`src/mitm/tproxy/commands.ts`) ಮತ್ತು ರನ್ನರ್ (`src/mitm/tproxy/setup.ts`)
**ಹಿಂತೆಗೆತವು ಅನ್ವಯಿಸುವಿಕೆಯ ನಿಖರವಾದ ವಿಲೋಮವಾಗಿದ್ದು, ಹಿಮ್ಮುಖ ಕ್ರಮದಲ್ಲಿರುತ್ತದೆ** ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸುತ್ತವೆ.

`applyTproxy(cfg)` ಅನ್ವಯಿಸುವ ಕಮಾಂಡ್ಗಳನ್ನು ಕ್ರಮವಾಗಿ ಚಲಾಯಿಸುತ್ತದೆ; **ಯಾವುದೇ** ವೈಫಲ್ಯವಾದರೆ,
ಅದು ಸಾಧ್ಯವಾದಷ್ಟು ಉತ್ತಮ ರೀತಿಯಲ್ಲಿ ಸಂಪೂರ್ಣ `revertTproxy(cfg)` ಅನ್ನು ಚಲಾಯಿಸಿ ದೋಷವನ್ನು ಮರು-ಎಸೆಯುತ್ತದೆ — ಹೀಗಾಗಿ
ಫೈರ್ವಾಲ್ ಸಂಪೂರ್ಣವಾಗಿ ಅನ್ವಯಿಸಲ್ಪಟ್ಟಿರುತ್ತದೆ ಅಥವಾ ಸಂಪೂರ್ಣವಾಗಿ ಹಿಂತೆಗೆದುಕೊಳ್ಳಲ್ಪಟ್ಟಿರುತ್ತದೆ,
ಎಂದಿಗೂ ಅರ್ಧ-ಅನ್ವಯಿತವಾಗಿರುವುದಿಲ್ಲ. `revertTproxy(cfg)` ವಿಲೋಮ ಕಮಾಂಡ್ಗಳನ್ನು ಹಿಮ್ಮುಖ ಕ್ರಮದಲ್ಲಿ
ಚಲಾಯಿಸಿ ವೈಫಲ್ಯಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸುತ್ತದೆ (ಐಡೆಂಪೊಟೆಂಟ್ — ಯಾವುದೇ ಷರತ್ತಿಲ್ಲದೆ ಕರೆಮಾಡಲು ಸುರಕ್ಷಿತ,
ಉದಾ. AgentBridge `repairMitm()` ಕ್ಲೀನಪ್ನಿಂದ).

ಯಾವುದೇ ಕಮಾಂಡ್ಗೆ ಮೊದಲು `validateTproxyConfig(cfg)` ಚಲಿಸುತ್ತದೆ: ಪೋರ್ಟ್ಗಳು `1–65535`
ಆಗಿರಬೇಕು, `mark`/`routeTable`/`bypassMark` ಧನಾತ್ಮಕ ಪೂರ್ಣಾಂಕಗಳಾಗಿರಬೇಕು ಮತ್ತು
`bypassMark`, `mark` ಗಿಂತ ಭಿನ್ನವಾಗಿರಬೇಕು (ಆಂಟಿ-ಲೂಪ್).

### ಅನ್ವಯಿಸುವ ಕಮಾಂಡ್ಗಳು (ಕ್ರಮವಾಗಿ)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

ಹಿಂತೆಗೆತವು ಅವುಗಳನ್ನು ಹಿಮ್ಮುಖ ಕ್ರಮದಲ್ಲಿ ಅಳಿಸುತ್ತದೆ: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> ಈ ವಿಧಾನವು **OUTPUT-ಆಧಾರಿತವಾಗಿದೆ**, ಏಕೆಂದರೆ MITM ಬಳಕೆಯ ಸಂದರ್ಭವು _ಸ್ಥಳೀಯ_ ಹೊರಹೋಗುವ
> ಟ್ರಾಫಿಕ್ಗೆ (ಅದೇ ಹೋಸ್ಟ್ನಲ್ಲಿರುವ ಆ್ಯಪ್ಗಳು) ಸಂಬಂಧಿಸಿದೆ; `PREROUTING` ನಲ್ಲಿ TPROXY ಮಾತ್ರ
> ಅದನ್ನು ನೋಡುವುದಿಲ್ಲ — `PREROUTING` ಫಾರ್ವರ್ಡ್ ಮಾಡಲಾದ ಟ್ರಾಫಿಕ್ ಅನ್ನು ಮಾತ್ರ ನೋಡುತ್ತದೆ. `OUTPUT`
> ಚೈನ್ ಹೊಸ ಸ್ಥಳೀಯ ಸಂಪರ್ಕಗಳನ್ನು ಗುರುತಿಸುತ್ತದೆ, `ip rule` ಅವುಗಳನ್ನು ಸ್ಥಳೀಯ ವಿತರಣೆಗೆ (`lo`)
> ಮರುರೂಟ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ನಂತರ `PREROUTING` ಅವುಗಳನ್ನು ಪಾರದರ್ಶಕ ಲಿಸನರ್ಗೆ ನಿಯೋಜಿಸುತ್ತದೆ.

| ---------------- | ------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | ಪಾರದರ್ಶಕವಾಗಿ ಪ್ರತಿಬಂಧಿಸಬೇಕಾದ ಗಮ್ಯಸ್ಥಾನ TCP ಪೋರ್ಟ್                                                                                   |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT` ನಲ್ಲಿ ಹೊಂದಿಸಲಾದ ಫೈರ್ವಾಲ್ ಗುರುತು; ಇದನ್ನು `ip rule` + `PREROUTING` ಹೊಂದಾಣಿಕೆ ಮಾಡುತ್ತವೆ                                       |
| **onPort**       | int (1–65535)      | `8443`   | ಪಾರದರ್ಶಕ (**IP_TRANSPARENT**) ಲಿಸನರ್ ಬೈಂಡ್ ಆಗುವ ಪೋರ್ಟ್                                                                              |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` ರೂಟ್ ಅನ್ನು ಹೊಂದಿರುವ ಪಾಲಿಸಿ-ರೂಟಿಂಗ್ ಟೇಬಲ್ ಐಡಿ                                                                      |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | ಪ್ರಾಕ್ಸಿಯು ತನ್ನದೇ ಅಪ್ಸ್ಟ್ರೀಮ್ ಸಂಪರ್ಕಗಳ ಮೇಲೆ ಹೊಂದಿಸುವ ಬೈಪಾಸ್ ಸಾಕೆಟ್ ಗುರುತು (**SO_MARK**); `OUTPUT` ನಲ್ಲಿ ಹೊರತುಪಡಿಸಲಾಗಿದೆ (ಆಂಟಿ-ಲೂಪ್) |
| **sudoPassword** | string             | —        | ರೂಟ್ ಅಲ್ಲದ ಡೆಸ್ಕ್ಟಾಪ್ಗಳಿಗೆ ಮಾತ್ರ: ಟ್ರಸ್ಟ್-ಸ್ಟೋರ್ ಸ್ಥಾಪನೆಗೆ ಅನುಮತಿ ನೀಡುತ್ತದೆ; ರೂಟ್ ಆಗಿರುವಾಗ ನಿರ್ಲಕ್ಷಿಸಲಾಗುತ್ತದೆ                      |

TPROXY ಗಾಗಿ **ಯಾವುದೇ ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ಗಳಿಲ್ಲ** — ಎಲ್ಲಾ ಕಾನ್ಫಿಗರೇಶನ್ಗಳು
POST ಬಾಡಿ ಅಥವಾ ಮೇಲಿನ ಡೀಫಾಲ್ಟ್ಗಳ ಮೂಲಕವೇ ಒದಗಿಸಲಾಗುತ್ತವೆ.

## §9 Traffic Inspector ನಿಂದ ಸಕ್ರಿಯಗೊಳಿಸುವುದು

1. **Traffic Inspector** (`/dashboard/tools/traffic-inspector`) ತೆರೆಯಿರಿ.
2. ಕ್ಯಾಪ್ಚರ್-ಮೋಡ್ಗಳ ಪರಿಕರಪಟ್ಟಿಯಲ್ಲಿ **"TPROXY Decrypt"** ⚠ ಬಟನ್ ಅನ್ನು ಹುಡುಕಿ
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - "TPROXY decrypt requires Linux + root + the native addon" ಎಂಬ ಟೂಲ್ಟಿಪ್ನೊಂದಿಗೆ ಅದು
     **ನಿಷ್ಕ್ರಿಯಗೊಂಡಿದ್ದರೆ**, ಈ ಹೋಸ್ಟ್ನಲ್ಲಿ ನೇಟಿವ್ ಆಡ್ಆನ್ ಲಭ್ಯವಿಲ್ಲ (Linux ಅಲ್ಲದಿರುವುದು,
     ಟೂಲ್ಚೈನ್ ಇಲ್ಲದಿರುವುದು, ಅಥವಾ ಆಡ್ಆನ್ ಬಿಲ್ಡ್ ಆಗಿಲ್ಲ). [§2](#2-requirements) ಮತ್ತು [§3](#3-the-native-ip_transparent-addon) ನೋಡಿ.
3. ಬಟನ್ ಕ್ಲಿಕ್ ಮಾಡಿ. ಅದು `startTproxyCaptureMode()`
   (`src/lib/inspector/tproxyCaptureApi.ts`) ಮೂಲಕ `POST /api/tools/agent-bridge/tproxy`
   ಅನ್ನು ಕರೆ ಮಾಡುತ್ತದೆ, ಇದು: ಡೈನಾಮಿಕ್ CA ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ, ಟ್ರಾನ್ಸ್ಪರೆಂಟ್ ಲಿಸನರ್ ಅನ್ನು ತೆರೆಯುತ್ತದೆ,
   ಫೈರ್ವಾಲ್ ನಿಯಮಗಳನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ ಮತ್ತು OS ಟ್ರಸ್ಟ್ ಸ್ಟೋರ್ನಲ್ಲಿ CA ಅನ್ನು ಸ್ಥಾಪಿಸುತ್ತದೆ.
4. ಚಾಲನೆಯಲ್ಲಿರುವಾಗ, ಟಾಗಲ್ ಆಂಬರ್ ಬಣ್ಣಕ್ಕೆ ತಿರುಗುತ್ತದೆ ಮತ್ತು ಲೈವ್ ಇಂಟರ್ಸೆಪ್ಟ್ ಎಣಿಕೆಯನ್ನು
   (`· <interceptCount>`) ತೋರಿಸುತ್ತದೆ. ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡಿದ ವಿನಂತಿಗಳು ವಿನಂತಿ ಪಟ್ಟಿಯಲ್ಲಿ
   `source: "tproxy"` ಜೊತೆಗೆ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ.
5. ನಿಲ್ಲಿಸಲು ಮತ್ತೊಮ್ಮೆ ಕ್ಲಿಕ್ ಮಾಡಿ — `stopTproxyCaptureMode()` ಮೂಲಕ
   `DELETE /api/tools/agent-bridge/tproxy` ಲಿಸನರ್ ಅನ್ನು ಮುಚ್ಚುತ್ತದೆ, CA ಅನ್ನು ಅನ್ಇನ್ಸ್ಟಾಲ್
   ಮಾಡುತ್ತದೆ ಮತ್ತು ಫೈರ್ವಾಲ್ ನಿಯಮಗಳನ್ನು ಹಿಂದಕ್ಕೆ ತರುತ್ತದೆ.

ಕ್ಯಾಪ್ಚರ್-ಮೋಡ್ ಸ್ಥಿತಿ (ಚಾಲನೆಯಲ್ಲಿದೆಯೇ / ಲಭ್ಯವಿದೆಯೇ / ಇಂಟರ್ಸೆಪ್ಟ್ ಎಣಿಕೆ / ಲಿಸನರ್ ಪೋರ್ಟ್)
`GET /api/tools/agent-bridge/tproxy` ನಿಂದ ಬರುತ್ತದೆ
(`src/mitm/tproxy/captureManager.ts` ನಲ್ಲಿನ `getCaptureStatus()`). ಒಂದು ಸಮಯದಲ್ಲಿ
**ಒಂದು** TPROXY ಸೆಷನ್ ಮಾತ್ರ ಚಾಲನೆಯಲ್ಲಿರುತ್ತದೆ — ಎರಡನೆಯದನ್ನು ಪ್ರಾರಂಭಿಸಿದರೆ
"TPROXY capture mode is already running" ಎಂಬ ಸಂದೇಶದೊಂದಿಗೆ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

## §10 ದೋಷನಿವಾರಣೆ

### ಟಾಗಲ್ ನಿಷ್ಕ್ರಿಯಗೊಂಡಿದೆ

ನೇಟಿವ್ ಆಡ್ಆನ್ ಅನ್ನು ಲೋಡ್ ಮಾಡಲು ಸಾಧ್ಯವಾಗುತ್ತಿಲ್ಲ. ಇವುಗಳನ್ನು ದೃಢೀಕರಿಸಿ: ನೀವು Linux ನಲ್ಲಿದ್ದೀರಿ,
ಆಡ್ಆನ್ ಅನ್ನು ಬಿಲ್ಡ್ ಮಾಡಿದ್ದೀರಿ (`npm run build:native:tproxy`) ಮತ್ತು ಪ್ರಕ್ರಿಯೆಯು
`transparent.node` ಅನ್ನು ಲೋಡ್ ಮಾಡಬಲ್ಲದು. `isTransparentSocketAvailable()` ಟಾಗಲ್ನ
ಲಭ್ಯತೆಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ; ಆಡ್ಆನ್ ಇಲ್ಲದಿದ್ದಾಗ `GET /api/tools/agent-bridge/tproxy`
`available: false` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

### ಯಾವುದೂ ಕ್ಯಾಪ್ಚರ್ ಆಗುತ್ತಿಲ್ಲ

- ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡಲಾದ ಪ್ರಕ್ರಿಯೆಯು ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ `dport` ಗೆ (ಡೀಫಾಲ್ಟ್ `443`)
  ನಿಜವಾಗಿಯೂ ಸಂಪರ್ಕಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ.
- ಪ್ರಕ್ರಿಯೆಯು ಡೈನಾಮಿಕ್ CA ಅನ್ನು ನಂಬುತ್ತದೆ ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ. CA ಅನ್ನು
  `omniroute-tproxy-ca.crt` ಅಡಿಯಲ್ಲಿ ಸ್ಥಾಪಿಸಲಾಗುತ್ತದೆ; ತಮ್ಮದೇ ಟ್ರಸ್ಟ್ ಸ್ಟೋರ್ ಹೊಂದಿರುವ
  ಅಪ್ಲಿಕೇಶನ್ಗಳಿಗೆ (Firefox/Chrome NSS) ಪ್ರಮಾಣಪತ್ರವನ್ನು ಅಲ್ಲಿಯೂ ಸೇರಿಸಬೇಕಾಗಬಹುದು.
- ಪ್ರಮಾಣಪತ್ರ-ವಿಶ್ವಾಸಾರ್ಹತೆ / ಸರ್ವರ್ ಆರೋಗ್ಯ ತಪಾಸಣೆಗಳಿಗಾಗಿ AgentBridge **Diagnose**
  ಸ್ವಯಂ-ಪರೀಕ್ಷೆಯನ್ನು ಚಲಾಯಿಸಿ ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) ನೋಡಿ).

### ಕ್ರ್ಯಾಶ್ ನಂತರ ಉಳಿದಿರುವ ಹಳೆಯ ಫೈರ್ವಾಲ್ ನಿಯಮಗಳು

`revertTproxy()` ಎಂಬುದು apply ಕಾರ್ಯಾಚರಣೆಯ ನಿಖರವಾದ ವಿಲೋಮವಾಗಿದೆ ಮತ್ತು ಐಡೆಂಪೊಟೆಂಟ್ ಆಗಿದೆ.
ಮೋಡ್ ಅನ್ನು ನಿಲ್ಲಿಸುವುದರಿಂದ ನಿಯಮಗಳು ಹಿಂದಕ್ಕೆ ತರಲ್ಪಡುತ್ತವೆ; ಸೆಷನ್ನ ಮಧ್ಯದಲ್ಲಿ OmniRoute
ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಿದ್ದರೆ, ಅನಾಥವಾಗಿರುವ ಸಿಸ್ಟಮ್ ಸ್ಥಿತಿಯನ್ನು (DNS ಸ್ಪೂಫ್, ರೂಟ್ CA, ಸಿಸ್ಟಮ್ ಪ್ರಾಕ್ಸಿ)
ರದ್ದುಮಾಡಲು AgentBridge **Repair** ಕ್ರಿಯೆಯನ್ನು (`POST /api/tools/agent-bridge/repair`)
ಬಳಸಿ. TPROXY `mangle` ನಿಯಮಗಳು ಮತ್ತು ರೂಟ್ ಸಹ ರೀಬೂಟ್ ಆದಾಗ ಸ್ವಯಂಚಾಲಿತವಾಗಿ
ಫ್ಲಷ್ ಆಗುತ್ತವೆ.

### ಅನಂತ ಲೂಪ್ / ಪ್ರಾಕ್ಸಿಯು ತನ್ನದೇ ಫಾರ್ವರ್ಡ್ ಅನ್ನು ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡುತ್ತದೆ

ಇದು ಆಂಟಿ-ಲೂಪ್ ಸಂದರ್ಭವಾಗಿದೆ. `bypassMark`, `mark` ಗಿಂತ ಭಿನ್ನವಾಗಿದೆ ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ
(ಮೌಲ್ಯೀಕರಣವು ಇದನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ) ಮತ್ತು ಫಾರ್ವರ್ಡ್ `connectMarked` ಅನ್ನು ಬಳಸುತ್ತದೆ
ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ (`realForward` ನಲ್ಲಿ ಅದು ಹಾಗೆಯೇ ಮಾಡುತ್ತದೆ).
[§5 ಆಂಟಿ-ಲೂಪ್](#anti-loop-so_mark) ನೋಡಿ.
