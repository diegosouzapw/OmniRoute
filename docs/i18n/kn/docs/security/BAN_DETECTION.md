OmniRoute, ಪೂರೈಕೆದಾರರ **ಖಾತೆಯು ಶಾಶ್ವತವಾಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ** (ಅಮಾನತುಗೊಳಿಸಲಾಗಿದೆ / ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ / ToS-ನಿಷೇಧಿಸಲಾಗಿದೆ) ಎಂಬುದನ್ನು ಸೂಚಿಸುವ ಸಂಕೇತಗಳಿಗಾಗಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ ಮತ್ತು ಹೊಂದಾಣಿಕೆ ಕಂಡುಬಂದಾಗ, ಆ ಸಂಪರ್ಕವನ್ನು **ಟರ್ಮಿನಲ್ `banned` ಸ್ಥಿತಿಗೆ** ವರ್ಗಾಯಿಸುತ್ತದೆ; ಹೀಗಾಗಿ ವಿನಂತಿಗಳಿಗಾಗಿ ಅದನ್ನು ಇನ್ನು ಮುಂದೆ ಆಯ್ಕೆ ಮಾಡಲಾಗುವುದಿಲ್ಲ. **Security → Banned Keywords** ಸೆಟ್ಟಿಂಗ್ಗಳ ಕಾರ್ಡ್ ಇದನ್ನೇ ಕಾನ್ಫಿಗರ್ ಮಾಡುತ್ತದೆ ("ಶಾಶ್ವತ ಖಾತೆ ನಿಷೇಧ ಪತ್ತೆಯನ್ನು ಪ್ರಚೋದಿಸುವ ಹೆಚ್ಚುವರಿ ಕೀವರ್ಡ್ಗಳು. ಅಂತರ್ನಿರ್ಮಿತ ಕೀವರ್ಡ್ಗಳು ಯಾವಾಗಲೂ ಅನ್ವಯಿಸುತ್ತವೆ.").

ಈ ಪುಟವು ಅಂತರ್ನಿರ್ಮಿತ ಪಟ್ಟಿಯನ್ನು, ಪತ್ತೆ ಪ್ರಕ್ರಿಯೆಯನ್ನು, ಅದರ ವ್ಯಾಪ್ತಿಯನ್ನು, ಕಸ್ಟಮ್ ಕೀವರ್ಡ್ಗಳನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ಸೇರಿಸುವ ವಿಧಾನವನ್ನು ಮತ್ತು ಗುರುತಿಸಲಾದ ಸಂಪರ್ಕವನ್ನು ಮರುಸ್ಥಾಪಿಸುವ ವಿಧಾನವನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಯು ಸ್ವತಃ ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವದ ಮಾದರಿಯ ಭಾಗವಾಗಿದೆ — ನೋಡಿ
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ("ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳು").

**ಅಧಿಕೃತ ಮೂಲ:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`).

## ಅಂತರ್ನಿರ್ಮಿತ ಕೀವರ್ಡ್ಗಳು

ಯಾವುದೇ ಕಸ್ಟಮ್ ಪಟ್ಟಿಯನ್ನು ಲೆಕ್ಕಿಸದೆ, ಈ 8 ಉಪಸ್ಟ್ರಿಂಗ್ಗಳು ಯಾವಾಗಲೂ ಅನ್ವಯಿಸುತ್ತವೆ (ಅಕ್ಷರಗಳ ಗಾತ್ರವನ್ನು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ):

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
verify your account to continue                                 (Antigravity / Google Cloud Code)
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> ಪೂರೈಕೆದಾರರು ತಮ್ಮ ನಿಷೇಧದ ಪದಪ್ರಯೋಗವನ್ನು ಬದಲಾಯಿಸಿದಂತೆ ಈ ಪಟ್ಟಿಯೂ ವಿಕಸಿಸುತ್ತದೆ. ಅಧಿಕೃತ
> ಪ್ರತಿಯು `open-sse/services/accountFallback.ts` ನಲ್ಲಿರುವ `ACCOUNT_DEACTIVATED_SIGNALS`;
> ಮೇಲಿನ ಬ್ಲಾಕ್ ಅನ್ನು ಒಂದು ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಎಂದು ಪರಿಗಣಿಸಿ.

ಅದೇ ಫೈಲ್ನಲ್ಲಿ ಹೊಂದಿಕೊಂಡಿರುವ ಎರಡು **ಪ್ರತ್ಯೇಕ** ಸಂಕೇತ ಕೋಷ್ಟಕಗಳಿವೆ ಮತ್ತು ಅವು ನಿಷೇಧಿತ-ಕೀವರ್ಡ್ ಪತ್ತೆಯ ಭಾಗವಲ್ಲ:

- `CREDITS_EXHAUSTED_SIGNALS` — ಬಿಲ್ಲಿಂಗ್/ಕೋಟಾ ಖಾಲಿಯಾಗಿದೆ (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → ಟರ್ಮಿನಲ್ `credits_exhausted`.
- `OAUTH_INVALID_TOKEN_SIGNALS` — **ಟರ್ಮಿನಲ್ ಅಲ್ಲ**; ಟೋಕನ್ ರಿಫ್ರೆಶ್ ಮೂಲಕ ಮರುಸ್ಥಾಪಿಸಬಹುದು.

ಗಮನಿಸಿ: **`rate limit`** / `429` ನಂತಹ ಸಾಮಾನ್ಯ ತಾತ್ಕಾಲಿಕ ಪದಗುಚ್ಛಗಳನ್ನು ದರ-ಮಿತಿ / ಸಂಪರ್ಕ-ಕೂಲ್ಡೌನ್ ಮಾರ್ಗವು ನಿರ್ವಹಿಸುತ್ತದೆ ಮತ್ತು ಅವು ನಿಷೇಧ ಸಂಕೇತಗಳಲ್ಲ.

## ಪತ್ತೆ ಪ್ರಕ್ರಿಯೆ

```
ಅಪ್ಸ್ಟ್ರೀಮ್ ದೋಷ ಪ್ರತಿಕ್ರಿಯೆ
  → ಬಾಡಿಯನ್ನು ಸ್ಟ್ರಿಂಗ್ ಆಗಿ ಪರಿವರ್ತಿಸಿ + ಸಣ್ಣ ಅಕ್ಷರಗಳಿಗೆ ಬದಲಾಯಿಸಲಾಗುತ್ತದೆ
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [ಉಪಸ್ಟ್ರಿಂಗ್ ಹೊಂದಾಣಿಕೆ]
  → ಹೊಂದಾಣಿಕೆಯೇ?
      → ಸಂಪರ್ಕದ testStatus = "banned"      (ಶಾಶ್ವತ — 1-ವರ್ಷದ ಕೂಲ್ಡೌನ್, ಎಂದಿಗೂ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮರುಸ್ಥಾಪನೆಯಾಗುವುದಿಲ್ಲ)
      → `autoDisableBannedAccounts` ಸೆಟ್ಟಿಂಗ್ ಸಕ್ರಿಯವಾಗಿದ್ದರೆ ಮತ್ತು `autoDisableBannedScope`
        ಈ ಸಂಪರ್ಕವನ್ನು ಒಳಗೊಂಡಿದ್ದರೆ (`all`, ಅಥವಾ OAuth/cookie/session ಗಾಗಿ `subscription`)
        → isActive = false ಕೂಡ ಆಗುತ್ತದೆ. ವ್ಯಾಪ್ತಿಯು `subscription`
        ಆಗಿರುವಾಗ ಪ್ರಿಪೇಯ್ಡ್ API ಕೀಗಳು ಸಕ್ರಿಯವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.
      → ಖಾತೆ ಆಯ್ಕೆಯ ಸಮಯದಲ್ಲಿ ಸಂಪರ್ಕವನ್ನು ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ (ಸಂಯೋಜಿತ QUOTA_BLOCKING ಸ್ಥಿತಿಗಳು)
```

- ಹೊಂದಾಣಿಕೆಯು ಪ್ರತಿಕ್ರಿಯೆಯ **ಬಾಡಿ** ಮೇಲಿನ **ಅಕ್ಷರ ಗಾತ್ರವನ್ನು ಪರಿಗಣಿಸದ ಉಪಸ್ಟ್ರಿಂಗ್** ಹುಡುಕಾಟವಾಗಿದೆ
  (`isAccountDeactivated`, `accountFallback.ts`).
- ನಿಷೇಧ-ಸಂಕೇತದ ಬಾಡಿ ಕಂಡುಬಂದಾಗ ಶಾಶ್ವತ `banned` ಟರ್ಮಿನಲ್ಗೊಳಿಸುವಿಕೆಯು **ಯಾವುದೇ
  HTTP ಸ್ಥಿತಿಯಲ್ಲೂ** ಸಂಭವಿಸುತ್ತದೆ (`markAccountUnavailable` → `checkFallbackError` ಮೂಲಕ). ಸಂಪರ್ಕದಲ್ಲಿ
  ಹೆಚ್ಚುವರಿ API ಕೀಗಳಿಲ್ಲದಾಗ ಬರೆಯಲಾಗುವ, ಹೆಚ್ಚು ಸೀಮಿತವಾದ **`deactivated`** ಲೇಬಲ್
  (`isActive=false`) ಅನ್ನು ಇನ್ಲೈನ್ `chatCore.ts` ಮಾರ್ಗವು **HTTP 401 / 403** ನಲ್ಲಿ
  ಬರೆಯುತ್ತದೆ (`classifyProviderError` → `ACCOUNT_DEACTIVATED` ಮೂಲಕ ವರ್ಗೀಕರಿಸಲಾಗಿದೆ). ಅದೇ
  `ACCOUNT_DEACTIVATED` ಸಂಕೇತಕ್ಕಾಗಿ `markAccountUnavailable()` ಮಾರ್ಗವು
  (`resolveTerminalConnectionStatus` ಮೂಲಕ) _ಬೇರೆಯಾದ_ ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಯಾದ —
  **`expired`** — ಅನ್ನು ಬರೆಯುತ್ತದೆ ಎಂಬುದನ್ನು ಗಮನಿಸಿ; ಆದ್ದರಿಂದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಯಾವ
  ಮಾರ್ಗ ನಿರ್ವಹಿಸಿದೆ ಎಂಬುದನ್ನು ಅವಲಂಬಿಸಿ ಅದೇ ನಿಷೇಧವು `deactivated` ಅಥವಾ `expired`
  ಎರಡರಲ್ಲಿ ಯಾವುದಾದರೂ ಒಂದಾಗಿ ಕಾಣಿಸಿಕೊಳ್ಳಬಹುದು. (ಹಳೆಯ ಕೋಡ್ ಕಾಮೆಂಟ್ನಲ್ಲಿ "401 ಬಾಡಿಯು ಈ ಸ್ಟ್ರಿಂಗ್ಗಳನ್ನು ಹೊಂದಿರುವಾಗ" ಎಂದು ಹೇಳಲಾಗಿದೆ — ಅದು ಪ್ರಸ್ತುತ ನಡವಳಿಕೆಯನ್ನು ಪೂರ್ಣವಾಗಿ ವಿವರಿಸುವುದಿಲ್ಲ.)
- ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಗಳನ್ನು ಫಿಲ್ಟರ್ ಮಾಡುವ ಎಲ್ಲೆಡೆ `banned` ಸಂಪರ್ಕವನ್ನು ಆಯ್ಕೆಯಿಂದ ಹೊರಗಿಡಲಾಗುತ್ತದೆ
  (`isTerminalConnectionStatus`, ಸಂಯೋಜಿತ `QUOTA_BLOCKING_CONNECTION_STATUSES`).

## ವ್ಯಾಪ್ತಿ — ಯಾವ ಪೂರೈಕೆದಾರರನ್ನು ಸ್ಕ್ಯಾನ್ ಮಾಡಲಾಗುತ್ತದೆ

**ಎಲ್ಲಾ ಪೂರೈಕೆದಾರರು.** ವಿಫಲವಾದ ಪ್ರತಿಯೊಂದು ಅಪ್ಸ್ಟ್ರೀಮ್ ವಿನಂತಿಯೂ ಹಾದುಹೋಗುವ ಸಾಮಾನ್ಯ ದೋಷ-ನಿರ್ವಹಣಾ ಪೈಪ್ಲೈನ್ನಲ್ಲಿ ಈ ಪರಿಶೀಲನೆ ನಡೆಯುತ್ತದೆ — ಇದು OAuth/ಚಂದಾದಾರಿಕೆ ಸ್ಕ್ರೇಪರ್ಗಳಿಗೆ **ಮಾತ್ರ** ಸೀಮಿತವಾಗಿಲ್ಲ. ಫಲಿತಾಂಶವಾಗಿ ಬರುವ ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿಯು ಪ್ರತಿ **connection**ಗೆ ಅನ್ವಯಿಸುತ್ತದೆ, ಪ್ರತಿ ಪೂರೈಕೆದಾರರಿಗೆ ಅಲ್ಲ.

ಆದಾಗ್ಯೂ, ಅಂತರ್ನಿರ್ಮಿತ _strings_ ನೈಜ ನಿಷೇಧದ ಅಪಾಯವಿರುವ ಚಂದಾದಾರಿಕೆ/OAuth ಪೂರೈಕೆದಾರರತ್ತ (ChatGPT Web Codex, Claude Web, Codex, Muse Spark, Antigravity) ಕೇಂದ್ರೀಕೃತವಾಗಿವೆ. API-key ಪೂರೈಕೆದಾರರ ದೋಷದ ಬಾಡಿಯು ಉಪಸ್ಟ್ರಿಂಗ್ಗಳಲ್ಲಿ ಒಂದನ್ನು ಅಕ್ಷರಶಃ ಒಳಗೊಂಡಿದ್ದರೆ ಮಾತ್ರ ಅದು ಡಿಟೆಕ್ಟರ್ ಅನ್ನು ಪ್ರಚೋದಿಸುತ್ತದೆ.

`autoDisableBannedScope` (`all` | `subscription`, ಡೀಫಾಲ್ಟ್ `all`) ಹೊಂದಾಣಿಕೆ ಕಂಡುಬಂದಾಗ `isActive=false` ಅನ್ನು ಸಹ ಹೊಂದಿಸಬೇಕೇ ಎಂಬುದನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ. `subscription` ಎಂದರೆ ಲಾಗಿನ್-ಶೈಲಿಯ ಸೀಟ್ಗಳು (ವೆಬ್-ಕುಕಿ ಸೆಷನ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಪಾವತಿಸಿದ ಚಂದಾದಾರಿಕೆಗಳು ಮತ್ತು ಉಚಿತ ಖಾತೆಗಳು). ಇದು ಪ್ರಿಪೇಯ್ಡ್ API ಕೀಗಳಿಗೆ `testStatus=banned` ಅನ್ನು ಇನ್ನೂ ದಾಖಲಿಸುತ್ತದೆ, ಆದರೆ ಅವುಗಳನ್ನು ರೂಟಿಂಗ್ ಪೂಲ್ನಲ್ಲಿಯೇ ಉಳಿಸುತ್ತದೆ. ದೀರ್ಘಕಾಲಿಕ ವಿನ್ಯಾಸವು ಪ್ರತಿ-ಪೂರೈಕೆದಾರ ಮತ್ತು ಪ್ರತಿ-ಖಾತೆ ಓವರ್ರೈಡ್ ಆಗಿದೆ; ಜಾಗತಿಕ enum ಮೊದಲ ಅನುಷ್ಠಾನವಾಗಿದೆ.

## ಕಸ್ಟಮ್ ನಿಷೇಧಿತ ಕೀವರ್ಡ್ಗಳು

**Security → Banned Keywords** ನಲ್ಲಿ ಕೀವರ್ಡ್ಗಳನ್ನು ಸೇರಿಸಿ ಅಥವಾ ತೆಗೆದುಹಾಕಿ (`PATCH /api/settings` ಮೂಲಕ ಜಾಗತಿಕ `customBannedSignals` ಸೆಟ್ಟಿಂಗ್ ಆಗಿ ಉಳಿಸಲಾಗುತ್ತದೆ). ಅವುಗಳನ್ನು ಅಂತರ್ನಿರ್ಮಿತ ಪಟ್ಟಿಗೆ **ಸೇರಿಸಲಾಗುತ್ತದೆ** — ಅವು ಎಂದಿಗೂ ಬದಲಿಪಟ್ಟಿಯಲ್ಲ — ಮತ್ತು ಉಳಿಸಿದಾಗ (ಹಾಗೂ ಸ್ಟಾರ್ಟ್ಅಪ್ನಲ್ಲಿ) `setCustomBannedSignals()` ಮೂಲಕ ಹಾಟ್-ರೀಲೋಡ್ ಆಗುತ್ತವೆ. ಪ್ರತಿಯೊಂದು ಕೀವರ್ಡ್ ಅನ್ನು 200 ಅಕ್ಷರಗಳಿಗೆ ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ; ಅರೇ ಉದ್ದಕ್ಕೆ ಯಾವುದೇ ಮಿತಿಯಿಲ್ಲ.

**⚠ ತಪ್ಪಾದ-ಪಾಸಿಟಿವ್ ಅಪಾಯ — ನಿರ್ದಿಷ್ಟ ನುಡಿಗಟ್ಟುಗಳನ್ನು ಆಯ್ಕೆಮಾಡಿ.** ಪತ್ತೆಹಚ್ಚುವಿಕೆಯು ಸಂಪೂರ್ಣ ಪ್ರತಿಕ್ರಿಯೆ ಬಾಡಿಯ ಮೇಲಿನ ಕಚ್ಚಾ ಉಪಸ್ಟ್ರಿಂಗ್ ಹೊಂದಾಣಿಕೆಯಾಗಿದೆ ಮತ್ತು ಒಂದು ಹೊಂದಾಣಿಕೆಯು **ಶಾಶ್ವತ**ವಾಗಿರುತ್ತದೆ (1-ವರ್ಷದ ಕೂಲ್ಡೌನ್, ಹಸ್ತಚಾಲಿತ ಮರುಪಡೆಯುವಿಕೆ). ಅತಿ ಸಾಮಾನ್ಯವಾದ ಕೀವರ್ಡ್ ಸಂಪೂರ್ಣವಾಗಿ ಸುಸ್ಥಿತಿಯಲ್ಲಿರುವ ಸಂಪರ್ಕವನ್ನು ನಿಷೇಧಿಸಬಹುದು:

- **ಕೆಟ್ಟದು:** `quota`, `limit`, `error`, `denied` — ಅನೇಕ ತಾತ್ಕಾಲಿಕ ದೋಷಗಳಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ.
- **ಒಳ್ಳೆಯದು:** ಸಂಪೂರ್ಣ ನಿಷೇಧ ವಾಕ್ಯಗಳು, ಉದಾ. `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`.

ನೈಜ ನಿಷೇಧದ ವೇಳೆ ಪೂರೈಕೆದಾರರು ಹಿಂದಿರುಗಿಸುವ, ಅಸಂದಿಗ್ಧವಾದ ಅತ್ಯಂತ ಉದ್ದದ ನುಡಿಗಟ್ಟಿಗೆ ಆದ್ಯತೆ ನೀಡಿ. ಅನುಮಾನವಿದ್ದರೆ, ಮೊದಲು ಸಂಪರ್ಕದ `lastError` ಅನ್ನು ಗಮನಿಸಿ, ನಂತರ ನಿಖರವಾದ ಪದವಿನ್ಯಾಸವನ್ನು ಸೇರಿಸಿ.

## ಫ್ಲ್ಯಾಗ್ ಮಾಡಲಾದ ಸಂಪರ್ಕವನ್ನು ಮರುಸ್ಥಾಪಿಸುವುದು

ಟರ್ಮಿನಲ್ `banned` / `deactivated` ಸ್ಥಿತಿಗಳು **ಎಂದಿಗೂ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮರುಸ್ಥಾಪನೆಯಾಗುವುದಿಲ್ಲ** (ಅವುಗಳನ್ನು ಪೂರ್ವಸಕ್ರಿಯ-ಮರುಸ್ಥಾಪನೆ ಟಿಕ್ನಿಂದ ಹೊರಗಿಡಲಾಗಿದೆ — `unavailable` ಕೂಲ್ಡೌನ್ಗಳು ಮಾತ್ರ ಸ್ವತಃ ಮರುಸ್ಥಾಪನೆಯಾಗುತ್ತವೆ). ಆಪರೇಟರ್ ಅವುಗಳನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ತೆರವುಗೊಳಿಸಬೇಕು:

1. **ಸಂಪರ್ಕವನ್ನು ಮರು-ಪರೀಕ್ಷಿಸಿ** — ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ **Test** ಕ್ರಿಯೆ
   (`POST /api/providers/{id}/test`); ಯಶಸ್ವಿ ಪ್ರೋಬ್ `testStatus` ಅನ್ನು
   `active`ಗೆ ಮರುಹೊಂದಿಸಿ ದೋಷ ಕ್ಷೇತ್ರಗಳನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.
2. **ಮರು-ದೃಢೀಕರಿಸಿ / ಕ್ರೆಡೆನ್ಷಿಯಲ್ಗಳನ್ನು ಸಂಪಾದಿಸಿ** — OAuth ಪೂರೈಕೆದಾರರಿಗಾಗಿ, ಲಾಗಿನ್
   / ರಿಫ್ರೆಶ್ ಫ್ಲೋ ಅನ್ನು ಮರುಚಾಲನೆ ಮಾಡಿ; ಪೂರೈಕೆದಾರರ ರಚನೆ/ಆಮದು ರೂಟ್ಗಳು `isActive = true` ಅನ್ನು ಹೊಂದಿಸುತ್ತವೆ.
3. **ಸಂಪರ್ಕವನ್ನು ಮರು-ಸಕ್ರಿಯಗೊಳಿಸಿ** — ಸ್ವಯಂ-ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವಿಕೆಯು `isActive = false`
   ಅನ್ನು ಹೊಂದಿಸಿದ್ದರೆ (`all` ವ್ಯಾಪ್ತಿ, ಅಥವಾ OAuth/ಕುಕಿ/ಸೆಷನ್ ಸಂಪರ್ಕಕ್ಕೆ `subscription`),
   ಖಾತೆಯನ್ನು ಸರಿಪಡಿಸಿದ ನಂತರ ಅದನ್ನು ಮತ್ತೆ ಆನ್ ಮಾಡಿ.

ಪ್ರತ್ಯೇಕ "clear ban flag" ಬಟನ್ ಇಲ್ಲ — ಮರುಸ್ಥಾಪನೆಯು ಮರು-ಪರೀಕ್ಷೆ, ಮರು-ದೃಢೀಕರಣ ಅಥವಾ ಮರು-ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆಯ ಮೂಲಕ ನಡೆಯುತ್ತದೆ; ಇದು
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ನಲ್ಲಿರುವ ಸಾಮಾನ್ಯ ಟರ್ಮಿನಲ್-ಸ್ಥಿತಿ ನಿಯಮಕ್ಕೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ.

## ಪ್ರೋಬ್ ಪ್ರತ್ಯೇಕಣೆ (ಮಾದರಿ test-all)

`runAsProbe` ಒಳಗೆ ಕಾರ್ಯಗತಗೊಳಿಸಲಾದ **ಪ್ರೋಬ್-ಮೂಲದ ವೈಫಲ್ಯ** (ಮಾದರಿ test-all / ಆರೋಗ್ಯ-ಪರಿಶೀಲನಾ ಡಿಸ್ಪ್ಯಾಚ್ಗಳು) ಸಂಪರ್ಕವನ್ನು ಎಂದಿಗೂ ಪೂಲ್ನಿಂದ ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ (#9817): ಅದನ್ನು **ಗೋಚರತೆಗಾಗಿ ದಾಖಲಿಸಲಾಗುತ್ತದೆ** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`), ಆದರೆ **ಪ್ರತಿಯೊಂದು** ರೂಟಿಂಗ್ ಮ್ಯೂಟೇಶನ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ — ಕೂಲ್ಡೌನ್ಗಳು, ಟರ್ಮಿನಲ್ ಸ್ಥಿತಿ (`banned` / `deactivated` / `credits_exhausted`), ಪ್ರತಿ-ಮಾದರಿ ಲಾಕ್ಔಟ್ಗಳು, ಪೂರೈಕೆದಾರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್, 5-ನಿಮಿಷದ ಕೋಟಾ ಕ್ಯಾಶ್, OAuth ಟೋಕನ್ ರಿಫ್ರೆಶ್ ಮತ್ತು ಸ್ವಯಂ-ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವಿಕೆ. ನೈಜ ವಿನಂತಿ-ಪಥದ ವೈಫಲ್ಯ ಮಾತ್ರ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ. ದಾಖಲಿಸಲಾದ ದೋಷವು ಫ್ಲ್ಯಾಗ್ ಮಾಡಲಾದ ಖಾತೆಯು ಟ್ರಾಫಿಕ್ಗೆ ಸೇವೆ ಸಲ್ಲಿಸುತ್ತಲೇ ಇದ್ದರೂ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಗೋಚರಿಸುವಂತೆ ಮಾಡುತ್ತದೆ.

ಏಕೈಕ ನಿರ್ಧಾರ ಬಿಂದು `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`) ಆಗಿದ್ದು, ಪ್ರೋಬ್-ಮೂಲದ ವೈಫಲ್ಯದಿಂದ ರೂಟಿಂಗ್ ಸ್ಥಿತಿಯನ್ನು ಮ್ಯೂಟೇಟ್ ಮಾಡಬಹುದಾದ **ಪ್ರತಿಯೊಂದು** ಸ್ಥಳವೂ ಇದನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ:

- `markAccountUnavailable` (`auth.ts`) — ದಾಖಲೆ-ಮಾತ್ರ (`lastError` ಕಚ್ಚಾ ಪಠ್ಯ,
  `lastErrorType`, `errorCode`, `lastErrorAt`; ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ `backoffLevel` **ಇಲ್ಲ**,
  ಏಕೆಂದರೆ ಅದು ಆಯ್ಕೆ-ಸಮಯದ ಸ್ವಯಂ-ಕ್ಷಯವನ್ನು ಪ್ರಚೋದಿಸಿ ದಾಖಲೆಯನ್ನು ಅಳಿಸುತ್ತದೆ)
- `maybeAutoDisableBannedAccount` — ಸ್ವಯಂ-ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಇಲ್ಲ
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (ದಾಖಲೆ-ಮಾತ್ರ,
  ಟರ್ಮಿನಲ್ `credits_exhausted` ಇಲ್ಲ), GEO_BLOCKED (24h ಹೊರಗಿಡುವಿಕೆ ಇಲ್ಲ),
  MODEL_NOT_FOUND (`lockModel` ಇಲ್ಲ), codex 429 ಖಾತೆ-ರೊಟೇಶನ್ ಫೇಲ್ಓವರ್
  (`markCodexScopeRateLimited` ಇಲ್ಲ, ಉಳಿಸಲಾದ `rate_limited_until` ಇಲ್ಲ,
  ಸೆಷನ್-ಅಫಿನಿಟಿ ತೆರವುಗೊಳಿಸುವಿಕೆ ಇಲ್ಲ), `persistCodexQuotaState` (ಕೋಟಾ-ಸ್ಥಿತಿ ಬರವಣಿಗೆ ಇಲ್ಲ,
  ಕ್ಯಾಶ್ ಅಮಾನ್ಯಗೊಳಿಸುವಿಕೆ ಇಲ್ಲ), `recordKeyHealthStatus` (ಕೀ-ಹೆಲ್ತ್ ರೊಟೇಟರ್
  ಬದಲಾಗದೆ ಉಳಿಯುತ್ತದೆ)
- OAuth ರಿಫ್ರೆಶ್ — ಎಕ್ಸಿಕ್ಯೂಟರ್ ಬೇಸ್ನ ಪೂರ್ವಸಕ್ರಿಯ ರಿಫ್ರೆಶ್
  (`base.ts` `execute()`, ರಿಫ್ರೆಶ್-ಟೋಕನ್ ರೊಟೇಶನ್ ಬಳಸಲಾಗುವುದಿಲ್ಲ) ಮತ್ತು
  `chatCore` ನಲ್ಲಿನ ಪ್ರತಿಕ್ರಿಯಾತ್ಮಕ 401/403 ಪಥ (ಯಾವುದೇ `expired` ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವಿಕೆ ಇಲ್ಲ)
- `chat.ts` — ಪೂರೈಕೆದಾರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಮತ್ತು 5-ನಿಮಿಷದ ಕೋಟಾ ಕ್ಯಾಶ್
  (`markAccountExhaustedFrom429`) ಎಂದಿಗೂ ಕುಗ್ಗುವುದಿಲ್ಲ

ದಾಖಲಿಸಲಾದ ದೋಷವು ಫ್ಲ್ಯಾಗ್ ಮಾಡಲಾದ ಖಾತೆಯು ಟ್ರಾಫಿಕ್ಗೆ ಸೇವೆ ಸಲ್ಲಿಸುತ್ತಲೇ ಇದ್ದರೂ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಗೋಚರಿಸುವಂತೆ ಮಾಡುತ್ತದೆ. ಗಮನಿಸಿ: ನೈಜ ಪಥದ `slice(0,100)` ಮೊಟಕುಗೊಳಿಸುವಿಕೆಗೆ ಭಿನ್ನವಾಗಿ, ಪ್ರೋಬ್ ದಾಖಲೆಯು **ಕಚ್ಚಾ**
(ತುಂಡರಿಸದ) ದೋಷ ಪಠ್ಯವನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ.

test-all ಅನ್ನು ನಿರ್ವಹಣಾ ಸಾಧನವಾಗಿ ಬಳಸುವ ಆಪರೇಟರ್ಗಳು ಈ ಕೆಳಗಿನ ಯಾವುದಾದರೂ ಒಂದರ ಮೂಲಕ ಐತಿಹಾಸಿಕ ನಡವಳಿಕೆಯನ್ನು (ಪ್ರೋಬ್ ಅನ್ನು ನೈಜ ಜನರೇಷನ್ ಎಂದು ಪರಿಗಣಿಸುವುದು) ಮರುಸ್ಥಾಪಿಸಬಹುದು:

- `probeCanDisable` ಸೆಟ್ಟಿಂಗ್ (`{"probeCanDisable": true}` ಜೊತೆಗೆ
  `POST /api/settings`, ಅಥವಾ ನೇರ `key_value` DB ಸಂಪಾದನೆ), ಅಥವಾ
- ವೈಶಿಷ್ಟ್ಯ ಫ್ಲ್ಯಾಗ್ **`PROBE_CAN_DISABLE=true`** (env ಅಥವಾ DB ಓವರ್ರೈಡ್; ಸೆಟ್ಟಿಂಗ್ಗಿಂತ ಆದ್ಯತೆ ಪಡೆಯುತ್ತದೆ).

ವೈಫಲ್ಯ-ಸುರಕ್ಷತೆ: ಫ್ಲ್ಯಾಗ್ ಅಥವಾ ಸೆಟ್ಟಿಂಗ್ಗಳ ಲುಕ್ಅಪ್ ದೋಷವನ್ನು ಎಸೆದರೆ, ಪ್ರತ್ಯೇಕಣೆ ಆನ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ.
