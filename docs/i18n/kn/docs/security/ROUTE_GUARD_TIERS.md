## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಹಂತಗಳು

### ಹಂತ 1 — LOCAL_ONLY

**ಜಾರಿಗೊಳಿಸುವುದು:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆ
**ಬೈಪಾಸ್:** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ವ್ಯಾಪ್ತಿಯನ್ನು ಹೊಂದಿರುವ ಮಾನ್ಯ
API ಕೀಲಿಯನ್ನು ಒಳಗೊಂಡಿದ್ದಾಗ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿನ ಮಾರ್ಗಗಳಿಗೆ
ಮಾತ್ರ ಸೀಮಿತ ವಿನಾಯಿತಿ ಇದೆ ([ನಿರ್ವಹಣಾ-ವ್ಯಾಪ್ತಿಯ ವಿನಾಯಿತಿ](#manage-scope-carve-out) ನೋಡಿ).

ಈ ಮಾರ್ಗಗಳು ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಅವುಗಳನ್ನು
ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ಗೆ ತೆರೆದಿಡುವುದರಿಂದ, ಮಾನ್ಯ JWT ಅನ್ನು ಪಡೆದ ಆಕ್ರಮಣಕಾರರು (ಉದಾ.,
Cloudflared/Ngrok ಸುರಂಗದ ಮೂಲಕ) ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವಿಕೆಯನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ — ಇದು ಪರಿಚಿತ CVE
ವರ್ಗವಾಗಿದೆ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ದಾಳಿಯ ವರ್ಗ):** ನಿರ್ವಹಣಾ/ಏಜೆಂಟ್ ಸರ್ವರ್
ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ (`npm install`, `node`, ಬ್ರೌಸರ್,
ಪ್ರಾಕ್ಸಿ, `git`, `tar`, …). ಆ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ತಲುಪಬಹುದಾದರೆ —
ಆಪರೇಟರ್ OmniRoute ಅನ್ನು nginx/Cloudflare/Tailscale ಸುರಂಗದ ಹಿಂದೆ ಇರಿಸಿ JWT
ಸೋರಿಕೆಯಾಗಿರುವುದರಿಂದ ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಸಂರಚಿಸಿರುವುದರಿಂದ — ಆಕ್ರಮಣಕಾರರು "API ಅನ್ನು ಕರೆಮಾಡುವುದನ್ನು"
"ಹೋಸ್ಟ್ನಲ್ಲಿ ಕಮಾಂಡ್ ಚಲಾಯಿಸುವುದಾಗಿ" ಪರಿವರ್ತಿಸುತ್ತಾರೆ (ದೂರಸ್ಥ ಕೋಡ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆ). ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸಬಲ್ಲ
ಪ್ರತಿಯೊಂದು ಮಾರ್ಗದಲ್ಲೂ **ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗೂ ಮೊದಲು, ಷರತ್ತಿಲ್ಲದೆ ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್
ಪರಿಶೀಲನೆಯನ್ನು** ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ OmniRoute ಇದನ್ನು ತಡೆಯುತ್ತದೆ: ಸುರಂಗದ ಮೂಲಕ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ಗೂ
ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವಿಕೆಯನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಾಗುವುದಿಲ್ಲ.

**ಸಂಪೂರ್ಣ LOCAL_ONLY ಸಮೂಹ.** ಅಧಿಕೃತ ಮೂಲವು
`src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` /
`LOCAL_ONLY_API_PATTERNS` ಆಗಿದೆ; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ.
`check-route-guard-membership` ಗೇಟ್ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪೂರ್ವಪ್ರತ್ಯಯಗಳ ಅಡಿಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು
`route.ts` ಅನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಅವುಗಳಲ್ಲಿ ಯಾವುದಾದರೂ ಸ್ಥಳೀಯ-ಮಾತ್ರ ಎಂದು ವರ್ಗೀಕರಿಸದಿದ್ದರೆ CI ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

#### Manage-scope ವಿನಾಯಿತಿ

LOCAL_ONLY ಪಥಗಳ ಒಂದು ಉಪಸಮೂಹವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಸ್ಥಳದಿಂದಲೂ ಪ್ರವೇಶಿಸಬಹುದು, ಆದರೆ
ವಿನಂತಿಯು `Authorization: Bearer <api-key>` ಅನ್ನು ಹೊಂದಿದ್ದು, ಅದರ
ಮೆಟಾಡೇಟಾದಲ್ಲಿ `manage` ವ್ಯಾಪ್ತಿ (ಅಥವಾ `admin`) ಇದ್ದರೆ ಮಾತ್ರ. ಈ ವಿನಾಯಿತಿಯನ್ನು
ಪ್ರತಿ ಪಥಕ್ಕೂ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಮೂಲಕ ಸ್ಪಷ್ಟವಾಗಿ
ನಿಯಂತ್ರಿಸಲಾಗುತ್ತದೆ; ಆದ್ದರಿಂದ ಯಾವುದೇ ಹೊಸ LOCAL_ONLY ಪಥದ ಪೂರ್ವನಿಯೋಜಿತ ನಡವಳಿಕೆಯು
ಕಟ್ಟುನಿಟ್ಟಾದ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ದೃಢೀಕರಿಸದ ವಿನಂತಿಗಳು ಮತ್ತು manage
ಅಲ್ಲದ ಕೀಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗಳು ಇನ್ನೂ `403 LOCAL_ONLY` ನೊಂದಿಗೆ
ತಿರಸ್ಕರಿಸಲ್ಪಡುತ್ತವೆ.

ಪ್ರಸ್ತುತ ವಿನಾಯಿತಿ ನೀಡಬಹುದಾದ ಏಕೈಕ ಪೂರ್ವಪ್ರತ್ಯಯ `/api/mcp/` ಆಗಿದೆ. `/api/cli-tools/runtime/` ಮತ್ತು
`/api/services/` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ, ಏಕೆಂದರೆ ಅವು ಅನಿಯಂತ್ರಿತ
ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು (`npm install`, `node`) ಪ್ರಾರಂಭಿಸಬಲ್ಲವು; LOCAL_ONLY ಹಂತವು
ತಡೆಯಲು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ CVE ವರ್ಗ ಇದೇ ಆಗಿದೆ.

#### ನಿರ್ವಾಹಕರ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಲೆಕ್ಕಪರಿಶೋಧನೆ

ನೀವು OmniRoute ಅನ್ನು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಟನಲ್ನ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ಹಿಂದೆ ಚಲಾಯಿಸಿದರೆ, ಲೂಪ್ಬ್ಯಾಕ್ ಪರಿಶೀಲನೆಯು ಮೇಲಿನ
ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭ ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾರ್ಗಗಳನ್ನು ಇನ್ನೂ ರಕ್ಷಿಸುತ್ತದೆ — ಕ್ಲೈಂಟ್ ವಿಳಾಸವು
ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ವಿನಂತಿಯನ್ನು **ದೃಢೀಕರಣ ನಡೆಯುವ ಮೊದಲು** `403 LOCAL_ONLY` ನೊಂದಿಗೆ
ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ; ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭವನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ.
ನಿರ್ವಾಹಕರಿಗೆ ಇನ್ನೂ ಎರಡು ಜವಾಬ್ದಾರಿಗಳಿವೆ:

- **ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಎಂದು ಕೃತಕವಾಗಿ ತೋರಿಸುವ ಮೂಲಕ 403 ಅನ್ನು "ಸರಿಪಡಿಸಬೇಡಿ".**
  `X-Forwarded-For: 127.0.0.1` ಅನ್ನು ಹೊಂದಿಸುವುದು ಅಥವಾ ಮೂಲ ವಿಳಾಸವನ್ನು
  ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮರುಬರೆಯುವ ಪ್ರಾಕ್ಸಿ ಈ ಹಂತವು ಮುಚ್ಚುವ ನಿಖರವಾದ RCE ವರ್ಗವನ್ನೇ
  ಪುನಃ ತೆರೆಯುತ್ತದೆ. ಪ್ರಾಕ್ಸಿಯ ಮೂಲಕ ಡ್ಯಾಶ್ಬೋರ್ಡ್/API ಅನ್ನು ಬಹಿರಂಗಪಡಿಸಿ —
  ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭ ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾರ್ಗಗಳನ್ನು ಎಂದಿಗೂ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.
- **Manage-scope ವಿನಾಯಿತಿಯನ್ನು ಕನಿಷ್ಠ ಮಟ್ಟದಲ್ಲಿಡಿ.** `/api/mcp/` ಗೆ ಮಾತ್ರ
  ವಿನಾಯಿತಿ ನೀಡಬಹುದು ಮತ್ತು ಅದು `manage` ವ್ಯಾಪ್ತಿಯ API ಕೀಯೊಂದಿಗೆ ಮಾತ್ರ ಸಾಧ್ಯ.
  `SPAWN_CAPABLE_PREFIXES` ಅನ್ನು ಎಂದಿಗೂ ವಿನಾಯಿತಿ ಪಟ್ಟಿಗೆ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ —
  zod ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು ರನ್ಟೈಮ್ನಲ್ಲಿ
  `isLocalOnlyBypassableByManageScope` ಅವುಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ (ಬಹುಪದರ ರಕ್ಷಣೆ);
  ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ "ವಿನಾಯಿತಿ ನೀಡುವಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ" ಎನ್ನುವುದರ ಅರ್ಥ ಇದೇ.
  `/api/providers/` ಅಡಿಯಲ್ಲಿನ ಡೈನಾಮಿಕ್-ಸೆಗ್ಮೆಂಟ್ ಮತ್ತು ಸ್ಥಿರ-ಪಥದ
  ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭ ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾರ್ಗಗಳು (ಉದಾ. `/login`,
  `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿರುವ
  regex-ಆಧಾರಿತ `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಸಹಚರದಿಂದ ಒಳಗೊಳ್ಳುತ್ತವೆ; ಸಮತಟ್ಟಾದ
  `SPAWN_CAPABLE_PREFIXES` ಅರೇಯಿಂದ ಅಲ್ಲ — ಅವುಗಳನ್ನು ಹಿಡಿಯಲು ಸಮತಟ್ಟಾದ ಅರೇಯು
  ಸಂಪೂರ್ಣ `/api/providers/` ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಒಳಗೊಳ್ಳಬೇಕಾಗುತ್ತದೆ, ಇದರಿಂದ
  ದೂರಸ್ಥ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು ಪೂರೈಕೆದಾರರ CRUD ಗಾಗಿ ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಬಳಸುವ ಮಾರ್ಗ
  ವೃಕ್ಷವು ಅತಿಯಾಗಿ ವಿಸ್ತರಿಸಲ್ಪಡುತ್ತದೆ.

**ಪ್ರವೇಶದ ಲೆಕ್ಕಪರಿಶೋಧನೆ** — ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ಯಾವುದೂ ಈ ಮಾರ್ಗಗಳನ್ನು ತಲುಪುತ್ತಿಲ್ಲ ಎಂದು ಪರಿಶೀಲಿಸಲು:

- `/dashboard/settings/security` ನಲ್ಲಿ **ಅಧಿಕಾರ ನೀಡಿಕೆ ಇನ್ವೆಂಟರಿ** ತೆರೆಯಿರಿ: ಇದು
  ನೇರ LOCAL_ONLY ಪೂರ್ವಪ್ರತ್ಯಯ ಪಟ್ಟಿಯನ್ನು, ಯಾವ ಪೂರ್ವಪ್ರತ್ಯಯಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡಬಹುದು ಎಂಬುದನ್ನು ಮತ್ತು ಕಂಪೈಲ್-ಸಮಯದ
  ಪ್ರಕ್ರಿಯೆ-ಆರಂಭಿಸಬಲ್ಲ ("ಬೈಪಾಸ್ ಮಾಡಬಹುದಾಗಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ") ಗುಂಪನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ.
- ಮೇಲಿನ ಪೂರ್ವಪ್ರತ್ಯಯಗಳಿಗೆ ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಕ್ಲೈಂಟ್ ವಿಳಾಸವನ್ನು ಜೋಡಿಸಿ, ನಿಮ್ಮ ರಿವರ್ಸ್-ಪ್ರಾಕ್ಸಿ / ಪ್ರವೇಶ ಲಾಗ್ಗಳಲ್ಲಿ Grep ಮಾಡಿ.
  `403 LOCAL_ONLY` ಬದಲಿಗೆ `200` ಹಿಂತಿರುಗಿಸಿದ ಯಾವುದೇ ಹಿಟ್, ಪ್ರಾಕ್ಸಿಯು ನಿಜವಾದ ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಮರೆಮಾಚುತ್ತಿದೆ
  ಎಂದರ್ಥ — ಪ್ರಾಕ್ಸಿಯನ್ನು ಸರಿಪಡಿಸಿ.
- ಈ ಮಾರ್ಗಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ OmniRoute ಲಾಗ್ಗಳಲ್ಲಿ ಕಾಣಿಸುವ `403 LOCAL_ONLY`, ಗಾರ್ಡ್ ಉದ್ದೇಶಿಸಿದಂತೆ
  ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆ ಎಂದರ್ಥ; ಅದು ಮರೆಮಾಡಬೇಕಾದ ದೋಷವಲ್ಲ.

### ಹಂತ 2 — ALWAYS_PROTECTED

**ಜಾರಿಗೊಳಿಸುವುದು:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ಬೈಪಾಸ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡಿ
**ಬೈಪಾಸ್:** `requireLogin=false` ಆಗಿರುವಾಗ ಯಾವುದೂ ಇಲ್ಲ; JWT ಯಾವಾಗಲೂ ಅಗತ್ಯ

ಈ ಮಾರ್ಗಗಳು ವಿನಾಶಕಾರಿ ಅಥವಾ ಹಿಂತಿರುಗಿಸಲಾಗದವು. "ಪಾಸ್ವರ್ಡ್-ಇಲ್ಲದ"
ಸ್ಥಾಪನೆಯಲ್ಲಿ ಇವುಗಳನ್ನು ಅನುಮತಿಸುವುದೆಂದರೆ, ಅದೇ LAN ನಲ್ಲಿರುವ ಯಾರಾದರೂ ಡೇಟಾಬೇಸ್ ಅನ್ನು ಅಳಿಸಬಹುದು ಅಥವಾ
ಸರ್ವರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಕೊನೆಗೊಳಿಸಬಹುದು ಎಂದರ್ಥ.

| ಮಾರ್ಗ                                     | ಕಾರಣ                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------- |
| `/api/shutdown`                           | ಸರ್ವರ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ                                     |
| `/api/settings/database`                  | ಡೇಟಾಬೇಸ್ ರಫ್ತು, ಆಮದು ಮತ್ತು ಸಂಪೂರ್ಣ ಅಳಿಸುವಿಕೆ                              |
| `/api/db-backups`                         | ಪೂರ್ಣ ಡೇಟಾಬೇಸ್ ಬ್ಯಾಕಪ್ ಆರ್ಕೈವ್ಗೆ ಪ್ರವೇಶ                                   |
| `/api/settings/export-json`               | ಸಂಪೂರ್ಣ ಸೆಟ್ಟಿಂಗ್ಗಳ ಬ್ಲಾಬ್ ಅನ್ನು ರಫ್ತು ಮಾಡುತ್ತದೆ (ರಹಸ್ಯಗಳು ಸೇರಿದಂತೆ)      |
| `/api/settings/import-json`               | ಸಂಪೂರ್ಣ ಸೆಟ್ಟಿಂಗ್ಗಳ ಬ್ಲಾಬ್ ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ                            |
| `/api/providers/health-autopilot/actions` | ಆಟೋಪೈಲಟ್ ಪರಿಹಾರ ಕ್ರಮಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆ                             |
| `/api/settings/obsidian`                  | ಯಾವುದೇ ವಾಲ್ಟ್ ರೂಟ್ಗಾಗಿ ಮರುಬಳಕೆ ಮಾಡಬಹುದಾದ WebDAV ರುಜುವಾತುಗಳನ್ನು ರಚಿಸುತ್ತದೆ |

**ಉಲ್ಲಂಘನೆಯ ಪ್ರತಿಕ್ರಿಯೆ:** `401 Authentication required`

`/api/settings/obsidian` ಅದರ `/webdav` ಉಪಮಾರ್ಗವನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ: `POST`, ಈ ಪೈಪ್ಲೈನ್ನ ಹೊರಗೆ Next.js ಗಿಂತ ಮೊದಲು ಕಸ್ಟಮ್ Node ಪದರದಿಂದ
ಒದಗಿಸಲ್ಪಡುವ WebDAV ಫೈಲ್ ಸೇವೆಯನ್ನು — ಕರೆ ಮಾಡುವವರು ಆಯ್ಕೆಮಾಡಿದ ರೂಟ್ಗೆ — ನಿರ್ದೇಶಿಸುತ್ತದೆ
ಮತ್ತು ಹೊಸದಾಗಿ ರಚಿಸಿದ Basic ರುಜುವಾತುಗಳನ್ನು ಪ್ರತಿಧ್ವನಿಸುತ್ತದೆ, `DELETE` ಅವುಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ, ಮತ್ತು ಮೂಲ `POST`
Obsidian REST API ಟೋಕನ್ ಅನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ. GHSA-62vw ಕೇವಲ `GET` ಪಾಸ್ವರ್ಡ್ ಬಹಿರಂಗಪಡಿಸುವಿಕೆಯನ್ನು ಮರೆಮಾಡಿತು;
ರುಜುವಾತು ನೀಡುವಿಕೆ ಇನ್ನೂ ವಿಫಲವಾದಾಗ-ತೆರೆದಿರುವ ಹಂತದಲ್ಲೇ ಇತ್ತು (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` ಹೆಚ್ಚುವರಿಯಾಗಿ
ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯೇ ಆಗಿರುವ, ಅದರೊಳಗೆ ಇರುವ ಅಥವಾ ಅದನ್ನು ಒಳಗೊಂಡಿರುವ ವಾಲ್ಟ್ ಅನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ.

### ಹೊಸ-ಸ್ಥಾಪನೆಯ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮಾತ್ರ — ನಿಜವಾದ ಪಿಯರ್ ಆಧಾರಿತ, `Host` ಅಲ್ಲ

ಯಾವುದೇ ನಿರ್ವಹಣಾ ಪಾಸ್ವರ್ಡ್ ಕಾನ್ಫಿಗರ್ ಮಾಡದಿದ್ದಾಗ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲದಾಗ),
`src/shared/utils/apiAuth.ts` ನಲ್ಲಿರುವ `isAuthRequired()` ಅನಾಮಧೇಯ ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಅನ್ನು **ಲೂಪ್ಬ್ಯಾಕ್ ಪಿಯರ್ಗಳಿಗೆ ಮಾತ್ರ** ತೆರೆದಿಡುತ್ತದೆ.
ವಿಶ್ವಾಸಾರ್ಹ ಪಿಯರ್ ಸಂಕೇತಗಳಿಂದ ಈ ಕ್ರಮದಲ್ಲಿ ಲೂಪ್ಬ್ಯಾಕ್ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ: ಟೋಕನ್-ಮುದ್ರಿತ ನಿಜವಾದ TCP ಪಿಯರ್
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ನೀತಿಯು ನೋಡುವುದು), ಪೈಪ್ಲೈನ್ನ ಸ್ವಂತ
`AUTHZ_HEADER_PEER_LOCALITY` ತೀರ್ಪು (ಮಾರ್ಗ ಹ್ಯಾಂಡ್ಲರ್ಗಳು ನೋಡುವುದು, `OMNIROUTE_PEER_STAMP_TOKEN`
ಹೊಂದಿಸಿರುವಾಗ ಮಾತ್ರ ವಿಶ್ವಾಸಾರ್ಹ), ಅಥವಾ ನೇರ ಕರೆಗಾರರ ನಿಜವಾದ ಸಾಕೆಟ್ ಪಿಯರ್. `Host` /
`nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಪರಿಶೀಲಿಸಲಾಗುವುದಿಲ್ಲ, ಮತ್ತು ಮೊದಲ-ಪಾಸ್ವರ್ಡ್ ಬರವಣಿಗೆ
(`POST /api/settings/require-login`) ಪ್ರತಿ ನೆಟ್ವರ್ಕ್ ಪಿಯರ್ಗೆ ತೆರೆದಿರುವ ಬದಲು ಇದೇ
ನಿರ್ಬಂಧಕ್ಕೆ ಒಳಪಟ್ಟಿರುತ್ತದೆ (GHSA-7pq4-8pvv-rx7r). `managementPolicy` ತನ್ನದೇ `peerContext` ತೀರ್ಪನ್ನು
ಸ್ಪಷ್ಟವಾಗಿ ಕೆಳಗೆ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ORIGINAL (ತೆಗೆದುಹಾಕುವಿಕೆ-ಪೂರ್ವ) ವಿನಂತಿಯ ಹೆಡರ್ಗಳು ಅದನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಹಂತ 3 — MANAGEMENT (ಡೀಫಾಲ್ಟ್)

ಉಳಿದ ಎಲ್ಲಾ ನಿರ್ವಹಣಾ ಮಾರ್ಗಗಳು. `requireLogin=false` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದಿದ್ದರೆ ದೃಢೀಕರಣ ಅಗತ್ಯ.
CLI ಟೋಕನ್ಗಳು ಈ ಮಾರ್ಗಗಳನ್ನು ದೃಢೀಕರಿಸಬಹುದು (ಲೂಪ್ಬ್ಯಾಕ್ + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

| `tests/unit/authz/management-policy.test.ts` | evaluate() ಗಾಗಿ ಘಟಕ ಪರೀಕ್ಷೆಗಳು     |

## OpenAPI ನಲ್ಲಿ ಭದ್ರತಾ ಹಂತಗಳನ್ನು ದಾಖಲಿಸುವುದು

`docs/openapi.yaml` ಗೆ ಹೊಸ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವಾಗ, ಮಾರ್ಗವನ್ನು `routeGuard.ts` ವರ್ಗೀಕರಿಸಿದ್ದರೆ ಅದಕ್ಕೆ ಅನುಗುಣವಾದ vendor extension ಅನ್ನು ಅನ್ವಯಿಸಿ:

| routeGuard.ts ವರ್ಗೀಕರಣ                     | YAML ಟಿಪ್ಪಣಿ                | ಜಾರಿಗೊಳಿಸುವಿಕೆ                                                     |
| ------------------------------------------ | --------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`     | ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಮೂಲಗಳಿಂದ ಬರುವುದನ್ನು ಬೇಷರತ್ತಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`  | `requireLogin=false` ಇದ್ದರೂ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ                      |
| ಆಂತರಿಕ admin/debug ಮಾರ್ಗ                   | `x-internal: true`          | ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ /dashboard/api-endpoints ನಿಂದ ಮರೆಮಾಡಲಾಗುತ್ತದೆ     |
| ಯಾವುದೂ ಇಲ್ಲ (ಸಾರ್ವಜನಿಕ / ಪ್ರಮಾಣಿತ ದೃಢೀಕರಣ) | (ಯಾವುದೇ ಟಿಪ್ಪಣಿ ಅಗತ್ಯವಿಲ್ಲ) | ಪ್ರಮಾಣಿತ `requireLogin`-ನಿಯಂತ್ರಿತ ಪ್ರವೇಶ                           |

### ಮೌಲ್ಯೀಕರಣ

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
