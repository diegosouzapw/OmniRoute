## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಹಂತಗಳು

### ಹಂತ 1 — LOCAL_ONLY

**ಜಾರಿಗೊಳಿಸುವುದು:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆ  
**ಬೈಪಾಸ್:** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ಸ್ಕೋಪ್ ಹೊಂದಿರುವ ಮಾನ್ಯ API ಕೀಲಿಯನ್ನು ಒಳಗೊಂಡಿರುವಾಗ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿರುವ ಪಥಗಳಿಗೆ ಸೀಮಿತ ವಿನಾಯಿತಿ ಅನ್ವಯಿಸುತ್ತದೆ (ನೋಡಿ [Manage-ಸ್ಕೋಪ್ ವಿನಾಯಿತಿ](#manage-scope-carve-out)).

ಈ ರೂಟ್ಗಳು ಚೈಲ್ಡ್ ಪ್ರೊಸೆಸ್ಗಳನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಅವುಗಳನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ಗೆ ಬಹಿರಂಗಪಡಿಸಿದರೆ, ಮಾನ್ಯ JWT ಅನ್ನು ಪಡೆದ ಆಕ್ರಮಣಕಾರರು (ಉದಾ., Cloudflared/Ngrok ಟನಲ್ ಮೂಲಕ) ಪ್ರೊಸೆಸ್ಗಳ ಪ್ರಾರಂಭವನ್ನು ಟ್ರಿಗರ್ ಮಾಡಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ — ಇದು ತಿಳಿದಿರುವ CVE ವರ್ಗವಾಗಿದೆ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ಆಕ್ರಮಣದ ವರ್ಗ):** ಒಂದು ನಿರ್ವಹಣೆ/ಏಜೆಂಟ್ ಸರ್ವರ್ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ (`npm install`, `node`, ಬ್ರೌಸರ್, ಪ್ರಾಕ್ಸಿ, `git`, `tar`, …). ಆ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ತಲುಪಲು ಸಾಧ್ಯವಾದರೆ — ಆಪರೇಟರ್ OmniRoute ಅನ್ನು nginx/Cloudflare/Tailscale ಟನಲ್ನ ಹಿಂದೆ ಇರಿಸಿ JWT ಸೋರಿಕೆಯಾಗಿರುವುದರಿಂದ, ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಸಂರಚಿಸಿರುವುದರಿಂದ — ಆಕ್ರಮಣಕಾರರು "API ಅನ್ನು ಕರೆಮಾಡುವುದನ್ನು" "ಹೋಸ್ಟ್ನಲ್ಲಿ ಕಮಾಂಡ್ ಚಲಾಯಿಸುವುದಾಗಿ" ಪರಿವರ್ತಿಸುತ್ತಾರೆ (ರಿಮೋಟ್ ಕೋಡ್ ಎಕ್ಸಿಕ್ಯೂಷನ್). ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪ್ರತಿಯೊಂದು ರೂಟ್ನಲ್ಲಿ **ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗೂ ಮೊದಲು, ಬೇಷರತ್ತಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆಯನ್ನು** ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ OmniRoute ಇದನ್ನು ತಡೆಯುತ್ತದೆ: ಟನಲ್ ಮೂಲಕ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಇದ್ದರೂ ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸುವುದನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಸಂಪೂರ್ಣ LOCAL_ONLY ಸಮೂಹ.** ಅಧಿಕೃತ ಮೂಲವು `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ಆಗಿದೆ; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ. `check-route-guard-membership` ಗೇಟ್ ಪ್ರೊಸೆಸ್ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪ್ರಿಫಿಕ್ಸ್ಗಳ ಅಡಿಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು `route.ts` ಅನ್ನು ಎಣಿಸುತ್ತದೆ ಮತ್ತು ಅವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ local-only ಎಂದು ವರ್ಗೀಕರಿಸದಿದ್ದರೆ CI ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

#### ನಿರ್ವಹಣಾ-ವ್ಯಾಪ್ತಿಯ ವಿನಾಯಿತಿ

ವಿನಂತಿಯು `manage` ವ್ಯಾಪ್ತಿಯನ್ನು (ಅಥವಾ `admin`) ಒಳಗೊಂಡಿರುವ ಮೆಟಾಡೇಟಾವನ್ನು ಹೊಂದಿರುವ
`Authorization: Bearer <api-key>` ಅನ್ನು ಹೊತ್ತಿದ್ದರೆ ಮತ್ತು ಆಗ ಮಾತ್ರ, LOCAL_ONLY
ಪಥಗಳ ಉಪಸಮೂಹವನ್ನು ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್ನಿಂದಲೂ ಪ್ರವೇಶಿಸಬಹುದು. ಯಾವುದೇ ಹೊಸ LOCAL_ONLY
ಪಥದ ಡೀಫಾಲ್ಟ್ ಕಟ್ಟುನಿಟ್ಟಾದ-ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುವಂತೆ, ಈ ವಿನಾಯಿತಿಯನ್ನು ಪ್ರತಿ-ಪಥಕ್ಕೆ
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಮೂಲಕ ಸ್ಪಷ್ಟವಾಗಿ ನಿಯಂತ್ರಿಸಲಾಗಿದೆ.
ದೃಢೀಕರಿಸದ ವಿನಂತಿಗಳು ಮತ್ತು ನಿರ್ವಹಣಾ ವ್ಯಾಪ್ತಿಯಿಲ್ಲದ ಕೀಲಿಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗಳನ್ನು
ಇನ್ನೂ `403 LOCAL_ONLY` ಮೂಲಕ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಏಕೈಕ ಪ್ರಿಫಿಕ್ಸ್ `/api/mcp/`. `/api/cli-tools/runtime/`
ಮತ್ತು `/api/services/` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ, ಏಕೆಂದರೆ ಅವು ಮನಬಂದಂತೆ
ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು (`npm install`, `node`) ಪ್ರಾರಂಭಿಸಬಹುದು; LOCAL_ONLY ಹಂತವು ತಡೆಯಲು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ CVE ವರ್ಗ ಇದೇ ಆಗಿದೆ.

#### ನಿರ್ವಾಹಕರ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಲೆಕ್ಕಪರಿಶೋಧನೆ

ನೀವು OmniRoute ಅನ್ನು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಟನಲ್ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ಹಿಂದೆ ಚಲಾಯಿಸಿದರೆ, ಲೂಪ್ಬ್ಯಾಕ್ ಪರಿಶೀಲನೆಯು ಮೇಲಿನ
ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಮಾರ್ಗಗಳನ್ನು ಇನ್ನೂ ರಕ್ಷಿಸುತ್ತದೆ — ಕ್ಲೈಂಟ್ ವಿಳಾಸವು
ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿರುವ ವಿನಂತಿಯನ್ನು **ದೃಢೀಕರಣ ನಡೆಯುವ ಮೊದಲೇ** `403 LOCAL_ONLY`
ಮೂಲಕ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ; ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT ಒಂದು ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವ ಹಂತವನ್ನು
ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ನಿರ್ವಾಹಕರ ಎರಡು ಜವಾಬ್ದಾರಿಗಳು ಉಳಿದಿವೆ:

- **ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಎಂದು ನಕಲಿಸುವ ಮೂಲಕ 403 ಅನ್ನು "ಸರಿಪಡಿಸಬೇಡಿ".**
  `X-Forwarded-For: 127.0.0.1` ಅನ್ನು ಹೊಂದಿಸುವುದು ಅಥವಾ ಮೂಲ ವಿಳಾಸವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ಗೆ
  ಮರುಬರೆಯುವ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಳಸುವುದು, ಈ ಹಂತವು ಮುಚ್ಚುವ ನಿಖರವಾದ RCE ವರ್ಗವನ್ನೇ ಮತ್ತೆ
  ತೆರೆಯುತ್ತದೆ. ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ಡ್ಯಾಶ್ಬೋರ್ಡ್/API ಅನ್ನು ಬಹಿರಂಗಪಡಿಸಿ — ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭಿಸಬಲ್ಲ
  ಮಾರ್ಗಗಳನ್ನು ಎಂದಿಗೂ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.
- **ನಿರ್ವಹಣಾ-ವ್ಯಾಪ್ತಿಯ ಬೈಪಾಸ್ ಅನ್ನು ಕನಿಷ್ಠ ಮಟ್ಟದಲ್ಲಿಡಿ.** `/api/mcp/` ಮಾತ್ರ ಬೈಪಾಸ್
  ಮಾಡಬಹುದಾಗಿದೆ ಮತ್ತು ಅದು `manage`-ವ್ಯಾಪ್ತಿಯ API ಕೀಲಿಯಿಂದ ಮಾತ್ರ ಸಾಧ್ಯ.
  `SPAWN_CAPABLE_PREFIXES` ಅನ್ನು ಬೈಪಾಸ್ ಪಟ್ಟಿಗೆ ಎಂದಿಗೂ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ — zod
  ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು `isLocalOnlyBypassableByManageScope`
  ರನ್ಟೈಮ್ನಲ್ಲಿ ಅವುಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ (ಆಳವಾದ-ರಕ್ಷಣೆ); ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿರುವ
  "ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ" ಎಂಬುದರ ಅರ್ಥ ಇದೇ. `/api/providers/`
  ಅಡಿಯಲ್ಲಿನ ಡೈನಾಮಿಕ್-ಸೆಗ್ಮೆಂಟ್ ಮತ್ತು ಸ್ಥಿರ-ಪಥದ ಪ್ರಕ್ರಿಯೆ-ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಮಾರ್ಗಗಳು
  (ಉದಾ. `/login`, `/refresh-cursor`) ಸರಳವಾದ `SPAWN_CAPABLE_PREFIXES` ಅರೆ ಮೂಲಕವಲ್ಲ,
  `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿರುವ regex-ಆಧಾರಿತ
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಸಹಚರ ವ್ಯವಸ್ಥೆಯಿಂದ
  ಒಳಗೊಳ್ಳುತ್ತವೆ — ಅವುಗಳನ್ನು ಹಿಡಿಯಲು ಸರಳ ಅರೆ ಸಂಪೂರ್ಣ `/api/providers/` ಪ್ರಿಫಿಕ್ಸ್
  ಅನ್ನು ಒಳಗೊಳ್ಳಬೇಕಾಗುತ್ತದೆ; ಇದರಿಂದ ದೂರಸ್ಥ ಡ್ಯಾಶ್ಬೋರ್ಡ್ಗಳು ಪೂರೈಕೆದಾರರ CRUD ಗಾಗಿ
  ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಬಳಸುವ ಮಾರ್ಗ ವೃಕ್ಷವು ಅತಿಯಾಗಿ ವಿಸ್ತಾರಗೊಳ್ಳುತ್ತದೆ.

ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಲು:

- `/dashboard/settings/security` ನಲ್ಲಿ **ದೃಢೀಕರಣ ದಾಸ್ತಾನು** ತೆರೆಯಿರಿ: ಇದು
  ಸಕ್ರಿಯ LOCAL_ONLY ಪೂರ್ವಪ್ರತ್ಯಯ ಪಟ್ಟಿಯನ್ನು, ಯಾವ ಪೂರ್ವಪ್ರತ್ಯಯಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡಬಹುದು ಎಂಬುದನ್ನು ಮತ್ತು ಕಂಪೈಲ್-ಸಮಯದ
  ಪ್ರಕ್ರಿಯೆ-ಆರಂಭಿಸಬಲ್ಲ ("ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ") ಸಮೂಹವನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ.
- ಮೇಲಿನ ಪೂರ್ವಪ್ರತ್ಯಯಗಳು ಮತ್ತು loopback ಅಲ್ಲದ ಕ್ಲೈಂಟ್ ವಿಳಾಸ ಒಟ್ಟಿಗೆ ಕಂಡುಬರುವುದಕ್ಕಾಗಿ ನಿಮ್ಮ reverse-proxy / access ಲಾಗ್ಗಳಲ್ಲಿ Grep ಮಾಡಿ.
  ಅಂತಹ ಯಾವುದೇ ಹಿಟ್ `403 LOCAL_ONLY` ಬದಲು `200` ಹಿಂತಿರುಗಿಸಿದರೆ,
  proxy ನೈಜ ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಮರೆಮಾಚುತ್ತಿದೆ ಎಂದರ್ಥ — proxy ಅನ್ನು ಸರಿಪಡಿಸಿ.
- ಈ ಪಥಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ OmniRoute ಲಾಗ್ಗಳಲ್ಲಿ ಕಾಣಿಸುವ `403 LOCAL_ONLY`, guard
  ಉದ್ದೇಶಿಸಿದಂತೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆ ಎಂಬುದನ್ನು ಸೂಚಿಸುತ್ತದೆ; ಅದು ನಿರ್ಲಕ್ಷಿಸಬೇಕಾದ ದೋಷವಲ್ಲ.

### ಶ್ರೇಣಿ 2 — ALWAYS_PROTECTED

**ಜಾರಿಗೊಳಿಸುವುದು:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ಬೈಪಾಸ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ
**ಬೈಪಾಸ್:** `requireLogin=false` ಆಗಿರುವಾಗ ಯಾವುದೂ ಇಲ್ಲ; JWT ಯಾವಾಗಲೂ ಅಗತ್ಯ

ಈ ಮಾರ್ಗಗಳು ವಿನಾಶಕಾರಿ ಅಥವಾ ಹಿಂತಿರುಗಿಸಲಾಗದವು. "ಪಾಸ್ವರ್ಡ್ ಇಲ್ಲದ"
ಸ್ಥಾಪನೆಯಲ್ಲಿ ಇವುಗಳನ್ನು ಅನುಮತಿಸಿದರೆ, ಅದೇ LAN ನಲ್ಲಿರುವ ಯಾರಾದರೂ database ಅನ್ನು ಅಳಿಸಬಹುದು ಅಥವಾ
server process ಅನ್ನು ಕೊನೆಗೊಳಿಸಬಹುದು.

| ಪಥ                                        | ಕಾರಣ                                                                   |
| ----------------------------------------- | ---------------------------------------------------------------------- |
| `/api/shutdown`                           | server process ಅನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ                                   |
| `/api/settings/database`                  | database export, import ಮತ್ತು wipe                                     |
| `/api/db-backups`                         | ಸಂಪೂರ್ಣ database backup archive ಗೆ ಪ್ರವೇಶ                              |
| `/api/settings/export-json`               | ಸಂಪೂರ್ಣ settings blob ಅನ್ನು export ಮಾಡುತ್ತದೆ (ರಹಸ್ಯಗಳೂ ಸೇರಿದಂತೆ)       |
| `/api/settings/import-json`               | ಸಂಪೂರ್ಣ settings blob ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ                              |
| `/api/providers/health-autopilot/actions` | autopilot ಪರಿಹಾರ ಕ್ರಮಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆ                         |

**ಉಲ್ಲಂಘನೆಯಾಗುವಾಗ ಪ್ರತಿಕ್ರಿಯೆ:** `401 Authentication required`

`/api/settings/obsidian` ಅದರ `/webdav` child ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ: `POST`, Next.js ಗಿಂತ ಮೊದಲು ಈ pipeline ನ ಹೊರಗೆ custom Node layer ಮೂಲಕ ಒದಗಿಸಲಾಗುವ WebDAV file service ಅನ್ನು —
ಕರೆ ಮಾಡುವವರು ಆಯ್ಕೆಮಾಡಿದ root ಕಡೆಗೆ ನಿರ್ದೇಶಿಸುತ್ತದೆ
ಮತ್ತು ಹೊಸದಾಗಿ ರಚಿಸಿದ Basic credentials ಅನ್ನು ಪ್ರತಿಧ್ವನಿಸುತ್ತದೆ, `DELETE` ಅವುಗಳನ್ನು ಪರಿವರ್ತಿಸುತ್ತದೆ, ಹಾಗೂ parent `POST`
Obsidian REST API token ಅನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ. GHSA-62vw ಕೇವಲ `GET` password ಬಹಿರಂಗಪಡಿಸುವಿಕೆಯನ್ನು ಮರೆಮಾಚಿತು; credentials ನೀಡುವಿಕೆ
ಇನ್ನೂ fail-open ಶ್ರೇಣಿಯಲ್ಲೇ ಇತ್ತು (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` ಹೆಚ್ಚುವರಿಯಾಗಿ
data directory ಆಗಿರುವ, ಅದರೊಳಗಿರುವ ಅಥವಾ ಅದನ್ನು ಒಳಗೊಂಡಿರುವ vault ಅನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ.

### ಹೊಸ ಸ್ಥಾಪನೆಯ bootstrap loopback ಗೆ ಮಾತ್ರ ಸೀಮಿತ — `Host` ಆಧಾರಿತವಲ್ಲ, ನೈಜ peer ಆಧಾರಿತ

ಯಾವುದೇ management password ಕಾನ್ಫಿಗರ್ ಮಾಡದಿದ್ದಾಗ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲದಿದ್ದಾಗ),
`src/shared/utils/apiAuth.ts` ನಲ್ಲಿನ `isAuthRequired()` ಅನಾಮಧೇಯ bootstrap ಅನ್ನು **loopback peer ಗಳಿಗೆ ಮಾತ್ರ** ತೆರೆದಿಡುತ್ತದೆ.
loopback ಅನ್ನು ಈ ಆದ್ಯತಾಕ್ರಮದಲ್ಲಿರುವ ವಿಶ್ವಾಸಾರ್ಹ peer ಸಂಕೇತಗಳಿಂದ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ: token-stamped ನೈಜ TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy ನೋಡುವುದು), pipeline ನ ಸ್ವಂತ
`AUTHZ_HEADER_PEER_LOCALITY` ತೀರ್ಪು (route handler ಗಳು ನೋಡುವುದು, `OMNIROUTE_PEER_STAMP_TOKEN` ಹೊಂದಿಸಿರುವಾಗ ಮಾತ್ರ ವಿಶ್ವಾಸಾರ್ಹ),
ಅಥವಾ ನೇರ caller ಗಳಿಗಾಗಿ ನೈಜ socket peer. `Host` /
`nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ, ಮತ್ತು ಮೊದಲ-password write
(`POST /api/settings/require-login`) ಅನ್ನು ಪ್ರತಿಯೊಂದು network peer ಗೂ ತೆರೆದಿಡುವ ಬದಲು ಅದೇ ನಿರ್ಬಂಧಕ್ಕೆ ಒಳಪಡಿಸಲಾಗುತ್ತದೆ
(GHSA-7pq4-8pvv-rx7r). `managementPolicy` ತನ್ನದೇ `peerContext` ತೀರ್ಪನ್ನು
ಸ್ಪಷ್ಟವಾಗಿ ಕೆಳಗೆ ರವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ORIGINAL (strip ಮಾಡುವುದಕ್ಕಿಂತ ಮೊದಲಿನ) request ನ header ಗಳು ಅದನ್ನು ಎಂದಿಗೂ ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಶ್ರೇಣಿ 3 — MANAGEMENT (ಪೂರ್ವನಿಯೋಜಿತ)

ಉಳಿದ ಎಲ್ಲಾ management route ಗಳು. `requireLogin=false` ಅನ್ನು
ಕಾನ್ಫಿಗರ್ ಮಾಡದ ಹೊರತು auth ಅಗತ್ಯವಿದೆ. CLI token ಗಳು ಈ route ಗಳನ್ನು ದೃಢೀಕರಿಸಬಹುದು (loopback + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
