> **ಸತ್ಯದ ಮೂಲ:** `src/lib/guardrails/`
> **ಕೊನೆಯ ನವೀಕರಣ:** 2026-08-29 — v3.8.51 (Video Bridge ಪ್ರತಿಲೇಖದ ಮೂಲವನ್ನು ಕರೆಮಾಡುವವರು ಘೋಷಿಸುತ್ತಾರೆ,
> ಸರ್ವರ್ ಇನ್ನೂ ಅದನ್ನು ಪರಿಶೀಲಿಸುವುದಿಲ್ಲ — #11661 ಪ್ರಕಾರ ಸ್ಪಷ್ಟಪಡಿಸಲಾಗಿದೆ)

Guardrails, OmniRoute ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ಸುರಕ್ಷತೆ,
ನೀತಿ ಮತ್ತು ವಿಷಯ ರೂಪಾಂತರಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿಯೊಂದು guardrail ವಿನಂತಿಯ
ಪೇಲೋಡ್ಗಳನ್ನು (`preCall`) ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು (`postCall`)
ಪರಿಶೀಲಿಸಬಹುದು (ಮತ್ತು ಐಚ್ಛಿಕವಾಗಿ ತಿರಸ್ಕರಿಸಬಹುದು, ರೂಪಾಂತರಿಸಬಹುದು ಅಥವಾ ಟಿಪ್ಪಣಿ ಸೇರಿಸಬಹುದು).

ಈ ವ್ಯವಸ್ಥೆಯು **fail-open** ಆಗಿದೆ: ಕಾರ್ಯಗತಗೊಳ್ಳುವಾಗ guardrail ದೋಷವನ್ನು ಎಸೆದರೆ,
registry ಆ ದೋಷವನ್ನು ದಾಖಲಿಸಿ, ವಿನಂತಿಯನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು ಮುಂದಿನ guardrail
ಜೊತೆಗೆ ಮುಂದುವರಿಯುತ್ತದೆ. ನಿರ್ಬಂಧಿಸುವುದು ಸ್ಪಷ್ಟ ನಿರ್ಧಾರವಾಗಿದೆ (`block: true`),
ಎಂದಿಗೂ ಆಕಸ್ಮಿಕವಲ್ಲ.

## ಅಂತರ್ಗತ ಗಾರ್ಡ್ರೈಲ್ಗಳು

ರಿಜಿಸ್ಟ್ರಿ ಆಮದು ಮಾಡಿಕೊಳ್ಳುವಾಗ ಆರು ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ಸ್ವಯಂ-ಲೋಡ್ ಮಾಡುತ್ತದೆ
(`registry.ts` → `registerDefaultGuardrails()` ನೋಡಿ):

| ಆದ್ಯತೆ | ಹೆಸರು               | ಹಂತ(ಗಳು)       | ಫೈಲ್                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ಕಡಿಮೆ ಆದ್ಯತೆಯ ಸಂಖ್ಯೆಗಳು **ಮೊದಲು** ರನ್ ಆಗುತ್ತವೆ.

### ವಿಷನ್ ಬ್ರಿಡ್ಜ್ (`visionBridge.ts`) — ಮೊಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ PR-1

**ವಿಷನ್-ಅಲ್ಲದ ಮಾದರಿಗಳನ್ನು** ಗುರಿಯಾಗಿಸಿಕೊಂಡಿರುವ ಚಿತ್ರ-ಹೊಂದಿರುವ ವಿನಂತಿಗಳನ್ನು ತಡೆಹಿಡಿಯುತ್ತದೆ ಮತ್ತು ಸಂಪೂರ್ಣ ವಿನಂತಿಯನ್ನು ವಿಷನ್-ಸಾಮರ್ಥ್ಯದ ಮಾದರಿಗೆ ಮರುನಿರ್ದೇಶಿಸುತ್ತದೆ ಅಥವಾ ಅಪ್ಸ್ಟ್ರೀಮ್ ಕರೆಗೆ ಮೊದಲು ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ ವಿಷನ್ ಮಾದರಿಯಿಂದ ಉತ್ಪತ್ತಿಯಾಗುವ ಪಠ್ಯ ವಿವರಣೆಗಳೊಂದಿಗೆ ಚಿತ್ರದ ಭಾಗಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ. ಇದು ಪಠ್ಯ-ಮಾತ್ರ ಪೂರೈಕೆದಾರರಿಗೆ ಬಹುಮಾದರಿ ಪೇಲೋಡ್ಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ನಿರ್ವಹಿಸಲು ಅನುವು ಮಾಡಿಕೊಡುತ್ತದೆ.

ಹರಿವು:

1. ಗುರಿ ಮಾದರಿಯು ಈಗಾಗಲೇ ವಿಷನ್ ಅನ್ನು ಬೆಂಬಲಿಸಿದರೆ (ಬಲವಂತದ-ಬ್ರಿಡ್ಜ್ ಪಟ್ಟಿಯಲ್ಲಿ `isVisionBridgeForcedModel` ಕಾಣಿಸದಿದ್ದರೆ) ಸ್ಕಿಪ್ ಮಾಡಿ.
2. `extractImageParts(messages)` (`visionBridgeHelpers.ts`) ಮೂಲಕ ಚಿತ್ರದ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ, ಇದು `open-sse/utils/mediaParts.ts` ನಲ್ಲಿರುವ **ಏಕೀಕೃತ ಮಾಧ್ಯಮ ಡಿಟೆಕ್ಟರ್** `detectMediaParts()` ಗೆ ನಿಯೋಜಿಸುತ್ತದೆ — ಕಾಂಬೊ ಹೊಂದಾಣಿಕೆ ಫಿಲ್ಟರ್ನೊಂದಿಗೆ ಹಂಚಿಕೊಳ್ಳಲಾದ ಸತ್ಯದ ಏಕೈಕ ಮೂಲ. ಹೊರತೆಗೆಯುವಿಕೆಯು `replaceImageParts` ಮತ್ತೆ ಸೇರಿಸಬಹುದಾದ ಆಕಾರಗಳ ಉನ್ನತ-ಮಟ್ಟದ ಭಾಗಗಳಿಗೆ ಅನುಮತಿಸಲಾಗಿದೆ (ಹೊರತೆಗೆಯುವಿಕೆ↔ಬದಲಾಯಿಸುವಿಕೆ ಒಪ್ಪಂದ): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"`, ಮತ್ತು Responses API `input_image`. ನೆಸ್ಟೆಡ್ ಹಿಟ್ಗಳು ಮತ್ತು ಸೂಚಕ-ಮಾತ್ರ ಆಕಾರಗಳು ಕಾಂಬೊ-ಫಿಲ್ಟರ್ ವಸ್ತುಗಳಾಗಿವೆ ಮತ್ತು ಎಂದಿಗೂ ಹೊರತೆಗೆಯಲಾಗುವುದಿಲ್ಲ. ಯಾವುದೂ ಕಂಡುಬರದಿದ್ದರೆ ಸ್ಕಿಪ್ ಮಾಡಿ.
3. `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`) ಮೂಲಕ ರನ್ಟೈಮ್ ಕಾನ್ಫಿಗರ್ ಅನ್ನು ಪರಿಹರಿಸಿ: ಹೊಸ `modalityBridge*` ಸೆಟ್ಟಿಂಗ್ಗಳ ಕೀಗಳು ಗೆಲ್ಲುತ್ತವೆ; ಲೆಗಸಿ `visionBridge*` ಕೀಗಳು **ಒಂದು-ಚಕ್ರದ ಫಾಲ್ಬ್ಯಾಕ್** ಆಗಿ ಉಳಿಯುತ್ತವೆ (ರೋಲ್ಬ್ಯಾಕ್ ವಿಂಡೋ). ಬ್ರಿಡ್ಜ್ ನಿಷ್ಕ್ರಿಯಗೊಂಡಾಗ ಯಾವುದೇ ಮಾಧ್ಯಮ ಸಂಚಾರಕ್ಕೆ ಮೊದಲು ಸ್ಕಿಪ್ ಮಾಡಿ.
4. ಮೋಡ್ ಸೆಲೆಕ್ಟರ್ (`modalityBridgeVisionMode`, ಕೆಳಗಿನ ಕೋಷ್ಟಕವನ್ನು ನೋಡಿ) ಮರುನಿರ್ದೇಶನ vs ವಿವರಿಸುವುದನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ. ಮರುನಿರ್ದೇಶನವು `model` ಅನ್ನು ಮಾತ್ರ ಬದಲಾಯಿಸಿದ `modifiedPayload` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ, ಜೊತೆಗೆ ಮೆಟಾ `{ rerouted, fromModel, toModel, imagesKept }`.
5. ವಿವರಿಸುವ ಮಾರ್ಗ: `maxImages` ನಲ್ಲಿ ಚಿತ್ರಗಳನ್ನು ಕ್ಯಾಪ್ ಮಾಡಿ, ಕಾರ್ಯ-ಅರಿವಿನ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ರಚಿಸಿ, ವಿವರಿಸುವ ಸಂಗ್ರಹವನ್ನು ಸಂಪರ್ಕಿಸಿ, ವಿಷನ್ ಮಾದರಿಯನ್ನು **ಸಮಾನಾಂತರವಾಗಿ** ಕರೆಯಿರಿ (`Promise.allSettled`), ಮತ್ತು `[Image N]: <description>` ಪಠ್ಯ ಭಾಗಗಳನ್ನು ಅವುಗಳ ಸ್ಥಳದಲ್ಲಿ ಸೇರಿಸಿ. ವಿಫಲವಾದ ವಿವರಣೆಯು `null` ಅನ್ನು ನೀಡುತ್ತದೆ ಮತ್ತು ಮೂಲ ಚಿತ್ರದ ಭಾಗವನ್ನು **ಸಂರಕ್ಷಿಸಲಾಗಿದೆ** (#4012) — ಪ್ರತಿ ವಿವರಣೆಯು ವಿಫಲವಾದಾಗ ಕಾಂಬೊ ವಿವರಿಸುವ ಮಾರ್ಗದಲ್ಲಿ ಹೊರತುಪಡಿಸಿ, ಅಲ್ಲಿ ದೃಢೀಕರಿಸಿದ ವಿಷನ್-ಅಲ್ಲದ ಅಪ್ಸ್ಟ್ರೀಮ್ ಬದಲಿಗೆ `(ಲಭ್ಯವಿಲ್ಲ — ಯಾವುದೇ ವಿಷನ್-ಸಾಮರ್ಥ್ಯದ ಪೂರೈಕೆದಾರರು ಸಂಪರ್ಕಗೊಂಡಿಲ್ಲ)` ಸ್ಟಬ್ ಅನ್ನು ಪಡೆಯುತ್ತದೆ (#8430).
6. `modifiedPayload` + ಮೆಟಾ (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`) ಅನ್ನು ಹಿಂತಿರುಗಿಸಿ.

| `describe` |          | ಯಾವಾಗಲೂ ವಿವರಿಸಿ — ಮರುನಿರ್ದೇಶನ ಬ್ಲಾಕ್ ಅನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ; ಬಳಕೆದಾರರು ಆಯ್ಕೆ ಮಾಡಿದ ಮಾದರಿಯು ಯಾವಾಗಲೂ ಉತ್ತರಿಸುತ್ತದೆ.                                                                                                                                                                    |
| `reroute`  |          | ಬಲವಂತವಾಗಿ ಮರುನಿರ್ದೇಶಿಸಿ: ರುಜುವಾತು ಹೊಂದಿರುವ ಮಾದರಿ ಗಾರ್ಡ್ ಅನ್ನು ಬೈಪಾಸ್ ಮಾಡಲಾಗುತ್ತದೆ. ಮರುನಿರ್ದೇಶನ-**ಗುರಿ** ರುಜುವಾತು ಗಾರ್ಡ್ ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ — ಯಾವುದೇ ಬಳಸಬಹುದಾದ ವಿಷನ್ ಗುರಿ ಇಲ್ಲದಿದ್ದಾಗ, ವಿನಂತಿಯು ವಿವರಿಸಲು ಬೀಳುತ್ತದೆ ಆದ್ದರಿಂದ ಕಚ್ಚಾ ಚಿತ್ರಗಳು ಪಠ್ಯ-ಮಾತ್ರ ಬ್ಯಾಕೆಂಡ್ ಅನ್ನು ಎಂದಿಗೂ ತಲುಪುವುದಿಲ್ಲ (#8430). |

ಬಲವಂತದ ಮೋಡ್ಗಳು ಸ್ವಯಂ ಹ್ಯೂರಿಸ್ಟಿಕ್ ರನ್ ಆಗುವ **ಮೊದಲು** ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತವೆ; `auto` ವರ್ತನೆಯು PR-1 ಪೂರ್ವ ಗಾರ್ಡ್ರೈಲ್ಗೆ ಬೈಟ್-ಐಡೆಂಟಿಕಲ್ ಆಗಿದೆ.

#### ಕಾರ್ಯ-ಅರಿವಿನ ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್ (`modalityBridgeVisionTaskAware`)

ಡೀಫಾಲ್ಟ್ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ಮೂಲ ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್ಗೆ **ಕೊನೆಯ ಬಳಕೆದಾರ ಸಂದೇಶದ** ಪಠ್ಯವನ್ನು (500 ಅಕ್ಷರಗಳಿಗೆ ಕತ್ತರಿಸಲಾಗಿದೆ) ಸೇರಿಸುತ್ತದೆ, ಬಳಕೆದಾರರು ನಿಜವಾಗಿ ಕೇಳಿದ ಕಡೆಗೆ ವಿವರಣೆಯನ್ನು ನಿರ್ದೇಶಿಸುತ್ತದೆ (ಕೋಡೆಕ್ಸ್-ವಿಷನ್-ಪ್ರಾಕ್ಸಿ ಪ್ಯಾಟರ್ನ್) ಮತ್ತು ಗೋಚರಿಸುವ ಪಠ್ಯವನ್ನು ಲಿಪ್ಯಂತರ ಮಾಡಲು ವಿಷನ್ ಮಾದರಿಯನ್ನು ಕೇಳುತ್ತದೆ. ಫ್ಲ್ಯಾಗ್ ಆಫ್ ಆಗಿದ್ದರೆ — ಅಥವಾ ಬಳಕೆದಾರರ ಪಠ್ಯವಿಲ್ಲದಿದ್ದರೆ — ಮೂಲ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಬದಲಾಯಿಸದೆ ಬಳಸಲಾಗುತ್ತದೆ.

ಸ್ವಯಂ-ಲೂಪ್ನ ಸ್ವಂತ OpenAI-ಹೊಂದಾಣಿಕೆಯ ವಿನಂತಿಯನ್ನು ವಿವರಿಸಿ (`callVisionModelSingle()`
`visionBridgeHelpers.ts` ನಲ್ಲಿ) ಯಾವಾಗಲೂ `image_url.detail: "high"` ಅನ್ನು ವಿನಂತಿಸುತ್ತದೆ —
ಷರತ್ತುರಹಿತವಾಗಿ, ಪ್ರತಿ ಕರೆ ಮಾಡುವವರು/ಪೂರೈಕೆದಾರರಿಗೆ, ಯಾವುದೇ ಕ್ಲೈಂಟ್ ಸಿಗ್ನಲ್ನಲ್ಲಿ ಗೇಟ್ ಮಾಡಲಾಗಿಲ್ಲ.
ಕಡಿಮೆ-ವಿವರದ ಮಾದರಿಯು OCR ನಿಖರತೆಯನ್ನು ನಿಖರವಾಗಿ ಪಠ್ಯ-ಪ್ರತಿಕೃತಿಗಾಗಿ ಕಡಿಮೆ ಮಾಡುತ್ತದೆ
ಈ ಪ್ರಾಂಪ್ಟ್ ಕೇಳುವ ಕಾರ್ಯ, ಆದ್ದರಿಂದ ವಿವರಣೆ ಕರೆಯು ಯಾವಾಗಲೂ ಹೆಚ್ಚಿನದನ್ನು ಕೇಳುತ್ತದೆ
ಮೂಲ ಒಳಬರುವ ವಿನಂತಿಯು ಯಾವ ವಿವರ ಮಟ್ಟವನ್ನು ಬಳಸಿದೆ ಎಂಬುದನ್ನು ಲೆಕ್ಕಿಸದೆ ವಿವರ. ಇದು
ಆಂತರಿಕ ವಿವರಣೆ ವಿನಂತಿ ದೇಹದ ಮೇಲೆ ಮಾತ್ರ ಪರಿಣಾಮ ಬೀರುತ್ತದೆ; ಅದು ಹೇಗೆ ಎಂಬುದನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ
OmniRoute ಕರೆ ಮಾಡುವವರ ಸ್ವಂತ `image_url.detail` ಅನ್ನು ಪ್ರಾಥಮಿಕ ವಿನಂತಿಯ ಮೇಲೆ ಫಾರ್ವರ್ಡ್ ಮಾಡುತ್ತದೆ —
ಆ ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ಪತ್ತೆಯಾದ OpenCode ಕ್ಲೈಂಟ್ಗಳಿಗೆ ಮಾತ್ರ,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). ದಿ
ವಿವರಣೆ ಸ್ವಯಂ-ಲೂಪ್ನ ಆಂಥ್ರೋಪಿಕ್ ವೈರ್-ಫಾರ್ಮ್ಯಾಟ್ ಶಾಖೆಗೆ `detail` ಕ್ಷೇತ್ರವಿಲ್ಲ
ಮತ್ತು ಯಾವುದೇ ಡೀಫಾಲ್ಟ್ನಿಂದ ಪ್ರಭಾವಿತವಾಗುವುದಿಲ್ಲ.

#### ಔಟ್ಪುಟ್ ಕ್ಯಾಪ್ ವಿವರಿಸಿ (`modalityBridgeVisionMaxChars`)

| ಕೀಲಿ                           | ಡೀಫಾಲ್ಟ್ | ಶ್ರೇಣಿ             |
| ------------------------------ | -------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`      | `0` ಅಥವಾ 100–50000 |

`0` (ಡೀಫಾಲ್ಟ್) ಎಂದರೆ **ಕ್ಯಾಪ್ ಇಲ್ಲ** — `callVisionModel()` ನಿಂದ ಹಿಂತಿರುಗಿದ ವಿವರಣೆಯನ್ನು
ಮಾರ್ಪಡಿಸದೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಡವಳಿಕೆಯನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ.
100–50000 ಶ್ರೇಣಿಯಲ್ಲಿನ ಯಾವುದೇ ಮೌಲ್ಯವು `…` ಪ್ರತ್ಯಯದೊಂದಿಗೆ ವಿವರಣೆಯನ್ನು ಕಡಿತಗೊಳಿಸುತ್ತದೆ
ಅದನ್ನು `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()`
`src/lib/guardrails/visionBridge.ts` ನಲ್ಲಿ) ಎಂದು ಮರಳಿ ಸೇರಿಸುವ ಮೊದಲು.
ಡೌನ್ಸ್ಟ್ರೀಮ್ ಮಾದರಿಗೆ ಪೂರ್ಣ ಪ್ರತಿಲೇಖನ ಅಗತ್ಯವಿರುವ ವಿವರ-ಹೆಚ್ಚಿನ OCR ಕಾರ್ಯಗಳಿಗಾಗಿ ಇದನ್ನು ಹೆಚ್ಚಿಸಿ;
ಚಾಟಿ ವಿಷನ್ ಮಾದರಿಗಳಲ್ಲಿ ಟೋಕನ್ ಬಳಕೆಯನ್ನು ಮಿತಿಗೊಳಿಸಲು ಇದನ್ನು ಕಡಿಮೆ ಮಾಡಿ.
ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಕ್ಷೇತ್ರವು ವಿಷನ್ ಟ್ಯಾಬ್ನ ಸುಧಾರಿತ ಫಲಕದಲ್ಲಿ ವಾಸಿಸುತ್ತದೆ
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` ನಲ್ಲಿ) ಮತ್ತು
1 ಮತ್ತು 99 ರ ನಡುವಿನ ಯಾವುದೇ ಮೌಲ್ಯವನ್ನು 100 ಫ್ಲೋರ್ಗೆ ಕ್ಲ್ಯಾಂಪ್ ಮಾಡುತ್ತದೆ,
ಅದೇ ಸಮಯದಲ್ಲಿ ಸ್ಪಷ್ಟವಾದ `0` ಅನ್ನು ಮುಟ್ಟದೆ ಬಿಡುತ್ತದೆ — `0` ತನ್ನದೇ ಆದ ಮಾನ್ಯವಾದ Zod ಮೌಲ್ಯವಾಗಿದೆ
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`),
ಕೇವಲ "ಅನ್ಸೆಟ್" ಡೀಫಾಲ್ಟ್ ಅಲ್ಲ.

#### ಕ್ಯಾಶ್ ವಿವರಿಸಿ (`modalityBridge/bridgeCache.ts`)

ವಿವರಣೆ ಔಟ್ಪುಟ್ಗಳಿಗಾಗಿ ಇನ್-ಮೆಮೊರಿ LRU + TTL ಕ್ಯಾಶ್, ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪಕವಾಗಿ ಹಂಚಿಕೊಳ್ಳಲಾಗಿದೆ.
ಕೀ = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
ಉದ್ದ-ಪೂರ್ವಪ್ರತ್ಯಯ ಫ್ರೇಮಿಂಗ್ನೊಂದಿಗೆ (ಕ್ಷೇತ್ರ-ಗಡಿ ಘರ್ಷಣೆಗಳಿಲ್ಲ). ಮಾದರಿ ಘಟಕವು
**ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ** ಸೇತುವೆ ಮಾದರಿಯಾಗಿದೆ, ವಾಸ್ತವವಾಗಿ ಉತ್ತರಿಸಿದ ಮಾದರಿಯಲ್ಲ —
`callVisionModel` ಆಂತರಿಕವಾಗಿ ಹಿಂತಿರುಗಬಹುದು, ಮತ್ತು ಪ್ರತಿ ಪ್ರಯತ್ನಕ್ಕೆ ಕೀ ಮಾಡುವುದು
ಕ್ಯಾಶ್ ಅನ್ನು ವಿಭಜಿಸುತ್ತದೆ. ವಿಫಲವಾದ ವಿವರಣೆಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಸೆಟ್ಟಿಂಗ್ಗಳು:

| ಕೀಲಿ                            | ಡೀಫಾಲ್ಟ್ | ಶ್ರೇಣಿ  |
| ------------------------------- | -------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`   | —       |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000 |

#### ರಿಮೋಟ್ ಇಮೇಜ್ ನಾರ್ಮಲೈಸೇಶನ್ (ಸ್ವಯಂ-ಲೂಪ್ ವಿವರಣೆ/base64 ಫೆಚ್)

ಸೇತುವೆಯು **ರಿಮೋಟ್** ಚಿತ್ರವನ್ನು ತಾನೇ ಪಡೆದಾಗ — ಆಂಥ್ರೋಪಿಕ್ ವಿವರಣೆ
ಸ್ವಯಂ-ಕರೆ ಮತ್ತು ಕ್ಲೌಡ್-ವೈರ್-ಫಾರ್ಮ್ಯಾಟ್ base64 ಪರಿವರ್ತನೆ
(`ensureBase64ImagesForClaudeWire`), ಎರಡೂ `fetchRemoteImageAsDataUri()` ಮೂಲಕ
`visionBridgeHelpers.ts` ನಲ್ಲಿ — ಫಲಿತಾಂಶದ ಡೇಟಾ URI ಅನ್ನು `normalizeDataUri()` ಮೂಲಕ ರವಾನಿಸಲಾಗುತ್ತದೆ
(`open-sse/utils/imageNormalize.ts`) ವಿಷನ್-ಮಾದರಿ ವಿನಂತಿಯಲ್ಲಿ ಎಂಬೆಡ್ ಮಾಡುವ ಮೊದಲು.
ಅತಿಯಾದ ಗಾತ್ರದ ಚಿತ್ರಗಳನ್ನು **2048px ಉದ್ದದ ಅಂಚಿಗೆ** ಡೌನ್ಸ್ಕೇಲ್ ಮಾಡಲಾಗುತ್ತದೆ
(OpenAI/Anthropic ಈಗಾಗಲೇ ಸರ್ವರ್-ಸೈಡ್ನಲ್ಲಿ ಅನ್ವಯಿಸುವ ಮರುಗಾತ್ರಗೊಳಿಸುವ ಕ್ಯಾಪ್ಗೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ),
ಇದು ವಿಷನ್ ಮಾದರಿಯು ನೋಡುವದನ್ನು ಬದಲಾಯಿಸದೆ ಅಪ್ಲೋಡ್ ಬೈಟ್ಗಳು/ಲೇಟೆನ್ಸಿಯನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ.
ಮರುಗಾತ್ರಗೊಳಿಸುವಿಕೆಯು `sharp` ಅನ್ನು ಬಳಸುತ್ತದೆ, ಡೈನಾಮಿಕ್ ಆಮದು ಮೂಲಕ ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ:
ಅದರ ಸ್ಥಳೀಯ ಬೈನರಿ ಲೋಡ್ ಆಗಲು ವಿಫಲವಾದ ಪ್ಲಾಟ್ಫಾರ್ಮ್ನಲ್ಲಿ, `normalizeDataUri()`
**ಎಂದಿಗೂ ದೋಷವನ್ನು ಎಸೆಯುವುದಿಲ್ಲ** — ಅದು ಮೂಲ ಬೈಟ್ಗಳ ಪಾಸ್ಥ್ರೂಗೆ ಹಿಂತಿರುಗುತ್ತದೆ,
ಆದ್ದರಿಂದ ವಿವರಣೆ/base64-ಪರಿವರ್ತನೆ ಮಾರ್ಗವು ಯಾವಾಗಲೂ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.
ಚಿತ್ರವಲ್ಲದ ಬೈಟ್ಗಳು (ಡಿಕೋಡ್ ಮಾಡಬಹುದಾದ ಚಿತ್ರವನ್ನು ಹಿಂತಿರುಗಿಸದ ಫೆಚ್) ಸಹ ಮುಟ್ಟದೆ ರವಾನಿಸಲಾಗುತ್ತದೆ.
ಈ ನಾರ್ಮಲೈಸೇಶನ್ ಸೇತುವೆಯು ತನ್ನ ಸ್ವಂತ ಸ್ವಯಂ-ಕರೆಗಾಗಿ ಪಡೆಯುವ ಚಿತ್ರಗಳಿಗೆ ಸೀಮಿತವಾಗಿದೆ —
ಕರೆ ಮಾಡುವವರ ಕಚ್ಚಾ ಪಾಸ್ಥ್ರೂ ಪೇಲೋಡ್ಗೆ ಇದನ್ನು ಎಂದಿಗೂ ಅನ್ವಯಿಸಲಾಗುವುದಿಲ್ಲ,
ಆಯ್ಕೆ-ಮಾತ್ರ ರೂಪಾಂತರ ತತ್ವಕ್ಕೆ ಅನುಗುಣವಾಗಿ (ಹಾರ್ಡ್ ರೂಲ್ #20).

ಲೆಗಸಿ ಕೀಗಳು ಒಂದು ಬಿಡುಗಡೆ ಚಕ್ರಕ್ಕೆ ಓದುವ ಫಾಲ್ಬ್ಯಾಕ್ ಆಗಿ ಸ್ವೀಕರಿಸಲ್ಪಡುತ್ತವೆ.

#### ಪಾರದರ್ಶಕತೆ ಹೆಡರ್ + ಅಂಕಿಅಂಶಗಳು

ವಿವರಣೆ-ಪರಿವರ್ತಿತ ಪ್ರತಿಕ್ರಿಯೆಗಳು `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ಅನ್ನು ಹೊಂದಿರುತ್ತವೆ
(`modalityBridge/bridgeStats.ts` ನಲ್ಲಿ `buildModalityBridgeHeader()` ನಿಂದ ನಿರ್ಮಿಸಲಾಗಿದೆ,
`src/sse/handlers/chatHelpers.ts` ನಲ್ಲಿ `withModalityBridgeHeader()` ನಿಂದ ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಲಾಗಿದೆ).
ಮರುಮಾರ್ಗಗೊಳಿಸಿದ ವಿನಂತಿಗಳಿಗೆ **ಯಾವುದೇ** ಹೆಡರ್ ಸಿಗುವುದಿಲ್ಲ — ಪೇಲೋಡ್ ಮುಟ್ಟದೆ ಇತ್ತು ಮತ್ತು
ಮಾದರಿ ಸ್ವಾಪ್ ಪ್ರತಿಕ್ರಿಯೆ ದೇಹದ `model` ಕ್ಷೇತ್ರದಲ್ಲಿ ಈಗಾಗಲೇ ಗೋಚರಿಸುತ್ತದೆ.

`GET /api/modality-bridge/stats` (ನಿರ್ವಹಣೆ ದೃಢೀಕರಣ, `GET /api/settings` ನಂತೆಯೇ)
ಇನ್-ಮೆಮೊರಿ ಪ್ರತಿ-ಮೋಡಾಲಿಟಿ ಕೌಂಟರ್ಗಳನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio`, ಮತ್ತು
`video` ಗಾಗಿ. `averageLatencyMs` ತನ್ನ ಛೇದವಾಗಿ `latencySamples` ಅನ್ನು ಬಳಸುತ್ತದೆ,
ಎಲ್ಲಾ ಪ್ರಯತ್ನಗಳನ್ನಲ್ಲ; ಸಮಯವಿಲ್ಲದ ಕಾರ್ಯಾಚರಣೆಯು ಶೂನ್ಯ-ಮಿಲಿಸೆಕೆಂಡ್ ಮಾದರಿಯನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ.
`bridged` ಯಶಸ್ವಿ ಪರಿವರ್ತನೆಗಳಿಗೆ ಹಿಂದುಳಿದ-ಹೊಂದಾಣಿಕೆಯ ಅಲಿಯಾಸ್ ಆಗಿ ಉಳಿದಿದೆ;
ವಿಫಲ ಪ್ರಯತ್ನಗಳು ಅದನ್ನು ಹೆಚ್ಚಿಸುವುದಿಲ್ಲ.
ಪ್ರಕ್ರಿಯೆ ಮರುಪ್ರಾರಂಭದಲ್ಲಿ ಕೌಂಟರ್ಗಳು ವಿನ್ಯಾಸದ ಮೂಲಕ ಮರುಹೊಂದಿಸಲ್ಪಡುತ್ತವೆ
(ಟೆಲಿಮೆಟ್ರಿ, ಅಕೌಂಟಿಂಗ್ ಅಲ್ಲ).

#### ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಕಾನ್ಫಿಗರೇಶನ್

ಮೀಸಲಾದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪುಟವು
`/dashboard/settings/modality-bridge` ಆಗಿದೆ. ಇದರ URL-ವಿಳಾಸೀಯ `Vision`, `Audio`,
ಮತ್ತು `Video` ಟ್ಯಾಬ್ಗಳು `tab` ಮೌಲ್ಯವನ್ನು ಬದಲಾಯಿಸುವಾಗ ಪ್ರಶ್ನೆ ನಿಯತಾಂಕಗಳನ್ನು ಸಂರಕ್ಷಿಸುತ್ತವೆ.
ವಿಷನ್ ಟ್ಯಾಬ್ ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ, ಮೋಡ್, ಮಾದರಿ ಆಯ್ಕೆ (ಸ್ವಯಂಚಾಲಿತ
ಡೀಫಾಲ್ಟ್ ಸೇರಿದಂತೆ), ಕಾರ್ಯ-ಅರಿವಿನ ಪ್ರಾಂಪ್ಟಿಂಗ್, ಸುಧಾರಿತ ಸಮಯಾವಧಿ/ಚಿತ್ರ/ವಿವರಣೆ-ಉದ್ದ/ಕ್ಯಾಶ್
ಮಿತಿಗಳು, ರನ್ಟೈಮ್
ಕೌಂಟರ್ಗಳು ಮತ್ತು ಕಾವಲು ಕಾಯುವ ಮಾದರಿ ವಿನಂತಿಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. ಆಡಿಯೋ ಟ್ಯಾಬ್ ಸಹ ಲೈವ್ ಆಗಿದೆ: ಇದು
ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ, ಆಟೋ ಜೊತೆ STT-ಮಾತ್ರ ಮಾದರಿ ಪಿಕ್ಕರ್, ಸಮಯಾವಧಿ/ಗರಿಷ್ಠ-ಕ್ಲಿಪ್ ಮಿತಿಗಳು, ಆಡಿಯೋ
ಕೌಂಟರ್ಗಳು ಮತ್ತು `input_audio` ಮಾದರಿ ಪರೀಕ್ಷೆಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. ವೀಡಿಯೋ ಟ್ಯಾಬ್ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ: ಇದು
FFmpeg/ffprobe ರನ್ಟೈಮ್ ಸ್ಥಿತಿಯನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ — ನಾಲ್ಕು ಸ್ಪಷ್ಟ UI ಸ್ಥಿತಿಗಳಲ್ಲಿ ಒಂದು (`unknown` ಪ್ರೋಬ್ ಹಾರಾಟದಲ್ಲಿರುವಾಗ ಅಥವಾ ಪೂರ್ಣಗೊಳಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ, `restricted` ನಾನ್-ಲೂಪ್ಬ್ಯಾಕ್
ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಹೋಸ್ಟ್ನಲ್ಲಿ ಪ್ರೋಬ್ ಕ್ಲೈಂಟ್-ಸೈಡ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಟ್ಟಾಗ, `unavailable` ಒಮ್ಮೆ ಪ್ರೋಬ್ ಮಾಡಿದ ನಂತರ ಮತ್ತು ಕಾಣೆಯಾಗಿದೆ ಎಂದು ದೃಢಪಡಿಸಿದಾಗ, ಅಥವಾ FFmpeg/ffprobe ಆವೃತ್ತಿಗಳೊಂದಿಗೆ `available`) — ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ/ಮಾದರಿ/ಫ್ರೇಮ್/ವೀಡಿಯೋ/ಸಮಯಾವಧಿ ಮಿತಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ, ಮಾದರಿ ಪಿಕ್ಕರ್ ಅನ್ನು ವಿಷನ್-ಸಾಮರ್ಥ್ಯದ
ಮಾದರಿಗಳಿಗೆ ಫಿಲ್ಟರ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ವೀಡಿಯೋ ಕೌಂಟರ್ಗಳನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.

AI ಸೆಟ್ಟಿಂಗ್ಗಳ ಅಡಿಯಲ್ಲಿನ ಹಿಂದಿನ ವಿಷನ್ ಬ್ರಿಡ್ಜ್ ಕಾರ್ಡ್ ಹೊಸ ಪುಟಕ್ಕೆ ಹೊಂದಾಣಿಕೆಯ ಲಿಂಕ್ ಆಗಿದೆ;
ಇದು ಇನ್ನು ಮುಂದೆ ಫಾರ್ಮ್ನ ಎರಡನೇ ಪ್ರತಿಯನ್ನು ಹೊಂದಿಲ್ಲ. ಮೀಡಿಯಾ ಪ್ರೊವೈಡರ್ಗಳು ಸಹ
ಇಮೇಜ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಮತ್ತು ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ವರ್ಕ್ಫ್ಲೋಗಳನ್ನು ಅನುಗುಣವಾದ ಮೊಡಾಲಿಟಿ
ಬ್ರಿಡ್ಜ್ ಟ್ಯಾಬ್ಗಳಿಗೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಪ್ಲೇಗ್ರೌಂಡ್ ಅನ್ನು ತೆಗೆದುಹಾಕದೆ ಲಿಂಕ್ ಮಾಡುತ್ತದೆ.

**ಸ್ವಯಂ-ಲೂಪ್ ಪ್ರವೇಶ ಬೈಪಾಸ್:** OmniRoute ನ
ಸ್ವಂತ `/v1` ಸ್ವಯಂ-ಲೂಪ್ ಮೂಲಕ ವಿವರಣೆ ಕರೆ ಮಾರ್ಗಗಳನ್ನು (ಪ್ರಮಾಣಿತವಲ್ಲದ ಪೂರೈಕೆದಾರ ಮಾದರಿ), ಉಪ-ವಿನಂತಿಯು
`x-omniroute-admission-bypass: internal` ಅನ್ನು ಕಳುಹಿಸುತ್ತದೆ ಮತ್ತು ಪರಿಹರಿಸಿದ
ಸ್ವಯಂ-ಲೂಪ್ ರುಜುವಾತುಗಳೊಂದಿಗೆ ದೃಢೀಕರಿಸಲಾಗುತ್ತದೆ — ಸ್ಥಳೀಯ ಮೋಡ್ನಲ್ಲಿ ಸ್ಥಳೀಯ `sk_omniroute` ಸೆಂಟಿನೆಲ್, ಅಥವಾ
ಆಪರೇಟರ್-ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` ಎನ್ವಿ ಕೀ (#1350) ಆದ್ದರಿಂದ
`REQUIRE_API_KEY=true` ನಿಯೋಜನೆಗಳು ಇನ್ನೂ ವಿವರಣೆ ಕರೆಯನ್ನು ಚಲಾಯಿಸಬಹುದು. ಬೈಪಾಸ್
ಆ ನಿಖರವಾದ ರುಜುವಾತುಗಳಿಗೆ ಮಾತ್ರ ಗೌರವಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಬಾಹ್ಯ ಕ್ಲೈಂಟ್ಗಳು
ಪ್ರವೇಶವನ್ನು ಬಿಟ್ಟುಬಿಡಲು ಹೆಡರ್ ಅನ್ನು ಬಳಸಲಾಗುವುದಿಲ್ಲ.

ಲೆಗಸಿ ಡೀಫಾಲ್ಟ್ಗಳು `src/shared/constants/visionBridgeDefaults.ts` ನಲ್ಲಿವೆ;
ಹೊಸ ಮೋಡ್/ಕಾರ್ಯ-ಅರಿವಿನ/ಕ್ಯಾಶ್ ಡೀಫಾಲ್ಟ್ಗಳು ಮತ್ತು ಸೆಟ್ಟಿಂಗ್ಗಳ ರೆಸಲ್ಯೂವರ್
`src/shared/constants/modalityBridgeDefaults.ts` ನಲ್ಲಿವೆ. ಗಾರ್ಡ್ರೈಲ್
`deps` ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು ನಕಲಿ `getSettings` ಮತ್ತು
`callVisionModel` ಅನುಷ್ಠಾನಗಳನ್ನು ಇಂಜೆಕ್ಟ್ ಮಾಡಬಹುದು.

### ಆಡಿಯೋ ಬ್ರಿಡ್ಜ್ (`audioBridge.ts`) — ಮೊಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ PR-3

ಆಡಿಯೋ ಇನ್ಪುಟ್ ಅನ್ನು ಸ್ವೀಕರಿಸಲು ತಿಳಿದಿಲ್ಲದ ಗುರಿಯನ್ನು ತಲುಪುವ ಮೊದಲು ಆಡಿಯೋ-ಬೇರಿಂಗ್ ಚಾಟ್ ವಿನಂತಿಗಳನ್ನು ತಡೆಯುತ್ತದೆ.
ಇದು ಎಂದಿಗೂ ಚಾಟ್ ವಿನಂತಿಯನ್ನು ಮರುಮಾರ್ಗಗೊಳಿಸುವುದಿಲ್ಲ: ಆಡಿಯೋ ಭಾಗಗಳನ್ನು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OpenAI-ಹೊಂದಾಣಿಕೆಯ ಮಲ್ಟಿಪಾರ್ಟ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ ಲಿಪ್ಯಂತರ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು
ಆಯ್ಕೆಮಾಡಿದ ಚಾಟ್ ಮಾದರಿಯು ಪಠ್ಯ ಲಿಪ್ಯಂತರಗಳೊಂದಿಗೆ ಮುಂದುವರಿಯುತ್ತದೆ.

ಹರಿವು:

1. `getResolvedModelCapabilities()` ಮೂಲಕ `supportsAudio` ಅನ್ನು ಪರಿಹರಿಸಿ. ಸ್ಪಷ್ಟ
   ಪೂರೈಕೆದಾರ-ರಿಜಿಸ್ಟ್ರಿ ಮೆಟಾಡೇಟಾ ಗೆಲ್ಲುತ್ತದೆ, ನಂತರ ಸ್ಥಿರ ಮಾದರಿ ಮೆಟಾಡೇಟಾ, ನಂತರ ಸಿಂಕ್ ಮಾಡಿದ
   `modalities_input`. `audio` ಇಲ್ಲದ ಘೋಷಿತ ಇನ್ಪುಟ್ ಪಟ್ಟಿಯು `false`; ಯಾವುದೇ
   ಸಾಮರ್ಥ್ಯದ ಪುರಾವೆಗಳು `null` ಆಗಿ ಉಳಿಯುತ್ತವೆ. `false` ಮತ್ತು `null` ಎರಡೂ
   ಸಂಪ್ರದಾಯವಾದಿ ಸೇತುವೆಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ಆದರೆ `true` ಅದನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತದೆ.
2. `modalityBridgeAudio*` ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಪರಿಹರಿಸಿ ಮತ್ತು ಹಂಚಿದ `detectMediaParts()`
   ಡಿಟೆಕ್ಟರ್ ಮೂಲಕ ಪ್ರತಿ ಸಂದೇಶದಿಂದ ಸ್ಪ್ಲೈಸ್ ಮಾಡಬಹುದಾದ ಉನ್ನತ-ಮಟ್ಟದ ಆಡಿಯೋ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ.
   ಬೆಂಬಲಿತ ವೈರ್ ಆಕಾರಗಳು OpenAI `input_audio`, `audio_url`, ಮತ್ತು
   `source.media_type: "audio/*"` ಆಗಿವೆ. ನೆಸ್ಟೆಡ್ ಆಡಿಯೋವನ್ನು ರೂಟಿಂಗ್ಗಾಗಿ ಪತ್ತೆ ಮಾಡಲಾಗುತ್ತದೆ ಆದರೆ
   ಸ್ಪ್ಲೈಸ್ ಮಾರ್ಗದಿಂದ ತೆಗೆದುಹಾಕಲಾಗುವುದಿಲ್ಲ. ಕೆಲಸವನ್ನು `modalityBridgeAudioMaxClips` ನಿಂದ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ;
   ನಂತರದ ಭಾಗಗಳು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತವೆ.
3. ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ `provider/model` ಅನ್ನು ಗೌರವಿಸಿ, ಅಥವಾ `selectAudioBridgeModel()`
   `AUDIO_TRANSCRIPTION_PROVIDERS` ಅನ್ನು ಸ್ಥಿರ ಕ್ಯಾಟಲಾಗ್ ಕ್ರಮದಲ್ಲಿ ನಡೆಸಿ
   ಬಳಸಬಹುದಾದ ಸಕ್ರಿಯ ಪೂರೈಕೆದಾರ ರುಜುವಾತುಗಳೊಂದಿಗೆ ಮೊದಲ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಅವಕಾಶ ಮಾಡಿಕೊಡಿ.
4. `callAudioTranscription()` base64/data-URI ಆಡಿಯೋವನ್ನು ಮಲ್ಟಿಪಾರ್ಟ್
   `file` ಗೆ ಪರಿವರ್ತಿಸುತ್ತದೆ, ಅಥವಾ ಸಾರ್ವಜನಿಕ-ಮಾತ್ರ ಹೊರಹೋಗುವ
   ಗಾರ್ಡ್ ಮೂಲಕ DNS ಪಿನ್ನಿಂಗ್ ಮತ್ತು 25 MB ಮಿತಿಯೊಂದಿಗೆ ರಿಮೋಟ್ `audio_url` ಅನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುತ್ತದೆ.
   ನಂತರ ಅದು ಫೈಲ್ ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ ಮಾದರಿಯನ್ನು ಸ್ಥಳೀಯ `/v1/audio/transcriptions`
   ಸ್ವಯಂ-ಲೂಪ್ಗೆ POST ಮಾಡುತ್ತದೆ, `resolveSelfLoopBearer()` ನೊಂದಿಗೆ ದೃಢೀಕರಿಸಲಾಗುತ್ತದೆ.
   ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲಿಪ್ಯಂತರ ಮಾರ್ಗವು ಸಾಮಾನ್ಯ ರುಜುವಾತು ಹುಡುಕಾಟ, ಕೂಲ್ಡೌನ್/ರೇಟ್-ಲಿಮಿಟ್ ನಿರ್ವಹಣೆ,
   ಮತ್ತು ಪೂರೈಕೆದಾರ ರವಾನೆಯನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
5. ಯಶಸ್ವಿ ಕರೆಗಳು ತಮ್ಮ ಭಾಗಗಳನ್ನು `[Audio N]: <transcript>` ನೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತವೆ. ಕರೆಗಳು
   `Promise.allSettled` ನೊಂದಿಗೆ ಚಲಿಸುತ್ತವೆ: ವೈಯಕ್ತಿಕ ವೈಫಲ್ಯವು ಆ ಮೂಲ
   ಆಡಿಯೋ ಭಾಗವನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ (#4012 ಒಪ್ಪಂದ). ಪ್ರತಿ ಕರೆಯು ವಿಫಲವಾದರೆ ಮತ್ತು ಗುರಿಯು
   `supportsAudio === false` ಎಂದು ಸಾಬೀತಾದರೆ, ಭಾಗಗಳು
   `[Audio N]: (unavailable — no STT provider connected)` ಆಗುತ್ತವೆ (#8430 ಒಪ್ಪಂದ).
   ಅಜ್ಞಾತ ಗುರಿಗಾಗಿ (`null`), ಎಲ್ಲಾ-ವೈಫಲ್ಯದ ಫಲಿತಾಂಶವು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತದೆ.
   ಬಳಸಬಹುದಾದ STT ರುಜುವಾತು ಇಲ್ಲದ ಸಾಬೀತಾದ ಪಠ್ಯ-ಮಾತ್ರ ಗುರಿಯು ನೆಟ್ವರ್ಕ್ ಕರೆಯನ್ನು ನೀಡದೆ
   ಅದೇ ಸ್ಪಷ್ಟ ಸ್ಟಬ್ ಅನ್ನು ಪಡೆಯುತ್ತದೆ.

ಯಶಸ್ವಿ ಲಿಪ್ಯಂತರಗಳು ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪಿ ಮೊಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ LRU/TTL ಕ್ಯಾಶ್ ಅನ್ನು ಬಳಸುತ್ತವೆ. ಕೀಲಿಯು
ಆಡಿಯೋ ಉಲ್ಲೇಖ, ಸ್ಥಿರ `audio-transcription` ಕಾರ್ಯಾಚರಣೆ ಲೇಬಲ್,
ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ STT ಮಾದರಿಯನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ; ವೈಫಲ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ.
ಆಡಿಯೋ ಪ್ರಯತ್ನಗಳು ಹಂಚಿದ `bridged`, `cacheHits`, `failures`, ಮತ್ತು `lastUsedAt` ಕೌಂಟರ್ಗಳನ್ನು ನವೀಕರಿಸುತ್ತವೆ.
ಪರಿವರ್ತಿತ ಪ್ರತಿಕ್ರಿಯೆಗಳು
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ಅನ್ನು ಒಯ್ಯುತ್ತವೆ;
ಸ್ಪರ್ಶಿಸದ ವಿನಂತಿಗಳು ಆಡಿಯೋ ಬ್ರಿಡ್ಜ್ ವಿಭಾಗವನ್ನು ಪಡೆಯುವುದಿಲ್ಲ.

ರನ್ಟೈಮ್ ಸೆಟ್ಟಿಂಗ್ಗಳು DB-ಬೆಂಬಲಿತ ಮತ್ತು Zod-ಮೌಲ್ಯೀಕರಿಸಿದವು:

| ಕೀ                            | ಡೀಫಾಲ್ಟ್ | ಶ್ರೇಣಿ          |
| ----------------------------- | -------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`   | —               |
| `modalityBridgeAudioModel`    | `""`     | ಆಟೋ ಅಥವಾ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10            |

ಹಂಚಿದ ಕ್ಯಾಶ್ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ಮತ್ತು `modalityBridgeCacheMaxEntries` ನಿಂದ ನಿಯಂತ್ರಿಸಲ್ಪಡುತ್ತದೆ.

### ವೀಡಿಯೋ ಬ್ರಿಡ್ಜ್ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ಚಾಟ್ ಕಂಪ್ಲೀಷನ್ಸ್ `messages` ಮತ್ತು ರೆಸ್ಪಾನ್ಸಸ್ API `input` ನಲ್ಲಿ ಉನ್ನತ-ಮಟ್ಟದ ವೀಡಿಯೊ ಭಾಗಗಳನ್ನು ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಬೆಂಬಲವಿಲ್ಲದ ಗುರಿಯನ್ನು ಕರೆಯುವ ಮೊದಲು ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡುತ್ತದೆ.
ಬೆಂಬಲಿತ ಆಕಾರಗಳು `input_video`, `video_url`, `video_source`, HTTPS URL ಗಳು,
ಮತ್ತು `data:video/*;base64,...` ಡೇಟಾ URI ಗಳು. ಪಠ್ಯದಲ್ಲಿನ ಸರಳ ಫೈಲ್ ಹೆಸರುಗಳನ್ನು
ವೀಡಿಯೊ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ವಿನಂತಿಯ ಸಂಚಾರ,
ಸಾಮರ್ಥ್ಯ/ನೀತಿ ಪರಿಶೀಲನೆ, ಪ್ರತಿ-ವಿನಂತಿಯ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು
ನಿರ್ವಹಿಸುತ್ತದೆ. ಪ್ರತಿ-ವೀಡಿಯೊ ಕೆಲಸ — ಸ್ವಾಧೀನ, ಸಂಪೂರ್ಣ-ಫಲಿತಾಂಶದ ಸಂಗ್ರಹ, ಫ್ರೇಮ್
ಅನುಕ್ರಮವನ್ನು ವಿವರಿಸುವುದು (ಇದು ಯಾವುದೇ ಕರೆ ಮಾಡುವವರು ಘೋಷಿಸಿದ ಆಡಿಯೊ ಪ್ರತಿಲೇಖನವನ್ನು
ಸಂಯೋಜಿಸುತ್ತದೆ), ಮತ್ತು ಪ್ರತಿ-ಪ್ರಯತ್ನದ ಮೆಟ್ರಿಕ್ಗಳು/ಅಬಾರ್ಟ್/ಕ್ಲೀನಪ್ — `preCall` ನ ಲೂಪ್
ಒಳಗೆ ಪ್ರತಿ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಒಮ್ಮೆ ಕರೆಯಲಾಗುವ `videoBridgePipeline.ts` ನಲ್ಲಿ
`processVideoPart` ಹಿಂದೆ ಮರೆಮಾಡಲಾಗಿದೆ. ಆ ಮಾಡ್ಯೂಲ್ ಸ್ಪಷ್ಟ ಪೋರ್ಟ್ ಗಡಿಗಳನ್ನು
`VideoMediaBrokerPort` (ಬೈಟ್ಗಳನ್ನು ಪಡೆದುಕೊಳ್ಳುವುದು ಮತ್ತು ಮಾದರಿ ಫ್ರೇಮ್ಗಳನ್ನು
ಹೊರತೆಗೆಯುವುದು), `VideoAudioTranscriptionPort` (ಕರೆ ಮಾಡುವವರು ಘೋಷಿಸಿದ ಆಡಿಯೊ
ಪ್ರತಿಲೇಖನವನ್ನು ಮಾದರಿ ಶೀರ್ಷಿಕೆಗಳೊಂದಿಗೆ ಸಂಯೋಜಿಸುವುದು), ಮತ್ತು `VideoDrilldownPort`
(ಫ್ರೇಮ್ ಡ್ರಿಲ್ಡೌನ್ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಗಡಿ; `processVideoPart` ಗೆ ಇನ್ನೂ ವೈರ್ ಮಾಡಿಲ್ಲ —
ಇಂದು `/api/modality-bridge/video/drilldown` ಮಾರ್ಗ ಮಾತ್ರ ಡ್ರಿಲ್ಡೌನ್ ನಮೂದುಗಳನ್ನು
ಬರೆಯುತ್ತದೆ) ಅನ್ನು ಸಹ ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ.

ಸಾರ್ವಜನಿಕ `/v1` ವಿನಂತಿಯ ಮಾರ್ಗವು ಎಂದಿಗೂ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಆಮದು ಮಾಡಿಕೊಳ್ಳುವುದಿಲ್ಲ ಅಥವಾ
ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ. ರಿಮೋಟ್ ವೀಡಿಯೊಗಳನ್ನು 50 MiB ಮಿತಿಯ ಅಡಿಯಲ್ಲಿ ಡೌನ್ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ;
ಇನ್ಲೈನ್ ಬೇಸ್64 ವೀಡಿಯೊಗಳು ಪ್ರತಿ-ವೀಡಿಯೊಗೆ 36 MiB ಡಿಕೋಡ್ ಮಾಡಿದ ಸಂಪ್ರದಾಯವಾದಿ ಕ್ಯಾಪ್ ಅನ್ನು
ಹೊಂದಿವೆ, ಇದರಿಂದ ಮಾದರಿ/ಸಂದೇಶಗಳು/ಫ್ರೇಮಿಂಗ್ ಎನ್ವೆಲಪ್ 50 MiB ನ ಸಾರ್ವಜನಿಕ JSON
ವಿನಂತಿಯ ಪ್ರವೇಶ ಮಿತಿಯೊಳಗೆ ಉಳಿಯಬಹುದು. ಹಂಚಿಕೆ ಮಾಡುವ ಮೊದಲು ಇನ್ಲೈನ್ ಉದ್ದ ಮತ್ತು
ಡಿಕೋಡ್ ಮಾಡಿದ-ಗಾತ್ರದ ಅಂದಾಜುಗಳನ್ನು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. DNS ಪಿನ್ನಿಂಗ್ನೊಂದಿಗೆ
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಾರ್ವಜನಿಕ-ಮಾತ್ರ ಹೊರಹೋಗುವ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸಿಕೊಂಡು ಆರಂಭಿಕ ರಿಮೋಟ್ URL
ಮತ್ತು ಪ್ರತಿ ಮರುನಿರ್ದೇಶನದಲ್ಲಿ HTTPS ಅಗತ್ಯವಿದೆ. ನಂತರ ಬೈಟ್ಗಳು ನಿಖರವಾದ ಆಂತರಿಕ
`POST /api/modality-bridge/video/extract` ಬ್ರೋಕರ್ ಗಡಿಯನ್ನು ದಾಟುತ್ತವೆ. ಆ ಮಾರ್ಗವು
`LOCAL_ONLY` ಮತ್ತು `SPAWN_CAPABLE` ಎರಡೂ ಆಗಿದೆ, ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಗೆ ದೃಢೀಕರಿಸಿದ,
ವಿಶ್ವಾಸಾರ್ಹ-ಲೂಪ್ಬ್ಯಾಕ್ ವಿನಂತಿಯನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು ಎಂದಿಗೂ URL,
ಫೈಲ್ಸಿಸ್ಟಮ್ ಮಾರ್ಗ, ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದ ಅಥವಾ ಆರ್ಗ್ಯುಮೆಂಟ್ ಪಟ್ಟಿಯನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.
API ಬಾಡಿ-ಸೈಜ್ ಪೈಪ್ಲೈನ್ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ನ ಹೆಚ್ಚುತ್ತಿರುವ ಬಾಡಿ ರೀಡರ್ ಸ್ವತಂತ್ರವಾಗಿ 50
MiB ಬ್ರೋಕರ್ ಇನ್ಪುಟ್ ಕ್ಯಾಪ್ ಅನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಅದರ ಬೌಂಡೆಡ್ ಕ್ಯೂ ಒಂದು ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು
ಒಂದೇ ಸಮಯದಲ್ಲಿ ನಡೆಸುತ್ತದೆ, ನಾಲ್ಕು ಬಾಕಿ ಇರುವ ಕೆಲಸಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ ಮತ್ತು ಬಾಕಿ ಇರುವ
ಇನ್ಪುಟ್ ಅನ್ನು 100 MiB ಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ.

ಬ್ರೋಕರ್ ಒಳಗೆ, `ffprobe` ಖಾಸಗಿ ಸ್ಥಳೀಯ ಫೈಲ್ ಅನ್ನು ಓದುತ್ತದೆ; ಸ್ಥಿರ ಸ್ವರೂಪದ
ಅನುಮತಿ ಪಟ್ಟಿಯು ಪ್ಲೇಲಿಸ್ಟ್ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್ ಸ್ವರೂಪಗಳನ್ನು ಹೊರತುಪಡಿಸುತ್ತದೆ.
ಅನುಮತಿಸಲಾದ MOV-ಕುಟುಂಬದ ಕಂಟೇನರ್ಗಳಿಗಾಗಿ, ಬಾಹ್ಯ MOV ಡೇಟಾ ಉಲ್ಲೇಖಗಳು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ
ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತವೆ ಮತ್ತು ಸ್ಥಿರ ಆಜ್ಞೆಯು ಅವುಗಳನ್ನು ಆಯ್ಕೆ ಮಾಡುವುದಿಲ್ಲ. `ffprobe` ಮತ್ತು
`ffmpeg` ಎರಡೂ `file`-ಮಾತ್ರ ಪ್ರೋಟೋಕಾಲ್ ವೈಟ್ಲಿಸ್ಟ್, ಒಂದು ಥ್ರೆಡ್, ಸ್ಥಿರ ಆರ್ಗ್ಯುಮೆಂಟ್
ಅರೇಗಳು, ಶೆಲ್ ಇಲ್ಲದೆ ಮತ್ತು `PATH` ನಿಂದ ಪರಿಹರಿಸಲಾದ ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದವುಗಳನ್ನು ಬಳಸುತ್ತವೆ.
ಲಗತ್ತಿಸಲಾದ-ಚಿತ್ರದ ಕವರ್ ಸ್ಟ್ರೀಮ್ಗಳು ಪ್ಲೇ ಮಾಡಬಹುದಾದ ಅಭ್ಯರ್ಥಿಗಳಲ್ಲ. ಎಲ್ಲಾ ಪ್ಲೇ ಮಾಡಬಹುದಾದ
ಸ್ಟ್ರೀಮ್ಗಳು ಮಿತಿಗಳನ್ನು ಪೂರೈಸಬೇಕು, ಮತ್ತು ನಿರ್ದಿಷ್ಟ ಡೀಫಾಲ್ಟ್ ಸ್ಟ್ರೀಮ್ ಅನ್ನು
ನಿರ್ಣಾಯಕ ಕಡಿಮೆ-ಸೂಚ್ಯಂಕದ ಫಾಲ್ಬ್ಯಾಕ್ಗಿಂತ ಮೊದಲು ಆದ್ಯತೆ ನೀಡಲಾಗುತ್ತದೆ. ವೀಡಿಯೊಗಳನ್ನು
600 ಸೆಕೆಂಡುಗಳು, ಪ್ರತಿ ಆಯಾಮಕ್ಕೆ 8,192 ಪಿಕ್ಸೆಲ್ಗಳು ಮತ್ತು 33,554,432 ಮೂಲ ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ
ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ. FFmpeg 1–16 ಮಧ್ಯಬಿಂದು JPEG ಫ್ರೇಮ್ಗಳನ್ನು ಮಾದರಿ ಮಾಡುತ್ತದೆ,
ಸಣ್ಣ ಇನ್ಪುಟ್ಗಳನ್ನು ಅಪ್ಸ್ಕೇಲ್ ಮಾಡದೆ ಉದ್ದನೆಯ ಅಂಚನ್ನು ಗರಿಷ್ಠ 1,024 ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ
ಸ್ಕೇಲ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಎಂದಿಗೂ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಮಾದರಿ ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ
`uniform` ಆಗಿದೆ. ಐಚ್ಛಿಕ `scene_aware` ಮತ್ತು ಪ್ರಾಯೋಗಿಕ `segment_aware` ನೀತಿಗಳು
ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಿದ ಸ್ಥಳೀಯ ಸ್ಟ್ರೀಮ್ನಲ್ಲಿ ಒಂದು ಹೆಚ್ಚುವರಿ ಸ್ಥಿರ FFmpeg ಪಾಸ್ ಅನ್ನು
ನಿರ್ವಹಿಸುತ್ತವೆ, ಬೌಂಡೆಡ್ `showinfo` ದೃಶ್ಯ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ಗಳನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತವೆ ಮತ್ತು
ಡಿಟೆಕ್ಟರ್ ವೈಫಲ್ಯ, ಸಮಯ ಮೀರಿದ, ತಪ್ಪಾದ ಔಟ್ಪುಟ್ ಅಥವಾ ಖಾಲಿ ಅಭ್ಯರ್ಥಿ ಸೆಟ್ನಲ್ಲಿ
ಅದೇ ಏಕರೂಪದ ಮಧ್ಯಬಿಂದುಗಳಿಗೆ ನಿರ್ಣಾಯಕವಾಗಿ ಹಿಂತಿರುಗುತ್ತವೆ. ವಿಭಾಗ-ಅರಿವಿನ ಮೋಡ್
ಮಧ್ಯಬಿಂದು ಮಾದರಿಗಳನ್ನು ಮೌಲ್ಯೀಕರಿಸಿದ ದೃಶ್ಯ ಮಧ್ಯಂತರಗಳಿಗೆ ಅನುಪಾತದಲ್ಲಿ ಹಂಚುತ್ತದೆ;
ವಿಭಾಗ-ಅರಿವಿನ ಪುರಾವೆ ಮತ್ತು ಫಾಲ್ಬ್ಯಾಕ್ ನಡವಳಿಕೆಯನ್ನು ಕೆಳಗೆ ವಿವರಿಸಲಾಗಿದೆ.
ಪ್ರತಿ ನೀತಿಯಲ್ಲಿ ಆಯ್ಕೆಯ ನಂತರ ಕಠಿಣ 16-ಫ್ರೇಮ್ ಕ್ಯಾಪ್ ಅನ್ನು ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.
ದೃಶ್ಯ-ಅರಿವಿನ ವಿನಂತಿಯು ಕೇವಲ ಒಂದು-ಫ್ರೇಮ್ ಬಜೆಟ್ ಹೊಂದಿರುವಾಗ, ಅದು ಸಕ್ರಿಯ ಪೂರ್ಣ-ವೀಡಿಯೊ
ಅಥವಾ ಫೋಕಸ್ ವಿಂಡೋದ ಏಕರೂಪದ ಮಧ್ಯಬಿಂದುವನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು `policyEffective: uniform`
ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ: ಒಂದೇ ಆಯ್ಕೆಮಾಡಿದ ದೃಶ್ಯ ಫ್ರೇಮ್ ಎರಡೂ ತಾತ್ಕಾಲಿಕ ತುದಿಗಳನ್ನು
ಸಂರಕ್ಷಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಕರೆ ಮಾಡುವವರು ಐಚ್ಛಿಕವಾಗಿ ಸೀಮಿತ ಫೋಕಸ್ ವಿಂಡೋವನ್ನು
(`start`/`end` ಸೆಕೆಂಡುಗಳು) ಒದಗಿಸಬಹುದು; ಗಡಿಗಳನ್ನು ಮಾಧ್ಯಮದ ಅವಧಿಗೆ ಕ್ಲ್ಯಾಂಪ್
ಮಾಡಲಾಗುತ್ತದೆ, ಹಿಮ್ಮುಖ ಅಥವಾ ಅನಂತ ವಿಂಡೋಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಎಲ್ಲಾ
ಮಾದರಿ ನೀತಿಗಳನ್ನು ಸಾಮಾನ್ಯೀಕರಿಸಿದ ಮಧ್ಯಂತರದೊಳಗೆ ಮಾತ್ರ ನಿರ್ವಹಿಸಲಾಗುತ್ತದೆ.
ಪರಿಣಾಮವಾಗಿ ಬರುವ ವಿಂಡೋವನ್ನು ಮಾದರಿ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ವಿವರಣೆಯ
ಪೂರ್ವಪ್ರತ್ಯಯದಲ್ಲಿ ಸೇರಿಸಲಾಗುತ್ತದೆ, ಇದರಿಂದ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಮಾದರಿಗಳು ಪೂರ್ಣ ಟೈಮ್ಲೈನ್ನಿಂದ
ಕೇಂದ್ರೀಕೃತ ಆಯ್ದ ಭಾಗವನ್ನು ಪ್ರತ್ಯೇಕಿಸಬಹುದು.

ಶಬ್ದಾರ್ಥದ ಶೀರ್ಷಿಕೆ ಗಮನವು ಪ್ರತ್ಯೇಕ, ಸ್ಪಷ್ಟವಾದ ಸೆಟ್ಟಿಂಗ್ ಆಗಿದೆ. ಡೀಫಾಲ್ಟ್ `full`
ವಿಶ್ಲೇಷಣೆ ಮೋಡ್ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಫ್ರೇಮ್ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ ಮತ್ತು
ಶೀರ್ಷಿಕೆ ಮಾದರಿಗೆ ವಿನಂತಿಯ ಪಠ್ಯವನ್ನು ಎಂದಿಗೂ ಫಾರ್ವರ್ಡ್ ಮಾಡುವುದಿಲ್ಲ. `focused`
ಮೋಡ್ನಲ್ಲಿ, ಸೇತುವೆಯು ಅದೇ ಚಾಟ್ ಅಥವಾ ಪ್ರತಿಕ್ರಿಯೆಗಳ ಕಂಟೇನರ್ನಿಂದ ಇತ್ತೀಚಿನ
ಖಾಲಿಯಲ್ಲದ ಬಳಕೆದಾರ-ರಚಿಸಿದ `text`/`input_text` ಅನ್ನು ಮಾತ್ರ ಓದುತ್ತದೆ, ಅದನ್ನು NFC ಗೆ
ಸಾಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ, ನಿಯಂತ್ರಣ ಅಕ್ಷರಗಳು ಮತ್ತು ವೈಟ್ಸ್ಪೇಸ್ ಅನ್ನು ಕುಗ್ಗಿಸುತ್ತದೆ ಮತ್ತು
ಅದನ್ನು 500 ಯೂನಿಕೋಡ್ ಕೋಡ್ ಪಾಯಿಂಟ್ಗಳಿಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ. ಖಾಲಿ ಫಲಿತಾಂಶವು ನಿಖರವಾದ
`full` ಪ್ರಾಂಪ್ಟ್ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ. ಬಳಸಬಹುದಾದ ಸುಳಿವನ್ನು ಮೀಸಲಾದ ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ-ಬಳಕೆದಾರ-ಸಂದರ್ಭ
ಬ್ಲಾಕ್ನಲ್ಲಿ JSON ಆಗಿ ಸರಣೀಕರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಗಮನಿಸಬಹುದಾದ ವಿವರಗಳಿಗೆ ಮಾತ್ರ ಆದ್ಯತೆ
ನೀಡಬಹುದು; ಇದು ಮಾಧ್ಯಮದಲ್ಲಿ ಗೋಚರಿಸುವ ಅಥವಾ ಕೇಳಿಸುವ ಸೂಚನೆಗಳನ್ನು ಅನುಸರಿಸುವ ವಿರುದ್ಧದ
ಪ್ರತ್ಯೇಕ ಎಚ್ಚರಿಕೆಯನ್ನು ಅತಿಕ್ರಮಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪಠ್ಯದ ಗಮನವು ಎಂದಿಗೂ `start`/`end`
ಅನ್ನು ಊಹಿಸುವುದಿಲ್ಲ ಅಥವಾ ತಾತ್ಕಾಲಿಕ ಮಾದರಿಯನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

#### FU-07 ರಚನಾತ್ಮಕ ವಿಭಾಗದ ಪುರಾವೆ

`segment_aware` ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಿದ ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಸ್ಟ್ರೀಮ್ನಲ್ಲಿ ಒಂದು ಬೌಂಡೆಡ್
ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆ ಪಾಸ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಸ್ಥಿರ ಫಿಲ್ಟರ್ ಚೈನ್ ಮೊದಲು ಗರಿಷ್ಠ 320 ಪಿಕ್ಸೆಲ್ಗಳ
ಅಗಲಕ್ಕೆ ಸ್ಕೇಲ್ ಮಾಡುತ್ತದೆ, ದೃಶ್ಯ ಬದಲಾವಣೆಗಳು ಮತ್ತು ಹೆಪ್ಪುಗಟ್ಟಿದ ಮಧ್ಯಂತರಗಳನ್ನು
ಪತ್ತೆ ಮಾಡುತ್ತದೆ, ನಂತರ ಮಸುಕು, ಸರಾಸರಿ ಲೂಮಾ ಮತ್ತು ಪ್ರಾದೇಶಿಕ/ತಾತ್ಕಾಲಿಕ ಮಾಹಿತಿಗಾಗಿ
ಪ್ರತಿ ಸೆಕೆಂಡಿಗೆ 1 ಫ್ರೇಮ್ನಲ್ಲಿ ಮಾದರಿ ಮಾಡುತ್ತದೆ. ಪಾಸ್ ಅನ್ನು 600 ರಚನಾತ್ಮಕ ಮಾದರಿಗಳು,
ಒಂದು FFmpeg/ಫಿಲ್ಟರ್ ಥ್ರೆಡ್, ಅದೇ `file`-ಮಾತ್ರ ಪ್ರೋಟೋಕಾಲ್ ಮತ್ತು ಕಂಟೇನರ್ ಅನುಮತಿ ಪಟ್ಟಿಗಳು,
1 MiB ಪ್ರಕ್ರಿಯೆ-ಔಟ್ಪುಟ್ ಮಿತಿ ಮತ್ತು ಬ್ರೋಕರ್ನ ಹಂಚಿದ ಅಬಾರ್ಟ್/ಡೆಡ್ಲೈನ್ ಒಳಗೆ ಗರಿಷ್ಠ
30 ಸೆಕೆಂಡುಗಳಿಗೆ ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ. ಇದು ವಿನಂತಿಯಿಂದ ಆಜ್ಞೆ, ಫಿಲ್ಟರ್, ಮಾರ್ಗ ಅಥವಾ URL
ಅನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

ರಚನಾತ್ಮಕ ಮೌಲ್ಯಗಳು ನಿರ್ಣಾಯಕ ಮಾದರಿ ಪುರಾವೆಗಳಾಗಿವೆ, ಶಬ್ದಾರ್ಥದ ವೀಡಿಯೊ ತಿಳುವಳಿಕೆಯಲ್ಲ. ಅವು ವಿಷಯಗಳು, ಕ್ರಿಯೆಗಳು, ಶೀರ್ಷಿಕೆಗಳು, ಭಾಷಣ ಅಥವಾ ಬಳಕೆದಾರರ ಉದ್ದೇಶವನ್ನು ಊಹಿಸುವುದಿಲ್ಲ. ದೃಶ್ಯ ಮತ್ತು ಫ್ರೀಜ್ ಗಡಿಗಳು ವಿಭಾಗಗಳನ್ನು ರೂಪಿಸುತ್ತವೆ; ಫ್ರೀಜ್ ವ್ಯಾಪ್ತಿ, ಮಸುಕು, ಎಕ್ಸ್ಪೋಸರ್, ಪ್ರಾದೇಶಿಕ ವಿವರ ಮತ್ತು ತಾತ್ಕಾಲಿಕ ಬದಲಾವಣೆಯು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ 1-16 ಫ್ರೇಮ್ ಬಜೆಟ್ ಅನ್ನು ಹೇಗೆ ಹಂಚಲಾಗುತ್ತದೆ ಎಂಬುದನ್ನು ಮಾತ್ರ ಪ್ರಭಾವಿಸುತ್ತದೆ. ಸಂಪೂರ್ಣವಾಗಿ ಫ್ರೀಜ್ ಮಾಡಿದ ವಿಭಾಗವನ್ನು ಒಂದು ಫ್ರೇಮ್ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಫ್ರೀಜ್ ಮಾಡದ ವಿಭಾಗಗಳು ಉಳಿದ ಬಜೆಟ್ಗಾಗಿ ಸ್ಪರ್ಧಿಸುತ್ತವೆ. ಗಡಿಗಳು ಫ್ರೇಮ್ಗಳಿಗಿಂತ ಹೆಚ್ಚಾದಾಗ, ಏಕರೂಪದ ಟೈಮ್ಲೈನ್ ವ್ಯಾಪ್ತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ, ಇದರಿಂದಾಗಿ ವೇಗದ ಆರಂಭಿಕ ಕಡಿತಗಳು ದೀರ್ಘವಾದ ಹಿಂದುಳಿದ ವಿಭಾಗವನ್ನು ಮರೆಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಫ್ರೀಜ್ ಗಡಿಯ 1-ಸೆಕೆಂಡ್ ವಿಶ್ಲೇಷಣೆಯ ರೆಸಲ್ಯೂಶನ್ನಲ್ಲಿನ ದೃಶ್ಯ ಗಡಿಗಳನ್ನು ಒಗ್ಗೂಡಿಸಲಾಗುತ್ತದೆ.

ಕಾಣೆಯಾದ ಫಿಲ್ಟರ್ಗಳು, ತಪ್ಪಾಗಿ ರೂಪುಗೊಂಡ/ಖಾಲಿ ಪುರಾವೆಗಳು, ಡಿಟೆಕ್ಟರ್ ದೋಷ ಅಥವಾ ಬೌಂಡೆಡ್ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯ ಸಮಯ ಮೀರುವಿಕೆಯು ನಿಖರವಾದ ಏಕರೂಪದ ಮಧ್ಯಬಿಂದು ನೀತಿಗೆ ತೆರೆದುಕೊಳ್ಳುತ್ತದೆ. ಕರೆ ಮಾಡುವವರ ಅಬಾರ್ಟ್ ಅಥವಾ ಬ್ರೋಕರ್ ಗಡುವು ತೆರೆದುಕೊಳ್ಳುವುದಿಲ್ಲ: ಇದು ಇನ್-ಫ್ಲೈಟ್ ಸಬ್ಪ್ರೊಸೆಸ್ ಅನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ, ನಂತರದ ಫ್ರೇಮ್ ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು ತಡೆಯುತ್ತದೆ ಮತ್ತು ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಟ್ರೀ ಅನ್ನು `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ.

`scripts/perf/video-bridge-fu07-eval.ts` ಪೋಸ್ಟ್-ಡಿಡಪ್ ಶೀರ್ಷಿಕೆ-ಕರೆ ಉಳಿತಾಯ, ದಟ್ಟ-ಚಲನೆಯ ಬಜೆಟ್ ಹಂಚಿಕೆ, ಮಸುಕು/ಎಕ್ಸ್ಪೋಸರ್/SI-TI ಪುರಾವೆ, ದೀರ್ಘ ಬಾಲದೊಂದಿಗೆ ವೇಗದ ಕಡಿತಗಳು ಮತ್ತು ಕ್ರಮೇಣ-ಮಸುಕಾಗುವ ಸುಳ್ಳು ಧನಾತ್ಮಕತೆಗಳಿಗಾಗಿ ನಿರ್ಣಾಯಕ ನೈಜ FFmpeg ಫಿಕ್ಚರ್ಗಳನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ. ಇದು ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯ ವಾಲ್ ಸಮಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು, `/usr/bin/time` ಲಭ್ಯವಿದ್ದಲ್ಲಿ, ಚೈಲ್ಡ್ CPU ಮತ್ತು ಪೀಕ್ RSS ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಇದರ ಗುಣಮಟ್ಟದ ಪರಿಶೀಲನೆಗಳು ರಚನಾತ್ಮಕ ಒರಾಕಲ್ಗಳು ಮಾತ್ರ. ನೈಜ ಶೀರ್ಷಿಕೆ-ಮಾದರಿ ಗುಣಮಟ್ಟವು `HOLD` ಆಗಿ ಉಳಿದಿದೆ ಏಕೆಂದರೆ ಈ ಹಾರ್ನೆಸ್ ಅಧಿಕೃತ ಎಂಡ್ಪಾಯಿಂಟ್ ಅಥವಾ ಫ್ರೀಜ್ ಮಾಡಿದ ನ್ಯಾಯಾಧೀಶರನ್ನು ಹೊಂದಿಲ್ಲ. `--caption-cost-per-call-usd` ಸ್ಪಷ್ಟವಾದ ಧನಾತ್ಮಕ ಪ್ರತಿ-ಕರೆ ಅಂದಾಜನ್ನು ಒದಗಿಸದ ಹೊರತು ಹಣಕಾಸಿನ ಉಳಿತಾಯವೂ `HOLD` ಆಗಿ ಉಳಿದಿದೆ; ಸ್ಕ್ರಿಪ್ಟ್ ಎಂದಿಗೂ ಎರಡೂ ಫಲಿತಾಂಶಗಳನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ.

ಪ್ರತಿ ಫ್ರೇಮ್ ಅನ್ನು 4 MiB ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ, ಎಲ್ಲಾ ಕಚ್ಚಾ ಫ್ರೇಮ್ಗಳನ್ನು ಒಟ್ಟಾಗಿ 23 MiB ಗೆ, ಮತ್ತು ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಬ್ರೋಕರ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು 32 MiB ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ. ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಡೈರೆಕ್ಟರಿಯನ್ನು `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ. OmniRoute FFmpeg ಅನ್ನು ಬಂಡಲ್ ಮಾಡುವುದಿಲ್ಲ ಮತ್ತು ಕಸ್ಟಮ್ ಎಕ್ಸಿಕ್ಯೂಟಬಲ್ ಮಾರ್ಗವನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಶೀರ್ಷಿಕೆ ಮಾಡುವ ಮೊದಲು, ಸೇತುವೆಯು ಸಂಪ್ರದಾಯವಾದಿ ದೃಶ್ಯ ಡಿಡ್ಯೂಪ್ಲಿಕೇಶನ್ ಪಾಸ್ ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ: ಪ್ರತಿ JPEG ಅನ್ನು 16×16 ಗ್ರೇಸ್ಕೇಲ್ ಬಫರ್ಗೆ ಇಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಉಳಿಸಿಕೊಂಡ ಕೊನೆಯ ಫ್ರೇಮ್ನೊಂದಿಗೆ ಮಾತ್ರ ಹೋಲಿಸಲಾಗುತ್ತದೆ. ಒಂದು ಫ್ರೇಮ್ಗಿಂತ ಹೆಚ್ಚಿನ ವಿನಂತಿಸಿದ ಶೀರ್ಷಿಕೆ ಬಜೆಟ್ಗಾಗಿ, ಹೊರತೆಗೆಯುವಿಕೆಯು ಆ ಬಜೆಟ್ನ ಎರಡು ಪಟ್ಟು ಮತ್ತು 16 ಫ್ರೇಮ್ಗಳಿಗಿಂತ ಹೆಚ್ಚಿಲ್ಲದ ಬೌಂಡೆಡ್ ಕ್ಯಾಂಡಿಡೇಟ್ ಪೂಲ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ. ವಿನಂತಿಸಿದ ಕ್ಯಾಪ್ ಅನ್ನು ಡಿಡ್ಯೂಪ್ಲಿಕೇಶನ್ ನಂತರ ಮಾತ್ರ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ, ಬಜೆಟ್ ಕನಿಷ್ಠ ಎರಡಾಗಿದ್ದಾಗ ಅಂತಿಮ ತೆಳುವಾಗಿಸುವಿಕೆಯ ಸಮಯದಲ್ಲಿ ಮೊದಲ ಮತ್ತು ಅಂತಿಮ ಆಯ್ಕೆಮಾಡಿದ ಕ್ಯಾಂಡಿಡೇಟ್ಗಳನ್ನು ಸಂರಕ್ಷಿಸಲಾಗುತ್ತದೆ. ಆವೃತ್ತಿಯ `grayscale-16x16-mean-cells-v2` ನೀತಿಯು ಸರಾಸರಿ ಲೂಮಾ ಡೆಲ್ಟಾ ಮತ್ತು ಥಂಬ್ನೇಲ್ ಸೆಲ್ಗಳ ಅನುಪಾತದಲ್ಲಿ ದೊಡ್ಡದನ್ನು ಬಳಸುತ್ತದೆ, ಅದರ ಸಾಮಾನ್ಯೀಕರಿಸಿದ ಡೆಲ್ಟಾ ಕನಿಷ್ಠ 0.05 ಆಗಿದೆ. ನಕಲು ಮಿತಿ ಸ್ಥಿರ 0.04 ಆಗಿದೆ, ಇದನ್ನು ರನ್ಟೈಮ್ ಸೆಟ್ಟಿಂಗ್ನಂತೆ ಬಹಿರಂಗಪಡಿಸುವುದಕ್ಕಿಂತ ಹೆಚ್ಚಾಗಿ ಊಹಿಸುವಿಕೆಗಾಗಿ ಆಯ್ಕೆಮಾಡಲಾಗಿದೆ. ಈ ದ್ವಿತೀಯಕ ಹೆಚ್ಚಿನ-ಕಾಂಟ್ರಾಸ್ಟ್ ಸಿಗ್ನಲ್ ಸಣ್ಣ ಚಲನೆ ಮತ್ತು ಗೋಚರ-ಪಠ್ಯ ಬದಲಾವಣೆಗಳನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ, ಅದನ್ನು ಸರಾಸರಿ-ಮಾತ್ರ ಹೋಲಿಕೆ ಮರೆಮಾಡಬಹುದು. ಹೋಲಿಕೆದಾರ ಅಥವಾ ಡಿಕೋಡರ್ ದೋಷಗಳು ತೆರೆದುಕೊಳ್ಳುತ್ತವೆ ಮತ್ತು ವ್ಯಾಪ್ತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಔಟ್ಪುಟ್ ಮೆಟಾಡೇಟಾ ಹೊರತೆಗೆದ ಕ್ಯಾಂಡಿಡೇಟ್ಗಳು, ಯಶಸ್ವಿಯಾಗಿ ಬಳಸಿದ ಫ್ರೇಮ್ಗಳು ಮತ್ತು ಕೈಬಿಟ್ಟ ದೃಶ್ಯ ನಕಲುಗಳನ್ನು ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ.

ಸ್ಪಷ್ಟವಾಗಿ ಗುರುತಿಸಲಾದ ವೀಡಿಯೊ ಭಾಗವು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಮಾಡಿದ ಸಂಪರ್ಕ ಹಾಳೆಯನ್ನು ವಿನಂತಿಸಬಹುದು. ಸೇತುವೆಯು ಗರಿಷ್ಠ 4-ಕಾಲಮ್, 16-ಫ್ರೇಮ್ JPEG ಗ್ರಿಡ್ ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ. ಪ್ರತಿ 512-ಪಿಕ್ಸೆಲ್ ಸೆಲ್ ತನ್ನ ಮೂಲ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಹೆಚ್ಚಿನ-ಕಾಂಟ್ರಾಸ್ಟ್ ಬಾಟಮ್ ಬ್ಯಾಂಡ್ಗೆ ಸುಡುತ್ತದೆ, ಆದರೆ ಅದೇ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ಗಳು ಡೌನ್ಸ್ಟ್ರೀಮ್ ಸಂಯೋಜನೆ ಮತ್ತು ಆಡಿಟ್ಗಾಗಿ ಪಠ್ಯ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಉಳಿಯುತ್ತವೆ. ಸಂಪೂರ್ಣ JPEG 32 MiB ಗೆ ಸೀಮಿತವಾಗಿರುತ್ತದೆ. `sharp` ಗ್ರಿಡ್ ಅನ್ನು ಡಿಕೋಡ್ ಮಾಡಲು ಅಥವಾ ಸಂಯೋಜಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ, ಸೇತುವೆಯು ವೈಯಕ್ತಿಕ JPEG ಫ್ರೇಮ್ಗಳಿಗೆ ಹಿಂತಿರುಗುತ್ತದೆ; ಕ್ಲೈಂಟ್ ಅಬಾರ್ಟ್ ಇನ್ನೂ ಶೀಟ್ ಕಾರ್ಯಾಚರಣೆಯ ಮೂಲಕ ಪ್ರಸಾರವಾಗುತ್ತದೆ.

ಪ್ರಚಾರದ ಪುರಾವೆಗಳು ಸಂಶ್ಲೇಷಿತ ಸಂಯೋಜನೆಯ ಮೈಕ್ರೋಬೆಂಚ್ಮಾರ್ಕ್ನಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿವೆ. `scripts/perf/video-bridge-contact-sheet-eval.ts` ನೈಜ OpenAI-ಹೊಂದಾಣಿಕೆಯ ದೃಷ್ಟಿ ಮಾದರಿಗಳಿಗಾಗಿ ಸ್ಕೀಮಾ-ಆವೃತ್ತಿಯ A/B ಹಾರ್ನೆಸ್ ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. ಇದು ಪೂರೈಕೆದಾರರು ವರದಿ ಮಾಡಿದ ಟೋಕನ್ಗಳು, ಎಂಡ್-ಟು-ಎಂಡ್ ವಾಲ್ ಲೇಟೆನ್ಸಿ (ಶೀಟ್ ಸಂಯೋಜನೆ ಸೇರಿದಂತೆ), ಮಾದರಿ-ಕರೆ ಎಣಿಕೆ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್-ವ್ಯಾಖ್ಯಾನಿತ ಸತ್ಯ ಧಾರಣೆಯನ್ನು ಅಳೆಯುತ್ತದೆ. ಕಚ್ಚಾ ಮಾದರಿ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ವರದಿಗೆ ಬರೆಯಲಾಗುವುದಿಲ್ಲ; SHA-256 ಡೈಜೆಸ್ಟ್ಗಳು ಮತ್ತು ಹೊಂದಾಣಿಕೆಯ ಸತ್ಯ ID ಗಳನ್ನು ಮಾತ್ರ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. `--execute-real` ಅನ್ನು ಪಾಸ್ ಮಾಡದ ಹೊರತು ಮತ್ತು `--model`, `OMNIROUTE_BASE_URL`, ಮತ್ತು `OMNIROUTE_API_KEY` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದ ಹೊರತು ಹಾರ್ನೆಸ್ ಯಾವುದೇ ನೆಟ್ವರ್ಕ್ ಅಥವಾ ಪಾವತಿಸಿದ ಮಾದರಿ ಕರೆಯನ್ನು ಮಾಡುವುದಿಲ್ಲ. ಆ ಸ್ಪಷ್ಟವಾದ ನೈಜ ರನ್ ಇಲ್ಲದೆ, ಅದರ ಯಂತ್ರ-ಓದಬಲ್ಲ ತೀರ್ಪು `HOLD` ಆಗಿ ಉಳಿದಿದೆ; ಸಂಶ್ಲೇಷಿತ ಪೇಲೋಡ್/ಕರೆ-ಎಣಿಕೆ ಮಾಪನಗಳು ಮಾತ್ರ ಪ್ರಚಾರದ ಪುರಾವೆಗಳಲ್ಲ.

ಕರೆ ಮಾಡುವವರು ಈಗಾಗಲೇ ಜೋಡಿಸಲಾದ ಪಠ್ಯವನ್ನು ಹೊಂದಿರುವಾಗ ಬೆಂಬಲಿತ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಐಚ್ಛಿಕ `transcript.cues` ಅರೇ ಅನ್ನು ಲಗತ್ತಿಸಬಹುದು. ಪ್ರತಿ ಕ್ಯೂ `text`, ಪರೀಕ್ಷಿಸಿದ ಅವಧಿಯೊಳಗೆ ಸೀಮಿತ `start`/`end` ಮಧ್ಯಂತರ ಮತ್ತು ವೈಟ್ಲಿಸ್ಟ್ ಮಾಡಿದ `source` (`client`, `embedded`, ಅಥವಾ `audio-bridge`) ಅನ್ನು ಹೊಂದಿರಬೇಕು; `confidence` ಡೀಫಾಲ್ಟ್ ಆಗಿ `1` ಆಗಿರುತ್ತದೆ ಮತ್ತು `0` ಮತ್ತು `1` ರ ನಡುವೆ ಇರಬೇಕು. ನಿಖರವಾದ ನಕಲು ಕ್ಯೂಗಳನ್ನು ಕುಗ್ಗಿಸಲಾಗುತ್ತದೆ. OmniRoute ಎಂದಿಗೂ ಈ ಮೆಟಾಡೇಟಾದಿಂದ ಪ್ರತಿಲೇಖನವನ್ನು ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ: ಮೌಲ್ಯೀಕರಿಸಿದ ಕ್ಯೂಗಳನ್ನು ಮೂಲ, ವಿಶ್ವಾಸ ಮತ್ತು ಮಧ್ಯಂತರದೊಂದಿಗೆ ವಿವರಿಸಿದ ಫಲಿತಾಂಶಕ್ಕೆ ನಕಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಫ್ರೇಮ್ ಶೀರ್ಷಿಕೆಗಳ ಜೊತೆಗೆ ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ಅವಲೋಕನಗಳಾಗಿ ರೆಂಡರ್ ಮಾಡಲಾಗುತ್ತದೆ. ಅಮಾನ್ಯ, ಶ್ರೇಣಿಯಿಂದ ಹೊರಗಿರುವ ಅಥವಾ ಮೂಲ-ಮುಕ್ತ ಪಠ್ಯವನ್ನು ಶೀರ್ಷಿಕೆ ಸ್ಟ್ರೀಮ್ಗೆ ಮಿಶ್ರಣ ಮಾಡುವ ಬದಲು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. `source` ಕ್ಷೇತ್ರವು ಪ್ರಸ್ತುತ ಕರೆ ಮಾಡುವವರಿಂದ ಘೋಷಿಸಲ್ಪಟ್ಟಿದೆ, ಸರ್ವರ್-ಪರಿಶೀಲಿಸಲ್ಪಟ್ಟಿಲ್ಲ: OmniRoute ಮೌಲ್ಯವು ಮೂರು ಅನುಮತಿಸಲಾದ ಸ್ಟ್ರಿಂಗ್ಗಳಲ್ಲಿ ಒಂದಾಗಿದೆ ಎಂದು ಜಾರಿಗೊಳಿಸುತ್ತದೆ, ಆದರೆ `embedded` ಅಥವಾ `audio-bridge` ಲೇಬಲ್ ನಿಜವಾಗಿಯೂ ಸರ್ವರ್-ಮಾಲೀಕತ್ವದ ಹೊರತೆಗೆಯುವಿಕೆಯಿಂದ ಬಂದಿದೆ ಎಂದು ಕ್ರಿಪ್ಟೋಗ್ರಾಫಿಕವಾಗಿ ದೃಢೀಕರಿಸುವುದಿಲ್ಲ. ಆ ಪರಿಶೀಲನೆ ಬರುವವರೆಗೆ `source` ಅನ್ನು ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ಸುಳಿವಾಗಿ ಪರಿಗಣಿಸಿ; ಅದರ ಮೇಲೆ ಅಧಿಕಾರ ನಿರ್ಧಾರಗಳನ್ನು ನಿರ್ಮಿಸಬೇಡಿ.

ಸುಧಾರಿತ ಕರೆ ಮಾಡುವವರು ಅದೇ ವೀಡಿಯೊಗಾಗಿ ಈಗಾಗಲೇ ಅಧಿಕೃತ `audioTranscript` ಟ್ರ್ಯಾಕ್ ಅನ್ನು ಒದಗಿಸಬಹುದು. ಫ್ಯೂಷನ್ ಸೀಮ್ ದೃಶ್ಯ ಮತ್ತು ಆಡಿಯೊ ಅವಲೋಕನಗಳನ್ನು ಒಂದೇ ಗಡುವು ಮತ್ತು ಅಬಾರ್ಟ್ ಸಿಗ್ನಲ್ ಅಡಿಯಲ್ಲಿ ನಡೆಸುತ್ತದೆ, ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ಟೈಮ್ಲೈನ್ನಲ್ಲಿ ಆದೇಶಿಸುತ್ತದೆ, ನಿಖರವಾದ ನಕಲುಗಳನ್ನು ಕುಸಿಯುತ್ತದೆ ಮತ್ತು ಒಂದು ಕಡೆ ಮಾತ್ರ ಯಶಸ್ವಿಯಾದಾಗ ಭಾಗಶಃ ಫಲಿತಾಂಶವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಅಮಾನ್ಯ `audioTranscript` ಆ ಭಾಗಶಃ ಫಲಿತಾಂಶಕ್ಕೆ ಇಳಿಯುತ್ತದೆ — ದೃಶ್ಯ ವಿವರಣೆಯನ್ನು ಇರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಆಡಿಯೊ ಶಾಖೆಯು ಸ್ಯಾನಿಟೈಸ್ ಮಾಡಿದ ವೈಫಲ್ಯ ಕೋಡ್ ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ — ಸಂಪೂರ್ಣ ವೀಡಿಯೊವನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು. ಪ್ರತಿ-ಶಾಖೆಯ ಲಭ್ಯತೆ, ಭಾಗಶಃ ಫ್ಲ್ಯಾಗ್ ಮತ್ತು ಸ್ಯಾನಿಟೈಸ್ ಮಾಡಿದ ವೈಫಲ್ಯ ಕೋಡ್ಗಳನ್ನು ವಿವರಿಸಿದ ಫಲಿತಾಂಶದಲ್ಲಿ, ಗಾರ್ಡ್ರೈಲ್ ಮೆಟಾಡೇಟಾದಲ್ಲಿ (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), ಫಲಿತಾಂಶ-ಸಂಗ್ರಹ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ಸೇತುವೆ ಫ್ಯೂಷನ್ ಕೌಂಟರ್ಗಳಲ್ಲಿ ಸಂರಕ್ಷಿಸಲಾಗಿದೆ. ಡೀಫಾಲ್ಟ್ ವೀಡಿಯೊ ಬ್ರಿಡ್ಜ್ ಮಾರ್ಗವು ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಅನ್ನು ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ ಅಥವಾ ಎರಡನೇ ಮಾಧ್ಯಮ ನಕಲನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ; ಆ ಸ್ಪಷ್ಟ ಟ್ರ್ಯಾಕ್ ಇಲ್ಲದೆ, ಅದು ವೀಡಿಯೊ-ಮಾತ್ರವಾಗಿ ಉಳಿಯುತ್ತದೆ.

**ಪ್ರತಿಲೇಖನ ಧಾರಣ (#12150 P1).** ವೀಡಿಯೊ ಬ್ರಿಡ್ಜ್ (ಸ್ವತಃ ಆಪ್ಟ್-ಇನ್) ಪ್ರತಿಲೇಖನ ಕ್ಯೂ ಅನ್ನು ರೆಂಡರ್ ಮಾಡಿದಾಗಲೆಲ್ಲಾ ಇದು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಅನ್ವಯಿಸುತ್ತದೆ — ಯಾವುದೇ ಪ್ರತ್ಯೇಕ ಧಾರಣ ಫ್ಲ್ಯಾಗ್ ಇಲ್ಲ. ವಿನಂತಿಯು ಯಾವುದೇ ಪ್ರತಿಲೇಖನ ಕ್ಯೂ ಅನ್ನು ರೆಂಡರ್ ಮಾಡಿದಾಗ (ಕರೆ ಮಾಡುವವರು ಘೋಷಿಸಿದ `transcript` ಅಥವಾ ಫ್ಯೂಸ್ ಮಾಡಿದ `audioTranscript`), ಗಾರ್ಡ್ರೈಲ್ ಅದನ್ನು `videoBridgeObserved` ಎಂದು ಗುರುತಿಸುತ್ತದೆ ಮತ್ತು ವೀಡಿಯೊ ವಿವರಣೆಯ ಸಂಪಾದಿತ ನೆರಳನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ — ಪ್ರತಿ ಕ್ಯೂನ ಉಚಿತ-ಪಠ್ಯ ದೇಹವನ್ನು `[redacted-video-transcript]` ನಿಂದ ಬದಲಾಯಿಸುವ ಒಂದೇ ರೀತಿಯ ರೆಂಡರಿಂಗ್, ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು ಜೋಡಿಸುವ ಮೊದಲು ರಚನಾತ್ಮಕ ಕ್ಯೂ ಕ್ಷೇತ್ರವನ್ನು ಬದಲಿಸುವ ಮೂಲಕ ನಿರ್ಮಿಸಲಾಗಿದೆ (ಫ್ಲಾಟ್ ಮಾಡಿದ ಪಠ್ಯವನ್ನು ಪಾರ್ಸ್ ಮಾಡುವ ಮೂಲಕ ಎಂದಿಗೂ ಅಲ್ಲ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಕ್ಯೂ ವಿಷಯ — ಪ್ರತಿಕೂಲ ಅಥವಾ ಸಾಮಾನ್ಯ, `]` ಹೊಂದಿರುವ ದೇಹಗಳು ಸೇರಿದಂತೆ `[inaudible]`/`[music]` — ಉಳಿಯಲು ಸಾಧ್ಯವಿಲ್ಲ). ನಿರಂತರವಾದ ಕರೆ-ಲಾಗ್ ವಿನಂತಿ ದೇಹವು ಪ್ರತಿ ವೀಡಿಯೊ-ಪಡೆದ ಪಠ್ಯ ಭಾಗವನ್ನು ಆ ಸಂಪಾದಿತ ನೆರಳಿಗಾಗಿ ಬದಲಾಯಿಸುತ್ತದೆ, ವಿಷಯ ಸಮಾನತೆಯಿಂದ ಹೊಂದಾಣಿಕೆಯಾಗುತ್ತದೆ; `fullText` ಆಂಕರ್ ಅನ್ನು ಪೂರ್ಣಗೊಂಡ ಪೂರ್ವ-ಕರೆ ಗಾರ್ಡ್ರೈಲ್ ಪೇಲೋಡ್ನಿಂದ ಮರು-ಓದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ನಂತರದ ಚೈನ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು (PII ಮತ್ತು ರುಜುವಾತು ಮಾಸ್ಕರ್ಗಳು, ಆದ್ಯತೆಗಳು 10/95) ವಿವರಣೆಯ ಪಠ್ಯವನ್ನು ಸ್ಥಳದಲ್ಲಿ ಪುನಃ ಬರೆದ ನಂತರ ಮತ್ತು ಸಿಸ್ಟಮ್-ಪ್ರಾಂಪ್ಟ್/ಹ್ಯಾಂಡಾಫ್/ಮೆಮೊರಿ ಇಂಜೆಕ್ಷನ್ ಸಂದೇಶ ಶ್ರೇಣಿಯನ್ನು ಮರುರೂಪಿಸಿದ ನಂತರವೂ ಹೊಂದಾಣಿಕೆಯು ಯಶಸ್ವಿಯಾಗುತ್ತದೆ. ಮಾದರಿಗೆ ಅಪ್ಸ್ಟ್ರೀಮ್ ಕಳುಹಿಸಿದ ದೇಹವು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತದೆ. ಗಮನಿಸಿದ ವಿನಂತಿಯು ಯಾವುದೇ ಬಾಳಿಕೆ ಬರುವ ಮೆಮೊರಿಯನ್ನು ಸಹ ಜನಪ್ರಿಯಗೊಳಿಸುವುದಿಲ್ಲ (ವಿನಂತಿ- ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ-ಪಡೆದ ಹೊರತೆಗೆಯುವಿಕೆ ಎರಡನ್ನೂ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ), ಆದ್ದರಿಂದ ಮಾದರಿಯ ಸ್ವಂತ ಪ್ರತ್ಯುತ್ತರವು ಪ್ರತಿಲೇಖನ ಪಠ್ಯವನ್ನು ಮೆಮೊರಿಗೆ ಪ್ರತಿಧ್ವನಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಹೆಚ್ಚುವರಿ ಉಳಿಸಿಕೊಂಡ ನಕಲುಗಳು ಅದೇ ಗಮನಿಸಿದ-ವಿನಂತಿ ಸಂಕೇತವನ್ನು ಬಳಸುತ್ತವೆ. ಕಚ್ಚಾ ಪೂರ್ವ-ಗಾರ್ಡ್ರೈಲ್ ಕ್ಲೈಂಟ್-ವಿನಂತಿ ಸ್ನ್ಯಾಪ್ಶಾಟ್, ಮೆಮೊರಿಯಲ್ಲಿ ಬಾಕಿ ಉಳಿದಿರುವ ವಿನಂತಿ ಮತ್ತು ಆರಂಭಿಕ ತಿರಸ್ಕರಿಸಿದ-ವಿನಂತಿ ಲಾಗ್ ವೀಡಿಯೊ ಭಾಗಗಳಲ್ಲಿನ ಪ್ರತಿಲೇಖನ ಕ್ಷೇತ್ರಗಳನ್ನು ರಚನಾತ್ಮಕವಾಗಿ ಬದಲಾಯಿಸುತ್ತದೆ; ಪೈಪ್ಲೈನ್ ಹಂತಗಳಿಂದ ಸಂಶ್ಲೇಷಿಸಲ್ಪಟ್ಟ ಸ್ಟ್ರಿಂಗ್ ಪ್ರಾಂಪ್ಟ್ಗಳು ಮತ್ತು ಸಂದರ್ಭ ಹ್ಯಾಂಡಾಫ್ ಅನ್ನು ನಿರಂತರವಾದ-ವಿನಂತಿ-ದೇಹ ಸಿಂಕ್ನಲ್ಲಿ ಸಂಪಾದಿಸಲಾಗುತ್ತದೆ. ನಿರಂತರವಾದ `video_content_removed` ಮಾರ್ಕರ್ `previous_response_id` ಮುಂದುವರಿಕೆಯನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ತಿರಸ್ಕರಿಸಿದ ಪಠ್ಯವನ್ನು ಪುನರ್ನಿರ್ಮಿಸುವ ಬದಲು ಮುಚ್ಚಿದಂತೆ ವಿಫಲಗೊಳಿಸುತ್ತದೆ. ಗಮನಿಸಿದ ವಿನಂತಿಯು ಲಾಗಿಂಗ್ ಮಾಡುವ ಮೊದಲು ಅದರ ಪ್ರತಿ-ಭಾಗದ ಸಂಪಾದನೆ ನೆರಳನ್ನು ಕಳೆದುಕೊಂಡರೆ, ಅಥವಾ ನಂತರದ ವಿನಂತಿ ರೂಪಾಂತರಗಳ ನಂತರ ಹಲವಾರು ವೀಡಿಯೊ ನೆರಳುಗಳಲ್ಲಿ ಒಂದಾದರೂ ಹೊಂದಾಣಿಕೆಯಾಗದಿದ್ದರೆ, ಭಾಗಶಃ ಸಂಪಾದಿತ ಪ್ರತಿಲೇಖನವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುವ ಬದಲು ಉಳಿಸಿಕೊಂಡ ವಿನಂತಿ ದೇಹವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ.

ಗಮನಿಸಿದ ವಿನಂತಿಗಾಗಿ, ಮಾದರಿ ಪ್ರತಿಕ್ರಿಯೆಯು ರಚನಾತ್ಮಕ ಕ್ಯೂ ಗಡಿ ಇಲ್ಲದೆ ಪ್ರತಿಲೇಖನದ ಯಾವುದೇ ಭಾಗವನ್ನು ಉಲ್ಲೇಖಿಸಬಹುದು. ಅದರ ನಿರಂತರವಾದ ಕರೆ-ಲಾಗ್ `responseBody` ಅನ್ನು ಆದ್ದರಿಂದ ಲೋಪ ಮಾರ್ಕರ್ನಿಂದ ಬದಲಾಯಿಸಲಾಗುತ್ತದೆ; ವಿವರವಾದ ಪೈಪ್ಲೈನ್ ಕಲಾಕೃತಿಯನ್ನು (ಇದು ಅಪ್ಸ್ಟ್ರೀಮ್/ಕ್ಲೈಂಟ್ ದೇಹಗಳು ಮತ್ತು ಸ್ಟ್ರೀಮ್ ಚಂಕ್ಗಳನ್ನು ಒಳಗೊಂಡಿರಬಹುದು) ಉಳಿಸಿಕೊಳ್ಳಲಾಗುವುದಿಲ್ಲ. ಸಿಮ್ಯಾಂಟಿಕ್, ಐಡೆಂಪೊಟೆನ್ಸಿ ಮತ್ತು ರೀಸನಿಂಗ್-ರಿಪ್ಲೇ ಸಂಗ್ರಹಗಳು ಆ ವಿನಂತಿಗಾಗಿ ಓದುವಿಕೆ ಮತ್ತು ಬರವಣಿಗೆಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತವೆ. ಒದಗಿಸುವವರ ವಿನಂತಿ ಮತ್ತು ಕ್ಲೈಂಟ್-ಗೋಚರ ಪ್ರತಿಕ್ರಿಯೆ ಬದಲಾಗದೆ ಉಳಿಯುತ್ತವೆ. ವಿವರವಾದ ಕಲಾಕೃತಿಯನ್ನು ಬಿಟ್ಟುಬಿಟ್ಟಾಗ ಆರಂಭಿಕ ಕೀಪಲೈವ್ ಬೈಟ್ಗಳನ್ನು ತಾತ್ಕಾಲಿಕ ಬಫರ್ನಿಂದ ಹೊರಹಾಕಲಾಗುತ್ತದೆ. ಕಿರೋನ ಅಸಮರ್ಪಕ EventStream ಎಚ್ಚರಿಕೆಯು ಪೇಲೋಡ್ ಬೈಟ್ ಎಣಿಕೆಯನ್ನು ಮಾತ್ರ ವರದಿ ಮಾಡುತ್ತದೆ, ಅದರ ವಿಷಯಗಳನ್ನು ಅಥವಾ JSON ಪಾರ್ಸರ್ನ ಕಚ್ಚಾ ದೋಷವನ್ನು ಎಂದಿಗೂ ವರದಿ ಮಾಡುವುದಿಲ್ಲ.
ಪ್ರತಿ ಸಂಬಂಧವಿಲ್ಲದ ಒದಗಿಸುವವರು/ಪ್ಲಗಿನ್ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ ಅನ್ನು ಆಡಿಟ್ ಮಾಡಲಾಗಿದೆ ಎಂದು ಇದು ಹೇಳಿಕೊಳ್ಳುವುದಿಲ್ಲ; ವಿಶಾಲವಾದ ಉಳಿಸಿಕೊಂಡ-ಸಿಂಕ್ ಸ್ವೀಪ್ ಅನ್ನು #11658 ರಲ್ಲಿ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗಿದೆ.

ಆಂತರಿಕ `/api/modality-bridge/video/drilldown` ಜೀವಿತಾವಧಿಯು ಪ್ರತ್ಯೇಕ, ಲೂಪ್ಬ್ಯಾಕ್/ಟೋಕನ್-ದೃಢೀಕೃತ ಸಂಗ್ರಹ ಸಬ್ಸ್ಟ್ರೇಟ್ ಆಗಿದೆ. ಪ್ರತಿ ಕಾರ್ಯಾಚರಣೆಗೆ ಅಧಿಕೃತ ಅಪಾರದರ್ಶಕ ಪ್ರಿನ್ಸಿಪಾಲ್ ID ಸಹ ಅಗತ್ಯವಿದೆ. ಉತ್ಪಾದನಾ ಕರೆ ಮಾಡುವವರನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವ ಮೊದಲು, ಅದು ದೃಢೀಕೃತ ಟೆನೆಂಟ್ನಿಂದ ಆ ID ಅನ್ನು ಪಡೆಯಬೇಕು ಮತ್ತು ಕ್ಲೈಂಟ್-ಆಯ್ಕೆ ಮಾಡಿದ ಮೌಲ್ಯವನ್ನು ಎಂದಿಗೂ ಫಾರ್ವರ್ಡ್ ಮಾಡಬಾರದು. ಸಂಗ್ರಹ ಕೀಗಳು ಆ ಪ್ರಿನ್ಸಿಪಾಲ್ ಅನ್ನು ಅಧಿಕೃತ ಸೆಷನ್ ಮತ್ತು ವೀಡಿಯೊ-ಉಲ್ಲೇಖ ID ಗಳಿಗೆ ಬಂಧಿಸುತ್ತವೆ, ಅವುಗಳ SHA-256-ಪಡೆದ ಕೀಗಳನ್ನು ಮಾತ್ರ ಸಂಗ್ರಹಿಸುತ್ತವೆ ಮತ್ತು ಓದುವಿಕೆ ಮತ್ತು ಅಳಿಸುವಿಕೆ ಎರಡನ್ನೂ ಅದೇ ಪ್ರಿನ್ಸಿಪಾಲ್ಗೆ ವ್ಯಾಪ್ತಿಗೊಳಿಸುತ್ತವೆ. ಸಂಗ್ರಹವು ಪ್ರತಿ ನಮೂದಿಗೆ ಗರಿಷ್ಠ 16 ಪಡೆದ JPEG ಫ್ರೇಮ್ಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ, ಹತ್ತು ನಿಮಿಷಗಳ ನಂತರ ಅವುಗಳನ್ನು ಮುಕ್ತಾಯಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಬೌಂಡೆಡ್ `start`/`end` ಓದುವಿಕೆಗಳು ಅಥವಾ ಸ್ಪಷ್ಟ ಸೆಷನ್ ಅಳಿಸುವಿಕೆಯನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ.

ಪ್ರತಿ ಪ್ರಿನ್ಸಿಪಾಲ್ 16 ನಮೂದುಗಳು ಮತ್ತು 64 MiB ಅಧಿಕೃತ JPEG ಡೇಟಾಗೆ ಸೀಮಿತವಾಗಿದೆ. ಆ ಮಿತಿಗಳು ಜಾಗತಿಕ 64-ನಮೂದು/256 MiB ಮಿತಿಯಿಂದ ಸ್ವತಂತ್ರವಾಗಿವೆ: ಜಾಗತಿಕ LRU ಹೊರಹಾಕುವಿಕೆಯನ್ನು ಪರಿಗಣಿಸುವ ಮೊದಲು ಪ್ರಿನ್ಸಿಪಾಲ್ ಕೋಟಾ ಒತ್ತಡವು ಆ ಪ್ರಿನ್ಸಿಪಾಲ್ನ ಕನಿಷ್ಠ-ಇತ್ತೀಚೆಗೆ ಬಳಸಿದ ನಮೂದುಗಳನ್ನು ಮಾತ್ರ ಹೊರಹಾಕುತ್ತದೆ. ಸಂಗ್ರಹ ಚಟುವಟಿಕೆಯ ಮೇಲೆ ಮುಕ್ತಾಯಗೊಂಡ ನಮೂದುಗಳನ್ನು ಪ್ರಿನ್ಸಿಪಾಲ್ ಮತ್ತು ಜಾಗತಿಕ ಲೆಕ್ಕಪತ್ರ ಎರಡರಿಂದಲೂ ಸ್ವೀಪ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ರದ್ದತಿ ಮತ್ತು ಮೌಲ್ಯೀಕರಣ ವೈಫಲ್ಯವು ಭಾಗಶಃ ಬದಲಿಯನ್ನು ಮಾಡುವುದಿಲ್ಲ.

ಸಂಗ್ರಹವು ಅಧಿಕೃತವಲ್ಲದ Base64, ಹೆಚ್ಚುವರಿ ಪ್ಯಾಡಿಂಗ್, JPEG ಅಲ್ಲದ ಮಾಧ್ಯಮ, ಅಸಮರ್ಪಕ ಅಥವಾ ಕತ್ತರಿಸಿದ JPEG ಗಳು ಮತ್ತು ಬೌಂಡೆಡ್ ಪೂರ್ಣ-ಚಿತ್ರ `sharp` ಡಿಕೋಡ್ ಸಮಯದಲ್ಲಿ ಎಚ್ಚರಿಕೆಯನ್ನು ನೀಡುವ JPEG ಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ಇದು ಪ್ರತಿ ಸ್ವೀಕರಿಸಿದ ಚಿತ್ರವನ್ನು ಅಧಿಕೃತ JPEG ಆಗಿ ಮರು-ಎನ್ಕೋಡ್ ಮಾಡುತ್ತದೆ, ಕರೆ ಮಾಡುವವರ ಕ್ಷೇತ್ರಗಳನ್ನು ನಂಬುವ ಬದಲು ಡಿಕೋಡ್ ಮಾಡಿದ ಬೈಟ್ಗಳಿಂದ ಅಗಲ ಮತ್ತು ಎತ್ತರವನ್ನು ಪಡೆಯುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ ಹಿಂದುಳಿದ ಪಾಲಿಗ್ಲಾಟ್ ಬೈಟ್ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುವ ಬದಲು ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ. ಬೌಂಡೆಡ್ ಅಧಿಕೃತ ಸಂಕುಚಿತ ಬಫರ್ ಅನ್ನು ಮಾತ್ರ ಎರಡೂ ಕೋಟಾಗಳಿಗೆ ವಿಧಿಸಲಾಗುತ್ತದೆ. JSON ವೈರ್ ಮಿತಿಯು 32 MiB ಡಿಕೋಡ್ ಮಾಡಿದ-ಇನ್ಪುಟ್ ಮಿತಿಗಾಗಿ Base64 ಓವರ್ಹೆಡ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಪ್ರತಿ ಸಂಗ್ರಹಿಸಿದ ಉತ್ಪನ್ನವು ಅದರ ಮೌಲ್ಯೀಕರಿಸಿದ JPEG ಸ್ವರೂಪ/ರೆಸಲ್ಯೂಶನ್, ಮಾದರಿ ನೀತಿ, ಉತ್ಪನ್ನ ಆವೃತ್ತಿ, ರಚನೆ ಸಮಯ, ಸರ್ವರ್-ಲೆಕ್ಕಾಚಾರ ಮಾಡಿದ ವಿಷಯ ಹ್ಯಾಶ್ ಮತ್ತು ಹ್ಯಾಶ್ ಮಾಡಿದ ಪೋಷಕ ಉಲ್ಲೇಖ ಜೊತೆಗೆ ವಿಶ್ವಾಸಾರ್ಹ ಕರೆ ಮಾಡುವವರ ಪೋಷಕ-ವಿಷಯ ಹ್ಯಾಶ್ ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಅಟಾಮಿಕ್ ಸಂಗ್ರಹ ಬದ್ಧತೆಯ ಮೊದಲು ಅಸಮಕಾಲಿಕ ಡಿಕೋಡ್/ಹ್ಯಾಶ್ ಹಂತಗಳ ನಡುವೆ ರದ್ದತಿಯನ್ನು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ.

ಈ ಟ್ರ್ಯಾಂಚ್ ಇನ್ನೂ ಉತ್ಪಾದನಾ ನಿರ್ಮಾಪಕರನ್ನು ಮಾರ್ಗಕ್ಕೆ ಸಂಪರ್ಕಿಸುವುದಿಲ್ಲ ಮತ್ತು ಬಹು-ರೆಸಲ್ಯೂಶನ್ ರೂಪಾಂತರ ಆಯ್ಕೆಯನ್ನು ಒದಗಿಸುವುದಿಲ್ಲ. ಆದ್ದರಿಂದ ಪಾರದರ್ಶಕ ವೀಡಿಯೊ ಬ್ರಿಡ್ಜ್ ವಿನಂತಿ ಮಾರ್ಗವು ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಕೆಲಸವನ್ನು ಉಂಟುಮಾಡುವುದಿಲ್ಲ, ಆದರೆ ಟೆನೆಂಟ್-ಬೌಂಡ್ ಪ್ರಿನ್ಸಿಪಾಲ್ ಡಿರೈವೇಶನ್ ಮತ್ತು ಪೂರ್ಣ FU-08 ಬಹು-ರೆಸಲ್ಯೂಶನ್ ಜೀವನಚಕ್ರವು ಸಂಪೂರ್ಣ ನಡವಳಿಕೆಯಾಗಿ ದಾಖಲಿಸುವುದಕ್ಕಿಂತ ಹೆಚ್ಚಾಗಿ ಸ್ಪಷ್ಟವಾದ ಫಾಲೋ-ಅಪ್ ಕೆಲಸವಾಗಿ ಉಳಿದಿದೆ.

ಫ್ರೇಮ್ಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ ವೀಡಿಯೊ ಮಾದರಿಯೊಂದಿಗೆ ಅನುಕ್ರಮವಾಗಿ ಶೀರ್ಷಿಕೆ ಮಾಡಲಾಗುತ್ತದೆ. ಖಾಲಿ ವೀಡಿಯೊ ಓವರ್ರೈಡ್ ವಿಷನ್ ಸೆಟ್ಟಿಂಗ್ ಅನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯುತ್ತದೆ; ಎರಡೂ ಖಾಲಿಯಾಗಿದ್ದರೆ, ವಿಷನ್ ಆಟೋ-ರೂಟರ್ ಪರಿಣಾಮಕಾರಿ ವಿಷನ್-ಸಾಮರ್ಥ್ಯದ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆ ಮಾಡುತ್ತದೆ. ಯಶಸ್ವಿ ಶೀರ್ಷಿಕೆಗಳು ಮೂಲ ಭಾಗವನ್ನು ಸ್ಥಿರವಾದ `[Video description:` ಪೂರ್ವಪ್ರತ್ಯಯದೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತವೆ, ಇದು ಪಠ್ಯವನ್ನು ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ಮಾಧ್ಯಮ-ಪಡೆದ ಅವಲೋಕನ ಎಂದು ಗುರುತಿಸುತ್ತದೆ ಮತ್ತು ಮಾಧ್ಯಮದಲ್ಲಿ ಕಂಡುಬರುವ ಸೂಚನೆಗಳನ್ನು ಅನುಸರಿಸದಂತೆ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಮಾದರಿಗಳಿಗೆ ತಿಳಿಸುತ್ತದೆ. ಫ್ರೇಮ್-ಶೀರ್ಷಿಕೆ ಸಂಗ್ರಹ ಕೀಗಳು JPEG ಬೈಟ್ಗಳು, ಪ್ರಾಂಪ್ಟ್, ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಮತ್ತು ಪರಿಣಾಮಕಾರಿ ಮಾದರಿಯನ್ನು ಒಳಗೊಂಡಿರುತ್ತವೆ; ಯಶಸ್ವಿ ಶೀರ್ಷಿಕೆಗಳನ್ನು ಮಾತ್ರ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ. ಸಂಗ್ರಹ ನಮೂದುಗಳು ನಿಜವಾದ ಯಶಸ್ವಿ ನಿರ್ಮಾಪಕ ಮಾದರಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ, ಫಾಲ್ಬ್ಯಾಕ್ ಮಾದರಿ ಸೇರಿದಂತೆ; ವಿಭಿನ್ನ ಫ್ರೇಮ್ಗಳನ್ನು ವಿಭಿನ್ನ ಮಾದರಿಗಳಿಂದ ಉತ್ಪಾದಿಸಿದಾಗ ಸೇತುವೆಯು `mixed` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ. ಸಂಗ್ರಹ ಹಿಟ್ ಆ ವಿನಂತಿಸಿದ ರೂಟಿಂಗ್ ಯೋಜನೆಯಾಗಿ ಮರು-ಲೇಬಲ್ ಮಾಡುವ ಬದಲು ಆ ನಿರ್ಮಾಪಕ ಗುರುತನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ. ಸಂಪೂರ್ಣ-ವೀಡಿಯೊ ಫಲಿತಾಂಶ ಸಂಗ್ರಹವು ಔಟ್ಪುಟ್ ಅನ್ನು ಬದಲಾಯಿಸುವ ಪ್ರತಿಯೊಂದು ಇನ್ಪುಟ್ನಲ್ಲಿ ಕೀ ಮಾಡಲಾಗುತ್ತದೆ - ಪ್ರಾಂಪ್ಟ್, ಪರಿಣಾಮಕಾರಿ ಮಾದರಿ, ಮಾದರಿ ನೀತಿ, ಫ್ರೇಮ್ ಎಣಿಕೆ, ಸಿಮ್ಯಾಂಟಿಕ್ ವಿಶ್ಲೇಷಣೆ ಮೋಡ್, ಸಾಮಾನ್ಯೀಕರಿಸಿದ ಫೋಕಸ್ ಸುಳಿವಿನ SHA-256 ಫಿಂಗರ್ಪ್ರಿಂಟ್, ಫೋಕಸ್ ವಿಂಡೋ, `transcript`, `audioTranscript`, ಮತ್ತು ಸಂಪರ್ಕ-ಹಾಳೆ ಫ್ಲ್ಯಾಗ್ - ಆದ್ದರಿಂದ ಆ ಯಾವುದೇ ಆಯಾಮಗಳನ್ನು ಬದಲಾಯಿಸುವುದು ಸಂಗ್ರಹ ತಪ್ಪಾಗಿದೆ, ಎಂದಿಗೂ ಹಳೆಯ ಮರುಬಳಕೆ ಅಲ್ಲ. ದೃಶ್ಯ ಡಿಡಪ್ ನೀತಿ ಆವೃತ್ತಿ, ಥ್ರೆಶೋಲ್ಡ್ ಮತ್ತು ಬೌಂಡೆಡ್ ಕ್ಯಾಂಡಿಡೇಟ್-ಫ್ರೇಮ್ ಎಣಿಕೆ ಕೂಡ ಫಲಿತಾಂಶ-ಸಂಗ್ರಹ ಕೀ ಮತ್ತು ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಸ್ಪಷ್ಟವಾಗಿವೆ; ಆದ್ದರಿಂದ ನೀತಿ ಬದಲಾವಣೆಯು ಹಳೆಯ ಸಂಪೂರ್ಣ-ವೀಡಿಯೊ ವಿವರಣೆಯನ್ನು ಮರುಬಳಕೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಫಲಿತಾಂಶ-ಸಂಗ್ರಹ v4 ಮೆಟಾಡೇಟಾ ಮೋಡ್ ಮತ್ತು ಫಿಂಗರ್ಪ್ರಿಂಟ್ ಅನ್ನು ಇರಿಸುತ್ತದೆ, ಎಂದಿಗೂ ಕಚ್ಚಾ ಬಳಕೆದಾರ ಕಾರ್ಯವನ್ನು ಇರಿಸುವುದಿಲ್ಲ. ಗಾರ್ಡ್ರೈಲ್ ಮೆಟಾಡೇಟಾ ವಿನಂತಿಸಿದ ಮತ್ತು ಪರಿಣಾಮಕಾರಿ ವಿಶ್ಲೇಷಣೆ ಮೋಡ್ಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ; ಬಳಸಬಹುದಾದ ಬಳಕೆದಾರ ಪಠ್ಯವಿಲ್ಲದೆ ವಿನಂತಿಸಿದ `focused` ಮೋಡ್ ಅನ್ನು ಪರಿಣಾಮಕಾರಿಯಾಗಿ `full` ಎಂದು ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ.

ಗಾರ್ಡ್ರೈಲ್ ಪ್ರತಿ ಬೆಂಬಲಿತ ವೀಡಿಯೊ ಭಾಗವನ್ನು ಹೊರತೆಗೆಯುತ್ತದೆ ಆದರೆ `modalityBridgeVideoMaxVideos` ಗಿಂತ ಹೆಚ್ಚು ವಿವರಿಸುವುದಿಲ್ಲ. `supportsVideo === false` ಎಂದು ಸಾಬೀತಾದ ಗುರಿಗಾಗಿ, ವಿಫಲವಾದ ಮತ್ತು ಮಿತಿಮೀರಿದ ವೀಡಿಯೊಗಳು ಸ್ಪಷ್ಟವಾದ ಸುರಕ್ಷಿತ ಪಠ್ಯ ಗುರುತುಗಳಾಗುತ್ತವೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಕಚ್ಚಾ ವೀಡಿಯೊ ಉಳಿಯುವುದಿಲ್ಲ. ಸಾಮರ್ಥ್ಯವು ತಿಳಿದಿಲ್ಲದಿದ್ದಾಗ, ಆ ಭಾಗಗಳು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತವೆ. `supportsVideo === true` ಹೊಂದಿರುವ ಗುರಿಗಳು ಸೇತುವೆಯನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತವೆ. ಕ್ಲೈಂಟ್ ವಿನಂತಿ ಅಬಾರ್ಟ್ ಸಿಗ್ನಲ್ ಡೌನ್ಲೋಡ್, ಬ್ರೋಕರ್ ಕ್ಯೂ, ಸಬ್ಪ್ರೊಸೆಸ್ಗಳು ಮತ್ತು ಶೀರ್ಷಿಕೆ ಕರೆಗಳ ಮೂಲಕ ಹರಡುತ್ತದೆ; ಅಬಾರ್ಟ್ಗಳು ವೀಡಿಯೊಗಳ ನಡುವೆ ನಿಲ್ಲುತ್ತವೆ ಮತ್ತು ಕಚ್ಚಾ ಮಾಧ್ಯಮಕ್ಕೆ ಎಂದಿಗೂ ತೆರೆದುಕೊಳ್ಳುವುದಿಲ್ಲ.

120 ಸೆಕೆಂಡುಗಳಿಗಿಂತ ಹೆಚ್ಚಿನ ಲೆಗಸಿ ಪರ್ಸಿಸ್ಟೆಡ್ ವೀಡಿಯೊ ಟೈಮ್ಔಟ್ ಮೌಲ್ಯಗಳನ್ನು ಬ್ರೋಕರ್ ಗಡುವಿಗೆ ಕ್ಲ್ಯಾಂಪ್ ಮಾಡಲಾಗುತ್ತದೆ; ಆ ಮಿತಿಗಿಂತ ಹೆಚ್ಚಿನ ಹೊಸ ಸೆಟ್ಟಿಂಗ್ಗಳ ಬರವಣಿಗೆಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. `GET /api/modality-bridge/video/runtime` ದೃಢೀಕರಣ ಅಥವಾ ರನ್ಟೈಮ್ ಪ್ರೋಬಿಂಗ್ಗೆ ಮೊದಲು ವಿಶ್ವಾಸಾರ್ಹ ಸ್ಟ್ಯಾಂಪ್ಡ್ ಲೂಪ್ಬ್ಯಾಕ್ ಸ್ಥಳೀಯತೆಯನ್ನು ಬಯಸುತ್ತದೆ, ನಂತರ ನಿರ್ವಹಣೆ ದೃಢೀಕರಣವನ್ನು ಬಯಸುತ್ತದೆ. ಇದು `available`, ಸ್ಯಾನಿಟೈಸ್ ಮಾಡಿದ FFmpeg/ffprobe ಆವೃತ್ತಿಗಳನ್ನು ಮಾತ್ರ ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಮತ್ತು ರನ್ಟೈಮ್ ಲಭ್ಯವಿಲ್ಲದಿದ್ದಾಗ ಸ್ಥಿರ ಕಾರಣವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಆಂತರಿಕ ಹೊರತೆಗೆಯುವಿಕೆ ಎಂಡ್ಪಾಯಿಂಟ್ ಸಾರ್ವಜನಿಕ ಅಪ್ಲೋಡ್ API ಅಲ್ಲ: ಕ್ಯೂ ಸ್ಯಾಚುರೇಶನ್ `503` ಜೊತೆಗೆ `Retry-After` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ, ಕರೆ ಮಾಡುವವರ ಸಂಪರ್ಕ ಕಡಿತವು `499` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ, ಮತ್ತು ಸ್ಥಿರ ಬ್ರೋಕರ್ ಗಡುವು `504` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಪರಿವರ್ತಿತ ಪ್ರತಿಕ್ರಿಯೆಗಳು ವಿಷನ್ ಅಥವಾ ಆಡಿಯೊ ವಿಭಾಗಗಳನ್ನು ತೆಗೆದುಹಾಕದೆ ಕೇಂದ್ರ `x-omniroute-modality-bridge` ಹೆಡರ್ಗೆ `video->text;model=<visionModel>;parts=<videos>` ಅನ್ನು ಸೇರಿಸುತ್ತವೆ.

### PII ಮಾಸ್ಕರ್ (`piiMasker.ts`)

**ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.

- **`preCall`** ಪೇಲೋಡ್ ಅನ್ನು ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `system`, `messages`, `input`, ಮತ್ತು `prompt` (ಸರಳ ಸ್ಟ್ರಿಂಗ್ ಐಟಂಗಳು ಸೇರಿದಂತೆ) ಮೂಲಕ ನಡೆಯುತ್ತದೆ, ಮತ್ತು ಸ್ಟ್ರಿಂಗ್ `content`/`text` ಕ್ಷೇತ್ರಗಳಿಗೆ `processPII()` ( `@/shared/utils/inputSanitizer` ನಿಂದ) ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ. `PII_REDACTION_ENABLED=true` ಆಗಿರುವಾಗ, ಪತ್ತೆಯಾದ PII ಅನ್ನು ಹೊರಹೋಗುವ ಪೇಲೋಡ್ನಲ್ಲಿ ರೆಡಾಕ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ. ಇದು `INPUT_SANITER_MODE` ನಿಂದ ಸ್ವತಂತ್ರವಾಗಿದೆ (ಇದು ಪ್ರಾಂಪ್ಟ್-ಇಂಜೆಕ್ಷನ್ ನೀತಿಯನ್ನು ಮಾತ್ರ ನಿಯಂತ್ರಿಸುತ್ತದೆ). ರೆಡಾಕ್ಷನ್ ಆಫ್ ಆಗಿರುವಾಗ, ಕರೆಯು ವಿಷಯವನ್ನು ಮರುಬರೆಯದೆ ಪತ್ತೆ ಎಣಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ.
- **`postCall`** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಡೀಪ್-ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `sanitizePIIResponse()` ಜೊತೆಗೆ ರೆಸ್ಪಾನ್ಸಸ್-API-ಆಕಾರ ಮಾಸ್ಕರ್ (`maskResponsesOutput` — `output_text` ಮತ್ತು `output[].content[].text` ಅನ್ನು ಒಳಗೊಂಡಿದೆ) ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಯಾವುದೇ ರೆಡಾಕ್ಷನ್ ಸಂಭವಿಸಿದರೆ, ಮಾರ್ಪಡಿಸಿದ ಪ್ರತಿಕ್ರಿಯೆಯು ಮೂಲವನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.

ಗಾರ್ಡ್ರೈಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಇದು ಕೇವಲ ಟಿಪ್ಪಣಿಗಳನ್ನು ನೀಡುತ್ತದೆ (`meta.detections`, `meta.redacted`) ಅಥವಾ ಮರುಬರೆಯುತ್ತದೆ.

### ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ (`promptInjection.ts`)

ಬಳಕೆದಾರ-ಒದಗಿಸಿದ ವಿಷಯದಲ್ಲಿ ಪ್ರತಿಕೂಲ ರಚನೆಗಳನ್ನು ಪತ್ತೆ ಮಾಡುತ್ತದೆ ಮತ್ತು ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ ನೀತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ. ನಡವಳಿಕೆಯನ್ನು ಪರಿಸರ ವೇರಿಯಬಲ್ಗಳು ಮತ್ತು ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳಿಂದ ನಡೆಸಲಾಗುತ್ತದೆ:

| Setting         | Env var                                                                                               | Default | Effect                                                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` ಆಗಿದ್ದಾಗ, ಗಾರ್ಡ್ರೈಲ್ ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತದೆ.                                                                                                                                                            |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `block`, `warn`, ಅಥವಾ `log`. (`redact` ಅನ್ನು ಬ್ಯಾಕ್-ಕಂಪ್ಯಾಟ್ ಗಾಗಿ ಸ್ವೀಕರಿಸಲಾಗಿದೆ ಆದರೆ ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ; PII ಪುನಃ ಬರೆಯುವ ವಿನಂತಿಯನ್ನು `PII_REDACTION_ENABLED` ನಿಯಂತ್ರಿಸುತ್ತದೆ.) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ನಿರ್ಬಂಧಿಸಲು ಅಗತ್ಯವಿರುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ. ಡೀಫಾಲ್ಟ್ನಲ್ಲಿ ಮಧ್ಯಮವು ಕೇವಲ ವೀಕ್ಷಣೆ-ಮಾತ್ರ.                                                                                                                                   |

**Mode precedence** (`getMode`): ಕಾಲರ್ `options.mode` →
`INJECTION_GUARD_MODE` **DB ಫೀಚರ್-ಫ್ಲಾಗ್ ಓವರ್ರೈಡ್** (ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು →
ಫೀಚರ್ ಫ್ಲಾಗ್ಗಳು) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. ಆದ್ದರಿಂದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಓವರ್ರೈಡ್ env ವೇರಿಯಬಲ್ಗಳಿಗಿಂತ ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತದೆ, ಇದರಿಂದ ಫೀಚರ್
ಫ್ಲಾಗ್ಗಳ UI ಚಾಲನೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ ಅನ್ನು ಲೈವ್ ಆಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ (ಮರುಪ್ರಾರಂಭವಿಲ್ಲದೆ). DB ಓದುವಿಕೆ ಫೇಲ್-ಸೇಫ್ ಆಗಿದೆ:
ಅದು ದೋಷವನ್ನು ನೀಡಿದರೆ, ಗಾರ್ಡ್ env-ಆಧಾರಿತ ನಡವಳಿಕೆಗೆ ಹಿಂತಿರುಗುತ್ತದೆ, ಮತ್ತು ಯಾವುದೇ
ಓವರ್ರೈಡ್ ಅನ್ನು ಹೊಂದಿಸದಿದ್ದಾಗ ನಡವಳಿಕೆಯು env-ಮಾತ್ರ ರೆಸಲ್ಯೂಶನ್ಗೆ ಹೋಲುತ್ತದೆ.

ಪತ್ತೆ ಮೂಲಗಳು:

1. `@/shared/utils/inputSanitizer` ನಿಂದ `sanitizeRequest()` (ಪೈಪ್ಲೈನ್ನಲ್ಲಿ ಬೇರೆಡೆ ಬಳಸುವ ಹಂಚಿದ ಡಿಟೆಕ್ಟರ್
   ಸೆಟ್).
2. ಅಂತರ್ನಿರ್ಮಿತ `DEFAULT_GUARD_PATTERNS` (ಪ್ರಸ್ತುತ `system_override_inline` ಮತ್ತು
   `markdown_system_block`, ಎರಡೂ `high` ತೀವ್ರತೆ).
3. ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳ ಮೂಲಕ ರವಾನಿಸಲಾದ ಐಚ್ಛಿಕ `customPatterns` (ಸ್ಟ್ರಿಂಗ್ಗಳು, ರೆಜೆಕ್ಸ್,
   ಅಥವಾ `{ name, pattern, severity }` ದಾಖಲೆಗಳು).

`mode === "block"` **ಮತ್ತು** ಕನಿಷ್ಠ ಒಂದು ಪತ್ತೆಯು ತೀವ್ರತೆಯ
ಮಿತಿಯನ್ನು ಪೂರೈಸಿದಾಗ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. `warn`/`log` ಮೋಡ್ಗಳಲ್ಲಿ ಗಾರ್ಡ್ರೈಲ್ ಲಾಗ್ ಮಾಡುತ್ತದೆ ಆದರೆ
ಕರೆಯನ್ನು ಅನುಮತಿಸುತ್ತದೆ. ರಿಜಿಸ್ಟ್ರಿ ಮೂಲಕ ಹೋಗದೆ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡಬೇಕಾದ
ಕಾಲರ್ಗಳಿಗಾಗಿ ಹಂಚಿದ ಸಹಾಯಕ `evaluatePromptInjection()` ಅನ್ನು ಸಹ ರಫ್ತು ಮಾಡಲಾಗುತ್ತದೆ.

**ಸ್ಕ್ಯಾನ್ ಬೌಂಡ್ (v3.8.20):** ಡಿಟೆಕ್ಟರ್ ಜಾಯಿನ್ ಮಾಡಿದ ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯದ **ಮೊದಲ 16 KB** ಅನ್ನು ಮಾತ್ರ ಪರಿಶೀಲಿಸುತ್ತದೆ — `src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿ `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ಬೈಟ್ಗಳು). `detectInjection()` ಮತ್ತು `evaluatePromptInjection()` ಎರಡೂ ಪ್ಯಾಟರ್ನ್ ಲೂಪ್ ಅನ್ನು ಚಲಾಯಿಸುವ ಮೊದಲು `slice(0, MAX_INJECTION_SCAN_BYTES)` ಅನ್ನು ಬಳಸುತ್ತವೆ. ಇಂಜೆಕ್ಷನ್ ನಿರ್ದೇಶನಗಳು ಇನ್ಪುಟ್ನ ಮೇಲ್ಭಾಗದಲ್ಲಿರುತ್ತವೆ, ಆದ್ದರಿಂದ ಇದು ಪತ್ತೆಯನ್ನು ದುರ್ಬಲಗೊಳಿಸದೆ ನೂರಾರು-KB ಪೇಲೋಡ್ಗಳಲ್ಲಿ ರೆಜೆಕ್ಸ್ CPU/GC ಅನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ (cf. #3932, #4041).

### ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಮಾಸ್ಕರ್ (`credentialMasker.ts`)

ಎರಡೂ ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ, ಡೀಫಾಲ್ಟ್ ಚೈನ್ನಲ್ಲಿ ಕೊನೆಯದು (ಆದ್ಯತೆ `95`). ಹೊರಹೋಗುವ ಪೇಲೋಡ್ನಿಂದ (ಸಂದೇಶ ವಿಷಯ, ಟೂಲ್-ಕಾಲ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳು, ಟೂಲ್ ಫಲಿತಾಂಶಗಳು) **ಮತ್ತು** ಪ್ರೊವೈಡರ್ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ ಸುಪರಿಚಿತ API-ಕೀ / ಸೀಕ್ರೆಟ್-ಟೋಕನ್ ಪ್ಯಾಟರ್ನ್ಗಳನ್ನು ರೆಡಾಕ್ಟ್ ಮಾಡುತ್ತದೆ, ಇದರಿಂದ ಪ್ರಾಂಪ್ಟ್ಗೆ ಅಂಟಿಸಿದ (ಅಥವಾ ಟೂಲ್ ಫಲಿತಾಂಶದಿಂದ ಮರಳಿ ಪ್ರತಿಧ್ವನಿಸಿದ) ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರೊವೈಡರ್ಗೆ ಅಥವಾ ಕ್ಲೈಂಟ್ಗೆ ಸೋರಿಕೆಯಾಗುವುದಿಲ್ಲ.

- **ಆಯ್ಕೆ-ಮಾತ್ರ**, PII ರೆಡಾಕ್ಷನ್ಗೆ ಅದೇ ಸಂಪ್ರದಾಯ (ಹಾರ್ಡ್ ರೂಲ್ #20-ಸಮೀಪ): `settings.credentialRedactionEnabled === true` **ಅಥವಾ** `CREDENTIAL_REDACTION_ENABLED=true` ಆಗದ ಹೊರತು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ. ಅದು ಆಫ್ ಆಗಿದ್ದರೆ, ಗಾರ್ಡ್ರೈಲ್ ಯಾವುದೇ ಕಾರ್ಯಾಚರಣೆ ಮಾಡುವುದಿಲ್ಲ — ಅದು ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ ಮತ್ತು ಎಂದಿಗೂ ಪುನಃ ಬರೆಯುವುದಿಲ್ಲ.
- `redactCredentials()` ಸಂಪೂರ್ಣ ಪೇಲೋಡ್/ಪ್ರತಿಕ್ರಿಯೆ ಟ್ರೀ ಅನ್ನು (`walkValue()`, ಪ್ರೋಟೋಟೈಪ್-ಪೊಲ್ಯೂಷನ್-ಸುರಕ್ಷಿತ, `WeakSet` ಮೂಲಕ ಸೈಕಲ್-ಸುರಕ್ಷಿತ) ಪರಿಶೀಲಿಸುತ್ತದೆ ಮತ್ತು ಹೊಂದಾಣಿಕೆಗಳನ್ನು `[REDACTED:<type>]` ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ನೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತದೆ, ನಿಜವಾಗಿ ಬದಲಾದ ಶಾಖೆಗಳನ್ನು ಮಾತ್ರ ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ.
- `CREDENTIAL_PATTERNS` LLM ಪ್ರೊವೈಡರ್ ಕೀಗಳನ್ನು (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ಟೋಕನ್ಗಳನ್ನು (GitHub, Slack, Linear, Notion, npm, Postman, Discord), ಪಾವತಿ ಕೀಗಳನ್ನು (Stripe, Square), ಕ್ಲೌಡ್ ಕೀಗಳನ್ನು (AWS access key, Twilio, SendGrid, Mailgun), ಖಾಸಗಿ ಕೀಗಳು / JWT ಗಳು, ಕ್ರೆಡೆನ್ಶಿಯಲ್-ಹೊಂದಿರುವ ಸಂಪರ್ಕ ಸ್ಟ್ರಿಂಗ್ಗಳನ್ನು (`mongodb://user:pass@...`, ಇತ್ಯಾದಿ), ಮತ್ತು ಸಾಮಾನ್ಯ `Authorization`/`x-api-key`/`api-key`/`apikey` ಹೆಡರ್-ಮೌಲ್ಯ ಪ್ಯಾಟರ್ನ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಹೆಡರ್-ಆಕಾರದ ಕೀಗಳನ್ನು (`authorization`, `x-api-key`, `api-key`, `apikey`) ರಚನಾತ್ಮಕವಾಗಿ (ಮೌಲ್ಯ ಮಾತ್ರ, `Bearer `/`Basic ` ನಂತಹ ಸ್ಕೀಮ್ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸಂರಕ್ಷಿಸಲಾಗಿದೆ) ಸಾಮಾನ್ಯ ಪಠ್ಯ ರೆಜೆಕ್ಸ್ ಮೂಲಕವಲ್ಲದೆ ರೆಡಾಕ್ಟ್ ಮಾಡಲಾಗುತ್ತದೆ.
- ಗಾರ್ಡ್ರೈಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಕೇವಲ ಪುನಃ ಬರೆಯುತ್ತದೆ (`modifiedPayload` / `modifiedResponse`) ಮತ್ತು ಟಿಪ್ಪಣಿಗಳನ್ನು ನೀಡುತ್ತದೆ (`meta.credentialsRedacted`, `meta.count`).

ರಿಗ್ರೆಷನ್ ಗಾರ್ಡ್: `tests/unit/credential-masker-guardrail.test.ts`.

## ಮೂಲ ಒಪ್ಪಂದ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ಸರಪಳಿಯನ್ನು ತಕ್ಷಣವೇ ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ
  message?: string; // ನಿರ್ಬಂಧಿಸುವಾಗ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ವಿನಂತಿಯನ್ನು ಮರುಬರೆಯಲು preCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
  modifiedResponse?: TValue; // ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯಲು postCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, ಅಥವಾ `{ block: false }` ಇವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ ಹಿಂತಿರುಗಿಸುವ ಮೂಲಕ guardrail "ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲ" ಎಂದು ಸೂಚಿಸುತ್ತದೆ. `modifiedPayload`/`modifiedResponse` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವುದರಿಂದ, ನಂತರದ guardrailಗಳಿಗಾಗಿ ಸರಪಳಿಯ ಮೂಲಕ ಹರಿಯುವ ಮೌಲ್ಯವನ್ನು ಅದು ಬದಲಿಸುತ್ತದೆ.
`signal?: AbortSignal` ಕಾಲರ್ನ ಜೀವನಚಕ್ರವನ್ನು guardrailಗಳಿಗೆ ಒಯ್ಯುತ್ತದೆ. ವಿನಂತಿಯ ರದ್ದತಿಯು ಉದ್ದೇಶಪೂರ್ವಕ fail-open ಅಪವಾದವಾಗಿದೆ: media bridgeಗಳು ಕೆಲಸವನ್ನು ನಿಲ್ಲಿಸಿ cleanup ಮಾಡುತ್ತವೆ ಮತ್ತು ಅದನ್ನು ಬೆಂಬಲಿಸುವುದಿಲ್ಲ ಎಂದು ತಿಳಿದಿರುವ ಗುರಿಗೆ raw media ಅನ್ನು ಮರುಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

## ರಿಜಿಸ್ಟ್ರಿ (`registry.ts`)

singleton `guardrailRegistry` ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

- `register(guardrail)` — guardrail ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಅಥವಾ normalized name ಆಧಾರದಲ್ಲಿ ಬದಲಿಸುತ್ತದೆ) ಮತ್ತು ಏರಿಕೆ ಕ್ರಮದ `priority` ಪ್ರಕಾರ ಮರು-ವಿಂಗಡಿಸುತ್ತದೆ.
- `clear()` / `list()` — ಆಡಳಿತಾತ್ಮಕ ಸಹಾಯಕಗಳು.
- `runPreCallHooks(payload, context)` — ಸಕ್ರಿಯ guardrailಗಳ ಮೂಲಕ ಪುನರಾವರ್ತಿಸುತ್ತದೆ, `modifiedPayload` ಮೂಲಕ payload ಅನ್ನು ಮುಂದಕ್ಕೆ ಕೊಂಡೊಯ್ಯುತ್ತದೆ ಮತ್ತು ಮೊದಲ `block: true` ದೊರೆತಾಗ ನಿಲ್ಲುತ್ತದೆ.
- `runPostCallHooks(response, context)` — response ಭಾಗದಲ್ಲಿಯೂ ಇದೇ ಹರಿವನ್ನು ಅನುಸರಿಸುತ್ತದೆ.
- `resetGuardrailsForTests({ registerDefaults })` — ಸ್ಥಿತಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಸ್ವಚ್ಛ test isolationಗಾಗಿ ಐಚ್ಛಿಕವಾಗಿ defaults ಅನ್ನು ಮರು-ನೋಂದಾಯಿಸುತ್ತದೆ.

ಎರಡೂ runnerಗಳು `{ blocked, payload|response, results, guardrail?, message? }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ, ಇಲ್ಲಿ `results` ಎಂಬುದು ಪ್ರತಿಯೊಂದು guardrailಗೆ ಸಂಬಂಧಿಸಿದ `blocked`, `skipped`, `modified`, `error`, ಮತ್ತು `meta` ಕ್ಷೇತ್ರಗಳನ್ನು ಒಳಗೊಂಡಿರುವ `GuardrailExecutionResult` recordಗಳ array ಆಗಿದ್ದು, tracingಗೆ ಉಪಯುಕ್ತವಾಗಿದೆ.

### ಪ್ರತಿ ವಿನಂತಿಗೆ Guardrailಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ಪ್ರಸ್ತುತ ವಿನಂತಿಗಾಗಿ ಬಿಟ್ಟುಬಿಡಬೇಕಾದ guardrail ಹೆಸರುಗಳ duplicate ತೆಗೆದುಹಾಕಿದ ಪಟ್ಟಿಯನ್ನು ಒಟ್ಟುಗೂಡಿಸುತ್ತದೆ. ಮೂಲಗಳು (ಎಲ್ಲವೂ ಐಚ್ಛಿಕ, ಎಲ್ಲವನ್ನೂ ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ):

- `apiKeyInfo.disabledGuardrails`
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `disabledGuardrails` (top-level)
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (ಅಥವಾ ಹಳೆಯ
  `x-disabled-guardrails`)

ಮೌಲ್ಯಗಳು stringಗಳ array ಆಗಿರಬಹುದು ಅಥವಾ comma-separated string ಆಗಿರಬಹುದು; ಹೆಸರುಗಳನ್ನು lowercase kebab-caseಗೆ normalize ಮಾಡಲಾಗುತ್ತದೆ (`pii_masker` → `pii-masker`). ಫಲಿತಾಂಶವನ್ನು `context.disabledGuardrails` ಮೂಲಕ registryಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಅದು ಹೊಂದಿಕೆಯಾಗುವ guardrailಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`results` ನಲ್ಲಿ `skipped: true`).

## ಕಾರ್ಯಗತಗೊಳಿಸುವ ಕ್ರಮ

`src/sse/handlers/chat.ts` ಮತ್ತು
`open-sse/handlers/chatCore.ts` ಮೂಲಕ ಹರಿಯುವ ಪ್ರತಿ ವಿನಂತಿಗಾಗಿ:

1. `resolveDisabledGuardrails(...)` API ಕೀ, ಬಾಡಿ ಮತ್ತು ಹೆಡರ್ಗಳಿಂದ ಬಿಟ್ಟುಬಿಡುವ ಪಟ್ಟಿಯನ್ನು ರಚಿಸುತ್ತದೆ.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಆದ್ಯತೆಯ ಆರೋಹಣ ಕ್ರಮದಲ್ಲಿ ಚಲಾಯಿಸುತ್ತದೆ:
   - ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `skipped` ಎಂದು ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
   - ಪ್ರತಿ ಗಾರ್ಡ್ರೇಲ್ನ `preCall`, `modifiedPayload` ಮೂಲಕ ಪೇಲೋಡ್ ಅನ್ನು ಮರುಬರೆಯಬಹುದು.
   - ಮೊದಲ `block: true` ಸರಪಳಿಯನ್ನು ಅಲ್ಲಿಯೇ ನಿಲ್ಲಿಸುತ್ತದೆ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ ಗಾರ್ಡ್ರೇಲ್ ನಿರಾಕರಣೆಯ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
3. (ಸಂಭಾವ್ಯವಾಗಿ ಮರುಬರೆಯಲಾದ) ಪೇಲೋಡ್ ಕಾಂಬೊ ರೂಟಿಂಗ್ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಹರಿಯುತ್ತದೆ.
4. ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಜೋಡಿಸಿದ ನಂತರ, `guardrailRegistry.runPostCallHooks(...)` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೇಲೆ ಅದೇ ಸರಪಳಿಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇಲ್ಲಿ `block: true` ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಕೈಬಿಡುತ್ತದೆ.

ದೋಷ ಎಸೆಯುವ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `error: <message>` ಜೊತೆಗೆ ದಾಖಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`logger.warn` ಮೂಲಕ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸರಪಳಿ ಮುಂದುವರಿಯುತ್ತದೆ — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ದೋಷ ಸಂಭವಿಸಿದಾಗಲೂ ಅನುಮತಿಸಲಾಗುತ್ತದೆ.

## ಕಸ್ಟಮ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ಹಂತಗಳು:

1. `BaseGuardrail` ಅನ್ನು ವಿಸ್ತರಿಸುವ `src/lib/guardrails/myGuardrail.ts` ಅನ್ನು ರಚಿಸಿ.
2. `preCall` ಮತ್ತು/ಅಥವಾ `postCall` ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ.
3. ಇಂಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿಯೇ ನೋಂದಾಯಿಸಿ (`registerDefaultGuardrails` ನಿಂದ ಪುಶ್ ಮಾಡಿ) ಅಥವಾ
   ರನ್ಟೈಮ್ನಲ್ಲಿ `guardrailRegistry.register(...)` ಅನ್ನು ಕರೆ ಮಾಡಿ — ಅದೇ ಸಾಮಾನ್ಯೀಕರಿಸಿದ
   ಹೆಸರನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಹಿಂದಿನ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ರಿಜಿಸ್ಟ್ರಿ ಬದಲಿಸುತ್ತದೆ.
4. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉದಾಹರಣೆಗಳು:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ಪರೀಕ್ಷೆ

ತಿಳಿದಿರುವ ಸ್ಥಿತಿಯಿಂದ ಪ್ರಾರಂಭಿಸಲು ಪರೀಕ್ಷೆಗಳ ನಡುವೆ `resetGuardrailsForTests()` ಅನ್ನು ಬಳಸಿ.
ಖಾಲಿ ರಿಜಿಸ್ಟ್ರಿಯೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಲು `{ registerDefaults: false }` ಅನ್ನು ಪಾಸ್ ಮಾಡಿ ಮತ್ತು
ಪರೀಕ್ಷೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಮಾತ್ರ ನೋಂದಾಯಿಸಿ. Vision Bridge ಡಿಪೆಂಡೆನ್ಸಿ
ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge,
ಸೆಟ್ಟಿಂಗ್ಗಳು, ಸಾಮರ್ಥ್ಯಗಳು, STT ಮಾದರಿ ಆಯ್ಕೆ, ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು
ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ಗಾಗಿ ಸಮಾನವಾದ ಸೀಮ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು DB
ಅಥವಾ ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶವಿಲ್ಲದೆಯೇ ಎರಡೂ ಫ್ಲೋಗಳನ್ನು ಪರೀಕ್ಷಿಸಬಹುದು.

## ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ರೂಟ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು ರೆಡ್-ಟೀಮ್ (ಹಂತ 8 · ಬ್ಲಾಕ್ D)

ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ (`createInjectionGuard` / `withInjectionGuard`) ಬಳಕೆದಾರರ
ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸ್ವೀಕರಿಸುವ ಎಲ್ಲಾ ರೂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. ಇದು `INJECTION_GUARD_MODE`
ಅನ್ನು ಗೌರವಿಸುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `warn` = ಲಾಗ್ ಮಾತ್ರ; `block` = HTTP 400 `SECURITY_001` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ).

| ಪ್ರಕಾರ                     | ರೂಟ್ಗಳು                                                                                                                                              | ಡೀಫಾಲ್ಟ್ ಮೋಡ್ |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| ಪಠ್ಯ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವುದು) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| ಜನರೇಟಿವ್                   | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| ಡೇಟಾ                       | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

ಪಠ್ಯ ಹೊರತೆಗೆಯುವಿಕೆ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ.

**ರೆಡ್-ಟೀಮ್ (ಪ್ರತಿ ರಾತ್ರಿ, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block`
ನಲ್ಲಿ ಪ್ರತಿಯೊಂದು ರೂಟ್, `OWASP-LLM` ಕಾರ್ಪಸ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಎಂಬುದನ್ನು promptfoo
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; garak ಪ್ರೋಬ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ).
ಸ್ಥಿರತೆಗಾಗಿ `moderations` ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ — ಬ್ಲಾಕ್-ಮೋಡ್ನಲ್ಲಿರುವ ಆಪರೇಟರ್ಗಳು
`resolveDisabledGuardrails` ಮೂಲಕ ಅದಕ್ಕೆ ವಿನಾಯಿತಿ ನೀಡಬಹುದು.

ಪ್ರತಿ ರಾತ್ರಿಯ ವರ್ಕ್ಫ್ಲೋ (`.github/workflows/nightly-llm-security.yml`, cron + ಮ್ಯಾನುಯಲ್
ಡಿಸ್ಪ್ಯಾಚ್) ಎರಡು ಜಾಬ್ಗಳನ್ನು ಹೊಂದಿದೆ:

- **`promptfoo-guard` (ನಿರ್ಬಂಧಿಸುವುದು)** — `INJECTION_GUARD_MODE=block` ಜೊತೆಗೆ
  `promptfoo eval -c promptfooconfig.yaml` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಪ್ರತಿಕೂಲ
  ಪ್ರಕರಣವು (ಉದಾ. "ಹಿಂದಿನ ಎಲ್ಲಾ ಸೂಚನೆಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸಿ…", DAN-ಶೈಲಿಯ ಜೈಲ್ಬ್ರೇಕ್ಗಳು)
  ಪ್ರತಿಕ್ರಿಯೆಯು `error.code === "SECURITY_001"` ಅನ್ನು ಹೊಂದಿದೆ ಎಂದು ದೃಢೀಕರಿಸುತ್ತದೆ,
  ಅಂದರೆ ಗಾರ್ಡ್ ನಿಜವಾಗಿಯೂ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಿದೆ.
- **`garak` (ಸಲಹಾತ್ಮಕ)** — ಸ್ಥಳೀಯ OmniRoute ಇನ್ಸ್ಟನ್ಸ್
  (`http://localhost:20128/v1`) ವಿರುದ್ಧ garak `--probes promptinject,dan,leakreplay`
  ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇದು ಪ್ರೊವೈಡರ್ ಸೀಕ್ರೆಟ್ (`PROMPTFOO_PROVIDER_KEY`) ಮೇಲೆ
  ಅವಲಂಬಿತವಾಗಿದೆ; ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಸರಾಗವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು `|| true`
  ಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ, ಆದ್ದರಿಂದ CI ವಿಫಲಗೊಳಿಸದೆಯೇ ವರದಿ ಮಾಡುತ್ತದೆ.

ಗಾರ್ಡ್ ಹೆಲ್ಪರ್ನ (`createInjectionGuard` / `withInjectionGuard`) ವ್ಯಾಪ್ತಿಯು ಪ್ರಾಂಪ್ಟ್
ಹೊಂದಿರುವ ಪ್ರತಿಯೊಂದು `/v1` ರೂಟ್ಗೆ ವಿಸ್ತರಿಸುತ್ತದೆ; ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯವನ್ನು
`src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿರುವ `extractMessageContents()` ಮೂಲಕ
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ನಿಂದ
ಪಡೆಯಲಾಗುತ್ತದೆ.
