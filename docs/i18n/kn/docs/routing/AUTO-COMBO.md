## ಶೂನ್ಯ-ಕಾನ್ಫಿಗರೇಶನ್ ಸ್ವಯಂ-ರೂಟಿಂಗ್ (`auto/` ಪೂರ್ವಪ್ರತ್ಯಯ)

> **ಹೊಸದು:** ಕಾಂಬೊ ರಚಿಸುವ ಅಗತ್ಯವಿಲ್ಲ. ಯಾವುದೇ ಕ್ಲೈಂಟ್ನಲ್ಲಿ ನೇರವಾಗಿ `auto/` ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಬಳಸಿ.

### ತ್ವರಿತ ಉದಾಹರಣೆಗಳು

| ಮಾದರಿ ID       | ವೇರಿಯಂಟ್ | ವರ್ತನೆ                                                               |
| -------------- | -------- | -------------------------------------------------------------------- |
| `auto`         | default  | ಸಂಪರ್ಕಗೊಂಡಿರುವ ಎಲ್ಲಾ ಪೂರೈಕೆದಾರರು, LKGP ತಂತ್ರ, ಸಮತೋಲಿತ ತೂಕಗಳು         |
| `auto/coding`  | coding   | ಗುಣಮಟ್ಟಕ್ಕೆ ಆದ್ಯತೆಯ ತೂಕಗಳು, ಕೋಡ್ ರಚನೆಗೆ ಸೂಕ್ತ                        |
| `auto/fast`    | fast     | ಕಡಿಮೆ-ವಿಳಂಬದ ತೂಕ ನೀಡಿದ ಆಯ್ಕೆ                                         |
| `auto/cheap`   | cheap    | ವೆಚ್ಚಕ್ಕೆ ಹೊಂದುವಂತೆ ಆಪ್ಟಿಮೈಸ್ ಮಾಡಿದ ರೂಟಿಂಗ್ (ಮೊದಲು ಅತಿ ಕಡಿಮೆ ವೆಚ್ಚ)  |
| `auto/offline` | offline  | ಅತ್ಯಧಿಕ ಕೋಟಾ ಲಭ್ಯತೆಯಿರುವ ಪೂರೈಕೆದಾರರಿಗೆ ಆದ್ಯತೆ ನೀಡುತ್ತದೆ              |
| `auto/smart`   | smart    | ಉತ್ತಮ ಮಾದರಿ ಪತ್ತೆಗಾಗಿ ಗುಣಮಟ್ಟಕ್ಕೆ ಆದ್ಯತೆ + ಹೆಚ್ಚಿನ ಅನ್ವೇಷಣಾ ದರ (10%) |
| `auto/lkgp`    | lkgp     | ಸ್ಪಷ್ಟವಾದ LKGP (ಡೀಫಾಲ್ಟ್ `auto`ಗೆ ಸಮಾನ)                              |
| `auto/chaos`   | chaos    | ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ ಪರೀಕ್ಷೆಗಾಗಿ ದೋಷ-ಅಳವಡಿಕೆ ತೂಕಗಳು (ಕೆಯಾಸ್ ಎಂಜಿನಿಯರಿಂಗ್) |

### ವರ್ಗ × ಟಿಯರ್ ಸಂಯೋಜನೆ (`auto/<category>:<tier>`)

OpenRouter-ಶೈಲಿಯ ಪ್ರತ್ಯಯಗಳು **ಯಾವ ರೀತಿಯ ರೂಟ್** (ವರ್ಗ) ಎಂಬುದನ್ನು **ಅದನ್ನು ಹೇಗೆ ಆಪ್ಟಿಮೈಸ್ ಮಾಡಬೇಕು** (ಟಿಯರ್) ಎಂಬುದರಿಂದ ಪ್ರತ್ಯೇಕಿಸುತ್ತವೆ, ಆದ್ದರಿಂದ ಅವುಗಳನ್ನು ನೀವು ಮುಕ್ತವಾಗಿ ಸಂಯೋಜಿಸಬಹುದು (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ವರ್ಗಗಳು** (ಸಾಮರ್ಥ್ಯದ ಆಧಾರದ ಮೇಲೆ ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಅನ್ನು ಫಿಲ್ಟರ್ ಮಾಡಿ): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` ದೃಶ್ಯ-ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾದರಿಗಳನ್ನು ಉಳಿಸುತ್ತವೆ; `reasoning` ತಾರ್ಕಿಕ/ಚಿಂತನಾ ಮಾದರಿಗಳನ್ನು ಉಳಿಸುತ್ತದೆ.
- **ಟಿಯರ್ಗಳು** (ಸ್ಕೋರಿಂಗ್ ತೂಕಗಳು / ಪೂಲ್ ಫಿಲ್ಟರ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ): `fast` (ವೇಗವಾಗಿ ಬಿಡುಗಡೆ) · `cheap` (`floor` ಎಂಬ ಅಲಿಯಾಸ್, ವೆಚ್ಚ-ಉಳಿತಾಯ) · `reliable` (ಸರ್ಕ್ಯೂಟ್-ಬ್ರೇಕರ್ ಆರೋಗ್ಯ + ವಿಳಂಬದ ಸ್ಥಿರತೆ) · `free` / `pro` (`classifyTier` ಮೂಲಕ ಮಾದರಿ ಟಿಯರ್ ಆಧಾರದಲ್ಲಿ ಪೂಲ್ ಅನ್ನು ಫಿಲ್ಟರ್ ಮಾಡಿ — ಉಚಿತ ಟಿಯರ್ ಮತ್ತು ಪ್ರೀಮಿಯಂ).

| ಉದಾಹರಣೆ                | ಈ ರೀತಿಯಾಗಿ ಪರಿಹರಿಸಲಾಗುತ್ತದೆ                                                         |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `auto/coding:fast`     | ಕೋಡಿಂಗ್ ಪೂಲ್, ಕಡಿಮೆ-ವಿಳಂಬದ ತೂಕಗಳು                                                   |
| `auto/coding:cheap`    | ಕೋಡಿಂಗ್ ಪೂಲ್, ವೆಚ್ಚಕ್ಕೆ ಹೊಂದುವಂತೆ ಆಪ್ಟಿಮೈಸ್ ಮಾಡಲಾಗಿದೆ (`auto/coding:floor` ಅಲಿಯಾಸ್) |
| `auto/reasoning:pro`   | ತಾರ್ಕಿಕ/ಚಿಂತನಾ ಮಾದರಿಗಳು ಮಾತ್ರ, ಪ್ರೀಮಿಯಂ ಟಿಯರ್                                       |
| `auto/vision`          | ದೃಶ್ಯ-ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾದರಿಗಳು (ಟಿಯರ್ ಇಲ್ಲ → ಸಮತೋಲಿತ ತೂಕಗಳು)                          |
| `auto/multimodal:free` | ಬಹುಮಾಧ್ಯಮ-ಸಾಮರ್ಥ್ಯವಿರುವ ಮಾದರಿಗಳು, ಉಚಿತ ಟಿಯರ್ ಮಾತ್ರ                                  |

ಯಾವುದೇ ಮಾನ್ಯವಾದ `auto/<category>[:<tier>]` ಅನ್ನು ಅಗತ್ಯವಿದ್ದಾಗ ಪರಿಹರಿಸಲಾಗುತ್ತದೆ; ಆಯ್ದ ಉಪಸಮೂಹವನ್ನು `/v1/models` ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಜಾಹೀರಾತು ಮಾಡಲಾಗುತ್ತದೆ (`open-sse/services/autoCombo/builtinCatalog.ts`ನಲ್ಲಿರುವ `AUTO_SUFFIX_VARIANTS`). ಫಿಲ್ಟರಿಂಗ್ **fail-open** ಆಗಿದೆ — ಯಾವುದೇ ನಿರ್ಬಂಧಕ್ಕೆ ಸಂಪರ್ಕಗೊಂಡ ಮಾದರಿಗಳು ಹೊಂದಿಕೆಯಾಗದಿದ್ದರೆ, ರೂಟಿಂಗ್ ಎಂದಿಗೂ ವಿಫಲವಾಗದಂತೆ ಸಂಪೂರ್ಣ ಪೂಲ್ ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ. ಕೋರ್ ಸ್ಕೋರರ್ (`combo.ts`) ಬದಲಾಗಿಲ್ಲ; ವರ್ಗ/ಟಿಯರ್ ಫಿಲ್ಟರ್ ಅನ್ನು `buildAutoCandidates`ನಲ್ಲಿ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ.

> **ಲೈವ್ ಮಾದರಿ ಬುದ್ಧಿಮತ್ತೆ:** `ARENA_ELO_SYNC_ENABLED` ಫ್ಲ್ಯಾಗ್ ಆನ್ ಆಗಿರುವಾಗ, ಲೈವ್ **Arena ELO** ಶ್ರೇಯಾಂಕಗಳು + **models.dev** ಟಿಯರ್ ಡೇಟಾ ಸ್ವಯಂ-ರೂಟಿಂಗ್ನ ಸೂಕ್ತತೆಯನ್ನು ನಿರ್ಧರಿಸಲು ನೆರವಾಗುತ್ತವೆ (ಇಲ್ಲದಿದ್ದರೆ ಸ್ಥಿರ ಫಿಟ್ನೆಸ್ ಮ್ಯಾಪ್ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ).

**ಬಳಸುವ ವಿಧಾನ:**

```bash
# OpenAI ಸ್ವರೂಪವನ್ನು ಬೆಂಬಲಿಸುವ ಯಾವುದೇ IDE ಅಥವಾ CLI ಉಪಕರಣ
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ನಿಮ್ಮ ಕೋಡ್/ಕಾನ್ಫಿಗ್ನಲ್ಲಿ model ಅನ್ನು ಹೀಗೆ ಹೊಂದಿಸಿ:
model: "auto"                 # ಸಮತೋಲಿತ ಡೀಫಾಲ್ಟ್
model: "auto/coding"          # ಕೋಡಿಂಗ್ ಕಾರ್ಯಗಳಿಗೆ ಅತ್ಯುತ್ತಮ
model: "auto/fast"            # ಲಭ್ಯವಿರುವುದರಲ್ಲಿ ಅತ್ಯಂತ ವೇಗವಾದದ್ದು
model: "auto/cheap"           # ಪ್ರತಿ ಟೋಕನ್ಗೆ ಅತ್ಯಂತ ಅಗ್ಗವಾದದ್ದು
```

**ಏನಾಗುತ್ತದೆ:**

1. OmniRoute, `src/sse/handlers/chat.ts`ನಲ್ಲಿ `auto/` ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಪತ್ತೆಮಾಡುತ್ತದೆ
2. ಡೇಟಾಬೇಸ್ನಿಂದ ಎಲ್ಲಾ **ಸಕ್ರಿಯ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳನ್ನು** ಕ್ವೆರಿ ಮಾಡುತ್ತದೆ
3. ಮಾನ್ಯ ಕ್ರೆಡೆನ್ಷಿಯಲ್ಗಳನ್ನು (API ಕೀ ಅಥವಾ OAuth ಟೋಕನ್) ಹೊಂದಿರುವವುಗಳಿಗೆ ಫಿಲ್ಟರ್ ಮಾಡುತ್ತದೆ
4. ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೆ ಮಾದರಿಯನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ (`connection.defaultModel` ಅಥವಾ ಪೂರೈಕೆದಾರರ ಮೊದಲ ಮಾದರಿ)
5. ಮೆಮೊರಿಯಲ್ಲಿ **ವರ್ಚುವಲ್ ಕಾಂಬೊ** ನಿರ್ಮಿಸುತ್ತದೆ (DBಯಲ್ಲಿ ಸಂಗ್ರಹಿಸುವುದಿಲ್ಲ)
6. ಆಯ್ಕೆಮಾಡಿದ ವೇರಿಯಂಟ್ನ ತೂಕದ ಪ್ರೊಫೈಲ್ + LKGP ತಂತ್ರವನ್ನು ಬಳಸಿ ರೂಟ್ ಮಾಡುತ್ತದೆ

**ಪ್ರಮುಖ ಗುಣಲಕ್ಷಣಗಳು:**

- ✅ **ಯಾವಾಗಲೂ ಆನ್:** ಯಾವುದೇ ಟಾಗಲ್, ಕಾಂಬೊ ರಚನೆ ಅಥವಾ ಕಾನ್ಫಿಗರೇಶನ್ ಅಗತ್ಯವಿಲ್ಲ
- ✅ **ಡೈನಾಮಿಕ್:** ಪ್ರಸ್ತುತ ಸಂಪರ್ಕಗೊಂಡ ಪೂರೈಕೆದಾರರನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ
- ✅ **ಸೆಷನ್ ಸ್ಥಿರತೆ:** ಕೊನೆಯ ಯಶಸ್ವಿ ಪೂರೈಕೆದಾರರಿಗೆ ಆದ್ಯತೆ ನೀಡುವುದನ್ನು LKGP ಖಚಿತಪಡಿಸುತ್ತದೆ
- ✅ **ಬಹು-ಖಾತೆ ಅರಿವು:** ಪ್ರತಿ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕವು ಪ್ರತ್ಯೇಕ ಅಭ್ಯರ್ಥಿಯಾಗುತ್ತದೆ
- ✅ **DB ಬರಹಗಳಿಲ್ಲ:** ವರ್ಚುವಲ್ ಕಾಂಬೊ ವಿನಂತಿಗಾಗಿ ಮಾತ್ರ ಅಸ್ತಿತ್ವದಲ್ಲಿರುತ್ತದೆ, ನಿರಂತರ ಸಂಗ್ರಹಣೆಯ ಓವರ್ಹೆಡ್ ಶೂನ್ಯ

### ಪ್ರತಿ-ಕೀ ಅಭ್ಯರ್ಥಿ ನಿಯಂತ್ರಣ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` ನಂತರದ ಪ್ರತ್ಯಯ, ಅಥವಾ
ಮೂಲ ಚಾನಲ್ಗಾಗಿ ಅಕ್ಷರಶಃ `auto`) ಒಂದು **ಓದಲು-ಮಾತ್ರ** ಎಂಡ್ಪಾಯಿಂಟ್ ಆಗಿದ್ದು, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವದ ಓದುಗಳನ್ನು ಮರುಬಳಕೆ ಮಾಡಿಕೊಂಡು, ಲೈವ್ ತಲುಪುವಿಕೆಯ ಮಾಹಿತಿಯೊಂದಿಗೆ ಅಲಂಕರಿಸಲಾದ
`auto/*` ಚಾನಲ್ನ ಪ್ರಸ್ತುತ ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಅನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ (ಬ್ರೇಕರ್ನ ಕಚ್ಚಾ `state` ಅನ್ನು ಎಂದಿಗೂ ಬಳಸುವುದಿಲ್ಲ):

- ಪೂರೈಕೆದಾರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್ — ಪರಿಹರಿಸಲಾದ `provider_connections` ಸಾಲಿನಲ್ಲಿರುವ
  `rateLimitedUntil` / `testStatus`
- ಮಾದರಿ ಲಾಕ್ಔಟ್ — `isModelLocked(provider, connectionId, model)`

ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯು ಈ API ಕೀಗೆ ಸಂಬಂಧಿಸಿದ `excluded` ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಸಹ ಹೊಂದಿರುತ್ತದೆ. ಹೊರಗಿಡುವಿಕೆಗಳನ್ನು
ಪ್ರತಿ-API-ಕೀ ಆಧಾರದಲ್ಲಿ (`auto_candidate_overrides` ಟೇಬಲ್, ಮೈಗ್ರೇಶನ್ `128`) ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ — OmniRoute
`users` ಟೇಬಲ್ ಇಲ್ಲದ ಏಕ-ಟೆನೆಂಟ್ ವ್ಯವಸ್ಥೆಯಾಗಿರುವುದರಿಂದ, `apiKeyId` ಎಂಬುದು ಪ್ರತಿ ಕರೆಗಾರನಿಗೆ ಲಭ್ಯವಿರುವ
ಅತ್ಯಂತ ಸಮೀಪದ ನೈಜ ಗುರುತು — ಮತ್ತು ಶುದ್ಧ, ಘಟಕ-ಪರೀಕ್ಷಿತ
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) ಮೂಲಕ
`open-sse/services/autoCombo/virtualFactory.ts`ನ ಅಭ್ಯರ್ಥಿ-ಪೂಲ್ ಚೋಕ್ಪಾಯಿಂಟ್ನಲ್ಲಿ ಜಾರಿಗೊಳಿಸಲಾಗುತ್ತದೆ.
ಫಿಲ್ಟರ್ **fail-open** ಆಗಿದೆ: ಹೊಂದಿಸದ apiKeyId/channel ಅಥವಾ DB ಲುಕ್ಅಪ್ ವೈಫಲ್ಯ ಎರಡೂ
ಪೂಲ್ ಅನ್ನು ಫಿಲ್ಟರ್ ಮಾಡದೆ ಬಿಡುತ್ತವೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಓವರ್ರೈಡ್ಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದ ಆಪರೇಟರ್ಗೆ ರೂಟಿಂಗ್
ಈ ವೈಶಿಷ್ಟ್ಯಕ್ಕೂ ಮೊದಲಿದ್ದಂತೆಯೇ ಬೈಟ್-ಸಮಾನವಾಗಿ ಕಾಣುತ್ತದೆ.

**ಮುಂದಿನ ಅನುಸರಣಾ ಇಶ್ಯೂಗೆ ಮುಂದೂಡಲಾಗಿದೆ:** ಪ್ರತಿ-ಅಭ್ಯರ್ಥಿ ತೂಕಗಳು + ಸ್ಪಷ್ಟ ಕ್ರಮಗೊಳಿಸುವಿಕೆ (Level 3
— ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ತೂಕ ನೀಡಿದ/ಆದ್ಯತಾ ತಂತ್ರದ ಮಾರ್ಗಗಳಿಗೆ ಫೀಡ್ ಆಗುತ್ತದೆ) ಮತ್ತು ಪ್ರತಿ `auto/*` ಚಾನಲ್ಗೆ ನಿರ್ದಿಷ್ಟ
`combo.ts` ತಂತ್ರವನ್ನು ಪಿನ್ ಮಾಡುವುದು (Level 4). ಏಕ-ಟೆನೆಂಟ್ ಮಾದರಿಯನ್ನು ಪರಿಗಣಿಸಿದಾಗ ಓವರ್ರೈಡ್ಗಳು
ಪ್ರತಿ-API-ಕೀ ಆಧಾರದಲ್ಲೇ ಉಳಿಯಬೇಕೇ ಅಥವಾ ಗ್ಲೋಬಲ್ ಆಗಬೇಕೇ ಎಂಬ ಮುಕ್ತ ಪ್ರಶ್ನೆಗಾಗಿ #7819 ಯೋಜನೆಯನ್ನು ನೋಡಿ.

**ಹಿನ್ನೆಲೆಯಲ್ಲಿ:**

```txt
ವಿನಂತಿ: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಪತ್ತೆಮಾಡುತ್ತದೆ
   ↓
createVirtualAutoCombo('coding') → ಸಕ್ರಿಯ ಸಂಪರ್ಕಗಳಿಂದ candidatePool
   ↓
handleComboChat (ಉಳಿಸಲಾದ ಕಾಂಬೊಗಳಂತೆಯೇ ಅದೇ ಎಂಜಿನ್)
   ↓
ಸ್ವಯಂ-ಸ್ಕೋರಿಂಗ್ ಪ್ರತಿ ವಿನಂತಿಗೆ ಅತ್ಯುತ್ತಮ ಪೂರೈಕೆದಾರ/ಮಾದರಿಯನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ
```

**ಅನುಷ್ಠಾನ ಫೈಲ್ಗಳು:**

| ಫೈಲ್                                                      | ಉದ್ದೇಶ                                                |
| --------------------------------------------------------- | ----------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | ಪೂರ್ವಪ್ರತ್ಯಯ ಪಾರ್ಸರ್ (`parseAutoPrefix`)              |
| `open-sse/services/autoCombo/virtualFactory.ts`           | ವರ್ಚುವಲ್ `AutoComboConfig` ಆಬ್ಜೆಕ್ಟ್ಗಳನ್ನು ರಚಿಸುತ್ತದೆ |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | ಪೂರೈಕೆದಾರ ರಿಜಿಸ್ಟ್ರಿಯನ್ನು ಮಾಕ್ ಮಾಡುವ ಪರೀಕ್ಷಾ ಹುಕ್     |
| `src/sse/handlers/chat.ts`                                | ಏಕೀಕರಣ: ಸ್ವಯಂ ಪೂರ್ವಪ್ರತ್ಯಯ ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್           |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` ಸಿಸ್ಟಮ್ ಎಂಟ್ರಿ                |

## ನೈಜ ಮಾಡೆಲ್ ಐಡಿಗೆ ಹೊಂದಿಕೆಯಾಗುವ ಕಾಂಬೊ ಹೆಸರುಗಳು

`name` ನೈಜ ಮಾಡೆಲ್ ಐಡಿಗೆ ತದ್ರೂಪವಾಗಿರುವ ಕಾಂಬೊ (ಉದಾ. `gpt-5.5` ಎಂಬ ಹೆಸರಿನ ಕಾಂಬೊ)
ಒಂದು **ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಬೆಂಬಲಿತ ಮಾದರಿ** ಆಗಿದೆಯೇ ಹೊರತು ದೋಷವಲ್ಲ: ಇದು
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) ನಲ್ಲಿ ದಾಖಲಿಸಲಾದ
ಪ್ರತಿ-ಮಾಡೆಲ್-ಐಡಿ ಪ್ರೊವೈಡರ್ ಫಾಲ್ಬ್ಯಾಕ್ ಕಾರ್ಯವಿಧಾನವಾಗಿದೆ. ನೇರ ಮಾಡೆಲ್-ಐಡಿ ರೆಸಲ್ಯೂಶನ್ಗಿಂತ ಮೊದಲು
ಕಾಂಬೊ ರೆಸಲ್ಯೂಶನ್ ಪರಿಶೀಲಿಸಲ್ಪಡುವುದರಿಂದ
(`src/sse/services/model.ts` ನಲ್ಲಿನ `getComboForModel()`), ನೇರ ಐಡಿ
`gpt-5.5` ಗಾಗಿನ ವಿನಂತಿಯು ಒಂದೇ ಪ್ರೊವೈಡರ್ಗೆ ನೇರವಾಗಿ ಹೋಗುವ ಬದಲು ಕಾಂಬೊದ

ರೀರೈಟ್ಗಿಂತ-ಮೊದಲು-ಕಾಂಬೊ ಆದ್ಯತೆಯನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ ಮತ್ತು

ನೈಜ ಮಾಡೆಲ್ ಐಡಿಯನ್ನು ಮರೆಮಾಡುವ ಹೆಸರಿನ ಕಾಂಬೊವನ್ನು ರಚಿಸುವುದು ಅಥವಾ ಆ ಹೆಸರಿಗೆ ಮರುಹೆಸರಿಸುವುದನ್ನು
**ಎಂದಿಗೂ ತಿರಸ್ಕರಿಸಲಾಗುವುದಿಲ್ಲ** — ಹಾಗೆ ಮಾಡುವುದರಿಂದ ಈ ದಾಖಲಿತ ಕಾರ್ಯವಿಧಾನವು ಮುರಿಯುತ್ತದೆ. ಬದಲಾಗಿ

`PUT /api/combos/[id]` ಪ್ರತಿಕ್ರಿಯೆಗೆ ತಡೆಯೊಡ್ಡದ

ಪಟ್ಟಿಮಾಡುವ ಒಂದು-ಸಾಲಿನ `[STARTUP]` ಎಚ್ಚರಿಕೆಯನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ; ಇದರಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
(#6940 ಪ್ರಕಾರ) ಅಲ್ಲದೆ ಆಕಸ್ಮಿಕವಾಗಿ ಇದನ್ನು ಎದುರಿಸುವ ಆಪರೇಟರ್ಗಳಿಗೆ ಸೂಚನೆ ಸಿಗುತ್ತದೆ.

## ಕ್ಲೈಂಟ್ನಿಂದ ಕಸ್ಟಮ್ ಕಾಂಬೊವನ್ನು ಕರೆದು ಬಳಸುವುದು

ಉಳಿಸಿಟ್ಟ ಕಾಂಬೊಗಳನ್ನು (ಸೆಟ್ಟಿಂಗ್ಗಳು → ಕಾಂಬೊಗಳು) ಕ್ಲೈಂಟ್ `model` ಕ್ಷೇತ್ರದಲ್ಲಿ ಕಾಂಬೊದ **ನಿಖರವಾದ ಹೆಸರನ್ನು** ಕಳುಹಿಸಿದಾಗ ಮಾತ್ರ ಬಳಸಲಾಗುತ್ತದೆ — ಕಾಂಬೊ ಹೆಸರಿಗೆ ಅಸ್ಪಷ್ಟ ಅಥವಾ ಭಾಗಶಃ ಹೊಂದಾಣಿಕೆ ಇರುವುದಿಲ್ಲ ಮತ್ತು `auto/` ಪೂರ್ವಪ್ರತ್ಯಯವೂ ಒಳಗೊಂಡಿಲ್ಲ. ರೆಸಲ್ಯೂಶನ್ ಕ್ರಮ (`src/sse/services/model.ts` ನಲ್ಲಿನ `getComboForModel()`):

1. ನಿಖರವಾದ ಕಾಂಬೊ-ಹೆಸರು ಹೊಂದಾಣಿಕೆ (`model: "my-combo"`),
2. `combo/<name>` ಪೂರ್ವಪ್ರತ್ಯಯ (`model: "combo/my-combo"`),
3. ಮಾಡೆಲ್→ಕಾಂಬೊ ಗ್ಲಾಬ್ ಮ್ಯಾಪಿಂಗ್ಗಳು (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ಎರಡು ಸಾಮಾನ್ಯ ತಪ್ಪುಗ್ರಹಿಕೆಗಳು:

- **`auto` ನಿಮ್ಮ ಕಾಂಬೊಗಳನ್ನು ಬಳಸುವುದಿಲ್ಲ.** `auto`/`auto/*` ತನ್ನದೇ ಆದ ಶೂನ್ಯ-ಕಾನ್ಫಿಗರೇಶನ್ ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ ಮತ್ತು ಕಾಂಬೊಗೆ ಅಕ್ಷರಶಃ `auto` ಎಂದು ಹೆಸರಿಟ್ಟಿದ್ದರೆ ಮಾತ್ರ ಉಳಿಸಿಟ್ಟ ಕಾಂಬೊಗಳನ್ನು ಪರಿಗಣಿಸುತ್ತದೆ (ಶಿಫಾರಸು ಮಾಡುವುದಿಲ್ಲ). ಕಾಂಬೊ ಮೂಲಕ ರೂಟ್ ಮಾಡಲು, ಅದರ ನಿಖರವಾದ ಹೆಸರನ್ನು ಕಳುಹಿಸಿ — `auto` ಅಲ್ಲ.
- **`openrouter/auto` ಒಂದು ನೈಜ ಪಾವತಿಸಬೇಕಾದ OpenRouter ಉತ್ಪನ್ನವಾಗಿದೆ** ("Auto Best Available"), OmniRoute ಅಲಿಯಾಸ್ ಅಲ್ಲ. ಇದು OpenRouter ರಿಜಿಸ್ಟ್ರಿಯ (`open-sse/config/providers/registry/openrouter/index.ts`) ಏಕೈಕ ಸ್ಥಿರ ಮಾಡೆಲ್ ನಮೂದು ಆಗಿದ್ದು, ಇದಕ್ಕಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಬಿಲ್ ಮಾಡಲಾಗುತ್ತದೆ. ಇದನ್ನು `auto` ಪೂಲ್ಗಳಿಂದ ಹೊರಗಿಡಲು ಸೆಟ್ಟಿಂಗ್ಗಳು → ರೂಟಿಂಗ್ → ಪಾವತಿಸಬೇಕಾದ ಮಾಡೆಲ್ಗಳನ್ನು ಮರೆಮಾಡಿ ಆಯ್ಕೆಯನ್ನು ಬಳಸಿ.

ಇಲ್ಲಿ ದಾಖಲಿಸಲಾಗಿರುವ ಮೂಲ ಗೊಂದಲಕ್ಕಾಗಿ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) ಮತ್ತು [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) ನೋಡಿ.

## ಇದು ಹೇಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ (ಸ್ಥಿರವಾಗಿ ಸಂಗ್ರಹಿಸಲಾದ ಆಟೋ-ಕಾಂಬೊಗಳು)

ಆಟೋ-ಕಾಂಬೊ ಎಂಜಿನ್ ಪ್ರತಿ ವಿನಂತಿಗೂ ಅತ್ಯುತ್ತಮ ಪೂರೈಕೆದಾರ/ಮಾದರಿಯನ್ನು **16-ಅಂಶಗಳ ಸ್ಕೋರಿಂಗ್ ಫಂಕ್ಷನ್** ಬಳಸಿ ಕ್ರಿಯಾತ್ಮಕವಾಗಿ ಆಯ್ಕೆಮಾಡುತ್ತದೆ (ಇದನ್ನು `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` ನಲ್ಲಿ ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ). ಡೀಫಾಲ್ಟ್ ತೂಕಗಳ ಮೊತ್ತ `1.0`; ಕಸ್ಟಮ್ ತೂಕಗಳನ್ನು `normalizeScoringWeights()` ಮೂಲಕ ಮರು-ಸಾಮಾನ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ. ಹದಿನಾರರಲ್ಲಿ ಎರಡು — `cacheAffinity` ಮತ್ತು `resetWindowAffinity` — ಡೀಫಾಲ್ಟ್ ತೂಕ `0` ಅನ್ನು ಹೊಂದಿವೆ; `reliability` ಎಂಬುದು `DEFAULT_WEIGHTS` ನಲ್ಲಿ `0` ಅನ್ನು, ಆದರೆ ಸಾಮಾನ್ಯ ಪ್ಯಾಕ್ಗಳಲ್ಲಿ `0.03` ಮತ್ತು `reliability-first` ನಲ್ಲಿ `0.04` ಅನ್ನು ಹೊಂದಿದೆ, ಹಾಗೂ `quality` ಪ್ಯಾಕ್ಗಳಲ್ಲಿ `0.02` ಅನ್ನು (`quality-first` ನಲ್ಲಿ `0.03`) ಹೊಂದಿದೆ: ಆದರೂ ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಗೂ ಅವುಗಳನ್ನು ಲೆಕ್ಕಹಾಕಲಾಗುತ್ತದೆ, ಮತ್ತು `cacheAffinity` ಸ್ಕೋರ್ನ ಹೊರಗೆ ಪ್ರಾಂಪ್ಟ್-ಕ್ಯಾಶ್ ನಕಲು ನಿವಾರಣೆಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಶೂನ್ಯ-ಡೀಫಾಲ್ಟ್ ಅಂಶಗಳು ಡೀಫಾಲ್ಟ್ ಆಗಿ ಮತ ನೀಡುವುದಿಲ್ಲ, ಆದರೆ ಪ್ಯಾಕ್ಗಳು ಮತ ನೀಡುತ್ತವೆ.

## ಮೋಡ್ ಪ್ಯಾಕ್ಗಳು

`open-sse/services/autoCombo/modePacks.ts` ನಲ್ಲಿ ಪೂರ್ವನಿರ್ಧರಿತ 6 ತೂಕದ ಪ್ರೊಫೈಲ್ಗಳಿವೆ. ಆಯ್ಕೆಯನ್ನು ಒಂದು ಗುರಿಯತ್ತ ವಾಲಿಸಲು ಪ್ರತಿಯೊಂದು ಪ್ಯಾಕ್ ಡೀಫಾಲ್ಟ್ ತೂಕಗಳನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬದಲಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಪ್ಯಾಕ್ನ ಮೊತ್ತವು ಈಗಾಗಲೇ `1.0` ಆಗಿದೆ (ನಾಲ್ಕು ದಶಮಾಂಶ ಸ್ಥಾನಗಳಲ್ಲಿ ಮುದ್ರಿಸಿದಾಗ `0.9999`), ಆದ್ದರಿಂದ ಪ್ಯಾಕ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ `normalizeScoringWeights()` ಸರಿಪಡಿಸಲು ಅರ್ಥಪೂರ್ಣವಾದದ್ದೇನೂ ಇರುವುದಿಲ್ಲ — ಕೆಳಗಿನ ಮೌಲ್ಯಗಳೇ, ಪೂರ್ಣಾಂಕೀಕರಣವನ್ನು ಪರಿಗಣಿಸಿದರೆ, ಸ್ಕೋರರ್ ಅನ್ವಯಿಸುವ ಮೌಲ್ಯಗಳಾಗಿವೆ.

  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04, ಯಾವುದೇ ಪ್ಯಾಕ್ಗಿಂತಲೂ ಅತ್ಯಧಿಕ (ಅತ್ಯಂತ ಕಡಿಮೆ ಅನಿರೀಕ್ಷಿತ ಘಟನೆಗಳು)

### ಪ್ರತಿ-ವಿನಂತಿಯ ನಿಯಂತ್ರಣಗಳು (ಹೆಡರ್ಗಳು) — #6023 / #6024 / #6025 / #3470

ಕಾಂಬೊದಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾದ ಕಾನ್ಫಿಗ್ ಅನ್ನು ಬದಲಾಯಿಸದೆಯೇ, ಮೂರು ಹೆಡರ್ಗಳ ಮೂಲಕ `auto` ಕಾಂಬೊವನ್ನು **ಪ್ರತಿ ವಿನಂತಿಗೆ** ಅನುಗುಣವಾಗಿ ನಿಯಂತ್ರಿಸಬಹುದು. ಇವು `auto` ಕಾರ್ಯತಂತ್ರಕ್ಕೆ ಮಾತ್ರ ಮತ್ತು ಅವುಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತವೆ; ಹೆಡರ್ ಇಲ್ಲದಿರುವಾಗ ಕಾಂಬೊದಲ್ಲಿ ಉಳಿಸಲಾದ `modePack`/`budgetCap`/`budgetFallback` ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ.

### `weighted` ನ ಅರ್ಥವ್ಯವಸ್ಥೆ

`weighted` ಎಂಬುದು **ಪ್ರತಿ ವಿನಂತಿಗೆ ಅನುಪಾತದ ಯಾದೃಚ್ಛಿಕ ಆಯ್ಕೆ**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ಸಮೀಕರಕವಲ್ಲ:

- ಪ್ರತಿ ವಿನಂತಿಯು `weight / totalWeight` ಸಂಭವನೀಯತೆಯೊಂದಿಗೆ **ಒಂದು** ಹಂತವನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ; ಉಳಿದ ಹಂತಗಳನ್ನು
  ಆ ವಿನಂತಿಯ ಹಿಮ್ಮೆಟ್ಟುವಿಕೆ ಸರಪಳಿಯಾಗಿ ತೂಕದ ಅವರೋಹಣ ಕ್ರಮದಲ್ಲಿ ಜೋಡಿಸಲಾಗುತ್ತದೆ.
- ತೂಕ `0` ಆಗಿರುವ (ಅಥವಾ ತೂಕವೇ ಇಲ್ಲದ) ಹಂತವನ್ನು, ಬೇರೆ ಯಾವುದೇ ಹಂತದ ತೂಕ
  > 0 ಆಗಿರುವವರೆಗೆ **ಎಂದಿಗೂ ಆಯ್ಕೆಮಾಡಲಾಗುವುದಿಲ್ಲ** — ಆಯ್ಕೆಮಾಡಿದ ಹಂತ ವಿಫಲವಾದ ನಂತರ ಮಾತ್ರ ಅದು ಹಿಮ್ಮೆಟ್ಟುವಿಕೆಯಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸಬಹುದು. **ಎಲ್ಲಾ**
  > ತೂಕಗಳು 0 ಆಗಿದ್ದಾಗ ಮಾತ್ರ ಆಯ್ಕೆಯು ಏಕರೂಪವಾಗುತ್ತದೆ.
- ತಮ್ಮ ಎಲ್ಲ ಗುರಿಗಳೂ ಅಲಭ್ಯವಾಗಿರುವ ಹಂತಗಳನ್ನು — ಪೂರೈಕೆದಾರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ `OPEN`, ಸಂಪರ್ಕದ
  ಕೂಲ್ಡೌನ್, ಮಾದರಿ ಲಾಕ್ಔಟ್ — ಆಯ್ಕೆ ನಡೆಯುವ ಮೊದಲೇ ಅದರಿಂದ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ
  (`open-sse/services/combo/targetResolution.ts`), ಆದ್ದರಿಂದ ಒಂದು ಆರೋಗ್ಯಕರ ಹಂತವು ತಾತ್ಕಾಲಿಕವಾಗಿ
  ಪ್ರತಿಯೊಂದು ವಿನಂತಿಯಲ್ಲೂ ಗೆಲ್ಲಬಹುದು.
- `stickyWeightedLimit` (ಕಾಂಬೊ ಸಂರಚನೆ, ಡೀಫಾಲ್ಟ್ `1` = ನಿಷ್ಕ್ರಿಯ) ಮರು-ಆಯ್ಕೆ ಮಾಡುವ ಮೊದಲು ಆಯ್ಕೆಗೊಂಡ ಹಂತವನ್ನು ಅಷ್ಟು
  ಅನುಕ್ರಮ ಯಶಸ್ಸುಗಳವರೆಗೆ ಸ್ಥಿರಗೊಳಿಸುತ್ತದೆ.

ಕಟ್ಟುನಿಟ್ಟಾದ ಆವರ್ತನೆಗಾಗಿ `round-robin` ಬಳಸಿ; `weighted` ನಲ್ಲಿ ಸಮಾನ ತೂಕಗಳು ಸಂಖ್ಯಾಶಾಸ್ತ್ರೀಯ ಸಮತೋಲನವನ್ನು ನೀಡುತ್ತವೆ —
ಕಟ್ಟುನಿಟ್ಟಾದ ಸಮತೋಲನವನ್ನಲ್ಲ.

## ಫ್ಯೂಷನ್ ತಂತ್ರ

`fusion` ಎಂಬುದು ಒಂದೇ ಗುರಿಯನ್ನು ಆಯ್ಕೆ **ಮಾಡದ** ಏಕೈಕ ತಂತ್ರವಾಗಿದೆ. ಇದು ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು
**ಪ್ರತಿಯೊಂದು ಪ್ಯಾನೆಲ್ ಮಾದರಿಗೂ ಸಮಾನಾಂತರವಾಗಿ** ಕಳುಹಿಸುತ್ತದೆ; ನಂತರ ಸಂರಚಿಸಬಹುದಾದ **ನಿರ್ಣಾಯಕ ಮಾದರಿ**
ಎಲ್ಲಾ ಪ್ಯಾನೆಲ್ ಪ್ರತಿಕ್ರಿಯೆಗಳಿಂದ ಒಂದೇ ಅಂತಿಮ ಉತ್ತರವನ್ನು ಸಂಶ್ಲೇಷಿಸುತ್ತದೆ. ಅಪ್ಸ್ಟ್ರೀಮ್ `decolua/9router`
(OpenRouter ನ Fusion ವಿನ್ಯಾಸ) ನಿಂದ ಪೋರ್ಟ್ ಮಾಡಲಾಗಿದೆ; ಅನುಷ್ಠಾನವು `open-sse/services/fusion.ts` ನಲ್ಲಿದೆ.

ಇದು ಕಾರ್ಯನಿರ್ವಹಿಸುವ ವಿಧಾನ:

0. **ಪರಿಕರ-ಒಳಗೊಂಡ ವಿನಂತಿಗಳ ಬೈಪಾಸ್** — ಖಾಲಿಯಲ್ಲದ `tools` ಅರೇ ಹೊಂದಿರುವ ಮತ್ತು
   `tool_choice` ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ `"none"` ಎಂದು ಹೊಂದಿಸದ ವಿನಂತಿಯು ಪ್ಯಾನೆಲ್ ಅನ್ನು ಸಂಪೂರ್ಣವಾಗಿ
   ಬಿಟ್ಟುಬಿಡುತ್ತದೆ: ಅದು ಒಂದೇ ಮಾದರಿಗೆ (ಸಂರಚಿಸಲಾದ ನಿರ್ಣಾಯಕ ಅಥವಾ `panel[0]`) ನೇರವಾಗಿ ರೌಟ್ ಆಗುತ್ತದೆ,
   ಮತ್ತು `tools`/`tool_choice` ಅನ್ನು ಯಾವುದೇ ಬದಲಾವಣೆಯಿಲ್ಲದೆ ರವಾನಿಸಲಾಗುತ್ತದೆ. ಪ್ಯಾನೆಲ್ ಸದಸ್ಯರಿಗೆ
   ಪರಿಕರ ಪ್ರವೇಶವಿಲ್ಲ ಮತ್ತು ನಿರ್ಣಾಯಕನ ಸಂಶ್ಲೇಷಣಾ ನಿರ್ದೇಶನವು ಟೂಲ್-ಕಾಲ್ ಹೊರಸೂಸುವಿಕೆಯನ್ನು
   ನಿರುತ್ಸಾಹಗೊಳಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಏಜೆಂಟಿಕ್/ಟೂಲ್-ಕಾಲಿಂಗ್ ಕ್ಲೈಂಟ್ಗಳು ಸಂಶ್ಲೇಷಿತ ಗದ್ಯದ ಬದಲಿಗೆ
   ನಿಜವಾದ ಟೂಲ್-ಕಾಲ್ ನಿರ್ಧಾರವನ್ನು ಪಡೆಯುತ್ತವೆ (#6771).
1. **ಫ್ಯಾನ್-ಔಟ್** (ಪರಿಕರಗಳನ್ನು ಹೊಂದಿರದ ವಿನಂತಿಗಳಿಗೆ ಮಾತ್ರ) — ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಎಲ್ಲಾ ಪ್ಯಾನೆಲ್
   ಮಾದರಿಗಳಿಗೆ ಏಕಕಾಲದಲ್ಲಿ ಕಳುಹಿಸಲಾಗುತ್ತದೆ; ಪರಿಕರಗಳನ್ನು ತೆಗೆದುಹಾಕಿ, ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದಂತೆ
   ಬಲವಂತಪಡಿಸಲಾಗುತ್ತದೆ (ಸಂಶ್ಲೇಷಿಸಲು ನಿರ್ಣಾಯಕನಿಗೆ ಸಂಪೂರ್ಣ ಗದ್ಯದ ಅಗತ್ಯವಿದೆ).
2. **ಕೋರಮ್-ಗ್ರೇಸ್ ಸಂಗ್ರಹಣೆ** — `minPanel` ಉತ್ತರಗಳು ತಲುಪಿದ ತಕ್ಷಣ, ತಡವಾಗಿ ಬರುವವುಗಳಿಗಾಗಿ
   ಕಿರು ಗ್ರೇಸ್ ಟೈಮರ್ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ; ನಂತರ ಸಂಗ್ರಹಿಸಲಾದ ಉತ್ತರಗಳೊಂದಿಗೆ ಫ್ಯೂಷನ್ ಮುಂದುವರಿಯುತ್ತದೆ.
   ಹಾರ್ಡ್ ಟೈಮ್ಔಟ್ನ ಮಿತಿಯೊಳಗೆ, ಇದರಿಂದ ಅತ್ಯಂತ ನಿಧಾನವಾದ ಮಾದರಿಯಿಂದ ಒಟ್ಟು ಸಮಯಕ್ಕೆ ಉಂಟಾಗುವ
   ವಿಳಂಬ ಸೀಮಿತವಾಗುತ್ತದೆ.
3. **ನಿರ್ಣಾಯಕ ಸಂಶ್ಲೇಷಣೆ** — ಪ್ಯಾನೆಲ್ ಉತ್ತರಗಳನ್ನು ಅನಾಮಧೇಯಗೊಳಿಸಿ (`Source 1`, `Source 2`, … —
   ಇದರಿಂದ ನಿರ್ಣಾಯಕನು ಮಾದರಿಯ ಬ್ರ್ಯಾಂಡ್ ಬದಲಿಗೆ ವಿಷಯದ ತೂಕವನ್ನು ಪರಿಗಣಿಸುತ್ತಾನೆ) ನಿರ್ಣಾಯಕನಿಗೆ
   ನೀಡಲಾಗುತ್ತದೆ. ಅದು ಒಮ್ಮತ / ವಿರೋಧಾಭಾಸಗಳು / ಭಾಗಶಃ ವ್ಯಾಪ್ತಿ / ವಿಶಿಷ್ಟ ಒಳನೋಟಗಳು / ಗಮನಕ್ಕೆ
   ಬಾರದ ಅಂಶಗಳನ್ನು ವಿಶ್ಲೇಷಿಸಿ, ನಂತರ **ಒಂದು** ಅಧಿಕೃತ ಉತ್ತರವನ್ನು ಬರೆಯುತ್ತದೆ. ನಿರ್ಣಾಯಕನ ಕರೆಗೆ
   ಕ್ಲೈಂಟ್ನ ಮೂಲ `stream` ಫ್ಲ್ಯಾಗ್ + ಪರಿಕರಗಳನ್ನು ಹಾಗೆಯೇ ಉಳಿಸಲಾಗುತ್ತದೆ; ಆದ್ದರಿಂದ ಸ್ಟ್ರೀಮಿಂಗ್
   ಮತ್ತು ಡೌನ್ಸ್ಟ್ರೀಮ್ ಪರಿಕರ ಬಳಕೆ ಇನ್ನೂ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ.
4. **ಸಮರ್ಪಕ ಅವನತಿ** — 0 ಪ್ಯಾನೆಲ್ ಉತ್ತರಗಳು → `503`; ನಿಖರವಾಗಿ 1 ಉತ್ತರ ಮಾತ್ರ ಉಳಿದರೆ → ಆ
   ಉತ್ತರವನ್ನು ನೇರವಾಗಿ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ (ಸಂಯೋಜಿಸಲು ಏನೂ ಇರುವುದಿಲ್ಲ); ಏಕ-ಮಾದರಿ ಪ್ಯಾನೆಲ್
   ನೇರವಾಗಿ ಉತ್ತರಿಸುತ್ತದೆ.

ಪ್ಯಾನೆಲ್ ಸದಸ್ಯನು ಮತ್ತೊಂದು ಕಾಂಬೊವನ್ನು ಉಲ್ಲೇಖಿಸುವ `combo-ref` ಹಂತವೂ
(`{kind: "combo-ref", comboName: "..."}`) ಆಗಿರಬಹುದು — ಅದು **ಒಂದು ಬ್ಲ್ಯಾಕ್-ಬಾಕ್ಸ್ ಪ್ಯಾನೆಲ್ ಧ್ವನಿಯಾಗಿ**
ಪರಿಹರಿಸಲ್ಪಡುತ್ತದೆ (ಉಲ್ಲೇಖಿತ ಕಾಂಬೊಗೆ ಪೂರ್ಣ ಪುನರಾವರ್ತಿತ ಡಿಸ್ಪ್ಯಾಚ್; ಆ ಕಾಂಬೊದ ಸ್ವಂತ ಗುರಿಗಳ
ಫ್ಯಾನ್-ಔಟ್ ಅಲ್ಲ), ಮತ್ತು ಇತರ ಪ್ರತಿಯೊಂದು combo-ref-ಬಳಸುವ ತಂತ್ರವು ಈಗಾಗಲೇ ಬಳಸುವ ಅದೇ
ಆಳ/ಚಕ್ರ ರಕ್ಷಣೆಯನ್ನು ಹೊಂದಿರುತ್ತದೆ (#6764).

### ಸಂರಚನೆ

ಕಾಂಬೊದ `config` ಬ್ಲಾಬ್ನಲ್ಲಿ ಸಂರಚಿಸಲಾಗುತ್ತದೆ (ಸ್ಕೀಮಾ ಮೈಗ್ರೇಶನ್ ಇಲ್ಲ — ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
`combos` ಟೇಬಲ್ ಅನ್ನು ಮರುಬಳಸುತ್ತದೆ):

| ಕ್ಷೇತ್ರ                                  | ಪ್ರಕಾರ   | ಡೀಫಾಲ್ಟ್            | ಉದ್ದೇಶ                                                                                            |
| :--------------------------------------- | :------- | :------------------ | :------------------------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | ಮೊದಲ ಪ್ಯಾನೆಲ್ ಮಾದರಿ | ಅಂತಿಮ ಉತ್ತರವನ್ನು ಸಂಶ್ಲೇಷಿಸುವ ಮಾದರಿ                                                                |
| `config.fusionTuning.minPanel`           | `number` | `2`                 | ಗ್ರೇಸ್ ಟೈಮರ್ ಪ್ರಾರಂಭವಾಗುವ ಮೊದಲು ಅಗತ್ಯವಿರುವ ಯಶಸ್ವಿ ಉತ್ತರಗಳು (`[2, panelSize]` ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`              | ಕೋರಮ್ ತಲುಪಿದ ನಂತರ ತಡವಾಗಿ ಬರುವವುಗಳಿಗಾಗಿ ಕಾಯಬೇಕಾದ ಅವಧಿ                                              |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`             | ಪ್ರತಿಕ್ರಿಯಿಸದೆ ಸ್ಥಗಿತಗೊಂಡ ಒಂದು ಮಾದರಿಯು ವಿನಂತಿಯನ್ನು ತಡೆಹಿಡಿಯದಂತೆ ಮಾಡುವ ನಿರಪೇಕ್ಷ ಗರಿಷ್ಠ ಮಿತಿ        |

ಡೀಫಾಲ್ಟ್ಗಳು `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) ನಲ್ಲಿವೆ.

### ಉದಾಹರಣೆ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

ನಂತರ ಅದನ್ನು ಯಾವುದೇ ಕಾಂಬೊದಂತೆ ಕರೆ ಮಾಡಿ: `{"model":"fusion-panel","messages":[...]}`.

## ವರ್ಚುವಲ್ ಆಟೋ-ಕಾಂಬೊ ಫ್ಯಾಕ್ಟರಿ

ಆಟೋ ಕಾಂಬೊ ಎಂಜಿನ್ಗೆ ಪೂರ್ವನಿರ್ಧರಿತ ಕಾಂಬೊಗಳು ಅಗತ್ಯವಿಲ್ಲ. ಬದಲಿಗೆ, `open-sse/services/autoCombo/virtualFactory.ts` ಅಗತ್ಯವಿರುವಾಗಲೇ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ:

1. `getProviderConnections({ isActive: true })` ಅನ್ನು ಪಡೆಯುತ್ತದೆ (ಸಕ್ರಿಯಗೊಳಿಸಲಾದ ಎಲ್ಲಾ ಸಂಪರ್ಕಗಳು)
2. ಮಾನ್ಯ ರುಜುವಾತುಗಳನ್ನು ಹೊಂದಿರುವವುಗಳಿಗೆ ಫಿಲ್ಟರ್ ಮಾಡುತ್ತದೆ (API ಕೀ ಅಥವಾ `hasUsableOAuthToken()` ಮೂಲಕ ಅವಧಿ ಮೀರದ OAuth ಟೋಕನ್)
3. ಮಾದರಿ ಲಭ್ಯತೆ + ಬೆಲೆಗಾಗಿ `getProviderRegistry()` ಜೊತೆ ಅಡ್ಡ-ಉಲ್ಲೇಖಿಸುತ್ತದೆ
4. ಪ್ರತಿಯೊಂದು `(provider, model, connection)` ಟ್ಯೂಪಲ್ಗೆ ಒಂದು `VirtualAutoComboCandidate` ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ
5. ರವಾನೆ ಗುರಿಯಾಗಿ `connection.defaultModel` ಅನ್ನು (ಅಥವಾ ರಿಜಿಸ್ಟ್ರಿಯ ಮೊದಲ ಮಾದರಿಯನ್ನು) ಆಯ್ಕೆಮಾಡುತ್ತದೆ
6. 16-ಅಂಶಗಳ `scorePool()` ಮತ್ತು ವೇರಿಯಂಟ್ನ ತೂಕಗಳ ಪ್ಯಾಕ್ ಬಳಸಿ ಪ್ರತಿಯೊಬ್ಬ ಅಭ್ಯರ್ಥಿಗೆ ಸ್ಕೋರ್ ನೀಡುತ್ತದೆ
7. `handleComboChat()` ಗಾಗಿ ಫಲಿತಾಂಶದ ಇನ್-ಮೆಮೊರಿ `AutoComboConfig` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ — ಇದನ್ನು ಎಂದಿಗೂ DBಗೆ ಉಳಿಸುವುದಿಲ್ಲ

ಇದರರ್ಥ **`auto/*` ಸಕ್ರಿಯಗೊಳಿಸಿದ ಹೊಸ ಪ್ರೊವೈಡರ್ ಅನ್ನು ಸೇರಿಸುವುದರಿಂದ ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ವಿಸ್ತರಿಸುತ್ತದೆ** — ಕಾಂಬೊವನ್ನು ಕೈಯಾರೆ ಸಂಪಾದಿಸುವ ಅಗತ್ಯವಿಲ್ಲ. ಪ್ರತಿ ವಿನಂತಿಗೂ ವರ್ಚುವಲ್ ಕಾಂಬೊವನ್ನು ಮರುನಿರ್ಮಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಹೊಸದಾಗಿ ಸೇರಿಸಲಾದ ಅಥವಾ ಮತ್ತೆ ಆರೋಗ್ಯಕರವಾದ ಸಂಪರ್ಕಗಳನ್ನು ತಕ್ಷಣವೇ ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ.

## ಸ್ವಯಂ-ಚೇತರಿಕೆ

- **ತಾತ್ಕಾಲಿಕ ಹೊರಗಿಡುವಿಕೆ**: ಸ್ಕೋರ್ < 0.2 → 5 ನಿಮಿಷಗಳವರೆಗೆ ಹೊರಗಿಡಲಾಗುತ್ತದೆ (ಹಂತಹಂತವಾಗಿ ಹೆಚ್ಚುವ ಬ್ಯಾಕ್ಆಫ್, ಗರಿಷ್ಠ 30 ನಿಮಿಷಗಳು)
- **ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಅರಿವು**: OPEN → ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಹೊರಗಿಡಲಾಗುತ್ತದೆ; HALF_OPEN → ಪ್ರೋಬ್ ವಿನಂತಿಗಳು
- **ಘಟನೆ ಮೋಡ್**: >50% OPEN → ಅನ್ವೇಷಣೆಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿ, ಸ್ಥಿರತೆಯನ್ನು ಗರಿಷ್ಠಗೊಳಿಸುತ್ತದೆ
- **ಕೂಲ್ಡೌನ್ ಚೇತರಿಕೆ**: ಹೊರಗಿಡುವಿಕೆಯ ನಂತರ, ಮೊದಲ ವಿನಂತಿಯು ಕಡಿಮೆ ಟೈಮ್ಔಟ್ ಹೊಂದಿರುವ "ಪ್ರೋಬ್" ಆಗಿರುತ್ತದೆ

## ಬ್ಯಾಂಡಿಟ್ ಅನ್ವೇಷಣೆ

5% ವಿನಂತಿಗಳನ್ನು (ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ) ಅನ್ವೇಷಣೆಗಾಗಿ ಯಾದೃಚ್ಛಿಕ ಪ್ರೊವೈಡರ್ಗಳಿಗೆ ರೂಟ್ ಮಾಡಲಾಗುತ್ತದೆ. ಘಟನೆ ಮೋಡ್ನಲ್ಲಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗುತ್ತದೆ.

## API

**ಯಾವುದೇ ಮೀಸಲಾದ `POST /api/combos/auto` ಎಂಡ್ಪಾಯಿಂಟ್ ಇಲ್ಲ** — ಆಟೋ-ಕಾಂಬೊವನ್ನು ಎರಡು ರೀತಿಯಲ್ಲಿ ಬಳಸಲಾಗುತ್ತದೆ:

1. **ಶೂನ್ಯ-ಕಾನ್ಫಿಗ್ (ಶಿಫಾರಸು ಮಾಡಲಾಗಿದೆ):** `model: "auto"` ಅಥವಾ `model: "auto/<variant>"` ಹೊಂದಿರುವ ಯಾವುದೇ ಚಾಟ್ ಪೂರ್ಣಗೊಳಿಸುವಿಕೆ ವಿನಂತಿಯನ್ನು ಕಳುಹಿಸಿ. ವರ್ಚುವಲ್ ಫ್ಯಾಕ್ಟರಿ ಪ್ರತಿ ವಿನಂತಿಗೂ ಕಾಂಬೊವನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ — ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಅಥವಾ API ಕರೆಗಳು ಅಗತ್ಯವಿಲ್ಲ.

2. **`strategy: "auto"` ಹೊಂದಿರುವ ಉಳಿಸಲಾದ ಕಾಂಬೊ:** `POST /api/combos` ಮೂಲಕ ಸಾಮಾನ್ಯ ಕಾಂಬೊವನ್ನು ರಚಿಸಿ ಮತ್ತು `strategy: "auto"` ಜೊತೆಗೆ `config.auto.weights` / `config.auto.candidatePool` ಅನ್ನು ಹೊಂದಿಸಿ. ಅದೇ ಸ್ಕೋರಿಂಗ್ ಎಂಜಿನ್ ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ; ಕಾಂಬೊವನ್ನು `combos` ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ID ಮೂಲಕ ಮರುಬಳಕೆ ಮಾಡಬಹುದು.

ಅನ್ವೇಷಣೆಗಾಗಿ, `GET /api/combos/auto` ಪ್ರತಿ ವೇರಿಯಂಟ್ ಅನ್ನು ಅದರ ಪರಿಹರಿಸಲಾದ ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಹಾಗೂ `context_length` / `max_output_tokens` ಜೊತೆಗೆ ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ — ಇವು ಅಭ್ಯರ್ಥಿ ಪೂಲ್ನ ವಿಂಡೋಗಳಾದ್ಯಂತ ಇರುವ MAX ಮೌಲ್ಯಗಳಾಗಿವೆ. ಕ್ಲೈಂಟ್ಗಳು (ಉದಾ. opencode ಪ್ಲಗಿನ್) `0` ಬದಲಿಗೆ ಈ ಮೌಲ್ಯಗಳನ್ನು ಪ್ರಕಟಿಸಬೇಕು: ಶೂನ್ಯ ಕಾಂಟೆಕ್ಸ್ಟ್ opencodeನ ಸ್ವಯಂ-ಸಂಕುಚನವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ, ಇದರಿಂದ ಗೇಟ್ವೇಯ ಇತಿಹಾಸ ಶುದ್ಧೀಕರಣವು ಕಾಂಟೆಕ್ಸ್ಟ್ ಅನ್ನು ನಾಶಪಡಿಸುವವರೆಗೆ ಸೆಷನ್ಗಳು ಬೆಳೆಯುತ್ತವೆ. MAX ಅನ್ನು ಪ್ರಕಟಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿದೆ, ಏಕೆಂದರೆ ಆಟೋ-ಕಾಂಬೊ ಕಾಂಟೆಕ್ಸ್ಟ್ ಪೂರ್ವ-ಫಿಲ್ಟರ್ ಅತಿಗಾತ್ರದ ವಿನಂತಿಗಳನ್ನು ದೊಡ್ಡ-ವಿಂಡೋ ಅಭ್ಯರ್ಥಿಗಳಿಗೆ ರೂಟ್ ಮಾಡುತ್ತದೆ.

```bash
# ಶೂನ್ಯ-ಕಾನ್ಫಿಗ್ ಬಳಕೆ (ಕಾಂಬೊ ರಚನೆ ಇಲ್ಲ)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ಸಾಮಾನ್ಯ ಕಾಂಬೊಗಳ ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ ಉಳಿಸಲಾದ ಆಟೋ ಕಾಂಬೊ
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ಆಟೋ ರೂಟರ್ ತಂತ್ರಗಳು

ಉಳಿಸಲಾದ `strategy: "auto"` ಕಾಂಬೊಗಳು `config.routerStrategy` (ಅಥವಾ ಹಳೆಯ
`config.auto.routerStrategy`) ಅನ್ನು ಇವುಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ ಹೊಂದಿಸಬಹುದು:

- `rules` — ಡೀಫಾಲ್ಟ್ ತೂಕ ನೀಡಲಾದ ಸ್ಕೋರಿಂಗ್
- `score` — ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ ಅತ್ಯಧಿಕ ತೂಕದ ಸ್ಕೋರ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ. ನಿಖರ ಟೈಗಳು ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ
  ಅಭ್ಯರ್ಥಿ ಕ್ರಮವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ; ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ `explorationRate` ಸಂಪೂರ್ಣ ಶ್ರೇಯಾಂಕಿತ ಪೂಲ್ನಿಂದ ಮಾದರಿಗಳನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ.
- `cost` / `eco` — ಅತ್ಯಂತ ಅಗ್ಗದ ಆರೋಗ್ಯಕರ ಪ್ರೊವೈಡರ್
- `latency` / `fast` — ವಿಶ್ವಾಸಾರ್ಹತೆ ದಂಡದೊಂದಿಗೆ ಅತ್ಯಂತ ಕಡಿಮೆ p95 ಲೇಟೆನ್ಸಿ
- `sla-aware` / `sla` — p95 ಲೇಟೆನ್ಸಿ, ದೋಷ ದರ ಮತ್ತು ಐಚ್ಛಿಕ
  ವೆಚ್ಚದ SLOಗಳನ್ನು ಪೂರೈಸುವ ಅಭ್ಯರ್ಥಿಗಳಿಗೆ ಆದ್ಯತೆ ನೀಡುತ್ತದೆ
- `lkgp` — ಕೊನೆಯದಾಗಿ ಉತ್ತಮವೆಂದು ತಿಳಿದಿರುವ ಪ್ರೊವೈಡರ್ ಮೊದಲು

### ರೂಟರ್ ತಂತ್ರಗಳ ವಿವರ

ಆಟೋ-ಕಾಂಬೊ ಎಂಜಿನ್ `config.routerStrategy` (ಅಥವಾ ಹಳೆಯ `config.auto.routerStrategy`)
ಮೂಲಕ ಬದಲಾಯಿಸಬಹುದಾದ 6 ಪ್ಲಗ್ ಮಾಡಬಹುದಾದ **RouterStrategy** ಅನುಷ್ಠಾನಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ.
ಪ್ರತಿಯೊಂದು ತಂತ್ರವು `RoutingContext` ಅನ್ನು ಆಧರಿಸಿ ಅಭ್ಯರ್ಥಿ ಪೂಲ್ನಿಂದ ಒಂದು ಪ್ರೊವೈಡರ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ
(ಕಾರ್ಯ ಪ್ರಕಾರ, ಟೂಲ್/ವಿಷನ್ ಸುಳಿವುಗಳು, ಟೋಕನ್ ಅಂದಾಜು, ಐಚ್ಛಿಕ SLA ನೀತಿ, ಐಚ್ಛಿಕ
ಕೊನೆಯದಾಗಿ ಉತ್ತಮವೆಂದು ತಿಳಿದಿರುವ ಪ್ರೊವೈಡರ್).

#### 1. `rules` (ಡೀಫಾಲ್ಟ್) — 16-ಅಂಶಗಳ ತೂಕ ನೀಡಲಾದ ಸ್ಕೋರಿಂಗ್

ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸ್ಕೋರಿಂಗ್ ಎಂಜಿನ್ ಅನ್ನು ರ್ಯಾಪ್ ಮಾಡುತ್ತದೆ. `OPEN` ಸರ್ಕ್ಯೂಟ್-ಬ್ರೇಕರ್
ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಫಿಲ್ಟರ್ ಮಾಡಿ, ನಂತರ ಪ್ರಸ್ತುತ ಕಾರ್ಯ ಪ್ರಕಾರ ಮತ್ತು `getTaskFitness()` ಜೊತೆಗೆ `scorePool()` ಅನ್ನು ಚಲಾಯಿಸಿ,
ಅತ್ಯಧಿಕ ಸ್ಕೋರ್ ಹೊಂದಿರುವ ಪ್ರೊವೈಡರ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**ಯಾವಾಗ ಬಳಸಬೇಕು**: ಡೀಫಾಲ್ಟ್. ಎಲ್ಲಾ ಸಂಕೇತಗಳಾದ್ಯಂತ ಸಮತೋಲಿತ ಹೊಂದಾಣಿಕೆ ಬೇಕಾದಾಗ ಬಳಸಿ.

**ಅಲಿಯಾಸ್**: `rules` (ಅಲಿಯಾಸ್ ಇಲ್ಲ)

---

#### 2. `cost` / `eco` — ಅತ್ಯಂತ ಅಗ್ಗದ ಆರೋಗ್ಯಕರ ಪ್ರೊವೈಡರ್

ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಅನ್ನು `costPer1MTokens` ಆಧರಿಸಿ (ಏರಿಕೆ ಕ್ರಮದಲ್ಲಿ) ವಿಂಗಡಿಸಿ ಅತ್ಯಂತ ಅಗ್ಗದದನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ.
ಮೊದಲು `OPEN` ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಫಿಲ್ಟರ್ ಮಾಡುತ್ತದೆ.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ಯಾವಾಗ ಬಳಸಬೇಕು**: ವೆಚ್ಚ-ಸಂವೇದನಾಶೀಲ ವರ್ಕ್ಲೋಡ್ಗಳು, ಬ್ಯಾಚ್ ಪ್ರಕ್ರಿಯೆ ಅಥವಾ ಹಿನ್ನೆಲೆ ಜಾಬ್ಗಳು.

**ಅಲಿಯಾಸ್ಗಳು**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ವಿಶ್ವಾಸಾರ್ಹತೆ ದಂಡದೊಂದಿಗೆ ಅತ್ಯಂತ ಕಡಿಮೆ p95 ಲೇಟೆನ್ಸಿ

`p95LatencyMs + (errorRate * 1000)` ಆಧರಿಸಿ ವಿಂಗಡಿಸುತ್ತದೆ. ದೋಷ-ದರದ ದಂಡವು
ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ಪ್ರೊವೈಡರ್ಗಳ ನಾಮಮಾತ್ರ ಲೇಟೆನ್ಸಿ ಕಡಿಮೆಯಿದ್ದರೂ ಅವುಗಳಿಗೆ ಕಡಿಮೆ ಶ್ರೇಣಿ ಸಿಗುವುದನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**ಯಾವಾಗ ಬಳಸಬೇಕು**: ರಿಯಲ್-ಟೈಮ್ ಚಾಟ್, ಆಟೋಕಂಪ್ಲೀಟ್ ಅಥವಾ
ಸಂವಾದಾತ್ಮಕ ಕೋಡಿಂಗ್ ಸಹಾಯಕಗಳಂತಹ ಲೇಟೆನ್ಸಿ-ಸಂವೇದನಾಶೀಲ ವರ್ಕ್ಲೋಡ್ಗಳು.

**ಅಲಿಯಾಸ್ಗಳು**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ಲೇಟೆನ್ಸಿ/ದೋಷ/ವೆಚ್ಚ SLO ಅನುಸರಣೆ

ಪ್ರತಿಯೊಬ್ಬ ಅಭ್ಯರ್ಥಿಯು ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾದ SLO ನೀತಿಯನ್ನು ಎಷ್ಟು ಚೆನ್ನಾಗಿ ಪೂರೈಸುತ್ತಾನೆ ಎಂಬುದರ ಆಧಾರದ ಮೇಲೆ ಸ್ಕೋರ್ ನೀಡುತ್ತದೆ:

| ಅಂಶ             | ತೂಕ | ಸೂತ್ರ                                              |
| --------------- | --- | -------------------------------------------------- |
| ಲೇಟೆನ್ಸಿ ಸ್ಕೋರ್ | 35% | `threshold / max(value, ε)`                        |
| ದೋಷ ಸ್ಕೋರ್      | 35% | `threshold / max(value, ε)`                        |
| ಆರೋಗ್ಯ ಸ್ಕೋರ್   | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)  |
| ವೆಚ್ಚದ ಸ್ಕೋರ್   | 10% | `threshold / max(value, ε)` ಅಥವಾ ವಿಲೋಮ ಸಾಮಾನ್ಯೀಕರಣ |
| ಸ್ಥಿರತೆ ಸ್ಕೋರ್  | 5%  | ಲೇಟೆನ್ಸಿ ಪ್ರಮಾಣಿತ ವಿಚಲನದ ವಿಲೋಮ ಸಾಮಾನ್ಯೀಕರಣ         |

`hardConstraints: true` ಆಗಿರುವಾಗ, ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಮುಖ್ಯವಾಗಿ **ಉಲ್ಲಂಘನೆ ಸ್ಕೋರ್**
(ಅವರು ಯಾವುದೇ SLO ಅನ್ನು ಎಷ್ಟು ಮೀರಿದ್ದಾರೆ) ಆಧರಿಸಿ, ನಂತರ ಸಂಯುಕ್ತ ಸ್ಕೋರ್ ಆಧರಿಸಿ ವಿಂಗಡಿಸಲಾಗುತ್ತದೆ. ಇಲ್ಲದಿದ್ದರೆ ಕೇವಲ
ಸಂಯುಕ್ತ ಸ್ಕೋರ್ ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ನೀತಿಗೆ ಎದುರಾಗಿ ಪ್ರತಿಯೊಬ್ಬ ಅಭ್ಯರ್ಥಿಗೆ ಸ್ಕೋರ್ ನೀಡುತ್ತದೆ: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ಕ್ಷೇತ್ರಗಳು** (ಕಾಂಬೊ ಕಾನ್ಫಿಗ್ನಲ್ಲಿ ಹೊಂದಿಸಿ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**ಯಾವಾಗ ಬಳಸಬೇಕು**: ಕಟ್ಟುನಿಟ್ಟಾದ ಲೇಟೆನ್ಸಿ, ದೋಷ-ದರ ಅಥವಾ ವೆಚ್ಚದ ಬಜೆಟ್ಗಳನ್ನು ಹೊಂದಿರುವ ಪ್ರೊಡಕ್ಷನ್ ವರ್ಕ್ಲೋಡ್ಗಳು.

**ಅಲಿಯಾಸ್ಗಳು**: `sla-aware`, `sla`

#### 5. `lkgp` — ಕೊನೆಯದಾಗಿ ಉತ್ತಮವೆಂದು ತಿಳಿದಿರುವ ಪ್ರೊವೈಡರ್ ಮೊದಲು

ಮೊದಲು **ಕೊನೆಯದಾಗಿ ಉತ್ತಮವೆಂದು ತಿಳಿದಿರುವ ಪ್ರೊವೈಡರ್** ಅನ್ನು (ಹೊಂದಿಸಿದ್ದರೆ) ಪ್ರಯತ್ನಿಸುತ್ತದೆ, ನಂತರ
`rules` ತಂತ್ರಕ್ಕೆ ಫಾಲ್ಬ್ಯಾಕ್ ಆಗುತ್ತದೆ. ಸೆಷನ್ ಸ್ಥಿರತೆಗೆ ಇದು ಉಪಯುಕ್ತವಾಗಿದೆ — ಸಂಭಾಷಣೆಯಲ್ಲಿನ
ಮುಂದುವರಿದ ವಿನಂತಿಗಳನ್ನು ಅದೇ ಪ್ರೊವೈಡರ್ ನಿರ್ವಹಿಸುತ್ತದೆ.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules ತಂತ್ರಕ್ಕೆ ಫಾಲ್ಬ್ಯಾಕ್
    return getStrategy("rules").select(pool, context);
  }
}
```

**ಯಾವಾಗ ಬಳಸಬೇಕು**: ಅದೇ ಪ್ರೊವೈಡರ್ ಮುಂದುವರಿದ ವಿನಂತಿಗಳನ್ನು ನಿರ್ವಹಿಸಬೇಕೆಂದು ಬಯಸುವ
ಬಹು-ತಿರುವಿನ ಸಂಭಾಷಣೆಗಳು (ಉದಾ., ಕ್ಯಾಶಿಂಗ್, ಕಾಂಟೆಕ್ಸ್ಟ್ ನಿರಂತರತೆ ಅಥವಾ ಬೆಲೆ ಸ್ಥಿರತೆಗಾಗಿ).

**ಅಲಿಯಾಸ್**: `lkgp` (ಅಲಿಯಾಸ್ ಇಲ್ಲ)

### ಕಸ್ಟಮ್ ರೂಟರ್ ತಂತ್ರಗಳು

ಸಾರ್ವಜನಿಕ API ಮೂಲಕ ನಿಮ್ಮದೇ `RouterStrategy` ಅನುಷ್ಠಾನವನ್ನು ನೋಂದಾಯಿಸಬಹುದು:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ನಿಮ್ಮ ರೂಟಿಂಗ್ ತರ್ಕ ಇಲ್ಲಿ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ನಂತರ ಅದನ್ನು ಬಳಸಿ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## ಕಾರ್ಯ ಸೂಕ್ತತೆ

6 ಕಾರ್ಯ ಪ್ರಕಾರಗಳಲ್ಲಿ (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) 30+ ಮಾದರಿಗಳಿಗೆ ಅಂಕ ನೀಡಲಾಗಿದೆ. ವೈಲ್ಡ್ಕಾರ್ಡ್ ಮಾದರಿಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ (ಉದಾ., `*-coder` → ಹೆಚ್ಚಿನ ಕೋಡಿಂಗ್ ಅಂಕ).

## ಸ್ವಯಂ ರೂಪಾಂತರಗಳ ಪುನರವಲೋಕನ

ಮೂಲ `auto` (ಡೀಫಾಲ್ಟ್) ಜೊತೆಗೆ `autoPrefix.ts` ನಲ್ಲಿ ಘೋಷಿಸಲಾದ 6 `AutoVariant` ಮೌಲ್ಯಗಳನ್ನು ಸೇರಿಸಿದರೆ, **7 ಆಹ್ವಾನಿಸಬಹುದಾದ ಮಾದರಿ IDಗಳು** ಇವೆ:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ಸ್ವತಃ 6 ಮೌಲ್ಯಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ; 7ನೇ ಆಯ್ಕೆಯು "ಯಾವುದೇ ರೂಪಾಂತರವಿಲ್ಲ" — ಮೂಲ `auto` — ಇದನ್ನು `parseAutoPrefix()` `variant: undefined` ಆಗಿ ನಿರ್ವಹಿಸುತ್ತದೆ.)

## ಟಿಯರ್ಗಳು Auto-Comboಗೆ ಹೇಗೆ ಹೊಂದಿಕೊಳ್ಳುತ್ತವೆ

16-ಅಂಶಗಳ ಸ್ಕೋರಿಂಗ್ ಫಂಕ್ಷನ್ (`open-sse/services/autoCombo/scoring.ts`) ಟಿಯರ್
ಸದಸ್ಯತ್ವವನ್ನು ಎರಡು ಸಂಕೇತಗಳಾಗಿ ಪರಿಗಣಿಸುತ್ತದೆ: `tierPriority` (0.0476) ಮತ್ತು `tierAffinity` (0.0476). ಸಂಪೂರ್ಣ
`DEFAULT_WEIGHTS` ಸೆಟ್ಗಾಗಿ ಮೇಲಿನ ಪ್ರಮಾಣಿತ [ಸ್ಕೋರಿಂಗ್ ಅಂಶಗಳ ಕೋಷ್ಟಕ](#how-it-works-persisted-auto-combos) ನೋಡಿ
— ಪ್ರತಿ-ಪ್ಯಾಕ್ ಓವರ್ರೈಡ್ಗಳನ್ನು (ship-fast/cost-saver/quality-first/
offline-friendly) "ಪ್ರತಿ ಪ್ಯಾಕ್ನ ತೂಕ ಪ್ರೊಫೈಲ್ಗಳು" ಕೋಷ್ಟಕದಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾಗಿದೆ.

ಟಿಯರ್ ಮಾತ್ರವೇ ಟಿಯರ್ 1 ಅನ್ನು ಮೊದಲು ಆಯ್ಕೆಮಾಡುವಂತೆ **ಒತ್ತಾಯಿಸುವುದಿಲ್ಲ** — ಟಿಯರ್ 1 ವಿಳಂಬವು ಕೆಟ್ಟದಾಗಿದ್ದರೆ ಅಥವಾ
ವೆಚ್ಚ-ವಿರುದ್ಧ-ಗುಣಮಟ್ಟವು ಸೂಕ್ತವಾಗಿಲ್ಲದಿದ್ದರೆ, ಟಿಯರ್ 2 ಗೆಲ್ಲುತ್ತದೆ. ಟಿಯರ್ ಕ್ರಮವನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸಲು, ಕಾಂಬೊ
ತಂತ್ರ `priority` ಅನ್ನು ಬಳಸಿ ಮತ್ತು ಪೂರೈಕೆದಾರರನ್ನು ಟಿಯರ್ ಪ್ರಕಾರ ಜೋಡಿಸಿ.

ಟಿಯರ್ 1 (ಚಂದಾದಾರಿಕೆ) ಅನ್ನು ಬಲವಾಗಿ ಆದ್ಯತೆ ನೀಡಲು, `tierPriority` ತೂಕವನ್ನು ಹೆಚ್ಚಿಸಿ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ಟಿಯರ್ ವ್ಯಾಖ್ಯಾನಗಳು ಮತ್ತು ಪೂರೈಕೆದಾರರ ವರ್ಗೀಕರಣಕ್ಕಾಗಿ `docs/marketing/TIERS.md` ನೋಡಿ.

## ಪರೀಕ್ಷೆ ಮತ್ತು ವ್ಯಾಪ್ತಿ

### ನಿರ್ಣಾಯಕ ರೂಟಿಂಗ್-ನಿರ್ಧಾರ ಮ್ಯಾಟ್ರಿಕ್ಸ್ (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ಅಣಕು ಅಪ್ಸ್ಟ್ರೀಮ್ನೊಂದಿಗೆ ನೈಜ ಕಾಂಬೊ ಪೈಪ್ಲೈನ್ ಮೂಲಕ ಎಲ್ಲಾ 19
ಸಾರ್ವಜನಿಕ ತಂತ್ರಗಳ ರೂಟಿಂಗ್ **ನಿರ್ಧಾರವನ್ನು** ಆರಂಭದಿಂದ ಅಂತ್ಯದವರೆಗೆ ಸಾಬೀತುಪಡಿಸುತ್ತದೆ.
ವ್ಯಾಪ್ತಿಯಲ್ಲಿ ಇವು ಸೇರಿವೆ:

- ಎಲ್ಲಾ 19 `ROUTING_STRATEGY_VALUES` ತಂತ್ರಗಳು (ಕ್ರಮಬದ್ಧ, ತೂಕ ನೀಡಿದ, ವೆಚ್ಚ, ಸಂದರ್ಭ, ಫ್ಯೂಷನ್, …).
- `quota-share` (ಆಂತರಿಕ) ಆರಂಭದಿಂದ ಅಂತ್ಯದವರೆಗೆ: ನೈಜ `selectQuotaShareTarget` ಸೀಮ್ ಮೂಲಕ DRR ನ್ಯಾಯಸಮ್ಮತತೆ + ಸ್ಯಾಚುರೇಶನ್ಗೆ ಆದ್ಯತೆ ತಗ್ಗಿಸುವಿಕೆ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`).
- ಪ್ರತಿಯೊಂದು ಗುರಿ ಎಣಿಕೆಯಾದ್ಯಂತ `context-relay` ಸಾರ್ವತ್ರಿಕ-ಹಸ್ತಾಂತರ ವ್ಯಾಪ್ತಿ.

ಈ ಸೂಟ್ CIಯಲ್ಲಿ (`test:integration` ಜಾಬ್) `--test-concurrency=1` ಮತ್ತು
`--test-force-exit` ಜೊತೆಗೆ ಚಲಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಇದು ನಿರ್ಣಾಯಕವಾಗಿದ್ದು ಲೈವ್ ರುಜುವಾತುಗಳ ಅಗತ್ಯವಿಲ್ಲ.

### ಗೇಟ್ ಮಾಡಲಾದ ಲೈವ್ ಸ್ಮೋಕ್ ಪರೀಕ್ಷೆ (CIಯಲ್ಲಿ ಇಲ್ಲ — ನೈಜ ಪೂರೈಕೆದಾರರು)

| ಕಮಾಂಡ್                                 | ಇದು ಏನು ಮಾಡುತ್ತದೆ                                                                                        |
| :------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` ಜೊತೆಗೆ ಪ್ರಕ್ರಿಯೆಯೊಳಗಿನ ನೈಜ ರೂಟಿಂಗ್; ಲೈವ್ OmniRoute DBಯ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ |
| `npm run test:combo:live:vps`          | ಲೈವ್ OmniRoute ಸರ್ವರ್ ವಿರುದ್ಧ HTTP ಕರೆಗಳು (`COMBO_LIVE_BASE_URL` ಹೊಂದಿಸಿ)                                |
| `npm run test:combo:live:vps:failover` | ಅದೇ, ಉದ್ದೇಶಪೂರ್ವಕ ಫೇಲ್ಓವರ್ ಸನ್ನಿವೇಶಗಳೊಂದಿಗೆ                                                              |

ಈ ಸ್ಮೋಕ್ ಪರೀಕ್ಷೆಗಳು ನೈಜ ವೈರ್ ಪಥವನ್ನು (ಕಾಂಬೊ → ಪೂರೈಕೆದಾರ → ಪೂರ್ಣಗೊಳಿಸುವಿಕೆ) ಪರೀಕ್ಷಿಸುತ್ತವೆ. ಇವುಗಳಿಗೆ
ಲೈವ್ ರುಜುವಾತುಗಳು ಮತ್ತು VPS ಪ್ರವೇಶದ ಅಗತ್ಯವಿರುವುದರಿಂದ, ಅವುಗಳನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ CIಯಿಂದ ಹೊರಗಿಡಲಾಗಿದೆ.
