> ಆಯ್ಕೆಮಾಡಿದಾಗ ಮಾತ್ರ ಸಕ್ರಿಯವಾಗುತ್ತದೆ, ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ (`settings.freeAccessPolicy !== "strict"` ಇದ್ದರೆ ಪ್ರತಿಯೊಂದು `auto/*`
> ಅಭ್ಯರ್ಥಿ ಪೂಲ್ ಬೈಟ್-ಮಟ್ಟದಲ್ಲಿ ಯಥಾವತ್ತಾಗಿರುತ್ತದೆ). ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಹಣಕಾಸಿನ ವೆಚ್ಚದ ವಿರುದ್ಧ ಕಟ್ಟುನಿಟ್ಟಿನ
> ಖಾತರಿ ಅಗತ್ಯವಿರುವ ನಿರ್ವಾಹಕರಿಗಾಗಿ `hidePaidModels`
> (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512) ನ ಇನ್ನಷ್ಟು ಕಟ್ಟುನಿಟ್ಟಿನ ಸಹೋದರ ಆಯ್ಕೆ;
> ಕೇವಲ "ಉಚಿತವೆಂದು ದಾಖಲಿಸಲಾಗಿದೆ" ಎಂಬುದಕ್ಕಷ್ಟೇ ಅಲ್ಲ.

## ಇದು ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ ಮತ್ತು `hidePaidModels` ಮಾತ್ರ ಏಕೆ ಸಾಕಾಗುವುದಿಲ್ಲ

`hidePaidModels`, "ಈ ಮಾದರಿಯನ್ನು ಇದೀಗ `FREE_MODEL_BUDGETS` ನಲ್ಲಿ ಉಚಿತವೆಂದು ವರ್ಗೀಕರಿಸಲಾಗಿದೆಯೇ?" ಎಂಬುದಕ್ಕೆ ಉತ್ತರಿಸುತ್ತದೆ —
ಇದು ನಿರ್ದಿಷ್ಟ ಸಮಯದ ಕ್ಯಾಟಲಾಗ್ ಸಂಗತಿಯಾಗಿದ್ದು, `isFreeModel()`/`providerHasFreeModels()`
(`src/shared/utils/freeModels.ts`) ಮೂಲಕ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಇದು ಎರಡು ನೈಜ ಅಪಾಯಗಳ ಬಗ್ಗೆ ಏನನ್ನೂ ಹೇಳುವುದಿಲ್ಲ:

1. `recurring-*`/`one-time-initial` ಉಚಿತ ಶ್ರೇಣಿಯ ಮಿತಿಯು **ಮುಗಿದಿರಬಹುದು** — ಕ್ಯಾಟಲಾಗ್ನಲ್ಲಿ
   ಮಾದರಿಯು ಇನ್ನೂ ಉಚಿತವೆಂದೇ ಪಟ್ಟಿಯಾಗಿರುತ್ತದೆ, ಆದರೆ ಅದರ ಹಿಂದಿರುವ ಖಾತೆಯಲ್ಲಿ ಯಾವುದೇ ಉಳಿದ ಸಾಮರ್ಥ್ಯವಿರುವುದಿಲ್ಲ.
2. ಉಚಿತ ಶ್ರೇಣಿಯನ್ನು ಮೀರಿದಾಗ ಯಾವಾಗಲೂ ಬಳಕೆ ಸಂಪೂರ್ಣವಾಗಿ ನಿಲ್ಲುವುದಿಲ್ಲ. ಕೆಲವು ಪೂರೈಕೆದಾರರು ಯಾವುದೇ
   ಪಾವತಿ ವಿಧಾನವನ್ನು ಲಗತ್ತಿಸಲು ಸಾಧ್ಯವೇ ಇಲ್ಲ ("ಕ್ರೆಡಿಟ್ ಕಾರ್ಡ್ ಅಗತ್ಯವಿಲ್ಲ") ಎಂದು ಸ್ಪಷ್ಟವಾಗಿ ದಾಖಲಿಸುತ್ತಾರೆ;
   ಇತರರು ಹಾಗೆ ಹೇಳುವುದಿಲ್ಲ, ಮತ್ತು ಕೆಲವರು ಉಚಿತ ಮಿತಿಯನ್ನು ಮೀರಿದ ನಂತರ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಶುಲ್ಕ ವಿಧಿಸುತ್ತಾರೆ.

`hidePaidModels` ಇವುಗಳ ನಡುವಿನ ವ್ಯತ್ಯಾಸವನ್ನು ಗುರುತಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ — ಅದನ್ನು ಅದಕ್ಕಾಗಿ ಎಂದಿಗೂ ಉದ್ದೇಶಿಸಿರಲಿಲ್ಲ. STRICT_ZERO_COST ನಿಖರವಾಗಿ
ಈ ಎರಡು ಪರಿಶೀಲನೆಗಳನ್ನು ಸೇರಿಸುತ್ತದೆ; ಅವುಗಳನ್ನು ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಗೆ, ವರ್ಗ/ಶ್ರೇಣಿ ಶ್ರೇಯಾಂಕದ **ಮೊದಲು** ಮತ್ತು
ರವಾನೆಯ **ಮೊದಲು** ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ — ವಿನಂತಿಯು ಈಗಾಗಲೇ ಹೊರಟ ನಂತರ ಎಂದಿಗೂ ಅಲ್ಲ.

## ಅಭ್ಯರ್ಥಿ ವರ್ಗೀಕರಣ

ಪೂಲ್ನಲ್ಲಿರುವ ಪ್ರತಿಯೊಬ್ಬ ಅಭ್ಯರ್ಥಿಗೂ (`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`,
`filterPaidOnlyCandidates` ನಂತರ ತಕ್ಷಣ):

1. **`FREE_MODEL_BUDGETS` ನಲ್ಲಿ ಇಲ್ಲವೇ ಇಲ್ಲ** → ಹೊರಗಿಡಲಾಗುತ್ತದೆ. ಇದು ನಿಜವಾಗಿಯೂ ಪಾವತಿಸಬೇಕಾದ ಮಾದರಿಗಳು ಮತ್ತು
   OmniRoute ಇನ್ನೂ ವರ್ಗೀಕರಿಸದ ಯಾವುದೇ ಪೂರೈಕೆದಾರ/ಮಾದರಿಯನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ — ಹೊಸ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಆರಂಭದಲ್ಲೇ
   ಹೊರಗಿಡಲಾಗುತ್ತದೆ, ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ.
2. **`freeType: "keyless"`** → ತಕ್ಷಣ ಅನುಮತಿಸಲಾಗುತ್ತದೆ, **ಆದರೆ ನಿಜವಾಗಿಯೂ ದೃಢೀಕರಣ-ರಹಿತ ಮಾರ್ಗದ ಮೂಲಕ
   ಬಂದ ಅಭ್ಯರ್ಥಿಗೆ ಮಾತ್ರ** (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`). ಆ ಅಭ್ಯರ್ಥಿಗೆ ಯಾವುದೇ ರುಜುವಾತುಗಳಿಲ್ಲ,
   ಆದ್ದರಿಂದ ಅದರ ವಿರುದ್ಧದ ಯಾವುದೇ ವಿನಂತಿಗೆ ಎಂದಿಗೂ ಶುಲ್ಕ ವಿಧಿಸಲಾಗುವುದಿಲ್ಲ — ರನ್ಟೈಮ್ ಪರಿಶೀಲನೆ ಅಗತ್ಯವೂ ಇಲ್ಲ,
   ಸಾಧ್ಯವೂ ಇಲ್ಲ. ಅದೇ ಕ್ಯಾಟಲಾಗ್ನಲ್ಲಿರುವ `keyless` ಪೂರೈಕೆದಾರ/ಮಾದರಿಯನ್ನು **ನೈಜ** DB
   ಸಂಪರ್ಕದ ಮೂಲಕ ತಲುಪಿದರೆ (`connectionId` ನಿಜವಾದ ಸಂಪರ್ಕ ಐಡಿ ಆಗಿದ್ದರೆ ಅಥವಾ ಅಭ್ಯರ್ಥಿಯು
   `allowedConnectionIds` ಹೊಂದಿದ್ದರೆ), ಅದಕ್ಕೆ ಈ ಶಾರ್ಟ್ಕಟ್ ಅನ್ವಯಿಸುವುದಿಲ್ಲ — `keyless` ಮೆಟಾಡೇಟಾ
   ನಿರ್ದಿಷ್ಟವಾಗಿ ದೃಢೀಕರಣ-ರಹಿತ ಮಾರ್ಗವನ್ನು ವಿವರಿಸುತ್ತದೆ, ಸಾಮಾನ್ಯವಾಗಿ ಪೂರೈಕೆದಾರನನ್ನಲ್ಲ, ಮತ್ತು ನೈಜ,
   ರುಜುವಾತು-ಸಹಿತ ಖಾತೆಯನ್ನು ಎಂದಿಗೂ ಅಧಿಕೃತಗೊಳಿಸುವುದಿಲ್ಲ. ಇಂತಹ ಅಭ್ಯರ್ಥಿಯು ಉಳಿದ ಎಲ್ಲರಂತೆಯೇ ಪರಿಶೀಲನೆ 3ಕ್ಕೆ
   ಮುಂದುವರಿಯುತ್ತದೆ; ಅಲ್ಲಿ ಕ್ಯಾಟಲಾಗ್ ದಾಖಲೆಯು ಪ್ರತ್ಯೇಕವಾಗಿ `hardStopGuaranteed: true` ಹೊಂದಿರದಿದ್ದರೆ ಅದನ್ನು
   ಹೊರಗಿಡಲಾಗುತ್ತದೆ (ನೈಜ `keyless` ದಾಖಲೆಗಳು ಎಂದಿಗೂ ಹಾಗೆ ಹೊಂದಿರುವುದಿಲ್ಲ — ಆ ಶಾರ್ಟ್ಕಟ್ ಮಾತ್ರವೇ ಅವುಗಳ
   ಸುರಕ್ಷತಾ ಮಾರ್ಗವಾಗಿತ್ತು).
3. **ಬೇರೆ ಯಾವುದೇ `freeType`** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial`, ಮತ್ತು ಈ ಮಾಡ್ಯೂಲ್ ವಿಶೇಷವಾಗಿ ನಿರ್ವಹಿಸದ ಯಾವುದೇ ಭವಿಷ್ಯದ ಪ್ರಕಾರ) →
   ಈ ಕೆಳಗಿನ **ಎಲ್ಲಾ** ಷರತ್ತುಗಳು ಈಡೇರಿದರೆ ಮಾತ್ರ ಅನುಮತಿಸಲಾಗುತ್ತದೆ:
   - ಕ್ಯಾಟಲಾಗ್ ದಾಖಲೆಯಲ್ಲಿ `hardStopGuaranteed: true` ಹೊಂದಿಸಿರಬೇಕು (`FreeModelBudget.hardStopGuaranteed`,
     `open-sse/config/freeModelCatalog.ts`) — ಇದು ಪೂರೈಕೆದಾರನ ಸ್ವಂತ ಪ್ರಕಟಿತ ಷರತ್ತುಗಳ ಕುರಿತ
     **ಕ್ಯುರೇಟ್ ಮಾಡಿ, ಕೈಯಾರೆ ಹೊಂದಿಸಿದ ಸಂಗತಿ** (ಉದಾ., "ಕ್ರೆಡಿಟ್ ಕಾರ್ಡ್ ಅಗತ್ಯವಿಲ್ಲ" ಎಂಬ ಸ್ಪಷ್ಟ ಹೇಳಿಕೆ);
     ಇದನ್ನು ಎಂದಿಗೂ `freeType` ನಿಂದ ಅಥವಾ ಲೈವ್ API ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ ಪಡೆಯಲಾಗುವುದಿಲ್ಲ. ಹೊಂದಿಸದಿರುವುದು
     (`undefined`) ಮತ್ತು `false` ಎರಡನ್ನೂ "ಖಾತರಿಪಡಿಸಿಲ್ಲ" ಎಂದು ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ.
   - `USAGE_FETCHER_PROVIDERS` ನಲ್ಲಿ ಪೂರೈಕೆದಾರನಿಗಾಗಿ ಬಳಕೆ ಅಡಾಪ್ಟರ್ ಅಸ್ತಿತ್ವದಲ್ಲಿರಬೇಕು
     (`open-sse/services/usage.ts`) — ಕೋಟಾ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಮತ್ತು `getUsageForProvider()` ಗೆ ಈಗಾಗಲೇ
     ಆಧಾರವಾಗಿರುವ ಅದೇ ರಿಜಿಸ್ಟ್ರಿ. ಅಡಾಪ್ಟರ್ ಇಲ್ಲ → ಒಂದನ್ನು ಸೇರಿಸುವವರೆಗೆ ಶಾಶ್ವತವಾಗಿ ಹೊರಗಿಡಲಾಗುತ್ತದೆ.
   - **ವಾಸ್ತವವಾಗಿ ಮೌಲ್ಯಮಾಪನಗೊಳ್ಳುತ್ತಿರುವ ನಿರ್ದಿಷ್ಟ ಸಂಪರ್ಕದ** ಲೈವ್, ಕ್ಯಾಶ್ ಮಾಡಲಾದ `FreeAccessState`
     `status: "SAFE"` ಆಗಿರಬೇಕು, `settings.autoRefreshProviderQuotaInterval` ಅವಧಿಯೊಳಗೆ ಪರಿಶೀಲಿಸಲ್ಪಟ್ಟಿರಬೇಕು
     (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ 180s — ಈಗಿರುವ ಸೆಟ್ಟಿಂಗ್, ಹೊಸ ಸಂಖ್ಯೆಯಲ್ಲ), ಮತ್ತು ಸಣ್ಣ ಸುರಕ್ಷತಾ ಅಂಚಿಗಿಂತ ಹೆಚ್ಚಿನ
     `remainingFreeAllowance` ಅನ್ನು ವರದಿ ಮಾಡಬೇಕು.
4. **`freeType: "discontinued"`** → ಯಾವಾಗಲೂ ಹೊರಗಿಡಲಾಗುತ್ತದೆ.

## ಸಂಪರ್ಕ ಸುರಕ್ಷತೆ (ಪ್ರತಿ-ಸಂಪರ್ಕ ಪರಿಶೀಲನೆ, ಎಂದಿಗೂ ಪ್ರತಿ-ಅಭ್ಯರ್ಥಿಯಂತೆ ಅಲ್ಲ)

ಸ್ವಯಂ-ಕಾಂಬೊ ಪೂಲ್ನಲ್ಲಿರುವ ಅಭ್ಯರ್ಥಿಯು ಯಾವಾಗಲೂ ಒಂದೇ ಸಂಪರ್ಕಕ್ಕೆ ಬದ್ಧವಾಗಿರುವುದಿಲ್ಲ. ಒಂದು "ತಾರ್ಕಿಕ" ಅಭ್ಯರ್ಥಿಯು
(`connectionId: null`) `allowedConnectionIds` ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಹೊಂದಿರುತ್ತದೆ — ವಿನಂತಿಯನ್ನು ಪೂರೈಸಬಹುದಾದ ಒಂದು ಅಥವಾ ಹೆಚ್ಚಿನ ನೈಜ
ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗಳು/ಖಾತೆಗಳು — ಮತ್ತು ವಾಸ್ತವವಾಗಿ ಬಳಸಲಾಗುವ ಖಾತೆಯನ್ನು ನಂತರ, ರವಾನೆ ಸಮಯದಲ್ಲಿ, `open-sse/services/combo/autoStrategy.ts`
ತನ್ನದೇ ಸಂಪರ್ಕ-ಆಯ್ಕೆ ತರ್ಕದೊಂದಿಗೆ `allowedConnectionIds` ಅನ್ನು ಛೇದಿಸುವ ಮೂಲಕ ನಿರ್ಧರಿಸುತ್ತದೆ (~ಸಾಲು 315-331).

STRICT_ZERO_COST ಆ ಅನುಮತಿ ಪಟ್ಟಿಯಲ್ಲಿರುವ **ಪ್ರತಿಯೊಂದು ಸಂಪರ್ಕದ ಮುಕ್ತ-ಪ್ರವೇಶ ಸ್ಥಿತಿಯನ್ನು
ಪ್ರತ್ಯೇಕವಾಗಿ** ಪರಿಶೀಲಿಸುತ್ತದೆ (`strictZeroCostFilter.ts` ನಲ್ಲಿನ `evaluateCandidateConnections()`) ಮತ್ತು
`allowedConnectionIds` ಅನ್ನು ನಿಖರವಾಗಿ `SAFE` ಎಂದು ಹಿಂದಿರುಗಿದ ಉಪಸಮೂಹಕ್ಕೆ ಮರುಬರೆಯುತ್ತದೆ — ಎಂದಿಗೂ ಸಂಪೂರ್ಣ
ಮೂಲ ಪಟ್ಟಿಗೆ ಅಲ್ಲ ಮತ್ತು ಎಂದಿಗೂ ಅನಿಯಂತ್ರಿತವಾಗಿ ಆಯ್ಕೆಮಾಡಿದ ಏಕೈಕ ಸದಸ್ಯನಿಗೆ ಅಲ್ಲ. ನಿರ್ದಿಷ್ಟವಾಗಿ:

- ಖಾತೆ A `SAFE`, ಖಾತೆ B `UNKNOWN`/ಮಿತಿಮೀರಿದ/ಶುಲ್ಕ ವಿಧಿಸಬಹುದಾದ → A ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಬಹುದಾಗಿ ಉಳಿಯುತ್ತದೆ.
- ಎಲ್ಲ ಖಾತೆಗಳೂ `UNKNOWN` → ಅಭ್ಯರ್ಥಿಯನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಕೈಬಿಡಲಾಗುತ್ತದೆ (ಖಾಲಿ ಸುರಕ್ಷಿತ ಸಮೂಹ).
- ವಿಫಲವಾಗುವ ಏಕ-ಸಂಪರ್ಕ ಅಭ್ಯರ್ಥಿಯನ್ನು (`connectionId` ನೇರವಾಗಿ ಹೊಂದಿಸಲಾಗಿದೆ, ಅನುಮತಿ ಪಟ್ಟಿ ಇಲ್ಲ) ಸಂಪೂರ್ಣವಾಗಿ
  ಕೈಬಿಡಲಾಗುತ್ತದೆ; ಖಾಲಿ `allowedConnectionIds` ಜೊತೆಗೆ ಎಂದಿಗೂ ಹಿಂದಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ.

ರವಾನೆಗೆ ಸಂಪರ್ಕವನ್ನು ಆಯ್ಕೆಮಾಡುವ ಮೊದಲು `autoStrategy.ts` ಈಗಾಗಲೇ `allowedConnectionIds` ಅನ್ನು ಕಟ್ಟುನಿಟ್ಟಿನ ಅನುಮತಿ ಪಟ್ಟಿಯಾಗಿ
ಜಾರಿಗೊಳಿಸುವುದರಿಂದ, ಅದನ್ನು ಪರಿಶೀಲಿಸಲಾದ-SAFE ಉಪಸಮೂಹಕ್ಕೆ ಮರುಬರೆಯುವುದು ರವಾನೆ ಸಮಯದಲ್ಲಿ ವಾಸ್ತವವಾಗಿ ಬಳಸಲಾಗುವ ಸಂಪರ್ಕವು
ಯಾವಾಗಲೂ ಈ ಫಿಲ್ಟರ್ ಸ್ವತಃ ಪರಿಶೀಲಿಸಿದ ಸಂಪರ್ಕವೇ ಆಗಿರುತ್ತದೆ ಎಂಬುದನ್ನು ಖಾತರಿಪಡಿಸಲು ಸಾಕಾಗುತ್ತದೆ —
ಅದೇ ಅಭ್ಯರ್ಥಿಯಲ್ಲಿರುವ ಬೇರೊಂದು, ಪರಿಶೀಲಿಸದ ಖಾತೆ ಎಂದಿಗೂ ಅಲ್ಲ. ಹಿಂಜರಿತದ ಪುರಾವೆಗಾಗಿ
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts` ನೋಡಿ
(ಕೀಲಿರಹಿತ-ಬೈಪಾಸ್ ಪ್ರಕರಣಗಳು A/B/C, ಬಹು-ಖಾತೆ ಪ್ರಕರಣಗಳು 1-5).

`ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪತ್ತೆಹಚ್ಚಲಾಗಿದೆ`: ಸೂಕ್ತ ಮೆಟಾಡೇಟಾದೊಂದಿಗೆ ನಾಳೆ ಬಿಡುಗಡೆಯಾಗುವ ಪೂರೈಕೆದಾರ/ಮಾದರಿಯು (ಕ್ಯಾಟಲಾಗ್ನಲ್ಲಿ,
ಬಳಕೆ ಅಡಾಪ್ಟರ್ ಜೊತೆಗೆ, `hardStopGuaranteed: true`) OmniRoute ಗೆ ಅದರ ಬಗ್ಗೆ ತಿಳಿದ ಕ್ಷಣದಿಂದಲೇ
ಬಳಸಬಹುದಾಗಿರುತ್ತದೆ — ಯಾವುದೇ ಕೋಡ್ ಬದಲಾವಣೆ ಇಲ್ಲ, ಅನುಮತಿ-ಪಟ್ಟಿ ನಮೂದು ಇಲ್ಲ, ಈ ಮಾಡ್ಯೂಲ್ನಲ್ಲಿ ಸಂಪಾದಿಸಲು ಏನೂ ಇಲ್ಲ. ಕ್ಯಾಟಲಾಗ್ನಿಂದ
ತೆಗೆದುಹಾಕಲಾದುದು ಅದೇ ರೀತಿಯಲ್ಲಿ ಕಣ್ಮರೆಯಾಗುತ್ತದೆ. ಹಿಂಜರಿತದ ಪುರಾವೆಗಾಗಿ
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` ನೋಡಿ (ನೈಜ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಪರಿವರ್ತಿಸುವ ಬದಲು
ಇಂಜೆಕ್ಟ್ ಮಾಡಬಹುದಾದ ಫಿಕ್ಸ್ಚರ್ಗಳ ಮೂಲಕ).

## ಕೋಟಾ ಕ್ಯಾಶಿಂಗ್ (`open-sse/services/autoCombo/freeAccessQuota.ts`)

`getUsageForProvider()` ಅನ್ನು ಮರುಬಳಸುತ್ತದೆ — ಎರಡನೇ ಕೋಟಾ ವ್ಯವಸ್ಥೆಯಿಲ್ಲ. ಸಂಕ್ಷಿಪ್ತ, ಇನ್-ಮೆಮೊರಿ,
ಪ್ರಕ್ರಿಯೆ-ಆಯುಷ್ಯದ ಕ್ಯಾಶ್ ಅದರ ಮುಂದೆ ಇರುತ್ತದೆ (TTL ಡೀಫಾಲ್ಟ್
`autoRefreshProviderQuotaInterval` ಗೆ ಸಮನಾಗಿರುತ್ತದೆ), ಆದ್ದರಿಂದ Telegram-ಪ್ರಮಾಣದ ವಿನಂತಿ ದರವು ಪ್ರತಿ ವಿನಂತಿಯ ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಗೆ
ನೇರ billing-API ಕರೆಯನ್ನು ಎಂದಿಗೂ ಪ್ರಚೋದಿಸುವುದಿಲ್ಲ. ಓದುವಿಕೆಗಳು ಸಮಕಾಲಿಕವಾಗಿವೆ: ಕ್ಯಾಶ್ ಮಿಸ್
`undefined` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ (→ ಹೊರಗಿಡಲಾಗುತ್ತದೆ, ವಿಫಲವಾದಾಗ ಮುಚ್ಚಲಾಗುತ್ತದೆ) ಮತ್ತು _ಮುಂದಿನ_ ಓದುವಿಕೆಗಾಗಿ ಹಿನ್ನೆಲೆಯಲ್ಲಿ ರಿಫ್ರೆಶ್ ಅನ್ನು
ಪ್ರಾರಂಭಿಸುತ್ತದೆ — ಅಭ್ಯರ್ಥಿ-ಪೂಲ್ ನಿರ್ಮಾಣ ಮಾರ್ಗದಲ್ಲಿರುವ ಯಾವುದೂ ನೆಟ್ವರ್ಕ್ ಕರೆಗಾಗಿ ಎಂದಿಗೂ ಕಾಯುವುದಿಲ್ಲ.

ಯಾವುದೇ ಕಾರಣಕ್ಕಾಗಿ ಸಂಪರ್ಕವು ವಿಫಲವಾದ ಕ್ಷಣದಲ್ಲೇ
`src/sse/services/auth.ts::markAccountUnavailable()` ನಿಂದ `invalidateFreeAccessState(provider, connectionId)` ಅನ್ನು ಕರೆಯಲಾಗುತ್ತದೆ,
ಆದ್ದರಿಂದ ನಂತರದ ತಕ್ಷಣದ ಪೂಲ್ ನಿರ್ಮಾಣವು ಹಳೆಯ `SAFE` ನಮೂದಿನ ಬದಲು ಶುದ್ಧ ಕ್ಯಾಶ್ ಮಿಸ್ ಅನ್ನು ಓದುತ್ತದೆ —
402/403/ಕೋಟಾ-ಮುಗಿದ ಪ್ರತಿಕ್ರಿಯೆಯ ನಂತರ TTL ಮುಗಿಯುವವರೆಗೆ ಕಾಯುವ ಅಗತ್ಯವಿಲ್ಲ.

## ToS ರಕ್ಷಣೆ (ಆರ್ಥಿಕ ಸುರಕ್ಷತೆಯಿಂದ ಸ್ವತಂತ್ರ)

`excludeTosAvoid` (ಡೀಫಾಲ್ಟ್ `false`) ಕ್ಯುರೇಟ್ ಮಾಡಲಾದ `tos` ತೀರ್ಪು
(`FreeModelBudget.tos`) `"avoid"` ಆಗಿರುವ ಯಾವುದೇ ಅಭ್ಯರ್ಥಿಯನ್ನು ಕೈಬಿಡುತ್ತದೆ — ಈಗಾಗಲೇ ಮೌಲ್ಯಗಳನ್ನು ಹೊಂದಿರುವ `hidePaidModels`-ನ ಸಹೋದರ ದಸ್ತಾವೇಜುಗಳ
(`docs/reference/FREE_TIERS.md`) ಅದೇ ಕ್ಷೇತ್ರವನ್ನು ಇದು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ. ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
`freeAccessPolicy`-ಯಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿ ಇರಿಸಲಾಗಿದೆ: ಅಭ್ಯರ್ಥಿಯೊಂದು ಆರ್ಥಿಕವಾಗಿ `SAFE` ಆಗಿದ್ದರೂ ಒಪ್ಪಂದಾತ್ಮಕ
ಕಾರಣಗಳಿಂದ ಇಲ್ಲಿ ಹೊರಗಿಡಬಹುದು, ಅಥವಾ ಈ ರಕ್ಷಣೆ ಆಫ್ ಆಗಿರುವಾಗ `freeAccessPolicy: "strict"` ಆನ್ ಇದ್ದರೂ ಅದನ್ನು ಉಳಿಸಬಹುದು.

ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯನ್ನು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದೂ `freeAccessExclusion` ಅನ್ನು ಹೊಂದಿರುತ್ತದೆ — ರಕ್ಷಣೆಯ

| `no-hard-stop`         | ಉಚಿತ ವ್ಯವಸ್ಥೆ, ಆದರೆ `hardStopGuaranteed` `true` ಅಲ್ಲ; ಆದ್ದರಿಂದ ಮಿತಿಯನ್ನು ಮೀರಿದರೆ ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಬಿಲ್ಲಿಂಗ್ ಆರಂಭವಾಗಬಹುದು. | ಪೂರೈಕೆದಾರರ ನಿಯಮಗಳನ್ನು ಪರಿಶೀಲಿಸಿ ಮತ್ತು ಮೂಲವನ್ನು ಕಾಮೆಂಟ್ನಲ್ಲಿ ಉಲ್ಲೇಖಿಸಿ ಫ್ಲ್ಯಾಗ್ ಅನ್ನು ಹೊಂದಿಸಿ — ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ವಿಸ್ತರಿಸುವ ಉದ್ದೇಶಕ್ಕಾಗಿ ಎಂದಿಗೂ ಹಾಗೆ ಮಾಡಬೇಡಿ. |
| `contradictory-noauth` | ಕ್ಯಾಟಲಾಗ್ ನಮೂದು `keyless` ಆಗಿರದ, ದೃಢೀಕರಣ ಅಗತ್ಯವಿಲ್ಲದ ಅಭ್ಯರ್ಥಿ. ಅಸಂಗತ ಮೆಟಾಡೇಟಾ ಇದ್ದಾಗ ಸುರಕ್ಷಿತವಾಗಿ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ.         | ಕ್ಯಾಟಲಾಗ್ ನಮೂದನ್ನು ಸರಿಪಡಿಸಿ; ಈ ಎರಡು ಸಂಗತಿಗಳು ಪರಸ್ಪರ ಹೊಂದಿಕೆಯಾಗುವುದಿಲ್ಲ.                                                                                     |
| `exhausted`            | ಇತ್ತೀಚಿನ ರೀಡಿಂಗ್ ಪ್ರಕಾರ ಮಿತಿಯು ಸಂಪೂರ್ಣವಾಗಿ ಬಳಕೆಯಾಗಿದೆ.                                                                       | ಮರುಹೊಂದಿಕೆಗಾಗಿ ಕಾಯಿರಿ. ಇದು ಸ್ವತಃ ಪರಿಹಾರವಾಗುತ್ತದೆ.                                                                                                           |
| `state-unknown`        | ಕೋಟಾ ರೀಡಿಂಗ್ ಇಲ್ಲ, ಅಥವಾ ಇರುವ ರೀಡಿಂಗ್ ನಂಬಲಾಗದಷ್ಟು ಹಳೆಯದು.                                                                     | ಪರಿಶೀಲಿಸಿ: ಪೂರೈಕೆದಾರರಿಗಾಗಿ ಯಾವುದೇ ಬಳಕೆ ಅಡಾಪ್ಟರ್ ನೋಂದಾಯಿಸಿರದೇ ಇರಬಹುದು, ಅಥವಾ ಕೋಟಾ ಪಡೆಯುವಿಕೆ ವಿಫಲವಾಗುತ್ತಿರಬಹುದು.                                               |
| `no-connection`        | ಪರಿಶೀಲಿಸಲು ಅಭ್ಯರ್ಥಿಯು ಯಾವುದೇ ಖಾತೆಯನ್ನು ಹೊಂದಿಲ್ಲ.                                                                             | ಇದು ಕೋಟಾ ಸಮಸ್ಯೆಯಲ್ಲ: ಅಭ್ಯರ್ಥಿಯನ್ನು ಸಂಪರ್ಕವಿಲ್ಲದೆ ನಿರ್ಮಿಸಲಾಗಿದೆ, ಆದ್ದರಿಂದ ಯಾವುದನ್ನೂ ಎಂದಿಗೂ ಪರಿಶೀಲಿಸಲಾಗಿಲ್ಲ. ಪೂಲ್ ಹೇಗೆ ರಚಿಸಲಾಗಿದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ.        |

ಕೊನೆಯ ಎರಡು ಪ್ರತ್ಯೇಕವಾಗಿ ಗುರುತಿಸಬೇಕಾದ ಜೋಡಿಯಾಗಿವೆ. ಸಂಪೂರ್ಣವಾಗಿ ಬಳಸಿದ ಮಿತಿಯು ಸ್ವತಃ ಮರುಹೊಂದಿಕೆಯಾಗುತ್ತದೆ; ಎಂದಿಗೂ
ಬಾರದ ರೀಡಿಂಗ್ ಎಂದರೆ ಲುಕ್ಅಪ್ ಸ್ವತಃ ದೋಷಪೂರಿತವಾಗಿದೆ ಎಂದರ್ಥ, ಮತ್ತು ಇದುವರೆಗೆ ಹೊರಗಿನಿಂದ ನೋಡಿದಾಗ ಎರಡೂ ಒಂದೇ ರೀತಿ
ಕಾಣುತ್ತಿದ್ದವು — ಅಭ್ಯರ್ಥಿಯು ಸುಮ್ಮನೆ ಕಣ್ಮರೆಯಾಗುತ್ತಿತ್ತು.

**ಒಂದು ಅಂತರ ಇನ್ನೂ ಉಳಿದಿದೆ, ಮತ್ತು ಅದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದೆ.** ಪಟ್ಟಿಯನ್ನು ನಿರ್ಮಿಸುವ ಮೊದಲೇ `excludeTosAvoid` ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಇನ್ನೂ ತೆಗೆದುಹಾಕುತ್ತದೆ,
ಆದ್ದರಿಂದ `tos: "avoid"` ಎಂದು ಕ್ಯುರೇಟ್ ಮಾಡಲಾದ ಮಾದರಿಯು ಯಾವುದೇ ಕಾರಣ ನೀಡದೆ ಪಟ್ಟಿಯಿಂದ ಗೈರಾಗಿರುತ್ತದೆ — ಶೂನ್ಯ-ವೆಚ್ಚದ ರಕ್ಷಣೆಗಾಗಿ ಈ ವಿಭಾಗವು ಈಗಷ್ಟೇ
ನಿವಾರಿಸಿದ ಅದೇ ಅದೃಶ್ಯತೆ ಇದು. ಇದನ್ನೂ ನಿವಾರಿಸುವುದೆಂದರೆ ToS ಹೊರಗಿಡುವಿಕೆಯು ಏನನ್ನು ವರದಿ ಮಾಡಬೇಕು ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸುವುದು,
ಇದು ಆರ್ಥಿಕ ಸುರಕ್ಷತೆಯಿಂದ ಪ್ರತ್ಯೇಕವಾದ ಪ್ರಶ್ನೆ; ಈ ಪುಟವು ಆ ಅಂತರವೇ ಇಲ್ಲವೆಂದು ನಟಿಸುವ ಬದಲು ಅದನ್ನು ಹೆಸರಿಸುತ್ತದೆ.

ಆಫ್ಲೈನ್ ಮೊದಲು/ನಂತರದ ಹೋಲಿಕೆಗಾಗಿ, `npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` ಇನ್ನೂ ಚಾಲನೆಯಲ್ಲಿರುವ
ಇನ್ಸ್ಟಾನ್ಸ್ನ ಅಭ್ಯರ್ಥಿಗಳ ಔಟ್ಪುಟ್ ವಿರುದ್ಧ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ; ಇದು ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯ ನೈಜ `connectionId` ಅನ್ನು ಓದುತ್ತದೆ, ಆದ್ದರಿಂದ
ಸಂಪರ್ಕ-ಸುರಕ್ಷತಾ ಮಾರ್ಗವನ್ನೂ ಪರೀಕ್ಷಿಸುತ್ತದೆ. ಕೀಲಿರಹಿತ ಅಭ್ಯರ್ಥಿಗಳು ಕೃತಕ
ದೃಢೀಕರಣ-ರಹಿತ `connectionId` ಜೊತೆಯಲ್ಲೇ ಬರಬೇಕು, ನೈಜ ಸಂಪರ್ಕದೊಂದಿಗೆ ಎಂದಿಗೂ ಅಲ್ಲ. ಪ್ರಸ್ತುತ ಅಂತರ್ನಿರ್ಮಿತ ಕೀಲಿರಹಿತ ಸ್ವಯಂಚಾಲಿತ ಮಾರ್ಗವು OpenCode Free ಆಗಿದೆ; ನಿಖರವಾದ ಅಭ್ಯರ್ಥಿ ಸಂಖ್ಯೆಗಳು
ಇನ್ನೂ ಚಾಲನೆಯಲ್ಲಿರುವ ಮಾದರಿ ಅನ್ವೇಷಣೆಯನ್ನು ಅವಲಂಬಿಸಿವೆ ಮತ್ತು ಅವುಗಳನ್ನು ಹಳೆಯ ರನ್ನಿಂದ ನಕಲಿಸುವ ಬದಲು ಗುರಿ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ನಲ್ಲಿ
ಅಳೆಯಬೇಕು. `recurring-*` ಅಭ್ಯರ್ಥಿಯು ನೋಂದಾಯಿತ ಬಳಕೆ ಅಡಾಪ್ಟರ್ ಮತ್ತು `hardStopGuaranteed: true` ಎರಡನ್ನೂ
ಹೊಂದಿದ್ದಾಗ ಮಾತ್ರ ಉತ್ತೀರ್ಣವಾಗುತ್ತದೆ; ಅಪೂರ್ಣ ಮೆಟಾಡೇಟಾವನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ನಿರಾಕರಿಸುವುದು ಮುಂದುವರಿಯುತ್ತದೆ.

`excludeTosAvoid: true` ಇದ್ದಾಗ, `tos: "avoid"` ಎಂದು ಕ್ಯುರೇಟ್ ಮಾಡಲಾದ ಪ್ರತಿಯೊಂದು ಅಭ್ಯರ್ಥಿಯನ್ನೂ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ. OpenCode Free
ಪ್ರಸ್ತುತ ಆ ತೀರ್ಪನ್ನು ಹೊಂದಿದೆ, ಆದ್ದರಿಂದ ರಕ್ಷಣೆಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದರಿಂದ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ನಲ್ಲಿ ಉಳಿದಿರುವ ಕೀಲಿರಹಿತ
ಪೂಲ್ ಖಾಲಿಯಾಗಬಹುದು. ಇದು ToS ರಕ್ಷಣೆಯನ್ನು ಆನ್ ಮಾಡುವುದರಿಂದ ಉಂಟಾಗುವ ನಿರೀಕ್ಷಿತ ರಾಜಿ, ದೋಷವಲ್ಲ: ನಿಖರವಾಗಿ ಈ ಕಾರಣಕ್ಕಾಗಿಯೇ ರಕ್ಷಣೆಯು ಡೀಫಾಲ್ಟ್ ಆಗಿ `false`
ಆಗಿದೆ (ಮೇಲಿನ "ToS ರಕ್ಷಣೆ" ನೋಡಿ).

## ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

ಎರಡೂ ಹೊಸ ಸೆಟ್ಟಿಂಗ್ಗಳು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಅವುಗಳ ವೈಶಿಷ್ಟ್ಯ-ಪೂರ್ವ ಮೌಲ್ಯಗಳನ್ನು (`"off"` / `false`) ಹೊಂದಿರುತ್ತವೆ — ಯಾವುದನ್ನೂ ಸಕ್ರಿಯಗೊಳಿಸದಿದ್ದರೆ
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಯಾವುದೇ `auto/*` ರೂಟಿಂಗ್ ನಡವಳಿಕೆ ಬದಲಾಗುವುದಿಲ್ಲ.
