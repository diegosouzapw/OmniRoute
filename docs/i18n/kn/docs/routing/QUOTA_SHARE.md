## ಅವಲೋಕನ

ಕೋಟಾ ಹಂಚಿಕೆ ಎಂಜಿನ್, ಒಂದೇ ಸಂಪರ್ಕವನ್ನು ಹಂಚಿಕೊಳ್ಳುವ ಹಲವು API ಕೀಗಳ ನಡುವೆ ಪೂರೈಕೆದಾರರ ಸಮಯಾಧಾರಿತ ಕೋಟಾವನ್ನು (ಉದಾ. Codex
5-ಗಂಟೆಗಳ ವಿಂಡೋ, Kimi 1500 req/h) ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಹಂಚುತ್ತದೆ.

**ಇದು ಪರಿಹರಿಸುವ ಸಮಸ್ಯೆ:** OmniRoute ಒಂದೇ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ಖಾತೆಯ ವಿರುದ್ಧ ಅನೇಕ API ಕೀಗಳನ್ನು ಪ್ರಾಕ್ಸಿ ಮಾಡುತ್ತದೆ.
ಹಂಚಿಕೆ ತರ್ಕವಿಲ್ಲದೆ, ಕೀ Aಯಿಂದ ಬರುವ ಹಠಾತ್ ವಿನಂತಿಗಳ ಹೆಚ್ಚಳವು ಆ ಗಂಟೆಯ ಪೂರೈಕೆದಾರರ ಕೋಟಾವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಳಸಿಬಿಡಬಹುದು;
ಇದರಿಂದ ವಿಂಡೋ ಮರುಹೊಂದುವವರೆಗೆ ಕೀಗಳು B ಮತ್ತು C ನಿರ್ಬಂಧಿತವಾಗಿರುತ್ತವೆ.
ಎಂಜಿನ್ ಇದನ್ನು ಈ ರೀತಿ ತಡೆಯುತ್ತದೆ:

1. ಪ್ರತಿ ಆಯಾಮದಾದ್ಯಂತ (%, ವಿನಂತಿಗಳು, ಟೋಕನ್ಗಳು, $) ಪ್ರತಿಯೊಂದು ಕೀಯ ರೋಲಿಂಗ್ ಬಳಕೆಯನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ.
2. ಕೆಲಸವನ್ನು ಸಂರಕ್ಷಿಸುವ ನ್ಯಾಯಸಮ್ಮತ-ಹಂಚಿಕೆ ಅಲ್ಗಾರಿದಮ್ ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ: ಜಾಗತಿಕ ಪೂಲ್ ಪರಿಪೂರ್ಣವಾಗಿ ಬಳಕೆಯಾಗದಿರುವವರೆಗೆ ಕೀಯೊಂದು ನಿಷ್ಕ್ರಿಯ
   ಪಾಲುಗಳಿಂದ ಎರವಲು ಪಡೆಯಬಹುದು.
3. ವಿನಂತಿಯು ಅಪ್ಸ್ಟ್ರೀಮ್ ಎಕ್ಸಿಕ್ಯೂಟರ್ ಅನ್ನು ತಲುಪುವ ಮೊದಲು ಹಾಟ್ ಪಾತ್ನಲ್ಲಿ (`chatCore.ts`) ಫಲಿತಾಂಶವನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ.

## ಅಲ್ಗಾರಿದಮ್: ಕೆಲಸವನ್ನು ಸಂರಕ್ಷಿಸುವ ನ್ಯಾಯಸಮ್ಮತ-ಹಂಚಿಕೆ

`src/lib/quota/fairShare.ts`ನಲ್ಲಿ ಅನುಷ್ಠಾನಗೊಳಿಸಲಾಗಿದೆ.

### ಮೋಡ್ಗಳು

| ಷರತ್ತು                                     | ಮೋಡ್            | ವರ್ತನೆ                                                                    |
| ------------------------------------------ | --------------- | ------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **ಉದಾರ**        | ಒಟ್ಟು ಮಿತಿಯಿಂದ ಬಳಕೆಯಾದ ಒಟ್ಟು ಪ್ರಮಾಣವನ್ನು ಕಳೆದಷ್ಟರವರೆಗೆ ಕೀ ಎರವಲು ಪಡೆಯಬಹುದು |
| `globalUsedPercent >= saturationThreshold` | **ಕಟ್ಟುನಿಟ್ಟು** | ಪ್ರತ್ಯೇಕ ನ್ಯಾಯಸಮ್ಮತ ಪಾಲನ್ನು ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಜಾರಿಗೊಳಿಸುತ್ತದೆ                 |

ಡೀಫಾಲ್ಟ್ `saturationThreshold = 0.5` (env `QUOTA_SATURATION_THRESHOLD`).

### ಪ್ರತಿ-ಆಯಾಮದ ನಿರ್ಧಾರ

ಪೂಲ್ನಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು ಸಕ್ರಿಯ ಆಯಾಮಕ್ಕಾಗಿ, ಎಂಜಿನ್ ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಲೆಕ್ಕಹಾಕುತ್ತದೆ:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

ನಂತರ:

- **`policy = hard`**: `consumed > fairShareAllowed` ಆಗಿದ್ದು ಮೋಡ್ ಕಟ್ಟುನಿಟ್ಟಾಗಿದ್ದರೆ → **ನಿರ್ಬಂಧಿಸು**.
- **`policy = soft`**: `consumed > fairShareAllowed` ಆಗಿದ್ದು ಮೋಡ್ ಕಟ್ಟುನಿಟ್ಟಾಗಿದ್ದರೆ → **ದಂಡ ವಿಧಿಸು** (ಕಾಂಬೊದಲ್ಲಿ ಆದ್ಯತೆಯನ್ನು ಕಡಿಮೆಮಾಡಿ; ಎಂದಿಗೂ ಸಂಪೂರ್ಣವಾಗಿ ನಿರ್ಬಂಧಿಸಬೇಡಿ).
- **`policy = burst`**: ನ್ಯಾಯಸಮ್ಮತ ಪಾಲನ್ನು ಲೆಕ್ಕಿಸದೆ ಜಾಗತಿಕವಾಗಿ ಲಭ್ಯ ಸಾಮರ್ಥ್ಯ ಇರುವವರೆಗೆ ಅನುಮತಿಸಿ.

### ಸಂಪೂರ್ಣ ಮಿತಿ

ಹಂಚಿಕೆಯಲ್ಲಿರುವ `capValue` + `capUnit`, ಮೋಡ್ ಅಥವಾ ನೀತಿಯಿಂದ ಸ್ವತಂತ್ರವಾದ ಕಟ್ಟುನಿಟ್ಟಿನ ಗರಿಷ್ಠ ಮಿತಿಯಾಗಿದೆ.
`consumed >= capValue` ಆಗಿರುವ ಯಾವುದೇ ಆಯಾಮವು ಯಾವಾಗಲೂ ವಿನಂತಿಯನ್ನು **ನಿರ್ಬಂಧಿಸುತ್ತದೆ**.

### ಬಹು-ಆಯಾಮದ ಪರಿಶೀಲನೆ

ಪೂಲ್ನಲ್ಲಿರುವ **ಯಾವುದೇ** ಆಯಾಮವು ವಿನಂತಿಯನ್ನು ನಿರ್ಬಂಧಿಸುವುದಾದರೆ, ಆ ವಿನಂತಿಯನ್ನು ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ. ಆಯಾಮಗಳು
ಪರಸ್ಪರ ಸ್ವತಂತ್ರವಾಗಿವೆ — 5h% ಖಾಲಿಯಾಗುವುದರಿಂದ weekly% ಆಯಾಮದ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

### ಎರವಲು ಪಡೆಯುವಿಕೆ

ಉದಾರ ಮೋಡ್ನಲ್ಲಿ, ತನ್ನ ಹಂಚಿಕೆಯನ್ನು ಕಡಿಮೆ ಬಳಸಿರುವ ಕೀಯೊಂದು ಇತರ ಕೀಗಳ ಹಂಚಿಕೆಯಾಗದ ಪಾಲುಗಳಿಂದ ಹೆಚ್ಚುವರಿ ಸಾಮರ್ಥ್ಯವನ್ನು
ಬಳಸಬಹುದು. ಸೂತ್ರವು ಹೀಗಿದೆ:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

ಇಲ್ಲಿ `consumedByOtherKeys = consumedTotal - consumedByThisKey`. ಜಾಗತಿಕ ಗರಿಷ್ಠ ಮಿತಿ
(ಆ ಆಯಾಮದ ಪೂಲ್ `limit`) ಯಾವಾಗಲೂ ಕಟ್ಟುನಿಟ್ಟಿನ ಗರಿಷ್ಠ ಮಿತಿಯಾಗಿರುತ್ತದೆ.

## ಸ್ಲೈಡಿಂಗ್ ವಿಂಡೋ ಕೌಂಟರ್

`src/lib/quota/sqliteQuotaStore.ts` ಮತ್ತು `redisQuotaStore.ts`ನಲ್ಲಿ ಅನುಷ್ಠಾನಗೊಳಿಸಲಾಗಿದೆ.

ಪ್ರತಿ `(apiKeyId, dimensionKey)`ಗೆ ಎರಡು ಬಕೆಟ್ಗಳು:

- `curr`: ಪ್ರಸ್ತುತ ಬಕೆಟ್ (`floor(nowMs / windowMs)`)
- `prev`: ಹಿಂದಿನ ಬಕೆಟ್ (`curr - 1`)

ಪರಿಣಾಮಕಾರಿ ರೋಲಿಂಗ್ ಮೌಲ್ಯ:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ನಿಖರತೆ**: ಸುಮಾರು 99% ನಿಖರವಾಗಿದೆ. ಬಕೆಟ್ಗಳ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ದೋಷವು ವಿಂಡೋ ಗಾತ್ರದ ಗರಿಷ್ಠ 1%ರಷ್ಟಿರುತ್ತದೆ
(2-ಬಕೆಟ್ ಅಂದಾಜಿನಲ್ಲಿ ಇದು ಅಂತರ್ಗತವಾಗಿದೆ).

### ಸಮಕಾಲೀನತೆ

SQLite ಡ್ರೈವರ್: ಪ್ರತಿ `(apiKeyId | dimensionKey)` ಕೀಗಾಗಿ ಇನ್-ಮೆಮೊರಿ ಮ್ಯೂಟೆಕ್ಸ್,
ಓದು-ಮಾರ್ಪಡಿಸು-ಬರೆಯುವಿಕೆ ರೇಸ್ ಅನ್ನು ತಡೆಯುತ್ತದೆ. ಈ ಮಾದರಿಯು `src/sse/services/auth.ts`ನ anti-thundering-herd ವಿಧಾನವನ್ನು ಅನುಸರಿಸುತ್ತದೆ.

Redis ಡ್ರೈವರ್: ಅಟಾಮಿಕ್ ಇನ್ಕ್ರಿಮೆಂಟ್ಗಾಗಿ Lua EVAL ಸ್ಕ್ರಿಪ್ಟ್ — ಇದು ಒಂದೇ Redis ಕಮಾಂಡ್ ಆಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.

## ಡ್ರೈವರ್ಗಳು

### SQLite (ಡೀಫಾಲ್ಟ್, 0-ಇನ್ಸ್ಟಾಲ್)

- ಟೇಬಲ್: `quota_consumption` (ಮೈಗ್ರೇಶನ್ `073_quota_pools.sql` / `074_quota_consumption.sql` ನೋಡಿ).
- ಏಕ-ಇನ್ಸ್ಟೆನ್ಸ್ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ಗಳಿಗೆ ಅತ್ಯುತ್ತಮವಾಗಿದೆ.
- ಎಲ್ಲಾ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OmniRoute SQLite DB (`DATA_DIR/storage.sqlite`) ನಲ್ಲಿರುತ್ತದೆ.

### Redis (ಐಚ್ಛಿಕ, ಬಹು-ಇನ್ಸ್ಟೆನ್ಸ್)

- `ioredis` npm ಪ್ಯಾಕೇಜ್ ಅಗತ್ಯವಿದೆ.
- ಕೌಂಟರ್ಗಳನ್ನು Redis ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ; ಮೆಟಾಡೇಟಾ (ಪೂಲ್ಗಳು/ಹಂಚಿಕೆಗಳು) ಇನ್ನೂ SQLite ನಲ್ಲಿರುತ್ತದೆ.
- ಕೌಂಟರ್ಗಳನ್ನು ಹಂಚಿಕೊಳ್ಳಬೇಕಾದ ಬಹು-ರೆಪ್ಲಿಕಾ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ಗಳಿಗೆ ಅತ್ಯುತ್ತಮವಾಗಿದೆ.

### ಡ್ರೈವರ್ಗಳನ್ನು ಬದಲಾಯಿಸುವುದು

ಸೆಟ್ಟಿಂಗ್ಗಳ UI ಮೂಲಕ (`/dashboard/settings` → Quota Store), ಅಥವಾ env vars ಮೂಲಕ:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

env ಗಿಂತ DB ಸೆಟ್ಟಿಂಗ್ಗೆ ಆದ್ಯತೆ ಇದೆ. `driver=redis` ಆಗಿದ್ದರೂ URL ಇಲ್ಲದಿದ್ದರೆ ಅಥವಾ
`ioredis` ಇನ್ಸ್ಟಾಲ್ ಆಗಿರದಿದ್ದರೆ, ಫ್ಯಾಕ್ಟರಿಯು SQLite ಗೆ ಹಿಂತಿರುಗಿ ಎಚ್ಚರಿಕೆಯನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ.

ಡ್ರೈವರ್ ಆಯ್ಕೆಯ ಕ್ರಮ:

1. DB ಸೆಟ್ಟಿಂಗ್ `quotaStore.driver`
2. Env `QUOTA_STORE_DRIVER`
3. ಡೀಫಾಲ್ಟ್: `sqlite`

## ಬಹು-ಆಯಾಮ

ಒಂದು ಪೂಲ್ ಅನೇಕ ಆಯಾಮಗಳನ್ನು ಹೊಂದಿರಬಹುದು. ಪ್ರತಿಯೊಂದು ಆಯಾಮವೂ ಸ್ವತಂತ್ರವಾಗಿದೆ:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // ಈ ಆಯಾಮಕ್ಕಾಗಿ ಜಾಗತಿಕ ಪೂಲ್ನ ಗರಿಷ್ಠ ಮಿತಿ
}
```

**ಉದಾಹರಣೆ: Codex ಪ್ಲಾನ್** (5h% + weekly%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

ಅನುಮತಿಸಲ್ಪಡಲು ವಿನಂತಿಯು ಎಲ್ಲಾ ಆಯಾಮಗಳನ್ನೂ ಪೂರೈಸಬೇಕು.

## ಪೈಪ್ಲೈನ್ ಇಂಟಿಗ್ರೇಶನ್

### PRE ಹುಕ್ (`open-sse/handlers/chatCore.ts`)

ದೃಢೀಕರಣ ಮತ್ತು ಪಾಲಿಸಿ ಪರಿಶೀಲನೆಗಳ ನಂತರ, ಅಪ್ಸ್ಟ್ರೀಮ್ ಎಕ್ಸಿಕ್ಯೂಟರ್ಗೆ ಮೊದಲು ರನ್ ಆಗುತ್ತದೆ:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → ಪ್ರತಿ ಆಯಾಮಕ್ಕೆ getQuotaStore().peek()
      → fairShare.decideFairShare()
      → ನಿರ್ಬಂಧಿಸಿದರೆ → 429 ಹಿಂತಿರುಗಿಸಿ (buildErrorBody, ಕಠಿಣ ನಿಯಮ #12)
      → ಅನುಮತಿಸಿದರೆ + ಆದ್ಯತೆ ತಗ್ಗಿಸಿದರೆ → ಅಭ್ಯರ್ಥಿಯಲ್ಲಿ quotaSoftPenalty=true ಹೊಂದಿಸಿ
  → executor.execute()
```

**ವಿಫಲವಾದರೂ-ಅನುಮತಿಸಿ**: `enforceQuotaShare` ದೋಷವನ್ನು ಎಸೆದರೆ, `pino.warn` ಲಾಗ್ನೊಂದಿಗೆ
ವಿನಂತಿಯನ್ನು ಮುಂದುವರಿಯಲು ಅನುಮತಿಸಲಾಗುತ್ತದೆ. ಇದು ಕೋಟಾ-ಎಂಜಿನ್ನ ದೋಷವು ಎಲ್ಲಾ
ಟ್ರಾಫಿಕ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುವುದನ್ನು ತಡೆಯುತ್ತದೆ.

### POST ಹುಕ್ (ಬಳಕೆಯನ್ನು ದಾಖಲಿಸಿ)

ಯಶಸ್ವಿ ಪ್ರತಿಕ್ರಿಯೆಯ ನಂತರ:

```
ಎಕ್ಸಿಕ್ಯೂಟರ್ ಯಶಸ್ಸನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → ಪ್ರತಿ ಆಯಾಮಕ್ಕೆ getQuotaStore().consume()
      → ವಿಫಲವಾದರೂ-ಅನುಮತಿಸಿ: ದೋಷಗಳನ್ನು pino.warn ಆಗಿ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಕ್ಲೈಂಟ್ಗೆ ಎಂದಿಗೂ ಕಳುಹಿಸಲಾಗುವುದಿಲ್ಲ
```

**ವ್ಯತ್ಯಾಸದ ಟಿಪ್ಪಣಿ**: ಪ್ರತಿಕ್ರಿಯೆಯ ನಂತರ `consume` ವಿಫಲವಾದರೆ, ರೋಲಿಂಗ್ ಕೌಂಟರ್ ಕಡಿಮೆ ಎಣಿಕೆ ಮಾಡುತ್ತದೆ.
ಪ್ರೊವೈಡರ್ನಿಂದ ಬರುವ ಸ್ಯಾಚುರೇಶನ್ ಸಿಗ್ನಲ್ (ಉದಾ. `anthropic-ratelimit-unified-5h-utilization`)
ಮುಂದಿನ ವಿನಂತಿಯಲ್ಲಿ ಜಾಗತಿಕ ಅಂದಾಜನ್ನು ಸರಿಪಡಿಸುತ್ತದೆ.

### ಕಾಂಬೊ ಸಾಫ್ಟ್ ಪೆನಾಲ್ಟಿ (`open-sse/services/combo.ts`)

`decision.deprioritize === true` ಆಗಿರುವಾಗ:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // ಡೀಫಾಲ್ಟ್ 0.7
}
```

ಎಲ್ಲಾ ಇತರ ಸ್ಕೋರಿಂಗ್ ಅಂಶಗಳ ನಂತರ ಪೆನಾಲ್ಟಿಯನ್ನು ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ. ಇದು ಕಠಿಣವಾಗಿ ನಿರ್ಬಂಧಿಸದೆ,
ಸ್ಯಾಚುರೇಟ್ ಆದ ಕೀಯನ್ನು ಆಯ್ಕೆ ಮಾಡುವ ಆಟೊ-ಕಾಂಬೊ ಸಂಭವನೀಯತೆಯನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ.

## ಸಮಸ್ಯೆ ಪರಿಹಾರ

### Redis ಸಂರಚಿಸಲಾಗಿದೆ ಆದರೆ ಸಂಪರ್ಕಗೊಳ್ಳುತ್ತಿಲ್ಲ

`ioredis` ಸ್ಥಾಪಿಸಲಾಗಿದೆಯೇ (`npm ls ioredis`) ಮತ್ತು `QUOTA_STORE_REDIS_URL`
ತಲುಪಬಹುದೇ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ. ಸಂಪರ್ಕ ವಿಫಲವಾದಾಗ ಫ್ಯಾಕ್ಟರಿಯು SQLite ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ
(`warn` ನಲ್ಲಿ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ).

### `peek` ಹಳೆಯ ಡೇಟಾವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ / ವೈಫಲ್ಯವಾದರೂ ಅನುಮತಿಸುತ್ತದೆ

`peek` ದೋಷವನ್ನು ಎಸೆದರೆ, `enforceQuotaShare` ಫಲಿತಾಂಶವನ್ನು "ಅನುಮತಿಸಿ" (ವೈಫಲ್ಯವಾದರೂ ಅನುಮತಿಸಿ) ಎಂದು ಪರಿಗಣಿಸುತ್ತದೆ.
ಮೂಲ ಕಾರಣವನ್ನು ಗುರುತಿಸಲು `quota:enforce` ಮತ್ತು `quota:factory` ನಮೂದುಗಳಿಗಾಗಿ
`pino` ಲಾಗ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.

### ಬಳಕೆ ಕೌಂಟರ್ ವ್ಯತ್ಯಾಸ

ನಿಜವಾದ ಪೂರೈಕೆದಾರರ ಬಳಕೆಯು ಕೌಂಟರ್ಗಳಿಗಿಂತ ಭಿನ್ನವಾಗಿದ್ದರೆ, ಅದು ನಿರೀಕ್ಷಿತವಾಗಿದೆ —
2-ಬಕೆಟ್ ಸ್ಲೈಡಿಂಗ್ ವಿಂಡೋ ವಿಂಡೋ ಗಡಿಗಳಲ್ಲಿ ~1% ದೋಷವನ್ನು ಹೊಂದಿರುತ್ತದೆ ಮತ್ತು `consume`
ಪ್ರತಿಕ್ರಿಯೆಯ ನಂತರ ನಿರೀಕ್ಷಿಸದೆ ಕಾರ್ಯಗತಗೊಳ್ಳುತ್ತದೆ. ಸ್ಯಾಚುರೇಶನ್ ಸಂಕೇತವು (`saturationSignals.ts`)
30s TTL ಜೊತೆಗೆ ನಿಜವಾದ ಪೂರೈಕೆದಾರರ ಬಳಕೆಯನ್ನು ಓದುತ್ತದೆ ಮತ್ತು ಅದಕ್ಕೆ ಅನುಗುಣವಾಗಿ `globalUsedPercent`
ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ.

### ಬರ್ನ್ ರೇಟ್ಗಾಗಿ ಪೂಲ್ "ಡೇಟಾ ಇಲ್ಲ" ಎಂದು ತೋರಿಸುತ್ತದೆ

`computeBurnRate` ಗೆ ಕನಿಷ್ಠ 2 ಐತಿಹಾಸಿಕ ಮಾದರಿಗಳು ಅಗತ್ಯವಿವೆ. ಹಿಂದಿನ
`consume` ಕರೆಗಳಿಲ್ಲದ ಹೊಸ ಪೂಲ್ಗಳು `tokensPerSecond: 0` ಮತ್ತು `timeToExhaustionMs: null` ಅನ್ನು ತೋರಿಸುತ್ತವೆ.

## localStorage ನಿಂದ ವಲಸೆ

`/dashboard/costs/quota-share` ಮೊದಲ ಬಾರಿ ಲೋಡ್ ಆದಾಗ, `useLocalStoragePoolMigration` ಹುಕ್ ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ:

1. `localStorage.getItem("omniroute:quota-share:pools")` ಖಾಲಿಯಾಗಿಲ್ಲ.
2. `GET /api/quota/pools` `[]` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ (DB ಖಾಲಿಯಾಗಿದೆ).

ಎರಡೂ ನಿಜವಾಗಿದ್ದರೆ, ಅದು ಪ್ರತಿಯೊಂದು ಹಳೆಯ ಪೂಲ್ ಅನ್ನು ಬ್ಯಾಚ್ನಲ್ಲಿ `POST /api/quota/pools` ಗೆ ಪೋಸ್ಟ್ ಮಾಡುತ್ತದೆ,
ನಂತರ localStorage ಕೀಲಿಯನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ. ಈ ವಲಸೆಯು ಐಡೆಂಪೊಟೆಂಟ್ ಆಗಿದೆ: ಷರತ್ತು 2
ಮರು-ವಲಸೆಯನ್ನು ತಡೆಯುತ್ತದೆ.

## ಆಂತರಿಕ ತಂತ್ರದ ವರ್ಗೀಕರಣ

`quota-share` ಒಂದು **ಆಂತರಿಕ-ಮಾತ್ರದ** ರೂಟಿಂಗ್ ತಂತ್ರವಾಗಿದೆ (`src/shared/constants/routingStrategies.ts` ನಲ್ಲಿರುವ
`INTERNAL_ROUTING_STRATEGY_VALUES`). ಇದನ್ನು ಸಿಸ್ಟಂ ರಚಿಸಿದ `qtSd/` ಪೂಲ್ ಕಾಂಬೊಗಳು ಮಾತ್ರ
ಬಳಸುತ್ತವೆ ಮತ್ತು ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ `ROUTING_STRATEGY_VALUES` ನಿಂದ ಹೊರಗಿಡಲಾಗಿದೆ, ಆದ್ದರಿಂದ ಇದು
UI ಅಥವಾ API ಯಲ್ಲಿ ಬಳಕೆದಾರರು ಆಯ್ಕೆಮಾಡಬಹುದಾದ ಆಯ್ಕೆಯಾಗಿ ಎಂದಿಗೂ ಕಾಣಿಸುವುದಿಲ್ಲ.

## ಪರೀಕ್ಷಾ ವ್ಯಾಪ್ತಿ

quota-share ಎಂಜಿನ್ನೊಂದಿಗೆ ಸ್ವಯಂಚಾಲಿತ ಪರೀಕ್ಷಾ ವ್ಯಾಪ್ತಿಯ ಎರಡು ಪದರಗಳನ್ನು ಒದಗಿಸಲಾಗಿದೆ:

| ಪರೀಕ್ಷಾ ಸಮೂಹ             | ಕಮಾಂಡ್                                                                 | ಇದು ಒಳಗೊಳ್ಳುವ ಅಂಶಗಳು                                                                                                                                                                             |
| :----------------------- | :--------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಯುನಿಟ್ (29 ಪರೀಕ್ಷೆಗಳು)   | `node --import tsx/esm --test tests/unit/quota-share-strategy.test.ts` | DRR ಶೆಡ್ಯೂಲರ್, ಸ್ಯಾಚುರೇಶನ್ ಗೇಟಿಂಗ್, ಕನ್ಕರೆನ್ಸಿ ಮಿತಿಗಳು, fairShare ಗಣಿತ, ಬ್ಯಾಕ್ಲಾಗ್ ಕ್ಯೂಯಿಂಗ್                                                                                                     |
| ಇಂಟಿಗ್ರೇಶನ್ ಮ್ಯಾಟ್ರಿಕ್ಸ್ | `npm run test:combo:matrix`                                            | ನೈಜ ಕಾಂಬೊ ಪೈಪ್ಲೈನ್ ಮೂಲಕ ಎಂಡ್-ಟು-ಎಂಡ್ ರೂಟಿಂಗ್ ನಿರ್ಧಾರ; ಲೈವ್ ಸೀಮ್ಗಳ ಮೂಲಕ DRR ನ್ಯಾಯಸಮ್ಮತತೆ + ಸ್ಯಾಚುರೇಶನ್ ಆದ್ಯತೆ ಇಳಿಕೆ (`registerQuotaFetcher`, `setLKGP`, `__setHeadroomSaturationFetcherForTests`) |

ಇಂಟಿಗ್ರೇಶನ್ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಎಲ್ಲಾ 19 ಸಾರ್ವಜನಿಕ ತಂತ್ರಗಳೊಂದಿಗೆ CI ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ. ಯುನಿಟ್ ಪರೀಕ್ಷಾ ಸಮೂಹವನ್ನು
ಸ್ವತಂತ್ರವಾಗಿ ರನ್ ಮಾಡಬಹುದು.

## DB ಸ್ಕೀಮಾ ಸಾರಾಂಶ

`078`, `079` ಮತ್ತು `085` ವಲಸೆಗಳಿಂದ ಮೂರು ಟೇಬಲ್ಗಳನ್ನು ಸೇರಿಸಲಾಗಿದೆ:

- `quota_pools` + `quota_allocations` — ಪೂಲ್ ವ್ಯಾಖ್ಯಾನಗಳು ಮತ್ತು ಪ್ರತಿ-ಕೀಲಿಯ ಹಂಚಿಕೆಗಳು.
- `quota_consumption` — ಪ್ರತಿ `(apiKeyId, dimensionKey)` ಗಾಗಿ ರೋಲಿಂಗ್ 2-ಬಕೆಟ್ ಕೌಂಟರ್ಗಳು.
- `provider_plans` — ಕೈಯಾರೆ ನಿರ್ದಿಷ್ಟಪಡಿಸಿದ ಪ್ರೊವೈಡರ್ ಪ್ಲಾನ್ ಓವರ್ರೈಡ್ಗಳು (ಪ್ರತಿ connectionId ಗೆ ಡೈಮೆನ್ಶನ್ಗಳ JSON).

ಎಲ್ಲಾ ಟೇಬಲ್ಗಳನ್ನು ಐಡೆಂಪೊಟೆಂಟ್ `CREATE TABLE IF NOT EXISTS` ವಲಸೆಗಳ ಮೂಲಕ ಸೇರಿಸಲಾಗಿದೆ.
