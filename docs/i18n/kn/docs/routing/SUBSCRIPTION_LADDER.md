> ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡು ಬಳಸಬೇಕು: ಕರೆ ಮಾಡುವವರು ಹೆಸರಿನಿಂದ idಯನ್ನು ಕೇಳದ ಹೊರತು ಯಾವುದೂ ಅವುಗಳ ಮೂಲಕ
> route ಆಗುವುದಿಲ್ಲ, ಮತ್ತು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಯಾವುದೇ pool, strategy ಅಥವಾ default ಬದಲಾಗುವುದಿಲ್ಲ.

## ಇದು ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ

OmniRoute ಈಗಾಗಲೇ ವೆಚ್ಚಕ್ಕೆ ಸಂಬಂಧಿಸಿದ ಎರಡು ಪ್ರಶ್ನೆಗಳಿಗೆ ಉತ್ತರಿಸುತ್ತದೆ, ಆದರೆ ಹೆಚ್ಚಿನ operators ಕೇಳುವ ಪ್ರಶ್ನೆ ಅವುಗಳಲ್ಲಿ ಯಾವುದೂ ಅಲ್ಲ.

| ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಕಾರ್ಯವಿಧಾನ                              | ಉತ್ತರಿಸುವ ಪ್ರಶ್ನೆ                              |
| -------------------------------------------------------- | ---------------------------------------------- |
| `hidePaidModels` (`autoCombo/paidModelFilter.ts`)        | "ಈ model ಉಚಿತವೆಂದು catalog ಮಾಡಲಾಗಿದೆಯೇ?"       |
| `freeAccessPolicy: "strict"` (`strictZeroCostFilter.ts`) | "ಈ connection ಎಂದಾದರೂ ನನಗೆ bill ಮಾಡಬಹುದೇ?"     |
| `quotaPreflight` (`combo/quotaExhaustionCutoff.ts`)      | "ಈ connection ತನ್ನ ಮಿತಿಗೆ ಸಮೀಪದಲ್ಲಿದೆಯೇ?"      |
| `budgetCap` / `budgetFallback` (`autoCombo/engine.ts`)   | "ವೆಚ್ಚಕ್ಕೆ ಮಿತಿ ಹಾಕಿ, ಅತಿ ಅಗ್ಗದ ಆಯ್ಕೆಗೆ ಇಳಿಸಿ" |

ಪ್ರತಿಯೊಂದು ಉಚಿತ-ಮಾತ್ರದ ಕಾರ್ಯವಿಧಾನವೂ **ವಿಫಲವಾದಾಗ ಮುಚ್ಚಿಕೊಳ್ಳುತ್ತದೆ** — ಖಾಲಿಯಾದ ಉಚಿತ pool ಎಂದರೆ ಖಾಲಿ pool,
ಪಾವತಿಸಬೇಕಾದ ಆಯ್ಕೆಗೆ ಮೇಲೇರಿಕೆ ಎಂದಿಗೂ ಅಲ್ಲ — ಮತ್ತು ಪಾವತಿ-ಬದಿಯ ಪ್ರತಿಯೊಂದು ಕಾರ್ಯವಿಧಾನವೂ tier ಬಗ್ಗೆ ಅಜ್ಞೇಯವಾಗಿರುತ್ತದೆ. ಯಾವುದೂ ಇದಕ್ಕೆ ಉತ್ತರಿಸುವುದಿಲ್ಲ:

> "ನಾನು ಈಗಾಗಲೇ ಪಾವತಿಸುತ್ತಿರುವ quotaವನ್ನು ಬಳಸಿ. ಅದು ಮುಗಿದಾಗ ನಿಲ್ಲಿಸಿ, ಅಥವಾ ಅತಿ ಅಗ್ಗದ ಪಾವತಿ ಆಯ್ಕೆಗಳ ಮೂಲಕ
> ಒಂದೊಂದೇ ಮೆಟ್ಟಿಲು ಮೇಲೇರಿ — ಮತ್ತು ಅದು reset ಆದ ಕ್ಷಣದಲ್ಲೇ ಹಿಂತಿರುಗಿ."

## Billing ಎನ್ನುವುದು connectionನ ಸಂಗತಿ, modelನ ಸಂಗತಿಯಲ್ಲ

`classifyTier()` (`open-sse/services/tierResolver.ts`) `(provider, model)` ಅನ್ನು key ಆಗಿ ಬಳಸುತ್ತದೆ ಮತ್ತು
catalog pricingನಿಂದ `free | cheap | premium` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. ಆದರೆ requestಗೆ ಹೆಚ್ಚುವರಿ ಹಣ ಖರ್ಚಾಗುತ್ತದೆಯೇ
ಎಂಬುದು **ಯಾವ connection ಅದನ್ನು ಪೂರೈಸುತ್ತದೆ** ಎಂಬುದರ ಮೇಲೆ ಅವಲಂಬಿತವಾಗಿದೆ: ಅದೇ model Claude Code
OAuth connection ಮೂಲಕ planನಲ್ಲಿ ಒಳಗೊಂಡಿರುತ್ತದೆ ಮತ್ತು API-key connection ಮೂಲಕ ಪ್ರತಿ tokenಗೆ bill ಆಗುತ್ತದೆ.

`provider_connections.auth_type` ಎರಡೂ ದಿಕ್ಕಿನಲ್ಲೂ ಸುರಕ್ಷಿತ proxy ಅಲ್ಲ — metered OAuth
connections ಅಸ್ತಿತ್ವದಲ್ಲಿವೆ ಮತ್ತು planನಲ್ಲಿ ಒಳಗೊಂಡಿರುವ API-key connections ಕೂಡ ಅಸ್ತಿತ್ವದಲ್ಲಿವೆ (Copilot seat token,
metered API key ಅಲ್ಲ). ಆದ್ದರಿಂದ billing class ಅನ್ನು ಪ್ರತಿಯೊಂದು providerನ ಪ್ರಕಟಿತ ಷರತ್ತುಗಳ ಆಧಾರದ ಮೇಲೆ ಕೈಯಾರೆ ಹೊಂದಿಸಲಾದ
**ಆಯ್ದ catalog** ಆದ `open-sse/config/connectionBillingCatalog.ts`ನಿಂದ ಪಡೆಯಲಾಗುತ್ತದೆ —
ಇದು ಉಚಿತ modelsಗಾಗಿ `FreeModelBudget.hardStopGuaranteed` ಈಗಾಗಲೇ ಸ್ಥಾಪಿಸಿರುವ ಅದೇ ಮಾದರಿ.

```ts
type ConnectionBillingClass = "subscription" | "metered" | "keyless" | "unknown";
type ConnectionOverageBehavior = "hard-stop" | "meters-to-paid" | "unknown";
```

ಪರಿಹಾರ ಕ್ರಮ (`autoCombo/connectionBilling.ts`): synthetic no-auth sentinel →
`keyless`; provider **ಮತ್ತು** `authType` ಎರಡಕ್ಕೂ ಹೊಂದಿಕೆಯಾಗುವ catalog entry; provider-ವ್ಯಾಪಿ entry;
ಇಲ್ಲದಿದ್ದರೆ `unknown`. **Catalogಗೆ ಸೇರಿಸದಿರುವುದು ಉಚಿತವಲ್ಲ** — `unknown` ಅನ್ನು ಎಲ್ಲೆಡೆಯೂ `metered` ಆಗಿ
ಬಳಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ನಾಳೆ ಸೇರಿಸಲಾದ provider subscription ಮೆಟ್ಟಿಲಿನ ಹೊರಗಿನಿಂದ ಪ್ರಾರಂಭವಾಗುತ್ತದೆ ಮತ್ತು ಅದನ್ನು
ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ catalogಗೆ ಸೇರಿಸಬೇಕಾಗುತ್ತದೆ.

## ಮೆಟ್ಟಿಲು ಮಾದರಿ

ಏರಿಕೆಯ ಕ್ರಮದಲ್ಲಿ ಐದು ಮೆಟ್ಟಿಲುಗಳು. ಅವು ಬೆಲೆಯಲ್ಲಿ ಮಾತ್ರವಲ್ಲದೆ ಇನ್ನೂ ಹೆಚ್ಚಿನ ರೀತಿಯಲ್ಲಿ ಭಿನ್ನವಾಗಿವೆ — ಪ್ರತಿಯೊಂದಕ್ಕೂ ಅದರ
**ಸ್ವಂತ** exhaustion signal ಇದೆ; ಅದಕ್ಕಾಗಿಯೇ ಇದು ಕೇವಲ sort ಅಲ್ಲ.

| #   | ಮೆಟ್ಟಿಲು       | ಸದಸ್ಯತ್ವ                                           | ಖಾಲಿಯಾಗಿದೆ ಎಂದು ಪರಿಗಣಿಸುವ ಸಂದರ್ಭ        |
| --- | -------------- | -------------------------------------------------- | --------------------------------------- |
| 0   | `subscription` | ಆಯ್ದ `billing: "subscription"`                     | quota window cutoffನಲ್ಲಿ/ಅದಕ್ಕಿಂತ ಕೆಳಗೆ |
| 1   | `keyless`      | synthetic no-auth path                             | connection cooldown / breaker           |
| 2   | `free`         | metered connection, `classifyTier() === "free"`    | ಉಚಿತ allowance ಖಾಲಿಯಾದಾಗ                |
| 3   | `cheap`        | metered connection, `classifyTier() === "cheap"`   | ಪ್ರತಿ-ಮೆಟ್ಟಿಲಿನ budget ಬಳಸಲ್ಪಟ್ಟಾಗ      |
| 4   | `premium`      | metered connection, `classifyTier() === "premium"` | ಪ್ರತಿ-ಮೆಟ್ಟಿಲಿನ budget ಬಳಸಲ್ಪಟ್ಟಾಗ      |

ಮೆಟ್ಟಿಲುಗಳು 0-2 **quota** ಆಧಾರದಲ್ಲಿ ಖಾಲಿಯಾಗುತ್ತವೆ; ಅದನ್ನು ವೀಕ್ಷಿಸಬಹುದು ಮತ್ತು ಈಗಾಗಲೇ track ಮಾಡಲಾಗುತ್ತಿದೆ. ಮೆಟ್ಟಿಲುಗಳು 3-4ಕ್ಕೆ
quota ಇಲ್ಲ — ಪಾವತಿಸಿದ connection ಎಂದೆಂದಿಗೂ ಸೇವೆ ನೀಡುತ್ತದೆ — ಆದ್ದರಿಂದ ಅವುಗಳಿಗೆ ಸಮಂಜಸವಾದ ಏಕೈಕ exhaustion signal ಎಂದರೆ
ಪ್ರತಿ-ಮೆಟ್ಟಿಲಿನ **budget**. ಅದು ಇಲ್ಲದೆ, "cheap ಖಾಲಿಯಾದಾಗ ಮೇಲೇರಿ" ಎಂಬುದಕ್ಕೆ ಯಾವುದೇ trigger ಇರುವುದಿಲ್ಲ.

## `auto/subscription` — ಮುಚ್ಚಿದ ಸ್ಥಿತಿಯಲ್ಲಿ ವಿಫಲಗೊಳಿಸಿ

ಪೂಲ್ = ಮೆಟ್ಟಿಲು 0 ಮಾತ್ರ; ಹೆಚ್ಚುವರಿ ಬಳಕೆಯು ದಾಖಲಿತ `hard-stop` ಆಗಿರುವ ಸಂಪರ್ಕಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿದ್ದು, ಪ್ರತಿಯೊಂದು ಸಂಪರ್ಕದಲ್ಲೂ ಸಾಕಷ್ಟು ಕೋಟಾ ಉಳಿದಿದೆ ಎಂಬುದನ್ನು ಲೈವ್ ಆಗಿ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಅಸ್ಪಷ್ಟವಾದ ಎಲ್ಲವನ್ನೂ ಹೊರಗಿಡಲಾಗುತ್ತದೆ: ಕ್ಯೂರೇಟ್ ಮಾಡದ ಪ್ರೊವೈಡರ್, ಪರಿಶೀಲಿಸಲಾಗದ ಕೋಟಾ ರೀಡಿಂಗ್, ಹಳೆಯ ರೀಡಿಂಗ್ ಅಥವಾ ಪಾವತಿಸಬೇಕಾದ ಹೆಚ್ಚುವರಿ ಬಳಕೆ.

ಖಾಲಿ ಪೂಲ್ ಒಂದು ದೋಷವಲ್ಲ, ಅದು **ಉದ್ದೇಶಿತ** ಉತ್ತರ — ಕರೆ ಮಾಡುವವರ ಈಗಾಗಲೇ ಇರುವ ಖಾಲಿ-ಪೂಲ್ ಮಾರ್ಗವು ಅದನ್ನು ಮೌನವಾದ, ಬಿಲ್ ಮಾಡಬಹುದಾದ ಫಾಲ್ಬ್ಯಾಕ್ ಆಗಿಸುವ ಬದಲು ಸ್ಪಷ್ಟ ದೋಷವನ್ನಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ. ಈ id ನೀಡುವ ಸಂಪೂರ್ಣ ಭರವಸೆ ಇದೇ.

`keyless` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಅರ್ಹವೆಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ: ಈ ಗುಂಪೀಕರಣದ ಅರ್ಥ "ನಾನು ಪಾವತಿಸುವ ಪ್ಲಾನ್", ಆದ್ದರಿಂದ ದೃಢೀಕರಣ ಅಗತ್ಯವಿಲ್ಲದ ಬ್ಯಾಕೆಂಡ್ ಇದರಲ್ಲಿ ಸೇರುವುದಿಲ್ಲ. ಅದಕ್ಕಾಗಿ `auto/thrifty` (ಅಥವಾ `auto/best-free`) ಬಳಸಿ.

### ಸಂಪರ್ಕದ ಸುರಕ್ಷತೆ

ಅಭ್ಯರ್ಥಿಯು ಯಾವಾಗಲೂ ಒಂದೇ ಸಂಪರ್ಕಕ್ಕೆ ಬದ್ಧವಾಗಿರುವುದಿಲ್ಲ — ತಾರ್ಕಿಕ ಅಭ್ಯರ್ಥಿಯು `allowedConnectionIds` ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಹೊಂದಿರುತ್ತದೆ ಮತ್ತು ನಿಜವಾಗಿ ಬಳಸುವ ಖಾತೆಯನ್ನು ನಂತರ, ಡಿಸ್ಪ್ಯಾಚ್ ಸಮಯದಲ್ಲಿ, `open-sse/services/combo/autoStrategy.ts` ಆಯ್ಕೆಮಾಡುತ್ತದೆ. ಆದ್ದರಿಂದ ಎರಡೂ ಗುಂಪೀಕರಣಗಳು **ಪ್ರತಿಯೊಂದು ಸಂಪರ್ಕವನ್ನೂ ಪ್ರತ್ಯೇಕವಾಗಿ** ಪರಿಶೀಲಿಸಿ, `allowedConnectionIds` ಅನ್ನು ಉಳಿದಿರುವ ನಿಖರ ಉಪಸಮೂಹಕ್ಕೆ ಮರುಬರೆಯುತ್ತವೆ — ಎಂದಿಗೂ ಪೂರ್ಣ ಮೂಲ ಪಟ್ಟಿಗೆ ಅಲ್ಲ, ಅಥವಾ ಯಾದೃಚ್ಛಿಕವಾಗಿ ಆಯ್ಕೆಮಾಡಿದ ಒಬ್ಬ ಸದಸ್ಯನಿಗೆ ಅಲ್ಲ. `autoStrategy.ts` ಈಗಾಗಲೇ ಆ ಅರೇಯನ್ನು ಕಟ್ಟುನಿಟ್ಟಿನ ಅನುಮತಿ ಪಟ್ಟಿಯಾಗಿ ಜಾರಿಗೊಳಿಸುವುದರಿಂದ, ಅದನ್ನು ಇಲ್ಲಿ ಮರುಬರೆಯುವುದು ವಿನ್ಯಾಸದ ಮೂಲಕವೇ "ಪರಿಶೀಲಿಸಲಾದ" ಮತ್ತು "ನಿಜವಾಗಿ ಬಳಸಲಾದ" ಸೆಟ್ಗಳು ಒಂದೇ ಆಗಿರುವಂತೆ ಮಾಡುತ್ತದೆ. ಇದು [STRICT_ZERO_COST](./STRICT_ZERO_COST.md) ನಲ್ಲಿರುವ ಅದೇ ಅವಿಚಲ ನಿಯಮ ಮತ್ತು ಅದೇ ತಾರ್ಕಿಕತೆ.

## `auto/thrifty` — ಒಂದೊಂದು ಮೆಟ್ಟಿಲಿನಂತೆ ಮೇಲೇರಿಸಿ

ಪೂಲ್ = ಎಲ್ಲಾ ಮೆಟ್ಟಿಲುಗಳು, ಮೆಟ್ಟಿಲಿನ ಸೂಚ್ಯಂಕದ ಪ್ರಕಾರ ಕ್ರಮಗೊಳಿಸಲಾಗಿದ್ದು, ಕೋಟಾ ಮುಗಿದ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಗೇಟ್ ಮೂಲಕ ಹೊರಗಿಡಲಾಗುತ್ತದೆ. ಉಳಿದಿರುವ ಪೂಲ್ನ **ಒಳಗೆ** `auto` ಎಂಜಿನ್ ಇನ್ನೂ ಸ್ಕೋರ್ ಮಾಡುತ್ತದೆ: ಯಾವ ಮೆಟ್ಟಿಲುಗಳು ಪರಿಗಣನೆಯಲ್ಲಿವೆ ಎಂಬುದನ್ನು ಲ್ಯಾಡರ್ ನಿರ್ಧರಿಸುತ್ತದೆ; ಅವುಗಳೊಳಗೆ ಯಾವ ಅಭ್ಯರ್ಥಿ ಗೆಲ್ಲುತ್ತಾನೆ ಎಂಬುದನ್ನು ಸ್ಕೋರಿಂಗ್ ನಿರ್ಧರಿಸುತ್ತದೆ. ಮೆಟ್ಟಿಲಿನೊಳಗಿನ ಕ್ರಮವು ಸ್ಥಿರವಾಗಿರುತ್ತದೆ, ಆದ್ದರಿಂದ ಸ್ಕೋರರ್ನ ಸ್ವಂತ ಶ್ರೇಯಾಂಕವನ್ನು ಈ ಓವರ್ಲೇ ಎಂದಿಗೂ ಮರುಹೊಂದಿಸುವುದಿಲ್ಲ.

ಇದು ಕ್ರಮಗೊಳಿಸುವಿಕೆ + ಗೇಟಿಂಗ್ ಓವರ್ಲೇ ಆಗಿದೆಯೇ ಹೊರತು, ಹೊಸ ಡಿಸ್ಪ್ಯಾಚರ್ **ಅಲ್ಲ**: `combo.ts` ನ ಊಹಾತ್ಮಕ ಲೂಪ್ ಈಗಾಗಲೇ ಗುರಿಗಳನ್ನು ಕ್ರಮವಾಗಿ ಪರಿಶೀಲಿಸಿ, ವಿಫಲವಾದಾಗ ಮುಂದಿನದಕ್ಕೆ ಸಾಗುತ್ತದೆ; ಆದ್ದರಿಂದ ಪ್ರಿಫ್ಲೈಟ್ ಗುರುತಿಸದ ರನ್ಟೈಮ್ ಕೋಟಾ ಮುಗಿದ ಸ್ಥಿತಿಯು ಅದೇ ವಿನಂತಿಯೊಳಗೆ ಮುಂದಿನ ಮೆಟ್ಟಿಲಿಗೆ ಇನ್ನೂ ಏರುತ್ತದೆ.

`auto/subscription` ಮುಚ್ಚಿದ ಸ್ಥಿತಿಯಲ್ಲಿ ವಿಫಲವಾದರೆ, `auto/thrifty` **ತೆರೆದ ಸ್ಥಿತಿಯಲ್ಲಿ** ವಿಫಲವಾಗುತ್ತದೆ: ಬಳಸಬಹುದಾದ ಕೋಟಾ ರೀಡಿಂಗ್ ಇಲ್ಲದಿದ್ದರೂ, ಪ್ಲಾನ್ನಲ್ಲಿ ಒಳಗೊಂಡಿರುವ ಸಂಪರ್ಕವನ್ನು ಮೊದಲು ಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ. ಅದನ್ನು ಪ್ರಯತ್ನಿಸಲು ಯಾವುದೇ ವೆಚ್ಚವಿಲ್ಲ; ಅದರ ಕೋಟಾ ಮುಗಿದಿದೆ ಎಂದು ಕಂಡುಬಂದರೆ, ಫಾಲ್-ಥ್ರೂ ಹೇಗಾದರೂ ಮುಂದಿನ ಮೆಟ್ಟಿಲನ್ನು ತಲುಪುತ್ತದೆ — ಆದರೆ ಅದನ್ನು ಪ್ರಯತ್ನಿಸಲು ನಿರಾಕರಿಸಿದರೆ, ಟೆಲಿಮೆಟ್ರಿ ಇಲ್ಲದಾಗ ವಿನಂತಿಯನ್ನು ಪಾವತಿಸಬೇಕಾದ ಮೆಟ್ಟಿಲಿಗೆ ಕಳುಹಿಸಲಾಗುತ್ತದೆ; ಈ ಗುಂಪೀಕರಣವು ತಪ್ಪಿಸಲು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ ಫಲಿತಾಂಶವೇ ಅದು.

## ರೀಸೆಟ್ ನಂತರ ಪ್ಲಾನ್ಗೆ ಮರಳುವುದು

ರೂಟಿಂಗ್ ಮೆಟ್ಟಿಲು 0 ಗೆ ಮರಳುವ ಮೊದಲು ಪರಸ್ಪರ ಸ್ವತಂತ್ರವಾದ ಮೂರು ಸಂಗತಿಗಳು ಅವಧಿ ಮುಗಿಸಬೇಕು. ಅವುಗಳಲ್ಲಿ ಒಂದನ್ನು ಮಾತ್ರ ಸರಿಪಡಿಸಿದರೆ, ಪ್ಲಾನ್ ಮರುಪೂರಣಗೊಂಡ ಬಹಳ ಸಮಯದ ನಂತರವೂ ಲ್ಯಾಡರ್ ಪಾವತಿಸಬೇಕಾದ ಮೆಟ್ಟಿಲುಗಳಲ್ಲೇ ಸಿಲುಕಿರುತ್ತದೆ.

1. **ಕೋಟಾ-ಸ್ಥಿತಿಯ ಕ್ಯಾಶ್** — `freeAccessQuota.ts` ಪ್ರತಿ `(provider, connection)` ಗೆ 180s TTL ಜೊತೆಗೆ ಕ್ಯಾಶ್ ಮಾಡುತ್ತದೆ. ತನ್ನದೇ `resetAt` ಈಗಾಗಲೇ ಕಳೆದಿರುವ ಕ್ಯಾಶ್ ನಮೂದು, ಇನ್ನು ಅಸ್ತಿತ್ವದಲ್ಲಿರದ ವಿಂಡೋವನ್ನು ವಿವರಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಅದರ ವಯಸ್ಸನ್ನು **ಲೆಕ್ಕಿಸದೆ** ಈಗ ಅದನ್ನು ಹಳೆಯದಾಗಿ ಪರಿಗಣಿಸಿ ರಿಫ್ರೆಶ್ ಮಾಡಲು ಒತ್ತಾಯಿಸಲಾಗುತ್ತದೆ. ಇದಿಲ್ಲದಿದ್ದರೆ, ಮಧ್ಯರಾತ್ರಿಯಲ್ಲಿ ಮರುಪೂರಣಗೊಂಡ ಪ್ಲಾನ್ TTL ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ಕೋಟಾ ಮುಗಿದಿದೆ ಎಂದೇ ತೋರಿಸುತ್ತಿರುತ್ತದೆ.
2. **ಲ್ಯಾಡರ್ನ ಸ್ವಂತ ಸ್ಥಿತಿ** — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ಅಂತಹ ಯಾವುದೇ ಸ್ಥಿತಿ ಇಲ್ಲ. ಪ್ರತಿ ಪೂಲ್ ನಿರ್ಮಾಣದಲ್ಲೂ ಲೈವ್ ಕೋಟಾ ಸ್ಥಿತಿಯಿಂದ ಮೆಟ್ಟಿಲಿನ ಅರ್ಹತೆಯನ್ನು ಮರುಲೆಕ್ಕಿಸಲಾಗುತ್ತದೆ; ರೀಸೆಟ್ಗಿಂತಲೂ ಹೆಚ್ಚು ಕಾಲ ಉಳಿದು ರೂಟಿಂಗ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಬಹುದಾದ, ಪರ್ಸಿಸ್ಟ್ ಮಾಡಲಾದ "ಪ್ರಸ್ತುತ ಮೆಟ್ಟಿಲು 3 ರಲ್ಲಿದೆ" ಎಂಬ ಯಾವುದೇ ದಾಖಲೆ ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲ.
3. **ಸಂಪರ್ಕದ ಕೂಲ್ಡೌನ್** — ಕೋಟಾ ಮುಗಿಯಲು ಕಾರಣವಾದ 429, ಘಾತೀಯ ಬ್ಯಾಕ್ಆಫ್ನಿಂದ `rateLimitedUntil` ಅನ್ನು ಹೊಂದಿಸುತ್ತದೆ; ಪ್ಲಾನ್ ಸಂಪರ್ಕದ ಸಂದರ್ಭದಲ್ಲಿ ಇದು ನಿಜವಾದ ರೀಸೆಟ್ ಸಮಯವನ್ನು ಮೀರಬಹುದು. `clampCooldownToReset()` (`subscriptionLadder.ts`) ಕೂಲ್ಡೌನ್ ಅನ್ನು ಅಪ್ಸ್ಟ್ರೀಮ್ನ ಸ್ವಂತ ರೀಸೆಟ್ ಕ್ಷಣಕ್ಕೆ ಸೀಮಿತಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಅದನ್ನು ಎಂದಿಗೂ ವಿಸ್ತರಿಸಲಾರದು. **ಇದನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ ಪರೀಕ್ಷಿಸಲಾಗಿದೆ, ಆದರೆ ಇನ್ನೂ ವೈರ್ ಮಾಡಿಲ್ಲ**: ಯಾವುದೇ ಕೂಲ್ಡೌನ್ ಬರೆಯುವ _ಮೊದಲು_ `src/sse/services/auth.ts` ನಲ್ಲಿ ಕೋಟಾ ಕ್ಯಾಶ್ ಅಮಾನ್ಯಗೊಳಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಆ ಫಂಕ್ಷನ್ನಲ್ಲಿ `resetAt` ಅನ್ನು ಅದಕ್ಕೂ ಮೊದಲೇ ಸೆರೆಹಿಡಿಯಬೇಕು — ಇದು ಸ್ಥಿತಿಸ್ಥಾಪಕತೆಯ ಹಾಟ್ ಪಾತ್ಗೆ ಮಾಡುವ ಬದಲಾವಣೆಯಾಗಿದ್ದು, ತನ್ನದೇ ಪರಿಶೀಲಿತ PR ನಲ್ಲಿ ಸೇರಬೇಕು. ಅಲ್ಲಿಯವರೆಗೆ, ಮರುಪ್ರವೇಶವು ಸಂಪರ್ಕದ ಕೂಲ್ಡೌನ್ ಮುಗಿಯುವವರೆಗೆ ಕಾಯುತ್ತದೆ (ಪ್ರೊವೈಡರ್ ಕಳುಹಿಸಿದಾಗ ಇದು ಈಗಾಗಲೇ ಅಪ್ಸ್ಟ್ರೀಮ್ `Retry-After` ಸುಳಿವುಗಳಿಗೆ ಆದ್ಯತೆ ನೀಡುತ್ತದೆ).

### ಏರಿಳಿತ ತಡೆ

ಈಗಷ್ಟೇ ರೀಸೆಟ್ ಆದ ಮೆಟ್ಟಿಲನ್ನು `reentryMinRemainingPercent` ಗಿಂತ ಹೆಚ್ಚಿದ್ದಾಗ ಮಾತ್ರ ಮರುಸೇರಿಸಲಾಗುತ್ತದೆ (ಡಿಫಾಲ್ಟ್ 5); ಆದರೆ ಈಗಾಗಲೇ ಬಳಕೆಯಲ್ಲಿರುವ ಸಂಪರ್ಕವು `exitCutoffPercent` ಗಿಂತ ಹೆಚ್ಚಾಗಿ ಉಳಿದಿದ್ದರೆ ಸಾಕು (ಡಿಫಾಲ್ಟ್ 2, ಇದು `quotaPreflight.defaultThresholdPercent` ಗೆ ಹೊಂದಿಕೆಯಾಗುತ್ತದೆ). ಇವುಗಳ ನಡುವಿನ ಅಂತರವೇ ಹಿಸ್ಟೆರಿಸಿಸ್ ಬ್ಯಾಂಡ್ — ಇದಿಲ್ಲದಿದ್ದರೆ, ಕಟ್ಆಫ್ ಸಮೀಪ ತೂಗಾಡುವ ಸಂಪರ್ಕವು ಸತತ ವಿನಂತಿಗಳಲ್ಲಿ ಮೆಟ್ಟಿಲುಗಳ ನಡುವೆ ಆಂದೋಲನಗೊಳ್ಳುತ್ತದೆ.

## ಸಂರಚನೆ

ಟ್ಯೂನಿಂಗ್ಗಾಗಿ ಮಾತ್ರ. ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿಯೇ `enabled` ಫ್ಲ್ಯಾಗ್ **ಇಲ್ಲ**: ಇವುಗಳನ್ನು ಆಫ್ ಮಾಡಬಲ್ಲ ಟಾಗಲ್,
ಅದರ ಹೆಸರಿಗೆ ವಿರುದ್ಧವಾಗಿ, ಪಾವತಿಸಿದ ಮಾದರಿಗಳನ್ನೂ ಒಳಗೊಂಡಂತೆ ಪೂರ್ಣ ಪೂಲ್ ಅನ್ನು `auto/subscription`
ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಒದಗಿಸುವಂತೆ ಮಾಡುತ್ತದೆ.

```jsonc
{
  "subscriptionLadder": {
    "exitCutoffPercent": 2,
    "reentryMinRemainingPercent": 5,
    "rungBudgetUsd": { "cheap": 5.0, "premium": 0 }, // 0 ಒಂದು ಹಂತವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ
  },
}
```

ವೆಚ್ಚ ರಿಸಾಲ್ವರ್ ಅನ್ನು ಸಂಪರ್ಕಿಸುವವರೆಗೆ ಬಜೆಟ್ ಗೇಟಿಂಗ್ ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ: ಲೆಕ್ಕಪತ್ರ ಲಭ್ಯವಿಲ್ಲದಿದ್ದಾಗ ಪಾವತಿಸಿದ
ಹಂತವನ್ನು ಕ್ರಮಗೊಳಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಅದಕ್ಕೆ ಎಂದಿಗೂ ಗೇಟ್ ಅನ್ವಯಿಸುವುದಿಲ್ಲ. v3.8.51 ಪ್ರಕಾರ `rungBudgetUsd` ಸೆಟ್ಟಿಂಗ್ ಅನ್ನು
ಸ್ಕೀಮಾ ಸ್ವೀಕರಿಸುತ್ತದೆ, ಆದರೆ ಇನ್ನೂ ಜಾರಿಗೊಳಿಸಿಲ್ಲ — ಇದನ್ನು ಸಕ್ರಿಯ ವೆಚ್ಚ ಮಿತಿಯಂತೆ ಅಲ್ಲದೆ, ಕಾಯ್ದಿರಿಸಿದ ಸಂರಚನೆಯಂತೆ ಪರಿಗಣಿಸಿ. ಹಂತಗಳ ಕ್ರಮಗೊಳಿಸುವಿಕೆ, ಕೋಟಾ-ಆಧಾರಿತ ಖಾಲಿಯಾಗುವಿಕೆ ಮತ್ತು ರೀಸೆಟ್ ನಂತರದ ಮರು-ಪ್ರವೇಶ ಇವೆಲ್ಲವೂ
ಅದಿಲ್ಲದೆಯೇ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ.

## ಸಂಯೋಜನೆ

`subscription` ಮತ್ತು `thrifty` ಇವು `AutoTier` ಮೌಲ್ಯಗಳಾಗಿರುವುದರಿಂದ, ಅವು ಪ್ರತಿಯೊಂದು ವರ್ಗದೊಂದಿಗೆ ಸಂಯೋಜಿಸುತ್ತವೆ:
`auto/coding:thrifty`, `auto/reasoning:subscription`, ಇತ್ಯಾದಿ. ಈ ಎರಡು ಫ್ಲ್ಯಾಟ್ ಐಡಿಗಳನ್ನು
(`auto/subscription`, `auto/thrifty`) `/v1/models` ಮತ್ತು ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ.

ಎರಡೂ ಐಡಿಗಳು ಪಾವತಿಸಿದ ಟಿಯರ್ಗೆ ಸೇರಿಲ್ಲ, ಆದ್ದರಿಂದ `isPaidTierAutoId()` ಎರಡಕ್ಕೂ `false` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಮತ್ತು
`auto/subscription` ಎಂಬುದು `hidePaidModels` ಅನ್ವಯಿಸಿದ ನಂತರವೂ ಉಳಿಯುತ್ತದೆ.
