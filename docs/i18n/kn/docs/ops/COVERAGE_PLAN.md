## ನಿಯಮಗಳು

- ವ್ಯಾಪ್ತಿ ಗುರಿಗಳು ಮೂಲ ಫೈಲ್ಗಳಿಗೆ ಅನ್ವಯಿಸುತ್ತವೆ, `tests/**` ಗೆ ಅಲ್ಲ.
- `open-sse/**` ಉತ್ಪನ್ನದ ಭಾಗವಾಗಿದೆ ಮತ್ತು ವ್ಯಾಪ್ತಿಯಲ್ಲಿ ಉಳಿಯಲೇಬೇಕು.
- ಹೊಸ ಕೋಡ್, ಬದಲಾವಣೆ ಮಾಡಿದ ಪ್ರದೇಶಗಳಲ್ಲಿನ ವ್ಯಾಪ್ತಿಯನ್ನು ಕಡಿಮೆ ಮಾಡಬಾರದು.
- ಅನುಷ್ಠಾನದ ವಿವರಗಳಿಗಿಂತ ವರ್ತನೆ ಮತ್ತು ಶಾಖೆಯ ಫಲಿತಾಂಶಗಳನ್ನು ಪರೀಕ್ಷಿಸುವುದಕ್ಕೆ ಆದ್ಯತೆ ನೀಡಿ.
- `src/lib/db/**` ಗಾಗಿ ವ್ಯಾಪಕ ಮಾಕ್ಗಳಿಗಿಂತ ತಾತ್ಕಾಲಿಕ SQLite ಡೇಟಾಬೇಸ್ಗಳು ಮತ್ತು ಸಣ್ಣ ಫಿಕ್ಸ್ಚರ್ಗಳಿಗೆ ಆದ್ಯತೆ ನೀಡಿ.

## ಪ್ರಸ್ತುತ ಕಮಾಂಡ್ಗಳ ಸಮೂಹ

- `npm run test:coverage`
  - ಘಟಕ ಪರೀಕ್ಷಾ ಸಂಕಲನಕ್ಕಾಗಿ ಮುಖ್ಯ ಮೂಲ ವ್ಯಾಪ್ತಿ ದ್ವಾರ
  - `text-summary`, `html`, `json-summary`, ಮತ್ತು `lcov` ಅನ್ನು ರಚಿಸುತ್ತದೆ
- `npm run coverage:report`
  - ಇತ್ತೀಚಿನ ರನ್ನಿಂದ ಫೈಲ್-ಪ್ರತಿ-ಫೈಲ್ ವಿವರವಾದ ವರದಿ
- `npm run test:coverage:legacy`
  - ಐತಿಹಾಸಿಕ ಹೋಲಿಕೆಗಾಗಿ ಮಾತ್ರ

## ರ್ಯಾಚೆಟ್ ನೀತಿ

ಯೋಜನೆಯು ಮುಂದಿನ ಮೈಲಿಗಲ್ಲನ್ನು ಸಾಕಷ್ಟು ಅಂತರದೊಂದಿಗೆ ನಿಜವಾಗಿಯೂ ಮೀರಿದ ನಂತರವೇ `npm run test:coverage` ಮಿತಿಗಳನ್ನು ನವೀಕರಿಸಿ.

**ಪ್ರಸ್ತುತ ಗೇಟ್:** `npm run test:coverage` **60 ಸ್ಟೇಟ್ಮೆಂಟ್ಗಳು / 60 ಸಾಲುಗಳು / 60 ಫಂಕ್ಷನ್ಗಳು / 60 ಬ್ರಾಂಚ್ಗಳು** ಎಂಬ ಮಿತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ (Quality-Gates Fase 6A.1 ನಲ್ಲಿ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಮರುಆಧಾರಗೊಳಿಸಲಾಯಿತು — ಹಿಂದಿನ 82.58% ಮೂಲಮಟ್ಟವು ಟೆಸ್ಟ್ ಫೈಲ್ಗಳನ್ನು ಎಣಿಸಿದ್ದರಿಂದ ಮತ್ತು `open-sse` ಅನ್ನು ಹೊರತುಪಡಿಸಿದ್ದರಿಂದ ಹೆಚ್ಚಾಗಿ ತೋರಿಸಲ್ಪಟ್ಟಿತ್ತು). ಐತಿಹಾಸಿಕ ಹೋಲಿಕೆಗಾಗಿ `test:coverage:legacy` ಕಮಾಂಡ್ ಹಳೆಯ 50/50/50 ಮೆಟ್ರಿಕ್ ಅನ್ನು ಉಳಿಸಿಕೊಂಡಿದೆ.

ಇತ್ತೀಚಿನ ವರದಿಯ ಮೇಲೆ ತಾತ್ಕಾಲಿಕ ಮಿತಿ ಪರಿಶೀಲನೆಗಳನ್ನು ನಡೆಸಲು ಇದನ್ನು ಬಳಸಿ:

## ತಿಳಿದಿರುವ ಕೊರತೆ

ಪ್ರಸ್ತುತ ಕವರೇಜ್ ಕಮಾಂಡ್ ಮುಖ್ಯ Node ಯೂನಿಟ್ ಸೂಟ್ ಅನ್ನು ಅಳೆಯುತ್ತದೆ ಮತ್ತು ಅದರಿಂದ ತಲುಪಲಾದ ಸೋರ್ಸ್ಗಳನ್ನು, `open-sse` ಸೇರಿದಂತೆ, ಒಳಗೊಂಡಿರುತ್ತದೆ. ಇದು ಇನ್ನೂ Vitest ಕವರೇಜ್ ಅನ್ನು ಒಂದೇ ಏಕೀಕೃತ ವರದಿಯಲ್ಲಿ ವಿಲೀನಗೊಳಿಸುವುದಿಲ್ಲ. ಆ ವಿಲೀನವನ್ನು ನಂತರ ಮಾಡುವುದು ಉಪಯುಕ್ತವಾಗಿದೆ, ಆದರೆ 60% -> 80% ಏರಿಕೆಯನ್ನು ಪ್ರಾರಂಭಿಸಲು ಅದು ಅಡ್ಡಿಯಾಗುವುದಿಲ್ಲ.
