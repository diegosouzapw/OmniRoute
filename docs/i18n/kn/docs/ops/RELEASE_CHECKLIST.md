## npm Trusted Publishing (v3.8.51 ರಿಂದ ಡೀಫಾಲ್ಟ್) — ವಿನಂತಿಯ ಮೇರೆಗೆ ಹಂತಗೊಳಿಸುವಿಕೆ, ಪರ್ಯಾಯವಾಗಿ ನೇರ ಪ್ರಕಟಣೆ

`npm-publish.yml` ಡೀಫಾಲ್ಟ್ ಆಗಿ **npm Trusted Publishing (OIDC)** ಮೂಲಕ ಪ್ರಕಟಿಸುತ್ತದೆ:
`stage-npm` ಜಾಬ್ (github-hosted) ಆ ಚಾಲನೆಗಾಗಿ GitHub ನ id-token ಅನ್ನು ಅಲ್ಪಾವಧಿಯ npm
ರುಜುವಾತಿಗೆ ವಿನಿಮಯ ಮಾಡುತ್ತದೆ — ರೆಪೊಸಿಟರಿ ಸೀಕ್ರೆಟ್ಗಳಲ್ಲಿ ದೀರ್ಘಾವಧಿಯ npm ಟೋಕನ್ ಇಲ್ಲ, 2FA ಪ್ರಾಂಪ್ಟ್ ಇಲ್ಲ, provenance ಲಗತ್ತಿಸಲಾಗುತ್ತದೆ.
2FA ಅನ್ನು ಬಿಟ್ಟುಬಿಡುವ ಟೋಕನ್ಗಳನ್ನು ನಿವೃತ್ತಿಗೊಳಿಸಲಾಗುತ್ತಿರುವುದರಿಂದ, npm ಈಗ ಅನುಮೋದಿಸುವ ಬೈಪಾಸ್ ಇದೇ;
WS1.3 ಖಾತರಿಯನ್ನು ಉಳಿಸಿಕೊಂಡೇ (ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಒಂದರಿಂದಲೇ ಪ್ರಕಟಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ — ಇಲ್ಲಿ ಟೋಕನ್ ಇಲ್ಲ)
v3.8.48 ವರೆಗೆ ಯೋಜನೆಯಲ್ಲಿದ್ದ ಸಂಪೂರ್ಣ ಸ್ವಯಂಚಾಲಿತ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಇದು ಮರುಸ್ಥಾಪಿಸುತ್ತದೆ.

**ಒಂದು ಬಾರಿಯ ಸೆಟಪ್ (ಮಾಲೀಕರು):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: none). ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವವರೆಗೆ, ಸ್ವಯಂಚಾಲಿತ ಹಂತವು `ENEEDAUTH` ಜೊತೆಗೆ ವಿಫಲವಾಗುತ್ತದೆ:
`publish_mode=staged` (ಕೆಳಗೆ) ಅಥವಾ `direct` ಬಳಸಿ ಮರು-ಡಿಸ್ಪ್ಯಾಚ್ ಮಾಡಿ.

### ಹಂತಗೊಳಿಸಿದ ಪ್ರಕಟಣೆ (ವಿನಂತಿಯ ಮೇರೆಗೆ — `publish_mode=staged`)

npm-publish ವರ್ಕ್ಫ್ಲೋ ಇನ್ನು ಮುಂದೆ ನೇರವಾಗಿ ಪ್ರಕಟಿಸುವುದಿಲ್ಲ: ಅದು ಪ್ಯಾಕ್ ಮಾಡಿದ tarball ಅನ್ನು
ಬೂಟ್ ಮಾಡುತ್ತದೆ (`check:pack-boot`), ನಂತರ `npm stage publish` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ — ಅದೇ ನಿಖರ ಬೈಟ್ಗಳನ್ನು
ರೆಜಿಸ್ಟ್ರಿಯಲ್ಲಿ ಇರಿಸಲಾಗುತ್ತದೆ, ಮಾಲೀಕರು ಅನುಮೋದಿಸುವವರೆಗೆ ಅವುಗಳನ್ನು **ಇನ್ಸ್ಟಾಲ್ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ**.
ಮಾನವ 2FA ಗೇಟ್ ಈಗ ಪುರಾವೆಗೆ ಮೊದಲಲ್ಲ, ಅದರ ನಂತರ ಬರುತ್ತದೆ.

**ವರ್ಕ್ಫ್ಲೋ ಹಸಿರು ಸ್ಥಿತಿಗೆ ಬಂದ ನಂತರ ಮಾಲೀಕರ ಪ್ರಕ್ರಿಯೆ:**

1. `npm stage list omniroute` — stage id ಅನ್ನು ಹುಡುಕಿ (ಇದು ವರ್ಕ್ಫ್ಲೋ ಸಾರಾಂಶದಲ್ಲಿಯೂ ಮುದ್ರಿತವಾಗಿರುತ್ತದೆ).
2. ಹಂತಗೊಳಿಸಿದ ಬೈಟ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ (ಶಿಫಾರಸು ಮಾಡಲಾಗಿದೆ): `npm stage download <id>`, ನಂತರ ಡೌನ್ಲೋಡ್ ಮಾಡಿದ
   tarball ಅನ್ನು ತಾತ್ಕಾಲಿಕ prefix ಗೆ ಇನ್ಸ್ಟಾಲ್ ಮಾಡಿ ಮತ್ತು ಅದನ್ನು ಬೂಟ್ ಮಾಡಿ (`npm run check:pack-boot` CI ಯಲ್ಲಿ
   ಅದೇ pack→install→boot ತೀರ್ಪನ್ನು ಸ್ವಯಂಚಾಲಿತಗೊಳಿಸುತ್ತದೆ).
3. `npm stage approve <id>` — 2FA ಪ್ರಾಂಪ್ಟ್ವೇ ಪ್ರಕಟಣೆ. `npm stage reject <id>` ಅದನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ.
4. ಪ್ರಕಟಣೆಯ ನಂತರದ ಸುರಕ್ಷತಾ ಜಾಲ: ಪ್ರಕಟಣೆಯ ನಂತರದ ಪರಿಶೀಲಕವು (v3.8.49 ಯೋಜನೆಯ WS1.4) ಸ್ವಚ್ಛ
   ಕಂಟೇನರ್ನಲ್ಲಿ ಸಾರ್ವಜನಿಕ ರೆಜಿಸ್ಟ್ರಿಯಿಂದ ಪ್ರಕಟಿತ ಆವೃತ್ತಿಯನ್ನು ಇನ್ಸ್ಟಾಲ್ ಮಾಡಿ ಬೂಟ್ ಮಾಡುತ್ತದೆ.

**ತುರ್ತು ಪರ್ಯಾಯ:** `publish_mode=direct` ಜೊತೆಗೆ `workflow_dispatch` ಹಳೆಯ ತಕ್ಷಣದ
`npm publish` ಅನ್ನು ಮರುಸ್ಥಾಪಿಸುತ್ತದೆ (ಹಂತಗೊಳಿಸುವಿಕೆಯೇ ತಪ್ಪಾಗಿ ವರ್ತಿಸಿದರೆ ಮಾತ್ರ ಬಳಸಿ; ಕಾರಣವನ್ನು ದಾಖಲಿಸಿ).

**ಒಂದು ಬಾರಿಯ ಗಟ್ಟಿಗೊಳಿಸುವಿಕೆ (ಮಾಲೀಕರು, npmjs.com):** `omniroute` ಗಾಗಿ Trusted Publisher ಅನ್ನು
stage-only ಮೋಡ್ನಲ್ಲಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಿ; ಇದರಿಂದ ಸೋರಿಕೆಯಾದ ದೀರ್ಘಾವಧಿಯ ಟೋಕನ್ ಯಾವುದೇ ಸ್ಥಳದಿಂದಲೂ ನೇರವಾಗಿ
`npm publish` ಮಾಡಲು ಸಾಧ್ಯವಾಗುವುದಿಲ್ಲ — CI ಕೇವಲ ಹಂತಗೊಳಿಸಬಹುದು; ಮಾಲೀಕರ 2FA ಮಾತ್ರ ಬಿಡುಗಡೆ ಮಾಡಬಹುದು.

**ದೋಷಪೂರಿತ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಕಾರ್ಯಸೂಚಿ (ಬದಲಾಗಿಲ್ಲ):** ಡೀಫಾಲ್ಟ್ ತಕ್ಷಣದ ಕ್ರಮವಾಗಿ
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` ಬಳಸಿ (ನಿಮಿಷಗಳು, ಹಿಂತಿರುಗಿಸಬಹುದು);
`npm unpublish` ಅನ್ನು 72h/ಅವಲಂಬಿತರಿಲ್ಲದ ವಿಂಡೋದೊಳಗೆ ಮಾತ್ರ ಬಳಸಿ ಮತ್ತು ಎಂದಿಗೂ ಮೊದಲ ಕ್ರಮವಾಗಿ ಬಳಸಬೇಡಿ.
Docker: ಆವೃತ್ತಿ ಟ್ಯಾಗ್ ಅನ್ನು ಎಂದಿಗೂ ಮರುಬರೆಯಬೇಡಿ — rollback ಎಂದರೆ `latest` ಅನ್ನು ಕೊನೆಯ ಉತ್ತಮ digest ಗೆ ಮರುನಿರ್ದೇಶಿಸುವುದು.

**Docker Hub `latest` (ಪ್ರತಿ ಸ್ಥಿರ SemVer ಪ್ರಕಟಣೆಯಲ್ಲೂ ಅಗತ್ಯ):**
`docker-publish` ವರ್ಕ್ಫ್ಲೋ **ಎರಡಕ್ಕೂ** ಟ್ಯಾಗ್ ಮಾಡಬೇಕು: `X.Y.Z` ಮತ್ತು,
ಇದು ಅತ್ಯುನ್ನತ ಸ್ಥಿರ SemVer ಎಂದು `should-promote-latest.sh` ಒಪ್ಪಿದಾಗ, `:latest` —
ಎರಡಕ್ಕೂ **ಒಂದೇ digest** ಇರಬೇಕು. ಜಾಬ್ ನಂತರ: Hub ನ `latest` digest ಹೊಸ
SemVer digest ಗೆ ಸಮನಾಗಿರಬೇಕು ಮತ್ತು `last_updated` ಮುಂದಕ್ಕೆ ಸರಿದಿರಬೇಕು. git ನಲ್ಲಿ ಮಾತ್ರ ಇರುವ
ಸರಿಪಡಿಕೆಗಳ ಕುರಿತು ಬಿಡುಗಡೆ ಟಿಪ್ಪಣಿಗಳು ಹೇಳುತ್ತಿರುವಾಗ `:latest` ಅನ್ನು ಹಳೆಯ ಬಿಲ್ಡ್ನಲ್ಲೇ ಬಿಡಬೇಡಿ.
Compose ಕ್ವಿಕ್ಸ್ಟಾರ್ಟ್ಗಳು `:latest` ಬಳಸುತ್ತವೆ; GitOps `X.Y.Z` ಅನ್ನು ಪಿನ್ ಮಾಡುವುದನ್ನು ಮುಂದುವರಿಸಬೇಕು.
[Docker ಬಿಡುಗಡೆ ಚಾನೆಲ್ಗಳು](../guides/DOCKER_GUIDE.md#release-channels) ಮತ್ತು #10317 ನೋಡಿ.

## ಹಾಟ್ಫಿಕ್ಸ್ ಫಾಸ್ಟ್-ಲೇನ್ (ಲೇಬಲ್ `hotfix`)

`hotfix` ಲೇಬಲ್ ಹೊಂದಿರುವ PR ಭಾರವಾದ CI ಮ್ಯಾಟ್ರಿಕ್ಸ್ನ್ನು (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) ಬಿಟ್ಟು, ವೇಗವಾದ ಮತ್ತು ಹೆಚ್ಚಿನ-ಸಿಗ್ನಲ್ ಗೇಟ್ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ: build,
unit shards, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
ಮತ್ತು tarball boot-smoke (`check:pack-boot`). ಗುರಿ: ~33min ಬದಲಿಗೆ ≤15min ಒಳಗೆ green.

**ಪ್ರವೇಶ ನೀತಿ — ಎಲ್ಲಾ ನಾಲ್ಕೂ ಕಡ್ಡಾಯ (Chromium/VS Code/Node ತುರ್ತು ಲೇನ್ಗಳ ಮಾದರಿಯಲ್ಲಿ):**

1. **ತೀವ್ರತೆ**: production ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿಲ್ಲ — ಪ್ರಕಟಿತ artifact boot ಸಮಯದಲ್ಲಿ crash ಆಗುತ್ತದೆ / ಒಂದು
   security fix / releaseನ ಪ್ರತಿಯೊಬ್ಬ ಬಳಕೆದಾರರೂ ಪರಿಣಾಮಕ್ಕೆ ಒಳಗಾಗಿದ್ದಾರೆ. "ಪ್ರಮುಖ" ಎಂದರೆ "ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿಲ್ಲ" ಎಂದಲ್ಲ.
2. **ಅಧಿಕಾರ**: repository owner ಮಾತ್ರ `hotfix` ಲೇಬಲ್ ಅನ್ವಯಿಸುತ್ತಾರೆ. ಲೇಬಲ್ವೇ
   ಅನುಮೋದನೆ — campaign PRನಲ್ಲಿ ಎಂದಿಗೂ ಸ್ವಯಂ-ಸೇವೆಯಾಗಿ ಬಳಸಬೇಡಿ.
3. **ಸಾಕ್ಷ್ಯ**: PR body ಹಿಂದಿನ ಸಂಪೂರ್ಣ-green heavy runಗೆ (ಬಿಟ್ಟುಹೋದ jobs ಮರು-ಮೌಲ್ಯೀಕರಿಸುವ suite)
   ಹಾಗೂ fixನ ಸ್ವಂತ ಮೊದಲು-failing-ನಂತರ-passing testಗೆ ಲಿಂಕ್ ಮಾಡುತ್ತದೆ.
4. **ವ್ಯಾಪ್ತಿ**: cherry-pick-only — ಕನಿಷ್ಠ fix ಮಾತ್ರ, ಯಾವುದೇ refactors ಅಥವಾ ride-alongs ಬೇಡ.

ಬಿಟ್ಟುಹೋದ coverage/ratchet ಮೇಲ್ಮೈಯನ್ನು release branchನ ಮುಂದಿನ full run ಮೂಲಕ
ಮರು-ಮೌಲ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ (continuous release-green) — ಈ lane ಕಾಯುವಿಕೆಯನ್ನು ಮಾತ್ರ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ, validation ಅನ್ನು ಎಂದಿಗೂ ಅಲ್ಲ.
Tests-only diffs (`tests/` ಅಡಿಯಲ್ಲಿ ಇರುವ ಎಲ್ಲಾ files, `tests/e2e/` ಅಡಿಯಲ್ಲಿ ಯಾವುದೂ ಇಲ್ಲ) ಯಾವುದೇ label ಇಲ್ಲದೆ
E2E matrix ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತವೆ.

### Build ವಿನ್ಯಾಸ

Repository ಮೂರು ಪ್ರತ್ಯೇಕ output directories ಅನ್ನು ಬಳಸುತ್ತದೆ — ಅವುಗಳನ್ನು ಎಂದಿಗೂ ಗೊಂದಲಗೊಳಿಸಬೇಡಿ:

| Directory | ಉದ್ದೇಶ                                                          | Track ಮಾಡಲಾಗಿದೆಯೇ? |
| --------- | --------------------------------------------------------------- | ------------------ |
| `src/`    | Application source (TypeScript / TSX)                           | ಹೌದು               |
| `.build/` | Build intermediates — `next build` output (`distDir`)           | ಇಲ್ಲ (gitignored)  |
| `dist/`   | ವಿತರಿಸಬಹುದಾದ npm bundle — `assembleStandalone` ಮೂಲಕ ಜೋಡಿಸಲಾಗಿದೆ | ಇಲ್ಲ (gitignored)  |

> **Operator ಟಿಪ್ಪಣಿ:** remote VPS image directory `/usr/lib/node_modules/omniroute/app/` ಆಗಿಯೇ ಉಳಿದಿದೆ.
> **Repository ಒಳಗಿನ** build output ಮಾತ್ರ ಸ್ಥಳಾಂತರಗೊಂಡಿದೆ (`app/` → `dist/`). Deploy skills,
> `dist/` contents ಅನ್ನು remote `app/` dirಗೆ rsync ಮಾಡುತ್ತವೆ — VPS path ಬದಲಾವಣೆಗಳ ಅಗತ್ಯವಿಲ್ಲ.

**Single-build flow:**

```
npm run build:release
  └─ rm -rf .build dist          (ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ)
  └─ next build → .build/next/   (ಮಧ್ಯಂತರಗಳು)
  └─ assembleStandalone          (standalone + static + public + natives ಅನ್ನು dist/ಗೆ ನಕಲಿಸುತ್ತದೆ)
  └─ dist/BUILD_SHA ಬರೆಯುತ್ತದೆ   (HEAD sentinel)
```

Deployಗಾಗಿ `npm run build` ಚಲಾಯಿಸಿ ನಂತರ ಪ್ರತ್ಯೇಕವಾಗಿ `npm run build:cli` ಚಲಾಯಿಸಬೇಡಿ —
ಒಂದೇ commandನಲ್ಲಿ clean rebuild + sentinel ಮಾಡುವ `npm run build:release` ಬಳಸಿ.

## ರೋಲ್ಬ್ಯಾಕ್

ಬಿಡುಗಡೆಯಲ್ಲಿ ಗಂಭೀರ ಸಮಸ್ಯೆಯಿದ್ದರೆ:

1. `gh release edit vX.Y.Z --prerelease` (ಇದನ್ನು ಇತ್ತೀಚಿನ ಬಿಡುಗಡೆ ಅಲ್ಲ ಎಂದು ಗುರುತಿಸುತ್ತದೆ)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (ಬಳಕೆದಾರರು ಇನ್ನೂ ಅಳವಡಿಸಿಕೊಂಡಿಲ್ಲದಿದ್ದರೆ ಮಾತ್ರ)
3. ಅಥವಾ: `release/vX.Y.0` ನಲ್ಲಿ ಹಾಟ್ಫಿಕ್ಸ್ → ಪ್ಯಾಚ್ ಬಿಡುಗಡೆ `vX.Y.(Z+1)`
4. GitHub Discussions ಮತ್ತು Discord ನಲ್ಲಿ ತಕ್ಷಣವೇ ತಿಳಿಸಿ

## ಕಟ್ಟುನಿಟ್ಟಿನ ನಿಯಮಗಳು

- `main` ಗೆ ಎಂದಿಗೂ ನೇರವಾಗಿ ಕಮಿಟ್ ಮಾಡಬೇಡಿ
- `main` ಅಥವಾ `release/*` ಶಾಖೆಗಳಿಗೆ ಎಂದಿಗೂ `git push --force` ಬಳಸಬೇಡಿ
- Husky ಹುಕ್ಗಳನ್ನು (`--no-verify`) ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ
- ರಹಸ್ಯಗಳು, ರುಜುವಾತುಗಳು ಅಥವಾ `.env` ಫೈಲ್ಗಳನ್ನು ಎಂದಿಗೂ ಕಮಿಟ್ ಮಾಡಬೇಡಿ
- ಕವರೇಜ್ ≥60/60/60/60 (ಸ್ಟೇಟ್ಮೆಂಟ್ಗಳು/ಲೈನ್ಗಳು/ಫಂಕ್ಷನ್ಗಳು/ಬ್ರಾಂಚ್ಗಳು) ಆಗಿಯೇ ಉಳಿಯಬೇಕು
- `src/`, `open-sse/`, `electron/`, ಅಥವಾ `bin/` ನಲ್ಲಿನ ಪ್ರೊಡಕ್ಷನ್ ಕೋಡ್ ಅನ್ನು ಬದಲಾಯಿಸುವಾಗ ಯಾವಾಗಲೂ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ ಅಥವಾ ನವೀಕರಿಸಿ
