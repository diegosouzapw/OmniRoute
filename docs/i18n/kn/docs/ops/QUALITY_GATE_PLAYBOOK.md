## ಭಾಗ 1 — ತೀರ್ಪು ಮತ್ತು ಪ್ರಬುದ್ಧತೆಯ ವರ್ಗೀಕರಣ

**ಒಟ್ಟಾರೆ ಗ್ರೇಡ್: A− / "ಸುಧಾರಿತ". ಅಗ್ರ ~5–10% ಪ್ರಾಜೆಕ್ಟ್ಗಳಲ್ಲಿ ಒಂದು.** ಉದ್ಯಮವು ಸ್ಪಷ್ಟವಾಗಿ ಹೆಸರಿಸುವ
ಹಲವಾರು ಮಾದರಿಗಳನ್ನು ಈ ವ್ಯವಸ್ಥೆಯು ಸ್ವತಂತ್ರವಾಗಿ ಅನುಷ್ಠಾನಗೊಳಿಸುತ್ತದೆ — ಇದು ಹೊಂದಾಣಿಕೆಯ ಅತ್ಯಂತ
ಬಲವಾದ ಸಂಕೇತವಾಗಿದೆ (ನಾವು ಪರಿಶೀಲನಾ ಪಟ್ಟಿಯನ್ನು ನಕಲಿಸಲಿಲ್ಲ; ಸರಿಯಾದ ಅಭ್ಯಾಸಗಳತ್ತ ಸ್ವತಂತ್ರವಾಗಿ ಒಮ್ಮತಗೊಂಡೆವು).

## ಭಾಗ 2 — ವಿಮರ್ಶಾತ್ಮಕ ಮೌಲ್ಯಮಾಪನ (ಸಾಮರ್ಥ್ಯಗಳು + ಪ್ರಾಮಾಣಿಕ ದೌರ್ಬಲ್ಯಗಳು)

### ಸಾಮರ್ಥ್ಯಗಳು (ಸರಾಸರಿಗಿಂತ ಉತ್ತಮವಾಗಿರುವವು)

1. **ಬಹು-ಮೆಟ್ರಿಕ್ ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್.** ವ್ಯವಸ್ಥೆಯ ಹೃದಯಭಾಗ. `quality-baseline.json` ನಲ್ಲಿ 24 ಮೆಟ್ರಿಕ್ಗಳು
   - 4 ಮೀಸಲಾದ ಬೇಸ್ಲೈನ್ಗಳು; ಪ್ರತಿಯೊಂದರಲ್ಲೂ ದಿಕ್ಕು (`up`/`down`), ಸಹಿಷ್ಣುತೆ (`eps`), ಸಡಿಲಿಕೆ
     (`tightenSlack`) ಮತ್ತು `dedicatedGate` ಫ್ಲ್ಯಾಗ್ ಇವೆ. ಸರಿಪಡಿಸಲಾದ ವಿಷಯಗಳು **ಸರಿಯಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ** — ಇದು
     ಕೋಡ್ಬೇಸ್ ಎಂಟ್ರೊಪಿಗೆ ಪ್ರತಿವಿಷವಾಗಿದೆ.
2. **ಸರಬರಾಜು-ಸರಪಳಿಗಾಗಿ ಬಹುಪದರ ರಕ್ಷಣೆ.** SAST (CodeQL/Sonar) + ಸೀಕ್ರೆಟ್ಗಳು (`useDefault` ಜೊತೆಗೆ gitleaks)
   - SCA (osv/npm-audit/Trivy/Dependabot) + ಪರವಾನಗಿಗಳು + ಲಾಕ್ಫೈಲ್ + SBOM + SLSA
     ಮೂಲದಾಖಲೆ + Scorecard + ವರ್ಕ್ಫ್ಲೋ ಬಲವರ್ಧನೆ (zizmor). ಕೆಲವೇ ಕೋಡ್ಬೇಸ್ಗಳು ಇಷ್ಟು ಸಂಪೂರ್ಣವಾದ ಸ್ಟ್ಯಾಕ್ ಹೊಂದಿವೆ.
3. **ಗುಡ್ಹಾರ್ಟ್ನ ನಿಯಮದ ವಿರುದ್ಧದ ಪ್ರತಿವಿಷಗಳು.** ಕವರೇಜ್ ಅನ್ನು ಗುರಿಯಾಗಿ ಪರಿಗಣಿಸುವುದು ಒಂದು ಸಾಂಪ್ರದಾಯಿಕ ಪ್ರತಿಕೂಲ ಮಾದರಿ
   ("ಅಳತೆಯೇ ಗುರಿಯಾದಾಗ, ಅದು ಉತ್ತಮ ಅಳತೆಯಾಗಿರುವುದನ್ನು ನಿಲ್ಲಿಸುತ್ತದೆ"). ನಮ್ಮಲ್ಲಿ ಇದಕ್ಕೆ
   ಸಮತೋಲಕಗಳಿವೆ: **ಮ್ಯೂಟೇಶನ್ ಟೆಸ್ಟಿಂಗ್** (ಪರೀಕ್ಷೆಯು ಕೇವಲ ಸಾಲನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆಯೇ ಎಂಬುದಕ್ಕಿಂತ,
   ದೋಷವನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆಯೇ ಎಂಬುದನ್ನು ಅಳೆಯುತ್ತದೆ), **`check-test-masking`** (ಪಾಸ್ ಆಗುವುದಕ್ಕಾಗಿ assertಗಳನ್ನು ದುರ್ಬಲಗೊಳಿಸುವುದನ್ನು ತಡೆಯುತ್ತದೆ),
   **ಪ್ರತಿ-ಮಾಡ್ಯೂಲ್ ಕವರೇಜ್ ಕನಿಷ್ಠ ಮಿತಿಗಳು** (ಸುಲಭ ಭಾಗಗಳನ್ನಷ್ಟೇ ಅಲ್ಲದೆ, ಹೆಚ್ಚಿನ ಅಪಾಯದ ಕೋಡ್ ಅನ್ನು ಪರೀಕ್ಷಿಸಲು ಒತ್ತಾಯಿಸುತ್ತವೆ) ಮತ್ತು
   **`check-pr-evidence`** (ಕಠಿಣ ನಿಯಮ #18).
4. **ಭ್ರಮೆ-ವಿರೋಧಿ / ಸ್ಥಿರತೆ ಗೇಟ್ಗಳು.** ಅಪರೂಪದ ಮತ್ತು ಮೌಲ್ಯಯುತ ವರ್ಗ: `check-known-symbols`,
   `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols` ಇವು ಡಾಕ್ಯುಮೆಂಟ್ಗಳು, ಸ್ಪೆಕ್ಗಳು ಮತ್ತು
   ಸ್ಟ್ರಿಂಗ್ ಡಿಸ್ಪ್ಯಾಚ್ಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸಿಂಬಲ್ಗಳನ್ನು ಸೂಚಿಸುತ್ತವೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸುತ್ತವೆ. lint/test ಪತ್ತೆಹಚ್ಚದ "ಕ್ಷಯ"ವನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತವೆ.
5. **ಸಲಹಾತ್ಮಕ→ತಡೆಹಿಡಿಯುವ ಜೀವನಚಕ್ರ.** ಹೊಸ ಗೇಟ್ಗಳು ಸಲಹಾತ್ಮಕವಾಗಿ ಪ್ರವೇಶಿಸುತ್ತವೆ (ಪಕ್ವಗೊಳ್ಳುವಾಗ
   ವಿಲೀನಗಳನ್ನು ತಡೆಯುವುದಿಲ್ಲ), ನಂತರ ಚಕ್ರದ ಅಂತ್ಯದಲ್ಲಿ ತಡೆಹಿಡಿಯುವಂತಾಗುತ್ತವೆ. ಗರಿಷ್ಠ ಮಿತಿಯನ್ನು ಕಳೆದುಕೊಳ್ಳದೆ ಘರ್ಷಣೆಯನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ.
6. **ಮೂಲಸೌಕರ್ಯ ಇಲ್ಲದಾಗ ಸುಗಮವಾಗಿ ಬಿಟ್ಟುಬಿಡುವಿಕೆ.** ಬೈನರಿ/ನೆಟ್ವರ್ಕ್ ವಿಫಲವಾದರೆ ಸ್ಕ್ಯಾನರ್ಗಳು (`--ratchet`)
   `exit 0` ಮೂಲಕ ನಿರ್ಗಮಿಸುತ್ತವೆ — ಕಾಣೆಯಾದ ಮೂಲಸೌಕರ್ಯವು ನ್ಯಾಯಸಮ್ಮತ PR ಅನ್ನು ಎಂದಿಗೂ ತಡೆಯುವುದಿಲ್ಲ. ಪಕ್ವವಾದ ಎಂಜಿನಿಯರಿಂಗ್.
7. **ನಿಯಮಬದ್ಧಗೊಳಿಸಿದ ಸಂಸ್ಕೃತಿ.** ಕಠಿಣ ನಿಯಮಗಳು + `trust-but-verify` + ಹಳೆಯ-ಅನುಮತಿಪಟ್ಟಿ + ಸಾಕ್ಷ್ಯ-ಗೇಟ್
   ಶಿಸ್ತನ್ನು ಸ್ವಯಂಚಾಲಿತ ಪರಿಶೀಲನೆಯಾಗಿ ಪರಿವರ್ತಿಸುತ್ತವೆ.

### ಪ್ರಾಮಾಣಿಕ ದೌರ್ಬಲ್ಯಗಳು (ವಾಸ್ತವಿಕ ಕೊರತೆಗಳು)

1. **🔴 ವೇಗದ-ಗೇಟ್ಗಳ ವಿಭಜನೆಯು ಇನ್ನೂ ರಚನಾತ್ಮಕ ಕೊರತೆಯನ್ನು ಉಳಿಸಿದೆ.** `quality.yml` (PR→`release/**`)
   ಈಗ ಕೋಡ್ PRಗಳಿಗಾಗಿ typecheck, ವೇಗವಾದ ನಿರ್ಧಾರಾತ್ಮಕ ಪರೀಕ್ಷೆಗಳು ಮತ್ತು ಸಲಹಾತ್ಮಕ production build ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ,
   ಆದರೆ ಅದು ಇನ್ನೂ `ci.yml` ನ ಸಂಪೂರ್ಣ release-PR ವ್ಯಾಪ್ತಿಯನ್ನು (ಕವರೇಜ್ ರ್ಯಾಚೆಟ್ಗಳು,
   ಪ್ಯಾಕೇಜ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್, ಏಕೀಕರಣ, E2E, SonarQube) ಚಲಾಯಿಸುವುದಿಲ್ಲ. ಪ್ರೇರಣೆ (ವೇಗ) ಸಮರ್ಥನೀಯವಾಗಿದೆ, ಆದರೆ
   ವಿಲೀನ ನಡೆಯುವ ಸ್ಥಳದಲ್ಲೇ ಗೇಟ್ ಇರಬೇಕು (shift-left). **ಬಾಕಿಯಿರುವ ಅತಿದೊಡ್ಡ ರಚನಾತ್ಮಕ ಪರಿಹಾರ.**
2. **🟠 ಗೇಟ್ಗಳ ಅತಿವಿಸ್ತರಣೆ/ಆಯಾಸದ ಅಪಾಯ.** ~46 ಗೇಟ್ಗಳು + 25 ಜಾಬ್ಗಳು ಬಹಳ ಹೆಚ್ಚು. Sonar ಸ್ವತಃ ಎಚ್ಚರಿಸುತ್ತದೆ:
   ಅತಿಯಾದ ಷರತ್ತುಗಳು "ಗೇಟ್ ಆಯಾಸ" ಮತ್ತು ಆದ್ಯತೆಯ ಚರ್ಚೆಗಳಿಗೆ ಕಾರಣವಾಗುತ್ತವೆ ಹಾಗೂ ಗೇಟ್ ಅನ್ನು
   ನಿರ್ಲಕ್ಷಿಸುವ ಅಪಾಯವಿರುತ್ತದೆ. ಭಾರವಾದ ಗೇಟ್ಗಳು ಲೀಡ್-ಟೈಮ್ ಹೆಚ್ಚಿಸುತ್ತವೆ ಎಂದು DORA ಎಚ್ಚರಿಸುತ್ತದೆ. ನಾವು ಸಲಹಾತ್ಮಕ ಹಂತಗಳು ಮತ್ತು
   ನಿರಪೇಕ್ಷವಲ್ಲದ ರ್ಯಾಚೆಟ್ಗಳ ಮೂಲಕ ಇದನ್ನು ತಗ್ಗಿಸುತ್ತೇವೆ, ಆದರೆ **ಪ್ರತಿ ಗೇಟ್ಗೆ ಆವರ್ತಕ ROI ವಿಮರ್ಶೆ** ಇಲ್ಲವಾಗಿದೆ (doc-sync ಗಾಗಿರುವ
   ಕೆಲವು ಮೈಕ್ರೋ-ಗೇಟ್ಗಳನ್ನು ಏಕೀಕರಿಸಬಹುದು).
3. **🟠 ಮ್ಯೂಟೇಶನ್ ಸ್ಕೋರ್ ಇನ್ನೂ ರ್ಯಾಚೆಟ್ ಆಗಿಲ್ಲ.** ಕವರೇಜ್-ಗೇಮಿಂಗ್ ವಿರುದ್ಧದ ಅತ್ಯಂತ ಬಲವಾದ ಪ್ರತಿವಿಷವು
   **ಸಲಹಾತ್ಮಕವಾಗಿದೆ**. ಇದು ಬಾಕಿಯಿರುವ ಅತ್ಯಂತ ಮೌಲ್ಯಯುತ ಅಂಶವಾಗಿದೆ (ಮತ್ತು ಈಗಾಗಲೇ 90% ನಿರ್ಮಾಣಗೊಂಡಿದೆ).
4. **🟡 ತಡೆಯಬೇಕಾದ ಸಲಹಾತ್ಮಕ ಗೇಟ್ಗಳು (ಸರಿಯಾದ ವ್ಯಾಪ್ತಿಯೊಂದಿಗೆ).** ಸ್ಥಿರಗೊಳಿಸಿದ ಬೇಸ್ಲೈನ್ಗಳಿದ್ದರೂ `osv` (vulnCount) ಮತ್ತು `oasdiff`
   ಸಲಹಾತ್ಮಕವಾಗಿವೆ. osv ಸಲಹಾತ್ಮಕವಾಗಿರುವುದು ಅರ್ಥಪೂರ್ಣವಾಗಿದೆ (ಹಳೆಯ dependency ಯಲ್ಲಿನ ಹೊಸ CVE,
   ಸಂಬಂಧವಿಲ್ಲದ PR ಅನ್ನು ತಡೆಯಬಹುದು) — ಆದರೆ ಮಧ್ಯಮ ಮಾರ್ಗವಿದೆ (ನಾವು
   Trivy ಯೊಂದಿಗೆ ಮಾಡಿದಂತೆ CRITICAL+fixable ಅನ್ನು ಮಾತ್ರ ತಡೆಯುವುದು). oasdiff ಸಲಹಾತ್ಮಕವಾಗಿರುವುದರಿಂದ ಒಪ್ಪಂದವನ್ನು ಮುರಿಯುವ ಬದಲಾವಣೆಯೂ ಪಾಸ್ ಆಗಬಹುದು.

   ಸರಿಯಾದ ನಿರ್ಧಾರ (ನಿಧಾನ, ಲೈವ್ ಸರ್ವರ್ ಅಗತ್ಯ), ಆದರೆ PR ಒಂದು injection-guard ರಿಗ್ರೆಶನ್ ಅನ್ನು ಪರಿಚಯಿಸಬಹುದು
   ಮತ್ತು ಅದು ಮರುದಿನ ರಾತ್ರಿ ಮಾತ್ರ ಪತ್ತೆಯಾಗಬಹುದು.

## ಭಾಗ 3 — ಗುಣಮಟ್ಟದ ಪರಿಶೀಲನಾ ಬಿಂದುಗಳ ಸಂಪೂರ್ಣ ಕ್ಯಾಟಲಾಗ್ (ಪೋರ್ಟಬಲ್)

ಕೆಳಗಿನ 12 ವರ್ಗಗಳು ಮರುಬಳಕೆ ಮಾಡಬಹುದಾದ ರೂಪದಲ್ಲಿರುವ "ಗುಣಮಟ್ಟದ ವ್ಯವಸ್ಥೆ". ಪ್ರತಿಯೊಂದೂ
**ಉದ್ದೇಶ** (ಯಾವುದನ್ನು ರಕ್ಷಿಸಬೇಕು), **ನಾವು ಬಳಸುವ ಪರಿಕರಗಳು** ಮತ್ತು ಯಾವುದೇ ಸ್ಟ್ಯಾಕ್ನಲ್ಲಿ ಪುನರಾವರ್ತಿಸಲು ಬೇಕಾದ **ಪರಿಕರ-ಸ್ವತಂತ್ರ ಸಮಾನ ವಿಧಾನ**
ಇವುಗಳನ್ನು ಪಟ್ಟಿಮಾಡುತ್ತದೆ.

### 1. ಶೈಲಿ ಮತ್ತು ಫಾರ್ಮ್ಯಾಟಿಂಗ್ (ನಿರ್ಣಾಯಕ, ವೇಗವಾದ)

- **OmniRoute:** lint-staged ಮೂಲಕ Prettier + ESLint (pre-commit), 2-spaces/double-quotes/100col.
- **ಸಾಮಾನ್ಯ:** ಸ್ವಯಂ-ಸರಿಪಡಿಸಬಹುದಾದ ಒಂದು ಫಾರ್ಮ್ಯಾಟರ್ + ಒಂದು ಲಿಂಟರ್, staged ಫೈಲ್ಗಳ ಮೇಲೆ pre-commitನಲ್ಲಿ ಚಾಲನೆಯಾಗಬೇಕು.

### 2. ಪ್ರಕಾರಗಳು

- **OmniRoute:** `typecheck:core` (ನಿರ್ಬಂಧಕ) + `typecheck:noimplicit:core` (ಸಲಹಾತ್ಮಕ) + `type-coverage` ರ್ಯಾಚೆಟ್ 92.17% + ಪ್ರತಿ-ಫೈಲ್ any-ಬಜೆಟ್.
- **ಸಾಮಾನ್ಯ:** CIಯಲ್ಲಿ ಕಟ್ಟುನಿಟ್ಟಾದ typecheck + ರ್ಯಾಚೆಟ್ ಮಾಡಿದ type-coverage ಮೆಟ್ರಿಕ್ + ಪ್ರತಿ-ಫೈಲ್ `any`/ತಪ್ಪಿಸಿಕೊಳ್ಳುವ ಮಾರ್ಗದ ಬಜೆಟ್.

### 3. ಪರೀಕ್ಷೆಗಳು (ತೀವ್ರತೆ)

- **OmniRoute:** ಪರಸ್ಪರ ಅತಿಕ್ರಮಿಸದ 2 ರನ್ನರ್ಗಳು (Node native + vitest), 8 shards, ಜಾಗತಿಕ coverage 60/60/60/60 + ರ್ಯಾಚೆಟ್ ~76% + **ನಿರ್ಣಾಯಕ ಮಾಡ್ಯೂಲ್ಗಳಿಗೆ 8 ಪ್ರತಿ-ಮಾಡ್ಯೂಲ್ ಕನಿಷ್ಠ ಮಿತಿಗಳು** + ರಾತ್ರಿಯ property tests + ರಾತ್ರಿಯ **mutation testing**.
- **ಸಾಮಾನ್ಯ:** test runner(s) + **ನಿರಪೇಕ್ಷ** coverage ಕನಿಷ್ಠ ಮಿತಿ (ಶೂನ್ಯ-ವಿರೋಧಿ) + coverage **ರ್ಯಾಚೆಟ್** (ಹಿಂಜರಿಕೆ-ವಿರೋಧಿ) + **ಹೆಚ್ಚಿನ ಅಪಾಯದ ಕೋಡ್ಗೆ ಪ್ರತಿ-ಮಾಡ್ಯೂಲ್ ಕನಿಷ್ಠ ಮಿತಿಗಳು** (Goodhart-ವಿರೋಧಿ) + ಶುದ್ಧ ಲಾಜಿಕ್ಗೆ property-based ಪರೀಕ್ಷೆ + ಪರೀಕ್ಷಾ ಗುಣಮಟ್ಟದ ನೈಜ ಮಾಪನವಾಗಿ ರಾತ್ರಿಯ **mutation testing**.

### 4. ಪರೀಕ್ಷಾ ನೀತಿ (ವಂಚನೆ-ವಿರೋಧಿ)

- **OmniRoute:** `pr-test-policy` (production ಕೋಡ್ಗೆ ಪರೀಕ್ಷೆ ಅಗತ್ಯ), `check-test-masking` (ದುರ್ಬಲಗೊಳಿಸಿದ asserts ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ), `pr-evidence` (ಯಶಸ್ಸಿನ ಹೇಳಿಕೆಗೆ evidence block ಅಗತ್ಯ), `test-discovery` (ಪ್ರತಿ ಪರೀಕ್ಷೆಯನ್ನೂ runner ಸಂಗ್ರಹಿಸುತ್ತದೆ).
- **ಸಾಮಾನ್ಯ:** "ಹೊಸ ಕೋಡ್ ⇒ ಹೊಸ ಪರೀಕ್ಷೆ" ಗೇಟ್ + assert ತೆಗೆದುಹಾಕಿರುವುದನ್ನು/tautologyಯನ್ನು ಪತ್ತೆಮಾಡುವ ಸಾಧನ + ಸಾಕ್ಷ್ಯದ ಅಗತ್ಯ (TDD ಅಥವಾ living test) + ಯಾವುದೇ ಪರೀಕ್ಷೆಯು globsನ ಹೊರಗೆ ಅನಾಥವಾಗಿಲ್ಲ ಎಂಬ ಖಾತರಿ.

### 5. ಸಂಕೀರ್ಣತೆ ಮತ್ತು ಕೋಡ್ ಆರೋಗ್ಯ (ರ್ಯಾಚೆಟ್ಗಳು)

- **OmniRoute:** ESLint-warnings (3769↓), jscpd duplication (5.72%↓), cyclomatic+max-lines complexity (1800↓), cognitive complexity sonarjs (753↓), dead-code/unused-exports knip (339↓), ಪ್ರತಿ-ಫೈಲ್ file-size (ಸ್ಥಿರಗೊಳಿಸಿದ, ಕುಗ್ಗಿಸಲು ಮಾತ್ರ), circular-deps (ಕಸ್ಟಮ್ Tarjan, ನಿರ್ಬಂಧಕ).
- **ಸಾಮಾನ್ಯ:** ಪ್ರತಿಯೊಂದು ಆರೋಗ್ಯ ಮೆಟ್ರಿಕ್ನ್ನೂ ರ್ಯಾಚೆಟ್ ಮಾಡಿ (ಎಚ್ಚರಿಕೆಗಳು, ನಕಲು, cyclomatic **ಮತ್ತು** cognitive complexity, dead code, file size, import cycles). ದಿಕ್ಕು ಯಾವಾಗಲೂ "ಹಿಂಜರಿಯಬೇಡಿ" ಆಗಿರಬೇಕು.

### 6. ಸ್ಥಿರ ಭದ್ರತೆ (SAST + ರಹಸ್ಯಗಳು)

- **OmniRoute:** CodeQL (alerts ರ್ಯಾಚೆಟ್ = 0), gitleaks (`[extend] useDefault=true` — ಅತ್ಯಂತ ನಿರ್ಣಾಯಕ!), SonarQube, ಕಸ್ಟಮ್ ಭದ್ರತಾ ನಿಯಮಗಳು (public-creds, error-helper, route-guard-membership, route-validation).
- **ಸಾಮಾನ್ಯ:** alert ರ್ಯಾಚೆಟ್ ಹೊಂದಿರುವ SAST (CodeQL/Sonar/semgrep) + **ಪಾರಂಪರ್ಯವಾಗಿ ಪಡೆದ ಡೀಫಾಲ್ಟ್ ruleset** ಹೊಂದಿರುವ secrets scanner (ಡೀಫಾಲ್ಟ್ ಅನ್ನು override ಮಾಡುವ ಕಸ್ಟಮ್ config = ಕುರುಡುತನ) + ಪ್ರಾಜೆಕ್ಟ್ಗೆ ನಿರ್ದಿಷ್ಟವಾದ Hard Rule ಭದ್ರತಾ ಗೇಟ್ಗಳು.

### 7. ಪೂರೈಕೆ ಸರಪಳಿ (ಅವಲಂಬನೆಗಳು)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (SPDX allowlist), lockfile-lint (HTTPS+sha512+registry), `check-deps` anti-slopsquatting (allowlist + ವಯಸ್ಸು ≥72h).
- **ಸಾಮಾನ್ಯ:** ಬಹು-ಮೂಲ SCA + ಪರವಾನಗಿ allowlist + lockfile ಸಮಗ್ರತೆ ಪರಿಶೀಲನೆ + ವಯಸ್ಸು/typosquatting ಪರಿಶೀಲನೆಯೊಂದಿಗಿನ dependency allowlist + ಗುಂಪುಮಾಡಿದ update bot.

### 8. ಪೂರೈಕೆ ಸರಪಳಿ (ಬಿಲ್ಡ್ ಮತ್ತು ಬಿಡುಗಡೆ)

- **OmniRoute:** SBOM (CycloneDX + syft), SLSA provenance (`--provenance`), OpenSSF Scorecard (ವಾರಕ್ಕೊಮ್ಮೆ), workflow hardening (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions).
- **ಸಾಮಾನ್ಯ:** ಪ್ರಕಟಿಸುವಾಗ SBOM ರಚಿಸಿ + ಸಹಿ ಮಾಡಿದ provenance (SLSA L2+) + ನಿಗದಿತ ವೇಳಾಪಟ್ಟಿಯ Scorecard + ಎಲ್ಲಾ workflows ಅನ್ನು ಬಲಪಡಿಸಿ (ಕನಿಷ್ಠ-ಸವಲತ್ತಿನ tokens, non-pusher checkoutನಲ್ಲಿ ಉಳಿಸಿಟ್ಟ credentials ಇರಬಾರದು, actions ಅನ್ನು SHA ಮೂಲಕ pin ಮಾಡಬೇಕು).

### 9. ಒಪ್ಪಂದಗಳು ಮತ್ತು API

- **OmniRoute:** oasdiff (breaking-change OpenAPI), schemathesis (ರಾತ್ರಿಯ contract fuzz), openapi-coverage (% ದಾಖಲಿಸಲಾದ routes, ರ್ಯಾಚೆಟ್ 38.3%), openapi-security-tiers (spec ಮತ್ತು route-guard ನಡುವಿನ ಹೋಲಿಕೆ).
- **ಸಾಮಾನ್ಯ:** breaking-change contract diff (oasdiff/buf) + spec ವಿರುದ್ಧ property-based fuzz (schemathesis) + ರ್ಯಾಚೆಟ್ ಮಾಡಿದ documentation coverage + spec↔code ಸ್ಥಿರತೆ.

### 10. ಡಾಕ್ಸ್ ಮತ್ತು i18n (ಕ್ಷಯ-ವಿರೋಧಿ)

- **OmniRoute:** docs-sync (ಪ್ರತಿಬಿಂಬಿತ versions), docs-counts-sync (docs ಮತ್ತು codeನಲ್ಲಿರುವ ಸಂಖ್ಯೆಗಳು), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + ರ್ಯಾಚೆಟ್ 80.1%).
- **ಸಾಮಾನ್ಯ:** docs ಮತ್ತು code ನಡುವೆ versions/counts/env-vars ಅನ್ನು ಸಿಂಕ್ ಮಾಡಿ (ಗೇಟ್, ನಂಬಿಕೆ ಅಲ್ಲ) + ಆಂತರಿಕ links ಅನ್ನು ಮೌಲ್ಯೀಕರಿಸಿ + ರ್ಯಾಚೆಟ್ ಮಾಡಿದ i18n coverage.

### 11. ಭ್ರಮೆ-ವಿರೋಧಿ / ಸ್ಥಿರತೆ (ಅಪರೂಪದ ವರ್ಗ)

- **OmniRoute:** known-symbols (string dispatch ⇒ ಜೀವಂತ symbol), provider-consistency, fetch-targets (client fetch ⇒ ನೈಜ route), docs-symbols, db-rules (Hard Rules #2/#5), migration-numbering.
- **ಸಾಮಾನ್ಯ:** ಪ್ರತಿಯೊಂದು "ನಕಲುಗೊಂಡ ಏಕೈಕ ಸತ್ಯದ ಮೂಲ"ಕ್ಕೆ (registry, string dispatch, cross-layer references), ಎರಡೂ ಬದಿಗಳು ಹೊಂದಿಕೆಯಾಗುತ್ತವೆ ಎಂದು ಸಾಬೀತುಪಡಿಸುವ ಗೇಟ್ ಇರಬೇಕು. typecheck/test ಪತ್ತೆಮಾಡದ ಕ್ಷಯವನ್ನು ಇದು ಪತ್ತೆಮಾಡುತ್ತದೆ.

### 12. ಸ್ಥಿತಿಸ್ಥಾಪಕತೆ ಮತ್ತು ಡೊಮೇನ್ (ಉತ್ಪನ್ನ-ನಿರ್ದಿಷ್ಟ)

- **OmniRoute:** chaos (fault-injection), heap-growth (leak), k6 (soak), promptfoo+garak (LLM red-team OWASP LLM Top 10), ಸ್ಥಿತಿಸ್ಥಾಪಕತೆಯ 3 ನಿಯಮಗಳು (circuit-breaker/cooldown/lockout).
- **ಸಾಮಾನ್ಯ:** **ನಿಮ್ಮ** ಡೊಮೇನ್ನ ವೈಫಲ್ಯ ವಿಧಾನಗಳನ್ನು ಗುರುತಿಸಿ ಮತ್ತು ಪ್ರತಿಯೊಂದಕ್ಕೂ ಒಂದು ಗೇಟ್ ಇರಿಸಿ (ಅದು ರಾತ್ರಿಯಲ್ಲಿ ಮಾತ್ರ ಚಾಲನೆಯಾದರೂ ಸಹ). AI appsಗೆ: injection red-team. distributed systemsಗೆ: chaos + leak + soak.

## ಭಾಗ 4 — ಯಾವುದೇ ಪ್ರಾಜೆಕ್ಟ್ಗಾಗಿ ಪುನರಾವರ್ತನಾ ಯೋಜನೆ

**ಹಂತಗಳಲ್ಲಿ** ನಿರ್ಮಿಸಿ; ಪ್ರತಿಯೊಂದು ಹಂತವೂ ಸ್ವತಂತ್ರವಾಗಿ ಮೌಲ್ಯವನ್ನು ಒದಗಿಸಬೇಕು. ಎಲ್ಲಾ 12 ವರ್ಗಗಳನ್ನು ಒಂದೇ ಬಾರಿ ಪ್ರಯತ್ನಿಸಬೇಡಿ —
ಅದು ಭಾಗ 2 ಎಚ್ಚರಿಸುವ ಗೇಟ್ ಆಯಾಸವನ್ನೇ ಉಂಟುಮಾಡುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಹೊಸ ಗೇಟ್ **ಸಲಹಾತ್ಮಕ**ವಾಗಿ ಪ್ರಾರಂಭವಾಗಿ,
ಸ್ಥಿರವಾದಾಗ **ತಡೆಯುವ** ಗೇಟ್ ಆಗುತ್ತದೆ.

### ಮರುಬಳಕೆ ಮಾಡಬಹುದಾದ ಕೇಂದ್ರಬಿಂದು: "ರ್ಯಾಚೆಟ್ ಗೇಟ್ನ ಅಂಗರಚನೆ"

ಸಂಪೂರ್ಣ ವ್ಯವಸ್ಥೆಯು ಈ 3-ಫೈಲ್ ಮಾದರಿಯ ಸುತ್ತ ಸುತ್ತುತ್ತದೆ. ಮೊದಲು ಇದನ್ನು ನಕಲಿಸಿ:

1. **`baseline.json`** — ಸ್ಥಿರಗೊಳಿಸಿದ ಮೆಟ್ರಿಕ್ ಮೌಲ್ಯ + `direction` (`up`/`down`) + `eps` (ಅಸ್ಥಿರತೆ-ನಿರೋಧಕ) + `tightenSlack` + `dedicatedGate`.
2. **`collect-metrics.<ext>`** — ಟೂಲ್ ಅನ್ನು ಚಲಾಯಿಸಿ, ಸಂಖ್ಯೆಯನ್ನು ಹೊರತೆಗೆದು, `metrics.json` ಅನ್ನು ಬರೆಯುತ್ತದೆ.
3. **`check-ratchet.<ext>`** — `metrics.json` ಅನ್ನು `baseline.json` ಜೊತೆ ಹೋಲಿಸುತ್ತದೆ; `eps` ಮಿತಿಯನ್ನು ಮೀರಿ ಹಿಂಜರಿತವಾದರೆ **ಮಾತ್ರ** `exit 1`; ಟೂಲ್/ಮೂಲಸೌಕರ್ಯ ಲಭ್ಯವಿಲ್ಲದಿದ್ದರೆ `exit 0` (ಸಮರ್ಪಕವಾಗಿ ಬಿಟ್ಟುಬಿಡುವುದು); `--require-tighten` ಜೊತೆಗೆ, ಬೇಸ್ಲೈನ್ ನವೀಕರಿಸದೆ ಅದು **ಸುಧಾರಿಸಿದ್ದರೆ** `exit 1` (ಸುಧಾರಣೆಯನ್ನು ಸ್ಥಿರಗೊಳಿಸುತ್ತದೆ).

ಇದು ಸಿದ್ಧವಾದ ನಂತರ, **ಪ್ರತಿಯೊಂದು** ಹೊಸ ಮೆಟ್ರಿಕ್ (ಕವರೇಜ್, ಸಂಕೀರ್ಣತೆ, ಎಚ್ಚರಿಕೆಗಳು, SAST ಅಲರ್ಟ್ಗಳು, ಬಂಡಲ್ ಗಾತ್ರ, ಮ್ಯೂಟೇಶನ್ ಸ್ಕೋರ್…) ಬೇಸ್ಲೈನ್ನಲ್ಲಿ ಕೇವಲ ಒಂದು ಸಾಲಾಗಿರುತ್ತದೆ.

### ಹಂತ 0 — ಅಡಿಪಾಯ (ವಾರ 1)

CI ಅಸ್ತಿತ್ವದಲ್ಲಿರಬೇಕು; ಫಾರ್ಮ್ಯಾಟರ್ + ಲಿಂಟರ್ + ಟೈಪ್ಚೆಕ್ + 1 ಟೆಸ್ಟ್ ರನ್ನರ್ + **ನಿರಪೇಕ್ಷ** ಕವರೇಜ್ ಕನಿಷ್ಠ ಮಿತಿ
(ಉದಾ., 60%). ಪ್ರೀ-ಕಮಿಟ್ ವೇಗವಾದ, ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸರಿಪಡಿಸಬಹುದಾದ ಪರಿಶೀಲನೆಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. _ಫಲಿತಾಂಶ: ಯಾವುದೇ PR ಮೂಲಭೂತ ಅಂಶಗಳನ್ನು ಮುರಿಯುವುದಿಲ್ಲ._

### ಹಂತ 1 — ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್ (ವಾರ 2) — **ಎಲ್ಲದರ ಅಡಿಪಾಯ**

ಮೇಲಿನ 3 ಫೈಲ್ಗಳನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ. ಇವುಗಳಿಗಾಗಿ ಬೇಸ್ಲೈನ್ಗಳನ್ನು ಸ್ಥಿರಗೊಳಿಸಿ: ಎಚ್ಚರಿಕೆಗಳು, ಕವರೇಜ್, ಸಂಕೀರ್ಣತೆ, ನಕಲು,
ಬಳಕೆಯಾಗದ ಕೋಡ್, ಫೈಲ್ ಗಾತ್ರ. _ಫಲಿತಾಂಶ: ಇಲ್ಲಿಂದ ಮುಂದೆ ಕೋಡ್ಬೇಸ್ ಸುಧಾರಿಸಬಹುದು ಮಾತ್ರ._

### ಹಂತ 2 — ಸ್ಥಿರ ವಿಶ್ಲೇಷಣೆಯ ಆಳ (ವಾರ 3)

ಅಲರ್ಟ್ ರ್ಯಾಚೆಟ್ನೊಂದಿಗೆ SAST (CodeQL/Sonar/semgrep); ಸೀಕ್ರೆಟ್ಸ್ ಸ್ಕ್ಯಾನರ್ (**ಡೀಫಾಲ್ಟ್ ನಿಯಮಸಮೂಹವನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯಿರಿ**);
SCA (osv/Dependabot) + ಲೈಸೆನ್ಸ್ ಅನುಮತಿ ಪಟ್ಟಿ + lockfile-lint. _ಫಲಿತಾಂಶ: ತಿಳಿದಿರುವ ದುರ್ಬಲತೆಗಳು ಮತ್ತು
ಸೋರಿಕೆಯಾದ ರಹಸ್ಯಗಳು ಪಾಸ್ ಆಗುವುದಿಲ್ಲ._

### ಹಂತ 3 — ಬಿಲ್ಡ್ ಪೂರೈಕೆ ಸರಪಳಿ (ವಾರ 4)

ಪ್ರಕಟಿಸುವಾಗ SBOM + ಸಹಿ ಮಾಡಿದ ಮೂಲಸಾಕ್ಷ್ಯ (SLSA L2) + ನಿಗದಿತ Scorecard + ವರ್ಕ್ಫ್ಲೋ ಬಲಪಡಿಸುವಿಕೆ
(zizmor: ಕನಿಷ್ಠ ಟೋಕನ್ಗಳು, ಉಳಿಸಿಕೊಂಡ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳಿಲ್ಲ, ಪಿನ್ ಮಾಡಿದ ಆಕ್ಷನ್ಗಳು). _ಫಲಿತಾಂಶ: ಪತ್ತೆಹಚ್ಚಬಹುದಾದ ಮತ್ತು
ತಿದ್ದುಪಡಿ-ನಿರೋಧಕ ಬಿಡುಗಡೆಗಳು._

### ಹಂತ 4 — ಪರೀಕ್ಷಾ ತೀವ್ರತೆ (ವಾರ 5–6)

ಉಪಯುಕ್ತವಾಗಿದ್ದರೆ 2ನೇ ರನ್ನರ್; **ನಿರ್ಣಾಯಕ ಮಾಡ್ಯೂಲ್ಗಳಿಗೆ ಪ್ರತಿ-ಮಾಡ್ಯೂಲ್ ಕವರೇಜ್ ಕನಿಷ್ಠ ಮಿತಿಗಳು** (Goodhart-ನಿರೋಧಕ);
ಶುದ್ಧ ಲಾಜಿಕ್ಗೆ ಪ್ರಾಪರ್ಟಿ-ಆಧಾರಿತ ಪರೀಕ್ಷೆ; **ಪ್ರತಿ ರಾತ್ರಿ ಮ್ಯೂಟೇಶನ್ ಟೆಸ್ಟಿಂಗ್** → 1ನೇ ಸ್ಕೋರ್ ಬಂದಾಗ,
`mutationScore` ಅನ್ನು ರ್ಯಾಚೆಟ್ ಆಗಿ ಮಾಡಿ. _ಫಲಿತಾಂಶ: ಕವರೇಜ್ ಕೇವಲ ತೋರಿಕೆಯ ಮೆಟ್ರಿಕ್ ಆಗಿರುವುದು ನಿಲ್ಲುತ್ತದೆ; ಪರೀಕ್ಷೆಗಳು ದೋಷಗಳನ್ನು ಹಿಡಿಯುತ್ತವೆ ಎಂಬುದು ಸಾಬೀತಾಗುತ್ತದೆ._

### ಹಂತ 5 — ಒಪ್ಪಂದ ಮತ್ತು ಡೈನಾಮಿಕ್ ಪರೀಕ್ಷೆ (ವಾರ 7)

ಸಾರ್ವಜನಿಕ API ಇದ್ದರೆ: oasdiff (ಬ್ರೇಕಿಂಗ್ ಬದಲಾವಣೆ, **ತಡೆಯುವ**) + schemathesis (ರಾತ್ರಿಯ ಫಜಿಂಗ್).
ಡೊಮೇನ್ಗೆ ಸೂಕ್ತವಾದಂತೆ ಪ್ರತಿ ರಾತ್ರಿ DAST/ರೆಡ್-ಟೀಮ್ ಪರೀಕ್ಷೆ. _ಫಲಿತಾಂಶ: ಒಪ್ಪಂದಗಳು ಮೌನವಾಗಿ ಮುರಿಯುವುದಿಲ್ಲ._

### ಹಂತ 6 — ಭ್ರಮೆ-ನಿರೋಧಕ ಮತ್ತು ಡೊಮೇನ್ ಪರೀಕ್ಷೆ (ವಾರ 8)

ಪ್ರಾಜೆಕ್ಟ್ನಲ್ಲಿನ ಪ್ರತಿಯೊಂದು "ನಕಲು ಮಾಡಲಾದ ಸತ್ಯ"ಕ್ಕಾಗಿ ಒಂದು ಸ್ಥಿರತಾ ಗೇಟ್. ಡೊಮೇನ್-ನಿರ್ದಿಷ್ಟ ವೈಫಲ್ಯ-ವಿಧಾನದ
ಗೇಟ್ಗಳು (AI ಗಾಗಿ: ಇಂಜೆಕ್ಷನ್ ರೆಡ್-ಟೀಮ್). _ಫಲಿತಾಂಶ: ರಚನಾತ್ಮಕ ಕುಸಿತ ಮತ್ತು ಡೊಮೇನ್ ವೈಫಲ್ಯಗಳಿಗೆ ಸುರಕ್ಷತಾ ಜಾಲವಿರುತ್ತದೆ._

### ಹಂತ 7 — ಆಡಳಿತ (ನಿರಂತರ)

- ಪ್ರತಿಯೊಂದು ಹೊಸ ಗೇಟ್ಗೆ ಸಲಹಾತ್ಮಕ→ತಡೆಯುವ ಚಕ್ರ.
- `stale-allowlist`: ಪ್ರತಿಯೊಂದು ವಿನಾಯಿತಿಗೂ ಸಮರ್ಥನೆ + ಇಶ್ಯೂ ಇರಬೇಕು; ಬಳಕೆಯಲ್ಲಿಲ್ಲದ ವಿನಾಯಿತಿಯನ್ನು ಪತ್ತೆಹಚ್ಚಲಾಗುತ್ತದೆ.
- `evidence-gate`: PRನಲ್ಲಿನ ಯಶಸ್ಸಿನ ಪ್ರತಿಪಾದನೆಗೆ ಪುರಾವೆ ಅಗತ್ಯವಿರುತ್ತದೆ (ಟೆಸ್ಟ್ ಅಥವಾ ಜೀವಂತ ಟೆಸ್ಟ್).
- **ಪ್ರತಿ ಗೇಟ್ಗೆ ತ್ರೈಮಾಸಿಕ ROI ಪರಿಶೀಲನೆ** (ಪ್ರತಿಫಲ ನೀಡದವುಗಳನ್ನು ತೆಗೆದುಹಾಕಿ/ಹಣಕಾಸು ನಿಲ್ಲಿಸಿ — ಇದು ಆಯಾಸವನ್ನು ಎದುರಿಸುತ್ತದೆ).
- ನಿಮ್ಮ ಪ್ರಾಜೆಕ್ಟ್ನ ಕಠಿಣ ನಿಯಮಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದ ಗೇಟ್ಗಳಾಗಿ ಉನ್ನತೀಕರಿಸಿ.

### ಅಡ್ಡ-ವ್ಯಾಪಿ ತತ್ವಗಳು (ಸಂಧಾನಕ್ಕೆ ಅವಕಾಶವಿಲ್ಲದವು)

- **ರ್ಯಾಚೆಟ್, ನಿರಪೇಕ್ಷವಲ್ಲ.** ನಿಗದಿತ ಸಂಖ್ಯೆಯ ಬದಲು _ಹಿಂಜರಿತವಾಗದಿರುವುದನ್ನು_ ಗೇಟ್ ಮಾಡಿ (ಶೂನ್ಯ-ನಿರೋಧಕ ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು ಹೊರತುಪಡಿಸಿ).
- **ನಿರಪೇಕ್ಷ ಕನಿಷ್ಠ ಮಿತಿ + ರ್ಯಾಚೆಟ್ ಒಟ್ಟಿಗೆ.** ಕನಿಷ್ಠ ಮಿತಿ ಕುಸಿತವನ್ನು ತಡೆಯುತ್ತದೆ; ರ್ಯಾಚೆಟ್ ನಿಧಾನವಾದ ಸವಕಳಿಯನ್ನು ತಡೆಯುತ್ತದೆ.
- **ವಿನ್ಯಾಸದಲ್ಲೇ Goodhart-ನಿರೋಧಕ.** ಪ್ರತಿಯೊಂದು ಗುರಿ ಮೆಟ್ರಿಕ್ಗೆ ಸಮತೋಲಕ ಅಗತ್ಯವಿದೆ (ಕವರೇಜ್ ⇒ ಮ್ಯೂಟೇಶನ್ + ಮರೆಮಾಚುವಿಕೆ-ನಿರೋಧಕ; ಕಠಿಣ ಕೋಡ್ನ ಪರೀಕ್ಷೆಯನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸಲು ಪ್ರತಿ-ಮಾಡ್ಯೂಲ್ ಕನಿಷ್ಠ ಮಿತಿಗಳು).
- **ಸಮರ್ಪಕವಾಗಿ ಬಿಟ್ಟುಬಿಡಿ.** ಲಭ್ಯವಿಲ್ಲದ ಮೂಲಸೌಕರ್ಯ ಎಂದಿಗೂ ತಡೆಯುವುದಿಲ್ಲ; ನಿಜವಾದ ಹಿಂಜರಿತ ಮಾತ್ರ ತಡೆಯುತ್ತದೆ.
- **ದುಬಾರಿ ಮೆಟ್ರಿಕ್ಗಳಿಗೆ `dedicatedGate`.** ಬಾಹ್ಯ ಬೈನರಿ ಅಗತ್ಯವಿರುವ ಮೆಟ್ರಿಕ್ಗಳು ಸಮಕಾಲಿಕ ಕೇಂದ್ರ ರ್ಯಾಚೆಟ್ನ ಹೊರಗೆ, ತಮ್ಮದೇ ಸ್ಕ್ರಿಪ್ಟ್ ಅನ್ನು (ಬಿಟ್ಟುಬಿಡುವಿಕೆಯೊಂದಿಗೆ) ಪಡೆಯುತ್ತವೆ.
- **ಮರ್ಜ್ ನಡೆಯುವ ಸ್ಥಳದಲ್ಲೇ ಗೇಟ್ ಮಾಡಿ.** ವೇಗದ ಗೇಟ್ ಮತ್ತು ನಿಜವಾದ ಮರ್ಜ್ ನಡುವೆ ಅಂತರವನ್ನು ಬಿಡಬೇಡಿ (ವೇಗದ-ಗೇಟ್ಗಳ ವಿಭಜನೆಯಿಂದ ಕಲಿತ ಪಾಠ).
- **ಕಡಿಮೆ ಸಂಖ್ಯೆಯ, ಉತ್ತಮವಾಗಿ ಆಯ್ಕೆಮಾಡಿದ ತಡೆಯುವ ಗೇಟ್ಗಳು.** Sonar/DORA: ಅತಿಯಾದ ಷರತ್ತುಗಳು = ಆಯಾಸ. ತಡೆಯುವ ಗೇಟ್ಗಳ ಗೋಡೆಯ ಬದಲು ಸಲಹಾತ್ಮಕ + ರ್ಯಾಚೆಟ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ.

## ಭಾಗ 5 — ಶಿಫಾರಸು ಮಾಡಲಾದ ಸುಧಾರಣೆಗಳು (ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ, ಹೊಂದಾಣಿಕೆಯಾಗುವಂತೆ)

**P0 — ಅತ್ಯಧಿಕ ROI, ಬಹುತೇಕ ಸಿದ್ಧವಾಗಿದೆ**

1. **ಮ್ಯೂಟೇಶನ್ ಸ್ಕೋರ್ ರ್ಯಾಚೆಟ್** (1ನೇ ರಾತ್ರಿಯ Stryker ಮೌಲ್ಯಗಳನ್ನು ಉತ್ಪಾದಿಸಿದ ನಂತರ). ಕವರೇಜ್-Goodhart ವಿರುದ್ಧದ ಪ್ರಮುಖ ಪ್ರತಿವಿಷ; ~90% ಪೂರ್ಣಗೊಂಡಿದೆ.
2. **ಉಳಿದಿರುವ fast-gates ಲೋಪವನ್ನು ಮುಚ್ಚಿ** — `quality.yml` ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ನ
   ಸಲಹಾತ್ಮಕ ವಾರದ ನಂತರ ಅದನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸಿ ಮತ್ತು ನಿರ್ಧಾರಾತ್ಮಕವಾದ release-PR-only ಪರಿಶೀಲನೆಗಳನ್ನು PR→release ಪಥಕ್ಕೆ ಸ್ಥಳಾಂತರಿಸುವುದನ್ನು ಮುಂದುವರಿಸಿ.
3. **`main` ಮೇಲೆ branch-protection** (ಮಾಲೀಕರ ಸೆಟ್ಟಿಂಗ್) — Scorecard ಅನ್ನು ಹೆಚ್ಚಿಸುತ್ತದೆ, DSOMM ಅಂತರವನ್ನು ಮುಚ್ಚುತ್ತದೆ.

**P1 — ಮೌಲ್ಯಯುತ** 4. **osv/oasdiff → ಸರಿಯಾದ ವ್ಯಾಪ್ತಿಯೊಂದಿಗೆ ನಿರ್ಬಂಧಿಸುವಂತೆ** — osv ಕೇವಲ CRITICAL+fixable (Trivy ರೀತಿಯ ಎರಡು-ಹಂತದ ವಿಧಾನ); oasdiff breaking-changes ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ. 5. **`require-tighten` → ನಿರ್ಬಂಧಿಸುವಂತೆ** (ಚಕ್ರದ ಅಂತ್ಯದಲ್ಲಿ) — ಮೆಟ್ರಿಕ್ ಸುಧಾರಣೆಗಳನ್ನು ಸ್ಥಿರಗೊಳಿಸುತ್ತದೆ. 6. **`ci-summary` ನಲ್ಲಿ ಪ್ರತಿ-gate ಗೆ ROI/ಸಮಯ ಪರಿಶೀಲನೆ** — ನಿಧಾನವಾದ/ಕಡಿಮೆ-ಮೌಲ್ಯದ gates ಅನ್ನು ಗುರುತಿಸಿ ತೆಗೆದುಹಾಕಿ.

**P2 — ಕ್ರಮೇಣ ಕಡಿಮೆಯಾಗುವ ಲಾಭಗಳು** 7. **SLSA L3** — L2 ನಿಂದ ಮೇಲಕ್ಕೆ ಹೋಗಲು ಬಯಸಿದರೆ ಹರ್ಮೆಟಿಕ್/ಪುನರುತ್ಪಾದಿಸಬಹುದಾದ builder (GitHub SLSA generator). 8. **ಕಮಿಟ್ ಮಾಡಲಾದ CodeQL config + ಆವೃತ್ತಿಗೊಳಿಸಿದ semgrep** — ಹೆಚ್ಚಿನ ನಿಯಂತ್ರಣ/ಪುನರುತ್ಪಾದನೀಯತೆ. 9. **ಪ್ರತಿ-PR DAST smoke** — ಅತ್ಯಧಿಕ-ಅಪಾಯದ endpoints ಮೇಲೆ schemathesis/promptfoo ನ ವೇಗದ ಉಪಸಮೂಹ (ಕೇವಲ ರಾತ್ರಿಯಷ್ಟೇ ಅಲ್ಲ). 10. **ಅಸ್ಥಿರತೆ dashboard + DORA metrics** — gates ವೇಗವನ್ನು ಕುಗ್ಗಿಸುತ್ತಿಲ್ಲವೆಂದು ಖಚಿತಪಡಿಸಿ.

  ಪರೀಕ್ಷೆಗಳು CI ನಲ್ಲಿನ server timeout/cascade (env) ಕಾರಣದಿಂದ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ, logic ನಿಂದಲ್ಲ. ಇವುಗಳನ್ನು
  `known-flaky` (issue ಸಹಿತ quarantine ಮಾಡಲಾದವು) ಎಂದು ಗುರುತಿಸಿ, ಇದರಿಂದ release-PR ನ red **ನೈಜ signals ಮಾತ್ರ** ಆಗಿರುತ್ತದೆ ಮತ್ತು
  ಮಧ್ಯದಲ್ಲಿರುವ ನಿರ್ಧಾರಾತ್ಮಕ ರಿಗ್ರೆಷನ್ಗಳನ್ನು ಮರೆಮಾಡುವ noise ಆಗಿರುವುದಿಲ್ಲ.

**ತತ್ವ:** _merge ನಡೆಯುವ ಸ್ಥಳದಲ್ಲೇ gate ಚಲಾಯಿಸಬೇಕು_ ("Cross-cutting principles" ನಲ್ಲಿ ಈಗಾಗಲೇ ಇದೆ).
v3.8.27 ಘಟನೆ ಇದು ಕೇವಲ lint/typecheck ಗೆ ಮಾತ್ರವಲ್ಲ, **ನಿರ್ಧಾರಾತ್ಮಕ ಪರೀಕ್ಷಾ ಪದರಕ್ಕೂ** ಅನ್ವಯಿಸುತ್ತದೆ ಎಂಬುದನ್ನು ತೋರಿಸುತ್ತದೆ —
ಇಲ್ಲದಿದ್ದರೆ ಹಳೆಯದಾದ ಪರೀಕ್ಷೆಗಳು + ನಷ್ಟಕಾರಿಯಾದ modularization ನ ತಾಂತ್ರಿಕ ಸಾಲವು PR→main ನಲ್ಲಿ, ಗುಂಪಾಗಿ ಮತ್ತು
ಅತ್ಯಂತ ಕೆಟ್ಟ ಕ್ಷಣದಲ್ಲಿ ಮಾತ್ರ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತದೆ.
