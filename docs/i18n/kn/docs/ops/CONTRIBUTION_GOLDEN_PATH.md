ಪುಲ್ ರಿಕ್ವೆಸ್ಟ್ಗಾಗಿ ಅತ್ಯಂತ ಚಿಕ್ಕದಾದ ವಿಶ್ವಾಸಾರ್ಹ ಡೆವಲಪ್ಮೆಂಟ್ ಲೂಪ್ ಅನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಈ ಮಾರ್ಗದರ್ಶಿಯನ್ನು ಬಳಸಿ. ಇದು ಕೆಳಗೆ ಲಿಂಕ್ ಮಾಡಲಾದ, ನಿರ್ದಿಷ್ಟ ಕ್ಷೇತ್ರಕ್ಕೆ ಸಂಬಂಧಿಸಿದ ಆರ್ಕಿಟೆಕ್ಚರ್ ಮತ್ತು ಭದ್ರತಾ ದಸ್ತಾವೇಜುಗಳನ್ನು
ಬದಲಿಸುವುದಿಲ್ಲ; ಇದು ಪ್ರತಿಯೊಂದು ಸಾಮಾನ್ಯ ಬದಲಾವಣೆಯ ಪ್ರಕಾರವನ್ನು ಅದರ ಒಪ್ಪಂದಗಳು, ಕೇಂದ್ರೀಕೃತ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು CI ವ್ಯಾಪ್ತಿಯೊಂದಿಗೆ ಸಂಪರ್ಕಿಸುತ್ತದೆ.

## ಪ್ರತಿಯೊಂದು ಬದಲಾವಣೆಯೂ ಅನುಸರಿಸುವ ಮಾರ್ಗ

1. **ಎಡಿಟ್ ಮಾಡುವ ಮೊದಲು ಮೂಲ ಬ್ರಾಂಚ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ.** ಅತ್ಯುನ್ನತ ಸಕ್ರಿಯ `release/v*` ಬ್ರಾಂಚ್ ಅನ್ನು ಕಂಡುಹಿಡಿದು, ಅದರ
   ತುದಿಯಿಂದ ಬ್ರಾಂಚ್ ರಚಿಸಿ. `main` ಅನ್ನು ಅಲ್ಲ, ಆ ಬ್ರಾಂಚ್ ಅನ್ನು ಗುರಿಯಾಗಿಸಿ. ರಿಲೀಸ್ ಫ್ರೀಜ್ ಸಕ್ರಿಯವಾಗಿದ್ದರೆ, ಫ್ರೀಜ್ ಮಾಡಲಾದ
   ಬ್ರಾಂಚ್ ಅನ್ನು ಗುರಿಯಾಗಿಸಬೇಡಿ; [Branching & Release Model](BRANCHING_MODEL.md) ನಲ್ಲಿ ವಿವರಿಸಿರುವ
   ಮುಂದಿನ ಸಕ್ರಿಯ ಚಕ್ರವನ್ನು ಬಳಸಿ.
2. **ಒಪ್ಪಂದಗಳನ್ನು ಹೆಸರಿಸಿ.** ಬದಲಾವಣೆಯಿಂದ ಪರಿಣಾಮಗೊಳ್ಳುವ ಪ್ರತಿಯೊಂದು ಕ್ಯಾಟಲಾಗ್, ಸ್ಕೀಮಾ, ರಚಿಸಲಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್, ಸಾರ್ವಜನಿಕ API ಅಥವಾ ಬಳಕೆದಾರ
   ಇಂಟರ್ಫೇಸ್ ಅನ್ನು ಗುರುತಿಸಿ. ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಕನಿಷ್ಠ ಆರಂಭಿಕ ಸಮೂಹವನ್ನು ನೀಡುತ್ತದೆ.
3. **ಕೇಂದ್ರೀಕೃತ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ ಅಥವಾ ನವೀಕರಿಸಿ.** `src/`, `open-sse/`, `electron/`, ಅಥವಾ
   `bin/` ನಲ್ಲಿನ ಪ್ರೊಡಕ್ಷನ್ ಬದಲಾವಣೆಗಳಿಗೆ ಅದೇ PR ನಲ್ಲಿ ಸ್ವಯಂಚಾಲಿತ ಪರೀಕ್ಷೆಯ ಅಗತ್ಯವಿದೆ. ವರ್ತನೆಯನ್ನು ಸಾಬೀತುಪಡಿಸುವ ಅತ್ಯಂತ ಚಿಕ್ಕ ಪರೀಕ್ಷಾ ಫೈಲ್ಗಳನ್ನು
   ಚಲಾಯಿಸಿ, ನಂತರ ಪಟ್ಟಿ ಮಾಡಲಾದ ಕೇಂದ್ರೀಕೃತ ಗೇಟ್ಗಳನ್ನು ಚಲಾಯಿಸಿ.
4. **ವಿಸ್ತೃತ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು CI ಚಲಾಯಿಸಲು ಬಿಡಿ.** ಸಂಪೂರ್ಣ ಯುನಿಟ್ ಶಾರ್ಡ್ಗಳು, Vitest, ಕವರೇಜ್ ರ್ಯಾಚೆಟ್ ಮತ್ತು
   ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ ಅನ್ನು PR ನಲ್ಲಿ ಚಲಾಯಿಸಲಾಗುತ್ತದೆ. ಕೇಂದ್ರೀಕೃತ ವೈಫಲ್ಯವು ವ್ಯಾಪಕ ಪರಿಣಾಮವನ್ನು ಸೂಚಿಸಿದಾಗ ಅಥವಾ ಬದಲಾವಣೆಯು ಹಲವಾರು ಉಪವ್ಯವಸ್ಥೆಗಳನ್ನು ವ್ಯಾಪಿಸಿದಾಗ ಮಾತ್ರ
   ವಿಸ್ತೃತ ಸೂಟ್ ಅನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಿ.
5. **ವಿಮರ್ಶೆಗೆ ಮೊದಲು ಸಮನ್ವಯಗೊಳಿಸಿ.** ಸಕ್ರಿಯ ಮೂಲ ಬ್ರಾಂಚ್ ಅನ್ನು ಫೆಚ್ ಮಾಡಿ, ಅದರ ಹೊಸ ಕಮಿಟ್ಗಳನ್ನು ಮತ್ತು ಅದಕ್ಕೆ ಹೋಲಿಸಿದ ನಿಮ್ಮ ಡಿಫ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ,
   ನಂತರ ಕೊಡುಗೆದಾರರ ವರ್ಕ್ಫ್ಲೋ ಪ್ರಕಾರ ಮೂಲ ಬ್ರಾಂಚ್ ಅನ್ನು ರೀಬೇಸ್ ಅಥವಾ ಮರ್ಜ್ ಮಾಡಿ. ರಚಿಸಲಾದ ಫೈಲ್
   ಮತ್ತು ಕ್ಯಾಟಲಾಗ್ ಸಂಘರ್ಷಗಳನ್ನು ಅವುಗಳ ಮೂಲದಿಂದ ಪರಿಹರಿಸಿ, ಅವುಗಳನ್ನು ಮರುರಚಿಸಿ, ಕೇಂದ್ರೀಕೃತ ಲೂಪ್ ಅನ್ನು ಪುನಃ ಚಲಾಯಿಸಿ ಮತ್ತು
   PR ಇನ್ನೂ ಸಕ್ರಿಯ ರಿಲೀಸ್ ಬ್ರಾಂಚ್ ಅನ್ನೇ ಗುರಿಯಾಗಿಸಿದೆ ಎಂಬುದನ್ನು ದೃಢೀಕರಿಸಿ.
6. **ಸಾಕ್ಷ್ಯವನ್ನು ದಾಖಲಿಸಿ.** PR ಟೆಂಪ್ಲೇಟ್ನಲ್ಲಿ, ಚಲಾಯಿಸಿದ ಕಮಾಂಡ್ಗಳು, ಸೇರಿಸಿದ ಅಥವಾ ಬದಲಾಯಿಸಿದ ಪ್ರತಿಯೊಂದು ಪರೀಕ್ಷಾ ಫೈಲ್,
   ಮೈಗ್ರೇಶನ್ಗಳು ಅಥವಾ ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ಗಳು ಮತ್ತು ಇನ್ನೂ ಬಾಕಿಯಿರುವ ಯಾವುದೇ CI-ಮಾತ್ರದ ಮೌಲ್ಯಮಾಪನವನ್ನು ಪಟ್ಟಿ ಮಾಡಿ.

## ಬದಲಾವಣೆಯ ಪ್ರಕಾರದ ಆದರ್ಶ ಮಾರ್ಗಗಳು

ಕೆಳಗಿನ ಕಮಾಂಡ್ಗಳು ಕನಿಷ್ಠ ಕೇಂದ್ರೀಕೃತ ಪರಿಶೀಲನೆಗಳಾಗಿವೆ; ನೀವು ಬದಲಾಯಿಸಿದ
ವರ್ತನೆಯನ್ನು ನೇರವಾಗಿ ಒಳಗೊಳ್ಳುವ ಪರೀಕ್ಷೆಯನ್ನು ಬಿಟ್ಟುಬಿಡಲು ಅವು ಅನುಮತಿಯಲ್ಲ.

### ಪೂರೈಕೆದಾರ

**ಒಪ್ಪಂದಗಳು**

- `src/shared/constants/providers/` ನಲ್ಲಿನ ಪೂರೈಕೆದಾರ ವ್ಯಾಖ್ಯಾನ ಮತ್ತು
  `src/shared/constants/providers.ts` ನಲ್ಲಿನ ಅದರ ಸಂಯೋಜನೆ.
- `open-sse/config/providerRegistry.ts` ಅಥವಾ ಅದರಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾದ ರಿಜಿಸ್ಟ್ರಿ ಫೈಲ್ಗಳಲ್ಲಿನ ಮಾಡೆಲ್ಗಳು ಮತ್ತು ಸಾಮರ್ಥ್ಯಗಳು.
- ಅನ್ವಯಿಸಿದಾಗ ಎಕ್ಸಿಕ್ಯೂಟರ್/ಟ್ರಾನ್ಸ್ಲೇಟರ್ ಆಯ್ಕೆ, OAuth ಅಥವಾ API-ಕೀ ಕಾನ್ಫಿಗರೇಶನ್, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಅಸೆಟ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ
  ಪೂರೈಕೆದಾರ ಉಲ್ಲೇಖ.
- ಸಾರ್ವಜನಿಕ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು `resolvePublicCred()` ಅನ್ನು ಬಳಸಬೇಕು; ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳು ಹಂಚಿಕೊಂಡ ಸ್ಯಾನಿಟೈಸ್ ಮಾಡಿದ
  ದೋಷ ಸಹಾಯಕಗಳನ್ನು ಬಳಸಬೇಕು. `docs/security/PUBLIC_CREDS.md` (git; `/docs` ಗೆ ಕಂಪೈಲ್ ಮಾಡಲಾಗಿಲ್ಲ) ಮತ್ತು
  [ದೋಷ ಸ್ಯಾನಿಟೈಸೇಶನ್](../security/ERROR_SANITIZATION.md) ನೋಡಿ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # ಕ್ಯಾಟಲಾಗ್ ಬದಲಾದಾಗ; ರಚಿಸಲಾದ ಡಿಫ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ
npm run lint
```

ಪರಿಣಾಮಗೊಳ್ಳುವ ಪ್ರತಿಯೊಂದು ವಿನಂತಿ ಕುಟುಂಬವನ್ನೂ ಪರೀಕ್ಷಿಸಿ: ಚಾಟ್, Responses, ಚಿತ್ರಗಳು, ಎಂಬೆಡಿಂಗ್ಗಳು, ಆಡಿಯೊ ಅಥವಾ ವೀಡಿಯೊ.
ರಚಿಸಲಾದ ಕ್ಯಾಟಲಾಗ್ ಮತ್ತು ಗೋಲ್ಡನ್ ಡಿಫ್ಗಳನ್ನು ಒಪ್ಪಂದದ ಬದಲಾವಣೆಗಳಾಗಿ ಪರಿಶೀಲಿಸಿ; ಅವುಗಳನ್ನು ಪರಿಶೀಲಿಸದೆ ಸ್ವೀಕರಿಸಬೇಡಿ.

### ರೂಟಿಂಗ್

**ಒಪ್ಪಂದಗಳು**

- `src/shared/constants/routingStrategies.ts` ನಲ್ಲಿನ ಸಾರ್ವಜನಿಕ ಸ್ಟ್ರಾಟಜಿ ಮೌಲ್ಯಗಳು ಮತ್ತು UI ಮೆಟಾಡೇಟಾ.
- `open-sse/services/combo.ts` ಮತ್ತು `open-sse/services/combo/` ಅಡಿಯಲ್ಲಿನ ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು ಕ್ರಮಗೊಳಿಸುವಿಕೆ.
- ಕಾಂಬೊ ಸ್ಕೀಮಾಗಳು, ಪರ್ಸಿಸ್ಟೆನ್ಸ್, ರೆಸಿಲಿಯನ್ಸ್ ಸ್ಥಿತಿ, ಮಾಡೆಲ್ ಸಾಮರ್ಥ್ಯಗಳು ಮತ್ತು API/UI ನಿಯಂತ್ರಣಗಳು.
- ವರ್ತನೆ ಬದಲಾದಾಗ [Auto-Combo Engine](../routing/AUTO-COMBO.md) ಮತ್ತು ರೆಸಿಲಿಯನ್ಸ್ ದಸ್ತಾವೇಜೀಕರಣ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # ಸ್ಟ್ರಾಟಜಿ ಅಥವಾ ಡಿಸ್ಪ್ಯಾಚ್ ಬದಲಾವಣೆಗಳು
npm run check:known-symbols      # ಸ್ಟ್ರಾಟಜಿ ನೋಂದಣಿ ಬದಲಾವಣೆಗಳು
```

ಸ್ಥಳೀಯವಾಗಿ ನಿರ್ಧಾರಾತ್ಮಕ ಮಾಕ್ ಮಾಡಿದ ಅಪ್ಸ್ಟ್ರೀಮ್ ಪರೀಕ್ಷೆಗಳನ್ನು ಬಳಸಿ. ಲೈವ್ ಕಾಂಬೊ ಸ್ಮೋಕ್ ಪರೀಕ್ಷೆಗಳಿಗೆ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು ಅಗತ್ಯವಿದ್ದು,
ಅವು ಕೈಯಾರೆ ನಡೆಸಬೇಕಾದವು; CI ಗೆ ಪರ್ಯಾಯಗಳಲ್ಲ.

### UI / UX

**ಒಪ್ಪಂದಗಳು**

- `src/app/` ಮತ್ತು `src/shared/components/` ಅಡಿಯಲ್ಲಿನ Next.js ರೂಟ್/ಪುಟ ಮತ್ತು
  ಹಂಚಿಕೊಂಡ ಕಾಂಪೊನೆಂಟ್ ಗಡಿಗಳು.
- API ಪ್ರತಿಕ್ರಿಯೆಯ ಆಕಾರಗಳು, ಲೋಡಿಂಗ್/ಖಾಲಿ/ದೋಷ ಸ್ಥಿತಿಗಳು, ಕೀಬೋರ್ಡ್ ಮತ್ತು ಸ್ಕ್ರೀನ್-ರೀಡರ್ ವರ್ತನೆ,
  ರೆಸ್ಪಾನ್ಸಿವ್ ಲೇಔಟ್, ಥೀಮಿಂಗ್ ಮತ್ತು ಲೋಕೇಲ್ ವಿಸ್ತರಣೆ.
- `src/i18n/messages/en.json` ನಲ್ಲಿನ ಇಂಗ್ಲಿಷ್ UI ಮೂಲ ಸ್ಟ್ರಿಂಗ್ಗಳು; ಬಳಕೆದಾರರಿಗೆ ಕಾಣಿಸುವ ಹೊಸ ಪಠ್ಯವನ್ನು ಹಾರ್ಡ್-ಕೋಡ್ ಮಾಡಬೇಡಿ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash

npm run check:dashboard-typecheck
npm run lint
```

ಇಂಟರ್ಯಾಕ್ಷನ್ ಅಥವಾ ದೃಶ್ಯ ಬದಲಾವಣೆಗಳಿಗಾಗಿ ಆ್ಯಪ್ ಅನ್ನು ಚಲಾಯಿಸಿ ಮತ್ತು ಕಿರಿದಾದ ಹಾಗೂ ಅಗಲವಾದ ಎರಡೂ ವ್ಯೂಪೋರ್ಟ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ. CI
ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ ಮತ್ತು ವಿಸ್ತೃತ ಸೂಟ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ; ದೃಶ್ಯ ವರ್ತನೆಗೆ ಇನ್ನೂ ಬದಲಾವಣೆಗೆ ಸೂಕ್ತವಾದ ಕೇಂದ್ರೀಕೃತ ಕಾಂಪೊನೆಂಟ್, Playwright,
ಅಥವಾ ದಾಖಲಿಸಲಾದ ಕೈಯಾರೆ ಪರಿಶೀಲನೆ ಅಗತ್ಯವಿದೆ.

### i18n

**ಒಪ್ಪಂದಗಳು**

- `src/i18n/messages/en.json` UI ಮೂಲವಾಗಿದೆ; `config/i18n.json` ಲೋಕೇಲ್ ಮೂಲವಾಗಿದೆ.
- CLI ಕ್ಯಾಟಲಾಗ್ಗಳು `bin/cli/locales/` ಅಡಿಯಲ್ಲಿ ಪ್ರತ್ಯೇಕವಾಗಿ ಇರುತ್ತವೆ.
- ICU ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ಗಳು ಮತ್ತು ಟ್ಯಾಗ್ಗಳನ್ನು ಯಥಾವತ್ತಾಗಿ ಉಳಿಸಿ. ಉತ್ಪನ್ನ/ಪೂರೈಕೆದಾರ/ಮಾಡೆಲ್ ಹೆಸರುಗಳು,
  ಪ್ರೋಟೋಕಾಲ್ ಮತ್ತು ಹೆಡರ್ ಹೆಸರುಗಳು, ಕಮಾಂಡ್ಗಳು, ಕೋಡ್/JSON ಐಡೆಂಟಿಫೈಯರ್ಗಳು, URLಗಳು, ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್ಗಳು ಅಥವಾ
  `OmniRoute`, `OAuth`, `MCP`, ಮತ್ತು `A2A` ನಂತಹ ಸಂರಕ್ಷಿತ ಪದಗಳನ್ನು ಅನುವಾದಿಸಬೇಡಿ. ಪ್ರಸ್ತುತ ಮೂಲ ಪಟ್ಟಿಯು
  `scripts/i18n/glossary/protected-terms.json` ಆಗಿದೆ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI ಸ್ಟ್ರಿಂಗ್ಗಳು/ಕ್ಯಾಟಲಾಗ್ಗಳು ಬದಲಾದಾಗ
npm run lint
```

ಇದು ಈಗಿರುವ ವ್ಯವಸ್ಥೆಗೆ ಮಾರ್ಗದರ್ಶನವಾಗಿದೆ, ಅದರ ಟೂಲಿಂಗ್ ಅಥವಾ ಕೀ ಮಾಡೆಲ್ ಅನ್ನು ವಿಸ್ತರಿಸುವ ಆಹ್ವಾನವಲ್ಲ.
ಬದಲಿ ವ್ಯವಸ್ಥೆಯನ್ನು ವಿನ್ಯಾಸಗೊಳಿಸುತ್ತಿರುವಾಗ i18n ಪ್ಯಾಚ್ಗಳನ್ನು ನಿಖರ ಮತ್ತು ಸೀಮಿತವಾಗಿರಿಸಿ. ಟಾಸ್ಕ್ ಸ್ಪಷ್ಟವಾಗಿ ರಚಿಸಲಾದ ಅನುವಾದಗಳನ್ನು ಅಗತ್ಯಪಡಿಸದಿದ್ದರೆ ಮತ್ತು
ಫಲಿತಾಂಶದ ಡಿಫ್ ಅನ್ನು ನೀವು ಪರಿಶೀಲಿಸದಿದ್ದರೆ, ಬಾಹ್ಯ ಸೇವೆಗಳನ್ನು ಕರೆಯುವ ಅನುವಾದ ಕಮಾಂಡ್ಗಳನ್ನು ಚಲಾಯಿಸಬೇಡಿ.

### CLI

**ಒಪ್ಪಂದಗಳು**

- `bin/cli/` ನಲ್ಲಿನ ಸಾರ್ವಜನಿಕ ಕಮಾಂಡ್ಗಳು ಮತ್ತು ಫ್ಲ್ಯಾಗ್ಗಳು, ರಚಿಸಲಾದ API ಕಮಾಂಡ್ಗಳು, ನಿರ್ಗಮನ ಕೋಡ್ಗಳು, stdout/stderr ಮತ್ತು
  JSON ಔಟ್ಪುಟ್ ಆಕಾರಗಳು, ಕಾನ್ಫಿಗ್/ಎನ್ವಿರಾನ್ಮೆಂಟ್ ನಡವಳಿಕೆ ಹಾಗೂ ಪ್ಯಾಕೇಜ್ ಮಾಡಲಾದ ಫೈಲ್ಗಳು.
- CLI ಬಳಕೆದಾರರಿಗೆ ಗೋಚರಿಸುವ ಸ್ಟ್ರಿಂಗ್ಗಳು CLI i18n ಲೇಯರ್ ಅನ್ನು ಬಳಸಬೇಕು ಮತ್ತು `en`/`pt-BR` ಕ್ಯಾಟಲಾಗ್ಗಳನ್ನು ಸಮನ್ವಯದಲ್ಲಿರಿಸಬೇಕು.
- ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ಆಗಿ Node ಅನ್ನು ಮತ್ತು ಪ್ರಕಟಿತ ಬೈನರಿ ಒಪ್ಪಂದವನ್ನು ಸಂರಕ್ಷಿಸಿ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # ರಚಿಸಲಾದ/ಬಂಡಲ್ ಮಾಡಲಾದ CLI ಬದಲಾವಣೆಗಳು
npm run check:pack-policy     # ಪ್ಯಾಕೇಜ್ ಮೇಲ್ಮೈ ಬದಲಾವಣೆಗಳು
npm run lint
```

ನಡವಳಿಕೆಯು ಪಾರ್ಸಿಂಗ್, ಫೈಲ್ಗಳು ಅಥವಾ ನಿರ್ಗಮನ ಸ್ಥಿತಿಯನ್ನು ಅವಲಂಬಿಸಿದಾಗ, ತಾತ್ಕಾಲಿಕ ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯಲ್ಲಿ ನಿಖರವಾದ ಕಮಾಂಡ್ ಅನ್ನು ಬಳಸಿ.
CI ವಿಸ್ತೃತ ಪ್ಯಾಕೇಜ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಮತ್ತು ಎಕೋಸಿಸ್ಟಮ್ ಪರಿಶೀಲನೆಗಳನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.

### ಡೇಟಾಬೇಸ್

**ಒಪ್ಪಂದಗಳು**

- `src/lib/db/` ಅಡಿಯಲ್ಲಿರುವ ಡೊಮೇನ್ ಮಾಡ್ಯೂಲ್ಗಳು; ನಿರ್ದಿಷ್ಟ ಮಾಡ್ಯೂಲ್ಗಳನ್ನು ನೇರವಾಗಿ ಇಂಪೋರ್ಟ್ ಮಾಡಿ (ಹಳೆಯ `localDb.ts` ಮರು-ಎಕ್ಸ್ಪೋರ್ಟ್ ಲೇಯರ್ ಅನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ).
- `src/lib/db/migrations/` ಅಡಿಯಲ್ಲಿರುವ ಸಂಖ್ಯೆಯುಳ್ಳ, ಐಡೆಂಪೊಟೆಂಟ್ SQL ಮೈಗ್ರೇಶನ್ಗಳು, ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಸುರಕ್ಷತೆ, ಅಪ್ಗ್ರೇಡ್
  ನಡವಳಿಕೆ, ಇಂಡೆಕ್ಸ್ಗಳು ಮತ್ತು ಸ್ಕೀಮಾದಿಂದ ಪ್ರಭಾವಿತವಾಗುವ ಪ್ರತಿಯೊಂದು ಕಾಲರ್.
- ರೂಟ್ಗಳು ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ಗಳು ಎಂದಿಗೂ ನೇರವಾಗಿ raw SQL ಅನ್ನು ನೀಡುವುದಿಲ್ಲ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ಮೈಗ್ರೇಶನ್ ಸೇರಿಸುವಾಗ ಹೊಸ ಡೇಟಾಬೇಸ್ ಮತ್ತು ಹಿಂದಿನ ಸ್ಕೀಮಾದಿಂದ ಅಪ್ಗ್ರೇಡ್—ಎರಡನ್ನೂ ಪರೀಕ್ಷಿಸಿ. ಡೇಟಾಬೇಸ್ ಪರೀಕ್ಷೆಗಳು
ಹ್ಯಾಂಡಲ್ಗಳನ್ನು ಮುಚ್ಚಬೇಕು ಮತ್ತು ಕ್ಲೀನ್ಅಪ್ ಸಮಯದಲ್ಲಿ `resetDbInstance()` ಅನ್ನು ಕರೆ ಮಾಡಬೇಕು. ಬೆಸ್ಟ್-ಎಫರ್ಟ್ Bun ಅಡಾಪ್ಟರ್ ಪಥವು
ಬದಲಾದಾಗ ಮಾತ್ರ `npm run test:bun:db` ಅನ್ನು ಚಲಾಯಿಸಿ; Node ಅಧಿಕೃತವಾಗಿ ಉಳಿಯುತ್ತದೆ.

### ಬಿಲ್ಡ್ / ಡಿಪ್ಲಾಯ್

**ಒಪ್ಪಂದಗಳು**

- ರೂಟ್ ಮತ್ತು ವರ್ಕ್ಸ್ಪೇಸ್ ಮ್ಯಾನಿಫೆಸ್ಟ್ಗಳು/ಲಾಕ್ಫೈಲ್, `scripts/build/`, Next.js ಸ್ಟ್ಯಾಂಡ್ಅಲೋನ್ ಅಸೆಂಬ್ಲಿ, `dist/`
  ಪ್ಯಾಕೇಜ್ ವಿಷಯಗಳು, Electron ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಮೆಟಾಡೇಟಾ, CI ವರ್ಕ್ಫ್ಲೋಗಳು ಮತ್ತು ಡಿಪ್ಲಾಯ್ ಸೆಂಟಿನೆಲ್ಗಳು.
- ಬೆಂಬಲಿತ Node ಶ್ರೇಣಿಗಳು ಮತ್ತು `CLAUDE.md` ನಲ್ಲಿನ ಅನುಮತಿ-ಪಟ್ಟಿಗೆ ಸೇರಿಸಲಾದ Bun ಬಳಕೆ ಅಚಲವಾಗಿರಬೇಕು.
- ಬಿಲ್ಡ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು ಟ್ರ್ಯಾಕ್ ಮಾಡದೆ ಉಳಿಯಬೇಕು; ಡಿಪೆಂಡೆನ್ಸಿ, ಲೈಸೆನ್ಸ್, ವರ್ಕ್ಫ್ಲೋ ಮತ್ತು ಪ್ಯಾಕೇಜ್ ನೀತಿಗಳು ಅನ್ವಯಿಸುತ್ತವೆ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ಡಿಪೆಂಡೆನ್ಸಿ ಅಥವಾ ಲಾಕ್ಫೈಲ್ ಬದಲಾವಣೆಗಳು
npm run check:pack-policy      # ಪ್ರಕಟಿತ ಪ್ಯಾಕೇಜ್ ಮೇಲ್ಮೈ ಬದಲಾವಣೆಗಳು
npm run lint
```

ಬದಲಾವಣೆಯು ಕಂಪೈಲೇಶನ್, ಸ್ಟ್ಯಾಂಡ್ಅಲೋನ್ ಅಸೆಂಬ್ಲಿ, ಅಸೆಟ್ಗಳು ಅಥವಾ ರನ್ಟೈಮ್ ಬಂಡ್ಲಿಂಗ್ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರಿದಾಗ ಮಾತ್ರ
ಸ್ಥಳೀಯವಾಗಿ `npm run build` ಅನ್ನು ಬಳಸಿ. ಬಿಡುಗಡೆ/ಡಿಪ್ಲಾಯ್ ಮೌಲ್ಯೀಕರಣಕ್ಕಾಗಿ ಮಾತ್ರ `npm run build:release` ಅನ್ನು ಬಳಸಿ. CI ಬಿಲ್ಡ್
ಅಂತಿಮ ಕ್ರಾಸ್-ಪ್ಲಾಟ್ಫಾರ್ಮ್ ಸಂಕೇತವಾಗಿದೆ; ಪ್ಲಾಟ್ಫಾರ್ಮ್-ನಿರ್ದಿಷ್ಟ Electron ಬದಲಾವಣೆಗಳಿಗೆ ಹೊಂದಿಕೆಯಾಗುವ ಕೇಂದ್ರೀಕೃತ ಬಿಲ್ಡ್
ಅಥವಾ ಸ್ಮೋಕ್ ಪುರಾವೆ ಅಗತ್ಯವಿದೆ.

ಹಸಿರು ಸ್ಥಿತಿಯಲ್ಲಿರುವ ಕೇಂದ್ರೀಕೃತ ಲೂಪ್, ಬದಲಾಯಿಸಲಾದ ಒಪ್ಪಂದದ ಕುರಿತಾದ ಪುರಾವೆಯೇ ಹೊರತು, ಸಂಬಂಧವಿಲ್ಲದ CI ಪರಿಶೀಲನೆಗಳು
ಪಾಸ್ ಆಗುತ್ತವೆ ಎಂಬುದಕ್ಕೆ ಪುರಾವೆಯಲ್ಲ. ಇದಕ್ಕೆ ವಿರುದ್ಧವಾಗಿ, ಪ್ರತಿಯೊಂದು ಸ್ಥಳೀಯ ತಿದ್ದುಪಡಿಯೂ ಸಂಪೂರ್ಣ ರೆಪೊಸಿಟರಿ ಮ್ಯಾಟ್ರಿಕ್ಸ್ಗಾಗಿ ಕಾಯುವಂತೆ ಮಾಡಬೇಡಿ.

## ಸಮನ್ವಯ ಪರಿಶೀಲನಾ ಪಟ್ಟಿ

ವಿಮರ್ಶೆಯನ್ನು ವಿನಂತಿಸುವ ಮೊದಲು:

- PR ಬೇಸ್ ಇನ್ನೂ ಅತ್ಯುನ್ನತ ಸಕ್ರಿಯ `release/v*` ಬ್ರಾಂಚ್ ಆಗಿದೆಯೇ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ.
- ಆ ಬೇಸ್ ಅನ್ನು ಫೆಚ್ ಮಾಡಿ ಮತ್ತು ನೀವು ಬ್ರಾಂಚ್ ಮಾಡಿದ ನಂತರ ಸೇರಿಸಲಾದ ಕಮಿಟ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
- ಆಕಸ್ಮಿಕ ಅಥವಾ ರಚಿಸಲಾದ ಅನಗತ್ಯ ಬದಲಾವಣೆಗಳಿಗಾಗಿ `git diff <active-base>...HEAD` ಅನ್ನು ಪರಿಶೀಲಿಸಿ.
- ಮೂಲವನ್ನು ಅಪ್ಡೇಟ್ ಮಾಡಿ ಮತ್ತು ಔಟ್ಪುಟ್ ಅನ್ನು ಮರುರಚಿಸುವ ಮೂಲಕ ಕ್ಯಾಟಲಾಗ್ ಮತ್ತು ರಚಿಸಲಾದ ಡಾಕ್ಯುಮೆಂಟ್ ಸಂಘರ್ಷಗಳನ್ನು ಪರಿಹರಿಸಿ.
- ಸಮನ್ವಯದ ನಂತರ PR ವಿವರಣೆಯಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾದ ಪ್ರತಿಯೊಂದು ಕೇಂದ್ರೀಕೃತ ಪರೀಕ್ಷೆ/ಗೇಟ್ ಅನ್ನು ಮರುರನ್ ಮಾಡಿ.
- ಬದಲಾದ ಬೇಸ್ಗೆ ಹೊಂದಿಸಲು ಮಾತ್ರ ಎಂದಿಗೂ ಅಸರ್ಟ್ಮೆಂಟ್ಗಳನ್ನು ದುರ್ಬಲಗೊಳಿಸಬೇಡಿ ಅಥವಾ ಅಗತ್ಯ ಪರೀಕ್ಷೆಗಳನ್ನು ಕೈಬಿಡಬೇಡಿ.

ರಿಲೀಸ್-ಫ್ರೀಜ್ ಮತ್ತು ಮರುಗುರಿಪಡಿಸುವ ನಿಯಮಗಳಿಗಾಗಿ,
[ಬ್ರಾಂಚಿಂಗ್ ಮತ್ತು ರಿಲೀಸ್ ಮಾದರಿ](BRANCHING_MODEL.md) ಬಳಸಿ. ಸಂಪೂರ್ಣ CI ಇನ್ವೆಂಟರಿಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳ ಉಲ್ಲೇಖ](../architecture/QUALITY_GATES.md) ಬಳಸಿ.
