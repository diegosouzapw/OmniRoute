ಪುಲ್ ರಿಕ್ವೆಸ್ಟ್ಗಾಗಿ ಅತ್ಯಂತ ಚಿಕ್ಕದಾದ ವಿಶ್ವಾಸಾರ್ಹ ಡೆವಲಪ್ಮೆಂಟ್ ಲೂಪ್ ಅನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಈ ಮಾರ್ಗದರ್ಶಿಯನ್ನು ಬಳಸಿ. ಇದು ಕೆಳಗೆ ಲಿಂಕ್ ಮಾಡಲಾದ
ಕ್ಷೇತ್ರ-ನಿರ್ದಿಷ್ಟ ಆರ್ಕಿಟೆಕ್ಚರ್ ಮತ್ತು ಭದ್ರತಾ ದಾಖಲೆಗಳನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ; ಇದು ಪ್ರತಿಯೊಂದು ಸಾಮಾನ್ಯ
ಬದಲಾವಣೆಯ ಪ್ರಕಾರವನ್ನು ಅದರ ಒಪ್ಪಂದಗಳು, ಕೇಂದ್ರೀಕೃತ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು CI ವ್ಯಾಪ್ತಿಗೆ ಸಂಪರ್ಕಿಸುತ್ತದೆ.

## ಪ್ರತಿಯೊಂದು ಬದಲಾವಣೆಯೂ ಅನುಸರಿಸುವ ಮಾರ್ಗ

1. **ತಿದ್ದುಪಡಿ ಮಾಡುವ ಮೊದಲು ಬೇಸ್ ಅನ್ನು ಆಯ್ಕೆಮಾಡಿ.** ಅತ್ಯುನ್ನತ ಸಕ್ರಿಯ `release/v*` ಬ್ರಾಂಚ್ ಅನ್ನು ಕಂಡುಹಿಡಿದು, ಅದರ
   ತುದಿಯಿಂದ ಬ್ರಾಂಚ್ ರಚಿಸಿ. `main` ಅನ್ನು ಅಲ್ಲ, ಆ ಬ್ರಾಂಚ್ ಅನ್ನು ಗುರಿಯಾಗಿಸಿ. ರಿಲೀಸ್ ಫ್ರೀಜ್ ಸಕ್ರಿಯವಾಗಿದ್ದರೆ, ಫ್ರೀಜ್ ಮಾಡಲಾದ
   ಬ್ರಾಂಚ್ ಅನ್ನು ಗುರಿಯಾಗಿಸಬೇಡಿ;
   [Branching & Release Model](BRANCHING_MODEL.md) ನಲ್ಲಿ ವಿವರಿಸಲಾದ ಮುಂದಿನ ಸಕ್ರಿಯ ಚಕ್ರವನ್ನು ಬಳಸಿ.
2. **ಒಪ್ಪಂದಗಳನ್ನು ಹೆಸರಿಸಿ.** ಬದಲಾವಣೆಯು ಪರಿಣಾಮ ಬೀರುವ ಪ್ರತಿಯೊಂದು ಕ್ಯಾಟಲಾಗ್, ಸ್ಕೀಮಾ, ರಚಿಸಲಾದ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್, ಸಾರ್ವಜನಿಕ API ಅಥವಾ ಬಳಕೆದಾರ
   ಇಂಟರ್ಫೇಸ್ ಅನ್ನು ಗುರುತಿಸಿ. ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಕನಿಷ್ಠ ಆರಂಭಿಕ ಸಮೂಹವನ್ನು ನೀಡುತ್ತದೆ.
3. **ಕೇಂದ್ರೀಕೃತ ಪರೀಕ್ಷೆಗಳನ್ನು ಬರೆಯಿರಿ ಅಥವಾ ನವೀಕರಿಸಿ.** `src/`, `open-sse/`, `electron/`, ಅಥವಾ
   `bin/` ನಲ್ಲಿನ ಪ್ರೊಡಕ್ಷನ್ ಬದಲಾವಣೆಗಳಿಗೆ ಅದೇ PR ನಲ್ಲಿ ಸ್ವಯಂಚಾಲಿತ ಪರೀಕ್ಷೆ ಅಗತ್ಯ. ವರ್ತನೆಯನ್ನು ಸಾಬೀತುಪಡಿಸುವ ಅತ್ಯಂತ ಚಿಕ್ಕ ಪರೀಕ್ಷಾ
   ಫೈಲ್ಗಳನ್ನು ಮೊದಲು ಚಲಾಯಿಸಿ, ನಂತರ ಪಟ್ಟಿ ಮಾಡಲಾದ ಕೇಂದ್ರೀಕೃತ ಗೇಟ್ಗಳನ್ನು ಚಲಾಯಿಸಿ.
4. **ವಿಶಾಲ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಅನ್ನು CI ಚಲಾಯಿಸಲು ಬಿಡಿ.** ಸಂಪೂರ್ಣ ಯುನಿಟ್ ಶಾರ್ಡ್ಗಳು, Vitest, ಕವರೇಜ್ ರ್ಯಾಚೆಟ್ ಮತ್ತು
   ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ PR ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ. ಕೇಂದ್ರೀಕೃತ ವೈಫಲ್ಯವು ವ್ಯಾಪಕ ಪರಿಣಾಮವನ್ನು ಸೂಚಿಸಿದಾಗ ಅಥವಾ ಬದಲಾವಣೆಯು ಹಲವು
   ಉಪವ್ಯವಸ್ಥೆಗಳನ್ನು ವ್ಯಾಪಿಸಿದಾಗ ಮಾತ್ರ ಸ್ಥಳೀಯವಾಗಿ ವಿಶಾಲ ಸೂಟ್ ಅನ್ನು ಚಲಾಯಿಸಿ.
5. **ಪರಿಶೀಲನೆಯ ಮೊದಲು ಸಮನ್ವಯಗೊಳಿಸಿ.** ಸಕ್ರಿಯ ಬೇಸ್ ಅನ್ನು ಫೆಚ್ ಮಾಡಿ, ಅದರ ಹೊಸ ಕಮಿಟ್ಗಳನ್ನು ಮತ್ತು ಅದಕ್ಕೆ ಹೋಲಿಸಿದ ನಿಮ್ಮ ಡಿಫ್ ಅನ್ನು
   ಪರಿಶೀಲಿಸಿ, ನಂತರ ಕೊಡುಗೆದಾರರ ವರ್ಕ್ಫ್ಲೋ ಪ್ರಕಾರ ಬೇಸ್ ಅನ್ನು ರಿಬೇಸ್ ಅಥವಾ ಮರ್ಜ್ ಮಾಡಿ. ರಚಿಸಲಾದ ಫೈಲ್
   ಮತ್ತು ಕ್ಯಾಟಲಾಗ್ ಸಂಘರ್ಷಗಳನ್ನು ಅವುಗಳ ಮೂಲದಿಂದ ಪರಿಹರಿಸಿ, ಅವುಗಳನ್ನು ಮರುರಚಿಸಿ, ಕೇಂದ್ರೀಕೃತ ಲೂಪ್ ಅನ್ನು ಪುನಃ ಚಲಾಯಿಸಿ ಮತ್ತು
   PR ಇನ್ನೂ ಸಕ್ರಿಯ ರಿಲೀಸ್ ಬ್ರಾಂಚ್ ಅನ್ನು ಗುರಿಯಾಗಿಸಿದೆ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ.
6. **ಪುರಾವೆಯನ್ನು ದಾಖಲಿಸಿ.** PR ಟೆಂಪ್ಲೇಟ್ನಲ್ಲಿ ಚಲಾಯಿಸಿದ ಕಮಾಂಡ್ಗಳು, ಸೇರಿಸಲಾದ ಅಥವಾ ಬದಲಾಯಿಸಲಾದ ಪ್ರತಿಯೊಂದು ಪರೀಕ್ಷಾ ಫೈಲ್,
   ಮೈಗ್ರೇಶನ್ಗಳು ಅಥವಾ ಫೀಚರ್ ಫ್ಲ್ಯಾಗ್ಗಳು ಮತ್ತು ಇನ್ನೂ ಬಾಕಿ ಇರುವ ಯಾವುದೇ CI-ಮಾತ್ರ ಮೌಲ್ಯೀಕರಣವನ್ನು ಪಟ್ಟಿ ಮಾಡಿ.

## ಬದಲಾವಣೆಯ ಪ್ರಕಾರದ ಆದರ್ಶ ಮಾರ್ಗಗಳು

ಕೆಳಗಿನ ಕಮಾಂಡ್ಗಳು ಕನಿಷ್ಠ ಕೇಂದ್ರೀಕೃತ ಪರಿಶೀಲನೆಗಳಾಗಿವೆ; ನೀವು ಬದಲಾಯಿಸಿದ
ವರ್ತನೆಯನ್ನು ನೇರವಾಗಿ ಒಳಗೊಳ್ಳುವ ಪರೀಕ್ಷೆಯನ್ನು ಬಿಟ್ಟುಬಿಡಲು ಅವು ಅನುಮತಿಯಲ್ಲ.

### ಪ್ರೊವೈಡರ್

**ಒಪ್ಪಂದಗಳು**

- `src/shared/constants/providers/` ನಲ್ಲಿನ ಪ್ರೊವೈಡರ್ ವ್ಯಾಖ್ಯಾನ ಮತ್ತು
  `src/shared/constants/providers.ts` ನಲ್ಲಿನ ಅದರ ಸಂಯೋಜನೆ.
- `open-sse/config/providerRegistry.ts` ಅಥವಾ ಅದರಿಂದ ಪ್ರತ್ಯೇಕಿಸಲಾದ ರಿಜಿಸ್ಟ್ರಿ ಫೈಲ್ಗಳಲ್ಲಿನ ಮಾಡೆಲ್ಗಳು ಮತ್ತು ಸಾಮರ್ಥ್ಯಗಳು.
- ಅನ್ವಯಿಸುವಲ್ಲಿ ಎಕ್ಸಿಕ್ಯೂಟರ್/ಟ್ರಾನ್ಸ್ಲೇಟರ್ ಆಯ್ಕೆ, OAuth ಅಥವಾ API-ಕೀ ಕಾನ್ಫಿಗರೇಶನ್, ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಅಸೆಟ್ಗಳು ಮತ್ತು ರಚಿಸಲಾದ
  ಪ್ರೊವೈಡರ್ ಉಲ್ಲೇಖ.
- ಸಾರ್ವಜನಿಕ ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳು `resolvePublicCred()` ಅನ್ನು ಬಳಸಬೇಕು; ದೋಷ ಪ್ರತಿಕ್ರಿಯೆಗಳು ಹಂಚಿಕೊಳ್ಳಲಾದ ಸ್ಯಾನಿಟೈಸ್ ಮಾಡಿದ
  ದೋಷ ಸಹಾಯಕಗಳನ್ನು ಬಳಸಬೇಕು. `docs/security/PUBLIC_CREDS.md` (git; `/docs` ಒಳಗೆ ಕಂಪೈಲ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ) ಮತ್ತು
  [ದೋಷ ಸ್ಯಾನಿಟೈಸೇಶನ್](../security/ERROR_SANITIZATION.md) ನೋಡಿ.

**ಕೇಂದ್ರೀಕೃತ ಲೂಪ್**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # ಕ್ಯಾಟಲಾಗ್ ಬದಲಾದಾಗ; ರಚಿಸಲಾದ ಡಿಫ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ
npm run lint
```

ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಪ್ರತಿಯೊಂದು ರಿಕ್ವೆಸ್ಟ್ ಕುಟುಂಬವನ್ನೂ ಪರೀಕ್ಷಿಸಿ: ಚಾಟ್, Responses, ಇಮೇಜ್ಗಳು, ಎಂಬೆಡಿಂಗ್ಗಳು, ಆಡಿಯೊ ಅಥವಾ ವೀಡಿಯೊ.
ರಚಿಸಲಾದ ಕ್ಯಾಟಲಾಗ್ ಮತ್ತು ಗೋಲ್ಡನ್ ಡಿಫ್ಗಳನ್ನು ಒಪ್ಪಂದ ಬದಲಾವಣೆಗಳಾಗಿ ಪರಿಶೀಲಿಸಿ; ಅವುಗಳನ್ನು ಕಣ್ಣುಮುಚ್ಚಿ ಸ್ವೀಕರಿಸಬೇಡಿ.

### ರೂಟಿಂಗ್

**ಒಪ್ಪಂದಗಳು**

- `src/shared/constants/routingStrategies.ts` ನಲ್ಲಿನ ಸಾರ್ವಜನಿಕ ಸ್ಟ್ರಾಟೆಜಿ ಮೌಲ್ಯಗಳು ಮತ್ತು UI ಮೆಟಾಡೇಟಾ.
- `open-sse/services/combo.ts` ಮತ್ತು `open-sse/services/combo/` ಅಡಿಯಲ್ಲಿನ ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು ಕ್ರಮಗೊಳಿಸುವಿಕೆ.
- ಕಾಂಬೊ ಸ್ಕೀಮಾಗಳು, ಪರ್ಸಿಸ್ಟೆನ್ಸ್, ರೆಸಿಲಿಯನ್ಸ್ ಸ್ಥಿತಿ, ಮಾಡೆಲ್ ಸಾಮರ್ಥ್ಯಗಳು ಮತ್ತು API/UI ನಿಯಂತ್ರಣಗಳು.
- ವರ್ತನೆ ಬದಲಾದಾಗ [Auto-Combo Engine](../routing/AUTO-COMBO.md) ಮತ್ತು ರೆಸಿಲಿಯನ್ಸ್ ದಾಖಲೆಗಳು.

npm run check:known-symbols      # ಸ್ಟ್ರಾಟೆಜಿ ನೋಂದಣಿ ಬದಲಾವಣೆಗಳು

## ಸ್ಥಳೀಯ candidate ಲೂಪ್

ಮೂಲ ಪರೀಕ್ಷೆಗಳು ಪ್ಯಾಕೇಜ್ ಮಾಡಿದ artifact ಬೂಟ್ ಆಗುತ್ತದೆ ಎಂಬುದನ್ನು ಸಾಬೀತುಪಡಿಸಲಾರವು: packaging ಪಟ್ಟಿಗಳು, ತೆಗೆದುಹಾಕಲಾದ dependencies ಮತ್ತು native binaries ಸಂಬಂಧಿತ ದೋಷಗಳು tarball ಅನ್ನು ಸ್ಥಾಪಿಸಿ ಪ್ರಾರಂಭಿಸಿದ ನಂತರವಷ್ಟೇ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) ಎಂಬುದು RFC #8084 ರ build-once / validate / promote ಹರಿವಿನ ಸ್ಥಳೀಯ ಭಾಗವಾಗಿದೆ: ಇದು ಒಂದು candidate ಅನ್ನು build ಮಾಡುತ್ತದೆ, ಅದೇ artifact ಅನ್ನು validate ಮಾಡುತ್ತದೆ, directory ಹೆಸರುಗಳನ್ನು ಬದಲಿಸುವ ಮೂಲಕ ಅದನ್ನು promote ಮಾಡುತ್ತದೆ ಮತ್ತು promote ಮಾಡಿದ slot ತನ್ನ health check ನಲ್ಲಿ ವಿಫಲವಾದಾಗ ಅದನ್ನು roll back ಮಾಡುತ್ತದೆ.

```bash
npm run dev:candidate -- run --dry-run --json  # ಯೋಜನೆಯನ್ನು ಮುದ್ರಿಸಿ, ಏನನ್ನೂ ಬದಲಿಸಬೇಡಿ
npm run dev:candidate -- run                   # build + validate + promote, ಸ್ವಯಂಚಾಲಿತ rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ಗೆ ಸ್ಥಾಪಿಸಿ
npm run dev:candidate -- validate --id <id>    # ಖಾಲಿ port ನಲ್ಲಿ ಬೂಟ್ ಮಾಡಿ, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current ಮತ್ತು previous ಅನ್ನು ಪರಸ್ಪರ ಬದಲಿಸಿ
npm run dev:candidate -- run --from-tarball <file.tgz>  # ಬೇರೆಡೆ (CI) build ಮಾಡಿದ tarball ಅನ್ನು ಮರುಬಳಸಿ
```

- **ಒಮ್ಮೆ ಮಾತ್ರ build ಮಾಡಿ.** `build` ಪ್ರಸ್ತುತ tree ಅನ್ನು pack ಮಾಡುತ್ತದೆ (ಇದಕ್ಕೆ `dist/server.js` ಅಗತ್ಯವಿರುವುದರಿಂದ, ಮೊದಲು `npm run build:release` ಚಲಾಯಿಸಿ) ಅಥವಾ `--from-tarball` ಅನ್ನು ನಕಲಿಸುತ್ತದೆ; ನಂತರ tarball ಯಾವುದೇ `node_modules` ಅನ್ನು ಒಳಗೊಂಡಿರದ ಕಾರಣ, ಅದನ್ನು ಪ್ರತ್ಯೇಕ npm prefix ನಲ್ಲಿ ಸ್ಥಾಪಿಸುತ್ತದೆ. id ಎಂಬುದು ಸಂಕ್ಷಿಪ್ತ `HEAD` sha (tree ನಲ್ಲಿ ಸ್ಥಳೀಯ ಬದಲಾವಣೆಗಳಿದ್ದರೆ `-dirty`) ಅಥವಾ tarball ಗಾಗಿ `tgz-<sha256>` ಆಗಿರುತ್ತದೆ. ಈಗಾಗಲೇ build ಆಗಿರುವ clean id ಅನ್ನು ಮರು-build ಮಾಡುವ ಬದಲು ಮರುಬಳಸಲಾಗುತ್ತದೆ; ಅದನ್ನು ಮರು-build ಮಾಡಲು `--force` ಬಳಸಿ.
- **ಮೂಲವನ್ನು ಅಲ್ಲ, package ಅನ್ನು validate ಮಾಡಿ.** `validate`, ಹೊಸ `DATA_DIR=<candidate>/data`, ನಕಲಿ secrets ಹಾಗೂ environment ನಿಂದ ತೆಗೆದುಹಾಕಲಾದ operator ನ `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ಮತ್ತು `INITIAL_PASSWORD` ಜೊತೆಗೆ ಸ್ಥಾಪಿಸಲಾದ CLI ಅನ್ನು (`serve --port <free port>`) ಪ್ರಾರಂಭಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ಇದು ಹೊಸ installation ನ keyless loopback ಸ್ಥಿತಿಯನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ. ಇದು `GET /api/health` 200 ಅನ್ನು ಹಿಂದಿರುಗಿಸುವವರೆಗೆ ಕಾಯುತ್ತದೆ, `GET /v1/models` 200 ಅನ್ನು ಹಿಂದಿರುಗಿಸುವುದನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ, process group ಅನ್ನು ನಿಲ್ಲಿಸುತ್ತದೆ ಮತ್ತು tarball hash ಜೊತೆಗೆ ತೀರ್ಪನ್ನು `validation.json` ನಲ್ಲಿ ದಾಖಲಿಸುತ್ತದೆ.
- **ಅದೇ artifact ಅನ್ನು promote ಮಾಡಿ.** ತನ್ನ ಪ್ರಸ್ತುತ tarball hash ಗೆ ಯಶಸ್ವಿ validation ಇಲ್ಲದ candidate ಅನ್ನು `promote` ನಿರಾಕರಿಸುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ active slot `_artifacts/candidate/current` ಆಗಿದೆ; `--target <dir>` ಅದೇ filesystem ನಲ್ಲಿರುವ ಮತ್ತೊಂದು directory ಅನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ ಮತ್ತು ಅದರ ಹಿಂದಿನ slot `<dir>.previous` ಆಗಿರುತ್ತದೆ. ಪ್ರತಿಯೊಂದು rename atomic ಆಗಿರುತ್ತದೆ ಮತ್ತು ಪ್ರಕ್ರಿಯೆಯ ಮಧ್ಯದಲ್ಲಿ ವೈಫಲ್ಯ ಉಂಟಾದರೆ, ಈಗಾಗಲೇ ನಡೆದ rename ಗಳನ್ನು ಹಿಮ್ಮುಖಗೊಳಿಸಲಾಗುತ್ತದೆ.
- **Roll back ಮಾಡಿ.** `run`, promote ಮಾಡಿದ slot ಅನ್ನು ಮತ್ತೊಮ್ಮೆ validate ಮಾಡುತ್ತದೆ ಮತ್ತು ಆ ಪರಿಶೀಲನೆ ವಿಫಲವಾದಾಗ `current` ಹಾಗೂ `previous` ಅನ್ನು ಹಿಂದಕ್ಕೆ ಪರಸ್ಪರ ಬದಲಿಸುತ್ತದೆ. ಮೊದಲ validation ನಲ್ಲೇ ವಿಫಲವಾಗುವ candidate ಅನ್ನು ಎಂದಿಗೂ promote ಮಾಡಲಾಗುವುದಿಲ್ಲ.

ಎಲ್ಲವನ್ನೂ gitignore ಮಾಡಲಾದ `_artifacts/candidate/` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ; ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OmniRoute installation ಮತ್ತು ಅದರ data directory ಅನ್ನು ಎಂದಿಗೂ ಬದಲಿಸಲಾಗುವುದಿಲ್ಲ. Promote ಮಾಡಿದ CLI `_artifacts/candidate/current/prefix/bin/omniroute` ಆಗಿದೆ; ಅದನ್ನು ಬಳಸುವಾಗ ನಿಮ್ಮದೇ `DATA_DIR` ನೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಿ. Exit codes: `0` ಯಶಸ್ಸು, `1` ವಿಫಲವಾದ validation ಅಥವಾ promotion, `2` ಬಳಕೆಯ ದೋಷ ಅಥವಾ ಕಾಣೆಯಾದ build.

| ಪ್ರತಿ ಪ್ಯಾಚ್ಗಾಗಿ ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಿ                                                                          | CI ವ್ಯಾಪಕ ಸಂಕೇತವನ್ನು ಒದಗಿಸುತ್ತದೆ                                                       |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| ಮೇಲಿನ ನೇರ ವರ್ತನೆ ಪರೀಕ್ಷೆಗಳು ಮತ್ತು ವರ್ಗದ ಗೇಟ್ಗಳು                                                              | ಶಾರ್ಡ್ ಮಾಡಲಾದ ಸಂಪೂರ್ಣ ಯೂನಿಟ್ ಸೂಟ್ ಮತ್ತು ಸರಣಿ ಪರೀಕ್ಷೆಗಳು                                |

ಹಸಿರು ಸ್ಥಿತಿಯಲ್ಲಿರುವ ಕೇಂದ್ರೀಕೃತ ಲೂಪ್ ಬದಲಾದ ಒಪ್ಪಂದದ ಕುರಿತ ಸಾಕ್ಷಿಯಾಗಿದೆ; ಸಂಬಂಧವಿಲ್ಲದ CI ಪರಿಶೀಲನೆಗಳು
ಯಶಸ್ವಿಯಾಗುತ್ತವೆ ಎಂಬುದಕ್ಕೆ ಅದು ಪುರಾವೆಯಲ್ಲ. ಇದಕ್ಕೆ ವಿರುದ್ಧವಾಗಿ, ಪ್ರತಿ ಸ್ಥಳೀಯ ತಿದ್ದುಪಡಿಯೂ ಸಂಪೂರ್ಣ ರೆಪೊಸಿಟರಿ ಮ್ಯಾಟ್ರಿಕ್ಸ್ಗಾಗಿ ಕಾಯುವಂತೆ ಮಾಡಬೇಡಿ.

## ಸಮನ್ವಯ ಪರಿಶೀಲನಾಪಟ್ಟಿ

ಪರಿಶೀಲನೆಗಾಗಿ ವಿನಂತಿಸುವ ಮೊದಲು:

- PR ಬೇಸ್ ಇನ್ನೂ ಅತ್ಯುನ್ನತ ಸಕ್ರಿಯ `release/v*` ಶಾಖೆಯೇ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿ.
- ಆ ಬೇಸ್ ಅನ್ನು ಫೆಚ್ ಮಾಡಿ ಮತ್ತು ನೀವು ಶಾಖೆ ರಚಿಸಿದ ನಂತರ ಸೇರಿಸಲಾದ ಕಮಿಟ್ಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
- ಆಕಸ್ಮಿಕ ಅಥವಾ ಜನರೇಟ್ ಮಾಡಲಾದ ಅನಗತ್ಯ ಬದಲಾವಣೆಗಳಿಗಾಗಿ `git diff <active-base>...HEAD` ಅನ್ನು ಪರಿಶೀಲಿಸಿ.
- ಮೂಲವನ್ನು ನವೀಕರಿಸಿ ಮತ್ತು ಔಟ್ಪುಟ್ ಅನ್ನು ಪುನಃ ಜನರೇಟ್ ಮಾಡುವ ಮೂಲಕ ಕ್ಯಾಟಲಾಗ್ ಮತ್ತು ಜನರೇಟ್ ಮಾಡಲಾದ ಡಾಕ್ಯುಮೆಂಟ್ ಸಂಘರ್ಷಗಳನ್ನು ಪರಿಹರಿಸಿ.
- ಸಮನ್ವಯದ ನಂತರ PR ವಿವರಣೆಯಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾದ ಪ್ರತಿಯೊಂದು ಕೇಂದ್ರೀಕೃತ ಪರೀಕ್ಷೆ/ಗೇಟ್ ಅನ್ನು ಮರುಚಲಾಯಿಸಿ.
- ಬದಲಾದ ಬೇಸ್ಗೆ ಹೊಂದಿಸಲು ಮಾತ್ರ ಅಸರ್ಷನ್ಗಳನ್ನು ಎಂದಿಗೂ ದುರ್ಬಲಗೊಳಿಸಬೇಡಿ ಅಥವಾ ಅಗತ್ಯ ಪರೀಕ್ಷೆಗಳನ್ನು ತೆಗೆದುಹಾಕಬೇಡಿ.

ರಿಲೀಸ್-ಫ್ರೀಜ್ ಮತ್ತು ಮರು-ಟಾರ್ಗೆಟ್ ಮಾಡುವ ನಿಯಮಗಳಿಗಾಗಿ,
[ಶಾಖೀಕರಣ ಮತ್ತು ರಿಲೀಸ್ ಮಾದರಿ](BRANCHING_MODEL.md) ಬಳಸಿ. ಸಂಪೂರ್ಣ CI ಪಟ್ಟಿಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳ ಉಲ್ಲೇಖ](../architecture/QUALITY_GATES.md) ಬಳಸಿ.
