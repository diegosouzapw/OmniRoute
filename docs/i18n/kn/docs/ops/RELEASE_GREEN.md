## ಇದು ಪರಿಹರಿಸುವ ಸಮಸ್ಯೆ

**ಸಂಪೂರ್ಣ ಗೇಟ್** (`.github/workflows/ci.yml` — ಯುನಿಟ್ ಶಾರ್ಡ್ಗಳು, vitest, ರ್ಯಾಚೆಟ್ಗಳು,
`package-artifact`, SonarQube, E2E) **ಬಿಡುಗಡೆ PRನಲ್ಲಿ ಮಾತ್ರ** (PR → `main`) ರನ್ ಆಗುತ್ತದೆ.
`release/**` ಅನ್ನು ಗುರಿಯಾಗಿಸುವ PRಗಳು **ವೇಗದ ಗೇಟ್ಗಳನ್ನು** (`quality.yml`: TIA-ಪ್ರಭಾವಿತ
ಪರೀಕ್ಷೆಗಳು + ಟೈಪ್ ಪರಿಶೀಲನೆ + ಲಿಂಟ್) ಪಡೆಯುತ್ತವೆ ಮತ್ತು ಕೋಡ್ ಬದಲಾವಣೆಗಳಿಗಾಗಿ **ಸಲಹಾತ್ಮಕ**
ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ ಅನ್ನು ಪಡೆಯುತ್ತವೆ. ಇದರ ಪರಿಣಾಮವಾಗಿ, ಬಿಡುಗಡೆಗೆ ಮಾತ್ರ ಸಂಬಂಧಿಸಿದ ರೆಡ್ಗಳು ಬಿಡುಗಡೆ
ಬ್ರಾಂಚ್ನಲ್ಲಿ ಮೌನವಾಗಿ ಸಂಗ್ರಹವಾಗುತ್ತಾ, ಬಿಡುಗಡೆ ಸಮಯದಲ್ಲಿ **ಒಂದೊಂದಾಗಿ ~40 ನಿಮಿಷಗಳ ಪದರಗಳಲ್ಲಿ
ಸ್ಫೋಟಿಸಬಹುದು**.

"release-green ಕುಟುಂಬ"ವು ಆ ರೆಡ್ಗಳನ್ನು **ಮುಂಚಿತವಾಗಿ ನಿರೀಕ್ಷಿಸಲು** ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ — ಸಂಪೂರ್ಣ
ಗೇಟ್ಗೆ ಸಮಾನವಾದುದನ್ನು ಯಾವುದೇ ಸಮಯದಲ್ಲಿ **ಸ್ಥಳೀಯವಾಗಿ / ಬಿಡುಗಡೆಯ ಹೊರಗೆ** ಮೌಲ್ಯೀಕರಿಸುವ ಮೂಲಕ,
ಬಿಡುಗಡೆ PR ತನ್ನ ಮೊದಲ CI ರನ್ನಲ್ಲಿಯೇ ಗ್ರೀನ್ ಆಗಿರುವಂತೆ ನೋಡಿಕೊಳ್ಳುತ್ತದೆ.

> **ರಾಜಿ ಮಾಡಲಾಗದ ತತ್ವ:** ಇದರಲ್ಲಿ ಯಾವುದೂ ಕೊಡುಗೆದಾರರನ್ನು ತಡೆಯುವುದಿಲ್ಲ. ಅವರ PR ವಿಫಲವಾಗುವಂತೆ
> ಮಾಡುವ ಅಗತ್ಯ ಪರಿಶೀಲನೆಯನ್ನು ನಾವು ಸೇರಿಸುವುದಿಲ್ಲ. **ಡ್ರಿಫ್ಟ್** (ರ್ಯಾಚೆಟ್ಗಳು) ಅನ್ನು ಬಿಡುಗಡೆ ಸಮಯದಲ್ಲಿ
> ನಿರ್ವಹಕರು ಮರುಬೇಸ್ಲೈನ್ ಮಾಡಬೇಕು — ಅದು ಎಂದಿಗೂ ಕೊಡುಗೆದಾರರ ಕಾಳಜಿಯಲ್ಲ. ಯಾವುದೇ ಭಾಗವೂ PR ಅನ್ನು
> **ಮುಚ್ಚುವುದಿಲ್ಲ** (ಕ್ರೆಡಿಟ್ ಕಳವು) ಅಥವಾ ಪಾಸ್ ಆಗಲು ಪರೀಕ್ಷೆಯನ್ನು **ದುರ್ಬಲಗೊಳಿಸುವುದಿಲ್ಲ**.

| ಭಾಗ                                                                      | ಅದು ಏನು                                                                                    | ಯಾವಾಗ ರನ್ ಮಾಡಬೇಕು                                                                 | ವ್ಯಾಪ್ತಿ                        |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ------------------------------- |
| **`/green-prs`** (ಪರಿಹಾರ A)                                              | **ತೆರೆದಿರುವ PRಗಳ ಸರತಿಯ** ನಿರ್ವಾಹಕರ ಬೇಡಿಕೆ-ಆಧಾರಿತ ಸ್ಕ್ಯಾನ್                                  | **ಸ್ವತಂತ್ರವಾಗಿ, ನಿಯತಕಾಲಿಕವಾಗಿ** — ಮತ್ತು ವಿಶೇಷವಾಗಿ `/generate-release`ಗೆ **ಮೊದಲು** | ಸಂಪೂರ್ಣ PR ಸರತಿ → `release/**`  |

**"ಇದು ಬಿಡುಗಡೆಗಳಿಗಾಗಿ ಮಾತ್ರವೇ?" ಎಂಬುದಕ್ಕೆ ಸಂಕ್ಷಿಪ್ತ ಉತ್ತರ:** **ಇಲ್ಲ.** `/green-prs` ಅನ್ನು
**ನಿಯತಕಾಲಿಕವಾಗಿ, ಬಿಡುಗಡೆಗಳ ನಡುವೆ** ರನ್ ಮಾಡುವಂತೆ ವಿನ್ಯಾಸಗೊಳಿಸಲಾಗಿದೆ. ಅದನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ರನ್
ಮಾಡುವುದು ಸಾಮಾನ್ಯ ಬಳಕೆ — ಬಿಡುಗಡೆ ಎಂದರೆ ಅದನ್ನು ರನ್ ಮಾಡುವುದರಿಂದ ಅತ್ಯಧಿಕ ಮೌಲ್ಯ ದೊರೆಯುವ ಸಂದರ್ಭ
ಮಾತ್ರ.

## PR-ನಿಂದ-ರಿಲೀಸ್ ಸಲಹಾತ್ಮಕ ಬಿಲ್ಡ್

`quality.yml` ಈಗ ಡ್ರಾಫ್ಟ್ ಅಲ್ಲದ ಕೋಡ್ PRಗಳು ಮತ್ತು Mergify ಕ್ಯೂ ಬ್ರಾಂಚ್ಗಳಿಗಾಗಿ `Build (advisory)` ಅನ್ನು ಒಳಗೊಂಡಿದೆ.
ಇದು `ci.yml` ನಲ್ಲಿನ ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ ವಿಧಾನವನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ: Node 24, `npm-ci-retry`,
`check:node-runtime`, ಮತ್ತು `OMNIROUTE_USE_TURBOPACK=1` ಜೊತೆಗೆ `npm run build`. ಈ ವರ್ಕ್ಫ್ಲೋದಲ್ಲಿ ಯಾವುದೇ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಗುಣಮಟ್ಟದ ಜಾಬ್ ಬಿಲ್ಡ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಅನ್ನು ಬಳಸುವುದಿಲ್ಲವಾದ್ದರಿಂದ, ಇದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಅದನ್ನು ಅಪ್ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ.
ಒಂದು ವಾರದ ಸ್ಥಿರ ರಿಲೀಸ್-PR ರನ್ಗಳ ನಂತರ `continue-on-error` ಅನ್ನು ತೆಗೆದುಹಾಕಿ, ಇದರಿಂದ ಈ ಸಂಕೇತವು
ತಡೆಯೊಡ್ಡುವ PR-ನಿಂದ-ರಿಲೀಸ್ ಗೇಟ್ ಆಗುತ್ತದೆ.

## ಪರಿಹಾರ C — `npm run check:release-green` (ಎಂಜಿನ್)

ಪ್ರಸ್ತುತ ವರ್ಕಿಂಗ್ ಟ್ರೀಗೆ ವಿರುದ್ಧವಾಗಿ ರಿಲೀಸ್ಗೆ ಸಮಾನವಾದ ಮೌಲ್ಯೀಕರಣವನ್ನು ಪುನರುತ್ಪಾದಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು ರೆಡ್ ಅನ್ನು ವರ್ಗೀಕರಿಸುತ್ತದೆ:

- **HARD** (ಟೈಪ್ಚೆಕ್, ಲಿಂಟ್ ದೋಷಗಳು, ಯೂನಿಟ್, vitest, db-rules, public-creds, ಐಚ್ಛಿಕ
  `package-artifact`) → **ನೈಜ ದೋಷ**; `exit 1`. ಮೂಲ ಬ್ರಾಂಚ್ನಲ್ಲಿ ಸರಿಪಡಿಸಲಾಗುತ್ತದೆ (TDD, ನಿಯಮ #18).
- **DRIFT** (eslint **ಎಚ್ಚರಿಕೆಗಳು**, ಕಾಗ್ನಿಟಿವ್-ಕಾಂಪ್ಲೆಕ್ಸಿಟಿ, ಫೈಲ್-ಗಾತ್ರ) → ಸೈಕಲ್ನಲ್ಲಿ ಸಂಗ್ರಹವಾದ ರ್ಯಾಚೆಟ್ ಡ್ರಿಫ್ಟ್,
  **ಕೊಡುಗೆದಾರರ ತಪ್ಪಲ್ಲ**; ಇದನ್ನು ವರದಿ ಮಾತ್ರ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು **ರಿಲೀಸ್ ಸಮಯದಲ್ಲಿ ನಿರ್ವಹಣೆಗಾರರು ಮರುಬೇಸ್ಲೈನ್ ಮಾಡುತ್ತಾರೆ**.
  ಡ್ರಿಫ್ಟ್ **ಎಂದಿಗೂ** ಎಕ್ಸಿಟ್ ಕೋಡ್ ಅನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ — ಆದ್ದರಿಂದ ಅದು ಯಾರನ್ನೂ ಎಂದಿಗೂ ತಡೆಯುವುದಿಲ್ಲ.

```bash
npm run check:release-green                 # ಪ್ರಸ್ತುತ ಬ್ರಾಂಚ್ (ವರ್ಕಿಂಗ್ ಟ್ರೀ)
node scripts/quality/validate-release-green.mjs --json   # ರಚನಾತ್ಮಕ ಔಟ್ಪುಟ್
node scripts/quality/validate-release-green.mjs --quick  # ಯೂನಿಟ್+vitest ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (ಡ್ರಿಫ್ಟ್+ಟೈಪ್ಚೆಕ್+ಲಿಂಟ್ ಮಾತ್ರ)
node scripts/quality/validate-release-green.mjs --with-build  # package-artifact ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ (ನಿಧಾನ)
```

ರೋಗನಿರ್ಣಯ ಮಾಡಿ **ವರದಿ ಮಾತ್ರ** ಮಾಡುತ್ತದೆ (ಸ್ವಯಂ-ಸರಿಪಡಿಸುವಿಕೆ ಇಲ್ಲ). ಗ್ರೀನ್ಗೆ-ಸರಿಪಡಿಸುವ ಆರ್ಕೆಸ್ಟ್ರೇಶನ್
`/green-prs` ಮತ್ತು `/review-prs` ನಲ್ಲಿ ಇರುತ್ತದೆ.

## ಪರಿಹಾರ A — `/green-prs` (ಕ್ಯೂ ಸ್ಕ್ಯಾನ್)

ಕಾರ್ಯವಿಧಾನ (ಸಾರಾಂಶ — ವಿವರಗಳಿಗಾಗಿ `green-prs` ಸ್ಕಿಲ್ ನೋಡಿ):

1. ಸಕ್ರಿಯ ರಿಲೀಸ್ ಬ್ರಾಂಚ್ಗೆ ವಿರುದ್ಧವಾಗಿ ಓಪನ್ PRಗಳ ಕ್ಯೂ ಅನ್ನು **ಪಟ್ಟಿಮಾಡಿ**.
2. ಪ್ರತಿಯೊಂದು PR ಅನ್ನು **ಟ್ರಯಾಜ್ ಮಾಡಿ** (ಕಾರ್ಯಸಾಧ್ಯ / ತಿರಸ್ಕಾರಯೋಗ್ಯ / ಲೇಖಕರ-ಕ್ರಮ-ಅಗತ್ಯ) — ತಿರಸ್ಕಾರ/ಲೇಖಕರ-ಕ್ರಮ-ಅಗತ್ಯ ಸ್ಥಿತಿಗಳನ್ನು
   **ವರದಿ ಮಾಡಲಾಗುತ್ತದೆ, ಮುಚ್ಚಲಾಗುವುದಿಲ್ಲ** (ಲೇಖಕರು ನಿರ್ಧರಿಸುತ್ತಾರೆ).
3. ಪ್ರತಿಯೊಂದು ಕಾರ್ಯಸಾಧ್ಯ PRಗಾಗಿ, **ಪ್ರತ್ಯೇಕಿಸಿದ ವರ್ಕ್ಟ್ರೀಯಲ್ಲಿ** (ನಿಯಮ #19), PR ಅನ್ನು ರಿಲೀಸ್ ಟಿಪ್ಗೆ ತಂದು
   `npm run check:release-green` ಅನ್ನು ರನ್ ಮಾಡಿ:
   - **HARD** → ಸಹ-ಕರ್ತೃತ್ವದ ಮೂಲಕ **ಕೊಡುಗೆದಾರರ ಬ್ರಾಂಚ್ನಲ್ಲೇ** ಸರಿಪಡಿಸಿ (ಲೇಖಕರ "Merged" ಸ್ಥಿತಿಯನ್ನು ಉಳಿಸುತ್ತದೆ),
     ಎಲ್ಲಾ HARDಗಳು ತೆರವುಗೊಳ್ಳುವವರೆಗೆ ಮರು-ರನ್ ಮಾಡಿ.
   - **DRIFT** → ಹಾಗೆಯೇ ಬಿಡಿ; ರಿಲೀಸ್ ಸಮಯದಲ್ಲಿ ಅದನ್ನು ಮರುಬೇಸ್ಲೈನ್ ಮಾಡಲಾಗುತ್ತದೆ.
4. PR × (ತೀರ್ಪು, HARD ರೆಡ್ಗಳು, ಸರಿಪಡಿಸಲಾಗಿದೆಯೇ?, DRIFT, ಈಗ ರಿಲೀಸ್-ಗ್ರೀನ್ ಆಗಿದೆಯೇ?) ಟೇಬಲ್ ಅನ್ನು **ವರದಿ ಮಾಡಿ**.

ಮರ್ಜ್ ಮಾಡದೆಯೇ ಕ್ಯೂ ಅನ್ನು **ಸಿದ್ಧಪಡಿಸಬಹುದು**; ಸ್ಪಷ್ಟವಾಗಿ ವಿನಂತಿಸಿದಾಗ ಮಾತ್ರ ಮರ್ಜ್ ಮಾಡುತ್ತದೆ — ಮತ್ತು PR ಅನ್ನು ಎಂದಿಗೂ ಮುಚ್ಚುವುದಿಲ್ಲ.

## ಶಿಫಾರಸು ಮಾಡಿದ ಆವರ್ತನೆ

- **`/green-prs` ಅನ್ನು ನಿಯತಕಾಲಿಕವಾಗಿ ರನ್ ಮಾಡಿ** (ಉದಾ., ವಾರಕ್ಕೊಮ್ಮೆ) ಮತ್ತು
  `/generate-release` ಗೆ **ಯಾವಾಗಲೂ ಮೊದಲು** ರನ್ ಮಾಡಿ.
- **`nightly-release-green.yml`** (ಪರಿಹಾರ D) ಅನ್ನು ನಿರಂತರ ಸಂಕೇತವಾಗಿ ಇರಿಸಿ: ಅದು HARD ರೆಡ್ ಇಶ್ಯೂ ಅನ್ನು ತೆರೆದಾಗ,
  ಸ್ಕ್ಯಾನ್ ಮಾಡುವ ಸಮಯ ಬಂದಿದೆ.
- ಬ್ರಾಂಚ್ ಅಥವಾ ನಿರ್ದಿಷ್ಟ ಮರ್ಜ್ ಅಭ್ಯರ್ಥಿಯನ್ನು ಪರಿಶೀಲಿಸಲು **`/validate-release-green`** ಅನ್ನು ಅಗತ್ಯಕ್ಕೆ ತಕ್ಕಂತೆ ಬಳಸಿ.
- ನಿರ್ದಿಷ್ಟ PR ಅನ್ನು ಲೈವ್ CIನಲ್ಲಿ ಗ್ರೀನ್ ಸ್ಥಿತಿಗೆ ತರಬೇಕಾದಾಗ **`/babysit <PR#>`** ಬಳಸಿ.

## ರಿಲೀಸ್ನೊಂದಿಗಿನ ಸಂಬಂಧ

- `/generate-release` **ಹಂತ 0 (ಪ್ರೀ-ಫ್ಲೈಟ್)** ನಲ್ಲಿ ಮೌಲ್ಯೀಕರಣವನ್ನು ಕರೆಮಾಡುತ್ತದೆ: ರಿಲೀಸ್ PR ಅನ್ನು ತೆರೆಯುವ ಮೊದಲು DRIFT ಅನ್ನು ಮರುಬೇಸ್ಲೈನ್ ಮಾಡುತ್ತದೆ ಮತ್ತು
  HARD ಅನ್ನು ಸರಿಪಡಿಸುತ್ತದೆ.
- `/review-prs` ಮರ್ಜ್ ನಿರ್ಧಾರದ ಹಂತದಲ್ಲಿ ರಿಲೀಸ್-ಗ್ರೀನ್ ಗೇಟ್ ಅನ್ನು ಬಳಸುತ್ತದೆ (ಮರ್ಜ್ಗೆ-ಮೊದಲು-ಗ್ರೀನ್).

ಎಲ್ಲಾ ಭಾಗಗಳ ಗುರಿ ಒಂದೇ: ರಿಲೀಸ್ ದಿನದಂದು 40-ನಿಮಿಷಗಳ ಪದರಗಳಲ್ಲಿ ರೆಡ್ಗಳನ್ನು ಎದುರಿಸುವ ಬದಲು,
**ಮೊದಲ CI ರನ್ನಲ್ಲೇ ಗ್ರೀನ್ ರಿಲೀಸ್ PR**.
