ಈ ದಸ್ತಾವೇಜು OmniRouteಗೆ ಸೇರಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆ-ಚಾಲಿತ ಹೊಂದಾಣಿಕೆಯ ರೂಟಿಂಗ್ ಅಡಿಪಾಯವನ್ನು
ವಿವರಿಸುತ್ತದೆ. ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಚಿಕ್ಕದಾಗಿ ಇರಿಸಲಾಗಿದೆ: ಇದು ಟೈಪ್ಗೊಳಿಸಿದ ರೂಟಿಂಗ್-ಫಲಿತಾಂಶ
ಚಾನಲ್, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ auto-combo ಸ್ಕೋರರ್ಗೆ ಮಾಹಿತಿ ಒದಗಿಸುವ ಆನ್ಲೈನ್ ಗುಣಮಟ್ಟದ ಸಂಕೇತ,
ಐಚ್ಛಿಕ OpenTelemetry ಎಕ್ಸ್ಪೋರ್ಟರ್ ಮತ್ತು ವಿವರಣೀಯತೆ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಪರಿಚಯಿಸುತ್ತದೆ. ಇದು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವದ ಸ್ಟ್ಯಾಕ್ ಅನ್ನು (ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್, ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್,
ಮಾದರಿ ಲಾಕ್ಔಟ್, ಆರೋಗ್ಯ ಮ್ಯಾಟ್ರಿಕ್ಸ್, ಆಟೋಪೈಲಟ್) **ಬದಲಿಸುವುದಿಲ್ಲ** — ಅದಕ್ಕೆ ಪೂರಕವಾಗಿದೆ.

## 1. ವಾಸ್ತುಶಿಲ್ಪದ ಸಂದರ್ಭ

OmniRoute ಒಂದು **ವಿನಂತಿಯ ಹಾಟ್ ಪಾತ್** ಮತ್ತು **ನಿಯಂತ್ರಣ/ಬುದ್ಧಿಮತ್ತೆಯ
ಪ್ಲೇನ್** ಹೊಂದಿರುವ ಡೇಟಾ ಪ್ಲೇನ್ ಆಗಿದೆ. ಹಾಟ್ ಪಾತ್ ವೇಗವಾಗಿ, ಮೆಮೊರಿ-ಸಮರ್ಥವಾಗಿ, ಅಸಿಂಕ್ರೋನಸ್ ಆಗಿ, ಸ್ಥಿತಿಸ್ಥಾಪಕವಾಗಿ ಮತ್ತು
ಊಹಿಸಬಹುದಾದ ರೀತಿಯಲ್ಲಿ ಉಳಿಯಬೇಕು. ಮೌಲ್ಯಮಾಪನ, ಗುಣಮಟ್ಟದ ಸ್ಕೋರಿಂಗ್, ಪ್ರಯೋಗಗಳು ಮತ್ತು ಐತಿಹಾಸಿಕ ವಿಶ್ಲೇಷಣೆ
ನಿಯಂತ್ರಣ ಪ್ಲೇನ್ಗೆ ಸೇರಿವೆ.

```
AI ಏಜೆಂಟ್ / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   ಡೇಟಾ ಪ್ಲೇನ್ (ವೇಗದ, ಸಿಂಕ್, ಇನ್-ಮೆಮೊರಿ)
│  ರೂಟಿಂಗ್ / ಫೇಲ್ಓವರ್ │
│  ಆರೋಗ್ಯ / ಗಾರ್ಡ್ರೇಲ್ │
│  ಕ್ಯಾಶ್ / ಸ್ಟ್ರೀಮಿಂಗ್ │
└──────────┬──────────┘
           │ RoutingEvent (ಫೈರ್-ಅಂಡ್-ಫರ್ಗೆಟ್, ~0.2µs)
           ▼
┌─────────────────────┐
│  ಪ್ರತಿಕ್ರಿಯೆ ಸಿಂಕ್ಗಳು │   ನಿಯಂತ್ರಣ ಪ್ಲೇನ್ (ಅಸಿಂಕ್, ಅತ್ಯುತ್ತಮ-ಪ್ರಯತ್ನ)
│  ಗುಣಮಟ್ಟ ಟ್ರ್ಯಾಕರ್     │
│  OTel ಎಕ್ಸ್ಪೋರ್ಟರ್    │
│  ವಿವರಣೆ ಸ್ಟೋರ್        │
└──────────┬──────────┘
           ▼  ಗುಣಮಟ್ಟದ ಸ್ಕೋರ್
      auto-combo ಸ್ಕೋರರ್
```

### ಈಗಾಗಲೇ ಇದ್ದದ್ದು (ಪರಿಶೋಧಿಸಲಾಗಿದೆ, ನಕಲು ಮಾಡಿಲ್ಲ)

| ಪರಿಕಲ್ಪನೆ                              | ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅನುಷ್ಠಾನ                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| ಲಭ್ಯತೆ (ನಾವು ಟ್ರಾಫಿಕ್ ಕಳುಹಿಸಬಹುದೇ?)    | ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ (CLOSED/DEGRADED/OPEN/HALF_OPEN, DBಯಲ್ಲಿ ಉಳಿಸಲಾಗಿದೆ), ಸಂಪರ್ಕ ಕೂಲ್ಡೌನ್, ಮಾದರಿ ಲಾಕ್ಔಟ್ |
| ಆರೋಗ್ಯ ವರದಿಗಾರಿಕೆ                      | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                |
| ಶ್ಯಾಡೋ ಟ್ರಾಫಿಕ್                        | `open-sse/services/combo/shadowRouting.ts`                                                             |
| ಗಾರ್ಡ್ರೇಲ್ಗಳು                          | `src/lib/guardrails/` (ಪೂರ್ವ/ನಂತರದ ಹುಕ್ಗಳು)                                                            |
| ನಿಖರ ಕ್ಯಾಶ್                            | `src/lib/semanticCache.ts` (ಸಿಗ್ನೇಚರ್-ಆಧಾರಿತ)                                                          |
| ಮೌಲ್ಯಮಾಪಕಗಳು / ಮೌಲ್ಯಮಾಪನ-ಚಾಲಿತ ರೂಟಿಂಗ್ | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                   |
| ಕಾಂಬೊ ನಿರ್ಧಾರದ ವಿವರಣೀಯತೆ               | `open-sse/services/combo/decisionTrace.ts`                                                             |
| ಡ್ಯಾಶ್ಬೋರ್ಡ್ ರಿಯಲ್-ಟೈಮ್ ಈವೆಂಟ್ಗಳು      | `src/lib/events/eventBus.ts` (UI ಅಧಿಸೂಚನೆ ಚಾನಲ್, `unknown` ಪೇಲೋಡ್ಗಳು, 100-ನಮೂದುಗಳ ಇತಿಹಾಸ)              |

ರೂಟಿಂಗ್-ಈವೆಂಟ್ ಲೇಯರ್ `eventBus`ನ ಮರು-ಅನುಷ್ಠಾನ **ಅಲ್ಲ**: ಆ ಬಸ್
ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ ರಿಯಲ್-ಟೈಮ್ ಅಧಿಸೂಚನೆ ಚಾನಲ್ ಆಗಿದೆ (ಟೈಪ್ಗೊಳಿಸಿದ _ಈವೆಂಟ್ ಹೆಸರುಗಳು_, ಅಪಾರದರ್ಶಕ
ಪೇಲೋಡ್ಗಳು, UI ಗ್ರಾಹಕರು). `RoutingEvent` ಎನ್ನುವುದು ನಿಯಂತ್ರಣ ಪ್ಲೇನ್ನ
ಪ್ರತಿಕ್ರಿಯೆ ಸಿಂಕ್ಗಳು (ಗುಣಮಟ್ಟ ಟ್ರ್ಯಾಕರ್, OTel ಎಕ್ಸ್ಪೋರ್ಟರ್, ವಿವರಣೆ ಸ್ಟೋರ್) ಬಳಸುವ ಟೈಪ್ಗೊಳಿಸಿದ _ಫಲಿತಾಂಶ_ ಸ್ಟ್ರಕ್ಟ್
(ಲೇಟೆನ್ಸಿ/ಟೋಕನ್ಗಳು/ವೆಚ್ಚ/ಫಲಿತಾಂಶ/ಮುಕ್ತಾಯ-ಕಾರಣ) ಆಗಿದೆ.

### ಕೊರತೆಯಾಗಿದ್ದದ್ದು (ಇಲ್ಲಿ ಸೇರಿಸಲಾಗಿದೆ)

1. ಒಂದು **ಟೈಪ್ಗೊಳಿಸಿದ ರೂಟಿಂಗ್-ಫಲಿತಾಂಶ ಈವೆಂಟ್ + ಸಿಂಕ್ ಅಮೂರ್ತತೆ** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` ಕಾಂಬೊ-ವ್ಯಾಪ್ತಿಗೆ ಸೀಮಿತವಾಗಿದ್ದು ಇನ್-ಮೆಮೊರಿ ಮಾತ್ರ;
   `comboMetrics` ಸಂಚಿತ ಕೌಂಟರ್ಗಳಾಗಿವೆ; `call_logs` ಕಚ್ಚಾ ಅಸಿಂಕ್ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಆಗಿದೆ.
   ಇವುಗಳಲ್ಲಿ ಯಾವುದೂ ಗುಣಮಟ್ಟ ಟ್ರ್ಯಾಕರ್, OTel ಎಕ್ಸ್ಪೋರ್ಟರ್ ಅಥವಾ Future-AGI-ಶೈಲಿಯ
   ಮೌಲ್ಯಮಾಪಕ ಸಬ್ಸ್ಕ್ರೈಬ್ ಮಾಡಬಹುದಾದ ಟೈಪ್ಗೊಳಿಸಿದ, ಸಿಂಕ್-ಆಧಾರಿತ ಫಲಿತಾಂಶ ಚಾನಲ್ ಅಲ್ಲ.
2. ಔಟ್ಪುಟ್ ಗುಣಮಟ್ಟಕ್ಕಾಗಿ ಒಂದು **ಆನ್ಲೈನ್ ಗುಣಮಟ್ಟದ ಸಂಕೇತ** (EWMA) — ಈ ಹಿಂದೆ ಸ್ಕೋರರ್
   ಸ್ಥಿರ ಕಾರ್ಯ-ಹೊಂದಾಣಿಕೆ ಮತ್ತು ಆಯ್ಕೆ-ಆಧಾರಿತ ಮೌಲ್ಯಮಾಪನ ಉತ್ತೀರ್ಣತಾ ದರಗಳ ಮೂಲಕ ಮಾತ್ರ "ಗುಣಮಟ್ಟ"ವನ್ನು
   ಪರೋಕ್ಷವಾಗಿ ಅಂದಾಜಿಸುತ್ತಿತ್ತು.
3. GenAI ಶಬ್ದಾರ್ಥ ಸಂಪ್ರದಾಯಗಳನ್ನು ಬಳಸುವ ಒಂದು **ಐಚ್ಛಿಕ, ಅವಲಂಬನೆ-ರಹಿತ OTel ಎಕ್ಸ್ಪೋರ್ಟರ್**.
4. ನೈಜ ರೂಟಿಂಗ್ ನಿರ್ಧಾರಗಳು + ಗುಣಮಟ್ಟದ ಸ್ಥಿತಿಯನ್ನು ಹಿಂದಿರುಗಿಸುವ ಒಂದು **ವಿವರಣೀಯತೆ ಎಂಡ್ಪಾಯಿಂಟ್**.

## 2. ರೌಟಿಂಗ್ ಈವೆಂಟ್ಗಳು (ಪ್ರತಿಕ್ರಿಯೆಯ ಅಡಿಪಾಯ)

ಫೈಲ್ಗಳು: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` ಕೇವಲ ರೌಟಿಂಗ್ ಮೆಟಾಡೇಟಾವನ್ನು ಹೊಂದಿರುತ್ತದೆ:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // ಅನುಮತಿಪಟ್ಟಿಯಲ್ಲಿರುವ ಯೂನಿಯನ್
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` ಎಂಬುದು TypeScriptನಲ್ಲಿನ `Send+Sync`-ಶೈಲಿಯ ಟ್ರೇಟ್ ಆಗಿದೆ:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // O(1) ಆಗಿರಬೇಕು, ಸಮಕಾಲಿಕ I/O ಇರಬಾರದು
}
```

ಹಾಟ್ ಪಾತ್, ಪೂರ್ಣಗೊಂಡ ಪ್ರತಿ ವಿನಂತಿಗೆ ಒಮ್ಮೆ `emitRoutingEvent(event)` ಅನ್ನು ಕರೆಮಾಡುತ್ತದೆ
(ಸ್ಟ್ರೀಮಿಂಗ್-ಪೂರ್ಣಗೊಳಿಸುವಿಕೆ ಕಾಲ್ಬ್ಯಾಕ್, ನಾನ್-ಸ್ಟ್ರೀಮಿಂಗ್ ಯಶಸ್ಸಿನ ಪಾತ್ ಮತ್ತು
`handleChatCore`ನಲ್ಲಿನ ಅಸಮರ್ಪಕ-200 ವೈಫಲ್ಯದ ಪಾತ್). ನೋಂದಾಯಿತ ಸಿಂಕ್ಗಳಿಗೆ ಡಿಸ್ಪ್ಯಾಚ್ ಸಮಕಾಲಿಕ ಫ್ಯಾನ್-ಔಟ್
ಆಗಿರುತ್ತದೆ, ಆದರೆ ಪ್ರತಿ ಸಿಂಕ್ ಕೇವಲ ಕ್ಯೂಗೆ ಸೇರಿಸುತ್ತದೆ/ಇನ್-ಮೆಮೊರಿ ಸ್ಥಿತಿಯನ್ನು ನವೀಕರಿಸುತ್ತದೆ. **ಹಾಟ್
ಪಾತ್ನಲ್ಲಿ ಯಾವುದೇ ಸಮಕಾಲಿಕ ಡೇಟಾಬೇಸ್ ಬರವಣಿಗೆಗಳಿಲ್ಲ, ನೆಟ್ವರ್ಕ್ I/O ಇಲ್ಲ.**

ಡೀಫಾಲ್ಟ್ ಸಿಂಕ್ಗಳು:

- `MemoryRoutingEventStore` — ಎಕ್ಸ್ಪ್ಲೇನ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗಾಗಿ ಮಿತಿಗೊಳಿಸಲಾದ (500)
  ರಿಂಗ್ ಬಫರ್, ಇತ್ತೀಚಿನವು ಮೊದಲು.
- `QualityTracker` ಗ್ರಾಹಕ — EWMA ಗುಣಮಟ್ಟದ ಅಂದಾಜನ್ನು ನವೀಕರಿಸುತ್ತದೆ.
- `OtlpHttpsEventSink` — ಐಚ್ಛಿಕ; `OMNIROUTE_OTEL_ENDPOINT`
  (ಅಥವಾ `OTEL_EXPORTER_OTLP_ENDPOINT`) ಹೊಂದಿಸಿದಾಗ ಮಾತ್ರ ಸಕ್ರಿಯಗೊಳ್ಳುತ್ತದೆ.

### ಅಳೆಯಲಾದ ಓವರ್ಹೆಡ್ (ಪ್ರಾಮಾಣಿಕ ಹೋಲಿಕೆ)

ಈ ವರ್ಕ್ಸ್ಟೇಷನ್ನಲ್ಲಿ `npm run bench:routing-events` (100k ಪುನರಾವರ್ತನೆಗಳು; ಪ್ರತಿ-ಕಾರ್ಯಾಚರಣೆಯ
ಪರ್ಸೆಂಟೈಲ್ಗಳು `performance.now()` ಟೈಮರ್ ರೆಸಲ್ಯೂಶನ್ಗಿಂತ ಕಡಿಮೆ ಇರುವುದರಿಂದ ಉಪ-µs ಕಾರ್ಯಾಚರಣೆಗಳನ್ನು
ಒಟ್ಟು µs/op ಆಗಿ ಅಳೆಯಲಾಗಿದೆ):

| ಸನ್ನಿವೇಶ                             | µs/op  | ops/s  |
| ------------------------------------ | ------ | ------ |
| ಬೇಸ್ಲೈನ್ (ಸ್ಕೋರಿಂಗ್ ಮಾತ್ರ)           | ~0.045 | ~22 M  |
| ಬೇಸ್ಲೈನ್ + RoutingEvent (2 ಸಿಂಕ್ಗಳು) | ~0.168 | ~5.9 M |
| ಬೇಸ್ಲೈನ್ + ಈವೆಂಟ್ + OTel ಎನ್ಕ್ಯೂ     | ~0.163 | ~6.1 M |
| ಸಮಕಾಲೀನ (8 ಇಂಟರ್ಲೀವ್ಡ್ ಬರ್ಸ್ಟ್ಗಳು)   | ~0.18  | —      |

ಬೇಸ್ಲೈನ್ ಸ್ಕೋರಿಂಗ್ಗೆ ಹೋಲಿಸಿದರೆ ಈವೆಂಟ್-ಡಿಸ್ಪ್ಯಾಚ್ ವ್ಯತ್ಯಾಸವು ~0.12 µs/request ಆಗಿದೆ; OTel ಸಿಂಕ್
ಕೇವಲ ಕ್ಯೂಗೆ ಸೇರಿಸುತ್ತದೆ (O(1) ಬಫರ್ ಪುಶ್), ಹೀಗಾಗಿ ಅಳೆಯಬಹುದಾದ ಹೆಚ್ಚುವರಿ ವೆಚ್ಚವನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ. ಈ ಸಂಖ್ಯೆಗಳು
ಯಂತ್ರ-ನಿರ್ದಿಷ್ಟ ಮತ್ತು ಸಾಪೇಕ್ಷವಾಗಿವೆ — ಇವು ಪ್ರೊಡಕ್ಷನ್ ಖಾತರಿಯಲ್ಲ. v1ನ "~0.2 µs"
ಅಂಕಿ ಒಟ್ಟು ಅಂದಾಜಾಗಿತ್ತು; ಈ ವಿಧಾನವು ಸ್ಕೋರಿಂಗ್ ಬೇಸ್ಲೈನ್ ಅನ್ನು
ಈವೆಂಟ್-ಡಿಸ್ಪ್ಯಾಚ್ ವೆಚ್ಚದಿಂದ ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ.

## 3. ಗುಣಮಟ್ಟದ ಸಂಕೇತ (ಪ್ರತಿಕ್ರಿಯೆ-ಚಾಲಿತ ಪ್ರೊವೈಡರ್ ಸ್ಥಿತಿ)

ಫೈಲ್ಗಳು: `open-sse/services/routing/quality.ts`

v2 **ಕಾರ್ಯಾಚರಣಾತ್ಮಕ** ಗುಣಮಟ್ಟವನ್ನು **ಅರ್ಥಾತ್ಮಕ** ಗುಣಮಟ್ಟದಿಂದ ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ:

- **ಕಾರ್ಯಾಚರಣಾತ್ಮಕ** — ರೌಟಿಂಗ್ ಹಾಟ್ ಪಾತ್ನಿಂದ ಪಡೆಯಲಾಗುತ್ತದೆ (HTTP 4xx/5xx, ಸಂಪರ್ಕ
  ವೈಫಲ್ಯಗಳು, 429ಗಳು, ಅಸಮರ್ಪಕ ಪ್ರತಿಕ್ರಿಯೆಗಳು, ಸ್ಟ್ರೀಮ್ ಅಡಚಣೆಗಳು, `finish_reason=length`,
  ಶೂನ್ಯ-ಔಟ್ಪುಟ್ ಯಶಸ್ಸುಗಳು, ಲೇಟೆನ್ಸಿ/TTFT EWMA). 200 ಅನ್ನು ಅರ್ಥಾತ್ಮಕ
  ಗುಣಮಟ್ಟವೆಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.
- **ಅರ್ಥಾತ್ಮಕ** — ರಚಿಸಲಾದ ಔಟ್ಪುಟ್ನ ನಿಜವಾದ ಮೌಲ್ಯ. ಇದನ್ನು ಮೌಲ್ಯಮಾಪಕವು
  `setSemanticQuality()` ಮೂಲಕ ಮಾತ್ರ ಉತ್ಪಾದಿಸುತ್ತದೆ. ಯಾವುದಾದರೂ ಮೌಲ್ಯಮಾಪಕ ಅದನ್ನು ಒದಗಿಸುವವರೆಗೆ ಇದು `null`
  ಆಗಿರುತ್ತದೆ ಮತ್ತು ಕಾರ್ಯಾಚರಣಾತ್ಮಕ ಸ್ಕೋರ್ಗೆ ಎಂದಿಗೂ ಸೇರುವುದಿಲ್ಲ.

ಪ್ರತಿ-(ಪ್ರೊವೈಡರ್, ಮಾಡೆಲ್) ಸ್ಥಿತಿ (EWMA + ಮಿತಿಗೊಳಿಸಲಾದ ಕೌಂಟರ್ಗಳು):

- `successEwma` — ಫಲಿತಾಂಶದ ಯಶಸ್ಸಿನ EWMA (α=0.2).
- `latencyEwma` / `ttftEwma` — ಲೇಟೆನ್ಸಿಯ EWMA (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — ಮಾಡೆಲ್ ಅನ್ನು ಕೊನೆಯದಾಗಿ ಎಷ್ಟು ಇತ್ತೀಚೆಗೆ ಗಮನಿಸಲಾಗಿದೆ.

### ವಿಶ್ವಾಸಾರ್ಹತೆ / ಮಾದರಿ ಅರಿವು

`confidence = clamp01(samples / 50)`, ಮತ್ತು ಸ್ಕೋರರ್ಗೆ ಮರಳಿಸಲಾದ ಸ್ಕೋರ್ ಅನ್ನು
ತಟಸ್ಥ ಮಧ್ಯಬಿಂದುವಿನತ್ತ ಮಿಶ್ರಣ ಮಾಡಲಾಗುತ್ತದೆ:

```
score = 0.5 + confidence * (operational - 0.5)
```

ಪರಿಣಾಮಗಳು (ಪರೀಕ್ಷೆಗಳಿಂದ ದೃಢೀಕರಿಸಲಾಗಿದೆ):

- ಕೋಲ್ಡ್ ಪ್ರೊವೈಡರ್ (0 ಮಾದರಿಗಳು) **0.5** ಸ್ಕೋರ್ ಪಡೆಯುತ್ತದೆ — ಅನ್ಯಾಯವಾಗಿ ದಂಡಿಸಲ್ಪಡುವುದಿಲ್ಲ, ಆದರೆ
  ಸಾವಿರಾರು ದೃಢವಾದ ಅವಲೋಕನಗಳನ್ನು ಹೊಂದಿರುವ ಪ್ರೊವೈಡರ್ಗಿಂತ ಮೇಲುಗೈ ಸಾಧಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.
- 7 ಅದೃಷ್ಟದ ಯಶಸ್ಸುಗಳನ್ನು ಹೊಂದಿರುವ ಪ್ರೊವೈಡರ್ ಅನ್ನು 0.5ರತ್ತ ಎಳೆಯಲಾಗುತ್ತದೆ (ಆಶಾವಾದಿ
  ಪ್ರಾರಂಭಿಕ ಮೌಲ್ಯದಿಂದ ಎಂದಿಗೂ ಮೇಲುಗೈ ಸಾಧಿಸುವುದಿಲ್ಲ).
- 50+ ಮಾದರಿಗಳನ್ನು ಹೊಂದಿರುವ ಪ್ರೊವೈಡರ್ ತನ್ನ ನಿಜವಾದ ಕಾರ್ಯಾಚರಣಾತ್ಮಕ ಸ್ಕೋರ್ಗೆ ಒಮ್ಮುಖವಾಗುತ್ತದೆ.
- ಕುಸಿತ ಮತ್ತು ಚೇತರಿಕೆ ಕ್ರಮೇಣ ಸಂಭವಿಸುತ್ತವೆ (EWMA), ಮತ್ತು ಒಂದು ಪ್ರತ್ಯೇಕ ವೈಫಲ್ಯವು
  ಆರೋಗ್ಯಕರ ಪ್ರೊವೈಡರ್ ಅನ್ನು ಹಾಳುಮಾಡುವುದಿಲ್ಲ.

`ProviderQuality` ಇದು `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }` ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.

ಇದು `quality` ಸ್ಕೋರಿಂಗ್ ಅಂಶವಾಗಿ ಆಟೋ-ಕಾಂಬೊ ಸ್ಕೋರರ್ಗೆ ಪೂರೈಕೆಯಾಗುತ್ತದೆ:

- `open-sse/services/autoCombo/scoring.ts`ನಲ್ಲಿನ
  `ScoringFactors.quality` / `ScoringWeights.quality`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. ಮೊತ್ತವು 1.0 ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ.
- `buildAutoCandidates`, ಟ್ರ್ಯಾಕರ್ನಿಂದ `candidate.quality` ಅನ್ನು ಭರ್ತಿ ಮಾಡುತ್ತದೆ; ಡೇಟಾ
  ಇಲ್ಲದ ಅಭ್ಯರ್ಥಿಗಳು ಡೀಫಾಲ್ಟ್ ಆಗಿ ತಟಸ್ಥ **0.5** ಅನ್ನು ಪಡೆಯುತ್ತಾರೆ (ಕೋಲ್ಡ್ ಅಭ್ಯರ್ಥಿಯನ್ನು ಉತ್ತೇಜಿಸಲಾಗುವುದಿಲ್ಲ ಅಥವಾ
  ದಂಡಿಸಲಾಗುವುದಿಲ್ಲ).

ಕ್ಲೋಸ್ಡ್ ಲೂಪ್:

```
RoutingEvent → QualityTracker → getQualityScore → ಆಟೋ-ಕಾಂಬೊ ಗುಣಮಟ್ಟದ ಅಂಶ
      ↑                                                    │
      └────── ವಿನಂತಿಯ ಫಲಿತಾಂಶ (handleChatCore) ←────────────┘
```

### ಕಠಿಣ ಹೊರಗಿಡುವಿಕೆ ಮತ್ತು ಮೃದು ದಂಡನೆ

ಗುಣಮಟ್ಟದ ಸಂಕೇತವು ಕೇವಲ **ಮೃದು ಹೊಂದಾಣಿಕೆಯ ಆದ್ಯತೆ** ಆಗಿದೆ. ಕಠಿಣ ಹೊರಗಿಡುವಿಕೆಯು
ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ ಸ್ಟ್ಯಾಕ್ನಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ: ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ OPEN, ಕೋಟಾ ಮುಗಿದಿರುವುದು,
ದೃಢೀಕರಣ ವೈಫಲ್ಯ, ಮಾಡೆಲ್ ಲಾಕ್ಔಟ್ — ಇವುಗಳಲ್ಲಿ ಯಾವುದೂ ಗುಣಮಟ್ಟದ ಸ್ಕೋರ್ನಿಂದ ಪ್ರಭಾವಿತವಾಗುವುದಿಲ್ಲ.
ತಾತ್ಕಾಲಿಕವಾಗಿ ಗುಣಮಟ್ಟದ ಸ್ಕೋರ್ ಕುಸಿಯುವ ಪ್ರೊವೈಡರ್ಗೆ ಕಡಿಮೆ ಆದ್ಯತೆ ನೀಡಲಾಗುತ್ತದೆ, ಅದನ್ನು ಎಂದಿಗೂ
ಕಠಿಣವಾಗಿ ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾಗುವುದಿಲ್ಲ.

## 3b. ಕ್ಯಾನಾನಿಕಲ್ ಸ್ಟ್ರೀಮ್ ಟೈಮಿಂಗ್ (TTFT / ITL)

ಫೈಲ್ಗಳು: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` ಎಂಬುದು ಸ್ಟ್ರೀಮಿಂಗ್ ಪಥದ ಏಕೈಕ ಇನ್ಸ್ಟ್ರುಮೆಂಟೇಶನ್ ಸೀಮ್ ಆಗಿದ್ದು,
`createSSEStream` (`open-sse/utils/stream.ts`) ಗೆ ಜೋಡಿಸಲಾಗಿದೆ:

- `markByte()` — ಮೊದಲ ಅಪ್ಸ್ಟ್ರೀಮ್ ಚಂಕ್ ಸ್ವೀಕರಿಸಲಾಗಿದೆ.
- `markForward()` — ಕ್ಲೈಂಟ್ಗೆ ಫಾರ್ವರ್ಡ್ ಮಾಡಿದ ಮೊದಲ ಚಂಕ್ (TTFT ಗಾಗಿ ಬಳಸಲಾಗುತ್ತದೆ).
- `markInterrupted()` — ಸರಿಯಾಗಿ ಪೂರ್ಣಗೊಳ್ಳುವ ಮೊದಲು ಸ್ಟ್ರೀಮ್ ಟೈಮ್ಔಟ್/ಅಬಾರ್ಟ್/ದೋಷ.
- `ttft()` = ಮೊದಲ ಬಾರಿಗೆ ಫಾರ್ವರ್ಡ್ ಮಾಡಿದ SSE ಚಂಕ್ನ ಲೇಟೆನ್ಸಿ. **ಇದು ಟೋಕನ್-ಮಟ್ಟದ TTFT ಅಲ್ಲ** —
  ಒಂದೇ SSE ಚಂಕ್ ಶೂನ್ಯ/ಒಂದು/ಹಲವು ಟೋಕನ್ಗಳನ್ನು ಒಳಗೊಂಡಿರಬಹುದು. ಇದನ್ನು ನಿಖರವಾಗಿ ದಾಖಲಿಸಲಾಗಿದೆ.
- `avgItlMs()` = ಚಂಕ್ಗಳ ನಡುವಿನ ಸರಾಸರಿ ಅಂತರ (ITL ಗಾಗಿ ಚಂಕ್-ಲೇಟೆನ್ಸಿ ಪ್ರಾಕ್ಸಿ).

TTFT/ITL/interrupted ಮಾಹಿತಿಯು `RoutingEvent` (`ttftMs`, `itlMs`) ಗೆ ಹರಿಯುತ್ತದೆ ಮತ್ತು
OTel ಸಿಂಕ್ನಿಂದ GenAI/OmniRoute ಸ್ಪ್ಯಾನ್ ಅಟ್ರಿಬ್ಯೂಟ್ಗಳಾಗಿ ಎಕ್ಸ್ಪೋರ್ಟ್ ಆಗುತ್ತದೆ.

## 4. OpenTelemetry / GenAI ಅವಲೋಕನೀಯತೆ

ಫೈಲ್ಗಳು: `open-sse/services/routing/otel.ts`

- ಅವಲಂಬನೆ-ಮುಕ್ತ OTLP/HTTP JSON ಎಕ್ಸ್ಪೋರ್ಟರ್ (ಗ್ಲೋಬಲ್ `fetch` ಅನ್ನು ಬಳಸುತ್ತದೆ,
  `@opentelemetry/*` SDK ಅಲ್ಲ).
- ಸ್ಪ್ಯಾನ್ಗಳು GenAI ಸೆಮ್ಯಾಂಟಿಕ್ ಕನ್ವೆನ್ಷನ್ಗಳನ್ನು (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) ಹಾಗೂ OmniRoute ರೌಟಿಂಗ್
  ಅಟ್ರಿಬ್ಯೂಟ್ಗಳನ್ನು (ಫಲಿತಾಂಶ, ಸ್ಥಿತಿ, ttft, ಮರುಪ್ರಯತ್ನಗಳು, ಫಾಲ್ಬ್ಯಾಕ್) ಅನುಸರಿಸುತ್ತವೆ.
- `record()` ಬೌಂಡೆಡ್ ಬಫರ್ಗೆ ಮಾತ್ರ ಎನ್ಕ್ಯೂ ಮಾಡುತ್ತದೆ (O(1)); ಹಿನ್ನೆಲೆ ಟೈಮರ್
  `POST {endpoint}/v1/traces` ಮೂಲಕ ಅಸಿಂಕ್ರೋನಸ್ ಆಗಿ ಫ್ಲಶ್ ಮಾಡುತ್ತದೆ. ಓವರ್ಲೋಡ್ ಸಂದರ್ಭದಲ್ಲಿ
  ಅತ್ಯಂತ ಹಳೆಯ ಈವೆಂಟ್ಗಳನ್ನು ಕೈಬಿಡಲಾಗುತ್ತದೆ (`dropped` ಕೌಂಟರ್) — ಡೇಟಾ
  ಪ್ಲೇನ್ಗೆ ಎಂದಿಗೂ ಬ್ಯಾಕ್ಪ್ರೆಶರ್ ಉಂಟಾಗುವುದಿಲ್ಲ.
- **ಕಾನ್ಫಿಗರ್ ಮಾಡದಿದ್ದರೆ ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ.** `OMNIROUTE_OTEL_ENDPOINT` (ಅಥವಾ
  `OTEL_EXPORTER_OTLP_ENDPOINT`) ಅನ್ನು ಹೊಂದಿಸಬೇಕು; ಇಲ್ಲದಿದ್ದರೆ ಸಿಂಕ್ ಅನ್ನು
  ನೋಂದಾಯಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು ಯಾವುದೇ OTel ಕೋಡ್ ರನ್ ಆಗುವುದಿಲ್ಲ.

## 5. ವಿವರಣೀಯತೆ

- `GET /v1/explain/routing` ಇತ್ತೀಚಿನ `RoutingEvent`ಗಳನ್ನು (ನೈಜ
  ನಿರ್ಧಾರಗಳು, ಹೊಸದು ಮೊದಲು) ಮತ್ತು ಪ್ರತಿ-ಪ್ರೊವೈಡರ್/ಮಾದರಿಯ ಗುಣಮಟ್ಟದ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
- ದೃಢೀಕರಣವು `/v1/combos` ಅನ್ನು ಅನುಸರಿಸುತ್ತದೆ (Bearer API ಕೀ ಅಥವಾ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಷನ್;
  `REQUIRE_API_KEY=false` ಇರುವ ಏಕ-ಬಳಕೆದಾರರ ಸ್ಥಳೀಯ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ಗಳಲ್ಲಿ ಅನಾಮಧೇಯ ಪ್ರವೇಶ).
- ಪ್ರತಿ ಇನ್ವೊಕೇಶನ್ಗೆ ಸಂಬಂಧಿಸಿದ ಕಾಂಬೊ-ಮಟ್ಟದ ಟ್ರೇಸ್ಗಳು ಈಗಾಗಲೇ ಇರುವ
  `decisionTrace.ts` ಮೂಲಕ ಲಭ್ಯವಾಗುತ್ತವೆ (`X-OmniRoute-Combo-Trace` ಹೆಡರ್).
- ಸುರಕ್ಷತೆ: ಈವೆಂಟ್ಗಳು ರೌಟಿಂಗ್ ಮೆಟಾಡೇಟಾವನ್ನು ಮಾತ್ರ ಹೊಂದಿರುತ್ತವೆ; ಪ್ರಾಂಪ್ಟ್ಗಳು/ಬಾಡಿಗಳು/ಕ್ರೆಡೆನ್ಷಿಯಲ್ಗಳನ್ನು ಎಂದಿಗೂ ಹೊಂದಿರುವುದಿಲ್ಲ.

## 6. ಮೌಲ್ಯಮಾಪನ-ಪ್ಲೇನ್ ಏಕೀಕರಣ (ಭವಿಷ್ಯದ AGI ಸಿದ್ಧತೆ)

OmniRoute, Future AGI ಅನ್ನು (ಅಥವಾ ಯಾವುದೇ ಮೌಲ್ಯಮಾಪಕವನ್ನು) **ಸಂಭಾವ್ಯ
ಬುದ್ಧಿಮತ್ತೆ/ಮೌಲ್ಯಮಾಪನ ಬ್ಯಾಕೆಂಡ್ ಆಗಿ ಪರಿಗಣಿಸುತ್ತದೆಯೇ ಹೊರತು, ಅವಲಂಬನೆಯಾಗಿ ಅಲ್ಲ**. ಸೀಮ್ಗಳು:

- `RoutingEventSink` ಈವೆಂಟ್ಗಳನ್ನು ಅಸಿಂಕ್ರೋನಸ್ ಆಗಿ ಮೌಲ್ಯಮಾಪಕಕ್ಕೆ ಫಾರ್ವರ್ಡ್ ಮಾಡಬಹುದು.
- `MemoryRoutingEventStore` + ಗುಣಮಟ್ಟದ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಮೌಲ್ಯಮಾಪಕಕ್ಕೆ ಕಚ್ಚಾ
  ನಿರ್ಧಾರ ಸ್ಟ್ರೀಮ್ ಅನ್ನು ಒದಗಿಸುತ್ತವೆ.
- ಭವಿಷ್ಯದ `Evaluator` (ಡಿಟರ್ಮಿನಿಸ್ಟಿಕ್, ಸ್ಥಳೀಯ ಜಡ್ಜ್, HTTP, WASM) ಈವೆಂಟ್ಗಳು/ಟ್ರೇಸ್ಗಳನ್ನು
  ಬಳಸಿಕೊಂಡು, ಅದೇ `getQualityScore`/ಗುಣಮಟ್ಟ-ಫ್ಯಾಕ್ಟರ್ ಪಥಕ್ಕೆ ಫೀಡ್ ಆಗುವ
  `QualityScore` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
- ಈಗಾಗಲೇ ಇರುವ ಮೌಲ್ಯಮಾಪನ-ಚಾಲಿತ ರೌಟಿಂಗ್ (`open-sse/services/evalRouting.ts`) ಸಕ್ರಿಯಗೊಂಡಾಗ
  `eval_runs` ಪಾಸ್-ರೇಟ್ಗಳ ಆಧಾರದ ಮೇಲೆ ಕಾಂಬೊ ಟಾರ್ಗೆಟ್ಗಳನ್ನು ಈಗಾಗಲೇ ಮರುಕ್ರಮಗೊಳಿಸುತ್ತದೆ.

ವಿನಂತಿ ಪಥದಲ್ಲಿ ಯಾವುದೇ ಮೌಲ್ಯಮಾಪನವು ಸಿಂಕ್ರೋನಸ್ ಆಗಿ ನಡೆಯುವುದಿಲ್ಲ ಮತ್ತು ಮೌಲ್ಯಮಾಪಕವು
ಇಲ್ಲದಿದ್ದರೂ ಗೇಟ್ವೇ ಸಂಪೂರ್ಣವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.

## 7. ಅಂತಿಮ ಆರ್ಕಿಟೆಕ್ಚರಲ್ ವಿಮರ್ಶೆ

1. **ಸಿಂಕ್ರೋನಸ್ ಹಾಟ್ ಪಥದಲ್ಲಿ ಏನು ಉಳಿದಿದೆ?** ರೌಟಿಂಗ್/ಸ್ಕೋರಿಂಗ್, ಗಾರ್ಡ್ರೇಲ್
   ಪೂರ್ವ-ಪರಿಶೀಲನೆಗಳು, ಕ್ಯಾಶ್ ಲುಕ್ಅಪ್ ಮತ್ತು ಇನ್-ಮೆಮೊರಿ ಸಿಂಕ್ಗಳಿಗೆ ಒಂದು `emitRoutingEvent`
   ಫ್ಯಾನ್-ಔಟ್ (ಬೇಸ್ಲೈನ್ ಸ್ಕೋರಿಂಗ್ಗಿಂತ ~0.12 µs ಹೆಚ್ಚುವರಿ).
2. **ಯಾವುದನ್ನು ಅಸಿಂಕ್ರೋನಸ್ ಪ್ರೊಸೆಸಿಂಗ್ಗೆ ಸ್ಥಳಾಂತರಿಸಲಾಗಿದೆ?** OTel ಎಕ್ಸ್ಪೋರ್ಟ್
   (ಟೈಮರ್ + fetch), `call_logs`/ಬಳಕೆ ಪರ್ಸಿಸ್ಟೆನ್ಸ್, ಸೆಮ್ಯಾಂಟಿಕ್-ಕ್ಯಾಶ್ ರೈಟ್ಗಳು;
   ಗುಣಮಟ್ಟವು ಇನ್-ಮೆಮೊರಿ ಮತ್ತು O(1) ಆಗಿದೆ (ಅಸಿಂಕ್ ಅಗತ್ಯವಿಲ್ಲ).
3. **ರೌಟಿಂಗ್ ಫಲಿತಾಂಶವು ಫೀಡ್ಬ್ಯಾಕ್ ಆಗುವುದು ಹೇಗೆ?** `handleChatCore` ಒಂದು
   `RoutingEvent` ಅನ್ನು ಎಮಿಟ್ ಮಾಡುತ್ತದೆ → `QualityTracker` EWMA ಸ್ಥಿತಿಯನ್ನು ಅಪ್ಡೇಟ್ ಮಾಡುತ್ತದೆ →
   `getQualityScore` ಸ್ವಯಂ-ಕಾಂಬೊದ `quality` ಫ್ಯಾಕ್ಟರ್ಗೆ ಫೀಡ್ ಮಾಡುತ್ತದೆ.
4. **ಗುಣಮಟ್ಟವು ಭವಿಷ್ಯದ ರೌಟಿಂಗ್ ಮೇಲೆ ಹೇಗೆ ಪ್ರಭಾವ ಬೀರುತ್ತದೆ?** ಕಡಿಮೆ ಗುಣಮಟ್ಟದ ಸ್ಕೋರ್
   `scoreAutoTargets` ನಲ್ಲಿ ಆ ಪ್ರೊವೈಡರ್/ಮಾದರಿಯ ತೂಕಿತ ಸ್ಕೋರ್ ಅನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ; ಹೀಗಾಗಿ
   ಕಾರ್ಯಕ್ಷಮತೆ ಕುಸಿದ ಮಾದರಿಗಳಿಗೆ ಕ್ರಮೇಣ ಕಡಿಮೆ ಆದ್ಯತೆ ನೀಡಲಾಗುತ್ತದೆ ಮತ್ತು ಅವುಗಳ EWMA ಸುಧಾರಿಸಿದಂತೆ
   ಅವು ಚೇತರಿಸಿಕೊಳ್ಳುತ್ತವೆ.
5. **Future AGI ಒಂದು ಅವಲಂಬನೆಯಾಗದೆ ಹೇಗೆ ಏಕೀಕರಣಗೊಳ್ಳಬಹುದು?** `RoutingEventSink`
   ಇಂಟರ್ಫೇಸ್ / ಭವಿಷ್ಯದ `Evaluator` ಅಡಾಪ್ಟರ್ ಮೂಲಕ — ಯಾವುದೇ ಹಾರ್ಡ್ಕೋಡ್ ಮಾಡಿದ
   ಅವಲಂಬನೆ ಇಲ್ಲ.
6. **ಮೌಲ್ಯಮಾಪಕ ಲಭ್ಯವಿಲ್ಲದಿದ್ದರೆ ಏನಾಗುತ್ತದೆ?** ರೌಟಿಂಗ್ ಮೇಲೆ ಯಾವುದೇ ಪರಿಣಾಮವಿಲ್ಲ;
   ಯಾವುದೇ ವೀಕ್ಷಿತ ಸಿಗ್ನಲ್ ಇಲ್ಲದ ಮಾದರಿಗಳಿಗೆ ಗುಣಮಟ್ಟವು ನ್ಯೂಟ್ರಲ್ (1.0) ಮೌಲ್ಯವನ್ನು ಬಳಸುತ್ತದೆ.
7. **ಟೆಲಿಮೆಟ್ರಿ ಲಭ್ಯವಿಲ್ಲದಿದ್ದರೆ ಏನಾಗುತ್ತದೆ?** OTel ಸಿಂಕ್ ಅನ್ನು ನೋಂದಾಯಿಸುವುದೇ ಇಲ್ಲ;
   ಉಳಿದ ರೌಟಿಂಗ್ ಲೇಯರ್ ಯಾವುದೇ ಬದಲಾವಣೆಯಿಲ್ಲದೆ ರನ್ ಆಗುತ್ತದೆ.
8. **ಓವರ್ಲೋಡ್ ಸಂದರ್ಭದಲ್ಲಿ ಏನಾಗುತ್ತದೆ?** OTel ಬಫರ್ ಅತ್ಯಂತ ಹಳೆಯ ಈವೆಂಟ್ಗಳನ್ನು
   ಕೈಬಿಡುತ್ತದೆ; ಗುಣಮಟ್ಟ ಮತ್ತು ರಿಂಗ್ ಬಫರ್ ವಿನ್ಯಾಸದಿಂದಲೇ ಬೌಂಡೆಡ್ ಆಗಿವೆ; ಯಾವುದೇ ಬ್ಯಾಕ್ಪ್ರೆಶರ್ ಇಲ್ಲ.
9. **ಕುಸಿತದ ನಂತರ ಪ್ರೊವೈಡರ್ ಸ್ಥಿತಿ ಹೇಗೆ ಚೇತರಿಸಿಕೊಳ್ಳುತ್ತದೆ?** ಯಶಸ್ಸುಗಳು ಸಂಗ್ರಹವಾದಂತೆ
   EWMA ಮರು-ಅಭಿಸರಿಸುತ್ತದೆ; ವಾರ್ಮ್ಅಪ್ ಕೋಲ್ಡ್ ಮಾದರಿಗಳನ್ನು ನ್ಯೂಟ್ರಲ್ ಆಗಿರಿಸುತ್ತದೆ; ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್
   ಸ್ವತಂತ್ರವಾಗಿ HALF_OPEN ಪ್ರೋಬ್ಗಳ ಮೂಲಕ ಚೇತರಿಸಿಕೊಳ್ಳುತ್ತದೆ.
10. **ಪ್ರಸ್ತಾಪಿಸಲಾದ ಯಾವ ವೈಶಿಷ್ಟ್ಯಗಳನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಅಳವಡಿಸಲಾಗಿಲ್ಲ ಮತ್ತು ಏಕೆ?**
    - ಶ್ಯಾಡೋ ಟ್ರಾಫಿಕ್ / ಪ್ರಯೋಗಗಳು — ಈಗಾಗಲೇ ಅಳವಡಿಸಲಾಗಿದೆ
      (`combo/shadowRouting.ts`); ಮರುನಿರ್ಮಿಸಲಾಗಿಲ್ಲ.
    - ಗಾರ್ಡ್ರೇಲ್ಗಳು — ಈಗಾಗಲೇ ಅಳವಡಿಸಲಾಗಿದೆ (`src/lib/guardrails/`); ನಕಲು ಮಾಡಿಲ್ಲ.
    - ಸೆಮ್ಯಾಂಟಿಕ್ ಕ್ಯಾಶ್ — ಈಗಾಗಲೇ ಅಳವಡಿಸಲಾಗಿದೆ (`src/lib/semanticCache.ts`); ನಕಲು
      ಮಾಡಿಲ್ಲ.
    - ಸಂಪೂರ್ಣ ಪ್ರಯೋಗ-ನಿರ್ವಹಣಾ ಪ್ಲಾಟ್ಫಾರ್ಮ್, ಡೇಟಾಸೆಟ್ ಟೂಲಿಂಗ್, ಪ್ರಾಂಪ್ಟ್-ಆಪ್ಟಿಮೈಸೇಶನ್
      ಪ್ಲಾಟ್ಫಾರ್ಮ್, ವೆಕ್ಟರ್ DB ಅಥವಾ ಕಡ್ಡಾಯ ಬಾಹ್ಯ OTel ಇನ್ಫ್ರಾಸ್ಟ್ರಕ್ಚರ್ — ಹಗುರವಾದ
      ಡೇಟಾ ಪ್ಲೇನ್ನ ವ್ಯಾಪ್ತಿಗೆ ಹೊರತಾಗಿದೆ.
    - Rust `RoutingEvent` ಸ್ಟ್ರಕ್ಟ್ — ಡೇಟಾ ಪ್ಲೇನ್ TypeScriptನಲ್ಲಿದೆ; TS ಟೈಪ್
      ಅದಕ್ಕೆ ಹೊಂದಿಸಿದ ಸಮಾನರೂಪವಾಗಿದೆ.

  ನಿರ್ಧಾರಾತ್ಮಕ ಎಂಡ್-ಟು-ಎಂಡ್ ಲೂಪ್: ಆರೋಗ್ಯಕರ → ಕುಸಿತ → ಚೇತರಿಕೆ → ಕ್ಷಣಿಕ ವ್ಯತ್ಯಯ, ಜೊತೆಗೆ
  ಕೋಲ್ಡ್-ಸ್ಟಾರ್ಟ್ ಮತ್ತು ಅದೃಷ್ಟಶಾಲಿ-ಕೋಲ್ಡ್-ಪ್ರೊವೈಡರ್ ಸನ್ನಿವೇಶಗಳು.
- `tests/unit/stream-timing.test.ts` — TTFT (ಮೊದಲು-ಫಾರ್ವರ್ಡ್-ಆದ-ಚಂಕ್), ITL,
  ಮೊದಲ-ಬೈಟ್ ಮತ್ತು ಮೊದಲ-ಫಾರ್ವರ್ಡ್, ಅಡಚಣೆ, ದೋಷಪೂರಿತ/ಖಾಲಿ ಚಂಕ್ ಸುರಕ್ಷತೆ.
