ಈ ದಸ್ತಾವೇಜು OmniRouteನಲ್ಲಿನ ಎಲ್ಲಾ CI ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳಿಗೆ ಅಧಿಕೃತ ಉಲ್ಲೇಖವಾಗಿದೆ.
ಇದು ಪ್ರತಿಯೊಂದು ಗೇಟ್, ಅದು ಏನನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ, ಅದು ಯಾವ CI ಜಾಬ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ, ಅದು
ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ ಅಥವಾ ಪಾಸ್/ಫೇಲ್ ನೀತಿಯನ್ನು ಬಳಸುತ್ತದೆಯೇ ಮತ್ತು ಅದು ಬಿಲ್ಡ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆಯೇ ಅಥವಾ ಸಲಹಾತ್ಮಕವಾಗಿದೆಯೇ ಎಂಬುದನ್ನು ವಿವರಿಸುತ್ತದೆ.

ಸಂಕ್ಷಿಪ್ತ ಸಾರಾಂಶ ಮತ್ತು ಅನುಮತಿಪಟ್ಟಿ ನೀತಿಗಾಗಿ, `AGENTS.md`ನಲ್ಲಿರುವ "ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳು ಮತ್ತು ರ್ಯಾಚೆಟ್ಗಳು" ವಿಭಾಗವನ್ನು
ನೋಡಿ. ಇದೇ ಸಿಸ್ಟಮ್ನ ವಿಮರ್ಶಾತ್ಮಕ ಮೌಲ್ಯಮಾಪನ, ಪಕ್ವತೆಯ ವರ್ಗೀಕರಣ ಮತ್ತು ಉಪಕರಣ-ಸ್ವತಂತ್ರ
ಮರುಅನುಷ್ಠಾನ ಯೋಜನೆಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ ಪ್ಲೇಬುಕ್](../ops/QUALITY_GATE_PLAYBOOK.md) ನೋಡಿ.

## ಗೇಟ್ ಇನ್ವೆಂಟರಿ ಮತ್ತು ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆ ಪ್ರೊಫೈಲ್ಗಳು

### ಅಭ್ಯರ್ಥಿ ಪ್ರವೇಶ

CI ಮತ್ತು Quality Gates ವರ್ಕ್ಫ್ಲೋಗಳು ಪ್ರತಿಯೊಂದೂ ಸ್ಥಿರ ತೀರ್ಪನ್ನು ಹೊರಸೂಸುತ್ತವೆ: `Gate / CI` ಮತ್ತು
`Gate / Quality`. ಅವುಗಳ ಆವೃತ್ತಿಗೊಳಿಸಿದ ಪ್ರವೇಶ ನೀತಿಯು ಪ್ರತಿಯೊಂದು ಅಪ್ಸ್ಟ್ರೀಮ್ ಜಾಬ್ ಅನ್ನು
ಕಡ್ಡಾಯ ಅಥವಾ ಸಲಹಾತ್ಮಕ ಎಂದು ಪಟ್ಟಿಮಾಡುತ್ತದೆ. ಅನ್ವಯವಾಗುವ ಕಡ್ಡಾಯ ಜಾಬ್ ಯಶಸ್ವಿಯಾಗಬೇಕು: ಕಾಣೆಯಾದ,
ರದ್ದಾದ, ಬಿಟ್ಟುಬಿಡಲಾದ, ಬಾಕಿಯಿರುವ ಮತ್ತು ಅಜ್ಞಾತ ಫಲಿತಾಂಶಗಳು PASS ಅನ್ನು ಸ್ಥಾಪಿಸಲಾರವು. ಮಾನ್ಯವಾದ
docs-only ಅಥವಾ catalog-only ವರ್ಗೀಕರಣವು ಕೋಡ್ ಲೇನ್ ಅನ್ನು ಅನ್ವಯವಾಗದಂತೆ ಮಾಡಬಹುದು;
ಕರಡು PR ಅಂಗೀಕೃತ ಅಭ್ಯರ್ಥಿಯಲ್ಲ. `hotfix` ಲೇಬಲ್ ಸಾಕ್ಷ್ಯದ ಅಗತ್ಯವನ್ನು ಮನ್ನಾ ಮಾಡುವುದಿಲ್ಲ.

ಎರಡೂ ವರ್ಕ್ಫ್ಲೋಗಳು PR-ಗಳು ಮತ್ತು main/release ಬ್ರಾಂಚ್ಗಳಿಗೆ ಪುಶ್ಗಳು, ಹಸ್ತಚಾಲಿತ ಡಿಸ್ಪ್ಯಾಚ್ ಹಾಗೂ
ಮರ್ಜ್-ಗ್ರೂಪ್ ಈವೆಂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ. ಪುಶ್, ಡಿಸ್ಪ್ಯಾಚ್ ಮತ್ತು ಮರ್ಜ್-ಗ್ರೂಪ್ ಪೂರ್ಣ ಆಯ್ಕೆಯನ್ನು ಚಲಾಯಿಸುತ್ತವೆ. ಫೋರ್ಕ್ಗಳು
ಮತ್ತು ಮರ್ಜ್ ಗ್ರೂಪ್ಗಳು, ಸಾಮಾನ್ಯವಾಗಿ ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ ರನ್ನರ್ಗಳನ್ನು ಆಯ್ಕೆಮಾಡುವ ಜಾಬ್ಗಳಿಗೆ ಹೋಸ್ಟ್ ಮಾಡಿದ ರನ್ನರ್ಗಳನ್ನು
ಬಳಸುತ್ತವೆ; ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಸಾಕಷ್ಟು ಹೋಸ್ಟ್ ಮಾಡಿದ ಸಾಮರ್ಥ್ಯವನ್ನು ಪರಿಶೀಲಿಸಬೇಕು.

ಪ್ರತಿ JSON ರಸೀದಿಯು ಚೆಕ್ಔಟ್ ಮಾಡಿದ SHA, ವರ್ಕ್ಫ್ಲೋ ರನ್ ಮತ್ತು ಪ್ರಯತ್ನವನ್ನು ಗುರುತಿಸುತ್ತದೆ.
ಚೆಕ್ಔಟ್/ಈವೆಂಟ್ SHA ಅಸಾಮ್ಯವನ್ನು CLI ತಿರಸ್ಕರಿಸುತ್ತದೆ. ವರ್ಕ್ಫ್ಲೋ ಪರೀಕ್ಷೆಗಳು ನೀತಿ ಸದಸ್ಯತ್ವವನ್ನು
ತೀರ್ಪು ಜಾಬ್ನ `needs` ಪಟ್ಟಿಗೆ ಬದ್ಧಗೊಳಿಸುತ್ತವೆ, ಆದ್ದರಿಂದ ಹೊಸ ಅಥವಾ ತೆಗೆದುಹಾಕಿದ ಲೇನ್ ಮೌನವಾಗಿ ಕಣ್ಮರೆಯಾಗಲು ಸಾಧ್ಯವಿಲ್ಲ.
ರಸೀದಿಗಳು ತಮ್ಮದೇ ವರ್ಕ್ಫ್ಲೋವನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ, ಪ್ರಕಟಣೆ, ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ ಅಥವಾ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಸಲಹಾತ್ಮಕ ಸ್ಕ್ಯಾನರ್ನ ಆಂತರಿಕ ಅಂಶಗಳನ್ನಲ್ಲ. ಬ್ರಾಂಚ್ ನಿಯಮಗಳಲ್ಲಿ ಎರಡೂ ಚೆಕ್ ಹೆಸರುಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದು
ಪ್ರತ್ಯೇಕ ಆಡಳಿತಾತ್ಮಕ ಬದಲಾವಣೆಯಾಗಿದೆ; ಈ ಜಾಬ್ಗಳನ್ನು ಸೇರಿಸುವುದರಿಂದ ಮಾತ್ರ ಬ್ರಾಂಚ್ ರಕ್ಷಿತವಾಗುವುದಿಲ್ಲ.

### ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಇನ್ವೆಂಟರಿ

ಆವೃತ್ತಿಗೊಳಿಸಿದ npm-ಅಲಿಯಾಸ್ ಇನ್ವೆಂಟರಿ ಮತ್ತು ಸ್ಥಿರ-ಸ್ಕ್ಯಾನ್ ಸದಸ್ಯತ್ವವು
`config/quality/gate-manifest.json` ನಲ್ಲಿ ಇವೆ. ಸ್ಕ್ರಿಪ್ಟ್ ಹೆಸರುಗಳು ಮತ್ತು ನಿಖರ ಕಮಾಂಡ್ಗಳನ್ನು
`package.json` ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸಲು `npm run check:gate-manifest` ಅನ್ನು ಚಲಾಯಿಸಿ; ಸೇರ್ಪಡೆಗಳು, ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ಮತ್ತು
ಕಮಾಂಡ್ ವ್ಯತ್ಯಾಸಗಳು ಸ್ಥಳೀಯ ಹುಕ್ ಹಾಗೂ CI-ಯಲ್ಲಿನ ಬದಲಾವಣೆ-ವರ್ಗೀಕರಣ ಜಾಬ್ಗಳೆರಡನ್ನೂ ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
ಅಲಿಯಾಸ್ ಎಂಬುದು ವರ್ಕ್ಫ್ಲೋ ಜಾಬ್, ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಇನ್ಸ್ಟಾನ್ಸ್ ಅಥವಾ ಟೆಸ್ಟ್ ಕೇಸ್ ಅಲ್ಲ: ಈ ಎಣಿಕೆಗಳನ್ನು
ಪರಸ್ಪರ ವಿನಿಮಯಸಾಧ್ಯವೆಂದು ಪ್ರಸ್ತುತಪಡಿಸಬಾರದು.

ಆಯ್ಕೆಮಾಡಿದ ಅಲಿಯಾಸ್ಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸದೆ ಪರಿಶೀಲಿಸಲು `npm run quality:scan -- --list` ಅಥವಾ `npm run quality:scan:fast -- --list`
ಬಳಸಿ. ರನ್ನರ್ npm ಎಂಟ್ರಿಪಾಯಿಂಟ್ ಅನ್ನು ಆಹ್ವಾನಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದರ ರನ್ಟೈಮ್ (ಕಾನ್ಫಿಗರ್ ಮಾಡಿರುವಲ್ಲಿ Bun ಸೇರಿದಂತೆ) ಉಳಿಯುತ್ತದೆ.
ಮ್ಯಾನಿಫೆಸ್ಟ್ ಆ ಪ್ರೊಫೈಲ್ಗಳ ಹೊರಗಿನ ಅಲಿಯಾಸ್ಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಆಹ್ವಾನಿಸಲಾದವುಗಳೆಂದು ದಾಖಲಿಸುತ್ತದೆ, ಮತ್ತು
ಓದಲು-ಮಾತ್ರವಾದ ಸ್ಕ್ಯಾನ್ ಪ್ರೊಫೈಲ್ಗಳಲ್ಲಿ ನಿರ್ವಹಣಾ ಕಮಾಂಡ್ಗಳನ್ನು ನಿಷೇಧಿಸಲಾಗಿದೆ.

ಈ ಪ್ರೊಫೈಲ್ಗಳು ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಅನ್ನು ಮಾತ್ರ ಒಳಗೊಳ್ಳುತ್ತವೆ. ಅವು ಉತ್ಪನ್ನ ಪರೀಕ್ಷೆಗಳು,
ಕವರೇಜ್, ಪ್ಯಾಕೇಜಿಂಗ್, ಬಾಹ್ಯ ಚೆಕ್ಗಳು ಅಥವಾ ಅಭ್ಯರ್ಥಿಯ ಸಂಪೂರ್ಣ ಬಿಡುಗಡೆ ಅಂಗೀಕಾರವನ್ನು ಪ್ರಮಾಣೀಕರಿಸುವುದಿಲ್ಲ.
ವರ್ಕ್ಫ್ಲೋ ಪ್ರವೇಶವು ಲಿಂಕ್ ಮಾಡಲಾದ `config/quality/admission-policy.json` ಮತ್ತು
`scripts/quality/admission-verdict.mjs` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಬಿಡುಗಡೆ-ವೀಕ್ಷಕ ಪ್ರೊಫೈಲ್ಗಳು ಪ್ರತ್ಯೇಕವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ;
ಅವುಗಳಿಗೆ ಅನ್ವಯವಾಗುವ ಚೆಕ್ಗಳು ಮತ್ತು ರಸೀದಿಗಳನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸಿ. ಕೆಳಗಿನ ಗದ್ಯರೂಪದ
ಇನ್ವೆಂಟರಿ ಒಂದು ಉಲ್ಲೇಖವೇ ಹೊರತು, ಗೇಟ್ ನಿಜವಾಗಿಯೂ ಚಲಾಯಿತೆಂಬುದಕ್ಕೆ ಪುರಾವೆಯಲ್ಲ.

ಸ್ಕ್ರಿಪ್ಟ್ಗಳು `scripts/check/` (ನೀತಿ ಗೇಟ್ಗಳು) ಮತ್ತು `scripts/quality/` (ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್) ಅಡಿಯಲ್ಲಿ ಇವೆ.
CI-ಯ ಸತ್ಯದ ಮೂಲವು `.github/workflows/ci.yml` ಆಗಿದೆ.

### ಬಿಡುಗಡೆ PR ವೇಗದ-ಮಾರ್ಗ (`quality.yml`)

`.github/workflows/quality.yml` main/release PR-ಗಳು, ರಕ್ಷಿತ-ಬ್ರಾಂಚ್

#### ಮರೆತುಹೋದ ಸಹೋದರ ಪರೀಕ್ಷೆಗಳ ವರದಿ

`npm run check:forgotten-sibling-tests` ಪರೀಕ್ಷಾ-ಪರಿಣಾಮ ನಕ್ಷೆಯ ಹಿಂದಿರುವ ಇಂಪೋರ್ಟ್ ರಿಸಾಲ್ವರ್ ಅನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ.
ಬದಲಾದ ಪ್ರತಿಯೊಂದು ಪ್ರೊಡಕ್ಷನ್ ಮಾಡ್ಯೂಲ್ಗಾಗಿ, ಸಂಭಾವ್ಯ
ಪರೀಕ್ಷೆಯು ಪುಲ್-ರಿಕ್ವೆಸ್ಟ್ ಡಿಫ್ನಲ್ಲಿ ಇಲ್ಲದಿದ್ದಾಗ ಇದು ನಿರ್ಣಾಯಕ `changed module/symbol -> static consumer -> candidate sibling test` ಸರಪಳಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.
ಯಾವುದೇ ತಡೆಯುವ ರೋಲ್ಔಟ್ಗೆ ಮುನ್ನ ಕ್ಯಾಲಿಬ್ರೇಶನ್ಗಾಗಿ Markdown ಸಾರಾಂಶ ಮತ್ತು JSON ಫಲಿತಾಂಶವನ್ನು
`forgotten-sibling-tests` ವರ್ಕ್ಫ್ಲೋ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

ಬ್ಯಾರೆಲ್ ಮರು-ರಫ್ತುಗಳು ಮತ್ತು ಡೈನಾಮಿಕ್ ಆಮದುಗಳು ರೆಸಲ್ಯೂಷನ್ ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಸ್ಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿವೆ; ಅವು ಎಂದಿಗೂ
ತಡೆಯುವ ಫಲಿತಾಂಶವನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ. ಪರಿಶೀಲಿಸಲಾದ ವಿನಾಯಿತಿಗಳು
`config/quality/forgotten-sibling-allowlist.json` ನಲ್ಲಿ ಇರುತ್ತವೆ. ಪ್ರತಿ ನಮೂದಿನಲ್ಲಿ ಗ್ರಾಹಕ ಮತ್ತು ಅಭ್ಯರ್ಥಿ
ಪರೀಕ್ಷೆಯ ಹೆಸರನ್ನು ನಮೂದಿಸಬೇಕು, ನಿರ್ದಿಷ್ಟ ತಾರ್ಕಿಕ ಕಾರಣವನ್ನು ನೀಡಬೇಕು ಮತ್ತು GitHub issue ಅಥವಾ pull requestಗೆ ಲಿಂಕ್ ಮಾಡಬೇಕು. ದೋಷಪೂರಿತ ನಮೂದುಗಳು
ಮುಚ್ಚಿದ ಸ್ಥಿತಿಯಲ್ಲಿ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ. ಅಳಿಸಲಾದ ಅಭ್ಯರ್ಥಿ ಪರೀಕ್ಷೆ ಅಥವಾ `.skip`/`.todo` ಸೇರಿಸುವ diff ಅನ್ನು ವಿನಾಯಿತಿಗಳು ನಿರ್ಬಂಧಿಸಲಾರವು;
assertion ದುರ್ಬಲಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಇತರ ಮರೆಮಾಚುವಿಕೆಗಳು ಸ್ವತಂತ್ರವಾಗಿ ತಡೆಯುವ
`check:test-masking` ಗೇಟ್ನ ನಿಯಂತ್ರಣದಲ್ಲಿಯೇ ಇರುತ್ತವೆ.

#### `check-ui-value-drift` — ಹಳೆಯ-ಅನುವಾದ ಗೇಟ್

ಇತರ ಗೇಟ್ಗಳು ರಚನಾತ್ಮಕವಾಗಿ ಗುರುತಿಸಲಾಗದ ಏಕೈಕ i18n regression ಅನ್ನು ಇದು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ: ಇಂಗ್ಲಿಷ್ value ಅನ್ನು
ಮರುಬರೆಯಲಾಗಿದ್ದರೂ, _ಹಿಂದಿನ_ ಇಂಗ್ಲಿಷ್ನಿಂದ ಪಡೆದ ಅನುವಾದಗಳು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತವೆ; ಪರಿಣಾಮವಾಗಿ
ಇಂಗ್ಲಿಷ್ ಹೊರತಾದ ಭಾಷೆಗಳ ಬಳಕೆದಾರರು ಆತ್ಮವಿಶ್ವಾಸದಿಂದ ಬರೆದಿರುವ, ಆದರೆ ಈಗ ತಪ್ಪಾಗಿರುವ ಪಠ್ಯವನ್ನೇ ಓದುತ್ತಿರುತ್ತಾರೆ.

ಇದು ನಿಜವಾಗಿಯೂ ಬಿಡುಗಡೆಯಾಗಿತ್ತು. Antigravity login helper ಸೇರಿಸಲಾದಾಗ (#5203)
`oauthModal.googleOAuthWarning` ಅನ್ನು ಮರುಬರೆಯಲಾಯಿತು; **43 ಲೊಕೇಲ್ಗಳಲ್ಲಿ 39** ಲೊಕೇಲ್ಗಳು ಆಪರೇಟರ್ಗಳಿಗೆ "ಸಂಪೂರ್ಣ
URL ಅನ್ನು ನಕಲಿಸಿ ಮತ್ತು ಅದನ್ನು ಕೆಳಗೆ ಅಂಟಿಸಿ" ಎಂದು ಹೇಳುವ ಪಠ್ಯವನ್ನೇ ಉಳಿಸಿಕೊಂಡಿದ್ದವು — ಆ provider ಗಾಗಿ ಪೂರ್ಣಗೊಳ್ಳಲು ಸಾಧ್ಯವಿಲ್ಲದ flow. ಈ ಕೆಳಗಿನ ಕಾರಣಗಳಿಂದ
#8463 ವರೆಗೆ ಇದು ಗಮನಕ್ಕೆ ಬರಲಿಲ್ಲ:

- `sync-ui-keys` **ಇಲ್ಲದಿರುವ** keys ಅನ್ನು ಮಾತ್ರ backfill ಮಾಡುತ್ತದೆ, **ಹಳೆಯದಾದ** keys ಅನ್ನು ಎಂದಿಗೂ ಮಾಡುವುದಿಲ್ಲ;
- `check-ui-keys-coverage` key _ಇರುವಿಕೆಯನ್ನು_ ಎಣಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಹಳೆಯ ಅನುವಾದವೂ ಒಳಗೊಂಡಿದೆ ಎಂದು ಪರಿಗಣಿಸಲ್ಪಡುತ್ತದೆ;
- `check-translation-drift` ಎಂಬುದು `docs/i18n/<locale>/**.md` documentation mirrors ಅನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ —
  ಅದು `src/i18n/messages/*.json` ಅನ್ನು ಎಂದಿಗೂ ಓದುವುದಿಲ್ಲ. 2026-09 ಮರು-ಸಿಂಕ್ನಿಂದ ಜಾಬ್ `docs-sync-strict` ನಲ್ಲಿ ತಡೆಯಲಾಗುತ್ತಿದೆ:
  core doc ಅನ್ನು ಸಂಪಾದಿಸಿ → `npm run i18n:run -- --files=<doc>` (ವಿಭಾಗ-ಮಟ್ಟದ, ಕಡಿಮೆ ವೆಚ್ಚದ).

**ಡಿಫ್-ಅರಿವುಳ್ಳದ್ದು, ಬೇಸ್ಲೈನ್-ಆಧಾರಿತವಲ್ಲ.** ಇದು ವಿಲೀನದ ಮೂಲದಲ್ಲಿರುವ `en.json` ಅನ್ನು
ವರ್ಕಿಂಗ್ ಟ್ರೀಯೊಂದಿಗೆ ಹೋಲಿಸುತ್ತದೆ; ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯ ಬದಲಾಗಿರುವ ಪ್ರತಿಯೊಂದು ಕೀಗಾಗಿ, ಇನ್ನೂ
ಬದಲಾಗದ ಅನುವಾದವನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಲೊಕೇಲ್ ಹಳತಾಗಿದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ **ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಬಾಕಿಯನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ** — ದೀರ್ಘಕಾಲದಿಂದ ಇರುವ ಅನುವಾದವು ಯಾವ ಹಳೆಯ ಇಂಗ್ಲಿಷ್ನಿಂದ ಬಂದಿದೆ ಎಂಬುದನ್ನು ಡಿಫ್
ಬಹಿರಂಗಪಡಿಸಲಾರದು, ಆದ್ದರಿಂದ ಗೇಟ್ ಪ್ರಸ್ತುತ ಬದಲಾವಣೆಯು ಸ್ಪರ್ಶಿಸುವುದನ್ನು ಮಾತ್ರ ನಿರ್ಣಯಿಸುತ್ತದೆ.
ಪರ್ಯಾಯವು (ಪ್ರತಿ-ಕೀ ಹ್ಯಾಶ್ ಬೇಸ್ಲೈನ್) ಸುಮಾರು 600 KB ಗಾತ್ರದ ರಚಿಸಲಾದ ಫೈಲ್ ಅಗತ್ಯಪಡಿಸುತ್ತದೆ,
ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅತಿ ದೊಡ್ಡ ಬೇಸ್ಲೈನ್ಗಿಂತ 3× ದೊಡ್ಡದಾಗಿದ್ದು, ಪ್ರತಿ i18n PR ನಲ್ಲೂ ಬದಲಾವಣೆಗಳನ್ನು ಉಂಟುಮಾಡುತ್ತದೆ.

ಇದನ್ನು ಪೂರೈಸಲು ಎರಡು ಮಾರ್ಗಗಳಿವೆ:

1. ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಅನುವಾದಗಳನ್ನು ನವೀಕರಿಸಿ, ಅಥವಾ
2. ಅವುಗಳನ್ನು `__MISSING__:<new english>` ಎಂದು ಹೊಂದಿಸಿ — ಆಗ ರನ್ಟೈಮ್ ಸರಿಪಡಿಸಿದ ಇಂಗ್ಲಿಷ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ಮತ್ತು ಕೀ ಅನುವಾದಕ್ಕಾಗಿ ಸರದಿಗೆ ಸೇರುತ್ತದೆ.

ಸ್ಟ್ರಿಂಗ್ನ **ಅರ್ಥ** ಬದಲಾಗಿದ್ದರೆ, **ಕೀಗೆ ಮರುಹೆಸರಿಸುವುದಕ್ಕೆ** ಆದ್ಯತೆ ನೀಡಿ: ಹೊಸ ಕೀ
ಹಳತಾದ ಅನುವಾದವನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. #8463 ಬಳಸಿದ ಮಾದರಿ ಇದೇ.

```bash
npm run i18n:check-value-drift          # ಕಟ್ಟುನಿಟ್ಟಿನದು (CI ಚಲಾಯಿಸುವುದು)
npm run i18n:check-value-drift:warn     # ವರದಿ ಮಾತ್ರ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ಮೂಲ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಓದಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ (ಬೇಸ್ ref ಇಲ್ಲದ ಶಾಲೋ
ಕ್ಲೋನ್), `check-openapi-breaking` ಅನ್ನು ಅನುಸರಿಸುವಂತೆ, `SKIP reason=base-unresolved` ಜೊತೆಗೆ 0 ಅನ್ನು ನಿರ್ಗಮನ ಮೌಲ್ಯವಾಗಿ ನೀಡುತ್ತದೆ.

  (`scripts/quality/baseline-headroom.mjs`). ರಾತ್ರಿಯ `baseline-headroom` ಕೆಲಸವು ಕೋಷ್ಟಕವನ್ನು ಸಕ್ರಿಯ ಸಮಸ್ಯೆ

  ಅದನ್ನು ಮೀರಿದ್ದರೆ `headroom-alert` ಲೇಬಲ್ ಅನ್ನು ಸೇರಿಸುತ್ತದೆ. ಆ ಸಮಸ್ಯೆಯೇ ಮುಂಚಿತ ಎಚ್ಚರಿಕೆ: ಕೆಲವೇ ದಿನಗಳಲ್ಲಿ ತುಂಬುವ ಬಜೆಟ್ ಎಂದರೆ,
  ಸಡಿಲಿಕೆಯನ್ನು ಇಡೀ ತಂಡವಲ್ಲದೆ ಕೆಲವೇ PRಗಳು ಬಳಸಿಕೊಳ್ಳುತ್ತಿವೆ — ಸಮಸ್ಯೆಯಿರುವ ಗೇಟ್ನ `_rebaseline_*` ಟಿಪ್ಪಣಿಗಳನ್ನು ನೋಡಿ.

**ಹೊಸ-ಕೋಡ್ ಮೋಡ್ (ಕೋಡ್ ಬರೆಯುವಾಗಲೇ ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ) — 2026-08-30 ರಿಂದ, PR ವೇಗದ ಮಾರ್ಗಕ್ಕೆ ಮಾತ್ರ**

`pull_request` ಈವೆಂಟ್ಗಳಲ್ಲಿ `quality.yml`, `check:file-size`,
`check:complexity-ratchets` ಮತ್ತು `check:dead-code` ಗೆ `--base-ref <PR base SHA>` ಅನ್ನು ರವಾನಿಸುತ್ತದೆ. ಆ ಮೋಡ್ನಲ್ಲಿ ಗೇಟ್,
HEAD ಅನ್ನು merge-base ಜೊತೆ **PR ಸ್ಪರ್ಶಿಸಿದ ಫೈಲ್ಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತಗೊಳಿಸಿ** ಹೋಲಿಸುತ್ತದೆ (`scripts/check/newCodeMode.mjs`:
merge-base ಅನ್ನು ತಾತ್ಕಾಲಿಕ `git worktree` ನಲ್ಲಿ ಸೃಷ್ಟಿಸಲಾಗುತ್ತದೆ, ESLint/knip ಅನ್ನು ಅಲ್ಲಿ ಮತ್ತು HEAD ಮೇಲೆ ಚಲಾಯಿಸಲಾಗುತ್ತದೆ,
ನಂತರ ಪ್ರತಿ-ಫೈಲ್ ಎಣಿಕೆಗಳ ವ್ಯತ್ಯಾಸವನ್ನು ಲೆಕ್ಕಿಸಲಾಗುತ್ತದೆ):

- **ತಡೆಹಿಡಿಯುವ** — PR ತಾನು ಬದಲಾಯಿಸಿದ ಫೈಲ್ಗಳಲ್ಲಿ ಸೈಕ್ಲೊಮ್ಯಾಟಿಕ್/ಕಾಗ್ನಿಟಿವ್ ಉಲ್ಲಂಘನೆಗಳು ಅಥವಾ ಬಳಕೆಯಾಗದ ಎಕ್ಸ್ಪೋರ್ಟ್ಗಳನ್ನು ಸೇರಿಸಿದೆ
  (ಲಾಗ್ನಲ್ಲಿ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ಸಲಹಾತ್ಮಕ** — ಸ್ಥಗಿತಗೊಳಿಸಿದ ಮೂಲಮಟ್ಟದ ವಿರುದ್ಧ ಜಾಗತಿಕ ಒಟ್ಟು. ಆನುವಂಶಿಕ ವ್ಯತ್ಯಾಸವು ನಿರ್ದೋಷಿ PR ಅನ್ನು ಎಂದಿಗೂ
  ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ; ಬಿಡುಗಡೆ ಸಮನ್ವಯದ ಸಮಯದಲ್ಲಿ ವ್ಯತ್ಯಾಸವನ್ನು ಮರು-ಸ್ಥಗಿತಗೊಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಹೆಚ್ಚುವರಿ ಅವಕಾಶದ ಕೆಲಸವು ಅದನ್ನು ಮೇಲ್ವಿಚಾರಣೆ ಮಾಡುತ್ತದೆ.

`workflow_dispatch` ಚಾಲನೆಗಳು, release-green ಪರಿಶೀಲನೆ ಮತ್ತು ರಾತ್ರಿಯ ಹೆಚ್ಚುವರಿ ಅವಕಾಶದ ಕೆಲಸಕ್ಕೆ PR ಮೂಲವಿಲ್ಲ
ಮತ್ತು ಅವು ನಿರಪೇಕ್ಷ (ಜಾಗತಿಕ) ಹೋಲಿಕೆಯನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ. ವ್ಯಾಪ್ತಿ, ನಕಲು ಮತ್ತು type-coverage ಸದ್ಯಕ್ಕೆ ಜಾಗತಿಕವಾಗಿಯೇ
ಉಳಿಯುತ್ತವೆ (ಅವುಗಳ ಉಪಕರಣಗಳು ಪ್ರತಿ-ಫೈಲ್ ವ್ಯತ್ಯಾಸವನ್ನು ಕಡಿಮೆ ವೆಚ್ಚದಲ್ಲಿ ಒದಗಿಸುವುದಿಲ್ಲ) — ಇದೇ ರೀತಿಯ ನಿರ್ವಹಣೆಗೆ ಅಭ್ಯರ್ಥಿಗಳು.

**v4.0 ನಲ್ಲಿ ಹಂತವನ್ನು ಮುಕ್ತಾಯಗೊಳಿಸುವುದು (LTS = ಹಿಂದಿಗಿಂತ ಹೆಚ್ಚು ಕಟ್ಟುನಿಟ್ಟು, "ಸಾಮಾನ್ಯ ಸ್ಥಿತಿಗೆ ಮರಳುವುದು" ಅಲ್ಲ)**

1. ಸ್ವಚ್ಛವಾದ `release/v4.0.0` ತುದಿಯಲ್ಲಿ: ದಾಖಲಾತಿಗಾಗಿ `npm run quality:headroom --json`, ನಂತರ
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ಪ್ರತಿಯೊಂದು typecheck ಗೇಟ್ನ
   `--update` — ಪ್ರತಿಯೊಂದು ಬೇಸ್ಲೈನ್ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕೆ ಇಳಿಯುತ್ತದೆ.
2. `quality-baseline.json` ನಿಂದ `_policy` ಅನ್ನು ಅಳಿಸಿ (`--require-tighten` ಮತ್ತು ರಾತ್ರಿಯ
   ಬ್ಯಾಂಕಿಂಗ್ ಅನ್ನು ಮರುಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ), `check-openapi-coverage.mjs` ನಲ್ಲಿ `THRESHOLD = 36` (ಅಥವಾ ಹೆಚ್ಚಿನದು) ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ.
3. ಮಾಡ್ಯುಲರೀಕರಣದಿಂದ ಪ್ರಯೋಜನ ದೊರೆತ ಕಡೆಗಳಲ್ಲಿ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕಿಂತಲೂ ಹೆಚ್ಚು ಬಿಗಿಗೊಳಿಸಿ: file-size `cap` ಅನ್ನು ಮತ್ತೆ 1000
   (ಅಥವಾ 800) ಗೆ, coverage ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು +5 ಗೆ, ಮಾಡ್ಯುಲರೀಕರಿಸಿದ ಪ್ಯಾಕೇಜ್ಗಳ dead exports ಅನ್ನು 0 ಗೆ ಹೊಂದಿಸಿ.

ಹೆಚ್ಚು ಹಿಂಜರಿದರೆ, ಬಿಲ್ಡ್ ವಿಫಲವಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿರುವ ಮೆಟ್ರಿಕ್ಗಳು:

| ಮೆಟ್ರಿಕ್              | ದಿಕ್ಕು | ಅರ್ಥ                                  |
| --------------------- | ------ | ------------------------------------- |
| `eslintWarnings`      | `down` | ESLint ಎಚ್ಚರಿಕೆಗಳ ಸಂಖ್ಯೆ ಹೆಚ್ಚಾಗಬಾರದು |
| `coverage.statements` | `up`   | ಸ್ಟೇಟ್ಮೆಂಟ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು      |
| `coverage.lines`      | `up`   | ಲೈನ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು             |
| `coverage.functions`  | `up`   | ಫಂಕ್ಷನ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು          |
| `coverage.branches`   | `up`   | ಬ್ರಾಂಚ್ ಕವರೇಜ್ ಕಡಿಮೆಯಾಗಬಾರದು          |

ನೈಜ ಸುಧಾರಣೆಯ ನಂತರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ನವೀಕರಿಸಲು:

```bash

git add quality-baseline.json
```

`--update` ಫ್ಲ್ಯಾಗ್ ಪ್ರಸ್ತುತ ಅಳೆಯಲಾದ ಮೌಲ್ಯಗಳನ್ನು `quality-baseline.json` ಗೆ ಬರೆಯುತ್ತದೆ.
ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸಿದ ಬದಲಾವಣೆಯ ಜೊತೆಯಲ್ಲೇ ಈ ಫೈಲ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ. ಬೇಸ್ಲೈನ್ ಅನ್ನು
ನವೀಕರಿಸದೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸುವ PR ಅನ್ನು `--require-tighten` ಪತ್ತೆಹಚ್ಚುತ್ತದೆ (ಹಂತ 6A.5,
ಅನುಷ್ಠಾನ ಬಾಕಿಯಿದೆ).

### CodeQL ರ್ಯಾಚೆಟ್: ರಿಫ್ರೆಶ್ ಆವರ್ತನೆ ಮತ್ತು ಹಸ್ತಚಾಲಿತ ಟ್ರಿಗರ್

`check:codeql-ratchet` **ರೆಪೊ ಸ್ಥಿತಿಯನ್ನು ಓದುತ್ತದೆ; ಅದನ್ನು ವೇಳಾಪಟ್ಟಿಯ ಪ್ರಕಾರ ರಿಫ್ರೆಶ್ ಮಾಡಲಾಗುತ್ತದೆ — ಪ್ರತಿ PR ಗೆ ಅಲ್ಲ.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ವರದಿ ಮಾಡುವ
`state: configured`, `schedule: weekly` ಎಂಬುದು GitHub ನ ಡೀಫಾಲ್ಟ್-ಸೆಟಪ್ ಸ್ಕ್ಯಾನ್ ಆಗಿದ್ದು,
ಪ್ರತಿ ಪುಶ್ಗೆ ನಡೆಯುವ ವಿಶ್ಲೇಷಣೆಯಲ್ಲ. ಪರಿಣಾಮ: ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸುವ PR ವಿಲೀನಗೊಂಡ ನಂತರವೂ,
ಮುಂದಿನ ನಿಗದಿತ ಸ್ಕ್ಯಾನ್ ನಡೆಯುವವರೆಗೆ ರ್ಯಾಚೆಟ್ ಹಳೆಯ, ಹೆಚ್ಚಿನ ಸಂಖ್ಯೆಯನ್ನೇ ಓದುತ್ತಿರುತ್ತದೆ —
ಆದ್ದರಿಂದ ಸ್ಕ್ಯಾನ್ ನವೀಕರಿಸುವವರೆಗೆ, ಸರಿಪಡಿಸಿದ PR ನ ಸ್ವಂತ ಫಾಲೋ-ಅಪ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಪ್ರತಿಯೊಂದು
ತೆರೆದ PR ನಲ್ಲಿಯೂ ಅದು ಹಿಂಜರಿತವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

**ಹಸ್ತಚಾಲಿತ ರಿಫ್ರೆಶ್**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ವಿಶ್ಲೇಷಣೆಯನ್ನು
ಮತ್ತೆ ಚಲಾಯಿಸಿ, ಕೆಲವೇ ನಿಮಿಷಗಳಲ್ಲಿ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಮರುಪ್ರಕಟಿಸುತ್ತದೆ. ಮೊದಲು `.github/workflows/codeql.yml`
ಓದಿ — GitHub ನ **"default setup" ಜೊತೆಗೆ ಅದು ಸಂಘರ್ಷಿಸುವುದರಿಂದಲೇ** ಇದು `workflow_dispatch`-ಗೆ ಮಾತ್ರ
ಸೀಮಿತವಾಗಿದೆ ಎಂದು ಅದರ ಹೆಡರ್ ವಿವರಿಸುತ್ತದೆ (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`). `push`/`pull_request`/
`schedule` ಟ್ರಿಗರ್ಗಳನ್ನು ಮರುಸ್ಥಾಪಿಸಲು ಮೊದಲು **ಮಾಲೀಕರ ಕ್ರಮ** ಅಗತ್ಯ: Settings → Code security →
CodeQL: Default → Advanced. ಆ ಬದಲಾವಣೆ ಮಾಡದೆ `schedule:` ಟ್ರಿಗರ್ ಸೇರಿಸಬೇಡಿ — ಅದು
ವಿಫಲಗೊಳ್ಳುವ ರನ್ಗಳನ್ನು ಮಾತ್ರ ಉಂಟುಮಾಡುತ್ತದೆ.

**ಸಂಖ್ಯೆ ಕಡಿಮೆಯಾದ ನಂತರ ಬೇಸ್ಲೈನ್ ಅನ್ನು ಬಿಗಿಗೊಳಿಸಿ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ಹೊಸದಾಗಿ ಅಳೆಯಲಾದ ಸಂಖ್ಯೆಯನ್ನು `quality-baseline.json` →
`metrics.codeqlAlerts.value` ಗೆ ಬರೆಯುತ್ತದೆ; ಹೀಗಾಗಿ ಹಳೆಯ ಗರಿಷ್ಠ ಮಿತಿಯವರೆಗೆ ಮತ್ತೆ ಹಿಂಜರಿಯುವುದನ್ನು
ರ್ಯಾಚೆಟ್ ಮೌನವಾಗಿ ಅನುಮತಿಸುವುದಿಲ್ಲ. ಕಾರ್ಯನಿರ್ವಹಿತ ಉದಾಹರಣೆ (2026-09-02/03): PR #12502 ನೈಜವಾದ
7 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸಿತು (ಅಳೆಯಲಾದ ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳು 13 → 6); ಅದಕ್ಕೆ ಹೊಂದುವಂತೆ PR #12530
ಸ್ಥಿರಗೊಳಿಸಲಾದ ಬೇಸ್ಲೈನ್ ಅನ್ನು 11 → 6 ಗೆ ಬಿಗಿಗೊಳಿಸಿತು; ನಂತರ ಉಳಿದ 6 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಪ್ರತಿಯೊಂದು
ಎಚ್ಚರಿಕೆಗೆ ಪ್ರತ್ಯೇಕ ಸಮರ್ಥನೆ ನೀಡಿ ವಜಾಗೊಳಿಸಿ, ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳ ಸಂಖ್ಯೆಯನ್ನು 0 ಗೆ ಇಳಿಸಲಾಯಿತು.

**ವಜಾಗೊಳಿಸುವಿಕೆಗಳು ಆಪರೇಟರ್ನ ನಿರ್ಧಾರ (ಕಠಿಣ ನಿಯಮ #14)** — ವಜಾಗೊಳಿಸುವಿಕೆಯ ಕಾಮೆಂಟ್ನಲ್ಲಿ
ತಾಂತ್ರಿಕ ಸಮರ್ಥನೆಯನ್ನು ದಾಖಲಿಸದೆ CodeQL ಎಚ್ಚರಿಕೆಯನ್ನು ಎಂದಿಗೂ ವಜಾಗೊಳಿಸಬೇಡಿ: ಅಪ್ಸ್ಟ್ರೀಮ್-ಪ್ರೋಟೋಕಾಲ್
ಅವಶ್ಯಕತೆಗೆ `won't fix`, ಟೆಸ್ಟ್ ಫಿಕ್ಸ್ಚರ್ಗೆ `used in tests`, CodeQL ಗುರುತಿಸಲಾಗದ ಸ್ಯಾನಿಟೈಸರ್ಗೆ
`false positive` (ಪೂರ್ವನಿದರ್ಶನ: `docs/security/ERROR_SANITIZATION.md`).

## ರಿಲೀಸ್-ಮಟ್ಟದ ರ್ಯಾಚೆಟ್ ಡ್ರಿಫ್ಟ್ (WS5.5, v3.8.49)

PURE ರಿಲೀಸ್ ಟಿಪ್ನಲ್ಲಿ ಒಂದು ರ್ಯಾಚೆಟ್ (ಫೈಲ್ ಗಾತ್ರ, ಸಂಕೀರ್ಣತೆ, eslint ಎಚ್ಚರಿಕೆಗಳು) ಹಿಮ್ಮೆಟ್ಟಿದಾಗ —
ಅಂದರೆ, ಮರ್ಜ್ಗಳ ಸಂಯೋಜನೆಯು ಅದನ್ನು ಹಿಮ್ಮೆಟ್ಟಿಸಿದೆ ಮತ್ತು ಯಾವುದೇ ಒಂದು PR ತನ್ನದೇ ಬ್ರಾಂಚ್ನಲ್ಲಿ ಆ
ರಿಗ್ರೆಷನ್ ಅನ್ನು ಪುನರುತ್ಪಾದಿಸುವುದಿಲ್ಲವಾದರೆ — ಅದನ್ನು ಸರಿಪಡಿಸುವ ಹೊಣೆ **ರಿಲೀಸ್ ಕ್ಯಾಪ್ಟನ್ಗೆ, ಒಮ್ಮೆ ಮಾತ್ರ,
ರಿಲೀಸ್ ಬ್ರಾಂಚ್ನಲ್ಲಿ** ಸೇರಿದೆ: ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್/ರಿಫ್ಯಾಕ್ಟರ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ; ದಾಖಲಿಸಲಾದ
ಸಮರ್ಥನೆ ನಮೂದಿನೊಂದಿಗೆ ಮಾತ್ರ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಿ. ಸಂಯೋಜನೆಯಿಂದಾದ ಡ್ರಿಫ್ಟ್ ಅನ್ನು ಕೊಡುಗೆದಾರರ PR ಮೇಲೆ ಎಂದಿಗೂ
ಹೊರಿಸಬೇಡಿ ಮತ್ತು ಪ್ರತಿ-PR ಗೆ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಬೇಡಿ (ಅದು ನೈಜ ರಿಗ್ರೆಷನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ). ಮೊದಲು ವ್ಯತ್ಯಾಸವನ್ನು ಗುರುತಿಸಿ:
ನಿಮ್ಮ PR ಅದಕ್ಕೆ ಕಾರಣವೆಂದು ಊಹಿಸುವ ಮೊದಲು ಪ್ರೋಬ್ ವರ್ಕ್ಟ್ರೀಯಲ್ಲಿ ಶುದ್ಧ ಟಿಪ್ ವಿರುದ್ಧದ ಕೆಂಪು ಸ್ಥಿತಿಯನ್ನು ಪುನರುತ್ಪಾದಿಸಿ.

## ರ್ಯಾಚೆಟ್ ಇಳಿಕೆಗಳನ್ನು ಬ್ಯಾಂಕ್ ಮಾಡುವುದು — ಕೆಳಮುಖ ದಿಕ್ಕು (#8584)

ರ್ಯಾಚೆಟ್ ಅರ್ಧದಷ್ಟು ಮಾತ್ರ ಸ್ವಯಂಚಾಲಿತವಾಗಿದೆ, ಮತ್ತು ಅದು ತಪ್ಪಾದ ಅರ್ಧವಾಗಿದೆ. ಮಿತಿಯನ್ನು **ಹೆಚ್ಚಿಸುವುದು**
ಹತ್ತು ಸೆಕೆಂಡ್ ತೆಗೆದುಕೊಳ್ಳುವ ಕೈಯಾರೆ JSON ತಿದ್ದುಪಡಿಯಾಗಿದ್ದು, ಕೆಂಪಾಗಿರುವ PR ಅನ್ನು ಅನ್ಬ್ಲಾಕ್ ಮಾಡುವ ಅತ್ಯಂತ ವೇಗದ ವಿಧಾನವಾಗಿದೆ.
ಮಿತಿಯನ್ನು **ಕಡಿಮೆ ಮಾಡಲು** ಯಾರಾದರೂ `--update` ಚಲಾಯಿಸಿ ಫಲಿತಾಂಶವನ್ನು ಕಮಿಟ್ ಮಾಡಬೇಕು — ಮತ್ತು
`bank-ratchet-shrinks` ಜಾಬ್ ಬರುವವರೆಗೂ, ಯಾವುದೇ ವರ್ಕ್ಫ್ಲೋ ಅದನ್ನು ಚಲಾಯಿಸುತ್ತಿರಲಿಲ್ಲ. ಮಾಪನ ಮಾಡಿದ ಪರಿಣಾಮ
(2026-07-25): ಈಗಾಗಲೇ 800-ಸಾಲಿನ ಹೊಸ-ಫೈಲ್ ಮಿತಿಯಲ್ಲಿ ಅಥವಾ ಅದಕ್ಕಿಂತ ಕೆಳಗಿರುವ 18 ಸ್ಥಗಿತಗೊಳಿಸಿದ ಫೈಲ್ಗಳು, ಅತ್ಯಂತ ಕೆಟ್ಟದ್ದು
132× (`src/shared/validation/schemas.ts`, 2,523 ಮಿತಿಯನ್ನು ಹೊಂದಿರುವ 19 ಸಾಲುಗಳು); ಸಂಕೀರ್ಣತೆಯ ಗರಿಷ್ಠ ಮಿತಿ
~37 ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸುವ ಟಿಪ್ಪಣಿಗಳಾದ್ಯಂತ `1794 → 2169` ಕ್ಕೆ ಏರಿತು, ನಿಖರವಾಗಿ ಒಂದೇ ಇಳಿಕೆಯೊಂದಿಗೆ
(−1); ಮತ್ತು "ಮುಂದಿನ ಚಕ್ರದಲ್ಲಿ `--update` ಮೂಲಕ ಬಿಗಿಗೊಳಿಸಿ" ಎಂದು 31 ಬಾರಿ ಬರೆದು, ಒಮ್ಮೆ ಮಾತ್ರ ಪಾಲಿಸಲಾಯಿತು.
ಅದಕ್ಕೆ ಕಾರಣವಾದ ಕೋಡ್ಗಿಂತಲೂ ಹೆಚ್ಚು ಕಾಲ ಉಳಿಯುವ ಮಿತಿಯು, ಪೂರ್ಣಗೊಂಡ ಪ್ರತಿಯೊಂದು ವಿಭಜನೆಯನ್ನು ಆ ಫೈಲ್ ಅನ್ನು ಮುಂದಿನ ಬಾರಿ
ತಿದ್ದುಪಡಿ ಮಾಡುವವರಿಗೆ ಬೆಳವಣಿಗೆಯ ಅನುಮತಿಯಾಗಿ ಮೌನವಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ.

`nightly-release-green.yml` → ಜಾಬ್ **`bank-ratchet-shrinks`** ಆ ಲೂಪ್ ಅನ್ನು ಮುಚ್ಚುತ್ತದೆ:

|           |                                                                                                                      |
| --------- | -------------------------------------------------------------------------------------------------------------------- |
| ಚಾಲನೆ     | `schedule` (ದಿನಕ್ಕೆ 3×) + `workflow_dispatch` — ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ `push` **ಅಲ್ಲ**                                     |
| ಮಾಪನ      | ಅತ್ಯುನ್ನತ `release/vX.Y.Z`, `release-green` ನಲ್ಲಿರುವಂತೆಯೇ ಅದೇ ರೆಸಲ್ಯೂಷನ್ + ಇಂಜೆಕ್ಷನ್ ಗಾರ್ಡ್                          |
| ಬರೆಯುವುದು | `check:file-size --update` ಮತ್ತು `check:complexity-ratchets --update` (ಎರಡೂ ವಿನ್ಯಾಸತಃ ಇಳಿಕೆ-ಮಾತ್ರ)                   |
| ಪರಿಶೀಲನೆ  | `npm run check:ratchet-bank` (`scripts/quality/verify-ratchet-bank.mjs`)                                             |
| ರವಾನೆ     | ರಿಲೀಸ್ ಬ್ರಾಂಚ್ ವಿರುದ್ಧ ಯಾವಾಗಲೂ ಪ್ರಸ್ತುತವಾಗಿರುವ ಒಂದೇ PR — ಬಲವಂತವಾಗಿ ಅಪ್ಡೇಟ್ ಮಾಡಲಾಗುತ್ತದೆ, ಎಂದಿಗೂ ಸ್ಪ್ಯಾಮ್ ಮಾಡುವುದಿಲ್ಲ |

ಬ್ಯಾಂಕಿಂಗ್ ಅನ್ನು ಪ್ರತಿ-push ಬದಲಿಗೆ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ ಮಾಡಲಾಗುತ್ತದೆ, ಏಕೆಂದರೆ ಇದಕ್ಕೆ ಯಾವುದೇ ಲೇಟೆನ್ಸಿ ಅವಶ್ಯಕತೆ ಇಲ್ಲ
(8 ಗಂಟೆಗಳೊಳಗೆ ಬ್ಯಾಂಕ್ ಮಾಡಿದ ಇಳಿಕೆ ಸಾಕು), ಆದರೆ ಪ್ರತಿ-ಮರ್ಜ್ ಚಾಲನೆಯು ಮರ್ಜ್ ಅಭಿಯಾನಗಳ ಸಮಯದಲ್ಲಿ PR ಬ್ರಾಂಚ್ ಅನ್ನು
ಪದೇಪದೇ ಮರುನಿರ್ಮಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಬಾರಿ ಪೂರ್ಣ ESLint ಸ್ಕ್ಯಾನ್ನ ವೆಚ್ಚವನ್ನು ಭರಿಸುತ್ತದೆ. ಪತ್ತೆಹಚ್ಚುವಿಕೆಯು
push (`release-green`) ನಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ; ಬ್ಯಾಂಕಿಂಗ್ ಮಾತ್ರ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ ನಡೆಯುತ್ತದೆ.

### ಸುರಕ್ಷತಾ ಪರಿಶೀಲಕ

ಜಾಬ್ ಮೇಲ್ವಿಚಾರಣೆಯಿಲ್ಲದೆ ಬೇಸ್ಲೈನ್ಗಳಿಗೆ ಬರೆಯುತ್ತದೆ, ಆದ್ದರಿಂದ `verify-ratchet-bank.mjs` ಅದನ್ನು
ಸ್ವೀಕಾರಾರ್ಹವಾಗಿಸುತ್ತದೆ. ಅದು `--update` ನಂತರದ ಟ್ರೀ ಅನ್ನು `HEAD` ವಿರುದ್ಧ diff ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು
ಬದಲಾವಣೆಯೂ ಕೆಳಗಿನವುಗಳಲ್ಲಿ ಒಂದಾಗಿರದಿದ್ದರೆ, **ಯಾವುದೇ ಕಮಿಟ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು ಜಾಬ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ**
— ಯಾವುದೇ PR ತೆರೆಯುವುದಿಲ್ಲ:

- `frozen` / `testFrozen` ಸಂಖ್ಯಾತ್ಮಕ ನಮೂದನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ** ಅಥವಾ **ತೆಗೆದುಹಾಕಲಾಗಿದೆ**
- `complexity-baseline.json` → `count` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**

ಬೇರಾವುದೇ ಬದಲಾವಣೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ: ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸುವುದು, ನಮೂದನ್ನು ಸೇರಿಸುವುದು, `cap`/`testCap` ಅನ್ನು ಬದಲಿಸುವುದು ಅಥವಾ
`_rebaseline_*` ಟಿಪ್ಪಣಿಯನ್ನು ಅಳಿಸುವುದು/ಮರುಬರೆಯುವುದು (ಪ್ರತಿ ಗರಿಷ್ಠ ಮಿತಿ ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ ಎಂಬುದಕ್ಕೆ ಆ ಟಿಪ್ಪಣಿಗಳು ಆಡಿಟ್ ದಾಖಲೆಯಾಗಿದ್ದು,
ಫೈಲ್ ನಮೂದುಗಳಂತೆಯೇ ಅದೇ `frozen` ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ).
ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಬಲ್ಲ ಬಾಟ್ ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಗಿಂತ ಖಂಡಿತವಾಗಿಯೂ ಕೆಟ್ಟದಾಗಿರುತ್ತದೆ. ರಿಗ್ರೆಷನ್
ಗಾರ್ಡ್: `tests/unit/verify-ratchet-bank.test.ts`.

ಜಾಬ್ ಎಂದಿಗೂ `release/*` ಗೆ push ಮಾಡುವುದಿಲ್ಲ — ಒಬ್ಬ ವ್ಯಕ್ತಿ PR ಅನ್ನು ಮರ್ಜ್ ಮಾಡುತ್ತಾರೆ, ಆದ್ದರಿಂದ ತಪ್ಪಾದ ಮಾಪನವು
ಪರಿಶೀಲಿಸದೆ ಸೇರಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಅನುಮತಿ ಪಟ್ಟಿ ನೀತಿ

ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉಲ್ಲಂಘನೆಗಳಿಂದ ವಿಫಲವಾಗಬಾರದ ಪ್ರತಿಯೊಂದು ಗೇಟ್ ಸ್ಥಿರಗೊಳಿಸಲಾದ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸುತ್ತದೆ
(ಉದಾ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). ನೀತಿ ಹೀಗಿದೆ:

**ಮೂಲ ಕಾರಣವನ್ನು ಸರಿಪಡಿಸಿ; ಉಲ್ಲಂಘನೆಯು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದು, ಅದನ್ನು ಅದೇ PRನಲ್ಲಿ
ಸರಿಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ ಮಾತ್ರ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸಿ.**

ಅನುಮತಿ ಪಟ್ಟಿಗೆ ನಮೂದನ್ನು ಸೇರಿಸುವಾಗ:

1. ಸಮರ್ಥನೆಯೊಂದಿಗೆ ಒಂದು ಕಾಮೆಂಟ್ ಸೇರಿಸಿ.
2. ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯನ್ನು ಉಲ್ಲೇಖಿಸಿ (ಉದಾ., `// #3498 — ಹಂತ 2ರ ವೈಶಿಷ್ಟ್ಯ, ಇನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸಿಲ್ಲ`).
3. ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸುವ ಅದೇ PRನಲ್ಲಿ ನಮೂದನ್ನು ತೆಗೆದುಹಾಕಿ — ಇನ್ನು ಮುಂದೆ ಸಕ್ರಿಯ ಉಲ್ಲಂಘನೆಯನ್ನು
   ನಿಗ್ರಹಿಸದ ಹಳತಾದ ನಮೂದು ಸ್ವತಃ ಒಂದು ದೋಷವಾಗಿದೆ (ಅನುಷ್ಠಾನಗೊಂಡ ನಂತರ 6A.3 stale-enforcement,
   ಅನಾಥ ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದಿನ ಕಾರಣದಿಂದ ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ).

ಪರೀಕ್ಷೆಗಳು ವೇಗವಾಗಿ ಪಾಸ್ ಆಗುವಂತೆ ಮಾಡಲು ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದುಗಳನ್ನು ಸೇರಿಸ**ಬೇಡಿ**. ಬೆಳೆಯುತ್ತಿರುವ
ಅನುಮತಿ ಪಟ್ಟಿಯೊಂದಿಗಿನ ಹಸಿರು ಗೇಟ್ ಗುಣಮಟ್ಟದ ಕುರಿತು ತಪ್ಪು ಭರವಸೆಯನ್ನು ನೀಡುತ್ತದೆ.

### ನಿಮ್ಮ PRನಲ್ಲಿ ಗೇಟ್ ವಿಫಲವಾದಾಗ

1. **ಗೇಟ್ ಔಟ್ಪುಟ್ ಅನ್ನು ಎಚ್ಚರಿಕೆಯಿಂದ ಓದಿ** — ಯಾವ ಫೈಲ್ ಅಥವಾ ಸಂಕೇತವು ನಿಯಮವನ್ನು ಉಲ್ಲಂಘಿಸಿದೆ
   ಎಂಬುದನ್ನು ಅದು ನಿಖರವಾಗಿ ತಿಳಿಸುತ್ತದೆ.
2. **ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸಿ** — ಬಹುತೇಕ ಗೇಟ್ಗಳು ನಿರ್ಣಾಯಕ ಫೈಲ್ಸಿಸ್ಟಮ್ ಪರಿಶೀಲನೆಗಳಾಗಿದ್ದು,
   ಕೋಡ್ ಸರಿಯಾದ ತಕ್ಷಣವೇ ಪಾಸ್ ಆಗುತ್ತವೆ.
3. **ಉಲ್ಲಂಘನೆಯು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದರೆ** (ಅಂದರೆ, ನೀವು ಅದನ್ನು ಪರಿಚಯಿಸಿಲ್ಲ, ಆದರೆ ಈಗ ಗೇಟ್
   ಅದನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ): ಸಮರ್ಥನೆಯ ಕಾಮೆಂಟ್ ಮತ್ತು ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯೊಂದಿಗೆ ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದನ್ನು ಸೇರಿಸಿ.
4. **ಗೇಟ್ ರ್ಯಾಚೆಟ್ ಆಗಿದ್ದರೆ** (ವ್ಯಾಪ್ತಿ, ESLint ಎಚ್ಚರಿಕೆಗಳು, ನಕಲು, ಸಂಕೀರ್ಣತೆ):
   ನಿಮ್ಮ ಬದಲಾವಣೆಯು ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹದಗೆಡಿಸಿದೆ. ಮೂಲ ಸಮಸ್ಯೆಯನ್ನು ಸರಿಪಡಿಸಿ ಅಥವಾ (ಅಪರೂಪವಾಗಿ) ಬದಲಾವಣೆಯು
   ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದ್ದು ಮೆಟ್ರಿಕ್ ಕುಸಿತವು ಸ್ವೀಕಾರಾರ್ಹವಾಗಿದ್ದರೆ `npm run quality:ratchet -- --update`
   ಅನ್ನು ಚಲಾಯಿಸಿ — ಆದರೆ PR ವಿವರಣೆಯಲ್ಲಿ ಕಾರಣವನ್ನು ದಾಖಲಿಸಿ.
5. **ಸಲಹಾತ್ಮಕ ಗೇಟ್ಗಳು** (`continue-on-error: true`) ಮಾಹಿತಿಗಾಗಿ ಮಾತ್ರ — ಅವು ವಿಲೀನವನ್ನು
   ತಡೆಯುವುದಿಲ್ಲ, ಆದರೆ CI ಸಾರಾಂಶದಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಆದರೂ ಅವುಗಳನ್ನು ಸರಿಪಡಿಸಿ.

## ಹೊಸ ಗೇಟ್ ಸೇರಿಸುವುದು

1. `scripts/check/check-<name>.mjs` (ಅಥವಾ `.ts`) ರಚಿಸಿ. ನೀತಿ ಗೇಟ್ಗಳು 0/1 ಸ್ಥಿತಿಯೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತವೆ.
   ರ್ಯಾಚೆಟ್-ಶೈಲಿಯ ಗೇಟ್ಗಳು `collect-metrics.mjs` ಮೂಲಕ `quality-metrics.json` ಗೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹೊರಸೂಸುತ್ತವೆ.
2. `package.json` ಗೆ `"check:<name>": "node scripts/check/check-<name>.mjs"` ಸೇರಿಸಿ.
3. ಸೂಕ್ತ ಜಾಬ್ ಅಡಿಯಲ್ಲಿ `.github/workflows/ci.yml` ನಲ್ಲಿ ಅದನ್ನು ಜೋಡಿಸಿ
   (ನೀತಿ → `lint` ಅಥವಾ `docs-sync-strict`; ರ್ಯಾಚೆಟ್ → `quality-gate`).
4. ಅದಕ್ಕೆ ಅನುಮತಿ ಪಟ್ಟಿ ಇದ್ದರೆ, ಹಳತಾದ ನಮೂದುಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪತ್ತೆಯಾಗುವಂತೆ
   `scripts/check/lib/allowlist.mjs` ನಿಂದ `reportStaleEntries()` ಅನ್ನು ಅನ್ವಯಿಸಿ.
5. ಗೇಟ್ನ ಪತ್ತೆ ತರ್ಕವನ್ನು ಒಳಗೊಂಡ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/build/` ನಲ್ಲಿ ಬರೆಯಿರಿ.
6. ಈ ಡಾಕ್ಯುಮೆಂಟ್ ಅನ್ನು ನವೀಕರಿಸಿ (ಸಂಬಂಧಿತ ಜಾಬ್ ಟೇಬಲ್ಗೆ ಒಂದು ಸಾಲನ್ನು ಸೇರಿಸಿ).

## ಏಜೆಂಟ್ ಉಪಕರಣಗಳು: LSP-in-the-loop (ಆಯ್ಕೆಯ ಮೇರೆಗೆ)

CI ಗೇಟ್ಗಳ ಜೊತೆಗೆ, OmniRoute ಒಂದು **ಆಯ್ಕೆಯ ಮೇರೆಗೆ ಬಳಸಬಹುದಾದ** `agent-lsp` ಸ್ಕ್ಯಾಫೋಲ್ಡ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
(ಪ್ರಾಜೆಕ್ಟ್-ಮಟ್ಟದ `.mcp.json`, Fase 7 Task 15). ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ಗಳಿಗೆ TypeScript ಭಾಷಾ ಸರ್ವರ್ ಅನ್ನು
ಒದಗಿಸಲು `.mcp.json` ರಚಿಸಿ, ಇದರಿಂದ ಅವು ಕೋಡ್ ಬರೆಯುವ **ಮೊದಲು** ಸಂಕೇತಗಳು /
ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಗಳನ್ನು ಪರಿಹರಿಸುತ್ತವೆ — ಮೂಲದಲ್ಲೇ "ಕಲ್ಪಿತ ಸಂಕೇತ" ದೋಷಗಳನ್ನು ಕಡಿತಗೊಳಿಸುವ
`typecheck:core` ಗೆ ಕಂಪೈಲ್-ಬಿಫೋರ್-ಕ್ಲೇಮ್ ಸಹಚರ. ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
ಸ್ವಯಂ-ಲೋಡ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ (MCP↔LSP ಬ್ರಿಡ್ಜ್ ಅನ್ನು ನೀವು ಆಯ್ಕೆಮಾಡಿ ಪರಿಶೀಲಿಸುತ್ತೀರಿ); ದೋಷಪೂರಿತ ನಮೂದು
ಕೇವಲ ಸಂಪರ್ಕ ದೋಷವನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸೆಷನ್ಗಳನ್ನು ಎಂದಿಗೂ ಸ್ಥಗಿತಗೊಳಿಸುವುದಿಲ್ಲ.

ಈ ದಾಸ್ತಾನನ್ನು 2026-06-17 ರಂದು `ci.yml` ಗೆ ಹೋಲಿಸಿ ಸಮನ್ವಯಗೊಳಿಸಲಾಗಿದೆ (ಹಿಂದಿನ ಆವೃತ್ತಿಯಲ್ಲಿ
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,
`check:dead-code`, `check:cognitive-complexity`, `check:type-coverage`,

ಕೆಳಗಿನ ತರ್ಕಬದ್ಧೀಕರಣ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಗುರುತಿಸಿದೆ. **ವಿಲೀನಗಳು ಯಾಂತ್ರಿಕ CI
ಬದಲಾವಣೆಗಳಾಗಿವೆ; ಬದಲಾವಣೆಗಳು/ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ಆಪರೇಟರ್ಗೆ ಮೀಸಲಾದ ನೀತಿ ನಿರ್ಧಾರಗಳಾಗಿವೆ.** ಕೆಳಗಿನ ಯಾವುದನ್ನೂ

### ವಿಲೀನ / ನಕಲು ನಿವಾರಣೆ (ಯಾಂತ್ರಿಕ, ಕಡಿಮೆ ಅಪಾಯ)

ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯನ್ನೂ 2026-06-17 ರಲ್ಲಿದ್ದ ಸಕ್ರಿಯ gate ಸ್ಥಿತಿಗೆ ಹೋಲಿಸಿ ಮೌಲ್ಯೀಕರಿಸಲಾಗಿದೆ (ನಂಬಿ, ಆದರೆ ಪರಿಶೀಲಿಸಿ);
ಹಲವು "ಸ್ಪಷ್ಟ" ವಿಲೀನಗಳು ಅಡಗಿದ ತಾಂತ್ರಿಕ ಸಾಲವನ್ನು ಮರೆಮಾಡುತ್ತವೆ ಎಂದು ಕಂಡುಬಂದಿದ್ದು, ಅವು **ನೇರವಾಗಿ ಬದಲಿಸಬಹುದಾದವುಗಳಲ್ಲ**.

- **`check:docs-sync` ಎರಡು ಬಾರಿ ಚಲಿಸುತ್ತದೆ** — `lint` job ನಲ್ಲಿ ಸ್ವತಂತ್ರವಾಗಿ ಮತ್ತು `check:docs-all` (`docs-sync-strict`) ಒಳಗೆ ಹಾಗೂ husky pre-commit hookನಲ್ಲಿ ಮತ್ತೊಮ್ಮೆ. ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** — ಸ್ವತಂತ್ರ `lint` invocation ತೆಗೆದುಹಾಕಲಾಗಿದೆ.
- **CVE ಸ್ಕ್ಯಾನಿಂಗ್** — ❌ **ಸ್ವಚ್ಛವಾದ ವಿಲೀನವಲ್ಲ.** ಯಾವುದೇ high/critical CVE ಕಂಡುಬಂದರೆ `audit:deps` ಕಡ್ಡಾಯವಾಗಿ ವಿಫಲವಾಗುತ್ತದೆ; `check:vuln-ratchet` (osv) baselineಗೆ ಹೋಲಿಸಿದಾಗ _ಹಿಂಜರಿತ_ ಉಂಟಾದರೆ ಮಾತ್ರ ವಿಫಲವಾಗುತ್ತದೆ (ಪ್ರಸ್ತುತ 1 MODERATE). ಅರ್ಥವ್ಯಾಪ್ತಿಗಳು ಭಿನ್ನವಾಗಿವೆ — `audit:deps` ತೆಗೆದುಹಾಕಿದರೆ ನಿರಪೇಕ್ಷ high/critical gate ಕಳೆದುಹೋಗುತ್ತದೆ. ಎರಡನ್ನೂ ಉಳಿಸಿಕೊಳ್ಳಿ.
- **Cycle ಪತ್ತೆ** — ❌ **ಸ್ವಚ್ಛವಾದ ವಿಲೀನವಲ್ಲ.** `check:circular-deps` (dpdm) **91 cycles** ವರದಿ ಮಾಡುತ್ತದೆ (ಅದಕ್ಕಾಗಿಯೇ ಅದು ಸಲಹಾತ್ಮಕವಾಗಿದೆ); ಅವುಗಳನ್ನು ಮೊದಲು ಪರಿಹರಿಸದೆ ಅದನ್ನು ತಡೆಗಟ್ಟುವ ಹಂತಕ್ಕೆ ಏರಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ, ಮತ್ತು green ಆಗಿರುವ, ಆಯ್ದ `check:cycles` ಗಿಂತ ಇದರ ವ್ಯಾಪ್ತಿ ವಿಶಾಲವಾಗಿದೆ. `check:cycles` ಅನ್ನು ತಡೆಗಟ್ಟುವಂತೆಯೇ ಉಳಿಸಿಕೊಳ್ಳಿ; 91 dpdm cyclesಗಳನ್ನು ಪರಿಹರಿಸುವುದು ಪ್ರತ್ಯೇಕ ಬಾಕಿಪಟ್ಟಿಯಾಗಿದೆ.
- **ಸಂಕೀರ್ಣತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ಒಂದೇ ESLint walk, ruleId ಪ್ರಕಾರ ಎಣಿಕೆ ಮಾಡುವುದರಿಂದ cyclomatic+max-lines ಮತ್ತು cognitive baselineಗಳು ಸ್ವತಂತ್ರವಾಗಿ ಉಳಿಯುತ್ತವೆ; ಸ್ಥಳೀಯ `--update` ಗಾಗಿ ಪ್ರತ್ಯೇಕ `check:complexity` / `check:cognitive-complexity` ಉಳಿದಿವೆ.
- **`/api` anti-hallucination** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ಯ ಒಂದೇ FS inventory, openapi-routes + docs-symbols ಇನ್ನೂ ಸ್ವತಂತ್ರವಾಗಿ ವರದಿ ಮಾಡುತ್ತವೆ; ಸ್ಥಳೀಯ runಗಳಿಗಾಗಿ ಪ್ರತ್ಯೇಕವಾದವುಗಳು ಉಳಿದಿವೆ.
- **`check:node-runtime` 11 jobಗಳಲ್ಲಿ ಚಲಿಸುತ್ತದೆ** — ⚠️ **ಕಡಿಮೆ ROI.** ಪ್ರತಿಯೊಂದೂ ಪ್ರತ್ಯೇಕ runner ಆಗಿದ್ದು check <1s ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ; ಅಗ್ಗದ ಪ್ರತಿ-job guard ಅನ್ನು ಕಳೆದುಕೊಳ್ಳುವುದಕ್ಕೆ ಪ್ರತಿಯಾಗಿ ಒಟ್ಟು ಉಳಿತಾಯ ~10s. ಈ ಬದಲಾವಣೆಯ ಗೊಂದಲಕ್ಕೆ ತಕ್ಕಷ್ಟು ಮೌಲ್ಯವಿಲ್ಲ.
- **CI lintನಲ್ಲಿನ `typecheck:noimplicit:core`** — ✅ **lint jobನಿಂದ ತೆಗೆದುಹಾಕಲಾಗಿದೆ** (ಇದು ಸಲಹಾತ್ಮಕ `continue-on-error` ಆಗಿತ್ತು); ತಡೆಗಟ್ಟುವ type surface ಎಂದರೆ `typecheck:core` + `check:type-coverage`. ಸ್ಥಳೀಯ script ಉಳಿಸಿಕೊಳ್ಳಲಾಗಿದೆ.

### ಬದಲಿಸಿ / ನಿರ್ಧರಿಸಿ (ಆಪರೇಟರ್ ನೀತಿ)

- `check:openapi-security-tiers` (ಸಲಹಾತ್ಮಕ) — ❌ **ನೇರವಾಗಿ ಬದಲಿಸಲಾಗುವುದಿಲ್ಲ.** ಇದು 0 ನೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ, ಆದರೆ `LOCAL_ONLY_API_PREFIXES` ಅಡಿಯಲ್ಲಿರುವ ಹಲವಾರು `traffic-inspector` routeಗಳಲ್ಲಿ `x-loopback-only: true` annotation ಇಲ್ಲವೆಂದು ಎಚ್ಚರಿಸುತ್ತದೆ. ಅದನ್ನು ಜಾರಿಗೊಳಿಸಲು ಮೊದಲು ಆ annotationಗಳನ್ನು `openapi.yaml` ಗೆ ಸೇರಿಸಬೇಕು.
- `typecheck:noimplicit:core` (ಸಲಹಾತ್ಮಕ) — ತಡೆಗಟ್ಟುವ `check:type-coverage` ratchet ಇದನ್ನು ಬಹುಮಟ್ಟಿಗೆ ಒಳಗೊಳ್ಳುತ್ತದೆ. ಇದನ್ನು ratchetಗೆ ಬದಲಿಸಿ ಅಥವಾ ಅನಗತ್ಯವಾಗಿ ಮರುಕಳಿಸುವ ಎರಡನೇ `tsc` pass ಅನ್ನು ತೆಗೆದುಹಾಕಿ.
- `test:vitest:ui` (ಈಗ **ತಡೆಗಟ್ಟುವಂತಿದೆ**) — ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದ ವೈಫಲ್ಯಗಳನ್ನು `vitest.config.ts` ನಲ್ಲಿ `// #8618` tracking commentಗಳೊಂದಿಗೆ ಸ್ಪಷ್ಟವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ; ಹೊಸ ವೈಫಲ್ಯಗಳು job ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
- `check:secrets` (gitleaks, ದಾಖಲಿಸಲಾದ 3 false-positiveಗಳಲ್ಲಿ ಸ್ಥಿರಗೊಳಿಸಲಾದ ತಡೆಗಟ್ಟುವ ratchet) — 0 ತಲುಪಲು ಆ 3 ಅನ್ನು allowlistಗೆ ಸೇರಿಸಿ, ಅಥವಾ ಸಲಹಾತ್ಮಕ ಹಂತಕ್ಕೆ ಇಳಿಸಿ. ಇದು GitHub native secret-scanning + `check:public-creds` ಜೊತೆ ಅತಿಕ್ರಮಿಸುತ್ತದೆ.
- `check:pr-evidence` (ತಡೆಗಟ್ಟುವ, PR-body ಗದ್ಯವನ್ನು greps ಮಾಡುತ್ತದೆ) — false-positive ಅಪಾಯ ಹೆಚ್ಚು; ಇದನ್ನು ತೆಗೆದುಹಾಕಿದರೆ Hard Rule #18 ಜಾರಿ ದುರ್ಬಲಗೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ ಇದು ನಿಜವಾದ ನೀತಿ ನಿರ್ಧಾರವಾಗಿದೆ.
- `semgrep` (ಸ್ವತಂತ್ರ ಸಲಹಾತ್ಮಕ) — OWASP familyಗಳಿಗೆ ಸಂಬಂಧಿಸಿದಂತೆ CodeQL ಜೊತೆ ಅತಿಕ್ರಮಿಸುತ್ತದೆ; ಅದರ baseline ಅನ್ನು ratchetಗೆ ಸಂಪರ್ಕಿಸಿ ಅಥವಾ ತೆಗೆದುಹಾಕಿ.
