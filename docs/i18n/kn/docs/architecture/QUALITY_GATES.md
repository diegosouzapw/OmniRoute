ಈ ದಸ್ತಾವೇಜು OmniRouteನಲ್ಲಿನ ಎಲ್ಲಾ CI ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳಿಗೆ ಅಧಿಕೃತ ಉಲ್ಲೇಖವಾಗಿದೆ.
ಇದು ಪ್ರತಿಯೊಂದು ಗೇಟ್, ಅದು ಏನನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ, ಅದು ಯಾವ CI ಜಾಬ್ನಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ, ಅದು
ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ ಅಥವಾ ಪಾಸ್/ಫೇಲ್ ನೀತಿಯನ್ನು ಬಳಸುತ್ತದೆಯೇ ಮತ್ತು ಅದು ಬಿಲ್ಡ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆಯೇ ಅಥವಾ ಸಲಹಾತ್ಮಕವಾಗಿದೆಯೇ ಎಂಬುದನ್ನು ವಿವರಿಸುತ್ತದೆ.

ಸಂಕ್ಷಿಪ್ತ ಸಾರಾಂಶ ಮತ್ತು ಅನುಮತಿಪಟ್ಟಿ ನೀತಿಗಾಗಿ, `AGENTS.md`ನಲ್ಲಿರುವ "ಗುಣಮಟ್ಟದ ಗೇಟ್ಗಳು ಮತ್ತು ರ್ಯಾಚೆಟ್ಗಳು" ವಿಭಾಗವನ್ನು
ನೋಡಿ. ಇದೇ ಸಿಸ್ಟಮ್ನ ವಿಮರ್ಶಾತ್ಮಕ ಮೌಲ್ಯಮಾಪನ, ಪಕ್ವತೆಯ ವರ್ಗೀಕರಣ ಮತ್ತು ಉಪಕರಣ-ಸ್ವತಂತ್ರ
ಮರುಅನುಷ್ಠಾನ ಯೋಜನೆಗಾಗಿ,
[ಗುಣಮಟ್ಟದ ಗೇಟ್ ಪ್ಲೇಬುಕ್](../ops/QUALITY_GATE_PLAYBOOK.md) ನೋಡಿ.

## ಗೇಟ್ ಇನ್ವೆಂಟರಿ ಮತ್ತು ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆ ಪ್ರೊಫೈಲ್ಗಳು

### ಅಭ್ಯರ್ಥಿ ಪ್ರವೇಶ

CI ಮತ್ತು Quality Gates ವರ್ಕ್ಫ್ಲೋಗಳು ಪ್ರತಿಯೊಂದೂ ಸ್ಥಿರ ತೀರ್ಪನ್ನು ನೀಡುತ್ತವೆ: `Gate / CI` ಮತ್ತು
`Gate / Quality`. ಅವುಗಳ ಆವೃತ್ತಿಗೊಳಿಸಲಾದ ಪ್ರವೇಶ ನೀತಿಯು ಪ್ರತಿ ಅಪ್ಸ್ಟ್ರೀಮ್ ಜಾಬ್ ಅನ್ನು
ಕಡ್ಡಾಯ ಅಥವಾ ಸಲಹಾತ್ಮಕ ಎಂದು ಪಟ್ಟಿ ಮಾಡುತ್ತದೆ. ಅನ್ವಯವಾಗುವ ಕಡ್ಡಾಯ ಜಾಬ್ ಯಶಸ್ವಿಯಾಗಬೇಕು: ಕಾಣೆಯಾದ,
ರದ್ದಾದ, ಸ್ಕಿಪ್ ಆದ, ಬಾಕಿ ಇರುವ ಮತ್ತು ಅಜ್ಞಾತ ಫಲಿತಾಂಶಗಳು PASS ಅನ್ನು ಸ್ಥಾಪಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಮಾನ್ಯವಾದ
docs-only ಅಥವಾ catalog-only ವರ್ಗೀಕರಣವು ಕೋಡ್ ಲೇನ್ ಅನ್ನು ಅನ್ವಯವಾಗದಂತೆ ಮಾಡಬಹುದು;
ಡ್ರಾಫ್ಟ್ PR ಅನ್ನು ಅಂಗೀಕೃತ ಅಭ್ಯರ್ಥಿಯಾಗಿ ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ. `hotfix` ಲೇಬಲ್ ಸಾಕ್ಷ್ಯದ ಅಗತ್ಯವನ್ನು ಮನ್ನಾ ಮಾಡುವುದಿಲ್ಲ.

ಎರಡೂ ವರ್ಕ್ಫ್ಲೋಗಳು PRಗಳು ಮತ್ತು main/release ಬ್ರಾಂಚ್ಗಳಿಗೆ ಪುಶ್ಗಳು, ಹಸ್ತಚಾಲಿತ dispatch ಹಾಗೂ
merge-group ಈವೆಂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ. Push, dispatch ಮತ್ತು merge-group ಸಂಪೂರ್ಣ ಆಯ್ಕೆಯನ್ನು ಚಲಾಯಿಸುತ್ತವೆ. Forkಗಳು
ಮತ್ತು merge groupಗಳು, ಇಲ್ಲದಿದ್ದರೆ self-hosted ರನ್ನರ್ಗಳನ್ನು ಆಯ್ಕೆಮಾಡುವ ಜಾಬ್ಗಳಿಗೆ hosted ರನ್ನರ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ;
ರೋಲ್ಔಟ್ಗೆ ಮೊದಲು ಸಾಕಷ್ಟು hosted ಸಾಮರ್ಥ್ಯವನ್ನು ಪರಿಶೀಲಿಸಬೇಕು.

ಪ್ರತಿ JSON ರಸೀದಿಯು ಚೆಕ್ಔಟ್ ಮಾಡಲಾದ SHA, ವರ್ಕ್ಫ್ಲೋ ರನ್ ಮತ್ತು ಪ್ರಯತ್ನವನ್ನು ಗುರುತಿಸುತ್ತದೆ.
ಚೆಕ್ಔಟ್/event SHA ಅಸಂಗತತೆಯನ್ನು CLI ತಿರಸ್ಕರಿಸುತ್ತದೆ. ವರ್ಕ್ಫ್ಲೋ ಪರೀಕ್ಷೆಗಳು ನೀತಿ ಸದಸ್ಯತ್ವವನ್ನು
ತೀರ್ಪು ಜಾಬ್ನ `needs` ಪಟ್ಟಿಗೆ ಬಿಗಿದಿಡುತ್ತವೆ, ಹೀಗಾಗಿ ಹೊಸದಾಗಿ ಸೇರಿಸಲಾದ ಅಥವಾ ತೆಗೆದುಹಾಕಲಾದ ಲೇನ್ ಮೌನವಾಗಿ ಕಣ್ಮರೆಯಾಗಲು ಸಾಧ್ಯವಿಲ್ಲ.
ರಸೀದಿಗಳು ತಮ್ಮದೇ ವರ್ಕ್ಫ್ಲೋವನ್ನು ಒಳಗೊಳ್ಳುತ್ತವೆ; ಪ್ರಕಟಣೆ, ನಿಯೋಜನೆ ಅಥವಾ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಸಲಹಾತ್ಮಕ ಸ್ಕ್ಯಾನರ್ನ ಆಂತರಿಕ ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಅಲ್ಲ. ಬ್ರಾಂಚ್ ನಿಯಮಗಳಲ್ಲಿ ಎರಡೂ ಚೆಕ್ ಹೆಸರುಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದು
ಪ್ರತ್ಯೇಕ ಆಡಳಿತಾತ್ಮಕ ಬದಲಾವಣೆಯಾಗಿದೆ; ಈ ಜಾಬ್ಗಳನ್ನು ಸೇರಿಸುವುದರಿಂದ ಮಾತ್ರ ಬ್ರಾಂಚ್ ಸಂರಕ್ಷಿತವಾಗುವುದಿಲ್ಲ.

### ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಇನ್ವೆಂಟರಿ

ಆವೃತ್ತಿಗೊಳಿಸಲಾದ npm-alias ಇನ್ವೆಂಟರಿ ಮತ್ತು ಸ್ಥಿರ-ಸ್ಕ್ಯಾನ್ ಸದಸ್ಯತ್ವವು
`config/quality/gate-manifest.json` ನಲ್ಲಿವೆ. ಸ್ಕ್ರಿಪ್ಟ್ ಹೆಸರುಗಳು ಮತ್ತು ನಿಖರ ಕಮಾಂಡ್ಗಳನ್ನು
`package.json` ಗೆ ಹೋಲಿಸಿ ಮೌಲ್ಯೀಕರಿಸಲು `npm run check:gate-manifest` ಅನ್ನು ಚಲಾಯಿಸಿ; ಸೇರ್ಪಡೆಗಳು, ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ಮತ್ತು
ಕಮಾಂಡ್ ವ್ಯತ್ಯಾಸಗಳು ಸ್ಥಳೀಯ hook ಮತ್ತು CIಯಲ್ಲಿನ ಬದಲಾವಣೆ-ವರ್ಗೀಕರಣ ಜಾಬ್ಗಳೆರಡನ್ನೂ ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
alias ಎಂಬುದು ವರ್ಕ್ಫ್ಲೋ ಜಾಬ್, matrix instance ಅಥವಾ test case ಅಲ್ಲ: ಈ ಎಣಿಕೆಗಳನ್ನು
ಪರಸ್ಪರ ಬದಲಾಯಿಸಬಹುದಾದವುಗಳಂತೆ ಪ್ರಸ್ತುತಪಡಿಸಬಾರದು.

ಆಯ್ಕೆಮಾಡಲಾದ aliasಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸದೆ ಪರಿಶೀಲಿಸಲು `npm run quality:scan -- --list` ಅಥವಾ `npm run quality:scan:fast -- --list`
ಬಳಸಿ. ರನ್ನರ್ npm entrypoint ಅನ್ನು ಆವಾಹಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದರ runtime (ಕಾನ್ಫಿಗರ್ ಮಾಡಿರುವಲ್ಲಿ Bun ಸೇರಿದಂತೆ) ಉಳಿಯುತ್ತದೆ.
manifest ಆ ಪ್ರೊಫೈಲ್ಗಳ ಹೊರಗಿನ aliasಗಳನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಆವಾಹಿಸಲಾದವುಗಳೆಂದು ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು
ಓದಲು-ಮಾತ್ರವಾದ ಸ್ಕ್ಯಾನ್ ಪ್ರೊಫೈಲ್ಗಳಲ್ಲಿ ನಿರ್ವಹಣಾ ಕಮಾಂಡ್ಗಳನ್ನು ನಿಷೇಧಿಸಲಾಗಿದೆ.

ಈ ಪ್ರೊಫೈಲ್ಗಳು ಸ್ಥಿರ ಸ್ಕ್ಯಾನ್ ಅನ್ನು ಮಾತ್ರ ಒಳಗೊಳ್ಳುತ್ತವೆ. ಇವು ಉತ್ಪನ್ನ ಪರೀಕ್ಷೆಗಳು,
ವ್ಯಾಪ್ತಿ, ಪ್ಯಾಕೇಜಿಂಗ್, ಬಾಹ್ಯ ಚೆಕ್ಗಳು ಅಥವಾ ಅಭ್ಯರ್ಥಿಯ ಸಂಪೂರ್ಣ ಬಿಡುಗಡೆ ಅಂಗೀಕಾರವನ್ನು ಪ್ರಮಾಣೀಕರಿಸುವುದಿಲ್ಲ.
ವರ್ಕ್ಫ್ಲೋ ಪ್ರವೇಶವು ಲಿಂಕ್ ಮಾಡಲಾದ `config/quality/admission-policy.json` ಮತ್ತು
`scripts/quality/admission-verdict.mjs` ಅನ್ನು ಬಳಸುತ್ತದೆ. Release-observer ಪ್ರೊಫೈಲ್ಗಳು ಪ್ರತ್ಯೇಕವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ;
ಅವುಗಳ ಅನ್ವಯವಾಗುವ ಚೆಕ್ಗಳು ಮತ್ತು ರಸೀದಿಗಳನ್ನು ಸ್ವತಂತ್ರವಾಗಿ ಪರಿಶೀಲಿಸಿ. ಕೆಳಗಿನ ಗದ್ಯರೂಪದ
ಇನ್ವೆಂಟರಿ ಒಂದು ಉಲ್ಲೇಖವಾಗಿದೆ; ಗೇಟ್ ನಿಜವಾಗಿಯೂ ಚಲಾಯಿಸಲ್ಪಟ್ಟಿದೆ ಎಂಬುದಕ್ಕೆ ಪುರಾವೆಯಲ್ಲ.

ಸ್ಕ್ರಿಪ್ಟ್ಗಳು `scripts/check/` (ನೀತಿ ಗೇಟ್ಗಳು) ಮತ್ತು `scripts/quality/` (ratchet ಎಂಜಿನ್) ಅಡಿಯಲ್ಲಿ ಇವೆ.
CIಗೆ ಮೂಲ ಸತ್ಯವು `.github/workflows/ci.yml` ಆಗಿದೆ.

### ಬಿಡುಗಡೆ PR ವೇಗದ-ಮಾರ್ಗ (`quality.yml`)

`.github/workflows/quality.yml` main/release PRಗಳು, ಸಂರಕ್ಷಿತ-ಬ್ರಾಂಚ್
ಪುಶ್ಗಳು, dispatch ಮತ್ತು merge groupಗಳಲ್ಲಿ CIಗೆ ಪೂರಕವಾಗಿದೆ. PRಗಳು ಪಥ-ಫಿಲ್ಟರ್ ಮಾಡಿದ ವೇಗದ ಚೆಕ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಶಾಶ್ವತವಾಗಿ
ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ನಕಲಿ build ಅನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ; ನೈಜ build/package/boot ಚೆಕ್ಗಳು CIಯಲ್ಲಿಯೇ ಉಳಿದಿವೆ.

#### ಮರೆತುಹೋದ sibling tests ವರದಿ

`npm run check:forgotten-sibling-tests` test-impact map ಹಿಂದಿರುವ import resolver ಅನ್ನು ಮರುಬಳಕೆ ಮಾಡುತ್ತದೆ.
ಬದಲಾದ ಪ್ರತಿಯೊಂದು production moduleಗೆ, ಅಭ್ಯರ್ಥಿ
test pull-request diffನಲ್ಲಿ ಇಲ್ಲದಿದ್ದಾಗ, ಇದು ನಿರ್ಣಾಯಕ
`changed module/symbol -> static consumer -> candidate sibling test` ಸರಪಳಿಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಯಾವುದೇ ನಿರ್ಬಂಧಕ ರೋಲ್ಔಟ್ಗೆ ಮುನ್ನ ಮಾಪನಾಂಕ ನಿರ್ಣಯಕ್ಕಾಗಿ
Markdown ಸಾರಾಂಶ ಮತ್ತು JSON ಫಲಿತಾಂಶವನ್ನು `forgotten-sibling-tests` ವರ್ಕ್ಫ್ಲೋ artifact ಆಗಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

Barrel re-exports ಮತ್ತು dynamic imports ಕೇವಲ resolution diagnostics ಆಗಿವೆ; ಅವು ಎಂದಿಗೂ
ತಡೆಯುವ finding ಅನ್ನು ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ. ಪರಿಶೀಲಿಸಲಾದ ವಿನಾಯಿತಿಗಳು
`config/quality/forgotten-sibling-allowlist.json` ನಲ್ಲಿ ಇರುತ್ತವೆ. ಪ್ರತಿಯೊಂದು ನಮೂದು consumer ಮತ್ತು candidate
test ಅನ್ನು ಹೆಸರಿಸಬೇಕು, ನಿರ್ದಿಷ್ಟ ತಾರ್ಕಿಕ ಕಾರಣವನ್ನು ನೀಡಬೇಕು ಮತ್ತು GitHub issue ಅಥವಾ pull requestಗೆ ಲಿಂಕ್ ಮಾಡಬೇಕು. ದೋಷಪೂರಿತ ನಮೂದುಗಳು

| `check-ui-value-drift` (inline)   | ಮರುಬರೆಯಲಾದ ಇಂಗ್ಲಿಷ್ **ಮೌಲ್ಯವು** ಯಾವುದೇ ಹಳೆಯ ಅನುವಾದವನ್ನು ಉಳಿಸುವುದಿಲ್ಲ                                                                                                                         | ಹೌದು           |
| `check-new-key-coverage` (inline) | ಒಂದು **ಹೊಸ** ಇಂಗ್ಲಿಷ್ ಕೀ ಪ್ರತಿ ಲೊಕೇಲ್ನಲ್ಲಿಯೂ ಅನುವಾದಗೊಂಡಿದೆ — `__MISSING__:` ಗುರುತನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ                                                                                     | ಹೌದು           |
| `check-translation-ratio`         | ಪ್ರತಿ ಲೊಕೇಲ್ನ ನೈಜ-ಅನುವಾದ ಅನುಪಾತವು (ಅನುಮತಿ ಪಟ್ಟಿಯ ಹೊರಗೆ ಇಂಗ್ಲಿಷ್ಗೆ ತದ್ರೂಪವಾದ / ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ / ಕಾಣೆಯಾದ ಲೀಫ್ಗಳು) `config/quality/i18n-translation-baseline.json` + ಸಡಿಲಿಕೆಯ ಮಿತಿಯನ್ನು ಮೀರಬಾರದು | **ಸಲಹಾತ್ಮಕ**   |

`fetch-depth: 0` ಅಗತ್ಯವಿದೆ — ಮೌಲ್ಯ-ವ್ಯತ್ಯಾಸ ಗೇಟ್, ವಿಲೀನದ ಮೂಲದ ವಿರುದ್ಧ `en.json` ಅನ್ನು ಹೋಲಿಸುತ್ತದೆ.

#### `check-ui-value-drift` — ಹಳೆಯ-ಅನುವಾದ ಗೇಟ್

ಇತರ ಗೇಟ್ಗಳು ರಚನಾತ್ಮಕವಾಗಿ ಪತ್ತೆಹಚ್ಚಲಾಗದ ಏಕೈಕ i18n ರಿಗ್ರೆಷನ್ ಅನ್ನು ಇದು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ: ಒಂದು ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯವನ್ನು
ಮರುಬರೆಯಲಾಗುತ್ತದೆ ಮತ್ತು _ಹಿಂದಿನ_ ಇಂಗ್ಲಿಷ್ನಿಂದ ಪಡೆದ ಅನುವಾದಗಳು ಹಾಗೆಯೇ ಉಳಿಯುತ್ತವೆ, ಆದ್ದರಿಂದ
ಇಂಗ್ಲಿಷ್ ಹೊರತಾದ ಭಾಷೆಗಳ ಬಳಕೆದಾರರು ಆತ್ಮವಿಶ್ವಾಸದಿಂದ ಬರೆಯಲಾದ, ಈಗ ತಪ್ಪಾಗಿರುವ ಪಠ್ಯವನ್ನೇ ಓದುತ್ತಿರುತ್ತಾರೆ.

ಇದು ನಿಜವಾಗಿಯೂ ಬಿಡುಗಡೆಗೊಂಡಿತ್ತು. Antigravity ಲಾಗಿನ್ ಸಹಾಯಕವನ್ನು ಸೇರಿಸಿದಾಗ (#5203)
`oauthModal.googleOAuthWarning` ಅನ್ನು ಮರುಬರೆಯಲಾಗಿತ್ತು; **43 ಲೊಕೇಲ್ಗಳಲ್ಲಿ 39** ಲೊಕೇಲ್ಗಳು ಆಪರೇಟರ್ಗಳಿಗೆ "ಸಂಪೂರ್ಣ
URL ಅನ್ನು ನಕಲಿಸಿ ಮತ್ತು ಕೆಳಗೆ ಅಂಟಿಸಿ" ಎಂದು ಹೇಳುವ ಪಠ್ಯವನ್ನು ಉಳಿಸಿಕೊಂಡಿದ್ದವು — ಆ ಪ್ರೊವೈಡರ್ಗಾಗಿ ಪೂರ್ಣಗೊಳಿಸಲಾಗದ ಪ್ರಕ್ರಿಯೆ. ಈ ಕೆಳಗಿನ ಕಾರಣಗಳಿಂದ
#8463 ವರೆಗೆ ಇದು ಗಮನಕ್ಕೆ ಬಂದಿರಲಿಲ್ಲ:

- `sync-ui-keys` **ಇಲ್ಲದಿರುವ** ಕೀಗಳನ್ನು ಮಾತ್ರ ಬ್ಯಾಕ್ಫಿಲ್ ಮಾಡುತ್ತದೆ, **ಹಳೆಯದಾದ** ಕೀಗಳನ್ನು ಎಂದಿಗೂ ಅಲ್ಲ;
- `check-ui-keys-coverage` ಕೀಗಳ _ಉಪಸ್ಥಿತಿಯನ್ನು_ ಎಣಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಹಳೆಯ ಅನುವಾದವೂ ವ್ಯಾಪ್ತಿಗೆ ಒಳಪಟ್ಟಂತೆ ಪರಿಗಣಿಸಲ್ಪಡುತ್ತದೆ;
- `check-translation-drift` ಎಂಬುದು `docs/i18n/<locale>/**.md` ದಸ್ತಾವೇಜೀಕರಣ ಮಿರರ್ಗಳನ್ನು ಟ್ರ್ಯಾಕ್ ಮಾಡುತ್ತದೆ —
  ಅದು ಎಂದಿಗೂ `src/i18n/messages/*.json` ಅನ್ನು ಓದುವುದಿಲ್ಲ. 2026-09 ಮರು-ಸಿಂಕ್ನಿಂದ `docs-sync-strict` ಜಾಬ್ನಲ್ಲಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತಿದೆ:
  ಪ್ರಮುಖ doc ಅನ್ನು ಸಂಪಾದಿಸಿ → `npm run i18n:run -- --files=<doc>` (ವಿಭಾಗ-ಮಟ್ಟದ, ಕಡಿಮೆ ವೆಚ್ಚದ).

**ವ್ಯತ್ಯಾಸ-ಅರಿವಿನದು, ಬೇಸ್ಲೈನ್-ಆಧಾರಿತವಲ್ಲ.** ಇದು ವಿಲೀನ ಬೇಸ್ನಲ್ಲಿರುವ `en.json` ಅನ್ನು
ವರ್ಕಿಂಗ್ ಟ್ರೀಯೊಂದಿಗೆ ಹೋಲಿಸುತ್ತದೆ; ಇಂಗ್ಲಿಷ್ ಮೌಲ್ಯ ಬದಲಾದ ಪ್ರತಿಯೊಂದು ಕೀಗಾಗಿ, ಇನ್ನೂ
ಬದಲಾಯಿಸದ ಅನುವಾದವನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಲೊಕೇಲ್ ಹಳೆಯದಾಗಿದೆ. ಇದು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ **ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಬಾಕಿಯನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ** — ದೀರ್ಘಕಾಲದಿಂದ ಇರುವ ಅನುವಾದವು ಯಾವ ಹಳೆಯ ಇಂಗ್ಲಿಷ್ನಿಂದ ಬಂದಿದೆ ಎಂಬುದನ್ನು
ವ್ಯತ್ಯಾಸವು ಬಹಿರಂಗಪಡಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ, ಆದ್ದರಿಂದ ಪ್ರಸ್ತುತ ಬದಲಾವಣೆಯು ಸ್ಪರ್ಶಿಸುವುದನ್ನು ಮಾತ್ರ ಗೇಟ್ ನಿರ್ಣಯಿಸುತ್ತದೆ.
ಪರ್ಯಾಯಕ್ಕೆ (ಪ್ರತಿ-ಕೀ ಹ್ಯಾಶ್ ಬೇಸ್ಲೈನ್) ~600 KB ರಚಿಸಲಾದ ಫೈಲ್ ಅಗತ್ಯವಿರುತ್ತದೆ,
ಇದು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅತಿದೊಡ್ಡ ಬೇಸ್ಲೈನ್ಗಿಂತ 3× ದೊಡ್ಡದು ಮತ್ತು ಪ್ರತಿಯೊಂದು i18n PRನಲ್ಲಿಯೂ ಬದಲಾವಣೆಗೆ ಒಳಗಾಗುತ್ತದೆ.

ಇದನ್ನು ಪೂರೈಸಲು ಎರಡು ಮಾರ್ಗಗಳಿವೆ:

1. ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಅನುವಾದಗಳನ್ನು ನವೀಕರಿಸಿ, ಅಥವಾ
2. ಅವುಗಳನ್ನು `__MISSING__:<new english>` ಎಂದು ಹೊಂದಿಸಿ — ನಂತರ ರನ್ಟೈಮ್ ಸರಿಪಡಿಸಿದ ಇಂಗ್ಲಿಷ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ಮತ್ತು ಕೀ ಅನುವಾದಕ್ಕಾಗಿ ಸರತಿಗೆ ಸೇರುತ್ತದೆ.

ಸ್ಟ್ರಿಂಗ್ನ **ಅರ್ಥ** ಬದಲಾಗಿದ್ದರೆ, **ಕೀಗೆ ಮರುಹೆಸರಿಸುವುದಕ್ಕೆ** ಆದ್ಯತೆ ನೀಡಿ: ಹೊಸ ಕೀಗೆ
ಹಳೆಯ ಅನುವಾದವನ್ನು ಆನುವಂಶಿಕವಾಗಿ ಪಡೆಯಲು ಸಾಧ್ಯವಿಲ್ಲ. #8463 ಬಳಸಿದ ಮಾದರಿ ಇದೇ.

```bash
npm run i18n:check-value-drift          # ಕಟ್ಟುನಿಟ್ಟಾದುದು (CI ಚಲಾಯಿಸುವುದು)
npm run i18n:check-value-drift:warn     # ವರದಿ ಮಾತ್ರ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ಬೇಸ್ ಕ್ಯಾಟಲಾಗ್ ಅನ್ನು ಓದಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ (ಬೇಸ್ ref ಇಲ್ಲದ ಶಾಲೋ
ಕ್ಲೋನ್), `check-openapi-breaking` ಅನ್ನು ಅನುಸರಿಸುವಂತೆ `SKIP reason=base-unresolved` ಜೊತೆಗೆ 0 ಮೌಲ್ಯದಿಂದ ನಿರ್ಗಮಿಸುತ್ತದೆ.

- `npm run quality:relax-baselines -- --pct 20 --note velocity_YYYY_MM_DD [--dry-run]` — ಏಕಕಾಲಿಕ

- `npm run quality:headroom [-- --only deadExports,fileSize] [--json out.json --md out.md]` —
  CI ಅಳೆಯುವ ರೀತಿಯಲ್ಲೇ ಪ್ರತಿಯೊಂದು ಸಂಖ್ಯಾತ್ಮಕ ಗೇಟ್ ಅನ್ನು ಅಳೆದು, ಪ್ರತಿ ಗೇಟ್ಗೆ ಉಳಿದಿರುವ ಹೆಚ್ಚುವರಿ ಅವಕಾಶವನ್ನು ಮುದ್ರಿಸುತ್ತದೆ
  (`scripts/quality/baseline-headroom.mjs`). ರಾತ್ರಿಯ `baseline-headroom` ಕೆಲಸವು ಕೋಷ್ಟಕವನ್ನು ಸಕ್ರಿಯ ಸಮಸ್ಯೆ
  **📈 ಮೂಲಮಟ್ಟದ ಹೆಚ್ಚುವರಿ ಅವಕಾಶ (ವೇಗದ ಹಂತ)** ಗೆ ಪೋಸ್ಟ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ ಗೇಟ್ ತನ್ನ ಮಿತಿಯ 10% ಒಳಗಿದ್ದರೆ ಅಥವಾ ಈಗಾಗಲೇ
  ಅದನ್ನು ಮೀರಿದ್ದರೆ `headroom-alert` ಲೇಬಲ್ ಅನ್ನು ಸೇರಿಸುತ್ತದೆ. ಆ ಸಮಸ್ಯೆಯೇ ಮುಂಚಿತ ಎಚ್ಚರಿಕೆ: ಕೆಲವೇ ದಿನಗಳಲ್ಲಿ ತುಂಬುವ ಬಜೆಟ್ ಎಂದರೆ,
  ಸಡಿಲಿಕೆಯನ್ನು ಇಡೀ ತಂಡವಲ್ಲದೆ ಕೆಲವೇ PRಗಳು ಬಳಸಿಕೊಳ್ಳುತ್ತಿವೆ — ಸಮಸ್ಯೆಯಿರುವ ಗೇಟ್ನ `_rebaseline_*` ಟಿಪ್ಪಣಿಗಳನ್ನು ನೋಡಿ.

**ಹೊಸ-ಕೋಡ್ ಮೋಡ್ (ಕೋಡ್ ಬರೆಯುವಾಗಲೇ ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ) — 2026-08-30 ರಿಂದ, PR ವೇಗದ ಮಾರ್ಗಕ್ಕೆ ಮಾತ್ರ**

`pull_request` ಈವೆಂಟ್ಗಳಲ್ಲಿ `quality.yml`, `check:file-size`,
`check:complexity-ratchets` ಮತ್ತು `check:dead-code` ಗೆ `--base-ref <PR base SHA>` ಅನ್ನು ರವಾನಿಸುತ್ತದೆ. ಆ ಮೋಡ್ನಲ್ಲಿ ಗೇಟ್,
HEAD ಅನ್ನು merge-base ಜೊತೆ **PR ಸ್ಪರ್ಶಿಸಿದ ಫೈಲ್ಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತಗೊಳಿಸಿ** ಹೋಲಿಸುತ್ತದೆ (`scripts/check/newCodeMode.mjs`:
merge-base ಅನ್ನು ತಾತ್ಕಾಲಿಕ `git worktree` ನಲ್ಲಿ ಸೃಷ್ಟಿಸಲಾಗುತ್ತದೆ, ESLint/knip ಅನ್ನು ಅಲ್ಲಿ ಮತ್ತು HEAD ಮೇಲೆ ಚಲಾಯಿಸಲಾಗುತ್ತದೆ,
ನಂತರ ಪ್ರತಿ-ಫೈಲ್ ಎಣಿಕೆಗಳ ವ್ಯತ್ಯಾಸವನ್ನು ಲೆಕ್ಕಿಸಲಾಗುತ್ತದೆ):

- **ತಡೆಹಿಡಿಯುವ** — PR ತಾನು ಬದಲಾಯಿಸಿದ ಫೈಲ್ಗಳಲ್ಲಿ ಸೈಕ್ಲೊಮ್ಯಾಟಿಕ್/ಕಾಗ್ನಿಟಿವ್ ಉಲ್ಲಂಘನೆಗಳು ಅಥವಾ ಬಳಕೆಯಾಗದ ಎಕ್ಸ್ಪೋರ್ಟ್ಗಳನ್ನು ಸೇರಿಸಿದೆ
  (ಲಾಗ್ನಲ್ಲಿ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ಸಲಹಾತ್ಮಕ** — ಸ್ಥಗಿತಗೊಳಿಸಿದ ಮೂಲಮಟ್ಟದ ವಿರುದ್ಧ ಜಾಗತಿಕ ಒಟ್ಟು. ಆನುವಂಶಿಕ ವ್ಯತ್ಯಾಸವು ನಿರ್ದೋಷಿ PR ಅನ್ನು ಎಂದಿಗೂ
  ವಿಫಲಗೊಳಿಸುವುದಿಲ್ಲ; ಬಿಡುಗಡೆ ಸಮನ್ವಯದ ಸಮಯದಲ್ಲಿ ವ್ಯತ್ಯಾಸವನ್ನು ಮರು-ಸ್ಥಗಿತಗೊಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಹೆಚ್ಚುವರಿ ಅವಕಾಶದ ಕೆಲಸವು ಅದನ್ನು ಮೇಲ್ವಿಚಾರಣೆ ಮಾಡುತ್ತದೆ.

`workflow_dispatch` ಚಾಲನೆಗಳು, release-green ಪರಿಶೀಲನೆ ಮತ್ತು ರಾತ್ರಿಯ ಹೆಚ್ಚುವರಿ ಅವಕಾಶದ ಕೆಲಸಕ್ಕೆ PR ಮೂಲವಿಲ್ಲ
ಮತ್ತು ಅವು ನಿರಪೇಕ್ಷ (ಜಾಗತಿಕ) ಹೋಲಿಕೆಯನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ. ವ್ಯಾಪ್ತಿ, ನಕಲು ಮತ್ತು type-coverage ಸದ್ಯಕ್ಕೆ ಜಾಗತಿಕವಾಗಿಯೇ
ಉಳಿಯುತ್ತವೆ (ಅವುಗಳ ಉಪಕರಣಗಳು ಪ್ರತಿ-ಫೈಲ್ ವ್ಯತ್ಯಾಸವನ್ನು ಕಡಿಮೆ ವೆಚ್ಚದಲ್ಲಿ ಒದಗಿಸುವುದಿಲ್ಲ) — ಇದೇ ರೀತಿಯ ನಿರ್ವಹಣೆಗೆ ಅಭ್ಯರ್ಥಿಗಳು.

**v4.0 ನಲ್ಲಿ ಹಂತವನ್ನು ಮುಕ್ತಾಯಗೊಳಿಸುವುದು (LTS = ಹಿಂದಿಗಿಂತ ಹೆಚ್ಚು ಕಟ್ಟುನಿಟ್ಟು, "ಸಾಮಾನ್ಯ ಸ್ಥಿತಿಗೆ ಮರಳುವುದು" ಅಲ್ಲ)**

1. ಸ್ವಚ್ಛವಾದ `release/v4.0.0` ತುದಿಯಲ್ಲಿ: ದಾಖಲಾತಿಗಾಗಿ `npm run quality:headroom --json`, ನಂತರ
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ಪ್ರತಿಯೊಂದು typecheck ಗೇಟ್ನ
   `--update` — ಪ್ರತಿಯೊಂದು ಬೇಸ್ಲೈನ್ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕೆ ಇಳಿಯುತ್ತದೆ.
2. `quality-baseline.json` ನಿಂದ `_policy` ಅನ್ನು ಅಳಿಸಿ (`--require-tighten` ಮತ್ತು ರಾತ್ರಿಯ
   ಬ್ಯಾಂಕಿಂಗ್ ಅನ್ನು ಮರುಸಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ), `check-openapi-coverage.mjs` ನಲ್ಲಿ `THRESHOLD = 36` (ಅಥವಾ ಹೆಚ್ಚಿನದು) ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ.
3. ಮಾಡ್ಯುಲರೀಕರಣದಿಂದ ಪ್ರಯೋಜನ ದೊರೆತ ಕಡೆಗಳಲ್ಲಿ ಅಳೆಯಲಾದ ಮೌಲ್ಯಕ್ಕಿಂತಲೂ ಹೆಚ್ಚು ಬಿಗಿಗೊಳಿಸಿ: file-size `cap` ಅನ್ನು ಮತ್ತೆ 1000
   (ಅಥವಾ 800) ಗೆ, coverage ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು +5 ಗೆ, ಮಾಡ್ಯುಲರೀಕರಿಸಿದ ಪ್ಯಾಕೇಜ್ಗಳ dead exports ಅನ್ನು 0 ಗೆ ಹೊಂದಿಸಿ.

## ರ್ಯಾಚೆಟ್ ಬೇಸ್ಲೈನ್ (`quality-baseline.json`)

ರ್ಯಾಚೆಟ್ ಎಂಜಿನ್ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ಅನ್ನು ಓದಿ,

ಹೆಚ್ಚು ಹಿಂಜರಿದರೆ, ಬಿಲ್ಡ್ ವಿಫಲವಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗುತ್ತಿರುವ ಮೆಟ್ರಿಕ್ಗಳು:

ಮೆಟ್ರಿಕ್ ಅನ್ನು ಸುಧಾರಿಸಿದ ಬದಲಾವಣೆಯ ಜೊತೆಯಲ್ಲೇ ಈ ಫೈಲ್ ಅನ್ನು ಕಮಿಟ್ ಮಾಡಿ. ಬೇಸ್ಲೈನ್ ಅನ್ನು

ಅನುಷ್ಠಾನ ಬಾಕಿಯಿದೆ).

`check:codeql-ratchet` **ರೆಪೊ ಸ್ಥಿತಿಯನ್ನು ಓದುತ್ತದೆ; ಅದನ್ನು ವೇಳಾಪಟ್ಟಿಯ ಪ್ರಕಾರ ರಿಫ್ರೆಶ್ ಮಾಡಲಾಗುತ್ತದೆ — ಪ್ರತಿ PR ಗೆ ಅಲ್ಲ.**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ವರದಿ ಮಾಡುವ
`state: configured`, `schedule: weekly` ಎಂಬುದು GitHub ನ ಡೀಫಾಲ್ಟ್-ಸೆಟಪ್ ಸ್ಕ್ಯಾನ್ ಆಗಿದ್ದು,
ಪ್ರತಿ ಪುಶ್ಗೆ ನಡೆಯುವ ವಿಶ್ಲೇಷಣೆಯಲ್ಲ. ಪರಿಣಾಮ: ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸುವ PR ವಿಲೀನಗೊಂಡ ನಂತರವೂ,
ಮುಂದಿನ ನಿಗದಿತ ಸ್ಕ್ಯಾನ್ ನಡೆಯುವವರೆಗೆ ರ್ಯಾಚೆಟ್ ಹಳೆಯ, ಹೆಚ್ಚಿನ ಸಂಖ್ಯೆಯನ್ನೇ ಓದುತ್ತಿರುತ್ತದೆ —
ಆದ್ದರಿಂದ ಸ್ಕ್ಯಾನ್ ನವೀಕರಿಸುವವರೆಗೆ, ಸರಿಪಡಿಸಿದ PR ನ ಸ್ವಂತ ಫಾಲೋ-ಅಪ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಪ್ರತಿಯೊಂದು
ತೆರೆದ PR ನಲ್ಲಿಯೂ ಅದು ಹಿಂಜರಿತವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ.

**ಹಸ್ತಚಾಲಿತ ರಿಫ್ರೆಶ್**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ವಿಶ್ಲೇಷಣೆಯನ್ನು
ಮತ್ತೆ ಚಲಾಯಿಸಿ, ಕೆಲವೇ ನಿಮಿಷಗಳಲ್ಲಿ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಮರುಪ್ರಕಟಿಸುತ್ತದೆ. ಮೊದಲು `.github/workflows/codeql.yml`
ಓದಿ — GitHub ನ **"default setup" ಜೊತೆಗೆ ಅದು ಸಂಘರ್ಷಿಸುವುದರಿಂದಲೇ** ಇದು `workflow_dispatch`-ಗೆ ಮಾತ್ರ

processed when the default setup is enabled`). `push`/`pull_request`/

7 ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸರಿಪಡಿಸಿತು (ಅಳೆಯಲಾದ ತೆರೆದ ಎಚ್ಚರಿಕೆಗಳು 13 → 6); ಅದಕ್ಕೆ ಹೊಂದುವಂತೆ PR #12530

## ರಿಲೀಸ್-ಮಟ್ಟದ ರ್ಯಾಚೆಟ್ ಡ್ರಿಫ್ಟ್ (WS5.5, v3.8.49)

ಅಂದರೆ, ಮರ್ಜ್ಗಳ ಸಂಯೋಜನೆಯು ಅದನ್ನು ಹಿಮ್ಮೆಟ್ಟಿಸಿದೆ ಮತ್ತು ಯಾವುದೇ ಒಂದು PR ತನ್ನದೇ ಬ್ರಾಂಚ್ನಲ್ಲಿ ಆ
ರಿಗ್ರೆಷನ್ ಅನ್ನು ಪುನರುತ್ಪಾದಿಸುವುದಿಲ್ಲವಾದರೆ — ಅದನ್ನು ಸರಿಪಡಿಸುವ ಹೊಣೆ **ರಿಲೀಸ್ ಕ್ಯಾಪ್ಟನ್ಗೆ, ಒಮ್ಮೆ ಮಾತ್ರ,
ರಿಲೀಸ್ ಬ್ರಾಂಚ್ನಲ್ಲಿ** ಸೇರಿದೆ: ಎಕ್ಸ್ಟ್ರಾಕ್ಷನ್/ರಿಫ್ಯಾಕ್ಟರ್ಗೆ ಆದ್ಯತೆ ನೀಡಿ; ದಾಖಲಿಸಲಾದ
ಸಮರ್ಥನೆ ನಮೂದಿನೊಂದಿಗೆ ಮಾತ್ರ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಿ. ಸಂಯೋಜನೆಯಿಂದಾದ ಡ್ರಿಫ್ಟ್ ಅನ್ನು ಕೊಡುಗೆದಾರರ PR ಮೇಲೆ ಎಂದಿಗೂ
ಹೊರಿಸಬೇಡಿ ಮತ್ತು ಪ್ರತಿ-PR ಗೆ ಬೇಸ್ಲೈನ್ ಮರುಹೊಂದಿಸಬೇಡಿ (ಅದು ನೈಜ ರಿಗ್ರೆಷನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ). ಮೊದಲು ವ್ಯತ್ಯಾಸವನ್ನು ಗುರುತಿಸಿ:
ನಿಮ್ಮ PR ಅದಕ್ಕೆ ಕಾರಣವೆಂದು ಊಹಿಸುವ ಮೊದಲು ಪ್ರೋಬ್ ವರ್ಕ್ಟ್ರೀಯಲ್ಲಿ ಶುದ್ಧ ಟಿಪ್ ವಿರುದ್ಧದ ಕೆಂಪು ಸ್ಥಿತಿಯನ್ನು ಪುನರುತ್ಪಾದಿಸಿ.

| ರವಾನೆ     | ರಿಲೀಸ್ ಬ್ರಾಂಚ್ ವಿರುದ್ಧ ಯಾವಾಗಲೂ ಪ್ರಸ್ತುತವಾಗಿರುವ ಒಂದೇ PR — ಬಲವಂತವಾಗಿ ಅಪ್ಡೇಟ್ ಮಾಡಲಾಗುತ್ತದೆ, ಎಂದಿಗೂ ಸ್ಪ್ಯಾಮ್ ಮಾಡುವುದಿಲ್ಲ |

ಬ್ಯಾಂಕಿಂಗ್ ಅನ್ನು ಪ್ರತಿ-push ಬದಲಿಗೆ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ ಮಾಡಲಾಗುತ್ತದೆ, ಏಕೆಂದರೆ ಇದಕ್ಕೆ ಯಾವುದೇ ಲೇಟೆನ್ಸಿ ಅವಶ್ಯಕತೆ ಇಲ್ಲ
(8 ಗಂಟೆಗಳೊಳಗೆ ಬ್ಯಾಂಕ್ ಮಾಡಿದ ಇಳಿಕೆ ಸಾಕು), ಆದರೆ ಪ್ರತಿ-ಮರ್ಜ್ ಚಾಲನೆಯು ಮರ್ಜ್ ಅಭಿಯಾನಗಳ ಸಮಯದಲ್ಲಿ PR ಬ್ರಾಂಚ್ ಅನ್ನು
ಪದೇಪದೇ ಮರುನಿರ್ಮಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿ ಬಾರಿ ಪೂರ್ಣ ESLint ಸ್ಕ್ಯಾನ್ನ ವೆಚ್ಚವನ್ನು ಭರಿಸುತ್ತದೆ. ಪತ್ತೆಹಚ್ಚುವಿಕೆಯು
push (`release-green`) ನಲ್ಲಿಯೇ ಉಳಿಯುತ್ತದೆ; ಬ್ಯಾಂಕಿಂಗ್ ಮಾತ್ರ ಬ್ಯಾಚ್ಗಳಲ್ಲಿ ನಡೆಯುತ್ತದೆ.

### ಸುರಕ್ಷತಾ ಪರಿಶೀಲಕ

ಜಾಬ್ ಮೇಲ್ವಿಚಾರಣೆಯಿಲ್ಲದೆ ಬೇಸ್ಲೈನ್ಗಳಿಗೆ ಬರೆಯುತ್ತದೆ, ಆದ್ದರಿಂದ `verify-ratchet-bank.mjs` ಅದನ್ನು
ಸ್ವೀಕಾರಾರ್ಹವಾಗಿಸುತ್ತದೆ. ಅದು `--update` ನಂತರದ ಟ್ರೀ ಅನ್ನು `HEAD` ವಿರುದ್ಧ diff ಮಾಡುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಯೊಂದು
ಬದಲಾವಣೆಯೂ ಕೆಳಗಿನವುಗಳಲ್ಲಿ ಒಂದಾಗಿರದಿದ್ದರೆ, **ಯಾವುದೇ ಕಮಿಟ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮೊದಲು ಜಾಬ್ ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ**
— ಯಾವುದೇ PR ತೆರೆಯುವುದಿಲ್ಲ:

- `frozen` / `testFrozen` ಸಂಖ್ಯಾತ್ಮಕ ನಮೂದನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ** ಅಥವಾ **ತೆಗೆದುಹಾಕಲಾಗಿದೆ**
- `complexity-baseline.json` → `count` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**
- `quality-baseline.json` → `metrics.cognitiveComplexity.value` ಅನ್ನು **ಕಡಿಮೆ ಮಾಡಲಾಗಿದೆ**

ಬೇರಾವುದೇ ಬದಲಾವಣೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ: ಸಂಖ್ಯೆಯನ್ನು ಹೆಚ್ಚಿಸುವುದು, ನಮೂದನ್ನು ಸೇರಿಸುವುದು, `cap`/`testCap` ಅನ್ನು ಬದಲಿಸುವುದು ಅಥವಾ
`_rebaseline_*` ಟಿಪ್ಪಣಿಯನ್ನು ಅಳಿಸುವುದು/ಮರುಬರೆಯುವುದು (ಪ್ರತಿ ಗರಿಷ್ಠ ಮಿತಿ ಏಕೆ ಅಸ್ತಿತ್ವದಲ್ಲಿದೆ ಎಂಬುದಕ್ಕೆ ಆ ಟಿಪ್ಪಣಿಗಳು ಆಡಿಟ್ ದಾಖಲೆಯಾಗಿದ್ದು,
ಫೈಲ್ ನಮೂದುಗಳಂತೆಯೇ ಅದೇ `frozen` ಆಬ್ಜೆಕ್ಟ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗಿದೆ).
ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಬಲ್ಲ ಬಾಟ್ ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಗಿಂತ ಖಂಡಿತವಾಗಿಯೂ ಕೆಟ್ಟದಾಗಿರುತ್ತದೆ. ರಿಗ್ರೆಷನ್
ಗಾರ್ಡ್: `tests/unit/verify-ratchet-bank.test.ts`.

ಜಾಬ್ ಎಂದಿಗೂ `release/*` ಗೆ push ಮಾಡುವುದಿಲ್ಲ — ಒಬ್ಬ ವ್ಯಕ್ತಿ PR ಅನ್ನು ಮರ್ಜ್ ಮಾಡುತ್ತಾರೆ, ಆದ್ದರಿಂದ ತಪ್ಪಾದ ಮಾಪನವು
ಪರಿಶೀಲಿಸದೆ ಸೇರಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಅನುಮತಿ ಪಟ್ಟಿ ನೀತಿ

ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉಲ್ಲಂಘನೆಗಳಿಂದ ವಿಫಲವಾಗಬಾರದ ಪ್ರತಿಯೊಂದು ಗೇಟ್ ಸ್ಥಿರಗೊಳಿಸಲಾದ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸುತ್ತದೆ
(ಉದಾ., `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`). ನೀತಿ ಹೀಗಿದೆ:

**ಮೂಲ ಕಾರಣವನ್ನು ಸರಿಪಡಿಸಿ; ಉಲ್ಲಂಘನೆಯು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದು, ಅದನ್ನು ಅದೇ PRನಲ್ಲಿ
ಸರಿಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದಾಗ ಮಾತ್ರ ಅನುಮತಿ ಪಟ್ಟಿಯನ್ನು ಬಳಸಿ.**

ಅನುಮತಿ ಪಟ್ಟಿಗೆ ನಮೂದನ್ನು ಸೇರಿಸುವಾಗ:

1. ಸಮರ್ಥನೆಯೊಂದಿಗೆ ಒಂದು ಕಾಮೆಂಟ್ ಸೇರಿಸಿ.
2. ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯನ್ನು ಉಲ್ಲೇಖಿಸಿ (ಉದಾ., `// #3498 — ಹಂತ 2ರ ವೈಶಿಷ್ಟ್ಯ, ಇನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸಿಲ್ಲ`).
3. ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸುವ ಅದೇ PRನಲ್ಲಿ ನಮೂದನ್ನು ತೆಗೆದುಹಾಕಿ — ಇನ್ನು ಮುಂದೆ ಸಕ್ರಿಯ ಉಲ್ಲಂಘನೆಯನ್ನು
   ನಿಗ್ರಹಿಸದ ಹಳತಾದ ನಮೂದು ಸ್ವತಃ ಒಂದು ದೋಷವಾಗಿದೆ (ಅನುಷ್ಠಾನಗೊಂಡ ನಂತರ 6A.3 stale-enforcement,
   ಅನಾಥ ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದಿನ ಕಾರಣದಿಂದ ಗೇಟ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತದೆ).

ಪರೀಕ್ಷೆಗಳು ವೇಗವಾಗಿ ಪಾಸ್ ಆಗುವಂತೆ ಮಾಡಲು ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದುಗಳನ್ನು ಸೇರಿಸ**ಬೇಡಿ**. ಬೆಳೆಯುತ್ತಿರುವ
ಅನುಮತಿ ಪಟ್ಟಿಯೊಂದಿಗಿನ ಹಸಿರು ಗೇಟ್ ಗುಣಮಟ್ಟದ ಕುರಿತು ತಪ್ಪು ಭರವಸೆಯನ್ನು ನೀಡುತ್ತದೆ.

### ನಿಮ್ಮ PRನಲ್ಲಿ ಗೇಟ್ ವಿಫಲವಾದಾಗ

1. **ಗೇಟ್ ಔಟ್ಪುಟ್ ಅನ್ನು ಎಚ್ಚರಿಕೆಯಿಂದ ಓದಿ** — ಯಾವ ಫೈಲ್ ಅಥವಾ ಸಂಕೇತವು ನಿಯಮವನ್ನು ಉಲ್ಲಂಘಿಸಿದೆ
   ಎಂಬುದನ್ನು ಅದು ನಿಖರವಾಗಿ ತಿಳಿಸುತ್ತದೆ.
2. **ಉಲ್ಲಂಘನೆಯನ್ನು ಸರಿಪಡಿಸಿ** — ಬಹುತೇಕ ಗೇಟ್ಗಳು ನಿರ್ಣಾಯಕ ಫೈಲ್ಸಿಸ್ಟಮ್ ಪರಿಶೀಲನೆಗಳಾಗಿದ್ದು,
   ಕೋಡ್ ಸರಿಯಾದ ತಕ್ಷಣವೇ ಪಾಸ್ ಆಗುತ್ತವೆ.
3. **ಉಲ್ಲಂಘನೆಯು ಈಗಾಗಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದರೆ** (ಅಂದರೆ, ನೀವು ಅದನ್ನು ಪರಿಚಯಿಸಿಲ್ಲ, ಆದರೆ ಈಗ ಗೇಟ್
   ಅದನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ): ಸಮರ್ಥನೆಯ ಕಾಮೆಂಟ್ ಮತ್ತು ಟ್ರ್ಯಾಕಿಂಗ್ ಸಮಸ್ಯೆಯೊಂದಿಗೆ ಅನುಮತಿ ಪಟ್ಟಿ ನಮೂದನ್ನು ಸೇರಿಸಿ.
4. **ಗೇಟ್ ರ್ಯಾಚೆಟ್ ಆಗಿದ್ದರೆ** (ವ್ಯಾಪ್ತಿ, ESLint ಎಚ್ಚರಿಕೆಗಳು, ನಕಲು, ಸಂಕೀರ್ಣತೆ):
   ನಿಮ್ಮ ಬದಲಾವಣೆಯು ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹದಗೆಡಿಸಿದೆ. ಮೂಲ ಸಮಸ್ಯೆಯನ್ನು ಸರಿಪಡಿಸಿ ಅಥವಾ (ಅಪರೂಪವಾಗಿ) ಬದಲಾವಣೆಯು
   ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿದ್ದು ಮೆಟ್ರಿಕ್ ಕುಸಿತವು ಸ್ವೀಕಾರಾರ್ಹವಾಗಿದ್ದರೆ `npm run quality:ratchet -- --update`
   ಅನ್ನು ಚಲಾಯಿಸಿ — ಆದರೆ PR ವಿವರಣೆಯಲ್ಲಿ ಕಾರಣವನ್ನು ದಾಖಲಿಸಿ.
5. **ಸಲಹಾತ್ಮಕ ಗೇಟ್ಗಳು** (`continue-on-error: true`) ಮಾಹಿತಿಗಾಗಿ ಮಾತ್ರ — ಅವು ವಿಲೀನವನ್ನು
   ತಡೆಯುವುದಿಲ್ಲ, ಆದರೆ CI ಸಾರಾಂಶದಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಆದರೂ ಅವುಗಳನ್ನು ಸರಿಪಡಿಸಿ.

## ಹೊಸ ಗೇಟ್ ಸೇರಿಸುವುದು

1. `scripts/check/check-<name>.mjs` (ಅಥವಾ `.ts`) ರಚಿಸಿ. ನೀತಿ ಗೇಟ್ಗಳು 0/1 ಸ್ಥಿತಿಯೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತವೆ.
   ರ್ಯಾಚೆಟ್-ಶೈಲಿಯ ಗೇಟ್ಗಳು `collect-metrics.mjs` ಮೂಲಕ `quality-metrics.json` ಗೆ ಮೆಟ್ರಿಕ್ ಅನ್ನು ಹೊರಸೂಸುತ್ತವೆ.
2. `package.json` ಗೆ `"check:<name>": "node scripts/check/check-<name>.mjs"` ಸೇರಿಸಿ.
3. ಸೂಕ್ತ ಜಾಬ್ ಅಡಿಯಲ್ಲಿ `.github/workflows/ci.yml` ನಲ್ಲಿ ಅದನ್ನು ಜೋಡಿಸಿ
   (ನೀತಿ → `lint` ಅಥವಾ `docs-sync-strict`; ರ್ಯಾಚೆಟ್ → `quality-gate`).
4. ಅದಕ್ಕೆ ಅನುಮತಿ ಪಟ್ಟಿ ಇದ್ದರೆ, ಹಳತಾದ ನಮೂದುಗಳು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪತ್ತೆಯಾಗುವಂತೆ
   `scripts/check/lib/allowlist.mjs` ನಿಂದ `reportStaleEntries()` ಅನ್ನು ಅನ್ವಯಿಸಿ.
5. ಗೇಟ್ನ ಪತ್ತೆ ತರ್ಕವನ್ನು ಒಳಗೊಂಡ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/build/` ನಲ್ಲಿ ಬರೆಯಿರಿ.
6. ಈ ಡಾಕ್ಯುಮೆಂಟ್ ಅನ್ನು ನವೀಕರಿಸಿ (ಸಂಬಂಧಿತ ಜಾಬ್ ಟೇಬಲ್ಗೆ ಒಂದು ಸಾಲನ್ನು ಸೇರಿಸಿ).

## ಏಜೆಂಟ್ ಉಪಕರಣಗಳು: LSP-in-the-loop (ಆಯ್ಕೆಯ ಮೇರೆಗೆ)

CI ಗೇಟ್ಗಳ ಜೊತೆಗೆ, OmniRoute ಒಂದು **ಆಯ್ಕೆಯ ಮೇರೆಗೆ ಬಳಸಬಹುದಾದ** `agent-lsp` ಸ್ಕ್ಯಾಫೋಲ್ಡ್ ಅನ್ನು ಒದಗಿಸುತ್ತದೆ
(ಪ್ರಾಜೆಕ್ಟ್-ಮಟ್ಟದ `.mcp.json`, Fase 7 Task 15). ಕೋಡಿಂಗ್ ಏಜೆಂಟ್ಗಳಿಗೆ TypeScript ಭಾಷಾ ಸರ್ವರ್ ಅನ್ನು
ಒದಗಿಸಲು `.mcp.json` ರಚಿಸಿ, ಇದರಿಂದ ಅವು ಕೋಡ್ ಬರೆಯುವ **ಮೊದಲು** ಸಂಕೇತಗಳು /
ಡಯಾಗ್ನೋಸ್ಟಿಕ್ಗಳನ್ನು ಪರಿಹರಿಸುತ್ತವೆ — ಮೂಲದಲ್ಲೇ "ಕಲ್ಪಿತ ಸಂಕೇತ" ದೋಷಗಳನ್ನು ಕಡಿತಗೊಳಿಸುವ
`typecheck:core` ಗೆ ಕಂಪೈಲ್-ಬಿಫೋರ್-ಕ್ಲೇಮ್ ಸಹಚರ. ಇದನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ
ಸ್ವಯಂ-ಲೋಡ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ (MCP↔LSP ಬ್ರಿಡ್ಜ್ ಅನ್ನು ನೀವು ಆಯ್ಕೆಮಾಡಿ ಪರಿಶೀಲಿಸುತ್ತೀರಿ); ದೋಷಪೂರಿತ ನಮೂದು
ಕೇವಲ ಸಂಪರ್ಕ ದೋಷವನ್ನು ಲಾಗ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಸೆಷನ್ಗಳನ್ನು ಎಂದಿಗೂ ಸ್ಥಗಿತಗೊಳಿಸುವುದಿಲ್ಲ.

ಈ ಪಟ್ಟಿಯನ್ನು 2026-06-17 ರಂದು `ci.yml` ಜೊತೆಗೆ ಹೊಂದಾಣಿಕೆ ಮಾಡಲಾಗಿದೆ (ಹಿಂದಿನ ಆವೃತ್ತಿಯಲ್ಲಿ

`check:codeql-ratchet`, `check:pr-evidence` ಬಿಟ್ಟುಹೋಗಿದ್ದವು). ಹೊಂದಾಣಿಕೆ ಮಾಡಿದ ಸಮೂಹದ ROI ಪರಿಶೀಲನೆಯು
ಕೆಳಗಿನ ತರ್ಕಬದ್ಧಗೊಳಿಸುವಿಕೆ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಗುರುತಿಸಿದೆ. **ವಿಲೀನಗಳು ಯಾಂತ್ರಿಕ CI
ಬದಲಾವಣೆಗಳಾಗಿವೆ; ತಿರುಗಿಸುವಿಕೆಗಳು/ತೆಗೆದುಹಾಕುವಿಕೆಗಳು ನಿರ್ವಾಹಕರಿಗೆ ಮೀಸಲಾದ ನೀತಿ ನಿರ್ಧಾರಗಳಾಗಿವೆ.** ಕೆಳಗಿನ ಯಾವುದನ್ನೂ
ಇನ್ನೂ ಅನ್ವಯಿಸಲಾಗಿಲ್ಲ.

**ಮೇಲೆ ದಾಖಲಿಸದಿರುವವುಗಳೂ ಇವೆ** (ಸಲಹಾತ್ಮಕ, ಕಡಿಮೆ ಸಂಕೇತ): `docs-lint` ಜಾಬ್
(markdownlint + Vale, ಸಂಪೂರ್ಣ ಜಾಬ್ಗೆ `continue-on-error`) ಮತ್ತು ಸ್ವತಂತ್ರ ಸ್ಕ್ಯಾನರ್ ವರ್ಕ್ಫ್ಲೋಗಳಾದ
`semgrep.yml` / `codeql.yml` / `scorecard.yml`. `semgrepFindings: 0` ಎಂಬುದು
`quality-baseline.json` ನಲ್ಲಿದೆ, ಆದರೆ `ci.yml` ನಲ್ಲಿ ತಡೆಹಿಡಿಯುವ ರ್ಯಾಚೆಟ್ಗೆ ಜೋಡಿಸಲಾಗಿಲ್ಲ — ಈ ಮೆಟ್ರಿಕ್ ಪ್ರಸ್ತುತ
ಅನಾಥವಾಗಿದೆ.

### ವಿಲೀನ / ನಕಲು ನಿವಾರಣೆ (ಯಾಂತ್ರಿಕ, ಕಡಿಮೆ ಅಪಾಯ)

ಪ್ರತಿ ಅಭ್ಯರ್ಥಿಯನ್ನೂ 2026-06-17 ರಂದು ಲೈವ್ ಗೇಟ್ ಸ್ಥಿತಿಯ ವಿರುದ್ಧ ಮೌಲ್ಯೀಕರಿಸಲಾಗಿದೆ (ನಂಬಿ, ಆದರೆ ಪರಿಶೀಲಿಸಿ);
ಹಲವಾರು "ಸ್ಪಷ್ಟ" ವಿಲೀನಗಳು ಸಾಲವನ್ನು ಮರೆಮಾಡಿರುವುದು ಕಂಡುಬಂದಿದ್ದು, ಅವು **ಸ್ವಚ್ಛ ಪರ್ಯಾಯಗಳಲ್ಲ**.

- **`check:docs-sync` ಎರಡು ಬಾರಿ ರನ್ ಆಗುತ್ತದೆ** — `lint` ಜಾಬ್ನಲ್ಲಿ ಸ್ವತಂತ್ರವಾಗಿ ಮತ್ತು `check:docs-all` (`docs-sync-strict`) ಒಳಗೆ ಮತ್ತೊಮ್ಮೆ, ಹಾಗೆಯೇ husky pre-commit hookನಲ್ಲಿಯೂ. ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** — ಸ್ವತಂತ್ರ `lint` ಆಹ್ವಾನವನ್ನು ತೆಗೆದುಹಾಕಲಾಗಿದೆ.
- **CVE ಸ್ಕ್ಯಾನಿಂಗ್** — ❌ **ಸ್ವಚ್ಛ ವಿಲೀನವಲ್ಲ.** ಯಾವುದೇ high/critical CVE ಕಂಡುಬಂದರೆ `audit:deps` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ; `check:vuln-ratchet` (osv) baselineಗೆ ಹೋಲಿಸಿದಾಗ _ಹಿಂಜರಿತ_ ಉಂಟಾದರೆ ಮಾತ್ರ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ (ಪ್ರಸ್ತುತ 1 MODERATE). ಅರ್ಥವ್ಯವಸ್ಥೆಗಳು ವಿಭಿನ್ನವಾಗಿವೆ — `audit:deps` ತೆಗೆದುಹಾಕಿದರೆ ಸಂಪೂರ್ಣ high/critical ಗೇಟ್ ಕಳೆದುಹೋಗುತ್ತದೆ. ಎರಡನ್ನೂ ಉಳಿಸಿ.
- **ಚಕ್ರ ಪತ್ತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (#15159 G-01/G-02). ಇಲ್ಲಿನ ಹಳೆಯ ಪಠ್ಯವು `check:cycles` ಅನ್ನು "ಹಸಿರು, ಆಯ್ದ" ಗೇಟ್ ಎಂದು ಕರೆದಿತ್ತು ಮತ್ತು `check:circular-deps` (dpdm) 91 ಚಕ್ರಗಳನ್ನು ವರದಿ ಮಾಡಿದ್ದರಿಂದ ಅದನ್ನು ತಡೆಹಿಡಿಯುವ ಗೇಟ್ ಆಗಿ ಉಳಿಸುವುದನ್ನು ಸಮರ್ಥಿಸಿತ್ತು. ಆ ಹಸಿರು ಸ್ಥಿತಿ **ತಪ್ಪು ಹಸಿರು** ಆಗಿತ್ತು: `check:cycles` 5 ಉಪಡೈರೆಕ್ಟರಿಗಳನ್ನು (450 ಫೈಲ್ಗಳು) ಸ್ಕ್ಯಾನ್ ಮಾಡುತ್ತಿತ್ತು, ಸ್ಥಿರ `import|export … from` ಮಾತ್ರ ಹೊಂದಿಸುತ್ತಿತ್ತು ಮತ್ತು ಪ್ರತಿಯೊಂದು `@/` ಹಾಗೂ `@omniroute/open-sse/` ಸ್ಪೆಸಿಫೈಯರ್ ಅನ್ನು ಕೈಬಿಡುತ್ತಿತ್ತು; ಆದ್ದರಿಂದ ರೆಪೊದಲ್ಲಿ ಪ್ರಾಬಲ್ಯ ಹೊಂದಿದ್ದ dynamic-import + alias ಚಕ್ರಗಳನ್ನು ಅದು ನೋಡಲಾಗುತ್ತಿರಲಿಲ್ಲ. ಸರಿಪಡಿಸಲಾಗಿದೆ: ಗೇಟ್ ಈಗ `src` + `open-sse` (5023 ಫೈಲ್ಗಳು) ಅನ್ನು ಸಂಚರಿಸುತ್ತದೆ, TypeScript AST ನಿಂದ ಸ್ಪೆಸಿಫೈಯರ್ಗಳನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ (ಹೀಗಾಗಿ `import("…")` ಎಣಿಕೆಯಾಗುತ್ತದೆ ಮತ್ತು type-position `typeof import("…")` ಎಣಿಕೆಯಾಗುವುದಿಲ್ಲ), ಹಾಗೂ tsconfig `paths` ಅನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. ಇದು 0 ಅಲ್ಲ, **14** ಚಕ್ರಗಳನ್ನು ಕಂಡುಹಿಡಿಯುತ್ತದೆ. ಗೇಟ್ PRನಲ್ಲಿ ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ 14 ಚಕ್ರಗಳನ್ನು ಸರಿಪಡಿಸಲಾಗದ ಕಾರಣ, `check:cycles` ಈಗ ಒಂದು **ರ್ಯಾಚೆಟ್** ಆಗಿದೆ (`--ratchet`, `quality-baseline.json` ನಲ್ಲಿ ಗರಿಷ್ಠ ಮಿತಿ `metrics.cycles.value = 14`, `direction: down`) — ಇದು ಯಾವುದೇ _ಹಿಂಜರಿತವನ್ನು_ ತಡೆಯುತ್ತದೆ ಮತ್ತು ಎಣಿಕೆ ಕೇವಲ ಕಡಿಮೆಯಾಗಬಹುದು. CI `npm run check:cycles:ratchet` ಅನ್ನು ರನ್ ಮಾಡುತ್ತದೆ. ಕ್ರಮೇಣ ಕಡಿತವು **A-01** ಜೊತೆಗೆ ಸಾಗುತ್ತದೆ. ವಿಶಾಲವಾದ ಎರಡನೇ ಅಭಿಪ್ರಾಯವಾಗಿ `check:circular-deps` (dpdm) ಸಲಹಾತ್ಮಕವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ.
- **ಸಂಕೀರ್ಣತೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ಒಂದು ESLint ಸಂಚಾರ, ruleId ಪ್ರಕಾರ ಎಣಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ cyclomatic+max-lines ಮತ್ತು cognitive baselineಗಳು ಸ್ವತಂತ್ರವಾಗಿರುತ್ತವೆ; ಪ್ರತ್ಯೇಕ `check:complexity` / `check:cognitive-complexity` ಸ್ಥಳೀಯ `--update` ಗಾಗಿ ಉಳಿಯುತ್ತವೆ.
- **`/api` ಭ್ರಮೆ-ವಿರೋಧಿ ಪರಿಶೀಲನೆ** — ✅ **ಪೂರ್ಣಗೊಂಡಿದೆ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ಯ ಒಂದು FS ಪಟ್ಟಿ; openapi-routes + docs-symbols ಇನ್ನೂ ಸ್ವತಂತ್ರವಾಗಿ ವರದಿ ಮಾಡುತ್ತವೆ; ಪ್ರತ್ಯೇಕ ಪರಿಶೀಲನೆಗಳು ಸ್ಥಳೀಯ ರನ್ಗಳಿಗಾಗಿ ಉಳಿಯುತ್ತವೆ.
- **`check:node-runtime` 11 ಜಾಬ್ಗಳಲ್ಲಿ ರನ್ ಆಗುತ್ತದೆ** — ⚠️ **ಕಡಿಮೆ ROI.** ಪ್ರತಿಯೊಂದೂ ಪ್ರತ್ಯೇಕ ರನ್ನರ್ ಆಗಿದ್ದು, ಪರಿಶೀಲನೆಗೆ <1s ಬೇಕಾಗುತ್ತದೆ; ಅಗ್ಗದ ಪ್ರತಿ-ಜಾಬ್ ಸುರಕ್ಷತಾ ಪರಿಶೀಲನೆಯನ್ನು ಕಳೆದುಕೊಳ್ಳುವ ಬದಲಾಗಿ ಒಟ್ಟು ಉಳಿತಾಯ ~10s ಮಾತ್ರ. ಈ ಬದಲಾವಣೆಯ ಗೊಂದಲಕ್ಕೆ ತಕ್ಕ ಮೌಲ್ಯವಿಲ್ಲ.
- **CI lintನಲ್ಲಿ `typecheck:noimplicit:core`** — ✅ **lint ಜಾಬ್ನಿಂದ ತೆಗೆದುಹಾಕಲಾಗಿದೆ** (ಇದು ಸಲಹಾತ್ಮಕ `continue-on-error` ಆಗಿತ್ತು); ತಡೆಹಿಡಿಯುವ ಪ್ರಕಾರ ಮೇಲ್ಮೈ `typecheck:core` + `check:type-coverage` ಆಗಿದೆ. ಸ್ಥಳೀಯ ಸ್ಕ್ರಿಪ್ಟ್ ಉಳಿಸಲಾಗಿದೆ.

### ತಿರುಗಿಸಿ / ನಿರ್ಧರಿಸಿ (ನಿರ್ವಾಹಕರ ನೀತಿ)

- `check:openapi-security-tiers` (ಸಲಹಾತ್ಮಕ) — ❌ **ನೇರವಾಗಿ ತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ.** ಇದು 0 ನೊಂದಿಗೆ ನಿರ್ಗಮಿಸುತ್ತದೆ, ಆದರೆ `LOCAL_ONLY_API_PREFIXES` ಅಡಿಯಲ್ಲಿರುವ ಹಲವಾರು `traffic-inspector` ರೂಟ್ಗಳಲ್ಲಿ `x-loopback-only: true` annotation ಇಲ್ಲವೆಂದು ಎಚ್ಚರಿಸುತ್ತದೆ. ಇದನ್ನು ಜಾರಿಗೊಳಿಸುವ ಮೊದಲು ಆ annotationಗಳನ್ನು `openapi.yaml` ಗೆ ಸೇರಿಸುವುದು ಅಗತ್ಯ.
- `typecheck:noimplicit:core` (ಸಲಹಾತ್ಮಕ) — ತಡೆಹಿಡಿಯುವ `check:type-coverage` ರ್ಯಾಚೆಟ್ ಇದನ್ನು ಬಹುಮಟ್ಟಿಗೆ ಒಳಗೊಂಡಿದೆ. ಇದನ್ನು ರ್ಯಾಚೆಟ್ಗೆ ತಿರುಗಿಸಿ ಅಥವಾ ಅನಗತ್ಯವಾದ ಎರಡನೇ `tsc` ಪಾಸ್ ಅನ್ನು ತೆಗೆದುಹಾಕಿ.
- `test:vitest:ui` (ಈಗ **ತಡೆಹಿಡಿಯುವ**) — ಮೊದಲೇ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ವೈಫಲ್ಯಗಳನ್ನು `vitest.config.ts` ನಲ್ಲಿ `// #8618` ಟ್ರ್ಯಾಕಿಂಗ್ ಕಾಮೆಂಟ್ಗಳೊಂದಿಗೆ ಸ್ಪಷ್ಟವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ; ಹೊಸ ವೈಫಲ್ಯಗಳು ಜಾಬ್ ಅನ್ನು ವಿಫಲಗೊಳಿಸುತ್ತವೆ.
- `check:secrets` (gitleaks, ದಾಖಲೀಕರಿಸಿದ 3 false-positiveಗಳಲ್ಲಿ ಸ್ಥಗಿತಗೊಳಿಸಿದ ತಡೆಹಿಡಿಯುವ ರ್ಯಾಚೆಟ್) — 0 ತಲುಪಲು ಆ 3 ಅನ್ನು allowlistಗೆ ಸೇರಿಸಿ, ಅಥವಾ ಸಲಹಾತ್ಮಕ ಮಟ್ಟಕ್ಕೆ ಇಳಿಸಿ. ಇದು GitHubನ ಮೂಲ secret-scanning + `check:public-creds` ಜೊತೆ ಅತಿಕ್ರಮಿಸುತ್ತದೆ.
- `check:pr-evidence` (ತಡೆಹಿಡಿಯುವ, PR-body ಗದ್ಯವನ್ನು grep ಮಾಡುತ್ತದೆ) — false-positive ಅಪಾಯ ಹೆಚ್ಚು; ತೆಗೆದುಹಾಕಿದರೆ Hard Rule #18 ಜಾರಿ ದುರ್ಬಲಗೊಳ್ಳುತ್ತದೆ, ಆದ್ದರಿಂದ ಇದು ನಿಜವಾದ ನೀತಿ ನಿರ್ಧಾರವಾಗಿದೆ.
- `semgrep` (ಸಲಹಾತ್ಮಕ ಸ್ವತಂತ್ರ ಪರಿಶೀಲನೆ) — OWASP ವರ್ಗಗಳಿಗೆ ಸಂಬಂಧಿಸಿ CodeQL ಜೊತೆ ಅತಿಕ್ರಮಿಸುತ್ತದೆ; ಅದರ baseline ಅನ್ನು ರ್ಯಾಚೆಟ್ಗೆ ಜೋಡಿಸಿ ಅಥವಾ ತೆಗೆದುಹಾಕಿ.
