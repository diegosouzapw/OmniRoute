## ಸಂದರ್ಭ

OmniRoute ಪ್ರಸ್ತುತ `src/lib/db/` ನಿಂದ ಡೊಮೇನ್-ಆಧಾರಿತ ಸ್ಥಿರತೆ ಫಂಕ್ಷನ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ, ಹಾಗೆಯೇ
`src/lib/db/core.ts` ಹಿಂದಿರುಗಿಸುವ ಹಂಚಿಕೆಯ ಸಂಪರ್ಕವು `src/lib/db/adapters/types.ts` ನಲ್ಲಿರುವ ಸಿಂಕ್ರೊನಸ್ `SqliteAdapter`
ಒಪ್ಪಂದವನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸುತ್ತದೆ. ಆ ಅಡಾಪ್ಟರ್ ಹಲವಾರು SQLite ರನ್ಟೈಮ್ಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ, ಆದರೆ ಅದರ
ಇಂಟರ್ಫೇಸ್ SQLite-ಆಧಾರಿತವಾಗಿಯೇ ಉಳಿದಿದೆ: ಸಿಂಕ್ರೊನಸ್ ಪ್ರಿಪೇರ್ಡ್ ಸ್ಟೇಟ್ಮೆಂಟ್ಗಳು, `pragma`, ಡಿಫರ್ಡ್ ಮತ್ತು ಇಮೀಡಿಯೇಟ್
ಟ್ರಾನ್ಸಾಕ್ಷನ್ಗಳು, ನೇಟಿವ್/ಫೈಲ್-ಕಾಪಿ ಬ್ಯಾಕಪ್, ಚೆಕ್ಪಾಯಿಂಟ್ ಮತ್ತು ಸ್ಥಳೀಯ ಡೇಟಾಬೇಸ್ ಹ್ಯಾಂಡಲ್.

ಪ್ರಸ್ತುತ ಸ್ಟಾರ್ಟ್ಅಪ್ ಮತ್ತು ರಿಕವರಿ ಮಾರ್ಗವು SQLite ಫೈಲ್ ಜೀವನಚಕ್ರವನ್ನೂ ನಿರ್ವಹಿಸುತ್ತದೆ. `src/lib/db/core.ts`
`storage.sqlite` ಅನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ, ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪ್ತಿಯ ಒಂದೇ ಅಡಾಪ್ಟರ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ, WAL ಅನ್ನು ಚೆಕ್ಪಾಯಿಂಟ್ ಮಾಡುತ್ತದೆ, ರಿಕವರಿ
ಸಮಯದಲ್ಲಿ ಆಯ್ದ ಟೇಬಲ್ಗಳನ್ನು ಸಂರಕ್ಷಿಸುತ್ತದೆ ಮತ್ತು ಡೇಟಾಬೇಸ್ ಅನ್ನು ಮರುನಿರ್ಮಿಸುವಾಗ SQLite ಕಂಪ್ಯಾನಿಯನ್ ಫೈಲ್ಗಳನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ. `src/lib/db/adapters/driverFactory.ts` ನಲ್ಲಿನ ಡ್ರೈವರ್
ಆಯ್ಕೆಯು ಬೆಂಬಲಿತ SQLite ರನ್ಟೈಮ್ಗಳಿಂದ ಒಂದನ್ನು ಆಯ್ಕೆ ಮಾಡುತ್ತದೆ; ಅದು ಬಾಹ್ಯ-ಬ್ಯಾಕೆಂಡ್ ಅಬ್ಸ್ಟ್ರಾಕ್ಷನ್ ಅಲ್ಲ.

ಸ್ಕೀಮಾ ವಿಕಸನವೂ ಇದೇ ರೀತಿಯಲ್ಲಿ ಬಿಗಿಯಾಗಿ ಜೋಡಿತವಾಗಿದೆ. `src/lib/db/migrationRunner.ts` ಸಂಖ್ಯೆಯುಳ್ಳ SQL ಫೈಲ್ಗಳನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ,
`sqlite_master` ಮತ್ತು `PRAGMA table_info` ಅನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ, ಐಚ್ಛಿಕ FTS5 ಬೆಂಬಲವನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ ಮತ್ತು ಮೈಗ್ರೇಶನ್
ಕೆಲಸವನ್ನು SQLite ಟ್ರಾನ್ಸಾಕ್ಷನ್ಗಳಲ್ಲಿ ನಡೆಸುತ್ತದೆ. `src/lib/db/backup.ts` ಮತ್ತು
`src/lib/db/optimizationSettings.ts` ನಂತಹ ಕಾರ್ಯಾಚರಣಾ ಮಾಡ್ಯೂಲ್ಗಳು ಬ್ಯಾಕಪ್, `PRAGMA`, WAL, ಪೇಜ್-ಗಾತ್ರ, ಆಟೋ-ವ್ಯಾಕ್ಯೂಮ್ ಮತ್ತು `VACUUM`
ಸೆಮ್ಯಾಂಟಿಕ್ಸ್ ಅನ್ನು ನೇರವಾಗಿ ಬಳಸುತ್ತವೆ.

ಇವು ಎಂಬೆಡೆಡ್ SQLite ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ನ ಮಾನ್ಯ ಗುಣಲಕ್ಷಣಗಳು. PostgreSQL ಅಥವಾ MySQL ಮೇಲೆ SQLite API ಅನ್ನು ಅನುಕರಿಸುವ
ಒತ್ತಾಯವಿಲ್ಲದೆ ಇವು ಲಭ್ಯವಾಗಿಯೇ ಇರಬೇಕು.

## ನಿರ್ಧಾರ

ಪೋರ್ಟಬಲ್ ದೀರ್ಘಕಾಲಿಕ ಸ್ಥಿತಿಗಾಗಿ ಎರಡು-ಹಂತದ ಸ್ಥಿರತೆ ಗಡಿಯನ್ನು ಅಳವಡಿಸಿಕೊಳ್ಳಿ:

1. **ಡೊಮೇನ್ ರೆಪೊಸಿಟರಿ ಒಪ್ಪಂದಗಳು** ವ್ಯವಹಾರ ಮತ್ತು ರೂಟಿಂಗ್
   ಕೋಡ್ಗೆ ಅಗತ್ಯವಿರುವ ಸ್ಥಿರತೆ ಕಾರ್ಯಾಚರಣೆಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತವೆ. ಕರೆಮಾಡುವವರು SQL ಪಠ್ಯ, ಪ್ರಿಪೇರ್ಡ್ ಸ್ಟೇಟ್ಮೆಂಟ್ಗಳು,
   ಡೇಟಾಬೇಸ್ ಫೈಲ್ಗಳು ಅಥವಾ ಡೈಲೆಕ್ಟ್ ಆಬ್ಜೆಕ್ಟ್ಗಳ ಬದಲಿಗೆ ಡೊಮೇನ್ ವರ್ತನೆ ಮತ್ತು ಡೊಮೇನ್ ಡೇಟಾವನ್ನು ಅವಲಂಬಿಸುತ್ತಾರೆ.
2. **ಆಂತರಿಕ ಅಸಿಂಕ್ರೊನಸ್ ಬ್ಯಾಕೆಂಡ್ ಒಪ್ಪಂದವು** ರೆಪೊಸಿಟರಿ ಅನುಷ್ಠಾನಗಳಿಗೆ
   ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಕಾಂಟೆಕ್ಸ್ಟ್ಗಳು, ಆರೋಗ್ಯ/ಸಿದ್ಧತೆ, ಮೈಗ್ರೇಶನ್ ಸಮನ್ವಯ, ಬ್ಯಾಕೆಂಡ್ ಸಾಮರ್ಥ್ಯಗಳು ಮತ್ತು
   ವರ್ಗೀಕೃತ ದೋಷಗಳೊಂದಿಗೆ ಬೆಂಬಲ ನೀಡುತ್ತದೆ. ನಿಖರವಾದ TypeScript ಇಂಟರ್ಫೇಸ್ ಅನ್ನು ಮೊದಲ ಅನುಷ್ಠಾನ
   PR ನಲ್ಲಿ ಪ್ರಸ್ತಾಪಿಸಿ, ಅನುಸರಣೆ ಪರೀಕ್ಷೆಗಳ ಮೂಲಕ ಸಾಬೀತುಪಡಿಸಲಾಗುತ್ತದೆ; ಈ ADR ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಊಹಾತ್ಮಕ API ಅನ್ನು ಸ್ಥಿರಗೊಳಿಸುವುದಿಲ್ಲ.

SQLite ಡೀಫಾಲ್ಟ್ ಅನುಷ್ಠಾನವಾಗಿ ಉಳಿಯುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ SQLite ಡ್ರೈವರ್ ಕ್ಯಾಸ್ಕೇಡ್ ಮತ್ತು ಸಿಂಕ್ರೊನಸ್
`SqliteAdapter`, ಡೊಮೇನ್ಗಳನ್ನು ಸಣ್ಣ ವರ್ಟಿಕಲ್ ಸ್ಲೈಸ್ಗಳಲ್ಲಿ ಮೈಗ್ರೇಟ್ ಮಾಡುವಾಗ SQLite ರೆಪೊಸಿಟರಿ ಅನುಷ್ಠಾನದ ಹಿಂದೆ
ಉಳಿಯುತ್ತವೆ. ಯಾವುದೇ ಬಳಕೆದಾರರು ಬಾಹ್ಯ ಸೇವೆಯನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಬೇಕಾಗಿಲ್ಲ.

ರೆಪೊಸಿಟರಿ ಗಡಿಯನ್ನು SQLite ವಿರುದ್ಧ ಸಾಬೀತುಪಡಿಸಿದ ನಂತರ PostgreSQL ಮೊದಲ ಪ್ರಸ್ತಾವಿತ ಬಾಹ್ಯ ಅನುಷ್ಠಾನವಾಗಿರುತ್ತದೆ.
MySQL, ಎರಡನೇ ವ್ಯವಹಾರ-ತರ್ಕ ಫೋರ್ಕ್ ಆಗುವ ಬದಲು ಅದೇ ಅನುಸರಣೆ ಸೂಟ್ ವಿರುದ್ಧ ಸಮಾನಾಂತರ ಅನುಷ್ಠಾನವಾಗಿ
ಅನುಸರಿಸುತ್ತದೆ.

## ಗಡಿ ನಿಯಮಗಳು

### ಪೋರ್ಟಬಲ್ ರೆಪೊಸಿಟರಿ ಇಂಟರ್ಫೇಸ್

ಪೋರ್ಟಬಲ್ ರೆಪೊಸಿಟರಿ ಇವುಗಳನ್ನು ಒದಗಿಸಬಹುದು:

- ಡೊಮೇನ್ ರೀಡ್ಗಳು ಮತ್ತು ರೈಟ್ಗಳು;
- ಸ್ಪಷ್ಟ ಅಟಾಮಿಕ್ ಕಾರ್ಯಾಚರಣೆಗಳು ಮತ್ತು ಟ್ರಾನ್ಸಾಕ್ಷನ್-ಸ್ಕೋಪ್ಡ್ ರೆಪೊಸಿಟರಿ ಪ್ರವೇಶ;
- ಸಮಕಾಲೀನತೆ ಸೆಮ್ಯಾಂಟಿಕ್ಸ್ ಡೊಮೇನ್ನ ಭಾಗವಾಗಿರುವಲ್ಲಿ ಕಂಪೇರ್/ಅಪ್ಡೇಟ್ ಅಥವಾ ಲೀಸ್ ಕಾರ್ಯಾಚರಣೆಗಳು;
- ಬ್ಯಾಕೆಂಡ್-ನ್ಯೂಟ್ರಲ್ ಪೇಜಿನೇಶನ್, ಕ್ರಮಗೊಳಿಸುವಿಕೆ ಮತ್ತು ಕನ್ಸ್ಟ್ರೇಂಟ್ ದೋಷಗಳು.

ಬ್ಯಾಕೆಂಡ್ ಆರೋಗ್ಯ, ಸಿದ್ಧತೆ ಮತ್ತು ಮೈಗ್ರೇಶನ್ ಸಮನ್ವಯವು ಪ್ರತ್ಯೇಕ ಡೊಮೇನ್ ರೆಪೊಸಿಟರಿಗಳಿಗೆ ಬದಲಾಗಿ ಆಂತರಿಕ ಬ್ಯಾಕೆಂಡ್/ಕಾರ್ಯಾಚರಣಾ
ಒಪ್ಪಂದಕ್ಕೆ ಸೇರಿವೆ.

ಪೋರ್ಟಬಲ್ ರೆಪೊಸಿಟರಿಯು ಇವುಗಳನ್ನು ಒದಗಿಸಬಾರದು:

- `prepare`, `get`, `all`, `run` ಅಥವಾ ಕಚ್ಚಾ ಡ್ರೈವರ್ ಹ್ಯಾಂಡಲ್ಗಳು;
- `PRAGMA`, WAL ಚೆಕ್ಪಾಯಿಂಟ್ ಮೋಡ್ಗಳು, `VACUUM` ಅಥವಾ ಪೇಜ್/ಕ್ಯಾಶ್ ಟ್ಯೂನಿಂಗ್;
- SQLite ಫೈಲ್ ಪಥಗಳು, ಕಂಪ್ಯಾನಿಯನ್ ಫೈಲ್ಗಳು ಅಥವಾ ಫೈಲ್-ಕಾಪಿ ಬ್ಯಾಕಪ್;
- ಕ್ರಾಸ್-ಬ್ಯಾಕೆಂಡ್ ಡೊಮೇನ್ ಒಪ್ಪಂದವಾಗಿ `lastInsertRowid`;
- FTS5 ಅಥವಾ `sqlite-vec` ಸಿಂಟ್ಯಾಕ್ಸ್;
- ಸಾಮಾನ್ಯ ವ್ಯವಹಾರ ಕೋಡ್ ಬಳಸುವ ಜೆನೆರಿಕ್ ಡೈಲೆಕ್ಟ್ ಎಸ್ಕೇಪ್ ಹ್ಯಾಚ್.

### ಬ್ಯಾಕೆಂಡ್ ಸಾಮರ್ಥ್ಯ ಇಂಟರ್ಫೇಸ್

ಬ್ಯಾಕೆಂಡ್-ನಿರ್ದಿಷ್ಟ ವರ್ತನೆಯು ಸ್ಪಷ್ಟವಾಗಿ ಮತ್ತು ಸುಲಭವಾಗಿ ಪತ್ತೆಹಚ್ಚಬಹುದಾಗಿ ಉಳಿಯುತ್ತದೆ. SQLite-ಮಾತ್ರದ ನಿರ್ವಹಣೆಯು
ತನ್ನದೇ ಅನುಷ್ಠಾನ ಮತ್ತು ಕಾರ್ಯಾಚರಣಾ ಇಂಟರ್ಫೇಸ್ನ ಹಿಂದೆ ಉಳಿಯುತ್ತದೆ, ಇದರಲ್ಲಿ ಇವು ಸೇರಿವೆ:

- ರನ್ಟೈಮ್ ಡ್ರೈವರ್ ಆಯ್ಕೆ;
- WAL ಚೆಕ್ಪಾಯಿಂಟ್ ಮತ್ತು SQLite ಶಟ್ಡೌನ್ ವರ್ತನೆ;
- ಪೇಜ್-ಗಾತ್ರ, ಕ್ಯಾಶ್-ಗಾತ್ರ ಮತ್ತು ಆಟೋ-ವ್ಯಾಕ್ಯೂಮ್ ಸೆಟ್ಟಿಂಗ್ಗಳು;
- ಡೇಟಾಬೇಸ್-ಫೈಲ್ ಬ್ಯಾಕಪ್, ಮರುಸ್ಥಾಪನೆ ಮತ್ತು ರಿಕವರಿ;
- SQLite ಸ್ಕೀಮಾ ಪರಿಶೀಲನೆ;
- FTS5 ಮತ್ತು `sqlite-vec` ಏಕೀಕರಣ.

ಬಾಹ್ಯ ಬ್ಯಾಕೆಂಡ್ ಆ ವೈಶಿಷ್ಟ್ಯಗಳನ್ನು ಅನುಕರಿಸುವ ಅಗತ್ಯವಿಲ್ಲ. ರೆಪೊಸಿಟರಿಗಳು ಪೋರ್ಟಬಲ್ ಸಾಮರ್ಥ್ಯವನ್ನು ಬಳಸಬೇಕು,
ದಾಖಲೀಕೃತ ವರ್ತನೆಯೊಂದಿಗೆ ಬ್ಯಾಕೆಂಡ್-ನಿರ್ದಿಷ್ಟ ಅನುಷ್ಠಾನವನ್ನು ಒದಗಿಸಬೇಕು ಅಥವಾ ಆ ಸಾಮರ್ಥ್ಯವು ಲಭ್ಯವಿಲ್ಲ ಎಂದು ವರದಿ
ಮಾಡಬೇಕು.

## ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಮತ್ತು ಮೈಗ್ರೇಶನ್ ಮಾದರಿ

ರೆಪೊಸಿಟರಿ APIಗಳು ಅಣುಸ್ವರೂಪದ ವ್ಯವಹಾರ ಕಾರ್ಯಾಚರಣೆಯನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತವೆ; ಕರೆ ಮಾಡುವವರು SQL ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಮೋಡ್ ಅನ್ನು ಆಯ್ಕೆ ಮಾಡುವುದಿಲ್ಲ.
ಪ್ರತಿ ಕಾರ್ಯಾಚರಣೆಯು ತನ್ನ ಗೋಚರ ಸಮಕಾಲೀನತಾ ಖಾತರಿಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸಬೇಕು: ಸಂರಕ್ಷಿತ ಅವಿಕಾರಿಗಳು, ಸಂಘರ್ಷ
ಪತ್ತೆಹಚ್ಚುವಿಕೆ, ಮರುಪ್ರಯತ್ನ ವರ್ಗೀಕರಣ, ಐಡೆಂಪೊಟೆನ್ಸಿ ನಿರೀಕ್ಷೆಗಳು ಮತ್ತು ಟ್ರಾನ್ಸಾಕ್ಷನ್-ಸಂದರ್ಭದ ಪ್ರಸರಣ.
ಆ ಗೋಚರ ಖಾತರಿಗಳು ಸಮಾನವಾಗಿ ಉಳಿದಾಗ ಮಾತ್ರ ಅನುಷ್ಠಾನಗಳು ವಿಭಿನ್ನ ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಮತ್ತು ಪ್ರತ್ಯೇಕತಾ ಕಾರ್ಯವಿಧಾನಗಳನ್ನು
ಬಳಸಬಹುದು. ಕಾರ್ಯಾಚರಣೆಯ ಒಪ್ಪಂದವನ್ನು ಪೂರೈಸುವಲ್ಲಿ SQLite ಆಂತರಿಕವಾಗಿ ತನ್ನ ಪ್ರಸ್ತುತ deferred ಅಥವಾ immediate
ಟ್ರಾನ್ಸಾಕ್ಷನ್ ನಡವಳಿಕೆಯನ್ನು ಬಳಸುವುದನ್ನು ಮುಂದುವರಿಸಬಹುದು.

ಒಂದೇ ಸ್ಕೀಮಾ ಬದಲಾವಣೆಗಾಗಿ ಅನೇಕ ಅಪ್ಲಿಕೇಶನ್ ಪ್ರತಿಕೃತಿಗಳು ಪೈಪೋಟಿ ನಡೆಸದಂತೆ ಬಾಹ್ಯ ಬ್ಯಾಕೆಂಡ್ಗಳಿಗೆ ಸ್ಪಷ್ಟವಾದ ಮೈಗ್ರೇಶನ್ ಮಾಲೀಕತ್ವದ ಅಗತ್ಯವಿದೆ.
ಬ್ಯಾಕೆಂಡ್ ಮೈಗ್ರೇಶನ್ ಇತಿಹಾಸಗಳು ತಾರ್ಕಿಕ ಮೈಲಿಗಲ್ಲುಗಳನ್ನು ಹಂಚಿಕೊಳ್ಳಬಹುದು, ಆದರೆ SQLite SQL
ಫೈಲ್ಗಳು ಮತ್ತೊಂದು ಡೈಲೆಕ್ಟ್ಗೆ ಪೋರ್ಟಬಲ್ ಅಥವಾ ಮರುಬಳಕೆ ಮಾಡಬಹುದೆಂದು ಊಹಿಸಲಾಗುವುದಿಲ್ಲ.

## ಅಡ್ಡ-ಬ್ಯಾಕೆಂಡ್ ಅನುಸರಣೆ ಅರ್ಥವಿಜ್ಞಾನ

ಅನುಸರಣೆ ಪರೀಕ್ಷೆಗಳು ಕೇವಲ ರೆಪೊಸಿಟರಿ ವಿಧಾನಗಳ ಸಿಗ್ನೇಚರ್ಗಳನ್ನಷ್ಟೇ ಅಲ್ಲದೆ, ನಡವಳಿಕೆಯನ್ನೂ ಒಳಗೊಂಡಿರಬೇಕು. ಮೈಗ್ರೇಟ್ ಮಾಡಿದ ಪ್ರತಿಯೊಂದು ಡೊಮೇನ್
ಈ ಕೆಳಗಿನವುಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸಿ ಪರಿಶೀಲಿಸಬೇಕು:

- ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಸಮಯ ವಲಯ, ನಿಖರತೆ ಮತ್ತು ಸರಣೀಕರಣ;
- `NULL` ಕ್ರಮಗೊಳಿಸುವಿಕೆ, ಕೊಲೇಶನ್ ಮತ್ತು ಅಕ್ಷರ ಗಾತ್ರದ ಸಂವೇದನಾಶೀಲತೆಯ ನಿರೀಕ್ಷೆಗಳು;
- JSON ಪ್ರಾತಿನಿಧ್ಯ ಮತ್ತು ಹೋಲಿಕೆ ನಡವಳಿಕೆ;
- ಪೂರ್ಣಾಂಕ, ದಶಮಾಂಶ ಮತ್ತು ವಿತ್ತೀಯ ನಿಖರತೆ;
- ಪುಟವಿಂಗಡಣೆಗಾಗಿ ಸ್ಥಿರ ಕ್ರಮಗೊಳಿಸುವಿಕೆ ಮತ್ತು ನಿರ್ಣಾಯಕ ಸಮಸ್ಥಿತಿ-ಭೇದಕಗಳು;
- SQLite ಸಾಲಿನ IDಗಳನ್ನು ಅವಲಂಬಿಸದ ID ಉತ್ಪಾದನೆ;
- ಅನನ್ಯತೆ ಮತ್ತು ಫಾರಿನ್-ಕೀ ಉಲ್ಲಂಘನೆ ವರ್ಗೀಕರಣ;
- ಯಾವುದೇ ಬದಲಾವಣೆಯಿಲ್ಲದ, ಹೋಲಿಕೆ/ನವೀಕರಣ ಮತ್ತು ಅಳಿಸುವಿಕೆ ಕಾರ್ಯಾಚರಣೆಗಳಿಗಾಗಿ ಪರಿಣಾಮಿತ-ಸಾಲುಗಳ ನಡವಳಿಕೆ;
- ಸಮಕಾಲೀನ-ಬರಹದ ಫಲಿತಾಂಶಗಳು, ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ ಸಂಘರ್ಷಗಳು ಮತ್ತು ಐಡೆಂಪೊಟೆಂಟ್ ಮರುಪ್ರಯತ್ನಗಳು.

ಒಂದು ಡೊಮೇನ್ ಸಮಾನವಾದ ಗೋಚರ ಅರ್ಥವಿಜ್ಞಾನವನ್ನು ನಿರ್ದಿಷ್ಟಪಡಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ, ಅದು ಇನ್ನೂ ಪೋರ್ಟಬಲ್ ಆಗಿಲ್ಲ ಮತ್ತು ಆ ಒಪ್ಪಂದವನ್ನು
ವಿನ್ಯಾಸಗೊಳಿಸುವವರೆಗೆ ಬ್ಯಾಕೆಂಡ್-ನಿರ್ದಿಷ್ಟವಾಗಿಯೇ ಉಳಿಯಬೇಕು.

## ಹೊಂದಾಣಿಕೆ ಅವಶ್ಯಕತೆಗಳು

ಈ ADR ಅನ್ನು ಅನುಸರಿಸುವ ಯಾವುದೇ ಅನುಷ್ಠಾನವು ಈ ಗುಣಲಕ್ಷಣಗಳನ್ನು ಸಂರಕ್ಷಿಸಬೇಕು:

- SQLite ಶೂನ್ಯ-ಕಾನ್ಫಿಗರೇಶನ್ ಡೀಫಾಲ್ಟ್ ಆಗಿ ಉಳಿಯುತ್ತದೆ.
- ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ SQLite ಫೈಲ್ಗಳು ಮತ್ತು ಮೈಗ್ರೇಶನ್ ಇತಿಹಾಸವು ಓದಬಹುದಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.
- npm, Electron, Docker ಮತ್ತು ನಿರ್ಬಂಧಿತ-ರನ್ಟೈಮ್ SQLite ಪರ್ಯಾಯಗಳು ತಮ್ಮ ಪ್ರಸ್ತುತ ಪ್ರಾರಂಭ ಮಾರ್ಗವನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.
- ಸಂಗ್ರಹಿತ ಪ್ರೊವೈಡರ್ ರುಜುವಾತುಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಅಪ್ಲಿಕೇಶನ್ ಎನ್ಕ್ರಿಪ್ಶನ್ ನಡವಳಿಕೆಯನ್ನು ಬಳಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ.
- ರೆಪೊಸಿಟರಿ ಮೈಗ್ರೇಶನ್ ರೂಟಿಂಗ್, ಕೋಟಾ, API-ಕೀ ಅಥವಾ ಆಡಿಟ್ ಅರ್ಥವಿಜ್ಞಾನವನ್ನು ಮೌನವಾಗಿ ಬದಲಾಯಿಸುವುದಿಲ್ಲ.
- ಬ್ಯಾಕಪ್ ಮತ್ತು ಮರುಪಡೆಯುವಿಕೆ ನಡವಳಿಕೆಯನ್ನು ಸಾರ್ವತ್ರಿಕವೆಂದು ಪ್ರಸ್ತುತಪಡಿಸುವ ಬದಲು ಪ್ರತಿ ಬ್ಯಾಕೆಂಡ್ಗೆ ಪ್ರತ್ಯೇಕವಾಗಿ ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
- ಸ್ವಚ್ಛವಾದ SQLite-ಮಾತ್ರದ ಸ್ಥಾಪನೆಯು ಬಾಹ್ಯ ಡೇಟಾಬೇಸ್ ಡ್ರೈವರ್ ಅನ್ನು ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ ಅಥವಾ ಅವಶ್ಯಪಡಿಸುವುದಿಲ್ಲ.

## ವಿತರಣೆ ಅನುಕ್ರಮ

1. ಪುನರುತ್ಪಾದಿಸಬಹುದಾದ SQLite ಕಪ್ಲಿಂಗ್ ಇನ್ವೆಂಟರಿಯನ್ನು ಪ್ರತ್ಯೇಕ ಪರಿಶೀಲನಾ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಆಗಿ ಪ್ರಕಟಿಸಿ.
2. ಮೊದಲ ಡೊಮೇನ್ ರೆಪೊಸಿಟರಿ ಒಪ್ಪಂದಗಳು ಮತ್ತು ಅನುಸರಣೆ ಪರೀಕ್ಷೆಗಳನ್ನು ಪರಿಚಯಿಸಿ.
3. ಡೀಫಾಲ್ಟ್ಗಳನ್ನು ಬದಲಾಯಿಸದೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ SQLite ಅನುಷ್ಠಾನವನ್ನು ಆ ಒಪ್ಪಂದಗಳ ಹಿಂದೆ ಹೊಂದಿಸಿ.
4. ನಿರ್ವಹಕರ ಅನುಮೋದನೆಗೆ ಒಳಪಟ್ಟು, ಒಂದು ಮಿತಿಗೊಳಿಸಲಾದ ಕಂಟ್ರೋಲ್-ಪ್ಲೇನ್ ಸ್ಲೈಸ್ಗಾಗಿ PostgreSQL ಅನ್ನು ಮೊದಲ ಬಾಹ್ಯ ಅನುಷ್ಠಾನವಾಗಿ
   ಸೇರಿಸಿ.
5. ಸಮಕಾಲೀನ-ಬರಹ ಮತ್ತು ಮೈಗ್ರೇಶನ್-ಮಾಲೀಕತ್ವ ಪರೀಕ್ಷೆಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿದ್ದ ನಂತರವೇ ಹಂಚಿಕೆಯ ಸ್ಥಿತಿಯನ್ನು ವಿಸ್ತರಿಸಿ.
6. ಡೇಟಾಬೇಸ್ ಬದಲಾವಣೆಯನ್ನು ಜಾಹೀರಾತು ಮಾಡುವ ಮೊದಲು ಆಫ್ಲೈನ್, ಮೌಲ್ಯೀಕರಿಸಿದ SQLite-ನಿಂದ-ಬಾಹ್ಯಕ್ಕೆ ಮೈಗ್ರೇಶನ್ ಮಾರ್ಗವನ್ನು ಸೇರಿಸಿ.
7. ಸಾಬೀತಾಗಿರುವ ರೆಪೊಸಿಟರಿ ಮತ್ತು ಬ್ಯಾಕೆಂಡ್ ಒಪ್ಪಂದಗಳಿಗೆ ಅನುಗುಣವಾಗಿ MySQL ಅನ್ನು ಸೇರಿಸಿ.

ಪ್ರತಿ ರನ್ಟೈಮ್ ಹಂತವು ಪ್ರತ್ಯೇಕವಾಗಿ ಪರಿಶೀಲಿಸಬಹುದಾದ PR ಆಗಿರುತ್ತದೆ. ಹಿಂದಿನ ಹಂತದಲ್ಲಿ ಸಾಬೀತಾಗದ ಅಮೂರ್ತೀಕರಣವನ್ನು ವಿಲೀನಗೊಳಿಸುವುದನ್ನು
ಸಮರ್ಥಿಸಲು ನಂತರದ ಹಂತವನ್ನು ಬಳಸಬಾರದು.

## ಮೊದಲ ಅನುಷ್ಠಾನ ಹಂತ

ಕಪ್ಲಿಂಗ್ ಇನ್ವೆಂಟರಿಯನ್ನು ಪರಿಶೀಲಿಸಿದ ನಂತರ ಮೊದಲ ರನ್ಟೈಮ್ ಹಂತವನ್ನು ಆಯ್ಕೆ ಮಾಡಬೇಕು. ಪ್ರೊವೈಡರ್
ಸಂಪರ್ಕಗಳು, API ಕೀಗಳು, ಕಾಂಬೊಗಳು ಮತ್ತು ರೌಟಿಂಗ್ ಕಾನ್ಫಿಗರೇಶನ್ ಅಭ್ಯರ್ಥಿಗಳಾಗಿವೆ, ಏಕೆಂದರೆ ಅವುಗಳ ಮೂಲ ಟೇಬಲ್ಗಳು
`src/lib/db/core.ts` ನಲ್ಲಿ ಗೋಚರಿಸುತ್ತವೆ; ಆದರೆ ಈ ADR ಯಾವುದೇ ಟೇಬಲ್ ಪಟ್ಟಿಯನ್ನಾಗಲಿ ಮೈಗ್ರೇಶನ್ PR ಅನ್ನಾಗಲಿ ಅನುಮೋದಿಸುವುದಿಲ್ಲ.
ಈ ಹಂತವು ಇವುಗಳನ್ನು ಒಳಗೊಂಡಿರಬೇಕು:

- SQLite ನಡವಳಿಕೆ-ಸಂರಕ್ಷಣಾ ಪರೀಕ್ಷೆಗಳು;
- ರೆಪೊಸಿಟರಿ ಅನುಸರಣೆ ಪರೀಕ್ಷೆಗಳು;
- ಸ್ಪಷ್ಟ ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಗಡಿಗಳು;
- ಸಂಗ್ರಹಿಸಿದ ರುಜುವಾತುಗಳಿಗೆ ಎನ್ಕ್ರಿಪ್ಶನ್ ಮತ್ತು ರಿಡ್ಯಾಕ್ಷನ್ ಪರಿಶೀಲನೆ;
- ಡೀಫಾಲ್ಟ್ ಸ್ಟಾರ್ಟ್ಅಪ್ ಕಾನ್ಫಿಗರೇಶನ್ಗೆ ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲದಿರುವುದು.

## ಪರಿಗಣಿಸಿದ ಪರ್ಯಾಯಗಳು

### `SqliteAdapter` ಅಡಿಯಲ್ಲಿ PostgreSQL ಸೇರಿಸುವುದು

ತಿರಸ್ಕರಿಸಲಾಗಿದೆ. `SqliteAdapter` ಎಂಬುದು SQLite ರನ್ಟೈಮ್ಗಳಿಗಾಗಿ ಇರುವ ಹೊಂದಾಣಿಕೆ ಪದರವಾಗಿದ್ದು, SQLite-ನಿರ್ದಿಷ್ಟ
ಕಾರ್ಯಾಚರಣೆಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಆ ಮೇಲ್ಮೈಯನ್ನು ಅನುಕರಿಸುವುದರಿಂದ ಸಿಂಕ್ರೋನಸ್ ಮತ್ತು ಡಯಲೆಕ್ಟ್-ನಿರ್ದಿಷ್ಟ ಪೂರ್ವಧಾರಣೆಗಳು
ಹೊಸ ಬ್ಯಾಕೆಂಡ್ಗೆ ಸೋರಿಕೆಯಾಗುತ್ತವೆ.

### ಎಲ್ಲಾ ಡೊಮೇನ್ಗಳಿಗೆ ಜೆನೆರಿಕ್ query/execute API ಅನ್ನು ಒದಗಿಸುವುದು

ಪ್ರಾಥಮಿಕ ಗಡಿಯಾಗಿ ತಿರಸ್ಕರಿಸಲಾಗಿದೆ. ಇದು ಸಂಪರ್ಕ ನಿರ್ವಹಣೆಯನ್ನು ಕೇಂದ್ರೀಕರಿಸುತ್ತದೆ, ಆದರೆ SQL ಡಯಲೆಕ್ಟ್,
ಟ್ರಾನ್ಸಾಕ್ಷನ್ ಮತ್ತು ಟೇಬಲ್ ಕಪ್ಲಿಂಗ್ ಅನ್ನು ಬಿಸಿನೆಸ್ ಮಾಡ್ಯೂಲ್ಗಳಲ್ಲಿಯೇ ಉಳಿಸುತ್ತದೆ. ಕೆಳಮಟ್ಟದ ಬ್ಯಾಕೆಂಡ್ ಪ್ರಿಮಿಟಿವ್
ರೆಪೊಸಿಟರಿ ಅನುಷ್ಠಾನಗಳ ಒಳಗೆ ಇರಬಹುದು; ಅಪ್ಲಿಕೇಶನ್ ಎದುರಿಸುವ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ API ಆಗಿರಬಾರದು.

### ಒಂದು ಹಂತವನ್ನು ಮೌಲ್ಯೀಕರಿಸುವ ಮೊದಲು ಎಲ್ಲಾ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಅನ್ನು ಮರುಬರೆಯುವುದು

ತಿರಸ್ಕರಿಸಲಾಗಿದೆ. ಪ್ರಸ್ತುತ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಮೇಲ್ಮೈ ವಿಶಾಲವಾಗಿದ್ದು, ಫೈಲ್ ಲೈಫ್ಸೈಕಲ್, ರಿಕವರಿ, ಸರ್ಚ್
ಮತ್ತು ಕಾರ್ಯಾಚರಣಾ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಒಳಗೊಂಡಿದೆ. ವರ್ಟಿಕಲ್ ಹಂತಗಳು ಪರಿಶೀಲಿಸಬಹುದಾದ ನಡವಳಿಕೆ ಮತ್ತು ರೋಲ್ಬ್ಯಾಕ್ ಗಡಿಗಳನ್ನು ಒದಗಿಸುತ್ತವೆ.

### SQLite ಅನ್ನು ಡೀಫಾಲ್ಟ್ ಆಗಿ ಬದಲಾಯಿಸುವುದು

ತಿರಸ್ಕರಿಸಲಾಗಿದೆ. ಎಂಬೆಡೆಡ್ ಮತ್ತು ಡೆಸ್ಕ್ಟಾಪ್ ಡಿಪ್ಲಾಯ್ಮೆಂಟ್ಗಳು ಪ್ರಸ್ತುತ ಶೂನ್ಯ-ಸೇವೆಯ ಸ್ಟಾರ್ಟ್ಅಪ್ ಮಾದರಿಯನ್ನು ಅವಲಂಬಿಸಿವೆ.
ಬಾಹ್ಯ ಬ್ಯಾಕೆಂಡ್ ಆಯ್ಕೆಯಾಧಾರಿತವಾಗಿದೆ.

### Redis ಅನ್ನು ಶಾಶ್ವತ ಅಧಿಕೃತ ಮೂಲವಾಗಿ ಬಳಸುವುದು

ತಿರಸ್ಕರಿಸಲಾಗಿದೆ. Redis ಸ್ಪಷ್ಟವಾಗಿ ತಾತ್ಕಾಲಿಕವಾದ ಸಮನ್ವಯ, ಕ್ಯಾಶ್ ಅಥವಾ ಕೌಂಟರ್ಗಳಿಗೆ ಬೆಂಬಲ ನೀಡಬಹುದು; ಆದರೆ ಇಲ್ಲಿ
ವಿವರಿಸಿದ ಶಾಶ್ವತ ರೆಪೊಸಿಟರಿ ಒಪ್ಪಂದವನ್ನು ಅದು ಬದಲಿಸುವುದಿಲ್ಲ.

## ಪರಿಣಾಮಗಳು

### ಸಕಾರಾತ್ಮಕ

- ಬಿಸಿನೆಸ್ ಕೋಡ್ ಡೇಟಾಬೇಸ್ ಡಯಲೆಕ್ಟ್ನಿಂದ ಸ್ವತಂತ್ರವಾದ ಸ್ಥಿರ ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಗಡಿಯನ್ನು ಪಡೆಯುತ್ತದೆ.
- ಬಾಹ್ಯ ಬ್ಯಾಕೆಂಡ್ ಅಮೂರ್ತತೆಯನ್ನು ನಿರ್ಧರಿಸುವ ಮೊದಲು SQLite ನಡವಳಿಕೆಯನ್ನು ಪರೀಕ್ಷಿಸಲಾಗುತ್ತದೆ.
- PostgreSQL ಮತ್ತು MySQL ಡೊಮೇನ್ ಲಾಜಿಕ್ ಅನ್ನು ನಕಲಿಸುವ ಬದಲು ಒಪ್ಪಂದಗಳು ಮತ್ತು ಪರೀಕ್ಷೆಗಳನ್ನು ಹಂಚಿಕೊಳ್ಳುತ್ತವೆ.
- SQLite-ಗೆ ಮಾತ್ರ ಸೀಮಿತವಾದ ಸಾಮರ್ಥ್ಯಗಳು ಸೋರಿಕೆಯಾಗುವ ಹೊಂದಾಣಿಕೆ ಶಿಮ್ಗಳಾಗುವ ಬದಲು ಪ್ರಥಮ-ದರ್ಜೆಯವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.
- ಬಹು-ರೆಪ್ಲಿಕಾ ಮೈಗ್ರೇಶನ್ ಮತ್ತು ಟ್ರಾನ್ಸಾಕ್ಷನ್ ನಡವಳಿಕೆಯು ಸ್ಪಷ್ಟ ವಿನ್ಯಾಸ ಕಾಳಜಿಯಾಗುತ್ತದೆ.

### ವೆಚ್ಚಗಳು ಮತ್ತು ಅಪಾಯಗಳು

- ರೆಪೊಸಿಟರಿ ಬೇರ್ಪಡಿಸುವಿಕೆಗೆ ಹಂತ ಹಂತದ ಕಾಲ್-ಸೈಟ್ ಮೈಗ್ರೇಶನ್ ಅಗತ್ಯವಿದೆ.
- ಅಸಿಂಕ್ ಗಡಿಗಳು ಪ್ರಸ್ತುತ ಸಿಂಕ್ರೋನಸ್ ಸರ್ವಿಸ್ ಕೋಡ್ನಾದ್ಯಂತ ಹರಡಬಹುದು.
- ಕ್ರಾಸ್-ಬ್ಯಾಕೆಂಡ್ ಅರ್ಥವ್ಯವಸ್ಥೆಗೆ SQL ಸಿಂಟ್ಯಾಕ್ಸ್ ಹೊಂದಾಣಿಕೆಯನ್ನು ಮೀರಿದ ಅನುಸರಣೆ ಪರೀಕ್ಷೆಗಳು ಅಗತ್ಯವಿವೆ.
- ಬ್ಯಾಕಪ್, ಸರ್ಚ್, ವೆಕ್ಟರ್ ಸ್ಟೋರೇಜ್ ಮತ್ತು ನಿರ್ವಹಣೆ ಸಾಮರ್ಥ್ಯ-ನಿರ್ದಿಷ್ಟವಾಗಿಯೇ ಉಳಿಯುತ್ತವೆ.
- ಒಂದಕ್ಕಿಂತ ಹೆಚ್ಚು ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಅನುಷ್ಠಾನಗಳನ್ನು ಚಲಾಯಿಸುವುದರಿಂದ CI ಮತ್ತು ಕಾರ್ಯಾಚರಣಾ ಬೆಂಬಲದ ವೆಚ್ಚ ಹೆಚ್ಚುತ್ತದೆ.

## ಗುರಿಗಳಲ್ಲದವು

ಈ ADR ಇವುಗಳನ್ನು ಮಾಡುವುದಿಲ್ಲ:

- ಡೇಟಾಬೇಸ್ ಡಿಪೆಂಡೆನ್ಸಿ, ಎನ್ವಿರಾನ್ಮೆಂಟ್ ವೇರಿಯಬಲ್, ಸ್ಕೀಮಾ ಅಥವಾ ಮೈಗ್ರೇಶನ್ ಅನ್ನು ಸೇರಿಸುವುದಿಲ್ಲ;
- ಚಾಲ್ತಿಯಲ್ಲಿರುವ SQLite ಸಿಂಗಲ್ಟನ್ ಅಥವಾ ಡ್ರೈವರ್ ಕ್ಯಾಸ್ಕೇಡ್ ಅನ್ನು ಬದಲಿಸುವುದಿಲ್ಲ;
- ನಿರ್ದಿಷ್ಟ ರಿಲೀಸ್ನಲ್ಲಿ PostgreSQL ಅಥವಾ MySQL ಬೆಂಬಲವನ್ನು ಒದಗಿಸುವುದಾಗಿ ಭರವಸೆ ನೀಡುವುದಿಲ್ಲ;
- FTS5, `sqlite-vec`, ಬ್ಯಾಕಪ್ ಫೈಲ್ಗಳು ಅಥವಾ SQLite ನಿರ್ವಹಣೆಯನ್ನು ಪೋರ್ಟಬಲ್ ಮಾಡುವುದಿಲ್ಲ;
- ಹಂಚಿಕೆಯ ಸ್ಥಿತಿ ಮತ್ತು ಸಮನ್ವಯ ಪರೀಕ್ಷೆಗಳು ಲಭ್ಯವಾಗುವ ಮೊದಲು ಆಕ್ಟಿವ್-ಆಕ್ಟಿವ್ ಸಿದ್ಧತೆಯನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುವುದಿಲ್ಲ;
- `src/lib/db/` ಅನ್ನು ಒಂದೇ ಬಾರಿಗೆ ಮರುಬರೆಯುವುದನ್ನು ಅನುಮೋದಿಸುವುದಿಲ್ಲ.

## ನಿರ್ವಹಕರ ಅನುಮೋದನೆಗಾಗಿ ಮುಕ್ತ ಪ್ರಶ್ನೆಗಳು

1. ರೆಪೊಸಿಟರಿ ಮತ್ತು ಆಂತರಿಕ async backend ಗಡಿ ಆದ್ಯತೆಯ ನಿರ್ದೇಶನವೇ, ಅಥವಾ
   ಬಾಹ್ಯ ಸ್ಥಿರತೆ ಪ್ರತ್ಯೇಕ control-plane service ಹಿಂದೆ ಇರಬೇಕೇ?
2. SQLite ಅನುಸರಣೆಯ ನಂತರದ ಮೊದಲ ಬಾಹ್ಯ ಅನುಷ್ಠಾನವಾಗಿ PostgreSQL ಸ್ವೀಕಾರಾರ್ಹವೇ?
3. ಮೊದಲ bounded repository slice ಯಾವ domain ಆಗಿರಬೇಕು?
4. ಮೊದಲ multi-replica milestone ಗಾಗಿ ಯಾವ state ಹಂಚಿಕೆಯಾಗಬೇಕು ಮತ್ತು ಯಾವುದು node-local ಆಗಿಯೇ ಉಳಿಯಬೇಕು?
5. ಅಡಚಣೆಯಾದ ಅಥವಾ ಹಿಂದಕ್ಕೆ ತರಲಾದ repository migration ಗಾಗಿ ಯಾವ compatibility window ಅಗತ್ಯವಿದೆ?

ಈ ಪ್ರಶ್ನೆಗಳು ಇತ್ಯರ್ಥವಾಗುವವರೆಗೆ, ಈ ದಸ್ತಾವೇಜು ಒಂದು ಪ್ರಸ್ತಾವನೆಯಾಗಿರುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ runtime refactor ಅನ್ನು ಸೂಚಿಸುವುದಿಲ್ಲ.
