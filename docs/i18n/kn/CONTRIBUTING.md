## ಅಭಿವೃದ್ಧಿ ಸೆಟಪ್

### ಪೂರ್ವಾಪೇಕ್ಷಿತಗಳು

- **Node.js** `>=22.22.3 <23`, ಅಥವಾ `>=24.0.0 <27` (ಶಿಫಾರಸು: 24 LTS)
- **npm** 10+

> **npm v11+ ಬಳಕೆದಾರರು (Node 24+):** `npm install` ನಂತರ, ಸ್ಥಳೀಯ ಮಾಡ್ಯೂಲ್ಗಳನ್ನು ಸ್ಥಾಪಿಸಲಾಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ:
> `node -e "require('better-sqlite3')"`. ಅದು `MODULE_NOT_FOUND` ದೋಷದೊಂದಿಗೆ ವಿಫಲವಾದರೆ,
> `npm approve-scripts better-sqlite3 && npm install` ಅನ್ನು ಚಲಾಯಿಸಿ. ನೋಡಿ:
> [ದೋಷನಿವಾರಣೆ](docs/guides/TROUBLESHOOTING.md#npm-v11-better-sqlite3-not-installed-cannot-find-module).

- **Git**

### ಕ್ಲೋನ್ ಮಾಡಿ ಮತ್ತು ಸ್ಥಾಪಿಸಿ

```bash
git clone https://github.com/diegosouzapw/OmniRoute.git
cd OmniRoute
npm install
```

### ಪರಿಸರ ಚರಾಂಕಗಳು

```bash
# ಟೆಂಪ್ಲೇಟ್ನಿಂದ ನಿಮ್ಮ .env ಅನ್ನು ರಚಿಸಿ
cp .env.example .env

# ಅಗತ್ಯವಿರುವ ರಹಸ್ಯಗಳನ್ನು ರಚಿಸಿ
echo "JWT_SECRET=$(openssl rand -base64 48)" >> .env
echo "API_KEY_SECRET=$(openssl rand -hex 32)" >> .env
```

| ಚರಾಂಕ                  | ಅಭಿವೃದ್ಧಿಯ ಡೀಫಾಲ್ಟ್      | ವಿವರಣೆ                 |
| ---------------------- | ------------------------ | ---------------------- |
| `PORT`                 | `20128`                  | ಸರ್ವರ್ ಪೋರ್ಟ್          |
| `NEXT_PUBLIC_BASE_URL` | `http://localhost:20128` | ಫ್ರಂಟ್ಎಂಡ್ನ ಮೂಲ URL    |
| `JWT_SECRET`           | (ಮೇಲೆ ರಚಿಸಿ)             | JWT ಸಹಿ ಮಾಡುವ ರಹಸ್ಯ    |
| `INITIAL_PASSWORD`     | `CHANGEME`               | ಮೊದಲ ಲಾಗಿನ್ನ ಪಾಸ್ವರ್ಡ್ |
| `APP_LOG_LEVEL`        | `info`                   | ಲಾಗ್ ವಿವರದ ಮಟ್ಟ        |

### ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸೆಟ್ಟಿಂಗ್ಗಳು

ಪರಿಸರ ಚರಾಂಕಗಳ ಮೂಲಕವೂ ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ ವೈಶಿಷ್ಟ್ಯಗಳಿಗಾಗಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್ UI ಟಾಗಲ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

| ಸೆಟ್ಟಿಂಗ್ನ ಸ್ಥಳ        | ಟಾಗಲ್           | ವಿವರಣೆ                                    |
| ---------------------- | --------------- | ----------------------------------------- |
| ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸುಧಾರಿತ | ಡೀಬಗ್ ಮೋಡ್      | ಡೀಬಗ್ ವಿನಂತಿ ಲಾಗ್ಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ (UI) |
| ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸಾಮಾನ್ಯ | ಸೈಡ್ಬಾರ್ ಗೋಚರತೆ | ಸೈಡ್ಬಾರ್ ವಿಭಾಗಗಳನ್ನು ತೋರಿಸಿ/ಮರೆಮಾಡಿ       |

ಈ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಡೇಟಾಬೇಸ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಮರುಪ್ರಾರಂಭಗಳ ನಂತರವೂ ಉಳಿಯುತ್ತವೆ; ಹೊಂದಿಸಿದಾಗ ಅವು env var ಡೀಫಾಲ್ಟ್ಗಳನ್ನು ಅತಿಕ್ರಮಿಸುತ್ತವೆ.

### ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸುವುದು

```bash
# ಅಭಿವೃದ್ಧಿ ಮೋಡ್ (ಹಾಟ್ ರೀಲೋಡ್)
npm run dev

# ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್
npm run build    # next build → .build/next/ ನಂತರ assembleStandalone → dist/
npm run start

# ಕೊಡುಗೆದಾರರ ಬದಲಾವಣೆಗಳಿಗಾಗಿ ವೇಗವಾದ ಬ್ಯಾಕೆಂಡ್/API-ಮಾತ್ರ ಕಂಪೈಲ್
npm run build:contributor

# ಬಿಡುಗಡೆ ಬಿಲ್ಡ್ (ಸ್ವಚ್ಛ ಮರುನಿರ್ಮಾಣ + HEAD ಸೆಂಟಿನಲ್ — ನಿಯೋಜನೆಗೆ ಅಗತ್ಯ)
npm run build:release   # rm -rf .build dist && build + dist/BUILD_SHA ಅನ್ನು ಬರೆಯುತ್ತದೆ

# ಸಾಮಾನ್ಯ ಪೋರ್ಟ್ ಕಾನ್ಫಿಗರೇಶನ್
PORT=20128 NEXT_PUBLIC_BASE_URL=http://localhost:20128 npm run dev
```

ಕೊಡುಗೆದಾರರ ಬಿಲ್ಡ್ ಕಂಪೈಲ್-ಮಾತ್ರ ಮೌಲ್ಯೀಕರಣವನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ: ಇದು ಸ್ವತಂತ್ರ
ವಿತರಣೆಯನ್ನು ಜೋಡಿಸುವುದಿಲ್ಲ ಅಥವಾ ಐಚ್ಛಿಕ ಸ್ಥಳೀಯ ಪ್ಯಾಕೇಜಿಂಗ್ ಅಸೆಟ್ಗಳನ್ನು ನಿರ್ಮಿಸುವುದಿಲ್ಲ. ವಿತರಿಸಬಹುದಾದ ಬಂಡಲ್ ಅನ್ನು
ಮೌಲ್ಯೀಕರಿಸಬೇಕಾದಾಗ ಸಾಮಾನ್ಯ ಪ್ರೊಡಕ್ಷನ್ ಬಿಲ್ಡ್ ಅನ್ನು ಬಳಸಿ.

### ಬಿಲ್ಡ್ ಔಟ್ಪುಟ್ ವಿನ್ಯಾಸ

| ಡೈರೆಕ್ಟರಿ | ವಿಷಯಗಳು                                                                          | ಟ್ರ್ಯಾಕ್ ಮಾಡಲಾಗಿದೆಯೇ |
| --------- | -------------------------------------------------------------------------------- | -------------------- |
| `src/`    | ಅಪ್ಲಿಕೇಶನ್ ಮೂಲ (TypeScript / TSX)                                                | ಹೌದು                 |
| `.build/` | ಮಧ್ಯಂತರಗಳು — `next build` ಔಟ್ಪುಟ್ (gitignore ಮಾಡಲಾಗಿದೆ, `distDir = .build/next`) | ಇಲ್ಲ                 |
| `dist/`   | ವಿತರಿಸಬಹುದಾದ ಬಂಡಲ್ — `assembleStandalone` ಮೂಲಕ ಜೋಡಿಸಲಾಗಿದೆ (gitignore ಮಾಡಲಾಗಿದೆ) | ಇಲ್ಲ                 |

ಬಿಲ್ಡ್ ಪೈಪ್ಲೈನ್ ಒಂದೇ ಪಾಸ್ನಲ್ಲಿ ನಡೆಯುತ್ತದೆ:

```
npm run build
  └─ next build → .build/next/standalone  (Next.js ಔಟ್ಪುಟ್)
  └─ assembleStandalone()                 (ಸ್ವತಂತ್ರ + ಸ್ಥಿರ + ಸಾರ್ವಜನಿಕ + ಸ್ಥಳೀಯ ಅಸೆಟ್ಗಳನ್ನು ನಕಲಿಸುತ್ತದೆ)
       └─ ಔಟ್ಪುಟ್: dist/                 (server.js, .next/static/, public/, node_modules/)
```

`npm run build:release` ಹೆಚ್ಚುವರಿಯಾಗಿ ಮೊದಲು ಎರಡೂ ಡೈರೆಕ್ಟರಿಗಳನ್ನು ಸ್ವಚ್ಛಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ನಿಯೋಜನೆಯ ಸಮಗ್ರತಾ ಸೆಂಟಿನಲ್ ಆಗಿ
`dist/BUILD_SHA` (= `git rev-parse --short HEAD`) ಅನ್ನು ಬರೆಯುತ್ತದೆ.

`npm run build:contributor` ಬ್ಯಾಕೆಂಡ್-ಮಾತ್ರ ಬಿಲ್ಡ್ ಪ್ರೊಫೈಲ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಬಿಲ್ಡ್ ಮಾಡುವಾಗ ಇದು ತಾತ್ಕಾಲಿಕವಾಗಿ
ಡ್ಯಾಶ್ಬೋರ್ಡ್ UI ಫೈಲ್ಗಳಿಗೆ ಸ್ಟಬ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ, API ರೂಟ್ ಹ್ಯಾಂಡ್ಲರ್ಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಬಿಲ್ಡ್ ನಂತರ ಮೂಲ ಫೈಲ್ಗಳನ್ನು
ಮರುಸ್ಥಾಪಿಸುತ್ತದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ UI ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವ ಬದಲಾವಣೆಗಳಿಗಾಗಿ ಅಥವಾ ಸಂಪೂರ್ಣ ಬಿಡುಗಡೆ
ಮೌಲ್ಯೀಕರಣಕ್ಕಾಗಿ `npm run build` ಅನ್ನು ಬಳಸಿ; ಕೊಡುಗೆದಾರರ ಪ್ರೊಫೈಲ್ ಬಿಡುಗಡೆ ಬಿಲ್ಡ್ಗೆ ಪರ್ಯಾಯವಲ್ಲ.

> **VPS ನಿಯೋಜನೆ ಸೂಚನೆ:** ರಿಮೋಟ್ ಇಮೇಜ್ ಡೈರೆಕ್ಟರಿ `/usr/lib/node_modules/omniroute/app/`
> ಬದಲಾಗಿಲ್ಲ. ನಿಯೋಜನೆ ಸ್ಕಿಲ್ಗಳು `dist/` ನ ವಿಷಯಗಳನ್ನು ಅದಕ್ಕೆ rsync ಮಾಡುತ್ತವೆ.
> ರೆಪೊ ಒಳಗಿನ ಬಿಲ್ಡ್ ಔಟ್ಪುಟ್ ಮಾರ್ಗ ಮಾತ್ರ ಬದಲಾಗಿದೆ (`app/` → `dist/`).

ಡೀಫಾಲ್ಟ್ URLಗಳು:

- **ಡ್ಯಾಶ್ಬೋರ್ಡ್**: `http://localhost:20128/dashboard`
- **API**: `http://localhost:20128/v1`

## Git ಕಾರ್ಯಪ್ರವಾಹ

> ⚠️ **`main` ಗೆ ನೇರವಾಗಿ ಎಂದಿಗೂ commit ಮಾಡಬೇಡಿ.** ಯಾವಾಗಲೂ feature ಶಾಖೆಗಳನ್ನು ಬಳಸಿ.
>
> **PR ಆಧಾರ:** ಸಕ್ರಿಯ `release/vX.Y.Z` ಶಾಖೆಯನ್ನು ಗುರಿಯಾಗಿಸಿ (`main` ಅಲ್ಲ). ಪ್ರತಿ-ಶಾಖೆಗೆ-release + ರವಾನಿಸುವಾಗ-tag ಮಾದರಿಗಾಗಿ
> [`docs/ops/BRANCHING_MODEL.md`](docs/ops/BRANCHING_MODEL.md) ನೋಡಿ.

```bash
# ಸಕ್ರಿಯ release ತುದಿಯಿಂದ ಶಾಖೆಯನ್ನು ರಚಿಸಿ (ಉದಾಹರಣೆ: release/v3.8.49)
git fetch origin
git checkout -b feat/your-feature-name origin/release/v3.8.49
# ... ಬದಲಾವಣೆಗಳನ್ನು ಮಾಡಿ ...
git commit -m "feat: describe your change"
git push -u origin feat/your-feature-name
# base = release/v3.8.49 ಹೊಂದಿರುವ Pull Request ತೆರೆಯಿರಿ
```

### ಶಾಖೆಯ ಹೆಸರಿಡುವಿಕೆ

| Prefix      | ಉದ್ದೇಶ                           |
| ----------- | -------------------------------- |
| `feat/`     | ಹೊಸ ವೈಶಿಷ್ಟ್ಯಗಳು                 |
| `fix/`      | ದೋಷ ಸರಿಪಡಿಕೆಗಳು                  |
| `refactor/` | ಕೋಡ್ ಪುನರ್ರಚನೆ                   |
| `docs/`     | ದಸ್ತಾವೇಜೀಕರಣ ಬದಲಾವಣೆಗಳು          |
| `test/`     | ಪರೀಕ್ಷೆಗಳ ಸೇರ್ಪಡೆಗಳು/ಸರಿಪಡಿಕೆಗಳು |
| `chore/`    | ಪರಿಕರಗಳು, CI, ಅವಲಂಬನೆಗಳು         |

### Commit ಸಂದೇಶಗಳು

[Conventional Commits](https://www.conventionalcommits.org/) ಅನುಸರಿಸಿ:

```
feat: add circuit breaker for provider calls
fix: resolve JWT secret validation edge case
docs: update SECURITY.md with PII protection
test: add observability unit tests
refactor(db): consolidate rate limit tables
```

ವ್ಯಾಪ್ತಿಗಳು (v3.8): `db`, `sse`, `oauth`, `dashboard`, `api`, `cli`, `docker`, `ci`, `mcp`, `a2a`, `memory`, `skills`, `cloud-agent`, `guardrails`, `compression`, `auto-combo`, `resilience`, `providers`, `executors`, `translator`, `domain`, `authz`.

## ಪರೀಕ್ಷೆಗಳನ್ನು ಚಲಾಯಿಸುವುದು


### Pull Request ಅಗತ್ಯತೆಗಳು

PR ತೆರೆಯುವ ಮೊದಲು, ನೀವು ಬದಲಾಯಿಸಿದ ವಿಷಯಕ್ಕಾಗಿ ಕೇಂದ್ರೀಕೃತ loop ಅನ್ನು ಚಲಾಯಿಸಲು
[Contribution Golden Path](docs/ops/CONTRIBUTION_GOLDEN_PATH.md) ಬಳಸಿ. ಸಂಪೂರ್ಣ unit suite (4 CI shards), Vitest, **60%+** coverage gate ಮತ್ತು
production build ಇವು CI ಯ ಜವಾಬ್ದಾರಿ — ಅವುಗಳನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸುವುದರಿಂದ PR
ಪರಿಶೀಲನೆಗಳು ಈಗಾಗಲೇ ನಿಮಗೆ ನೀಡದ ಯಾವುದೇ ಹೆಚ್ಚುವರಿ ಸಂಕೇತ ದೊರೆಯುವುದಿಲ್ಲ ಮತ್ತು ಸಣ್ಣ ಯಂತ್ರಗಳಲ್ಲಿ ಅದು host ಅನ್ನು ಪೂರ್ತಿಯಾಗಿ ಬಳಸಬಹುದು (#8084):

- ನಿಮ್ಮ ಬದಲಾವಣೆಯನ್ನು ಒಳಗೊಳ್ಳುವ test files ಅನ್ನು ಚಲಾಯಿಸಿ: `node --import tsx/esm --test tests/unit/<file>.test.ts`
- `npm run lint` ಚಲಾಯಿಸಿ
- production code ಬದಲಾದಾಗಲೆಲ್ಲ ಅದೇ PR ನಲ್ಲಿ automated tests ಅನ್ನು ಸೇರಿಸಿ ಅಥವಾ ನವೀಕರಿಸಿ
- production code ಬದಲಾದಾಗ ಬದಲಾಯಿಸಿದ ಅಥವಾ ಸೇರಿಸಿದ test files ಅನ್ನು PR ವಿವರಣೆಯಲ್ಲಿ ಸೇರಿಸಿ
- project secrets ಅನ್ನು CI ನಲ್ಲಿ configure ಮಾಡಿದ್ದರೆ PR ನಲ್ಲಿನ SonarQube ಫಲಿತಾಂಶವನ್ನು ಪರಿಶೀಲಿಸಿ

### ದೋಷ ನಿರ್ವಹಣೆ / ಖಾಲಿ catch ಬ್ಲಾಕ್ಗಳು

ವಿವರಣೆಯಿಲ್ಲದೆ `catch` ಅನ್ನು ಎಂದಿಗೂ ಬಿಡಬೇಡಿ. ಅದನ್ನು ಎರಡು ವರ್ಗಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ ವರ್ಗೀಕರಿಸಿ (ಇದು
"SSE ಸ್ಟ್ರೀಮ್ಗಳಲ್ಲಿ ದೋಷಗಳನ್ನು ಎಂದಿಗೂ ಮೌನವಾಗಿ ನಿರ್ಲಕ್ಷಿಸಬೇಡಿ" ಎಂಬ ಕಟ್ಟುನಿಟ್ಟಿನ ನಿಯಮವನ್ನು ಕಾರ್ಯರೂಪಕ್ಕೆ
ತರುತ್ತದೆ):

- **ಉದ್ದೇಶಪೂರ್ವಕ (ನಮ್ಮದೇ ಆದ ಸಾಧ್ಯವಾದಷ್ಟು ಉತ್ತಮ ಕ್ಲೀನಪ್/ಟೆಲಿಮೆಟ್ರಿ)** — ಇಲ್ಲಿ ವೈಫಲ್ಯವು ನಿರೀಕ್ಷಿತ ಮತ್ತು
  ನಿರುಪದ್ರವವಾಗಿದೆ; ಒಂದು ಸಾಲಿನ ಕಾರಣದ ಕಾಮೆಂಟ್ ಸೇರಿಸಿ, ಲಾಗಿಂಗ್ ಬೇಡ (ಪ್ರತಿ ವಿನಂತಿಯಲ್ಲೂ ಲಾಗ್ ಮಾಡುವುದರಿಂದ
  ಉಂಟಾಗುವ ಅನಗತ್ಯ ಗದ್ದಲವನ್ನು ಈ ಸಂಪ್ರದಾಯ ತಪ್ಪಿಸುತ್ತದೆ).

  ```ts
  } catch {} // ಕ್ಲೈಂಟ್ ಸಂಪರ್ಕ ಕಡಿತಗೊಂಡ ನಂತರ ಈಗಾಗಲೇ ಮುಚ್ಚಿದ ಕಂಟ್ರೋಲರ್ ಅನ್ನು ಮುಚ್ಚುವುದು ನಿರೀಕ್ಷಿತವಾಗಿದೆ
  ```

- **ಲಾಗ್ ಮಾಡಬೇಕು (ಬಾಹ್ಯ/ಕಾಲರ್ ಒದಗಿಸಿದ ಕೋಡ್, ಅಥವಾ ನಿರ್ಲಕ್ಷಿಸುವುದರಿಂದ ನಿಯಂತ್ರಣ ಹರಿವು ಬದಲಾಗುತ್ತದೆ)** — ಸ್ಟ್ರೀಮ್ಗೆ
  ಅಡ್ಡಿಯಾಗದಂತೆ catch ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳಿ, ಆದರೆ ವೈಫಲ್ಯವನ್ನು ಪತ್ತೆಹಚ್ಚಲು ಸಾಧ್ಯವಾಗುವಂತೆ ಸಂದರ್ಭಸಹಿತ
  `console.debug`/`warn` ಅನ್ನು ಹೊರಸೂಸಿ.

  ```ts
  } catch (e) {
    console.debug("[STREAM] onFailure ಕಾಲ್ಬ್ಯಾಕ್ ದೋಷ:", e);
  }
  ```

ಅನ್ವಯಿಸಲಾದ ಉದಾಹರಣೆಗಳಿಗಾಗಿ `open-sse/utils/stream.ts` ಮತ್ತು `open-sse/utils/streamHandler.ts` ಅನ್ನು ನೋಡಿ.

## ಹೊಸ Provider ಸೇರಿಸುವುದು

### ಹಂತ 1: Provider Constants ನೋಂದಾಯಿಸಿ

`src/shared/constants/providers.ts` ಗೆ ಸೇರಿಸಿ — module load ಸಮಯದಲ್ಲಿ Zod ಮೂಲಕ ಮೌಲ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ.

### ಹಂತ 2: Executor ಸೇರಿಸಿ (ಕಸ್ಟಮ್ ಲಾಜಿಕ್ ಅಗತ್ಯವಿದ್ದರೆ)

base executor ಅನ್ನು ವಿಸ್ತರಿಸುವ executor ಅನ್ನು `open-sse/executors/your-provider.ts` ನಲ್ಲಿ ರಚಿಸಿ.

### ಹಂತ 3: Translator ಸೇರಿಸಿ (OpenAI ಅಲ್ಲದ ಸ್ವರೂಪವಾಗಿದ್ದರೆ)

request/response translators ಅನ್ನು `open-sse/translator/` ನಲ್ಲಿ ರಚಿಸಿ.

### ಹಂತ 4: OAuth Config ಸೇರಿಸಿ (OAuth ಆಧಾರಿತವಾಗಿದ್ದರೆ)

OAuth credentials ಅನ್ನು `src/lib/oauth/constants/oauth.ts` ನಲ್ಲಿ ಮತ್ತು service ಅನ್ನು `src/lib/oauth/services/` ನಲ್ಲಿ ಸೇರಿಸಿ.

upstream provider ತನ್ನ ಸಾರ್ವಜನಿಕ CLI / browser bundle ಒಳಗೆ ಸಾರ್ವಜನಿಕ OAuth client_id/secret ಅಥವಾ Firebase Web API key ಅನ್ನು ವಿತರಿಸಿದರೆ, ಅದನ್ನು string literal ಆಗಿ **ಎಂದಿಗೂ** embed ಮಾಡಬೇಡಿ. `open-sse/utils/publicCreds.ts` ನಲ್ಲಿರುವ `resolvePublicCred()` ಅನ್ನು ಬಳಸಿ ಮತ್ತು `EMBEDDED_DEFAULTS` ಗೆ masked byte entry ಅನ್ನು ಸೇರಿಸಿ. ಸಂಪೂರ್ಣ ಕಡ್ಡಾಯ workflow ಅನ್ನು [`docs/security/PUBLIC_CREDS.md`](./docs/security/PUBLIC_CREDS.md) ನಲ್ಲಿ ದಾಖಲಿಸಲಾಗಿದೆ.

handlers/executors ಒಳಗೆ, client ಅನ್ನು ತಲುಪುವ error messages ಗಳು `open-sse/utils/error.ts` ನಲ್ಲಿರುವ `buildErrorBody()` / `sanitizeErrorMessage()` ಮೂಲಕ ಹಾದುಹೋಗಬೇಕು — ಕಚ್ಚಾ `err.stack` ಅಥವಾ `err.message` ಅನ್ನು Response body ಯಲ್ಲಿ ಎಂದಿಗೂ ಇರಿಸಬೇಡಿ. [`docs/security/ERROR_SANITIZATION.md`](./docs/security/ERROR_SANITIZATION.md) ನೋಡಿ.

### ಹಂತ 5: Models ನೋಂದಾಯಿಸಿ

model definitions ಅನ್ನು `open-sse/config/providerRegistry.ts` ನಲ್ಲಿ ಸೇರಿಸಿ.

### ಹಂತ 6: Tests ಸೇರಿಸಿ

ಕನಿಷ್ಠ ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒಳಗೊಂಡ unit tests ಅನ್ನು `tests/unit/` ನಲ್ಲಿ ಬರೆಯಿರಿ:

- Provider ನೋಂದಣಿ
- Request/response ಅನುವಾದ
- Error ನಿರ್ವಹಣೆ

## ಬಿಡುಗಡೆ

ಬಿಡುಗಡೆಗಳನ್ನು `/generate-release` ವರ್ಕ್ಫ್ಲೋ ಮೂಲಕ ನಿರ್ವಹಿಸಲಾಗುತ್ತದೆ. ಹೊಸ GitHub Release ರಚಿಸಿದಾಗ, GitHub Actions ಮೂಲಕ ಪ್ಯಾಕೇಜ್ **ಸ್ವಯಂಚಾಲಿತವಾಗಿ npm ಗೆ ಪ್ರಕಟವಾಗುತ್ತದೆ**.

VPS ನಿಯೋಜನೆಗಳಿಗಾಗಿ, `npm run build` ಬದಲಿಗೆ `npm run build:release` ಬಳಸಿ — ಇದು ಸಂಪೂರ್ಣವಾಗಿ
ಮರುನಿರ್ಮಿಸುತ್ತದೆ, ಬಂಡಲ್ ಅನ್ನು `dist/` ಒಳಗೆ ಜೋಡಿಸುತ್ತದೆ ಮತ್ತು `dist/BUILD_SHA` ಸೆಂಟಿನಲ್ ಅನ್ನು ಬರೆಯುತ್ತದೆ.
ನಂತರ `dist/` ಅನ್ನು ದೂರಸ್ಥ `app/` ಡೈರೆಕ್ಟರಿಗೆ rsync ಮಾಡುವ `/deploy-vps-*-cc` ಸ್ಕಿಲ್ಗಳನ್ನು ಬಳಸಿ.
