> ორი ახალი `auto/*` იდენტიფიკატორი — `auto/subscription` და `auto/thrifty`. ორივე არჩევითად
> აქტიურდება მათი მოთხოვნით: მათ გავლით არაფერი მარშრუტდება, თუ გამომძახებელი იდენტიფიკატორს სახელით
> არ მოითხოვს, და არცერთი არსებული პული, სტრატეგია ან ნაგულისხმევი პარამეტრი არ იცვლება.

## რატომ არსებობს ეს

OmniRoute უკვე პასუხობს ღირებულებასთან დაკავშირებულ ორ კითხვას, თუმცა არცერთი მათგანი არ არის ის, რასაც ოპერატორების უმეტესობა სვამს.

| არსებული მექანიზმი                                       | რას პასუხობს                                    |
| -------------------------------------------------------- | ----------------------------------------------- |
| `hidePaidModels` (`autoCombo/paidModelFilter.ts`)        | "ეს მოდელი კატალოგში უფასოდ არის მონიშნული?"    |
| `freeAccessPolicy: "strict"` (`strictZeroCostFilter.ts`) | "შეიძლება ამ კავშირმა ოდესმე თანხა ჩამომაჭრას?" |
| `quotaPreflight` (`combo/quotaExhaustionCutoff.ts`)      | "ეს კავშირი თავის ზღვართან ახლოსაა?"            |
| `budgetCap` / `budgetFallback` (`autoCombo/engine.ts`)   | "შეზღუდე ხარჯვა, გადადი ყველაზე იაფ ვარიანტზე"  |

მხოლოდ უფასო ვარიანტებზე ორიენტირებული ყველა მექანიზმი **დახურული პრინციპით წყვეტს მუშაობას** — ამოწურული უფასო პული ცარიელ პულად რჩება და არასოდეს გადადის ფასიან ვარიანტზე — ხოლო ფასიან მხარეს მოქმედი ყველა მექანიზმი ტარიფული დონის მიმართ აგნოსტიკურია. არცერთი მათგანი არ პასუხობს კითხვას:

> "გამოიყენე კვოტა, რომელშიც უკვე ვიხდი. როცა ის ამოიწურება, ან შეჩერდი, ან თითო საფეხურით
> გადადი ყველაზე იაფ ფასიან ვარიანტებზე — და მისი განახლებისთანავე უკან დაბრუნდი."

## ბილინგი კავშირის თვისებაა და არა მოდელის

`classifyTier()` (`open-sse/services/tierResolver.ts`) ეფუძნება `(provider, model)` წყვილს და
კატალოგში მითითებული ფასების საფუძველზე აბრუნებს `free | cheap | premium` მნიშვნელობას. თუმცა მოთხოვნა დამატებით თანხას მოითხოვს თუ არა, დამოკიდებულია იმაზე, **რომელი კავშირი ამუშავებს მას**: ერთი და იგივე მოდელი Claude Code-ის
OAuth კავშირის მეშვეობით გეგმაშია ჩართული, ხოლო API გასაღების კავშირის მეშვეობით გამოყენებისას თითოეულ ტოკენზე თანხა ირიცხება.

`provider_connections.auth_type` არცერთი მიმართულებით არ არის საიმედო მაჩვენებელი — არსებობს გამოყენების მიხედვით დარიცხული OAuth
კავშირები და გეგმაში ჩართული API გასაღების კავშირები (Copilot-ის ადგილის ტოკენი გამოყენების მიხედვით დარიცხვადი API გასაღები არ არის). ამიტომ ბილინგის კლასი განისაზღვრება **კურირებული კატალოგიდან**,
`open-sse/config/connectionBillingCatalog.ts`, რომელიც ხელითაა შედგენილი თითოეული პროვაიდერის გამოქვეყნებული პირობების მიხედვით —
იმავე მიდგომით, რომელიც `FreeModelBudget.hardStopGuaranteed`-მა უკვე დაამკვიდრა უფასო მოდელებისთვის.

```ts
type ConnectionBillingClass = "subscription" | "metered" | "keyless" | "unknown";
type ConnectionOverageBehavior = "hard-stop" | "meters-to-paid" | "unknown";
```

განსაზღვრის რიგითობა (`autoCombo/connectionBilling.ts`): სინთეზური no-auth სენტინელი →
`keyless`; კატალოგის ჩანაწერი, რომელიც ემთხვევა როგორც პროვაიდერს, **ასევე** `authType`-ს; პროვაიდერის საერთო ჩანაწერი;
წინააღმდეგ შემთხვევაში — `unknown`. **არაკურირებული უფასოს არ ნიშნავს** — `unknown` ყველგან `metered`-ის
სახით გამოიყენება, ამიტომ ხვალ დამატებული პროვაიდერი თავიდან გამოწერის საფეხურის მიღმა აღმოჩნდება და მისი დამატება კურირების გზით მიზანმიმართულად უნდა მოხდეს.

## საფეხურების მოდელი

ესკალაციის თანმიმდევრობით ხუთი საფეხურია. ისინი მხოლოდ ფასით არ განსხვავდება — თითოეულს ამოწურვის **საკუთარი**
სიგნალი აქვს, რის გამოც ეს უბრალოდ დახარისხება არ არის.

| #   | საფეხური       | კუთვნილება                                                              | ამოწურულად ითვლება, როცა                   |
| --- | -------------- | ----------------------------------------------------------------------- | ------------------------------------------ |
| 0   | `subscription` | კურირებული `billing: "subscription"`                                    | კვოტის ფანჯარა ზღვარზეა ან მასზე დაბლაა    |
| 1   | `keyless`      | სინთეზური no-auth გზა                                                   | კავშირი დაყოვნებულია / ამომრთველი ჩართულია |
| 2   | `free`         | გამოყენების მიხედვით დარიცხვადი კავშირი, `classifyTier() === "free"`    | უფასო ლიმიტი ამოწურულია                    |
| 3   | `cheap`        | გამოყენების მიხედვით დარიცხვადი კავშირი, `classifyTier() === "cheap"`   | საფეხურის ბიუჯეტი დახარჯულია               |
| 4   | `premium`      | გამოყენების მიხედვით დარიცხვადი კავშირი, `classifyTier() === "premium"` | საფეხურის ბიუჯეტი დახარჯულია               |

0-2 საფეხურები **კვოტის** ამოწურვისას იწურება, რაც დაკვირვებადია და უკვე აღირიცხება. 3-4 საფეხურებს კვოტა არ აქვთ —
ფასიანი კავშირი მომსახურებას უსასრულოდ განაგრძობს — ამიტომ მათთვის ამოწურვის ერთადერთი გონივრული სიგნალი თითოეული საფეხურის
**ბიუჯეტია**. მის გარეშე, პირობას „გააკეთე ესკალაცია, როცა იაფი ვარიანტი ამოიწურება“ ამოქმედების სიგნალი არ აქვს.

## `auto/subscription` — გაურკვევლობისას აკრძალვა

პული = მხოლოდ საფეხური 0, შეზღუდული იმ კავშირებით, რომელთა ლიმიტის გადაჭარბება დოკუმენტირებულია როგორც `hard-stop` და თითოეული მათგანი რეალურ დროშია შემოწმებული, რომ კვოტის მარაგი აქვს. ყველაფერი ორაზროვანი გამოირიცხება: არაკურირებული პროვაიდერი, კვოტის შეუმოწმებელი მაჩვენებელი, მოძველებული მაჩვენებელი ან ისეთი გადაჭარბება, რომელიც ფასიან მოხმარებად აღირიცხება.

ცარიელი პული **განზრახ მიღებული** პასუხია და არა დეფექტი — გამომძახებლის არსებული ცარიელი პულის დამუშავების გზა მას მკაფიო შეცდომად გარდაქმნის და არა ჩუმ, ფასიან სათადარიგო ვარიანტად. ეს არის ამ id-ის სრული გარანტია.

`keyless` განზრახ **არ** აკმაყოფილებს კრიტერიუმებს: ეს დაჯგუფება ნიშნავს „გეგმას, რომლისთვისაც ვიხდი“, ამიტომ ავტორიზაციის არმომთხოვნი ბეკენდი მასში არ შედის. ამისთვის გამოიყენეთ `auto/thrifty` (ან `auto/best-free`).

### კავშირის უსაფრთხოება

კანდიდატი ყოველთვის ერთ კავშირთან არ არის მიბმული — ლოგიკური კანდიდატი შეიცავს `allowedConnectionIds` დაშვებულთა სიას, ხოლო რეალურად გამოსაყენებელი ანგარიში მოგვიანებით, გაგზავნისას, აირჩევა `open-sse/services/combo/autoStrategy.ts`-ის მიერ. ამიტომ ორივე დაჯგუფება **თითოეულ კავშირს ინდივიდუალურად** ამოწმებს და `allowedConnectionIds`-ს ზუსტად გადარჩენილ ქვეჯგუფამდე ამცირებს — არასოდეს სრულ თავდაპირველ სიამდე და არასოდეს თვითნებურად არჩეულ ერთ წევრამდე. ვინაიდან `autoStrategy.ts` ამ მასივს უკვე მკაცრ დაშვებულთა სიად აღასრულებს, მისი აქ გადაწერა უზრუნველყოფს, რომ „შემოწმებული“ და „რეალურად გამოყენებული“ სიმრავლეები კონსტრუქციულად იდენტური იყოს. ეს იგივე ინვარიანტი და იგივე მსჯელობაა, რაც
[STRICT_ZERO_COST](./STRICT_ZERO_COST.md)-ში.

## `auto/thrifty` — თითო ჯერზე ერთი საფეხურით ესკალაცია

პული = ყველა საფეხური, დალაგებული საფეხურის ინდექსის მიხედვით, ამოწურული კანდიდატების გამორიცხვით. `auto` ძრავა კვლავ აფასებს გადარჩენილი პულის **შიგნით**: კიბე წყვეტს, რომელი საფეხურები მონაწილეობს, ხოლო შეფასება — რომელი კანდიდატი იმარჯვებს მათ შიგნით. საფეხურის ფარგლებში რიგითობა სტაბილურია, ამიტომ ეს ზედდებული ფენა შემფასებლის საკუთარ რანჟირებას არასოდეს გადაალაგებს.

ეს არის დალაგებისა და დაშვების კონტროლის ზედდებული ფენა და **არა** ახალი დისპეტჩერი: `combo.ts`-ის სპეკულაციური ციკლი სამიზნეებს უკვე თანმიმდევრობით გადის და წარუმატებლობისას შემდეგზე გადადის, ამიტომ შესრულების დროს აღმოჩენილი ამოწურვა, რომელიც წინასწარმა შემოწმებამ ვერ დაიჭირა, იმავე მოთხოვნის ფარგლებში მაინც იწვევს შემდეგ საფეხურზე ესკალაციას.

თუ `auto/subscription` გაურკვევლობისას წვდომას **კეტავს**, `auto/thrifty` მას **ხსნის**: გეგმაში შემავალი კავშირი, რომლის კვოტის გამოყენებადი მაჩვენებელი არ არსებობს, მაინც პირველი გამოიცდება. მისი ცდა არაფერს ღირს და, თუ აღმოჩნდება, რომ ის ამოწურულია, შემდეგ ვარიანტზე გადასვლა მაინც მიაღწევს მომდევნო საფეხურს — მაშინ, როცა მისი გამოცდის უარყოფა ტელემეტრიის არარსებობის გამო მოთხოვნას ფასიან საფეხურზე გაგზავნიდა, რაც ზუსტად ის შედეგია, რომლის თავიდან ასაცილებლადაც ეს დაჯგუფება არსებობს.

## ჩამოყრის შემდეგ გეგმაზე დაბრუნება

სამი დამოუკიდებელი რამ უნდა ამოიწუროს, სანამ მარშრუტიზაცია საფეხურ 0-ზე დაბრუნდება. მხოლოდ ერთის გამოსწორება კიბეს ფასიან საფეხურებზე გაჭედილს ტოვებს გეგმის შევსებიდან დიდი ხნის შემდეგაც.

1. **კვოტის მდგომარეობის კეში** — `freeAccessQuota.ts` მონაცემებს თითოეული `(provider, connection)` წყვილისთვის 180s TTL-ით აკეშავს. დაკეშილი ჩანაწერი, რომლის საკუთარი `resetAt` უკვე გასულია, აღწერს ფანჯარას, რომელიც აღარ არსებობს, ამიტომ ახლა ის მოძველებულად ითვლება **ასაკის მიუხედავად** და განახლებას აიძულებს. ამის გარეშე გეგმა, რომელიც შუაღამით შეივსო, ამოწურულად იკითხება მანამ, სანამ TTL შემთხვევით არ ამოიწურება.
2. **კიბის საკუთარი მდგომარეობა** — დიზაინის მიხედვით, ასეთი მდგომარეობა არ არსებობს. საფეხურის შესაბამისობა ყოველი პულის აგებისას თავიდან გამოითვლება კვოტის მიმდინარე მდგომარეობიდან; არ არსებობს შენახული ჩანაწერი „ამჟამად საფეხურ 3-ზეა“, რომელმაც შეიძლება ჩამოყრას გადაასწროს და მარშრუტიზაცია გააჭედოს.
3. **კავშირის დაყოვნების პერიოდი** — ამოწურვის გამომწვევი 429 ექსპონენციალური დაყოვნების საფუძველზე აყენებს `rateLimitedUntil`-ს, რომელმაც გეგმის კავშირის შემთხვევაში შეიძლება რეალურ ჩამოყრის დროს გადააჭარბოს. `clampCooldownToReset()`
   (`subscriptionLadder.ts`) დაყოვნების პერიოდს ზემდგომი სერვისის საკუთარ ჩამოყრის მომენტამდე ამცირებს და მის გახანგრძლივებას ვერასოდეს მოახდენს. **ის რეალიზებული და გატესტილია, მაგრამ ჯერ არ არის მიერთებული**: კვოტის კეში `src/sse/services/auth.ts`-ში ბათილდება _მანამდე_, სანამ დაყოვნების ნებისმიერი პერიოდი ჩაიწერება, ამიტომ `resetAt` ამ ფუნქციაში უფრო ადრე უნდა დაფიქსირდეს — ეს მდგრადობის კრიტიკული გზის ცვლილებაა, რომელიც ცალკე განხილულ PR-ში უნდა შევიდეს. მანამდე ხელახალი დაშვება კავშირის დაყოვნების პერიოდის დასრულებას ელოდება (რომელიც უკვე უპირატესობას ანიჭებს ზემდგომი სერვისის `Retry-After` მითითებებს, როდესაც პროვაიდერი მათ აგზავნის).

### რყევის საწინააღმდეგო მექანიზმი

საფეხური, რომელიც ახლახან ჩამოიყარა, ხელახლა დაიშვება მხოლოდ მაშინ, როცა `reentryMinRemainingPercent`-ზე მეტია (ნაგულისხმევად 5), ხოლო უკვე გამოყენებაში მყოფ კავშირს მხოლოდ `exitCutoffPercent`-ზე მაღლა დარჩენა მოეთხოვება (ნაგულისხმევად 2, რაც ემთხვევა `quotaPreflight.defaultThresholdPercent`-ს). მათ შორის სხვაობა ჰისტერეზისის დიაპაზონია — მის გარეშე ზღვართან მერყევი კავშირი თანმიმდევრულ მოთხოვნებზე საფეხურებს შორის მონაცვლეობით გადაინაცვლებს.

## კონფიგურაცია

მხოლოდ პარამეტრების მორგება. განზრახ **არ არსებობს** `enabled` ალამი: გადამრთველი, რომელსაც მათი გამორთვა შეეძლებოდა,
`auto/subscription`-ს საშუალებას მისცემდა, შეუმჩნევლად მოემსახურებინა სრული პული — ფასიანი მოდელების ჩათვლით — ისეთი
სახელით, რომელიც საპირისპიროს გვპირდება.

```jsonc
{
  "subscriptionLadder": {
    "exitCutoffPercent": 2,
    "reentryMinRemainingPercent": 5,
    "rungBudgetUsd": { "cheap": 5.0, "premium": 0 }, // 0 საფეხურს სრულად თიშავს
  },
}
```

ბიუჯეტით შეზღუდვა უმოქმედოა, სანამ ხარჯების განმსაზღვრელი არ იქნება მიერთებული: როდესაც აღრიცხვა მიუწვდომელია, ფასიანი
საფეხური რიგში ხვდება, მაგრამ არასოდეს იზღუდება. v3.8.51-ის მდგომარეობით, `rungBudgetUsd` პარამეტრი სქემის მიერ მიიღება,
მაგრამ ჯერ არ არის აღსრულებული — იგი მიიჩნიეთ დარეზერვებულ კონფიგურაციად და არა ხარჯების აქტიურ ლიმიტად. საფეხურების დალაგება, კვოტაზე დაფუძნებული ამოწურვა და განულების შემდეგ ხელახალი ჩართვა მის გარეშეც
მუშაობს.

## კომპოზიცია

`subscription` და `thrifty` არის `AutoTier` მნიშვნელობები, ამიტომ ისინი ყველა კატეგორიასთან კომბინირდება:
`auto/coding:thrifty`, `auto/reasoning:subscription` და ა.შ. ორი ბრტყელი id
(`auto/subscription`, `auto/thrifty`) გამოქვეყნებულია `/v1/models`-სა და მართვის პანელში.

არცერთი id არ მიეკუთვნება ფასიან დონეს, ამიტომ `isPaidTierAutoId()` ორივესთვის აბრუნებს `false`-ს და
`auto/subscription` ნარჩუნდება `hidePaidModels`-ის გამოყენებისას.
