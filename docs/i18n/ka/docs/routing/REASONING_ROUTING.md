მსჯელობის მარშრუტიზაციის წესები აფართოებს მოდელებისა და კომბინაციების არსებულ მარშრუტიზაციას. როდესაც არცერთი აქტიური წესი არ ემთხვევა,
არსებული აზროვნების, სუფიქსის, ნაგულისხმევი კავშირისა და პროვაიდერის ტრანსლაციის ქცევა
უცვლელი რჩება.

## მართვა

წესების მართვა ხელმისაწვდომია **პარამეტრები → გლობალური მარშრუტიზაცია** განყოფილებაში. API-გასაღების რედაქტორი უზრუნველყოფს
მართვის იმავე ინტერფეისს, რომელიც გაფილტრულია არჩეული გასაღების მიხედვით.

მართვის API ხელმისაწვდომია შემდეგი მარშრუტებით:

- `GET` და `POST` მისამართზე `/api/settings/reasoning-routing-rules`
- `GET`, `PATCH` და `DELETE` მისამართზე `/api/settings/reasoning-routing-rules/[id]`
- `POST` მისამართზე `/api/settings/reasoning-routing-rules/simulate`

ყველა მარშრუტი იყენებს `requireManagementAuth`-ს. შემავალი მონაცემები მოწმდება
`src/shared/validation/schemas/reasoningRouting.ts`-ში არსებული სქემებით. სიმულატორი არასოდეს ახორციელებს აღმავალ გამოძახებას.

## წესის განსაზღვრა

ადრეული შეფასება ზუსტად ერთ წესს ირჩევს. მოქმედების არეები მოწმდება შემდეგი თანმიმდევრობით:

1. `apiKey`
2. `combo`
3. `model`
4. `global`

მოქმედების არეში ჯერ უფრო მაღალი `priority` იმარჯვებს, შემდეგ — მოდელის ზუსტი დამთხვევა glob-შაბლონთან შედარებით,
ხოლო შემდეგ გამოიყენება სტაბილური `createdAt`-ისა და `id`-ის თანმიმდევრობა. `requestTags` იკითხება მხოლოდ `metadata.tags`-იდან
და მხარს უჭერს `any` ან `all` დამთხვევას.

`connection` წესი ფასდება მხოლოდ მაშინ, როდესაც ადრეულ ეტაპზე არცერთმა წესმა არ გაიმარჯვა და კონკრეტული პროვაიდერის კავშირი
უკვე არჩეულია. მას მხოლოდ ძალისხმევისა და ბიუჯეტის შეცვლა შეუძლია.

## ძალისხმევა და ბიუჯეტი

`sourceEffort` იღებს მნიშვნელობებს `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max` და
`ultra`. `missing` ნიშნავს, რომ მოთხოვნა არ შეიცავს არც დისკრეტულ ძალისხმევას, არც აზროვნების გადამრთველს
და არც აზროვნების ბიუჯეტს. შესაბამისად, მხოლოდ ბიუჯეტის სიგნალს მხოლოდ `any` ემთხვევა.

`effortMode`-ს სამი ვარიანტი აქვს:

- `inherit` ინარჩუნებს კლიენტის ძალისხმევას და ამავე დროს მოდელის ან კომბინაციის შეცვლის შესაძლებლობას ტოვებს.
- `default` `targetEffort`-ს მხოლოდ მაშინ აყენებს, როდესაც მსჯელობის მკაფიო სიგნალი არ არსებობს.
- `force` დისკრეტულ ძალისხმევას `targetEffort`-ით ანაცვლებს.

ამისგან დამოუკიდებლად, `budgetAction` შეიძლება იყოს `preserve`, `remove` ან `set`. `force` მნიშვნელობით `none` შლის
ძალისხმევისა და ბიუჯეტის ყველა ცნობილ ველს. `none` და `set` ერთად არასწორი კომბინაციაა.

ცნობილ შეუთავსებელ მოდელებზე მიმართული მოთხოვნები აღმავალ გამოძახებამდე უარყოფილია. კომბინაციის
სამიზნეებიდან შეუთავსებელი ჩანაწერები იშლება; თუ არცერთი არ დარჩა, მოთხოვნა აბრუნებს სტატუსს `400`.
შესაძლებლობების უცნობი მონაცემები წარმოქმნის გაფრთხილებას და წესს აქტიურს ტოვებს.

## უსაფრთხოება და ტრანსპორტები

საწყისი და სამიზნე მოდელი, ან საწყისი და სამიზნე კომბინაცია, კვლავ ექვემდებარება API-გასაღების
არსებულ პოლიტიკას. მსჯელობის წესი არასოდეს აფართოებს მოდელის, კომბინაციის ან კვოტის ნებართვებს.

ძრავა ინტეგრირებულია Chat Completions-ში, Responses-ში, Anthropic Messages-ში და შიდა
Codex WebSocket გზაში. WebSocket გზა იღებს მხოლოდ Codex-ის სამიზნე მოდელებს; კომბინაციის სამიზნეები იქ ვერ
შესრულდება. წესის გადაწყვეტილება საიდუმლო მონაცემების გარეშე ინახება არსებულ მარშრუტის კვალში.

## მუდმივი შენახვა

მიგრაცია `src/lib/db/migrations/126_reasoning_routing_rules.sql` ქმნის
`reasoning_routing_rules` ცხრილს. წესები მიუთითებს შენახულ API-გასაღებებზე, კომბინაციებსა და პროვაიდერის კავშირებზე.
წაშლისას დაკავშირებული წესებიც იწმინდება. მონაცემთა ბაზაზე წვდომის შრე
`src/lib/db/reasoningRoutingRules.ts`-ში მოთხოვნის გზისთვის გაუქმებად ქეშს მართავს.

წესები შედის SQLite-ის სარეზერვო ასლებში, მონაცემთა ბაზის სრულ ექსპორტსა და კონფიგურაციის სინქრონიზაციის პაკეტში.
`reconcileReasoningRulesForSync` თიშავს იმპორტირებულ წესებს, რომლებსაც მითითებული ობიექტები აკლია, და ამ
კონფლიქტებს ანგარიშში ასახავს.
