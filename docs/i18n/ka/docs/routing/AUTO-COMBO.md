## კონფიგურაციის არმომთხოვნი ავტომარშრუტიზაცია (`auto/` პრეფიქსი)

> **სიახლე:** კომბინაციის შექმნა საჭირო აღარ არის. გამოიყენეთ `auto/` პრეფიქსი პირდაპირ ნებისმიერ კლიენტში.

### სწრაფი მაგალითები

| `auto/cheap`   | იაფი         | ხარჯებზე ოპტიმიზებული მარშრუტიზაცია (ჯერ ყველაზე დაბალი ღირებულება)                   |

### კატეგორიის × დონის კომპოზიცია (`auto/<category>:<tier>`)

OpenRouter-ის სტილის სუფიქსები ერთმანეთისგან გამოყოფს **რა სახის მარშრუტია საჭირო** (კატეგორია) და **როგორ უნდა მოხდეს მისი ოპტიმიზაცია** (დონე), ამიტომ მათი თავისუფლად კომბინირება შეგიძლიათ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **კატეგორიები** (შესაძლებლობის მიხედვით ფილტრავს კანდიდატთა ერთობლიობას): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` ტოვებს ხედვის შესაძლებლობის მქონე მოდელებს; `reasoning` ტოვებს მსჯელობის/აზროვნების მოდელებს.
- **დონეები** (ირჩევს შეფასების წონებს / ერთობლიობის ფილტრს): `fast` (სწრაფი მიწოდება) · `cheap` (`floor`-ის ფსევდონიმი, ხარჯების დამზოგავი) · `reliable` (წრედის ამომრთველის მდგომარეობა + დაყოვნების სტაბილურობა) · `free` / `pro` (ფილტრავს ერთობლიობას მოდელის დონის მიხედვით `classifyTier`-ის მეშვეობით — უფასო დონე პრემიუმის წინააღმდეგ).

| მაგალითი               | გარდაიქმნება შემდეგად                                                           |
| ---------------------- | ------------------------------------------------------------------------------- |
| `auto/coding:fast`     | კოდირების ერთობლიობა, დაბალი დაყოვნების წონები                                  |
| `auto/coding:cheap`    | კოდირების ერთობლიობა, ხარჯებზე ოპტიმიზებული (`auto/coding:floor`-ის ფსევდონიმი) |
| `auto/reasoning:pro`   | მხოლოდ მსჯელობის/აზროვნების მოდელები, პრემიუმ-დონე                              |
| `auto/vision`          | ხედვის შესაძლებლობის მქონე მოდელები (დონის გარეშე → დაბალანსებული წონები)       |
| `auto/multimodal:free` | მულტიმოდალური შესაძლებლობის მქონე მოდელები, მხოლოდ უფასო დონე                   |

ნებისმიერი მართებული `auto/<category>[:<tier>]` მოთხოვნისას დინამიკურად განისაზღვრება; საგულდაგულოდ შერჩეული ქვეჯგუფი წარმოდგენილია `/v1/models`-სა და მართვის პანელში (`AUTO_SUFFIX_VARIANTS` ფაილში `open-sse/services/autoCombo/builtinCatalog.ts`). ფილტრაცია **შეცდომისას ღიაა** — თუ შეზღუდვას არცერთი დაკავშირებული მოდელი არ შეესაბამება, გამოიყენება სრული ერთობლიობა, რათა მარშრუტიზაცია არასოდეს დაირღვეს. ძირითადი შემფასებელი (`combo.ts`) უცვლელია; კატეგორიის/დონის ფილტრი გამოიყენება `buildAutoCandidates`-ში.

> **მოდელების ცოცხალი ანალიტიკა:** ავტომარშრუტიზაციის შესაბამისობა ეფუძნება **Arena ELO**-ს ცოცხალ რეიტინგებს + **models.dev**-ის დონეების მონაცემებს, როდესაც `ARENA_ELO_SYNC_ENABLED` ალამი ჩართულია (წინააღმდეგ შემთხვევაში გამოიყენება შესაბამისობის სტატიკური რუკა).

**გამოყენების წესი:**

```bash
# ნებისმიერი IDE ან CLI ინსტრუმენტი, რომელსაც OpenAI-ის ფორმატის მხარდაჭერა აქვს
საბაზისო URL: http://localhost:20128/v1
API გასაღები:  <თქვენი-საბოლოო-წერტილის-გასაღები>

# თქვენს კოდში/კონფიგურაციაში მოდელს მიანიჭეთ:
model: "auto"                 # დაბალანსებული ნაგულისხმევი ვარიანტი
model: "auto/coding"          # საუკეთესოა კოდირების ამოცანებისთვის
model: "auto/fast"            # ხელმისაწვდომ ვარიანტებს შორის უსწრაფესი
model: "auto/cheap"           # ყველაზე იაფი თითო ტოკენზე
```

**რა ხდება:**

1. OmniRoute აღმოაჩენს `auto/` პრეფიქსს `src/sse/handlers/chat.ts`-ში
2. მონაცემთა ბაზიდან მოითხოვს ყველა **აქტიურ პროვაიდერის კავშირს**
3. ფილტრავს მათ და ტოვებს მოქმედი ავტორიზაციის მონაცემების მქონეებს (API გასაღები ან OAuth ტოკენი)
4. განსაზღვრავს მოდელს თითოეული კავშირისთვის (`connection.defaultModel` ან პროვაიდერის პირველი მოდელი)
5. მეხსიერებაში ქმნის **ვირტუალურ კომბინაციას** (DB-ში არ ინახება)
6. მარშრუტიზაციას ახორციელებს არჩეული ვარიანტის წონების პროფილის + LKGP სტრატეგიის გამოყენებით

**ძირითადი თვისებები:**

- ✅ **ყოველთვის ჩართული:** არ არის საჭირო გადამრთველი, კომბინაციის შექმნა ან კონფიგურაცია
- ✅ **დინამიკური:** ავტომატურად ასახავს ამჟამად დაკავშირებულ პროვაიდერებს
- ✅ **სესიის მიჯაჭვულობა:** LKGP უზრუნველყოფს ბოლო წარმატებული პროვაიდერის პრიორიტეტიზაციას
- ✅ **მრავალი ანგარიშის მხარდაჭერა:** თითოეული პროვაიდერის კავშირი ცალკე კანდიდატი ხდება
- ✅ **DB-ში ჩაწერის გარეშე:** ვირტუალური კომბინაცია მხოლოდ მოთხოვნის განმავლობაში არსებობს, შენახვის ნულოვანი დამატებითი დანახარჯით

### თითოეული გასაღებისთვის კანდიდატების მართვა (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = სუფიქსი `auto/`-ის შემდეგ, ან
ლიტერალი `auto` საბაზისო არხისთვის) არის **მხოლოდ წაკითხვის** საბოლოო წერტილი, რომელიც
ჩამოთვლის `auto/*` არხის კანდიდატთა მიმდინარე ერთობლიობას და ურთავს ცოცხალი ხელმისაწვდომობის
მონაცემებს არსებული მდგრადობის წაკითხვების ხელახლა გამოყენებით (არასოდეს — ამომრთველის დაუმუშავებელი `state`):

- პროვაიდერის წრედის ამომრთველი — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- კავშირის დაყოვნების პერიოდი — `rateLimitedUntil` / `testStatus` განსაზღვრულ
  `provider_connections` სტრიქონზე
- მოდელის ბლოკირება — `isModelLocked(provider, connectionId, model)`

თითოეული კანდიდატი ასევე შეიცავს ამ API გასაღების `excluded` ალამს. გამორიცხვები ინახება
ცალ-ცალკე თითოეული API გასაღებისთვის (`auto_candidate_overrides` ცხრილი, მიგრაცია `128`) — OmniRoute
ერთმომხმარებლიანია და არ აქვს `users` ცხრილი, ამიტომ `apiKeyId` არის ყველაზე ახლოს მდგომი რეალური
იდენტიფიკატორი თითოეული გამომძახებლისთვის — და ისინი კანდიდატთა ნაკადის საკვანძო წერტილში აღსრულდება,
`open-sse/services/autoCombo/virtualFactory.ts`-ში, სუფთა, ერთეულოვანი ტესტებით დაფარული
`filterExcludedCandidates()`-ის მეშვეობით (`open-sse/services/autoCombo/candidateOverrides.ts`).
ფილტრი არის **fail-open**: დაუყენებელი apiKeyId/channel ან DB ძიების შეცდომა ორივე შემთხვევაში
ნაკადს გაუფილტრავს ტოვებს, ამიტომ ოპერატორი, რომელსაც გადაფარვები არ აქვს კონფიგურირებული, ხედავს მარშრუტიზაციას,
რომელიც ბაიტების დონეზე ამ ფუნქციის დამატებამდე არსებულის იდენტურია.

**გადადებულია შემდგომ საკითხზე:** თითოეული კანდიდატის წონები + ცხადად განსაზღვრული მიმდევრობა (Level 3
— მიეწოდება არსებულ შეწონილ/პრიორიტეტულ სტრატეგიის გზებს) და კონკრეტული
`combo.ts` სტრატეგიის მიმაგრება თითოეულ `auto/*` არხზე (Level 4). იხილეთ #7819 გეგმა ღია
კითხვისთვის, უნდა დარჩეს თუ არა გადაფარვები თითოეული API გასაღებისთვის ცალ-ცალკე, თუ გახდეს გლობალური
ერთმომხმარებლიანი მოდელის გათვალისწინებით.

**შიდა მუშაობის პრინციპი:**

## კომბოების სახელები, რომლებიც რეალური მოდელის იდენტიფიკატორს ემთხვევა

კომბო, რომლის `name` ზუსტად ემთხვევა მოდელის მარტივ იდენტიფიკატორს (მაგ., კომბო სახელად
`gpt-5.5`), არის **განზრახ გათვალისწინებული და მხარდაჭერილი ნიმუში** და არა შეცდომა: ეს არის
თითოეული მოდელის იდენტიფიკატორისთვის პროვაიდერის სარეზერვო ვარიანტზე გადართვის მექანიზმი, რომელიც აღწერილია
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)-ში. რადგან კომბოს
განსაზღვრა მოწმდება მოდელის მარტივი იდენტიფიკატორის განსაზღვრამდე
(`getComboForModel()` ფაილში `src/sse/services/model.ts`), მარტივი
იდენტიფიკატორისთვის `gpt-5.5` გაგზავნილი მოთხოვნა მარშრუტდება კომბოს სამიზნეების გავლით (მაგ.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) და არა პირდაპირ
ერთი პროვაიდერისკენ — ეს ხელახლა იყენებს კომბოს გადაწერაზე წინ მდგომ პრიორიტეტს, რომელიც შეიქმნა
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227)-ისთვის და
რეგრესიულად მოწმდება `tests/unit/responses-combo-resolution-3227.test.ts`-ითა და
`tests/unit/combo-name-codex-responses-rewrite.test.ts`-ით.

კომბოს შექმნა ან მისთვის ისეთი სახელის დარქმევა, რომელიც რეალური მოდელის იდენტიფიკატორს ფარავს,
**არასდროს იქნება უარყოფილი** — ამის გაკეთება ამ დოკუმენტირებულ სამუშაო პროცესს დაარღვევდა. ამის ნაცვლად
(#8530), `POST /api/combos` და `PUT /api/combos/[id]` პასუხს ურთავს არაბლოკირებად
`warning` ველს, როდესაც (ახალი) სახელი რეალური
მოდელის იდენტიფიკატორის იდენტურია:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
```

(`src/instrumentation-node.ts`) ასევე ჟურნალში წერს ერთსტრიქონიან `[STARTUP]` გაფრთხილებას,
რომელშიც ჩამოთვლილია ყველა არსებული კომბო, რომელიც მოდელის იდენტიფიკატორს ფარავს, რათა ოპერატორებმა,
რომლებიც ამას შემთხვევით წააწყდნენ (და არა განზრახ, როგორც #6940-შია აღწერილი), შესაბამისი სიგნალი მიიღონ.
აღმომჩენი დამხმარე ფუნქცია განთავსებულია `src/lib/combos/modelNameCollision.ts`-ში.

## კლიენტიდან მორგებული კომბოს გამოძახება

შენახული კომბოები (პარამეტრები → კომბოები) გამოიყენება მხოლოდ მაშინ, როდესაც კლიენტი `model` ველში აგზავნის კომბოს **ზუსტ სახელს** — კომბოს სახელის მიახლოებითი ან ნაწილობრივი დამთხვევა არ ხდება და `auto/` პრეფიქსიც არ გამოიყენება. განსაზღვრის თანმიმდევრობა (`getComboForModel()` ფაილში `src/sse/services/model.ts`):

1. კომბოს სახელის ზუსტი დამთხვევა (`model: "my-combo"`),
2. `combo/<name>` პრეფიქსი (`model: "combo/my-combo"`),
3. model→combo glob შესაბამისობები (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ორი გავრცელებული შეცდომა:

- **`auto` თქვენს კომბოებს არ იყენებს.** `auto`/`auto/*` ქმნის საკუთარ, ნულოვანი კონფიგურაციის მქონე კანდიდატთა ერთობლიობას და შენახულ კომბოებს მხოლოდ მაშინ ამოწმებს, თუ რომელიმე კომბოს პირდაპირ `auto` ჰქვია (არ არის რეკომენდებული). კომბოს გავლით მარშრუტიზაციისთვის გაგზავნეთ მისი ზუსტი სახელი — არა `auto`.
- **`openrouter/auto` არის OpenRouter-ის რეალური ფასიანი პროდუქტი** („ავტომატურად საუკეთესო ხელმისაწვდომი“) და არა OmniRoute-ის ფსევდონიმი. ის OpenRouter-ის რეესტრის ერთადერთი სტატიკური მოდელის ჩანაწერია (`open-sse/config/providers/registry/openrouter/index.ts`) და მისი საფასური ცალკე ირიცხება. `auto` ერთობლიობებიდან მის გამოსარიცხად გამოიყენეთ პარამეტრები → მარშრუტიზაცია → ფასიანი მოდელების დამალვა.

თავდაპირველი გაუგებრობის შესახებ, რომელსაც ეს დოკუმენტაცია განმარტავს, იხილეთ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) და [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111).

## როგორ მუშაობს (შენახული Auto-Combo-ები)

Auto-Combo Engine თითოეული მოთხოვნისთვის დინამიკურად ირჩევს საუკეთესო პროვაიდერს/მოდელს **16-ფაქტორიანი შეფასების ფუნქციის** გამოყენებით (განსაზღვრულია `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`-ში). ნაგულისხმევი წონების ჯამია `1.0`; მორგებული წონების ხელახალი ნორმალიზება ხდება `normalizeScoringWeights()`-ის მიერ. თექვსმეტი ფაქტორიდან ორს — `cacheAffinity`-სა და `resetWindowAffinity`-ს — ნაგულისხმევად აქვს წონა `0`; `reliability`-ს `DEFAULT_WEIGHTS`-ში აქვს `0`, მაგრამ ზოგად პაკეტებში — `0.03`, ხოლო `reliability-first`-ში — `0.04`; `quality`-ს კი პაკეტებში აქვს `0.02` (`quality-first`-ში — `0.03`): ისინი მაინც გამოითვლება თითოეული კანდიდატისთვის, ხოლო `cacheAffinity` შეფასების მიღმა მართავს მოთხოვნის ქეშის დუბლირების აღმოფხვრას, ამიტომ ნულოვანი ნაგულისხმევი წონის მქონე ფაქტორები ნაგულისხმევად უბრალოდ არ მონაწილეობენ შეფასებაში, პაკეტებში კი მონაწილეობენ.

### `weighted`-ის სემანტიკა

`weighted` არის **თითოეულ მოთხოვნაზე პროპორციული შემთხვევითი არჩევა**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`) და არა გამათანაბრებელი:

- თითოეული მოთხოვნა ირჩევს **ერთ** ეტაპს `weight / totalWeight` ალბათობით; დარჩენილი ეტაპები
  ამ მოთხოვნის სარეზერვო ჯაჭვისთვის წონის კლებადობის მიხედვით ლაგდება.
- ეტაპი, რომლის წონაა `0` (ან წონა არ აქვს), **არასოდეს აირჩევა**, სანამ რომელიმე სხვა ეტაპის
  წონა > 0-ია — ის შეიძლება მხოლოდ სარეზერვო ვარიანტად იქნეს გამოყენებული არჩეული ეტაპის წარუმატებლობის შემდეგ. არჩევა თანაბარი ალბათობის ხდება მხოლოდ მაშინ, როდესაც **ყველა**
  წონა 0-ის ტოლია.
- ეტაპები, რომელთა ყველა სამიზნეც მიუწვდომელია — პროვაიდერის ამომრთველის მდგომარეობაა `OPEN`, კავშირი
  დაყოვნების რეჟიმშია, ან მოდელი დაბლოკილია — არჩევამდე გამოირიცხება
  (`open-sse/services/combo/targetResolution.ts`), ამიტომ ერთადერთმა გამართულმა ეტაპმა შეიძლება დროებით
  ყველა მოთხოვნა მიიღოს.
- `stickyWeightedLimit` (კომბინაციის კონფიგურაცია, ნაგულისხმევი მნიშვნელობა `1` = გამორთულია) არჩეულ ეტაპს აფიქსირებს ამდენი
  თანმიმდევრული წარმატების განმავლობაში, ხელახლა არჩევამდე.

მკაცრი მონაცვლეობისთვის გამოიყენეთ `round-robin`; `weighted`-ში თანაბარი წონები იძლევა სტატისტიკურ და არა
მკაცრ ბალანსს.

## შერწყმის სტრატეგია

`fusion` ერთადერთი სტრატეგიაა, რომელიც ერთ სამიზნეს **არ** ირჩევს. ის მოთხოვნას
**პანელის ყველა მოდელს პარალელურად** უგზავნის, შემდეგ კი კონფიგურირებადი **მსაჯი მოდელი**
პანელის ყველა პასუხიდან ერთ საბოლოო პასუხს აყალიბებს. გადმოტანილია საწყისი `decolua/9router`-იდან
(OpenRouter-ის Fusion დიზაინი); იმპლემენტაცია მდებარეობს `open-sse/services/fusion.ts`-ში.

როგორ მუშაობს:

0. **ინსტრუმენტების მქონე მოთხოვნის გვერდის ავლა** — მოთხოვნა, რომელიც შეიცავს არაცარიელ `tools` მასივს და
   რომლის `tool_choice` აშკარად არ არის `"none"`, პანელს მთლიანად გამოტოვებს: ის პირდაპირ
   ერთ მოდელთან (კონფიგურირებულ მსაჯთან ან `panel[0]`-თან) მარშრუტდება, ხოლო `tools`/`tool_choice`
   უცვლელად გადაეცემა. პანელის წევრებს ინსტრუმენტებზე წვდომა არ აქვთ, ხოლო მსაჯის
   სინთეზის დირექტივა ხელს უშლის ინსტრუმენტის გამოძახების გენერირებას, ამიტომ აგენტური/ინსტრუმენტების გამომძახებელი კლიენტები
   სინთეზირებული პროზის ნაცვლად ინსტრუმენტის გამოძახების რეალურ გადაწყვეტილებას იღებენ (#6771).
1. **პარალელური განაწილება** (მხოლოდ ინსტრუმენტების არმქონე მოთხოვნებისთვის) — მოთხოვნა ერთდროულად ეგზავნება პანელის
   ყველა მოდელს, იძულებით არანაკადურ რეჟიმში და ინსტრუმენტების გარეშე (მსაჯს სინთეზისთვის
   სრული ტექსტი სჭირდება).
2. **კვორუმისა და დამატებითი დროის გათვალისწინებით შეგროვება** — როგორც კი `minPanel` რაოდენობის პასუხი მოვა, დაგვიანებული
   პასუხებისთვის მოკლე დამატებითი დროის ტაიმერი იწყება, რის შემდეგაც შერწყმა შეგროვებული მასალით გრძელდება.
   ეს ზღუდავს ყველაზე ნელი მოდელის გავლენას შესრულების მთლიან დროზე, ხოლო ზედა ზღვარს მკაცრი დროის ლიმიტი ადგენს.
3. **მსაჯის სინთეზი** — პანელის პასუხები ანონიმიზებულია (`Source 1`, `Source 2`, … — რათა
   მსაჯმა მოდელის ბრენდის ნაცვლად შინაარსი შეაფასოს) და გადაეცემა მსაჯს, რომელიც აანალიზებს
   კონსენსუსს / წინააღმდეგობებს / ნაწილობრივ დაფარვას / უნიკალურ მიგნებებს / გამორჩენილ ასპექტებს, შემდეგ კი
   წერს **ერთ** ავტორიტეტულ პასუხს. მსაჯის გამოძახება ინარჩუნებს კლიენტის თავდაპირველ
   `stream` პარამეტრსა და ინსტრუმენტებს, ამიტომ ნაკადური რეჟიმი და შემდგომი ინსტრუმენტების გამოყენება კვლავ მუშაობს.
4. **თანდათანობითი დეგრადაცია** — პანელის 0 პასუხი → `503`; ზუსტად 1 გადარჩენილი პასუხი → ეს პასუხი
   პირდაპირ ბრუნდება (შესარწყმელი არაფერია); ერთმოდელიანი პანელი პირდაპირ პასუხობს.

პანელის წევრი ასევე შეიძლება იყოს `combo-ref` ნაბიჯი (`{kind: "combo-ref", comboName: "..."}`), რომელიც
სხვა კომბინაციას მიუთითებს — ის გადაიჭრება, როგორც **პანელის ერთი შავი ყუთის ტიპის ხმა** (სრული რეკურსიული გადამისამართება
მითითებულ კომბინაციაში და არა ამ კომბინაციის საკუთარ სამიზნეებზე პარალელური განაწილება), სიღრმისა და ციკლის იმავე
დაცვით, რომელსაც `combo-ref`-ის მომხმარებელი ყველა სხვა სტრატეგია უკვე იყენებს (#6764).

### კონფიგურაცია

კონფიგურირდება კომბინაციის `config` ბლობში (სქემის მიგრაცია საჭირო არ არის — ის არსებულ
`combos` ცხრილს ხელახლა იყენებს):

| ველი                                     | ტიპი     | ნაგულისხმევი მნიშვნელობა | დანიშნულება                                                                                             |
| :--------------------------------------- | :------- | :----------------------- | :------------------------------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | პანელის პირველი მოდელი   | მოდელი, რომელიც საბოლოო პასუხს ასინთეზებს                                                               |
| `config.fusionTuning.minPanel`           | `number` | `2`                      | დამატებითი დროის ტაიმერის დაწყებამდე საჭირო წარმატებული პასუხები (იზღუდება `[2, panelSize]` დიაპაზონით) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`                   | რამდენ ხანს უნდა დაელოდოს დაგვიანებულ პასუხებს კვორუმის მიღწევის შემდეგ                                 |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`                  | აბსოლუტური ზღვარი, რათა ერთმა გაჭედილმა მოდელმა მოთხოვნა ვერ შეაყოვნოს                                  |

ნაგულისხმევი მნიშვნელობები განსაზღვრულია `FUSION_DEFAULTS`-ში (`open-sse/services/fusion.ts`).

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \

  -d '{

    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },

```

## ვირტუალური Auto-Combo ქარხანა

Auto Combo ძრავას წინასწარ განსაზღვრული კომბოები არ სჭირდება. ამის ნაცვლად, `open-sse/services/autoCombo/virtualFactory.ts` კანდიდატებს დინამიკურად ქმნის:

1. იღებს `getProviderConnections({ isActive: true })`-ს (ყველა ჩართული კავშირი)
2. ფილტრავს და ტოვებს მოქმედი ავტორიზაციის მონაცემების მქონე კავშირებს (API გასაღები ან `hasUsableOAuthToken()`-ის მეშვეობით შემოწმებული, ვადაგაუსვლელი OAuth ტოკენი)
3. მოდელების ხელმისაწვდომობისა და ფასების დასადგენად ადარებს `getProviderRegistry()`-ს
4. თითოეული `(provider, model, connection)` სამეულისთვის ქმნის `VirtualAutoComboCandidate`-ს
5. მოთხოვნის გადაგზავნის სამიზნედ ირჩევს `connection.defaultModel`-ს (ან რეესტრის პირველ მოდელს)
6. თითოეულ კანდიდატს აფასებს 16-ფაქტორიანი `scorePool()`-ისა და ვარიანტის წონების ნაკრების გამოყენებით
7. `handleComboChat()`-ისთვის აბრუნებს მეხსიერებაში შექმნილ საბოლოო `AutoComboConfig`-ს — ის არასოდეს ინახება DB-ში

ეს ნიშნავს, რომ **ახალი პროვაიდერის დამატება, რომელზეც `auto/*` ჩართულია, კანდიდატების ერთობლიობას ავტომატურად აფართოებს** — კომბოს ხელით რედაქტირება საჭირო არ არის. ვირტუალური კომბო ყოველი მოთხოვნისთვის თავიდან იქმნება, ამიტომ ახლად დამატებული ან ახლახან გამართულად ამუშავებული კავშირები დაუყოვნებლივ გამოიყენება.

## თვითაღდგენა

- **დროებითი გამორიცხვა**: ქულა < 0.2 → გამოირიცხება 5 წუთით (პროგრესული დაყოვნება, მაქს. 30 წუთი)
- **Circuit breaker-ის მდგომარეობის გათვალისწინება**: OPEN → ავტომატურად გამოირიცხება; HALF_OPEN → საცდელი მოთხოვნები
- **ინციდენტის რეჟიმი**: >50% OPEN → კვლევის გამორთვა, სტაბილურობის მაქსიმიზაცია
- **აღდგენა მოცდის პერიოდის შემდეგ**: გამორიცხვის დასრულების შემდეგ პირველი მოთხოვნა არის შემცირებული timeout-ის მქონე „საცდელი“ მოთხოვნა

## Bandit კვლევა

მოთხოვნების 5% (კონფიგურირებადია) კვლევის მიზნით შემთხვევით პროვაიდერებთან იგზავნება. ინციდენტის რეჟიმში გამორთულია.

## API

**ცალკე `POST /api/combos/auto` endpoint არ არსებობს** — Auto-Combo გამოიყენება ორი გზით:

1. **კონფიგურაციის გარეშე (რეკომენდებული):** გაგზავნეთ ჩატის დასრულების ნებისმიერი მოთხოვნა `model: "auto"`-ს ან `model: "auto/<variant>"`-ის მითითებით. ვირტუალური ქარხანა კომბოს თითოეული მოთხოვნისთვის ქმნის — შენახვა და API გამოძახებები საჭირო არ არის.

2. **შენახული კომბო `strategy: "auto"`-ით:** შექმენით ჩვეულებრივი კომბო `POST /api/combos`-ის მეშვეობით და დააყენეთ `strategy: "auto"`, ასევე `config.auto.weights` / `config.auto.candidatePool`. გამოიყენება იგივე შეფასების ძრავა; კომბო ინახება `combos`-ში და მისი ID-ით ხელახლა გამოყენება შესაძლებელია.

აღმოჩენისთვის `GET /api/combos/auto` ჩამოთვლის ყველა ვარიანტს მის დამუშავებულ კანდიდატთა ერთობლიობასთან ერთად, ასევე `context_length` / `max_output_tokens`-ს — კანდიდატთა ერთობლიობის ფანჯრებს შორის მაქსიმალურ მნიშვნელობას. კლიენტებმა (მაგ., opencode plugin-მა) `0`-ის ნაცვლად ეს მნიშვნელობები უნდა გამოაცხადონ: ნულოვანი კონტექსტი opencode-ის ავტომატურ შეკუმშვას მთლიანად თიშავს, რის გამოც სესიები იზრდება მანამ, სანამ gateway-ის ისტორიის გასუფთავება კონტექსტს არ გაანადგურებს. MAX-ის გამოცხადება უსაფრთხოა, რადგან auto-combo-ს კონტექსტის წინასწარი ფილტრი ზედმეტად დიდ მოთხოვნებს დიდი ფანჯრის მქონე კანდიდატებთან მიმართავს.

```bash
# გამოყენება კონფიგურაციის გარეშე (კომბოს შექმნის გარეშე)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# შენახული ავტო-კომბო ჩვეულებრივი combos endpoint-ის მეშვეობით
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ავტო-როუტერის სტრატეგიები

შენახულ `strategy: "auto"` კომბოებს შეუძლიათ `config.routerStrategy` (ან ძველი
`config.auto.routerStrategy`) დააყენონ ერთ-ერთ შემდეგ მნიშვნელობაზე:

- `rules` — ნაგულისხმევი შეწონილი შეფასება
- `score` — ირჩევს ყველაზე მაღალი კონფიგურირებული შეწონილი ქულის მქონე ვარიანტს. ზუსტი თანაბრობის შემთხვევაში შენარჩუნდება კანდიდატების კონფიგურირებული
  თანმიმდევრობა; არსებული `explorationRate` ნიმუშს სრული რანჟირებული ერთობლიობიდან იღებს.
- `cost` / `eco` — ყველაზე იაფი გამართული პროვაიდერი
- `latency` / `fast` — ყველაზე დაბალი p95 დაყოვნება საიმედოობის ჯარიმის გათვალისწინებით
- `sla-aware` / `sla` — უპირატესობა ენიჭება კანდიდატებს, რომლებიც აკმაყოფილებენ p95 დაყოვნების, შეცდომების სიხშირისა და არასავალდებულო
  ღირებულების SLO-ებს
- `lkgp` — პირველ რიგში ბოლო ცნობილი გამართული პროვაიდერი

### როუტერის სტრატეგიები დეტალურად

Auto-combo ძრავა გთავაზობთ 6 ჩანაცვლებად **RouterStrategy** იმპლემენტაციას, რომელთა
შეცვლაც შეგიძლიათ `config.routerStrategy`-ის (ან ძველი `config.auto.routerStrategy`-ის) მეშვეობით.
თითოეული სტრატეგია კანდიდატთა ერთობლიობიდან ერთ პროვაიდერს ირჩევს მოცემული `RoutingContext`-ის
(დავალების ტიპი, ხელსაწყოს/ხედვის მინიშნებები, ტოკენების სავარაუდო რაოდენობა, არასავალდებულო SLA პოლიტიკა, არასავალდებულო
ბოლო ცნობილი გამართული პროვაიდერი) საფუძველზე.

#### 1. `rules` (ნაგულისხმევი) — 16-ფაქტორიანი შეწონილი შეფასება

არსებულ შეფასების ძრავას გარსად ეხვევა. ფილტრავს `OPEN` მდგომარეობაში მყოფ circuit-breaker
კანდიდატებს, შემდეგ კი `scorePool()`-ს უშვებს მიმდინარე დავალების ტიპითა და `getTaskFitness()`-ით,
და ირჩევს ყველაზე მაღალი ქულის მქონე პროვაიდერს.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**როდის გამოიყენოთ**: ნაგულისხმევად. გამოიყენეთ, როდესაც ყველა სიგნალს შორის დაბალანსებული კომპრომისი გსურთ.

**ალიასი**: `rules` (ალიასი არ აქვს)

---

#### 2. `cost` / `eco` — ყველაზე იაფი გამართული პროვაიდერი

კანდიდატთა ერთობლიობას `costPer1MTokens`-ის მიხედვით (ზრდადობით) ახარისხებს და ყველაზე იაფს ირჩევს.
ჯერ `OPEN` კანდიდატებს ფილტრავს.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**როდის გამოიყენოთ**: ხარჯებზე ორიენტირებული დატვირთვები, პაკეტური დამუშავება ან ფონური დავალებები.

**ალიასები**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ყველაზე დაბალი p95 დაყოვნება საიმედოობის ჯარიმის გათვალისწინებით

ალაგებს `p95LatencyMs + (errorRate * 1000)` მნიშვნელობის მიხედვით. შეცდომების სიხშირის ჯარიმა უზრუნველყოფს,
რომ არასაიმედო პროვაიდერები უფრო დაბალ პოზიციაზე მოხვდნენ, მაშინაც კი, თუ მათი ნომინალური დაყოვნება მცირეა.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**როდის გამოიყენოთ**: დაყოვნების მიმართ მგრძნობიარე სამუშაო დატვირთვებისთვის, როგორიცაა რეალურ დროში ჩატი, ავტომატური შევსება ან
ინტერაქტიული პროგრამირების ასისტენტები.

**ალტერნატიული სახელები**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — დაყოვნების/შეცდომების/ღირებულების SLO-სთან შესაბამისობა

თითოეულ კანდიდატს ანიჭებს ქულას იმის მიხედვით, თუ რამდენად კარგად აკმაყოფილებს ის კონფიგურირებულ SLO პოლიტიკას:

| ფაქტორი           | წონა | ფორმულა                                                               |
| ----------------- | ---- | --------------------------------------------------------------------- |
| დაყოვნების ქულა   | 35%  | `threshold / max(value, ε)`                                           |
| შეცდომების ქულა   | 35%  | `threshold / max(value, ε)`                                           |
| სიჯანსაღის ქულა   | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)                     |
| ღირებულების ქულა  | 10%  | `threshold / max(value, ε)` ან შებრუნებული ნორმალიზებული              |
| სტაბილურობის ქულა | 5%   | დაყოვნების სტანდარტული გადახრის შებრუნებული ნორმალიზებული მნიშვნელობა |

როდესაც `hardConstraints: true`, კანდიდატები თავდაპირველად ლაგდებიან **დარღვევის ქულის**
მიხედვით (რამდენად აჭარბებენ ისინი რომელიმე SLO-ს), შემდეგ კი — კომპოზიტური ქულის მიხედვით. წინააღმდეგ შემთხვევაში გამოიყენება მხოლოდ
კომპოზიტური ქულა.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... თითოეულ კანდიდატს ანიჭებს ქულას პოლიტიკასთან მიმართებით: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ველები** (მიეთითება კომბინირებულ კონფიგურაციაში):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**როდის გამოიყენოთ**: საწარმოო სამუშაო დატვირთვებისთვის, რომლებსაც დაყოვნების, შეცდომების სიხშირის ან ღირებულების მკაცრი ბიუჯეტები აქვთ.

**ალტერნატიული სახელები**: `sla-aware`, `sla`

---

#### 5. `lkgp` — ბოლოს ცნობილი კარგი პროვაიდერი პირველად

ჯერ ცდის **ბოლოს ცნობილ კარგ პროვაიდერს** (თუ მითითებულია), შემდეგ კი სარეზერვოდ იყენებს
`rules` სტრატეგიას. სასარგებლოა სესიის მიჯაჭვულობისთვის — საუბარში შემდგომ მოთხოვნებს
იგივე პროვაიდერი ამუშავებს.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // სარეზერვოდ გამოიყენეთ rules სტრატეგია
    return getStrategy("rules").select(pool, context);
  }
}
```

**როდის გამოიყენოთ**: მრავალსვლიანი საუბრებისთვის, სადაც გსურთ, რომ შემდგომი მოთხოვნები
იმავე პროვაიდერმა დაამუშაოს (მაგ., ქეშირების, კონტექსტის უწყვეტობის ან ფასების თანმიმდევრულობისთვის).

**ალტერნატიული სახელი**: `lkgp` (ალტერნატიული სახელი არ აქვს)

---

### მარშრუტიზატორის მორგებული სტრატეგიები

საჯარო API-ის მეშვეობით შეგიძლიათ დაარეგისტრიროთ `RouterStrategy`-ის საკუთარი იმპლემენტაცია:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // თქვენი მარშრუტიზაციის ლოგიკა აქ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

შემდეგ გამოიყენეთ ის:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## როგორ ერგება დონეები Auto-Combo-ს

16-ფაქტორიანი შეფასების ფუნქცია (`open-sse/services/autoCombo/scoring.ts`) დონისადმი
კუთვნილებას განიხილავს ორ სიგნალად: `tierPriority` (0.0476) და `tierAffinity` (0.0476). სრული
`DEFAULT_WEIGHTS` ნაკრებისთვის იხილეთ ზემოთ მოცემული კანონიკური [შეფასების ფაქტორების ცხრილი](#how-it-works-persisted-auto-combos) —
თითოეული პაკეტის გადაფარვები (ship-fast/cost-saver/quality-first/
offline-friendly) ჩამოთვლილია ცხრილში „წონების პროფილები თითოეული პაკეტისთვის“.

მხოლოდ დონე **არ** აიძულებს სისტემას, რომ Tier 1 ყოველთვის პირველი იყოს — თუ Tier 1-ის დაყოვნება მაღალია ან
ღირებულებისა და ხარისხის თანაფარდობა არაოპტიმალურია, Tier 2 იმარჯვებს. დონეების თანმიმდევრობის იძულებით დასადგენად გამოიყენეთ კომბოს
`priority` სტრატეგია და პროვაიდერები დონეების მიხედვით დაალაგეთ.

Tier 1-ისთვის (გამოწერა) მკვეთრი უპირატესობის მისანიჭებლად გაზარდეთ `tierPriority`-ის წონა:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

დონეების განმარტებებისა და პროვაიდერების კლასიფიკაციისთვის იხილეთ `docs/marketing/TIERS.md`.
