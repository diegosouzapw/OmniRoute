## მიმოხილვა

კვოტის გაზიარების ძრავა პროვაიდერის დროზე დაფუძნებულ კვოტას (მაგ., Codex-ის
5-საათიანი ფანჯარა, Kimi-ის 1500 მოთხოვნა/სთ) სამართლიანად ანაწილებს რამდენიმე API გასაღებს შორის, რომლებიც
ერთსა და იმავე კავშირს იზიარებენ.

**პრობლემა, რომელსაც ის წყვეტს:** OmniRoute მრავალი API გასაღების მოთხოვნებს ერთი და იმავე ზედა დონის
პროვაიდერის ანგარიშისკენ ამისამართებს. გაზიარების ლოგიკის გარეშე, A გასაღებიდან წამოსულმა მოთხოვნების ნაკადმა შეიძლება
ამოწუროს პროვაიდერის საათობრივი კვოტა და B და C გასაღებები დაბლოკილი დატოვოს ფანჯრის განულებამდე.
ძრავა ამას შემდეგი გზებით უშლის ხელს:

1. თითოეული გასაღების მოძრავი მოხმარების აღრიცხვა თითოეული განზომილების მიხედვით (%, მოთხოვნები, ტოკენები, $).
2. სამუშაოს შემნახველი სამართლიანი განაწილების ალგორითმის გამოყენება: გასაღებს შეუძლია ისესხოს უმოქმედო
   წილებიდან, სანამ გლობალური პული გაჯერებული არ არის.
3. შედეგის აღსრულება კრიტიკულ გზაზე (`chatCore.ts`), სანამ მოთხოვნა
   ზედა დონის შემსრულებლამდე მიაღწევს.

## ალგორითმი: სამუშაოს შემნახველი სამართლიანი განაწილება

რეალიზებულია `src/lib/quota/fairShare.ts`-ში.

### რეჟიმები

| პირობა                                     | რეჟიმი      | ქცევა                                                                       |
| ------------------------------------------ | ----------- | --------------------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **გულუხვი** | გასაღებს შეუძლია ისესხოს გლობალურ ლიმიტსა და ჯამურ მოხმარებას შორის სხვაობა |
| `globalUsedPercent >= saturationThreshold` | **მკაცრი**  | ინდივიდუალური სამართლიანი წილის მკაცრად აღსრულება                           |

ნაგულისხმევი მნიშვნელობაა `saturationThreshold = 0.5` (გარემოს ცვლადი `QUOTA_SATURATION_THRESHOLD`).

### გადაწყვეტილება თითოეული განზომილებისთვის

პულის თითოეული აქტიური განზომილებისთვის ძრავა გამოთვლის:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = current rolling value for this key (from QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

შემდეგ:

- **`policy = hard`**: თუ `consumed > fairShareAllowed` და რეჟიმი მკაცრია → **დაბლოკვა**.
- **`policy = soft`**: თუ `consumed > fairShareAllowed` და რეჟიმი მკაცრია → **ჯარიმის დაკისრება** (კომბინაციაში პრიორიტეტის დაქვეითება; მკაცრი დაბლოკვა არასდროს ხდება).
- **`policy = burst`**: დაშვება მანამ, სანამ გლობალური თავისუფალი რესურსი არსებობს, სამართლიანი წილის მიუხედავად.

### აბსოლუტური ზედა ზღვარი

განაწილებაზე მითითებული `capValue` + `capUnit` არის მკაცრი ზედა ზღვარი, რომელიც რეჟიმისა და
პოლიტიკისგან დამოუკიდებელია. ნებისმიერი განზომილება, სადაც `consumed >= capValue`, მოთხოვნას ყოველთვის **ბლოკავს**.

### მრავალგანზომილებიანი შემოწმება

მოთხოვნა იბლოკება, თუ პულში არსებული **რომელიმე** განზომილება მას დაბლოკავდა. განზომილებები
დამოუკიდებელია — 5h% კვოტის ამოწურვა weekly% განზომილებაზე გავლენას არ ახდენს.

### სესხება

გულუხვ რეჟიმში გასაღებს, რომლის განაწილებული წილი სრულად არ არის მოხმარებული, შეუძლია სხვა
გასაღებების გამოუყენებელი წილების ნამატის გამოყენება. ფორმულაა:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

სადაც `consumedByOtherKeys = consumedTotal - consumedByThisKey`. გლობალური ზედა ზღვარი
(ამ განზომილებისთვის პულის `limit`) ყოველთვის მკაცრი ზღვარია.

## მოძრავი ფანჯრის მთვლელი

რეალიზებულია `src/lib/quota/sqliteQuotaStore.ts`-სა და `redisQuotaStore.ts`-ში.

ორი სეგმენტი თითოეული `(apiKeyId, dimensionKey)` წყვილისთვის:

- `curr`: მიმდინარე სეგმენტი (`floor(nowMs / windowMs)`)
- `prev`: წინა სეგმენტი (`curr - 1`)

ეფექტური მოძრავი მნიშვნელობა:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**სიზუსტე**: დაახლოებით 99%. სეგმენტებს შორის საზღვარზე ცდომილება ფანჯრის ზომის მაქსიმუმ
1%-ია (ეს 2-სეგმენტიანი მიახლოების თანდაყოლილი თვისებაა).

### კონკურენტული წვდომა

SQLite-ის დრაივერი: თითოეული `(apiKeyId | dimensionKey)` გასაღებისთვის მეხსიერებაში არსებული mutex
წაკითხვა-შეცვლა-ჩაწერის შეჯიბრის მდგომარეობას თავიდან გვაცილებს. შაბლონი იმეორებს `src/sse/services/auth.ts`-ში გამოყენებულ მოთხოვნების ერთდროული მოზღვავების საწინააღმდეგო მიდგომას.

Redis-ის დრაივერი: ატომური ზრდისთვის გამოიყენება Lua EVAL სკრიპტი — ის Redis-ის ერთი ბრძანების სახით სრულდება.

## დრაივერები

### SQLite (ნაგულისხმევი, ინსტალაციის გარეშე)

- ცხრილი: `quota_consumption` (იხილეთ მიგრაციები `073_quota_pools.sql` / `074_quota_consumption.sql`).
- საუკეთესოა ერთი ინსტანციის მქონე განთავსებებისთვის.
- ყველა მუდმივი მონაცემი ინახება არსებულ OmniRoute SQLite DB-ში (`DATA_DIR/storage.sqlite`).

### Redis (არასავალდებულო, მრავალი ინსტანციისთვის)

- საჭიროებს `ioredis` npm პაკეტს.
- მრიცხველები ინახება Redis-ში; მეტამონაცემები (პულები/განაწილებები) კვლავ SQLite-ში ინახება.
- საუკეთესოა მრავალი რეპლიკის მქონე განთავსებებისთვის, სადაც მრიცხველები საზიარო უნდა იყოს.

### დრაივერების გადართვა

პარამეტრების ინტერფეისიდან (`/dashboard/settings` → Quota Store), ან გარემოს ცვლადების მეშვეობით:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

DB-ის პარამეტრს გარემოს ცვლადზე მაღალი პრიორიტეტი აქვს. თუ `driver=redis`, მაგრამ URL არ არის მითითებული ან
`ioredis` არ არის დაინსტალირებული, ფაბრიკა უბრუნდება SQLite-ს და ჟურნალში გაფრთხილებას წერს.

დრაივერის არჩევის თანმიმდევრობა:

1. DB-ის პარამეტრი `quotaStore.driver`
2. გარემოს ცვლადი `QUOTA_STORE_DRIVER`
3. ნაგულისხმევი: `sqlite`

QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // ამ განზომილებისთვის პულის გლობალური ზედა ზღვარი

**მაგალითი: Codex-ის გეგმა** (5h% + weekly%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

მოთხოვნის დასაშვებად ის ყველა განზომილების პირობას უნდა აკმაყოფილებდეს.

## კონვეიერში ინტეგრაცია

### PRE ჰუკი (`open-sse/handlers/chatCore.ts`)

სრულდება ზედა დონის შემსრულებლამდე, ავთენტიფიკაციისა და პოლიტიკის შემოწმებების შემდეგ:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() თითოეულ განზომილებაზე
      → fairShare.decideFairShare()
      → თუ დაბლოკილია → დააბრუნოს 429 (buildErrorBody, მკაცრი წესი #12)
      → თუ დაშვებულია + პრიორიტეტი დაქვეითებულია → კანდიდატზე quotaSoftPenalty=true-ის დაყენება
  → executor.execute()
```

**შეცდომისას დაშვება**: თუ `enforceQuotaShare` გამონაკლისს გამოიწვევს, მოთხოვნა დაშვებული იქნება
და ჩაიწერება `pino.warn` ჟურნალის ჩანაწერი. ეს ხელს უშლის კვოტის ძრავის შეცდომას მთელი
ტრაფიკის დაბლოკვაში.

### POST ჰუკი (მოხმარების ჩაწერა)

წარმატებული პასუხის შემდეგ:

```
შემსრულებელი აბრუნებს წარმატებულ შედეგს
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() თითოეულ განზომილებაზე
      → შეცდომისას დაშვება: შეცდომები იწერება როგორც pino.warn და არასდროს გადაეცემა კლიენტს
```

**გადახრის შენიშვნა**: თუ პასუხის შემდეგ `consume` ვერ შესრულდება, მოძრავი მრიცხველი ნაკლებ მნიშვნელობას აჩვენებს.
პროვაიდერისგან მიღებული გაჯერების სიგნალი (მაგ., `anthropic-ratelimit-unified-5h-utilization`)
შემდეგ მოთხოვნაზე გლობალურ შეფასებას ასწორებს.

### კომბინაციის რბილი ჯარიმა (`open-sse/services/combo.ts`)

როდესაც `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // ნაგულისხმევად 0.7
}
```

ჯარიმა გამოიყენება შეფასების ყველა სხვა ფაქტორის შემდეგ. ის ამცირებს გაჯერებული გასაღების არჩევის
ალბათობას ავტომატურ კომბინაციაში, მისი მკაცრად დაბლოკვის გარეშე.

## პრობლემების მოგვარება

### Redis კონფიგურირებულია, მაგრამ კავშირი არ მყარდება

შეამოწმეთ, რომ `ioredis` დაყენებულია (`npm ls ioredis`) და `QUOTA_STORE_REDIS_URL`
ხელმისაწვდომია. კავშირის შეცდომის შემთხვევაში ფაბრიკა SQLite-ზე გადაერთვება (ლოგირდება
`warn` დონეზე).

### `peek` მოძველებულ შედეგს აბრუნებს / შეცდომისას ღიად მუშაობს

თუ `peek` გამონაკლისს აგდებს, `enforceQuotaShare` შედეგს განიხილავს როგორც „დაშვებას“ (შეცდომისას ღია რეჟიმი).
ძირითადი მიზეზის დასადგენად `pino`-ს ლოგებში შეამოწმეთ `quota:enforce` და `quota:factory`
ჩანაწერები.

### მოხმარების მრიცხველის აცდენა

თუ პროვაიდერის ფაქტობრივი გამოყენება მრიცხველებისგან განსხვავდება, ეს მოსალოდნელია —
2-კალათიანი მოძრავი ფანჯრის ცდომილება ფანჯრის საზღვრებთან ~1%-ია, ხოლო `consume`
პასუხის შემდეგ „გაუშვი და დაივიწყე“ პრინციპით სრულდება. გაჯერების სიგნალი (`saturationSignals.ts`)
კითხულობს პროვაიდერის რეალურ დატვირთვას 30-წამიანი TTL-ით და შესაბამისად არეგულირებს `globalUsedPercent`-ს.

### პული ხარჯვის სიჩქარისთვის „მონაცემები არ არის“-ს აჩვენებს

`computeBurnRate`-ს სულ მცირე 2 ისტორიული ნიმუში სჭირდება. ახალი პულები, რომლებზეც მანამდე
`consume` არ გამოძახებულა, აჩვენებენ `tokensPerSecond: 0`-სა და `timeToExhaustionMs: null`-ს.

## მიგრაცია localStorage-იდან

როდესაც `/dashboard/costs/quota-share` პირველად იტვირთება, hook-ი `useLocalStoragePoolMigration`
ამოწმებს:

1. `localStorage.getItem("omniroute:quota-share:pools")` ცარიელი არ არის.
2. `GET /api/quota/pools` აბრუნებს `[]`-ს (DB ცარიელია).

თუ ორივე პირობა ჭეშმარიტია, ის თითოეულ ძველ pool-ს ჯგუფურად აგზავნის `POST /api/quota/pools`-ზე,
შემდეგ კი localStorage-ის key-ს შლის. მიგრაცია იდემპოტენტურია: მე-2 პირობა
ხელახალ მიგრაციას ხელს უშლის.

## შიდა სტრატეგიის კლასიფიკაცია

`quota-share` არის **მხოლოდ შიდა გამოყენებისთვის განკუთვნილი** მარშრუტიზაციის სტრატეგია (`INTERNAL_ROUTING_STRATEGY_VALUES`

`qtSd/` pool-ების კომბინაციებისთვის და განზრახ გამორიცხულია `ROUTING_STRATEGY_VALUES`-დან, რათა UI-ში ან API-ში
მომხმარებლის მიერ ასარჩევ ვარიანტად არასოდეს გამოჩნდეს.

## DB სქემის შეჯამება

`078`, `079` და `085` მიგრაციებით დამატებულია სამი ცხრილი:

- `quota_pools` + `quota_allocations` — pool-ების განსაზღვრებები და თითოეული key-ისთვის გამოყოფილი მოცულობები.
- `quota_consumption` — მოძრავი 2-bucket მთვლელები თითოეული `(apiKeyId, dimensionKey)`-ისთვის.
- `provider_plans` — პროვაიდერის გეგმის ხელით მითითებული ჩანაცვლებები (dimensions JSON თითოეული connectionId-ისთვის).

ყველა ცხრილი დამატებულია იდემპოტენტური `CREATE TABLE IF NOT EXISTS` მიგრაციებით.
