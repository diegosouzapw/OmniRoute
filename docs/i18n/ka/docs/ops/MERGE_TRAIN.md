v3.8.49-დან (ხარისხის/სიჩქარის გეგმის WS3.2/WS3.4) შემოწმებული PR-ების
`release/vX.Y.Z`-ში შერწყმის ნაგულისხმევი გზა არის **Mergify-ის შერწყმის რიგი** (`.mergify.yml`);
ქვემოთ დოკუმენტირებული **ხელით მართვადი შერწყმის მატარებელი** კი სათადარიგო გზაა — ის გამოიყენება ინციდენტების,
რელიზის გაყინვის დროს ან იმ შემთხვევაში, თუ Mergify Open Source-ის გეგმა ოდესმე შეიცვლება.

## ნაგულისხმევი გზა: Mergify-ის რიგი

1. PR გადახედილია/მწვანედ არის მონიშნული კამპანიების მიერ და დამტკიცებულია მფლობელის შერწყმამდელი ⭐
   საკონტროლო ეტაპის მიერ (ანგარიში + გადაწყვეტილება თითოეული ელემენტისთვის — იხილეთ `/merge-prs` ნაბიჯი 0.75).
2. მფლობელი (ან სესია, რომელიც მფლობელის გადაწყვეტილების საფუძველზე მოქმედებს) ანიჭებს **`queue`**
   ჭდეს. ეს ჭდე თავად არის შერწყმის დამტკიცება; Mergify მხოლოდ ასრულებს მას.
3. Mergify რიგში მყოფ PR-ებს სწრაფი საკონტროლო ეტაპების მიხედვით **თანმიმდევრულად**
   (ერთ ჯერზე ერთს) ამოწმებს და აერთიანებს (squash). პაკეტური დამუშავება + ავტომატური ბისექცია Mergify-ის ფასიანი დონეა
   (უფასო გეგმაზე — "Cannot use Merge Queue batch", #7220), ამიტომ `.mergify.yml` არ ადგენს
   `batch_size`-ს; პაკეტური დამუშავება ქვემოთ მოცემული ხელით სამართავი შერწყმის მატარებლის ამოცანად რჩება. PR, რომლის
   შემოწმებებიც `checks_timeout`-ის შემდეგაც მოლოდინის რეჟიმშია (240 წთ = `quality.yml`-ის
   გაზომილი p95-ის 2×), რიგის შეფერხების ნაცვლად რიგიდან ამოიღება.
4. შერწყმის შემდეგ, უწყვეტი გამოშვების მწვანე სტატუსის სამუშაო პროცესი push-ისას ახალ წვერს ამოწმებს
   და, თუ კომბინაციამ რეგრესია გამოიწვია, ატრიბუციის საკითხს ხსნის (ავტომატურად არასოდეს აბრუნებს ცვლილებას).

დამცავი წესები (იმეორებს `CLAUDE.md`-ის მკაცრ წესებს #21/#22):

- **გამოშვების გაყინვა აქტიურია** → გაყინული ტოტისკენ მიმართულ PR-ებს ჭდე არ მიანიჭოთ; ჯერ
  აქტიურ `release/vX+1`-ზე გადაამისამართეთ.
- **სხვა სესიის მიმდინარე PR** → არასოდეს მიანიჭოთ მას ჭდე; საკუთარ ნამუშევარს რიგში მხოლოდ მისი მფლობელი სესია
  აყენებს.
- მხოლოდ ტესტების შემცველი სხვაობები და `hotfix` ჭდის მქონე PR-ები უკვე შემცირებულ CI-ს ასრულებენ (იხილეთ
  `RELEASE_CHECKLIST.md` → Hotfix Fast-Lane); რიგის პირობები იღებს რეალურად შესრულებულ
  შემოწმებათა ნებისმიერ ნაკრებს (`#check-failure=0` + `#check-pending=0`).

## სათადარიგო გზა: ხელით მართვადი შერწყმის მატარებელი

გამოიყენება, როდესაც რიგი მიუწვდომელია. ეს ფორმალურად აღწერს პრაქტიკას, რომელმაც v3.8.47 ციკლის
განმავლობაში ერთ დღეში 33 PR დაამუშავა:

1. **შეკრიბეთ ჯგუფი** (~10–30 შემოწმებული+დამტკიცებული PR). შეამოწმეთ `linked:` კონფლიქტები
   (იგივე `tap.testFiles`, იგივე CHANGELOG-ის ფრაგმენტები) და ისინი თანმიმდევრულად დაამუშავეთ.
2. **შეამოწმეთ ერთხელ**: რელიზის წვეროდან შექმნილ იზოლირებულ worktree-ში ლოკალურად გააერთიანეთ ჯგუფის
   ყველა head, შემდეგ კი გაუშვით რელიზის ეკვივალენტური ნაკრები
   (`npm run check:release-green`, რელიზამდე დაამატეთ `--with-build`).
   `scripts/release/merge-train.sh <base> <PR#>…` ავტომატიზაციას უკეთებს ნაბიჯებს 1–2 (კონფლიქტური
   PR-ები გამოირიცხება, მატარებელი კი აგრძელებს მუშაობას). სრული რეჟიმი უშვებს `npm run test:unit`-ს —
   მანქანისთვის მორგებულ გამშვებს (`--test-concurrency=20`) და **არა** ორ თანმიმდევრულ 4-ბირთვიან CI
   shard-ს, რომელთა გამოც დომინანტური ფაზა 16-ბირთვიანი მანქანის დაახლოებით 25%-ს იყენებდა (გამოსწორდა
   2026-07-18). `--fast` (დღის განმავლობაში მეგა-მატარებლების დაცლა, მფლობელის მიერ დამტკიცებული 2026-07-18)
   ინარჩუნებს ყველა სტატიკურ კონტროლს + vitest-ს, მაგრამ უშვებს მხოლოდ ბორტზე მიღებული PR-ებით შეცვლილ
   node:test ფაილებს; სრული ნაკრები მაინც უნდა გაეშვას დღეში მინიმუმ ერთხელ
   დაგროვილ წვეროზე (ერთი მატარებელი `--fast`-ის გარეშე).
3. **მწვანე** → თანმიმდევრულად გააერთიანეთ PR-ები (თითოეულის წინ ხელახლა შეამოწმეთ `state,headRefOid` —
   PR, რომლის head გადაადგილდა, ხელახლა გადის მიმოხილვას). დაამტკიცეთ, რომ თითოეული შერწყმის წმინდა განსხვავება
   მხოლოდ თავად PR-ის ცვლილებაა (ავტომატური გადაწყვეტით დაბრუნებები აკრძალულია: ფარგლებს გარეთ არსებული
   წაშლების გამოსავლენად შეამოწმეთ `git diff --stat`).
4. **წითელი** → ჯგუფი გაყავით ორ ნაწილად (შეამოწმეთ თითოეული ნახევარი), ნაცვლად იმისა, რომ თითოეული
   ცალ-ცალკე გადაამოწმოთ; პრობლემური PR მტკიცებულებებთან ერთად დააბრუნეთ მიმოხილვის რიგში.
5. **არასდროს**: გაყინვის დროს არ შეიტანოთ ცვლილებები გაყინულ შტოში; არსად გამოიყენოთ `git stash`;
   ნუ გაუშვებთ CI-ს განურჩევლად ხელახლა იმ იმედით, რომ წითელი გაქრება (წესი: წითელი შედეგი ინფორმაციაა).

და არა თითოეულ PR-ზე, რაც გამორიცხავს O(N) ორმხრივ ციკლებს.

## ახალი checkout-ის წინაპირობები `merge-train.sh`-ისთვის

სკრიპტი ძირეულ checkout-ზე (ნებისმიერ worktree სამუშაომდე) უშვებს მყისიერი შეწყვეტის მქონე
**წინასწარ შემოწმებას**, რათა დაზიანებული ინსტალაცია ვერასდროს გამოჩნდეს წითელ მატარებლად:

1. გაუშვით `npm ci`, შემდეგ კი `bun`-ის postinstall, რომელსაც npm ბლოკავს:
   `(cd node_modules/bun && node install.js)` — წინააღმდეგ შემთხვევაში `check:provider-consistency`
   და `check:known-symbols` (ორივე `bun scripts/…`) ჩაიშლება როგორც მატარებელზე, ისე საბაზისო მდგომარეობაზე,
   დარღვევის სტრიქონის გარეშე.
2. არ უნდა არსებობდეს ზედმეტი `node_modules/node_modules` (დამოკიდებულებების დუბლირებული ხე; React ორჯერ იტვირთება
   და UI vitest ნაკრებები მყისიერად იშლება).
3. `node_modules/.bin/tsc` უნდა არსებობდეს და შესრულებადი იყოს (არასრულ ინსტალაციაში ის არ არის).

მატარებელი უშვებს ბლოკირებად `npm run check:cycles:ratchet`-ს; უბრალო `npm run check:cycles`
სარეკომენდაციოა (ის ჩამოთვლის SCC-ებს და ჯანმრთელ საბაზისო მდგომარეობაზეც კი არანულოვანი კოდით სრულდება).
