> **TL;DR**: OmniRoute-ს მოჰყვება ჩაშენებული ჯანმრთელობის მონიტორინგი, პროვაიდერის ავტოპილოტი, კვოტების თვალყურის დევნება და დაკვირვებადობის ჰუკები. ეს სახელმძღვანელო მოიცავს მართვის პანელს, გაფრთხილებებსა და პრობლემების აღმოფხვრას.

**წყაროები:**

- `src/lib/monitoring/observability.ts` — დაკვირვებადობის სნეპშოტი
- `src/lib/monitoring/comboHealthAutopilot.ts` — კომბინაციის ჯანმრთელობის ავტოპილოტი
- `src/lib/monitoring/providerHealthAutopilot.ts` — პროვაიდერის ავტოპილოტი
- `src/lib/monitoring/providerHealthMatrix.ts` — პროვაიდერის ჯანმრთელობის მატრიცა
- `src/lib/localHealthCheck.ts` — ლოკალური ჯანმრთელობის შემოწმება
- `src/lib/tokenHealthCheck.ts` — ტოკენის განახლების ჯანმრთელობა
- `src/lib/proxyHealth.ts` — პროქსის ჯანმრთელობის ქეში (განხილულია PROXY_GUIDE.md-ში)

## ჯანმრთელობის შემოწმების API

OmniRoute ხელმისაწვდომს ხდის HTTP ჯანმრთელობის შემოწმების **ორ** ინტერფეისს. ორკესტრატორებისთვის ისინი ურთიერთჩანაცვლებადი არ არის.

| გზა                          | დანიშნულება                                                                          | დატვირთვა                                    | გამოყენება                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET /healthz`               | სასიცოცხლო ციკლის სიცოცხლისუნარიანობა/მზადყოფნა (`ok` / `starting` / `stopping`)     | უმნიშვნელო (მხოლოდ ფაზის დროშა)              | Kubernetes-ის **მზადყოფნა**; მსუბუქი **სიცოცხლისუნარიანობა**, თუ HTTP-ის გამოყენება აუცილებელია         |
| `GET /api/monitoring/health` | სისტემისა და პროვაიდერების სიღრმისეული შეჯამება (DB, heap, კატალოგის რაოდენობები, …) | მძიმე (სინქრონული DB / მონიტორინგის სამუშაო) | საინფორმაციო პანელები, blackbox-ის სიღრმისეული შემოწმებები, Docker-ის ჩაშენებული ჯანმრთელობის შემოწმება |

> **შენიშვნა:** პროვაიდერის ჯანმრთელობის მატრიცები, ავტოპილოტის პრობლემები, კვოტის მონიტორები, ტოკენების ჯანმრთელობა და `/api/monitoring/health`-ზე უფრო დეტალური დაყოვნების მონაცემები ხელმისაწვდომია **MCP ხელსაწყოს** `observability_snapshot` ან **საინფორმაციო პანელის** გვერდების მეშვეობით — მათთვის გამოყოფილი REST მარშრუტები არ არსებობს.

ორივე მარშრუტი მუშაობს მოთხოვნების დამუშავების **იმავე Node event loop-ზე**. CPU-ზე დამოკიდებულმა გზამ (დიდი `GET /v1/models` კატალოგის დამუშავება, გრძელი კონტექსტის შეკუმშვა / ტოკენების დათვლა) შეიძლება დააყოვნოს **ყველა** HTTP დამმუშავებელი, მათ შორის `/healthz`. დაკავებული event loop ≠ მკვდარი პროცესი. უმჯობესია დატვირთვის გამომწვევი მიზეზი გამოსწორდეს; შემოწმების პარამეტრების მორგება მხოლოდ მცდარ შეწყვეტებს ამცირებს.

### მსუბუქი ორკესტრატორის შემოწმება

```bash
GET /healthz
# ან HEAD /healthz
```

- **200** + პასუხის სხეული `ok`, როდესაც სერვერის სასიცოცხლო ციკლის ფაზა მზადაა
- **503** + `starting` / `stopping` გაშვების ან გამორთვის დროს
- იმპლემენტაცია: `src/app/healthz/route.ts` (DB ping-ის გარეშე)

#### `credentialHealth`: შემოწმების ქეში SQLite-ის `test_status`-ის წინააღმდეგ

`GET /api/monitoring/health` → `credentialHealth` არის **მეხსიერებაში არსებული შემოწმების ქეშის
მაჩვენებელი** და არა `provider_connections.test_status`-ის მიმდინარე ასლი. #12532-ის შემდეგ
მოთხოვნის გზა მხოლოდ `getCachedCredentialHealthSummary()`-ს კითხულობს; ფონური შემოწმებები
ქეშს event loop-ის მიღმა აახლებენ.

| ფენა                           | ადგილმდებარეობა                                                       | მნიშვნელობა                                                                                                                                                                                                                      |
| ------------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| შემოწმების ქეშის მაჩვენებელი   | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | ავტორიზაციის მონაცემების ჯანმრთელობის ბოლო შემოწმებების შედეგები, რომლებიც კვლავ პროცესის მეხსიერებაში ინახება. `source` ყოველთვის არის `probe-cache`.                                                                           |
| წარუმატებელი კავშირის დეტალები | `credentialHealth.failedConnections`                                  | წარმოდგენილია **მხოლოდ მაშინ, როდესაც `failed > 0`**. ქეშის `status=error` მქონე მწკრივების შეზღუდული სია (`connectionId`, `status`, გასუფთავებული `lastError` / `lastErrorType`). სიის შეზღუდვისას დაყენებულია `failedOmitted`. |
| SQLite-ის მუდმივი სტატუსი      | `credentialHealth.staleDbNonOkCount`                                  | იმ **აქტიური** (`is_active=1`) კავშირის მწკრივების რაოდენობა, რომელთა შენახული `test_status` ცნობილ არადამაკმაყოფილებელ მნიშვნელობას შეიცავს (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).  |

ეს ორი ფენა შეიძლება განზრახ განსხვავდებოდეს:

- მაჩვენებელი `failed=0`, ხოლო `staleDbNonOkCount>0` — SQLite-ში კვლავ ინახება მუდმივი
  `test_status` (მაგალითად, `expired` ან `credits_exhausted`), რომელსაც შემოწმების ქეშის უახლესი
  სურათი `status=error`-ად არ ითვლის.
- მაჩვენებელი `failed>0`, ხოლო SQLite ჯანმრთელად გამოიყურება — ბოლო შემოწმება წარუმატებელი იყო და
  ქეშში ინახება; DB-ის მწკრივი ჯერ არ განახლებულა ან მოგვიანებით გასუფთავდა.

ამ საბოლოო წერტილიდან მონაცემების ამოღებისას გაფრთხილება მხოლოდ `provider_connections.test_status`-ზე
არ დააფუძნოთ. მიმდინარე შემოწმების წარუმატებლობებისთვის გამოიყენეთ `failed` + `failedConnections`, ხოლო
შენახული მუდმივი სტატუსების რაოდენობისთვის — `staleDbNonOkCount`.

### Kubernetes-ის შემოწმების რეკომენდაციები

OmniRoute არის **ერთი Node პროცესი** (ერთი event loop). Docker-ის სტანდარტული `HEALTHCHECK` მსუბუქ `/healthz`-ს იყენებს. `/api/monitoring/health` kubelet-ის სიცოცხლისუნარიანობის შემოწმების ინტერვალებისთვის **ზედმეტად მძიმეა**.

| შემოწმება               | რეკომენდებული სამიზნე                                                                  | შენიშვნები                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **გაშვება**             | HTTP `GET /healthz` დიდი `failureThreshold`-ით (ან დიდი `startPeriod`-ით)              | ცივმა გაშვებამ + SQLite-ის მიგრაციამ შეიძლება რამდენიმე წამზე მეტხანს გასტანოს                                                                                                                                                                                                                                                                                                                                                                 |
| **მზადყოფნა**           | HTTP `GET /healthz`                                                                    | სასიცოცხლო ციკლი: `ok` / `starting` / `stopping` (200 და 503). მდგომარეობა კვლავ მერყეობს, თუ ციკლი CPU-ის მიერაა დაბლოკილი. **რამდენიმე წამში მიღებული 200 ჯანსაღ მდგომარეობას არ ნიშნავს** (#10303) — ეს ნიშნავს, რომ 3-ბაიტიანი დამმუშავებლის გაშვებამდე მოვლენათა ციკლი რესურსების გარეშე იყო დარჩენილი                                                                                                                                    |
| **სიცოცხლისუნარიანობა** | HTTP `GET /livez`, **ან TCP** ძირითადი სერვისის პორტზე (`PORT`, ნაგულისხმევად `20128`) | `/livez` მხოლოდ პროცესის მუშაობას ამოწმებს (თუ დამმუშავებელი გაეშვა, ყოველთვის 200-ს აბრუნებს). ის კვლავ მოვლენათა იმავე ციკლს იყენებს — დატვირთული ≠ მკვდარი და მოვლენათა ციკლის რესურსების გარეშე დარჩენას (#10303) TCP-ზე უკეთ ვერ ადგენს. უპირატესობა მიანიჭეთ **TCP**-ს, თუ კატალოგის/შეკუმშვის დატვირთვისას HTTP-შემოწმებების მოლოდინის დრო იწურება; არც ერთ შემთხვევაში **არ** გააჩეროთ pod მოვლენათა ციკლის ხანმოკლე შეყოვნებების გამო |
| **ღრმა შემოწმება**      | `GET /api/monitoring/health` გარე შემმოწმებლიდან                                       | არ გამოიყენოთ kubelet-ის `livenessProbe`-ისთვის / ხშირი `readinessProbe`-ისთვის                                                                                                                                                                                                                                                                                                                                                                |

კონფიგურაციის მაგალითი (ზღვრები მოარგეთ ცივი გაშვებისა და შეკუმშვის დატვირთვას):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # მოვლენათა ციკლის შეყოვნებისას HTTP /livez-ის მოლოდინის დრო შესაძლოა მაინც ამოიწუროს. TCP
  # უფრო კონსერვატიული ალტერნატივაა:
  # tcpSocket:
  #   port: http
```

kubelet-ის **სიცოცხლისუნარიანობის** შემოწმება **არ** მიმართოთ `/api/monitoring/health`-ზე. ეს მარშრუტი რეალურ DB/მონიტორინგის სამუშაოს ასრულებს და დატვირთვისას ცრუ დადებით შედეგს დააბრუნებს.

დაკავშირებული საკითხები: [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (შემოწმებები მოვლენათა ციკლის დატვირთულობისას), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (კატალოგის ფასების დამუშავება რესურსებს ითვისებს), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (შეკუმშვის ტოკენების დათვლა რესურსებს ითვისებს).

### systemd-ის watchdog (გაყინული მოვლენათა ციკლი)

systemd-ის ჰოსტზე OmniRoute სერვისების მენეჯერს ატყობინებს, როცა მზად არის, და პერიოდულად უგზავნის სიგნალს, რათა სერვერი, რომლის მოვლენათა ციკლიც გაჭედილია, მუშაობის გაგრძელებისა და უხმოდ დარჩენის ნაცვლად გაითიშოს და თავიდან გაეშვას. სიგნალები სერვერის საკუთარი მოვლენათა ციკლიდან იგზავნება: როდესაც ის იბლოკება, სიგნალები წყდება და `WatchdogSec`-ით განსაზღვრული დროის განმავლობაში სიგნალის მიუღებლობის შემდეგ systemd სერვისს თავიდან უშვებს.

[`omniroute autostart enable`](../../bin/cli/tray/autostart.mjs) უკვე ქმნის მომხმარებლის unit-ს ამ პარამეტრებით. თქვენ მიერ შექმნილ unit-ს (ნაგულისხმევი `Type=simple`) watchdog არ ექნება, ამიტომ მის `[Service]` სექციაში დაამატეთ შემდეგი ხაზები:

```ini
[Service]
Type=notify
NotifyAccess=all
WatchdogSec=180
TimeoutStartSec=300
```

გენერირებული unit აყენებს `Restart=on-failure`-ს, ამიტომ ეს ხაზიც დაამატეთ — მის გარეშე watchdog გაჭედილ სერვისს მხოლოდ გააჩერებს და თავიდან არ გაუშვებს.

- `Type=notify`: სერვისი „გაშვებულად“ ითვლება მაშინ, როდესაც სერვერი `READY=1`-ს აგზავნის და არა მაშინ, როდესაც პროცესი fork-ს ასრულებს. `TimeoutStartSec` ზღუდავს ნელი გაშვების ხანგრძლივობას.
- `NotifyAccess=all`: სიგნალებს აგზავნის სერვერის პროცესი, რომელიც `omniroute serve` ზედამხედველი პროცესის შვილობილი პროცესია.
- `WatchdogSec`: სიგნალები ყოველ 60 წამში იგზავნება, ამიტომ გამოიყენეთ **120 ან მეტი**. უფრო მცირე მნიშვნელობები ჯანსაღ სერვერს თავიდან გაუშვებს.
- გაუშვით `omniroute serve` წინა პლანზე. `--daemon` სერვერს unit-ის cgroup-ისგან განცალკევებით უშვებს და შეტყობინებების გაცვლა არასდროს სრულდება.

თავიდან გაშვების შემდეგ შეამოწმეთ, რომ ის აქტიურია:

```bash
systemctl --user show omniroute -p WatchdogUSec -p WatchdogTimestamp
```

`WatchdogUSec` აჩვენებს კონფიგურირებულ დაყოვნებას, ხოლო `WatchdogTimestamp` ყოველ წუთს განახლდება. watchdog-ის მიერ გამოწვეული თავიდან გაშვება ჩაიწერება როგორც `Result=watchdog`. unit-ის უცვლელად დატოვებისას სიგნალების გასათიშად დააყენეთ `OMNIROUTE_DISABLE_SD_NOTIFY=1`; `NOTIFY_SOCKET`-ის გარეშე (terminal, Docker, Electron, Windows) არაფერი გაიგზავნება.

watchdog მხოლოდ იმას ამოწმებს, რომ მოვლენათა ციკლი მუშაობას აგრძელებს. სერვერი, რომელიც ნელია, მაგრამ ციკლის შესრულებას მაინც აგრძელებს, თავიდან არ გაეშვება.

### მოთხოვნის დამუშავების გზაზე შესასრულებელი არასავალდებულო სამუშაო (მეხსიერება, უნარები, ტოკენის განახლება)

მეხსიერების ამოღება, უნარების ინექცია და OAuth ტოკენის განახლება `/healthz`-თან ერთად იყენებს **Node-ის მთავარ მოვლენათა ციკლს**. ესენი დაფიდან ჩასართავი ფუნქციებია (`memoryEnabled`, `skillsEnabled`) და არა worker pool. იხილეთ [გარემო — მოვლენათა ციკლის დანახარჯი](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349).

## პროვაიდერის ჯანმრთელობის ავტოპილოტი

`providerHealthAutopilot.ts` მოდული არის **თვითაღდგენის სისტემა**, რომელიც:

1. აღმოაჩენს პროვაიდერის პრობლემებს (გახსნილი წრედი, დაყოვნების პერიოდები, ბლოკირებები, კვოტის გაფრთხილებები)

2. კონკრეტული შეცდომის კლასის სანახავად გადახედეთ **ბოლო შეცდომებს**
3. პროვაიდერის ბარათზე სცადეთ **კავშირის ტესტი**
4. შეამოწმეთ, ხომ არ არის პროვაიდერი **ზედა დონეზე სიხშირით შეზღუდული** (ლოკალურად არ ჩანს)

### „კვოტა მიუთითებს, რომ ყველაფერი გამართულადაა, მაგრამ ვხედავ 429 შეცდომებს“

- 429 ნიშნავს, რომ პროვაიდერის მიხედვით თქვენი კვოტა ამოწურეთ
- OmniRoute-ის კვოტის აღრიცხვა შეიძლება **მოძველებული** იყოს — ჭეშმარიტი მონაცემები პროვაიდერთანაა
- კვოტის მონაცემები ავტომატურად ახლდება კვოტის შიდა მონიტორის საშუალებით

### „კომბინაცია ვერ მუშაობს, თუმცა ყველა სამიზნე გამართულად გამოიყურება“

- სამიზნეების მიმდევრობასთან დაკავშირებული პრობლემების სანახავად შეამოწმეთ **კომბინაციის მდგომარეობის** მართვის პანელი
- გადახედეთ **სარეზერვო გადართვის მოვლენებს** — შესაძლოა, კომბინაცია ვარიანტებს ზედმეტად სწრაფად ამოწურავს
- დარწმუნდით, რომ **სტრატეგია** შეესაბამება თქვენს გამოყენების შემთხვევას (პრიორიტეტული, ციკლური ან ავტომატური)

### „მონაცემთა ბაზის მდგომარეობის შემოწმება ვერ სრულდება“

- გაუშვით `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- თუ შედეგია „ok“ — ეს ცრუ განგაშია და მდგომარეობის შემოწმება ზედმეტად მკაცრია
- ნებისმიერი სხვა შედეგის შემთხვევაში — **გააჩერეთ OmniRoute** და მიჰყევით [კატასტროფის შემდეგ აღდგენის სახელმძღვანელოს](./DATABASE_GUIDE.md#disaster-recovery)

### „მეხსიერების გროვაზე დატვირთვა კრიტიკულია“

```bash
# მიმდინარე გროვის შემოწმება

# მეხსიერების ხელით გაწმენდის გაშვება (თუ გამოყენებულია --expose-gc)

# ერთდროული მოთხოვნების რაოდენობის შემცირება (დააყენეთ მართვის პანელის Settings გვერდიდან და არა გარემოს ცვლადით)
# `MAX_CONCURRENT_REQUESTS` გარემოს ცვლადი არ არსებობს — დააკონფიგურირეთ Settings → Concurrency განყოფილებაში.
```
