> **TL;DR**: OmniRoute-ს მოჰყვება ჩაშენებული ჯანმრთელობის მონიტორინგი, პროვაიდერის ავტოპილოტი, კვოტების თვალყურის დევნება და დაკვირვებადობის ჰუკები. ეს სახელმძღვანელო მოიცავს მართვის პანელს, გაფრთხილებებსა და პრობლემების აღმოფხვრას.

**წყაროები:**

- `src/lib/monitoring/observability.ts` — დაკვირვებადობის სნეპშოტი
- `src/lib/monitoring/comboHealthAutopilot.ts` — კომბინაციის ჯანმრთელობის ავტოპილოტი
- `src/lib/monitoring/providerHealthAutopilot.ts` — პროვაიდერის ავტოპილოტი
- `src/lib/monitoring/providerHealthMatrix.ts` — პროვაიდერის ჯანმრთელობის მატრიცა
- `src/lib/localHealthCheck.ts` — ლოკალური ჯანმრთელობის შემოწმება
- `src/lib/tokenHealthCheck.ts` — ტოკენის განახლების ჯანმრთელობა
- `src/lib/proxyHealth.ts` — პროქსის ჯანმრთელობის ქეში (განხილულია PROXY_GUIDE.md-ში)

## ჯანმრთელობის შემოწმების API

OmniRoute ხელმისაწვდომს ხდის HTTP ჯანმრთელობის შემოწმების **ორ** ინტერფეისს. ორკესტრატორებისთვის ისინი ურთიერთჩანაცვლებადი არ არის.

| გზა                          | დანიშნულება                                                                           | დატვირთვა                                    | გამოყენება                                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `GET /healthz`               | სასიცოცხლო ციკლის სიცოცხლისუნარიანობა/მზადყოფნა (`ok` / `starting` / `stopping`)      | უმნიშვნელო (მხოლოდ ფაზის დროშა)              | Kubernetes-ის **მზადყოფნა**; მსუბუქი **სიცოცხლისუნარიანობის** შემოწმება, თუ HTTP-ის გამოყენება აუცილებელია |
| `GET /api/monitoring/health` | სისტემისა და პროვაიდერების სიღრმისეული შეჯამება (DB, გროვა, კატალოგის რაოდენობები, …) | მძიმე (სინქრონული DB / მონიტორინგის სამუშაო) | საინფორმაციო დაფები, blackbox-ის სიღრმისეული შემოწმებები, Docker-ის ჩაშენებული ჯანმრთელობის შემოწმება      |

> **შენიშვნა:** პროვაიდერების ჯანმრთელობის მატრიცები, autopilot-ის პრობლემები, კვოტის მონიტორები, ტოკენების ჯანმრთელობა და `/api/monitoring/health`-ზე უფრო დეტალური შეყოვნების ინფორმაცია ხელმისაწვდომია **MCP ინსტრუმენტის** `observability_snapshot` ან **საინფორმაციო დაფის** გვერდების მეშვეობით — მათთვის ცალკეული REST მარშრუტები არ არსებობს.

ორივე მარშრუტი მოთხოვნების დამუშავების მსგავსად **იმავე Node-ის მოვლენათა ციკლში** მუშაობს. CPU-ზე დამოკიდებულმა მარშრუტმა (`GET /v1/models`-ის დიდი კატალოგის დამუშავება, გრძელი კონტექსტის შეკუმშვა / ტოკენების დათვლა) შეიძლება **ყველა** HTTP დამმუშავებლის მუშაობა შეაყოვნოს, მათ შორის `/healthz`-ისაც. მოვლენათა ციკლის დატვირთულობა ≠ პროცესის სიკვდილი. უპირატესობა მიანიჭეთ დატვირთვის გამომწვევი მიზეზის გამოსწორებას; შემოწმების პარამეტრების მორგება მხოლოდ მცდარი შეწყვეტების რაოდენობას ამცირებს.

### მსუბუქი საორკესტრაციო შემოწმება

```bash
GET /healthz
# ან HEAD /healthz
```

- **200** + სხეული `ok`, როდესაც სერვერის სასიცოცხლო ციკლის ფაზა მზადაა
- **503** + `starting` / `stopping` გაშვების ან გამორთვის დროს
- იმპლემენტაცია: `src/app/healthz/route.ts` (DB-ის შემოწმების გარეშე)

მაჩვენებელი** და არა `provider_connections.test_status`-ის მიმდინარე ასლი. #12532-ის შემდეგ
მოთხოვნის მარშრუტი მხოლოდ `getCachedCredentialHealthSummary()`-ს კითხულობს; ფონური შემოწმებები
კეშს მოვლენათა ციკლის მიღმა აახლებს.

| ფენა                           | მდებარეობა                                                            | მნიშვნელობა                                                                                                                                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| შემოწმების კეშის მაჩვენებელი   | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | ავტორიზაციის მონაცემების ჯანმრთელობის ბოლო შემოწმებების შედეგები, რომლებიც ჯერ კიდევ პროცესის მეხსიერებაში ინახება. `source` ყოველთვის არის `probe-cache`.                                                                             |
| წარუმატებელი კავშირის დეტალები | `credentialHealth.failedConnections`                                  | წარმოდგენილია **მხოლოდ მაშინ, როცა `failed > 0`**. `status=error`-ის მქონე კეშის ჩანაწერების შეზღუდული სია (`connectionId`, `status`, გასუფთავებული `lastError` / `lastErrorType`). `failedOmitted` დაყენებულია, როდესაც სია შეიზღუდა. |
| SQLite-ის მუდმივი სტატუსი      | `credentialHealth.staleDbNonOkCount`                                  | იმ **აქტიური** (`is_active=1`) კავშირის ჩანაწერების რაოდენობა, რომელთა შენახული `test_status` არის ცნობილი არადამაკმაყოფილებელი მნიშვნელობა (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`).         |

ეს ორი ფენა შესაძლოა განზრახ არ ემთხვეოდეს ერთმანეთს:

- მაჩვენებელი `failed=0`, ხოლო `staleDbNonOkCount>0` — SQLite-ში ჯერ კიდევ ინახება მუდმივი
  `test_status` (მაგალითად, `expired` ან `credits_exhausted`), რომელსაც შემოწმების კეშის უახლესი
  სურათი `status=error`-ად არ ითვლის.
- მაჩვენებელი `failed>0`, ხოლო SQLite ჯანმრთელად გამოიყურება — ბოლო შემოწმება წარუმატებელი იყო და
  დაკეშილია; DB-ის ჩანაწერი ჯერ არ განახლებულა ან მოგვიანებით გასუფთავდა.

ამ საბოლოო წერტილის შეგროვებისას გაფრთხილება მხოლოდ `provider_connections.test_status`-ზე
არ დააფუძნოთ. მიმდინარე შემოწმებების წარუმატებლობებისთვის გამოიყენეთ `failed` + `failedConnections`, ხოლო
შენახული მუდმივი სტატუსების რაოდენობისთვის — `staleDbNonOkCount`.

### Kubernetes-ის შემოწმებების რეკომენდაციები

OmniRoute არის **ერთი Node პროცესი** (ერთი მოვლენათა ციკლი). Docker-ის სტანდარტული `HEALTHCHECK` მსუბუქ `/healthz`-ს იყენებს. `/api/monitoring/health` **ზედმეტად მძიმეა** kubelet-ის სიცოცხლისუნარიანობის შემოწმების ინტერვალებისთვის.

| შემოწმება                   | რეკომენდებული სამიზნე                                                                  | შენიშვნები                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **გაშვება**                 | HTTP `GET /healthz` ხანგრძლივი `failureThreshold`-ით (ან დიდი `startPeriod`-ით)        | ცივი გაშვება + SQLite-ის მიგრაცია შეიძლება რამდენიმე წამზე მეტხანს გაგრძელდეს                                                                                                                                                                                                                                                                                                                                                        |
| **მზადყოფნა**               | HTTP `GET /healthz`                                                                    | სასიცოცხლო ციკლი: `ok` / `starting` / `stopping` (200 და 503). მდგომარეობა კვლავ მერყეობს, თუ ციკლი CPU-ის მიერაა დაბლოკილი. **რამდენიმე წამში მიღებული 200 ჯანსაღ მდგომარეობას არ ნიშნავს** (#10303) — ეს ნიშნავს, რომ 3-ბაიტიანი დამმუშავებლის გაშვებამდე მოვლენათა ციკლი რესურსის გარეშე იყო დარჩენილი                                                                                                                            |
| **სიცოცხლისუნარიანობა**     | HTTP `GET /livez`, **ან TCP** ძირითადი სერვისის პორტზე (`PORT`, ნაგულისხმევად `20128`) | `/livez` მხოლოდ პროცესის აქტიურობას ამოწმებს (ყოველთვის 200, თუ დამმუშავებელი გაეშვება). ის კვლავ იზიარებს მოვლენათა ციკლს — დაკავებული ≠ მკვდარი და მოვლენათა ციკლის რესურსის გარეშე დარჩენას (#10303) TCP-ზე უკეთ ვერ აფიქსირებს. უპირატესობა მიანიჭეთ **TCP**-ს, თუ HTTP-შემოწმებებს კატალოგის/შეკუმშვის დატვირთვისას მოლოდინის დრო ეწურებათ; არც ერთ შემთხვევაში **არ** გააჩეროთ pod მოვლენათა ციკლის ხანმოკლე შეფერხებების გამო |
| **სიღრმისეული მდგომარეობა** | `GET /api/monitoring/health` გარე შემმოწმებლიდან                                       | არ გამოიყენოთ kubelet-ის `livenessProbe`-ისთვის / მოკლე ინტერვალის მქონე `readinessProbe`-ისთვის                                                                                                                                                                                                                                                                                                                                     |

კონფიგურაციის მაგალითი (ზღვრები მოარგეთ ცივი გაშვებისა და შეკუმშვის დატვირთვას):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # მოვლენათა ციკლის შეფერხებისას HTTP /livez-ს შესაძლოა კვლავ ამოეწუროს მოლოდინის დრო. TCP არის
  # კონსერვატიული ალტერნატივა:
  # tcpSocket:
  #   port: http
```

**არ** მიუთითოთ kubelet-ის **სიცოცხლისუნარიანობის** შემოწმება `/api/monitoring/health`-ზე. ეს მისამართი რეალურ DB/მონიტორინგის სამუშაოს ასრულებს და დატვირთვისას ცრუ დადებით შედეგს დააბრუნებს.

დაკავშირებული საკითხები: [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (შემოწმებები მოვლენათა ციკლის დაკავებისას), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (კატალოგის ფასების დამუშავების მიერ რესურსების მონოპოლიზება), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (შეკუმშვის ტოკენების დათვლის მიერ რესურსების მონოპოლიზება).

## კომბინაციების ჯანმრთელობის ავტოპილოტი

`comboHealthAutopilot.ts` არის პროვაიდერის ავტოპილოტის **კომბინაციებისთვის განკუთვნილი** ეკვივალენტი. ის:

- აღმოაჩენს არაჯანსაღ კომბინაციებს
- იძლევა სამიზნეების თანმიმდევრობის შეცვლის რეკომენდაციას
- გვთავაზობს გაუმართავი სამიზნეების გამორთვას
- N წარუმატებლობის შემდეგ ავტომატურად შლის უმოქმედო სამიზნეებს

### კომბინაციის პრობლემების მაგალითები

```
კომბინაცია "always-on" (პრიორიტეტული სტრატეგია)
├─ სამიზნე 1: openai/gpt-5 (ჯანსაღი)
```

## კვოტის მონიტორები

`observability.ts` სააბონენტო პროვაიდერებისთვის (Claude Code, Codex, GitHub Copilot) ხელმისაწვდომს ხდის **თითოეული სესიის კვოტის მონიტორებს**:

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### სტატუსების მნიშვნელობები

| სტატუსი     | როდის                           | UI-ის მოქმედება                                  |
| ----------- | ------------------------------- | ------------------------------------------------ |
| `starting`  | მიმდინარეობს საწყისი გამოკითხვა | ჩატვირთვის ინდიკატორი                            |
| `idle`      | ბოლო დროს აქტივობა არ ყოფილა    | მართვის პანელზე დამალულია                        |
| `healthy`   | დარჩენილია კვოტის > 50%         | მწვანე წერტილი                                   |
| `warning`   | დარჩენილია კვოტის < 50%         | ყვითელი გაფრთხილება                              |
| `exhausted` | კვოტა = 0%                      | წითელი ბლოკი, შემდეგ პროვაიდერზე გადამისამართება |
| `error`     | გამოკითხვა ვერ შესრულდა         | წითელი წერტილი, მალე ხელახლა ცდა                 |

## პრობლემების აღმოფხვრა

### „პროვაიდერი მიუთითებს, რომ გამართულად მუშაობს, მაგრამ მოთხოვნები ვერ სრულდება“

1. შეამოწმეთ **ავტოპილოტის პრობლემები** — შესაძლოა, მოდელი დაბლოკილია
2. კონკრეტული შეცდომის კლასის სანახავად გადახედეთ **ბოლო შეცდომებს**
3. პროვაიდერის ბარათზე სცადეთ **კავშირის ტესტი**
4. შეამოწმეთ, ხომ არ არის პროვაიდერი **ზედა დონეზე სიხშირით შეზღუდული** (ლოკალურად არ ჩანს)

### „კვოტა მიუთითებს, რომ ყველაფერი გამართულადაა, მაგრამ ვხედავ 429 შეცდომებს“

- 429 ნიშნავს, რომ პროვაიდერის მიხედვით თქვენი კვოტა ამოწურეთ
- OmniRoute-ის კვოტის აღრიცხვა შეიძლება **მოძველებული** იყოს — ჭეშმარიტი მონაცემები პროვაიდერთანაა
- კვოტის მონაცემები ავტომატურად ახლდება კვოტის შიდა მონიტორის საშუალებით

### „კომბინაცია ვერ მუშაობს, თუმცა ყველა სამიზნე გამართულად გამოიყურება“

- სამიზნეების მიმდევრობასთან დაკავშირებული პრობლემების სანახავად შეამოწმეთ **კომბინაციის მდგომარეობის** მართვის პანელი
- გადახედეთ **სარეზერვო გადართვის მოვლენებს** — შესაძლოა, კომბინაცია ვარიანტებს ზედმეტად სწრაფად ამოწურავს
- დარწმუნდით, რომ **სტრატეგია** შეესაბამება თქვენს გამოყენების შემთხვევას (პრიორიტეტული, ციკლური ან ავტომატური)

### „მონაცემთა ბაზის მდგომარეობის შემოწმება ვერ სრულდება“

- გაუშვით `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- თუ შედეგია „ok“ — ეს ცრუ განგაშია და მდგომარეობის შემოწმება ზედმეტად მკაცრია
- ნებისმიერი სხვა შედეგის შემთხვევაში — **გააჩერეთ OmniRoute** და მიჰყევით [კატასტროფის შემდეგ აღდგენის სახელმძღვანელოს](./DATABASE_GUIDE.md#disaster-recovery)

### „მეხსიერების გროვაზე დატვირთვა კრიტიკულია“

```bash
# მიმდინარე გროვის შემოწმება

# მეხსიერების ხელით გაწმენდის გაშვება (თუ გამოყენებულია --expose-gc)
```
