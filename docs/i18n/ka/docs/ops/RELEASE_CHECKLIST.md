## npm Trusted Publishing (ნაგულისხმევი v3.8.51-დან) — მოთხოვნის შემთხვევაში ეტაპობრივი, სარეზერვოდ პირდაპირი

`npm-publish.yml` ნაგულისხმევად აქვეყნებს **npm Trusted Publishing-ის (OIDC)** მეშვეობით:
`stage-npm` დავალება (github-hosted) GitHub-ის id-token-ს ამ კონკრეტული გაშვებისთვის
ხანმოკლე npm ავტორიზაციის მონაცემებზე ცვლის — რეპოზიტორიის საიდუმლოებებში აღარ არის
ხანგრძლივად მოქმედი npm ტოკენი, არ ჩნდება 2FA მოთხოვნა და თან ერთვის წარმომავლობის დამადასტურებელი ინფორმაცია.
ეს არის შემოვლითი გზა, რომელსაც npm ახლა უჭერს მხარს, რადგან 2FA-ს გამომტოვებელი ტოკენები
ხმარებიდან ამოიღება; იგი აღადგენს სრულად ავტომატურ პროცესს, რომელიც პროექტს v3.8.48-მდე
ჰქონდა, ამავდროულად კი ინარჩუნებს WS1.3 გარანტიას (გაჟონილი ტოკენი დამოუკიდებლად ვერ გამოაქვეყნებს — ტოკენი საერთოდ არ არსებობს).

**ერთჯერადი დაყენება (მფლობელი):** npmjs.com → პაკეტი `omniroute` → Settings → _Trusted
Publisher_ → GitHub: მფლობელი `diegosouzapw`, რეპოზიტორია `OmniRoute`, სამუშაო პროცესი `npm-publish.yml`
(გარემო: არცერთი). მის შექმნამდე ავტომატური ნაბიჯი დასრულდება `ENEEDAUTH` შეცდომით:
ხელახლა გაუშვით `publish_mode=staged`-ით (ქვემოთ) ან `direct`-ით.

### ეტაპობრივი გამოქვეყნება (მოთხოვნის შემთხვევაში — `publish_mode=staged`)

npm-publish სამუშაო პროცესი პირდაპირ აღარ აქვეყნებს: ის ჩატვირთავს შეფუთულ tarball-ს
(`check:pack-boot`) და შემდეგ გაუშვებს `npm stage publish`-ს — ზუსტად ეს ბაიტები განთავსდება
რეესტრში, თუმცა მფლობელის დამტკიცებამდე **მათი დაყენება შეუძლებელია**. ადამიანის მიერ გასავლელი
2FA ბარიერი მტკიცებულების მიღების შემდეგ გადავიდა და არა მის წინ.

**მფლობელის პროცესი სამუშაო პროცესის წარმატებით დასრულების შემდეგ:**

1. `npm stage list omniroute` — იპოვეთ ეტაპის id (ის ასევე სამუშაო პროცესის შეჯამებაში იბეჭდება).
2. შეამოწმეთ ეტაპობრივად განთავსებული ბაიტები (რეკომენდებულია): `npm stage download <id>`, შემდეგ
   ჩამოტვირთული tarball დროებით პრეფიქსში დააყენეთ და ჩატვირთეთ (`npm run check:pack-boot`
   CI-ში იმავე შეფუთვა→დაყენება→ჩატვირთვის შედეგს ავტომატიზებს).
3. `npm stage approve <id>` — 2FA მოთხოვნა თავად გამოქვეყნებაა. `npm stage reject <id>` უარყოფს მას.
4. გამოქვეყნების შემდგომი დამცავი მექანიზმი: გამოქვეყნების შემდგომი შემმოწმებელი (v3.8.49 გეგმის WS1.4)
   სუფთა კონტეინერში საჯარო რეესტრიდან აყენებს გამოქვეყნებულ ვერსიას და ჩატვირთავს მას.

**საგანგებო სარეზერვო გზა:** `workflow_dispatch` პარამეტრით `publish_mode=direct` აღადგენს
ძველ, დაუყოვნებელ `npm publish`-ს (გამოიყენეთ მხოლოდ მაშინ, თუ თავად ეტაპობრივი გამოქვეყნება
არასწორად მუშაობს; დააფიქსირეთ მიზეზი).

**ერთჯერადი გამკაცრება (მფლობელი, npmjs.com):** `omniroute`-ისთვის Trusted Publisher
მხოლოდ ეტაპობრივ რეჟიმში დააკონფიგურირეთ, რათა გაჟონილმა ხანგრძლივად მოქმედმა ტოკენმა
ვერსად შეძლოს პირდაპირ `npm publish`-ის შესრულება — CI-ს მხოლოდ ეტაპობრივად განთავსება
შეუძლია; გამოშვება მხოლოდ მფლობელის 2FA-ს შეუძლია.

**დაზიანებული არტეფაქტის სამოქმედო გეგმა (უცვლელი):** ნაგულისხმევი დაუყოვნებელი მოქმედებაა
`npm deprecate omniroute@<bad> "<reason> — use <fixed>"` (წუთებში სრულდება და შექცევადია);
`npm unpublish` გამოიყენეთ მხოლოდ 72-საათიან/დამოკიდებულებების არმქონე ფანჯარაში და არასდროს
პირველ ნაბიჯად. Docker: არასდროს გადაწეროთ ვერსიის ტეგი — უკან დაბრუნება ნიშნავს `latest`-ის
ბოლო გამართულ დაიჯესტზე გადამისამართებას.

**Docker Hub-ის `latest` (სავალდებულოა ყოველი სტაბილური SemVer გამოქვეყნებისას):**
`docker-publish` სამუშაო პროცესმა უნდა მიანიჭოს **ორივე** ტეგი, `X.Y.Z` და, როდესაც
`should-promote-latest.sh` დაადასტურებს, რომ ეს უმაღლესი სტაბილური SemVer-ია, `:latest`,
**ერთი და იმავე დაიჯესტით**. დავალების შემდეგ: Hub-ზე `latest`-ის დაიჯესტი ახალი
SemVer-ის დაიჯესტის ტოლი უნდა იყოს და `last_updated` უნდა განახლდეს. არ დატოვოთ `:latest`
ძველ აგებაზე, როცა გამოშვების შენიშვებში აღწერილია შესწორებები, რომლებიც მხოლოდ git-ში
არსებობს. Compose-ის სწრაფი დაწყების მაგალითები `:latest`-ს იყენებს; GitOps-მა კვლავ
`X.Y.Z` უნდა დააფიქსიროს. იხილეთ [Docker-ის გამოშვების არხები](../guides/DOCKER_GUIDE.md#release-channels) და #10317.

## Hotfix-ის სწრაფი ზოლი (ჭდე `hotfix`)

PR, რომელსაც აქვს ჭდე `hotfix`, გამოტოვებს CI-ის მძიმე მატრიცას (9-შარდიანი E2E, დაფარვის ratchet,
quality-gate, quality-extended) და ინარჩუნებს სწრაფ, მაღალი სიგნალის მქონე შემოწმებებს: build,
unit-შარდები, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
და tarball-ის ჩატვირთვის smoke-ტესტი (`check:pack-boot`). მიზანი: ~33 წუთის ნაცვლად მწვანე სტატუსი ≤15 წუთში.

**შესვლის პოლიტიკა — ოთხივე პირობა სავალდებულოა (Chromium/VS Code/Node-ის საგანგებო ზოლების მოდელის მიხედვით):**

1. **სიმძიმე**: production გატეხილია — გამოქვეყნებული არტეფაქტი ჩატვირთვისას ითიშება /
   უსაფრთხოების შესწორებაა საჭირო / რელიზის ყველა მომხმარებელი დაზარალებულია. „მნიშვნელოვანი“ არ ნიშნავს „გატეხილს“.
2. **უფლებამოსილება**: `hotfix` ჭდეს მხოლოდ რეპოზიტორიის მფლობელი ანიჭებს. ჭდე თავად არის
   დამტკიცება — campaign PR-ზე მისი თვითნებურად გამოყენება დაუშვებელია.
3. **მტკიცებულება**: PR-ის აღწერაში მოცემულია ბმული წინა სრულად მწვანე მძიმე გაშვებაზე (პაკეტზე, რომელსაც
   გამოტოვებული დავალებები ხელახლა გადაამოწმებდა), ასევე შესწორების საკუთარ ტესტზე, რომელიც ჯერ ჩავარდა, შემდეგ კი გაიარა.
4. **მოცულობა**: მხოლოდ cherry-pick — მინიმალური შესწორება, refactor-ების და თანმხლები ცვლილებების გარეშე.

გამოტოვებული დაფარვის/ratchet-ის ზედაპირი ხელახლა მოწმდება release-ბრენჩზე შემდეგი სრული გაშვებით
(რელიზის უწყვეტი მწვანე სტატუსი) — ზოლი გამოტოვებს მხოლოდ ლოდინს და არასოდეს ვალიდაციას.

### Hook-ები (შემოწმებულია Husky-ით)

Husky-ის hook-ები მდებარეობს `.husky/`-ში და git ოპერაციებისას ავტომატურად ეშვება.

- **pre-commit:** `npx lint-staged + node scripts/check/check-docs-sync.mjs + npm run check:any-budget:t11`
- **pre-push:** სწრაფი დეტერმინისტული შემოწმებები — `npm run check:any-budget:t11 && npm run check:tracked-artifacts` (გააქტიურდა 2026-06-13). განზრახ გამორიცხავს `test:unit`-ს (ნელია; დაფარულია CI-ის `test-unit` დავალებით).
  - release-ბრენჩების push-მდე ხელით გაუშვით `npm run test:unit`.

თუ hook ჩავარდა: გამოასწორეთ გამომწვევი პრობლემა და ნუ აუვლით გვერდს `--no-verify`-ით.

### ანაწყობის განლაგება

რეპოზიტორია იყენებს სამ განსხვავებულ გამომავალ დირექტორიას — ისინი არასდროს აურიოთ:

| დირექტორია | დანიშნულება                                                        | კონტროლდება?     |
| ---------- | ------------------------------------------------------------------ | ---------------- |
| `src/`     | აპლიკაციის საწყისი კოდი (TypeScript / TSX)                         | დიახ             |
| `.build/`  | ანაწყობის შუალედური ფაილები — `next build`-ის შედეგი (`distDir`)   | არა (gitignored) |
| `dist/`    | გასავრცელებელი npm-პაკეტი — აწყობილია `assembleStandalone`-ის მიერ | არა (gitignored) |

> **ოპერატორის შენიშვნა:** დაშორებულ VPS-ზე image-ის დირექტორიად კვლავ რჩება `/usr/lib/node_modules/omniroute/app/`.
> შეიცვალა მხოლოდ **რეპოზიტორიის შიგნით არსებული** ანაწყობის გამომავალი (`app/` → `dist/`). განთავსების უნარები rsync-ის მეშვეობით
> `dist/`-ის შიგთავსს დაშორებულ `app/` დირექტორიაში აკოპირებს — VPS-ის ბილიკების შეცვლა საჭირო არ არის.

**ერთჯერადი ანაწყობის პროცესი:**

```
npm run build:release
  └─ rm -rf .build dist          (გასუფთავება)
  └─ next build → .build/next/   (შუალედური ფაილები)
  └─ assembleStandalone          (აკოპირებს standalone + static + public + natives → dist/)
  └─ წერს dist/BUILD_SHA-ს       (HEAD-ის საკონტროლო მნიშვნელობა)
```

```bash
npm run release:dry-run-lts-cut                       # რეალური განშტოება: 3.9.0 HEAD-იდან, წინა ტეგი v3.8.59
```

`scripts/release/dry-run-lts-cut.mjs` არაფერს ასრულებს: ის კითხულობს git-სა და `gh`-ს და ბეჭდავს
მთელ თანმიმდევრობას — წინაპირობებს (საწყისი მითითება იძებნება, წინა ტეგი არსებობს, `package.json`
სამიზნე ვერსიას შეიცავს, `release-freeze` საკითხი ღიაა, არსებულ რელიზის განშტოებაზე არ არის ღია
`Release branch not green` საკითხი — არარსებული განშტოება აღინიშნება როგორც `?`, უცნობი, და არასოდეს
როგორც მზად — Mergify-ის `release` რიგი კონფიგურირებულია (G11: `queue_rules`, `checks_timeout`,
ჭდე `queue`), `release/*` წესების ნაკრები კვლავ ბლოკავს წაშლასა და იძულებით push-ს და
`stable/v3` და `develop` ჯერ არ არსებობს), განშტოებების ორ ნაბიჯს, უმოქმედო სამუშაო პროცესების
რომელი ტრიგერები და `if:` პირობები ხდება ჭეშმარიტი (და რომელი რჩება საცავის ცვლადით შეზღუდული ან
კანონიკურ საცავზე მიბმული), მოსალოდნელ dist-tag-ებს (`latest` → 3.9.0, `next` და
`nightly` ცარიელია) და უკუგდებას. გამოსვლის კოდი `0` = `RESULT: READY`, `1` = დამბლოკავი წინაპირობა
ვერ შესრულდა (`✗`), `2` = გამოყენების შეცდომა. `--advisory <id,...>` შემოწმებას გაფრთხილებამდე (`!`)
აქვეითებს მისი დამალვის გარეშე.

რეალური განშტოების საცდელი გაშვება შეასრულეთ, სანამ 3.9.0-ის რელიზის გაყინვა კვლავ აქტიურია —
განშტოებები იქმნება ტეგის შემდეგ და მანამდე, სანამ ფაზა 12c გაყინვას მოხსნის.

`electron/package.json`, `package-lock.json` და `docs/openapi.yaml`. `[4.0.0]`

### PR-ის წინასწარი ნახვის არტეფაქტი (ერთხელ ააწყვეთ, შემდეგ იგივე ბაიტები გადაიტანეთ)

`.github/workflows/preview-artifact.yml` PR-ის ბოლო კომიტიდან ერთ საწარმოო tarball-ს აწყობს და
ზუსტად ამ ანაწყობს ამოწმებს (#8084-ის ნაწილი (a)). მხოლოდ იმავე საცავის PR-ებისთვის; არაფერი ქვეყნდება.

```bash
gh workflow run preview-artifact.yml -f pr_number=<N>   # ან დაამატეთ `preview-artifact` ჭდე
gh run download <run-id> --name preview-artifact-pr<N>-<sha7> --dir preview
cd preview && sha256sum -c SHA256SUMS
gh attestation verify omniroute-*.tgz --repo diegosouzapw/OmniRoute
npm install -g ./omniroute-*.tgz                          # წინასწარი ვერსიის ინსტალაცია
```

გაშვება ასრულებს `npm ci`, `npm run build:release`, `npm run check:pack-artifact` ბრძანებებს, ფუთავს
tarball-ს, ასრულებს `npm run check:pack-boot`-ს (ყალბი საიდუმლოებები, დროებითი მონაცემთა დირექტორია), ხელახლა
ფუთავს და შეცდომით სრულდება, თუ დაიჯესტი იდენტური არ არის; შემდეგ იწერს `artifact-identity.json`-ს (ბოლო კომიტის SHA,
საბაზისო SHA, lockfile-ის ჰეში, პლატფორმა, არქიტექტურა, node ABI, ბანდლერი, აწყობის პოლიტიკა —
`scripts/release/artifact-identity.mjs`) და ცალკე დავალებაში ადასტურებს tarball-ს. წინასწარი ვერსიის
გადატანა ნიშნავს ამ tarball-ის ინსტალაციას: წყაროდან ხელახლა არასოდეს ააწყოთ.

### განშტოება (3.9.0, GO-ს შემდეგ)

1. GO ჩაწერილია [LTS_GO_NO_GO.md](./LTS_GO_NO_GO.md)-ში.
2. `npm run release:dry-run-lts-cut -- --from v3.9.0` ბეჭდავს `RESULT: READY`-ს.
3. შექმენით განშტოებები `origin`-ზე ხელით, საცდელი გაშვების მიერ დაბეჭდილი ბრძანებებით —
   სკრიპტი უარს ამბობს `origin`-ზე push-ის შესრულებაზე. მიმოხილული develop კომიტის ხელახლა გამოსაყენებლად ჯერ
   გაუშვით `--execute`-ით რეპეტიცია 3.9.0-ის ბოლო კომიტზე თქვენი ფორკის მიმართ; იგი ორივე SHA-ს დაბეჭდავს და
   იგივე კომიტების push შეიძლება:

   ```bash
   git push origin <stable-sha>:refs/heads/stable/v3 <develop-sha>:refs/heads/develop
   ```

4. დაიცავით `stable/v3` და `develop` (წესების ნაკრებები + შერწყმის რიგი), სანამ პირველი PR გაერთიანდება.
5. უმოქმედო სამუშაო პროცესები განშტოებების არსებობისას ჩაირთვება: `forward-port.yml` (`stable/v3`-ზე
   push), `validate-stable-pr.yml` (`stable/v3`-ისკენ მიმართული PR-ები) და `nightly-v4-build.yml`
   (`develop`-ს აწყობს). ამოქმედებამდე დააყენეთ საცავის საიდუმლო `secrets.FORWARD_PORT_TOKEN` (რათა CI
   გაეშვას შემდგომ ვერსიაში გადატანის PR-ებზე); ღამის ვერსიის გამოქვეყნება გამორთული რჩება, სანამ მფლობელი
   საცავის ცვლად `vars.NIGHTLY_PUBLISH`-ს `true`-ზე არ დააყენებს და npm Trusted Publishing
   `nightly-v4-build.yml`-ს არ მიიღებს. არხის განსაზღვრას ასრულებს `scripts/release/dist-tag.mjs`,
   იგივე განმსაზღვრელი, რომელსაც `npm-publish.yml` იყენებს.
6. გადაამოწმეთ არხები: `npm view omniroute dist-tags --json` აჩვენებს `latest` = 3.9.0-ს და არ აჩვენებს
   `next` / `nightly`-ს, სანამ v4 არ გამოქვეყნდება.
7. საჭიროების შემთხვევაში უკუგდება: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   და `npm dist-tag add omniroute@3.8.59 latest`.
