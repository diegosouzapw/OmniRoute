გამოიყენეთ ეს სახელმძღვანელო pull request-ისთვის უმცირესი საიმედო განვითარების ციკლის ასარჩევად. ის არ
ანაცვლებს ქვემოთ მითითებულ, კონკრეტული სფეროს არქიტექტურისა და უსაფრთხოების დოკუმენტებს; ის თითოეულ გავრცელებულ
ცვლილების ტიპს აკავშირებს მის კონტრაქტებთან, მიზნობრივ შემოწმებებთან და CI დაფარვასთან.

## გზა, რომელსაც ყოველი ცვლილება გადის

1. **რედაქტირებამდე აირჩიეთ საბაზისო branch.** იპოვეთ უმაღლესი აქტიური `release/v*` branch და შექმენით ახალი branch
   მისი ბოლო commit-იდან. სამიზნედ აირჩიეთ ეს branch და არა `main`. თუ აქტიურია რელიზის გაყინვა, სამიზნედ არ აირჩიოთ გაყინული
   branch; გამოიყენეთ შემდეგი აქტიური ციკლი, რომელიც აღწერილია
   [Branching & Release Model](BRANCHING_MODEL.md)-ში.
2. **დაასახელეთ კონტრაქტები.** განსაზღვრეთ ყველა კატალოგი, სქემა, გენერირებული არტეფაქტი, საჯარო API ან მომხმარებლის
   ინტერფეისი, რომელზეც ცვლილება მოქმედებს. ქვემოთ მოცემულ ცხრილში მითითებულია მინიმალური საწყისი ნაკრები.
3. **დაწერეთ ან განაახლეთ მიზნობრივი ტესტები.** საწარმოო ცვლილებები `src/`, `open-sse/`, `electron/` ან
   `bin/`-ში იმავე PR-ში ავტომატიზებულ ტესტს მოითხოვს. გაუშვით უმცირესი სატესტო ფაილები, რომლებიც ამ ქცევას
   ადასტურებს, შემდეგ კი — ჩამოთვლილი მიზნობრივი საკონტროლო ეტაპები.
4. **ფართო მატრიცის გაშვება CI-ს მიანდეთ.** PR-ზე გაეშვება unit shards-ის სრული ნაკრები, Vitest, coverage ratchet და
   საწარმოო build. ფართო ნაკრები ლოკალურად გაუშვით მხოლოდ მაშინ, როდესაც მიზნობრივი შემოწმების მარცხი
   უფრო ფართო გავლენაზე მიუთითებს ან ცვლილება რამდენიმე ქვესისტემას მოიცავს.
5. **მიმოხილვამდე შეათანხმეთ ცვლილებები.** ჩამოტვირთეთ აქტიური საბაზისო branch, შეამოწმეთ მისი ახალი commit-ები და თქვენი diff
   მასთან მიმართებით, შემდეგ კი contributor workflow-ის შესაბამისად შეასრულეთ rebase ან merge. გენერირებული ფაილებისა
   და კატალოგების კონფლიქტები მათი წყაროდან მოაგვარეთ, ხელახლა დააგენერირეთ ისინი, ხელახლა გაუშვით მიზნობრივი ციკლი და
   დაადასტურეთ, რომ PR კვლავ აქტიურ release branch-ზეა მიმართული.
6. **დააფიქსირეთ მტკიცებულებები.** PR-ის შაბლონში ჩამოთვალეთ გაშვებული ბრძანებები, ყველა დამატებული ან შეცვლილი სატესტო ფაილი,
   მიგრაციები ან feature flag-ები და ნებისმიერი მხოლოდ CI-ზე შესასრულებელი ვალიდაცია, რომელიც ჯერ კიდევ მოლოდინშია.

## ძირითადი გზები ცვლილების ტიპის მიხედვით

ქვემოთ მოცემული ბრძანებები მინიმალური მიზნობრივი შემოწმებებია და არა იმ ტესტის გამოტოვების ნებართვა, რომელიც უშუალოდ ფარავს
თქვენ მიერ შეცვლილ ქცევას.

### პროვაიდერი

**კონტრაქტები**

- პროვაიდერის განსაზღვრება `src/shared/constants/providers/`-ში და მისი კომპოზიცია
  `src/shared/constants/providers.ts`-ში.
- მოდელები და შესაძლებლობები `open-sse/config/providerRegistry.ts`-ში ან მისგან გამოყოფილ რეესტრის ფაილებში.
- Executor/translator-ის არჩევა, OAuth-ის ან API key-ის კონფიგურაცია, dashboard-ის რესურსები და, საჭიროების შემთხვევაში,
  გენერირებული პროვაიდერის ცნობარი.
- საჯარო ავტორიზაციის მონაცემებმა უნდა გამოიყენოს `resolvePublicCred()`; შეცდომის პასუხებმა უნდა გამოიყენოს საზიარო გასუფთავებული
  შეცდომების დამხმარე ფუნქციები. იხილეთ `docs/security/PUBLIC_CREDS.md` (git; `/docs`-ში არ კომპილირდება) და
  [შეცდომების გასუფთავება](../security/ERROR_SANITIZATION.md).

**მიზნობრივი ციკლი**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # როდესაც კატალოგი იცვლება; შეიტანეთ გენერირებული diff commit-ში
npm run lint
```

ასევე შეამოწმეთ ყველა მოთხოვნის ოჯახი, რომელსაც ცვლილება შეეხო: chat, Responses, images, embeddings, audio ან video.
განიხილეთ გენერირებული კატალოგისა და golden diff-ების ცვლილებები, როგორც კონტრაქტის ცვლილებები; ნუ მიიღებთ მათ
ბრმად.

### მარშრუტიზაცია

**კონტრაქტები**

- საჯარო სტრატეგიის მნიშვნელობები და UI მეტამონაცემები `src/shared/constants/routingStrategies.ts`-ში.
- განაწილება და მიმდევრობა `open-sse/services/combo.ts`-ისა და `open-sse/services/combo/`-ის ქვეშ.
- Combo სქემები, მუდმივი შენახვა, მდგრადობის მდგომარეობა, მოდელის შესაძლებლობები და API/UI მართვის ელემენტები.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) და მდგრადობის დოკუმენტაცია ქცევის ცვლილებისას.

**მიზნობრივი ციკლი**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # სტრატეგიის ან განაწილების ცვლილებები
npm run check:known-symbols      # სტრატეგიის რეგისტრაციის ცვლილებები
npm run lint
```

ლოკალურად გამოიყენეთ დეტერმინისტული ტესტები იმიტირებული upstream-ით. Combo-ს ცოცხალი smoke ტესტები ავტორიზაციის მონაცემებს
მოითხოვს და ხელით სრულდება; ისინი CI-ის შემცვლელი არ არის.

### UI / UX

**კონტრაქტები**

- Next.js-ის route/page და საზიარო კომპონენტების საზღვრები `src/app/`-ისა და
  `src/shared/components/`-ის ქვეშ.
- API პასუხების ფორმები, ჩატვირთვის/ცარიელი/შეცდომის მდგომარეობები, კლავიატურისა და ეკრანის წამკითხველის ქცევა,
  ადაპტიური განლაგება, თემები და locale-ების გაფართოება.
- ინგლისური UI-ის საწყისი სტრიქონები `src/i18n/messages/en.json`-ში; არ ჩაწეროთ ახალი მომხმარებლისთვის განკუთვნილი ტექსტი პირდაპირ კოდში.

**მიზნობრივი ციკლი**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ინტერაქციის ან ვიზუალური ცვლილებებისთვის გაუშვით აპლიკაცია და შეამოწმეთ როგორც ვიწრო, ისე ფართო viewport-ები. CI გაუშვებს
საწარმოო build-სა და უფრო ფართო ნაკრებებს; ვიზუალურ ქცევას მაინც სჭირდება ცვლილების შესაბამისი მიზნობრივი კომპონენტის ტესტი, Playwright
ან დოკუმენტირებული ხელით შემოწმება.

### i18n

**კონტრაქტები**

- `src/i18n/messages/en.json` არის UI-ის წყარო; `config/i18n.json` არის locale-ების წყარო.
- CLI კატალოგები ცალკე ინახება `bin/cli/locales/`-ის ქვეშ.
- ზუსტად შეინარჩუნეთ ICU placeholder-ები და tag-ები. არ თარგმნოთ პროდუქტის/პროვაიდერის/მოდელის სახელები,
  პროტოკოლისა და header-ის სახელები, ბრძანებები, კოდის/JSON-ის იდენტიფიკატორები, URL-ები, გარემოს ცვლადები ან
  დაცული ტერმინები, როგორიცაა `OmniRoute`, `OAuth`, `MCP` და `A2A`. მიმდინარე საწყისი სიაა
  `scripts/i18n/glossary/protected-terms.json`.

**მიზნობრივი ციკლი**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # როდესაც CLI-ის სტრიქონები/კატალოგები იცვლება
npm run lint
```

ეს არის არსებული სისტემის სახელმძღვანელო და არა მისი ხელსაწყოების ან key მოდელის გაფართოების მოწოდება.
სანამ შემცვლელი სისტემა მუშავდება, i18n patch-ები მინიმალური და ზუსტი უნდა იყოს. არ გაუშვათ თარგმნის
ბრძანებები, რომლებიც გარე სერვისებს მიმართავს, თუ დავალება პირდაპირ არ მოითხოვს გენერირებულ თარგმანებს და
მიღებული diff არ შეგიმოწმებიათ.

### CLI

**კონტრაქტები**

- საჯარო ბრძანებები და ალმები `bin/cli/`-ში, გენერირებული API ბრძანებები, გამოსვლის კოდები, stdout/stderr და
  JSON გამოტანის სტრუქტურები, კონფიგურაციის/გარემოს ქცევა და პაკეტში შემავალი ფაილები.
- CLI-ის მომხმარებლისთვის ხილული სტრიქონები უნდა იყენებდეს CLI i18n ფენას, ხოლო `en`/`pt-BR` კატალოგები სინქრონიზებული უნდა დარჩეს.
- შეინარჩუნეთ Node, როგორც მხარდაჭერილი შესრულების გარემო, და გამოქვეყნებული ბინარული კონტრაქტი.

**ფოკუსირებული ციკლი**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # გენერირებული/ერთ პაკეტად გაერთიანებული CLI-ის ცვლილებები
npm run check:pack-policy     # პაკეტის საჯარო ზედაპირის ცვლილებები
npm run lint
```

გამოიყენეთ ზუსტი ბრძანება დროებით მონაცემთა დირექტორიაში, როდესაც ქცევა დამოკიდებულია დამუშავებაზე, ფაილებზე ან გამოსვლის
სტატუსზე. CI ასრულებს პაკეტის არტეფაქტებისა და ეკოსისტემის უფრო ფართო შემოწმებებს.

### მონაცემთა ბაზა

**კონტრაქტები**

- დომენის მოდულები მდებარეობს `src/lib/db/`-ში; პირდაპირ შემოიტანეთ კონკრეტული მოდულები (ძველი `localDb.ts` რეექსპორტის ფენა წაიშალა).
- დანომრილი, იდემპოტენტური SQL მიგრაციები `src/lib/db/migrations/`-ში, ტრანზაქციების უსაფრთხოება, განახლების
  ქცევა, ინდექსები და სქემით გავლენილი ყველა გამომძახებელი.
- მარშრუტები და დამმუშავებლები არასოდეს უშვებენ დაუმუშავებელ SQL-ს პირდაპირ.

**ფოკუსირებული ციკლი**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

მიგრაციის დამატებისას შეამოწმეთ როგორც ახალი მონაცემთა ბაზა, ისე წინა სქემიდან განახლება. მონაცემთა ბაზის ტესტებმა
უნდა დახუროს დესკრიპტორები და გასუფთავებისას გამოიძახოს `resetDbInstance()`. გაუშვით `npm run test:bun:db` მხოლოდ მაშინ, როდესაც
იცვლება Bun ადაპტერის შეზღუდული მხარდაჭერის გზა; Node კვლავ ავტორიტეტულია.

### აგება / განთავსება

**კონტრაქტები**

- ძირითადი და სამუშაო სივრცის მანიფესტები/ჩაკეტვის ფაილი, `scripts/build/`, Next.js-ის ავტონომიური ასამბლეა, `dist/`
  პაკეტის შიგთავსი, Electron-ის პლატფორმის მეტამონაცემები, CI სამუშაო პროცესები და განთავსების საკონტროლო ნიშნულები.
- Node-ის მხარდაჭერილი დიაპაზონები და `CLAUDE.md`-ში Bun-ის ნებადართული გამოყენება ხელუხლებელი უნდა დარჩეს.
- აგების არტეფაქტები ვერსიების კონტროლში არ უნდა მოხვდეს; მოქმედებს დამოკიდებულებების, ლიცენზიების, სამუშაო პროცესებისა და პაკეტების პოლიტიკები.

**ფოკუსირებული ციკლი**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # დამოკიდებულების ან ჩაკეტვის ფაილის ცვლილებები
npm run check:pack-policy      # გამოქვეყნებული პაკეტის საჯარო ზედაპირის ცვლილებები
npm run lint
```

ლოკალურად გამოიყენეთ `npm run build` მხოლოდ მაშინ, როდესაც ცვლილება გავლენას ახდენს კომპილაციაზე, ავტონომიურ ასამბლეაზე, რესურსებზე
ან შესრულების გარემოს ერთ პაკეტად გაერთიანებაზე. გამოიყენეთ `npm run build:release` მხოლოდ გამოშვების/განთავსების ვალიდაციისთვის. CI-ის აგება
საბოლოო კროსპლატფორმული სიგნალია; Electron-ის პლატფორმისთვის სპეციფიკურ ცვლილებებს სჭირდება შესაბამისი ფოკუსირებული აგების
ან სწრაფი შემოწმების მტკიცებულება.

წარმატებით დასრულდება. ამავდროულად, ნუ აიძულებთ ყველა ლოკალურ ცვლილებას დაელოდოს რეპოზიტორიის სრულ მატრიცას.

## შეჯერების საკონტროლო სია

review-ის მოთხოვნამდე:

- დარწმუნდით, რომ PR-ის საბაზო branch კვლავ ყველაზე მაღალი აქტიური `release/v*` branch-ია.
- ჩამოტვირთეთ ეს საბაზო branch და გადახედეთ commit-ებს, რომლებიც თქვენი branch-ის შექმნის შემდეგ დაემატა.
- შემთხვევითი ან გენერირებული ზედმეტი ცვლილებების გამოსავლენად გადახედეთ `git diff <active-base>...HEAD`-ს.
- კატალოგისა და გენერირებული დოკუმენტების კონფლიქტები მოაგვარეთ წყაროს განახლებითა და output-ის ხელახლა გენერირებით.
- შეჯერების შემდეგ ხელახლა გაუშვით PR-ის აღწერაში ჩამოთვლილი ყველა ფოკუსირებული ტესტი/გეითი.
- არასოდეს შეასუსტოთ assertion-ები ან ამოიღოთ აუცილებელი ტესტები მხოლოდ გადაადგილებულ საბაზო branch-თან შესაბამისობისთვის.

release freeze-ისა და retargeting-ის წესებისთვის გამოიყენეთ
[Branching & Release Model](BRANCHING_MODEL.md). CI-ის სრული ინვენტარისთვის გამოიყენეთ
[Quality Gates Reference](../architecture/QUALITY_GATES.md).
