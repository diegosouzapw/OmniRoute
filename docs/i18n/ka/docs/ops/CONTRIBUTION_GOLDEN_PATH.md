გამოიყენეთ ეს სახელმძღვანელო pull request-ისთვის უმცირესი საიმედო დეველოპმენტის ციკლის ასარჩევად. ის არ
ანაცვლებს ქვემოთ მითითებულ, კონკრეტული სფეროს არქიტექტურისა და უსაფრთხოების დოკუმენტებს; ის ცვლილებების
თითოეულ გავრცელებულ ტიპს მის კონტრაქტებთან, მიზნობრივ შემოწმებებთან და CI დაფარვასთან აკავშირებს.

## გზა, რომელსაც ყველა ცვლილება გადის

1. **რედაქტირებამდე აირჩიეთ საბაზისო ბრენჩი.** იპოვეთ ყველაზე მაღალი აქტიური `release/v*` ბრენჩი და შექმენით
   ახალი ბრენჩი მისი ბოლო კომიტიდან. სამიზნედ მიუთითეთ ეს ბრენჩი და არა `main`. თუ რელიზის გაყინვა მოქმედებს, სამიზნედ ნუ მიუთითებთ გაყინულ
   ბრენჩს; გამოიყენეთ შემდეგი აქტიური ციკლი, რომელიც აღწერილია
   [ბრენჩინგისა და რელიზების მოდელში](BRANCHING_MODEL.md).
2. **დაასახელეთ კონტრაქტები.** განსაზღვრეთ ყველა კატალოგი, სქემა, გენერირებული არტეფაქტი, საჯარო API ან მომხმარებლის
   ინტერფეისი, რომელზეც ცვლილება მოქმედებს. ქვემოთ მოცემული ცხრილი მინიმალურ საწყის ნაკრებს გიჩვენებთ.
3. **დაწერეთ ან განაახლეთ მიზნობრივი ტესტები.** საწარმოო ცვლილებები `src/`, `open-sse/`, `electron/` ან
   `bin/` დირექტორიებში იმავე PR-ში ავტომატიზებულ ტესტს საჭიროებს. გაუშვით უმცირესი სატესტო ფაილები, რომლებიც
   ქცევას ადასტურებს, შემდეგ კი — ჩამოთვლილი მიზნობრივი შემოწმებები.
4. **ფართო მატრიცის გაშვება CI-ს მიანდეთ.** PR-ზე სრულდება unit-ტესტების სრული შარდები, Vitest, დაფარვის ზღურბლის შემოწმება და
   საწარმოო build. ფართო ნაკრები ლოკალურად მხოლოდ მაშინ გაუშვით, როდესაც მიზნობრივი შემოწმების წარუმატებლობა
   უფრო ფართო გავლენაზე მიუთითებს ან ცვლილება რამდენიმე ქვესისტემას მოიცავს.
5. **რევიუმდე მოახდინეთ სინქრონიზაცია.** ჩამოტვირთეთ აქტიური საბაზისო ბრენჩი, შეამოწმეთ მისი ახალი კომიტები და მასთან შედარებით თქვენი diff,
   შემდეგ კი კონტრიბუტორის სამუშაო პროცესის შესაბამისად გააკეთეთ rebase ან merge. გენერირებული ფაილებისა
   და კატალოგების კონფლიქტები მათი წყაროდან მოაგვარეთ, ხელახლა დააგენერირეთ ისინი, თავიდან გაუშვით მიზნობრივი ციკლი და დაადასტურეთ, რომ
   PR-ის სამიზნე კვლავ აქტიური რელიზის ბრენჩია.
6. **დააფიქსირეთ მტკიცებულებები.** PR-ის შაბლონში ჩამოწერეთ გაშვებული ბრძანებები, ყველა დამატებული ან შეცვლილი სატესტო ფაილი,
   მიგრაციები ან ფუნქციური ალმები და მხოლოდ CI-ში შესასრულებელი ნებისმიერი ვალიდაცია, რომელიც ჯერ კიდევ მოლოდინშია.

## რეკომენდებული გზები ცვლილების ტიპის მიხედვით

ქვემოთ მოცემული ბრძანებები მინიმალური მიზნობრივი შემოწმებებია და არა ნებართვა, გამოტოვოთ ტესტი, რომელიც უშუალოდ ფარავს
თქვენ მიერ შეცვლილ ქცევას.

### პროვაიდერი

**კონტრაქტები**

- პროვაიდერის განსაზღვრება `src/shared/constants/providers/`-ში და მისი კომპოზიცია
  `src/shared/constants/providers.ts`-ში.
- მოდელები და შესაძლებლობები `open-sse/config/providerRegistry.ts`-ში ან მისგან გამოყოფილ რეესტრის ფაილებში.
- Executor/translator-ის შერჩევა, OAuth-ის ან API-გასაღების კონფიგურაცია, დეშბორდის რესურსები და, საჭიროების შემთხვევაში, გენერირებული
  პროვაიდერის ცნობარი.
- საჯარო ავტორიზაციის მონაცემებმა უნდა გამოიყენოს `resolvePublicCred()`; შეცდომის პასუხებმა კი — საერთო სანიტიზებული
  შეცდომების დამხმარე ფუნქციები. იხილეთ `docs/security/PUBLIC_CREDS.md` (git-შია; `/docs`-ში არ კომპილირდება) და
  [შეცდომების სანიტიზაცია](../security/ERROR_SANITIZATION.md).

**მიზნობრივი ციკლი**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # როდესაც კატალოგი იცვლება; დააკომიტეთ გენერირებული diff
npm run lint
```

ასევე შეამოწმეთ მოთხოვნების ყველა შესაბამისი ოჯახი: chat, Responses, images, embeddings, audio ან video.
გენერირებული კატალოგისა და golden diff-ების რევიუ განახორციელეთ როგორც კონტრაქტის ცვლილებებისა; ბრმად ნუ მიიღებთ მათ.

### მარშრუტიზაცია

**კონტრაქტები**

- საჯარო სტრატეგიის მნიშვნელობები და UI-ის მეტამონაცემები `src/shared/constants/routingStrategies.ts`-ში.
- დისპეტჩერიზაცია და თანმიმდევრობა `open-sse/services/combo.ts`-სა და `open-sse/services/combo/`-ში.
- Combo-ს სქემები, მუდმივი შენახვა, მდგრადობის მდგომარეობა, მოდელის შესაძლებლობები და API/UI მართვის ელემენტები.
- [Auto-Combo ძრავა](../routing/AUTO-COMBO.md) და მდგრადობის დოკუმენტაცია, როდესაც ქცევა იცვლება.

**მიზნობრივი ციკლი**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # სტრატეგიის ან დისპეტჩერიზაციის ცვლილებები
npm run check:known-symbols      # სტრატეგიის რეგისტრაციის ცვლილებები
npm run lint
```

ლოკალურად გამოიყენეთ დეტერმინისტული ტესტები იმიტირებული upstream-ით. ცოცხალი combo smoke-ტესტები ავტორიზაციის მონაცემებს საჭიროებს და
ხელით სრულდება; ისინი CI-ის შემცვლელი არ არის.

### UI / UX

**კონტრაქტები**

- Next.js-ის მარშრუტის/გვერდისა და საზიარო კომპონენტების საზღვრები `src/app/`-სა და
  `src/shared/components/`-ში.
- API-ის პასუხების ფორმები, ჩატვირთვის/ცარიელი/შეცდომის მდგომარეობები, კლავიატურისა და ეკრანის წამკითხველის ქცევა,
  ადაპტიური განლაგება, თემები და ლოკალების გაფართოება.
- ინგლისური UI-ის საწყისი სტრიქონები `src/i18n/messages/en.json`-ში; მომხმარებლისთვის ხილული ახალი ტექსტი პირდაპირ კოდში არ ჩაწეროთ.

**მიზნობრივი ციკლი**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

ინტერაქციის ან ვიზუალური ცვლილებებისას გაუშვით აპლიკაცია და შეამოწმეთ როგორც ვიწრო, ისე ფართო viewport-ები. CI უშვებს
საწარმოო build-სა და უფრო ფართო ნაკრებებს; ვიზუალურ ქცევას მაინც სჭირდება ცვლილების შესაბამისი მიზნობრივი კომპონენტის ტესტი, Playwright-ის ტესტი
ან დოკუმენტირებული ხელით შემოწმება.

### i18n

**კონტრაქტები**

- `src/i18n/messages/en.json` UI-ის წყაროა; `config/i18n.json` კი — ლოკალების წყარო.
- CLI-ის კატალოგები ცალკე, `bin/cli/locales/`-ში ინახება.
- ICU-ის ჩანაცვლების ნიშნები და ტეგები ზუსტად შეინარჩუნეთ. არ თარგმნოთ პროდუქტის/პროვაიდერის/მოდელის სახელები,
  პროტოკოლისა და სათაურების სახელები, ბრძანებები, კოდის/JSON-ის იდენტიფიკატორები, URL-ები, გარემოს ცვლადები ან
  დაცული ტერმინები, როგორიცაა `OmniRoute`, `OAuth`, `MCP` და `A2A`. მიმდინარე საწყისი სია არის
  `scripts/i18n/glossary/protected-terms.json`.

## ლოკალური კანდიდატის ციკლი

საწყისი კოდის ტესტები ვერ დაამტკიცებს, რომ შეფუთული არტეფაქტი წარმატებით გაეშვება: შეფუთვის სიებთან, ამოღებულ დამოკიდებულებებთან
და ნატიურ ბინარულ ფაილებთან დაკავშირებული შეცდომები მხოლოდ tarball-ის დაყენებისა და გაშვების შემდეგ ვლინდება. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) არის RFC #8084-ში აღწერილი ერთხელ აგების / ვალიდაციის / დაწინაურების პროცესის
ლოკალური მხარე: ის აგებს ერთ კანდიდატს, ამოწმებს ზუსტად ამ არტეფაქტს, დირექტორიების
სახელების გადარქმევით აწინაურებს მას და უკან აბრუნებს, თუ დაწინაურებული სლოტი ჯანმრთელობის შემოწმებას ვერ გაივლის.

```bash
npm run dev:candidate -- run --dry-run --json  # გეგმის გამოტანა, არაფრის შეცვლის გარეშე
npm run dev:candidate -- run                   # აგება + ვალიდაცია + დაწინაურება, ავტომატური უკან დაბრუნებით
npm run dev:candidate -- build                 # npm pack + დაყენება _artifacts/candidate/<id>/-ში
npm run dev:candidate -- validate --id <id>    # გაშვება თავისუფალ პორტზე, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current-ისა და previous-ის ადგილების გაცვლა
npm run dev:candidate -- run --from-tarball <file.tgz>  # სხვაგან აგებული tarball-ის ხელახლა გამოყენება (CI)
```

- **ერთხელ ააგეთ.** `build` აფუთავს მიმდინარე ხეს (მას სჭირდება `dist/server.js`, ამიტომ ჯერ გაუშვით
  `npm run build:release`) ან აკოპირებს `--from-tarball`-ს, შემდეგ კი tarball-ს იზოლირებულ npm პრეფიქსში
  აყენებს, რადგან tarball არ შეიცავს `node_modules`-ს. id არის მოკლე `HEAD`
  sha (`-dirty`, როდესაც ხეში ლოკალური ცვლილებებია) ან `tgz-<sha256>` tarball-ისთვის. უკვე
  აგებული სუფთა id ხელახლა გამოიყენება თავიდან აგების ნაცვლად; მის თავიდან ასაგებად მიუთითეთ `--force`.
- **შეამოწმეთ პაკეტი და არა საწყისი კოდი.** `validate` ახლად შექმნილი
  `DATA_DIR=<candidate>/data`-ით, ყალბი საიდუმლო მნიშვნელობებით და გარემოდან ამოღებული ოპერატორის
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` და `INITIAL_PASSWORD` ცვლადებით უშვებს დაყენებულ CLI-ს
  (`serve --port <free port>`), რათა შეამოწმოს ახალი ინსტალაციის გასაღების გარეშე loopback-ზე მუშაობის რეჟიმი. ის ელოდება,
  რომ `GET /api/health` დააბრუნებს 200-ს, მოითხოვს, რომ `GET /v1/models`-მაც დააბრუნოს 200, აჩერებს პროცესების ჯგუფს
  და შედეგს tarball-ის ჰეშთან ერთად `validation.json`-ში იწერს.
- **დააწინაურეთ იგივე არტეფაქტი.** `promote` უარს ამბობს კანდიდატზე, რომელსაც თავისი
  მიმდინარე tarball-ის ჰეშისთვის წარმატებული ვალიდაცია არ აქვს. ნაგულისხმევი აქტიური სლოტია `_artifacts/candidate/current`; `--target <dir>`
  იმავე ფაილურ სისტემაში სხვა დირექტორიას ირჩევს, ხოლო მისი წინა სლოტია `<dir>.previous`.
  სახელის თითოეული გადარქმევა ატომურია, ხოლო პროცესის შუაში წარმოქმნილი შეცდომის შემთხვევაში უკვე შესრულებული გადარქმევები უკუმიმართულებით სრულდება.
- **უკან დააბრუნეთ.** `run` დაწინაურებულ სლოტს ხელახლა ამოწმებს და, თუ ეს შემოწმება ვერ გაიარა,
  `current`-სა და `previous`-ს ადგილებს უცვლის. კანდიდატი, რომელიც პირველ ვალიდაციას ვერ გაივლის, არასოდეს დაწინაურდება.

ყველაფერი იწერება git-ის მიერ იგნორირებულ `_artifacts/candidate/`-ში; OmniRoute-ის არსებულ
ინსტალაციასა და მის მონაცემთა დირექტორიას ცვლილება არასოდეს შეეხება. დაწინაურებული CLI არის
`_artifacts/candidate/current/prefix/bin/omniroute`; გამოყენებისას გაუშვით ის თქვენი საკუთარი `DATA_DIR`-ით.
გასვლის კოდები: `0` — წარმატება, `1` — წარუმატებელი ვალიდაცია ან დაწინაურება, `2` — გამოყენების შეცდომა ან არარსებული აგება.

წარმატებით დასრულდება. ამასთანავე, ნუ აიძულებთ ყოველ ლოკალურ ცვლილებას, დაელოდოს რეპოზიტორიის სრულ მატრიცას.

## შეჯერების საკონტროლო სია

მიმოხილვის მოთხოვნამდე:

- დაადასტურეთ, რომ PR-ის საბაზისო ტოტი კვლავ ყველაზე მაღალი აქტიური `release/v*` ტოტია.
- მიიღეთ ამ საბაზისო ტოტის განახლებები და მიმოიხილეთ კომიტები, რომლებიც თქვენი ტოტის შექმნის შემდეგ დაემატა.
- შეამოწმეთ `git diff <active-base>...HEAD` შემთხვევითი ან გენერირებული ზედმეტი ცვლილებების გამოსავლენად.
- კატალოგისა და გენერირებული დოკუმენტების კონფლიქტები მოაგვარეთ წყაროს განახლებითა და შედეგის ხელახლა გენერირებით.
- შეჯერების შემდეგ ხელახლა გაუშვით PR-ის აღწერაში ჩამოთვლილი ყველა ფოკუსირებული ტესტი/ბარიერი.
- არასოდეს შეასუსტოთ მტკიცებები და არ ამოიღოთ სავალდებულო ტესტები მხოლოდ იმისთვის, რომ გადაადგილებულ საბაზისო ტოტს მოერგოთ.
