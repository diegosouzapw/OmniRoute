## 1. VM-ის კონფიგურაცია

### 1.1 ინსტანციის შექმნა

თქვენთვის სასურველ VPS-პროვაიდერთან:

- აირჩიეთ Ubuntu 24.04 LTS
- აირჩიეთ მინიმალური გეგმა (1 vCPU / 1 GB RAM)
- დააყენეთ ძლიერი root-პაროლი ან დააკონფიგურირეთ SSH-გასაღები
- ჩაინიშნეთ **საჯარო IP** (მაგ., `203.0.113.10`)

### 1.2 SSH-ით დაკავშირება

```bash
ssh root@203.0.113.10
```

### 1.3 სისტემის განახლება

```bash
apt update && apt upgrade -y
```

### 1.4 Docker-ის დაყენება

```bash
# დამოკიდებულებების დაყენება
apt install -y ca-certificates curl gnupg

# Docker-ის ოფიციალური რეპოზიტორიის დამატება
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $ (. /etc/os-release && echo "$VERSION_CODENAME") stable" | tee /etc/apt/sources.list.d/docker.list > /dev/null
apt update
apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
```

### 1.5 nginx-ის დაყენება

```bash
apt install -y nginx
```

### 1.6 Firewall-ის (UFW) კონფიგურაცია

```bash
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp    # SSH
ufw allow 80/tcp    # HTTP (გადამისამართება)
ufw allow 443/tcp   # HTTPS
ufw enable
```

> **რჩევა**: მაქსიმალური უსაფრთხოებისთვის 80 და 443 პორტებზე წვდომა მხოლოდ Cloudflare-ის IP-ებისთვის შეზღუდეთ. იხილეთ განყოფილება [გაფართოებული უსაფრთხოება](#advanced-security).

## 2. OmniRoute-ის დაყენება

### 2.1 კონფიგურაციის დირექტორიის შექმნა

```bash
mkdir -p /opt/omniroute
```

### 2.2 გარემოს ცვლადების ფაილის შექმნა

```bash
cat > /opt/omniroute/.env << 'EOF'
# === უსაფრთხოება ===
JWT_SECRET=CHANGE-TO-A-UNIQUE-64-CHAR-SECRET-KEY
INITIAL_PASSWORD=YourSecurePassword123!
API_KEY_SECRET=REPLACE-WITH-ANOTHER-SECRET-KEY
STORAGE_ENCRYPTION_KEY=REPLACE-WITH-THIRD-SECRET-KEY
STORAGE_ENCRYPTION_KEY_VERSION=v1
MACHINE_ID_SALT=CHANGE-TO-A-UNIQUE-SALT
OMNIROUTE_WS_BRIDGE_SECRET=REPLACE-WITH-WS-BRIDGE-SECRET  # სავალდებულოა საწარმოო გარემოში: გამოიყენება Codex Responses WS bridge-ის მიერ

# === აპლიკაცია ===
PORT=20128
NODE_ENV=production
HOSTNAME=0.0.0.0
DATA_DIR=/app/data
APP_LOG_TO_FILE=true
AUTH_COOKIE_SECURE=true
REQUIRE_API_KEY=false

# === URL-ები (შეცვალეთ თქვენი დომენით) ===
# შიდა სერვერებს შორის საბაზისო URL დაგეგმილი დავალებებისთვის / საკუთარ რესურსებზე მოთხოვნებისთვის.
BASE_URL=http://127.0.0.1:20128
# ბრაუზერისთვის განკუთვნილი URL, რომელიც გამოიყენება OAuth-ის უკუგამოძახებებისთვის, მართვის პანელის ბმულებისა და გენერირებული საჯარო URL-ებისთვის.
NEXT_PUBLIC_BASE_URL=https://llms.seudominio.com
# არასავალდებულო საჯარო origin-ის აშკარა ჩანაცვლება გენერირებული საჯარო რესურსების URL-ებისთვის.
# OMNIROUTE_PUBLIC_BASE_URL=https://llms.seudominio.com

# === ღრუბლოვანი სინქრონიზაცია (არასავალდებულო) ===
# CLOUD_URL=https://cloud.omniroute.online
# NEXT_PUBLIC_CLOUD_URL=https://cloud.omniroute.online
EOF
```

> ⚠️ **მნიშვნელოვანია**: დააგენერირეთ უნიკალური საიდუმლო გასაღებები! თითოეული გასაღებისთვის გამოიყენეთ `openssl rand -hex 32`.

### 2.3 კონტეინერის გაშვება

```bash
docker pull diegosouzapw/omniroute:latest

docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --env-file /opt/omniroute/.env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

### 2.4 მუშაობის შემოწმება

```bash
docker ps | grep omniroute
docker logs omniroute --tail 20
```

უნდა გამოჩნდეს: `[DB] SQLite database ready` და `listening on port 20128`.

## 3. nginx-ის კონფიგურაცია (უკუ პროქსი)

### 3.1 SSL სერტიფიკატის გენერირება (Cloudflare Origin)

Cloudflare-ის მართვის პანელში:

1. გადადით **SSL/TLS → Origin Server**
2. დააწკაპუნეთ **Create Certificate**
3. დატოვეთ ნაგულისხმევი პარამეტრები (15 წელი, \*.yourdomain.com)
4. დააკოპირეთ **Origin Certificate** და **Private Key**

```bash
mkdir -p /etc/nginx/ssl

# ჩასვით სერტიფიკატი
nano /etc/nginx/ssl/origin.crt

# ჩასვით პირადი გასაღები
nano /etc/nginx/ssl/origin.key

chmod 600 /etc/nginx/ssl/origin.key
```

### 3.2 Nginx-ის კონფიგურაცია

```bash
cat > /etc/nginx/sites-available/omniroute << 'NGINX'
# ნაგულისხმევი სერვერი — ბლოკავს IP-ის მეშვეობით პირდაპირ წვდომას
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    listen 443 ssl default_server;
    listen [::]:443 ssl default_server;
    ssl_certificate     /etc/nginx/ssl/origin.crt;
    ssl_certificate_key /etc/nginx/ssl/origin.key;
    server_name _;
    return 444;
}

# OmniRoute — HTTPS
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name llms.yourdomain.com;  # შეცვალეთ თქვენი დომენით

    ssl_certificate     /etc/nginx/ssl/origin.crt;
    ssl_certificate_key /etc/nginx/ssl/origin.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    client_max_body_size 100M;

    location / {
        proxy_pass http://127.0.0.1:20128;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket-ის მხარდაჭერა
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        # SSE (სერვერის მიერ გაგზავნილი მოვლენები) — AI-ის პასუხების ნაკადური გადაცემა

        proxy_cache off;

```

უკუ პროქსის ნაკადის დროის ამოწურვის პარამეტრები შეუსაბამეთ OmniRoute-ის დროის ამოწურვის გარემოს ცვლადებს. თუ გაზრდით
`FETCH_TIMEOUT_MS` / `STREAM_IDLE_TIMEOUT_MS`-ს, გაზარდეთ `proxy_read_timeout` / `proxy_send_timeout`
იმავე ზღვარზე მეტად.

OmniRoute იყენებს `NEXT_PUBLIC_BASE_URL`-ს, როგორც ბრაუზერისთვის განკუთვნილ კანონიკურ წყაროს OAuth-ის
უკუგამოძახებებისა და გენერირებული საჯარო ბმულებისთვის. ავთენტიფიცირებული მართვის პანელის ჩაწერის მოთხოვნები იყენებს იმავე წყაროს მოთხოვნებს
და სესიასთან მიბმულ CSRF დაცვას, ამიტომ მათ არ სჭირდებათ სტატიკური საჯარო საბაზისო URL. ზემოთ მოცემული
`X-Forwarded-*` სათაურები კვლავ სასარგებლო მარშრუტიზაციის მეტამონაცემებია, თუმცა ისინი ვერ ჩაანაცვლებს
ცხადად განსაზღვრული საჯარო URL-ის დაყენებას, როდესაც ის OAuth-ს ან გენერირებულ ბრაუზერის ბმულებს სჭირდება. ჩართეთ
`OMNIROUTE_TRUST_PROXY` მხოლოდ იმ შემთხვევაში, თუ OmniRoute კლიენტებისთვის პირდაპირ ხელმისაწვდომი არ არის და თქვენი პროქსი
შემოავალ გადამისამართების სათაურებს შლის/ხელახლა აგებს.

## დაბალი მეხსიერების / მცირე VPS-ის ოპტიმიზაცია

მცირე VPS ეგზემპლარებზე (1 GB RAM ან ნაკლები) განთავსებისთვის:

- **გამორთეთ ფონური სერვისები** — დააყენეთ `OMNIROUTE_DISABLE_BACKGROUND_SERVICES=1`, რათა გამოტოვოთ დამგეგმავი, MCP სერვერი და პერიოდული ტექნიკური მომსახურების ამოცანები. იხილეთ `docs/reference/ENVIRONMENT.md`.
- **გამოიყენეთ SQLite WAL რეჟიმი** — ნაგულისხმევად ჩართულია და ამცირებს მეხსიერების პიკურ მოხმარებას პარალელური წაკითხვისას.
- **შეზღუდეთ V8-ის გროვა** — დააყენეთ `OMNIROUTE_MEMORY_MB` (მაგ. `512`), რათა შესრულების გარემომ VM-ზე მეტი ზედა ზღვარი არ დააკალიბროს. იხილეთ `docs/reference/ENVIRONMENT.md`.
- **მძიმე მოთხოვნების დაშვება გროვის ლიმიტის შესაბამისად ავტომატურად მასშტაბირდება** -- ზემოთ `OMNIROUTE_MEMORY_MB`-ის დაყენების შემდეგ, მიღებული მონაცემების ბაიტური ბიუჯეტი (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) იმავე ზედა ზღვრის საფუძველზე გამოითვლება, ამიტომ მეხსიერებით შეზღუდული VM დამატებითი კონფიგურაციის გარეშე იღებს პარალელური მოთხოვნების უფრო მცირე ბიუჯეტს; ჭარბი მოთხოვნები მეხსიერებისთვის კონკურენციის ნაცვლად იღებენ განმეორებად `503` პასუხს `Retry-After`-ით. მემკვიდრეობითი `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` მოთხოვნების რაოდენობის ლიმიტი დააყენეთ მხოლოდ მაშინ, თუ ამის დამატებით მკაცრი ზედა ზღვარი გჭირდებათ.
- **არ გაუშვათ `next build` VPS-ზე** — ააგეთ ლოკალურად და განათავსეთ დამოუკიდებელი გამომავალი (`.next/standalone/`).
- **აკონტროლეთ `top` / `free -m`-ით** — OmniRoute, როგორც წესი, უმოქმედო მდგომარეობაში 1 GB-იან VM-ზე 200-400 MB RSS-ს იყენებს.
