## რატომ უნდა გამოიყენოთ პროქსი?

AI პროვაიდერების დიდი ნაწილი წვდომას გეოგრაფიული რეგიონის მიხედვით ზღუდავს. დეველოპერები **რუსეთში, ჩინეთში, ირანში, კუბაში, თურქეთსა** და სხვა ქვეყნებში აწყდებიან შემდეგი ტიპის შეცდომებს:

```
unsupported_country_region_territory
```

პროქსი სასარგებლოა დაბლოკილი რეგიონების გარეთაც:

| გამოყენების შემთხვევა                   | აღწერა                                                                                |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| **გეოგრაფიული ბლოკირების გვერდის ავლა** | OpenAI-ზე, Anthropic-ზე, Codex-სა და Copilot-ზე წვდომა დაბლოკილი ქვეყნებიდან          |
| **IP-მისამართების როტაცია**             | მოთხოვნების განაწილება რამდენიმე IP-მისამართზე სიხშირის შეზღუდვის თავიდან ასაცილებლად |
| **კონფიდენციალურობა**                   | თქვენი რეალური IP-მისამართის დამალვა ზედა დონის პროვაიდერებისგან                      |
| **შესაბამისობა**                        | ტრაფიკის გატარება კონკრეტული იურისდიქციების გავლით                                    |
| **ტესტირება**                           | სხვადასხვა რეგიონიდან გაგზავნილი მოთხოვნების სიმულაცია                                |

## 4-დონიანი პროქსი-სისტემა

OmniRoute მხარს უჭერს პროქსის კონფიგურაციას **ოთხ დამოუკიდებელ დონეზე**, რომლებიც პრიორიტეტების მიხედვით განისაზღვრება:

```
პრიორიტეტების განსაზღვრის თანმიმდევრობა (უმაღლესი → უმდაბლესი):

  1. 🔵 ანგარიშის/კავშირის პროქსი  →  თითოეული API-გასაღების / OAuth-კავშირისთვის
  2. 🟡 პროვაიდერის პროქსი         →  თითოეული პროვაიდერისთვის (მაგ., OpenAI-ის მთელი ტრაფიკი)
  3. 🟠 კომბინაციის პროქსი         →  თითოეული კომბინაციის/მარშრუტიზაციის კონფიგურაციისთვის
  4. 🟢 გლობალური პროქსი           →  მთელი ტრაფიკისა და ყველა პროვაიდერისთვის
```

### როგორ მუშაობს განსაზღვრა

როდესაც OmniRoute მოთხოვნას ზედა დონის პროვაიდერთან აგზავნის, ის იძახებს `resolveProxyForConnectionFromRegistry()`-ს, რომელიც თითოეულ დონეს თანმიმდევრულად ამოწმებს:

1. **ანგარიშის დონე** — არის თუ არა პროქსი მინიჭებული ამ კონკრეტული კავშირის ID-ზე?
2. **პროვაიდერის დონე** — არის თუ არა პროქსი მინიჭებული ამ პროვაიდერზე (მაგ., `openai`)?
3. **გლობალური დონე** — არის თუ არა გლობალური პროქსი კონფიგურირებული?
4. **პროქსის გარეშე** — პირდაპირი კავშირი პროვაიდერთან.

გამოიყენება პირველი დამთხვევა. ეს ნიშნავს, რომ შეგიძლიათ გლობალური პროქსი სარეზერვო ვარიანტად დააყენოთ, ხოლო კონკრეტული პროვაიდერებისთვის ან კავშირებისთვის იგი სხვა პარამეტრებით ჩაანაცვლოთ.

## პროქსების რეესტრი (CRUD)

პროქსების რეესტრი არის SQLite-ცხრილი (`proxy_registry`), რომელიც ყველა თქვენს პროქსის ინახავს. თითოეულ პროქსის აქვს:

| ველი       | ტიპი         | აღწერა                                                      |
| ---------- | ------------ | ----------------------------------------------------------- |
| `id`       | UUID         | უნიკალური იდენტიფიკატორი                                    |
| `name`     | სტრიქონი     | ადამიანისთვის გასაგები დასახელება                           |
| `type`     | სტრიქონი     | პროტოკოლი: `http`, `https`, `socks5`                        |
| `host`     | სტრიქონი     | პროქსის ჰოსტის სახელი ან IP                                 |
| `port`     | მთელი რიცხვი | პორტის ნომერი                                               |
| `username` | სტრიქონი     | ავთენტიფიკაციის მომხმარებლის სახელი (დაშიფრულია შენახვისას) |
| `password` | სტრიქონი     | ავთენტიფიკაციის პაროლი (დაშიფრულია შენახვისას)              |
| `region`   | სტრიქონი     | გეოგრაფიული რეგიონის დასახელება                             |
| `notes`    | სტრიქონი     | თავისუფალი ფორმის შენიშვნები                                |
| `status`   | სტრიქონი     | `active` ან `inactive`                                      |
| `source`   | სტრიქონი     | `manual` ან `oneproxy`                                      |

### პროქსის შექმნა

**მართვის პანელიდან:**

1. გადადით **პარამეტრები → პროქსი**
2. დააწკაპუნეთ **პროქსის დამატება**
3. შეავსეთ ტიპი, ჰოსტი, პორტი და, სურვილისამებრ, ავთენტიფიკაციის მონაცემები
4. შეინახეთ

**API-ის საშუალებით:**


### მასობრივი მინიჭება

ერთი პროქსი ერთდროულად რამდენიმე პროვაიდერს ან კავშირს მიანიჭეთ:

```bash
    "scope": "provider",

    "proxyId": "proxy-uuid"
  }'
```

### იმპორტი/ექსპორტი

პროქსები შედის **სარეზერვო ასლის შექმნის/აღდგენის** სისტემაში. OmniRoute-ის კონფიგურაციის ექსპორტისას:

1. გადადით **მართვის პანელი → პარამეტრები → სარეზერვო ასლი**
2. დააწკაპუნეთ **ექსპორტი** — პროქსების რეესტრი და მინიჭებები ასევე შევა ექსპორტში
3. აღსადგენად დააწკაპუნეთ **იმპორტი** და ატვირთეთ სარეზერვო ასლის ფაილი

პროქსების რეესტრი ასევე მხარს უჭერს **host+port-ის მიხედვით upsert-ს** — თუ შემოიტანთ უკვე არსებულ პროქსის (იგივე ჰოსტითა და პორტით), დუბლიკატის შექმნის ნაცვლად არსებული ჩანაწერი განახლდება.

### მოძველებული კონფიგურაციის მიგრაცია

თუ პროქსიები უფრო ძველ ვერსიაში (რეესტრამდელ ვერსიაში) დააკონფიგურირეთ, OmniRoute მათ ავტომატურად გადაიტანს:

```
მოძველებული key_value საცავი → proxy_registry + proxy_assignments
```

ეს განახლების შემდეგ პირველი გაშვებისას მხოლოდ ერთხელ ხდება. ხელახლა გასაშვებად გამოიყენეთ `migrateLegacyProxyConfigToRegistry({ force: true })`.

## 1proxy-ის უფასო პროქსი-მარკეტპლეისი

> 🆕 **წვლილი შეიტანა [@oyi77](https://github.com/oyi77)-მა** — PR [#1847](https://github.com/diegosouzapw/OmniRoute/pull/1847) (Issue [#1788](https://github.com/diegosouzapw/OmniRoute/issues/1788))

OmniRoute ინტეგრირებულია **[1proxy](https://1proxy-api.aitradepulse.com)** საზოგადოებრივ პლატფორმასთან, რათა უზრუნველყოს წვდომა მთელი მსოფლიოდან მიღებულ **ასობით უფასო, გადამოწმებულ პროქსიზე**. ეს იდეალურია მომხმარებლებისთვის, რომლებსაც საკუთარი პროქსი-ინფრასტრუქტურა არ აქვთ.

### როგორ მუშაობს

```
┌─────────────┐  სინქრონიზაცია  ┌─────────────────┐   როტაცია    ┌──────────┐
│  1proxy API │ ──────────────▶ │  proxy_registry  │ ────────────▶ │ Provider │
│  (გარე)     │  500-მდე პროქსი │  source=oneproxy │ ხარისხის მიხედვით │   API    │
└─────────────┘                 └─────────────────┘               └──────────┘
```

1. **სინქრონიზაცია** — OmniRoute იღებს გადამოწმებულ პროქსიებს 1proxy API-დან
2. **შენახვა** — პროქსიები ინახება იმავე `proxy_registry` ცხრილში, `source = 'oneproxy'` მნიშვნელობით
3. **ფილტრაცია** — გაფილტრეთ პროტოკოლის, ქვეყნისა და ხარისხის ქულის მიხედვით
4. **როტაცია** — აირჩიეთ საუკეთესო პროქსი ხარისხზე დაფუძნებული, შემთხვევითი ან თანმიმდევრული სტრატეგიის გამოყენებით
5. **ავტომატური დაქვეითება** — წარუმატებელი პროქსიების ხარისხის ქულა მცირდება; ზღვრულ მნიშვნელობაზე დაბლა ჩამოსვლისას → მოინიშნება არააქტიურად

### პროქსიების სინქრონიზაცია

**მართვის პანელიდან:**

1. გადადით **Settings → 1proxy** ჩანართზე
2. დააწკაპუნეთ **„Sync Now“**
3. იხილეთ სტატისტიკა: პროქსიების საერთო რაოდენობა, აქტიურების რაოდენობა, საშუალო ხარისხი და ქვეყნების მიხედვით განაწილება

**API-ის საშუალებით:**

```bash
# სინქრონიზაციის გაშვება
curl -X POST http://localhost:20128/api/settings/oneproxy \
  -H "Content-Type: application/json" \
  -d '{}'

# პასუხი:
# { "success": true, "added": 127, "updated": 45, "failed": 2, "total": 172 }
```

### პროქსიების ფილტრაცია

```bash

# ქვეყნის მიხედვით გაფილტვრა

# ხარისხის მინიმალური ქულის მიხედვით გაფილტვრა
```

### პროქსის ხარისხის ქულები

თითოეულ 1proxy პროქსის თან ახლავს მეტამონაცემები:

| ველი            | აღწერა                                             |

| `googleAccess`  | შეუძლია თუ არა პროქსის Google-ის სერვისებზე წვდომა |
| `countryCode`   | ქვეყნის ორასოიანი ISO კოდი                         |
| `lastValidated` | ბოლო ვალიდაციის დროის ნიშნული                      |

ხარისხის ქულები დინამიკურად კორექტირდება:

- **წარუმატებელი მოთხოვნები** ქულას 10 პუნქტით ამცირებს

## აღმოჩენისგან დაცვა და შეუმჩნევლობა

OmniRoute არა მხოლოდ მარშრუტიზებს ტრაფიკს პროქსის გავლით — ის ტრაფიკს ლეგიტიმურ იერსაც აძლევს:

### TLS-თითის ანაბეჭდის გაყალბება

იყენებს `wreq-js`-ს ბრაუზერის მსგავსი TLS-თითის ანაბეჭდების შესაქმნელად და გვერდს უვლის ბოტების აღმოჩენის სისტემებს, რომლებიც არაბრაუზერულ TLS-ხელის ჩამორთმევებს საეჭვოდ მიიჩნევენ.

### CLI-თითის ანაბეჭდთან შესაბამისობა

**CLI-თითის ანაბეჭდის გადამრთველი** (`პარამეტრები → უსაფრთხოება`) ხელახლა ალაგებს HTTP-სათაურებსა და JSON-ის სხეულის ველებს ისე, რომ ზუსტად დაემთხვეს ნატიური CLI-ბინარული ფაილების (Claude Code, Codex და სხვ.) სიგნატურას. ეს მუშაობს პროქსის **ზემოდან**:

```
თქვენი IP (დაბლოკილი) → პროქსის IP (აშშ) → პროვაიდერის API
                         + TLS-ის გაყალბება
                         + CLI-თითის ანაბეჭდი
```

ამგვარად, ერთდროულად იღებთ როგორც **IP-ის შენიღბვას**, ისე **მოთხოვნის ავთენტურობას**.

### პროქსის IP-ის შენარჩუნება

მართვის პანელზე ფერებით კოდირებული ნიშნები აჩვენებს, პროქსის რომელი დონეა აქტიური:

| ნიშანი | დონე       | მნიშვნელობა                                        |
| ------ | ---------- | -------------------------------------------------- |
| 🟢     | გლობალური  | მთელი ტრაფიკი ამ პროქსის გავლით გადის              |
| 🟡     | პროვაიდერი | პროქსირდება მხოლოდ ამ პროვაიდერის ტრაფიკი          |
| 🔵     | კავშირი    | ეს კონკრეტული გასაღები/ანგარიში ამ პროქსის იყენებს |

გადამოწმებისთვის ნიშანი ასევე აჩვენებს განსაზღვრულ პროქსის IP-ს.

```bash
curl -X PUT "http://localhost:20128/api/upstream-proxy/openai" \
```

## მართვის პანელის ინტერფეისი

### პარამეტრები → პროქსის ჩანართი

- **გლობალური პროქსის** კონფიგურაცია (ერთჯერადად მთელი ტრაფიკისთვის)
- **თითოეული პროვაიდერის პროქსის** ჩანაცვლებები
- **თითოეული კავშირის პროქსის** მინიჭებები
- **კავშირის ტესტი** კონფიგურირებული პროქსის გავლით
- **ფერებით კოდირებული ნიშნები**, რომლებიც აქტიური პროქსის დონეს აჩვენებს

### პარამეტრები → 1proxy-ის ჩანართი

- ღილაკი **სინქრონიზაცია ახლა** უფასო პროქსი-სერვერების მისაღებად
- **სტატისტიკის ბარათები**: სულ, აქტიური, საშუალო ხარისხი, ბოლო სინქრონიზაცია
- **ფილტრები**: პროტოკოლი, ქვეყნის კოდი, მინიმალური ხარისხი
- **პროქსის ცხრილი** ჰოსტით, პროტოკოლით, ქვეყნით, ხარისხის ქულით, დაყოვნებით, ანონიმურობითა და Google-ზე წვდომით
- **სინქრონიზაციის სტატუსის** პანელი წარმატებული/წარუმატებელი მცდელობებისა და ზედიზედ წარუმატებლობების რაოდენობის აღრიცხვით
- **ყველას გასუფთავება** 1proxy-ის ყველა ჩანაწერის წასაშლელად

## პრობლემების მოგვარება

### „SOCKS5 პროქსი გამორთულია“

თქვენს `.env` ფაილში მიუთითეთ `ENABLE_SOCKS5_PROXY=true` და გადატვირთეთ.

### პროქსის გავლით მიღებული „socket hang up“ შეცდომები

ეს ნორმალურია იაფი პროქსებისთვის, რომლებიც უმოქმედო კავშირებს წყვეტენ. OmniRoute ამას უკვე შემდეგნაირად ამუშავებს:

- პროქსი-კავშირებისთვის keep-alive-ის გამორთვით (`keepAliveTimeout: 1`)
- pipelining-ის გამორთვით (`pipelining: 0`)
- დისპეტჩერების კეშირებით განმეორებითი ხელის ჩამორთმევების თავიდან ასაცილებლად

თუ პრობლემა კვლავ მეორდება, სცადეთ სხვა პროქსი ან გამოიყენეთ 1proxy-ის როტაციის ფუნქცია.

### „unsupported_country_region_territory“ OAuth-ის დროს

OAuth პროცესის დაწყებამდე დარწმუნდით, რომ პროქსი კონფიგურირებულია. OmniRoute OAuth ტოკენების გაცვლას კონფიგურირებული პროქსის გავლით წარმართავს. ჯერ დააყენეთ გლობალური ან პროვაიდერის დონის პროქსი, შემდეგ კი დაამყარეთ კავშირი.

### პროქსი არ გამოიყენება

შეამოწმეთ განსაზღვრის თანმიმდევრობა:

1. გადაამოწმეთ `GET /api/settings/proxy?resolve=your-connection-id`-ის გამოყენებით
2. შეამოწმეთ, რომ პროქსის `status` არის `active` (და არა `inactive`)
3. დარწმუნდით, რომ პროქსის მინიჭების არე შეესაბამება თქვენს კავშირს

### 1proxy-ის სინქრონიზაცია ვერ სრულდება

შეამოწმეთ სინქრონიზაციის სტატუსი:

```bash
curl "http://localhost:20128/api/settings/oneproxy?action=status"
```

თუ `consecutiveFailures >= 5`, ამოქმედებულია მიკროსქემის ამომრთველი. გასანულებლად გადატვირთეთ სერვერი ან დაელოდეთ ხელით გასანულებას.

### `proxy_registry` ცხრილი

```sql
CREATE TABLE proxy_registry (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  type TEXT NOT NULL DEFAULT 'http',
  host TEXT NOT NULL,
  port INTEGER NOT NULL,
  username TEXT DEFAULT '',
  password TEXT DEFAULT '',
  region TEXT,
  notes TEXT,
  status TEXT DEFAULT 'active',
  source TEXT NOT NULL DEFAULT 'manual',    -- 'manual' ან 'oneproxy'
  quality_score INTEGER,                     -- 0-100 (მხოლოდ 1proxy)
  latency_ms INTEGER,                        -- მილიწამები (მხოლოდ 1proxy)
  anonymity TEXT,                            -- გამჭვირვალე/ანონიმური/ელიტური
  google_access INTEGER DEFAULT 0,           -- შეუძლია Google-ზე წვდომა? (1proxy)
  last_validated TEXT,                       -- ISO დროის ნიშნული (1proxy)
  country_code TEXT,                         -- ISO-ს 2-ასოიანი კოდი (1proxy)
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

### `proxy_assignments` ცხრილი

```sql
CREATE TABLE proxy_assignments (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  proxy_id TEXT NOT NULL REFERENCES proxy_registry(id),
  scope TEXT NOT NULL,        -- 'global', 'provider', 'account', 'combo'
  scope_id TEXT,              -- პროვაიდერის ID, კავშირის ID ან კომბინაციის ID
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(scope, scope_id)
);
```

## პროქსის მდგომარეობის შემოწმება (v3.8.16+)

OmniRoute-ის **პროქსის სწრაფი უარყოფის** მექანიზმი (`src/lib/proxyHealth.ts`) სწრაფი TCP კავშირის შემოწმებით გაუმართავ პროქსებს <2 წამში აღმოაჩენს, შემდეგ კი თითოეული მოთხოვნის დამატებითი დანახარჯის თავიდან ასაცილებლად **შედეგს კეშში ინახავს**.

### როგორ მუშაობს

```
მოთხოვნა ──▶ ProxyHealthCache.get(url)
             │
             ├─ კეშშია + ახალია?  ──▶ კეშირებული სტატუსის დაბრუნება
             │
             └─ კეშში არაა / მოძველებულია?  ──▶ TCP კავშირი host:port-თან
                                                (ტაიმაუტი: FAST_FAIL_TIMEOUT_MS)
                                                ──▶ კეშირება HEALTH_CACHE_TTL_MS-ით
                                                ──▶ შედეგის დაბრუნება
```

ამის გარეშე გაუმართავი პროქსი ყოველი მოთხოვნის შესრულებას `PROXY_TIMEOUT_MS`-ის სრული ხანგრძლივობით (ნაგულისხმევად 30 წამი) დაბლოკავდა, სანამ შეცდომით დასრულდებოდა.

### რეგულირებადი გარემოს ცვლადები

| ცვლადი                       | ნაგულისხმევი მნიშვნელობა | დანიშნულება                                         |
| ---------------------------- | ------------------------ | --------------------------------------------------- |
| `PROXY_FAST_FAIL_TIMEOUT_MS` | `2000`                   | TCP კავშირის ტაიმაუტი მდგომარეობის თითო შემოწმებაზე |
| `PROXY_HEALTH_CACHE_TTL_MS`  | `30000`                  | მდგომარეობის შედეგის კეშში შენახვის ხანგრძლივობა    |

**რეკომენდებული მნიშვნელობები:**

| სცენარი                                   | სწრაფი უარყოფის ტაიმაუტი | კეშის TTL | დასაბუთება                                                                          |
| ----------------------------------------- | ------------------------ | --------- | ----------------------------------------------------------------------------------- |
| მაღალი გამტარუნარიანობის API-კარიბჭე      | 1500ms                   | 60000ms   | აგრესიული სწრაფი უარყოფა და უფრო ხანგრძლივი კეში შემოწმებების შესამცირებლად         |
| გეოგრაფიულად განაწილებული კვანძები        | 3000ms                   | 15000ms   | ნელ ქსელებს მეტი დრო სჭირდება; სწრაფი გადართვისთვის უფრო ხანმოკლე კეში              |
| შემუშავება / ტესტირება                    | 1000ms                   | 10000ms   | ლოკალურ პროქსებზე სწრაფი იტერაცია                                                   |
| ფარული რეჟიმი / აღმოჩენის თავიდან აცილება | 2500ms                   | 45000ms   | სწრაფი ზონდირების თავიდან აცილება, რომელმაც შეიძლება სიხშირის შეზღუდვები აამოქმედოს |

### პროქსის მდგომარეობის შემოწმება

```ts
import { getAllProxyHealthStatuses, invalidateProxyHealth } from "omniroute/proxyHealth";

const statuses = getAllProxyHealthStatuses();
for (const s of statuses) {
  console.log(`${s.proxyUrl} → healthy=${s.healthy}, stale=${s.stale}`);
}

// კონკრეტული პროქსის ხელახალი შემოწმების იძულება
invalidateProxyHealth("http://user:pass@203.0.113.7:8080");
```

`stale` დროშა არის `true`, როდესაც კეშის ჩანაწერმა `HEALTH_CACHE_TTL_MS`-ს გადააჭარბა და მომდევნო მოთხოვნა ახალ შემოწმებას გამოიწვევს.

### ნაგულისხმევი მნიშვნელობები პროქსის ტიპის მიხედვით

მდგომარეობის შემოწმება URL-ის სქემაზე დაფუძნებულ გონივრულ ნაგულისხმევ მნიშვნელობებს იყენებს:

| სქემა                      | ნაგულისხმევი პორტი |
| -------------------------- | ------------------ |
| `http://`                  | 8080               |
| `https://`                 | 443                |
| `socks5://` / `socks5h://` | 1080               |

URL-ში მითითებულ მორგებულ პორტებს (`http://host:9999`) ყოველთვის უპირატესობა ენიჭება სქემის ნაგულისხმევ მნიშვნელობასთან შედარებით.

## პროქსის ანალიტიკა და დაკვირვებადობა

OmniRoute აღრიცხავს თითოეული პროქსის გამოყენებას, რათა ოპერატორებს მარშრუტიზაციის შაბლონების, შეყოვნების მკვეთრი ზრდისა და განმეორებადი შეცდომების დიაგნოსტიკაში დაეხმაროს.

### რა აღირიცხება

კონფიგურირებული პროქსის გავლით შესრულებული ყოველი მოთხოვნისთვის OmniRoute აღრიცხავს:

| მეტრიკა      | აღწერა                                                          |
| ------------ | --------------------------------------------------------------- |
| `proxy_url`  | პროქსის სრული URL (ავტორიზაციის მონაცემები შენიღბულია)          |
| `provider`   | ზედა დონის პროვაიდერის ID (openai, anthropic და ა.შ.)           |
| `latency_ms` | სრული ორმხრივი გადაცემის დრო, პროქსის ხელის ჩამორთმევის ჩათვლით |
| `connect_ms` | მხოლოდ TCP კავშირის დამყარების დრო                              |
| `status`     | ზედა დონის სერვისიდან მიღებული HTTP სტატუსის კოდი               |
| `error`      | შეცდომის კლასი, თუ მოთხოვნა წარუმატებელი იყო                    |
| `timestamp`  | ISO 8601 UTC                                                    |

### მონაცემებზე წვდომა

```bash
# პროქსის ბოლო მოვლენები
curl -H "Authorization: Bearer $OMNIROUTE_KEY" \
  "http://localhost:20128/api/usage/proxy-logs?limit=100"
```

რეალური საბოლოო წერტილია `/api/usage/proxy-logs` (იხილეთ `src/app/api/usage/proxy-logs/route.ts`). ამ საბოლოო წერტილს აქვს შემდეგი მხარდაჭერა:

- `GET /api/usage/proxy-logs` — პროქსის ჟურნალების მიღება
- `DELETE /api/usage/proxy-logs` — პროქსის ყველა ჟურნალის გასუფთავება

საჭიროების შემთხვევაში, აგრეგირებული სტატისტიკის მოთხოვნა შესაძლებელია უშუალოდ `proxy_logs` ცხრილიდან SQL-ის საშუალებით. საინფორმაციო პანელის ინტერფეისში შესაძლოა ხელმისაწვდომი იყოს აგრეგირებული ხედები.

### გავრცელებული შაბლონები

**არასტაბილური პროქსის აღმოჩენა** (წარმატებასა და წარუმატებლობას შორის მონაცვლეობს):

```sql
SELECT proxy_url,
       COUNT(*) AS total,
       SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END) AS errors,
       ROUND(100.0 * SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END) / COUNT(*), 1) AS error_pct
FROM proxy_logs
WHERE timestamp > datetime('now', '-1 hour')
GROUP BY proxy_url
HAVING error_pct > 5
ORDER BY error_pct DESC;
```

**ნელი პროქსიების პოვნა** (p95 შეყოვნება > 2წმ):

```sql
WITH ranked AS (
  SELECT proxy_url, latency_ms,
         PERCENT_RANK() OVER (PARTITION BY proxy_url ORDER BY latency_ms) AS pct
  FROM proxy_logs
  WHERE timestamp > datetime('now', '-24 hour')
)
SELECT proxy_url, latency_ms
FROM ranked
WHERE pct >= 0.95
ORDER BY latency_ms DESC;
```

## როტაციის სტრატეგიის გადაწყვეტილების ხე

როდესაც ერთ არეს რამდენიმე პროქსი აქვს მინიჭებული, OmniRoute იყენებს **როტაციის სტრატეგიას**, რათა თითოეული მოთხოვნისთვის გამოსაყენებელი პროქსი შეარჩიოს. სტრატეგია კონფიგურირდება არის დონეზე (გლობალურად, თითოეული პროვაიდერისთვის, თითოეული ანგარიშისთვის, თითოეული კომბინაციისთვის).

### ხელმისაწვდომი სტრატეგიები

| სტრატეგია                | როდის გამოვიყენოთ                                    | კომპრომისი                                                                                                             |
| ------------------------ | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `quality` (ნაგულისხმევი) | საწარმოო გარემოში, განსხვავებული ხარისხის პროქსიებით | უპირატესობას ანიჭებს მაღალი შეფასების მქონე პროქსიებს; დაბალი შეფასების მქონე პროქსიები შესაძლოა საერთოდ არ გამოიყენოს |
| `random`                 | დატვირთვის განაწილება, კონფიდენციალურობა             | თანაბარი განაწილება; ხარისხის სიგნალებს უგულებელყოფს                                                                   |
| `sequential`             | გამართვა, დეტერმინისტული ტესტირება                   | პროქსიებს თანმიმდევრობით ცვლის; შედეგის გააზრება მარტივია                                                              |

## საკუთარი პროქსი-სერვერების ავტომატური გამორიცხვა მარცხის შემთხვევაში

1proxy-ის სავაჭრო სივრცის პული უკვე ავტომატურად აქვეითებს გაუმართავი პროქსი-სერვერების სტატუსს (იხილეთ
[პროქსი-სერვერის ხარისხის ქულები](#proxy-quality-scores)). რეესტრში **თქვენ** მიერ დამატებული
პროქსი-სერვერებისთვის ფონური მდგომარეობის შემმოწმებელი დამგეგმავი
(`src/lib/proxyHealth/scheduler.ts`) უზრუნველყოფს იმავე ქცევას — „ავტომატურად გამორიცხე
გაუმართავი წევრი ჯაჭვიდან“ — არაფრის წაშლის გარეშე:

```bash
# .env — რბილად გამორთეთ პროქსი-სერვერი ზედიზედ 3 წარუმატებელი შემოწმების შემდეგ და ხელახლა ჩართეთ
# ავტომატურად, როგორც კი ის შემოწმების მოთხოვნებზე პასუხს კვლავ დაიწყებს.
PROXY_AUTO_DISABLE=true
PROXY_AUTO_REMOVE_AFTER=3
```

როგორ მუშაობს ეს მრავალპროქსიან ჯაჭვში:

1. დამგეგმავი ყველა რეგისტრირებულ პროქსი-სერვერს ამოწმებს ყოველ `PROXY_HEALTH_INTERVAL_MS`
   ინტერვალში (ნაგულისხმევად 10 წთ; მინიმუმ 1 წთ).
2. ზედიზედ `PROXY_AUTO_REMOVE_AFTER` რაოდენობის **დადასტურებული** მარცხის შემდეგ (რეალური
   კავშირის მარცხი — დროის ამოწურვა ან შემოწმების სამიზნის საკუთარი 5xx პასუხი არასოდეს ითვლება; იხილეთ
   [პროქსი-სერვერის მდგომარეობის შემოწმება](#proxy-health-checking-v3816)), პროქსი-სერვერის `status`
   დაყენდება მნიშვნელობაზე `dead`.
3. `dead` არის ერთ-ერთი სტატუსი, რომელსაც პულის/როტაციის
   განსაზღვრისას გამოყენებული აქტიური სტატუსების ფილტრი გამორიცხავს, ამიტომ შესაბამისი არეალის როტაცია (რიგრიგობითი / შემთხვევითი / მიმაგრებული /
   დაყოვნებაზე დაფუძნებული — იხილეთ [როტაციის სტრატეგიის გადაწყვეტილების ხე](#rotation-strategy-decision-tree))
   დაუყოვნებლივ წყვეტს ამ პროქსი-სერვერის ახალი მოთხოვნებისთვის გადაცემას. პულის სხვა პროქსი-სერვერებზე
   ეს გავლენას არ ახდენს და მთელი პული პირდაპირ კავშირზე ფარულად არასოდეს
   გადაერთვება — იხილეთ [4-დონიანი პროქსი-სისტემის](#4-level-proxy-system) შეცდომისას დახურვის
   დამცავი მექანიზმი.
4. დამგეგმავი `dead` პროქსი-სერვერების იმავე ინტერვალით შემოწმებას აგრძელებს. მომდევნო
   წარმატებული შემოწმება `status`-ს კვლავ `active` მნიშვნელობაზე გადაიყვანს და პროქსი-სერვერი როტაციაში დაბრუნდება —
   ხელით ხელახლა დამატება საჭირო არ არის.

ეს განზრახ **არჩევით გასააქტიურებელი და არადესტრუქციული** ფუნქციაა: ნაგულისხმევად დამგეგმავი მხოლოდ
ითვლის და ჟურნალში აღრიცხავს მარცხებს (იხილეთ პოლიტიკა C ფაილში `decision.ts`), ხოლო `PROXY_AUTO_DISABLE`
ჩანაწერს არასოდეს შლის — ამისთვის განკუთვნილია ცალკე, უფრო აგრესიული
`PROXY_AUTO_REMOVE` პარამეტრი. თუ ორივე დაყენებულია მნიშვნელობაზე `true`, უპირატესობა `PROXY_AUTO_REMOVE`-ს
ენიჭება (წასაშლელ პროქსი-სერვერს შუალედური რბილი გამორთვა არაფერში სჭირდება). ცვლადების სრული
სიისთვის იხილეთ [გარემოს კონფიგურაციის](../reference/ENVIRONMENT.md) ცნობარი.
