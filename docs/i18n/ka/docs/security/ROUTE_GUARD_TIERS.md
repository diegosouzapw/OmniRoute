## მიმოხილვა

OmniRoute-ის მართვის API-ის ყველა მარშრუტი დაცვის სამი დონიდან ერთ-ერთს
მიეკუთვნება. კლასიფიკაცია სტატიკურია, განსაზღვრულია `src/server/authz/routeGuard.ts`-ში
და მოწმდება ავტორიზაციის ნებისმიერი სხვა განშტოების შესრულებამდე.

## დონეები

### დონე 1 — LOCAL_ONLY

**აღსრულდება:** `isLocalOnlyPath(path)` → ლუპბექ-ჰოსტის შემოწმება
**გვერდის ავლა:** ნაგულისხმევად არ არის შესაძლებელი. ვიწრო გამონაკლისი მოქმედებს
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში შემავალი ბილიკებისთვის, როდესაც მოთხოვნა შეიცავს
მართებულ API გასაღებს `manage` წვდომის სფეროთი (იხილეთ [გამონაკლისი `manage` წვდომის სფეროსთვის](#manage-scope-carve-out)).

ეს მარშრუტები ქმნის შვილობილ პროცესებს ან ასრულებს კოდს შესრულების გარემოში. მათი
არალუპბექ ტრაფიკისთვის ხელმისაწვდომობა საშუალებას მისცემდა თავდამსხმელს, რომელმაც მოიპოვა მართებული JWT (მაგ.,
Cloudflared/Ngrok გვირაბის მეშვეობით), პროცესების შექმნა გამოეწვია — ეს არის ცნობილი CVE
კლასი ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**რას წარმოადგენს GHSA-fhh6-4qxv-rpqj (შეტევის კლასი):** მართვის/აგენტის სერვერი
ხელმისაწვდომს ხდის საბოლოო წერტილს, რომელიც უშვებს ქვეპროცესს (`npm install`, `node`, ბრაუზერს,
პროქსის, `git`, `tar`, …). თუ ეს საბოლოო წერტილი ჰოსტის გარედან ხელმისაწვდომია — რადგან
ოპერატორმა OmniRoute მოათავსა nginx/Cloudflare/Tailscale გვირაბის უკან და JWT
გაჟონა, ან ავთენტიფიკაცია არასწორად იყო კონფიგურირებული — თავდამსხმელი „API-ის გამოძახებას“ გარდაქმნის „ჰოსტზე
ბრძანების შესრულებად“ (კოდის დისტანციური შესრულება). OmniRoute ამას თავიდან იცილებს
**ლუპბექ-ჰოსტის შემოწმების უპირობოდ, ავთენტიფიკაციის ნებისმიერ შემოწმებამდე აღსრულებით** ყველა
მარშრუტზე, რომელსაც პროცესის შექმნა შეუძლია: გვირაბში გაჟონილი ტოკენიც კი ვერ მიაღწევს პროცესის შექმნის ფუნქციას.

**LOCAL_ONLY-ის სრული ნაკრები.** ავტორიტეტული წყაროა
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ფაილში
`src/server/authz/routeGuard.ts`; ქვემოთ მოცემული ცხრილი ასახავს მიმდინარე მდგომარეობას.
`check-route-guard-membership` შემოწმება ჩამოთვლის ყველა `route.ts`-ს
პროცესის შექმნის შესაძლებლობის მქონე პრეფიქსების ქვეშ და CI-ს წარუმატებლად დაასრულებს, თუ რომელიმე მათგანი მხოლოდ ლოკალურად ხელმისაწვდომად არ არის კლასიფიცირებული.

### ახალი ინსტალაციის bootstrap მხოლოდ loopback-ისთვისაა — რეალური peer-ის მიხედვით და არა `Host`-ის

როდესაც მართვის პაროლი კონფიგურირებული არ არის (და არც `INITIAL_PASSWORD` არსებობს),
`src/shared/utils/apiAuth.ts`-ში `isAuthRequired()` ანონიმურ bootstrap-ს ღიას ტოვებს **მხოლოდ loopback peer-ებისთვის**.
Loopback განისაზღვრება სანდო peer-სიგნალებით, შემდეგი თანმიმდევრობით: ტოკენით მონიშნული რეალური TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, რასაც პოლიტიკა ხედავს), pipeline-ის საკუთარი
`AUTHZ_HEADER_PEER_LOCALITY` ვერდიქტი (რასაც მარშრუტების დამმუშავებლები ხედავენ და რომელიც სანდოა მხოლოდ მაშინ,
როდესაც `OMNIROUTE_PEER_STAMP_TOKEN` დაყენებულია), ან პირდაპირი გამომძახებლებისთვის რეალური socket peer.
`Host` / `nextUrl.hostname` არასდროს მოწმდება, ხოლო პირველი პაროლის ჩაწერა
(`POST /api/settings/require-login`) იმავე შეზღუდვას ექვემდებარება და ყველა
ქსელური peer-ისთვის ღია არ არის (GHSA-7pq4-8pvv-rx7r). `managementPolicy` თავის `peerContext` ვერდიქტს
ცალსახად გადასცემს ქვედა დონეს, ამიტომ თავდაპირველი (წაშლამდე არსებული) მოთხოვნის სათაურები მასზე არასდროს მოქმედებს.

### დონე 3 — MANAGEMENT (ნაგულისხმევი)

ყველა სხვა მართვის მარშრუტი. ავტორიზაცია აუცილებელია, თუ
`requireLogin=false` არ არის კონფიგურირებული. CLI ტოკენებს ამ მარშრუტებზე ავთენტიფიკაცია შეუძლიათ (loopback + მოქმედი HMAC).

## შეფასების თანმიმდევრობა

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → შემდეგ ეტაპზე გადასვლა
     → non-loopback, manage-სკოპის Bearer
        AND isLocalOnlyBypassableByManageScope   → დაშვება (management_key)
     → სხვა შემთხვევაში                           → უარყოფა 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → დაშვება (system)
  3. hasValidCliToken(headers)?
     → დაშვება (cli) [loopback + timingSafeEqual HMAC შემოწმება]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → დაშვება (dashboard_session)
     → manage-სკოპის Bearer არაგვერდასავლელ მარშრუტზე?
        → დაშვება (management_key)
     → უარყოფა 401/403
  5. requireLogin=false?
     → დაშვება (anonymous)
```

1-ლი ნაბიჯის manage-სკოპის განშტოება ერთადერთი ავთენტიფიცირებული გზაა, რომელსაც
LOCAL_ONLY მარშრუტის დაკმაყოფილება შეუძლია; ავთენტიფიკაციის ბექენდის გაუმართაობის
რეჟიმი აბრუნებს 503-ს (და არა 403-ს), რათა ვადაგასული DB შეუმჩნევლად არ
გადავიდეს „უარყოფის“ რეჟიმზე.

## ახალი პროცესის გაშვების უნარის მქონე მარშრუტის დამატება

1. დაამატეთ გზის პრეფიქსი `LOCAL_ONLY_API_PREFIXES`-ში,
   `src/server/authz/routeGuard.ts` ფაილში
2. დაამატეთ ტესტი `tests/unit/authz/routeGuard.test.ts`-ში, რომელიც ადასტურებს,
   რომ ახალი პრეფიქსისთვის `isLocalOnlyPath()` აბრუნებს true-ს
3. **არასოდეს გამოტოვოთ ეს ნაბიჯი** — იხილეთ მკაცრი წესი #15 `CLAUDE.md`-ში
4. გადაწყვიტეთ: უნდა შედიოდეს თუ არა ეს მარშრუტი ასევე
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში?
   ნაგულისხმევი პასუხია **არა**. ჩართეთ მხოლოდ მაშინ, როდესაც მარშრუტის
   manage-სკოპის მფლობელისთვის გახსნა უსაფრთხოა (ანუ ის არ უშვებს მომხმარებლის
   მიერ სრულად კონტროლირებად ნებისმიერ კოდს).

## manage-სკოპით შემოვლის დაშვების მქონე გზის დამატება

1. დაადასტურეთ, რომ მარშრუტი არ ასრულებს მომხმარებლის მიერ მოწოდებულ კოდს ან
   ბრძანებებს. თუ ასრულებს, შეჩერდით — ეს გამონაკლისი ამისთვის არასწორი
   ინსტრუმენტია.
2. დაამატეთ პრეფიქსი `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში,
   `src/server/authz/routeGuard.ts` ფაილში
3. დაამატეთ დაფარვა `tests/unit/authz/management-policy.test.ts`-ში მოთხოვნის
   ოთხივე ფორმისთვის: Bearer-ის გარეშე (403), manage Bearer (დაშვება),
   არა-manage Bearer (403) და თითოეული პრეფიქსის რეგრესიული ტესტი, რომელიც
   ადასტურებს, რომ `/api/cli-tools/runtime/*` manage Bearer-ის შემთხვევაშიც
   მკაცრად loopback-ად რჩება.

`docs/openapi.yaml`-ში ახალი მარშრუტის დამატებისას გამოიყენეთ შესაბამისი

### ვალიდაცია

ორი სკრიპტი უზრუნველყოფს YAML ანოტაციებსა და `routeGuard.ts`-ს შორის
თანმიმდევრულობას:

- `scripts/check/check-openapi-coverage.mjs` — მარცხდება, თუ დაფარვა < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — მარცხდება, თუ `x-loopback-only`
  ან `x-always-protected` ანოტაციები კომპილაციის დროის კონსტანტებს არ ემთხვევა

ორივე სკრიპტი სრულდება წინასწარი commit-ის hook-ში და CI-ში.

### ცრუ დადებითი შედეგის წესი

თუ `x-always-protected` ან `x-loopback-only` ანოტაცია მითითებულია მარშრუტზე,
რომელიც `routeGuard.ts`-ის კონსტანტაში არ შედის, დაფარვის სკრიპტი მარცხდება.
გამოსავალი ყოველთვის არის YAML-ის შესაბამისობაში მოყვანა იმასთან, რასაც
`routeGuard.ts` რეალურად აღასრულებს — და არა მარშრუტების `routeGuard.ts`-ში
დამატება აღსრულების ლოგიკის იმავდროულად განხორციელების გარეშე.
