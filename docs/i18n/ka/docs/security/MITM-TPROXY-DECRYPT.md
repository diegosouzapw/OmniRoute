TPROXY-ის გამჭვირვალე გაშიფვრა OmniRoute-ის **მე-5 ჩაჭერის რეჟიმია**
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM სტეკისთვის. ის Linux-ზე ბირთვის TPROXY-სა და პოლიტიკაზე დაფუძნებული მარშრუტიზაციის გამოყენებით იჭერს და **შიფრავს ხსნის** ლოკალურ გამავალ HTTPS ტრაფიკს — `/etc/hosts`-ის გაყალბებისა და
OS-ის მასშტაბით სისტემური პროქსის პარამეტრების შეცვლის **გარეშე**. ის მოსახერხებელია
უგრაფიკო გარემოებისთვის (გასასუფთავებელი DNS ცვლილებების გარეშე), ხოლო firewall-ის წესები გადატვირთვისას ავტომატურად იშლება.

ჩაჭერის სხვა რეჟიმებისგან განსხვავებით, TPROXY-ს თითოეული ჰოსტისთვის ცალკე გამართვა არ სჭირდება: ის გამჭვირვალედ
იჭერს **ნებისმიერი** დანიშნულების ჰოსტის ტრაფიკს სამიზნე პორტზე, ასრულებს TLS-ს
ფოთლოვანი სერტიფიკატით, რომელსაც თითოეული SNI ჰოსტის სახელისთვის დინამიკურად გასცემს, იწერს გაშიფრულ
მიმოცვლას და მოთხოვნას თავდაპირველი დანიშნულების მისამართისთვის ხელახლა შიფრავს.

> **მხოლოდ Linux-ისთვის, მხოლოდ root-ისთვის, საჭიროებს პირდაპირ ჩართვას.** ეს რეჟიმი საჭიროებს Linux-ს, C ინსტრუმენტთა ჯაჭვით აგებულ ნატიურ addon-ს
> და **CAP_NET_ADMIN** შესაძლებლობას (როგორც წესი, root-ს). მასზე წვდომა
> შემოიფარგლება მხოლოდ loopback-ზე მომუშავე AgentBridge API-ით და ნაგულისხმევად გამორთულია. სანდო
> MITM CA, რომელსაც ნებისმიერი ჰოსტისთვის ხელმოწერა შეუძლია, მძლავრი შესაძლებლობაა — იხილეთ [§6 უსაფრთხოება](#6-security).

**წყარო:** `src/mitm/tproxy/`
**API მარშრუტი:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`

## §1 რა არის და როდის უნდა გამოიყენოთ

ჩაჭერის დანარჩენ ოთხ რეჟიმს თითო შეზღუდვა აქვს:

| რეჟიმი            | როგორ ხდება ტრაფიკის მიმართვა                               | შეზღუდვა                                                     |
| ----------------- | ----------------------------------------------------------- | ------------------------------------------------------------ |
| AgentBridge       | `/etc/hosts`-ში ფიქსირებული ჰოსტების ნაკრების DNS გაყალბება | მხოლოდ რეგისტრირებული IDE-აგენტის ჰოსტები                    |
| მორგებული ჰოსტები | `/etc/hosts`-ში თითოეული ჰოსტისთვის DNS გაყალბება           | თითო ჰოსტზე ერთი ჩანაწერი; ჰოსტების შესაცვლელად საჭიროა sudo |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` გარემო                           | მხოლოდ ის აპები, რომლებიც გარემოს ცვლადს ითვალისწინებენ      |
| სისტემური პროქსი  | OS-ის პროქსის პარამეტრები                                   | ცვლის გლობალურ მდგომარეობას; საჭიროებს უკუგდებას             |

ამის ნაცვლად, TPROXY-ის გამჭვირვალე გაშიფვრა ტრაფიკს **ბირთვის** დონეზე მიმართავს. ის
`mangle OUTPUT` ჯაჭვში სამიზნე პორტისკენ (ნაგულისხმევად `443`) მიმართულ ახალ ლოკალურ გამავალ TCP კავშირებს
ნიშნავს, `ip rule` მონიშნულ პაკეტებს ლოკალურ მიწოდებაზე გადაამისამართებს,
ხოლო ხელახლა შემოსვლისას `mangle PREROUTING`-ის `TPROXY` სამიზნე მათ
**IP_TRANSPARENT** მსმენელს გადასცემს — რომელიც შემდეგ TLS-ს ასრულებს და ღია ტექსტს იწერს.

გამოიყენეთ, როდესაც გსურთ ჩაიჭიროთ და გაშიფროთ ტრაფიკი პროცესიდან, რომელიც:

- უკავშირდება ჰოსტს, რომელსაც AgentBridge არ არეგისტრირებს, და
- არ ითვალისწინებს `HTTP_PROXY`-ს, და
- არ გსურთ მისი მუშაობის დარღვევა სისტემური პროქსის შეცვლით.

რადგან ჩაჭერა ბირთვში ხდება, საწყის პროცესს კონფიგურაციის **არანაირი
ცვლილება** არ სჭირდება — თუმცა პროცესი უნდა ენდობოდეს დინამიკურ CA-ს, რომელსაც OmniRoute
აყენებს (იხილეთ [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 მოთხოვნები

| მოთხოვნა             | დეტალები                                                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**               | მხოლოდ Linux — **IP_TRANSPARENT** სოკეტის მხოლოდ Linux-ზე ხელმისაწვდომი პარამეტრია. ყველა სხვა პლატფორმაზე ჩამტვირთავი აბრუნებს „unavailable“-ს.                |
| **პრივილეგია**       | გამჭვირვალე სოკეტის შესაქმნელად და `iptables`/`ip` წესების გამოსაყენებლად საჭიროა **CAP_NET_ADMIN** შესაძლებლობა — პრაქტიკაში, გაუშვით root-ის სახელით.         |
| **ნატიური დამატება** | უნდა აიგოს ან წინასწარ აგებული სახით გავრცელდეს მცირე N-API დამატება (`src/mitm/tproxy/native/transparent.c`). იხილეთ [§3](#3-the-native-ip_transparent-addon). |
| **ბირთვის მოდულები** | `iptables` `TPROXY`, `mangle` და `mark` დამთხვევების მხარდაჭერით (შემოწმებულია kernel 6.8.0-ზე).                                                                |

**შეუფერხებელი დეგრადაცია:** თუ რომელიმე მოთხოვნა არ სრულდება (არა-Linux სისტემა, ხელსაწყოთა ჯაჭვის არარსებობა,
აუგებელი დამატება), დამატების ჩამტვირთავი (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
გამონაკლისის წარმოქმნის ნაცვლად აბრუნებს `null`-ს. ამის შემდეგ დაფიქსირების რეჟიმის სტატუსი აჩვენებს
`available: false`-ს, საინფორმაციო დაფაზე გადამრთველი **გამორთულია** შემდეგი მინიშნებით:
„TPROXY გაშიფვრა მოითხოვს Linux-ს + root-ს + ნატიურ დამატებას“, ხოლო
OmniRoute-ის დანარჩენი ნაწილი მუშაობას აგრძელებს.

## §3 ნატიური IP_TRANSPARENT დამატება

Node-ის `net` მოდულს არ შეუძლია `setsockopt(IP_TRANSPARENT)`-ის გამოძახება _`bind()`-მდე_, რასაც
TPROXY მოითხოვს (წინააღმდეგ შემთხვევაში ბირთვი გადამისამართებულ პაკეტებს უარყოფს). დამატება
(`src/mitm/tproxy/native/transparent.c`, აგებული `binding.gyp`-ის მეშვეობით) არის მცირე N-API
მოდული, რომელიც სამ ფუნქციას გვთავაზობს და `transparentSocket.ts`-ის მეშვეობით გამოიყენება:

| დამატების ფუნქცია                     | სოკეტთან შესრულებული მოქმედება                                                                         | გამოყენება                                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, აბრუნებს დაუმუშავებელ fd-ს | გამჭვირვალე დაფიქსირების მსმენელი (Node ითვისებს fd-ს `server.listen({ fd })`-ის მეშვეობით) |
| `setSocketMark(fd, mark)`             | არსებულ fd-ზე `setsockopt` **SO_MARK**                                                                 | ციკლის თავიდან აცილება (პროქსის საკუთარი სოკეტების მონიშვნა)                                |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** არაბლოკირებად `connect()`-მდე, აბრუნებს fd-ს                                  | ხელახლა დაშიფრული აღმავალი გადაგზავნა (SYN შეიცავს ნიშანს)                                  |

საწყისი დანიშნულება იკითხება `socket.localAddress`/`localPort`-დან — TPROXY
მას ინარჩუნებს, ამიტომ **SO_ORIGINAL_DST**/NAT ძიება საჭირო არ არის.

### დამატების აგება

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- `npm run build`-ის დროს `scripts/build/build-tproxy-native.mjs` უშვებს `node-gyp
rebuild`-ს. ის **მხოლოდ Linux-ზე მუშაობს და შეცდომა ფატალური არ არის** — ხელსაწყოთა ჯაჭვის არარსებობის შემთხვევაში
  დაფიქსირების რეჟიმი უბრალოდ მიუწვდომელი რჩება.
- `assembleStandalone.mjs` აკოპირებს `build/Release/transparent.node`-ს
  დამოუკიდებელ პაკეტში; `transparentSocket.ts` მას პოულობს როგორც მოდულის, ისე

## §4 თითოეული SNI-სთვის დინამიკური CA და ნდობის საცავის ინსტალატორი

> **#6684 განახლება:** AgentBridge-ის სტატიკური სერვერი (`src/mitm/server.cjs`) ახლა
> ერთი სტატიკური, თვითხელმოწერილი leaf-სერტიფიკატის ნაცვლად იმავე CA/leaf არქიტექტურულ
> შაბლონს იყენებს. ის იყენებს **ცალკე** CA ეგზემპლარს
> (`src/mitm/cert/rootCa.ts`, რომელიც ინახება `<DATA_DIR>/mitm/ca.key`/`ca.crt`-ში)
> და თავსდება ნდობის საცავის უკვე არსებულ `omniroute-mitm.crt` სლოტში
> (იქ ძველი ერთი leaf-სერტიფიკატის ჩანაცვლებით — ორმაგი ნდობის გასუფთავება საჭირო არ არის),
> რომელიც სრულად განცალკევებულია ქვემოთ აღწერილი TPROXY-ის საკუთარი
> `omniroute-tproxy-ca.crt` სლოტისგან.
> AgentBridge-ის ახალი ინსტალაციები CA მოდელს ავტომატურად იღებენ; ინსტალაცია,
> რომელიც უკვე ენდობოდა ძველ სტატიკურ leaf-სერტიფიკატს, მის გამოყენებას აგრძელებს,
> სანამ ოპერატორი `MITM_ROOT_CA_ENABLED=true`-ის მეშვეობით არ ჩართავს ახალ მოდელს
> (იხილეთ `src/mitm/cert/migration.ts`) — სანდო MITM CA, რომელსაც შეუძლია
> **ნებისმიერი** ჰოსტისთვის leaf-სერტიფიკატის ხელმოწერა, არსებითად უფრო ძლიერია,
> ვიდრე ძველი, ფიქსირებული SAN-ის მქონე leaf-სერტიფიკატი, ამიტომ უკვე სანდოდ
> მიჩნეულ ინსტალაციაში გადართვა არასოდეს ხდება შეუმჩნევლად.

ისტორიულად, AgentBridge-ის სტატიკური MITM სერტიფიკატი მხოლოდ იმიტომ მუშაობდა,
რომ AgentBridge DNS-ის გაყალბებას ახდენს ჰოსტების **ფიქსირებული** ნაკრებისთვის
(რომელიც ახლა ქვემოთ მოცემულ მოდელთან არის გაერთიანებული). TPROXY
**ნებისმიერ** ჰოსტს იჭერს, ამიტომ მისმა მსმენელმა უნდა წარადგინოს მოქმედი
leaf-სერტიფიკატი ნებისმიერი SNI-სთვის, რომელსაც კლიენტი მოითხოვს — იგივე
მოთხოვნა ახლა AgentBridge-საც აქვს `MITM_TOOL_HOSTS`-ის სრული ნაკრებისთვის
(ინსტრუმენტის 9 ჩანაწერი), ნაცვლად მხოლოდ 4 antigravity ჰოსტისა.

### დინამიკური CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` მართავს ლოკალურ CA-ს (`selfsigned` დამოკიდებულებაზე აგებულს), რომელიც:

- `generateMitmCa()`-ის მეშვეობით ქმნის ხანგრძლივი მოქმედების CA-ს
  (CN `"OmniRoute MITM CA"`, მოქმედების ვადა 10 წელი,
  `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-ბიტიანი RSA / SHA-256).
- მოთხოვნისას `issueLeafCert()`-ის მეშვეობით გასცემს **leaf-სერტიფიკატს თითოეული SNI ჰოსტის სახელისთვის**
  (მოქმედების ვადა 1 წელი, `subjectAltName` = SNI ჰოსტი) და თითოეული ჰოსტის
  სახელისთვის ერთ `tls.SecureContext`-ს კეშირებს.
- TLS-ის დამსრულებელი სერვერისთვის ხელმისაწვდომს ხდის `createSNICallback()`-ს
  (იხილეთ [§5](#5-how-decrypt-and-capture-work)).
- შესაძლებელია მისი შექმნა `existingCa`-ს გამოყენებით, რათა CA გადატვირთვებს
  შორის უცვლელი დარჩეს (და ნდობის საცავში ხელახლა ინსტალაცია საჭირო არ გახდეს).

CA-ს პირადი გასაღები **არასოდეს ტოვებს მოწყობილობას**.

### ნდობის საცავის ინსტალატორი (`src/mitm/tproxy/caTrust.ts`)

ჩაჭერილი კლიენტი დინამიკურ CA-ს უნდა ენდობოდეს, ამიტომ ჩაჭერის რეჟიმის
გაშვებისას CA სერტიფიკატი ოპერაციული სისტემის ნდობის საცავში **ცალკე სლოტში**
ინსტალირდება — `omniroute-tproxy-ca.crt` (კონსტანტა `TPROXY_CA_CERT_NAME`) —
და განცალკევებულია სტატიკური MITM სერტიფიკატის სლოტისგან
(`omniroute-mitm.crt`), რათა მათ არასოდეს გადაწერონ ერთმანეთი.

`installTproxyCa(caPem, sudoPassword?)` განსაზღვრავს დისტრიბუტივის anchor
დირექტორიას (თანმიმდევრობით: ჯერ Debian-ის სტილის) და შესაბამის განახლების
ბრძანებას უშვებს:

| Anchor დირექტორია                           | განახლების ბრძანება      |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ინსტალაციისას PEM თავსდება დროებით ფაილში, შემდეგ კი (პრივილეგირებულად)
`mkdir -p` ქმნის anchor დირექტორიას, `cp` მომზადებულ ფაილს მასში აკოპირებს
და განახლების ბრძანებას უშვებს. `uninstallTproxyCa()` მხოლოდ გამოყოფილ სლოტს
შლის (სტატიკურ MITM სერტიფიკატს ხელუხლებლად ტოვებს) და განახლებას ასრულებს —
არა-Linux სისტემებზე ეს ოპერაცია არაფერს აკეთებს.

ყველა პრივილეგირებული ბრძანება სრულდება `execFileWithPassword`-ის
(`src/mitm/systemCommands.ts`) მეშვეობით — `spawn` **არგუმენტების მასივებით,
shell-ისა და სტრიქონების ინტერპოლაციის გარეშე** (მკაცრი წესი #13).
როდესაც პროცესი root-ის სახელით მუშაობს (მაგალითად, VPS-ზე), სამიზნე ბრძანება
პირდაპირ სრულდება და პაროლი საჭირო არ არის; არა-root დესკტოპზე `sudoPassword`
stdin-ის საშუალებით გადაეცემა `sudo -S`-ს.

> დესკტოპის `sudoPassword` ნდობის საცავში ინსტალაციის ავტორიზაციისთვის POST-ის
> body-ში გადაიცემა; როდესაც პროცესი root-ის სახელით მუშაობს, ის სრულად
> იგნორირდება.

## §5 როგორ მუშაობს გაშიფვრა და ჩაჭერა

კონვეიერი (მთლიანად `src/mitm/tproxy/`-ში):

```
ლოკალური აპი  ──TCP/443──▶  mangle OUTPUT კავშირს მონიშნავს (fwmark)
                             ip rule → ლოკალური მარშრუტიზაციის ცხრილი → lo
                             mangle PREROUTING TPROXY → IP_TRANSPARENT მსმენელი (პორტი 8443)
                                 │  captureMode.ts: თავდაპირველ დანიშნულებას socket.localAddress-იდან კითხულობს
                                 ▼
                             tlsCapture.ts:
                               1. CLIENT-ის TLS-კავშირის დასრულება თითოეული SNI-სთვის განკუთვნილი ფოთლოვანი სერტიფიკატით (dynamicCert)
                               2. შიდა http.Server გაშიფრულ ღია ტექსტს აანალიზებს
                               3. ჩაჭერა → globalTrafficBuffer.push() წყაროთი: "tproxy"
                                  (გამოყენებულია sanitizeHeaders + maskSecret)
                               4. თავდაპირველ დანიშნულებისკენ ხელახლა დაშიფრული სახით გადაგზავნა
                                  გვერდის ავლის ნიშნით მონიშნული სოკეტით (connectMarked, მარყუჟის საწინააღმდეგო)
                                 │
                                 ▼
                             თავდაპირველი ზედა დონის სერვერი (api.example.com)
```

- **TLS-კავშირის დასრულება** (`createTlsCaptureServer`): დინამიკური CA-ის SNI-უკუგამოძახების გამოყენებით, დაუმუშავებელ ჩაჭერილ
  სოკეტს სერვერის მხარის `tls.TLSSocket`-ში ახვევს,
  შემდეგ კი გაშიფრულ ნაკადს შიდა `http.Server`-ს გადასცემს (სტანდარტული MITM
  დასრულების ხერხი). სოკეტების არსებობის ხანგრძლივობა შეზღუდულია `MITM_IDLE_TIMEOUT_MS`-ით, რათა
  გაჭედილმა გვირაბმა ფაილის დესკრიპტორები ვერ ამოწუროს.
- **ჩაჭერა** (`handleDecryptedRequest`): ამატებს `InterceptedRequest`-ს
  `source: "tproxy"`-ით, საწყისი სტატუსით `"in-flight"`; ბუფერში
  მოხვედრამდე სათაურები მუშავდება `sanitizeHeaders()`-ით, ხოლო სხეულები — `maskSecret()`-ით.
  შემდეგ ჩანაწერი ახლდება პასუხით, ზომებითა და დაყოვნებით.
- **ხელახლა დაშიფრული გადაგზავნა** (`createForward` / `realForward`): მონაცემებს ხელახლა შიფრავს და
  თავდაპირველი დანიშნულებისკენ აგზავნის. `rejectUnauthorized`-ის ნაგულისხმევი მნიშვნელობაა **`true`** (ნაგულისხმევად
  უსაფრთხო) — ზედა დონის სერვერის სერტიფიკატი მოწმდება კლიენტის მიერ მოთხოვნილი
  SNI/Host-ის მიმართ, ამიტომ პროქსი უარყოფს ზუსტად იმას, რასაც თავდაპირველი კლიენტი უარყოფდა.

### მარყუჟის საწინააღმდეგო დაცვა (SO_MARK)

რადგან წესები ახალ ლოკალურ გამავალ კავშირებს ნიშნავენ, პროქსის **საკუთარი**
ხელახლა დაშიფრული გადაგზავნა ჩვეულებრივ კვლავ ჩაიჭრებოდა — წარმოიქმნებოდა უსასრულო მარყუჟი.
გადაგზავნის გზა ამისგან თავს იცავს გვერდის ავლის სოკეტის ნიშნით (**SO_MARK**):

- `realForward` თავის ზედა დონის სერვერის სოკეტს ხსნის `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`-ის მეშვეობით
  — `DEFAULT_BYPASS_MARK = 0x539` — რომელიც **SO_MARK**-ს `connect()`-მდე აყენებს,
  ამიტომ გადაგზავნის SYN გვერდის ავლის ნიშნით გადაიცემა.
- `mangle OUTPUT`-ის წესი გამორიცხავს კავშირებს, რომლებსაც გვერდის ავლის ნიშანი უკვე აქვთ
  (`-m mark ! --mark <bypassMark>`), ამიტომ პროქსის გადაგზავნა ხელახლა **არ** ინიშნება
  და TPROXY-ში აღარ შედის.

> იმპლემენტაციის შენიშვნა: გვერდის ავლის ნიშნით მონიშნული სოკეტი აგენტის
> `createConnection`-ზე უნდა დაინსტალირდეს (`https.request({ createConnection })` უხმაუროდ იგნორირდება,
> როდესაც აგენტი არსებობს), წინააღმდეგ შემთხვევაში გადაგზავნა უნიშნო სოკეტს გახსნიდა და
> მარყუჟი დაბრუნდებოდა. ეს იყო e2e-ით დადასტურებული მარყუჟის საწინააღმდეგო შესწორება.

## §7 ფაირვოლის ტრანზაქციული გამოყენება / გაუქმება

ავარიულმა გათიშვამ არასოდეს უნდა დატოვოს `mangle`-ის წესი ან მოძველებული მარშრუტი. ბრძანებების გენერატორი
(`src/mitm/tproxy/commands.ts`) და შემსრულებელი (`src/mitm/tproxy/setup.ts`) უზრუნველყოფენ, რომ
**გაუქმება გამოყენების ზუსტი შებრუნებული ოპერაციაა და შებრუნებული თანმიმდევრობით სრულდება**.

`applyTproxy(cfg)` გამოყენების ბრძანებებს თანმიმდევრობით ასრულებს; **ნებისმიერი** შეცდომის შემთხვევაში ის
მთლიანი `revertTproxy(cfg)`-ის შესრულებას მაქსიმალურად ცდილობს და შემდეგ შეცდომას ხელახლა აგდებს — ამგვარად, ფაირვოლის
კონფიგურაცია ან სრულად გამოიყენება, ან სრულად უქმდება და არასოდეს რჩება ნაწილობრივ გამოყენებული. `revertTproxy(cfg)`
შებრუნებულ ბრძანებებს უკუთანმიმდევრობით ასრულებს და შეცდომებს უგულებელყოფს (იდემპოტენტურია — მისი უპირობოდ გამოძახება
უსაფრთხოა, მაგალითად, AgentBridge-ის `repairMitm()`-ის გასუფთავებისას).

`validateTproxyConfig(cfg)` ნებისმიერი ბრძანების წინ სრულდება: პორტები უნდა იყოს `1–65535` დიაპაზონში,
`mark`/`routeTable`/`bypassMark` უნდა იყოს დადებითი მთელი რიცხვები, ხოლო `bypassMark`
უნდა განსხვავდებოდეს `mark`-ისგან (ციკლის თავიდან ასაცილებლად).

### გამოყენების ბრძანებები (თანმიმდევრობით)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

გაუქმებისას ისინი უკუთანმიმდევრობით იშლება: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> ეს რეცეპტი **OUTPUT-ზეა დაფუძნებული**, რადგან MITM-ის გამოყენების შემთხვევა _ლოკალური_ გამავალი
> ტრაფიკია (იმავე ჰოსტზე გაშვებული აპლიკაციები), რომელსაც მხოლოდ `PREROUTING`-ში არსებული TPROXY
> ვერ ხედავს — `PREROUTING` მხოლოდ გადამისამართებულ ტრაფიკს ხედავს. `OUTPUT` ჯაჭვი ახალ
> ლოკალურ კავშირებს ნიშნავს, `ip rule` მათ ლოკალური მიწოდებისკენ (`lo`) გადაამისამართებს, ხოლო
> შემდეგ `PREROUTING` მათ გამჭვირვალე მსმენელს მიაკუთვნებს.

## §8 კონფიგურაცია

გაშვების მოთხოვნა (`POST /api/tools/agent-bridge/tproxy`) იღებს შემდეგ
ველებს, რომლებსაც `StartTproxyBodySchema` (`tproxy/route.ts`) ამოწმებს. ყველა მათგანი არასავალდებულოა
და მიუთითებლობის შემთხვევაში ნაგულისხმევ მნიშვნელობებს იყენებს:

| ველი             | ტიპი               | ნაგულისხმევი | შენიშვნები                                                                                                                                            |
| ---------------- | ------------------ | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`        | დანიშნულების TCP პორტი, რომლის გამჭვირვალედ ჩაჭერაც უნდა მოხდეს                                                                                       |
| **mark**         | int (≥1)           | `0x2333`     | `OUTPUT`-ში დაყენებული ფაირვოლის ნიშანი, რომელსაც `ip rule` + `PREROUTING` ამოიცნობს                                                                  |
| **onPort**       | int (1–65535)      | `8443`       | პორტი, რომელსაც გამჭვირვალე (**IP_TRANSPARENT**) მსმენელი უკავშირდება                                                                                 |
| **routeTable**   | int (≥1)           | `233`        | პოლიტიკაზე დაფუძნებული მარშრუტიზაციის ცხრილის იდენტიფიკატორი, რომელიც `local 0.0.0.0/0` მარშრუტს შეიცავს                                              |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`      | გვერდის ავლის სოკეტის ნიშანი (**SO_MARK**), რომელსაც პროქსი საკუთარ აღმავალ კავშირებზე აყენებს; გამორიცხულია `OUTPUT`-ში (ციკლის თავიდან ასაცილებლად) |
| **sudoPassword** | string             | —            | მხოლოდ არა-root დესკტოპებისთვის: სანდო სერტიფიკატების საცავში ინსტალაციის ავტორიზაციას ახდენს; root-ის შემთხვევაში უგულებელყოფილია                    |

TPROXY-სთვის **გარემოს ცვლადები არ არსებობს** — მთელი კონფიგურაცია POST მოთხოვნის
სხეულით ან ზემოთ მოცემული ნაგულისხმევი მნიშვნელობებით განისაზღვრება.

1. გახსენით **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).

   აგებს დინამიკურ CA-ს, ხსნის გამჭვირვალე მსმენელს, იყენებს ქსელთაშორისი ეკრანის
   წესებს და CA-ს ოპერაციული სისტემის სანდო სერტიფიკატების საცავში აყენებს.

   ქსელთაშორისი ეკრანის წესებს.

გადაღების რეჟიმის სტატუსი (გაშვებულია / ხელმისაწვდომია / გადაჭერების რაოდენობა / მსმენელის პორტი)

## §10 პრობლემების მოგვარება

### გადამრთველი გამორთულია

ნატიური დამატების ჩატვირთვა შეუძლებელია. დარწმუნდით, რომ: იყენებთ Linux-ს, აგებული გაქვთ დამატება
(`npm run build:native:tproxy`) და პროცესს შეუძლია `transparent.node`-ის ჩატვირთვა.
გადამრთველის ხელმისაწვდომობას `isTransparentSocketAvailable()` აკონტროლებს; როდესაც დამატება არ არის,
`GET /api/tools/agent-bridge/tproxy` აბრუნებს `available: false`-ს.

### არაფერი გადაიჭირება

- დარწმუნდით, რომ გადასაჭერი პროცესი ნამდვილად უკავშირდება კონფიგურირებულ `dport`-ს
  (ნაგულისხმევად `443`).
- დარწმუნდით, რომ პროცესი ენდობა დინამიკურ CA-ს. CA დაყენებულია სახელით
  `omniroute-tproxy-ca.crt`; აპებში, რომლებსაც საკუთარი სანდო სერტიფიკატების საცავი აქვთ (Firefox/Chrome NSS),
  შესაძლოა სერტიფიკატის იქ დამატებაც გახდეს საჭირო.
- სერტიფიკატის სანდოობისა და სერვერის მდგომარეობის შესამოწმებლად გაუშვით AgentBridge-ის
  **Diagnose** თვითტესტი (იხილეთ
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)).

### ავარიის შემდეგ დარჩენილი ქსელთაშორისი ეკრანის წესები

`revertTproxy()` გამოყენების ოპერაციის ზუსტი შებრუნებული მოქმედებაა და იდემპოტენტურია. რეჟიმის
გაჩერება წესებს აუქმებს; თუ OmniRoute სესიის მიმდინარეობისას იძულებით გაითიშა, გამოიყენეთ AgentBridge-ის
**Repair** მოქმედება (`POST /api/tools/agent-bridge/repair`) ობლად დარჩენილი სისტემური
მდგომარეობის გასაუქმებლად (DNS-ის გაყალბება, ძირეული CA, სისტემური პროქსი). TPROXY-ის `mangle`
წესები და მარშრუტიც ავტომატურად იშლება გადატვირთვისას.

### უსასრულო ციკლი / პროქსი საკუთარ გადაგზავნას გადაჭერს

ეს ციკლის საწინააღმდეგო შემთხვევაა. დარწმუნდით, რომ `bypassMark` განსხვავდება `mark`-ისგან (ამას
ვალიდაცია უზრუნველყოფს) და გადაგზავნა `connectMarked`-ს იყენებს (ასეც ხდება `realForward`-ში).
იხილეთ [§5 ციკლის საწინააღმდეგო მექანიზმი](#anti-loop-so_mark).
