## სამართლებრივი და ეთიკური შეტყობინება

შენიღბვის ფუნქციები არსებობს იმისთვის, რომ OmniRoute-მა იმოქმედოს თავსებადობის შრის სახით მომხმარებლის საკუთრებაში არსებულ ოფიციალურ ანგარიშებსა (Claude Code CLI, Codex, Antigravity, Cursor და სხვ.) და OmniRoute-ის ერთიან API-ს შორის. ისინი **არ არის** განკუთვნილი თაღლითობის გამოვლენის მექანიზმებისთვის თავის ასარიდებლად, ავტორიზაციის მონაცემების გასაზიარებლად ან პროვაიდერის მომსახურების პირობების დასარღვევად. მომვლელები მოელიან, რომ ოპერატორები დაიცავენ იმ ზედა დონის პროვაიდერის ToS-ს, რომელსაც ანგარიშების შექმნისას დაეთანხმნენ.

## TLS თითის ანაბეჭდის შრე

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

მუდმივი `wreq-js` სესიები თითოეული ანგარიშის არეალისა და განსაზღვრული პროქსისთვის ზარმაცად იქმნება. პროცესის მასშტაბით მოქმედი `TlsClient` მაქსიმუმ 128 სესიას აერთიანებს, რომლებიც Cloudflare-ის მიღმა არსებული ზედა დონის სერვისებისთვის **Chrome 124-ს macOS-ზე** განასახიერებს. როდესაც ნატიური შესრულების გარემო მიუწვდომელია, `TlsClient.fetch()` უსაფრთხოების მიზნით შეცდომით სრულდება; გამომძახებელს შეუძლია ამ გარსის გარეთ ცხადად აირჩიოს სარეზერვო ვარიანტი.

- სესიის პროფილი: `browser: "chrome_124", os: "macos"`
- პროქსის განსაზღვრა (პრიორიტეტი): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (ასევე ქვედა რეგისტრით)
- მოლოდინის ვადა: `TLS_CLIENT_TIMEOUT_MS` (მემკვიდრეობით იღებს `FETCH_TIMEOUT_MS`-დან, ნაგულისხმევად 600000)
- `wreq-js` Response თავსებადია fetch-თან (`headers`, `text()`, `json()`, `clone()`, `body`).
- პირველი ბაიტის საკონტროლო მექანიზმი (`open-sse/utils/tlsFirstByteWatchdog.ts`, #12656): `TlsClient.fetch()`
  სრულდება ზედა დონის სერვისიდან სათაურების მიღებისთანავე, ამიტომ მხოლოდ `TLS_CLIENT_TIMEOUT_MS` ვერ შეზღუდავს
  სხეულს, რომელიც პირველ ბაიტს არასდროს აბრუნებს. `guardTlsFirstByte()` სხეულის პირველ `read()`-ს
  `TLS_FIRST_BYTE_WATCHDOG_MS`-ს უპირისპირებს (ნაგულისხმევად `10000`, `0` მას გამორთავს); გამართული სხეული
  უცვლელი რჩება, ხოლო გაჩერებული სხეულის შემთხვევაში wreq წამკითხველი უქმდება და `proxyFetch`-ის არსებული
  TLS სარეზერვო ლოგიკა პირდაპირ/პროქსი დისპეტჩერზე გადადის (განმეორებით გასაშვებად სახიფათო მოთხოვნა, მაგალითად,
  სხეულის მქონე POST, ჩუმად ხელახლა ცდის ნაცვლად კვლავ შეცდომას გამოიტანს).

### ვებ-ქუქიზე დაფუძნებული პროვაიდერის ტრანსპორტი — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` ქვემოთ მოცემული ხუთი სპეციალიზებული ვებ-ქუქი ტრანსპორტის
საერთო ადაპტერია. თითოეული თხელი პროვაიდერის გარსი ბრაუზერის/OS-ის პროფილს ირჩევს. ადაპტერი
იყენებს `open-sse/utils/tlsClient.ts`-ში არსებულ ერთადერთ wreq შესრულების გარემოს ჩამტვირთველსა და
ტრანსპორტების პულს, რომლებიც პროფილის + OS-ის + განსაზღვრული პროქსის მიხედვით არის გასაღებებით დაყოფილი,
ხოლო ყოველი მოთხოვნა იყენებს `cookieMode: "ephemeral"`-ს. შესაბამისად, ანგარიშები და მოთხოვნები
ტრანსპორტის დონის კავშირებს იზიარებენ, მაგრამ არასდროს იზიარებენ wreq სესიას ან ქუქი-ფაილების საცავს.

| პროვაიდერი | პროფილი       | ემულირებული OS | ნაკადის EOF-ის პოლიტიკა                  |
| ---------- | ------------- | -------------- | ---------------------------------------- |
| Claude     | `chrome_146`  | Linux          | `[DONE]`-ის ჩათვლით                      |
| Perplexity | `firefox_148` | macOS          | `event: end_of_stream`-ის ჩათვლით        |
| Grok       | `chrome_146`  | Linux          | `[DONE]`-ის გამოკლებით                   |
| Notion     | `chrome_146`  | Windows        | `[DONE]`-ის ჩათვლით                      |
| LMArena    | `chrome_146`  | Windows        | სენტინელის გარეშე; დახურვა ნატიურ EOF-ზე |

- სტრიმინგი უშუალოდ მოიხმარს ნატიური პასუხის `ReadableStream`-ს; დროებითი ფაილი ან დამხმარე პროცესი
  არ იქმნება.
- ნაკადის ხელმისაწვდომობამდე მოწმდება მაქსიმუმ 256 საწყისი ბაიტი. SSE პროვაიდერები არა-SSE
  შეცდომებს ბუფერიზაციას უკეთებენ; Grok/LMArena Cloudflare-ის გამოწვევებს `403`-ად, ხოლო HTML-ის შუალედურ გვერდებს `502`-ად გარდაქმნიან.
- ნატიური მოთხოვნის მოლოდინის ვადას კვლავ ფარავს JS-ის აბსოლუტური მკაცრი ვადა. გაჭედვა აუქმებს
  და ხურავს მხოლოდ შესაბამისი პროფილის/OS-ის/პროქსის ტრანსპორტს, ვიდრე მომდევნო მოთხოვნა მას ხელახლა შექმნის.
- პროქსის განსაზღვრის პრიორიტეტია: თითოეული გამოძახების `proxyUrl` → მოთხოვნის არეალში არსებული ანგარიშის/სამართავი დაფის კონტექსტი →
  `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (ქვედა რეგისტრის ვარიანტების ჩათვლით). განსაზღვრის შეცდომები
  უსაფრთხოების მიზნით წარუმატებლად სრულდება, პირდაპირი კავშირის გაჟონვის ნაცვლად. LMArena შეგნებულად ახდენს განსაზღვრას `arena.ai`-ს მიმართ.
- `byteResponse` აბრუნებს შიგთავსის ტიპის მქონე `data:` URL-ს UTF-8-ის დაზიანების გარეშე.
- შეცდომებია `TlsClientUnavailableError` (პაკეტი/დამატება მიუწვდომელია), `TlsClientHangError`
  (ვადა გადაცილებულია) და `WreqTransportCapacityError` (საერთო სესიის ტევადობის შეცდომის კოდი),
  როდესაც პროფილის/OS-ის/პროქსის 128-ვე შეზღუდული სლოტი აქტიურია ან იხურება.

ზემოთ აღწერილი ზოგადი `TlsClient` სესია კვლავ სპეციალიზებულია ბრაუზერზე დაფუძნებული ქუქი-მდგომარეობის
მუდმივად შესანარჩუნებლად. ორივე გზა ხელახლა იყენებს ერთ ქეშირებულ wreq მოდულის ჩამტვირთველსა და პროცესის
სასიცოცხლო ციკლის ჰუკს; მათი პულები განცალკევებული რჩება, რადგან მათი ქუქი-ფაილების სიცოცხლის ხანგრძლივობა
განზრახ განსხვავებულია.

პროფილები მხარდაჭერილია დაფიქსირებული პაკეტის მიერ, თუმცა რეალური WAF-ის მხრიდან მიღება შეიძლება ადგილობრივი
კონტრაქტული ტესტებისგან დამოუკიდებლად შეიცვალოს. ზედა დონის ბრაუზერთან პარიტეტის მტკიცებამდე თითის ანაბეჭდის

## Claude Code-ის შენიღბვის პაკეტი

როდესაც `cliCompatMode` ჩართულია, OmniRoute გამავალ Claude-ის მოთხოვნებს ისე გარდაქმნის, რომ ისინი `claude-cli`-ის ტრაფიკისგან განურჩეველი იყოს. ამაზე სამი მოდული ერთობლივად მუშაობს:

### `claudeCodeFingerprint.ts`

ითვლის ბილინგის სათაურში ჩაშენებულ 3-სიმბოლოიან `cc_version` ანაბეჭდს:

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (კოდშია ფიქსირებულად ჩაწერილი; ემთხვევა ოფიციალურ კლიენტს)
- შეყვანა: პირველი მომხმარებლის შეტყობინების ტექსტის მე-4, მე-7 და მე-20 ინდექსებზე არსებული სიმბოლოები + ვერსიის სტრიქონი
- გამომავალი: 3-სიმბოლოიანი თექვსმეტობითი პრეფიქსი

### `claudeCodeCCH.ts` (კლიენტის შიგთავსის ჰეში)

სერვერის მხარეს მთლიანობის შემოწმება, რომელსაც ოფიციალური Claude Code CLI Bun/Zig-ის საშუალებით ითვლის. OmniRoute ამას `xxhash-wasm`-ით ხელახლა ახორციელებს:

1. სხეულის სერიალიზაცია `cch=00000;` ადგილმჭერის გამოყენებით
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. ნულებით შევსებული 5-სიმბოლოიანი, ქვედა რეგისტრის თექვსმეტობითი მნიშვნელობა
4. `cch=00000;`-ის ჩანაცვლება გამოთვლილი ტოკენით

კონსტანტები:

- საწყისი მნიშვნელობა: `0x6e52736ac806831e`
- ნიმუში: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

„სენსიტიური“ კლიენტების სახელების პირველი სიმბოლოს შემდეგ ამატებს Unicode-ის **ნულოვანი სიგანის შემაერთებელს** (`U+200D`), რათა ზედა დონის ფილტრებმა ისინი ტექსტური ძიებით ვერ იპოვონ. სიტყვების ნაგულისხმევი სია:

```
aider, continue.dev, copilot, avante, codecompanion
```

## Antigravity-ის შენიღბვა

Antigravity-ის მოთხოვნები გამომძახებლის ტექსტს ბაიტ-ბაიტ უცვლელად ინარჩუნებს. IDE კლიენტის იმიტაციისთვის OmniRoute მოთხოვნებში ნულოვანი სიგანის სიმბოლოებს არ ამატებს და ხელსაწყოებს არც გადაარქმევს სახელს და არც ამატებს.

### `antigravityHeaderScrub.ts`

გადაგზავნამდე შლის Stainless SDK-ის მარკერებს (`x-stainless-lang`, `x-stainless-package-version`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-timeout`, `x-stainless-retry-count`, `x-stainless-helper-method`).

### ⚠️ რისკი: `ANTIGRAVITY_CREDITS=always` (ანგარიშის დაბლოკვის მაღალი რისკის წერტილი)

`ANTIGRAVITY_CREDITS=always` (`open-sse/executors/antigravity.ts`-ის მიერ გამოიყენება) **ყველა** მოთხოვნას Antigravity AI Credit Overages-ის (Google-ის ფასიანი კრედიტების) მეშვეობით წარმართავს, ნაცვლად იმისა, რომ მოთხოვნები Google-ის უფასო დონის კვოტამ შეზღუდოს. ეს ფუნქციად არის დოკუმენტირებული, მაგრამ ის არის **მომსახურების პირობების დარღვევის შესახებ ჩვენ მიერ მიღებული შეტყობინებების ერთადერთი ყველაზე გავრცელებული მიზეზი** — რამდენიმე Google Ultra ანგარიში დაიბლოკა `403 / "service disabled for ToS violation" / insufficient_quota` პასუხით `=always` რეჟიმში რამდენიმე საათიანი მუშაობის შემდეგ.

ზედა დონის შეზღუდვები მოქმედებს **Google-ის მხარეს** და OmniRoute ამას ვერ აღკვეთს. გარემოს ცვლადის სახელი და არსებული დოკუმენტაცია ქმნის შთაბეჭდილებას, რომ მისი ჩართვა უსაფრთხოა; სინამდვილეში ასე არ არის.

**რატომ იწვევს ეს ბოროტად გამოყენების გამოვლენას უფრო აგრესიულად, ვიდრე მხოლოდ უფასო დონის გამოყენება:**

- ერთ Google ანგარიშზე ხანგრძლივი ავტომატიზებული დანახარჯი განსხვავებულად მონიშვნადია, ვიდრე უფასო დონის კვოტის ამოწურვა და შემდგომი გაჩერება.
- ჭარბი კრედიტების გამოყენებას სიხშირის ზედა ზღვარი არ აქვს, ამიტომ არასწორად კონფიგურირებულ კლიენტს რამდენიმე წუთში რამდენიმე ასეული USD-ის დახარჯვა შეუძლია და ეს შესაძლოა API გასაღების ხელახალ გაყიდვას ან ბოტის ტრაფიკს დაემსგავსოს.
- როდესაც OmniRoute-ის რამდენიმე მომხმარებელი ერთი და იმავე გარე IP-დან ჭარბ კრედიტებს პარალელურად იყენებს, ეს სიგნალს აძლიერებს.

**რეკომენდებული მიდგომა:**

1. შეინარჩუნეთ ნაგულისხმევი `ANTIGRAVITY_CREDITS=off`, თუ ოპერატორი ფასიანი კრედიტებისა და ანგარიშზე სანქციების რისკს ცალსახად არ ეთანხმება. `retry` ჯერ ჩვეულებრივ მოთხოვნას აგზავნის და შესაბამისი კვოტის 429 პასუხის შემდეგ კრედიტებს მაქსიმუმ ერთხელ ამატებს; `always` კრედიტებს პირველივე მოთხოვნაში ამატებს.
2. ერთი Antigravity ანგარიშის გადატვირთვის ნაცვლად, **დატვირთვა პროვაიდერებზე Auto-Combo-ს საშუალებით გაანაწილეთ** (`model: "auto"` ან `kr/glm/etc`-combo).
3. **დააყენეთ თითოეული კავშირის RPM ლიმიტები** Antigravity პროვაიდერის რედაქტირების გვერდზე (Dashboard → Providers → Antigravity → connection → rate limit). უწყვეტი გამოყენებისთვის 30–60 RPM დასაბუთებული ზედა ზღვარია.
4. **გამოიყენეთ სტაბილური, ოპერატორის მიერ კონტროლირებული ზედა დონის ქსელური ინფრასტრუქტურა** და მოერიდეთ ერთი ანგარიშის ერთმანეთთან დაუკავშირებელ მომხმარებლებსა თუ სამუშაო დატვირთვებს შორის გაზიარებას.
5. **დაბლოკვის შემთხვევაში**: გაასაჩივრეთ `support.google.com` → „Restore Workspace/Account access“-ის მეშვეობით და დაურთეთ Google-ის მიერ გამოგზავნილი ზუსტი `quota_exceeded` / `service disabled` პასუხის სხეული. აღდგენა გარანტირებული არ არის.

გარემოს ცვლადების საცნობარო დოკუმენტაცია აღწერს კრედიტების თითოეული რეჟიმის გავლენას ანგარიშსა და დანახარჯებზე.

- `open-sse/executors/antigravity.ts` — კითხულობს `process.env.ANTIGRAVITY_CREDITS`-ს
- `src/lib/oauth/providers/antigravity.ts` — ავტორიზაციის მონაცემების დამუშავება

## MITM პროქსი (Antigravity, Linux/macOS/Windows)

იმ CLI-ებისთვის, რომელთა ბინარული ფაილების გადამისამართებაც `OPENAI_BASE_URL`-ის მეშვეობით შეუძლებელია, OmniRoute უშვებს ლოკალურ TLS-ტერმინირებად პროქსის. საბოლოო წერტილები მდებარეობს `src/app/api/cli-tools/antigravity-mitm/`-ის ქვეშ.

### გაშვების თანმიმდევრობა (`src/mitm/manager.ts::startMitm`)

1. თვითხელმოწერილი სერტიფიკატის გენერირება `selfsigned`-ის მეშვეობით (RSA-2048, SHA-256, 1 წელი) — `cert/generate.ts`
2. სერტიფიკატის დაყენება სისტემის სანდო სერტიფიკატების საცავში — `cert/install.ts`
3. ჰოსტების ჩანაწერის `127.0.0.1 daily-cloudcode-pa.googleapis.com` დამატება — `dns/dnsConfig.ts`
4. `src/mitm/server.cjs`-ის გაშვება `ROUTER_API_KEY` + `MITM_LOCAL_PORT`-ით (ნაგულისხმევი მნიშვნელობაა `443`)
5. PID-ის შენახვა `<DATA_DIR>/mitm/.mitm.pid`-ში

### Linux-ის სანდო სერტიფიკატების საცავის დინამიკური აღმოჩენა — `cert/install.ts`

`getLinuxCertConfig()` ამოწმებს პრიორიტეტულ სიას და ირჩევს პირველ არსებულ დირექტორიას:

| დისტრიბუტივების ოჯახი    | დირექტორია                                  | განახლების ბრძანება      |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

სერტიფიკატის ფაილის სახელი: `omniroute-mitm.crt`. თითის ანაბეჭდის დამთხვევა ხდება `getCertFingerprint()`-ის მეშვეობით (DER-ის SHA-1).

დამატებით, როდესაც `certutil` ხელმისაწვდომია, `updateNssDatabases()` სერტიფიკატს აყენებს თითოეული მომხმარებლის NSS მონაცემთა ბაზებში: `~/.pki/nssdb`, `~/snap/chromium/.../nssdb`, Firefox-ის ყველა პროფილში (snap-ის ჩათვლით), მეტსახელით **`OmniRoute MITM Root CA`**.

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** ადმინისტრატორის უფლებებით გაშვებული PowerShell → `certutil -addstore Root`

### ავთენტიფიკაცია

MITM-ის ყველა საბოლოო წერტილი მოითხოვს მართვის ავთენტიფიკაციას (`requireCliToolsAuth`). sudo-ს პაროლი ინახება მოდულის ხედვის არეში (არასოდეს `globalThis`-ში) და იშლება `stopMitm()`-ის გამოძახებისას.

## თითის ანაბეჭდების განახლება პროვაიდერის მიერ მათი შეცვლისას

1. ჩაიწერეთ ოფიციალური CLI-ის ტრაფიკი `mitmproxy`-ით (TLS-ის ჩაჭრა + დამპი)

3. განაახლეთ შესაბამისი `CLI_FINGERPRINTS[...]` ჩანაწერი
4. გაზარდეთ შესაბამისი `*_USER_AGENT`-ის ნაგულისხმევი ვერსია `.env.example`-ში
5. თუ თავად TLS-ის ხელის ჩამორთმევა შეიცვალა, განაახლეთ შესაბამისი პროვაიდერის გარსი ან wreq-js-ის `browser:` პარამეტრი
6. გაუშვით პროვაიდერისთვის სპეციფიკური TLS-ტესტები და ხელით შესრულებული საცდელი შემოწმება მოქმედ პროვაიდერთან
7. გამოაქვეყნეთ პატჩ-რელიზში; აღწერეთ `CHANGELOG.md`-ში
