ეს დოკუმენტი აღწერს უკუკავშირზე დაფუძნებული ადაპტიური მარშრუტიზაციის საფუძველს, რომელიც
OmniRoute-ს დაემატა. ის განზრახ მცირეა: შემოაქვს ტიპიზებული მარშრუტიზაციის შედეგების
არხი, ონლაინ ხარისხის სიგნალი, რომელიც მონაცემებით ამარაგებს არსებულ auto-combo შეფასების მექანიზმს,
არასავალდებულო OpenTelemetry ექსპორტერი და ახსნადობის საბოლოო წერტილი. ის **არ**
ანაცვლებს მდგრადობის არსებულ სტეკს (ამომრთველი, კავშირის დაყოვნება,
მოდელის დაბლოკვა, ჯანმრთელობის მატრიცა, ავტოპილოტი) — ის ავსებს მას.

## 1. არქიტექტურული კონტექსტი

OmniRoute არის მონაცემთა სიბრტყე, რომელსაც აქვს **მოთხოვნის ცხელი გზა** და **მართვის/ინტელექტის
სიბრტყე**. ცხელი გზა უნდა დარჩეს სწრაფი, მეხსიერების ეფექტიანად გამომყენებელი, ასინქრონული, მდგრადი და
პროგნოზირებადი. შეფასება, ხარისხის ქულების გამოთვლა, ექსპერიმენტები და ისტორიული ანალიზი
მართვის სიბრტყეს ეკუთვნის.

```
AI აგენტი / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   მონაცემთა სიბრტყე (სწრაფი, სინქრონული, მეხსიერებაში)
│  მარშრუტიზაცია /    │
│  გადართვა           │
│  ჯანმრთელობა /      │
│  დამცავი მექანიზმი  │
│  კეში / სტრიმინგი   │
└──────────┬──────────┘
           │ RoutingEvent (გაგზავნა და დავიწყება, ~0.2µs)
           ▼
┌─────────────────────┐
│  უკუკავშირის მიმღებები │   მართვის სიბრტყე (ასინქრონული, შესაძლებლობის ფარგლებში)
│  ხარისხის ტრეკერი   │
│  OTel ექსპორტერი    │
│  განმარტებების საცავი │
└──────────┬──────────┘
           ▼  ხარისხის ქულა
      auto-combo შეფასების მექანიზმი
```

### რაც უკვე არსებობდა (აუდიტირებული, არა დუბლირებული)

| კონცეფცია                                            | არსებული იმპლემენტაცია                                                                                |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| ხელმისაწვდომობა (შეგვიძლია ტრაფიკის გაგზავნა?)       | ამომრთველი (CLOSED/DEGRADED/OPEN/HALF_OPEN, DB-ში შენახული), კავშირის დაყოვნება, მოდელის დაბლოკვა     |
| ჯანმრთელობის ანგარიშგება                             | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                               |
| ჩრდილოვანი ტრაფიკი                                   | `open-sse/services/combo/shadowRouting.ts`                                                            |
| დამცავი მექანიზმები                                  | `src/lib/guardrails/` (წინასწარი/შემდგომი ჰუკები)                                                     |
| ზუსტი კეში                                           | `src/lib/semanticCache.ts` (სიგნატურაზე დაფუძნებული)                                                  |
| შემფასებლები / შეფასებებზე დაფუძნებული მარშრუტიზაცია | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                  |
| Combo გადაწყვეტილების ახსნადობა                      | `open-sse/services/combo/decisionTrace.ts`                                                            |
| დაფის რეალურ დროში მოვლენები                         | `src/lib/events/eventBus.ts` (UI შეტყობინებების არხი, `unknown` დატვირთვები, 100-ჩანაწერიანი ისტორია) |

მარშრუტიზაციის მოვლენების ფენა **არ არის** `eventBus`-ის ხელახალი იმპლემენტაცია: ეს არხი
დაფის რეალურ დროში შეტყობინებების არხია (ტიპიზებული _მოვლენების სახელები_, გაუმჭვირვალე
დატვირთვები, UI მომხმარებლები). `RoutingEvent` არის ტიპიზებული _შედეგის_ სტრუქტურა
(დაყოვნება/ტოკენები/ღირებულება/შედეგი/დასრულების-მიზეზი), რომელსაც მართვის სიბრტყის
უკუკავშირის მიმღებები იყენებენ (ხარისხის ტრეკერი, OTel ექსპორტერი, განმარტებების საცავი).

### რაც აკლდა (აქ დაემატა)

1. **ტიპიზებული მარშრუტიზაციის შედეგის მოვლენა + მიმღების აბსტრაქცია** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` შემოიფარგლება combo-თი და მხოლოდ მეხსიერებაში ინახება;
   `comboMetrics` არის კუმულაციური მრიცხველები; `call_logs` არის დაუმუშავებელი ასინქრონული საცავი.
   არცერთი მათგანი არ წარმოადგენს ტიპიზებულ, მიმღებებზე დაფუძნებულ შედეგების არხს, რომელზეც ხარისხის ტრეკერს, OTel
   ექსპორტერს ან Future-AGI-ის სტილის შემფასებელს შეუძლია გამოწერა.
2. გამომავალი მონაცემების ხარისხის **ონლაინ ხარისხის სიგნალი** (EWMA) — მანამდე შეფასების მექანიზმი
   "ხარისხს" მხოლოდ დავალების სტატიკური შესაბამისობითა და სურვილისამებრ ჩართული შეფასებების წარმატების მაჩვენებლებით
   აფასებდა.
3. GenAI-ის სემანტიკური კონვენციების გამოყენებით შექმნილი **არასავალდებულო, დამოკიდებულებების არმქონე OTel ექსპორტერი**.
4. **ახსნადობის საბოლოო წერტილი**, რომელიც აბრუნებს მარშრუტიზაციის რეალურ გადაწყვეტილებებს + ხარისხის მდგომარეობას.

## 2. მარშრუტიზაციის მოვლენები (უკუკავშირის საფუძველი)

ფაილები: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` შეიცავს მხოლოდ მარშრუტიზაციის მეტამონაცემებს:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // დაშვებული მნიშვნელობების გაერთიანება
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` არის TypeScript-ში `Send+Sync`-ის სტილის ტრეიტი:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // უნდა იყოს O(1), სინქრონული I/O-ის გარეშე
}
```

ცხელი გზა თითოეულ დასრულებულ მოთხოვნაზე ერთხელ იძახებს `emitRoutingEvent(event)`-ს
(სტრიმინგის დასრულების უკუგამოძახება, არასტრიმინგული წარმატების გზა და
არასწორად ფორმირებული 200-პასუხის წარუმატებლობის გზა `handleChatCore`-ში). დისპეტჩერიზაცია
სინქრონულად ანაწილებს მოვლენას რეგისტრირებულ მიმღებებზე, თუმცა თითოეული მიმღები მხოლოდ რიგში
ამატებს მონაცემებს ან განაახლებს მეხსიერებაში არსებულ მდგომარეობას. **ცხელ გზაზე არ ხდება
მონაცემთა ბაზაში სინქრონული ჩაწერა ან ქსელური I/O.**

ნაგულისხმევი მიმღებები:

- `MemoryRoutingEventStore` — შეზღუდული ზომის (500) რგოლური ბუფერი, უახლესიდან უძველესისკენ,
  explain ბოლო წერტილისთვის.
- `QualityTracker` მომხმარებელი — განაახლებს ხარისხის EWMA შეფასებას.
- `OtlpHttpsEventSink` — არასავალდებულო; ჩართულია მხოლოდ მაშინ, როდესაც დაყენებულია
  `OMNIROUTE_OTEL_ENDPOINT` (ან `OTEL_EXPORTER_OTLP_ENDPOINT`).

### გაზომილი ზედნადები ხარჯი (კეთილსინდისიერი შედარება)

`npm run bench:routing-events` ამ სამუშაო სადგურზე (100k იტერაცია; სუბ-მიკროწამიანი
ოპერაციები გაზომილია აგრეგირებული µs/op მნიშვნელობით, რადგან თითოეული ოპერაციის
პროცენტილები `performance.now()` ტაიმერის გარჩევადობაზე დაბალია):

| სცენარი                                     | µs/op  | ops/s  |
| ------------------------------------------- | ------ | ------ |
| საბაზისო (მხოლოდ ქულების გამოთვლა)          | ~0.045 | ~22 M  |
| საბაზისო + RoutingEvent (2 მიმღები)         | ~0.168 | ~5.9 M |
| საბაზისო + მოვლენა + OTel-ის რიგში დამატება | ~0.163 | ~6.1 M |
| კონკურენტული (8 მონაცვლეობითი პაკეტი)       | ~0.18  | —      |

მოვლენების დისპეტჩერიზაციის სხვაობა საბაზისო ქულების გამოთვლასთან შედარებით არის
~0.12 µs/მოთხოვნა; OTel მიმღები მხოლოდ რიგში ამატებს მონაცემებს (O(1) ბუფერში ჩასმა),
ამიტომ გაზომვად დანამატს არ ქმნის. ეს რიცხვები კონკრეტულ მანქანაზეა დამოკიდებული და
ფარდობითია — ისინი საწარმოო გარემოსთვის გარანტიას არ წარმოადგენს. v1-ის "~0.2 µs"
მაჩვენებელი აგრეგირებული შეფასება იყო; ეს მეთოდოლოგია საბაზისო ქულების გამოთვლას
მოვლენების დისპეტჩერიზაციის დანახარჯისგან განცალკევებით ზომავს.

## 3. ხარისხის სიგნალი (უკუკავშირით მართული პროვაიდერის მდგომარეობა)

ფაილები: `open-sse/services/routing/quality.ts`

v2 **ოპერაციულ** ხარისხს **სემანტიკური** ხარისხისგან გამოყოფს:

- **ოპერაციული** — მიიღება მარშრუტიზაციის ცხელი გზიდან (HTTP 4xx/5xx, კავშირის
  წარუმატებლობები, 429-ები, არასწორად ფორმირებული პასუხები, სტრიმის წყვეტები,
  `finish_reason=length`, წარმატებული პასუხები ნულოვანი გამოტანით, დაყოვნების/TTFT-ის
  EWMA). 200-პასუხი სემანტიკურ ხარისხად არ განიხილება.
- **სემანტიკური** — გენერირებული გამოტანის რეალური ღირებულება. წარმოიქმნება მხოლოდ
  შემფასებლის მიერ `setSemanticQuality()`-ის მეშვეობით. მნიშვნელობა არის `null`,
  სანამ შემფასებელი მას არ მიაწვდის, და ის არასოდეს ხვდება ოპერაციულ ქულაში.

მდგომარეობა თითოეული (პროვაიდერი, მოდელი) წყვილისთვის (EWMA + შეზღუდული მრიცხველები):

- `successEwma` — შედეგის წარმატების EWMA (α=0.2).
- `latencyEwma` / `ttftEwma` — დაყოვნების EWMA (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — რამდენად ცოტა ხნის წინ დაფიქსირდა მოდელი უკანასკნელად.

### სანდოობის / ნიმუშების რაოდენობის გათვალისწინება

`confidence = clamp01(samples / 50)`, ხოლო შემფასებლისთვის დაბრუნებული ქულა
ნეიტრალური შუა წერტილისკენ იხრება:

```
score = 0.5 + confidence * (operational - 0.5)
```

შედეგები (დადასტურებულია ტესტებით):

- ცივი პროვაიდერის (0 ნიმუში) ქულაა **0.5** — ის უსამართლოდ არ ჯარიმდება, თუმცა
  ვერც ათასობით სტაბილური დაკვირვების მქონე პროვაიდერზე დომინირებს.
- პროვაიდერი, რომელსაც 7 შემთხვევითი წარმატება აქვს, 0.5-ისკენ გადაიხრება
  (ოპტიმისტური ინიციალიზაციის გამო ის ვერასოდეს დომინირებს).
- 50+ ნიმუშის მქონე პროვაიდერი თავის რეალურ ოპერაციულ ქულას უახლოვდება.
- გაუარესება და აღდგენა თანდათანობითია (EWMA), ხოლო ერთი იზოლირებული წარუმატებლობა
  ჯანმრთელ პროვაიდერს არ ანადგურებს.

`ProviderQuality` ექსპორტს უკეთებს `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`-ს.

ეს მონაცემები auto-combo შემფასებელს `quality` შეფასების ფაქტორად მიეწოდება:

- `ScoringFactors.quality` / `ScoringWeights.quality` ფაილში
  `open-sse/services/autoCombo/scoring.ts`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. ჯამი კვლავ 1.0-ია.
- `buildAutoCandidates` ავსებს `candidate.quality`-ს ტრეკერიდან; მონაცემების არმქონე
  კანდიდატებისთვის ნაგულისხმევია ნეიტრალური **0.5** (ცივი კანდიდატი არც უპირატესობას
  იღებს და არც ჯარიმდება).

დახურული ციკლი:

```
RoutingEvent → QualityTracker → getQualityScore → auto-combo ხარისხის ფაქტორი
      ↑                                                    │
      └────── მოთხოვნის შედეგი (handleChatCore) ←──────────┘
```

### მკაცრი გამორიცხვა რბილი ჯარიმის წინააღმდეგ

ხარისხის სიგნალი მხოლოდ **რბილი ადაპტიური უპირატესობაა**. მკაცრი გამორიცხვა კვლავ
არსებული მდგრადობის სტეკის პასუხისმგებლობად რჩება: ავტომატური ამომრთველი OPEN
მდგომარეობაშია, კვოტა ამოწურულია, ავთენტიფიკაცია წარუმატებელია, მოდელი დაბლოკილია —
ხარისხის ქულა არცერთ მათგანზე არ მოქმედებს. პროვაიდერს, რომლის ხარისხის ქულაც
დროებით ეცემა, ნაკლები უპირატესობა ენიჭება, თუმცა ის მკაცრად არასოდეს ითიშება.

## 3b. ნაკადის კანონიკური ტაიმინგი (TTFT / ITL)

ფაილები: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` არის სტრიმინგის გზის ინსტრუმენტაციის ერთადერთი წერტილი,
რომელიც დაკავშირებულია `createSSEStream`-თან (open-sse/utils/stream.ts):

- `markByte()` — მიღებულია პირველი აღმავალი ნაკადის ფრაგმენტი.
- `markForward()` — პირველი ფრაგმენტი გადაეგზავნა კლიენტს (გამოიყენება TTFT-ისთვის).
- `markInterrupted()` — ნაკადის ტაიმაუტი/შეწყვეტა/შეცდომა სუფთა დასრულებამდე.
- `ttft()` = პირველი გადაგზავნილი SSE-ფრაგმენტის დაყოვნება. **ეს არ არის ტოკენის დონის TTFT** —
  ერთი SSE-ფრაგმენტი შეიძლება შეიცავდეს ნულ/ერთ/მრავალ ტოკენს. ზუსტად არის დოკუმენტირებული.
- `avgItlMs()` = ფრაგმენტებს შორის შუალედის საშუალო მნიშვნელობა (ფრაგმენტის დაყოვნების მიახლოებითი მაჩვენებელი ITL-ისთვის).

TTFT/ITL/interrupted გადაეცემა `RoutingEvent`-ს (`ttftMs`, `itlMs`) და
OTel-ის მიმღების მიერ ექსპორტირდება GenAI/OmniRoute სპანის ატრიბუტების სახით.

## 4. OpenTelemetry / GenAI დაკვირვებადობა

ფაილები: `open-sse/services/routing/otel.ts`

- სპანები მიჰყვება GenAI-ის სემანტიკურ კონვენციებს (`gen_ai.provider.name`,

  ასინქრონულად ახორციელებს გაგზავნას `POST {endpoint}/v1/traces`-ის მეშვეობით. გადატვირთვისას
  უძველესი მოვლენები იშლება (`dropped` მთვლელი) — მონაცემთა სიბრტყეზე უკუწნევა
  არასოდეს იქმნება.
- **გამორთულია, თუ კონფიგურირებული არ არის.** უნდა იყოს დაყენებული `OMNIROUTE_OTEL_ENDPOINT` (ან
  `OTEL_EXPORTER_OTLP_ENDPOINT`); წინააღმდეგ შემთხვევაში მიმღები არ
  რეგისტრირდება და OTel-ის კოდი საერთოდ არ სრულდება.

## 6. შეფასების სიბრტყესთან ინტეგრაცია (მზადყოფნა Future AGI-სთვის)

OmniRoute Future AGI-ს (ან ნებისმიერ შემფასებელს) განიხილავს როგორც **პოტენციურ
ინტელექტის/შეფასების ბექენდს და არა დამოკიდებულებას**. ინტეგრაციის წერტილებია:

- `RoutingEventSink`-ს შეუძლია მოვლენები ასინქრონულად გადააგზავნოს შემფასებელთან.
- `MemoryRoutingEventStore` + ხარისხის სურათი შემფასებელს აძლევს გადაწყვეტილებების დაუმუშავებელ
  ნაკადს.
- სამომავლო `Evaluator` (დეტერმინისტული, ლოკალური შემფასებელი, HTTP, WASM) მოიხმარს
  მოვლენებს/ტრეისებს და დააბრუნებს `QualityScore`-ს, რომელიც მიეწოდება იმავე
  `getQualityScore`/ხარისხის ფაქტორის გზას.
- შეფასებაზე დაფუძნებული არსებული მარშრუტიზაცია (`open-sse/services/evalRouting.ts`) უკვე
  თავიდან ალაგებს კომბინაციის სამიზნეებს `eval_runs`-ის წარმატების მაჩვენებლების მიხედვით, როდესაც ჩართულია.

მოთხოვნის გზაზე არცერთი შეფასება არ სრულდება სინქრონულად, ხოლო კარიბჭე
სრულად ფუნქციონირებს შემფასებლის გარეშეც.

## 7. საბოლოო არქიტექტურული მიმოხილვა

1. **რა რჩება სინქრონულ ცხელ გზაზე?** მარშრუტიზაცია/ქულების გამოთვლა, დამცავი მექანიზმების
   წინასწარი შემოწმებები, ქეშში ძიება და ერთი `emitRoutingEvent`-ის განშტოება (~0.12 µs
   საბაზისო ქულების გამოთვლასთან შედარებით) მეხსიერებაში არსებულ მიმღებებზე.
2. **რა გადავიდა ასინქრონულ დამუშავებაზე?** OTel-ის ექსპორტი (ტაიმერი + fetch),
   `call_logs`/გამოყენების შენახვა, სემანტიკურ ქეშში ჩაწერა; ხარისხი ინახება მეხსიერებაში
   და არის O(1) (ასინქრონულობა საჭირო არ არის).
3. **როგორ გარდაიქმნება მარშრუტიზაციის შედეგი უკუკავშირად?** `handleChatCore` გამოსცემს
   `RoutingEvent`-ს → `QualityTracker` განაახლებს EWMA მდგომარეობას → `getQualityScore`
   მიეწოდება ავტომატური კომბინაციის `quality` ფაქტორს.
4. **როგორ ახდენს ხარისხი გავლენას სამომავლო მარშრუტიზაციაზე?** დაბალი ხარისხის ქულა ამცირებს
   ამ პროვაიდერის/მოდელის შეწონილ ქულას `scoreAutoTargets`-ში, ამიტომ
   დეგრადირებული მოდელების პრიორიტეტი თანდათან მცირდება და მათი EWMA-ის გაუმჯობესებისას აღდგება.
5. **როგორ შეუძლია Future AGI-ს ინტეგრირება დამოკიდებულებად ქცევის გარეშე?**
   `RoutingEventSink` ინტერფეისის / სამომავლო `Evaluator` ადაპტერის მეშვეობით — პირდაპირ კოდში ჩაშენებული
   დამოკიდებულების გარეშე.
6. **რა ხდება, როდესაც შემფასებელი მიუწვდომელია?** მარშრუტიზაციაზე გავლენა არ ხდება;
   მოდელებისთვის, რომლებსაც დაკვირვებული სიგნალი არ აქვთ, ხარისხი ნეიტრალურ მნიშვნელობაზე (1.0) გადადის.
7. **რა ხდება, როდესაც ტელემეტრია მიუწვდომელია?** OTel მიმღები უბრალოდ არ
   რეგისტრირდება; მარშრუტიზაციის დანარჩენი ფენა უცვლელად მუშაობს.
8. **რა ხდება გადატვირთვისას?** OTel ბუფერი უძველეს მოვლენებს შლის; ხარისხი
   და რგოლური ბუფერი კონსტრუქციითვე შეზღუდულია; უკუწნევა არ არსებობს.
9. **როგორ აღდგება პროვაიდერის მდგომარეობა დეგრადაციის შემდეგ?** წარმატებების
   დაგროვებასთან ერთად EWMA კვლავ კრებადდება; გახურების ეტაპი გამოუყენებელ მოდელებს ნეიტრალურს ტოვებს; ამომრთველი
   დამოუკიდებლად აღდგება HALF_OPEN საცდელი მოთხოვნების მეშვეობით.
10. **რომელი შემოთავაზებული ფუნქციები განზრახ არ განხორციელდა და რატომ?**
    - ჩრდილოვანი ტრაფიკი / ექსპერიმენტები — უკვე განხორციელებულია
      (`combo/shadowRouting.ts`); თავიდან არ შექმნილა.
    - დამცავი მექანიზმები — უკვე განხორციელებულია (`src/lib/guardrails/`); არ დუბლირებულა.
    - სემანტიკური ქეში — უკვე განხორციელებულია (`src/lib/semanticCache.ts`); არ
      დუბლირებულა.
    - ექსპერიმენტების მართვის სრულფასოვანი პლატფორმა, მონაცემთა ნაკრებების ხელსაწყოები, პრომპტების ოპტიმიზაციის
      პლატფორმა, ვექტორული DB ან სავალდებულო გარე OTel ინფრასტრუქტურა — სცდება
      მსუბუქი მონაცემთა სიბრტყის ფარგლებს.
    - Rust-ის `RoutingEvent` სტრუქტურა — მონაცემთა სიბრტყე TypeScript-ზეა; TS ტიპი
      ადაპტირებული ეკვივალენტია.
