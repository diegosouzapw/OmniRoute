Cursor-ის OmniRoute-ის უკან IDE სესიის გარეშე განთავსების ორი გზა:

1. **`cursor-api` პროვაიდერი** (ბარათი „Cursor API“, ალიასი `cua`): API-გასაღებზე
   დაფუძნებული პროვაიდერი, რომელიც ინახავს Cursor-ის მომხმარებლის API-გასაღებს (`crsr_…`,
   გენერირდება მისამართზე `https://cursor.com/dashboard/api`). ამის შემდეგ OmniRoute-ის
   ნებისმიერ კლიენტს შეუძლია Cursor-ის მოდელებთან წვდომა `/v1/chat/completions`-ის
   მეშვეობით, როგორც `cursor-api/<model>` ან `cua/<model>`, კვოტის, სარეზერვო
   გადართვისა და ლოგირების ჩვეულებრივი შრეებით. IDE პროვაიდერი (`cursor`,
   OAuth/IDE სესია) უცვლელია.
2. **Cursor CLI-ის გამჭოლი გადამისამართება**: მიმართეთ Cursor CLI (`agent`)
   OmniRoute-ზე, რათა CLI-ის მიერ შესრულებული თითოეული RPC ავთენტიფიცირდეს
   OmniRoute-ის API-გასაღებით, გადაიგზავნოს Cursor-ში `cursor-api` კავშირის
   ავტორიზაციის მონაცემით და აღირიცხოს Logs გვერდზე.

## რატომ ხდება გასაღების გაცვლა

`api2.cursor.sh` უარყოფს დაუმუშავებელ `crsr_…` გასაღებს Bearer ტოკენის სახით (401).
Cursor CLI ჯერ POST მოთხოვნით აგზავნის გასაღებს `/auth/exchange_user_api_key`-ზე
და იღებს სესიის JWT-ს, რომელსაც ვადა ერთი საათის შემდეგ გასდის; დაბრუნებულ
`refreshToken`-ს იგივე `exp` აქვს, ამიტომ განახლება გასაღების ხელახლა გაცვლას ნიშნავს.
`open-sse/services/cursorApiKeyAuth.ts` ასრულებს ამ გაცვლას, თითოეული გასაღებისთვის
ქეშავს ერთ სესიის ტოკენს, ვადის გასვლამდე ხუთი წუთით ადრე ხელახლა ცვლის მას და
ქეშირებულ ტოკენს შლის, როდესაც Cursor 401 პასუხს აბრუნებს. `CursorExecutor` მას
უშუალოდ ზედა დონის ნაკადის გახსნამდე იძახებს `cursor-api` კავშირებისთვის.

## `cursor-api` პროვაიდერი

რეესტრი: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, იგივე `format`, `baseUrl` და
`models`, რაც `cursor`-ს აქვს). კატალოგის ბარათი:
`src/shared/constants/providers/apikey/specialty-media.ts`. შემსრულებლების რუკა:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

მართვის პანელი: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

შემდეგ:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

შენიშვნები:

- `cursor-api`-სთვის მოდელების სია სტატიკური Cursor რეესტრიდან მიიღება
  (იგივე სიიდან, რომელსაც IDE პროვაიდერი სარეზერვოდ იყენებს); OmniRoute-ის
  ჰოსტზე `cursor-agent`-ის ინსტალაცია საჭირო არ არის.
- `POST /api/providers/{id}/refresh-cursor` განკუთვნილია მხოლოდ `cursor` IDE
  პროვაიდერისთვის; `cursor-api` კავშირებს განახლებისთვის IDE სესია არ აქვთ.

## მოდელების ნატიური ID-ები და ძალისხმევა

`cursor` / `cu` და `cursor-api` / `cua` მარშრუტებისთვის Claude-ის ძალისხმევის
საერთო ნორმალიზატორი მოთხოვნილი მოდელის ID-ს უცვლელად ტოვებს. Cursor-ს შეუძლია
`-low`-ის მსგავსი სუფიქსი რეალური მოდელის ID-ის ნაწილად გამოაცხადოს და არა
OmniRoute-ის ძალისხმევის ალიასად. Cursor-ის შემსრულებელი ზუსტ დამთხვევას
აქტიურ კატალოგთან ინარჩუნებს; როდესაც დამთხვევა არ არის, სუფიქსის პარამეტრად
გარდაქმნის სარეზერვო ლოგიკას მისი არსებული მოდელის განმსაზღვრელი მართავს.

ეს არ ცვლის ძალისხმევის ნორმალიზებას პირდაპირი Claude, Claude-თავსებადი ან
Vertex მარშრუტებისთვის. ხელმისაწვდომობა კვლავ არჩეული Cursor ანგარიშის
კატალოგსა და წვდომის უფლებებზეა დამოკიდებული.

## Cursor CLI-ის გამჭოლი გადამისამართება

მარშრუტი: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. პრეფიქსი `/api/cursor-cli/`
რეგისტრირებულია `src/shared/constants/publicApiRoutes.ts`-ში, რადგან დამმუშავებელი
საკუთარ ავთენტიფიკაციას თავად უზრუნველყოფს:

| გზა                                                                                                                        | CLI-ისგან მოსალოდნელი ავთენტიფიკაცია | რას აკეთებს OmniRoute                                                                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                         | `Bearer <OmniRoute API key>`         | ამოწმებს გასაღებს, ქმნის 1-საათიან HS256 JWT-ს (`JWT_SECRET`-ით ხელმოწერილს) და აბრუნებს მას                                                                                        |
| ყველა სხვა გზა (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`                  | ამოწმებს გამომცემელს/აუდიტორიას/ვადის გასვლას, ირჩევს აქტიურ `cursor-api` კავშირს, Authorization სათაურს ანაცვლებს გაცვლილი Cursor-ის ტოკენით და პასუხს ნაკადის სახით უკან აბრუნებს |

CLI მიღებული ნებისმიერი ტოკენიდან დეკოდირებს `exp`-ს, ამიტომ მისთვის გაუმჭვირვალე
ტოკენის გადაცემა თითქმის ყოველი მოთხოვნის წინ ხელახალ გაცვლას იწვევს; შექმნილი JWT
ამას თავიდან იცილებს. OmniRoute-ისგან მიღებული 401 აიძულებს CLI-ს, გაცვლა გაიმეოროს.

### გამართვა

1. შექმენით OmniRoute API გასაღები (Dashboard → API keys) და `cursor-api`
   კავშირი.
2. მიუთითეთ CLI-ს, რომ აგენტის ნაკადისთვის HTTP/1.1 გამოიყენოს.
   `~/.cursor/cli-config.json`-ში:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   ამის გარეშე CLI აგენტის სესიას HTTP/2-ით, ცალკე
   კონფიგურირებულ აგენტის ჰოსტთან ხსნის და ამ საბოლოო წერტილში მხოლოდ
   მართვის სიბრტყის RPC-ები გადის.

3. გაუშვით CLI OmniRoute-ის გამოყენებით:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

ყოველი ეტაპი Logs-ში ფიქსირდება პროვაიდერით `cursor-api`, მოთხოვნის ტიპით `cursor-cli`,
გზით `/api/cursor-cli/<rpc>` და მიეწერება OmniRoute API გასაღებსა და
იმ კავშირს, რომელმაც მოთხოვნა დაამუშავა.

### შეცდომის შემთხვევები

| სიტუაცია                                            | პასუხი CLI-სთვის                               |
| --------------------------------------------------- | ---------------------------------------------- |
| უცნობი OmniRoute გასაღები და `REQUIRE_API_KEY=true` | გაცვლისას 401 `unauthenticated`                |
| `REQUIRE_API_KEY=false`                             | ანონიმური სესია (იმეორებს `/v1/*`-ის ქცევას)   |
| ვადაგასული / უცხო / შეცვლილი სესიის JWT             | 401, CLI ხელახლა ასრულებს გაცვლას              |
| გაცვლის შემდეგ გაუქმებული OmniRoute API გასაღები    | მომდევნო RPC-ზე 401                            |
| აქტიური `cursor-api` კავშირი არ არსებობს            | 503 `unavailable`                              |
| Cursor უარყოფს კავშირის გასაღებს                    | 401 `unauthenticated`, კეშირებული სესია იშლება |
| ზედა დონის სერვერი მიუწვდომელია                     | 502 `unavailable` (გასუფთავებული შეტყობინება)  |
| `JWT_SECRET` დაყენებული არ არის                     | გაცვლისას 503                                  |
