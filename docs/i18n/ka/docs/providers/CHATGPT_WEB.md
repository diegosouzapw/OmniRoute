`chatgpt-web-codex` (alias `cgpt-codex`) Codex Responses-ის ციკლებს ავთენტიფიცირებული ChatGPT-ის ბრაუზერის სესიის მეშვეობით აკავშირებს. ის დამოუკიდებელია გაუქმებული საერთო `chatgpt-web` პროვაიდერისგან და იყენებს MIT შეტყობინების მქონე იმპლემენტაციას `open-sse/vendor/codex-chatgpt-web/`-ში, რომელიც განახლებულია upstream v4.0.7-ის commit-მდე `b59d7dc51b84fb1f465ff1d00f5207f3b2b4a494`.

## საერთო პროვაიდერის გაუქმება

ყოფილი საერთო პროვაიდერის ID-ები `chatgpt-web` და `cgpt-web` აღარ ვრცელდება, რადგან მათი pre-key/proof-of-work იმპლემენტაციის წარმომავლობის დადასტურება ვერ მოხერხდა. რომელიმე ID-ზე გაგზავნილი აშკარა მოთხოვნები, მათ შორის დახრილი ხაზით დაწყებული მოდელის ID-ები და შენახული alias-ები, ნებისმიერ upstream მოთხოვნამდე იხურება HTTP `410`-ითა და კოდით **PROVIDER_RETIRED**.

მიგრაცია `168_retire_chatgpt_web.sql` შესაბამის პროვაიდერის კავშირებს გაუქმებულად მონიშნავს და მათ აქტიურ სესიის lease-ებს აუქმებს. ის ინარჩუნებს კავშირების ისტორიასა და API გასაღებების allowlist-ებს; ის allowlist-ში შემცვლელ წვდომას არ ამატებს. ეს გაუქმება Codex პროვაიდერსა და მის კავშირებს არ ეხება.

## წინაპირობები

- სისტემაში შესული ChatGPT სესიიდან მიღებული სრული Cookie header;
- Chrome ან Chromium, ასევე გრაფიკული სესია ან Xvfb display npm, systemd და PM2 ინსტალაციებისთვის;
- Docker-ის `web` პროფილის გამოყენებისას — შიდა Chromium სერვისი `docker-compose.yml`-იდან;
- OpenAI `tunnel-client` v0.0.13 და ChatGPT-ის მორგებული connector ლოკალური Codex ხელსაწყოებისთვის.

გვირაბი საჭიროა მხოლოდ ხელსაწყოების შემცველი ციკლებისთვის. ჩამოთვლილი ყველა route, მათ შორის `pro`, შეიძლება იყენებდეს იმავე, ციკლთან მიბმულ ლოკალურ ხელსაწყოთა შესაძლებლობას, როდესაც გვირაბი და connector კონფიგურირებულია.

## Dashboard-ის დაყენება

1. გახსენით **ChatGPT Web (Codex)** პროვაიდერი და დაამატეთ კავშირი.
2. ჩასვით სრული ChatGPT Cookie header, tunnel ID, runtime key და მორგებული connector-ის სახელი. ხელსაწყოების მხარდაჭერის მქონე ახალ კონფიგურაციებში უნდა გამოიყენოთ ახლად შექმნილი connector ზუსტად შემდეგი სახელით: `OmniRoute Codex v2`; Authentication უნდა იყოს დაყენებული None-ზე, ხოლო Permissions — Allow all actions-ზე.
3. გაუშვით კავშირის შემოწმება. OmniRoute ხსნის ბრაუზერზე დაფუძნებულ Temporary Chat-ს და ადგენს, ხელმისაწვდომია თუ არა ანგარიშისთვის Sol და Pro.
4. შეინახეთ კავშირი. OmniRoute ჩასმულ cookie-ს ჩაანაცვლებს დადასტურებული Playwright storage state-ით და runtime key-სთან ერთად შეინახავს მას დაშიფრული ავტორიზაციის მონაცემების აბსტრაქციის მეშვეობით.

წარმატებით შენახვის შემდეგ დაუმუშავებელი cookie არ ინახება. როდესაც სესიას ვადა გაუვა, გახსენით კავშირი, ჩასვით ახალი სრული Cookie header და ხელახლა გაუშვით შემოწმება. რედაქტირების დიალოგში doctor status ცალ-ცალკე აჩვენებს ბრაუზერის, storage state-ის, სისტემაში შესვლის, Temporary Chat-ის, გვირაბის, connector-ისა და ხელსაწყოს სრული ციკლის სტატუსს.

## მოდელები და combo-ები

მოდელების ფიქსირებული route-ებია:

- `chatgpt-web-codex/luna` — GPT-5.6 Luna, მსჯელობის დაბალი ინტენსივობა
- `chatgpt-web-codex/think` — GPT-5.6 Luna, მსჯელობის საშუალო ინტენსივობა
- `chatgpt-web-codex/instant`
- `chatgpt-web-codex/medium`
- `chatgpt-web-codex/high`
- `chatgpt-web-codex/extra-high`
- `chatgpt-web-codex/pro`

დაამატეთ რომელიმე მათგანი combo-ში, ისევე როგორც ნებისმიერი სხვა მოდელი. Codex აპი combo-ს სახელს `model`-ის სახით აგზავნის ჩვეულებრივ Responses endpoint-ზე, `/v1/responses`; ცალკე Codex endpoint ან რეჟიმის გადამრთველი არ არსებობს.

Free/Go ანგარიშებისთვის ხელმისაწვდომია Luna route-ები. Sol-ის მხარდაჭერის მქონე ანგარიშებისთვის ხელმისაწვდომია Instant-იდან High-ის ჩათვლით, ხოლო Pro-ს მხარდაჭერის მქონე ანგარიშებისთვის დამატებით ხელმისაწვდომია Extra High და Pro. თითოეულ route-ს აქვს ფიქსირებული backend მოდელი და მსჯელობის ინტენსივობა; კონფლიქტური, აშკარად მითითებული Responses-ის ინტენსივობის შემთხვევაში მოთხოვნა იხურება, ნაცვლად იმისა, რომ არჩეული ბრაუზერის რეჟიმი შეუმჩნევლად შეიცვალოს.

არ გადაარქვათ სახელი და ხელახლა არ გამოიყენოთ ძველი `Codex Native` ან `OmniRoute Codex` connector. ChatGPT საჯარო MCP კონტრაქტს connector-ის იდენტობის მიხედვით აკეშირებს, ხოლო განახლებული bridge იყენებს ახალ, პირდაპირ turn-token კონტრაქტს. runtime უარყოფს ამ მოძველებულ იდენტობებს და მოითხოვს ახალ `OmniRoute Codex v2` connector-ს.

  მონაცემების გენერირების დაწყების შემდეგ პროვაიდერი, მოდელი, კავშირი და ბრაუზერის სვლა სვლის

  პასუხებში ან მოთხოვნების ჟურნალებში არ ჩნდება.

## ეკრანის გარეშე VPS და Docker

npm, systemd და PM2 ინსტალაციებისთვის OmniRoute ამოიცნობს Chrome-ისა და Chromium-ის გავრცელებულ ბილიკებს.
ალტერნატიულად, დააყენეთ `CHATGPT_WEB_CODEX_CHROME_PATH`. შესრულების გარემოს სვლები განზრახ იყენებს
გრაფიკული ინტერფეისით გაშვებულ Chrome-ს, რადგან ChatGPT ნამდვილ headless-ბრაუზერის კონფიგურაციას უარყოფს.
ამიტომ ეკრანის არმქონე ჰოსტმა OmniRoute უნდა გაუშვას კერძო Xvfb დისპლეით; მხოლოდ Chrome-ის ბილიკის
მითითება დისპლეის გარემოს არ უზრუნველყოფს.

Docker-ის `web` პროფილი შიდა Compose ქსელში უშვებს `chatgpt-web-codex-browser`-ს.
გვერდითი კონტეინერი გრაფიკული ინტერფეისით გაშვებულ Chrome-ს Xvfb-ის შიგნით ასრულებს, ამიტომ ფიზიკური
დისპლეი საჭირო არ არის. მისი CDP პორტი ჰოსტზე არ ქვეყნდება. დაცული ბრაუზერის პროფილის ტომი
OmniRoute-ის მონაცემთა ტომისგან განცალკევებულია, ხოლო ბრაუზერი საკმარისი მოცულობის საზიარო მეხსიერებას
იღებს. შიდა CDP პროქსი მხოლოდ `9223` პორტზე უსმენს Compose ქსელის შიგნით; გვერდით კონტეინერში Chrome
კვლავ loopback ინტერფეისზეა მიბმული.

`DATA_DIR`-ში განთავსებული ზედამხედველის lease მექანიზმი ხელს უშლის OmniRoute-ის რამდენიმე პროცესს,
ერთდროულად ფლობდეს ერთსა და იმავე გვირაბისა და ბროკერის მდგომარეობას. კონფლიქტის შესახებ doctor
გვატყობინებს.

## ინტერაქტიული აღდგენა

Docker-ის ავტომატიზებულ გზას ჰოსტზე ხილული ფანჯარა არ აქვს, თუმცა თავად Chrome კერძო Xvfb დისპლეის
შიგნით გრაფიკული ინტერფეისით მუშაობს. როდესაც ChatGPT ინტერაქტიულ ავტორიზაციას ან შემოწმებას მოითხოვს,
აღდგენისთვის შესაძლებელია არსებული VNC ბრაუზერის ინფრასტრუქტურის გამოყენება. ბრაუზერის UI და CDP
ხელმისაწვდომი უნდა დარჩეს მხოლოდ loopback-ის, ავტორიზებული მართვის კავშირის ან SSH გვირაბის მეშვეობით;
ნორმალური მუშაობისას noVNC გამორთული რჩება.

## WebSocket-ის სარეზერვო რეჟიმი

როდესაც კომბინაცია შეიცავს ChatGPT Web-ს (Codex), Responses WebSocket ხიდი ზედა დონის სერვერთან
დაკავშირებამდე HTTP/SSE სარეზერვო რეჟიმს ითხოვს. შემდეგ გადაცემა `/v1/responses`-ის მეშვეობით
ხორციელდება.
