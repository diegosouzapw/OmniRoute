ეს დოკუმენტი აღწერს იმპლემენტაციის გადაწყვეტილებას
[Issue #7854](https://github.com/diegosouzapw/OmniRoute/issues/7854)-ისთვის. საჯარო პროდუქტები
წარმოდგენილია პროვაიდერთა ოთხი ოჯახის სახით. რეგიონი კავშირის მონაცემია და არა ცალკე პროდუქტი.

## გადაწყვეტილება

| პროვაიდერის ოჯახი                                         | OmniRoute ID            | გლობალური რეგიონი | ჩინეთის რეგიონი |
| --------------------------------------------------------- | ----------------------- | ----------------- | --------------- |
| Alibaba Cloud Model Studio (გამოყენების მიხედვით გადახდა) | `alibaba`               | სინგაპური         | პეკინი          |
| Alibaba Cloud Token Plan                                  | `bailian-coding-plan`   | სინგაპური         | პეკინი          |
| Qwen Cloud (გამოყენების მიხედვით გადახდა)                 | `qwen-cloud`            | გლობალური         | პეკინი          |
| Qwen Cloud Token Plan                                     | `qwen-cloud-token-plan` | სინგაპური         | პეკინი          |

არსებული `alibaba-cn` ID შენახული კავშირებისთვის, მოდელების მარშრუტებისთვის, კომბინაციებისა და
ისტორიული გამოყენებისთვის რჩება გაშვების დროის თავსებადობის ფსევდონიმად. მისი საინფორმაციო დაფის
ბარათი გაერთიანებულია `alibaba`-ში; მონაცემთა ბაზის გადაწერა საჭირო არ არის.

Qwen Cloud-ის გამოყენების მიხედვით გადახდის პროდუქტი და Alibaba Cloud Model Studio ამჟამად იყენებენ
DashScope-თან თავსებად გაშვების დროის საერთო ჰოსტებს, თუმცა ისინი რჩებიან პროვაიდერის ცალკეულ
იდენტობებად, რადგან მომხმარებლები გასაღებებს იღებენ და ანგარიშებს მართავენ სხვადასხვა პროდუქტის
ინტერფეისის მეშვეობით. Alibaba-სა და Qwen Cloud Token Plan-ის პროდუქტები იყენებენ endpoint-ების
განსხვავებულ ოჯახებს, ამიტომ ოთხივე პროდუქტი რჩება პროვაიდერის ცალკეულ ID-ებად.

API გასაღები და endpoint ერთსა და იმავე პროდუქტსა და რეგიონს უნდა ეკუთვნოდეს. რეგიონის არჩევა
ცვლის წინასწარ განსაზღვრულ endpoint-ს, რომელსაც ვალიდაცია და ჩვეულებრივი მოთხოვნები იყენებს.

## კავშირის კონტრაქტი

ახალი კავშირები სტაბილურ რეგიონის გასაღებს `providerSpecificData`-ში ინახავს:

```json
{
  "region": "global-sg"
}
```

დაშვებული მნიშვნელობებია `global-sg` და `china-beijing`. Endpoint ცენტრალიზებულად განისაზღვრება
პროვაიდერის ID-ისა და რეგიონის მიხედვით. წინასწარ განსაზღვრულისგან განსხვავებული
`providerSpecificData.baseUrl` რჩება ოპერატორის ცალსახა ჩანაცვლებად და აქვს უპირატესობა, ხოლო ძველი
შენახული წინასწარ განსაზღვრული URL-ები კვლავ რეგიონულ მატრიცასთან შესაბამისობაში ნორმალიზდება.

ეს კავშირის სქემას გაფართოებადს ტოვებს: კიდევ ერთი რეგიონი შეიძლება დაემატოს გადამწყვეტ მექანიზმს
პროვაიდერის ახალი ბარათის შექმნის ან შენახული პროვაიდერის ID-ების შეცვლის გარეშე.

## თავსებადობა და ეტაპობრივი დანერგვა

1. დაამატეთ რეგიონული endpoint-ის resolver და შეინარჩუნეთ მიმდინარე გლობალური ნაგულისხმევი პარამეტრები.
2. გამოიყენეთ ცოცხალი რეგიონული DashScope `/models` აღმოჩენა `alibaba`-სთვის, მისი `alibaba-cn` თავსებადობის
   ID-სთვის და `qwen-cloud`-ისთვის. მათი პასუხები თავდაპირველად გადის ტექსტის გენერაციის ერთ ფილტრს, რადგან ზოგადი
   endpoint ასევე აბრუნებს გამოსახულების, ვიდეოს, აუდიოს, embedding-ისა და სხვა არასასაუბრო მოდელებს. შემდეგ `qwen-cloud`
   იყენებს მის პროვაიდერთა რეესტრში გამოცხადებულ და მხარდაჭერილ დაშვებულ სიას. Alibaba Model Studio
   და Qwen Cloud ინარჩუნებენ ცალკეულ კურირებულ კატალოგებს, მიუხედავად იმისა, რომ ამჟამად საერთო runtime host-ებს იყენებენ.
3. დაარეგისტრირეთ `qwen-cloud-token-plan` მიმდინარე Token Plan-ის ტექსტური მოდელების დაშვებული სიით.
4. კავშირის დამატების/რედაქტირების დიალოგებს დაამატეთ ტიპიზებული რეგიონის ამრჩევი.
5. დამალეთ დუბლირებული `alibaba-cn` ბარათი და მისი არსებული კავშირები ჩართეთ `alibaba`
   პროვაიდერის გვერდზე.
6. დატოვეთ მორგებული endpoint-ის ჩანაცვლებები ხელმისაწვდომი გაფართოებული და სამუშაო სივრცისთვის სპეციფიკური განთავსებებისთვის.

Token Plan-ის მედია-მოდელები ჩატის კატალოგის მიღმა რჩება, რადგან ისინი სპეციალიზებულ endpoint-ებს იყენებენ.
`wan2.7-image` და `wan2.7-image-pro` რეგისტრირებულია `open-sse/config/imageRegistry.ts`-ში;
`happyhorse-1.1-i2v`, `happyhorse-1.1-t2v` და `happyhorse-1.1-r2v` რეგისტრირებულია
`open-sse/config/videoRegistry.ts`-ში. ორივე რეესტრი ხელახლა იყენებს `qwen-cloud-token-plan` კავშირის
იდენტობასა და მის რეგიონისთვის სპეციფიკურ ავტორიზაციის მონაცემებს.

ჩვეულებრივ Qwen Cloud-ს აქვს ცალკეული გამოყენების მიხედვით გადახდადი გამოსახულებისა და ვიდეოს კატალოგები `qwen-cloud`
იდენტობის ქვეშ. მისი გამოსახულების მოდელებია `wan2.7-image-pro`, `wan2.7-image`, `qwen-image-3.0-pro`,
`qwen-image-2.0-pro-2026-06-22`, `qwen-image-2.0-2026-03-03` და `z-image-turbo`. მისი ვიდეო
მოდელებია `happyhorse-1.1-i2v`, `happyhorse-1.1-t2v`, `happyhorse-1.1-r2v`,
`happyhorse-1.0-video-edit`, `wan2.7-t2v`, `wan2.7-i2v`, `wan2.7-r2v-2026-06-12` და
`wan2.7-videoedit`. ეს მოდელები ხელახლა იყენებს მხოლოდ ჩვეულებრივ `qwen-cloud` კავშირსა და რეგიონულ
DashScope მედია-endpoint-ს. Token Plan-ისა და გამოყენების მიხედვით გადახდადი რეესტრები ერთმანეთის
მოდელების სიებს არც მემკვიდრეობით იღებს და არც აერთიანებს.

`bailian-coding-plan` იდენტობას ასევე აქვს საკუთარი მედიის დაშვებული სიები:
`wan2.7-image`, `wan2.7-image-pro`, `qwen-image-2.0` და `qwen-image-2.0-pro` გამოსახულების
გენერაციისთვის, ასევე
`happyhorse-1.1-i2v`, `happyhorse-1.1-t2v` და `happyhorse-1.1-r2v` ვიდეოს
გენერაციისთვის. ის იყენებს მხოლოდ Bailian Coding Plan-ის კავშირსა და რეგიონულ Coding Plan endpoint-ს.
მისი გამოსახულებისა და ვიდეოს რეესტრები არც ერთი Qwen Cloud პროვაიდერისგან არაფერს იღებს მემკვიდრეობით და არც მათთან ერთიანდება.

ჩვეულებრივ `alibaba` იდენტობას გამოსახულებისა და ვიდეოს ცალკეული დაშვებული სიები აქვს. მისი გამოსახულების მოდელებია
`qwen-image-3.0-pro`, `qwen-image-2.0-pro-2026-06-22`, `qwen-image-2.0`,
`z-image-turbo` და `wan2.6-t2i`. მისი დამატებული ვიდეო-მოდელებია `happyhorse-1.1-i2v`,
