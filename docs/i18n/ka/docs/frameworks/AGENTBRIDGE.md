AgentBridge არის OmniRoute-ის MITM (Man-in-the-Middle) პროქსი, რომელიც IDE-ის AI აგენტების HTTPS ტრაფიკს იჭერს და OmniRoute-ის ერთიანი მარშრუტიზაციის ძრავის გავლით გადაამისამართებს. იგი მხარს უჭერს **10 IDE აგენტს** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code და Trae (მიმდინარეობს კვლევა) — რაც OmniRoute-ს ბაზარზე AI კოდირების ასისტენტებისთვის ყველაზე ფართო დაფარვის მქონე MITM პროქსიდ აქცევს.

**მართვის პანელის მდებარეობა:** `/dashboard/tools/agent-bridge`
**გვერდითი ზოლის ჯგუფი:** ხელსაწყოები (Cloud Agents-ის შემდეგ)
**ასევე იხილეთ:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — აკონტროლეთ მთელი დაჭერილი ტრაფიკი რეალურ დროში; `docs/security/MITM-TPROXY-DECRYPT.md` (git; არ კომპილირდება `/docs`-ში) — Linux TPROXY-ის გამჭვირვალე გაშიფვრის რეჟიმი, რომელსაც `/api/tools/agent-bridge/tproxy` მარშრუტი მართავს.

## §1 მიმოხილვა

### რა არის AgentBridge?

როდესაც IDE აგენტი (მაგ., GitHub Copilot, Cursor, Claude Code) API გამოძახებას ასრულებს, ის პირდაპირ უკავშირდება ზემდგომ AI პროვაიდერს (OpenAI, Anthropic და სხვ.). AgentBridge ამ კავშირს გამჭვირვალედ, TLS-ის დონეზე იჭერს — აგენტის კონფიგურაციაში რაიმე ცვლილების მოთხოვნის გარეშე — და მოთხოვნას OmniRoute-ის გავლით გადაამისამართებს.

ეს ნიშნავს, რომ შეგიძლიათ:

- **ნებისმიერი აგენტი ნებისმიერ პროვაიდერზე გადაამისამართოთ**: Copilot უკავშირდება OpenAI-ს? გადაამისამართეთ ის Anthropic Claude-ზე, Gemini-ზე ან OmniRoute-ის 352 პროვაიდერიდან ნებისმიერზე.
- **გამოიყენოთ მოდელების შესაბამისობები**: `gemini-3-flash` → `claude-sonnet-4.7` დამმუშავებლის დონეზე გამჭვირვალედ.
- **დააკვირდეთ აგენტების მთელ ტრაფიკს**: ყოველი დაჭერილი მოთხოვნა ქვეყნდება [Traffic Inspector](./TRAFFIC_INSPECTOR.md)-ში.
- **გამოიყენოთ OmniRoute-ის მდგრადობის მექანიზმები**: კომბინირებული მარშრუტიზაცია, circuit breaker-ები, სარეზერვო მარშრუტები და ხარჯების აღრიცხვა IDE აგენტების ტრაფიკზეც მუშაობს.

### 2.1 კომპონენტების მიმოხილვა

```

    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS გადამისამართება
    │
    ▼
src/mitm/server.cjs  (პორტი 443, CJS შვილობილი პროცესი)
    │  სამიზნეს განსაზღვრავს Host სათაურის SNI-ის მიხედვით
    │  ქმნის თითოეული SNI-ისთვის TLS სერტიფიკატს, რომელსაც ხელს აწერს AgentBridge CA
    ├── გვერდის ავლის სიას ემთხვევა? → TCP გამჭოლი გადაცემა (გაშიფვრის გარეშე)
    ├── სამიზნეს ემთხვევა? → fetch → OmniRoute მარშრუტიზატორი (პორტი 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() მოთხოვნის სხეულზე/სათაურებზე

    │               └── fetchRouter() → /v1/chat/completions
    └── შესაბამისობა არ არის? → TCP გამჭოლი გადაცემა (გაშიფვრის გარეშე)
```

### 2.2 MITM სერვერი (`src/mitm/server.cjs`)

ძირითადი MITM სერვერი მუშაობს Node.js CJS შვილობილი პროცესის სახით (არსებული CJS კოდური ბაზის ხელახლა გადაწერის თავიდან ასაცილებლად). ის:

- უსმენს 443-ე პორტს (საჭიროებს პრივილეგიას ან `authbind`/`setcap`-ს)
- ოპერაციული სისტემისგან იღებს CONNECT გვირაბებს (`/etc/hosts`-ის DNS გადამისამართების მეშვეობით)
- ქმნის თითოეული SNI-ისთვის TLS სერტიფიკატებს, რომლებსაც ხელს აწერს AgentBridge CA (`DATA_DIR/mitm/ca.crt`)
- `targets/index.ts` რეესტრის მეშვეობით Host სათაურის მიხედვით განსაზღვრავს სამიზნე აგენტს
- მოთხოვნებს HTTP-ის მეშვეობით გადასცემს TypeScript დამმუშავებლის შრეს მისამართზე `http://127.0.0.1:20128`

`TARGET_HOSTS` იტვირთება `DATA_DIR/mitm/targets.json`-დან (რომელსაც ჩატვირთვისას წერს `targets/index.ts`), რაც CJS სერვერის გადატვირთვის გარეშე დინამიკური განახლებების საშუალებას იძლევა.

> **Root-CA მოდელი (#6684).** ზემოთ აღწერილი, თითოეული SNI-ისთვის CA-ის მიერ ხელმოწერილი სერტიფიკატის
> მოდელი არის #6684-ში დამატებული მუდმივად შენახვადი root-CA მოდელი (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, რომელიც ხელახლა იყენებს CA/leaf კრიპტოგრაფიას, რომლის
> მუშაობაც უკვე დადასტურებულია TPROXY-სთვის `src/mitm/tproxy/dynamicCert.ts`-ში) — ის ანაცვლებს
> ძველ, ერთ სტატიკურ, თვითხელმოწერილ leaf სერტიფიკატს (`src/mitm/cert/generate.ts`, რომელიც კვლავ
> მხოლოდ antigravity ჰოსტებით შემოიფარგლება), რომლის არსებობაზეც დისკზე განთავსებული უბრალო
> `server.crt`/`server.key` წყვილი მიუთითებს. **მიგრაციის ქცევა**: ახალი ინსტალაცია (წინა
> `server.crt`-ის გარეშე) root-CA მოდელს ავტომატურად იღებს; ინსტალაცია, რომელიც უკვე ენდობა
> ძველ სტატიკურ leaf სერტიფიკატს, განაგრძობს მის გამოყენებას, სანამ ოპერატორი არ დააყენებს
> `MITM_ROOT_CA_ENABLED=true`-ს და არ გადატვირთავს ხიდს (`src/mitm/cert/migration.ts`
> არის გადაწყვეტილების წმინდა ფუნქცია — სანდო MITM CA, რომელსაც შეუძლია ხელი მოაწეროს leaf სერტიფიკატს
> **ნებისმიერი** ჰოსტისთვის, არსებითად უფრო ძლიერია, ვიდრე ძველი, ფიქსირებული SAN-ის მქონე leaf სერტიფიკატი,
> ამიტომ უკვე სანდოდ მიჩნეული ინსტალაციისთვის გადართვა არასდროს ხდება ჩუმად). CA სერტიფიკატი
> ინსტალირდება ნდობის საცავის იმავე `omniroute-mitm.crt` სლოტში, რომელსაც ძველი leaf სერტიფიკატი იყენებდა
> (`cert/install.ts::installCaCert`) — ორმაგი ნდობის გასუფთავება საჭირო არ არის.

### 2.3 დამმუშავებლის საბაზისო კლასი (`src/mitm/handlers/base.ts`)

აგენტების ყველა დამმუშავებელი აფართოებს `MitmHandlerBase`-ს:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // დაცული დამხმარე ფუნქციები: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

თითოეული დამმუშავებელი პროქსირებამდე იძახებს `hookBufferStart()`-ს, ხოლო დასრულებისას — `hookBufferUpdate()`-ს. ისინი `InterceptedRequest` ჩანაწერებს ამატებენ `globalTrafficBuffer`-ში (იხილეთ [ტრაფიკის ინსპექტორი](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 სამიზნეების რეესტრი (`src/mitm/targets/`)

თითოეულ აგენტს აქვს დეკლარაციული სამიზნის ფაილი:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

რეესტრი (`targets/index.ts`) ექსპორტს უკეთებს `ALL_TARGETS`-ს და ჩატვირთვისას ქმნის `DATA_DIR/mitm/targets.json`-ს.

### 2.5 გამჭოლი გადაცემა და გვერდის ავლის სია (`src/mitm/passthrough.ts`)

**გვერდის ავლის სია** (მოწმდება პირველ რიგში და სამიზნესთან დამთხვევაზე უპირატესობა აქვს):

- ნაგულისხმევი ნიმუშები: საბანკო ჰოსტები, `.gov.`, OAuth/SSO პროვაიდერები (Okta, Auth0) და ა.შ.
- მომხმარებლის ნიმუშები: ინახება მონაცემთა ბაზის `agent_bridge_bypass` ცხრილში
- გვერდის ავლის სიაში მყოფი ჰოსტები იღებენ გამჭვირვალე TCP გვირაბს — TLS **არასდროს იშიფრება**

**ნაგულისხმევი გამჭოლი გადაცემა** (სამიზნესთან დამთხვევა არ არის და არც გვერდის ავლის სიაშია):

- ასევე იღებს TCP გვირაბს — კავშირები არასდროს წყდება
- ხელს უშლის AgentBridge-ს, დაარღვიოს სისტემის ზოგადი HTTPS ტრაფიკი

მარშრუტიზაციის პრიორიტეტი:

```
გვერდის ავლის სია → სამიზნესთან დამთხვევა → გამჭოლი გადაცემა
```

### 2.6 ზედა დონის CA სერტიფიკატი (`src/mitm/upstreamTrust.ts`)

მორგებული CA-ის მქონე კორპორაციული ქსელური გარემოებისთვის:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

დაყენების შემთხვევაში, `undici`-ის გლობალური დისპეტჩერი კონფიგურირდება დამატებითი CA სერტიფიკატით, რაც AgentBridge-ს საშუალებას აძლევს, კორპორაციული TLS ტერმინაციის პროქსიების გავლით დაუკავშირდეს ზედა დონის პროვაიდერებს.

### 2.7 საიდუმლო მონაცემების შენიღბვა (`src/mitm/maskSecrets.ts`)

დამოუკიდებელი clean-room სკანერი მოთხოვნის სხეულებსა და ავტორიზაციის მონაცემების შემცველ სათაურებზე გამოიყენება
**მანამდე**, სანამ ისინი Traffic Inspector-ის ბუფერში ან რომელიმე ჟურნალში მოხვდება. ის ასრულებს ერთ ხაზოვან გავლას:

- `sk-` / `ak-` / `pk-` პრეფიქსიანი ტოკენები (OpenAI/Anthropic-ის სტილი)
- RFC 6750 `Authorization: Bearer <token>` ავტორიზაციის მონაცემები, მთლიანი ტოკენის პრიორიტეტით
- ზოგადი გრძელი გაუმჭვირვალე ტოკენები (≥40 სიმბოლო), მათ შორის წერტილებიანი და შევსებული ფორმები

`sanitizeHeaders()` შენარჩუნებულ სახელებს ქვედა რეგისტრში გარდაქმნის, მასივის მნიშვნელობებს დეტერმინისტულად აერთიანებს, საერთო
hop-by-hop/ფრეიმინგის აკრძალულ სიას (პროქსის ავთენტიფიკაციის ჩათვლით) შლის, `cookie`-სა და
`set-cookie`-ს სრულად ფარავს და ავტორიზაციის მონაცემების მნიშვნელობებს სკანერს გადასცემს.

### 3.2 სერტიფიკატის სანდოდ მონიშვნა

სანამ IDE-ები MITM კავშირს მიიღებენ, AgentBridge-ის CA სერტიფიკატი OS-ის მიერ სანდოდ უნდა იყოს მიჩნეული.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

ან გამოიყენეთ მართვის პანელზე არსებული ღილაკი „სერტიფიკატის ნდობა“ (ის თქვენი OS-ისთვის შესაბამის ბრძანებას გაუშვებს და, საჭიროების შემთხვევაში, sudo-ს მოთხოვნას აჩვენებს).

#### Electron-ზე დაფუძნებული IDE-ები უგულებელყოფენ OS-ის სანდო სერტიფიკატების საცავს (`NODE_EXTRA_CA_CERTS`)

ზოგიერთი IDE — განსაკუთრებით **Antigravity IDE** და Electron-ის / VS Code-ის საფუძველზე შექმნილი სხვა აპები — შეიცავს საკუთარ Node.js-ის გაშვების გარემოს, რომელიც გამავალი `fetch`/HTTPS კავშირებისთვის **არ იყენებს OS-ის სანდო სერტიფიკატების საცავს**. OS/NSS დონეზე CA-ს სანდოდ მონიშვნა საკმარისია IDE-ის მშობლიური **ბექენდისთვის** (მაგ., Go ენის სერვერისთვის, რომელიც OS-ის CA კრებულს იყენებს), მაგრამ **Electron ფრონტენდისთვის** TLS მაინც წარუმატებელი იქნება — ეს გამოიხატება იმით, რომ აპი მომხმარებელს _სისტემიდან გამოსულად_ აჩვენებს ან _„კავშირის შეცდომას“_ აჩვენებს, მიუხედავად იმისა, რომ MITM ჟურნალი ბექენდის საწყისი მოთხოვნებისთვის დაბრუნებულ `200` პასუხებს აჩვენებს. საჭიროა ორი ნაბიჯი და ორივე მნიშვნელოვანია:

1. გაშვების გარემოსთვის პირდაპირ მიუთითეთ CA:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **გაუშვით IDE ამ გარსიდან.** დესკტოპის ხატულიდან / Dock-იდან / Start მენიუდან გაშვებისას გარსში ექსპორტირებული ცვლადები **არ** მემკვიდრეობს, ხოლო `~/.config/environment.d/*.conf` მხოლოდ ახალ გრაფიკულ სესიაში შესვლის შემდეგ მოქმედებს. თავდაპირველად სრულად დახურეთ IDE — Electron-ის ერთეული ეგზემპლარის ბლოკირების გამო, მეორე გაშვება მხოლოდ უკვე არსებულ პროცესზე გადაიტანს ფოკუსს და ახალი გარემო უგულებელყოფილი იქნება.

ზემოთ აღწერილი OS-ის ნდობის + NSS ნაბიჯი კვლავ აუცილებელია (ზოგიერთი ავტორიზაციის ნაკადის მიერ გამოყენებული Chromium-ის ქსელური სტეკი თითოეული მომხმარებლის NSS საცავს კითხულობს და `*.googleapis.com`-ისთვის საკუთარი სტატიკური მიბმებიც აქვს, რომლებსაც ადგილობრივად სანდოდ მონიშნული CA გადაფარავს). დამატებით, `NODE_EXTRA_CA_CERTS` ფარავს Node-ის `fetch` გზას.

### 3.3 DNS მარშრუტიზაცია

თითოეული აგენტისთვის, რომლის ტრაფიკის ჩაჭერაც გსურთ, მისი API ჰოსტი ან ჰოსტები უნდა მიუთითებდეს `127.0.0.1`-ზე. AgentBridge ავტომატურად მართავს `/etc/hosts` ჩანაწერებს, როდესაც დაყენების ოსტატში აგენტისთვის DNS-ს გადართავთ.

GitHub Copilot-ისთვის `/etc/hosts` ჩანაწერების მაგალითი:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 მოდელების ასახვა

წყარო → სამიზნე ასახვების განსაზღვრისთვის თითოეული აგენტის ბარათში გამოიყენეთ მოდელების ასახვის ცხრილი:

| საწყისი მოდელი (აგენტის მშობლიური) | სამიზნე მოდელი (OmniRoute) |
| ---------------------------------- | -------------------------- |
| `gpt-4o`                           | `claude-sonnet-4.7`        |
| `*` (უნივერსალური შაბლონი)         | `claude-haiku-4.7`         |

უნივერსალური შაბლონი `*` ნებისმიერ ამოუცნობ მოდელს მითითებულ სამიზნეზე ასახავს. მონაცემები ინახება `agent_bridge_mappings` ცხრილში.

> **რჩევა — აღმოაჩინეთ აგენტის რეალური მოდელის ID-ები.** IDE-მ შეიძლება გაგზავნოს მოდელების სახელები, რომლებიც განსხვავდება მის UI-ში ნაჩვენები სახელებისგან და იცვლება ძირითად ვერსიებს შორის. მაგალითად, **Antigravity 2** ქსელით აგზავნის `gemini-3.1-pro-low`, `gemini-pro-agent` და `gemini-3.1-flash-lite` მნიშვნელობებს — და არა ძველ დოკუმენტაციაში ნაჩვენებ `gemini-2.5-pro`-ს. გაგზავნეთ ერთი ჩატი შესაბამისი ასახვის გარეშე: MITM ჟურნალში ჩაიწერება შემომავალი `model:`-ის ზუსტი მნიშვნელობა და მოთხოვნა უცვლელად გატარდება. ასახეთ სწორედ ეს მნიშვნელობა, რის შემდეგაც მომდევნო მოთხოვნა ჩაიჭრება და თქვენს სამიზნეზე გადამისამართდება.

### 3.5 რისკის შესახებ შეტყობინება

AgentBridge იჭერს ავტორიზაციის მონაცემებს (OAuth ტოკენებს, API გასაღებებს), რომლებსაც IDE ზედა დონის პროვაიდერებთან ავთენტიფიკაციისთვის იყენებს. ეს მონაცემები **ჟურნალში ჩაწერამდე ინიღბება** (იხ. §2.7), თუმცა ხილულია OmniRoute-ის MITM ფენისთვის. თითოეული აგენტის პირველი გააქტიურებისას ნაჩვენებია რისკის შესახებ დახურვადი მოდალური შეტყობინება.

მართვის პანელზე ხელმისაწვდომია **ტექნიკური მომსახურებისა და დიაგნოსტიკის** ბარათი (`AgentBridgeMaintenanceCard`, მდებარეობს `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`-ში), რომელიც აჩვენებს ოპერაციულ MITM მარშრუტებს, რომლებსაც ადრე UI არ გააჩნდა. მისი ქვესათაურია: _„ჩაჭერის კონვეიერის თვითშემოწმება, სისტემის დარჩენილი მდგომარეობის გაუქმება და თქვენი კონფიგურაციის სხვა კომპიუტერზე გადატანა.“_ ბარათის კლიენტის დამხმარე ფუნქციები მდებარეობს `src/lib/inspector/agentBridgeMaintenanceApi.ts`-ში.

### 3.7 პორტატული კონფიგურაციის იმპორტი/ექსპორტი

AgentBridge-ს შეუძლია **ოპერატორის მიერ რეგულირებადი** მდგომარეობის სერიალიზაცია ვერსირებულ JSON ბლოკად, რათა კონფიგურაცია სხვადასხვა კომპიუტერზე გამეორდეს. სერიალიზატორია `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), ხოლო ვალიდაცია სრულდება `AgentBridgeConfigSchema`-ით.

ექსპორტი ზუსტად სამ ნაწილს მოიცავს (ჩაშენებული ნაგულისხმევი მნიშვნელობები განზრახ **არ** ექსპორტირდება, რათა იმპორტმა ისინი არასდროს დაადუბლიროს ან მათთან კონფლიქტი არ შექმნას):

| ველი             | წყარო                                                                          | შენიშვნები                                                                       |
| ---------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| `bypassPatterns` | მომხმარებლის მიერ განსაზღვრული გვერდის ავლის შაბლონები (`agent_bridge_bypass`) | bank/gov/okta-ს ნაგულისხმევი შაბლონები გამორიცხულია                              |
| `customHosts`    | Traffic Inspector-ის მორგებული ჰოსტები (`inspector_custom_hosts`)              | თითოეული: `{ host, kind: "llm"\|"app"\|"custom", label? }`                       |
| `agentMappings`  | თითოეული აგენტის მოდელების შესაბამისობები (`agent_bridge_mappings`)            | `{ [agentId]: [{ source, target }] }` შესაბამისობების მქონე თითოეული აგენტისთვის |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**იმპორტის ქცევა** (`POST /api/tools/agent-bridge/config`): გვერდის ავლის შაბლონები და თითოეული აგენტის შესაბამისობები **სრულად ჩანაცვლდება**; მორგებული ჰოსტები ემატება **იდემპოტენტურად** (`INSERT OR IGNORE`). პასუხი იტყობინება, თითოეული მათგანიდან რამდენი იქნა გამოყენებული:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

რა **არ** შედის კონფიგურაციაში: სერვერის გაშვებული მდგომარეობა, სერტიფიკატების ბილიკები, თითოეული აგენტის DNS მდგომარეობა, ზედა დონის CA-ს ბილიკი და TPROXY-ის პარამეტრები — ეს ჰოსტის/გაშვების გარემოს მდგომარეობაა და არა პორტატული პრეფერენციები.

### მგრძნობიარე ჰოსტების გვერდის ავლის სია

გვერდის ავლის სია უზრუნველყოფს, რომ ფინანსური დაწესებულებების, OAuth/SSO პროვაიდერებისა და სხვა მგრძნობიარე ჰოსტების ტრაფიკი **არასოდეს გაიშიფროს**. მათი TLS ტრაფიკი გამჭვირვალე TCP გვირაბის სახით გადაიცემა — OmniRoute არასოდეს ხედავს ღია ტექსტს.

გვერდის ავლის ნაგულისხმევი ნიმუშებია:

- `*.bank.*`, `*.gov.*` (ფინანსური/სამთავრობო)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/იდენტობა)
- `*.apple.com`, `*.icloud.com` (Apple-ის სისტემური სერვისები)

მომხმარებლის მიერ დამატებული გვერდის ავლის ნიმუშები ინახება `agent_bridge_bypass` ცხრილში და ყველა დანარჩენზე უპირატესია.

### საიდუმლო მონაცემების შენიღბვა

გამოიყენება `maskSecrets()` ფაილიდან `src/mitm/maskSecrets.ts`:

- თითოეული მოთხოვნის სხეულზე `TrafficBuffer.push()`-ამდე
- თითოეულ სათაურზე ჟურნალში ჩაწერამდე ან გავრცელებამდე

ნიმუშები: `sk-`/`ak-`/`pk-` პრეფიქსიანი ტოკენები, `Bearer` ტოკენები და ≥40-სიმბოლოიანი ზოგადი ტოკენები.

### ზედა დონის CA სერტიფიკატი

როდესაც `AGENTBRIDGE_UPSTREAM_CA_CERT` დაყენებულია, ფაილი გაშვებისას იკითხება. თუ გზა არსებობს, მაგრამ ფაილის წაკითხვა შეუძლებელია, AgentBridge ჟურნალში გასაგებ შეცდომას წერს და გაშვებაზე უარს ამბობს (ეს კორპორაციულ გარემოებში TLS-ის შეუმჩნეველ ხარვეზებს თავიდან აცილებს).

### ცნობილი შეზღუდვები

- **პორტი 443 პრივილეგიას საჭიროებს**: Linux-ზე AgentBridge-ს Node-ის ბინარულ ფაილზე სჭირდება `setcap 'cap_net_bind_service=+ep'`, ან ის `authbind`-ის მეშვეობით უნდა გაეშვას. დაყენების ოსტატი აჩვენებს ოპერაციული სისტემისთვის სპეციფიკურ ინსტრუქციებს.
- **საჭიროა IDE-ის ხელახლა გაშვება**: DNS-ის გადამისამართების შემდეგ IDE უნდა გადაიტვირთოს, რათა ჰოსტის ახალი გარჩევა ამოქმედდეს.
- **კოდში მყარად ჩაწერილი OAuth ტოკენები**: ზოგიერთი აგენტი (Kiro, Antigravity) OAuth-ის განახლების ტოკენებს ლოკალურად ინახავს. ისინი AgentBridge-ისთვის გამჭვირვალეა — ის თითოეულ მოთხოვნაში ხედავს Bearer ტოკენს, რომელიც ჟურნალში ჩაწერამდე ინიღბება.
- **Electron-ის ფრონტენდებს `NODE_EXTRA_CA_CERTS` სჭირდებათ**: IDE-ები, რომელთა ფრონტენდი ჩაშენებულ Node/Electron გარემოში მუშაობს, ოპერაციული სისტემის/NSS-ის სანდოობის საცავს უგულებელყოფენ და უნდა გაეშვან გარსიდან, სადაც `NODE_EXTRA_CA_CERTS` დაყენებულია (იხილეთ §3.2). მისი არარსებობის სიმპტომი: IDE-ის ბეკენდი ავთენტიფიკაციას გადის (MITM აჩვენებს `200` პასუხებს), მაგრამ UI სისტემაში შესულ მდგომარეობაში არ რჩება.
- **ერთი და იმავე IDE-ის რამდენიმე ინსტალაცია ერთმანეთისგან დამოუკიდებელია**: სისტემური ინსტალაცია (მაგ., `/usr/share/antigravity/antigravity`) და მომხმარებლის ლოკალური „Full“ ინსტალაცია (მაგ., `~/AntigravityIDE_Full/antigravity-ide`) სხვადასხვა პროცესია, საკუთარი გარემოებით — თითოეული მათგანი CA-ის ჩასმით თავიდან უნდა გაეშვას. ხელახლა გაშვებამდე ბინარული ფაილის გზით დაადგინეთ, რომელი მათგანია გაშვებული.
- **იდენტობას ადგენს აგენტის სისტემური მოთხოვნა და არა მარშრუტიზებული მოდელი**: როდესაც აგენტის მოდელს სხვა პროვაიდერზე გადაამისამართებთ, პასუხში აგენტი კვლავ საკუთარ თავდაპირველ იდენტობას ასახელებს (მაგ., Antigravity პასუხობს „მე Gemini-ზე ვმუშაობ“), რადგან IDE ამას სისტემურ მოთხოვნაში ამატებს. რეალური ბეკენდი გადაამოწმეთ `call_logs` / `proxy_logs`-ში (`provider`, `model`, `target_format`) და არა მოდელისთვის მისი ვინაობის კითხვით.

## §6 პრობლემების აღმოფხვრა

### პორტ 443-ის კონფლიქტი

თუ სხვა პროცესი უკვე უსმენს პორტ 443-ს (ვებ-სერვერი, VPN და ა.შ.):

```bash
lsof -i :443          # პროცესის პოვნა
sudo fuser -k 443/tcp  # იძულებით შეწყვეტა (გამოიყენეთ სიფრთხილით)
```

ალტერნატიულად, AgentBridge-ის პარამეტრებში მიუთითეთ არაპრივილეგირებული პორტი და დააყენეთ `iptables` / `pf` გადამისამართების წესები.

### სერტიფიკატი არ არის სანდოდ მიჩნეული

თუ AgentBridge-ის გაშვების შემდეგ IDE აჩვენებს TLS შეცდომებს:

1. გადაამოწმეთ, რომ სერტიფიკატი დაინსტალირებულია: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) ან `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. ზოგიერთი აპლიკაცია საკუთარ სანდოობის საცავს იყენებს (Firefox, Chrome Linux-ზე). ხელახლა გაუშვით „Trust Cert“ და შეამოწმეთ NSS/Firefox-ისთვის განკუთვნილი სერტიფიკატების საცავი.
3. სერტიფიკატის სანდოდ მონიშვნის შემდეგ გადატვირთეთ IDE — მიმდინარე TLS სესიები სანდოობის ძველ მდგომარეობას იყენებს.

### IDE-დან გამოსული ხართ / „კავშირის შეცდომა“ სანდო CA-ის მიუხედავად

სიმპტომი: DNS-ის გადამისამართებისა და CA-ის სანდოდ მონიშვნის შემდეგ Electron-ზე დაფუძნებული IDE (მაგ., Antigravity)
იხსნება **ანგარიშიდან გამოსულ მდგომარეობაში** ან აჩვენებს ავთენტიფიკაციის/კავშირის შეცდომას, თუმცა MITM-ის ჟურნალი აჩვენებს, რომ
საწყისი გამოძახებები (`loadCodeAssist`, `fetchAvailableModels`, …) აბრუნებს `200`-ს.

მიზეზი: IDE-ში **ჩაშენებული Node/Electron-ის შესრულების გარემო უგულებელყოფს OS-ის სანდოობის საცავს**. ნატიური
ბექენდი (Go-ს ენის სერვერი) ენდობა OS-ის CA-ს და გადის ავთენტიფიკაციას, მაგრამ Electron-ის ფრონტენდი
არა — ამიტომ UI მიიჩნევს, რომ კავშირი არ არის.

გამოსწორება (ორივე ნაბიჯი): გაიტანეთ `NODE_EXTRA_CA_CERTS=<ca.crt>` **და ხელახლა გაუშვით IDE ამ
shell-იდან**, და არა სამუშაო მაგიდის ხატულიდან. ჯერ სრულად დახურეთ IDE — Electron-ის singleton-ჩაკეტვა ნიშნავს,
რომ მეორე გაშვება მხოლოდ უკვე არსებულ პროცესზე გადაიტანს ფოკუსს და ახალი გარემო იგნორირებული იქნება. იხილეთ §3.2.
ეს შეესაბამება upstream-ში არსებულ ღია ანგარიშს, სადაც დამოუკიდებელი აგენტი MITM-ის გავლით მუშაობს, მაგრამ IDE-ის
ვარიანტი იმავე კონფიგურაციაში ვერ მუშაობს.

### DNS არ გავრცელებულა

შეამოწმეთ, განახლდა თუ არა `/etc/hosts`:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

გაასუფთავეთ DNS-ის კეში:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE ვერ გამოვლინდა

ავტომატური გამოვლენა გავრცელებულ ინსტალაციის ბილიკებს იყენებს. თუ გამოვლენა ვერ მოხერხდა, თუმცა IDE დაინსტალირებულია:

- შეამოწმეთ, ხომ არ მდებარეობს IDE-ის ორობითი ფაილი არასტანდარტულ ადგილას
- Setup Wizard მაინც იმუშავებს — გამოვლენის წარუმატებლობა მხოლოდ იმას ნიშნავს, რომ სამკერდე ნიშანი ინსტალაციის ბილიკს არ აჩვენებს

### დამმუშავებლის შეცდომები (upstream-იდან მიღება ვერ ხერხდება)

თუ AgentBridge მოთხოვნებს იჭერს, მაგრამ ყველა მათგანი წარუმატებელია:

1. გადაამოწმეთ, რომ `/dashboard/providers`-ზე მინიმუმ ერთი პროვაიდერია დაკავშირებული
2. შეამოწმეთ OmniRoute-ის სერვერის ჟურნალები: `APP_LOG_LEVEL=debug` `.env`-ში
3. გადაამოწმეთ, რომ `OMNIROUTE_BASE_URL` მიუთითებს როუტერის სწორ საბოლოო წერტილზე (ნაგულისხმევი: `http://127.0.0.1:20128`)

## §8 განვითარების გეგმა

### Trae-ის კვლევა

Trae შედარებით ახალი AI კოდირების ასისტენტია. დამმუშავებლის იმპლემენტაციამდე:

1. იდენტიფიცირება გაუკეთეთ ბინარულ ფაილს/გაფართოებას VS Code-ის / JetBrains-ის მარკეტპლეისებში ან ცალკე აპის სახით
2. API ჰოსტებისა და endpoint-ების სტრუქტურის აღმოსაჩენად mitmproxy-ით ჩაიწერეთ ტრაფიკი
3. განსაზღვრეთ ავთენტიფიკაციის მექანიზმი
4. მომსახურების პირობებისა და API-ის აღმოჩენადობის საფუძველზე შეაფასეთ, ღირს თუ არა გაგრძელება

კვლევის დასრულებამდე დაფაზე Trae-ის ბარათს აქვს „კვლევის პროცესშია“ სამკერდე ნიშანი და ბმული „სიცოცხლისუნარიანობის შეტყობინება“. დამმუშავებლის stub-ი მისამართზე `src/mitm/handlers/trae.ts` წარმოქმნის სტრუქტურირებულ შეცდომას `ჯერ არ არის იმპლემენტირებული`.

### რიგში მყოფი აგენტები (საჭიროა MITM — ინდივიდუალური საბაზისო URL-ის მხარდაჭერა არ აქვთ)

შემდეგ ხელსაწყოებს მიმდინარე ვერსიებში ინდივიდუალური საბაზისო URL-ების მხარდაჭერა არ აქვთ, რის გამოც MITM მონაცემთა გადაჭერის ერთადერთი გზაა. სიცოცხლისუნარიანობის შეფასება ჯერ არ დასრულებულა:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDE-ისგან დამოუკიდებელი)
- **Cowork** (Anthropic-ის დესკტოპ-აპი)

შენიშვნა: GitHub Copilot CLI ≥v1.0.19-ს აქვს `COPILOT_PROVIDER_BASE_URL`-ის მხარდაჭერა — ამ ხელსაწყოსთვის MITM-ის ნაცვლად პირდაპირი კონფიგურაცია გამოიყენეთ.
