```

├─ დიახ → ღრუბლოვანი აგენტები (POST /api/v1/agents/tasks)
└─ არა → განაგრძეთ
    │
    გყავთ სხვა აგენტი, რომელიც A2A-ს იყენებს და თანამშრომლობა სურს?
    ├─ დიახ → A2A (POST /a2a)
    └─ არა → განაგრძეთ
        │
        გჭირდებათ ლოკალურად დაყენებული CLI კოდირების აგენტების სიის ნახვა / კონფიგურაცია?
        ├─ დიახ → ACP (GET /api/acp/agents)
        └─ არა → გამოიყენეთ ჩვეულებრივი /v1/chat/completions
```

## 1. A2A — აგენტებს შორის

**სპეციფიკაცია:** [A2A v0.3](https://a2a-protocol.org)
**OmniRoute-ის საბოლოო წერტილი:** `POST /a2a` (JSON-RPC 2.0)
**აგენტის ბარათი:** `GET /.well-known/agent.json`

### როდის გამოვიყენოთ

- მრავალაგენტიანი სისტემის შექმნისას, სადაც OmniRoute ერთ-ერთი თანასწორი მონაწილეა
- OmniRoute-ის მარშრუტიზაციის ინტელექტის (`smart-routing`, `quota-management` და სხვ.) მისაწვდომად ისეთი ფრეიმვორკების აგენტებისთვის, როგორიცაა Google ADK, ან ზოგადი აგენტების ქსელებისთვის
- OmniRoute-ის სტანდარტული აღმოჩენისა და გამოძახების ინტერფეისის მიღმა მოსაქცევად

### მეთოდები

- `message/send` — შეტყობინების გაგზავნა და სინქრონული პასუხის მიღება
- `message/stream` — შეტყობინების გაგზავნა და SSE-ნაკადით პროგრესის მოვლენების მიღება
- `tasks/get` — ამოცანის ID-ით წაკითხვა
- `tasks/cancel` — მიმდინარე ამოცანის გაუქმება

### ჩაშენებული უნარები (6)

- `smart-routing` — მოთხოვნის ოპტიმალური კომბინაციის გავლით მარშრუტიზაცია
- `quota-management` — თითოეული პროვაიდერის კვოტის მდგომარეობის მიწოდება
- `provider-discovery` — დაყენებული პროვაიდერებისა და მათი შესაძლებლობების ჩამოთვლა
- `cost-analysis` — მოთხოვნის/საუბრის ღირებულების შეფასება
- `health-report` — თითოეული პროვაიდერისთვის breaker/cooldown/lockout მდგომარეობების გაერთიანება
- `list-capabilities` — აგენტის ხელმისაწვდომი უნარებისა და მეტამონაცემების ჩამოთვლა

### დეტალური მიმოხილვა

ტრანსპორტის დეტალების, აგენტის ბარათის სტრუქტურის, ამოცანის TTL-ის კონფიგურაციისა და ახალი უნარების დამატების შაბლონისთვის იხილეთ [A2A-SERVER.md](./A2A-SERVER.md).

## 2. ACP — CLI აგენტების რეესტრი

**OmniRoute-ის endpoint:** `GET /api/acp/agents`
**წყარო:** `src/lib/acp/{index,manager,registry}.ts`

### რას წარმოადგენს

ACP არის OmniRoute-ის **ლოკალური CLI აგენტების ინვენტარი**. ის ადგენს, რომელი პროგრამირების CLI-ებია დაინსტალირებული ჰოსტზე (Cursor, Cline, Claude Code, Codex CLI, Continue და ა.შ.), განსაზღვრავს მათ ვერსიებს და აჩვენებს მათ მართვის პანელში, რათა მომხმარებელმა თითოეული CLI OmniRoute-ზე მიმართოს.

ეს გარე პროტოკოლი არ არის — ეს არის შიდა რეესტრი, რომელიც უზრუნველყოფს „CLI Tools“ ინტერფეისისა და CLI-ის ციფრული ანაბეჭდების თვალყურის დევნების ფუნქციონირებას (იხილეთ [CLI-TOOLS.md](../reference/CLI-TOOLS.md)).

### რას აკეთებს

- ამოწმებს ჰოსტს დაინსტალირებული CLI-ის შესრულებადი ფაილების მოსაძებნად (OS-ის მიხედვით იყენებს `which` / `where`-ს)
- კითხულობს თითოეული CLI-ის ვერსიას (იძახებს `<bin> --version`-ს)
- სურვილისამებრ იღებს მომხმარებლის მიერ განსაზღვრულ მორგებულ აგენტებს (შესრულებადი ფაილის გზა + ვერსიის შემოწმება + გაშვების არგუმენტები)
- მორგებულ აგენტებს პარამეტრებში ინახავს
- მართვის პანელს უბრუნებს გაერთიანებულ სიას

### REST API

| Endpoint          | მეთოდი | აღწერა                                                                                | ავტორიზაცია  |
| ----------------- | ------ | ------------------------------------------------------------------------------------- | ------------ |
| `/api/acp/agents` | GET    | აღმოჩენილი + მორგებული აგენტების სია (დაინსტალირებულთა/საერთო რაოდენობა)              | API გასაღები |
| `/api/acp/agents` | POST   | მორგებული აგენტის დამატება/განახლება/წაშლა (ქმედების განმსაზღვრელი მოთხოვნის სხეულში) | API გასაღები |

POST-ის სხეულის ფორმა (`customAgentBodySchema` ფაილში `src/app/api/acp/agents/route.ts`):

```json
{
  "action": "add|update|remove",
  "id": "cursor",
  "name": "Cursor",
  "binary": "/usr/local/bin/cursor",
  "versionCommand": "--version",
  "providerAlias": "cursor",
  "spawnArgs": ["--api-base", "http://localhost:20128"],
  "protocol": "stdio"
}
```

### გამოყენების შემთხვევები

- მართვის პანელის „CLI Tools“ გვერდი აჩვენებს, რა არის დაინსტალირებული, და გეხმარებათ თითოეული მათგანის OmniRoute-ზე მიმართვაში
- მორგებული აგენტები გამოცდილ მომხმარებლებს საშუალებას აძლევს, დაარეგისტრირონ შიდა/დახურული CLI-ები, რომლებსაც OmniRoute ნაგულისხმევად არ იცნობს
- აღმოჩენის შედეგი ავსებს `cli-tools`-ის ციფრული ანაბეჭდების მატრიცას

### როდის არ უნდა გამოიყენოთ ACP

- ACP ამოცანებს არ _ასრულებს_. ის მხოლოდ აღმოაჩენს და აკონფიგურირებს CLI-ებს. CLI-ის რეალურად გამოსაძახებლად ის თავად უნდა გაუშვათ OmniRoute-ის მიერ მოწოდებული გარემოს ცვლადებით (`OPENAI_BASE_URL`, `OPENAI_API_KEY` და ა.შ.).

## 3. ღრუბლოვანი აგენტები

**OmniRoute-ის endpoint-ები:** `/api/v1/agents/tasks/*` (სიცოცხლის ციკლი) + `/api/cloud/*` (დამაკავშირებელი ინფრასტრუქტურა)
**წყარო:** `src/lib/cloudAgent/`

### რას წარმოადგენს

მესამე მხარის ღრუბლოვანი პროგრამირების აგენტებისთვის განკუთვნილი ერთიანი ინტერფეისი. თქვენ აგზავნით მოთხოვნას + რეპოზიტორიუმის URL-ს, OmniRoute გადასცემს მას შესაბამის ღრუბლოვან აგენტს, პერიოდულად ამოწმებს სტატუსს და აბრუნებს შედეგებს.

### მხარდაჭერილი აგენტები (3, ყველა დადასტურებულია `src/lib/cloudAgent/agents/`-ში)

- `codex-cloud` — OpenAI Codex Cloud
- `devin` — Cognition Devin
- `jules` — Google Jules

### სიცოცხლის ციკლი

```
POST /api/v1/agents/tasks
  → BaseAgent.createTask() აგენტის თითოეული კლასისთვის
  → გარე სერვისი იწყებს მუშაობას
  → DB-ში იქმნება ამოცანის ჩანაწერი (cloud_agent_tasks)
  ↓
GET /api/v1/agents/tasks/[id]
  → სტატუსის ზარმაცი სინქრონიზაცია პროვაიდერისგან
  → აბრუნებს მიმდინარე სტატუსს + გეგმას + აქტივობის ჟურნალს
  ↓
POST /api/v1/agents/tasks/[id]   (ქმედება: "approve" | "message" | "cancel")
  → გადაგზავნის პროვაიდერთან (ან ლოკალურად მონიშნავს გაუქმებულად)
  ↓
DELETE /api/v1/agents/tasks/[id]
  → ლოკალური გაუქმება
```

### ავტორიზაცია

⚠️ **ყველა `/api/v1/agents/tasks/*` endpoint საჭიროებს მართვის ავტორიზაციას** (commit `588a0333`). მხოლოდ Bearer-ის გამომყენებელი კლიენტები v3.8.0-დან იღებენ 401-ს.

### დეტალური მიმოხილვა

`CloudAgentBase` კონტრაქტის, თითოეული აგენტის სპეციფიკის, სქემის დეტალებისა და ავტორიზაციის მონაცემების დამაკავშირებელი endpoint-ების შესახებ იხილეთ [CLOUD_AGENT.md](./CLOUD_AGENT.md).

## შედარება: A2A და Cloud Agents

ორივეს აქვს „ხანგრძლივად მიმდინარე დავალებები“, თუმცა სხვადასხვა დონეზე:

| ასპექტი                       | A2A                                                                                                        | Cloud Agents                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| სტანდარტი                     | ღია A2A v0.3                                                                                               | OmniRoute-სთვის სპეციფიკური                                   |
| სად სრულდება გამოთვლები       | OmniRoute-ის შიგნით (იყენებს კონფიგურირებულ კომბინაციებს)                                                  | გარეთ (Codex / Devin / Jules სერვერებზე)                      |
| დავალების ხანგრძლივობა        | ნაგულისხმევი TTL — 5 წთ. (კონფიგურირებადია `TaskManager`-ში)                                               | რამდენიმე წუთიდან რამდენიმე საათამდე                          |
| რეპოზიტორიის კონტექსტის ცოდნა | არა (გადასცემს მხოლოდ მოთხოვნებს)                                                                          | დიახ (რეპოზიტორიის URL + ბრენჩი)                              |
| გამოყენების შემთხვევა         | აგენტებს შორის თანამშრომლობა, ჭკვიანი მარშრუტიზაცია სერვისის სახით                                         | „განახორციელე ფუნქცია X რეპოზიტორიაში Y“ დავალების დელეგირება |
| ავთენტიფიკაცია                | არასავალდებულო `OMNIROUTE_API_KEY` `/a2a`-სთვის; მართვის ავთენტიფიკაცია `/api/a2a/*` REST დამხმარეებისთვის | ყოველთვის მართვის ავთენტიფიკაცია                              |

## ინტეგრაციის მაგალითები

### OmniRoute-ის A2A შესაძლებლობების აღმოჩენა

```bash
curl http://localhost:20128/.well-known/agent.json
```

აბრუნებს Agent Card-ს ექვსივე უნარით, ტრანსპორტებითა და ვერსიით.

### OmniRoute-ის A2A აგენტად გამოძახება

```bash
curl -X POST http://localhost:20128/a2a \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "method": "message/send",
    "params": {
      "messages": [{"role": "user", "content": "Route this prompt"}],
      "skill": "smart-routing"
    },
    "id": 1
  }'
```

### ACP-ის მეშვეობით დაყენებული CLI აგენტების ჩამონათვალის მიღება

```bash
curl http://localhost:20128/api/acp/agents \
  -H "Authorization: Bearer <api-key>"
```

### მორგებული CLI აგენტის დამატება

```bash
curl -X POST http://localhost:20128/api/acp/agents \
  -H "Authorization: Bearer <api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "add",
    "id": "my-custom-cli",
    "name": "My Custom CLI",
    "binary": "/opt/mycli/bin/mycli",
    "versionCommand": "--version",
    "providerAlias": "openai"
  }'
```

### Cloud Agent-ის დავალების გაგზავნა

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "devin",
    "prompt": "Implement feature X in repo Y",
    "source": {
      "repoName": "user/repo",
      "repoUrl": "https://github.com/user/repo",
      "branch": "main"
    }
  }'
```

### ღრუბლოვანი დავალების სტატუსის პერიოდულად შემოწმება

```bash
curl http://localhost:20128/api/v1/agents/tasks/<task-id> \
  -H "Cookie: auth_token=..."
```

## როდის რომელი გამოიყენოთ

- **ჩატბოტის / კოპილოტის ფრონტენდი** → `/v1/chat/completions` (OpenAI-თან თავსებადი — არ არის აგენტების პროტოკოლი)
- **მრავალაგენტიანი თანამშრომლობა** → A2A
- **ლოკალური CLI-ების დაფაზე ჩამოთვლა** → ACP
- **ხანგრძლივად მიმდინარე კოდირების დავალებების ღრუბლოვანი სერვისებისთვის დელეგირება** → Cloud Agents
