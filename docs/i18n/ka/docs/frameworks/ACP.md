OmniRoute ერთმანეთისგან განასხვავებს **CLI-ის აღმოჩენას**, **ნატიურ Agent Client Protocol-ს** და
**მემკვიდრეობით stdio ადაპტერებს**. დაინსტალირებული ბინარული ფაილის პოვნა არ ადასტურებს
მის ავთენტიფიკაციას, მოდელთან თავსებადობას ან მოთხოვნის დასამუშავებლად მზადყოფნას.

მართვის პანელი ინვენტარიზაციისა და მორგებული აგენტების რეგისტრაციისთვის იყენებს
`GET /api/acp/agents`-სა და `POST /api/acp/agents`-ს. ეს მხოლოდ ლოკალური მართვის
მარშრუტებია და არა პროცესების გასაშვებად ან მოთხოვნების გასაგზავნად განკუთვნილი
საჯარო API. შიდა `AcpManager` ავტომატურად არ ხდება HTTP-პროვაიდერის სათადარიგო ვარიანტი.

## რეგისტრირებული კონტრაქტები

`config/cli-tools-manifest.json` არის ჩაშენებული გაშვების ბინარული ფაილების,
არგუმენტებისა და ბეკენდის რეჟიმების ჭეშმარიტების წყარო. რეესტრი თავის განსაზღვრებებს
ამ მანიფესტიდან იღებს. აღმოჩენის შედეგი 60 წამის განმავლობაში კეშირდება.

- `acp`: Gemini-ის კონტრაქტი უშვებს `gemini --experimental-acp`-ს და
  ოფიციალური TypeScript SDK-ის მეშვეობით ახალ ხაზებზე დაყოფილი ACP JSON-RPC-ით
  ურთიერთობს.
- `stdio-adapter`: სხვა რეგისტრირებული კონტრაქტები ინარჩუნებენ მემკვიდრეობით
  ადაპტერს, რომელიც შეყვანას ახალი ხაზებით იღებს და გამოტანას stdout-ში წერს.
  გამოტანის ორწამიანი უმოქმედობის პერიოდი მის პასუხს ასრულებს.
  ეს ადაპტერი ამ CLI-ებისთვის ნატიური ACP-ის მხარდაჭერას **არ** ადასტურებს.

Gemini გაშვების ალამს თავის [CLI ცნობარში](https://geminicli.com/docs/cli/cli-reference/) აღწერს.
კლიენტი ინიციალიზაციისთვის, სესიის შესაქმნელად, მოთხოვნების გასაგზავნად,
შეტყობინებებისა და გაუქმებისთვის [ოფიციალურ ACP SDK-ს](https://github.com/agentclientprotocol/typescript-sdk)
იყენებს.

მორგებული აგენტების განსაზღვრებები ადმინისტრატორის მიერ კონტროლირებულ გაშვების
კონტრაქტებად რჩება. ბინარული ფაილისა და არგუმენტების რეგისტრაცია ამ პროცესს
სერვერის მომხმარებლის ლოკალური შესრულების პრივილეგიებს ანიჭებს; რეგისტრაცია
იზოლირებულ გარემოს არ ქმნის. ვერსიის შემოწმება იღებს მხოლოდ რეგისტრირებულ
შესრულებად ფაილსა და ვერსიის ამოცნობილ ალამს.

## შიდა გაშვების API

```typescript
import { acpManager } from "@/lib/acp";

const session = acpManager.spawn("gemini", {
  cwd: process.cwd(),
  // გადასცით მხოლოდ ამ აგენტისთვის განზრახ მინიჭებული პროვაიდერის ცვლადები.
  env: {
    GEMINI_API_KEY: process.env.GEMINI_API_KEY,
  },
});

try {
  const response = await acpManager.sendPrompt(session.id, "ახსენით ეს პროექტი", 120_000);
  // პასუხი დაამუშავეთ გამომძახებელ აპლიკაციაში.
} finally {
  acpManager.kill(session.id);
}
```

`spawn(agentId, options)` შესრულებად ფაილსა და არგუმენტებს რეგისტრირებული
განსაზღვრებიდან ადგენს. გამომძახებლისთვის ხელმისაწვდომი ერთადერთი პარამეტრებია
`cwd` და `env`; ძველი `spawn(agentId, binary, args, env)` სიგნატურა და შესრულებადი
ფაილის ჩანაცვლება უარყოფილია. ეს მენეჯერი HTTP გაშვების კონტრაქტებს არ უჭერს მხარს.

შვილობილი პროცესი მემკვიდრეობით იღებს იმავე ოპერაციულ სისტემას, ტერმინალს,
ლოკალსა და სერტიფიკატების დაშვებულ სიას, რასაც CLI გამშვებები. სერვერისა და
პროვაიდერის საიდუმლო მონაცემები მშობელი გარემოდან არ კოპირდება. არჩეული CLI-ისთვის
საჭირო ავტორიზაციის მონაცემები ცხადად უნდა გადაეცეს ან ამ CLI-ის საკუთარი
ლოკალური ავთენტიფიკაციის მეშვეობით მიეწოდოს. შვილობილ პროცესს კვლავ აქვს
ლოკალური მომხმარებლის ფაილური სისტემის ნებართვები და საკუთარი კონფიგურაციის
წაკითხვა შეუძლია.

## ნატიური სასიცოცხლო ციკლი და შეზღუდვები

1. გაუშვით რეგისტრირებული ბინარული ფაილი, მოახდინეთ ACP-ის ინიციალიზაცია და
   შექმენით სესია, რომლის ფესვიც არჩეული სამუშაო დირექტორიაა. ინიციალიზაციის
   ლიმიტი ათი წამია.
2. გაგზავნეთ მოთხოვნა და შეაგროვეთ მხოლოდ ამ სესიის ტექსტური შეტყობინებები.
   დასრულებას ნიშნავს მოთხოვნის RPC პასუხი და არა stdout-ის უმოქმედობის პერიოდი.
3. გამოიყენეთ მოთხოვნის ერთი ვადა, რომელიც დაუსრულებელ ინიციალიზაციასაც მოიცავს;
   ნაგულისხმევი მნიშვნელობა 120 წამია. ერთსა და იმავე პროცესში პარალელური
   მოთხოვნები უარყოფილია.
4. ნატიური ვადის ამოწურვისას სცადეთ `session/cancel` და დაასრულეთ პროცესი.
   შეზღუდული 100 ms-იანი ფანჯარა შეტყობინებას დასრულებამდე გამოტანის საშუალებას აძლევს.
5. დახურეთ ტრანსპორტის მდგომარეობა და წაშალეთ სესია, როდესაც ინიციალიზაცია
   წარუმატებელია, კავშირი იხურება, პროცესი სრულდება ან გამომძახებელი მას წყვეტს.

ხელსაწყოების ნებართვების მოთხოვნები უარყოფილია. ფაილური სისტემის ან ტერმინალის
კლიენტის შესაძლებლობები არ ცხადდება. ეს შეზღუდვები თავად შვილობილ ბინარულ ფაილს
იზოლირებულ გარემოში არ ათავსებს და CLI-ის საკუთარ ავტორიზაციის პარამეტრებს არ
ანაცვლებს.

როგორც ნატიური ტექსტი, ისე მემკვიდრეობითი stdout/stderr ინახავს არაუმეტეს 1 MiB
სიმბოლოს, ამასთან ინარჩუნებს უახლეს გამოტანას და ამატებს შეკვეცის შეტყობინებას.
SDK-ის დამუშავებამდე ნატიური სადენური პროტოკოლის ერთი ფრეიმი მაქსიმუმ 2 MiB
ბაიტით შემოიფარგლება. ბუფერები თითოეულ მოთხოვნაზე ნულდება.

`kill(sessionId)` აგზავნის SIGTERM-ს, შემდეგ კი, თუ პროცესი არ დასრულებულა,
ხუთი წამის შემდეგ — SIGKILL-ს. მემკვიდრეობითი მოთხოვნის ვადის ამოწურვა
ათავისუფლებს მსმენელებსა და ტაიმერებს, თუმცა სესიას სხვა მოთხოვნისთვის
ხელმისაწვდომად ტოვებს; დასრულების შემდეგ `kill()`-ის ან `killAll()`-ის გამოძახებაზე
პასუხისმგებლები კვლავ გამომძახებლები არიან.

## მოვლენები და ინსპექტირება

მენეჯერი გამოსცემს `stdout`, `stderr` და `exit` მოვლენებს, თითოეულს `sessionId`-თან
ერთად. `sessionError` ასახავს გასუფთავებულ სატრანსპორტო შეცდომას. თავსებადობის
`error` მოვლენა მხოლოდ მაშინ გამოიცემა, როდესაც მას გამომწერი ჰყავს, ამიტომ
ბინარული ფაილის არარსებობა დაუმუშავებელ EventEmitter შეცდომას ვერ გამოიწვევს.

- `getSession(sessionId)` აბრუნებს მართულ სესიას ან `undefined`-ს.
- `getActiveSessions()` გამორიცხავს გაჩერებულ ან გაჩერების პროცესში მყოფ სესიებს.
- `sendInput(sessionId, input)` ხელმისაწვდომია მხოლოდ აქტიური მემკვიდრეობითი
  ადაპტერისთვის; ნატიური ACP უარყოფს დაუმუშავებელ შეყვანას თავისი JSON-RPC
  ნაკადის დასაცავად.
- `killAll()` ასრულებს ამ ეგზემპლარის მიერ მართულ ყველა სესიას.

## ვალიდაციის საზღვრები

დეტერმინისტული ფიქსტურები მოიცავს ნატიურ ხელის ჩამორთმევას, ტექსტურ გამოტანას,
უარყოფილ ნებართვებს, გაუქმებას, პარალელურ მოთხოვნებს, წარუმატებელ ინიციალიზაციას,
პროცესის დასრულებას, გამოტანის ლიმიტებსა და საიდუმლო მონაცემების იზოლაციას.
