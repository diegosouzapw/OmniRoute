## არქიტექტურა

```
კლიენტი → /v1/chat/completions (apiKeyInfo წინასწარ განსაზღვრულია)
  → handleChatCore() [open-sse/handlers/chatCore.ts]
    → resolveMemoryOwnerId(apiKeyInfo)        # იღებს id-ს
    → getMemorySettings()                     # დაკეშილი პარამეტრები
    → shouldInjectMemory(body, {enabled})     # შემოწმების შლუზი
    → retrieveMemories(apiKeyId, config)      # SQL + FTS5 + სურვილისამებრ ვექტორი
    → injectMemory(body, memories, provider)  # სისტემური ან მომხმარებლის შეტყობინება
  → ზედა დონის პროვაიდერის გამოძახება
  → პასუხისას: extractFacts(text, apiKeyId, sessionId)  # არამბლოკავი
    → setImmediate → createMemory(fact) თითოეულ დამთხვევაზე
                   → embed(content) + upsertVector(id, vec)
```

ჩასმისა და ამოღების გამოძახების ადგილები დაკავშირებულია
`open-sse/handlers/chatCore.ts`-ში (მოძებნეთ `retrieveMemories`, `injectMemory`
და `extractFacts`).

## ძრავის არქიტექტურა (3-დონიანი განსაზღვრა)

Memory Engine შესრულების დროს განსაზღვრავს მოძიების გზას ხელმისაწვდომი
ინფრასტრუქტურისა და პარამეტრების საფუძველზე. არსებობს სამი დონე, რომლებიც
პრიორიტეტების მიხედვით გამოიყენება:

```
  ┌─────────────────────────────────────────────────────────────┐
  │  დონე 0 — საკვანძო სიტყვა (FTS5)                            │
  │  ხელმისაწვდომობა განისაზღვრება შემოწმებით: FTS5 მაშინ, როცა │
  │  SQLite-ის აგება მას მხარს უჭერს (better-sqlite3 /          │
  │  node:sqlite / bun:sqlite); მიუწვდომელია FTS5-ის არმქონე    │
  │  აგებებში (მაგ., sql.js/WASM — "no such module: fts5").     │
  │  გამოიყენება, როცა strategy = "exact", ან სარეზერვოდ;       │
  │  ძრავის სტატუსში keyword ასახავს შემოწმების შედეგს.         │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ strategy = semantic|hybrid?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  დონე 1 — ჩაშენებული ვექტორი (sqlite-vec)                   │
  │  sqlite-vec v0.1.9 იტვირთება db.loadExtension()-ით.         │
  │  KNN-ის სრული ძიება Float32 ვექტორებზე. აქტიურია, როცა:     │
  │   • sqlite-vec loadExtension წარმატებით სრულდება            │
  │   • ხელმისაწვდომია embedding-ის წყარო (remote | static |    │
  │     transformers), რომელსაც Float32Array-ის შექმნა შეუძლია │
  │   • vec_memories ცხრილი არსებობს (იქმნება ready()-ის        │
  │     პირველი გამოძახებისას)                                  │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ qdrant.enabled?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  დონე 2 — Qdrant (სურვილისამებრ გარე ვექტორული მონაცემთა   │
  │  ბაზა)                                                       │
  │  ჩართვისას semantic/hybrid რეჟიმებისთვის sqlite-vec-ს       │
  │  ანაცვლებს. საჭიროა გაშვებული Qdrant ეგზემპლარი და          │
```

დეგრადაცია ავტომატური და გამჭვირვალეა:

- თუ sqlite-vec-ის ჩატვირთვა ვერ მოხერხდება, დონე 1 მიუწვდომელია → სისტემა
  სარეზერვოდ დონე 0-ზე გადადის.
- თუ embedding-ის წყარო შეცდომას აბრუნებს, დონე 1 სარეზერვოდ დონე 0-ზე
  გადადის.
- თუ Qdrant გაუმართავია, დონე 2 სარეზერვოდ დონე 1-ზე გადადის (ან დონე 0-ზე,
  თუ დონე 1-ც მიუწვდომელია).

## ემბედინგის წყაროები

ემბედინგის შრე (`src/lib/memory/embedding/`) განსაზღვრავს გამოსაყენებელ წყაროს
`MemorySettingsExtended.embeddingSource`-ის მიხედვით:

| წყარო          | აღწერა                                                                                         | საჭიროა გასაღები | ცივი გაშვება     |
| -------------- | ---------------------------------------------------------------------------------------------- | ---------------- | ---------------- |
| `remote`       | იყენებს კონფიგურირებული პროვაიდერის ემბედინგის API-ს (OpenAI, Cohere და სხვ.)                  | დიახ             | არ არის          |
| `static`       | ლოკალური საძიებო ცხრილის ემბედინგი `potion-base-8M`-ის მეშვეობით (WordPiece + საშუალო პულინგი) | არა              | ~200ms           |
| `transformers` | ლოკალური ONNX ინფერენსი `@huggingface/transformers` v4-ის, `all-MiniLM-L6-v2`-ის მეშვეობით     | არა              | ~3s + ~400MB RAM |
| `auto`         | შესრულების დროს განსაზღვრა: remote (თუ გასაღები არსებობს) → static → transformers → null       | დამოკიდებულია    | დამოკიდებულია    |

**განსაზღვრის თანმიმდევრობა `auto`-სთვის:**

1. მოიძებნოს პირველი პროვაიდერი `listEmbeddingProviders()`-ში, რომლისთვისაც `hasKey === true` → `remote`.
2. თუ `settings.staticEnabled === true` → `static`.
3. თუ `settings.transformersEnabled === true` → `transformers`.
4. წინააღმდეგ შემთხვევაში → `null` (გადადის FTS5 საკვანძო სიტყვებით ძიებაზე).

ემბედინგის კეში (`src/lib/memory/embedding/cache.ts`) იყენებს მეხსიერებაში არსებულ
LRU რუკას, რომლის გასაღებია `${source}:${model}:${dim}:${sha256(text)}` და რომელიც
შეზღუდულია `MEMORY_EMBEDDING_CACHE_MAX` ჩანაწერით (ნაგულისხმევად 1000), ხოლო
TTL არის `MEMORY_EMBEDDING_CACHE_TTL_MS` (ნაგულისხმევად 5 წთ). ის საერთოა ყველა
გამომძახებლისთვის პროცესის სასიცოცხლო ციკლის განმავლობაში.

## ჰიბრიდული RRF (k=60)

როდესაც `strategy = "hybrid"` და ვექტორული საცავი ხელმისაწვდომია, შედეგების მიღება
იყენებს Reciprocal Rank Fusion-ს FTS5-ისა და ვექტორული შედეგების გასაერთიანებლად:

```
RRF(d) = Σ  1 / (k + rank_i(d))      სადაც k = 60 (კონფიგურირებადია MEMORY_RRF_K-ის მეშვეობით)
          i
```

კერძოდ:

1. შესრულდეს FTS5 ძიება → რანჟირებული სია `R_fts` (პოზიცია 1..N).
2. შესრულდეს KNN ვექტორული ძიება → რანჟირებული სია `R_vec` (პოზიცია 1..M).
3. თითოეული უნიკალური `memoryId`-სთვის:  
   `rrf_score = 1/(60 + fts_rank)` + `1/(60 + vec_rank)` (0, თუ სიაში არ არის).
4. დალაგდეს `rrf_score`-ის მიხედვით კლებადობით და გამოყენებულ იქნეს ტოკენების ბიუჯეტის თანმიმდევრული გავლა.

ცნობილია, რომ RRF ეფექტიანია ჰეტეროგენულ მოძიების სისტემებს შორის ქულების
ნორმალიზაციის საჭიროების გარეშე. ნაგულისხმევი `k=60` აღებულია Cormack და სხვების
თავდაპირველი ნაშრომიდან და კარგად მუშაობს მცირე კორპუსებისთვის (<10k მეხსიერების ჩანაწერი).

## შევსება (ზარმაცი + ხელახალი ინდექსაცია)

როდესაც ემბედინგის მოდელი იცვლება (რაც `embedding_signature`-ის მეშვეობით
ვლინდება), ვექტორული საცავი თავიდან აიგება და ყველა არსებული მეხსიერების ჩანაწერი
`memories` ცხრილში მოინიშნება მნიშვნელობით `needs_reindex = 1`.

**ზარმაცი შევსება**: მომდევნო მოძიებისას, ნებისმიერი მეხსიერების ჩანაწერი, რომელსაც
ვექტორული ჩანაწერი აკლია, ძიების გაშვებამდე ემბედირდება და `vec_memories`-ში
ჩაისმება. ამგვარად, შევსების ხარჯი ნაწილდება რეალურ მოთხოვნებზე და არ ბლოკავს გაშვებას.

**ცხადი ხელახალი ინდექსაცია**: `/dashboard/memory`-ის Engine ჩანართში
ხელმისაწვდომია ღილაკი "ხელახლა დააინდექსირე ახლა", რომელიც იძახებს
`POST /api/memory/reindex`-ს. დამმუშავებელი იძახებს `runReindexBatch()`-ს
`src/lib/memory/reindex.ts`-დან, რომელიც თითო მოთხოვნაზე ამუშავებს მაქსიმუმ
`limit` მომლოდინე ჩანაწერს. პროგრესის პერიოდულად შემოწმება შესაძლებელია
`GET /api/memory/engine-status`-ის მეშვეობით (`vectorStore.needsReindex`).

`memory_vec_meta` ცხრილი (მიგრაცია `083_memory_vec.sql`) ინახავს:

- `active_dim` — მიმდინარე ვექტორის განზომილება (null = ჯერ არ არის დაკალიბრებული).
- `embedding_signature` — `${source}:${model}:${dim}`, რომელიც ცვლილებების აღმოსაჩენად გამოიყენება.
- `last_reset_at` — ბოლო სრული განულების დროის ნიშნული.
- `vec_loaded` — 0/1 ალამი, რომელიც მიუთითებს, წარმატებით ჩაიტვირთა თუ არა sqlite-vec.

| `vectorStore` | `"sqlite-vec" \| "qdrant" \| "auto"` | `"auto"` | გამოსაყენებელი ვექტორული backend |

ეს პარამეტრები ხელმისაწვდომია `GET /PUT /api/settings/memory`-ის მეშვეობით (სქემა `MemorySettingsExtendedSchema`).

ინდექსები: `api_key_id`, `session_id`, `type`, `expires_at`, ასევე უნიკალური

ზრდას განმეორებითი უპირატესობის განცხადებების გამო.

### სრულტექსტური ძიება (`memory_fts` ვირტუალური ცხრილი)

`022_add_memory_fts5.sql` ქმნის FTS5 ვირტუალურ ცხრილს `content`-ისა და
`key`-ისთვის. `023_fix_memory_fts_uuid.sql` ასწორებს რეალურ პირობებში აღმოჩენილ
შეცდომას, რომლის გამოც UUID პირველადი გასაღები ვერ უერთდებოდა FTS5-ის მთელრიცხვიან
rowid-ს — მიგრაცია ამატებს `memory_id` სვეტს, ხელახლა ქმნის FTS ცხრილს და აკავშირებს
ტრიგერებს (`memory_fts_ai`, `memory_fts_ad`, `memory_fts_au`), რომლებიც FTS-ს
INSERT, DELETE და UPDATE ოპერაციებისას სინქრონიზებულად ინარჩუნებენ.

გამოიყენება `retrieval.ts`-ის მიერ `semantic` და `hybrid` სტრატეგიებისთვის
(იხილეთ ქვემოთ). მოძიების კოდი ამოწმებს `hasTable("memory_fts")`-ით და გადადის
ქრონოლოგიურ დალაგებაზე, თუ FTS ცხრილი არ არსებობს ან FTS მოთხოვნა შეცდომას გამოიწვევს.

### არასავალდებულო: Qdrant (ვექტორული საცავის მე-2 დონე)

`src/lib/memory/qdrant.ts` ახორციელებს Qdrant-ის არასავალდებულო ინტეგრაციას,
როგორც მე-2 დონის ვექტორულ საცავს. მოძიება Qdrant-ზე მხოლოდ მაშინ გადამისამართდება,
როდესაც ძრავის სელექტორი `memoryVectorStore === "qdrant"`-ია — ნაგულისხმევი
`"auto"` (და `"sqlite-vec"`) Qdrant-ს **არასოდეს** ირჩევს. Engine ჩანართის
გადამრთველი ერთდროულად აყენებს **ორივე** პარამეტრს — `qdrantEnabled`-სა და
`memoryVectorStore`-ს: ჩართვა Qdrant-ს ძირითად საცავად აქცევს, ხოლო გამორთვა
`"auto"`-ზე აბრუნებს (#5597 — ამ შესწორებამდე ჩართვა უმოქმედო იყო, რადგან
ძრავის სელექტორში არაფერი იწერებოდა). თუ Qdrant მიუწვდომელია ან არაფერს აბრუნებს,
მოძიება გადადის sqlite-vec → FTS5-ზე.

- `upsertSemanticMemoryPoint()` — აკონფიგურირებს `key + content`-ის embedding-ს მითითებული
  embedding-მოდელით, უზრუნველყოფს კოლექციის არსებობას (პირველი გამოყენებისას ქმნის კოსინუსური მანძილის
  ვექტორებს) და ამატებს ან განაახლებს წერტილს payload-ით `{memoryId,
apiKeyId, sessionId, key, content, metadata, createdAtUnix, expiresAtUnix}`.
- `searchSemanticMemory(query, topK, scope)` — აკონფიგურირებს მოთხოვნის embedding-ს და ეძებს
  კოლექციაში `kind = "omniroute_memory"` ფილტრით და, სურვილისამებრ,
  `apiKeyId` / `sessionId`-ით. ზღუდავს `topK`-ს `[1, 20]` დიაპაზონით.
- `deleteSemanticMemoryPoint(id)` — ერთი წერტილის წაშლა. მას
  `deleteMemory()` იძახებს SQLite-ის სტრიქონის წაშლის შემდეგ (D15).
- `cleanupSemanticMemoryPoints({retentionDays})` — მასობრივად შლის წერტილებს, რომელთა
  `expiresAtUnix` წარსულშია ან რომელთა `createdAtUnix` შენახვის ვადაზე
  ძველია. ჯერ ითვლის, რათა მართვის პანელმა რეალური რიცხვები აჩვენოს.
- `checkQdrantHealth()` — `GET /readyz` ხელმისაწვდომობის შემოწმება დაყოვნების გაზომვით.

და გასუფთავებას `/dashboard/memory`-ის **ძრავის ჩანართში** აჩვენებს. შესაბამისი

| `/api/settings/qdrant/embedding-models` | `GET`         | ხელმისაწვდომი embedding-მოდელების ჩამონათვალი |

**ქცევის შენიშვნები (რას უნდა ელოდოთ):**

- **ძრავის არჩევა** — ძრავის ჩანართში Qdrant-ის ჩართვა მას ძირითად
  საცავად აქცევს (აყენებს `memoryVectorStore="qdrant"`-ს); გამორთვა მნიშვნელობას `"auto"`-ზე აბრუნებს (#5597).
- **ძველი მონაცემების შევსება არ ხდება** — მასში იწერება მხოლოდ Qdrant-ის ჩართვის **შემდეგ** შექმნილი/განახლებული
  მეხსიერებები (ასინქრონული ორმაგი ჩაწერა, პასუხის ლოდინის გარეშე). მანამდე არსებული SQLite-ის მეხსიერებები **არ**
  მიგრირდება; „ხელახლა ინდექსირება ახლა“ მხოლოდ sqlite-vec ინდექსს აღადგენს და არა Qdrant-ს.
- **ვექტორის განზომილება ავტომატურად განისაზღვრება** პირველი გამოყენებისას რეალური embedding-იდან — შესავსები
  განზომილების ველი არ არსებობს. კოლექციის შექმნის შემდეგ embedding-მოდელის შეცვლა
  ავტომატურად **არ** მუშავდება: არსებული კოლექცია უცვლელი რჩება, განზომილების
  შეუსაბამო ჩაწერები/ძიებები შეცდომით სრულდება და sqlite-vec-ზე გადადის. embedding-მოდელის
  შესაცვლელად ხელახლა შექმენით კოლექცია (ახალი სახელით, ან წაშალეთ იგი Qdrant-ში).
- **მანძილის მეტრიკა** — ყოველთვის **კოსინუსურია** (კოლექციის შექმნისას მკაცრადაა გაწერილი;
  კონფიგურირებადი არ არის).
- **ავთენტიფიკაცია** — მხოლოდ API-გასაღები (იგზავნება `api-key` სათაურით; ავთენტიფიკაციის არმქონე
  ლოკალური Docker-ისთვის არასავალდებულოა). JWT/RBAC არ გამოიყენება.
- **კონფიგურაციის ველები** — ინტერფეისში ხელმისაწვდომია `host`, `port`, `collection`, `embeddingModel`,
  `apiKey`. `vectorSize` / `hnswEfConstruct` ხელმისაწვდომია მხოლოდ გარემოს ცვლადებით/DB-ით, ხოლო `vectorSize`
  კოლექციის შექმნისას არ გამოიყენება (განზომილება embedding-იდან მიიღება).

### ვექტორების კვანტიზაცია (int8 — სურვილისამებრ, ორივე backend-ში)

ორივე ვექტორული backend მხარს უჭერს **სურვილისამებრ int8 კვანტიზაციას**, რათა შენახული ვექტორების
მეხსიერების მოცულობა შემცირდეს (Float32-ზე დაახლოებით 4-ჯერ ნაკლები) მოძიების სიზუსტის მცირედი დანაკარგის ხარჯზე.
ნაგულისხმევად ეს ფუნქცია ორივეგან **გამორთულია** — ვექტორები სრულ სიზუსტეს ინარჩუნებს, თუ ფუნქცია აშკარად
არ ჩაირთო.

| Backend    | პარამეტრი                                  | ტიპი                           | ნაგულისხმევი | საიდან იკითხება                                             |
| ---------- | ------------------------------------------ | ------------------------------ | ------------ | ----------------------------------------------------------- |
| Qdrant     | `qdrantQuantization` (DB გასაღები)         | `"none" \| "int8" \| "binary"` | `"none"`     | `src/lib/memory/qdrant.ts::normalizeQdrantConfig()`         |
| sqlite-vec | `MEMORY_VEC_QUANTIZATION` (გარემოს ცვლადი) | `"none" \| "int8"`             | `"none"`     | `src/lib/memory/vectorStore.ts::requestedVecQuantization()` |

- **Qdrant** თითოეული ინსტანციისთვის კონფიგურირდება `qdrantQuantization` პარამეტრის
  გასაღებით (`PUT /api/settings/qdrant`-ში წარმოდგენილია, როგორც `quantization` ველი). როდესაც მნიშვნელობაა
  `"int8"`, `buildQuantizationConfig()` ითხოვს სკალარულ კვანტიზაციას
  (`always_ram`, კვანტილი `0.99`), ხოლო ძიებები რთავს `rescore: true`-ს, რათა
  სრული სიზუსტის ვექტორებმა int8 კანდიდატების ნაკრები დააზუსტოს.
- **sqlite-vec**-ის კვანტიზაცია ხელმისაწვდომია **მხოლოდ გარემოს ცვლადით** (და არა DB პარამეტრით): დააყენეთ
  `MEMORY_VEC_QUANTIZATION=int8`, რათა ლოკალური ვექტორები შეინახოს `int8[dim]`
  სვეტად `vec_quantize_int8(?, 'unit')`-ის მეშვეობით. არჩეული რეჟიმი ერთიანდება
  `embedding_signature`-ში (`:int8` სუფიქსი), ამიტომ რეჟიმების გადართვა იწვევს
  `vec_memories` ცხრილის სრულ ხელახალ ინდექსირებას — იგივე ზარმაცი შევსების მექანიზმით, რომელიც
  embedding-მოდელის შეცვლისას გამოიყენება.

## მეხსიერების ტიპები

`MemoryType` (`src/lib/memory/types.ts`):

| ტიპი         | გამოყენება                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| `factual`    | პრეფერენციები, მომხმარებლის სტაბილური ფაქტები, ქცევის ნიმუშები                                        |
| `episodic`   | კონკრეტულ მომენტთან დაკავშირებული გადაწყვეტილებები ("I chose Postgres")                               |
| `procedural` | სამუშაო პროცესი / ინსტრუქციული მეხსიერება (რეზერვირებული; ამჟამად ავტომატური ექსტრაქტორი არ არსებობს) |
| `semantic`   | რეზერვირებულია ვექტორული საცავის ჩანაწერებისთვის                                                      |

ხოლო მოქმედების არეალია `session`, `apiKey` ან `global`. `getMemorySettings()`-იდან
ნაგულისხმევი მოქმედების არეალია `apiKey`.

## ფაქტების ამოღება (`extraction.ts`)

ამოღება **რეგულარულ გამოსახულებებზეა დაფუძნებული** და არა LLM-ზე — ის პროცესშივე
ეშვება `setImmediate()`-ის გამოყენებით, ამიტომ პასუხის ნაკადს არასოდეს ბლოკავს:

- **პრეფერენციის შაბლონები** → `MemoryType.FACTUAL`
  (მაგ., `I prefer …`, `I really like …`, `my favorite is …`, `I hate …`)
- **გადაწყვეტილების შაბლონები** → `MemoryType.EPISODIC`
  (მაგ., `I'll use …`, `I chose …`, `I went with …`, `I'm going to adopt …`)
- **ქცევის შაბლონები** → `MemoryType.FACTUAL`
  (მაგ., `I usually …`, `I always …`, `I tend to …`)

თითოეული დამთხვევა სანიტიზდება (`trim`, ჰარეების შეკუმშვა, მაქსიმუმ 500 სიმბოლო),
პაკეტის ფარგლებში დუბლიკატები იშლება სტაბილური `factKey(category, content)`-ის
მეშვეობით და ინახება `createMemory()`-ით, მეტამონაცემებთან ერთად:
`{category, extractedAt, source: "llm_response"}`. შემავალი ტექსტი იზღუდება
64 KiB-მდე (`MAX_EXTRACTION_TEXT_LENGTH`) — თუ ის უფრო გრძელია, გამოიყენება ტექსტის
**ბოლო ნაწილი**, რათა ასისტენტის უახლესი შიგთავსი ყოველთვის დამუშავდეს.

`extractFactsFromText(text)` ექსპორტირებულია ტესტებისთვის და სტრუქტურირებულ
ფაქტებს მათი შენახვის გარეშე აბრუნებს.

## მოძიება (`retrieval.ts`)

`retrieveMemories(apiKeyId, config)` არის მთავარი შესასვლელი წერტილი. ის:

1. `MemoryConfigSchema`-ის მეშვეობით ახდენს კონფიგურაციის ნორმალიზებასა და ვალიდაციას.
2. დაუყოვნებლივ აბრუნებს `[]`-ს, როდესაც `enabled` არის false ან `maxTokens <= 0`.
3. ზღუდავს `maxTokens`-ს `[1, 8000]` დიაპაზონში.
4. ამოწმებს, არსებობს თუ არა თანამედროვე `memories` ცხრილი (ძველი `memory`
   ცხრილის ნაცვლად), რათა ძველმა მონაცემთა ბაზებმა მუშაობა გააგრძელონ.
5. ქმნის საბაზისო მოთხოვნას ვადის გასვლის შემოწმებით
   (`expires_at IS NULL OR datetime(expires_at) > datetime('now')`), არასავალდებულო
   სესიის მოქმედების არეალითა და არასავალდებულო `retentionDays`-ის ზღვარით.
6. სტრატეგიის მიხედვით იყოფა:
   - **`exact`** (ნაგულისხმევი): ქრონოლოგიური `ORDER BY created_at DESC LIMIT 100`.
   - **`semantic`**: თუ `config.query` და `memory_fts` არსებობს, ასრულებს
     `memory_fts MATCH ?` JOIN-ს და ალაგებს FTS რანგის მიხედვით; თუ FTS 0 სტრიქონს
     აბრუნებს, გადადის ქრონოლოგიურ დალაგებაზე.
   - **`hybrid`**: FTS შედეგებისა (უფრო მაღალი რელევანტურობა) და
     ქრონოლოგიური ნაკრების გაერთიანება, id-ის მიხედვით დუბლიკატების მოცილებით.
7. როდესაც მოთხოვნა მოწოდებულია, ითვლის საკვანძო სიტყვების რელევანტურობის ქულას
   (`getRelevanceScore`) `content`, `key` და `metadata` JSON ველებზე. ნულოვანი
   ქულის მქონე სტრიქონები იფილტრება.
8. ალაგებს ჯერ ქულის კლებადობით, შემდეგ კი `createdAt`-ის კლებადობით.
9. მიჰყვება რანჟირებულ სიას და იღებს ჩანაწერებს მანამ, სანამ მიმდინარე
   `estimateTokens(content)` (≈ `length / 4`) ბიუჯეტის ფარგლებში რჩება. თუ
   დამთხვევა არსებობს, ყოველთვის აბრუნებს სულ მცირე ერთ ჩანაწერს.

`estimateTokens` ექსპორტირებულია და გამოიყენება მოძიების, შეჯამებისა და MCP-ის
`omniroute_memory_search` ხელსაწყოს მიერ.

## ინექცია (`injection.ts`)

`injectMemory(request, memories, provider)`:

1. მეხსიერების ყველა შიგთავსს აერთიანებს ერთ `Memory context: …` სტრიქონად.
2. სტრატეგიას პროვაიდერის სახელის მიხედვით ირჩევს:
   - **სისტემური შეტყობინება** (ნაგულისხმევია OpenAI-ისთვის, Anthropic-ისთვის, Gemini-ისთვის, …) — არსებულ სისტემურ შეტყობინებებს წინ უმატებს
     `{role: "system", content: memoryText}`-ს, რათა მომხმარებლის სისტემურ მოთხოვნებს კვლავ უფრო მაღალი პრიორიტეტი ჰქონდეს.
   - **მომხმარებლის შეტყობინება** (სათადარიგო ვარიანტი) — `PROVIDERS_WITHOUT_SYSTEM_MESSAGE`-ში შემავალი პროვაიდერებისთვის: `o1`, `o1-mini`, `o1-preview`,
     `glm`, `glmt`, `glm-cn`, `zai`, `qianfan`. ისინი სისტემურ როლს უარყოფენ
     და სხვა შემთხვევაში 400 შეცდომას დააბრუნებდნენ (იხ. საკითხი #1701 GLM/Zhipu-სთვის).
3. მეხსიერებების რაოდენობას, სტრატეგიასა და მოდელს `memory.injection.injected`-ის ქვეშ აღრიცხავს ჟურნალში.

`providerSupportsSystemMessage(provider)` ექსპორტირებულია გამომძახებლებისთვის, რომლებსაც
საკუთარი მარშრუტიზაციის გადაწყვეტილებების მიღება სჭირდებათ. უცნობი პროვაიდერებისთვის, უსაფრთხოების მიზნით, ნაგულისხმევი მნიშვნელობაა `true`
(სისტემური როლი დაშვებულია).

## პარამეტრები (`settings.ts`)

მეხსიერების კონფიგურაცია **ინახება მონაცემთა ბაზის პარამეტრების ცხრილში** და არა გარემოს ცვლადებში.
`getMemorySettings()` მონაცემებს `getSettings()`-დან კითხულობს და შედეგს
პროცესის ფარგლებში აკეშირებს; ჩაწერის შემდეგ პარამეტრების PUT
მარშრუტი `invalidateMemorySettingsCache()`-ს იძახებს.

## შეჯამება (`summarization.ts`)

`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)` ახდენს ძველი
შიგთავსის შეკუმშვას, როდესაც გასაღების მეხსიერებების მიმდინარე ტოკენების საერთო რაოდენობა
ბიუჯეტს აჭარბებს. ის `created_at`-ის მიხედვით DESC თანმიმდევრობით გადაუყვება სტრიქონებს, ინარჩუნებს
იმ სტრიქონებს, რომლებიც ეტევა, ხოლო დანარჩენებისთვის `content`-ს ადგილზე ანაცვლებს
ორიგინალის პირველი სამი წინადადებით. `tokensSaved` არის ძველ და
ახალ შიგთავსზე `estimateTokens`-ის მნიშვნელობებს შორის სხვაობა.

ეს პროცედურა **ხელმისაწვდომია, მაგრამ ავტომატურად არ გამოიძახება** მიმდინარე
ჩატის კონვეიერში — თუ მუდმივი შეკუმშვა გჭირდებათ, გამოიძახეთ ის cron-იდან, ადმინისტრატორის მოქმედებიდან ან
`MemoryConfig.autoSummarize`-ის დამაკავშირებელი ლოგიკიდან. მონაცემთა
დაკარგვა შეუქცევადია: ორიგინალი ტექსტი გადაიწერება.

  `semantic` ან `hybrid`, ხელმისაწვდომობის შემთხვევაში გამოიყენება ვექტორული
  საცავი.

metadata?}` → წარმოადგენს `createMemory()`-ის გარსს. იღებს მხოლოდ 4 კანონიკურ ტიპს:

## მართვის პანელი (Memory Studio)

`src/app/(dashboard)/dashboard/memory/page.tsx` ახლა არის **3-ჩანართიანი სტუდია**:

### ჩანართი: მეხსიერებები

- კონცეფციის ბარათი (ჩამოსაკეცი განმარტება „როგორ მუშაობს“).
- რეალურ დროში განახლებადი სია, ძიება და გვერდებად დაყოფა (300 ms დაყოვნებით).
- ტიპის ფილტრი (`factual` / `episodic` / `procedural` / `semantic` / ყველა).
- მეხსიერების დამატების მოდალური ფანჯარა (გასაღები, შიგთავსი, ტიპი).
- ჩანაწერის ადგილზე რედაქტირება (ფანქრის ღილაკი → `PUT /api/memory/[id]`).
- თითოეული მწკრივის წაშლა (დადასტურების დიალოგით).
- მიმდინარე გვერდის JSON-ად ექსპორტი; JSON-ის იმპორტი ფაილის ამრჩევის მეშვეობით.
- სტატისტიკის ბარათები: `totalEntries`, `tokensUsed`, `hitRate`.
- ღილაკი „ძველების შეკუმშვა“ → `POST /api/memory/summarize` (ჯერ საცდელი გაშვება
  აჩვენებს კანდიდატების რაოდენობას, შემდეგ კი ითხოვს დადასტურებას).
- მწვანე/წითელი მდგომარეობის ინდიკატორი, რომელსაც მართავს `GET /api/memory/health`.

## Embedding პროვაიდერის არჩევა (v3.8.16+)

OmniRoute-ის მეხსიერების ძრავა მხარს უჭერს **embedding-ის ოთხ წყაროს** (`src/lib/memory/embedding/`). თითოეულს განსხვავებული კომპრომისები აქვს **დაყოვნების, ღირებულების, მოდელის ხარისხისა და გამართვის სირთულის** მხრივ.

### Embedding-ის წყაროები

| პროვაიდერი     | წყარო                                                  | დაყოვნება                                 | ღირებულება           | ხარისხი                              | გამართვა                                    |
| -------------- | ------------------------------------------------------ | ----------------------------------------- | -------------------- | ------------------------------------ | ------------------------------------------- |
| `transformers` | ლოკალური ONNX მოდელი (Xenova/all-MiniLM-L6-v2)         | ~50-150ms (CPU)                           | უფასო                | კარგი                                | მხოლოდ `npm install`                        |
| `static`       | წინასწარ გამოთვლილი ვექტორები (კეშირებული)             | <1ms                                      | უფასო                | N/A (დამოკიდებულია კეშში მოხვედრაზე) | არ საჭიროებს                                |
| `remote`       | OpenAI / Cohere / Voyage API                           | ~100-300ms                                | $0.02-0.10/1M ტოკენი | შესანიშნავი                          | API გასაღები                                |

### მონაცემთა ბაზისა და API-ის კონფიგურაცია

მეხსიერების embedding პარამეტრები კონფიგურირდება Settings API/UI-ის მეშვეობით და არა გარემოს ცვლადებით. პარამეტრების მონაცემთა ბაზის შესაბამისი გასაღებები Settings-ში (`normalizeMemorySettings` `src/lib/memory/settings.ts`-ში) არის:

- `memoryEmbeddingSource`: `"transformers"` (ლოკალური), `"remote"` (API-ზე დაფუძნებული, მაგ., OpenAI), `"static"` (გარე საცავი), ან `"auto"`
- `memoryEmbeddingProviderModel`: მოდელის იდენტიფიკატორი დისტანციური/სტატიკური წყაროებისთვის (მაგ., `"text-embedding-3-small"`)
- `memoryTransformersEnabled`: `true` | `false`
- `memoryStaticEnabled`: `true` | `false`
- `memoryVectorStore`: `"sqlite-vec"`, `"qdrant"`, ან `"auto"`

#### ლოკალური მოდელი (`transformers`)

ლოკალური მოდელების გასაშვებად შიდა დონეზე იყენებს transformers.js-ს:

```bash
# კოდში წაკითხული გარემოს ცვლადები (src/lib/memory/embedding/index.ts):
MEMORY_TRANSFORMERS_MODEL=Xenova/all-MiniLM-L6-v2  # HF მოდელის რეპოზიტორია
MEMORY_STATIC_MODEL=minishlab/potion-base-8M       # HF-ის სტატიკური potion მოდელი
MEMORY_STATIC_CACHE_DIR=<DATA_DIR>/embeddings      # კეშის დირექტორია
```

#### LRU Embedding კეში

კეში ნაგულისხმევად ყოველთვის ჩართულია და კონფიგურირდება გარემოს ცვლადებით:

```bash
MEMORY_EMBEDDING_CACHE_MAX=1000                    # კეშირებული ელემენტების მაქსიმალური რაოდენობა
MEMORY_EMBEDDING_CACHE_TTL_MS=300000               # TTL (5 წთ)
```

## ჰიბრიდული RRF-ის გამართვა (v3.8.16+)

**Reciprocal Rank Fusion (RRF)** ალგორითმი აერთიანებს FTS5-ის (საკვანძო სიტყვებზე დაფუძნებულ) და ვექტორულ (სემანტიკურ) შედეგებს. `k` პარამეტრი აკონტროლებს, რამდენად დიდი წონა ენიჭება დაბალი რანგის შედეგებს.

### ფორმულა

თითოეული კანდიდატი მეხსიერების ჩანაწერისთვის RRF ქულაა:

```
RRF(d) = Σ  1 / (k + rank_i(d))
```

სადაც:

- `k` არის მუდმივა (ნაგულისხმევად 60)
- `rank_i(d)` არის `d` დოკუმენტის რანგი i-ურ ძიების სისტემაში (FTS, ვექტორი)
- ჯამი გამოითვლება ყველა ძიების სისტემის მიხედვით

### როგორ მოქმედებს `k` შედეგებზე

| `k`-ის მნიშვნელობა        | ეფექტი                                                                                                | საუკეთესოა შემდეგისთვის                             |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `k=0`                     | რანგების წმინდა გაერთიანება (გამარტივების გარეშე)                                                     | თეორიული საბაზისო მაჩვენებელი                       |
| `k=10-30`                 | ძლიერ წონას ანიჭებს მოწინავე შედეგებს, დაბალი რანგი თითქმის არ მონაწილეობს                            | როდესაც პირველი 3 შედეგი, როგორც წესი, სწორია       |
| **`k=60`** (ნაგულისხმევი) | დაბალანსებული — პირველი 10 შედეგი მნიშვნელოვნად მონაწილეობს                                           | ზოგადი დანიშნულების ძიება                           |
| `k=100+`                  | უფრო ბრტყელი — დაბალი რანგის შედეგებსაც კი შეუძლიათ დომინირება, თუ ისინი რამდენიმე სისტემაში გვხვდება | როდესაც სისრულე > სიზუსტე კრიტიკულად მნიშვნელოვანია |

### `k`-ის პრაქტიკული გამართვა

```bash
# ნაგულისხმევი
MEMORY_RRF_K=60

# აგრესიული სიზუსტე (მცირე მეხსიერება, ცოტა დოკუმენტი)
MEMORY_RRF_K=20

# მაქსიმალური სისრულე (დიდი მეხსიერება, მრავალფეროვანი მოთხოვნები)
MEMORY_RRF_K=120
```

**მაგალითი `k=20`-ით:**

- FTS რანგი 1 → წვლილი `1/21 = 0.048`
- FTS რანგი 10 → წვლილი `1/30 = 0.033`
- ვექტორული რანგი 1 → წვლილი `0.048`
- გაერთიანებული მაქსიმუმი: `0.096`

**მაგალითი `k=60`-ით:**

- FTS რანგი 1 → წვლილი `1/61 = 0.016`
- FTS რანგი 10 → წვლილი `1/70 = 0.014`
- ვექტორული რანგი 1 → წვლილი `0.016`
- გაერთიანებული მაქსიმუმი: `0.033`

უფრო მაღალი `k`-ის შემთხვევაში, პირველ და მე-10 რანგებს შორის **ფარდობითი სხვაობა** უფრო მცირეა, ამიტომ ალგორითმი მეტად ეყრდნობა **ძიების სისტემებს შორის კონსენსუსს**, ვიდრე უმაღლესი რანგის სანდოობას.

### როდის უნდა შეცვალოთ `k`

| სიმპტომი                                               | სცადეთ                                                                    |
| ------------------------------------------------------ | ------------------------------------------------------------------------- |
| პირველი შედეგი ყოველთვის იმარჯვებს, მაგრამ არასწორია   | **შეამცირეთ** k (მაგ., 20) — უმაღლესი რანგის სანდოობა უფრო მნიშვნელოვანია |
| სწორი პასუხი პირველ 5-შია, მაგრამ არა პირველ ადგილზე   | **გაზარდეთ** k (მაგ., 100) — უფრო ბრტყელი შეფასება აჯილდოებს კონსენსუსს   |
| სისრულე მაღალია, მაგრამ სიზუსტე დაბალი                 | **შეამცირეთ** k — გაამკვეთრეთ რანჟირება                                   |
| სისრულე დაბალია (შესაბამისი დოკუმენტები გამოტოვებულია) | **გაზარდეთ** k — მიეცით შანსი დაბალი რანგის დოკუმენტებს                   |

### RRF-ის წონები

რანგების შებრუნებული გაერთიანება თანაბარ წონებს იყენებს სემანტიკური ვექტორული რანგისა და სრულტექსტური ძიების რანგისთვის:

```
RRF(d) = 1/(k + rank_vector) + 1/(k + rank_fts)
```

ინდივიდუალური წონების დასარეგულირებლად გარემოს ცვლადები არ არსებობს (`MEMORY_RRF_VECTOR_WEIGHT`/`MEMORY_RRF_FTS_WEIGHT` არ არსებობს).

## შეჯამების სტრატეგია (v3.8.16+)

`summarization.ts` მოდული (`src/lib/memory/summarization.ts`) ძველ მეხსიერებებს შეკუმშავს, რათა აქტიური ნაკრები მცირე ზომის დარჩეს, ინფორმაციის გახსენების შესაძლებლობის შენარჩუნებით.

### როდის ირთვება შეჯამება

| გამომწვევი                  | ზღვარი (ნაგულისხმევი) |
| --------------------------- | --------------------- |
| ხელით გაშვება API-ის გავლით | არ გამოიყენება        |

### რა შეჯამდება

`summarization.ts`-იდან ორი შესასვლელი წერტილია ექსპორტირებული:

- **`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)`** — სესიის
  მეხსიერებებს აერთიანებს ერთ შეჯამებულ ტექსტად, რომლის ზომაც ტოკენების ბიუჯეტითაა შეზღუდული.
- **`summarizeMemoriesOlderThan(apiKeyId, days, dryRun)`** — API-ის მიერ გამოყენებული,
  ასაკზე დაფუძნებული შეკუმშვა: ის ირჩევს `days`-ზე ძველ ყველა მეხსიერებას, მათგან ქმნის
  ერთ შეკუმშულ შემაჯამებელ მეხსიერებას და (როდესაც `dryRun` არის `false`) შლის
  ორიგინალებს. მიუთითეთ `dryRun: true`, რათა ცვლილებების გარეშე წინასწარ იხილოთ
  კანდიდატთა ნაკრები და ტოკენების ჯამური რაოდენობა.

ტეგების/გასაღებების მიხედვით დაჯგუფების ეტაპი ან თითოეული მეხსიერების „ძირითადი vs შეჯამებადი“ შეფასება არ არსებობს —
შერჩევა ეფუძნება მხოლოდ ასაკობრივ ზღვარს, ხოლო შეჯამების ტექსტი თითოეული კანდიდატისთვის
ტიპის პრეფიქსით წარმოდგენილი შეკუმშული ხაზია.

### შეჯამების გაშვება

შეჯამება **ხელით გასაშვები / არასავალდებულოა** — `autoSummarize` პარამეტრის


მის გამოსართავად უბრალოდ დატოვეთ `autoSummarize` ნაგულისხმევ მნიშვნელობაზე (`false`).

### შეჯამების ხარისხის გასაუმჯობესებელი რჩევები

## MemoryBackend პროვაიდერის შაბლონი

#### MemoryManager (`manager.ts`)

#### GenericMemoryBackend (`genericBackend.ts`)

ზოგადი HTTP კონექტორი, რომელიც ნებისმიერ REST API-ს MemoryBackend-ად ადაპტირებს. გამოსადეგია შემდეგისთვის:

- **Notion** — დაკავშირება Notion API-ის მეშვეობით
- **Obsidian** — დაკავშირება Obsidian Local REST API-ის მეშვეობით
- **მორგებული ბექენდები** — ნებისმიერი სერვისი, რომელიც RESTful მეხსიერების API-ს უზრუნველყოფს

**კონფიგურაცია:**

```typescript
interface GenericBackendConfig {
  baseUrl: string;           // ბეკენდის API-ის საბაზისო URL
  apiKey?: string;           // Bearer ტოკენი ავთენტიფიკაციისთვის
  headers?: Record<string, string>;  // მორგებული HTTP სათაურები
  timeout?: number;          // მოთხოვნის მოლოდინის დროის ამოწურვა (ნაგულისხმევი: 30000ms)
  backendType?: string;      // ჟურნალში აღრიცხვისთვის

  // ბოლო წერტილების ჩანაცვლებები (ნაგულისხმევად გამოიყენება REST კონვენციები)
  endpoints?: {
    search?: string;   // ნაგულისხმევი: "/memories/search"
    create?: string;   // ნაგულისხმევი: "/memories"
    list?: string;     // ნაგულისხმევი: "/memories"
    get?: string;      // ნაგულისხმევი: "/memories/{id}"
    update?: string;   // ნაგულისხმევი: "/memories/{id}"
    delete?: string;   // ნაგულისხმევი: "/memories/{id}"
    health?: string;   // ნაგულისხმევი: "/health"
  };

  // მოთხოვნის პარამეტრების სახელების შესაბამისობები
  queryParams?: {
    query?/apiKeyId?/limit?/offset?/strategy?/maxTokens?/type?/sessionId?/orderBy?/orderDir?/options?
  };

  // ბილიკის პარამეტრების სახელების შესაბამისობები
  pathParams?: {
    id?/memoryId?
  };
}
```

**ცნობილი ბეკენდები** წინასწარ არის კონფიგურირებული `KNOWN_BACKENDS`-ში:

```typescript
createKnownBackend("obsidian"); // → GenericMemoryBackend, მიმართული localhost:27123-ზე
createKnownBackend("notion"); // → GenericMemoryBackend, მიმართული api.notion.com/v1-ზე
```

#### ჩაშენებული ბეკენდები

##### SQLiteBackend (`sqliteBackend.ts`)

ნაგულისხმევი ძირითადი ბეკენდი. `src/lib/memory/store.ts`-ის გამოყენებით ახვევს არსებულ SQLite-ზე დაფუძნებულ მეხსიერების საცავს. ჩატვირთვისას ავტომატურად რეგისტრირდება.

```typescript
import { sqliteBackend } from "./sqliteBackend";
memoryManager.register(sqliteBackend);
```

##### ObsidianBackend (`obsidianBackend.ts`)

ახვევს არსებულ Obsidian ინტეგრაციას (`src/lib/memory/obsidianBackend.ts`). Obsidian Local REST API-ის მეშვეობით უკავშირდება Obsidian-ის საცავს.

### პარამეტრები

მეხსიერების ბეკენდის პარამეტრები ინახება აპის პარამეტრების ცხრილში და იმართება `src/lib/memory/settings.ts`-ის მეშვეობით:

| პარამეტრი               | გარემოს/კონფიგურაციის გასაღები | ნაგულისხმევი | აღწერა                                       |
| ----------------------- | ------------------------------ | ------------ | -------------------------------------------- |
| ძირითადი ბეკენდი        | `memoryPrimaryBackend`         | `"sqlite"`   | ძირითადი ბეკენდის ID                         |
| სარეზერვო ბეკენდები     | `memoryFallbackBackends`       | `[]`         | დალაგებული სარეზერვო ბეკენდების ID-ები       |
| ბეკენდის კონფიგურაციები | `memoryBackendConfigs`         | `{}`         | თითოეული ბეკენდის კონფიგურაციის ჩანაცვლებები |

პარამეტრები ნორმალიზდება `normalizeMemorySettings()`-ის მეშვეობით და კეშირდება `getMemorySettings()`-ში.

### ინიციალიზაციის ნაკადი

```
აპის საწყისი ჩატვირთვა
  → index.ts-ის იმპორტები (გვერდითი ეფექტი): არეგისტრირებს SQLiteBackend-ს
  → initMemoryBackends() გამოიძახება აპის სასიცოცხლო ციკლიდან:
      1. პარამეტრების ჩატვირთვა (getMemorySettings)
      2. ძირითადი + სარეზერვო ბეკენდების კონფიგურაცია
      3. ყველა ბეკენდის ინიციალიზაცია (მდგომარეობის შემოწმება)
      4. მზადაა მოთხოვნებისთვის
```

### ახალი ბეკენდის დამატება

1. **განახორციელეთ `MemoryBackend`** ინტერფეისი `src/lib/memory/<name>Backend.ts`-ში
2. **გაიტანეთ ექსპორტზე** `src/lib/memory/index.ts`-დან
3. **დაარეგისტრირეთ** ჩატვირთვისას `memoryManager.register(yourBackend)`-ით
4. **დააკონფიგურირეთ** პარამეტრების მეშვეობით: `memoryPrimaryBackend`-ის მნიშვნელობად მიუთითეთ თქვენი ბეკენდის ID
5. **გატესტეთ** `src/lib/memory/__tests__/generic-backend.test.ts`-ის ნიმუშად გამოყენებით

#### მაგალითი: Brain ბეკენდი

```typescript
import { createGenericMemoryBackend } from "./genericBackend";

const brainBackend = createGenericMemoryBackend("brain", "BK-Brain", {
  baseUrl: process.env.BRAIN_API_URL || "http://localhost:9099",
  apiKey: process.env.BRAIN_API_KEY,
  endpoints: {
    search: "/api/memory/search",
    create: "/api/memory",
    health: "/api/health",
  },
});

memoryManager.register(brainBackend);
```
