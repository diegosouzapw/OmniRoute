OmniRoute გთავაზობთ გაფართოებად Skills ფრეიმვორკს, რომელიც ენის მოდელებს (და ოპერატორებს) მრავალჯერადი გამოყენების შესაძლებლობების გაერთიანების საშუალებას აძლევს — ფაილური სისტემიდან წაკითხვითა და HTTP მოთხოვნებით დაწყებული, იზოლირებულ გარემოში კოდის შესრულებითა და შერჩეული მარკეტპლეისის უნარებით დასრულებული.

უნარი არის სამუშაოს ვერსირებული, სქემით განსაზღვრული ერთეული. OmniRoute-ს შეუძლია უნარების ინსტრუმენტების განსაზღვრებების სახით გამავალ მოთხოვნებში ჩასმა, მოდელიდან დაბრუნებული ინსტრუმენტის გამოძახებების გადაჭერა, შესაბამისი დამმუშავებლის გაშვება და შედეგის მოდელისთვის დაბრუნება, რათა საუბარი გაგრძელდეს. მოდელი არასდროს ხედავს იმპლემენტაციას — მხოლოდ ინსტრუმენტის ინტერფეისს.

## Agent Skills და Omni Skills

OmniRoute-ს აქვს უნარების ორი განსხვავებული, თუმცა ურთიერთშემავსებელი სისტემა:

| განზომილება        | **Omni Skills** (ეს დოკუმენტი)                                               | **Agent Skills**                                                                                    |
| :----------------- | :--------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| დანიშნულება        | LLM ინსტრუმენტების ჩასმა + იზოლირებულ გარემოში შესრულება                     | SKILL.md კატალოგი, რომლის აღმოჩენა და გამოყენება გარე აგენტებს შეუძლიათ                             |
| ჭეშმარიტების წყარო | `src/lib/skills/` + მარკეტპლეისი                                             | `src/lib/agentSkills/` + `skills/` დირექტორია                                                       |
| გაშვების რეჟიმი    | ჩაისმება გამავალ მოთხოვნებში და სრულდება ინსტრუმენტის გამოძახების მოვლენებზე | სტატიკური markdown კატალოგი + REST/MCP/A2A აღმოჩენის საბოლოო წერტილები                              |
| ვინ იყენებს        | თავად OmniRoute (კომბინირებული მარშრუტიზაცია, შემომავალი LLM გამოძახებები)   | გარე აგენტები, MCP კლიენტები, A2A ორკესტრატორები                                                    |
| რაოდენობა          | ცვალებადი (დამოკიდებულია მარკეტპლეისზე)                                      | კატალოგის 45 ჩანაწერი (23 API + 21 CLI + 1 კონფიგურაცია)                                            |
| ფორმატი            | `SkillDefinition` ინსტრუმენტის სქემით + დამმუშავებლით                        | `SKILL.md` frontmatter + markdown ტექსტი                                                            |
| აღმოჩენა           | `/api/skills/*` REST + `omniroute_skills_*` MCP ინსტრუმენტები                | `/api/agent-skills/*` REST + `omniroute_agent_skills_*` MCP ინსტრუმენტები + A2A `list-capabilities` |

**Omni Skills** არის შესრულების ძრავა — ისინი განსაზღვრავენ, რისი _გაკეთება შეუძლია_ OmniRoute-ს, როდესაც LLM ინსტრუმენტს იძახებს.

**Agent Skills** არის დოკუმენტაციის კატალოგი — ისინი გარე აგენტებს უხსნიან, _როგორ გამოიყენონ_ OmniRoute-ის REST API და CLI, სტრუქტურირებული SKILL.md ფაილების მეშვეობით, რომელთა პირდაპირ აგენტების მოთხოვნებში მიწოდებაც შეიძლება.

Agent Skills-ის კატალოგის, გენერატორის, MCP ინსტრუმენტებისა და A2A უნარის შესახებ იხილეთ [docs/frameworks/AGENT-SKILLS.md](./AGENT-SKILLS.md).

## კონცეფციები

### უნარების წყაროები

უნარების სამი წყარო ერთსა და იმავე რეესტრში თანაარსებობს:

1. **ჩაშენებული უნარები** (`src/lib/skills/builtins.ts`) — OmniRoute-თან ერთად ვრცელდება. მოიცავს გავრცელებულ შემთხვევებს:
   - `file_read`, `file_write` — თითოეული API გასაღებისთვის განკუთვნილი იზოლირებული სამუშაო სივრცე მისამართზე `<DATA_DIR>/skills/workspaces/<hashed-key>/`
   - `http_request` — გამავალი HTTP `safeOutboundFetch`-ის გავლით, `guard: "public-only"` პარამეტრით
   - `web_search` — ჩანაცვლებადი საძიებო პროვაიდერი კეშირებით (`executeWebSearch`)
   - `eval_code` — Docker-ის იზოლირებულ გარემოში `node` ან `python` კოდის შესრულება
   - `execute_command` — Docker-ის იზოლირებულ გარემოში shell ბრძანების შესრულება
   - `browser` — Playwright-ზე დაფუძნებული საწყისი სტრუქტურა, ნაგულისხმევად გამორთული (`builtin/browser.ts`)
2. **SkillsMP** (OmniRoute-ის მარკეტპლეისი) — მოიპოვება `https://skillsmp.com/api/v1/skills/search`-დან. Settings-ში მოითხოვს `skillsmpApiKey`-ს.
3. **SkillsSH** (`skills.sh` საზოგადოების კატალოგი) — მოიპოვება `https://skills.sh/api/search`-დან. ავთენტიფიკაცია საჭირო არ არის; SKILL.md-ის შიგთავსი ჩამოიტვირთება GitHub raw-დან.

ერთი „აქტიური პროვაიდერი“ განსაზღვრავს, რომელი კატალოგიდან დააინსტალირებს დაფა (`src/lib/skills/providerSettings.ts`). შეცვალეთ ის **Settings → Memory & Skills** განყოფილებაში. ნაგულისხმევი მნიშვნელობა: `skillsmp`.

### უნარის იდენტობა

მეხსიერებაში არსებულ რეესტრში უნარების გასაღებია `name@version` (`src/lib/skills/registry.ts`). ვერსია უნდა იყოს semver (`^\d+\.\d+\.\d+$`). `resolveVersion()`-ს ესმის `^`, `~`, `>`, `>=`, `<`, `<=`, `==` და ზუსტი დამთხვევის შეზღუდვები.

### უნარის რეჟიმი

თითოეულ უნარს აქვს გაშვების რეჟიმი, რომელიც განსაზღვრავს, როდის მოხდება მისი ჩასმა:

| რეჟიმი | ქცევა                                                                                                          |
| ------ | -------------------------------------------------------------------------------------------------------------- |
| `on`   | ყოველთვის ჩაისმება ინსტრუმენტის განსაზღვრების სახით                                                            |
| `off`  | არასდროს ჩაისმება და არასდროს შესრულდება                                                                       |
| `auto` | ფასდება შემომავალ მოთხოვნასთან მიმართებით; ჩაისმება მხოლოდ მაშინ, თუ ქულა ≥ `AUTO_MIN_SCORE` (ნაგულისხმევად 3) |

`auto` მარკეტპლეისიდან დაინსტალირებული უნარებისთვის ნაგულისხმევი მნიშვნელობაა. `enabled=true` და `mode="off"` ერთად ნიშნავს „რეგისტრირებული, მაგრამ არააქტიური“ — მოძველებული სვეტის მეშვეობით `enabled`-ის გადართვა ასევე ცვლის `mode`-ს, რათა კოდის ძველი გზები თანმიმდევრული დარჩეს (`src/app/api/skills/[id]/route.ts`).

### სტატუსი (შესრულებები)

უნარების შესრულებები აღირიცხება `skill_executions` ცხრილში შემდეგი სტატუსებით (`src/lib/skills/types.ts`):

```ts
enum SkillStatus {
  PENDING = "pending",
  RUNNING = "running",
  SUCCESS = "success",
  ERROR = "error",
  TIMEOUT = "timeout",
}
```

### რეესტრის კეში

`SkillRegistry` არის singleton 60-წამიანი TTL კეშით (`registry.ts:14`). `loadFromDatabase()` იდემპოტენტურია და `pendingLoad`-ის მეშვეობით პარალელური გამოძახებების დუბლირებას გამორიცხავს. ნებისმიერი ჩაწერა (`register`/`unregister`/`unregisterById`) კეშს აბათილებს. ვერსიების მოსაძებნად გამოიყენეთ `getSkillVersions(name)` და `resolveVersion(name, constraint)`.

### პროვაიდერის გათვალისწინებით ჩასმა

`injectSkills()` ფაილში `src/lib/skills/injection.ts` არის შესვლის წერტილი, რომელიც რეგისტრირებულ უნარებს პროვაიდერისთვის სპეციფიკურ ინსტრუმენტების განსაზღვრებებად გარდაქმნის:

- **OpenAI** — `{ type: "function", function: { name, description, parameters } }`
- **Anthropic** — `{ name, description, input_schema }`
- **Google (Gemini)** — `{ name, description, parameters }`

ინსტრუმენტის სახელი კოდირებულია როგორც `name@version`, რათა დამმუშავებელმა შეძლოს სწორი ვერსიის არჩევა, როდესაც მოდელი მას გამოიძახებს.

| ტეგებში პროვაიდერის მინიშნება ემთხვევა მოთხოვნის პროვაიდერს | +2 / −2         |

ინექცია უკეთდება საუკეთესო `AUTO_MAX_SKILLS = 5` უნარს, რომელთა `score >= AUTO_MIN_SCORE = 3`. თანაბარი შედეგები წყდება `installCount`-ის მიხედვით (კლებადობით), შემდეგ კი სახელის ანბანური თანმიმდევრობით (`injection.ts:225-235`).

### ინსტრუმენტის გამოძახების ჩაჭერა

`handleToolCallExecution()` ფაილში `src/lib/skills/interception.ts` გამოიძახება ჩატის დამმუშავებლის მიერ მას შემდეგ, რაც ზედა დონის პროვაიდერი დააბრუნებს ინსტრუმენტის გამოძახვის შემცველ პასუხს:

1. `extractToolCalls()` კითხულობს პროვაიდერისთვის სპეციფიკურ ფორმატებს (OpenAI-ის `tool_calls` / Responses-ის `function_call`, Anthropic-ის `tool_use`, Gemini-ის `functionCalls`).
2. თავდაპირველად მუშავდება ჩაშენებული ინსტრუმენტების ფსევდონიმები (მაგ., `omniroute_web_search` → `web_search`). ჩაშენებული დამმუშავებლები სრულდება უშუალოდ მიმდინარე პროცესში.
3. ყველა დანარჩენი გამოძახება გადამისამართდება `skillExecutor.execute(name@version, args, { apiKeyId, sessionId })`-ის გავლით.
4. შედეგები პასუხში შესაბამის ადგილას ჩაისმება — `tool_results`, `function_call_output` ელემენტების ან, საჭიროებისამებრ, Anthropic-ის `tool_result` ბლოკების სახით.

შესრულების კონტექსტში `customSkillExecutionEnabled` შეიძლება დაყენდეს `false`-ზე, რათა დაშვებული იყოს მხოლოდ ჩაშენებული ჩაჭერა (გამოიყენება მოთხოვნის იმ მარშრუტებში, რომლებიც მომხმარებლის მიერ განსაზღვრულ დამმუშავებლებს აშკარად თიშავს).

## Docker-ის ქვიშის ყუთი

არაჩაშენებული კოდის გზები (`eval_code`, `execute_command`) Docker-ის შიგნით სრულდება `SandboxRunner`-ის მეშვეობით (`src/lib/skills/sandbox.ts`). თითოეული კონტეინერი გაეშვება შემდეგი პარამეტრებით:

```
--rm --network none|bridge --cap-drop ALL
--security-opt no-new-privileges --pids-limit 100
--cpus <cpuLimit/1000> --memory <memoryLimit>m
--tmpfs /tmp:rw,noexec,nosuid,size=64m
--tmpfs /workspace:rw,noexec,nosuid,size=64m
--read-only (როდესაც readOnly=true)
```

ნაგულისხმევი მნიშვნელობები (`SandboxRunner.DEFAULT_CONFIG`):

| ველი             | ნაგულისხმევი    | შენიშვნები                                                   |
| ---------------- | --------------- | ------------------------------------------------------------ |
| `cpuLimit`       | 100 (= 0.1 CPU) | `--cpus`-ისთვის გადაცემამდე იყოფა 1000-ზე                    |
| `memoryLimit`    | 256 MB          | მკაცრი ლიმიტი                                                |
| `timeout`        | 30000 ms        | რბილი შეწყვეტა `SIGTERM`-ის + `docker kill`-ის მეშვეობით     |
| `networkEnabled` | `false`         | გარდაიქმნება `--network none`-ად                             |
| `readOnly`       | `true`          | Root FS მხოლოდ წასაკითხია; `/tmp` და `/workspace` არის tmpfs |

`SandboxRunner.kill(id)` და `killAll()` ხელმისაწვდომია მუშაობის დასასრულებლად; გაშვებული კონტეინერები აღირიცხება `runningContainers: Map<string, ChildProcess>`-ში.

### ქვიშის ყუთის გარემოს ცვლადები

კონფიგურირდება `process.env`-ის მეშვეობით `src/lib/skills/builtins.ts`-ში:

| გარემოს ცვლადი                    | ნაგულისხმევი     | დანიშნულება                                                                                             |
| --------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------- |
| `SKILLS_MAX_FILE_BYTES`           | `1048576` (1 MB) | ლიმიტი `file_read`-ისა და `file_write`-ისთვის                                                           |
| `SKILLS_MAX_HTTP_RESPONSE_BYTES`  | `256000`         | ლიმიტი `http_request`-ის პასუხის სხეულისთვის                                                            |
| `SKILLS_MAX_SANDBOX_OUTPUT_CHARS` | `100000`         | გამომძახებლისთვის დაბრუნებული stdout/stderr-ის ლიმიტი                                                   |
| `SKILLS_SANDBOX_TIMEOUT_MS`       | `10000`          | ქვიშის ყუთში შესრულებული ბრძანებების ნაგულისხმევი მოლოდინის ვადა; მაქსიმუმ 60 s                         |
| `SKILLS_SANDBOX_NETWORK_ENABLED`  | `false`          | გამავალი ტრაფიკის მთავარი ჩამკეტი. თითოეული გამოძახებისთვის თანხმობით დასაშვებად მიუთითეთ `1` ან `true` |
| `SKILLS_ALLOWED_SANDBOX_IMAGES`   | (იხილეთ ქვემოთ)  | Docker-ის დაშვებული იმიჯების მძიმით გამოყოფილი სია                                                      |

ნაგულისხმევად დაშვებული იმიჯებია: `alpine:3.20`, `node:22-alpine`, `python:3.12-alpine`. `SKILLS_ALLOWED_SANDBOX_IMAGES`-ის მეშვეობით დამატებული ნებისმიერი იმიჯი ნაგულისხმევ სიასთან გაერთიანდება; უცნობ იმიჯებს `normalizeImage()` უარყოფს.

> შენიშვნა: ცალკე `SKILLS_EXECUTION_TIMEOUT_MS` გარემოს ცვლადი არ არსებობს. ქვიშის ყუთის გარეთ დამმუშავებლის მოლოდინის ვადა `SkillExecutor`-ში (`executor.ts:13`) მყარად არის დაყენებული 30 s-ზე, თუმცა შესრულების დროს მისი შეცვლა შესაძლებელია `skillExecutor.setTimeout(ms)`-ის მეშვეობით.

### სამუშაო სივრცის იზოლაცია

`file_read` და `file_write` თითოეულ გზას გარდაქმნის API-გასაღებზე მიბმული სამუშაო სივრცის მიმართ, რომელიც მდებარეობს მისამართზე `<DATA_DIR>/skills/workspaces/<sha256(apiKeyId).slice(0,24)>/`. გზის საზღვრებს გარეთ გადასვლა (`..`) და აკრძალული სეგმენტები (`.env`, `.git`, `.ssh`, `.omniroute`, `.codex`, `secrets`) დისკზე ნებისმიერი I/O ოპერაციის შესრულებამდე უარყოფილია.

### HTTP-ის გაძლიერებული დაცვა

`http_request` (`builtins.ts:257`):

- მეთოდების დაშვებული სია: `GET, HEAD, POST, PUT, PATCH, DELETE`
- დაბლოკილი გამავალი სათაურები: `host, connection, content-length, cookie, set-cookie, authorization, proxy-authorization`
- გადამისამართებები გამორთულია (`allowRedirect: false`)
- მარშრუტიზაცია ხორციელდება `safeOutboundFetch`-ის მეშვეობით, `guard: "public-only"` პარამეტრით (კერძო/უკუმარყუჟის დიაპაზონები დაბლოკილია)
- პასუხი იჭრება `SKILLS_MAX_HTTP_RESPONSE_BYTES`-ზე; კლიენტი იღებს `truncated: true`-ს

## REST API

ყველა საბოლოო წერტილი განთავსებულია `src/app/api/skills/`-ში. მართვის საბოლოო წერტილები (`/api/skills`, `/api/skills/[id]`, `/api/skills/install`) მოითხოვს **მართვის ავტორიზაციას** `requireManagementAuth()`-ის მეშვეობით. მარკეტპლეისის/ინსტალაციის ნაკადები იყენებს შედარებით მსუბუქ `isAuthenticated()`-ს (სესია ან API გასაღები).

| საბოლოო წერტილი | მეთოდი | დანიშნულება |
| --------------------------------- | ------ | ------------------------------------------------------------------------ | --- | ------------------------ | -------- | ------------------ |
| `/api/skills` | GET | რეგისტრირებული უნარების სია. მხარდაჭერილია `?q=`, `?mode=on              | off | auto`, `?source=skillsmp | skillssh | local`, გვერდებად დაყოფა |
| `/api/skills/[id]` | PUT | `enabled`-ის ან `mode`-ის განახლება |
| `/api/skills/[id]` | DELETE | რეგისტრაციის გაუქმება id-ის მიხედვით |
| `/api/skills/install` | POST | მორგებული უნარის ინსტალაცია (დამმუშავებლის კოდი + სქემა) |
| `/api/skills/marketplace` | GET | SkillsMP კატალოგში ძიება (როდესაც `q` ცარიელია, აბრუნებს პოპულარულ ნაგულისხმევ ვარიანტებს) |
| `/api/skills/marketplace/install` | POST | SkillsMP უნარის ინსტალაცია (მოითხოვს აქტიურ პროვაიდერს = `skillsmp`) |
| `/api/skills/skillssh` | GET | skills.sh კატალოგში ძიება (`?q=&limit=`, მაქსიმუმ 100) |
| `/api/skills/skillssh/install` | POST | skills.sh უნარის ინსტალაცია (მოითხოვს აქტიურ პროვაიდერს = `skillssh`) |
| `/api/skills/executions` | GET | გვერდებად დაყოფილი შესრულების ისტორია (`?apiKeyId=`) |
| `/api/skills/executions` | POST | რეგისტრირებული უნარის ერთჯერადი შესრულება |

`POST /api/skills/executions` საბოლოო წერტილი აბრუნებს HTTP `503`-ს პასუხით `{ error: "Skills execution is disabled..." }`, როდესაც `settings.skillsEnabled === false` (`executor.ts:42-45`). ოპერატორებს შეუძლიათ მთავარი გადამრთველის შეცვლა **პარამეტრები → AI**-დან.

### მაგალითი: მორგებული უნარის ინსტალაცია

```bash
curl -X POST http://localhost:20128/api/skills/install \
  -H "Authorization: Bearer $OMNIROUTE_MGMT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "reverse-text",
    "version": "1.0.0",
    "description": "Reverses a string",
    "schema": {
      "input":  { "type": "object", "properties": { "text": { "type": "string" } }, "required": ["text"] },
      "output": { "type": "object", "properties": { "reversed": { "type": "string" } } }
    },
    "handlerCode": "echo-handler",
    "apiKeyId": "your-api-key-id"
  }'
```

`handlerCode` სტრიქონი არის **დამმუშავებლის სახელით მოძიება** — და არა შესრულებადი კოდი. შემსრულებელი მას ასახავს `skillExecutor.registerHandler(name, fn)`-ის მეშვეობით (`executor.ts:25`). მარკეტპლეისიდან ინსტალაციისას SKILL.md-ის ტექსტი ამ ველში ინახება, როგორც დოკუმენტაცია, ხოლო შესრულება მოდელის მიერ გენერირებული ხელსაწყოს გამოძახებების მეშვეობით მარშრუტდება. მომხმარებლის მიერ მიწოდებული ნებისმიერი საწყისი კოდი `eval`-ით არ სრულდება.

- **მთავარი გადამრთველი:** `settings.skillsEnabled = false` ბლოკავს ყველა შესრულებას და `/api/skills/executions`-ზე აბრუნებს HTTP `503`-ს. რეესტრი ჩატვირთვას განაგრძობს.

## შესრულების სასიცოცხლო ციკლი (v3.8.16+)

`SkillExecutor` (`src/lib/skills/executor.ts`) არის **singleton**, რომელიც მართავს უნარის ყოველ გამოძახებას. მისი სასიცოცხლო ციკლის გაგება კრიტიკულად მნიშვნელოვანია დროის ლიმიტების, განმეორებითი მცდელობებისა და შესრულების მდგომარეობის გამართვისთვის.

### 5-ეტაპიანი სასიცოცხლო ციკლი

```
   execute() გამოძახებულია
        │
        ▼
  ┌─────────────┐
  │  PENDING    │  ← რიგშია, ჯერ არ დაწყებულა (DB ჩანაწერი შეიქმნა)
  └──────┬──────┘
         │ დამმუშავებლის გაშვება
         ▼
  ┌─────────────┐
  │  RUNNING    │  ← დამმუშავებელი გამოძახებულია დროის ლიმიტით
  └──────┬──────┘
         │
    ┌────┴────┬──────────┬──────────┐
    │         │          │          │
    ▼         ▼          ▼          ▼
  SUCCESS   ERROR     TIMEOUT   (სხვა გზა არ არსებობს — შეწყვეტილია მშობელი პროცესის მიერ)
    │         │          │
    └────┬────┴──────────┘
         │
         ▼
   DB ჩანაწერი განახლებულია სტატუსით, შედეგითა და durationMs-ით
```

### ნაგულისხმევი კონფიგურაცია

| პარამეტრი    | ნაგულისხმევი მნიშვნელობა | კონფიგურირდება შემდეგის მეშვეობით    |
| ------------ | ------------------------ | ------------------------------------ |
| `timeout`    | `30000` (30 წმ)          | `skillExecutor.setTimeout(ms)`       |
| `maxRetries` | `3`                      | `skillExecutor.setMaxRetries(count)` |

> **მნიშვნელოვანია**: შემსრულებელი singleton-ია — `setTimeout()`-ის გამოძახება გლობალურად მოქმედებს ყველა მომდევნო გამოძახებაზე. ცალკეული უნარისთვის დროის ლიმიტები ამჟამად მხარდაჭერილი არ არის; თუ სხვადასხვა უნარისთვის განსხვავებული დროის ლიმიტები გჭირდებათ, გაუშვით ცალკეული პროცესები ან შექმენით შემსრულებლის fork.

### სტატუსის მნიშვნელობები

`src/lib/skills/types.ts`-დან:

```ts
enum SkillStatus {
  PENDING = "pending", // რიგშია, ჯერ არ დაწყებულა
  RUNNING = "running", // დამმუშავებელი გამოძახებულია
  SUCCESS = "success", // დამმუშავებელმა დააბრუნა მართებული შედეგი
  ERROR = "error", // დამმუშავებელმა გამონაკლისი წარმოშვა
  TIMEOUT = "timeout", // შემსრულებლის დროის ლიმიტს გადააჭარბა
}
```

> **შენიშვნა**: `TIMEOUT` სტატუსი enum-ში განსაზღვრულია, თუმცა შემსრულებლის მიმდინარე იმპლემენტაცია მას **DB-ში ფაქტობრივად არ წერს** — დროის ლიმიტის ამოწურვა აისახება როგორც `ERROR`, შეტყობინებით `"Skill execution timed out"`. სტატუსის ეს enum სამომავლო გამოყენებისთვისაა შენახული.

### შესრულებების შემოწმება

```ts
import { skillExecutor } from "omniroute/skills/executor";

// კონკრეტული შესრულების მიღება ID-ით
const exec = skillExecutor.getExecution("exec-uuid-123");
if (exec) {
  console.log(`${exec.skillName}: ${exec.status} in ${exec.durationMs}ms`);
}

// API გასაღებისთვის ბოლო შესრულებების ჩამონათვალის მიღება
const recent = skillExecutor.listExecutions("api-key-id", 50, 0);
for (const e of recent) {
  console.log(`${e.skillName} → ${e.status} (${e.durationMs}ms)`);
}

// შესრულებების საერთო რაოდენობის დათვლა
const total = skillExecutor.countExecutions("api-key-id");
```

### განმეორებითი მცდელობების ქცევა

`maxRetries` პარამეტრი ინახება, თუმცა ამჟამად შემსრულებლის `execute()` მეთოდი მას **არ იყენებს** — ის მხოლოდ ერთ მცდელობას ასრულებს. `maxRetries` მნიშვნელობა ხელმისაწვდომია სამომავლო იმპლემენტაციისთვის და იმ hook-ებისთვის, რომლებსაც მისი წაკითხვა სურთ.

ამჟამად განმეორებითი მცდელობები თავად უნარის დამმუშავებელში უნდა განხორციელდეს. ჩაშენებული უნარები რეგისტრირდება შემსრულებელში (მაგ., `registerBuiltinSkills(executor)`
/ `registerBrowserSkill(executor)` ფაილში `src/lib/skills/builtin/`); თქვენ მიერ რეგისტრირებულ ნებისმიერ დამმუშავებელს შეუძლია საკუთარი განმეორებითი მცდელობების ციკლის შეფუთვა:

```ts
// უნარის დამმუშავებლის შიგნით
async function handler(input, ctx) {
  const maxRetries = 3;
  let lastError: Error | null = null;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await fetchSomething(input);
    } catch (err) {
      lastError = err as Error;
      if (attempt < maxRetries) {
        await new Promise((r) => setTimeout(r, 1000 * attempt));
      }
    }
  }
  throw lastError;
}
```

## SkillMode დეტალურად

`SkillMode` enum (`src/lib/skills/types.ts`) განსაზღვრავს, **როდის და როგორ** ხდება უნარების გამოძახება:

```ts
enum SkillMode {
  AUTO = "auto", // LLM წყვეტს, როდის გამოიძახოს უნარი
  MANUAL = "manual", // გამოიძახება მხოლოდ მომხმარებლის ცალსახა მოთხოვნით
  HYBRID = "hybrid", // AUTO შეფასება + ხელით გადაფარვა
}
```

> **შენიშვნა**: კოდის ბაზაში განსაზღვრულია `SkillMode` (AUTO/MANUAL/HYBRID), ხოლო `Skill.mode` ველი სხვა ფორმას იყენებს (`"on" | "off" | "auto"`). ისინი ერთმანეთთან დაკავშირებულია, თუმცა იდენტური არ არის — `SkillMode` შემსრულებლის პოლიტიკისთვისაა განკუთვნილი, ხოლო `Skill.mode` — თითოეული უნარის ჩასართავად ან გამოსართავად.

### როდის გამოვიყენოთ თითოეული რეჟიმი

| რეჟიმი   | LLM-ის ქცევა                                                                                    | გამოყენების შემთხვევა                                             |
| -------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `AUTO`   | LLM-ს შეუძლია გამოიძახოს უნარი, როდესაც ამას საჭიროდ მიიჩნევს                                   | ზოგადი დანიშნულების უნარები (ფაილების წაკითხვა, HTTP მოთხოვნები)  |
| `MANUAL` | LLM-ს არ შეუძლია უნარის გამოძახება; მას მხოლოდ ცალსახა `executeSkill` API გამოძახება ააქტიურებს | სენსიტიური ოპერაციები (მონაცემთა ბაზაში ჩაწერა, გადახდები)        |
| `HYBRID` | LLM-ს შეუძლია უნარის შეთავაზება; მომხმარებელმა უნდა დაადასტუროს                                 | უნარები, რომლებსაც გვერდითი ეფექტები აქვს, თუმცა სახიფათო არ არის |

### AUTO შეფასება

როდესაც `AUTO` რეჟიმი აქტიურია, თითოეული კანდიდატი უნარი მოთხოვნის
კონტექსტთან მიმართებით ფასდება `scoreAutoSkill()` ფუნქციის მიერ
`src/lib/skills/injection.ts`-ში — ადიტიური, მთელი რიცხვებით ქულების მინიჭების
სისტემით (უნარის სახელის დამთხვევა, სახელის/ტეგის/აღწერის ტოკენების თანხვედრა,
ფონური მიზეზის მინიშნებები, პროვაიდერის მინიშნების ბონუსი/ჯარიმა). საუკეთესო
`AUTO_MAX_SKILLS = 5` უნარი, რომელთა `score >= AUTO_MIN_SCORE = 3`, ჩასმულია
გამოძახებად ხელსაწყოებად; თანაბარი ქულების შემთხვევაში უპირატესობა განისაზღვრება
ჯერ `installCount`-ით, შემდეგ კი სახელით. ქულების სრული ცხრილი იხილეთ ამ
დოკუმენტის წინა ნაწილში: [**ხელსაწყოს სქემის გენერირება → AUTO შეფასება**](#auto-scoring);
`0.6`-ის მსგავსი ათწილადი ზღვარი და `registry.ts`-ში შეფასება არ არსებობს.

## ჩაშენებული უნარების კატალოგი

OmniRoute-ს მოჰყვება `src/lib/skills/builtin/`-ში განთავსებული ჩაშენებული უნარების საგულდაგულოდ შერჩეული ნაკრები. ყველაზე გავრცელებული მათგანია:

### ბრაუზერის ავტომატიზაციის უნარი

ბრაუზერის უნარი (`src/lib/skills/builtin/browser.ts`) Playwright/Puppeteer-ის მეშვეობით უთავო ბრაუზერის ავტომატიზაციას უზრუნველყოფს. **ის რეალიზებულია, თუმცა უნარების ნაგულისხმევ კატალოგში არ შედის** — მის გამოსაყენებლად ბრაუზერის გაფართოების პლაგინი ცალკე დააინსტალირეთ.

```ts
// ჩართეთ თქვენს კონფიგურაციაში
const config: SkillConfig = {
  enabled: true,
  mode: SkillMode.MANUAL, // ყოველთვის მოითხოვეთ ცალსახა გამოძახება
  allowedSkills: ["browser"],
  timeout: 60000, // 60 წამი გვერდების ჩასატვირთად
  maxRetries: 1,
};
```

| კატეგორია       | უნარები                                       | რეჟიმი |
| --------------- | --------------------------------------------- | ------ |

| ძიება           | `web_search`                                  | AUTO   |
