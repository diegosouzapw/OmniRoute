> **მოკლედ**: `open-sse/` არის სტრიმინგის ძირითადი ძრავა, რომელიც OmniRoute-ში LLM-ის ყველა მოთხოვნას ამუშავებს. ის შეიცავს დაახლოებით 1,400 ფაილს, რომლებშიც რეალიზებულია მოთხოვნების დამუშავების კონვეიერი, შემსრულებლები, სერვისები, MCP სერვერი და ტრანსლაციის შრე. ეს სახელმძღვანელო განმარტავს, როგორ მუშაობს ეს ნაწილები ერთად.

**წყარო:** `open-sse/` (სამუშაო სივრცის პაკეტი, დაახლოებით 1,440 სატესტო არა `.ts` ფაილი)

## რატომ არის ეს ცალკე სამუშაო სივრცის პაკეტი?

`open-sse/` OmniRoute-ის მონორეპოში **დამოუკიდებელი სამუშაო სივრცეა** რამდენიმე მიზეზის გამო:

1. **ხელახლა გამოყენების შესაძლებლობა** — `open-sse` npm-ზე ქვეყნდება როგორც `@omniroute/open-sse`, ამიტომ სხვა პროექტებსაც შეუძლიათ მისი დამოუკიდებლად გამოყენება
2. **მკაფიო საზღვრები** — სტრიმინგის ძრავა გამოყოფილია OmniRoute-ის სპეციფიკური UI/DB შრისგან
3. **წარმადობა** — ძრავას არ აქვს Next.js-ზე დამოკიდებულებები, რაც CLI-ისა და უსერვერო გარემოებში უფრო სწრაფ ცივ გაშვებას უზრუნველყოფს
4. **ვერსიების მართვა** — `open-sse`-ს შეუძლია რელიზები საკუთარი გრაფიკით გამოუშვას

```json
// package.json
"workspaces": ["open-sse"]
```

### ეტაპი 1: მარშრუტიზაცია (services/combo.ts)

**შესვლის წერტილი**: `handleComboChat()` ფაილში `services/combo.ts`

მოთხოვნას აკავშირებს კონკრეტულ `(provider, model, account, credentials)` კორტეჟთან:

- მოძებნოს კომბინაცია ID-ის მიხედვით (ან შექმნას ვირტუალური კომბინაცია `auto/*` მოდელებისთვის)
- გამოიყენოს მარშრუტიზაციის სტრატეგია (პრიორიტეტული, შეწონილი, წრიული და სხვ.)
- გამორიცხოს გაუმართავი პროვაიდერები (წრედის ამომრთველი)
- შეარჩიოს შემდეგი გამოსადეგი სამიზნე

`auto/*` მოდელებისთვის ეს ეტაპი ასევე:

- უშვებს **16-ფაქტორიანი შეფასების** ალგორითმს (`services/autoCombo/`)
- ჯანმრთელობის მდგომარეობის, ღირებულების, დაყოვნებისა და სხვა ფაქტორების საფუძველზე ირჩევს `provider+model` წყვილს

### ეტაპი 2: ტრანსლაცია (translator/)

თუ საწყისი ფორმატი (მაგ., OpenAI) განსხვავდება სამიზნე ფორმატისგან (მაგ., Claude), მოთხოვნა **ტრანსლირდება**:

- სისტემური პრომპტი → სისტემური შეტყობინება
- ხელსაწყოების განსაზღვრებები → პროვაიდერისთვის სპეციფიკური ხელსაწყოების ფორმატი
- მსჯელობის/ფიქრის პარამეტრები → პროვაიდერისთვის სპეციფიკური ეკვივალენტები
- შეტყობინების როლების ნორმალიზება (`developer` → `system` არა-OpenAI პროვაიდერებისთვის)

`translator/index.ts` ხელმისაწვდომს ხდის:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### ეტაპი 3: შესრულება (executors/)

**შესვლის წერტილი**: `getExecutor(providerId).execute(request, options)`

ყველა პროვაიდერი `getExecutor()` ფაბრიკის სარეზერვო მექანიზმის მეშვეობით იყენებს `DefaultExecutor`-ს (`executors/default.ts`). შემსრულებელი:

- აწყობს ზედა დონის URL-ს (`buildUrl()`)
- ამატებს პროვაიდერისთვის სპეციფიკურ სათაურებს (`buildHeaders()`)
- გარდაქმნის მოთხოვნის სხეულს (`transformRequest()`)
- აგზავნის HTTP მოთხოვნას ხელახალი ცდისა და ექსპონენციალური დაყოვნების გამოყენებით
- საჭიროების შემთხვევაში ამუშავებს ავთენტიფიკაციის განახლებას (OAuth პროვაიდერები)

ყველა შემსრულებელი აფართოებს `BaseExecutor`-ს (`executors/base.ts`, კოდის 1170 სტრიქონი), რომელიც უზრუნველყოფს:

- ხელახალი ცდის საერთო ლოგიკას
- პროქსის ინტეგრაციას
- წრედის ამომრთველის ინტეგრაციას
- გამოყენების აღრიცხვის ჰუკებს

### ეტაპი 4: ნაკადი (utils/stream.ts)

სტრიმინგული პასუხებისთვის შემსრულებელი აბრუნებს **ReadableStream**-ს. დამმუშავებელი:

- ატარებს მას SSE გარდაქმნაში (`createSSETransformStreamWithLogger`)
- მკვდარი კავშირების აღმოსაჩენად იყენებს პერიოდულ საკონტროლო სიგნალებს
- კორექტულად ამუშავებს კლიენტის გათიშვას (`pipeWithDisconnect`)
- არასტრიმინგული კლიენტებისთვის გარდაქმნის SSE-ს → JSON-ად

არასტრიმინგული პასუხებისთვის შემსრულებელი აბრუნებს დამუშავებულ JSON ობიექტს, რომელიც უცვლელად გადაიცემა.

### ეტაპი 5: ჩაწერა (services/usage.ts)

პასუხის მიღების შემდეგ (წარმატებული ან წარუმატებელი), გამოყენების მონაცემები აღირიცხება:

- პასუხიდან მიღებული `prompt_tokens`, `completion_tokens`, `cached_tokens`
- ფასების მონაცემებზე დაყრდნობით გამოთვლილი `cost_usd`
- `latency_ms`, `status`, ხოლო წარუმატებლობის შემთხვევაში — `error_class`
- ინახება `usage_history` ცხრილში

  // 2. მოთხოვნის სხეულის ვალიდაცია

      await recordUsage(result);

ხელსაწყოები რეგისტრირდება ცალკეულ ფაილებად `open-sse/mcp-server/tools/`-ში, რომელთაგან თითოეული ექსპორტირებს სახელს, სქემას, დამმუშავებელსა და წვდომის სფეროს:

## ტრანსფორმერები

`open-sse/transformer/` ახორციელებს გარდაქმნას **Chat Completions**-ისა და **Responses API**-ის ფორმატებს შორის.

### რატომ არის საჭირო ცალკე ტრანსფორმერი?

Responses API არის OpenAI-ის ახალი ფორმატი **მდგომარეობის მქონე საუბრებით** (`previous_response_id`). როდესაც კლიენტი აგზავნის Responses მოთხოვნას, OmniRoute:

1. შიდა დონეზე გარდაქმნის Responses → Chat Completions
2. აგზავნის პროვაიდერთან (ნებისმიერ პროვაიდერთან, რომელსაც Chat Completions-ის მხარდაჭერა აქვს)
3. პასუხს კვლავ Responses ფორმატში გარდაქმნის
4. გარდაქმნილ პასუხს ნაკადის სახით გადასცემს კლიენტს

ტრანსფორმერი (`transformer/responsesTransformer.ts`) გვთავაზობს:

```ts
createResponsesApiTransformStream(): TransformStream
```

ის ამუშავებს:

- `response.output_item.added` მოვლენებს
- `response.output_text.delta` მოვლენებს
- `response.completed` მოვლენას
- ხელსაწყოს გამოძახებების ასახვას (`function_call` ↔ `tool_calls`)

## კონფიგურაცია

`open-sse/config/` შეიცავს კონფიგურაციის ფენას:

| ფაილი                         | დანიშნულება                                                  |
| ----------------------------- | ------------------------------------------------------------ |
| `providerRegistry.ts`         | ჩატის მოდელების რეესტრი 352 პროვაიდერის კატალოგის საფუძველზე |
| `providerModels.ts`           | მოდელების ფსევდონიმები, ფორმატების ასახვა                    |
| `constants.ts`                | მოლოდინის დროები, ლიმიტები, სტატუსის კოდები                  |
| `defaultThinkingSignature.ts` | Claude-ის ნაგულისხმევი აზროვნების ხელმოწერა                  |
| `modelStrip.ts` (სერვისებში)  | ველების პროვაიდერის მიხედვით მოცილება                        |

### პროვაიდერის რეესტრის სქემა

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

მოდულის ჩატვირთვისას Zod-ის ვალიდაცია უზრუნველყოფს, რომ პროვაიდერების ყველა კონფიგურაცია ვალიდურია.

## ახალი კომპონენტის დამატება

### ახალი სერვისის დამატება

1. შექმენით `open-sse/services/[serviceName].ts` მკაფიოდ განსაზღვრული პასუხისმგებლობით
2. დააექსპორტეთ მთავარი დამმუშავებელი ფუნქცია და ყველა საჭირო კონსტანტა
3. დაამატეთ მოდულური ტესტები `tests/unit/services/[serviceName].test.mjs`-ში
4. მოახდინეთ ინტეგრაცია მოთხოვნის დამუშავების კონვეიერში, `handlers/chatCore.ts`-ში (თუ მარშრუტიზაციას უკავშირდება)
5. განაახლეთ მარშრუტიზაციის ლოგიკა `combo.ts`-ში, თუ სერვისი სამიზნის არჩევაზე ახდენს გავლენას
6. დაადოკუმენტირეთ ამ ფაილში

### ახალი შემსრულებლის დამატება

1. შექმენით `open-sse/executors/[provider].ts`, რომელიც აფართოებს `BaseExecutor`-ს
2. დაარეგისტრირეთ `config/providerRegistry.ts`-ში
3. დაამატეთ `executors/index.ts` ფაბრიკაში
4. დაამატეთ შემსრულებლის მოდულური ტესტები
5. დაადოკუმენტირეთ `docs/architecture/ARCHITECTURE.md`-ში

### ახალი MCP ხელსაწყოს დამატება

1. შექმენით ან განაახლეთ `open-sse/mcp-server/tools/[category]Tools.ts`
2. განსაზღვრეთ Zod სქემა შეყვანის მონაცემებისთვის
3. დაარეგისტრირეთ ხელსაწყო `mcp-server/index.ts`-ში
4. დაამატეთ წვდომის ფარგლების მატრიცაში, `mcp-server/auth/`-ში
5. დაამატეთ მოდულური ტესტები
