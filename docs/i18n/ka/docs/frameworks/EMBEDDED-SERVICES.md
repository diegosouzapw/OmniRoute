API-გასაღებების მეშვეობით ხდება), ჩაშენებული სერვისები OmniRoute-ის იმავე კომპიუტერზე მუშაობენ და loopback-ის მეშვეობით ურთიერთობენ.

## 1. მიმოხილვა

### რატომ ჩაშენებული სერვისები?

| სერვისი         | npm პაკეტი                                    | ნაგულისხმევი პორტი | დანიშნულება                                                                                                                                                                                                                     |
| --------------- | --------------------------------------------- | :----------------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9Router**     | `9router`                                     |       20130        | AI-როუტერი, რომელიც OmniRoute-ს შეუძლია ქვეპროვაიდერად გამოიყენოს. მოდელები ხელმისაწვდომია ფორმატით `9router/{sub}/{model}`                                                                                                     |
| **CLIProxyAPI** | GitHub-ის რელიზის ბინარული ფაილი (`cliproxy`) |        8317        | ლოკალური პროქსი-ადაპტერი Anthropic CLI-ის ავთენტიფიკაციის ნაკადებისთვის. უზრუნველყოფს სარეზერვო მარშრუტიზაციას OAuth ტოკენების ვადის ამოწურვისას                                                                                |

| **Dario**       | `@askalf/dario`                               |        3456        | Claude-ის გამოწერის პროქსი — CLIProxyAPI-ის ალტერნატივა/სარეზერვო ვარიანტი Claude-Code-ის ფორმატის ტრაფიკისთვის; ჩასმული გასაღები ხდება `DARIO_ADMIN_TOKEN`, რომელიც მის `/admin/*` OAuth მართვის სიბრტყეზე წვდომას აკონტროლებს |

ექვსივე ერთსა და იმავე ზედამხედველობის მოდელს მიჰყვება:

- OmniRoute მათ აყენებს `DATA_DIR/services/{name}/`-ში (იზოლირებულად OmniRoute-ის საკუთარი `package.json`-ისგან)
- OmniRoute მათ შვილობილ პროცესებად უშვებს და მონიტორინგს უწევს
- OmniRoute შვილობილი პროცესის გარემოში დროებით API გასაღებს ამატებს და მას მუშაობის შეწყვეტის გარეშე ანაცვლებს (სადაც შესაძლებელია)
- მართვის ყველა მარშრუტი (`/api/services/*`) არის **მხოლოდ ლოკალური** — ხელმისაწვდომია მხოლოდ უკუმარყუჟის ინტერფეისიდან (მკაცრი წესი #17)

## 3. სასიცოცხლო ციკლის მდგომარეობათა ავტომატი

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
             ჯანმრთელობის შემოწმება │         ავარია / SIGTERM   │
                 წარმატებულია       │     (გასვლა 5 წმ-ში)       │
                               ┌────▼─────┐                      │
                               │ running  │──── ავარია ─────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

მდგომარეობები ინახება `version_manager` DB ცხრილში (`status` სვეტი) და აისახება
`ServiceSupervisor`-ის მეხსიერებაში არსებულ მდგომარეობაში. გაშვებული პროცესისთვის
მეხსიერებაში არსებული მდგომარეობა ავტორიტეტულია; DB მდგომარეობა ჩატვირთვისას
გამოყენებული მდგრადი სარეზერვო ვარიანტია.

### მდგომარეობათა გადასვლები

| საიდან          | მოვლენა                                  | სად                     |
| --------------- | ---------------------------------------- | ----------------------- |
| `not_installed` | `install()` წარმატებით სრულდება          | `stopped`               |
| `stopped`       | გამოძახებულია `start()`                  | `starting`              |
| `starting`      | ჯანმრთელობის შემოწმება აბრუნებს 200-ს    | `running`               |
| `starting`      | პროცესი სრულდება ჯანმრთელ მდგომარეობამდე | `error`                 |
| `running`       | გამოძახებულია `stop()`                   | `stopping` → `stopped`  |
| `running`       | პროცესი მოულოდნელად სრულდება (< 5 წმ)    | `error` (სწრაფი ავარია) |
| `running`       | პროცესი მოულოდნელად სრულდება (> 5 წმ)    | `error`                 |
| `error`         | გამოძახებულია `start()`                  | `starting`              |
| ნებისმიერი      | `stop()` მდგომარეობაში `stopping`        | ოპერაციის გარეშე        |

### ოპერაციის ბლოკირება

`ServiceSupervisor` სასიცოცხლო ციკლის ოპერაციებს ასინქრონული ოპერაციის ბლოკირების
(`withLock()`) მეშვეობით თანმიმდევრულად ასრულებს. ერთსა და იმავე ზედამხედველზე
`start()`-ის კონკურენტული გამოძახებები ზუსტად ერთ პროცესს ქმნის; მეორე გამომძახებელი
ელოდება და არსებულ სტატუსს აბრუნებს. ეს ხელს უშლის შეჯიბრების პირობებს, როდესაც,
მაგალითად, ავტომატური გაშვება და UI ღილაკი ერთდროულად აქტიურდება.

## 4. API ცნობარი

`/api/services/`-ის ქვეშ არსებული ყველა მარშრუტი არის **LOCAL_ONLY** (მხოლოდ loopback, მკაცრი წესი #17).
არა-loopback მოთხოვნები ავტორიზაციის ტოკენის მიუხედავად იღებენ `403 LOCAL_ONLY` პასუხს.

დააყენებს 9Router-ს npm-დან. ქმნის `DATA_DIR/services/9router/`-ს საკუთარი
`package.json`-ითა და `node_modules/`-ით. არ ეწინააღმდეგება OmniRoute-ის საკუთარ დამოკიდებულებებს.

**მოთხოვნის სხეული** (ყველა ველი არასავალდებულოა):

```json

```

| ველი      | ტიპი     | ნაგულისხმევი | აღწერა                                  |
| --------- | -------- | ------------ | --------------------------------------- |

**პასუხები:**

| სტატუსი | აღწერა                                                                  |
| ------- | ----------------------------------------------------------------------- |
| `200`   | `{ ok: true, installedVersion: "x.y.z", path: "..." }`                  |
| `400`   | მოთხოვნის არასწორი სხეული (Zod-ის ვალიდაციის შეცდომა)                   |
| `409`   | ინსტალაცია უკვე მიმდინარეობს (ბლოკირება დაკავებულია)                    |
| `500`   | npm-ის ინსტალაცია ვერ შესრულდა — გასაგები შეცდომისთვის იხილეთ `message` |

**შენიშვნები:** იყენებს `execFile('npm', [...])`-ს — shell-ისა და ინტერპოლაციის გარეშე (მკაცრი წესი #13).

### 4.2 CLIProxyAPI-ის საბოლოო წერტილები (10 მარშრუტი)

CLIProxyAPI-ს აქვს ისეთივე საბოლოო წერტილების სტრუქტურა, როგორიც 9Router-ს, თუმცა `rotate-key`-ის გარეშე და დამატებული
`accounts`, `provider-expose` და `auto-restart-adopted` მარშრუტებით. ახლა ის გაშვებისას იღებს
სპეციალურ data-plane API გასაღებს (`needsApiKey: true`

### 4.7 უკუ პროქსი (9Router-ის მართვის პანელის ჩაშენება)

მართვის პანელი 9Router-ის ვებინტერფეისს iframe-ში, შიდა უკუ
პროქსის მეშვეობით აჩენს შემდეგ მისამართზე:

```
GET|POST|... /dashboard/providers/services/9router/embed/[...path]
```

ეს პროქსი:

- მოთხოვნას გადაამისამართებს `http://127.0.0.1:{port}/{path}`-ზე (მხოლოდ loopback)
- შემომავალი მოთხოვნიდან შლის `cookie` და `authorization` სათაურებს (OmniRoute-ის სესიის მონაცემების გაჟონვის თავიდან ასაცილებლად)
- 9Router-ის ავთენტიფიკაციისთვის ამატებს `Authorization: Bearer {apiKey}`-ს
- პასუხიდან შლის `set-cookie`, `content-security-policy`, `x-frame-options`, `cross-origin-*` სათაურებს
- HTML პასუხებს გარდაქმნის `<base href>`-ის ჩასამატებლად და აბსოლუტური მისამართების ნორმალიზებისთვის (`/foo` → `/dashboard/.../embed/foo`)

ჩაშენებული მართვის პანელის WebSocket განახლებებს ცალკე პორტზე გაშვებული
თანმხლები სერვერი ამუშავებს (იხილეთ `src/lib/services/embedWsProxy.ts`).

**უსაფრთხოება:** ჩაშენების პროქსის მარშრუტები კლასიფიცირებულია `LOCAL_ONLY_API_PREFIXES`-ის
ქვეშ და მათზე წვდომა მხოლოდ loopback-იდან არის შესაძლებელი. თავდამსხმელი, რომელიც
Cloudflare/Ngrok გვირაბის მეშვეობით JWT-ს მოიპოვებს, ჩაშენებულ სერვისებში პროქსის
გავლით წვდომას ვერ მიიღებს.

## 5. უსაფრთხოება

### LOCAL_ONLY-ის აღსრულება (მკაცრი წესი #17)

ყველა მარშრუტი `/api/services/`-ისა და `/dashboard/providers/services/*/embed/`-ის ქვეშ
კლასიფიცირებულია როგორც LOCAL_ONLY ფაილში `src/server/authz/routeGuard.ts`. loopback-ის შემოწმება
უპირობოდ სრულდება ავტორიზაციის ნებისმიერ განშტოებამდე:

```
მოთხოვნა შემოდის
  → isLocalOnlyPath(path)?
      → არა-loopback → 403 LOCAL_ONLY (ყოველთვის, ავტორიზაციის შემოწმებამდე)
      → loopback     → ჩვეულებრივი ავტორიზაციის გაგრძელება
```

ეს ხელს უშლის გაჟონილი JWT-ის (მაგ., გვირაბის მეშვეობით) მიერ `npm install`-ის ან
პროცესის გაშვების ინიციირებას. დონეების სრული მატრიცისთვის იხილეთ
`docs/security/ROUTE_GUARD_TIERS.md`.

### API გასაღების ჩასმა

9Router-სა და Mux-ს საკუთარი HTTP საბოლოო წერტილებისთვის API გასაღები/bearer-ტოკენი სჭირდებათ.
OmniRoute:

1. ქმნის გასაღებს `crypto.randomBytes(32).toString("base64url")`-ის მეშვეობით,
   სერვისისთვის სპეციფიკური პრეფიქსით (`nr_` 9Router-ისთვის, `mx_` Mux-ისთვის).
2. შენახვისას შიფრავს მას AES-256-GCM-ის გამოყენებით (იგივე შიფრი გამოიყენება პროვაიდერის ავტორიზაციის მონაცემებისთვის).
3. გაშვებისას შიფრს ხსნის და გარემოს ცვლადის სახით გადასცემს —
   `NINEROUTER_API_KEY` 9Router-ისთვის, `MUX_SERVER_AUTH_TOKEN` Mux-ისთვის (არასდროს CLI
   დროშის სახით, ამიტომ ტოკენი არასდროს გამოჩნდება `ps`/პროცესების სიებში).
4. არცერთ HTTP პასუხში არასდროს აბრუნებს გასაღებს ღია ტექსტის სახით.

CLIProxyAPI იღებს მონაცემთა სიბრტყის სპეციალურ გასაღებს, რომელიც გაშვებისას გადაეცემა
(`needsApiKey: true` — გამოიყენება მოდელის ადაპტერთან სინქრონიზაციისთვის).

### SSRF-ისგან დაცვა

უკუმიმართულების HTTP პროქსი (`/dashboard/.../embed/[...path]`) მკაცრად არის გაწერილი ისე, რომ მოთხოვნები
გადაამისამართოს მხოლოდ `http://127.0.0.1:{port}`-ზე. ის არასდროს მიჰყვება გადამისამართებებს არა-loopback
დანიშნულების ადგილებისკენ. `ssrf-req-filter` ბიბლიოთეკა გამოიყენება ნებისმიერი ზედა დონის URL-ის უარსაყოფად, რომელიც
loopback დიაპაზონის მიღმა რეზოლვდება.

### shell-ის უსაფრთხოება (მკაცრი წესი #13)

`npm install` გამოიძახება `execFile('npm', ['install', pkg, '--prefix', dir])`-ის მეშვეობით —
არ გამოიყენება შაბლონური ლიტერალები, shell ან გარე გზების ინტერპოლაცია ბრძანების
სტრიქონში. შესრულების დროის მნიშვნელობები (პორტები, API გასაღებები) შვილობილი პროცესის `env` ობიექტის მეშვეობით გადაიცემა.

### შეცდომების სანიტიზაცია (მკაცრი წესი #12)

ყველა შეცდომის პასუხი `/api/services/*`-დან გადის `buildErrorBody()`-ს ან
`sanitizeErrorMessage()`-ს. დაუმუშავებელი `err.stack` და `err.message` გამომძახებელს
სიტყვასიტყვით არასდროს უბრუნდება.

## 6. ახალი ჩაშენებული სერვისის დამატება

მიჰყევით ამ 8 ნაბიჯს. ეტალონურ ნიმუშად წაიკითხეთ არსებული იმპლემენტაციები
`src/lib/services/installers/`-სა და `src/app/api/services/`-ში.

### ნაბიჯი 1 — ინსტალატორის შექმნა

შექმენით `src/lib/services/installers/{name}.ts` `ninerouter.ts`-ის მიხედვით:

```typescript
export const NAME_PACKAGE = "your-npm-package";
export const NAME_DEFAULT_PORT = 20132; // აირჩიეთ თავისუფალი პორტი

export async function install(version = "latest"): Promise<InstallResult> { ... }
export async function update(version = "latest"): Promise<InstallResult> { ... }
export async function uninstall(): Promise<void> { ... }

export async function getLatestVersion(): Promise<string | null> { ... }
```

გამოიყენეთ `runNpm(['install', NAME_PACKAGE, '--prefix', dir])` ფაილიდან `installers/utils.ts`
— არასდროს გამოიყენოთ `execSync` ან shell-ის ინტერპოლაცია.

### ნაბიჯი 2 — bootstrap-ში რეგისტრაცია

დაამატეთ `ServiceEntry` `SERVICES` მასივში, ფაილში `src/lib/services/bootstrap.ts`:

```typescript
{
  tool: "myservice",
  port: NAME_DEFAULT_PORT,
  healthPath: "/health",
  healthIntervalMs: 5_000,
  stopTimeoutMs: 15_000,
  logsBufferBytes: 5_242_880,
  needsApiKey: true, // false, თუ API გასაღები საჭირო არ არის
}
```

გააფართოეთ `buildSpawnArgsFactory()`, რათა დაამუშაოს `cfg.tool === "myservice"`.

#### ჩანაცვლებადი პროვაიდერის დანამატის კონტრაქტი (ფაზა 1, #7333)

`src/lib/services/providerPlugins/` წარმოგვიდგენს `ServiceProviderPlugin` კონტრაქტს, რომელიც
backend-ის `bootstrap.ts`-ის `ServiceEntry` ველებსა და `serviceBackends.ts`-ის
მანიფესტის შაბლონის ველებს ერთ ობიექტში აერთიანებს, ნაცვლად იმისა, რომ ერთი და იმავე backend-ის სტრუქტურა
ცალ-ცალკე იყოს აღწერილი ორ ერთმანეთთან დაუკავშირებელ ფაილში. ამ ტექსტის დაწერის დროისთვის **მიგრირებულია მხოლოდ `9router`** —
`bootstrap.ts` თავის `SERVICES[]` ჩანაწერს იღებს
`getServiceProviderPlugin("9router")`-დან (`src/lib/services/providerPlugins/registry.ts`)
და გაშვების შეცდომას აგენერირებს, თუ დანამატი ოდესმე არ აღმოჩნდება. `cliproxy`, `mux` და `bifrost`
უცვლელად რჩება მანამდე არსებულ ჩაშენებულ `SERVICES[]` ლიტერალებზე.

`open-sse/config/providerPluginManifest.ts`-საც დაემატა დამატებითი
`createServiceBackendManifestEntry(pluginId, template)` დამხმარე ფუნქცია, რომელიც სწორად ფორმირებულ
`ProviderPluginManifestEntry`-ს აგებს `SERVICE_BACKEND_MANIFEST_TEMPLATE` ჩანაწერიდან — ის
ჯერ **არ არის** დაკავშირებული მოთხოვნების არცერთ მოქმედ გზასთან (არც `generateProviderPluginManifestFromRegistry()`-თან
და არც `/v1/providers/[provider]/models`-თან); ეს შემდგომ სამუშაოდ რჩება მას შემდეგ, რაც კონტრაქტი
მეორე backend-ისთვისაც დამტკიცდება.

შემდგომ PR-ებზეა გადადებული და აღრიცხულია საკითხში #7333: `cliproxyapi`-ის მიგრაცია იმავე
რეესტრის გავლით, `mux`/`bifrost`-ის განზოგადება `ServiceBackendPluginId` გაერთიანებაში,
შემსრულებლის მარშრუტიზაციის სპეციალური დამუშავების (`open-sse/executors/index.ts`,
`open-sse/handlers/chatCore/executorProxy.ts`) დანამატის კონტრაქტში მოქცევა და
`createServiceBackendManifestEntry()`-ის მოქმედ მანიფესტის/მოდელების კოდის გზასთან დაკავშირება.

## 7. პრობლემების აღმოფხვრა

### სერვისი არ იწყება

**სიმპტომები:** გაშვების ღილაკი აბრუნებს 503-ს, მდგომარეობა რჩება `"error"` ან `"starting"`.

**შესამოწმებელი სია:**

1. შეამოწმეთ `GET /api/services/{name}/logs` (ან მართვის პანელში Logs პანელი). მოძებნეთ
   ისეთი სტრიქონები, როგორიცაა `Error: ENOENT`, `address already in use` ან `Cannot find module`.
2. გადაამოწმეთ, რომ `npm` PATH-შია: გაუშვით `which npm` იმავე მომხმარებლის ანგარიშიდან, რომლითაც OmniRoute მუშაობს.
3. გადაამოწმეთ, რომ სერვისი დაყენებულია: `GET /api/services/{name}/status`-ში შეამოწმეთ
   `installedVersion`. თუ მნიშვნელობაა `null`, ჯერ ინსტალაცია გაუშვით.
4. შეამოწმეთ, რომ `DATA_DIR/services/{name}/node_modules/` არსებობს და ცარიელი არ არის.
5. გასუფთავებული დასრულების მიზეზის სანახავად სტატუსის პასუხში შეამოწმეთ `lastError` ველი.

### ცივი გაშვება ნელია (> 10 წმ `running` მდგომარეობამდე)

**სიმპტომები:** მდგომარეობა დიდი ხნის განმავლობაში რჩება `"starting"`, სანამ გადავა `"running"` ან `"error"` მდგომარეობაში.

**განმარტება:** 9Router-ის ცივი გაშვება მოიცავს დამოკიდებულებების დიდი ხეების იმპორტს (DNS,
გვირაბისა და MITM-ის მოდულები). ჯანმრთელობის შემოწმების ნაგულისხმევი ინტერვალია 2 წმ, ხოლო
ზედამხედველის მიერ დროის ამოწურვის გამოცხადებამდე სრულდება 3 მცდელობა (თუმცა გამოკითხვა გრძელდება).

**გამოსწორება:** `healthIntervalMs` და `waitForHealthy`-ის დროის ლიმიტი
(`healthIntervalMs * 3`) კონფიგურირებადია `bootstrap.ts`-ში. სერვისებისთვის, რომელთა
გაშვებასაც მეტი დრო სჭირდება, გაზარდეთ `healthIntervalMs` 5000-მდე და `stopTimeoutMs` 30 000-მდე.

### პორტის კონფლიქტი (`EADDRINUSE`)

**სიმპტომები:** ჟურნალებში ნაჩვენებია `address already in use :::20130`.

**მიზეზები:**

- სხვა პროცესი უკვე იყენებს პორტს 20130.
- 9Router-ის წინა პროცესი სრულად არ გაჩერებულა (ზომბი PID).

**გამოსწორება:**

1. შეცვალეთ ნაგულისხმევი პორტი `.env`-ში `NINEROUTER_PORT` გარემოს ცვლადის მეშვეობით.
2. იპოვეთ და იძულებით შეწყვიტეთ კონფლიქტის გამომწვევი პროცესი: `lsof -ti :20130 | xargs kill -9`.
3. პორტის კონფიგურირება შესაძლებელია თითოეული სერვისისთვის `bootstrap.ts`-ში `port` ველის მეშვეობით.

**შენიშვნა:** 9Router ნაგულისხმევად იყენებს პორტს 20130, რათა თავიდან აიცილოს
OmniRoute-ის ნაგულისხმევ პორტთან 20128 კონფლიქტი.

---

### ინსტალაციისას წვდომა აკრძალულია (EACCES)

**სიმპტომები:** ინსტალაცია აბრუნებს 500-ს, ჟურნალებში ნაჩვენებია `EACCES` ან `permission denied`.

**მიზეზები:**

- OmniRoute-ის პროცესს `DATA_DIR`-ში ან მის მშობელ დირექტორიაში ჩაწერის უფლება არ აქვს.
- სისტემა გაშვებულია rootless Docker-ში და დაკავშირებულ ტომზე ჩაწერის წვდომა არ აქვს.

**გამოსწორება:**

1. შეამოწმეთ `DATA_DIR` (ნაგულისხმევად: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. დარწმუნდით, რომ დირექტორიის მფლობელია მომხმარებელი, რომლის სახელითაც OmniRoute-ის პროცესი მუშაობს: `chown -R $USER ~/.omniroute/`
3. Docker-ში დარწმუნდით, რომ ტომის მიერთების წერტილს კონტეინერის მომხმარებლისთვის სწორი ნებართვები აქვს.

---

### განახლება ვერ სრულდება (`npm install`-ის დროის ლიმიტი ან ქსელის შეცდომა)

**სიმპტომები:** განახლება აბრუნებს 500-ს `InstallError`-ით, ჟურნალებში ნაჩვენებია ქსელის დროის ლიმიტის ამოწურვა.

**შესამოწმებელი სია:**

1. დაადასტურეთ, რომ npm-ის რეესტრი ხელმისაწვდომია: `npm ping`.
2. შეამოწმეთ კორპორაციული პროქსი: `npm config get proxy`, `npm config get https-proxy`.
3. სცადეთ ხელით ინსტალაცია: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`.
4. თუ სისტემა იზოლირებულ ქსელშია, წინასწარ ჩამოტვირთეთ tarball და გამოიყენეთ `npm install /path/to/tarball.tgz`.

---

### გაშვებისთანავე სერვისი აჩვენებს `"error"` მდგომარეობას (სწრაფი ავარიული დასრულება)

**სიმპტომები:** მდგომარეობა 5 წამზე ნაკლებ დროში გადადის `"starting"`-დან `"error"`-ზე.
`lastError` აჩვენებს `"Fast crash (exited with code 1)"`.

**შესამოწმებელი სია:**

1. წაიკითხეთ ჟურნალის ბოლო ნაწილი სრულად: `GET /api/services/{name}/logs?tail=500`.
2. ხშირი მიზეზი: სერვისისთვის საჭირო გარემოს ცვლადები არ არის მითითებული.
3. 9Router-ისთვის: გადაამოწმეთ, რომ პროცესის შექმნისას გადაცემულ გარემოში მითითებულია `NINEROUTER_DISABLE_MITM=true` და
   `NINEROUTER_DISABLE_TUNNEL=true` (იხილეთ
   `installers/ninerouter.ts`-ში `resolveSpawnArgs`).

## 8. ხშირად დასმული კითხვები

**კითხვა: შემიძლია ჩაშენებული სერვისების endpoint-ები არა-loopback კლიენტებისთვის ხელმისაწვდომი გავხადო?**

არა. LOCAL_ONLY დონე მიზანმიმართულად არის განსაზღვრული (მკაცრი წესი #17). მარშრუტები, რომლებსაც
შეუძლიათ `npm install`-ის გამოძახება ან `node` პროცესების გაშვება, არ უნდა იყოს ხელმისაწვდომი
არა-loopback ტრაფიკისთვის, რადგან გვირაბის (Cloudflare, Ngrok, Tailscale) მეშვეობით გაჟონილი JWT
სხვაგვარად ნებისმიერი პროცესის გაშვების საშუალებას მისცემდა. `/api/services/`-ისთვის
გამონაკლისის დაშვება არ არსებობს — `/api/mcp/`-ისგან განსხვავებით, ის გამორიცხულია
manage-scope-ის გვერდის ავლის სიიდან. იხილეთ `docs/security/ROUTE_GUARD_TIERS.md`.

---

**კითხვა: ხელმისაწვდომი იქნება 9Router და CLIProxyAPI საწარმოო/cloud განთავსებებში?**

დიახ. ორივე სერვისი იმავე local-first მოდელს მიჰყვება, რომელსაც თავად OmniRoute. ისინი მუშაობენ
ერთსა და იმავე მანქანაზე და loopback-ის მეშვეობით ურთიერთობენ. აქ „საწარმოო“ ნიშნავს VPS-ს
ან ლოკალურ სერვერს, რომელზეც OmniRoute არის განთავსებული, და არა დისტანციურ cloud პროვაიდერს.

---

**კითხვა: როგორ მოვახდინო supervisor-ის გამართვა?**

1. თვალი ადევნეთ SSE ჟურნალის ნაკადს: `curl -N http://localhost:20128/api/services/9router/logs`.
2. შეამოწმეთ OmniRoute-ის pino გამომავალი სტრუქტურირებული ჟურნალები,
   `service:supervisor` namespace-ის მიხედვით გაფილტრული.
3. შეამოწმეთ DB ჩანაწერი: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`.
4. გამოიყენეთ `GET /api/services/9router/status`, რათა ერთი გამოძახებით იხილოთ მიმდინარე აქტიური მდგომარეობა, PID, ჯანმრთელობის სტატუსი
   და `lastError`.

---

**კითხვა: supervisor აჩვენებს `health: "degraded"` ან `health: "unknown"`, თუმცა მდგომარეობაა `"running"`. ეს პრობლემაა?**

`"degraded"` ნიშნავს, რომ ჯანმრთელობის შემოწმებამ არა-200 პასუხი დააბრუნა. `"unknown"` ნიშნავს, რომ
ჯერ არცერთი შემოწმება არ დასრულებულა (პირველ გამოკითხვასთან race condition). გაშვებისას ორივე
დროებითია. თუ `"running"` მდგომარეობაში გადასვლიდან `healthIntervalMs * 3` ms-ზე მეტი ხნის განმავლობაში
ჯანმრთელობის სტატუსი კვლავ `"degraded"` რჩება, ჩაშენებული სერვისი გაშვებულია, მაგრამ მისი HTTP API არ პასუხობს. შეამოწმეთ,
სწორია თუ არა პორტი სტატუსის პასუხში და ნამდვილად უსმენს თუ არა სერვისი ამ პორტს.

---

**კითხვა: შემიძლია 9Router API გასაღები სრული გადატვირთვის გარეშე შევცვალო?**

არა. API გასაღები 9Router-ს პროცესის გაშვებისას გარემოს ცვლადის მეშვეობით გადაეცემა.
გაშვებულ პროცესში გარემოს ცვლადების შეცვლა შეუძლებელია. `POST .../rotate-key`
ავტომატურად აჩერებს და ხელახლა უშვებს სერვისს ახალი გასაღების გამოსაყენებლად. გასაღების როტაცია
ძალაში შედის სერვისის `stopTimeoutMs`-ის (ნაგულისხმევად 15 s) და მისი გაშვების
დროის ჯამის განმავლობაში.

---

**კითხვა: რა არის ring buffer-ის ლიმიტი და რა ხდება მისი შევსებისას?**

თითოეულ სერვისს აქვს გამოყოფილი 5 MB ring buffer. როდესაც ბუფერი ივსება, ყველაზე ძველი
ჟურნალის სტრიქონები იშლება, რათა ახლებისთვის ადგილი გათავისუფლდეს. SSE `snapshot` მოვლენა აბრუნებს
`tail` ლიმიტის ფარგლებში მოქცეულ უახლეს სტრიქონებს. ჟურნალები დისკზე არ ინახება, თუ
DB ჩანაწერში `logsBufferPath` არ არის დაყენებული.
