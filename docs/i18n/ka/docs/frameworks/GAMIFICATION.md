> **ბოლო განახლება:** 2026-06-28 — v3.8.40

OmniRoute მოიცავს ლოკალურობაზე ორიენტირებულ გეიმიფიკაციის ფენას, რომელიც მომხმარებლებს
აჯილდოებს პლატფორმასთან ურთიერთქმედებისთვის — მოთხოვნების გაგზავნისთვის, პროვაიდერების
გადართვისთვის, კომბინაციების შექმნისთვის, ტოკენების გაზიარებისა და საზოგადოებაში
წვლილის შეტანისთვის. მთელი მდგომარეობა ინახება SQLite-ში; საზოგადოებრივ სერვერებთან
ფედერაცია არჩევითია და მონაცემების გაგზავნის პრინციპზეა დაფუძნებული.

სისტემა შექმნილია ისე, რომ **კრიტიკულ გზაზე ნულოვანი დაყოვნება** უზრუნველყოს — გეიმიფიკაციის
მოვლენები მოთხოვნების დამუშავების კონვეიერიდან „გაგზავნე და დაივიწყე“ პრინციპით იგზავნება
და LLM-ის პასუხს არასოდეს ბლოკავს.

## მიმოხილვა

### დანიშნულება

მომხმარებელთა ჩართულობისა და შენარჩუნების გაზრდა თვალსაჩინო პროგრესის (XP,
დონეები, სამკერდე ნიშნები), სოციალური მტკიცებულების (ლიდერბორდები) და ეკონომიკური
სტიმულების (ტოკენების გაზიარება, მოწვევის ჯილდოები) უზრუნველყოფით.

### დიზაინის პრინციპები

1. **ლოკალურობაზე ორიენტირებული** — მთელი მდგომარეობა ინახება SQLite-ში; გარე სერვისები საჭირო არ არის.
2. **არამბლოკირებადი** — მოვლენები „გაგზავნე და დაივიწყე“ პრინციპით მუშავდება; LLM-ის პასუხის გზა
   გეიმიფიკაციის ლოგიკით არასოდეს ყოვნდება.
3. **სერვერი ავტორიტეტულია** — XP გამოითვლება მხოლოდ სერვერის მხარეს; კლიენტებს
   ქულების ხელოვნურად გაზრდა არ შეუძლიათ.
4. **კონფიდენციალურობის პატივისცემა** — ლიდერბორდში მონაწილეობა არჩევითია; მომხმარებლებს შეუძლიათ
   საკუთარი პროფილის დამალვა.
5. **ფედერაციისთვის მზადყოფნა** — საზოგადოებრივ სერვერებს შეუძლიათ ქულების გაგზავნა ხელმოწერილი API-ის მეშვეობით;
   სინქრონიზაცია გადაწერით ხდება და არა დამატებით.

### დომენის მოდული: `src/lib/db/gamification.ts`

მიჰყვება OmniRoute-ის სტანდარტულ შაბლონს — ახდენს `getDbInstance()`-ის იმპორტს
`core.ts`-დან და ექსპორტზე გამოაქვს ტიპიზებული CRUD ფუნქციები. მარშრუტების დამმუშავებლებში დაუმუშავებელი SQL არ გამოიყენება.

ძირითადი ფუნქციები:

| ფუნქცია                    | აღწერა                                                         |

### მინიჭების პროცესი

```typescript
export async function awardXp(
  apiKeyId: string,
  action: XpAction,
  metadata?: Record<string, unknown>
): Promise<{ xp: number; level: number; title: string; levelUp: boolean }>;
```

1. XP-ის ოდენობის მისაღებად მოძებნეთ `XP_REWARDS[action]`.
2. გაატარეთ `checkRateLimit()`-ში (თაღლითობის საწინააღმდეგო დაცვა: თითოეულ გასაღებზე მაქსიმუმ 1000 XP/წთ).
3. გახსენით ტრანზაქცია:
   - წაიკითხეთ მიმდინარე `user_levels` სტრიქონი.
   - დაამატეთ XP; დონე ხელახლა გამოთვალეთ `levelFromXp(totalXp)`-ის მეშვეობით.
   - თუ დონე შეიცვალა, დააყენეთ `levelUp = true`.
   - განაახლეთ `user_levels` სტრიქონი.
   - ჩასვით ჩანაწერი `xp_audit_log`-ში.
4. დააბრუნეთ შედეგი. შეტყობინებებს გამომძახებელი ამუშავებს.

### დამხმარე ფუნქცია: `levelFromXp(totalXp)`

გაივლის 1..100 დონეებს და აჯამებს `xp_for_level(n)`-ს, სანამ ჯამური XP
`totalXp`-ს არ გადააჭარბებს. აბრუნებს უმაღლეს დონეს, რომლის ზღვარიც მიღწეულია.
მისი სირთულეა O(100) — ეს მისაღებია, რადგან დონეების მაქსიმუმი 100-ია.

### შეფასების პროცესი

```

  → evaluateBadges(apiKeyId, event)
    → getBadgeDefinitions()           # ყველა განსაზღვრება
    → getUserBadges(apiKeyId)         # უკვე მიღებული (გამოტოვება)
    → თითოეული მიუღებელი სამკერდე ნიშნისთვის:
```

შეფასება **მოვლენებზეა ორიენტირებული** — ის ყოველი გეიმიფიკაციის მოვლენის შემდეგ სრულდება, თუმცა

## სერიის ტრეკერი

**ფაილი:** `src/lib/gamification/streaks.ts`

### მონაცემთა მოდელი

სერიები ინახება `key_value` ცხრილში (საერთო დანიშნულების დამხმარე ცხრილი)
სახელთა სივრცით გამოყოფილი გასაღებებით:

| გასაღები                      | მნიშვნელობა                      | აღწერა                    |
| ----------------------------- | -------------------------------- | ------------------------- |
| `gamification:streak:{keyId}` | `{current},{longest},{lastDate}` | აქტიური სერიის მონაცემები |

### ლოგიკა

```typescript
export async function updateStreak(
  apiKeyId: string
): Promise<{ current: number; longest: number; milestone: boolean }>;
```

1. წაიკითხეთ სერიის ჩანაწერი `key_value`-დან.
2. გააანალიზეთ `{current}`, `{longest}`, `{lastDate}` (ISO თარიღის სტრიქონი).
3. თუ `lastDate === today` — ცვლილება არ არის (დღეს უკვე დათვლილია).
4. თუ `lastDate === yesterday` — გაზარდეთ `current`; საჭიროების შემთხვევაში განაახლეთ `longest`.
5. თუ `lastDate < yesterday` — ჩამოაყენეთ `current = 1` (სერია შეწყდა).
6. ჩაწერეთ განახლებული ჩანაწერი.
7. შეამოწმეთ ეტაპები: 7, 14, 30, 60, 90, 180, 365 დღე. ზღვრის გადალახვის შემთხვევაში დააყენეთ
   `milestone = true` (გამომძახებელი ანიჭებს XP-ს და ამოწმებს სამკერდე ნიშნებს).

### განსაკუთრებული შემთხვევები

- **დროის სარტყელი**: სერიები იყენებს UTC თარიღებს (`new Date().toISOString().slice(0, 10)`).
  ეს მიზანმიმართულია — ერთიანი კანონიკური დროის სარტყელი ხელს უშლის დროის
  სარტყლებს შორის გადართვით სისტემის ბოროტად გამოყენებას.
- **ახალი მომხმარებლები**: სერიის ჩანაწერი არ არსებობს; პირველი მოთხოვნა მას ქმნის
  მნიშვნელობებით `current=1, longest=1, lastDate=today`.
- **რამდენიმე მოთხოვნა დღეში**: სერიას ზრდის მხოლოდ UTC დღის პირველი მოთხოვნა.

## ტოკენების გაზიარება

**ფაილი:** `src/lib/gamification/sharing.ts`

### ორმაგი ჩანაწერის რეესტრი

ყოველი გადარიცხვა `token_ledger`-ში ორ სტრიქონს ქმნის:

| სტრიქონი | `from_key_id` | `to_key_id` | `amount` |
| -------- | ------------- | ----------- | -------- |
| დებეტი   | გამგზავნი     | მიმღები     | +amount  |
| კრედიტი  | მიმღები       | გამგზავნი   | -amount  |

მოიცადეთ — გამოყენებული შეთანხმება ასეთია:

| სტრიქონი | `from_key_id` | `to_key_id` | `amount` | მნიშვნელობა            |
| -------- | ------------- | ----------- | -------- | ---------------------- |
| გაგზავნა | გამგზავნი     | მიმღები     | +amount  | გამგზავნისგან გადინება |
| მიღება   | მიმღები       | გამგზავნი   | +amount  | მიმღებთან შემოდინება   |

ბალანსი გამოითვლება შემდეგნაირად:

```sql
SELECT
  COALESCE(SUM(CASE WHEN to_key_id = ? THEN amount ELSE 0 END), 0)
  - COALESCE(SUM(CASE WHEN from_key_id = ? THEN amount ELSE 0 END), 0)
  AS balance
FROM token_ledger
WHERE from_key_id = ? OR to_key_id = ?
```

### გადარიცხვის პროცესი

```typescript
export async function transferTokens(
  fromKeyId: string,
  toKeyId: string,
  amount: number,
  idempotencyKey: string
): Promise<{ success: boolean; balance: number }>;
```

1. **ვალიდაცია**: `amount > 0`, `fromKeyId !== toKeyId`.
2. **იდემპოტენტურობა**: შეამოწმეთ, უკვე არსებობს თუ არა `idempotency_key` რეესტრში.
   თუ არსებობს, დააბრუნეთ დაკეშილი შედეგი.
3. **ტრანზაქცია** (ერთი SQLite ტრანზაქცია):
   a. გამოთვალეთ გამგზავნის ბალანსი.
   b. თუ `balance < amount`, შეწყვიტეთ ოპერაცია (არასაკმარისი სახსრები).
   c. ჩასვით გაგზავნის სტრიქონი (`from=sender,`.

სიხშირის შეზღუდვები იყენებს მეხსიერებაში შენახულ მცოცავ ფანჯარას (იგივე მიდგომას, რომელსაც `RateLimitManager` იყენებს `open-sse/services/`-ში). პროცესის გადატვირთვის შემთხვევაში სისტემა გადადის SQLite-ზე დაფუძნებულ მრიცხველებზე.

### ანომალიების Z-ქულით გამოვლენა

თითოეული API გასაღებისთვის სისტემა ინარჩუნებს საათში გამომუშავებული XP-ის მოძრავ 7-დღიან ფანჯარას. XP-ის ყოველი მინიჭებისას:

1. გამოთვლის მომხმარებლის XP-ის მიმდინარე საათობრივ სიჩქარეს.
2. გამოთვლის პოპულაციის საშუალო მნიშვნელობასა და სტანდარტულ გადახრას.
3. გამოთვლის `z = (user_rate - mean) / stddev`.
4. თუ `z > 3.0` (3 სტანდარტული გადახრა), აღნიშნავს მას ანომალიად.

ანომალიები იწერება `xp_audit_log`-ში `action = 'anomaly_detected'` მნიშვნელობით და გამოჩნდება ადმინისტრატორის მართვის პანელზე.

### აუდიტის ჟურნალი

XP-ის ყოველი მინიჭება, გადარიცხვა, სამკერდე ნიშნის მოპოვება და ანომალიის გამოვლენა იწერება `xp_audit_log`-ში შემდეგი ველებით:

| ველი         | აღწერა                                        |
| ------------ | --------------------------------------------- |
| `api_key_id` | ვინ                                           |
| `action`     | რა მოხდა (xp_award, transfer, anomaly, …)     |
| `xp_awarded` | ოდენობა (0 არა-XP მოვლენებისთვის)             |
| `metadata`   | JSON კონტექსტით (მოქმედების ტიპი, სამიზნე, …) |
| `created_at` | როდის (ISO 8601)                              |

ადმინისტრატორებს აუდიტის სრული ჟურნალის გამოთხოვა შეუძლიათ `GET /api/gamification/anomalies`-ის მეშვეობით.

```typescript
// კლიენტისთვის პასუხის გაგზავნის შემდეგ:
setImmediate(() => {

    type: "request.completed",

    metadata: {
      provider: selectedProvider,
      model: selectedModel,
      comboId: resolvedCombo?.id,
      compressionUsed: compressionStats?.applied,
      skillUsed: skillExecution?.name,
    },
  }).catch(() => {
    // გაშვება და დავიწყება: ჩაიწეროს ჟურნალში, მაგრამ არასოდეს გადაეცეს კლიენტს
```

### არაბლოკირების გარანტია

`setImmediate` + `.catch(() => {})` შაბლონი უზრუნველყოფს:

1. გეიმიფიკაციის გაშვებამდე პასუხი სრულად იგზავნება.
2. გეიმიფიკაციის შეცდომები კლიენტამდე არასოდეს აღწევს.

- **სეზონური ღონისძიებები**: დროში შეზღუდული ბეჯების ნაკრებები და ლიდერბორდის სეზონები.

- **ლიდერბორდის API**: საჯარო API მესამე მხარის ინტეგრაციებისთვის.
