Devin, Jules) როგორც ხანგრძლივად გაშვებულ ამოცანებს. თითოეული აგენტი შეფუთულია ერთიანი ინტერფეისით, რათა

პროვაიდერისთვის სპეციფიკურ API-ებთან უშუალო მუშაობის გარეშე.

Cloud Agent-ის ამოცანა **არ არის** ჩვეულებრივი ჩატის დასრულება. ის არის მდგრადი, მრავალსაფეხურიანი
სამუშაო ერთეული, რომლის შესრულებასაც შეიძლება წუთებიდან საათებამდე დასჭირდეს, რომელსაც შეუძლია არტეფაქტის
სახით Pull Request-ის შექმნა და რომელიც მხარს უჭერს შემდგომ შეტყობინებებსა და (ზოგიერთ პროვაიდერთან) გეგმის დამტკიცების ეტაპებს.

უბრალო, მეხსიერებაში შენახულ `Record<string, CloudAgentBase>`-ს, რომელიც მოდულის ჩატვირთვისას ივსება.

## არქიტექტურა

```
კლიენტი (მართვის პანელი / CLI / API)
  → POST /api/v1/agents/tasks (საჭიროა მართვის ავტორიზაცია)
    → CreateCloudAgentTaskSchema-ით ვალიდაცია (Zod)
    → registry.getAgent(providerId)
    → getCloudAgentCredentials(providerId)
      └─ იღებს getProviderConnections({ provider, isActive: true })-დან
         (ჯერ apiKey, შემდეგ სათადარიგოდ accessToken)
    → agent.createTask({ prompt, source, options }, credentials)
      └─ HTTP POST ზედა დონის პროვაიდერის API-ში
      └─ აბრუნებს CloudAgentTask-ს შიდა id-ითა და externalId-ით
    → insertCloudAgentTask(...) cloud_agent_tasks-ში (SQLite)

პოლინგი (ზარმაცი სინქრონიზაცია წაკითხვისას):
  GET /api/v1/agents/tasks/[id]
    → getCloudAgentTaskById(id)
    → agent.getStatus(externalId, credentials)  // აახლებს სტატუსსა და აქტივობებს
    → updateCloudAgentTask(...) ახალი სტატუსით, შედეგითა და completed_at-ით
    → აბრუნებს სერიალიზებულ ამოცანას

ურთიერთქმედებები:
  POST /api/v1/agents/tasks/[id]  body: { action: "approve" | "message" | "cancel" }
    → agent.approvePlan(externalId, credentials)        "approve"-ისთვის
    → agent.sendMessage(externalId, message, credentials) "message"-ისთვის
    → სტატუსი იცვლება "cancelled"-ზე                       "cancel"-ისთვის (მხოლოდ ლოკალურად)
```

სინქრონიზაცია **ზარმაცია**: სტატუსი ზედა დონის წყაროდან ახლდება ყოველი `GET /tasks/[id]` მოთხოვნისას.
ფონური პოლერი არ არსებობს. მართვის პანელებმა, რომლებსაც ახალი მდგომარეობა სჭირდებათ, GET
endpoint გონივრული ინტერვალით უნდა გამოკითხონ.

## `CloudAgentBase` ინტერფეისი

წყარო: `src/lib/cloudAgent/baseAgent.ts`

```typescript
export interface AgentCredentials {
  apiKey: string;
  baseUrl?: string;
}

export interface CreateTaskParams {
  prompt: string;
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
}

export interface GetStatusResult {
  status: CloudAgentStatus;
  externalId?: string;
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
}

export abstract class CloudAgentBase {
  abstract readonly providerId: string;
  abstract readonly baseUrl: string;

  abstract createTask(p: CreateTaskParams, c: AgentCredentials): Promise<CloudAgentTask>;
  abstract getStatus(externalId: string, c: AgentCredentials): Promise<GetStatusResult>;
  abstract approvePlan(externalId: string, c: AgentCredentials): Promise<void>;
  abstract sendMessage(
    externalId: string,
    message: string,
    c: AgentCredentials
  ): Promise<CloudAgentActivity>;
  abstract listSources(
    c: AgentCredentials
  ): Promise<{ name: string; url: string; branch?: string }[]>;

  protected mapStatus(raw: string): CloudAgentStatus; // ევრისტიკული საწყისი სტრიქონი → ჩამონათვალი
  protected generateTaskId(): string; // `task_<ts>_<rand>`
  protected generateActivityId(): string; // `act_<ts>_<rand>`
}
```

`CodexCloudAgent.approvePlan` განზრახ წარმოქმნის გამონაკლისს — Codex Cloud გეგმას ავტომატურად ქმნის და დამტკიცების ეტაპი არ აქვს. `CodexCloudAgent.listSources` აბრუნებს `[]`-ს.

`CursorCloudAgent` Cursor-ის Background / Cloud Agents-ს მისი ოფიციალური REST API-ის (`api.cursor.com/v0`) მეშვეობით მართავს, **მომხმარებლის ან სერვისული ანგარიშის API გასაღებით** — ეს Cursor IDE-ის OAuth სესიის ხელახლა გამოყენების უფრო უსაფრთხო, უშუალოდ მწარმოებლის მიერ მხარდაჭერილი ალტერნატივაა (პროვაიდერი `cursor`, რომელსაც დაბლოკვის რისკის გაფრთხილება ახლავს). ის ჩვეულებრივი REST ადაპტერია (`@cursor/sdk`-ზე ნატიური დამოკიდებულების გარეშე). `approvePlan` წარმოქმნის გამონაკლისს (Cursor-ის აგენტები ავტონომიურად მუშაობენ); `listSources` ჩამოთვლის გასაღებისთვის ხელმისაწვდომ რეპოზიტორიებს. Cursor აბრუნებს ზედა რეგისტრში ჩაწერილ სტატუსის ჩამონათვალის მნიშვნელობებს (`CREATING`/`RUNNING`/`FINISHED`/`ERROR`), რომლებიც აშკარად აისახება საერთო `CloudAgentStatus`-ზე. `baseUrl`-ის ჩანაცვლება შესაძლებელია თითოეული ავტორიზაციის მონაცემისთვის, რათა API-ის ვერსია/გზა კოდის შეცვლის გარეშე გასწორდეს.

## დომენის ტიპები

წყარო: `src/lib/cloudAgent/types.ts`

```typescript
export const CLOUD_AGENT_STATUS = {
  QUEUED: "queued",
  RUNNING: "running",
  AWAITING_APPROVAL: "awaiting_approval",
  COMPLETED: "completed",
  FAILED: "failed",
  CANCELLED: "cancelled",
} as const;

export interface CloudAgentSource {
  repoName: string;
  repoUrl: string; // უნდა იყოს მოქმედი URL
  branch?: string;
}

export interface CloudAgentResult {
  prUrl?: string;
  prNumber?: number;
  commitMessage?: string;
  diffUrl?: string;
  summary?: string;
  duration?: number; // წამები, დადებითი მთელი რიცხვი
  cost?: number; // დადებითი ათწილადი რიცხვი
}

export interface CloudAgentActivity {
  id: string;
  type: "plan" | "command" | "code_change" | "message" | "error" | "completion";
  content: string;
  timestamp: string; // ISO 8601
  metadata?: Record<string, unknown>;
}

export interface CloudAgentTask {
  id: string; // შიდა `task_...` id
  providerId: "jules" | "devin" | "codex-cloud" | "cursor-cloud";
  externalId?: string; // საწყისი პროვაიდერის id
  status: CloudAgentStatus;
  prompt: string; // 1..10000 სიმბოლო
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
}
```

ვალიდაციის სქემები (`CreateCloudAgentTaskSchema`, `UpdateCloudAgentTaskSchema`) ტიპებთან ერთად ექსპორტირდება და მარშრუტების დამმუშავებლების მიერ გამოიყენება.

## მონაცემთა ბაზა

წყარო: `src/lib/cloudAgent/db.ts` — ცხრილი ზარმაცად იქმნება
`createCloudAgentTaskTable()`-ის მეშვეობით (ის ასევე გამოიძახება `src/lib/cloudAgent/index.ts`-დან
მოდულის იმპორტისას).

```sql
CREATE TABLE IF NOT EXISTS cloud_agent_tasks (
  id           TEXT PRIMARY KEY,
  provider_id  TEXT NOT NULL,
  external_id  TEXT,
  status       TEXT NOT NULL DEFAULT 'queued',
  prompt       TEXT NOT NULL,
  source       TEXT NOT NULL,             -- JSON
  options      TEXT DEFAULT '{}',         -- JSON
  result       TEXT,                       -- JSON
  activities   TEXT DEFAULT '[]',          -- JSON
  error        TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_provider ON cloud_agent_tasks(provider_id);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_status   ON cloud_agent_tasks(status);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_created  ON cloud_agent_tasks(created_at DESC);
```

SQL ინექციის თავიდან ასაცილებლად `updateCloudAgentTask` იყენებს **სვეტების თეთრ სიას**:
`status`, `prompt`, `source`, `options`, `result`, `activities`, `error`,
`completed_at`. ნაწილობრივ განახლებაში არსებული ნებისმიერი სხვა გასაღები უხმაუროდ გამოიტოვება.

## REST API — დავალების სასიცოცხლო ციკლი

**ავთენტიფიკაცია:** ყველა `/api/v1/agents/tasks*` endpoint მოითხოვს **მართვის ავთენტიფიკაციას**
(`requireCloudAgentManagementAuth` გარს აკრავს `requireManagementAuth`-ს
`src/lib/api/requireManagementAuth`-დან). ეს სავალდებულოა `588a0333` commit-ის შემდეგ
(_"fix(auth): require management auth for agent and cooldown APIs"_).

| მეთოდი  | გზა                           | დანიშნულება                                                       |
| ------- | ----------------------------- | ----------------------------------------------------------------- |
| OPTIONS | `/api/v1/agents/tasks`        | CORS-ის წინასწარი მოთხოვნა                                        |
| GET     | `/api/v1/agents/tasks`        | დავალებების სია (ფილტრი: `provider`, `status`, `limit≤500`)       |
| POST    | `/api/v1/agents/tasks`        | დავალების შექმნა (აგზავნის upstream-ში + ინახავს)                 |
| DELETE  | `/api/v1/agents/tasks?id=...` | დავალების წაშლა მოთხოვნის id-ით (**არ** აუქმებს upstream-ში)      |
| OPTIONS | `/api/v1/agents/tasks/[id]`   | CORS-ის წინასწარი მოთხოვნა                                        |
| GET     | `/api/v1/agents/tasks/[id]`   | დავალების წაკითხვა + სტატუსის ზარმაცი სინქრონიზაცია upstream-იდან |
| POST    | `/api/v1/agents/tasks/[id]`   | მოქმედება: `approve` / `message` / `cancel`                       |
| DELETE  | `/api/v1/agents/tasks/[id]`   | დავალების წაშლა გზაში მითითებული id-ით                            |

`cancel` ლოკალურ DB-ში `status`-ს `"cancelled"` მნიშვნელობაზე ცვლის, მაგრამ upstream
პროვაიდერს **არ** იძახებს — `CloudAgentBase`-ში შეწყვეტის RPC არ არსებობს. upstream-ში
ბილინგის შესაჩერებლად დაასრულეთ დავალება თავად პროვაიდერის კონსოლში.

## REST API — Cloud-პროვაიდერის დამაკავშირებელი ინფრასტრუქტურა

ეს დამხმარე endpoint-ები, რომლებიც მდებარეობს `src/app/api/cloud/`-ში, გამოიყენება დისტანციური კლიენტების მიერ
(CLI, Electron აპი ან სინქრონიზაციის worker-ები), რათა წაიკითხონ პროვაიდერის კავშირის მეტამონაცემები
და ამოხსნან მოდელების alias-ები. მათი ავთენტიფიკაცია ხდება **ჩვეულებრივი API გასაღებით**
(`validateApiKey`-ის მეშვეობით) და არა მართვის ავთენტიფიკაციით, რომელსაც ამოცანების endpoint-ები იყენებენ.

| მეთოდი | გზა                             | დანიშნულება                                                                                    |
| ------ | ------------------------------- | ---------------------------------------------------------------------------------------------- |
| POST   | `/api/cloud/auth`               | API გასაღების ვალიდაცია, შენიღბული კავშირის მეტამონაცემებისა და მოდელების alias-ების დაბრუნება |
| PUT    | `/api/cloud/credentials/update` | `accessToken` / `refreshToken` / `expiresAt`-ის განახლება                                      |
| POST   | `/api/cloud/model/resolve`      | მოდელის alias-ის ამოხსნა `{ provider, model }`-ად                                              |
| GET    | `/api/cloud/models/alias`       | მოდელების ყველა alias-ის ჩამონათვალი                                                           |
| PUT    | `/api/cloud/models/alias`       | მოდელის alias-ის დაყენება (და, თუ ჩართულია, Cloud-თან ავტომატური სინქრონიზაცია)                |

`/api/cloud/auth` არასოდეს აბრუნებს დაუმუშავებელ `apiKey` / `accessToken` / `refreshToken`-ს. ის
აბრუნებს `hasApiKey`, `hasAccessToken`, `hasRefreshToken`-სა და შენიღბულ გადახედვას
(`maskedApiKey`: პირველი 4 + `****` + ბოლო 4).

## ავტორიზაციის მონაცემების ამოხსნა

`getCloudAgentCredentials(providerId)` ფაილში `src/lib/cloudAgent/api.ts`:

1. იტვირთება პროვაიდერის აქტიური კავშირები `getProviderConnections({ provider: providerId, isActive: true })`-ის მეშვეობით.
2. თითოეული კავშირისთვის უპირატესობა ენიჭება `apiKey`-ს (ჩამოჭრილი ზედმეტი სივრცეებით). ალტერნატივად გამოიყენება `accessToken`.
3. აბრუნებს პირველ არაცარიელ ტოკენს, შეფუთულს როგორც `{ apiKey: token }`.
4. აბრუნებს `null`-ს, თუ გამოსაყენებელი ტოკენი ვერ მოიძებნა — API პასუხობს `400`-ით და
   `"Cloud agent provider-ისთვის აქტიური ავტორიზაციის მონაცემები კონფიგურირებული არ არის: <id>"`.

ეს ნიშნავს, რომ Cloud Agent-ები იყენებენ იმავე Provider Connection ცხრილს, რომელსაც ჩვეულებრივი LLM
პროვაიდერები. Jules-ის ჩასართავად შექმენით აქტიური კავშირი `provider: "jules"`-ით
და შევსებული `apiKey`-ით.

## A2A-სთან ინტეგრაცია

Cloud Agent-ები შეიძლება წარმოდგენილი იყოს A2A უნარების სახით, თუ დარეგისტრირდება A2A უნარი, რომელიც
თავის `tasks/send` დამმუშავებელს გადასცემს `getAgent(...).createTask(...)`-ს და A2A ამოცანის
სტატუსის მოვლენებს JSON-RPC 2.0 პროტოკოლში გარდაქმნის. იხილეთ [A2A-SERVER.md](./A2A-SERVER.md).

## ახალი Cloud Agent-ის დამატება

1. შექმენით `src/lib/cloudAgent/agents/<name>.ts`, რომელიც აფართოებს `CloudAgentBase`-ს.
2. განახორციელეთ `createTask`, `getStatus`, `approvePlan` (ან გამოისროლეთ შეცდომა, თუ არ გამოიყენება),
   `sendMessage`, `listSources`. სტატუსის ნორმალიზაციისთვის გამოიყენეთ `this.mapStatus(...)`.
3. დაარეგისტრირეთ `src/lib/cloudAgent/registry.ts`-ში სტაბილური `providerId`-ის ქვეშ.
4. გააფართოეთ `providerId` ლიტერალების გაერთიანება `src/lib/cloudAgent/types.ts`-ში
   (`CloudAgentTask.providerId` და `CreateCloudAgentTaskSchema`).
5. დაამატეთ პროვაიდერი `src/shared/constants/providers.ts`-ში, თუ მას კავშირის
   ჩანაწერი სჭირდება. OAuth-ზე დაფუძნებულ პროვაიდერებს ასევე სჭირდებათ `src/lib/oauth/providers/`.
6. დაამატეთ ტესტები `tests/unit/cloud-agent-*.test.ts`-ში.
7. განაახლეთ ეს დოკუმენტი და მართვის პანელის `CLOUD_AGENTS` კონსტანტა.
