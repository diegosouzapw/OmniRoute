## საჯარო განცხადებების წამკითხველი

ზოგადი განცხადებების წამკითხველი Radar-ის ფუნქციური დროშისგან განცალკევებულია. საინფორმაციო დაფის მთავარი გვერდი და
ცვლილებების ჟურნალის დამთვალიერებელი საცავის საჯარო `news.json`-ს ჩვეულებრივი `GET` მოთხოვნით იღებენ
`NEWS_JSON_URL`-დან (`src/shared/utils/releaseNotes.ts`). ისინი არ აგზავნიან Radar-ის არცერთ პარამეტრს, მოთხოვნას, პროვაიდერის
კონფიგურაციას, გამოყენების ჩანაწერს ან ლოკალური უგულებელყოფის მდგომარეობას.

`news.json` იყენებს `parseNewsPayload()`-ში იმპლემენტირებულ დახურულ v2 სქემას:

- `schemaVersion: 2` და შეზღუდული ზომის `items[]` კოლექცია;
- განცხადებების სტაბილური, უნიკალური `id` მნიშვნელობები;
- ცალსახა `active` და ISO `publishedAt` ველები;
- სავალდებულო ინგლისური ტექსტი და არასავალდებულო ლოკალიზებული ტექსტი;
- არასავალდებულო, ავტორიზაციის მონაცემების არმომთხოვნი HTTPS ბმულები და ნებადართულ სიაში შეტანილი ხატულა;
- უახლესი აქტიურის პირველად შერჩევა, ლოკალის ინგლისურზე გადართვა და თითოეული ID-ის ლოკალური უგულებელყოფა.

პარსერი დროებით იღებს წინა, ერთეული ობიექტის `{ active, title, message, ... }` ფორმას, რათა
ძველმა ფორკებმა მიგრაცია ცვლილებების ჟურნალის ხედის გაფუჭების გარეშე შეძლონ. არასწორი არხები უმოქმედოა. Radar-ის გაშვების
ჩანაწერი გამოიცემა `active: false` მნიშვნელობით; მისი `true`-ზე შეცვლა ცალკე, შერწყმისა და განთავსების შემდგომი
გამოშვების ქმედებაა და არ ცვლის `RADAR_ENABLED`-ს ან არხის სინქრონიზაციის დამოუკიდებელ თანხმობას.

`RADAR_ENABLED`-ის ჩართვა მხოლოდ UI-ს განბლოკავს. არხის სინქრონიზაცია მოითხოვს მეორე,
დამოუკიდებელ თანხმობას, რომელიც ინახება `radar_settings.opt_in`-ში (`src/lib/db/radar.ts`,
მიგრაცია `136_radar_cache_settings.sql`). `syncRadar()` ნებისმიერი ქსელური გამოძახების შესრულებამდე ამოწმებს როგორც დროშას, _ისე_
თანხმობას:

```
დროშა გამორთულია  → { status: "disabled" }   — ქსელური გამოძახება არ სრულდება

```

როდესაც ორივე ჩართულია, სინქრონიზაცია შემდეგნაირად მიმდინარეობს:

1. `GET <არხის საბაზისო URL>/v1/catalog/latest` მოთხოვნა `x-omniroute-radar-schema: 2` სათაურითა და არასავალდებულო
   `Authorization: Bearer <მხარდამჭერის გასაღები>` სათაურით (იხ. ქვემოთ). როდესაც სქემის სათაური არ არის მითითებული, სერვერები ნაგულისხმევად
   ცალკე ხელმოწერილ v1 გარდამავალ არტეფაქტს იყენებენ, რათა ძველმა დაინსტალირებულმა კლიენტებმაც განაგრძონ
   განახლებების მიღება.
2. ეს აპლიკაციის მხოლოდ ჩამოტვირთვის ნაკადია, თუმცა მაინც HTTPS მოთხოვნას წარმოადგენს. ჰოსტინგის
   ინფრასტრუქტურა იღებს ჩვეულებრივ კავშირის მეტამონაცემებს, როგორიცაა წყაროს IP. როდესაც მხარდამჭერის
   გასაღები კონფიგურირებულია, სინქრონიზაცია ასევე აგზავნის ამ გასაღებს Bearer სათაურში, რათა სერვისმა
   წვდომის უფლება განსაზღვროს. ზუსტად იმ კერძო სერვერის რევიზიაში, რომელიც ზემოთ მოცემული მტკიცებულებების საზღვრებშია იდენტიფიცირებული,
   არხის მოთხოვნების აღრიცხვა იყენებს გასაღებების ჰეშებს, აგრეგირებულ გამოყენებას და IP-ის ყოველდღიურად როტირებად შეკვეცილ HMAC-ს
   ბოროტად გამოყენების ხელით შესამოწმებლად; ეს ცხრილები არც გასაღებს და არც IP-ს დაუმუშავებელი სახით არ ინახავს.
   ინფრასტრუქტურის წვდომის ჟურნალები და დაშიფრული მიწოდების გამავალი შეტყობინებების საცავი ცალკე საოპერაციო
   საზღვრებს წარმოადგენს.
3. OmniRoute არასოდეს უგზავნის Radar სერვისს მოთხოვნებს, პასუხებს, საუბრებს, პროვაიდერის ავტორიზაციის მონაცემებს, მოდელის ტრაფიკს,
   ხელმისაწვდომობის დროს, დაყოვნებას ან პროვაიდერის ლოკალურ კონფიგურაციას.
4. პასუხი მოწმდება, ვალიდირდება და ლოკალურად კეშირდება (იხ.
   [უსაფრთხოების მოდელი](#security-model)). Radar-ს ზუსტად ოთხი სერვერის მხარის ქსელური გზა აქვს:
   `syncRadar()` კატალოგისთვის, `syncRadarReferrals()` რეფერალებისთვის და
   `syncRadarOffers()` / `syncRadarIntel()` მხოლოდ მხარდამჭერებისთვის განკუთვნილი შეთავაზებებისა და Intel-ისთვის.

**მხარდამჭერის გასაღები** არის არასავალდებულო Bearer ტოკენი (`radar_settings.supporter_key`),
რომელიც არხის სერვისს საშუალებას აძლევს გადაწყვიტოს, რომელი დონე მოემსახუროს (იხ.

- ინახება **დაშიფრული სახით** იმავე AES-256-GCM `encrypt()`/`decrypt()`
  დამხმარე ფუნქციებით (`src/lib/db/encryption.ts`), რომლებიც პროვაიდერის ავტორიზაციის მონაცემებისთვის გამოიყენება.
- ყენდება `POST /api/radar/settings`-ის მეშვეობით (`{ supporterKey: "omr_" + 40 hex chars }`) და
  **პასუხში არასოდეს ბრუნდება** — პასუხი აბრუნებს შენიღბულ ფორმას (`omr_****abcd`).
- მისი შეცვლა ან გასუფთავება ატომურად აუქმებს კატალოგის, რეფერალების, შეთავაზებებისა და Intel-ის კეშებს. შემდეგი
  სინქრონიზაცია/წაკითხვა სერვერის მხარეს განსაზღვრავს წვდომის ახალ უფლებას; გასაღების შენახვა თავისთავად
  არ ახორციელებს ქსელურ მოთხოვნას და არ ხარჯავს ერთჯერადი აქტივაციის გასაღებს.
- სინქრონიზაციის GET მოთხოვნისას არხის სერვისს ეგზავნება Bearer ტოკენის სახით — გასაღების შესახებ სხვა არაფერი
  ტოვებს კლიენტს.

### დაკარგული მხარდამჭერის გასაღების აღდგენა

განთავსებული სერვისის აღდგენის საწყისი წერტილია `https://radar.omniroute.online/recover`; მისი ბმული ასევე
მოცემულია გეგმების გვერდზე. აღდგენა სრულად OSS კლიენტის ფარგლებს გარეთ რჩება, რადგან ლოკალური
ინსტალაცია არასოდეს იღებს მყიდველის/კონტრიბუტორის ელფოსტის მისამართს და დაშიფრული პარამეტრებიდან
დაუმუშავებელი გასაღების აღდგენა არ შეუძლია.

1. მიუთითეთ გასაღებთან დაკავშირებული ელფოსტის მისამართი. სერვისი ერთსა და იმავე მიღების გვერდს აბრუნებს იმის მიუხედავად,
   არსებობს თუ არა აღდგენადი ლიცენზია, ამიტომ ფორმა ანგარიშების არსებობას არ ამჟღავნებს.
2. შესაბამისობის შემთხვევაში, მიწოდების მუშა პროცესი აგზავნის ხანმოკლე, ერთჯერადად გამოსაყენებელ ბმულს. მისი გახსნისას
   ტოკენი დაუყოვნებლივ გადადის დროებით დაშიფრულ `HttpOnly`/`Secure` cookie-ში და მომხმარებელი გადამისამართდება სუფთა
   `/recover` URL-ზე; გვერდი არ შეიცავს ტოკენს, ელფოსტის მისამართს, ძველ გასაღებს ან შემცვლელ გასაღებს.
3. დაადასტურეთ გაუქმება. კერძო სერვისი აუქმებს წინა გასაღებს, ქმნის შემცვლელს
   იგივე გეგმით/ვადის გასვლის თარიღით და ერთ ტრანზაქციაში აყენებს მას ელფოსტით გასაგზავნ რიგში. შემცვლელი
   ბრაუზერს არასოდეს უბრუნდება.
4. ჩასვით შემცვლელი `/dashboard/radar`-ში. ძველი გასაღების სტატუსი ახლა `community`-მდე უნდა დაქვეითდეს;
   შემცვლელმა კი უნდა უზრუნველყოს დადასტურებული `live` სინქრონიზაცია. იმავე აღდგენის ბმულის ხელახლა გახსნა უნდა დასრულდეს
   ზოგადი არასწორი/ვადაგასული პასუხით.

განთავსებული აღდგენის მარშრუტი და ფოსტის მუშა პროცესი შეიძლება კოდში არსებობდეს, თუმცა კონკრეტულ
განთავსებაში კვლავ მიუწვდომელი იყოს. პროცესს საწარმოო გამოყენებისთვის მზად ნუ მიიჩნევთ, სანამ სერვერი არ განთავსდება, მიწოდების
პროვაიდერი კონტროლირებადი მიმღებით არ დაკონფიგურირდება და სრული ერთჯერადი ბმული არ გამოიცდება.

როგორც კი ვიზიტორს ექნება გასაღები (`omr_` + 40 თექვსმეტობითი სიმბოლო), აქტივაციის ეკრანზე
(`src/app/(dashboard)/dashboard/radar/page.tsx`) გასაღების ჩასასმელი ველი მთავარი
გზაა: გასაღების ჩასმა და გაგზავნა ერთი გამოძახებით აგზავნის `POST /api/radar/settings` მოთხოვნას
(`{ optIn: true, supporterKey }`) — გასაღების ჩასმა ერთდროულად აყენებს მას და რთავს მონაწილეობას,
რითაც ეკრანი იხსნება. ფორმატი (`omr_` + 40 თექვსმეტობითი სიმბოლო) თავდაპირველად კლიენტის მხარეს
მოწმდება საზიარო `isValidSupporterKeyFormat()` დამხმარე ფუნქციით (`src/lib/radar/supporterKey.ts`),
როგორც UX-ის გაუმჯობესება; ნებისმიერ შემთხვევაში, საბოლოო შემოწმების ავტორიტეტული წყარო სერვერის Zod სქემაა. გასაღების
დაყენების შემდეგ აქტივაციის ეკრანი ცარიელი ველის ნაცვლად აჩვენებს შენიღბულ ფორმას (`supporterKeyMasked`
`GET /api/radar/settings`-იდან), „გასაღების შეცვლის“ მართვის ელემენტით, რომლითაც ახალი გასაღების
ჩასმაა შესაძლებელი — დაუმუშავებელი გასაღები ხელახლა არასოდეს გამოჩნდება. ზემოთ მოცემული მოთხოვნის/გეგმების ორი ღილაკი
კვლავ გამოიყენება გასაღების თავდაპირველად _მისაღებად_; ეს ველი კი განკუთვნილია იმ ოპერატორისთვის,
რომელსაც გასაღები უკვე აქვს და მისი გააქტიურება სურს.

### გამჭოლი აქტივაცია და მართვადი დაყენება

კერძო არხის სერვისსა და ამ OSS კლიენტს შორის განზრახ ვიწრო საზღვარია: სერვისი
გასცემს და ამოწმებს მხარდამჭერის გასაღებს, ხოლო ლოკალური OmniRoute ინსტალაცია შიფრავს გასაღებს,
სერვერის მხარეს ასინქრონებს ხელმოწერილ არტეფაქტებს და პროვაიდერის დაყენების პროცესს წარმართავს. დამხმარე ვალიდაციის თანმიმდევრობაა:

1. მიიღეთ ახლად გაცემული ან აღდგენილი გასაღები კონტრიბუტორის მოთხოვნის, plans/checkout-ის, აღდგენის
   პროცესის ან ავტორიზებული კერძო სერვერის ოპერატორისგან. არ ჩასვათ დაუმუშავებელი გასაღები ჟურნალებში,
   ეკრანის სურათებში, საკითხების კომენტარებში ან ბრძანების სტრიქონის არგუმენტებში.
2. ლოკალურ OmniRoute ინსტალაციაზე ჩართეთ `RADAR_ENABLED` ფუნქციის ალამი. ეს გამოაჩენს UI-ს,
   თუმცა ცალკე თანხმობის შენახვამდე ქსელური აქტივობა არ განხორციელდება.
3. გახსენით `/dashboard/radar`, ჩასვით გასაღები და გაააქტიურეთ. ბრაუზერი ლოკალურად აგზავნის ერთ
   `POST /api/radar/settings` მოთხოვნას `{ optIn: true, supporterKey }` მონაცემებით; გასაღები ლოკალურად იშიფრება და
   პასუხი შეიცავს მხოლოდ `omr_****<last4>`-ს.
4. აცადეთ აქტივაციის ეკრანს კატალოგის სინქრონიზაციის დასრულება, ან აირჩიეთ **ახლავე სინქრონიზაცია**. დარწმუნდით, რომ გვერდზე
   ნაჩვენებია `live`, არხის ვერსია და მიღების დრო. ავთენტიფიცირებული ლოკალური დიაგნოსტიკისთვის
   `GET /api/radar/status` აბრუნებს თანხმობის/გასაღების არსებობის სტატუსსა და ოთხი ქეშის მდგომარეობას ისე, რომ
   გასაღებს არ აბრუნებს. `POST /api/radar/sync-all`-ს შეუძლია კატალოგის, რეფერალების, შეთავაზებებისა და Intel-ის ცალსახად განახლება.

   აირჩიეთ **API გასაღების დამატება**, შეინახეთ პროვაიდერის რეალური ფორმით, დაბრუნდით სახელმძღვანელოში და გაუშვით
   **კავშირის ტესტირება**. სახელმძღვანელო იყენებს ჩვეულებრივ `/api/providers` და
   `/api/providers/<connection-id>/test` მარშრუტებს; ის არ ქმნის პარალელურ Radar ავტორიზაციის მონაცემებს.
6. გახსენით `/dashboard/radar/combos` მას შემდეგ, რაც სულ მცირე ორი თავსებადი პროვაიდერის კავშირი გააქტიურდება.
   გადახედეთ შემოთავაზებულ ოჯახს და შექმენით კომბინაცია არსებული combo API-ის მეშვეობით. შეთავაზებები და
   Intel რჩება განცალკევებულ, მხოლოდ live რეჟიმის ხელმოწერილ ქეშებად და მათი შემოწმება შესაძლებელია Radar-ის მათთვის განკუთვნილ გვერდებზე.
7. ხელახლა ჩატვირთეთ `/dashboard/radar` და დაყენების გვერდი. თანხმობა, შენიღბული გასაღების მდგომარეობა, ვერიფიცირებული ქეში, შენახული
   პროვაიდერის კავშირი და ტესტირების მოქმედება ხელახალი ჩატვირთვის შემდეგაც უნდა შენარჩუნდეს. მტკიცებულება გადაიღეთ მხოლოდ მას შემდეგ, რაც
   დაუმუშავებელი გასაღები და პროვაიდერის ავტორიზაციის მონაცემები აღარ გამოჩნდება.

გასაღების შენახვა თავისთავად არ ადასტურებს live წვდომის უფლებას. მტკიცებულება არის კერძო
სერვისის `GET /v1/license/check` შედეგის, OSS კატალოგის მიერ მოწოდებული `live` დონის, ვერიფიცირებული ხელმოწერილი
ქეშისა და პროვაიდერის რეალური კავშირის/ტესტირების პროცესის ერთობლიობა. არასწორი, ვადაგასული ან გაუქმებული გასაღების შემთხვევაში
კატალოგი უსაფრთხოდ გადადის `community` დონეზე; ეს არ უნდა დაფიქსირდეს live-გასაღების წარმატებულ ვალიდაციად.

### კერძო ადმინისტრატორის პანელის ბმული

`RADAR_ADMIN_URL` სურვილისამებრ ამატებს **Radar Admin ↗** პუნქტს უშუალოდ მომხმარებლისთვის განკუთვნილი
Radar პუნქტის შემდეგ, გვერდითი პანელის Costs განყოფილებაში. მას განზრახ არ აქვს ნაგულისხმევი მნიშვნელობა: როდესაც ცვლადი
არ არის დაყენებული ან არასწორია, სტატიკური გვერდითი პანელი, ბრძანებების პალიტრა და გვერდითი პანელის მორგების ეკრანი არ შეიცავს
ადმინისტრატორის პუნქტს ან კერძო URL-ს.

მნიშვნელობა განისაზღვრება სერვერის მხარეს და მართვის ავთენტიფიკაციით დაცული
`GET /api/settings` პასუხის მეშვეობით გადაეცემა მხოლოდ ავთენტიფიცირებულ დაფის სესიას, ან სანდო
loopback მფლობელს ლოკალური, შესვლის გარეშე საწყისი ჩატვირთვისას. CLI, შიდა სერვისი და manage-scope API-გასაღებით
ავთენტიფიკაცია მას არ იღებს. გარე ბმულის შექმნამდე ბრაუზერი პასუხს ხელახლა ამოწმებს,
ხოლო ბმული იხსნება `noopener noreferrer` პარამეტრებით.

გამოიყენეთ ავტორიზაციის მონაცემებისგან თავისუფალი HTTPS გვირაბის/tailnet-ის URL. უბრალო HTTP მიიღება მხოლოდ loopback SSH
გადამისამართებისთვის, როგორიცაა `http://127.0.0.1:9351`; სხვა სქემები, ჩაშენებული ავტორიზაციის მონაცემები, არასწორად შედგენილი URL-ები და
დისტანციური HTTP მისამართები უსაფრთხოების მიზნით უარყოფილია და ნავიგაცია უმოქმედო რჩება.

## უსაფრთხოების მოდელი

### Ed25519 ხელმოწერა ზუსტ ბაიტებზე

არხის მონაცემები ხელმოწერილია Ed25519-ით. `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) ამოწმებს ხელმოწერას ქსელით მიღებულ **ზუსტად იმავე პასუხის ბაიტებზე** — შემოწმებამდე მონაცემები არასოდეს სერიალიზდება ხელახლა, ამიტომ ბაიტი-ბაიტზე ხელახალი კოდირება ვერ შეძლებს ხელმოწერის შემოწმების შეუმჩნევლად გაუქმებას ან გვერდის ავლას.
შემოწმების წარუმატებლობა (`invalid_signature`) სინქრონიზაციას წყვეტს მანამ, სანამ მონაცემები დამუშავდება ან ქეშში შეინახება.

### მიბმული საჯარო გასაღები + როტაცია

შემოწმების საჯარო გასაღები მიბმულია `src/lib/radar/pinnedKeys.ts`-ში
(`PINNED_FEED_PUBLIC_KEYS`), მასივის სახით, რათა როტაციის წინ ახალი გასაღები დასაწყისში დაემატოს, ხოლო წინა გასაღებით ხელმოწერილი ძველი ქეშირებული არხები ხელახლა სინქრონიზაციამდე კვლავ ვალიდური დარჩეს.

### განშტოებებისთვის მოსახერხებელი გარემოს ცვლადებით გადაფარვა

ორი გარემოს ცვლადი საშუალებას აძლევს განშტოებებსა და თვითჰოსტინგის მომხმარებლებს, ნაგულისხმევი OmniRoute სერვისის ნაცვლად კლიენტი საკუთარ არხზე მიუთითონ — იხილეთ
[როგორ განვათავსოთ არხი საკუთარ სერვერზე](#how-to-self-host-a-feed) ქვემოთ:

| ცვლადი              | დანიშნულება                                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | გადაფარავს არხის საბაზისო URL-ს (ნაგულისხმევია `https://radar.omniroute.online`).                                |
| `RADAR_FEED_PUBKEY` | გადაფარავს მიბმულ საჯარო გასაღებს (base64-DER SPKI ან PEM) და ჩაშენებულ მასივს ამ ერთადერთი გასაღებით ანაცვლებს. |

### ვერსიის ქვედა ზღვარი

`syncRadar()` უარყოფს ჩამოტვირთულ არხს, რომლის `version` მკაცრად არ აღემატება
ამჟამად ქეშირებულ ვერსიას (`compareVersions()`, წერტილებით გამოყოფილი `YYYY.MM.DD.n` შედარება) —
`{ status: "stale" }`. ეს ხელს უშლის კომპრომეტირებულ ან არასწორად კონფიგურირებულ არხის ბოლო წერტილს, კლიენტი დააბრუნოს უფრო ძველ, სხვაგვარად ხელმოწერილ მონაცემებზე.

### ორი თარიღი და რატომ ინახება ორივე

ქეშირებული არხი ორ განსხვავებულ თარიღს შეიცავს და მათი აღრევის თავიდან აცილება სწორედ ორივეს შენახვის მიზანია:

| ველი          | წყარო                    | რას გვიჩვენებს                         |
| ------------- | ------------------------ | -------------------------------------- |
| `generatedAt` | ხელმოწერილი არხის სხეული | რამდენად ძველია **მონაცემები**         |
| `fetchedAt`   | ამ ინსტალაციის საათი     | როდის **ჩამოტვირთა** ის ამ ინსტალაციამ |

რამდენიმე წუთის წინ ჩამოტვირთული არხი შეიძლება რამდენიმე კვირის წინანდელ მონაცემებს შეიცავდეს, ამიტომ მხოლოდ `fetchedAt` ოპერატორს ვერ ეტყვის, არის თუ არა ზედდებული მონაცემები იმ საბაზისო მონაცემებზე ახალი, რომლებზეც ის არის განთავსებული. ორივე ინახება `radar_feed_cache`-ში, ბრუნდება `getRadarCatalog().meta`-ს მიერ და ცალ-ცალკე მიეწოდება
`GET /api/radar/status`-ის მიერ. ჩანაწერი, რომელიც `generated_at` სვეტის დამატებამდე (მიგრაცია 163) იყო ქეშირებული, წაკითხვისას აბრუნებს `null`-ს — უცნობი მნიშვნელობა უცნობად რჩება და ჩამოტვირთვის დროს არ სესხულობს. `radar_referrals_cache` საკუთარ `generated_at`-ს მიგრაცია 142-იდან ინახავს.

ზემოთ აღწერილი ვერსიის ქვედა ზღვარი ადარებს `version`-ს და არა რომელიმე თარიღს.

რჩება ორი ხარვეზი და ორივე მიზანმიმართულია: საინფორმაციო დაფა ჯერ კიდევ მხოლოდ `Last fetched`-ს აჩვენებს, ამიტომ იქ აგების თარიღის გამოსატანად საჭიროა ახალი წარწერა (და მისი 41 ლოკალიზებული ჩანაწერი); შეთავაზებებისა და სადაზვერვო მონაცემების ქეშები კი აგების თარიღს საერთოდ არ ინახავს, მიუხედავად იმისა, რომ მათი არხის სქემები მას შეიცავს — ამიტომ `GET
/api/radar/status` ამ ორი ქეშისთვის ველს საერთოდ გამოტოვებს, ნაცვლად `null`-ის დაბრუნებისა, რომელიც „უცნობად“ აღიქმებოდა.

### სქემის ვალიდაცია

ჩამოტვირთული ბაიტები მუშავდება და მოწმდება `RadarFeedSchema`-სთან
(`src/lib/radar/feedSchema.ts`, Zod-ის სქემა) შესაბამისობაზე ხელმოწერის შემოწმების **შემდეგ**. სქემის შეუსაბამობა აბრუნებს `{ status: "invalid_schema" }`-ს და ქეში ხელუხლებელი რჩება. ქეშირებული მონაცემები ყოველი წაკითხვისას (`getRadarCatalog()`) უსაფრთხოების მიზნით ხელახლა მოწმდება — დაზიანებული ან ხელით რედაქტირებული ქეშის ჩანაწერის ნაცვლად გამოიყენება საბაზისო მონაცემები.

### პასუხის ზომის ზღვარი (10 MB)

`syncRadar()` არხის პასუხის სხეულზე აწესებს **10 MB მკაცრ ზღვარს** — ხელმოწერილი არხი KB-ის მასშტაბის JSON დოკუმენტია, ამიტომ ამ ზღვარზე მეტი მიუთითებს არასწორად კონფიგურირებულ ან მტრულ `RADAR_FEED_URL`-ზე (ან ზედა დონის სერვისზე, რომელიც უსარგებლო მონაცემებს აბრუნებს) და არა ლეგიტიმურ კატალოგზე.
შეზღუდვა ორ დონეზე მოქმედებს:

1. `Content-Length`-ის წინასწარი შემოწმება სხეულის წაკითხვას მთლიანად გამოტოვებს, როცა
   სათაური უკვე მიუთითებს ზღვარზე მეტ მნიშვნელობას.
2. სხეულის წაკითხვისას მიმდინარე ჯამის შემოწმება ზღვარს მაშინაც აღასრულებს, როცა
   `Content-Length` არ არსებობს ან რეალურ ზომაზე ნაკლებს მიუთითებს — მხოლოდ სათაური
   არასოდეს ითვლება სანდოდ. დაგროვილი ფრაგმენტების გაერთიანება ინარჩუნებს ზუსტ
   ბაიტებს, რომლებიც შემდგომ Ed25519 ხელმოწერის შესამოწმებლადაა საჭირო.

ზღვრის გადაჭარბება აბრუნებს `{ status: "too_large" }`-ს და ქეშს ხელუხლებლად ტოვებს,
ისევე, როგორც სინქრონიზაციის ნებისმიერი სხვა წარუმატებლობისას
(`invalid_signature`, `invalid_schema`, `stale`).

არხის სქემა შეიცავს `tier: "community" | "live"` ველს, რომელსაც არხის სერვისი მოთხოვნის საფუძველზე **სერვერის მხარეს** განსაზღვრავს (მხარდამჭერის გასაღების არსებობისა და ვალიდურობის მიხედვით)
— კლიენტი საკუთარ დონეს არასოდეს განსაზღვრავს.

- **`community`** — უფასო კატალოგი, რომელიც უახლეს მონაცემებს დაახლოებით 30 დღით ჩამორჩება.
  ამას იღებს არაავთენტიფიცირებული ან არავალიდური გასაღებით გაგზავნილი მოთხოვნა.
- **`live`** — უახლესი კატალოგი, რომელიც ვალიდური მხარდამჭერის
  გასაღების შემცველ მოთხოვნებს მიეწოდება.

**არავალიდური ან ვადაგასული მხარდამჭერის გასაღები `community` დონემდე ქვეითდება — ეს
შეცდომა არასოდეს არის.** სინქრონიზაციის გზა მხოლოდ ხელმოწერის/სქემის/ვერსიის წარუმატებლობებს (ყველა
აღდგენადია და არცერთი არ არის ფატალური კეშირებული მდგომარეობისთვის) და წარმატებულ `{ status:
"updated", version, tier }` შედეგს განასხვავებს. არ არსებობს დონის სპეციფიკური შეცდომის გზა, რომლის
დამუშავებაც კლიენტს სჭირდება.

### მიწოდებული დონე პასუხის სათაურიდან მოდის და არა ხელმოწერილი სხეულიდან

ხელმოწერილი არხის **სხეულის** `tier` ველი ყოველთვის `"live"`-ია — არხის სერვისი თითოეულ ვერსიაზე
**ორ ხელმოწერილ არტეფაქტს** ავრცელებს: live შეიცავს მიმდინარე კამპანიებს, ხოლო community
მათ გამოტოვებს. თითოეული არტეფაქტი ხელმოწერილია ზუსტად საკუთარ ბაიტებზე. სხეული კვლავ არ
გამოიყენება წვდომის უფლების შესახებ გადაწყვეტილების მისაღებად; მოთხოვნისთვის რეალურად შერჩეული დონე
გადაეცემა **`x-omniroute-feed-tier` პასუხის სათაურში**, რომელიც სერვერის მხარეს მოთხოვნის
`Authorization` გასაღების მიხედვით განისაზღვრება.

`syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) ერთადერთი ადგილია,
რომელიც განსაზღვრავს დონეს, რომელსაც კლიენტი უნდა ენდოს:

1. დაამუშავეთ `x-omniroute-feed-tier` `RadarTierSchema`-ით (Zod) — არარსებული სათაური ან
   მნიშვნელობა, რომელიც ზუსტად `"community"` ან `"live"` არ არის, ითვლება **არარსებულად**
   (ის არასოდეს ხვდება კეშში/UI-ში უცვლელი სახით; ეს ასევე მოიცავს არხის ძველ
   სერვერებს, რომლებიც ამ სათაურამდე არსებობდა).
2. მხოლოდ მაშინ გამოიყენეთ სათადარიგოდ ხელმოწერილი სხეულის `tier` ველი (ყოველთვის `"live"`), როცა 1-ლი ნაბიჯი
   არაფერს აბრუნებს.
3. განსაზღვრული დონე კეშირდება და ბრუნდება, როგორც `{ status: "updated",
version, tier }` — საინფორმაციო დაფა სწორედ ამ მნიშვნელობას აჩვენებს და არა სხეულის დაუმუშავებელ
   ველს.

## წაკითხვის დროს ზედდების გაერთიანების წესები

`applyFeed()` (`src/lib/radar/applyFeed.ts`) კეშირებულ არხს სტატიკურ საბაზისო მონაცემებზე **ზედდებით**
აერთიანებს **წაკითხვის დროს**, `getRadarCatalog()`-ის შიგნით. საბაზისო მასივი
(`FREE_MODEL_BUDGETS`) არასოდეს იცვლება — ყოველ გამოძახებაზე ახალი `MergedEntry[]` გამოითვლება.

ოთხი წესი, უპირატესობის მიხედვით:

1. **არხი არასოდეს გადაწერს ლოკალურ ჩანაცვლებას.** თითოეული ველისთვის: თუ ოპერატორმა
   ჩანაწერის რომელიმე ველი შეცვალა (`localOverrides` რუკა, გასაღებით `provider:modelId`),
   არხის მნიშვნელობა ამ კონკრეტული ველისთვის გამოტოვებულია — უპირატესობა ოპერატორის მნიშვნელობას ენიჭება.
2. **`enabled: false` ჩანაწერს თიშავს და წარმომავლობასაც აფიქსირებს.** არხის ჩანაწერი, რომელიც
   ჩანაწერს თიშავს, გაერთიანებულ შედეგში აყენებს `enabled: false`-სა და `disabledBy: "radar"`-ს,
   რათა UI-მ ახსნას, _რატომ_ შეიცვალა ჩანაწერი ხელმისაწვდომიდან გათიშულამდე.
3. **არხში არარსებული, მომხმარებლის მიერ დამატებული ჩანაწერი უცვლელად ნარჩუნდება.** ჩანაწერები, რომლებიც
   მხოლოდ საბაზისო მონაცემებში არსებობს (ან ლოკალურად დაემატა) და არხში შესაბამისი
   ჩანაწერი არ აქვს, უცვლელად გაივლის.
4. **სამუდამოდ წაშლილი ჩანაწერი აღარასოდეს აღდგება.** თუ ოპერატორმა ჩანაწერი პირდაპირ წაშალა
   (`tombstones` ნაკრები), არხის მიერ მოგვიანებით ვერსიაში იმავე `provider:modelId`-ის ხელახლა
   დამატება მას არ დააბრუნებს.

რედაქტირებადი ველები და წაშლის ნიშნები ინახება
`radar_local_model_state`-ში (მიგრაცია `153_radar_local_model_state.sql`). საჯარო DB
ადაპტერი (`src/lib/db/radar.ts`) ამ სტრიქონებს გარდაქმნის `localOverrides` რუკად და
`tombstones` ნაკრებად, რომლებსაც `applyFeed()` იყენებს; საწარმოო `getRadarCatalog()` ამ მდგომარეობას
დროშის, კეშისა და სქემის შემოწმებების წარმატებით გავლის შემდეგ ტვირთავს. ოპერატორს მხოლოდ `displayName`-ისა და `enabled`-ის
რედაქტირება შეუძლია. პროვაიდერის/მოდელის იდენტობა, არხის წარმომავლობა, კვოტა, შესაძლებლობები, ToS
და კონფიგურაციის მონაცემები ამ ინტერფეისის გავლით ვერ ჩაიწერება.

საინფორმაციო დაფა ოთხ ლოკალურ მოქმედებას იძლევა:

- **რედაქტირება** ცვლის ლოკალურ საჩვენებელ სახელსა და ჩართულობის მდგომარეობას.
- **ლოკალური ცვლილებების ჩამოყრა** ასუფთავებს ორივე რედაქტირებად ველს წაშლის ნიშნის შეცვლის გარეშე.
- **დამალვა** ქმნის წაშლის ნიშანს, რათა არხის შემდგომმა განახლებებმა სტრიქონი ვეღარ აღადგინოს.
- **აღდგენა** შლის წაშლის ნიშანს; ცალკე შენახული ნებისმიერი ჩანაცვლება ძალაში რჩება.

არხის `enabled: false` უსაფრთხოების გამონაკლისად რჩება: მას უპირატესობა აქვს მოძველებულ ლოკალურ
`enabled: true`-თან შედარებით, გაერთიანებულ ჩანაწერს გათიშულად ტოვებს და აფიქსირებს `disabledBy: "radar"`-ს.

კატალოგის პუბლიკაციები იყენებს `schemaVersion: 2`-ს. `contextWindow` და თითოეული `tools`, `vision` და
`thinking` ერთმანეთისგან დამოუკიდებლად არის `number | null` / `boolean | null`: `null` ნიშნავს უცნობს, ხოლო
`false` ნიშნავს, რომ D16-ით დადასტურებული ოფიციალური პროვაიდერის წყარო ცალსახად მიუთითებს შესაძლებლობის არარსებობაზე.
OmniRoute-ის შიდა რეესტრის/მოდელის სპეციფიკაციის დროშები პირდაპირ არხის ფაქტებად არასოდეს გარდაიქმნება. კლიენტი
კვლავ იღებს v1 ანაბეჭდებს; რადგან ძველი შემქმნელი არარსებობის ადგილს `false`-ით ავსებდა, v1-ის `false`
ნორმალიზდება უცნობ მნიშვნელობად, ხოლო v1-ის `true` ფაქტად რჩება. სქემის უცნობი ვერსიები უსაფრთხოდ უარყოფილია და
ბოლო ვალიდური კეში ხელმისაწვდომი რჩება. ყველა v2 მოდელს, რომელსაც არანულოვანი კონტექსტი/შესაძლებლობა აქვს, უნდა ახლდეს
ავტორიზაციის მონაცემების არმომთხოვნი HTTPS `metadataEvidenceUrls[]`; წინააღმდეგ შემთხვევაში სქემის ვალიდაცია ვერ გაივლის და კეში
არ ჩანაცვლდება. კატალოგის ცხრილი სამივე მდგომარეობას აჩვენებს, როგორც `✓`, `✕` და `?`.

### მართული კომბინაციები და MCP-ზე წვდომა

დადასტურებული `familyId` მნიშვნელობები წაკითხვის დროს ზედდებას გადაურჩება და მართავს სუფთა
`buildRadarComboSuggestions()` მოდულს (`src/lib/radar/comboSuggestions.ts`). ოჯახი შეთავაზებულია
მხოლოდ მაშინ, როცა სულ მცირე ორ განსხვავებულ პროვაიდერს აქტიური კავშირები აქვს და ზუსტად მითითებულ კურირებულ მოდელის
ID-ს სთავაზობს. გათიშული მოდელები, არააქტიური პროვაიდერები, არარსებული მოდელის ID-ები, ერთელემენტიანი ოჯახები და ორაზროვანი
ფსევდონიმის/პრეფიქსის დამთხვევები უსაფრთხოდ უარყოფილია. შეთავაზებები იყენებს არსებულ `priority` სტრატეგიას და
უდიდეს განმეორებად ყოველთვიურ ბიუჯეტს პირველ ადგილზე აყენებს; UI მათ მხოლოდ `POST /api/combos`-ის მეშვეობით ქმნის.

მართვადი UI მდებარეობს მისამართზე `/dashboard/radar/combos`. ის კითხულობს მხოლოდ ლოკალურ
`GET /api/radar/catalog` და `GET /api/combos/builder/options` ბოლო წერტილებს. ის არასოდეს იწვევს Radar-ის სინქრონიზაციას,
არ კითხულობს პროვაიდერის ავტორიზაციის მონაცემებს და არ წერს პირდაპირ combo მონაცემთა ბაზაში.

MCP კლიენტებს შეუძლიათ წაიკითხონ იგივე ლოკალური პროექცია `omniroute_radar_catalog`-ის (`read:radar`) მეშვეობით. არასავალდებულო
`provider`, `familyId` და `enabledOnly` ფილტრები ფასდება ერთი ლოკალური
`GET /api/radar/catalog` წაკითხვის შემდეგ. მისი დახურული გამომავალი შეიცავს კატალოგის მეტამონაცემებს, ასევე პროვაიდერს/მოდელს,
საჩვენებელ სახელს, `familyId`-ს, კვოტას, შესაძლებლობებს, ჩართულობის მდგომარეობას, წარმომავლობასა და `disabledBy`-ს; დაყენების URL-ები,
ნაბიჯები, კავშირები, ელფოსტის მისამართები, გასაღებები და რეფერალური მონაცემები არასოდეს ბრუნდება. ეს ხელსაწყო
მხოლოდ წასაკითხადაა და არასოდეს იძახებს `/api/radar/sync`-ს.

### წარმომავლობის ნიშნულები

ყოველი გაერთიანებული ჩანაწერი შეიცავს `origin` ველს, რომელსაც UI სამკერდე ნიშნად აჩვენებს:

- `"baseline"` — უცვლელადაა აღებული გამოშვების სტატიკური კატალოგიდან.
- `"radar"` — ერთი ან მეტი ველი განახლდა არხის მეშვეობით.
- `"local"` — ოპერატორს ამ ჩანაწერზე მინიმუმ ერთი ლოკალური გადაფარვა აქვს (ლოკალური
  გადაფარვები ყოველთვის უპირატესია არხის მონაცემებთან შედარებით, 1-ლი წესის მიხედვით, მიუხედავად იმისა, თუ რას მიუთითებს არხი).

auth მდგომარეობისა — მხოლოდ შენიღბულ ფორმასა და `hasSupporterKey` boolean-ს.

## მხარდამჭერის შეთავაზებები

შეთავაზებები იყენებს საკუთარ ხელმოწერილ არტეფაქტს, `GET /v1/offers/latest`, და არასოდეს იზიარებს კატალოგის ან რეფერალების კეშს. სერვერის ენდპოინტი მოითხოვს მოქმედ მხარდამჭერის Bearer გასაღებს; საზოგადოებრივი რეჟიმის სარეზერვო ვარიანტი არ არსებობს. ამიტომ, `syncRadarOffers()` ქსელთან დაკავშირებამდე წყდება, როდესაც ფუნქციის ალამი გამორთულია, ოპერატორს თანხმობა არ განუცხადებია ან მხარდამჭერის გასაღები კონფიგურირებული არ არის.

წარმატებული GET-ის შემდეგ კლიენტი ამოწმებს Ed25519 ხელმოწერას ზუსტად მიღებული პასუხის ბაიტებზე, ახდენს `RadarOffersFeedSchema`-ის ვალიდაციას, მოითხოვს, რომ როგორც ხელმოწერილ სხეულში, ისე `x-omniroute-feed-tier` სათაურში მითითებული იყოს `live`, უზრუნველყოფს, რომ წერტილებით გამოყოფილი ვერსია მკაცრად უფრო ახალი იყოს, და მხოლოდ ამის შემდეგ ანაცვლებს ატომურად `radar_offers_cache`-ს (მიგრაცია `144_radar_offers_cache.sql`). აქაც მოქმედებს სათაურისა და ნაკადის ჯამური 10 MB-იანი ზღვარი, რომელიც სხვა არხებისთვის გამოიყენება. ხელმოწერის, სქემის, დონის, განმეორებითი ვერსიის, ზომის, HTTP-ისა და ქსელის შეცდომების შემთხვევაში ბოლო ვერიფიცირებული კეში უცვლელად ინახება.

შეთავაზების დახურული ფორმა მხარს უჭერს სამი ტიპის შესადარებელ სარგებელს: პროცენტულ მაჩვენებელს საბაზისო პუნქტებში, კრედიტს ვალუტის უმცირეს ერთეულებში ან საცდელი პერიოდის დღეებს. პარტნიორის შეთავაზება უნდა შეიცავდეს იმავე ტიპის საჯარო საბაზისო ვარიანტს და მისი სარგებელი მკაცრად მეტი უნდა იყოს; ოფიციალურ შეთავაზებებს პარტნიორის საბაზისო ვარიანტი არ გააჩნია. URL-ები უნდა იყენებდეს HTTPS-ს და არ უნდა შეიცავდეს ავტორიზაციის მონაცემებს. `getRadarOffers()` თავდაცვითად ხელახლა ამოწმებს კეშირებულ მონაცემებს და ყოველი ლოკალური წაკითხვისას ფილტრავს ვადაგასულ ჩანაწერებს; `/dashboard/radar/offers` რენდერინგამდე კიდევ ერთხელ ფილტრავს ვადაგასულ ჩანაწერებს, ხელმისაწვდომობის შემთხვევაში იყენებს პორტუგალიურ ტექსტს, ხოლო წინააღმდეგ შემთხვევაში — ინგლისურს, და პარტნიორის შეთავაზებებს მკაფიოდ მონიშნავს.

ბრაუზერი მხოლოდ ლოკალურ მარშრუტებს იძახებს: კითხულობს შენიღბულ პარამეტრების სნეპშოტს, სერვერის მხარეს განახლებისთვის მიმართავს `POST /api/radar/offers/sync`-ს, შემდეგ კი კითხულობს `GET /api/radar/offers`-ს. გასაღების გარეშე არხის მოთხოვნის მცდელობის ნაცვლად ის აჩვენებს კონტრიბუტორის/მხარდაჭერის არსებულ ბმულებს. გარე შეთავაზებების ბმულები ახალ ჩანართში იხსნება `noopener noreferrer`-ით. ამ გამოშვებაში `radar_offers` MCP ინსტრუმენტი ხელმისაწვდომი არ არის.

## Radar Intel, მხარდამჭერის სამკერდე ნიშანი და CLI

Intel არის ხელმოწერილი არტეფაქტი მისამართზე `GET /v1/intel/latest`. დახურული `RadarIntelFeedSchema` იღებს მხოლოდ Radar-ის კუთვნილ ELO რეიტინგებს, რომლებიც კერძო კურატორმა დადასტურებული შედარებებიდან მიიღო, და ხელმოწერილი კატალოგის სნეპშოტებიდან მიღებულ კატალოგის ასაკისა და რაოდენობის ფაქტობრივ სხვაობებს. მეთოდოლოგია ფიქსირებულია: საწყისი რეიტინგია 1000, ხოლო K=32. ცარიელი რეიტინგი ვალიდურია, როდესაც არცერთი შედარება არ დადასტურებულა; კლიენტი მას არასოდეს ასინთეზირებს.

`syncRadarIntel()` იყენებს იმავე სერვერის მხარეს არსებულ Bearer-ს, 30-წამიან ტაიმაუტს, ნაკადისთვის დაწესებულ 10 MiB-იან ზღვარს, ზუსტ ბაიტებზე Ed25519 ვერიფიკაციას, მკაცრ სქემას, სხეულსა და სათაურში `live`-ის მოთხოვნას, ვერსიის მინიმალურ ზღვარს და ბოლო გამართული კეშის შენარჩუნებას, რასაც შეთავაზებები იყენებს. ვერიფიცირებული მოქმედი სნეპშოტის შენახვის შემდეგ კლიენტი გამოითვლის `radar:<sha256(supporter key)>`-ს, ინახავს მხოლოდ ამ ცალმხრივ იდენტობას და გამოსცემს სპეციალურ `radar_supporter` აღიარების მოვლენას. მისი `radar-supporter` სამკერდე ნიშანი იდემპოტენტურია და ნულ XP-ს ანიჭებს; ის არასოდეს განაახლებს ლიდერთა ცხრილებს და არ იყენებს ხელახლა `token_share`-ს. `/dashboard/radar/intel` სამკერდე ნიშანს არენდერებს მხოლოდ ვერიფიცირებული ლოკალური კეშის მეტამონაცემებიდან.

CLI გთავაზობთ `omniroute radar status` და `omniroute radar sync` ბრძანებებს. ორივე მხოლოდ ლოკალურ OmniRoute API-სთან ურთიერთქმედებს. `status` ასრულებს მხოლოდ წაკითხვისთვის განკუთვნილ `GET /api/radar/status` მოთხოვნას; `sync` აგზავნის ერთ `POST /api/radar/sync-all` მოთხოვნას და თითოეული არხისთვის შედეგს ბეჭდავს. არცერთი ბრძანება არ კითხულობს, არ იღებს და არ ბეჭდავს მხარდამჭერის გასაღებს, ასევე არცერთი არ უკავშირდება Radar სერვისს პირდაპირ.

## რეფერალური ბმულები (უფასო კრედიტები)

რეფერალური ბმულები მოწოდებულია **დამოუკიდებელი, ყოველთვის აქტუალური** არხიდან —
`GET /v1/referrals/latest` — კატალოგის არხისგან განცალკევებით. ეს მიზანმიმართულია:
community დონეზე კატალოგის არხი წარმოადგენს ანაბეჭდს, რომელიც შეიძლება 30 დღემდე
ძველი იყოს, ამიტომ მისგან ამოღებული რეფერალური ბმული სერვერის რეალურ ბმულთა სიას
იმავე დროით ჩამორჩებოდა (ახლად დამატებული რეფერალური ბმული უფასო/community
მომხმარებლამდე შესაძლოა ერთი თვის განმავლობაში ვერ მისულიყო). რეფერალების არხი
ამ დაყოვნებას საკუთარი, გაცილებით მოკლე პერიოდულობით სინქრონიზაციის გზით აღმოფხვრის.

```ts
// GET /v1/referrals/latest პასუხის სხეული (ხელმოწერილია Ed25519-ით, იგივე
// ფიქსირებული გასაღებით, რომელსაც კატალოგის არხი იყენებს):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — დეტერმინისტული: max(updatedAt) ყველა
                                  // რეფერალურ ბმულს შორის, ამიტომ ორი იდენტური მოთხოვნა
                                  // ზუსტად ერთნაირ ხელმოწერილ ბაიტებს/ხელმოწერას ქმნის
  referrals: {
    fixed: RadarReferral[],      // წარმოდგენილია ყველა დონეზე, მათ შორის ავტორიზაციის
                                  // გარეშე/community დონეზე
    campaigns: RadarReferral[],  // ივსება მხოლოდ მოქმედი live (supporter) Bearer
                                  // გასაღებისთვის; ავტორიზაციის გარეშე/ვადაგასული
                                  // გასაღებით მოთხოვნები იღებს []
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

კატალოგის არხისგან განსხვავებით, ეს სხეული საერთოდ არ შეიცავს `tier` ველს —
სერვერი თითოეული მოთხოვნისთვის `Authorization` გასაღების საფუძველზე წყვეტს, რა
ჩართოს, ამიტომ `x-omniroute-feed-tier` პასუხის სათაური არის მოწოდებული დონის
ერთადერთი წყარო (`referralsSync.ts::syncRadarReferrals`); არარსებული ან ამოუცნობი
სათაური ჩამოიქვეითება `"community"` დონემდე, რაც ყველაზე ნაკლებად პრივილეგირებული
ვარაუდია. `RadarReferralsFeedSchema` (`src/lib/radar/referralsFeedSchema.ts`) ამოწმებს
მთელ სხეულს და ხელახლა იყენებს `feedSchema.ts`-იდან ექსპორტირებულ იმავე
`RadarReferralSchema`-ს თითოეული რეფერალისთვის, რათა ორივე არხმა ცალკეული რეფერალები
იდენტურად შეამოწმოს. ყოველი `RadarReferral.url` უნდა იწყებოდეს `https://`-ით —
`http://` url სქემის ვალიდაციას ვერ გაივლის.

ძველი, კატალოგში ჩაშენებული `referrals` ველი `RadarFeedSchema`-ში (`feedSchema.ts`)
შენარჩუნებულია უკვე დაკეშილ კატალოგის არხებთან უკუთავსებადობისთვის, თუმცა
`getRadarReferrals()` მას აღარ კითხულობს — იხილეთ ქვემოთ
[წვდომის ფუნქცია](#accessor).

### სინქრონიზაცია

`syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) არის ერთადერთი მოდული,
რომელიც რეფერალებისთვის ქსელს უკავშირდება და ზუსტად იმეორებს `syncRadar()`-ის
კონტრაქტს: გამორთული ფლაგი → `disabled`; უარი მონაწილეობაზე → `opt_out`; ჩამოტვირთავს
`${RADAR_FEED_URL}/v1/referrals/latest`-ს (კატალოგის მსგავსად, იგივე
`RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` განშტოების ჩანაცვლებებით), ამოწმებს ზუსტი პასუხის
ბაიტების Ed25519 ხელმოწერას (`verifyFeedBytes`), ატარებს ვალიდაციას
`RadarReferralsFeedSchema`-ით და კეშავს `radar_referrals_cache` ცხრილში
(მიგრაცია `142_radar_referrals_cache.sql`) — ეს ცხრილი კატალოგის
`radar_feed_cache`-ისგან სრულიად განცალკევებულია. პასუხის 10 MB-იანი ზღვარი და
`generatedAt`-ის ქვედა ზღვარი უარყოფს შემომავალ არხს, თუ ის დაკეშილზე ძველია, რაც
უფრო ძველი ხელმოწერილი არტეფაქტის ხელახლა გამოყენებისგან იცავს. თანაბარი დროის
ნიშნული მიიღება: სერვერი community და live რეფერალურ ვარიანტებს განზრახ ანიჭებს
ერთსა და იმავე დეტერმინისტულ `generatedAt`-ს, რათა supporter გასაღების ცვლილების
შემდეგ ხელმოწერილი დატვირთვა და მოწოდებული დონე შეიცვალოს ისე, რომ ბმულების საბაზისო
ნაკრები არ შეიცვალოს. გამონაკლისს არასდროს აგდებს — ყოველთვის აბრუნებს სტატუსის
ობიექტს; შეცდომების `reason` არასდროს შეიცავს სტეკის კვალს.

რეფერალების კეშს აქტუალურს ორი ტრიგერი უნარჩუნებს; ორივე მათგანი კატალოგის საკუთარ
24-საათიან პერიოდულობაზე დამოუკიდებელია:

- **სინქრონიზაცია წაკითხვისას** — `GET /api/radar/referrals` თავად იძახებს
  `syncRadarReferrals()`-ს უშუალოდ მაშინ, როდესაც კეში არ არსებობს ან
  `REFERRALS_STALE_MS`-ზე ძველია (1სთ, `shouldSyncReferralsOnRead()`), პასუხის
  მიწოდებამდე. სწორედ ეს ხდის ფიქსირებულ ბმულებს „ყოველთვის აქტუალურს“ დაფის
  მომდევნო ჩატვირთვისთანავე, ფონური ტაიმერის ლოდინის გარეშე.
- **დამგეგმავის გვერდითი სინქრონიზაცია** — `radarSchedulerTick()` (`scheduler.ts`)
  დამოუკიდებლად აფასებს რეფერალების მოძველებას იმავე საათობრივ ტაქტზე, რომელიც
  კატალოგისთვის გამოიყენება, და საჭიროებისას იძახებს `syncRadarReferrals()`-ს. ეს
  სრულდება იმის მიუხედავად, იყო თუ არა კატალოგის სინქრონიზაცია იმ ტაქტზე საჭირო, და
  არასდროს ცვლის `RadarTickResult`-ის ფორმას (მხოლოდ მაქსიმალური ძალისხმევით
  შესრულებული გვერდითი ეფექტია, რომლის შეცდომაც ჩაიხშობა).

### წვდომის ფუნქცია

`src/lib/radar/index.ts` ექსპორტს უკეთებს ორ მხოლოდ წაკითხვისთვის განკუთვნილ წვდომის
ფუნქციას. არცერთი მათგანი არასდროს აგდებს გამონაკლისს (იგივე თავდაცვითი კონტრაქტი,
რაც `getRadarCatalog()`-ს აქვს — გამორთული ფლაგი, კეშის არარსებობა ან დაზიანებული
დაკეშილი დატვირთვა შეცდომის ნაცვლად ცარიელ ფორმას აბრუნებს):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  კითხულობს `radar_referrals_cache`-იდან (`getRadarReferralsCache()`-ის მეშვეობით) და
  ვალიდაციას `RadarReferralsFeedSchema`-ით ატარებს — **არა** კატალოგის კეშიდან.
- `getDefaultReferralFor(provider)` → ამ პროვაიდერის `fixed` რეფერალი, რომლისთვისაც
  `isDefault: true`, ან `null`. ამოწმებს მხოლოდ `fixed`-ს — კამპანია არასდროს
  გამოიყენება პროვაიდერის „ნაგულისხმევ“ ბმულად.

ფაქტობრივი წესი, რომელიც განსაზღვრავს, „რომელი რეფერალია პროვაიდერისთვის
ნაგულისხმევი“, განთავსებულია `findDefaultReferral()`-ში
(`src/lib/radar/referrals.ts`) — პატარა სუფთა ფუნქციაში, რომელსაც **DB-ის იმპორტი არ
აქვს** — მისი იმპორტი `"use client"` კომპონენტში უსაფრთხოა. `getRadarReferrals`/
`getDefaultReferralFor` (`index.ts`-ში) ტვირთავს `@/lib/db/radar`-ს და ამიტომ მხოლოდ
სერვერზე რჩება; პროვაიდერების დაფა `index.ts`-ის ნაცვლად პირდაპირ
`referrals.ts`-ს აიმპორტებს (იხილეთ ქვემოთ), რათა ბრაუზერის პაკეტში
`better-sqlite3` არ მოხვდეს.

### `GET /api/radar/referrals`

იცავს ზუსტად იმავე შემოწმებების თანმიმდევრობას, რასაც Radar-ის ყველა სხვა მარშრუტი: `RADAR_ENABLED` გამორთულია →
`404` (მოწმდება პირველად, ბაიტობრივად იდენტური ინერცია); არაავტორიზებული → `401`; წინააღმდეგ შემთხვევაში,
მოძველებული მონაცემებისას იწვევს წაკითხვისას სინქრონიზაციას (იხ. ზემოთ), შემდეგ კი აბრუნებს `200`-ს
`{ fixed, campaigns, tier }`-ით — `tier` პირდაპირ (შესაძლოა ახლახან განახლებული)
ქეშის ჩანაწერიდან მოდის და მხოლოდ საინფორმაციო დანიშნულება აქვს (მართავს ქვემოთ მოცემულ UI-ში მსუბუქი
გაუმჯობესებული გეგმის შეთავაზების ტექსტს). არასდროს ახდენს არხის სერვერის პირდაპირ პროქსირებას — თავად მარშრუტის
საწყისი კოდი არ შეიცავს `fetch(` გამოძახებას; ქსელური მოთხოვნა მხოლოდ `syncRadarReferrals()`-ის შიგნით ხდება,
იმავე მხოლოდ ლოკალურ ქეშზე დაფუძნებული პრინციპით, როგორც `/api/radar/catalog`.

### დაფის UI — "უფასო კრედიტების" ჩანართი `/dashboard/radar`-ზე

არსებულ Radar-ის გვერდს (`src/app/(dashboard)/dashboard/radar/page.tsx`) ხელახლა იყენებს,
როგორც მეორე ჩანართს, ახალი მარშრუტის შექმნის ნაცვლად — ნაკლები მარშრუტიზაციის/i18n ზედაპირი ფუნქციისთვის,
რომელიც გვერდის მიერ უკვე მიღებული მონაცემების ვარიაციას წარმოადგენს. ჩართვის შემდეგ ჩანართების ზოლი გთავაზობთ
**კატალოგს** (არსებული ცხრილი) და **უფასო კრედიტებს**:

- ფიქსირებული ბმულები დაჯგუფებულია პროვაიდერის მიხედვით; თითოეული აჩვენებს `requiredAction`-ს (არსებობის შემთხვევაში)
  და რეფერალურ URL-ზე მიმავალ `target="_blank" rel="noopener noreferrer"` ღილაკს.
- კამპანიები იმავეს აჩვენებს, დამატებით კი `validUntil`-საც, როდესაც ის არსებობს.
- როდესაც `campaigns` ცარიელია **და** მოწოდებული დონე არის `community`, UI აჩვენებს
  მოკლე გაუმჯობესებული გეგმის შეთავაზების შენიშვნას ("შეზღუდული დროის კამპანიები მხარდამჭერებისთვის განკუთვნილი დამატებითი შესაძლებლობაა") — ეს **არასდროს**
  მალავს ან ზღუდავს ფიქსირებული ბმულების სიას, რომელიც ყველა დონისთვის სრულად შევსებული რჩება. ეს
  შეთავაზება მხოლოდ მსუბუქი საინფორმაციო ტექსტია და არასდროს წარმოადგენს ბლოკირებას.

### რეფერალური ბმული პროვაიდერის სახელზე (პროვაიდერების დაფა)

`ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
არსებობის შემთხვევაში პროვაიდერის სახელს უკვე აკავშირებდა `providerInfo.website`-თან და მონეტიზებული
ბმულის ერთი პრეცედენტიც არსებობდა: Kimi-ის (Moonshot AI) პარტნიორული ბმულის შენიშვნა
(`providers.kimiPartnerLinkNote` i18n გასაღები). D28 Radar-ის ნაგულისხმევი რეფერალებისთვის ზუსტად იმავე
შეუმჩნეველი შენიშვნის ნიმუშს იყენებს, ახალი გასაღების დამატების ნაცვლად.

დიზაინის მიხედვით სუსტი დაკავშირებულობა:

- `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  არის **სუფთა** ფუნქცია — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — `@/lib/radar`-ზე ან `@/lib/db/*`-ზე ყოველგვარი დამოკიდებულების გარეშე. მთლიანად
  `providerPageUtils.ts` ამ იმპორტებისგან თავისუფალი რჩება (რასაც ამოწმებს
  `tests/unit/provider-header-referral-link.test.ts`).
- `ProviderDetailPageClient.tsx` (`"use client"` კომპონენტი) ერთადერთი ადგილია, სადაც
  Radar-ის მონაცემების მიღება დაშვებულია — `fetch("/api/radar/referrals")`-ის მეშვეობით, იმავე ლოკალური მარშრუტის
  ნიმუშით, რომელსაც თავად Radar-ის დაფის გვერდი იყენებს — და ის ნაგულისხმევ რეფერალს კლიენტის მხარეს
  DB-სგან დამოუკიდებელი `src/lib/radar/referrals.ts`-იდან აღებული `findDefaultReferral()`-ით გამოთვლის.
- როდესაც `RADAR_ENABLED` გამორთულია, მოთხოვნა აბრუნებს 404-ს, `referralUrl` რჩება `null`, ხოლო
  `resolveProviderHeaderLink()` უცვლელად აბრუნებს სტატიკური კატალოგის `website`-ს — პროვაიდერის
  გვერდი ბაიტობრივად იდენტურია იმ მდგომარეობისა, სანამ ეს ფუნქცია იარსებებდა. იგივე შედეგია მაშინაც,
  როდესაც ქეში ჯერ არ არსებობს ან კონკრეტული პროვაიდერისთვის ნაგულისხმევი რეფერალი არ არის.
- როდესაც ნაგულისხმევი რეფერალი გამოიყენება, `ProviderPageHeader` იღებს `isReferralLink`-ს
  და აჩვენებს იმავე შეუმჩნეველ შენიშვნას/მინიშნებას, რასაც Kimi-ის პარტნიორული ბმული (`providers.kimiPartnerLinkNote`
  გასაღების ხელახლა გამოყენებით) — არასდროს იყენებს ახალ, ცალკე ვიზუალურ გაფორმებას.

## როგორ განათავსოთ feed საკუთარ სერვერზე

fork-ს ან საკუთარ სერვერზე განმთავსებელს, რომელსაც კატალოგზე სრული კონტროლი სურს, შეუძლია გაუშვას საკუთარი feed-სერვისი
კლიენტის კოდში ცვლილებების შეტანის გარეშე:

1. უზრუნველყავით `GET /v1/catalog/latest` endpoint, რომელიც აბრუნებს
   `RadarFeedSchema`-ს (`src/lib/radar/feedSchema.ts`) შესაბამის JSON body-ს — ზედა დონის `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks` და `totals`. გაითვალისწინეთ `x-omniroute-radar-schema: 2`; გარდამავალ პერიოდთან თავსებადმა სერვერმა
   მის გარეშე მიღებული მოთხოვნებისთვის ნაგულისხმევად ცალკე ხელმოწერილი v1 artifact უნდა დააბრუნოს.
2. პასუხის ზუსტ byte-ებს ხელი მოაწერეთ Ed25519 key pair-ით და base64
   signature დააბრუნეთ `x-omniroute-feed-signature` response header-ში.
3. `RADAR_FEED_URL`-ს მიანიჭეთ ახალი base URL, ხოლო `RADAR_FEED_PUBKEY`-ს — შესაბამისი
   public key (base64-DER SPKI ან PEM) — იხილეთ
   [environment variable-ების ცნობარი](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting).
4. ჩართეთ `RADAR_ENABLED` და მონაწილეობაზე თანხმობა გამოხატეთ `POST /api/radar/settings`-ის მეშვეობით
   (`{ optIn: true }`).

კოდში სხვა ცვლილებები საჭირო არ არის — `verifyFeedBytes()` override-ს
ავტომატურად იყენებს (`getFeedPublicKeys()` ფაილში `src/lib/radar/pinnedKeys.ts`), ხოლო version-ების
შედარება, schema-ს ვალიდაცია და გაერთიანების წესები საკუთარ სერვერზე განთავსებულ
feed-ზეც იდენტურად ვრცელდება.

Referral link-ები (იხილეთ ზემოთ [Referral link-ები (უფასო კრედიტები)](#referral-links-free-credits))
ცალკე, არასავალდებულო artifact-ია: fork, რომელიც მხოლოდ `/v1/catalog/latest`-ს ემსახურება,
მაინც სრულად მუშაობს — `/v1/referrals/latest`-დან მიღებული `404`-ის შემთხვევაში
`syncRadarReferrals()` უსაფრთხოდ გადადის `{ status: "error" }` მდგომარეობაში, cache კი უბრალოდ ცარიელი რჩება, ამიტომ
`GET /api/radar/referrals` კვლავ აბრუნებს `{ fixed: [], campaigns: [], tier: null }`-ს
გვერდის დანარჩენი ნაწილის მუშაობის შეფერხების ნაცვლად. Referral link-ების შესათავაზებლადაც უზრუნველყავით
`GET /v1/referrals/latest`, რომელიც აკმაყოფილებს `RadarReferralsFeedSchema`-ს
(`src/lib/radar/referralsFeedSchema.ts`), და მას ხელი მოაწერეთ იმავე Ed25519 key pair-ით, რომლითაც
კატალოგის feed-ს აწერთ ხელს.

Supporter-ებისთვის განკუთვნილი შეთავაზებები კიდევ ერთი არასავალდებულო artifact-ია. მათ მოსაწოდებლად დანერგეთ
`GET /v1/offers/latest` დახურული `RadarOffersFeedSchema`-ით
(`src/lib/radar/offersFeedSchema.ts`), მოითხოვეთ მოქმედი entitlement, დააბრუნეთ
`x-omniroute-feed-tier: live` და ზუსტ byte-ებს ხელი იმავე key-ით მოაწერეთ. fork-ში ამ
endpoint-ის გამოტოვება კატალოგისა და referral-ების ქცევას უცვლელად ტოვებს; შეთავაზებების განახლება მონაცემების დაკარგვის გარეშე ვერ სრულდება და
ბოლო ვალიდირებული ლოკალური შეთავაზებების cache ხელმისაწვდომი რჩება.

Intel-იც იმავე პრინციპით არასავალდებულოა. საკუთარ სერვერზე განმთავსებელს შეუძლია უზრუნველყოს `GET /v1/intel/latest`
`RadarIntelFeedSchema`-ს (`src/lib/radar/intelFeedSchema.ts`) გამოყენებით, მოითხოვოს მოქმედი entitlement, დააბრუნოს
`x-omniroute-feed-tier: live` და ზუსტ byte-ებს ხელი საზიარო Ed25519 key-ით მოაწეროს. ამ
endpoint-ის გამოტოვება კატალოგს, referral-ებსა და შეთავაზებებს უცვლელად ტოვებს; Intel-ის განახლებისას შენარჩუნდება ბოლო ვალიდირებული
ლოკალური snapshot.
