`open-sse/config/providerPluginManifest.ts` განსაზღვრავს JSON-თან თავსებადი პროვაიდერის
პლაგინის კონტრაქტს. `open-sse/config/providerPluginManifestRegistry.ts` ამ
კონტრაქტს აკავშირებს მიმდინარე პროვაიდერების რეესტრთან ისეთი sidecar-ებისთვის, როგორებიცაა Bifrost,
CLIProxyAPI ან მომავალი Go/Rust როუტერი. TypeScript-ის რეესტრი კვლავ რჩება
ჭეშმარიტების წყაროდ, თუმცა sidecar-ებს შეუძლიათ გამოიყენონ მანიფესტი
executor-ის კოდის, OAuth-ის ნაგულისხმევი პარამეტრების, სათაურების ან პროცესის გარემოს მდგომარეობის იმპორტის გარეშე.

იგივე მანიფესტი ხელმისაწვდომია HTTP-ითაც მისამართზე
`GET /api/v1/provider-plugin-manifest` იმ sidecar-ებისთვის, რომლებიც პროცესის გარეთ მუშაობენ.

OmniRoute ამ URL-ს Bifrost-სა და CLIProxyAPI-ს გადასცემს
`X-OmniRoute-Provider-Manifest-Url` მოთხოვნის სათაურის მეშვეობით. დააყენეთ
`OMNIROUTE_PROVIDER_MANIFEST_URL`, როდესაც sidecar-ს ადგილობრივი მოთხოვნის წყაროს ნაცვლად
საჯარო ან კონტეინერის ქსელის URL სჭირდება.

## მანიფესტის განახლება

HTTP endpoint აბრუნებს `Cache-Control: public, max-age=60`-სა და ძლიერ
`ETag`-ს. sidecar-მა უნდა შეინარჩუნოს ბოლო ვალიდირებული მანიფესტი და განახლებისას მისი ETag
გაგზავნოს `If-None-Match`-ში. `304 Not Modified` პასუხს სხეული არ აქვს;
sidecar ინარჩუნებს ქეშირებულ მანიფესტს. თუ ვალიდირებული ქეშირებული მანიფესტი არ არსებობს,
sidecar-მა `304`-ის მიღების ნაცვლად უპირობო მოთხოვნა უნდა გაგზავნოს.

## მიზანი

პროვაიდერის მეტამონაცემები გადავიდეს პლაგინის კონტრაქტისკენ, რათა მოთხოვნების სწრაფი დამუშავების გზა
საბოლოოდ უფრო დაბალი დაყოვნების მქონე sidecar-მა მართოს, ხოლო OmniRoute-მა შეინარჩუნოს
TypeScript-ის მარშრუტი, როგორც პოლიტიკის საკონტროლო შრე და სათადარიგო გზა. მანიფესტი დანამატურია:
თავისთავად იგი მოთხოვნების მარშრუტიზაციას არ ცვლის.

## კონტრაქტი

მანიფესტი შეიცავს:

- პროვაიდერის id-სა და alias-ს
- upstream ფორმატსა და executor-ის სახელს
- ავტორიზაციის ტიპს, ავტორიზაციის სათაურსა და არასავალდებულო ავტორიზაციის პრეფიქსს
- endpoint-ის სტატიკურ მეტამონაცემებს
- sidecar-ისთვის ვარგისიანობასა და ცხად მიზეზებს, როდესაც პროვაიდერი TS-ზე უნდა დარჩეს
- JSON-თან თავსებად მოდელის მეტამონაცემებს, როგორებიცაა კონტექსტის სიგრძე, ხედვის/მსჯელობის ნიშნები და
  მხარდაუჭერელი პარამეტრები
- შესაძლებლობების ტეგებს, მათ შორის `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` და `usage-supported`

მანიფესტი განზრახ არ შეიცავს:

- OAuth კლიენტის საიდუმლოებებსა და საიდუმლო მნიშვნელობების ნაგულისხმევ მნიშვნელობებს
- შესრულების გარემოს დინამიკურ განსაზღვრას
- მოთხოვნის სათაურებსა და საჯარო ავტორიზაციის მონაცემების დამხმარე ფუნქციებს
- დინამიკურ URL-შემქმნელებს
- executor ფუნქციებს
- სესიების პულის შიდა დეტალებს

## შესაძლებლობების ტეგები

`capabilities` არის რეესტრის ჩანაწერიდან მიღებული ტეგების დახარისხებული მასივი. ინტეგრატორებმა
იგი უნდა აღიქვან, როგორც მანქანურად წაკითხვადი პასუხი კითხვაზე „რისი გაკეთება შეუძლია ამ პროვაიდერს“,
TypeScript-ის წყაროების ხელახლა წაკითხვის ნაცვლად.

| ტეგი                 | მნიშვნელობა                                                                     |
| -------------------- | ------------------------------------------------------------------------------- |
| `apikey`             | იღებს API გასაღებს (`authType` არის `apikey` ან `optional`).                    |
| `oauth`              | იყენებს OAuth-ის ან სესიის ნაკადს.                                              |
| `responses`          | აქვეყნებს OpenAI Responses-API-ის საბაზისო URL-ს.                               |
| `passthrough-models` | მოდელებს სტატიკური კატალოგის ნაცვლად პირდაპირ upstream-იდან აწვდის.             |
| `custom-executor`    | იყენებს არანაგულისხმევ executor-ს, ამიტომ TypeScript-ის გზაზე რჩება.            |
| `sidecar-candidate`  | ასახავს `sidecar.eligible`-ს — უსაფრთხოა sidecar-ში იმპორტისთვის განსახილველად. |
| `usage-fetch`        | აქვს მიერთებული მოხმარების ან კვოტის მიმღები (`getUsageForProvider`).           |
| `usage-supported`    | მოხმარების API იღებს ამ პროვაიდერს (`isSupportedUsageConnection`).              |

`usage-fetch` მხოლოდ აღმოჩენისთვისაა. ის მიუთითებს, რომ OmniRoute-მა იცის, როგორ წაიკითხოს პროვაიდერის
მოხმარება; იგი არ ააქტიურებს მონაცემების მიღებას, არ ცვლის კვოტის სემანტიკას და არ ნიშნავს, რომ
Dashboard-ის კვოტის ვიჯეტი ამ პროვაიდერისთვის ჩართულია — ამ ვიჯეტს ცალკე აკონტროლებს
`USAGE_SUPPORTED_PROVIDERS`. ჭეშმარიტების წყაროა `USAGE_FETCHER_PROVIDERS` ფაილში
`open-sse/services/usage/fetcherProviders.ts`.

ეს სია გასაღებებად იყენებს სტრიქონებს, რომლებსაც მოხმარების დისპეტჩერი იღებს, ამიტომ მასში შერეულია კანონიკური id-ები
და alias-ები და იგი მონიშნული პროვაიდერების რაოდენობაზე ოდნავ გრძელია: ჩანაწერებს, რომლებიც
მანიფესტის რეესტრში ჩატის პროვაიდერები არ არიან (მაგალითად, `firecrawl` საძიებო პროვაიდერი
და `amazon-q` ACP პროვაიდერი), მოსანიშნი მანიფესტის ჩანაწერი არ აქვთ.

`usage-supported` პასუხობს, იღებენ თუ არა სერვერისა და Dashboard-ის მოხმარების მარშრუტები ამ პროვაიდერის
კავშირს. იგი ასახავს `isSupportedUsageConnection()`-სა (`src/lib/usage/providerLimits.ts`)
და `supportsProviderQuota()`-ს (`src/shared/utils/providerQuotaVisibility.ts`), რომელთაც ორივეს
`USAGE_SUPPORTED_PROVIDERS` აკონტროლებს (`open-sse/services/usage/supportedProviders.ts`). განსხვავებით
`usage-fetch`-ისგან, იგი მხოლოდ პროვაიდერის id-ზე გამოიცემა — შესრულების დროის შემოწმება იყენებს
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)`-ს alias-ის გარდაქმნის გარეშე, ამიტომ მანიფესტი
იმავე წესს ინარჩუნებს. ამ ორ ტეგს განსხვავებული მოცვის არე აქვს: 3 პროვაიდერს აქვს მხოლოდ
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), ხოლო 1-ს — მხოლოდ
`usage-supported` (`xiaomi-mimo-token-plan`), ამიტომ ერთი მეორეს არ გულისხმობს.

## Sidecar-ის გამოყენება

Sidecar-ებმა `sidecar.eligible` უნდა განიხილონ, როგორც კანდიდატის კონსერვატიული სიგნალი და არა როგორც მარშრუტიზაციის უპირობო გადაწყვეტილება. იმპორტის პირველი სამიზნე უნდა იყოს API-გასაღებზე დაფუძნებული, სტატიკური endpoint-ის მქონე პროვაიდერები, რომლებიც ნაგულისხმევ executor-ს იყენებენ. პროვაიდერები, რომლებსაც აქვთ მორგებული ვებ-executor-ები, OAuth/სესიის ნაკადები, დინამიკური URL-ის შემქმნელები ან pool-ის კონფიგურაცია, TypeScript-ის fallback-გზაზე უნდა დარჩნენ მანამ, სანამ Sidecar არ დანერგავს ეკვივალენტურ ქცევას და ტელემეტრია პარიტეტს არ დაადასტურებს.

მიგრაციის შემოთავაზებული ეტაპები:

1. TS-რეესტრიდან პროვაიდერის plugin-მანიფესტის გენერირება და ვალიდაცია.
2. Bifrost-ის ან CLIProxyAPI-ისთვის API-გასაღების/სტატიკური კონფიგურაციის მქონე პროვაიდერების მანიფესტის იმპორტის შესაძლებლობის დამატება.
3. შესაბამისი პროვაიდერების Sidecar-ის გავლით მარშრუტიზაცია `OMNIROUTE_RELAY_BACKEND`-ის უკან, TS-ის fallback-ის ჩართული მდგომარეობის შენარჩუნებით.
4. პროვაიდერების დაწინაურება მხოლოდ მაშინ, როდესაც წარმატების მაჩვენებელი, p99 დაყოვნება, სტრიმინგის ქცევა და მხარდაუჭერელი პარამეტრების დამუშავება TS-გზას ემთხვევა.
5. მორგებული executor-ებისთვის Sidecar-ის ნატიური plugin-ების დამატება — ერთ ჯერზე პროვაიდერთა ერთი ოჯახისთვის.
