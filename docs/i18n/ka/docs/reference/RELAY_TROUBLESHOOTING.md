რელეები (Vercel, Deno, Cloudflare) serverless ბექენდზე წყვეტენ upstream კავშირს, რათა OmniRoute-მა ტრაფიკი სტაბილური რეგიონიდან გააგზავნოს, ხოლო პროვაიდერის API გასაღები სერვერის მხარეს შეინახოს. ამ დოკუმენტში განხილულია ორი შეფერხების რეჟიმი, რომლებსაც ოპერატორები საწარმოო გარემოში აწყდებიან, და აღდგენის გზები, რომლებსაც OmniRoute თითოეული მათგანისთვის უზრუნველყოფს.

## როგორ ინახება რელეს ავთენტიფიკაცია

როდესაც რელეს **პარამეტრები → პროქსების პული → რელეს განთავსება** მენიუდან განათავსებთ, განთავსების პროცესი რელეს ავთენტიფიკაციის ტოკენს პროქსის `notes` JSON ველში ინახავს:

- თუ `STORAGE_ENCRYPTION_KEY` დაყენებულია, ტოკენი ჩაიწერება როგორც `relayAuthEnc`
  (AES-ით დაშიფრული შენახვისას).
- წინააღმდეგ შემთხვევაში, ის ღია ტექსტის სახით ჩაიწერება როგორც `relayAuth`.

მოთხოვნის დროს `extractRelayAuth(notes)` აბრუნებს წარმოდგენილი ფორმებიდან ერთ-ერთს, ამიტომ რელე მუშაობას გადატვირთვების შემდეგაც აგრძელებს.

## შეფერხების რეჟიმი 1 — გასაღების როტაციის შემდეგ ტოკენის გაშიფვრა შეუძლებელია

**სიმპტომი:** რელეები, რომლებიც მანამდე მუშაობდნენ, ახლა upstream `401`/ავთენტიფიკაციის შეცდომებს აბრუნებენ გარემოში ან საიდუმლოებების მმართველში `STORAGE_ENCRYPTION_KEY`-ის როტაციის შემდეგ. შენახული `relayAuthEnc` ბლობის გაშიფვრა აღარ ხერხდება, ამიტომ `extractRelayAuth` ცარიელ სტრიქონს აბრუნებს და რელე ავთენტიფიკაციის მონაცემებს არ აგზავნის.

**აღდგენა — ადგილზე შეკეთება (ხელახლა განთავსების გარეშე):**

1. გახსენით **პარამეტრები → პროქსების პული**.
2. რელეს სტრიქონებზე, რომლებშიც ავთენტიფიკაცია აკლია, ნაჩვენებია ყვითელი `auth missing` ნიშანი და
   **შეკეთება** ღილაკი.
3. დააწკაპუნეთ **შეკეთება**. OmniRoute გამოიძახებს
   `POST /api/settings/proxies/[id]/repair-relay`-ს, რომელიც:
   - შიფრავს `relayAuthEnc`-ს **მიმდინარე** გასაღებით,
   - ღია ტექსტის `relayAuth`-ს კვლავ წერს `notes`-ში,
   - აბრუნებს `{ repaired: true, mode: "recovered" }`-ს.

რელე განაგრძობს მომსახურებას განთავსების ავტორიზაციის მონაცემების ხელახლა შეყვანის გარეშე.

ეს მუშაობს მხოლოდ მაშინ, თუ მიმდინარე `STORAGE_ENCRYPTION_KEY`-ს კვლავ შეუძლია ბლობის გაშიფვრა. თუ გასაღები მიგრაციის **გარეშე** შეცვალეთ, ბლობის აღდგენა შეუძლებელია.

## შეფერხების რეჟიმი 2 — აღუდგენელი ტოკენი (ძველი გასაღები აღარ არსებობს)

**სიმპტომი:** დააწკაპუნეთ **შეკეთება** და მიიღეთ
`{ repaired: false, mode: "redeploy", status: 409 }`.

**აღდგენა — ხელახლა განთავსება:**

შენახული ტოკენის აღდგენა მიმდინარე გასაღებით შეუძლებელია. ხელახლა განათავსეთ რელე იმავე მოდალური ფანჯრიდან, რომელიც თავდაპირველად გამოიყენეთ (**რელეს განთავსება** მენიუ → Vercel / Deno
/ Cloudflare). განთავსების პროცესი ჩაწერს ახალ ტოკენს (მიმდინარე გასაღებით დაშიფრულს) და სტრიქონიდან `auth missing` ნიშანი გაქრება.

მომხმარებლის ინტერფეისში **შეკეთება** ღილაკი თავად გახსნის ხელახლა განთავსების მოდალურ ფანჯარას, როდესაც ტოკენის აღდგენა შეუძლებელია, ამიტომ მისი ხელით მოძებნა არ დაგჭირდებათ.

## შეფერხების რეჟიმი 3 — რელე ხელმისაწვდომია, მაგრამ გაუმართავია

**სიმპტომი:** პროქსის ტესტი (`speed` ღილაკი) აჩვენებს, რომ რელე მუშაობს, თუმცა მოთხოვნები პერიოდულად მაინც ვერ სრულდება.

შეამოწმეთ რელეს შესახებ ინფორმაციის სათაურები, რომლებსაც OmniRoute-ის ავტომატური სატესტო მოთხოვნა აბრუნებს (იხილეთ **პარამეტრები → პროქსების პული** და `relayTested` / `relayAlive` მრიცხველები):

- `x-relay-url` — რომელმა რელეს ბექენდმა უპასუხა.
- `x-relay-mode` — `ts` | `bifrost` | `auto` ამ მოთხოვნისთვის.
- `x-relay-attempts` — წარმატებამდე რელეს რამდენი გადასვლა იქნა ნაცადი.
- `x-relay-fallback` — `true`, როდესაც მოთხოვნა სასურველი ბექენდიდან TypeScript რელეზე გადაერთო.

`x-relay-fallback`-ის მაღალი მაჩვენებელი და `relayAlive`-ის დაბალი მნიშვნელობა ნიშნავს, რომ sidecar ბექენდი გაუმართავია და ის ან უნდა შეაკეთოთ, ან რელეს ბექენდის სტრატეგია `ts`-ზე გადართოთ (იხილეთ `RELAY_BACKEND_STRATEGY.md`).

## API ცნობარი

| მეთოდი | გზა                                       | სხეული                  | წარმატება                                                                                                                                                       | წარუმატებლობა                                                                                |
| ------ | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }`, როდესაც მნიშვნელობა ხელახლა წარმოებულია; `200 { repaired: false, mode: "noop" }`, როდესაც ღია ტექსტი უკვე არსებობს | `409 { mode: "redeploy" }` აღდგენა შეუძლებელია; `400` არ არის რელეს ტიპი; `404` ვერ მოიძებნა |

სიის მარშრუტი `GET /api/settings/proxies` თითოეულ ელემენტს ამატებს საიდუმლო მონაცემების არშემცველ `relayInfo: { isRelay, authMissing, repairMode }`-ს, რათა მართვის პანელმა შეკეთების შესაძლებლობა ტოკენის გამჟღავნების გარეშე აჩვენოს.
