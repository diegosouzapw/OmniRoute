OmniRoute-ის შეკუმშვა აგებულია ძრავის კონტრაქტების ირგვლივ. რეჟიმს შეუძლია უშუალოდ გაუშვას ერთი ძრავა
(`caveman` ან `rtk`) ან დეტერმინისტული, თანმიმდევრული კონვეიერი, რომელიც რამდენიმე ძრავას განსაზღვრული რიგითობით ასრულებს.

## რეჟიმები

| რეჟიმი       | ძრავის გზა                                    | განკუთვნილი შეყვანა                                                 |
| ------------ | --------------------------------------------- | ------------------------------------------------------------------- |
| `off`        | არცერთი                                       | მოთხოვნის ზუსტი სახით შენარჩუნება                                   |
| `lite`       | Caveman-ის მსუბუქი დამხმარეები                | დაბალი რისკის მქონე, მუდმივად ჩართული გასუფთავება                   |
| `standard`   | Caveman                                       | ბუნებრივ ენაზე დაწერილი მოთხოვნის შემოკლება                         |
| `aggressive` | Caveman + ისტორიის/ხელსაწყოების შემაჯამებლები | ხანგრძლივი ჩატის სესიები                                            |
| `ultra`      | Caveman + შემცირების დამხმარეები              | კონტექსტის ლიმიტის ამოწურვის შემდეგ აღდგენა                         |
| `rtk`        | RTK                                           | ტერმინალის, გარსის, აგების, ტესტირებისა და git-ის გამოტანილი შედეგი |
| `omniglyph`  | OmniGlyph                                     | კონტექსტი გამოსახულების სახით, პროვაიდერის ნატიურ არხზე             |
| `stacked`    | კონვეიერი, ნაგულისხმევად `rtk -> caveman`     | ხელსაწყოების შერეული ჟურნალები და პროზა, მაქსიმალური ეკონომია       |

### OmniGlyph-ის შეკუმშვის პროფილები

`omniglyph` ძრავა (პაკეტი `omniglyph`, 1.4.0+) იღებს სახელდებულ სემანტიკურ პროფილს, რომელიც
გლობალურად განისაზღვრება შეკუმშვის პარამეტრებში `omniglyph.profile`-ის მეშვეობით, ან თითოეული ნაბიჯისთვის —
თანმიმდევრული კონვეიერის ნაბიჯის კონფიგურაციით:

| პროფილი       | საზღვარი                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `aggressive`  | ნაგულისხმევი. გამოქვეყნებული შედეგების გასაზომად გამოყენებული პოლიტიკა — სისტემის, ხელსაწყოების დოკუმენტაციისა და მკვრივი ისტორიის გამოსახულებებად გარდაქმნა |
| `balanced`    | მიმდინარე მდგომარეობას ნატიურ ფორმატში ინარჩუნებს, იცავს ბოლო 8 სვლას და კუმშავს უფრო ძველ, დახურულ ისტორიას                                                 |
| `coding-safe` | უფლებამოსილებას, ხელსაწყოების სქემებსა და ხელსაწყოების მიმდინარე გამოტანილ შედეგს ნატიურ ფორმატში ინარჩუნებს და იცავს ბოლო 12 სვლას                          |
| `passthrough` | მარშრუტიზაციას გარდაქმნის გარეშე ასრულებს; ძრავა გამოტოვებულია                                                                                               |

პროფილი არის **ზედა ზღვარი და არა ქვედა ზღვარი**: პაკეტში არსებული `mergeCompressionProfileOptions`
არ აძლევს გამომძახებელს უფლებას, პარამეტრის გადაფარვით ხელახლა გახსნას პროფილის მიერ დახურული დანაკარგიანი არხი, ამიტომ თითოეული ნაბიჯისთვის მითითებული
`preserveSystemPrompt: false` ვერ ჩართავს სისტემის შეკუმშვას `coding-safe` პროფილში.

ამ კოდურ ბაზაზე გაზომვის მიხედვით: `coding-safe` და `balanced` ზრდიან `minCompressChars`-ს მის
მაქსიმალურ მნიშვნელობამდე და სისტემას, ხელსაწყოების სქემებსა და ხელსაწყოების შედეგებს ნატიურ ფორმატში ინარჩუნებენ, ამიტომ სესია, რომელსაც
ისტორია ჯერ არ დაუგროვებია, ჩერდება `below_min_chars`-ზე და ძრავა არაფერს გარდაქმნის. სწორედ
ამიტომ არის ნაგულისხმევი პროფილი `aggressive` და არა ყველაზე უსაფრთხო პროფილი.

პაკეტი საკუთარი მოდელის მოქმედების არესა და პროფილს გარემოს კონფიგურაციიდან განსაზღვრავს.
OmniRoute გადაწყვეტილების მიღებას არასოდეს გადასცემს სხვას: ადაპტერი მოდელის ფილტრს პაკეტის
ყველაზე შემზღუდველ მოქმედების არეზე აფიქსირებს, ამიტომ მასპინძელი გარემოს პარამეტრებს მხოლოდ დაშვებული მოდელების სიის შევიწროება შეუძლია და ვერასოდეს
გააფართოებს მას OmniRoute-ის გაზომილი შედეგებით დადგენილ საზღვრებს მიღმა.

## ძრავების რეესტრი

რეესტრი მდებარეობს `open-sse/services/compression/engines/registry.ts`-ში. ძრავები საერთო
კონტრაქტს უზრუნველყოფენ:

- `id`: ძრავის სტაბილური იდენტიფიკატორი, როგორიცაა `caveman` ან `rtk`
- `apply(text, config)`: შესრულების მოძველებული გზა, რომელსაც მრავალშრიანი კონვეიერები იყენებენ
- `compress(input, config)`: შესრულების ძირითადი გზა, რომელიც აბრუნებს ტექსტსა და სტატისტიკას
- `getConfigSchema()`: აბრუნებს მართებული კონფიგურაციის JSON-Schema-ს მსგავს სტრუქტურას
- `validateConfig(config)`: აბრუნებს `{ valid, errors[] }`-ს

რეგისტრაცია იყენებს `registerCompressionEngine(engine)`-ს (ან `registerEngine`-ს გაფართოებული შემთხვევებისთვის),
რომელიც მიღებამდე იძახებს `assertValidEngine()`-სა და `validateConfig(defaultConfig)`-ს.
ძრავის შესრულების დროს წასაშლელად გამოიყენეთ `unregisterCompressionEngine(id)`.

`strategySelector.ts` შეკუმშვის დაწყებამდე არეგისტრირებს ჩაშენებულ ძრავებს. ეს საშუალებას აძლევს წინასწარ დათვალიერებას,
შესრულებისას შეკუმშვას, მრავალშრიან რეჟიმს, ტესტებსა და მომავალ ძრავებს, გამოიყენონ შესრულების ერთი და იგივე გზა.

### MCP-ის აღწერის შეკუმშვა (დაკავშირებული)

ცალკე რეესტრი რეესტრის დონეზე კუმშავს MCP ინსტრუმენტების აღწერის მეტამონაცემებს — იხილეთ
`open-sse/mcp-server/descriptionCompressor.ts` და [MCP-SERVER.md](../frameworks/MCP-SERVER.md). ის ხელახლა იყენებს
Caveman-ის წესებს, თუმცა მუშაობს ინსტრუმენტების მეტამონაცემებზე და არა მოთხოვნის სასარგებლო დატვირთვებზე.

### დამატებითი ჩაშენებული ძრავები

Caveman-ის, RTK-ისა და LLMLingua-2-ის გარდა, რეესტრი მოიცავს რამდენიმე სპეციალიზებულ უდანაკარგო /
სტრუქტურულ ძრავას (რომლებსაც იყენებენ მრავალშრიანი კონვეიერები, სათამაშო გარემო და ტესტები):

| ძრავა         | Id              | რას აკეთებს                                                                                                                                                                                                   |
| ------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CCR           | `ccr`           | Content-Compress-Retrieve (H4): დიდ, უწყვეტ ტექსტურ ბლოკებს ანაცვლებს შიგთავსის მიხედვით მისამართებად გარდაქმნილი ბმულებით, რათა განმეორებადი/დიდი ბლოკები ერთხელ გაიგზავნოს და შემდეგ მათზე მითითება მოხდეს. |
| headroom      | `headroom`      | SmartCrusher (H3 + N5): ერთგვაროვანი JSON-მასივის სასარგებლო დატვირთვების უდანაკარგო ცხრილური შეკუმშვა სვეტურ `[N rows]` ფორმაში.                                                                             |
| ionizer       | `ionizer`       | ძალიან დიდი ერთგვაროვანი ბლოკებიდან საწყისი/შუა/ბოლო სტრიქონების შერჩევა, გამოტოვებული შუა ნაწილის CCR-ის შიგთავსის მიხედვით მისამართებად გარდაქმნილ ბმულად შენახვით.                                         |
| session-dedup | `session-dedup` | სვლებს შორის შიგთავსის მიხედვით მისამართებად გარდაქმნილი დუბლიკატების მოცილება (TokenMizer-ით შთაგონებული): გამოტოვებს ტექსტს, რომელიც იმავე სესიის წინა სვლებში უკვე გამოჩნდა.                               |

**CCR-ის მიღების პროტოკოლის ინსტრუქცია (#8033):** როდესაც CCR პირველად ანაცვლებს ≥1 ბლოკს
მოთხოვნაში, ძრავა დასაწყისში ამატებს ერთ, იდემპოტენტურ `system` შეტყობინებას (რომელიც იწყება
`[CCR protocol]` სენტინელით), რათა გამომძახებელს ასწავლოს მარკერის → ინსტრუმენტის კონტრაქტი: რას ნიშნავს
`[CCR retrieve hash=<24hex> chars=N]` მარკერი, რომ ჰეში სიტყვასიტყვით უნდა დაკოპირდეს
(ყველა 24 თექვსმეტობითი სიმბოლო — არასწორად დაკოპირებული ჰეშები, სავარაუდოდ, "block not found"
შეცდომების მიზეზია) და რომ `[dedup:ref sha=...]` მარკერი ნიშნავს „მოძებნე ისტორიაში“ და არა „გამოიძახე
ინსტრუმენტი“. შენიშვნა ემატება **მხოლოდ მაშინ, როდესაც გამომძახებლის მიერ გამოცხადებული `tools[]` ადასტურებს, რომ მას
ნამდვილად შეუძლია `omniroute_ccr_retrieve`-თან წვდომა** (`callerSupportsCcrRetrieve()` ფუნქცია
`open-sse/services/compression/engines/ccr/protocolInstruction.ts`-ში) — უბრალო
OpenAI-თან თავსებადი გამომძახებელი, რომელსაც ეს ინსტრუმენტი არ აქვს, არასოდეს მიიღებს ინსტრუქციას, გამოიძახოს ის,
რაზეც წვდომა არ გააჩნია. იდემპოტენტურობა უზრუნველყოფილია შეტყობინებების ისტორიაში სენტინელის
მოძებნით მის დამატებამდე, ამიტომ მრავალსვლიანი მოთხოვნები (რომლებიც წინა შეტყობინებებს ხელახლა გადასცემენ)
ყოველ სვლაზე შენიშვნის ახალ ასლს არ ამატებენ.

## Caveman

Caveman-ის რეჟიმი ორიენტირებულია ჩვეულებრივი პროზის სემანტიკურ შეკუმშვაზე:

- ინარჩუნებს კოდის ბლოკებს, URL-ებს, JSON-ს, ბილიკებსა და სტრუქტურირებულ მონაცემებს
- შლის ზედმეტ ტექსტს, გაურკვევლობის გამომხატველ ფრაზებს, განმეორებით კონტექსტსა და მრავალსიტყვიან დამაკავშირებელ ფორმულირებებს
- მხარს უჭერს ენის გათვალისწინებით შედგენილ ფაილური წესების ნაკრებებს `open-sse/services/compression/rules/`-ში
- კვლავ ხელმისაწვდომია ძველი `standard`, `aggressive` და `ultra` რეჟიმების მეშვეობით

მართვის პანელში მისი მდებარეობაა `Dashboard -> Context & Cache -> Caveman`.

Caveman-ის საწყისი პროექტის მონაცემებით, გამომავალი ტოკენების რაოდენობა მცირდება `~75%`-ით, საორიენტაციო ტესტებში გამომავალი მონაცემების საშუალო ეკონომია არის `65%`,
`22-87%` დიაპაზონით, ხოლო შემავალი მონაცემების შეკუმშვის მაჩვენებელი — `~46%`. OmniRoute იყენებს Caveman-ის შემავალი მხარის
მაჩვენებელს მოთხოვნის/კონტექსტის კომბინირებული ეკონომიის დოკუმენტირებისას; Caveman-ის გამომავალი რეჟიმი კვლავ
პასუხის ქცევის ცალკე ფუნქციაა.

## RTK

RTK რეჟიმი ორიენტირებულია ბრძანებებისა და ხელსაწყოების გამომავალ მონაცემებზე:

- ამოიცნობს გამომავალი მონაცემების ისეთ კლასებს, როგორიცაა `git status`, `git branch`, `git diff`, Vitest/Jest/Pytest,
  Cargo/Go ტესტები, TypeScript/Vite/Webpack აგებები, ESLint, npm აუდიტები/ინსტალაციები, Docker-ის ჟურნალები,
  shell-ის `find`/`grep`, სტეკის ტრასირებები და ზოგადი ჟურნალები
- იყენებს 49 JSON ფილტრს `open-sse/services/compression/engines/rtk/filters/`-დან
- მხარს უჭერს RTK-ის სტილის დეკლარაციულ კონვეიერს: ANSI-ის მოცილებას, ჩანაცვლებას, match-output მოკლე ჩართვას,
  ხაზების მოცილებას/შენარჩუნებას, თითოეული ხაზის შემოკლებას, დასაწყისის/ბოლოს/ხაზების მაქსიმალური რაოდენობის მიხედვით შემოკლებასა და ცარიელი შედეგის შემთხვევაში სარეზერვო მნიშვნელობას
- მხარს უჭერს ნდობით შეზღუდულ პროექტის ფილტრებს `.rtk/filters.json`-ში და გლობალურ ფილტრებს
  `DATA_DIR/rtk/filters.json`-ში
- შლის ANSI თანმიმდევრობებს, პროგრესის ხმაურს, განმეორებით ხაზებსა და უსარგებლო შაბლონურ ტექსტს
- ინარჩუნებს რეაგირებად შეცდომებს, გაფრთხილებებს, შეჯამებებს, შეცვლილ ფაილებსა და საბოლოო კონტექსტს
- სურვილისამებრ შეუძლია შეინარჩუნოს რედაქტირებული ნედლი გამომავალი აღდგენის/გამართვისთვის ავთენტიფიცირებული მართვის
  მარშრუტების მეშვეობით

მართვის პანელში მისი მდებარეობაა `Dashboard -> Context & Cache -> RTK`.

მორგებული ფილტრების, ნდობის, გადამოწმებისა და ნედლი გამომავალი მონაცემების აღდგენის საოპერაციო დეტალები მოცემულია
[`RTK_COMPRESSION.md`](./RTK_COMPRESSION.md)-ში.

RTK-ის საწყისი პროექტის მონაცემებით, ბრძანებების გამომავალი მონაცემების შეკუმშვა `60-90%` ეკონომიას იძლევა. მის README-ში მოცემულ მაგალითში
Claude Code-ის 30-წუთიანი სესია `~118,000` ტოკენიდან `~23,900` ტოკენამდე მცირდება, რაც `79.7%` ეკონომიას ნიშნავს.

## LLMLingua-2 (სემანტიკური შემცირება)

LLMLingua-2-ის რეჟიმი მცირე ONNX ტოკენების კლასიფიკატორის გამოყენებით პროზაზე ახორციელებს **ტოკენების სემანტიკურ შემცირებას**,
რითაც ავსებს წესებზე დაფუძნებულ Caveman და RTK ძრავებს:

- პროზას კუმშავს მხოლოდ არასისტემურ შეტყობინებებში; შემოღობილი კოდის ბლოკები და სხვა შესანარჩუნებელი
  კონსტრუქციები არასოდეს იცვლება
- უშვებს `@atjsh/llmlingua-2` ბეკენდს (ONNX `@huggingface/transformers`-ის მეშვეობით)
  სამუშაო ნაკადში, ამიტომ მოდელის ინფერენცია არასოდეს ბლოკავს მოთხოვნის მოვლენათა ციკლს
- არის **დასტვადი** (`stackPriority` 35): დასტვად კონვეიერში ის სრულდება
  სტრუქტურული ძრავების (CCR, session-dedup, headroom, Caveman) შემდეგ, თუმცა `ultra`-მდე, რადგან
  სემანტიკური შემცირება ყველაზე ეფექტურია უკვე სტრუქტურულად შეკუმშულ ტექსტზე — მაგალითად,
  `rtk -> caveman -> llmlingua`
- **ნებისმიერი შეცდომისას მუშაობას ღიად აგრძელებს** (არარსებული არასავალდებულო დამოკიდებულებები, სამუშაო ნაკადის გაშვება, მოდელის ჩატვირთვა, ინფერენცია
  ან დროის ამოწურვა) → თავდაპირველი ტექსტი უცვლელად ბრუნდება და შეცდომა — არასოდეს

ძრავის მდებარეობაა: `open-sse/services/compression/engines/llmlingua/`. მართვის პანელში მისი მდებარეობაა
`Dashboard -> Context & Cache -> LLMLingua`.

### მოდელები

ნაგულისხმევი მოდელია **TinyBERT** (`atjsh/llmlingua-2-js-tinybert-meetingbank`, ~57 MB,
სწრაფი). უფრო მაღალი სიზუსტის **BERT-base** მოდელი (`Arcoldd/llmlingua4j-bert-base-onnx`,
~710 MB) ხელმისაწვდომია ძრავის კონფიგურაციის `model` ველის მეშვეობით. პირველი გამოძახებისას `@huggingface/transformers`
არჩეულ მოდელს საჭიროებისამებრ HuggingFace Hub-იდან
`${DATA_DIR}/models/llmlingua`-ში ჩამოტვირთავს (`modelStore.ts`); კონფიგურაციაში `modelPath`-ის
გადაფარვა მის ნაცვლად ადგილობრივ ასლზე მიუთითებს (ოფლაინ / ინტერნეტისგან იზოლირებული ინსტალაციებისთვის).

### არასავალდებულო დამოკიდებულებები და მოთხოვნისამებრ ინსტალაცია

შემცირებადი LLMLingua-ს შესრულების გარემოს peer-სტეკი **არასავალდებულოა**. ორი პაკეტი
`package.json`-ში გამოცხადებულია როგორც `optionalDependencies` და საწარმოო აგებისას **გარე დამოკიდებულებებად** რჩება
(`scripts/build/prepublish.ts` მათ პაკეტში არ აერთიანებს):

| პაკეტი               | ვერსია (ფიქსირებული) | შენიშვნები                                        |
| -------------------- | -------------------- | ------------------------------------------------- |
| `@atjsh/llmlingua-2` | `2.0.5`              | შესასვლელი პაკეტი; დანარჩენებს peer-ებად აცხადებს |
| `js-tiktoken`        | `^1.0.20`            | ტოკენიზატორი                                      |

`@huggingface/transformers` ფიქსირებულია `^4.2.0` ვერსიაზე (გაზიარებულია ადგილობრივი ემბედინგების ბილიკთან და
ასევე შეტანილია დამოუკიდებელ პაკეტში); `@atjsh/llmlingua-2@2.0.5` მასთან peer-კავშირშია
`"^3.5.2 || ^4.0.0"` მოთხოვნით, ამიტომ მხარდაჭერილია როგორც Transformers.js v3, ისე v4. 2.0.4 ვერსიიდან
`@atjsh/llmlingua-2`-ს აღარ სჭირდება `@tensorflow/tfjs`, რამაც SLM სტეკიდან ამოიღო მოცულობის ყველაზე დიდი ცალკეული
შემადგენელი (TensorFlow.js). შემცირებად SLM peer-ებად მხოლოდ ზემოთ ჩამოთვლილი ორი პაკეტი რჩება.
სტანდარტული `npm install` (დეველოპერულ გარემოში) არასავალდებულო სტეკს ავტომატურად აყენებს, თუ არასავალდებულო
დამოკიდებულებები გამოტოვებული არ არის.

**რატომ მოთხოვნისამებრ:** npm-ში გამოქვეყნებული პაკეტი, დამოუკიდებელი პაკეტი და Docker-ის იმიჯი
ზომის შესამცირებლად ამ დამოკიდებულებების **გარეშე** ვრცელდება. როდესაც ისინი არ არსებობს, სამუშაო ნაკადის დამოკიდებულებების
შემოწმება (`@atjsh/llmlingua-2`-ის ამოხსნის ცდა `worker.ts`-ში) წარუმატებელია და ძრავა
**უხმაუროდ აგრძელებს მუშაობას** — LLMLingua-ს არჩევა უშედეგო ოპერაციად იქცევა (ტექსტი უცვლელად ბრუნდება და
შეცდომა ჟურნალში არ იწერება). მის გასააქტიურებლად შემცირებულ გარემოში დააყენეთ არასავალდებულო სტეკი:

```bash

npm install @atjsh/llmlingua-2@2.0.5 js-tiktoken
```

`@tensorflow/tfjs`-ის ამოღება (2.0.4+) გამორიცხავს მანამდე დომინანტურ ~800 MB-იან
შემადგენელს — დარჩენილ მოცულობას ქმნის transformers.js + onnxruntime-node-ის შესრულების გარემოები,
ასევე TinyBERT მოდელი (~57 MB), რომელიც პირველი გამოყენებისას ჩამოიტვირთება (არა npm-ის მეშვეობით).

თითოეული გარემოსთვის:

- **Dev / `npm install`** — ავტომატურად ინსტალირდება, თუ არ გადაგიციათ `--omit=optional`
  (ან `--no-optional`). დამატებითი მოქმედება საჭირო არ არის.
- **გლობალური npm (`npm i -g omniroute`) / დამოუკიდებელი ვერსია** — გაუშვით ზემოთ მოცემული ინსტალაციის ბრძანება
  დაინსტალირებული პაკეტის დირექტორიაში, ან ხელახლა დააინსტალირეთ არასავალდებულო დამოკიდებულებების გამოტოვების გარეშე.
- **Docker** — დაამატეთ ინსტალაციის ბრძანება წარმოებული იმიჯის შრეში; გამოქვეყნებული იმიჯი
  განზრახ მინიმალისტურია.
- **VPS (PM2)** — დააინსტალირეთ აპის `node_modules`-ში, შემდეგ კი გადატვირთეთ პროცესი, რათა
  worker-მა gate ხელახლა შეამოწმოს.
- **უშუალო Next standalone (`npm run build` → `.build/next/standalone/server.js`)** —
  standalone trace არ შეიცავს არც worker-ს და არც არასავალდებულო დამოკიდებულებებს, ამიტომ ძრავა შეუმჩნევლად
  გადადის fail-open რეჟიმში. `scripts/build/colocate-standalone.mjs` ხელახლა ამატებს ორივეს (worker esbuild +
  არასავალდებულო დამოკიდებულებების სრულ ნაკრებს standalone ხეში); ყოველი build-ის შემდეგ ის ავტომატურად ეშვება
  `postbuild` npm hook-ის მეშვეობით. იდემპოტენტურია და დამოკიდებულებების არარსებობისას შეცდომას რბილად ამუშავებს.

**შეამოწმეთ, რომ აქტიურია:** LLMLingua-ს არჩევისას რეალური პროზა მართლაც მცირდება (ძრავა
წყვეტს fail-open რეჟიმში გადასვლას), ხოლო პირველი მოთხოვნა იწვევს მოდელის ჩამოტვირთვას
`${DATA_DIR}/models/llmlingua`-ში. gate განზრახ ამოწმებს მხოლოდ `@atjsh/llmlingua-2`-ს —
სხვა peer-ები მხოლოდ ESM-თანაა თავსებადი და მათზე `require.resolve` გამონაკლისს აგდებს მაშინაც კი, როცა ისინი ხელმისაწვდომია — ამიტომ
worker კვლავ fail-open რეჟიმში გადადის, თუ რომელიმე peer ნამდვილად აკლია `import()`-ის შესრულებისას.

## თანმიმდევრული კონვეიერები

თანმიმდევრული რეჟიმი კონვეიერის ნაბიჯებს რიგითობით ასრულებს. ნაგულისხმევი თანმიმდევრობაა:

```txt
rtk -> caveman
```

გამოიყენეთ ეს პროგრამირების აგენტის სესიებისთვის, სადაც მოთხოვნა აერთიანებს ბრძანების გამოტანილ შედეგს ადამიანურ ან ასისტენტის მიერ დაწერილ ტექსტთან. RTK ჯერ ამცირებს ხმაურიან ხელსაწყოთა ჟურნალებს, შემდეგ კი Caveman დარჩენილ ბუნებრივ ენას კუმშავს.

კონვეიერის ნაბიჯები კონფიგურირდება შეკუმშვის პარამეტრებში `stackedPipeline`-ის მეშვეობით ან შეკუმშვის კომბინაციების გამოყენებით.

როდესაც ორივე ძრავა ამცირებს ერთსა და იმავე შესაბამის მონაცემებს, ეკონომია მრავლდება:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## MCP-ის ხელმისაწვდომობის ხის ფილტრი

MCP-ის ხელმისაწვდომობის ხის ჭკვიანი ფილტრი არის შესრულების შემდგომი შეკუმშვის შრე, რომელიც მუშაობს MCP-ის **ხელსაწყოს შედეგებზე** და არა მოთხოვნებზე ან კონტექსტზე. ის განკუთვნილია ისეთი ხელსაწყოების მიერ დაბრუნებული ვრცელი ხელმისაწვდომობის ხისა და ბრაუზერის სნეპშოტის მონაცემებისთვის, როგორებიცაა Playwright, computer-use და ბრაუზერის ავტომატიზაციის MCP სერვერები.

### რას აკეთებს

1. **ხმაურის მოცილება** — შლის ცარიელ ზოგად/ტექსტურ ჩანაწერებს (`- generic:`, `- text: ""`)
2. **მეზობელი ელემენტების შეკუმშვა** — როდესაც ≥ `collapseThreshold` (ნაგულისხმევად 30) მიმდევრობითი სტრიქონი სტრუქტურულად მეორდება, შეკუმშავს მათ პირველ `collapseKeepHead` (ნაგულისხმევად 10) სტრიქონად + რაოდენობის შეჯამებად + ბოლო `collapseKeepTail` (ნაგულისხმევად 5) სტრიქონად
3. **ბმულების შენარჩუნება** — Playwright/computer-use-ისთვის საჭირო `[ref=eXX]` ანკერები არასოდეს იცვლება
4. **მკაცრი შეკვეცა** — თუ შეკუმშვის შემდეგ ტექსტი კვლავ აჭარბებს `maxTextChars`-ს (ნაგულისხმევად 50,000), ის იკვეცება ნავიგაციის მინიშნებით, რათა აგენტმა მუშაობის გაგრძელება შეძლოს

### ძრავის მდებარეობა

```txt
open-sse/services/compression/engines/mcpAccessibility/
  index.ts            ← smartFilterText()-ის შესვლის წერტილი
  collapseRepeated.ts ← მეზობელი ელემენტების შეკუმშვის ალგორითმი
  constants.ts        ← DEFAULT_MCP_ACCESSIBILITY_CONFIG
```

### კონფიგურაცია

იმართება გლობალურ პარამეტრებში `compression.mcpAccessibility`-ით (მიგრაცია 056). ნაგულისხმევი კონფიგურაცია:

```json
{
  "enabled": true,
  "maxTextChars": 50000,
  "collapseThreshold": 30,
  "collapseKeepHead": 10,
  "collapseKeepTail": 5,
  "minLengthToProcess": 2000
}
```

ფილტრი გამოიყენება მხოლოდ იმ ხელსაწყოს შედეგების მონაცემებზე, რომელთა `type` არის `"text"` და რომელთა სიგრძე აჭარბებს `minLengthToProcess`-ს. ის გავლენას არ ახდენს მოთხოვნის შეკუმშვაზე ან მოთხოვნის მონაცემებზე.

### მოსალოდნელი ეკონომია

ბრაუზერის სნეპშოტის ხელსაწყოს შედეგებზე 60–80%, გვერდის სირთულის მიხედვით. შეკუმშვის ალგორითმის სირთულეა O(n) სტრიქონების რაოდენობის მიმართ და ის უმნიშვნელო დაყოვნებას ამატებს.

### ეს ფილტრი ზემოთ მოცემულ შეკუმშვის ძრავებთან შედარებით

| გამშვები         | შეკუმშვის რეჟიმის პარამეტრი | `compression.mcpAccessibility.enabled` |

## შეკუმშვის კომბინაციები

შეკუმშვის კომბინაციები არის სახელდებული შეკუმშვის პროფილები, რომლებიც შეიძლება მიენიჭოს მარშრუტიზაციის კომბინაციებს:

- `compression_combos`: ინახავს რეჟიმს, კონვეიერს, RTK-ის კონფიგურაციას, ენის კონფიგურაციასა და ნაგულისხმევი მნიშვნელობის მარკერს
- `compression_combo_assignments`: შეკუმშვის კომბინაციას მარშრუტიზაციის კომბინაციასთან აკავშირებს
- შესრულების დროის ინტეგრაცია მინიჭებულ შეკუმშვის კომბინაციას ზოგადი კომბინაციის გადაფარვებამდე განსაზღვრავს
- ანალიტიკა მოიცავს `compression_combo_id`-სა და `engine`-ს

მართვის პანელის მდებარეობა: `მართვის პანელი -> კონტექსტი და კეში -> შეკუმშვის კომბინაციები`.

პრეფიქსები და ა.შ.).

- პარამეტრების ველი: `exclusions?: string[]` შეკუმშვის გლობალურ კონფიგურაციაში
  (`GET`/`PUT /api/settings/compression`), რომელიც ინახება არსებული `key_value` შეკუმშვის
  სახელთა სივრცის მეშვეობით (`src/lib/db/compression.ts`) — ახალი ცხრილი საჭირო არ არის.
- მართვის პანელის ჩანართი: **მართვის პანელი → შეკუმშვა → გამონაკლისები**
  (`/dashboard/compression/exclusions`).
- ნიმუშის სინტაქსი: `*` ერთადერთი ველური ბარათია. ნიმუშში არსებული ყველა სხვა რეგულარული გამოსახულების მეტასიმბოლო
  დამთხვევის შემოწმებამდე ეკრანირდება, ამიტომ `gpt-5.6` მხოლოდ ლიტერალურ სტრიქონს ემთხვევა და არასოდეს — `gpt-5x6`-ს
  (დაცულია ReDoS-ისგან, შეზღუდულია და არ შეიცავს ჩადგმულ კვანტიფიკატორებს). ნიმუშები რეგისტრის გაუთვალისწინებლად მოწმდება
  როგორც უშუალოდ მოდელის id-სთან, ისე `provider/model` კომპოზიტთან — `gpt-5-6`, `openai/gpt-5-6`
  და `openai/*` მუშაობს, ხოლო ცალკე `*` ყველა მოდელს გამორიცხავს.
- დამთხვევა: `isCompressionExcluded()` / `normalizeCompressionExclusions()` ფაილში
  `open-sse/services/compression/exclusions.ts`. `chatCore.ts` გამორიცხულ სამიზნეს ამოწმებს
  შეკუმშვის პარამეტრების განსაზღვრისთანავე, **ნებისმიერი ძრავის გაშვებამდე**, და დამთხვევას
  ზუსტად ისე განიხილავს, როგორც შეკუმშვის გლობალურ გამორთვას — მოთხოვნის სხეული გარანტირებულად
  ბაიტობრივად იდენტური რჩება. გამოტოვება ანალიტიკაში ხილვადობისთვის აღირიცხება
  `writeCompressionSkip(..., "excluded")`-ის მეშვეობით.
- ნაგულისხმევი მნიშვნელობა (ცარიელი/არარსებული სია): #8034-მდე არსებულ ქცევას ემთხვევა — არაფერი გამოირიცხება.

## ცნობილი შეზღუდვები

- **LLMLingua-2 (SLM) მოითხოვს არასავალდებულო დამოკიდებულებების ერთ ადგილას განთავსებას.** worker საწარმოო ანაწყობში მხოლოდ მაშინ მუშაობს, როდესაც `@atjsh/llmlingua-2` და მისი peer-დამოკიდებულებები ერთადაა განთავსებული
  `dist/node_modules`-ში (იხილეთ `scripts/build/colocateOptionals.mjs`, #4286). მათ გარეშე
  ძრავა უსაფრთხოდ წყვეტს მუშაობას (აბრუნებს საწყის ტექსტს). worker-ის ამოცნობა აღარ არის დამოკიდებული
  `import.meta.url`-ზე (ის დამოუკიდებელ bundle-ში მუშაობას წყვეტს) — ამის ნაცვლად, ის ეყრდნობა გაშვების გარემოს
  cwd-ს / `argv[1]`-ს.

  `dedup`/`ultra` წესებზე ფარული fallback არ ხდება, რადგან ეს უცხოენოვან ტექსტს დაამახინჯებდა).
