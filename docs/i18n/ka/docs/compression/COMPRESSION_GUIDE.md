## მიმოხილვა

OmniRoute ახორციელებს მოთხოვნის მოდულურ შეკუმშვის კონვეიერს, რომელიც **პროაქტიულად** მუშაობს მანამ, სანამ მოთხოვნები ზედა დონის პროვაიდერებამდე მიაღწევს. ეს ნიშნავს, რომ ტოკენების დაზოგვა გამჭვირვალედ ხდება — თქვენს სამუშაო პროცესში ცვლილებები საჭირო არ არის.

```
კლიენტის მოთხოვნა
  → შეკუმშვის სტრატეგიის ამომრჩევი
    → არის კომბინაციის ჩანაცვლება? → გამოიყენე კომბინაციის პარამეტრი
    → მიღწეულია ავტომატური გააქტიურების ზღვარი? → გამოიყენე ავტომატური რეჟიმი
    → არის ნაგულისხმევი რეჟიმი? → გამოიყენე გლობალური პარამეტრი
    → გამორთულია? → გამოტოვე შეკუმშვა
  → არჩეული შეკუმშვის რეჟიმი
    → Off: შეკუმშვის გარეშე
    → Lite: ჰარების/ფორმატირების უსაფრთხო გასუფთავება (~15%)
    → Standard: Caveman-ის სტილში შემავსებელი სიტყვების მოცილება (~30%)
    → Aggressive: ისტორიის დაძველება + შეჯამება (~50%)
    → Ultra: ევრისტიკული შემცირება + კოდის ბლოკების გათხელება (~75%)
    → RTK: ბრძანებების გათვალისწინებით ტერმინალის/ხელსაწყოს გამომავალი მონაცემების გაფილტვრა (ზედა დონის 60-90%-იანი დიაპაზონი)
    → Stacked: მოწესრიგებული მრავალძრავიანი კონვეიერი, ჩვეულებრივ ჯერ RTK, შემდეგ Caveman (შესაბამისი კონტექსტის 78-95%-იანი დიაპაზონი)
  → შეკუმშული მოთხოვნა → პროვაიდერი
```

## შეკუმშვის რეჟიმები

### Off

შეკუმშვა არ გამოიყენება. ყველა შეტყობინება უცვლელად გადაიცემა.

### Lite რეჟიმი (~15% დაზოგვა, <1ms დაყოვნება)

ყველაზე უსაფრთხო რეჟიმი — სემანტიკური ცვლილების გარეშე, მხოლოდ ფორმატირების გასუფთავება:

| ტექნიკა                  | აღწერა                                                              |
| ------------------------ | ------------------------------------------------------------------- |
| `collapseWhitespace`     | ზედიზედ არსებული ცარიელი ხაზებისა და დაბოლოების ჰარების გაერთიანება |
| `dedupSystemPrompt`      | დუბლირებული სისტემური შეტყობინებების მოცილება                       |
| `compressToolResults`    | ვრცელი ხელსაწყოს/ფუნქციის გამომავალი მონაცემების შეკუმშვა           |
| `removeRedundantContent` | განმეორებითი ინსტრუქციების მოცილება                                 |
| `replaceImageUrls`       | base64 გამოსახულების მონაცემთა URI-ების შემოკლება                   |

**საუკეთესოა:** მუდმივად ჩართული გამოყენებისთვის და უსაფრთხოების მხრივ კრიტიკული სამუშაო პროცესებისთვის.

### Standard რეჟიმი (~30% დაზოგვა)

შთაგონებულია [Caveman-ით](https://github.com/JuliusBrussee/caveman) — მნიშვნელობის შენარჩუნებით აშორებს შემავსებელ სიტყვებსა და ზედმეტად ვრცელ ფორმულირებებს:

- აშორებს შემავსებელ სიტყვებს ("გთხოვთ", "ვფიქრობ", "ზოგადად", "სინამდვილეში")
- ამოკლებს ზედმეტად ვრცელ ფრაზებს ("იმისათვის, რომ" → "რომ", "ამის შედეგად" → "რადგან")
- აშორებს თავაზიან შემარბილებელ ფრაზებს ("ხომ არ შეგაწუხებდათ...", "თუ შეძლებდით...")
- 30-ზე მეტი regex წესი, მორგებული პროგრამირების მოთხოვნებზე

**საუკეთესოა:** ყოველდღიური პროგრამირების სამუშაო პროცესებისა და ხარჯებზე ორიენტირებული გუნდებისთვის.

### Aggressive რეჟიმი (~50% დაზოგვა)

ისტორიის გონივრული მართვა ხანგრძლივი სესიებისთვის:

- **შეტყობინებების დაძველება** — ძველი შეტყობინებები თანდათან უფრო მეტად იკუმშება
- **ხელსაწყოს შედეგების შეკუმშვა** — ხელსაწყოს გრძელი გამომავალი მონაცემები იკვეთება ან გამოტოვებით ჩანაცვლდება (პირველი/ბოლო ხაზები,
  დამთხვევის მქონე ხაზების გაფილტვრა, JSON გასაღებების კომპაქტურად წარმოდგენა)
- **სტრუქტურული მთლიანობის დამცავი მექანიზმები** — უზრუნველყოფს `tool_use` + `tool_result` წყვილების თანმიმდევრულობას
- **კონტექსტის ფანჯრის გათვალისწინება** — იცავს თითოეული მოდელის ტოკენების ლიმიტებს

**საუკეთესოა:** ხანგრძლივი გამართვის სესიებისა და დიდი კოდური ბაზებისთვის.

### Ultra რეჟიმი (~75% დაზოგვა)

მაქსიმალური შეკუმშვა ტოკენების მხრივ კრიტიკული სცენარებისთვის:

- **ევრისტიკული შემცირება** — ტექსტის ქულებზე დაფუძნებული ტოკენური შემცირება
- **სტრუქტურის შენარჩუნება** — შემოსაზღვრული კოდის ბლოკები, სტრიქონშიდა კოდი, URL-ები და იდენტიფიკატორები
  დროებითი ნიშნებით ჩანაცვლდება და შემდეგ სიტყვასიტყვით აღდგება; ისინი არასოდეს იკვეცება
- **არასავალდებულო SLM დონე** — კონფიგურაციის შემთხვევაში მცირე ლოკალურ მოდელს შეუძლია შემცირების დახვეწა
- Aggressive რეჟიმისგან დამოუკიდებელია: ის არ ახორციელებს შეტყობინებების დაძველებას, ხელსაწყოს შედეგების შეკუმშვას
  ან სარეზერვო შემაჯამებლის გამოყენებას (მხოლოდ SLM დონის შეცდომამ შეიძლება გადაამისამართოს სარეზერვო დამუშავება
  aggressive რეჟიმის გავლით)

**საუკეთესოა:** როდესაც კონტექსტის ლიმიტებს განმეორებით აწყდებით.

### RTK რეჟიმი (ზედა დონის 60-90%-იანი დიაპაზონი)

RTK რეჟიმი ოპტიმიზებულია პროგრამირების აგენტის სესიებში არსებული ვრცელი ხელსაწყოს გამომავალი მონაცემებისთვის:

- ამოიცნობს ბრძანებების/გამომავალი მონაცემების კლასებს, როგორიცაა `git status`, `git diff`, `git log`, ტესტების გამშვები საშუალებები,
  TypeScript/Vite/Webpack აგებები, ESLint/Biome/Prettier, npm აუდიტები/ინსტალაციები, Docker ჟურნალები, ინფრასტრუქტურის
  გამომავალი მონაცემები და გარსის ზოგადი გამომავალი მონაცემები
- იყენებს JSON ფილტრების პაკეტებს `open-sse/services/compression/engines/rtk/filters/`-დან
- პროექტის ან გლობალური `filters.toml` ფაილებიდან შემოაქვს RTK TOML schema v1 ფილტრები, ჩაშენებული ტესტების
  ვალიდაციითა და პროექტის ფაილების სანდოობის შემოწმებით
- მოიცავს 55 ჩაშენებულ ფილტრს, ჩაშენებული შემოწმების ნიმუშებით
- აშორებს ANSI საკონტროლო მიმდევრობებს, პროგრესის ზოლებს, განმეორებით ხაზებსა და არაპრაქტიკულ ხმაურს
- ინარჩუნებს ჩავარდნებს, შეცდომებს, გაფრთხილებებს, შეცვლილ ფაილებს, შეჯამებებსა და გრძელი გამომავალი მონაცემების ბოლო ნაწილს
- მხარს უჭერს სანდოობის შემოწმებით დაცულ პროექტის ფილტრებს, გლობალურ ფილტრებსა და სურვილისამებრ დაფარული საწყისი გამომავალი მონაცემების აღდგენას

**საუკეთესოა:** აგენტის სესიებისთვის, რომლებიც შეიცავს გარსის, აგების, ტესტირების, git-ის, grep-ისა და ფაილების გამომავალი მონაცემების ჩანაწერებს.

### Stacked რეჟიმი (შესაბამისი კონტექსტის 78-95%-იანი დიაპაზონი)

Stacked რეჟიმი რამდენიმე შეკუმშვის ძრავას განსაზღვრული თანმიმდევრობით ამუშავებს. ნაგულისხმევი კონვეიერია:

ეს თანმიმდევრობა ჯერ ტერმინალის/ხელსაწყოს გამომავალ მონაცემებს ამცირებს, შემდეგ კი
დარჩენილ ბუნებრივ ენაზე დაწერილ მოთხოვნაზე Caveman-ის სემანტიკურ შეკუმშვას იყენებს. Stacked კონვეიერების კონფიგურაცია შესაძლებელია გლობალურად ან

## ზედა დონის დაზოგვის გამოთვლა

OmniRoute შეკუმშვით მიღებულ დაზოგვას ორი წყაროს საფუძველზე აღწერს: ზედა დონის პროექტების საორიენტაციო ტესტებისა და
OmniRoute-ის საკუთარი ძრავების კომბინაციის.

| წყარო   | ზედა დონის README-დან აქ გამოყენებული მაჩვენებელი                                                                                                                                        |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%`-ით ნაკლები გამომავალი ტოკენი, საორიენტაციო ტესტებში გამომავალი მონაცემების საშუალოდ `65%`-იანი დაზოგვა, `22-87%` დიაპაზონი და `~46%`-იანი შემავალი მონაცემების შეკუმშვის ხელსაწყო |
| RTK     | ბრძანების გამომავალი მონაცემების `60-90%`-იანი დაზოგვა; სანიმუშო სესიაში `~118,000 -> ~23,900` ტოკენი, ანუ დაზოგილია `79.7%` (`~80%`)                                                    |

ხელსაწყოს/კონტექსტის ურთიერთგადამფარავი მონაცემებისთვის, OmniRoute-ის ნაგულისხმევი კომბინაცია ძრავებს თანმიმდევრულად იყენებს:

```txt
RTK -> Caveman
```

საერთო დაზოგვა მულტიპლიკაციურია და არა ადიტიური:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ეს `78-95%` მაჩვენებელი მოქმედებს მაშინ, როდესაც RTK-საც და Caveman-საც შეუძლია ერთი და იმავე შემავალი მონაცემების/კონტექსტის შემცირება.
Caveman-ის პასუხის გამომავალი რეჟიმი განცალკევებულია: მისი ჩართვისას გამოიყენეთ თავად Caveman-ის გამომავალი მონაცემების დაზოგვის მაჩვენებლები (საშუალოდ `65%`,
მთავარი მაჩვენებელი `~75%`, დიაპაზონი `22-87%`). ბილინგის ჯამური დაზოგვა დამოკიდებულია თქვენს მოთხოვნებსა და გამომავალ მონაცემებს შორის თანაფარდობაზე.

### რას ნიშნავს სინამდვილეში „შესაფერისი“

მთავარ სათაურში მითითებული 15-95%-იანი დიაპაზონი რეალურია, თუმცა ის ვრცელდება მხოლოდ **ჭარბ ან ზედმეტად ვრცელ** შიგთავსზე — განმეორებად
შეცდომის სტრიქონებზე, აგების ჟურნალზე, რომელიც ერთი და იმავე გაფრთხილებას განუწყვეტლივ იმეორებს, ზედმეტად დიდ `grep`/ფაილის წაკითხვის ამონაწერზე. ეს
**არ** ნიშნავს, რომ თითოეული მოთხოვნა ამდენს დაზოგავს.

ემპირიულად დადასტურებულია (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): `stacked`
(RTK + Caveman) გაშვებამ Anthropic-ის ფორმის `tool_result` ბლოკზე, რომელიც 300 იდენტურ
შეცდომის სტრიქონს შეიცავდა, უზრუნველყო **ტოკენების 95.93%-იანი დაზოგვა / სიმბოლოების 96.26%-იანი დაზოგვა** — ზუსტად რეკლამირებულ
დიაპაზონში. თუმცა იმავე დამუშავების ჯაჭვის გაშვება ხელსაწყოს ჩვეულებრივ, არაჭარბ გამომავალ მონაცემებზე (სუფთა `grep` დამთხვევების სია,
მოკლე ფაილის წაკითხვა, ჩვეულებრივი სასაუბრო ტექსტი) მართებულად იძლევა **ნულთან მიახლოებულ დაზოგვას**, რადგან
წასაშლელი განმეორებადი შიგთავსი არ არსებობს, ხოლო `validateCompression()` (`validation.ts`) უარს ამბობს ისეთი
გადაწერილი ვერსიის გაგზავნაზე, რომელიც კოდის ბლოკებს, URL-ებს, სათაურებს, ვერსიებს ან ALL-CAPS მუდმივების იდენტიფიკატორებს ამოიღებდა ან შეცვლიდა.

ეს მოსალოდნელი და უსაფრთხო ქცევაა, არა შეცდომა: პროგრამირების სესიაში, რომელიც ძირითადად სუფთა ფაილებს კითხულობს ან მათში `grep`-ით ეძებს,
ჯამური დაზოგვა ზომიერი იქნება მაშინაც კი, როცა შეკუმშვა სრულადაა ჩართული, ხოლო სესიაში, რომელიც წარუმატებელ
ციკლს ან ზედმეტად ბევრის გამომტან ლინტერს წააწყდება, ამ ტრაფიკზე სრულ 78-95%-იან დიაპაზონს მიიღებთ. ერთი სესიის
დაზოგვის დაბალი ჯამური პროცენტი არ გამოიყენოთ იმის მტკიცებულებად, რომ შეკუმშვა არასწორადაა კონფიგურირებული — ჯერ შეამოწმეთ, იყო თუ არა

## კონფიგურაცია

### მართვის პანელი

გადადით `Dashboard → Context & Cache`-ში:

- **Caveman** — რეჟიმის არჩევა, ენის პაკეტები, წინასწარი გადახედვა და გლობალური ნაგულისხმევი პარამეტრები
- **RTK** — ბრძანებების ფილტრის წინასწარი გადახედვა, RTK-ის უსაფრთხოების პარამეტრები და ფილტრების კატალოგი
- **Compression Combos** — სახელდებული ძრავების კონვეიერები, რომლებიც მარშრუტიზაციის კომბინაციებს ენიჭება
- **Auto-Trigger Threshold** — შეკუმშვის ავტომატურად ჩართვა, როდესაც ტოკენების რაოდენობა ზღვრულ მნიშვნელობას გადააჭარბებს

### ცალკეული კომბინაციის გადაფარვა

`Dashboard → Context & Cache → Compression Combos`-ში მიანიჭეთ შეკუმშვის კომბინაცია მარშრუტიზაციის
კომბინაციას:

```txt
კომბინაცია: "free-tier-fallback"
  შეკუმშვის კომბინაცია: "coding-agent-stack"
  კონვეიერი: RTK -> Caveman
  სამიზნეები:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ეს საშუალებას გაძლევთ, უფასო/კოდირებისთვის განკუთვნილ პროვაიდერებთან გამოიყენოთ საფეხურებრივი შეკუმშვა, ხოლო ფასიან
გამოწერებში მსუბუქი რეჟიმი შეინარჩუნოთ.

ეს „ცალკეული კომბინაციის გადაფარვის“ მინიჭება განსხვავდება **მარშრუტიზაციის კომბინაციის შეკუმშვის
რეჟიმის** გადაფარვისგან (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — ველის
სქემა ასევე იღებს `rtk`, `stacked` და `omniglyph` მნიშვნელობებს) — ეს გადაფარვა არ ირჩევს სახელდებულ
შეკუმშვის კომბინაციის კონვეიერს; ის მხოლოდ ადგენს `compressionMode` ველს, რომელსაც
`resolveCompressionPlan` ამოწმებს. მისი დაყენება შესაძლებელია როგორც კომბინაციის ბარათზე (`Dashboard → Combos`), ასევე,
#6760-დან მოყოლებული, თითოეული მარშრუტიზაციის კომბინაციისთვის „Assign to routing“ სიაში,
`Dashboard → Context & Cache → Compression Combos`-ში, ზემოთ აღწერილი კონვეიერის მინიჭების მოსანიშნი ველის
გვერდით. ორივე ინტერფეისი მონაცემებს იმავე `PUT /api/combos/{id}` ბოლო წერტილის მეშვეობით ინახავს.

### ცალკეული მოთხოვნის გადაფარვა

ერთი მოთხოვნისთვის შეკუმშვის გეგმის გადასაფარად გაგზავნეთ `x-omniroute-compression` მოთხოვნის
სათაური. მას უმაღლესი პრიორიტეტი აქვს — ის უპირატესია მარშრუტიზაციის კომბინაციის გადაფარვაზე, აქტიურ პროფილზე,
ავტომატურ გააქტიურებასა და პანელის ნაგულისხმევ პარამეტრზე. უცნობი მნიშვნელობები იგნორირდება (მოთხოვნა არასოდეს უარყოფილა) და
გლობალური მთავარი გადამრთველი კვლავ ყველაფერს აკონტროლებს: როდესაც შეკუმშვა გლობალურად გამორთულია, სათაური მას
ვერ ჩართავს. მნიშვნელობები:

| მნიშვნელობა   | ეფექტი                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | ამ მოთხოვნისთვის შეკუმშვა არ გამოიყენება.                                                                         |
| `default`     | პანელიდან მიღებული ნაგულისხმევი პროფილი (აქტიურ პროფილს უგულებელყოფს). დანაკარგიანი ძრავები გამორთული რჩება.      |
| `safe`        | იგივეა, რაც სათაურის გამოტოვება: მხოლოდ დუბლიკატების მოცილება და ჰარიების შეკუმშვა.                               |
| `allow-lossy` | ამ მოთხოვნის ოპერატორის გეგმის შენარჩუნება, შეჯამებების, რელევანტურობის ფილტრებისა და სტილის გადაწერის ჩათვლით.   |
| `engine:<id>` | ერთი ძრავა, თუ ის ჩართულია, მაგალითად `engine:rtk`. ეს ამ ძრავისთვის ცალკეული მოთხოვნის დონეზე თანხმობის მიცემაა. |
| `<combo>`     | სახელდებული კომბინაცია, რომელიც ჯერ სახელით (რეგისტრის გაუთვალისწინებლად), შემდეგ კი id-ით ემთხვევა.              |

`allow-lossy`-ის, `engine:<id>`-ის ან სახელდებული კომბინაციის გარეშე დანაკარგიანი ძრავები არ გამოიყენება.
როდესაც შეკუმშვა ჩართულია, მოთხოვნაზე კვლავ ვრცელდება სესიის დუბლიკატების მოცილება და ჰარიების შეკუმშვა.

გამოყენებული გეგმა პასუხში აისახება `X-OmniRoute-Compression: <mode>; source=<source>` სათაურში,
სადაც `<source>` არის ერთ-ერთი: `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` ან `off`.

ზემოთ აღწერილი 7 რეჟიმის გარდა (საწყისი კოდი ასევე იღებს `codex-responses` და
`omniglyph` რეჟიმებს, რომლებსაც ეს სახელმძღვანელო არ განიხილავს), ქვემოთ მოცემულ სექციებში აღწერილია ფუნქციები,
რომლებიც ამ რეჟიმების შიგნით ან მათთან ერთად მუშაობს: ხელსაწყოს შედეგების შეკუმშვა და პროგრესული დაძველება
aggressive ძრავის 1-ლი და მე-2 ნაბიჯებია (Aggressive რეჟიმი და stacked
კონვეიერის `aggressive` ნაბიჯი), Stacked Pipeline განსაზღვრავს Stacked რეჟიმის მუშაობის წესს, ქეშის გათვალისწინებით შეკუმშვა
ქეშირების მქონე მომწოდებლებისთვის `aggressive` და `ultra` რეჟიმებს `standard` რეჟიმამდე აქვეითებს, როდესაც შეკუმშვა
ჩართულია, ხოლო Caveman Output Mode და Output Styles არის ნებაყოფლობით ჩასართავი სისტემური მოთხოვნის ინსტრუქციები,
რომლებიც ნაგულისხმევად გამორთულია და მოთხოვნის შეკუმშვის ნაცვლად მოდელის გამომავალ მონაცემებს აყალიბებს.

### ქეშის გათვალისწინებით შეკუმშვა

ზოგიერთი მომწოდებელი (მაგალითად, Anthropic მოთხოვნების ქეშირებით) მხარს უჭერს **მოთხოვნების ქეშირებას**,
რაც მათ საშუალებას აძლევს, ხარჯებისა და დაყოვნების შესამცირებლად მოთხოვნის ნაწილები ქეშში შეინახონ. როდესაც
ქეშირება ჩართულია, aggressive შეკუმშვამ შესაძლოა წარმადობა რეალურად **გააუარესოს**,
რადგან ის ცვლის ქეშირებულ ტოკენებს და ამით ქეშს ძალადაკარგულად აქცევს.

`cachingAware.ts` მოდული ამ პრობლემას **ქეშირების კონტექსტის აღმოჩენითა** და
**შეკუმშვის სტრატეგიის შესაბამისი კორექტირებით** აგვარებს.

#### როგორ მუშაობს

1. **ქეშირების კონტექსტის აღმოჩენა** — მოთხოვნის სხეულში ეძებს `cache_control` მარკერებს
2. **ქეშირების მომწოდებლების იდენტიფიცირება** — ამოწმებს, აქვს თუ არა სამიზნე მომწოდებელს ქეშირების მხარდაჭერა
3. **სტრატეგიის კორექტირება** — ქეშირების მომწოდებლებისთვის `aggressive`/`ultra` რეჟიმებს `standard` რეჟიმამდე აქვეითებს
4. **სისტემური მოთხოვნის გამოტოვება** — სისტემური მოთხოვნები, როგორც წესი, ქეშირებულია, ამიტომ მათ ნუ შეკუმშავთ

სტრატეგიის დამხმარე ფუნქცია ასევე აბრუნებს `deterministicOnly` ალამს, თუმცა გეგმის შემქმნელი
მხოლოდ სტრატეგიას იყენებს — ამჟამად შემდგომ ეტაპებზე ალამს არაფერი კითხულობს.

#### კოდის მაგალითი

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← ქეშის მარკერი
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### როდის გამოვიყენოთ

ქეშის გათვალისწინებით შეკუმშვა **ყოველთვის ჩართულია** — კონფიგურაცია საჭირო არ არის. ის ამოქმედდება მაშინ, როდესაც
შეკუმშვა ჩართულია და სამიზნე მომწოდებელს მოთხოვნების ქეშირების მხარდაჭერა აქვს (Anthropic, OpenAI
და სხვ.); ცხადად მითითებული `cache_control` მარკერები საჭირო არ არის — დაქვეითების
გამოსაწვევად მხოლოდ ქეშირების მომწოდებლის არსებობაც საკმარისია, ხოლო მხოლოდ მარკერები ამას არასდროს იწვევს (მარკერების აღმოჩენა ქეშის
ტელემეტრიას აწვდის მონაცემებს და არა სტრატეგიის გადაწყვეტილებას).

### პროგრესული დაძველება

ხანგრძლივი საუბრებისას შეტყობინებების მრავალი რაუნდი გროვდება, თუმცა ძველი რაუნდები თანდათან ნაკლებად
რელევანტური ხდება. `progressiveAging.ts` მოდული **შეტყობინებებს რაუნდის დაშორების მიხედვით ამარტივებს**
(დაშორება საუბრის ბოლოდან იზომება). მოწოდებული ნაგულისხმევი პარამეტრებით
(`verbatim: 2, light: 2, moderate: 3`):

- **ბოლო 2 მონაცვლეობა (მანძილი ≤ 2)**: უცვლელად ინახება
- **მანძილი 3**: Caveman შეკუმშვა (შემავსებელი სიტყვების მოცილება)
- **მანძილი 4+**: ასისტენტის შეტყობინებები შეჯამებულია; მომხმარებლის შეტყობინებები შემოკლებულია პირველ
  სტრიქონამდე, მაქსიმუმ 120 სიმბოლოთი; სხვა როლები ხელუხლებელია. სისტემური მოთხოვნები, უკვე დაძველებული
  შეტყობინებები და მომხმარებლის უახლესი შეტყობინება ყოველთვის უცვლელად ინახება, მანძილის მიუხედავად.
  არაფერი იშლება მთლიანად, ხოლო `light`
  დიაპაზონი ნაგულისხმევი პარამეტრებით მიუწვდომელია (`light` უდრის `verbatim`-ს).

#### კოდის მაგალითი

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... კიდევ 50 მონაცვლეობა ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ბოლო 3 მონაცვლეობა: უცვლელად
  light: 8, // მანძილი <= 8: მსუბუქი შეკუმშვა
  moderate: 20, // მანძილი <= 20: caveman შეკუმშვა
  fullSummary: 5, // ტიპის მიხედვით სავალდებულოა, მაგრამ დიაპაზონების კოდი არ კითხულობს
  // მანძილი > 20: შეჯამებული (ასისტენტი) / შენახულია პირველი სტრიქონი (მომხმარებელი)
});

// saved = დაზოგილი ტოკენების რაოდენობა
```

#### როდის გამოვიყენოთ

პროგრესული დაძველება **ყოველთვის ჩართულია** `aggressive` რეჟიმისთვის — ის
`compressAggressive()`-ის მე-2 ნაბიჯია. Ultra რეჟიმი მას არ ასრულებს. ის
განსაკუთრებით ეფექტურია შემდეგ შემთხვევებში:

- ხანგრძლივი პროგრამირების სესიები
- მრავალდღიანი საუბრები
- აგენტური სამუშაო პროცესები მრავალი ხელსაწყოს გამოძახებით

### Caveman გამომავალი რეჟიმი

Caveman გამომავალი რეჟიმი ამატებს **სისტემური მოთხოვნის ინსტრუქციებს**, რომლებიც თავად მოდელს
სთხოვს მოკლე პასუხების გაცემას — `lite` დონე ითხოვს ლაკონიურ პასუხებს სრული წინადადებების შენარჩუნებით, `full`
სთხოვს, რომ „ჭკვიანი გამოქვაბულის ადამიანის მსგავსად მოკლედ უპასუხოს“, ხოლო `ultra` ტელეგრაფულ პასუხს ითხოვს;
ინსტრუქციები მხოლოდ ითხოვს და ამის გარანტიას ვერ იძლევა. მოთხოვნები მათ იღებს
`applyOutputStyles()`-ის მეშვეობით (`open-sse/services/compression/outputStyles/apply.ts`):
`open-sse/handlers/chatCore.ts` თავდაპირველად არჩევანს უკუთავსებადობის შიმის მეშვეობით განსაზღვრავს
(`resolveOutputStyleSelection()` ფაილში
`open-sse/services/compression/outputStyles/backCompat.ts`), რომელიც, სანამ `outputStyles`
ცარიელია, ჩართულ `cavemanOutputMode`-ს `terse-prose` გამომავალი სტილზე ასახავს
`cavemanOutputMode.intensity` ინტენსივობით (იხილეთ უკუთავსებადობა ქვემოთ); არაცარიელი `outputStyles`
არჩევანი გამოიყენება უცვლელად, რის შემდეგაც `cavemanOutputMode.enabled` და `intensity`
გავლენას აღარ ახდენს, თუმცა მისი `autoClarity` გადამრთველი კვლავ მოქმედებს. `outputMode.ts` შეიცავს
ინსტრუქციების ტექსტებს (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), შიგთავსის გვერდის ავლისა და
განთავსების დამხმარე მექანიზმს, რომელსაც ინექცია იყენებს; მის საკუთარ `applyCavemanOutputMode()`
ინჟექტორს საწარმოო გარემოში გამომძახებელი არ ჰყავს.

#### როგორ მუშაობს

ეს რეჟიმი შემავალ მონაცემებს არ კუმშავს. ის სისტემურ მოთხოვნას ინსტრუქციების ბლოკს ამატებს
(იხილეთ ქვემოთ, როგორ მუშაობს ინექცია), ხოლო მოთხოვნისთვის არჩეული შემავალი მონაცემების შეკუმშვის
ნებისმიერი რეჟიმი შემდეგ მაინც სრულდება იმ სხეულზე, რომელიც ახლა ამ ბლოკს შეიცავს. საერთო
შეზღუდვების პუნქტის წინ, რომლითაც ყველა დონე სრულდება, ინგლისური `full` დონე ასე ჟღერს:

> „უპასუხე მოკლედ, როგორც ჭკვიანმა გამოქვაბულის ადამიანმა. ამოიღე არტიკლები (a/an/the), შემავსებელი სიტყვები (just/really/basically/actually/simply), თავაზიანობის ფორმები და თავის დაზღვევის გამომხატველი სიტყვები. ფრაგმენტები დასაშვებია. გამოიყენე მოკლე სინონიმები (big და არა extensive, fix და არა implement). ზუსტად შეინარჩუნე ყველა ტექნიკური შინაარსი, კოდი, შეცდომა, URL და იდენტიფიკატორი.“

ეს განსაკუთრებით კარგად მუშაობს შემდეგ შემთხვევებში:

- კოდის გენერაცია (უფრო მოკლე გამომავალი = ნაკლები ტოკენი)
- სწრაფი კითხვა-პასუხი (ვრცელი ახსნა საჭირო არ არის)
- პაკეტური დამუშავება (გამტარუნარიანობის მაქსიმიზაცია)

#### როდის გამოვიყენოთ

Caveman გამომავალი რეჟიმი **არჩევითია**. როდესაც შეკუმშვა ჩართულია (`enabled: true`, მთავარი გადამრთველი
Compression Settings გვერდზე), ჩართეთ ის `cavemanOutputMode.enabled`-ის მეშვეობით; `intensity`
ირჩევს `lite`, `full` ან `ultra` დონეს:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

შეკუმშვის კომბინაციის **Output Mode** გადამრთველი (`outputMode`, დონე `outputModeIntensity`-ში)
იმავე პარამეტრს ადგენს იმ მოთხოვნებისთვის, რომლებზეც ეს კომბინაცია ვრცელდება, ხოლო
`omniroute_set_compression_engine` MCP ხელსაწყო მას თავისი ლოგიკური `outputMode`
არგუმენტის მეშვეობით წერს. არაცარიელ `outputStyles` არჩევანს ამ გადამრთველთან შედარებით უპირატესობა აქვს. მართვის
პანელში **Terse prose** გამომავალი სტილის ჩართვა იმავე ბლოკს უკეთებს ინექციას (იხილეთ ქვემოთ, გამომავალი
სტილები).

#### როგორ მუშაობს ჩასმა

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) არჩევანს
კატალოგთან ადარებს (უცნობი id-ები და ლოკალთან შეუსაბამო სტილები გამოირიცხება და არასოდეს იწვევს
შეცდომას; არჩევანი, რომლისგანაც არცერთი სტილი არ განისაზღვრება, სხეულს უცვლელად ტოვებს და გამოტოვებულია, როგორც
`no_styles`), არჩეულ ინსტრუქციებს კატალოგის თანმიმდევრობით აერთიანებს,
საზღვრების პუნქტს **ერთხელ** ამატებს (უსაფრთხოების პუნქტთან, `SAFETY_BOUNDARIES`-თან ან მის
თარგმანთან ერთად, როდესაც არჩეულია `less-code` ან `ponytail`) და ბლოკს იწყებს
ერთიანი იდემპოტენტურობის მარკერით (`[OmniRoute Output Styles]`), ამიტომ ხელახლა გამოყენებას ეფექტი არ აქვს. როდესაც
განსაზღვრულ ენას (იხილეთ ქვემოთ „ენის არჩევა“) თარგმანი აქვს, ინგლისურის ნაცვლად
ლოკალიზებული ინსტრუქცია ჩაისმება.

არაცარიელი `messages` მასივის მქონე სხეულში იდემპოტენტურობის შემოწმება შიგთავსის
გვერდის ავლამდე სრულდება: როდესაც `[OmniRoute Output Styles]` მარკერი უკვე არის ზედა დონის
`system` ველში (სტრიქონში ან შიგთავსის ბლოკების მასივში) ან სტრიქონული
შიგთავსის მქონე სისტემურ შეტყობინებაში, სხეული უცვლელი რჩება, როგორც `already_applied`, და საკვანძო სიტყვების შემოწმება არ
სრულდება. წინააღმდეგ შემთხვევაში, შიგთავსის გვერდის ავლა (`shouldBypassCavemanOutputMode()`
ფაილში `open-sse/services/compression/outputMode.ts`) ამოწმებს ბოლო სამი
შეტყობინების ტექსტს, მათი როლის მიუხედავად, და მთელი სვლისთვის გამოტოვებს სტილებს, როდესაც ტექსტი
ემთხვევა უსაფრთხოების, შეუქცევადი მოქმედების ან დაზუსტების საკვანძო სიტყვებს, ან
თანმიმდევრობაზე დამოკიდებულ წყობას: `first`, `then`, `after that`, `before`, `rollback` ან
`backup`, რომელსაც 240 სიმბოლოს ფარგლებში მოსდევს `delete`, `drop`, `migrate`, `deploy` ან
`release`. გვერდის ავლა მუშაობს, სანამ **Auto-Clarity Bypass** გადამრთველი
(`cavemanOutputMode.autoClarity`, ნაგულისხმევად ჩართული) ჩართულია; გადამრთველის გამორთვა
საკვანძო სიტყვების შემოწმებას გამოტოვებს.

როდესაც გვერდის ავლა სვლას ატარებს, `placeSystemInstruction()` (იგივე ფაილი), რომელიც
არასოდეს ქმნის ახალ `messages[0]`-ს, ბლოკს ათავსებს ქვემოთ ჩამოთვლილთაგან პირველივე ნაპოვნ ადგილას:

1. საწყისი სისტემური შეტყობინება სტრიქონული შიგთავსით: ბლოკი მის ტექსტს ემატება.
2. ზედა დონის `system` ველი: ბლოკი სტრიქონის ტექსტს ემატება ან
   შიგთავსის ბლოკების მასივს ახალი ტექსტური ბლოკის სახით ემატება.
3. პირველი მომდევნო სისტემური შეტყობინება სტრიქონული შიგთავსით: ბლოკი მის
   ტექსტს ემატება.
4. არცერთი ზემოთ ჩამოთვლილი: ბლოკი `messages`-ის ბოლოში ახალ სისტემურ შეტყობინებაში თავსდება.

`messages` მასივის არმქონე (ან ცარიელი მასივის მქონე) სხეულში შიგთავსის გვერდის ავლა არ
სრულდება და ზედა დონის `system` ველი არ მოწმდება. ბლოკი სტრიქონული
`instructions` ველის ტექსტს ემატება, გარდა იმ შემთხვევისა, როდესაც ეს ველი უკვე შეიცავს
`[OmniRoute Output Styles]` მარკერს; ამ შემთხვევაში სხეული უცვლელი რჩება, როგორც
`already_applied`. როდესაც სხეულს არ აქვს სტრიქონული `instructions` ველი, მაგრამ შეიცავს `input`-ს
(სტრიქონს ან მასივს), ბლოკი ხდება `instructions` და ანაცვლებს ამ ველში მანამდე არსებულ ნებისმიერ არასტრიქონულ
მნიშვნელობას. სხეული, რომელსაც არც სტრიქონული `instructions` ველი აქვს და არც სტრიქონული ან მასივის ტიპის
`input`, უცვლელი რჩება და გამოტოვებულია, როგორც `no_messages`.

#### როგორ ჩავრთოთ

მართვის პანელში: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles სექცია: თითოეული სტილისთვის ერთი სტრიქონი, ჩართვა/გამორთვის
გადამრთველითა და დონის ამომრჩევით. სტილები ემატება მაშინ, როდესაც თავად შეკუმშვა ჩართულია (გვერდის
მთავარი გადამრთველი, `enabled`). **Auto-Clarity Bypass** გადამრთველი მდებარეობს **Caveman**
გვერდზე (`/dashboard/context/caveman`), მის **Output Mode** ბარათში. პროგრამულად,
შეკუმშვის კონფიგურაცია არჩევანს ინახავს შემდეგი სახით:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

უკუთავსებადობა: სანამ `outputStyles` ცარიელია, ძველი `cavemanOutputMode.enabled`
პარამეტრი აისახება `terse-prose`-ზე `cavemanOutputMode.intensity` ინტენსივობით. შემდეგ ბლოკი
იწყება `[OmniRoute Output Styles]` მარკერით, მაშინ როცა ძველი `applyCavemanOutputMode()`
ინჟექტორი წერდა `[OmniRoute Caveman Output Mode]`-ს. მარკერის ქვემოთ ტექსტი ემთხვევა
ძველ ინექციას en, pt-BR, es, de, fr, it, ru, id და vi ენებზე; ja და zh ენებზე კი
საზღვრების პუნქტის წინ ერთი დამატებითი სივრცეა. `terse-prose` თარგმნილია pt-BR, es, de,
fr, it, ru, zh, ja, id და vi ენებზე, ამიტომ მოთხოვნა, რომლის განსაზღვრული ენაა `hu`,
იღებს ინგლისურ ტექსტს იქ, სადაც ძველი ინჟექტორი უნგრულ ტექსტს იყენებდა.

გამომავალი სტილის ენის არჩევა (`resolveOutputStyleLanguage()` ფაილში
`outputStyles/apply.ts`): როდესაც `languageConfig.enabled` ჩართულია, `autoDetect`
იღებს ნიმუშად მოთხოვნის `messages` მასივში მომხმარებლის უახლეს შეტყობინებას, რომელიც
შეიცავს ტექსტს (სტრიქონულ შიგთავსს ან მისი შიგთავსის ნაწილების `text`-ს), და მასზე
უშვებს Caveman ძრავის დეტექტორს (`detectCompressionLanguage()`). დეტექტორი აბრუნებს
`zh`-ს ტექსტისთვის, რომელიც შეიცავს ჰანის სიმბოლოებს და არ შეიცავს კანას; სხვა
შემთხვევაში ის აბრუნებს `it`, `pt-BR`, `es`, `de`, `fr`, `ru`, `ja`, `hu` და `id`
ენებიდან იმ ენას, რომელსაც ყველაზე მეტი მინიშნების დამთხვევა აქვს, ხოლო როდესაც
არცერთი არ ემთხვევა — `en`-ს. ტექსტი, რომლის კლასიფიცირებაც შეუძლებელია, იღებს
ინგლისურს და არასდროს `defaultLanguage`-ს; `vi` კი საერთოდ არასდროს გამოვლინდება,
მიუხედავად იმისა, რომ სტილებს `vi` ტექსტიც მოჰყვება. Responses API-ის სხეული თავის
მიმოცვლებს `input`-ში ინახავს, რომელიც ნიმუშად არ გამოიყენება, ამიტომ ის ჯერ
`defaultLanguage`-ს, შემდეგ კი ინგლისურს იღებს. როდესაც `messages`-ში მომხმარებლის
არცერთი შეტყობინება არ შეიცავს ტექსტს, ან `autoDetect` გამორთულია, გამოიყენება
`defaultLanguage`, შემდეგ კი ინგლისური. როდესაც `languageConfig.enabled` გამორთულია,
ენა ინგლისურია — გარდა იმ შემთხვევისა, როდესაც მოთხოვნაზე შეკუმშვის კომბინაცია
ვრცელდება (კომბინაცია, რომელიც მოთხოვნის მარშრუტიზაციის კომბინაციას აქვს მინიჭებული,
ან ნაგულისხმევი შეკუმშვის კომბინაცია, რომელსაც chatCore ჩაშენებული დაწყობილი
კონვეიერისთვის იყენებს): კომბინაციის გამოყენება ამ მოთხოვნისთვის
`languageConfig.enabled`-ს რთავს და `defaultLanguage`-ს კომბინაციის ენის პაკეტებიდან
ადგენს (შენახული მნიშვნელობა, თუ ის კომბინაციის ერთ-ერთი პაკეტია; წინააღმდეგ

### ხელსაწყოს შედეგის შეკუმშვა

`compressToolResult()` ფაილში `open-sse/services/compression/toolResultCompressor.ts`
ხელსაწყოს შედეგის ტექსტს **5 სტრატეგიით** კუმშავს. ის მათ ამ თანმიმდევრობით ცდის და
შედეგს განსაზღვრავს პირველი ჩართული სტრატეგია, რომლის შემოწმებაც შიგთავსს ემთხვევა:

1. **`fileContent`**: 3 ან მეტი სტრიქონისგან შემდგარი შიგთავსი, რომელშიც, საწყისი
   შეწევის უგულებელყოფით, სულ მცირე ერთი სტრიქონი იწყება `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` ან `return `-ით (საკვანძო სიტყვა და ჰარე), ან `if`,
   `for` ან `while`-ით, რასაც მოსდევს `(` ან ` (`; ინარჩუნებს პირველ 20 და ბოლო 5 სტრიქონს,
   ხოლო გამოტოვებულ შუა ნაწილს შესაბამისი ნიშნით აღნიშნავს.
2. **`grepSearch`**: შიგთავსი სულ მცირე ერთი `<path>:<digits>:` ფორმის სტრიქონით,
   სადაც პირველი ორწერტილის წინა ტექსტი ჰარეებს არ შეიცავს; ინარჩუნებს მხოლოდ ასეთ სტრიქონებს,
   მაქსიმუმ 30-ს, რასაც მოსდევს დარჩენილი დამთხვევების რაოდენობა და დამთხვევის მქონე ფაილების სია;
   ყველა სხვა სტრიქონი იშლება. სტრატეგიის გასააქტიურებლად ერთი ასეთი სტრიქონიც საკმარისია, ამიტომ
   დროის ნიშნულით დაწყებული ჟურნალის ჩანაწერი, როგორიცაა `12:30:45`, ასევე ითვლება.
3. **`shellOutput`**: გამომავალი, რომელიც შეიცავს ANSI CSI მიმდევრობას (`ESC[`, შემდეგ ციფრები ან
   წერტილმძიმეები და ბოლოს ასო, როგორც ფერთა კოდებში) ან ტექსტის ნებისმიერ ადგილას `$`-ს,
   რომელსაც ჰარე მოსდევს, კარგავს ამ მიმდევრობებს (სხვა მმართველი მიმდევრობები, როგორიცაა `ESC[?25l` ან
   OSC ფანჯრის სათაურის მიმდევრობა, შენარჩუნდება) და ინარჩუნებს ბოლო 50 სტრიქონს, ხოლო მიმდევრობით
   განმეორებული სტრიქონები ერთ სტრიქონად იკუმშება. რადგან ეს შემოწმება `json`-სა და `errorMessage`-მდე
   სრულდება, ასეთი `$`-ის შემცველი JSON ან შეცდომის გამომავალი მათამდე ვერასოდეს აღწევს, სანამ
   `shellOutput` ჩართულია.
4. **`json`**: 2,000 სიმბოლოზე დიდი JSON მონაცემები, რომლებიც `{`-ით ან `[`-ით იწყება
   (არასავალდებულო ჰარეების შემდეგ) და წარმატებით ირჩევა, შეჯამდება: 7-ზე მეტი ელემენტის მქონე მასივიდან
   შენარჩუნდება პირველი 5 და ბოლო 2 ელემენტი და ელემენტების საერთო რაოდენობა, ხოლო ობიექტიდან — პირველი 20
   გასაღები; თითოეული ჩადგმული ობიექტის ან მასივის მნიშვნელობა ჩანაცვლდება `{…N keys}` ადგილმჭერით
   (მასივისთვის N მისი სიგრძეა) და დაემატება `_remaining_<N>_keys` მარკერი, რომელიც პირველი 20-ის შემდეგ
   გამოტოვებულ გასაღებებს ითვლის. სკალარული მნიშვნელობები სრულად კოპირდება, ამიტომ 20 ან ნაკლები გასაღების
   მქონე ობიექტი, რომელსაც ჩადგმული მნიშვნელობები არ აქვს, მხოლოდ ხელახლა იწევა — მინიფიცირებულ ვერსიას
   სიმბოლოები ემატება და ის უცვლელი რჩება.
5. **`errorMessage`**: გამომავალი, რომელიც ნებისმიერ ადგილას და ასოთა ნებისმიერი რეგისტრით შეიცავს `error:`,
   `error `-ს (სიტყვა, რომელსაც ჰარე მოსდევს, როგორც `no error found`-ში), `[error]`,
   `exception:`, `exception `, `[exception]` ან `traceback`-ს, ინარჩუნებს პირველ სტრიქონს,
   მომდევნო 10 სტრიქონსა და ბოლო 3-ს, ხოლო მათ შორის არსებულ სტრიქონებს
   `… [N frames elided] …` მარკერით ანაცვლებს. მარკერი მხოლოდ მაშინ ჩნდება, როდესაც პირველ
   სტრიქონს 13-ზე მეტი სტრიქონი მოსდევს, ამიტომ 14 ან ნაკლები სტრიქონისგან შემდგარი შეცდომის გამომავალი
   არ მოკლდება (12 ან 13 სტრიქონის შემთხვევაში ბოლო 3 სტრიქონი უკვე შენარჩუნებულ სტრიქონებს იმეორებს).

სტრატეგიის დამთხვევის შემდეგ, მაშინაც კი, თუ ის არაფერს ზოგავს, მომდევნო სტრატეგიები აღარ
გამოიცდება. როდესაც დამთხვეული სტრატეგია სავარაუდო ტოკენებს არ ზოგავს (სიგრძე ÷ 4, ზემოთ დამრგვალებული) —
მაგალითად, კოდის მსგავსი ფაილი 25 ან ნაკლები სტრიქონით, ან 2,000
სიმბოლოზე დიდი JSON მასივი 7 ან ნაკლები ელემენტით — აგრესიული ძრავა ხელსაწყოს თავდაპირველ
შედეგს ინარჩუნებს: ორივე გამომძახებელი (`compressAggressive()` და `compressAnthropicToolResultBlock()`)
თავდაპირველ შედეგს ინარჩუნებს, როდესაც `saved` არის 0 ან ნაკლები, ხოლო თავად `compressToolResult()`
კვლავ ამ სტრატეგიის გამომავალს აბრუნებს. ხელსაწყოს შედეგის ეტაპი საბოლოო სიტყვა არ არის:
ძრავის სარეზერვო შემაჯამებელს მაინც შეუძლია 8,192 სიმბოლოზე გრძელი `tool` ან `function`
შეტყობინების შემოკლება (`maxTokensPerMessage`, 2,048, გამრავლებული 4-ზე).

#### როდის გამოვიყენოთ

ხელსაწყოს შედეგის შეკუმშვა აგრესიული ძრავის პირველი ეტაპია (`compressAggressive()` ფაილში
`open-sse/services/compression/aggressive.ts`), ამიტომ ის მუშაობს Aggressive რეჟიმში და
დაწყობილი კონვეიერის `aggressive` ეტაპზე. ის კუმშავს OpenAI-ის ფორმის `tool` და `function`
შეტყობინებებს და Anthropic-ის `tool_result` ბლოკებში არსებულ ტექსტს. თითოეულ სტრატეგიას
აქვს საკუთარი გადამრთველი `aggressive.toolStrategies`-ის ქვეშ და ყველა მათგანი ნაგულისხმევად
ჩართულია. მართვის პანელში გადამრთველები Caveman გვერდის **Advanced** ხედშია, როდესაც შეკუმშვა
ჩართულია და ნაგულისხმევი რეჟიმია Aggressive.

### დაწყობილი კონვეიერი

დაწყობილი რეჟიმი **რამდენიმე ძრავას თანმიმდევრულად** უშვებს — ჩვეულებრივ ჯერ RTK-ს
(ხელსაწყოს გამომავალზე 60-90%-იანი დანაზოგი), შემდეგ კი Caveman-ს დარჩენილ ტექსტზე (~46%-იანი
შეყვანის დანაზოგი). კომბინირებული შედეგია **დასაშვები 78-95%-იანი დიაპაზონი** (იხილეთ ზემოთ
Upstream Savings Math): `1 - (1 - 0.60..0.90) × (1 - 0.46)` საშუალოდ ≈89%-ს შეადგენს.

#### როგორ მუშაობს

```
შეყვანა (1000 ტოკენი)
  → RTK (ბრძანებების გამთვალისწინებელი ფილტრი) → 200 ტოკენი
    → Caveman (შემავსებელი ტექსტის მოცილება) → 108 ტოკენი
  → გამომავალი (108 ტოკენი, ~89%-იანი დანაზოგი)
```

#### როდის გამოვიყენოთ

გამოიყენეთ დაწყობილი რეჟიმი:

- ხელსაწყოებით დატვირთული სამუშაო პროცესებისთვის (აგენტური კოდირება, კვლევა)
- ხარჯებისადმი მგრძნობიარე პაკეტური დამუშავებისთვის
- როდესაც ტოკენების მაქსიმალური დაზოგვა გჭირდებათ

დაწყობილი კონვეიერების კონფიგურაცია ხდება გლობალური `stackedPipeline` შეკუმშვის
პარამეტრით ან სახელდებული შეკუმშვის კომბინაციით, რომელიც მარშრუტიზაციის კომბინაციას ენიჭება (იხილეთ
ზემოთ Per-Combo Override) — და არა ავტოკომბინაციის `modePack`-ით (ეს ველი მხოლოდ
ავტოკომბინაციის მოდელების შერჩევის წონებს ცვლის, ხოლო `stacked` პაკეტის სწორი სახელი არ არის).

## შეკუმშვის კომბინაციების გადაფარვები

სხვადასხვა გამოყენების შემთხვევისთვის ქცევის ზუსტად მოსარგებად, შეგიძლიათ შეკუმშვის გლობალური რეჟიმი **თითოეული კომბინაციისთვის** გადააფაროთ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ეს სასარგებლოა შემდეგ შემთხვევებში:

- **პროგრამირების კომბინაციები**: ხანგრძლივი სესიებისთვის გამოიყენეთ `aggressive` რეჟიმი
- **სწრაფი კითხვა-პასუხის კომბინაციები**: სწრაფი პასუხებისთვის გამოიყენეთ `lite` რეჟიმი
- **ინსტრუმენტებზე ძლიერ დამოკიდებული კომბინაციები**: მაქსიმალური ეკონომიისთვის გამოიყენეთ `stacked` რეჟიმი
- **საწარმოო კომბინაციები**: ქეშირების პროვაიდერებისთვის გადაფარვა გამორთული დატოვეთ — მუდმივად ჩართული, ქეშის გათვალისწინებით შესრულებული კორექტირება `aggressive`/`ultra` რეჟიმებს ავტომატურად `standard` რეჟიმამდე აქვეითებს
  (ასარჩევი `cache-aware` რეჟიმი არ არსებობს)
