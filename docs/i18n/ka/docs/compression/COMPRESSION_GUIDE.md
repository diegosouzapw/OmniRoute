## მიმოხილვა

OmniRoute ახორციელებს მოთხოვნის მოდულარულ შეკუმშვის კონვეიერს, რომელიც **პროაქტიულად** მუშაობს, სანამ მოთხოვნები გარე პროვაიდერებამდე მიაღწევს. ეს ნიშნავს, რომ ტოკენების დაზოგვა გამჭვირვალედ ხდება — თქვენს სამუშაო პროცესში ცვლილებები საჭირო არ არის.

```
კლიენტის მოთხოვნა
  → შეკუმშვის სტრატეგიის ამრჩევი
    → კომბინაციის გადაფარვა? → კომბინაციის პარამეტრის გამოყენება
    → ავტომატური გააქტიურების ზღვარი? → ავტომატური რეჟიმის გამოყენება
    → ნაგულისხმევი რეჟიმი? → გლობალური პარამეტრის გამოყენება
    → გამორთულია? → შეკუმშვის გამოტოვება
  → არჩეული შეკუმშვის რეჟიმი
    → გამორთული: შეკუმშვის გარეშე
    → მსუბუქი: ჰარეებისა და ფორმატირების უსაფრთხო გასუფთავება (~15%)
    → სტანდარტული: ტელეგრაფული სტილით ზედმეტი სიტყვების მოცილება (~30%)
    → აგრესიული: ისტორიის დაძველება + შეჯამება (~50%)
    → ულტრა: ევრისტიკული გაფილტვრა + კოდის ბლოკების შემჭიდროება (~75%)
    → RTK: ბრძანებების გათვალისწინებით ტერმინალის/ინსტრუმენტის გამომავალი მონაცემების გაფილტვრა (გარე პროვაიდერთან 60-90%-იანი დიაპაზონი)
    → დაწყობილი: მოწესრიგებული მრავალძრავიანი კონვეიერი, ჩვეულებრივ ჯერ RTK, შემდეგ Caveman (დასაშვები მონაცემების 78-95%-იანი დიაპაზონი)
  → შეკუმშული მოთხოვნა → პროვაიდერი
```

## შეკუმშვის რეჟიმები

### გამორთული

შეკუმშვა არ გამოიყენება. ყველა შეტყობინება უცვლელად გადაიცემა.

### მსუბუქი რეჟიმი (~15% დაზოგვა, <1ms დაყოვნება)

ყველაზე უსაფრთხო რეჟიმი — სემანტიკური ცვლილებების გარეშე, მხოლოდ ფორმატირების გასუფთავება:

| ტექნიკა                  | აღწერა                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------- |
| `collapseWhitespace`     | ზედიზედ განლაგებული ცარიელი ხაზებისა და ხაზის ბოლოში არსებული ჰარეების გაერთიანება |
| `dedupSystemPrompt`      | დუბლირებული სისტემური შეტყობინებების მოცილება                                      |
| `compressToolResults`    | ვრცელი ინსტრუმენტის/ფუნქციის შედეგების შეკუმშვა                                    |
| `removeRedundantContent` | განმეორებითი ინსტრუქციების მოცილება                                                |
| `replaceImageUrls`       | base64-ფორმატის გამოსახულების მონაცემთა URI-ების შემოკლება                         |

**საუკეთესოა:** მუდმივი გამოყენებისა და უსაფრთხოებისადმი კრიტიკული სამუშაო პროცესებისთვის.

### სტანდარტული რეჟიმი (~30% დაზოგვა)

შთაგონებულია [Caveman-ით](https://github.com/JuliusBrussee/caveman) — მნიშვნელობის შენარჩუნებით აშორებს ზედმეტ სიტყვებსა და გაწელილ ფორმულირებებს:

- აშორებს ზედმეტ სიტყვებს ("გთხოვთ", "ვფიქრობ", "ძირითადად", "სინამდვილეში")
- ამოკლებს გაწელილ ფრაზებს ("იმისათვის, რომ" → "რომ", "ამის შედეგად" → "რადგან")
- აშორებს თავაზიან შემარბილებელ ფორმულირებებს ("ხომ ვერ...", "თუ შეძლებდით...")
- პროგრამირების მოთხოვნებისთვის მორგებული 30-ზე მეტი რეგულარული გამოსახულების წესი

**საუკეთესოა:** პროგრამირების ყოველდღიური სამუშაო პროცესებისა და ხარჯებზე ორიენტირებული გუნდებისთვის.

### აგრესიული რეჟიმი (~50% დაზოგვა)

ისტორიის გონივრული მართვა ხანგრძლივი სესიებისთვის:

- **შეტყობინებების დაძველება** — ძველი შეტყობინებები თანდათან უფრო მეტად იკუმშება
- **ინსტრუმენტის შედეგების შეჯამება** — ინსტრუმენტის ვრცელი გამომავალი მონაცემები შეჯამებებით ჩანაცვლდება
- **სტრუქტურული მთლიანობის დამცავი მექანიზმები** — უზრუნველყოფს `tool_use` + `tool_result` წყვილების თანმიმდევრულობას
- **კონტექსტის ფანჯრის გათვალისწინება** — იცავს თითოეული მოდელის ტოკენების ლიმიტებს

**საუკეთესოა:** ხანგრძლივი გამართვის სესიებისა და დიდი კოდური ბაზებისთვის.

### ულტრა რეჟიმი (~75% დაზოგვა)

მაქსიმალური შეკუმშვა ტოკენების მხრივ კრიტიკული სცენარებისთვის:

- **ევრისტიკული გაფილტვრა** — აშორებს შესაბამისობის ზღვარზე დაბლა მყოფ შეტყობინებებს
- **კოდის ბლოკების შემჭიდროება** — კუმშავს განმეორებით კოდის მაგალითებს
- **ორობითი ძიებით შეკვეცა** — კონტექსტის ფანჯრისთვის პოულობს ოპტიმალურ ჭრის წერტილს
- მოიცავს აგრესიული რეჟიმის ყველა შესაძლებლობას

**საუკეთესოა:** როდესაც კონტექსტის ლიმიტებს ხშირად აწყდებით.

### RTK რეჟიმი (გარე პროვაიდერთან 60-90%-იანი დიაპაზონი)

RTK რეჟიმი ოპტიმიზებულია პროგრამირების აგენტების სესიებში არსებული ვრცელი ინსტრუმენტული გამომავალი მონაცემებისთვის:

- ამოიცნობს ბრძანებების/გამომავალი მონაცემების კლასებს, როგორიცაა `git status`, `git diff`, `git log`, ტესტების გამშვები პროგრამები,
  TypeScript/Vite/Webpack-ის აგებები, ESLint/Biome/Prettier, npm-ის აუდიტები/ინსტალაციები, Docker-ის ჟურნალები, ინფრასტრუქტურის
  გამომავალი მონაცემები და გარსის ზოგადი გამომავალი მონაცემები
- იყენებს JSON-ფილტრების პაკეტებს `open-sse/services/compression/engines/rtk/filters/`-დან
- პროექტის ან გლობალური `filters.toml` ფაილებიდან ახდენს RTK TOML schema v1 ფილტრების იმპორტირებას, ჩაშენებული ტესტების
  ვალიდაციითა და პროექტის ფაილებისთვის ნდობაზე დაფუძნებული დაშვებით
- მოჰყვება 49 ჩაშენებული ფილტრი და ჩაშენებული შემოწმების ნიმუშები
- აშორებს ANSI საკონტროლო მიმდევრობებს, პროგრესის ზოლებს, განმეორებით ხაზებსა და არაპრაქტიკულ ხმაურს
- ინარჩუნებს წარუმატებლობებს, შეცდომებს, გაფრთხილებებს, შეცვლილ ფაილებს, შეჯამებებსა და გრძელი გამომავალი მონაცემების ბოლო ნაწილს
- მხარს უჭერს ნდობაზე დაფუძნებულ პროექტის ფილტრებს, გლობალურ ფილტრებსა და რედაქტირებული დაუმუშავებელი გამომავალი მონაცემების არასავალდებულო აღდგენას

**საუკეთესოა:** აგენტის სესიებისთვის, რომლებიც შეიცავს გარსის, აგების, ტესტების, git-ის, grep-ისა და ფაილების გამომავალი მონაცემების ჩანაწერებს.

### დაწყობილი რეჟიმი (დასაშვები მონაცემების 78-95%-იანი დიაპაზონი)

დაწყობილი რეჟიმი შეკუმშვის რამდენიმე ძრავას განსაზღვრული თანმიმდევრობით უშვებს. ნაგულისხმევი კონვეიერია:

```txt
RTK -> Caveman
```

ეს თანმიმდევრობა ჯერ ტერმინალის/ინსტრუმენტის გამომავალ მონაცემებს ამჭიდროებს, შემდეგ კი
დარჩენილ ბუნებრივ ენაზე დაწერილ მოთხოვნაზე Caveman-ის სემანტიკურ შემჭიდროებას იყენებს. დაწყობილი კონვეიერების კონფიგურაცია შესაძლებელია გლობალურად ან
მარშრუტიზაციის კომბინაციებზე მინიჭებული შეკუმშვის კომბინაციების მეშვეობით.

**საუკეთესოა:** შერეული კონტექსტისთვის, რომელიც შეიცავს ინსტრუმენტების დიდ ჟურნალებს და ადამიანის ინსტრუქციებს ან ასისტენტის შეჯამებებს.

## ზედა დონის დაზოგვის გამოთვლა

OmniRoute შეკუმშვით მიღებულ დანაზოგს ორი წყაროს საფუძველზე აღწერს: ზედა დონის პროექტების საორიენტაციო ტესტებისა და
OmniRoute-ის საკუთარი ძრავების კომბინაციის.

| წყარო   | აქ გამოყენებული ზედა დონის README-ის მაჩვენებელი                                                                                                                                                      |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | გამომავალი ტოკენების `~75%`-ით ნაკლები რაოდენობა, საორიენტაციო ტესტებში გამომავალი მონაცემების საშუალოდ `65%`-იანი დაზოგვა, `22-87%` დიაპაზონი და შემავალი მონაცემების `~46%`-იანი შეკუმშვის ხელსაწყო |
| RTK     | ბრძანებების გამომავალი მონაცემების `60-90%`-იანი დაზოგვა; სესიის მაგალითი: `~118,000 -> ~23,900` ტოკენი, ანუ დაზოგილია `79.7%` (`~80%`)                                                               |

გადაფარული ხელსაწყოს/კონტექსტის მონაცემებისთვის OmniRoute-ის ნაგულისხმევი კომბინაცია ძრავებს თანმიმდევრულად იყენებს:

```txt
RTK -> Caveman
```

ერთობლივი დაზოგვა მულტიპლიკაციურია და არა ადიტიური:

```txt
ერთობლივი = 1 - (1 - RTK-ის დაზოგვა) * (1 - Caveman-ის შემავალი მონაცემების დაზოგვა)
საშუალო   = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
დიაპაზონი = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ეს `78-95%` მაჩვენებელი გამოიყენება მაშინ, როდესაც RTK-სა და Caveman-ს ერთი და იმავე შემავალი მონაცემების/კონტექსტის მოცულობის შემცირება შეუძლიათ.
Caveman-ის პასუხის გამომავალი რეჟიმი ცალკეა: მისი ჩართვისას გამოიყენეთ თავად Caveman-ის გამომავალი მონაცემების დაზოგვის მაჩვენებლები (საშუალოდ `65%`,
მთავარი მაჩვენებელი `~75%`, დიაპაზონი `22-87%`). ბილინგის ჯამური დაზოგვა დამოკიდებულია თქვენს მოთხოვნებსა და გამომავალ მონაცემებს შორის თანაფარდობაზე.

### რას ნიშნავს სინამდვილეში „შესაფერისი“

მთავარ სათაურში მითითებული 15-95%-იანი დიაპაზონი რეალურია, მაგრამ ის მხოლოდ **ჭარბ ან ზედმეტად ვრცელ** შიგთავსზე ვრცელდება — განმეორებით
შეცდომის სტრიქონებზე, აგების ჟურნალზე, რომელიც ერთსა და იმავე გაფრთხილებას განუწყვეტლივ იმეორებს, ან ზედმეტად დიდ `grep`/ფაილის წაკითხვის ამონაბეჭდზე. ეს
**არ** ნიშნავს, რომ ყველა მოთხოვნა ამდენს დაზოგავს.

ემპირიულად დადასტურებულია (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): `stacked` (RTK + Caveman)
გაშვებამ Anthropic-ის ფორმის `tool_result` ბლოკზე, რომელიც 300 იდენტურ შეცდომის სტრიქონს შეიცავდა, უზრუნველყო **ტოკენების 95.93%-იანი დაზოგვა / სიმბოლოების 96.26%-იანი დაზოგვა** — ზუსტად რეკლამირებულ
დიაპაზონში. თუმცა, იმავე კონვეიერის გაშვება ჩვეულებრივ, არაგანმეორებად ხელსაწყოს გამომავალ მონაცემებზე (`grep`-ის დამთხვევების სუფთა სია,
მოკლე ფაილის წაკითხვა, ჩვეულებრივი სასაუბრო ტექსტი) სამართლიანად იძლევა **თითქმის ნულოვან დაზოგვას**, რადგან
წასაშლელი განმეორებადი შიგთავსი არ არსებობს და `validateCompression()` (`validation.ts`) უარს ამბობს ისეთი
გადაწერილი ვერსიის გაგზავნაზე, რომელიც კოდის ბლოკებს, URL-ებს, სათაურებს, ვერსიებს ან ALL-CAPS მუდმივების იდენტიფიკატორებს ამოიღებს ან შეცვლის.

ეს მოსალოდნელი და უსაფრთხო ქცევაა და არა ხარვეზი: პროგრამირების სესია, რომელიც ძირითადად სუფთა ფაილებს კითხულობს ან მათში `grep`-ით ეძებს,
სრულად ჩართული შეკუმშვის შემთხვევაშიც კი ზომიერ ჯამურ დაზოგვას აჩვენებს, ხოლო სესია, რომელიც შეცდომების ციკლს ან
ზედმეტად მრავალსიტყვიან ლინტერს წააწყდება, ამ ტრაფიკზე სრულ 78-95%-იან დიაპაზონს მიიღებს. ნუ გამოიყენებთ ერთი სესიის
დაბალ ჯამურ დაზოგვის პროცენტს იმის მტკიცებულებად, რომ შეკუმშვა არასწორადაა კონფიგურირებული — ჯერ შეამოწმეთ, იყო თუ არა
ხელსაწყოს ძირითადი გამომავალი მონაცემები რეალურად განმეორებადი.

## კონფიგურაცია

### დაფა

გადადით `Dashboard → Context & Cache`-ზე:

- **Caveman** — რეჟიმის არჩევა, ენის პაკეტები, გადახედვა და გლობალური ნაგულისხმევი პარამეტრები
- **RTK** — ბრძანების ფილტრის გადახედვა, RTK უსაფრთხოების პარამეტრები და ფილტრების კატალოგი
- **Compression Combos** — დასახელებული ძრავის კონვეიერები, რომლებიც მინიჭებულია მარშრუტიზაციის კომბინაციებზე
- **Auto-Trigger Threshold** — ავტომატურად ჩართავს შეკუმშვას, როდესაც ტოკენების რაოდენობა გადააჭარბებს ზღვარს

### თითო-კომბინაციის გადაფარვა

`Dashboard → Context & Cache → Compression Combos`-ში, მიანიჭეთ შეკუმშვის კომბინაცია მარშრუტიზაციის კომბინაციას:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ეს საშუალებას გაძლევთ გამოიყენოთ დაწყობილი შეკუმშვა უფასო/კოდირების პროვაიდერებზე, ხოლო ფასიან გამოწერებზე Lite რეჟიმის შენარჩუნებით.

ეს „თითო-კომბინაციის გადაფარვის“ მინიჭება განსხვავებული კონტროლია **მარშრუტიზაციის-კომბინაციის შეკუმშვის რეჟიმის** გადაფარვისგან (Default/Off/Lite/Standard/Aggressive/Ultra) — ეს გადაფარვა არ ირჩევს დასახელებულ შეკუმშვის-კომბინაციის კონვეიერს; ის უბრალოდ ადგენს `compressionMode` ველს, რომელსაც `resolveCompressionPlan` იყენებს. მისი დაყენება შესაძლებელია როგორც კომბინაციის ბარათზე (`Dashboard → Combos`), ასევე, #6760-ის შემდეგ, თითოეულ მარშრუტიზაციის კომბინაციაზე „Assign to routing“ სიაში `Dashboard → Context & Cache → Compression Combos`-ზე, კონვეიერის მინიჭების მოსანიშნი ველის გვერდით, რომელიც ზემოთ არის დოკუმენტირებული. ორივე ზედაპირი შენარჩუნებულია იმავე `PUT /api/combos/{id}` ბოლო წერტილის მეშვეობით.

### თითო-მოთხოვნის გადაფარვა

გაგზავნეთ `x-omniroute-compression` მოთხოვნის სათაური, რათა გადაფაროთ შეკუმშვის გეგმა ერთი მოთხოვნისთვის. მას აქვს უმაღლესი პრიორიტეტი — ის სჯობს მარშრუტიზაციის-კომბინაციის გადაფარვას, აქტიურ პროფილს, ავტომატურ გააქტიურებას და პანელის ნაგულისხმევს. უცნობი მნიშვნელობები იგნორირებულია (მოთხოვნა არასოდეს უარყოფილია) და გლობალური მთავარი გადამრთველი მაინც აკონტროლებს ყველაფერს: როდესაც შეკუმშვა გლობალურად გამორთულია, სათაურს არ შეუძლია მისი ჩართვა. მნიშვნელობები:

| მნიშვნელობა   | ეფექტი                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------- |
| `off`         | ამ მოთხოვნისთვის შეკუმშვა არ ხდება.                                                                       |
| `default`     | პანელიდან მიღებული ნაგულისხმევი პროფილი (უგულებელყოფს აქტიურ პროფილს). დანაკარგიანი ძრავები გამორთულია.   |
| `safe`        | იგივეა, რაც სათაურის გამოტოვება: მხოლოდ დედუპლიკაცია და ცარიელი ადგილების დაკეცვა.                        |
| `allow-lossy` | შეინახეთ ამ მოთხოვნის ოპერატორის გეგმა, მათ შორის შეჯამებები, რელევანტურობის ფილტრები და სტილის გადაწერა. |
| `engine:<id>` | ერთი ძრავა ჩართვისას, მაგ. `engine:rtk`. ეს არის თითო-მოთხოვნის ოპტ-ინი ამ ძრავისთვის.                    |
| `<combo>`     | დასახელებული კომბინაცია, რომელიც ჯერ სახელით (რეგისტრის მიმართ არამგრძნობიარე), შემდეგ ID-ით ემთხვევა.    |

`allow-lossy`, `engine:<id>` ან დასახელებული კომბინაციის გარეშე, დანაკარგიანი ძრავები არ გამოიყენება. მოთხოვნა მაინც იღებს სესიის დედუპლიკაციას და ცარიელი ადგილების დაკეცვას, როდესაც შეკუმშვა ჩართულია.

გამოყენებული გეგმა უკან ბრუნდება `X-OmniRoute-Compression: <mode>; source=<source>` საპასუხო სათაურში, სადაც `<source>` არის `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ან `off`.

Caveman-ის მონაცემებით, გამომავალი ტოკენების რაოდენობა მცირდება `~75%`-ით, საორიენტაციო ტესტებში გამომავალი მონაცემების საშუალო ეკონომიაა `65%`, გამომავალი მონაცემების ეკონომიის დიაპაზონია `22-87%`, ხოლო შემავალი მონაცემების შეკუმშვის ხელსაწყოს მაჩვენებელია `~46%`.

RTK რეჟიმი შთაგონებულია **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)**-ით, რომლის ავტორია **[RTK AI](https://github.com/rtk-ai)** — ეს არის მაღალი წარმადობის მქონე პროექტი, რომელიც განკუთვნილია ტერმინალის, აწყობის, ტესტირების, git-ისა და ხელსაწყოების გამომავალი მონაცემების შეკუმშვისა და გაფილტვრისთვის. RTK-ის მონაცემებით, ეკონომია `60-90%`-ს შეადგენს, ხოლო მის README-ში მოცემულ სესიის ნიმუშში დაზოგილია `~80%`.

## შეკუმშვის გაფართოებული სისტემები

7 სტანდარტული რეჟიმის გარდა, OmniRoute მოიცავს შეკუმშვის რამდენიმე გაფართოებულ სისტემას, რომლებიც კონტექსტის მიხედვით ავტომატურად მუშაობს.

### ქეშის გათვალისწინებით შეკუმშვა

ზოგიერთ პროვაიდერს (მაგალითად, Anthropic-ს მოთხოვნის ქეშირებით) აქვს **მოთხოვნის ქეშირების** მხარდაჭერა, რაც მათ საშუალებას აძლევს, ხარჯებისა და დაყოვნების შესამცირებლად მოთხოვნის ნაწილები დააქეშირონ. როდესაც ქეშირება ჩართულია, აგრესიულმა შეკუმშვამ შეიძლება რეალურად **გააუარესოს** წარმადობა, რადგან ის ცვლის დაქეშილ ტოკენებს და ქეშს აბათილებს.

`cachingAware.ts` მოდული ამ პრობლემას აგვარებს **ქეშირების კონტექსტის გამოვლენით** და **შეკუმშვის სტრატეგიის შესაბამისად მორგებით**.

#### როგორ მუშაობს

1. **ქეშირების კონტექსტის გამოვლენა** — მოთხოვნის სხეულში ეძებს `cache_control` მარკერებს
2. **ქეშირების მხარდამჭერი პროვაიდერების ამოცნობა** — ამოწმებს, აქვს თუ არა სამიზნე პროვაიდერს ქეშირების მხარდაჭერა
3. **სტრატეგიის მორგება** — ქეშირების მხარდამჭერი პროვაიდერებისთვის `aggressive`/`ultra` რეჟიმებს `standard` რეჟიმამდე აქვეითებს
4. **სისტემური მოთხოვნის გამოტოვება** — სისტემური მოთხოვნები, როგორც წესი, ქეშირდება, ამიტომ ისინი არ შეკუმშოთ
5. **დეტერმინისტული გარდაქმნების გამოყენება** — გამოიყენეთ მხოლოდ ის გარდაქმნები, რომლებიც თანმიმდევრულ შედეგს იძლევა

#### კოდის მაგალითი

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← ქეშის მარკერი
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### როდის გამოვიყენოთ

ქეშის გათვალისწინებით შეკუმშვა **ყოველთვის ჩართულია** — კონფიგურაცია საჭირო არ არის. ის მხოლოდ მაშინ აქტიურდება, როდესაც:

- მოთხოვნას აქვს `cache_control` მარკერები
- სამიზნე პროვაიდერს აქვს მოთხოვნის ქეშირების მხარდაჭერა (Anthropic, OpenAI და სხვ.)

### პროგრესული დაძველება

ხანგრძლივი საუბრები შეტყობინებების მრავალ რეპლიკას აგროვებს, თუმცა ძველი რეპლიკები ნაკლებად რელევანტური ხდება. `progressiveAging.ts` მოდული **ამცირებს შეტყობინებების დეტალურობას რეპლიკათა შორის მანძილის მიხედვით**:

- **ბოლო რეპლიკები (0-3)**: უცვლელად ინახება (სრული დეტალებით)
- **საშუალო ასაკის რეპლიკები (4-8)**: მსუბუქი შეკუმშვა (ჰარების, ფორმატირების გასუფთავება)
- **ძველი რეპლიკები (9+)**: ტელეგრაფული შეკუმშვა (შემავსებელი სიტყვების მოცილება, შეჯამება)
- **ძალიან ძველი რეპლიკები (20+)**: მნიშვნელოვნად ჯამდება ან იშლება

#### კოდის მაგალითი

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... კიდევ 50 რეპლიკა ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // პირველი 3 რეპლიკა: უცვლელად
  light: 8, // რეპლიკები 4-8: მსუბუქი შეკუმშვა
  moderate: 20, // რეპლიკები 9-20: ტელეგრაფული შეკუმშვა
  // რეპლიკები 21+: ინტენსიური შეჯამება
});

// saved = დაზოგილი ტოკენების რაოდენობა
```

#### როდის გამოვიყენოთ

პროგრესული დაძველება `aggressive` და `ultra` რეჟიმებისთვის **ყოველთვის ჩართულია**. ის განსაკუთრებით ეფექტურია შემდეგ შემთხვევებში:

- პროგრამული კოდის წერის ხანგრძლივი სესიები
- მრავალდღიანი საუბრები
- მრავალი ხელსაწყოს გამოძახების მქონე აგენტური სამუშაო პროცესები

### ტელეგრაფული გამოყვანის რეჟიმი

`outputMode.ts` მოდული ამატებს **სისტემური მოთხოვნის ინსტრუქციებს**, რათა თავად მოდელმა წარმოქმნას შეკუმშული, ლაკონიური შედეგი („ტელეგრაფული“ სტილით).

#### როგორ მუშაობს

შეყვანის შეკუმშვის ნაცვლად, ეს რეჟიმი ამატებს შემდეგი ტიპის სისტემურ მოთხოვნას:

> „უპასუხე მინიმალური რაოდენობის სიტყვებით. გამოტოვე თავაზიანობის ფორმები. გამოიყენე მოკლე წინადადებები.“

ეს განსაკუთრებით კარგად მუშაობს შემდეგ შემთხვევებში:

- კოდის გენერირება (უფრო ლაკონიური შედეგი = ნაკლები ტოკენი)
- სწრაფი კითხვა-პასუხი (ვრცელი განმარტებები საჭირო არ არის)
- პაკეტური დამუშავება (გამტარუნარიანობის მაქსიმიზაცია)

#### როდის გამოვიყენოთ

#### როგორ მუშაობს ჩასმა

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) არჩევანს
კატალოგთან მიმართებით განსაზღვრავს (უცნობი id-ები და ლოკალთან შეუსაბამო სტილები
გამოირიცხება და შეცდომას არასდროს იწვევს), შერჩეულ ინსტრუქციებს კატალოგის რიგითობით
აერთიანებს, საზღვრების პუნქტს **ერთხელ** ამატებს და ბლოკს ერთი იდემპოტენტურობის
მარკერით (`[OmniRoute Output Styles]`) იწყებს, ამიტომ ხელახლა გამოყენება არაფერს ცვლის. როცა
განსაზღვრულ ენას (იხილეთ ენის შერჩევა ქვემოთ) თარგმანი აქვს, ინგლისურის ნაცვლად
ლოკალიზებული ინსტრუქცია ჩაისმება.

`messages`-ის მქონე body-ში, შიგთავსის გვერდის ავლა (`shouldBypassCavemanOutputMode()`
`open-sse/services/compression/outputMode.ts`-ში) ბოლო სამ შეტყობინებას ამოწმებს და
მთელი turn-ისთვის სტილებს გამოტოვებს, როცა ისინი უსაფრთხოების, შეუქცევადი მოქმედების,
დაზუსტების ან რიგითობაზე დამოკიდებულ საკვანძო სიტყვებს ემთხვევა. გვერდის ავლა მუშაობს, სანამ dashboard-ის **Auto-Clarity Bypass** გადამრთველი (`cavemanOutputMode.autoClarity`) ჩართულია, რაც ნაგულისხმევია; გადამრთველის გამორთვისას არჩეული სტილები ამ turn-ებზეც ვრცელდება.

როცა გვერდის ავლა turn-ს ატარებს, `placeSystemInstruction()` (იმავე ფაილში), რომელიც
ახალ `messages[0]`-ს არასდროს ქმნის, ბლოკს ათავსებს პირველივე ნაპოვნ ადგილას:

1. საწყისი system შეტყობინება სტრიქონული შიგთავსით: ბლოკი მის ტექსტს ემატება.
2. ზედა დონის `system` ველი: ბლოკი სტრიქონის ტექსტს ემატება, ან
   შიგთავსის ბლოკების მასივს ახალი ტექსტური ბლოკის სახით ემატება.
3. პირველი მომდევნო system შეტყობინება სტრიქონული შიგთავსით: ბლოკი მის
   ტექსტს ემატება.
4. თუ ზემოთ ჩამოთვლილთაგან არცერთი არსებობს: ბლოკი `messages`-ის ბოლოში ახალ system შეტყობინებაში თავსდება.

`messages`-ის არმქონე body-ში ბლოკი სტრიქონულ `instructions` ველს ემატება,
ან `instructions` ხდება, როცა body შეიცავს `input`-ს (სტრიქონს ან მასივს). body,
რომელსაც არც `instructions` აქვს და არც `input`, გამოტოვებულია როგორც `no_messages`.

#### როგორ ჩაირთოს

dashboard-ში: **Context → Settings → Compression** — თითო სტილზე თითო სტრიქონი
ჩართვა/გამორთვის გადამრთველითა და დონის ამრჩევით. პროგრამულად, შეკუმშვის კონფიგურაცია
არჩევანს ასე ინახავს:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

უკუთავსებადობა: ძველი კომბინირებული პარამეტრი `outputMode: "caveman"` კვლავ მუშაობს და
`terse-prose`-ზე აისახება; ყველა ძველ ენაში იგი ძველ ჩასმასთან ბაიტობრივად იდენტურია.

ენის შერჩევა: როცა `languageConfig.enabled` ჩართულია, `autoDetect` ირჩევს
უახლესი მომხმარებლის შეტყობინების ენას (იგივე დეტექტორით, რომელსაც შეყვანის ძრავები იყენებს);
`autoDetect`-ის გამორთვა აფიქსირებს `defaultLanguage`-ს. გამორთული → ინგლისური.

სტილის × ენის მატრიცა ფიქსირდება
`tests/unit/compression/output-styles-i18n-matrix.test.ts`-ით: ახალი სტილი ვერ გამოვა
მინიმუმ pt-BR თარგმანის გარეშე (ან მკაფიოდ აღრიცხული გამონაკლისის გარეშე), ხოლო
არსებული სტილი ლოკალს შეუმჩნევლად ვერ დაკარგავს. სტილის დასამატებლად იხილეთ
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### ხელსაწყოს შედეგების შეკუმშვა

`toolResultCompressor.ts` მოდული ხელსაწყოს შედეგებისთვის (ფუნქციების გამოძახებები,
აგენტების გამომავალი მონაცემები, ძიების შედეგები და ა.შ.) უზრუნველყოფს **5 სპეციალიზებულ შეკუმშვის სტრატეგიას**:

1. **ძიების შედეგების შეკუმშვა** — შლის დუბლირებულ შედეგებს, ინარჩუნებს საუკეთესო N-ს
2. **ფაილის წაკითხვის შეკუმშვა** — ამოკლებს დიდ ფაილებს, ინარჩუნებს სათაურებს/იმპორტებს
3. **კოდის შესრულების შეკუმშვა** — ინარჩუნებს მხოლოდ აუცილებელ stdout/stderr-ს
4. **მონაცემთა ბაზის მოთხოვნის შეკუმშვა** — ზღუდავს სტრიქონებს, შლის ჭარბ მეტამონაცემებს
5. **API პასუხის შეკუმშვა** — შლის null ველებს, ამჭიდროებს მასივებს

#### როდის გამოვიყენოთ

ინსტრუმენტის შედეგების შეკუმშვა **ყოველთვის ჩართულია**, როდესაც ინსტრუმენტების გამოძახებები გამოიყენება. დამატებითი
კონფიგურაცია საჭირო არ არის.

### მიმდევრობითი კონვეიერი

მიმდევრობითი რეჟიმი **რამდენიმე ძრავას თანმიმდევრულად** უშვებს — ჩვეულებრივ, ჯერ RTK-ს
(ინსტრუმენტის გამოტანის 60-90%-ით შემცირება), შემდეგ კი Caveman-ს (დარჩენილი ტექსტის
დამატებით 30%-ით შემცირება). შედეგად მიიღწევა **საერთო ჯამში 78-95%-იანი შემცირება**.

#### როგორ მუშაობს

```
შეტანა (1000 ტოკენი)
  → RTK (ბრძანებების მცოდნე ფილტრი) → 200 ტოკენი
    → Caveman (შემავსებელი ტექსტის მოცილება) → 140 ტოკენი
  → გამოტანა (140 ტოკენი, 86%-იანი შემცირება)
```

#### როდის გამოვიყენოთ

გამოიყენეთ მიმდევრობითი რეჟიმი შემდეგ შემთხვევებში:

- ინსტრუმენტებზე ინტენსიურად დამოკიდებული სამუშაო პროცესები (აგენტური პროგრამირება, კვლევა)
- ხარჯებისადმი მგრძნობიარე პაკეტური დამუშავება
- როდესაც ტოკენების მაქსიმალური შემცირება გჭირდებათ

დააკონფიგურირეთ კომბინაციის მეშვეობით:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## შეკუმშვის კომბინაციების გადაფარვები

შეგიძლიათ, სხვადასხვა გამოყენების შემთხვევებისთვის ქცევის ზუსტად მოსარგებად, შეკუმშვის გლობალური რეჟიმი **თითოეული კომბინაციისთვის** ცალ-ცალკე გადაფაროთ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

ეს სასარგებლოა შემდეგ შემთხვევებში:

- **პროგრამირების კომბინაციები**: ხანგრძლივი სესიებისთვის გამოიყენეთ `aggressive` რეჟიმი
- **სწრაფი კითხვა-პასუხის კომბინაციები**: სწრაფი პასუხებისთვის გამოიყენეთ `lite` რეჟიმი
- **ინსტრუმენტებზე ინტენსიურად დამოკიდებული კომბინაციები**: მაქსიმალური ეკონომიისთვის გამოიყენეთ `stacked` რეჟიმი
- **საწარმოო გარემოს კომბინაციები**: ქეშირების მხარდამჭერ პროვაიდერებთან გამოიყენეთ `cache-aware` რეჟიმი
