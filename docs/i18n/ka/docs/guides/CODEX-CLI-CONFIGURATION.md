OmniRoute-ზე, როგორც OpenAI-თან თავსებად ბეკენდზე, მიმართული Codex CLI-ის გამოყენების სრული გზამკვლევი.

---

> **TOML ერთადერთი ქმედითი ფორმატია.** თანამედროვე Codex ექსკლუზიურად კითხულობს
> `~/.codex/config.toml`-ს (შემოწმებულია codex-cli 0.147.0-ზე: `codex --help` აღწერს,
> რომ `-c/--config`-ის გადაფარვები „იტვირთება `~/.codex/config.toml`-დან“). ძველი
> `~/.codex/config.yaml` მემკვიდრეობით npm CLI-ს ეკუთვნოდა და უხმოდ იგნორირდება.
> დაფის გენერატორი (`/api/cli-tools/apply`, ინსტრუმენტი `codex`) TOML-ს
> კონსერვატიული შერწყმით წერს — არსებული გასაღებები და სხვა პროვაიდერების ბლოკები
> შენარჩუნებულია, API გასაღები რჩება `OMNIROUTE_API_KEY`-ში (და არასდროს ფაილში),
> ხოლო დარჩენილი მემკვიდრეობითი `config.yaml` აღინიშნება მიგრაციის შენიშვნის სახით,
> მასში ცვლილებების შეტანის გარეშე.

## ჩასასმელად გამზადებული config.toml

ჩაანაცვლეთ `<YOUR_HOST>` და `<YOUR_KEY>` თქვენი მნიშვნელობებით:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ისტორიის შენახვის ლიმიტი თითოეული ინსტრუმენტის გამოძახებისთვის

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc ან ~/.zshrc — გასაღების რეალური მნიშვნელობა, არასდროს config.toml-ში
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: ChatGPT აპში ჩაშენებული Codex

თუ Codex ChatGPT-ის დესკტოპის აპის მეშვეობით დააინსტალირეთ, `codex`-ის ბინარული
ფაილი შესაძლოა მხოლოდ აპის პაკეტში არსებობდეს და ჯერ არ იყოს თქვენი shell-ის
`PATH`-ში. დაამატეთ რესურსების დირექტორია shell-ის გაშვების ფაილში:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

გახსენით ახალი shell და შემდეგ გადაამოწმეთ:

```bash
command -v codex
codex --version
```

### ლოკალური OmniRoute ავთენტიფიკაციის გარეშე: საკმარისია დროებითი გასაღები

Codex ამოწმებს, არსებობს თუ არა `env_key`-ით მითითებული გარემოს ცვლადი,
**მანამდე**, სანამ პირველი მოთხოვნა CLI-ს დატოვებს. თუ თქვენი **ლოკალური**
OmniRoute-ის ინსტანცია ავთენტიფიკაციას არ საჭიროებს, ნებისმიერი არაცარიელი
დროებითი მნიშვნელობა გამოდგება:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

თუ თქვენი OmniRoute სერვერი დაცულია ან დისტანციურია, ამის ნაცვლად გამოიყენეთ რეალური გასაღები.

> **ჰოსტის გავრცელებული ვარიანტები**
>
> | წვდომა         | URL                           |
> | -------------- | ----------------------------- |
> | ლოკალური ქსელი | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | Loopback       | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — რატომ მუშაობს ის ყველა მოდელისთვის

Codex CLI-მ `wire_api = "chat"` (Chat Completions) 2026 წლის თებერვალში მოძველებულად გამოაცხადა და ახლა **მოითხოვს** `wire_api = "responses"`-ს (OpenAI Responses API). `wire_api = "chat"`-ის დაყენება v0.138-დან მოყოლებული გაშვებისთანავე ავარიულ დასრულებას იწვევს.

ბევრი პროვაიდერი, მათ შორის GLM და Kimi, კვლავ მხოლოდ Chat Completions-ის საბოლოო წერტილს გვთავაზობს. DeepSeek V4 ახლა გვთავაზობს როგორც ნატიურ Responses API-ს, ასევე Anthropic-თან თავსებად საბოლოო წერტილს; OmniRoute ნაგულისხმევად Responses-ს იყენებს და DeepSeek-ის თითოეულ კავშირს Anthropic-თან თავსებადობის არჩევის საშუალებას აძლევს.

**OmniRoute ამას გამჭვირვალედ აგვარებს:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute ირჩევს პროვაიდერის ნატიურ პროტოკოლს და საჭიროების შემთხვევაში გარდაქმნის
    → POST /responses (DeepSeek V4) ან /chat/completions (Mistral / GLM / Kimi / სხვები)
```

OmniRoute-ის გამოყენებისას ცალკე გარდამქმნელი პროქსი არასდროს გჭირდებათ. **ყველა მოდელი იყენებს `wire_api = "responses"`-ს** — დანარჩენს OmniRoute ამუშავებს.

> **`wire_api` ნაგულისხმევი მნიშვნელობაა** — ველის ნაგულისხმევი მნიშვნელობაა `"responses"` და მისი `config.toml`-დან სრულად გამოტოვება შეიძლება. ის ცხადად მხოლოდ მაშინ მიუთითეთ, თუ თქვენი განზრახვის დოკუმენტირება გსურთ.

## კონტექსტის ფანჯარა და კომპაქტაცია

### ტოკენების კონფიგურაციის ველები

| ველი                             | აღწერა                                                                                                                                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | აქტიური მოდელის ტოკენების სრული ბიუჯეტი. მიუთითეთ მოდელისთვის გამოცხადებული ლიმიტი.                                                                                                                                                     |
| `model_auto_compact_token_limit` | ზღვარი, რომელიც ისტორიის ავტომატურ კომპაქტაციას იწვევს. **მაქსიმუმი: `model_context_window`-ის 90%** — 90%-ზე მეტი მნიშვნელობები გაფრთხილების გარეშე იგნორირდება.                                                                       |
| `tool_output_token_limit`        | ისტორიაში თითოეული ხელსაწყოს გამოძახების შედეგისთვის შესანახი ტოკენების ზედა ზღვარი. ხელს უშლის ხელსაწყოს ერთ დიდ პასუხს მთელი ფანჯრის შევსებაში. **ეს გამომავალი მონაცემების მაქსიმუმი არ არის** — ეს ისტორიაში შენახვის ზედა ზღვარია. |
| `compact_prompt`                 | კომპაქტაციისას გამოყენებული სისტემური მოთხოვნის ჩაშენებული გადაფარვა (v0.138+).                                                                                                                                                         |

> **შენიშვნა `model_max_output_tokens`-ის შესახებ**: ეს ველი **Codex CLI-ის კონფიგურაციის სქემის ნაწილი არ არის** (Codex-ის Rust კოდურ ბაზაში არ გვხვდება). მითითების შემთხვევაში იგი გაფრთხილების გარეშე იგნორირდება. მას ნუ დაეყრდნობით — ისტორიაში ხელსაწყოს შედეგებიდან შესანახი მოცულობის სამართავად გამოიყენეთ `tool_output_token_limit`.

## მოდელის პრეფიქსი: `cx/`

OmniRoute-ში ყველა Codex მოდელი იყენებს `cx/` პრეფიქსს:

| Codex CLI-ის სახელი     | OmniRoute-ის მოდელი |
| ----------------------- | ------------------- |
| `cx/gpt-5.5`            | GPT-5.5 სტანდარტული |
| `cx/gpt-5.4`            | GPT-5.4 სტანდარტული |
| `cx/gpt-5.4-mini`       | GPT-5.4 mini        |
| `cx/gpt-5.1-codex-mini` | GPT-5.1 Codex mini  |

სხვა პროვაიდერები საკუთარ პრეფიქსებს იყენებენ (`kmc/`, `glm/`, `ds/`, `ollamacloud/`, `opencode-go/`, `mistral/`) — პრეფიქსი OmniRoute-ის პროვაიდერის ფსევდონიმს ემთხვევა.

## მსჯელობის ინტენსივობა

აკონტროლებს, პასუხის გაცემამდე რამდენად ბევრს „იფიქრებს“ მოდელი.

| მნიშვნელობა | რისთვის გამოიყენება                                               |
| ----------- | ----------------------------------------------------------------- |
| `none`      | მსჯელობის გარეშე — პირდაპირი პასუხი                               |
| `low`       | მარტივი ამოცანები (სახელის შეცვლა, ფორმატირება)                   |
| `medium`    | **სერვერის ნაგულისხმევი მნიშვნელობა**, როდესაც მითითებული არ არის |
| `high`      | საშუალო სირთულის ამოცანები (რეფაქტორინგი, გამართვა)               |
| `xhigh`     | არქიტექტურა, ღრმა ანალიზი, რთული პრობლემები                       |

```bash
# ცალკეული გამოძახებისთვის მნიშვნელობის ჩანაცვლება
codex -c model_reasoning_effort=low "შეუცვალე x ცვლადს სახელი და დაარქვი count"
codex -c model_reasoning_effort=xhigh "დააპროექტე ავტორიზაციის მოდული"
```

ასევე დააყენეთ მსჯელობის **შეჯამება**, რათა Desktop-მა შეძლოს აზროვნების ტექსტის ჩვენება (და არა მხოლოდ დაშიფრული ბლოკებისა):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # ან ultra, როცა მხარდაჭერილია
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### OmniRoute-ის აზროვნების ბიუჯეტი (სერვერის პარამეტრი)

OmniRoute-ის ჰოსტზე **Settings → AI → Thinking Budget** უნდა იყოს დაყენებული **`passthrough`**-ზე, რათა Codex-ის ინტენსივობა/შეჯამება ზედა დონის სერვისამდე მივიდეს. რეჟიმი **`auto` შლის** კლიენტის ყველა `reasoning` / `reasoning_effort` ველს და აზროვნების პანელებს ცარიელს დატოვებს მაშინაც კი, როდესაც Codex სწორადაა კონფიგურირებული.

სრული სახელმძღვანელო: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

შეკუმშვა და მოთხოვნის კეში ერთმანეთისგან დამოუკიდებელია და `passthrough` რეჟიმშიც განაგრძობს მუშაობას.

## პროფილები — მოდელის/სამუშაო პროცესის სახელდებული კონფიგურაციები

პროფილები საშუალებას გაძლევთ, ერთი ალმით გადართოთ მოდელი და კონტექსტური ფანჯარა. თითოეული პროფილი არის ბრტყელი
`~/.codex/<name>.config.toml` ფაილი, რომელიც საბაზისო `config.toml`-ს ზემოდან ეფარება.

> **სახელდების წესი (Codex CLI v0.137+):** ფაილი უნდა იყოს `~/.codex/<name>.config.toml` — **`profile-` პრეფიქსის გარეშე**.
> CLI გარდაქმნის `-p kimi-k27`-ს → `~/.codex/kimi-k27.config.toml`. თუ ფაილი ვერ მოიძებნა, ნაგულისხმევი კონფიგურაცია უხმაუროდ გამოიყენება.

```bash

codex -p glm52 "არქიტექტურის მიმოხილვა"
codex --profile deepseek-flash "შეუცვალე ცვლადს სახელი"   # სწრაფი, იაფი
```

## პროფილების ავტომატურად გენერირება `omniroute setup-codex`-ით

თუ OmniRoute-ს VPS-ზე უშვებთ, შეგიძლიათ პროფილის ფაილები მოქმედი მოდელების კატალოგიდან ავტომატურად დააგენერიროთ:

```bash
# VPS-იდან (იყენებს ლოკალურ OmniRoute-ს 20128 პორტზე)
omniroute setup-codex

# ნებისმიერი კომპიუტერიდან — მიუთითეთ თქვენი VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# წინასწარი ნახვა ფაილების ჩაწერის გარეშე
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# მხოლოდ GLM და Kimi პროფილების გენერირება
omniroute setup-codex --only glm,kimi

# მორგებულ დირექტორიაში ჩაწერა
omniroute setup-codex --codex-home /path/to/.codex
```

ბრძანება იღებს `/v1/models`-ს, ცნობილი მოდელებისთვის იყენებს ოპტიმიზებულ პროფილებს, სხვა თავსებადი ტექსტური მოდელებისთვის კი კატალოგის მეტამონაცემებზე გადადის და თითოეულისთვის ქმნის `~/.codex/<name>.config.toml` ფაილს. ოპერაცია იდემპოტენტურია — მისი ხელახლა გაშვება უსაფრთხოა.

OmniRoute-ს ასევე შეუძლია ამავე პროფილის ფაილების **ავტომატური სინქრონიზაცია** მას შემდეგ, რაც პროვაიდერის მოდელების წარმატებული აღმოჩენა/იმპორტი მოქმედ კატალოგს შეცვლის. ეს ფუნქცია **ნებაყოფლობითია და ნაგულისხმევად გამორთულია**: ჩართეთ ის **CLI Code dashboard**-იდან („CLI profile auto-sync“ → Codex), ან დააყენეთ `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (ის ასევე ითვალისწინებს `CLI_ALLOW_CONFIG_WRITES`-ს, რომელიც ნაგულისხმევად ჩართულია). ჩართვისას ის მხოლოდ ცალკეულ `~/.codex/*.config.toml` პროფილის ფაილებს წერს; არასოდეს ცვლის აქტიურ/ნაგულისხმევ `~/.codex/config.toml`-ს, Codex-lb-ის პარამეტრებს, ავთენტიფიკაციას ან პროვაიდერის არჩევანს.

## Codex-ის გაშვება `omniroute launch-codex`-ით

Codex-ის გაშვებამდე ამოწმებს თქვენი OmniRoute ინსტანციის მდგომარეობას:

```bash
# ლოკალურ OmniRoute-თან გაშვება (ნაგულისხმევი პორტი 20128)
omniroute launch-codex

# კონკრეტული პროფილით გაშვება
omniroute launch-codex --profile kimi-k27

# დისტანციურ VPS-თან გაშვება
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# დამატებითი არგუმენტების codex-ისთვის გადაცემა
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex ასევე წარმოადგენს ორი ზოგადი, მანიფესტით მართული შესვლის წერტილის სამიზნეს
(`bin/cli/cli-manifest.mjs`):

```bash
# მოდელის ინტერაქტიური ამრჩევი → წერს ~/.codex/<name>.config.toml-ს (TOML, env_key)
omniroute configure codex

# codex-ის გაშვება -c ალმებით ჩასმული omniroute პროვაიდერით (კონფიგურაცია არ იწერება)
omniroute run codex
```

### `config.toml`-ის ახალი ველები (v0.137-ის შემდეგ)

```toml
# ნატიური ვებძიება (v0.139)
web_search = "live"   # "disabled" | "cached" | "live"

# დეველოპერის ცალკე სისტემური მითითება (v0.138)
developer_instructions = "Always prefer functional style."
```

## ხანგრძლივი ამოცანები

OmniRoute-ის ორ ნაგულისხმევ პარამეტრს შეუძლია შეუმჩნევლად ჩაშალოს Codex CLI-ის მრავალსაათიანი სესიები. არცერთი მათგანი არ არის Codex CLI-ის პარამეტრი — ორივე OmniRoute-ის მხარესაა. მომხმარებლები, რომლებსაც კონფიგურაცია გადააქვთ ზედა დონის პროქსიებიდან, რომლებიც ანგარიშებს ამაგრებენ და უმოქმედობის შეზღუდვებს თიშავენ, ხშირად ორივე პრობლემას აწყდებიან და ასკვნიან, რომ OmniRoute-ს „ხანგრძლივი სესიის შენარჩუნება არ შეუძლია“.

| სიმპტომი                                                                                | სავარაუდო მიზეზი                                                                                  | პარამეტრი                |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------ |
| სესია გამუდმებით ცვლის ანგარიშებს / მოთხოვნებს შორის prompt-cache-ის უწყვეტობა იკარგება | სესიის მიბმის TTL არის `0` (გამორთულია)                                                           | `sessionAffinityTtlMs`   |
| კავშირი მსჯელობის შუაში წყდება კლიენტისთვის ხილული მოთხოვნის გარეშე                     | ნაკადის უმოქმედობის კონტროლი ამოქმედდა ზედა დონიდან ბლოკის 10 წუთის განმავლობაში მიუღებლობის გამო | `STREAM_IDLE_TIMEOUT_MS` |

დაკავშირებული განხილვები: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (ხანგრძლივი ამოცანების გაწყვეტა), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (რატომ არის მიბმა ნაგულისხმევად გამორთული). თვალყურის დევნება: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. სესიის მიბმა — ერთი საუბრის ერთ ანგარიშზე მიმაგრება

**ნაგულისხმევი მნიშვნელობა:** `sessionAffinityTtlMs = 0` (გამორთულია).

**სად უნდა დააყენოთ**

- მართვის პანელი → **პარამეტრები → მარშრუტიზაცია** → **სესიის მიბმა** → **მიბმის TTL (წამები)** (`ComboDefaultsTab`)
- ან PATCH-მოთხოვნით განაახლეთ პარამეტრები, `sessionAffinityTtlMs`-ის **მილიწამებში** მითითებით (Zod-ის დიაპაზონი `0`–`86_400_000`, ანუ მაქსიმუმ 24 საათი)

> #7274-ში სახელი შეიცვალა მხოლოდ Codex-ისთვის განკუთვნილი `codexSessionAffinityTtlMs`-იდან. ძველი გასაღები კვლავ მიიღება მხოლოდ წასაკითხ ფსევდონიმად; ახალმა კონფიგურაციებმა უნდა გამოიყენონ `sessionAffinityTtlMs`. როდესაც TTL `0`-ზე მეტია, მიბმა უკვე ვრცელდება **ნებისმიერ** პროვაიდერზე და არა მხოლოდ Codex-ზე — იხილეთ [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → სესიის მიბმა.

**რა ფუჭდება, როდესაც მნიშვნელობა 0-ად რჩება**

Codex-ის მრავალეტაპიანი საუბრის თითოეული მოთხოვნა დამოუკიდებლად მარშრუტიზდება აქტიური კომბინირებული სტრატეგიით და თითოეულ ჯერზე შეიძლება **სხვადასხვა ანგარიშზე** მოხვდეს. ეს არღვევს ზედა დონის სესიის / prompt-cache-ის უწყვეტობას. OmniRoute Codex-ის სესიის სათაურებს (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) და სხეულის ისეთ ველებს, როგორებიცაა `prompt_cache_key` / `session_id`, მხოლოდ მაშინ ამოწმებს, როდესაც TTL `0`-ზე მეტია (`extractSessionAffinityKey` ფაილში `src/sse/services/auth.ts`).

**რეკომენდაცია მრავალსაათიანი ერთი ამოცანისთვის**

დააყენეთ TTL **ამოცანის მოსალოდნელ რეალურ ხანგრძლივობაზე მეტი** (UI-ის მაქსიმუმია **86400 წამი** = 24 საათი):

| ამოცანის მოსალოდნელი ხანგრძლივობა | მიბმის TTL (UI, წამები)    | `sessionAffinityTtlMs` |
| --------------------------------- | -------------------------- | ---------------------- |
| რამდენიმე საათი                   | `14400` (4 სთ)             | `14400000`             |
| მთელი ღამე / ~12 სთ               | `43200` (12 სთ)            | `43200000`             |
| სრული დღე                         | `86400` (24 სთ, მაქსიმუმი) | `86400000`             |

ნებაყოფლობით ჩართვა მიზანმიმართული გადაწყვეტილებაა: მიბმის გამორთვა უპირატესობას ანიჭებს ანგარიშებს შორის დატვირთვის დაბალანსებას; მისი ჩართვა კი — ერთი ხანგრძლივი აგენტური სესიის უწყვეტობას. ეს სახელმძღვანელო ნაგულისხმევ მნიშვნელობას **არ** ცვლის — ოპერატორებმა, რომლებიც Codex-ის ხანგრძლივ ამოცანებს ასრულებენ, ეს ფუნქცია თავად უნდა ჩართონ.

### 2. ნაკადის უმოქმედობის ტაიმაუტი — არ შეწყვიტოთ მსჯელობის წყნარი ეტაპები

**ნაგულისხმევი მნიშვნელობა:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 წუთი). თუ მნიშვნელობა მითითებული არ არის, ის მემკვიდრეობით მიიღება `REQUEST_TIMEOUT_MS`-იდან; საერთო საბაზისო მნიშვნელობაც 600000-ია. იხილეთ [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → ტაიმაუტები.

**რა ფუჭდება ნაგულისხმევი მნიშვნელობისას**

Codex-ის reasoning / tool ეტაპი, რომელიც 10 წუთზე მეტხანს ჩუმად რჩება და **არცერთ რეალურ upstream chunk-ს** არ იღებს, SSE-ის უმოქმედობის watchdog-ის მიერ იძულებით იხურება (`open-sse/utils/stream.ts`). კლიენტი ხშირად მხოლოდ კავშირის მოულოდნელ გაწყვეტას ხედავს — რაც შეესაბამება აღწერას: „ავტომატურად შეჩერდა ყოველგვარი შეტყობინების გარეშე“.

კრიტიკული დეტალი: OmniRoute-ის სინთეზური SSE **heartbeat არ ანულებს** უმოქმედობის ტაიმერს. `lastChunkTime` განახლდება მხოლოდ რეალური upstream body chunk-ის მიღებისას. მოდელი, რომელიც ჩუმად აგრძელებს „ფიქრს“, watchdog-ის თვალსაზრისით არაფრით განსხვავდება გაჭედილი upstream-ისგან.

Undici-ს body-ის უმოქმედობასთან დაკავშირებული პარამეტრი: `FETCH_BODY_TIMEOUT_MS` (ნაგულისხმევად ასევე იგივე 10-წუთიანი საბაზისო მნიშვნელობა აქვს; `0` მას გამორთავს). სტრიმინგისას `FETCH_TIMEOUT_MS` მხოლოდ კავშირის დამყარებას / პირველი headers-ის მიღებას მოიცავს — სტრიმის გააქტიურების შემდეგ შეფერხებებს `STREAM_IDLE_TIMEOUT_MS` და `FETCH_BODY_TIMEOUT_MS` მართავს.

**რეკომენდაცია მრავალსაათიანი ერთეული დავალებისთვის**

OmniRoute-ის პროცესის გარემოში (`.env` / compose / systemd):

```bash
# ხანგრძლივი reasoning ეტაპებისთვის გამორთეთ სტრიმის უმოქმედობისა და body-ის უმოქმედობის შეზღუდვები
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

ან გაზარდეთ ისინი იმაზე მეტად, ვიდრე მოსალოდნელი ყველაზე ხანგრძლივი ჩუმი შუალედია (მნიშვნელობები მილიწამებშია):

```bash
# მაგალითი: upstream chunk-ებს შორის დაუშვით მაქსიმუმ 2-საათიანი სიჩუმე
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

ამ env vars-ის შეცვლის შემდეგ გადატვირთეთ OmniRoute.

### კონკრეტული ინსტრუქცია — მრავალსაათიანი Codex-ის დავალება

1. **მიამაგრეთ ანგარიში:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12სთ) ან `86400` (მაქს. 24სთ).
2. **გაზარდეთ / გამორთეთ უმოქმედობის შეზღუდვები** OmniRoute-ის გარემოში:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. შეინარჩუნეთ Codex-ის ჩვეულებრივი `config.toml` (`wire_api = "responses"`, სწორი `base_url`, `OMNIROUTE_API_KEY`) — ამ ორი ქცევის სამართავად Codex-ის მხარეს affinity/idle პარამეტრები არ არსებობს.
4. გადატვირთეთ OmniRoute, შემდეგ კი გაუშვით Codex-ის ხანგრძლივი დავალება.

| `sessionAffinityTtlMs`   | `0` (გამორთული)                     | **არა** — რჩება სურვილისამებრ ჩასართავი (დატვირთვის დაბალანსება და უწყვეტობა; იხილეთ Discussion #5718) |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 წთ)                    | **არა** — ზოგადი ტრაფიკისთვის რჩება 10 წუთი; ხანგრძლივი Codex-ის ოპერატორები ზრდიან ან თიშავენ მას     |

რომელიმე ნაგულისხმევი მნიშვნელობის გლობალურად შეცვლა გავლენას მოახდენდა ინსტანციის ყველა კლიენტის ქცევაზე და არა მხოლოდ Codex-ზე. აღწერეთ პარამეტრები დოკუმენტაციაში; დატოვეთ ნაგულისხმევი მნიშვნელობები უცვლელად, სანამ ოპერატორი აშკარა გადაწყვეტილებას არ მიიღებს.

### უმოქმედობით გამოწვეული გათიშვების დიაგნოსტიკა

როდესაც უმოქმედობის watchdog ამოქმედდება, OmniRoute ჟურნალში წერს დაახლოებით ასეთ სტრიქონს:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

მოძებნეთ `Idle timeout: no data from` (ან კოდი `stream_idle_timeout` / შეცდომის სახელი `StreamIdleTimeoutError`). პროვაიდერის სეგმენტი არის ის მნიშვნელობა, რომელიც OmniRoute-მა ამ მოთხოვნისთვის გამოიყენა (`codex`, სხვა პროვაიდერის id, ან `provider`, თუ უცნობია) — ის ყოველთვის პირდაპირი მნიშვნელობით `codex` არ არის.

## პრობლემების მოგვარება

**`Error: wire_api = "chat" is no longer supported`**
კონფიგურაციიდან წაშალეთ `wire_api = "chat"`. მიუთითეთ `wire_api = "responses"` ან გამოტოვეთ ეს ველი (v0.138-დან ნაგულისხმევი მნიშვნელობაა `"responses"`).

**`Error: model not found`**
შეამოწმეთ, რომ მოდელი OmniRoute-ში სწორი პრეფიქსით არსებობს. გამოიყენეთ `omniroute models list` ან გახსენით `/dashboard/providers/<provider>`.

**`Authentication error`**
დარწმუნდით, რომ `OMNIROUTE_API_KEY` ექსპორტირებულია: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex პირველი მოთხოვნის გაგზავნამდე ამოწმებს, არსებობს თუ არა გარემოს ცვლადი. დაცული სერვერებისთვის მოახდინეთ რეალური გასაღების ექსპორტი, ხოლო თუ თქვენი **ლოკალური** OmniRoute-ის ინსტანცია ავტორიზაციას არ საჭიროებს, გამოიყენეთ არაცარიელი დროებითი მნიშვნელობა, მაგალითად `OMNIROUTE_API_KEY=local`. თუ ის `~/.bashrc`-ში ან `~/.zshrc`-ში დაამატეთ, ხელახლა გაუშვით გარსი.

**`Connection refused`**
შეამოწმეთ, რომ OmniRoute გაშვებულია და `base_url`-ის ჰოსტი/პორტი თქვენი ქსელისთვის სწორია (ლოკალური, Tailscale ან VPS).

**სესია კონტექსტის ლიმიტთან მიახლოებისას ითიშება**
ცალსახად მიუთითეთ `model_context_window` და `model_auto_compact_token_limit`. იხილეთ ზემოთ მოცემული კონტექსტის ფანჯრის ცხრილი.

**კომპაქტაცია მეტისმეტად გვიან იწყება**
შეამცირეთ `model_auto_compact_token_limit` ფანჯრის 80–85%-მდე. არასოდეს მიუთითოთ 90%-ზე მეტი.

**პროფილი არ იტვირთება (`-p <name>` უხმოდ იგნორირებულია)**
დარწმუნდით, რომ ფაილი არსებობს მისამართზე `~/.codex/<name>.config.toml` (`profile-` პრეფიქსის გარეშე). გაუშვით `ls ~/.codex/*.config.toml`.

**Codex-ის ხანგრძლივი დავალება შესრულებისას შუაში წყდება / სვლებს შორის ანგარიშებს ცვლის**
იხილეთ [ხანგრძლივად შესრულებადი დავალებები](#long-running-tasks). ჩართეთ სესიის მიბმა (TTL დავალების ხანგრძლივობაზე მეტი უნდა იყოს) და გაზარდეთ ან გამორთეთ `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. OmniRoute-ის ჟურნალებში `grep`-ით მოძებნეთ `Idle timeout: no data from`.
