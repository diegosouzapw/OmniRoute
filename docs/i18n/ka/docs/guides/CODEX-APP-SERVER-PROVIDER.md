OmniRoute გთავაზობთ OpenAI Codex-ის გამოყენების **ორ** გზას:

| პროვაიდერი             | როგორ უკავშირდება OpenAI-ს                                                                                                                                                                                        | გამოყენების შეზღუდვა                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **`codex`**            | თქვენს ChatGPT/OpenAI OAuth ტოკენს პირდაპირ Responses API-ში ხელახლა გადასცემს                                                                                                                                    | **დიახ** — ოფიციალური სესია პროქსის/როუტერის მეშვეობით გამოსაყენებლად ავტორიზებული არ არის |
| **`codex-app-server`** | JSON-RPC/WebSocket-ის მეშვეობით მართავს **Codex CLI-ის საკუთარ `codex app-server`-ს**; CLI თავად ფლობს და ავტომატურად აახლებს თავის OAuth-ს (`~/.codex/auth.json`), ზუსტად ისე, როგორც ინტერაქტიული `codex` სესია | **არა** — OmniRoute არასოდეს გადასცემს ტოკენს API-ში ხელახლა                               |

რადგან `codex-app-server` ტოკენს არასოდეს გადასცემს ხელახლა, მასზე არ
ვრცელდება სესიის ხელახალი გადაცემის გამოყენების შეზღუდვა. თუმცა საჭიროა, რომ
**Codex CLI ხელმისაწვდომი იყოს კონფიგურირებულ app-server URL-ზე** და ეს CLI
**ავტორიზებული** უნდა იყოს.

## 1. არქიტექტურა

```
┌─ OmniRoute აპი ─────────────────┐        ┌─ codex-app-server sidecar ─────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ შესაძლებლობის ტოკენი)        │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  თავად მართავს OpenAI OAuth-ს       │
└──────────────────────────────────┘        │  (~/.codex/auth.json, ავტო-განახლება)│
        │ გაზიარებულია (compose ტომები)      └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → WS შესაძლებლობის ტოკენი (ორივე ამონტაჟებს მას)
  codex-appserver-home    → ~/.codex (auth.json იწერება მართვის პანელის მიერ,
                             ხოლო sidecar-ის codex app-server კითხულობს მას)
```

- sidecar უსმენს **მხოლოდ** შიდა compose ქსელში
  (`ws://codex-app-server:1456`), შესაძლებლობის ტოკენის მიღმა. ის **არასოდეს**
  ქვეყნდება ჰოსტზე ან ინტერნეტში.
- Codex CLI ჩაშენებულია `omniroute:base`-ში, ამიტომ sidecar-ის გაშვებისას
  ჰოსტზე ან მომხმარებლის კომპიუტერზე codex-ის დაყენება საჭირო არ არის.

## 2. გაშვება

```bash
# გაუშვით სტეკი codex app-server sidecar პროფილთან ერთად:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

პირველი გაშვებისას sidecar ქმნის თავის WS შესაძლებლობის ტოკენს (გაზიარებულ
`codex-appserver-token` ტომში), ხოლო აპი იმავე ტოკენს
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`-ის მეშვეობით კითხულობს. ტოკენის
ხელით დაკავშირება საჭირო არ არის.

## 3. დაკავშირება + ავტორიზაცია

1. მართვის პანელში დაამატეთ კავშირი **OpenAI Codex (App-Server)**-ისთვის. API
   გასაღები ან ტოკენი საჭირო არ არის (ეს ავტორიზაციის არმომთხოვნი პროვაიდერია —
   ავტორიზაციას sidecar მართავს).
2. თუ sidecar-ის Codex CLI-ში **ჯერ არ ხართ ავტორიზებული**, კავშირის
   ჯანმრთელობის შემოწმება აჩვენებს _„გაშვებულია, მაგრამ ავტორიზებული არ არის“_
   (და არა ავტორიზაციის წითელ შეცდომას). გამოიყენეთ **ChatGPT-ით შესვლა**: ეს
   თქვენს ბრაუზერში გაუშვებს Codex-ის სტანდარტულ მოწყობილობის OAuth-ს, შემდეგ კი
   **ავტორიზაციის გამოყენების** მეშვეობით `~/.codex/auth.json`-ს გაზიარებულ ტომში
   ჩაწერს (ერთი და იგივე ავტორიზაცია ემსახურება როგორც `codex`, ისე
   `codex-app-server` პროვაიდერებს).
3. ავტორიზაციის შემდეგ ჯანმრთელობის შემოწმება მწვანე ხდება (ის ამოწმებს როგორც
   `/readyz`-ს, **ისე** `account/read`-ს — ანუ სერვერი ერთდროულად გაშვებული და
   ავტორიზებულია) და მუშაობას იწყებს.

მართვის პანელი არსებულ გამართულ `~/.codex/auth.json`-ს არასოდეს გადააწერს — ის
მხოლოდ მაშინ წერს, როდესაც ფაილი არ არსებობს ან მისი ტოკენი მოძველებულია
(სარეზერვო ასლი ყოველთვის იქმნება).

## 4. განთავსების სცენარები

- **ოპერატორი უკვე ავტორიზებული Codex CLI-ით** — sidecar-ში
  (`codex-appserver-home`) დაამონტაჟეთ თქვენი ჰოსტის `~/.codex` და გამოტოვეთ
  ავტორიზაციის ეტაპი.
- **საჯარო მომხმარებელი, რომელსაც codex ლოკალურად არ აქვს დაყენებული** —
  ამას მნიშვნელობა არ აქვს: CLI sidecar-შია. მომხმარებელი ავტორიზაციას მხოლოდ
  მართვის პანელის მეშვეობით გადის.
- **Bare-metal OmniRoute (sidecar-ის გარეშე, ჰოსტის codex)** —
  `OMNIROUTE_CODEX_APPSERVER_WS` მიუთითეთ თქვენს საკუთარ `codex app-server`-ზე
  და დარწმუნდით, რომ ჰოსტის codex ავტორიზებულია; თუ ბინარული ფაილი არ არსებობს,
  გამოჩნდება მინიშნება „codex არ არის დაყენებული“.

## 5. საცხოვრებელი / UDP გამავალი ტრაფიკი (ოპერატორის დამატება, არ მოჰყვება)

ზემოთ აღწერილი ზოგადი sidecar გამავალ ტრაფიკს კონტეინერის ჩვეულებრივი ქსელის
მეშვეობით აგზავნის. ოპერატორი, რომელსაც Codex-ის ტრაფიკის **საცხოვრებელი
გამოსასვლელის** მეშვეობით გატარება სჭირდება (მაგ., TUN tailscale sidecar,
რომელსაც TCP + UDP/QUIC გადააქვს), ამას ცალკე compose override-ის სახით უშვებს;
ის განზრახ **არ** შედის მოწოდებულ `codex-app-server` პროფილში. ამ კონფიგურაციის
შესახებ იხილეთ შიდა საოპერაციო სახელმძღვანელო.
