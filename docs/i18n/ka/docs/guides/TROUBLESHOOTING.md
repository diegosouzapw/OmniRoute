### უფასო პროვაიდერებზე სიხშირის შეზღუდვა (429 / 400 / 401)

**სიმპტომი**: `model: "auto"`-ს უფასო/ავთენტიფიკაციის არმომთხოვნ პროვაიდერებთან (opencode, auggie და სხვ.) გამოყენებისას პასუხების ნაცვლად პერიოდულად იღებთ `HTTP 429`, `400` ან `401` შეცდომას. რამდენიმე წამის შემდეგ იმავე მოთხოვნის ხელახლა გაგზავნისას ის წარმატებით სრულდება, თუმცა ავტომატიზაცია (cron დავალებები, აგენტები, სკრიპტები) პირველივე შეცდომისას წყდება.

**ძირეული მიზეზი**: ერთმანეთს სამი დამოუკიდებელი ხარვეზის რეჟიმი ემატება:

1. **პროვაიდერის სიხშირის ლიმიტი (`429`)**: უფასო ტარიფებს დროის თითოეულ მონაკვეთში კვოტის დაწესება შეუძლიათ. პარალელური გამოძახებების მოზღვავება კვოტას ამოწურავს, ამიტომ შემდეგი მოთხოვნა უარყოფილი იქნება, სანამ დროის მონაკვეთი არ განახლდება.
2. **გაუმართავი მოდელი პირდაპირი გადაცემის რეჟიმში (`400`/`401`)**: `auto/*` პულები შეიძლება შეიცავდეს `opencode`-ის პირდაპირი გადაცემის მოდელებს, რომლებიც კატალოგში რეგისტრირებულია, მაგრამ მოქმედი ავტორიზაციის მონაცემები არ გააჩნია (მაგ., `oc/north-mini-code-free` → `401`). ავტომატური მარშრუტიზატორი ერთ-ერთ მათგანს ცდის, მარცხდება და შეცდომა ვრცელდება მანამ, სანამ სათადარიგო ვარიანტი ჩაირთვება.
3. **კონკურენტულობით გაძლიერება (დატვირთვისას `429`)**: როდესაც რამდენიმე აგენტის/cron-ის სესია ერთდროულად მიმართავს `auto`-ს, მოთხოვნების ჯამური სიხშირე აჭარბებს უფასო პროვაიდერების მიერ დასაშვებ ზღვარს, რის გამოც მართებული გამოძახებებიც კი ბოროტად გამოყენებად აღინიშნება.

**დადასტურებული გამოსწორება (საზოგადოების მიერ მოწოდებული, 2026-08-10)**: მოარგეთ სამი გარემოს ცვლადი ისე, რომ როტაციამ, კონკურენტულობამ და სათადარიგო ვარიანტზე გადასვლამ უფასო ტარიფების ცვალებადობა მარცხის ნაცვლად საკუთარ თავზე აიღოს:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401-ისას სხვა მოდელზე/პროვაიდერზე გადასვლა (გაუმართავი პირდაპირი გადაცემის მოდელების გამოტოვება)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # მძიმე მოთხოვნების მიღების მკაფიო ზედა ზღვარი (ნაგულისხმევად დაყენებული არ არის: მოთხოვნების რაოდენობაზე ზღვარი არ მოქმედებს; იხილეთ შენიშვნა ქვემოთ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ნელი ზედა დონის სერვისებისთვის შეზღუდული ლოდინის გაზრდა RATE_LIMIT_MAX_WAIT_MS-ის ნაგულისხმევ მნიშვნელობაზე მეტად
```

დააყენეთ ისინი OmniRoute პროცესის გარემოში (დემონში, მაგალითად, LaunchAgent plist-ის ან `systemctl edit`-ის საშუალებით), შემდეგ კი გადატვირთეთ OmniRoute. როტაციის ალამი ყველაზე ეფექტური ბერკეტია: ის სრულ მარცხს პულში არსებული გამართული პროვაიდერის გამოყენებით გამჭვირვალე ხელახალ მცდელობად გარდაქმნის.

**შენიშვნა**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ზღუდავს ერთდროულად გაშვებული მძიმე — გრძელი კონტექსტის მქონე — მოთხოვნების რაოდენობას; ეს ზღვარი მოთხოვნების მიღების კარიბჭეა და არა პროვაიდერის სიხშირის შემზღუდველი. **#503-fanout განახლება:** ეს ცვლადი ნაგულისხმევად აღარ ყენდება (ახლა ის მხოლოდ მკაფიოდ კონფიგურირებისას მოქმედებს, როგორც ზემოთაა ნაჩვენები) — ამის ნაცვლად, მძიმე მოთხოვნების მიღებას ზღუდავს ავტომატურად გამოთვლილი ბაიტების ბიუჯეტი (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), რომელიც ჰოსტის მეხსიერების რეალური ზღვრის მიხედვით მასშტაბირდება. ამიტომ ახალ განთავსებაში ამ ცვლადის საერთოდ დაუყენებლად გაცილებით ნაკლები `503 chat_admission_busy` უარყოფა უნდა დაფიქსირდეს; თუმცა მისი აქ მკაფიოდ დაყენება კვლავ ზუსტად ისე მუშაობს, როგორც დოკუმენტაციაშია აღწერილი. ბაიტების ბიუჯეტის მკაფიოდ მითითებული მნიშვნელობები 8 MiB–2 GiB დიაპაზონში იზღუდება. `413 body_exceeds_budget` დროებითი შეცდომა არ არის: გაზარდეთ ბაიტების ეს ბიუჯეტი, შეამცირეთ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ან გაზარდეთ პროცესის მეხსიერების ზღვარი. `inflight_bytes_budget`-ით დატვირთვის მოხსნა დროებითი კონკურენციის შედეგია და ხელახალი მცდელობა კვლავ შესაძლებელია. თითოეული პროვაიდერის სიხშირის შეზღუდვა (`open-sse/services/rateLimitManager.ts`) ცალკე იმართება `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` და `RATE_LIMIT_AUTO_ENABLE` ცვლადებით — იხილეთ `.env.example`.

**როგორ გადაამოწმოთ, რომ იმუშავა**: გაუშვით თქვენი აგენტი/cron ორჯერ სწრაფი მიმდევრობით და დარწმუნდით, რომ ორივე გაშვება წარმატებით სრულდება. შესწორებამდე მეორე გაშვება, როგორც წესი, აბრუნებს `429`/`401` შეცდომას. შესწორების შემდეგ წარუმატებელი მცდელობები (თუ ასეთი იქნება) ავტომატურად და შეუმჩნევლად განმეორდება და გამოძახება დასრულდება. ასევე შეგიძლიათ გაუშვათ `curl /monitoring/health` და პროვაიდერის კავშირებზე დააკვირდეთ `rateLimitedUntil` ველს, ხოლო შესაბამისი პროვაიდერებისთვის — `circuitBreakers.providerBreakers[].state`-ს. მდგომარეობა შეიძლება იყოს `CLOSED`, `DEGRADED`, `OPEN` ან `HALF_OPEN` (იხილეთ `src/shared/utils/circuitBreaker.ts`), ხოლო პროვაიდერი, რომლის გამოძახებებიც კვლავ წარუმატებლად სრულდება, გადავა მდგომარეობებში `CLOSED → DEGRADED → OPEN`, სანამ განულების დროის ფანჯარა საცდელ გამოძახებას არ დაუშვებს (`HALF_OPEN`).

**თუ კვლავ ხედავთ 429-ს**: ამ პროვაიდერის აქტიურ ანგარიშს ნამდვილად ამოეწურა _კვოტა_ (და არა მხოლოდ სიხშირის ლიმიტი). დაამატეთ იმავე პროვაიდერის მეორე ანგარიში OmniRoute-ის მართვის პანელში → Providers → Accounts, ან გამოიყენეთ დამატებით სხვა უფასო პროვაიდერი (მაგ., `routeway`, `auggie`). როტაცია მხოლოდ დროებითი სიხშირის შეზღუდვისა და 400/401 შეცდომების შემთხვევაში გეხმარებათ; კვოტის სრულად ამოწურვისას საჭიროა მეორე ავტორიზაციის მონაცემი ან სხვა პროვაიდერი.

**თუ ხედავთ 403-ს ხედვის მოდელებზე (`auto/vision`, `bazaarlink/*`)**: დაკავშირებულ ანგარიშს არ აქვს ფასიანი გეგმა, რომელიც ხედვის ფუნქციას მოიცავს, ან API გასაღებს არასაკმარისი ნებართვები აქვს. პროვაიდერის მართვის პანელში გადაამოწმეთ, რომ გასაღების წვდომის ფარგლები ხედვას/მულტიმოდალურ ფუნქციებს მოიცავს, ან დააკავშირეთ ფასიანი დონის ანგარიში და დატოვეთ ის ხედვის სამიზნედ.

## npm install-ის გაფრთხილებები (ERESOLVE / peer / deprecated)

როდესაც გაუშვებთ `npm install -g omniroute` ბრძანებას, შესაძლოა იხილოთ გაფრთხილებების დიდი რაოდენობა, როგორიცაა `npm warn ERESOLVE`, peer-დამოკიდებულებების შეტყობინებები და `deprecated` შეტყობინებები. **ეს მოსალოდნელი და უვნებელია.** ინსტალაცია წარმატებით დასრულდა, თუ გამოტანილ შედეგში ხედავთ `added <N> packages` შეტყობინებას.

Peer-დამოკიდებულებების ამოხსნის გაფრთხილებების დასამალად გამოიყენეთ OmniRoute-ის მიერ მხარდაჭერილი ინსტალაციის ფორმა:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` მალავს მხოლოდ `ERESOLVE` და peer-დამოკიდებულებების შეტყობინებებს. მოძველების შესახებ შეტყობინებები კვლავ გამოჩნდება, რადგან ისინი ტრანზიტიული მესამე მხარის პაკეტებიდან მოდის; ისინი არ მიუთითებს, რომ ინსტალაცია წარუმატებლად დასრულდა.

გაფრთხილებები გამოწვეულია მესამე მხარის პაკეტებში არსებული მოძველებული peer-დამოკიდებულებების დიაპაზონებით, რომლებსაც OmniRoute არ აკონტროლებს:

1. **`marked-terminal` მოითხოვს `marked >=1 <16`-ს, ნაპოვნია `marked@18`** — პრაქტიკაში გამართულად მუშაობს; upstream peer-დიაპაზონი უბრალოდ მოძველებულია.
2. **`deprecated prebuild-install@7.1.3`** — ტრანზიტიული დამხმარე საშუალება ნატიური ბინარული ფაილების ჩამოსატვირთად. ის არ
   გამოიყენება დაფიქსირებული `wreq-js` სატრანსპორტო binding-ის დასაინსტალირებლად და არ მიუთითებს, რომ web-cookie
   პროვაიდერის ტრანსპორტის გამართვა წარუმატებლად დასრულდა.

**მოქმედება საჭირო არ არის** — upstream პაკეტების fork-ის შექმნის გარეშე გაფრთხილებების სრულად გამორთვა შეუძლებელია.

## npm install-სკრიპტების დაბლოკვის გაფრთხილება (გლობალური ინსტალაცია)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` ბრძანების გაშვებისას npm-ის ახალი ვერსიები (v11+ და v12+) ნაგულისხმევად ბლოკავს პაკეტის სასიცოცხლო ციკლის სკრიპტებს და აჩვენებს install-scripts გაფრთხილებას:

```
npm warn install-scripts 7 პაკეტის ინსტალაციის სკრიპტები დაიბლოკა, რადგან ისინი არ არის გათვალისწინებული allowScripts-ში:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### შეიძლება თუ არა ამ გაფრთხილების უგულებელყოფა?

**ნაწილობრივ, თუმცა სკრიპტების გარეშე გაშვება რეკომენდებული არ არის.** OmniRoute მოიცავს შეცდომის შემთხვევაში ალტერნატივაზე გადასვლის მექანიზმებს: თუ ნატიური `better-sqlite3` binding-ების ჩატვირთვა დამოუკიდებელი bundle-იდან ვერ ხერხდება, აპლიკაცია გადადის ალტერნატიულ დრაივერებზე, როგორიცაა `node:sqlite` ან `sql.js` (იხილეთ [SQLite-ის გაშვების გარემოს ამორჩევა](../ops/SQLITE_RUNTIME.md)). სერვერი მაინც გაეშვება, თუმცა `sql.js`-ის მსგავსი WASM ალტერნატივების გამოყენება გამორთავს SQLite WAL (წინასწარი ჩაწერის ჟურნალი) რეჟიმს და ზრდის მეხსიერებისა და დისკთან სინქრონიზაციის ზედნადებ ხარჯებს.

### რომელი სკრიპტებია რეალურად აუცილებელი?

OmniRoute-ის გასაშვებად ყველა დაბლოკილი სკრიპტი აუცილებელი არ არის:

- **აუცილებელი (`omniroute`, `better-sqlite3`):** OmniRoute მუშაობს Next.js-ის დამოუკიდებელი აპლიკაციის bundle-იდან (`dist/`). ინსტალაციის დროს npm ჩამოტვირთავს ან აკომპილირებს კონკრეტული ჰოსტისთვის განკუთვნილ ნატიურ SQLite დრაივერს ზედა დონის `node_modules/better-sqlite3/`-ში. შემდეგ OmniRoute-ის `postinstall` სკრიპტი (`scripts/build/postinstall.mjs`) ამოწმებს და აკოპირებს ამ ჰოსტისთვის განკუთვნილ ბინარულ ფაილებს `dist/node_modules/`-ში, რათა დამოუკიდებელ სერვერს მათზე წვდომა ჰქონდეს. თუ `omniroute`-ის postinstall სკრიპტი დაბლოკილია, კოპირების ეს ეტაპი გამოტოვებული იქნება.
- **არასავალდებულო/ტრანზიტიული (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** ესენია build-ის დამხმარე საშუალებები, ცვლილებებზე დაკვირვების ხელსაწყოები ან სისტემური keychain-ის უტილიტები. მათი დაშვება თავიდან აგაცილებთ build-ის გაფრთხილებებს, თუმცა ისინი ძირითადი მარშრუტიზაციის ფუნქციონირებისთვის აუცილებელი არ არის.
- **გამორიცხული (`onnxruntime-node`):** არასავალდებულო დამოკიდებულება ლოკალური AI embedding-ებისთვის და OmniRoute-ის მუშაობისთვის **საჭირო არ არის**. მისი postinstall სკრიპტი NuGet-იდან ჩამოტვირთავს დაახლოებით 300MB მოცულობის CUDA რესურსებს; ნუ დაამატებთ მას დაშვებულთა სიაში, თუ მხარდაჭერილ აპარატურაზე ლოკალური ONNX აჩქარების გამოყენებას ცალსახად არ გეგმავთ.

### რეკომენდებული გამოსავალი

გლობალური ინსტალაციის დროს აუცილებელი install-სკრიპტების დასაშვებად და გაფრთხილებების გასაჩუმებლად OmniRoute-ისა და მისი ნატიური დამოკიდებულებებისთვის მიუთითეთ `--allow-scripts`:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

ალტერნატიულად, თქვენს მომხმარებლის ანგარიშზე ყველა გლობალური ინსტალაციისთვის ამის მუდმივად დასაკონფიგურირებლად:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

ინსტალაციის შემდეგ გაუშვით ჩაშენებული დიაგნოსტიკური ხელსაწყო, რათა დარწმუნდეთ, რომ ნატიური binding-ები და გაშვების გარემო გამართულად მუშაობს:


აგების სამიზნე), რომელიც Chromium-სა და მის დამოკიდებულებებს მოიცავს; საბაზისო იმიჯი მათ

### Avast/AVG ათავსებს `README.md`-ს კარანტინში ნიშნულით `MD:HttpRequest-inf[Susp]`

**ეს ცრუ დადებითი შედეგია. არაფერი არ არის ინფიცირებული და არანაირი მოქმედება არ არის საჭირო.**

Avast და AVG იყენებენ ევრისტიკულ შემოწმებას, რომელიც მონიშნავს უბრალო ტექსტის/Markdown-ის ფაილებს, თუ ისინი HTTP-მოთხოვნის მსგავს ბევრ ბმულს შეიცავს. OmniRoute-ის `README.md` შედის npm პაკეტში (ის მითითებულია `package.json` → `files`-ში), ამიტომ გლობალური ინსტალაციისას ის ხვდება `node_modules/omniroute/README.md`-ში — და შეიცავს დაახლოებით 15 `http://localhost:20128/...` მაგალითს (MCP HTTP/SSE საბოლოო წერტილებს, A2A `.well-known` URL-სა და `curl` ფრაგმენტებს). ბმულების ასეთი სიმჭიდროვე საკმარისია ევრისტიკული შემოწმების გასააქტიურებლად.

თუ ეს მხოლოდ ახლახან დაიწყო: ფაილის ტიპი არ შეცვლილა. README-ში გაიზარდა საბოლოო წერტილების ცხრილი (დაემატა MCP HTTP + SSE + A2A) და `curl`-ის მაგალითების რაოდენობა, რის გამოც მან ზღვარს გადააჭარბა.

ეს ფაილი უმოქმედო დოკუმენტაციაა და საერთოდ არ შეიცავს შესრულებად შიგთავსს. მისი კარანტინიდან აღდგენა უსაფრთხოა.

**რა უნდა გააკეთოთ:**

1. **შეაჩერეთ შეტყობინებები** — თქვენს ანტივირუსში გამონაკლისად დაამატეთ ინსტალაციის დირექტორია
   (Avast: Settings → Exceptions), მათ შორის თქვენი გლობალური `node_modules`-ის გზა და/ან
   OmniRoute-ის მონაცემთა დირექტორია (`~/.omniroute/`).
2. **შეატყობინეთ ცრუ დადებითი შედეგის შესახებ** — <https://www.avast.com/false-positive-file-form.php>,
   თან დაურთეთ კარანტინში მოთავსებული `README.md`. ეს არის გამოსწორება, რომელიც ყველას ეხმარება, რადგან

### Kaspersky მონიშნავს Desktop აპს როგორც `PDM:Trojan.Win32.Generic`

**ეს ქცევითი ევრისტიკული შემოწმებით გამოწვეული ცრუ დადებითი შედეგია. არაფერი არ არის ინფიცირებული.**
Kaspersky-ის `PDM:` პრეფიქსი ნიშნავს, რომ დასკვნა მომდინარეობს მისი Proactive Defense Module-იდან

მავნე პროგრამებს შეადაროს. როდესაც ის აქტიურდება, Kaspersky „უკუაქცევს“ მთელ ინსტალაციას — შლის
ფაილებს, რომლებიც უკვე ჩაწერილი ჰქონდა — რის შედეგადაც აპი დაზიანებული ან დაკარგულია.

  ბიბლიოთეკა, რომელიც გამოიყენება აპის შიგნით პროვაიდერთან შესასვლელად და ბრაუზერზე დაფუძნებული

  ვებ-ქუქიების პროვაიდერებზე (`<arch>` არის `x64` ან `arm64`).

**რატომ აქტიურდება:** Windows-ის ინსტალატორი **ჯერ არ არის ხელმოწერილი კოდის სერტიფიკატით**, ამიტომ
ხელმოუწერელ NSIS ინსტალატორს ნულოვანი რეპუტაცია აქვს და ქცევითი ევრისტიკული შემოწმებები მაქსიმალური
სიმკაცრით მუშაობს. ამას ემატება შეფუთული ნატიური DLL და ასობით `.js` ფაილი, რომლებიც იწერება
`%LOCALAPPDATA%\Programs\OmniRoute`-ში (მათ შორის Next.js-ის ავტონომიური ანაწყობის მიერ შექმნილი,
ჰეშის სუფიქსის მქონე პაკეტების დირექტორიები), რაც საკმარისია ევრისტიკული შემოწმების გასააქტიურებლად.

**რა უნდა გააკეთოთ:**

   ახლავს `latest.yml`, რომლის `sha512` ველი (base64) მოიცავს
   `OmniRoute.Setup.<version>.exe` ინსტალატორს. PowerShell-ში, ინსტალატორის შემცველი საქაღალდიდან:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   ```

## Node.js-თან თავსებადობა

<a name="nodejs-compatibility"></a>

### შესვლის გვერდი ითიშება ან აჩვენებს შეცდომას „Module self-registration“

**მიზეზი:** თქვენ იყენებთ Node.js-ის ვერსიას, რომელიც OmniRoute-ის მიერ დამტკიცებულ უსაფრთხო გარემოს მინიმალურ მოთხოვნებს არ აკმაყოფილებს. ყველაზე გავრცელებული შემთხვევაა Node 22-ის ან 24-ის ისეთი ძველი პატჩ-ვერსიის გამოყენება, რომელიც OmniRoute-ის მიერ მოთხოვნილ უსაფრთხოების განახლებების მინიმალურ ზღვარს ჩამორჩება.

**სიმპტომები:**

- შესვლის გვერდზე ჩანს ცარიელი ეკრანი ან სერვერის შეცდომა
- კონსოლში ჩანს `Error: Module did not self-register` ან მსგავსი შეცდომები, რომლებიც ნატიურ ბაინდინგებს უკავშირდება
- თუ გაშვების გარემო მხარდაჭერილ უსაფრთხოების პოლიტიკას არ შეესაბამება, შესვლის გვერდზე გამოჩნდება **ნარინჯისფერი გამაფრთხილებელი ბანერი**, რომელზეც მითითებულია თქვენი Node-ის ვერსია

**გამოსწორება:**

1. დააინსტალირეთ მხარდაჭერილი Node.js LTS გამოშვება (რეკომენდებულია: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. შეამოწმეთ თქვენი ვერსია: `node --version`-მა უნდა აჩვენოს `v24.0.0` ან უფრო ახალი ვერსია 24.x LTS ხაზიდან
3. ხელახლა დააინსტალირეთ OmniRoute: `npm install -g omniroute`
4. გადატვირთეთ: `omniroute`

> **მხარდაჭერილი უსაფრთხო ვერსიები:** `>=22.22.2 <23` ან `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) და Node.js 26 სრულად მხარდაჭერილია.

### npm v11+: `better-sqlite3` არ არის დაინსტალირებული (მოდული ვერ მოიძებნა)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**მიზეზი:** npm v11 (რომელიც მოჰყვება Node.js 24+-ს) ნაგულისხმევად ბლოკავს არასავალდებულო
დამოკიდებულებების ინსტალაციის სკრიპტებს. რადგან `better-sqlite3` ჩამოთვლილია `optionalDependencies`-ში
და საჭიროებს ნატიურ კომპილაციას (`node-gyp rebuild`), npm მას შეტყობინების გარეშე გამოტოვებს.

**სიმპტომები:**

- გაშვებისას სერვერი ითიშება შეცდომით `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` აჩვენებს „No such file or directory“
- `npm ls better-sqlite3` აჩვენებს `(empty)`-ს

**გამოსწორება:**

1. დაამტკიცეთ ინსტალაციის სკრიპტები და ხელახლა დააინსტალირეთ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ან წინასწარ აგებული ვერსია ხელით დააინსტალირეთ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. შეამოწმეთ, რომ მუშაობს: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file“

<a name="macos-native-module-rebuild"></a>

**მიზეზი:** გლობალური `npm install -g omniroute`-ის შემდეგ, პაკეტში შემავალი `better-sqlite3`-ის ნატიური ბინარული ფაილი შესაძლოა დაკომპილირებული იყოს სხვა არქიტექტურისთვის ან Node.js ABI-სთვის, რომელიც ადგილობრივად გაშვებულ გარემოს არ ემთხვევა. ეს ხშირად ხდება macOS-ზე (როგორც Apple Silicon-ზე, ისე Intel-ზე), როდესაც წინასწარ აგებული ბინარული ფაილი თქვენს გარემოს არ შეესაბამება.

**სიმპტომები:**

- გაშვებისთანავე სერვერი ითიშება `dlopen` შეცდომით
- შეცდომა შეიცავს ტექსტს `slice is not valid mach-o file`
- სრული მაგალითი:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**გამოსწორება — ხელახლა ააგეთ თქვენი ადგილობრივი გარემოსთვის (Node.js-ის ვერსიის დაქვეითება საჭირო არ არის):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **შენიშვნა:** ეს ნატიურ ბაინდინგს თქვენი ადგილობრივი Node.js-ის ვერსიისა და CPU-ს არქიტექტურისთვის ხელახლა აკომპილირებს, რითაც ბინარული ფაილების შეუსაბამობას აღმოფხვრის. ოფიციალურად მხარდაჭერილი გაშვების გარემოს დიაპაზონია **`>=22.22.2 <23` ან `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` ფაილში `src/shared/utils/nodeRuntimeSupport.ts`, რაც შეესაბამება `package.json`-ის `engines` ველს). Node.js 24.x LTS (Krypton) და Node.js 26 სრულად არის მხარდაჭერილი `better-sqlite3` v12.x-თან ერთად.

## პროქსის პრობლემები

<a name="proxy-issues"></a>

### პროვაიდერის ვალიდაციისას ნაჩვენებია „fetch failed“

**მიზეზი:** API გასაღების ვალიდაციის საბოლოო წერტილი (`POST /api/providers/validate`) ადრე გვერდს უვლიდა პროქსის კონფიგურაციას, რაც იწვევდა შეცდომებს იმ გარემოებში, სადაც საჭიროა ტრაფიკის პროქსის მეშვეობით მარშრუტიზაცია.

**გამოსწორება (v3.5.5+):** ეს პრობლემა ახლა გამოსწორებულია. პროვაიდერის ვალიდაცია სრულდება `runWithProxyContext`-ის მეშვეობით და ავტომატურად ითვალისწინებს პროვაიდერის დონისა და გლობალურ პროქსის პარამეტრებს.

### ტოკენის მდგომარეობის შემოწმება სრულდება შეცდომით „fetch failed“

**მიზეზი:** OAuth ტოკენის ფონური განახლებისას პროქსის კონფიგურაცია თითოეული კავშირისთვის ცალ-ცალკე არ განისაზღვრებოდა.

**გამოსწორება (v3.5.5+):** ტოკენის მდგომარეობის შემოწმების დამგეგმავი ახლა განახლების მცდელობამდე თითოეული კავშირისთვის განსაზღვრავს პროქსის კონფიგურაციას. განაახლეთ v3.5.5+-ზე.

### SOCKS5 პროქსი აბრუნებს შეცდომას „invalid onRequestStart method“

**მიზეზი:** Node.js 22-ზე undici@8-ის დისპეტჩერი შეუთავსებელია Node-ის ჩაშენებულ `fetch()` იმპლემენტაციასთან.

**გამოსწორება (v3.5.5+):** როცა პროქსის დისპეტჩერი აქტიურია, თანმიმდევრული მუშაობის უზრუნველსაყოფად OmniRoute ახლა თავად undici-ის `fetch()` ფუნქციას იყენებს. განაახლეთ v3.5.5+-ზე.

### MITM პროქსი WSL-ში: Windows ჰოსტზე გაშვებული დესკტოპ-აპლიკაციების ტრაფიკი არ გადაიჭირება

**მიზეზი:** MITM პროქსი და მისი CA სერტიფიკატი ინსტალირდება იმ გარემოში, სადაც OmniRoute მუშაობს. WSL-ის გამოყენებისას ეს გარემო Linux სტუმარი სისტემაა, ხოლო AI დესკტოპ-აპლიკაციები (Kiro, Trae, Copilot, Zed, …) Windows ჰოსტზე მუშაობს. ჰოსტის აპლიკაციები არ ენდობიან სტუმარი სისტემის სერტიფიკატების საცავს და არ იყენებენ სტუმარი სისტემის პროქსის პარამეტრებს, ამიტომ დესკტოპ-ტრაფიკის გადაჭერა არ აქტიურდება.

**რეკომენდაცია:** გაუშვით OmniRoute უშუალოდ იმავე ოპერაციულ სისტემაზე, რომელზეც მუშაობს დესკტოპ-აპლიკაციები, რომელთა ტრაფიკის გადაჭერაც გსურთ (Windows — Windows-ის აპლიკაციებისთვის; ანალოგიურად macOS/Linux). თუ OmniRoute-ს WSL-ში დატოვებთ და ჰოსტის აპლიკაციებს დაუმიზნებთ, დაგჭირდებათ გენერირებული CA სერტიფიკატის ხელით სანდოდ მონიშვნა Windows ჰოსტზე და თითოეული ჰოსტის აპლიკაციის ქსელის/პროქსის პარამეტრების WSL პროქსის საბოლოო წერტილზე მითითება — ეს არის არამხარდაჭერილი და არასტაბილური კონფიგურაცია.

## პროვაიდერის პრობლემები

**გამოსწორება:**

1. შეამოწმეთ კვოტის მაჩვენებელი მართვის პანელზე
2. გამოიყენეთ კომბინაცია სარეზერვო დონეებით
3. გადაერთეთ უფრო იაფ/უფასო დონეზე

### სიხშირის შეზღუდვა

**მიზეზი:** გამოწერის კვოტა ამოიწურა.

**გამოსწორება:**

- დაამატეთ სარეზერვო ვარიანტები: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`

2. წაშალეთ პროვაიდერის კავშირი და თავიდან დაამატეთ

## Cloud-ის პრობლემები

### Cloud სინქრონიზაციის შეცდომები

1. დარწმუნდით, რომ `BASE_URL` მიუთითებს თქვენს გაშვებულ ინსტანციაზე (მაგ., `http://localhost:20128`)
2. დარწმუნდით, რომ `CLOUD_URL` მიუთითებს თქვენს Cloud საბოლოო წერტილზე (მაგ., `https://omniroute.dev`)
3. შეინარჩუნეთ `NEXT_PUBLIC_*` მნიშვნელობები სერვერის მხარის მნიშვნელობებთან შესაბამისობაში

### Cloud-ზე `stream=false` აბრუნებს 500-ს

**სიმპტომი:** `Unexpected token 'd'...` Cloud-ის საბოლოო წერტილზე არანაკადური გამოძახებებისას.

**მიზეზი:** ზედა დონის სერვისი აბრუნებს SSE დატვირთვას, ხოლო კლიენტი JSON-ს მოელის.

**დროებითი გამოსავალი:** Cloud-ზე პირდაპირი გამოძახებებისთვის გამოიყენეთ `stream=true`. ლოკალური გაშვების გარემო შეიცავს SSE→JSON სარეზერვო მექანიზმს.

### Cloud მიუთითებს, რომ დაკავშირებულია, მაგრამ აჩვენებს „Invalid API key“

1. შექმენით ახალი გასაღები ლოკალური მართვის პანელიდან (`/api/keys`)
2. გაუშვით Cloud სინქრონიზაცია: ჩართეთ Cloud → დაასინქრონეთ ახლა
3. ძველმა/არასინქრონიზებულმა გასაღებებმა Cloud-ზე შესაძლოა კვლავ დააბრუნოს `401`

## Docker-ის პრობლემები

### Docker-ის IPv6 / კავშირის განულება

<a name="docker-ipv6"></a>

**სიმპტომები:** `curl http://localhost:20128/v1/models` აბრუნებს `curl: (56) Recv failure: Connection reset by peer`. მართვის პანელი და არაავთენტიფიცირებული საბოლოო წერტილები მუშაობს, მაგრამ ავთენტიფიცირებული საბოლოო წერტილები ვერ მუშაობს — ეს ავთენტიფიკაციის პრობლემას ჰგავს, თუმცა ასე არ არის.

**მიზეზი:** `docker run -p 20128:20128` პორტს აქვეყნებს როგორც `0.0.0.0`-ზე (IPv4), ისე `::`-ზე (IPv6), მაგრამ კონტეინერში არსებული პროცესი მხოლოდ IPv4-ზე უსმენს. ჰოსტებზე, სადაც `localhost` პირველად `::1`-ად გარდაიქმნება, კავშირი ხვდება გამოქვეყნებულ IPv6 პორტზე, რომლის უკანაც მსმენელი არ არის → კავშირი ნულდება.

**გამოსწორება:**

1. **სწრაფი დიაგნოსტიკა:** გაუშვით `curl -4 http://localhost:20128/v1/models`. თუ `-4`-ით მუშაობს, მის გარეშე კი ვერა, გაქვთ IPv6 მიბმის შეუსაბამობა.
2. **მუდმივი გამოსწორება:** თქვენს `docker run` ბრძანებაში `-p 127.0.0.1:20128:20128`-ის გამოყენებით აშკარად მიაბით IPv4-ს:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ეს აიძულებს IPv4 მიბმას და ასევე თავიდან აგაცილებთ პროქსის ჰოსტის ყველა ინტერფეისზე გამოქვეყნებას.

## გამართვა

### ჟურნალის ფაილების ჩართვა

თქვენს `.env` ფაილში დააყენეთ `APP_LOG_TO_FILE=true`. აპლიკაციის ჟურნალები იწერება `logs/`-ში.
მოთხოვნის არტეფაქტები ინახება `${DATA_DIR}/call_logs/`-ში, როდესაც პარამეტრებში
გამოძახებების ჟურნალის კონვეიერი ჩართულია.
როდესაც კონვეიერის ჩაწერა ჩართულია, ნაკადის ფრაგმენტების დატვირთვების გამოსატოვებლად დააყენეთ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`,
ან KB-ში არტეფაქტის ზომის ზღვრის შესაცვლელად მოარგეთ `CALL_LOG_PIPELINE_MAX_SIZE_KB`.

### პროვაიდერის მდგომარეობის შემოწმება

```bash
# მდგომარეობის მართვის პანელი
http://localhost:20128/dashboard/health

# API-ის მდგომარეობის შემოწმება
curl http://localhost:20128/api/monitoring/health
```

### გაშვების გარემოს საცავი

- ძირითადი მდგომარეობა: `${DATA_DIR}/storage.sqlite` (პროვაიდერები, კომბინაციები, ალიასები, გასაღებები, პარამეტრები)
- გამოყენება: SQLite ცხრილები `storage.sqlite`-ში (`usage_history`, `call_logs`, `proxy_logs`) + არასავალდებულო `${DATA_DIR}/call_logs/`
- აპლიკაციის ჟურნალები: `<repo>/logs/...` (როდესაც `APP_LOG_TO_FILE=true`)
- გამოძახებების ჟურნალის არტეფაქტები: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, როდესაც გამოძახებების ჟურნალის კონვეიერი ჩართულია

მოთხოვნების ჟურნალების გვერდზე მოქმედება **ისტორიის გასუფთავება** ასუფთავებს `call_logs`-ს, მოძველებულ
`request_detail_logs`-ს და ლოკალურ `${DATA_DIR}/call_logs/` არტეფაქტების დირექტორიას.

## Circuit Breaker-ის პრობლემები

### პროვაიდერი გაჭედილია OPEN მდგომარეობაში

როდესაც პროვაიდერის Circuit Breaker OPEN მდგომარეობაშია, მოთხოვნები იბლოკება გაგრილების პერიოდის ამოწურვამდე.

**გამოსწორება:**

1. გადადით **მართვის პანელი → პარამეტრები → მდგრადობა**
2. შეამოწმეთ Circuit Breaker-ის ბარათი პრობლემური პროვაიდერისთვის
3. ყველა Breaker-ის გასასუფთავებლად დააწკაპუნეთ **ყველას ჩამოყრა**-ზე, ან დაელოდეთ გაგრილების პერიოდის ამოწურვას
4. ჩამოყრამდე დარწმუნდით, რომ პროვაიდერი ნამდვილად ხელმისაწვდომია

### პროვაიდერი მუდმივად ააქტიურებს Circuit Breaker-ს

თუ პროვაიდერი განმეორებით გადადის OPEN მდგომარეობაში:

1. გაუმართაობის სქემის სანახავად შეამოწმეთ **მართვის პანელი → მდგომარეობა → პროვაიდერის მდგომარეობა**
2. გადადით **პარამეტრები → მდგრადობა → პროვაიდერის პროფილები** და გაზარდეთ გაუმართაობის ზღვარი
3. შეამოწმეთ, ხომ არ შეცვალა პროვაიდერმა API-ის ლიმიტები ან ხომ არ მოითხოვს ხელახალ ავთენტიფიკაციას
4. გადახედეთ დაყოვნების ტელემეტრიას — დიდმა დაყოვნებამ შესაძლოა ტაიმაუტით გამოწვეული გაუმართაობები გამოიწვიოს

## მდგრადობის პარამეტრები

### სიჩქარის ავტომატური შეზღუდვა არ ირთვება

- სიჩქარის ავტომატური შეზღუდვა ვრცელდება მხოლოდ API-გასაღების პროვაიდერებზე (არა OAuth/გამოწერაზე)
- დარწმუნდით, რომ **პარამეტრები → მდგრადობა → პროვაიდერის პროფილები** განყოფილებაში სიჩქარის ავტომატური შეზღუდვა ჩართულია
- შეამოწმეთ, აბრუნებს თუ არა პროვაიდერი `429` სტატუსის კოდებს ან `Retry-After` სათაურებს

### ექსპონენციალური დაყოვნების მორგება

პროვაიდერის პროფილები მხარს უჭერს შემდეგ პარამეტრებს:

- **საბაზისო დაყოვნება** — პირველი წარუმატებლობის შემდეგ ლოდინის საწყისი დრო (ნაგულისხმევი: 1s)
- **მაქსიმალური დაყოვნება** — ლოდინის დროის მაქსიმალური ზღვარი (ნაგულისხმევი: 30s)
- **მამრავლი** — რამდენად უნდა გაიზარდოს დაყოვნება ყოველი მომდევნო წარუმატებლობისას (ნაგულისხმევი: 2x)

### ერთდროული მოთხოვნების მოზღვავებისგან დაცვა

როდესაც ბევრი თანადროული მოთხოვნა ხვდება სიჩქარეშეზღუდულ პროვაიდერთან, OmniRoute მოთხოვნების თანმიმდევრულად დასამუშავებლად და კასკადური შეცდომების თავიდან ასაცილებლად იყენებს mutex-სა და სიჩქარის ავტომატურ შეზღუდვას. API-გასაღების პროვაიდერებისთვის ეს ავტომატურად ხდება.

### ჩატის მოთხოვნები ვერ სრულდება 503 / chat_admission_busy შეცდომით

**სიმპტომები:**

- ჩატის დასრულებების საბოლოო წერტილი აბრუნებს ხელახლა ცდად `503` პასუხს, რომლის შეცდომის კოდია
  `chat_admission_busy`.
- პასუხი შეიცავს `Retry-After`-ს. #12135-დან მოყოლებული, მისი მნიშვნელობა გამოითვლება დაკვირვებული
  დატვირთულობის მიხედვით — მოთხოვნის მიერ უკვე მოცდილი `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ფანჯრისა
  და მიმდინარე მძიმე იჯარების დაკავების დროიდან უდიდესი — მრგვალდება ზემოთ მთელ
  წამამდე და იზღუდება 60-ით. უმოქმედო კარიბჭეზე ის ინარჩუნებს ისტორიულ მინიმუმებს: 2 წამს
  ბაიტებზე დაფუძნებულ გზაზე და 1 წამს სტრუქტურაზე დაფუძნებულ გზაზე (რომელიც ასევე შეიცავს
  `reason: "structure_limit"`-ს).
- ეს შეიძლება მოხდეს მაშინ, როცა სხვა მძიმე ჩატის მოთხოვნა ან ხანგრძლივი ნაკადური პასუხი ჯერ კიდევ
  დამუშავების პროცესშია.

ბაიტებზე დაფუძნებული პასუხის სხეულია:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

სტრუქტურაზე დაფუძნებული პასუხი იყენებს იმავე ტიპსა და კოდს, შეტყობინებით
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
და `reason: "structure_limit"`-ით.
ნაგულისხმევი ზღვრების პირობებში მოთხოვნა სტრუქტურულად მძიმეა, როდესაც მას აქვს სულ მცირე `200` შეტყობინება,
სულ მცირე `64` ხელსაწყო ან სულ მცირე `32,000` შეფასებული ტოკენი, ან როდესაც შეზღუდული სტრუქტურის შეფასება
ამოწურავს თავის ზღვრებს — `10,000` მონახულებულ კვანძს ან `12` სიღრმეს.

**მიზეზი:** ეს არის OmniRoute-ის შიგნით დატვირთვის განზრახ შემცირება და არა ზედა დონის პროვაიდერის შეცდომა.
თითოეული პროცესი იყენებს პროცესის ლოკალურ დამცავს, რათა დიდი მოთხოვნის სხეულის შენახვამდე
და გარჩევამდე მძიმე მოთხოვნებისთვის შეზღუდული გამტარუნარიანობა დაჯავშნოს. მძიმე მოთხოვნის იჯარა ძალაში რჩება SSE
პასუხის მთელი სასიცოცხლო ციკლის განმავლობაში.

**#503-ის გავრცელება:** ამ შესწორებამდე დამცავი თანადროულობას ზღუდავდა მოთხოვნების ფიქსირებული რაოდენობით
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ნაგულისხმევი `1`) ჰოსტის მეხსიერების მიუხედავად, ამიტომ პროგრამირების აგენტების
განშტოება (რამდენიმე ქვეაგენტი/CLI, სხეულები ჩვეულებრივ > 256 KB) ეფექტურ თანადროულობას
დაახლოებით 1-მდე ამცირებდა და სრულიად ნორმალური დატვირთვის პირობებში 503 შეცდომებს იწვევდა. ახლა დამცავი
ავტომატურად ერგება გარემოს: მას მართავს მიღებისთვის ავტომატურად გამოთვლილი ბაიტური ბიუჯეტი (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`),
რომლის ზომაც პროცესის რეალური მეხსიერების ზღვრის მიხედვით განისაზღვრება, და ის ასევე ითვალისწინებს რესურსებზე ზეწოლის მიმდინარე სიგნალს — ამიტომ
დატვირთვას მხოლოდ მაშინ ამცირებს, როდესაც ჰოსტზე მეხსიერების რეალური დეფიციტია და არა უბრალოდ იმიტომ, რომ ერთზე მეტი
მძიმე მოთხოვნა ერთდროულად მოვიდა. ძველი რაოდენობრივი ზღვარი (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
კვლავ მოქმედებს, მაგრამ მხოლოდ იმ შემთხვევაში, თუ მას აშკარად დააყენებთ.

როდესაც გამტარუნარიანობა დაკავებულია, მძიმე მოთხოვნა ჯერ
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`-მდე ელოდება (ნაგულისხმევად `RATE_LIMIT_MAX_WAIT_MS`; `0` ლოდინს თიშავს), რომ ადგილი გათავისუფლდეს,
და მხოლოდ ამის შემდეგ პასუხობს ხელახლა ცდადი `503`-ით. შეზღუდული ლოდინი არსებობს იმისთვის, რომ აგენტის ტიპის კლიენტებმა
(OpenCode, Claude Code, Cursor), რომლებიც მძიმე ქვემოთხოვნებს ერთდროულად ანაწილებენ, მოთხოვნების მოზღვავება თანმიმდევრულად დაამუშაონ,
ნაცვლად იმისა, რომ მყისიერ უარყოფებზე ხელახლა ცდების მთელი ბიუჯეტი დახარჯონ და დავალების შუაში შეწყვიტონ მუშაობა.
მძიმე მოთხოვნების მიმდინარე იჯარების დატვირთულობა, განსაზღვრული ბაიტური ბიუჯეტი და მიმდინარე ზეწოლის სიმძიმე
ხელმისაწვდომია `GET /api/monitoring/health` → `chatAdmission`-ში (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — შეამოწმეთ ისინი ნებისმიერი გარემოს ცვლადის შეცვლამდე.
პარამეტრები → მდგრადობა → მოთხოვნების რიგი → თანადროული მოთხოვნები ამას არ აკონტროლებს; ეს პარამეტრი
პროვაიდერის მოთხოვნების რიგის ცალკე მექანიზმს მართავს.

**გამოსწორება:**

1. ჯერ ხელახლა სცადეთ. კლიენტებმა უნდა გაითვალისწინონ `Retry-After` და მოთხოვნის დაუყოვნებლივ
   გამეორების ნაცვლად დაყოვნება გამოიყენონ.
2. რაიმეს მორგებამდე შეამოწმეთ `/api/monitoring/health` → `chatAdmission`. `countCapEnabled:
false` და საკმარისად დიდი `maxInflightBytes` ნიშნავს, რომ ავტომატურად გამოთვლილი ბიუჯეტი უკვე სწორად
   მუშაობს; ხოლო `high`/`critical` მნიშვნელობის `pressureSeverity` ნიშნავს, რომ ჰოსტს ნამდვილად აკლია მეხსიერება —
   ეს მიღების გარემოს ცვლადით ვერ გამოსწორდება; საჭიროა მეტი RAM ან ნაკლები სამუშაო დატვირთვა.
3. მხოლოდ იმ შემთხვევაში, თუ `/api/monitoring/health` აჩვენებს, რომ ავტომატურად გამოთვლილი ბიუჯეტი ნამდვილად ძალიან მცირეა

   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`-ით, ნაცვლად ძველ მოთხოვნათა რაოდენობის ზღვარზე დაბრუნებისა.

## არასავალდებულო RAG / LLM-ის შეცდომების ტაქსონომია (16 პრობლემა)

OmniRoute-ის ზოგიერთი მომხმარებელი კარიბჭეს RAG-ის ან აგენტური სტეკების წინ ათავსებს. ასეთ კონფიგურაციებში ხშირად გვხვდება უცნაური სურათი: OmniRoute გამართულად გამოიყურება (პროვაიდერები ხელმისაწვდომია, მარშრუტიზაციის პროფილები წესრიგშია, სიჩქარის შეზღუდვის გაფრთხილებები არ არის), მაგრამ საბოლოო პასუხი მაინც არასწორია.

პრაქტიკაში, ასეთი ინციდენტები, როგორც წესი, ქვემდგომი RAG-კონვეიერიდან მომდინარეობს და არა თავად კარიბჭიდან.

თუ ამ ხარვეზების აღსაწერად საერთო ტერმინოლოგია გსურთ, შეგიძლიათ გამოიყენოთ WFGY ProblemMap — MIT ლიცენზიის მქონე გარე ტექსტური რესურსი, რომელიც RAG / LLM-ის თექვსმეტ განმეორებად ხარვეზის ნიმუშს განსაზღვრავს. ზოგადად, ის მოიცავს:

- მოძიების გადახრასა და კონტექსტის დარღვეულ საზღვრებს
- ცარიელ ან მოძველებულ ინდექსებსა და ვექტორულ საცავებს
- ემბედინგსა და სემანტიკას შორის შეუსაბამობას
- მოთხოვნის აწყობისა და კონტექსტური ფანჯრის პრობლემებს
- ლოგიკის მოშლასა და ზედმეტად თავდაჯერებულ პასუხებს
- გრძელი ჯაჭვებისა და აგენტების კოორდინაციის ხარვეზებს
- მრავალი აგენტის მეხსიერებისა და როლების გადახრას
- განთავსებისა და საწყისი ჩატვირთვის მიმდევრობის პრობლემებს

იდეა მარტივია:

1. არასწორი პასუხის გამოკვლევისას აღრიცხეთ:
   - მომხმარებლის დავალება და მოთხოვნა
   - OmniRoute-ში გამოყენებული მარშრუტის ან პროვაიდერების კომბინაცია
   - ქვემდგომ სისტემაში გამოყენებული ნებისმიერი RAG-კონტექსტი (მოძიებული დოკუმენტები, ხელსაწყოების გამოძახებები და ა.შ.)
2. ინციდენტი დაუკავშირეთ WFGY ProblemMap-ის ერთ ან ორ ნომერს (`No.1` … `No.16`).
3. ნომერი OmniRoute-ის ჟურნალების გვერდით, თქვენს საკუთარ საინფორმაციო დაფაზე, საოპერაციო ინსტრუქციაში ან ინციდენტების აღრიცხვის სისტემაში შეინახეთ.
4. გამოიყენეთ შესაბამისი WFGY გვერდი იმის გადასაწყვეტად, საჭიროა თუ არა თქვენი RAG-სტეკის, ინფორმაციის მომძიებლის ან მარშრუტიზაციის სტრატეგიის შეცვლა.

სრული ტექსტი და კონკრეტული ინსტრუქციები ხელმისაწვდომია აქ (MIT ლიცენზია, მხოლოდ ტექსტი):

[WFGY ProblemMap-ის README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

თუ OmniRoute-ის უკან RAG-ის ან აგენტურ კონვეიერებს არ იყენებთ, შეგიძლიათ ეს განყოფილება გამოტოვოთ.

## ნელი გაშვება / მზადყოფნის მოლოდინის დროის ამოწურვა

თუ CLI აჩვენებს შეტყობინებას `⚠ Server did not respond within 60s`, თუმცა სერვერი
რეალურად მუშაობს, თქვენს გარემოში მზადყოფნის შემოწმებისთვის გამოყოფილი დრო ზედმეტად მოკლეა.

ეს ხშირად ხდება Windows-ზე (ანტივირუსის, ფაილური სისტემის დამკვირვებლების გამო) ან ისეთ კონტეინერებში,
სადაც გაშვებისას დიდი დატვირთვაა.

**გამოსწორება — გაზარდეთ გამოყოფილი დრო:**

```bash
# გარემოს ცვლადის მეშვეობით (შენარჩუნდება გაშვებებს შორის):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 წუთი
omniroute serve

# CLI-ის პარამეტრის მეშვეობით (ერთჯერადად):
omniroute serve --ready-timeout 180000
```

ნაგულისხმევი მნიშვნელობაა 60 000 მწმ (60 წმ). გაფრთხილება მხოლოდ საინფორმაციო ხასიათისაა; სერვერი
ფონურ რეჟიმში განაგრძობს გაშვებას და ჩატვირთვის დასრულების შემდეგ ხელმისაწვდომი გახდება.

`OMNIROUTE_READY_TIMEOUT_MS`-ის შესახებ სრული
დეტალებისთვის იხილეთ [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
