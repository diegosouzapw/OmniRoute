OmniRoute-ს მოყვება `setup-*` ბრძანებების ოჯახი, რომლებიც აკონფიგურირებენ კოდირების CLI-ს (Codex, Claude Code, OpenCode, Cline, …) OmniRoute-ის ბექენდად გამოსაყენებლად — ასე რომ, ინსტრუმენტი უკავშირდება **ერთ** ენდპოინტს და OmniRoute ავტომატური უკუსვლით მიმართავს სწორ პროვაიდერს. თითოეული ბრძანება კითხულობს **ცოცხალ** მოდელის კატალოგს გაშვებული OmniRoute-დან (ლოკალური ან დისტანციური) და წერს ინსტრუმენტის საკუთარ კონფიგურაციის ფაილს **თქვენს** მანქანაზე. API გასაღები მითითებულია გარემოს ცვლადით, სადაც კი ინსტრუმენტი ამას მხარს უჭერს. ბრძანებები, რომლებიც ინახავენ ინსტრუმენტის ლოკალურ გარემოს ფაილს, მოცემულია ქვემოთ.

ასევე არსებობს ზოგადი გამშვები — `omniroute run <target>` — რომელიც ააქტიურებს `claude`, `codex`, `aider`, `goose`, `opencode`, `qwen` ან `gemini`-ს სწორი გარემოს ინექციით, ყოველგვარი კონფიგურაციის ჩაწერის გარეშე. სამიზნეები და მათი ფსევდონიმები მომდინარეობს კანონიკური მანიფესტიდან `bin/cli/cli-manifest.mjs` (`claude-code|cc|anthropic`, `codex-cli|openai-codex|openai`, `goose-cli`, `open-code`, `qwen-code`, `gemini-cli`), და `omniroute completion` გთავაზობთ იმავე მანიფესტიდან მიღებულ სამიზნე სიტყვებს. ძველი, ინსტრუმენტზე დამოკიდებული გამშვებები — `omniroute launch` (Claude Code) და `omniroute launch-codex` (Codex) — კვლავ ხელმისაწვდომია.

პროვაიდერის ჩართვა ხელმისაწვდომია იმავე ლოკალური/დისტანციური კონტექსტიდან. ქვემოთ მოცემული API-პირველი ბრძანებები მართვის ავთენტიფიკაციას განაცალკევებენ პროვაიდერის სერთიფიკატებისგან და არასოდეს ბეჭდავენ სერთიფიკატს სტრუქტურირებულ გამოსავალში:

```bash
omniroute providers add glm --credential-env GLM_API_KEY --name work
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth openai
omniroute providers edit <connection-id> --default-model glm/glm-5.2
omniroute providers remove <connection-id> --yes
```

სკრიპტებისთვის უპირატესობა მიანიჭეთ `--credential-stdin` ან `--credential-env`; `--credential` შენარჩუნებულია კონტროლირებადი ლოკალური გამოყენებისთვის. `providers remove` მოითხოვს `--yes` არაინტერაქტიულ ტერმინალზე, და ყველა ხუთი ბრძანება ითვალისწინებს აქტიურ კონტექსტს ან გლობალურ `--base-url`/`--api-key` ოფციებს.

პროვაიდერის სელექტორები უარყოფენ ორაზროვან ID პრეფიქსებს, სახელებს ან პროვაიდერის სახელებს; გამოიყენეთ სრული კავშირის ID, როდესაც რამდენიმე კავშირი ემთხვევა. შექმნის და რედაქტირების ბრძანებები უკან კითხულობენ შენახულ კავშირს, და წაშლა ამოწმებს, რომ ის აღარ არის წაკითხვადი. იმპორტი გამოტოვებს არსებულ პროვაიდერის/სახელის წყვილს. იმპორტირებულ ჩანაწერებს არ შეუძლიათ გადაფარონ მართვის ენდპოინტი, კონტექსტი ან მართვის სერთიფიკატები, რომლებიც მიწოდებულია CLI-სთვის.

ორი ყველაზე მდიდარი ინტეგრაციის ერთჯერადი, ხელით დაწერილი საბაზისო კონფიგურაციისთვის, იხილეთ ინსტრუმენტების სიღრმისეული მიმოხილვები:

- [Claude Code კონფიგურაცია](./CLAUDE-CODE-CONFIGURATION.md)
- [Codex CLI კონფიგურაცია](./CODEX-CLI-CONFIGURATION.md)
- [დისტანციური რეჟიმი](./REMOTE-MODE.md) — მართეთ დისტანციური OmniRoute (VPS / Tailnet) თქვენი ლეპტოპიდან
- [VS Code Copilot Chat](./VSCODE-COPILOT.md) — OmniCopilot გაფართოება; მას ასევე შეუძლია ამ `setup-*` ბრძანებების გაშვება თქვენთვის რედაქტორის შიგნიდან

## ძირითადი ცხრილი

თითოეული ბრძანება ითვალისწინებს **აქტიურ კონტექსტს** (რომელიც `omniroute connect`-ით განისაზღვრება; იხილეთ
[დისტანციური რეჟიმი](./REMOTE-MODE.md)) ან აშკარად მითითებულ `--remote <url> --api-key <key>` ალმებს.
ქვემოთ „ლოკალური და დისტანციური“ ნიშნავს: ალმების გარეშე სამიზნეა `http://localhost:20128`;
`--remote`-ის გამოყენებისას (ან აქტიური დისტანციური კონტექსტის არსებობისას) კატალოგი ამ
სერვერიდან იტვირთება, ხოლო კონფიგურაცია ლოკალურად იწერება.

| `omniroute launch-codex`   | OpenAI Codex CLI                 | არაფერი — უშვებს `codex`-ს `-c` ალმების მეშვეობით ჩასმული `omniroute` პროვაიდერით                                                                                                         | `--remote` `--api-key` `--profile` (`-p`) `--port`                                                                                         | ორივე                   |

ფლაგების შესახებ შენიშვნები (გადამოწმებულია ბრძანების საწყის კოდში):

- `--remote <url>` — კატალოგის მიღება დისტანციური OmniRoute-იდან (`--port`-ისა
  და აქტიური კონტექსტის უგულებელყოფით). `--api-key <key>` მიუთითებს ამ
  სერვერის ავტორიზაციის მონაცემს (ნაგულისხმევად გამოიყენება `OMNIROUTE_API_KEY`
  გარემოს ცვლადი ან აქტიური კონტექსტის ტოკენი).
- `--only <patterns>` — მძიმეებით გამოყოფილი ქვესტრიქონები; ტოვებს მხოლოდ
  მოდელების იმ ID-ებს, რომლებიც ემთხვევა (მაგ., `--only glm,kimi`). ხელმისაწვდომია
  `setup-codex`, `setup-claude`, `setup-opencode`, `setup-continue`,
  `setup-cursor`, `setup-crush` ბრძანებებისთვის.
- `--dry-run` — ფაილურ სისტემაში ცვლილებების შეტანის გარეშე ზუსტად ბეჭდავს,
  რა ჩაიწერებოდა. ხელმისაწვდომია ყველა `setup-*` ბრძანებისთვის, **გარდა**
  `setup-cursor`-ისა (რომელიც ფაილში არასდროს წერს).
- `--model <id>` — სავალდებულოა (ან ინტერაქტიულად შეირჩევა) იმ ხელსაწყოებისთვის,
  რომლებსაც მოდელების ავტომატური აღმოჩენა არ აქვთ: Cline, Kilo, Roo, Goose,
  Qwen, Aider, 5dive. არაინტერაქტიული გაშვებისთვის ეს ხელსაწყოები ასევე იღებენ
  `--yes`-ს (რაც თავის მხრივ `--model`-ს მოითხოვს). `setup-opencode` იღებს
  `--model`-ს ზედა დონის ნაგულისხმევი მოდელის დასაყენებლად.
- `omniroute run`-ზე მითითებული `--model <id>` მიჰყვება მანიფესტში თითოეული
  სამიზნისთვის განსაზღვრულ დაკავშირებას (`bin/cli/cli-manifest.mjs`):
  **aider** იღებს `--model openai/<id>`-ს, ხოლო **opencode** —
  `--model omniroute/<id>`-ს (პრეფიქსი ემატება მხოლოდ მაშინ, როდესაც ID-ს ის
  უკვე არ აქვს); **qwen** და **gemini** ID-ს უცვლელად იღებენ; **claude** მას
  იღებს `ANTHROPIC_MODEL`-ის, **goose** — `GOOSE_MODEL`-ის, ხოლო **codex** —
  `-c model_providers.omniroute.*` არგუმენტების მეშვეობით. **Qwen გაშვების
  ერთადერთი სამიზნეა, რომელიც აუცილებლად მოითხოვს `--model`-ს** —
  `omniroute run qwen` მის გარეშე სრულდება კოდით `2` და აშკარა შეცდომის
  შეტყობინებით.
- `--port <port>` — ლოკალური OmniRoute-ის პორტი (ნაგულისხმევად `20128`;
  იგნორირდება, როდესაც მითითებულია `--remote`). წარმოდგენილია ყველა `setup-*`
  ბრძანებასა და ორივე გამშვებში.
- `omniroute run`-ის დასრულების კოდები: შვილობილი CLI-ის საკუთარი დასრულების
  კოდი უცვლელად გადაიცემა; `2` = არასწორი არგუმენტები (მხარდაუჭერელი სამიზნე,
  სავალდებულო `--model`-ის არქონა, კონტეინერის შეზღუდვა); `127` = სამიზნე
  ბინარული ფაილი `PATH`-ში არ არის; `130`/`143`/`129`, როდესაც გაშვება
  სრულდება `SIGINT`/`SIGTERM`/`SIGHUP`-ით; `1` = გაშვების დროის სხვა შეცდომა.
- ორივე გამშვები (`launch`, `launch-codex`) იღებს `--profile <name>`-ს
  `setup-claude` / `setup-codex`-ის მიერ ჩაწერილი პროფილის ასარჩევად, ასევე
  საბაზისო `claude` / `codex` ბინარული ფაილისთვის უცვლელად გადასაცემ არგუმენტებს.

ინტერაქტიული ამრჩევი ასევე საერთოა გამართვის რეცეპტებისთვის:

```bash
# აირჩიეთ აქტიური ლოკალური ან დისტანციური მოდელების კატალოგიდან და გამართეთ სამიზნე.
omniroute configure claude
omniroute configure opencode --provider glm
omniroute configure qwen --model qwen/qwen3.8-max-preview --yes
```

`configure` ამჟამად იყენებს გამოცდილი რეცეპტების დელეგირებას `codex`, `claude`,
`opencode`, `qwen`, `aider`, `goose`, `cline`, `continue`, `kilo` და `5dive`-ისთვის.
მხოლოდ IDE-სთვის განკუთვნილი,

## ლოკალური გამოყენება

როდესაც OmniRoute გაშვებულია `localhost:20128`-ზე, უბრალოდ გაუშვით დაყენების ბრძანება თქვენი
ხელსაწყოსთვის. კატალოგი ლოკალური სერვერიდან ჩამოიტვირთება.

```bash
# Codex: თითოეული შესაბამისი მოდელისთვის პროფილის ჩაწერა ~/.codex/-ში
omniroute setup-codex
codex --profile glm52            # გენერირებული პროფილის გამოყენება

# Claude Code: თითოეული მოდელისთვის პროფილების ჩაწერა, შემდეგ ერთ-ერთის გაშვება
omniroute setup-claude
omniroute launch --profile glm52

# OpenCode: openai-თან თავსებადი პროვაიდერის ჩაწერა კატალოგის ყველა მოდელით
omniroute setup-opencode
export OMNIROUTE_API_KEY=sk-...  # გამოიყენება {env:OMNIROUTE_API_KEY}-ის მეშვეობით და არასდროს იწერება დისკზე
opencode -m omniroute/glm/glm-5.2 "..."

# ხელსაწყოებისთვის, რომლებსაც ავტომატური აღმოჩენა არ აქვთ, საჭიროა მოდელის ცხადად მითითება:
omniroute setup-aider --model glm/glm-5.2
omniroute setup-qwen --model qwen/qwen3.8-max-preview

# წინასწარი ნახვა არაფრის ჩაწერის გარეშე:
omniroute setup-continue --dry-run
```

გაშვება კონფიგურაციის საერთოდ ჩაწერის გარეშე (მხოლოდ გარემოს ცვლადების ინექციით):

```bash
omniroute launch                 # Claude Code → ლოკალური OmniRoute
omniroute launch-codex           # Codex CLI → ლოკალური OmniRoute
omniroute launch-codex --profile glm52
omniroute run claude --model openai/gpt-5.4
omniroute run codex --model openai/gpt-5.4 --dry-run --json
omniroute run aider --model glm/glm-5.2 -- --message "reply OK"
omniroute run goose --model glm/glm-5.2
omniroute run opencode --model glm/glm-5.2 -- run "reply OK"
omniroute run qwen --model glm/glm-5.2 -- -p "reply OK"
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "reply OK"

# ბრძანების ცხადად მითითებული გზა: უცვლელად გადაეცემა ყველაფერი, რაც -- შემდეგ მოდის
omniroute run claude -- --print-system-prompt "review this diff"
```

## დისტანციური გამოყენება

დაყენების ნებისმიერი ბრძანება მიმართეთ დისტანციულ OmniRoute-ზე `--remote` + `--api-key` პარამეტრებით.
კატალოგი დისტანციური სერვერიდან ჩამოიტვირთება, ხოლო კონფიგურაცია თქვენს ლოკალურ კომპიუტერზე ჩაიწერება.

```bash
# OpenCode დისტანციურ VPS-თან, მხოლოდ glm/kimi მოდელების შენარჩუნებით
omniroute setup-opencode --remote http://192.168.0.15:20128 --api-key oma_live_xxx \
  --only glm,kimi
opencode -m omniroute/glm/glm-5.2 "..."   # ჯერ OMNIROUTE_API_KEY-ის ექსპორტი

# Codex-ის პროფილები დისტანციური კატალოგიდან
omniroute setup-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx

# CLI-ის პირდაპირ დისტანციურ სერვერთან გაშვება
omniroute launch       --remote http://192.168.0.15:20128 --api-key oma_live_xxx
omniroute launch-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx
```

იმის ნაცვლად, რომ ყოველ ჯერზე გადასცეთ `--remote`/`--api-key`, ერთხელ შედით სისტემაში და
**აქტიურ კონტექსტს** მიეცით მათი ავტომატურად მიწოდების საშუალება:

```bash
omniroute connect 192.168.0.15        # ქმნის შეზღუდული მოქმედების არეალის ტოკენს და ინახავს კონტექსტს
omniroute setup-codex                 # ← ახლა იყენებს დისტანციურ კატალოგს
omniroute setup-opencode              # ← იგივე
omniroute launch                      # ← Claude Code დისტანციურ სერვერთან
```

კონტექსტების, მოქმედების არეალებისა და ტოკენების მართვის შესახებ იხილეთ [დისტანციური რეჟიმი](./REMOTE-MODE.md).

## 5dive-ის აგენტთა ფლოტები

[5dive](https://5dive.ai) უშვებს ხანგრძლივად მომუშავე პროგრამირების აგენტთა ფლოტს, რომელთაგან თითოეული
არის systemd-ის ერთეული საკუთარი Unix მომხმარებლის ქვეშ. თავად ის პროგრამირების CLI არ არის, ამიტომ
`omniroute run`-ისთვის გასაშვები არაფერია — `5dive` არის სამიზნე **მხოლოდ კონფიგურაციისთვის**.

```bash
omniroute configure 5dive --model failover-demo --yes
omniroute setup-5dive --model failover-demo --auth-profile omniroute --agent worker1
```

ორივე ფორმა წერს 5dive-ის ერთ **ავთენტიფიკაციის პროფილს**, რის შემდეგაც ამ
პროფილთან დაკავშირებული ყოველი `claude` ადგილი OmniRoute-ს უკავშირდება. ამ სამიზნისთვის სამი რამ არის სპეციფიკური:

- **ის მუშაობს ფლოტის ჰოსტზე, root-ის სახელით.** 5dive-ის ქმედებები ვრცელდება ლოკალურ systemd ერთეულებზე
  და root-ის მფლობელობაში არსებულ მდგომარეობის დირექტორიაზე; დისტანციური რეჟიმი არ არსებობს. რეცეპტი ხელახლა ეშვება
  `sudo`-ს მეშვეობით, როდესაც ის უკვე root-ის სახელით არ მუშაობს (`--no-sudo` ამას თიშავს და სანაცვლოდ
  ბრძანებას ბეჭდავს).
- **საბოლოო წერტილი უნდა იყოს `https://`, თუ ის loopback არ არის.** აგენტის API გასაღები
  ამ URL-ით გადაიცემა ყოველ მოთხოვნაში, ხოლო 5dive უარს ამბობს ღია ტექსტის სახით გამოყენებულ გარე საბოლოო წერტილზე.
  კერძო LAN მისამართი გამონაკლისი არ არის.
- **თითოეული ადგილის საკუთარი მოდელის ფიქსაცია პროფილზე პრიორიტეტულია.** პროფილი შეიცავს
  `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`-ს, მაგრამ სტანდარტული
  მოდელის id-ზე კვლავ მიბმული ადგილი პირველივე სვლაზე მარცხდება შეტყობინებით _"There's an issue with the selected model"_.
  ადგილების დასაფიქსირებლადაც გადასცით `--agent <name>` (შესაძლებელია გამეორება); თუ ამას არ გააკეთებთ, რეცეპტი
  შესაბამის ბრძანებას დაბეჭდავს.

API გასაღები 5dive-ს გადაეცემა **stdin**-ზე (`--api-key=-`), ამიტომ ის არასდროს გამოჩნდება
`ps`-ის გამომავალში.

პროფილის OmniRoute-ის **კომბინაციაზე** და არა ერთ მოდელზე მიმართვა უზრუნველყოფს
ფლოტის პროვაიდერის ავარიულ გადართვას: როდესაც ძირითადი საბოლოო წერტილი სვლის შუაში სრულად გაითიშა
[#11578](https://github.com/diegosouzapw/OmniRoute/issues/11578)-ში აღბეჭდილი გაშვების დროს, აგენტმა
დარჩენილი ნაბიჯები სარეზერვო ვარიანტზე დაასრულა და გათიშვა მომხმარებლისთვის არასდროს უჩვენებია.

## ნატიური დამოკიდებულებების შენარჩუნება განახლებისას: `--include=optional`

როდესაც განახლებას `omniroute update`-ით ასრულებთ (დადასტურების შემდეგ ან `--apply`-ის გამოყენებით),
OmniRoute ინსტალაციას ჩაშენებული `--include=optional` პარამეტრით უშვებს:

```bash
npm install -g omniroute@latest --include=optional
```

ეს **არ არის** პარამეტრი, რომელიც `omniroute update`-ს უნდა გადასცეთ — განახლების პროგრამა მას
ყოველთვის იყენებს. ის უზრუნველყოფს, რომ `optionalDependencies` (`better-sqlite3`, `keytar`,
`tls-client`, LLMLingua SLM სტეკი) განახლების შემდეგაც შენარჩუნდეს, მაშინაც კი, თუ თქვენს npm-ის
კონფიგურაციაში დაყენებულია `omit=optional`, რაც სხვა შემთხვევაში SQLite-ის ნატიურ დრაივერსა და
ოპერაციული სისტემის გასაღებების საცავთან დამაკავშირებელ მოდულს უხმაუროდ წაშლიდა. ზუსტი ბრძანების
შესრულების გარეშე წინასწარ სანახავად:

```bash
omniroute update --dry-run
# [საცდელი გაშვება] შესრულდებოდა: npm install -g omniroute@latest --include=optional
```

`omniroute update`-ის სხვა პარამეტრები (გადამოწმებულია საწყის კოდში): `--check` (თუ
ვერსია მოძველებულია, დასრულება კოდით 1), `--apply` (ინსტალაცია დადასტურების მოთხოვნის გარეშე),
`--changelog`, `--no-backup`, `--yes`.

## Google Gemini CLI `omniroute run gemini`-ის მეშვეობით

კონტრაქტი გადამოწმებულია `@google/gemini-cli` 0.50.0-თან: CLI ითვალისწინებს
`GOOGLE_GEMINI_BASE_URL`-ს და მის მისამართზე აგზავნის
`POST /v1beta/models/<model>:generateContent` მოთხოვნას
(ასევე `:streamGenerateContent?alt=sse`-ს) — ზუსტად OmniRoute-ის ნატიურ
Gemini ინტერფეისზე (`/v1beta`). `omniroute run gemini` ამას ავტომატურად აკონფიგურირებს:

- `GOOGLE_GEMINI_BASE_URL` → OmniRoute-ის აქტიური საბაზისო URL (ძირეული, `/v1`-ის გარეშე);
- `GEMINI_API_KEY` → OmniRoute-ის განსაზღვრული ავტორიზაციის მონაცემი (პარამეტრი/გარემო/კონტექსტი);
- **დროებითი, იზოლირებული `GEMINI_CLI_HOME`**, რომლის `.gemini/settings.json`
  ავტორიზაციის მეთოდად `gemini-api-key`-ს ირჩევს, რათა შენახულმა Google OAuth სესიამ (Code Assist)
  არასოდეს ჩაანაცვლოს OmniRoute-ისკენ მიმართული გაშვება — პროცესის დასრულების შემდეგ ის იშლება;
- **გარემოს ჰიგიენა**: შვილობილი პროცესის გარემოდან იშლება `GOOGLE_API_KEY`,
  `GOOGLE_GENAI_USE_VERTEXAI` და `GOOGLE_GENAI_USE_GCA` (რომლებიც ავტორიზაციას
  Vertex/Code Assist-ზე გადაამისამართებდა), ხოლო დამატებითი საიმედოობისთვის
  `GEMINI_DEFAULT_AUTH_TYPE=gemini-api-key` ყენდება — სხვა `run` სამიზნეებიც იმავე
  მიდგომას იყენებს საკუთარი კონფლიქტური ცვლადებისთვის;
- `--model <id>`-ის ჩასმა `--provider`/`--model`-იდან.

```bash
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "hello"
```

Gemini-ის სამუშაო სივრცის სანდოობის დაცვა კვლავ მოქმედებს უთავო რეჟიმში — თავად მიუთითეთ
`--skip-trust` (ან დირექტორიას ინტერაქტიულად მიანიჭეთ ნდობა); გამშვები მას განზრახ არ უვლის გვერდს.
ეს გამშვები განსხვავდება **ACP რეგისტრაციისგან**
(`src/lib/acp/registry.ts`, `gemini --acp`), რომელიც `/dashboard/acp-agents`-ისთვის
აგენტის პროტოკოლის ინტეგრაციად რჩება.

## რეალური smoke შემოწმება (არჩევითი)

დეტერმინისტული გაშვების გეგმის რეგრესიული ტესტები სრულდება CI-ში (`tests/unit/cli/run-command.test.ts`,
`tests/unit/cli/run-execution.test.ts`). რეალური ბინარული ფაილების რეალურ
OmniRoute სერვერთან შესამოწმებლად ხელმისაწვდომია არჩევითი სატესტო გარემო მისამართზე
`tests/integration/upstream-cli-smoke.int.test.ts`. ის ავტომატურად არასოდეს ეშვება
(თითოეული ქვეტესტი გამოტოვებულია, თუ `RUN_CLI_SMOKE=1` არ არის მითითებული), ავტორიზაციის მონაცემს გადასცემს გარემოს ცვლადის
სახელით (და არასოდეს მნიშვნელობით), ნებისმიერ ჩაწერილ გამომავალში ფარავს გასაღების ფორმის სტრიქონებს, გამოტოვებს
სამიზნეებს, რომელთა ბინარული ფაილიც არ არის დაინსტალირებული, და წარუმატებლობებს უბრალო ლოგიკური მნიშვნელობის ნაცვლად
კლასიფიცირებს, როგორც ავტორიზაციის / upstream-ის / კონფიგურაციის პრობლემებს:

```bash
RUN_CLI_SMOKE=1 \
OMNIROUTE_SMOKE_BASE_URL="http://localhost:20128" \
OMNIROUTE_SMOKE_MODEL="<provider/model>" \
OMNIROUTE_SMOKE_API_KEY_ENV="OMNIROUTE_API_KEY" \
node --import tsx/esm --test tests/integration/upstream-cli-smoke.int.test.ts
```

არასავალდებულო: `OMNIROUTE_SMOKE_TARGETS="codex,opencode,qwen"` ზღუდავს შემოწმების ფარგლებს;
`OMNIROUTE_SMOKE_TIMEOUT_MS` ცვლის თითოეული სამიზნისთვის განსაზღვრულ 120-წამიან მოლოდინის ვადას.
