გაუშვით `omniroute` CLI თქვენს ლეპტოპზე, მაშინ როცა თავად OmniRoute სხვაგანაა გაშვებული
(VPS-ზე, სახლის სერვერზე ან თქვენს Tailnet-ში არსებულ სხვა მოწყობილობაზე). სისტემაში ერთხელ შედიხართ
`omniroute connect`-ით და ამის შემდეგ **ყველა** CLI ბრძანება იმ დისტანციურ
სერვერზეა მიმართული — იგივე ბრძანებები, იგივე გამომავალი, უბრალოდ დისტანციურ სერვერზე შესრულებული.

მეორე ხელსაწყოს დაყენება საჭირო არ არის: დისტანციური რეჟიმი იყენებს ჩვეულებრივ `omniroute` CLI-ს
და შეზღუდული უფლებების მქონე **წვდომის ტოკენებს**.

```bash
npm install -g omniroute                 # ჩვეულებრივი CLI
omniroute connect 192.168.0.15           # სისტემაში შესვლა (პაროლი → შეზღუდული უფლებების ტოკენი)
omniroute models list                    # ← ახლა აჩვენებს დისტანციური სერვერის მოდელებს
omniroute configure codex                # ← დისტანციური კატალოგიდან ქმნის ლოკალურ Codex პროფილს
```

## როგორ მუშაობს

```
თქვენი ლეპტოპი                          დისტანციური OmniRoute (VPS)
┌────────────────────┐                   ┌───────────────────────────────┐
│ omniroute CLI      │  POST /api/cli/connect  (პაროლი → ტოკენი)          │
│  კონტექსტი: vps    │ ───────────────►  │ ქმნის შეზღუდული უფლებების      │
│  baseUrl, token    │  Authorization: Bearer oma_live_…                  │
│                    │ ───────────────►  │ წვდომის ტოკენს; თითოეული        │
│ კონფიგურაციებს     │ ◄───────────────  │ მართვის მარშრუტი მოწმდება       │
│ წერს ლოკალურად     │                   │ ტოკენის უფლებების მიხედვით      │
└────────────────────┘                   └───────────────────────────────┘
```

- **კონტექსტები** თითო სერვერის მონაცემებს ინახავს (`~/.omniroute/config.json`, `chmod 600`).
  `omniroute contexts use <name>` ცვლის აქტიურ სერვერს; `default` ლოკალურია.
- **წვდომის ტოკენები** (`oma_live_…`) მართვის ბრძანებების ავტორიზაციისთვის გამოიყენება. ისინი
  განსხვავდება ინფერენსის API გასაღებებისგან (`sk-…`, რომლებიც `/v1/chat/completions`-ისთვის გამოიყენება).
- სერვერის მხარეს ინახება მხოლოდ ტოკენის SHA-256 ჰეში. ღია ტექსტი ნაჩვენებია
  **ერთხელ**, შექმნის დროს.

## დაკავშირება

### მართვის პაროლით (საწყისი კონფიგურაცია)

```bash
omniroute connect 192.168.0.15
# მართვის პაროლი მისამართისთვის http://192.168.0.15:20128: ********
# ✔ დაკავშირებულია http://192.168.0.15:20128-თან — კონტექსტი '192.168.0.15' (უფლებები: admin)
```

პაროლით დაკავშირების ნაკადი ნაგულისხმევად ქმნის **admin** ტოკენს (რადგან პაროლი გაქვთ,
თქვენ უკვე ფლობთ სრულ კონტროლს). უფლებების შესამცირებლად გამოიყენეთ `--scope`:

```bash
omniroute connect 192.168.0.15 --scope write
```

პარამეტრები: `--port <p>` (როცა ჰოსტი პორტს არ შეიცავს), `--name <ctx>` (კონტექსტის სახელი),
`--scope read|write|admin`. სრული URL უცვლელად გამოიყენება:
`omniroute connect https://omni.example.com`.

### წინასწარ გენერირებული ტოკენით

შექმენით შეზღუდული უფლებების მქონე ტოკენი მართვის პანელში (ან `omniroute tokens create`-ით) და
ჩასვით ის — პაროლი საჭირო არ არის:

```bash
omniroute connect 192.168.0.15 --key oma_live_xxxxxxxx
```

CLI მას `GET /api/cli/whoami`-ის საშუალებით ამოწმებს და აქტიურ კონტექსტად ინახავს.

---

## უფლებების დონეები

სამი იერარქიული დონე (`admin ⊃ write ⊃ read`):

| უფლებები | შესაძლებლობები                                                                             |
| -------- | ------------------------------------------------------------------------------------------ |
| `read`   | ჩამონათვალი/დათვალიერება — `models list`, `providers status`, `logs`, `usage`, `cost`      |
| `write`  | read **+** კონფიგურაცია/გამოყენება — `setup-codex`, `keys add`, `config set`, კომბინაციები |
| `admin`  | write **+** მართვა — `tokens` CRUD, პროვაიდერების დამატება, სერვისები, პოლიტიკა, oauth     |

სერვერი თითოეული მარშრუტისთვის საჭირო უფლებების დონეს HTTP მეთოდის მიხედვით განსაზღვრავს
(`GET`→read, ცვლილებები→write), ხოლო სენსიტიური ზედაპირებისთვის იყენებს admin ნებადართულ სიას
(`/api/cli/tokens`, `/api/providers`-ის ცვლილებები, `/api/oauth`, `/api/services`, …).
არასაკმარისი უფლებების მქონე ტოკენი იღებს `403` პასუხს მკაფიო შეტყობინებით.

> მარშრუტები, რომლებიც პროცესებს უშვებს (`/api/services/*`, `/api/mcp/*`, …),
> **მხოლოდ loopback-ისთვის** რჩება — დისტანციური ტოკენი მათზე წვდომას ვერასოდეს მიიღებს,
> უფლებების დონის მიუხედავად.

## Antigravity-ს დაკავშირება დისტანციურ ინსტალაციაზე

Antigravity იყენებს Google-ის firstparty/nativeapp თანხმობის ეკრანს. Google ავტორიზაციის კოდს მხოლოდ მაშინ გასცემს, როცა **loopback გადამისამართება**
(`http://127.0.0.1:<port>/callback`) **ხელმისაწვდომია იმ ბრაუზერიდან, რომელშიც
შესვლა დასტურდება**. დისტანციურ VPS-ზე ინსტალაციისას ეს loopback სერვერზეა
და არა თქვენს კომპიუტერზე, ამიტომ თანხმობის ეკრანი **სამუდამოდ იტვირთება და
კოდს არასოდეს გასცემს** — ჩვეულებრივ სათადარიგო ვარიანტში, „ჩასვით callback URL“,
ჩასასმელი არაფერია. (ეს Google-ის მხრიდან დაწესებული შეზღუდვაა: იგივე გაჭედვა
ხდება ნებისმიერ პროქსიში, რომელიც თანდართულ Antigravity დესკტოპ-კლიენტს იყენებს
და არა მხოლოდ OmniRoute-ში.)

დაფა ამას გაჭედვამდე აღმოაჩენს: **Providers → Antigravity →
Connect**-ის არა-localhost მისამართიდან გახსნისას ზოგადი შეტყობინება „დააკოპირეთ callback URL“
ჩანაცვლდება ქვემოთ მოცემული ორი გამოსავლით, რომლებშიც თქვენი ჰოსტი და პორტი უკვე
შევსებულია. (LAN მისამართიც ითვლება — ამ callback-ის თვალსაზრისით
`192.168.x.x` localhost არ არის.)

Antigravity-ს დისტანციურ OmniRoute-თან დაკავშირების ორი მხარდაჭერილი გზა არსებობს.

### ვარიანტი A — ლოკალური შესვლის დამხმარე (რეკომენდებულია)

OAuth გაუშვით **საკუთარ კომპიუტერზე**, სადაც `127.0.0.1` ხელმისაწვდომია. დამხმარე
Google-ს პირდაპირ უკავშირდება, ამიტომ თანხმობის პროცესი სრულდება იქ, სადაც დაფის
ვერსიას მისი დასრულება არ შეუძლია.

**თუ უკვე დაკავშირებული ხართ** (`omniroute connect <host>`), არაფრის
კოპირება არ გჭირდებათ — დამხმარე ავტორიზაციის მონაცემს თქვენ ნაცვლად გადასცემს
იმ ინსტალაციას:

```bash
# თქვენს ლოკალურ კომპიუტერზე (საჭიროა Node.js + ბრაუზერი):
omniroute connect 192.168.0.15        # ერთხელ — ქმნის ადმინისტრატორის უფლებების მქონე კონტექსტურ ტოკენს
npx omniroute login antigravity
#   ↳ ხსნის Google-ის თანხმობის ეკრანს, callback-ს ლოკალურ loopback პორტზე იღებს,
#     ცვლის მას და ავტორიზაციის მონაცემს POST მოთხოვნით აქტიურ კონტექსტში აგზავნის:
#
#   Antigravity დაკავშირებულია მისამართზე http://192.168.0.15:20128 (კავშირი abc123).
#   ჩასმა საჭირო არ არის — შეგიძლიათ ეს ტერმინალი დახუროთ.
```

გადაგზავნა ავტომატურად ხდება ყოველთვის, როცა აქტიური კონტექსტი სხვა
კომპიუტერზე მიუთითებს. ნებისმიერ შემთხვევაში იძულებით სამართავად გამოიყენეთ
`--push` / `--no-push`, ხოლო კონკრეტული კონტექსტის მისათითებლად —
`--context <name>`.

**თუ თქვენი კომპიუტერიდან VPS მიუწვდომელია** (firewall-ით დაბლოკილი, SSH-ის გარეშე,
ქსელისგან იზოლირებული სამუშაო ადგილი), დამხმარე მაინც მუშაობს — მას მხოლოდ
Google სჭირდება. გამოიყენეთ `--no-push`, ან უბრალოდ მიეცით გადაგზავნას ჩავარდნის
საშუალება: უკვე დასრულებული ავტორიზაციის გაუქმების ნაცვლად, ის სათადარიგო რეჟიმში
blob-ს დაბეჭდავს.

```bash
npx omniroute login antigravity --no-push
#   omniroute-cred-v1.eyJ2IjoxLCJ...
```

შემდეგ **დისტანციურ** დაფაზე გადადით: **Providers → Antigravity → Connect** და
`omniroute-cred-v1.…` blob ჩასვით **Step 2** ველში (ის იღებს როგორც
callback URL-ს, ისე ავტორიზაციის მონაცემების blob-ს). OmniRoute მას დეკოდირებს,
Cloud Code-ის საწყის გამართვას სერვერის მხარეს გაუშვებს და კავშირს შეინახავს.

> blob შეიცავს refresh token-ს — მოეპყარით მას, როგორც პაროლს. გადაგზავნის გზის
> გამოყენებისას ის ერთხელ იგზავნება თქვენი კონტექსტის ავთენტიფიცირებული კავშირით;
> ჩასმის გზის გამოყენებისას კი — დაფასთან თქვენი კავშირით. ორივე შემთხვევაში ის
> დისკზე დაშიფრული სახით ინახება, ხოლო წარმატებული გადაგზავნისას თქვენს ტერმინალში
> არასოდეს იბეჭდება.

ალმები: `--no-browser` (ავტომატურად გახსნის ნაცვლად URL-ის დაბეჭდვა), `--port <n>`
(loopback პორტის დაფიქსირება), `--timeout <ms>`, `--push` / `--no-push` (ავტომატური
მიწოდების უგულებელყოფა), `--context <name>` (კონკრეტული კონტექსტის მითითება).

### ვარიანტი B — SSH-ის ლოკალური გადამისამართების გვირაბი

თუ VPS-ზე SSH წვდომა გაქვთ, გადაამისამართეთ დაფის პორტი ისე, რომ
loopback callback გვირაბის გავლით ისევ სერვერზე მოხვდეს:

```bash
# თქვენს ლოკალურ კომპიუტერზე:
ssh -L 20128:127.0.0.1:20128 user@your-vps
# შემდეგ თქვენს ლოკალურ ბრაუზერში გახსენით http://localhost:20128 და Antigravity
# ჩვეულებრივ დააკავშირეთ — 127.0.0.1:20128/callback გადამისამართება ახლა VPS-ს SSH-ის გავლით აღწევს.
```

რადგან დაფას `localhost:20128` მისამართით უკავშირდებით, Google-ის თანხმობის
პროცესი სრულდება და callback იმავე გვირაბის გავლით სერვერს გადაეცემა —
blob საჭირო არ არის. გვირაბი ღია დატოვეთ, სანამ კავშირი აქტიურად არ გამოჩნდება.

ქვემოთ მოცემული ფიქსირებული loopback-ის მქონე პროვაიდერებისგან განსხვავებით,
აქ **ერთი გადამისამართებაც საკმარისია**: Antigravity-ის callback თავად დაფის
პორტს იყენებს, ამიტომ პროვაიდერისთვის განკუთვნილი მეორე პორტის გვირაბით
გატარება საჭირო არ არის.

> სრულად headless ალტერნატივისთვის (დამხმარისა და გვირაბის გარეშე) დააკონფიგურირეთ
> Google OAuth-ის **საკუთარი** ვებ-ავტორიზაციის მონაცემები + საჯარო საბაზო URL;
> იხილეთ პროვაიდერის OAuth გარემოს ცვლადები. ზემოთ მოცემულ ორ ვარიანტს Google-ის
> დამატებითი კონფიგურაცია არ სჭირდება.

## Codex / Grok-ის დაკავშირება დისტანციურ ინსტალაციასთან (ფიქსირებული loopback-ის მქონე პროვაიდერები)

Codex, xAI (`xai-oauth`) და Grok CLI (`grok-cli`) თავიანთ ზემდგომ OAuth აპში
**ფიქსირებულ** loopback `redirect_uri`-ს არეგისტრირებენ. OmniRoute-ს მისი შეცვლა
არ შეუძლია — პროვაიდერი ბრაუზერს ყოველთვის იმავე, კოდში გაწერილ მისამართზე აბრუნებს:

| პროვაიდერი  | ფიქსირებული callback, რომელზეც პროვაიდერი გადამისამართებას ახდენს |
| ----------- | ----------------------------------------------------------------- |
| `codex`     | `http://localhost:1455/auth/callback`                             |
| `xai-oauth` | `http://127.0.0.1:56121/callback`                                 |
| `grok-cli`  | `http://127.0.0.1:56122/callback`                                 |

აქ `localhost` ნიშნავს **მანქანას, რომელზეც ბრაუზერი მუშაობს**, ხოლო OmniRoute-ის PKCE
callback-სერვერი **სერვერის** loopback-ზე უსმენს. თუ დაფას გახსნით LAN
მისამართზე, მაგალითად `http://192.168.0.15:20128`, ეს ორი ერთმანეთს ვერ დაუკავშირდება:
ავტორიზაციის კოდი გადაეცემა თქვენი ლეპტოპის `localhost:1455`-ს, სადაც არაფერი უსმენს,
და პროვაიდერი სისტემაში შესვლას ხილული შეცდომის გარეშე წყვეტს.

დაფა ამას popup-ის გახსნამდე ამოიცნობს და ჩუმად წარუმატებელი შესვლის ნაცვლად
გვირაბის ბრძანებას აჩვენებს (#8046).

### გამოსწორება — გადაამისამართეთ **ორივე** პორტი

```bash
# მანქანაზე, რომელზეც ბრაუზერი მუშაობს:
ssh -L 20128:127.0.0.1:20128 -L 1455:127.0.0.1:1455 <user>@192.168.0.15
# შემდეგ გახსენით http://localhost:20128 და იქიდან დააკავშირეთ Codex
```

საჭიროა ორი გადამისამართება და მხოლოდ ერთის გადამისამართება მაინც წარუმატებლად დასრულდება:

- **`20128`** (დაფის პორტი) origin-ს ნამდვილ localhost-ად აქცევს, რაც
  OmniRoute-ს საერთოდ PKCE callback-სერვერის გაშვებას აიძულებს — LAN origin
  ამ განშტოებამდე არასდროს აღწევს.
- **`1455`** (პროვაიდერის ფიქსირებული callback-პორტი) არის ადგილი, სადაც ბრაუზერი
  ბრუნდება; ის გვირაბით სერვერის loopback-მდე უნდა მივიდეს.

xAI-ის ან Grok CLI-ის დაკავშირებისას `1455` შეცვალეთ `56121`/`56122`-ით, ხოლო
`20128` — თქვენი დაფის რეალური პორტით. გვირაბი ღია დატოვეთ, სანამ კავშირი
აქტიურად არ გამოჩნდება.

> **SSH-ზე წვდომა არ გაქვთ?** Codex და Grok CLI ასევე იღებენ ჩასმულ ტოკენს —
> დაკავშირების დიალოგში არსებული **API გასაღების ჩასმა** / **auth.json-ის იმპორტი**
> ჩანართიდან. ამ გზას loopback callback არ აქვს, ამიტომ ის ნებისმიერი origin-იდან
> მუშაობს. Codex დამატებით იღებს ცალკეულ წვდომის ტოკენს ან `~/.codex/auth.json`
> სესიის ბლობს.

omniroute tokens create --name "laptop" --scope write [--expires 30]

omniroute tokens list                 # შენიღბული: id, სახელი, scope, პრეფიქსი, სტატუსი, ვადის გასვლა

(შექმნა, გაუქმება, ერთჯერადი კოპირება).

## კოდირების CLI-ის კონფიგურაცია დისტანციური კატალოგიდან

`omniroute configure` კითხულობს **აქტიური სერვერის** მოდელების მიმდინარე კატალოგს
და კონფიგურაციას **თქვენს** მანქანაზე წერს.

```bash
omniroute configure codex
#   პროვაიდერები: glm, kmc, ollamacloud, opencode-go, …
#   პროვაიდერი: glm
#   მოდელის id: glm/glm-5.2
#   ✔ ჩაიწერა ~/.codex/glm52.config.toml
#   გამოყენება:  codex --profile glm52

# არაინტერაქტიული
omniroute configure codex --provider glm --model glm/glm-5.2 --name glm52

# ხშირად გამოყენებული მოდელის ინტერაქტიული ამომრჩევლის თავში დატოვება
omniroute configure codex --provider glm --model glm/glm-5.2 --favorite --yes
```

ამომრჩეველი ლოკალურ `model-preferences.json` ფაილში ინახავს მხოლოდ მოდელის ID-ებს
(არასდროს URL-ებს ან ავტორიზაციის მონაცემებს), კონტექსტისა და CLI სამიზნის მიხედვით.
რჩეულები უახლეს არჩევანებამდე გამოჩნდება; არჩეული მოდელის ამ კონტექსტის/სამიზნის
სიიდან ამოსაღებად გამოიყენეთ `--unfavorite`.

ჩაწერილი პროფილი ინფერენსის გასაღებს env var-ის მეშვეობით მიმართავს
(`OMNIROUTE_API_KEY`) — საიდუმლო დისკზე არასდროს იწერება. Codex-ის ერთჯერადი
საბაზისო გამართვისთვის (`[model_providers.omniroute]` ბლოკი) იხილეთ
[CODEX-CLI-CONFIGURATION.md](./CODEX-CLI-CONFIGURATION.md).

### CLI-ის გაშვება დისტანციურ სერვერთან (კონფიგურაციის ჩაწერის გარეშე)

`omniroute run <target>` ასევე ითვალისწინებს აქტიურ კონტექსტს: დისტანციური საბაზისო
URL და კონტექსტის ავტორიზაციის მონაცემები მხოლოდ გაშვებულ პროცესში ინექცირდება.

```bash
omniroute connect 192.168.0.15
omniroute run claude   --model openai/gpt-5.4          # Claude Code → დისტანციური
omniroute run gemini   --model glm/glm-5.2 -- --skip-trust -p "hello"
omniroute run opencode --model glm/glm-5.2 -- run "reply OK"

# ზუსტად იმის წინასწარი ნახვა, რაც გაეშვებოდა (მხოლოდ env გასაღებების სახელები, არასდროს მნიშვნელობები):
omniroute run codex --dry-run --json
```

სამიზნეები: `claude`, `codex`, `aider`, `goose`, `opencode`, `qwen`, `gemini`
(ერთიანი წყარო: `bin/cli/cli-manifest.mjs`). Qwen და Gemini მუშაობენ დროებით,
იზოლირებულ home-ში, რომელიც გასვლისას იშლება, ამიტომ გაშვება თქვენს პირად
ხელსაწყოთა კონფიგურაციას არასდროს ეხება — და არც მასში ჟონავს.

| Goose       | `omniroute setup-goose`    | `~/.config/goose/config.yaml` (`GOOSE_PROVIDER=openai` + `OPENAI_HOST` `/v1`-ის **გარეშე** + `GOOSE_MODEL`) + გარემოს ცვლადების ინსტრუქცია                                                                         |
| Aider       | `omniroute setup-aider`    | `~/.aider.conf.yml` (`openai-api-base` `/v1`-ის **გარეშე** + `model: openai/<id>`) + გარემოს ცვლადების ინსტრუქცია (`aider --message --yes`)                                                                        |
| Qwen Code   | `omniroute setup-qwen`     | `~/.qwen/settings.json` V4-ის `modelProviders.openai` ჩანაწერი + `OMNIROUTE_API_KEY` ფაილში `~/.qwen/.env`                                                                                                         |

```bash
# OpenCode (OpenAI-თან თავსებადი პროვაიდერი, კატალოგის ყველა მოდელი, დისტანციური VPS)
omniroute setup-opencode --remote http://192.168.0.15:20128 --api-key oma_live_xxx
omniroute setup-opencode --only glm,kimi        # მხოლოდ შესაბამისი მოდელების დატოვება
opencode -m omniroute/glm/glm-5.2 "..."          # ჯერ OMNIROUTE_API_KEY-ის ექსპორტი
```

> OpenCode-ს ასევე აქვს უფრო ფუნქციური **მოდულის** ინტეგრაცია: `omniroute setup opencode`
> (`--remote`-ის მეშვეობით ახლა დისტანციურ რეჟიმსაც უჭერს მხარს), რომელიც აყენებს `@omniroute/opencode-plugin`-ს.
> `setup-opencode` არის მსუბუქი, OpenAI-თან თავსებადი ალტერნატივა. API გასაღები
> მითითებულია `{env:OMNIROUTE_API_KEY}`-ის მეშვეობით — ის არასოდეს იწერება დისკზე.
>
> OpenCode v2-ში მის ნაცვლად გამოიყენეთ `@omniroute/opencode-plugin-v2`: იგივე კატალოგი,
> განსხვავებული ჩამტვირთავის კონტრაქტი. როდესაც ინტეგრაცია დაკავშირებულია, ის გასაღებს OpenCode-ის საკუთარი ავტორიზაციის მონაცემების
> საცავიდან კითხულობს, ამიტომ დისტანციური კარიბჭისთვის `opencode.json`-ში გასაღები საერთოდ არ არის საჭირო.

## კონტექსტების მართვა (სერვერებს შორის გადართვა)

**კონტექსტი** არის შენახული სერვერი (baseUrl + სერთიფიკატი + scope). `omniroute connect` ქმნის მას და აქტიურს ხდის; ამის შემდეგ ყველა ბრძანება მასზეა მიმართული. მართეთ და გადართეთ მათ შორის `omniroute contexts`-ის გამოყენებით:

```bash
omniroute contexts list            # all contexts; the active one is marked ●
omniroute contexts current         # the active server, auth status, scope
```

```text
  | სახელი   | ბაზის URL                 | ავთ.  | Scope | აღწერა
● | vps     | http://100.67.86.91:20128 | token | admin | დისტანციური OmniRoute (…)
  | default | http://localhost:20128    | ✗     |       |
```

**სერვერების გადართვა** — ყოველი მომდევნო ბრძანება მიჰყვება აქტიურ კონტექსტს:

```bash
omniroute contexts use vps         # → all commands now hit the remote VPS
omniroute tokens list              #   (მუშაობს VPS-ის წინააღმდეგ)

omniroute contexts use default     # → back to localhost
omniroute tokens list              #   (მუშაობს ლოკალური სერვერის წინააღმდეგ)
```

**კონტექსტის ხელით დამატება** (`connect`-ის ნაცვლად), შემოწმება ან გადარქმევა:

```bash
omniroute contexts add staging --url https://staging.example.com:20128 \
  --access-token oma_live_xxxx --scope write --description "staging box"
omniroute contexts show staging    # სრული დეტალები ერთი კონტექსტისთვის
omniroute contexts rename staging stg
```

**კონტექსტის წაშლა** — ითხოვს დადასტურებას; გამოიყენეთ `--yes` მის გამოსატოვებლად (საჭიროა სკრიპტებისთვის / არაინტერაქტიული გარსებისთვის, რომლებიც სხვა შემთხვევაში უსაფრთხოდ უარს ამბობენ):

```bash
omniroute contexts remove stg --yes
```

> `default` (localhost) ვერ წაიშლება. აქტიური კონტექსტის წაშლა `default`-ზე ბრუნდება. რჩევა: კონტექსტის წაშლა მხოლოდ შლის **ლოკალურად** შენახულ სერთიფიკატს — გააუქმეთ ტოკენი სერვერზე `omniroute tokens revoke <id>`-ის გამოყენებით წვდომის სრულად გასაუქმებლად.

**კონტექსტების ექსპორტი / იმპორტი** (მაგ., მათი მანქანებს შორის გადასატანად). ექსპორტი ნაგულისხმევად გამოტოვებს სერთიფიკატებს, მათ შორის ფაილის სარეზერვო ასლის მიერ შენახულ სერთიფიკატებს. გამოიყენეთ `--include-secrets` მკაფიოდ, როდესაც საჭიროა პორტატული სერთიფიკატების შემცველი სარეზერვო ასლი:

```bash
omniroute contexts export --out contexts.json     # რედაქტირებული; ნაგულისხმევი დანიშნულება: stdout
omniroute contexts export --include-secrets --out private-contexts.json
omniroute contexts import contexts.json            # გადაწერა; --merge არსებულის შესანარჩუნებლად
omniroute contexts migrate --yes                  # ძველი plaintext ტოკენების გადატანა keychain-ში
```

`--include-secrets` აგვარებს keychain-ის მითითებებს ექსპორტამდე და ვერ ხერხდება, თუ რომელიმე მითითებული სერთიფიკატის წაკითხვა შეუძლებელია. `--no-secrets` ყოველთვის უპირატესია. ექსპორტის ფაილები იწერება ატომურად `0600` რეჟიმით. განიხილეთ მკაფიო საიდუმლოების შემცველი ექსპორტი, როგორც საიდუმლო მასალა. უსათაურო სისტემებზე გამოსაყენებელი OS keychain-ის გარეშე, CLI ბრუნდება `config.json`-ზე `0600` რეჟიმით და ბეჭდავს ერთჯერად გაფრთხილებას; ნაგულისხმევი ექსპორტი რჩება რედაქტირებული ამ რეჟიმში.

## სწრაფი სრული შემოწმება

დასაკოპირებლად გამზადებული სრული ციკლი დისტანციური კონფიგურაციის ნულიდან შესამოწმებლად — დაკავშირება, შეზღუდული
წვდომის დონის მქონე ტოკენის შექმნა, ბრძანების გაგზავნა, უკან გადართვა და კონფიგურაციის წაშლა. ჩაანაცვლეთ
`192.168.0.15` თქვენი სერვერის ჰოსტით/IP-ით (Tailscale, LAN ან საჯარო
`https://…` URL).

```bash
# 1. დაკავშირება (პაროლი → admin ტოკენი, ინახება კონტექსტად და აქტიურდება)
omniroute connect 192.168.0.15                 # ან: --key oma_live_xxxx  (პაროლის გარეშე)
omniroute contexts current                     # აჩვენებს დისტანციურ სერვერს + წვდომის დონეს

# 2. გამოყენება — მართვის ბრძანებები ახლა დისტანციურ სერვერზე სრულდება
omniroute tokens create --name laptop --scope read   # უფრო შეზღუდული ტოკენის შექმნა
omniroute tokens list                                 # შენიღბული სია დისტანციური სერვერიდან

# 3. წინ და უკან გადართვა
omniroute contexts use default                 # → ლოკალური
omniroute contexts use 192-168-0-15            # → ისევ დისტანციური (სახელი `contexts list`-იდან)

# 4. კონფიგურაციის წაშლა. შენიშვნა: `contexts remove` მხოლოდ ლოკალურ ავტორიზაციის მონაცემს შლის —
#    ის სერვერზე ტოკენს არ აუქმებს. საჭიროების შემთხვევაში ჯერ სერვერის მხარეს გააუქმეთ,
#    რათა წვდომა რეალურად შეწყდეს.
omniroute tokens revoke <id|prefix>            # წყვეტს სერვერზე წვდომას
omniroute contexts remove 192-168-0-15 --yes   # შლის ლოკალურ კონტექსტს (აქტიურიც რომ იყოს → ბრუნდება default-ზე), დადასტურების გარეშე
```

> `--yes` ბრძანებას `contexts remove` არაინტერაქციულს ხდის (აუცილებელია სკრიპტებში/CI-ში; მის გარეშე
> არაინტერაქციული გარსი გაჭედვის ნაცვლად უსაფრთხოდ უარყოფს მოქმედებას). **აქტიური**
> კონტექსტის წაშლისას სისტემა ავტომატურად `default`-ზე ბრუნდება.

## უსაფრთხოების შენიშვნები

- ტოკენის ღია ტექსტი მხოლოდ ერთხელ გამოჩნდება; ინახება მხოლოდ SHA-256 ჰეში (ისევე, როგორც API გასაღებების შემთხვევაში).
- `omniroute connect` ხელახლა იყენებს სისტემაში შესვლის უხეში ძალის მეთოდით შეტევებისგან დაბლოკვასა და აუდიტის ჟურნალის წარმოებას.
- ტრანსპორტისთვის უპირატესობა მიანიჭეთ HTTPS-ს ან Tailnet-ს; მხოლოდ ჰოსტის მითითებისას ნაგულისხმევად გამოიყენება `http://`
  LAN/Tailscale-ის მოხერხებულობისთვის — TLS-ის გამოსაყენებლად მიუთითეთ სრული `https://…` URL.
- სასურველი ლოკალური კონტექსტის ფაილია `~/.omniroute/config.json` (`chmod 600`),
  რომელიც შეიცავს მხოლოდ `credentialRef`-ს; თავად ტოკენი ინახება ოპერაციული სისტემის
  გასაღებების საცავში (`keytar`) და არასოდეს იბეჭდება ჟურნალებში. გრაფიკული ინტერფეისის გარეშე ინსტალაციები, რომლებშიც
  მოქმედი ნატიური გასაღებების საცავი არ არის, აშკარად განსაზღვრული სარეზერვო ვარიანტის სახით იყენებენ იმავე
  `0600` ფაილს და ერთხელ გამოსცემენ გაფრთხილებას. გასაღებების საცავის ბექენდის დაყენების შემდეგ გამოიყენეთ
  `omniroute contexts migrate --yes`.
