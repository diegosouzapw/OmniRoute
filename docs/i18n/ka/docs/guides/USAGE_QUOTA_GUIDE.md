> **TL;DR**: OmniRoute აღრიცხავს თითოეული მოთხოვნის ტოკენების გამოყენებას, ითვლის ღირებულებას, აღასრულებს თითოეული API გასაღებისთვის განსაზღვრულ კვოტას და ანალიტიკას მართვის პანელში აჩვენებს. ეს სახელმძღვანელო განმარტავს, როგორ მუშაობს ეს ყველაფერი.

**წყაროები:**

- `open-sse/services/usage.ts` (~70KB) — გამოყენების ძირითადი აღრიცხვა
- `src/lib/usageAnalytics.ts` (~10KB) — მონაცემების აგრეგაცია მართვის პანელისთვის
- `src/lib/db/quotaSnapshots.ts` — კვოტის ისტორიული მონაცემები
- `src/lib/db/usage*.ts` — გამოყენებასთან დაკავშირებული მონაცემთა ბაზის რამდენიმე მოდული

## მიმოხილვა

OmniRoute-ში გამავალი თითოეული მოთხოვნა ქმნის **გამოყენების ჩანაწერს**, რომელიც მოიცავს:

- **იდენტიფიკაციას**: რომელი API გასაღები, პროვაიდერი, მოდელი და კომბინაცია გამოიყენებოდა
- **ტოკენებს**: პრომპტის ტოკენები, დასრულების ტოკენები, ქეშირებული ტოკენები და ჯამური რაოდენობა
- **ღირებულებას**: თანხა აშშ დოლარში (გამოთვლილი ფასების მონაცემების საფუძველზე)
- **დროით მონაცემებს**: დაყოვნებას, დაწყებისა და დასრულების დროის ნიშნულებს
- **სტატუსს**: წარმატება, შეცდომა, სიხშირის შეზღუდვა და სხვ.

ეს ჩანაწერები ერთიანდება **ანალიტიკურ მონაცემებად**, ინახება **კვოტის სნეპშოტების** სახით და გამოიყენება **თითოეული გასაღებისთვის განსაზღვრული ბიუჯეტის ლიმიტების** აღსასრულებლად.

```
მოთხოვნა ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    ანალიტიკა   კვოტა   ბილინგი
                 (მართვის პანელი) (აღსრულება) (ექსპორტი)
```

## რა აღირიცხება

`usage.ts` სერვისი თითოეული მოთხოვნისთვის აფიქსირებს **გამოყენების მოვლენას**:

| ველი               | ტიპი    | წყარო                                                              |
| ------------------ | ------- | ------------------------------------------------------------------ |
| `id`               | string  | ჩანაწერის შექმნისას გენერირებული UUID                              |
| `apiKeyId`         | string  | API გასაღები, რომელმაც მოთხოვნა წამოიწყო                           |
| `provider`         | string  | პროვაიდერის ID (openai, anthropic და სხვ.)                         |
| `model`            | string  | მოდელის ID (gpt-5, claude-opus-4-6 და სხვ.)                        |
| `comboId`          | string? | კომბინაციის ID, თუ მარშრუტიზაცია კომბინაციის გავლით მოხდა          |
| `promptTokens`     | number  | ზედა დონის სერვისის პასუხიდან                                      |
| `completionTokens` | number  | ზედა დონის სერვისის პასუხიდან                                      |
| `cachedTokens`     | number  | ქეშში დამთხვევის ტოკენები (Anthropic-ის პრომპტის ქეშირება და სხვ.) |
| `totalTokens`      | number  | პრომპტისა და დასრულების ტოკენების ჯამი                             |
| `costUsd`          | number  | გამოთვლილია ფასების მონაცემების საფუძველზე                         |
| `latencyMs`        | number  | მოთხოვნის სრული ხანგრძლივობა                                       |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled`         |
| `errorClass`       | string? | შეცდომის კლასი, თუ status != success                               |
| `timestamp`        | string  | ISO 8601 UTC                                                       |
| `metadata`         | object  | პლაგინის მიერ დამატებული მორგებული მონაცემები                      |

### საიდან მიიღება ტოკენები

ტოკენები ზედა დონის პროვაიდერის პასუხიდან **პასუხის დამმუშავებელში** ამოიღება:

```ts
// ფაილიდან open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

იმ პროვაიდერებისთვის, რომლებიც გამოყენების მონაცემებს არ აბრუნებენ (მაგალითად, ზოგიერთი ვებ-ქუქიზე დაფუძნებული პროვაიდერი), OmniRoute ტოკენების რაოდენობას **მიახლოებით ითვლის** ევრისტიკის გამოყენებით: `~4 სიმბოლო თითო ტოკენზე` (იხილეთ `open-sse/services/autoCombo/pipelineRouter.ts`).

### ქეშირებული ტოკენები

OmniRoute `cached_tokens`-ს `prompt_tokens`-ისგან განცალკევებით აღრიცხავს, რადგან:

- Anthropic-ის პრომპტის ქეშირებისას ქეშირებული ტოკენებისთვის შემცირებული ტარიფი მოქმედებს (ჩვეულებრივი ტარიფის 10%)
- ზოგიერთი პროვაიდერი აბრუნებს `cache_read_input_tokens`-ს, რომლის ღირებულებაც განსხვავებულად უნდა გამოითვალოს
- ანალიტიკას შეუძლია აჩვენოს **ქეშში დამთხვევის მაჩვენებელი** = `cached_tokens / prompt_tokens`

## ღირებულების გამოთვლა

ღირებულება გამოითვლება LiteLLM-იდან სინქრონიზებული **ფასების მონაცემების** საფუძველზე (`src/lib/pricingSync.ts`):

| მოდელი            | შეყვანა $/1M | გამოყვანა $/1M | კეშირებული $/1M |
| ----------------- | ------------ | -------------- | --------------- |
| gpt-5             | $2.50        | $10.00         | —               |
| claude-opus-4-6   | $15.00       | $75.00         | $1.50           |
| claude-sonnet-4-5 | $3.00        | $15.00         | $0.30           |
| gemini-2.5-pro    | $1.25        | $10.00         | —               |

ღირებულების ფორმულა (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **რატომ აკლდება კეშირებული ტოკენები მოთხოვნის ტოკენებს?** კეშირებული ნაწილი ცალკე ფასდება; შეყვანის ფასის მთელ მოთხოვნაზე დარიცხვა ღირებულების გადაჭარბებულად დათვლას გამოიწვევდა.

### ფასების სინქრონიზაცია

ფასების მონაცემები ავტომატურად სინქრონიზდება LiteLLM-იდან `/api/pricing/sync` ბოლო წერტილის მეშვეობით (ამოქმედდება ჩაშენებული cron ამოცანით და არა მომხმარებლისთვის განკუთვნილი გარემოს ცვლადით):

```bash
# ხელით ამოქმედება
curl -X POST http://localhost:20128/api/pricing/sync
```

მოდელებისთვის, რომლებისთვისაც ფასების მონაცემები არ არსებობს, OmniRoute ღირებულების **შეფასებისთვის** იყენებს შიდა საშუალო ტარიფებს (რომლებიც LiteLLM-ის ფასების მონაცემებიდანაა მიღებული).

### მართვის პანელისთვის გამოთვლილი ვიჯეტები

თარიღების ნებისმიერი დიაპაზონისთვის ანალიტიკის შრე ითვლის:

| ვიჯეტი                         | აღწერა                                                                                              |
| ------------------------------ | --------------------------------------------------------------------------------------------------- |
| **შემაჯამებელი ბარათები**      | მოთხოვნების ჯამური რაოდენობა, ჯამური ღირებულება, ტოკენების ჯამური რაოდენობა, წარმატების მაჩვენებელი |
| **დღიური ტენდენციის დიაგრამა** | ღირებულება + ტოკენები დღიურად, მოდელების მიხედვით დაწყობილი                                         |
| **აქტივობის თბური რუკა**       | დღის საათი × კვირის დღე, ფერი = მოთხოვნების რაოდენობა                                               |
| **მოდელების განაწილება**       | ღირებულების წრიული დიაგრამა მოდელების მიხედვით                                                      |
| **პროვაიდერების განაწილება**   | მოთხოვნების სვეტოვანი დიაგრამა პროვაიდერების მიხედვით                                               |
| **საუკეთესო API გასაღებები**   | ღირებულების მიხედვით 10 საუკეთესო გასაღების ცხრილი                                                  |
| **შეცდომების ანალიზი**         | შეცდომების მაჩვენებელი დროში, შეცდომების მთავარი კლასები                                            |

### პროგრამული წვდომა

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // გამოყენების ისტორიის ჩანაწერები
  "7d",                 // დროის დიაპაზონი: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // პროვაიდერის კავშირების რუკა (connectionId → ანგარიშის სახელი)
  {
    startDate: "2025-01-01",  // არასავალდებულო: "custom" დიაპაზონისთვის
    endDate: "2025-06-01",   // არასავალდებულო: "custom" დიაპაზონისთვის
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (ცენტი)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## კვოტის აღსრულება

თითოეული API გასაღებისთვის კვოტა ორ ადგილას აღსრულდება:

1. **რბილი ლიმიტი** (`quotaWarnAt`): დაფაზე გამოჩნდება გაფრთხილება, როდესაც გამოყენება ზღვარს გადააჭარბებს
2. **მკაცრი ლიმიტი** (`quotaLimit`): ლიმიტის გადაჭარბებისას მოთხოვნა უარყოფილი იქნება HTTP 429 კოდით

### კონფიგურაცია

```ts
// თითოეული API გასაღებისთვის
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — გაფრთხილების ჩვენება
  quotaLimit: 10_00,    // $10.00 — სრული შეჩერება
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### აღსრულების პროცესი

```
მოთხოვნა ──▶ quotaCheck()
              │
              ├── ლიმიტის ფარგლებშია?  ──▶ დაშვება
              │
              └── ლიმიტს აჭარბებს?  ──▶ 429 Too Many Requests
                                        Retry-After სათაურით
```

### კვოტის სურათები

`quotaSnapshots` ცხრილი ტენდენციების ანალიზისთვის ინახავს **კვოტის ისტორიულ მდგომარეობას**:

| ველი | აღწერა |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | გასაღები, რომლის მონიტორინგიც ხდება |
| `window` | "day" | "week" | "month" |
| `used` | ამ ფანჯარაში გამოყენებული ღირებულება (ცენტებში) |
| `limit` | ლიმიტი (ცენტებში) |
| `resetAt` | ფანჯრის განულების დრო |
| `createdAt` | სურათის შექმნის დრო |

სურათები იქმნება **ყოველი მოთხოვნისას**, რომლის ღირებულებაც > 0-ია, და გამოიყენება შემდეგისთვის:

- დაფაზე კვოტის პროგრესის ზოლის გამოსახვა
- კვოტის 30-დღიანი ტენდენციის დიაგრამების ჩვენება
- გაფრთხილებების გააქტიურება, როდესაც გამოყენება ლიმიტს უახლოვდება

## შენახვა და გასუფთავება

გამოყენების მონაცემების მოცულობა თითოეულ მოთხოვნაზე დაახლოებით ~1-10KB-ით იზრდება. დიდი მასშტაბის შემთხვევაში ეს შეიძლება მნიშვნელოვანი იყოს.

### შენახვის პარამეტრები

გამოყენების ისტორიის შენახვა კონფიგურირდება UI-ში Database Settings-ის მეშვეობით ან `/api/settings/database`-ის გამოყენებით.

ნაგულისხმევად, გამოყენების ისტორია ინახება **90 დღის** განმავლობაში.

### გასუფთავება

ძველ ჩანაწერებს ასუფთავებს `src/lib/db/cleanup.ts`:

- მისი გაშვება ხდება ფონური cron-პროცესის მიერ
- შლის `usage_history`-დან იმ ჩანაწერებს, რომლებიც კონფიგურირებულ `usageHistory` შენახვის პერიოდზე ძველია

### საცავის მოცულობის შეფასება

| მოთხოვნების სიხშირე  | საცავი 30 დღისთვის | საცავი 90 დღისთვის |
| -------------------- | ------------------ | ------------------ |
| 100 მოთხოვნა/დღე     | ~3MB               | ~9MB               |
| 1,000 მოთხოვნა/დღე   | ~30MB              | ~90MB              |
| 10,000 მოთხოვნა/დღე  | ~300MB             | ~900MB             |
| 100,000 მოთხოვნა/დღე | ~3GB               | ~9GB               |

ძალიან მაღალი ტრაფიკის შემთხვევაში გაითვალისწინეთ:

- Database Settings-ის მეშვეობით შენახვის პერიოდის შემცირება
- დაუმუშავებელი ჩანაწერების ნაცვლად `aggregated_metrics`-ის გამოყენება (მხოლოდ ანალიტიკისთვის)

## პრობლემების მოგვარება

### „ხარჯი მოსალოდნელზე მაღალია“

1. შეამოწმეთ **`/api/usage/analytics?groupBy=model`** — იპოვეთ ძვირადღირებული მოდელი
2. შეამოწმეთ **`/api/usage/analytics?groupBy=apiKey`** — იპოვეთ ინტენსიური მომხმარებელი
3. დარწმუნდით, რომ ფასების მონაცემები განახლებულია: `POST /api/pricing/sync`

### „ჩანაწერები აკლია“

- შეამოწმეთ DB-ის შენახვის პარამეტრები Dashboard → Database → Cleanup განყოფილებაში — ძველი ჩანაწერები იშლება პერიოდული გასუფთავების ამოცანის მიერ (`src/lib/db/cleanup.ts`)
- შეამოწმეთ შეცდომები `src/lib/db/usage*.ts`-ში — DB-ში ჩაწერის შეცდომები ჟურნალში ინახება, მაგრამ ინტერფეისში არ გამოჩნდება
- დარწმუნდით, რომ მოთხოვნამ რეალურად მიაღწია `chatCore`-მდე — შეამოწმეთ კომბინირებული მარშრუტიზაცია

### „კვოტა არ მოქმედებს“

- შეამოწმეთ გასაღების `quotaLimit` პარამეტრი
- დარწმუნდით, რომ `quotaWindow` სწორად არის დაყენებული
- მოძებნეთ `quotaSnapshots` ჩანაწერები — ისინი ყოველი მოთხოვნისას უნდა შეიქმნას
