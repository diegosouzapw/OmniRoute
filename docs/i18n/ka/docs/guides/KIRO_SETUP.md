ეს სახელმძღვანელო აღწერს Kiro-ს (AWS-ზე განთავსებული AI კოდირების ასისტენტი) ანგარიშების OmniRoute-ში დამატებას,
განსაკუთრებული აქცენტით რამდენიმე ანგარიშის ერთდროულად გაშვებაზე სესიების კონფლიქტების გარეშე.

---

## წინაპირობა: რატომ შეიძლება წარმოიშვას კონფლიქტი Kiro-ს ანგარიშებს შორის

Kiro-ს ბექენდი აქტიური სესიების აღსარიცხად AWS SSO OIDC კლიენტის რეგისტრაციებს იყენებს.
მთავარი შეზღუდვაა: **OIDC კლიენტის თითოეული რეგისტრაცია ერთდროულად მხოლოდ ერთ აქტიურ
სესიას უჭერს მხარს**. როდესაც მეორე მოწყობილობა ან მომხმარებელი იმავე
რეგისტრირებული კლიენტით გაივლის ავთენტიფიკაციას, ბექენდი პირველი ანგარიშის განახლების ტოკენს აუქმებს.

ეს იგივე მექანიზმია, რომელიც პრობლემებს იწვევს `kiro-cli login`-ის გაშვებისას იმ
კომპიუტერზე, სადაც Kiro-ს სხვა ანგარიშით უკვე შესული ხართ — ახალი შესვლა
პირველი ანგარიშის ტოკენს აუქმებს.

---

## როგორ აგვარებს ამას OmniRoute (v3.8.0+)

v3.8.0-დან დაწყებული, OmniRoute Kiro-ს კავშირის ყოველი იმპორტისას იძახებს
`registerClient()`-ს (AWS SSO OIDC). შედეგად, OmniRoute-ის თითოეული კავშირი საკუთარ,
გამოყოფილ OIDC კლიენტის რეგისტრაციას იღებს. რადგან კლიენტის თითოეული რეგისტრაცია დამოუკიდებელია,
ერთი ანგარიშის განახლება ან ხელახალი ავთენტიფიკაცია სხვა ანგარიშების განახლების ტოკენებზე არ მოქმედებს.

იზოლაცია ვრცელდება განახლების ტოკენის იმპორტის მეთოდებზე, ხოლო API-გასაღებით ავთენტიფიკაცია
OIDC-ის განახლების სესიებს საერთოდ არ იყენებს:

| იმპორტის მეთოდი                                            | იზოლაციის სტატუსი                                                                                             |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| AWS Builder ID / IDC მოწყობილობის კოდის ნაკადი             | იზოლირებულია მოწყობილობის კოდის ნაკადის დანერგვის მომენტიდან                                                  |
| **ტოკენის იმპორტი** (განახლების ტოკენის ხელით ჩასმა)       | იზოლირებულია v3.8.0-დან                                                                                       |
| **Google / GitHub სოციალური შესვლა**                       | იზოლირებულია v3.8.0-დან                                                                                       |
| **ავტომატური იმპორტი** (kiro-cli SQLite)                   | იზოლირებულია v3.8.0-დან (SQLite-ის გზა უკვე იზოლირებული იყო; SSO-ქეშის სარეზერვო ვარიანტიც ახლა იზოლირებულია) |
| **API-გასაღები** (ხანგრძლივმოქმედი CodeWhisperer გასაღები) | განახლების სესია არ გამოიყენება; გასაღები მოწმდება და ინახება bearer ავტორიზაციის მონაცემად                   |

## მიგრაციის შენიშვნა v3.8.0-მდე შექმნილი კავშირებისთვის

v3.8.0-მდე იმპორტირებულ კავშირებს `providerSpecificData`-ში შენახული გამოყოფილი OIDC კლიენტის
რეგისტრაცია არ აქვთ. ეს კავშირები მუშაობას აგრძელებს, თუმცა იყენებს სოციალური ავთენტიფიკაციის
საერთო განახლების საბოლოო წერტილს, რაც ნიშნავს, რომ ორ ასეთ კავშირს კვლავ შეუძლია ერთმანეთის
ტოკენების გაუქმება.

**იზოლაციის მისაღებად:** წაშალეთ ძველი კავშირი **მართვის პანელი → პროვაიდერები** განყოფილებიდან და
ხელახლა დააიმპორტეთ იგი ნებისმიერი მხარდაჭერილი იმპორტის ნაკადის გამოყენებით. ყველა ახლად შექმნილი
კავშირი საკუთარ კლიენტის რეგისტრაციას ავტომატურად მიიღებს.

## Kiro-ს ორი ანგარიშის გვერდიგვერდ დამატება

### წინაპირობები

- OmniRoute v3.8.0 ან უფრო ახალი.
- მოქმედი Kiro ანგარიში (ელფოსტა + პაროლი, Google ან GitHub შესვლა).
- სურვილისამებრ, Kiro-ს მეორე ანგარიში.

### ნაბიჯი 1: პირველი ანგარიშის იმპორტი

1. გახსენით **მართვის პანელი → პროვაიდერები → პროვაიდერის დამატება → Kiro**.
2. აირჩიეთ ერთ-ერთი:
   - **ტოკენის იმპორტი** — ჩასვით `aorAAAAAG`-ით დაწყებული განახლების ტოკენი.
   - **API-გასაღები** — ჩასვით Kiro / CodeWhisperer-ის ხანგრძლივმოქმედი API-გასაღები.
   - **Google / GitHub შესვლა** — დაასრულეთ OAuth ნაკადი ბრაუზერში.
   - **ავტომატური იმპორტი** — დააწკაპუნეთ ღილაკზე; OmniRoute ავტორიზაციის მონაცემებს
     ადგილობრივი kiro-cli მონაცემთა ბაზიდან ან `~/.aws/sso/cache`-დან წაიკითხავს.
3. კავშირი შეინახება. განახლების ტოკენის ნაკადები ავტომატურად არეგისტრირებს გამოყოფილ
   OIDC კლიენტს. API-გასაღების ნაკადები გასაღებს AWS-ის მეშვეობით ამოწმებს და განახლების ტოკენს არ ინახავს.

### ნაბიჯი 2: მეორე ანგარიშის იმპორტი

გაიმეორეთ ნაბიჯი 1 მეორე ანგარიშისთვის. რადგან თითოეული იმპორტი OIDC კლიენტის ცალკე
რეგისტრაციას ქმნის, ეს ორი კავშირი სრულად იზოლირებულია.

### ნაბიჯი 3: შეამოწმეთ, რომ ორივე კავშირი აქტიურია

1. **მართვის პანელი → პროვაიდერები** — Kiro-ს ორივე კავშირს უნდა ჰქონდეს სტატუსი **აქტიური**.
2. **მართვის პანელი → ჯანმრთელობის მდგომარეობა** — ორივე კავშირმა წარმატებით უნდა გაიაროს ტოკენის მდგომარეობის შემოწმება.

### ნაბიჯი 4: ანგარიშებს შორის მარშრუტიზაციისთვის გამოიყენეთ კომბინაცია

შექმენით კომბინაცია, რომელშიც ორივე კავშირი სამიზნედ იქნება მითითებული, რათა მათ შორის დატვირთვა გაანაწილოთ ან მარცხის შემთხვევაში სარეზერვო კავშირზე გადაერთოთ:

```
kiro/kiro-dev → kiro/kiro-pro
```

კომბინაციის კონფიგურაციის შესახებ იხილეთ [FEATURES.md](./FEATURES.md) და მარშრუტიზაციის დოკუმენტაცია.

## საწარმო / IDC მომხმარებლები

AWS IAM Identity Center (IDC) ანგარიშებისთვის გამოიყენეთ **AWS Builder ID / IDC მოწყობილობის კოდის**
ნაკადი: **Dashboard → Providers → Kiro → Device Code**. მოწყობილობის კოდის ნაკადი
ყოველთვის სრულად იზოლირებული იყო. ამ კავშირებისთვის ხელახალი იმპორტი საჭირო არ არის.

საწარმო მომხმარებლებს, რომლებიც AWS-ის არანაგულისხმევ რეგიონში მუშაობენ, შეუძლიათ რეგიონის მითითება
Import Token API-ის მეშვეობით იმპორტისას:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

თუ `region` ველი გამოტოვებულია, მისი ნაგულისხმევი მნიშვნელობაა `us-east-1`.

## API გასაღების იმპორტის ნაკადი

API გასაღებით ავთენტიფიკაცია განკუთვნილია Kiro / AWS CodeWhisperer-ის ხანგრძლივი მოქმედების bearer ავტორიზაციის მონაცემებისთვის. ის
არ იყენებს OAuth განახლებას, ამიტომ თავიდან იცილებს საზიარო OIDC სესიის გაუქმებას.

### მართვის პანელი

1. გახსენით **Dashboard -> Providers -> Kiro**.
2. აირჩიეთ **API Key**.
3. ჩასვით API გასაღები და, სურვილისამებრ, AWS-ის რეგიონი (ნაგულისხმევად `us-east-1`).
4. OmniRoute ამოწმებს გასაღებს და ინახავს კავშირს.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### შიდა კონტრაქტი

API მარშრუტი გასაღებს ამოწმებს `KiroService.validateApiKey()`-ის გამოძახებით, რომელიც
რეგიონის შესაბამის CodeWhisperer/Amazon Q-ის საბოლოო წერტილზე იყენებს `ListAvailableProfiles`-ს
და განსაზღვრავს `profileArn`-ს.

შენახული კავშირი იყენებს:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

შესრულების დროს `KiroExecutor.buildHeaders()` გასაღებს აგზავნის, როგორც
`Authorization: Bearer <key>`, და ამატებს `tokentype: API_KEY`-ს. კვოტისა და პროფილის გამოძახებები
იმავე მარკერს იყენებს, რათა AWS-მა bearer აღიქვას ხანგრძლივი მოქმედების API გასაღებად და არა
OIDC ან სოციალური ქსელის წვდომის ტოკენად.

## OIDC კლიენტის მოქმედების ვადა

AWS SSO OIDC საჯარო კლიენტების მოქმედების ვადა, როგორც წესი, 90 დღის შემდეგ იწურება
(`clientSecretExpiresAt`). დაკვირვებადობისთვის OmniRoute ამ დროის ნიშნულს `providerSpecificData`-ში
ინახავს. თუ კავშირის განახლება დაახლოებით 90 დღის შემდეგ შეწყდება, ახალი OIDC კლიენტის რეგისტრაციის
მისაღებად კავშირი ხელახლა დააიმპორტეთ. მოქმედების ვადის ამოწურვისას ავტომატური ხელახალი რეგისტრაცია
სამომავლო გაუმჯობესებად არის დაგეგმილი.

API გასაღების კავშირებს OIDC კლიენტის მოქმედების ვადა არ აქვთ, რადგან ისინი
AWS SSO OIDC-ის მეშვეობით არ ახლდება.

## პრობლემების მოგვარება

### მეორე ანგარიშიდან სისტემა მუდმივად გამოგყავთ

- შეამოწმეთ ორივე კავშირი **Dashboard → Providers**-ში და დაადასტურეთ, რომ თითოეულის დაუმუშავებელ
  JSON-ში ნაჩვენებია არანულოვანი `clientId` (ხილულია ინფორმაციის ხატულის მეშვეობით). თუ რომელიმე კავშირს
  `clientId` აკლია, ის v3.8.0-მდე იყო იმპორტირებული — ხელახლა დააიმპორტეთ.

### იმპორტი ვერ სრულდება შეცდომით "Token validation failed"

- დარწმუნდით, რომ განახლების ტოკენი იწყება `aorAAAAAG`-ით.
- დარწმუნდით, რომ OmniRoute-ს შეუძლია `https://oidc.us-east-1.amazonaws.com`-თან (ან კონფიგურირებულ
  რეგიონთან) დაკავშირება. თუ კორპორაციული პროქსის მიღმა ხართ, პროვაიდერის დონის პროქსი დააყენეთ
  **Dashboard → Settings → Proxies**-ში.

### API გასაღების იმპორტი ვერ სრულდება

- დაადასტურეთ, რომ გასაღები Kiro / CodeWhisperer-ის API გასაღებია და არა განახლების ტოკენი.
- დაადასტურეთ, რომ AWS-ის რეგიონი გასაღებს/ანგარიშს შეესაბამება. ნაგულისხმევია `us-east-1`.
- გასაღებს უნდა შეეძლოს `ListAvailableProfiles`-ის გამოძახება; წინააღმდეგ შემთხვევაში OmniRoute ვერ
  განსაზღვრავს საჭირო `profileArn`-ს.
