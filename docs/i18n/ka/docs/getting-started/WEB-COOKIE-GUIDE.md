Web Cookie პროვაიდერები OmniRoute-ს საშუალებას აძლევს, API გასაღების ნაცვლად, AI სერვისი თქვენი არსებული ბრაუზერის სესიის მეშვეობით გამოიყენოს. ისინი სასარგებლოა, როდესაც სერვისზე მისი ვებსაიტის მეშვეობით უკვე გაქვთ წვდომა და გსურთ, რომ OmniRoute-მა იგივე ავთენტიფიცირებული სესია გამოიყენოს.

API გასაღების მქონე პროვაიდერებისგან განსხვავებით, Web Cookie პროვაიდერები ავთენტიფიკაციისთვის იყენებენ იმ ავტორიზაციის მონაცემებს, რომლებსაც თქვენი ბრაუზერი ვებსაიტს უგზავნის.

# დაწყებამდე

> **მნიშვნელოვანია:** ავტორიზაციის მონაცემები ყოველთვის დააკოპირეთ **აქტიური ქსელური მოთხოვნიდან** და **არა** თქვენი ბრაუზერის cookie-ების საცავიდან.

ავთენტიფიკაციის მრავალი პრობლემა გამოწვეულია cookie-ების არასწორი ადგილიდან კოპირებით.

## არ დააკოპიროთ Cookie Storage-დან

ბრაუზერების უმეტესობა შენახულ cookie-ებს შემდეგი გზით აჩვენებს:

```
DevTools
→ Application (ან Storage)
→ Cookies
```

მიუხედავად იმისა, რომ ეს cookie-ები შეიძლება სწორად გამოიყურებოდეს, შესაძლოა ისინი იყოს:

- მოძველებული
- არასრული
- არ შეიცავდეს cookie-ებს, რომლებიც მხოლოდ ავთენტიფიცირებული მოთხოვნების დროს იგზავნება

ამ მნიშვნელობების გამოყენებამ შეიძლება გამოიწვიოს ავთენტიფიკაციის შეცდომები, მაშინაც კი, თუ ისინი სწორად გამოიყურება.

## დააკოპირეთ აქტიური მოთხოვნიდან

ამის ნაცვლად, გამოიყენეთ წარმატებული მოთხოვნის cookie-ები:

```
DevTools
→ Network
→ განაახლეთ გვერდი
→ გახსენით ჩატის ან საუბრის მოთხოვნა
→ Request Headers
→ Cookie
```

`Cookie` მოთხოვნის სათაური შეიცავს ზუსტად იმ საავტორიზაციო ინფორმაციას, რომელიც თქვენმა ბრაუზერმა წარმატებით გამოიყენა.

Web Cookie პროვაიდერების უმეტესობისთვის სწორედ ეს მნიშვნელობა უნდა ჩასვათ OmniRoute-ში.

# ზოგადი კონფიგურაცია

Web Cookie პროვაიდერების უმეტესობისთვის კონფიგურაციის პროცესი ერთნაირია.

1. შედით პროვაიდერის ვებსაიტზე.
2. გახსენით ბრაუზერის Developer Tools.
3. გახსენით **Network** ჩანართი.
4. განაახლეთ გვერდი.
5. გახსენით ავთენტიფიცირებული ჩატის ან საუბრის მოთხოვნა.
6. დააკოპირეთ საჭირო საავტორიზაციო მონაცემები.
7. გახსენით OmniRoute.
8. გადადით **Providers → Add Provider**-ზე.
9. აირჩიეთ თქვენი Web Cookie პროვაიდერი.
10. ჩასვით საავტორიზაციო მონაცემები.
11. დააწკაპუნეთ **Test Connection**-ზე.
12. შეინახეთ პროვაიდერი.

ზუსტად რომელი საავტორიზაციო მონაცემებია საჭირო, დამოკიდებულია პროვაიდერზე.

# რისი გაკეთება შეუძლიათ და არ შეუძლიათ Web Cookie პროვაიდერებს

Web Cookie პროვაიდერები ხელახლა იყენებენ ვებსაიტის ჩატის ინტერფეისს. ისინი **არ** უზრუნველყოფენ იმავე შესაძლებლობებს, რასაც ოფიციალური API-ები.

## მხარდაჭერილია

- ავთენტიფიკაცია თქვენი არსებული ბრაუზერის სესიის გამოყენებით
- თქვენს ანგარიშზე ხელმისაწვდომ მოდელებზე წვდომა
- ჩატის პასუხების ნაკადურ რეჟიმში მიღება
- API გასაღები საჭირო არ არის

## მხარდაჭერილი არ არის

- ფუნქციების გამოძახება
- ხელსაწყოების გამოძახება
- ფაილების ავტომატური რედაქტირება
- აგენტური IDE სამუშაო პროცესები
- მხოლოდ API-სთვის განკუთვნილი ფუნქციები

ეს მოსალოდნელი ქცევაა და **არ** წარმოადგენს შეცდომას.

თუ გჭირდებათ ხელსაწყოების შესრულება, ფაილების ავტომატური რედაქტირება ან სხვა აგენტური სამუშაო პროცესები, Web Cookie პროვაიდერის ნაცვლად გამოიყენეთ **API გასაღების მქონე პროვაიდერი**.

# ვალიდაციის შეზღუდვა

წარმატებული **Test Connection** ან cookie-ის ვალიდაცია მხოლოდ იმას ამოწმებს, რომ მოწოდებული საავტორიზაციო მონაცემები მოსალოდნელ ფორმატს შეესაბამება.

Issue #7857-ის გადაწყვეტამდე წარმატებული ვალიდაცია **არ იძლევა გარანტიას**, რომ პროვაიდერი ავთენტიფიკაციას წარმატებით გაივლის.

თუ ავთენტიფიკაცია კვლავ ვერ ხერხდება, შეამოწმეთ, რომ საავტორიზაციო მონაცემები დააკოპირეთ აქტიური ქსელური მოთხოვნიდან და არა ბრაუზერის cookie-ების საცავიდან.

# პროვაიდერის მაგალითი

# საუკეთესო პრაქტიკები

- საავტორიზაციო მონაცემები დააკოპირეთ ახალი ავთენტიფიცირებული მოთხოვნიდან.
- მოერიდეთ ძველი cookie-ების ხელახლა გამოყენებას.
- Web Cookie პროვაიდერების გამოყენებისას ბრაუზერის სესია აქტიური შეინარჩუნეთ.
- დაკოპირებული cookie-ები კონფიდენციალურ საავტორიზაციო მონაცემებად მიიჩნიეთ.
- როდესაც გჭირდებათ ფუნქციების გამოძახება ან აგენტური სამუშაო პროცესები, გამოიყენეთ API გასაღების მქონე პროვაიდერები.
