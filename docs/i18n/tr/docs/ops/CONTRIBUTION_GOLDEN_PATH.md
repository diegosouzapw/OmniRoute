Bir pull request için güvenilir en küçük geliştirme döngüsünü seçmek üzere bu kılavuzu kullanın. Bu kılavuz,
aşağıda bağlantıları verilen alana özgü mimari ve güvenlik belgelerinin yerini almaz; yaygın değişiklik
türlerinin her birini ilgili sözleşmelere, odaklı kontrollere ve CI kapsamına bağlar.

## Her değişikliğin izlediği yol

1. **Düzenlemeye başlamadan önce temel dalı seçin.** Etkin olan en yüksek `release/v*` dalını bulun ve
   bu dalın en son commit'inden yeni bir dal oluşturun. `main` dalını değil, bu dalı hedefleyin. Bir sürüm dondurma süreci etkinse dondurulmuş
   dalı hedeflemeyin; [Dallanma ve Sürüm Modeli](BRANCHING_MODEL.md) belgesinde açıklanan
   bir sonraki etkin döngüyü kullanın.
2. **Sözleşmeleri belirtin.** Değişikliğin etkilediği her kataloğu, şemayı, oluşturulmuş yapıyı, herkese açık API'yi veya kullanıcı
   arayüzünü belirleyin. Aşağıdaki tablo, gerekli asgari başlangıç kümesini sunar.
3. **Odaklı testler yazın veya mevcut testleri güncelleyin.** `src/`, `open-sse/`, `electron/` veya
   `bin/` altındaki üretim değişiklikleri, aynı PR'da otomatik bir test gerektirir. Davranışı
   doğrulayan en küçük test dosyalarını, ardından listelenen odaklı kontrolleri çalıştırın.
4. **Geniş matrisi CI'ın çalıştırmasına izin verin.** Eksiksiz birim testi parçaları, Vitest, kapsam eşiği ve
   üretim derlemesi PR üzerinde çalıştırılır. Geniş kapsamlı bir paketi yerel olarak yalnızca odaklı bir hata
   daha geniş bir etkiye işaret ettiğinde veya değişiklik birkaç alt sistemi kapsadığında çalıştırın.
5. **İncelemeden önce uzlaştırın.** Etkin temel dalı çekin, bu daldaki yeni commit'leri ve dalınızın bu dala göre
   farkını inceleyin, ardından katkıda bulunan iş akışına uygun olarak temel dalı rebase veya merge edin. Oluşturulmuş dosya
   ve katalog çakışmalarını kaynaklarından giderin, bunları yeniden oluşturun, odaklı döngüyü tekrar çalıştırın ve
   PR'ın hâlâ etkin sürüm dalını hedeflediğini doğrulayın.
6. **Kanıtları kaydedin.** PR şablonunda çalıştırılan komutları, eklenen veya değiştirilen tüm test dosyalarını,
   geçişleri ya da özellik bayraklarını ve hâlâ bekleyen, yalnızca CI'da gerçekleştirilecek doğrulamaları listeleyin.

## Değişiklik türüne göre önerilen yollar

Aşağıdaki komutlar asgari odaklı kontrollerdir; değiştirdiğiniz davranışı doğrudan kapsayan bir testi
atlama izni vermez.

### Sağlayıcı

**Sözleşmeler**

- `src/shared/constants/providers/` içindeki sağlayıcı tanımı ve bunun
  `src/shared/constants/providers.ts` içindeki bileşimi.
- `open-sse/config/providerRegistry.ts` veya bundan ayrıştırılmış kayıt defteri dosyalarındaki modeller ve yetenekler.
- Uygun olduğunda yürütücü/çevirici seçimi, OAuth veya API anahtarı yapılandırması, pano varlıkları ve oluşturulmuş
  sağlayıcı referansı.
- Herkese açık kimlik bilgileri `resolvePublicCred()` kullanmalıdır; hata yanıtları ortak temizlenmiş
  hata yardımcılarını kullanmalıdır. `docs/security/PUBLIC_CREDS.md` (git'te bulunur; `/docs` içine derlenmez) ve
  [Hata Temizleme](../security/ERROR_SANITIZATION.md) belgelerine bakın.

**Odaklı döngü**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # katalog değiştiğinde; oluşturulan farkı commit edin
npm run lint
```

Etkilenen her istek ailesini de test edin: sohbet, Responses, görseller, yerleştirmeler, ses veya video.
Oluşturulmuş katalog ve golden farklarını sözleşme değişiklikleri olarak inceleyin; bunları sorgulamadan kabul etmeyin.

### Yönlendirme

**Sözleşmeler**

- `src/shared/constants/routingStrategies.ts` içindeki herkese açık strateji değerleri ve kullanıcı arayüzü meta verileri.
- `open-sse/services/combo.ts` ve `open-sse/services/combo/` altındaki dağıtım ve sıralama.
- Combo şemaları, kalıcılık, dayanıklılık durumu, model yetenekleri ve API/kullanıcı arayüzü denetimleri.
- Davranış değiştiğinde [Auto-Combo Motoru](../routing/AUTO-COMBO.md) ve dayanıklılık belgeleri.

**Odaklı döngü**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strateji veya dağıtım değişiklikleri
npm run check:known-symbols      # strateji kaydı değişiklikleri
npm run lint
```

Yerel olarak deterministik ve sahte üst sistem kullanan testler kullanın. Canlı combo smoke testleri kimlik bilgileri gerektirir ve
manuel olarak çalıştırılır; CI testlerinin yerine geçmez.

### UI / UX

**Sözleşmeler**

- `src/app/` ve `src/shared/components/` altındaki Next.js rota/sayfa ve ortak bileşen sınırları.
- API yanıt biçimleri, yükleme/boş/hata durumları, klavye ve ekran okuyucu davranışı,
  duyarlı düzen, tema ve yerel ayar genişletmesi.
- `src/i18n/messages/en.json` içindeki İngilizce kullanıcı arayüzü kaynak dizeleri; kullanıcıya yönelik yeni metinleri doğrudan kod içine yazmayın.

**Odaklı döngü**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Etkileşim veya görsel değişiklikler için uygulamayı çalıştırın ve hem dar hem de geniş görünüm alanlarını kontrol edin. CI,
üretim derlemesini ve daha geniş test paketlerini çalıştırır; görsel davranış için yine de değişikliğe uygun odaklı bir bileşen testi,
Playwright testi veya belgelenmiş manuel kontrol gerekir.

### i18n

**Sözleşmeler**

- `src/i18n/messages/en.json` kullanıcı arayüzü kaynağıdır; `config/i18n.json` yerel ayar kaynağıdır.
- CLI katalogları ayrı olarak `bin/cli/locales/` altında bulunur.
- ICU yer tutucularını ve etiketlerini birebir koruyun. Ürün/sağlayıcı/model adlarını,
  protokol ve başlık adlarını, komutları, kod/JSON tanımlayıcılarını, URL'leri, ortam değişkenlerini veya
  `OmniRoute`, `OAuth`, `MCP` ve `A2A` gibi korunan terimleri çevirmeyin. Geçerli kaynak listesi
  `scripts/i18n/glossary/protected-terms.json` dosyasındadır.

**Odaklı döngü**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI dizeleri/katalogları değiştiğinde
npm run lint
```

Bu, mevcut sistem için bir kılavuzdur; sistemin araçlarını veya anahtar modelini genişletme daveti değildir.
Yeni sistem tasarlanırken i18n yamalarını yalnızca gerekli değişikliklerle sınırlı tutun. Görev açıkça oluşturulmuş çeviriler
gerektirmediği ve ortaya çıkan farkı incelemediğiniz sürece harici hizmetleri çağıran çeviri
komutlarını çalıştırmayın.

### CLI

**Sözleşmeler**

- `bin/cli/` içindeki genel kullanıma açık komutlar ve bayraklar, oluşturulan API komutları, çıkış kodları, stdout/stderr ve
  JSON çıktı biçimleri, yapılandırma/ortam davranışı ve paketlenmiş dosyalar.
- CLI'da kullanıcıya gösterilen dizeler, CLI i18n katmanını kullanmalı ve `en`/`pt-BR` katalogları uyumlu tutulmalıdır.
- Desteklenen çalışma zamanı olarak Node'u ve yayımlanmış ikili sözleşmesini koruyun.

**Odaklı döngü**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # oluşturulan/paketlenen CLI değişiklikleri
npm run check:pack-policy     # paket yüzeyi değişiklikleri
npm run lint
```

Davranış ayrıştırmaya, dosyalara veya çıkış durumuna bağlı olduğunda tam komutu geçici bir veri dizininde kullanın. CI, daha kapsamlı paket yapıtı ve ekosistem kontrollerini gerçekleştirir.

### Veritabanı

**Sözleşmeler**

- `src/lib/db/` altındaki etki alanı modülleri; belirli modülleri doğrudan içe aktarın (eski `localDb.ts` yeniden dışa aktarma katmanı kaldırıldı).
- `src/lib/db/migrations/` altındaki numaralandırılmış, birden fazla kez güvenle çalıştırılabilen SQL geçişleri, işlem güvenliği, yükseltme
  davranışı, indeksler ve şemadan etkilenen her çağıran.
- Rotalar ve işleyiciler hiçbir zaman doğrudan ham SQL sorguları çalıştırmaz.

**Odaklı döngü**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Bir geçiş eklerken hem yeni bir veritabanını hem de önceki şemadan yükseltmeyi test edin. Veritabanı testleri, temizleme sırasında tanıtıcıları kapatmalı ve `resetDbInstance()` çağrısı yapmalıdır. `npm run test:bun:db` komutunu yalnızca en iyi çaba esasına dayalı Bun bağdaştırıcı yolu değiştiğinde çalıştırın; Node belirleyici olmaya devam eder.

### Derleme / dağıtım

**Sözleşmeler**

- Kök ve çalışma alanı bildirimleri/kilit dosyası, `scripts/build/`, Next.js bağımsız derleme düzeni, `dist/`
  paket içerikleri, Electron platform meta verileri, CI iş akışları ve dağıtım gözcüleri.
- Desteklenen Node aralıkları ve `CLAUDE.md` içindeki izin verilen Bun kullanımı bozulmadan kalmalıdır.
- Derleme yapıtları izlenmeden kalır; bağımlılık, lisans, iş akışı ve paket ilkeleri geçerlidir.

**Odaklı döngü**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # bağımlılık veya kilit dosyası değişiklikleri
npm run check:pack-policy      # yayımlanan paket yüzeyi değişiklikleri
npm run lint
```

`npm run build` komutunu yerel olarak yalnızca değişiklik derlemeyi, bağımsız derleme düzenini, varlıkları veya çalışma zamanı paketlemesini etkilediğinde kullanın. `npm run build:release` komutunu yalnızca sürüm/dağıtım doğrulaması için kullanın. CI derlemesi, platformlar arası nihai göstergedir; platforma özgü Electron değişiklikleri, eşleşen odaklı derleme veya temel çalışma kanıtını gerektirir.

## Yerel döngü ile CI karşılaştırması

| Her yama için yerel olarak çalıştırılır                                         | CI geniş kapsamlı sinyal sağlar                                                    |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Yukarıdaki doğrudan davranış testleri ve kategori kapıları                      | Parçalanmış tam birim testi paketi ve seri testler                                 |
| `npm run lint`                                                                  | Vitest test paketleri ve kapsam/kalite eşikleri                                    |
| Yalnızca etkilenen sözleşme gerektiriyorsa tür denetimi veya derleme            | Üretim derlemesi, güvenlik, dokümantasyon, bağımlılık ve PR politikası kapıları    |
| Yalnızca otomasyon davranışı doğrulayamıyorsa manuel etkileşim/canlı kontroller | İş akışı tarafından yapılandırılan işler arası entegrasyon ve platform kontrolleri |

Başarılı bir odaklı döngü, değiştirilen sözleşme hakkında kanıt sağlar; ilgisiz CI kontrollerinin
başarılı olacağının kanıtı değildir. Buna karşılık, her yerel düzenlemeyi deponun tam matrisini beklemek zorunda bırakmayın.

## Uzlaştırma kontrol listesi

İnceleme talep etmeden önce:

- PR tabanının hâlâ en yüksek etkin `release/v*` dalı olduğunu doğrulayın.
- Bu tabanı getirin ve dalınızı oluşturduğunuzdan beri eklenen commit'leri inceleyin.
- Yanlışlıkla oluşan veya üretilmiş gereksiz değişiklikler için `git diff <active-base>...HEAD` çıktısını inceleyin.
- Katalog ve üretilmiş belge çakışmalarını, kaynağı güncelleyip çıktıyı yeniden üreterek çözün.
- Uzlaştırmadan sonra PR açıklamasında listelenen tüm odaklı testleri/kapıları yeniden çalıştırın.
- Değişen bir tabana uyum sağlamak amacıyla iddiaları asla zayıflatmayın veya gerekli testleri kaldırmayın.

Sürüm dondurma ve yeniden hedefleme kuralları için
[Dallanma ve Sürüm Modeli](BRANCHING_MODEL.md) belgesini kullanın. Eksiksiz CI envanteri için
[Kalite Kapıları Referansı](../architecture/QUALITY_GATES.md) belgesini kullanın.
