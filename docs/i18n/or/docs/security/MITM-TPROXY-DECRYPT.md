TPROXY ସ୍ୱଚ୍ଛ ଡିକ୍ରିପ୍ସନ୍ ହେଉଛି OmniRouteର
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM ଷ୍ଟାକ୍ ପାଇଁ **5ମ କ୍ୟାପ୍ଚର୍ ମୋଡ୍**। ଏହା Linuxରେ kernel TPROXY + ପଲିସି ରାଉଟିଂ ବ୍ୟବହାର କରି
ସ୍ଥାନୀୟ ଆଉଟବାଉଣ୍ଡ HTTPS ଟ୍ରାଫିକ୍କୁ ଇଣ୍ଟରସେପ୍ଟ ଏବଂ **ଡିକ୍ରିପ୍ଟ** କରେ — `/etc/hosts`କୁ
ସ୍ପୁଫ୍ **ନକରି** ଏବଂ ସମଗ୍ର OSର ସିଷ୍ଟମ୍-ପ୍ରକ୍ସି ସେଟିଂସ୍କୁ ପରିବର୍ତ୍ତନ **ନକରି**।
ଏହା ହେଡ୍ଲେସ୍ ପରିବେଶ ପାଇଁ ଉପଯୋଗୀ (ସଫା କରିବା ପାଇଁ କୌଣସି DNS ସମ୍ପାଦନା ନାହିଁ) ଏବଂ
ରିବୁଟ୍ ହେଲେ ଫାୟାରୱାଲ୍ ନିୟମଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବେ ଫ୍ଲସ୍ ହୋଇଯାଏ।

ଅନ୍ୟ କ୍ୟାପ୍ଚର୍ ମୋଡ୍ଗୁଡ଼ିକ ତୁଳନାରେ, TPROXY ପାଇଁ ପ୍ରତ୍ୟେକ ହୋଷ୍ଟରେ ଅଲଗା ସେଟଅପ୍ ଆବଶ୍ୟକ ନୁହେଁ: ଏହା ଏକ ଲକ୍ଷ୍ୟ ପୋର୍ଟରେ **ଯେକୌଣସି** ଗନ୍ତବ୍ୟ ହୋଷ୍ଟକୁ ସ୍ୱଚ୍ଛ ଭାବେ
ଇଣ୍ଟରସେପ୍ଟ କରେ, ପ୍ରତ୍ୟେକ SNI ହୋଷ୍ଟନେମ୍ ପାଇଁ ତତ୍କ୍ଷଣାତ୍ ଜାରି କରୁଥିବା ଏକ ଲିଫ୍ ସାର୍ଟିଫିକେଟ୍ ସହିତ TLSକୁ
ସମାପ୍ତ କରେ, ଡିକ୍ରିପ୍ଟ ହୋଇଥିବା ଆଦାନପ୍ରଦାନକୁ କ୍ୟାପ୍ଚର୍ କରେ, ଏବଂ ଅନୁରୋଧକୁ ମୂଳ ଗନ୍ତବ୍ୟ ପାଇଁ ପୁନଃ ଏନ୍କ୍ରିପ୍ଟ କରେ।

> **କେବଳ Linux, କେବଳ root, ଇଚ୍ଛାଧୀନ।** ଏହି ମୋଡ୍ ପାଇଁ Linux, ଏକ C ଟୁଲ୍ଚେନ୍ ସହିତ
> ବିଲ୍ଡ୍ ହୋଇଥିବା ନେଟିଭ୍ ଆଡଅନ୍, ଏବଂ **CAP_NET_ADMIN** କ୍ଷମତା (ସାଧାରଣତଃ root) ଆବଶ୍ୟକ। ଏହା
> କେବଳ-loopback AgentBridge API ଦ୍ୱାରା ସୀମିତ ଏବଂ ଡିଫଲ୍ଟ ଭାବେ ଅକ୍ଷମ। ଯେକୌଣସି
> ହୋଷ୍ଟକୁ ସାଇନ୍ କରିପାରୁଥିବା ଏକ ବିଶ୍ୱସ୍ତ MITM CA ଏକ ଶକ୍ତିଶାଳୀ କ୍ଷମତା — [§6 ସୁରକ୍ଷା](#6-security) ଦେଖନ୍ତୁ।

**ଉତ୍ସ:** `src/mitm/tproxy/`

## §1 ଏହା କ’ଣ ଏବଂ କେବେ ଏହାକୁ ବ୍ୟବହାର କରିବେ

ଅନ୍ୟ ଚାରିଟି କ୍ୟାପ୍ଚର୍ ମୋଡ୍ର ପ୍ରତ୍ୟେକର ଗୋଟିଏ ସୀମାବଦ୍ଧତା ଅଛି:

| ମୋଡ୍                   | ଟ୍ରାଫିକ୍ କିପରି ପରିଚାଳିତ ହୁଏ                        | ସୀମାବଦ୍ଧତା                                                  |
| ---------------------- | -------------------------------------------------- | ----------------------------------------------------------- |
| AgentBridge            | ଏକ ନିର୍ଦ୍ଧାରିତ ହୋଷ୍ଟ ସେଟ୍ର `/etc/hosts` DNS ସ୍ପୁଫ୍ | କେବଳ ପଞ୍ଜୀକୃତ IDE-agent ହୋଷ୍ଟଗୁଡ଼ିକ                         |
| କଷ୍ଟମ୍ ହୋଷ୍ଟଗୁଡ଼ିକ     | ପ୍ରତ୍ୟେକ ହୋଷ୍ଟ ପାଇଁ `/etc/hosts` DNS ସ୍ପୁଫ୍        | ପ୍ରତ୍ୟେକ ହୋଷ୍ଟ ପାଇଁ ଗୋଟିଏ ଏଣ୍ଟ୍ରି; hosts ସମ୍ପାଦନା ପାଇଁ sudo |
| HTTP_PROXY             | `HTTP_PROXY`/`HTTPS_PROXY` env                     | କେବଳ env varକୁ ସମ୍ମାନ କରୁଥିବା ଆପ୍ଗୁଡ଼ିକ                     |
| ସିଷ୍ଟମ୍-ବ୍ୟାପୀ ପ୍ରକ୍ସି | OS ପ୍ରକ୍ସି ସେଟିଂସ୍                                 | ଗ୍ଲୋବାଲ୍ ଅବସ୍ଥା ପରିବର୍ତ୍ତନ କରେ; ପ୍ରତ୍ୟାବର୍ତ୍ତନ ଆବଶ୍ୟକ       |

TPROXY ସ୍ୱଚ୍ଛ ଡିକ୍ରିପ୍ସନ୍ ଏହା ପରିବର୍ତ୍ତେ **kernel** ସ୍ତରରେ ଟ୍ରାଫିକ୍କୁ ପରିଚାଳନା କରେ। ଏହା
`mangle OUTPUT` ଚେନ୍ରେ ଏକ ଲକ୍ଷ୍ୟ ପୋର୍ଟକୁ (ଡିଫଲ୍ଟ `443`) ଯାଉଥିବା ନୂଆ ସ୍ଥାନୀୟ ଆଉଟବାଉଣ୍ଡ TCP ସଂଯୋଗଗୁଡ଼ିକୁ
ଚିହ୍ନିତ କରେ, ଏକ `ip rule` ଚିହ୍ନିତ ପ୍ୟାକେଟ୍ଗୁଡ଼ିକୁ ସ୍ଥାନୀୟ ଡେଲିଭରି ଆଡ଼କୁ ପୁନଃ ରାଉଟ୍ କରେ,
ଏବଂ ପୁନଃ ପ୍ରବେଶ ସମୟରେ `mangle PREROUTING` `TPROXY` ଟାର୍ଗେଟ୍ ସେଗୁଡ଼ିକୁ ଏକ
**IP_TRANSPARENT** ଲିସନର୍କୁ ହସ୍ତାନ୍ତର କରେ — ଯାହା ପରେ TLSକୁ ସମାପ୍ତ କରି ପ୍ଲେନ୍ଟେକ୍ସ୍ଟ କ୍ୟାପ୍ଚର୍ କରେ।

ଏପରି ଏକ ପ୍ରୋସେସ୍ରୁ ଟ୍ରାଫିକ୍ କ୍ୟାପ୍ଚର୍ ଏବଂ ଡିକ୍ରିପ୍ଟ କରିବାକୁ ଚାହୁଁଥିଲେ ଏହାକୁ ବ୍ୟବହାର କରନ୍ତୁ, ଯାହା:

- AgentBridge ପଞ୍ଜୀକୃତ କରିନଥିବା ଏକ ହୋଷ୍ଟ ସହିତ ଯୋଗାଯୋଗ କରେ, ଏବଂ
- `HTTP_PROXY`କୁ ସମ୍ମାନ କରେ ନାହିଁ, ଏବଂ
- ଯାହାକୁ ଆପଣ ସିଷ୍ଟମ୍-ବ୍ୟାପୀ ପ୍ରକ୍ସି ପରିବର୍ତ୍ତନ ଦ୍ୱାରା ବାଧା ଦେବାକୁ ଚାହୁଁନାହାନ୍ତି।

ଇଣ୍ଟରସେପ୍ସନ୍ kernelରେ ଘଟୁଥିବାରୁ, ଉତ୍ପତ୍ତିକାରୀ ପ୍ରୋସେସ୍କୁ **କୌଣସି
କନଫିଗରେସନ୍ ପରିବର୍ତ୍ତନ** ଦରକାର ନାହିଁ — କିନ୍ତୁ ପ୍ରୋସେସ୍ଟି OmniRoute ଇନ୍ଷ୍ଟଲ୍ କରୁଥିବା ଡାଇନାମିକ୍ CAକୁ
ବିଶ୍ୱାସ କରିବା ଆବଶ୍ୟକ ([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) ଦେଖନ୍ତୁ)।

## §2 ଆବଶ୍ୟକତାଗୁଡ଼ିକ

| ଆବଶ୍ୟକତା                | ବିବରଣୀ                                                                                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**                  | କେବଳ Linux — **IP_TRANSPARENT** ହେଉଛି କେବଳ Linux ପାଇଁ ଉପଲବ୍ଧ socket ବିକଳ୍ପ। ଅନ୍ୟ ପ୍ରତ୍ୟେକ ପ୍ଲାଟଫର୍ମରେ loader "ଅନୁପଲବ୍ଧ" ଫେରାଏ।                                          |
| **ବିଶେଷାଧିକାର**         | transparent socket ସୃଷ୍ଟି କରିବା ଏବଂ `iptables`/`ip` ନିୟମ ପ୍ରୟୋଗ କରିବା ପାଇଁ **CAP_NET_ADMIN** capability — ବ୍ୟବହାରିକ ଭାବରେ, root ଭାବେ ଚଲାନ୍ତୁ।                           |
| **Native addon**        | ଏକ ଛୋଟ N-API addon (`src/mitm/tproxy/native/transparent.c`) build କରାଯିବା କିମ୍ବା prebuild ଭାବେ ପ୍ରଦାନ କରାଯିବା ଆବଶ୍ୟକ। [§3](#3-the-native-ip_transparent-addon) ଦେଖନ୍ତୁ। |
| **Kernel moduleଗୁଡ଼ିକ** | `TPROXY`, `mangle`, ଏବଂ `mark` match ସମର୍ଥନ ସହିତ `iptables` (kernel 6.8.0 ବିପକ୍ଷରେ ବୈଧତା ଯାଞ୍ଚ କରାଯାଇଛି)।                                                               |

**ସୁଚାରୁ ଅବନତି:** ଯଦି କୌଣସି ଆବଶ୍ୟକତା ଅନୁପସ୍ଥିତ ଥାଏ (non-Linux, toolchain ନାହିଁ,
addon build ହୋଇନାହିଁ), ତେବେ addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
ବ୍ୟତିକ୍ରମ ଉତ୍ଥାପନ କରିବା ପରିବର୍ତ୍ତେ `null` ଫେରାଏ। ଏହାପରେ capture-mode ସ୍ଥିତି
`available: false` ରିପୋର୍ଟ କରେ, dashboard toggleଟି
"TPROXY decrypt ପାଇଁ Linux + root + native addon ଆବଶ୍ୟକ" tooltip ସହିତ **ଅକ୍ଷମ** ହୁଏ,
ଏବଂ OmniRouteର ଅବଶିଷ୍ଟ ଅଂଶ କାମ କରିବା ଜାରି ରଖେ।

## §3 Native IP_TRANSPARENT addon

Nodeର `net` module, `bind()` ପୂର୍ବରୁ `setsockopt(IP_TRANSPARENT)` କରିପାରେ ନାହିଁ, ଯାହା
TPROXY ପାଇଁ ଆବଶ୍ୟକ (ଅନ୍ୟଥା kernel redirect ହୋଇଥିବା packetଗୁଡ଼ିକୁ ଛାଡ଼ିଦିଏ)। addonଟି
(`src/mitm/tproxy/native/transparent.c`, `binding.gyp` ମାଧ୍ୟମରେ build ହୋଇଥାଏ) ହେଉଛି ଏକ ଛୋଟ N-API
module, ଯାହା `transparentSocket.ts` ମାଧ୍ୟମରେ ବ୍ୟବହୃତ ତିନୋଟି function ପ୍ରଦାନ କରେ:

| Addon function                        | Socket କାର୍ଯ୍ୟ                                                                           | ଯେଉଁଥିପାଇଁ ବ୍ୟବହୃତ                                                                  |
| ------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, raw fd ଫେରାଏ | transparent capture listener (Node `server.listen({ fd })` ମାଧ୍ୟମରେ fdକୁ ଗ୍ରହଣ କରେ) |
| `setSocketMark(fd, mark)`             | ଏକ ବିଦ୍ୟମାନ fdରେ `setsockopt` **SO_MARK**                                                | anti-loop (proxyର ନିଜସ୍ୱ socketଗୁଡ଼ିକୁ mark କରେ)                                    |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()`ର **ପୂର୍ବରୁ** `socket()` + **SO_MARK**, fd ଫେରାଏ                 | ପୁନଃ-encrypt ହୋଇଥିବା upstream forward (SYN markକୁ ବହନ କରେ)                          |

ମୂଳ destinationଟି `socket.localAddress`/`localPort`ରୁ ପଢ଼ାଯାଏ — TPROXY
ଏହାକୁ ସଂରକ୍ଷିତ ରଖେ, ତେଣୁ **SO_ORIGINAL_DST**/NAT lookupର ଆବଶ୍ୟକତା ନାହିଁ।

### Addon build କରିବା

```bash
npm run build:native:tproxy      # src/mitm/tproxy/nativeକୁ cd କରି node-gyp rebuild ଚଲାନ୍ତୁ
                                 # -> native/build/Release/transparent.node
```

- `npm run build` ସମୟରେ, `scripts/build/build-tproxy-native.mjs`, `node-gyp
rebuild` ଚଲାଏ। ଏହା **କେବଳ Linux ପାଇଁ ଏବଂ non-fatal** — toolchain ନଥିଲେ କେବଳ
  capture modeଟି ଅନୁପଲବ୍ଧ ରହେ।
- `assembleStandalone.mjs`, `build/Release/transparent.node`କୁ
  standalone bundle ମଧ୍ୟକୁ copy କରେ; `transparentSocket.ts` ଏହାକୁ module-relative ଏବଂ
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) ଉଭୟ ଭାବେ resolve କରେ।
- `build/` ଏବଂ `prebuilds/` git-ignored — binaryଟି **build ହୁଏ, କେବେବି
  commit ହୁଏ ନାହିଁ**।

Loaderଟି ଅଗ୍ରାଧିକାର କ୍ରମରେ ନିମ୍ନଗୁଡ଼ିକୁ probe କରେ:
`native/build/Release/transparent.node`, ତାପରେ `native/prebuilds/transparent.node`
(ଉଭୟ module-relative ଏବଂ `<cwd>/src/mitm/tproxy/` ଅଧୀନରେ)।

## §4 ପ୍ରତି-SNI ଡାଇନାମିକ୍ CA ଏବଂ ଟ୍ରଷ୍ଟ-ଷ୍ଟୋର୍ ଇନଷ୍ଟଲର୍

> **#6684 ଅପଡେଟ୍:** AgentBridge ଷ୍ଟାଟିକ୍ ସର୍ଭର୍ (`src/mitm/server.cjs`) ବର୍ତ୍ତମାନ
> ଗୋଟିଏ ମାତ୍ର ଷ୍ଟାଟିକ୍ ସ୍ୱ-ସ୍ୱାକ୍ଷରିତ ଲିଫ୍ ପରିବର୍ତ୍ତେ ଏହି ସମାନ CA/ଲିଫ୍ ଆର୍କିଟେକ୍ଚର୍
> ପ୍ୟାଟର୍ନ୍ ଅଂଶୀଦାର କରେ। ଏହା ଏକ **ସ୍ୱତନ୍ତ୍ର** CA ଇନଷ୍ଟାନ୍ସ୍
> (`src/mitm/cert/rootCa.ts`, `<DATA_DIR>/mitm/ca.key`/`ca.crt`ରେ ସଂରକ୍ଷିତ)
> ବ୍ୟବହାର କରେ ଏବଂ ପୂର୍ବରୁ ଥିବା `omniroute-mitm.crt` ଟ୍ରଷ୍ଟ-ଷ୍ଟୋର୍ ସ୍ଲଟ୍ରେ
> ଇନଷ୍ଟଲ୍ କରେ (ସେଠାରେ ପୁରୁଣା ଏକକ ଲିଫ୍କୁ ପ୍ରତିସ୍ଥାପିତ କରି — ଦ୍ୱୈତ-ଟ୍ରଷ୍ଟ
> କ୍ଲିନଅପ୍ ଆବଶ୍ୟକ ନୁହେଁ), ଏବଂ ଏହାକୁ ନିମ୍ନରେ ଥିବା TPROXYର ନିଜସ୍ୱ
> `omniroute-tproxy-ca.crt` ସ୍ଲଟ୍ଠାରୁ ସମ୍ପୂର୍ଣ୍ଣ ପୃଥକ୍ ରଖାଯାଏ।
> ନୂତନ AgentBridge ଇନଷ୍ଟଲେସନ୍ଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବେ CA ମଡେଲ୍ ପାଆନ୍ତି;
> ପୁରୁଣା ଷ୍ଟାଟିକ୍ ଲିଫ୍କୁ ପୂର୍ବରୁ ଭରସା କରୁଥିବା ଏକ ଇନଷ୍ଟଲେସନ୍, ଅପରେଟର୍
> `MITM_ROOT_CA_ENABLED=true` ମାଧ୍ୟମରେ ବିକଳ୍ପଟି ସକ୍ରିୟ ନକରିବା ପର୍ଯ୍ୟନ୍ତ
> ତାହାକୁ ବ୍ୟବହାର କରିଚାଲେ (ଦେଖନ୍ତୁ `src/mitm/cert/migration.ts`) — **ଯେକୌଣସି**
> ହୋଷ୍ଟ୍ ପାଇଁ ଏକ ଲିଫ୍ ସ୍ୱାକ୍ଷର କରିପାରୁଥିବା ଏକ ବିଶ୍ୱସ୍ତ MITM CA ପୁରୁଣା
> ସ୍ଥିର-SAN ଲିଫ୍ଠାରୁ ବାସ୍ତବରେ ଅଧିକ ଶକ୍ତିଶାଳୀ, ତେଣୁ ପୂର୍ବରୁ ବିଶ୍ୱସ୍ତ
> ଇନଷ୍ଟଲେସନ୍ ପାଇଁ ଏହି ପରିବର୍ତ୍ତନ କେବେବି ନିରବରେ ହୁଏ ନାହିଁ।

ଐତିହାସିକ ଭାବେ, ଷ୍ଟାଟିକ୍ AgentBridge MITM ସାର୍ଟିଫିକେଟ୍ କେବଳ ଏଥିପାଇଁ କାମ
କରୁଥିଲା ଯେ AgentBridge ଏକ **ସ୍ଥିର** ହୋଷ୍ଟ୍ ସେଟ୍ର DNS ସ୍ପୁଫ୍ କରେ
(ବର୍ତ୍ତମାନ ନିମ୍ନସ୍ଥ ମଡେଲ୍ ସହିତ ଏକୀକୃତ)। TPROXY **ଇଚ୍ଛାଧୀନ** ହୋଷ୍ଟ୍ଗୁଡ଼ିକୁ
ଇଣ୍ଟରସେପ୍ଟ୍ କରେ, ତେଣୁ ଏହାର ଲିସନର୍କୁ କ୍ଲାଏଣ୍ଟ୍ ଅନୁରୋଧ କରୁଥିବା
ଯେକୌଣସି SNI ପାଇଁ ଏକ ବୈଧ ଲିଫ୍ ପ୍ରଦାନ କରିବାକୁ ହେବ — କେବଳ 4ଟି
antigravity ହୋଷ୍ଟ୍ ପରିବର୍ତ୍ତେ ସମ୍ପୂର୍ଣ୍ଣ `MITM_TOOL_HOSTS` ସେଟ୍ (9ଟି ଟୁଲ୍
ଏଣ୍ଟ୍ରି) ପାଇଁ AgentBridgeର ବର୍ତ୍ତମାନ ଯେଉଁ ସମାନ ଆବଶ୍ୟକତା ରହିଛି।

### ଡାଇନାମିକ୍ CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore`, `selfsigned` ଡିପେଣ୍ଡେନ୍ସି ଉପରେ ନିର୍ମିତ ଏକ ସ୍ଥାନୀୟ CA ଚଲାଏ, ଯାହା:

- `generateMitmCa()` ମାଧ୍ୟମରେ ଏକ ଦୀର୍ଘକାଳୀନ CA ସୃଷ୍ଟି କରେ (CN `"OmniRoute MITM CA"`,
  10 ବର୍ଷର ବୈଧତା, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-bit RSA / SHA-256)।
- `issueLeafCert()` ମାଧ୍ୟମରେ **ଚାହିଦା ଅନୁଯାୟୀ ପ୍ରତ୍ୟେକ SNI ହୋଷ୍ଟନେମ୍ ପାଇଁ
  ଗୋଟିଏ ଲିଫ୍** ଜାରି କରେ (1 ବର୍ଷର ବୈଧତା, `subjectAltName` = SNI ହୋଷ୍ଟ୍)
  ଏବଂ ପ୍ରତି ହୋଷ୍ଟନେମ୍ରେ ଗୋଟିଏ `tls.SecureContext` କ୍ୟାଶ୍ କରେ।
- TLS-ଟର୍ମିନେଟିଂ ସର୍ଭର୍ ପାଇଁ `createSNICallback()` ଉପଲବ୍ଧ କରାଏ
  (ଦେଖନ୍ତୁ [§5](#5-how-decrypt-and-capture-work))।
- ପୁନଃଆରମ୍ଭଗୁଡ଼ିକ ମଧ୍ୟରେ CAକୁ ସ୍ଥିର ରଖିବା ପାଇଁ ଏକ `existingCa` ସହିତ
  ନିର୍ମାଣ କରାଯାଇପାରେ (ଯାହାଫଳରେ ଟ୍ରଷ୍ଟ୍ ଷ୍ଟୋର୍କୁ ପୁଣି ଇନଷ୍ଟଲ୍ କରିବାକୁ
  ପଡ଼େ ନାହିଁ)।

CA ପ୍ରାଇଭେଟ୍ କି **କେବେବି ମେସିନ୍ରୁ ବାହାରକୁ ଯାଏ ନାହିଁ**।

### ଟ୍ରଷ୍ଟ-ଷ୍ଟୋର୍ ଇନଷ୍ଟଲର୍ (`src/mitm/tproxy/caTrust.ts`)

ଇଣ୍ଟରସେପ୍ଟ୍ ହୋଇଥିବା କ୍ଲାଏଣ୍ଟ୍କୁ ଡାଇନାମିକ୍ CA ଉପରେ ଭରସା କରିବାକୁ ହେବ,
ତେଣୁ କ୍ୟାପଚର୍ ମୋଡ୍ ଆରମ୍ଭ କରିବାବେଳେ CA ସାର୍ଟିଫିକେଟ୍କୁ OS ଟ୍ରଷ୍ଟ୍ ଷ୍ଟୋର୍ରେ
ଏକ **ଉତ୍ସର୍ଗୀକୃତ ସ୍ଲଟ୍** — `omniroute-tproxy-ca.crt` (କନଷ୍ଟାଣ୍ଟ୍
`TPROXY_CA_CERT_NAME`) — ଅଧୀନରେ ଇନଷ୍ଟଲ୍ କରାଯାଏ; ଏହାକୁ ଷ୍ଟାଟିକ୍ MITM
ସାର୍ଟିଫିକେଟ୍ର ସ୍ଲଟ୍ (`omniroute-mitm.crt`) ଠାରୁ ପୃଥକ୍ ରଖାଯାଏ, ଯାହାଦ୍ୱାରା
ଦୁଇଟି ପରସ୍ପରକୁ କେବେବି ଓଭର୍ରାଇଟ୍ କରନ୍ତି ନାହିଁ।

`installTproxyCa(caPem, sudoPassword?)` ଡିଷ୍ଟ୍ରୋର ଆଙ୍କର୍ ଡିରେକ୍ଟୋରିକୁ
ଚିହ୍ନଟ କରେ (କ୍ରମାନୁସାରେ: ପ୍ରଥମେ Debian-ଶୈଳୀ) ଏବଂ ମେଳ ଖାଉଥିବା
ରିଫ୍ରେଶ୍ କମାଣ୍ଡ୍ ଚଲାଏ:

| ଆଙ୍କର୍ ଡିରେକ୍ଟୋରି                           | ରିଫ୍ରେଶ୍ କମାଣ୍ଡ୍         |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

ଇନଷ୍ଟଲେସନ୍ PEMକୁ ଏକ ଅସ୍ଥାୟୀ ଫାଇଲ୍ରେ ଷ୍ଟେଜ୍ କରେ, ତା’ପରେ (ବିଶେଷାଧିକାର ସହିତ)
ଆଙ୍କର୍ ଡିରେକ୍ଟୋରିରେ `mkdir -p` ଚଲାଏ, ଷ୍ଟେଜ୍ ହୋଇଥିବା ଫାଇଲ୍କୁ ସେଠାକୁ
`cp` କରେ ଏବଂ ରିଫ୍ରେଶ୍ କମାଣ୍ଡ୍ ଚଲାଏ। `uninstallTproxyCa()` କେବଳ
ଉତ୍ସର୍ଗୀକୃତ ସ୍ଲଟ୍କୁ ଅପସାରଣ କରେ (ଷ୍ଟାଟିକ୍ MITM ସାର୍ଟିଫିକେଟ୍କୁ ଅପରିବର୍ତ୍ତିତ
ରଖି) ଏବଂ ରିଫ୍ରେଶ୍ କରେ — non-Linuxରେ ଏହା ଏକ no-op।

ସମସ୍ତ ବିଶେଷାଧିକାରପ୍ରାପ୍ତ କମାଣ୍ଡ୍ `execFileWithPassword`
(`src/mitm/systemCommands.ts`) ମାଧ୍ୟମରେ ଚଲେ — **ଆର୍ଗ୍ ଆରେ ସହିତ, କୌଣସି
ଶେଲ୍ ନାହିଁ, କୌଣସି ଷ୍ଟ୍ରିଂ ଇଣ୍ଟରପୋଲେସନ୍ ନାହିଁ** ଏମିତି `spawn`
(କଠୋର ନିୟମ #13)। ପ୍ରୋସେସ୍ଟି root ହୋଇଥିବାବେଳେ (ଉଦାହରଣ ସ୍ୱରୂପ VPS)
ଟାର୍ଗେଟ୍ ସିଧାସଳଖ ଚାଲେ ଏବଂ କୌଣସି ପାସୱାର୍ଡ୍ ଆବଶ୍ୟକ ହୁଏ ନାହିଁ;
ଏକ non-root ଡେସ୍କଟପ୍ରେ `sudoPassword`କୁ stdinରେ `sudo -S` ମାଧ୍ୟମରେ
ପାସ୍ କରାଯାଏ।

> ଟ୍ରଷ୍ଟ-ଷ୍ଟୋର୍ ଇନଷ୍ଟଲେସନ୍କୁ ଅନୁମୋଦନ କରିବା ପାଇଁ ଡେସ୍କଟପ୍ର
> `sudoPassword` POST ବଡିରେ ପ୍ରଦାନ କରାଯାଏ; ପ୍ରୋସେସ୍ଟି root ହୋଇଥିଲେ
> ଏହାକୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ଅଣଦେଖା କରାଯାଏ।

## §5 ଡିକ୍ରିପ୍ସନ୍ ଏବଂ କ୍ୟାପ୍ଚର୍ କିପରି କାମ କରେ

ପାଇପ୍ଲାଇନ୍ (ସମ୍ପୂର୍ଣ୍ଣ `src/mitm/tproxy/` ଅଧୀନରେ):

```
ସ୍ଥାନୀୟ ଆପ୍  ──TCP/443──▶  mangle OUTPUT ସଂଯୋଗକୁ ଚିହ୍ନିତ କରେ (fwmark)
                          ip rule → ସ୍ଥାନୀୟ ରୁଟ୍ ଟେବୁଲ୍ → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT ଲିସନର୍ (ପୋର୍ଟ 8443)
                              │  captureMode.ts: socket.localAddress ରୁ ମୂଳ ଗନ୍ତବ୍ୟ ପଢ଼େ
                              ▼
                          tlsCapture.ts:
                            1. ପ୍ରତି-SNI ଲିଫ୍ (dynamicCert) ସହିତ CLIENT ର TLS ସମାପ୍ତ କରେ
                            2. ଆଭ୍ୟନ୍ତରୀଣ http.Server ଡିକ୍ରିପ୍ଟ ହୋଇଥିବା ପ୍ଲେନ୍ଟେକ୍ସଟ୍ ପାର୍ସ କରେ
                            3. କ୍ୟାପ୍ଚର୍ → source: "tproxy" ସହିତ globalTrafficBuffer.push()
                               (sanitizeHeaders + maskSecret ପ୍ରୟୋଗ କରାଯାଏ)
                            4. ବାଇପାସ୍-ଚିହ୍ନିତ ସକେଟ୍ ମାଧ୍ୟମରେ ମୂଳ ଗନ୍ତବ୍ୟକୁ
                               ପୁନଃ-ଏନ୍କ୍ରିପ୍ଟ କରି ଫର୍ୱାର୍ଡ କରେ (connectMarked, ଆଣ୍ଟି-ଲୁପ୍)
                              │
                              ▼
                          ମୂଳ ଅପ୍ଷ୍ଟ୍ରିମ୍ (api.example.com)
```

- **TLS ସମାପ୍ତି** (`createTlsCaptureServer`): ଡାଇନାମିକ୍ CA ର SNI କଲ୍ବ୍ୟାକ୍ ବ୍ୟବହାର କରି କଞ୍ଚା ଇଣ୍ଟରସେପ୍ଟ ହୋଇଥିବା
  ସକେଟ୍କୁ ସର୍ଭର୍-ସାଇଡ୍ `tls.TLSSocket` ମଧ୍ୟରେ ରାପ୍ କରେ,
  ତା’ପରେ ଡିକ୍ରିପ୍ଟ ହୋଇଥିବା ଷ୍ଟ୍ରିମ୍କୁ ଏକ ଆଭ୍ୟନ୍ତରୀଣ `http.Server` କୁ ପ୍ରଦାନ କରେ (ମାନକ MITM
  ସମାପ୍ତି କୌଶଳ)। ସକେଟ୍ର ଜୀବନକାଳ `MITM_IDLE_TIMEOUT_MS` ଦ୍ୱାରା ସୀମିତ ରହେ, ଯାହାଦ୍ୱାରା
  ଅଟକିଥିବା ଟନେଲ୍ ଫାଇଲ୍ ଡେସ୍କ୍ରିପ୍ଟର୍ଗୁଡ଼ିକୁ ନିଃଶେଷ କରିପାରିବ ନାହିଁ।
- **କ୍ୟାପ୍ଚର୍** (`handleDecryptedRequest`): `source: "tproxy"`, `"in-flight"` ରୁ ଆରମ୍ଭ ହେଉଥିବା ସ୍ଥିତି,
  `sanitizeHeaders()` ମାଧ୍ୟମରେ ପ୍ରକ୍ରିୟାକୃତ ହେଡର୍ ଏବଂ ବଫର୍ରେ ପ୍ରବେଶ କରିବା ପୂର୍ବରୁ
  `maskSecret()` ମାଧ୍ୟମରେ ପ୍ରକ୍ରିୟାକୃତ ବଡି ସହିତ ଏକ `InterceptedRequest` ପୁଶ୍ କରେ।
  ତା’ପରେ ଏଣ୍ଟ୍ରିଟିକୁ ପ୍ରତିକ୍ରିୟା, ଆକାର ଏବଂ ବିଳମ୍ବ ସହିତ ଅଦ୍ୟତନ କରାଯାଏ।
- **ପୁନଃ-ଏନ୍କ୍ରିପ୍ଟ ହୋଇଥିବା ଫର୍ୱାର୍ଡ** (`createForward` / `realForward`): ମୂଳ ଗନ୍ତବ୍ୟକୁ
  ପୁନଃ-ଏନ୍କ୍ରିପ୍ଟ କରେ। `rejectUnauthorized` ର ଡିଫଲ୍ଟ ହେଉଛି **`true`** (ଡିଫଲ୍ଟ ଭାବେ
  ସୁରକ୍ଷିତ) — କ୍ଲାଏଣ୍ଟ ଅନୁରୋଧ କରିଥିବା SNI/Host ବିପକ୍ଷରେ ଅପ୍ଷ୍ଟ୍ରିମ୍ ସାର୍ଟିଫିକେଟ୍
  ଯାଞ୍ଚ କରାଯାଏ, ତେଣୁ ମୂଳ କ୍ଲାଏଣ୍ଟ ଯାହାକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରିଥାନ୍ତା ପ୍ରକ୍ସି ଠିକ୍ ସେହିଟିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

### ଆଣ୍ଟି-ଲୁପ୍ (SO_MARK)

ଯେହେତୁ ନିୟମଗୁଡ଼ିକ ନୂଆ ସ୍ଥାନୀୟ ଆଉଟ୍ବାଉଣ୍ଡ ସଂଯୋଗଗୁଡ଼ିକୁ ଚିହ୍ନିତ କରେ, ପ୍ରକ୍ସିର **ନିଜସ୍ୱ**
ପୁନଃ-ଏନ୍କ୍ରିପ୍ଟ ହୋଇଥିବା ଫର୍ୱାର୍ଡ ସାଧାରଣତଃ ପୁଣି ଇଣ୍ଟରସେପ୍ଟ ହେବ — ଏକ ଅସୀମ ଲୁପ୍। ଫର୍ୱାର୍ଡ
ପଥ ଏକ ବାଇପାସ୍ ସକେଟ୍ ମାର୍କ (**SO_MARK**) ସହିତ ଏହା ବିରୋଧରେ ସୁରକ୍ଷା ଦିଏ:

- `realForward` ତାହାର ଅପ୍ଷ୍ଟ୍ରିମ୍ ସକେଟ୍କୁ `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  ମାଧ୍ୟମରେ ଖୋଲେ — `DEFAULT_BYPASS_MARK = 0x539` — ଯାହା `connect()` ର **ପୂର୍ବରୁ**
  **SO_MARK** ସେଟ୍ କରେ, ତେଣୁ ଫର୍ୱାର୍ଡର SYN ବାଇପାସ୍ ମାର୍କ ବହନ କରେ।
- `mangle OUTPUT` ନିୟମ ପୂର୍ବରୁ ବାଇପାସ୍ ମାର୍କ ବହନ କରୁଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ
  ବାଦ ଦିଏ (`-m mark ! --mark <bypassMark>`), ତେଣୁ ପ୍ରକ୍ସିର ଫର୍ୱାର୍ଡକୁ ପୁନଃ ଚିହ୍ନିତ
  କରାଯାଏ **ନାହିଁ** ଏବଂ ଏହା ପୁଣି TPROXY ରେ ପ୍ରବେଶ କରେ ନାହିଁ।

> କାର୍ଯ୍ୟାନ୍ୱୟନ ଟିପ୍ପଣୀ: ବାଇପାସ୍-ଚିହ୍ନିତ ସକେଟ୍କୁ ଏଜେଣ୍ଟର
> `createConnection` ରେ ସ୍ଥାପନ କରିବା ଆବଶ୍ୟକ (ଏକ ଏଜେଣ୍ଟ ଉପସ୍ଥିତ ଥିବାବେଳେ
> `https.request({ createConnection })` କୁ ନିରବରେ ଅଣଦେଖା କରାଯାଏ), ନଚେତ୍ ଫର୍ୱାର୍ଡ
> ଏକ ଅଚିହ୍ନିତ ସକେଟ୍ ଖୋଲିବ ଏବଂ ଲୁପ୍ ପୁଣି ଫେରିଆସିବ। ଏହା e2e-ଯାଞ୍ଚିତ ଆଣ୍ଟି-ଲୁପ୍ ସମାଧାନ ଥିଲା।

## §7 ଟ୍ରାଞ୍ଜାକ୍ସନାଲ୍ ଫାୟାରୱାଲ୍ ପ୍ରୟୋଗ / ପ୍ରତ୍ୟାବର୍ତ୍ତନ

କୌଣସି କ୍ରାଶ୍ କେବେବି ଏକ `mangle` ନିୟମ କିମ୍ବା ପୁରୁଣା ରୁଟ୍କୁ ଛାଡ଼ିଯିବା ଉଚିତ ନୁହେଁ। କମାଣ୍ଡ୍ ବିଲ୍ଡର୍
(`src/mitm/tproxy/commands.ts`) ଏବଂ ରନର୍ (`src/mitm/tproxy/setup.ts`) ସୁନିଶ୍ଚିତ କରନ୍ତି ଯେ
**ପ୍ରତ୍ୟାବର୍ତ୍ତନ ହେଉଛି ପ୍ରୟୋଗର ସଠିକ୍ ବିପରୀତ, ଓଲଟା କ୍ରମରେ**।

`applyTproxy(cfg)` ପ୍ରୟୋଗ କମାଣ୍ଡ୍ଗୁଡ଼ିକୁ କ୍ରମାନୁସାରେ ଚଲାଏ; **ଯେକୌଣସି** ବିଫଳତା ଘଟିଲେ ଏହା
ସର୍ବୋତ୍ତମ-ପ୍ରୟାସରେ ସମ୍ପୂର୍ଣ୍ଣ `revertTproxy(cfg)` ଚଲାଇ ପୁନଃ ତ୍ରୁଟି ଉତ୍ଥାପନ କରେ — ତେଣୁ ଫାୟାରୱାଲ୍
ସମ୍ପୂର୍ଣ୍ଣ ପ୍ରୟୋଗ ହୋଇଥାଏ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ପ୍ରତ୍ୟାବର୍ତ୍ତିତ ହୋଇଥାଏ, କେବେବି ଆଂଶିକ ଭାବେ ପ୍ରୟୋଗ ହୁଏନାହିଁ। `revertTproxy(cfg)`
ବିପରୀତ କମାଣ୍ଡ୍ଗୁଡ଼ିକୁ ଓଲଟା କ୍ରମରେ ଚଲାଏ ଏବଂ ବିଫଳତାଗୁଡ଼ିକୁ ଅଣଦେଖା କରେ (ଇଡେମ୍ପୋଟେଣ୍ଟ୍ — ବିନା ସର୍ତ୍ତରେ କଲ୍ କରିବା ସୁରକ୍ଷିତ,
ଯଥା AgentBridge `repairMitm()` କ୍ଲିନ୍ଅପ୍ରୁ)।

କୌଣସି କମାଣ୍ଡ୍ ପୂର୍ବରୁ `validateTproxyConfig(cfg)` ଚାଲେ: ପୋର୍ଟଗୁଡ଼ିକ `1–65535` ହେବା ଆବଶ୍ୟକ,
`mark`/`routeTable`/`bypassMark` ଧନାତ୍ମକ ପୂର୍ଣ୍ଣସଂଖ୍ୟା ହେବା ଆବଶ୍ୟକ, ଏବଂ `bypassMark`
`mark` ଠାରୁ ଭିନ୍ନ ହେବା ଆବଶ୍ୟକ (ଆଣ୍ଟି-ଲୁପ୍)।

### ପ୍ରୟୋଗ କମାଣ୍ଡ୍ଗୁଡ଼ିକ (କ୍ରମାନୁସାରେ)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

ପ୍ରତ୍ୟାବର୍ତ୍ତନ ସେଗୁଡ଼ିକୁ ଓଲଟା କ୍ରମରେ ବିଲୋପ କରେ: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`।

> ଏହି ପ୍ରକ୍ରିୟାଟି **OUTPUT-ଆଧାରିତ**, କାରଣ MITM ବ୍ୟବହାର ପରିସ୍ଥିତିଟି _ସ୍ଥାନୀୟ_ ଆଉଟ୍ବାଉଣ୍ଡ୍
> ଟ୍ରାଫିକ୍ (ସମାନ ହୋଷ୍ଟରେ ଥିବା ଆପ୍ଗୁଡ଼ିକ) ପାଇଁ, ଯାହାକୁ କେବଳ `PREROUTING`ରେ ଥିବା TPROXY
> ଦେଖିପାରେ ନାହିଁ — `PREROUTING` କେବଳ ଫରୱାର୍ଡ୍ ହୋଇଥିବା ଟ୍ରାଫିକ୍କୁ ଦେଖେ। `OUTPUT` ଚେନ୍ ନୂତନ
> ସ୍ଥାନୀୟ ସଂଯୋଗଗୁଡ଼ିକୁ ଚିହ୍ନିତ କରେ, `ip rule` ସେଗୁଡ଼ିକୁ ସ୍ଥାନୀୟ ଡେଲିଭରି (`lo`) ପାଇଁ ପୁନଃ-ରୁଟ୍ କରେ, ଏବଂ
> ତା’ପରେ `PREROUTING` ସେଗୁଡ଼ିକୁ ଟ୍ରାନ୍ସପାରେଣ୍ଟ୍ ଲିସନର୍କୁ ନ୍ୟସ୍ତ କରେ।

## §8 ବିନ୍ୟାସ

ଆରମ୍ଭ ଅନୁରୋଧ (`POST /api/tools/agent-bridge/tproxy`) ନିମ୍ନଲିଖିତ
ଫିଲ୍ଡଗୁଡ଼ିକୁ ଗ୍ରହଣ କରେ, ଯାହା `StartTproxyBodySchema` (`tproxy/route.ts`) ଦ୍ୱାରା ବୈଧୀକୃତ ହୁଏ। ସବୁଗୁଡ଼ିକ ଇଚ୍ଛାଧୀନ
ଏବଂ ଦିଆଯାଇନଥିଲେ ସେମାନଙ୍କର ଡିଫଲ୍ଟ ମୂଲ୍ୟ ବ୍ୟବହାର କରନ୍ତି:

| ଫିଲ୍ଡ            | ପ୍ରକାର             | ଡିଫଲ୍ଟ   | ଟିପ୍ପଣୀ                                                                                                                   |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | ଟ୍ରାନ୍ସପାରେଣ୍ଟ୍ ଭାବେ ଇଣ୍ଟରସେପ୍ଟ୍ କରାଯିବାକୁ ଥିବା ଗନ୍ତବ୍ୟ TCP ପୋର୍ଟ                                                         |
| **mark**         | int (≥1)           | `0x2333` | `OUTPUT`ରେ ସେଟ୍ ହୋଇଥିବା ଫାୟାରୱାଲ୍ ମାର୍କ, ଯାହା `ip rule` + `PREROUTING` ଦ୍ୱାରା ମେଳ କରାଯାଏ                                  |
| **onPort**       | int (1–65535)      | `8443`   | ଟ୍ରାନ୍ସପାରେଣ୍ଟ୍ (**IP_TRANSPARENT**) ଲିସନର୍ ବାଇଣ୍ଡ୍ କରୁଥିବା ପୋର୍ଟ                                                         |
| **routeTable**   | int (≥1)           | `233`    | `local 0.0.0.0/0` ରୁଟ୍ ଧାରଣ କରୁଥିବା ପଲିସି-ରାଉଟିଂ ଟେବୁଲ୍ id                                                                |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | ପ୍ରକ୍ସି ନିଜର ଅପ୍ଷ୍ଟ୍ରିମ୍ ସଂଯୋଗଗୁଡ଼ିକରେ ସେଟ୍ କରୁଥିବା ବାଇପାସ୍ ସକେଟ୍ ମାର୍କ (**SO_MARK**); `OUTPUT`ରେ ବାଦ ଦିଆଯାଏ (ଆଣ୍ଟି-ଲୁପ୍) |
| **sudoPassword** | string             | —        | କେବଳ ଅଣ-root ଡେସ୍କଟପ୍: ଟ୍ରଷ୍ଟ-ଷ୍ଟୋର୍ ଇନ୍ଷ୍ଟଲ୍କୁ ଅନୁମୋଦନ କରେ; root ଥିଲେ ଅଣଦେଖା କରାଯାଏ                                      |

TPROXY ପାଇଁ **କୌଣସି ପରିବେଶ ଚର ନାହିଁ** — ସମସ୍ତ ବିନ୍ୟାସ
POST ବଡି କିମ୍ବା ଉପରୋକ୍ତ ଡିଫଲ୍ଟଗୁଡ଼ିକ ମାଧ୍ୟମରେ କରାଯାଏ।

   firewall ନିୟମଗୁଡ଼ିକୁ ପୂର୍ବାବସ୍ଥାକୁ ଫେରାଏ।

capture-mode ସ୍ଥିତି (ଚାଲୁଛି / ଉପଲବ୍ଧ / intercept ସଂଖ୍ୟା / listener port)

## §10 ସମସ୍ୟା ସମାଧାନ

### ଟଗଲ୍ଟି ଅକ୍ଷମ ଅଛି

native addon ଲୋଡ୍ ହୋଇପାରୁନାହିଁ। ନିଶ୍ଚିତ କରନ୍ତୁ: ଆପଣ Linux ରେ ଅଛନ୍ତି, addon କୁ
(`npm run build:native:tproxy`) ଦ୍ୱାରା build କରିଛନ୍ତି ଏବଂ process ଟି `transparent.node` ଲୋଡ୍ କରିପାରୁଛି।
`isTransparentSocketAvailable()` ଟଗଲ୍କୁ ନିୟନ୍ତ୍ରଣ କରେ; addon ନଥିଲେ `GET /api/tools/agent-bridge/tproxy`
`available: false` ଫେରାଏ।

### କିଛି capture ହେଉନାହିଁ

- intercept ହୋଇଥିବା process ପ୍ରକୃତରେ ବିନ୍ୟାସିତ `dport`
  (ଡିଫଲ୍ଟ `443`) ସହିତ ସଂଯୋଗ କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।
- process ଟି dynamic CA କୁ ବିଶ୍ୱାସ କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ। CA ଟି
  `omniroute-tproxy-ca.crt` ଅଧୀନରେ ଇନ୍ଷ୍ଟଲ୍ ହୁଏ; ନିଜସ୍ୱ trust store (Firefox/Chrome NSS)
  ଥିବା app ଗୁଡ଼ିକରେ cert ଟି ସେଠାରେ ମଧ୍ୟ ଯୋଡ଼ିବାକୁ ପଡ଼ିପାରେ।
- cert-trusted / server
  health check ପାଇଁ AgentBridge **Diagnose** self-test ଚଲାନ୍ତୁ ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)
  ଦେଖନ୍ତୁ)।

### crash ପରେ ରହିଯାଇଥିବା firewall ନିୟମ

`revertTproxy()` ହେଉଛି apply ର ଠିକ୍ ବିପରୀତ ଏବଂ ଏହା idempotent। mode ବନ୍ଦ କଲେ
ନିୟମଗୁଡ଼ିକ ପୂର୍ବାବସ୍ଥାକୁ ଫେରେ; ଯଦି session ମଝିରେ OmniRoute କୁ ବନ୍ଦ କରିଦିଆଯାଇଥିଲା, ଅନାଥ system
state (DNS spoof, root CA, system proxy) କୁ ପୂର୍ବାବସ୍ଥାକୁ ଫେରାଇବା ପାଇଁ AgentBridge
**Repair** action (`POST /api/tools/agent-bridge/repair`) ବ୍ୟବହାର କରନ୍ତୁ। TPROXY `mangle` ନିୟମ ଏବଂ route ମଧ୍ୟ
reboot ସମୟରେ ସ୍ୱୟଂଚାଳିତ ଭାବେ flush ହୁଏ।

### ଅସୀମ loop / proxy ନିଜ forward କୁ intercept କରୁଛି

ଏହା anti-loop କ୍ଷେତ୍ର। `bypassMark`, `mark` ଠାରୁ ଭିନ୍ନ ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ (validation
ଏହାକୁ ବାଧ୍ୟତାମୂଳକ କରେ) ଏବଂ forward ଟି `connectMarked` ବ୍ୟବହାର କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ (ଏହା `realForward` ରେ କରେ)।
[§5 Anti-loop](#anti-loop-so_mark) ଦେଖନ୍ତୁ।
