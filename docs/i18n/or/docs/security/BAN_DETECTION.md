OmniRoute ଏକ ପ୍ରଦାନକାରୀଙ୍କ **ଆକାଉଣ୍ଟ ସ୍ଥାୟୀ ଭାବେ ଅଚଳ** (ନିଲମ୍ବିତ / ନିଷ୍କ୍ରିୟ / ToS-ନିଷିଦ୍ଧ) ବୋଲି ସୂଚିତ କରୁଥିବା ସଙ୍କେତଗୁଡ଼ିକ ପାଇଁ ଅପ୍ଷ୍ଟ୍ରିମ୍ ତ୍ରୁଟି ପ୍ରତିକ୍ରିୟାଗୁଡ଼ିକୁ ସ୍କାନ୍ କରେ ଏବଂ, ମେଳ ମିଳିଲେ, ସେହି ସଂଯୋଗକୁ ଏକ **ଟର୍ମିନାଲ୍ `banned` ଅବସ୍ଥାକୁ** ନେଇଯାଏ, ଯାହାଫଳରେ ଅନୁରୋଧଗୁଡ଼ିକ ପାଇଁ ଏହାକୁ ଆଉ ଚୟନ କରାଯାଏ ନାହିଁ। **Security → Banned Keywords** ସେଟିଂସ୍ କାର୍ଡ ଏହାକୁ ହିଁ ବିନ୍ୟାସ କରେ ("ସ୍ଥାୟୀ ଆକାଉଣ୍ଟ ନିଷେଧ ଚିହ୍ନଟକୁ ସକ୍ରିୟ କରୁଥିବା ଅତିରିକ୍ତ କୀୱାର୍ଡଗୁଡ଼ିକ। ଅନ୍ତର୍ନିର୍ମିତ କୀୱାର୍ଡଗୁଡ଼ିକ ସର୍ବଦା ପ୍ରୟୋଗ ହୁଏ।")।

ଏହି ପୃଷ୍ଠାଟି ଅନ୍ତର୍ନିର୍ମିତ ତାଲିକା, ଚିହ୍ନଟ ପ୍ରବାହ, ଏହାର ପରିସର, କିପରି ସୁରକ୍ଷିତ ଭାବେ କଷ୍ଟମ୍ କୀୱାର୍ଡ ଯୋଡ଼ାଯିବ ଏବଂ କିପରି ଏକ ଚିହ୍ନିତ ସଂଯୋଗକୁ ପୁନରୁଦ୍ଧାର କରାଯିବ—ତାହା ଡକ୍ୟୁମେଣ୍ଟ କରେ। ଟର୍ମିନାଲ୍ ଅବସ୍ଥାଟି ନିଜେ ସ୍ଥିତିସ୍ଥାପକତା ମଡେଲ୍ର ଅଂଶ — ("ଟର୍ମିନାଲ୍ ଅବସ୍ଥାଗୁଡ଼ିକ") ପାଇଁ [RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ଦେଖନ୍ତୁ।

**ପ୍ରାମାଣିକ ଉତ୍ସ:** `open-sse/services/accountFallback.ts`
(`ACCOUNT_DEACTIVATED_SIGNALS`, `getMergedBannedSignals()`, `isAccountDeactivated()`),
ଏବଂ ଅଣ-ଟର୍ମିନାଲ୍ ସତ୍ୟାପନ ଶ୍ରେଣୀ
(`ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` / `isAccountVerificationRequired()`) ତଥା ଏହାକୁ ବ୍ୟବହାର କରୁଥିବା 403 ଶାଖା ପାଇଁ
`open-sse/services/errorClassifier.ts`।

## ଅନ୍ତର୍ନିହିତ କୀୱାର୍ଡଗୁଡ଼ିକ

ଯେକୌଣସି କଷ୍ଟମ୍ ତାଲିକା ଥିଲେ ମଧ୍ୟ, ଏହି 7ଟି ସବ୍ଷ୍ଟ୍ରିଙ୍ଗ ସର୍ବଦା ପ୍ରଯୁଜ୍ୟ (ବଡ଼/ଛୋଟ ଅକ୍ଷର ନିର୍ବିଶେଷରେ):

```
account_deactivated
account has been deactivated
account has been disabled
your account has been suspended
this account is deactivated
this service has been disabled in this account for violation    (Antigravity)
this service has been disabled in this account                  (Antigravity)
```

> ପ୍ରଦାନକାରୀମାନେ ସେମାନଙ୍କର ନିଷେଧ-ସମ୍ବନ୍ଧୀୟ ଶବ୍ଦାବଳୀ ପରିବର୍ତ୍ତନ କରିବା ସହିତ ଏହି ତାଲିକା ମଧ୍ୟ ବିକଶିତ ହୁଏ। ପ୍ରାମାଣିକ
> କପିଟି `open-sse/services/accountFallback.ts` ମଧ୍ୟରେ ଥିବା `ACCOUNT_DEACTIVATED_SIGNALS`;
> ଉପରୋକ୍ତ ବ୍ଲକ୍କୁ ଏକ ସ୍ନାପ୍ଶଟ୍ ଭାବେ ଗ୍ରହଣ କରନ୍ତୁ।

### ନିଷେଧ ନୁହେଁ: ଅପରେଟର୍ଙ୍କ ଦ୍ୱାରା କାର୍ଯ୍ୟଯୋଗ୍ୟ ଯାଞ୍ଚ ପ୍ରମ୍ପ୍ଟଗୁଡ଼ିକ

`verify your account to continue` **ପୂର୍ବରୁ** ଉପରୋକ୍ତ ତାଲିକାରେ ଥିଲା। ଏହା ଏକ ନିଷେଧ
ସଙ୍କେତ ନୁହେଁ ଏବଂ ବର୍ତ୍ତମାନ `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` ମଧ୍ୟରେ ରହିଛି, ଯାହା ସଂଯୋଗକୁ
ସମାପ୍ତ କରିବା ପରିବର୍ତ୍ତେ ଏହାକୁ ପୁନରୁଦ୍ଧାରଯୋଗ୍ୟ `PROJECT_ROUTE_ERROR` ଭାବେ ବର୍ଗୀକୃତ କରେ।

Google Cloud Code / Antigravity ଏହାକୁ `403 VALIDATION_REQUIRED` ଭାବେ ଫେରାଏ। ଏହା
**ସାମୟିକ ଏବଂ ସୁସ୍ଥ, ସମ୍ପୂର୍ଣ୍ଣ କୋଟା ଥିବା ଆକାଉଣ୍ଟଗୁଡ଼ିକରେ ମଧ୍ୟ ଘଟେ** — ଏକ ଲାଇଭ୍
ଡିପ୍ଲୟମେଣ୍ଟରେ ମାପ କରାଯାଇଛି (2026-09-25, `proxy_logs`): ଗୋଟିଏ Antigravity ସଂଯୋଗ 10 ମିନିଟ୍ ମଧ୍ୟରେ ଏପରି 33ଟି
403 ଫେରାଇଥିଲା ଏବଂ `active` ରହିଥିଲା, ଯେତେବେଳେ ସମସ୍ତ 17ଟି ୱିଣ୍ଡୋରେ ନିଜ କୋଟାର 100 % ଧାରଣ କରିଥିବା
ଏକ ସମାନାନ୍ତର ସଂଯୋଗ ଏପରି **ଗୋଟିଏମାତ୍ର** ପ୍ରତିକ୍ରିୟା ଦ୍ୱାରା ସ୍ଥାୟୀ ଭାବେ ନିଷିଦ୍ଧ ହୋଇଥିଲା। ଏକମାତ୍ର
ପାର୍ଥକ୍ୟ ଥିଲା କେଉଁ ପ୍ରୟାସଟି ସର୍ଭ୍ ହୋଇଥିଲା।

ଏହି ପାର୍ଥକ୍ୟଟି ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ, କାରଣ ଏକ ଟର୍ମିନାଲ୍ ମେଳ ହେଉଛି `permanent: true` (1-ବର୍ଷର କୁଲ୍ଡାଉନ୍,
କେବେବି ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନରୁଦ୍ଧାର ହୁଏ ନାହିଁ), ଯେତେବେଳେ ଅପରେଟର୍ ଏକ ବ୍ରାଉଜର୍ରେ ଯାଞ୍ଚ ପ୍ରମ୍ପ୍ଟକୁ ସମାଧାନ କରନ୍ତି।
ବାକ୍ୟାଂଶଟିକୁ ନିଷେଧ ତାଲିକାରେ ରଖିବା ଫଳରେ `classifyProviderError` ମଧ୍ୟରେ ଥିବା ପୁନରୁଦ୍ଧାରଯୋଗ୍ୟ cloud-code 403 ଶାଖାଟି
ଏହି ଶବ୍ଦାବଳୀ ପାଇଁ ଅପହଞ୍ଚ ହୋଇଯାଇଥିଲା, କାରଣ `accountDeactivated`କୁ
ପ୍ରଥମେ ମୂଲ୍ୟାୟନ କରାଯାଏ — ତେଣୁ Gemini Code Assist ପାଇଁ
[#868](https://github.com/diegosouzapw/OmniRoute/pull/868) ଏବଂ
[#6452](https://github.com/diegosouzapw/OmniRoute/pull/6452)ରେ ଯୋଡ଼ାଯାଇଥିବା project-route ପୁନରୁଦ୍ଧାର କେବେବି ଚାଲିପାରୁ ନଥିଲା।

ପାଖାପାଖି ଥିବା ତିନୋଟି **ପୃଥକ** ସଙ୍କେତ ଟେବୁଲ୍ ନିଷିଦ୍ଧ-କୀୱାର୍ଡ ଚିହ୍ନଟର ଅଂଶ _ନୁହେଁ_:

- `CREDITS_EXHAUSTED_SIGNALS` — ବିଲିଂ/କୋଟା ଶେଷ ହୋଇଛି (`insufficient_quota`,
  `credit_balance_too_low`, `payment required`, …) → ଟର୍ମିନାଲ୍ `credits_exhausted`।
- `OAUTH_INVALID_TOKEN_SIGNALS` — **ଅଣ-ଟର୍ମିନାଲ୍**; ଏକ ଟୋକନ୍ ରିଫ୍ରେଶ୍ ଏହାକୁ ପୁନରୁଦ୍ଧାର କରିପାରେ।
- `ACCOUNT_VERIFICATION_REQUIRED_SIGNALS` — **ଅଣ-ଟର୍ମିନାଲ୍**; ଅପରେଟର୍ଙ୍କୁ ଅପ୍ଷ୍ଟ୍ରିମ୍ରେ
  ଆକାଉଣ୍ଟଟି ପୁନଃଯାଞ୍ଚ କରିବାକୁ ପଡ଼ିବ। ଏହା `open-sse/services/errorClassifier.ts` ମଧ୍ୟରେ ରହେ
  (ଅନ୍ୟ ଦୁଇଟି `accountFallback.ts` ମଧ୍ୟରେ ରହେ)। ଉପରୋକ୍ତ ବିଭାଗ ଦେଖନ୍ତୁ।

ଟିପ୍ପଣୀ: **`rate limit`** / `429` ପରି ସାଧାରଣ ସାମୟିକ ବାକ୍ୟାଂଶଗୁଡ଼ିକୁ
ରେଟ୍-ଲିମିଟ୍ / ସଂଯୋଗ-କୁଲ୍ଡାଉନ୍ ପଥ ଦ୍ୱାରା ପରିଚାଳନା କରାଯାଏ ଏବଂ ସେଗୁଡ଼ିକ ନିଷେଧ ସଙ୍କେତ **ନୁହେଁ**।

## ଚିହ୍ନଟ ପ୍ରବାହ

```
ଅପସ୍ଟ୍ରିମ୍ ତ୍ରୁଟି ପ୍ରତିକ୍ରିୟା
  → ବଡିକୁ ଷ୍ଟ୍ରିଙ୍ଗ୍ରେ ପରିବର୍ତ୍ତନ + ଲୋଅର୍କେସ୍ରେ ପରିବର୍ତ୍ତନ
  → isAccountDeactivated(body): getMergedBannedSignals().some(sig => body.includes(sig))   [ସବ୍ଷ୍ଟ୍ରିଙ୍ଗ୍ ମେଳ]
  → ମେଳିଛି?
      → କନେକ୍ସନ୍ testStatus = "banned"      (ସ୍ଥାୟୀ — 1-ବର୍ଷର କୁଲ୍ଡାଉନ୍, କେବେବି ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନରୁଦ୍ଧାର ହୁଏ ନାହିଁ)
      → ଯଦି `autoDisableBannedAccounts` ସେଟିଂ ଚାଲୁ ଅଛି ଏବଂ `autoDisableBannedScope`
        ଏହି କନେକ୍ସନ୍କୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ (`all`, କିମ୍ବା OAuth/cookie/session ପାଇଁ `subscription`)
        → `isActive = false` ମଧ୍ୟ। ସ୍କୋପ୍ `subscription` ଥିବାବେଳେ ପ୍ରିପେଡ୍ API କୀଗୁଡ଼ିକ ସକ୍ରିୟ
        ରହେ।
      → ଆକାଉଣ୍ଟ ଚୟନ ସମୟରେ କନେକ୍ସନ୍କୁ ଏଡ଼ାଇ ଦିଆଯାଏ (କମ୍ବୋ QUOTA_BLOCKING ଅବସ୍ଥାଗୁଡ଼ିକ)
```

- ଏହି ମେଳଟି ପ୍ରତିକ୍ରିୟା **ବଡି** ଉପରେ ଏକ **ଅକ୍ଷରର କେସ୍ ପ୍ରତି ଅସମ୍ବେଦନଶୀଳ ସବ୍ଷ୍ଟ୍ରିଙ୍ଗ୍** ସନ୍ଧାନ
  (`isAccountDeactivated`, `accountFallback.ts`)।
- ଏକ ନିଷେଧ-ସଙ୍କେତ ବଡି ମିଳିଲେ, **ଯେକୌଣସି
  HTTP ସ୍ଥିତି**ରେ ସ୍ଥାୟୀ `banned` ଟର୍ମିନାଲାଇଜେସନ୍ ସକ୍ରିୟ ହୁଏ (`markAccountUnavailable` → `checkFallbackError` ମାଧ୍ୟମରେ)। ଅଧିକ
  ସୀମିତ **`deactivated`** ଲେବଲ୍ (କନେକ୍ସନ୍ରେ କୌଣସି
  ଅତିରିକ୍ତ API କୀ ନଥିଲେ `isActive=false`) ଇନ୍ଲାଇନ୍ `chatCore.ts` ପଥ ଦ୍ୱାରା **HTTP 401 / 403**ରେ
  ଲେଖାଯାଏ (`classifyProviderError` → `ACCOUNT_DEACTIVATED` ମାଧ୍ୟମରେ ବର୍ଗୀକୃତ)। ଧ୍ୟାନ ଦିଅନ୍ତୁ,
  `markAccountUnavailable()` ପଥ ସେହି `ACCOUNT_DEACTIVATED` ସଙ୍କେତ ପାଇଁ (`resolveTerminalConnectionStatus`
  ମାଧ୍ୟମରେ) ଏକ _ଭିନ୍ନ_ ଟର୍ମିନାଲ୍ ଅବସ୍ଥା — **`expired`** — ଲେଖେ; ତେଣୁ ପ୍ରତିକ୍ରିୟାକୁ କେଉଁ ପଥ ପରିଚାଳନା କରିଥିଲା ତାହା ଉପରେ ନିର୍ଭର କରି
  ସମାନ ନିଷେଧ `deactivated` କିମ୍ବା `expired` ଭାବେ ଦେଖାଯାଇପାରେ। (ପୁରୁଣା
  କୋଡ୍ ଟିପ୍ପଣୀରେ କୁହାଯାଇଛି "ଯେତେବେଳେ ଏକ 401 ବଡିରେ ଏହି ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକ ଥାଏ" — ଏହା
  ବର୍ତ୍ତମାନର ଆଚରଣକୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ବର୍ଣ୍ଣନା କରେ ନାହିଁ।)
- ଟର୍ମିନାଲ୍ ଅବସ୍ଥାଗୁଡ଼ିକୁ ଫିଲ୍ଟର୍ କରାଯାଉଥିବା ସମସ୍ତ ସ୍ଥାନରେ ଏକ `banned` କନେକ୍ସନ୍କୁ ଚୟନରୁ
  ବାଦ ଦିଆଯାଏ (`isTerminalConnectionStatus`, କମ୍ବୋ `QUOTA_BLOCKING_CONNECTION_STATUSES`)।

## ପରିସର — କେଉଁ ପ୍ରଦାନକାରୀଗୁଡ଼ିକୁ ସ୍କାନ୍ କରାଯାଏ

**ସମସ୍ତ ପ୍ରଦାନକାରୀ।** ଏହି ଯାଞ୍ଚ ସାଧାରଣ ତ୍ରୁଟି-ପରିଚାଳନା ପାଇପଲାଇନ୍ରେ ଚାଲେ,
ଯାହା ମଧ୍ୟ ଦେଇ ପ୍ରତ୍ୟେକ ବିଫଳ ଅପ୍ଷ୍ଟ୍ରିମ୍ ଅନୁରୋଧ ପ୍ରବାହିତ ହୁଏ — ଏହା
OAuth/ସବ୍ସ୍କ୍ରିପ୍ସନ୍ ସ୍କ୍ରାପର୍ଗୁଡ଼ିକ ମଧ୍ୟରେ **ସୀମିତ ନୁହେଁ**। ଫଳସ୍ୱରୂପ ମିଳୁଥିବା ଟର୍ମିନାଲ୍ ସ୍ଥିତି ପ୍ରତ୍ୟେକ **ସଂଯୋଗ** ପାଇଁ ହୋଇଥାଏ,
ପ୍ରତ୍ୟେକ ପ୍ରଦାନକାରୀ ପାଇଁ ନୁହେଁ।

ତଥାପି, ବିଲ୍ଟ-ଇନ୍ _ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକ_ ପ୍ରକୃତ ବ୍ୟାନ୍ ହେବାର ବିପଦ ଥିବା
ସବ୍ସ୍କ୍ରିପ୍ସନ୍/OAuth ପ୍ରଦାନକାରୀମାନଙ୍କ ପାଇଁ ଉନ୍ମୁଖୀ (ChatGPT Web Codex, Claude Web, Codex, Muse Spark,
Antigravity)। କୌଣସି API-key ପ୍ରଦାନକାରୀର ତ୍ରୁଟି ବଡିରେ ଯଦି ଉପ-ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକ ମଧ୍ୟରୁ ଗୋଟିଏ
ଆକ୍ଷରିକ ଭାବେ ରହିଥାଏ, କେବଳ ସେତେବେଳେ ଏହା ଡିଟେକ୍ଟର୍କୁ ଟ୍ରିଗର୍ କରିବ।

`autoDisableBannedScope` (`all` | `subscription`, ଡିଫଲ୍ଟ `all`) କୌଣସି
ମେଳ ମିଳିଲେ `isActive=false` ମଧ୍ୟ ସେଟ୍ ହେବ କି ନାହିଁ ନିୟନ୍ତ୍ରଣ କରେ। `subscription` ଅର୍ଥ ହେଉଛି ଲଗ୍ଇନ୍-ଶୈଳୀର ସିଟ୍ଗୁଡ଼ିକ
(ପେଡ୍ ସବ୍ସ୍କ୍ରିପ୍ସନ୍ ଓ ମାଗଣା ଆକାଉଣ୍ଟ, web-cookie ସେସନ୍ଗୁଡ଼ିକ ସମେତ)। ଏହା ତଥାପି
ପ୍ରିପେଡ୍ API କୀଗୁଡ଼ିକ ପାଇଁ `testStatus=banned` ରେକର୍ଡ କରେ, କିନ୍ତୁ ସେଗୁଡ଼ିକୁ ରାଉଟିଂ
ପୁଲ୍ରେ ରଖେ। ସ୍ଥାୟୀ ଡିଜାଇନ୍ ହେଉଛି ପ୍ରତ୍ୟେକ ପ୍ରଦାନକାରୀ ଓ ପ୍ରତ୍ୟେକ ଆକାଉଣ୍ଟ ପାଇଁ ଏକ ଓଭର୍ରାଇଡ୍; ଗ୍ଲୋବାଲ୍
enum ହେଉଛି ପ୍ରାରମ୍ଭିକ ସଂସ୍କରଣ।

## କଷ୍ଟମ୍ ବ୍ୟାନ୍ କୀୱାର୍ଡ

**Security → Banned Keywords** ରେ କୀୱାର୍ଡ ଯୋଡ଼ନ୍ତୁ କିମ୍ବା ଅପସାରଣ କରନ୍ତୁ (ଗ୍ଲୋବାଲ୍
`customBannedSignals` ସେଟିଂ ଭାବେ `PATCH /api/settings` ମାଧ୍ୟମରେ ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ)। ସେଗୁଡ଼ିକ ବିଲ୍ଟ-ଇନ୍ ତାଲିକାରେ **ଯୋଡ଼ାଯାଏ**
— କେବେବି ଏହାର ପ୍ରତିସ୍ଥାପନ ନୁହେଁ — ଏବଂ ସେଭ୍ କଲେ (ଏବଂ ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ)
`setCustomBannedSignals()` ମାଧ୍ୟମରେ ହଟ୍-ରିଲୋଡ୍ ହୁଏ। ପ୍ରତ୍ୟେକ କୀୱାର୍ଡ ସର୍ବାଧିକ 200 ଅକ୍ଷର ହୋଇପାରିବ; ଆରେର ଦୈର୍ଘ୍ୟ ପାଇଁ
କୌଣସି ସୀମା ନାହିଁ।

**⚠ ଭୁଲ୍-ପଜିଟିଭ୍ ବିପଦ — ନିର୍ଦ୍ଦିଷ୍ଟ ବାକ୍ୟାଂଶ ବାଛନ୍ତୁ।** ଚିହ୍ନଟ ପ୍ରକ୍ରିୟା ସମ୍ପୂର୍ଣ୍ଣ ରେସ୍ପନ୍ସ
ବଡିରେ ଏକ କଞ୍ଚା ଉପ-ଷ୍ଟ୍ରିଙ୍ଗ୍ ମେଳ, ଏବଂ ଏକ ମେଳ **ସ୍ଥାୟୀ** ଅଟେ (1-ବର୍ଷର କୁଲ୍ଡାଉନ୍,
ମାନୁଆଲ୍ ପୁନରୁଦ୍ଧାର)। ଏକ ବ୍ୟାପକ କୀୱାର୍ଡ ସମ୍ପୂର୍ଣ୍ଣ ସୁସ୍ଥ ସଂଯୋଗକୁ ମଧ୍ୟ ବ୍ୟାନ୍ କରିପାରେ:

- **ଖରାପ:** `quota`, `limit`, `error`, `denied` — ଅନେକ କ୍ଷଣସ୍ଥାୟୀ ତ୍ରୁଟିରେ ଦେଖାଯାଏ।
- **ଭଲ:** ସମ୍ପୂର୍ଣ୍ଣ ବ୍ୟାନ୍ ବାକ୍ୟ, ଯଥା `your account has been suspended for`,
  `account permanently banned`, `violation of our terms`।

ପ୍ରକୃତ ବ୍ୟାନ୍ ସମୟରେ ପ୍ରଦାନକାରୀ ଫେରାଉଥିବା ସବୁଠାରୁ ଦୀର୍ଘ ଓ ଅସନ୍ଦିଗ୍ଧ ବାକ୍ୟାଂଶକୁ ପ୍ରାଧାନ୍ୟ ଦିଅନ୍ତୁ। ସନ୍ଦେହ ଥିଲେ,
ପ୍ରଥମେ ସଂଯୋଗର `lastError` ଦେଖନ୍ତୁ, ତା’ପରେ ଠିକ୍ ସେହି ଶବ୍ଦବିନ୍ୟାସ ଯୋଡ଼ନ୍ତୁ।

## ଫ୍ଲାଗ୍ ହୋଇଥିବା ସଂଯୋଗକୁ ପୁନରୁଦ୍ଧାର କରିବା

ଟର୍ମିନାଲ୍ `banned` / `deactivated` ସ୍ଥିତିଗୁଡ଼ିକ **କେବେବି ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନରୁଦ୍ଧାର ହୁଏ ନାହିଁ** (ସେଗୁଡ଼ିକୁ
ପ୍ରୋଆକ୍ଟିଭ୍-ରିକଭରି ଟିକ୍ରୁ ବାଦ ଦିଆଯାଏ — କେବଳ `unavailable` କୁଲ୍ଡାଉନ୍ ନିଜେ
ପୁନରୁଦ୍ଧାର ହୁଏ)। ଜଣେ ଅପରେଟର୍ଙ୍କୁ ସେଗୁଡ଼ିକ ସ୍ପଷ୍ଟ ଭାବେ କ୍ଲିୟର୍ କରିବାକୁ ପଡ଼ିବ:

1. **ସଂଯୋଗକୁ ପୁନଃ ପରୀକ୍ଷା କରନ୍ତୁ** — ଡ୍ୟାସ୍ବୋର୍ଡର **Test** କାର୍ଯ୍ୟ
   (`POST /api/providers/{id}/test`); ଏକ ସଫଳ ପ୍ରୋବ୍ `testStatus` କୁ
   `active` ରେ ରିସେଟ୍ କରେ ଏବଂ ତ୍ରୁଟି ଫିଲ୍ଡଗୁଡ଼ିକୁ କ୍ଲିୟର୍ କରେ।
2. **ପୁନଃ ପ୍ରମାଣିତ କରନ୍ତୁ / କ୍ରେଡେନ୍ସିଆଲ୍ଗୁଡ଼ିକ ସମ୍ପାଦନା କରନ୍ତୁ** — OAuth ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ, ଲଗ୍ଇନ୍
   / ରିଫ୍ରେଶ୍ ପ୍ରବାହକୁ ପୁନଃ ଚଲାନ୍ତୁ; ପ୍ରଦାନକାରୀ create/import ରୁଟ୍ଗୁଡ଼ିକ `isActive = true` ସେଟ୍ କରନ୍ତି।
3. **ସଂଯୋଗକୁ ପୁନଃ ସକ୍ଷମ କରନ୍ତୁ** — ଯଦି ଅଟୋ-ଡିସେବଲ୍ `isActive = false` ସେଟ୍ କରିଥିଲା
   (`all` ପରିସର, କିମ୍ବା OAuth/cookie/session ସଂଯୋଗ ପାଇଁ `subscription`),
   ଆକାଉଣ୍ଟ ଠିକ୍ କରିବା ପରେ ଏହାକୁ ପୁନଃ ଅନ୍ କରନ୍ତୁ।

କୌଣସି ପୃଥକ "ବ୍ୟାନ୍ ଫ୍ଲାଗ୍ କ୍ଲିୟର୍ କରନ୍ତୁ" ବଟନ୍ ନାହିଁ — ପୁନରୁଦ୍ଧାରର ଅର୍ଥ ହେଉଛି ପୁନଃ ପରୀକ୍ଷା, ପୁନଃ ପ୍ରମାଣୀକରଣ, କିମ୍ବା
ପୁନଃ ସକ୍ଷମ କରିବା, ଯାହା
[RESILIENCE_GUIDE](../architecture/RESILIENCE_GUIDE.md) ର ସାଧାରଣ ଟର୍ମିନାଲ୍-ସ୍ଥିତି ନିୟମ ସହ ମେଳ ଖାଏ।

## ପ୍ରୋବ୍ ପୃଥକୀକରଣ (ମଡେଲ୍ test-all)

ଏକ **ପ୍ରୋବ୍-ମୂଳ ବିଫଳତା** (`runAsProbe` ଭିତରେ କାର୍ଯ୍ୟକାରୀ ହୋଇଥିବା ମଡେଲ୍ test-all / ସ୍ୱାସ୍ଥ୍ୟ-ଯାଞ୍ଚ ଡିସ୍ପ୍ୟାଚ୍)
କେବେବି ପୁଲ୍ରୁ କୌଣସି ସଂଯୋଗକୁ ଅପସାରଣ କରେ ନାହିଁ (#9817): ଏହା
**ଦୃଶ୍ୟମାନତା ପାଇଁ ରେକର୍ଡ କରାଯାଏ** (`last_error`, `last_error_type`, `error_code`,
`last_error_at`), କିନ୍ତୁ **ପ୍ରତ୍ୟେକ** ରାଉଟିଂ ପରିବର୍ତ୍ତନକୁ ଏଡ଼ାଇଯାଏ — କୁଲ୍ଡାଉନ୍, ଟର୍ମିନାଲ୍
ସ୍ଥିତି (`banned` / `deactivated` / `credits_exhausted`), ପ୍ରତି-ମଡେଲ୍ ଲକ୍ଆଉଟ୍,
ପ୍ରଦାନକାରୀ ସର୍କିଟ୍ ବ୍ରେକର୍, 5-ମିନିଟ୍ କୋଟା କ୍ୟାଶ୍, OAuth ଟୋକେନ୍ ରିଫ୍ରେଶ୍
ଏବଂ ଅଟୋ-ଡିସେବଲ୍। କେବଳ ପ୍ରକୃତ ଅନୁରୋଧ-ପଥ ବିଫଳତା ନିଷ୍କ୍ରିୟ କରେ। ରେକର୍ଡ ହୋଇଥିବା
ତ୍ରୁଟି ହିଁ ଫ୍ଲାଗ୍ ହୋଇଥିବା ଆକାଉଣ୍ଟକୁ ଟ୍ରାଫିକ୍ ସେବା ଜାରି ରଖିଥିବା ବେଳେ ଡ୍ୟାସ୍ବୋର୍ଡରେ ଦୃଶ୍ୟମାନ କରେ।

ଏକକ ନିଷ୍ପତ୍ତି ବିନ୍ଦୁ ହେଉଛି `shouldIsolateProbeFailures()`
(`src/shared/utils/probeOrigin.ts`), ଯାହାକୁ ପ୍ରୋବ୍-ମୂଳ ବିଫଳତାରୁ
ରାଉଟିଂ ସ୍ଥିତି ପରିବର୍ତ୍ତନ କରିପାରୁଥିବା **ପ୍ରତ୍ୟେକ** ସ୍ଥାନ ପରାମର୍ଶ କରେ:

- `markAccountUnavailable` (`auth.ts`) — କେବଳ ରେକର୍ଡ (`lastError` କଞ୍ଚା ଟେକ୍ସଟ୍,
  `lastErrorType`, `errorCode`, `lastErrorAt`; ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ **କୌଣସି**
  `backoffLevel` ନାହିଁ, କାରଣ ଏହା ଚୟନ-ସମୟର ଅଟୋ-ଡିକେ ଟ୍ରିଗର୍ କରି ରେକର୍ଡକୁ
  ମିଟାଇ ଦେବ)
- `maybeAutoDisableBannedAccount` — କୌଣସି ଅଟୋ-ଡିସେବଲ୍ ନାହିଁ
- `chatCore` — FORBIDDEN, ACCOUNT_DEACTIVATED, QUOTA_EXHAUSTED (କେବଳ ରେକର୍ଡ,
  କୌଣସି ଟର୍ମିନାଲ୍ `credits_exhausted` ନାହିଁ), GEO_BLOCKED (କୌଣସି 24h ବାଦ ନାହିଁ),
  MODEL_NOT_FOUND (କୌଣସି `lockModel` ନାହିଁ), codex 429 ଆକାଉଣ୍ଟ-ରୋଟେସନ୍ ଫେଲ୍ଓଭର୍
  (କୌଣସି `markCodexScopeRateLimited` ନାହିଁ, ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ `rate_limited_until` ନାହିଁ, କୌଣସି
  ସେସନ୍-ଆଫିନିଟି କ୍ଲିୟର୍ ନାହିଁ), `persistCodexQuotaState` (କୌଣସି କୋଟା-ସ୍ଥିତି ଲେଖା ନାହିଁ,
  କୌଣସି କ୍ୟାଶ୍ ଅବୈଧୀକରଣ ନାହିଁ), `recordKeyHealthStatus` (କୀ-ସ୍ୱାସ୍ଥ୍ୟ ରୋଟେଟର୍
  ଅପରିବର୍ତ୍ତିତ)
- OAuth ରିଫ୍ରେଶ୍ — ଏକ୍ଜିକ୍ୟୁଟର୍ ବେସ୍ରେ ଥିବା ପ୍ରୋଆକ୍ଟିଭ୍ ରିଫ୍ରେଶ୍
  (`base.ts` `execute()`, କୌଣସି ରିଫ୍ରେଶ୍-ଟୋକେନ୍ ରୋଟେସନ୍ ବ୍ୟବହୃତ ହୁଏ ନାହିଁ) ଏବଂ
  `chatCore` ରେ ଥିବା ରିଆକ୍ଟିଭ୍ 401/403 ପଥ (କୌଣସି `expired` ନିଷ୍କ୍ରିୟକରଣ ନାହିଁ), ଉଭୟ
- `chat.ts` — ପ୍ରଦାନକାରୀ ସର୍କିଟ୍ ବ୍ରେକର୍ ଏବଂ 5-ମିନିଟ୍ କୋଟା କ୍ୟାଶ୍
  (`markAccountExhaustedFrom429`) କେବେବି ଅବନତ ହୁଏ ନାହିଁ

ରେକର୍ଡ ହୋଇଥିବା ତ୍ରୁଟି ହିଁ ଫ୍ଲାଗ୍ ହୋଇଥିବା ଆକାଉଣ୍ଟକୁ ଟ୍ରାଫିକ୍ ସେବା ଜାରି ରଖିଥିବା ବେଳେ
ଡ୍ୟାସ୍ବୋର୍ଡରେ ଦୃଶ୍ୟମାନ କରେ। ଧ୍ୟାନ ଦିଅନ୍ତୁ: ପ୍ରୋବ୍ ରେକର୍ଡରେ **କଞ୍ଚା**
(କଟାଯାଇନଥିବା) ତ୍ରୁଟି ଟେକ୍ସଟ୍ ସଂରକ୍ଷିତ ହୁଏ, ଯାହା ପ୍ରକୃତ ପଥର `slice(0,100)` ଟ୍ରଙ୍କେସନ୍ଠାରୁ ଭିନ୍ନ।

ରକ୍ଷଣାବେକ୍ଷଣ ଉପକରଣ ଭାବେ test-all ବ୍ୟବହାର କରୁଥିବା ଅପରେଟର୍ମାନେ ନିମ୍ନୋକ୍ତ ଯେକୌଣସି ଉପାୟରେ
ପୂର୍ବ ବ୍ୟବହାର ପୁନଃସ୍ଥାପନ କରିପାରିବେ (ପ୍ରୋବ୍କୁ ପ୍ରକୃତ ଜେନେରେସନ୍ ଭାବେ ଗଣନା କରାଯିବ):

- `probeCanDisable` ସେଟିଂ (`POST /api/settings` ସହିତ
  `{"probeCanDisable": true}`, କିମ୍ବା ସିଧାସଳଖ `key_value` DB ସମ୍ପାଦନା), କିମ୍ବା
- ଫିଚର୍ ଫ୍ଲାଗ୍ **`PROBE_CAN_DISABLE=true`** (env କିମ୍ବା DB ଓଭର୍ରାଇଡ୍; ସେଟିଂ ଉପରେ
  ଏହାର ପ୍ରାଧାନ୍ୟ ରହେ)।

ଫେଲ୍-ସେଫ୍: ଫ୍ଲାଗ୍ କିମ୍ବା ସେଟିଂ ଲୁକ୍ଅପ୍ରେ ତ୍ରୁଟି ହେଲେ, ପୃଥକୀକରଣ ON ରହେ।
