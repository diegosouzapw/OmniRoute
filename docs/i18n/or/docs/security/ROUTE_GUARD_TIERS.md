## ସାରାଂଶ

ସମସ୍ତ OmniRoute ପରିଚାଳନା API ରୁଟ୍କୁ ତିନୋଟି ସୁରକ୍ଷା
ସ୍ତର ମଧ୍ୟରୁ ଗୋଟିଏରେ ବର୍ଗୀକୃତ କରାଯାଇଛି। ବର୍ଗୀକରଣ ସ୍ଥିର, ଯାହା `src/server/authz/routeGuard.ts`ରେ
ପରିଭାଷିତ ହୋଇଛି, ଏବଂ ଅନ୍ୟ କୌଣସି ପ୍ରମାଣୀକରଣ ଶାଖା ଚାଲିବା ପୂର୍ବରୁ ଏହାର ମୂଲ୍ୟାଙ୍କନ କରାଯାଏ।

## ସ୍ତରଗୁଡ଼ିକ

### ସ୍ତର 1 — LOCAL_ONLY

**ଏହା ଦ୍ୱାରା ବଳବତ୍ତର କରାଯାଏ:** `isLocalOnlyPath(path)` → ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ
**ବାଇପାସ୍:** ଡିଫଲ୍ଟ ଭାବେ କିଛି ନାହିଁ। `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ ଥିବା ପଥଗୁଡ଼ିକ ପାଇଁ ସୀମିତ ବ୍ୟତିକ୍ରମ ରହିଛି, ଯେତେବେଳେ ଅନୁରୋଧରେ `manage` ସ୍କୋପ୍ ସହିତ ଏକ ବୈଧ
API କୀ ଥାଏ ([ପରିଚାଳନା-ସ୍କୋପ୍ ବ୍ୟତିକ୍ରମ](#manage-scope-carve-out) ଦେଖନ୍ତୁ)।

ଏହି ରୁଟ୍ଗୁଡ଼ିକ ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ସୃଷ୍ଟି କରନ୍ତି କିମ୍ବା ରନ୍ଟାଇମ୍ କୋଡ୍ ନିଷ୍ପାଦନ କରନ୍ତି। ଏଗୁଡ଼ିକୁ
ନନ୍-ଲୁପ୍ବ୍ୟାକ୍ ଟ୍ରାଫିକ୍ ପାଇଁ ଉନ୍ମୁକ୍ତ କଲେ ଏକ ବୈଧ JWT ହାସଲ କରିଥିବା ଆକ୍ରମଣକାରୀ (ଉଦାହରଣ ସ୍ୱରୂପ,
Cloudflared/Ngrok ଟନେଲ୍ ମାଧ୍ୟମରେ) ପ୍ରୋସେସ୍ ସୃଷ୍ଟିକୁ ଟ୍ରିଗର୍ କରିପାରିବେ — ଏହା ଏକ ଜଣାଶୁଣା CVE
ଶ୍ରେଣୀ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))।

**GHSA-fhh6-4qxv-rpqj କ’ଣ (ଆକ୍ରମଣ ଶ୍ରେଣୀ):** ଏକ ପରିଚାଳନା/ଏଜେଣ୍ଟ ସର୍ଭର
ଏପରି ଏକ ଏଣ୍ଡପଏଣ୍ଟ ଉନ୍ମୁକ୍ତ କରେ ଯାହା ଏକ ସବ୍ପ୍ରୋସେସ୍ (`npm install`, `node`, ଏକ ବ୍ରାଉଜର୍,
ଏକ ପ୍ରକ୍ସି, `git`, `tar`, …) ଆରମ୍ଭ କରେ। ଯଦି ସେହି ଏଣ୍ଡପଏଣ୍ଟକୁ ହୋଷ୍ଟ ବାହାରୁ ପହଞ୍ଚିହୁଏ — କାରଣ
ଅପରେଟର୍ OmniRouteକୁ ଏକ nginx/Cloudflare/Tailscale ଟନେଲ୍ ପଛରେ ରଖିଥିଲେ ଏବଂ ଏକ JWT
ଲିକ୍ ହୋଇଥିଲା, କିମ୍ବା ପ୍ରମାଣୀକରଣ ଭୁଲ୍ ଭାବେ ବିନ୍ୟାସିତ ହୋଇଥିଲା — ତେବେ ଆକ୍ରମଣକାରୀ "ଏକ APIକୁ କଲ୍ କରିବା"କୁ "ହୋଷ୍ଟରେ ଏକ
କମାଣ୍ଡ ଚଲାଇବା"ରେ ପରିଣତ କରନ୍ତି (ରିମୋଟ୍ କୋଡ୍ ନିଷ୍ପାଦନ)। ପ୍ରତ୍ୟେକ
ପ୍ରୋସେସ୍-ସୃଷ୍ଟି-ସକ୍ଷମ ରୁଟ୍ରେ **କୌଣସି ପ୍ରମାଣୀକରଣ ଯାଞ୍ଚ ପୂର୍ବରୁ, ବିନା ସର୍ତ୍ତରେ ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ** ବଳବତ୍ତର କରି OmniRoute ଏହି ସମସ୍ୟାକୁ ରୋକେ: ଟନେଲ୍ ମାଧ୍ୟମରେ ଲିକ୍ ହୋଇଥିବା ଟୋକେନ୍ ମଧ୍ୟ ପ୍ରୋସେସ୍ ସୃଷ୍ଟି ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ।

**ସମ୍ପୂର୍ଣ୍ଣ LOCAL_ONLY ସେଟ୍।** ପ୍ରାମାଣିକ ଉତ୍ସ ହେଉଛି
`src/server/authz/routeGuard.ts`ରେ ଥିବା `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`;
ନିମ୍ନର ସାରଣୀ ବର୍ତ୍ତମାନର ସ୍ଥିତିକୁ ପ୍ରତିଫଳିତ କରେ। `check-route-guard-membership` ଗେଟ୍
ପ୍ରୋସେସ୍-ସୃଷ୍ଟି-ସକ୍ଷମ ପ୍ରିଫିକ୍ସଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା ପ୍ରତ୍ୟେକ `route.ts`କୁ ଗଣନା କରେ ଏବଂ କୌଣସିଟି ସ୍ଥାନୀୟ-ମାତ୍ର ଭାବେ ବର୍ଗୀକୃତ ନହୋଇଥିଲେ CIକୁ ବିଫଳ କରେ।

#### ଅପରେଟର୍ ମାର୍ଗଦର୍ଶନ ଏବଂ ଅଡିଟିଂ

ଯଦି ଆପଣ OmniRouteକୁ ଏକ reverse proxy କିମ୍ବା tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ପଛରେ ଚଳାନ୍ତି, ତେବେ loopback ଯାଞ୍ଚ ଉପରୋକ୍ତ spawn-capable
routeଗୁଡ଼ିକୁ ଏବେ ମଧ୍ୟ ସୁରକ୍ଷିତ ରଖେ — ଯେଉଁ ଅନୁରୋଧର client address non-loopback, ତାହାକୁ
**ପ୍ରମାଣୀକରଣ ଚାଲିବା ପୂର୍ବରୁ** `403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ, ତେଣୁ ଏକ leaked JWT
କୌଣସି spawn ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ। ଅପରେଟର୍ଙ୍କର ଦୁଇଟି ଦାୟିତ୍ୱ ରହିଛି:

- **client IPକୁ loopback ଭାବେ ଜାଲିଆତି କରି 403କୁ "ଠିକ୍" କରନ୍ତୁ ନାହିଁ।**
  `X-Forwarded-For: 127.0.0.1` ସେଟ୍ କରିବା, କିମ୍ବା source addressକୁ
  loopback ଭାବେ ପୁନଃଲିଖନ କରୁଥିବା proxy, ଏହି ସ୍ତର ବନ୍ଦ କରୁଥିବା ସେହି RCE ଶ୍ରେଣୀକୁ ପୁଣି ଖୋଲିଦିଏ।
  proxy ମାଧ୍ୟମରେ dashboard/APIକୁ ପ୍ରକାଶ କରନ୍ତୁ — spawn-capable routeଗୁଡ଼ିକୁ କେବେ ନୁହେଁ।
- **manage-scope bypassକୁ ସର୍ବନିମ୍ନ ରଖନ୍ତୁ।** କେବଳ `/api/mcp/` bypassଯୋଗ୍ୟ, ଏବଂ
  କେବଳ ଏକ `manage`-scoped API key ସହିତ। `SPAWN_CAPABLE_PREFIXES`କୁ କେବେ ମଧ୍ୟ
  bypass ତାଲିକାରେ ଯୋଡ଼ାଯାଇପାରିବ ନାହିଁ — zod schema ସେଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ ଏବଂ
  runtimeରେ `isLocalOnlyBypassableByManageScope` ସେଗୁଡ଼ିକୁ ଅସ୍ୱୀକାର କରେ (defence-in-depth),
  dashboardରେ "bypassଯୋଗ୍ୟ କରାଯାଇପାରିବ ନାହିଁ"ର ଅର୍ଥ ଏହା ହିଁ। `/api/providers/` ଅଧୀନରେ ଥିବା dynamic-segment
  ଏବଂ static-path spawn-capable routeଗୁଡ଼ିକ (ଯଥା `/login`,
  `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts`ର regex-ଆଧାରିତ `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` companion ଦ୍ୱାରା ଆବୃତ, flat
  `SPAWN_CAPABLE_PREFIXES` array ଦ୍ୱାରା ନୁହେଁ — ସେଗୁଡ଼ିକୁ ଧରିବା ପାଇଁ flat arrayକୁ
  ସମ୍ପୂର୍ଣ୍ଣ `/api/providers/` prefix ଆବୃତ କରିବାକୁ ପଡ଼ିବ, ଯାହା remote dashboardଗୁଡ଼ିକ provider CRUD ପାଇଁ ବୈଧ ଭାବେ ବ୍ୟବହାର କରୁଥିବା
  route treeକୁ ଅତ୍ୟଧିକ ବ୍ୟାପକ କରିଦେବ।

**ପ୍ରବେଶ ଅଡିଟିଂ** — off-hostରୁ କିଛି ମଧ୍ୟ ଏହି routeଗୁଡ଼ିକ ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚୁନାହିଁ ବୋଲି ଯାଞ୍ଚ କରିବା ପାଇଁ:

- `/dashboard/settings/security`ରେ **Authorization Inventory** ଖୋଲନ୍ତୁ: ଏହା ସକ୍ରିୟ LOCAL_ONLY ପ୍ରିଫିକ୍ସ ତାଲିକା, କେଉଁ ପ୍ରିଫିକ୍ସଗୁଡ଼ିକୁ ବାଇପାସ୍ କରାଯାଇପାରିବ, ଏବଂ କମ୍ପାଇଲ୍-ସମୟରେ ନିର୍ଦ୍ଧାରିତ spawn-ସକ୍ଷମ ("ବାଇପାସ୍ଯୋଗ୍ୟ କରାଯାଇପାରିବ ନାହିଁ") ସେଟ୍ ପ୍ରଦର୍ଶନ କରେ।
- ଉପରୋକ୍ତ ପ୍ରିଫିକ୍ସଗୁଡ଼ିକୁ ଏକ non-loopback କ୍ଲାଏଣ୍ଟ ଠିକଣା ସହ ଯୋଡ଼ି ଆପଣଙ୍କ reverse-proxy / access ଲଗ୍ଗୁଡ଼ିକରେ Grep କରନ୍ତୁ। ଏପରି କୌଣସି ହିଟ୍ `403 LOCAL_ONLY` ପରିବର୍ତ୍ତେ `200` ଫେରାଇଥିଲେ, ତାହାର ଅର୍ଥ proxy ପ୍ରକୃତ କ୍ଲାଏଣ୍ଟ IPକୁ ଲୁଚାଉଛି — proxyକୁ ଠିକ୍ କରନ୍ତୁ।
- ଏହି ପଥଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସି ଗୋଟିଏ ପାଇଁ OmniRouteର ଲଗ୍ରେ ଥିବା `403 LOCAL_ONLY`ର ଅର୍ଥ guard ଉଦ୍ଦିଷ୍ଟ ଭାବେ କାମ କରୁଛି; ଏହା ଦମନ କରିବାକୁ ଥିବା କୌଣସି ତ୍ରୁଟି ନୁହେଁ।

**ଏହା ଦ୍ୱାରା ବାଧ୍ୟତାମୂଳକ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ବାଇପାସ୍କୁ ଏଡ଼ାଇଯାଏ
**ବାଇପାସ୍:** `requireLogin=false` ଥିବାବେଳେ କିଛି ନାହିଁ; JWT ସର୍ବଦା ଆବଶ୍ୟକ

ଏହି ରୁଟ୍ଗୁଡ଼ିକ ବିନାଶକାରୀ କିମ୍ବା ଅପରିବର୍ତ୍ତନୀୟ। ଏକ "no-password"
ଇନ୍ଷ୍ଟଲେସନ୍ରେ ଏଗୁଡ଼ିକୁ ଅନୁମତି ଦେବାର ଅର୍ଥ ହେବ, ସମାନ LANରେ ଥିବା ଯେକୌଣସି ବ୍ୟକ୍ତି databaseକୁ ସମ୍ପୂର୍ଣ୍ଣ ପୋଛିଦେଇପାରିବେ କିମ୍ବା
server processକୁ ବନ୍ଦ କରିପାରିବେ।

| ପଥ                                        | କାରଣ                                                               |
| ----------------------------------------- | ------------------------------------------------------------------ |

**ଉଲ୍ଲଂଘନରେ ପ୍ରତିକ୍ରିୟା:** `401 Authentication required`

କଲ୍କାରୀଙ୍କ ଦ୍ୱାରା ବଛାଯାଇଥିବା root ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରେ
ଏବଂ ସଦ୍ୟ ଜାରି ହୋଇଥିବା Basic ପରିଚୟପତ୍ରଗୁଡ଼ିକୁ ପୁନର୍ବାର ଫେରାଏ, `DELETE` ସେଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରେ, ଏବଂ parent `POST`
Obsidian REST API tokenକୁ ସଂରକ୍ଷଣ କରେ। GHSA-62vw କେବଳ `GET` password ପ୍ରକାଶକୁ ଲୁଚାଇଥିଲା; ପରିଚୟପତ୍ର ଜାରିକରଣ
ତଥାପି fail-open ସ୍ତରରେ ଥିଲା (GHSA-7pq4-8pvv-rx7r)। `enableObsidianVaultSync()` ଅତିରିକ୍ତ ଭାବେ
data directory ହୋଇଥିବା, ତାହାର ଭିତରେ ଅବସ୍ଥିତ, କିମ୍ବା ତାହାକୁ ଧାରଣ କରିଥିବା vaultକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

### ନୂତନ ଇନ୍ଷ୍ଟଲେସନ୍ର bootstrap କେବଳ loopback ପାଇଁ — `Host` ନୁହେଁ, ପ୍ରକୃତ peer ଆଧାରରେ

କୌଣସି management password ବିନ୍ୟାସ କରାଯାଇନଥିଲେ (ଏବଂ `INITIAL_PASSWORD` ନଥିଲେ),
`src/shared/utils/apiAuth.ts`ରେ ଥିବା `isAuthRequired()` ଅଜ୍ଞାତ bootstrapକୁ **କେବଳ loopback peerମାନଙ୍କ ପାଇଁ** ଖୋଲା ରଖେ।
ବିଶ୍ୱସ୍ତ peer signalଗୁଡ଼ିକ ଆଧାରରେ ନିମ୍ନ କ୍ରମରେ loopback ନିର୍ଦ୍ଧାରଣ କରାଯାଏ: token-stamped ପ୍ରକୃତ TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy ଯାହା ଦେଖେ), pipelineର ନିଜସ୍ୱ
`AUTHZ_HEADER_PEER_LOCALITY` ନିଷ୍ପତ୍ତି (route handlerଗୁଡ଼ିକ ଯାହା ଦେଖନ୍ତି, କେବଳ
`OMNIROUTE_PEER_STAMP_TOKEN` ସେଟ୍ ଥିବାବେଳେ ବିଶ୍ୱସ୍ତ), କିମ୍ବା ପ୍ରତ୍ୟକ୍ଷ କଲ୍କାରୀଙ୍କ ପାଇଁ ପ୍ରକୃତ socket peer। `Host` /
`nextUrl.hostname`କୁ କେବେ ବି ବିଚାର କରାଯାଏ ନାହିଁ, ଏବଂ ପ୍ରଥମ password write
(`POST /api/settings/require-login`) ପ୍ରତ୍ୟେକ network peer ପାଇଁ ଖୋଲା ରହିବା ପରିବର୍ତ୍ତେ ସମାନ
ପ୍ରତିବନ୍ଧକ ଅଧୀନରେ ରହେ (GHSA-7pq4-8pvv-rx7r)। `managementPolicy` ନିଜର `peerContext` ନିଷ୍ପତ୍ତିକୁ
ସ୍ପଷ୍ଟ ଭାବରେ ତଳକୁ ପଠାଏ, ଯାହାଦ୍ୱାରା ORIGINAL (pre-strip) requestର headerଗୁଡ଼ିକ ଏହା ନିର୍ଦ୍ଧାରଣ କରନ୍ତି ନାହିଁ।

### ସ୍ତର 3 — MANAGEMENT (ଡିଫଲ୍ଟ)

ଅନ୍ୟ ସମସ୍ତ management route। `requireLogin=false` ବିନ୍ୟାସ କରାଯାଇନଥିଲେ auth ଆବଶ୍ୟକ।
CLI tokenଗୁଡ଼ିକ ଏହି routeଗୁଡ଼ିକୁ ପ୍ରମାଣୀକୃତ କରିପାରିବେ (loopback + ବୈଧ HMAC)।

## ମୂଲ୍ୟାଙ୍କନ କ୍ରମ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ପରବର୍ତ୍ତୀ ପଦକ୍ଷେପକୁ ଯାଆନ୍ତୁ
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → ଅନ୍ୟଥା                                    → 403 LOCAL_ONLY ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  2. isInternalModelSyncRequest(ctx)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (system)
  3. hasValidCliToken(headers)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (cli) [loopback + timingSafeEqual HMAC ଯାଞ୍ଚ]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ଅନୁମତି ଦିଅନ୍ତୁ (dashboard_session)
     → bypass କରିହେଉ ନଥିବା ପଥରେ manage-scope Bearer?
        → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → 401/403 ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  5. requireLogin=false?
     → ଅନୁମତି ଦିଅନ୍ତୁ (anonymous)
```

ପଦକ୍ଷେପ 1ର manage-scope ଶାଖା ହେଉଛି ଏକମାତ୍ର ପ୍ରମାଣୀକୃତ ପଥ ଯାହା ଏକ
LOCAL_ONLY ରୁଟ୍କୁ ସନ୍ତୁଷ୍ଟ କରିପାରେ; auth-backend ବିଫଳତା ମୋଡ୍ 503 ଫେରାଏ
(403 ନୁହେଁ), ଯାହାଫଳରେ ଏକ ମିଆଦ ଶେଷ ହୋଇଥିବା DB ନିରବରେ "deny"କୁ
ଡାଉନ୍ଗ୍ରେଡ୍ ହୁଏ ନାହିଁ।

## ଏକ ନୂତନ spawn-ସକ୍ଷମ ରୁଟ୍ ଯୋଡ଼ିବା

1. ପଥ ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_API_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
2. `tests/unit/authz/routeGuard.test.ts`ରେ ଏକ ପରୀକ୍ଷା ଯୋଡ଼ନ୍ତୁ, ଯାହା ନୂତନ
   ପ୍ରିଫିକ୍ସ ପାଇଁ `isLocalOnlyPath()` true ଫେରାଉଥିବା ନିଶ୍ଚିତ କରେ
3. **ଏହି ପଦକ୍ଷେପକୁ କେବେବି ଏଡ଼ାନ୍ତୁ ନାହିଁ** — `CLAUDE.md`ର କଠୋର ନିୟମ #15 ଦେଖନ୍ତୁ
4. ନିଷ୍ପତ୍ତି ନିଅନ୍ତୁ: ଏହି ରୁଟ୍ଟି କ’ଣ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ
   ମଧ୍ୟ ରହିବା ଉଚିତ? ଡିଫଲ୍ଟ ଉତ୍ତର ହେଉଛି **ନା**। କେବଳ ସେତେବେଳେ opt-in କରନ୍ତୁ,
   ଯେତେବେଳେ ରୁଟ୍ଟିକୁ ଏକ manage-scope ଧାରକଙ୍କ ପାଇଁ ଉନ୍ମୁକ୍ତ କରିବା ସୁରକ୍ଷିତ
   (ଅର୍ଥାତ୍, ଏହା ଇଚ୍ଛାମତେ ବ୍ୟବହାରକାରୀ-ନିୟନ୍ତ୍ରିତ କୋଡ୍ spawn କରେ **ନାହିଁ**)।

## ଏକ manage-scope-bypassable ପଥ ଯୋଡ଼ିବା

1. ରୁଟ୍ଟି ବ୍ୟବହାରକାରୀ-ପ୍ରଦତ୍ତ କୋଡ୍ କିମ୍ବା କମାଣ୍ଡ ଚାଲୁ କରେ ନାହିଁ ବୋଲି
   ନିଶ୍ଚିତ କରନ୍ତୁ। ଯଦି କରେ, ଅଟକି ଯାଆନ୍ତୁ — ଏହି ବ୍ୟତିକ୍ରମ ଏଥିପାଇଁ ଉପଯୁକ୍ତ
   ଉପକରଣ ନୁହେଁ।
2. ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
3. ସମସ୍ତ ଚାରିଟି ଅନୁରୋଧ ରୂପ ପାଇଁ `tests/unit/authz/management-policy.test.ts`ରେ
   କଭରେଜ୍ ଯୋଡ଼ନ୍ତୁ: Bearer ନାହିଁ (403), manage Bearer (ଅନୁମତି), non-manage Bearer
   (403), ଏବଂ manage Bearer ଥିଲେ ମଧ୍ୟ `/api/cli-tools/runtime/*`
   strict-loopback ରହୁଥିବା ପ୍ରତି-ପ୍ରିଫିକ୍ସ ରିଗ୍ରେସନ୍।

ତାହା ସହିତ ସମନ୍ୱିତ କରିବା — ପ୍ରବର୍ତ୍ତନ ଲଜିକ୍ ମଧ୍ୟ କାର୍ଯ୍ୟକାରୀ ନକରି କେବଳ
`routeGuard.ts`ରେ ରୁଟ୍ ଯୋଡ଼ିବା ନୁହେଁ।
