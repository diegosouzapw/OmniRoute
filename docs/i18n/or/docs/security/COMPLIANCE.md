OmniRoute ପ୍ରଶାସନିକ କାର୍ଯ୍ୟ, ପ୍ରମାଣୀକରଣ ଘଟଣା, ପ୍ରଦାତା
ପରିଚୟପତ୍ର ଜୀବନଚକ୍ର ପରିବର୍ତ୍ତନ ଏବଂ MCP ଟୁଲ୍ ଆହ୍ୱାନଗୁଡ଼ିକୁ SQLite-ସମର୍ଥିତ ଅଡିଟ୍
ଟେବୁଲ୍ଗୁଡ଼ିକରେ ରେକର୍ଡ କରେ। ଏହି ପୃଷ୍ଠାରେ କେଉଁ ତଥ୍ୟ ଲଗ୍ ହୁଏ, ତାହା କେଉଁଠି ରହେ, କେତେ ସମୟ ପର୍ଯ୍ୟନ୍ତ
ସଂରକ୍ଷିତ ହୁଏ, API କୀଗୁଡ଼ିକ କିପରି ଏଥିରୁ ବାଦ ପଡ଼ିପାରିବେ ଏବଂ ତଥ୍ୟକୁ କିପରି କ୍ୱେରି କରିବେ, ତାହା ବର୍ଣ୍ଣନା କରାଯାଇଛି।

କାର୍ଯ୍ୟାନ୍ୱୟନଟି `src/lib/compliance/index.ts` (T-43 — "ଅନୁପାଳନ
ନିୟନ୍ତ୍ରଣ") ଏବଂ `src/lib/compliance/providerAudit.ts`ରେ ରହିଛି। ଅଡିଟ୍ ଲେଖନ କେବେ ମଧ୍ୟ ତ୍ରୁଟି ଉତ୍କ୍ଷେପ କରେନାହିଁ:
କୌଣସି ବିଫଳତା ହେଲେ କଲ୍ଟିକୁ ନିରବରେ ଅଣଦେଖା କରାଯାଏ, ଯାହାଦ୍ୱାରା ଅଡିଟ୍ ଲଗିଂ ମୁଖ୍ୟ
ଅନୁରୋଧ ପ୍ରବାହକୁ ବାଧା ଦେଇପାରିବ ନାହିଁ।

## କ’ଣ ଲଗ୍ ହୁଏ

### ପ୍ରଶାସନିକ ଅଡିଟ୍ ଘଟଣା (`audit_log`)

`logAuditEvent({ action, actor, target, details, ... })`କୁ ପ୍ରତ୍ୟେକ କଲ୍
ଗୋଟିଏ ଧାଡ଼ି ସୃଷ୍ଟି କରେ। କାର୍ଯ୍ୟ ଷ୍ଟ୍ରିଙ୍ଗଗୁଡ଼ିକ ଏକ `domain.verb` (କିମ୍ବା `domain.verb.outcome`)
ଢାଞ୍ଚା ଅନୁସରଣ କରେ। କୋଡ୍ବେସ୍ରେ ସୁନିଶ୍ଚିତ ହୋଇଥିବା କାର୍ଯ୍ୟ ପ୍ରକାରଗୁଡ଼ିକ ହେଲା:

| କାର୍ଯ୍ୟ                              | ଉତ୍ସ                                    |
| ------------------------------------ | --------------------------------------- |
| `auth.login.success`                 | `src/app/api/auth/login/route.ts`       |
| `auth.login.failed`                  | `src/app/api/auth/login/route.ts`       |
| `auth.login.locked`                  | `src/app/api/auth/login/route.ts`       |
| `auth.login.error`                   | `src/app/api/auth/login/route.ts`       |
| `auth.login.misconfigured`           | `src/app/api/auth/login/route.ts`       |
| `auth.login.setup_required`          | `src/app/api/auth/login/route.ts`       |
| `auth.logout.success`                | `src/app/api/auth/logout/route.ts`      |
| `provider.credentials.created`       | `src/app/api/providers/route.ts`        |
| `provider.credentials.updated`       | `src/app/api/providers/[id]/route.ts`   |
| `provider.credentials.revoked`       | `src/app/api/providers/[id]/route.ts`   |
| `provider.credentials.batch_revoked` | `src/app/api/providers/route.ts`        |
| `sync.token.created`                 | `src/app/api/sync/tokens/route.ts`      |
| `sync.token.revoked`                 | `src/app/api/sync/tokens/[id]/route.ts` |
| `compliance.cleanup`                 | `src/lib/compliance/index.ts`           |

ପ୍ରତ୍ୟେକ ଏଣ୍ଟ୍ରି `action`, `actor` (ଡିଫଲ୍ଟ ଭାବେ `"system"`), `target`,
`details`/`metadata` (JSON), `ip_address`, `resource_type`, `status`,
`request_id` ଏବଂ `timestamp`କୁ ସଂଗ୍ରହ କରେ। ସମ୍ବେଦନଶୀଳ କୀଗୁଡ଼ିକ (`apiKey`, `accessToken`,
`refreshToken`, `password`, `*token`/`*secret`/`*apikey` ସହ ମେଳ ଖାଉଥିବା ଯେକୌଣସି କୀ,
ଇତ୍ୟାଦି) ଧାଡ଼ିଟି ଲେଖାଯିବା ପୂର୍ବରୁ ପୁନରାବୃତ୍ତିମୂଳକ ଭାବେ `"[redacted]"` ଦ୍ୱାରା ଲୁଚାଇ ଦିଆଯାଏ।

### ଅନୁରୋଧ / ବ୍ୟବହାର ଲଗ୍ଗୁଡ଼ିକ

ଏଗୁଡ଼ିକ କାର୍ଯ୍ୟକ୍ଷମ ଟେଲିମେଟ୍ରି (କଠୋର ଭାବେ ପ୍ରଶାସନିକ ଅଡିଟ୍ ନୁହେଁ), କିନ୍ତୁ ସମାନ
ସଂରକ୍ଷଣ ପାଇପ୍ଲାଇନ୍ ବ୍ୟବହାର କରନ୍ତି:

- `usage_history` — ପ୍ରତ୍ୟେକ ଅନୁରୋଧର ବ୍ୟବହାର ସାରାଂଶ
- `call_logs` — ପ୍ରତ୍ୟେକ ଅନୁରୋଧର ସମ୍ପୂର୍ଣ୍ଣ ଲଗ୍ (ଧାଡ଼ି ସୀମା ଅଧୀନରେ, ନିମ୍ନରେ ଦେଖନ୍ତୁ)
- `proxy_logs` — ପ୍ରକ୍ସି ଟ୍ରାଫିକ୍ ଲଗ୍ (ଧାଡ଼ି ସୀମା ଅଧୀନରେ)
- `request_detail_logs` — ପୁରୁଣା ବିସ୍ତୃତ ଅନୁରୋଧ ଲଗ୍ (ଉପସ୍ଥିତ ଥିଲେ ଏବେ ମଧ୍ୟ ଛାଟି ଦିଆଯାଏ)

## ସ୍ଟୋରେଜ୍ ସ୍କିମା

ପ୍ରଥମ ବ୍ୟବହାର ସମୟରେ `ensureAuditLogSchema()` ଦ୍ୱାରା `audit_log` ଆବଶ୍ୟକତା ଅନୁଯାୟୀ ସୃଷ୍ଟି କରାଯାଏ:

```sql
CREATE TABLE IF NOT EXISTS audit_log (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  timestamp     TEXT NOT NULL DEFAULT (datetime('now')),
  action        TEXT NOT NULL,
  actor         TEXT NOT NULL DEFAULT 'system',
  target        TEXT,
  details       TEXT,
  ip_address    TEXT,
  resource_type TEXT,
  status        TEXT,
  request_id    TEXT,
  metadata      TEXT
);
```

`timestamp`, `action`, `actor`, `resource_type`, `status`, ଏବଂ `request_id` ଉପରେ ଇଣ୍ଡେକ୍ସ ସୃଷ୍ଟି କରାଯାଏ। ପୁରୁଣା DBଗୁଡ଼ିକରେ ଅନୁପସ୍ଥିତ କଲମଗୁଡ଼ିକୁ ଆବଶ୍ୟକତା ଅନୁଯାୟୀ `ALTER TABLE` ମାଧ୍ୟମରେ ଯୋଡ଼ାଯାଏ।

## ଧାରଣ ଅବଧି ଏବଂ ସଫେଇ

ଦୁଇଟି ପୃଥକ ଧାରଣ ଅବଧିକୁ ପାଳନ କରାଯାଏ:

| ପରିବେଶ ଭେରିଏବଲ୍             | ଡିଫଲ୍ଟ   | ଯେଉଁଥିରେ ପ୍ରୟୋଗ ହୁଏ                                               |
| --------------------------- | -------- | ----------------------------------------------------------------- |
| `APP_LOG_RETENTION_DAYS`    | `7`      | `audit_log`, `mcp_tool_audit`                                     |
| `CALL_LOG_RETENTION_DAYS`   | `7`      | `usage_history`, `call_logs`, `proxy_logs`, `request_detail_logs` |
| `CALL_LOGS_TABLE_MAX_ROWS`  | `100000` | `call_logs` ପାଇଁ ଧାଡ଼ି-ସୀମା ଛାଟ                                   |
| `PROXY_LOGS_TABLE_MAX_ROWS` | `100000` | `proxy_logs` ପାଇଁ ଧାଡ଼ି-ସୀମା ଛାଟ                                  |

`cleanupExpiredLogs()` ଧାରଣ ଅବଧି ପାସ୍ ଚଲାଏ। ସର୍ଭର ଆରମ୍ଭ ସମୟରେ `src/instrumentation-node.ts` ରୁ ଏହାକୁ ଆହ୍ୱାନ କରାଯାଏ। ପ୍ରତ୍ୟେକ ଚାଳନା, ପ୍ରତି-ଟେବୁଲ୍ ବିଲୋପ ସଂଖ୍ୟା ସହିତ ଗୋଟିଏ `compliance.cleanup` ଅଡିଟ୍ ଇଭେଣ୍ଟ୍ ଲଗ୍ କରେ। ଦୀର୍ଘସ୍ଥାୟୀ ରାଇଟ୍ ଲକ୍ ଏଡ଼ାଇବା ପାଇଁ ପ୍ରକ୍ସି/କଲ୍ ଲଗ୍ ଛାଟକୁ ବ୍ୟାଚ୍ରେ (`BATCH_SIZE = 5000`) କରାଯାଏ।

ମାନୁଆଲ୍ ରିକ୍ୱେଷ୍ଟ୍-ହିଷ୍ଟ୍ରି ସଫେଇ ଧାରଣ ଅବଧିଠାରୁ ପୃଥକ। ରିକ୍ୱେଷ୍ଟ୍ ଲଗ୍ସ ପୃଷ୍ଠା `POST /api/settings/purge-request-history` କୁ କଲ୍ କରେ, ଯାହା `call_logs`, ପୁରୁଣା `request_detail_logs`, ଏବଂ `${DATA_DIR}/call_logs/` ଅଧୀନରେ ଥିବା ସ୍ଥାନୀୟ ରିକ୍ୱେଷ୍ଟ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟଗୁଡ଼ିକୁ ବିଲୋପ କରେ।

ଡିଫଲ୍ଟଗୁଡ଼ିକ `src/lib/logEnv.ts` ରେ ପରିଭାଷିତ ହୋଇଛି
(`DEFAULT_APP_LOG_RETENTION_DAYS = 7`, `DEFAULT_CALL_LOG_RETENTION_DAYS = 7`)।

## `noLog` ଅପ୍ଟ-ଆଉଟ୍ (ପ୍ରତି API କୀ)

API କୀଗୁଡ଼ିକୁ ଏପରି ଫ୍ଲାଗ୍ କରାଯାଇପାରେ, ଯାହାଦ୍ୱାରା ସେମାନଙ୍କର ଡାଉନ୍ଷ୍ଟ୍ରିମ୍ କଲ୍ ଟ୍ରାଫିକ୍ ଲଗ୍ କରାଯିବ ନାହିଁ। ଫ୍ଲାଗ୍ଟି `api_keys` ଟେବୁଲ୍ରେ (`no_log INTEGER DEFAULT 0`) ରହେ ଏବଂ ହଟ୍-ପାଥ୍ ଲୁକ୍ଅପ୍ ପାଇଁ ଏକ ଇନ୍-ମେମୋରି ସେଟ୍ରେ ଏହାର ପ୍ରତିରୂପ ରଖାଯାଏ।

```bash
# ଏକ ନୋ-ଲଗ୍ କୀ ସୃଷ୍ଟି କରନ୍ତୁ (ପରିଚାଳନା ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ)
curl -X POST http://localhost:20128/api/keys \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"name": "Privacy key", "noLog": true}'
```

ସହାୟକଗୁଡ଼ିକ (`src/lib/compliance/index.ts`):

- `setNoLog(apiKeyId, true|false)` — ଇନ୍-ମେମୋରି ଏଣ୍ଟ୍ରିକୁ ଟୋଗଲ୍ କରେ
- `isNoLog(apiKeyId)` — ରିକ୍ୱେଷ୍ଟ୍ ପାଥ୍ରେ ଯାଞ୍ଚ କରାଯାଏ; ବିଫଳ ହେଲେ `api_keys.no_log` ରୁ 30 s ପାଇଁ କ୍ୟାଶ୍ ହୋଇଥିବା ରିଡ୍ ବ୍ୟବହାର କରେ
- `NO_LOG_API_KEY_IDS` (ପରିବେଶ ଭେରିଏବଲ୍, କମା-ପୃଥକ) — ବୁଟ୍ ସମୟରେ ଇନ୍-ମେମୋରି ସେଟ୍ରେ ପୂର୍ବରୁ ଲୋଡ୍ କରାଯାଏ; ଯେତେବେଳେ ଆପଣ ସିଧାସଳଖ କଲମ୍କୁ ଟୋଗଲ୍ କରିପାରନ୍ତି ନାହିଁ, ସେତେବେଳେ ଉପଯୋଗୀ

ପ୍ରଶାସନିକ ଅଡିଟ୍ ଇଭେଣ୍ଟଗୁଡ଼ିକ (ଲଗ୍ଇନ୍, ପ୍ରଦାନକାରୀ ପରିବର୍ତ୍ତନ, MCP ଟୁଲ୍ କଲ୍ ଇତ୍ୟାଦି) `noLog` ଦ୍ୱାରା **ପ୍ରଭାବିତ ହୁଏ ନାହିଁ** — କେବଳ ପ୍ରତି-ରିକ୍ୱେଷ୍ଟ୍ ଟ୍ରାଫିକ୍ ଲଗିଂରୁ ଅପ୍ଟ-ଆଉଟ୍ କରାଯାଏ।

SQLite ଡାଟାବେସ୍କୁ ସିଧାସଳଖ କ୍ୱେରି କରନ୍ତୁ।

### `/api/compliance/audit-log` କ୍ୱେରି କରିବା

ସମର୍ଥିତ କ୍ୱେରି ପାରାମିଟରଗୁଡ଼ିକ (ସମସ୍ତ ଇଚ୍ଛାଧୀନ, ଟେକ୍ସଟ୍ ଫିଲ୍ଟର ପାଇଁ ସମସ୍ତେ
`LIKE %value%` ମେଳକ ବ୍ୟବହାର କରନ୍ତି):

- `action`, `actor`, `target`, `resourceType` (କିମ୍ବା `resource_type`),
  `status`, `requestId` (କିମ୍ବା `request_id`)
- `from` / `since`, `to` / `until` — ISO ଟାଇମ୍ଷ୍ଟାମ୍ପ
- `limit` (ଡିଫଲ୍ଟ `50`, ସର୍ବନିମ୍ନ `1`, ସର୍ବାଧିକ `500`)
- `offset` (ଡିଫଲ୍ଟ `0`, ସର୍ବାଧିକ `10_000`)

ପ୍ରତିକ୍ରିୟାଟି ଏକ JSON ଆରେ। ପୃଷ୍ଠାଙ୍କନ ମେଟାଡାଟା ହେଡର୍ଗୁଡ଼ିକରେ ଫେରାଯାଏ:
`x-total-count`, `x-page-limit`, `x-page-offset`।

```bash
curl "http://localhost:20128/api/compliance/audit-log?action=provider.credentials&from=2026-05-01" \
  -H "Cookie: auth_token=..."
```

## ଡ୍ୟାସବୋର୍ଡ

ଡ୍ୟାସବୋର୍ଡ **`/dashboard/audit`** ଠାରେ ଅଡିଟ୍ ଡାଟା ଉପଲବ୍ଧ କରାଏ
(`src/app/(dashboard)/dashboard/audit/page.tsx`)। ପୃଷ୍ଠାରେ ଦୁଇଟି ଟ୍ୟାବ୍ ଅଛି:

- **ଅନୁପାଳନ** (`ComplianceTab.tsx`) — `/api/compliance/audit-log`ରୁ ଆଡମିନ୍ ଅଡିଟ୍ ଇଭେଣ୍ଟଗୁଡ଼ିକ।
  ଇଭେଣ୍ଟ ପ୍ରକାର, ଗମ୍ଭୀରତା (ସୂଚନା / ଚେତାବନୀ / ଗୁରୁତର, କାର୍ଯ୍ୟ + ସ୍ଥିତିରୁ
  ନିର୍ଦ୍ଧାରିତ), ଏବଂ ତାରିଖ ପରିସର ଅନୁଯାୟୀ ଫିଲ୍ଟର କରେ। କାର୍ଯ୍ୟ/ସ୍ଥିତି ଷ୍ଟ୍ରିଙ୍ଗରୁ
  କ୍ଲାଏଣ୍ଟ ପାର୍ଶ୍ୱରେ ଗମ୍ଭୀରତା ଗଣନା କରାଯାଏ।
- **MCP** (`McpAuditTab.tsx`) — `/api/mcp/audit`ରୁ MCP ଟୁଲ୍ ଅଡିଟ୍, ଯେଉଁଥିରେ
  ଟୁଲ୍ ନାମ ଏବଂ ସଫଳତା/ବିଫଳତା ଅନୁଯାୟୀ ଫିଲ୍ଟର ରହିଛି।

ଉଭୟ ଟ୍ୟାବ୍ ଯଥାକ୍ରମେ `50` (ଅନୁପାଳନ) ଏବଂ `25` (MCP) ପୃଷ୍ଠା ଆକାର ସହିତ
ପୃଷ୍ଠାଙ୍କନ କରନ୍ତି।

## ପ୍ରଦାତା କ୍ରେଡେନ୍ସିଆଲ୍ ସହାୟକଗୁଡ଼ିକ

`src/lib/compliance/providerAudit.ts` ପ୍ରଦାତା-ପରିଚାଳନା ରୁଟ୍ଗୁଡ଼ିକ କ୍ରେଡେନ୍ସିଆଲ୍ ଇଭେଣ୍ଟ
ନିର୍ଗତ କରିବାବେଳେ ବ୍ୟବହାର କରୁଥିବା ଆକୃତିକରଣ ସହାୟକଗୁଡ଼ିକ ପ୍ରଦାନ କରେ:

- `summarizeProviderConnectionForAudit(connection)` — ସଂଯୋଗ ସ୍ନାପ୍ଶଟ୍ଟି
  `details`ରେ ଲେଖାଯିବା ପୂର୍ବରୁ `apiKey`, `accessToken`, `refreshToken`, `idToken`, ଏବଂ
  `providerSpecificData.consoleApiKey`କୁ କାଢ଼ିଦିଏ।
- `getProviderAuditTarget(connection)` — `target` ଫିଲ୍ଡ ପାଇଁ ଏକ ସ୍ଥିର
  `"<provider>:<name|id>"` ଷ୍ଟ୍ରିଙ୍ଗ ଗଠନ କରେ।
- `extractProviderWarnings(...payloads)` — ନୀତି/ସୁରକ୍ଷା ଚେତାବନୀ
  (`[sanitizer]`, `prompt injection detected`, `content has been filtered`,
  `safety filter`, `policy violation`) ପାଇଁ ପ୍ରଦାତା ପ୍ରତିକ୍ରିୟାଗୁଡ଼ିକୁ ସ୍କାନ୍ କରେ ଏବଂ
  ସର୍ବାଧିକ 5ଟି ମେଳ ଦେଖାଏ, ପ୍ରତ୍ୟେକକୁ 400ଟି ଅକ୍ଷରରେ ସୀମିତ କରେ।

## ସର୍ବୋତ୍ତମ ଅଭ୍ୟାସଗୁଡ଼ିକ

- PII (ଆଇନଗତ, ଚିକିତ୍ସାଗତ ଇତ୍ୟାଦି) ପରିଚାଳନା କରୁଥିବା API କୀଗୁଡ଼ିକୁ `noLog: true` ସହିତ ଚିହ୍ନିତ କରନ୍ତୁ।
- ଆପଣଙ୍କର ସଂରକ୍ଷଣ ନୀତି ପୂରଣ କରିବା ପାଇଁ `APP_LOG_RETENTION_DAYS` /
  `CALL_LOG_RETENTION_DAYS` ସମନ୍ୱୟ କରନ୍ତୁ। 7-ଦିନର ଡିଫଲ୍ଟଗୁଡ଼ିକ ସତର୍କତାମୂଳକ।
- ଆପଣଙ୍କ ଅନୁପାଳନ କାର୍ଯ୍ୟକ୍ରମ ଆବଶ୍ୟକ କରୁଥିବା ଯେକୌଣସି ବ୍ୟବଧାନରେ ଅଡିଟ୍ ଟେବୁଲ୍କୁ
  ପ୍ଲାଟଫର୍ମ ବାହାରକୁ (`sqlite3 dump`) ରପ୍ତାନି କରନ୍ତୁ — କୌଣସି ବିଲ୍ଟ-ଇନ୍ ଅଭିଲେଖୀକରଣ ନାହିଁ।
- ବ୍ରୁଟ୍-ଫୋର୍ସ ଚିହ୍ନଟ ପାଇଁ `auth.login.failed` ଏବଂ `auth.login.locked` ଗଣନାଗୁଡ଼ିକୁ ଟ୍ରାକ୍ କରନ୍ତୁ।
- ନୂତନ ଆଡମିନ୍ ଏଣ୍ଡପଏଣ୍ଟ ଯୋଗ କରିବାବେଳେ, ଏକ ସ୍ଥିର `domain.verb.outcome` କାର୍ଯ୍ୟ ଷ୍ଟ୍ରିଙ୍ଗ ସହିତ
  `logAuditEvent({ ... })` କଲ୍ କରନ୍ତୁ ଏବଂ `getAuditRequestContext(request)` ମାଧ୍ୟମରେ
  ଅନୁରୋଧ ପ୍ରସଙ୍ଗ ପାସ୍ କରନ୍ତୁ, ଯାହାଦ୍ୱାରା IP ଏବଂ `requestId` ସ୍ୱୟଂଚାଳିତ ଭାବେ
  ଧରାଯାଏ।
