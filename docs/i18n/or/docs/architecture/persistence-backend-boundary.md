## ପ୍ରସଙ୍ଗ

OmniRoute ବର୍ତ୍ତମାନ `src/lib/db/` ରୁ ଡୋମେନ୍-କେନ୍ଦ୍ରିତ ସ୍ଥାୟୀକରଣ ଫଙ୍କସନ୍ଗୁଡ଼ିକ ପ୍ରଦାନ କରେ, ଯେତେବେଳେ
`src/lib/db/core.ts` ଦ୍ୱାରା ଫେରସ୍ତ କରାଯାଉଥିବା ସହଭାଗୀ କନେକ୍ସନ୍ `src/lib/db/adapters/types.ts` ରେ ଥିବା ସିଙ୍କ୍ରୋନସ୍ `SqliteAdapter`
କଣ୍ଟ୍ରାକ୍ଟକୁ କାର୍ଯ୍ୟକାରୀ କରେ। ସେହି ଆଡାପ୍ଟର୍ ଅନେକ SQLite ରନ୍ଟାଇମ୍କୁ ସମର୍ଥନ କରେ, କିନ୍ତୁ ଏହାର
ପୃଷ୍ଠଭାଗ SQLite-ଆକୃତିର ହୋଇ ରହେ: ସିଙ୍କ୍ରୋନସ୍ ପ୍ରସ୍ତୁତ ଷ୍ଟେଟ୍ମେଣ୍ଟ, `pragma`, ସ୍ଥଗିତ ଏବଂ ତତ୍କ୍ଷଣାତ୍
ଟ୍ରାଞ୍ଜାକ୍ସନ୍, ନେଟିଭ୍/ଫାଇଲ୍-କପି ବ୍ୟାକଅପ୍, ଚେକ୍ପଏଣ୍ଟ, ଏବଂ ଏକ ସ୍ଥାନୀୟ ଡାଟାବେସ୍ ହ୍ୟାଣ୍ଡଲ୍।

ବର୍ତ୍ତମାନର ଷ୍ଟାର୍ଟଅପ୍ ଏବଂ ପୁନରୁଦ୍ଧାର ପଥ ମଧ୍ୟ SQLite ଫାଇଲ୍ର ଜୀବନଚକ୍ର ପରିଚାଳନା କରେ। `src/lib/db/core.ts`
`storage.sqlite` କୁ ରିଜଲ୍ଭ କରେ, ଗୋଟିଏ ପ୍ରୋସେସ୍-ଗ୍ଲୋବାଲ୍ ଆଡାପ୍ଟର୍ ରକ୍ଷଣାବେକ୍ଷଣ କରେ, WAL କୁ ଚେକ୍ପଏଣ୍ଟ କରେ, ପୁନରୁଦ୍ଧାର
ସମୟରେ ଚୟନିତ ଟେବୁଲ୍ଗୁଡ଼ିକୁ ସଂରକ୍ଷିତ ରଖେ, ଏବଂ ଡାଟାବେସ୍ ପୁନଃନିର୍ମାଣ କରିବା ବେଳେ SQLite ସହାୟକ ଫାଇଲ୍ଗୁଡ଼ିକୁ ଅପସାରଣ
କରେ। `src/lib/db/adapters/driverFactory.ts` ରେ ଡ୍ରାଇଭର୍ ଚୟନ ସମର୍ଥିତ SQLite ରନ୍ଟାଇମ୍ଗୁଡ଼ିକ ମଧ୍ୟରୁ ବାଛେ; ଏହା
କୌଣସି ବାହ୍ୟ-ବ୍ୟାକଏଣ୍ଡ ଅବ୍ଷ୍ଟ୍ରାକ୍ସନ୍ ନୁହେଁ।

ସ୍କିମା ବିବର୍ତ୍ତନ ମଧ୍ୟ ସେହିପରି ଭାବେ ସଂଯୁକ୍ତ। `src/lib/db/migrationRunner.ts` କ୍ରମାଙ୍କିତ SQL ଫାଇଲ୍ଗୁଡ଼ିକୁ ପ୍ରୟୋଗ କରେ,
`sqlite_master` ଏବଂ `PRAGMA table_info` କୁ ଯାଞ୍ଚ କରେ, ଇଚ୍ଛାଧୀନ FTS5 ସମର୍ଥନ ଚିହ୍ନଟ କରେ, ଏବଂ SQLite
ଟ୍ରାଞ୍ଜାକ୍ସନ୍ରେ ମାଇଗ୍ରେସନ୍ କାର୍ଯ୍ୟ ଚଲାଏ। `src/lib/db/backup.ts` ଏବଂ
`src/lib/db/optimizationSettings.ts` ପରି ପରିଚାଳନାଗତ ମଡ୍ୟୁଲ୍ଗୁଡ଼ିକ ବ୍ୟାକଅପ୍, `PRAGMA`, WAL, ପେଜ୍-ସାଇଜ୍,
ଅଟୋ-ଭ୍ୟାକ୍ୟୁମ୍, ଏବଂ `VACUUM` ସେମାଣ୍ଟିକ୍ସକୁ ସିଧାସଳଖ ବ୍ୟବହାର କରନ୍ତି।

ଏଗୁଡ଼ିକ ଏମ୍ବେଡେଡ୍ SQLite ଡିପ୍ଲୟମେଣ୍ଟର ବୈଧ ବୈଶିଷ୍ଟ୍ୟ। PostgreSQL କିମ୍ବା MySQL କୁ SQLite API
ଅନୁକରଣ କରିବାକୁ ବାଧ୍ୟ ନକରି ଏଗୁଡ଼ିକ ଉପଲବ୍ଧ ରହିବା ଉଚିତ।

## ନିଷ୍ପତ୍ତି

ପୋର୍ଟେବଲ୍ ସ୍ଥାୟୀ ଅବସ୍ଥା ପାଇଁ ଏକ ଦୁଇ-ସ୍ତରୀୟ ସ୍ଥାୟୀକରଣ ସୀମା ଗ୍ରହଣ କରନ୍ତୁ:

1. **ଡୋମେନ୍ ରିପୋଜିଟୋରୀ କଣ୍ଟ୍ରାକ୍ଟଗୁଡ଼ିକ** ବ୍ୟବସାୟ ଏବଂ ରାଉଟିଂ
   କୋଡ୍କୁ ଆବଶ୍ୟକ ସ୍ଥାୟୀକରଣ କାର୍ଯ୍ୟଗୁଡ଼ିକ ପରିଭାଷିତ କରେ। କଲର୍ମାନେ SQL ଟେକ୍ସଟ୍, ପ୍ରସ୍ତୁତ ଷ୍ଟେଟ୍ମେଣ୍ଟ,
   ଡାଟାବେସ୍ ଫାଇଲ୍, କିମ୍ବା ଡାଇଲେକ୍ଟ ଅବଜେକ୍ଟ ଉପରେ ନୁହେଁ, ଡୋମେନ୍ ଆଚରଣ ଏବଂ ଡୋମେନ୍ ଡାଟା ଉପରେ ନିର୍ଭର କରନ୍ତି।
2. **ଏକ ଆଭ୍ୟନ୍ତରୀଣ ଆସିଙ୍କ୍ରୋନସ୍ ବ୍ୟାକଏଣ୍ଡ କଣ୍ଟ୍ରାକ୍ଟ** ଟ୍ରାଞ୍ଜାକ୍ସନ୍ କଣ୍ଟେକ୍ସ୍ଟ, ସ୍ୱାସ୍ଥ୍ୟ/ପ୍ରସ୍ତୁତି,
   ମାଇଗ୍ରେସନ୍ ସମନ୍ୱୟ, ବ୍ୟାକଏଣ୍ଡ କ୍ଷମତା, ଏବଂ ଶ୍ରେଣୀବଦ୍ଧ ତ୍ରୁଟି ସହିତ ରିପୋଜିଟୋରୀ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ଗୁଡ଼ିକୁ
   ସମର୍ଥନ କରେ। ସଠିକ୍ TypeScript ପୃଷ୍ଠଭାଗ ପ୍ରଥମ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ PR ସହିତ ପ୍ରସ୍ତାବିତ ହେବ ଏବଂ
   ଅନୁରୂପତା ପରୀକ୍ଷା ଦ୍ୱାରା ପ୍ରମାଣିତ ହେବ; ଏହି ADR ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ କୌଣସି କଳ୍ପନାଭିତ୍ତିକ API କୁ ସ୍ଥିର କରେ ନାହିଁ।

SQLite ଡିଫଲ୍ଟ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ଭାବେ ରହିବ। ଡୋମେନ୍ଗୁଡ଼ିକୁ ଛୋଟ ଭର୍ଟିକାଲ୍ ସ୍ଲାଇସ୍ରେ ମାଇଗ୍ରେଟ୍ କରାଯାଉଥିବା
ସମୟରେ ବିଦ୍ୟମାନ SQLite ଡ୍ରାଇଭର୍ କ୍ୟାସ୍କେଡ୍ ଏବଂ ସିଙ୍କ୍ରୋନସ୍ `SqliteAdapter`, SQLite ରିପୋଜିଟୋରୀ
ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ପଛରେ ରହିବ। କୌଣସି ବ୍ୟବହାରକାରୀଙ୍କୁ ବାହ୍ୟ ସେବା କନଫିଗର୍ କରିବା ଆବଶ୍ୟକ ନୁହେଁ।

SQLite ବିପକ୍ଷରେ ରିପୋଜିଟୋରୀ ସୀମା ପ୍ରମାଣିତ ହେବା ପରେ PostgreSQL ହେଉଛି ପ୍ରଥମ ପ୍ରସ୍ତାବିତ ବାହ୍ୟ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍।
ଦ୍ୱିତୀୟ ବ୍ୟବସାୟ-ଲଜିକ୍ ଫୋର୍କ ଭାବେ ନୁହେଁ, ବରଂ ସମାନ ଅନୁରୂପତା ସୁଇଟ୍ ବିପକ୍ଷରେ ଏକ ସମକକ୍ଷ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ଭାବେ
MySQL ଏହା ପରେ ଆସିବ।

## ସୀମା ନିୟମ

### ପୋର୍ଟେବଲ୍ ରିପୋଜିଟୋରୀ ପୃଷ୍ଠଭାଗ

ଏକ ପୋର୍ଟେବଲ୍ ରିପୋଜିଟୋରୀ ନିମ୍ନଲିଖିତଗୁଡ଼ିକ ପ୍ରଦାନ କରିପାରେ:

- ଡୋମେନ୍ ପଠନ ଏବଂ ଲିଖନ;
- ସ୍ପଷ୍ଟ ଆଟମିକ୍ କାର୍ଯ୍ୟ ଏବଂ ଟ୍ରାଞ୍ଜାକ୍ସନ୍-ସ୍କୋପ୍ଯୁକ୍ତ ରିପୋଜିଟୋରୀ ଆକ୍ସେସ୍;
- ଯେଉଁଠାରେ କନ୍କରେନ୍ସି ସେମାଣ୍ଟିକ୍ସ ଡୋମେନ୍ର ଅଂଶ, ସେଠାରେ ତୁଳନା/ଅଦ୍ୟତନ କିମ୍ବା ଲିଜ୍ କାର୍ଯ୍ୟ;
- ବ୍ୟାକଏଣ୍ଡ-ନିରପେକ୍ଷ ପେଜିନେସନ୍, କ୍ରମବିନ୍ୟାସ, ଏବଂ କନ୍ଷ୍ଟ୍ରେଣ୍ଟ ତ୍ରୁଟି।

ବ୍ୟାକଏଣ୍ଡ ସ୍ୱାସ୍ଥ୍ୟ, ପ୍ରସ୍ତୁତି, ଏବଂ ମାଇଗ୍ରେସନ୍ ସମନ୍ୱୟ ବ୍ୟକ୍ତିଗତ ଡୋମେନ୍ ରିପୋଜିଟୋରୀ ପରିବର୍ତ୍ତେ
ଆଭ୍ୟନ୍ତରୀଣ ବ୍ୟାକଏଣ୍ଡ/ପରିଚାଳନାଗତ କଣ୍ଟ୍ରାକ୍ଟର ଅନ୍ତର୍ଗତ।

ଏକ ପୋର୍ଟେବଲ୍ ରିପୋଜିଟୋରୀ ନିମ୍ନଲିଖିତଗୁଡ଼ିକ ପ୍ରଦାନ କରିବା ଉଚିତ୍ ନୁହେଁ:

- `prepare`, `get`, `all`, `run`, କିମ୍ବା କଞ୍ଚା ଡ୍ରାଇଭର୍ ହ୍ୟାଣ୍ଡଲ୍;
- `PRAGMA`, WAL ଚେକ୍ପଏଣ୍ଟ ମୋଡ୍, `VACUUM`, କିମ୍ବା ପେଜ୍/କ୍ୟାଶ୍ ଟ୍ୟୁନିଂ;
- SQLite ଫାଇଲ୍ ପଥ, ସହାୟକ ଫାଇଲ୍, କିମ୍ବା ଫାଇଲ୍-କପି ବ୍ୟାକଅପ୍;
- କ୍ରସ୍-ବ୍ୟାକଏଣ୍ଡ ଡୋମେନ୍ କଣ୍ଟ୍ରାକ୍ଟ ଭାବେ `lastInsertRowid`;
- FTS5 କିମ୍ବା `sqlite-vec` ସିଣ୍ଟାକ୍ସ;
- ସାଧାରଣ ବ୍ୟବସାୟ କୋଡ୍ ଦ୍ୱାରା ବ୍ୟବହୃତ ଏକ ଜେନେରିକ୍ ଡାଇଲେକ୍ଟ ଏସ୍କେପ୍ ହ୍ୟାଚ୍।

### ବ୍ୟାକଏଣ୍ଡ କ୍ଷମତା ପୃଷ୍ଠଭାଗ

ବ୍ୟାକଏଣ୍ଡ-ନିର୍ଦ୍ଦିଷ୍ଟ ଆଚରଣ ସ୍ପଷ୍ଟ ଏବଂ ଅନ୍ୱେଷଣଯୋଗ୍ୟ ହୋଇ ରହେ। SQLite-ମାତ୍ର ରକ୍ଷଣାବେକ୍ଷଣ ଏହାର
ନିଜସ୍ୱ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ଏବଂ ପରିଚାଳନାଗତ ଇଣ୍ଟରଫେସ୍ ପଛରେ ରହେ, ଯେଉଁଥିରେ ଅନ୍ତର୍ଭୁକ୍ତ:

- ରନ୍ଟାଇମ୍ ଡ୍ରାଇଭର୍ ଚୟନ;
- WAL ଚେକ୍ପଏଣ୍ଟ ଏବଂ SQLite ସଟ୍ଡାଉନ୍ ଆଚରଣ;
- ପେଜ୍-ସାଇଜ୍, କ୍ୟାଶ୍-ସାଇଜ୍, ଏବଂ ଅଟୋ-ଭ୍ୟାକ୍ୟୁମ୍ ସେଟିଂସ୍;
- ଡାଟାବେସ୍-ଫାଇଲ୍ ବ୍ୟାକଅପ୍, ପୁନଃସ୍ଥାପନ, ଏବଂ ପୁନରୁଦ୍ଧାର;
- SQLite ସ୍କିମା ଅନ୍ତର୍ନିରୀକ୍ଷଣ;
- FTS5 ଏବଂ `sqlite-vec` ଇଣ୍ଟିଗ୍ରେସନ୍।

କୌଣସି ବାହ୍ୟ ବ୍ୟାକଏଣ୍ଡକୁ ସେହି ବୈଶିଷ୍ଟ୍ୟଗୁଡ଼ିକ ଅନୁକରଣ କରିବା ଆବଶ୍ୟକ ନୁହେଁ। ରିପୋଜିଟୋରୀଗୁଡ଼ିକୁ ଏକ
ପୋର୍ଟେବଲ୍ କ୍ଷମତା ବ୍ୟବହାର କରିବାକୁ, ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ଆଚରଣ ସହିତ ଏକ ବ୍ୟାକଏଣ୍ଡ-ନିର୍ଦ୍ଦିଷ୍ଟ ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍
ପ୍ରଦାନ କରିବାକୁ, କିମ୍ବା ଏକ କ୍ଷମତା ଅନୁପଲବ୍ଧ ବୋଲି ରିପୋର୍ଟ କରିବାକୁ ହେବ।

## ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ଏବଂ ମାଇଗ୍ରେସନ୍ ମଡେଲ୍

ରିପୋଜିଟୋରି APIଗୁଡ଼ିକ ପରମାଣବିକ ବ୍ୟବସାୟିକ କାର୍ଯ୍ୟକୁ ପରିଭାଷିତ କରନ୍ତି; କଲର୍ମାନେ କୌଣସି SQL ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ମୋଡ୍ ଚୟନ କରନ୍ତି ନାହିଁ।
ପ୍ରତ୍ୟେକ କାର୍ଯ୍ୟ ଏହାର ପର୍ଯ୍ୟବେକ୍ଷଣଯୋଗ୍ୟ ସମକାଳୀନତା ଗ୍ୟାରେଣ୍ଟିଗୁଡ଼ିକୁ ପରିଭାଷିତ କରିବା ଆବଶ୍ୟକ: ସୁରକ୍ଷିତ ଅପରିବର୍ତ୍ତନୀୟ ନିୟମ, ଦ୍ୱନ୍ଦ୍ୱ
ଚିହ୍ନଟ, ପୁନଃପ୍ରୟାସ ବର୍ଗୀକରଣ, ଆଇଡେମ୍ପୋଟେନ୍ସି ଆଶା, ଏବଂ ଟ୍ରାଞ୍ଜାକ୍ସନ୍-ପ୍ରସଙ୍ଗ ପ୍ରସାରଣ।
କେବଳ ସେହି ପର୍ଯ୍ୟବେକ୍ଷଣଯୋଗ୍ୟ ଗ୍ୟାରେଣ୍ଟିଗୁଡ଼ିକ ସମତୁଲ୍ୟ ରହିଲେ ହିଁ କାର୍ଯ୍ୟାନ୍ୱୟନଗୁଡ଼ିକ ଭିନ୍ନ ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ଏବଂ ଆଇସୋଲେସନ୍ ପ୍ରଣାଳୀ ବ୍ୟବହାର କରିପାରିବେ। SQLite ଆଭ୍ୟନ୍ତରୀଣ ଭାବରେ ଏହାର ବର୍ତ୍ତମାନର ବିଳମ୍ବିତ କିମ୍ବା ତତ୍କାଳ
ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ଆଚରଣ ବ୍ୟବହାର ଜାରି ରଖିପାରିବ, ଯେଉଁଠାରେ ତାହା କାର୍ଯ୍ୟର ଚୁକ୍ତି ପୂରଣ କରେ।

ବାହ୍ୟ ବ୍ୟାକେଣ୍ଡଗୁଡ଼ିକ ପାଇଁ ସ୍ପଷ୍ଟ ମାଇଗ୍ରେସନ୍ ମାଲିକାନା ଆବଶ୍ୟକ, ଯାହାଦ୍ୱାରା ଏକାଧିକ ଆପ୍ଲିକେସନ୍ ରେପ୍ଲିକା ସମାନ ସ୍କିମା ପରିବର୍ତ୍ତନ ପାଇଁ ପ୍ରତିଯୋଗିତା କରିପାରିବେ ନାହିଁ।
ବ୍ୟାକେଣ୍ଡ ମାଇଗ୍ରେସନ୍ ଇତିହାସଗୁଡ଼ିକ ଯୁକ୍ତିସଙ୍ଗତ ମାଇଲଖୁଣ୍ଟ ଅଂଶୀଦାର କରିପାରନ୍ତି, କିନ୍ତୁ SQLite SQL
ଫାଇଲ୍ଗୁଡ଼ିକୁ ଅନ୍ୟ ଏକ ଡାଇଲେକ୍ଟରେ ପୋର୍ଟେବଲ୍ କିମ୍ବା ପୁନଃବ୍ୟବହାରଯୋଗ୍ୟ ବୋଲି ଧରାଯାଏ ନାହିଁ।

## କ୍ରସ୍-ବ୍ୟାକେଣ୍ଡ ଅନୁରୂପତା ଅର୍ଥବିଜ୍ଞାନ

ଅନୁରୂପତା ପରୀକ୍ଷାଗୁଡ଼ିକ କେବଳ ରିପୋଜିଟୋରି ପଦ୍ଧତି ସ୍ୱାକ୍ଷର ନୁହେଁ, ଆଚରଣକୁ ମଧ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ କରିବା ଆବଶ୍ୟକ। ପ୍ରତ୍ୟେକ ମାଇଗ୍ରେଟ୍ ହୋଇଥିବା ଡୋମେନ୍
ନିମ୍ନଲିଖିତଗୁଡ଼ିକୁ ପରିଭାଷିତ ଏବଂ ଯାଞ୍ଚ କରିବା ଆବଶ୍ୟକ:

- ଟାଇମ୍ଷ୍ଟାମ୍ପ ଟାଇମ୍ଜୋନ୍, ସୂକ୍ଷ୍ମତା, ଏବଂ ସିରିଆଲାଇଜେସନ୍;
- `NULL` କ୍ରମବିନ୍ୟାସ, କୋଲେସନ୍, ଏବଂ କେସ୍-ସେନ୍ସିଟିଭିଟି ଆଶା;
- JSON ଉପସ୍ଥାପନା ଏବଂ ତୁଳନା ଆଚରଣ;
- ପୂର୍ଣ୍ଣସଂଖ୍ୟା, ଦଶମିକ, ଏବଂ ମୁଦ୍ରାଗତ ସୂକ୍ଷ୍ମତା;
- ପୃଷ୍ଠାଙ୍କନ ପାଇଁ ସ୍ଥିର କ୍ରମବିନ୍ୟାସ ଏବଂ ନିର୍ଦ୍ଧାରଣାତ୍ମକ ସମତା-ଭଞ୍ଜକ;
- SQLite ରୋ ID ଉପରେ ନିର୍ଭର ନ କରି ID ସୃଷ୍ଟି;
- ଅନନ୍ୟତା ଏବଂ ଫରେନ୍-କି ଉଲ୍ଲଂଘନ ବର୍ଗୀକରଣ;
- କୌଣସି-କାର୍ଯ୍ୟ-ନଥିବା, ତୁଳନା/ଅଦ୍ୟତନ, ଏବଂ ବିଲୋପ କାର୍ଯ୍ୟଗୁଡ଼ିକ ପାଇଁ ପ୍ରଭାବିତ-ରୋ ଆଚରଣ;
- ସମକାଳୀନ-ଲିଖନ ଫଳାଫଳ, ପୁନଃପ୍ରୟାସଯୋଗ୍ୟ ଦ୍ୱନ୍ଦ୍ୱ, ଏବଂ ଆଇଡେମ୍ପୋଟେଣ୍ଟ ପୁନଃପ୍ରୟାସ।

ଯଦି କୌଣସି ଡୋମେନ୍ ସମତୁଲ୍ୟ ପର୍ଯ୍ୟବେକ୍ଷଣଯୋଗ୍ୟ ଅର୍ଥବିଜ୍ଞାନ ଉଲ୍ଲେଖ କରିପାରେ ନାହିଁ, ତେବେ ଏହା ଏପର୍ଯ୍ୟନ୍ତ ପୋର୍ଟେବଲ୍ ନୁହେଁ ଏବଂ ସେହି ଚୁକ୍ତି ଡିଜାଇନ୍ ହେବା ପର୍ଯ୍ୟନ୍ତ
ବ୍ୟାକେଣ୍ଡ-ନିର୍ଦ୍ଦିଷ୍ଟ ରହିବା ଆବଶ୍ୟକ।

## ସୁସଙ୍ଗତତା ଆବଶ୍ୟକତା

ଏହି ADR ଅନୁସରଣ କରୁଥିବା ଯେକୌଣସି କାର୍ଯ୍ୟାନ୍ୱୟନ ନିମ୍ନଲିଖିତ ଗୁଣଗୁଡ଼ିକୁ ସଂରକ୍ଷଣ କରିବା ଆବଶ୍ୟକ:

- SQLite ଶୂନ୍ୟ-ବିନ୍ୟାସ ଡିଫଲ୍ଟ ଭାବେ ରହିବ।
- ବିଦ୍ୟମାନ SQLite ଫାଇଲ୍ ଏବଂ ମାଇଗ୍ରେସନ୍ ଇତିହାସ ପଠନଯୋଗ୍ୟ ରହିବ।
- npm, Electron, Docker, ଏବଂ ସୀମିତ-ରନ୍ଟାଇମ୍ SQLite ଫଲ୍ବ୍ୟାକ୍ଗୁଡ଼ିକ ସେମାନଙ୍କ ବର୍ତ୍ତମାନର ଷ୍ଟାର୍ଟଅପ୍ ପଥ ବଜାୟ ରଖିବେ।
- ସଂରକ୍ଷିତ ପ୍ରଦାନକାରୀ ପରିଚୟପତ୍ରଗୁଡ଼ିକ ବିଦ୍ୟମାନ ଆପ୍ଲିକେସନ୍ ଏନ୍କ୍ରିପ୍ସନ୍ ଆଚରଣ ବ୍ୟବହାର ଜାରି ରଖିବ।
- କୌଣସି ରିପୋଜିଟୋରି ମାଇଗ୍ରେସନ୍ ନିରବରେ ରାଉଟିଂ, କୋଟା, API-କି, କିମ୍ବା ଅଡିଟ୍ ଅର୍ଥବିଜ୍ଞାନ ପରିବର୍ତ୍ତନ କରିବ ନାହିଁ।
- ବ୍ୟାକଅପ୍ ଏବଂ ପୁନରୁଦ୍ଧାର ଆଚରଣକୁ ସାର୍ବଜନୀନ ଭାବେ ଉପସ୍ଥାପନ କରିବା ପରିବର୍ତ୍ତେ ପ୍ରତ୍ୟେକ ବ୍ୟାକେଣ୍ଡ ଅନୁଯାୟୀ ଡକ୍ୟୁମେଣ୍ଟ କରାଯିବ।
- ଏକ ସ୍ୱଚ୍ଛ କେବଳ-SQLite ସଂସ୍ଥାପନ କୌଣସି ବାହ୍ୟ ଡାଟାବେସ୍ ଡ୍ରାଇଭର୍ ଲୋଡ୍ କିମ୍ବା ଆବଶ୍ୟକ କରିବ ନାହିଁ।

## ବିତରଣ କ୍ରମ

1. ଏକ ପୃଥକ ସମୀକ୍ଷା ଆର୍ଟିଫ୍ୟାକ୍ଟ ଭାବେ ଏକ ପୁନରୁତ୍ପାଦନଯୋଗ୍ୟ SQLite କପ୍ଲିଂ ଇନ୍ଭେଣ୍ଟୋରି ପ୍ରକାଶ କରନ୍ତୁ।
2. ପ୍ରଥମ ଡୋମେନ୍ ରିପୋଜିଟୋରି ଚୁକ୍ତି ଏବଂ ଅନୁରୂପତା ପରୀକ୍ଷା ପ୍ରବର୍ତ୍ତନ କରନ୍ତୁ।
3. ଡିଫଲ୍ଟଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ ନ କରି ସେହି ଚୁକ୍ତିଗୁଡ଼ିକ ପଛରେ ବିଦ୍ୟମାନ SQLite କାର୍ଯ୍ୟାନ୍ୱୟନକୁ ଅନୁକୂଳିତ କରନ୍ତୁ।
4. ରକ୍ଷଣାବେକ୍ଷକଙ୍କ ଅନୁମୋଦନ ସାପେକ୍ଷରେ, ଗୋଟିଏ ସୀମାବଦ୍ଧ କଣ୍ଟ୍ରୋଲ୍-ପ୍ଲେନ୍ ସ୍ଲାଇସ୍ ପାଇଁ PostgreSQLକୁ ପ୍ରଥମ ବାହ୍ୟ କାର୍ଯ୍ୟାନ୍ୱୟନ ଭାବେ ଯୋଡ଼ନ୍ତୁ।
5. ସମକାଳୀନ-ଲିଖନ ଏବଂ ମାଇଗ୍ରେସନ୍-ମାଲିକାନା ପରୀକ୍ଷା ଉପଲବ୍ଧ ହେବା ପରେ ହିଁ ଅଂଶୀଦାର ଅବସ୍ଥାକୁ ବିସ୍ତାର କରନ୍ତୁ।
6. ଡାଟାବେସ୍ ସ୍ୱିଚିଂର ପ୍ରଚାର କରିବା ପୂର୍ବରୁ ଏକ ଅଫ୍ଲାଇନ୍, ବୈଧୀକୃତ SQLite-ରୁ-ବାହ୍ୟ ମାଇଗ୍ରେସନ୍ ପଥ ଯୋଡ଼ନ୍ତୁ।
7. ପ୍ରମାଣିତ ରିପୋଜିଟୋରି ଏବଂ ବ୍ୟାକେଣ୍ଡ ଚୁକ୍ତିଗୁଡ଼ିକ ଆଧାରରେ MySQL ଯୋଡ଼ନ୍ତୁ।

ପ୍ରତ୍ୟେକ ରନ୍ଟାଇମ୍ ପଦକ୍ଷେପ ଏକ ପୃଥକ, ସମୀକ୍ଷାଯୋଗ୍ୟ PR। ପୂର୍ବ ପଦକ୍ଷେପରେ ଥିବା ଏକ ଅପ୍ରମାଣିତ ଅବସ୍ତ୍ରାକ୍ସନ୍କୁ ମର୍ଜ୍ କରିବାର ଯଥାର୍ଥତା ପ୍ରଦାନ ପାଇଁ ପରବର୍ତ୍ତୀ ପଦକ୍ଷେପକୁ ବ୍ୟବହାର କରାଯିବା ଉଚିତ ନୁହେଁ।

## ପ୍ରଥମ କାର୍ଯ୍ୟାନ୍ୱୟନ ସ୍ଲାଇସ୍

କପ୍ଲିଂ ଇନଭେଣ୍ଟରୀ ସମୀକ୍ଷା କରାଯିବା ପରେ ପ୍ରଥମ ରନ୍ଟାଇମ୍ ସ୍ଲାଇସ୍ ଚୟନ କରାଯିବା ଉଚିତ। ପ୍ରଦାତା
ସଂଯୋଗ, API କୀ, କମ୍ବୋ ଏବଂ ରାଉଟିଂ ବିନ୍ୟାସ ଏହାର ପ୍ରାର୍ଥୀ, କାରଣ ସେଗୁଡ଼ିକର ମୂଳ ଟେବୁଲ୍
`src/lib/db/core.ts`ରେ ଦୃଶ୍ୟମାନ; କିନ୍ତୁ ଏହି ADR କୌଣସି ଟେବୁଲ୍ ତାଲିକା କିମ୍ବା ମାଇଗ୍ରେସନ୍ PRକୁ ଅନୁମୋଦନ କରେ ନାହିଁ।
ସ୍ଲାଇସ୍ରେ ନିମ୍ନଲିଖିତଗୁଡ଼ିକ ଅବଶ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ ହେବ:

- SQLite ଆଚରଣ-ସଂରକ୍ଷଣ ପରୀକ୍ଷା;
- ରିପୋଜିଟୋରି ଅନୁରୂପତା ପରୀକ୍ଷା;
- ସ୍ପଷ୍ଟ ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ସୀମା;
- ସଞ୍ଚିତ ପ୍ରମାଣପତ୍ରଗୁଡ଼ିକ ପାଇଁ ଏନ୍କ୍ରିପ୍ସନ୍ ଏବଂ ରିଡାକ୍ସନ୍ ଯାଞ୍ଚ;
- ଡିଫଲ୍ଟ ଷ୍ଟାର୍ଟଅପ୍ ବିନ୍ୟାସରେ କୌଣସି ପରିବର୍ତ୍ତନ ନୁହେଁ।

## ବିଚାର କରାଯାଇଥିବା ବିକଳ୍ପଗୁଡ଼ିକ

### `SqliteAdapter` ଅଧୀନରେ PostgreSQL ଯୋଡ଼ିବା

ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଇଛି। `SqliteAdapter` ହେଉଛି SQLite ରନ୍ଟାଇମ୍ଗୁଡ଼ିକ ପାଇଁ ଏକ ସୁସଙ୍ଗତତା ସ୍ତର ଏବଂ ଏହା SQLite-ନିର୍ଦ୍ଦିଷ୍ଟ
ଅପରେସନ୍ଗୁଡ଼ିକୁ ପ୍ରକାଶ କରେ। ସେହି ପୃଷ୍ଠକୁ ଅନୁକରଣ କରିବା ଫଳରେ ସିଙ୍କ୍ରୋନସ୍ ଏବଂ ଡାୟାଲେକ୍ଟ-ନିର୍ଦ୍ଦିଷ୍ଟ ଧାରଣାଗୁଡ଼ିକ
ଏକ ନୂତନ ବ୍ୟାକେଣ୍ଡ୍ରେ ଲିକ୍ ହେବ।

### ସମସ୍ତ ଡୋମେନ୍ ପାଇଁ ଏକ ସାଧାରଣ କ୍ୱେରୀ/ନିଷ୍ପାଦନ API ପ୍ରକାଶ କରିବା

ପ୍ରାଥମିକ ସୀମା ଭାବେ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଇଛି। ଏହା ସଂଯୋଗ ପରିଚାଳନାକୁ କେନ୍ଦ୍ରୀଭୂତ କରିବ, କିନ୍ତୁ SQL ଡାୟାଲେକ୍ଟ,
ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ଏବଂ ଟେବୁଲ୍ କପ୍ଲିଂକୁ ବ୍ୟବସାୟ ମଡ୍ୟୁଲ୍ଗୁଡ଼ିକରେ ଛାଡ଼ିଦେବ। ଏକ ନିମ୍ନ-ସ୍ତରୀୟ ବ୍ୟାକେଣ୍ଡ୍ ପ୍ରିମିଟିଭ୍
ରିପୋଜିଟୋରି କାର୍ଯ୍ୟାନ୍ୱୟନ ଭିତରେ ରହିପାରେ, କିନ୍ତୁ ଆପ୍ଲିକେସନ୍-ମୁଖୀ ପର୍ସିଷ୍ଟେନ୍ସ API ଭାବେ ନୁହେଁ।

### ଗୋଟିଏ ସ୍ଲାଇସ୍କୁ ବୈଧ କରିବା ପୂର୍ବରୁ ସମସ୍ତ ପର୍ସିଷ୍ଟେନ୍ସକୁ ପୁନଃଲେଖନ କରିବା

ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଇଛି। ବର୍ତ୍ତମାନର ପର୍ସିଷ୍ଟେନ୍ସ ପୃଷ୍ଠ ବ୍ୟାପକ ଏବଂ ଏଥିରେ ଫାଇଲ୍ ଜୀବନଚକ୍ର, ପୁନରୁଦ୍ଧାର, ସନ୍ଧାନ
ଏବଂ କାର୍ଯ୍ୟକ୍ଷମ ବିନ୍ୟାସ ଅନ୍ତର୍ଭୁକ୍ତ। ଭର୍ଟିକାଲ୍ ସ୍ଲାଇସ୍ଗୁଡ଼ିକ ସମୀକ୍ଷାଯୋଗ୍ୟ ଆଚରଣ ଏବଂ ରୋଲ୍ବ୍ୟାକ୍ ସୀମା ପ୍ରଦାନ କରେ।

### SQLiteକୁ ଡିଫଲ୍ଟ ଭାବେ ପ୍ରତିସ୍ଥାପନ କରିବା

ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଇଛି। ଏମ୍ବେଡେଡ୍ ଏବଂ ଡେସ୍କଟପ୍ ଡିପ୍ଲୟମେଣ୍ଟ୍ଗୁଡ଼ିକ ବର୍ତ୍ତମାନର ଶୂନ୍ୟ-ସେବା ଷ୍ଟାର୍ଟଅପ୍ ମଡେଲ୍ ଉପରେ ନିର୍ଭର କରନ୍ତି। ଏକ
ବାହ୍ୟ ବ୍ୟାକେଣ୍ଡ୍ ଇଚ୍ଛାଧୀନ।

### Redisକୁ ସ୍ଥାୟୀ ପ୍ରାଧିକରଣ ଭାବେ ବ୍ୟବହାର କରିବା

ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଇଛି। Redis ସ୍ପଷ୍ଟ ଭାବେ କ୍ଷଣସ୍ଥାୟୀ ସମନ୍ୱୟ, କ୍ୟାଶ୍ କିମ୍ବା କାଉଣ୍ଟର୍ଗୁଡ଼ିକୁ ସମର୍ଥନ କରିପାରେ, କିନ୍ତୁ ଏହା ଏଠାରେ
ବର୍ଣ୍ଣିତ ସ୍ଥାୟୀ ରିପୋଜିଟୋରି ଚୁକ୍ତିକୁ ପ୍ରତିସ୍ଥାପନ କରେ ନାହିଁ।

## ପରିଣାମ

### ସକାରାତ୍ମକ

- ବ୍ୟବସାୟ କୋଡ୍ ଡାଟାବେସ୍ ଡାୟାଲେକ୍ଟରୁ ସ୍ୱାଧୀନ ଏକ ସ୍ଥିର ପର୍ସିଷ୍ଟେନ୍ସ ସୀମା ପାଏ।
- ଏକ ବାହ୍ୟ ବ୍ୟାକେଣ୍ଡ୍ ଅବ୍ଷ୍ଟ୍ରାକ୍ସନ୍କୁ ପରିଭାଷିତ କରିବା ପୂର୍ବରୁ SQLite ଆଚରଣ ପରୀକ୍ଷା କରାଯାଏ।
- PostgreSQL ଏବଂ MySQL ଡୋମେନ୍ ତର୍କକୁ ନକଲ କରିବା ପରିବର୍ତ୍ତେ ଚୁକ୍ତି ଏବଂ ପରୀକ୍ଷାଗୁଡ଼ିକୁ ସହଭାଗ କରନ୍ତି।
- SQLite-ମାତ୍ର କ୍ଷମତାଗୁଡ଼ିକ ଲିକ୍ କରୁଥିବା ସୁସଙ୍ଗତତା ଶିମ୍ରେ ପରିଣତ ହେବା ପରିବର୍ତ୍ତେ ପ୍ରଥମ-ଶ୍ରେଣୀୟ ରହେ।
- ମଲ୍ଟି-ରେପ୍ଲିକା ମାଇଗ୍ରେସନ୍ ଏବଂ ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ଆଚରଣ ଏକ ସ୍ପଷ୍ଟ ଡିଜାଇନ୍ ଚିନ୍ତାବିଷୟ ହୁଏ।

### ବ୍ୟୟ ଏବଂ ବିପଦ

- ରିପୋଜିଟୋରି ନିଷ୍କାସନ ପାଇଁ ପର୍ଯ୍ୟାୟକ୍ରମିକ କଲ୍-ସାଇଟ୍ ମାଇଗ୍ରେସନ୍ ଆବଶ୍ୟକ।
- ଆସିଙ୍କ୍ ସୀମାଗୁଡ଼ିକ ବର୍ତ୍ତମାନର ସିଙ୍କ୍ରୋନସ୍ ସେବା କୋଡ୍ରେ ପ୍ରସାରିତ ହୋଇପାରେ।
- କ୍ରସ୍-ବ୍ୟାକେଣ୍ଡ୍ ସେମାଣ୍ଟିକ୍ସ ପାଇଁ SQL ସିଣ୍ଟାକ୍ସ ସୁସଙ୍ଗତତା ବ୍ୟତୀତ ଅନୁରୂପତା ପରୀକ୍ଷା ଆବଶ୍ୟକ।
- ବ୍ୟାକଅପ୍, ସନ୍ଧାନ, ଭେକ୍ଟର୍ ଷ୍ଟୋରେଜ୍ ଏବଂ ରକ୍ଷଣାବେକ୍ଷଣ କ୍ଷମତା-ନିର୍ଦ୍ଦିଷ୍ଟ ରହେ।
- ଏକାଧିକ ପର୍ସିଷ୍ଟେନ୍ସ କାର୍ଯ୍ୟାନ୍ୱୟନ ଚଳାଇବା CI ଏବଂ କାର୍ଯ୍ୟକ୍ଷମ ସମର୍ଥନ ବ୍ୟୟ ବୃଦ୍ଧି କରେ।

## ଅଣ-ଲକ୍ଷ୍ୟଗୁଡ଼ିକ

ଏହି ADR ନିମ୍ନଲିଖିତଗୁଡ଼ିକ କରେ ନାହିଁ:

- କୌଣସି ଡାଟାବେସ୍ ନିର୍ଭରଶୀଳତା, ପରିବେଶ ଭେରିଏବଲ୍, ସ୍କିମା କିମ୍ବା ମାଇଗ୍ରେସନ୍ ଯୋଡ଼ିବା;
- ସକ୍ରିୟ SQLite ସିଙ୍ଗଲ୍ଟନ୍ କିମ୍ବା ଡ୍ରାଇଭର୍ କାସ୍କେଡ୍ ପରିବର୍ତ୍ତନ କରିବା;
- ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ରିଲିଜ୍ରେ PostgreSQL କିମ୍ବା MySQL ସମର୍ଥନର ପ୍ରତିଶ୍ରୁତି ଦେବା;
- FTS5, `sqlite-vec`, ବ୍ୟାକଅପ୍ ଫାଇଲ୍ କିମ୍ବା SQLite ରକ୍ଷଣାବେକ୍ଷଣକୁ ପୋର୍ଟେବଲ୍ କରିବା;
- ସହଭାଗୀ-ସ୍ଥିତି ଏବଂ ସମନ୍ୱୟ ପରୀକ୍ଷା ଉପଲବ୍ଧ ହେବା ପୂର୍ବରୁ ଆକ୍ଟିଭ୍-ଆକ୍ଟିଭ୍ ପ୍ରସ୍ତୁତିକୁ ପରିଭାଷିତ କରିବା;
- `src/lib/db/`ର ଏକକାଳୀନ ପୁନଃଲେଖନକୁ ଅନୁମୋଦନ କରିବା।

## ରକ୍ଷଣାବେକ୍ଷକଙ୍କ ଅନୁମୋଦନ ପାଇଁ ଅନିର୍ଣ୍ଣୀତ ପ୍ରଶ୍ନଗୁଡ଼ିକ

1. ରିପୋଜିଟୋରୀ ସହିତ ଆଭ୍ୟନ୍ତରୀଣ ଅସିଙ୍କ୍ରୋନସ୍ ବ୍ୟାକଏଣ୍ଡ ସୀମା ପସନ୍ଦଯୋଗ୍ୟ ଦିଗ କି, ନା
   ବାହ୍ୟ ସ୍ଥାୟୀ ସଂରକ୍ଷଣ ଏକ ପୃଥକ କଣ୍ଟ୍ରୋଲ୍-ପ୍ଲେନ୍ ସେବା ପଛରେ ରହିବା ଉଚିତ?
2. SQLite ଅନୁରୂପତା ପରେ ପ୍ରଥମ ବାହ୍ୟ କାର୍ଯ୍ୟାନ୍ୱୟନ ଭାବେ PostgreSQL ଗ୍ରହଣଯୋଗ୍ୟ କି?
3. କେଉଁ ଡୋମେନ୍ ପ୍ରଥମ ସୀମିତ ରିପୋଜିଟୋରୀ ଖଣ୍ଡ ହେବା ଉଚିତ?
4. ପ୍ରଥମ ମଲ୍ଟି-ରେପ୍ଲିକା ମାଇଲ୍ଷ୍ଟୋନ୍ ପାଇଁ କେଉଁ ଅବସ୍ଥା ଅଂଶୀଦାର ହେବା ଆବଶ୍ୟକ, ଏବଂ କେଉଁଟି ନୋଡ୍-ଲୋକାଲ୍ ରହିବ?
5. ବାଧାପ୍ରାପ୍ତ କିମ୍ବା ପ୍ରତ୍ୟାବର୍ତ୍ତିତ ରିପୋଜିଟୋରୀ ମାଇଗ୍ରେସନ୍ ପାଇଁ କେଉଁ ସୁସଙ୍ଗତତା ଅବଧି ଆବଶ୍ୟକ?

ଏହି ପ୍ରଶ୍ନଗୁଡ଼ିକର ସମାଧାନ ନହେବା ପର୍ଯ୍ୟନ୍ତ, ଏହି ଦଲିଲଟି ଏକ ପ୍ରସ୍ତାବ ଏବଂ ଏହାଦ୍ୱାରା କୌଣସି ରନ୍ଟାଇମ୍ ରିଫ୍ୟାକ୍ଟର୍ ସୂଚିତ ହୁଏ ନାହିଁ।
