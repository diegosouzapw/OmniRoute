ଏହି ଡକ୍ୟୁମେଣ୍ଟଟି OmniRoute-ରେ ଯୋଡ଼ାଯାଇଥିବା ଫିଡ୍ବ୍ୟାକ୍-ଚାଳିତ ଅନୁକୂଳନଶୀଳ ରାଉଟିଂ ଭିତ୍ତିଭୂମିକୁ ବର୍ଣ୍ଣନା କରେ।
ଏହାକୁ ଜାଣିଶୁଣି ଛୋଟ ରଖାଯାଇଛି: ଏହା ଏକ ଟାଇପ୍ଡ୍ ରାଉଟିଂ-ଫଳାଫଳ
ଚ୍ୟାନେଲ୍, ବିଦ୍ୟମାନ auto-combo ସ୍କୋରର୍କୁ ତଥ୍ୟ ଯୋଗାଉଥିବା ଏକ ଅନ୍ଲାଇନ୍ ଗୁଣବତ୍ତା ସଙ୍କେତ, ଏକ
ଇଚ୍ଛାଧୀନ OpenTelemetry ଏକ୍ସପୋର୍ଟର୍ ଏବଂ ଏକ ବ୍ୟାଖ୍ୟାଯୋଗ୍ୟତା ଏଣ୍ଡପଏଣ୍ଟ ପ୍ରବର୍ତ୍ତନ କରେ। ଏହା ବିଦ୍ୟମାନ ସ୍ଥିତିସ୍ଥାପକତା ଷ୍ଟାକ୍କୁ (circuit breaker, connection cooldown,
model lockout, health matrix, autopilot) ପ୍ରତିସ୍ଥାପନ କରେ **ନାହିଁ** — ବରଂ ଏହାକୁ ପରିପୂରକ କରେ।

## 1. ସ୍ଥାପତ୍ୟଗତ ପ୍ରସଙ୍ଗ

OmniRoute ହେଉଛି ଏକ ଡାଟା ପ୍ଲେନ୍, ଯେଉଁଥିରେ ଏକ **ଅନୁରୋଧ ହଟ୍ ପାଥ୍** ଏବଂ ଏକ **ନିୟନ୍ତ୍ରଣ/ବୁଦ୍ଧିମତ୍ତା
ପ୍ଲେନ୍** ରହିଛି। ହଟ୍ ପାଥ୍ଟି ଦ୍ରୁତ, ମେମୋରି-ଦକ୍ଷ, ଅସମକାଳୀନ, ସ୍ଥିତିସ୍ଥାପକ ଏବଂ
ପୂର୍ବାନୁମାନଯୋଗ୍ୟ ରହିବା ଆବଶ୍ୟକ। ମୂଲ୍ୟାଙ୍କନ, ଗୁଣବତ୍ତା ସ୍କୋରିଂ, ପରୀକ୍ଷଣ ଏବଂ ଐତିହାସିକ ବିଶ୍ଳେଷଣ
ନିୟନ୍ତ୍ରଣ ପ୍ଲେନ୍ର ଅଂଶ।


### ପୂର୍ବରୁ ଯାହା ଉପଲବ୍ଧ ଥିଲା (ଅଡିଟ୍ କରାଯାଇଛି, ନକଲ କରାଯାଇନାହିଁ)

| ଧାରଣା                                    | ବିଦ୍ୟମାନ କାର୍ଯ୍ୟାନ୍ୱୟନ                                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| ଉପଲବ୍ଧତା (ଆମେ ଟ୍ରାଫିକ୍ ପଠାଇପାରିବା କି?)   | Circuit breaker (CLOSED/DEGRADED/OPEN/HALF_OPEN, DB-ରେ ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ), connection cooldown, model lockout |
| ସ୍ୱାସ୍ଥ୍ୟ ରିପୋର୍ଟିଂ                      | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                          |

| ସଠିକ୍ କ୍ୟାଶ୍                             | `src/lib/semanticCache.ts` (ସ୍ୱାକ୍ଷର-ଆଧାରିତ)                                                                     |

| Combo ନିଷ୍ପତ୍ତିର ବ୍ୟାଖ୍ୟାଯୋଗ୍ୟତା         | `open-sse/services/combo/decisionTrace.ts`                                                                       |

ରାଉଟିଂ-ଇଭେଣ୍ଟ ସ୍ତରଟି `eventBus`-ର ପୁନଃ-କାର୍ଯ୍ୟାନ୍ୱୟନ **ନୁହେଁ**: ସେହି ବସ୍ଟି ହେଉଛି
dashboard-ର ରିଅଲ୍-ଟାଇମ୍ ବିଜ୍ଞପ୍ତି ଚ୍ୟାନେଲ୍ (ଟାଇପ୍ଡ୍ _ଇଭେଣ୍ଟ ନାମଗୁଡ଼ିକ_, ଅସ୍ପଷ୍ଟ
ପେଲୋଡ୍ଗୁଡ଼ିକ, UI ଉପଭୋକ୍ତାମାନେ)। `RoutingEvent` ହେଉଛି ଏକ ଟାଇପ୍ଡ୍ _ଫଳାଫଳ_ ଷ୍ଟ୍ରକ୍ଟ
(ବିଳମ୍ବ/ଟୋକେନ୍/ଖର୍ଚ୍ଚ/ଫଳାଫଳ/ସମାପ୍ତି-କାରଣ), ଯାହାକୁ ନିୟନ୍ତ୍ରଣ ପ୍ଲେନ୍ର
ଫିଡ୍ବ୍ୟାକ୍ ସିଙ୍କ୍ଗୁଡ଼ିକ (ଗୁଣବତ୍ତା ଟ୍ରାକର୍, OTel ଏକ୍ସପୋର୍ଟର୍, ବ୍ୟାଖ୍ୟା ଷ୍ଟୋର୍) ବ୍ୟବହାର କରନ୍ତି।

### ଯାହା ଅନୁପସ୍ଥିତ ଥିଲା (ଏଠାରେ ଯୋଡ଼ାଯାଇଛି)

1. ଏକ **ଟାଇପ୍ଡ୍ ରାଉଟିଂ-ଫଳାଫଳ ଇଭେଣ୍ଟ + ସିଙ୍କ୍ ଆବ୍ଷ୍ଟ୍ରାକ୍ସନ୍** (`RoutingEvent` /
   `RoutingEventSink`)। `decisionTrace` combo-ସୀମିତ ଏବଂ କେବଳ ଇନ୍-ମେମୋରି;
   `comboMetrics` ହେଉଛି ସଞ୍ଚୟୀ କାଉଣ୍ଟର୍; `call_logs` ହେଉଛି କଞ୍ଚା ଅସମକାଳୀନ ସ୍ଥାୟୀ ସଂରକ୍ଷଣ।
   ଏଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସିଟି ମଧ୍ୟ ଏକ ଟାଇପ୍ଡ୍, ସିଙ୍କ୍-ଆଧାରିତ ଫଳାଫଳ ଚ୍ୟାନେଲ୍ ନୁହେଁ, ଯାହାକୁ ଏକ ଗୁଣବତ୍ତା ଟ୍ରାକର୍, ଏକ OTel
   ଏକ୍ସପୋର୍ଟର୍ କିମ୍ବା ଏକ Future-AGI-ଶୈଳୀର ମୂଲ୍ୟାଙ୍କନକାରୀ ସବ୍ସ୍କ୍ରାଇବ୍ କରିପାରିବ।
2. ଆଉଟ୍ପୁଟ୍ ଗୁଣବତ୍ତା ପାଇଁ ଏକ **ଅନ୍ଲାଇନ୍ ଗୁଣବତ୍ତା ସଙ୍କେତ** (EWMA) — ପୂର୍ବରୁ ସ୍କୋରର୍
   "ଗୁଣବତ୍ତା"କୁ କେବଳ ସ୍ଥିର କାର୍ଯ୍ୟ ଉପଯୋଗିତା ଏବଂ ସ୍ୱେଚ୍ଛାଧୀନ eval ପାସ୍-ରେଟ୍ଗୁଡ଼ିକ ମାଧ୍ୟମରେ ପ୍ରତିନିଧିତ୍ୱ କରୁଥିଲା।
3. GenAI ଅର୍ଥଗତ ପରମ୍ପରା ବ୍ୟବହାର କରୁଥିବା ଏକ **ଇଚ୍ଛାଧୀନ, ନିର୍ଭରଶୀଳତା-ମୁକ୍ତ OTel ଏକ୍ସପୋର୍ଟର୍**।
4. ପ୍ରକୃତ ରାଉଟିଂ ନିଷ୍ପତ୍ତିଗୁଡ଼ିକ + ଗୁଣବତ୍ତା ସ୍ଥିତି ଫେରାଉଥିବା ଏକ **ବ୍ୟାଖ୍ୟାଯୋଗ୍ୟତା ଏଣ୍ଡପଏଣ୍ଟ**।

## 2. ରାଉଟିଂ ଇଭେଣ୍ଟଗୁଡ଼ିକ (ଫିଡ୍ବ୍ୟାକ୍ର ଭିତ୍ତିଭୂମି)

ଫାଇଲ୍ଗୁଡ଼ିକ: `open-sse/services/routing/events.ts`, `.../index.ts`

ଏକ `RoutingEvent` କେବଳ ରାଉଟିଂ ମେଟାଡାଟା ବହନ କରେ:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // ଅନୁମୋଦିତ ତାଲିକାଭୁକ୍ତ ୟୁନିଅନ୍
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` ହେଉଛି TypeScriptରେ ଏକ `Send+Sync`-ଶୈଳୀର ଟ୍ରେଟ୍:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // O(1) ହେବା ଆବଶ୍ୟକ, କୌଣସି ସିଙ୍କ୍ରୋନସ୍ I/O ନୁହେଁ
}
```

ହଟ୍ ପାଥ୍ ପ୍ରତ୍ୟେକ ସମ୍ପୂର୍ଣ୍ଣ ହୋଇଥିବା ଅନୁରୋଧ ପାଇଁ ଥରେ `emitRoutingEvent(event)` କଲ୍ କରେ
(ଷ୍ଟ୍ରିମିଂ-କମ୍ପ୍ଲିସନ୍ କଲ୍ବ୍ୟାକ୍, ନନ୍-ଷ୍ଟ୍ରିମିଂ ସଫଳତା ପାଥ୍, ଏବଂ
`handleChatCore`ରେ ଥିବା ତ୍ରୁଟିପୂର୍ଣ୍ଣ-200 ବିଫଳତା ପାଥ୍)। ପଞ୍ଜୀକୃତ ସିଙ୍କ୍ଗୁଡ଼ିକୁ ଡିସ୍ପ୍ୟାଚ୍ ସିଙ୍କ୍ରୋନସ୍ ଫ୍ୟାନ୍-ଆଉଟ୍ ଭାବେ ହୁଏ,
କିନ୍ତୁ ପ୍ରତ୍ୟେକ ସିଙ୍କ୍ କେବଳ କ୍ୟୁରେ ଯୋଡ଼େ/ଇନ୍-ମେମୋରି ସ୍ଥିତି ଅପଡେଟ୍ କରେ। **ହଟ୍ ପାଥ୍ରେ କୌଣସି
ସିଙ୍କ୍ରୋନସ୍ ଡାଟାବେସ୍ ରାଇଟ୍ କିମ୍ବା ନେଟୱର୍କ I/O ନାହିଁ।**

ଡିଫଲ୍ଟ ସିଙ୍କ୍ଗୁଡ଼ିକ:

- `MemoryRoutingEventStore` — ବ୍ୟାଖ୍ୟା ଏଣ୍ଡପଏଣ୍ଟ ପାଇଁ ସୀମିତ (500) ରିଙ୍ଗ୍ ବଫର୍,
  ସବୁଠାରୁ ନୂଆଟି ପ୍ରଥମେ।
- `QualityTracker` ଉପଭୋକ୍ତା — EWMA ଗୁଣବତ୍ତା ଆକଳନକୁ ଅପଡେଟ୍ କରେ।
- `OtlpHttpsEventSink` — ଇଚ୍ଛାଧୀନ, କେବଳ `OMNIROUTE_OTEL_ENDPOINT`
  (କିମ୍ବା `OTEL_EXPORTER_OTLP_ENDPOINT`) ସେଟ୍ ହୋଇଥିଲେ ସକ୍ଷମ ହୁଏ।

## 3. ଗୁଣବତ୍ତା ସଙ୍କେତ (ଫିଡ୍ବ୍ୟାକ୍-ଚାଳିତ ପ୍ରଦାନକାରୀ ସ୍ଥିତି)

ଫାଇଲ୍ଗୁଡ଼ିକ: `open-sse/services/routing/quality.ts`

v2 **ପରିଚାଳନାଗତ** ଗୁଣବତ୍ତାକୁ **ଅର୍ଥଗତ** ଗୁଣବତ୍ତାଠାରୁ ପୃଥକ କରେ:

- **ପରିଚାଳନାଗତ** — ରାଉଟିଂ ହଟ୍ ପାଥ୍ରୁ ବ୍ୟୁତ୍ପନ୍ନ (HTTP 4xx/5xx, ସଂଯୋଗ
  ବିଫଳତା, 429ଗୁଡ଼ିକ, ତ୍ରୁଟିପୂର୍ଣ୍ଣ ପ୍ରତିକ୍ରିୟା, ଷ୍ଟ୍ରିମ୍ ବାଧା, `finish_reason=length`,
  ଶୂନ୍ୟ-ଆଉଟପୁଟ୍ ସଫଳତା, ଲେଟେନ୍ସି/TTFT EWMA)। ଏକ 200କୁ ଅର୍ଥଗତ
  ଗୁଣବତ୍ତା ଭାବେ ଧରାଯାଏ ନାହିଁ।
- **ଅର୍ଥଗତ** — ଉତ୍ପନ୍ନ ଆଉଟପୁଟ୍ର ପ୍ରକୃତ ମୂଲ୍ୟ। କେବଳ ଏକ ମୂଲ୍ୟାଙ୍କନକାରୀ ଦ୍ୱାରା
  `setSemanticQuality()` ମାଧ୍ୟମରେ ଉତ୍ପାଦିତ ହୁଏ। କେହି ଏହା ପ୍ରଦାନ ନ କରିବା ପର୍ଯ୍ୟନ୍ତ ଏହା `null` ରହେ ଏବଂ
  କେବେ ମଧ୍ୟ ପରିଚାଳନାଗତ ସ୍କୋର୍ରେ ମିଶେ ନାହିଁ।

ପ୍ରତି-(ପ୍ରଦାନକାରୀ, ମଡେଲ୍) ସ୍ଥିତି (EWMA + ସୀମିତ କାଉଣ୍ଟର୍ଗୁଡ଼ିକ):

- `successEwma` — ଫଳାଫଳ ସଫଳତାର EWMA (α=0.2)।
- `latencyEwma` / `ttftEwma` — ଲେଟେନ୍ସିର EWMA (α=0.1)।
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`।
- `recencyMs` — ମଡେଲ୍ଟିକୁ ଶେଷଥର କେତେ ସମ୍ପ୍ରତି ପର୍ଯ୍ୟବେକ୍ଷଣ କରାଯାଇଥିଲା।

### ବିଶ୍ୱାସଯୋଗ୍ୟତା / ନମୁନା ସଚେତନତା

`confidence = clamp01(samples / 50)`, ଏବଂ ସ୍କୋରର୍କୁ ଫେରାଯାଉଥିବା ସ୍କୋର୍କୁ
ନିରପେକ୍ଷ ମଧ୍ୟବିନ୍ଦୁ ଆଡ଼କୁ ମିଶ୍ରିତ କରାଯାଏ:

```
score = 0.5 + confidence * (operational - 0.5)
```

ପରିଣାମଗୁଡ଼ିକ (ପରୀକ୍ଷା ଦ୍ୱାରା ଯାଞ୍ଚିତ):

- ଏକ କୋଲ୍ଡ୍ ପ୍ରଦାନକାରୀ (0 ନମୁନା)ର ସ୍କୋର୍ **0.5** — ଅନ୍ୟାୟ ଭାବେ ଦଣ୍ଡିତ ନୁହେଁ, କିନ୍ତୁ
  ହଜାର ହଜାର ଦୃଢ଼ ପର୍ଯ୍ୟବେକ୍ଷଣ ଥିବା ପ୍ରଦାନକାରୀଙ୍କୁ ଅତିକ୍ରମ କରିପାରେ ନାହିଁ।
- 7ଟି ଭାଗ୍ୟଜନିତ ସଫଳତା ଥିବା ପ୍ରଦାନକାରୀଙ୍କ ସ୍କୋର୍ 0.5 ଆଡ଼କୁ ଟଣାଯାଏ (ଆଶାବାଦୀ
  ଇନିସିଆଲାଇଜେସନ୍ରୁ କେବେ ବି ପ୍ରାଧାନ୍ୟ ବିସ୍ତାର କରେ ନାହିଁ)।
- 50+ ନମୁନା ଥିବା ପ୍ରଦାନକାରୀ ତାହାର ପ୍ରକୃତ ପରିଚାଳନାଗତ ସ୍କୋର୍କୁ ଅଭିସରଣ କରେ।
- ଅବନତି ଏବଂ ପୁନରୁଦ୍ଧାର କ୍ରମଶଃ ହୁଏ (EWMA), ଏବଂ ଗୋଟିଏ ବିଚ୍ଛିନ୍ନ ବିଫଳତା
  ଏକ ସୁସ୍ଥ ପ୍ରଦାନକାରୀଙ୍କୁ ନଷ୍ଟ କରେ ନାହିଁ।

`ProviderQuality` `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`କୁ ପ୍ରକାଶ କରେ।

ଏହା `quality` ସ୍କୋରିଂ ଫ୍ୟାକ୍ଟର୍ ଭାବେ ଅଟୋ-କମ୍ବୋ ସ୍କୋରର୍କୁ ଯୋଗାଣ କରେ:

- `open-sse/services/autoCombo/scoring.ts`ରେ
  `ScoringFactors.quality` / `ScoringWeights.quality`।
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03। ମୋଟ ଯୋଗଫଳ 1.0 ରହେ।
- `buildAutoCandidates` ଟ୍ରାକର୍ରୁ `candidate.quality` ପୂରଣ କରେ; ଡାଟା ନଥିବା ପ୍ରାର୍ଥୀମାନେ
  ଡିଫଲ୍ଟ ଭାବେ ନିରପେକ୍ଷ **0.5** ପାଆନ୍ତି (ଏକ କୋଲ୍ଡ୍ ପ୍ରାର୍ଥୀକୁ ବୁଷ୍ଟ୍ କିମ୍ବା
  ଦଣ୍ଡିତ କରାଯାଏ ନାହିଁ)।

କ୍ଲୋଜ୍ଡ୍ ଲୁପ୍:

```
RoutingEvent → QualityTracker → getQualityScore → ଅଟୋ-କମ୍ବୋ quality ଫ୍ୟାକ୍ଟର୍
      ↑                                                    │
      └────── ଅନୁରୋଧ ଫଳାଫଳ (handleChatCore) ←────────────┘
```

### କଠୋର ବହିଷ୍କରଣ ବନାମ ନରମ ଦଣ୍ଡ

ଗୁଣବତ୍ତା ସଙ୍କେତ କେବଳ ଏକ **ନରମ ଅନୁକୂଳନଶୀଳ ପସନ୍ଦ**। କଠୋର ବହିଷ୍କରଣ
ବର୍ତ୍ତମାନର ରେଜିଲିଏନ୍ସ ଷ୍ଟାକ୍ ପାଖରେ ରହେ: ସର୍କିଟ୍ ବ୍ରେକର୍ OPEN, କୋଟା ଶେଷ,
ପ୍ରମାଣୀକରଣ ବିଫଳତା, ମଡେଲ୍ ଲକ୍ଆଉଟ୍ — ଏଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସିଟି ଗୁଣବତ୍ତା ସ୍କୋର୍ରେ ପ୍ରଭାବିତ ହୁଏ ନାହିଁ।
ଯେଉଁ ପ୍ରଦାନକାରୀଙ୍କ ଗୁଣବତ୍ତା ସ୍କୋର୍ ସାମୟିକ ଭାବେ ହ୍ରାସ ପାଏ, ତାଙ୍କର ପ୍ରାଥମିକତା କମାଯାଏ,
କିନ୍ତୁ କେବେ ବି କଠୋର ଭାବେ ଅକ୍ଷମ କରାଯାଏ ନାହିଁ।

## 3b. କ୍ୟାନୋନିକାଲ୍ ଷ୍ଟ୍ରିମ୍ ଟାଇମିଂ (TTFT / ITL)

ଫାଇଲ୍ଗୁଡ଼ିକ: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` ହେଉଛି ଷ୍ଟ୍ରିମିଂ ପଥ ପାଇଁ ଏକମାତ୍ର ଇନ୍ଷ୍ଟ୍ରୁମେଣ୍ଟେସନ୍ ସୀମ୍,
ଯାହା `createSSEStream` (`open-sse/utils/stream.ts`) ସହିତ ସଂଯୁକ୍ତ:

- `markByte()` — ପ୍ରଥମ ଅପ୍ଷ୍ଟ୍ରିମ୍ ଚଙ୍କ୍ ଗ୍ରହଣ କରାଗଲା।
- `markForward()` — କ୍ଲାଏଣ୍ଟକୁ ଫର୍ୱାର୍ଡ କରାଯାଇଥିବା ପ୍ରଥମ ଚଙ୍କ୍ (TTFT ପାଇଁ ବ୍ୟବହୃତ)।
- `markInterrupted()` — ସ୍ୱଚ୍ଛ ଭାବେ ସମାପ୍ତ ହେବା ପୂର୍ବରୁ ଷ୍ଟ୍ରିମ୍ର ସମୟସୀମା ଶେଷ/ବାତିଲ୍/ତ୍ରୁଟି।
- `ttft()` = ପ୍ରଥମେ-ଫର୍ୱାର୍ଡ-କରାଯାଇଥିବା-SSE-ଚଙ୍କ୍ର ବିଳମ୍ବତା। **ଏହା ଟୋକନ୍-ସ୍ତରୀୟ TTFT ନୁହେଁ** —
  ଗୋଟିଏ SSE ଚଙ୍କ୍ରେ ଶୂନ୍ୟ/ଗୋଟିଏ/ଅନେକ ଟୋକନ୍ ଥାଇପାରେ। ଏହାକୁ ସଠିକ୍ ଭାବେ ଦଲିଲଭୁକ୍ତ କରାଯାଇଛି।
- `avgItlMs()` = ଚଙ୍କ୍ଗୁଡ଼ିକ ମଧ୍ୟରେ ହାରାହାରି ବ୍ୟବଧାନ (ITL ପାଇଁ ଏକ ଚଙ୍କ୍-ବିଳମ୍ବତା ପ୍ରତିନିଧି)।

TTFT/ITL/ବାଧାପ୍ରାପ୍ତ ସ୍ଥିତି `RoutingEvent` (`ttftMs`, `itlMs`) ମଧ୍ୟକୁ ପ୍ରବାହିତ ହୁଏ ଏବଂ
OTel ସିଙ୍କ୍ ଦ୍ୱାରା GenAI/OmniRoute ସ୍ପାନ୍ ଆଟ୍ରିବ୍ୟୁଟ୍ ଭାବେ ରପ୍ତାନି ହୁଏ।

## 4. OpenTelemetry / GenAI ପର୍ଯ୍ୟବେକ୍ଷଣକ୍ଷମତା

ଫାଇଲ୍ଗୁଡ଼ିକ: `open-sse/services/routing/otel.ts`

- ନିର୍ଭରତା-ମୁକ୍ତ OTLP/HTTP JSON ଏକ୍ସପୋର୍ଟର୍ (ଗ୍ଲୋବାଲ୍ `fetch` ବ୍ୟବହାର କରେ, କୌଣସି
  `@opentelemetry/*` SDK ନାହିଁ)।
- ସ୍ପାନ୍ଗୁଡ଼ିକ GenAI ସେମାଣ୍ଟିକ୍ ପ୍ରଥା (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) ସହିତ OmniRoute ରାଉଟିଂ
  ଆଟ୍ରିବ୍ୟୁଟ୍ଗୁଡ଼ିକୁ (ଫଳାଫଳ, ସ୍ଥିତି, ttft, ପୁନଃପ୍ରୟାସ, ଫଲ୍ବ୍ୟାକ୍) ଅନୁସରଣ କରେ।
- `record()` କେବଳ ଏକ ସୀମିତ ବଫର୍ରେ (O(1)) ଧାଡ଼ିବଦ୍ଧ କରେ; ଏକ ପୃଷ୍ଠଭୂମି ଟାଇମର୍
  ଅସମକାଳୀନ ଭାବେ `POST {endpoint}/v1/traces` ମାଧ୍ୟମରେ ଫ୍ଲସ୍ କରେ। ଅତ୍ୟଧିକ ଲୋଡ୍ ସମୟରେ
  ସବୁଠାରୁ ପୁରୁଣା ଇଭେଣ୍ଟ୍ଗୁଡ଼ିକୁ ବାଦ ଦିଆଯାଏ (`dropped` କାଉଣ୍ଟର୍) — ଡାଟା
  ପ୍ଲେନ୍ରେ କେବେବି ବ୍ୟାକ୍ପ୍ରେସର୍ ସୃଷ୍ଟି କରେନାହିଁ।
- **ବିନ୍ୟାସ ନହେଲେ ଅକ୍ଷମ ରହେ।** `OMNIROUTE_OTEL_ENDPOINT` (କିମ୍ବା
  `OTEL_EXPORTER_OTLP_ENDPOINT`) ସେଟ୍ ହେବା ଆବଶ୍ୟକ; ନଚେତ୍ ସିଙ୍କ୍ ପଞ୍ଜୀକୃତ
  ହୁଏନାହିଁ ଏବଂ କୌଣସି OTel କୋଡ୍ ଚାଲେନାହିଁ।

## 5. ବ୍ୟାଖ୍ୟାଯୋଗ୍ୟତା

- `GET /v1/explain/routing` ସାମ୍ପ୍ରତିକ `RoutingEvent`ଗୁଡ଼ିକୁ (ପ୍ରକୃତ
  ନିଷ୍ପତ୍ତିଗୁଡ଼ିକ, ସବୁଠାରୁ ନୂଆ ପ୍ରଥମେ) ଏବଂ ପ୍ରତି-ପ୍ରଦାତା/ମଡେଲ୍ ଗୁଣବତ୍ତା ସ୍ନାପ୍ଶଟ୍ ଫେରାଏ।
- ପ୍ରମାଣୀକରଣ `/v1/combos`କୁ ଅନୁସରଣ କରେ (Bearer API କୀ କିମ୍ବା ଡ୍ୟାସ୍ବୋର୍ଡ ସେସନ୍;
  `REQUIRE_API_KEY=false` ଥିବା ଏକକ-ବ୍ୟବହାରକାରୀ ସ୍ଥାନୀୟ ଡିପ୍ଲୟମେଣ୍ଟରେ ଅଜ୍ଞାତ ପ୍ରବେଶ)।
- କମ୍ବୋ-ସ୍ତରୀୟ ପ୍ରତି-ଆହ୍ୱାନ ଟ୍ରେସ୍ଗୁଡ଼ିକ ବିଦ୍ୟମାନ
  `decisionTrace.ts` (ହେଡର୍ `X-OmniRoute-Combo-Trace`) ମାଧ୍ୟମରେ ଉପଲବ୍ଧ ରହେ।
- ସୁରକ୍ଷା: ଇଭେଣ୍ଟ୍ଗୁଡ଼ିକ କେବଳ ରାଉଟିଂ ମେଟାଡାଟା ବହନ କରେ, କେବେବି ପ୍ରମ୍ପ୍ଟ୍/ବଡି/ପ୍ରମାଣପତ୍ର ନୁହେଁ।

## 6. ମୂଲ୍ୟାୟନ-ପ୍ଲେନ୍ ସମନ୍ୱୟ (Future AGI ପ୍ରସ୍ତୁତି)

OmniRoute, Future AGI (କିମ୍ବା ଯେକୌଣସି ମୂଲ୍ୟାୟନକାରୀ)କୁ **ଏକ ସମ୍ଭାବ୍ୟ
ବୁଦ୍ଧିମତ୍ତା/ମୂଲ୍ୟାୟନ ବ୍ୟାକ୍ଏଣ୍ଡ୍ ଭାବେ ବିବେଚନା କରେ, ନିର୍ଭରତା ଭାବେ ନୁହେଁ**। ସମନ୍ୱୟ ସୀମ୍ଗୁଡ଼ିକ:

- ଏକ `RoutingEventSink` ଅସମକାଳୀନ ଭାବେ ଇଭେଣ୍ଟ୍ଗୁଡ଼ିକୁ ମୂଲ୍ୟାୟନକାରୀଙ୍କ ପାଖକୁ ଫର୍ୱାର୍ଡ କରିପାରେ।
- `MemoryRoutingEventStore` + ଗୁଣବତ୍ତା ସ୍ନାପ୍ଶଟ୍ ମୂଲ୍ୟାୟନକାରୀଙ୍କୁ କଞ୍ଚା
  ନିଷ୍ପତ୍ତି ଷ୍ଟ୍ରିମ୍ ଯୋଗାଇଥାଏ।
- ଏକ ଭବିଷ୍ୟତ `Evaluator` (ନିର୍ଦ୍ଧାରଣାତ୍ମକ, ସ୍ଥାନୀୟ ବିଚାରକ, HTTP, WASM)
  ଇଭେଣ୍ଟ୍/ଟ୍ରେସ୍ଗୁଡ଼ିକୁ ଗ୍ରହଣ କରିବ ଏବଂ ଏକ `QualityScore` ଫେରାଇବ, ଯାହା ସେହି
  `getQualityScore`/ଗୁଣବତ୍ତା-ଫ୍ୟାକ୍ଟର୍ ପଥକୁ ଯୋଗାଣ କରେ।
- ବିଦ୍ୟମାନ ମୂଲ୍ୟାୟନ-ଚାଳିତ ରାଉଟିଂ (`open-sse/services/evalRouting.ts`) ସକ୍ଷମ ଥିବାବେଳେ
  `eval_runs` ପାସ୍-ରେଟ୍ ଅନୁଯାୟୀ କମ୍ବୋ ଲକ୍ଷ୍ୟଗୁଡ଼ିକୁ ପୂର୍ବରୁ ପୁନଃକ୍ରମବଦ୍ଧ କରେ।

ଅନୁରୋଧ ପଥରେ କୌଣସି ମୂଲ୍ୟାୟନ ସମକାଳୀନ ଭାବେ ଚାଲେନାହିଁ, ଏବଂ ମୂଲ୍ୟାୟନକାରୀ ଅନୁପସ୍ଥିତ ଥିଲେ ମଧ୍ୟ
ଗେଟ୍ୱେ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ କାର୍ଯ୍ୟ କରେ।

## 7. ଅନ୍ତିମ ସ୍ଥାପତ୍ୟ ସମୀକ୍ଷା

1. **ସମକାଳୀନ ହଟ୍ ପଥରେ କ'ଣ ରହିଛି?** ରାଉଟିଂ/ସ୍କୋରିଂ, ଗାର୍ଡରେଲ୍
   ପୂର୍ବ-ଯାଞ୍ଚ, କ୍ୟାଶ୍ ଲୁକ୍ଅପ୍, ଏବଂ ଇନ୍-ମେମୋରି ସିଙ୍କ୍ଗୁଡ଼ିକ ପାଇଁ ଗୋଟିଏ `emitRoutingEvent`
   ଫ୍ୟାନ୍-ଆଉଟ୍ (ମୂଳ ସ୍କୋରିଂଠାରୁ ~0.12 µs ଅଧିକ)।
2. **କ'ଣ ଅସମକାଳୀନ ପ୍ରକ୍ରିୟାକରଣକୁ ସ୍ଥାନାନ୍ତରିତ ହୋଇଛି?** OTel ରପ୍ତାନି (ଟାଇମର୍ + fetch),
   `call_logs`/ବ୍ୟବହାର ସ୍ଥାୟୀକରଣ, ସେମାଣ୍ଟିକ୍-କ୍ୟାଶ୍ ଲେଖନ; ଗୁଣବତ୍ତା ଇନ୍-ମେମୋରି
   ଏବଂ O(1) ଅଟେ (ଅସମକାଳୀନତା ଆବଶ୍ୟକ ନାହିଁ)।
3. **ଏକ ରାଉଟିଂ ଫଳାଫଳ କିପରି ଫିଡ୍ବ୍ୟାକ୍ରେ ପରିଣତ ହୁଏ?** `handleChatCore` ଏକ
   `RoutingEvent` ନିର୍ଗତ କରେ → `QualityTracker` EWMA ସ୍ଥିତି ଅଦ୍ୟତନ କରେ → `getQualityScore`
   ଅଟୋ-କମ୍ବୋ `quality` ଫ୍ୟାକ୍ଟର୍କୁ ଯୋଗାଣ କରେ।
4. **ଗୁଣବତ୍ତା ଭବିଷ୍ୟତ ରାଉଟିଂକୁ କିପରି ପ୍ରଭାବିତ କରେ?** କମ୍ ଗୁଣବତ୍ତା ସ୍କୋର୍
   `scoreAutoTargets`ରେ ସେହି ପ୍ରଦାତା/ମଡେଲ୍ର ଭାରିତ ସ୍କୋର୍କୁ କମାଏ, ଫଳରେ ଅବନତ
   ମଡେଲ୍ଗୁଡ଼ିକ ଧୀରେ ଧୀରେ କମ୍ ପ୍ରାଥମିକତା ପାଆନ୍ତି ଏବଂ ସେମାନଙ୍କର EWMA ଉନ୍ନତ ହେବା ସହିତ ପୁନରୁଦ୍ଧାର ହୁଅନ୍ତି।
5. **Future AGI କିପରି ଏକ ନିର୍ଭରତା ନ ହୋଇ ସମନ୍ୱିତ ହୋଇପାରିବ?**
   `RoutingEventSink` ଇଣ୍ଟର୍ଫେସ୍ / ଏକ ଭବିଷ୍ୟତ `Evaluator` ଆଡାପ୍ଟର୍ ମାଧ୍ୟମରେ — କୌଣସି ହାର୍ଡକୋଡ୍
   ନିର୍ଭରତା ନାହିଁ।
6. **ମୂଲ୍ୟାୟନକାରୀ ଉପଲବ୍ଧ ନଥିଲେ କ'ଣ ହୁଏ?** ରାଉଟିଂ ପ୍ରଭାବିତ ହୁଏନାହିଁ;
   କୌଣସି ପର୍ଯ୍ୟବେକ୍ଷିତ ସଙ୍କେତ ନଥିବା ମଡେଲ୍ଗୁଡ଼ିକ ପାଇଁ ଗୁଣବତ୍ତା ନିରପେକ୍ଷ (1.0)କୁ ଫଲ୍ବ୍ୟାକ୍ କରେ।
7. **ଟେଲିମେଟ୍ରି ଉପଲବ୍ଧ ନଥିଲେ କ'ଣ ହୁଏ?** OTel ସିଙ୍କ୍ କେବଳ
   ପଞ୍ଜୀକୃତ ହୁଏନାହିଁ; ରାଉଟିଂ ସ୍ତରର ଅବଶିଷ୍ଟ ଅଂଶ ଅପରିବର୍ତ୍ତିତ ଭାବେ ଚାଲେ।
8. **ଅତ୍ୟଧିକ ଲୋଡ୍ରେ କ'ଣ ହୁଏ?** OTel ବଫର୍ ସବୁଠାରୁ ପୁରୁଣା ଇଭେଣ୍ଟ୍ଗୁଡ଼ିକୁ ବାଦ ଦିଏ; ଗୁଣବତ୍ତା
   ଏବଂ ରିଙ୍ଗ୍ ବଫର୍ ଗଠନଗତ ଭାବେ ସୀମିତ; କୌଣସି ବ୍ୟାକ୍ପ୍ରେସର୍ ନାହିଁ।
9. **ଅବନତି ପରେ ପ୍ରଦାତାର ସ୍ଥିତି କିପରି ପୁନରୁଦ୍ଧାର ହୁଏ?** ସଫଳତା ସଞ୍ଚିତ ହେବା ସହିତ
   EWMA ପୁନଃ-ଅଭିସରଣ କରେ; ୱାର୍ମଅପ୍ କୋଲ୍ଡ୍ ମଡେଲ୍ଗୁଡ଼ିକୁ ନିରପେକ୍ଷ ରଖେ; ସର୍କିଟ୍ ବ୍ରେକର୍
   ସ୍ୱାଧୀନ ଭାବେ HALF_OPEN ପ୍ରୋବ୍ ମାଧ୍ୟମରେ ପୁନରୁଦ୍ଧାର କରେ।
10. **କେଉଁ ପ୍ରସ୍ତାବିତ ବୈଶିଷ୍ଟ୍ୟଗୁଡ଼ିକ ଜାଣିଶୁଣି କାର୍ଯ୍ୟକାରୀ କରାଯାଇନାହିଁ, ଏବଂ କାହିଁକି?**
    - ଶାଡୋ ଟ୍ରାଫିକ୍ / ପରୀକ୍ଷଣ — ପୂର୍ବରୁ କାର୍ଯ୍ୟକାରୀ ହୋଇଛି
      (`combo/shadowRouting.ts`); ପୁନଃନିର୍ମାଣ କରାଯାଇନାହିଁ।
    - ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକ — ପୂର୍ବରୁ କାର୍ଯ୍ୟକାରୀ ହୋଇଛି (`src/lib/guardrails/`); ନକଲ କରାଯାଇନାହିଁ।
    - ସେମାଣ୍ଟିକ୍ କ୍ୟାଶ୍ — ପୂର୍ବରୁ କାର୍ଯ୍ୟକାରୀ ହୋଇଛି (`src/lib/semanticCache.ts`); ନକଲ
      କରାଯାଇନାହିଁ।
    - ଏକ ସମ୍ପୂର୍ଣ୍ଣ ପରୀକ୍ଷଣ-ପରିଚାଳନା ପ୍ଲାଟ୍ଫର୍ମ, ଡାଟାସେଟ୍ ଟୁଲିଂ, ପ୍ରମ୍ପ୍ଟ୍-ଅପ୍ଟିମାଇଜେସନ୍
      ପ୍ଲାଟ୍ଫର୍ମ, ଭେକ୍ଟର୍ DB, କିମ୍ବା ବାଧ୍ୟତାମୂଳକ ବାହ୍ୟ OTel ଭିତ୍ତିଭୂମି — ଏକ
      ହାଲୁକା ଡାଟା ପ୍ଲେନ୍ର ପରିସର ବାହାରେ।
    - ଏକ Rust `RoutingEvent` ଷ୍ଟ୍ରକ୍ଟ୍ — ଡାଟା ପ୍ଲେନ୍ ହେଉଛି TypeScript; TS ଟାଇପ୍
      ହେଉଛି ଅନୁକୂଳିତ ସମତୁଲ୍ୟ ରୂପ।
