### ମାଗଣା ପ୍ରଦାନକାରୀଙ୍କ ଉପରେ ହାର ସୀମିତକରଣ (429 / 400 / 401)

**ଲକ୍ଷଣ**: ମାଗଣା/ପ୍ରମାଣୀକରଣ-ବିହୀନ ପ୍ରଦାନକାରୀ (opencode, auggie, ଇତ୍ୟାଦି) ସହ `model: "auto"` ବ୍ୟବହାର କରିବାବେଳେ, ଆପଣ ମଧ୍ୟେମଧ୍ୟେ ଉତ୍ତର ପରିବର୍ତ୍ତେ `HTTP 429`, `400`, କିମ୍ବା `401` ପାଆନ୍ତି। କିଛି କ୍ଷଣ ପରେ ସମାନ ପ୍ରମ୍ପ୍ଟ୍କୁ ପୁନଃଚେଷ୍ଟା କଲେ ଅନୁରୋଧଗୁଡ଼ିକ ସଫଳ ହୁଏ, କିନ୍ତୁ ପ୍ରଥମ ବିଫଳତାରେ ସ୍ୱୟଂଚାଳନ (cron jobs, agents, scripts) ବନ୍ଦ ହୋଇଯାଏ।

**ମୂଳ କାରଣ**: ତିନୋଟି ସ୍ୱାଧୀନ ବିଫଳତା ଧାରା ଏକାଠି ହୁଏ:

1. **ପ୍ରଦାନକାରୀ ହାର-ସୀମା (`429`)**: ମାଗଣା ସ୍ତରଗୁଡ଼ିକ ପ୍ରତି-ୱିଣ୍ଡୋ କୋଟା ଲାଗୁ କରିପାରନ୍ତି। ସମାନ୍ତରାଳ କଲ୍ର ହଠାତ୍ ବୃଦ୍ଧି ଏହାକୁ ଶେଷ କରିଦିଏ, ତେଣୁ ୱିଣ୍ଡୋ ରିସେଟ୍ ହେବା ପର୍ଯ୍ୟନ୍ତ ପରବର୍ତ୍ତୀ ଅନୁରୋଧ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ।
2. **ପାସ୍ଥ୍ରୁରେ ତ୍ରୁଟିପୂର୍ଣ୍ଣ ମଡେଲ୍ (`400`/`401`)**: `auto/*` ପୁଲ୍ଗୁଡ଼ିକରେ `opencode` ର ପାସ୍ଥ୍ରୁ ମଡେଲ୍ ସାମିଲ ହୋଇପାରେ, ଯେଉଁଗୁଡ଼ିକ କ୍ୟାଟାଲଗ୍ରେ ପଞ୍ଜୀକୃତ କିନ୍ତୁ ସେମାନଙ୍କର ସକ୍ରିୟ ପରିଚୟପତ୍ର ନାହିଁ (ଉଦାହରଣ ସ୍ୱରୂପ `oc/north-mini-code-free` → `401`)। ଅଟୋ-ରାଉଟର୍ ଗୋଟିଏକୁ ଚେଷ୍ଟା କରେ, ବିଫଳ ହୁଏ, ଏବଂ ଫଲ୍ବ୍ୟାକ୍ ସକ୍ରିୟ ହେବା ପୂର୍ବରୁ ତ୍ରୁଟି ପ୍ରସାରିତ ହୁଏ।
3. **ସମବର୍ତ୍ତିତା ବୃଦ୍ଧି (`429` ଲୋଡ୍ରେ)**: ଯେତେବେଳେ ଏକାଧିକ agent/cron ସେସନ୍ ଏକାସାଙ୍ଗରେ `auto` କୁ ଅନୁରୋଧ ପଠାନ୍ତି, ସମୁଦାୟ ଅନୁରୋଧ ହାର ମାଗଣା ପ୍ରଦାନକାରୀଙ୍କ ସହନଶୀଳତାକୁ ଅତିକ୍ରମ କରେ, ତେଣୁ ବୈଧ କଲ୍ଗୁଡ଼ିକୁ ମଧ୍ୟ ଅପବ୍ୟବହାର ଭାବେ ଚିହ୍ନଟ କରାଯାଏ।

**ଯାଞ୍ଚିତ ସମାଧାନ (ସମୁଦାୟ ଦ୍ୱାରା ରିପୋର୍ଟ କରାଯାଇଛି, 2026-08-10)**: ତିନୋଟି environment variables କୁ ଏପରି ଟ୍ୟୁନ୍ କରନ୍ତୁ ଯାହାଦ୍ୱାରା rotation, concurrency ଏବଂ fallback ମାଗଣା-ସ୍ତରର ଅସ୍ଥିରତାକୁ ବିଫଳ ହେବା ପରିବର୍ତ୍ତେ ସମ୍ଭାଳିପାରିବ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ରେ ଅନ୍ୟ ମଡେଲ୍/ପ୍ରଦାନକାରୀକୁ ଯାଆନ୍ତୁ (ତ୍ରୁଟିପୂର୍ଣ୍ଣ ପାସ୍ଥ୍ରୁ ମଡେଲ୍ଗୁଡ଼ିକୁ ଏଡ଼ାଇଯାଏ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ସ୍ପଷ୍ଟ ହେଭିୱେଟ୍ ପ୍ରବେଶ ସୀମା (ଡିଫଲ୍ଟ ଭାବେ ସେଟ୍ ହୋଇନାହିଁ: କୌଣସି ଅନୁରୋଧ-ଗଣନା ସୀମା ନାହିଁ, ନିମ୍ନର ଟିପ୍ପଣୀ ଦେଖନ୍ତୁ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # ଧୀର ଅପ୍ଷ୍ଟ୍ରିମ୍ ପାଇଁ ସୀମିତ ଅପେକ୍ଷାକୁ RATE_LIMIT_MAX_WAIT_MS ଡିଫଲ୍ଟଠାରୁ ଅଧିକ ବଢ଼ାନ୍ତୁ
```

ଏଗୁଡ଼ିକୁ OmniRoute ପ୍ରକ୍ରିୟା environment ରେ ସେଟ୍ କରନ୍ତୁ (daemon ରେ, ଉଦାହରଣ ସ୍ୱରୂପ LaunchAgent plist କିମ୍ବା `systemctl edit` ମାଧ୍ୟମରେ), ତା'ପରେ OmniRoute ପୁନଃଚାଳୁ କରନ୍ତୁ। rotation flag ହେଉଛି ସର୍ବାଧିକ ପ୍ରଭାବଶାଳୀ ବ୍ୟବସ୍ଥା: ଏହା ଏକ କଠିନ ବିଫଳତାକୁ ପୁଲ୍ରେ ଥିବା ଏକ ସୁସ୍ଥ ପ୍ରଦାନକାରୀ ବିରୁଦ୍ଧରେ ସ୍ୱଚ୍ଛ ପୁନଃଚେଷ୍ଟାରେ ପରିଣତ କରେ।

**ଟିପ୍ପଣୀ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ଏକାସାଙ୍ଗରେ କେତେ ହେଭିୱେଟ୍ — ଦୀର୍ଘ-କଣ୍ଟେକ୍ସ୍ଟ — ଅନୁରୋଧ ଚାଲିବ ତାହା ସୀମିତ କରେ; ଏହି ସୀମା ଏକ ପ୍ରବେଶ ଗେଟ୍, ପ୍ରଦାନକାରୀ ହାର ସୀମାକାରୀ ନୁହେଁ। **#503-fanout ଅପଡେଟ୍:** ଏହି var ଆଉ ଡିଫଲ୍ଟ ଭାବେ ସେଟ୍ ହୁଏନାହିଁ (ଏବେ ଏହା କେବଳ ସ୍ପଷ୍ଟ ଭାବେ କନଫିଗର୍ କରାଗଲେ, ଉପରୋକ୍ତ ପରି, ବାଧ୍ୟ ହୁଏ) — ଏହା ପରିବର୍ତ୍ତେ ହେଭିୱେଟ୍ ପ୍ରବେଶ ଏକ ସ୍ୱୟଂ-ବ୍ୟୁତ୍ପନ୍ନ byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ଦ୍ୱାରା ନିୟନ୍ତ୍ରିତ ହୁଏ, ଯାହା host ର ପ୍ରକୃତ memory ceiling ଆଧାରରେ ନିଜକୁ ସ୍କେଲ୍ କରେ; ତେଣୁ ଏକ ନୂଆ deployment ରେ ଏହି var କୁ ଆଦୌ ସେଟ୍ ନ କରି ମଧ୍ୟ ଅତ୍ୟନ୍ତ କମ୍ `503 chat_admission_busy` ପ୍ରତ୍ୟାଖ୍ୟାନ ଦେଖାଯିବା ଉଚିତ; ଏଠାରେ ଏହାକୁ ସ୍ପଷ୍ଟ ଭାବେ ସେଟ୍ କଲେ ମଧ୍ୟ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ପରି ଠିକ୍ ଭାବେ କାମ କରେ। ସ୍ପଷ୍ଟ byte-budget override ଗୁଡ଼ିକ 8 MiB–2 GiB ମଧ୍ୟରେ ସୀମିତ ହୁଏ। ଏକ `413 body_exceeds_budget` ଅସ୍ଥାୟୀ ନୁହେଁ: ସେହି byte budget ବଢ଼ାନ୍ତୁ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` କମାନ୍ତୁ, କିମ୍ବା process memory ceiling ବଢ଼ାନ୍ତୁ। ଏକ `inflight_bytes_budget` shed ହେଉଛି ଅସ୍ଥାୟୀ contention ଏବଂ ଏହା ପୁନଃଚେଷ୍ଟାଯୋଗ୍ୟ ରହେ। ପ୍ରତି-ପ୍ରଦାନକାରୀ ହାର ସୀମିତକରଣ (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ଏବଂ `RATE_LIMIT_AUTO_ENABLE` ଦ୍ୱାରା ପୃଥକ ଭାବେ ପରିଚାଳିତ ହୁଏ — `.env.example` ଦେଖନ୍ତୁ।

**ଏହା କାମ କରିଛି କି ନାହିଁ କିପରି ଯାଞ୍ଚ କରିବେ**: ଅତି କମ୍ ସମୟ ବ୍ୟବଧାନରେ ଆପଣଙ୍କ agent/cronକୁ ଦୁଇଥର ଚଲାନ୍ତୁ ଏବଂ ଉଭୟ ସଫଳ ହେଉଛି କି ନାହିଁ ନିଶ୍ଚିତ କରନ୍ତୁ। ସମାଧାନ ପୂର୍ବରୁ, ଦ୍ୱିତୀୟ ରନ୍ରେ ସାଧାରଣତଃ `429`/`401` ତ୍ରୁଟି ଆସେ। ସମାଧାନ ପରେ, ବିଫଳତାଗୁଡ଼ିକ (ଯଦି କିଛି ଥାଏ) ସ୍ୱଚ୍ଛ ଭାବରେ ପୁନଃଚେଷ୍ଟା କରାଯାଏ ଏବଂ କଲ୍ଟି ସମ୍ପୂର୍ଣ୍ଣ ହୁଏ। ଆପଣ `curl /monitoring/health` ମଧ୍ୟ ଚଲାଇପାରିବେ ଏବଂ provider ସଂଯୋଗଗୁଡ଼ିକରେ `rateLimitedUntil` ଫିଲ୍ଡ ସହିତ ପ୍ରଭାବିତ providerଗୁଡ଼ିକ ପାଇଁ `circuitBreakers.providerBreakers[].state` ଉପରେ ନଜର ରଖିପାରିବେ — stateଟି `CLOSED`, `DEGRADED`, `OPEN`, କିମ୍ବା `HALF_OPEN` ମଧ୍ୟରୁ ଗୋଟିଏ ହୋଇଥାଏ (`src/shared/utils/circuitBreaker.ts` ଦେଖନ୍ତୁ), ଏବଂ ବାରମ୍ବାର ବିଫଳ ହେଉଥିବା providerଟି reset window ଗୋଟିଏ probeକୁ ଅନୁମତି ଦେବା ପୂର୍ବରୁ `CLOSED → DEGRADED → OPEN`କୁ ପରିବର୍ତ୍ତିତ ହେବ (`HALF_OPEN`)।

**ଯଦି ତଥାପି 429 ଦେଖନ୍ତି**: ସେହି provider ପାଇଁ ସକ୍ରିୟ accountଟି ବାସ୍ତବରେ ତାହାର _quota_ ଶେଷ କରିଦେଇଛି (କେବଳ rate ନୁହେଁ)। OmniRoute dashboard → Providers → Accountsରେ ସେହି provider ପାଇଁ ଏକ ଦ୍ୱିତୀୟ account ଯୋଡ଼ନ୍ତୁ, କିମ୍ବା ଅନ୍ୟ ଏକ ମାଗଣା provider (ଯଥା `routeway`, `auggie`) ମିଶାନ୍ତୁ। Rotation କେବଳ ଅସ୍ଥାୟୀ rate/400/401 ସମସ୍ୟାରେ ସାହାଯ୍ୟ କରେ; quota ସମ୍ପୂର୍ଣ୍ଣ ଶେଷ ହୋଇଗଲେ ଏକ ଦ୍ୱିତୀୟ credential କିମ୍ବା ଭିନ୍ନ provider ଆବଶ୍ୟକ।

**ଯଦି vision modelଗୁଡ଼ିକରେ (`auto/vision`, `bazaarlink/*`) 403 ଦେଖନ୍ତି**: ସଂଯୁକ୍ତ accountରେ vision ସମ୍ମିଳିତ ଥିବା ଏକ paid plan ନାହିଁ, କିମ୍ବା API keyରେ ପର୍ଯ୍ୟାପ୍ତ permission ନାହିଁ। provider dashboardରେ ଯାଞ୍ଚ କରନ୍ତୁ ଯେ key scopeରେ vision/multimodal ସମ୍ମିଳିତ ଅଛି, କିମ୍ବା ଏକ paid tier account ସଂଯୋଗ କରି ତାହାକୁ vision target ଭାବେ ରଖନ୍ତୁ।

## npm install ଚେତାବନୀଗୁଡ଼ିକ (ERESOLVE / peer / deprecated)

ଆପଣ `npm install -g omniroute` ଚଲାଇବାବେଳେ, `npm warn ERESOLVE`, peer-dependency ସୂଚନା ଏବଂ `deprecated` ସନ୍ଦେଶ ପରି ଅନେକ ଚେତାବନୀ ଦେଖିପାରନ୍ତି। **ଏଗୁଡ଼ିକ ଆଶାକରାଯାଇଥିବା ଏବଂ କ୍ଷତିହୀନ।** ଆଉଟପୁଟ୍ରେ `added <N> packages` ଦେଖାଗଲେ, ଆପଣଙ୍କ ଇନଷ୍ଟଲେସନ୍ ସଫଳ ହୋଇଛି।

peer-dependency resolution ଚେତାବନୀଗୁଡ଼ିକୁ ଦମନ କରିବା ପାଇଁ, OmniRoute ସମର୍ଥିତ ଇନଷ୍ଟଲେସନ୍ ରୂପ ବ୍ୟବହାର କରନ୍ତୁ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` କେବଳ `ERESOLVE` ଏବଂ peer-dependency ସୂଚନାଗୁଡ଼ିକୁ ଦମନ କରେ। Deprecation ସୂଚନାଗୁଡ଼ିକ ଦୃଶ୍ୟମାନ ରହେ, କାରଣ ସେଗୁଡ଼ିକ transitive third-party package-ଗୁଡ଼ିକରୁ ଆସେ; ସେଗୁଡ଼ିକ ଇନଷ୍ଟଲେସନ୍ ବିଫଳ ହୋଇଥିବାର ସୂଚନା ଦିଅନ୍ତି ନାହିଁ।

ଏହି ଚେତାବନୀଗୁଡ଼ିକ OmniRoute ନିୟନ୍ତ୍ରଣ କରୁ ନଥିବା third-party package-ଗୁଡ଼ିକର ପୁରୁଣା peer-dependency range-ରୁ ଆସେ:

1. **`marked-terminal` ପାଇଁ `marked >=1 <16` ଆବଶ୍ୟକ, କିନ୍ତୁ `marked@18` ମିଳିଛି** — ବ୍ୟବହାରରେ ଏହା ଠିକ୍ ଭାବେ କାମ କରେ; upstream peer range-ଟି କେବଳ ପୁରୁଣା।
2. **`deprecated prebuild-install@7.1.3`** — ଏକ transitive native-binary fetch helper। ଏହା pinned `wreq-js` transport binding ଇନଷ୍ଟଲ୍ କରିବା ପାଇଁ
   ବ୍ୟବହୃତ ହୁଏ ନାହିଁ ଏବଂ web-cookie provider transport setup ବିଫଳ ହୋଇଥିବାର
   ସୂଚନା ଦିଏ ନାହିଁ।

**କୌଣସି ପଦକ୍ଷେପ ଆବଶ୍ୟକ ନାହିଁ** — upstream package-ଗୁଡ଼ିକୁ fork ନ କରି ଏହି ଚେତାବନୀଗୁଡ଼ିକୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ନିରବ କରାଯାଇପାରିବ ନାହିଁ।

## npm install-scripts ଅବରୋଧିତ ଚେତାବନୀ (global install)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` ଚଲାଇବାବେଳେ, ନୂତନ npm ସଂସ୍କରଣଗୁଡ଼ିକ (v11+ ଏବଂ v12+) package lifecycle script-ଗୁଡ଼ିକୁ ଡିଫଲ୍ଟ ଭାବେ ଅବରୋଧ କରନ୍ତି ଏବଂ ଏକ install-scripts ଚେତାବନୀ ପ୍ରଦର୍ଶନ କରନ୍ତି:

```
npm warn install-scripts 7ଟି package-ର install script ଅବରୋଧ କରାଯାଇଛି, କାରଣ ସେଗୁଡ଼ିକ allowScripts ଦ୍ୱାରା ଅନ୍ତର୍ଭୁକ୍ତ ନୁହେଁ:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### ଏହି ଚେତାବନୀକୁ ଅଣଦେଖା କରାଯାଇପାରିବ କି?

**ଆଂଶିକ ଭାବେ, କିନ୍ତୁ script ବିନା ଚଲାଇବା ସୁପାରିସ କରାଯାଏ ନାହିଁ।** OmniRoute-ରେ ସୁଚାରୁ fallback ବ୍ୟବସ୍ଥା ଅନ୍ତର୍ଭୁକ୍ତ: standalone bundle-ରୁ native `better-sqlite3` binding ଲୋଡ୍ କରାଯାଇ ନ ପାରିଲେ, applicationଟି `node:sqlite` କିମ୍ବା `sql.js` ପରି ବିକଳ୍ପ driver ମାଧ୍ୟମରେ fallback କରେ ([SQLite Runtime Resolution](../ops/SQLITE_RUNTIME.md) ଦେଖନ୍ତୁ)। Serverଟି ତଥାପି ଆରମ୍ଭ ହେବ, କିନ୍ତୁ `sql.js` ପରି WASM fallback-ରେ ଚଲାଇବା ଦ୍ୱାରା SQLite WAL (Write-Ahead Logging) mode ଅକ୍ଷମ ହୁଏ ଏବଂ memory ଓ disk-sync overhead ବୃଦ୍ଧି ପାଏ।

### ପ୍ରକୃତରେ କେଉଁ script-ଗୁଡ଼ିକ ଆବଶ୍ୟକ?

ଅବରୋଧିତ ସମସ୍ତ script OmniRoute ଚଲାଇବା ପାଇଁ ଅତ୍ୟାବଶ୍ୟକ ନୁହେଁ:

- **ଅତ୍ୟାବଶ୍ୟକ (`omniroute`, `better-sqlite3`):** OmniRoute ଏକ Next.js standalone application bundle (`dist/`) ରୁ ଚାଲେ। ଇନଷ୍ଟଲେସନ୍ ସମୟରେ, npm top-level `node_modules/better-sqlite3/` ମଧ୍ୟରେ host-specific native SQLite driver ଡାଉନଲୋଡ୍ କିମ୍ବା compile କରେ। ତା’ପରେ OmniRoute-ର `postinstall` script (`scripts/build/postinstall.mjs`) ଏହି host-specific binary-ଗୁଡ଼ିକୁ ଯାଞ୍ଚ କରି `dist/node_modules/` ମଧ୍ୟକୁ କପି କରେ, ଯାହାଦ୍ୱାରା standalone server ସେଗୁଡ଼ିକୁ ଆକ୍ସେସ୍ କରିପାରେ। `omniroute`-ର postinstall script ଅବରୋଧିତ ହେଲେ, ଏହି copy ପଦକ୍ଷେପଟି ଏଡ଼ାଇ ଦିଆଯାଏ।
- **ଇଚ୍ଛାଧୀନ/transitive (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** ଏଗୁଡ଼ିକ build helper, watcher tool କିମ୍ବା system keychain utility। ସେଗୁଡ଼ିକୁ ଅନୁମତି ଦେଲେ build ଚେତାବନୀଗୁଡ଼ିକ ପ୍ରତିରୋଧ ହୁଏ, କିନ୍ତୁ ମୂଳ routing କାର୍ଯ୍ୟକାରିତା ପାଇଁ ସେଗୁଡ଼ିକ ଆବଶ୍ୟକ ନୁହେଁ।
- **ବାଦ୍ ଦିଆଯାଇଛି (`onnxruntime-node`):** ସ୍ଥାନୀୟ AI embedding ପାଇଁ ଏକ ଇଚ୍ଛାଧୀନ dependency ଏବଂ OmniRoute ଚଲାଇବା ପାଇଁ ଏହା **ଆବଶ୍ୟକ ନୁହେଁ**। ଏହାର postinstall script NuGet ରୁ ପ୍ରାୟ ~300MB CUDA asset ଡାଉନଲୋଡ୍ କରେ; ସମର୍ଥିତ hardware-ରେ ସ୍ଥାନୀୟ ONNX acceleration ବ୍ୟବହାର କରିବାକୁ ଆପଣ ସ୍ପଷ୍ଟ ଭାବେ ଇଚ୍ଛା କରୁ ନଥିଲେ, ଏହାକୁ allow-list-ରେ ସାମିଲ କରନ୍ତୁ ନାହିଁ।

### ସୁପାରିସକୃତ ସମାଧାନ

global install ସମୟରେ ଆବଶ୍ୟକ install script-ଗୁଡ଼ିକୁ ଅନୁମତି ଦେବା ଏବଂ ଚେତାବନୀଗୁଡ଼ିକୁ ନିରବ କରିବା ପାଇଁ, OmniRoute ଓ ଏହାର native dependency-ଗୁଡ଼ିକ ପାଇଁ `--allow-scripts` ପାସ୍ କରନ୍ତୁ:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

ବିକଳ୍ପ ଭାବେ, ଆପଣଙ୍କ user account-ର ସମସ୍ତ global installation ପାଇଁ ଏହାକୁ ସ୍ଥାୟୀ ଭାବେ configure କରିବାକୁ:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### ଆପଣଙ୍କ ଇନଷ୍ଟଲେସନ୍ ଯାଞ୍ଚ କରନ୍ତୁ

ଇନଷ୍ଟଲେସନ୍ ପରେ, native binding ଏବଂ runtime environment ସଠିକ୍ ଅବସ୍ଥାରେ ଅଛି ବୋଲି ନିଶ୍ଚିତ କରିବାକୁ built-in diagnostic tool ଚଲାନ୍ତୁ:

```bash
omniroute doctor
```

## Gemini Web ଏବଂ Playwright Chromium

ଯଦି ଏକ Gemini Web ଅନୁରୋଧ `503` ଫେରାଏ ଏବଂ Playwright Chromium
ଇନଷ୍ଟଲ୍ ହୋଇନାହିଁ ବୋଲି ଏକ ସନ୍ଦେଶ ଦିଏ, ତେବେ npm ପ୍ୟାକେଜ୍ ଉପସ୍ଥିତ ଅଛି କିନ୍ତୁ ବ୍ରାଉଜର୍ ବାଇନେରୀ ଅନୁପସ୍ଥିତ।
Playwright ଜାଣିଶୁଣି ବ୍ରାଉଜର୍ ଡାଉନଲୋଡ୍ଗୁଡ଼ିକୁ npm ପ୍ୟାକେଜ୍
ଇନଷ୍ଟଲେସନ୍ରୁ ଅଲଗା ରଖେ, ତେଣୁ ବ୍ରାଉଜର୍ ଇନଷ୍ଟଲ୍ ନହେବା ପର୍ଯ୍ୟନ୍ତ ଏହି ପ୍ରତିକ୍ରିୟା ଆଶା କରାଯାଏ।

ଏକ ଗ୍ଲୋବାଲ୍ npm ଇନଷ୍ଟଲେସନ୍ ପାଇଁ, OmniRoute ପ୍ୟାକେଜ୍ର
ଡିରେକ୍ଟୋରୀରୁ Chromium ଇନଷ୍ଟଲ୍ କରନ୍ତୁ, ଯାହାଦ୍ୱାରା ବ୍ରାଉଜର୍ କ୍ୟାଶ୍ ସେହି Playwright ଇନଷ୍ଟଲେସନ୍ର ଅଂଶ ହେବ:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

ଇନଷ୍ଟଲେସନ୍ ପରେ OmniRoute ପୁନଃଚାଳୁ କରନ୍ତୁ, ତା’ପରେ Gemini Web ଅନୁରୋଧକୁ ପୁଣି ଚେଷ୍ଟା କରନ୍ତୁ। ଯଦି ଆପଣ
ଏକ Docker ଇମେଜ୍ରୁ OmniRoute ଚଲାନ୍ତି, ତେବେ `-web` ଇମେଜ୍ (କିମ୍ବା `runner-web`
ବିଲ୍ଡ ଟାର୍ଗେଟ୍) ବ୍ୟବହାର କରନ୍ତୁ, ଯେଉଁଥିରେ Chromium ଏବଂ ଏହାର ନିର୍ଭରତାଗୁଡ଼ିକ ସାମିଲ ଅଛି; ବେସ୍ ଇମେଜ୍ରେ
ସେଗୁଡ଼ିକ ନାହିଁ।

## ଆଣ୍ଟିଭାଇରସ୍ର ମିଥ୍ୟା ପଜିଟିଭ୍

<a name="antivirus-false-positives"></a>

### Avast/AVG `README.md`-କୁ `MD:HttpRequest-inf[Susp]` ଭାବେ କ୍ୱାରାଣ୍ଟାଇନ୍ କରେ

**ଏହା ଏକ ମିଥ୍ୟା ପଜିଟିଭ୍। କୌଣସି ଜିନିଷ ସଂକ୍ରମିତ ହୋଇନାହିଁ ଏବଂ କୌଣସି ପଦକ୍ଷେପର ଆବଶ୍ୟକତା ନାହିଁ।**

Avast ଏବଂ AVG ଏକ ହ୍ୟୁରିଷ୍ଟିକ୍ ଚଲାନ୍ତି, ଯାହା ଅନେକ
HTTP ଅନୁରୋଧ ପରି ଦେଖାଯାଉଥିବା ଲିଙ୍କ୍ ଥିବା ସାଧାରଣ-ଟେକ୍ସଟ୍/Markdown ଫାଇଲ୍ଗୁଡ଼ିକୁ ଫ୍ଲାଗ୍ କରେ। OmniRouteର `README.md` npm ପ୍ୟାକେଜ୍ ଭିତରେ ଅନ୍ତର୍ଭୁକ୍ତ ହୋଇ ଆସେ (ଏହା
`package.json` → `files`ରେ ତାଲିକାଭୁକ୍ତ), ତେଣୁ ଏକ ଗ୍ଲୋବାଲ୍ ଇନ୍ଷ୍ଟଲ୍ରେ ଏହା `node_modules/omniroute/README.md`ରେ
ପହଞ୍ଚେ — ଏବଂ ଏଥିରେ ପ୍ରାୟ 15ଟି `http://localhost:20128/...` ଉଦାହରଣ ରହିଛି (MCP
HTTP/SSE ଏଣ୍ଡପଏଣ୍ଟ୍ଗୁଡ଼ିକ, A2A `.well-known` URL ଏବଂ `curl` ସ୍ନିପେଟ୍ଗୁଡ଼ିକ)। ସେହି ଲିଙ୍କ୍ଗୁଡ଼ିକର ଘନତା
ହ୍ୟୁରିଷ୍ଟିକ୍କୁ ସକ୍ରିୟ କରିବା ପାଇଁ ଯଥେଷ୍ଟ।

ଯଦି ଏହା କେବଳ ସମ୍ପ୍ରତି ଆରମ୍ଭ ହୋଇଛି: ଫାଇଲ୍ର ପ୍ରକାରରେ କୌଣସି ପରିବର୍ତ୍ତନ ହୋଇନାହିଁ। READMEର
ଏଣ୍ଡପଏଣ୍ଟ୍ ଟେବୁଲ୍ ବଢ଼ିଛି (MCP HTTP + SSE + A2A ଯୋଡ଼ାଯାଇଛି) ଏବଂ ଅଧିକ `curl` ଉଦାହରଣ ଯୋଡ଼ାଯାଇଛି, ଯାହା
ଏହାକୁ ସୀମାରୁ ଆଗକୁ ନେଇଯାଇଛି।

ଏହି ଫାଇଲ୍ଟି ଶୂନ୍ୟ ନିଷ୍ପାଦନଯୋଗ୍ୟ ବିଷୟବସ୍ତୁ ଥିବା ଏକ ନିଷ୍କ୍ରିୟ ଡକ୍ୟୁମେଣ୍ଟେସନ୍। ଆପଣ ଏହାକୁ ସୁରକ୍ଷିତ ଭାବେ
କ୍ୱାରାଣ୍ଟାଇନ୍ରୁ ପୁନଃସ୍ଥାପନ କରିପାରିବେ।

**କ’ଣ କରିବେ:**

1. **ବିଜ୍ଞପ୍ତିଗୁଡ଼ିକୁ ବନ୍ଦ କରନ୍ତୁ** — ଆପଣଙ୍କ ଆଣ୍ଟିଭାଇରସ୍ରେ ଇନ୍ଷ୍ଟଲ୍ ଡିରେକ୍ଟୋରିକୁ ବାଦ ଦିଅନ୍ତୁ
   (Avast: Settings → Exceptions), ଏବଂ ଆପଣଙ୍କ ଗ୍ଲୋବାଲ୍ `node_modules` ପଥ ଏବଂ/କିମ୍ବା
   OmniRoute ଡାଟା ଡିରେକ୍ଟୋରି (`~/.omniroute/`) ଯୋଡ଼ନ୍ତୁ।
2. **ମିଥ୍ୟା ପଜିଟିଭ୍ଟି ରିପୋର୍ଟ କରନ୍ତୁ** — <https://www.avast.com/false-positive-file-form.php>,
   କ୍ୱାରାଣ୍ଟାଇନ୍ ହୋଇଥିବା `README.md` ସଂଲଗ୍ନ କରନ୍ତୁ। ଏହି ସମାଧାନ ସମସ୍ତଙ୍କୁ ସାହାଯ୍ୟ କରେ, କାରଣ ଏହା
   ଏକ ଟେକ୍ସଟ୍ ଫାଇଲ୍ ପ୍ରତି ଭେଣ୍ଡର୍ର ହ୍ୟୁରିଷ୍ଟିକ୍ର ଅତ୍ୟଧିକ ପ୍ରତିକ୍ରିୟା।

**ଆମେ ନିଜ ପକ୍ଷରୁ ଏହାକୁ କାହିଁକି "ସମାଧାନ" କରୁନାହୁଁ:** ସମସ୍ତ ଉଦାହରଣ `http://localhost` ଅଟେ, ଏବଂ
ସ୍ୱୟଂ-ସ୍ୱାକ୍ଷରିତ ସାର୍ଟିଫିକେଟ୍ର ଅସୁବିଧା ବିନା localhostକୁ `https` କରାଯାଇପାରିବ ନାହିଁ। ଗୋଟିଏ ଭେଣ୍ଡର୍ର ହ୍ୟୁରିଷ୍ଟିକ୍କୁ
ଏଡ଼ାଇବା ପାଇଁ ଡକ୍ୟୁମେଣ୍ଟ୍କୁ ବିକୃତ କରିବା ଏକ ସ୍କାନର୍ ବଗ୍କୁ ସନ୍ତୁଷ୍ଟ କରିବା ପାଇଁ ପ୍ରତ୍ୟେକ ପାଠକଙ୍କୁ ଅସୁବିଧାରେ ପକାଇବ।

### Kaspersky ଡେସ୍କଟପ୍ ଆପ୍କୁ `PDM:Trojan.Win32.Generic` ଭାବେ ଫ୍ଲାଗ୍ କରେ

**ଏହା ଏକ ଆଚରଣଗତ ହ୍ୟୁରିଷ୍ଟିକ୍ରୁ ଆସିଥିବା ମିଥ୍ୟା ପଜିଟିଭ୍। କୌଣସି ଜିନିଷ ସଂକ୍ରମିତ ହୋଇନାହିଁ।** Kasperskyର
`PDM:` ଉପସର୍ଗର ଅର୍ଥ ହେଉଛି ନିଷ୍ପତ୍ତିଟି ଏହାର Proactive Defense Module (System Watcher)ରୁ ଆସିଛି,
ଯାହା ଇନ୍ଷ୍ଟଲର୍କୁ ଜଣାଶୁଣା ମାଲୱେର୍ ସହ ମେଳ କରିବା ପରିବର୍ତ୍ତେ ଏହା _କ’ଣ କରେ_ ତାହା ବିଚାର କରେ। ଯେତେବେଳେ
ଏହା ସକ୍ରିୟ ହୁଏ, Kaspersky ସମ୍ପୂର୍ଣ୍ଣ ଇନ୍ଷ୍ଟଲେସନ୍କୁ "ରୋଲ୍ ବ୍ୟାକ୍" କରେ — ପୂର୍ବରୁ
ଲେଖାଯାଇଥିବା ଫାଇଲ୍ଗୁଡ଼ିକୁ ବିଲୋପ କରେ — ତେଣୁ ଆପ୍ଟି ଶେଷରେ ନଷ୍ଟ ହୋଇଯାଏ କିମ୍ବା ଗାୟବ ହୋଇଯାଏ।

ଏହା ଫ୍ଲାଗ୍ କରୁଥିବା ଫାଇଲ୍ଗୁଡ଼ିକ ଡେସ୍କଟପ୍ ଆପ୍ ସହ ବଣ୍ଡଲ୍ କରାଯାଇଥିବା ଘୋଷିତ, ଓପନ୍-ସୋର୍ସ ନିର୍ଭରଶୀଳତାଗୁଡ଼ିକର
ମାନକ ଅଂଶ, ଉଦାହରଣ ସ୍ୱରୂପ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ଏବଂ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ଇନ୍-ଆପ୍ ପ୍ରଦାନକାରୀ ଲଗଇନ୍ ଏବଂ ବ୍ରାଉଜର୍-ସମର୍ଥିତ ଚାଟ୍ ପାଇଁ
  ବ୍ୟବହୃତ ବ୍ରାଉଜର୍-ଅଟୋମେସନ୍ ଲାଇବ୍ରେରୀ।
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ୱେବ୍-କୁକି ପ୍ରଦାନକାରୀଙ୍କ ଉପରେ ବ୍ରାଉଜର୍-ଫିଙ୍ଗରପ୍ରିଣ୍ଟ ହୋଇଥିବା HTTP ପାଇଁ ବ୍ୟବହୃତ ପିନ୍ କରାଯାଇଥିବା `wreq-js` ନେଟିଭ୍ ବାଇଣ୍ଡିଂ
  (`<arch>` ହେଉଛି `x64` କିମ୍ବା `arm64`)।

**ଏହା କାହିଁକି ସକ୍ରିୟ ହୁଏ:** Windows ଇନ୍ଷ୍ଟଲର୍ଟି **ଏପର୍ଯ୍ୟନ୍ତ କୋଡ୍-ସ୍ୱାକ୍ଷରିତ ହୋଇନାହିଁ**, ତେଣୁ ଏକ ସ୍ୱାକ୍ଷରବିହୀନ NSIS
ଇନ୍ଷ୍ଟଲର୍ର କୌଣସି ଖ୍ୟାତି ନଥାଏ ଏବଂ ଆଚରଣଗତ ହ୍ୟୁରିଷ୍ଟିକ୍ଗୁଡ଼ିକ ସର୍ବାଧିକ ଆକ୍ରମଣାତ୍ମକତାରେ ଚାଲେ। ଏହା ସହ
ଏକ ବଣ୍ଡଲ୍ କରାଯାଇଥିବା ନେଟିଭ୍ DLL ଏବଂ `%LOCALAPPDATA%\Programs\OmniRoute` ଅଧୀନରେ ଲେଖାଯାଇଥିବା ଶହ ଶହ `.js` ଫାଇଲ୍
(Next.js ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ବିଲ୍ଡରୁ ହ୍ୟାସ୍-ପ୍ରତ୍ୟୟଯୁକ୍ତ ପ୍ୟାକେଜ୍ ଡିରେକ୍ଟୋରିଗୁଡ଼ିକ ସମେତ) ମିଶି
ହ୍ୟୁରିଷ୍ଟିକ୍କୁ ସକ୍ରିୟ କରିବା ପାଇଁ ଯଥେଷ୍ଟ। କୋଡ୍ ସାଇନିଂର ଯୋଜନା ରହିଛି;
ଏହା କାର୍ଯ୍ୟକାରୀ ହେବା ପର୍ଯ୍ୟନ୍ତ ନୂଆ ରିଲିଜ୍ଗୁଡ଼ିକରେ ଏହା ପୁନରାବୃତ୍ତି ହୋଇପାରେ।

**କ’ଣ କରିବେ:**

1. **ପ୍ରଥମେ ଆପଣଙ୍କ ଡାଉନଲୋଡ୍ ଯାଞ୍ଚ କରନ୍ତୁ** (ଏହା ଫାଇଲ୍ଟି ସହ ହସ୍ତକ୍ଷେପ କରାଯାଇଥିବା ସମ୍ଭାବନାକୁ ବାଦ ଦିଏ)। ପ୍ରତ୍ୟେକ ରିଲିଜ୍
   `latest.yml` ପ୍ରକାଶ କରେ, ଯାହାର `sha512` ଫିଲ୍ଡ (base64) `OmniRoute.Setup.<version>.exe`
   ଇନ୍ଷ୍ଟଲର୍କୁ ଆବୃତ କରେ। PowerShellରେ, ଇନ୍ଷ୍ଟଲର୍ ଥିବା ଫୋଲ୍ଡର୍ରୁ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ଆଉଟପୁଟ୍ଟି `latest.yml` → `sha512` ସହ ମେଳ ଖାଇବା ଆବଶ୍ୟକ। ଯଦି ଏହା ମେଳ ଖାଏ ନାହିଁ, ଫାଇଲ୍ଟି ବିଲୋପ କରନ୍ତୁ ଏବଂ
   କେବଳ [GitHub ରିଲିଜ୍ ପୃଷ୍ଠା](https://github.com/diegosouzapw/OmniRoute/releases)ରୁ ପୁନଃ ଡାଉନଲୋଡ୍ କରନ୍ତୁ।
2. **ପୁନଃସ୍ଥାପନ + ବାଦ ଦିଅନ୍ତୁ** — ରୋଲ୍ ବ୍ୟାକ୍ ହୋଇଥିବା ଆଇଟମ୍ଗୁଡ଼ିକୁ କ୍ୱାରାଣ୍ଟାଇନ୍ରୁ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ ଏବଂ
   `%LOCALAPPDATA%\Programs\OmniRoute` ପାଇଁ ଏକ ବାଦ ଯୋଡ଼ନ୍ତୁ (Kaspersky → Settings → Threats and Exclusions),
   ତା’ପରେ ପୁନଃ ଇନ୍ଷ୍ଟଲ୍ କରନ୍ତୁ।
3. **ମିଥ୍ୟା ପଜିଟିଭ୍ଟି ରିପୋର୍ଟ କରନ୍ତୁ** — <https://opentip.kaspersky.com/>। ବ୍ୟବହାରକାରୀଙ୍କ ଦ୍ୱାରା ଦାଖଲ ହୋଇଥିବା ମିଥ୍ୟା ପଜିଟିଭ୍
   ରିପୋର୍ଟଗୁଡ଼ିକ ପ୍ରକୃତରେ ଅନୁମୋଦିତ ତାଲିକାରେ ସାମିଲ ହେବାକୁ ଦ୍ରୁତ କରେ।

### ଲଗଇନ୍ ପୃଷ୍ଠା କ୍ରାଶ୍ ହୁଏ କିମ୍ବା "Module self-registration" ତ୍ରୁଟି ଦେଖାଏ

**କାରଣ:** ଆପଣ OmniRoute ଦ୍ୱାରା ଅନୁମୋଦିତ ସୁରକ୍ଷିତ ରନ୍ଟାଇମ୍ର ସର୍ବନିମ୍ନ ସୀମା ବାହାରେ ଥିବା ଏକ Node.js ସଂସ୍କରଣ ଚଳାଉଛନ୍ତି। ସାଧାରଣତଃ ଏହା ସେତେବେଳେ ଘଟେ, ଯେତେବେଳେ Node 22 କିମ୍ବା 24ର ଏକ ପୁରୁଣା ପ୍ୟାଚ୍ ସ୍ତର ଚଳାଯାଏ, ଯାହା OmniRoute ଆବଶ୍ୟକ କରୁଥିବା ପ୍ୟାଚ୍ଯୁକ୍ତ ସୁରକ୍ଷା ସୀମାଠାରୁ ନିମ୍ନରେ ଥାଏ।

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଲଗଇନ୍ ପୃଷ୍ଠା ଏକ ଖାଲି ସ୍କ୍ରିନ୍ କିମ୍ବା ସର୍ଭର୍ ତ୍ରୁଟି ଦେଖାଏ
- କନ୍ସୋଲ୍ରେ `Error: Module did not self-register` କିମ୍ବା ସମାନ ନେଟିଭ୍ ବାଇଣ୍ଡିଂ ତ୍ରୁଟି ଦେଖାଯାଏ
- ଯଦି ରନ୍ଟାଇମ୍ ସମର୍ଥିତ ସୁରକ୍ଷା ନୀତି ବାହାରେ ଥାଏ, ତେବେ ଲଗଇନ୍ ପୃଷ୍ଠା ଆପଣଙ୍କ Node ସଂସ୍କରଣ ସହିତ ଏକ **କମଳା ଚେତାବନୀ ବ୍ୟାନର୍** ଦେଖାଏ

**ସମାଧାନ:**

1. ଏକ ସମର୍ଥିତ Node.js LTS ରିଲିଜ୍ ସଂସ୍ଥାପନ କରନ୍ତୁ (ସୁପାରିସ୍: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ଆପଣଙ୍କ ସଂସ୍କରଣ ଯାଞ୍ଚ କରନ୍ତୁ: `node --version` 24.x LTS ଶୃଙ୍ଖଳାରେ `v24.0.0` କିମ୍ବା ତାଠାରୁ ନୂତନ ସଂସ୍କରଣ ଦେଖାଇବା ଉଚିତ
3. OmniRoute ପୁନଃସଂସ୍ଥାପନ କରନ୍ତୁ: `npm install -g omniroute`
4. ପୁନଃଆରମ୍ଭ କରନ୍ତୁ: `omniroute`

> **ସମର୍ଥିତ ସୁରକ୍ଷିତ ସଂସ୍କରଣଗୁଡ଼ିକ:** `>=22.22.2 <23` କିମ୍ବା `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) ଏବଂ Node.js 26 ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ସମର୍ଥିତ।

### npm v11+: `better-sqlite3` ସଂସ୍ଥାପିତ ହୋଇନାହିଁ (ମଡ୍ୟୁଲ୍ ମିଳୁନାହିଁ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**କାରଣ:** npm v11 (Node.js 24+ ସହିତ ପ୍ରଦାନ କରାଯାଇଥାଏ) ଡିଫଲ୍ଟ ଭାବରେ ବୈକଳ୍ପିକ
ନିର୍ଭରତାଗୁଡ଼ିକ ପାଇଁ ସଂସ୍ଥାପନ ସ୍କ୍ରିପ୍ଟଗୁଡ଼ିକୁ ଅବରୋଧ କରେ। ଯେହେତୁ `better-sqlite3`, `optionalDependencies`ରେ ତାଲିକାଭୁକ୍ତ
ଏବଂ ନେଟିଭ୍ କମ୍ପାଇଲେସନ୍ (`node-gyp rebuild`) ଆବଶ୍ୟକ କରେ, npm ନିରବରେ ଏହାକୁ ଏଡ଼ାଇଯାଏ।

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ `Cannot find module 'better-sqlite3'` ସହିତ ସର୍ଭର୍ କ୍ରାଶ୍ ହୁଏ
- `ls node_modules/better-sqlite3` "ଏପରି କୌଣସି ଫାଇଲ୍ କିମ୍ବା ଡିରେକ୍ଟୋରୀ ନାହିଁ" ଦେଖାଏ
- `npm ls better-sqlite3` `(empty)` ଦେଖାଏ

**ସମାଧାନ:**

1. ସଂସ୍ଥାପନ ସ୍କ୍ରିପ୍ଟଗୁଡ଼ିକୁ ଅନୁମୋଦନ କରି ପୁନଃସଂସ୍ଥାପନ କରନ୍ତୁ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. କିମ୍ବା ପୂର୍ବରୁ ବିଲ୍ଡ୍ ହୋଇଥିବା ପ୍ୟାକେଜ୍କୁ ମାନୁଆଲ୍ ଭାବେ ସଂସ୍ଥାପନ କରନ୍ତୁ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ଏହା କାମ କରୁଛି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**କାରଣ:** ଏକ ଗ୍ଲୋବାଲ୍ `npm install -g omniroute` ପରେ, ପ୍ୟାକେଜ୍ ଭିତରେ ଥିବା `better-sqlite3` ନେଟିଭ୍ ବାଇନାରିଟି ସ୍ଥାନୀୟ ଭାବେ ଚାଲୁଥିବା ଆର୍କିଟେକ୍ଚର୍ କିମ୍ବା Node.js ABIଠାରୁ ଭିନ୍ନ ଏକ ଆର୍କିଟେକ୍ଚର୍ କିମ୍ବା Node.js ABI ପାଇଁ କମ୍ପାଇଲ୍ ହୋଇଥାଇପାରେ। ପୂର୍ବରୁ ବିଲ୍ଡ୍ ହୋଇଥିବା ବାଇନାରି ଆପଣଙ୍କ ପରିବେଶ ସହିତ ମେଳ ନ ଖାଇଲେ, macOSରେ (Apple Silicon ଏବଂ Intel ଉଭୟରେ) ଏହା ସାଧାରଣତଃ ଘଟେ।

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ ଏକ `dlopen` ତ୍ରୁଟି ସହିତ ସର୍ଭର୍ ତୁରନ୍ତ ବିଫଳ ହୁଏ
- ତ୍ରୁଟିରେ `slice is not valid mach-o file` ଥାଏ
- ସମ୍ପୂର୍ଣ୍ଣ ଉଦାହରଣ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ସମାଧାନ — ଆପଣଙ୍କ ସ୍ଥାନୀୟ ପରିବେଶ ପାଇଁ ପୁନଃବିଲ୍ଡ୍ କରନ୍ତୁ (Node.js ଡାଉନ୍ଗ୍ରେଡ୍ ଆବଶ୍ୟକ ନୁହେଁ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ଟିପ୍ପଣୀ:** ଏହା ଆପଣଙ୍କ ସ୍ଥାନୀୟ Node.js ସଂସ୍କରଣ ଏବଂ CPU ଆର୍କିଟେକ୍ଚର୍ ଅନୁଯାୟୀ ନେଟିଭ୍ ବାଇଣ୍ଡିଂକୁ ପୁନଃକମ୍ପାଇଲ୍ କରେ, ଯାହା ବାଇନାରି ଅମେଳକୁ ସମାଧାନ କରେ। ଆଧିକାରିକ ଭାବେ ସମର୍ଥିତ ରନ୍ଟାଇମ୍ ପରିସର ହେଉଛି **`>=22.22.2 <23` କିମ୍ବା `>=24.0.0 <27`** (`src/shared/utils/nodeRuntimeSupport.ts`ରେ `SUPPORTED_NODE_RANGE`, `package.json`ର `engines` ଫିଲ୍ଡ ସହିତ ସମନ୍ୱିତ)। Node.js 24.x LTS (Krypton) ଏବଂ Node.js 26, `better-sqlite3` v12.x ସହିତ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ସମର୍ଥିତ।

## ପ୍ରକ୍ସି ସମସ୍ୟାଗୁଡ଼ିକ

<a name="proxy-issues"></a>

### ପ୍ରଦାତା ଯାଞ୍ଚରେ "fetch failed" ଦେଖାଯାଉଛି

**କାରଣ:** API କୀ ଯାଞ୍ଚ ଏଣ୍ଡପଏଣ୍ଟ (`POST /api/providers/validate`) ପୂର୍ବରୁ ପ୍ରକ୍ସି କନଫିଗରେସନ୍କୁ ଏଡ଼ାଇ ଯାଉଥିଲା, ଯାହା ପ୍ରକ୍ସି ରାଉଟିଂ ଆବଶ୍ୟକ କରୁଥିବା ପରିବେଶଗୁଡ଼ିକରେ ବିଫଳତା ସୃଷ୍ଟି କରୁଥିଲା।

**ସମାଧାନ (v3.5.5+):** ଏହା ବର୍ତ୍ତମାନ ସମାଧାନ କରାଯାଇଛି। ପ୍ରଦାତା ଯାଞ୍ଚ `runWithProxyContext` ମାଧ୍ୟମରେ ରାଉଟ୍ ହୁଏ ଏବଂ ସ୍ୱୟଂଚାଳିତ ଭାବେ ପ୍ରଦାତା-ସ୍ତରୀୟ ଓ ଗ୍ଲୋବାଲ୍ ପ୍ରକ୍ସି ସେଟିଂସ୍କୁ ସମ୍ମାନ କରେ।

### ଟୋକେନ୍ ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ "fetch failed" ସହିତ ବିଫଳ ହେଉଛି

**କାରଣ:** ବ୍ୟାକଗ୍ରାଉଣ୍ଡ OAuth ଟୋକେନ୍ ରିଫ୍ରେଶ୍ ପ୍ରତ୍ୟେକ କନେକ୍ସନ୍ ପାଇଁ ପ୍ରକ୍ସି କନଫିଗରେସନ୍କୁ ରିଜଲ୍ଭ କରୁନଥିଲା।

**ସମାଧାନ (v3.5.5+):** ଟୋକେନ୍ ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ ସ୍କେଜୁଲର୍ ବର୍ତ୍ତମାନ ରିଫ୍ରେଶ୍ କରିବାକୁ ଚେଷ୍ଟା କରିବା ପୂର୍ବରୁ ପ୍ରତ୍ୟେକ କନେକ୍ସନ୍ ପାଇଁ ପ୍ରକ୍ସି କନଫିଗ୍ ରିଜଲ୍ଭ କରେ। v3.5.5+କୁ ଅପଡେଟ୍ କରନ୍ତୁ।

### SOCKS5 ପ୍ରକ୍ସି "invalid onRequestStart method" ଫେରାଉଛି

**କାରଣ:** Node.js 22ରେ, undici@8 ଡିସ୍ପାଚର୍ Nodeର ବିଲ୍ଟ-ଇନ୍ `fetch()` ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ସହିତ ଅସଙ୍ଗତ।

**ସମାଧାନ (v3.5.5+):** ଏକ ପ୍ରକ୍ସି ଡିସ୍ପାଚର୍ ସକ୍ରିୟ ଥିବାବେଳେ OmniRoute ବର୍ତ୍ତମାନ undiciର ନିଜସ୍ୱ `fetch()` ଫଙ୍କସନ୍ ବ୍ୟବହାର କରେ, ଯାହା ସୁସଙ୍ଗତ ଆଚରଣ ସୁନିଶ୍ଚିତ କରେ। v3.5.5+କୁ ଅପଡେଟ୍ କରନ୍ତୁ।

### WSL ଅଧୀନରେ MITM ପ୍ରକ୍ସି: Windows ହୋଷ୍ଟରେ ଥିବା ଡେସ୍କଟପ୍ ଆପ୍ଗୁଡ଼ିକ ଇଣ୍ଟରସେପ୍ଟ ହେଉନାହାନ୍ତି

**କାରଣ:** MITM ପ୍ରକ୍ସି ଏବଂ ଏହାର CA ସାର୍ଟିଫିକେଟ୍ OmniRoute ଚାଲୁଥିବା ପରିବେଶରେ ଇନଷ୍ଟଲ୍ ହୁଏ। WSL ଅଧୀନରେ ସେହି ପରିବେଶଟି Linux ଗେଷ୍ଟ ହୋଇଥିବାବେଳେ, AI ଡେସ୍କଟପ୍ ଆପ୍ଗୁଡ଼ିକ (Kiro, Trae, Copilot, Zed, …) Windows ହୋଷ୍ଟରେ ଚାଲେ। ହୋଷ୍ଟ ଆପ୍ଗୁଡ଼ିକ ଗେଷ୍ଟର ସାର୍ଟିଫିକେଟ୍ ଷ୍ଟୋର୍କୁ ବିଶ୍ୱାସ କରନ୍ତି ନାହିଁ ଏବଂ ଗେଷ୍ଟର ସିଷ୍ଟମ୍ ପ୍ରକ୍ସି ମାଧ୍ୟମରେ ରାଉଟ୍ ହୁଅନ୍ତି ନାହିଁ, ତେଣୁ ସେଠାରେ ଡେସ୍କଟପ୍ ଇଣ୍ଟରସେପ୍ସନ୍ ସକ୍ରିୟ ହୁଏ ନାହିଁ।

**ସୁପାରିସ:** ଯେଉଁ ଡେସ୍କଟପ୍ ଆପ୍ଗୁଡ଼ିକୁ ଆପଣ ଇଣ୍ଟରସେପ୍ଟ କରିବାକୁ ଚାହାନ୍ତି, ସେଗୁଡ଼ିକ ଥିବା ସମାନ OSରେ OmniRouteକୁ ନେଟିଭ୍ ଭାବେ ଚଲାନ୍ତୁ (Windows ଆପ୍ଗୁଡ଼ିକ ପାଇଁ Windows; macOS/Linux ପାଇଁ ମଧ୍ୟ ସେହିପରି)। ହୋଷ୍ଟ ଆପ୍ଗୁଡ଼ିକୁ ଟାର୍ଗେଟ୍ କରିବା ସମୟରେ OmniRouteକୁ WSL ଭିତରେ ରଖିବା ପାଇଁ Windows ହୋଷ୍ଟରେ ଜେନେରେଟ୍ ହୋଇଥିବା CA ସାର୍ଟିଫିକେଟ୍କୁ ମାନୁଆଲ୍ ଭାବେ ବିଶ୍ୱସ୍ତ କରିବା ଏବଂ ପ୍ରତ୍ୟେକ ହୋଷ୍ଟ ଆପ୍ର ନେଟୱର୍କ/ପ୍ରକ୍ସି ସେଟିଂସ୍କୁ WSL ପ୍ରକ୍ସି ଏଣ୍ଡପଏଣ୍ଟ ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରିବା ଆବଶ୍ୟକ — ଏହା ଏକ ଅସମର୍ଥିତ ଓ ଭଙ୍ଗୁର ସେଟଅପ୍।

## କ୍ଲାଉଡ୍ ସମସ୍ୟାଗୁଡ଼ିକ

### କ୍ଲାଉଡ୍ ସିଙ୍କ୍ ତ୍ରୁଟିଗୁଡ଼ିକ

1. `BASE_URL` ଆପଣଙ୍କ ଚାଲୁଥିବା ଇନ୍ଷ୍ଟାନ୍ସକୁ ସୂଚାଉଛି କି ଯାଞ୍ଚ କରନ୍ତୁ (ଉଦାହରଣ ସ୍ୱରୂପ, `http://localhost:20128`)
2. `CLOUD_URL` ଆପଣଙ୍କ କ୍ଲାଉଡ୍ ଏଣ୍ଡପଏଣ୍ଟକୁ ସୂଚାଉଛି କି ଯାଞ୍ଚ କରନ୍ତୁ (ଉଦାହରଣ ସ୍ୱରୂପ, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ମୂଲ୍ୟଗୁଡ଼ିକୁ ସର୍ଭର୍-ସାଇଡ୍ ମୂଲ୍ୟଗୁଡ଼ିକ ସହିତ ସମନ୍ୱିତ ରଖନ୍ତୁ

### କ୍ଲାଉଡ୍ରେ `stream=false` 500 ଫେରାଏ

**ଲକ୍ଷଣ:** ନନ୍-ଷ୍ଟ୍ରିମିଂ କଲ୍ଗୁଡ଼ିକ ପାଇଁ କ୍ଲାଉଡ୍ ଏଣ୍ଡପଏଣ୍ଟରେ `Unexpected token 'd'...`।

**କାରଣ:** କ୍ଲାଏଣ୍ଟ JSON ଆଶା କରୁଥିବାବେଳେ ଅପ୍ଷ୍ଟ୍ରିମ୍ SSE ପେଲୋଡ୍ ଫେରାଏ।

**ଅସ୍ଥାୟୀ ସମାଧାନ:** କ୍ଲାଉଡ୍କୁ ସିଧାସଳଖ କଲ୍ କରିବା ପାଇଁ `stream=true` ବ୍ୟବହାର କରନ୍ତୁ। ଲୋକାଲ୍ ରନ୍ଟାଇମ୍ରେ SSE→JSON ଫଲ୍ବ୍ୟାକ୍ ଅନ୍ତର୍ଭୁକ୍ତ ଅଛି।

### କ୍ଲାଉଡ୍ ସଂଯୁକ୍ତ ବୋଲି ଦେଖାଏ, କିନ୍ତୁ "ଅବୈଧ API କି"

1. ଲୋକାଲ୍ ଡ୍ୟାସ୍ବୋର୍ଡରୁ ଏକ ନୂତନ କି ସୃଷ୍ଟି କରନ୍ତୁ (`/api/keys`)
2. କ୍ଲାଉଡ୍ ସିଙ୍କ୍ ଚଲାନ୍ତୁ: କ୍ଲାଉଡ୍ ସକ୍ଷମ କରନ୍ତୁ → ବର୍ତ୍ତମାନ ସିଙ୍କ୍ କରନ୍ତୁ
3. ପୁରୁଣା/ସିଙ୍କ୍ ହୋଇନଥିବା କିଗୁଡ଼ିକ କ୍ଲାଉଡ୍ରେ ଏବେ ମଧ୍ୟ `401` ଫେରାଇପାରନ୍ତି

## Docker ସମସ୍ୟାଗୁଡ଼ିକ

### Docker IPv6 / ସଂଯୋଗ ପୁନଃସେଟ୍

<a name="docker-ipv6"></a>

**ଲକ୍ଷଣଗୁଡ଼ିକ:** `curl http://localhost:20128/v1/models` ଚଲାଇଲେ `curl: (56) Recv failure: Connection reset by peer` ଫେରାଏ। ଡ୍ୟାସ୍ବୋର୍ଡ ଏବଂ ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ ନଥିବା ଏଣ୍ଡପଏଣ୍ଟଗୁଡ଼ିକ କାମ କରନ୍ତି, କିନ୍ତୁ ପ୍ରମାଣୀକୃତ ଏଣ୍ଡପଏଣ୍ଟଗୁଡ଼ିକ ବିଫଳ ହୁଅନ୍ତି — ଏହା ଏକ ପ୍ରମାଣୀକରଣ ସମସ୍ୟା ପରି ଦେଖାଯାଏ, କିନ୍ତୁ ପ୍ରକୃତରେ ସେପରି ନୁହେଁ।

**କାରଣ:** `docker run -p 20128:20128`, `0.0.0.0` (IPv4) ଏବଂ `::` (IPv6) ଉଭୟରେ ପ୍ରକାଶ କରେ, କିନ୍ତୁ କଣ୍ଟେନର୍ ଭିତରେ ଥିବା ପ୍ରକ୍ରିୟା କେବଳ IPv4ରେ ଲିସନ୍ କରେ। ଯେଉଁ ହୋଷ୍ଟଗୁଡ଼ିକରେ `localhost` ପ୍ରଥମେ `::1`କୁ ରିଜଲ୍ଭ ହୁଏ, ସେଠାରେ ସଂଯୋଗଟି IPv6ରେ ପ୍ରକାଶିତ ପୋର୍ଟରେ ପହଞ୍ଚେ, କିନ୍ତୁ ତାହା ପଛରେ କୌଣସି ଲିସନର୍ ନଥାଏ → ସଂଯୋଗ ପୁନଃସେଟ୍ ହୁଏ।

**ସମାଧାନ:**

1. **ତ୍ୱରିତ ନିଦାନ:** `curl -4 http://localhost:20128/v1/models` ଚଲାନ୍ତୁ। ଯଦି ଏହା `-4` ସହିତ କାମ କରେ କିନ୍ତୁ ଏହା ବିନା ବିଫଳ ହୁଏ, ତେବେ ଆପଣଙ୍କର IPv6 ବାଇଣ୍ଡ୍ ଅମେଳ ରହିଛି।
2. **ସ୍ଥାୟୀ ସମାଧାନ:** ଆପଣଙ୍କ `docker run` କମାଣ୍ଡରେ `-p 127.0.0.1:20128:20128` ବ୍ୟବହାର କରି ସ୍ପଷ୍ଟ ଭାବରେ IPv4 ସହିତ ବାଇଣ୍ଡ୍ କରନ୍ତୁ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ଏହା IPv4 ବାଇଣ୍ଡ୍କୁ ବାଧ୍ୟତାମୂଳକ କରେ ଏବଂ ସମସ୍ତ ହୋଷ୍ଟ ଇଣ୍ଟରଫେସରେ ପ୍ରକ୍ସିକୁ ଉନ୍ମୁକ୍ତ କରିବାରୁ ମଧ୍ୟ ରୋକେ।

### CLI ଟୁଲ୍ ଇନ୍ଷ୍ଟଲ୍ ହୋଇନଥିବା ଦେଖାଏ

1. ରନ୍ଟାଇମ୍ ଫିଲ୍ଡଗୁଡ଼ିକ ଯାଞ୍ଚ କରନ୍ତୁ: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. ପୋର୍ଟେବଲ୍ ମୋଡ୍ ପାଇଁ: ଇମେଜ୍ ଟାର୍ଗେଟ୍ `runner-cli` ବ୍ୟବହାର କରନ୍ତୁ (ବଣ୍ଡଲ୍ ହୋଇଥିବା CLIଗୁଡ଼ିକ)
3. ହୋଷ୍ଟ ମାଉଣ୍ଟ୍ ମୋଡ୍ ପାଇଁ: `CLI_EXTRA_PATHS` ସେଟ୍ କରନ୍ତୁ ଏବଂ ହୋଷ୍ଟ bin ଡିରେକ୍ଟୋରିକୁ କେବଳ-ପଠନୀୟ ଭାବରେ ମାଉଣ୍ଟ୍ କରନ୍ତୁ
4. ଯଦି `installed=true` ଏବଂ `runnable=false`: ବାଇନାରି ମିଳିଛି, କିନ୍ତୁ ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚରେ ବିଫଳ ହୋଇଛି

ଆପଣଙ୍କ `.env` ଫାଇଲ୍ରେ `APP_LOG_TO_FILE=true` ସେଟ୍ କରନ୍ତୁ। ଆପ୍ଲିକେସନ୍ ଲଗ୍ଗୁଡ଼ିକ `logs/` ଅଧୀନରେ ଲେଖାଯାଏ।
ସେଟିଂସ୍ରେ କଲ୍ ଲଗ୍ ପାଇପ୍ଲାଇନ୍ ସକ୍ଷମ ଥିବାବେଳେ ଅନୁରୋଧ ଆର୍ଟିଫ୍ୟାକ୍ଟଗୁଡ଼ିକ `${DATA_DIR}/call_logs/` ଅଧୀନରେ ସଂରକ୍ଷିତ ହୁଏ।
ପାଇପ୍ଲାଇନ୍ କ୍ୟାପ୍ଚର୍ ସକ୍ଷମ ଥିବାବେଳେ, ଷ୍ଟ୍ରିମ୍ ଚଙ୍କ୍ ପେଲୋଡ୍ଗୁଡ଼ିକୁ ବାଦ୍ ଦେବା ପାଇଁ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ସେଟ୍ କରନ୍ତୁ, କିମ୍ବା KBରେ ଆର୍ଟିଫ୍ୟାକ୍ଟ ସୀମା ପରିବର୍ତ୍ତନ କରିବା ପାଇଁ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ସମନ୍ୱୟ କରନ୍ତୁ।

### ରନ୍ଟାଇମ୍ ଷ୍ଟୋରେଜ୍

- ମୁଖ୍ୟ ସ୍ଥିତି: `${DATA_DIR}/storage.sqlite` (ପ୍ରଦାନକାରୀ, କମ୍ବୋ, ଉପନାମ, କି, ସେଟିଂସ୍)
- ବ୍ୟବହାର: `storage.sqlite`ରେ SQLite ଟେବୁଲ୍ଗୁଡ଼ିକ (`usage_history`, `call_logs`, `proxy_logs`) + ଇଚ୍ଛାଧୀନ `${DATA_DIR}/call_logs/`
- ଆପ୍ଲିକେସନ୍ ଲଗ୍ଗୁଡ଼ିକ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ଥିବାବେଳେ)
- କଲ୍ ଲଗ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟଗୁଡ଼ିକ: କଲ୍ ଲଗ୍ ପାଇପ୍ଲାଇନ୍ ସକ୍ଷମ ଥିବାବେଳେ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

ଅନୁରୋଧ ଲଗ୍ ପୃଷ୍ଠାର **ଇତିହାସ ସଫା କରନ୍ତୁ** କାର୍ଯ୍ୟଟି `call_logs`, ପୁରୁଣା
`request_detail_logs`, ଏବଂ ଲୋକାଲ୍ `${DATA_DIR}/call_logs/` ଆର୍ଟିଫ୍ୟାକ୍ଟ ଡିରେକ୍ଟୋରିକୁ ସଫା କରେ।

## ସର୍କିଟ୍ ବ୍ରେକର୍ ସମସ୍ୟାଗୁଡ଼ିକ

### ପ୍ରଦାନକାରୀ OPEN ଅବସ୍ଥାରେ ଅଟକି ରହିଛି

ଯେତେବେଳେ କୌଣସି ପ୍ରଦାନକାରୀଙ୍କ ସର୍କିଟ୍ ବ୍ରେକର୍ OPEN ଥାଏ, କୁଲ୍ଡାଉନ୍ ଅବଧି ଶେଷ ହେବା ପର୍ଯ୍ୟନ୍ତ ଅନୁରୋଧଗୁଡ଼ିକୁ ଅବରୋଧ କରାଯାଏ।

**ସମାଧାନ:**

1. **ଡ୍ୟାସ୍ବୋର୍ଡ → ସେଟିଂସ୍ → ସ୍ଥିତିସ୍ଥାପକତା**କୁ ଯାଆନ୍ତୁ
2. ପ୍ରଭାବିତ ପ୍ରଦାନକାରୀଙ୍କ ସର୍କିଟ୍ ବ୍ରେକର୍ କାର୍ଡ ଯାଞ୍ଚ କରନ୍ତୁ
3. ସମସ୍ତ ବ୍ରେକର୍ ସଫା କରିବାକୁ **ସବୁ ରିସେଟ୍ କରନ୍ତୁ**ରେ କ୍ଲିକ୍ କରନ୍ତୁ, କିମ୍ବା କୁଲ୍ଡାଉନ୍ ଅବଧି ଶେଷ ହେବା ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରନ୍ତୁ
4. ରିସେଟ୍ କରିବା ପୂର୍ବରୁ ପ୍ରଦାନକାରୀ ପ୍ରକୃତରେ ଉପଲବ୍ଧ ଅଛନ୍ତି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ

### ପ୍ରଦାନକାରୀଙ୍କ ସର୍କିଟ୍ ବ୍ରେକର୍ ବାରମ୍ବାର ଟ୍ରିପ୍ ହେଉଛି

ଯଦି କୌଣସି ପ୍ରଦାନକାରୀ ବାରମ୍ବାର OPEN ଅବସ୍ଥାକୁ ଯାଆନ୍ତି:

1. ବିଫଳତାର ଢାଞ୍ଚା ଦେଖିବା ପାଇଁ **ଡ୍ୟାସ୍ବୋର୍ଡ → ସ୍ୱାସ୍ଥ୍ୟ → ପ୍ରଦାନକାରୀଙ୍କ ସ୍ୱାସ୍ଥ୍ୟ** ଯାଞ୍ଚ କରନ୍ତୁ
2. **ସେଟିଂସ୍ → ସ୍ଥିତିସ୍ଥାପକତା → ପ୍ରଦାନକାରୀ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ**କୁ ଯାଇ ବିଫଳତା ସୀମା ବୃଦ୍ଧି କରନ୍ତୁ
3. ପ୍ରଦାନକାରୀ API ସୀମା ପରିବର୍ତ୍ତନ କରିଛନ୍ତି କିମ୍ବା ପୁନଃ-ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ କରୁଛନ୍ତି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ
4. ବିଳମ୍ବ ଟେଲିମେଟ୍ରି ସମୀକ୍ଷା କରନ୍ତୁ — ଅଧିକ ବିଳମ୍ବ ଟାଇମ୍ଆଉଟ୍-ଆଧାରିତ ବିଫଳତା ସୃଷ୍ଟି କରିପାରେ

## ଅଡିଓ ଟ୍ରାନ୍ସକ୍ରିପ୍ସନ୍ ସମସ୍ୟାଗୁଡ଼ିକ

### "ଅସମର୍ଥିତ ମଡେଲ୍" ତ୍ରୁଟି

- ଏପରି ଏକ ମଡେଲ୍ id ବ୍ୟବହାର କରନ୍ତୁ ଯାହାର ପ୍ରଥମ ଖଣ୍ଡ ଏପରି ଜଣେ ପ୍ରଦାନକାରୀ, ଯାହାଙ୍କ ପାଇଁ ଆପଣଙ୍କ ପାଖରେ ପ୍ରମାଣପତ୍ର ଅଛି (`openai/whisper-1`, `openrouter/deepgram/nova-3`)। କେବଳ `deepgram/nova-3` ବ୍ୟବହାର କରିବାକୁ ଏକ ମୂଳ Deepgram କୀ ଆବଶ୍ୟକ।
- ପ୍ରଦାନକାରୀ **ଡ୍ୟାସ୍ବୋର୍ଡ → ପ୍ରଦାନକାରୀମାନେ**ରେ ସଂଯୁକ୍ତ ଅଛନ୍ତି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ

### ଟ୍ରାନ୍ସକ୍ରିପ୍ସନ୍ ଖାଲି ଫେରାଉଛି କିମ୍ବା ବିଫଳ ହେଉଛି

- ସମର୍ଥିତ ଅଡିଓ ଫର୍ମାଟ୍ଗୁଡ଼ିକ ଯାଞ୍ଚ କରନ୍ତୁ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ଫାଇଲ୍ ଆକାର ପ୍ରଦାନକାରୀଙ୍କ ସୀମା ମଧ୍ୟରେ ଅଛି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ (ସାଧାରଣତଃ < 25MB)
- ପ୍ରଦାନକାରୀ କାର୍ଡରେ ପ୍ରଦାନକାରୀଙ୍କ API କୀର ବୈଧତା ଯାଞ୍ଚ କରନ୍ତୁ

### ସାଧାରଣ ଫର୍ମାଟ୍ ସମସ୍ୟାଗୁଡ଼ିକ

- **ଚିନ୍ତନ ଟ୍ୟାଗ୍ଗୁଡ଼ିକ ଦେଖାଯାଉନାହିଁ** — ଲକ୍ଷ୍ୟ ପ୍ରଦାନକାରୀ ଚିନ୍ତନକୁ ସମର୍ଥନ କରୁଛନ୍ତି କି ନାହିଁ ଏବଂ ଚିନ୍ତନ ବଜେଟ୍ ସେଟିଂ ଯାଞ୍ଚ କରନ୍ତୁ
- **ଟୁଲ୍ କଲ୍ଗୁଡ଼ିକ ହଟିଯାଉଛି** — କେତେକ ଫର୍ମାଟ୍ ଅନୁବାଦ ଅସମର୍ଥିତ ଫିଲ୍ଡଗୁଡ଼ିକୁ ବାଦ୍ ଦେଇପାରେ; ପ୍ଲେଗ୍ରାଉଣ୍ଡ ମୋଡ୍ରେ ଯାଞ୍ଚ କରନ୍ତୁ
- **ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ଅନୁପସ୍ଥିତ** — Claude ଏବଂ Gemini ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟଗୁଡ଼ିକୁ ଭିନ୍ନ ଭାବରେ ପରିଚାଳନା କରନ୍ତି; ଅନୁବାଦ ଆଉଟ୍ପୁଟ୍ ଯାଞ୍ଚ କରନ୍ତୁ
- **SDK ଅବଜେକ୍ଟ ପରିବର୍ତ୍ତେ କଞ୍ଚା ଷ୍ଟ୍ରିଂ ଫେରାଉଛି** — v1.xରେ ସମାଧାନ କରାଯାଇଛି; ପ୍ରତିକ୍ରିୟା ସାନିଟାଇଜର୍ OpenAI SDK Pydantic ବୈଧତା ଯାଞ୍ଚ ବିଫଳତା ସୃଷ୍ଟି କରୁଥିବା ଅଣ-ମାନକ ଫିଲ୍ଡଗୁଡ଼ିକୁ (`x_groq`, `usage_breakdown`, ଇତ୍ୟାଦି) ବାଦ୍ ଦିଏ। ଯଦି ଆପଣ ଏବେ ମଧ୍ୟ v3.x+ରେ ଏହା ଦେଖୁଛନ୍ତି, ଦୟାକରି ଏକ ଇସ୍ୟୁ ଦାଖଲ କରନ୍ତୁ।
- **GLM/ERNIE `system` ଭୂମିକାକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରୁଛି** — v1.xରେ ସମାଧାନ କରାଯାଇଛି; ଭୂମିକା ନର୍ମାଲାଇଜର୍ ଅସଙ୍ଗତ ମଡେଲ୍ଗୁଡ଼ିକ ପାଇଁ ସିଷ୍ଟମ୍ ସନ୍ଦେଶଗୁଡ଼ିକୁ ସ୍ୱୟଂଚାଳିତ ଭାବେ ବ୍ୟବହାରକାରୀ ସନ୍ଦେଶଗୁଡ଼ିକରେ ମିଶ୍ରଣ କରେ। ଯଦି ଆପଣ ଏବେ ମଧ୍ୟ v3.x+ରେ ଏହା ଦେଖୁଛନ୍ତି, ଦୟାକରି ଏକ ଇସ୍ୟୁ ଦାଖଲ କରନ୍ତୁ।
- **`developer` ଭୂମିକା ଚିହ୍ନଟ ହେଉନାହିଁ** — v1.xରେ ସମାଧାନ କରାଯାଇଛି; ଅଣ-OpenAI ପ୍ରଦାନକାରୀମାନଙ୍କ ପାଇଁ ସ୍ୱୟଂଚାଳିତ ଭାବେ `system`କୁ ରୂପାନ୍ତରିତ ହୁଏ। ଯଦି ଆପଣ ଏବେ ମଧ୍ୟ v3.x+ରେ ଏହା ଦେଖୁଛନ୍ତି, ଦୟାକରି ଏକ ଇସ୍ୟୁ ଦାଖଲ କରନ୍ତୁ।
- **`json_schema` Gemini ସହିତ କାମ କରୁନାହିଁ** — v1.xରେ ସମାଧାନ କରାଯାଇଛି; `response_format` ବର୍ତ୍ତମାନ Geminiର `responseMimeType` + `responseSchema`କୁ ରୂପାନ୍ତରିତ ହୁଏ। ଯଦି ଆପଣ ଏବେ ମଧ୍ୟ v3.x+ରେ ଏହା ଦେଖୁଛନ୍ତି, ଦୟାକରି ଏକ ଇସ୍ୟୁ ଦାଖଲ କରନ୍ତୁ।

## ସ୍ଥିତିସ୍ଥାପକତା ସେଟିଂସ୍

### ସ୍ୱୟଂଚାଳିତ ହାର-ସୀମା ସକ୍ରିୟ ନ ହେବା

- ସ୍ୱୟଂଚାଳିତ ହାର-ସୀମା କେବଳ API କୀ ପ୍ରଦାତାଙ୍କ ପାଇଁ ପ୍ରଯୁଜ୍ୟ (OAuth/ସବ୍ସ୍କ୍ରିପ୍ସନ୍ ପାଇଁ ନୁହେଁ)
- **ସେଟିଂସ୍ → ସ୍ଥିତିସ୍ଥାପକତା → ପ୍ରଦାତା ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ**ରେ ସ୍ୱୟଂଚାଳିତ ହାର-ସୀମା ସକ୍ରିୟ ଅଛି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ
- ପ୍ରଦାତା `429` ସ୍ଥିତି କୋଡ୍ କିମ୍ବା `Retry-After` ହେଡର୍ ଫେରାଉଛି କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ

### ଏକ୍ସପୋନେନ୍ସିଆଲ୍ ବ୍ୟାକଅଫ୍ ସମନ୍ୱୟ କରିବା

ପ୍ରଦାତା ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ ଏହି ସେଟିଂସ୍କୁ ସମର୍ଥନ କରେ:

- **ମୂଳ ବିଳମ୍ବ** — ପ୍ରଥମ ବିଫଳତା ପରେ ପ୍ରାରମ୍ଭିକ ଅପେକ୍ଷା ସମୟ (ଡିଫଲ୍ଟ: 1s)
- **ସର୍ବାଧିକ ବିଳମ୍ବ** — ସର୍ବାଧିକ ଅପେକ୍ଷା ସମୟ ସୀମା (ଡିଫଲ୍ଟ: 30s)
- **ଗୁଣକ** — ପ୍ରତ୍ୟେକ କ୍ରମାଗତ ବିଫଳତାରେ ବିଳମ୍ବ କେତେ ବଢ଼ିବ (ଡିଫଲ୍ଟ: 2x)

### ଥଣ୍ଡରିଂ ହର୍ଡ ପ୍ରତିରୋଧ

ଅନେକ ସମକାଳୀନ ଅନୁରୋଧ ଏକ ହାର-ସୀମିତ ପ୍ରଦାତାଙ୍କୁ ପହଞ୍ଚିଲେ, ଅନୁରୋଧଗୁଡ଼ିକୁ କ୍ରମିକ କରିବା ଏବଂ ପର୍ଯ୍ୟାୟକ୍ରମିକ ବିଫଳତା ରୋକିବା ପାଇଁ OmniRoute ମ୍ୟୁଟେକ୍ସ୍ + ସ୍ୱୟଂଚାଳିତ ହାର-ସୀମା ବ୍ୟବହାର କରେ। API କୀ ପ୍ରଦାତାଙ୍କ ପାଇଁ ଏହା ସ୍ୱୟଂଚାଳିତ ଅଟେ।

### ଚାଟ୍ ଅନୁରୋଧଗୁଡ଼ିକ 503 / chat_admission_busy ସହିତ ବିଫଳ ହେଉଛି

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଚାଟ୍ କମ୍ପ୍ଲିସନ୍ସ ଏଣ୍ଡପଏଣ୍ଟ ଏକ ପୁନଃଚେଷ୍ଟାଯୋଗ୍ୟ `503` ପ୍ରତିକ୍ରିୟା ଫେରାଏ, ଯାହାର ତ୍ରୁଟି କୋଡ୍ ହେଉଛି
  `chat_admission_busy`।

  ଅଧିଭୋଗରୁ ନିର୍ଦ୍ଧାରିତ ହୁଏ — ଅନୁରୋଧଟି ପୂର୍ବରୁ ଅପେକ୍ଷା କରିଥିବା `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`

  ବାଇଟ୍-ଆଧାରିତ ପଥରେ 2 ସେକେଣ୍ଡ, ଗଠନ-ଆଧାରିତ ପଥରେ 1 ସେକେଣ୍ଡ (ଯେଉଁଥିରେ
  `reason: "structure_limit"` ମଧ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ)।

**କାରଣ:** ଏହା OmniRoute ଭିତରେ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଲୋଡ୍ ହ୍ରାସ, କୌଣସି ଅପ୍ଷ୍ଟ୍ରିମ୍-ପ୍ରଦାତା ବିଫଳତା ନୁହେଁ।

**#503-ଫ୍ୟାନ୍ଆଉଟ୍:** ଏହି ସମାଧାନ ପୂର୍ବରୁ, ଗାର୍ଡ ହୋଷ୍ଟ ମେମୋରିକୁ ବିଚାର ନକରି ଏକ ନିର୍ଦ୍ଧାରିତ ଅନୁରୋଧ ସଂଖ୍ୟା

ସମସାମୟିକତାକୁ ~1କୁ ହ୍ରାସ କରୁଥିଲା ଏବଂ ସମ୍ପୂର୍ଣ୍ଣ ସାଧାରଣ ଲୋଡ୍ରେ 503 ତ୍ରୁଟି ଦେଉଥିଲା। ଗାର୍ଡ ଏବେ ନିଜେ ସମନ୍ୱିତ ହୁଏ: ଏହା

(OpenCode, Claude Code, Cursor) ତୁରନ୍ତ ପ୍ରତ୍ୟାଖ୍ୟାନରେ ସେମାନଙ୍କ ସମ୍ପୂର୍ଣ୍ଣ ପୁନଃଚେଷ୍ଟା ବଜେଟ୍ ଖର୍ଚ୍ଚ କରି

ବର୍ତ୍ତମାନର ହେଭିୱେଟ୍ ଲିଜ୍ ଅଧିଭୋଗ, ସମାଧାନ କରାଯାଇଥିବା ବାଇଟ୍ ବଜେଟ୍ ଏବଂ ସଜୀବ ଚାପର ତୀବ୍ରତା
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`)ରେ ପ୍ରଦର୍ଶିତ ହୁଏ — କୌଣସି env var ପରିବର୍ତ୍ତନ କରିବା ପୂର୍ବରୁ ଏଗୁଡ଼ିକୁ ଯାଞ୍ଚ କରନ୍ତୁ।
ସେଟିଂସ୍ → ସ୍ଥିତିସ୍ଥାପକତା → ଅନୁରୋଧ କ୍ୟୁ → ସମକାଳୀନ ଅନୁରୋଧଗୁଡ଼ିକ ଏହାକୁ ନିୟନ୍ତ୍ରଣ କରେ ନାହିଁ; ସେହି ସେଟିଂ
ଏକ ପୃଥକ ପ୍ରଦାତା ଅନୁରୋଧ-କ୍ୟୁ ବ୍ୟବସ୍ଥାକୁ ନିୟନ୍ତ୍ରଣ କରେ।

**ସମାଧାନ:**

1. ପ୍ରଥମେ ପୁନଃଚେଷ୍ଟା କରନ୍ତୁ। ଅନୁରୋଧଟିକୁ ତୁରନ୍ତ ପୁନରାବୃତ୍ତି କରିବା ପରିବର୍ତ୍ତେ କ୍ଲାଏଣ୍ଟମାନେ `Retry-After`କୁ
   ସମ୍ମାନ ଦେବା ଏବଂ ବ୍ୟାକଅଫ୍ ବ୍ୟବହାର କରିବା ଉଚିତ।
2. କୌଣସି ସମନ୍ୱୟ କରିବା ପୂର୍ବରୁ `/api/monitoring/health` → `chatAdmission` ଯାଞ୍ଚ କରନ୍ତୁ। `countCapEnabled:
false` ଏବଂ ଏକ ଉଦାର `maxInflightBytes`ର ଅର୍ଥ ହେଉଛି ସ୍ୱୟଂ-ବ୍ୟୁତ୍ପନ୍ନ ବଜେଟ୍ ପୂର୍ବରୁ ନିଜ କାର୍ଯ୍ୟ
   କରୁଛି; `high`/`critical` ମୂଲ୍ୟର `pressureSeverity`ର ଅର୍ଥ ହେଉଛି ହୋଷ୍ଟରେ ପ୍ରକୃତରେ ମେମୋରି କମ୍ ଅଛି —
   ଏହାକୁ କୌଣସି ଆଡ୍ମିସନ୍ env var ଦ୍ୱାରା ସମାଧାନ କରାଯାଇପାରିବ ନାହିଁ; ଏଥିପାଇଁ ଅଧିକ RAM କିମ୍ବା ଏକ ଛୋଟ ୱର୍କଲୋଡ୍ ଆବଶ୍ୟକ।
3. କେବଳ `/api/monitoring/health`ରେ ସ୍ୱୟଂ-ବ୍ୟୁତ୍ପନ୍ନ ବଜେଟ୍ ଆପଣଙ୍କ ହୋଷ୍ଟ ପାଇଁ ପ୍ରକୃତରେ ବହୁତ ଛୋଟ ବୋଲି
   ଦେଖାଗଲେ (ଏହା ବିରଳ — ଏହା ପୂର୍ବରୁ କଣ୍ଟେନର୍ରୁ ବେୟାର୍-ମେଟାଲ୍ ପର୍ଯ୍ୟନ୍ତ ସ୍କେଲ୍ କରେ), ପୁରୁଣା ଅନୁରୋଧ-ସଂଖ୍ୟା ସୀମାକୁ ଫେରିବା ପରିବର୍ତ୍ତେ
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ଦ୍ୱାରା ଏହାକୁ ସିଧାସଳଖ ଓଭର୍ରାଇଡ୍ କରନ୍ତୁ।

ପ୍ରାମାଣିକ ଆଡ୍ମିସନ୍ ସେଟିଂସ୍ ପାଇଁ [ପରିବେଶ-ଭେରିଏବଲ୍ ସନ୍ଦର୍ଭ](../reference/ENVIRONMENT.md#4-security--authentication)
ଦେଖନ୍ତୁ।

## ଇଚ୍ଛାଧୀନ RAG / LLM ବିଫଳତା ବର୍ଗୀକରଣ (16ଟି ସମସ୍ୟା)

କିଛି OmniRoute ବ୍ୟବହାରକାରୀ RAG କିମ୍ବା ଏଜେଣ୍ଟ ଷ୍ଟାକ୍ଗୁଡ଼ିକର ସମ୍ମୁଖରେ ଗେଟୱେକୁ ରଖନ୍ତି। ସେହିପରି ସେଟଅପ୍ଗୁଡ଼ିକରେ ଏକ ଅଜବ ଢାଞ୍ଚା ଦେଖିବା ସାଧାରଣ କଥା: OmniRoute ସୁସ୍ଥ ଦେଖାଯାଏ (ପ୍ରଦାନକାରୀଗୁଡ଼ିକ ସକ୍ରିୟ, ରାଉଟିଂ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ ଠିକ୍, କୌଣସି ରେଟ୍ ଲିମିଟ୍ ସତର୍କତା ନାହିଁ), କିନ୍ତୁ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ତଥାପି ଭୁଲ୍ ହୋଇଥାଏ।

ବ୍ୟବହାରିକ ଭାବେ, ଏହି ଘଟଣାଗୁଡ଼ିକ ସାଧାରଣତଃ ନିଜେ ଗେଟୱେରୁ ନୁହେଁ, ବରଂ ଡାଉନ୍ଷ୍ଟ୍ରିମ୍ RAG ପାଇପଲାଇନ୍ରୁ ଆସିଥାଏ।

ସେହି ବିଫଳତାଗୁଡ଼ିକୁ ବର୍ଣ୍ଣନା କରିବା ପାଇଁ ଯଦି ଆପଣ ଏକ ସାଧାରଣ ଶବ୍ଦାବଳୀ ଚାହାନ୍ତି, ତେବେ WFGY ProblemMap ବ୍ୟବହାର କରିପାରିବେ। ଏହା ଏକ ବାହ୍ୟ MIT ଲାଇସେନ୍ସପ୍ରାପ୍ତ ପାଠ୍ୟ ସମ୍ବଳ, ଯାହା ଷୋହଳଟି ପୁନରାବୃତ୍ତ RAG / LLM ବିଫଳତା ଢାଞ୍ଚାକୁ ପରିଭାଷିତ କରେ। ଉଚ୍ଚ ସ୍ତରରେ ଏହା ନିମ୍ନଲିଖିତ ବିଷୟଗୁଡ଼ିକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ:

- ପୁନରୁଦ୍ଧାର ବିଚ୍ୟୁତି ଏବଂ ଭଙ୍ଗା ପ୍ରସଙ୍ଗ ସୀମା
- ଖାଲି କିମ୍ବା ପୁରୁଣା ଇଣ୍ଡେକ୍ସ ଏବଂ ଭେକ୍ଟର୍ ଷ୍ଟୋର୍
- ଏମ୍ବେଡିଂ ଓ ଅର୍ଥଗତ ଅସଙ୍ଗତି
- ପ୍ରମ୍ପ୍ଟ ସଂଯୋଜନ ଏବଂ ପ୍ରସଙ୍ଗ ୱିଣ୍ଡୋ ସମସ୍ୟା
- ତାର୍କିକ ପତନ ଏବଂ ଅତ୍ୟଧିକ ଆତ୍ମବିଶ୍ୱାସୀ ଉତ୍ତର
- ଦୀର୍ଘ ଶୃଙ୍ଖଳା ଏବଂ ଏଜେଣ୍ଟ ସମନ୍ୱୟ ବିଫଳତା
- ବହୁ-ଏଜେଣ୍ଟ ମେମୋରି ଏବଂ ଭୂମିକା ବିଚ୍ୟୁତି
- ଡିପ୍ଲୟମେଣ୍ଟ ଏବଂ ବୁଟ୍ଷ୍ଟ୍ରାପ୍ କ୍ରମ ସମସ୍ୟା

ଧାରଣାଟି ସରଳ:

1. ଆପଣ ଏକ ଖରାପ ପ୍ରତିକ୍ରିୟାର ତଦନ୍ତ କରିବାବେଳେ, ନିମ୍ନଲିଖିତଗୁଡ଼ିକ ସଂଗ୍ରହ କରନ୍ତୁ:
   - ବ୍ୟବହାରକାରୀ କାର୍ଯ୍ୟ ଏବଂ ଅନୁରୋଧ
   - OmniRouteରେ ରୁଟ୍ କିମ୍ବା ପ୍ରଦାନକାରୀ ସଂଯୋଜନ
   - ଡାଉନ୍ଷ୍ଟ୍ରିମ୍ରେ ବ୍ୟବହୃତ ଯେକୌଣସି RAG ପ୍ରସଙ୍ଗ (ପୁନରୁଦ୍ଧାର କରାଯାଇଥିବା ଡକ୍ୟୁମେଣ୍ଟ, ଟୁଲ୍ କଲ୍ ଇତ୍ୟାଦି)
2. ଘଟଣାଟିକୁ ଗୋଟିଏ କିମ୍ବା ଦୁଇଟି WFGY ProblemMap ନମ୍ବର୍ (`No.1` … `No.16`) ସହିତ ମ୍ୟାପ୍ କରନ୍ତୁ।
3. OmniRoute ଲଗ୍ଗୁଡ଼ିକ ପାଖରେ ନିଜ ଡ୍ୟାସବୋର୍ଡ, ରନ୍ବୁକ୍ କିମ୍ବା ଘଟଣା ଟ୍ରାକର୍ରେ ନମ୍ବର୍ଟି ସଂରକ୍ଷଣ କରନ୍ତୁ।
4. ଆପଣଙ୍କ RAG ଷ୍ଟାକ୍, ରିଟ୍ରିଭର୍ କିମ୍ବା ରାଉଟିଂ କୌଶଳ ପରିବର୍ତ୍ତନ କରିବା ଆବଶ୍ୟକ କି ନାହିଁ ନିର୍ଣ୍ଣୟ କରିବାକୁ ସମ୍ପୃକ୍ତ WFGY ପୃଷ୍ଠା ବ୍ୟବହାର କରନ୍ତୁ।

ସମ୍ପୂର୍ଣ୍ଣ ପାଠ୍ୟ ଏବଂ ନିର୍ଦ୍ଦିଷ୍ଟ ପଦ୍ଧତିଗୁଡ଼ିକ ଏଠାରେ ଉପଲବ୍ଧ (MIT ଲାଇସେନ୍ସ, କେବଳ ପାଠ୍ୟ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ଯଦି ଆପଣ OmniRoute ପଛରେ RAG କିମ୍ବା ଏଜେଣ୍ଟ ପାଇପଲାଇନ୍ ଚଲାନ୍ତି ନାହିଁ, ତେବେ ଏହି ବିଭାଗକୁ ଅଣଦେଖା କରିପାରିବେ।

- **API:** ପରିଚାଳନା ପ୍ରମାଣୀକରଣ ହେଡର୍ଗୁଡ଼ିକ ସହିତ `DELETE /api/resilience/model-cooldowns`

### Command Code ପ୍ରଦାନକାରୀ ସଂଯୋଗ 403 ସହିତ ବିଫଳ ହୁଏ

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- Command Code ପ୍ରଦାନକାରୀ ସଂଯୋଗ ପରୀକ୍ଷା କରିବାବେଳେ 403
- ନୂଆକରି ଯୋଡ଼ିବା ପରେ ପ୍ରଦାନକାରୀ କାର୍ଡ "ଅନଧିକୃତ" ଦେଖାଏ

**କାରଣ:** OAuth ପ୍ରବାହ ସମ୍ପୂର୍ଣ୍ଣ ହୋଇନଥିଲା (କଲ୍ବ୍ୟାକ୍ ମିଳିନଥିଲା କିମ୍ବା ଟୋକେନ୍ ସ୍ଥାୟୀ ଭାବେ ସଂରକ୍ଷିତ ହୋଇନଥିଲା)।

**ସମାଧାନ:**

- OAuth ପ୍ରବାହକୁ ପୁନଃଟ୍ରିଗର୍ କରିବା ପାଇଁ CLIରୁ `omniroute providers` ଚଲାନ୍ତୁ, କିମ୍ବା
- **ଡ୍ୟାସବୋର୍ଡ → ପ୍ରଦାନକାରୀଗୁଡ଼ିକ → Command Code → ପୁନଃସଂଯୋଗ କରନ୍ତୁ**ରୁ OAuth ପୁନଃଚାଳନ କରନ୍ତୁ

### ModelScope ଅତ୍ୟଧିକ ଆକ୍ରମଣାତ୍ମକ 429 କୁଲ୍ଡାଉନ୍ ଫେରାଏ

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଅନୁରୋଧଗୁଡ଼ିକର ଏକ ଛୋଟ ବର୍ଷ୍ଟ ପରେ ModelScopeରେ ଅତ୍ୟନ୍ତ ସ୍ୱଳ୍ପ କିମ୍ବା ତତ୍କ୍ଷଣାତ୍ କୁଲ୍ଡାଉନ୍
- କମ୍ବୋ ରାଉଟିଂ ଆଶା କରାଯାଇଥିବା ସମୟଠାରୁ ପୂର୍ବରୁ ModelScopeକୁ ଏଡ଼ାଇଯାଏ

**କାରଣ:** ModelScope ପ୍ରଦାନକାରୀ-ନିର୍ଦ୍ଦିଷ୍ଟ `Retry-After` ହେଡର୍ଗୁଡ଼ିକ ନିର୍ଗତ କରେ। v3.8.0ରେ ସେହି ହେଡର୍ଗୁଡ଼ିକ ପାଇଁ ସ୍ୱତନ୍ତ୍ର ପରିଚାଳନା ଅନ୍ତର୍ଭୁକ୍ତ ଅଛି, ତେଣୁ ପୁରୁଣା ସଂସ୍କରଣଗୁଡ଼ିକ ସେଗୁଡ଼ିକୁ ସାଧାରଣ ରେଟ୍-ଲିମିଟ୍ ସଙ୍କେତ ଭାବେ ଭୁଲ୍ ପଢ଼ନ୍ତି।

**ସମାଧାନ:**

- ଆପଣ v3.8.0 କିମ୍ବା ପରବର୍ତ୍ତୀ ସଂସ୍କରଣରେ ଅଛନ୍ତି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ
- **ସେଟିଂସ୍ → ସ୍ଥିତିସ୍ଥାପକତା** ଅଧୀନରେ `useUpstream429BreakerHints` ଟଗଲ୍ ସକ୍ରିୟ ଅଛି ବୋଲି ଯାଞ୍ଚ କରନ୍ତୁ

### ପ୍ରଡକ୍ସନ୍ରେ OMNIROUTE_WS_BRIDGE_SECRET ଅନୁପସ୍ଥିତ

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଦୂରବର୍ତ୍ତୀ ପ୍ରଡକ୍ସନ୍ ହୋଷ୍ଟରେ ଚାଲୁଥିବାବେଳେ ପ୍ରତ୍ୟେକ Codex/Responses WebSocket ବ୍ରିଜ୍ ଅନୁରୋଧରେ 401
- ସଂଯୋଗ ହେବାର ତୁରନ୍ତ ପରେ WebSocket ବ୍ରିଜ୍ ହ୍ୟାଣ୍ଡସେକ୍ ବନ୍ଦ ହୋଇଯାଏ

**କାରଣ:** ପ୍ରଡକ୍ସନ୍ ପରିବେଶରେ `OMNIROUTE_WS_BRIDGE_SECRET` env var ଅନୁପସ୍ଥିତ।

**ସମାଧାନ:**

1. ଏକ ଯାଦୃଚ୍ଛିକ ସିକ୍ରେଟ୍ ସୃଷ୍ଟି କରନ୍ତୁ: `openssl rand -hex 32`
2. ପ୍ରଡକ୍ସନ୍ ସର୍ଭର୍ envରେ (ଏବଂ ବ୍ରିଜ୍ ସହିତ ଯୋଗାଯୋଗ କରୁଥିବା ଯେକୌଣସି କ୍ଲାଏଣ୍ଟରେ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ସେଟ୍ କରନ୍ତୁ
3. OmniRoute ପୁନଃଚାଳନ କରନ୍ତୁ

### Responses API: ବ୍ୟାକଗ୍ରାଉଣ୍ଡ ମୋଡ୍ ସିଙ୍କ୍ରୋନସ୍ ମୋଡ୍କୁ ଅବନମିତ ହୋଇଛି

**ଲକ୍ଷଣଗୁଡ଼ିକ:**

- ଲଗ୍ ହୋଇଥିବା ସତର୍କତା: `background mode degraded to synchronous`
- ଏକ `background: true` ଅନୁରୋଧ ବ୍ୟାକଗ୍ରାଉଣ୍ଡ ଜବ୍ ହ୍ୟାଣ୍ଡଲ୍ ପରିବର୍ତ୍ତେ ସାଧାରଣ ସିଙ୍କ୍ରୋନସ୍ ପ୍ରତିକ୍ରିୟା ଫେରାଏ

**କାରଣ:** v3.8.0ରେ ଏକ ସତର୍କତା ନିର୍ଗତ କରାଯାଉଥିବାବେଳେ Responses APIର `background: true`କୁ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ ସିଙ୍କ୍ରୋନସ୍ ନିଷ୍ପାଦନକୁ ଅବନମିତ କରାଯାଏ। ସମ୍ପୂର୍ଣ୍ଣ ଅସିଙ୍କ୍ରୋନସ୍ ବ୍ୟାକଗ୍ରାଉଣ୍ଡ ନିଷ୍ପାଦନ ଭବିଷ୍ୟତରେ ପ୍ରଦାନ କରାଯିବ।

**ସମାଧାନ:**

- `background` ବିନା କଲ୍ କରିବା ପାଇଁ କ୍ଲାଏଣ୍ଟକୁ ସମନ୍ୱୟ କରନ୍ତୁ, କିମ୍ବା
- ସମ୍ପୂର୍ଣ୍ଣ ଅସିଙ୍କ୍ରୋନସ୍ ବ୍ୟାକଗ୍ରାଉଣ୍ଡ ମୋଡ୍ ସହିତ ପରବର୍ତ୍ତୀ ରିଲିଜ୍ ପାଇଁ ଅପେକ୍ଷା କରନ୍ତୁ (ଚେଞ୍ଜଲଗ୍ ଅନୁସରଣ କରନ୍ତୁ)

## ଧୀର ଷ୍ଟାର୍ଟଅପ୍ / ପ୍ରସ୍ତୁତି ସମୟସୀମା

ଯଦି CLI `⚠ Server did not respond within 60s` ପ୍ରଦର୍ଶନ କରେ, କିନ୍ତୁ ସର୍ଭର୍
ବାସ୍ତବରେ କାର୍ଯ୍ୟ କରୁଛି, ତେବେ ଆପଣଙ୍କ ପରିବେଶ ପାଇଁ ପ୍ରସ୍ତୁତି ଯାଞ୍ଚର ସମୟସୀମା ଅତ୍ୟନ୍ତ କମ୍ ଅଟେ।

ଏହା ସାଧାରଣତଃ Windows (ଆଣ୍ଟିଭାଇରସ୍, ଫାଇଲ୍ସିଷ୍ଟମ୍ ୱାଚର୍) କିମ୍ବା ଅଧିକ
ଷ୍ଟାର୍ଟଅପ୍ କାର୍ଯ୍ୟଭାର ଥିବା କଣ୍ଟେନର୍ଗୁଡ଼ିକରେ ଘଟେ।

**ସମାଧାନ — ସମୟସୀମା ବଢ଼ାନ୍ତୁ:**

```bash
# ପରିବେଶ ଭେରିଏବଲ୍ ମାଧ୍ୟମରେ (ପରବର୍ତ୍ତୀ ଷ୍ଟାର୍ଟଗୁଡ଼ିକରେ ମଧ୍ୟ ରହିବ):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 ମିନିଟ୍
omniroute serve

# CLI ଫ୍ଲାଗ୍ ମାଧ୍ୟମରେ (କେବଳ ଥରେ):
omniroute serve --ready-timeout 180000
```

ଡିଫଲ୍ଟ ହେଉଛି 60 000 ms (60 s)। ଚେତାବନୀଟି କେବଳ ସୂଚନାମୂଳକ; ସର୍ଭର୍
ପୃଷ୍ଠଭୂମିରେ ଆରମ୍ଭ ହେବା ଜାରି ରଖେ ଏବଂ ବୁଟ୍ ସମ୍ପୂର୍ଣ୍ଣ ହେଲେ ଏହାକୁ ଆକ୍ସେସ୍ କରାଯାଇପାରିବ।

`OMNIROUTE_READY_TIMEOUT_MS` ବିଷୟରେ ସମ୍ପୂର୍ଣ୍ଣ ବିବରଣୀ ପାଇଁ
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) ଦେଖନ୍ତୁ।
