## ଦ୍ରୁତ ଚାଳନ

> **ଗୋଟିଏ କମାଣ୍ଡରେ ସ୍ୱୟଂ-ହୋଷ୍ଟ କରିବେ?**
> [ସ୍ୱୟଂ-ହୋଷ୍ଟ ମାର୍ଗଦର୍ଶିକା](../getting-started/SELF_HOST_GUIDE.md) ଦେଖନ୍ତୁ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ପ୍ରକାଶିତ ଇମେଜ୍ +
> Redis, କେବଳ ଲୁପ୍ବ୍ୟାକ୍, କୌଣସି ପ୍ରୋଫାଇଲ୍ ଚୟନ ନାହିଁ)। ନିମ୍ନରେ ଥିବା ଦ୍ରୁତ ଚାଳନ
> ପୂର୍ବରୁ ଅନ୍ୟତ୍ର Redis ଚଲାଉଥିବା ବ୍ୟବହାରକାରୀଙ୍କ ପାଇଁ ଏକକ-କଣ୍ଟେନର୍ ପଦ୍ଧତି ଅଟେ।

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## ପରିବେଶ ଫାଇଲ୍ ସହିତ

# ପ୍ରଥମେ .envକୁ କପି କରି ସମ୍ପାଦନା କରନ୍ତୁ

## Docker Compose

```bash
# ମୂଳ ପ୍ରୋଫାଇଲ୍ (କୌଣସି CLI ଟୁଲ୍ ନାହିଁ)
docker compose --profile base up -d

# CLI ପ୍ରୋଫାଇଲ୍ (Claude Code, Codex, OpenClaw ଅନ୍ତର୍ନିର୍ମିତ)
docker compose --profile cli up -d

# ହୋଷ୍ଟ ପ୍ରୋଫାଇଲ୍ (ମୁଖ୍ୟତଃ Linux ପାଇଁ; ହୋଷ୍ଟ CLI ବାଇନାରିଗୁଡ଼ିକୁ କେବଳ ପଠନୀୟ ଭାବେ ମାଉଣ୍ଟ କରେ)
docker compose --profile host up -d

# CLI + CLIProxyAPI ସାଇଡ୍କାର୍କୁ ମିଶାନ୍ତୁ
docker compose --profile cli --profile cliproxyapi up -d
```

## ଉପଲବ୍ଧ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ

OmniRoute ସହିତ ଚାରୋଟି Compose ପ୍ରୋଫାଇଲ୍ ଉପଲବ୍ଧ। ଆପଣଙ୍କ ପରିବେଶ ସହ ମେଳ ଖାଉଥିବା ପ୍ରୋଫାଇଲ୍ ବାଛନ୍ତୁ।

| ପ୍ରୋଫାଇଲ୍       | ସେବା             | କେବେ ବ୍ୟବହାର କରିବେ                                                                                                                              | କମାଣ୍ଡ                                       |
| --------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ଡିଫଲ୍ଟ) | `omniroute-base` | ହେଡ୍ଲେସ୍ ସର୍ଭର୍ / ସର୍ବନିମ୍ନ ରନ୍ଟାଇମ୍, କୌଣସି ପ୍ରଦାନକାରୀ CLI ସମ୍ମିଳିତ ନୁହେଁ                                                                       | `docker compose --profile base up -d`        |
| `cli`           | `omniroute-cli`  | `omniroute providers/setup/doctor` ଏବଂ ସମ୍ମିଳିତ CLIଗୁଡ଼ିକୁ (Codex, Claude Code, Droid, OpenClaw) କଲ୍ କରୁଥିବା ଏଜେଣ୍ଟିକ୍ ୱାର୍କଫ୍ଲୋ                | `docker compose --profile cli up -d`         |
| `host`          | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` ଇତ୍ୟାଦିକୁ କେବଳ ପଠନୀୟ ଭାବେ ମାଉଣ୍ଟ କରି ହୋଷ୍ଟ CLIଗୁଡ଼ିକୁ `network_mode`-ସଦୃଶ ଆକ୍ସେସ୍ ଚାହୁଁଥିବା Linux ହୋଷ୍ଟ | `docker compose --profile host up -d`        |
| `cliproxyapi`   | `cliproxyapi`    | ଅପ୍ଷ୍ଟ୍ରିମ୍ CLI ପ୍ରକ୍ସି ପାଇଁ ପୋର୍ଟ `8317`ରେ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ସାଇଡ୍କାର୍ ଚଲାନ୍ତୁ                       | `docker compose --profile cliproxyapi up -d` |

> ଏକାଧିକ ପ୍ରୋଫାଇଲ୍କୁ ମିଶାଯାଇପାରିବ: `docker compose --profile cli --profile cliproxyapi up -d`।

## OmniRoute Dockerରେ ଚାଲୁଥିବାବେଳେ ହୋଷ୍ଟ CLI ଟୁଲ୍ଗୁଡ଼ିକୁ କନଫିଗର୍ କରିବା

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡର
**କନଫିଗ୍ ସଞ୍ଚୟ କରନ୍ତୁ** ବଟନ୍—ସମସ୍ତେ `~/.codex/*.config.toml` ପରି ଫାଇଲ୍ରେ ଲେଖନ୍ତି। ସେହି ପଥଗୁଡ଼ିକ
କେବଳ CLI ପ୍ରକୃତରେ ଯେଉଁ ମେସିନ୍ରେ ଚାଲୁଛି, ସେଠାରେ ହିଁ ଅର୍ଥପୂର୍ଣ୍ଣ। ସେଗୁଡ଼ିକୁ
କଣ୍ଟେନର୍ ଭିତରେ ଚଲାଇଲେ, ଲେଖା କଣ୍ଟେନର୍ର ନିଜସ୍ୱ ହୋମ୍ରେ (`/home/node` —
ଇମେଜ୍ଟି `USER node` ଭାବେ ଚାଲେ) ସଞ୍ଚିତ ହୁଏ, ଯାହାକୁ କୌଣସି ହୋଷ୍ଟ CLI କେବେ ପଢ଼ିବ ନାହିଁ ଏବଂ କଣ୍ଟେନର୍ଟି
ପୁନଃସୃଷ୍ଟି ହେବା ମାତ୍ରେ ଯାହା ବିଲୋପ ହୋଇଯାଏ।

OmniRoute ଏହାକୁ ଚିହ୍ନଟ କରେ ଏବଂ ଆପଣ ବ୍ୟବହାର କରିପାରିବେ ନାହିଁ ଏପରି ସଫଳତା ସୂଚନା ଦେବା ପରିବର୍ତ୍ତେ
ନିର୍ଦ୍ଦେଶାବଳୀ ସହିତ ଲେଖାକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ: CLI `2` ସହିତ ବନ୍ଦ ହୁଏ ଏବଂ API
`containerEphemeralTarget: true` ସହିତ `422` ଉତ୍ତର ଦିଏ।

### ସୁପାରିସକୃତ: CLIକୁ ହୋଷ୍ଟରେ ଏବଂ OmniRouteକୁ Dockerରେ ଚଲାନ୍ତୁ

କଣ୍ଟେନର୍ API ପରିବେଷଣ କରେ; CLI ଆପଣଙ୍କ ହୋଷ୍ଟ ଟୁଲ୍ଗୁଡ଼ିକୁ କନଫିଗର୍ କରେ।

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLIକୁ କଣ୍ଟେନର୍ ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ
omniroute setup-codex                      # ଆପଣଙ୍କ ହୋଷ୍ଟରେ ପ୍ରକୃତ ~/.codex ଲେଖେ
```

Codex, Claude Code, Cursor କିମ୍ବା ସମାନ ଟୁଲ୍ ଆପଣଙ୍କ
ଲ୍ୟାପ୍ଟପ୍ରେ ଚାଲୁଥିଲେ ଏହା ହିଁ ଉପଯୁକ୍ତ ବିକଳ୍ପ — ଏବଂ ସାଧାରଣତଃ ସେଟ୍ଅପ୍ ଏହିପରି ହୋଇଥାଏ।

### ବିକଳ୍ପ: ହୋଷ୍ଟ କନଫିଗ୍ ଡିରେକ୍ଟୋରିଗୁଡ଼ିକୁ bind-mount କରନ୍ତୁ (`host` ପ୍ରୋଫାଇଲ୍)

ଯଦି ଆପଣ କଣ୍ଟେନର୍କୁ ହିଁ ଆପଣଙ୍କ ହୋଷ୍ଟ କନଫିଗ୍ରେ ଲେଖିବାକୁ ଦେବାକୁ ଚାହାନ୍ତି, ତେବେ
ଡିରେକ୍ଟୋରିଗୁଡ଼ିକୁ ମାଉଣ୍ଟ କରନ୍ତୁ ଏବଂ `CLI_CONFIG_HOME`କୁ ମାଉଣ୍ଟ ରୁଟ୍କୁ ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ। `host` ପ୍ରୋଫାଇଲ୍
ପୂର୍ବରୁ ଏହା କରେ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

ଏକ bind mount ହିଁ ପଥଟିକୁ ବିଶ୍ୱସନୀୟ କରେ: OmniRoute
`/proc/self/mountinfo` ପଢ଼େ ଏବଂ ମାଉଣ୍ଟ ହୋଇଥିବା ପଥଗୁଡ଼ିକରେ (ଏବଂ ଯେଉଁ ଡିରେକ୍ଟୋରିଗୁଡ଼ିକର
ଚାଇଲ୍ଡଗୁଡ଼ିକ ମାଉଣ୍ଟ ହୋଇଛି, ଯାହା ଉପରୋକ୍ତ `/host-home` ଗଠନ ସହିତ ଠିକ୍ ମେଳ ଖାଏ) ଲେଖିବାକୁ ଅନୁମତି ଦିଏ,
କିନ୍ତୁ ମାଉଣ୍ଟ ହୋଇନଥିବା ପଥଗୁଡ଼ିକୁ ଏବେ ମଧ୍ୟ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

### ବିକଳ୍ପ ଉପାୟ: କଣ୍ଟେନର୍ର ନିଜସ୍ୱ CLIଗୁଡ଼ିକୁ କନଫିଗର୍ କରନ୍ତୁ (ସଂଯମର ସହିତ ବ୍ୟବହାର କରନ୍ତୁ)

ଯେତେବେଳେ CLIଗୁଡ଼ିକ ପ୍ରକୃତରେ କଣ୍ଟେନର୍ ଭିତରେ ଥାଏ (`cli` ପ୍ରୋଫାଇଲ୍), ଲେଖାଟି
ଉଦ୍ଦେଶ୍ୟମୂଳକ ହୋଇଥାଏ। ଯେକୌଣସି `setup-*` କମାଣ୍ଡକୁ `--allow-container-write` ପାସ୍ କରନ୍ତୁ, କିମ୍ବା ସର୍ଭର୍ ପାଇଁ
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ସେଟ୍ କରନ୍ତୁ। ଏହା କଣ୍ଟେନର୍ର ପୁନଃସୃଷ୍ଟି ପରେ ରହିବ ନାହିଁ ବୋଲି
ଏକ ଚେତାବନୀ ସହିତ ଲେଖା ଜାରି ରହେ।

> **ସୁରକ୍ଷା ଚେତାବନୀ — `cli` ପ୍ରୋଫାଇଲ୍ + `docker.sock` ମାଉଣ୍ଟ।**
> କଣ୍ଟେନର୍ଭିତରର ସ୍ୱୟଂଚାଳିତ ଅପଡେଟର୍ ଯେପରି ହୋଷ୍ଟ daemonରୁ stackକୁ
> ପୁନଃସୃଷ୍ଟି କରିପାରିବ, ସେଥିପାଇଁ `cli` ପ୍ରୋଫାଇଲ୍ `/var/run/docker.sock`କୁ bind-mount କରେ
> (`src/lib/system/autoUpdate.ts` ସେହି socketକୁ ଯାଞ୍ଚ କରେ ଏବଂ ଏହା ନଥିଲେ
> Docker ପଥକୁ ଏଡ଼ାଇଯାଏ)। ସେହି socketଟି **ଏକ host-root ବିଶ୍ୱାସ
> ସୀମା**: ଏହାକୁ ପହଞ୍ଚିପାରୁଥିବା ଯେକୌଣସି ଜିନିଷ root ଭାବେ ହୋଷ୍ଟ Docker daemonକୁ
> ନିୟନ୍ତ୍ରଣ କରେ — ଏହା ହୋଷ୍ଟରେ ଥିବା ଯେକୌଣସି କଣ୍ଟେନର୍କୁ ସୃଷ୍ଟି, ଯାଞ୍ଚ, ବନ୍ଦ ଏବଂ ଅପସାରଣ କରିପାରେ।
> ଏହାର ପ୍ରଭାବ:
>
> 1. **`cli` ପ୍ରୋଫାଇଲ୍ର ପୋର୍ଟକୁ କେବେବି ନେଟୱର୍କରେ ପ୍ରକାଶ କରନ୍ତୁ ନାହିଁ।** ଏହାକୁ
>    `127.0.0.1`ରେ ପ୍ରକାଶ କରନ୍ତୁ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LANରୁ ପହଞ୍ଚଯୋଗ୍ୟ `cli` ପ୍ରୋଫାଇଲ୍ ଯେକୌଣସି dashboard-ସ୍ତରୀୟ RCEକୁ
>    ସମ୍ପୂର୍ଣ୍ଣ ହୋଷ୍ଟ ଦଖଲରେ ପରିଣତ କରେ।
> 2. **`cli` ପ୍ରୋଫାଇଲ୍ରେ କୌଣସି ଅତିରିକ୍ତ ହୋଷ୍ଟ ଡିରେକ୍ଟୋରି bind କରନ୍ତୁ ନାହିଁ।**
>    Docker socket ସହିତ ଯେକୌଣସି ଅତିରିକ୍ତ ମାଉଣ୍ଟ କଣ୍ଟେନର୍କୁ ଆପଣଙ୍କ filesystem ଏବଂ ହୋଷ୍ଟ କନଫିଗ୍ରେ
>    ସମ୍ପୂର୍ଣ୍ଣ ପଢ଼ିବା/ଲେଖିବା ଅଧିକାର ଦିଏ। ଯଦି କୌଣସି ଟୁଲ୍କୁ ପ୍ରୋଜେକ୍ଟ ଦେଖିବାକୁ ପଡ଼େ,
>    ତେବେ CLI binary ସହିତ ଏହାକୁ ସ୍ଥାନୀୟ ଭାବେ ଚଲାନ୍ତୁ — ଏହାକୁ `cli` କଣ୍ଟେନର୍ରେ ମାଉଣ୍ଟ କରନ୍ତୁ ନାହିଁ।
>
> ଯଦି ଆପଣଙ୍କୁ କଣ୍ଟେନର୍ଭିତରେ ସ୍ୱୟଂଚାଳିତ ଅପଡେଟ୍ ଆବଶ୍ୟକ ନାହିଁ, ତେବେ `cli` ପ୍ରୋଫାଇଲ୍କୁ ବନ୍ଦ ରଖନ୍ତୁ
> (`COMPOSE_PROFILES=core,redis` କିମ୍ବା ଏହାଠାରୁ ଛୋଟ)। ଅନ୍ୟ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ
> Docker socketକୁ ମାଉଣ୍ଟ କରନ୍ତି ନାହିଁ।
>
> MITM ସମ୍ବନ୍ଧୀୟ threat model ପାଇଁ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`ରେ କମ୍ପାଇଲ୍ କରାଯାଇନାହିଁ) ଏବଂ
> `codex`/`claude-code`/`droid`/`openclaw` binaryର ଉତ୍ପତ୍ତି ଶୃଙ୍ଖଳ ପାଇଁ
> `docs/security/SUPPLY_CHAIN.md` ଦେଖନ୍ତୁ।

## Redis Sidecar

ବିତରିତ ହାର ସୀମାକାରୀ ଏବଂ ସହଭାଗୀ କ୍ୟାଶ୍କୁ ସମର୍ଥନ କରିବା ପାଇଁ OmniRoute, Redis ଉପରେ ନିର୍ଭର କରେ। `redis` ସେବାଟି `docker-compose.yml`ରେ **ସର୍ବଦା ପରିଭାଷିତ** ଥାଏ (ଏଥିରେ କୌଣସି ପ୍ରୋଫାଇଲ୍ ଗେଟ୍ ନାହିଁ) ଏବଂ ଅନ୍ୟ ଯେକୌଣସି ପ୍ରୋଫାଇଲ୍ ସହିତ ଆରମ୍ଭ ହୁଏ।

| ବିବରଣୀ                   | ମୂଲ୍ୟ                                        |
| ------------------------ | -------------------------------------------- |
| ଇମେଜ୍                    | `redis:7-alpine`                             |
| କଣ୍ଟେନର୍ ନାମ             | `omniroute-redis`                            |
| ଆଭ୍ୟନ୍ତରୀଣ ପୋର୍ଟ         | `6379`                                       |
| ହୋଷ୍ଟ ପୋର୍ଟ (ଓଭର୍ରାଇଡ୍)  | `REDIS_PORT` (ଡିଫଲ୍ଟ ହେଉଛି `6379`)           |
| ହୋଷ୍ଟ ବାଇଣ୍ଡ (ଓଭର୍ରାଇଡ୍) | `REDIS_BIND_HOST` (ଡିଫଲ୍ଟ ହେଉଛି `127.0.0.1`) |
| ଭଲ୍ୟୁମ୍                  | `omniroute-redis-data` → `/data`             |
| ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ          | `redis-cli ping` (10s ବ୍ୟବଧାନ)               |

ସମ୍ପର୍କିତ ପରିବେଶ ଭେରିଏବଲ୍ଗୁଡ଼ିକ:

- `REDIS_URL` — ଆପ୍ରେ ଇଞ୍ଜେକ୍ଟ କରାଯାଉଥିବା ସଂଯୋଗ ଷ୍ଟ୍ରିଙ୍ଗ୍ (ଡିଫଲ୍ଟ ଭାବେ `redis://redis:6379`)।
- `REDIS_PORT` — Redis କଣ୍ଟେନର୍ ପାଇଁ ହୋଷ୍ଟ-ପାର୍ଶ୍ୱ ପୋର୍ଟ ମ୍ୟାପିଂ।
- `REDIS_BIND_HOST` — ଯେଉଁ ହୋଷ୍ଟ ଇଣ୍ଟରଫେସ୍ରେ ପୋର୍ଟଟି ପ୍ରକାଶିତ ହୁଏ। ଡିଫଲ୍ଟ ହେଉଛି `127.0.0.1`।

> **ଡିଫଲ୍ଟ ଭାବେ ଲୁପ୍ବ୍ୟାକ୍ କାହିଁକି:** sidecarଟି `requirepass` ବିନା ଚାଲେ, ଏବଂ ଆପ୍
> କଣ୍ଟେନର୍ଗୁଡ଼ିକ compose ନେଟୱର୍କ (`redis:6379`) ମାଧ୍ୟମରେ ଏଥିରେ ପହଞ୍ଚନ୍ତି — ପ୍ରକାଶିତ ପୋର୍ଟଟି
> କେବଳ ହୋଷ୍ଟ-ପାର୍ଶ୍ୱ ଟୁଲିଂ (`redis-cli`, ଏକ ସ୍ଥାନୀୟ `npm run dev`) ପାଇଁ ରହିଛି। `0.0.0.0`ରେ
> ପ୍ରକାଶ କଲେ ଆପଣଙ୍କ LANର ପ୍ରତ୍ୟେକ ହୋଷ୍ଟ ପାଇଁ ଏକ ଅପ୍ରମାଣିତ Redis ଉନ୍ମୁକ୍ତ ହୋଇଯିବ। ଯଦି ଆପଣ
> `REDIS_BIND_HOST=0.0.0.0` ସେଟ୍ କରନ୍ତି, ତେବେ ସେବାର `command:`ରେ `--requirepass` ମଧ୍ୟ ଯୋଡ଼ନ୍ତୁ।

**Redis ଅକ୍ଷମ କରିବା** ସୁପାରିସ କରାଯାଏ ନାହିଁ (ହାର ସୀମାକାରୀ ଇନ୍-ମେମୋରି ଫଲ୍ବ୍ୟାକ୍କୁ ଅବନମିତ ହେବ)। ଯଦି ଏହା କରିବା ଆବଶ୍ୟକ ହୁଏ, ତେବେ `docker-compose.yml`ରେ ଥିବା `redis:` ସେବା ବ୍ଲକ୍କୁ ହଟାନ୍ତୁ/କମେଣ୍ଟ କରନ୍ତୁ କିମ୍ବା ଏହାକୁ ଶୂନ୍ୟକୁ ସ୍କେଲ୍ କରନ୍ତୁ:

```bash
docker compose up -d --scale redis=0
```

## ପ୍ରଡକ୍ସନ୍ Compose

ଡେଭ୍ ସହିତ ସମାନ୍ତରାଳ ଭାବେ ଚାଲୁଥିବା ଏକ ପୃଥକ ପ୍ରଡକ୍ସନ୍ ସ୍ନାପ୍ଶଟ୍ ପାଇଁ `docker-compose.prod.yml` ବ୍ୟବହାର କରନ୍ତୁ।

| ବିବରଣୀ                   | ମୂଲ୍ୟ                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| ଫାଇଲ୍                    | `docker-compose.prod.yml`                                                                 |
| ଡିଫଲ୍ଟ ଡ୍ୟାସ୍ବୋର୍ଡ ପୋର୍ଟ | `PROD_DASHBOARD_PORT=20130` (ଆଭ୍ୟନ୍ତରୀଣ `${DASHBOARD_PORT:-20128}` ସହିତ ମ୍ୟାପ୍ ହୋଇଛି)     |
| ଡିଫଲ୍ଟ API ପୋର୍ଟ         | `PROD_API_PORT=20131`                                                                     |
| ଇମେଜ୍                    | `omniroute:prod` (`runner-cli` ଟାର୍ଗେଟ୍ରୁ ବିଲ୍ଡ କରାଯାଇଛି)                                 |
| Redis କଣ୍ଟେନର୍           | `omniroute-redis-prod` (`redis:8.6.2`, ଉତ୍ସର୍ଗୀକୃତ `redis-prod-data` ଭଲ୍ୟୁମ୍)             |
| ଡାଟା ଭଲ୍ୟୁମ୍             | `omniroute-prod-data` (ନାମିତ, ପୁନଃବିଲ୍ଡଗୁଡ଼ିକ ମଧ୍ୟରେ ସ୍ଥାୟୀ)                              |
| ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚଗୁଡ଼ିକ    | `node healthcheck.mjs` + `redis-cli ping`, Redis ସ୍ୱାସ୍ଥ୍ୟ ଆଧାରରେ `depends_on` ଗେଟ୍ ହୋଇଛି |

ବ୍ୟବହାର ପ୍ରଣାଳୀ:

```bash
# ପ୍ରଡକ୍ସନ୍ ଷ୍ଟାକ୍ ବିଲ୍ଡ କରନ୍ତୁ ଏବଂ ଆରମ୍ଭ କରନ୍ତୁ
docker compose -f docker-compose.prod.yml up -d --build

# ଲଗ୍ଗୁଡ଼ିକୁ ଷ୍ଟ୍ରିମ୍ କରନ୍ତୁ
docker compose -f docker-compose.prod.yml logs -f

# ବନ୍ଦ କରନ୍ତୁ (ଭଲ୍ୟୁମ୍ଗୁଡ଼ିକୁ ରଖନ୍ତୁ)
docker compose -f docker-compose.prod.yml down
```

ପ୍ରଡକ୍ସନ୍ ଷ୍ଟାକ୍ଟି ଡେଭ୍ compose ସହିତ ସମାନ୍ତରାଳ ଭାବେ ଚାଲେ (ଭିନ୍ନ କଣ୍ଟେନର୍ ନାମ, ପୋର୍ଟ ଏବଂ ଭଲ୍ୟୁମ୍), ତେଣୁ ପ୍ରଡକ୍ସନ୍ ଚାଲୁ ଥିବା ସମୟରେ ଆପଣ ସ୍ଥାନୀୟ ଭାବେ ପୁନରାବୃତ୍ତିମୂଳକ ବିକାଶ ଜାରି ରଖିପାରିବେ।

## Dockerfile ପର୍ଯ୍ୟାୟଗୁଡ଼ିକ

ରିପୋଜିଟୋରୀ ସହିତ ଏକ ବହୁ-ପର୍ଯ୍ୟାୟ Dockerfile (`Dockerfile`) ମିଳେ। ତିନୋଟି ପର୍ଯ୍ୟାୟ ଉପଲବ୍ଧ କରାଯାଇଛି; ଆପଣଙ୍କ ବ୍ୟବହାର ପାଇଁ ଉପଯୁକ୍ତ `target` ବାଛନ୍ତୁ।

| ପର୍ଯ୍ୟାୟ      | ବେସ୍ ଇମେଜ୍            | ଉଦ୍ଦେଶ୍ୟ                                                                                                                                                                           |
| ------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ନିର୍ଭରତାଗୁଡ଼ିକ ଇନଷ୍ଟଲ୍ କରେ (`npm ci --legacy-peer-deps`) ଏବଂ `npm run build` ଚଲାଏ (ଡିଫଲ୍ଟ ଭାବେ Turbopack — ତଳେ ଥିବା ବିଲ୍ଡ-ସମୟ ସମ୍ବଳ ଦେଖନ୍ତୁ)                                       |

### ବିଲ୍ଡ-ସମୟ ସମ୍ବଳ

ତିନୋଟି ବିଲ୍ଡ ଆର୍ଗୁମେଣ୍ଟ୍ `builder` ପର୍ଯ୍ୟାୟର ସମ୍ବଳ ବ୍ୟୟ ନିୟନ୍ତ୍ରଣ କରେ। ସେଗୁଡ଼ିକ କେବଳ ବିଲ୍ଡ-ସମୟ ପାଇଁ —
`OMNIROUTE_MEMORY_MB` (ତଳେ) ଏକ ପୃଥକ ରନ୍ଟାଇମ୍ ନିୟନ୍ତ୍ରଣ।

| ବିଲ୍ଡ ଆର୍ଗୁମେଣ୍ଟ୍           | ଡିଫଲ୍ଟ | ପ୍ରଭାବ                                                                                          |
| --------------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `1`    | `0` ଏହା ପରିବର୍ତ୍ତେ webpack ସହିତ ବିଲ୍ଡ କରେ। ସର୍ବୋଚ୍ଚ ମେମୋରୀ ବ୍ୟବହାର କମ୍, କିନ୍ତୁ ଧୀର।             |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144` | ଆରମ୍ଭ କରାଯାଇଥିବା `next build` ପାଇଁ V8 ହିପ୍ ସୀମା (`--max-old-space-size`)।                       |
| `OMNIROUTE_BUILD_WORKERS`   | `2`    | `CIRCLE_NODE_TOTAL`କୁ ମୂଲ୍ୟ ଦିଏ; ପୃଷ୍ଠା-ଡାଟା ସଂଗ୍ରହ ପାଇଁ Next `workers = N - 1` ନିର୍ଦ୍ଧାରଣ କରେ। |

ବଡ଼ ବିଲ୍ଡର୍ରେ `OMNIROUTE_BUILD_WORKERS`ର ମୂଲ୍ୟ ବଢ଼ାଇବା ଉଚିତ ଏବଂ ସୀମିତ-ସମ୍ବଳ ବିଲ୍ଡ **`✓ Compiled successfully` ପରେ** ବିଫଳ ହେଲେ ପ୍ରଥମେ ଏହାକୁ ସନ୍ଦେହ କରିବା ଉଚିତ। ପ୍ରତ୍ୟେକ
ପୃଷ୍ଠା-ଡାଟା ୱର୍କର୍ ନିଜସ୍ୱ ପ୍ରକ୍ରିୟା, ଏବଂ ମୂଳ `next build` ମଧ୍ୟ ଏକ ପୃଥକ ପ୍ରକ୍ରିୟା;
ଏକ ଲାଇଭ୍ VPS ପୁନଃସୃଷ୍ଟିରେ (ସମସ୍ୟା #7518) ପ୍ରତ୍ୟେକ ପ୍ରକ୍ରିୟାର ସର୍ବୋଚ୍ଚ RSS
~4.5 GB ମାପ କରାଯାଇଥିଲା, ଯାହା `NODE_OPTIONS` ହିପ୍ ଫ୍ଲାଗ୍ରୁ ସ୍ୱାଧୀନ ଥିଲା (Turbopack
V8 ହିପ୍ର ବାହାରେ ଥିବା ନେଟିଭ୍/Rust ମେମୋରୀରେ କମ୍ପାଇଲ୍ କରେ)। `2` ଡିଫଲ୍ଟ (→ 1 ୱର୍କର୍, ମୋଟ 2ଟି
ପ୍ରକ୍ରିୟା) ପ୍ରକାଶନ ପାଇପଲାଇନ୍ ବ୍ୟବହାର କରୁଥିବା 16 GB / 4 vCPU GitHub-ହୋଷ୍ଟେଡ୍ ରନର୍ଗୁଡ଼ିକ
ପାଇଁ ନିର୍ଦ୍ଧାରିତ। `8`ରେ (→ 7 ୱର୍କର୍) ସେହି ରନର୍ର ମେମୋରୀ ଶେଷ ହୋଇଗଲା ଏବଂ
buildkit `ResourceExhausted: ... cannot allocate memory` ସହିତ ପଦକ୍ଷେପଟିକୁ ବିଫଳ କଲା;
ପ୍ରତି-ପ୍ରକ୍ରିୟା RSSକୁ ଅନୁମାନ କରିବା ପରିବର୍ତ୍ତେ ସିଧାସଳଖ ମାପ କରାଯିବା ପରେ
`3` (→ 2 ୱର୍କର୍) ମଧ୍ୟ ଫିଟ୍ ହେଲା ନାହିଁ। `tests/unit/docker-build-memory-budget.test.ts`
ମାପ କରାଯାଇଥିବା ମୂଲ୍ୟ ଆଧାରରେ ଗଣନା କରେ ଏବଂ ଯେକୌଣସି ନିୟନ୍ତ୍ରଣର ମୂଲ୍ୟ
ରନର୍ର କ୍ଷମତା ଅତିକ୍ରମ କଲେ ବିଫଳ ହୁଏ।

Turbopack V8 ହିପ୍ର **ବାହାରେ** ଥିବା ନେଟିଭ୍ Rust ମେମୋରୀରେ କମ୍ପାଇଲ୍ କରେ, ତେଣୁ
`OMNIROUTE_BUILD_MEMORY_MB` ଏହାକୁ ସୀମିତ କରେ ନାହିଁ। ମେମୋରୀ ସୀମା ଥିବା ହୋଷ୍ଟରେ
ବିଲ୍ଡଟି କୌଣସି ତ୍ରୁଟି ବାର୍ତ୍ତା ବିନା OOM killer ଦ୍ୱାରା SIGKILL ହୁଏ — ଏହା କେବଳ
`Creating an optimized production build` ମଝିରେ ଅଟକିଯାଏ, ଯାହା ମେମୋରୀ ଶେଷ
ହେବା ପରିବର୍ତ୍ତେ ହ୍ୟାଙ୍ଗ୍ ହୋଇଥିବା ପରି ଲାଗେ। ବିଲ୍ଡ ହୋଷ୍ଟର ସମ୍ବଳ ସୀମିତ ଥିଲେ, ବଣ୍ଡଲର୍ ପରିବର୍ତ୍ତନ କରନ୍ତୁ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=0 \
  -t omniroute:base .
```

`webpackBuildWorker` ସକ୍ଷମ ଅଛି, ତେଣୁ `next build` ଏକ ମୂଳ **ଏବଂ** ଏକ ୱର୍କର୍
ପ୍ରକ୍ରିୟା ଚଲାଏ ଏବଂ ପ୍ରତ୍ୟେକଟି ପୃଥକ ଭାବେ `OMNIROUTE_BUILD_MEMORY_MB`କୁ ମାନେ।
କଣ୍ଟେନର୍ ସୀମାକୁ ସେହି ମୂଲ୍ୟର ପ୍ରାୟ ଦୁଇଗୁଣାରୁ ଅଧିକ ରଖନ୍ତୁ, ଏକଗୁଣା ନୁହେଁ।

ଏହି ଟ୍ରିରେ ମାପ କରାଯାଇଛି (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ବଣ୍ଡଲର୍   | କଣ୍ଟେନର୍ ସୀମା  | ଫଳାଫଳ                          |
| --------- | -------------- | ------------------------------ |
| Turbopack | 8 GiB / 16 GiB | ଉଭୟରେ ନିରବରେ OOM-killed        |
| webpack   | 8 GiB          | ବିଲ୍ଡ ୱର୍କର୍ SIGKILLed         |
| webpack   | 12 GiB         | ସଫଳ, ସର୍ବୋଚ୍ଚ ବ୍ୟବହାର 11.1 GiB |

### ରନ୍ଟାଇମ୍ ଡିଫଲ୍ଟଗୁଡ଼ିକ

`runner-base` ଦ୍ୱାରା ଏକ୍ସପୋର୍ଟ୍ ହୋଇଥିବା ଡିଫଲ୍ଟଗୁଡ଼ିକ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`।

Dockerରେ ମେମୋରୀ ଆଚରଣ:

- ଇମେଜ୍ଟି `OMNIROUTE_MEMORY_MB=1024` ସେଟ୍ କରେ ଏବଂ ଏଥିରୁ `NODE_OPTIONS=--max-old-space-size=1024` ନିର୍ଦ୍ଧାରଣ କରେ।
- ପ୍ରକୃତ ସର୍ଭର୍ ପ୍ରକ୍ରିୟା ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ଲଞ୍ଚର୍ ଦ୍ୱାରା ଆରମ୍ଭ ହୁଏ, ଯାହା `OMNIROUTE_MEMORY_MB` ପଢ଼େ ଏବଂ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ଯୋଡ଼େ।
- Node ଶେଷରେ ପୁନରାବୃତ୍ତ ହୋଇଥିବା `--max-old-space-size` ମୂଲ୍ୟ ବ୍ୟବହାର କରେ, ତେଣୁ `OMNIROUTE_MEMORY_MB` ସେଟ୍ କରିବା ଦ୍ୱାରା ପ୍ରଭାବୀ Docker ହିପ୍ ସୀମା ନିୟନ୍ତ୍ରିତ ହୁଏ।
- ଇମେଜ୍ଟି ସର୍ବଦା ଏହାକୁ ସେଟ୍ କରୁଥିବାରୁ, ଲଞ୍ଚର୍ର ନିଜସ୍ୱ RAM-କ୍ୟାଲିବ୍ରେଟେଡ୍ ଫଲ୍ବ୍ୟାକ୍ Docker ଅଧୀନରେ କେବେ ପ୍ରୟୋଗ ହୁଏ ନାହିଁ। ୱର୍କଲୋଡ୍ ପାଇଁ ଏହାକୁ ସ୍ପଷ୍ଟ ଭାବେ ବଢ଼ାନ୍ତୁ (ତଳେ ଥିବା ସାରଣୀ)। କୋଡିଂ-ଏଜେଣ୍ଟ୍ `/v1/responses` ପାଇଁ `2048` ଏବେ ମଧ୍ୟ ଅତ୍ୟନ୍ତ କମ୍।

### କୋଡିଂ ଏଜେଣ୍ଟ୍ଗୁଡ଼ିକ ପାଇଁ ରନ୍ଟାଇମ୍ RAM

1 GiB Docker ଡିଫଲ୍ଟ ଏକ ଡ୍ୟାସ୍ବୋର୍ଡ୍/ହାଲୁକା-ଚାଟ୍ର ସର୍ବନିମ୍ନ ସୀମା, ପ୍ରଡକ୍ସନ୍ ଆକାର ନୁହେଁ। ଦୀର୍ଘ `POST /v1/responses` ବଡିଗୁଡ଼ିକ (ଶହ ଶହ ବାର୍ତ୍ତା, ଦଶ ଦଶଟି ଟୁଲ୍) ସଂକୋଚନ ସମୟରେ ଏକାଧିକ ଇନ୍-ମେମୋରୀ ଗ୍ରାଫ୍ ଧାରଣ କରେ। ପରସ୍ପର ଓଭରଲାପ୍ କରୁଥିବା ଦୁଇଟି ~3 MiB / ~750k-token ଅନୁରୋଧ **12 GiB** old-spaceରେ V8କୁ ବନ୍ଦ କରିଛି (`FATAL ERROR: Reached heap limit`) ଏବଂ 16 GiB cgroup OOM ମଧ୍ୟ ଘଟାଇଛି। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ଦେଖନ୍ତୁ।

cgroup `--memory`କୁ **ହିପ୍ଠାରୁ ଅଧିକ** ଆକାର ଦିଅନ୍ତୁ — ନେଟିଭ୍ ବଫର୍, SQLite ଏବଂ ସଂକୋଚନର ମଧ୍ୟବର୍ତ୍ତୀ ଡାଟା V8ର ବାହାରେ ରହେ।

| କାର୍ଯ୍ୟଭାର                                | `OMNIROUTE_MEMORY_MB`         | କଣ୍ଟେନର୍ / cgroup              | ଟିପ୍ପଣୀ                                                                               |
| ----------------------------------------- | ----------------------------- | ------------------------------ | ------------------------------------------------------------------------------------- |
| ଡ୍ୟାଶବୋର୍ଡ, ଗୋଟିଏ ହାଲୁକା ଚାଟ୍             | `1024` (ଇମେଜ୍ ଡିଫଲ୍ଟ)         | ≥2 GiB                         |                                                                                       |
| ଗୋଟିଏ କୋଡିଂ ଏଜେଣ୍ଟ (Claude/Codex/Grok)    | `8192`                        | ≥10 GiB                        | ସାଧାରଣ ଏକକ-ସେସନ୍ `/v1/responses`                                                      |
| ଏକସଙ୍ଗେ ଦୁଇଟି ଦୀର୍ଘ `/v1/responses`       | `10240`–`12288`               | ≥12–16 GiB                     | ~12 GiB ହିପ୍ରେ ମାପ କରାଯାଇଥିବା V8 ବିଚ୍ଛିନ୍ନତା                                          |
| ଏକସଙ୍ଗେ ତିନି କିମ୍ବା ଅଧିକ ଦୀର୍ଘ କଣ୍ଟେକ୍ସ୍ଟ | ଗୋଟିଏ ପ୍ରୋସେସ୍ରେ କରନ୍ତୁ ନାହିଁ | କ୍ରମିକ ଭାବେ ଚଲାନ୍ତୁ / ଅଧିକ RAM | ଡିଫଲ୍ଟ ଭାରୀ ଆଡ୍ମିସନ୍ରେ 1ଟି ଇନ୍-ଫ୍ଲାଇଟ୍ ରହେ; RAM ବିନା ଏହା ବଢ଼ାଇଲେ ବିଚ୍ଛିନ୍ନତା ପୁଣି ଘଟେ |

ବେୟାର୍ ମେଟାଲ୍ରେ `omniroute serve`, `OMNIROUTE_MEMORY_MB` **ସେଟ୍ ହୋଇନଥିଲେ**, RAMର ~35% (`[512, 4096]` ସୀମା ମଧ୍ୟରେ) କ୍ୟାଲିବ୍ରେଟ୍ କରେ। Docker ସର୍ବଦା `1024` ସେଟ୍ କରେ, ତେଣୁ ଅଫିସିଆଲ୍ ଇମେଜ୍ରେ ସେହି କ୍ୟାଲିବ୍ରେସନ୍ କେବେ ଚାଲେ ନାହିଁ।

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ସବ୍ପାଥ୍ରେ ରିଭର୍ସ ପ୍ରକ୍ସି (Traefik / nginx)

Next.js `basePath` ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ବଣ୍ଡଲ୍ରେ କମ୍ପାଇଲ୍ ହୋଇଥାଏ। OmniRoute ଆପ୍ର ରୁଟ୍ରେ ଥିବା ଏକ ସେଣ୍ଟିନେଲ୍ ଫାଇଲ୍ରେ ପୂର୍ବରୁ ସଂଯୋଜିତ ମୂଲ୍ୟକୁ ରେକର୍ଡ କରେ (`npm run build` ସମୟରେ ଲେଖାଯାଏ; `scripts/docker/ensure-docker-base-path.mjs` ଦ୍ୱାରା ପଢ଼ାଯାଏ) ଏବଂ କଣ୍ଟେନର୍ ଆରମ୍ଭ ହେବାବେଳେ ଏହାକୁ `OMNIROUTE_BASE_PATH` ସହ ତୁଳନା କରେ। ଯେତେବେଳେ ସେଗୁଡ଼ିକ ଭିନ୍ନ ଥାଏ ଏବଂ ଇମେଜ୍ଟି ଡୋମେନ୍ ରୁଟ୍ ପାଇଁ ବିଲ୍ଡ ହୋଇଥାଏ, ସେତେବେଳେ `node dev/run-standalone.mjs` ଚାଲିବା ପୂର୍ବରୁ ଏଣ୍ଟ୍ରିପଏଣ୍ଟ ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ମ୍ୟାନିଫେଷ୍ଟଗୁଡ଼ିକ, ଏମ୍ବେଡ୍ ହୋଇଥିବା `basePath`/`assetPrefix` ଲିଟେରାଲ୍ଗୁଡ଼ିକ (Next 16 କେବଳ `assetPrefix`ରୁ SSR ଆସେଟ୍ URL ରେଣ୍ଡର୍ କରେ — ପ୍ୟାଚର୍ ସବ୍ପାଥ୍କୁ ମଧ୍ୟ ଏଥିରେ ପ୍ରତିଫଳିତ କରେ), ପୂର୍ବରୁ ସଂଯୋଜିତ `/_next/static` ଆସେଟ୍ URLଗୁଡ଼ିକ (କ୍ଲାଏଣ୍ଟ-ରେଫରେନ୍ସ ମ୍ୟାନିଫେଷ୍ଟ, ମିଡିଆ ଇମ୍ପୋର୍ଟ, ପ୍ରିରେଣ୍ଡର୍ ହୋଇଥିବା ତ୍ରୁଟି ପୃଷ୍ଠା) ଏବଂ କ୍ଲାଏଣ୍ଟ `process.env` ଶିମ୍କୁ ପୁନଃଲେଖନ କରେ।

### Compose ବିଲ୍ଡ (ସୁପାରିଶକୃତ)

`.env`ରେ ଉଭୟ ଭେରିଏବଲ୍ ସେଟ୍ କରନ୍ତୁ, ତା’ପରେ ଇମେଜ୍ ଏବଂ ରନ୍ଟାଇମ୍ରେ ସମାନ ମୂଲ୍ୟ ରହିବା ପାଇଁ ପୁନଃବିଲ୍ଡ କରନ୍ତୁ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH`କୁ ଏକ Docker ବିଲ୍ଡ-ଆର୍ଗ୍ ଭାବରେ ଏବଂ ଏକ ରନ୍ଟାଇମ୍ ପରିବେଶ ଭେରିଏବଲ୍ ଭାବରେ ଫରୱାର୍ଡ କରେ।

### ପୂର୍ବରୁ ବିଲ୍ଡ ହୋଇଥିବା ରୁଟ୍ ଇମେଜ୍ + ରନ୍ଟାଇମ୍ ସବ୍ପାଥ୍

ପ୍ରକାଶିତ `diegosouzapw/omniroute:*` ଇମେଜ୍ଗୁଡ଼ିକ ଡୋମେନ୍ ରୁଟ୍ ପାଇଁ ବିଲ୍ଡ ହୋଇଛି। ତଥାପି ଆପଣ ରନ୍ଟାଇମ୍ରେ `OMNIROUTE_BASE_PATH` ସେଟ୍ କରିପାରିବେ; କଣ୍ଟେନର୍ ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ ବଣ୍ଡଲ୍କୁ ଥରେ ପ୍ୟାଚ୍ କରେ। ଏହା ସହିତ ମେଳ ଖାଉଥିବା ସାର୍ବଜନୀନ ଅରିଜିନ୍କୁ ଯୋଡ଼ନ୍ତୁ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

**ସମ୍ପୂର୍ଣ୍ଣ** ବାହ୍ୟ ପାଥ୍କୁ ଫରୱାର୍ଡ କରିବା ପାଇଁ ରିଭର୍ସ ପ୍ରକ୍ସିକୁ କନଫିଗର୍ କରନ୍ତୁ (ପ୍ରିଫିକ୍ସ ହଟାନ୍ତୁ ନାହିଁ)। Traefik, `StripPrefix` ବିନା `PathPrefix(`/omniroute`)`କୁ କଣ୍ଟେନର୍ ଆଡ଼କୁ ରୁଟ୍ କରିବା ଉଚିତ, ଯାହାଦ୍ୱାରା Next.js `/omniroute/...` ଗ୍ରହଣ କରିବ ଏବଂ `/omniroute/_next/...`ରୁ ଆସେଟ୍ ପରିବେଷଣ କରିବ।

Docker ହେଲ୍ଥଚେକ୍, ସକ୍ରିୟ `OMNIROUTE_BASE_PATH` ପ୍ରିଫିକ୍ସ ସହିତ ହାଲୁକା `/healthz` ଲାଇଫସାଇକଲ୍ ଏଣ୍ଡପଏଣ୍ଟକୁ ପ୍ରୋବ୍ କରେ। ମାନବ/ଡ୍ୟାସବୋର୍ଡ ଡାୟାଗ୍ନୋଷ୍ଟିକ୍ସ ପାଇଁ `/api/monitoring/health` ଉପଲବ୍ଧ ରହେ; କଣ୍ଟେନର୍ HEALTHCHECKକୁ ପୁଣି ଏହା ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରିବା ପାଇଁ (ଉଦାହରଣ ସ୍ୱରୂପ, ଗଭୀର ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ ବାଧ୍ୟତାମୂଳକ କରିବାକୁ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ସେଟ୍ କରନ୍ତୁ। ସେହି ପାଥ୍ ଏକ **ଗଭୀର** ଯାଞ୍ଚ (DB + ମନିଟରିଂ ସାରାଂଶ) — ଆପଣ ପୁଣି ଏହାକୁ ସକ୍ରିୟ କଲେ Dockerର ବିରଳ `HEALTHCHECK` ପାଇଁ ଉପଯୁକ୍ତ, କିନ୍ତୁ Kubernetes `livenessProbe` ଇଣ୍ଟରଭାଲ୍ ପାଇଁ **ନୁହେଁ**।

| ରେଡିନେସ୍          | HTTP `GET /healthz`                                                  | ଇଭେଣ୍ଟ-ଲୁପ୍ ବ୍ୟସ୍ତ ଥିବାକୁ ନିଷ୍କ୍ରିୟ ଭାବେ ଧରୁଥିବା କଡ଼ା ଟାଇମ୍ଆଉଟ୍ |

`/healthz` ପ୍ରକ୍ରିୟାର ଲାଇଫସାଇକଲ୍ (`ok` / `starting` / `stopping`) ରିପୋର୍ଟ କରେ। `/livez` କେବଳ ପ୍ରକ୍ରିୟାଟି ସକ୍ରିୟ ଅଛି କି ନାହିଁ ଜଣାଏ (ହ୍ୟାଣ୍ଡଲର୍ ଚାଲିପାରିଲେ ସବୁବେଳେ 200; ଏହା ରେଡିନେସ୍ ପାଇଁ ଅପେକ୍ଷା କରେ ନାହିଁ)। ଉଭୟ ତଥାପି ଅନୁରୋଧ ପରିଚାଳନା ସହିତ ସମାନ Node ଇଭେଣ୍ଟ ଲୁପ୍ରେ ଚାଲେ, ତେଣୁ CPU-ବାଉଣ୍ଡ କ୍ୟାଟାଲଗ୍ କିମ୍ବା କମ୍ପ୍ରେସନ୍ କାର୍ଯ୍ୟ ସେଗୁଡ଼ିକୁ ବିଳମ୍ବିତ କରିପାରେ — ବ୍ୟସ୍ତ ≠ ନିଷ୍କ୍ରିୟ। HTTP ପ୍ରୋବ୍ର ସମୟ ସମାପ୍ତ ହେଲେ TCP ଲାଇଭ୍ନେସ୍କୁ ପସନ୍ଦ କରନ୍ତୁ। ସମ୍ପୂର୍ଣ୍ଣ ପ୍ରୋବ୍ ମାର୍ଗଦର୍ଶନ:
[ମନିଟରିଂ ଗାଇଡ୍ — Kubernetes ପ୍ରୋବ୍ ସୁପାରିଶଗୁଡ଼ିକ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)।

## Caddy ସହିତ Docker Compose (HTTPS Auto-TLS)

Caddyର ସ୍ୱୟଂଚାଳିତ SSL ପ୍ରୋଭିଜନିଂ ବ୍ୟବହାର କରି OmniRouteକୁ ସୁରକ୍ଷିତ ଭାବରେ ଉପଲବ୍ଧ କରାଯାଇପାରିବ। ଆପଣଙ୍କ ଡୋମେନ୍ର DNS A ରେକର୍ଡ ଆପଣଙ୍କ ସର୍ଭର୍ର IPକୁ ସୂଚାଉଥିବା ନିଶ୍ଚିତ କରନ୍ତୁ।

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth କଲ୍ବ୍ୟାକ୍, ଡ୍ୟାସ୍ବୋର୍ଡ ଲିଙ୍କ ଏବଂ ଉତ୍ପାଦିତ ସାର୍ବଜନୀନ URLଗୁଡ଼ିକ ପାଇଁ ବ୍ରାଉଜର୍-ସମ୍ମୁଖୀନ ଅରିଜିନ୍।
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ନିର୍ଦ୍ଧାରିତ କାର୍ଯ୍ୟ / ସ୍ୱୟଂ-ଫେଚ୍ ପାଇଁ ଆଭ୍ୟନ୍ତରୀଣ ସର୍ଭର୍-ରୁ-ସର୍ଭର୍ URL।
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy ଅପ୍ଷ୍ଟ୍ରିମ୍ କଣ୍ଟେନର୍ ପାଇଁ ମାନକ ଫରୱାର୍ଡିଂ ହେଡର୍ଗୁଡ଼ିକ ସେଟ୍ କରେ। OAuth କଲ୍ବ୍ୟାକ୍ ଏବଂ ଉତ୍ପାଦିତ ସାର୍ବଜନୀନ
ଲିଙ୍କଗୁଡ଼ିକ ପାଇଁ OmniRoute, `NEXT_PUBLIC_BASE_URL`କୁ କ୍ୟାନୋନିକାଲ୍ ସାର୍ବଜନୀନ ଅରିଜିନ୍ ଭାବରେ ବ୍ୟବହାର କରେ;
ପ୍ରାମାଣିକୃତ ଡ୍ୟାସ୍ବୋର୍ଡ ଲେଖନ କାର୍ଯ୍ୟଗୁଡ଼ିକ ସମାନ-ଅରିଜିନ୍ ଅନୁରୋଧ ସହିତ ସେସନ୍-ବାଉଣ୍ଡ CSRF
ସୁରକ୍ଷା ବ୍ୟବହାର କରେ। କେବଳ ସେହି ଉନ୍ନତ ଡିପ୍ଲୟମେଣ୍ଟ ପାଇଁ `OMNIROUTE_TRUST_PROXY` ସକ୍ଷମ କରନ୍ତୁ, ଯେଉଁଠାରେ ଆପଣ ସ୍ପଷ୍ଟ
ବିନ୍ୟାସ ପରିବର୍ତ୍ତେ ବିଶ୍ୱସ୍ତ ଫରୱାର୍ଡ କରାଯାଇଥିବା ହେଡର୍ଗୁଡ଼ିକରୁ OmniRoute ସାର୍ବଜନୀନ ଅରିଜିନ୍ ନିର୍ଣ୍ଣୟ କରୁ ବୋଲି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ
ଚାହୁଁଛନ୍ତି।

## Cloudflare Quick Tunnel

Docker ଡିପ୍ଲୟମେଣ୍ଟ ପାଇଁ ଡ୍ୟାସ୍ବୋର୍ଡ ସମର୍ଥନରେ `Dashboard → Endpoints`ଠାରେ ଏକ-କ୍ଲିକ୍ **Cloudflare Quick Tunnel** ଅନ୍ତର୍ଭୁକ୍ତ। ପ୍ରଥମ ଥର ସକ୍ଷମ କଲେ, କେବଳ ଆବଶ୍ୟକ ସମୟରେ `cloudflared` ଡାଉନଲୋଡ୍ ହୁଏ, ଆପଣଙ୍କ ବର୍ତ୍ତମାନର `/v1` ଏଣ୍ଡପଏଣ୍ଟ ପାଇଁ ଏକ ଅସ୍ଥାୟୀ ଟନେଲ୍ ଆରମ୍ଭ ହୁଏ ଏବଂ ଆପଣଙ୍କ ସାଧାରଣ ସାର୍ବଜନୀନ URLର ଠିକ୍ ତଳେ ଉତ୍ପାଦିତ `https://*.trycloudflare.com/v1` URL ଦେଖାଯାଏ।

ସକ୍ରିୟ ଟନେଲ୍ର ସ୍ଥିତି ପରିବର୍ତ୍ତନ ନକରି ଏଣ୍ଡପଏଣ୍ଟ ଟନେଲ୍ ପ୍ୟାନେଲ୍ଗୁଡ଼ିକୁ (Cloudflare, Tailscale, ngrok) `Settings → Appearance`ରୁ ଦେଖାଇବା କିମ୍ବା ଲୁଚାଇବା ଯାଇପାରିବ।

### ଟନେଲ୍ ସମ୍ବନ୍ଧୀୟ ଟିପ୍ପଣୀ

- Quick Tunnel URLଗୁଡ଼ିକ ଅସ୍ଥାୟୀ ଏବଂ ପ୍ରତ୍ୟେକ ପୁନଃପ୍ରାରମ୍ଭ ପରେ ପରିବର୍ତ୍ତିତ ହୁଏ।
- OmniRoute କିମ୍ବା କଣ୍ଟେନର୍ ପୁନଃପ୍ରାରମ୍ଭ ପରେ Quick Tunnelଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ପୁନରୁଦ୍ଧାର ହୁଏନାହିଁ। ଆବଶ୍ୟକ ସମୟରେ ଡ୍ୟାସ୍ବୋର୍ଡରୁ ସେଗୁଡ଼ିକୁ ପୁନଃ ସକ୍ଷମ କରନ୍ତୁ।
- ପରିଚାଳିତ ଇନ୍ଷ୍ଟଲେସନ୍ ବର୍ତ୍ତମାନ `x64` / `arm64`ରେ Linux, macOS ଏବଂ Windowsକୁ ସମର୍ଥନ କରେ।
- ସୀମିତ କଣ୍ଟେନର୍ ପରିବେଶରେ କୋଳାହଳପୂର୍ଣ୍ଣ QUIC UDP ବଫର୍ ଚେତାବନୀ ଏଡ଼ାଇବା ପାଇଁ ପରିଚାଳିତ Quick Tunnelଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବରେ HTTP/2 ପରିବହନ ବ୍ୟବହାର କରେ। ଆପଣ ଭିନ୍ନ ପରିବହନ ଚାହୁଁଥିଲେ `CLOUDFLARED_PROTOCOL=quic` କିମ୍ବା `auto` ସେଟ୍ କରନ୍ତୁ।
- Docker ଇମେଜ୍ଗୁଡ଼ିକ ସିଷ୍ଟମ୍ CA ରୁଟ୍ଗୁଡ଼ିକୁ ବଣ୍ଡଲ୍ କରି ପରିଚାଳିତ `cloudflared`କୁ ପଠାଏ, ଯାହା କଣ୍ଟେନର୍ ଭିତରେ ଟନେଲ୍ ବୁଟ୍ଷ୍ଟ୍ରାପ୍ ହେବା ସମୟରେ TLS ବିଶ୍ୱାସ ବିଫଳତାକୁ ଏଡ଼ାଏ।
- OmniRoute ଏକ ନୂଆ ବାଇନାରି ଡାଉନଲୋଡ୍ କରିବା ପରିବର୍ତ୍ତେ ପୂର୍ବରୁ ଥିବା ବାଇନାରି ବ୍ୟବହାର କରୁ ବୋଲି ଚାହୁଁଥିଲେ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ସେଟ୍ କରନ୍ତୁ।

#### ପ୍ରି-ରିଲିଜ୍ ଚ୍ୟାନେଲ୍ର ବ୍ୟବହାର

ବର୍ତ୍ତମାନର ଡିଫଲ୍ଟ `release/v*` ବ୍ରାଞ୍ଚକୁ ପ୍ରତ୍ୟେକ ପୁସ୍ରେ `next` ଚ୍ୟାନେଲ୍ ପୁନଃନିର୍ମିତ ହୁଏ ଏବଂ AMD64 ଓ ARM64 ଉଭୟ ପାଇଁ ପ୍ରକାଶିତ ହୁଏ। ପୁରୁଣା ରକ୍ଷଣାବେକ୍ଷଣ ବ୍ରାଞ୍ଚଗୁଡ଼ିକ ଏହାକୁ ଓଭର୍ରାଇଟ୍ କରିପାରିବେ ନାହିଁ। ପରବର୍ତ୍ତୀ ସ୍ଥିର ଟ୍ୟାଗ୍ ତିଆରି ହେବା ପୂର୍ବରୁ ସକ୍ରିୟ ରିଲିଜ୍ ବ୍ରାଞ୍ଚରେ ମର୍ଜ୍ ହୋଇଥିବା ସମାଧାନଗୁଡ଼ିକ ପାଇଁ ଏହି ଚ୍ୟାନେଲ୍ ଏକ ପୁଲ୍ କରିହେବା ଯୋଗ୍ୟ ଇମେଜ୍ ପ୍ରଦାନ କରେ।

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ପାଇଁ, ଚୟନିତ ପ୍ରୋଫାଇଲ୍ରେ ବ୍ୟବହୃତ ଇମେଜ୍ ଟ୍ୟାଗ୍କୁ ଓଭର୍ରାଇଡ୍ କରନ୍ତୁ, ତା’ପରେ ସେବାକୁ ପୁଲ୍ କରି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ସୁରକ୍ଷା ଏବଂ ରୋଲ୍ବ୍ୟାକ୍

`next` ହେଉଛି ଏକ ଫ୍ଲୋଟିଂ ପ୍ରି-ରିଲିଜ୍ ଚ୍ୟାନେଲ୍। ସକ୍ରିୟ ରିଲିଜ୍ ବ୍ରାଞ୍ଚକୁ ଯେକୌଣସି ପୁସ୍ରେ ଏହା ପରିବର୍ତ୍ତିତ ହୋଇପାରେ ଏବଂ ଏହା **ପ୍ରଡକ୍ସନ୍ ବ୍ୟବହାର ପାଇଁ ସମର୍ଥିତ ନୁହେଁ**। ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ବିଲ୍ଡକୁ ମୂଲ୍ୟାୟନ କରୁଥିବା ସମୟରେ ଇମେଜ୍ ଡାଇଜେଷ୍ଟକୁ ପିନ୍ କରନ୍ତୁ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ପରୀକ୍ଷଣ ପୂର୍ବରୁ, OmniRoute ଡାଟା ଭଲ୍ୟୁମ୍ କିମ୍ବା bind-mounted ଡାଟା ଡିରେକ୍ଟୋରୀର ବ୍ୟାକଅପ୍ ନିଅନ୍ତୁ। ପୂର୍ବ ସ୍ଥିତିକୁ ଫେରାଇବା ପାଇଁ, ପୂର୍ବରୁ ବ୍ୟବହୃତ ସ୍ଥିର ସଂସ୍କରଣ କିମ୍ବା digest ପୁନଃସ୍ଥାପନ କରନ୍ତୁ ଏବଂ କଣ୍ଟେନର୍ଟି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

ଏକ release-branch ବିଲ୍ଡ କେବେବି `latest`କୁ ପରିବର୍ତ୍ତନ କରିପାରିବ ନାହିଁ; କେବଳ ଏକ ଯୋଗ୍ୟ ସ୍ଥିର semantic version ହିଁ ସ୍ଥିର ପଏଣ୍ଟର୍କୁ ପ୍ରୋମୋଟ୍ କରିପାରିବ। `next` ଇମେଜ୍ଗୁଡ଼ିକ release image inspection ଏବଂ ବ୍ଲକିଂ CRITICAL-vulnerability gateକୁ ବଜାୟ ରଖନ୍ତି।

**git ପାଇଁ `latest` ହେଉଛି ସଦ୍ୟତାର ନିଶ୍ଚିତତା ନୁହେଁ।** `main` କିମ୍ବା ସକ୍ରିୟ `release/v*` ବ୍ରାଞ୍ଚରେ ମର୍ଜ୍ ହୋଇଥିବା ସଂଶୋଧନଗୁଡ଼ିକ, ଏକ ସ୍ଥିର SemVer ଇମେଜ୍ ପ୍ରକାଶିତ ହୋଇ publish job ଦ୍ୱାରା `:latest` ପ୍ରୋମୋଟ୍ ନହେବା ପର୍ଯ୍ୟନ୍ତ `:latest`ରେ ଉପଲବ୍ଧ ହୁଏ ନାହିଁ (ସେହି SemVer ସହିତ ସମାନ digest)। GitHubରେ ସଂଶୋଧନଟି ପୂର୍ବରୁ ଦେଖାଯାଉଥିବା ବେଳେ ଯଦି `latest` ସ୍ଥିର ହୋଇ ରହିଥିବା ପରି ଲାଗେ, ତେବେ release ବ୍ରାଞ୍ଚ ପରୀକ୍ଷା କରିବାକୁ `:next` pull କରନ୍ତୁ କିମ୍ବା SemVer ଟ୍ୟାଗ୍ ପାଇଁ ଅପେକ୍ଷା କରନ୍ତୁ।

| ----------------------------------------------------------------------------------- | -------------------------------------------- |

## ଉପଲବ୍ଧତା: ଡିଫଲ୍ଟ SQLite ହେଉଛି ଏକକ-ରେପ୍ଲିକା

ମାନକ Docker / Kubernetes OmniRoute ହେଉଛି **ଗୋଟିଏ Node ପ୍ରକ୍ରିୟା + ଗୋଟିଏ SQLite ରାଇଟର୍**। ଏହି ଟୋପୋଲୋଜିରେ ଉଚ୍ଚ ଉପଲବ୍ଧତା **ସମର୍ଥିତ ନୁହେଁ**।

| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ଏକକ ରାଇଟର୍                                      | ସମାନ SQLite ଫାଇଲ୍ରେ ଏକାଧିକ ରେପ୍ଲିକା **ଚଲାନ୍ତୁ ନାହିଁ**। ଏହା DBକୁ ନଷ୍ଟ କରିଦିଏ।                                                                                                                                                                                                                                                                             |

| ----------------- | ---------------------------------------------------------- | ---------------------------------------------------------------- |
| ଲାଇଭ୍ନେସ୍         | `PORT`ରେ TCP (ଡିଫଲ୍ଟ `20128`), କିମ୍ବା ସଫ୍ଟ HTTP `/healthz` | `/api/monitoring/health`                                         |
| ରେଡିନେସ୍          | HTTP `GET /healthz`                                        | ଇଭେଣ୍ଟ ଲୁପ୍ର ବ୍ୟସ୍ତତାକୁ ବନ୍ଦ ଭାବେ ବିବେଚନା କରୁଥିବା କଠୋର ଟାଇମ୍ଆଉଟ୍ |
| ଗଭୀର ଯାଞ୍ଚ / ମଣିଷ | `/api/monitoring/health`                                   | ସ୍ୱୟଂଚାଳିତ kubelet ଲାଇଭ୍ନେସ୍                                     |

**ଅପ୍ଗ୍ରେଡ୍:** ପ୍ରତ୍ୟେକ ସେସନ୍ର ସଂଯୋଗ ବିଚ୍ଛିନ୍ନ ହେବ ବୋଲି ଆଶା କରନ୍ତୁ। ସମ୍ଭବ ହେଲେ କ୍ଲାଏଣ୍ଟଗୁଡ଼ିକୁ ଡ୍ରେନ୍ କରନ୍ତୁ; ଡିଫଲ୍ଟ SQLiteରେ କୌଣସି ରୋଲିଂ ଅପଡେଟ୍ ନାହିଁ। Docker `HEALTHCHECK` ସହ Compose `restart: unless-stopped` ମଧ୍ୟ କଣ୍ଟେନର୍ଟି Unhealthy ହେଲେ ଏକମାତ୍ର ପ୍ରକ୍ରିୟାକୁ ପ୍ରତିସ୍ଥାପନ କରିବ — ପ୍ରଭାବର ପରିସର ସମାନ ରହିବ।

ଏକ **ଏକକ ରେପ୍ଲିକା** ପାଇଁ Kubernetes ସ୍ନିପେଟ୍ (Recreate ଆବଶ୍ୟକ; ଗୋଟିଏ SQLite ଫାଇଲ୍ ପାଇଁ `replicas` ବଢ଼ାନ୍ତୁ ନାହିଁ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` ସ୍ଲିପ୍ SIGTERM ପୂର୍ବରୁ kubeକୁ Service ଏଣ୍ଡପଏଣ୍ଟଗୁଡ଼ିକୁ ହଟାଇବାକୁ ସମୟ ଦିଏ, ଯାହାଦ୍ୱାରା **ନୂତନ** ଟ୍ରାଫିକ୍ ବନ୍ଦ ହେଉଥିବା ପ୍ରକ୍ରିୟାକୁ ପହଞ୍ଚିବା ବନ୍ଦ କରେ। ଚାଲୁଥିବା `/v1/responses` SSEକୁ ହେଭିୱେଟ୍ ଆଡ୍ମିସନ୍ ଲିଜ୍ ମାଧ୍ୟମରେ `SHUTDOWN_TIMEOUT_MS` (ଡିଫଲ୍ଟ 30s) ପର୍ଯ୍ୟନ୍ତ ଡ୍ରେନ୍ କରାଯାଏ (#11015)। ତଥାପି ପ୍ରକ୍ରିୟା ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚୁଥିବା ନୂତନ ଅନୁରୋଧଗୁଡ଼ିକ `503` + `Retry-After: 5` ପାଆନ୍ତି। ପ୍ରତିସ୍ଥାପନଟି Ready ହେବା ପର୍ଯ୍ୟନ୍ତ Recreateର ଖାଲି-ଏଣ୍ଡପଏଣ୍ଟ ବ୍ୟବଧାନ ଏକ ସମ୍ପୂର୍ଣ୍ଣ ସେବା ବିଚ୍ଛିନ୍ନତା ଭାବେ ରହିଥାଏ — ଏହା SQLite ଟୋପୋଲୋଜି, ପ୍ରୋବ୍ର ଭୁଲ୍ ବିନ୍ୟାସ ନୁହେଁ।

ବାହ୍ୟ Postgres / ମଲ୍ଟି-ରାଇଟର୍ HA ଏକ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ମାନକ ପଥ **ନୁହେଁ**। ଯଦି ଆପଣଙ୍କୁ HA ଆବଶ୍ୟକ, ତେବେ ଏକକ ରେପ୍ଲିକା ରଖନ୍ତୁ କିମ୍ବା ପ୍ରକଳ୍ପ ଦ୍ୱାରା ପରୀକ୍ଷିତ ଏବଂ ପୃଥକ ଭାବେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ଟୋପୋଲୋଜି ଚଲାନ୍ତୁ। Postgres/MySQL କାର୍ଯ୍ୟ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)ରେ ରହିଛି। ଏହା ରିଲିଜ୍ ହେବା ପର୍ଯ୍ୟନ୍ତ, **ବୃହତ୍** `/v1/responses` କ୍ଷମତାକୁ ଗୁଣିତ କରିବାର ଏକମାତ୍ର ସମର୍ଥିତ ଉପାୟ ହେଉଛି Nଟି ସ୍ୱାଧୀନ ପ୍ରକ୍ରିୟା (ପରବର୍ତ୍ତୀ ବିଭାଗ), ଗୋଟିଏ ଭଲ୍ୟୁମ୍ରେ `replicas > 1` ନୁହେଁ।

## ସ୍କେଲ୍-ଆଉଟ୍: N ସ୍ୱାଧୀନ ପ୍ରକ୍ରିୟା

ଗୋଟିଏ Node ପ୍ରକ୍ରିୟା ହେଉଛି **ଗୋଟିଏ V8 heap**। ପରସ୍ପର ଓଭରଲାପ୍ କରୁଥିବା ଦୁଇଟି ~3 MiB / ~750k-token coding-agent `POST /v1/responses` (RTK + Caveman), ~12 Gi ରେ ସେହି heapକୁ ବନ୍ଦ କରିଦିଏ (`FATAL ERROR: Reached heap limit`) ଏବଂ ଗୋଟିଏ 16 Gi cgroupକୁ OOM କରିପାରେ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ଦେଖନ୍ତୁ। ସେହି ମାପ ଏକ **ମେମୋରି-ବଜେଟ୍** ସତର୍କତା, ଦୁଇଟି ସମକାଳୀନ ଦୀର୍ଘ `/v1/responses` ପାଇଁ ପ୍ରଡକ୍ଟର କଠୋର ସର୍ବାଧିକ ସୀମା ନୁହେଁ। Heavyweight chat admissionକୁ ସ୍ୱୟଂଚାଳିତ ଭାବେ ନିର୍ଦ୍ଧାରିତ ingest byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ଦ୍ୱାରା ନିୟନ୍ତ୍ରଣ କରାଯାଏ, ଯାହାକୁ ସେହି V8/cgroup ସୀମା ଅନୁସାରେ ଆକାର ଦିଆଯାଇଛି — ପୂର୍ବରୁ ଆକାର ନିର୍ଦ୍ଧାରିତ ପ୍ରକ୍ରିୟାରେ ଏହାକୁ ବଢ଼ାଇ override କଲେ (କିମ୍ବା ପୁରୁଣା `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` request-count cap ସେଟ୍ କଲେ) ପୁଣି ସେହି abort ସମସ୍ୟା ଦେଖାଦେବ। ଛୋଟ chat, `/healthz`, `/v1/models`, ଏବଂ MCP ସେହି capରେ **ଅନ୍ତର୍ଭୁକ୍ତ ନୁହେଁ**।

### ଗୋଟିଏ ପ୍ରକ୍ରିୟା: ଦୁଇଟିରୁ ଅଧିକ ଦୀର୍ଘ `/v1/responses`

ଏକ **ସୁସ୍ଥ** ପ୍ରକ୍ରିୟା (heap, `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO`ଠାରୁ କମ୍; ଡିଫଲ୍ଟ `0.75`)ରେ, ପ୍ରକ୍ରିୟା-ବ୍ୟାପୀ inflight-byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110)ରେ ଆହୁରି ସ୍ଥାନ ଥିଲେ, ଦୁଇଟିରୁ ଅଧିକ ସମକାଳୀନ ଦୀର୍ଘ `POST /v1/responses` ଚାଲି **ପାରେ**। `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (ଡିଫଲ୍ଟ 256 KiB) ସମାନ କିମ୍ବା ତା’ଠାରୁ ବଡ଼ body, structure-heavy request ପରି ସମାନ heavyweight lease ନିଏ ଏବଂ ସମାନ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` escape (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ବ୍ୟବହାର କରେ। ଦଶଦଶ ସମକାଳୀନ ଦୀର୍ଘ SSE client (operatorମାନଙ୍କୁ ପ୍ରାୟତଃ 40–50ଟି ଆବଶ୍ୟକ ହୁଏ) ଏକ **ମେମୋରି-ବଜେଟ୍** ପ୍ରଶ୍ନ — heap + primary/headroom slot + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`ର ଆକାର ନିର୍ଦ୍ଧାରଣ କରନ୍ତୁ — ଏହା ପ୍ରଡକ୍ଟର କଠୋର “ସର୍ବାଧିକ 2” ସୀମା ନୁହେଁ। ଚାପଗ୍ରସ୍ତ heap ତଥାପି ପୁନଃଚେଷ୍ଟାଯୋଗ୍ୟ `503` ସହିତ load କମାଏ, ଯାହାଦ୍ୱାରା #7849 ପୁଣି ଫେରି ନ ଆସେ।

**ଏକାଧିକ heap** (ସ୍ୱାଧୀନ V8 old-space) ପାଇବାକୁ **ବର୍ତ୍ତମାନ**:

| କରନ୍ତୁ                                                                                                                                                             | କରନ୍ତୁ ନାହିଁ                                                            |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **N containers/pods** ଚଲାନ୍ତୁ, ପ୍ରତ୍ୟେକର ନିଜସ୍ୱ `DATA_DIR` / volume ସହିତ                                                                                           | ଗୋଟିଏ SQLite file ପାଇଁ `replicas > 1` ସେଟ୍ କରନ୍ତୁ ନାହିଁ                 |
| heap / inflight-byte budget ଅନୁସାରେ heavy in-flight + healthy-headroomର ଆକାର ନିର୍ଦ୍ଧାରଣ କରନ୍ତୁ; 1–2 ହେଉଛି ରକ୍ଷଣଶୀଳ #7849 ଡିଫଲ୍ଟ, ପ୍ରଡକ୍ଟର କଠୋର ସର୍ବାଧିକ ସୀମା ନୁହେଁ | ଗୋଟିଏ ପ୍ରକ୍ରିୟାକୁ 8× RAM ଏବଂ ଅସୀମିତ count cap ଦିଅନ୍ତୁ ନାହିଁ             |
| ବୈକଳ୍ପିକ: **shared quota counter** ପାଇଁ `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                       | Redisକୁ shared SQLite ଭାବେ ଗ୍ରହଣ କରନ୍ତୁ ନାହିଁ — ଏହା ସେପରି ନୁହେଁ         |
| ପ୍ରତ୍ୟେକ instanceରେ provider secretଗୁଡ଼ିକୁ ନକଲ କରନ୍ତୁ (କିମ୍ବା ବିଭାଜିତ dashboard ଗ୍ରହଣ କରନ୍ତୁ)                                                                      | instanceଗୁଡ଼ିକ ମଧ୍ୟରେ ଗୋଟିଏ dashboard / ଗୋଟିଏ call-log ଆଶା କରନ୍ତୁ ନାହିଁ |
| ସାମ୍ନାରେ ଯେକୌଣସି load balancer ରଖନ୍ତୁ; API key କିମ୍ବା session ଅନୁସାରେ sticky routing ଯଥେଷ୍ଟ                                                                        | vendor-specific size-aware middleware ଆବଶ୍ୟକ ବୋଲି ଧରନ୍ତୁ ନାହିଁ          |

ହାର୍ଡୱେର୍: ପ୍ରତ୍ୟେକ instanceରେ ସମକାଳୀନ ଦୀର୍ଘ `/v1/responses` ସଂଖ୍ୟା ଏକ **ମେମୋରି-ବଜେଟ୍** ପ୍ରଶ୍ନ (heap + inflight-byte / #10110)। `N`ଟି ସ୍ୱାଧୀନ `DATA_DIR` ତଥାପି heap ସଂଖ୍ୟାକୁ ଗୁଣିତ କରେ: host RAMକୁ `N × cgroup` ପାଇଁ ଯଥେଷ୍ଟ ହେବା ଆବଶ୍ୟକ, “N=8 ସହିତ ଗୋଟିଏ 16 Gi pod” ପାଇଁ ନୁହେଁ। ଗୋଟିଏ SQLite fileରେ କେବେବି `replicas > 1` ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ।

Compose ରୂପରେଖା (ଦୁଇଟି heap, ଦୁଇଟି volume — `deploy.replicas: 2` ନୁହେଁ):

    image: diegosouzapw/omniroute:3.8.49

In-process density (HTTP isolateରୁ compressionକୁ ବାହାରେ ରଖିବା) ହେଉଛି [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023)। shared durable state ଉପରେ ଗୋଟିଏ logical cluster ହେଉଛି [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)।

## ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ଟିପ୍ପଣୀ

- **SQLite WAL ମୋଡ୍:** `docker stop`କୁ ସମ୍ପୂର୍ଣ୍ଣ ହେବାକୁ ଅନୁମତି ଦେବା ଉଚିତ, ଯାହାଦ୍ୱାରା OmniRoute ସଦ୍ୟତମ ପରିବର୍ତ୍ତନଗୁଡ଼ିକୁ `storage.sqlite`ରେ ପୁନଃ ଚେକ୍ପଏଣ୍ଟ କରିପାରିବ। ସହିତ ଥିବା Compose ଫାଇଲ୍ଗୁଡ଼ିକରେ ପୂର୍ବରୁ 40sର ଷ୍ଟପ୍ ଗ୍ରେସ୍ ପିରିୟଡ୍ ସେଟ୍ କରାଯାଇଛି। ଯଦି ଆପଣ ଇମେଜ୍ଟିକୁ ସିଧାସଳଖ ଚଲାନ୍ତି, ତେବେ `--stop-timeout 40` ରଖନ୍ତୁ।
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ଯଦି ନିୟମିତ/ଲେଖନ-ପୂର୍ବ ବ୍ୟାକଅପ୍ଗୁଡ଼ିକ ବାହ୍ୟ ଭାବରେ ପରିଚାଳିତ ହୁଏ, ତେବେ ଏହାକୁ `true`ରେ ସେଟ୍ କରନ୍ତୁ। ବିଦ୍ୟମାନ ଡାଟାବେସ୍ ମାଇଗ୍ରେସନ୍ଗୁଡ଼ିକ ପାଇଁ ତଥାପି ନିଜସ୍ୱ ସ୍ଥାୟୀ ସୁରକ୍ଷା ସ୍ନାପ୍ଶଟ୍ ଏବଂ ବ୍ୟାପକ ମାଇଗ୍ରେସନ୍ ସୁରକ୍ଷା ବ୍ୟବସ୍ଥା ଆବଶ୍ୟକ।
- **ଡାଟା ସ୍ଥାୟୀତ୍ୱ:** କଣ୍ଟେନର୍ ପୁନଃଚାଳନଗୁଡ଼ିକ ମଧ୍ୟରେ ଆପଣଙ୍କ ଡାଟାବେସ୍, କୀ ଏବଂ ବିନ୍ୟାସଗୁଡ଼ିକୁ ସ୍ଥାୟୀ ରଖିବା ପାଇଁ ସର୍ବଦା `/app/data`ରେ ଏକ ଭଲ୍ୟୁମ୍ ମାଉଣ୍ଟ୍ କରନ୍ତୁ।
- **ପୋର୍ଟ ବିନ୍ୟାସ:** ଡିଫଲ୍ଟ `20128` ପୋର୍ଟ ପରିବର୍ତ୍ତନ କରିବା ପାଇଁ `PORT` ପରିବେଶ ଭେରିଏବଲ୍କୁ ଓଭରରାଇଡ୍ କରନ୍ତୁ।
