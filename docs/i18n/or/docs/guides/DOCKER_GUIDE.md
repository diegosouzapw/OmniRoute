## ଶୀଘ୍ର ଚଲାନ୍ତୁ

> **ଗୋଟିଏ କମାଣ୍ଡରେ ସ୍ୱୟଂ-ହୋଷ୍ଟ କରିବେ?**
> [ସ୍ୱୟଂ-ହୋଷ୍ଟ ଗାଇଡ୍](../getting-started/SELF_HOST_GUIDE.md) ଦେଖନ୍ତୁ —
> `docker compose -f docker-compose.selfhost.yml up -d` (ପ୍ରକାଶିତ ଇମେଜ୍ +
> Redis, କେବଳ loopback, କୌଣସି ପ୍ରୋଫାଇଲ୍ ଚୟନ ନାହିଁ)। ନିମ୍ନରେ ଥିବା ଶୀଘ୍ର ଚଲାଇବା ପଦ୍ଧତିଟି
> ଅନ୍ୟତ୍ର ପୂର୍ବରୁ Redis ଚଲାଉଥିବା ବ୍ୟବହାରକାରୀଙ୍କ ପାଇଁ ଏକକ-କଣ୍ଟେନର୍ ପଥ ଅଟେ।

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## ପରିବେଶ ଫାଇଲ୍ ସହିତ

```bash
# ପ୍ରଥମେ .env କପି ଏବଂ ସମ୍ପାଦନା କରନ୍ତୁ
```

## Docker Compose

```bash
# ମୂଳ ପ୍ରୋଫାଇଲ୍ (କୌଣସି CLI ଟୁଲ୍ ନାହିଁ)
docker compose --profile base up -d

# CLI ପ୍ରୋଫାଇଲ୍ (Claude Code, Codex, OpenClaw ବିଲ୍ଟ-ଇନ୍)
docker compose --profile cli up -d

# ହୋଷ୍ଟ ପ୍ରୋଫାଇଲ୍ (Linux-ପ୍ରଥମ; ହୋଷ୍ଟ CLI ବାଇନାରିଗୁଡ଼ିକୁ କେବଳ-ପଠନୀୟ ଭାବେ ମାଉଣ୍ଟ କରେ)
docker compose --profile host up -d

# ୱେବ୍ ପ୍ରୋଫାଇଲ୍ (ୱେବ୍-ସେସନ୍ ପ୍ରଦାତାଙ୍କ ପାଇଁ Chromium/Playwright)
docker compose --profile web up -d

# CLI + CLIProxyAPI ସାଇଡ୍କାର୍ ମିଶ୍ରଣ କରନ୍ତୁ
docker compose --profile cli --profile cliproxyapi up -d
```

## ଉପଲବ୍ଧ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ

ମୁଖ୍ୟ ଡିପ୍ଲୟମେଣ୍ଟ ଆକୃତିଗୁଡ଼ିକ ପାଇଁ OmniRoute ସହିତ Compose ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ ମିଳେ। ଆପଣଙ୍କ ପରିବେଶ ସହିତ ମେଳ ଖାଉଥିବା ପ୍ରୋଫାଇଲ୍ଟି ବାଛନ୍ତୁ।

| ପ୍ରୋଫାଇଲ୍       | ସେବା             | କେତେବେଳେ ବ୍ୟବହାର କରିବେ                                                                                                                                     | କମାଣ୍ଡ                                       |
| --------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `base` (ଡିଫଲ୍ଟ) | `omniroute-base` | ହେଡ୍ଲେସ୍ ସର୍ଭର୍ / ସର୍ବନିମ୍ନ ରନ୍ଟାଇମ୍, କୌଣସି ପ୍ରଦାତା CLI ବଣ୍ଡଲ୍ କରାଯାଇନାହିଁ                                                                                 | `docker compose --profile base up -d`        |
| `cli`           | `omniroute-cli`  | `omniroute providers/setup/doctor` ଏବଂ ବଣ୍ଡଲ୍ କରାଯାଇଥିବା CLIଗୁଡ଼ିକୁ (Codex, Claude Code, Droid, OpenClaw) କଲ୍ କରୁଥିବା ଏଜେଣ୍ଟିକ୍ ୱାର୍କଫ୍ଲୋ                  | `docker compose --profile cli up -d`         |
| `host`          | `omniroute-host` | `~/.local/bin`, `~/.codex`, `~/.claude` ଇତ୍ୟାଦିକୁ କେବଳ-ପଠନୀୟ ଭାବେ ମାଉଣ୍ଟ କରି, ହୋଷ୍ଟ CLIଗୁଡ଼ିକ ପାଇଁ `network_mode`-ସଦୃଶ ଆକ୍ସେସ୍ ଚାହୁଁଥିବା Linux ହୋଷ୍ଟଗୁଡ଼ିକ | `docker compose --profile host up -d`        |
| `cliproxyapi`   | `cliproxyapi`    | ଅପ୍ଷ୍ଟ୍ରିମ୍ CLI ପ୍ରକ୍ସିଂ ପାଇଁ ପୋର୍ଟ୍ `8317`ରେ [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) ସାଇଡ୍କାର୍ ଚଲାନ୍ତୁ                                | `docker compose --profile cliproxyapi up -d` |
| `web`           | `omniroute-web`  | ବ୍ରାଉଜର୍ ଆବଶ୍ୟକ କରୁଥିବା ୱେବ୍-ସେସନ୍ ପ୍ରଦାତା: `gemini-web`, `claude-web`, `claude-turnstile` (`runner-web` ବିଲ୍ଡ କରେ, Chromium ଅନ୍ତର୍ଭୁକ୍ତ)                  | `docker compose --profile web up -d`         |

> ଏକାଧିକ ପ୍ରୋଫାଇଲ୍କୁ ମିଶ୍ରଣ କରାଯାଇପାରିବ: `docker compose --profile cli --profile cliproxyapi up -d`।

## OmniRoute Dockerରେ ଚାଲୁଥିବାବେଳେ ହୋଷ୍ଟ CLI ଟୁଲ୍ଗୁଡ଼ିକୁ ବିନ୍ୟାସ କରିବା

`omniroute setup-codex`, `setup-claude`, `config set <tool>` ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡର
**ବିନ୍ୟାସ ସଞ୍ଚୟ କରନ୍ତୁ** ବଟନ୍—ସମସ୍ତେ `~/.codex/*.config.toml` ଭଳି ଫାଇଲ୍ ଲେଖନ୍ତି। ସେହି ପଥଗୁଡ଼ିକ
କେବଳ CLI ପ୍ରକୃତରେ ଯେଉଁ ମେସିନ୍ରେ ଚାଲୁଛି, ସେହି ମେସିନ୍ରେ ହିଁ ଅର୍ଥପୂର୍ଣ୍ଣ। ସେଗୁଡ଼ିକୁ
କଣ୍ଟେନର୍ ଭିତରେ ଚଲାଇଲେ, ଲେଖାଟି କଣ୍ଟେନର୍ର ନିଜସ୍ୱ ହୋମ୍ରେ (`/home/node` —
ଇମେଜ୍ଟି `USER node` ଭାବେ ଚାଲେ) ସଞ୍ଚିତ ହୁଏ, ଯେଉଁଠାରୁ କୌଣସି ହୋଷ୍ଟ CLI କେବେ ମଧ୍ୟ ଏହାକୁ ପଢ଼ିବ ନାହିଁ ଏବଂ
କଣ୍ଟେନର୍ଟି ପୁନଃସୃଷ୍ଟି ହେବାମାତ୍ରେ ଏହା ବିଲୋପ ହୋଇଯାଏ।

OmniRoute ଏହାକୁ ଚିହ୍ନଟ କରେ ଏବଂ ଆପଣ ବ୍ୟବହାର କରିପାରିବେ ନାହିଁ ଏପରି ସଫଳତା ସୂଚନା ଦେବା ପରିବର୍ତ୍ତେ
ନିର୍ଦ୍ଦେଶାବଳୀ ସହିତ ଲେଖାକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ: CLI `2` ସହିତ ବନ୍ଦ ହୁଏ ଏବଂ API
`containerEphemeralTarget: true` ସହିତ `422` ଉତ୍ତର ଦିଏ।

### ସୁପାରିସକୃତ: CLIକୁ ହୋଷ୍ଟରେ ଏବଂ OmniRouteକୁ Dockerରେ ଚଲାନ୍ତୁ

କଣ୍ଟେନର୍ଟି API ପରିବେଷଣ କରେ; CLI ଆପଣଙ୍କ ହୋଷ୍ଟ ଟୁଲ୍ଗୁଡ଼ିକୁ ବିନ୍ୟାସ କରେ।

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # CLIକୁ କଣ୍ଟେନର୍ ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ
omniroute setup-codex                      # ଆପଣଙ୍କ ହୋଷ୍ଟର ପ୍ରକୃତ ~/.codexରେ ଲେଖେ
```

Codex, Claude Code, Cursor କିମ୍ବା ସମାନ ଟୁଲ୍ଗୁଡ଼ିକ ଆପଣଙ୍କ
ଲ୍ୟାପ୍ଟପ୍ରେ ଚାଲୁଥିବାବେଳେ—ଯାହା ସାଧାରଣ ବ୍ୟବସ୍ଥା—ଏହା ହେଉଛି ଠିକ୍ ପସନ୍ଦ।

### ବିକଳ୍ପ: ହୋଷ୍ଟ ବିନ୍ୟାସ ଡିରେକ୍ଟୋରୀଗୁଡ଼ିକୁ bind-mount କରନ୍ତୁ (`host` ପ୍ରୋଫାଇଲ୍)

ଯଦି ଆପଣ କଣ୍ଟେନର୍କୁ ନିଜେ ଆପଣଙ୍କ ହୋଷ୍ଟ ବିନ୍ୟାସ ଲେଖାଇବାକୁ ଚାହାନ୍ତି, ତେବେ
ଡିରେକ୍ଟୋରୀଗୁଡ଼ିକୁ ମାଉଣ୍ଟ କରନ୍ତୁ ଏବଂ `CLI_CONFIG_HOME`କୁ ମାଉଣ୍ଟ ରୁଟ୍ ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରନ୍ତୁ। `host` ପ୍ରୋଫାଇଲ୍
ପୂର୍ବରୁ ଏହା କରିଥାଏ:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

ଏକ bind mount ହିଁ ପଥଟିକୁ ବିଶ୍ୱସନୀୟ କରେ: OmniRoute
`/proc/self/mountinfo` ପଢ଼େ ଏବଂ ମାଉଣ୍ଟ ହୋଇଥିବା ପଥଗୁଡ଼ିକରେ (ଏବଂ ଯେଉଁ ଡିରେକ୍ଟୋରୀଗୁଡ଼ିକର
ଚାଇଲ୍ଡ ମାଉଣ୍ଟ ହୋଇଛି, ଯାହା ଉପରୋକ୍ତ `/host-home` ଗଠନ ସହିତ ଠିକ୍ ମେଳ ଖାଏ) ଲେଖାକୁ ଅନୁମତି ଦେଇଥାଏ, ଏହା ସହିତ
ମାଉଣ୍ଟ ହୋଇନଥିବା ପଥଗୁଡ଼ିକୁ ଏବେ ମଧ୍ୟ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

### ଶେଷ ବିକଳ୍ପ: କଣ୍ଟେନର୍ର ନିଜସ୍ୱ CLIଗୁଡ଼ିକୁ ବିନ୍ୟାସ କରନ୍ତୁ (ସଂଯମରେ ବ୍ୟବହାର କରନ୍ତୁ)

ଯେତେବେଳେ CLIଗୁଡ଼ିକ ପ୍ରକୃତରେ କଣ୍ଟେନର୍ ଭିତରେ ରହେ (`cli` ପ୍ରୋଫାଇଲ୍), ଲେଖାଟି
ଉଦ୍ଦେଶ୍ୟମୂଳକ ହୋଇଥାଏ। ଯେକୌଣସି `setup-*` କମାଣ୍ଡକୁ `--allow-container-write` ପାସ୍ କରନ୍ତୁ, କିମ୍ବା ସର୍ଭର୍ ପାଇଁ
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` ସେଟ୍ କରନ୍ତୁ। ଲେଖାଟି
କଣ୍ଟେନର୍ର ପୁନଃସୃଷ୍ଟି ପରେ ରହିବ ନାହିଁ ବୋଲି ଏକ ଚେତାବନୀ ସହିତ ଆଗକୁ ବଢ଼େ।

> **ସୁରକ୍ଷା ଚେତାବନୀ — `cli` ପ୍ରୋଫାଇଲ୍ + `docker.sock` ମାଉଣ୍ଟ।**
> କଣ୍ଟେନର୍ ଭିତରର ସ୍ୱୟଂଚାଳିତ ଅପଡେଟର୍ ହୋଷ୍ଟ daemonରୁ stackକୁ ପୁନଃସୃଷ୍ଟି କରିପାରିବା ପାଇଁ
> `cli` ପ୍ରୋଫାଇଲ୍ `/var/run/docker.sock`କୁ bind-mount କରେ
> (`src/lib/system/autoUpdate.ts` ସେହି socket ପାଇଁ ଯାଞ୍ଚ କରେ ଏବଂ ତାହା ଅନୁପସ୍ଥିତ ଥିଲେ
> Docker ପଥକୁ ଏଡ଼ାଇଯାଏ)। ସେହି socketଟି **ହୋଷ୍ଟ-root ବିଶ୍ୱାସ
> ସୀମା**: ଏହାକୁ ପହଞ୍ଚିପାରୁଥିବା ଯେକୌଣସି ଜିନିଷ ହୋଷ୍ଟ Docker daemonକୁ
> root ଭାବେ ପରିଚାଳନା କରେ—ଏହା ହୋଷ୍ଟର ଯେକୌଣସି କଣ୍ଟେନର୍ ସୃଷ୍ଟି, ନିରୀକ୍ଷଣ, ବନ୍ଦ ଏବଂ ଅପସାରଣ କରିପାରେ।
> ଏହାର ପ୍ରଭାବ:
>
> 1. **`cli` ପ୍ରୋଫାଇଲ୍ର ପୋର୍ଟକୁ କେବେ ମଧ୍ୟ ନେଟୱର୍କରେ ପ୍ରକାଶ କରନ୍ତୁ ନାହିଁ।** ଏହାକୁ
>    `127.0.0.1`ରେ ପ୍ରକାଶ କରନ୍ତୁ (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — LANରୁ ପହଞ୍ଚଯୋଗ୍ୟ `cli` ପ୍ରୋଫାଇଲ୍ ଯେକୌଣସି ଡ୍ୟାସ୍ବୋର୍ଡ-ସ୍ତରୀୟ RCEକୁ
>    ସମ୍ପୂର୍ଣ୍ଣ ହୋଷ୍ଟ ଅଧିକାର ହରଣରେ ପରିଣତ କରେ।
> 2. **`cli` ପ୍ରୋଫାଇଲ୍ରେ କୌଣସି ଅତିରିକ୍ତ ହୋଷ୍ଟ ଡିରେକ୍ଟୋରୀ bind କରନ୍ତୁ ନାହିଁ।**
>    Docker socket ସହିତ ଆଉ କୌଣସି mount ଯୋଡ଼ିଲେ, କଣ୍ଟେନର୍ଟି ଆପଣଙ୍କ filesystem ଏବଂ ହୋଷ୍ଟ ବିନ୍ୟାସ ଉପରେ
>    ସମ୍ପୂର୍ଣ୍ଣ ପଢ଼ିବା/ଲେଖିବା ଅଧିକାର ପାଏ। ଯଦି କୌଣସି ଟୁଲ୍କୁ ଏକ project ଦେଖିବା ଆବଶ୍ୟକ,
>    ତେବେ CLI binary ସହିତ ଏହାକୁ ସ୍ଥାନୀୟ ଭାବେ ଚଲାନ୍ତୁ—ଏହାକୁ `cli` କଣ୍ଟେନର୍ରେ mount କରନ୍ତୁ ନାହିଁ।
>
> ଯଦି ଆପଣଙ୍କୁ କଣ୍ଟେନର୍ ଭିତରର ସ୍ୱୟଂଚାଳିତ ଅପଡେଟ୍ ଆବଶ୍ୟକ ନାହିଁ, ତେବେ `cli` ପ୍ରୋଫାଇଲ୍କୁ ବନ୍ଦ ରଖନ୍ତୁ
> (`COMPOSE_PROFILES=core,redis` କିମ୍ବା ତାହାଠାରୁ ଛୋଟ)। ଅନ୍ୟ ପ୍ରୋଫାଇଲ୍ଗୁଡ଼ିକ
> Docker socketକୁ mount କରନ୍ତି ନାହିଁ।
>
> MITM ସମ୍ବନ୍ଧୀୟ ବିପଦ ମଡେଲ୍ ପାଇଁ `docs/security/MITM-TPROXY-DECRYPT.md` (git; `/docs`ରେ କମ୍ପାଇଲ୍ କରାଯାଇନାହିଁ) ଦେଖନ୍ତୁ,
> ଏବଂ `codex`/`claude-code`/`droid`/`openclaw` binaryର ଉତ୍ପତ୍ତି ଶୃଙ୍ଖଳ ପାଇଁ
> `docs/security/SUPPLY_CHAIN.md` ଦେଖନ୍ତୁ।

## Redis ସାଇଡ୍କାର୍

ବିତରିତ ରେଟ୍ ଲିମିଟର୍ ଏବଂ ସହଭାଗୀ କ୍ୟାଶ୍କୁ ସମର୍ଥନ କରିବା ପାଇଁ OmniRoute, Redis ଉପରେ ନିର୍ଭର କରେ। `redis` ସେବାଟି `docker-compose.yml` ମଧ୍ୟରେ **ସର୍ବଦା ବ୍ୟାଖ୍ୟାୟିତ** ଥାଏ (ଏଥିରେ କୌଣସି ପ୍ରୋଫାଇଲ୍ ଗେଟ୍ ନାହିଁ) ଏବଂ ଅନ୍ୟ ଯେକୌଣସି ପ୍ରୋଫାଇଲ୍ ସହିତ ଆରମ୍ଭ ହୁଏ।

| ବିବରଣୀ                    | ମୂଲ୍ୟ                                       |
| ------------------------- | ------------------------------------------- |
| ଇମେଜ୍                     | `redis:7-alpine`                            |
| କଣ୍ଟେନର୍ ନାମ              | `omniroute-redis`                           |
| ଆଭ୍ୟନ୍ତରୀଣ ପୋର୍ଟ          | `6379`                                      |
| ହୋଷ୍ଟ ପୋର୍ଟ (ଓଭର୍ରାଇଡ୍)   | `REDIS_PORT` (ଡିଫଲ୍ଟ ଭାବେ `6379`)           |
| ହୋଷ୍ଟ ବାଇଣ୍ଡ୍ (ଓଭର୍ରାଇଡ୍) | `REDIS_BIND_HOST` (ଡିଫଲ୍ଟ ଭାବେ `127.0.0.1`) |
| ଭଲ୍ୟୁମ୍                   | `omniroute-redis-data` → `/data`            |
| ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ           | `redis-cli ping` (10s ବ୍ୟବଧାନ)              |

ସମ୍ପର୍କିତ ପରିବେଶ ଭେରିଏବଲ୍ଗୁଡ଼ିକ:

- `REDIS_URL` — ଆପ୍ରେ ଇଞ୍ଜେକ୍ଟ କରାଯାଉଥିବା ସଂଯୋଗ ଷ୍ଟ୍ରିଙ୍ଗ୍ (ଡିଫଲ୍ଟ ଭାବେ `redis://redis:6379`)।
- `REDIS_PORT` — Redis କଣ୍ଟେନର୍ ପାଇଁ ହୋଷ୍ଟ-ପାର୍ଶ୍ୱ ପୋର୍ଟ ମ୍ୟାପିଂ।
- `REDIS_BIND_HOST` — ପୋର୍ଟ ପ୍ରକାଶିତ ହେଉଥିବା ହୋଷ୍ଟ ଇଣ୍ଟରଫେସ୍। ଡିଫଲ୍ଟ ଭାବେ `127.0.0.1`।

> **ଡିଫଲ୍ଟ ଭାବେ ଲୁପ୍ବ୍ୟାକ୍ କାହିଁକି:** ସାଇଡ୍କାର୍ଟି `requirepass` ବିନା ଚାଲେ, ଏବଂ ଆପ୍
> କଣ୍ଟେନର୍ଗୁଡ଼ିକ compose ନେଟ୍ୱର୍କ (`redis:6379`) ମାଧ୍ୟମରେ ଏଥିରେ ପହଞ୍ଚନ୍ତି — ପ୍ରକାଶିତ ପୋର୍ଟଟି
> କେବଳ ହୋଷ୍ଟ-ପାର୍ଶ୍ୱ ଟୁଲିଂ (`redis-cli`, ଏକ ସ୍ଥାନୀୟ `npm run dev`) ପାଇଁ ରହିଛି। `0.0.0.0`ରେ
> ପ୍ରକାଶ କଲେ ଆପଣଙ୍କ LANର ପ୍ରତ୍ୟେକ ହୋଷ୍ଟ ପାଇଁ ଏକ ଅପ୍ରମାଣୀକୃତ Redis ଉନ୍ମୁକ୍ତ ହୋଇଯିବ। ଯଦି ଆପଣ
> `REDIS_BIND_HOST=0.0.0.0` ସେଟ୍ କରନ୍ତି, ତେବେ ସେବାର `command:`ରେ `--requirepass` ମଧ୍ୟ ଯୋଡ଼ନ୍ତୁ।

**Redis ଅକ୍ଷମ କରିବା** ସୁପାରିସ କରାଯାଏ ନାହିଁ (ରେଟ୍ ଲିମିଟର୍ ଇନ୍-ମେମୋରି ଫଲ୍ବ୍ୟାକ୍କୁ ଅବନମିତ ହେବ)। ଯଦି ଏହା କରିବା ଆବଶ୍ୟକ, ତେବେ `docker-compose.yml`ରୁ `redis:` ସେବା ବ୍ଲକ୍କୁ ଅପସାରଣ/କମେଣ୍ଟ କରନ୍ତୁ କିମ୍ବା ଏହାକୁ ଶୂନ୍ୟକୁ ସ୍କେଲ୍ କରନ୍ତୁ:

```bash
docker compose up -d --scale redis=0
```

## ପ୍ରଡକ୍ସନ୍ Compose

ଡେଭ୍ ସହିତ ଚାଲୁଥିବା ଏକ ପୃଥକ ପ୍ରଡକ୍ସନ୍ ସ୍ନାପ୍ଶଟ୍ ପାଇଁ `docker-compose.prod.yml` ବ୍ୟବହାର କରନ୍ତୁ।

| ବିବରଣୀ                   | ମୂଲ୍ୟ                                                                                              |
| ------------------------ | -------------------------------------------------------------------------------------------------- |
| ଫାଇଲ୍                    | `docker-compose.prod.yml`                                                                          |
| ଡିଫଲ୍ଟ ଡ୍ୟାସ୍ବୋର୍ଡ ପୋର୍ଟ | `PROD_DASHBOARD_PORT=20130` (ଆଭ୍ୟନ୍ତରୀଣ `${DASHBOARD_PORT:-20128}`କୁ ମ୍ୟାପ୍ କରାଯାଇଛି)              |
| ଡିଫଲ୍ଟ API ପୋର୍ଟ         | `PROD_API_PORT=20131`                                                                              |
| ଇମେଜ୍                    | `omniroute:prod` (`runner-cli` ଟାର୍ଗେଟ୍ରୁ ବିଲ୍ଡ୍ କରାଯାଇଛି)                                         |
| Redis କଣ୍ଟେନର୍           | `omniroute-redis-prod` (`redis:8.6.2`, ଉତ୍ସର୍ଗୀକୃତ `redis-prod-data` ଭଲ୍ୟୁମ୍)                      |
| ଡାଟା ଭଲ୍ୟୁମ୍             | `omniroute-prod-data` (ନାମିତ, ପୁନଃବିଲ୍ଡ୍ଗୁଡ଼ିକ ମଧ୍ୟରେ ସ୍ଥାୟୀ ରହେ)                                  |
| ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚଗୁଡ଼ିକ    | `node healthcheck.mjs` + `redis-cli ping`, Redisର ସ୍ୱାସ୍ଥ୍ୟ ଉପରେ ଗେଟ୍ କରାଯାଇଥିବା `depends_on` ସହିତ |

ବ୍ୟବହାର ପ୍ରଣାଳୀ:

```bash
# ପ୍ରଡକ୍ସନ୍ ଷ୍ଟାକ୍ ବିଲ୍ଡ୍ କରି ଆରମ୍ଭ କରନ୍ତୁ
docker compose -f docker-compose.prod.yml up -d --build

# ଲଗ୍ଗୁଡ଼ିକୁ ଷ୍ଟ୍ରିମ୍ କରନ୍ତୁ
docker compose -f docker-compose.prod.yml logs -f

# ବନ୍ଦ କରନ୍ତୁ (ଭଲ୍ୟୁମ୍ଗୁଡ଼ିକୁ ରଖନ୍ତୁ)
docker compose -f docker-compose.prod.yml down
```

ପ୍ରଡ୍ ଷ୍ଟାକ୍ଟି ଡେଭ୍ compose ସହିତ ସମାନ୍ତରାଳ ଭାବେ ଚାଲେ (ଭିନ୍ନ କଣ୍ଟେନର୍ ନାମ, ପୋର୍ଟ ଏବଂ ଭଲ୍ୟୁମ୍), ତେଣୁ ପ୍ରଡକ୍ସନ୍ ଚାଲୁ ରହିଥିବାବେଳେ ଆପଣ ସ୍ଥାନୀୟ ଭାବେ ପୁନରାବୃତ୍ତିମୂଳକ ବିକାଶ ଜାରି ରଖିପାରିବେ।

## Dockerfile ଷ୍ଟେଜ୍ଗୁଡ଼ିକ

ରିପୋଜିଟୋରି ସହିତ ଏକ ମଲ୍ଟି-ଷ୍ଟେଜ୍ Dockerfile (`Dockerfile`) ଦିଆଯାଇଛି। ଚାରିଟି ଷ୍ଟେଜ୍ ଉପଲବ୍ଧ; ଆପଣଙ୍କ ବ୍ୟବହାର ଅନୁଯାୟୀ ଉପଯୁକ୍ତ `target` ବାଛନ୍ତୁ।

| ଷ୍ଟେଜ୍        | ବେସ୍ ଇମେଜ୍            | ଉଦ୍ଦେଶ୍ୟ                                                                                                                                                                                                                                                                                                  |
| ------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | ଡିପେଣ୍ଡେନ୍ସିଗୁଡ଼ିକ ଇନଷ୍ଟଲ୍ କରେ (`npm ci --legacy-peer-deps`) ଏବଂ `npm run build` ଚଳାଏ (ଡିଫଲ୍ଟ ଭାବେ Turbopack — ତଳେ ଥିବା ବିଲ୍ଡ-ସମୟ ସମ୍ବଳ ଦେଖନ୍ତୁ)                                                                                                                                                          |
| `runner-base` | `node:26-trixie-slim` | Next.js ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ଆଉଟପୁଟ୍ ସହିତ ପ୍ରଡକ୍ସନ୍ ରନ୍ଟାଇମ୍। **କୌଣସି ପ୍ରଦାନକାରୀ CLI ବଣ୍ଡଲ୍ କରାଯାଇନାହିଁ।**                                                                                                                                                                                                        |
| `runner-cli`  | `runner-base`         | `git`, `docker.io`, `docker-compose` ଏବଂ ଗ୍ଲୋବାଲ୍ CLIଗୁଡ଼ିକ ଯୋଗ କରେ: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`। **ଏଜେଣ୍ଟିକ୍ ୱର୍କଫ୍ଲୋ ପାଇଁ ଏହାକୁ ବାଛନ୍ତୁ।**                                                                                                                        |
| `runner-web`  | `runner-base`         | ୱେବ୍-ସେସନ୍ ପ୍ରଦାନକାରୀଗୁଡ଼ିକ ପାଇଁ Playwright + ଏକ Chromium ବ୍ରାଉଜର୍ (`--with-deps`) ଯୋଗ କରେ: `gemini-web`, `claude-web`, `claude-turnstile`। **ଏହି ପ୍ରଦାନକାରୀଗୁଡ଼ିକୁ ବ୍ୟବହାର କଲେ ଏହାକୁ ବାଛନ୍ତୁ** — ଏହା ବିନା ସାଧାରଣ ଇମେଜ୍ ଅନୁରୋଧ ସମୟରେ ବିଫଳ ହୁଏ (ରିଲିଜ୍ ଚ୍ୟାନେଲ୍ଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା `-web` ଟିପ୍ପଣୀ ଦେଖନ୍ତୁ)। |

ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ଟାର୍ଗେଟ୍ ମାନୁଆଲ୍ ଭାବେ ବିଲ୍ଡ କରନ୍ତୁ:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### ବିଲ୍ଡ-ସମୟ ସମ୍ବଳ

ତିନୋଟି ବିଲ୍ଡ ଆର୍ଗ୍ୟୁମେଣ୍ଟ୍ `builder` ଷ୍ଟେଜ୍ର ସମ୍ବଳ ବ୍ୟବହାର ନିୟନ୍ତ୍ରଣ କରେ। ସେଗୁଡ଼ିକ କେବଳ ବିଲ୍ଡ ସମୟ ପାଇଁ —
`OMNIROUTE_MEMORY_MB` (ତଳେ) ହେଉଛି ଏକ ପୃଥକ ରନ୍ଟାଇମ୍ ନିୟନ୍ତ୍ରଣ।

| ବିଲ୍ଡ ଆର୍ଗ୍ୟୁମେଣ୍ଟ୍         | ଡିଫଲ୍ଟ | ପ୍ରଭାବ                                                                                                 |
| --------------------------- | ------ | ------------------------------------------------------------------------------------------------------ |
| `OMNIROUTE_USE_TURBOPACK`   | `0`    | `0` webpack ସହିତ ବିଲ୍ଡ କରେ: ସର୍ବାଧିକ ମେମୋରି ବ୍ୟବହାର କମ୍, କିନ୍ତୁ ଧୀର। `1` Turbopack ବ୍ୟବହାର ସକ୍ରିୟ କରେ। |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144` | ସୃଷ୍ଟି କରାଯାଇଥିବା `next build` ପାଇଁ V8 ହିପ୍ର ସର୍ବୋଚ୍ଚ ସୀମା (`--max-old-space-size`)।                   |
| `OMNIROUTE_BUILD_WORKERS`   | `2`    | `CIRCLE_NODE_TOTAL`କୁ ମୂଲ୍ୟ ଯୋଗାଏ; ପୃଷ୍ଠା-ଡାଟା ସଂଗ୍ରହ ପାଇଁ Next `workers = N - 1` ନିର୍ଦ୍ଧାରଣ କରେ।      |

ଏକ ବଡ଼ ବିଲ୍ଡର୍ରେ `OMNIROUTE_BUILD_WORKERS` ବଢ଼ାଇବା ଉଚିତ ଏବଂ ସୀମିତ ସମ୍ବଳଯୁକ୍ତ ବିଲ୍ଡ୍ଟି `✓ Compiled successfully` **ପରେ** ବନ୍ଦ ହୋଇଗଲେ ପ୍ରଥମେ ଏହାକୁ ସନ୍ଦେହ କରିବା ଉଚିତ। ପ୍ରତ୍ୟେକ ପୃଷ୍ଠା-ଡାଟା ୱର୍କର୍ ଏକ ସ୍ୱତନ୍ତ୍ର ପ୍ରକ୍ରିୟା, ଏବଂ ମୂଳ `next build` ମଧ୍ୟ ସେହିପରି;
ଏକ ସକ୍ରିୟ VPS ପୁନଃସୃଷ୍ଟି (issue #7518)ରେ `NODE_OPTIONS` ହିପ୍ ଫ୍ଲାଗ୍ଠାରୁ ସ୍ୱାଧୀନ ଭାବେ ପ୍ରତ୍ୟେକ ପ୍ରକ୍ରିୟାର ସର୍ବାଧିକ RSS
~4.5 GB ମାପ କରାଯାଇଥିଲା (Turbopack, V8 ହିପ୍ର ବାହାରେ ନେଟିଭ୍/Rust ମେମୋରିରେ କମ୍ପାଇଲ୍ କରେ)। `2`ର ଡିଫଲ୍ଟ ମୂଲ୍ୟ (→ 1 ୱର୍କର୍, ମୋଟ 2ଟି
ପ୍ରକ୍ରିୟା) ପ୍ରକାଶନ ପାଇପଲାଇନ୍ ବ୍ୟବହାର କରୁଥିବା 16 GB / 4 vCPU GitHub-ହୋଷ୍ଟେଡ୍ ରନର୍ଗୁଡ଼ିକ ପାଇଁ ନିର୍ଦ୍ଧାରିତ। `8`ରେ (→ 7 ୱର୍କର୍) ସେହି ରନର୍ର ମେମୋରି ଶେଷ ହୋଇଗଲା ଏବଂ
buildkit `ResourceExhausted: ... cannot allocate memory` ସହିତ ଷ୍ଟେପ୍ଟିକୁ ବିଫଳ କଲା;
ପ୍ରତି-ପ୍ରକ୍ରିୟା RSSକୁ ଅନୁମାନ କରିବା ପରିବର୍ତ୍ତେ ସିଧାସଳଖ ମାପ କରାଯିବା ପରେ `3` (→ 2 ୱର୍କର୍) ମଧ୍ୟ ଉପଲବ୍ଧ ମେମୋରିରେ ଫିଟ୍ ହେଲାନାହିଁ। `tests/unit/docker-build-memory-budget.test.ts`
ମାପ କରାଯାଇଥିବା ମୂଲ୍ୟ ଆଧାରରେ ଗଣନା କରେ ଏବଂ ଯେକୌଣସି ନିୟନ୍ତ୍ରଣର ମୂଲ୍ୟ ରନର୍ର କ୍ଷମତା ଅତିକ୍ରମ କଲେ ବିଫଳ ହୁଏ।

Turbopack, V8 ହିପ୍ର **ବାହାରେ** ରହୁଥିବା ନେଟିଭ୍ Rust ମେମୋରିରେ କମ୍ପାଇଲ୍ କରେ, ତେଣୁ
`OMNIROUTE_BUILD_MEMORY_MB` ଏହାକୁ ସୀମିତ କରେନାହିଁ। ମେମୋରି ସୀମା ଥିବା ଏକ ହୋଷ୍ଟରେ ବିଲ୍ଡ୍ଟିକୁ
କୌଣସି ତ୍ରୁଟି ସନ୍ଦେଶ ବିନା OOM କିଲର୍ SIGKILL କରେ — ଏହା କେବଳ
`Creating an optimized production build`ର ମଝିରେ ଅଟକିଯାଏ, ଯାହା ମେମୋରି ଶେଷ ହେବା ପରିବର୍ତ୍ତେ ହ୍ୟାଙ୍ଗ୍ ହେବା ଭଳି ଦେଖାଯାଏ।
ଏହି କାରଣରୁ `npm run dev` / `npm run build`ରେ Turbopack କୋଡ୍ ଡିଫଲ୍ଟ ହୋଇଥିଲେ ମଧ୍ୟ, `Dockerfile` webpackକୁ
ଡିଫଲ୍ଟ (`OMNIROUTE_USE_TURBOPACK=0`) ଭାବେ ବ୍ୟବହାର କରେ: କୌଣସି ବିଲ୍ଡ ଆର୍ଗ୍ୟୁମେଣ୍ଟ୍ ବିନା ଏକ ସାଧାରଣ `docker build .` (ଯାହା
Railway ଏବଂ ଅନ୍ୟ ଏକ-କ୍ଲିକ୍ ହୋଷ୍ଟଗୁଡ଼ିକ ଚଳାନ୍ତି) ମେମୋରି-ସୀମିତ ବିଲ୍ଡର୍ରେ ନିରବରେ ବନ୍ଦ ହେବା ଉଚିତ ନୁହେଁ।
ପ୍ରକାଶିତ ଇମେଜ୍ଗୁଡ଼ିକ ପୂର୍ବରୁ `docker-publish.yml`ରେ ସ୍ପଷ୍ଟ ଭାବେ `OMNIROUTE_USE_TURBOPACK=0` ପାସ୍ କରନ୍ତି।
ପର୍ଯ୍ୟାପ୍ତ RAM ଥିବା ଏକ ବିଲ୍ଡର୍ରେ ଦ୍ରୁତତର ବିଲ୍ଡ ପାଇଁ Turbopack ସକ୍ରିୟ କରନ୍ତୁ:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` ସକ୍ରିୟ ଅଛି, ତେଣୁ `next build` ଏକ ମୂଳ ପ୍ରକ୍ରିୟା **ଏବଂ** ଏକ ୱର୍କର୍
ପ୍ରକ୍ରିୟା ଚଳାଏ ଏବଂ ପ୍ରତ୍ୟେକଟି ପୃଥକ ଭାବେ `OMNIROUTE_BUILD_MEMORY_MB`କୁ ମାନେ। କଣ୍ଟେନର୍ର ସର୍ବୋଚ୍ଚ ସୀମାକୁ
ସେହି ମୂଲ୍ୟର ଥରେ ନୁହେଁ, ବରଂ ପ୍ରାୟ ଦୁଇଗୁଣରୁ ଅଧିକ ରଖନ୍ତୁ।

ଏହି ଟ୍ରିରେ ମାପ କରାଯାଇଛି (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| ବଣ୍ଡଲର୍   | କଣ୍ଟେନର୍ର ସର୍ବୋଚ୍ଚ ସୀମା | ଫଳାଫଳ                          |
| --------- | ----------------------- | ------------------------------ |
| Turbopack | 8 GiB / 16 GiB          | ଉଭୟରେ OOM-killed, ନିରବରେ       |
| webpack   | 8 GiB                   | ବିଲ୍ଡ ୱର୍କର୍ SIGKILLed         |
| webpack   | 12 GiB                  | ସଫଳ, ସର୍ବାଧିକ ବ୍ୟବହାର 11.1 GiB |

### ରନ୍ଟାଇମ୍ ଡିଫଲ୍ଟଗୁଡ଼ିକ

`runner-base` ଦ୍ୱାରା ଏକ୍ସପୋର୍ଟ କରାଯାଇଥିବା ଡିଫଲ୍ଟଗୁଡ଼ିକ: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`।

Dockerରେ ମେମୋରିର ଆଚରଣ:

- ଇମେଜ୍ଟି `OMNIROUTE_MEMORY_MB=1024` ସେଟ୍ କରେ ଏବଂ ଏଥିରୁ `NODE_OPTIONS=--max-old-space-size=1024` ନିର୍ଦ୍ଧାରଣ କରେ।
- ପ୍ରକୃତ ସର୍ଭର ପ୍ରକ୍ରିୟାଟି standalone launcher ଦ୍ୱାରା ଆରମ୍ଭ ହୁଏ, ଯାହା `OMNIROUTE_MEMORY_MB` ପଢ଼େ ଏବଂ `--max-old-space-size=<OMNIROUTE_MEMORY_MB>` ଯୋଡ଼େ।
- Node ପୁନରାବୃତ୍ତ `--max-old-space-size` ମୂଲ୍ୟଗୁଡ଼ିକ ମଧ୍ୟରୁ ଶେଷଟି ବ୍ୟବହାର କରେ, ତେଣୁ `OMNIROUTE_MEMORY_MB` ସେଟ୍ କଲେ ପ୍ରଭାବୀ Docker heap ସୀମା ନିୟନ୍ତ୍ରିତ ହୁଏ।
- ଇମେଜ୍ଟି ସର୍ବଦା ଏହାକୁ ସେଟ୍ କରୁଥିବାରୁ, launcherର ନିଜସ୍ୱ RAM-ଅନୁଯାୟୀ ସମନ୍ୱିତ fallback Docker ଅଧୀନରେ କେବେ ଲାଗୁ ହୁଏ ନାହିଁ। କାର୍ଯ୍ୟଭାର ପାଇଁ ଏହାକୁ ସ୍ପଷ୍ଟ ଭାବେ ବଢ଼ାନ୍ତୁ (ନିମ୍ନର ସାରଣୀ)। coding-agent `/v1/responses` ପାଇଁ `2048` ମଧ୍ୟ ଅତ୍ୟନ୍ତ କମ୍।

### କୋଡିଂ ଏଜେଣ୍ଟଗୁଡ଼ିକ ପାଇଁ ରନ୍ଟାଇମ୍ RAM

1 GiB Docker ଡିଫଲ୍ଟ ହେଉଛି dashboard/ହାଲୁକା-chat ପାଇଁ ସର୍ବନିମ୍ନ ସୀମା, production ପାଇଁ ଉପଯୁକ୍ତ ଆକାର ନୁହେଁ। ଦୀର୍ଘ `POST /v1/responses` bodyଗୁଡ଼ିକ (ଶତାଧିକ message, ଦଶାଧିକ tool) compression ସମୟରେ ଏକାଧିକ in-memory graph ଧରି ରଖନ୍ତି। ପରସ୍ପର ଉପରେ ଅତିକ୍ରମ କରୁଥିବା ପ୍ରାୟ ~3 MiB / ~750k-tokenର ଦୁଇଟି request ଏକ **12 GiB** old-spaceରେ V8କୁ ବିଫଳ କରିଛି (`FATAL ERROR: Reached heap limit`) ଏବଂ 16 GiB cgroup OOM ସୀମାକୁ ମଧ୍ୟ ଛୁଇଁଛି। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ଦେଖନ୍ତୁ।

cgroup `--memory`କୁ **heapଠାରୁ ଅଧିକ** ଆକାର ଦିଅନ୍ତୁ — native buffer, SQLite ଏବଂ compression intermediateଗୁଡ଼ିକ V8 ବାହାରେ ରହନ୍ତି।

| କାର୍ଯ୍ୟଭାର                             | `OMNIROUTE_MEMORY_MB`        | Container / cgroup   | ଟିପ୍ପଣୀ                                                                                    |
| -------------------------------------- | ---------------------------- | -------------------- | ------------------------------------------------------------------------------------------ |
| Dashboard, ଗୋଟିଏ ହାଲୁକା chat           | `1024` (ଇମେଜ୍ ଡିଫଲ୍ଟ)        | ≥2 GiB               |                                                                                            |
| ଗୋଟିଏ କୋଡିଂ ଏଜେଣ୍ଟ (Claude/Codex/Grok) | `8192`                       | ≥10 GiB              | ସାଧାରଣ single-session `/v1/responses`                                                      |
| ଦୁଇଟି ସମକାଳୀନ ଦୀର୍ଘ `/v1/responses`    | `10240`–`12288`              | ≥12–16 GiB           | ପ୍ରାୟ ~12 GiB heapରେ V8 ବିଫଳତା ମାପ କରାଯାଇଛି                                                |
| ତିନି କିମ୍ବା ଅଧିକ ସମକାଳୀନ ଦୀର୍ଘ context | ଗୋଟିଏ processରେ କରନ୍ତୁ ନାହିଁ | serialize / ଅଧିକ RAM | ଡିଫଲ୍ଟ heavyweight admission ହେଉଛି 1 in-flight; RAM ନ ବଢ଼ାଇ ଏହାକୁ ବଢ଼ାଇଲେ ପୁଣି ବିଫଳତା ଘଟିବ |

bare metalରେ `omniroute serve`, `OMNIROUTE_MEMORY_MB` **ସେଟ୍ ହୋଇନଥିବା** ସମୟରେ RAMର ପ୍ରାୟ ~35% ଅନୁଯାୟୀ ସମନ୍ୱୟ କରେ (`[512, 4096]` ମଧ୍ୟରେ ସୀମିତ)। Docker ସର୍ବଦା `1024` ସେଟ୍ କରେ, ତେଣୁ official imageରେ ସେହି ସମନ୍ୱୟ କେବେ ଚାଲେ ନାହିଁ।

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## ଉପପଥରେ ରିଭର୍ସ ପ୍ରକ୍ସି (Traefik / nginx)

Next.js `basePath` ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ବଣ୍ଡଲ୍ରେ କମ୍ପାଇଲ୍ ହୋଇଥାଏ। OmniRoute ଆପ୍ର ରୁଟ୍ରେ ଥିବା ଏକ ସେଣ୍ଟିନେଲ୍ ଫାଇଲ୍ରେ ବିଲ୍ଡ ସମୟରେ ଅନ୍ତର୍ନିହିତ ହୋଇଥିବା ମୂଲ୍ୟକୁ ରେକର୍ଡ କରେ (`npm run build` ସମୟରେ ଲେଖାଯାଏ; `scripts/docker/ensure-docker-base-path.mjs` ଦ୍ୱାରା ପଢ଼ାଯାଏ) ଏବଂ କଣ୍ଟେନର୍ ଆରମ୍ଭ ହେବାବେଳେ ଏହାକୁ `OMNIROUTE_BASE_PATH` ସହ ତୁଳନା କରେ। ଯେତେବେଳେ ସେଗୁଡ଼ିକ ଭିନ୍ନ ହୋଇଥାଏ ଏବଂ ଇମେଜ୍ଟି ଡୋମେନ୍ ରୁଟ୍ ପାଇଁ ବିଲ୍ଡ ହୋଇଥାଏ, ସେତେବେଳେ `node dev/run-standalone.mjs` ଚାଲିବା ପୂର୍ବରୁ ଏଣ୍ଟ୍ରିପଏଣ୍ଟ ଷ୍ଟାଣ୍ଡଅଲୋନ୍ ମ୍ୟାନିଫେଷ୍ଟଗୁଡ଼ିକ, ଏମ୍ବେଡ୍ ହୋଇଥିବା `basePath`/`assetPrefix` ଲିଟେରାଲ୍ଗୁଡ଼ିକ (Next 16 କେବଳ `assetPrefix`ରୁ SSR ଆସେଟ୍ URLଗୁଡ଼ିକୁ ରେଣ୍ଡର୍ କରେ — ପ୍ୟାଚର୍ ଉପପଥଟିକୁ ଏଥିରେ ମିରର୍ କରେ), ଅନ୍ତର୍ନିହିତ `/_next/static` ଆସେଟ୍ URLଗୁଡ଼ିକ (କ୍ଲାଏଣ୍ଟ-ରେଫରେନ୍ସ ମ୍ୟାନିଫେଷ୍ଟ, ମିଡିଆ ଇମ୍ପୋର୍ଟ, ପ୍ରିରେଣ୍ଡର୍ ହୋଇଥିବା ତ୍ରୁଟି ପୃଷ୍ଠା) ଏବଂ କ୍ଲାଏଣ୍ଟ `process.env` ଶିମ୍କୁ ପୁନର୍ଲିଖନ କରେ।

### Compose ବିଲ୍ଡ (ସୁପାରିଶକୃତ)

ଇମେଜ୍ ଏବଂ ରନ୍ଟାଇମ୍କୁ ସମାନ ରଖିବା ପାଇଁ `.env`ରେ ଉଭୟ ଭେରିଏବଲ୍ ସେଟ୍ କରନ୍ତୁ, ତା’ପରେ ପୁନଃ ବିଲ୍ଡ କରନ୍ତୁ:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml`, `OMNIROUTE_BASE_PATH`କୁ Docker ବିଲ୍ଡ ଆର୍ଗୁମେଣ୍ଟ ଏବଂ ରନ୍ଟାଇମ୍ ଏନଭାୟରନମେଣ୍ଟ ଭେରିଏବଲ୍—ଉଭୟ ଭାବରେ ଫରୱାର୍ଡ କରେ।

### ପୂର୍ବରୁ ବିଲ୍ଡ ହୋଇଥିବା ରୁଟ୍ ଇମେଜ୍ + ରନ୍ଟାଇମ୍ ଉପପଥ

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

**ସମ୍ପୂର୍ଣ୍ଣ** ବାହ୍ୟ ପଥକୁ ଫରୱାର୍ଡ କରିବା ପାଇଁ ରିଭର୍ସ ପ୍ରକ୍ସିକୁ ବିନ୍ୟାସ କରନ୍ତୁ (ପ୍ରିଫିକ୍ସକୁ ହଟାନ୍ତୁ ନାହିଁ)। Traefik, `StripPrefix` ବିନା `PathPrefix(`/omniroute`)`କୁ କଣ୍ଟେନର୍କୁ ରୁଟ୍ କରିବା ଉଚିତ, ଯାହାଦ୍ୱାରା Next.js `/omniroute/...` ଗ୍ରହଣ କରିବ ଏବଂ `/omniroute/_next/...`ରୁ ଆସେଟ୍ଗୁଡ଼ିକୁ ସର୍ଭ୍ କରିବ।

Docker ହେଲ୍ଥଚେକ୍, ସକ୍ରିୟ `OMNIROUTE_BASE_PATH` ପ୍ରିଫିକ୍ସ ଥିବା ହାଲୁକା `/healthz` ଲାଇଫ୍ସାଇକଲ୍ ଏଣ୍ଡପଏଣ୍ଟକୁ ପ୍ରୋବ୍ କରେ। ମାନବ/ଡ୍ୟାସ୍ବୋର୍ଡ ଡାୟାଗ୍ନୋଷ୍ଟିକ୍ସ ପାଇଁ `/api/monitoring/health` ଉପଲବ୍ଧ ରହେ; କଣ୍ଟେନର୍ HEALTHCHECKକୁ ପୁନଃ ଏହା ଆଡ଼କୁ ନିର୍ଦ୍ଦେଶ କରିବା ପାଇଁ (ଉଦାହରଣ ସ୍ୱରୂପ ଗଭୀର ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ ବାଧ୍ୟତାମୂଳକ କରିବାକୁ), `OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health` ସେଟ୍ କରନ୍ତୁ। ସେହି ପଥଟି ଏକ **ଗଭୀର** ଯାଞ୍ଚ (DB + ମନିଟରିଂ ସାରାଂଶ) — ଆପଣ ପୁନଃ ଏହାକୁ ଚୟନ କଲେ Dockerର କମ୍ ବାରମ୍ବାର ଚାଲୁଥିବା `HEALTHCHECK` ପାଇଁ ଏହା ଉପଯୁକ୍ତ, କିନ୍ତୁ Kubernetes `livenessProbe` ଇଣ୍ଟରଭାଲ୍ଗୁଡ଼ିକ ପାଇଁ **ନୁହେଁ**।

ଅର୍କେଷ୍ଟ୍ରେଟର୍ଗୁଡ଼ିକ ପାଇଁ (Kubernetes, Nomad, ଇତ୍ୟାଦି):

| ପ୍ରୋବ୍            | ପସନ୍ଦ କରନ୍ତୁ                                                         | ଏଡ଼ାନ୍ତୁ                                                     |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ |
| ଲାଇଭ୍ନେସ୍         | HTTP `GET /livez`, କିମ୍ବା ମୁଖ୍ୟ ପୋର୍ଟରେ TCP (`PORT`, ଡିଫଲ୍ଟ `20128`) | ଲାଇଭ୍ନେସ୍ ଭାବରେ `/api/monitoring/health`                     |
| ରେଡିନେସ୍          | HTTP `GET /healthz`                                                  | ଇଭେଣ୍ଟ-ଲୁପ୍ ବ୍ୟସ୍ତତାକୁ ବନ୍ଦ ଭାବେ ଗଣନା କରୁଥିବା କଠୋର ଟାଇମ୍ଆଉଟ୍ |
| ଡିପ୍ / ବ୍ଲାକ୍ବକ୍ସ | `/api/monitoring/health`                                             | —                                                            |

`/healthz` ପ୍ରୋସେସ୍ ଲାଇଫ୍ସାଇକଲ୍ (`ok` / `starting` / `stopping`) ରିପୋର୍ଟ କରେ। `/livez` କେବଳ ପ୍ରୋସେସ୍ ସଚଳ ଅଛି କି ନାହିଁ ତାହା ସୂଚାଏ (ହ୍ୟାଣ୍ଡଲର୍ ଚାଲିପାରୁଥିବା ପ୍ରତ୍ୟେକ ସମୟରେ 200; ଏହା ରେଡିନେସ୍ ପାଇଁ ଅପେକ୍ଷା କରେ ନାହିଁ)। ଉଭୟ ରିକ୍ୱେଷ୍ଟ ହ୍ୟାଣ୍ଡଲିଂ ସହ ସମାନ Node ଇଭେଣ୍ଟ ଲୁପ୍ରେ ଚାଲେ, ତେଣୁ CPU-ବାଉଣ୍ଡ କ୍ୟାଟାଲଗ୍ କିମ୍ବା କମ୍ପ୍ରେସନ୍ କାର୍ଯ୍ୟ ସେଗୁଡ଼ିକୁ ବିଳମ୍ବିତ କରିପାରେ — ବ୍ୟସ୍ତ ≠ ବନ୍ଦ। HTTP ପ୍ରୋବ୍ଗୁଡ଼ିକ ଟାଇମ୍ ଆଉଟ୍ ହେଲେ TCP ଲାଇଭ୍ନେସ୍କୁ ପସନ୍ଦ କରନ୍ତୁ। ସମ୍ପୂର୍ଣ୍ଣ ପ୍ରୋବ୍ ମାର୍ଗଦର୍ଶନ:
[ମନିଟରିଂ ଗାଇଡ୍ — Kubernetes ପ୍ରୋବ୍ ସୁପାରିଶଗୁଡ଼ିକ](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)।

## Caddy ସହିତ Docker Compose (HTTPS Auto-TLS)

Caddyର ସ୍ୱୟଂଚାଳିତ SSL ପ୍ରଦାନ ବ୍ୟବହାର କରି OmniRouteକୁ ସୁରକ୍ଷିତ ଭାବେ ଉପଲବ୍ଧ କରାଯାଇପାରେ। ଆପଣଙ୍କ ଡୋମେନ୍ର DNS A ରେକର୍ଡ ଆପଣଙ୍କ ସର୍ଭର୍ର IPକୁ ସୂଚାଉଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # OAuth କଲ୍ବ୍ୟାକ୍, ଡ୍ୟାସ୍ବୋର୍ଡ ଲିଙ୍କ୍ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା ସାର୍ବଜନୀନ URLଗୁଡ଼ିକ ପାଇଁ ବ୍ରାଉଜର୍-ସମ୍ମୁଖୀନ ଉତ୍ସ।
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # ନିର୍ଦ୍ଧାରିତ କାର୍ଯ୍ୟ / ସ୍ୱୟଂ-ଫେଚ୍ ପାଇଁ ଆଭ୍ୟନ୍ତରୀଣ ସର୍ଭର୍-ଟୁ-ସର୍ଭର୍ URL।
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy ଅପ୍ଷ୍ଟ୍ରିମ୍ କଣ୍ଟେନର୍ ପାଇଁ ମାନକ ଫର୍ୱାର୍ଡିଂ ହେଡର୍ଗୁଡ଼ିକ ସେଟ୍ କରେ। OmniRoute, OAuth କଲ୍ବ୍ୟାକ୍ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା ସାର୍ବଜନୀନ ଲିଙ୍କ୍ଗୁଡ଼ିକ ପାଇଁ
`NEXT_PUBLIC_BASE_URL`କୁ ପ୍ରାମାଣିକ ସାର୍ବଜନୀନ ଉତ୍ସ ଭାବେ ବ୍ୟବହାର କରେ; ପ୍ରମାଣୀକୃତ ଡ୍ୟାସ୍ବୋର୍ଡ ରାଇଟ୍ କାର୍ଯ୍ୟଗୁଡ଼ିକ ସମାନ-ଉତ୍ସ ଅନୁରୋଧ ସହିତ ସେସନ୍-ବାଉଣ୍ଡ CSRF
ସୁରକ୍ଷା ବ୍ୟବହାର କରେ। ଯେଉଁ ଉନ୍ନତ ଡିପ୍ଲୟମେଣ୍ଟରେ ଆପଣ ସ୍ପଷ୍ଟ
ବିନ୍ୟାସ ପରିବର୍ତ୍ତେ ବିଶ୍ୱସ୍ତ ଫର୍ୱାର୍ଡ ହେଡର୍ରୁ OmniRouteକୁ ସାର୍ବଜନୀନ ଉତ୍ସ ନିର୍ଦ୍ଧାରଣ କରାଇବାକୁ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ ଚାହାନ୍ତି, କେବଳ ସେହି କ୍ଷେତ୍ରରେ `OMNIROUTE_TRUST_PROXY` ସକ୍ଷମ କରନ୍ତୁ।

## Cloudflare Quick Tunnel

Docker ଡିପ୍ଲୟମେଣ୍ଟ ପାଇଁ ଡ୍ୟାସ୍ବୋର୍ଡ ସମର୍ଥନରେ `Dashboard → Endpoints` ଉପରେ ଏକ-କ୍ଲିକ୍ **Cloudflare Quick Tunnel** ଅନ୍ତର୍ଭୁକ୍ତ। ପ୍ରଥମ ଥର ସକ୍ଷମ କଲେ, ଏହା କେବଳ ଆବଶ୍ୟକ ସମୟରେ `cloudflared` ଡାଉନ୍ଲୋଡ୍ କରେ, ଆପଣଙ୍କ ବର୍ତ୍ତମାନର `/v1` ଏଣ୍ଡପଏଣ୍ଟକୁ ଏକ ଅସ୍ଥାୟୀ ଟନେଲ୍ ଆରମ୍ଭ କରେ ଏବଂ ସୃଷ୍ଟି ହୋଇଥିବା `https://*.trycloudflare.com/v1` URLକୁ ଆପଣଙ୍କ ସାଧାରଣ ସାର୍ବଜନୀନ URLର ଠିକ୍ ତଳେ ଦେଖାଏ।

ସକ୍ରିୟ ଟନେଲ୍ର ସ୍ଥିତି ପରିବର୍ତ୍ତନ ନକରି ଏଣ୍ଡପଏଣ୍ଟ ଟନେଲ୍ ପ୍ୟାନେଲ୍ଗୁଡ଼ିକୁ (Cloudflare, Tailscale, ngrok) `Settings → Appearance`ରୁ ଦେଖାଯାଇପାରିବ କିମ୍ବା ଲୁଚାଯାଇପାରିବ।

### ଟନେଲ୍ ଟିପ୍ପଣୀ

- Quick Tunnel URLଗୁଡ଼ିକ ଅସ୍ଥାୟୀ ଏବଂ ପ୍ରତ୍ୟେକ ପୁନଃଆରମ୍ଭ ପରେ ପରିବର୍ତ୍ତିତ ହୁଏ।
- OmniRoute କିମ୍ବା କଣ୍ଟେନର୍ ପୁନଃଆରମ୍ଭ ପରେ Quick Tunnelଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବେ ପୁନଃସ୍ଥାପିତ ହୁଏ ନାହିଁ। ଆବଶ୍ୟକ ହେଲେ ଡ୍ୟାସ୍ବୋର୍ଡରୁ ସେଗୁଡ଼ିକୁ ପୁନଃସକ୍ଷମ କରନ୍ତୁ।
- ପରିଚାଳିତ ଇନ୍ଷ୍ଟଲ୍ ବର୍ତ୍ତମାନ `x64` / `arm64`ରେ Linux, macOS ଏବଂ Windowsକୁ ସମର୍ଥନ କରେ।
- ସୀମିତ କଣ୍ଟେନର୍ ପରିବେଶରେ କୋଳାହଳପୂର୍ଣ୍ଣ QUIC UDP ବଫର୍ ଚେତାବନୀ ଏଡ଼ାଇବା ପାଇଁ ପରିଚାଳିତ Quick Tunnelଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବେ HTTP/2 ପରିବହନ ବ୍ୟବହାର କରେ। ଭିନ୍ନ ପରିବହନ ଚାହୁଁଥିଲେ `CLOUDFLARED_PROTOCOL=quic` କିମ୍ବା `auto` ସେଟ୍ କରନ୍ତୁ।
- Docker ଇମେଜ୍ଗୁଡ଼ିକ ସିଷ୍ଟମ୍ CA ରୁଟ୍ଗୁଡ଼ିକୁ ବଣ୍ଡଲ୍ କରି ପରିଚାଳିତ `cloudflared`କୁ ପ୍ରଦାନ କରେ, ଯାହା କଣ୍ଟେନର୍ ଭିତରେ ଟନେଲ୍ ବୁଟ୍ଷ୍ଟ୍ରାପ୍ ହେବାବେଳେ TLS ବିଶ୍ୱସନୀୟତା ବିଫଳତାକୁ ଏଡ଼ାଇଥାଏ।
- ଯଦି ଆପଣ OmniRouteକୁ ଡାଉନ୍ଲୋଡ୍ କରାଯାଇଥିବା ବାଇନାରି ପରିବର୍ତ୍ତେ ଏକ ବିଦ୍ୟମାନ ବାଇନାରି ବ୍ୟବହାର କରାଇବାକୁ ଚାହାନ୍ତି, ତେବେ `CLOUDFLARED_BIN=/absolute/path/to/cloudflared` ସେଟ୍ କରନ୍ତୁ।

#### ୱେବ୍-ସେସନ୍ ପ୍ରଦାନକାରୀ: `-web` ଇମେଜ୍ଗୁଡ଼ିକ

ଉପରୋକ୍ତ ପ୍ରତ୍ୟେକ ଚ୍ୟାନେଲ୍ ଏକ `-web` ଟ୍ୟାଗ୍ (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`) ଭାବେ ମଧ୍ୟ ଉପଲବ୍ଧ, ଯାହା `runner-web` ଷ୍ଟେଜ୍ରୁ ବିଲ୍ଡ ହୋଇଛି — ସମାନ ଇମେଜ୍ ସହିତ Playwright ଏବଂ ଏକ Chromium ବ୍ରାଉଜର୍। ସାଧାରଣ ଇମେଜ୍ Chromium **ବିନା** ପ୍ରଦାନ କରାଯାଏ; `gemini-web`, `claude-web` ଏବଂ `claude-turnstile` ପାଇଁ ଏହା ଆବଶ୍ୟକ।

ବିଫଳତା ଷ୍ଟାର୍ଟଅପ୍ ସମୟରେ ନୁହେଁ, ବରଂ ପରବର୍ତ୍ତୀ ସମୟକୁ ବିଳମ୍ବିତ ହୁଏ: ସେହି ପ୍ରଦାନକାରୀମାନେ ନିଜ ମଡେଲ୍ଗୁଡ଼ିକୁ ତାଲିକାଭୁକ୍ତ କରନ୍ତି ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡରେ ସଂଯୁକ୍ତ ଭାବେ ଦେଖାଯାଆନ୍ତି, ଏବଂ କେବଳ ପ୍ରଥମ ଅନୁରୋଧଟି ନିମ୍ନଲିଖିତ ତ୍ରୁଟି ସହିତ ବିଫଳ ହୁଏ

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

ଆପଣ ସେହି ପ୍ରଦାନକାରୀମାନଙ୍କୁ ବ୍ୟବହାର କରୁଥିଲେ, ବର୍ତ୍ତମାନ ଯେଉଁ ଚ୍ୟାନେଲ୍ରେ ଅଛନ୍ତି ତାହାର `-web` ଟ୍ୟାଗ୍ ପୁଲ୍ କରନ୍ତୁ — ଅନ୍ୟ କିଛି ପରିବର୍ତ୍ତନ ହୁଏ ନାହିଁ। ଏକ npm/CLI ଇନ୍ଷ୍ଟଲ୍ରେ (Docker ଇମେଜ୍ ବିନା), ସମତୁଲ୍ୟ ଅନୁପସ୍ଥିତ ଅଂଶଟି ହେଉଛି ବ୍ରାଉଜର୍ ବାଇନାରି: ହୋଷ୍ଟରେ `npx playwright install chromium` ଚଲାନ୍ତୁ।

#### ପ୍ରି-ରିଲିଜ୍ ଚ୍ୟାନେଲ୍ର ବ୍ୟବହାର

`next` ଚ୍ୟାନେଲ୍ଟି ବର୍ତ୍ତମାନର ଡିଫଲ୍ଟ `release/v*` ବ୍ରାଞ୍ଚକୁ ପ୍ରତ୍ୟେକ push ସମୟରେ ପୁନଃନିର୍ମାଣ କରାଯାଏ ଏବଂ AMD64 ଓ ARM64 ଉଭୟ ପାଇଁ ପ୍ରକାଶ କରାଯାଏ। ପୁରୁଣା maintenance ବ୍ରାଞ୍ଚଗୁଡ଼ିକ ଏହାକୁ overwrite କରିପାରିବେ ନାହିଁ। ପରବର୍ତ୍ତୀ stable tag ପ୍ରସ୍ତୁତ ହେବା ପୂର୍ବରୁ ସକ୍ରିୟ release ବ୍ରାଞ୍ଚରେ merge ହୋଇଥିବା ସଂଶୋଧନଗୁଡ଼ିକ ପାଇଁ ଏହି ଚ୍ୟାନେଲ୍ ଏକ pull କରାଯୋଗ୍ୟ image ପ୍ରଦାନ କରେ।

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Docker Compose ପାଇଁ, ଚୟନିତ profile ଦ୍ୱାରା ବ୍ୟବହୃତ image tagକୁ override କରନ୍ତୁ, ତା'ପରେ serviceକୁ pull କରି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### ସୁରକ୍ଷା ଏବଂ rollback

`next` ଏକ ପରିବର୍ତ୍ତନଶୀଳ pre-release ଚ୍ୟାନେଲ୍। ସକ୍ରିୟ release ବ୍ରାଞ୍ଚକୁ ଯେକୌଣସି push ସମୟରେ ଏହା ପରିବର୍ତ୍ତିତ ହୋଇପାରେ ଏବଂ ଏହା **production ବ୍ୟବହାର ପାଇଁ ସମର୍ଥିତ ନୁହେଁ**। କୌଣସି ନିର୍ଦ୍ଦିଷ୍ଟ buildର ମୂଲ୍ୟାୟନ କରିବା ସମୟରେ image digestକୁ pin କରନ୍ତୁ:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

ପରୀକ୍ଷା କରିବା ପୂର୍ବରୁ OmniRoute data volume କିମ୍ବା bind-mounted data directoryର backup ନିଅନ୍ତୁ। rollback କରିବା ପାଇଁ, ପୂର୍ବରୁ ବ୍ୟବହୃତ stable version କିମ୍ବା digestକୁ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ ଏବଂ containerକୁ ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

କୌଣସି release-branch build କେବେ ମଧ୍ୟ `latest`କୁ ସ୍ଥାନାନ୍ତର କରିପାରିବ ନାହିଁ; କେବଳ ଏକ ଯୋଗ୍ୟ stable semantic version stable pointerକୁ promote କରିପାରିବ। `next` imageଗୁଡ଼ିକ release image inspection ଏବଂ CRITICAL-vulnerability blocking gateକୁ ବଜାୟ ରଖେ।

**`latest`, git ପାଇଁ ସଦ୍ୟତାର କୌଣସି ନିଶ୍ଚିତତା ନୁହେଁ।** `main` କିମ୍ବା ସକ୍ରିୟ `release/v*` ବ୍ରାଞ୍ଚରେ merge ହୋଇଥିବା ସଂଶୋଧନଗୁଡ଼ିକ ଏକ stable SemVer image ପ୍ରକାଶିତ ନହେବା ଏବଂ publish job ଦ୍ୱାରା `:latest` promote ନହେବା ପର୍ଯ୍ୟନ୍ତ `:latest`ରେ ରହିବ ନାହିଁ (ସେହି SemVer ସହ ସମାନ digest)। GitHubରେ ସଂଶୋଧନଟି ପୂର୍ବରୁ ଦେଖାଯାଉଥିବା ସତ୍ତ୍ୱେ ଯଦି `latest` ଅପରିବର୍ତ୍ତିତ ଲାଗେ, release ବ୍ରାଞ୍ଚ ପରୀକ୍ଷା କରିବା ପାଇଁ `:next` pull କରନ୍ତୁ କିମ୍ବା SemVer tag ପାଇଁ ଅପେକ୍ଷା କରନ୍ତୁ।

| ---------------------------------------------------------------------------- | --------------------------------------------- |

**ଅପ୍ଗ୍ରେଡ୍:** ପ୍ରତ୍ୟେକ ସେସନ୍ ବିଚ୍ଛିନ୍ନ ହେବ ବୋଲି ଆଶା କରନ୍ତୁ। ସମ୍ଭବ ହେଲେ କ୍ଲାଏଣ୍ଟମାନଙ୍କୁ ଡ୍ରେନ୍ କରନ୍ତୁ; ଡିଫଲ୍ଟ SQLiteରେ କୌଣସି ରୋଲିଂ ଅପଡେଟ୍ ନାହିଁ। Compose `restart: unless-stopped` ସହିତ Docker `HEALTHCHECK` ମଧ୍ୟ କଣ୍ଟେନର୍ Unhealthy ହେଲେ ଏକମାତ୍ର ପ୍ରକ୍ରିୟାକୁ ବଦଳାଇଦେବ — ପ୍ରଭାବର ପରିସର ସମାନ।

**ଏକକ ରେପ୍ଲିକା** ପାଇଁ Kubernetes ସ୍ନିପେଟ୍ (Recreate ଆବଶ୍ୟକ; ଗୋଟିଏ SQLite ଫାଇଲ୍ ବିପକ୍ଷରେ `replicas` ବଢ଼ାନ୍ତୁ ନାହିଁ):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

`preStop` ସ୍ଲିପ୍ ଯୋଗୁଁ SIGTERM ପୂର୍ବରୁ kube, Service ଏଣ୍ଡପଏଣ୍ଟଗୁଡ଼ିକୁ ହଟାଇପାରେ, ଯାହାଦ୍ୱାରା **ନୂଆ** ଟ୍ରାଫିକ୍ ବନ୍ଦ ହେଉଥିବା ପ୍ରକ୍ରିୟାକୁ ପହଞ୍ଚିବା ବନ୍ଦ ହୁଏ। ଚାଲୁଥିବା `/v1/responses` SSEକୁ ହେଭିୱେଟ୍ ଆଡ୍ମିସନ୍ ଲିଜ୍ଗୁଡ଼ିକ ମାଧ୍ୟମରେ `SHUTDOWN_TIMEOUT_MS` (ଡିଫଲ୍ଟ 30s) ପର୍ଯ୍ୟନ୍ତ ଡ୍ରେନ୍ କରାଯାଏ (#11015)। ତଥାପି ପ୍ରକ୍ରିୟା ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚୁଥିବା ନୂଆ ଅନୁରୋଧଗୁଡ଼ିକ `503` + `Retry-After: 5` ପାଆନ୍ତି। ପ୍ରତିସ୍ଥାପନଟି Ready ହେବା ପର୍ଯ୍ୟନ୍ତ ରହୁଥିବା Recreate ଖାଲି-ଏଣ୍ଡପଏଣ୍ଟ ବ୍ୟବଧାନ ଏକ ସମ୍ପୂର୍ଣ୍ଣ ସେବା ବିଚ୍ଛିନ୍ନତା ଭାବେ ରହିଯାଏ — ଏହା SQLite ଟୋପୋଲୋଜି, କୌଣସି ପ୍ରୋବ୍ ଭୁଲ୍ ବିନ୍ୟାସ ନୁହେଁ।

ବାହ୍ୟ Postgres / ମଲ୍ଟି-ରାଇଟର୍ HA ଏକ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ଷ୍ଟକ୍ ପଥ **ନୁହେଁ**। ଆପଣଙ୍କୁ HA ଆବଶ୍ୟକ ହେଲେ, ଏକକ ରେପ୍ଲିକା ରଖନ୍ତୁ କିମ୍ବା ପ୍ରକଳ୍ପ ଦ୍ୱାରା ପରୀକ୍ଷିତ ଏବଂ ପୃଥକ ଭାବେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ଏକ ଟୋପୋଲୋଜି ଚଲାନ୍ତୁ। Postgres/MySQL କାର୍ଯ୍ୟ [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)ରେ ଅଛି। ଏହା ରିଲିଜ୍ ହେବା ପର୍ଯ୍ୟନ୍ତ, **ବଡ଼** `/v1/responses` କ୍ଷମତା ବଢ଼ାଇବାର ଏକମାତ୍ର ସମର୍ଥିତ ଉପାୟ ହେଉଛି Nଟି ସ୍ୱାଧୀନ ପ୍ରକ୍ରିୟା (ପରବର୍ତ୍ତୀ ବିଭାଗ), ଗୋଟିଏ ଭଲ୍ୟୁମ୍ରେ `replicas > 1` ନୁହେଁ।

## ସ୍କେଲ୍-ଆଉଟ୍: Nଟି ସ୍ୱାଧୀନ ପ୍ରକ୍ରିୟା

ଗୋଟିଏ Node ପ୍ରକ୍ରିୟା ହେଉଛି **ଗୋଟିଏ V8 heap**। ପରସ୍ପର ଆଚ୍ଛାଦିତ ଦୁଇଟି ~3 MiB / ~750k-token coding-agent `POST /v1/responses` (RTK + Caveman) ~12 Giରେ ସେହି heapକୁ ବନ୍ଦ କରିଦିଏ (`FATAL ERROR: Reached heap limit`) ଏବଂ ଏକ 16 Gi cgroupକୁ OOM କରିପାରେ। [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849) ଦେଖନ୍ତୁ। ସେହି ମାପ ଏକ **ମେମୋରି-ବଜେଟ୍** ସତର୍କତା, ଏକାସାଙ୍ଗରେ ଚାଲୁଥିବା ଦୀର୍ଘ `/v1/responses` ପାଇଁ ଦୁଇଟିର କୌଣସି ଉତ୍ପାଦ-ସ୍ତରୀୟ ସର୍ବାଧିକ ସୀମା ନୁହେଁ। ଭାରୀ chat ଗ୍ରହଣକୁ ସ୍ୱୟଂ-ନିର୍ଦ୍ଧାରିତ ingest byte ବଜେଟ୍ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`) ଦ୍ୱାରା ନିୟନ୍ତ୍ରଣ କରାଯାଏ, ଯାହା ସେହି V8/cgroup ସୀମା ଆଧାରରେ ଆକାରିତ — ପୂର୍ବରୁ ଆକାରିତ ପ୍ରକ୍ରିୟାରେ ଏହାକୁ ଅଧିକ ମୂଲ୍ୟରେ override କଲେ (କିମ୍ବା ପୁରୁଣା `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ଅନୁରୋଧ-ଗଣନା ସୀମା ସେଟ୍ କଲେ) ପୁଣି ପ୍ରକ୍ରିୟା ବନ୍ଦ ହେବାର ସମସ୍ୟା ଫେରିଆସେ। ଛୋଟ chat, `/healthz`, `/v1/models`, ଏବଂ MCP ସେହି ସୀମାରେ **ଅନ୍ତର୍ଭୁକ୍ତ ନୁହେଁ**।

### ଏକ-ପ୍ରକ୍ରିୟା: ଦୁଇଟିରୁ ଅଧିକ ଦୀର୍ଘ `/v1/responses`

ଏକ **ସୁସ୍ଥ** ପ୍ରକ୍ରିୟା (heap `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO`ଠାରୁ କମ୍, ଡିଫଲ୍ଟ `0.75`) ପ୍ରକ୍ରିୟା-ବ୍ୟାପୀ inflight-byte ବଜେଟ୍ରେ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ଏପର୍ଯ୍ୟନ୍ତ ସ୍ଥାନ ଥିଲେ, ଏକାସାଙ୍ଗରେ ଦୁଇଟିରୁ ଅଧିକ ଦୀର୍ଘ `POST /v1/responses` ଚଲାଇ **ପାରେ**। `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (ଡିଫଲ୍ଟ 256 KiB) ସମାନ କିମ୍ବା ତାହାଠାରୁ ବଡ଼ bodyଗୁଡ଼ିକ structure-heavy ଅନୁରୋଧ ପରି ସମାନ heavyweight lease ନିଅନ୍ତି ଏବଂ ସମାନ [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) `tryAcquireHealthyHeadroom` escape (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`) ବ୍ୟବହାର କରନ୍ତି। ଏକାସାଙ୍ଗରେ ଦଶ ଦଶଟି ଦୀର୍ଘ SSE client (operatorମାନଙ୍କୁ ପ୍ରାୟତଃ 40–50ଟି ଆବଶ୍ୟକ ହୁଏ) ଏକ **ମେମୋରି-ବଜେଟ୍** ପ୍ରଶ୍ନ — heap + primary/headroom slot + `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`ର ଆକାର ନିର୍ଦ୍ଧାରଣ କରନ୍ତୁ — ଏହା କୌଣସି କଠୋର “ସର୍ବାଧିକ 2” ଉତ୍ପାଦ ସୀମା ନୁହେଁ। ଚାପଗ୍ରସ୍ତ heap ଏବେ ମଧ୍ୟ ପୁନଃଚେଷ୍ଟାଯୋଗ୍ୟ `503` ସହିତ load shed କରେ, ଯାହାଦ୍ୱାରା #7849 ପୁଣି ଫେରିନଆସେ।

**ଏକାଧିକ heap ସୃଷ୍ଟି କରିବାକୁ** (ସ୍ୱାଧୀନ V8 old-space) **ବର୍ତ୍ତମାନ**:

| କରନ୍ତୁ                                                                                                                                                         | କରନ୍ତୁ ନାହିଁ                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Nଟି container/pod** ଚଲାନ୍ତୁ, ପ୍ରତ୍ୟେକର ନିଜସ୍ୱ `DATA_DIR` / volume ସହିତ                                                                                       | ଗୋଟିଏ SQLite file ପାଇଁ `replicas > 1` ସେଟ୍ କରନ୍ତୁ ନାହିଁ               |
| heap / inflight-byte ବଜେଟ୍ ଆଧାରରେ heavy in-flight + healthy-headroomର ଆକାର ନିର୍ଦ୍ଧାରଣ କରନ୍ତୁ; 1–2 ହେଉଛି ରକ୍ଷଣଶୀଳ #7849 ଡିଫଲ୍ଟ, କଠୋର ଉତ୍ପାଦ ସର୍ବାଧିକ ସୀମା ନୁହେଁ | ଗୋଟିଏ ପ୍ରକ୍ରିୟାକୁ 8× RAM ଏବଂ ଏକ ଅସୀମିତ ଗଣନା ସୀମା ଦିଅନ୍ତୁ ନାହିଁ        |
| ଇଚ୍ଛାଧୀନ: **ଅଂଶୀଦାର quota counter** ପାଇଁ `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL`                                                                  | Redisକୁ ଅଂଶୀଦାର SQLite ଭାବେ ବିବେଚନା କରନ୍ତୁ ନାହିଁ — ଏହା ସେପରି ନୁହେଁ    |
| ପ୍ରତ୍ୟେକ instanceରେ provider secretଗୁଡ଼ିକୁ ନକଲ କରନ୍ତୁ (କିମ୍ବା ବିଭାଜିତ dashboardଗୁଡ଼ିକୁ ଗ୍ରହଣ କରନ୍ତୁ)                                                           | ସମସ୍ତ instance ପାଇଁ ଗୋଟିଏ dashboard / ଗୋଟିଏ call-log ଆଶା କରନ୍ତୁ ନାହିଁ |
| ଯେକୌଣସି load balancerକୁ ସାମ୍ନାରେ ରଖନ୍ତୁ; API key କିମ୍ବା session ଅନୁଯାୟୀ sticky routing ଯଥେଷ୍ଟ                                                                  | କୌଣସି vendor-ନିର୍ଦ୍ଦିଷ୍ଟ size-aware middleware ଆବଶ୍ୟକ କରନ୍ତୁ ନାହିଁ    |

Hardware: ପ୍ରତ୍ୟେକ instanceରେ ଏକାସାଙ୍ଗରେ ଚାଲୁଥିବା ଦୀର୍ଘ `/v1/responses` ସଂଖ୍ୟା ଏକ **ମେମୋରି-ବଜେଟ୍** ପ୍ରଶ୍ନ (heap + inflight-byte / #10110)। ସ୍ୱାଧୀନ `DATA_DIR` ସହିତ `N`ଟି instance ଏବେ ମଧ୍ୟ heap ସଂଖ୍ୟାକୁ ଗୁଣିତ କରେ: host RAMକୁ `N × cgroup` ପୂରଣ କରିବାକୁ ପଡ଼ିବ, “N=8 ସହିତ ଗୋଟିଏ 16 Gi pod” ନୁହେଁ। ଗୋଟିଏ SQLite file ଉପରେ କେବେବି `replicas > 1` ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ।

Compose ରୂପରେଖା (ଦୁଇଟି heap, ଦୁଇଟି volume — `deploy.replicas: 2` ନୁହେଁ):

```yaml
      DATA_DIR: /app/data

      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

In-process density (HTTP isolateରୁ compressionକୁ ବାହାରେ ରଖିବା) ହେଉଛି [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023)। ଅଂଶୀଦାର durable state ଉପରେ ଗୋଟିଏ logical cluster ହେଉଛି [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)।

### ସଂଯୋଗ-ନିର୍ଦ୍ଦିଷ୍ଟ ପ୍ରକ୍ସିକୁ ପ୍ରାଧାନ୍ୟ ଦିଅନ୍ତୁ

ପ୍ରଭାବିତ Gemini ସଂଯୋଗ ପାଇଁ OmniRouteର
[ପ୍ରତି-ସଂଯୋଗ ପ୍ରକ୍ସି ବିନ୍ୟାସ](../ops/PROXY_GUIDE.md#4-level-proxy-system)
ବ୍ୟବହାର କରନ୍ତୁ, ତା’ପରେ ସମାନ ମଡେଲ୍ ସହିତ **Test Connection** ଏବଂ ଏକ ଛୋଟ ଅନୁରୋଧ
ପୁଣି କରନ୍ତୁ। ଏହା ରାଉଟିଂ ପରିବର୍ତ୍ତନକୁ ସେହି ସଂଯୋଗ ମଧ୍ୟରେ ସୀମିତ ରଖେ। ପ୍ରକ୍ସିଟି
କଣ୍ଟେନର୍ରୁ ପହଞ୍ଚଯୋଗ୍ୟ ଏବଂ ସଂଯୋଗଟି ପ୍ରକୃତରେ ତାହାକୁ ଚୟନ କରୁଛି କି ନାହିଁ,
ତାହା ଯାଞ୍ଚ କରନ୍ତୁ। ରୁଟ୍ ପରିବର୍ତ୍ତନ କଲେ ଅପ୍ଷ୍ଟ୍ରିମ୍ ଆଞ୍ଚଳିକ ଯୋଗ୍ୟତା ସୁନିଶ୍ଚିତ ହୁଏ ନାହିଁ।

### ହୋଷ୍ଟ ଏବଂ କଣ୍ଟେନର୍ ନେଟୱର୍କିଂ ତୁଳନା କରନ୍ତୁ

ପ୍ରାମାଣୀକୃତ ଫଳାଫଳ ତୁଳନା କରିବାବେଳେ କୀ, ମଡେଲ୍ ଏବଂ ଅନୁରୋଧକୁ ସମାନ ରଖନ୍ତୁ;
କୌଣସି ଇସ୍ୟୁରେ କେବେବି ପରିଚୟପତ୍ର, ପ୍ରକ୍ସି ପାସୱାର୍ଡ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ପ୍ରାଧିକରଣ
ହେଡର୍ ପେଷ୍ଟ କରନ୍ତୁ ନାହିଁ। ପ୍ରଥମେ OS ରିଜଲ୍ଭର୍ କେଉଁ ଠିକଣା ପରିବାରଗୁଡ଼ିକ
ପ୍ରଦାନ କରୁଛି ତାହା ଯାଞ୍ଚ କରନ୍ତୁ, ହୋଷ୍ଟ ଏବଂ କଣ୍ଟେନର୍ ଭିତରେ ସମାନ କମାଣ୍ଡ ବ୍ୟବହାର କରି:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

`omniroute`କୁ ଆପଣ ଚଲାଉଥିବା ସର୍ଭିସ୍ର ନାମରେ ବଦଳାନ୍ତୁ (ଉଦାହରଣ ସ୍ୱରୂପ,
`omniroute-web`)। ଏହି କମାଣ୍ଡଗୁଡ଼ିକ ପରିଚୟପତ୍ର କିମ୍ବା IP ଠିକଣା ବିନା ଠିକଣା
ପରିବାରଗୁଡ଼ିକୁ ପ୍ରିଣ୍ଟ କରେ। ଫେରିଥିବା `6` କେବଳ ଏକ IPv6 DNS ଫଳାଫଳ ଦର୍ଶାଏ:
ଏହା ବ୍ୟବହାରଯୋଗ୍ୟ IPv6 ରୁଟ୍ କିମ୍ବା API ଆକ୍ସେସ୍କୁ ପ୍ରମାଣ କରେ **ନାହିଁ**।
ଯେଉଁଠାରେ `curl` ଇନ୍ଷ୍ଟଲ୍ ହୋଇଛି, ଉଭୟ ପରିବେଶରେ
`curl -4 -I https://generativelanguage.googleapis.com` ସହିତ
`curl -6 -I https://generativelanguage.googleapis.com`କୁ ତୁଳନା କରନ୍ତୁ।
ଏକ HTTP ପ୍ରତିକ୍ରିୟା ସେହି ପରୀକ୍ଷଣ ପାଇଁ ସଂଯୋଗକୁ ପ୍ରମାଣ କରେ, ଯଦିଓ ତାହା ଏକ
ଅପ୍ରାମାଣୀକୃତ ତ୍ରୁଟି ହୋଇଥାଏ; କେବଳ ପ୍ରାମାଣୀକୃତ ମଡେଲ୍ ଅନୁରୋଧ Gemini ଯୋଗ୍ୟତାକୁ ପରୀକ୍ଷା କରେ।

### ହୋଷ୍ଟ-ସ୍ତରୀୟ ବିକଳ୍ପ: କାର୍ଯ୍ୟକ୍ଷମ IPv6 ଏବଂ ରିଜଲ୍ଭର୍ ନୀତି

[#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762)ର ରିପୋର୍ଟକାରୀ
କଣ୍ଟେନର୍ IPv6 ସକ୍ଷମ କରି ଏବଂ glibc ଠିକଣା ଚୟନ ପରିବର୍ତ୍ତନ କରି ସେମାନଙ୍କ
ପରିବେଶରେ ଆକ୍ସେସ୍ ପୁନଃସ୍ଥାପନ କରିଥିଲେ। ଏହାକୁ ଏକ ପରିବେଶ-ନିର୍ଦ୍ଦିଷ୍ଟ ବିକଳ୍ପ
ଭାବରେ ବିବେଚନା କରନ୍ତୁ। ରିଜଲ୍ଭର୍ ପସନ୍ଦଗୁଡ଼ିକୁ ସମାଯୋଜନ କରିବା ପୂର୍ବରୁ
କାର୍ଯ୍ୟକ୍ଷମ ହୋଷ୍ଟ IPv6, କଣ୍ଟେନର୍ ଏଗ୍ରେସ୍/ରାଉଟିଂ ଏବଂ ଫାୟାରୱାଲ୍ ନିୟମଗୁଡ଼ିକ
ନିଶ୍ଚିତ କରନ୍ତୁ। ଏକ ଘରୋଇ ULA ଠିକଣା ନିଜେ ସାର୍ବଜନୀନ IPv6 ସଂଯୋଗ ସ୍ଥାପନ କରେ ନାହିଁ।

Composeର ଡିଫଲ୍ଟ ନେଟୱର୍କ ସହିତ ପୂର୍ବରୁ ସଂଲଗ୍ନ ସର୍ଭିସ୍ଗୁଡ଼ିକ ପାଇଁ, ଏହି
ଖଣ୍ଡଟି ସେହି ନେଟୱର୍କରେ IPv6 ସକ୍ଷମ କରେ; ଆପଣଙ୍କ ସର୍ଭିସ୍, ପୋର୍ଟ, ଭଲ୍ୟୁମ୍
ଏବଂ ବିନ୍ୟାସର ଅବଶିଷ୍ଟ ଅଂଶକୁ ଅପରିବର୍ତ୍ତିତ ରଖନ୍ତୁ:

```yaml
networks:
  default:
    enable_ipv6: true
```

ଏକ ନାମିତ ନେଟୱର୍କ ପାଇଁ, ସର୍ଭିସ୍ଟି ପ୍ରକୃତରେ ଯେଉଁ ନେଟୱର୍କରେ ଯୋଗ ଦେଉଛି,
ସେଥିରେ ଏହାକୁ ସକ୍ଷମ କରନ୍ତୁ। Docker ଏକ ULA ସବ୍ନେଟ୍ ବଣ୍ଟନ କରିପାରେ; କେବଳ
ଆପଣଙ୍କ ନେଟୱର୍କକୁ ଆବଶ୍ୟକ ହେଲେ ଏକ ସ୍ପଷ୍ଟ, ପରସ୍ପର ଓଭରଲାପ୍ ନକରୁଥିବା
ସବ୍ନେଟ୍ ଚୟନ କରନ୍ତୁ। [Docker IPv6 ନେଟୱର୍କିଂ](https://docs.docker.com/engine/daemon/ipv6/)
ଏବଂ [Compose ନେଟୱର୍କ ବିକଳ୍ପଗୁଡ଼ିକ](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6) ଦେଖନ୍ତୁ।

ଏକ **glibc-ଆଧାରିତ ଇମେଜ୍**ରେ, `/etc/gai.conf` ଠିକଣା ଚୟନ ପରିବର୍ତ୍ତନ କରିପାରେ।
ବର୍ତ୍ତମାନର ରିପୋଜିଟୋରି Dockerfile, Debian ବ୍ୟବହାର କରେ; କଷ୍ଟମ୍ musl-ଆଧାରିତ
ଇମେଜ୍ଗୁଡ଼ିକ ଏହି ପ୍ରଣାଳୀ ବ୍ୟବହାର କରନ୍ତି ନାହିଁ। ରିପୋର୍ଟ କରାଯାଇଥିବା
ସମାଯୋଜନ ULA ଲେବଲ୍କୁ `label fc00::/7 6`ରୁ `label fc00::/7 1`କୁ ପରିବର୍ତ୍ତନ
କରେ। ଇମେଜ୍ର ସମ୍ପୂର୍ଣ୍ଣ ନୀତି ଟେବୁଲ୍ରୁ ଆରମ୍ଭ କରନ୍ତୁ ଏବଂ ଏହାର ଅନ୍ୟ
ଏଣ୍ଟ୍ରିଗୁଡ଼ିକୁ ସଂରକ୍ଷିତ ରଖନ୍ତୁ: ଏକ `label` କିମ୍ବା `precedence` ଏଣ୍ଟ୍ରି
ଯୋଗ କଲେ ସେହି ଡିଫଲ୍ଟ ଟେବୁଲ୍ ପ୍ରତିସ୍ଥାପିତ ହୁଏ, ତେଣୁ କେବଳ ପରିବର୍ତ୍ତିତ ଲାଇନ୍
ଥିବା ଫାଇଲ୍ ପର୍ଯ୍ୟାପ୍ତ ନୁହେଁ।
[glibc ବିନ୍ୟାସ ସନ୍ଦର୍ଭ](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
ସେହି ଅର୍ଥବିଧିଗୁଡ଼ିକୁ ଦଲିଲଭୁକ୍ତ କରେ। ସମୀକ୍ଷା କରାଯାଇଥିବା ଫାଇଲ୍କୁ
`/etc/gai.conf`ରେ କେବଳ-ପଠନୀୟ ଭାବରେ ବାଇଣ୍ଡ-ମାଉଣ୍ଟ କରନ୍ତୁ ଏବଂ ଏହାକୁ
ପ୍ରୟୋଗ କରିବା ପାଇଁ ସର୍ଭିସ୍ଟି ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ।

ଏହା **ସେହି କଣ୍ଟେନର୍ର ସମସ୍ତ ଆଉଟବାଉଣ୍ଡ ଟ୍ରାଫିକ୍** ପାଇଁ OS ଠିକଣା ଚୟନକୁ
ପରିବର୍ତ୍ତନ କରେ। ଏହା ପ୍ରତ୍ୟେକ ଆପ୍ଲିକେସନ୍କୁ IPv6 ଚୟନ କରିବାକୁ ବାଧ୍ୟ କରେ
ନାହିଁ: Nodeର DNS କ୍ରମ ଏବଂ ସଂଯୋଗ ଚୟନ ମଧ୍ୟ ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ। ବିଶେଷତଃ,
`--dns-result-order=ipv4first` IPv4କୁ ପ୍ରାଧାନ୍ୟ ଦିଏ ଏବଂ ଏକ କେବଳ-IPv4
ବିଫଳତାର ପ୍ରତିକାର ନୁହେଁ। [Node DNS କ୍ରମ](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) ଦେଖନ୍ତୁ।

ଯେକୌଣସି ହୋଷ୍ଟ-ସ୍ତରୀୟ ପରିବର୍ତ୍ତନ ପରେ Gemini ଏବଂ ଆପଣଙ୍କ ଅନ୍ୟ
ପ୍ରଦାନକାରୀମାନଙ୍କୁ ପୁନଃପରୀକ୍ଷା କରନ୍ତୁ। ପଛକୁ ଫେରାଇବା ପାଇଁ, କଷ୍ଟମ୍
`gai.conf` ମାଉଣ୍ଟକୁ ହଟାନ୍ତୁ, ପୂର୍ବ ନେଟୱର୍କ ବିନ୍ୟାସ ପୁନଃସ୍ଥାପନ କରନ୍ତୁ
ଏବଂ ଏକ ରକ୍ଷଣାବେକ୍ଷଣ ସମୟସୀମା ମଧ୍ୟରେ ପ୍ରଭାବିତ ସର୍ଭିସ୍/ନେଟୱର୍କକୁ
ପୁନଃସୃଷ୍ଟି କରନ୍ତୁ। ଏକ ନେଟୱର୍କ ପୁନଃସୃଷ୍ଟି କରିବା ଏଥିରେ ସଂଲଗ୍ନ ଅନ୍ୟ
କଣ୍ଟେନର୍ଗୁଡ଼ିକୁ ବାଧା ଦେଇପାରେ; ସ୍ଥାୟୀ ଡାଟା ଭଲ୍ୟୁମ୍କୁ ଡିଲିଟ୍ କରନ୍ତୁ ନାହିଁ।

## ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ଟିପ୍ପଣୀ

- **SQLite WAL ମୋଡ୍:** `docker stop`କୁ ସମ୍ପୂର୍ଣ୍ଣ ହେବା ପାଇଁ ସମୟ ଦିଆଯିବା ଉଚିତ, ଯାହାଦ୍ୱାରା OmniRoute ସର୍ବଶେଷ ପରିବର୍ତ୍ତନଗୁଡ଼ିକୁ `storage.sqlite`ରେ ଚେକପଏଣ୍ଟ କରିପାରିବ। ସହିତ ଦିଆଯାଇଥିବା Compose ଫାଇଲ୍ଗୁଡ଼ିକରେ ପୂର୍ବରୁ 40s ର ଷ୍ଟପ୍ ଗ୍ରେସ୍ ପିରିୟଡ୍ ସେଟ୍ କରାଯାଇଛି। ଯଦି ଆପଣ ଇମେଜ୍କୁ ସିଧାସଳଖ ଚଲାନ୍ତି, ତେବେ `--stop-timeout 40` ରଖନ୍ତୁ।
- **`DISABLE_SQLITE_AUTO_BACKUP`:** ଯଦି ନିୟମିତ/ପୂର୍ବ-ଲେଖନ ବ୍ୟାକଅପ୍ଗୁଡ଼ିକ ବାହ୍ୟ ଭାବେ ପରିଚାଳିତ ହୁଏ, ତେବେ ଏହାକୁ `true` ସେଟ୍ କରନ୍ତୁ। ବିଦ୍ୟମାନ ଡାଟାବେସ୍ ମାଇଗ୍ରେସନ୍ଗୁଡ଼ିକ ପାଇଁ ତଥାପି ସେମାନଙ୍କର ନିଜସ୍ୱ ସ୍ଥାୟୀ ସୁରକ୍ଷା ସ୍ନାପ୍ଶଟ୍ ଏବଂ ବ୍ୟାପକ ମାଇଗ୍ରେସନ୍ ସୁରକ୍ଷା ଆବଶ୍ୟକ।
- **ଡାଟା ସ୍ଥାୟୀତ୍ୱ:** କଣ୍ଟେନର୍ ପୁନଃଚାଳନ ମଧ୍ୟରେ ଆପଣଙ୍କ ଡାଟାବେସ୍, କୀ ଏବଂ ବିନ୍ୟାସଗୁଡ଼ିକୁ ସ୍ଥାୟୀ ରଖିବା ପାଇଁ ସର୍ବଦା `/app/data`ରେ ଏକ ଭଲ୍ୟୁମ୍ ମାଉଣ୍ଟ କରନ୍ତୁ।
- **ପୋର୍ଟ ବିନ୍ୟାସ:** ଡିଫଲ୍ଟ `20128` ପୋର୍ଟ ପରିବର୍ତ୍ତନ କରିବାକୁ `PORT` ପରିବେଶ ଭେରିଏବଲ୍କୁ ଓଭର୍ରାଇଡ୍ କରନ୍ତୁ।
