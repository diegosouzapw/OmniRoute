`open-sse/config/providerPluginManifest.ts` JSON-ସୁରକ୍ଷିତ ପ୍ରଦାନକାରୀ
ପ୍ଲଗଇନ୍ ଚୁକ୍ତିକୁ ପରିଭାଷିତ କରେ। `open-sse/config/providerPluginManifestRegistry.ts` ସେହି
ଚୁକ୍ତିକୁ Bifrost, CLIProxyAPI, କିମ୍ବା ଭବିଷ୍ୟତର କୌଣସି Go/Rust ରାଉଟର୍ ପରି ସାଇଡ୍କାର୍ଗୁଡ଼ିକ ପାଇଁ
ବର୍ତ୍ତମାନର ପ୍ରଦାନକାରୀ ରେଜିଷ୍ଟ୍ରି ସହିତ ବାନ୍ଧେ। TypeScript ରେଜିଷ୍ଟ୍ରି ସତ୍ୟର
ମୂଳ ଉତ୍ସ ଭାବେ ରହେ, କିନ୍ତୁ ସାଇଡ୍କାର୍ଗୁଡ଼ିକ executor କୋଡ୍, OAuth ଡିଫଲ୍ଟ,
ହେଡର୍, କିମ୍ବା ପ୍ରୋସେସ୍ ପରିବେଶ ସ୍ଥିତି ଇମ୍ପୋର୍ଟ ନକରି ମାନିଫେଷ୍ଟ ବ୍ୟବହାର କରିପାରିବେ।

ସେହି ମାନିଫେଷ୍ଟ HTTP ମାଧ୍ୟମରେ
`GET /api/v1/provider-plugin-manifest` ଠାରେ ମଧ୍ୟ ଉପଲବ୍ଧ, ଯାହା ଅଲଗା ପ୍ରୋସେସ୍ରେ ଚାଲୁଥିବା ସାଇଡ୍କାର୍ଗୁଡ଼ିକ ପାଇଁ ଉଦ୍ଦିଷ୍ଟ।

OmniRoute, Bifrost ଏବଂ CLIProxyAPIକୁ ସେହି URL ବିଷୟରେ
`X-OmniRoute-Provider-Manifest-Url` ଅନୁରୋଧ ହେଡର୍ ମାଧ୍ୟମରେ ଜଣାଏ। ସାଇଡ୍କାର୍କୁ ସ୍ଥାନୀୟ ଅନୁରୋଧ ଉତ୍ସ
ପରିବର୍ତ୍ତେ ଏକ ସାର୍ବଜନୀନ କିମ୍ବା କଣ୍ଟେନର୍ ନେଟୱର୍କ URL ଆବଶ୍ୟକ ହେଲେ
`OMNIROUTE_PROVIDER_MANIFEST_URL` ସେଟ୍ କରନ୍ତୁ।

## ମାନିଫେଷ୍ଟ ରିଫ୍ରେଶ୍ କରିବା

HTTP ଏଣ୍ଡପଏଣ୍ଟ `Cache-Control: public, max-age=60` ଏବଂ ଏକ ଶକ୍ତିଶାଳୀ
`ETag` ଫେରାଏ। ଏକ ସାଇଡ୍କାର୍ ଶେଷ ବୈଧୀକୃତ ମାନିଫେଷ୍ଟକୁ ରଖିବା ଉଚିତ ଏବଂ ରିଫ୍ରେଶ୍ କରିବାବେଳେ ଏହାର ETagକୁ
`If-None-Match`ରେ ପଠାଇବା ଉଚିତ। ଏକ `304 Not Modified` ପ୍ରତିକ୍ରିୟାର କୌଣସି body ନଥାଏ;
ସାଇଡ୍କାର୍ ଏହାର କ୍ୟାଶ୍ରେ ଥିବା ମାନିଫେଷ୍ଟକୁ ରଖେ। ଯଦି କୌଣସି ବୈଧୀକୃତ କ୍ୟାଶ୍କୃତ ମାନିଫେଷ୍ଟ ନଥାଏ,
ତେବେ ସାଇଡ୍କାର୍କୁ `304` ଗ୍ରହଣ କରିବା ପରିବର୍ତ୍ତେ ଏକ ସର୍ତ୍ତବିହୀନ ଅନୁରୋଧ କରିବାକୁ ପଡ଼ିବ।

## ଲକ୍ଷ୍ୟ

ପ୍ରଦାନକାରୀ ମେଟାଡାଟାକୁ ଏକ ପ୍ଲଗଇନ୍ ଚୁକ୍ତି ଦିଗରେ ନେବା, ଯାହାଫଳରେ ହଟ୍ ଅନୁରୋଧ ପଥର
ମାଲିକାନା ଶେଷରେ ଏକ କମ୍-ବିଳମ୍ବତା ବିଶିଷ୍ଟ ସାଇଡ୍କାର୍ ନେଇପାରିବ, ଯେତେବେଳେ OmniRoute
TypeScript ରୁଟ୍କୁ ନୀତି ଗେଟ୍ ଏବଂ ଫଲ୍ବ୍ୟାକ୍ ଭାବେ ରଖିବ। ମାନିଫେଷ୍ଟଟି ଯୋଗାତ୍ମକ: ଏହା
ନିଜେ ଅନୁରୋଧ ରାଉଟିଂ ପରିବର୍ତ୍ତନ କରେ ନାହିଁ।

## ଚୁକ୍ତି

ମାନିଫେଷ୍ଟରେ ରହିଛି:

- ପ୍ରଦାନକାରୀ id ଏବଂ alias
- ଅପ୍ଷ୍ଟ୍ରିମ୍ ଫର୍ମାଟ୍ ଏବଂ executor ନାମ
- auth ପ୍ରକାର, auth ହେଡର୍, ଏବଂ ଇଚ୍ଛାଧୀନ auth ଉପସର୍ଗ
- ସ୍ଥିର ଏଣ୍ଡପଏଣ୍ଟ ମେଟାଡାଟା
- ସାଇଡ୍କାର୍ ଯୋଗ୍ୟତା ଏବଂ କୌଣସି ପ୍ରଦାନକାରୀ TSରେ ରହିବା ଉଚିତ ହେଲେ ତାହାର ସ୍ପଷ୍ଟ କାରଣ
- JSON-ସୁରକ୍ଷିତ ମଡେଲ୍ ମେଟାଡାଟା, ଯେପରିକି context ଦୈର୍ଘ୍ୟ, vision/reasoning ଫ୍ଲାଗ୍, ଏବଂ
  ଅସମର୍ଥିତ params
- `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, ଏବଂ `usage-supported` ସମେତ କ୍ଷମତା ଟ୍ୟାଗ୍

ମାନିଫେଷ୍ଟ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବରେ ଏଗୁଡ଼ିକୁ ବାଦ ଦିଏ:

- OAuth କ୍ଲାଏଣ୍ଟ ସିକ୍ରେଟ୍ ଏବଂ ଡିଫଲ୍ଟ ସିକ୍ରେଟ୍ ମୂଲ୍ୟ
- ରନ୍ଟାଇମ୍ ପରିବେଶ ରିଜୋଲ୍ୟୁସନ୍
- ଅନୁରୋଧ ହେଡର୍ ଏବଂ ସାର୍ବଜନୀନ କ୍ରେଡେନ୍ସିଆଲ୍ ହେଲ୍ପର୍
- ଡାଇନାମିକ୍ URL ବିଲ୍ଡର୍
- executor ଫଙ୍କସନ୍
- ସେସନ୍ ପୁଲ୍ର ଆଭ୍ୟନ୍ତରୀଣ ବିବରଣୀ

## କ୍ଷମତା ଟ୍ୟାଗ୍

`capabilities` ହେଉଛି ରେଜିଷ୍ଟ୍ରି ଏଣ୍ଟ୍ରିରୁ ପ୍ରାପ୍ତ ଟ୍ୟାଗ୍ଗୁଡ଼ିକର ଏକ କ୍ରମବଦ୍ଧ ଆରେ। ଇଣ୍ଟିଗ୍ରେଟର୍ମାନେ
TypeScript ଉତ୍ସଗୁଡ଼ିକୁ ପୁନର୍ବାର ପଢ଼ିବା ପରିବର୍ତ୍ତେ, ଏହାକୁ "ଏହି ପ୍ରଦାନକାରୀ କ’ଣ କରିପାରିବ" ପ୍ରଶ୍ନର
ମେସିନ୍-ପଠନୀୟ ଉତ୍ତର ଭାବେ ବିବେଚନା କରିବା ଉଚିତ।

| ଟ୍ୟାଗ୍               | ଅର୍ଥ                                                                             |
| -------------------- | -------------------------------------------------------------------------------- |
| `apikey`             | ଏକ API key ଗ୍ରହଣ କରେ (`authType` ହେଉଛି `apikey` କିମ୍ବା `optional`)।              |
| `oauth`              | ଏକ OAuth କିମ୍ବା ସେସନ୍ ପ୍ରବାହ ବ୍ୟବହାର କରେ।                                        |
| `responses`          | ଏକ OpenAI Responses-API ବେସ୍ URL ପ୍ରକାଶ କରେ।                                     |
| `passthrough-models` | ସ୍ଥିର କ୍ୟାଟାଲଗ୍ ପରିବର୍ତ୍ତେ ସିଧାସଳଖ ଅପ୍ଷ୍ଟ୍ରିମ୍ରୁ ମଡେଲ୍ ପ୍ରଦାନ କରେ।               |
| `custom-executor`    | ଏକ ଅଣ-ଡିଫଲ୍ଟ executor ଚଲାଏ, ତେଣୁ ଏହା TypeScript ପଥରେ ରହେ।                        |
| `sidecar-candidate`  | `sidecar.eligible`କୁ ପ୍ରତିଫଳିତ କରେ — ସାଇଡ୍କାର୍ ଇମ୍ପୋର୍ଟ ପାଇଁ ବିଚାର କରିବା ନିରାପଦ। |
| `usage-fetch`        | ଏକ ସଂଯୋଜିତ ବ୍ୟବହାର କିମ୍ବା କୋଟା fetcher (`getUsageForProvider`) ରହିଛି।            |
| `usage-supported`    | ବ୍ୟବହାର API ଏହି ପ୍ରଦାନକାରୀକୁ ଗ୍ରହଣ କରେ (`isSupportedUsageConnection`)।           |

`usage-fetch` କେବଳ ଆବିଷ୍କାର ପାଇଁ। ଏହା ଜଣାଏ ଯେ OmniRoute ପ୍ରଦାନକାରୀ ପାଇଁ ବ୍ୟବହାର
କିପରି ପଢ଼ିବାକୁ ଜାଣେ; ଏହା fetching ସକ୍ରିୟ କରେ ନାହିଁ, କୋଟାର ଅର୍ଥବିଜ୍ଞାନ ପରିବର୍ତ୍ତନ କରେ ନାହିଁ, କିମ୍ବା
ପ୍ରଦାନକାରୀ ପାଇଁ Dashboard କୋଟା widget ସକ୍ଷମ ଥିବା ସୂଚିତ କରେ ନାହିଁ — ସେହି widgetକୁ
`USAGE_SUPPORTED_PROVIDERS` ଦ୍ୱାରା ପୃଥକ ଭାବେ ଗେଟ୍ କରାଯାଏ। ସତ୍ୟର ମୂଳ ଉତ୍ସ ହେଉଛି
`open-sse/services/usage/fetcherProviders.ts`ରେ ଥିବା `USAGE_FETCHER_PROVIDERS`।

ସେହି ତାଲିକା ବ୍ୟବହାର dispatcher ଗ୍ରହଣ କରୁଥିବା ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକ ଦ୍ୱାରା key କରାଯାଇଛି, ତେଣୁ ଏଥିରେ canonical ids

## Sidecar ବ୍ୟବହାର

Sidecarଗୁଡ଼ିକ `sidecar.eligible`କୁ ଏକ ନିଃସର୍ତ୍ତ routing ନିଷ୍ପତ୍ତି ଭାବେ ନୁହେଁ, ବରଂ ଏକ ସତର୍କତାମୂଳକ candidate signal ଭାବେ ବିବେଚନା କରିବା ଉଚିତ। ପ୍ରଥମ import target ହେବା ଉଚିତ default executor ବ୍ୟବହାର କରୁଥିବା API-key, static-endpoint providerଗୁଡ଼ିକ। custom web executor, OAuth/session flow, dynamic URL builder, କିମ୍ବା pool config ଥିବା providerଗୁଡ଼ିକ TypeScript fallback pathରେ ରହିବେ, ଯେପର୍ଯ୍ୟନ୍ତ କୌଣସି sidecar ସମତୁଲ୍ୟ ଆଚରଣ implement ନକରେ ଏବଂ telemetry ସମତୁଲ୍ୟତା ପ୍ରମାଣ ନକରେ।

ପ୍ରସ୍ତାବିତ migration ପର୍ଯ୍ୟାୟଗୁଡ଼ିକ:

1. TS registryରୁ provider plugin manifest generate ଏବଂ validate କରନ୍ତୁ।
2. API-key/static providerଗୁଡ଼ିକ ପାଇଁ manifest import କରିବାକୁ Bifrost କିମ୍ବା CLIProxyAPIକୁ ସକ୍ଷମ କରନ୍ତୁ।
3. TS fallback ସକ୍ଷମ ରଖି `OMNIROUTE_RELAY_BACKEND` ପଛରେ sidecar ମାଧ୍ୟମରେ ଯୋଗ୍ୟ providerଗୁଡ଼ିକୁ route କରନ୍ତୁ।
4. success rate, p99 latency, streaming ଆଚରଣ ଏବଂ unsupported-param ପରିଚାଳନା TS path ସହିତ ମେଳ ଖାଇଲେ ହିଁ providerଗୁଡ଼ିକୁ promote କରନ୍ତୁ।
5. custom executorଗୁଡ଼ିକ ପାଇଁ ଏକ ସମୟରେ ଗୋଟିଏ provider family ନିମନ୍ତେ sidecar-native plugin ଯୋଡ଼ନ୍ତୁ।
