> ଦୁଇଟି ନୂତନ `auto/*` id — `auto/subscription` ଏବଂ `auto/thrifty`। ଉଭୟକୁ ଅନୁରୋଧ କରିବା ଦ୍ୱାରା ଚୟନ କରାଯାଏ:
> କୌଣସି କଲର୍ ନାମ ଦ୍ୱାରା id ନ ମାଗିଲେ କିଛି ମଧ୍ୟ ସେଗୁଡ଼ିକ ମାଧ୍ୟମରେ ରାଉଟ୍ ହୁଏ ନାହିଁ, ଏବଂ କୌଣସି
> ବିଦ୍ୟମାନ ପୁଲ୍, କୌଶଳ କିମ୍ବା ଡିଫଲ୍ଟ ପରିବର୍ତ୍ତନ ହୁଏ ନାହିଁ।

## ଏହା କାହିଁକି ରହିଛି

OmniRoute ପୂର୍ବରୁ ଦୁଇଟି ଖର୍ଚ୍ଚ-ସମ୍ବନ୍ଧୀୟ ପ୍ରଶ୍ନର ଉତ୍ତର ଦିଏ, କିନ୍ତୁ ଅଧିକାଂଶ ଅପରେଟର୍ ପଚାରୁଥିବା ପ୍ରଶ୍ନ ସେଗୁଡ଼ିକ ମଧ୍ୟରୁ କୌଣସିଟି ନୁହେଁ।

| ବିଦ୍ୟମାନ ବ୍ୟବସ୍ଥା                                        | ଯାହାର ଉତ୍ତର ଦିଏ                                           |
| -------------------------------------------------------- | --------------------------------------------------------- |
| `hidePaidModels` (`autoCombo/paidModelFilter.ts`)        | "ଏହି ମଡେଲ୍ଟି କ୍ୟାଟାଲଗ୍ରେ ମାଗଣା ଭାବେ ତାଲିକାଭୁକ୍ତ କି?"      |
| `freeAccessPolicy: "strict"` (`strictZeroCostFilter.ts`) | "ଏହି କନେକ୍ସନ୍ କେବେ ମୋତେ ବିଲ୍ କରିପାରିବ କି?"                |
| `quotaPreflight` (`combo/quotaExhaustionCutoff.ts`)      | "ଏହି କନେକ୍ସନ୍ ତାହାର ସୀମା ନିକଟରେ ଅଛି କି?"                  |
| `budgetCap` / `budgetFallback` (`autoCombo/engine.ts`)   | "ଖର୍ଚ୍ଚ ସୀମିତ କରନ୍ତୁ, ସବୁଠାରୁ ଶସ୍ତା ବିକଳ୍ପକୁ ଅବନତ କରନ୍ତୁ" |

ପ୍ରତ୍ୟେକ କେବଳ-ମାଗଣା ବ୍ୟବସ୍ଥା **ବନ୍ଦ ଅବସ୍ଥାରେ ବିଫଳ ହୁଏ** — ନିଃଶେଷ ହୋଇଥିବା ମାଗଣା ପୁଲ୍ ହେଉଛି ଏକ ଖାଲି ପୁଲ୍, କେବେ ମଧ୍ୟ
କୌଣସି ଶୁଳ୍କଯୁକ୍ତ ବିକଳ୍ପକୁ ଉନ୍ନୀତ ହୁଏ ନାହିଁ — ଏବଂ ପ୍ରତ୍ୟେକ ଶୁଳ୍କଯୁକ୍ତ-ପକ୍ଷ ବ୍ୟବସ୍ଥା ସ୍ତର-ନିରପେକ୍ଷ। କୌଣସିଟି ମଧ୍ୟ ଏହାର ଉତ୍ତର ଦିଏ ନାହିଁ:

> "ମୁଁ ଯେଉଁ କୋଟା ପାଇଁ ପୂର୍ବରୁ ଦେୟ ଦେଉଛି, ତାହା ବ୍ୟବହାର କରନ୍ତୁ। ଏହା ଶେଷ ହେଲେ, ହୁଏତ ବନ୍ଦ କରନ୍ତୁ, କିମ୍ବା
> ସବୁଠାରୁ ଶସ୍ତା ଶୁଳ୍କଯୁକ୍ତ ବିକଳ୍ପଗୁଡ଼ିକ ମଧ୍ୟରେ ଗୋଟିଏ ଲେଖାଏଁ ସ୍ତର ଉପରକୁ ଯାଆନ୍ତୁ — ଏବଂ ଏହା ରିସେଟ୍ ହେବା ମାତ୍ରେ ଫେରିଆସନ୍ତୁ।"

## ବିଲିଂ ହେଉଛି କନେକ୍ସନ୍ର ଏକ ତଥ୍ୟ, ମଡେଲ୍ର ନୁହେଁ

`classifyTier()` (`open-sse/services/tierResolver.ts`) `(provider, model)` ଉପରେ ଆଧାରିତ ହୋଇ କ୍ୟାଟାଲଗ୍ ମୂଲ୍ୟରୁ
`free | cheap | premium` ଫେରାଏ। କିନ୍ତୁ ଗୋଟିଏ ଅନୁରୋଧ ପାଇଁ ଅତିରିକ୍ତ ଟଙ୍କା ଖର୍ଚ୍ଚ ହେବ କି ନାହିଁ,
ତାହା **କେଉଁ କନେକ୍ସନ୍ ଏହାକୁ ସେବା ଦେଉଛି** ତାହା ଉପରେ ନିର୍ଭର କରେ: ସମାନ ମଡେଲ୍ଟି Claude Code
OAuth କନେକ୍ସନ୍ ମାଧ୍ୟମରେ ପ୍ଲାନ୍ରେ ଅନ୍ତର୍ଭୁକ୍ତ ହୋଇପାରେ ଏବଂ API-key କନେକ୍ସନ୍ ମାଧ୍ୟମରେ ପ୍ରତି ଟୋକନ୍ ଅନୁଯାୟୀ ବିଲ୍ ହୋଇପାରେ।

`provider_connections.auth_type` କୌଣସି ଦିଗରେ ମଧ୍ୟ ଏକ ସୁରକ୍ଷିତ ପ୍ରତିନିଧି ନୁହେଁ — ମିଟର୍ ହୋଇଥିବା OAuth
କନେକ୍ସନ୍ ରହିଛି, ଏବଂ ପ୍ଲାନ୍ରେ ଅନ୍ତର୍ଭୁକ୍ତ API-key କନେକ୍ସନ୍ ମଧ୍ୟ ରହିଛି (Copilot ସିଟ୍ ଟୋକନ୍ ଏକ
ମିଟର୍ ହୋଇଥିବା API key ନୁହେଁ)। ତେଣୁ ବିଲିଂ ଶ୍ରେଣୀ ଏକ **ଚୟନିତ କ୍ୟାଟାଲଗ୍**,
`open-sse/config/connectionBillingCatalog.ts` ରୁ ଆସେ, ଯାହା ପ୍ରତ୍ୟେକ ପ୍ରଦାନକାରୀଙ୍କ ପ୍ରକାଶିତ ସର୍ତ୍ତ ଅନୁଯାୟୀ ହସ୍ତଚାଳିତ ଭାବେ ସେଟ୍ କରାଯାଇଛି —
ଏହା ସେହି ପ୍ରତିରୂପ ଯାହା `FreeModelBudget.hardStopGuaranteed` ପୂର୍ବରୁ ମାଗଣା ମଡେଲ୍ଗୁଡ଼ିକ ପାଇଁ ସ୍ଥାପନ କରିସାରିଛି।

```ts
type ConnectionBillingClass = "subscription" | "metered" | "keyless" | "unknown";
type ConnectionOverageBehavior = "hard-stop" | "meters-to-paid" | "unknown";
```

ସମାଧାନ କ୍ରମ (`autoCombo/connectionBilling.ts`): କୃତ୍ରିମ no-auth ସେଣ୍ଟିନେଲ୍ →
`keyless`; ପ୍ରଦାନକାରୀ **ଏବଂ** `authType` ଉଭୟ ସହ ମେଳ ଖାଉଥିବା ଏକ କ୍ୟାଟାଲଗ୍ ଏଣ୍ଟ୍ରି; ଏକ ପ୍ରଦାନକାରୀ-ବ୍ୟାପୀ ଏଣ୍ଟ୍ରି;
ଅନ୍ୟଥା `unknown`। **କ୍ୟୁରେଟ୍ ହୋଇନଥିବା ମାନେ ମାଗଣା ନୁହେଁ** — ସବୁଠାରେ `unknown` କୁ `metered`
ଭାବେ ବ୍ୟବହାର କରାଯାଏ, ତେଣୁ ଆସନ୍ତାକାଲି ଯୋଡ଼ାଯାଇଥିବା କୌଣସି ପ୍ରଦାନକାରୀ subscription ସ୍ତର ବାହାରୁ ଆରମ୍ଭ କରେ ଏବଂ ତାହାକୁ
ସଚେତନ ଭାବେ କ୍ୟୁରେଟ୍ କରିବାକୁ ପଡ଼େ।

## ସ୍ତର ମଡେଲ୍

ଉନ୍ନତି କ୍ରମରେ ପାଞ୍ଚଟି ସ୍ତର। ସେଗୁଡ଼ିକ କେବଳ ମୂଲ୍ୟରେ ନୁହେଁ, ଅଧିକ କିଛିରେ ଭିନ୍ନ — ପ୍ରତ୍ୟେକର **ନିଜସ୍ୱ**
ନିଃଶେଷ ସଙ୍କେତ ରହିଛି, ଏହି କାରଣରୁ ଏହା କେବଳ ଏକ ସଜାଇବା ପ୍ରକ୍ରିୟା ନୁହେଁ।

| #   | ସ୍ତର           | ସଦସ୍ୟତା                                                | ଯେତେବେଳେ ନିଃଶେଷ ହୁଏ              |
| --- | -------------- | ------------------------------------------------------ | -------------------------------- |
| 0   | `subscription` | କ୍ୟୁରେଟ୍ କରାଯାଇଥିବା `billing: "subscription"`          | କୋଟା ୱିଣ୍ଡୋ cutoff ଠାରେ/ତଳେ ଥିଲେ |
| 1   | `keyless`      | କୃତ୍ରିମ no-auth ପଥ                                     | କନେକ୍ସନ୍ cooldown / breaker      |
| 2   | `free`         | ମିଟର୍ ହୋଇଥିବା କନେକ୍ସନ୍, `classifyTier() === "free"`    | ମାଗଣା ଭତ୍ତା ନିଃଶେଷ ହେଲେ          |
| 3   | `cheap`        | ମିଟର୍ ହୋଇଥିବା କନେକ୍ସନ୍, `classifyTier() === "cheap"`   | ପ୍ରତି-ସ୍ତର ବଜେଟ୍ ବ୍ୟୟ ହୋଇଗଲେ     |
| 4   | `premium`      | ମିଟର୍ ହୋଇଥିବା କନେକ୍ସନ୍, `classifyTier() === "premium"` | ପ୍ରତି-ସ୍ତର ବଜେଟ୍ ବ୍ୟୟ ହୋଇଗଲେ     |

ସ୍ତର 0-2 **କୋଟା** ଆଧାରରେ ନିଃଶେଷ ହୁଏ, ଯାହା ପର୍ଯ୍ୟବେକ୍ଷଣଯୋଗ୍ୟ ଏବଂ ପୂର୍ବରୁ ଟ୍ରାକ୍ କରାଯାଉଛି। ସ୍ତର 3-4 ରେ କୌଣସି
କୋଟା ନାହିଁ — ଏକ ଶୁଳ୍କଯୁକ୍ତ କନେକ୍ସନ୍ ସଦାକାଳ ସେବା ଯୋଗାଇପାରେ — ତେଣୁ ସେଗୁଡ଼ିକର ଏକମାତ୍ର ଯୁକ୍ତିସଙ୍ଗତ ନିଃଶେଷ ସଙ୍କେତ ହେଉଛି ପ୍ରତି-ସ୍ତର
**ବଜେଟ୍**। ଏହା ବିନା, "ଶସ୍ତା ସ୍ତର ନିଃଶେଷ ହେଲେ ଉନ୍ନୀତ କରନ୍ତୁ" ପାଇଁ କୌଣସି ଟ୍ରିଗର୍ ନାହିଁ।

## `auto/subscription` — ବନ୍ଦ ଅବସ୍ଥାରେ ବିଫଳ ହୁଅନ୍ତୁ

ପୁଲ୍ = କେବଳ rung 0, ସେହି ସଂଯୋଗଗୁଡ଼ିକ ମଧ୍ୟରେ ସୀମିତ ଯାହାର overage ଏକ ଡକ୍ୟୁମେଣ୍ଟ ହୋଇଥିବା `hard-stop`, ଏବଂ ପ୍ରତ୍ୟେକଟିରେ କୋଟାରେ ଅତିରିକ୍ତ ସ୍ଥାନ ଥିବା କଥା ଲାଇଭ୍ ଭାବେ ଯାଞ୍ଚ କରାଯାଇଛି। ସମସ୍ତ ଅସ୍ପଷ୍ଟ ବିଷୟ ବାଦ ଦିଆଯାଏ: କ୍ୟୁରେଟ୍ ହୋଇନଥିବା ପ୍ରଦାତା, ଯାଞ୍ଚ କରିହେଉନଥିବା କୋଟା ରିଡିଂ, ପୁରୁଣା ରିଡିଂ, କିମ୍ବା ଶୁଳ୍କଯୁକ୍ତ ବ୍ୟବହାର ଭାବେ ମିଟର୍ ହେଉଥିବା overage।

ଏକ ଖାଲି ପୁଲ୍ କୌଣସି ତ୍ରୁଟି ନୁହେଁ, ବରଂ **ଉଦ୍ଦିଷ୍ଟ** ଉତ୍ତର — କଲର୍ର ବିଦ୍ୟମାନ ଖାଲି-ପୁଲ୍ ପଥ ଏହାକୁ ଏକ ନିରବ, ଶୁଳ୍କଯୋଗ୍ୟ fallback ପରିବର୍ତ୍ତେ ଏକ ସ୍ପଷ୍ଟ ତ୍ରୁଟିରେ ପରିଣତ କରେ। ଏହାହିଁ ଏହି id-ର ସମ୍ପୂର୍ଣ୍ଣ ପ୍ରତିଶ୍ରୁତି।

`keyless` ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ ଯୋଗ୍ୟ **ନୁହେଁ**: ଏହି ଗ୍ରୁପିଂର ଅର୍ଥ ହେଉଛି "ମୁଁ ଯେଉଁ ପ୍ଲାନ୍ ପାଇଁ ଦେୟ ଦିଏ", ତେଣୁ ଏକ no-auth backend ଏଥିରେ ଅନ୍ତର୍ଭୁକ୍ତ ନୁହେଁ। ଏଥିପାଇଁ `auto/thrifty` (କିମ୍ବା `auto/best-free`) ବ୍ୟବହାର କରନ୍ତୁ।

### ସଂଯୋଗ ସୁରକ୍ଷା

ଏକ ପ୍ରାର୍ଥୀ ସବୁବେଳେ ଗୋଟିଏ ସଂଯୋଗ ସହ ବନ୍ଧା ନଥାଏ — ଏକ ଲଜିକାଲ୍ ପ୍ରାର୍ଥୀ ଗୋଟିଏ `allowedConnectionIds` ଅନୁମୋଦନ-ତାଲିକା ବହନ କରେ, ଏବଂ ପ୍ରକୃତରେ ବ୍ୟବହୃତ ଆକାଉଣ୍ଟ ପରେ dispatch ସମୟରେ `open-sse/services/combo/autoStrategy.ts` ଦ୍ୱାରା ବାଛାଯାଏ। ତେଣୁ ଉଭୟ ଗ୍ରୁପିଂ **ପ୍ରତ୍ୟେକ ସଂଯୋଗକୁ ପୃଥକ ଭାବେ** ଯାଞ୍ଚ କରନ୍ତି ଏବଂ `allowedConnectionIds`-କୁ ପୁନଃଲେଖି କେବଳ ଟିକି ରହିଥିବା ଉପସେଟ୍ରେ ସୀମିତ କରନ୍ତି — କେବେ ମଧ୍ୟ ସମ୍ପୂର୍ଣ୍ଣ ମୂଳ ତାଲିକା ନୁହେଁ, କିମ୍ବା ଇଚ୍ଛାମତେ ବାଛାଯାଇଥିବା ଗୋଟିଏ ସଦସ୍ୟ ନୁହେଁ। ଯେହେତୁ `autoStrategy.ts` ପୂର୍ବରୁ ସେହି array-କୁ ଏକ କଠୋର ଅନୁମୋଦନ-ତାଲିକା ଭାବେ ପ୍ରୟୋଗ କରେ, ଏଠାରେ ଏହାକୁ ପୁନଃଲେଖିବା ଦ୍ୱାରା "ଯାଞ୍ଚ ହୋଇଥିବା" ଏବଂ "ପ୍ରକୃତରେ ବ୍ୟବହୃତ" ସେଟ୍କୁ ନିର୍ମାଣଗତ ଭାବେ ସମାନ କରାଯାଏ। ଏହା [STRICT_ZERO_COST](./STRICT_ZERO_COST.md)-ର ସମାନ ଅପରିବର୍ତ୍ତନୀୟ ନିୟମ ଏବଂ ସମାନ ଯୁକ୍ତି।

## `auto/thrifty` — ଏକ ସମୟରେ ଗୋଟିଏ rung ଉପରକୁ ଯାଆନ୍ତୁ

ପୁଲ୍ = rung ସୂଚକାଙ୍କ ଅନୁଯାୟୀ କ୍ରମବଦ୍ଧ ସମସ୍ତ rung, ଯେଉଁଥିରେ ଶେଷ ହୋଇଯାଇଥିବା ପ୍ରାର୍ଥୀମାନଙ୍କୁ ବାଦ ଦିଆଯାଏ। `auto` ଇଞ୍ଜିନ୍ ଟିକି ରହିଥିବା ପୁଲ୍ର **ଭିତରେ** ତଥାପି ସ୍କୋର୍ କରେ: କେଉଁ rung-ଗୁଡ଼ିକ ସକ୍ରିୟ ରହିବେ ତାହା ladder ନିର୍ଦ୍ଧାରଣ କରେ, ଏବଂ ସେଗୁଡ଼ିକ ଭିତରେ କେଉଁ ପ୍ରାର୍ଥୀ ବିଜୟୀ ହେବେ ତାହା scoring ନିର୍ଦ୍ଧାରଣ କରେ। ଗୋଟିଏ rung ଭିତରେ କ୍ରମ ସ୍ଥିର ରହେ, ତେଣୁ ଏହି overlay ଦ୍ୱାରା scorer-ର ନିଜସ୍ୱ ranking କେବେ ମଧ୍ୟ ପୁନଃକ୍ରମିତ ହୁଏନାହିଁ।

ଏହା ଏକ କ୍ରମବିନ୍ୟାସ + gating overlay, ଏକ ନୂତନ dispatcher **ନୁହେଁ**: `combo.ts`-ର speculative loop ପୂର୍ବରୁ ଲକ୍ଷ୍ୟଗୁଡ଼ିକୁ କ୍ରମାନୁସାରେ ଅତିକ୍ରମ କରେ ଏବଂ ବିଫଳତାରେ ପରବର୍ତ୍ତୀ ଲକ୍ଷ୍ୟକୁ ଯାଏ, ତେଣୁ preflight ଧରିପାରିନଥିବା ଏକ runtime exhaustion ତଥାପି ସେହି ଅନୁରୋଧ ମଧ୍ୟରେ ପରବର୍ତ୍ତୀ rung-କୁ ନେଇଯାଏ।

ଯେଉଁଠାରେ `auto/subscription` ବନ୍ଦ ଅବସ୍ଥାରେ ବିଫଳ ହୁଏ, `auto/thrifty` **ଖୋଲା** ଅବସ୍ଥାରେ ବିଫଳ ହୁଏ: ବ୍ୟବହାରଯୋଗ୍ୟ କୋଟା ରିଡିଂ ନଥିବା ପ୍ଲାନ୍ରେ-ଅନ୍ତର୍ଭୁକ୍ତ ଏକ ସଂଯୋଗକୁ ତଥାପି ପ୍ରଥମେ ଚେଷ୍ଟା କରାଯାଏ। ଏହାକୁ ଚେଷ୍ଟା କରିବାରେ କିଛି ଖର୍ଚ୍ଚ ହୁଏନାହିଁ, ଏବଂ ଯଦି ଏହା ଶେଷ ହୋଇଯାଇଥିବା ଜଣାପଡ଼େ, ତେବେ fall-through ଯେକୌଣସି ପରିସ୍ଥିତିରେ ପରବର୍ତ୍ତୀ rung-କୁ ପହଞ୍ଚେ — ଅନ୍ୟପକ୍ଷରେ, ଏହାକୁ ଚେଷ୍ଟା କରିବାକୁ ମନା କଲେ telemetry ଅନୁପସ୍ଥିତ ଥିବା ସମୟରେ ଅନୁରୋଧଟି ଏକ ଶୁଳ୍କଯୁକ୍ତ rung-କୁ ପଠାଯିବ, ଯାହା ଏଡ଼ାଇବା ପାଇଁ ଏହି ଗ୍ରୁପିଂ ରହିଛି।

## ରିସେଟ୍ ପରେ ପ୍ଲାନ୍କୁ ଫେରିବା

ରାଉଟିଂ rung 0-କୁ ଫେରିବା ପୂର୍ବରୁ ତିନୋଟି ସ୍ୱାଧୀନ ବିଷୟର ମିଆଦ ଶେଷ ହେବା ଆବଶ୍ୟକ। କେବଳ ଗୋଟିଏକୁ ସୁଧାରିଲେ, ପ୍ଲାନ୍ ପୁନଃପୂରଣ ହେବାର ବହୁ ସମୟ ପର୍ଯ୍ୟନ୍ତ ladder ଶୁଳ୍କଯୁକ୍ତ rung-ଗୁଡ଼ିକରେ ଅଟକି ରହିବ।

1. **କୋଟା-ସ୍ଥିତି cache** — `freeAccessQuota.ts` ପ୍ରତ୍ୟେକ `(provider, connection)` ପାଇଁ 180s TTL ସହ cache କରେ। ଯେଉଁ cached entry-ର ନିଜସ୍ୱ `resetAt` ପୂର୍ବରୁ ଅତିକ୍ରମ କରିସାରିଛି, ତାହା ଆଉ ଅବସ୍ଥିତ ନଥିବା ଏକ window-କୁ ବର୍ଣ୍ଣନା କରେ; ତେଣୁ ବୟସ **ନିର୍ବିଶେଷରେ** ଏହାକୁ ବର୍ତ୍ତମାନ ପୁରୁଣା ବୋଲି ଧରାଯାଏ ଏବଂ ଏକ refresh ବାଧ୍ୟତାମୂଳକ କରାଯାଏ। ଏହା ବିନା, ମଧ୍ୟରାତ୍ରିରେ ପୁନଃପୂରଣ ହୋଇଥିବା ଏକ ପ୍ଲାନ୍ TTL-ର ମିଆଦ ଶେଷ ହେବା ପର୍ଯ୍ୟନ୍ତ ଶେଷ ହୋଇଯାଇଛି ବୋଲି ଦେଖାଉଥାଏ।
2. **ladder-ର ନିଜସ୍ୱ ସ୍ଥିତି** — ଡିଜାଇନ୍ ଅନୁଯାୟୀ ଏପରି କୌଣସି ସ୍ଥିତି ନାହିଁ। ପ୍ରତ୍ୟେକ ପୁଲ୍ ନିର୍ମାଣ ସମୟରେ ଲାଇଭ୍ କୋଟା ସ୍ଥିତିରୁ rung ଯୋଗ୍ୟତା ପୁନଃଗଣନା କରାଯାଏ; ଏପରି କୌଣସି ସଞ୍ଚିତ "currently on rung 3" ରେକର୍ଡ ନାହିଁ ଯାହା ଏକ ରିସେଟ୍ ପରେ ମଧ୍ୟ ରହି ରାଉଟିଂକୁ ଅଟକାଇପାରେ।
3. **ସଂଯୋଗ cooldown** — କୋଟା ଶେଷ କରୁଥିବା 429, exponential backoff-ରୁ `rateLimitedUntil` ସେଟ୍ କରେ, ଯାହା ଏକ ପ୍ଲାନ୍ ସଂଯୋଗ ପାଇଁ ପ୍ରକୃତ ରିସେଟ୍ ସମୟକୁ ଅତିକ୍ରମ କରିପାରେ। `clampCooldownToReset()` (`subscriptionLadder.ts`) ଏକ cooldown-କୁ upstream-ର ନିଜସ୍ୱ ରିସେଟ୍ ମୁହୂର୍ତ୍ତ ପର୍ଯ୍ୟନ୍ତ ସଂକୁଚିତ କରେ ଏବଂ କେବେ ମଧ୍ୟ ଏହାକୁ ବଢ଼ାଇପାରେ ନାହିଁ। **ଏହା କାର୍ଯ୍ୟକାରୀ ଏବଂ ପରୀକ୍ଷିତ ହୋଇଛି, କିନ୍ତୁ ଏପର୍ଯ୍ୟନ୍ତ ସଂଯୁକ୍ତ ହୋଇନାହିଁ**: `src/sse/services/auth.ts`-ରେ କୌଣସି cooldown ଲେଖାଯିବା _ପୂର୍ବରୁ_ କୋଟା cache ଅବୈଧ କରାଯାଏ, ତେଣୁ ସେହି function-ରେ `resetAt`-କୁ ଆଗରୁ ଧରି ରଖିବା ଆବଶ୍ୟକ — ଏହା resilience hot path-ର ଏକ ପରିବର୍ତ୍ତନ, ଯାହା ନିଜସ୍ୱ ସମୀକ୍ଷିତ PR-ରେ ରହିବା ଉଚିତ। ସେପର୍ଯ୍ୟନ୍ତ, ପୁନଃପ୍ରବେଶ ସଂଯୋଗ cooldown ଶେଷ ହେବା ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରେ (ପ୍ରଦାତା upstream `Retry-After` ସଙ୍କେତ ପଠାଇଲେ, ଏହା ପୂର୍ବରୁ ସେଗୁଡ଼ିକୁ ପ୍ରାଧାନ୍ୟ ଦିଏ)।

### ଦ୍ରୁତ ପୁନଃପରିବର୍ତ୍ତନ-ବିରୋଧୀ ବ୍ୟବସ୍ଥା

ସଦ୍ୟ ରିସେଟ୍ ହୋଇଥିବା ଏକ rung-କୁ କେବଳ `reentryMinRemainingPercent` (ଡିଫଲ୍ଟ 5)-ଠାରୁ ଅଧିକ ହେଲେ ପୁନଃସ୍ୱୀକୃତି ଦିଆଯାଏ, ଯେତେବେଳେ ପୂର୍ବରୁ ସକ୍ରିୟ ଥିବା ଏକ ସଂଯୋଗକୁ କେବଳ `exitCutoffPercent` (ଡିଫଲ୍ଟ 2, `quotaPreflight.defaultThresholdPercent` ସହ ମେଳ ଖାଏ)-ଠାରୁ ଉପରେ ରହିବାକୁ ପଡ଼େ। ଏହି ବ୍ୟବଧାନଟି ହେଉଛି hysteresis band — ଏହା ବିନା, cutoff ନିକଟରେ ରହୁଥିବା ଏକ ସଂଯୋଗ କ୍ରମାଗତ ଅନୁରୋଧଗୁଡ଼ିକରେ rung-ମଧ୍ୟରେ ଦୋଳାୟମାନ ହୁଏ।

## ବିନ୍ୟାସ

କେବଳ ସୂକ୍ଷ୍ମ ସମନ୍ୱୟ ପାଇଁ। ଜାଣିଶୁଣି କୌଣସି `enabled` ଫ୍ଲାଗ୍ ରଖାଯାଇନାହିଁ: ଏଗୁଡ଼ିକୁ ବନ୍ଦ କରିପାରୁଥିବା ଏକ ଟୋଗଲ୍
`auto/subscription`କୁ ନିରବରେ ସମ୍ପୂର୍ଣ୍ଣ ପୁଲ୍ — ଶୁଳ୍କଯୁକ୍ତ ମଡେଲ୍ଗୁଡ଼ିକ ସହିତ — ପରିବେଷଣ କରିବାକୁ ଛାଡ଼ିଦେବ,
ଯାହାର ନାମ ଠିକ୍ ଏହାର ବିପରୀତ ପ୍ରତିଶ୍ରୁତି ଦେଉଛି।

```jsonc
{
  "subscriptionLadder": {
    "exitCutoffPercent": 2,
    "reentryMinRemainingPercent": 5,
    "rungBudgetUsd": { "cheap": 5.0, "premium": 0 }, // 0 ଏକ ସୋପାନକୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ଅକ୍ଷମ କରେ
  },
}
```

ଏକ ବ୍ୟୟ ସମାଧାନକାରୀ ସଂଯୋଗ ନହେବା ପର୍ଯ୍ୟନ୍ତ ବଜେଟ୍ ଗେଟିଂ ନିଷ୍କ୍ରିୟ ରହେ: କୌଣସି ହିସାବ ଉପଲବ୍ଧ ନଥିଲେ ଏକ ଶୁଳ୍କଯୁକ୍ତ
ସୋପାନକୁ କ୍ରମରେ ରଖାଯାଏ, କିନ୍ତୁ କେବେବି ଗେଟ୍ କରାଯାଏନାହିଁ। v3.8.51 ଅନୁଯାୟୀ `rungBudgetUsd` ସେଟିଂକୁ
ସ୍କିମା ଗ୍ରହଣ କରେ, କିନ୍ତୁ ଏପର୍ଯ୍ୟନ୍ତ ଏହା ବାଧ୍ୟତାମୂଳକ ଭାବେ ପ୍ରୟୋଗ ହୋଇନାହିଁ — ଏହାକୁ ଏକ ସକ୍ରିୟ ବ୍ୟୟ ସୀମା ଭାବେ ନୁହେଁ, ସଂରକ୍ଷିତ ବିନ୍ୟାସ ଭାବେ ବିବେଚନା କରନ୍ତୁ। ସୋପାନ କ୍ରମବିନ୍ୟାସ, କୋଟା-ଆଧାରିତ ନିଃଶେଷତା ଏବଂ ରିସେଟ୍ ପରେ ପୁନଃ-ପ୍ରବେଶ—ସବୁ
ଏହା ବିନା କାମ କରେ।

## ସଂଯୋଜନ

`subscription` ଏବଂ `thrifty` ହେଉଛି `AutoTier` ମୂଲ୍ୟ, ତେଣୁ ସେଗୁଡ଼ିକ ପ୍ରତ୍ୟେକ ବର୍ଗ ସହିତ ସଂଯୋଜିତ ହୁଏ:
`auto/coding:thrifty`, `auto/reasoning:subscription`, ଇତ୍ୟାଦି। ଦୁଇଟି ଫ୍ଲାଟ୍ id
(`auto/subscription`, `auto/thrifty`)କୁ `/v1/models` ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡରେ ପ୍ରଦର୍ଶିତ କରାଯାଏ।

କୌଣସି id ଶୁଳ୍କଯୁକ୍ତ-ସ୍ତରର ନୁହେଁ, ତେଣୁ `isPaidTierAutoId()` ଉଭୟ ପାଇଁ `false` ଫେରାଏ ଏବଂ
`auto/subscription`, `hidePaidModels` ସକ୍ରିୟ ଥିଲେ ମଧ୍ୟ ଉପଲବ୍ଧ ରହେ।
