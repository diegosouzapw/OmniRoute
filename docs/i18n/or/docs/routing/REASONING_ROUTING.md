ରିଜନିଂ ରାଉଟିଂ ନିୟମଗୁଡ଼ିକ ବର୍ତ୍ତମାନର ମଡେଲ୍ ଏବଂ କମ୍ବୋ ରାଉଟିଂକୁ ବିସ୍ତାର କରେ। ଯେତେବେଳେ କୌଣସି ସକ୍ରିୟ ନିୟମ ମେଳ ଖାଏ ନାହିଁ,
ବର୍ତ୍ତମାନର ଥିଙ୍କିଂ, ସଫିକ୍ସ, କନେକ୍ସନ୍-ଡିଫଲ୍ଟ ଏବଂ ପ୍ରୋଭାଇଡର୍-ଟ୍ରାନ୍ସଲେସନ୍ ଆଚରଣ
ଅପରିବର୍ତ୍ତିତ ରହେ।

## ପରିଚାଳନା

ନିୟମ ପରିଚାଳନା **Settings → Global Routing** ଅଧୀନରେ ଉପଲବ୍ଧ। API-କି ଏଡିଟର୍ ଚୟନିତ କି ପାଇଁ
ଫିଲ୍ଟର୍ କରାଯାଇଥିବା ସମାନ ପରିଚାଳନା UI ପ୍ରଦାନ କରେ।

ପରିଚାଳନା API ଏହି ରୁଟ୍ଗୁଡ଼ିକ ଦ୍ୱାରା ଉପଲବ୍ଧ:

- `/api/settings/reasoning-routing-rules`ରେ `GET` ଏବଂ `POST`
- `/api/settings/reasoning-routing-rules/[id]`ରେ `GET`, `PATCH`, ଏବଂ `DELETE`
- `/api/settings/reasoning-routing-rules/simulate`ରେ `POST`

ସମସ୍ତ ରୁଟ୍ `requireManagementAuth` ବ୍ୟବହାର କରେ। ଇନ୍ପୁଟ୍ଗୁଡ଼ିକୁ
`src/shared/validation/schemas/reasoningRouting.ts`ରେ ଥିବା ସ୍କିମାଗୁଡ଼ିକ ସହିତ ବୈଧ କରାଯାଏ। ସିମ୍ୟୁଲେଟର୍ କେବେ ମଧ୍ୟ ଅପ୍ଷ୍ଟ୍ରିମ୍ କଲ୍ କରେ ନାହିଁ।

## ନିୟମ ସମାଧାନ

ପ୍ରାରମ୍ଭିକ ମୂଲ୍ୟାୟନ ଠିକ୍ ଗୋଟିଏ ନିୟମ ଚୟନ କରେ। ସ୍କୋପ୍ଗୁଡ଼ିକୁ ଏହି କ୍ରମରେ ଯାଞ୍ଚ କରାଯାଏ:

1. `apiKey`
2. `combo`
3. `model`
4. `global`

ଗୋଟିଏ ସ୍କୋପ୍ ମଧ୍ୟରେ, ପ୍ରଥମେ ଅଧିକ `priority` ବିଜୟୀ ହୁଏ, ତା’ପରେ ଗ୍ଲବ୍ ପ୍ୟାଟର୍ନ ଅପେକ୍ଷା ଏକ ସଠିକ୍ ମଡେଲ୍ ମେଳ,
ଏବଂ ତା’ପରେ ସ୍ଥିର `createdAt` ଓ `id` କ୍ରମ। `requestTags`ଗୁଡ଼ିକୁ କେବଳ `metadata.tags`ରୁ ପଢ଼ାଯାଏ
ଏବଂ `any` କିମ୍ବା `all` ମେଳକୁ ସମର୍ଥନ କରେ।

କୌଣସି ପ୍ରାରମ୍ଭିକ ନିୟମ ବିଜୟୀ ନ ହେଲେ ଏବଂ ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ପ୍ରୋଭାଇଡର୍ କନେକ୍ସନ୍
ପୂର୍ବରୁ ଚୟନ କରାଯାଇଥିଲେ ମାତ୍ର ଏକ `connection` ନିୟମର ମୂଲ୍ୟାୟନ କରାଯାଏ। ଏହା କେବଳ ଏଫର୍ଟ ଏବଂ ବଜେଟ୍ ପରିବର୍ତ୍ତନ କରିପାରେ।

## ଏଫର୍ଟ ଏବଂ ବଜେଟ୍

`sourceEffort`, `any`, `missing`, `none`, `low`, `medium`, `high`, `xhigh`, `max`, ଏବଂ
`ultra`କୁ ଗ୍ରହଣ କରେ। `missing`ର ଅର୍ଥ ହେଉଛି ଅନୁରୋଧରେ ନା ଏକ ସ୍ୱତନ୍ତ୍ର ଏଫର୍ଟ ଅଛି, ନା ଏକ ଥିଙ୍କିଂ ଟୋଗଲ୍
କିମ୍ବା ଥିଙ୍କିଂ ବଜେଟ୍ ଅଛି। ତେଣୁ କେବଳ-ବଜେଟ୍ ସିଗ୍ନାଲ୍ କେବଳ `any` ଦ୍ୱାରା ମେଳ ଖାଏ।

`effortMode`ର ତିନୋଟି ଭାରିଆଣ୍ଟ ଅଛି:

- `inherit` କ୍ଲାଏଣ୍ଟ ଏଫର୍ଟକୁ ବଜାୟ ରଖେ, ଏବଂ ତଥାପି ମଡେଲ୍ କିମ୍ବା କମ୍ବୋକୁ ପରିବର୍ତ୍ତନ ହେବାକୁ ଦିଏ।
- `default` କେବଳ କୌଣସି ସ୍ପଷ୍ଟ ରିଜନିଂ ସିଗ୍ନାଲ୍ ନଥିଲେ `targetEffort` ସେଟ୍ କରେ।
- `force` ସ୍ୱତନ୍ତ୍ର ଏଫର୍ଟକୁ `targetEffort` ସହିତ ବଦଳାଏ।

ସ୍ୱାଧୀନ ଭାବରେ, `budgetAction`, `preserve`, `remove`, କିମ୍ବା `set` ହୋଇପାରେ। `none` ସହିତ `force`
ସମସ୍ତ ସ୍ୱୀକୃତ ଏଫର୍ଟ ଏବଂ ବଜେଟ୍ ଫିଲ୍ଡ୍କୁ ହଟାଏ। `set` ସହିତ `none` ଅବୈଧ।

ଜଣାଶୁଣା-ଅସଙ୍ଗତ ମଡେଲ୍କୁ ଲକ୍ଷ୍ୟ କରୁଥିବା ଅନୁରୋଧଗୁଡ଼ିକୁ ଅପ୍ଷ୍ଟ୍ରିମ୍ କଲ୍ ପୂର୍ବରୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ। କମ୍ବୋ
ଟାର୍ଗେଟ୍ଗୁଡ଼ିକ ପାଇଁ, ଅସଙ୍ଗତ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକୁ ହଟାଯାଏ; ଯଦି କୌଣସିଟି ଅବଶିଷ୍ଟ ନଥାଏ, ଅନୁରୋଧଟି `400` ସ୍ଥିତି ଫେରାଏ।
ଅଜଣା କ୍ଷମତା ତଥ୍ୟ ଏକ ଚେତାବନୀ ଦିଏ ଏବଂ ନିୟମକୁ ସକ୍ରିୟ ରଖେ।

## ସୁରକ୍ଷା ଏବଂ ଟ୍ରାନ୍ସପୋର୍ଟ୍

ଉତ୍ସ ଏବଂ ଲକ୍ଷ୍ୟ ମଡେଲ୍, କିମ୍ବା ଉତ୍ସ ଏବଂ ଲକ୍ଷ୍ୟ କମ୍ବୋ, ବର୍ତ୍ତମାନର API-କି
ନୀତିର ଅଧୀନରେ ରହେ। ଏକ ରିଜନିଂ ନିୟମ କେବେ ମଧ୍ୟ ମଡେଲ୍, କମ୍ବୋ, କିମ୍ବା କୋଟା ଅନୁମତିକୁ ବିସ୍ତାର କରେ ନାହିଁ।

ଇଞ୍ଜିନ୍ଟି Chat Completions, Responses, Anthropic Messages, ଏବଂ ଆଭ୍ୟନ୍ତରୀଣ
Codex WebSocket ପଥରେ ଏକୀକୃତ ହୋଇଛି। WebSocket ପଥ କେବଳ Codex ଲକ୍ଷ୍ୟ ମଡେଲ୍ଗୁଡ଼ିକୁ ଗ୍ରହଣ କରେ; କମ୍ବୋ ଟାର୍ଗେଟ୍ଗୁଡ଼ିକୁ ସେଠାରେ
ନିଷ୍ପାଦନ କରାଯାଇପାରିବ ନାହିଁ। ନିୟମ ନିଷ୍ପତ୍ତିଟି ଗୁପ୍ତ ତଥ୍ୟ ବିନା ବର୍ତ୍ତମାନର ରୁଟ୍ ଟ୍ରେସ୍ରେ ସଂରକ୍ଷିତ ହୁଏ।

## ସ୍ଥାୟୀ ସଂରକ୍ଷଣ

ମାଇଗ୍ରେସନ୍ `src/lib/db/migrations/126_reasoning_routing_rules.sql`,
`reasoning_routing_rules` ଟେବୁଲ୍ ସୃଷ୍ଟି କରେ। ନିୟମଗୁଡ଼ିକ ସଂରକ୍ଷିତ API କି, କମ୍ବୋ, ଏବଂ ପ୍ରୋଭାଇଡର୍ କନେକ୍ସନ୍କୁ ସନ୍ଦର୍ଭ କରେ।
ଡିଲିଟ୍ କଲେ ସମ୍ବନ୍ଧିତ ନିୟମଗୁଡ଼ିକ ସଫା ହୋଇଯାଏ। `src/lib/db/reasoningRoutingRules.ts`ରେ ଥିବା ଡାଟାବେସ୍ ଆକ୍ସେସ୍ ସ୍ତର
ଅନୁରୋଧ ପଥ ପାଇଁ ଏକ ଅବୈଧଯୋଗ୍ୟ କ୍ୟାଶ୍ ବଜାୟ ରଖେ।

ନିୟମଗୁଡ଼ିକ SQLite ବ୍ୟାକଅପ୍, ସମ୍ପୂର୍ଣ୍ଣ ଡାଟାବେସ୍ ଏକ୍ସପୋର୍ଟ୍, ଏବଂ config-sync ବଣ୍ଡଲ୍ରେ ଅନ୍ତର୍ଭୁକ୍ତ।
`reconcileReasoningRulesForSync` ନଥିବା ରେଫରେନ୍ସ ସହିତ ଇମ୍ପୋର୍ଟ୍ ହୋଇଥିବା ନିୟମଗୁଡ଼ିକୁ ଅକ୍ଷମ କରେ ଏବଂ ସେହି
ଦ୍ୱନ୍ଦ୍ୱଗୁଡ଼ିକ ବିଷୟରେ ରିପୋର୍ଟ୍ କରେ।
