> ପ୍ରାର୍ଥୀ ପୁଲ୍କୁ ବାଇଟ୍-ଅଭିନ୍ନ ରଖେ)। ଯେଉଁ ଅପରେଟରମାନଙ୍କୁ କେବଳ "ମାଗଣା ଭାବେ
> ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଛି" ନୁହେଁ, ବରଂ ଯେକୌଣସି ବର୍ଦ୍ଧିତ ଆର୍ଥିକ ବ୍ୟୟ ବିରୋଧରେ ଏକ ଦୃଢ଼
> ଗ୍ୟାରେଣ୍ଟି ଆବଶ୍ୟକ, ସେମାନଙ୍କ ପାଇଁ `hidePaidModels`
> (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512)ର ଏକ ଅଧିକ କଠୋର ସହୋଦର।

## ଏହା କାହିଁକି ରହିଛି, ଏବଂ କେବଳ `hidePaidModels` କାହିଁକି ଯଥେଷ୍ଟ ନୁହେଁ

`hidePaidModels` "ଏହି ମଡେଲ୍ଟି ବର୍ତ୍ତମାନ `FREE_MODEL_BUDGETS`ରେ ମାଗଣା ଭାବେ ବର୍ଗୀକୃତ
ହୋଇଛି କି?" ପ୍ରଶ୍ନର ଉତ୍ତର ଦିଏ — ଏହା ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ସମୟର କ୍ୟାଟାଲଗ୍ ତଥ୍ୟ, ଯାହାକୁ
`isFreeModel()`/`providerHasFreeModels()` (`src/shared/utils/freeModels.ts`) ମାଧ୍ୟମରେ ଯାଞ୍ଚ
କରାଯାଏ। ଏହା ଦୁଇଟି ବାସ୍ତବ ବିପଦ ବିଷୟରେ କିଛି କୁହେ ନାହିଁ:

1. ଏକ `recurring-*`/`one-time-initial` ମାଗଣା ସ୍ତରର ଅନୁମୋଦିତ ପରିମାଣ **ଶେଷ ହୋଇପାରେ** —
   କ୍ୟାଟାଲଗ୍ରେ ମଡେଲ୍ଟି ତଥାପି ମାଗଣା ଭାବେ ତାଲିକାଭୁକ୍ତ ରହେ, କିନ୍ତୁ ଏହା ପଛରେ ଥିବା
   ଆକାଉଣ୍ଟରେ ଆଉ କୌଣସି ଅବଶିଷ୍ଟ କ୍ଷମତା ନଥାଏ।
2. ମାଗଣା ସ୍ତର ଅତିକ୍ରମ କରିବା ସବୁବେଳେ ଏକ କଠୋର ବନ୍ଦ ନୁହେଁ। କିଛି ପ୍ରଦାନକାରୀ ସ୍ପଷ୍ଟ
   ଭାବେ ଡକ୍ୟୁମେଣ୍ଟ କରନ୍ତି ଯେ କୌଣସି ପେମେଣ୍ଟ ପଦ୍ଧତି କେବେବି ସଂଲଗ୍ନ କରାଯାଇପାରିବ ନାହିଁ
   ("କୌଣସି କ୍ରେଡିଟ୍ କାର୍ଡ ଆବଶ୍ୟକ ନାହିଁ"); ଅନ୍ୟମାନେ ଏହା କୁହନ୍ତି ନାହିଁ, ଏବଂ କିଛି
   ପ୍ରଦାନକାରୀ ମାଗଣା ଅନୁମୋଦିତ ପରିମାଣ ଅତିକ୍ରମ କଲେ ସ୍ୱୟଂଚାଳିତ ଭାବେ ବିଲ୍ କରନ୍ତି।

`hidePaidModels` ଏଗୁଡ଼ିକୁ ପୃଥକ କରିପାରେ ନାହିଁ — ଏହାକୁ ସେହି ଉଦ୍ଦେଶ୍ୟରେ କେବେବି
ତିଆରି କରାଯାଇନଥିଲା। STRICT_ZERO_COST ଠିକ୍ ଏହି ଦୁଇଟି ଯାଞ୍ଚ ଯୋଡ଼େ, ଯାହା ପ୍ରତ୍ୟେକ
ପ୍ରାର୍ଥୀ ପାଇଁ, ବର୍ଗ/ସ୍ତର ର୍ୟାଙ୍କିଙ୍ଗ୍ର **ପୂର୍ବରୁ** ଏବଂ ଡିସ୍ପ୍ୟାଚ୍ର **ପୂର୍ବରୁ**
ମୂଲ୍ୟାୟନ କରାଯାଏ — ଅନୁରୋଧଟି ପୂର୍ବରୁ ପଠାଯାଇସାରିବା ପରେ କେବେବି ନୁହେଁ।

## ପ୍ରାର୍ଥୀ ବର୍ଗୀକରଣ

ପୁଲ୍ର ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ପାଇଁ (`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`,
`filterPaidOnlyCandidates`ର ଠିକ୍ ପରେ):

1. **`FREE_MODEL_BUDGETS`ରେ ଆଦୌ ନାହିଁ** → ବାଦ ଦିଆଯାଏ। ଏହା ପ୍ରକୃତରେ ଦେୟଯୁକ୍ତ
   ମଡେଲ୍ ଏବଂ OmniRoute ଏପର୍ଯ୍ୟନ୍ତ ବର୍ଗୀକୃତ କରିନଥିବା ଯେକୌଣସି ପ୍ରଦାନକାରୀ/ମଡେଲ୍କୁ
   ଅନ୍ତର୍ଭୁକ୍ତ କରେ — ନୂତନ ପ୍ରାର୍ଥୀମାନେ ଅନ୍ତର୍ଭୁକ୍ତ ନୁହେଁ, ବରଂ ବାଦ ଦିଆଯାଇଥିବା
   ଅବସ୍ଥାରୁ ଆରମ୍ଭ କରନ୍ତି।
2. **`freeType: "keyless"`** → ତୁରନ୍ତ ପାସ୍ କରେ, **କିନ୍ତୁ କେବଳ ସେହି ପ୍ରାର୍ଥୀ ପାଇଁ ଯିଏ
   ପ୍ରକୃତରେ no-auth ପଥ ଦେଇ ଆସିଛି** (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`)। ସେହି ପ୍ରାର୍ଥୀ ପାଇଁ କୌଣସି
   ପରିଚୟପତ୍ର ନାହିଁ, ତେଣୁ ଏହା ବିରୋଧରେ କୌଣସି ଅନୁରୋଧ ପାଇଁ କେବେବି ବିଲ୍ କରାଯାଇପାରିବ
   ନାହିଁ — କୌଣସି ରନ୍ଟାଇମ୍ ଯାଞ୍ଚ ଆବଶ୍ୟକ କିମ୍ବା ସମ୍ଭବ ନୁହେଁ। ଏକ **ପ୍ରକୃତ** DB
   ସଂଯୋଗ ମାଧ୍ୟମରେ ପହଞ୍ଚିଥିବା ସେହି କ୍ୟାଟାଲଗ୍ଭୁକ୍ତ `keyless` ପ୍ରଦାନକାରୀ/ମଡେଲ୍
   (`connectionId` ଏକ ବାସ୍ତବ ସଂଯୋଗ id, କିମ୍ବା ପ୍ରାର୍ଥୀଟି `allowedConnectionIds` ବହନ କରେ)
   ଏହି ସଂକ୍ଷିପ୍ତ ପଥ ପାଏ **ନାହିଁ** — `keyless` ମେଟାଡାଟା ବିଶେଷ ଭାବେ no-auth ପଥକୁ
   ବର୍ଣ୍ଣନା କରେ, ସାଧାରଣ ଭାବେ ପ୍ରଦାନକାରୀକୁ ନୁହେଁ, ଏବଂ କୌଣସି ବାସ୍ତବ,
   ପରିଚୟପତ୍ର-ଯୁକ୍ତ ଆକାଉଣ୍ଟକୁ କେବେବି ଅନୁମୋଦନ କରେ ନାହିଁ। ଏପରି ଏକ ପ୍ରାର୍ଥୀ
   ଅନ୍ୟମାନଙ୍କ ପରି ଯାଞ୍ଚ 3କୁ ଯାଏ, ଯେଉଁଠାରେ କ୍ୟାଟାଲଗ୍ ଏଣ୍ଟ୍ରିରେ ପୃଥକ ଭାବେ
   `hardStopGuaranteed: true` ନଥିଲେ ଏହାକୁ ବାଦ ଦିଆଯାଏ (ପ୍ରକୃତ `keyless` ଏଣ୍ଟ୍ରିଗୁଡ଼ିକରେ
   ଏହା କେବେବି ନଥାଏ — ସୁରକ୍ଷା ପାଇଁ ସଂକ୍ଷିପ୍ତ ପଥଟି ହିଁ ସେମାନଙ୍କର ଏକମାତ୍ର ଉପାୟ ଥିଲା)।
3. **ଅନ୍ୟ ଯେକୌଣସି `freeType`** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial`, ଏବଂ ଏହି ମଡ୍ୟୁଲ୍ ବିଶେଷ ଭାବେ ପରିଚାଳନା
   କରୁନଥିବା ଯେକୌଣସି ଭବିଷ୍ୟତ ପ୍ରକାର) → ନିମ୍ନୋକ୍ତ **ସମସ୍ତ** ସର୍ତ୍ତ ପୂରଣ ହେଲେ ହିଁ
   ପାସ୍ କରେ:
   - କ୍ୟାଟାଲଗ୍ ଏଣ୍ଟ୍ରିରେ `hardStopGuaranteed: true` ସେଟ୍ କରାଯାଇଛି
     (`FreeModelBudget.hardStopGuaranteed`, `open-sse/config/freeModelCatalog.ts`) — ପ୍ରଦାନକାରୀଙ୍କ
     ନିଜସ୍ୱ ପ୍ରକାଶିତ ସର୍ତ୍ତାବଳୀ ବିଷୟରେ ଏକ **କ୍ୟୁରେଟ୍ କରାଯାଇଥିବା, ହାତରେ ସେଟ୍ ହୋଇଥିବା
     ତଥ୍ୟ** (ଯଥା ଏକ ସ୍ପଷ୍ଟ "କୌଣସି କ୍ରେଡିଟ୍ କାର୍ଡ ଆବଶ୍ୟକ ନାହିଁ" ଦାବି), ଯାହା କେବେବି
     `freeType` କିମ୍ବା ଏକ ଲାଇଭ୍ API ପ୍ରତିକ୍ରିୟାରୁ ବ୍ୟୁତ୍ପନ୍ନ ହୁଏ ନାହିଁ। ସେଟ୍ ହୋଇନଥିବା
     (`undefined`) ଏବଂ `false` ଉଭୟକୁ "ଗ୍ୟାରେଣ୍ଟିଯୁକ୍ତ ନୁହେଁ" ଭାବେ ଗ୍ରହଣ କରାଯାଏ।
   - `USAGE_FETCHER_PROVIDERS`ରେ ପ୍ରଦାନକାରୀ ପାଇଁ ଏକ ବ୍ୟବହାର ଆଡାପ୍ଟର୍ ଅଛି
     (`open-sse/services/usage.ts`) — ସେହି ରେଜିଷ୍ଟ୍ରି ଯାହା ପୂର୍ବରୁ କୋଟା ଡ୍ୟାସ୍ବୋର୍ଡ ଏବଂ
     `getUsageForProvider()`କୁ ସମର୍ଥନ କରେ। କୌଣସି ଆଡାପ୍ଟର୍ ନାହିଁ → ଗୋଟିଏ ଯୋଡ଼ା ନହେବା
     ପର୍ଯ୍ୟନ୍ତ ସ୍ଥାୟୀ ଭାବେ ବାଦ ଦିଆଯାଏ।
   - **ମୂଲ୍ୟାୟନ କରାଯାଉଥିବା ନିର୍ଦ୍ଦିଷ୍ଟ ସଂଯୋଗ** ପାଇଁ ଲାଇଭ୍, କ୍ୟାଶ୍କୃତ
     `FreeAccessState`ର `status: "SAFE"` ଅଛି, ଏହାକୁ
     `settings.autoRefreshProviderQuotaInterval` ମଧ୍ୟରେ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ଡିଫଲ୍ଟ 180s —
     ବିଦ୍ୟମାନ ସେଟିଂ, ଏକ ନୂତନ ସଂଖ୍ୟା ନୁହେଁ), ଏବଂ ଏହା `remainingFreeAllowance` ଏକ ଛୋଟ
     ସୁରକ୍ଷା ମାର୍ଜିନ୍ଠାରୁ ଅଧିକ ଥିବା ରିପୋର୍ଟ କରେ।
4. **`freeType: "discontinued"`** → ସର୍ବଦା ବାଦ ଦିଆଯାଏ।

## ସଂଯୋଗ ସୁରକ୍ଷା (ପ୍ରତି-ସଂଯୋଗ ଯାଞ୍ଚ, କେବେବି ପ୍ରତି-ପ୍ରାର୍ଥୀ ନୁହେଁ)

auto-combo ପୁଲ୍ରେ ଥିବା ଏକ ପ୍ରାର୍ଥୀ ସର୍ବଦା ଗୋଟିଏ ସଂଯୋଗ ସହିତ ବନ୍ଧା ହୋଇନଥାଏ। ଏକ "ଲଜିକାଲ୍" ପ୍ରାର୍ଥୀ
(`connectionId: null`) ଏକ `allowedConnectionIds` ଅନୁମୋଦିତ-ତାଲିକା ବହନ କରେ — ଏକ କିମ୍ବା ଅଧିକ ପ୍ରକୃତ
ପ୍ରଦାନକାରୀ ସଂଯୋଗ/ଆକାଉଣ୍ଟ, ଯେଉଁଗୁଡ଼ିକ ମଧ୍ୟରୁ ଯେକୌଣସିଟି ଅନୁରୋଧଟି ପୂରଣ କରିପାରିବ — ଏବଂ ପ୍ରକୃତରେ
ବ୍ୟବହୃତ ଆକାଉଣ୍ଟଟି ପରେ, dispatch ସମୟରେ, `open-sse/services/combo/autoStrategy.ts`
ଦ୍ୱାରା ନିର୍ଦ୍ଧାରିତ ହୁଏ (`allowedConnectionIds`କୁ ଏହାର ନିଜସ୍ୱ ସଂଯୋଗ-ଚୟନ ଲଜିକ୍ ସହିତ ଛେଦ କରି, ~ଲାଇନ୍ 315-331)।

STRICT_ZERO_COST ସେହି ଅନୁମୋଦିତ-ତାଲିକାରେ ଥିବା **ପ୍ରତ୍ୟେକ ସଂଯୋଗର** ମାଗଣା-ପ୍ରବେଶ ସ୍ଥିତିକୁ
ପୃଥକ ଭାବେ ଯାଞ୍ଚ କରେ (`strictZeroCostFilter.ts`ରେ `evaluateCandidateConnections()`) ଏବଂ
`allowedConnectionIds`କୁ କେବଳ `SAFE` ଫେରାଇଥିବା ଉପସେଟ୍ରେ ପୁନଃଲେଖନ କରେ — କେବେବି ସମ୍ପୂର୍ଣ୍ଣ
ମୂଳ ତାଲିକା ନୁହେଁ, ଏବଂ କେବେବି ଇଚ୍ଛାମତେ ବାଛିନିଆଯାଇଥିବା ଗୋଟିଏ ସଦସ୍ୟ ନୁହେଁ। ନିର୍ଦ୍ଦିଷ୍ଟ ଭାବେ:

- ଆକାଉଣ୍ଟ A `SAFE`, ଆକାଉଣ୍ଟ B `UNKNOWN`/ଶେଷ ହୋଇଯାଇଛି/ଦେୟଯୋଗ୍ୟ → କେବଳ A ଚୟନଯୋଗ୍ୟ ରହେ।
- ସମସ୍ତ ଆକାଉଣ୍ଟ `UNKNOWN` → ପ୍ରାର୍ଥୀଟିକୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ବାଦ ଦିଆଯାଏ (ଖାଲି ସୁରକ୍ଷିତ ସେଟ୍)।
- ବିଫଳ ହେଉଥିବା ଏକକ-ସଂଯୋଗ ପ୍ରାର୍ଥୀ (`connectionId` ସିଧାସଳଖ ସେଟ୍ ହୋଇଛି, କୌଣସି ଅନୁମୋଦିତ-ତାଲିକା ନାହିଁ)
  ସିଧାସଳଖ ବାଦ ପଡ଼େ, ଏହାକୁ କେବେବି ଖାଲି `allowedConnectionIds` ସହିତ ଫେରାଯାଏ ନାହିଁ।

ଯେହେତୁ `autoStrategy.ts` dispatch ପାଇଁ ଏକ ସଂଯୋଗ ଚୟନ କରିବା ପୂର୍ବରୁ
`allowedConnectionIds`କୁ ପୂର୍ବରୁ ଏକ କଠୋର ଅନୁମୋଦିତ-ତାଲିକା ଭାବେ ବାଧ୍ୟତାମୂଳକ କରେ,
ଏହାକୁ ଯାଞ୍ଚିତ-`SAFE` ଉପସେଟ୍ରେ ପୁନଃଲେଖନ କରିବା, dispatch ସମୟରେ ପ୍ରକୃତରେ ବ୍ୟବହୃତ ସଂଯୋଗଟି
ସର୍ବଦା ଏହି ଫିଲ୍ଟର ନିଜେ ଯାଞ୍ଚ କରିଥିବା ସଂଯୋଗ ହେବ ବୋଲି ସୁନିଶ୍ଚିତ କରିବା ପାଇଁ ଯଥେଷ୍ଟ —
ସମାନ ପ୍ରାର୍ଥୀରେ ଥିବା କୌଣସି ଭିନ୍ନ, ଅଯାଞ୍ଚିତ ଆକାଉଣ୍ଟ କେବେବି ନୁହେଁ। ରିଗ୍ରେସନ୍ ପ୍ରମାଣ ପାଇଁ
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts` ଦେଖନ୍ତୁ
(keyless-bypass ମାମଲା A/B/C, ବହୁ-ଆକାଉଣ୍ଟ ମାମଲା 1-5)।

`discovered automatically`: ଆସନ୍ତାକାଲି ପ୍ରକାଶିତ ହେଉଥିବା ସଠିକ୍ ମେଟାଡାଟା ସହିତ ଏକ ପ୍ରଦାନକାରୀ/ମଡେଲ୍
(କ୍ୟାଟାଲଗ୍ରେ, ଏକ usage adapter ସହିତ, `hardStopGuaranteed: true`) OmniRoute ତାହା ବିଷୟରେ
ଜାଣିବା ମୁହୂର୍ତ୍ତରୁ ବ୍ୟବହାରଯୋଗ୍ୟ ହୁଏ — କୌଣସି କୋଡ୍ ପରିବର୍ତ୍ତନ ନାହିଁ, କୌଣସି whitelist ଏଣ୍ଟ୍ରି ନାହିଁ,
ଏହି ମଡ୍ୟୁଲ୍ରେ ସମ୍ପାଦନ କରିବାକୁ କିଛି ନାହିଁ। କ୍ୟାଟାଲଗ୍ରୁ ଅପସାରିତ ଗୋଟିଏ ମଡେଲ୍ ସେହିପରି ଅଦୃଶ୍ୟ ହୋଇଯାଏ।
ରିଗ୍ରେସନ୍ ପ୍ରମାଣ ପାଇଁ `tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` ଦେଖନ୍ତୁ
(ପ୍ରକୃତ କ୍ୟାଟାଲଗ୍କୁ ପରିବର୍ତ୍ତନ କରି ନୁହେଁ, injectable fixtures ମାଧ୍ୟମରେ)।

## କୋଟା କ୍ୟାଶିଂ (`open-sse/services/autoCombo/freeAccessQuota.ts`)

`getUsageForProvider()`କୁ ପୁନଃବ୍ୟବହାର କରେ — କୌଣସି ଦ୍ୱିତୀୟ କୋଟା ସିଷ୍ଟମ୍ ନାହିଁ। ଏକ ସ୍ୱଳ୍ପ-ଅବଧିର,
ଇନ୍-ମେମୋରି, ପ୍ରୋସେସ୍-ଜୀବନକାଳୀନ କ୍ୟାଶ୍ ଏହାର ସମ୍ମୁଖରେ ରହେ (TTL ଡିଫଲ୍ଟ
`autoRefreshProviderQuotaInterval` ସହିତ ସମାନ), ଯାହାଦ୍ୱାରା Telegram-ସ୍ତରୀୟ ଅନୁରୋଧ ହାର
ପ୍ରତ୍ୟେକ ଅନୁରୋଧର ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ପାଇଁ ଏକ ଲାଇଭ୍ billing-API କଲ୍କୁ କେବେବି ଟ୍ରିଗର୍ କରେନାହିଁ।
ରିଡ୍ଗୁଡ଼ିକ ସିଙ୍କ୍ରୋନସ୍: ଏକ cache miss `undefined` ଫେରାଏ (→ ବାଦ ଦିଆଯାଏ, fail-closed) ଏବଂ
_ପରବର୍ତ୍ତୀ_ ରିଡ୍ ପାଇଁ ଏକ background refresh ଆରମ୍ଭ କରେ — candidate-pool build ପଥରେ କୌଣସି
କାର୍ଯ୍ୟ କେବେବି ଏକ network call ପାଇଁ ଅପେକ୍ଷା କରେନାହିଁ।

କୌଣସି କାରଣରୁ ଏକ ସଂଯୋଗ ବିଫଳ ହେବା ମୁହୂର୍ତ୍ତରେ
