## ଶୂନ୍ୟ-ବିନ୍ୟାସ ଅଟୋ-ରାଉଟିଂ (`auto/` ଉପସର୍ଗ)

> **ନୂଆ:** କମ୍ବୋ ସୃଷ୍ଟି କରିବା ଆବଶ୍ୟକ ନୁହେଁ। ଯେକୌଣସି କ୍ଲାଏଣ୍ଟରେ ସିଧାସଳଖ `auto/` ଉପସର୍ଗ ବ୍ୟବହାର କରନ୍ତୁ।

### ଦ୍ରୁତ ଉଦାହରଣ

| -------------- | -------- | ----------------------------------------------------------------- |

| `auto/coding`  | କୋଡିଂ    | ଗୁଣବତ୍ତା-ପ୍ରଥମ ଓଜନ, କୋଡ୍ ଜେନେରେସନ୍ ପାଇଁ ଉପଯୁକ୍ତ                   |
| `auto/fast`    | ଦ୍ରୁତ    | କମ୍-ବିଳମ୍ବତା ବିଶିଷ୍ଟ ଚୟନ                                          |

| `auto/smart`   | ସ୍ମାର୍ଟ  | ଉନ୍ନତ ମଡେଲ୍ ଆବିଷ୍କାର ପାଇଁ ଗୁଣବତ୍ତା-ପ୍ରଥମ + ଅଧିକ ଅନ୍ୱେଷଣ ହାର (10%) |

### ବର୍ଗ × ସ୍ତର ସଂଯୋଜନ (`auto/<category>:<tier>`)

OpenRouter-ଶୈଳୀର ସଫିକ୍ସଗୁଡ଼ିକ **କେଉଁ ପ୍ରକାରର ରୁଟ୍** (ବର୍ଗ)କୁ **ଏହାକୁ କିପରି ଅନୁକୂଳିତ କରାଯିବ** (ସ୍ତର)ଠାରୁ ପୃଥକ କରେ, ଯାହାଦ୍ୱାରା ଆପଣ ସେଗୁଡ଼ିକୁ ସ୍ୱେଚ୍ଛାରେ ସଂଯୋଜନ କରିପାରିବେ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ବର୍ଗଗୁଡ଼ିକ** (କ୍ଷମତା ଅନୁଯାୟୀ ପ୍ରାର୍ଥୀ ପୁଲ୍ ଫିଲ୍ଟର୍ କରନ୍ତୁ): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍‌ଗୁଡ଼ିକୁ ରଖେ; `reasoning` ରିଜନିଂ/ଥିଙ୍କିଂ ମଡେଲ୍‌ଗୁଡ଼ିକୁ ରଖେ।
- **ସ୍ତରଗୁଡ଼ିକ** (ସ୍କୋରିଂ ଓଜନ / ପୁଲ୍ ଫିଲ୍ଟର୍ ବାଛନ୍ତୁ): `fast` (ଶୀଘ୍ର ପ୍ରେରଣ) · `cheap` (ଉପନାମ `floor`, ଖର୍ଚ୍ଚ-ସଞ୍ଚୟକାରୀ) · `reliable` (ସର୍କିଟ୍-ବ୍ରେକର୍ ସ୍ୱାସ୍ଥ୍ୟ + ବିଳମ୍ବତା ସ୍ଥିରତା) · `free` / `pro` (`classifyTier` ମାଧ୍ୟମରେ ମଡେଲ୍ ସ୍ତର ଅନୁଯାୟୀ ପୁଲ୍ ଫିଲ୍ଟର୍ କରେ — ମାଗଣା-ସ୍ତର ବନାମ ପ୍ରିମିୟମ୍)।

| ଉଦାହରଣ                 | ଏଥିରେ ସମାଧାନ ହୁଏ                                        |
| ---------------------- | ------------------------------------------------------- |
| `auto/coding:fast`     | କୋଡିଂ ପୁଲ୍, କମ୍-ବିଳମ୍ବତା ଓଜନ                            |
| `auto/coding:cheap`    | କୋଡିଂ ପୁଲ୍, ଖର୍ଚ୍ଚ-ଅନୁକୂଳିତ (ଉପନାମ `auto/coding:floor`) |
| `auto/reasoning:pro`   | କେବଳ ରିଜନିଂ/ଥିଙ୍କିଂ ମଡେଲ୍, ପ୍ରିମିୟମ୍ ସ୍ତର               |
| `auto/vision`          | ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍ (କୌଣସି ସ୍ତର ନାହିଁ → ସନ୍ତୁଳିତ ଓଜନ)     |
| `auto/multimodal:free` | ମଲ୍ଟିମୋଡାଲ୍-ସକ୍ଷମ ମଡେଲ୍, କେବଳ ମାଗଣା ସ୍ତର                |

ଯେକୌଣସି ବୈଧ `auto/<category>[:<tier>]` ଆବଶ୍ୟକତା ଅନୁଯାୟୀ ସମାଧାନ ହୁଏ; ଏକ ଚୟନିତ ଉପସେଟ୍ `/v1/models` ଏବଂ ଡ୍ୟାସ୍‌ବୋର୍ଡରେ (`open-sse/services/autoCombo/builtinCatalog.ts` ଭିତରେ `AUTO_SUFFIX_VARIANTS`) ପ୍ରଚାରିତ ହୁଏ। ଫିଲ୍ଟରିଂ **ଫେଲ୍-ଓପନ୍** ଅଟେ — ଯଦି କୌଣସି ସୀମାବଦ୍ଧତା କୌଣସି ସଂଯୁକ୍ତ ମଡେଲ୍ ସହିତ ମେଳ ଖାଏ ନାହିଁ, ତେବେ ସମ୍ପୂର୍ଣ୍ଣ ପୁଲ୍ ବ୍ୟବହୃତ ହୁଏ, ଯାହାଦ୍ୱାରା ରାଉଟିଂ କେବେ ମଧ୍ୟ ବିଫଳ ହୁଏ ନାହିଁ। ମୂଳ ସ୍କୋରର୍ (`combo.ts`) ଅପରିବର୍ତ୍ତିତ ରହେ; ବର୍ଗ/ସ୍ତର ଫିଲ୍ଟର୍ `buildAutoCandidates` ଭିତରେ ପ୍ରୟୋଗ କରାଯାଏ।

> **ଲାଇଭ୍ ମଡେଲ୍ ଇଣ୍ଟେଲିଜେନ୍ସ:** `ARENA_ELO_SYNC_ENABLED` ଫ୍ଲାଗ୍ ଚାଲୁ ଥିବାବେଳେ ଲାଇଭ୍ **Arena ELO** ର‍୍ୟାଙ୍କିଂ + **models.dev** ସ୍ତର ତଥ୍ୟ ଦ୍ୱାରା ଅଟୋ-ରାଉଟିଂ ଉପଯୁକ୍ତତା ସୂଚିତ ହୁଏ (ଅନ୍ୟଥା ଷ୍ଟାଟିକ୍ ଫିଟନେସ୍ ମ୍ୟାପ୍‌କୁ ଫେରିଯାଏ)।

**କିପରି ବ୍ୟବହାର କରିବେ:**

```bash
# OpenAI ଫର୍ମାଟ୍ ସମର୍ଥନ କରୁଥିବା ଯେକୌଣସି IDE କିମ୍ବା CLI ଟୁଲ୍
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# ଆପଣଙ୍କ କୋଡ୍/ବିନ୍ୟାସରେ ମଡେଲ୍‌କୁ ଏପରି ସେଟ୍ କରନ୍ତୁ:
model: "auto"                 # ସନ୍ତୁଳିତ ଡିଫଲ୍ଟ
model: "auto/coding"          # କୋଡିଂ କାର୍ଯ୍ୟ ପାଇଁ ସର୍ବୋତ୍ତମ
model: "auto/fast"            # ଉପଲବ୍ଧ ବିକଳ୍ପଗୁଡ଼ିକ ମଧ୍ୟରୁ ଦ୍ରୁତତମ
model: "auto/cheap"           # ପ୍ରତି ଟୋକେନ୍‌ରେ ସବୁଠାରୁ ଶସ୍ତା
```

**କ’ଣ ଘଟେ:**

1. OmniRoute `src/sse/handlers/chat.ts` ଭିତରେ `auto/` ଉପସର୍ଗ ଚିହ୍ନଟ କରେ
2. ଡେଟାବେସ୍‌ରୁ ସମସ୍ତ **ସକ୍ରିୟ ପ୍ରଦାତା ସଂଯୋଗ** କ୍ୱେରି କରେ
3. ବୈଧ ପ୍ରମାଣପତ୍ର (API କୀ କିମ୍ବା OAuth ଟୋକେନ୍) ଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ଫିଲ୍ଟର୍ କରେ
4. ପ୍ରତ୍ୟେକ ସଂଯୋଗ ପାଇଁ ମଡେଲ୍ ନିର୍ଦ୍ଧାରଣ କରେ (`connection.defaultModel` କିମ୍ବା ପ୍ରଦାତାଙ୍କ ପ୍ରଥମ ମଡେଲ୍)
5. ମେମୋରିରେ ଏକ **ଭର୍ଚୁଆଲ୍ କମ୍ବୋ** ନିର୍ମାଣ କରେ (DBରେ ସଂରକ୍ଷିତ ହୁଏ ନାହିଁ)
6. ଚୟନିତ ଭାରିଆଣ୍ଟର ଓଜନ ପ୍ରୋଫାଇଲ୍ + LKGP କୌଶଳ ବ୍ୟବହାର କରି ରାଉଟ୍ କରେ

**ମୁଖ୍ୟ ଗୁଣଧର୍ମ:**

- ✅ **ସର୍ବଦା-ସକ୍ରିୟ:** କୌଣସି ଟଗଲ୍, କମ୍ବୋ ସୃଷ୍ଟି କିମ୍ବା ବିନ୍ୟାସ ଆବଶ୍ୟକ ନାହିଁ
- ✅ **ଡାଇନାମିକ୍:** ବର୍ତ୍ତମାନ ସଂଯୁକ୍ତ ପ୍ରଦାତାମାନଙ୍କୁ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ପ୍ରତିଫଳିତ କରେ
- ✅ **ସେସନ୍ ଷ୍ଟିକିନେସ୍:** LKGP ସର୍ବଶେଷ ସଫଳ ପ୍ରଦାତାଙ୍କୁ ପ୍ରାଥମିକତା ଦେବା ସୁନିଶ୍ଚିତ କରେ
- ✅ **ମଲ୍ଟି-ଆକାଉଣ୍ଟ ସଚେତନ:** ପ୍ରତ୍ୟେକ ପ୍ରଦାତା ସଂଯୋଗ ଏକ ପୃଥକ ପ୍ରାର୍ଥୀ ହୁଏ
- ✅ **କୌଣସି DB ଲେଖନ ନାହିଁ:** ଭର୍ଚୁଆଲ୍ କମ୍ବୋ କେବଳ ଅନୁରୋଧ ପାଇଁ ଅବସ୍ଥିତ ରହେ, ସ୍ଥାୟୀକରଣରେ ଶୂନ୍ୟ ଅତିରିକ୍ତ ଭାର

### ପ୍ରତି-କୀ ପ୍ରାର୍ଥୀ ନିୟନ୍ତ୍ରଣ (#7819, ସ୍ତର 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` ପରେ ଥିବା ସଫିକ୍ସ, କିମ୍ବା
ମୂଳ ଚ୍ୟାନେଲ୍ ପାଇଁ ଆକ୍ଷରିକ `auto`) ଏକ **କେବଳ-ପଠନୀୟ** ଏଣ୍ଡପଏଣ୍ଟ୍, ଯାହା
ବର୍ତ୍ତମାନର ସହନଶୀଳତା ରିଡ୍‌ଗୁଡ଼ିକୁ ପୁନଃବ୍ୟବହାର କରି ଲାଇଭ୍ ପହଞ୍ଚଯୋଗ୍ୟତା ସହିତ ସଜ୍ଜିତ ଏକ
`auto/*` ଚ୍ୟାନେଲ୍‌ର ବର୍ତ୍ତମାନ ପ୍ରାର୍ଥୀ ପୁଲ୍‌କୁ ତାଲିକାଭୁକ୍ତ କରେ (କେବେ ମଧ୍ୟ କଞ୍ଚା ବ୍ରେକର୍ `state` ନୁହେଁ):

- ପ୍ରଦାତା ସର୍କିଟ୍ ବ୍ରେକର୍ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ସଂଯୋଗ କୁଲ୍‌ଡାଉନ୍ — ସମାଧାନ ହୋଇଥିବା `provider_connections` ଧାଡ଼ିରେ `rateLimitedUntil` / `testStatus`
- ମଡେଲ୍ ଲକ୍‌ଆଉଟ୍ — `isModelLocked(provider, connectionId, model)`

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ଏହି API କୀର `excluded` ଫ୍ଲାଗ୍‌କୁ ମଧ୍ୟ ବହନ କରେ। ବହିଷ୍କରଣଗୁଡ଼ିକୁ
ପ୍ରତି-API-କୀ ଆଧାରରେ (`auto_candidate_overrides` ଟେବୁଲ୍, ମାଇଗ୍ରେସନ୍ `128`) ସଂରକ୍ଷଣ କରାଯାଏ — OmniRoute
ଏକକ-ଟେନାଣ୍ଟ ଏବଂ ଏଥିରେ କୌଣସି `users` ଟେବୁଲ୍ ନାହିଁ, ତେଣୁ `apiKeyId` ହେଉଛି ପ୍ରତ୍ୟେକ କଲର୍ ପାଇଁ ସବୁଠାରୁ ନିକଟତମ ବାସ୍ତବ
ପରିଚୟ — ଏବଂ ଏହାକୁ
`open-sse/services/autoCombo/virtualFactory.ts` ମଧ୍ୟରେ ଥିବା ପ୍ରାର୍ଥୀ-ପୁଲ୍ ଚୋକ୍‌ପଏଣ୍ଟରେ ଶୁଦ୍ଧ, ୟୁନିଟ୍-ପରୀକ୍ଷିତ
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) ମାଧ୍ୟମରେ ପ୍ରବର୍ତ୍ତନ କରାଯାଏ।
ଫିଲ୍ଟର୍‌ଟି **fail-open** ଅଟେ: ଏକ ଅନିର୍ଦ୍ଧାରିତ apiKeyId/channel କିମ୍ବା DB ଲୁକ୍‌ଅପ୍ ବିଫଳତା, ଉଭୟ
ପୁଲ୍‌କୁ ଫିଲ୍ଟର୍ ନକରି ରଖେ, ତେଣୁ କୌଣସି ଓଭର୍‌ରାଇଡ୍ କନଫିଗର୍ କରିନଥିବା ଅପରେଟର୍ ଏହି ବୈଶିଷ୍ଟ୍ୟ ପୂର୍ବର ରାଉଟିଂକୁ
ବାଇଟ୍-ଅଭିନ୍ନ ଭାବରେ ଦେଖନ୍ତି।

**ଏକ ପରବର୍ତ୍ତୀ ଇସ୍ୟୁ ପାଇଁ ସ୍ଥଗିତ:** ପ୍ରତି-ପ୍ରାର୍ଥୀ ଓଜନ + ସ୍ପଷ୍ଟ କ୍ରମନିର୍ଦ୍ଧାରଣ (ସ୍ତର 3
— ବିଦ୍ୟମାନ ଓଜନଯୁକ୍ତ/ପ୍ରାଥମିକତା କୌଶଳ ପଥଗୁଡ଼ିକୁ ଫିଡ୍ କରେ) ଏବଂ ପ୍ରତ୍ୟେକ `auto/*` ଚ୍ୟାନେଲ୍ ପାଇଁ ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ
`combo.ts` କୌଶଳକୁ ପିନ୍ କରିବା (ସ୍ତର 4)। ଏକକ-ଟେନାଣ୍ଟ ମଡେଲ୍‌କୁ ବିଚାର କରି ଓଭର୍‌ରାଇଡ୍‌ଗୁଡ଼ିକ ପ୍ରତି-API-କୀ ଭାବେ ରହିବା ଉଚିତ କି ଗ୍ଲୋବାଲ୍ ହେବା ଉଚିତ, ସେହି ଖୋଲା ପ୍ରଶ୍ନ ପାଇଁ #7819 ଯୋଜନା ଦେଖନ୍ତୁ।

## ପ୍ରକୃତ Model Id ସହ ମେଳ ଖାଉଥିବା Combo ନାମଗୁଡ଼ିକ

ଯେଉଁ comboର `name` ଏକ bare model id ସହ ସମାନ (ଉଦାହରଣ ସ୍ୱରୂପ, ନାମ
`gpt-5.5` ଥିବା ଏକ combo), ତାହା ଏକ **ଉଦ୍ଦେଶ୍ୟମୂଳକ, ସମର୍ଥିତ ପ୍ୟାଟର୍ନ**, bug ନୁହେଁ: ଏହା
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)ରେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା
ପ୍ରତ୍ୟେକ model-id ପାଇଁ provider fallback ବ୍ୟବସ୍ଥା। କାରଣ bare-model-id resolution ପୂର୍ବରୁ
combo resolution ଯାଞ୍ଚ କରାଯାଏ
(`src/sse/services/model.ts`ରେ `getComboForModel()`), ତେଣୁ bare
id `gpt-5.5` ପାଇଁ ଏକ requestକୁ ସିଧାସଳଖ ଗୋଟିଏ providerକୁ ପଠାଇବା ପରିବର୍ତ୍ତେ
comboର targets (ଉଦାହରଣ ସ୍ୱରୂପ,
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) ମାଧ୍ୟମରେ route କରାଯାଏ
— ଏହା [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) ପାଇଁ
ନିର୍ମିତ combo-before-rewrite precedenceକୁ ପୁନଃବ୍ୟବହାର କରେ ଏବଂ
`tests/unit/responses-combo-resolution-3227.test.ts` ଓ
`tests/unit/combo-name-codex-responses-rewrite.test.ts` ଦ୍ୱାରା regression-test କରାଯାଇଛି।

ଏକ ପ୍ରକୃତ model idକୁ shadow କରୁଥିବା ନାମରେ combo ସୃଷ୍ଟି କିମ୍ବା rename କରିବା
**କେବେ ମଧ୍ୟ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ ନାହିଁ** — ଏପରି କଲେ ଏହି ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା workflow ଭାଙ୍ଗିଯିବ। ଏହା ପରିବର୍ତ୍ତେ
(#8530), (ନୂଆ) ନାମଟି ଏକ ପ୍ରକୃତ
model id ସହ ମେଳ ଖାଇଲେ `POST /api/combos` ଏବଂ `PUT /api/combos/[id]` responseରେ ଏକ non-blocking
`warning` field ଯୋଡ଼ନ୍ତି:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

Boot ସମୟରେ, `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) ମଧ୍ୟ model idକୁ shadow କରୁଥିବା ପ୍ରତ୍ୟେକ ବିଦ୍ୟମାନ comboର ତାଲିକା ସହିତ ଏକ ଏକ-ଧାଡ଼ିଆ `[STARTUP]` warning
log କରେ, ଯାହାଦ୍ୱାରା #6940 ଅନୁଯାୟୀ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବରେ କରିବା ପରିବର୍ତ୍ତେ
ଦୁର୍ଘଟଣାବଶତଃ ଏହାର ସମ୍ମୁଖୀନ ହୋଇଥିବା operatorsମାନେ ଏକ ସଙ୍କେତ ପାଆନ୍ତି।
Detection helperଟି `src/lib/combos/modelNameCollision.ts`ରେ ରହିଛି।

## ଏକ Clientରୁ Custom Comboକୁ Call କରିବା

Persisted combos (Settings → Combos) କେବଳ ସେତେବେଳେ ବ୍ୟବହୃତ ହୁଏ, ଯେତେବେଳେ client `model` fieldରେ comboର **ଅବିକଳ ନାମ** ପଠାଏ — combo ନାମର କୌଣସି fuzzy କିମ୍ବା partial matching ନାହିଁ, ଏବଂ କୌଣସି `auto/` prefix ମଧ୍ୟ ସମ୍ପୃକ୍ତ ନୁହେଁ। Resolution କ୍ରମ (`src/sse/services/model.ts`ରେ `getComboForModel()`):

1. ଅବିକଳ combo-name match (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ଦୁଇଟି ସାଧାରଣ ଭୁଲ:

- **`auto` ଆପଣଙ୍କ combos ବ୍ୟବହାର କରେ ନାହିଁ।** `auto`/`auto/*` ନିଜର zero-config candidate pool ନିର୍ମାଣ କରେ ଏବଂ କେବଳ ଯଦି କୌଣସି comboର ନାମ ଆକ୍ଷରିକ ଭାବରେ `auto` ଥାଏ, ତେବେ persisted combosକୁ ବିଚାର କରେ (ଏହା ସୁପାରିସ କରାଯାଏ ନାହିଁ)। ଏକ combo ମାଧ୍ୟମରେ route କରିବାକୁ, ଏହାର ଅବିକଳ ନାମ ପଠାନ୍ତୁ — `auto` ନୁହେଁ।
- **`openrouter/auto` ହେଉଛି ଏକ ପ୍ରକୃତ paid OpenRouter product** ("Auto Best Available"), OmniRoute alias ନୁହେଁ। ଏହା OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`)ର ଏକମାତ୍ର static model entry ଏବଂ ଏଥିପାଇଁ ପୃଥକ ଭାବରେ bill କରାଯାଏ। ଏହାକୁ `auto` poolsରୁ ବାଦ ଦେବା ପାଇଁ Settings → Routing → Hide paid models ବ୍ୟବହାର କରନ୍ତୁ।

ଏଠାରେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ମୂଳ ଦ୍ୱନ୍ଦ୍ୱ ପାଇଁ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) ଏବଂ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) ଦେଖନ୍ତୁ।

## ଏହା କିପରି କାମ କରେ (ସ୍ଥାୟୀ Auto-Combos)

Auto-Combo Engine ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ସର୍ବୋତ୍ତମ ପ୍ରଦାନକାରୀ/ମଡେଲ୍‌କୁ ଏକ **16-ଉପାଦାନ ସ୍କୋରିଂ ଫଙ୍କସନ୍** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`ରେ ପରିଭାଷିତ) ବ୍ୟବହାର କରି ଗତିଶୀଳ ଭାବରେ ଚୟନ କରେ। ଡିଫଲ୍ଟ ଓଜନଗୁଡ଼ିକର ଯୋଗଫଳ `1.0`; କଷ୍ଟମ୍ ଓଜନଗୁଡ଼ିକୁ `normalizeScoringWeights()` ଦ୍ୱାରା ପୁନଃସାମାନ୍ୟୀକୃତ କରାଯାଏ। ଷୋହଳଟି ମଧ୍ୟରୁ ଦୁଇଟି — `cacheAffinity` ଏବଂ `resetWindowAffinity` — ର ଡିଫଲ୍ଟ ଓଜନ `0`; `reliability`ର ଓଜନ `DEFAULT_WEIGHTS`ରେ `0`, କିନ୍ତୁ ସାଧାରଣ ପ୍ୟାକ୍‌ଗୁଡ଼ିକରେ `0.03` ଏବଂ `reliability-first`ରେ `0.04`, ଏବଂ `quality`ର ଓଜନ ପ୍ୟାକ୍‌ଗୁଡ଼ିକରେ `0.02` (`quality-first`ରେ `0.03`): ତଥାପି ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ପାଇଁ ଏଗୁଡ଼ିକ ଗଣନା କରାଯାଏ, ଏବଂ `cacheAffinity` ସ୍କୋର୍‌ର ବାହାରେ ପ୍ରମ୍ପ୍ଟ-କ୍ୟାଶ୍ ଡିଡୁପ୍ଲିକେସନ୍‌କୁ ନିୟନ୍ତ୍ରଣ କରେ, ତେଣୁ ଶୂନ୍ୟ-ଡିଫଲ୍ଟ ଉପାଦାନଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବେ ମତ ଦିଅନ୍ତି ନାହିଁ, କିନ୍ତୁ ପ୍ୟାକ୍‌ଗୁଡ଼ିକ ଦିଅନ୍ତି।

### ପ୍ରତି-ଅନୁରୋଧ ନିୟନ୍ତ୍ରଣ (ହେଡର୍ଗୁଡ଼ିକ) — #6023 / #6024 / #6025 / #3470

କମ୍ବୋର ସଞ୍ଚିତ କନଫିଗ୍କୁ ପରିବର୍ତ୍ତନ ନକରି, ତିନୋଟି ହେଡର୍ ମାଧ୍ୟମରେ **ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ** ଗୋଟିଏ `auto` କମ୍ବୋକୁ ନିୟନ୍ତ୍ରଣ କରାଯାଇପାରେ। ଏଗୁଡ଼ିକ କେବଳ `auto` କୌଶଳ ଏବଂ ସେଗୁଡ଼ିକୁ ବହନ କରୁଥିବା ଅନୁରୋଧ ପାଇଁ ପ୍ରଯୋଜ୍ୟ; ହେଡର୍ ଅନୁପସ୍ଥିତ ଥିଲେ କମ୍ବୋର ସଞ୍ଚିତ `modePack`/`budgetCap`/`budgetFallback` ବ୍ୟବହୃତ ହୁଏ।

### `weighted`ର ଅର୍ଥବିଧି

`weighted` ହେଉଛି **ପ୍ରତି ଅନୁରୋଧ ପାଇଁ ଏକ ଆନୁପାତିକ ଯାଦୃଚ୍ଛିକ ଡ୍ର**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ଏକ ସମକାରକ ନୁହେଁ:

- ପ୍ରତ୍ୟେକ ଅନୁରୋଧ `weight / totalWeight` ସମ୍ଭାବନା ସହିତ **ଗୋଟିଏ** ପଦକ୍ଷେପ ଚୟନ କରେ; ଅବଶିଷ୍ଟ ପଦକ୍ଷେପଗୁଡ଼ିକୁ ସେହି ଅନୁରୋଧର ଫଲ୍‌ବ୍ୟାକ୍ ଶୃଙ୍ଖଳା ଭାବରେ ଓଜନର ଅବରୋହୀ କ୍ରମରେ ସଜାଯାଏ।
- ଯେଉଁ ପଦକ୍ଷେପର ଓଜନ `0` (କିମ୍ବା ଅନୁପସ୍ଥିତ), ଅନ୍ୟ କୌଣସି ପଦକ୍ଷେପର ଓଜନ > 0 ଥିବାବେଳେ ତାହା **କେବେବି ଚୟନ କରାଯାଏ ନାହିଁ** — ଚୟନିତ ପଦକ୍ଷେପ ବିଫଳ ହେବା ପରେ ହିଁ ଏହା ଫଲ୍‌ବ୍ୟାକ୍ ଭାବରେ କାମ କରିପାରିବ। କେବଳ **ସମସ୍ତ** ଓଜନ 0 ହେଲେ ଚୟନ ସମବଣ୍ଟିତ ହୁଏ।
- ଯେଉଁ ପଦକ୍ଷେପଗୁଡ଼ିକର ସମସ୍ତ ଟାର୍ଗେଟ୍ ଅନୁପଲବ୍ଧ — ପ୍ରଦାନକାରୀ ସର୍କିଟ୍ ବ୍ରେକର୍ `OPEN`, ସଂଯୋଗ କୁଲ୍‌ଡାଉନ୍, ମଡେଲ୍ ଲକ୍‌ଆଉଟ୍ — ଡ୍ର ହେବା ପୂର୍ବରୁ ସେଗୁଡ଼ିକୁ ବାଦ ଦିଆଯାଏ (`open-sse/services/combo/targetResolution.ts`), ତେଣୁ ଗୋଟିଏ ସୁସ୍ଥ ପଦକ୍ଷେପ ଅସ୍ଥାୟୀ ଭାବରେ ପ୍ରତ୍ୟେକ ଅନୁରୋଧରେ ଜିତିପାରେ।
- `stickyWeightedLimit` (କମ୍ବୋ କନ୍‌ଫିଗ୍, ଡିଫଲ୍ଟ `1` = ବନ୍ଦ) ପୁନଃ ଡ୍ର କରିବା ପୂର୍ବରୁ ସେତେ ସଂଖ୍ୟକ କ୍ରମାଗତ ସଫଳତା ପାଇଁ ଚୟନିତ ପଦକ୍ଷେପକୁ ପିନ୍ କରେ।

କଠୋର ଘୂର୍ଣ୍ଣନ ପାଇଁ `round-robin` ବ୍ୟବହାର କରନ୍ତୁ; `weighted`ରେ ସମାନ ଓଜନ ସାଂଖ୍ୟିକ — କଠୋର ନୁହେଁ — ସନ୍ତୁଳନ ପ୍ରଦାନ କରେ।

## ଫ୍ୟୁଜନ୍ କୌଶଳ

`fusion` ହେଉଛି ଏକମାତ୍ର କୌଶଳ ଯାହା ଗୋଟିଏ ଲକ୍ଷ୍ୟ ଚୟନ କରେ **ନାହିଁ**। ଏହା ପ୍ରମ୍ପ୍ଟକୁ
**ପ୍ରତ୍ୟେକ ପ୍ୟାନେଲ୍ ମଡେଲ୍‌କୁ ସମାନ୍ତରାଳ ଭାବରେ** ପଠାଏ, ତା'ପରେ ଏକ ବିନ୍ୟାସଯୋଗ୍ୟ **ବିଚାରକ ମଡେଲ୍**
ସମସ୍ତ ପ୍ୟାନେଲ୍ ପ୍ରତିକ୍ରିୟାରୁ ଗୋଟିଏ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ସଂଶ୍ଳେଷଣ କରେ। ଏହାକୁ ଅପ୍‌ଷ୍ଟ୍ରିମ୍ `decolua/9router`
(OpenRouterର Fusion ଡିଜାଇନ୍)ରୁ ପୋର୍ଟ କରାଯାଇଛି; ଏହାର କାର୍ଯ୍ୟାନ୍ୱୟନ `open-sse/services/fusion.ts`ରେ ଅଛି।

ଏହା କିପରି କାମ କରେ:

0. **ଟୁଲ୍-ଯୁକ୍ତ ବାଇପାସ୍** — ଏକ ଅନୁରୋଧରେ ଖାଲି ନଥିବା `tools` ଆରେ ଥିଲେ ଏବଂ
   `tool_choice` ସ୍ପଷ୍ଟ ଭାବରେ `"none"` ନଥିଲେ, ଏହା ପ୍ୟାନେଲ୍‌କୁ ସମ୍ପୂର୍ଣ୍ଣ ଏଡ଼ାଇଯାଏ: ଏହା ସିଧାସଳଖ
   ଗୋଟିଏ ମଡେଲ୍‌କୁ (ବିନ୍ୟାସିତ ବିଚାରକ କିମ୍ବା `panel[0]`) ରୂଟ୍ ହୁଏ ଏବଂ `tools`/`tool_choice`
   କୌଣସି ପରିବର୍ତ୍ତନ ବିନା ପଠାଯାଏ। ପ୍ୟାନେଲ୍ ସଦସ୍ୟମାନଙ୍କ ପାଖରେ ଟୁଲ୍ ଆକ୍ସେସ୍ ନଥାଏ ଏବଂ ବିଚାରକର
   ସଂଶ୍ଳେଷଣ ନିର୍ଦ୍ଦେଶ ଟୁଲ୍-କଲ୍ ନିର୍ଗମନକୁ ନିରୁତ୍ସାହିତ କରେ, ତେଣୁ ଏଜେଣ୍ଟିକ୍/ଟୁଲ୍-କଲିଂ କ୍ଲାଏଣ୍ଟମାନେ
   ସଂଶ୍ଳେଷିତ ଗଦ୍ୟ ପରିବର୍ତ୍ତେ ଏକ ପ୍ରକୃତ ଟୁଲ୍-କଲ୍ ନିଷ୍ପତ୍ତି ପାଆନ୍ତି (#6771)।
1. **ଫ୍ୟାନ୍-ଆଉଟ୍** (କେବଳ ଟୁଲ୍-ବିହୀନ ଅନୁରୋଧ) — ପ୍ରମ୍ପ୍ଟଟିକୁ ଏକାସାଙ୍ଗରେ ପ୍ରତ୍ୟେକ ପ୍ୟାନେଲ୍
   ମଡେଲ୍‌କୁ ପଠାଯାଏ, ଟୁଲ୍‌ଗୁଡ଼ିକୁ ବାଦ ଦେଇ ବାଧ୍ୟତାମୂଳକ ଭାବେ ନନ୍-ଷ୍ଟ୍ରିମିଂ କରାଯାଏ (ସଂଶ୍ଳେଷଣ ପାଇଁ
   ବିଚାରକକୁ ସମ୍ପୂର୍ଣ୍ଣ ଗଦ୍ୟ ଆବଶ୍ୟକ)।
2. **କୋରମ୍-ଗ୍ରେସ୍ ସଂଗ୍ରହ** — `minPanel`ଟି ଉତ୍ତର ପହଞ୍ଚିବା ମାତ୍ରେ ପଛରେ ପଡ଼ିଥିବା
   ମଡେଲ୍‌ଗୁଡ଼ିକ ପାଇଁ ଏକ ସ୍ୱଳ୍ପ ଗ୍ରେସ୍ ଟାଇମର୍ ଆରମ୍ଭ ହୁଏ, ତା'ପରେ ଯାହା ସଂଗ୍ରହ ହୋଇଛି ତାହା ସହିତ
   ଫ୍ୟୁଜନ୍ ଆଗକୁ ବଢ଼େ। ଏହା ୱାଲ୍ ଟାଇମ୍‌ରେ ସବୁଠାରୁ ଧୀର ମଡେଲ୍‌ର ବିଳମ୍ବ ପ୍ରଭାବକୁ ସୀମିତ କରେ,
   ଯାହା ଏକ ହାର୍ଡ ଟାଇମ୍‌ଆଉଟ୍‌ରେ ବାନ୍ଧିତ।
3. **ବିଚାରକ ସଂଶ୍ଳେଷଣ** — ପ୍ୟାନେଲ୍ ଉତ୍ତରଗୁଡ଼ିକୁ ଅଜ୍ଞାତକୃତ କରାଯାଏ (`Source 1`, `Source 2`, … — ଯାହାଦ୍ୱାରା
   ବିଚାରକ ମଡେଲ୍ ବ୍ରାଣ୍ଡ ପରିବର୍ତ୍ତେ ବିଷୟବସ୍ତୁକୁ ଗୁରୁତ୍ୱ ଦିଏ) ଏବଂ ବିଚାରକକୁ ଦିଆଯାଏ, ଯିଏ
   ସହମତି / ବିରୋଧାଭାସ / ଆଂଶିକ ପରିସର / ଅନନ୍ୟ ଅନ୍ତର୍ଦୃଷ୍ଟି / ଅଦୃଶ୍ୟ ଦିଗଗୁଡ଼ିକୁ ବିଶ୍ଳେଷଣ କରି,
   **ଗୋଟିଏ** ପ୍ରାମାଣିକ ଉତ୍ତର ଲେଖେ। ବିଚାରକ କଲ୍ କ୍ଲାଏଣ୍ଟର ମୂଳ `stream` ଫ୍ଲାଗ୍ + ଟୁଲ୍‌ଗୁଡ଼ିକୁ
   ଅପରିବର୍ତ୍ତିତ ରଖେ, ଫଳରେ ଷ୍ଟ୍ରିମିଂ ଏବଂ ଡାଉନ୍‌ଷ୍ଟ୍ରିମ୍ ଟୁଲ୍ ବ୍ୟବହାର ଏବେ ମଧ୍ୟ କାମ କରେ।
4. **ସୁଗମ ଅବନତି** — 0ଟି ପ୍ୟାନେଲ୍ ଉତ୍ତର → `503`; ଠିକ୍ 1ଟି ଉତ୍ତର ରହିଲେ → ସେହି ଉତ୍ତର
   ସିଧାସଳଖ ଫେରାଯାଏ (ସଂଯୋଜନ କରିବାକୁ କିଛି ନାହିଁ); ଗୋଟିଏ-ମଡେଲ୍ ପ୍ୟାନେଲ୍ ସିଧାସଳଖ ଉତ୍ତର ଦିଏ।

(`{kind: "combo-ref", comboName: "..."}`) ମଧ୍ୟ ହୋଇପାରେ — ଏହା **ଗୋଟିଏ ବ୍ଲାକ୍-ବକ୍ସ ପ୍ୟାନେଲ୍ ସ୍ୱର** ଭାବେ
ସମାଧାନ ହୁଏ (ସନ୍ଦର୍ଭିତ କମ୍ବୋର ନିଜସ୍ୱ ଲକ୍ଷ୍ୟଗୁଡ଼ିକର ଫ୍ୟାନ୍-ଆଉଟ୍ ନୁହେଁ, ବରଂ ସେହି କମ୍ବୋ ମଧ୍ୟକୁ
ଏକ ସମ୍ପୂର୍ଣ୍ଣ ପୁନରାବୃତ୍ତିଶୀଳ ଡିସ୍ପାଚ୍), ଏବଂ ଏଥିରେ ପୂର୍ବରୁ ଅନ୍ୟ ସମସ୍ତ combo-ref-ବ୍ୟବହାରକାରୀ
କୌଶଳ ବ୍ୟବହାର କରୁଥିବା ସମାନ ଗଭୀରତା/ଚକ୍ର ସୁରକ୍ଷା ରହିଛି (#6764)।

### ବିନ୍ୟାସ

କମ୍ବୋର `config` ବ୍ଲବ୍‌ରେ ବିନ୍ୟାସ କରାଯାଏ (କୌଣସି ସ୍କିମା ମାଇଗ୍ରେସନ୍ ନାହିଁ — ଏହା ବିଦ୍ୟମାନ
`combos` ଟେବୁଲ୍‌କୁ ପୁନଃବ୍ୟବହାର କରେ):

| କ୍ଷେତ୍ର                                  | ପ୍ରକାର   | ଡିଫଲ୍ଟ               | ଉଦ୍ଦେଶ୍ୟ                                                                            |
| :--------------------------------------- | :------- | :------------------- | :---------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ପ୍ରଥମ ପ୍ୟାନେଲ୍ ମଡେଲ୍ | ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ସଂଶ୍ଳେଷଣ କରୁଥିବା ମଡେଲ୍                                               |
| `config.fusionTuning.minPanel`           | `number` | `2`                  | ଗ୍ରେସ୍ ଟାଇମର୍ ଆରମ୍ଭ ହେବା ପୂର୍ବରୁ ଆବଶ୍ୟକ ସଫଳ ଉତ୍ତର ସଂଖ୍ୟା (`[2, panelSize]`ରେ ସୀମିତ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`               | କୋରମ୍ ପୂରଣ ହେବା ପରେ ପଛରେ ପଡ଼ିଥିବା ମଡେଲ୍‌ଗୁଡ଼ିକ ପାଇଁ କେତେ ସମୟ ଅପେକ୍ଷା କରାଯିବ         |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`              | ଗୋଟିଏ ଅଟକିଥିବା ମଡେଲ୍ ଯେପରି ଅନୁରୋଧକୁ ଅଟକାଇ ନପାରେ, ସେଥିପାଇଁ ସର୍ବାଧିକ ସମୟସୀମା          |

ଡିଫଲ୍ଟଗୁଡ଼ିକ `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)ରେ ରହିଛି।

## ଭର୍ଚୁଆଲ୍ ଅଟୋ-କମ୍ବୋ ଫ୍ୟାକ୍ଟରୀ

ଅଟୋ କମ୍ବୋ ଇଞ୍ଜିନ୍‌କୁ ପୂର୍ବ-ନିର୍ଦ୍ଧାରିତ କମ୍ବୋ ଆବଶ୍ୟକ ହୁଏ ନାହିଁ। ଏହା ପରିବର୍ତ୍ତେ, `open-sse/services/autoCombo/virtualFactory.ts` ତତ୍କ୍ଷଣାତ୍ ପ୍ରାର୍ଥୀଗୁଡ଼ିକ ତିଆରି କରେ:

1. `getProviderConnections({ isActive: true })` (ସମସ୍ତ ସକ୍ରିୟ ସଂଯୋଗ) ଆଣେ
2. ବୈଧ ପ୍ରମାଣପତ୍ର ଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ଫିଲ୍ଟର୍ କରେ (API କୀ କିମ୍ବା `hasUsableOAuthToken()` ମାଧ୍ୟମରେ ମିଆଦ ଶେଷ ହୋଇନଥିବା OAuth ଟୋକେନ୍)
3. ମଡେଲ୍ ଉପଲବ୍ଧତା + ମୂଲ୍ୟ ନିର୍ଦ୍ଧାରଣ ପାଇଁ `getProviderRegistry()` ସହିତ କ୍ରସ୍-ରେଫରେନ୍ସ କରେ
4. ପ୍ରତ୍ୟେକ `(provider, model, connection)` ଟ୍ୟୁପଲ୍ ପାଇଁ ଏକ `VirtualAutoComboCandidate` ତିଆରି କରେ
5. ଡିସ୍ପାଚ୍ ଲକ୍ଷ୍ୟ ଭାବରେ `connection.defaultModel` (କିମ୍ବା ରେଜିଷ୍ଟ୍ରିର ପ୍ରଥମ ମଡେଲ୍) ବାଛେ
6. 16-ଫ୍ୟାକ୍ଟର୍ `scorePool()` ଏବଂ ଭାରିଆଣ୍ଟର ୱେଟ୍ ପ୍ୟାକ୍ ବ୍ୟବହାର କରି ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ ସ୍କୋର୍ କରେ
7. `handleComboChat()` ପାଇଁ ଫଳସ୍ୱରୂପ ମିଳିଥିବା ଇନ୍-ମେମୋରୀ `AutoComboConfig` ଫେରାଏ — ଏହା କେବେବି DBରେ ସ୍ଥାୟୀ ଭାବରେ ସଂରକ୍ଷିତ ହୁଏ ନାହିଁ

ଏହାର ଅର୍ଥ ହେଉଛି **`auto/*` ସକ୍ରିୟ ଥିବା ଏକ ନୂଆ ପ୍ରଦାନକାରୀ ଯୋଡ଼ିଲେ ପ୍ରାର୍ଥୀ ପୁଲ୍ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ବିସ୍ତାରିତ ହୁଏ** — ମାନୁଆଲ୍ କମ୍ବୋ ସମ୍ପାଦନା ଆବଶ୍ୟକ ନୁହେଁ। ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ଭର୍ଚୁଆଲ୍ କମ୍ବୋ ପୁନଃନିର୍ମାଣ ହୁଏ, ତେଣୁ ନୂତନ ଭାବେ ଯୋଡ଼ାଯାଇଥିବା କିମ୍ବା ନୂତନ ଭାବେ ସୁସ୍ଥ ହୋଇଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ତୁରନ୍ତ ବାଛାଯାଏ।

## ସ୍ୱୟଂ-ପୁନରୁଦ୍ଧାର

- **ଅସ୍ଥାୟୀ ବହିଷ୍କାର**: ସ୍କୋର୍ < 0.2 → 5 ମିନିଟ୍ ପାଇଁ ବହିଷ୍କୃତ (କ୍ରମବର୍ଦ୍ଧିଷ୍ଣୁ ବ୍ୟାକ୍‌ଅଫ୍, ସର୍ବାଧିକ 30 ମିନିଟ୍)
- **ସର୍କିଟ୍ ବ୍ରେକର୍ ସଚେତନତା**: OPEN → ସ୍ୱୟଂଚାଳିତ ଭାବରେ ବହିଷ୍କୃତ; HALF_OPEN → ପ୍ରୋବ୍ ଅନୁରୋଧ
- **ଘଟଣା ମୋଡ୍**: >50% OPEN → ଅନ୍ୱେଷଣ ଅକ୍ଷମ କରି ସ୍ଥିରତାକୁ ସର୍ବାଧିକ କରେ
- **କୁଲ୍‌ଡାଉନ୍ ପୁନରୁଦ୍ଧାର**: ବହିଷ୍କାର ପରେ, ପ୍ରଥମ ଅନୁରୋଧଟି ହ୍ରାସକୃତ ଟାଇମ୍‌ଆଉଟ୍ ସହିତ ଏକ "ପ୍ରୋବ୍" ହୁଏ

## ବ୍ୟାଣ୍ଡିଟ୍ ଅନ୍ୱେଷଣ

5% ଅନୁରୋଧ (ବିନ୍ୟାସଯୋଗ୍ୟ) ଅନ୍ୱେଷଣ ପାଇଁ ଯାଦୃଚ୍ଛିକ ପ୍ରଦାନକାରୀଙ୍କ ନିକଟକୁ ରାଉଟ୍ କରାଯାଏ। ଘଟଣା ମୋଡ୍‌ରେ ଏହା ଅକ୍ଷମ ରହେ।

## API

କୌଣସି **ଉତ୍ସର୍ଗୀକୃତ `POST /api/combos/auto` ଏଣ୍ଡପଏଣ୍ଟ ନାହିଁ** — ଅଟୋ-କମ୍ବୋକୁ ଦୁଇଟି ଉପାୟରେ ବ୍ୟବହାର କରାଯାଏ:

1. **ଶୂନ୍ୟ-ବିନ୍ୟାସ (ସୁପାରିଶକୃତ):** `model: "auto"` କିମ୍ବା `model: "auto/<variant>"` ସହିତ ଯେକୌଣସି ଚାଟ୍ କମ୍ପ୍ଲିସନ୍ ଅନୁରୋଧ ପଠାନ୍ତୁ। ଭର୍ଚୁଆଲ୍ ଫ୍ୟାକ୍ଟରୀ ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ କମ୍ବୋ ତିଆରି କରେ — କୌଣସି ସ୍ଥାୟୀ ସଂରକ୍ଷଣ କିମ୍ବା API କଲ୍ ଆବଶ୍ୟକ ନୁହେଁ।

2. **`strategy: "auto"` ସହିତ ସ୍ଥାୟୀ କମ୍ବୋ:** `POST /api/combos` ମାଧ୍ୟମରେ ଏକ ନିୟମିତ କମ୍ବୋ ତିଆରି କରନ୍ତୁ ଏବଂ `config.auto.weights` / `config.auto.candidatePool` ସହିତ `strategy: "auto"` ସେଟ୍ କରନ୍ତୁ। ସମାନ ସ୍କୋରିଂ ଇଞ୍ଜିନ୍ ବ୍ୟବହୃତ ହୁଏ; କମ୍ବୋଟି `combos`ରେ ସଂରକ୍ଷିତ ହୁଏ ଏବଂ ID ଦ୍ୱାରା ପୁନଃବ୍ୟବହାରଯୋଗ୍ୟ ହୁଏ।

ଆବିଷ୍କାର ପାଇଁ, `GET /api/combos/auto` ପ୍ରତ୍ୟେକ ଭାରିଆଣ୍ଟକୁ ତାହାର ସମାଧାନ କରାଯାଇଥିବା ପ୍ରାର୍ଥୀ ପୁଲ୍ ସହିତ `context_length` / `max_output_tokens` ସମେତ ତାଲିକାଭୁକ୍ତ କରେ — ଏଗୁଡ଼ିକ ପ୍ରାର୍ଥୀ ପୁଲ୍‌ର ୱିଣ୍ଡୋଗୁଡ଼ିକ ମଧ୍ୟରୁ ସର୍ବାଧିକ ମୂଲ୍ୟ। କ୍ଲାଏଣ୍ଟଗୁଡ଼ିକୁ (ଯଥା opencode ପ୍ଲଗିନ୍) `0` ପରିବର୍ତ୍ତେ ଏହି ମୂଲ୍ୟଗୁଡ଼ିକ ଘୋଷଣା କରିବାକୁ ପଡ଼ିବ: ଶୂନ୍ୟ କଣ୍ଟେକ୍ସ୍ଟ opencodeର ସ୍ୱୟଂଚାଳିତ କମ୍ପାକ୍ସନ୍‌କୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ଅକ୍ଷମ କରିଦିଏ, ଫଳରେ ଗେଟ୍‌ୱେର ଇତିହାସ ପରିଷ୍କାର କରିବା ପ୍ରକ୍ରିୟା କଣ୍ଟେକ୍ସ୍ଟ ନଷ୍ଟ କରିବା ପର୍ଯ୍ୟନ୍ତ ସେସନ୍‌ଗୁଡ଼ିକ ବଢ଼ିଚାଲେ। MAX ଘୋଷଣା କରିବା ସୁରକ୍ଷିତ, କାରଣ ଅଟୋ-କମ୍ବୋ କଣ୍ଟେକ୍ସ୍ଟ ପ୍ରି-ଫିଲ୍ଟର୍ ଅତ୍ୟଧିକ ବଡ଼ ଅନୁରୋଧଗୁଡ଼ିକୁ ବଡ଼-ୱିଣ୍ଡୋ ପ୍ରାର୍ଥୀଙ୍କ ନିକଟକୁ ରାଉଟ୍ କରେ।

```bash
# ଶୂନ୍ୟ-ବିନ୍ୟାସ ବ୍ୟବହାର (କୌଣସି କମ୍ବୋ ସୃଷ୍ଟି ନାହିଁ)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# ନିୟମିତ କମ୍ବୋ ଏଣ୍ଡପଏଣ୍ଟ ମାଧ୍ୟମରେ ସ୍ଥାୟୀ ଅଟୋ କମ୍ବୋ
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ଅଟୋ ରାଉଟର୍ କୌଶଳଗୁଡ଼ିକ

ସ୍ଥାୟୀ `strategy: "auto"` କମ୍ବୋଗୁଡ଼ିକ `config.routerStrategy` (କିମ୍ବା ପୁରୁଣା
`config.auto.routerStrategy`)କୁ ନିମ୍ନଲିଖିତ ମଧ୍ୟରୁ ଗୋଟିଏ ଭାବରେ ସେଟ୍ କରିପାରିବେ:

- `rules` — ଡିଫଲ୍ଟ ଭାରିତ ସ୍କୋରିଂ
- `score` — ସର୍ବାଧିକ ବିନ୍ୟାସିତ ଭାରିତ ସ୍କୋର୍ ବାଛେ। ସଠିକ୍ ଟାଇ ହେଲେ ବିନ୍ୟାସିତ
  ପ୍ରାର୍ଥୀ କ୍ରମ ସଂରକ୍ଷିତ ରହେ; ବର୍ତ୍ତମାନର `explorationRate` ସମ୍ପୂର୍ଣ୍ଣ ରାଙ୍କ୍ କରାଯାଇଥିବା ପୁଲ୍‌ରୁ ନମୁନା ବାଛେ।
- `cost` / `eco` — ସବୁଠାରୁ ଶସ୍ତା ସୁସ୍ଥ ପ୍ରଦାନକାରୀ
- `latency` / `fast` — ବିଶ୍ୱସନୀୟତା ଦଣ୍ଡ ସହିତ ସର୍ବନିମ୍ନ p95 ବିଳମ୍ବ
- `sla-aware` / `sla` — p95 ବିଳମ୍ବ, ତ୍ରୁଟି-ହାର ଏବଂ ବୈକଳ୍ପିକ
  ଖର୍ଚ୍ଚ SLO ପୂରଣ କରୁଥିବା ପ୍ରାର୍ଥୀଙ୍କୁ ପ୍ରାଧାନ୍ୟ ଦିଏ
- `lkgp` — ଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରଦାନକାରୀ ପ୍ରଥମେ

### ରାଉଟର୍ କୌଶଳଗୁଡ଼ିକର ବିବରଣୀ

ଅଟୋ-କମ୍ବୋ ଇଞ୍ଜିନ୍ 6ଟି ପ୍ଲଗ୍‌ଯୋଗ୍ୟ **RouterStrategy** କାର୍ଯ୍ୟାନ୍ୱୟନ ଉପଲବ୍ଧ କରାଏ, ଯାହାକୁ
ଆପଣ `config.routerStrategy` (କିମ୍ବା ପୁରୁଣା `config.auto.routerStrategy`) ମାଧ୍ୟମରେ ପରିବର୍ତ୍ତନ କରିପାରିବେ।
ପ୍ରତ୍ୟେକ କୌଶଳ ଏକ `RoutingContext`
(କାର୍ଯ୍ୟ ପ୍ରକାର, ଟୁଲ୍/ଭିଜନ୍ ସଙ୍କେତ, ଟୋକେନ୍ ଆକଳନ, ବୈକଳ୍ପିକ SLA ନୀତି, ବୈକଳ୍ପିକ
ଶେଷ-ଜଣାଶୁଣା-ଭଲ ପ୍ରଦାନକାରୀ) ଆଧାରରେ ପ୍ରାର୍ଥୀ ପୁଲ୍‌ରୁ ଗୋଟିଏ ପ୍ରଦାନକାରୀ ବାଛେ।

#### 1. `rules` (ଡିଫଲ୍ଟ) — 16-ଫ୍ୟାକ୍ଟର୍ ଭାରିତ ସ୍କୋରିଂ

ବର୍ତ୍ତମାନର ସ୍କୋରିଂ ଇଞ୍ଜିନ୍‌କୁ ଆବୃତ କରେ। `OPEN` ସର୍କିଟ୍-ବ୍ରେକର୍
ପ୍ରାର୍ଥୀଙ୍କୁ ଫିଲ୍ଟର୍ କରେ, ତା’ପରେ ବର୍ତ୍ତମାନର କାର୍ଯ୍ୟ ପ୍ରକାର ଏବଂ `getTaskFitness()` ସହିତ `scorePool()`
ଚଲାଇ ସର୍ବାଧିକ ସ୍କୋର୍ ପାଇଥିବା ପ୍ରଦାନକାରୀକୁ ବାଛେ।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**କେତେବେଳେ ବ୍ୟବହାର କରିବେ**: ଡିଫଲ୍ଟ। ସମସ୍ତ ସଙ୍କେତ ମଧ୍ୟରେ ଏକ ସନ୍ତୁଳିତ ସମନ୍ୱୟ ଚାହୁଁଥିଲେ ବ୍ୟବହାର କରନ୍ତୁ।

**ଉପନାମ**: `rules` (କୌଣସି ଉପନାମ ନାହିଁ)

---

#### 2. `cost` / `eco` — ସବୁଠାରୁ ଶସ୍ତା ସୁସ୍ଥ ପ୍ରଦାନକାରୀ

ପ୍ରାର୍ଥୀ ପୁଲ୍‌କୁ `costPer1MTokens` ଅନୁସାରେ (ଆରୋହୀ କ୍ରମରେ) ସଜାଇ ସବୁଠାରୁ ଶସ୍ତାଟିକୁ ବାଛେ।
ପ୍ରଥମେ `OPEN` ପ୍ରାର୍ଥୀଙ୍କୁ ଫିଲ୍ଟର୍ କରେ।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**କେତେବେଳେ ବ୍ୟବହାର କରିବେ**: ଖର୍ଚ୍ଚ-ସମ୍ବେଦନଶୀଳ ୱର୍କଲୋଡ୍, ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ କିମ୍ବା ପୃଷ୍ଠଭୂମି କାର୍ଯ୍ୟ ପାଇଁ।

**ଉପନାମଗୁଡ଼ିକ**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ବିଶ୍ୱସନୀୟତା ଦଣ୍ଡ ସହିତ ସର୍ବନିମ୍ନ p95 ବିଳମ୍ବ

`p95LatencyMs + (errorRate * 1000)` ଅନୁସାରେ ସଜାଏ। ତ୍ରୁଟି-ହାର ଦଣ୍ଡ ନିଶ୍ଚିତ କରେ ଯେ
ଅବିଶ୍ୱସନୀୟ ପ୍ରଦାତାଙ୍କ ନାମମାତ୍ର ବିଳମ୍ବତା କମ୍ ଥିଲେ ମଧ୍ୟ ସେମାନଙ୍କୁ ନିମ୍ନ ସ୍ଥାନ ଦିଆଯାଏ।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ରିଅଲ୍-ଟାଇମ୍ ଚାଟ୍, ସ୍ୱୟଂସମ୍ପୂର୍ଣ୍ଣତା କିମ୍ବା
ଇଣ୍ଟରାକ୍ଟିଭ୍ କୋଡିଂ ସହାୟକ ପରି ବିଳମ୍ବତା-ସମ୍ବେଦନଶୀଳ କାର୍ଯ୍ୟଭାର ପାଇଁ।

**ଉପନାମଗୁଡ଼ିକ**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ବିଳମ୍ବତା/ତ୍ରୁଟି/ଖର୍ଚ୍ଚ SLO ଅନୁପାଳନ

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ବିନ୍ୟାସିତ SLO ନୀତିକୁ କେତେ ଭଲ ଭାବରେ ପୂରଣ କରେ, ତାହା ଆଧାରରେ ସ୍କୋର୍ କରେ:

| କାରକ             | ଭାର | ସୂତ୍ର                                                   |
| ---------------- | --- | ------------------------------------------------------- |
| ବିଳମ୍ବତା ସ୍କୋର୍  | 35% | `threshold / max(value, ε)`                             |
| ତ୍ରୁଟି ସ୍କୋର୍    | 35% | `threshold / max(value, ε)`                             |
| ସ୍ୱାସ୍ଥ୍ୟ ସ୍କୋର୍ | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)       |
| ଖର୍ଚ୍ଚ ସ୍କୋର୍    | 10% | `threshold / max(value, ε)` କିମ୍ବା ବିପରୀତ ସ୍ୱାଭାବିକୀକୃତ |
| ସ୍ଥିରତା ସ୍କୋର୍   | 5%  | ବିପରୀତ ସ୍ୱାଭାବିକୀକୃତ ବିଳମ୍ବତା ମାନକ ବିଚ୍ୟୁତି             |

`hardConstraints: true` ଥିବାବେଳେ, ପ୍ରାର୍ଥୀମାନଙ୍କୁ ପ୍ରଥମେ **ଉଲ୍ଲଂଘନ ସ୍କୋର୍**
(ସେମାନେ କୌଣସି SLOକୁ କେତେ ଅତିକ୍ରମ କରନ୍ତି), ଏବଂ ତା’ପରେ ସଂଯୁକ୍ତ ସ୍କୋର୍ ଅନୁସାରେ ସଜାଯାଏ। ଅନ୍ୟଥା, କେବଳ
ସଂଯୁକ୍ତ ସ୍କୋର୍ ବ୍ୟବହାର କରାଯାଏ।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ନୀତି ସହିତ ତୁଳନା କରି ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀଙ୍କୁ ସ୍କୋର୍ କରେ: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ଫିଲ୍ଡଗୁଡ଼ିକ** (କମ୍ବୋ ବିନ୍ୟାସରେ ସେଟ୍ କରନ୍ତୁ):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: କଠୋର ବିଳମ୍ବତା, ତ୍ରୁଟି-ହାର କିମ୍ବା ଖର୍ଚ୍ଚ ବଜେଟ୍ ଥିବା ପ୍ରଡକ୍ସନ୍ କାର୍ଯ୍ୟଭାର ପାଇଁ।

**ଉପନାମଗୁଡ଼ିକ**: `sla-aware`, `sla`

---

#### 5. `lkgp` — ଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରଦାତା ପ୍ରଥମେ

ପ୍ରଥମେ **ଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରଦାତା**ଙ୍କୁ (ସେଟ୍ ହୋଇଥିଲେ) ଚେଷ୍ଟା କରେ, ତା’ପରେ
`rules` କୌଶଳକୁ ଫଲ୍‌ବ୍ୟାକ୍ କରେ। ସେସନ୍ ସ୍ଥିରତା ପାଇଁ ଉପଯୋଗୀ — ଏକେ ପ୍ରଦାତା
ବାର୍ତ୍ତାଳାପର ପରବର୍ତ୍ତୀ ଅନୁରୋଧଗୁଡ଼ିକୁ ପରିଚାଳନା କରନ୍ତି।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // rules କୌଶଳକୁ ଫଲ୍‌ବ୍ୟାକ୍ କରନ୍ତୁ
    return getStrategy("rules").select(pool, context);
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ଯେଉଁ ବହୁ-ପର୍ଯ୍ୟାୟ ବାର୍ତ୍ତାଳାପରେ ଆପଣ ଚାହାନ୍ତି ଯେ ଏକେ ପ୍ରଦାତା
ପରବର୍ତ୍ତୀ ଅନୁରୋଧଗୁଡ଼ିକୁ ପରିଚାଳନା କରନ୍ତୁ (ଯଥା, କ୍ୟାଶିଂ, ପ୍ରସଙ୍ଗ ନିରନ୍ତରତା କିମ୍ବା ମୂଲ୍ୟ ସ୍ଥିରତା ପାଇଁ)।

**ଉପନାମ**: `lkgp` (କୌଣସି ଉପନାମ ନାହିଁ)

---

### କଷ୍ଟମ୍ ରାଉଟର୍ କୌଶଳଗୁଡ଼ିକ

ଆପଣ ସାର୍ବଜନୀନ API ମାଧ୍ୟମରେ ନିଜର `RouterStrategy` ରୂପାୟନ ପଞ୍ଜୀକରଣ କରିପାରିବେ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // ଆପଣଙ୍କ ରାଉଟିଂ ତର୍କ ଏଠାରେ
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ତା’ପରେ ଏହାକୁ ବ୍ୟବହାର କରନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```


## କାର୍ଯ୍ୟ ଉପଯୁକ୍ତତା

6ଟି କାର୍ଯ୍ୟ ପ୍ରକାର (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) ମଧ୍ୟରେ 30+ ମଡେଲ୍‌କୁ ସ୍କୋର୍ କରାଯାଇଛି। ୱାଇଲ୍ଡକାର୍ଡ ପ୍ୟାଟର୍ନଗୁଡ଼ିକୁ ସମର୍ଥନ କରେ (ଉଦାହରଣ ସ୍ୱରୂପ, `*-coder` → ଉଚ୍ଚ କୋଡିଂ ସ୍କୋର୍)।

## Auto ଭାରିଆଣ୍ଟଗୁଡ଼ିକର ସାରାଂଶ

ଡିଫଲ୍ଟ ଖାଲି `auto` ସହିତ `autoPrefix.ts`ରେ ଘୋଷିତ 6ଟି `AutoVariant` ମୂଲ୍ୟକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରି, **7ଟି ଆହ୍ୱାନଯୋଗ୍ୟ ମଡେଲ୍ ID** ଅଛି:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ନିଜେ 6ଟି ମୂଲ୍ୟ ଗଣନା କରେ; 7ମ ବିକଳ୍ପଟି ହେଉଛି "କୌଣସି ଭାରିଆଣ୍ଟ ନାହିଁ" — ଖାଲି `auto` — ଯାହାକୁ `parseAutoPrefix()` ଦ୍ୱାରା `variant: undefined` ଭାବେ ପରିଚାଳନା କରାଯାଏ।)

## ଟିୟର୍‌ଗୁଡ଼ିକ Auto-Comboରେ କିପରି ଖାପ ଖାଏ

16-ଫ୍ୟାକ୍ଟର୍ ସ୍କୋରିଂ ଫଙ୍କସନ୍ (`open-sse/services/autoCombo/scoring.ts`) ଟିୟର୍
ସଦସ୍ୟତାକୁ ଦୁଇଟି ସିଗ୍ନାଲ୍ ଭାବେ ବ୍ୟବହାର କରେ: `tierPriority` (0.0476) ଏବଂ `tierAffinity` (0.0476)। ସମ୍ପୂର୍ଣ୍ଣ
`DEFAULT_WEIGHTS` ସେଟ୍ ପାଇଁ ଉପରେ ଥିବା ପ୍ରାମାଣିକ [ସ୍କୋରିଂ ଫ୍ୟାକ୍ଟର୍ ଟେବୁଲ୍](#how-it-works-persisted-auto-combos) ଦେଖନ୍ତୁ
— ପ୍ରତି-ପ୍ୟାକ୍ ଓଭର୍‌ରାଇଡ୍‌ଗୁଡ଼ିକ (ship-fast/cost-saver/quality-first/
offline-friendly) "ପ୍ରତି ପ୍ୟାକ୍‌ର ଓଜନ ପ୍ରୋଫାଇଲ୍" ଟେବୁଲ୍‌ରେ ତାଲିକାଭୁକ୍ତ ହୋଇଛି।

କେବଳ ଟିୟର୍ **Tier 1**କୁ ପ୍ରଥମେ ଆସିବାକୁ ବାଧ୍ୟ କରେ ନାହିଁ — ଯଦି **Tier 1**ର ବିଳମ୍ବତା ଖରାପ ଥାଏ କିମ୍ବା
ମୂଲ୍ୟ-ବନାମ-ଗୁଣବତ୍ତା ଅନୁକୂଳ ନଥାଏ, ତେବେ **Tier 2** ବିଜୟୀ ହୁଏ। ଟିୟର୍ କ୍ରମକୁ ବାଧ୍ୟତାମୂଳକ କରିବା ପାଇଁ, କମ୍ବୋ
କୌଶଳ `priority` ବ୍ୟବହାର କରନ୍ତୁ ଏବଂ ପ୍ରଦାତାମାନଙ୍କୁ ଟିୟର୍ ଅନୁସାରେ ସଜାନ୍ତୁ।

**Tier 1** (ସଦସ୍ୟତା)କୁ ଦୃଢ଼ ଭାବରେ ପ୍ରାଧାନ୍ୟ ଦେବା ପାଇଁ `tierPriority`ର ଓଜନ ବଢ଼ାନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ଟିୟର୍ ସଂଜ୍ଞା ଏବଂ ପ୍ରଦାତା ବର୍ଗୀକରଣ ପାଇଁ `docs/marketing/TIERS.md` ଦେଖନ୍ତୁ।

## ପରୀକ୍ଷଣ ଏବଂ କଭରେଜ୍

### ନିର୍ଦ୍ଧାରିତ ରାଉଟିଂ-ନିଷ୍ପତ୍ତି ମ୍ୟାଟ୍ରିକ୍ସ (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ଏକ ମକ୍ କରାଯାଇଥିବା ଅପ୍‌ଷ୍ଟ୍ରିମ୍ ସହିତ ବାସ୍ତବ କମ୍ବୋ ପାଇପ୍‌ଲାଇନ୍ ମାଧ୍ୟମରେ ସମସ୍ତ 19ଟି
ସାର୍ବଜନୀନ କୌଶଳର ଏଣ୍ଡ-ଟୁ-ଏଣ୍ଡ ରାଉଟିଂ **ନିଷ୍ପତ୍ତି**କୁ ପ୍ରମାଣ କରେ।
କଭରେଜ୍‌ରେ ଅନ୍ତର୍ଭୁକ୍ତ:

- ସମସ୍ତ 19ଟି `ROUTING_STRATEGY_VALUES` କୌଶଳ (କ୍ରମବଦ୍ଧ, ଓଜନଯୁକ୍ତ, ମୂଲ୍ୟ, ପ୍ରସଙ୍ଗ, ଫ୍ୟୁଜନ୍, …)।
- `quota-share` (ଆଭ୍ୟନ୍ତରୀଣ) ଏଣ୍ଡ-ଟୁ-ଏଣ୍ଡ: ବାସ୍ତବ `selectQuotaShareTarget` ସିମ୍ ମାଧ୍ୟମରେ DRR ନିରପେକ୍ଷତା + ସାଚୁରେସନ୍ ପ୍ରାଥମିକତା ହ୍ରାସ
  (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)।
- ପ୍ରତ୍ୟେକ ଟାର୍ଗେଟ୍ ସଂଖ୍ୟାରେ `context-relay` ସାର୍ବଜନୀନ-ହ୍ୟାଣ୍ଡଅଫ୍ କଭରେଜ୍।

ଏହି ସୁଇଟ୍ CIରେ (`test:integration` ଜବ୍) `--test-concurrency=1` ଏବଂ
`--test-force-exit` ସହିତ ଚାଲେ, ତେଣୁ ଏହା ନିର୍ଦ୍ଧାରିତ ଏବଂ ଲାଇଭ୍ କ୍ରେଡେନ୍ସିଆଲ୍‌ର ଆବଶ୍ୟକତା ନାହିଁ।

### ଗେଟେଡ୍ ଲାଇଭ୍ ସ୍ମୋକ୍ ପରୀକ୍ଷା (CIରେ ନୁହେଁ — ବାସ୍ତବ ପ୍ରଦାତା)

| କମାଣ୍ଡ୍                                | ଏହା କ’ଣ କରେ                                                                               |
| :------------------------------------- | :---------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` ସହିତ ଇନ୍-ପ୍ରୋସେସ୍ ବାସ୍ତବ ରାଉଟିଂ; ଏକ ଲାଇଭ୍ OmniRoute DBର ସ୍ନାପ୍‌ସଟ୍ ନିଏ |
| `npm run test:combo:live:vps`          | ଏକ ଲାଇଭ୍ OmniRoute ସର୍ଭର୍ ବିରୁଦ୍ଧରେ HTTP କଲ୍‌ଗୁଡ଼ିକ (`COMBO_LIVE_BASE_URL` ସେଟ୍ କରନ୍ତୁ)   |

ଏହି ସ୍ମୋକ୍ ପରୀକ୍ଷାଗୁଡ଼ିକ ବାସ୍ତବ ୱାୟାର୍ ପଥ (କମ୍ବୋ → ପ୍ରଦାତା → ସମ୍ପୂର୍ଣ୍ଣତା)କୁ ପରୀକ୍ଷା କରେ। ଏଗୁଡ଼ିକୁ
ଇଚ୍ଛାକୃତ ଭାବେ CIରୁ ବାଦ ଦିଆଯାଇଛି, କାରଣ ଏଗୁଡ଼ିକ ପାଇଁ ଲାଇଭ୍ କ୍ରେଡେନ୍ସିଆଲ୍ ଏବଂ VPS ଆକ୍ସେସ୍ ଆବଶ୍ୟକ।
