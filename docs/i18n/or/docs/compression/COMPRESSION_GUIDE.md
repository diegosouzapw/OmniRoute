> ଯୋଗ୍ୟ context ଉପରେ ସ୍ୱୟଂଚାଳିତ ଭାବେ 15-95% ସଞ୍ଚୟ କରନ୍ତୁ। ଏକ ଦ୍ରୁତ ସମୀକ୍ଷା ପାଇଁ, [README Compression ବିଭାଗ](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) ଦେଖନ୍ତୁ।

## ସାରାଂଶ

OmniRoute ଏକ ମଡ୍ୟୁଲାର୍ prompt compression pipeline କାର୍ଯ୍ୟକାରୀ କରେ, ଯାହା ଅନୁରୋଧଗୁଡ଼ିକ upstream providerଙ୍କ ପାଖରେ ପହଞ୍ଚିବା **ପୂର୍ବରୁ ସକ୍ରିୟ ଭାବେ** ଚାଲେ। ଏହାର ଅର୍ଥ ଆପଣଙ୍କ token ସଞ୍ଚୟ ସ୍ୱଚ୍ଛ ଭାବେ ହୁଏ — ଆପଣଙ୍କ workflowରେ କୌଣସି ପରିବର୍ତ୍ତନ ଦରକାର ନାହିଁ।

```
କ୍ଲାଏଣ୍ଟ ଅନୁରୋଧ
  → Compression କୌଶଳ ଚୟନକାରୀ
    → Combo override? → Combo ସେଟିଂ ବ୍ୟବହାର କରନ୍ତୁ
    → ସ୍ୱୟଂଚାଳିତ-ଟ୍ରିଗର୍ ସୀମା? → Auto mode ବ୍ୟବହାର କରନ୍ତୁ
    → ଡିଫଲ୍ଟ mode? → Global ସେଟିଂ ବ୍ୟବହାର କରନ୍ତୁ
    → ବନ୍ଦ? → Compression ଏଡ଼ାଇ ଯାଆନ୍ତୁ
  → ଚୟନିତ Compression Mode
    → ବନ୍ଦ: କୌଣସି compression ନାହିଁ
    → Lite: ସୁରକ୍ଷିତ whitespace/formatting ସଫେଇ (~15%)
    → Standard: Caveman-ଶୈଳୀର filler ଅପସାରଣ (~30%)
    → Aggressive: History aging + ସାରାଂଶକରଣ (~50%)
    → Ultra: Heuristic pruning + code-block thinning (~75%)
    → RTK: Command-aware terminal/tool-output filtering (60-90% upstream ପରିସର)
    → Stacked: କ୍ରମବଦ୍ଧ multi-engine pipeline, ସାଧାରଣତଃ ପ୍ରଥମେ RTK ଏବଂ ପରେ Caveman (78-95% ଯୋଗ୍ୟ ପରିସର)
  → ସଂକୁଚିତ ଅନୁରୋଧ → Provider
```

## Compression Modeଗୁଡ଼ିକ

### ବନ୍ଦ

କୌଣସି compression ପ୍ରୟୋଗ କରାଯାଏ ନାହିଁ। ସମସ୍ତ message ଅପରିବର୍ତ୍ତିତ ଭାବେ ପାର ହୁଏ।

### Lite Mode (~15% ସଞ୍ଚୟ, <1ms ବିଳମ୍ବ)

ସବୁଠାରୁ ସୁରକ୍ଷିତ mode — କୌଣସି ଅର୍ଥଗତ ପରିବର୍ତ୍ତନ ନାହିଁ, କେବଳ formatting ସଫେଇ:

| ପ୍ରକ୍ରିୟା                | ବର୍ଣ୍ଣନା                                                |
| ------------------------ | ------------------------------------------------------- |
| `collapseWhitespace`     | କ୍ରମାଗତ ଖାଲି ଧାଡ଼ି ଏବଂ ଶେଷରେ ଥିବା spaceଗୁଡ଼ିକୁ ମିଶାନ୍ତୁ |
| `dedupSystemPrompt`      | ନକଲ system messageଗୁଡ଼ିକୁ ଅପସାରଣ କରନ୍ତୁ                 |
| `compressToolResults`    | ବିସ୍ତୃତ tool/function outputକୁ ସଂକୁଚିତ କରନ୍ତୁ           |
| `removeRedundantContent` | ପୁନରାବୃତ୍ତ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ ହଟାନ୍ତୁ                     |
| `replaceImageUrls`       | base64 image data URIଗୁଡ଼ିକୁ ସଂକ୍ଷିପ୍ତ କରନ୍ତୁ           |

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ସର୍ବଦା-ସକ୍ରିୟ ବ୍ୟବହାର, ସୁରକ୍ଷା-ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ workflow।

### Standard Mode (~30% ସଞ୍ଚୟ)

[Caveman](https://github.com/JuliusBrussee/caveman) ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ — ଅର୍ଥ ସଂରକ୍ଷଣ କରି filler ଶବ୍ଦ ଏବଂ ଅତି-ବିସ୍ତୃତ ବାକ୍ୟାଂଶକୁ ଅପସାରଣ କରେ:

- filler ଶବ୍ଦଗୁଡ଼ିକୁ ଅପସାରଣ କରେ ("ଦୟାକରି", "ମୁଁ ଭାବୁଛି", "ମୂଳତଃ", "ବାସ୍ତବରେ")
- ଅତି-ବିସ୍ତୃତ ବାକ୍ୟାଂଶକୁ ସଂକ୍ଷିପ୍ତ କରେ ("କରିବା ଉଦ୍ଦେଶ୍ୟରେ" → "କରିବାକୁ", "ର ଫଳସ୍ୱରୂପ" → "କାରଣ")
- ବିନମ୍ର ଦ୍ୱିଧାସୂଚକ ବାକ୍ୟାଂଶକୁ ହଟାଏ ("ଆପଣ କ’ଣ...", "ଯଦି ଆପଣ ସମ୍ଭବତଃ...")
- coding prompt ପାଇଁ ସମନ୍ୱୟ କରାଯାଇଥିବା 30+ regex rule

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ଦୈନନ୍ଦିନ coding workflow, ଖର୍ଚ୍ଚ-ସଚେତନ team।

### Aggressive Mode (~50% ସଞ୍ଚୟ)

ଦୀର୍ଘ session ପାଇଁ ବୁଦ୍ଧିମାନ history ପରିଚାଳନା:

- **Message Aging** — ପୁରୁଣା messageଗୁଡ଼ିକ କ୍ରମଶଃ ଅଧିକ ସଂକୁଚିତ ହୁଏ
- **Tool Result Summarization** — ଦୀର୍ଘ tool outputକୁ ସାରାଂଶ ସହ ବଦଳାଯାଏ
- **Structural Integrity Guards** — `tool_use` + `tool_result` ଯୋଡ଼ିଗୁଡ଼ିକ ସୁସଙ୍ଗତ ରହିବା ସୁନିଶ୍ଚିତ କରେ
- **Context Window Awareness** — ପ୍ରତ୍ୟେକ modelର token ସୀମାକୁ ସମ୍ମାନ କରେ

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ବିସ୍ତୃତ debugging session, ବଡ଼ codebase।

### Ultra Mode (~75% ସଞ୍ଚୟ)

Token-ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ପରିସ୍ଥିତି ପାଇଁ ସର୍ବାଧିକ compression:

- **Heuristic Pruning** — ପ୍ରାସଙ୍ଗିକତା ସୀମାଠାରୁ ନିମ୍ନରେ ଥିବା messageଗୁଡ଼ିକୁ ଅପସାରଣ କରେ
- **Code Block Thinning** — ପୁନରାବୃତ୍ତ code ଉଦାହରଣଗୁଡ଼ିକୁ ସଂକୁଚିତ କରେ
- **Binary Search Truncation** — context window ପାଇଁ ସର୍ବୋତ୍ତମ cut point ଖୋଜେ
- Aggressive modeର ସମସ୍ତ ବୈଶିଷ୍ଟ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ଯେତେବେଳେ ଆପଣ ବାରମ୍ବାର context ସୀମାରେ ପହଞ୍ଚୁଛନ୍ତି।

### RTK Mode (60-90% upstream ପରିସର)

RTK modeକୁ coding-agent sessionରେ ଦେଖାଯାଉଥିବା ବିସ୍ତୃତ tool output ପାଇଁ ଅନୁକୂଳିତ କରାଯାଇଛି:

- `git status`, `git diff`, `git log`, test runner,
  TypeScript/Vite/Webpack build, ESLint/Biome/Prettier, npm audit/install, Docker log, infra
  output ଏବଂ generic shell output ଭଳି command/output class ଚିହ୍ନଟ କରେ
- `open-sse/services/compression/engines/rtk/filters/`ରୁ JSON filter pack ପ୍ରୟୋଗ କରେ
- inline-test validation ଏବଂ project file ପାଇଁ trust-gating ସହିତ project କିମ୍ବା global `filters.toml` fileରୁ RTK TOML schema v1 filter import କରେ
- inline verify sample ସହ 49ଟି built-in filter ପ୍ରଦାନ କରେ
- ANSI control sequence, progress bar, ପୁନରାବୃତ୍ତ ଧାଡ଼ି ଏବଂ କାର୍ଯ୍ୟଯୋଗ୍ୟ ନଥିବା noiseକୁ ଅପସାରଣ କରେ
- failure, error, warning, ପରିବର୍ତ୍ତିତ file, ସାରାଂଶ ଏବଂ ଦୀର୍ଘ outputର ଶେଷ ଭାଗକୁ ସଂରକ୍ଷଣ କରେ
- trust-gated project filter, global filter ଏବଂ ଇଚ୍ଛାଧୀନ ଭାବେ redacted raw-output recoveryକୁ ସମର୍ଥନ କରେ

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** shell, build, test, git, grep ଏବଂ file-output transcript ସହିତ agent session।

### Stacked Mode (78-95% ଯୋଗ୍ୟ ପରିସର)

Stacked mode ଏକ ନିର୍ଦ୍ଧାରିତ କ୍ରମରେ ଏକାଧିକ compression engine ଚଲାଏ। ଡିଫଲ୍ଟ pipeline ହେଉଛି:

```txt
RTK -> Caveman
```

ସେହି କ୍ରମ ପ୍ରଥମେ terminal/tool outputକୁ ସଂକ୍ଷିପ୍ତ ରଖେ, ତା’ପରେ ଅବଶିଷ୍ଟ natural-language promptରେ Caveman semantic condensation ପ୍ରୟୋଗ କରେ। Stacked pipelineକୁ global ଭାବେ କିମ୍ବା routing comboକୁ ନ୍ୟସ୍ତ compression combo ମାଧ୍ୟମରେ configure କରାଯାଇପାରେ।

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ବଡ଼ tool log ସହିତ ମାନବୀୟ ନିର୍ଦ୍ଦେଶ କିମ୍ବା assistant ସାରାଂଶ ଥିବା ମିଶ୍ରିତ context।

## ଅପ୍ଷ୍ଟ୍ରିମ୍ ସଞ୍ଚୟ ଗଣନା

OmniRoute ଦୁଇଟି ଉତ୍ସରୁ ମିଳୁଥିବା କମ୍ପ୍ରେସନ୍ ସଞ୍ଚୟକୁ ଡକ୍ୟୁମେଣ୍ଟ କରେ: ଅପ୍ଷ୍ଟ୍ରିମ୍ ପ୍ରକଳ୍ପ ବେଞ୍ଚମାର୍କ ଏବଂ
OmniRoute ର ନିଜସ୍ୱ ଇଞ୍ଜିନ୍ ସଂଯୋଜନ।

| ଉତ୍ସ    | ଏଠାରେ ବ୍ୟବହୃତ ଅପ୍ଷ୍ଟ୍ରିମ୍ README ସଂଖ୍ୟା                                                                                 |
| ------- | ----------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` କମ୍ ଆଉଟ୍ପୁଟ୍ ଟୋକନ୍, `65%` ବେଞ୍ଚମାର୍କ ହାରାହାରି ଆଉଟ୍ପୁଟ୍ ସଞ୍ଚୟ, `22-87%` ପରିସର, ଏବଂ `~46%` ଇନ୍ପୁଟ୍ କମ୍ପ୍ରେସନ୍ ଟୁଲ୍ |
| RTK     | କମାଣ୍ଡ ଆଉଟ୍ପୁଟ୍ରେ `60-90%` ସଞ୍ଚୟ; ନମୁନା ସେସନ୍ରେ `~118,000 -> ~23,900` ଟୋକନ୍, କିମ୍ବା `79.7%` ସଞ୍ଚିତ (`~80%`)             |

ପରସ୍ପର ଆଚ୍ଛାଦିତ ଟୁଲ୍/କନ୍ଟେକ୍ସ୍ଟ ପେଲୋଡ୍ଗୁଡ଼ିକ ପାଇଁ, ଡିଫଲ୍ଟ OmniRoute କମ୍ବୋ ଇଞ୍ଜିନ୍ଗୁଡ଼ିକୁ ଷ୍ଟାକ୍ କରେ:

```txt
RTK -> Caveman
```

ମିଳିତ ସଞ୍ଚୟ ଯୋଗାତ୍ମକ ନୁହେଁ, ଗୁଣାତ୍ମକ ଅଟେ:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ଯେତେବେଳେ RTK ଏବଂ Caveman ଉଭୟ ଏକେ ଇନ୍ପୁଟ୍/କନ୍ଟେକ୍ସ୍ଟ ପେଲୋଡ୍କୁ ହ୍ରାସ କରିପାରନ୍ତି, ସେତେବେଳେ ସେହି `78-95%` ସଂଖ୍ୟା ପ୍ରଯୁଜ୍ୟ।
Caveman ରେସ୍ପନ୍ସ ଆଉଟ୍ପୁଟ୍ ମୋଡ୍ ଅଲଗା: ଏହା ସକ୍ଷମ ଥିଲେ, Caveman ର ନିଜସ୍ୱ ଆଉଟ୍ପୁଟ୍ ସଞ୍ଚୟ (`65%`
ହାରାହାରି, `~75%` ମୁଖ୍ୟ ଆକଳନ, `22-87%` ପରିସର) ବ୍ୟବହାର କରନ୍ତୁ। ସମୁଦାୟ ବିଲିଂ ସଞ୍ଚୟ ଆପଣଙ୍କ ପ୍ରମ୍ପ୍ଟ/ଆଉଟ୍ପୁଟ୍ ମିଶ୍ରଣ ଉପରେ ନିର୍ଭର କରେ।

### "ଯୋଗ୍ୟ"ର ପ୍ରକୃତ ଅର୍ଥ କ’ଣ

15-95% ମୁଖ୍ୟ ପରିସରଟି ବାସ୍ତବ, କିନ୍ତୁ ଏହା କେବଳ **ଅନାବଶ୍ୟକ ଭାବେ ପୁନରାବୃତ୍ତ କିମ୍ବା ଅତ୍ୟଧିକ ବିସ୍ତୃତ** ବିଷୟବସ୍ତୁ ପାଇଁ ପ୍ରଯୁଜ୍ୟ — ପୁନରାବୃତ୍ତ
ତ୍ରୁଟି ଲାଇନ୍, ସମାନ ଚେତାବନୀକୁ ବାରମ୍ବାର ଦେଖାଉଥିବା ଏକ ବିଲ୍ଡ ଲଗ୍, ଏକ ଅତ୍ୟଧିକ ବଡ଼ `grep`/ଫାଇଲ୍-ରିଡ୍ ଡମ୍ପ। ଏହାର ଅର୍ଥ
**ଏହା ନୁହେଁ** ଯେ ପ୍ରତ୍ୟେକ ରିକ୍ୱେଷ୍ଟରେ ଏତେ ସଞ୍ଚୟ ହୁଏ।

ପରୀକ୍ଷାମୂଳକ ଭାବେ ଯାଞ୍ଚ କରାଯାଇଛି (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300ଟି ସମାନ
ତ୍ରୁଟି ଲାଇନ୍ ଥିବା Anthropic-ଆକୃତିର `tool_result` ବ୍ଲକ୍ ବିପକ୍ଷରେ ଏକ `stacked` (RTK + Caveman) ରନ୍
**95.93% ଟୋକନ୍ ସଞ୍ଚୟ / 96.26% କ୍ୟାରେକ୍ଟର୍ ସଞ୍ଚୟ** ପ୍ରଦାନ କରିଥିଲା — ଯାହା ପ୍ରଚାରିତ ପରିସର ମଧ୍ୟରେ ସ୍ପଷ୍ଟ ଭାବରେ ରହିଛି।
କିନ୍ତୁ ସାଧାରଣ, ପୁନରାବୃତ୍ତି-ବିହୀନ ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ (ଏକ ସ୍ୱଚ୍ଛ `grep` ମ୍ୟାଚ୍ ତାଲିକା,
ଏକ ଛୋଟ ଫାଇଲ୍ ରିଡ୍, ସାଧାରଣ ବାର୍ତ୍ତାଳାପମୂଳକ ପାଠ୍ୟ) ବିପକ୍ଷରେ ସମାନ ପାଇପ୍ଲାଇନ୍ ରନ୍ ସଠିକ୍ ଭାବରେ **ପ୍ରାୟ-ଶୂନ୍ୟ ସଞ୍ଚୟ** ପ୍ରଦାନ କରେ, କାରଣ
ଅପସାରଣ କରିବାକୁ କୌଣସି ପୁନରାବୃତ୍ତି ନାହିଁ ଏବଂ `validateCompression()` (`validation.ts`) ଏପରି କୌଣସି
ପୁନର୍ଲିଖନକୁ ପଠାଇବାକୁ ମନା କରେ, ଯାହା କୋଡ୍ ବ୍ଲକ୍, URL, ହେଡିଂ, ଭର୍ସନ୍ କିମ୍ବା ALL-CAPS କନ୍ଷ୍ଟାଣ୍ଟ ଆଇଡେଣ୍ଟିଫାୟର୍ଗୁଡ଼ିକୁ ବାଦ ଦେବ କିମ୍ବା ପରିବର୍ତ୍ତନ କରିବ।

ଏହା ଆଶାକରାଯାଇଥିବା ସୁରକ୍ଷିତ ଆଚରଣ, କୌଣସି ବଗ୍ ନୁହେଁ: ମୁଖ୍ୟତଃ ସ୍ୱଚ୍ଛ ଫାଇଲ୍ଗୁଡ଼ିକୁ ପଢ଼ୁଥିବା/grep କରୁଥିବା ଏକ କୋଡିଂ ସେସନ୍ରେ
କମ୍ପ୍ରେସନ୍ ସମ୍ପୂର୍ଣ୍ଣ ସକ୍ଷମ ଥିଲେ ମଧ୍ୟ ସାମାନ୍ୟ ସମୁଦାୟ ସଞ୍ଚୟ ଦେଖାଯିବ, ଯେତେବେଳେ ଏକ ବିଫଳ
ଲୁପ୍ କିମ୍ବା ଅତ୍ୟଧିକ ଆଉଟ୍ପୁଟ୍ ଦେଉଥିବା ଲିଣ୍ଟର୍ର ସମ୍ମୁଖୀନ ହେଉଥିବା ସେସନ୍ରେ ସେହି ଟ୍ରାଫିକ୍ ଉପରେ ସମ୍ପୂର୍ଣ୍ଣ 78-95% ପରିସର ଦେଖାଯିବ। କମ୍ ସମଗ୍ର ସଞ୍ଚୟ
ପ୍ରତିଶତ ଥିବା ଗୋଟିଏ ସେସନ୍କୁ କମ୍ପ୍ରେସନ୍ ଭୁଲ ଭାବେ କନ୍ଫିଗର୍ ହୋଇଥିବାର ପ୍ରମାଣ ଭାବେ ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ — ପ୍ରଥମେ ଯାଞ୍ଚ କରନ୍ତୁ ଯେ
ଅନ୍ତର୍ନିହିତ ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ ପ୍ରକୃତରେ ପୁନରାବୃତ୍ତ ଥିଲା କି ନାହିଁ।

### ଡ୍ୟାସବୋର୍ଡ

`Dashboard → Context & Cache` କୁ ଯାଆନ୍ତୁ:

- **କେଭମ୍ୟାନ୍** — ମୋଡ୍ ଚୟନ, ଭାଷା ପ୍ୟାକ୍, ପୂର୍ବାବଲୋକନ, ଏବଂ ଗ୍ଲୋବାଲ୍ ଡିଫଲ୍ଟ
- **RTK** — କମାଣ୍ଡ-ଫିଲ୍ଟର ପୂର୍ବାବଲୋକନ, RTK ସୁରକ୍ଷା ସେଟିଂସମୂହ, ଏବଂ ଫିଲ୍ଟର କାଟାଲଗ୍
- **ସଙ୍କୋଚନ କମ୍ବୋସ୍** — ରାଉଟିଂ କମ୍ବୋସ୍ କୁ ନିର୍ଦ୍ଦିଷ୍ଟ ଇଞ୍ଜିନ୍ ପାଇପଲାଇନ୍
- **ସ୍ୱୟଂ-ଟ୍ରିଗର ଥ୍ରେସହୋଲ୍ଡ** — ଯେତେବେଳେ ଟୋକେନ୍ ଗଣନା ଥ୍ରେସହୋଲ୍ଡ ଅତିକ୍ରମ କରେ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ସଙ୍କୋଚନକୁ ନିୟୋଜିତ କରନ୍ତୁ

### ପ୍ରତି-କମ୍ବୋ ଓଭରରାଇଡ୍

`Dashboard → Context & Cache → Compression Combos` ରେ, ଏକ ରାଉଟିଂ କମ୍ବୋକୁ ଏକ ସଙ୍କୋଚନ କମ୍ବୋ ନିର୍ଦ୍ଦିଷ୍ଟ କରନ୍ତୁ:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ଏହା ଆପଣଙ୍କୁ ମାଗଣା/କୋଡିଂ ପ୍ରଦାନକାରୀଙ୍କ ଉପରେ ଷ୍ଟାକଡ୍ ସଙ୍କୋଚନ ବ୍ୟବହାର କରିବାକୁ ଅନୁମତି ଦିଏ ଯେତେବେଳେ ପେଡ୍ ସବସ୍କ୍ରିପସନ୍ ଉପରେ ଲାଇଟ୍ ମୋଡ୍ ରଖିଥାଏ।

ଏହି "ପ୍ରତି-କମ୍ବୋ ଓଭରରାଇଡ୍" ନିର୍ଦ୍ଦିଷ୍ଟକରଣ **ରାଉଟିଂ-କମ୍ବୋ ସଙ୍କୋଚନ ମୋଡ୍** ଓଭରରାଇଡ୍ (Default/Off/Lite/Standard/Aggressive/Ultra) ଠାରୁ ଏକ ଭିନ୍ନ ନିୟନ୍ତ୍ରଣ — ସେହି ଓଭରରାଇଡ୍ ଏକ ନାମିତ ସଙ୍କୋଚନ-କମ୍ବୋ ପାଇପଲାଇନ୍ ବାଛି ନଥାଏ; ଏହା କେବଳ `resolveCompressionPlan` ଦ୍ୱାରା ପରାମର୍ଶିତ `compressionMode` ଫିଲ୍ଡ ସେଟ୍ କରେ। ଏହା କମ୍ବୋ କାର୍ଡ (`Dashboard → Combos`) ଉପରେ କିମ୍ବା, #6760 ପରଠାରୁ, `Dashboard → Context & Cache → Compression Combos` ଉପରେ "Assign to routing" ତାଲିକାରେ ପ୍ରତି ରାଉଟିଂ କମ୍ବୋ ପାଇଁ ସେଟ୍ କରାଯାଇପାରିବ, ଉପରେ ଡକ୍ୟୁମେଣ୍ଟ୍ ହୋଇଥିବା ପାଇପଲାଇନ୍-ନିର୍ଦ୍ଦିଷ୍ଟକରଣ ଚେକବକ୍ସ ପାଖରେ। ଉଭୟ ଇଣ୍ଟରଫେସ୍ ସମାନ `PUT /api/combos/{id}` ଏଣ୍ଡପଏଣ୍ଟ ମାଧ୍ୟମରେ ସ୍ଥାୟୀ ହୁଏ।

### ପ୍ରତି-ଅନୁରୋଧ ଓଭରରାଇଡ୍

ଏକକ ଅନୁରୋଧ ପାଇଁ ସଙ୍କୋଚନ ଯୋଜନାକୁ ଓଭରରାଇଡ୍ କରିବାକୁ `x-omniroute-compression` ଅନୁରୋଧ ହେଡର ପଠାନ୍ତୁ। ଏହାର ସର୍ବୋଚ୍ଚ ପ୍ରାଧାନ୍ୟ ଅଛି — ଏହା ରାଉଟିଂ-କମ୍ବୋ ଓଭରରାଇଡ୍, ସକ୍ରିୟ ପ୍ରୋଫାଇଲ୍, ଅଟୋ-ଟ୍ରିଗର, ଏବଂ ପ୍ୟାନେଲ୍ ଡିଫଲ୍ଟକୁ ଅତିକ୍ରମ କରେ। ଅଜ୍ଞାତ ମୂଲ୍ୟଗୁଡ଼ିକୁ ଅଣଦେଖା କରାଯାଏ (ଅନୁରୋଧ କେବେହେଲେ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ ନାହିଁ) ଏବଂ ଗ୍ଲୋବାଲ୍ ମାଷ୍ଟର ସୁଇଚ୍ ଏବେ ମଧ୍ୟ ସବୁକିଛିକୁ ନିୟନ୍ତ୍ରଣ କରେ: ଯେତେବେଳେ ସଙ୍କୋଚନ ଗ୍ଲୋବାଲ୍ ଭାବରେ ବନ୍ଦ ଥାଏ, ହେଡର ଏହାକୁ ଅନ୍ କରିପାରିବ ନାହିଁ। ମୂଲ୍ୟଗୁଡ଼ିକ:

| ମୂଲ୍ୟ         | ପ୍ରଭାବ                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| `off`         | ଏହି ଅନୁରୋଧ ପାଇଁ କୌଣସି ସଙ୍କୋଚନ ନାହିଁ।                                                                 |
| `default`     | ପ୍ୟାନେଲ୍-ଉତ୍ପନ୍ନ ଡିଫଲ୍ଟ ପ୍ରୋଫାଇଲ୍ (ସକ୍ରିୟ ପ୍ରୋଫାଇଲ୍କୁ ଅଣଦେଖା କରେ)। ଲୋସି ଇଞ୍ଜିନ୍ଗୁଡ଼ିକ ବନ୍ଦ ରଖାଯାଏ।   |
| `safe`        | ହେଡରକୁ ଛାଡିବା ସହିତ ସମାନ: କେବଳ ଡିଡୁପ୍ ଏବଂ ଧଳା ସ୍ଥାନ ଫୋଲ୍ଡିଂ।                                          |
| `allow-lossy` | ଏହି ଅନୁରୋଧର ଅପରେଟର ଯୋଜନା ରଖନ୍ତୁ, ସାରାଂଶ, ପ୍ରାସଙ୍ଗିକତା ଫିଲ୍ଟର, ଏବଂ ଶୈଳୀ ପୁନଃଲେଖା ସହିତ।                |
| `engine:<id>` | ସକ୍ଷମ ହେଲେ ଏକକ ଇଞ୍ଜିନ୍, ଉଦାହରଣ ସ୍ୱରୂପ `engine:rtk`। ଏହା ସେହି ଇଞ୍ଜିନ୍ ପାଇଁ ପ୍ରତି-ଅନୁରୋଧ ଅପ୍ଟ-ଇନ୍ ଅଟେ। |
| `<combo>`     | ଏକ ନାମିତ କମ୍ବୋ, ପ୍ରଥମେ ନାମ ଦ୍ୱାରା (କେସ୍-ଇନସେନସିଟିଭ୍), ତାପରେ id ଦ୍ୱାରା ମିଳିତ।                         |

`allow-lossy`, `engine:<id>`, କିମ୍ବା ଏକ ନାମିତ କମ୍ବୋ ବିନା, ଲୋସି ଇଞ୍ଜିନ୍ଗୁଡ଼ିକ ପ୍ରୟୋଗ କରାଯାଏ ନାହିଁ। ଯେତେବେଳେ ସଙ୍କୋଚନ ଅନ୍ ଥାଏ, ଅନୁରୋଧ ଏବେ ମଧ୍ୟ ସେସନ୍ ଡିଡୁପ୍ ଏବଂ ଧଳା ସ୍ଥାନ ଫୋଲ୍ଡିଂ ପାଇଥାଏ।

ପ୍ରୟୋଗ କରାଯାଇଥିବା ଯୋଜନା `X-OmniRoute-Compression: <mode>; source=<source>` ପ୍ରତିକ୍ରିୟା ହେଡରରେ ପ୍ରତିଧ୍ୱନିତ ହୁଏ, ଯେଉଁଠାରେ `<source>` ହେଉଛି `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, କିମ୍ବା `off` ମଧ୍ୟରୁ ଗୋଟିଏ।

### API

```bash
# ସଙ୍କୋଚନ ସେଟିଂସମୂହ ପ୍ରାପ୍ତ କରନ୍ତୁ
curl http://localhost:20128/api/settings/compression

# ସଙ୍କୋଚନ ସେଟିଂସମୂହ ଅପଡେଟ୍ କରନ୍ତୁ
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ RTK/ଷ୍ଟାକଡ୍ ପେଲୋଡ୍ ର ପୂର୍ବାବଲୋକନ କରନ୍ତୁ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK ଫିଲ୍ଟର ପ୍ୟାକ୍ ତାଲିକାଭୁକ୍ତ କରନ୍ତୁ
curl http://localhost:20128/api/context/rtk/filters

# ଐଚ୍ଛିକ କମାଣ୍ଡ ମେଟାଡାଟା ସହିତ RTK କୁ ସିଧାସଳଖ ପରୀକ୍ଷା କରନ୍ତୁ
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

- ✅ URL ଏବଂ ଫାଇଲ୍ ପାଥ୍ଗୁଡ଼ିକ
- ✅ JSON ଗଠନ ଏବଂ ସଂରଚିତ ଡାଟା
- ✅ ଆଇଡେଣ୍ଟିଫାୟର୍ ଏବଂ ସୁରକ୍ଷିତ ବୈଷୟିକ ଟୋକନ୍ଗୁଡ଼ିକ
- ✅ ଗାଣିତିକ ଏକ୍ସପ୍ରେସନ୍ଗୁଡ଼ିକ
- ✅ ଟୁଲ୍/ଫଙ୍କସନ୍ କଲ୍ ପରିଭାଷାଗୁଡ଼ିକ
- ✅ ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟଗୁଡ଼ିକ (lite ମୋଡ୍ରେ)

ପାସୱାର୍ଡ, ଟୋକନ୍ ଏବଂ ସିକ୍ରେଟ୍ଗୁଡ଼ିକୁ ଲୁଚାଇଦିଏ।

## ସ୍ୱୀକୃତି

Standard ମୋଡ୍ କମ୍ପ୍ରେସନ୍ ନିୟମଗୁଡ଼ିକ **[JuliusBrussee](https://github.com/JuliusBrussee)**ଙ୍କ **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) — ଭାଇରାଲ୍ "ଅଳ୍ପ ଟୋକନ୍ରେ କାମ ହେଉଥିବାବେଳେ ଅଧିକ ଟୋକନ୍ କାହିଁକି ବ୍ୟବହାର କରିବେ" ପ୍ରକଳ୍ପ — ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ। Caveman `~75%` କମ୍ ଆଉଟ୍ପୁଟ୍ ଟୋକନ୍, ବେଞ୍ଚମାର୍କରେ ହାରାହାରି `65%` ଆଉଟ୍ପୁଟ୍ ସଞ୍ଚୟ, `22-87%` ଆଉଟ୍ପୁଟ୍ ପରିସର ଏବଂ ଏକ `~46%` ଇନ୍ପୁଟ୍-କମ୍ପ୍ରେସନ୍ ଟୁଲ୍ ରିପୋର୍ଟ କରେ।

RTK ମୋଡ୍ **[RTK AI](https://github.com/rtk-ai)**ଙ୍କ **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** — ଟର୍ମିନାଲ୍, ବିଲ୍ଡ, ଟେଷ୍ଟ, git ଏବଂ ଟୁଲ୍-ଆଉଟ୍ପୁଟ୍ ଫିଲ୍ଟରିଂ ପାଇଁ ଉଚ୍ଚ-କାର୍ଯ୍ୟଦକ୍ଷତାସମ୍ପନ୍ନ କମାଣ୍ଡ-ଆଉଟ୍ପୁଟ୍ କମ୍ପ୍ରେସନ୍ ପ୍ରକଳ୍ପ — ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ। RTK `60-90%` ସଞ୍ଚୟ ରିପୋର୍ଟ କରେ, ଏବଂ ଏହାର README ନମୁନା ସେସନ୍ରେ `~80%` ସଞ୍ଚୟ ଦେଖାଯାଇଛି।

## ଉନ୍ନତ ସଙ୍କୋଚନ ପ୍ରଣାଳୀଗୁଡ଼ିକ

7ଟି ମାନକ ମୋଡ୍ ବ୍ୟତୀତ, OmniRouteରେ ଅନେକ ଉନ୍ନତ ସଙ୍କୋଚନ
ପ୍ରଣାଳୀ ଅନ୍ତର୍ଭୁକ୍ତ ଅଛି, ଯାହା ପ୍ରସଙ୍ଗ ଆଧାରରେ ସ୍ୱୟଂଚାଳିତ ଭାବେ କାମ କରେ।

### କ୍ୟାଶ୍-ସଚେତନ ସଙ୍କୋଚନ

କିଛି ପ୍ରଦାନକାରୀ (ଯେପରିକି ପ୍ରମ୍ପ୍ଟ କ୍ୟାଶିଂ ସହିତ Anthropic) **ପ୍ରମ୍ପ୍ଟ କ୍ୟାଶିଂ**
ସମର୍ଥନ କରନ୍ତି, ଯାହା ଖର୍ଚ୍ଚ ଏବଂ ବିଳମ୍ବତା ହ୍ରାସ କରିବା ପାଇଁ ସେମାନଙ୍କୁ ପ୍ରମ୍ପ୍ଟର କିଛି ଅଂଶ କ୍ୟାଶ୍ କରିବାକୁ ଦିଏ। କ୍ୟାଶିଂ
ସକ୍ଷମ ଥିବାବେଳେ, ଆକ୍ରମଣାତ୍ମକ ସଙ୍କୋଚନ ପ୍ରକୃତରେ କାର୍ଯ୍ୟଦକ୍ଷତାକୁ **କ୍ଷତିଗ୍ରସ୍ତ** କରିପାରେ,
କାରଣ ଏହା କ୍ୟାଶ୍ ହୋଇଥିବା ଟୋକନଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରି କ୍ୟାଶ୍କୁ ଅବୈଧ କରିଦିଏ।

`cachingAware.ts` ମଡ୍ୟୁଲ୍ **କ୍ୟାଶିଂ ପ୍ରସଙ୍ଗ ଚିହ୍ନଟ କରି** ଏବଂ
ସେହି ଅନୁସାରେ **ସଙ୍କୋଚନ କୌଶଳ ସମାୟୋଜନ କରି** ଏହାର ସମାଧାନ କରେ।

#### ଏହା କିପରି କାମ କରେ

1. **କ୍ୟାଶିଂ ପ୍ରସଙ୍ଗ ଚିହ୍ନଟ କରେ** — `cache_control` ଚିହ୍ନଗୁଡ଼ିକ ପାଇଁ ଅନୁରୋଧ ବଡିକୁ ସ୍କାନ୍ କରେ
2. **କ୍ୟାଶିଂ ପ୍ରଦାନକାରୀଙ୍କୁ ଚିହ୍ନଟ କରେ** — ଲକ୍ଷ୍ୟ ପ୍ରଦାନକାରୀ କ୍ୟାଶିଂ ସମର୍ଥନ କରନ୍ତି କି ନାହିଁ ଯାଞ୍ଚ କରେ
3. **କୌଶଳ ସମାୟୋଜନ କରେ** — କ୍ୟାଶିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ `aggressive`/`ultra`କୁ `standard`କୁ ଅବନମିତ କରେ
4. **ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ବାଦ୍ ଦିଏ** — ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟଗୁଡ଼ିକ ସାଧାରଣତଃ କ୍ୟାଶ୍ ହୋଇଥାଏ, ତେଣୁ ସେଗୁଡ଼ିକୁ ସଙ୍କୋଚନ କରେ ନାହିଁ
5. **ନିର୍ଦ୍ଧାରିତ ରୂପାନ୍ତରଣ ବ୍ୟବହାର କରେ** — କେବଳ ସୁସଙ୍ଗତ ଆଉଟପୁଟ୍ ଉତ୍ପାଦନ କରୁଥିବା ରୂପାନ୍ତରଣ ବ୍ୟବହାର କରେ

#### କୋଡ୍ ଉଦାହରଣ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← କ୍ୟାଶ୍ ଚିହ୍ନ
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### କେବେ ବ୍ୟବହାର କରିବେ

କ୍ୟାଶ୍-ସଚେତନ ସଙ୍କୋଚନ **ସର୍ବଦା ସକ୍ରିୟ** — କୌଣସି ବିନ୍ୟାସ ଆବଶ୍ୟକ ନାହିଁ। ଏହା କେବଳ ନିମ୍ନଲିଖିତ ସ୍ଥିତିରେ
ସକ୍ରିୟ ହୁଏ:

- ଅନୁରୋଧରେ `cache_control` ଚିହ୍ନ ଥାଏ
- ଲକ୍ଷ୍ୟ ପ୍ରଦାନକାରୀ ପ୍ରମ୍ପ୍ଟ କ୍ୟାଶିଂ ସମର୍ଥନ କରନ୍ତି (Anthropic, OpenAI, ଇତ୍ୟାଦି)

### କ୍ରମିକ ପୁରାତନତା

ଦୀର୍ଘ ବାର୍ତ୍ତାଳାପରେ ଅନେକ ସନ୍ଦେଶ ପର୍ଯ୍ୟାୟ ଜମା ହୁଏ, କିନ୍ତୁ ପୁରୁଣା ପର୍ଯ୍ୟାୟଗୁଡ଼ିକ କ୍ରମଶଃ କମ୍
ପ୍ରାସଙ୍ଗିକ ହୋଇଯାଆନ୍ତି। `progressiveAging.ts` ମଡ୍ୟୁଲ୍ **ପର୍ଯ୍ୟାୟ ଦୂରତା ଅନୁଯାୟୀ ସନ୍ଦେଶଗୁଡ଼ିକୁ ଅବନମିତ କରେ**:

- **ସାମ୍ପ୍ରତିକ ପର୍ଯ୍ୟାୟ (0-3)**: ଅବିକଳ ରଖାଯାଏ (ସମ୍ପୂର୍ଣ୍ଣ ବିବରଣୀ)
- **ମଧ୍ୟମ ପର୍ଯ୍ୟାୟ (4-8)**: ହାଲୁକା ସଙ୍କୋଚନ (ଖାଲି ସ୍ଥାନ, ଫର୍ମାଟିଂ ସଫାକରଣ)
- **ପୁରୁଣା ପର୍ଯ୍ୟାୟ (9+)**: କେଭ୍ମ୍ୟାନ୍ ସଙ୍କୋଚନ (ଅନାବଶ୍ୟକ ଶବ୍ଦ ଅପସାରଣ, ସାରାଂଶକରଣ)
- **ଅତି ପୁରୁଣା ପର୍ଯ୍ୟାୟ (20+)**: ବ୍ୟାପକ ଭାବେ ସାରାଂଶିତ କିମ୍ବା ବାଦ୍ ଦିଆଯାଏ

#### କୋଡ୍ ଉଦାହରଣ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ଆଉ 50ଟି ପର୍ଯ୍ୟାୟ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ପ୍ରଥମ 3ଟି ପର୍ଯ୍ୟାୟ: ଅବିକଳ
  light: 8, // ପର୍ଯ୍ୟାୟ 4-8: ହାଲୁକା ସଙ୍କୋଚନ
  moderate: 20, // ପର୍ଯ୍ୟାୟ 9-20: କେଭ୍ମ୍ୟାନ୍ ସଙ୍କୋଚନ
  // ପର୍ଯ୍ୟାୟ 21+: ବ୍ୟାପକ ସାରାଂଶକରଣ
});

// saved = ସଞ୍ଚୟ ହୋଇଥିବା ଟୋକନ୍ ସଂଖ୍ୟା
```

#### କେବେ ବ୍ୟବହାର କରିବେ

କ୍ରମିକ ପୁରାତନତା `aggressive` ଏବଂ `ultra` ମୋଡ୍ ପାଇଁ **ସର୍ବଦା ସକ୍ରିୟ**। ଏହା
ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରରେ ବିଶେଷ ଭାବେ ପ୍ରଭାବଶାଳୀ:

- ଦୀର୍ଘ ସମୟ ଧରି ଚାଲୁଥିବା କୋଡିଂ ସେସନ୍
- ଅନେକ ଦିନର ବାର୍ତ୍ତାଳାପ
- ଅନେକ ଟୁଲ୍ କଲ୍ ସହିତ ଏଜେଣ୍ଟିକ୍ କାର୍ଯ୍ୟପ୍ରବାହ

### କେଭ୍ମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍

`outputMode.ts` ମଡ୍ୟୁଲ୍ ମଡେଲ୍କୁ ସଙ୍କୋଚିତ, ସଂକ୍ଷିପ୍ତ ଆଉଟପୁଟ୍ (ଏକ "କେଭ୍ମ୍ୟାନ୍" ଶୈଳୀ)
ଉତ୍ପାଦନ କରାଇବା ପାଇଁ **ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ନିର୍ଦ୍ଦେଶାବଳୀ** ଅନ୍ତଃକ୍ଷେପ କରେ।

#### ଏହା କିପରି କାମ କରେ

ଇନପୁଟ୍କୁ ସଙ୍କୋଚନ କରିବା ପରିବର୍ତ୍ତେ, ଏହି ମୋଡ୍ ଏହିପରି ଏକ ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ଯୋଗ କରେ:

> "ସର୍ବନିମ୍ନ ଶବ୍ଦରେ ଉତ୍ତର ଦିଅନ୍ତୁ। ସୌଜନ୍ୟମୂଳକ କଥା ବାଦ୍ ଦିଅନ୍ତୁ। ଛୋଟ ବାକ୍ୟ ବ୍ୟବହାର କରନ୍ତୁ।"

ଏହା ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରରେ ବିଶେଷ ଭାବେ ଭଲ କାମ କରେ:

- କୋଡ୍ ଉତ୍ପାଦନ (ଅଧିକ ସଂକ୍ଷିପ୍ତ ଆଉଟପୁଟ୍ = କମ୍ ଟୋକନ୍)
- ଦ୍ରୁତ ପ୍ରଶ୍ନୋତ୍ତର (ବିସ୍ତୃତ ବ୍ୟାଖ୍ୟାର ଆବଶ୍ୟକତା ନାହିଁ)
- ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ (ଥ୍ରୁପୁଟ୍ ସର୍ବାଧିକ କରେ)

#### କେବେ ବ୍ୟବହାର କରିବେ

କେଭ୍ମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍ **ଇଚ୍ଛାଧୀନ** — କମ୍ବୋ ବିନ୍ୟାସ ମାଧ୍ୟମରେ ଏହାକୁ ସେଟ୍ କରନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

#### ଇଞ୍ଜେକ୍ସନ୍ କିପରି କାମ କରେ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ଚୟନକୁ
କ୍ୟାଟାଲଗ୍ ସହିତ ମେଳ କରି ନିର୍ଦ୍ଧାରଣ କରେ (ଅଜଣା id ଏବଂ ଲୋକେଲ୍ ସହିତ ନ ମେଳୁଥିବା ଶୈଳୀଗୁଡ଼ିକୁ
ବାଦ ଦିଆଯାଏ, କେବେ ମଧ୍ୟ ତ୍ରୁଟି ହୁଏନାହିଁ), ଚୟନିତ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ କ୍ୟାଟାଲଗ୍ କ୍ରମରେ ଯୋଡ଼େ,
ସୀମା ଧାରାକୁ **ଥରେ** ଯୋଡ଼େ ଏବଂ ବ୍ଲକ୍କୁ ଗୋଟିଏ idempotency
ଚିହ୍ନ (`[OmniRoute Output Styles]`) ସହିତ ଆରମ୍ଭ କରେ, ତେଣୁ ପୁନଃ ପ୍ରୟୋଗ କଲେ କୌଣସି ପରିବର୍ତ୍ତନ ହୁଏନାହିଁ। ଯେତେବେଳେ ନିର୍ଦ୍ଧାରିତ
ଭାଷାର (ନିମ୍ନରେ ଥିବା ଭାଷା ଚୟନ ଦେଖନ୍ତୁ) ଅନୁବାଦ ଥାଏ, ଇଂରାଜୀ ପରିବର୍ତ୍ତେ ସ୍ଥାନୀୟକୃତ ନିର୍ଦ୍ଦେଶ
ଇଞ୍ଜେକ୍ଟ କରାଯାଏ।

`messages` ଥିବା bodyରେ, ଏକ ବିଷୟବସ୍ତୁ ବାଇପାସ୍ (`shouldBypassCavemanOutputMode()`
`open-sse/services/compression/outputMode.ts`ରେ) ଶେଷ ତିନୋଟି ମେସେଜ୍ ଯାଞ୍ଚ କରେ ଏବଂ ସେଗୁଡ଼ିକ
ଏହାର ସୁରକ୍ଷା, ଅପରିବର୍ତ୍ତନୀୟ-କାର୍ଯ୍ୟ, ସ୍ପଷ୍ଟୀକରଣ କିମ୍ବା କ୍ରମ-ସମ୍ବେଦନଶୀଳ କୀୱାର୍ଡ ସହିତ ମେଳ ଖାଇଲେ
ସମଗ୍ର ଟର୍ନ୍ ପାଇଁ ଶୈଳୀଗୁଡ଼ିକୁ ଏଡ଼ାଇ ଦିଏ। ବାଇପାସ୍ ଡ୍ୟାଶବୋର୍ଡର
**Auto-Clarity Bypass** ଟଗଲ୍ (`cavemanOutputMode.autoClarity`) ଯେଉଁ ସେଟିଂରେ ରହିଛି, ସେହି ଅନୁସାରେ ଚାଲେ।

ବାଇପାସ୍ ଟର୍ନ୍କୁ ଅନୁମତି ଦେଲେ, `placeSystemInstruction()` (ସେହି ଫାଇଲ୍ରେ), ଯାହା
କେବେ ମଧ୍ୟ ନୂଆ `messages[0]` ସୃଷ୍ଟି କରେନାହିଁ, ବ୍ଲକ୍କୁ ନିମ୍ନଲିଖିତ ମଧ୍ୟରୁ ପ୍ରଥମେ ମିଳିଥିବା ସ୍ଥାନରେ ରଖେ:

1. ଷ୍ଟ୍ରିଙ୍ଗ୍ ବିଷୟବସ୍ତୁ ଥିବା ଏକ ପ୍ରାରମ୍ଭିକ system ମେସେଜ୍: ଏହାର ପାଠ୍ୟ ପରେ ବ୍ଲକ୍କୁ ଯୋଡ଼ାଯାଏ।
2. ଶୀର୍ଷ-ସ୍ତରୀୟ `system` ଫିଲ୍ଡ: ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ର ପାଠ୍ୟ ପରେ ବ୍ଲକ୍କୁ ଯୋଡ଼ାଯାଏ, କିମ୍ବା
   content-block ଆରେରେ ଏକ ନୂଆ ଟେକ୍ସଟ୍ ବ୍ଲକ୍ ଭାବରେ ଯୋଡ଼ାଯାଏ।
3. ଷ୍ଟ୍ରିଙ୍ଗ୍ ବିଷୟବସ୍ତୁ ଥିବା ପରବର୍ତ୍ତୀ ପ୍ରଥମ system ମେସେଜ୍: ଏହାର
   ପାଠ୍ୟ ପରେ ବ୍ଲକ୍କୁ ଯୋଡ଼ାଯାଏ।
4. ଉପରୋକ୍ତ ମଧ୍ୟରୁ କୌଣସିଟି ନଥିଲେ: ବ୍ଲକ୍କୁ `messages`ର ଶେଷରେ ଏକ ନୂଆ system ମେସେଜ୍ରେ ରଖାଯାଏ।

`messages` ନଥିବା bodyରେ, ବ୍ଲକ୍କୁ ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ `instructions` ଫିଲ୍ଡରେ ଯୋଡ଼ାଯାଏ,
କିମ୍ବା bodyରେ `input` (ଏକ ଷ୍ଟ୍ରିଙ୍ଗ୍ କିମ୍ବା ଆରେ) ଥିଲେ ଏହା `instructions` ହୋଇଯାଏ। ଉଭୟ
`instructions` ଏବଂ `input` ନଥିବା bodyକୁ `no_messages` ଭାବରେ ଏଡ଼ାଇ ଦିଆଯାଏ।

#### କିପରି ସକ୍ଷମ କରିବେ

ଡ୍ୟାଶବୋର୍ଡରେ: **ପ୍ରସଙ୍ଗ → ସେଟିଂସ୍ → ସଙ୍କୋଚନ** — ପ୍ରତ୍ୟେକ ଶୈଳୀ ପାଇଁ ଗୋଟିଏ ଧାଡ଼ି,
ଏକ on/off ଟଗଲ୍ ଏବଂ ଏକ ସ୍ତର ଚୟନକାରୀ ସହିତ। ପ୍ରୋଗ୍ରାମ୍ମାଧ୍ୟମରେ, compression config ଚୟନକୁ
ଏହିପରି ସଂରକ୍ଷଣ କରେ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ପଛୁଆ-ସୁସଙ୍ଗତତା: ପୁରୁଣା `outputMode: "caveman"` କମ୍ବୋ ସେଟିଂ ଏବେ ମଧ୍ୟ କାମ କରେ ଏବଂ
`terse-prose` ସହିତ ମ୍ୟାପ୍ ହୁଏ, ଯାହା ପ୍ରତ୍ୟେକ ପୁରୁଣା ଭାଷାରେ ପୁରୁଣା ଇଞ୍ଜେକ୍ସନ୍ ସହିତ byte-identical।

ଭାଷା ଚୟନ: `languageConfig.enabled` ଚାଲୁ ଥିଲେ, `autoDetect` ସବୁଠାରୁ ନୂତନ user ମେସେଜ୍ର
ଭାଷା ବାଛେ (input engines ସହିତ ସମାନ detector);
`autoDetect` ବନ୍ଦ କଲେ `defaultLanguage` ସ୍ଥିର ହୁଏ। ବନ୍ଦ → ଇଂରାଜୀ।

ଶୈଳୀ × ଭାଷା ମ୍ୟାଟ୍ରିକ୍ସକୁ
`tests/unit/compression/output-styles-i18n-matrix.test.ts` ଦ୍ୱାରା ସ୍ଥିର କରାଯାଇଛି: ଏକ ନୂଆ ଶୈଳୀ ଅତିକମ୍ରେ ଏକ pt-BR ଅନୁବାଦ
(କିମ୍ବା ସ୍ପଷ୍ଟ ଭାବରେ ଟ୍ରାକ୍ କରାଯାଇଥିବା ବ୍ୟତିକ୍ରମ) ବିନା ପ୍ରକାଶିତ ହୋଇପାରିବ ନାହିଁ, ଏବଂ ଏକ
ବର୍ତ୍ତମାନର ଶୈଳୀ ନିରବରେ କୌଣସି ଲୋକେଲ୍ ହରାଇପାରିବ ନାହିଁ। ଏକ ଶୈଳୀ ଯୋଡ଼ିବା ପାଇଁ,
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style) ଦେଖନ୍ତୁ।

### ଟୁଲ୍ ଫଳାଫଳ ସଙ୍କୋଚନ

`toolResultCompressor.ts` ମଡ୍ୟୁଲ୍ ଟୁଲ୍ ଫଳାଫଳଗୁଡ଼ିକ (ଫଙ୍କସନ୍ କଲ୍, ଏଜେଣ୍ଟ ଆଉଟପୁଟ୍, ସନ୍ଧାନ ଫଳାଫଳ ଇତ୍ୟାଦି) ପାଇଁ **5ଟି ବିଶେଷୀକୃତ ସଙ୍କୋଚନ କୌଶଳ**
ପ୍ରଦାନ କରେ:

1. **ସନ୍ଧାନ ଫଳାଫଳ ସଙ୍କୋଚନ** — ଅନାବଶ୍ୟକ ପୁନରାବୃତ୍ତ ଫଳାଫଳଗୁଡ଼ିକୁ ହଟାଏ, ଶୀର୍ଷ-Nକୁ ରଖେ
2. **ଫାଇଲ୍ ପଠନ ସଙ୍କୋଚନ** — ବଡ଼ ଫାଇଲ୍ଗୁଡ଼ିକୁ କାଟି ଛୋଟ କରେ, ହେଡର୍/importଗୁଡ଼ିକୁ ସଂରକ୍ଷଣ କରେ
3. **କୋଡ୍ ନିଷ୍ପାଦନ ସଙ୍କୋଚନ** — କେବଳ ଆବଶ୍ୟକ stdout/stderrକୁ ରଖେ
4. **ଡାଟାବେସ୍ କ୍ୱେରି ସଙ୍କୋଚନ** — ଧାଡ଼ି ସଂଖ୍ୟା ସୀମିତ କରେ, ଅତ୍ୟଧିକ ବିବରଣାତ୍ମକ metadataକୁ ହଟାଏ
5. **API ପ୍ରତିକ୍ରିୟା ସଙ୍କୋଚନ** — null ଫିଲ୍ଡଗୁଡ଼ିକୁ ବାଦ ଦିଏ, ଆରେଗୁଡ଼ିକୁ ସଂକ୍ଷିପ୍ତ କରେ

#### କେବେ ବ୍ୟବହାର କରିବେ

ଟୁଲ୍ କଲ୍ ଉପସ୍ଥିତ ଥିଲେ ଟୁଲ୍ ଫଳାଫଳ ସଂକୋଚନ **ସର୍ବଦା ସକ୍ରିୟ** ରହେ। କୌଣସି
ବିନ୍ୟାସ ଆବଶ୍ୟକ ନାହିଁ।

### ସ୍ତରୀକୃତ ପାଇପ୍ଲାଇନ୍

ସ୍ତରୀକୃତ ମୋଡ୍ **ଏକାଧିକ ଇଞ୍ଜିନ୍କୁ କ୍ରମାନ୍ୱୟରେ** ଚଲାଏ — ସାଧାରଣତଃ ପ୍ରଥମେ RTK
(ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ରେ 60-90% ସଞ୍ଚୟ), ତା’ପରେ Caveman (ଅବଶିଷ୍ଟ
ଟେକ୍ସଟ୍ରେ ଅତିରିକ୍ତ 30% ସଞ୍ଚୟ)। ଏହାଦ୍ୱାରା **ମୋଟ 78-95% ସଞ୍ଚୟ** ହାସଲ ହୁଏ।

#### ଏହା କିପରି କାମ କରେ

```
ଇନ୍ପୁଟ୍ (1000 ଟୋକନ୍)
  → RTK (କମାଣ୍ଡ-ସଚେତନ ଫିଲ୍ଟର୍) → 200 ଟୋକନ୍
    → Caveman (ଅନାବଶ୍ୟକ ବିଷୟବସ୍ତୁ ଅପସାରଣ) → 140 ଟୋକନ୍
  → ଆଉଟ୍ପୁଟ୍ (140 ଟୋକନ୍, 86% ସଞ୍ଚୟ)
```

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ

ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରରେ ସ୍ତରୀକୃତ ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ:

- ଟୁଲ୍-ବହୁଳ କାର୍ଯ୍ୟପ୍ରବାହ (ଏଜେଣ୍ଟିକ୍ କୋଡିଂ, ଗବେଷଣା)
- ଖର୍ଚ୍ଚ-ସମ୍ବେଦନଶୀଳ ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ
- ଯେତେବେଳେ ଆପଣଙ୍କୁ ସର୍ବାଧିକ ଟୋକନ୍ ସଞ୍ଚୟ ଆବଶ୍ୟକ

କମ୍ବୋ ମାଧ୍ୟମରେ ବିନ୍ୟାସ କରନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## କମ୍ପ୍ରେସନ୍ କମ୍ବୋ ଓଭରରାଇଡ୍ଗୁଡ଼ିକ

ବିଭିନ୍ନ ବ୍ୟବହାର ପରିସ୍ଥିତି ପାଇଁ ଆଚରଣକୁ ସୂକ୍ଷ୍ମ ଭାବରେ ସମନ୍ୱୟ କରିବାକୁ ଆପଣ ଗ୍ଲୋବାଲ୍ କମ୍ପ୍ରେସନ୍ ମୋଡ୍କୁ **ପ୍ରତ୍ୟେକ କମ୍ବୋ ପାଇଁ** ଓଭରରାଇଡ୍ କରିପାରିବେ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

ଏହା ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରଗୁଡ଼ିକ ପାଇଁ ଉପଯୋଗୀ:

- **କୋଡିଂ କମ୍ବୋଗୁଡ଼ିକ**: ଦୀର୍ଘ ସେସନ୍ ପାଇଁ `aggressive` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ଦ୍ରୁତ ପ୍ରଶ୍ନୋତ୍ତର କମ୍ବୋଗୁଡ଼ିକ**: ଦ୍ରୁତ ପ୍ରତିକ୍ରିୟା ପାଇଁ `lite` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ଅଧିକ ଟୁଲ୍ଯୁକ୍ତ କମ୍ବୋଗୁଡ଼ିକ**: ସର୍ବାଧିକ ସଞ୍ଚୟ ପାଇଁ `stacked` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ପ୍ରଡକ୍ସନ୍ କମ୍ବୋଗୁଡ଼ିକ**: କ୍ୟାସିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ `cache-aware` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
