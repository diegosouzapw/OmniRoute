> ଯୋଗ୍ୟ କଣ୍ଟେକ୍ସ୍ଟରେ ସ୍ୱୟଂଚାଳିତ ଭାବେ 15-95% ସଞ୍ଚୟ କରନ୍ତୁ। ଏକ ଦ୍ରୁତ ସାରାଂଶ ପାଇଁ [README କମ୍ପ୍ରେସନ୍ ବିଭାଗ](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically) ଦେଖନ୍ତୁ।

## ସାରାଂଶ

OmniRoute ଏକ ମଡ୍ୟୁଲାର୍ ପ୍ରମ୍ପ୍ଟ କମ୍ପ୍ରେସନ୍ ପାଇପ୍ଲାଇନ୍ କାର୍ଯ୍ୟକାରୀ କରେ, ଯାହା ଅନୁରୋଧଗୁଡ଼ିକ ଅପ୍ଷ୍ଟ୍ରିମ୍ ପ୍ରଦାନକାରୀଙ୍କ ପାଖରେ ପହଞ୍ଚିବା ପୂର୍ବରୁ **ସକ୍ରିୟ ଭାବେ** ଚାଲେ। ଏହାର ଅର୍ଥ ଆପଣଙ୍କ ଟୋକନ୍ ସଞ୍ଚୟ ସ୍ୱଚ୍ଛ ଭାବେ ହୁଏ — ଆପଣଙ୍କ କାର୍ଯ୍ୟପ୍ରବାହରେ କୌଣସି ପରିବର୍ତ୍ତନ ଆବଶ୍ୟକ ନାହିଁ।

```
କ୍ଲାଏଣ୍ଟ ଅନୁରୋଧ
  → କମ୍ପ୍ରେସନ୍ କୌଶଳ ଚୟନକର୍ତ୍ତା
    → Combo ଓଭର୍ରାଇଡ୍? → Combo ସେଟିଂ ବ୍ୟବହାର କରନ୍ତୁ
    → ସ୍ୱୟଂଚାଳିତ-ଟ୍ରିଗର୍ ଥ୍ରେସ୍ହୋଲ୍ଡ? → ସ୍ୱୟଂଚାଳିତ ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
    → ଡିଫଲ୍ଟ ମୋଡ୍? → ଗ୍ଲୋବାଲ୍ ସେଟିଂ ବ୍ୟବହାର କରନ୍ତୁ
    → ବନ୍ଦ? → କମ୍ପ୍ରେସନ୍ ଛାଡ଼ିଦିଅନ୍ତୁ
  → ଚୟନିତ କମ୍ପ୍ରେସନ୍ ମୋଡ୍
    → ବନ୍ଦ: କୌଣସି କମ୍ପ୍ରେସନ୍ ନାହିଁ
    → ଲାଇଟ୍: ସୁରକ୍ଷିତ ହ୍ୱାଇଟ୍ସ୍ପେସ୍/ଫର୍ମାଟିଂ ସଫେଇ (~15%)
    → ଷ୍ଟାଣ୍ଡାର୍ଡ: Caveman-ଶୈଳୀର ଅନାବଶ୍ୟକ ଶବ୍ଦ ଅପସାରଣ (~30%)
    → ଆଗ୍ରେସିଭ୍: ଇତିହାସ ଏଜିଂ + ସାରାଂଶକରଣ (~50%)
    → ଅଲ୍ଟ୍ରା: ହ୍ୟୁରିଷ୍ଟିକ୍ ପ୍ରୁନିଂ + କୋଡ୍-ବ୍ଲକ୍ ଥିନିଂ (~75%)
    → RTK: କମାଣ୍ଡ-ସଚେତନ ଟର୍ମିନାଲ୍/ଟୁଲ୍-ଆଉଟ୍ପୁଟ୍ ଫିଲ୍ଟରିଂ (60-90% ଅପ୍ଷ୍ଟ୍ରିମ୍ ପରିସର)
    → ଷ୍ଟାକ୍ଡ୍: କ୍ରମବଦ୍ଧ ମଲ୍ଟି-ଇଞ୍ଜିନ୍ ପାଇପ୍ଲାଇନ୍, ସାଧାରଣତଃ ପ୍ରଥମେ RTK ଓ ପରେ Caveman (78-95% ଯୋଗ୍ୟ ପରିସର)
  → କମ୍ପ୍ରେସ୍ ହୋଇଥିବା ଅନୁରୋଧ → ପ୍ରଦାନକାରୀ
```

## କମ୍ପ୍ରେସନ୍ ମୋଡ୍ଗୁଡ଼ିକ

### ବନ୍ଦ

କୌଣସି କମ୍ପ୍ରେସନ୍ ପ୍ରୟୋଗ କରାଯାଏ ନାହିଁ। ସମସ୍ତ ସନ୍ଦେଶ ଅପରିବର୍ତ୍ତିତ ଭାବେ ପଠାଯାଏ।

### ଲାଇଟ୍ ମୋଡ୍ (~15% ସଞ୍ଚୟ, <1ms ବିଳମ୍ବ)

ସବୁଠାରୁ ସୁରକ୍ଷିତ ମୋଡ୍ — ଶୂନ୍ୟ ଅର୍ଥଗତ ପରିବର୍ତ୍ତନ, କେବଳ ଫର୍ମାଟିଂ ସଫେଇ:

| ପ୍ରକ୍ରିୟା                | ବର୍ଣ୍ଣନା                                        |
| ------------------------ | ----------------------------------------------- |
| `collapseWhitespace`     | କ୍ରମାଗତ ଖାଲି ଧାଡ଼ି ଏବଂ ଶେଷର ସ୍ପେସ୍ଗୁଡ଼ିକୁ ମିଶାଏ |
| `dedupSystemPrompt`      | ନକଲ ସିଷ୍ଟମ୍ ସନ୍ଦେଶଗୁଡ଼ିକୁ ଅପସାରଣ କରେ            |
| `compressToolResults`    | ବିସ୍ତୃତ ଟୁଲ୍/ଫଙ୍କସନ୍ ଆଉଟ୍ପୁଟ୍କୁ କମ୍ପ୍ରେସ୍ କରେ   |
| `removeRedundantContent` | ପୁନରାବୃତ୍ତ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ ଅପସାରଣ କରେ          |
| `replaceImageUrls`       | base64 ଇମେଜ୍ ଡାଟା URIଗୁଡ଼ିକୁ ସଂକ୍ଷିପ୍ତ କରେ      |

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ସର୍ବଦା-ସକ୍ରିୟ ବ୍ୟବହାର, ସୁରକ୍ଷା-ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ କାର୍ଯ୍ୟପ୍ରବାହ।

### ଷ୍ଟାଣ୍ଡାର୍ଡ ମୋଡ୍ (~30% ସଞ୍ଚୟ)

[Caveman](https://github.com/JuliusBrussee/caveman) ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ — ଅର୍ଥକୁ ସଂରକ୍ଷିତ ରଖି ଅନାବଶ୍ୟକ ଶବ୍ଦ ଏବଂ ଅତ୍ୟଧିକ ବିସ୍ତୃତ ବାକ୍ୟାଂଶଗୁଡ଼ିକୁ ଅପସାରଣ କରେ:

- ଅନାବଶ୍ୟକ ଶବ୍ଦ ("ଦୟାକରି", "ମୋ ମତରେ", "ମୂଳତଃ", "ବାସ୍ତବରେ") ଅପସାରଣ କରେ
- ଅତ୍ୟଧିକ ବିସ୍ତୃତ ବାକ୍ୟାଂଶଗୁଡ଼ିକୁ ସଂକ୍ଷିପ୍ତ କରେ ("କରିବା ଉଦ୍ଦେଶ୍ୟରେ" → "କରିବାକୁ", "ଏହାର ପରିଣାମସ୍ୱରୂପ" → "କାରଣ")
- ବିନମ୍ର ଦ୍ୱିଧାସୂଚକ ବାକ୍ୟାଂଶକୁ ଅପସାରଣ କରେ ("ଆପଣ କ’ଣ ଦୟାକରି...", "ଯଦି ଆପଣ ସମ୍ଭବତଃ କରିପାରିବେ...")
- କୋଡିଂ ପ୍ରମ୍ପ୍ଟ ପାଇଁ ସଜାଯାଇଥିବା 30+ regex ନିୟମ

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ଦୈନିକ କୋଡିଂ କାର୍ଯ୍ୟପ୍ରବାହ, ଖର୍ଚ୍ଚ-ସଚେତନ ଟିମ୍।

### ଆଗ୍ରେସିଭ୍ ମୋଡ୍ (~50% ସଞ୍ଚୟ)

ଦୀର୍ଘ ସେସନ୍ ପାଇଁ ସ୍ମାର୍ଟ ଇତିହାସ ପରିଚାଳନା:

- **ସନ୍ଦେଶ ଏଜିଂ** — ପୁରୁଣା ସନ୍ଦେଶଗୁଡ଼ିକ କ୍ରମଶଃ ଅଧିକ କମ୍ପ୍ରେସ୍ ହୁଏ
- **ଟୁଲ୍ ଫଳାଫଳ କମ୍ପ୍ରେସନ୍** — ଦୀର୍ଘ ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ଗୁଡ଼ିକୁ କାଟି ଦିଆଯାଏ କିମ୍ବା ବାଦ୍ ଦିଆଯାଏ (ପ୍ରଥମ/ଶେଷ ଧାଡ଼ି,
  ମେଳ ଖାଉଥିବା ଧାଡ଼ିର ଫିଲ୍ଟରିଂ, JSON କୀ ସଂକ୍ଷିପ୍ତକରଣ)
- **ଗଠନାତ୍ମକ ଅଖଣ୍ଡତା ସୁରକ୍ଷା** — `tool_use` + `tool_result` ଯୁଗଳଗୁଡ଼ିକ ସୁସଙ୍ଗତ ରହିବା ସୁନିଶ୍ଚିତ କରେ
- **କଣ୍ଟେକ୍ସ୍ଟ ୱିଣ୍ଡୋ ସଚେତନତା** — ପ୍ରତ୍ୟେକ ମଡେଲ୍ର ଟୋକନ୍ ସୀମାକୁ ସମ୍ମାନ କରେ

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ଦୀର୍ଘ ଡିବଗିଂ ସେସନ୍, ବଡ଼ କୋଡ୍ବେସ୍।

### ଅଲ୍ଟ୍ରା ମୋଡ୍ (~75% ସଞ୍ଚୟ)

ଟୋକନ୍-ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ପରିସ୍ଥିତି ପାଇଁ ସର୍ବାଧିକ କମ୍ପ୍ରେସନ୍:

- **ହ୍ୟୁରିଷ୍ଟିକ୍ ପ୍ରୁନିଂ** — ଗଦ୍ୟର ସ୍କୋର୍-ଆଧାରିତ ଟୋକନ୍ ପ୍ରୁନିଂ
- **ଗଠନ ସଂରକ୍ଷଣ** — ଫେନ୍ସ୍ଡ୍ କୋଡ୍ ବ୍ଲକ୍, ଇନ୍ଲାଇନ୍ କୋଡ୍, URL ଏବଂ ଆଇଡେଣ୍ଟିଫାୟର୍ଗୁଡ଼ିକୁ
  ଟୁମ୍ଷ୍ଟୋନ୍ କରି ଅବିକଳ ଭାବେ ପୁନଃ ସଂଯୋଜନ କରାଯାଏ, କେବେବି ପ୍ରୁନ୍ କରାଯାଏ ନାହିଁ
- **ଇଚ୍ଛାଧୀନ SLM ସ୍ତର** — କନ୍ଫିଗର୍ କରାଯାଇଥିଲେ ଏକ ଛୋଟ ଲୋକାଲ୍ ମଡେଲ୍ ପ୍ରୁନିଂକୁ ଅଧିକ ସୁଦୃଢ଼ କରିପାରେ
- ଆଗ୍ରେସିଭ୍ ମୋଡ୍ରୁ ସ୍ୱାଧୀନ: ଏହା ସନ୍ଦେଶ ଏଜିଂ, ଟୁଲ୍-ଫଳାଫଳ କମ୍ପ୍ରେସନ୍
  କିମ୍ବା ଫଲ୍ବ୍ୟାକ୍ ସାରାଂଶକର୍ତ୍ତାକୁ ଚଲାଏ ନାହିଁ (କେବଳ SLM-ସ୍ତରର ବିଫଳତା ଏକ ଫଲ୍ବ୍ୟାକ୍ ପାସ୍କୁ
  ଆଗ୍ରେସିଭ୍ ମାଧ୍ୟମରେ ରୁଟ୍ କରିପାରେ)

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ଯେତେବେଳେ ଆପଣ ବାରମ୍ବାର କଣ୍ଟେକ୍ସ୍ଟ ସୀମାରେ ପହଞ୍ଚୁଛନ୍ତି।

### RTK ମୋଡ୍ (60-90% ଅପ୍ଷ୍ଟ୍ରିମ୍ ପରିସର)

RTK ମୋଡ୍ କୋଡିଂ-ଏଜେଣ୍ଟ ସେସନ୍ରେ ଦେଖାଯାଉଥିବା ବିସ୍ତୃତ ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ ପାଇଁ ଅପ୍ଟିମାଇଜ୍ କରାଯାଇଛି:

- `git status`, `git diff`, `git log`, ଟେଷ୍ଟ ରନର୍,
  TypeScript/Vite/Webpack ବିଲ୍ଡ୍, ESLint/Biome/Prettier, npm ଅଡିଟ୍/ଇନ୍ଷ୍ଟଲ୍, Docker ଲଗ୍, ଇନ୍ଫ୍ରା
  ଆଉଟ୍ପୁଟ୍ ଏବଂ ସାଧାରଣ shell ଆଉଟ୍ପୁଟ୍ ପରି କମାଣ୍ଡ/ଆଉଟ୍ପୁଟ୍ ଶ୍ରେଣୀଗୁଡ଼ିକୁ ଚିହ୍ନଟ କରେ
- `open-sse/services/compression/engines/rtk/filters/` ରୁ JSON ଫିଲ୍ଟର୍ ପ୍ୟାକ୍ ପ୍ରୟୋଗ କରେ
- ପ୍ରୋଜେକ୍ଟ କିମ୍ବା ଗ୍ଲୋବାଲ୍ `filters.toml` ଫାଇଲ୍ଗୁଡ଼ିକରୁ RTK TOML ସ୍କିମା v1 ଫିଲ୍ଟର୍ ଇମ୍ପୋର୍ଟ କରେ, ଇନ୍ଲାଇନ୍-ଟେଷ୍ଟ
  ଭ୍ୟାଲିଡେସନ୍ ଏବଂ ପ୍ରୋଜେକ୍ଟ ଫାଇଲ୍ ପାଇଁ ଟ୍ରଷ୍ଟ-ଗେଟିଂ ସହିତ
- ଇନ୍ଲାଇନ୍ ଯାଞ୍ଚ ନମୁନା ସହିତ 55ଟି ବିଲ୍ଟ-ଇନ୍ ଫିଲ୍ଟର୍ ପ୍ରଦାନ କରେ
- ANSI କଣ୍ଟ୍ରୋଲ୍ ସିକ୍ୱେନ୍ସ, ପ୍ରଗତି ବାର୍, ପୁନରାବୃତ୍ତ ଧାଡ଼ି ଏବଂ କାର୍ଯ୍ୟାନୁଷ୍ଠାନ-ଅଯୋଗ୍ୟ ଅନାବଶ୍ୟକ ତଥ୍ୟକୁ ଅପସାରଣ କରେ
- ବିଫଳତା, ତ୍ରୁଟି, ଚେତାବନୀ, ପରିବର୍ତ୍ତିତ ଫାଇଲ୍, ସାରାଂଶ ଏବଂ ଦୀର୍ଘ ଆଉଟ୍ପୁଟ୍ର ଶେଷ ଭାଗକୁ ସଂରକ୍ଷଣ କରେ
- ଟ୍ରଷ୍ଟ-ଗେଟେଡ୍ ପ୍ରୋଜେକ୍ଟ ଫିଲ୍ଟର୍, ଗ୍ଲୋବାଲ୍ ଫିଲ୍ଟର୍ ଏବଂ ଇଚ୍ଛାଧୀନ ରିଡାକ୍ଟ ହୋଇଥିବା ର' ଆଉଟ୍ପୁଟ୍ ପୁନରୁଦ୍ଧାରକୁ ସମର୍ଥନ କରେ

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** shell, ବିଲ୍ଡ୍, ଟେଷ୍ଟ, git, grep ଏବଂ ଫାଇଲ୍-ଆଉଟ୍ପୁଟ୍ ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ ସହିତ ଏଜେଣ୍ଟ ସେସନ୍।

### ଷ୍ଟାକ୍ଡ୍ ମୋଡ୍ (78-95% ଯୋଗ୍ୟ ପରିସର)

ଷ୍ଟାକ୍ଡ୍ ମୋଡ୍ ଏକ ନିର୍ଦ୍ଧାରିତ କ୍ରମରେ ଏକାଧିକ କମ୍ପ୍ରେସନ୍ ଇଞ୍ଜିନ୍ ଚଲାଏ। ଡିଫଲ୍ଟ ପାଇପ୍ଲାଇନ୍ ହେଉଛି:

```txt
RTK -> Caveman
```

ଏହି କ୍ରମ ପ୍ରଥମେ ଟର୍ମିନାଲ୍/ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍କୁ ସଂକ୍ଷିପ୍ତ ରଖେ, ତା’ପରେ ଅବଶିଷ୍ଟ ପ୍ରାକୃତିକ-ଭାଷା ପ୍ରମ୍ପ୍ଟରେ
Caveman ଅର୍ଥଗତ ସଂକ୍ଷିପ୍ତକରଣ ପ୍ରୟୋଗ କରେ। ଷ୍ଟାକ୍ଡ୍ ପାଇପ୍ଲାଇନ୍ଗୁଡ଼ିକୁ ଗ୍ଲୋବାଲ୍ ଭାବେ କିମ୍ବା ରାଉଟିଂ
କମ୍ବୋଗୁଡ଼ିକୁ ଆବଣ୍ଟିତ କମ୍ପ୍ରେସନ୍ କମ୍ବୋ ମାଧ୍ୟମରେ କନ୍ଫିଗର୍ କରାଯାଇପାରେ।

**ଏହା ପାଇଁ ସର୍ବୋତ୍ତମ:** ବଡ଼ ଟୁଲ୍ ଲଗ୍ ସହିତ ମାନବୀୟ ନିର୍ଦ୍ଦେଶ କିମ୍ବା ଆସିଷ୍ଟାଣ୍ଟ ସାରାଂଶ ଥିବା ମିଶ୍ରିତ କଣ୍ଟେକ୍ସ୍ଟ।

## ଅପ୍ଷ୍ଟ୍ରିମ୍ ସଞ୍ଚୟ ଗଣନା

OmniRoute ଦୁଇଟି ଉତ୍ସରୁ ମିଳୁଥିବା କମ୍ପ୍ରେସନ୍ ସଞ୍ଚୟକୁ ଡକ୍ୟୁମେଣ୍ଟ କରେ: ଅପ୍ଷ୍ଟ୍ରିମ୍ ପ୍ରୋଜେକ୍ଟ ବେଞ୍ଚମାର୍କ ଏବଂ
OmniRoute-ର ନିଜସ୍ୱ ଇଞ୍ଜିନ୍ ସଂଯୋଜନ।

| ଉତ୍ସ    | ଏଠାରେ ବ୍ୟବହୃତ ଅପ୍ଷ୍ଟ୍ରିମ୍ README ସଂଖ୍ୟା                                                                              |
| ------- | -------------------------------------------------------------------------------------------------------------------- |
| Caveman | `~75%` କମ୍ ଆଉଟପୁଟ୍ ଟୋକନ୍, `65%` ବେଞ୍ଚମାର୍କ ହାରାହାରି ଆଉଟପୁଟ୍ ସଞ୍ଚୟ, `22-87%` ପରିସର, ଏବଂ `~46%` ଇନପୁଟ୍ କମ୍ପ୍ରେସନ୍ ଟୁଲ୍ |
| RTK     | କମାଣ୍ଡ-ଆଉଟପୁଟ୍ରେ `60-90%` ସଞ୍ଚୟ; ନମୁନା ସେସନ୍ରେ `~118,000 -> ~23,900` ଟୋକନ୍, କିମ୍ବା `79.7%` ସଞ୍ଚୟ (`~80%`)            |

ପରସ୍ପରକୁ ଆବୃତ କରୁଥିବା ଟୁଲ୍/କଣ୍ଟେକ୍ସ୍ଟ ପେଲୋଡ୍ଗୁଡ଼ିକ ପାଇଁ, ଡିଫଲ୍ଟ OmniRoute କମ୍ବୋ ଇଞ୍ଜିନ୍ଗୁଡ଼ିକୁ କ୍ରମବଦ୍ଧ ଭାବେ ଯୋଡ଼େ:

```txt
RTK -> Caveman
```

ମିଳିତ ସଞ୍ଚୟ ଗୁଣାତ୍ମକ, ଯୋଗାତ୍ମକ ନୁହେଁ:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ଯେତେବେଳେ RTK ଏବଂ Caveman ଉଭୟ ସମାନ ଇନପୁଟ୍/କଣ୍ଟେକ୍ସ୍ଟ ପେଲୋଡ୍କୁ ହ୍ରାସ କରିପାରନ୍ତି, ସେତେବେଳେ ସେହି `78-95%` ସଂଖ୍ୟା ପ୍ରଯୁଜ୍ୟ।
Caveman ରେସ୍ପନ୍ସ ଆଉଟପୁଟ୍ ମୋଡ୍ ପୃଥକ: ସକ୍ଷମ କରାଯାଇଥିଲେ, Caveman-ର ନିଜସ୍ୱ ଆଉଟପୁଟ୍ ସଞ୍ଚୟ (`65%`
ହାରାହାରି, `~75%` ମୁଖ୍ୟ ଆକଳନ, `22-87%` ପରିସର) ବ୍ୟବହାର କରନ୍ତୁ। ମୋଟ ବିଲିଂ ସଞ୍ଚୟ ଆପଣଙ୍କ ପ୍ରମ୍ପ୍ଟ/ଆଉଟପୁଟ୍ ମିଶ୍ରଣ ଉପରେ ନିର୍ଭର କରେ।

### "ଯୋଗ୍ୟ"ର ପ୍ରକୃତ ଅର୍ଥ କ’ଣ

15-95% ମୁଖ୍ୟ ପରିସରଟି ବାସ୍ତବ, କିନ୍ତୁ ଏହା କେବଳ **ଅନାବଶ୍ୟକ କିମ୍ବା ଅତ୍ୟଧିକ ବିସ୍ତୃତ** ବିଷୟବସ୍ତୁ ପାଇଁ ପ୍ରଯୁଜ୍ୟ — ପୁନରାବୃତ୍ତ
ତ୍ରୁଟି ଲାଇନ୍, ସମାନ ଚେତାବନୀକୁ ବାରମ୍ବାର ଦେଖାଉଥିବା ଏକ ବିଲ୍ଡ ଲଗ୍, ଏକ ଅତ୍ୟଧିକ ବଡ଼ `grep`/ଫାଇଲ୍-ରିଡ୍ ଡମ୍ପ୍। ଏହାର ଅର୍ଥ
**ଏହା ନୁହେଁ** ଯେ ପ୍ରତ୍ୟେକ ଅନୁରୋଧରେ ଏତେ ସଞ୍ଚୟ ହୁଏ।

ପ୍ରୟୋଗମୂଳକ ଭାବେ ଯାଞ୍ଚ କରାଯାଇଛି (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): 300ଟି ସମାନ
ତ୍ରୁଟି ଲାଇନ୍ ଥିବା ଏକ Anthropic-ଆକୃତିର `tool_result` ବ୍ଲକ୍ରେ ଚାଲିଥିବା ଏକ `stacked` (RTK + Caveman)
ରନ୍ରେ **95.93% ଟୋକନ୍ ସଞ୍ଚୟ / 96.26% ଅକ୍ଷର ସଞ୍ଚୟ** ହୋଇଥିଲା — ଯାହା ବିଜ୍ଞାପିତ
ପରିସର ମଧ୍ୟରେ ସଠିକ୍ ଭାବେ ରହିଛି। କିନ୍ତୁ ସାଧାରଣ, ଅନାବଶ୍ୟକ ପୁନରାବୃତ୍ତି ନଥିବା ଟୁଲ୍ ଆଉଟପୁଟ୍ରେ (ଏକ ସ୍ୱଚ୍ଛ `grep` ମ୍ୟାଚ୍ ତାଲିକା,
ଏକ ଛୋଟ ଫାଇଲ୍ ରିଡ୍, ସାଧାରଣ କଥୋପକଥନମୂଳକ ପାଠ୍ୟ) ସମାନ ପାଇପ୍ଲାଇନ୍ ଚଲାଇଲେ ଯଥାର୍ଥ ଭାବେ **ପ୍ରାୟ-ଶୂନ୍ୟ ସଞ୍ଚୟ** ହୁଏ, କାରଣ
ଅପସାରଣ କରିବା ପାଇଁ କୌଣସି ପୁନରାବୃତ୍ତି ନାହିଁ ଏବଂ `validateCompression()` (`validation.ts`) କୋଡ୍ ବ୍ଲକ୍, URL, ଶୀର୍ଷକ, ସଂସ୍କରଣ କିମ୍ବା ALL-CAPS ସ୍ଥିରାଙ୍କ ପରିଚୟକଗୁଡ଼ିକୁ ଛାଡ଼ିଦେବା କିମ୍ବା ପରିବର୍ତ୍ତନ କରିଦେବା ଭଳି
କୌଣସି ପୁନର୍ଲିଖନ ପଠାଇବାକୁ ମନା କରେ।

ଏହା ଆଶାକରାଯାଉଥିବା, ସୁରକ୍ଷିତ ଆଚରଣ, କୌଣସି ବଗ୍ ନୁହେଁ: ମୁଖ୍ୟତଃ ସ୍ୱଚ୍ଛ ଫାଇଲ୍ଗୁଡ଼ିକୁ ପଢ଼ୁଥିବା/grep କରୁଥିବା ଏକ କୋଡିଂ ସେସନ୍ରେ
କମ୍ପ୍ରେସନ୍ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ସକ୍ଷମ ଥିଲେ ମଧ୍ୟ ସାମାନ୍ୟ ମୋଟ ସଞ୍ଚୟ ଦେଖାଯିବ, ଯେତେବେଳେ ବିଫଳ ହେଉଥିବା ଏକ
ଲୁପ୍ କିମ୍ବା ଅତ୍ୟଧିକ ଆଉଟପୁଟ୍ ଦେଉଥିବା ଏକ ଲିଣ୍ଟର୍ର ସମ୍ମୁଖୀନ ହେଉଥିବା ସେସନ୍ରେ ସେହି ଟ୍ରାଫିକ୍ରେ ସମ୍ପୂର୍ଣ୍ଣ 78-95% ପରିସର ଦେଖାଯିବ। କମ୍ପ୍ରେସନ୍ ଭୁଲ ଭାବେ ବିନ୍ୟାସ ହୋଇଛି ବୋଲି ପ୍ରମାଣ ଭାବେ ଗୋଟିଏ ସେସନ୍ର
କମ୍ ସମଗ୍ର ସଞ୍ଚୟ ପ୍ରତିଶତକୁ ବ୍ୟବହାର କରନ୍ତୁ ନାହିଁ — ପ୍ରଥମେ ମୂଳ ଟୁଲ୍ ଆଉଟପୁଟ୍ ପ୍ରକୃତରେ ଅନାବଶ୍ୟକ ଭାବେ ପୁନରାବୃତ୍ତ ଥିଲା କି ନାହିଁ ଯାଞ୍ଚ କରନ୍ତୁ।

## ବିନ୍ୟାସ

### ଡ୍ୟାସ୍ବୋର୍ଡ

`ଡ୍ୟାସ୍ବୋର୍ଡ → ପ୍ରସଙ୍ଗ ଏବଂ କ୍ୟାଶ୍`କୁ ଯାଆନ୍ତୁ:

- **Caveman** — ମୋଡ୍ ଚୟନ, ଭାଷା ପ୍ୟାକ୍, ପୂର୍ବାବଲୋକନ ଏବଂ ଗ୍ଲୋବାଲ୍ ଡିଫଲ୍ଟଗୁଡ଼ିକ
- **RTK** — କମାଣ୍ଡ-ଫିଲ୍ଟର୍ ପୂର୍ବାବଲୋକନ, RTK ସୁରକ୍ଷା ସେଟିଂସ୍ ଏବଂ ଫିଲ୍ଟର୍ କ୍ୟାଟାଲଗ୍
- **କମ୍ପ୍ରେସନ୍ କମ୍ବୋଗୁଡ଼ିକ** — ରାଉଟିଂ କମ୍ବୋଗୁଡ଼ିକୁ ନ୍ୟସ୍ତ କରାଯାଇଥିବା ନାମିତ ଇଞ୍ଜିନ୍ ପାଇପ୍ଲାଇନ୍ଗୁଡ଼ିକ
- **ସ୍ୱୟଂଚାଳିତ-ଟ୍ରିଗର୍ ଥ୍ରେଶହୋଲ୍ଡ** — ଟୋକନ୍ ସଂଖ୍ୟା ଥ୍ରେଶହୋଲ୍ଡ ଅତିକ୍ରମ କଲେ ସ୍ୱୟଂଚାଳିତ ଭାବେ କମ୍ପ୍ରେସନ୍ ସକ୍ରିୟ କରେ

### ପ୍ରତି-କମ୍ବୋ ଓଭର୍ରାଇଡ୍

`ଡ୍ୟାସ୍ବୋର୍ଡ → ପ୍ରସଙ୍ଗ ଏବଂ କ୍ୟାଶ୍ → କମ୍ପ୍ରେସନ୍ କମ୍ବୋଗୁଡ଼ିକ`ରେ, ଏକ ରାଉଟିଂ
କମ୍ବୋକୁ ଏକ କମ୍ପ୍ରେସନ୍ କମ୍ବୋ ନ୍ୟସ୍ତ କରନ୍ତୁ:

```txt
କମ୍ବୋ: "free-tier-fallback"
  କମ୍ପ୍ରେସନ୍ କମ୍ବୋ: "coding-agent-stack"
  ପାଇପ୍ଲାଇନ୍: RTK -> Caveman
  ଲକ୍ଷ୍ୟଗୁଡ଼ିକ:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

ଏହା ଆପଣଙ୍କୁ ପେଡ୍ ସବ୍ସ୍କ୍ରିପ୍ସନ୍ଗୁଡ଼ିକରେ ଲାଇଟ୍ ମୋଡ୍ ରଖିବା ସହିତ ମାଗଣା/କୋଡିଂ
ପ୍ରଦାନକାରୀମାନଙ୍କରେ ସ୍ତରୀକୃତ କମ୍ପ୍ରେସନ୍ ବ୍ୟବହାର କରିବାକୁ ଦିଏ।

ଏହି "ପ୍ରତି-କମ୍ବୋ ଓଭର୍ରାଇଡ୍" ନ୍ୟସ୍ତକରଣଟି **ରାଉଟିଂ-କମ୍ବୋ କମ୍ପ୍ରେସନ୍
ମୋଡ୍** ଓଭର୍ରାଇଡ୍ଠାରୁ ଭିନ୍ନ ଏକ ନିୟନ୍ତ୍ରଣ (ଡିଫଲ୍ଟ/ବନ୍ଦ/ଲାଇଟ୍/ଷ୍ଟାଣ୍ଡାର୍ଡ/ଆଗ୍ରେସିଭ୍/ଅଲ୍ଟ୍ରା/Codex Responses — ଏହି ଫିଲ୍ଡର
ସ୍କିମା `rtk`, `stacked` ଏବଂ `omniglyph`କୁ ମଧ୍ୟ ଗ୍ରହଣ କରେ) — ସେହି ଓଭର୍ରାଇଡ୍ କୌଣସି ନାମିତ
କମ୍ପ୍ରେସନ୍-କମ୍ବୋ ପାଇପ୍ଲାଇନ୍ ବାଛେ ନାହିଁ; ଏହା କେବଳ `resolveCompressionPlan` ଦ୍ୱାରା ପରାମର୍ଶ କରାଯାଉଥିବା
`compressionMode` ଫିଲ୍ଡକୁ ସେଟ୍ କରେ। ଏହାକୁ କମ୍ବୋ କାର୍ଡରେ (`ଡ୍ୟାସ୍ବୋର୍ଡ → କମ୍ବୋଗୁଡ଼ିକ`) କିମ୍ବା, #6760ଠାରୁ,
`ଡ୍ୟାସ୍ବୋର୍ଡ → ପ୍ରସଙ୍ଗ ଏବଂ କ୍ୟାଶ୍ → କମ୍ପ୍ରେସନ୍ କମ୍ବୋଗୁଡ଼ିକ`ର "ରାଉଟିଂକୁ ନ୍ୟସ୍ତ କରନ୍ତୁ" ତାଲିକାରେ ପ୍ରତ୍ୟେକ ରାଉଟିଂ କମ୍ବୋ ପାଇଁ, ଉପରେ
ଦଲିଲଭୁକ୍ତ ପାଇପ୍ଲାଇନ୍-ନ୍ୟସ୍ତକରଣ ଚେକ୍ବକ୍ସର ଠିକ୍ ପାଖରେ ସେଟ୍ କରାଯାଇପାରିବ।
ଉଭୟ ଇଣ୍ଟରଫେସ୍ ସମାନ `PUT /api/combos/{id}` ଏଣ୍ଡପଏଣ୍ଟ ମାଧ୍ୟମରେ ସ୍ଥାୟୀ ହୋଇ ରହେ।

### ପ୍ରତି-ଅନୁରୋଧ ଓଭର୍ରାଇଡ୍

ଗୋଟିଏ ଅନୁରୋଧ ପାଇଁ କମ୍ପ୍ରେସନ୍ ପ୍ଲାନ୍କୁ ଓଭର୍ରାଇଡ୍ କରିବାକୁ `x-omniroute-compression` ଅନୁରୋଧ ହେଡର୍
ପଠାନ୍ତୁ। ଏହାର ପ୍ରାଧାନ୍ୟ ସର୍ବାଧିକ — ଏହା ରାଉଟିଂ-କମ୍ବୋ ଓଭର୍ରାଇଡ୍, ସକ୍ରିୟ ପ୍ରୋଫାଇଲ୍,
ସ୍ୱୟଂଚାଳିତ-ଟ୍ରିଗର୍ ଏବଂ ପ୍ୟାନେଲ୍ ଡିଫଲ୍ଟକୁ ଅତିକ୍ରମ କରେ। ଅଜଣା ମୂଲ୍ୟଗୁଡ଼ିକୁ ଅଣଦେଖା କରାଯାଏ (ଅନୁରୋଧ କେବେବି ପ୍ରତ୍ୟାଖ୍ୟାନ ହୁଏ ନାହିଁ) ଏବଂ
ଗ୍ଲୋବାଲ୍ ମାଷ୍ଟର୍ ସ୍ୱିଚ୍ ତଥାପି ସବୁକିଛିକୁ ନିୟନ୍ତ୍ରଣ କରେ: ଯେତେବେଳେ କମ୍ପ୍ରେସନ୍ ଗ୍ଲୋବାଲ୍ ଭାବେ ବନ୍ଦ ଥାଏ, ହେଡର୍ ଏହାକୁ
ସକ୍ରିୟ କରିପାରିବ ନାହିଁ। ମୂଲ୍ୟଗୁଡ଼ିକ:

| ମୂଲ୍ୟ         | ପ୍ରଭାବ                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `off`         | ଏହି ଅନୁରୋଧ ପାଇଁ କୌଣସି କମ୍ପ୍ରେସନ୍ ନାହିଁ।                                                          |
| `default`     | ପ୍ୟାନେଲ୍ରୁ ପ୍ରାପ୍ତ ଡିଫଲ୍ଟ ପ୍ରୋଫାଇଲ୍ (ସକ୍ରିୟ ପ୍ରୋଫାଇଲ୍କୁ ଅଣଦେଖା କରେ)। ଲସି ଇଞ୍ଜିନ୍ଗୁଡ଼ିକ ବନ୍ଦ ରହେ। |
| `safe`        | ହେଡର୍ ବାଦ୍ ଦେବା ସହିତ ସମାନ: କେବଳ ଡିଡୁପ୍ ଏବଂ ହ୍ୱାଇଟ୍ସ୍ପେସ୍ ଫୋଲ୍ଡିଂ।                                |
| `allow-lossy` | ସାରାଂଶ, ପ୍ରାସଙ୍ଗିକତା ଫିଲ୍ଟର୍ ଏବଂ ଶୈଳୀ ପୁନର୍ଲିଖନ ସହିତ ଏହି ଅନୁରୋଧର ଅପରେଟର୍ ପ୍ଲାନ୍କୁ ରଖେ।           |
| `engine:<id>` | ସକ୍ରିୟ ଥିଲେ ଗୋଟିଏ ଇଞ୍ଜିନ୍, ଯଥା `engine:rtk`। ସେହି ଇଞ୍ଜିନ୍ ପାଇଁ ଏହା ପ୍ରତି-ଅନୁରୋଧ ଅପ୍ଟ-ଇନ୍।        |
| `<combo>`     | ଏକ ନାମିତ କମ୍ବୋ, ପ୍ରଥମେ ନାମ ଅନୁଯାୟୀ (କେସ୍-ଅସମ୍ବେଦନଶୀଳ), ତା'ପରେ id ଅନୁଯାୟୀ ମେଳ କରାଯାଏ।             |

`allow-lossy`, `engine:<id>` କିମ୍ବା ଏକ ନାମିତ କମ୍ବୋ ବିନା, ଲସି ଇଞ୍ଜିନ୍ଗୁଡ଼ିକ ପ୍ରୟୋଗ କରାଯାଏ ନାହିଁ।
କମ୍ପ୍ରେସନ୍ ସକ୍ରିୟ ଥିଲେ ଅନୁରୋଧଟି ତଥାପି ସେସନ୍ ଡିଡୁପ୍ ଏବଂ ହ୍ୱାଇଟ୍ସ୍ପେସ୍ ଫୋଲ୍ଡିଂ ପାଏ।

ପ୍ରୟୋଗ କରାଯାଇଥିବା ପ୍ଲାନ୍କୁ `X-OmniRoute-Compression: <mode>; source=<source>` ପ୍ରତିକ୍ରିୟା
ହେଡର୍ରେ ପୁନଃ ପଠାଯାଏ, ଯେଉଁଠାରେ `<source>` ହେଉଛି `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default`, କିମ୍ବା `off` ମଧ୍ୟରୁ ଗୋଟିଏ।

### API

```bash
# କମ୍ପ୍ରେସନ୍ ସେଟିଂସ୍ ପ୍ରାପ୍ତ କରନ୍ତୁ
curl http://localhost:20128/api/settings/compression

# କମ୍ପ୍ରେସନ୍ ସେଟିଂସ୍ ଅଦ୍ୟତନ କରନ୍ତୁ
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ RTK/stacked ପେଲୋଡ୍ର ପୂର୍ବାବଲୋକନ କରନ୍ତୁ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# RTK ଫିଲ୍ଟର୍ ପ୍ୟାକ୍ଗୁଡ଼ିକର ତାଲିକା ଦେଖନ୍ତୁ
curl http://localhost:20128/api/context/rtk/filters

# ଇଚ୍ଛାଧୀନ କମାଣ୍ଡ ମେଟାଡାଟା ସହିତ RTKକୁ ସିଧାସଳଖ ପରୀକ୍ଷା କରନ୍ତୁ
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## ସ୍ୱୀକୃତି

ଷ୍ଟାଣ୍ଡାର୍ଡ ମୋଡ୍ କମ୍ପ୍ରେସନ୍ ନିୟମଗୁଡ଼ିକ **[JuliusBrussee](https://github.com/JuliusBrussee)**ଙ୍କ **[Caveman](https://github.com/JuliusBrussee/caveman)** (⭐ 51K+) ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ — ଭାଇରାଲ୍ "କମ୍ ଟୋକେନ୍ରେ କାମ ହେଉଥିବା ବେଳେ ଅଧିକ ଟୋକେନ୍ କାହିଁକି ବ୍ୟବହାର କରିବେ" ପ୍ରକଳ୍ପ। Caveman `~75%` କମ୍ ଆଉଟପୁଟ୍ ଟୋକେନ୍, ବେଞ୍ଚମାର୍କରେ ହାରାହାରି `65%` ଆଉଟପୁଟ୍ ସଞ୍ଚୟ, `22-87%` ଆଉଟପୁଟ୍ ପରିସର ଏବଂ ଏକ `~46%` ଇନ୍ପୁଟ୍-କମ୍ପ୍ରେସନ୍ ଟୁଲ୍ ରିପୋର୍ଟ କରେ।

RTK ମୋଡ୍ **[RTK AI](https://github.com/rtk-ai)**ର **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** ଦ୍ୱାରା ଅନୁପ୍ରାଣିତ — ଟର୍ମିନାଲ୍, ବିଲ୍ଡ, ଟେଷ୍ଟ, git ଏବଂ ଟୁଲ୍-ଆଉଟପୁଟ୍ ଫିଲ୍ଟରିଂ ପାଇଁ ଉଚ୍ଚ-କାର୍ଯ୍ୟକ୍ଷମତାସମ୍ପନ୍ନ କମାଣ୍ଡ-ଆଉଟପୁଟ୍ କମ୍ପ୍ରେସନ୍ ପ୍ରକଳ୍ପ। RTK `60-90%` ସଞ୍ଚୟ ରିପୋର୍ଟ କରେ, ଏବଂ ଏହାର README ନମୁନା ସେସନ୍ରେ `~80%` ସଞ୍ଚୟ ଦେଖାଯାଇଛି।

## ଉନ୍ନତ କମ୍ପ୍ରେସନ୍ ସିଷ୍ଟମ୍ଗୁଡ଼ିକ

ଉପରେ ବର୍ଣ୍ଣିତ 7ଟି ମୋଡ୍ ବ୍ୟତୀତ (ସୋର୍ସ `codex-responses` ଏବଂ
`omniglyph` ମୋଡ୍ଗୁଡ଼ିକୁ ମଧ୍ୟ ଗ୍ରହଣ କରେ, ଯାହା ଏହି ଗାଇଡ୍ରେ ଆଲୋଚନା କରାଯାଇନାହିଁ), ନିମ୍ନର ବିଭାଗଗୁଡ଼ିକ ସେହି ମୋଡ୍ଗୁଡ଼ିକ ଭିତରେ କିମ୍ବା ସେଗୁଡ଼ିକ ସହିତ କାର୍ଯ୍ୟ କରୁଥିବା ବୈଶିଷ୍ଟ୍ୟଗୁଡ଼ିକୁ ବର୍ଣ୍ଣନା କରେ: ଟୁଲ୍ ରିଜଲ୍ଟ କମ୍ପ୍ରେସନ୍ ଏବଂ ପ୍ରୋଗ୍ରେସିଭ୍ ଏଜିଂ ହେଉଛି ଆଗ୍ରେସିଭ୍ ଇଞ୍ଜିନ୍ର ପଦକ୍ଷେପ 1 ଏବଂ 2 (ଆଗ୍ରେସିଭ୍ ମୋଡ୍ ଏବଂ ଏକ
ଷ୍ଟାକ୍ଡ ପାଇପ୍ଲାଇନ୍ର `aggressive` ପଦକ୍ଷେପ), ଷ୍ଟାକ୍ଡ ପାଇପ୍ଲାଇନ୍ ହେଉଛି ଷ୍ଟାକ୍ଡ ମୋଡ୍ ଚାଲିବାର ପ୍ରଣାଳୀ, କ୍ୟାଶ୍-ଆୱେର୍ କମ୍ପ୍ରେସନ୍ କମ୍ପ୍ରେସନ୍
ସକ୍ରିୟ ଥିବା ସମୟରେ କ୍ୟାଶିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ `aggressive` ଏବଂ `ultra`କୁ `standard`କୁ ଡାଉନ୍ଗ୍ରେଡ୍ କରେ, ଏବଂ Caveman ଆଉଟପୁଟ୍ ମୋଡ୍ ଓ ଆଉଟପୁଟ୍ ଶୈଳୀଗୁଡ଼ିକ ହେଉଛି ଇଚ୍ଛାଧୀନ ସିଷ୍ଟମ୍-ପ୍ରମ୍ପ୍ଟ ନିର୍ଦ୍ଦେଶ, ଯାହା ଡିଫଲ୍ଟ ଭାବେ ବନ୍ଦ ଥାଏ ଏବଂ ଅନୁରୋଧକୁ କମ୍ପ୍ରେସ୍ କରିବା ପରିବର୍ତ୍ତେ ମଡେଲ୍ର ଆଉଟପୁଟ୍କୁ ଆକାର ଦିଏ।

### କ୍ୟାଶ୍-ଆୱେର୍ କମ୍ପ୍ରେସନ୍

କିଛି ପ୍ରଦାନକାରୀ (ଯେପରିକି ପ୍ରମ୍ପ୍ଟ କ୍ୟାଶିଂ ସହିତ Anthropic) **ପ୍ରମ୍ପ୍ଟ କ୍ୟାଶିଂ** ସମର୍ଥନ କରନ୍ତି,
ଯାହା ସେମାନଙ୍କୁ ଖର୍ଚ୍ଚ ଏବଂ ବିଳମ୍ବ କମାଇବା ପାଇଁ ପ୍ରମ୍ପ୍ଟର କିଛି ଅଂଶ କ୍ୟାଶ୍ କରିବାକୁ ଦିଏ। କ୍ୟାଶିଂ
ସକ୍ରିୟ ଥିବାବେଳେ, ଆଗ୍ରେସିଭ୍ କମ୍ପ୍ରେସନ୍ ବାସ୍ତବରେ କାର୍ଯ୍ୟକ୍ଷମତାକୁ **କ୍ଷତିଗ୍ରସ୍ତ** କରିପାରେ,
କାରଣ ଏହା କ୍ୟାଶ୍ ହୋଇଥିବା ଟୋକେନ୍ଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରି କ୍ୟାଶ୍କୁ ଅବୈଧ କରିଦିଏ।

`cachingAware.ts` ମଡ୍ୟୁଲ୍ **କ୍ୟାଶିଂ କଣ୍ଟେକ୍ସ୍ଟ ଚିହ୍ନଟ** କରି ଏବଂ
ସେହି ଅନୁସାରେ **କମ୍ପ୍ରେସନ୍ ରଣନୀତି ସମନ୍ୱୟ** କରି ଏହାର ସମାଧାନ କରେ।

#### ଏହା କିପରି କାମ କରେ

1. **କ୍ୟାଶିଂ କଣ୍ଟେକ୍ସ୍ଟ ଚିହ୍ନଟ କରେ** — `cache_control` ମାର୍କର୍ ପାଇଁ ଅନୁରୋଧ ବଡିକୁ ସ୍କାନ୍ କରେ
2. **କ୍ୟାଶିଂ ପ୍ରଦାନକାରୀଙ୍କୁ ଚିହ୍ନଟ କରେ** — ଲକ୍ଷ୍ୟ ପ୍ରଦାନକାରୀ କ୍ୟାଶିଂ ସମର୍ଥନ କରନ୍ତି କି ନାହିଁ ଯାଞ୍ଚ କରେ
3. **ରଣନୀତି ସମନ୍ୱୟ କରେ** — କ୍ୟାଶିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ `aggressive`/`ultra`କୁ `standard`କୁ ଡାଉନ୍ଗ୍ରେଡ୍ କରେ
4. **ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ଛାଡ଼ିଦିଏ** — ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟଗୁଡ଼ିକ ସାଧାରଣତଃ କ୍ୟାଶ୍ ହୋଇଥାଏ, ତେଣୁ ସେଗୁଡ଼ିକୁ କମ୍ପ୍ରେସ୍ କରନ୍ତୁ ନାହିଁ

ରଣନୀତି ସହାୟକ ଏକ `deterministicOnly` ଫ୍ଲାଗ୍ ମଧ୍ୟ ଫେରାଏ, କିନ୍ତୁ ପ୍ଲାନ୍ ବିଲ୍ଡର୍
କେବଳ ରଣନୀତିକୁ ବ୍ୟବହାର କରେ — ବର୍ତ୍ତମାନ ଡାଉନ୍ଷ୍ଟ୍ରିମ୍ରେ କୌଣସି ଅଂଶ ଏହି ଫ୍ଲାଗ୍କୁ ପଢ଼େ ନାହିଁ।

#### କୋଡ୍ ଉଦାହରଣ

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← କ୍ୟାଶ୍ ମାର୍କର୍
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### କେବେ ବ୍ୟବହାର କରିବେ

କ୍ୟାଶ୍-ଆୱେର୍ କମ୍ପ୍ରେସନ୍ **ସର୍ବଦା ସକ୍ରିୟ** — କୌଣସି କନ୍ଫିଗରେସନ୍ ଆବଶ୍ୟକ ନାହିଁ। କମ୍ପ୍ରେସନ୍
ସକ୍ରିୟ ଥିବାବେଳେ ଏବଂ ଲକ୍ଷ୍ୟ ପ୍ରଦାନକାରୀ ପ୍ରମ୍ପ୍ଟ କ୍ୟାଶିଂ ସମର୍ଥନ କଲେ (Anthropic, OpenAI,
ଇତ୍ୟାଦି) ଏହା କାର୍ଯ୍ୟକ୍ଷମ ହୁଏ; ସ୍ପଷ୍ଟ `cache_control` ମାର୍କର୍ ଆବଶ୍ୟକ ନୁହେଁ — କେବଳ ଏକ କ୍ୟାଶିଂ ପ୍ରଦାନକାରୀ ହିଁ
ଡାଉନ୍ଗ୍ରେଡ୍କୁ ଟ୍ରିଗର୍ କରେ, ଏବଂ କେବଳ ମାର୍କର୍ କଦାପି ତାହା କରେ ନାହିଁ (ମାର୍କର୍ ଚିହ୍ନଟ କ୍ୟାଶ୍
ଟେଲିମେଟ୍ରିକୁ ଡାଟା ଯୋଗାଏ, ରଣନୀତି ନିଷ୍ପତ୍ତିକୁ ନୁହେଁ)।

### ପ୍ରୋଗ୍ରେସିଭ୍ ଏଜିଂ

ଦୀର୍ଘ କଥୋପକଥନରେ ଅନେକ ମେସେଜ୍ ଟର୍ଣ୍ଣ ସଞ୍ଚିତ ହୁଏ, କିନ୍ତୁ ପୁରୁଣା ଟର୍ଣ୍ଣଗୁଡ଼ିକ କ୍ରମେ କମ୍
ପ୍ରାସଙ୍ଗିକ ହୋଇଯାଏ। `progressiveAging.ts` ମଡ୍ୟୁଲ୍ **ଟର୍ଣ୍ଣ ଦୂରତା ଅନୁଯାୟୀ ମେସେଜ୍ଗୁଡ଼ିକୁ ଅବନତ କରେ**
(ଦୂରତାକୁ କଥୋପକଥନର ଶେଷରୁ ମାପାଯାଏ)। ପ୍ରକାଶିତ ଡିଫଲ୍ଟଗୁଡ଼ିକ
(`verbatim: 2, light: 2, moderate: 3`) ସହିତ:

- **ଶେଷ 2ଟି ଟର୍ଣ୍ଣ (ଦୂରତା ≤ 2)**: ଅବିକଳ ରଖାଯାଏ
- **ଦୂରତା 3**: କେଭ୍ମ୍ୟାନ୍ ସଙ୍କୋଚନ (ଅନାବଶ୍ୟକ ଶବ୍ଦ ଅପସାରଣ)
- **ଦୂରତା 4+**: ଆସିଷ୍ଟାଣ୍ଟ ସନ୍ଦେଶଗୁଡ଼ିକର ସାରାଂଶ କରାଯାଏ; ବ୍ୟବହାରକାରୀ ସନ୍ଦେଶଗୁଡ଼ିକୁ ସେମାନଙ୍କ ପ୍ରଥମ
  ଧାଡ଼ିକୁ ହ୍ରାସ କରାଯାଏ, ସର୍ବାଧିକ 120 ଅକ୍ଷର ପର୍ଯ୍ୟନ୍ତ; ଅନ୍ୟ ଭୂମିକାଗୁଡ଼ିକୁ ଅପରିବର୍ତ୍ତିତ ରଖାଯାଏ। ଦୂରତା ନିର୍ବିଶେଷରେ ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ, ପୂର୍ବରୁ ପୁରୁଣା କରାଯାଇଥିବା
  ସନ୍ଦେଶ ଏବଂ ସର୍ବଶେଷ ବ୍ୟବହାରକାରୀ ସନ୍ଦେଶକୁ ସବୁବେଳେ ଅବିକଳ ରଖାଯାଏ।
  କୌଣସି ବିଷୟକୁ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ ବାଦ ଦିଆଯାଏ ନାହିଁ, ଏବଂ ପ୍ରଦତ୍ତ ଡିଫଲ୍ଟଗୁଡ଼ିକ ସହିତ `light`
  ବ୍ୟାଣ୍ଡକୁ ପହଞ୍ଚିବା ସମ୍ଭବ ନୁହେଁ (`light`, `verbatim` ସହ ସମାନ)।

#### କୋଡ୍ ଉଦାହରଣ

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ଆହୁରି 50ଟି ଟର୍ଣ୍ଣ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // ଶେଷ 3ଟି ଟର୍ଣ୍ଣ: ଅବିକଳ
  light: 8, // ଦୂରତା <= 8: ହାଲୁକା ସଙ୍କୋଚନ
  moderate: 20, // ଦୂରତା <= 20: କେଭ୍ମ୍ୟାନ୍ ସଙ୍କୋଚନ
  fullSummary: 5, // ଟାଇପ୍ ଦ୍ୱାରା ଆବଶ୍ୟକ, ବ୍ୟାଣ୍ଡିଂ କୋଡ୍ ଦ୍ୱାରା ପଢ଼ାଯାଏ ନାହିଁ
  // ଦୂରତା > 20: ସାରାଂଶ କରାଯାଏ (ଆସିଷ୍ଟାଣ୍ଟ) / ପ୍ରଥମ ଧାଡ଼ି ରଖାଯାଏ (ବ୍ୟବହାରକାରୀ)
});

// saved = ସଞ୍ଚୟ ହୋଇଥିବା ଟୋକେନ୍ର ସଂଖ୍ୟା
```

#### କେବେ ବ୍ୟବହାର କରିବେ

`aggressive` ମୋଡ୍ ପାଇଁ ପ୍ରୋଗ୍ରେସିଭ୍ ଏଜିଂ **ସବୁବେଳେ ସକ୍ରିୟ** — ଏହା
`compressAggressive()`ର ପଦକ୍ଷେପ 2। Ultra ମୋଡ୍ ଏହାକୁ ଚଲାଏ ନାହିଁ। ଏହା ବିଶେଷ ଭାବରେ
ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରରେ ପ୍ରଭାବଶାଳୀ:

- ଦୀର୍ଘକାଳୀନ କୋଡିଂ ସେସନ୍
- ଏକାଧିକ ଦିନ ଧରି ଚାଲୁଥିବା ବାର୍ତ୍ତାଳାପ
- ଅନେକ ଟୁଲ୍ କଲ୍ ଥିବା ଏଜେଣ୍ଟିକ୍ କାର୍ଯ୍ୟପ୍ରବାହ

### କେଭ୍ମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍

କେଭ୍ମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍ **ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ ନିର୍ଦ୍ଦେଶ** ଯୋଗ କରେ, ଯାହା ମଡେଲ୍କୁ ନିଜେ
ସଂକ୍ଷିପ୍ତ ଆଉଟପୁଟ୍ ଦେବାକୁ କହେ — `lite` ସ୍ତରଟି ପୂର୍ଣ୍ଣ ବାକ୍ୟ ରଖି ସଂକ୍ଷିପ୍ତ ଉତ୍ତର ମାଗେ, `full`
ତାହାକୁ "ଚତୁର ଗୁହାମାନବ ପରି ସଂକ୍ଷିପ୍ତ ଉତ୍ତର ଦିଅ" ବୋଲି କହେ, ଏବଂ `ultra` ଟେଲିଗ୍ରାଫିକ୍ ଆଉଟପୁଟ୍ ମାଗେ;
ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକ କେବଳ ଅନୁରୋଧ କରିପାରନ୍ତି, ସେଗୁଡ଼ିକ ଏହାକୁ ସୁନିଶ୍ଚିତ କରିପାରନ୍ତି ନାହିଁ। ଅନୁରୋଧଗୁଡ଼ିକ
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ମାଧ୍ୟମରେ ସେଗୁଡ଼ିକୁ ପାଆନ୍ତି:
`open-sse/handlers/chatCore.ts` ପ୍ରଥମେ ବ୍ୟାକ୍ୱାର୍ଡ-କମ୍ପାଟିବିଲିଟି ଶିମ୍ ସହିତ ଚୟନକୁ ନିର୍ଦ୍ଧାରଣ କରେ
(`resolveOutputStyleSelection()` ଭିତରେ
`open-sse/services/compression/outputStyles/backCompat.ts`), ଯାହା `outputStyles`
ଖାଲି ଥିବାବେଳେ, ସକ୍ରିୟ `cavemanOutputMode`କୁ
`cavemanOutputMode.intensity`ରେ `terse-prose` ଆଉଟପୁଟ୍ ଶୈଳୀ ସହ ମ୍ୟାପ୍ କରେ
(ନିମ୍ନରେ ଥିବା ବ୍ୟାକ୍ୱାର୍ଡ-କମ୍ପାଟିବିଲିଟି ଦେଖନ୍ତୁ); ଏକ ଅଣ-ଖାଲି `outputStyles`
ଚୟନକୁ ଯେପରି ଅଛି ସେପରି ବ୍ୟବହାର କରାଯାଏ, ଏବଂ ତା’ପରେ `cavemanOutputMode.enabled` ଓ `intensity`ର
କୌଣସି ପ୍ରଭାବ ରହେ ନାହିଁ, ଯଦିଓ ଏହାର `autoClarity` ଟଗଲ୍ ତଥାପି ପ୍ରୟୋଗ ହୁଏ। `outputMode.ts`ରେ
ନିର୍ଦ୍ଦେଶ ପାଠ୍ୟଗୁଡ଼ିକ (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), ବିଷୟବସ୍ତୁ ବାଇପାସ୍ ଏବଂ
ଇଞ୍ଜେକ୍ସନ୍ ବ୍ୟବହାର କରୁଥିବା ସ୍ଥାନନିର୍ଦ୍ଧାରଣ ହେଲ୍ପର୍ ରହିଛି; ଏହାର ନିଜସ୍ୱ `applyCavemanOutputMode()` ଇଞ୍ଜେକ୍ଟର୍ର
କୌଣସି ପ୍ରଡକ୍ସନ୍ କଲର୍ ନାହିଁ।

#### ଏହା କିପରି କାମ କରେ

ଏହି ମୋଡ୍ ଇନପୁଟ୍କୁ ସଙ୍କୋଚନ କରେ ନାହିଁ। ଏହା ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟରେ ଏକ ନିର୍ଦ୍ଦେଶ ବ୍ଲକ୍ ଯୋଗ କରେ
(ନିମ୍ନରେ ଥିବା ଇଞ୍ଜେକ୍ସନ୍ କିପରି କାମ କରେ ଦେଖନ୍ତୁ), ଏବଂ ଅନୁରୋଧ ପାଇଁ ଚୟନ କରାଯାଇଥିବା ଯେକୌଣସି ଇନପୁଟ୍ ସଙ୍କୋଚନ ମୋଡ୍
ତା’ପରେ ମଧ୍ୟ ବ୍ଲକ୍ ବହନ କରୁଥିବା ବଡି ଉପରେ ଚାଲେ। ପ୍ରତ୍ୟେକ ସ୍ତର ଶେଷରେ ଥିବା ସାଧାରଣ
ସୀମାବଦ୍ଧତା ଧାରା ପୂର୍ବରୁ, ଇଂରାଜୀ `full` ସ୍ତରରେ ଲେଖାଅଛି:

> "ଚତୁର ଗୁହାମାନବ ପରି ସଂକ୍ଷିପ୍ତ ଉତ୍ତର ଦିଅ। ଆର୍ଟିକଲ୍ (a/an/the), ଅନାବଶ୍ୟକ ଶବ୍ଦ (just/really/basically/actually/simply), ଶିଷ୍ଟାଚାରମୂଳକ ଶବ୍ଦ, ଦ୍ୱିଧାସୂଚକ ଭାଷା ବାଦ ଦିଅ। ବାକ୍ୟଖଣ୍ଡ ଗ୍ରହଣୀୟ। ଛୋଟ ପ୍ରତିଶବ୍ଦ (extensive ନୁହେଁ big, implement ନୁହେଁ fix)। ସମସ୍ତ ବୈଷୟିକ ସାରବସ୍ତୁ, କୋଡ୍, ତ୍ରୁଟି, URLs, ପରିଚାୟକଗୁଡ଼ିକୁ ଅବିକଳ ରଖ।"

ଏହା ବିଶେଷ ଭାବରେ ନିମ୍ନଲିଖିତ ପାଇଁ ଭଲ କାମ କରେ:

- କୋଡ୍ ଜେନେରେସନ୍ (ଅଧିକ ସଂକ୍ଷିପ୍ତ ଆଉଟପୁଟ୍ = କମ୍ ଟୋକେନ୍)
- ଦ୍ରୁତ ପ୍ରଶ୍ନୋତ୍ତର (ବିସ୍ତୃତ ବ୍ୟାଖ୍ୟା ଆବଶ୍ୟକ ନାହିଁ)
- ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ (ଥ୍ରୁପୁଟ୍ ସର୍ବାଧିକ କରନ୍ତୁ)

#### କେବେ ବ୍ୟବହାର କରିବେ

କେଭ୍ମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍ **ଇଚ୍ଛାଧୀନ**। ସଙ୍କୋଚନ ସକ୍ରିୟ ଥିବାବେଳେ (`enabled: true`, Compression Settings ପୃଷ୍ଠାରେ ଥିବା ମାଷ୍ଟର୍ ଟଗଲ୍),
ଏହାକୁ `cavemanOutputMode.enabled` ସହିତ ସକ୍ରିୟ କରନ୍ତୁ; `intensity`
`lite`, `full` କିମ୍ବା `ultra` ବାଛେ:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ଏକ କମ୍ପ୍ରେସନ୍ କମ୍ବୋର **ଆଉଟପୁଟ୍ ମୋଡ୍** ଟଗଲ୍ (`outputMode`, `outputModeIntensity`ରେ ସ୍ତର)
ସେହି କମ୍ବୋ ଲାଗୁ ହେଉଥିବା ଅନୁରୋଧଗୁଡ଼ିକ ପାଇଁ ସମାନ ସ୍ୱିଚ୍ ସେଟ୍ କରେ, ଏବଂ
`omniroute_set_compression_engine` MCP ଟୁଲ୍ ଏହାକୁ ତାହାର ବୁଲିୟନ୍ `outputMode`
ଆର୍ଗୁମେଣ୍ଟ ମାଧ୍ୟମରେ ଲେଖେ। ଏକ ଅଣ-ଖାଲି `outputStyles` ଚୟନ ଏହି ସ୍ୱିଚ୍ଠାରୁ ଅଗ୍ରାଧିକାର ପାଏ। ଡ୍ୟାସ୍ବୋର୍ଡରେ,
**ସଂକ୍ଷିପ୍ତ ଗଦ୍ୟ** ଆଉଟପୁଟ୍ ଶୈଳୀ ସକ୍ରିୟ କରିବା ସମାନ ବ୍ଲକ୍କୁ ଇଞ୍ଜେକ୍ଟ କରେ (ନିମ୍ନରେ ଥିବା ଆଉଟପୁଟ୍
ଶୈଳୀଗୁଡ଼ିକ ଦେଖନ୍ତୁ)।

### ଆଉଟପୁଟ୍ ଶୈଳୀଗୁଡ଼ିକ (କ୍ୟାଟାଲଗ୍)

ଉପରେ ଥିବା କେଭ୍ମ୍ୟାନ୍ ଆଉଟପୁଟ୍ ମୋଡ୍ ହେଉଛି **ପୁରୁଣା ଏକକ-ଶୈଳୀ ପଥ**। Phase 4 ଏହାକୁ
ସଂଯୋଜନଯୋଗ୍ୟ ଆଉଟପୁଟ୍ ଶୈଳୀର ଏକ କ୍ୟାଟାଲଗ୍ରେ ସାଧାରଣୀକୃତ କରିଛି: `OUTPUT_STYLE_CATALOG`,
`open-sse/services/compression/outputStyles/catalog.ts`ରେ। ପ୍ରତ୍ୟେକ ଶୈଳୀ ହେଉଛି ଏକ ସିଷ୍ଟମ୍-ପ୍ରମ୍ପ୍ଟ
ନିର୍ଦ୍ଦେଶ, ଯାହା ମଡେଲ୍କୁ ନିଜେ କମ୍ ଖର୍ଚ୍ଚର ଆଉଟପୁଟ୍ ଦେବାକୁ କହେ; ଶୈଳୀଗୁଡ଼ିକୁ

settings API ଯେକୌଣସି style id ଗ୍ରହଣ କରେ, ଏବଂ ପୃଷ୍ଠାରେ ଅନ୍ୟ ଶୈଳୀଗୁଡ଼ିକୁ ସଞ୍ଚୟ କଲେ ଏହା ରହିଥାଏ। ଅନୁରୋଧ
ସମୟରେ, `applyOutputStyles()` ର ଭାଷା ଯାଞ୍ଚ ହିଁ ଏକମାତ୍ର ଲୋକେଲ୍ ଗେଟ୍।

#### ଇଞ୍ଜେକ୍ସନ୍ କିପରି କାମ କରେ

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) ଚୟନକୁ
କ୍ୟାଟାଲଗ୍ ସହିତ ସମାଧାନ କରେ (ଅଜଣା id ଏବଂ ଲୋକେଲ୍-ଅସଙ୍ଗତ ଶୈଳୀଗୁଡ଼ିକୁ
ବାଦ ଦିଆଯାଏ, କେବେ ତ୍ରୁଟି ହୁଏନାହିଁ; କୌଣସି ଶୈଳୀକୁ ସମାଧାନ ନକରୁଥିବା ଚୟନ bodyକୁ
ଅପରିବର୍ତ୍ତିତ ରଖେ, `no_styles` ଭାବେ ଏଡ଼ାଇ ଦିଆଯାଏ), ଚୟନିତ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ କ୍ୟାଟାଲଗ୍
କ୍ରମରେ ସଂଯୋଜନ କରେ,
ସୀମା ଧାରାକୁ **ଥରେ** ଯୋଡ଼େ (ସହିତ safety clause, `SAFETY_BOUNDARIES` କିମ୍ବା ଏହାର
ଅନୁବାଦ, ଯେତେବେଳେ `less-code` କିମ୍ବା `ponytail` ଚୟନ କରାଯାଏ), ଏବଂ ବ୍ଲକ୍କୁ
ଗୋଟିଏ ମାତ୍ର idempotency marker (`[OmniRoute Output Styles]`) ସହ ଆରମ୍ଭ କରେ, ତେଣୁ ପୁନଃ
ପ୍ରୟୋଗ କରିବା ଏକ no-op। ସମାଧାନ କରାଯାଇଥିବା ଭାଷାର (ତଳେ ଥିବା Language selection ଦେଖନ୍ତୁ) ଅନୁବାଦ ଥିଲେ, English ପରିବର୍ତ୍ତେ ସ୍ଥାନୀୟକୃତ
ନିର୍ଦ୍ଦେଶ ଇଞ୍ଜେକ୍ଟ କରାଯାଏ।

ଏକ non-empty `messages` array ଥିବା bodyରେ, idempotency ଯାଞ୍ଚ
content bypass ପୂର୍ବରୁ ଚାଲେ: ଯେତେବେଳେ `[OmniRoute Output Styles]` marker ପୂର୍ବରୁ top-level
`system` fieldରେ (ଏକ string କିମ୍ବା content-block array) କିମ୍ବା string
content ଥିବା system messageରେ ଅଛି, bodyକୁ `already_applied` ଭାବେ ଅପରିବର୍ତ୍ତିତ ରଖାଯାଏ ଏବଂ କୌଣସି keyword ଯାଞ୍ଚ ଚାଲେନାହିଁ।
ନଚେତ୍ ଏକ content bypass (`open-sse/services/compression/outputMode.ts` ରେ
`shouldBypassCavemanOutputMode()`) ଶେଷ ତିନୋଟି
messageର text ଯାଞ୍ଚ କରେ, ସେମାନଙ୍କ role ଯାହାହେଉନା କାହିଁକି, ଏବଂ ସେହି text ଏହାର security, irreversible-action କିମ୍ବା clarification keyword, ଅଥବା ଏକ
କ୍ରମ-ସମ୍ବେଦନଶୀଳ sequence ସହ ମେଳ ଖାଇଲେ ସମଗ୍ର turn ପାଇଁ styleଗୁଡ଼ିକୁ ଏଡ଼ାଇ ଦିଏ: `first`, `then`, `after that`, `before`, `rollback` କିମ୍ବା
`backup`, ଯାହାର 240 ଅକ୍ଷର ମଧ୍ୟରେ ପରେ `delete`, `drop`, `migrate`, `deploy` କିମ୍ବା
`release` ଥାଏ। **Auto-Clarity Bypass** toggle
(`cavemanOutputMode.autoClarity`, ଡିଫଲ୍ଟ ଭାବେ ଚାଲୁ) ଚାଲୁ ଥିବା ସମୟରେ bypass ଚାଲେ; toggleକୁ ବନ୍ଦ କଲେ
keyword ଯାଞ୍ଚ ଏଡ଼ାଇ ଦିଆଯାଏ।

bypass ଯେତେବେଳେ turnକୁ ଆଗକୁ ଯିବାକୁ ଦିଏ, `placeSystemInstruction()` (ସମାନ file), ଯାହା
କେବେ ନୂଆ `messages[0]` ସୃଷ୍ଟି କରେନାହିଁ, ବ୍ଲକ୍କୁ ଏହା ଖୋଜିପାଉଥିବା ପ୍ରଥମ ସ୍ଥାନରେ ରଖେ:

1. string content ଥିବା ଏକ ପ୍ରାରମ୍ଭିକ system message: ବ୍ଲକ୍ଟି ତାହାର text ପରେ ଯୋଡ଼ାଯାଏ।
2. top-level `system` field: ବ୍ଲକ୍ଟି ଏକ stringର text ପରେ ଯୋଡ଼ାଯାଏ, କିମ୍ବା
   ଏକ content-block arrayରେ ନୂଆ text block ଭାବେ ଯୋଡ଼ାଯାଏ।
3. string content ଥିବା ପରବର୍ତ୍ତୀ ପ୍ରଥମ system message: ବ୍ଲକ୍ଟି ତାହାର
   text ପରେ ଯୋଡ଼ାଯାଏ।
4. ଉପରୋକ୍ତ ମଧ୍ୟରୁ କିଛି ନୁହେଁ: ବ୍ଲକ୍ଟି `messages` ର ଶେଷରେ ଏକ ନୂଆ system message ଭିତରକୁ ଯାଏ।

`messages` array ନଥିବା (କିମ୍ବା ଖାଲି array ଥିବା) bodyରେ, କୌଣସି content bypass ଚାଲେନାହିଁ ଏବଂ
top-level `system` fieldକୁ ବିଚାର କରାଯାଏନାହିଁ। ବ୍ଲକ୍ଟି ଏକ string `instructions` fieldର text ପରେ ଯୋଡ଼ାଯାଏ,
ଯଦି ସେହି fieldରେ ପୂର୍ବରୁ
`[OmniRoute Output Styles]` marker ନଥାଏ; ଥିଲେ bodyକୁ
`already_applied` ଭାବେ ଅପରିବର୍ତ୍ତିତ ରଖାଯାଏ। bodyରେ string `instructions` field ନଥିଲେ କିନ୍ତୁ `input`
(ଏକ string କିମ୍ବା array) ଥିଲେ, ବ୍ଲକ୍ଟି `instructions` ହୁଏ ଏବଂ ସେହି fieldରେ ଥିବା ଯେକୌଣସି non-string valueକୁ
ପ୍ରତିସ୍ଥାପନ କରେ। string `instructions` field କିମ୍ବା string ବା array
`input` ମଧ୍ୟରୁ କୌଣସିଟି ନଥିବା bodyକୁ ଅପରିବର୍ତ୍ତିତ ରଖାଯାଏ ଏବଂ `no_messages` ଭାବେ ଏଡ଼ାଇ ଦିଆଯାଏ।

#### କିପରି ସକ୍ଷମ କରିବେ

ଡ୍ୟାଶବୋର୍ଡରେ: **Compression Context → Compression Settings**
(`/dashboard/context/settings`), Output styles ବିଭାଗ: ପ୍ରତ୍ୟେକ ଶୈଳୀ ପାଇଁ on/off
ଟଗଲ୍ ଏବଂ ଏକ ସ୍ତର ଚୟନକାରୀ ସହିତ ଗୋଟିଏ ଧାଡ଼ି। କମ୍ପ୍ରେସନ୍ ନିଜେ ଚାଲୁ ଥିବାବେଳେ ଶୈଳୀଗୁଡ଼ିକ ଇଞ୍ଜେକ୍ଟ ହୁଏ (ପୃଷ୍ଠାର
ମାଷ୍ଟର ଟଗଲ୍, `enabled`)। **Auto-Clarity Bypass** ଟଗଲ୍ଟି **Caveman**
ପୃଷ୍ଠାରେ (`/dashboard/context/caveman`), ଏହାର **Output Mode** କାର୍ଡରେ ଅଛି। ପ୍ରୋଗ୍ରାମ୍ ମାଧ୍ୟମରେ,
କମ୍ପ୍ରେସନ୍ କନଫିଗ୍ ଚୟନକୁ ଏପରି ସ୍ଥାୟୀ ଭାବରେ ସଂରକ୍ଷଣ କରେ:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ପଛୁଆ-ସୁସଙ୍ଗତି: `outputStyles` ଖାଲି ଥିବା ପର୍ଯ୍ୟନ୍ତ, ପୁରୁଣା `cavemanOutputMode.enabled`
ସେଟିଂଟି `cavemanOutputMode.intensity`ରେ `terse-prose` ସହିତ ମ୍ୟାପ୍ ହୁଏ। ତା’ପରେ ବ୍ଲକ୍ଟି

   ପ୍ରତିସ୍ଥାପିତ କରାଯାଏ (ଏକ ଆରେ ପାଇଁ, N ହେଉଛି ଏହାର ଦୈର୍ଘ୍ୟ) ଏବଂ ପ୍ରଥମ 20ଟି ପରେ ବାଦ୍ ଦିଆଯାଇଥିବା କୀଗୁଡ଼ିକୁ ଗଣିବା ପାଇଁ
   ଏକ `_remaining_<N>_keys` ମାର୍କର୍ ଥାଏ। ସ୍କେଲାର୍ ମୂଲ୍ୟଗୁଡ଼ିକ ସମ୍ପୂର୍ଣ୍ଣ ଭାବେ କପି ହୁଏ, ତେଣୁ ନେଷ୍ଟେଡ୍ ମୂଲ୍ୟ ନଥିବା
   20 କିମ୍ବା ତାହାଠାରୁ କମ୍ କୀ ଥିବା ଏକ ଅବଜେକ୍ଟକୁ କେବଳ ପୁନଃ-ଇଣ୍ଡେଣ୍ଟ କରାଯାଏ — ଏକ ମିନିଫାଇଡ୍ ଅବଜେକ୍ଟରେ ଅକ୍ଷର
   ବଢ଼ିଯାଏ ଏବଂ ଏହା ଅପରିବର୍ତ୍ତିତ ରହେ।
5. **`errorMessage`**: ଯେକୌଣସି ସ୍ଥାନରେ ଏବଂ ଅକ୍ଷରର ଯେକୌଣସି କେସ୍ରେ `error:`,
   `error ` (ଶବ୍ଦ ପରେ ଗୋଟିଏ ସ୍ପେସ୍, ଯେପରିକି `no error found`), `[error]`,
   `exception:`, `exception `, `[exception]` କିମ୍ବା `traceback` ଥିବା ଆଉଟ୍ପୁଟ୍ ଏହାର ପ୍ରଥମ ଧାଡ଼ି,
   ପରବର୍ତ୍ତୀ 10ଟି ଧାଡ଼ି ଏବଂ ଶେଷ 3ଟି ଧାଡ଼ି ରଖେ, ଏବଂ ସେଗୁଡ଼ିକ ମଧ୍ୟରେ ଥିବା ଧାଡ଼ିଗୁଡ଼ିକ ସ୍ଥାନରେ
   `… [N frames elided] …` ମାର୍କର୍ ରଖେ। ପ୍ରଥମ ଧାଡ଼ି ପରେ 13ଟିରୁ ଅଧିକ ଧାଡ଼ି ଥିଲେ ମାତ୍ର
   ମାର୍କର୍ ଦେଖାଯାଏ, ତେଣୁ 14ଟି କିମ୍ବା ତାହାଠାରୁ କମ୍ ଧାଡ଼ିର ତ୍ରୁଟି ଆଉଟ୍ପୁଟ୍କୁ ସଂକ୍ଷିପ୍ତ କରାଯାଏ ନାହିଁ (12 କିମ୍ବା 13ଟି ଧାଡ଼ିରେ
   ଶେଷ 3ଟି ଧାଡ଼ି ପୂର୍ବରୁ ରଖାଯାଇଥିବା ଧାଡ଼ିଗୁଡ଼ିକୁ ପୁନରାବୃତ୍ତ କରେ)।

ଗୋଟିଏ ରଣନୀତି ମେଳ ହେବା ପରେ, ଏପରିକି ଯଦି ତାହା କିଛି ସଞ୍ଚୟ ନ କରେ, ପରବର୍ତ୍ତୀ ରଣନୀତିଗୁଡ଼ିକୁ
ଚେଷ୍ଟା କରାଯାଏ ନାହିଁ। ଯେତେବେଳେ ମେଳ ହୋଇଥିବା ରଣନୀତି କୌଣସି ଆନୁମାନିକ ଟୋକନ୍ ସଞ୍ଚୟ କରେ ନାହିଁ (ଦୈର୍ଘ୍ୟ ÷ 4, ଉପରକୁ ପୂର୍ଣ୍ଣାଙ୍କିତ) —
ଉଦାହରଣ ସ୍ୱରୂପ 25ଟି କିମ୍ବା ତାହାଠାରୁ କମ୍ ଧାଡ଼ିର ଏକ କୋଡ୍-ସଦୃଶ ଫାଇଲ୍, କିମ୍ବା 2,000
ଅକ୍ଷରରୁ ଅଧିକ କିନ୍ତୁ 7ଟି କିମ୍ବା ତାହାଠାରୁ କମ୍ ଆଇଟମ୍ ଥିବା ଏକ JSON ଆରେ — ଆକ୍ରାମକ ଇଞ୍ଜିନ୍ ମୂଳ ଟୁଲ୍
ଫଳାଫଳକୁ ରଖେ: `saved` 0 କିମ୍ବା ତାହାଠାରୁ କମ୍ ଥିଲେ ଉଭୟ କଲର୍ (`compressAggressive()` ଏବଂ `compressAnthropicToolResultBlock()`)
ମୂଳଟିକୁ ରଖନ୍ତି, ଯେତେବେଳେ `compressToolResult()` ନିଜେ ତଥାପି
ସେହି ରଣନୀତିର ଆଉଟ୍ପୁଟ୍ ଫେରାଏ। ଟୁଲ୍-ଫଳାଫଳ ପଦକ୍ଷେପଟି ଚୂଡ଼ାନ୍ତ ନୁହେଁ:
ଇଞ୍ଜିନ୍ର ଫଲ୍ବ୍ୟାକ୍ ସାରାଂଶକାରୀ ଏବେ ମଧ୍ୟ 8,192 ଅକ୍ଷରରୁ ଅଧିକ ଲମ୍ବା `tool` କିମ୍ବା `function` ସନ୍ଦେଶକୁ
ସଂକ୍ଷିପ୍ତ କରିପାରେ (`maxTokensPerMessage`, 2,048, ଗୁଣିତ 4)।

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ

ଟୁଲ୍ ଫଳାଫଳ ସଂକୋଚନ ହେଉଛି ଆକ୍ରାମକ ଇଞ୍ଜିନ୍ର ପଦକ୍ଷେପ 1 (`compressAggressive()` ଏଠାରେ
`open-sse/services/compression/aggressive.ts`), ତେଣୁ ଏହା Aggressive ମୋଡ୍ରେ ଏବଂ ଏକ ଷ୍ଟାକ୍ଡ ପାଇପ୍ଲାଇନ୍ର
`aggressive` ପଦକ୍ଷେପରେ ଚାଲେ। ଏହା OpenAI-ଆକୃତିର `tool` ଓ `function`
ସନ୍ଦେଶଗୁଡ଼ିକ ଏବଂ Anthropic `tool_result` ବ୍ଲକ୍ଗୁଡ଼ିକ ଭିତରେ ଥିବା ପାଠ୍ୟକୁ ସଂକୁଚିତ କରେ। ପ୍ରତ୍ୟେକ ରଣନୀତିର
`aggressive.toolStrategies` ଅଧୀନରେ ନିଜସ୍ୱ ସ୍ୱିଚ୍ ଅଛି, ଯାହା ଡିଫଲ୍ଟ ଭାବରେ ସବୁ ଚାଲୁ ଥାଏ। ଡ୍ୟାସ୍ବୋର୍ଡରେ,
ସଂକୋଚନ ଚାଲୁ ଥିବାବେଳେ ଏବଂ ଡିଫଲ୍ଟ ମୋଡ୍ Aggressive ଥିଲେ, ସ୍ୱିଚ୍ଗୁଡ଼ିକ Caveman ପୃଷ୍ଠାର **Advanced** ଭ୍ୟୁରେ ଥାଏ।

### ଷ୍ଟାକ୍ଡ ପାଇପ୍ଲାଇନ୍

ଷ୍ଟାକ୍ଡ ମୋଡ୍ **ଏକାଧିକ ଇଞ୍ଜିନ୍କୁ କ୍ରମାନୁସାରେ** ଚଲାଏ — ସାଧାରଣତଃ ପ୍ରଥମେ RTK
(ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ରେ 60-90% ସଞ୍ଚୟ), ତାହା ପରେ ଅବଶିଷ୍ଟ ପାଠ୍ୟ ଉପରେ Caveman (~46% ଇନ୍ପୁଟ୍
ସଞ୍ଚୟ)। ମିଶ୍ରିତ ଭାବେ, ଏହା ହେଉଛି **78-95% ଯୋଗ୍ୟ ପରିସର** (ଉପରେ ଥିବା Upstream Savings Math ଦେଖନ୍ତୁ):
`1 - (1 - 0.60..0.90) × (1 - 0.46)`ର ହାରାହାରି ≈89%।

#### ଏହା କିପରି କାମ କରେ

```
ଇନ୍ପୁଟ୍ (1000 ଟୋକନ୍)
  → RTK (କମାଣ୍ଡ-ସଚେତନ ଫିଲ୍ଟର୍) → 200 ଟୋକନ୍
    → Caveman (ଅନାବଶ୍ୟକ ବିଷୟବସ୍ତୁ ଅପସାରଣ) → 108 ଟୋକନ୍
  → ଆଉଟ୍ପୁଟ୍ (108 ଟୋକନ୍, ~89% ସଞ୍ଚୟ)
```

#### କେତେବେଳେ ବ୍ୟବହାର କରିବେ

ଏଗୁଡ଼ିକ ପାଇଁ ଷ୍ଟାକ୍ଡ ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ:

- ଟୁଲ୍-ବହୁଳ ୱର୍କଫ୍ଲୋ (ଏଜେଣ୍ଟିକ୍ କୋଡିଂ, ଗବେଷଣା)
- ଖର୍ଚ୍ଚ-ସମ୍ବେଦନଶୀଳ ବ୍ୟାଚ୍ ପ୍ରକ୍ରିୟାକରଣ
- ଯେତେବେଳେ ଆପଣଙ୍କୁ ସର୍ବାଧିକ ଟୋକନ୍ ସଞ୍ଚୟ ଆବଶ୍ୟକ

ଷ୍ଟାକ୍ଡ ପାଇପ୍ଲାଇନ୍ଗୁଡ଼ିକୁ ଗ୍ଲୋବାଲ୍ `stackedPipeline` ସଂକୋଚନ
ସେଟିଂ ମାଧ୍ୟମରେ, କିମ୍ବା ଏକ ରାଉଟିଂ କମ୍ବୋକୁ ନ୍ୟସ୍ତ ହୋଇଥିବା ଏକ ନାମିତ ସଂକୋଚନ କମ୍ବୋ ମାଧ୍ୟମରେ ବିନ୍ୟାସ କରାଯାଏ (ଉପରେ ଥିବା
Per-Combo Override ଦେଖନ୍ତୁ) — ଏକ ଅଟୋ-କମ୍ବୋ `modePack` ମାଧ୍ୟମରେ ନୁହେଁ (ସେହି ଫିଲ୍ଡ କେବଳ
ଅଟୋ-କମ୍ବୋ ମଡେଲ୍ ଚୟନକୁ ପୁନଃ-ଭାରାଙ୍କିତ କରେ, ଏବଂ `stacked` ଏକ ବୈଧ ପ୍ୟାକ୍ ନାମ ନୁହେଁ)।

## କମ୍ପ୍ରେସନ୍ କମ୍ବୋ ଓଭରରାଇଡ୍

ବିଭିନ୍ନ ବ୍ୟବହାର ପରିସ୍ଥିତି ପାଇଁ ଆଚରଣକୁ ସୂକ୍ଷ୍ମ ଭାବରେ ସମନ୍ୱୟ କରିବାକୁ ଆପଣ **ପ୍ରତ୍ୟେକ କମ୍ବୋ ପାଇଁ** ଗ୍ଲୋବାଲ୍ କମ୍ପ୍ରେସନ୍ ମୋଡ୍କୁ ଓଭରରାଇଡ୍ କରିପାରିବେ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

ଏହା ନିମ୍ନଲିଖିତ କ୍ଷେତ୍ରରେ ଉପଯୋଗୀ:

- **କୋଡିଂ କମ୍ବୋ**: ଦୀର୍ଘ ସେସନ୍ ପାଇଁ `aggressive` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ଦ୍ରୁତ ପ୍ରଶ୍ନୋତ୍ତର କମ୍ବୋ**: ଦ୍ରୁତ ପ୍ରତିକ୍ରିୟା ପାଇଁ `lite` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ଅଧିକ ଟୁଲ୍-ଆଧାରିତ କମ୍ବୋ**: ସର୍ବାଧିକ ସଞ୍ଚୟ ପାଇଁ `stacked` ମୋଡ୍ ବ୍ୟବହାର କରନ୍ତୁ
- **ପ୍ରୋଡକ୍ସନ୍ କମ୍ବୋ**: କ୍ୟାସିଂ ପ୍ରଦାନକାରୀଙ୍କ ପାଇଁ ଓଭରରାଇଡ୍ ବନ୍ଦ ରଖନ୍ତୁ — ସର୍ବଦା ସକ୍ରିୟ
  କ୍ୟାସ୍-ସଚେତନ ସମନ୍ୱୟ `aggressive`/`ultra`କୁ ସ୍ୱୟଂଚାଳିତ ଭାବରେ `standard`କୁ ଡାଉନ୍ଗ୍ରେଡ୍ କରେ
  (ଚୟନଯୋଗ୍ୟ `cache-aware` ମୋଡ୍ ନାହିଁ)
