କମ୍ପ୍ରେସନ୍ ନିୟମଗୁଡ଼ିକ ହେଉଛି ରନ୍ଟାଇମ୍ରେ ଲୋଡ୍ ହେଉଥିବା JSON ଫାଇଲ୍। ସେଗୁଡ଼ିକୁ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବେ କେବଳ ଡାଟା ଭିତ୍ତିକ ରଖାଯାଇଛି, ଯାହାଦ୍ୱାରା ଇଞ୍ଜିନ୍ କୋଡ୍ ପରିବର୍ତ୍ତନ ନକରି ନୂଆ
ଭାଷା ପ୍ୟାକ୍ ଏବଂ RTK କମାଣ୍ଡ ଫିଲ୍ଟର୍ଗୁଡ଼ିକୁ ସମୀକ୍ଷା କରାଯାଇପାରିବ।

> **ପ୍ରାମାଣିକ ସ୍କିମା (ମୂଳ ସତ୍ୟ ଉତ୍ସ):** [`open-sse/services/compression/rules/_schema.json`](../../open-sse/services/compression/rules/_schema.json) (JSON Schema draft 2020-12)।
> ନିମ୍ନରେ ଥିବା ଉଦାହରଣଗୁଡ଼ିକ କେବଳ ଦୃଷ୍ଟାନ୍ତମୂଳକ — ସନ୍ଦେହ ହେଲେ, ଆପଣଙ୍କ ପ୍ୟାକ୍କୁ `_schema.json` ବିପରୀତରେ ବୈଧତା ଯାଞ୍ଚ କରନ୍ତୁ।

## Caveman ନିୟମ ପ୍ୟାକ୍

Caveman ନିୟମ ପ୍ୟାକ୍ଗୁଡ଼ିକ ଏହି ସ୍ଥାନରେ ରହେ:

```txt
open-sse/services/compression/rules/<language>/<pack>.json
```

ପ୍ରତ୍ୟେକ ପ୍ୟାକ୍ରେ ଏପରି ପ୍ରତିସ୍ଥାପନଗୁଡ଼ିକ ଥାଏ, ଯାହା ସୁରକ୍ଷିତ ଅଞ୍ଚଳଗୁଡ଼ିକୁ ପୃଥକ କରାଯିବା ପରେ ସାଧାରଣ ଗଦ୍ୟ ଉପରେ ପ୍ରୟୋଗ ହୁଏ।

```json
{
  "language": "en",
  "category": "filler",
  "rules": [
    {
      "name": "question_to_directive",
      "pattern": "\\b(?:Can you explain why|Could you show me how)\\b\\s*",
      "replacement": "Explain why ",
      "replacementMap": {
        "can you explain why": "Explain why ",
        "could you show me how": "Show how "
      },
      "flags": "gi",
      "context": "all",
      "category": "context",
      "minIntensity": "lite",
      "description": "Convert verbose questions into direct requests."
    }
  ]
}
```

### Caveman ଫିଲ୍ଡଗୁଡ଼ିକ

| ଫିଲ୍ଡ                    | ଆବଶ୍ୟକ | ବର୍ଣ୍ଣନା                                                                               |
| ------------------------ | ------ | -------------------------------------------------------------------------------------- |
| `language`               | ହଁ     | `en`, `pt-BR`, `es` ପରି BCP-47-ସଦୃଶ ଭାଷା କୀ                                            |
| `category`               | ହଁ     | ପ୍ୟାକ୍ ବର୍ଗ ଫାଇଲ୍ ନାମ/ବର୍ଗ, ଉଦାହରଣ ସ୍ୱରୂପ `filler` କିମ୍ବା `dedup`                      |
| `rules`                  | ହଁ     | regex ପ୍ରତିସ୍ଥାପନ ନିୟମଗୁଡ଼ିକର ଆରେ                                                      |
| `rules[].name`           | ହଁ     | ସ୍ଥିର ନିୟମ ନାମ                                                                         |
| `rules[].pattern`        | ହଁ     | JavaScript regex ଉତ୍ସ                                                                  |
| `rules[].flags`          | ନା     | JavaScript regex ଫ୍ଲାଗ୍; ଡିଫଲ୍ଟ `gi`                                                   |
| `rules[].replacement`    | ନା     | ପ୍ରତିସ୍ଥାପନ ଷ୍ଟ୍ରିଙ୍ଗ୍ କିମ୍ବା `replacementMap`ରେ ମେଳ ନମିଳିଲେ ଫଲ୍ବ୍ୟାକ୍                 |
| `rules[].replacementMap` | ନା     | ସାମାନ୍ୟୀକୃତ ମେଳ ହୋଇଥିବା ଟେକ୍ସଟ୍ ଦ୍ୱାରା କୀ କରାଯାଇଥିବା ମେଳ-ନିର୍ଦ୍ଦିଷ୍ଟ ପ୍ରତିସ୍ଥାପନଗୁଡ଼ିକ |
| `rules[].context`        | ନା     | `all`, `user`, `assistant`, କିମ୍ବା `system`; ଡିଫଲ୍ଟ `all`                              |
| `rules[].category`       | ନା     | `filler`, `context`, `structural`, `dedup`, `terse`, କିମ୍ବା `ultra`                    |
| `rules[].minIntensity`   | ନା     | `lite`, `full`, କିମ୍ବା `ultra`; ଡିଫଲ୍ଟ `lite`                                          |
| `rules[].description`    | ନା     | ମଣିଷ ପଢ଼ିପାରିବା ଯୋଗ୍ୟ ନିୟମ ସାରାଂଶ                                                      |

ଯେତେବେଳେ କେସ୍-ସେନ୍ସିଟିଭ୍ ମେଳକରଣ ଗୁରୁତ୍ୱପୂର୍ଣ୍ଣ ହୁଏ, ସେତେବେଳେ `flags` ବ୍ୟବହାର କରନ୍ତୁ; ଉଦାହରଣ ସ୍ୱରୂପ,
`the OpenAI API`କୁ ହଟାଇ ନଦେଇ ଲୋୟର୍କେସ୍ ଗଦ୍ୟ ପୂର୍ବରୁ ଆର୍ଟିକଲ୍ ଅପସାରଣ ପାଇଁ। ଯେତେବେଳେ ଗୋଟିଏ regexରେ ଏକାଧିକ ବିକଳ୍ପ ଥାଏ
ଏବଂ ସେଗୁଡ଼ିକ ପାଇଁ ଭିନ୍ନ ଆଉଟ୍ପୁଟ୍ ଆବଶ୍ୟକ ହୁଏ, ସେତେବେଳେ `replacementMap` ବ୍ୟବହାର କରନ୍ତୁ; ଏହା ଅଧିକ ସମୃଦ୍ଧ
ବିଲ୍ଟ-ଇନ୍ TypeScript ପ୍ରତିସ୍ଥାପନ ଫଙ୍କସନ୍ଗୁଡ଼ିକର ଆଚରଣକୁ ସଂରକ୍ଷଣ କରିବା ସହିତ JSON ନିୟମ ପ୍ୟାକ୍ଗୁଡ଼ିକୁ କେବଳ ଡାଟା ଭିତ୍ତିକ ରଖେ।

## RTK ଫିଲ୍ଟର ପ୍ୟାକ୍ଗୁଡ଼ିକ

RTK ଫିଲ୍ଟରଗୁଡ଼ିକ ଏଠାରେ ରହିଥାଏ:

```txt
open-sse/services/compression/engines/rtk/filters/<filter>.json
```

ପ୍ରତ୍ୟେକ ଫିଲ୍ଟର ଏକ କମାଣ୍ଡ-ଆଉଟପୁଟ୍ ପରିବାରକୁ କିପରି ଚିହ୍ନଟ ଏବଂ ସଙ୍କୋଚିତ କରାଯିବ, ତାହା ବର୍ଣ୍ଣନା କରେ।

```json
{
  "id": "test-vitest",
  "label": "Vitest output",
  "category": "test",
  "priority": 92,
  "match": {
    "outputTypes": ["test-vitest"],
    "commands": ["vitest", "npm test", "npm run test"],
    "patterns": ["\\bFAIL\\b", "\\bPASS\\b", "\\bTest Files\\b"]
  },
  "rules": {
    "stripAnsi": true,
    "replace": [{ "pattern": "\\s+\\[[0-9]+ms\\]", "replacement": "" }],
    "matchOutput": [
      {
        "pattern": "All tests passed",
        "message": "vitest: ok",
        "unless": "FAIL|Error:"
      }
    ],
    "includePatterns": ["FAIL", "Error:", "Test Files", "Tests"],
    "dropPatterns": ["^\\s*$", "Duration\\s+\\d+"],
    "collapsePatterns": ["^\\s+at "],
    "deduplicate": true,
    "truncateLineAt": 240,
    "maxLines": 160,
    "headLines": 24,
    "tailLines": 40,
    "onEmpty": "vitest: ok",
    "filterStderr": false
  },
  "preserve": {
    "errorPatterns": ["FAIL", "Error:", "AssertionError"],
    "summaryPatterns": ["Test Files", "Tests", "Snapshots"]
  },
  "tests": [
    {
      "name": "keeps failing tests",
      "command": "vitest",
      "input": "FAIL test/a.test.ts\\nError: boom\\nTest Files 1 failed",
      "expected": "FAIL test/a.test.ts\\nError: boom\\nTest Files 1 failed"
    }
  ]
}
```

### RTK ଫିଲ୍ଡଗୁଡ଼ିକ

| ଫିଲ୍ଡ                      | ଆବଶ୍ୟକ | ବର୍ଣ୍ଣନା                                                                       |
| -------------------------- | ------ | ------------------------------------------------------------------------------ |
| `id`                       | ହଁ     | ସ୍ଥିର ଫିଲ୍ଟର id                                                                |
| `label`                    | ହଁ     | ଡ୍ୟାସ୍ବୋର୍ଡରେ ପଢ଼ିହେବା ଭଳି ନାମ                                                 |
| `category`                 | ହଁ     | ଫିଲ୍ଟର ପରିବାର: git, test, build, shell, docker, package, infra, cloud, generic |
| `priority`                 | ନା     | ଏକାଧିକ ଫିଲ୍ଟର ମେଳ ଖାଇଲେ ଅଧିକ ପ୍ରାଥମିକତା ଥିବା ଫିଲ୍ଟର ବିଜୟୀ ହୁଏ                  |
| `match.outputTypes`        | ନା     | ଏହି ଫିଲ୍ଟରକୁ ଚୟନ କରୁଥିବା ଡିଟେକ୍ଟର ଆଉଟପୁଟ୍ id                                   |
| `match.commands`           | ନା     | ଏହି ଫିଲ୍ଟରକୁ ଚୟନ କରୁଥିବା କମାଣ୍ଡ ଟୋକନ୍                                          |
| `match.patterns`           | ନା     | ଆଉଟପୁଟ୍ ଟେକ୍ସଟ୍ରୁ ଏହି ଫିଲ୍ଟରକୁ ଚୟନ କରୁଥିବା Regex ପ୍ୟାଟର୍ନ                      |
| `rules.stripAnsi`          | ନା     | Regex ପର୍ଯ୍ୟାୟଗୁଡ଼ିକ ପୂର୍ବରୁ ANSI escape sequence ହଟାଏ                         |
| `rules.replace`            | ନା     | ପ୍ରତ୍ୟେକ ଧାଡ଼ିରେ କ୍ରମାନୁସାରେ ପ୍ରୟୋଗ କରାଯାଉଥିବା Regex ପ୍ରତିସ୍ଥାପନ               |
| `rules.matchOutput`        | ନା     | ଇଚ୍ଛାଧୀନ `unless` ଗାର୍ଡ ସହିତ ସର୍ଟ-ସର୍କିଟ୍ ଆଉଟପୁଟ୍ ନିୟମ                         |
| `rules.includePatterns`    | ନା     | ସଂରକ୍ଷଣକୁ ପ୍ରାଥମିକତା ଦିଆଯିବା ଧାଡ଼ିଗୁଡ଼ିକ                                       |
| `rules.dropPatterns`       | ନା     | ଅନାବଶ୍ୟକ ତଥ୍ୟ ଭାବେ ହଟାଯିବା ଧାଡ଼ିଗୁଡ଼ିକ                                         |
| `rules.collapsePatterns`   | ନା     | ସଙ୍କୁଚିତ କରାଯାଇପାରୁଥିବା ପୁନରାବୃତ୍ତ ମେଳ ଖାଉଥିବା ଧାଡ଼ିଗୁଡ଼ିକ                     |
| `rules.deduplicate`        | ନା     | ଏକାକାର କରାଯାଇଥିବା ନକଲ ଧାଡ଼ିଗୁଡ଼ିକୁ ସଙ୍କୁଚିତ କରେ                                |
| `rules.truncateLineAt`     | ନା     | ପ୍ରତି ଧାଡ଼ି ପାଇଁ Unicode-ନିରାପଦ ଅକ୍ଷର ସୀମା                                     |
| `rules.maxLines`           | ନା     | ଶେଷ ଅଂଶ ସଂରକ୍ଷଣ ପୂର୍ବରୁ ରଖାଯାଉଥିବା ସର୍ବାଧିକ ଧାଡ଼ି ସଂଖ୍ୟା                       |
| `rules.headLines`          | ନା     | କାଟଛାଟ ସମୟରେ ରଖାଯାଉଥିବା ଆରମ୍ଭର ଧାଡ଼ିଗୁଡ଼ିକ                                     |
| `rules.tailLines`          | ନା     | ସାମ୍ପ୍ରତିକ ପ୍ରସଙ୍ଗ ପାଇଁ ରଖାଯାଉଥିବା ଶେଷ ଧାଡ଼ିଗୁଡ଼ିକ                             |
| `rules.onEmpty`            | ନା     | ଫିଲ୍ଟରିଂ ସମସ୍ତ ବିଷୟବସ୍ତୁ ହଟାଇଦେଲେ ବିକଳ୍ପ ସନ୍ଦେଶ                                |
| `rules.filterStderr`       | ନା     | ପରବର୍ତ୍ତୀ ଫିଲ୍ଟରିଂ ପର୍ଯ୍ୟାୟ ପୂର୍ବରୁ ସାଧାରଣ stderr ଉପସର୍ଗଗୁଡ଼ିକୁ ଏକାକାର କରେ     |
| `preserve.errorPatterns`   | ନା     | କାଟଛାଟ ପରେ ମଧ୍ୟ ରହିବା ଉଚିତ ଥିବା ତ୍ରୁଟି ଧାଡ଼ିଗୁଡ଼ିକ                             |
| `preserve.summaryPatterns` | ନା     | କାଟଛାଟ ପରେ ମଧ୍ୟ ରହିବା ଉଚିତ ଥିବା ସାରାଂଶ ଧାଡ଼ିଗୁଡ଼ିକ                             |
| `tests[]`                  | ନା     | RTK verify gate ଦ୍ୱାରା ବ୍ୟବହୃତ ଇନ୍ଲାଇନ୍ ଯାଞ୍ଚ ନମୁନା                            |

RTK ନିମ୍ନ କ୍ରମରେ ଘୋଷଣାମୂଳକ ପର୍ଯ୍ୟାୟଗୁଡ଼ିକୁ ପ୍ରୟୋଗ କରେ: `stripAnsi`, `filterStderr`, `replace`,
`matchOutput`, `dropPatterns`/`includePatterns`, `truncateLineAt`, `headLines`/`tailLines`,
`maxLines`, ଏବଂ `onEmpty`।

କଷ୍ଟମ୍ ଫିଲ୍ଟରଗୁଡ଼ିକୁ ଏଠାରୁ ଲୋଡ୍ କରାଯାଇପାରେ:

1. କେବଳ ଏକ ମେଳ ଖାଉଥିବା `.rtk/trust.json` hash ଉପସ୍ଥିତ ଥିଲେ କିମ୍ବା
   `trustProjectFilters` ସକ୍ଷମ ଥିଲେ ପ୍ରୋଜେକ୍ଟ `.rtk/filters.json` ଫାଇଲ୍ଗୁଡ଼ିକ।
2. ଗ୍ଲୋବାଲ୍ `DATA_DIR/rtk/filters.json`।
3. ବିଲ୍ଟ-ଇନ୍ ଫିଲ୍ଟରଗୁଡ଼ିକ।

ପ୍ରୋଜେକ୍ଟ/ଗ୍ଲୋବାଲ୍ କଷ୍ଟମ୍ ଫାଇଲ୍ଗୁଡ଼ିକରେ ଗୋଟିଏ ଫିଲ୍ଟର ଅବଜେକ୍ଟ କିମ୍ବା ଫିଲ୍ଟର ଅବଜେକ୍ଟଗୁଡ଼ିକର ଏକ ଆରେ ରହିପାରେ। ଅବୈଧ
କଷ୍ଟମ୍ ଫିଲ୍ଟରଗୁଡ଼ିକୁ ଡାୟାଗ୍ନୋଷ୍ଟିକ୍ ସହିତ ଏଡ଼ାଇ ଦିଆଯାଏ; ଅବୈଧ ବିଲ୍ଟ-ଇନ୍ ଫିଲ୍ଟରଗୁଡ଼ିକ ଭ୍ୟାଲିଡେସନ୍କୁ ବିଫଳ କରେ।

ପ୍ରୋଜେକ୍ଟ ଟ୍ରଷ୍ଟ ଫାଇଲ୍:

```json
{
  "filtersSha256": "0123456789abcdef..."
}
```

ପରିବେଶ ଓଭରରାଇଡ୍ `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` କୌଣସି hash ବିନା ପ୍ରୋଜେକ୍ଟ ଫିଲ୍ଟରଗୁଡ଼ିକୁ ବିଶ୍ୱସ୍ତ ମାନେ ଏବଂ ଏହାର
ବ୍ୟବହାରକୁ ନିୟନ୍ତ୍ରିତ ସ୍ଥାନୀୟ ଡେଭଲପମେଣ୍ଟ ମଧ୍ୟରେ ସୀମିତ ରଖିବା ଉଚିତ।

## ସୁରକ୍ଷା ନିୟମଗୁଡ଼ିକ

- ନିୟମଗୁଡ଼ିକୁ ଇଡେମ୍ପୋଟେଣ୍ଟ ରଖନ୍ତୁ: ସମାନ ଫିଲ୍ଟର୍କୁ ଦୁଇଥର ଚଲାଇଲେ ଆଉଟପୁଟ୍ ବିକୃତ ହେବା ଉଚିତ୍ ନୁହେଁ।
- ଯେଉଁଠାରେ ସମ୍ଭବ, ସଠିକ୍ ତ୍ରୁଟି ପାଠ୍ୟ, ଫାଇଲ୍ ପଥ, ଧାଡ଼ି ସଂଖ୍ୟା ଏବଂ କମାଣ୍ଡ ସାରାଂଶଗୁଡ଼ିକୁ ଅପରିବର୍ତ୍ତିତ ରଖନ୍ତୁ।
- କୋଡ୍ ବ୍ଲକ୍, JSON ପେଲୋଡ୍, URL କିମ୍ବା ଗୁପ୍ତ ତଥ୍ୟକୁ ପରିବର୍ତ୍ତନ କରୁଥିବା ନିୟମଗୁଡ଼ିକୁ ଏଡ଼ାନ୍ତୁ।
- ଡିଟେକ୍ଟର୍/ଫିଲ୍ଟର୍ ପରୀକ୍ଷାଗୁଡ଼ିକରେ ନୂତନ କମାଣ୍ଡ ପରିବାର ପାଇଁ ୟୁନିଟ୍ କଭରେଜ୍ ଯୋଡ଼ନ୍ତୁ।
- ପ୍ରତ୍ୟେକ ବିଲ୍ଟ-ଇନ୍ ଫିଲ୍ଟର୍ ଏବଂ ସେୟାର୍ କରାଯାଇଥିବା କଷ୍ଟମ୍ ଫିଲ୍ଟର୍ରେ `tests[]` ନମୁନାଗୁଡ଼ିକ ଯୋଡ଼ନ୍ତୁ।

## ବୈଧତା ଯାଞ୍ଚ

ବ୍ୟବହାର ପୂର୍ବରୁ ନିୟମ ପ୍ୟାକ୍ଗୁଡ଼ିକର ବୈଧତା ଯାଞ୍ଚ କରାଯାଏ। ବିଲ୍ଟ-ଇନ୍ Caveman ପ୍ୟାକ୍ ଏବଂ ବିଲ୍ଟ-ଇନ୍ RTK ଫିଲ୍ଟର୍ଗୁଡ଼ିକ ବୈଧତା ଯାଞ୍ଚ ସମୟରେ ତୁରନ୍ତ ବିଫଳ ହୁଅନ୍ତି, ଯାହାଦ୍ୱାରା ତ୍ରୁଟିପୂର୍ଣ୍ଣ ରିଲିଜ୍ ଆସେଟ୍ଗୁଡ଼ିକୁ ପଠାଇବା ପୂର୍ବରୁ ଚିହ୍ନଟ କରାଯାଏ। ପାର୍ସିଂ କିମ୍ବା ବିଶ୍ୱସନୀୟତା ବୈଧତା ଯାଞ୍ଚ ବିଫଳ ହେଲେ, କଷ୍ଟମ୍ RTK ଫିଲ୍ଟର୍ଗୁଡ଼ିକୁ ଡାଇଗ୍ନୋଷ୍ଟିକ୍ସ ସହିତ ଏଡ଼ାଇ ଦିଆଯାଏ।

କେନ୍ଦ୍ରିତ ବୈଧତା ଯାଞ୍ଚ:

```bash
node --import tsx/esm --test tests/unit/compression/rule-loader.test.ts tests/unit/compression/language-packs.test.ts
node --import tsx/esm --test tests/unit/compression/rtk-verify.test.ts tests/unit/compression/rtk-dsl-pipeline.test.ts
```
