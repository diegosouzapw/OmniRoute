## ପୂର୍ବାବଶ୍ୟକତା

1. `.env.homolog.example`କୁ `.env.homolog`ରେ କପି କରନ୍ତୁ (gitignored — ଏହାକୁ କେବେବି commit କରନ୍ତୁ ନାହିଁ) ଏବଂ ନିମ୍ନଲିଖିତଗୁଡ଼ିକ ପୂରଣ କରନ୍ତୁ:
   - `HOMOLOG_BASE_URL` — ଲକ୍ଷ୍ୟ deploy, ଯଥା `http://192.168.0.15:20128`।
   - `HOMOLOG_ADMIN_PASSWORD` — ସେହି deploy ପାଇଁ dashboard ପରିଚାଳନା password।
   - `HOMOLOG_CRITICAL_PROVIDERS` — ପ୍ରକୃତ smoke chat request ପାଉଥିବା କମା-ପୃଥକ provider prefixଗୁଡ଼ିକ (ଯଥା `openai,anthropic,gemini,codex,grok,glm,deepseek,openrouter`)।
   - `HOMOLOG_API_KEY` — ସାଧାରଣ runରେ ଖାଲି ରଖନ୍ତୁ; suite ନିଜର ଅସ୍ଥାୟୀ key ସୃଷ୍ଟି ଏବଂ revoke କରେ। କେବଳ ଗୋଟିଏ layerକୁ ଅଲଗା ଭାବରେ debug କରିବା ପାଇଁ ଏହାକୁ ସେଟ୍ କରନ୍ତୁ।
2. repoରେ `npm install` ଚଲାନ୍ତୁ (suiteର dependencyଗୁଡ଼ିକ — `httpyac`, `promptfoo`, `playwright-ctrf-json-reporter`, `junit-to-ctrf`, `ctrf` — ସାଧାରଣ devDependencies ଅଟେ)।
3. browser binaryଗୁଡ଼ିକ ପୂର୍ବରୁ ଉପଲବ୍ଧ ନଥିଲେ `npx playwright install` ଚଲାନ୍ତୁ।

## କିପରି ଚଲାଇବେ

```bash
npm run homolog
```

ଯେଉଁ deployର version ସ୍ଥାନୀୟ `package.json` ସହିତ ମେଳ ଖାଉନାହିଁ (ଯଥା ଏବେ ମଧ୍ୟ ପୂର୍ବ patch releaseରେ ଥିବା ଏକ homologation box), ତାହା ବିପକ୍ଷରେ validate କରିବାକୁ ଆଶାକୃତ versionକୁ ସ୍ପଷ୍ଟ ଭାବରେ override କରନ୍ତୁ:

```bash
HOMOLOG_EXPECT_VERSION=3.8.47 npm run homolog
```

କୌଣସି layer ବିଫଳ ହେଲେ runଟି non-zero ସହିତ exit କରେ ଏବଂ ବିଫଳତା ସମୟରେ ମଧ୍ୟ ଏହା ସୃଷ୍ଟି କରିଥିବା ଅସ୍ଥାୟୀ API keyକୁ ସର୍ବଦା revoke କରିବାକୁ ଚେଷ୍ଟା କରେ (`scripts/homolog/run.mjs`ରେ `finally` block)।

## report ପଢ଼ିବା

ସମସ୍ତ output `homolog-report/`ରେ ରହେ (gitignored):

- `summary.md` — stdoutରେ print ହୋଇଥିବା ସମାନ table, ପ୍ରତ୍ୟେକ layer ପାଇଁ ଗୋଟିଏ row (✅/❌ + ବିବରଣୀ)।
- `homolog-ctrf.json` — ଏକୀକୃତ CTRF report (API/SSE, provider-smoke ଏବଂ UI resultଗୁଡ଼ିକର merge) — ଏହା ହେଉଛି release STOP #2 checklist ସହିତ ସଂଲଗ୍ନ କରିବାକୁ ଥିବା artifact।
- `httpyac-junit.xml`, `api-ctrf.json`, `providers-ctrf.json`, `ui-ctrf.json` — ପ୍ରତ୍ୟେକ layerର raw/intermediate report।
- `promptfooconfig.yaml`, `provider-misses.json` — ବର୍ତ୍ତମାନର run ପାଇଁ generate ହୋଇଥିବା promptfoo config ଏବଂ live catalogରୁ ଅନୁପସ୍ଥିତ ଥିବା ଯେକୌଣସି critical provider।

L0 ବିଫଳ ହେଲେ ଏହା ତୁରନ୍ତ abort କରେ (କୌଣସି ଅସ୍ଥାୟୀ key ସୃଷ୍ଟି ହୁଏ ନାହିଁ), କାରଣ version/health mismatchର ଅର୍ଥ ହେଉଛି ପ୍ରତ୍ୟେକ downstream layer ଭୁଲ deployକୁ validate କରିବ।

## UI ବୈଧ ଭାବରେ ପରିବର୍ତ୍ତନ ହେଲେ ପୁନଃ-baseline କରିବା

L4b (route smoke) ଏବଂ L4c (API-key UI flow) snapshot ଦ୍ୱାରା ନୁହେଁ, ପ୍ରକୃତ DOM locator ଦ୍ୱାରା ପରିଚାଳିତ ହୁଏ, ତେଣୁ ଅଧିକାଂଶ ବୈଧ UI ପରିବର୍ତ୍ତନ ପାଇଁ କୌଣସି suite update ଆବଶ୍ୟକ ହୁଏ ନାହିଁ। କୌଣସି ପରିବର୍ତ୍ତନ ଏକ locatorକୁ ଭାଙ୍ଗିଦେଲେ (ଯଥା ଏକ ପୁନଃନାମିତ button label କିମ୍ବା ସ୍ଥାନାନ୍ତରିତ settings page):

1. ବର୍ତ୍ତମାନର source ବିପକ୍ଷରେ locatorକୁ ପୁନଃ-ନିଶ୍ଚିତ କରନ୍ତୁ (ପ୍ରତ୍ୟେକ locator କେଉଁ file/line ବିପକ୍ଷରେ ନିଶ୍ଚିତ କରାଯାଇଥିଲା, specsରେ ତାହା ପୂର୍ବରୁ document କରାଯାଇଛି — ସମାନ pattern ଅନୁସରଣ କରନ୍ତୁ, ଅନୁମାନ କରନ୍ତୁ ନାହିଁ)।
2. `tests/homolog/ui/`ରେ specକୁ update କରନ୍ତୁ।
3. fixକୁ ନିଶ୍ଚିତ କରିବା ପାଇଁ VPS ବିପକ୍ଷରେ `npm run homolog` (କିମ୍ବା କେବଳ ପ୍ରଭାବିତ Playwright spec) ପୁନଃ ଚଲାନ୍ତୁ, ତା'ପରେ commit କରନ୍ତୁ।

ଏହି suiteରେ କୌଣସି visual/pixel baseline ନାହିଁ (F1) — ସେଥିପାଇଁ Roadmap ଦେଖନ୍ତୁ।
