ଏକ pull request ପାଇଁ ସବୁଠାରୁ ଛୋଟ ବିଶ୍ୱସନୀୟ development loop ବାଛିବାକୁ ଏହି ମାର୍ଗଦର୍ଶିକା ବ୍ୟବହାର କରନ୍ତୁ। ଏହା ନିମ୍ନରେ
ଲିଙ୍କ୍ ହୋଇଥିବା କ୍ଷେତ୍ର-ନିର୍ଦ୍ଦିଷ୍ଟ architecture ଏବଂ security ଡକ୍ୟୁମେଣ୍ଟଗୁଡ଼ିକୁ ପ୍ରତିସ୍ଥାପନ କରେ ନାହିଁ; ଏହା ପ୍ରତ୍ୟେକ ସାଧାରଣ
ପରିବର୍ତ୍ତନ ପ୍ରକାରକୁ ତାହାର contract, କେନ୍ଦ୍ରିତ ଯାଞ୍ଚ ଏବଂ CI coverage ସହ ସଂଯୋଗ କରେ।

## ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ଅନୁସରଣ କରୁଥିବା ପଥ

1. **ସମ୍ପାଦନା ପୂର୍ବରୁ base ବାଛନ୍ତୁ।** ସର୍ବୋଚ୍ଚ ସକ୍ରିୟ `release/v*` branch ଖୋଜନ୍ତୁ ଏବଂ
   ତାହାର tip ରୁ branch ସୃଷ୍ଟି କରନ୍ତୁ। `main` କୁ ନୁହେଁ, ସେହି branch କୁ target କରନ୍ତୁ। ଯଦି release freeze ସକ୍ରିୟ ଅଛି, freeze ହୋଇଥିବା
   branch କୁ target କରନ୍ତୁ ନାହିଁ; [Branching & Release Model](BRANCHING_MODEL.md) ରେ ବର୍ଣ୍ଣିତ
   ପରବର୍ତ୍ତୀ ସକ୍ରିୟ cycle ବ୍ୟବହାର କରନ୍ତୁ।
2. **Contract ଗୁଡ଼ିକ ଚିହ୍ନଟ କରନ୍ତୁ।** ପରିବର୍ତ୍ତନ ଦ୍ୱାରା ପ୍ରଭାବିତ ପ୍ରତ୍ୟେକ catalog, schema, generated artifact, public API, କିମ୍ବା user
   interface ଚିହ୍ନଟ କରନ୍ତୁ। ନିମ୍ନର table ସର୍ବନିମ୍ନ ପ୍ରାରମ୍ଭିକ ସେଟ୍ ପ୍ରଦାନ କରେ।
3. **କେନ୍ଦ୍ରିତ test ଲେଖନ୍ତୁ କିମ୍ବା update କରନ୍ତୁ।** `src/`, `open-sse/`, `electron/`, କିମ୍ବା
   `bin/` ରେ production ପରିବର୍ତ୍ତନ ପାଇଁ ସେହି PR ରେ ଏକ automated test ଆବଶ୍ୟକ। ଆଚରଣକୁ ପ୍ରମାଣିତ କରୁଥିବା ସବୁଠାରୁ ଛୋଟ test file ଗୁଡ଼ିକ ଚଲାନ୍ତୁ,
   ତା’ପରେ ତାଲିକାଭୁକ୍ତ କେନ୍ଦ୍ରିତ gate ଗୁଡ଼ିକ ଚଲାନ୍ତୁ।
4. **CI କୁ ବ୍ୟାପକ matrix ଚଲାଇବାକୁ ଦିଅନ୍ତୁ।** ସମ୍ପୂର୍ଣ୍ଣ unit shard, Vitest, coverage ratchet, ଏବଂ
   production build PR ରେ ଚାଲେ। କୌଣସି କେନ୍ଦ୍ରିତ ବିଫଳତା ବ୍ୟାପକ ପ୍ରଭାବ ସୂଚାଇଲେ କିମ୍ବା ପରିବର୍ତ୍ତନଟି ଅନେକ subsystem କୁ
   ବ୍ୟାପିଥିଲେ ମାତ୍ର ସ୍ଥାନୀୟ ଭାବେ ଏକ ବ୍ୟାପକ suite ଚଲାନ୍ତୁ।
5. **Review ପୂର୍ବରୁ ସମନ୍ୱୟ କରନ୍ତୁ।** ସକ୍ରିୟ base fetch କରନ୍ତୁ, ତାହାର ନୂଆ commit ଏବଂ ତାହା ବିପରୀତରେ ଆପଣଙ୍କ diff ଯାଞ୍ଚ କରନ୍ତୁ,
   ତା’ପରେ contributor workflow ଅନୁଯାୟୀ base କୁ rebase କିମ୍ବା merge କରନ୍ତୁ। Generated-file
   ଏବଂ catalog conflict ଗୁଡ଼ିକୁ ସେମାନଙ୍କ source ରୁ ସମାଧାନ କରନ୍ତୁ, ସେଗୁଡ଼ିକୁ ପୁନଃ generate କରନ୍ତୁ, କେନ୍ଦ୍ରିତ loop ପୁନଃ ଚଲାନ୍ତୁ, ଏବଂ
   PR ଏବେ ମଧ୍ୟ ସକ୍ରିୟ release branch କୁ target କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।
6. **ପ୍ରମାଣ ରେକର୍ଡ କରନ୍ତୁ।** PR template ରେ ଚଲାଯାଇଥିବା command, ଯୋଡ଼ା କିମ୍ବା ପରିବର୍ତ୍ତିତ ପ୍ରତ୍ୟେକ test file,
   migration କିମ୍ବା feature flag, ଏବଂ ଏବେ ମଧ୍ୟ pending ଥିବା ଯେକୌଣସି CI-only validation ତାଲିକାଭୁକ୍ତ କରନ୍ତୁ।

## ପରିବର୍ତ୍ତନ ପ୍ରକାର ଅନୁଯାୟୀ ସୁପାରିଶକୃତ ପଥ

ନିମ୍ନର command ଗୁଡ଼ିକ ସର୍ବନିମ୍ନ କେନ୍ଦ୍ରିତ ଯାଞ୍ଚ; ଆପଣ ପରିବର୍ତ୍ତନ କରିଥିବା ଆଚରଣକୁ ସିଧାସଳଖ cover କରୁଥିବା
test ଛାଡ଼ିଦେବାର ଅନୁମତି ନୁହେଁ।

### Provider

**Contract ଗୁଡ଼ିକ**

- `src/shared/constants/providers/` ରେ Provider ସଂଜ୍ଞା ଏବଂ
  `src/shared/constants/providers.ts` ରେ ତାହାର composition।
- `open-sse/config/providerRegistry.ts` କିମ୍ବା ଏହାର extracted registry file ଗୁଡ଼ିକରେ model ଏବଂ capability।
- Executor/translator selection, OAuth କିମ୍ବା API-key configuration, dashboard asset, ଏବଂ ପ୍ରଯୋଜ୍ୟ ହେଲେ generated
  provider reference।
- Public credential ଗୁଡ଼ିକ `resolvePublicCred()` ବ୍ୟବହାର କରିବା ଆବଶ୍ୟକ; error response ଗୁଡ଼ିକ shared sanitized
  error helper ବ୍ୟବହାର କରିବା ଆବଶ୍ୟକ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` ରେ compile ହୋଇନାହିଁ) ଏବଂ
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ଦେଖନ୍ତୁ।

**କେନ୍ଦ୍ରିତ loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ପରିବର୍ତ୍ତିତ ହେଲେ; generated diff commit କରନ୍ତୁ
npm run lint
```

ପ୍ରଭାବିତ ପ୍ରତ୍ୟେକ request family ମଧ୍ୟ test କରନ୍ତୁ: chat, Responses, images, embeddings, audio, କିମ୍ବା video।
Generated catalog ଏବଂ golden diff ଗୁଡ଼ିକୁ contract ପରିବର୍ତ୍ତନ ଭାବେ review କରନ୍ତୁ; ସେଗୁଡ଼ିକୁ ଅନ୍ଧ ଭାବେ ଗ୍ରହଣ କରନ୍ତୁ ନାହିଁ।

### Routing

**Contract ଗୁଡ଼ିକ**

- `src/shared/constants/routingStrategies.ts` ରେ public strategy value ଏବଂ UI metadata।
- `open-sse/services/combo.ts` ଏବଂ `open-sse/services/combo/` ଅଧୀନରେ dispatch ଏବଂ ordering।
- Combo schema, persistence, resilience state, model capability, ଏବଂ API/UI control।
- ଆଚରଣ ପରିବର୍ତ୍ତିତ ହେଲେ [Auto-Combo Engine](../routing/AUTO-COMBO.md) ଏବଂ resilience documentation।

**କେନ୍ଦ୍ରିତ loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy କିମ୍ବା dispatch ପରିବର୍ତ୍ତନ
npm run check:known-symbols      # strategy registration ପରିବର୍ତ୍ତନ
npm run lint
```

ସ୍ଥାନୀୟ ଭାବେ deterministic mocked-upstream test ବ୍ୟବହାର କରନ୍ତୁ। Live combo smoke test ପାଇଁ credential ଆବଶ୍ୟକ ଏବଂ ସେଗୁଡ଼ିକ
manual, CI ର ବିକଳ୍ପ ନୁହେଁ।

### UI / UX

**Contract ଗୁଡ଼ିକ**

- `src/app/` ଏବଂ `src/shared/components/` ଅଧୀନରେ Next.js route/page ଏବଂ shared component boundary।
- API response shape, loading/empty/error state, keyboard ଏବଂ screen-reader ଆଚରଣ,
  responsive layout, theming, ଏବଂ locale expansion।
- `src/i18n/messages/en.json` ରେ English UI source string; ନୂତନ user-facing copy hard-code କରନ୍ତୁ ନାହିଁ।

**କେନ୍ଦ୍ରିତ loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction କିମ୍ବା visual ପରିବର୍ତ୍ତନ ପାଇଁ app ଚଲାନ୍ତୁ ଏବଂ ଉଭୟ narrow ଏବଂ wide viewport ଯାଞ୍ଚ କରନ୍ତୁ। CI
production build ଏବଂ ବ୍ୟାପକ suite ଚଲାଏ; visual ଆଚରଣ ପାଇଁ ତଥାପି ପରିବର୍ତ୍ତନ ଅନୁଯାୟୀ ଏକ କେନ୍ଦ୍ରିତ component, Playwright,
କିମ୍ବା ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା manual ଯାଞ୍ଚ ଆବଶ୍ୟକ।

### i18n

**Contract ଗୁଡ଼ିକ**

- `src/i18n/messages/en.json` ହେଉଛି UI source; `config/i18n.json` ହେଉଛି locale source।
- CLI catalog ଗୁଡ଼ିକ `bin/cli/locales/` ଅଧୀନରେ ପୃଥକ ଭାବେ ରହିଛି।
- ICU placeholder ଏବଂ tag ଗୁଡ଼ିକୁ ଠିକ୍ ସେହିପରି ସଂରକ୍ଷଣ କରନ୍ତୁ। Product/provider/model ନାମ,
  protocol ଏବଂ header ନାମ, command, code/JSON identifier, URL, environment variable, କିମ୍ବା
  `OmniRoute`, `OAuth`, `MCP`, ଏବଂ `A2A` ପରି protected term ଅନୁବାଦ କରନ୍ତୁ ନାହିଁ। ବର୍ତ୍ତମାନର source list ହେଉଛି
  `scripts/i18n/glossary/protected-terms.json`।

**କେନ୍ଦ୍ରିତ loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI string/catalog ପରିବର୍ତ୍ତିତ ହେଲେ
npm run lint
```

ଏହା ବର୍ତ୍ତମାନର system ପାଇଁ ମାର୍ଗଦର୍ଶନ, ଏହାର tooling କିମ୍ବା key model ବିସ୍ତାର କରିବାକୁ ଆମନ୍ତ୍ରଣ ନୁହେଁ।
Replacement system design ହେଉଥିବା ସମୟରେ i18n patch ଗୁଡ଼ିକୁ ସୀମିତ ଏବଂ ନିର୍ଦ୍ଦିଷ୍ଟ ରଖନ୍ତୁ। Task ରେ generated translation ସ୍ପଷ୍ଟ ଭାବେ ଆବଶ୍ୟକ ନହେଲେ ଏବଂ
ଆପଣ resulting diff review କରିନଥିଲେ, external service call କରୁଥିବା translation
command ଚଲାନ୍ତୁ ନାହିଁ।

### CLI

**Contract ଗୁଡ଼ିକ**

- `bin/cli/` ରେ ଥିବା ସାର୍ବଜନୀନ କମାଣ୍ଡ ଏବଂ ଫ୍ଲାଗ୍ଗୁଡ଼ିକ, ଜେନେରେଟ୍ ହୋଇଥିବା API କମାଣ୍ଡଗୁଡ଼ିକ, ଏକ୍ଜିଟ୍ କୋଡ୍, stdout/stderr ଏବଂ
  JSON ଆଉଟ୍ପୁଟ୍ ଆକୃତି, କନଫିଗ୍/ଏନ୍ଭାଇରନ୍ମେଣ୍ଟ ଆଚରଣ, ଏବଂ ପ୍ୟାକେଜ୍ ହୋଇଥିବା ଫାଇଲ୍ଗୁଡ଼ିକ।
- CLI ବ୍ୟବହାରକାରୀମୁଖୀ ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକ ନିଶ୍ଚିତ ଭାବେ CLI i18n ସ୍ତର ବ୍ୟବହାର କରିବା ଉଚିତ ଏବଂ `en`/`pt-BR` କ୍ୟାଟାଲଗ୍ଗୁଡ଼ିକୁ ସମନ୍ୱିତ ରଖିବା ଉଚିତ।
- ସମର୍ଥିତ ରନ୍ଟାଇମ୍ ଭାବେ Node ଏବଂ ପ୍ରକାଶିତ ବାଇନାରି ଚୁକ୍ତିକୁ ସଂରକ୍ଷିତ ରଖନ୍ତୁ।

**କେନ୍ଦ୍ରିତ ଲୁପ୍**

```bash

npm run build:cli             # ଜେନେରେଟ୍/ବଣ୍ଡଲ୍ ହୋଇଥିବା CLI ପରିବର୍ତ୍ତନଗୁଡ଼ିକ
npm run check:pack-policy     # ପ୍ୟାକେଜ୍ ପୃଷ୍ଠଭାଗର ପରିବର୍ତ୍ତନଗୁଡ଼ିକ
npm run lint
```

ଯେତେବେଳେ ଆଚରଣ ପାର୍ସିଂ, ଫାଇଲ୍ କିମ୍ବା ଏକ୍ଜିଟ୍ ସ୍ଥିତି ଉପରେ ନିର୍ଭର କରେ, ଏକ ଅସ୍ଥାୟୀ ଡାଟା ଡିରେକ୍ଟୋରୀରେ ସଠିକ୍ କମାଣ୍ଡ ବ୍ୟବହାର କରନ୍ତୁ। CI ବ୍ୟାପକ ପ୍ୟାକେଜ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟ ଏବଂ ଇକୋସିଷ୍ଟମ୍ ଯାଞ୍ଚଗୁଡ଼ିକ କରେ।

### ଡାଟାବେସ୍

**ଚୁକ୍ତିଗୁଡ଼ିକ**

- `src/lib/db/` ଅଧୀନରେ ଥିବା ଡୋମେନ୍ ମଡ୍ୟୁଲ୍ଗୁଡ଼ିକ; ନିର୍ଦ୍ଦିଷ୍ଟ ମଡ୍ୟୁଲ୍ଗୁଡ଼ିକୁ ସିଧାସଳଖ ଇମ୍ପୋର୍ଟ କରନ୍ତୁ (ପୁରୁଣା `localDb.ts` ପୁନଃ-ଏକ୍ସପୋର୍ଟ ସ୍ତରକୁ ହଟାଇ ଦିଆଯାଇଛି)।
- `src/lib/db/migrations/` ଅଧୀନରେ ନମ୍ବରଯୁକ୍ତ, ଆଇଡେମ୍ପୋଟେଣ୍ଟ SQL ମାଇଗ୍ରେସନ୍ଗୁଡ଼ିକ, ଟ୍ରାଞ୍ଜାକ୍ସନ୍ ସୁରକ୍ଷା, ଅପ୍ଗ୍ରେଡ୍
  ଆଚରଣ, ଇଣ୍ଡେକ୍ସଗୁଡ଼ିକ, ଏବଂ ସ୍କିମା ଦ୍ୱାରା ପ୍ରଭାବିତ ପ୍ରତ୍ୟେକ କଲର୍।
- ରୁଟ୍ ଏବଂ ହ୍ୟାଣ୍ଡଲର୍ଗୁଡ଼ିକ କେବେ ମଧ୍ୟ ସିଧାସଳଖ ର’ SQL ଜାରି କରନ୍ତି ନାହିଁ।

**କେନ୍ଦ୍ରିତ ଲୁପ୍**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

ଏକ ମାଇଗ୍ରେସନ୍ ଯୋଡ଼ିବା ସମୟରେ ଉଭୟ ଏକ ନୂତନ ଡାଟାବେସ୍ ଏବଂ ପୂର୍ବ ସ୍କିମାରୁ ଅପ୍ଗ୍ରେଡ୍ ପରୀକ୍ଷା କରନ୍ତୁ। ଡାଟାବେସ୍ ପରୀକ୍ଷାଗୁଡ଼ିକ
ନିଶ୍ଚିତ ଭାବେ ହ୍ୟାଣ୍ଡଲ୍ଗୁଡ଼ିକୁ ବନ୍ଦ କରିବା ଏବଂ କ୍ଲିନ୍ଅପ୍ ସମୟରେ `resetDbInstance()` କଲ୍ କରିବା ଉଚିତ। କେବଳ
ସର୍ବୋତ୍ତମ-ପ୍ରୟାସ ଭିତ୍ତିକ Bun ଆଡାପ୍ଟର୍ ପଥ ପରିବର୍ତ୍ତିତ ହେଲେ `npm run test:bun:db` ଚଲାନ୍ତୁ; Node ହିଁ ପ୍ରାମାଣିକ ରହିବ।

### ବିଲ୍ଡ / ଡିପ୍ଲୟ

**ଚୁକ୍ତିଗୁଡ଼ିକ**

- ରୁଟ୍ ଏବଂ ୱର୍କସ୍ପେସ୍ ମାନିଫେଷ୍ଟ/ଲକ୍ଫାଇଲ୍, `scripts/build/`, Next.js ସ୍ୱତନ୍ତ୍ର ଆସେମ୍ବ୍ଲି, `dist/`
  ପ୍ୟାକେଜ୍ ବିଷୟବସ୍ତୁ, Electron ପ୍ଲାଟଫର୍ମ ମେଟାଡାଟା, CI ୱର୍କଫ୍ଲୋ, ଏବଂ ଡିପ୍ଲୟମେଣ୍ଟ ସେଣ୍ଟିନେଲ୍ଗୁଡ଼ିକ।
- ସମର୍ଥିତ Node ରେଞ୍ଜ ଏବଂ `CLAUDE.md` ରେ ଅନୁମୋଦିତ-ତାଲିକାଭୁକ୍ତ Bun ବ୍ୟବହାର ଅକ୍ଷୁଣ୍ଣ ରହିବା ଆବଶ୍ୟକ।
- ବିଲ୍ଡ ଆର୍ଟିଫ୍ୟାକ୍ଟଗୁଡ଼ିକ ଟ୍ରାକ୍ ହୋଇନଥିବା ଅବସ୍ଥାରେ ରହିବ; ଡିପେଣ୍ଡେନ୍ସି, ଲାଇସେନ୍ସ, ୱର୍କଫ୍ଲୋ ଏବଂ ପ୍ୟାକେଜ୍ ନୀତିଗୁଡ଼ିକ ଲାଗୁ ହୁଏ।

**କେନ୍ଦ୍ରିତ ଲୁପ୍**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # ଡିପେଣ୍ଡେନ୍ସି କିମ୍ବା ଲକ୍ଫାଇଲ୍ ପରିବର୍ତ୍ତନଗୁଡ଼ିକ
npm run check:pack-policy      # ପ୍ରକାଶିତ ପ୍ୟାକେଜ୍ ପୃଷ୍ଠଭାଗର ପରିବର୍ତ୍ତନଗୁଡ଼ିକ
npm run lint
```

ପରିବର୍ତ୍ତନଟି କମ୍ପାଇଲେସନ୍, ସ୍ୱତନ୍ତ୍ର ଆସେମ୍ବ୍ଲି, ଆସେଟ୍ କିମ୍ବା ରନ୍ଟାଇମ୍ ବଣ୍ଡଲିଂକୁ ପ୍ରଭାବିତ କଲେ ମାତ୍ର ସ୍ଥାନୀୟ ଭାବେ `npm run build` ବ୍ୟବହାର କରନ୍ତୁ। କେବଳ ରିଲିଜ୍/ଡିପ୍ଲୟ ବୈଧତା ଯାଞ୍ଚ ପାଇଁ `npm run build:release` ବ୍ୟବହାର କରନ୍ତୁ। CI ର ବିଲ୍ଡ ହେଉଛି ଅନ୍ତିମ କ୍ରସ୍-ପ୍ଲାଟଫର୍ମ ସଙ୍କେତ; ପ୍ଲାଟଫର୍ମ-ନିର୍ଦ୍ଦିଷ୍ଟ Electron ପରିବର୍ତ୍ତନଗୁଡ଼ିକ ପାଇଁ ସମ୍ବନ୍ଧିତ କେନ୍ଦ୍ରିତ ବିଲ୍ଡ କିମ୍ବା ସ୍ମୋକ୍ ପ୍ରମାଣ ଆବଶ୍ୟକ।

## ସମନ୍ୱୟ ଯାଞ୍ଚତାଲିକା

ସମୀକ୍ଷା ଅନୁରୋଧ କରିବା ପୂର୍ବରୁ:

- PR ବେସ୍ ଏବେ ମଧ୍ୟ ସର୍ବୋଚ୍ଚ ସକ୍ରିୟ `release/v*` ଶାଖା କି ନାହିଁ ନିଶ୍ଚିତ କରନ୍ତୁ।
- ସେହି ବେସ୍କୁ ଫେଚ୍ କରନ୍ତୁ ଏବଂ ଆପଣ ଶାଖା ସୃଷ୍ଟି କରିବା ପରେ ଯୋଡ଼ାଯାଇଥିବା କମିଟ୍ଗୁଡ଼ିକୁ ସମୀକ୍ଷା କରନ୍ତୁ।
- ଅନିଚ୍ଛାକୃତ କିମ୍ବା ଜେନେରେଟ୍ ହୋଇଥିବା ଅଦରକାରୀ ପରିବର୍ତ୍ତନ ପାଇଁ `git diff <active-base>...HEAD` ସମୀକ୍ଷା କରନ୍ତୁ।
- ଉତ୍ସକୁ ଅଦ୍ୟତନ କରି ଏବଂ ଆଉଟ୍ପୁଟ୍କୁ ପୁନଃଜେନେରେଟ୍ କରି କ୍ୟାଟାଲଗ୍ ଏବଂ ଜେନେରେଟ୍ ହୋଇଥିବା ଡକ୍ୟୁମେଣ୍ଟର ଦ୍ୱନ୍ଦ୍ୱ ସମାଧାନ କରନ୍ତୁ।
