ଏକ pull request ପାଇଁ ସବୁଠାରୁ ଛୋଟ ବିଶ୍ୱସନୀୟ development loop ବାଛିବାକୁ ଏହି ମାର୍ଗଦର୍ଶିକା ବ୍ୟବହାର କରନ୍ତୁ। ଏହା ନିମ୍ନରେ ଲିଙ୍କ୍ ହୋଇଥିବା
କ୍ଷେତ୍ର-ନିର୍ଦ୍ଦିଷ୍ଟ architecture ଏବଂ security ଦଲିଲଗୁଡ଼ିକୁ ପ୍ରତିସ୍ଥାପନ କରେ ନାହିଁ; ଏହା ପ୍ରତ୍ୟେକ ସାଧାରଣ
ପରିବର୍ତ୍ତନ ପ୍ରକାରକୁ ତାହାର contract, କେନ୍ଦ୍ରିତ ଯାଞ୍ଚ ଏବଂ CI coverage ସହିତ ସଂଯୋଗ କରେ।

## ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ଅନୁସରଣ କରୁଥିବା ପଥ

1. **ସମ୍ପାଦନା ପୂର୍ବରୁ base ବାଛନ୍ତୁ।** ସର୍ବୋଚ୍ଚ ସକ୍ରିୟ `release/v*` branch ଖୋଜନ୍ତୁ ଏବଂ
   ତାହାର tip ରୁ branch କରନ୍ତୁ। `main` ନୁହେଁ, ସେହି branch କୁ target କରନ୍ତୁ। ଯଦି କୌଣସି release freeze ସକ୍ରିୟ ଅଛି, ତେବେ freeze ହୋଇଥିବା
   branch କୁ target କରନ୍ତୁ ନାହିଁ; [Branching & Release Model](BRANCHING_MODEL.md) ରେ ବର୍ଣ୍ଣିତ
   ପରବର୍ତ୍ତୀ ସକ୍ରିୟ cycle ବ୍ୟବହାର କରନ୍ତୁ।
2. **Contract ଗୁଡ଼ିକର ନାମ ଦିଅନ୍ତୁ।** ପରିବର୍ତ୍ତନଟି ପ୍ରଭାବିତ କରୁଥିବା ପ୍ରତ୍ୟେକ catalog, schema, generated artifact, public API, କିମ୍ବା user
   interface ଚିହ୍ନଟ କରନ୍ତୁ। ନିମ୍ନର table ସର୍ବନିମ୍ନ ପ୍ରାରମ୍ଭିକ ସେଟ୍ ଦିଏ।
3. **କେନ୍ଦ୍ରିତ test ଲେଖନ୍ତୁ କିମ୍ବା update କରନ୍ତୁ।** `src/`, `open-sse/`, `electron/`, କିମ୍ବା
   `bin/` ର production ପରିବର୍ତ୍ତନଗୁଡ଼ିକ ପାଇଁ ସେହି PR ରେ ଏକ automated test ଆବଶ୍ୟକ। behavior ପ୍ରମାଣ କରୁଥିବା ସବୁଠାରୁ ଛୋଟ test file ଗୁଡ଼ିକ ଚଲାନ୍ତୁ,
   ତାପରେ ତାଲିକାଭୁକ୍ତ କେନ୍ଦ୍ରିତ gate ଗୁଡ଼ିକ ଚଲାନ୍ତୁ।
4. **CI କୁ ବ୍ୟାପକ matrix ଚଲାଇବାକୁ ଦିଅନ୍ତୁ।** ସମ୍ପୂର୍ଣ୍ଣ unit shard, Vitest, coverage ratchet, ଏବଂ
   production build PR ଉପରେ ଚାଲେ। କେବଳ ଯେତେବେଳେ କୌଣସି କେନ୍ଦ୍ରିତ ବିଫଳତା ଅଧିକ ବ୍ୟାପକ ପ୍ରଭାବ ସୂଚିତ କରେ
   କିମ୍ବା ପରିବର୍ତ୍ତନଟି ଅନେକ subsystem କୁ ବ୍ୟାପିଥାଏ, ସେତେବେଳେ ସ୍ଥାନୀୟ ଭାବେ ଏକ ବ୍ୟାପକ suite ଚଲାନ୍ତୁ।
5. **Review ପୂର୍ବରୁ ସମନ୍ୱୟ କରନ୍ତୁ।** ସକ୍ରିୟ base କୁ fetch କରନ୍ତୁ, ତାହାର ନୂତନ commit ଏବଂ ତାହା ବିପରୀତରେ ଆପଣଙ୍କ diff ଯାଞ୍ଚ କରନ୍ତୁ,
   ତାପରେ contributor workflow ଅନୁଯାୟୀ base କୁ rebase କିମ୍ବା merge କରନ୍ତୁ। generated-file
   ଏବଂ catalog conflict ଗୁଡ଼ିକୁ ସେମାନଙ୍କ source ରୁ ସମାଧାନ କରନ୍ତୁ, ସେଗୁଡ଼ିକୁ ପୁନଃ generate କରନ୍ତୁ, କେନ୍ଦ୍ରିତ loop ପୁନଃ ଚଲାନ୍ତୁ, ଏବଂ
   PR ଏବେ ମଧ୍ୟ ସକ୍ରିୟ release branch କୁ target କରୁଛି ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।
6. **ପ୍ରମାଣ ଲିପିବଦ୍ଧ କରନ୍ତୁ।** PR template ରେ ଚଲାଯାଇଥିବା command, ଯୋଡ଼ାଯାଇଥିବା କିମ୍ବା ପରିବର୍ତ୍ତିତ ପ୍ରତ୍ୟେକ test file,
   migration କିମ୍ବା feature flag, ଏବଂ ଏବେ ମଧ୍ୟ ବାକିଥିବା ଯେକୌଣସି CI-only validation ତାଲିକାଭୁକ୍ତ କରନ୍ତୁ।

## ପରିବର୍ତ୍ତନ ପ୍ରକାର ଅନୁଯାୟୀ Golden path

ନିମ୍ନର command ଗୁଡ଼ିକ ସର୍ବନିମ୍ନ କେନ୍ଦ୍ରିତ ଯାଞ୍ଚ ଅଟେ, ଆପଣ ପରିବର୍ତ୍ତନ କରିଥିବା
behavior କୁ ସିଧାସଳଖ cover କରୁଥିବା test ଛାଡ଼ିବାର ଅନୁମତି ନୁହେଁ।

### Provider

**Contract ଗୁଡ଼ିକ**

- `src/shared/constants/providers/` ରେ Provider definition ଏବଂ
  `src/shared/constants/providers.ts` ରେ ତାହାର composition।
- `open-sse/config/providerRegistry.ts` କିମ୍ବା ଏହାର extracted registry file ଗୁଡ଼ିକରେ model ଏବଂ capability।
- ପ୍ରଯୋଜ୍ୟ ହେଲେ executor/translator selection, OAuth କିମ୍ବା API-key configuration, dashboard asset, ଏବଂ generated
  provider reference।
- Public credential ଗୁଡ଼ିକ `resolvePublicCred()` ବ୍ୟବହାର କରିବା ଆବଶ୍ୟକ; error response ଗୁଡ଼ିକ shared sanitized
  error helper ବ୍ୟବହାର କରିବା ଆବଶ୍ୟକ। `docs/security/PUBLIC_CREDS.md` (git; `/docs` ଭିତରେ compile ହୋଇନାହିଁ) ଏବଂ
  [Error Sanitization](../security/ERROR_SANITIZATION.md) ଦେଖନ୍ତୁ।

**କେନ୍ଦ୍ରିତ loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # catalog ପରିବର୍ତ୍ତନ ହେଲେ; generated diff କୁ commit କରନ୍ତୁ
npm run lint
```

ପ୍ରଭାବିତ ପ୍ରତ୍ୟେକ request family ମଧ୍ୟ test କରନ୍ତୁ: chat, Responses, images, embeddings, audio, କିମ୍ବା video।
Generated catalog ଏବଂ golden diff ଗୁଡ଼ିକୁ contract ପରିବର୍ତ୍ତନ ଭାବେ review କରନ୍ତୁ; ସେଗୁଡ଼ିକୁ ଅନ୍ଧ ଭାବରେ ଗ୍ରହଣ କରନ୍ତୁ ନାହିଁ।

### Routing

**Contract ଗୁଡ଼ିକ**

- `src/shared/constants/routingStrategies.ts` ରେ public strategy value ଏବଂ UI metadata।
- `open-sse/services/combo.ts` ଏବଂ `open-sse/services/combo/` ଅଧୀନରେ dispatch ଏବଂ ordering।
- Combo schema, persistence, resilience state, model capability, ଏବଂ API/UI control।
- Behavior ପରିବର୍ତ୍ତନ ହେଲେ [Auto-Combo Engine](../routing/AUTO-COMBO.md) ଏବଂ resilience documentation।

**କେନ୍ଦ୍ରିତ loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy କିମ୍ବା dispatch ପରିବର୍ତ୍ତନ
npm run check:known-symbols      # strategy registration ପରିବର୍ତ୍ତନ
npm run lint
```

ସ୍ଥାନୀୟ ଭାବେ deterministic mocked-upstream test ବ୍ୟବହାର କରନ୍ତୁ। Live combo smoke ପାଇଁ credential ଆବଶ୍ୟକ ଏବଂ ସେଗୁଡ଼ିକ
manual, CI ର ବିକଳ୍ପ ନୁହେଁ।

### UI / UX

**Contract ଗୁଡ଼ିକ**

- `src/app/` ଏବଂ `src/shared/components/` ଅଧୀନରେ Next.js route/page ଏବଂ shared component boundary।
- API response shape, loading/empty/error state, keyboard ଏବଂ screen-reader behavior,
  responsive layout, theming, ଏବଂ locale expansion।
- `src/i18n/messages/en.json` ରେ English UI source string; ନୂତନ user-facing copy କୁ hard-code କରନ୍ତୁ ନାହିଁ।

**କେନ୍ଦ୍ରିତ loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction କିମ୍ବା visual ପରିବର୍ତ୍ତନ ପାଇଁ app ଚଲାନ୍ତୁ ଏବଂ narrow ଓ wide ଉଭୟ viewport ଯାଞ୍ଚ କରନ୍ତୁ। CI
production build ଏବଂ ବ୍ୟାପକ suite ଚଲାଏ; visual behavior ପାଇଁ ଏବେ ମଧ୍ୟ ପରିବର୍ତ୍ତନ ଉପଯୁକ୍ତ ଏକ କେନ୍ଦ୍ରିତ component, Playwright,
କିମ୍ବା ଲିପିବଦ୍ଧ manual ଯାଞ୍ଚ ଆବଶ୍ୟକ।

### i18n

**Contract ଗୁଡ଼ିକ**

- `src/i18n/messages/en.json` ହେଉଛି UI source; `config/i18n.json` ହେଉଛି locale source।
- CLI catalog ଗୁଡ଼ିକ `bin/cli/locales/` ଅଧୀନରେ ପୃଥକ ଭାବେ ରହିଛି।
- ICU placeholder ଏବଂ tag ଗୁଡ଼ିକୁ ଠିକ୍ ସେହିପରି ସଂରକ୍ଷଣ କରନ୍ତୁ। Product/provider/model ନାମ,
  protocol ଏବଂ header ନାମ, command, code/JSON identifier, URL, environment variable, କିମ୍ବା
  `OmniRoute`, `OAuth`, `MCP`, ଏବଂ `A2A` ପରି ସଂରକ୍ଷିତ term ଗୁଡ଼ିକୁ ଅନୁବାଦ କରନ୍ତୁ ନାହିଁ। ବର୍ତ୍ତମାନର source list ହେଉଛି
  `scripts/i18n/glossary/protected-terms.json`।

**କେନ୍ଦ୍ରିତ loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # CLI string/catalog ପରିବର୍ତ୍ତନ ହେଲେ
npm run lint
```

ଏହା ବିଦ୍ୟମାନ system ପାଇଁ ମାର୍ଗଦର୍ଶନ, ଏହାର tooling କିମ୍ବା key model ବିସ୍ତାର କରିବାକୁ ଆମନ୍ତ୍ରଣ ନୁହେଁ।

## ସ୍ଥାନୀୟ ପ୍ରାର୍ଥୀ ଲୁପ୍

ସୋର୍ସ ପରୀକ୍ଷାଗୁଡ଼ିକ ପ୍ୟାକେଜ୍ ହୋଇଥିବା ଆର୍ଟିଫ୍ୟାକ୍ଟ ବୁଟ୍ ହୁଏ ବୋଲି ପ୍ରମାଣ କରିପାରେ ନାହିଁ: ପ୍ୟାକେଜିଂ ତାଲିକା, ବାଦ୍ ଦିଆଯାଇଥିବା ଡିପେଣ୍ଡେନ୍ସି,
ଏବଂ ନେଟିଭ୍ ବାଇନେରୀଗୁଡ଼ିକ କେବଳ tarball ଇନଷ୍ଟଲ୍ ଓ ଆରମ୍ଭ ହେବା ପରେ ବିଫଳ ହୁଅନ୍ତି। `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ହେଉଛି RFC #8084ର build-once / validate / promote ପ୍ରବାହର ସ୍ଥାନୀୟ ପାର୍ଶ୍ୱ: ଏହା ଗୋଟିଏ ପ୍ରାର୍ଥୀ ନିର୍ମାଣ କରେ, ସେହି ସଠିକ୍ ଆର୍ଟିଫ୍ୟାକ୍ଟକୁ ବୈଧ କରେ, ଡିରେକ୍ଟୋରୀ
ନାମ ପରିବର୍ତ୍ତନ ମାଧ୍ୟମରେ ତାହାକୁ ପ୍ରମୋଟ୍ କରେ, ଏବଂ ପ୍ରମୋଟ୍ ହୋଇଥିବା ସ୍ଲଟ୍ର ସ୍ୱାସ୍ଥ୍ୟ ଯାଞ୍ଚ ବିଫଳ ହେଲେ ତାହାକୁ ରୋଲ୍ବ୍ୟାକ୍ କରେ।

```bash
npm run dev:candidate -- run --dry-run --json  # ଯୋଜନାଟି ପ୍ରିଣ୍ଟ୍ କରନ୍ତୁ, କିଛି ପରିବର୍ତ୍ତନ କରନ୍ତୁ ନାହିଁ
npm run dev:candidate -- run                   # ନିର୍ମାଣ + ବୈଧତା ଯାଞ୍ଚ + ପ୍ରମୋଟ୍, ସ୍ୱୟଂଚାଳିତ ରୋଲ୍ବ୍ୟାକ୍
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ ମଧ୍ୟରେ ଇନଷ୍ଟଲ୍
npm run dev:candidate -- validate --id <id>    # ଏକ ଖାଲି ପୋର୍ଟରେ ବୁଟ୍, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # current ଏବଂ previousକୁ ଅଦଳବଦଳ କରନ୍ତୁ
npm run dev:candidate -- run --from-tarball <file.tgz>  # ଅନ୍ୟତ୍ର (CI) ନିର୍ମିତ tarballକୁ ପୁନଃବ୍ୟବହାର କରନ୍ତୁ
```

- **ଥରେ ମାତ୍ର ନିର୍ମାଣ କରନ୍ତୁ।** `build` ସାମ୍ପ୍ରତିକ ଟ୍ରିକୁ ପ୍ୟାକ୍ କରେ (ଏଥିପାଇଁ `dist/server.js` ଆବଶ୍ୟକ, ତେଣୁ ପ୍ରଥମେ
  `npm run build:release` ଚଲାନ୍ତୁ) କିମ୍ବା `--from-tarball`କୁ କପି କରେ, ତା’ପରେ tarballକୁ ଏକ
  ପୃଥକ npm prefixରେ ଇନଷ୍ଟଲ୍ କରେ, କାରଣ tarballରେ କୌଣସି `node_modules` ନଥାଏ। idଟି ହେଉଛି ସଂକ୍ଷିପ୍ତ `HEAD`
  sha (ଟ୍ରିରେ ସ୍ଥାନୀୟ ପରିବର୍ତ୍ତନ ଥିଲେ `-dirty`) କିମ୍ବା ଏକ tarball ପାଇଁ `tgz-<sha256>`। ପୂର୍ବରୁ
  ନିର୍ମିତ ଏକ ସ୍ୱଚ୍ଛ idକୁ ପୁନଃନିର୍ମାଣ କରିବା ପରିବର୍ତ୍ତେ ପୁନଃବ୍ୟବହାର କରାଯାଏ; ଏହାକୁ ପୁନଃନିର୍ମାଣ କରିବାକୁ `--force` ପାସ୍ କରନ୍ତୁ।
- **ସୋର୍ସକୁ ନୁହେଁ, ପ୍ୟାକେଜ୍କୁ ବୈଧ କରନ୍ତୁ।** `validate` ଇନଷ୍ଟଲ୍ ହୋଇଥିବା CLIକୁ
  (`serve --port <free port>`) ଏକ ନୂତନ `DATA_DIR=<candidate>/data`, ନକଲି ସିକ୍ରେଟ୍ ସହିତ ଆରମ୍ଭ କରେ, ଏବଂ ଅପରେଟରଙ୍କ
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` ଓ `INITIAL_PASSWORD`କୁ ଏନ୍ଭାଇରନ୍ମେଣ୍ଟରୁ ହଟାଇଦିଏ,
  ଯାହାଦ୍ୱାରା ଏହା ଏକ ନୂତନ ଇନଷ୍ଟଲେସନ୍ର କି-ବିହୀନ ଲୁପ୍ବ୍ୟାକ୍ ଅବସ୍ଥାକୁ ଯାଞ୍ଚ କରେ। ଏହା
  `GET /api/health`ରୁ 200 ଫେରିବା ପର୍ଯ୍ୟନ୍ତ ଅପେକ୍ଷା କରେ, `GET /v1/models`ରୁ 200 ଫେରିବା ଆବଶ୍ୟକ କରେ, ପ୍ରୋସେସ୍ ଗ୍ରୁପ୍କୁ ବନ୍ଦ କରେ,
  ଏବଂ tarball ହ୍ୟାଶ୍ ସହିତ ଫଳାଫଳକୁ `validation.json`ରେ ରେକର୍ଡ କରେ।
- **ସେହି ସମାନ ଆର୍ଟିଫ୍ୟାକ୍ଟକୁ ପ୍ରମୋଟ୍ କରନ୍ତୁ।** `promote` ତାହାର
  ସାମ୍ପ୍ରତିକ tarball ହ୍ୟାଶ୍ ପାଇଁ ସଫଳ ବୈଧତା ଯାଞ୍ଚ ନଥିବା ପ୍ରାର୍ଥୀକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ। ଡିଫଲ୍ଟ ସକ୍ରିୟ ସ୍ଲଟ୍ ହେଉଛି `_artifacts/candidate/current`; `--target <dir>`
  ସେହି ଏକେ ଫାଇଲ୍ସିଷ୍ଟମ୍ରେ ଅନ୍ୟ ଏକ ଡିରେକ୍ଟୋରୀ ଚୟନ କରେ, ଏବଂ ତାହାର ପୂର୍ବ ସ୍ଲଟ୍ ହେଉଛି `<dir>.previous`।
  ପ୍ରତ୍ୟେକ ନାମ ପରିବର୍ତ୍ତନ ଆଟମିକ୍ ଅଟେ, ଏବଂ ମଝିରେ ବିଫଳତା ଘଟିଲେ ପୂର୍ବରୁ ସମ୍ପନ୍ନ ହୋଇଥିବା ନାମ ପରିବର୍ତ୍ତନଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାବର୍ତ୍ତନ କରାଯାଏ।
- **ରୋଲ୍ବ୍ୟାକ୍ କରନ୍ତୁ।** `run` ପ୍ରମୋଟ୍ ହୋଇଥିବା ସ୍ଲଟ୍କୁ ପୁଣି ବୈଧ କରେ ଏବଂ
  ସେହି ଯାଞ୍ଚ ବିଫଳ ହେଲେ `current` ଓ `previous`କୁ ପୁଣି ଅଦଳବଦଳ କରେ। ପ୍ରଥମ ବୈଧତା ଯାଞ୍ଚରେ ବିଫଳ ହେଉଥିବା ପ୍ରାର୍ଥୀକୁ କେବେବି ପ୍ରମୋଟ୍ କରାଯାଏ ନାହିଁ।

ସବୁକିଛି gitignored `_artifacts/candidate/` ଅଧୀନରେ ଲେଖାଯାଏ; ଏକ ବିଦ୍ୟମାନ OmniRoute
ଇନଷ୍ଟଲେସନ୍ ଏବଂ ତାହାର ଡାଟା ଡିରେକ୍ଟୋରୀକୁ କେବେବି ସ୍ପର୍ଶ କରାଯାଏ ନାହିଁ। ପ୍ରମୋଟ୍ ହୋଇଥିବା CLI ହେଉଛି
`_artifacts/candidate/current/prefix/bin/omniroute`; ଏହାକୁ ବ୍ୟବହାର କରିବାବେଳେ ନିଜ `DATA_DIR` ସହିତ ଆରମ୍ଭ କରନ୍ତୁ।
ପ୍ରସ୍ଥାନ କୋଡ୍ଗୁଡ଼ିକ: `0` ସଫଳତା, `1` ବିଫଳ ବୈଧତା ଯାଞ୍ଚ କିମ୍ବା ପ୍ରମୋସନ୍, `2` ବ୍ୟବହାର ତ୍ରୁଟି କିମ୍ବା ଅନୁପସ୍ଥିତ ବିଲ୍ଡ।

## ସମନ୍ୱୟ ଯାଞ୍ଚତାଲିକା

ସମୀକ୍ଷା ଅନୁରୋଧ କରିବା ପୂର୍ବରୁ:

- PR ବେସ୍ ଏବେ ମଧ୍ୟ ସର୍ବୋଚ୍ଚ ସକ୍ରିୟ `release/v*` ବ୍ରାଞ୍ଚ୍ ବୋଲି ନିଶ୍ଚିତ କରନ୍ତୁ।
- ସେହି ବେସ୍କୁ ଫେଚ୍ କରନ୍ତୁ ଏବଂ ଆପଣ ବ୍ରାଞ୍ଚ୍ କରିବା ପରେ ଯୋଡ଼ାଯାଇଥିବା କମିଟ୍ଗୁଡ଼ିକୁ ସମୀକ୍ଷା କରନ୍ତୁ।
- ଅନଭିପ୍ରେତ କିମ୍ବା ସୃଷ୍ଟି ହୋଇଥିବା ଅନାବଶ୍ୟକ ପରିବର୍ତ୍ତନ ପାଇଁ `git diff <active-base>...HEAD` ସମୀକ୍ଷା କରନ୍ତୁ।
- ଉତ୍ସକୁ ଅଦ୍ୟତନ କରି ଏବଂ ଆଉଟପୁଟ୍ ପୁନଃସୃଷ୍ଟି କରି କ୍ୟାଟାଲଗ୍ ଓ ସୃଷ୍ଟି ହୋଇଥିବା ଡକ୍ୟୁମେଣ୍ଟ୍ ଦ୍ୱନ୍ଦ୍ୱଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।
- ସମନ୍ୱୟ ପରେ PR ବର୍ଣ୍ଣନାରେ ତାଲିକାଭୁକ୍ତ ପ୍ରତ୍ୟେକ କେନ୍ଦ୍ରିତ ପରୀକ୍ଷା/ଗେଟ୍ ପୁନଃଚଲାନ୍ତୁ।
- ପରିବର୍ତ୍ତିତ ବେସ୍ ସହ ମେଳ କରିବା ପାଇଁ କେବଳ ଆସର୍ସନ୍ଗୁଡ଼ିକୁ କେବେ ଦୁର୍ବଳ କରନ୍ତୁ ନାହିଁ କିମ୍ବା ଆବଶ୍ୟକ ପରୀକ୍ଷାଗୁଡ଼ିକୁ ବାଦ ଦିଅନ୍ତୁ ନାହିଁ।
