Tinatapos ng mga relay (Vercel, Deno, Cloudflare) ang upstream na koneksyon sa isang
serverless na backend upang makapag-egress ang OmniRoute mula sa isang matatag na rehiyon habang
pinananatiling server-side ang API key ng provider. Tinatalakay ng dokumentong ito ang dalawang failure mode
na nararanasan ng mga operator sa production at ang mga recovery path na ibinibigay ng OmniRoute para sa
bawat isa.

## Paano iniimbak ang relay auth

Kapag nag-deploy ka ng relay mula sa **Settings → Proxy Pool → Deploy Relay**,
iniimbak ng deploy flow ang auth token ng relay sa JSON field na `notes` ng proxy:

- Kung nakatakda ang `STORAGE_ENCRYPTION_KEY`, isinusulat ang token bilang `relayAuthEnc`
  (naka-encrypt gamit ang AES habang nakaimbak).
- Kung hindi, isinusulat ito bilang plaintext na `relayAuth`.

Sa oras ng request, ibinabalik ng `extractRelayAuth(notes)` ang alinmang anyong naroroon,
kaya patuloy na gumagana ang relay pagkatapos ng mga restart.

## Failure mode 1 — hindi ma-decrypt na token pagkatapos ng key rotation

**Sintomas:** ang mga relay na dati nang gumagana ay nagbabalik na ngayon ng upstream na `401`/auth
error pagkatapos ng rotation ng `STORAGE_ENCRYPTION_KEY` sa environment o secret manager.
Hindi na maaaring i-decrypt ang nakaimbak na `relayAuthEnc` blob, kaya nagbabalik ang
`extractRelayAuth` ng empty string at walang ipinapadalang auth ang relay.

**Pag-recover — ayusin nang hindi nire-redeploy:**

1. Buksan ang **Settings → Proxy Pool**.
2. Ang mga relay row na walang auth ay nagpapakita ng dilaw na `auth missing` badge at
   **Repair** button.
3. I-click ang **Repair**. Tatawagin ng OmniRoute ang
   `POST /api/settings/proxies/[id]/repair-relay`, na:
   - nagde-decrypt ng `relayAuthEnc` gamit ang **kasalukuyang** key,
   - muling nagsusulat ng plaintext na `relayAuth` sa `notes`,
   - nagbabalik ng `{ repaired: true, mode: "recovered" }`.

Magpapatuloy sa pagseserbisyo ang relay nang hindi kailangang muling ilagay ang anumang deploy credential.

Gagana lamang ito kung maaari pa ring i-decrypt ng kasalukuyang `STORAGE_ENCRYPTION_KEY` ang
blob. Kung ni-rotate mo ang key **nang walang** migration, hindi na mare-recover ang blob.

## Failure mode 2 — hindi mare-recover na token (na-rotate na at wala na ang key)

**Sintomas:** na-click mo ang **Repair** at natanggap ang
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Pag-recover — muling mag-deploy:**

Hindi mare-recover ang nakaimbak na token gamit ang kasalukuyang key. Muling i-deploy ang relay
mula sa parehong modal na orihinal mong ginamit (**Deploy Relay** menu → Vercel / Deno
/ Cloudflare). Magsusulat ang deploy flow ng bagong token (naka-encrypt gamit ang kasalukuyang
key) at mawawala ang `auth missing` badge ng row.

Sa UI, ang **Repair** button mismo ang magbubukas sa redeploy modal kapag hindi
mare-recover ang token, kaya hindi mo na ito kailangang manual na hanapin.

## Failure mode 3 — naaabot ang relay ngunit hindi maayos ang kalagayan nito

**Sintomas:** ipinapakita ng proxy test (`speed` button) na gumagana ang relay ngunit
paminsan-minsan ay pumapalya pa rin ang mga request.

Suriin ang mga relay awareness header na ibinabalik ng auto-test probe ng OmniRoute
(tingnan ang **Settings → Proxy Pool** at ang mga counter na `relayTested` / `relayAlive`):

- `x-relay-url` — kung aling relay backend ang tumugon.
- `x-relay-mode` — `ts` | `bifrost` | `auto` para sa request na iyon.
- `x-relay-attempts` — kung ilang relay hop ang sinubukan bago magtagumpay.
- `x-relay-fallback` — `true` kapag nag-fallback ang request mula sa mas gustong
  backend patungo sa TypeScript relay.

Ang mataas na rate ng `x-relay-fallback` na may mababang `relayAlive` ay nangangahulugang
hindi maayos ang sidecar backend at dapat mo itong ayusin o ilipat ang relay backend
strategy sa `ts` (tingnan ang `RELAY_BACKEND_STRATEGY.md`).

## Sanggunian ng API

| Paraan | Path                                      | Body                    | Tagumpay                                                                                                                              | Kabiguan                                                                                     |
| ------ | ----------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` kapag muling nakuha; `200 { repaired: false, mode: "noop" }` kapag mayroon nang plaintext | `409 { mode: "redeploy" }` hindi mare-recover; `400` hindi relay type; `404` hindi natagpuan |

Nagdaragdag ang list route na `GET /api/settings/proxies` ng walang-secret na
`relayInfo: { isRelay, authMissing, repairMode }` sa bawat item upang maipakita ng dashboard
ang opsyon sa pag-aayos nang hindi kailanman inilalantad ang token.
