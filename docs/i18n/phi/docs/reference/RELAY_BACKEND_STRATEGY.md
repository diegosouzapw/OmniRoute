## Buod

Sinusuportahan na ngayon ng OmniRoute ang tatlong relay mode para sa `/api/v1/relay/chat/completions`:

- `ts`: Gamitin ang TypeScript relay sa loob ng proseso.
- `bifrost`: Piliting gamitin ang Bifrost gateway.
- `auto`: Unahin ang Bifrost kapag available, at bumalik sa TypeScript kapag nabigo.

Kapag tumatakbo ka sa mataas na request rate (malaking bilang ng tokens/araw, halos tuloy-tuloy na throughput), ang pinakamainam na estratehiya ay panatilihing tahasan at mabilis ang fallback path upang hindi kailanman ma-block ang hot path dahil sa hindi gumaganang sidecar.

## Gawi ng mode

- `ts`
  - Pinakamababang operational complexity.
  - Lahat ng routing at validation ay tumatakbo sa Node.
  - Walang dependency sa sidecar para sa availability.
- `bifrost`
  - Piliting idaan ang lahat ng request sa sidecar gateway.
  - Walang awtomatikong fallback.
  - Kapaki-pakinabang lamang kapag garantisado ang health at latency ng sidecar.
- `auto`
  - Ginagamit ang sidecar kapag maaabot at naka-enable ito.
  - Ang mga nabigong pagtatangka ay nagti-trigger ng mga fallback header at ibinabalik ang trapiko sa TS upang manatiling kontrolado ang tagumpay ng request.
  - Ang mode na ito ang pinakaligtas na pagpipilian para sa production kapag mas mahalaga ang uptime kaysa sa mahigpit na sidecar-only routing.

## 9router kumpara sa CLIPROXYAPI sa kasalukuyan

Ang 9router at CLIPROXYAPI ay kapwa mga integration na matagal nang naglalantad ng mga compatibility path para sa mga upstream provider.

- Ang 9router ay isang naka-embed na path para sa upstream orchestration at compatibility behavior.
- Ang CLIPROXYAPI ay isang proxy API bridge para sa trapikong CLI / SDK style.
- Pinatatatag ang Bifrost bilang externalized path kapag kailangan mo ng nakalaang sidecar-like hop at low-latency local dispatch.

Kung kasalukuyan mong inihahambing ang 9router/CLIPROXYAPI:

- Panatilihin ang request signing, mga allowlist check, at mga DB policy gate sa API route bago ang handoff.
- Kung kailangan ng workflow ng mahigpit na sidecar behavior at mas mababang variance kada request, gamitin ang `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Kung kailangan mo ng sidecar resilience na may maayos na degradation sa mga kondisyon ng insidente, gamitin ang `OMNIROUTE_RELAY_BACKEND=auto`.

## Kontrata ng hangganan ng backend

Ang matatag na hangganan ng produkto ay ang OmniRoute relay API, hindi ang pagpapatupad ng dashboard. Maaaring mag-install, mag-configure, at mangasiwa ang Next.js dashboard ng mga lokal na serbisyo, ngunit dapat pumasok ang request routing sa pamamagitan ng relay API at mag-handoff sa likod ng hangganang iyon.

Mga pangmatagalang pagpipilian sa backend:

- Panatilihin ang TypeScript relay bilang in-process policy at fallback path. Nananatili rito ang auth, mga allowlist, request normalization, accounting, at mga safety check bago ang anumang backend handoff.
- Gamitin ang Bifrost bilang piniling high-throughput Tier-1 sidecar kapag kailangan ng deployment ng mas mababang routing variance, sentralisadong provider rotation, o scale-out sa maraming OmniRoute replica.
- Panatilihin ang 9router at CLIPROXYAPI bilang mga naka-embed na compatibility service. Tumatakbo ang mga ito bilang mga pinangangasiwaang lokal na proseso at kapaki-pakinabang kapag ang kanilang provider/CLI behavior ang nais na adapter, ngunit hindi dapat maging default na Tier-1 routing engine ang mga ito.
- Huwag hayaang magpasa ang dashboard ng arbitraryong service URL sa hot path. Ang mga URL na ibinibigay ng UI ay mga configuration input; dapat i-resolve ng routing code ang mga nakarehistro at health-checked na backend mula sa mga server-side setting at supervisor state.
- Piliin ang loopback HTTP para sa mga pinangangasiwaang serbisyo sa kasalukuyan dahil naglalantad na ang mga managed process ng mga HTTP-compatible API, maaaring i-audit ng route guard ang hangganan, at makikita sa mga request log ang failure/fallback behavior. Sulit lamang magdagdag ng SDK o socket transport sa hinaharap kung masusukat nitong mapababa ang p99 routing latency nang hindi pinahihina ang isolation o fallback semantics.

Samakatuwid, para sa isang napakataas na throughput na deployment, ang default na sagot ay `auto` na naka-enable ang Bifrost: gamitin ang Go sidecar sa hot path habang pinananatili ang TypeScript fallback para sa success rate. Gamitin lamang ang `bifrost` kapag mas mahalaga ang mahigpit na sidecar-only behavior kaysa sa maayos na degradation.

## Gabay para sa mataas na throughput

Para sa tuloy-tuloy na mataas na RPM/RPS at mahigpit na success SLO:

1. Gamitin ang `auto` na may praktikal na cooldown at failure telemetry.
2. Panatilihin ang upstream validation at mga API-key check sa hangganan ng TypeScript route.
3. I-enable ang mga tahasang header/counter upang makita ng iyong alerting ang dalas at mga dahilan ng fallback.
4. I-tune ang mga timeout ng sidecar upang mabilis na mabigo, hindi upang maghintay nang walang hanggan.
5. Panatilihing maayos ang service auto-restart at health telemetry loop upang maging tunay na pambihira ang fallback.

## Iminungkahing baseline

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Panatilihing naka-enable ang mga API key, allowlist, sanitizer, at rate-limit check sa mga route handler (palaging tumatakbo ang mga ito bago ang downstream forwarding).
- I-export ang mga fallback metric mula sa iyong reverse proxy at mga request log upang makita ang mga sidecar outage sa loob ng isang minuto.

## Kontrata ng provider plugin

Dapat i-import ng mga sidecar ang provider metadata sa pamamagitan ng JSON-safe provider plugin
manifest sa halip na umasa sa mga internal ng TypeScript executor. Tingnan ang
[Manifest ng Provider Plugin](./PROVIDER_PLUGIN_MANIFEST.md) para sa kontrata sa pagiging
kwalipikado ng sidecar at mga yugto ng migration.
