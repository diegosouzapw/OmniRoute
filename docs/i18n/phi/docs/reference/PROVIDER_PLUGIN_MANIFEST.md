Tinutukoy ng `open-sse/config/providerPluginManifest.ts` ang JSON-safe na kontrata ng provider
plugin. Iniuugnay ng `open-sse/config/providerPluginManifestRegistry.ts` ang kontratang iyon
sa kasalukuyang provider registry para sa mga sidecar gaya ng Bifrost,
CLIProxyAPI, o isang Go/Rust router sa hinaharap. Nananatiling source of truth ang
TypeScript registry, ngunit maaaring gamitin ng mga sidecar ang manifest nang hindi nag-i-import
ng executor code, mga default ng OAuth, mga header, o estado ng process environment.

Available rin sa pamamagitan ng HTTP ang parehong manifest sa
`GET /api/v1/provider-plugin-manifest` para sa mga sidecar na tumatakbo sa labas ng proseso.

Ina-advertise ng OmniRoute ang URL na iyon sa Bifrost at CLIProxyAPI sa pamamagitan ng
request header na `X-OmniRoute-Provider-Manifest-Url`. Itakda ang
`OMNIROUTE_PROVIDER_MANIFEST_URL` kapag kailangan ng sidecar ng pampubliko o container
network URL sa halip na ang lokal na origin ng request.

## Pag-refresh ng Manifest

Ibinabalik ng HTTP endpoint ang `Cache-Control: public, max-age=60` at isang matibay na
`ETag`. Dapat panatilihin ng sidecar ang huling na-validate na manifest at ipadala ang ETag nito
sa `If-None-Match` kapag nagre-refresh. Walang body ang isang tugon na `304 Not Modified`;
pananatilihin ng sidecar ang naka-cache nitong manifest. Kung walang naka-validate na naka-cache na manifest,
dapat gumawa ang sidecar ng unconditional request sa halip na tumanggap ng `304`.

## Layunin

Ilipat ang provider metadata tungo sa isang plugin contract upang ang hot request path ay
maaari kalaunang pangasiwaan ng isang sidecar na may mas mababang latency habang pinananatili ng OmniRoute ang
TypeScript route bilang policy gate at fallback. Additive ang manifest: hindi nito
binabago nang mag-isa ang request routing.

## Kontrata

Naglalaman ang manifest ng:

- provider id at alias
- upstream format at pangalan ng executor
- uri ng auth, auth header, at opsyonal na auth prefix
- static na endpoint metadata
- pagiging kwalipikado para sa sidecar at mga tahasang dahilan kung bakit dapat manatili sa TS ang isang provider
- JSON-safe na model metadata gaya ng context length, mga vision/reasoning flag, at
  mga hindi sinusuportahang param
- mga capability tag kabilang ang `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch`, at `usage-supported`

Sadyang hindi isinasama ng manifest ang:

- mga OAuth client secret at default na secret value
- runtime environment resolution
- mga request header at pampublikong credential helper
- mga dynamic na URL builder
- mga executor function
- mga internal ng session pool

## Mga Capability Tag

Ang `capabilities` ay isang nakaayos na array ng mga tag na hinango mula sa registry entry. Dapat
itong ituring ng mga integrator bilang machine-readable na sagot sa "ano ang kayang gawin ng provider na ito", sa halip na
muling basahin ang mga TypeScript source.

| Tag                  | Kahulugan                                                                                 |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `apikey`             | Tumatanggap ng API key (ang `authType` ay `apikey` o `optional`).                         |
| `oauth`              | Gumagamit ng OAuth o session flow.                                                        |
| `responses`          | Naglalantad ng OpenAI Responses-API base URL.                                             |
| `passthrough-models` | Direktang naghahatid ng mga model mula sa upstream sa halip na mula sa static na catalog. |
| `custom-executor`    | Nagpapatakbo ng hindi default na executor, kaya nananatili ito sa TypeScript path.        |
| `sidecar-candidate`  | Sumasalamin sa `sidecar.eligible` — ligtas na isaalang-alang para sa sidecar import.      |
| `usage-fetch`        | May nakakonektang usage o quota fetcher (`getUsageForProvider`).                          |
| `usage-supported`    | Tinatanggap ng usage API ang provider na ito (`isSupportedUsageConnection`).              |

Para lamang sa discovery ang `usage-fetch`. Ipinapahiwatig nito na alam ng OmniRoute kung paano basahin ang usage para sa
provider; hindi nito ina-activate ang fetching, binabago ang quota semantics, o ipinahihiwatig na
naka-enable ang Dashboard quota widget para sa provider — hiwalay na ginagabayan ang widget na iyon ng
`USAGE_SUPPORTED_PROVIDERS`. Ang source of truth ay `USAGE_FETCHER_PROVIDERS` sa
`open-sse/services/usage/fetcherProviders.ts`.

Naka-key ang listahang iyon ayon sa mga string na tinatanggap ng usage dispatcher, kaya pinagsasama nito ang mga canonical id
at alias at bahagyang mas mahaba kaysa sa bilang ng mga provider na may tag: ang mga entry na
hindi chat provider sa manifest registry (halimbawa, ang `firecrawl` search provider
at ang `amazon-q` ACP provider) ay walang manifest entry na maaaring lagyan ng tag.

Sinasagot ng `usage-supported` kung tumatanggap ang server at mga Dashboard usage route ng isang connection
para sa provider. Sinasalamin nito ang `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
at `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), na kapwa ginagabayan ng
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Hindi tulad ng
`usage-fetch`, inilalabas lamang ito sa provider id — ginagawa ng runtime guard ang
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` nang walang alias resolution, kaya pinananatili ng manifest
ang parehong panuntunan. Magkaiba ang saklaw ng dalawang tag: 3 provider ang may
`usage-fetch` lamang (`opencode`, `opencode-zen`, `xai`) at 1 ang may
`usage-supported` lamang (`xiaomi-mimo-token-plan`), kaya hindi ipinahihiwatig ng isa ang isa pa.

## Paggamit ng Sidecar

Dapat ituring ng mga sidecar ang `sidecar.eligible` bilang konserbatibong hudyat ng pagiging kandidato, hindi bilang walang-kondisyong desisyon sa pagruruta. Ang unang target ng pag-import ay dapat ang mga provider na gumagamit ng API key at static na endpoint gamit ang default na executor. Ang mga provider na may mga custom na web executor, daloy ng OAuth/session, dynamic na URL builder, o configuration ng pool ay mananatili sa TypeScript fallback path hanggang sa maipatupad ng isang sidecar ang katumbas na gawi at mapatunayan ng telemetry ang pagkakapantay.

Mga iminumungkahing yugto ng migrasyon:

1. Bumuo at mag-validate ng provider plugin manifest mula sa TS registry.
2. Turuan ang Bifrost o CLIProxyAPI na i-import ang manifest para sa mga provider na gumagamit ng API key/static na endpoint.
3. Iruta ang mga kwalipikadong provider sa sidecar sa likod ng `OMNIROUTE_RELAY_BACKEND` habang nananatiling naka-enable ang TS fallback.
4. I-promote lamang ang mga provider kapag tumutugma sa TS path ang success rate, p99 latency, gawi sa streaming, at paghawak sa mga hindi sinusuportahang parameter.
5. Magdagdag ng mga sidecar-native na plugin para sa mga custom na executor, paisang pamilya ng provider.

## Bakit Hindi Direktang I-embed ang Mga Provider sa Next

Hindi dapat ang Next frontend ang namamahala sa pagpapatupad ng provider. Dapat nitong tawagin ang hangganan ng API. Pagkatapos, maaaring magpasya ang backend kung gagamitin ang TypeScript executor, Bifrost, CLIProxyAPI, o isang native na sidecar sa hinaharap. Pinapanatili nitong sentralisado ang paglagda sa request, mga pagsusuri sa allowlist, patakaran ng DB, at gawi ng fallback bago ang anumang paglilipat sa sidecar.
