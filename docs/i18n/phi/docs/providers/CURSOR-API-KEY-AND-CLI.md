Dalawang paraan upang ilagay ang Cursor sa likod ng OmniRoute nang walang IDE session:

1. **Provider na `cursor-api`** (card na "Cursor API", alias na `cua`): isang
   provider na gumagamit ng API key at naglalaman ng Cursor user API key
   (`crsr_…`, binubuo sa `https://cursor.com/dashboard/api`). Maa-access ng
   anumang OmniRoute client ang mga Cursor model sa pamamagitan ng
   `/v1/chat/completions` bilang `cursor-api/<model>` o `cua/<model>`, kasama
   ang karaniwang mga layer para sa quota, fallback, at pag-log. Hindi
   nagbabago ang IDE provider (`cursor`, OAuth/IDE session).
2. **Cursor CLI passthrough**: ituro ang Cursor CLI (`agent`) sa OmniRoute upang
   ang bawat RPC na ginagawa ng CLI ay ma-authenticate gamit ang isang
   OmniRoute API key, ma-forward sa Cursor gamit ang credential ng isang
   koneksyong `cursor-api`, at maitala sa pahina ng Logs.

## Bakit ipinagpapalit ang key

Tinatanggihan ng `api2.cursor.sh` ang isang raw na `crsr_…` key bilang Bearer
token (401). Ipo-POST muna ng Cursor CLI ang key sa
`/auth/exchange_user_api_key` at tatanggap ito ng session JWT na mag-e-expire
pagkalipas ng isang oras; ang ibinalik na `refreshToken` ay may kaparehong
`exp`, kaya ang pag-refresh ay nangangahulugang muling pagpapalit ng key.
Isinasagawa ng `open-sse/services/cursorApiKeyAuth.ts` ang pagpapalit na iyon,
nagka-cache ng isang session token bawat key, muling nagpapalit limang minuto
bago ang expiry, at nag-aalis ng naka-cache na token kapag sumagot ang Cursor
ng 401. Tinatawag ito ng `CursorExecutor` bago mismo buksan ang upstream stream
para sa mga koneksyong `cursor-api`.

## Ang provider na `cursor-api`

Registry: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, kaparehong `format`, `baseUrl`, at
`models` ng `cursor`). Catalog card:
`src/shared/constants/providers/apikey/specialty-media.ts`. Executor map:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Dashboard: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

Pagkatapos:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Mga tala:

- Ang listahan ng mga model para sa `cursor-api` ay nagmumula sa static na
  Cursor registry (ang parehong listahan na ginagamit ng IDE provider bilang
  fallback); hindi kailangang naka-install ang `cursor-agent` sa OmniRoute
  host.
- Ang `POST /api/providers/{id}/refresh-cursor` ay para lamang sa `cursor` IDE
  provider; walang IDE session na kailangang i-renew ang mga koneksyong
  `cursor-api`.

## Cursor CLI passthrough

Route: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Nakarehistro ang prefix na
`/api/cursor-cli/` sa `src/shared/constants/publicApiRoutes.ts` dahil
ipinatutupad ng handler ang sarili nitong authentication:

| Path                                                                                                                            | Auth na inaasahan mula sa CLI | Ginagawa ng OmniRoute                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                              | `Bearer <OmniRoute API key>`  | Vine-validate ang key, bumubuo ng 1h HS256 JWT (nilagdaan gamit ang `JWT_SECRET`), at ibinabalik ito                                                                                        |
| bawat iba pang path (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`           | Vine-verify ang issuer/audience/expiry, pumipili ng aktibong koneksyong `cursor-api`, pinapalitan ang Authorization header ng ipinagpalit na Cursor token, at sini-stream pabalik ang tugon |

Dine-decode ng CLI ang `exp` mula sa anumang token na natatanggap nito, kaya
kapag binigyan ito ng opaque token, muli itong magpapalit bago ang halos bawat
request; iniiwasan iyon ng nabuong JWT. Kapag nakatanggap ng 401 mula sa
OmniRoute, muling magpapalit ang CLI.

### Pag-setup

1. Gumawa ng OmniRoute API key (Dashboard → API keys) at koneksyong
   `cursor-api`.
2. Sabihin sa CLI na gamitin ang HTTP/1.1 para sa agent stream. Sa
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Kung wala ito, bubuksan ng CLI ang agent turn sa pamamagitan ng HTTP/2
   patungo sa hiwalay na naka-configure na agent host, at ang mga
   control-plane RPC lamang ang dadaan sa endpoint.

3. Patakbuhin ang CLI laban sa OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Ang bawat hop ay mapupunta sa Logs bilang provider na `cursor-api`, request
type na `cursor-cli`, path na `/api/cursor-cli/<rpc>`, at iuugnay sa OmniRoute
API key at sa koneksyong nagserbisyo rito.

### Mga uri ng pagkabigo

| Sitwasyon                                              | Tugon sa CLI                                             |
| ------------------------------------------------------ | -------------------------------------------------------- |
| Hindi kilalang OmniRoute key at `REQUIRE_API_KEY=true` | 401 `unauthenticated` sa exchange                        |
| `REQUIRE_API_KEY=false`                                | anonymous na session (ginagaya ang gawi ng `/v1/*`)      |
| Nag-expire / banyaga / binagong session JWT            | 401, muling nagsasagawa ng exchange ang CLI              |
| Binawi ang OmniRoute API key pagkatapos ng exchange    | 401 sa susunod na RPC                                    |
| Walang aktibong koneksyon sa `cursor-api`              | 503 `unavailable`                                        |
| Tinanggihan ng Cursor ang key ng koneksyon             | 401 `unauthenticated`, inaalis ang naka-cache na session |
| Hindi maabot ang upstream                              | 502 `unavailable` (nilinis na mensahe)                   |
| Hindi nakatakda ang `JWT_SECRET`                       | 503 sa exchange                                          |
