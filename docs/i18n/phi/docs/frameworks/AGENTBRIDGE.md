Ang AgentBridge ay ang MITM (Man-in-the-Middle) proxy ng OmniRoute na humaharang sa trapikong HTTPS mula sa mga IDE AI agent at muling niruruta ito sa pamamagitan ng pinag-isang routing engine ng OmniRoute. Sinusuportahan nito ang **10 IDE agent** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code, at Trae (iniimbestigahan) — kaya ang OmniRoute ang MITM proxy na may pinakamalawak na saklaw para sa mga AI coding assistant sa merkado.

**Lokasyon ng dashboard:** `/dashboard/tools/agent-bridge`
**Grupo sa sidebar:** Mga Tool (pagkatapos ng Mga Cloud Agent)
**Tingnan din:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — subaybayan ang lahat ng naharang na trapiko nang real-time; `docs/security/MITM-TPROXY-DECRYPT.md` (git; hindi kino-compile sa `/docs`) — ang Linux TPROXY transparent-decrypt capture mode na pinapagana ng route na `/api/tools/agent-bridge/tproxy`.

## §1 Pangkalahatang-ideya

### Ano ang AgentBridge?

Kapag nagsasagawa ng API call ang isang IDE agent (hal., GitHub Copilot, Cursor, Claude Code), direkta itong kumokonekta sa upstream na AI provider (OpenAI, Anthropic, atbp.). Transparent na hinaharang ng AgentBridge ang koneksiyong iyon sa antas ng TLS — nang hindi nangangailangan ng anumang pagbabago sa configuration ng agent — at muling isinusulat ang request sa pamamagitan ng OmniRoute.

Ibig sabihin, maaari mong:

- **Muling iruta ang anumang agent sa anumang provider**: Nakikipag-ugnayan ba ang Copilot sa OpenAI? I-redirect ito sa Anthropic Claude, Gemini, o alinman sa 352 provider ng OmniRoute.
- **Maglapat ng mga model mapping**: `gemini-3-flash` → `claude-sonnet-4.7` nang transparent sa antas ng handler.
- **Obserbahan ang lahat ng trapiko ng agent**: inilalathala ang bawat naharang na request sa [Traffic Inspector](./TRAFFIC_INSPECTOR.md).
- **Ilapat ang resiliency ng OmniRoute**: gumagana rin ang combo routing, mga circuit breaker, fallback, at pagsubaybay sa gastos para sa trapiko ng IDE agent.

## §2 Arkitektura

### 2.1 Pangkalahatang-ideya ng mga bahagi

```
IDE Agent (VS Code / Cursor / atbp.)
    │  HTTPS (port 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← Pag-redirect ng DNS
    │
    ▼
src/mitm/server.cjs  (port 443, CJS child process)
    │  tinutukoy ang target gamit ang Host header SNI
    │  bumubuo ng TLS cert para sa bawat SNI na nilagdaan ng AgentBridge CA
    ├── Tugma sa bypass list? → TCP passthrough (walang pag-decrypt)
    ├── Tugma sa target? → fetch → OmniRoute router (port 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() sa request body/mga header
    │               ├── TrafficBuffer.push() — inilalathala sa Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── Walang tugma? → TCP passthrough (walang pag-decrypt)
```

### 2.2 MITM server (`src/mitm/server.cjs`)

Tumatakbo ang pangunahing MITM server bilang Node.js CJS child process (upang maiwasang muling isulat ang kasalukuyang CJS codebase). Ito ay:

- Nakikinig sa port 443 (nangangailangan ng pribilehiyo o `authbind`/`setcap`)
- Tumatanggap ng mga CONNECT tunnel mula sa OS (sa pamamagitan ng `/etc/hosts` DNS redirect)
- Bumubuo ng mga TLS certificate para sa bawat SNI na nilagdaan ng AgentBridge CA (`DATA_DIR/mitm/ca.crt`)
- Tinutukoy ang target na agent gamit ang Host header sa pamamagitan ng registry na `targets/index.ts`
- Ipinapasa sa TypeScript handler layer sa pamamagitan ng HTTP patungo sa `http://127.0.0.1:20128`

Nilo-load ang `TARGET_HOSTS` mula sa `DATA_DIR/mitm/targets.json` (isinusulat ng `targets/index.ts` sa pag-boot), na nagbibigay-daan sa mga dinamikong update nang hindi nire-restart ang CJS server.

> **Modelo ng root CA (#6684).** Ang paglalarawan sa itaas tungkol sa certificate para sa bawat SNI na nilagdaan ng isang CA
> ay ang persistent na modelo ng root CA na idinagdag sa #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, na muling ginagamit ang CA/leaf crypto na napatunayan na
> para sa TPROXY sa `src/mitm/tproxy/dynamicCert.ts`) — pinapalitan nito ang
> mas lumang nag-iisang static at self-signed na leaf (`src/mitm/cert/generate.ts`, na
> nakalaan pa rin para lamang sa mga antigravity host) na ipinahihiwatig ng isang pares na
> `server.crt`/`server.key` sa disk. **Gawi sa migration**: awtomatikong makukuha ng bagong
> installation (walang dating `server.crt`) ang modelo ng root CA; patuloy namang gagamitin
> ng installation na nagtitiwala na sa lumang static leaf ang certificate na iyon hanggang
> itakda ng operator ang `MITM_ROOT_CA_ENABLED=true` at i-restart ang bridge
> (`src/mitm/cert/migration.ts` ang purong decision function — ang isang pinagkakatiwalaang
> MITM CA na maaaring lumagda ng leaf para sa **anumang** host ay higit na makapangyarihan
> kaysa sa lumang fixed-SAN leaf, kaya hindi kailanman tahimik ang pagpapalit para sa isang
> installation na nagtitiwala na rito). Ini-install ang CA cert sa parehong
> `omniroute-mitm.crt` trust-store slot na ginamit ng lumang leaf
> (`cert/install.ts::installCaCert`) — hindi kailangan ang paglilinis ng dual trust.

### 2.3 Batayang handler (`src/mitm/handlers/base.ts`)

Lahat ng agent handler ay nag-e-extend sa `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Mga protected helper: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Tinatawag ng bawat handler ang `hookBufferStart()` bago mag-proxy at ang `hookBufferUpdate()` kapag nakumpleto na. Nagpapadala ang mga ito ng mga entry na `InterceptedRequest` sa `globalTrafficBuffer` (tingnan ang [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Registry ng mga target (`src/mitm/targets/`)

May deklaratibong target file ang bawat agent:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Ini-export ng registry (`targets/index.ts`) ang `ALL_TARGETS` at ginagawa nito ang `DATA_DIR/mitm/targets.json` sa pag-boot.

### 2.5 Passthrough at bypass list (`src/mitm/passthrough.ts`)

**Bypass list** (sinusuri muna, at may prayoridad kaysa sa pagtutugma ng target):

- Mga default na pattern: mga banking host, `.gov.`, mga OAuth/SSO provider (Okta, Auth0), atbp.
- Mga pattern ng user: nakaimbak sa DB table na `agent_bridge_bypass`
- Nakakatanggap ang mga bina-bypass na host ng transparent na TCP tunnel — **hindi kailanman dine-decrypt** ang TLS

**Default na passthrough** (walang tugma sa target at wala sa bypass):

- Nakakatanggap din ng TCP tunnel — hindi kailanman pinuputol ang mga koneksyon
- Pinipigilan ang AgentBridge na gambalain ang pangkalahatang HTTPS traffic ng system

Prayoridad sa routing:

```
bypass list → pagtutugma ng target → passthrough
```

### 2.6 Upstream CA cert (`src/mitm/upstreamTrust.ts`)

Para sa mga corporate network environment na may custom na CA:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Kapag itinakda, kino-configure nito ang global dispatcher ng `undici` gamit ang karagdagang CA cert, na nagbibigay-daan sa AgentBridge na maabot ang mga upstream provider sa pamamagitan ng mga corporate TLS termination proxy.

### 2.7 Pagtatakip ng mga secret (`src/mitm/maskSecrets.ts`)

Inilalapat ang hiwalay na clean-room scanner sa mga request body at credential header
**bago** mapunta ang mga ito sa buffer ng Traffic Inspector o sa anumang log. Nagsasagawa ito ng iisang linear pass:

- Mga token na may prefix na `sk-` / `ak-` / `pk-` (istilong OpenAI/Anthropic)
- Mga credential na RFC 6750 `Authorization: Bearer <token>`, na inuuna ang buong token
- Mga generic na mahaba at opaque na token (≥40 character), kabilang ang mga anyong may tuldok at padding

Ginagawang lowercase ng `sanitizeHeaders()` ang mga pangalan na pinanatili, pinagsasama ang mga array value sa paraang deterministiko, inaalis ang
pinagsasaluhang denylist para sa hop-by-hop/framing (kabilang ang proxy authentication), ganap na nire-redact ang `cookie` at
`set-cookie`, at ipinapasa ang mga credential value sa scanner.

### 3.1 Simulan/ihinto ang MITM server

| Aksyon                 | Paglalarawan                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| Simulan ang Server     | Sinisimulan ang `src/mitm/server.cjs` sa port 443                                          |
| Ihinto ang Server      | Maayos na pinapatigil ang child process                                                    |
| I-restart ang Server   | Ihinto + simulan (ilalapat ang mga pagbabago sa target)                                    |
| Pagkatiwalaan ang Cert | Ini-install ang `DATA_DIR/mitm/ca.crt` sa trust store ng OS                                |
| I-download ang Cert    | Dina-download ang `ca.crt` para sa manu-manong pag-install                                 |
| Muling Buuin ang Cert  | Gumagawa ng bagong CA keypair (mawawalan ng bisa ang lahat ng kasalukuyang per-agent cert) |

### 3.2 Pagkatiwalaan ang certificate

Dapat pagkatiwalaan ng OS ang AgentBridge CA certificate bago tanggapin ng mga IDE ang koneksyong MITM.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

O gamitin ang button na "Pagkatiwalaan ang Cert" sa dashboard (pinapatakbo nito ang naaangkop na command para sa iyong OS, na may sudo prompt kung kinakailangan).

#### Binabalewala ng mga Electron-based IDE ang trust store ng OS (`NODE_EXTRA_CA_CERTS`)

Ang ilang IDE — lalo na ang **Antigravity IDE**, at iba pang app na hango sa Electron / VS Code — ay may kasamang
sariling Node.js runtime na **hindi kumokonsulta sa trust store ng OS** para sa papalabas na
`fetch`/HTTPS. Sapat na ang pagtitiwala sa CA sa antas ng OS/NSS para sa katutubong **backend**
ng IDE (hal. isang Go language server, na gumagamit ng OS CA bundle), ngunit mabibigo pa rin sa
TLS ang **Electron frontend** — makikita ito bilang _naka-log out_ ang app o nagpapakita ng
_"error sa koneksyon"_ kahit ipinapakita ng MITM log na nagbabalik ng `200` ang mga bootstrap
call ng backend. Dalawang hakbang ang kinakailangan, at parehong mahalaga:

1. Tahasang ituro ang runtime sa CA:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Ilunsad ang IDE mula sa shell na iyon.** Kapag sinimulan ito mula sa desktop icon / Dock / Start menu,
   **hindi** nito namamana ang mga shell export, at mailalapat lamang ang `~/.config/environment.d/*.conf`
   pagkatapos ng bagong graphical login. Ganap munang isara ang IDE — dahil sa singleton lock ng Electron,
   itutuon lamang ng ikalawang paglunsad ang kasalukuyang process at babalewalain ang bagong environment.

Kailangan pa rin ang hakbang para sa OS trust + NSS sa itaas (binabasa ng Chromium network stack na ginagamit
ng ilang auth flow ang per-user NSS store, at mayroon itong sariling static pin para sa `*.googleapis.com`
na ino-override ng isang locally trusted na CA). Sinasaklaw ng `NODE_EXTRA_CA_CERTS` ang Node `fetch` path
bilang karagdagan dito.

### 3.3 DNS routing

Para sa bawat agent na gusto mong ma-intercept, dapat mag-resolve sa `127.0.0.1` ang (mga) API host nito. Awtomatikong pinamamahalaan ng AgentBridge ang mga entry sa `/etc/hosts` kapag ini-toggle mo ang DNS para sa isang agent sa Setup Wizard.

Mga halimbawang entry sa `/etc/hosts` para sa GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Pagmamapa ng modelo

Gamitin ang Model Mapping Table sa bawat agent card upang tukuyin ang mga mapping mula source → target:

| Source model (katutubo sa agent) | Target model (OmniRoute) |
| -------------------------------- | ------------------------ |
| `gpt-4o`                         | `claude-sonnet-4.7`      |
| `*` (wildcard)                   | `claude-haiku-4.7`       |

Minamapa ng wildcard na `*` ang anumang hindi nakikilalang modelo sa tinukoy na target. Pine-persist ito sa table na `agent_bridge_mappings`.

> **Tip — tuklasin ang mga totoong model ID ng agent.** Maaaring magpadala ang isang IDE ng mga pangalan ng
> modelo na naiiba sa mga label sa UI nito at nagbabago sa pagitan ng mga pangunahing bersyon. Halimbawa,
> ipinapadala ng **Antigravity 2** ang `gemini-3.1-pro-low`, `gemini-pro-agent`, at
> `gemini-3.1-flash-lite` sa network — hindi ang `gemini-2.5-pro` na ipinapakita sa mas lumang docs.
> Magpadala ng isang chat habang walang nakatakdang tumutugmang mapping: ila-log ng MITM ang eksaktong
> papasok na `model:` at pahihintulutang magpatuloy ang request. Imapa ang literal na value na iyon, at
> mai-intercept at iri-route sa iyong target ang susunod na request.

### 3.5 Abiso tungkol sa panganib

Ini-intercept ng AgentBridge ang mga credential (mga OAuth token, API key) na ginagamit ng IDE upang mag-authenticate sa mga upstream provider. Ang mga ito ay **mina-mask bago i-log** (tingnan ang §2.7) ngunit nakikita ng MITM layer ng OmniRoute. Sa unang pag-activate ng bawat agent, ipinapakita ang isang risk notice modal na maaaring isara.

| `cert-exists`         | Nabuo na sa disk ang MITM certificate                                 | "Wala pang nabuong MITM certificate. Bumuo nito mula sa tab na AgentBridge."                                                                                          |
| `cert-trusted`        | Nasa OS trust store ang MITM root CA                                  | "Hindi pinagkakatiwalaan ng OS store ang MITM root CA, kaya mabibigo ang TLS interception. Pagkatiwalaan ang certificate mula sa tab na AgentBridge."                 |
| `dns-configured`      | Naka-spoof ang mga target hostname sa `/etc/hosts`                    | "Hindi naka-spoof ang mga target hostname sa /etc/hosts, kaya hindi nakararating sa proxy ang traffic. I-enable ang DNS para sa (mga) agent na gusto mong i-capture." |

**Banner para sa naiwang state:** kapag natukoy ng page ang state na naiwan dahil sa pag-crash (DNS spoof / CA / system proxy), nagpapakita ang card ng amber na banner — _"May naiwang system state ang nakaraang session (DNS spoof, CA, o system proxy). Patakbuhin ang Ayusin upang linisin ito."_ — at hina-highlight ang button na **Ayusin**. Ang `Repair` ang katumbas sa application layer ng flag na `--cleanup` ng ProxyBridge (idine-delegate nito sa `repairMitm()` sa `src/mitm/manager.ts`).

> Nananatiling naka-install ang MITM root CA sa pagitan ng paghinto/pagsisimula upang maiwasan ang paulit-ulit na mga prompt ng sudo
> (kaparehong gawi ng mitmproxy/Charles), kaya ang pag-aalis nito ay isang hayagang pagkilos na
> **Alisin ang CA** sa halip na isang bagay na awtomatikong nangyayari kapag huminto.

### 3.7 Pag-import/pag-export ng portable config

Maaaring i-serialize ng AgentBridge ang state na **maaaring isaayos ng operator** bilang isang may bersyong JSON blob upang makopya ang isang setup sa iba't ibang machine. Ang serializer ay `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), na bina-validate ng `AgentBridgeConfigSchema`.

Eksaktong tatlong bahagi ang kasama sa export (sadyang **HINDI** ine-export ang mga built-in default, kaya hindi kailanman nagdodoble o sumasalungat sa mga ito ang pag-import):

| Field            | Pinagmulan                                                      | Mga tala                                                                     |
| ---------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `bypassPatterns` | mga bypass pattern na tinukoy ng user (`agent_bridge_bypass`)   | hindi kasama ang mga default na pattern ng bank/gov/okta                     |
| `customHosts`    | mga custom host ng Traffic Inspector (`inspector_custom_hosts`) | bawat isa: `{ host, kind: "llm"\|"app"\|"custom", label? }`                  |
| `agentMappings`  | mga model mapping para sa bawat agent (`agent_bridge_mappings`) | `{ [agentId]: [{ source, target }] }` para sa bawat agent na may mga mapping |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Gawi ng pag-import** (`POST /api/tools/agent-bridge/config`): **ganap na pinapalitan** ang mga bypass pattern at mapping para sa bawat agent; idinaragdag ang mga custom host nang **idempotent** (`INSERT OR IGNORE`). Iniuulat ng tugon kung ilan sa bawat isa ang inilapat:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Ano ang **WALA** sa config: estado ng pagpapatakbo ng server, mga path ng certificate, estado ng DNS ng bawat agent, path ng upstream CA, at mga setting ng TPROXY — ang mga iyon ay estado ng host/runtime, hindi mga naililipat na preference.

## §5 Seguridad

### Mga inilapat na Mahigpit na Panuntunan

| Panuntunan                        | Paglalapat                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **#12** `sanitizeErrorMessage`    | Sini-sanitize ang lahat ng error ng handler bago tumugon o maglagay ng entry sa buffer                 |
| **#13** Shell env-passing         | Gumagamit ang mga pag-edit sa `/etc/hosts` ng opsyong `env` — walang string interpolation ng mga path  |
| **#15 + #17** `isLocalOnlyPath()` | Ang `/api/tools/agent-bridge/` ay LOCAL_ONLY + SPAWN_CAPABLE — ipinapatupad ang loopback bago ang auth |

### Listahan ng bypass para sa mga sensitibong host

Tinitiyak ng listahan ng bypass na ang mga institusyong pinansyal, OAuth/SSO provider, at iba pang sensitibong host ay **hindi kailanman dine-decrypt**. Dumaraan ang kanilang TLS traffic bilang transparent na TCP tunnel — hindi kailanman nakikita ng OmniRoute ang plaintext.

Kabilang sa mga default na pattern ng bypass ang:

- `*.bank.*`, `*.gov.*` (pananalapi/pamahalaan)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identity)
- `*.apple.com`, `*.icloud.com` (mga serbisyo ng Apple system)

Iniimbak sa talahanayang `agent_bridge_bypass` ang mga pattern ng bypass na idinagdag ng user at nangingibabaw ang mga ito sa lahat ng iba pa.

### Pag-mask ng mga lihim

Inilalapat ang `maskSecrets()` mula sa `src/mitm/maskSecrets.ts`:

- Sa bawat request body bago ang `TrafficBuffer.push()`
- Sa bawat header bago i-log o i-broadcast

Mga pattern: mga token na may prefix na `sk-`/`ak-`/`pk-`, mga `Bearer` token, at mga generic na token na may ≥40 character.

### Upstream CA cert

Kapag nakatakda ang `AGENTBRIDGE_UPSTREAM_CA_CERT`, binabasa ang file sa pagsisimula. Kung umiiral ang path ngunit hindi mabasa ang file, nagla-log ang AgentBridge ng malinaw na error at tumatangging magsimula (pinipigilan nito ang mga tahimik na pagkabigo ng TLS sa mga corporate environment).

### Mga kilalang limitasyon

- **Nangangailangan ng pribilehiyo ang port 443**: Sa Linux, kailangan ng AgentBridge ang `setcap 'cap_net_bind_service=+ep'` sa Node binary, o patakbuhin ito sa pamamagitan ng `authbind`. Nagpapakita ang Setup Wizard ng mga tagubiling partikular sa OS.
- **Kailangang i-restart ang IDE**: Pagkatapos ng DNS redirect, kailangang i-restart ang IDE upang magkabisa ang bagong host resolution.
- **Mga hardcoded na OAuth token**: Iniimbak ng ilang agent (Kiro, Antigravity) ang mga OAuth refresh token nang lokal. Transparent ang mga ito sa AgentBridge — nakikita nito ang Bearer token sa bawat request, na mina-mask bago i-log.
- **Kailangan ng mga Electron frontend ang `NODE_EXTRA_CA_CERTS`**: Binabalewala ng mga IDE na ang frontend ay tumatakbo sa bundled na Node/Electron runtime ang OS/NSS trust store at dapat ilunsad mula sa shell na may nakatakdang `NODE_EXTRA_CA_CERTS` (tingnan ang §3.2). Sintomas kapag wala ito: matagumpay na nag-a-authenticate ang IDE backend (nagpapakita ang MITM ng mga `200`) ngunit nananatiling naka-log out ang UI.
- **Magkakahiwalay ang maraming pagkaka-install ng parehong IDE**: ang system install (hal. `/usr/share/antigravity/antigravity`) at user-local na "Full" install (hal. `~/AntigravityIDE_Full/antigravity-ide`) ay magkahiwalay na proseso na may sariling runtime — kailangang muling ilunsad ang bawat isa na may naka-inject na CA. Tukuyin kung alin ang tumatakbo gamit ang binary path nito bago muling ilunsad.
- **Itinatakda ang identity ng system prompt ng agent, hindi ng naka-route na model**: kapag ni-remap mo ang model ng agent sa ibang provider, inaangkin pa rin ng tugon ang native na identity ng agent (hal. sumasagot ang Antigravity ng "Pinapagana ako ng Gemini") dahil ini-inject iyon ng IDE sa system prompt. Kumpirmahin ang tunay na backend sa `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), hindi sa pagtatanong sa model kung sino ito.

## §6 Pag-troubleshoot

### Salungatan sa port 443

Kung may ibang prosesong nakikinig na sa port 443 (web server, VPN, atbp.):

```bash
lsof -i :443          # hanapin ang proseso
sudo fuser -k 443/tcp  # sapilitang ihinto (gamitin nang may pag-iingat)
```

Bilang alternatibo, mag-configure ng hindi pribilehiyong port sa mga setting ng AgentBridge at mag-set up ng mga panuntunan sa pag-redirect ng `iptables` / `pf`.

### Hindi pinagkakatiwalaan ang certificate

Kung nagpapakita ang IDE ng mga TLS error pagkatapos simulan ang AgentBridge:

1. Tiyaking na-install ang cert: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) o `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Pinapanatili ng ilang app ang sarili nilang trust store (Firefox, Chrome sa Linux). Patakbuhin muli ang "Trust Cert" at suriin ang cert store na partikular sa NSS/Firefox.
3. I-restart ang IDE pagkatapos pagkatiwalaan ang certificate — ginagamit ng mga kasalukuyang TLS session ang lumang trust state.

### Naka-log out ang IDE / "connection error" sa kabila ng pinagkakatiwalaang CA

Sintomas: pagkatapos i-redirect ang DNS at pagkatiwalaan ang CA, bubukas ang isang IDE na nakabatay sa Electron (hal. Antigravity) na **naka-log out** o nagpapakita ng error sa authentication/koneksyon, ngunit ipinapakita ng MITM log na nagbabalik ng `200` ang mga bootstrap call (`loadCodeAssist`, `fetchAvailableModels`, …).

Sanhi: **binabalewala ng naka-bundle na Node/Electron runtime ng IDE ang OS trust store**. Pinagkakatiwalaan ng native na backend (isang Go language server) ang OS CA at nakakapag-authenticate, ngunit hindi ito ginagawa ng Electron frontend — kaya inaakala ng UI na offline ito.

Ayos (parehong hakbang): i-export ang `NODE_EXTRA_CA_CERTS=<ca.crt>` **at muling ilunsad ang IDE mula sa shell na iyon**, hindi mula sa desktop icon. Ganap munang isara ang IDE — nangangahulugan ang singleton lock ng Electron na itutuon lamang ng pangalawang paglunsad ang umiiral na proseso at babalewalain ang bagong environment. Tingnan ang §3.2. Katulad ito ng isang bukas na upstream report kung saan gumagana ang isang standalone agent sa pamamagitan ng MITM ngunit nabibigo ang variant ng IDE sa parehong setup.

### Hindi naipapalaganap ang DNS

Tiyaking na-update ang `/etc/hosts`:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

I-flush ang DNS cache:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### Hindi natukoy ang IDE

Gumagamit ang awtomatikong pagtukoy ng mga karaniwang path ng pag-install. Kung nabigo ang pagtukoy ngunit naka-install ang IDE:

- Suriin kung nasa hindi karaniwang lokasyon ang binary ng IDE
- Gumagana pa rin ang Setup Wizard — nangangahulugan lamang ang pagkabigo sa pagtukoy na hindi ipapakita ng badge ang path ng pag-install

### Mga error sa handler (nabigo ang upstream fetch)

Kung nakaka-intercept ang AgentBridge ngunit nabibigo ang lahat ng kahilingan:

1. Tiyaking nakakonekta ang kahit isang provider sa `/dashboard/providers`
2. Suriin ang mga log ng OmniRoute server: `APP_LOG_LEVEL=debug` sa `.env`
3. Tiyaking nakaturo ang `OMNIROUTE_BASE_URL` sa tamang router endpoint (default: `http://127.0.0.1:20128`)

## §8 Roadmap

### Pagsisiyasat sa Trae

Ang Trae ay isang medyo bagong AI coding assistant. Bago magpatupad ng handler:

1. Tukuyin ang binary/extension sa mga marketplace ng VS Code / JetBrains o bilang standalone app
2. Kunin ang traffic gamit ang mitmproxy upang matuklasan ang mga API host at anyo ng mga endpoint
3. Tukuyin ang mekanismo ng authentication
4. Suriin kung itutuloy o hindi batay sa TOS at kung gaano kadaling matuklasan ang API

Hanggang sa makumpleto ang pagsisiyasat, nagpapakita ang Trae card sa dashboard ng badge na "Sinisiyasat" na may link na "Iulat ang pagiging posible." Ang handler stub sa `src/mitm/handlers/trae.ts` ay naglalabas ng structured na error na `Hindi pa naipapatupad`.

### Mga backlog agent (kailangan ang MITM — walang suporta para sa custom base URL)

Hindi sinusuportahan ng mga sumusunod na tool ang mga custom base URL sa kanilang mga kasalukuyang bersyon, kaya MITM lamang ang paraan ng interception. Nakabinbin pa ang pagtatasa sa pagiging posible:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — hiwalay sa Kiro IDE)
- **Cowork** (Anthropic desktop)

Tandaan: Sinusuportahan ng GitHub Copilot CLI ≥v1.0.19 ang `COPILOT_PROVIDER_BASE_URL` — gumamit ng direktang configuration sa halip na MITM para sa tool na iyon.
