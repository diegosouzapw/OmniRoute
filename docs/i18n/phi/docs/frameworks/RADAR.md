Ang Radar ay isang **opsyonal na add-on** na naglalagay ng nilagdaan at bagong-kuratang katalogo ng
mga libreng modelo sa ibabaw ng baseline ng release (`FREE_MODEL_BUDGETS` sa
`open-sse/config/freeModelCatalog.data.ts`). Umiiral ito dahil mas mabilis magbago ang kalagayan
ng libreng tier kaysa sa iskedyul ng mga release — nagdaragdag, nagbabawas, o nag-aalis ang mga provider
ng mga libreng quota sa pagitan ng mga release, at maaari lamang i-refresh ang baseline na katalogo
kapag may inilabas na bagong bersyon.

**Walang anumang libre ngayon ang mawawalan ng pagiging libre dahil sa remote feed.** Hindi kailanman
nilalagyan ng Radar ng paywall ang isang baseline entry; nire-refresh lamang nito ang mga field ng limit/status
sa oras ng pagbasa at maaari itong magdagdag ng mga bagong natuklasang libreng modelo sa pagitan ng mga release.
Maaari pa ring lokal na itago ng isang operator ang isang modelo, at ibalik ito mula sa parehong dashboard.
Hindi kailanman binabago sa disk ang mismong baseline na katalogo — tingnan ang
[Mga panuntunan sa pagsasanib ng overlay sa oras ng pagbasa](#read-time-overlay-merge-rules) sa ibaba.

## Pampublikong reader ng anunsyo

Ang generic na reader ng anunsyo ay hiwalay sa feature flag ng Radar. Kinukuha ng Home ng dashboard at
viewer ng Changelog ang pampublikong `news.json` ng repository sa pamamagitan ng simpleng `GET` sa
`NEWS_JSON_URL` (`src/shared/utils/releaseNotes.ts`). Hindi sila nagpapadala ng setting ng Radar, prompt, configuration
ng provider, tala ng paggamit, o lokal na estado ng pag-dismiss.

Ginagamit ng `news.json` ang saradong v2 schema na ipinatutupad ng `parseNewsPayload()`:

- `schemaVersion: 2` at isang nililimitahang koleksyong `items[]`;
- matatag at natatanging mga value ng `id` ng anunsyo;
- tahasang mga field na `active` at ISO `publishedAt`;
- kinakailangang tekstong Ingles na may opsyonal na naka-localize na teksto;
- opsyonal na mga HTTPS link na hindi nangangailangan ng credential at isang icon na nasa allowlist;
- pagpili muna sa pinakabagong aktibong item, fallback ng locale sa Ingles, at lokal na pag-dismiss ayon sa ID.

Pansamantalang tinatanggap ng parser ang dating singular na anyong `{ active, title, message, ... }` upang
makapag-migrate ang mga mas lumang fork nang hindi nasisira ang view ng Changelog. Hindi kumikilos ang mga invalid na feed. Ipinapadala ang entry ng paglulunsad ng Radar
na may `active: false`; ang pagpapalit nito sa `true` ay isang hiwalay na aksyon sa release pagkatapos ng merge at deployment
at hindi nito binabago ang `RADAR_ENABLED` o ang hiwalay na opt-in sa pag-sync ng feed.

## Flag: `RADAR_ENABLED` (naka-off bilang default)

Ang Radar ay mahigpit na kinokontrol mula simula hanggang dulo ng feature flag na `RADAR_ENABLED`
(`src/shared/constants/featureFlagDefinitions.ts`, kategoryang `policies`,
`defaultValue: "false"`).

**Kapag naka-off ang flag, hindi umiiral ang surface:**

- Ang lahat ng endpoint na `/api/radar/*`, kabilang ang mga lokal na pagbasa at pagsulat ng estado ng modelo,
  ay nagbabalik ng `404` bago galawin ang anumang module ng Radar.
- Ang mga screen ng dashboard (`/dashboard/radar`, `/dashboard/radar/setup`,
  `/dashboard/radar/combos`, `/dashboard/radar/offers`, `/dashboard/radar/intel`) ay nagre-render ng
  `notFound()`.
- Ang `getRadarCatalog()` (`src/lib/radar/index.ts`) ay nagbabalik ng hindi nabagong baseline —
  parehong bilang ng entry, parehong mga value, bawat entry ay may tag na `origin: "baseline"` — at hindi kailanman
  binabasa ang cache ng feed.
- Walang anumang network call ng Radar na ginagawa; ang bawat module ng sync ay nagbabalik ng `{ status: "disabled" }`
  bago galawin ang `fetch`.

Isa itong mahigpit na superset gate: ang pag-on sa flag ay magbubukas lamang sa mga _screen_,
wala nang iba. Hindi ito nag-a-upload ng data, hindi nagsisimula ng background sync, at hindi binabago
ang routing o pagpili ng modelo — tingnan ang hiwalay na opt-in sa ibaba.

## HIWALAY na opt-in ang pag-sync ng data — ang pangako sa privacy

Ang pag-on sa `RADAR_ENABLED` ay nagbubukas lamang sa UI. Nangangailangan ang pag-sync ng feed ng pangalawa at
hiwalay na opt-in na nakaimbak sa `radar_settings.opt_in` (`src/lib/db/radar.ts`,
migration na `136_radar_cache_settings.sql`). Sinusuri ng `syncRadar()` ang flag _at_ ang
opt-in bago gumawa ng anumang network call:

```
Naka-off ang flag → { status: "disabled" }   — walang network call
False ang opt-in  → { status: "opt_out" }    — walang network call
```

Kapag parehong naka-on ang mga ito, ganito ang daloy ng sync:

1. `GET <feed base URL>/v1/catalog/latest` na may `x-omniroute-radar-schema: 2` at opsyonal na
   header na `Authorization: Bearer <supporter key>` (tingnan sa ibaba). Bilang default, ginagamit ng mga server ang hiwalay na
   nilagdaang v1 transition artifact kapag wala ang schema header, upang patuloy na
   makatanggap ng mga update ang mas lumang naka-install na client.
2. Isa itong daloy ng application na para lamang sa pag-download, ngunit isa pa rin itong HTTPS request. Tumatanggap ang naka-host na
   infrastructure ng karaniwang metadata ng koneksyon gaya ng source IP. Kapag may naka-configure na supporter
   key, ipinapadala rin ng sync ang key na iyon sa Bearer header upang matukoy ng serbisyo ang
   entitlement. Sa eksaktong revision ng private server na tinukoy sa evidence boundary sa itaas,
   gumagamit ang accounting ng mga feed request ng mga hash ng key, pinagsama-samang paggamit, at isang pinaikling HMAC
   ng IP na umiikot araw-araw para sa manu-manong pagsusuri ng pang-aabuso; hindi pinapanatili ng mga table na iyon ang key o IP sa raw na anyo.
   Hiwalay na mga hangganang operational ang mga access log ng infrastructure at ang naka-encrypt na delivery outbox.
3. Hindi kailanman ipinapadala ng OmniRoute sa serbisyo ng Radar ang mga prompt, response, conversation, credential ng provider, traffic ng modelo,
   uptime, latency, o lokal na configuration ng provider.
4. Bine-verify, bina-validate, at lokal na kina-cache ang response (tingnan ang
   [Modelo ng seguridad](#security-model)). May eksaktong apat na server-side network path ang Radar:
   `syncRadar()` para sa catalog, `syncRadarReferrals()` para sa mga referral, at
   `syncRadarOffers()` / `syncRadarIntel()` para sa mga offer at Intel na para lamang sa supporter.

Ang **supporter key** ay isang opsyonal na Bearer token (`radar_settings.supporter_key`)
na nagbibigay-daan sa serbisyo ng feed na magpasya kung aling tier ang ihahatid (tingnan ang
[Mga tier](#tiers-community-and-live)). Ito ay:

- Nakaimbak na **naka-encrypt habang hindi ginagamit** gamit ang parehong AES-256-GCM `encrypt()`/`decrypt()`
  helper (`src/lib/db/encryption.ts`) na ginagamit para sa mga credential ng provider.
- Itinatakda sa pamamagitan ng `POST /api/radar/settings` (`{ supporterKey: "omr_" + 40 hex chars }`) at
  **hindi kailanman ibinabalik nang buo** — isang naka-mask na anyo ang ibinabalik ng response (`omr_****abcd`).
- Ang pagbabago o pag-clear nito ay sabay-sabay na nagpapawalang-bisa sa mga cache ng catalog, referral, offer, at Intel. Sa
  susunod na sync/pagbasa, tinutukoy sa server-side ang bagong entitlement; ang pag-save ng key ay hindi mismo
  gumagawa ng network request o gumagamit ng single-use activation key.
- Ipinapadala sa serbisyo ng feed bilang Bearer token sa sync GET — walang iba pang impormasyon tungkol sa
  key ang umaalis sa client.

## Mga patakaran sa pag-access at kaligtasan na ipinapakita bago ang pag-opt in

Ipinapakita ng hindi aktibong dashboard ang mga patakarang ito mula sa
`src/app/(dashboard)/dashboard/radar/RadarAccessExplainer.tsx` **bago** ang alinman sa mga pagkilos sa pag-activate.
Ang opisyal na antas ng pag-access ay:

| Antas                      | Pagiging karapat-dapat                                                                            | Access                                                       | Patakaran sa pag-uulit/pag-expire                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Komunidad                  | Sinuman; walang key                                                                               | Kumpletong catalog na naantala nang humigit-kumulang 30 araw | Palaging available; walang pagbibigay                                                    |
| Star + follow              | Bine-verify ng GitHub OAuth ang star sa repository at pag-follow sa may-ari                       | Isang live na pagbasa sa catalog, pagkatapos ay Komunidad    | Isang pagbibigay sa bawat login; hindi na muling ibinibigay                              |
| Contributor Top 10         | Mga posisyong 1–10 sa pinakabagong kumpletong lingguhang ranking                                  | 365 live na araw                                             | Kino-claim kapag hiniling; hindi pinaikli ng pag-alis sa ranking ang iginawad na panahon |
| Contributor Top 100        | Mga posisyong 11–100 sa ranking na iyon                                                           | 90 live na araw                                              | Parehong patakaran sa pag-claim kapag hiniling/idempotent                                |
| Pagbili ng supporter       | Isahang pagbili para sa 6 na buwan, 1 taon, o panghabambuhay                                      | Live na catalog, mga nilagdaang live offer, at Intel         | Walang awtomatikong pag-renew                                                            |
| Donasyon/manu-manong grant | Donasyong sinuri ng may-ari o grant ng may-ari para sa tahasang bilang ng mga araw/panghabambuhay | Parehong live na karapatan para sa iginawad na panahon       | Na-audit at idempotent na grant                                                          |

Ang mga na-merge na PR, commit, at binagong linya ay **mga input lamang sa ranking**. Ang login na wala sa Top 100 ay
hindi makakatanggap ng contributor grant anuman ang bilang ng PR. Ang mga may takdang panahong pagbili, donasyon, panahon ng contributor, at
manu-manong grant ay naiipon mula sa kasalukuyang petsa ng pag-expire; nangingibabaw ang panghabambuhay. Ang pagbabago sa rank ay hindi kailanman
nagpapawalang-bisa o nagpapaikli nang retroaktibo sa panahong naigawad na.

Personal ang hosted license, at ang patakarang nakikita ng user ay isang aktibong installation lamang sa bawat pagkakataon. Ang
release na ito ay **hindi** nagsasabing may hardware lock: hindi nagfi-fingerprint ng hardware o nagpapanatili ng
cryptographic device lease ang OSS sync. Sa na-verify na revision ng private server sa itaas, ang ipinatupad na enforcement
ay validation ng entitlement kasama ang isang signal para sa manu-manong pagsusuri kapag nakita ang parehong live key mula sa ikaapat na
magkaibang IP sa loob ng 24 na oras. Hindi kailanman awtomatikong bina-block o binabawi ng signal na iyon ang isang key. Sa recovery,
binabawi at pinapalitan ang nawalang key habang pinananatili ang kasalukuyang expiration; hindi nito muling sinisimulan ang
binili o iginawad na panahon.

Manu-manong kino-curate ang mga live offer at maaaring magbago o mag-expire ang mga ito. Binabanggit din ng screen sa pag-opt in ang eksaktong
hangganan ng privacy: dina-download ang nilagdaang metadata ng catalog/referral; bukod dito, ina-unlock ng valid na key ang
mga nilagdaang offer at Intel; nakakarating sa hosted service ang Bearer key at karaniwang metadata ng koneksyon;
hindi nakakarating ang mga prompt, tugon, pag-uusap, credential ng provider, model traffic, uptime, latency, at lokal na
configuration ng provider.

## Pagkuha ng supporter key

Ang activation screen (`/dashboard/radar`) ay nagli-link sa dalawang flow para sa **pagkuha** ng
supporter key. Ang OSS repo mismo ay hindi kailanman nagbibigay nito, hindi nagpapatakbo ng payment code, at
**hindi kailanman nagsasaad ng presyo** — ang pagpepresyo ay ganap na pinagpapasyahan at ipinapakita sa mga
destination page, hindi sa repo na ito (spec decision D14).

- **"Isa akong contributor"** — binubuksan ang `RADAR_CONTRIBUTOR_CLAIM_URL` (default
  `https://radar.omniroute.online/auth/github`), isang GitHub OAuth claim flow na naka-host sa
  pribadong Radar server. Sinusuri nito ang pinakabagong kumpletong lingguhang ranking: makakatanggap ang Top 10 ng 365 araw
  at ang mga nasa posisyong 11–100 ay makakatanggap ng 90 araw. Sa labas ng Top 100, hindi kailanman nagbibigay ng access ang bilang ng PR; sa halip,
  sinusuri ng flow ang hiwalay na pang-isahang-gamit na antas ng star + follow.
- **"Suportahan ang proyekto"** — binubuksan ang `RADAR_SUPPORTER_PLANS_URL` (default
  `https://radar.omniroute.online/planos`), ang naka-host na page para sa minsanang 6 na buwan, 1 taon, at
  panghabambuhay na mga opsyon. Wala pa ring ipinapakitang halagang salapi ang OSS page.

Ang parehong URL ay nire-resolve sa server-side (`src/lib/radar/links.ts`, kaparehong env-override
pattern ng `RADAR_FEED_URL`) at ipinapasa sa dashboard sa pamamagitan ng kasalukuyang
`GET /api/radar/settings` response (`contributorClaimUrl`, `supporterPlansUrl`) — hindi
direktang binabasa ng client component ang `process.env`.

| Var                           | Layunin                                                                                        |
| ----------------------------- | ---------------------------------------------------------------------------------------------- |
| `RADAR_CONTRIBUTOR_CLAIM_URL` | Ino-override ang contributor-claim URL (default `https://radar.omniroute.online/auth/github`). |
| `RADAR_SUPPORTER_PLANS_URL`   | Ino-override ang supporter-plans URL (default `https://radar.omniroute.online/planos`).        |

### Pagbawi ng nawalang supporter key

Ang recovery entry point ng naka-host na serbisyo ay `https://radar.omniroute.online/recover`; naka-link din ito
mula sa plans page. Ganap na nananatili sa labas ng OSS client ang recovery dahil hindi kailanman natatanggap ng lokal na
installation ang e-mail ng bumili/contributor at hindi nito mabubuong muli ang raw key mula
sa mga naka-encrypt na setting nito.

1. Isumite ang e-mail na nauugnay sa key. Ibinabalik ng serbisyo ang parehong tinanggap na page mayroon man o walang
   mare-recover na license, kaya hindi inililista ng form ang mga account.
2. Kung kwalipikado, magpapadala ang delivery worker ng panandalian at pang-isahang-gamit na link. Kapag binuksan ito, agad nitong inililipat
   ang token sa isang pansamantalang naka-encrypt na `HttpOnly`/`Secure` cookie at nagre-redirect sa malinis na
   `/recover` URL; walang token, e-mail, lumang key, o pamalit na key ang page.
3. Kumpirmahin ang pagbawi. Babawiin ng pribadong serbisyo ang dating key, gagawa ng pamalit na may
   parehong plan/expiration, at ipipila ito para sa e-mail sa iisang transaction. Hindi kailanman
   ibinabalik sa browser ang pamalit.
4. I-paste ang pamalit sa `/dashboard/radar`. Dapat nang bumaba sa `community` ang lumang key; ang
   pamalit ay dapat magresulta sa isang beripikadong `live` sync. Dapat mabigo ang muling pagbubukas sa parehong recovery link
   gamit ang generic na invalid/expired response.

Maaaring nasa code ang naka-host na recovery route at mail worker ngunit hindi pa rin available sa isang partikular na
deployment. Huwag ituring na production-ready ang flow hangga't hindi pa nade-deploy ang server, hindi pa nako-configure ang delivery
provider gamit ang isang kontroladong recipient, at hindi pa nasusubukan ang buong pang-isahang-gamit na link.

Kapag mayroon nang key ang isang bisita (`omr_` + 40 hex chars), ang activation screen
(`src/app/(dashboard)/dashboard/radar/page.tsx`) ay may paste-key input bilang pangunahing
path: ang pag-paste ng key at pagsusumite ay nagpapadala ng `POST /api/radar/settings`
(`{ optIn: true, supporterKey }`) sa iisang call — ang pag-paste ng key ay sabay na nagse-set nito at nag-o-opt in,
kaya naa-unlock ang screen. Sinusuri muna sa client-side ang format (`omr_` + 40 hex chars)
gamit ang nakabahaging `isValidSupporterKeyFormat()` helper (`src/lib/radar/supporterKey.ts`)
bilang kaginhawahan sa UX; ang Zod schema ng server pa rin ang awtoritatibong pagsusuri sa alinmang kaso. Kapag
naitakda na ang key, ipinapakita ng activation screen ang naka-mask na anyo (`supporterKeyMasked` mula sa
`GET /api/radar/settings`) sa halip na isang walang-lamang input, kasama ang isang "palitan ang key" na control para
mag-paste ng bago — hindi kailanman muling ipinapakita ang raw key. Ang dalawang claim/plans button sa itaas
pa rin ang paraan upang _makakuha_ ng key sa simula; sa input na ito ito ina-activate ng isang operator
na mayroon na nito.

### End-to-end na activation at ginabayang setup

May sadyang makitid na boundary ang pribadong feed service at ang OSS client na ito: ang serbisyo
ang nagbibigay at nagva-validate sa supporter key, habang ine-encrypt ng lokal na OmniRoute installation ang key,
sini-sync ang mga nilagdaang artifact sa server-side, at ginagabayan ang provider setup. Ang pagkakasunod-sunod ng assisted validation ay:

1. Kumuha ng bagong ibinigay o na-recover na key mula sa contributor claim, plans/checkout, proseso ng
   recovery, o isang awtorisadong operator ng pribadong server. Huwag i-paste ang raw key sa mga log,
   screenshot, komento sa issue, o command-line argument.
2. I-enable ang feature flag na `RADAR_ENABLED` sa lokal na installation ng OmniRoute. Ilalantad nito ang UI
   ngunit mananatili itong hindi aktibo sa network hanggang sa ma-save ang hiwalay na pag-opt in.
3. Buksan ang `/dashboard/radar`, i-paste ang key, at i-activate. Magpapadala ang browser ng isang lokal na
   `POST /api/radar/settings` na may `{ optIn: true, supporterKey }`; lokal na ie-encrypt ang key at
   `omr_****<last4>` lamang ang laman ng response.
4. Hayaang patakbuhin ng activation screen ang catalog sync nito, o piliin ang **I-sync ngayon**. Tiyaking
   ipinapakita ng page ang `live`, isang bersyon ng feed, at oras ng pag-fetch. Para sa isang authenticated na lokal na diagnostic,
   iniuulat ng `GET /api/radar/status` ang katayuan ng pag-opt in/presensya ng key at ang apat na estado ng cache nang hindi ibinabalik
   ang key. Maaaring tahasang i-refresh ng `POST /api/radar/sync-all` ang catalog, referrals, offers, at Intel.
5. Buksan ang `/dashboard/radar/setup?provider=<provider>`. Sundan ang URL ng credential na pagmamay-ari ng provider,
   piliin ang **Magdagdag ng API key**, i-save gamit ang tunay na form ng provider, bumalik sa guide, at patakbuhin ang
   **Subukan ang koneksyon**. Ginagamit ng guide ang karaniwang `/api/providers` at
   `/api/providers/<connection-id>/test` na mga route; hindi ito gumagawa ng hiwalay na Radar credential.
6. Buksan ang `/dashboard/radar/combos` kapag aktibo na ang hindi bababa sa dalawang compatible na koneksyon sa provider.
   Suriin ang iminungkahing family at gawin ang combo sa pamamagitan ng umiiral na combo API. Nananatiling magkahiwalay na mga signed cache na live-only ang Offers at
   Intel at maaaring suriin sa kani-kanilang nakalaang Radar page.
7. I-reload ang `/dashboard/radar` at ang setup page. Dapat manatili pagkatapos ng reload ang pag-opt in, masked-key na estado, na-verify na cache, naka-save na
   koneksyon sa provider, at test action. Kumuha lamang ng ebidensya kapag hindi na nakikita ang
   raw key at credential ng provider.

Ang pag-save ng key ay hindi sapat na patunay ng live entitlement. Ang patunay ay ang kombinasyon ng resulta ng
`GET /v1/license/check` ng pribadong serbisyo, ang inihahaing `live` tier ng OSS catalog, isang na-verify na signed
cache, at ang tunay na daloy ng koneksyon/pagsubok sa provider. Ligtas na ibinababa ng invalid, expired, o revoked na key
ang catalog sa `community`; hindi ito dapat iulat bilang matagumpay na live-key validation.

### Link ng pribadong admin panel

Opsyonal na idinaragdag ng `RADAR_ADMIN_URL` ang **Radar Admin ↗** kaagad pagkatapos ng Radar item para sa user
sa seksyong Costs ng sidebar. Sadyang wala itong default: kapag hindi naka-set o invalid ang variable,
walang admin item at pribadong URL ang static sidebar, command palette, at screen para sa pag-customize ng sidebar.

Nire-resolve ang value sa server-side at ipinapasa sa pamamagitan ng management-authenticated na
`GET /api/settings` response para lamang sa isang authenticated na dashboard session, o sa pinagkakatiwalaang
loopback owner habang nagsasagawa ng lokal na no-login bootstrap. Hindi ito natatanggap ng CLI, internal-service, at manage-scope API-key
authentication. Muling vina-validate ng browser ang response bago buuin ang external link,
na bumubukas gamit ang `noopener noreferrer`.

Gumamit ng credential-free na HTTPS tunnel/tailnet URL. Tinatanggap lamang ang plain HTTP para sa isang loopback SSH
forward gaya ng `http://127.0.0.1:9351`; ang ibang scheme, naka-embed na credential, malformed na URL, at
remote HTTP destination ay ligtas na tinatanggihan at iniiwang hindi aktibo ang navigation.

## Modelo ng seguridad

### Lagdang Ed25519 sa eksaktong mga byte

Nilalagdaan gamit ang Ed25519 ang payload ng feed. Bine-verify ng `verifyFeedBytes()`
(`src/lib/radar/verify.ts`) ang lagda sa **eksaktong mga byte ng tugon**
na natanggap sa network — hindi kailanman muling sini-serialize ang payload bago ang pag-verify, kaya hindi
maaaring palihim na mapawalang-bisa o malampasan ng byte-for-byte na muling pag-encode ang pagsusuri sa lagda.
Kapag nabigo ang pag-verify (`invalid_signature`), ihihinto ang pag-sync bago pa man
ma-parse o ma-cache ang payload.

### Naka-pin na public key + rotation

Naka-pin ang public key para sa pag-verify sa `src/lib/radar/pinnedKeys.ts`
(`PINNED_FEED_PUBLIC_KEYS`), isang array upang maidagdag ang isang bagong key sa unahan bago ang isang
rotation habang nananatiling balido ang mga lumang naka-cache na feed na nilagdaan gamit ang dating key hanggang sa
muling ma-sync ang mga ito.

### Mga env override na angkop sa mga fork

Dalawang env var ang nagbibigay-daan sa mga fork at self-hoster na ituro ang client sa sarili nilang feed sa halip na
sa default na serbisyo ng OmniRoute — tingnan ang
[Paano mag-self-host ng feed](#how-to-self-host-a-feed) sa ibaba:

| Var                 | Layunin                                                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `RADAR_FEED_URL`    | Ino-override ang base URL ng feed (default na `https://radar.omniroute.online`).                                             |
| `RADAR_FEED_PUBKEY` | Ino-override ang naka-pin na public key (base64-DER SPKI o PEM), at pinapalitan ang built-in array ng nag-iisang key na ito. |

### Pinakamababang bersyon

Tinatanggihan ng `syncRadar()` ang isang na-download na feed kung ang `version` nito ay hindi
mahigpit na mas bago kaysa sa kasalukuyang naka-cache na bersyon (`compareVersions()`, paghahambing ng may-tuldok na
`YYYY.MM.DD.n`) — `{ status: "stale" }`. Pinipigilan nito ang isang nakompromiso o maling na-configure na feed endpoint na
ibalik ang isang client sa mas luma at ibang pagkakalagda na payload.

### Dalawang petsa, at kung bakit parehong pinapanatili

May dalawang magkaibang petsa ang isang naka-cache na feed, at ang posibilidad na mapagkamalan ang isa bilang isa pa ang mismong dahilan ng
pagpapanatili sa pareho:

| Field         | Pinagmulan               | Sinasagot                                         |
| ------------- | ------------------------ | ------------------------------------------------- |
| `generatedAt` | nilagdaang body ng feed  | kung gaano kaluma ang **data**                    |
| `fetchedAt`   | orasan ng install na ito | kung kailan ito **na-download** ng install na ito |

Ang isang feed na na-fetch ilang minuto lang ang nakalipas ay maaaring maglaman ng ilang linggo nang lumang mga bilang, kaya hindi
masasabi ng `fetchedAt` lamang sa isang operator kung mas bago ang overlay kaysa sa baseline na pinapatungan nito. Parehong
pinapanatili sa `radar_feed_cache`, ibinabalik ng `getRadarCatalog().meta`, at iniuulat
nang magkahiwalay ng `GET /api/radar/status`. Ang isang row na na-cache bago umiral ang column na `generated_at`
(migration 163) ay binabasa bilang `null` — nananatiling hindi alam ang hindi alam sa halip na
hiramin ang oras ng pag-fetch. Pinanatili ng `radar_referrals_cache` ang sarili nitong `generated_at` mula pa noong
migration 142.

`version` ang inihahambing ng pinakamababang bersyon sa itaas, hindi ang alinman sa mga petsa.

May natitira pang dalawang kakulangan, at kapwa sinadya: `Last fetched` lamang ang ipinapakita pa rin ng dashboard, kaya ang pagpapakita
ng petsa ng build doon ay nangangailangan ng bagong label (at ng 41 locale entry nito); at walang pinapanatiling petsa ng build
ang mga cache ng offers at intel, kahit mayroon nito ang mga schema ng kanilang feed — kaya hindi isinasama ng `GET
/api/radar/status` ang field para sa dalawang iyon sa halip na mag-ulat ng `null`
na mababasa bilang "hindi alam".

### Pag-validate ng schema

Pina-parse at vina-validate ang mga na-download na byte gamit ang `RadarFeedSchema`
(`src/lib/radar/feedSchema.ts`, isang Zod schema) **pagkatapos** ma-verify ang lagda. Kapag
hindi tumugma ang schema, ibinabalik ang `{ status: "invalid_schema" }` at hindi
binabago ang cache. Bilang pag-iingat, muling vina-validate ang naka-cache na payload sa bawat pagbasa
(`getRadarCatalog()`) — bumabalik sa baseline ang isang sira o mano-manong inedit na cache row sa halip na
ihatid ito.

### Limitasyon sa laki ng tugon (10 MB)

Nagpapatupad ang `syncRadar()` ng **mahigpit na limitasyong 10 MB** sa body ng tugon ng feed — ang nilagdaang
feed ay isang JSON document na nasa sukat na KB, kaya anumang lalampas dito ay nagpapahiwatig ng maling na-configure o
mapaminsalang `RADAR_FEED_URL` (o isang upstream na naghahatid ng walang-kuwentang data), hindi ng isang lehitimong catalog.
May dalawang antas ang pagpapatupad:

1. Nilalaktawan ng isang paunang pagsusuri sa `Content-Length` ang pagbabasa sa buong body kapag ang
   header ay nagdedeklara na ng halagang lampas sa limitasyon.
2. Ipinapatupad ng isang pagsusuri sa patuloy na kabuuan habang binabasa ang body ang limitasyon kahit na
   wala ang `Content-Length` o mas mababa rito ang ipinapakitang tunay na laki — hindi kailanman
   pinagkakatiwalaan nang mag-isa ang header. Ang pag-concatenate sa mga naipong chunk ay nagpapanatili sa eksaktong
   mga byte na kailangan para sa kasunod na pagsusuri sa lagdang Ed25519.

Kapag nalampasan ang limitasyon, ibinabalik ang `{ status: "too_large" }` at hindi binabago ang cache,
alinsunod sa parehong hindi mapanirang pattern gaya ng bawat iba pang kabiguan sa pag-sync
(`invalid_signature`, `invalid_schema`, `stale`).

## Mga tier: `community` at `live`

Ang feed schema ay may field na `tier: "community" | "live"`, na tinutukoy **sa server-side**
ng feed service batay sa request (pagkakaroon at pagiging valid ng supporter key)
— hindi kailanman ang client ang nagpapasya ng sarili nitong tier.

- **`community`** — ang libreng catalog na nahuhuli nang humigit-kumulang 30 araw sa
  pinakabagong data. Ito ang natatanggap ng request na hindi authenticated o may invalid na key.
- **`live`** — ang pinakabagong catalog, na ibinibigay sa mga request na may valid na supporter
  key.

**Kapag invalid o expired ang supporter key, ibinababa ito sa `community` — hindi ito kailanman
isang error.** Tanging mga pagkabigo sa signature/schema/version (lahat ay
nare-recover, at walang nakamamatay na epekto sa naka-cache na state) ang itinatangi ng sync path mula sa matagumpay na `{ status:
"updated", version, tier }`. Walang error path na partikular sa tier na kailangang
pangasiwaan ng client.

### Ang inihahaing tier ay nagmumula sa response header, hindi sa signed body

Ang field na `tier` ng **body** ng signed feed ay palaging `"live"` — nagpapadala ang feed service ng
**dalawang signed artifact sa bawat version**: kasama sa live ang mga kasalukuyang campaign, samantalang
hindi kasama ang mga ito sa community. Nilalagdaan ang bawat artifact ayon sa sarili nitong eksaktong bytes. Hindi pa rin
ang body ang nagsisilbing batayan ng desisyon sa entitlement; ang tier na aktuwal na pinili para sa isang request ay nasa
**`x-omniroute-feed-tier` response header**, na tinutukoy sa server-side mula sa
`Authorization` key ng request.

Ang `syncRadar()` (`src/lib/radar/sync.ts::parseServedTierHeader()`) ang tanging lugar
na tumutukoy sa tier na dapat pagkatiwalaan ng client:

1. I-parse ang `x-omniroute-feed-tier` gamit ang `RadarTierSchema` (Zod) — ang header na wala, o
   value na hindi eksaktong `"community"` o `"live"`, ay itinuturing na **hindi
   naroroon** (hindi kailanman pinagkakatiwalaan at inilalagay nang walang pagbabago sa cache/UI; saklaw din nito ang mga mas lumang feed
   server na nauna sa header).
2. Bumalik sa field na `tier` ng signed body (palaging `"live"`) kapag walang
   nakuha sa hakbang 1.
3. Ang natukoy na tier ang kina-cache at ibinabalik bilang `{ status: "updated",
version, tier }` — ito ang value na ipinapakita ng dashboard, at hindi kailanman ang raw na field ng
   body.

## Mga panuntunan sa read-time overlay merge

Pinagsasama ng `applyFeed()` (`src/lib/radar/applyFeed.ts`) ang naka-cache na feed **sa ibabaw** ng
static baseline sa **oras ng pagbasa**, sa loob ng `getRadarCatalog()`. Hindi kailanman binabago ang baseline array
(`FREE_MODEL_BUDGETS`) — isang bagong `MergedEntry[]` ang kinukuwenta sa bawat
pagtawag.

Apat na panuntunan, ayon sa pagkakasunod-sunod ng prayoridad:

1. **Hindi kailanman ino-overwrite ng feed ang isang local override.** Bawat field: kung
   na-customize ng operator ang isang field sa entry (`localOverrides` map, na may key na `provider:modelId`),
   nilalaktawan ang value ng feed para sa partikular na field na iyon — mananaig ang value ng operator.
2. **Dini-disable ng `enabled: false` ang entry, nang may provenance.** Ang feed entry na nag-o-off
   sa isang entry ay nagtatakda ng `enabled: false` at `disabledBy: "radar"` sa merged result,
   upang maipaliwanag ng UI _kung bakit_ naging disabled ang isang entry mula sa pagiging available.
3. **Nananatiling hindi nagbabago ang entry na idinagdag ng user ngunit wala sa feed.** Ang mga entry na
   nasa baseline lamang (o idinagdag nang lokal) at walang katumbas na feed
   entry ay ipinapasa nang walang pagbabago.
4. **Hindi kailanman muling binubuhay ang isang tombstoned na entry.** Kung tahasang nag-delete ang operator ng
   entry (`tombstones` set), hindi ito ibabalik ng muling pagdaragdag ng feed sa `provider:modelId` na iyon sa mas bagong
   version.

Ang mga nae-edit na field at tombstone ay pine-persist sa
`radar_local_model_state` (migration `153_radar_local_model_state.sql`). Kino-convert ng pampublikong DB
adapter (`src/lib/db/radar.ts`) ang mga row na iyon sa `localOverrides` map at
`tombstones` set na ginagamit ng `applyFeed()`; nilo-load ng production `getRadarCatalog()` ang state na iyon
pagkatapos pumasa sa mga gate para sa flag, cache, at schema. Tanging `displayName` at `enabled` ang
maaaring i-edit ng operator. Hindi maisusulat sa pamamagitan ng surface na ito ang provider/model identity, feed provenance, quota, capabilities, ToS,
at setup data.

Nagbibigay ang dashboard ng apat na lokal na action:

- Binabago ng **Edit** ang lokal na display name at enabled state.
- Nililinis ng **Reset local changes** ang parehong nae-edit na field nang hindi binabago ang tombstone.
- Lumilikha ang **Hide** ng tombstone, upang hindi muling malikha ng mga susunod na feed update ang row.
- Inaalis ng **Restore** ang tombstone; mananatiling may bisa ang anumang override na hiwalay na na-save.

Nananatiling safety exception ang `enabled: false` ng feed: nananaig ito sa lumang local na
`enabled: true`, pinananatiling disabled ang merged entry, at itinatala ang `disabledBy: "radar"`.

Gumagamit ang mga publication ng catalog ng `schemaVersion: 2`. Ang `contextWindow` at bawat isa sa `tools`, `vision`, at
`thinking` ay hiwa-hiwalay na `number | null` / `boolean | null`: ang `null` ay nangangahulugang hindi alam, samantalang
ang `false` ay nangangahulugang tahasang sinasabi ng opisyal na source ng provider na nakumpirma ng D16 na wala ang capability.
Hindi kailanman direktang ginagawang feed facts ang mga internal na flag ng OmniRoute registry/model-spec. Tumatanggap pa rin
ang client ng mga v1 snapshot; dahil gumamit ang lumang builder ng `false` bilang placeholder para sa kawalan, ang v1 `false` ay
ino-normalize bilang hindi alam habang nananatiling factual ang v1 `true`. Nagfa-fail closed ang mga hindi kilalang schema version at
nananatiling available ang huling valid na cache. Ang bawat v2 model na may non-null na context/capability ay dapat may
credential-free na HTTPS `metadataEvidenceUrls[]`; kung wala, mabibigo ang schema validation at hindi papalitan ang cache.
Ipinapakita ng catalog table ang lahat ng tatlong state bilang `✓`, `✕`, at `?`.

### Mga guided combo at MCP access

Nananatili ang mga nakumpirmang value ng `familyId` sa read-time overlay at ginagamit ng purong
`buildRadarComboSuggestions()` module (`src/lib/radar/comboSuggestions.ts`). Iminumungkahi lamang ang isang family
kapag may active na connection ang hindi bababa sa dalawang magkaibang provider at inilalantad nila ang eksaktong curated model
ID. Nagfa-fail closed ang mga disabled na model, inactive na provider, nawawalang model ID, singleton family, at malabong
alias/prefix match. Ginagamit ng mga mungkahi ang kasalukuyang `priority` strategy, kung saan inuuna ang
pinakamalaking nauulit na buwanang budget; nililikha lamang ang mga ito ng UI sa pamamagitan ng `POST /api/combos`.

Ang guided UI ay nasa `/dashboard/radar/combos`. Binabasa lamang nito ang mga lokal na endpoint na
`GET /api/radar/catalog` at `GET /api/combos/builder/options`. Hindi ito kailanman nagpapasimula ng Radar sync,
nagbabasa ng mga kredensyal ng provider, o direktang nagsusulat sa combo database.

Mababasa ng mga MCP client ang parehong lokal na projection gamit ang `omniroute_radar_catalog` (`read:radar`). Ang
mga opsyonal na filter na `provider`, `familyId`, at `enabledOnly` ay sinusuri pagkatapos ng isang lokal na
pagbasa sa `GET /api/radar/catalog`. Kasama sa saradong output nito ang metadata ng catalog pati ang provider/model,
display name, `familyId`, quota, mga capability, enabled state, origin, at `disabledBy`; hindi kailanman ibinabalik ang mga setup URL,
hakbang, koneksyon, e-mail address, key, at referral data. Read-only ang tool na ito
at hindi nito kailanman ini-invoke ang `/api/radar/sync`.

### Mga marker ng pinagmulan

Ang bawat pinagsamang entry ay may field na `origin` na nire-render ng UI bilang badge:

- `"baseline"` — hindi binago mula sa static release catalog.
- `"radar"` — isa o higit pang field ang na-refresh ng feed.
- `"local"` — may kahit isang lokal na override ang operator sa entry na ito (ang mga lokal na
  override ang palaging nangingibabaw sa feed ayon sa rule 1, anuman ang sinasabi ng feed).

## Mga lokal na surface — hindi kailanman proxy ng feed

Sinusuportahan ng mga lokal na pamilya ng route ng Radar sa ibaba ang UI sa ilalim ng `src/app/api/radar/`:

| Route                          | Paraan | Layunin                                                                                                                                      |
| ------------------------------ | ------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/radar/catalog`           | GET    | Ibinabalik ang pinagsamang catalog (`getRadarCatalog()`) mula sa lokal na cache.                                                             |
| `/api/radar/sync`              | POST   | Pinaandar ang `syncRadar()` sa server-side; ibinabalik ang nagresultang status.                                                              |
| `/api/radar/settings`          | GET    | Ibinabalik ang `{ optIn, hasSupporterKey, supporterKeyMasked }` — hindi kailanman ang raw key.                                               |
| `/api/radar/settings`          | POST   | Itinatakda ang opt-in at/o ang (naka-encrypt na) supporter key.                                                                              |
| `/api/radar/referrals`         | GET    | Ibinabalik ang `{ fixed, campaigns, tier }` mula sa lokal na cache — tingnan ang [Mga referral link](#referral-links-free-credits) sa ibaba. |
| `/api/radar/offers`            | GET    | Ibinabalik ang mga aktibong offer mula sa na-verify na lokal na live cache; hindi kailanman ibinabalik ang supporter key.                    |
| `/api/radar/offers/sync`       | POST   | Pinaandar ang server-side at live-key-only na pipeline na `syncRadarOffers()`.                                                               |
| `/api/radar/intel`             | GET    | Ibinabalik ang na-verify na lokal na live Intel kasama ang isang boolean para sa pagkilala sa supporter; hindi kailanman identity o key.     |
| `/api/radar/intel/sync`        | POST   | Pinaandar ang server-side at live-key-only na pipeline na `syncRadarIntel()`.                                                                |
| `/api/radar/status`            | GET    | Ibinabalik ang read-only na status ng mga lokal na setting/cache para sa catalog, mga referral, mga offer, at Intel, nang walang mga secret. |
| `/api/radar/sync-all`          | POST   | Pinapatakbo ang lahat ng apat na server-side sync module at nagbabalik ng hiwalay na status para sa bawat feed.                              |
| `/api/radar/local-model-state` | GET    | Inililista ang mga naka-persist na override at tombstone para sa mga kontrol na edit/restore.                                                |
| `/api/radar/local-model-state` | PATCH  | Itinatakda o nililinis ang mga na-validate na override field na `displayName`/`enabled`.                                                     |
| `/api/radar/local-model-state` | PUT    | Gumagawa o nag-aalis ng tombstone gamit ang `{ provider, modelId, tombstoned }`.                                                             |
| `/api/radar/local-model-state` | DELETE | Nililinis ang mga nae-edit na override field habang pinapanatili ang anumang tombstone.                                                      |

**Mahigpit na tuntunin: hindi kailanman nagsisilbing proxy ng feed service ang mga route na ito.** Nakikipag-ugnayan lamang ang browser
sa lokal na OmniRoute server. Ang apat na module na nakikipag-ugnayan sa Radar service ay
`src/lib/radar/sync.ts` (catalog), `src/lib/radar/referralsSync.ts` (mga referral), at
`src/lib/radar/offersSync.ts` (mga offer), kasama ang `src/lib/radar/intelSync.ts` (Intel); lahat ay tumatakbo
sa server-side, hindi kailanman sa client-side. Dahil dito, ganap na hindi naisasama
ang feed URL at anumang supporter key sa network traffic na nakikita ng client.

Nagbabalik ang lahat ng Radar endpoint ng `404` kapag naka-off ang `RADAR_ENABLED` (tingnan ang
[Flag](#flag-radar_enabled-default-off) sa itaas), at ipinapadaan ang mga route error response sa
`buildErrorBody()`/`sanitizeErrorMessage()` alinsunod sa tuntunin sa pag-sanitize ng error sa buong repo
(`docs/security/ERROR_SANITIZATION.md`).

### Authentication

Nangangailangan ang lahat ng Radar endpoint ng authentication sa pamamagitan ng `isAuthenticated()`
(`src/shared/utils/apiAuth.ts`) — isang dashboard session cookie o isang management-scoped
API key, ang parehong gate na nagpoprotekta sa iba pang bahagi ng `/api/settings/*`. Ang flag-off na
pagsusuri para sa `404` ay palaging tumatakbo **bago** ang pagsusuri sa auth, kaya nananatiling byte-identical
ang isang installation na naka-off ang `RADAR_ENABLED` (walang auth prompt para lamang malaman na hindi umiiral ang surface);
kapag naka-on na ang flag, makakatanggap ang isang hindi authenticated na request ng `401` bago ang anumang pagbasa o
pagsulat sa DB. Hindi kailanman ibinabalik ng `GET /api/radar/settings` ang raw supporter key anuman ang
auth state — tanging ang masked na anyo at isang boolean na `hasSupporterKey`.

## Mga alok para sa supporter

Gumagamit ang mga alok ng sarili nilang nilagdaang artifact, `GET /v1/offers/latest`, at hindi kailanman nakikibahagi sa cache ng catalog o mga referral. Nangangailangan ang endpoint ng server ng wastong aktibong Bearer key ng supporter; walang fallback para sa community. Samakatuwid, humihinto ang `syncRadarOffers()` bago kumonekta sa network kapag naka-off ang feature flag, hindi nag-opt in ang operator, o walang naka-configure na supporter key.

Pagkatapos ng matagumpay na GET, bine-verify ng client ang Ed25519 signature sa eksaktong bytes ng tugon, vina-validate ang `RadarOffersFeedSchema`, inaatasang parehong magsaad ng `live` ang nilagdaang body at ang `x-omniroute-feed-tier` header, nagpapatupad ng dotted version na talagang mas bago, at saka lamang atomikong pinapalitan ang `radar_offers_cache` (migration `144_radar_offers_cache.sql`). Nalalapat din ang parehong 10 MB na limitasyon sa header at stream na ginagamit ng iba pang feed. Pinananatili ng lahat ng pagkabigo sa signature, schema, tier, replay, laki, HTTP, at network ang huling na-verify na cache.

Sinusuportahan ng saradong anyo ng alok ang tatlong maihahambing na uri ng benepisyo: porsiyento sa basis points, credit sa pinakamaliit na unit ng currency, o mga araw ng trial. Dapat magsama ang isang alok ng partner ng pampublikong baseline na may kaparehong uri, at dapat na talagang mas malaki ang benepisyo nito; walang baseline ng partner ang mga opisyal na alok. Dapat ay HTTPS at walang credential ang mga URL. Bilang pag-iingat, muling vina-validate ng `getRadarOffers()` ang naka-cache na payload at sinasala ang mga nag-expire na entry sa bawat lokal na pagbasa; muling sinasala ng `/dashboard/radar/offers` ang mga nag-expire bago mag-render, gumagamit ng tekstong Portuguese kapag available at English bilang fallback, at tahasang nilalagyan ng label ang mga alok ng partner.

Mga lokal na route lamang ang tinatawagan ng browser: binabasa nito ang naka-mask na snapshot ng mga setting, hinihiling sa `POST /api/radar/offers/sync` na mag-refresh sa panig ng server, at pagkatapos ay binabasa ang `GET /api/radar/offers`. Kapag walang key, ipinapakita nito ang mga kasalukuyang link para sa contributor at suporta sa halip na subukang humiling ng feed. Bumubukas ang mga panlabas na link ng alok sa bagong tab gamit ang `noopener noreferrer`. Walang inilalantad na `radar_offers` MCP tool sa release na ito.

## Radar Intel, badge ng supporter, at CLI

Ang Intel ay isang nilagdaang artifact sa `GET /v1/intel/latest`. Tinatanggap lamang ng saradong `RadarIntelFeedSchema` ang mga ranking na ELO na pagmamay-ari ng Radar at hinango ng pribadong curator mula sa mga nakumpirmang paghahambing, at ang mga makatotohanang delta sa edad/bilang ng catalog na hinango mula sa mga nilagdaang snapshot ng catalog. Nakapirmi ang metodolohiya sa paunang rating na 1000 at K=32. Wasto ang isang walang-lamang ranking kapag walang nakumpirmang paghahambing; hindi kailanman gumagawa ang client ng artipisyal na ranking.

Inilalapat ng `syncRadarIntel()` ang parehong server-side Bearer, 30-segundong timeout, 10 MiB na limitasyon sa stream, pag-verify ng Ed25519 sa eksaktong bytes, mahigpit na schema, kinakailangang `live` na body/header, minimum na bersyon, at pagpapanatili ng huling mahusay na cache gaya ng sa mga alok. Pagkatapos ma-persist ang isang na-verify na live snapshot, hinahango ng client ang `radar:<sha256(supporter key)>`, iniimbak lamang ang one-way na identity na iyon, at naglalabas ng nakalaang `radar_supporter` recognition event. Idempotent ang `radar-supporter` badge nito at nagbibigay ng zero XP; hindi nito kailanman ina-update ang mga leaderboard o muling ginagamit ang `token_share`. Nagre-render lamang ang `/dashboard/radar/intel` ng badge mula sa na-verify na metadata ng lokal na cache.

Inilalantad ng CLI ang `omniroute radar status` at `omniroute radar sync`. Parehong nakikipag-ugnayan lamang ang mga ito sa lokal na OmniRoute API. Nagsasagawa ang `status` ng read-only na `GET /api/radar/status`; nagpapadala ang `sync` ng isang `POST /api/radar/sync-all` at nagpi-print ng resulta para sa bawat feed. Hindi binabasa, tinatanggap, o pini-print ng alinmang command ang supporter key, at hindi rin direktang kumokonekta ang mga ito sa serbisyo ng Radar.

## Mga referral link (libreng credits)

Inihahatid ang mga referral link mula sa isang **standalone at palaging napapanahong** feed —
`GET /v1/referrals/latest` — na hiwalay sa catalog feed. Sinadya ito: ang
catalog feed sa community tier ay isang snapshot na maaaring hanggang 30 araw na ang tanda, kaya ang
isang referral link na kinuha rito ay dating nahuhuli sa aktuwal na listahan ng mga link ng server nang gayunding
katagal (ang isang bagong idinagdag na referral ay maaaring hindi makarating sa isang free/community user nang hanggang isang buwan).
Inaalis ng referrals feed ang pagkaantalang iyon sa pamamagitan ng pag-sync sa sarili nitong mas maikling cadence.

```ts
// Katawan ng tugon ng GET /v1/referrals/latest (nilagdaan gamit ang Ed25519, parehong naka-pin na key gaya ng
// sa catalog feed):
{
  feed: "omniroute-radar-referrals",
  schemaVersion: 1,
  generatedAt: string,           // ISO — deterministic: max(updatedAt) sa lahat ng referral
                                  // link, kaya ang dalawang magkaparehong request ay gumagawa ng eksaktong
                                  // parehong nilagdaang bytes/signature
  referrals: {
    fixed: RadarReferral[],      // naroroon sa LAHAT ng tier, kabilang ang no-auth/community
    campaigns: RadarReferral[],  // nilalagyan lamang para sa isang valid at aktibong (supporter) Bearer
                                  // key; [] ang natatanggap ng mga request na no-auth/expired-key
  },
}
// RadarReferral = { provider, url, kind: "fixo" | "campanha", validUntil,
//                    requiredAction, isDefault }
```

Hindi tulad ng catalog feed, wala talagang `tier` field ang body na ito — nagpapasya ang server
kung ano ang isasama sa bawat request batay sa `Authorization` key, kaya ang
`x-omniroute-feed-tier` response header ang TANGING pinagmumulan ng inihatid na tier
(`referralsSync.ts::syncRadarReferrals`); ang wala o hindi nakikilalang header ay ibinababa sa
`"community"`, ang pagpapalagay na may pinakamababang pribilehiyo. Bine-validate ng `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) ang buong body, gamit muli ang parehong
`RadarReferralSchema` para sa bawat referral na ini-export mula sa `feedSchema.ts` upang magkapareho ang
pag-validate ng dalawang feed sa bawat referral. Dapat `https://` ang bawat `RadarReferral.url` — ang
isang `http://` url ay hindi papasa sa schema validation.

Pinananatili ang LUMANG catalog-embedded na `referrals` field sa `RadarFeedSchema` (`feedSchema.ts`)
para sa backward compatibility sa mga naka-cache nang catalog feed, ngunit hindi na ito binabasa ng `getRadarReferrals()` —
tingnan ang [Accessor](#accessor) sa ibaba.

### Pag-sync

Ang `syncRadarReferrals()` (`src/lib/radar/referralsSync.ts`) ang TANGING module na
kumokonekta sa network para sa mga referral, at eksaktong tinutularan ang contract ng `syncRadar()`: naka-off ang flag
→ `disabled`; false ang opt-in → `opt_out`; dina-download ang `${RADAR_FEED_URL}/v1/referrals/latest`
(kaparehong `RADAR_FEED_URL`/`RADAR_FEED_PUBKEY` fork override gaya ng catalog), bine-verify ang
Ed25519 signature sa eksaktong response bytes (`verifyFeedBytes`), vine-validate laban sa
`RadarReferralsFeedSchema`, at kino-cache sa table na `radar_referrals_cache`
(migration `142_radar_referrals_cache.sql`) — isang table na ganap na hiwalay sa
`radar_feed_cache` ng catalog. Tinatanggihan ng 10 MB na limitasyon sa response at ng `generatedAt` floor ang
papasok na feed na mas luma kaysa sa naka-cache, bilang proteksyon laban sa replay ng isang mas lumang nilagdaang
artifact. Tinatanggap ang magkaparehong timestamp: sinasadya ng server na bigyan ang community
at live referral variant ng parehong deterministic na `generatedAt`, upang magbago ang nilagdaang payload
at inihatid na tier pagkatapos ng pagbabago sa supporter key nang hindi nagbabago ang pinagbabatayang hanay ng mga link.
Hindi kailanman nag-throw — palaging nagbabalik ng status object; hindi kailanman naglalaman ng stack trace ang mga error
sa `reason`.

Dalawang trigger ang nagpapanatiling handa sa referrals cache, at parehong hindi nakadepende sa sariling
24h cadence ng catalog:

- **Pag-sync kapag binabasa** — ang `GET /api/radar/referrals` mismo ang tumatawag sa `syncRadarReferrals()`
  inline kapag nawawala ang cache o mas matanda ito kaysa sa `REFERRALS_STALE_MS` (1h,
  `shouldSyncReferralsOnRead()`), bago ihatid ang tugon. Ito ang dahilan kung bakit "palaging napapanahon" ang mga fixed
  link sa mismong susunod na pag-load ng dashboard, nang hindi naghihintay sa anumang
  background timer.
- **Side-sync ng scheduler** — hiwalay na sinusuri ng `radarSchedulerTick()` (`scheduler.ts`) ang
  staleness ng mga referral sa parehong oras-oras na tick na ginagamit para sa catalog, at tinatawag ang
  `syncRadarReferrals()` kapag kailangan na. Tumatakbo ito hindi alintana kung nakatakda ring mag-sync ang catalog
  sa tick na iyon, at hindi kailanman naaapektuhan ang shape ng `RadarTickResult` (best-effort na side
  effect lamang, at hindi na ipinapasa ang error).

### Accessor

Nag-e-export ang `src/lib/radar/index.ts` ng dalawang read-only accessor, na parehong hindi kailanman nagti-throw (kaparehong
defensive contract ng `getRadarCatalog()` — naka-off na flag, walang cache, o sirang naka-cache na
payload ay pawang nagreresulta sa empty shape sa halip na error):

- `getRadarReferrals()` → `{ fixed: RadarReferral[], campaigns: RadarReferral[] }`,
  nagbabasa mula sa `radar_referrals_cache` (sa pamamagitan ng `getRadarReferralsCache()`) at nagva-validate
  gamit ang `RadarReferralsFeedSchema` — **hindi** ang catalog cache.
- `getDefaultReferralFor(provider)` → ang `fixed` referral na may `isDefault: true` para sa
  provider na iyon, o `null`. Sa `fixed` lamang tumitingin — hindi kailanman ginagamit ang campaign bilang
  "default" na link ng isang provider.

Nasa `findDefaultReferral()` (`src/lib/radar/referrals.ts`) ang aktuwal na panuntunan kung
"aling referral ang default para sa isang provider"; isa itong maliit at pure na function na **walang
DB import** — ligtas itong i-import sa isang `"use client"` component. Ang `getRadarReferrals`/
`getDefaultReferralFor` (sa `index.ts`) ay naglo-load ng `@/lib/db/radar` at samakatuwid ay nananatiling
server-only; direktang ini-import ng providers dashboard ang `referrals.ts` sa halip na
`index.ts` (tingnan sa ibaba) upang maiwasang maisama ang `better-sqlite3` sa browser bundle.

### `GET /api/radar/referrals`

Sinusunod nito ang eksaktong parehong pagkakasunod-sunod ng gate gaya ng bawat iba pang Radar route: naka-off ang `RADAR_ENABLED` →
`404` (unang sinusuri, byte-identical na inertia); hindi naka-authenticate → `401`; kung hindi,
nagti-trigger ito ng sync-on-read (tingnan sa itaas) kapag stale, pagkatapos ay `200` na may
`{ fixed, campaigns, tier }` — ang `tier` ay direktang nagmumula sa cache row na (posibleng kaa-refresh lang)
at para lamang sa impormasyon (ito ang nagkokontrol sa soft upsell copy ng UI sa ibaba). Hindi nito kailanman
direktang pine-proxy ang feed server — walang `fetch(` call ang sariling source ng route;
nangyayari lamang ang network access sa loob ng `syncRadarReferrals()`, alinsunod sa parehong
prinsipyong local-cache-only gaya ng `/api/radar/catalog`.

### Dashboard UI — tab na "Libreng credits" sa `/dashboard/radar`

Ginagamit muli ang kasalukuyang Radar page (`src/app/(dashboard)/dashboard/radar/page.tsx`) bilang
pangalawang tab sa halip na bagong route — mas maliit na routing/i18n surface para sa isang feature na
variation lamang ng data na kinukuha na ng page. Kapag naka-opt in na, iniaalok ng tab bar ang
**Catalog** (kasalukuyang table) at **Libreng credits**:

- Nakapangkat ayon sa provider ang mga fixed link, at ipinapakita ng bawat isa ang `requiredAction` (kapag mayroon)
  at isang `target="_blank" rel="noopener noreferrer"` na button patungo sa referral URL.
- Ipinapakita rin ng mga campaign ang mga iyon, kasama ang `validUntil` kapag mayroon.
- Kapag walang laman ang `campaigns` **at** `community` ang inihahatid na tier, nagpapakita ang UI ng
  maikling upsell note ("ang mga limited-time campaign ay dagdag na benepisyo para sa mga supporter") — **hindi**
  nito kailanman itinatago o nililimitahan ang listahan ng mga fixed link, na nananatiling ganap na populated para sa bawat tier. Ang
  upsell ay soft messaging lamang, at hindi kailanman isang block.

### Referral link sa pangalan ng provider (dashboard ng mga provider)

Ini-link na ng `ProviderPageHeader` (`src/app/(dashboard)/dashboard/providers/[id]/components/`)
ang pangalan ng provider sa `providerInfo.website` kapag mayroon, at may isang
naunang halimbawa ng monetized link: ang partner-link note ng Kimi (Moonshot AI)
(`providers.kimiPartnerLinkNote` i18n key). Ginagamit muli ng D28 ang eksaktong parehong discreet-note
pattern para sa mga default referral ng Radar sa halip na magdagdag ng bagong key.

Loose coupling, ayon sa disenyo:

- Ang `resolveProviderHeaderLink()` (`src/app/(dashboard)/dashboard/providers/providerPageUtils.ts`)
  ay isang **pure** function — `(staticWebsite, referralUrl) => { website, isReferralLink }`
  — na walang dependency sa `@/lib/radar` o `@/lib/db/*`. Ang `providerPageUtils.ts` sa
  kabuuan ay nananatiling walang ganoong mga import (tinitiyak ng
  `tests/unit/provider-header-referral-link.test.ts`).
- Ang `ProviderDetailPageClient.tsx` (isang `"use client"` component) ang tanging lugar na pinapayagang
  kumuha ng Radar data — sa pamamagitan ng `fetch("/api/radar/referrals")`, gamit ang parehong local-route
  pattern na ginagamit ng mismong Radar dashboard page — at kinukuwenta nito ang default referral
  sa client-side gamit ang `findDefaultReferral()` mula sa DB-free na `src/lib/radar/referrals.ts`.
- Kapag naka-off ang `RADAR_ENABLED`, nagbabalik ng 404 ang fetch, nananatiling `null` ang `referralUrl`, at
  ibinabalik ng `resolveProviderHeaderLink()` ang static catalog `website` nang walang pagbabago — ang
  provider page ay byte-identical sa anyo nito bago umiral ang feature na ito. Pareho ang resulta kapag
  wala pang cache o walang default referral para sa partikular na provider na iyon.
- Kapag nalalapat ang isang default referral, natatanggap ng `ProviderPageHeader` ang `isReferralLink`
  at ipinapakita nito ang parehong discreet note/tooltip gaya ng Kimi partner link (muling ginagamit ang
  `providers.kimiPartnerLinkNote` key) — hindi kailanman isang bago at hiwalay na visual treatment.

## Paano mag-self-host ng feed

Maaaring magpatakbo ang isang fork o self-hoster na nagnanais ng ganap na kontrol sa catalog ng sarili nitong serbisyo ng feed nang hindi binabago ang client code:

1. Mag-serve ng `GET /v1/catalog/latest` endpoint na nagbabalik ng JSON body na sumusunod sa
   `RadarFeedSchema` (`src/lib/radar/feedSchema.ts`) — top-level na `feed:
"omniroute-radar"`, `schemaVersion: 2`, `version`, `tier`, `providers`, `models`,
   `quirks`, at `totals`. Sundin ang `x-omniroute-radar-schema: 2`; ang isang server na compatible sa transition
   ay dapat mag-default sa mga request na wala nito patungo sa isang hiwalay na nilagdaang v1 artifact.
2. Lagdaan ang eksaktong mga byte ng response gamit ang isang Ed25519 key pair at ibalik ang base64
   signature sa `x-omniroute-feed-signature` response header.
3. Itakda ang `RADAR_FEED_URL` sa bagong base URL at ang `RADAR_FEED_PUBKEY` sa katugmang
   public key (base64-DER SPKI o PEM) — tingnan ang
   [sanggunian ng env var](../reference/ENVIRONMENT.md#27-radar-feed-self-hosting).
4. I-enable ang `RADAR_ENABLED` at mag-opt in sa pamamagitan ng `POST /api/radar/settings`
   (`{ optIn: true }`).

Wala nang ibang kinakailangang pagbabago sa code — awtomatikong ginagamit ng `verifyFeedBytes()` ang override
(`getFeedPublicKeys()` sa `src/lib/radar/pinnedKeys.ts`), at magkaparehong inilalapat sa isang self-hosted
na feed ang paghahambing ng version, pag-validate ng schema, at mga panuntunan sa merge.

Ang mga referral link (tingnan ang [Mga referral link (libreng credits)](#referral-links-free-credits)
sa itaas) ay isang hiwalay at opsyonal na artifact: ganap pa ring gumagana ang isang fork na nagsi-serve lamang ng `/v1/catalog/latest`
— maayos na bumababa ang `syncRadarReferrals()` sa `{ status: "error" }` kapag nakatanggap ng `404`
mula sa `/v1/referrals/latest`, at nananatiling walang laman ang cache, kaya
patuloy na nagbabalik ang `GET /api/radar/referrals` ng `{ fixed: [], campaigns: [], tier: null }`
sa halip na maging sanhi ng pagkabigo ng natitirang bahagi ng page. Upang mag-alok din ng mga referral link, mag-serve ng
`GET /v1/referrals/latest` na sumusunod sa `RadarReferralsFeedSchema`
(`src/lib/radar/referralsFeedSchema.ts`) at lagdaan ito gamit ang parehong Ed25519 key pair na ginagamit sa
catalog feed.

Isa pang opsyonal na artifact ang mga alok para sa supporter. Upang i-serve ang mga ito, ipatupad ang
`GET /v1/offers/latest` gamit ang saradong `RadarOffersFeedSchema`
(`src/lib/radar/offersFeedSchema.ts`), mangailangan ng aktibong entitlement, ibalik ang
`x-omniroute-feed-tier: live`, at lagdaan ang eksaktong mga byte gamit ang parehong key. Hindi nababago ng isang fork na hindi nagsasama ng endpoint na ito
ang gawi ng catalog/referrals; hindi mapanirang nabibigo ang pag-refresh ng mga alok at
nananatiling available ang huling na-verify na local offer cache.

Opsyonal din ang Intel sa parehong paraan. Maaaring mag-serve ang isang self-hoster ng `GET /v1/intel/latest` gamit ang
`RadarIntelFeedSchema` (`src/lib/radar/intelFeedSchema.ts`), mangailangan ng aktibong entitlement, magbalik ng
`x-omniroute-feed-tier: live`, at lagdaan ang eksaktong mga byte gamit ang shared Ed25519 key. Kapag hindi isinama ang
endpoint, hindi mababago ang catalog, referrals, at offers; papanatilihin ng pag-refresh ng Intel ang anumang huling na-verify na
local snapshot.
