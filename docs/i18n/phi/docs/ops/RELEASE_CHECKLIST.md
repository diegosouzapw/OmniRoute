## npm Trusted Publishing (default mula v3.8.51) — staged kapag hiniling, direct bilang fallback

Nagpa-publish ang `npm-publish.yml` sa pamamagitan ng **npm Trusted Publishing (OIDC)** bilang default: ipinagpapalit ng
`stage-npm` job (github-hosted) ang id-token ng GitHub para sa isang panandaliang npm
credential para sa run na iyon — walang pangmatagalang npm token sa mga repository secret, walang 2FA prompt, at may kalakip na provenance.
Iyan ang bypass na pinahihintulutan ngayon ng npm habang inaalis na ang mga token na lumalaktaw sa 2FA;
ibinabalik nito ang ganap na awtomatikong daloy na mayroon ang proyekto hanggang v3.8.48 habang pinananatili ang
garantiya ng WS1.3 (hindi makakapag-publish nang mag-isa ang isang na-leak na token — walang token).

**Isahang pag-set up (may-ari):** npmjs.com → package `omniroute` → Settings → _Trusted
Publisher_ → GitHub: owner `diegosouzapw`, repo `OmniRoute`, workflow `npm-publish.yml`
(environment: wala). Hangga't hindi pa ito umiiral, mabibigo ang awtomatikong hakbang nang may `ENEEDAUTH`:
muling i-dispatch gamit ang `publish_mode=staged` (sa ibaba) o `direct`.

### Staged publishing (kapag hiniling — `publish_mode=staged`)

Hindi na direktang nagpa-publish ang npm-publish workflow: bino-boot nito ang naka-pack na tarball
(`check:pack-boot`) at pagkatapos ay pinapatakbo ang `npm stage publish` — inilalagay sa registry ang eksaktong mga byte,
ngunit **hindi mai-install** hanggang aprubahan ng may-ari. Inilipat ang human 2FA gate
PAGKATAPOS ng patunay, hindi bago nito.

**Daloy ng may-ari pagkatapos maging green ang workflow:**

1. `npm stage list omniroute` — hanapin ang stage id (naka-print din sa buod ng workflow).
2. I-verify ang mga naka-stage na byte (inirerekomenda): `npm stage download <id>`, pagkatapos ay i-install ang
   na-download na tarball sa isang pansamantalang prefix at i-boot ito (ina-automate ng `npm run check:pack-boot`
   ang parehong hatol na pack→install→boot sa CI).
3. `npm stage approve <id>` — ang 2FA prompt MISMO ang pag-publish. Itinatapon ng `npm stage reject <id>` ang stage.
4. Post-publish safety net: ini-install ng post-publish verifier (WS1.4 ng plano para sa v3.8.49) ang
   na-publish na bersyon mula sa pampublikong registry sa isang malinis na container at bino-boot ito.

**Fallback sa emergency:** ibinabalik ng `workflow_dispatch` na may `publish_mode=direct` ang
dating agarang `npm publish` (gamitin lamang kung nagkakaproblema mismo ang staging; itala kung bakit).

**Isahang pagpapatibay ng seguridad (may-ari, npmjs.com):** i-configure ang Trusted Publisher para sa
`omniroute` sa stage-only mode upang hindi makapagpatakbo ng `npm publish` nang direkta mula saanman
ang isang na-leak na pangmatagalang token — staging lamang ang magagawa ng CI; tanging 2FA ng may-ari ang makakapag-release.

**Playbook para sa sirang artifact (walang pagbabago):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
bilang default na tugon (ilang minuto, maaaring ibalik); gamitin lamang ang `npm unpublish` sa loob ng 72h/no-dependents
na palugit at huwag kailanman bilang unang hakbang. Docker: huwag kailanman muling magsulat ng version tag — ang rollback ay
pagtuturo muli ng `latest` sa huling maayos na digest.

**Docker Hub `latest` (kinakailangan sa bawat stable na SemVer publish):** dapat i-tag ng
`docker-publish` workflow ang **parehong** `X.Y.Z` at, kapag
sumasang-ayon ang `should-promote-latest.sh` na ito ang pinakamataas na stable SemVer, ang `:latest`
gamit ang **parehong digest**. Pagkatapos ng job: katumbas ng bagong
SemVer digest ang Hub `latest` digest at nabago ang `last_updated`. Huwag iwan ang `:latest` sa isang mas lumang
build habang tinatalakay sa mga release note ang mga pag-aayos na nasa git lamang.
Ginagamit ng mga Compose quickstart ang `:latest`; dapat patuloy na i-pin ng GitOps ang `X.Y.Z`. Tingnan ang
[Mga channel ng release ng Docker](../guides/DOCKER_GUIDE.md#release-channels) at #10317.

## Mabilisang Daan para sa Hotfix (label na `hotfix`)

Nilalaktawan ng PR na may label na `hotfix` ang mabigat na CI matrix (9-shard E2E, coverage ratchet,
quality-gate, quality-extended) at pinananatili ang mabilis at mapagkakatiwalaang mga gate: build,
mga unit shard, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
at tarball boot-smoke (`check:pack-boot`). Target: pumasa sa loob ng ≤15min sa halip na ~33min.

**Patakaran sa pagpasok — kinakailangan ang lahat ng apat (batay sa mga emergency lane ng Chromium/VS Code/Node):**

1. **Kalubhaan**: sira ang production — nagka-crash sa pag-boot ang isang nailathalang artifact / isang
   pag-aayos sa seguridad / apektado ang bawat user ng release. Ang "Mahalaga" ay hindi nangangahulugang "sira".
2. **Awtoridad**: tanging ang may-ari ng repository ang maaaring maglapat ng label na `hotfix`. Ang label MISMO
   ang pag-apruba — hindi kailanman self-service sa isang campaign PR.
3. **Ebidensya**: nagli-link ang body ng PR sa nakaraang ganap na pumasa na heavy run (ang suite na
   muling ibe-verify sana ng mga nilaktawang job), kasama ang sariling test ng pag-aayos na unang bumagsak at pagkatapos ay pumasa.
4. **Saklaw**: cherry-pick lamang — ang pinakamaliit na pag-aayos, walang refactor, walang kasabay na ibang pagbabago.

Muling bina-validate ng susunod na full run sa release branch ang nilaktawang coverage/ratchet surface
(continuous release-green) — PAGHIHINTAY lamang ang nilalaktawan ng lane, hindi validation.
Awtomatikong nilalaktawan ng mga tests-only diff (lahat ng file ay nasa ilalim ng `tests/`, walang nasa ilalim ng `tests/e2e/`) ang E2E
matrix, nang walang anumang label.

## Detalyadong Checklist

### Bago ang release

- [ ] Na-merge na sa `release/vX.Y.0` ang lahat ng PR na nakatuon sa release na ito
- [ ] Naisara na o nailipat sa susunod na milestone ang lahat ng bukas na Linear/issue item para sa bersyong ito
- [ ] Pumapasa ang CI sa branch na `release/vX.Y.0`
- [ ] Walang marker na `TODO(release)` sa code: `grep -r "TODO(release)" src/ open-sse/`
- [ ] Napapanahon ang Docker base image (kasalukuyang `node:24.15.0-trixie-slim`)

### Bersyon at Changelog

- [ ] Patakbuhin ang `/version-bump-cc <patch|minor|major>` (Claude Code skill)
  - Ina-update ang bersyon sa `package.json`, `electron/package.json`
  - Muling binubuo ang `CHANGELOG.md` mula sa mga git commit mula noong huling tag
  - Ina-update ang mga badge sa README.md
- [ ] Manu-manong suriin ang CHANGELOG.md at linisin ang mga commit message kung kinakailangan
- [ ] Tiyaking katumbas ng bersyon sa `package.json` ang pinakabagong seksyong semver sa `CHANGELOG.md`
- [ ] Panatilihin ang `## [Unreleased]` bilang unang seksyon ng changelog para sa paparating na gawain
- [ ] I-update ang `docs/openapi.yaml` → dapat katumbas ng bersyon sa `package.json` ang `info.version`

### Kalidad ng Code

- [ ] `npm run lint` — 0 error (umiiral na dati ang mga warning)
- [ ] `npm run typecheck:core` — malinis
- [ ] `npm run typecheck:noimplicit:core` — malinis (strict)
- [ ] `npm run check:cycles` — walang circular dependency
- [ ] `npm run check:any-budget:t11` — pasok sa budget
- [ ] `npm run check:route-validation:t06` — malinis
- [ ] `npm run check:node-runtime` — natutugunan ang minimum na sinusuportahang runtime (`>=22.22.2 <23`, `>=24.0.0 <27`, ayon sa `SUPPORTED_NODE_RANGE` sa `src/shared/utils/nodeRuntimeSupport.ts`; nakaayon sa `engines` ng `package.json`)

### Pagsubok

- [ ] `npm run test:unit` — pumasa
- [ ] `npm run test:vitest` — pumasa (MCP server, autoCombo, cache)
- [ ] `npm run test:coverage` — natugunan ang gate na 60/60/60/60 (mga statement/line/function/branch)
- [ ] `npm run test:integration` — pumasa (kung may epekto ang mga pagbabago sa DB / mga handler)
- [ ] `npm run test:combo:matrix` — pumasa (matrix ng combo strategy: deterministikong pinatutunayan ang mga desisyon sa pagpili ng lahat ng 19 na pampublikong routing strategy; patakbuhin kapag binabago ang combo routing, strategy resolution, o fallback logic)
- [ ] `RUN_COMBO_LIVE=1 npm run test:combo:live` — **opsyonal/manwal** (gated real-upstream smoke; kumukuha ng read-only na DB snapshot mula sa VPS na `root@192.168.0.15`; gumagamit ng mga totoong provider, gumagastos ng credits; hindi kailanman tumatakbo sa CI; maayos na nilalaktawan kapag wala ang gate)

- [ ] `npm run test:e2e` — pumasa (mga pagbabago sa UI)
- [ ] `npm run test:protocols:e2e` — pumasa (mga pagbabago sa MCP/A2A)
- [ ] `npm run test:ecosystem` — pumasa

### Layout ng Build

Gumagamit ang repository ng tatlong magkakaibang output directory — huwag kailanman paghalu-haluin ang mga ito:

| Directory | Layunin                                                        | Sinusubaybayan?    |
| --------- | -------------------------------------------------------------- | ------------------ |
| `src/`    | Source ng application (TypeScript / TSX)                       | Oo                 |
| `.build/` | Mga intermediate ng build — output ng `next build` (`distDir`) | Hindi (gitignored) |
| `dist/`   | Naipapamahaging npm bundle — binuo ng `assembleStandalone`     | Hindi (gitignored) |

> **Tala para sa operator:** nananatiling `/usr/lib/node_modules/omniroute/app/` ang directory ng image sa remote VPS.
> Ang **in-repo** na output ng build lamang ang inilipat (`app/` → `dist/`). Ini-rsync ng mga deploy skill
> ang mga nilalaman ng `dist/` papunta sa remote na `app/` dir — walang kinakailangang pagbabago sa path ng VPS.

**Daloy na iisang build lamang:**

```
npm run build:release
  └─ rm -rf .build dist          (paglilinis)
  └─ next build → .build/next/   (mga intermediate)
  └─ assembleStandalone          (kinokopya ang standalone + static + public + natives → dist/)
  └─ nagsusulat ng dist/BUILD_SHA       (HEAD sentinel)
```

HUWAG patakbuhin ang `npm run build` na susundan ng hiwalay na `npm run build:cli` para sa deploy — gamitin ang
`npm run build:release`, na nagsasagawa ng malinis na rebuild + sentinel sa iisang command.

## Pag-cut ng 3.9.0 LTS (inensayo sa 3.8.58)

Pagkatapos ng v3.8.59, ang susunod na bersyon ay 3.9.0, at ang tip nito ay magiging dalawang pangmatagalang branch:
`stable/v3` (ang linya ng v3 LTS, npm `latest`) at `develop` (v4, itataas sa 4.0.0, npm
`nightly`). Ang modelo ng branch/channel, forward-port, at mga label ay nasa
[RELEASE_STRATEGY.md](./RELEASE_STRATEGY.md); ang plano ay nasa [ROADMAP](../../ROADMAP.md) (Phase 3). Isang beses lang tatakbo ang cut;
iniensayo ito ng 3.8.58 mula simula hanggang dulo sa isang fork, at magtatapos ang 3.8.59 gamit ang
[checklist ng GO/NO-GO](./LTS_GO_NO_GO.md).

### Dry-run (read-only, ligtas anumang oras)

```bash
npm run release:dry-run-lts-cut                       # ang aktuwal na cut: 3.9.0 mula sa HEAD, dating tag na v3.8.59
npm run release:dry-run-lts-cut -- --from <3.9.0-tip> # i-pin ang source commit
```

Walang ine-execute ang `scripts/release/dry-run-lts-cut.mjs`: binabasa nito ang git at `gh` at ini-print ang
buong pagkakasunod-sunod — mga precondition (mare-resolve ang source, umiiral ang dating tag, ang `package.json` ay nasa
target na bersyon, may bukas na `release-freeze` issue, walang bukas na `Release branch not green` issue
sa isang umiiral na release branch — ang branch na hindi umiiral ay nag-uulat ng `?` na unknown, at hindi kailanman
green — naka-configure ang Mergify `release` queue (G11: `queue_rules`, `checks_timeout`,
label na `queue`), hinaharangan pa rin ng `release/*` ruleset ang deletion at force-push, at
hindi pa umiiral ang `stable/v3` at `develop`), ang dalawang hakbang para sa branch, kung aling mga dormant-workflow
trigger at `if:` condition ang magiging true (at kung alin ang mananatiling gated ng repository variable o
naka-pin sa canonical repository), ang inaasahang mga dist-tag (`latest` → 3.9.0, walang laman ang `next` at
`nightly`) at ang rollback. Exit `0` = `RESULT: READY`, `1` = may nabigong blocking precondition
(`✗`), `2` = error sa paggamit. Ibinababa ng `--advisory <id,...>` ang isang check upang maging warning (`!`)
nang hindi ito itinatago.

Patakbuhin ang dry-run ng aktuwal na cut habang bukas pa ang release freeze ng 3.9.0 — ginagawa ang mga branch
pagkatapos ng tag at bago alisin ng Phase 12c ang freeze.

## Pag-rollback

Kung may kritikal na isyu ang release:

1. `gh release edit vX.Y.Z --prerelease` (minamarkahan bilang hindi pinakabago)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (kung hindi pa ito ginagamit ng mga user)
3. O: hotfix sa `release/vX.Y.0` → patch release na `vX.Y.(Z+1)`
4. Makipag-ugnayan kaagad sa GitHub Discussions at Discord

## Mahihigpit na Panuntunan

- Huwag kailanman direktang mag-commit sa `main`
- Huwag kailanman gumamit ng `git push --force` sa `main` o sa mga branch na `release/*`
- Huwag kailanman laktawan ang mga Husky hook (`--no-verify`)
- Huwag kailanman mag-commit ng mga secret, credential, o `.env` file
- Dapat manatiling ≥60/60/60/60 ang coverage (mga statement/linya/function/branch)
- Palaging magsama o mag-update ng mga test kapag binabago ang production code sa `src/`, `open-sse/`, `electron/`, o `bin/`
