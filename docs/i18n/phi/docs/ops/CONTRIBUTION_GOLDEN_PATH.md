Gamitin ang gabay na ito upang piliin ang pinakamaliit na maaasahang development loop para sa isang pull request. Hindi nito
pinapalitan ang mga dokumento ng arkitektura at seguridad na partikular sa bawat bahagi at naka-link sa ibaba; iniuugnay nito ang bawat karaniwang
uri ng pagbabago sa mga kontrata, nakatuong pagsusuri, at saklaw ng CI nito.

## Ang landas na sinusundan ng bawat pagbabago

1. **Piliin ang base bago mag-edit.** Hanapin ang pinakamataas na aktibong `release/v*` branch at gumawa ng branch mula
   sa pinakahuling commit nito. I-target ang branch na iyon, hindi ang `main`. Kung may aktibong release freeze, huwag i-target ang naka-freeze na
   branch; gamitin ang susunod na aktibong cycle na inilalarawan sa
   [Modelo ng Branching at Release](BRANCHING_MODEL.md).
2. **Tukuyin ang mga kontrata.** Tukuyin ang bawat catalog, schema, generated artifact, pampublikong API, o user
   interface na naaapektuhan ng pagbabago. Ibinibigay ng talahanayan sa ibaba ang minimum na panimulang hanay.
3. **Sumulat o mag-update ng mga nakatuong test.** Ang mga pagbabago sa production sa `src/`, `open-sse/`, `electron/`, o
   `bin/` ay nangangailangan ng automated test sa parehong PR. Patakbuhin ang pinakamaliliit na test file na nagpapatunay sa
   gawi, pagkatapos ay ang mga nakalistang nakatuong gate.
4. **Hayaan ang CI na magpatakbo ng malawak na matrix.** Tumatakbo sa PR ang kumpletong unit shards, Vitest, coverage ratchet, at
   production build. Magpatakbo lamang ng malawak na suite nang lokal kapag ang isang nakatuong failure ay nagpapahiwatig ng
   mas malawak na epekto o kapag sumasaklaw ang pagbabago sa ilang subsystem.
5. **Ipagkasundo ang mga pagbabago bago ang review.** I-fetch ang aktibong base, suriin ang mga bagong commit nito at ang diff mo laban
   dito, pagkatapos ay i-rebase o i-merge ang base ayon sa contributor workflow. Resolbahin mula sa pinagmulan ng mga ito ang mga conflict sa generated file
   at catalog, muling i-generate ang mga ito, muling patakbuhin ang nakatuong loop, at kumpirmahing
   naka-target pa rin ang PR sa aktibong release branch.
6. **Itala ang ebidensya.** Sa PR template, ilista ang mga command na pinatakbo, bawat test file na idinagdag o binago,
   mga migration o feature flag, at anumang validation na para lamang sa CI at nakabinbin pa.

## Mga pangunahing landas ayon sa uri ng pagbabago

Ang mga command sa ibaba ay mga minimum na nakatuong pagsusuri, hindi pahintulot na laktawan ang isang test na direktang sumasaklaw sa
gawi na binago mo.

### Provider

**Mga Kontrata**

- Depinisyon ng provider sa `src/shared/constants/providers/` at ang pagkakabuo nito sa
  `src/shared/constants/providers.ts`.
- Mga model at capability sa `open-sse/config/providerRegistry.ts` o sa mga inihiwalay na registry file nito.
- Pagpili ng executor/translator, configuration ng OAuth o API key, mga asset ng dashboard, at generated
  provider reference kapag naaangkop.
- Dapat gamitin ng mga pampublikong credential ang `resolvePublicCred()`; dapat gamitin ng mga error response ang mga nakabahaging sanitized
  error helper. Tingnan ang `docs/security/PUBLIC_CREDS.md` (git; hindi kino-compile sa `/docs`) at
  [Pag-sanitize ng Error](../security/ERROR_SANITIZATION.md).

**Nakatuong loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # kapag nagbago ang catalog; i-commit ang generated diff
npm run lint
```

I-test din ang bawat apektadong request family: chat, Responses, images, embeddings, audio, o video.
Suriin ang mga generated catalog at golden diff bilang mga pagbabago sa kontrata; huwag tanggapin ang mga ito nang walang pagsusuri.

### Routing

**Mga Kontrata**

- Mga pampublikong strategy value at UI metadata sa `src/shared/constants/routingStrategies.ts`.
- Dispatch at pagkakasunod-sunod sa ilalim ng `open-sse/services/combo.ts` at `open-sse/services/combo/`.
- Mga combo schema, persistence, resilience state, model capability, at mga kontrol ng API/UI.
- [Auto-Combo Engine](../routing/AUTO-COMBO.md) at dokumentasyon ng resilience kapag nagbabago ang gawi.

**Nakatuong loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # mga pagbabago sa strategy o dispatch
npm run check:known-symbols      # mga pagbabago sa pagpaparehistro ng strategy
npm run lint
```

Gumamit ng mga deterministic mocked-upstream test nang lokal. Nangangailangan ng mga credential ang mga live combo smoke test at
manual ang mga ito, hindi mga pamalit sa CI.

### UI / UX

**Mga Kontrata**

- Mga hangganan ng Next.js route/page at shared component sa ilalim ng `src/app/` at
  `src/shared/components/`.
- Mga hugis ng API response, loading/empty/error state, gawi para sa keyboard at screen reader,
  responsive layout, theming, at pagpapalawak ng locale.
- Mga English UI source string sa `src/i18n/messages/en.json`; huwag mag-hard-code ng bagong copy na makikita ng user.

**Nakatuong loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Patakbuhin ang app para sa mga pagbabago sa interaction o visual at suriin ang makitid at malapad na viewport. Pinapatakbo ng CI ang
production build at mas malawak na mga suite; kailangan pa rin ng visual behavior ng isang nakatuong component, Playwright,
o nakadokumentong manual na pagsusuring naaangkop sa pagbabago.

### i18n

**Mga Kontrata**

- `src/i18n/messages/en.json` ang UI source; `config/i18n.json` ang locale source.
- Hiwalay na matatagpuan ang mga CLI catalog sa ilalim ng `bin/cli/locales/`.
- Panatilihin nang eksakto ang mga ICU placeholder at tag. Huwag isalin ang mga pangalan ng product/provider/model,
  mga pangalan ng protocol at header, mga command, code/JSON identifier, URL, environment variable, o
  mga protektadong termino gaya ng `OmniRoute`, `OAuth`, `MCP`, at `A2A`. Ang kasalukuyang source list ay
  `scripts/i18n/glossary/protected-terms.json`.

**Nakatuong loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # kapag nagbago ang mga CLI string/catalog
npm run lint
```

Gabay ito para sa kasalukuyang system, hindi isang paanyayang palawakin ang tooling o key model nito.
Panatilihing eksakto at limitado ang mga i18n patch habang idinidisenyo ang pamalit na system. Huwag magpatakbo ng mga translation
command na tumatawag sa mga external service maliban kung tahasang nangangailangan ang gawain ng mga generated translation at
nasuri mo na ang resultang diff.

### CLI

**Mga Kontrata**

- Mga pampublikong command at flag sa `bin/cli/`, mga nabuong API command, mga exit code, stdout/stderr at
  mga anyo ng JSON output, gawi ng config/environment, at mga naka-package na file.
- Dapat gamitin ng mga string na nakikita ng user sa CLI ang CLI i18n layer at panatilihing magkatugma ang mga catalog na `en`/`pt-BR`.
- Panatilihin ang Node bilang suportadong runtime at ang kontrata ng naka-publish na binary.

**Nakatuong loop**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # mga pagbabago sa nabuo/na-bundle na CLI
npm run check:pack-policy     # mga pagbabago sa surface ng package
npm run lint
```

Gamitin ang eksaktong command sa isang pansamantalang direktoryo ng data kapag nakadepende ang gawi sa pag-parse, mga file, o exit
status. Isinasagawa ng CI ang mas malawak na pagsusuri sa artifact ng package at ecosystem.

### Database

**Mga kontrata**

- Mga domain module sa ilalim ng `src/lib/db/`; direktang i-import ang mga partikular na module (inalis na ang lumang `localDb.ts` re-export layer).
- Mga may numero at idempotent na SQL migration sa ilalim ng `src/lib/db/migrations/`, kaligtasan ng transaction, gawi sa pag-upgrade,
  mga index, at bawat caller na apektado ng schema.
- Hindi kailanman direktang nagpapatakbo ng raw SQL ang mga route at handler.

**Nakatuong loop**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Subukan ang bagong database at ang pag-upgrade mula sa naunang schema kapag nagdaragdag ng migration. Dapat
isara ng mga database test ang mga handle at tawagin ang `resetDbInstance()` habang naglilinis. Patakbuhin lamang ang `npm run test:bun:db` kapag
nagbabago ang best-effort Bun adapter path; nananatiling awtoritatibo ang Node.

### Build / deploy

**Mga kontrata**

- Mga root at workspace manifest/lockfile, `scripts/build/`, standalone assembly ng Next.js, mga nilalaman ng package na `dist/`,
  platform metadata ng Electron, mga workflow ng CI, at mga sentinel ng deployment.
- Dapat manatiling buo ang mga sinusuportahang saklaw ng Node at ang naka-allow-list na paggamit ng Bun sa `CLAUDE.md`.
- Mananatiling hindi sinusubaybayan ang mga build artifact; nalalapat ang mga patakaran sa dependency, lisensya, workflow, at package.

**Nakatuong loop**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # mga pagbabago sa dependency o lockfile
npm run check:pack-policy      # mga pagbabago sa surface ng naka-publish na package
npm run lint
```

Gamitin lamang ang `npm run build` nang lokal kapag naaapektuhan ng pagbabago ang compilation, standalone assembly, mga asset,
o runtime bundling. Gamitin lamang ang `npm run build:release` para sa validation ng release/deploy. Ang build ng CI
ang panghuling cross-platform na signal; kailangan ng mga pagbabago sa Electron na partikular sa platform ang katugmang nakatuong build
o ebidensya ng smoke test.

## Lokal na loop ng kandidato

Hindi mapatutunayan ng mga source test na nagbu-boot ang naka-package na artifact: nabibigo lamang ang mga listahan sa packaging, mga na-prune na dependency,
at mga native binary kapag na-install at sinimulan na ang tarball. Ang `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ang lokal na bahagi ng daloy na build-once / validate / promote mula sa
RFC #8084: bumubuo ito ng isang kandidato, bina-validate ang mismong artifact na iyon, pino-promote ito sa pamamagitan ng pagpapalit
ng pangalan ng mga directory, at niro-roll back ito kapag bumagsak ang health check ng na-promote na slot.

```bash
npm run dev:candidate -- run --dry-run --json  # i-print ang plano, walang babaguhin
npm run dev:candidate -- run                   # bumuo + mag-validate + mag-promote, awtomatikong mag-rollback
npm run dev:candidate -- build                 # npm pack + i-install sa _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # mag-boot sa libreng port, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # pagpalitin ang current at previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # muling gumamit ng tarball na binuo sa ibang lugar (CI)
```

- **Isang beses lang bumuo.** Pina-package ng `build` ang kasalukuyang tree (kailangan nito ang `dist/server.js`, kaya patakbuhin muna ang
  `npm run build:release`) o kinokopya ang `--from-tarball`, pagkatapos ay ini-install ang tarball sa isang
  nakahiwalay na npm prefix, dahil walang kasamang `node_modules` ang tarball. Ang id ay ang maikling `HEAD`
  sha (`-dirty` kapag may mga lokal na pagbabago ang tree) o `tgz-<sha256>` para sa isang tarball. Ang malinis na id na
  nabuo na ay muling ginagamit sa halip na buuing muli; ipasa ang `--force` upang buuin itong muli.
- **I-validate ang package, hindi ang source.** Sinisimulan ng `validate` ang naka-install na CLI
  (`serve --port <free port>`) gamit ang bagong `DATA_DIR=<candidate>/data`, mga pekeng secret, at inaalis sa
  environment ang `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY`, at `INITIAL_PASSWORD` ng operator,
  upang masuri nito ang keyless loopback na katayuan ng isang bagong install. Hinihintay nitong
  magbalik ng 200 ang `GET /api/health`, inaatasan ang `GET /v1/models` na magbalik ng 200, itinitigil ang process group,
  at itinatala ang resulta sa `validation.json` kasama ng hash ng tarball.
- **I-promote ang parehong artifact.** Tinatanggihan ng `promote` ang kandidatong walang pumapasang validation para sa
  kasalukuyang hash ng tarball nito. Ang default na aktibong slot ay `_artifacts/candidate/current`; pumipili ang `--target <dir>`
  ng ibang directory sa parehong filesystem, at ang naunang slot nito ay `<dir>.previous`.
  Atomic ang bawat pagpapalit ng pangalan, at kapag nagkaroon ng pagkabigo habang isinasagawa ito, binabaligtad ang mga pagpapalit ng pangalang naisagawa na.
- **Mag-roll back.** Muling bina-validate ng `run` ang na-promote na slot at muling pinagpapalit ang `current` at `previous` kapag
  nabigo ang pagsusuring iyon. Hindi kailanman pino-promote ang kandidatong bumagsak sa unang validation.

Isinusulat ang lahat sa ilalim ng `_artifacts/candidate/` na hindi sinusubaybayan dahil nasa gitignore; hindi kailanman ginagalaw ang umiiral na
installation ng OmniRoute at ang data directory nito. Ang na-promote na CLI ay
`_artifacts/candidate/current/prefix/bin/omniroute`; simulan ito gamit ang sarili mong `DATA_DIR` kapag ginagamit
mo ito. Mga exit code: `0` tagumpay, `1` nabigong validation o promotion, `2` error sa paggamit o nawawalang build.

## Lokal na loop kumpara sa CI

| Patakbuhin nang lokal para sa bawat patch                                                     | Nagbibigay ang CI ng malawak na signal                                         |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Mga direktang pagsubok sa gawi at mga category gate sa itaas                                  | Naka-shard na buong unit suite at mga serial test                              |
| `npm run lint`                                                                                | Mga Vitest suite at mga ratchet para sa coverage/kalidad                       |
| Typecheck o build lamang kapag kinakailangan ito ng apektadong kontrata                       | Production build, seguridad, dokumentasyon, dependency, at PR-policy gate      |
| Mga manual na interaksiyon/live check lamang kapag hindi mapapatunayan ng automation ang gawi | Mga cross-job integration at platform check na naka-configure ayon sa workflow |

Ang matagumpay na focused loop ay ebidensiya tungkol sa binagong kontrata, hindi patunay na papasa
ang mga walang kaugnayang CI check. Sa kabilang banda, huwag paghintayin ang bawat lokal na pag-edit
sa buong repository matrix.

## Checklist sa rekonsilyasyon

Bago humiling ng review:

- Kumpirmahing ang base ng PR ay ang pinakamataas na aktibong branch na `release/v*`.
- I-fetch ang base na iyon at suriin ang mga commit na naisama mula nang gawin mo ang iyong branch.
- Suriin ang `git diff <active-base>...HEAD` para sa hindi sinasadya o generated na churn.
- Lutasin ang mga conflict sa catalog at generated na dokumento sa pamamagitan ng pag-update sa source at muling pag-generate ng output.
- Muling patakbuhin ang bawat focused test/gate na nakalista sa paglalarawan ng PR pagkatapos ng rekonsilyasyon.
- Huwag kailanman pahinain ang mga assertion o alisin ang mga kinakailangang test para lamang umangkop sa nabagong base.

Para sa mga panuntunan sa release freeze at retargeting, gamitin ang
[Modelo ng Branching at Release](BRANCHING_MODEL.md). Para sa kumpletong imbentaryo ng CI, gamitin ang
[Reperensiya ng mga Quality Gate](../architecture/QUALITY_GATES.md).
