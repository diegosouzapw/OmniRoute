---

Inilalantad ng OmniRoute ang **dalawang** paraan upang gamitin ang OpenAI Codex:

| Provider               | Paano ito nakikipag-ugnayan sa OpenAI                                                                                                                                                                                                             | Paalala sa paggamit                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **`codex`**            | Direktang nire-replay ang iyong ChatGPT/OpenAI OAuth token sa Responses API                                                                                                                                                                       | **Oo** — hindi awtorisado ang opisyal na session para sa paggamit bilang proxy/router |
| **`codex-app-server`** | Pinapatakbo ang sariling **`codex app-server` ng Codex CLI** sa pamamagitan ng JSON-RPC/WebSocket; ang CLI ang namamahala at awtomatikong nagre-refresh ng OAuth nito (`~/.codex/auth.json`), tulad mismo ng isang interactive na `codex` session | **Wala** — hindi kailanman nire-replay ng OmniRoute ang token sa API                  |

Dahil hindi kailanman nire-replay ng `codex-app-server` ang token, hindi naaangkop
dito ang paalala sa paggamit tungkol sa session replay. Kinakailangan nito ang
isang **Codex CLI na maaabot sa naka-configure na app-server URL**, at dapat
**naka-sign in** ang CLI na iyon.

---

## 1. Arkitektura

```
┌─ OmniRoute app ─────────────────┐        ┌─ codex-app-server sidecar ─────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ capability token)            │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  kusang namamahala ng OpenAI OAuth  │
└──────────────────────────────────┘        │  (~/.codex/auth.json, auto-refresh) │
        │ ibinabahagi (compose volumes)      └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → ang WS capability token (pareho itong mino-mount)
  codex-appserver-home    → ~/.codex (auth.json na isinusulat ng dashboard,
                             binabasa ng codex app-server ng sidecar)
```

- Nakikinig ang sidecar **lamang** sa internal compose network
  (`ws://codex-app-server:1456`) sa likod ng isang capability token. **Hindi**
  ito kailanman inilalantad sa host o internet.
- Kasama na ang Codex CLI sa `omniroute:base`, kaya hindi kailangang mag-install
  ng codex sa host o sa makina ng user kapag pinapatakbo mo ang sidecar.

## 2. Patakbuhin ito

```bash
# Simulan ang stack KASAMA ang codex app-server sidecar profile:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Gumagawa ang sidecar ng sarili nitong WS capability token sa unang pag-boot
(sa nakabahaging `codex-appserver-token` volume), at binabasa ng app ang parehong
token sa pamamagitan ng `OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Hindi
kailangang manu-manong ikonekta ang token.

## 3. Kumonekta + mag-sign in

1. Sa dashboard, magdagdag ng koneksyon para sa **OpenAI Codex (App-Server)**.
   Walang kinakailangang API key o token (isa itong no-auth provider — ang
   sidecar ang namamahala sa auth).
2. Kung **hindi pa naka-sign in** ang Codex CLI ng sidecar, iuulat ng connection
   health check ang _"tumatakbo ngunit hindi naka-sign in"_ (hindi isang pulang
   auth error). Gamitin ang **Mag-sign in gamit ang ChatGPT**: pinapatakbo nito
   ang karaniwang Codex device-OAuth sa iyong browser at pagkatapos ay isinusulat
   ang `~/.codex/auth.json` sa nakabahaging volume sa pamamagitan ng **Ilapat ang
   auth** (ang iisang pag-login na ito ang nagsisilbi sa parehong `codex` at
   `codex-app-server` provider).
3. Kapag naka-sign in na, magiging berde ang health check (bine-verify nito ang
   `/readyz` **at** `account/read` — ibig sabihin, tumatakbo _at_ authenticated)
   at magsisimula itong gumana.

Hindi kailanman ino-overwrite ng dashboard ang isang maayos na umiiral na
`~/.codex/auth.json` — nagsusulat lamang ito kapag wala ang file o lipas na ang
token nito (palaging gumagawa muna ng backup).

## 4. Mga sitwasyon sa deployment

- **Operator na may naka-authenticate nang Codex CLI** — i-mount ang iyong host
  `~/.codex` sa sidecar (`codex-appserver-home`) at laktawan ang hakbang sa
  pag-sign in.
- **Pampublikong user na walang lokal na naka-install na codex** — hindi ito
  mahalaga: nasa sidecar ang CLI. Sa dashboard lamang kailangang mag-authenticate
  ng user.
- **Bare-metal OmniRoute (walang sidecar, host codex)** — ituro ang
  `OMNIROUTE_CODEX_APPSERVER_WS` sa sarili mong `codex app-server` at tiyaking
  naka-sign in ang host codex; lalabas ang pahiwatig na "hindi naka-install ang
  codex" kung nawawala ang binary.

## 5. Residential / UDP egress (karagdagang opsyon ng operator, hindi kasama)

Lumalabas ang generic na sidecar sa pamamagitan ng normal na network ng
container. Ang operator na kailangang palabasin ang Codex traffic sa pamamagitan
ng isang **residential exit** (hal. isang TUN tailscale sidecar na nagdadala ng
TCP + UDP/QUIC) ay nagpapatakbo nito bilang hiwalay na compose override; sadya
itong **hindi** bahagi ng kasamang `codex-app-server` profile. Tingnan ang
internal operations runbook para sa setup na iyon.
