## Mabilisang Sanggunian

**Bago sa OmniRoute?** Magsimula rito — nalulutas ng mga ito ang 90% ng mga problema:

| Nakikita ko ito               | Ang ibig sabihin nito                       | Ang dapat gawin                                                                                                                       |
| ----------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| "Hindi makakonekta"           | Hindi tumatakbo ang OmniRoute               | Patakbuhin ang `omniroute` o `docker restart omniroute`                                                                               |
| "Di-wastong API key"          | Mali o nag-expire na ang iyong key          | Kopyahin muli ang key mula sa website ng provider                                                                                     |
| "Lumampas sa rate limit"      | Nagpapadala ka ng napakaraming request      | Maghintay nang 1 minuto, o gamitin ang `model: "auto"` para sa awtomatikong fallback                                                  |
| "Lumampas sa quota"           | Naubos mo na ang iyong libre/bayad na quota | Kumonekta sa mas maraming provider, o gumamit ng mga libreng provider (Kiro, Pollinations)                                            |
| "Mabagal na mga tugon"        | Abala o malayo ang provider                 | Gamitin ang `model: "auto/fast"` o kumonekta sa mas mabilis na provider (Groq, Cerebras)                                              |
| "Maling provider ang ginamit" | Pumili ang `auto` ng ibang provider         | Normal lang iyan! Pinipili ng `auto` ang pinakamahusay. Piliting gumamit ng partikular na provider gamit ang `model: "openai/gpt-4o"` |
| "502 Bad Gateway"             | Hindi gumagana ang provider                 | Maghintay at subukang muli, o gamitin ang `model: "auto"` upang lumipat ng provider                                                   |
| "401 Unauthorized"            | Mali ang iyong mga kredensyal               | Suriin ang iyong API key o muling mag-authenticate gamit ang OAuth                                                                    |
| "429 Too Many Requests"       | Nalimitahan ang rate                        | Maghintay nang 1 minuto, o kumonekta sa mas maraming provider                                                                         |

**Hindi pa rin malutas?** Tingnan ang [detalyadong pag-troubleshoot](#detailed-troubleshooting) sa ibaba, o magtanong sa [Discord](https://discord.gg/U47eFqAXCn).

## Detalyadong Pag-troubleshoot

---

### Paglilimita ng Rate sa Mga Libreng Provider (429 / 400 / 401)

**Sintomas**: Kapag gumagamit ng `model: "auto"` kasama ang mga libre/hindi nangangailangan ng authentication na provider (opencode, auggie, atbp.), paminsan-minsan kang nakakatanggap ng `HTTP 429`, `400`, o `401` sa halip na mga sagot. Nagtatagumpay ang mga request kapag sinusubukang muli ang parehong prompt makalipas ang ilang sandali, ngunit pumapalya ang automation (mga cron job, agent, script) sa unang kabiguan.

**Pangunahing sanhi**: Nagsasabay-sabay ang tatlong magkakahiwalay na uri ng kabiguan:

1. **Rate limit ng provider (`429`)**: Maaaring magpatupad ang mga libreng tier ng quota sa bawat takdang panahon. Nauubos ito ng sunod-sunod na parallel call, kaya tinatanggihan ang susunod na request hanggang sa mag-reset ang takdang panahon.
2. **Sirang model sa passthrough (`400`/`401`)**: Maaaring magsama ang mga `auto/*` pool ng mga passthrough model mula sa `opencode` na nakarehistro sa catalog ngunit walang aktibong kredensyal (hal. `oc/north-mini-code-free` → `401`). Susubukan ng auto-router ang isa, mabibigo ito, at ipapasa ang error bago pa gumana ang fallback.
3. **Paglaki dahil sa concurrency (`429` kapag mataas ang load)**: Kapag sabay-sabay na gumagamit ng `auto` ang maraming session ng agent/cron, lumalampas ang pinagsama-samang rate ng request sa kayang tanggapin ng mga libreng provider, kaya natutukoy bilang mapang-abuso kahit ang mga lehitimong call.

**Napatunayang solusyon (iniulat ng komunidad, 2026-08-10)**: ayusin ang tatlong environment variable upang masalo ng rotation, concurrency, at fallback ang pabago-bagong katangian ng libreng tier sa halip na tuluyang pumalya dahil dito:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # lumipat sa ibang model/provider kapag may 400/401 (nilalaktawan ang mga sirang passthrough model)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # tahasang maximum na bilang ng mabibigat na request na maaaring tanggapin (hindi naka-set bilang default: walang limitasyon sa bilang ng request, tingnan ang tala sa ibaba)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # mas mahabang limitadong paghihintay para sa kapasidad ng mabibigat na request sa halip na agarang retryable na 503
```

I-set ang mga ito sa process environment ng OmniRoute (ang daemon, hal. sa pamamagitan ng LaunchAgent plist o `systemctl edit`), pagkatapos ay i-restart ang OmniRoute. Ang rotation flag ang may pinakamalaking epekto: ginagawa nitong transparent na muling pagsubok sa isang maayos na provider sa pool ang isang ganap na kabiguan.

**Tala**: Nililimitahan ng `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` kung ilang mabibigat — may mahabang context — na request ang sabay-sabay na tatakbo; ang limitasyong ito ay isang admission gate, hindi rate limiter ng provider. **Update sa #503-fanout:** hindi na naka-set bilang default ang var na ito (gagana lamang ito ngayon kapag tahasang na-configure, gaya sa itaas) — sa halip, kinokontrol ang pagtanggap ng mabibigat na request ng awtomatikong kinukuwentang byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) na kusang umaayon sa aktuwal na limitasyon ng memory ng host, kaya dapat makaranas ang isang bagong deployment ng mas kaunting pagtanggi na `503 chat_admission_busy` kahit hindi i-set ang var na ito; gagana pa rin nang eksakto ayon sa dokumentasyon ang tahasang pag-set nito rito. Ang mga tahasang override sa byte budget ay lilimitahan sa 8 MiB–2 GiB. Hindi pansamantala ang isang `413 body_exceeds_budget`: dagdagan ang byte budget na iyon, babaan ang `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, o dagdagan ang limitasyon ng memory ng process. Pansamantalang agawan ng resource ang isang `inflight_bytes_budget` shed at maaari pa rin itong subukang muli. Hiwalay na pinamamahalaan ang paglilimita ng rate para sa bawat provider (`open-sse/services/rateLimitManager.ts`) ng `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, at `RATE_LIMIT_AUTO_ENABLE` — tingnan ang `.env.example`.

**Paano tiyaking gumana ito**: patakbuhin nang dalawang beses nang magkasunod ang iyong agent/cron at tiyaking magtatagumpay ang dalawa. Bago ang pag-aayos, karaniwang nagbabalik ang ikalawang pagpapatakbo ng `429`/`401`. Pagkatapos ng pag-aayos, transparent na sinusubukang muli ang mga kabiguan (kung mayroon man) at nakukumpleto ang call. Maaari mo ring patakbuhin ang `curl /monitoring/health` at subaybayan ang field na `rateLimitedUntil` sa mga koneksyon ng provider at ang `circuitBreakers.providerBreakers[].state` para sa mga apektadong provider — ang state ay isa sa `CLOSED`, `DEGRADED`, `OPEN`, o `HALF_OPEN` (tingnan ang `src/shared/utils/circuitBreaker.ts`), at ang provider na patuloy na pumapalya ay lilipat mula `CLOSED → DEGRADED → OPEN` bago payagan ng reset window na makalusot ang isang probe (`HALF_OPEN`).

**Kung nakikita mo pa rin ang 429**: talagang naubos na ng aktibong account para sa provider na iyon ang _quota_ nito (hindi lang ang rate limit). Magdagdag ng pangalawang account para sa parehong provider sa OmniRoute dashboard → Providers → Accounts, o magsama ng isa pang libreng provider (hal. `routeway`, `auggie`). Nakakatulong lamang ang rotation sa pansamantalang rate/400/401; kapag tuluyang naubos ang quota, kailangan ng pangalawang credential o ibang provider.

**Kung nakikita mo ang 403 sa mga vision model (`auto/vision`, `bazaarlink/*`)**: walang paid plan na may kasamang vision ang nakakonektang account, o walang sapat na pahintulot ang API key. Tiyakin sa provider dashboard na kasama sa scope ng key ang vision/multimodal, o magkonekta ng paid tier account at panatilihin ito bilang vision target.

## Mga Babala sa npm install (ERESOLVE / peer / deprecated)

Kapag pinatakbo mo ang `npm install -g omniroute`, maaari kang makakita ng napakaraming babala tulad ng `npm warn ERESOLVE`, mga abiso tungkol sa peer dependency, at mga mensaheng `deprecated`. **Inaasahan ang mga ito at hindi nakapipinsala.** Matagumpay ang iyong pag-install kung makikita mo ang `added <N> packages` sa output.

Nagmumula ang mga babala sa mga lumang saklaw ng peer dependency sa mga third-party package na hindi kontrolado ng OmniRoute:

1. **Kinakailangan ng `marked-terminal` ang `marked >=1 <16`, ngunit `marked@18` ang nakita** — gumagana ito nang maayos sa aktuwal na paggamit; luma lamang ang upstream peer range.
2. **`deprecated prebuild-install@7.1.3`** — isang transitive helper para sa pagkuha ng native binary. Hindi ito
   ginagamit upang i-install ang naka-pin na `wreq-js` transport binding at hindi ito nagpapahiwatig na nabigo ang
   pag-setup ng transport ng web-cookie provider.

**Walang kailangang gawin** — hindi ganap na mapapatahimik ang mga babala nang hindi nagfo-fork ng mga upstream package.

## Mga Maling Positibong Resulta ng Antivirus

<a name="antivirus-false-positives"></a>

### Kina-quarantine ng Avast/AVG ang `README.md` bilang `MD:HttpRequest-inf[Susp]`

**Isa itong maling positibong resulta. Walang nahawahan, at walang kinakailangang gawin.**

Gumagamit ang Avast at AVG ng heuristic na nagfa-flag sa mga plain-text/Markdown file na naglalaman ng maraming
link na mukhang mga HTTP request. Kasama ang `README.md` ng OmniRoute sa npm package (ito ay
nakalista sa `package.json` → `files`), kaya napupunta ito sa `node_modules/omniroute/README.md` sa
isang global install — at naglalaman ito ng ~15 halimbawa ng `http://localhost:20128/...` (ang mga MCP
HTTP/SSE endpoint, ang A2A `.well-known` URL, at mga snippet ng `curl`). Sapat ang dami ng mga link na iyon
upang ma-trigger ang heuristic.

Kung kamakailan lang ito nagsimula: hindi nagbago ang uri ng file. Lumawak ang talahanayan ng mga
endpoint sa README (idinagdag ang MCP HTTP + SSE + A2A) at dumami ang mga halimbawa ng `curl`, kaya
lumampas ito sa threshold.

Ang file ay dokumentasyong hindi aktibo at walang anumang executable na nilalaman. Ligtas mo itong maibabalik
mula sa quarantine.

**Ano ang dapat gawin:**

1. **Itigil ang mga notification** — ibukod ang direktoryo ng pag-install sa iyong antivirus
   (Avast: Settings → Exceptions), at idagdag ang path ng iyong global `node_modules` at/o ang
   direktoryo ng data ng OmniRoute (`~/.omniroute/`).
2. **Iulat ang maling positibong resulta** — <https://www.avast.com/false-positive-file-form.php>,
   at ilakip ang naka-quarantine na `README.md`. Ito ang solusyong makatutulong sa lahat, dahil ang
   heuristic ng vendor ang labis na tumutugon sa isang text file.

**Bakit hindi namin ito "inaayos" sa aming panig:** lahat ng halimbawa ay `http://localhost`, at
hindi maaaring maging `https` ang localhost nang walang abalang dulot ng self-signed certificate. Ang pagsira sa mga dokumento upang
maiwasan ang heuristic ng isang vendor ay makasasama sa bawat mambabasa para lamang mapagbigyan ang isang bug sa scanner.

### Fina-flag ng Kaspersky ang Desktop app bilang `PDM:Trojan.Win32.Generic`

**Isa itong maling positibong resulta mula sa isang behavioral heuristic. Walang nahawahan.** Ang prefix na
`PDM:` ng Kaspersky ay nangangahulugang nagmumula ang hatol sa Proactive Defense Module (System Watcher) nito,
na humahatol batay sa kung ano ang _ginagawa_ ng installer sa halip na itugma ito sa kilalang malware. Kapag
na-trigger ito, "ibinabalik" ng Kaspersky ang buong pag-install — binubura ang mga file na naisulat na nito
— kaya nasisira o nawawala ang app.

Ang mga file na fina-flag nito ay mga karaniwang bahagi ng mga idineklara at open-source na dependency na kasama sa
desktop app, halimbawa:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` at
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ang library para sa browser automation
  na ginagamit para sa pag-login sa provider sa loob ng app at chat na sinusuportahan ng browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ang naka-pin na native binding ng `wreq-js` na ginagamit para sa HTTP na may browser fingerprint sa mga provider na
  gumagamit ng web cookie (`<arch>` ay `x64` o `arm64`).

**Bakit ito nati-trigger:** ang Windows installer ay **hindi pa code-signed**, kaya walang anumang reputasyon
ang isang unsigned NSIS installer at tumatakbo nang napakaagresibo ang mga behavioral heuristic. Kapag isinama
ang isang naka-bundle na native DLL at daan-daang `.js` file na isinusulat sa ilalim ng
`%LOCALAPPDATA%\Programs\OmniRoute` (kabilang ang mga direktoryo ng package na may hash suffix mula sa
Next.js standalone build), sapat na iyon upang ma-trigger ang heuristic. Nakaplano ang code signing;
hanggang sa maipatupad ito, maaari itong maulit sa mga bagong release.

**Ano ang dapat gawin:**

1. **I-verify muna ang iyong download** (upang matiyak na hindi nabago ang file). Naglalathala ang bawat release ng
   `latest.yml`, na ang field na `sha512` (base64) ay sumasaklaw sa installer na `OmniRoute.Setup.<version>.exe`.
   Sa PowerShell, mula sa folder na naglalaman ng installer:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Dapat tumugma ang output sa `latest.yml` → `sha512`. Kung hindi ito tumutugma, burahin ang file at
   muling mag-download mula lamang sa [pahina ng mga release sa GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **I-restore + ibukod** — ibalik mula sa quarantine ang mga item na tinanggal sa rollback at magdagdag ng exclusion
   para sa `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   pagkatapos ay muling mag-install.
3. **Iulat ang maling positibong resulta** — <https://opentip.kaspersky.com/>. Ang mga ulat ng maling positibong resulta
   na isinusumite ng mga user ay talagang nagpapabilis sa pagdaragdag sa allowlist.

## Compatibility sa Node.js

<a name="nodejs-compatibility"></a>

### Nagka-crash ang pahina sa pag-login o ipinapakita ang error na "Module self-registration"

**Sanhi:** Gumagamit ka ng bersyon ng Node.js na wala sa aprubadong minimum na secure runtime ng OmniRoute. Ang pinakakaraniwang kaso ay ang paggamit ng mas lumang patch level ng Node 22 o 24 na mas mababa sa kinakailangang patched security floor ng OmniRoute.

**Mga sintomas:**

- Nagpapakita ang pahina sa pag-login ng blangkong screen o server error
- Ipinapakita ng console ang `Error: Module did not self-register` o mga katulad na error sa native binding
- Nagpapakita ang pahina sa pag-login ng **orange na banner ng babala** kasama ang iyong bersyon ng Node kung ang runtime ay wala sa sinusuportahang secure policy

**Pag-aayos:**

1. Mag-install ng sinusuportahang release ng Node.js LTS (inirerekomenda: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. I-verify ang iyong bersyon: dapat ipakita ng `node --version` ang `v24.0.0` o mas bago sa 24.x LTS line
3. Muling i-install ang OmniRoute: `npm install -g omniroute`
4. I-restart: `omniroute`

> **Mga sinusuportahang secure na bersyon:** `>=22.22.2 <23` o `>=24.0.0 <27`. Ganap na sinusuportahan ang Node.js 24.x LTS (Krypton) at Node.js 26.

### npm v11+: Hindi naka-install ang `better-sqlite3` (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Sanhi:** Bina-block ng npm v11 (kasama sa Node.js 24+) ang mga install script para sa mga opsyonal na dependency bilang default. Dahil nakalista ang `better-sqlite3` sa `optionalDependencies` at nangangailangan ng native compilation (`node-gyp rebuild`), tahimik itong nilalampasan ng npm.

**Mga sintomas:**

- Nagka-crash ang server sa pagsisimula at ipinapakita ang `Cannot find module 'better-sqlite3'`
- Ipinapakita ng `ls node_modules/better-sqlite3` ang "No such file or directory"
- Ipinapakita ng `npm ls better-sqlite3` ang `(empty)`

**Pag-aayos:**

1. Aprubahan ang mga install script at muling mag-install:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. O manu-manong i-install ang prebuilt:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. I-verify na gumagana ito: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Sanhi:** Pagkatapos ng global na `npm install -g omniroute`, maaaring na-compile ang native binary ng `better-sqlite3` sa loob ng package para sa ibang architecture o Node.js ABI kaysa sa lokal na ginagamit. Karaniwan ito sa macOS (Apple Silicon man o Intel) kapag hindi tugma sa iyong environment ang pre-built binary.

**Mga sintomas:**

- Agad na nabibigo ang server sa pagsisimula dahil sa isang `dlopen` error
- Naglalaman ang error ng `slice is not valid mach-o file`
- Buong halimbawa:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Pag-aayos — muling i-build para sa iyong lokal na environment (hindi kailangang mag-downgrade ng Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Tandaan:** Muli nitong kino-compile ang native binding ayon sa iyong lokal na bersyon ng Node.js at CPU architecture, na lumulutas sa hindi pagtutugma ng binary. Ang opisyal na sinusuportahang runtime range ay **`>=22.22.2 <23` o `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` sa `src/shared/utils/nodeRuntimeSupport.ts`, na nakaayon sa `engines` field ng `package.json`). Ganap na sinusuportahan ang Node.js 24.x LTS (Krypton) at Node.js 26 gamit ang `better-sqlite3` v12.x.

## Mga Isyu sa Proxy

<a name="proxy-issues"></a>

### Ipinapakita ng pagpapatunay ng provider ang "fetch failed"

**Sanhi:** Dati, nilalampasan ng endpoint para sa pagpapatunay ng API key (`POST /api/providers/validate`) ang configuration ng proxy, na nagdudulot ng mga pagkabigo sa mga environment na nangangailangan ng pagruruta sa proxy.

**Ayos (v3.5.5+):** Naayos na ito. Dumaraan na ang pagpapatunay ng provider sa `runWithProxyContext`, na awtomatikong sumusunod sa mga setting ng proxy sa antas ng provider at sa pangkalahatan.

### Nabibigo ang pagsusuri sa kalagayan ng token na may "fetch failed"

**Sanhi:** Hindi nire-resolve ng pang-background na pag-refresh ng OAuth token ang configuration ng proxy para sa bawat koneksyon.

**Ayos (v3.5.5+):** Nire-resolve na ngayon ng scheduler ng pagsusuri sa kalagayan ng token ang configuration ng proxy para sa bawat koneksyon bago subukang mag-refresh. Mag-update sa v3.5.5+.

### Nagbabalik ang SOCKS5 proxy ng "invalid onRequestStart method"

**Sanhi:** Sa Node.js 22, hindi compatible ang dispatcher ng undici@8 sa built-in na implementasyon ng `fetch()` ng Node.

**Ayos (v3.5.5+):** Ginagamit na ngayon ng OmniRoute ang sariling function na `fetch()` ng undici kapag aktibo ang isang proxy dispatcher, na tinitiyak ang pare-parehong gawi. Mag-update sa v3.5.5+.

### MITM proxy sa ilalim ng WSL: hindi nai-intercept ang mga desktop app sa Windows host

**Sanhi:** Nai-install ang MITM proxy at ang CA certificate nito sa environment kung saan tumatakbo ang OmniRoute. Sa ilalim ng WSL, ang environment na iyon ay ang Linux guest, habang tumatakbo naman sa Windows host ang mga AI desktop app (Kiro, Trae, Copilot, Zed, …). Hindi pinagkakatiwalaan ng mga host app ang certificate store ng guest at hindi dumaraan ang mga ito sa system proxy ng guest, kaya hindi gumagana roon ang pag-intercept sa desktop.

**Rekomendasyon:** Patakbuhin ang OmniRoute nang native sa parehong OS kung saan tumatakbo ang mga desktop app na gusto mong i-intercept (Windows para sa mga Windows app; gayundin para sa macOS/Linux). Kung pananatilihin ang OmniRoute sa loob ng WSL habang tina-target ang mga host app, kailangan mong manu-manong pagkatiwalaan ang nabuong CA certificate sa Windows host at ituro ang mga setting ng network/proxy ng bawat host app sa endpoint ng WSL proxy — isang hindi suportado at madaling masirang setup.

## Mga Isyu sa Docker

### Docker IPv6 / Pag-reset ng Koneksyon

<a name="docker-ipv6"></a>

**Mga Sintomas:** Nagbabalik ang `curl http://localhost:20128/v1/models` ng `curl: (56) Recv failure: Connection reset by peer`. Gumagana ang dashboard at mga endpoint na hindi nangangailangan ng authentication, ngunit pumapalya ang mga authenticated endpoint — mukhang problema ito sa authentication ngunit hindi.

**Sanhi:** Nagpa-publish ang `docker run -p 20128:20128` sa parehong `0.0.0.0` (IPv4) at `::` (IPv6), ngunit sa IPv4 lamang nakikinig ang proseso sa loob ng container. Sa mga host kung saan unang nagre-resolve ang `localhost` sa `::1`, napupunta ang koneksyon sa naka-publish na IPv6 port na walang listener sa likod nito → mare-reset ang koneksyon.

**Ayos:**

1. **Mabilisang pagsusuri:** Patakbuhin ang `curl -4 http://localhost:20128/v1/models`. Kung gumagana ito gamit ang `-4` ngunit pumapalya kapag wala iyon, mayroon kang hindi pagtutugma sa IPv6 bind.
2. **Permanenteng ayos:** Tahasang mag-bind sa IPv4 sa pamamagitan ng paggamit ng `-p 127.0.0.1:20128:20128` sa iyong `docker run` command:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Pinipilit nito ang IPv4 bind at iniiwasan ding ilantad ang proxy sa lahat ng interface ng host.

## Mga Setting ng Resilience

### Hindi nati-trigger ang awtomatikong rate-limit

- Nalalapat lamang ang awtomatikong rate-limit sa mga provider ng API key (hindi sa OAuth/subscription)
- Tiyaking naka-enable ang awtomatikong rate-limit sa **Settings → Resilience → Provider Profiles**
- Tingnan kung nagbabalik ang provider ng mga `429` status code o `Retry-After` header

### Pagsasaayos ng exponential backoff

Sinusuportahan ng mga profile ng provider ang mga setting na ito:

- **Base delay** — Paunang tagal ng paghihintay pagkatapos ng unang pagkabigo (default: 1s)
- **Max delay** — Pinakamataas na limitasyon ng tagal ng paghihintay (default: 30s)
- **Multiplier** — Gaano kalaki ang itataas sa delay sa bawat magkakasunod na pagkabigo (default: 2x)

### Pag-iwas sa thundering herd

Kapag maraming magkakasabay na request ang tumama sa isang provider na naka-rate-limit, gumagamit ang OmniRoute ng mutex + awtomatikong rate-limiting upang isa-isahin ang mga request at maiwasan ang sunod-sunod na pagkabigo. Awtomatiko ito para sa mga provider ng API key.

### Nabibigo ang mga chat request na may 503 / chat_admission_busy

**Mga sintomas:**

- Nagbabalik ang endpoint ng chat completions ng retryable na `503` response na ang error code ay
  `chat_admission_busy`.
- Kasama sa response ang `Retry-After`. Mula noong #12135, hinango ang value mula sa naobserbahang
  occupancy — alinman ang mas malaki sa window na `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` na naihintay na
  ng request at sa tagal na hawak ang kasalukuyang mga heavyweight lease — niro-round up sa buong
  segundo at nililimitahan sa 60. Kapag idle ang gate, pinananatili nito ang mga dating minimum: 2 segundo sa
  byte-based na path, 1 segundo sa structure-based na path (na kinabibilangan din ng
  `reason: "structure_limit"`).
- Maaari itong mangyari habang pinoproseso pa rin ang isa pang heavyweight chat o matagal na streaming
  response.

Ang byte-based na response body ay:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Ginagamit ng structure-based na response ang parehong type at code, kasama ang message na
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
at `reason: "structure_limit"`.
Sa mga default na threshold, itinuturing na structurally heavy ang isang request kapag mayroon itong hindi bababa sa `200` message,
hindi bababa sa `64` tool, o hindi bababa sa `32,000` tinatayang token, o kapag naubos ng bounded structure estimation
ang mga limitasyon nitong `10,000` binisitang node o depth na `12`.

**Sanhi:** Sinadyang load shedding ito sa loob ng OmniRoute, hindi pagkabigo ng upstream provider.
Gumagamit ang bawat process ng process-local na guard upang magreserba ng limitadong heavyweight capacity bago panatilihin
at i-parse ang malaking request body. Nananatiling hawak ang heavyweight lease sa buong lifecycle ng isang SSE
response.

**#503-fanout:** bago ang pag-aayos na ito, nililimitahan ng guard ang concurrency sa nakapirming request COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default `1`) anuman ang memory ng host, kaya ang fan-out ng coding-agent
(maraming subagent/CLI, mga body na karaniwang > 256 KB) ay bumabagsak sa epektibong
concurrency na ~1 at nakakatanggap ng 503 sa ilalim ng ganap na normal na load. Awtomatiko nang nagsasaayos ang guard: kinokontrol
ito ng awtomatikong hinangong ingest BYTE budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) na itinakda ayon sa
aktuwal na memory ceiling ng process, at kumukonsulta rin ito sa live na signal ng resource pressure — kaya
naglo-load shed lamang ito kapag talagang nakararanas ng memory pressure ang host, hindi dahil lamang mahigit sa isang
heavy request ang sabay-sabay na dumating. Sinusunod pa rin ang lumang count cap (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`),
ngunit kung tahasan mo lamang itong itinakda.

Kapag abala ang capacity, naghihintay muna ang heavyweight request nang hanggang
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default `2000`, dini-disable ng `0` ang paghihintay) para magkaroon ng bakanteng slot
bago tumugon ng retryable na `503`. Umiiral ang bounded na paghihintay upang ang mga agent-style na client
(OpenCode, Claude Code, Cursor) na sabay-sabay na nagfa-fan out ng mabibigat na sub-request ay isa-isahin ang biglaang pagdami
sa halip na ubusin ang kanilang buong retry budget sa mga agarang pagtanggi at mabigo sa gitna ng gawain.
Makikita sa `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ang kasalukuyang occupancy ng heavyweight lease, ang nalutas na byte budget, at ang
live na tindi ng pressure — suriin ang mga ito bago baguhin ang anumang env var.
Hindi ito kinokontrol ng Settings → Resilience → Request Queue → Concurrent Requests; ang setting na iyon
ay namamahala sa hiwalay na mekanismo ng request queue ng provider.

**Pag-aayos:**

1. Subukan munang muli. Dapat sundin ng mga client ang `Retry-After` at gumamit ng backoff sa halip na agad
   ulitin ang request.
2. Suriin ang `/api/monitoring/health` → `chatAdmission` bago magsaayos ng anuman. Ang `countCapEnabled:
false` at malaking `maxInflightBytes` ay nangangahulugang maayos nang gumagana ang awtomatikong hinangong budget;
   ang `pressureSeverity` na `high`/`critical` ay nangangahulugang talagang kapos sa memory ang host —
   hindi ito maaayos ng admission env var; kailangan nito ng mas maraming RAM o mas maliit na workload.
3. Kung ipinapakita lamang ng `/api/monitoring/health` na talagang napakaliit ng awtomatikong hinangong budget para sa
   iyong host (bihira — awtomatiko na itong nag-i-scale mula container hanggang bare-metal), direktang i-override ito gamit ang
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` sa halip na bumalik sa legacy na request-count cap.

Tingnan ang [sanggunian ng environment variable](../reference/ENVIRONMENT.md#4-security--authentication)
para sa opisyal na mga setting ng admission.

## Opsyonal na taksonomiya ng mga pagkabigo sa RAG / LLM (16 na problema)

Inilalagay ng ilang gumagamit ng OmniRoute ang gateway sa harap ng mga RAG o agent stack. Sa mga ganitong setup, karaniwang makakita ng kakaibang pattern: mukhang maayos ang OmniRoute (gumagana ang mga provider, maayos ang mga routing profile, walang alerto sa rate limit) ngunit mali pa rin ang huling sagot.

Sa aktuwal, karaniwang nagmumula ang mga insidenteng ito sa downstream na RAG pipeline, hindi sa gateway mismo.

Kung gusto ninyo ng iisang bokabularyo upang ilarawan ang mga pagkabigong iyon, maaari ninyong gamitin ang WFGY ProblemMap, isang panlabas na mapagkukunang teksto na may lisensyang MIT na tumutukoy sa labing-anim na paulit-ulit na pattern ng pagkabigo sa RAG / LLM. Sa pangkalahatan, saklaw nito ang:

- paglihis ng retrieval at mga sirang hangganan ng konteksto
- mga walang laman o lipas na index at vector store
- hindi pagtutugma ng embedding at semantika
- mga isyu sa pagbuo ng prompt at context window
- pagbagsak ng lohika at mga sagot na labis ang kumpiyansa
- mga pagkabigo sa mahabang chain at koordinasyon ng agent
- paglihis ng memorya at tungkulin sa multi-agent
- mga problema sa pagkakasunod-sunod ng deployment at bootstrap

Simple ang ideya:

1. Kapag nagsisiyasat kayo ng maling tugon, itala ang:
   - gawain at kahilingan ng gumagamit
   - route o kumbinasyon ng provider sa OmniRoute
   - anumang konteksto ng RAG na ginamit sa downstream (mga nakuhang dokumento, tool call, atbp.)
2. Itugma ang insidente sa isa o dalawang numero ng WFGY ProblemMap (`No.1` … `No.16`).
3. Itabi ang numero sa sarili ninyong dashboard, runbook, o incident tracker katabi ng mga log ng OmniRoute.
4. Gamitin ang kaukulang pahina ng WFGY upang matukoy kung kailangan ninyong baguhin ang inyong RAG stack, retriever, o routing strategy.

Narito ang kumpletong teksto at mga kongkretong recipe (lisensyang MIT, teksto lamang):

[README ng WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Maaari ninyong balewalain ang seksyong ito kung hindi kayo nagpapatakbo ng mga RAG o agent pipeline sa likod ng OmniRoute.

## Mga Kilalang Isyu sa v3.8.0

Mga isyung partikular sa release na v3.8.0 at ang kasalukuyang mga pansamantalang solusyon sa mga ito. Kung maisasama ang pag-aayos sa isang susunod na patch, ia-update o aalisin ang entry.

### Mga pagkabigo sa auth ng Devin CLI

**Mga sintomas:**

- "Hindi nakita ang Devin CLI" o "nabigo ang auth" kapag ginagamit ang mga tool na sinusuportahan ng Devin
- Iniuulat ng pagsusuri sa runtime ng CLI ang `installed=false`

**Mga sanhi:**

- Tumuturo ang `CLI_DEVIN_BIN` sa isang path na hindi umiiral
- Hindi naka-install ang Devin CLI sa host

**Pag-aayos:**

1. I-install ang Devin CLI para sa inyong platform
2. Itakda ang `CLI_DEVIN_BIN=/usr/local/bin/devin` (o ang tunay na path) sa `.env`
3. I-restart ang OmniRoute at muling subukan mula sa **Dashboard → Mga Tool ng CLI**

### Na-stuck ang cooldown ng modelo (manu-manong pag-reset)

**Mga sintomas:**

- Nananatiling nakalista sa cooldown ang isang modelo kahit lumipas na ang oras ng pag-expire
- Nilalaktawan pa rin ng mga kahilingan ang modelo sa combo routing kahit nasa nakaraan na ang timestamp

**Manu-manong pag-reset:**

- **Dashboard:** **Mga Setting → Mga Cooldown ng Modelo** → i-click ang **Muling Paganahin** sa apektadong card
- **API:** `DELETE /api/resilience/model-cooldowns` na may mga management auth header

### Nabibigo ang koneksyon sa provider ng Command Code at nagbabalik ng 403

**Mga sintomas:**

- 403 kapag sinusubukan ang koneksyon sa provider ng Command Code
- Ipinapakita ng provider card ang "hindi awtorisado" pagkatapos itong bagong idagdag

**Sanhi:** Hindi nakumpleto ang daloy ng OAuth (hindi natanggap ang callback o hindi na-save ang token).

**Pag-aayos:**

- Patakbuhin ang `omniroute providers` mula sa CLI upang muling simulan ang daloy ng OAuth, o
- Muling patakbuhin ang OAuth mula sa **Dashboard → Mga Provider → Command Code → Muling Kumonekta**

### Nagbabalik ang ModelScope ng mga agresibong 429 cooldown

**Mga sintomas:**

- Napakaikli o agarang mga cooldown sa ModelScope pagkatapos ng maliit na bugso ng mga kahilingan
- Nilalaktawan ng combo routing ang ModelScope nang mas maaga kaysa sa inaasahan

**Sanhi:** Naglalabas ang ModelScope ng mga header na `Retry-After` na partikular sa provider. May nakalaang pagproseso ang v3.8.0 para sa mga header na iyon, kaya maling binabasa ng mga mas lumang bersyon ang mga ito bilang mga pangkalahatang pahiwatig ng rate limit.

**Pag-aayos:**

- Tiyaking gumagamit kayo ng v3.8.0 o mas bago
- Tiyaking naka-enable ang toggle na `useUpstream429BreakerHints` sa ilalim ng **Mga Setting → Resilience**

### Nawawala ang OMNIROUTE_WS_BRIDGE_SECRET sa production

**Mga sintomas:**

- 401 sa bawat kahilingan sa Codex/Responses WebSocket bridge kapag tumatakbo sa isang remote na production host
- Agad na nagsasara ang handshake ng WebSocket bridge pagkatapos kumonekta

**Sanhi:** Nawawala sa production environment ang env var na `OMNIROUTE_WS_BRIDGE_SECRET`.

**Pag-aayos:**

1. Bumuo ng random na secret: `openssl rand -hex 32`
2. Itakda ang `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` sa env ng production server (at sa anumang client na nakikipag-ugnayan sa bridge)
3. I-restart ang OmniRoute

### Responses API: ibinaba ang background mode sa synchronous

**Mga sintomas:**

- Naka-log na babala: `background mode degraded to synchronous`
- Ang isang kahilingang `background: true` ay nagbabalik ng normal na synchronous na tugon sa halip na isang handle ng background job

**Sanhi:** Sinasadyang ibinababa ng v3.8.0 ang `background: true` sa Responses API patungo sa synchronous execution habang naglalabas ng babala. Ang ganap na async background execution ay ihahatid sa hinaharap.

**Pag-aayos:**

- I-adjust ang client upang tumawag nang walang `background`, o
- Hintayin ang susunod na release na may ganap na async background mode (subaybayan ang changelog)

## Mabagal na Pagsisimula / Timeout sa Kahandaan

Kung ipinapakita ng CLI ang `⚠ Server did not respond within 60s` ngunit
gumagana naman talaga ang server, masyadong maikli ang nakalaang oras ng readiness probe para sa iyong environment.

Karaniwan itong nangyayari sa Windows (antivirus, mga filesystem watcher) o sa mga container
na may mabibigat na workload sa pagsisimula.

**Solusyon — dagdagan ang nakalaang oras:**

```bash
# Sa pamamagitan ng env var (mananatili sa bawat pagsisimula):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuto
omniroute serve

# Sa pamamagitan ng CLI flag (isang beses lamang):
omniroute serve --ready-timeout 180000
```

Ang default ay 60 000 ms (60 s). Pang-impormasyon lamang ang babala; patuloy na
magsisimula ang server sa background at maa-access ito kapag nakumpleto na ang pag-boot.

Tingnan ang [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para sa kumpletong
detalye tungkol sa `OMNIROUTE_READY_TIMEOUT_MS`.
