## Mabilisang Sanggunian

**Bago sa OmniRoute?** Magsimula rito — nalulutas ng mga ito ang 90% ng mga problema:

| Nakikita ko ito               | Ang ibig sabihin nito                           | Ano ang gagawin                                                                                                                     |
| ----------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| "Can't connect"               | Hindi tumatakbo ang OmniRoute                   | Patakbuhin ang `omniroute` o `docker restart omniroute`                                                                             |
| "Invalid API key"             | Mali o nag-expire na ang iyong key              | Kopyahin muli ang key mula sa website ng provider                                                                                   |
| "Rate limit exceeded"         | Masyadong marami ang ipinapadala mong request   | Maghintay nang 1 minuto, o gamitin ang `model: "auto"` para sa awtomatikong fallback                                                |
| "Quota exceeded"              | Naubos mo na ang libre/binayarang quota mo      | Magkonekta ng higit pang provider, o gumamit ng mga libreng provider (Kiro, Pollinations)                                           |
| "Slow responses"              | Abala o malayo ang provider                     | Gamitin ang `model: "auto/fast"` o magkonekta ng mas mabilis na provider (Groq, Cerebras)                                           |
| "Wrong provider used"         | Pumili ang `auto` ng ibang provider             | Normal lang iyan! Pinipili ng `auto` ang pinakamahusay. Pilitin ang isang partikular na provider gamit ang `model: "openai/gpt-4o"` |
| "502 Bad Gateway"             | Hindi gumagana ang provider                     | Maghintay at subukang muli, o gamitin ang `model: "auto"` upang lumipat ng provider                                                 |
| "401 Unauthorized"            | Mali ang iyong mga kredensyal                   | Suriin ang iyong API key o muling mag-authenticate gamit ang OAuth                                                                  |
| "omniroute is not recognized" | Wala sa Windows PATH ang mga global node module | Idagdag ang iyong npm global prefix sa Windows PATH. Hanapin ito gamit ang `npm config get prefix`.                                 |
| "429 Too Many Requests"       | Nilimitahan ang rate                            | Maghintay nang 1 minuto, o magkonekta ng higit pang provider                                                                        |

**Hindi pa rin malutas?** Tingnan ang [detalyadong pag-troubleshoot](#detailed-troubleshooting) sa ibaba, o magtanong sa [Discord](https://discord.gg/U47eFqAXCn).

## Detalyadong Pag-troubleshoot

### Paglilimita sa Rate sa Mga Libreng Provider (429 / 400 / 401)

**Sintomas**: Kapag ginagamit ang `model: "auto"` kasama ng mga libre/walang-auth na provider (opencode, auggie, atbp.), paminsan-minsan kang nakakakuha ng `HTTP 429`, `400`, o `401` sa halip na mga sagot. Nagtatagumpay ang mga request kapag muling sinusubukan ang parehong prompt makalipas ang ilang sandali, ngunit humihinto ang automation (mga cron job, agent, script) sa unang pagkabigo.

**Pangunahing sanhi**: Nagsasama-sama ang tatlong magkakahiwalay na uri ng pagkabigo:

1. **Rate limit ng provider (`429`)**: Maaaring magpatupad ang mga libreng tier ng quota sa bawat takdang panahon. Nauubos ito ng biglaang pagdami ng magkakasabay na call, kaya tinatanggihan ang susunod na request hanggang sa mag-reset ang takdang panahon.
2. **Sirang model sa passthrough (`400`/`401`)**: Maaaring magsama ang mga `auto/*` pool ng mga passthrough model mula sa `opencode` na nakarehistro sa catalog ngunit walang aktibong kredensyal (hal. `oc/north-mini-code-free` → `401`). Susubukan ng auto-router ang isa, mabibigo ito, at maipapasa ang error bago pa gumana ang fallback.
3. **Pagpapalakas dahil sa concurrency (`429` kapag mataas ang load)**: Kapag sabay-sabay na gumagamit ng `auto` ang maraming agent/cron session, lumalampas ang pinagsama-samang rate ng request sa kayang tanggapin ng mga libreng provider, kaya namamarkahang mapang-abuso ang mga lehitimong call.

**Napatunayang pag-aayos (iniulat ng komunidad, 2026-08-10)**: isaayos ang tatlong environment variable upang masalo ng rotation, concurrency, at fallback ang pabago-bagong kondisyon ng libreng tier sa halip na tuluyang huminto dahil dito:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # lumipat sa ibang model/provider kapag 400/401 (nilalaktawan ang mga sirang passthrough model)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # tahasang maximum ng admission para sa heavyweight (bilang default, hindi nakatakda: walang limitasyon sa bilang ng request, tingnan ang tala sa ibaba)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # taasan ang limitadong paghihintay nang lampas sa default ng RATE_LIMIT_MAX_WAIT_MS para sa mababagal na upstream
```

Itakda ang mga ito sa process environment ng OmniRoute (ang daemon, hal. sa pamamagitan ng LaunchAgent plist o `systemctl edit`), pagkatapos ay i-restart ang OmniRoute. Ang rotation flag ang nag-iisang hakbang na may pinakamalaking epekto: ginagawa nitong transparent na muling pagsubok sa isang gumaganang provider sa pool ang isang ganap na pagkabigo.

**Tala**: Nililimitahan ng `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` kung ilang heavyweight — long-context — na request ang sabay-sabay na tatakbo; ang limitasyong ito ay isang admission gate, hindi isang rate limiter ng provider. **Update sa #503-fanout:** hindi na nakatakda bilang default ang var na ito (umiiral na lamang ito kapag tahasang na-configure, gaya sa itaas) — sa halip, ang heavyweight admission ay kinokontrol ng awtomatikong kinukuwentang byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) na awtomatikong umaayon sa aktuwal na limitasyon ng memory ng host, kaya dapat makakita ang isang bagong deployment ng mas kaunting pagtanggi na `503 chat_admission_busy` nang hindi kailangang itakda ang var na ito; gagana pa rin nang eksakto ayon sa dokumentasyon ang tahasang pagtatakda nito rito. Ang mga tahasang override sa byte budget ay nililimitahan sa 8 MiB–2 GiB. Hindi pansamantala ang isang `413 body_exceeds_budget`: taasan ang byte budget na iyon, babaan ang `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, o taasan ang limitasyon ng memory ng process. Ang isang `inflight_bytes_budget` shed ay pansamantalang contention at maaari pa ring subukang muli. Hiwalay na pinamamahalaan ang paglilimita sa rate para sa bawat provider (`open-sse/services/rateLimitManager.ts`) ng `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, at `RATE_LIMIT_AUTO_ENABLE` — tingnan ang `.env.example`.

**Paano tiyaking gumana ito**: patakbuhin ang iyong agent/cron nang dalawang beses nang magkasunod at tiyaking parehong matagumpay. Bago ang pag-aayos, karaniwang naghahagis ng `429`/`401` ang pangalawang pagtakbo. Pagkatapos ng pag-aayos, ang mga pagkabigo (kung mayroon man) ay awtomatikong sinusubukang muli at nakukumpleto ang tawag. Maaari mo ring patakbuhin ang `curl /monitoring/health` at subaybayan ang field na `rateLimitedUntil` sa mga koneksyon ng provider at ang `circuitBreakers.providerBreakers[].state` para sa mga apektadong provider — ang state ay isa sa `CLOSED`, `DEGRADED`, `OPEN`, o `HALF_OPEN` (tingnan ang `src/shared/utils/circuitBreaker.ts`), at ang provider na patuloy na nabibigo ay lilipat mula `CLOSED → DEGRADED → OPEN` bago magpahintulot ang reset window na makalusot ang isang probe (`HALF_OPEN`).

**Kung nakikita mo pa rin ang 429**: talagang naubos na ng aktibong account para sa provider na iyon ang _quota_ nito (hindi lang ang rate). Magdagdag ng pangalawang account para sa parehong provider sa OmniRoute dashboard → Providers → Accounts, o magsama ng isa pang libreng provider (hal. `routeway`, `auggie`). Nakakatulong lamang ang rotation sa pansamantalang rate/400/401; kapag ganap nang naubos ang quota, kailangan ng pangalawang credential o ibang provider.

**Kung nakikita mo ang 403 sa mga vision model (`auto/vision`, `bazaarlink/*`)**: walang bayad na plan ang nakakonektang account na may kasamang vision, o hindi sapat ang mga pahintulot ng API key. Tiyakin sa provider dashboard na kasama sa scope ng key ang vision/multimodal, o magkonekta ng paid tier account at panatilihin itong target para sa vision.

## Mga Babala sa npm install (ERESOLVE / peer / deprecated)

Kapag pinatakbo mo ang `npm install -g omniroute`, maaaring makakita ka ng napakaraming babala gaya ng `npm warn ERESOLVE`, mga abiso tungkol sa peer dependency, at mga mensaheng `deprecated`. **Inaasahan ang mga ito at hindi nakapipinsala.** Matagumpay ang iyong pag-install kung makikita mo ang `added <N> packages` sa output.

Upang hindi ipakita ang mga babala sa paglutas ng peer dependency, gamitin ang sinusuportahang paraan ng pag-install ng OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

Ang `--legacy-peer-deps` ay hindi nagpapakita ng `ERESOLVE` at mga abiso tungkol sa peer dependency lamang. Mananatiling nakikita ang mga abiso sa deprecation dahil nagmumula ang mga ito sa mga transitive na third-party package; hindi ipinahihiwatig ng mga ito na nabigo ang pag-install.

Nagmumula ang mga babala sa mga lipas na saklaw ng peer dependency sa mga third-party package na hindi kontrolado ng OmniRoute:

1. **Gusto ng `marked-terminal` ang `marked >=1 <16`, ngunit `marked@18` ang nahanap** — gumagana ito nang maayos sa aktuwal na paggamit; lipas lamang ang upstream na saklaw ng peer dependency.
2. **`deprecated prebuild-install@7.1.3`** — isang transitive na helper para sa pagkuha ng native binary. Hindi ito
   ginagamit upang i-install ang naka-pin na `wreq-js` transport binding at hindi nito ipinahihiwatig na nabigo ang
   pag-set up ng transport para sa web-cookie provider.

**Walang kinakailangang gawin** — hindi ganap na maitatago ang mga babala nang hindi nagfo-fork ng mga upstream package.

## Babala sa Na-block na npm install-scripts (pangkalahatang pag-install)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Kapag pinapatakbo ang `npm install -g omniroute`, bina-block ng mga mas bagong bersyon ng npm (v11+ at v12+) ang mga package lifecycle script bilang default at nagpapakita ng babala tungkol sa install-scripts:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Maaari bang balewalain ang babalang ito?

**Bahagya, ngunit hindi inirerekomenda ang pagpapatakbo nang walang mga script.** May kasamang maayos na mga fallback ang OmniRoute: kung hindi ma-load ang mga native na `better-sqlite3` binding mula sa standalone bundle, lilipat ang application sa mga alternatibong driver gaya ng `node:sqlite` o `sql.js` (tingnan ang [Paglutas sa SQLite Runtime](../ops/SQLITE_RUNTIME.md)). Magsisimula pa rin ang server, ngunit kapag tumatakbo sa mga WASM fallback gaya ng `sql.js`, hindi magagamit ang SQLite WAL (Write-Ahead Logging) mode at tataas ang overhead sa memory at pag-sync sa disk.

### Aling mga script ang talagang kinakailangan?

Hindi lahat ng na-block na script ay mahalaga upang mapatakbo ang OmniRoute:

- **Mahalaga (`omniroute`, `better-sqlite3`):** Tumatakbo ang OmniRoute mula sa isang Next.js standalone application bundle (`dist/`). Sa panahon ng pag-install, dina-download o kino-compile ng npm ang native na SQLite driver na partikular sa host sa pinakamataas na antas na `node_modules/better-sqlite3/`. Pagkatapos, vine-verify at kinokopya ng `postinstall` script (`scripts/build/postinstall.mjs`) ng OmniRoute ang mga binary na ito na partikular sa host papunta sa `dist/node_modules/` upang ma-access ng standalone server ang mga ito. Kung na-block ang postinstall script ng `omniroute`, lalaktawan ang hakbang na ito ng pagkopya.
- **Opsyonal/transitive (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Mga build helper, watcher tool, o system keychain utility ang mga ito. Kapag pinahintulutan ang mga ito, maiiwasan ang mga babala sa build, ngunit hindi kailangan ang mga ito para sa pangunahing functionality ng routing.
- **Hindi kasama (`onnxruntime-node`):** Isang opsyonal na dependency para sa mga lokal na AI embedding at **hindi** kinakailangan upang mapatakbo ang OmniRoute. Nagda-download ang postinstall script nito ng humigit-kumulang 300MB na CUDA asset mula sa NuGet; huwag itong isama sa allow-list maliban kung tahasan mong nilalayong gumamit ng lokal na ONNX acceleration sa sinusuportahang hardware.

### Inirerekomendang solusyon

Upang payagan ang mga kinakailangang install script sa panahon ng isang pangkalahatang pag-install at alisin ang mga babala, ipasa ang `--allow-scripts` para sa OmniRoute at mga native dependency nito:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Bilang alternatibo, upang permanenteng i-configure ito para sa lahat ng pangkalahatang pag-install sa iyong user account:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### I-verify ang iyong pag-install

Pagkatapos ng pag-install, patakbuhin ang built-in na diagnostic tool upang matiyak na maayos ang mga native binding at runtime environment:

```bash
omniroute doctor
```

## Mga Maling Positibong Deteksyon ng Antivirus

<a name="antivirus-false-positives"></a>

### Kina-quarantine ng Avast/AVG ang `README.md` bilang `MD:HttpRequest-inf[Susp]`

**Isa itong maling positibong deteksyon. Walang nahawahan, at walang kailangang gawin.**

Nagpapatakbo ang Avast at AVG ng heuristic na nagfa-flag sa mga plain-text/Markdown file na naglalaman ng maraming
link na mukhang HTTP request. Kasama ang `README.md` ng OmniRoute sa npm package (nakalista ito
sa `package.json` → `files`), kaya napupunta ito sa `node_modules/omniroute/README.md` kapag
nag-global install — at naglalaman ito ng ~15 halimbawa ng `http://localhost:20128/...` (ang mga MCP
HTTP/SSE endpoint, ang A2A `.well-known` URL, at mga snippet ng `curl`). Sapat ang dami ng mga
link na iyon upang ma-trigger ang heuristic.

Kung kamakailan lamang ito nagsimula: hindi nagbago ang uri ng file. Lumaki ang talahanayan ng mga
endpoint sa README (idinagdag ang MCP HTTP + SSE + A2A) at nadagdagan ang mga halimbawa ng `curl`,
kaya lumampas ito sa threshold.

Ang file ay isang inert na dokumentasyong walang anumang executable na nilalaman. Maaari mo itong
ligtas na ibalik mula sa quarantine.

**Ano ang dapat gawin:**

1. **Ihinto ang mga notification** — ibukod ang direktoryo ng pag-install sa iyong antivirus
   (Avast: Settings → Exceptions), at idagdag ang path ng iyong global na `node_modules` at/o ang
   direktoryo ng data ng OmniRoute (`~/.omniroute/`).
2. **Iulat ang maling positibong deteksyon** — <https://www.avast.com/false-positive-file-form.php>,
   at ilakip ang na-quarantine na `README.md`. Ito ang solusyong makatutulong sa lahat, dahil
   ang heuristic ng vendor ang labis na tumutugon sa isang text file.

**Bakit hindi namin ito "inaayos" sa aming panig:** ang lahat ng halimbawa ay `http://localhost`,
at hindi maaaring maging `https` ang localhost nang walang abalang dulot ng self-signed certificate.
Ang pagsira sa ayos ng dokumentasyon upang makaiwas sa heuristic ng isang vendor ay makasasama sa
bawat mambabasa para lamang tugunan ang bug ng scanner.

### Tina-flag ng Kaspersky ang Desktop app bilang `PDM:Trojan.Win32.Generic`

**Isa itong maling positibong deteksyon mula sa isang behavioral heuristic. Walang nahawahan.**
Ang prefix na `PDM:` ng Kaspersky ay nangangahulugang nagmumula ang hatol sa Proactive Defense
Module (System Watcher) nito, na sinusuri kung ano ang _ginagawa_ ng installer sa halip na itugma
ito sa kilalang malware. Kapag na-trigger ito, "nire-rollback" ng Kaspersky ang buong pag-install
— binubura ang mga file na naisulat na nito — kaya nasisira o nawawala ang app.

Ang mga file na tina-flag nito ay mga karaniwang bahagi ng mga idineklara at open-source na
dependency na kasama sa desktop app, halimbawa:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` at
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ang library para sa browser automation
  na ginagamit para sa pag-login sa provider sa loob ng app at chat na sinusuportahan ng browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ang naka-pin na native binding ng `wreq-js` na ginagamit para sa browser-fingerprinted HTTP sa mga
  provider na gumagamit ng web cookie (`<arch>` ay `x64` o `arm64`).

**Bakit ito nati-trigger:** ang Windows installer ay **hindi pa code-signed**, kaya walang
reputasyon ang isang unsigned na NSIS installer at nagpapatakbo nang sukdulang agresibo ang mga
behavioral heuristic. Kapag isinama ang bundled na native DLL at daan-daang `.js` file na isinusulat
sa ilalim ng `%LOCALAPPDATA%\Programs\OmniRoute` (kabilang ang mga direktoryo ng package na may
hash suffix mula sa standalone build ng Next.js), sapat na iyon upang ma-trigger ang heuristic.
Nakaplano ang code signing; hangga't hindi pa ito naipatutupad, maaaring maulit ito sa mga bagong release.

**Ano ang dapat gawin:**

1. **I-verify muna ang iyong download** (upang matiyak na hindi binago ang file). Naglalathala ang
   bawat release ng `latest.yml`, kung saan sinasaklaw ng field na `sha512` (base64) ang installer na
   `OmniRoute.Setup.<version>.exe`. Sa PowerShell, mula sa folder na naglalaman ng installer:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Dapat tumugma ang output sa `latest.yml` → `sha512`. Kung hindi ito tumutugma, burahin ang file at
   muling i-download ito mula lamang sa [pahina ng mga release sa GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Ibalik + ibukod** — ibalik mula sa quarantine ang mga item na na-rollback at magdagdag ng exclusion
   para sa `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   pagkatapos ay muling mag-install.
3. **Iulat ang maling positibong deteksyon** — <https://opentip.kaspersky.com/>. Ang mga ulat ng maling
   positibong deteksyon na isinusumite ng mga user ay tunay na nagpapabilis sa paglalagay sa allowlist.

## Compatibility sa Node.js

<a name="nodejs-compatibility"></a>

### Nagka-crash ang pahina sa pag-login o nagpapakita ng error na "Module self-registration"

**Sanhi:** Gumagamit ka ng bersyon ng Node.js na wala sa aprubadong minimum na secure runtime ng OmniRoute. Ang pinakakaraniwang kaso ay ang paggamit ng mas lumang patch level ng Node 22 o 24 na mas mababa sa minimum na patched security version na kinakailangan ng OmniRoute.

**Mga sintomas:**

- Nagpapakita ang pahina sa pag-login ng blangkong screen o server error
- Ipinapakita ng console ang `Error: Module did not self-register` o mga katulad na error sa native binding
- Nagpapakita ang pahina sa pag-login ng **orange na banner ng babala** kasama ang bersyon ng iyong Node kung ang runtime ay wala sa sinusuportahang secure policy

**Solusyon:**

1. Mag-install ng sinusuportahang release ng Node.js LTS (inirerekomenda: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Suriin ang iyong bersyon: dapat ipakita ng `node --version` ang `v24.0.0` o mas bago sa 24.x LTS line
3. Muling i-install ang OmniRoute: `npm install -g omniroute`
4. I-restart: `omniroute`

> **Mga sinusuportahang secure na bersyon:** `>=22.22.2 <23` o `>=24.0.0 <27`. Ganap na sinusuportahan ang Node.js 24.x LTS (Krypton) at Node.js 26.

### npm v11+: Hindi naka-install ang `better-sqlite3` (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Sanhi:** Hinaharangan ng npm v11 (kasama sa Node.js 24+) bilang default ang mga install script para sa mga opsiyonal na
dependency. Dahil nakalista ang `better-sqlite3` sa `optionalDependencies`
at nangangailangan ito ng native compilation (`node-gyp rebuild`), tahimik itong nilalaktawan ng npm.

**Mga sintomas:**

- Nagka-crash ang server sa pagsisimula na may `Cannot find module 'better-sqlite3'`
- Ipinapakita ng `ls node_modules/better-sqlite3` ang "No such file or directory"
- Ipinapakita ng `npm ls better-sqlite3` ang `(empty)`

**Solusyon:**

1. Aprubahan ang mga install script at muling mag-install:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. O manu-manong i-install ang prebuilt:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Tiyaking gumagana ito: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Sanhi:** Pagkatapos ng global na `npm install -g omniroute`, maaaring na-compile ang native binary ng `better-sqlite3` sa loob ng package para sa ibang architecture o Node.js ABI kaysa sa lokal na ginagamit. Karaniwan ito sa macOS (kapwa Apple Silicon at Intel) kapag hindi tumutugma ang pre-built binary sa iyong environment.

**Mga sintomas:**

- Agad na pumapalya ang server sa pagsisimula na may error na `dlopen`
- Naglalaman ang error ng `slice is not valid mach-o file`
- Buong halimbawa:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Solusyon — muling i-build para sa iyong lokal na environment (hindi kailangang mag-downgrade ng Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Tandaan:** Muli nitong kino-compile ang native binding ayon sa iyong lokal na bersyon ng Node.js at CPU architecture, na lumulutas sa hindi pagtutugma ng binary. Ang opisyal na sinusuportahang runtime range ay **`>=22.22.2 <23` o `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` sa `src/shared/utils/nodeRuntimeSupport.ts`, na nakaayon sa field na `engines` ng `package.json`). Ganap na sinusuportahan ang Node.js 24.x LTS (Krypton) at Node.js 26 gamit ang `better-sqlite3` v12.x.

## Mga Isyu sa Proxy

<a name="proxy-issues"></a>

### Ipinapakita ng pagpapatunay ng provider ang "fetch failed"

**Sanhi:** Dati, nilalampasan ng endpoint para sa pagpapatunay ng API key (`POST /api/providers/validate`) ang configuration ng proxy, na nagdudulot ng mga pagkabigo sa mga environment na nangangailangan ng pagruruta sa proxy.

**Ayos (v3.5.5+):** Naayos na ito. Dumadaan na ang pagpapatunay ng provider sa `runWithProxyContext`, at awtomatikong sinusunod ang mga setting ng proxy sa antas ng provider at ang mga global na setting ng proxy.

### Nabibigo ang pagsusuri sa kalagayan ng token na may "fetch failed"

**Sanhi:** Hindi nire-resolve ng pag-refresh ng OAuth token sa background ang configuration ng proxy para sa bawat koneksyon.

**Ayos (v3.5.5+):** Nire-resolve na ngayon ng scheduler ng pagsusuri sa kalagayan ng token ang configuration ng proxy para sa bawat koneksyon bago subukang mag-refresh. Mag-update sa v3.5.5+.

### Nagbabalik ang SOCKS5 proxy ng "invalid onRequestStart method"

**Sanhi:** Sa Node.js 22, hindi compatible ang undici@8 dispatcher sa built-in na implementasyon ng `fetch()` ng Node.

**Ayos (v3.5.5+):** Ginagamit na ngayon ng OmniRoute ang sariling `fetch()` function ng undici kapag may aktibong proxy dispatcher, upang matiyak ang pare-parehong paggana. Mag-update sa v3.5.5+.

### MITM proxy sa ilalim ng WSL: hindi nahaharang ang mga desktop app sa Windows host

**Sanhi:** Nai-install ang MITM proxy at ang CA certificate nito sa environment kung saan tumatakbo ang OmniRoute. Sa ilalim ng WSL, ang environment na iyon ay ang Linux guest, habang tumatakbo naman sa Windows host ang mga AI desktop app (Kiro, Trae, Copilot, Zed, …). Hindi pinagkakatiwalaan ng mga host app ang certificate store ng guest at hindi dumaraan ang mga ito sa system proxy ng guest, kaya hindi gumagana roon ang pagharang sa desktop.

**Rekomendasyon:** Patakbuhin ang OmniRoute nang native sa kaparehong OS ng mga desktop app na gusto mong harangin (Windows para sa mga Windows app; gayundin para sa macOS/Linux). Kung pananatilihin ang OmniRoute sa loob ng WSL habang tina-target ang mga host app, kinakailangang manu-manong pagkatiwalaan ang nabuong CA certificate sa Windows host at ituro ang mga setting ng network/proxy ng bawat host app sa WSL proxy endpoint — isang hindi sinusuportahan at marupok na setup.

## Mga Isyu sa Docker

### Docker IPv6 / Pag-reset ng Koneksyon

<a name="docker-ipv6"></a>

**Mga Sintomas:** Nagbabalik ang `curl http://localhost:20128/v1/models` ng `curl: (56) Recv failure: Connection reset by peer`. Gumagana ang dashboard at mga endpoint na hindi nangangailangan ng authentication, ngunit pumapalya ang mga authenticated endpoint — mukhang problema ito sa authentication ngunit hindi.

**Sanhi:** Nagpa-publish ang `docker run -p 20128:20128` sa parehong `0.0.0.0` (IPv4) at `::` (IPv6), ngunit sa IPv4 lamang nakikinig ang process sa loob ng container. Sa mga host kung saan unang nagre-resolve ang `localhost` sa `::1`, napupunta ang koneksyon sa naka-publish na IPv6 port na walang listener sa likod nito → nare-reset ang koneksyon.

**Ayos:**

1. **Mabilisang diagnostic:** Patakbuhin ang `curl -4 http://localhost:20128/v1/models`. Kung gumagana ito gamit ang `-4` ngunit pumapalya kapag wala iyon, mayroon kang IPv6 bind mismatch.
2. **Permanenteng ayos:** Tahasang mag-bind sa IPv4 sa pamamagitan ng paggamit ng `-p 127.0.0.1:20128:20128` sa iyong `docker run` command:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Pinipilit nito ang IPv4 bind at iniiwasan din nitong ilantad ang proxy sa lahat ng interface ng host.

## Mga Setting ng Resilience

### Hindi nati-trigger ang awtomatikong rate-limit

- Nalalapat lamang ang awtomatikong rate-limit sa mga provider ng API key (hindi sa OAuth/subscription)
- Tiyaking naka-enable ang awtomatikong rate-limit sa **Settings → Resilience → Provider Profiles**
- Tingnan kung nagbabalik ang provider ng mga status code na `429` o mga header na `Retry-After`

### Pag-tune ng exponential backoff

Sinusuportahan ng mga profile ng provider ang mga setting na ito:

- **Base delay** — Paunang oras ng paghihintay pagkatapos ng unang pagkabigo (default: 1s)
- **Max delay** — Pinakamataas na limitasyon ng oras ng paghihintay (default: 30s)
- **Multiplier** — Gaano kalaki ang itataas sa delay sa bawat sunod-sunod na pagkabigo (default: 2x)

### Pag-iwas sa thundering herd

Kapag maraming sabay-sabay na request ang tumama sa isang provider na may rate-limit, gumagamit ang OmniRoute ng mutex + awtomatikong rate-limiting upang isa-isahin ang mga request at maiwasan ang sunod-sunod na pagkabigo. Awtomatiko ito para sa mga provider ng API key.

### Nabibigo ang mga chat request na may 503 / chat_admission_busy

**Mga sintomas:**

- Nagbabalik ang endpoint ng chat completions ng retryable na `503` response na ang error code ay
  `chat_admission_busy`.
- Kasama sa response ang `Retry-After`. Mula noong #12135, nakukuha ang value mula sa naobserbahang
  occupancy — alinman ang mas malaki sa window na `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` na ipinaghintay na
  ng request at sa tagal ng pagkakahawak sa mga kasalukuyang heavyweight lease — niro-round up sa buong
  segundo at nililimitahan sa 60. Sa idle na gate, pinananatili nito ang dating mga minimum: 2 segundo sa
  byte-based na path, 1 segundo sa structure-based na path (na kasama rin ang
  `reason: "structure_limit"`).
- Maaari itong mangyari habang may isa pang heavyweight chat o matagal tumakbong streaming response na
  kasalukuyang pinoproseso.

Ang byte-based na response body ay:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Gumagamit ang structure-based na response ng parehong type at code, kasama ang mensaheng
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
at `reason: "structure_limit"`.
Sa mga default na threshold, itinuturing na structurally heavy ang isang request kapag mayroon itong hindi bababa sa `200` message,
hindi bababa sa `64` tool, o hindi bababa sa `32,000` tinatayang token, o kapag naubos ng bounded structure estimation
ang mga hangganan nitong `10,000` binisitang node o depth na `12`.

**Sanhi:** Sinasadyang load shedding ito sa loob ng OmniRoute, hindi pagkabigo ng upstream provider.
Gumagamit ang bawat process ng process-local guard upang magreserba ng limitadong heavyweight capacity bago panatilihin
at i-parse ang isang malaking request body. Nananatiling hawak ang isang heavyweight lease sa buong tagal ng isang SSE
response.

**#503-fanout:** bago ang pag-aayos na ito, nililimitahan ng guard ang concurrency sa isang nakapirming BILANG ng request
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default na `1`) anuman ang memory ng host, kaya ang fan-out ng coding agent
(maraming subagent/CLI, mga body na karaniwang > 256 KB) ay bumabagsak sa epektibong
concurrency na ~1 at nagbabalik ng 503 sa ilalim ng ganap na normal na load. Awtomatiko nang nag-a-adjust ang guard: kinokontrol ito
ng awtomatikong nakuhang ingest BYTE budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) na ibinatay sa
aktuwal na memory ceiling ng process, at kumokonsulta rin ito sa live na signal ng resource pressure — kaya
naglo-load shed lamang ito kapag tunay na nasa ilalim ng memory pressure ang host, hindi dahil lamang sa higit sa isang
heavy request na dumating nang sabay-sabay. Sinusunod pa rin ang lumang count cap (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`),
ngunit kung tahasan mo lamang itong itinakda.

Kapag abala ang capacity, maghihintay muna ang isang heavyweight request nang hanggang
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default sa `RATE_LIMIT_MAX_WAIT_MS`; dini-disable ng `0` ang paghihintay) para may mabakanteng slot
bago sumagot gamit ang retryable na `503`. Umiiral ang bounded na paghihintay upang ang mga agent-style na client
(OpenCode, Claude Code, Cursor) na sabay-sabay na nagpapadala ng mga heavy sub-request ay maisa-isa ang burst
sa halip na ubusin ang kanilang buong retry budget sa mga agarang pagtanggi at huminto sa gitna ng gawain.
Makikita sa `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ang kasalukuyang occupancy ng heavyweight lease, ang nalutas na byte budget, at ang
live na tindi ng pressure — tingnan ang mga ito bago baguhin ang anumang env var.
Hindi ito kinokontrol ng Settings → Resilience → Request Queue → Concurrent Requests; ang setting na iyon
ay namamahala sa hiwalay na mekanismo ng request queue ng provider.

**Pag-aayos:**

1. Subukan munang muli. Dapat sundin ng mga client ang `Retry-After` at gumamit ng backoff sa halip na agad
   ulitin ang request.
2. Tingnan ang `/api/monitoring/health` → `chatAdmission` bago mag-tune ng anuman. Ang `countCapEnabled:
false` at malaking `maxInflightBytes` ay nangangahulugang gumagana na nang tama ang awtomatikong nakuhang budget;
   ang `pressureSeverity` na `high`/`critical` ay nangangahulugang tunay na kapos sa memory ang host —
   hindi ito maaayos ng isang admission env var; kailangan nito ng mas maraming RAM o mas maliit na workload.
3. Kung ipinapakita lamang ng `/api/monitoring/health` na tunay na napakaliit ng awtomatikong nakuhang budget para sa
   iyong host (bihira — awtomatiko na itong nag-i-scale mula container hanggang bare-metal), direktang i-override ito gamit ang
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` sa halip na bumalik sa legacy na request-count cap.

Tingnan ang [sanggunian ng environment variable](../reference/ENVIRONMENT.md#4-security--authentication)
para sa opisyal na mga setting ng admission.

## Opsyonal na taksonomiya ng mga pagkabigo sa RAG / LLM (16 na problema)

Inilalagay ng ilang user ng OmniRoute ang gateway sa harap ng mga RAG o agent stack. Sa mga ganitong setup, karaniwang makakita ng kakaibang pattern: mukhang maayos ang OmniRoute (gumagana ang mga provider, maayos ang mga routing profile, walang mga alerto sa rate limit) ngunit mali pa rin ang panghuling sagot.

Sa aktuwal na paggamit, karaniwang nagmumula ang mga insidenteng ito sa downstream na RAG pipeline, hindi sa mismong gateway.

Kung gusto ninyo ng magkakatulad na bokabularyo para ilarawan ang mga pagkabigong iyon, maaari ninyong gamitin ang WFGY ProblemMap, isang external na text resource na may MIT license na tumutukoy sa labing-anim na paulit-ulit na pattern ng pagkabigo sa RAG / LLM. Sa pangkalahatan, saklaw nito ang:

- paglihis ng retrieval at mga sirang hangganan ng context
- mga walang laman o lipas na index at vector store
- hindi pagtutugma ng embedding at semantika
- mga problema sa pagbuo ng prompt at context window
- pagbagsak ng lohika at mga sagot na labis ang kumpiyansa
- mga pagkabigo sa mahahabang chain at koordinasyon ng agent
- paglihis ng memorya at tungkulin sa multi-agent
- mga problema sa pagkakasunod-sunod ng deployment at bootstrap

Simple lang ang ideya:

1. Kapag nag-iimbestiga kayo ng maling tugon, itala ang:
   - gawain at request ng user
   - route o kumbinasyon ng provider sa OmniRoute
   - anumang RAG context na ginamit sa downstream (mga na-retrieve na dokumento, mga tool call, atbp.)
2. Itugma ang insidente sa isa o dalawang numero ng WFGY ProblemMap (`No.1` … `No.16`).
3. I-store ang numero sa sarili ninyong dashboard, runbook, o incident tracker katabi ng mga log ng OmniRoute.
4. Gamitin ang kaukulang pahina ng WFGY upang magpasya kung kailangan ninyong baguhin ang inyong RAG stack, retriever, o routing strategy.

Narito ang buong teksto at mga kongkretong recipe (MIT license, teksto lamang):

[README ng WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Maaari ninyong balewalain ang seksiyong ito kung hindi kayo nagpapatakbo ng mga RAG o agent pipeline sa likod ng OmniRoute.

## Mga Kilalang Isyu sa v3.8.0

Mga isyung partikular sa release na v3.8.0 at ang mga kasalukuyang workaround para sa mga ito. Kung magkaroon ng pag-aayos sa susunod na patch, ia-update o aalisin ang entry.

### Mga pagkabigo sa auth ng Devin CLI

**Mga sintomas:**

- "Hindi natagpuan ang Devin CLI" o "nabigo ang auth" kapag gumagamit ng mga tool na nakabatay sa Devin
- Iniulat ng CLI runtime check ang `installed=false`

**Mga sanhi:**

- Nakaturo ang `CLI_DEVIN_BIN` sa isang path na hindi umiiral
- Hindi naka-install ang Devin CLI sa host

**Pag-aayos:**

1. I-install ang Devin CLI para sa inyong platform
2. Itakda ang `CLI_DEVIN_BIN=/usr/local/bin/devin` (o ang aktuwal na path) sa `.env`
3. I-restart ang OmniRoute at subukang muli mula sa **Dashboard → Mga CLI Tool**

### Hindi nawawala ang cooldown ng modelo (manual na pag-reset)

**Mga sintomas:**

- Nananatiling nakalista ang isang modelo sa cooldown kahit lumipas na ang oras ng pag-expire
- Nilalaktawan pa rin ng mga request ang modelo sa combo routing kahit nakalipas na ang timestamp

**Manual na pag-reset:**

- **Dashboard:** **Mga Setting → Mga Cooldown ng Modelo** → i-click ang **Muling paganahin** sa apektadong card
- **API:** `DELETE /api/resilience/model-cooldowns` na may mga management auth header

### Nabibigo ang koneksiyon sa Command Code provider at nagbabalik ng 403

**Mga sintomas:**

- 403 kapag sinusubukan ang koneksiyon sa Command Code provider
- Ipinapakita ng provider card ang "hindi awtorisado" pagkatapos itong idagdag

**Sanhi:** Hindi nakumpleto ang OAuth flow (hindi natanggap ang callback o hindi na-save ang token).

**Pag-aayos:**

- Patakbuhin ang `omniroute providers` mula sa CLI upang muling simulan ang OAuth flow, o
- Patakbuhin muli ang OAuth mula sa **Dashboard → Mga Provider → Command Code → Muling kumonekta**

### Nagbabalik ang ModelScope ng mga agresibong 429 cooldown

**Mga sintomas:**

- Napakaikli o agarang mga cooldown sa ModelScope pagkatapos ng kaunting sunod-sunod na request
- Nilalaktawan ng combo routing ang ModelScope nang mas maaga kaysa sa inaasahan

**Sanhi:** Naglalabas ang ModelScope ng mga provider-specific na `Retry-After` header. May nakalaang paghawak ang v3.8.0 para sa mga header na iyon, kaya mali ang pagbasa sa mga ito ng mga mas lumang bersyon bilang mga pangkalahatang pahiwatig ng rate limit.

**Pag-aayos:**

- Tiyaking gumagamit kayo ng v3.8.0 o mas bago
- Tiyaking naka-enable ang toggle na `useUpstream429BreakerHints` sa ilalim ng **Mga Setting → Resilience**

### Nawawala ang OMNIROUTE_WS_BRIDGE_SECRET sa production

**Mga sintomas:**

- 401 sa bawat Codex/Responses WebSocket bridge request kapag tumatakbo sa isang remote na production host
- Agad na nagsasara ang WebSocket bridge handshake pagkatapos kumonekta

**Sanhi:** Nawawala ang `OMNIROUTE_WS_BRIDGE_SECRET` env var sa production environment.

**Pag-aayos:**

1. Bumuo ng random na secret: `openssl rand -hex 32`
2. Itakda ang `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` sa env ng production server (at sa anumang client na nakikipag-ugnayan sa bridge)
3. I-restart ang OmniRoute

### Responses API: bumaba sa synchronous ang background mode

**Mga sintomas:**

- Naka-log na babala: `background mode degraded to synchronous`
- Nagbabalik ang isang `background: true` request ng normal na synchronous response sa halip na background job handle

**Sanhi:** Sadyang ibinababa ng v3.8.0 ang `background: true` sa Responses API sa synchronous na pagpapatupad habang naglalabas ng babala. Ang ganap na async na background execution ay ihahatid sa hinaharap.

**Pag-aayos:**

- I-adjust ang client upang tumawag nang walang `background`, o
- Maghintay ng susunod na release na may ganap na async na background mode (subaybayan ang changelog)

## Mabagal na Pagsisimula / Timeout sa Kahandaan

Kung ipinapakita ng CLI ang `⚠ Server did not respond within 60s` ngunit
gumagana naman talaga ang server, masyadong maikli para sa iyong environment ang inilaan na oras para sa readiness probe.

Karaniwan itong nangyayari sa Windows (antivirus, mga filesystem watcher) o sa mga container
na may mabibigat na workload sa pagsisimula.

**Ayos — dagdagan ang inilaan na oras:**

```bash
# Sa pamamagitan ng env var (mananatili sa bawat pagsisimula):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuto
omniroute serve

# Sa pamamagitan ng CLI flag (isang beses lang):
omniroute serve --ready-timeout 180000
```

Ang default ay 60 000 ms (60 s). Pang-impormasyon lamang ang babala; patuloy na
magsisimula ang server sa background at maa-access ito kapag natapos ang pag-boot.

Tingnan ang [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para sa kumpletong
detalye tungkol sa `OMNIROUTE_READY_TIMEOUT_MS`.
