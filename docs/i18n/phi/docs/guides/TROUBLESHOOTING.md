## Mabilisang Sanggunian

**Bago sa OmniRoute?** Magsimula rito — nalulutas ng mga ito ang 90% ng mga problema:

| Nakikita ko ito                  | Ang ibig sabihin nito                         | Ang dapat gawin                                                                                                                                  |
| -------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| "Hindi makakonekta"              | Hindi tumatakbo ang OmniRoute                 | Patakbuhin ang `omniroute` o `docker restart omniroute`                                                                                          |
| "Hindi wastong API key"          | Mali o nag-expire na ang iyong key            | Kopyahin muli ang key mula sa website ng provider                                                                                                |
| "Lumampas sa limitasyon ng rate" | Masyado kang maraming ipinapadalang request   | Maghintay ng 1 minuto, o gamitin ang `model: "auto"` para sa awtomatikong fallback                                                               |
| "Lumampas sa quota"              | Naubos mo na ang iyong libre/binayarang quota | Kumonekta sa mas maraming provider, o gumamit ng mga libreng provider (Kiro, Pollinations)                                                       |
| "Mabagal na mga tugon"           | Abala o malayo ang provider                   | Gamitin ang `model: "auto/fast"` o kumonekta sa mas mabilis na provider (Groq, Cerebras)                                                         |
| "Maling provider ang ginamit"    | Pumili ang `auto` ng ibang provider           | Normal lang iyon! Pinipili ng `auto` ang pinakamahusay. Puwersahang gumamit ng partikular na provider sa pamamagitan ng `model: "openai/gpt-4o"` |
| "502 Bad Gateway"                | Hindi gumagana ang provider                   | Maghintay at subukang muli, o gamitin ang `model: "auto"` upang lumipat ng provider                                                              |
| "401 Unauthorized"               | Mali ang iyong mga kredensyal                 | Suriin ang iyong API key o muling mag-authenticate gamit ang OAuth                                                                               |
| "hindi nakikilala ang omniroute" | Walang mga global node module sa Windows PATH | Idagdag ang iyong npm global prefix sa Windows PATH. Hanapin ito gamit ang `npm config get prefix`.                                              |
| "429 Too Many Requests"          | Nilimitahan ang rate                          | Maghintay ng 1 minuto, o kumonekta sa mas maraming provider                                                                                      |

**Hindi pa rin malutas?** Tingnan ang [detalyadong pag-troubleshoot](#detailed-troubleshooting) sa ibaba, o magtanong sa [Discord](https://discord.gg/U47eFqAXCn).

## Detalyadong Pag-troubleshoot

---

### Paglilimita ng Rate sa mga Libreng Provider (429 / 400 / 401)

**Sintomas**: Kapag gumagamit ng `model: "auto"` kasama ang mga libre/hindi nangangailangan ng authentication na provider (opencode, auggie, atbp.), paminsan-minsan kang nakakatanggap ng `HTTP 429`, `400`, o `401` sa halip na mga sagot. Nagtatagumpay ang mga request kapag muling sinusubukan ang parehong prompt makalipas ang ilang sandali, ngunit humihinto ang automation (mga cron job, agent, script) sa unang pagkabigo.

**Pangunahing sanhi**: Nagsasabay-sabay ang tatlong magkakahiwalay na uri ng pagkabigo:

1. **Limitasyon ng rate ng provider (`429`)**: Maaaring magpatupad ang mga libreng tier ng quota sa bawat takdang panahon. Nauubos ito ng bugso ng magkakasabay na call, kaya tinatanggihan ang susunod na request hanggang sa mag-reset ang takdang panahon.
2. **Sirang model sa passthrough (`400`/`401`)**: Maaaring magsama ang mga pool na `auto/*` ng mga passthrough model mula sa `opencode` na nakarehistro sa catalog ngunit walang aktibong kredensyal (hal. `oc/north-mini-code-free` → `401`). Sinusubukan ng auto-router ang isa, nabibigo ito, at naipapasa ang error bago gumana ang fallback.
3. **Pagpapalala dahil sa concurrency (`429` kapag maraming load)**: Kapag maraming session ng agent/cron ang sabay-sabay na gumagamit ng `auto`, lumalampas ang pinagsama-samang rate ng request sa kayang tanggapin ng mga libreng provider, kaya namamarkahan bilang mapang-abuso ang mga lehitimong call.

**Napatunayang solusyon (iniulat ng komunidad, 2026-08-10)**: isaayos ang tatlong environment variable upang ang rotation, concurrency, at fallback ang sumalo sa pabago-bagong kondisyon ng libreng tier sa halip na tuluyang mabigo dahil dito:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # lumipat sa ibang model/provider kapag may 400/401 (nilalaktawan ang mga sirang passthrough model)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # tahasang pinakamataas na bilang ng heavyweight admission (hindi naka-set bilang default: walang limitasyon sa bilang ng request, tingnan ang tala sa ibaba)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # mas mahabang limitadong paghihintay para sa heavyweight capacity sa halip na agarang retryable na 503
```

I-set ang mga ito sa process environment ng OmniRoute (ang daemon, hal. sa pamamagitan ng LaunchAgent plist o `systemctl edit`), pagkatapos ay i-restart ang OmniRoute. Ang rotation flag ang nag-iisang may pinakamalaking epekto: ginagawa nitong transparent na retry sa isang maayos na provider sa pool ang isang ganap na pagkabigo.

**Tala**: Nililimitahan ng `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` kung ilang heavyweight — long-context — request ang tumatakbo nang sabay-sabay; admission gate ang limitasyon, hindi provider rate limiter. **Update sa #503-fanout:** hindi na naka-set bilang default ang var na ito (nalalapat lang ito ngayon kapag tahasang na-configure, gaya sa itaas) — sa halip, kinokontrol na ang heavyweight admission ng awtomatikong kinuhang byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) na kusang umaangkop batay sa aktuwal na memory ceiling ng host, kaya dapat makakita ang isang bagong deployment ng mas kaunting pagtangging `503 chat_admission_busy` nang hindi kailangang i-set ang var na ito; gagana pa rin nang eksakto tulad ng nakadokumento ang tahasang pag-set nito rito. Nililimitahan sa 8 MiB–2 GiB ang mga tahasang byte-budget override. Hindi pansamantala ang `413 body_exceeds_budget`: taasan ang byte budget na iyon, babaan ang `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`, o taasan ang process memory ceiling. Pansamantalang contention ang isang `inflight_bytes_budget` shed at maaari pa ring subukang muli. Hiwalay na pinamamahalaan ng `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, at `RATE_LIMIT_AUTO_ENABLE` ang paglilimita ng rate sa bawat provider (`open-sse/services/rateLimitManager.ts`) — tingnan ang `.env.example`.

**Paano tiyaking gumana ito**: patakbuhin ang iyong agent/cron nang dalawang beses nang sunod-sunod at tiyaking parehong matagumpay. Bago ang pag-aayos, karaniwang naglalabas ang ikalawang pagtakbo ng `429`/`401`. Pagkatapos ng pag-aayos, ang mga kabiguan (kung mayroon man) ay awtomatikong sinusubukang muli at nakukumpleto ang tawag. Maaari mo ring patakbuhin ang `curl /monitoring/health` at subaybayan ang field na `rateLimitedUntil` sa mga koneksyon ng provider at ang `circuitBreakers.providerBreakers[].state` para sa mga apektadong provider — ang estado ay isa sa `CLOSED`, `DEGRADED`, `OPEN`, o `HALF_OPEN` (tingnan ang `src/shared/utils/circuitBreaker.ts`), at ang provider na patuloy na nabibigo ay lilipat mula `CLOSED → DEGRADED → OPEN` bago magpahintulot ang palugit ng pag-reset na makalusot ang isang pagsubok (`HALF_OPEN`).

**Kung nakikita mo pa rin ang 429**: talagang naubos na ng aktibong account para sa provider na iyon ang _quota_ nito (hindi lang ang limitasyon sa dalas). Magdagdag ng pangalawang account para sa parehong provider sa OmniRoute dashboard → Providers → Accounts, o magsama ng isa pang libreng provider (hal. `routeway`, `auggie`). Nakakatulong lamang ang pag-ikot sa pansamantalang rate/400/401; kapag ganap nang naubos ang quota, kailangan ng pangalawang kredensyal o ibang provider.

**Kung nakikita mo ang 403 sa mga vision model (`auto/vision`, `bazaarlink/*`)**: walang bayad na planong may kasamang vision ang nakakonektang account, o hindi sapat ang mga pahintulot ng API key. Tiyakin sa dashboard ng provider na kasama sa saklaw ng key ang vision/multimodal, o magkonekta ng account na may bayad na tier at panatilihin ito bilang target para sa vision.

## Mga Babala sa npm install (ERESOLVE / peer / deprecated)

Kapag pinatakbo mo ang `npm install -g omniroute`, maaari kang makakita ng napakaraming babala tulad ng `npm warn ERESOLVE`, mga abiso tungkol sa peer dependency, at mga mensaheng `deprecated`. **Inaasahan ang mga ito at hindi nakapipinsala.** Matagumpay ang pag-install kung makikita mo ang `added <N> packages` sa output.

Upang itago ang mga babala sa pagresolba ng peer dependency, gamitin ang suportadong paraan ng pag-install ng OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

Ang `--legacy-peer-deps` ay nagtatago lamang ng `ERESOLVE` at mga abiso tungkol sa peer dependency. Mananatiling nakikita ang mga abiso sa deprecation dahil nagmumula ang mga ito sa mga transitive na third-party package; hindi ipinahihiwatig ng mga ito na nabigo ang pag-install.

Nagmumula ang mga babala sa mga lipas na saklaw ng peer dependency sa mga third-party package na hindi kontrolado ng OmniRoute:

1. **Kailangan ng `marked-terminal` ang `marked >=1 <16`, ngunit `marked@18` ang natagpuan** — gumagana ito nang maayos sa aktuwal na paggamit; lipas lamang ang upstream na saklaw ng peer dependency.
2. **`deprecated prebuild-install@7.1.3`** — isang transitive na helper para sa pagkuha ng native binary. Hindi ito
   ginagamit upang i-install ang naka-pin na `wreq-js` transport binding at hindi nito ipinahihiwatig na nabigo ang
   pag-setup ng transport ng web-cookie provider.

**Walang kailangang gawin** — hindi ganap na maitatago ang mga babala nang hindi nagfo-fork ng mga upstream package.

## Gemini Web at Playwright Chromium

Kung nagbabalik ang isang kahilingan sa Gemini Web ng `503` na may mensaheng hindi
naka-install ang Playwright Chromium, naroon ang npm package ngunit nawawala ang browser binary.
Sadyang hinihiwalay ng Playwright ang mga pag-download ng browser mula sa pag-install
ng npm package, kaya inaasahan ang tugong ito hanggang sa ma-install ang browser.

Para sa isang global na pag-install ng npm, i-install ang Chromium mula sa directory
ng OmniRoute package upang mapabilang ang browser cache sa parehong pag-install ng Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

I-restart ang OmniRoute pagkatapos ng pag-install, at pagkatapos ay subukang muli ang kahilingan sa Gemini Web. Kung
pinapatakbo mo ang OmniRoute mula sa isang Docker image, gamitin ang `-web` image (o ang `runner-web`
build target), na naglalaman ng Chromium at mga dependency nito; hindi kasama ang mga ito sa base image.

## Mabilisang Pag-aayos

| Problema                                                   | Solusyon                                                                                                                                                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hindi gumagana ang unang pag-login                         | Itakda ang `INITIAL_PASSWORD` sa `.env` (walang hardcoded na default)                                                                                                                                |
| Bumubukas ang dashboard sa maling port                     | Itakda ang `PORT=20128` at `NEXT_PUBLIC_BASE_URL=http://localhost:20128`                                                                                                                             |
| Walang mga log na isinusulat sa disk                       | Itakda ang `APP_LOG_TO_FILE=true` at tiyaking naka-enable ang pagkuha ng call log                                                                                                                    |
| EACCES: tinanggihan ang pahintulot                         | Itakda ang `DATA_DIR=/path/to/writable/dir` upang palitan ang `~/.omniroute`                                                                                                                         |
| Hindi nase-save ang routing strategy                       | Mag-update sa pinakabagong v3.x release (ang pag-aayos sa Zod schema para sa pagpapanatili ng mga setting ay kasama na sa mga naunang bersyon)                                                       |
| Pag-crash sa pag-login / blangkong page                    | Suriin ang bersyon ng Node.js — tingnan ang [Compatibility ng Node.js](#nodejs-compatibility) sa ibaba                                                                                               |
| `dlopen` / `slice is not valid mach-o file` (macOS)        | Patakbuhin ang `cd $(npm root -g)/omniroute/app && npm rebuild better-sqlite3 && omniroute` — tingnan ang [pag-rebuild ng native module sa macOS](#macos-native-module-rebuild) sa ibaba             |
| "fetch failed" ng proxy                                    | Tiyaking nakatakda ang proxy config sa tamang antas — tingnan ang [Mga Isyu sa Proxy](#proxy-issues) sa ibaba                                                                                        |

## Mga Maling Positibong Resulta ng Antivirus

<a name="antivirus-false-positives"></a>

### Inilalagay ng Avast/AVG sa quarantine ang `README.md` na may `MD:HttpRequest-inf[Susp]`

**Isa itong maling positibong resulta. Walang nahawahan, at walang kailangang gawin.**

Nagpapatakbo ang Avast at AVG ng heuristic na nagfa-flag ng mga plain-text/Markdown file na naglalaman ng maraming
link na mukhang HTTP request. Kasama ang `README.md` ng OmniRoute sa npm package (ito ay
nakalista sa `package.json` → `files`), kaya napupunta ito sa `node_modules/omniroute/README.md` sa
isang global install — at naglalaman ito ng ~15 halimbawa ng `http://localhost:20128/...` (ang mga MCP
HTTP/SSE endpoint, ang A2A `.well-known` URL, at mga snippet ng `curl`). Sapat ang dami ng
mga link na iyon upang ma-trigger ang heuristic.

Kung kamakailan lamang ito nagsimula: walang nagbago sa uri ng file. Lumawak ang talahanayan ng mga
endpoint sa README (idinagdag ang MCP HTTP + SSE + A2A) at nadagdagan ang mga halimbawa ng `curl`, kaya
lumampas ito sa threshold.

Ang file ay hindi aktibong dokumentasyon at wala itong anumang executable na nilalaman. Maaari mo itong ligtas na ibalik
mula sa quarantine.

**Ano ang gagawin:**

1. **Itigil ang mga notification** — ibukod ang direktoryo ng pag-install sa iyong antivirus
   (Avast: Settings → Exceptions), sa pamamagitan ng pagdaragdag ng path ng iyong global `node_modules` at/o ng
   data dir ng OmniRoute (`~/.omniroute/`).
2. **Iulat ang maling positibong resulta** — <https://www.avast.com/false-positive-file-form.php>,
   at ilakip ang naka-quarantine na `README.md`. Ito ang pag-aayos na makatutulong sa lahat, dahil
   labis na tumutugon ang heuristic ng vendor sa isang text file.

**Bakit hindi namin ito "inaayos" sa aming panig:** ang lahat ng halimbawa ay `http://localhost`, at
hindi maaaring maging `https` ang localhost nang walang abala mula sa self-signed certificate. Ang pagsira sa mga dokumento upang
makaiwas sa heuristic ng isang vendor ay makasasama sa bawat mambabasa para lamang mapagbigyan ang isang bug sa scanner.

### Fina-flag ng Kaspersky ang Desktop app bilang `PDM:Trojan.Win32.Generic`

**Isa itong maling positibong resulta mula sa isang behavioral heuristic. Walang nahawahan.** Ang
prefix na `PDM:` ng Kaspersky ay nangangahulugang nagmumula ang hatol sa Proactive Defense Module (System Watcher) nito,
na humuhusga sa kung ano ang _ginagawa_ ng installer sa halip na itugma ito sa kilalang malware. Kapag
na-trigger ito, "iniro-roll back" ng Kaspersky ang buong pag-install — binubura ang mga file na naisulat na
nito — kaya nagiging sira o nawawala ang app.

Ang mga file na fina-flag nito ay mga karaniwang bahagi ng mga idineklarang open-source dependency na kasama sa
desktop app, halimbawa:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` at
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ang browser-automation
  library na ginagamit para sa pag-login sa provider sa loob ng app at chat na gumagamit ng browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ang naka-pin na native binding ng `wreq-js` na ginagamit para sa browser-fingerprinted HTTP sa mga provider na
  gumagamit ng web cookie (`<arch>` ay `x64` o `arm64`).

**Bakit ito nati-trigger:** **hindi pa code-signed** ang Windows installer, kaya ang isang unsigned NSIS
installer ay walang anumang reputasyon at tumatakbo ang mga behavioral heuristic sa pinakamataas na antas ng agresyon. Kapag isinama
ang isang naka-bundle na native DLL at daan-daang `.js` file na isinusulat sa ilalim ng
`%LOCALAPPDATA%\Programs\OmniRoute` (kabilang ang mga package directory na may hash suffix mula sa
Next.js standalone build), sapat na iyon upang ma-trigger ang heuristic. Nakaplano ang code signing;
hangga't hindi pa ito naipapatupad, maaari itong maulit sa mga bagong release.

**Ano ang gagawin:**

1. **I-verify muna ang iyong download** (upang matiyak na hindi binago ang file). Ang bawat release ay naglalathala ng
   `latest.yml`, na ang field na `sha512` (base64) ay sumasaklaw sa installer na `OmniRoute.Setup.<version>.exe`.
   Sa PowerShell, mula sa folder na naglalaman ng installer:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Dapat tumugma ang output sa `latest.yml` → `sha512`. Kung hindi ito tumutugma, burahin ang file at
   i-download itong muli mula lamang sa [pahina ng mga release sa GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Ibalik + ibukod** — ibalik mula sa quarantine ang mga item na inalis dahil sa rollback at magdagdag ng exclusion
   para sa `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   pagkatapos ay muling i-install.
3. **Iulat ang maling positibong resulta** — <https://opentip.kaspersky.com/>. Ang mga FP report na isinusumite ng mga user
   ay tunay na nagpapabilis sa pagdaragdag sa allowlist.

## Compatibility sa Node.js

<a name="nodejs-compatibility"></a>

### Nagka-crash ang pahina sa pag-login o ipinapakita ang error na "Module self-registration"

**Sanhi:** Gumagamit ka ng bersyon ng Node.js na wala sa aprubadong minimum na secure runtime ng OmniRoute. Ang pinakakaraniwang sitwasyon ay ang paggamit ng mas lumang patch level ng Node 22 o 24 na mas mababa sa minimum na antas ng seguridad na kinakailangan ng OmniRoute.

**Mga Sintomas:**

- Nagpapakita ang pahina sa pag-login ng blangkong screen o error ng server
- Ipinapakita ng console ang `Error: Module did not self-register` o mga katulad na error sa native binding
- Nagpapakita ang pahina sa pag-login ng **orange na banner ng babala** kasama ang bersyon ng iyong Node kung ang runtime ay wala sa sinusuportahang secure policy

**Solusyon:**

1. Mag-install ng sinusuportahang release ng Node.js LTS (inirerekomenda: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Suriin ang iyong bersyon: dapat ipakita ng `node --version` ang `v24.0.0` o mas bago sa 24.x LTS line
3. Muling i-install ang OmniRoute: `npm install -g omniroute`
4. I-restart: `omniroute`

> **Mga sinusuportahang secure na bersyon:** `>=22.22.2 <23` o `>=24.0.0 <27`. Ganap na sinusuportahan ang Node.js 24.x LTS (Krypton) at Node.js 26.

### npm v11+: Hindi naka-install ang `better-sqlite3` (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Sanhi:** Hinaharangan ng npm v11 (kasama sa Node.js 24+) ang mga install script para sa mga opsiyonal na
dependency bilang default. Dahil nakalista ang `better-sqlite3` sa `optionalDependencies`
at nangangailangan ito ng native compilation (`node-gyp rebuild`), tahimik itong nilalaktawan ng npm.

**Mga Sintomas:**

- Nagka-crash ang server sa pagsisimula at ipinapakita ang `Cannot find module 'better-sqlite3'`
- Ipinapakita ng `ls node_modules/better-sqlite3` ang "No such file or directory"
- Ipinapakita ng `npm ls better-sqlite3` ang `(empty)`

**Solusyon:**

1. Aprubahan ang mga install script at muling mag-install:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. O manu-manong i-install ang prebuilt:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Tiyaking gumagana ito: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Sanhi:** Pagkatapos ng global na `npm install -g omniroute`, maaaring na-compile ang native binary ng `better-sqlite3` sa loob ng package para sa ibang architecture o Node.js ABI kaysa sa lokal na ginagamit. Karaniwan ito sa macOS (kapwa sa Apple Silicon at Intel) kapag hindi tumutugma ang pre-built binary sa iyong environment.

**Mga Sintomas:**

- Agad na nabibigo ang server sa pagsisimula dahil sa isang `dlopen` error
- Naglalaman ang error ng `slice is not valid mach-o file`
- Buong halimbawa:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Solusyon — muling i-build para sa iyong lokal na environment (hindi kailangang mag-downgrade ng Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Tandaan:** Muli nitong kino-compile ang native binding ayon sa iyong lokal na bersyon ng Node.js at CPU architecture, na lumulutas sa hindi pagtutugma ng binary. Ang opisyal na sinusuportahang runtime range ay **`>=22.22.2 <23` o `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` sa `src/shared/utils/nodeRuntimeSupport.ts`, na nakaayon sa `engines` field ng `package.json`). Ganap na sinusuportahan ang Node.js 24.x LTS (Krypton) at Node.js 26 gamit ang `better-sqlite3` v12.x.

## Mga Isyu sa Proxy

<a name="proxy-issues"></a>

### Ipinapakita ng pag-validate ng provider ang "fetch failed"

**Sanhi:** Dati, nilalampasan ng endpoint para sa pag-validate ng API key (`POST /api/providers/validate`) ang configuration ng proxy, kaya nagkakaroon ng mga pagkabigo sa mga environment na nangangailangan ng pagruruta sa proxy.

**Pag-aayos (v3.5.5+):** Naayos na ito. Dumadaan na ang pag-validate ng provider sa `runWithProxyContext`, na awtomatikong sumusunod sa mga setting ng proxy sa antas ng provider at sa mga global na setting ng proxy.

### Nabibigo ang pagsusuri sa kalagayan ng token at lumalabas ang "fetch failed"

**Sanhi:** Hindi tinutukoy ng pag-refresh ng OAuth token sa background ang configuration ng proxy para sa bawat koneksyon.

**Pag-aayos (v3.5.5+):** Tinutukoy na ngayon ng scheduler ng pagsusuri sa kalagayan ng token ang config ng proxy para sa bawat koneksyon bago subukang mag-refresh. Mag-update sa v3.5.5+.

### Ibinabalik ng SOCKS5 proxy ang "invalid onRequestStart method"

**Sanhi:** Sa Node.js 22, hindi tugma ang undici@8 dispatcher sa built-in na implementasyon ng `fetch()` ng Node.

**Pag-aayos (v3.5.5+):** Ginagamit na ngayon ng OmniRoute ang sariling `fetch()` function ng undici kapag may aktibong proxy dispatcher, upang matiyak ang pare-parehong paggana. Mag-update sa v3.5.5+.

### MITM proxy sa WSL: hindi nahaharang ang mga desktop app sa Windows host

**Sanhi:** Nai-install ang MITM proxy at ang CA certificate nito sa environment kung saan tumatakbo ang OmniRoute. Sa WSL, ang environment na iyon ay ang Linux guest, samantalang tumatakbo sa Windows host ang mga AI desktop app (Kiro, Trae, Copilot, Zed, …). Hindi pinagkakatiwalaan ng mga host app ang certificate store ng guest at hindi dumadaan sa system proxy ng guest, kaya hindi gumagana roon ang desktop interception.

**Rekomendasyon:** Patakbuhin ang OmniRoute nang native sa parehong OS kung saan tumatakbo ang mga desktop app na gusto mong harangin (Windows para sa mga Windows app; gayundin para sa macOS/Linux). Kung pananatilihin ang OmniRoute sa loob ng WSL habang tina-target ang mga host app, kailangan mong manu-manong pagkatiwalaan ang nabuong CA certificate sa Windows host at ituro ang mga setting ng network/proxy ng bawat host app sa WSL proxy endpoint — isa itong hindi suportado at madaling masirang setup.

## Mga Isyu sa Docker

### Docker IPv6 / Pag-reset ng Koneksyon

<a name="docker-ipv6"></a>

**Mga Sintomas:** Nagbabalik ang `curl http://localhost:20128/v1/models` ng `curl: (56) Recv failure: Connection reset by peer`. Gumagana ang dashboard at mga endpoint na hindi nangangailangan ng authentication, ngunit pumapalya ang mga authenticated endpoint — mukhang problema ito sa authentication ngunit hindi pala.

**Sanhi:** Nagpa-publish ang `docker run -p 20128:20128` sa parehong `0.0.0.0` (IPv4) at `::` (IPv6), ngunit sa IPv4 lang nakikinig ang process sa loob ng container. Sa mga host kung saan unang nagre-resolve ang `localhost` sa `::1`, napupunta ang koneksyon sa naka-publish na IPv6 port na walang listener sa likod nito → nare-reset ang koneksyon.

**Ayos:**

1. **Mabilisang diagnostic:** Patakbuhin ang `curl -4 http://localhost:20128/v1/models`. Kung gumagana ito gamit ang `-4` ngunit pumapalya nang wala nito, mayroon kang IPv6 bind mismatch.
2. **Permanenteng ayos:** Tahasang mag-bind sa IPv4 sa pamamagitan ng paggamit ng `-p 127.0.0.1:20128:20128` sa iyong `docker run` command:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Pinipilit nito ang IPv4 bind at iniiwasan ding ilantad ang proxy sa lahat ng host interface.

- Pangunahing state: `${DATA_DIR}/storage.sqlite` (mga provider, combo, alias, key, setting)

- **Nagbabalik ang SDK ng raw string sa halip na object** — Nalutas sa v1.x; inaalis ng response sanitizer ang mga hindi karaniwang field (`x_groq`, `usage_breakdown`, atbp.) na nagdudulot ng mga pagkabigo sa Pydantic validation ng OpenAI SDK. Kung nakikita mo pa rin ito sa v3.x+, mangyaring maghain ng issue.
- **Tinatanggihan ng GLM/ERNIE ang role na `system`** — Nalutas sa v1.x; awtomatikong pinagsasama ng role normalizer ang mga system message sa mga user message para sa mga hindi compatible na modelo. Kung nakikita mo pa rin ito sa v3.x+, mangyaring maghain ng issue.
- **Hindi nakikilala ang role na `developer`** — Nalutas sa v1.x; awtomatikong kino-convert sa `system` para sa mga provider na hindi OpenAI. Kung nakikita mo pa rin ito sa v3.x+, mangyaring maghain ng issue.
- **Hindi gumagana ang `json_schema` sa Gemini** — Nalutas sa v1.x; kino-convert na ngayon ang `response_format` sa `responseMimeType` + `responseSchema` ng Gemini. Kung nakikita mo pa rin ito sa v3.x+, mangyaring maghain ng issue.

## Mga Setting ng Resilience

### Hindi nati-trigger ang awtomatikong rate-limit

- Nalalapat lamang ang awtomatikong rate-limit sa mga provider ng API key (hindi sa OAuth/subscription)
- Tiyaking naka-enable ang awtomatikong rate-limit sa **Settings → Resilience → Provider Profiles**
- Tingnan kung nagbabalik ang provider ng mga status code na `429` o mga header na `Retry-After`

### Pag-tune ng exponential backoff

Sinusuportahan ng mga profile ng provider ang mga setting na ito:

- **Base delay** — Paunang tagal ng paghihintay pagkatapos ng unang kabiguan (default: 1s)
- **Max delay** — Maximum na limitasyon ng tagal ng paghihintay (default: 30s)
- **Multiplier** — Gaano kalaki ang itataas sa delay sa bawat sunod-sunod na kabiguan (default: 2x)

### Pag-iwas sa thundering herd

Kapag maraming magkakasabay na request ang tumama sa isang provider na may rate-limit, gumagamit ang OmniRoute ng mutex + awtomatikong rate-limiting upang isa-isahin ang mga request at maiwasan ang magkakasunod na kabiguan. Awtomatiko ito para sa mga provider ng API key.

### Nabibigo ang mga chat request na may 503 / chat_admission_busy

**Mga Sintomas:**

- Nagbabalik ang endpoint ng chat completions ng retryable na tugong `503` na may error code na
  `chat_admission_busy`.
- Kasama sa tugon ang `Retry-After`. Mula noong #12135, hinango ang value mula sa naobserbahang
  occupancy — alinman ang mas malaki sa window na `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` na nahintay na ng request
  at sa tagal na hawak ang mga kasalukuyang heavyweight lease — ni-round up sa buong
  segundo at nilimitahan sa 60. Sa isang idle na gate, pinapanatili nito ang mga dating minimum: 2 segundo sa
  byte-based na path, 1 segundo sa structure-based na path (na may kasama ring
  `reason: "structure_limit"`).
- Maaari itong mangyari habang may isa pang heavyweight chat o matagal tumakbong streaming response na
  isinasagawa pa rin.

Ang byte-based na response body ay:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Gumagamit ang structure-based na tugon ng parehong type at code, na may mensaheng
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
at `reason: "structure_limit"`.
Sa mga default na threshold, itinuturing na structurally heavy ang isang request kapag mayroon itong hindi bababa sa `200` mensahe,
hindi bababa sa `64` tool, o hindi bababa sa tinatayang `32,000` token, o kapag naubos ng bounded structure estimation
ang mga limitasyon nitong `10,000` binisitang node o depth na `12`.

**Sanhi:** Sinadyang load shedding ito sa loob ng OmniRoute, hindi isang kabiguan ng upstream provider.
Gumagamit ang bawat process ng process-local guard upang magreserba ng limitadong heavyweight capacity bago panatilihin
at i-parse ang isang malaking request body. Nananatiling hawak ang isang heavyweight lease sa buong tagal ng isang SSE
response.

**#503-fanout:** bago ang pag-aayos na ito, nililimitahan ng guard ang concurrency sa isang nakapirming BILANG ng request
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, default na `1`) anuman ang memory ng host, kaya ang fan-out ng coding-agent
(maraming subagent/CLI, mga body na karaniwang > 256 KB) ay bumabagsak sa epektibong
concurrency na ~1 at nagbabalik ng 503 sa ganap na normal na load. Awtomatiko na ngayong nagtu-tune ang guard: kinokontrol ito
ng awtomatikong hinangong ingest BYTE budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) na ibinabatay sa
aktuwal na memory ceiling ng process, at kumokonsulta rin ito sa isang live na signal ng resource pressure — kaya
naglo-load shed lamang ito kapag talagang nakararanas ng memory pressure ang host, hindi dahil lamang sa higit sa isang
heavy request ang dumating nang sabay-sabay. Sinusunod pa rin ang lumang count cap (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`),
ngunit kung tahasan mo lamang itong ise-set.

Kapag abala ang capacity, naghihintay muna ang isang heavyweight request nang hanggang
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (default na `2000`, idi-disable ng `0` ang paghihintay) para may mabakanteng slot
bago ibalik ang retryable na `503`. Umiiral ang limitadong paghihintay upang ang mga agent-style client
(OpenCode, Claude Code, Cursor) na sabay-sabay na nagfa-fan out ng mga heavy sub-request ay isa-isahin ang burst
sa halip na ubusin ang kanilang buong retry budget sa mga agarang pagtanggi at huminto sa gitna ng gawain.
Makikita sa `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ang kasalukuyang occupancy ng heavyweight lease, ang nalutas na byte budget, at ang
antas ng live pressure — suriin ang mga ito bago baguhin ang anumang env var.
Hindi ito kinokontrol ng Settings → Resilience → Request Queue → Concurrent Requests; pinamamahalaan ng setting na iyon
ang isang hiwalay na mekanismo ng request queue ng provider.

**Pag-aayos:**

1. Subukan munang muli. Dapat sundin ng mga client ang `Retry-After` at gumamit ng backoff sa halip na agad
   ulitin ang request.
2. Suriin ang `/api/monitoring/health` → `chatAdmission` bago mag-tune ng anuman. Ang `countCapEnabled:
false` at isang sapat na malaking `maxInflightBytes` ay nangangahulugang maayos nang gumagana ang awtomatikong hinangong budget;
   ang `pressureSeverity` na `high`/`critical` ay nangangahulugang talagang kapos sa memory ang host —
   hindi ito maaayos ng isang admission env var; nangangailangan ito ng mas maraming RAM o mas maliit na workload.
3. Tanging kung ipinapakita ng `/api/monitoring/health` na talagang napakaliit ng awtomatikong hinangong budget para sa
   iyong host (bihira — awtomatiko na itong nag-i-scale mula container hanggang bare-metal), direktang i-override ito gamit ang
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` sa halip na bumalik sa legacy na request-count cap.

Tingnan ang [sanggunian ng environment variable](../reference/ENVIRONMENT.md#4-security--authentication)
para sa awtoritatibong mga setting ng admission.

## Opsyonal na taxonomy ng kabiguan ng RAG / LLM (16 na problema)

Inilalagay ng ilang user ng OmniRoute ang gateway sa harap ng mga RAG o agent stack. Sa mga setup na iyon, karaniwang makakita ng kakaibang pattern: mukhang maayos ang OmniRoute (gumagana ang mga provider, maayos ang mga routing profile, walang mga alerto sa rate limit) ngunit mali pa rin ang panghuling sagot.

Sa aktuwal na paggamit, ang mga insidenteng ito ay karaniwang nagmumula sa downstream na RAG pipeline, hindi sa mismong gateway.

Kung gusto ninyo ng magkakatulad na bokabularyo upang ilarawan ang mga kabiguang iyon, maaari ninyong gamitin ang WFGY ProblemMap, isang external na text resource na may lisensyang MIT na tumutukoy sa labing-anim na paulit-ulit na pattern ng kabiguan ng RAG / LLM. Sa pangkalahatan, saklaw nito ang:

- paglihis ng retrieval at mga sirang hangganan ng context
- mga walang laman o lipas na index at vector store
- hindi pagtutugma ng embedding at semantics
- mga isyu sa pagbuo ng prompt at context window
- pagbagsak ng lohika at mga sagot na labis ang kumpiyansa
- mga kabiguan sa mahabang chain at koordinasyon ng agent
- memorya ng maraming agent at paglihis ng tungkulin
- mga problema sa pagkakasunod-sunod ng deployment at bootstrap

Simple lang ang ideya:

1. Kapag nag-iimbestiga kayo ng maling tugon, itala ang:
   - gawain at request ng user
   - kumbinasyon ng route o provider sa OmniRoute
   - anumang RAG context na ginamit sa downstream (mga na-retrieve na dokumento, tool call, atbp.)
2. Itugma ang insidente sa isa o dalawang numero ng WFGY ProblemMap (`No.1` … `No.16`).
3. I-store ang numero sa sarili ninyong dashboard, runbook, o incident tracker sa tabi ng mga log ng OmniRoute.
4. Gamitin ang kaukulang page ng WFGY upang magpasya kung kailangan ninyong baguhin ang inyong RAG stack, retriever, o routing strategy.

Narito ang buong teksto at mga konkretong recipe (lisensyang MIT, teksto lamang):

[README ng WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Maaari ninyong balewalain ang seksyong ito kung hindi kayo nagpapatakbo ng mga RAG o agent pipeline sa likod ng OmniRoute.

## Mga Kilalang Isyu sa v3.8.0

Mga isyung partikular sa release na v3.8.0 at ang mga kasalukuyang workaround para sa mga ito. Kung may fix na maisama sa susunod na patch, ia-update o aalisin ang entry.

### Mga kabiguan sa auth ng Devin CLI

**Mga sintomas:**

- "Hindi nahanap ang Devin CLI" o "nabigo ang auth" kapag ginagamit ang mga tool na suportado ng Devin
- Ipinapakita ng runtime check ng CLI ang `installed=false`

**Mga sanhi:**

- Nakatalaga ang `CLI_DEVIN_BIN` sa path na hindi umiiral
- Hindi naka-install ang Devin CLI sa host

**Solusyon:**

1. I-install ang Devin CLI para sa inyong platform
2. Itakda ang `CLI_DEVIN_BIN=/usr/local/bin/devin` (o ang aktuwal na path) sa `.env`
3. I-restart ang OmniRoute at muling subukan mula sa **Dashboard → Mga CLI Tool**

### Hindi umaalis sa cooldown ang model (manu-manong pag-reset)

**Mga sintomas:**

- Nananatiling nakalista sa cooldown ang isang model kahit lumipas na ang oras ng expiration
- Nilalampasan pa rin ng mga request ang model sa combo routing kahit nasa nakaraan na ang timestamp

**Manu-manong pag-reset:**

- **Dashboard:** **Mga Setting → Mga Cooldown ng Model** → i-click ang **Muling i-enable** sa apektadong card
- **API:** `DELETE /api/resilience/model-cooldowns` na may mga management auth header

### Nabibigo nang may 403 ang koneksyon sa Command Code provider

**Mga sintomas:**

- 403 kapag sinusubukan ang koneksyon sa Command Code provider
- Ipinapakita ng provider card ang "hindi awtorisado" pagkatapos itong bagong idagdag

**Sanhi:** Hindi nakumpleto ang OAuth flow (hindi natanggap ang callback o hindi na-persist ang token).

**Solusyon:**

- Patakbuhin ang `omniroute providers` mula sa CLI upang muling simulan ang OAuth flow, o
- Muling patakbuhin ang OAuth mula sa **Dashboard → Mga Provider → Command Code → Muling kumonekta**

### Nagbabalik ang ModelScope ng agresibong mga 429 cooldown

**Mga sintomas:**

- Napakaikli o agarang mga cooldown sa ModelScope pagkatapos ng maliit na bugso ng mga request
- Nilalampasan ng combo routing ang ModelScope nang mas maaga kaysa sa inaasahan

**Sanhi:** Naglalabas ang ModelScope ng mga provider-specific na `Retry-After` header. May kasamang nakalaang pagproseso ang v3.8.0 para sa mga header na iyon, kaya mali ang pagbasa sa mga ito ng mas lumang mga bersyon bilang mga generic na pahiwatig ng rate limit.

**Solusyon:**

- Tiyaking gumagamit kayo ng v3.8.0 o mas bago
- Tiyaking naka-enable ang toggle na `useUpstream429BreakerHints` sa ilalim ng **Mga Setting → Resilience**

### Nawawala ang OMNIROUTE_WS_BRIDGE_SECRET sa production

**Mga sintomas:**

- 401 sa bawat request sa Codex/Responses WebSocket bridge kapag tumatakbo sa isang remote na production host
- Agad na nagsasara ang WebSocket bridge handshake pagkatapos kumonekta

**Sanhi:** Nawawala ang env var na `OMNIROUTE_WS_BRIDGE_SECRET` sa production environment.

**Solusyon:**

1. Bumuo ng random na secret: `openssl rand -hex 32`
2. Itakda ang `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` sa env ng production server (at sa anumang client na nakikipag-ugnayan sa bridge)
3. I-restart ang OmniRoute

### Responses API: ibinaba ang background mode sa synchronous

**Mga sintomas:**

- Na-log na babala: `background mode degraded to synchronous`
- Ang request na `background: true` ay nagbabalik ng normal na synchronous response sa halip na background job handle

**Sanhi:** Sadyang ibinababa ng v3.8.0 ang `background: true` sa Responses API tungo sa synchronous execution habang naglalabas ng babala. Ang ganap na async background execution ay ihahatid pa sa hinaharap.

**Solusyon:**

- I-adjust ang client upang tumawag nang walang `background`, o
- Maghintay ng susunod na release na may ganap na async background mode (subaybayan ang changelog)

## Mabagal na Pagsisimula / Timeout sa Kahandaan

Kung ipinapakita ng CLI ang `⚠ Server did not respond within 60s` ngunit gumagana
naman talaga ang server, masyadong maikli para sa iyong environment ang nakalaang oras ng readiness probe.

Karaniwan itong nangyayari sa Windows (antivirus, mga filesystem watcher) o sa mga container
na may mabibigat na workload sa pagsisimula.

**Solusyon — dagdagan ang nakalaang oras:**

```bash
# Sa pamamagitan ng env var (mananatili sa bawat pagsisimula):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minuto
omniroute serve

# Sa pamamagitan ng CLI flag (isang beses lang):
omniroute serve --ready-timeout 180000
```

Ang default ay 60 000 ms (60 s). Para sa impormasyon lamang ang babala; patuloy na
nagsisimula ang server sa background at maa-access ito kapag nakumpleto na ang pag-boot.

Tingnan ang [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) para sa kumpletong
mga detalye tungkol sa `OMNIROUTE_READY_TIMEOUT_MS`.
