Kumpletong gabay sa paggamit ng Codex CLI na nakaturo sa OmniRoute bilang backend na compatible sa OpenAI.

---

> **TOML lamang ang epektibong format.** Eksklusibong binabasa ng modernong Codex ang `~/.codex/config.toml`
> (na-verify gamit ang codex-cli 0.147.0: isinasaad ng `codex --help` na ang
> mga override ng `-c/--config` ay "loaded from `~/.codex/config.toml`"). Ang lumang
> `~/.codex/config.yaml` ay para sa legacy npm CLI at tahimik na binabalewala.
> Nagsusulat ang dashboard generator (`/api/cli-tools/apply`, tool na `codex`) ng TOML gamit ang
> konserbatibong pag-merge — pinapanatili ang mga kasalukuyang key at iba pang provider block, nananatili
> ang API key sa `OMNIROUTE_API_KEY` (hindi kailanman sa file), at iniuulat bilang migration note
> ang natitirang legacy na `config.yaml` nang hindi ito binabago.

## Handa nang i-paste na config.toml

Palitan ang `<YOUR_HOST>` at `<YOUR_KEY>` ng iyong mga value:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # limitasyon sa pag-store ng history sa bawat tool call

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc o ~/.zshrc — aktuwal na key value, hindi kailanman sa config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex na kasama sa ChatGPT app

Kung na-install mo ang Codex sa pamamagitan ng ChatGPT desktop app, maaaring
nasa loob lamang ng app bundle ang `codex` binary at wala pa sa `PATH` ng iyong shell. Idagdag ang
resources directory sa startup file ng iyong shell:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Magbukas ng bagong shell, pagkatapos ay i-verify:

```bash
command -v codex
codex --version
```

### Lokal na OmniRoute na walang authentication: sapat na ang placeholder key

Bine-validate ng Codex na umiiral ang environment variable na tinukoy ng `env_key`
**bago** lumabas sa CLI ang unang request. Kung hindi nangangailangan ng auth ang iyong **lokal** na
OmniRoute instance, gagana ang anumang placeholder na hindi walang laman:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Sa halip, gumamit ng tunay na key kapag protektado o remote ang iyong OmniRoute server.

> **Mga karaniwang opsyon sa host**
>
> | Access           | URL                           |
> | ---------------- | ----------------------------- |
> | Lokal na network | `http://192.168.0.1:20128/v1` |
> | Tailscale        | `http://100.x.x.x:20128/v1`   |
> | Loopback         | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — bakit gumagana ito sa lahat ng modelo

Itinigil ng Codex CLI ang suporta sa `wire_api = "chat"` (Chat Completions) noong Pebrero 2026 at **nangangailangan** na ngayon ng `wire_api = "responses"` (OpenAI Responses API). Ang pagtatakda ng `wire_api = "chat"` ay nagdudulot ng agarang pag-crash sa startup mula noong v0.138.

Maraming provider, kabilang ang GLM at Kimi, ang nag-aalok pa rin ng Chat Completions endpoint lamang. Nag-aalok na ngayon ang DeepSeek V4 ng native Responses API pati na rin ng Anthropic-compatible na endpoint; ginagamit ng OmniRoute ang Responses bilang default at hinahayaan ang bawat DeepSeek connection na pumili ng Anthropic compatibility.

**Malinaw na nilulutas ito ng OmniRoute:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → Pinipili ng OmniRoute ang native protocol ng provider at nagsasalin kapag kinakailangan
    → POST /responses (DeepSeek V4) o /chat/completions (Mistral / GLM / Kimi / iba pa)
```

Hindi mo kailangan ng hiwalay na translation proxy kapag gumagamit ng OmniRoute. **Gumagamit ang lahat ng modelo ng `wire_api = "responses"`** — ang OmniRoute na ang bahala sa iba pa.

> **`wire_api` ang default** — naka-default ang field sa `"responses"` at maaari itong ganap na alisin sa `config.toml`. Itakda lamang ito nang tahasan kung idinodokumento mo ang layunin.

## Context window at compaction

### Mga field ng configuration ng token

| Field                            | Paglalarawan                                                                                                                                                                                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Kabuuang badyet ng token para sa aktibong model. Itakda sa limitasyong inanunsyo para sa model.                                                                                                                                        |
| `model_auto_compact_token_limit` | Threshold na nagti-trigger ng awtomatikong pag-compact ng history. **Maximum: 90% ng `model_context_window`** — tahimik na binabalewala ang mga value na lampas sa 90%.                                                                |
| `tool_output_token_limit`        | Limitasyon sa mga token na iniimbak sa history para sa bawat output ng tool call. Pinipigilan nitong punuin ng isang malaking tugon ng tool ang window. **Hindi ito ang maximum na output** — limitasyon ito sa pag-iimbak sa history. |
| `compact_prompt`                 | Inline na override para sa system prompt na ginagamit habang nagko-compact (v0.138+).                                                                                                                                                  |

> **Tandaan tungkol sa `model_max_output_tokens`**: Ang field na ito ay **hindi bahagi ng config schema ng Codex CLI** (wala ito sa Codex Rust codebase). Tahimik itong binabalewala kung itatakda. Huwag umasa rito — gamitin ang `tool_output_token_limit` upang kontrolin kung gaano karaming output ng tool ang iniimbak sa history.

## Lalim ng Pangangatwiran

Kinokontrol nito kung gaano karaming "pag-iisip" ang ginagawa ng modelo bago tumugon.

| Value    | Gamitin para sa                                          |
| -------- | -------------------------------------------------------- |
| `none`   | Walang pangangatwiran — direktang tugon                  |
| `low`    | Mga simpleng gawain (pagpapalit ng pangalan, format)     |
| `medium` | **Default ng server** kapag hindi tinukoy                |
| `high`   | Mga katamtamang gawain (refactoring, pag-debug)          |
| `xhigh`  | Arkitektura, malalim na pagsusuri, komplikadong problema |

```bash
# Pag-override sa bawat invocation
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Magtakda rin ng **buod** ng pangangatwiran upang ma-render ng Desktop ang teksto ng pag-iisip (hindi lamang ang mga naka-encrypt na blob):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # o ultra kapag sinusuportahan
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Badyet sa Pag-iisip ng OmniRoute (setting ng server)

Sa host ng OmniRoute, ang **Settings → AI → Thinking Budget** ay dapat na **`passthrough`** upang makarating sa upstream ang effort/summary ng Codex. Tinatanggal ng mode na **`auto`** ang lahat ng field na `reasoning` / `reasoning_effort` ng client at gagawing walang laman ang mga panel ng pag-iisip kahit tama ang pagkaka-configure sa Codex.

Kumpletong gabay: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Magkahiwalay ang compression at prompt cache at patuloy na gumagana sa ilalim ng `passthrough`.

## Mga profile — mga pinangalanang configuration para sa bawat modelo/workflow

Nagbibigay-daan ang mga profile na magpalit ka ng modelo + context window gamit ang iisang flag. Ang bawat profile ay isang flat na
`~/.codex/<name>.config.toml` na ipinapatong sa base na `config.toml`.

> **Panuntunan sa pagpapangalan (Codex CLI v0.137+):** dapat ay `~/.codex/<name>.config.toml` ang file — **walang prefix na `profile-`**.
> Nire-resolve ng CLI ang `-p kimi-k27` → `~/.codex/kimi-k27.config.toml`. Kung hindi makita ang file, tahimik na ilalapat ang default.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # mabilis, mura
```

### Mga profile ng effort (parehong modelo, magkakaibang effort)

```bash
codex -p low      # cx/gpt-5.5, effort=low
codex -p medium   # cx/gpt-5.5, effort=medium
codex -p high     # cx/gpt-5.5, effort=high
codex -p xhigh    # cx/gpt-5.5, effort=xhigh (default)
codex -p chat     # cx/gpt-5.5, walang nakatakdang effort (default ng server)
```

## Awtomatikong pagbuo ng mga profile gamit ang `omniroute setup-codex`

Kung pinapatakbo mo ang OmniRoute sa isang VPS, maaari kang awtomatikong bumuo ng mga profile file mula sa live na katalogo ng modelo:

```bash
# Mula sa isang VPS (ginagamit ang lokal na OmniRoute sa port 20128)
omniroute setup-codex

# Mula sa anumang machine — ituro sa iyong VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# I-preview nang hindi nagsusulat ng mga file
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Bumuo lamang ng mga GLM at Kimi profile
omniroute setup-codex --only glm,kimi

# Isulat sa isang custom na directory
omniroute setup-codex --codex-home /path/to/.codex
```

Kinukuha ng command ang `/v1/models`, gumagamit ng mga naka-tune na profile para sa mga kilalang modelo, bumabalik sa metadata ng katalogo para sa iba pang compatible na text model, at nagsusulat ng `~/.codex/<name>.config.toml` para sa bawat isa. Idempotent — ligtas itong patakbuhin muli.

Maaari ring **awtomatikong i-sync** ng OmniRoute ang parehong mga profile file na ito pagkatapos matagumpay na makatuklas/mag-import ng mga provider model na nagpapabago sa live na katalogo. Ito ay **kailangang tahasang i-enable at naka-off bilang default**: i-toggle ito mula sa **CLI Code dashboard** ("CLI profile auto-sync" → Codex), o itakda ang `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (iginagalang din nito ang `CLI_ALLOW_CONFIG_WRITES`, na naka-on bilang default). Kapag naka-enable, hiwalay na `~/.codex/*.config.toml` profile file lamang ang isinusulat nito; hindi nito kailanman binabago ang aktibo/default na `~/.codex/config.toml`, mga setting ng Codex-lb, auth, o pagpili ng provider.

## Paglulunsad ng Codex gamit ang `omniroute launch-codex`

Sinusuri muna ang kalagayan ng iyong OmniRoute instance bago ilunsad ang Codex:

```bash
# Ilunsad gamit ang lokal na OmniRoute (default na port 20128)
omniroute launch-codex

# Ilunsad gamit ang isang partikular na profile
omniroute launch-codex --profile kimi-k27

# Ilunsad gamit ang isang remote na VPS
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# Magpasa ng mga karagdagang argument sa codex
omniroute launch-codex --profile glm52 -- --yolo "ayusin ang bug na ito"
```

Target din ang Codex ng dalawang generic na manifest-driven na entry point
(`bin/cli/cli-manifest.mjs`):

```bash
# Interactive na tagapili ng modelo → nagsusulat ng ~/.codex/<name>.config.toml (TOML, env_key)
omniroute configure codex

# Ilunsad ang codex na may omniroute provider na ini-inject sa pamamagitan ng mga -c flag (walang isinusulat na config)
omniroute run codex
```

## Mga gawaing matagal tumakbo

May dalawang default ng OmniRoute na maaaring palihim na makasira sa mga session ng Codex CLI na tumatagal nang ilang oras. Wala sa mga ito ang setting ng Codex CLI — parehong nasa panig ng OmniRoute. Madalas na nararanasan ng mga user na naglilipat ng config mula sa mga upstream proxy na nagpi-pin ng mga account at nagdi-disable ng mga idle cutoff ang parehong problema at naghihinuha silang “hindi kayang panatilihin ng OmniRoute ang isang mahabang session.”

| Sintomas                                                                                                      | Malamang na sanhi                                                                    | Kontrol                  |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------ |
| Patuloy na nagpapalit ng account ang session / nawawala ang continuity ng prompt cache sa pagitan ng mga turn | Ang session affinity TTL ay `0` (naka-disable)                                       | `sessionAffinityTtlMs`   |
| Napuputol ang koneksyon habang nangangatuwiran nang walang prompt na nakikita ng client                       | Na-trigger ang stream idle watchdog matapos ang 10 minuto nang walang upstream chunk | `STREAM_IDLE_TIMEOUT_MS` |

Mga kaugnay na talakayan: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (pagkaputol ng mahabang gawain), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (kung bakit naka-off bilang default ang affinity). Pagsubaybay: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Session affinity — i-pin ang isang pag-uusap sa isang account

**Default:** `sessionAffinityTtlMs = 0` (naka-disable).

**Kung saan ito ise-set**

- Dashboard → **Settings → Routing** → **Session affinity** → **Affinity TTL (seconds)** (`ComboDefaultsTab`)
- O i-PATCH ang mga setting gamit ang `sessionAffinityTtlMs` sa **milliseconds** (saklaw ng Zod na `0`–`86_400_000`, ibig sabihin, hanggang 24 na oras)

> Pinalitan ang pangalan sa #7274 mula sa Codex-only na `codexSessionAffinityTtlMs`. Tinatanggap pa rin ang legacy key bilang read-only na alias; dapat gamitin ng mga bagong config ang `sessionAffinityTtlMs`. Nalalapat na ngayon ang affinity sa **anumang** provider kapag higit sa `0` ang TTL, hindi lamang sa Codex — tingnan ang [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Session affinity.

**Ano ang nasisira kapag nananatili itong 0**

Ang bawat turn ng isang multi-turn na pag-uusap sa Codex ay hiwalay na niru-route ng aktibong combo strategy at maaaring mapunta sa **ibang account sa bawat turn**. Sinisira nito ang continuity ng upstream session / prompt cache. Kinokonsulta lamang ng OmniRoute ang mga header ng Codex session (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) at mga body field gaya ng `prompt_cache_key` / `session_id` kapag higit sa `0` ang TTL (`extractSessionAffinityKey` sa `src/sse/services/auth.ts`).

**Inirerekomenda para sa iisang gawaing tatagal nang ilang oras**

Itakda ang TTL nang **mas mataas sa inaasahang wall-clock na tagal ng gawain** (ang maximum sa UI ay **86400 segundo** = 24 na oras):

| Inaasahang tagal ng gawain | Affinity TTL (UI, segundo) | `sessionAffinityTtlMs` |
| -------------------------- | -------------------------- | ---------------------- |
| Ilang oras                 | `14400` (4h)               | `14400000`             |
| Magdamag / ~12h            | `43200` (12h)              | `43200000`             |
| Buong araw                 | `86400` (24h, maximum)     | `86400000`             |

Sinadya ang pag-opt in: mas pinapaboran ng pag-disable sa affinity ang load-balancing sa maraming account; mas pinapaboran naman ng pag-enable dito ang continuity para sa isang mahabang agent session. **Hindi** binabago ng gabay na ito ang default — kailangang mag-opt in ang mga operator na nagpapatakbo ng mahahabang gawain sa Codex.

### 2. Stream idle timeout — huwag patayin ang mga tahimik na reasoning turn

**Default:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minuto). Nagmamana ito mula sa `REQUEST_TIMEOUT_MS` kapag hindi naka-set; ang shared baseline ay 600000 din. Tingnan ang [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Mga timeout.

**Ano ang nasisira sa default**

Ang isang Codex reasoning / tool turn na nananatiling tahimik nang mahigit 10 minuto na **walang totoong upstream chunk** ay sapilitang isinasara ng SSE idle watchdog (`open-sse/utils/stream.ts`). Kadalasang nakikita ng client ang biglaang pagkaputol lamang ng koneksyon — tugma sa “awtomatikong huminto nang walang anumang abiso.”

Mahalagang detalye: **hindi nire-reset** ng synthetic SSE heartbeat ng OmniRoute ang idle clock. Isang totoong upstream body chunk lamang ang nag-a-update sa `lastChunkTime`. Ang isang tahimik na model na patuloy pang “nag-iisip” ay mukhang katulad na katulad ng isang natigil na upstream mula sa pananaw ng watchdog.

Kaugnay na Undici body inactivity: `FETCH_BODY_TIMEOUT_MS` (nagde-default din sa parehong 10-minutong baseline; dini-disable ito ng `0`). Para sa streaming, sinasaklaw lamang ng `FETCH_TIMEOUT_MS` ang pag-set up ng koneksyon / mga unang header — kapag aktibo na ang stream, ang mga pagkaantala ay pinamamahalaan ng `STREAM_IDLE_TIMEOUT_MS` at `FETCH_BODY_TIMEOUT_MS`.

**Inirerekomenda para sa isang multi-hour na iisang task**

Sa process environment ng OmniRoute (`.env` / compose / systemd):

```bash
# I-disable ang stream idle + body inactivity cutoff para sa mahahabang reasoning turn
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

O itaas ang mga ito nang lampas sa pinakamahabang tahimik na pagitan na inaasahan mo (ang mga value ay nasa millisecond):

```bash
# Halimbawa: magbigay-daan sa hanggang 2 oras na katahimikan sa pagitan ng mga upstream chunk
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

I-restart ang OmniRoute pagkatapos baguhin ang mga env var na ito.

### Kongkretong hakbang — multi-hour na Codex task

1. **I-pin ang account:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12h) o `86400` (24h max).
2. **Itaas / i-disable ang mga idle cutoff** sa environment ng OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Panatilihin ang karaniwang Codex `config.toml` (`wire_api = "responses"`, tamang `base_url`, `OMNIROUTE_API_KEY`) — walang mga Codex-side affinity/idle knob para sa dalawang gawi na ito.
4. I-restart ang OmniRoute, pagkatapos ay simulan ang mahabang Codex task.

### Desisyon sa mga default (#7287)

| Knob                     | Default na ilalabas | Babaguhin ba sa gabay na ito?                                                                                                            |
| ------------------------ | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (naka-off)      | **Hindi** — nananatiling opt-in (load-balancing vs continuity; tingnan ang Discussion #5718)                                             |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min)   | **Hindi** — nananatiling 10 minuto para sa pangkalahatang traffic; itinataas o dini-disable ito ng mga operator ng mahahabang Codex task |

Ang pagbago sa alinman sa mga default nang global ay magbabago sa gawi para sa bawat client ng isang instance, hindi lamang sa Codex. Idokumento ang mga knob; panatilihin ang mga default hanggang may tahasang desisyon ang operator na nagsasaad ng iba.

### Pag-diagnose sa mga idle cut

Kapag nag-trigger ang idle watchdog, nagla-log ang OmniRoute ng isang linyang ganito ang anyo:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Gamitin ang grep para sa `Idle timeout: no data from` (o sa code na `stream_idle_timeout` / pangalan ng error na `StreamIdleTimeoutError`). Ang provider segment ay anumang ginamit ng OmniRoute para sa request na iyon (`codex`, ibang provider id, o `provider` kung hindi alam) — hindi ito palaging literal na string na `codex`.

## Pag-troubleshoot

**`Error: wire_api = "chat" is no longer supported`**
Alisin ang `wire_api = "chat"` sa iyong config. Itakda ang `wire_api = "responses"` o alisin ang field (ang default ay `"responses"` mula noong v0.138).

**`Error: model not found`**
Tiyaking umiiral ang model sa OmniRoute gamit ang tamang prefix. Gamitin ang `omniroute models list` o buksan ang `/dashboard/providers/<provider>`.

**`Authentication error`**
Kumpirmahing naka-export ang `OMNIROUTE_API_KEY`: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Tinitiyak ng Codex na umiiral ang env var bago gawin ang unang request. Mag-export
ng tunay na key para sa mga protektadong server, o isang placeholder na hindi blangko gaya ng
`OMNIROUTE_API_KEY=local` kapag hindi nangangailangan ng auth ang iyong **lokal** na
instance ng OmniRoute. I-restart ang shell kung idinagdag mo ito sa `~/.bashrc` o `~/.zshrc`.

**`Connection refused`**
Tiyaking tumatakbo ang OmniRoute at tama ang host/port ng `base_url` para sa iyong network (lokal kumpara sa Tailscale kumpara sa VPS).

**Nagka-crash ang session kapag malapit na sa context limit**
Itakda nang tahasan ang `model_context_window` at `model_auto_compact_token_limit`. Tingnan ang talahanayan ng context window sa itaas.

**Masyadong nahuhuli ang compaction**
Ibaba ang `model_auto_compact_token_limit` sa 80–85% ng window. Huwag kailanman itong itakda nang lampas sa 90%.

**Hindi naglo-load ang profile (tahimik na binabalewala ang `-p <name>`)**
Kumpirmahing umiiral ang file sa `~/.codex/<name>.config.toml` (walang prefix na `profile-`). Patakbuhin ang `ls ~/.codex/*.config.toml`.

**Napuputol ang matagal na Codex task habang tumatakbo / nagpapalit ng account sa pagitan ng mga turn**
Tingnan ang [Mga matagal tumakbong task](#long-running-tasks). I-enable ang session affinity (TTL na mas mahaba sa tagal ng task) at taasan o i-disable ang `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Gamitin ang grep sa mga log ng OmniRoute para sa `Idle timeout: no data from`.
