Ang TPROXY transparent decrypt ang **ika-5 capture mode** ng OmniRoute para sa
MITM stack ng [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Hinaharang at **dini-decrypt** nito ang lokal na outbound HTTPS traffic sa Linux
gamit ang kernel TPROXY + policy routing — **nang hindi** nagsi-spoof ng `/etc/hosts` at
**nang hindi** binabago ang mga OS-wide system-proxy setting. Angkop ito sa headless na paggamit
(walang mga DNS edit na kailangang linisin) at awtomatikong nabubura ang mga firewall rule kapag nag-reboot.

Hindi tulad ng ibang mga capture mode, hindi kailangan ng TPROXY ng per-host setup: malinaw nitong
hinaharang ang **anumang** destination host sa isang target port, tinatapos ang TLS gamit
ang isang leaf certificate na iniisyu nito kaagad para sa bawat SNI hostname, kinukuha ang na-decrypt na
palitan, at muling ine-encrypt ang request patungo sa orihinal na destinasyon.

> **Para lang sa Linux, para lang sa root, at kailangang kusang i-enable.** Nangangailangan ang mode na ito ng Linux, isang native addon
> na binuo gamit ang C toolchain, at ng **CAP_NET_ADMIN** capability (karaniwan ay root). Nililimitahan ito
> sa loopback-only na AgentBridge API at naka-disable bilang default. Ang isang pinagkakatiwalaang
> MITM CA na maaaring lumagda para sa anumang host ay isang makapangyarihang capability — tingnan ang [§6 Seguridad](#6-security).

**Source:** `src/mitm/tproxy/`
**API route:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Dashboard toggle:** Traffic Inspector → toolbar ng mga capture mode → **"TPROXY Decrypt"** ⚠
**Tingnan din:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Ano ito at kailan ito gagamitin

May kanya-kanyang limitasyon ang bawat isa sa apat na iba pang capture mode:

| Mode              | Paano idinidirekta ang traffic                          | Limitasyon                                                      |
| ----------------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| AgentBridge       | `/etc/hosts` DNS spoof ng nakapirming hanay ng mga host | mga nakarehistrong IDE-agent host lang                          |
| Custom Hosts      | `/etc/hosts` DNS spoof bawat host                       | isang entry bawat host; kailangan ng sudo para i-edit ang hosts |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env                          | mga app lang na sumusunod sa env var                            |
| System-wide proxy | Mga OS proxy setting                                    | binabago ang global state; kailangang ibalik                    |

Sa halip, idinidirekta ng TPROXY transparent decrypt ang traffic sa **kernel** layer. Mina-markahan nito
ang mga bagong lokal na outbound TCP connection patungo sa isang target port (default na `443`) sa
`mangle OUTPUT` chain, muling idinidirekta ng isang `ip rule` ang mga minarkahang packet sa lokal na paghahatid,
at sa muling pagpasok, ipinapasa ng `TPROXY` target ng `mangle PREROUTING` ang mga ito sa isang
**IP_TRANSPARENT** listener — na siyang nagtatapos sa TLS at kumukuha sa plaintext.

Gamitin ito kapag gusto mong kumuha at mag-decrypt ng traffic mula sa isang process na:

- nakikipag-ugnayan sa isang host na hindi nirerehistro ng AgentBridge, at
- hindi sumusunod sa `HTTP_PROXY`, at
- ayaw mong gambalain sa pamamagitan ng pagbabago sa system-wide proxy.

Dahil nangyayari ang interception sa kernel, **walang kailangang baguhin sa configuration** ng pinagmulang
process — ngunit dapat pagkatiwalaan ng process ang dynamic CA na ini-install ng OmniRoute
(tingnan ang [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Mga Kinakailangan

| Kinakailangan         | Detalye                                                                                                                                                                 |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**                | Linux lamang — ang **IP_TRANSPARENT** ay isang socket option na para lamang sa Linux. Nagbabalik ang loader ng "hindi available" sa lahat ng iba pang platform.         |
| **Pribilehiyo**       | Ang capability na **CAP_NET_ADMIN** upang gawin ang transparent socket at ilapat ang mga panuntunan ng `iptables`/`ip` — sa praktika, patakbuhin bilang root.           |
| **Native addon**      | Dapat i-build o ipadala bilang prebuild ang isang maliit na N-API addon (`src/mitm/tproxy/native/transparent.c`). Tingnan ang [§3](#3-the-native-ip_transparent-addon). |
| **Mga kernel module** | `iptables` na may suporta para sa `TPROXY`, `mangle`, at `mark` match (sinuri gamit ang kernel 6.8.0).                                                                  |

**Maayos na pag-degrade:** kung may anumang kinakailangang nawawala (hindi Linux, walang toolchain,
hindi na-build ang addon), nagbabalik ang addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
ng `null` sa halip na mag-throw. Pagkatapos, iniulat ng status ng capture mode ang
`available: false`, **naka-disable** ang toggle sa dashboard na may tooltip na
"Kailangan ng TPROXY decrypt ang Linux + root + ang native addon", at patuloy na
gumagana ang natitirang bahagi ng OmniRoute.

## §3 Ang native IP_TRANSPARENT addon

Hindi kayang gamitin ng `net` module ng Node ang `setsockopt(IP_TRANSPARENT)` _bago_ ang `bind()`, na
kinakailangan ng TPROXY (kung hindi, dini-drop ng kernel ang mga na-redirect na packet). Ang addon
(`src/mitm/tproxy/native/transparent.c`, na bina-build sa pamamagitan ng `binding.gyp`) ay isang maliit na N-API
module na naglalantad ng tatlong function, na ginagamit sa pamamagitan ng `transparentSocket.ts`:

| Function ng addon                     | Gawain sa socket                                                                                  | Ginagamit para sa                                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, ibinabalik ang raw fd | ang transparent capture listener (ina-adopt ng Node ang fd sa pamamagitan ng `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** sa isang umiiral na fd                                                   | anti-loop (markahan ang sariling mga socket ng proxy)                                                 |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **bago** ang non-blocking na `connect()`, nagbabalik ng fd               | ang muling na-encrypt na upstream forward (dala ng SYN ang mark)                                      |

Binabasa ang orihinal na destinasyon mula sa `socket.localAddress`/`localPort` — pinapanatili ito ng TPROXY,
kaya walang **SO_ORIGINAL_DST**/NAT lookup.

### Pag-build ng addon

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Habang isinasagawa ang `npm run build`, pinapatakbo ng `scripts/build/build-tproxy-native.mjs` ang `node-gyp
rebuild`. Ito ay **para lamang sa Linux at hindi fatal** — kapag walang toolchain, mananatili lamang
  na hindi available ang capture mode.
- Kinokopya ng `assembleStandalone.mjs` ang `build/Release/transparent.node` papunta sa
  standalone bundle; hinahanap ito ng `transparentSocket.ts` nang parehong module-relative at
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`).
- Naka-git-ignore ang `build/` at `prebuilds/` — ang binary ay **bina-build, hindi kailanman
  kino-commit**.

Sinusuri ng loader ang mga sumusunod ayon sa pagkakasunod-sunod ng prayoridad:
`native/build/Release/transparent.node`, pagkatapos ay `native/prebuilds/transparent.node`
(parehong module-relative at nasa ilalim ng `<cwd>/src/mitm/tproxy/`).

## §4 Ang dynamic CA bawat SNI at installer ng trust store

> **Update sa #6684:** ang static server ng AgentBridge (`src/mitm/server.cjs`) ay
> gumagamit na rin ng parehong pattern ng arkitektura ng CA/leaf sa halip na iisang
> static na self-signed leaf. Gumagamit ito ng **hiwalay** na instance ng CA
> (`src/mitm/cert/rootCa.ts`, naka-persist sa `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> at ini-install sa dati nang `omniroute-mitm.crt` na slot ng trust store
> (pinapalitan ang lumang iisang leaf doon—hindi kailangan ng paglilinis para sa
> dalawahang trust), na pinananatiling ganap na hiwalay sa sariling
> `omniroute-tproxy-ca.crt` na slot ng TPROXY sa ibaba.
> Awtomatikong nakakakuha ang mga bagong install ng AgentBridge ng modelo ng CA;
> ang install na nagtitiwala na sa lumang static leaf ay patuloy na gumagamit
> nito hanggang sa kusang paganahin ito ng operator sa pamamagitan ng
> `MITM_ROOT_CA_ENABLED=true` (tingnan ang `src/mitm/cert/migration.ts`)—ang isang
> pinagkakatiwalaang MITM CA na maaaring lumagda ng leaf para sa **anumang** host
> ay higit na makapangyarihan kaysa sa lumang fixed-SAN leaf, kaya hindi kailanman
> tahimik na isinasagawa ang paglipat para sa isang install na nagtitiwala na rito.

Sa kasaysayan, gumagana lamang ang static na MITM cert ng AgentBridge dahil
pinepeke ng AgentBridge DNS ang isang **nakapirming** hanay ng mga host (na
pinag-isa na ngayon sa modelo sa ibaba). Sumasalo ang TPROXY ng **anumang** mga
host, kaya dapat magpakita ang listener nito ng wastong leaf para sa anumang SNI
na hinihiling ng client—ang parehong kinakailangan na mayroon na ngayon ang
AgentBridge para sa buong hanay ng `MITM_TOOL_HOSTS` (9 na entry ng tool) sa
halip na 4 na antigravity host lamang.

### Dynamic CA (`src/mitm/tproxy/dynamicCert.ts`)

Nagpapatakbo ang `DynamicCertStore` ng lokal na CA (na binuo gamit ang
dependency na `selfsigned`) na:

- Bumubuo ng pangmatagalang CA sa pamamagitan ng `generateMitmCa()` (CN
  `"OmniRoute MITM CA"`, 10-taong bisa, `basicConstraints CA=true` +
  `keyUsage keyCertSign,cRLSign`, 2048-bit RSA / SHA-256).
- Nag-iisyu ng **leaf bawat hostname ng SNI kapag hiniling** sa pamamagitan ng
  `issueLeafCert()` (1-taong bisa, `subjectAltName` = ang host ng SNI) at
  nagka-cache ng isang `tls.SecureContext` bawat hostname.
- Inilalantad ang `createSNICallback()` para sa server na nagte-terminate ng TLS
  (tingnan ang [§5](#5-how-decrypt-and-capture-work)).
- Maaaring buuin gamit ang isang `existingCa` upang manatiling stable ang CA sa
  bawat restart (nang sa gayon ay hindi na kailangang muling i-install ang trust
  store).

Ang private key ng CA ay **hindi kailanman lumalabas sa makina**.

### Installer ng trust store (`src/mitm/tproxy/caTrust.ts`)

Dapat pagkatiwalaan ng nasalong client ang dynamic CA, kaya kapag sinimulan ang
capture mode, ini-install ang cert ng CA sa trust store ng OS sa ilalim ng isang
**nakalaang slot**—`omniroute-tproxy-ca.crt` (constant na
`TPROXY_CA_CERT_NAME`)—na pinananatiling hiwalay sa slot ng static na MITM cert
(`omniroute-mitm.crt`) upang hindi mapatungan ng dalawa ang isa't isa.

Tinutukoy ng `installTproxyCa(caPem, sudoPassword?)` ang anchor directory ng
distro (ayon sa pagkakasunod-sunod: Debian-style muna) at pinapatakbo ang
katumbas na refresh command:

| Anchor directory                            | Refresh command          |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Sa pag-install, inilalagay muna ang PEM sa isang pansamantalang file, pagkatapos
ay isinasagawa nang may pribilehiyo ang `mkdir -p` sa anchor directory,
ginagamit ang `cp` upang ilagay rito ang pansamantalang file, at pinapatakbo ang
refresh command. Ang `uninstallTproxyCa()` ay nag-aalis lamang ng nakalaang slot
(hindi ginagalaw ang static na MITM cert) at nagre-refresh—wala itong ginagawa
sa mga system na hindi Linux.

Tumatakbo ang lahat ng privileged command sa pamamagitan ng
`execFileWithPassword` (`src/mitm/systemCommands.ts`)—`spawn` na may **mga array
ng argumento, walang shell, walang string interpolation** (Mahigpit na
Panuntunan #13). Kapag root ang process (hal. ang VPS), direktang tumatakbo ang
target at hindi kailangan ng password; sa isang non-root na desktop, ipinapasa
ang `sudoPassword` sa pamamagitan ng `sudo -S` sa stdin.

> Ibinibigay ang `sudoPassword` ng desktop sa POST body upang pahintulutan ang
> pag-install sa trust store; ganap itong binabalewala kapag root ang process.

## §5 Paano gumagana ang pag-decrypt at capture

Ang pipeline (lahat ay nasa ilalim ng `src/mitm/tproxy/`):

```
lokal na app  ──TCP/443──▶  minamarkahan ng mangle OUTPUT ang koneksyon (fwmark)
                            ip rule → lokal na routing table → lo
                            mangle PREROUTING TPROXY → IP_TRANSPARENT listener (port 8443)
                                │  captureMode.ts: binabasa ang orihinal na destinasyon mula sa socket.localAddress
                                ▼
                            tlsCapture.ts:
                              1. Tinatapos ang TLS ng CLIENT gamit ang per-SNI leaf (dynamicCert)
                              2. pina-parse ng internal na http.Server ang na-decrypt na plaintext
                              3. capture → globalTrafficBuffer.push() na may source: "tproxy"
                                 (inilalapat ang sanitizeHeaders + maskSecret)
                              4. ipinapasa nang MULING naka-encrypt sa orihinal na destinasyon
                                 sa pamamagitan ng bypass-marked socket (connectMarked, anti-loop)
                                │
                                ▼
                            orihinal na upstream (api.example.com)
```

- **TLS termination** (`createTlsCaptureServer`): binabalot ang raw na na-intercept na
  socket sa isang server-side na `tls.TLSSocket` gamit ang SNI callback ng dynamic CA,
  pagkatapos ay ipinapasa ang na-decrypt na stream sa isang internal na `http.Server`
  (ang karaniwang MITM termination na pamamaraan). Nililimitahan ng
  `MITM_IDLE_TIMEOUT_MS` ang mga lifetime ng socket upang hindi maubos ng isang
  hindi tumutugon na tunnel ang mga file descriptor.
- **Capture** (`handleDecryptedRequest`): nagpu-push ng `InterceptedRequest` na may
  `source: "tproxy"`, status na nagsisimula sa `"in-flight"`, mga header na idinaan sa
  `sanitizeHeaders()`, at mga body na idinaan sa `maskSecret()` bago pumasok ang mga ito
  sa buffer. Pagkatapos, ina-update ang entry gamit ang response, mga size, at latency.
- **Muling naka-encrypt na forwarding** (`createForward` / `realForward`): muling
  ine-encrypt papunta sa orihinal na destinasyon. Ang default ng `rejectUnauthorized`
  ay **`true`** (secure bilang default) — bine-verify ang upstream cert laban sa SNI/Host
  na hiniling ng client, kaya eksaktong tinatanggihan ng proxy ang tatanggihan din ng
  orihinal na client.

### Anti-loop (SO_MARK)

Dahil minamarkahan ng mga rule ang mga bagong lokal na outbound connection, ang
**sariling** muling naka-encrypt na forward ng proxy ay karaniwang muling
mai-intercept — isang infinite loop. Pinoprotektahan ang forward path laban dito
gamit ang bypass socket mark (**SO_MARK**):

- Binubuksan ng `realForward` ang upstream socket nito sa pamamagitan ng
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539` —
  na nagse-set ng **SO_MARK** **bago** ang `connect()`, kaya dala ng SYN ng forward
  ang bypass mark.
- Hindi isinasama ng `mangle OUTPUT` rule ang mga koneksyong mayroon nang bypass mark
  (`-m mark ! --mark <bypassMark>`), kaya **hindi** muling minamarkahan ang forward
  ng proxy at hindi ito muling pumapasok sa TPROXY.

> Tala sa implementasyon: dapat i-install ang bypass-marked socket sa
> `createConnection` ng agent (`https.request({ createConnection })` ay tahimik na
> binabalewala kapag may agent), kung hindi ay magbubukas ang forward ng unmarked na
> socket at babalik ang loop. Ito ang anti-loop fix na na-validate sa e2e.

## §6 Seguridad

| Kontrol                                          | Detalye                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **API para lamang sa loopback**                  | Saklaw ng prefix na `/api/tools/agent-bridge/` sa `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`) ang `/api/tools/agent-bridge/tproxy`. Ipinapatupad ang loopback **bago** ang awtentikasyon (Mahihigpit na Panuntunan #15 + #17) — hindi makapagsisimula ng TPROXY capture ang isang nalantad na JWT sa pamamagitan ng tunnel, na naglalapat ng mga panuntunan ng `iptables` at nag-i-install ng trust-store CA sa pamamagitan ng mga child process. |
| **Nakalaang puwesto ng CA**                      | Ini-install ang dynamic na CA sa `omniroute-tproxy-ca.crt`, at hindi nito kailanman pinapatungan ang static na MITM certificate.                                                                                                                                                                                                                                                                                                                                   |
| **Hindi kailanman lumalabas sa host ang CA key** | Pinananatili ng `DynamicCertStore` sa memory ang CA key; hindi ito ine-export.                                                                                                                                                                                                                                                                                                                                                                                     |
| **Pagtatakip ng mga lihim**                      | Pinapatakbo ang `maskSecret()` sa mga body ng request/response at ang `sanitizeHeaders()` sa mga header **bago** ang `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                                                                 |
| **Walang shell interpolation**                   | Pinapatakbo ang lahat ng command ng `iptables`/`ip`/trust-store sa pamamagitan ng `execFile`/`execFileWithPassword` gamit ang mga array ng argumento (Mahigpit na Panuntunan #13).                                                                                                                                                                                                                                                                                 |
| **Pag-verify sa upstream certificate**           | Bine-verify ng muling in-encrypt na forward ang upstream certificate bilang default (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                                                                  |
| **Paglilinis ng error**                          | Dumaraan sa `sanitizeErrorMessage()` ang mga tugon sa error ng route (Mahigpit na Panuntunan #12).                                                                                                                                                                                                                                                                                                                                                                 |

**Makapangyarihang kakayahan ang MITM CA.** Ang isang CA na pinagkakatiwalaan ng OS at maaaring lumagda para sa anumang
host ay nangangahulugang maaaring i-decrypt ang anumang naharang ng OmniRoute. Protektado ito sa likod ng
hayagan at local-only na TPROXY capture mode, naka-off bilang default, at inaalis ang entry sa trust-store
kapag itinigil mo ang mode.

## §7 Transaksiyonal na pag-apply / pag-revert ng firewall

Hindi kailanman dapat mag-iwan ang isang pag-crash ng `mangle` rule o lumang route. Ginagarantiya ng command builder
(`src/mitm/tproxy/commands.ts`) at runner (`src/mitm/tproxy/setup.ts`) na ang
**revert ay ang eksaktong kabaligtaran ng apply, sa baligtad na pagkakasunod-sunod**.

Pinapatakbo ng `applyTproxy(cfg)` ang mga apply command ayon sa pagkakasunod-sunod; sa **anumang** pagkabigo, nagpapatakbo ito ng
best-effort na buong `revertTproxy(cfg)` at muling ibinabato ang error — kaya ang firewall ay alinman sa
ganap na nailapat o ganap na na-revert, at hindi kailanman bahagyang nailapat. Pinapatakbo ng `revertTproxy(cfg)` ang
mga kabaligtarang command sa baligtad na pagkakasunod-sunod at hindi pinapansin ang mga pagkabigo (idempotent — ligtas tawagin
nang walang kondisyon, hal. mula sa cleanup na `repairMitm()` ng AgentBridge).

Pinapatakbo ang `validateTproxyConfig(cfg)` bago ang anumang command: ang mga port ay dapat `1–65535`,
ang `mark`/`routeTable`/`bypassMark` ay dapat mga positibong integer, at ang `bypassMark` ay dapat
naiiba sa `mark` (anti-loop).

### Mga apply command (ayon sa pagkakasunod-sunod)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Tinatanggal ng revert ang mga ito sa baligtad na pagkakasunod-sunod: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> **Nakabatay sa OUTPUT** ang recipe dahil ang MITM use case ay _lokal_ na papalabas na
> trapiko (mga app sa parehong host), na hindi nakikita ng TPROXY sa `PREROUTING` lamang
> — forwarded traffic lang ang nakikita ng `PREROUTING`. Minamarkahan ng `OUTPUT` chain ang mga bagong
> lokal na koneksyon, muli silang niruruta ng `ip rule` patungo sa lokal na paghahatid (`lo`), at
> pagkatapos ay itinatalaga sila ng `PREROUTING` sa transparent listener.

## §8 Configuration

Tinatanggap ng start request (`POST /api/tools/agent-bridge/tproxy`) ang mga sumusunod na
field, na bina-validate ng `StartTproxyBodySchema` (`tproxy/route.ts`). Opsyonal ang lahat
at gumagamit ng kani-kanilang default kapag walang ibinigay:

| Field            | Uri                | Default  | Mga Tala                                                                                                                         |
| ---------------- | ------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Destination TCP port na ita-transparently intercept                                                                              |
| **mark**         | int (≥1)           | `0x2333` | Firewall mark na itinatakda sa `OUTPUT`, at itinutugma ng `ip rule` + `PREROUTING`                                               |
| **onPort**       | int (1–65535)      | `8443`   | Port na bina-bind ng transparent (**IP_TRANSPARENT**) listener                                                                   |
| **routeTable**   | int (≥1)           | `233`    | Policy-routing table id na naglalaman ng route na `local 0.0.0.0/0`                                                              |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Bypass socket mark (**SO_MARK**) na itinatakda ng proxy sa sarili nitong upstream conns; hindi isinasama sa `OUTPUT` (anti-loop) |
| **sudoPassword** | string             | —        | Para lang sa mga non-root desktop: nagbibigay-awtorisasyon sa pag-install sa trust store; binabalewala kapag root                |

**Walang environment variables** para sa TPROXY — ang lahat ng configuration ay sa pamamagitan ng
POST body o ng mga default sa itaas.

## §9 Pag-enable mula sa Traffic Inspector

1. Buksan ang **Traffic Inspector** (`/dashboard/tools/traffic-inspector`).
2. Sa toolbar ng mga capture mode, hanapin ang ⚠ button na **"TPROXY Decrypt"**
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Kung ito ay **naka-disable** at may tooltip na "Nangangailangan ang TPROXY decrypt ng Linux + root +
     native addon", hindi available ang native addon sa host na ito (hindi Linux,
     walang toolchain, o hindi na-build ang addon). Tingnan ang [§2](#2-requirements) at [§3](#3-the-native-ip_transparent-addon).
3. I-click ang button. Tinatawag nito ang `POST /api/tools/agent-bridge/tproxy` sa pamamagitan ng
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), na:
   bumubuo ng dynamic CA, nagbubukas ng transparent listener, inilalapat ang mga firewall
   rule, at ini-install ang CA sa trust store ng OS.
4. Habang tumatakbo, nagiging amber ang toggle at ipinapakita ang kasalukuyang bilang ng mga intercept
   (`· <interceptCount>`). Lumilitaw sa listahan ng mga request ang mga na-intercept na request na may
   `source: "tproxy"`.
5. I-click itong muli upang ihinto — isinasara ng `DELETE /api/tools/agent-bridge/tproxy` sa pamamagitan ng
   `stopTproxyCaptureMode()` ang listener, ina-uninstall ang CA, at ibinabalik
   ang mga firewall rule.

Ang status ng capture mode (tumatakbo / available / bilang ng mga intercept / listener port) ay nagmumula
sa `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` sa
`src/mitm/tproxy/captureManager.ts`). **Isang** TPROXY session lang ang tumatakbo sa bawat pagkakataon —
tatanggihan ang pagsisimula ng pangalawa nang may mensaheng "Tumatakbo na ang TPROXY capture mode".

## §10 Pag-troubleshoot

### Naka-disable ang toggle

Hindi ma-load ang native addon. Kumpirmahin na: gumagamit ka ng Linux, na-build mo ang addon
(`npm run build:native:tproxy`), at kayang i-load ng process ang `transparent.node`.
Kinokontrol ng `isTransparentSocketAvailable()` ang toggle; nagbabalik ang `GET /api/tools/agent-bridge/tproxy`
ng `available: false` kapag nawawala ang addon.

### Walang nakukuha

- Kumpirmahing aktuwal na kumokonekta ang na-intercept na process sa naka-configure na `dport`
  (default na `443`).
- Kumpirmahing pinagkakatiwalaan ng process ang dynamic CA. Naka-install ang CA bilang
  `omniroute-tproxy-ca.crt`; maaaring kailanganin ding idagdag doon ang cert para sa mga app na may sariling trust store (Firefox/Chrome NSS).
- Patakbuhin ang **Diagnose** self-test ng AgentBridge (tingnan ang
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) para sa mga pagsusuri sa cert-trusted / server
  health.

### Mga lumang firewall rule pagkatapos ng pag-crash

Ang `revertTproxy()` ang eksaktong kabaligtaran ng apply at idempotent ito. Ibinabalik ng paghinto sa
mode ang mga rule; kung sapilitang nahinto ang OmniRoute habang nasa kalagitnaan ng session, gamitin ang
**Repair** action ng AgentBridge (`POST /api/tools/agent-bridge/repair`) upang i-undo ang naiwang system
state (DNS spoof, root CA, system proxy). Awtomatikong nafa-flush din ang mga TPROXY `mangle` rule at route
kapag nag-reboot.

### Walang-katapusang loop / nai-intercept ng proxy ang sarili nitong forward

Ito ang anti-loop na kaso. Kumpirmahing naiiba ang `bypassMark` sa `mark` (ipinapatupad ito ng validation)
at gumagamit ang forward ng `connectMarked` (ginagawa nito iyon sa `realForward`).
Tingnan ang [§5 Anti-loop](#anti-loop-so_mark).
