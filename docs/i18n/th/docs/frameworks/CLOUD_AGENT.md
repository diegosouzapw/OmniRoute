OmniRoute ประสานการทำงานของเอเจนต์เขียนโค้ดที่โฮสต์บนคลาวด์จากผู้ให้บริการภายนอก (Codex Cloud, Cursor,
Devin, Jules) ในรูปแบบงานที่ทำงานต่อเนื่องระยะยาว เอเจนต์แต่ละตัวถูกครอบด้วยอินเทอร์เฟซมาตรฐานเดียวกัน เพื่อให้
ไคลเอนต์สามารถส่งพรอมต์ + URL ของ repo และรับผลลัพธ์ได้โดยไม่ต้องจัดการกับ
API เฉพาะของผู้ให้บริการแต่ละราย

งาน Cloud Agent **ไม่ใช่** การเติมข้อความแชตแบบปกติ แต่เป็น
หน่วยงานแบบหลายขั้นตอนที่คงอยู่ถาวร ซึ่งอาจใช้เวลาตั้งแต่หลายนาทีจนถึงหลายชั่วโมง สามารถสร้าง Pull Request เป็น
อาร์ติแฟกต์ และรองรับข้อความติดตามผล รวมถึงจุดตรวจสอบการอนุมัติแผน (ในผู้ให้บริการบางราย)

| ID ผู้ให้บริการ | คลาส               | ซอร์ส                                 | URL ฐานของระบบต้นทาง                    | การอนุมัติแผน     |
| --------------- | ------------------ | ------------------------------------- | --------------------------------------- | ----------------- |
| `jules`         | `JulesAgent`       | `src/lib/cloudAgent/agents/jules.ts`  | `https://jules.googleapis.com/v1alpha`  | มี                |
| `devin`         | `DevinAgent`       | `src/lib/cloudAgent/agents/devin.ts`  | `https://api.devin.ai/v1`               | มี                |
| `codex-cloud`   | `CodexCloudAgent`  | `src/lib/cloudAgent/agents/codex.ts`  | `https://api.openai.com/v1/codex/cloud` | ไม่มี (อัตโนมัติ) |
| `cursor-cloud`  | `CursorCloudAgent` | `src/lib/cloudAgent/agents/cursor.ts` | `https://api.cursor.com/v0`             | ไม่มี (อัตโนมัติ) |

`Record<string, CloudAgentBase>` แบบอยู่ในหน่วยความจำ ซึ่งถูกเติมข้อมูลเมื่อโหลดโมดูล

## สถาปัตยกรรม

```
ไคลเอนต์ (แดชบอร์ด / CLI / API)
  → POST /api/v1/agents/tasks (ต้องมีการยืนยันตัวตนสำหรับการจัดการ)
    → การตรวจสอบความถูกต้องด้วย CreateCloudAgentTaskSchema (Zod)
    → registry.getAgent(providerId)
    → getCloudAgentCredentials(providerId)
      └─ ดึงข้อมูลจาก getProviderConnections({ provider, isActive: true })
         (ใช้ apiKey ก่อน หากไม่มีจึงใช้ accessToken)
    → agent.createTask({ prompt, source, options }, credentials)
      └─ ส่ง HTTP POST ไปยัง API ของผู้ให้บริการต้นทาง
      └─ คืนค่า CloudAgentTask พร้อม id ภายใน + externalId
    → insertCloudAgentTask(...) ลงใน cloud_agent_tasks (SQLite)

การโพล (ซิงค์แบบ lazy เมื่ออ่าน):
  GET /api/v1/agents/tasks/[id]
    → getCloudAgentTaskById(id)
    → agent.getStatus(externalId, credentials)  // รีเฟรชสถานะ + กิจกรรม
    → updateCloudAgentTask(...) ด้วยสถานะ ผลลัพธ์ และ completed_at ใหม่
    → คืนค่างานที่ผ่านการซีเรียลไลซ์

การโต้ตอบ:
  POST /api/v1/agents/tasks/[id]  เนื้อหา: { action: "approve" | "message" | "cancel" }
    → agent.approvePlan(externalId, credentials)        สำหรับ "approve"
    → agent.sendMessage(externalId, message, credentials) สำหรับ "message"
    → เปลี่ยนสถานะเป็น "cancelled"                     สำหรับ "cancel" (เฉพาะภายในระบบ)
```

การซิงค์เป็นแบบ **lazy**: ระบบจะรีเฟรชสถานะจากระบบต้นทางทุกครั้งที่เรียก `GET /tasks/[id]`
ไม่มีตัวโพลที่ทำงานอยู่เบื้องหลัง แดชบอร์ดที่ต้องการสถานะล่าสุดควรโพล endpoint แบบ GET
ตามช่วงเวลาที่เหมาะสม

## อินเทอร์เฟซ `CloudAgentBase`

แหล่งที่มา: `src/lib/cloudAgent/baseAgent.ts`

```typescript
export interface AgentCredentials {
  apiKey: string;
  baseUrl?: string;
}

export interface CreateTaskParams {
  prompt: string;
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
}

export interface GetStatusResult {
  status: CloudAgentStatus;
  externalId?: string;
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
}

export abstract class CloudAgentBase {
  abstract readonly providerId: string;
  abstract readonly baseUrl: string;

  abstract createTask(p: CreateTaskParams, c: AgentCredentials): Promise<CloudAgentTask>;
  abstract getStatus(externalId: string, c: AgentCredentials): Promise<GetStatusResult>;
  abstract approvePlan(externalId: string, c: AgentCredentials): Promise<void>;
  abstract sendMessage(
    externalId: string,
    message: string,
    c: AgentCredentials
  ): Promise<CloudAgentActivity>;
  abstract listSources(
    c: AgentCredentials
  ): Promise<{ name: string; url: string; branch?: string }[]>;

  protected mapStatus(raw: string): CloudAgentStatus; // การแปลงสตริงจากต้นทางเป็น enum ด้วยฮิวริสติก
  protected generateTaskId(): string; // `task_<ts>_<rand>`
  protected generateActivityId(): string; // `act_<ts>_<rand>`
}
```

`CodexCloudAgent.approvePlan` จะ throw โดยตั้งใจ — Codex Cloud วางแผนโดยอัตโนมัติและ
ไม่มีขั้นตอนการอนุมัติ `CodexCloudAgent.listSources` คืนค่า `[]`

`CursorCloudAgent` ควบคุม Background / Cloud Agents ของ Cursor ผ่าน REST
API อย่างเป็นทางการ (`api.cursor.com/v0`) โดยใช้ **คีย์ API ของผู้ใช้หรือบัญชีบริการ** — เป็นทางเลือกจากผู้ให้บริการโดยตรงที่ปลอดภัยกว่า
การนำเซสชัน OAuth ของ Cursor IDE กลับมาใช้ซ้ำ (ผู้ให้บริการ `cursor`
ซึ่งมีคำเตือนเกี่ยวกับความเสี่ยงที่จะถูกแบน) โดยเป็นอะแดปเตอร์ REST แบบธรรมดา (ไม่มี dependency แบบเนทีฟของ `@cursor/sdk`)
`approvePlan` จะ throw (เอเจนต์ Cursor ทำงานโดยอัตโนมัติ) ส่วน `listSources` จะแสดงรายการ
repository ที่คีย์สามารถเข้าถึงได้ Cursor คืนค่า enum สถานะเป็นตัวพิมพ์ใหญ่
(`CREATING`/`RUNNING`/`FINISHED`/`ERROR`) ซึ่งจะถูกแมปไปยัง
`CloudAgentStatus` ที่ใช้ร่วมกันอย่างชัดเจน `baseUrl` สามารถเขียนทับแยกตามข้อมูลรับรองได้ เพื่อให้สามารถ
แก้ไขเวอร์ชัน/พาธของ API โดยไม่ต้องเปลี่ยนแปลงโค้ด

## ชนิดข้อมูลโดเมน

แหล่งที่มา: `src/lib/cloudAgent/types.ts`

```typescript
export const CLOUD_AGENT_STATUS = {
  QUEUED: "queued",
  RUNNING: "running",
  AWAITING_APPROVAL: "awaiting_approval",
  COMPLETED: "completed",
  FAILED: "failed",
  CANCELLED: "cancelled",
} as const;

export interface CloudAgentSource {
  repoName: string;
  repoUrl: string; // ต้องเป็น URL ที่ถูกต้อง
  branch?: string;
}

export interface CloudAgentResult {
  prUrl?: string;
  prNumber?: number;
  commitMessage?: string;
  diffUrl?: string;
  summary?: string;
  duration?: number; // วินาที เป็นจำนวนเต็มบวก
  cost?: number; // จำนวนทศนิยมบวก
}

export interface CloudAgentActivity {
  id: string;
  type: "plan" | "command" | "code_change" | "message" | "error" | "completion";
  content: string;
  timestamp: string; // ISO 8601
  metadata?: Record<string, unknown>;
}

export interface CloudAgentTask {
  id: string; // id ภายในรูปแบบ `task_...`
  providerId: "jules" | "devin" | "codex-cloud" | "cursor-cloud";
  externalId?: string; // id ของผู้ให้บริการต้นทาง
  status: CloudAgentStatus;
  prompt: string; // 1..10000 อักขระ
  source: CloudAgentSource;
  options: {
    autoCreatePr?: boolean;
    planApprovalRequired?: boolean;
    environment?: Record<string, string>;
  };
  result?: CloudAgentResult;
  activities: CloudAgentActivity[];
  error?: string;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
}
```

สคีมาการตรวจสอบความถูกต้อง (`CreateCloudAgentTaskSchema`, `UpdateCloudAgentTaskSchema`) จะถูก
export ควบคู่ไปกับชนิดข้อมูล และถูกใช้โดยตัวจัดการ route

## ฐานข้อมูล

แหล่งที่มา: `src/lib/cloudAgent/db.ts` — ตารางจะถูกสร้างแบบ lazy ผ่าน
`createCloudAgentTaskTable()` (ซึ่งถูกเรียกจาก `src/lib/cloudAgent/index.ts` ขณะ
นำเข้าโมดูลด้วย)

```sql
CREATE TABLE IF NOT EXISTS cloud_agent_tasks (
  id           TEXT PRIMARY KEY,
  provider_id  TEXT NOT NULL,
  external_id  TEXT,
  status       TEXT NOT NULL DEFAULT 'queued',
  prompt       TEXT NOT NULL,
  source       TEXT NOT NULL,             -- JSON
  options      TEXT DEFAULT '{}',         -- JSON
  result       TEXT,                       -- JSON
  activities   TEXT DEFAULT '[]',          -- JSON
  error        TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_provider ON cloud_agent_tasks(provider_id);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_status   ON cloud_agent_tasks(status);
CREATE INDEX IF NOT EXISTS idx_cloud_agent_tasks_created  ON cloud_agent_tasks(created_at DESC);
```

`updateCloudAgentTask` บังคับใช้ **รายการคอลัมน์ที่อนุญาต** เพื่อป้องกัน SQL injection:
`status`, `prompt`, `source`, `options`, `result`, `activities`, `error`,
`completed_at` คีย์อื่นใดในการอัปเดตบางส่วนจะถูกละทิ้งโดยไม่มีการแจ้งเตือน

## REST API — วงจรชีวิตของงาน

**การยืนยันตัวตน:** endpoint `/api/v1/agents/tasks*` ทั้งหมดต้องใช้
**การยืนยันตัวตนระดับการจัดการ** (`requireCloudAgentManagementAuth` ครอบ
`requireManagementAuth` จาก `src/lib/api/requireManagementAuth`) ข้อกำหนดนี้มีผลหลังจาก
commit `588a0333` (_"fix(auth): require management auth for agent and cooldown APIs"_)

| เมธอด   | พาธ                           | วัตถุประสงค์                                               |
| ------- | ----------------------------- | ---------------------------------------------------------- |
| OPTIONS | `/api/v1/agents/tasks`        | CORS preflight                                             |
| GET     | `/api/v1/agents/tasks`        | แสดงรายการงาน (ตัวกรอง: `provider`, `status`, `limit≤500`) |
| POST    | `/api/v1/agents/tasks`        | สร้างงาน (ส่งไปยัง upstream และจัดเก็บถาวร)                |
| DELETE  | `/api/v1/agents/tasks?id=...` | ลบงานตาม query id (**ไม่** ยกเลิกงานใน upstream)           |
| OPTIONS | `/api/v1/agents/tasks/[id]`   | CORS preflight                                             |
| GET     | `/api/v1/agents/tasks/[id]`   | อ่านงานและซิงค์สถานะจาก upstream แบบ lazy                  |
| POST    | `/api/v1/agents/tasks/[id]`   | การดำเนินการ: `approve` / `message` / `cancel`             |
| DELETE  | `/api/v1/agents/tasks/[id]`   | ลบงานตาม path id                                           |

### สร้างงาน

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "devin",
    "prompt": "Fix the bug in src/foo.ts where the parser returns null",
    "source": {
      "repoName": "user/repo",
      "repoUrl": "https://github.com/user/repo",
      "branch": "main"
    },
    "options": {
      "autoCreatePr": true,
      "planApprovalRequired": false
    }
  }'
```

การตอบกลับ `201`:

```json
{
  "data": {
    "id": "task_1731512345678_abc123def",
    "providerId": "devin",
    "externalId": "session_xyz",
    "status": "queued",
    "prompt": "...",
    "source": { "repoName": "user/repo", "repoUrl": "...", "branch": "main" },
    "options": { "autoCreatePr": true },
    "createdAt": "2026-05-13T12:34:56.789Z"
  }
}
```

### อนุมัติแผน

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"action":"approve"}'
```

### ส่งข้อความติดตามผล

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -d '{"action":"message","message":"Also add a unit test for the parser"}'
```

### ยกเลิก (เฉพาะสถานะภายในระบบ)

```bash
curl -X POST http://localhost:20128/api/v1/agents/tasks/<id> \
  -d '{"action":"cancel"}'
```

`cancel` จะเปลี่ยน `status` เป็น `"cancelled"` ในฐานข้อมูลภายในระบบ แต่**ไม่**เรียก
ผู้ให้บริการ upstream เนื่องจากไม่มี abort RPC ใน `CloudAgentBase` หากต้องการหยุดการเรียกเก็บเงิน
จาก upstream ให้ยุติงานผ่านคอนโซลของผู้ให้บริการโดยตรง

## REST API — การเชื่อมต่อกับผู้ให้บริการคลาวด์

ปลายทางเสริมเหล่านี้ภายใต้ `src/app/api/cloud/` ถูกใช้โดยไคลเอนต์ระยะไกล
(CLI, แอป Electron หรือเวิร์กเกอร์ซิงค์) เพื่ออ่านข้อมูลเมตาของการเชื่อมต่อผู้ให้บริการ
และแปลงชื่อแทนของโมเดล ปลายทางเหล่านี้ตรวจสอบสิทธิ์ด้วย **API key ปกติ**
(ผ่าน `validateApiKey`) ไม่ใช่การตรวจสอบสิทธิ์สำหรับการจัดการที่ใช้โดยปลายทางงาน

| เมธอด | พาธ                             | วัตถุประสงค์                                                                    |
| ----- | ------------------------------- | ------------------------------------------------------------------------------- |
| POST  | `/api/cloud/auth`               | ตรวจสอบ API key และส่งคืนข้อมูลเมตาการเชื่อมต่อที่ปกปิดแล้วพร้อมชื่อแทนของโมเดล |
| PUT   | `/api/cloud/credentials/update` | รีเฟรช `accessToken` / `refreshToken` / `expiresAt`                             |
| POST  | `/api/cloud/model/resolve`      | แปลงชื่อแทนของโมเดลเป็น `{ provider, model }`                                   |
| GET   | `/api/cloud/models/alias`       | แสดงชื่อแทนของโมเดลทั้งหมด                                                      |
| PUT   | `/api/cloud/models/alias`       | กำหนดชื่อแทนของโมเดล (และซิงค์ไปยัง Cloud โดยอัตโนมัติหากเปิดใช้งาน)            |

`/api/cloud/auth` จะไม่ส่งคืน `apiKey` / `accessToken` / `refreshToken` แบบไม่ปกปิด โดยจะ
ส่งคืน `hasApiKey`, `hasAccessToken`, `hasRefreshToken` และตัวอย่างแบบปกปิด
(`maskedApiKey`: 4 ตัวแรก + `****` + 4 ตัวสุดท้าย)

## การค้นหาข้อมูลประจำตัว

`getCloudAgentCredentials(providerId)` ใน `src/lib/cloudAgent/api.ts`:

1. โหลดการเชื่อมต่อผู้ให้บริการที่ใช้งานอยู่ผ่าน `getProviderConnections({ provider: providerId, isActive: true })`
2. สำหรับแต่ละการเชื่อมต่อ จะเลือกใช้ `apiKey` ก่อน (หลังตัดช่องว่าง) และใช้ `accessToken` เป็นตัวสำรอง
3. ส่งคืนโทเค็นแรกที่ไม่ว่าง โดยห่อเป็น `{ apiKey: token }`
4. ส่งคืน `null` หากไม่พบโทเค็นที่ใช้งานได้ — API จะตอบกลับด้วย `400` พร้อม
   `"No active credentials configured for cloud agent provider: <id>"`

ซึ่งหมายความว่า Cloud Agents ใช้ตาราง Provider Connection เดียวกับผู้ให้บริการ LLM
ทั่วไป หากต้องการเปิดใช้งาน Jules ให้สร้างการเชื่อมต่อที่ใช้งานอยู่โดยมี `provider: "jules"`
และกำหนดค่า `apiKey`

## แดชบอร์ด

ซอร์ส: `src/app/(dashboard)/dashboard/cloud-agents/page.tsx`

หน้า React ที่มี `"use client"` ซึ่ง:

- แสดงรายการงาน (สำรวจเป็นระยะผ่าน `GET /api/v1/agents/tasks`)
- ส่งงานใหม่ผ่านฟอร์มที่แมปกับ `CreateCloudAgentTaskSchema`
- แสดงป้ายสถานะ (`queued`, `running`, `awaiting_approval`, `completed`,
  `failed`, `cancelled`) และเรนเดอร์ไทม์ไลน์ `activities[]`
- แสดง `result.prUrl` / `commitMessage` / `summary` เมื่อ `status === "completed"`

## การผสานรวมกับ A2A

Cloud Agents สามารถเปิดให้ใช้งานเป็นสกิล A2A ได้โดยลงทะเบียนสกิล A2A ที่มอบหมาย
ตัวจัดการ `tasks/send` ให้กับ `getAgent(...).createTask(...)` และแปลงเหตุการณ์สถานะงาน A2A
เป็นโปรโตคอล JSON-RPC 2.0 ดู [A2A-SERVER.md](./A2A-SERVER.md)

## การเพิ่ม Cloud Agent ใหม่

1. สร้าง `src/lib/cloudAgent/agents/<name>.ts` ที่สืบทอดจาก `CloudAgentBase`
2. อิมพลีเมนต์ `createTask`, `getStatus`, `approvePlan` (หรือ throw หากใช้ไม่ได้),
   `sendMessage`, `listSources` ใช้ `this.mapStatus(...)` เพื่อทำให้สถานะเป็นมาตรฐาน
3. ลงทะเบียนใน `src/lib/cloudAgent/registry.ts` ภายใต้ `providerId` ที่คงที่
4. ขยาย literal union ของ `providerId` ใน `src/lib/cloudAgent/types.ts`
   (`CloudAgentTask.providerId` และ `CreateCloudAgentTaskSchema`)
5. เพิ่มผู้ให้บริการลงใน `src/shared/constants/providers.ts` หากต้องใช้เรคคอร์ดการเชื่อมต่อ
   ผู้ให้บริการที่ใช้ OAuth ยังต้องมี `src/lib/oauth/providers/` ด้วย
6. เพิ่มการทดสอบภายใต้ `tests/unit/cloud-agent-*.test.ts`
7. อัปเดตเอกสารนี้และค่าคงที่ `CLOUD_AGENTS` ของแดชบอร์ด

## การกำหนดค่า

| ตัวแปรสภาพแวดล้อม | วัตถุประสงค์                                                              |
| ----------------- | ------------------------------------------------------------------------- |
| `DATA_DIR`        | ตำแหน่งของฐานข้อมูล SQLite ที่เก็บ `cloud_agent_tasks`                    |
| `JWT_SECRET`      | จำเป็นสำหรับการยืนยันตัวตนเพื่อการจัดการบนปลายทางของงาน                   |
| `API_KEY_SECRET`  | จำเป็นสำหรับเข้ารหัสข้อมูลประจำตัวในการเชื่อมต่อกับผู้ให้บริการขณะจัดเก็บ |

ปัจจุบันไม่มีตัวแปรสภาพแวดล้อมเฉพาะสำหรับ Cloud-Agent — ข้อมูลลับทั้งหมดจัดเก็บอยู่ใน
ตาราง `provider_connections`
