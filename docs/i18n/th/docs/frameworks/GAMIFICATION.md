OmniRoute มีเลเยอร์เกมมิฟิเคชันแบบ local-first ที่มอบรางวัลให้ผู้ใช้จากการ
มีส่วนร่วมกับแพลตฟอร์ม เช่น การส่งคำขอ การสลับผู้ให้บริการ การสร้าง
คอมโบ การแบ่งปันโทเค็น และการมีส่วนร่วมกับชุมชน สถานะทั้งหมดจัดเก็บอยู่ใน
SQLite ส่วนการเชื่อมโยงกับเซิร์ฟเวอร์ชุมชนเป็นแบบเลือกรับและใช้การพุชข้อมูล

ระบบได้รับการออกแบบให้มี **เวลาแฝงเป็นศูนย์บนเส้นทางการทำงานหลัก** — อีเวนต์เกมมิฟิเคชัน
จะถูกส่งแบบ fire-and-forget จากไปป์ไลน์คำขอ และจะไม่ขัดขวาง
การตอบกลับของ LLM

## ภาพรวม

### วัตถุประสงค์

เพิ่มการมีส่วนร่วมและการรักษาผู้ใช้ไว้ ด้วยการแสดงความคืบหน้าที่มองเห็นได้ (XP,
เลเวล, เหรียญตรา) การยืนยันทางสังคม (ลีดเดอร์บอร์ด) และสิ่งจูงใจทางเศรษฐกิจ (การแบ่งปันโทเค็น,
รางวัลจากการเชิญ)

### ขอบเขต

| ฟีเจอร์          | คำอธิบาย                                                                        |
| ---------------- | ------------------------------------------------------------------------------- |
| XP และเลเวล      | รับ XP จากแต่ละการกระทำ และเลื่อนเลเวลตามเส้นโค้งพหุนาม                         |
| เหรียญตรา        | ความสำเร็จมากกว่า 20 รายการใน 5 หมวดหมู่ พร้อมระดับความหายาก 4 ระดับ            |
| สตรีค            | ติดตามการใช้งานประจำวัน พร้อมสตรีคปัจจุบัน/ยาวนานที่สุด                         |
| ลีดเดอร์บอร์ด    | ขอบเขตแบบทั่วโลก รายสัปดาห์ รายเดือน การแบ่งปันโทเค็น และการมีส่วนร่วม          |
| การแบ่งปันโทเค็น | โอนเครดิตระหว่างผู้ใช้ผ่านบัญชีแยกประเภทแบบลงรายการคู่                          |
| การเชิญและแลกรับ | โค้ดแนะนำที่จัดเก็บในรูปแบบแฮช SHA-256                                          |
| เซิร์ฟเวอร์ชุมชน | เชื่อมโยงกับอินสแตนซ์ OmniRoute ภายนอก                                          |
| การป้องกันการโกง | การคำนวณคะแนนฝั่งเซิร์ฟเวอร์ การจำกัดอัตรา และการตรวจจับความผิดปกติด้วย z-score |

### หลักการออกแบบ

1. **Local-first** — สถานะทั้งหมดอยู่ใน SQLite โดยไม่จำเป็นต้องใช้บริการภายนอก
2. **ไม่ปิดกั้นการทำงาน** — อีเวนต์ทำงานแบบ fire-and-forget เส้นทางการตอบกลับของ LLM
   จะไม่ล่าช้าจากตรรกะเกมมิฟิเคชัน
3. **เซิร์ฟเวอร์เป็นผู้กำหนด** — XP จะคำนวณเฉพาะฝั่งเซิร์ฟเวอร์เท่านั้น ไคลเอนต์ไม่สามารถ
   เพิ่มคะแนนเกินจริงได้
4. **เคารพความเป็นส่วนตัว** — การเข้าร่วมลีดเดอร์บอร์ดเป็นแบบเลือกรับ ผู้ใช้สามารถ
   ซ่อนโปรไฟล์ของตนได้
5. **พร้อมสำหรับการเชื่อมโยง** — เซิร์ฟเวอร์ชุมชนสามารถพุชคะแนนผ่าน API ที่มีการลงนาม
   โดยการซิงค์จะเป็นการเขียนทับ ไม่ใช่การบวกเพิ่ม

## สถาปัตยกรรม

### โฟลว์ระดับสูง

```
คำขอจากไคลเอนต์
  → /v1/chat/completions
    → handleChatCore()                      [open-sse/handlers/chatCore.ts]
      → ... (ไปป์ไลน์ที่มีอยู่) ...
      → ส่งการตอบกลับจากต้นทางไปยังไคลเอนต์
      → setImmediate (fire-and-forget):
        → emitGamificationEvent()           [src/lib/gamification/events.ts]
          → awardXp()                       [src/lib/gamification/xp.ts]
          → updateStreak()                  [src/lib/gamification/streaks.ts]
          → evaluateBadges()                [src/lib/gamification/badges.ts]
          → updateLeaderboard()             [src/lib/gamification/leaderboard.ts]
          → checkAnomalies()                [src/lib/gamification/antiCheat.ts]
```

ตัวปล่อยอีเวนต์เป็นจุดผสานรวมเพียงจุดเดียว `chatCore.ts` เรียก
`emitGamificationEvent()` หลังจากส่งการตอบกลับแล้ว จากนั้นโมดูลอีเวนต์จะกระจายงาน
ไปยังระบบย่อยสำหรับ XP, สตรีค, เหรียญตรา, ลีดเดอร์บอร์ด และการป้องกันการโกง

## ระบบ XP / เลเวล

**ไฟล์:** `src/lib/gamification/xp.ts`

### เส้นโค้งเลเวล

XP ที่ต้องใช้เพื่อไปถึงเลเวล `n` เป็นไปตามเส้นโค้งพหุนาม:

```
xp_for_level(n) = floor(100 * n^1.5)
```

| เลเวล | XP สำหรับเลเวลถัดไป | XP สะสม   | ฉายา         |
| ----- | ------------------- | --------- | ------------ |
| 1     | 100                 | 100       | ผู้เริ่มต้น  |
| 5     | 1,118               | 2,415     | ผู้เริ่มต้น  |
| 10    | 3,162               | 10,523    | นักสำรวจ     |
| 25    | 12,500              | 86,024    | ผู้เชี่ยวชาญ |
| 50    | 35,355              | 345,529   | ปรมาจารย์    |
| 75    | 64,952              | 948,683   | ตำนาน        |
| 100   | 100,000             | 2,050,000 | ตำนาน        |

### ฉายา

| ช่วงเลเวล | ฉายา         |
| --------- | ------------ |
| 1 – 9     | ผู้เริ่มต้น  |

### ลำดับการมอบรางวัล

```typescript
export async function awardXp(
  apiKeyId: string,
  action: XpAction,
  metadata?: Record<string, unknown>
): Promise<{ xp: number; level: number; title: string; levelUp: boolean }>;
```

1. ค้นหา `XP_REWARDS[action]` เพื่อรับจำนวน XP
2. ส่งผ่าน `checkRateLimit()` (ป้องกันการโกง: สูงสุด 1000 XP/นาทีต่อคีย์)
3. เปิดทรานแซกชัน:
   - อ่านแถว `user_levels` ปัจจุบัน
   - เพิ่ม XP และคำนวณเลเวลใหม่ผ่าน `levelFromXp(totalXp)`
   - หากเลเวลเปลี่ยนแปลง ให้ตั้งค่า `levelUp = true`
   - อัปเดตแถว `user_levels`
   - แทรกข้อมูลลงใน `xp_audit_log`
4. ส่งคืนผลลัพธ์ โดยผู้เรียกจะเป็นผู้จัดการการแจ้งเตือน

### ตัวช่วย: `levelFromXp(totalXp)`

วนซ้ำตั้งแต่เลเวล 1..100 พร้อมรวม `xp_for_level(n)` จนกว่า XP สะสม
จะเกิน `totalXp` ส่งคืนเลเวลสูงสุดที่ผ่านเกณฑ์
การดำเนินการนี้มีความซับซ้อน O(100) ซึ่งยอมรับได้เนื่องจากเลเวลจำกัดสูงสุดที่ 100

### ลำดับการประเมิน

```
emitGamificationEvent(event)
  → evaluateBadges(apiKeyId, event)
    → getBadgeDefinitions()           # คำจำกัดความทั้งหมด
    → getUserBadges(apiKeyId)         # ได้รับแล้ว (ข้าม)
    → สำหรับเหรียญตราแต่ละรายการที่ยังไม่ได้รับ:
       → matchesCriteria(badge, event, userState)
       → หากตรงตามเกณฑ์: awardBadge(apiKeyId, badgeId)
         → ส่งคืนเพย์โหลดการแจ้งเตือน
```

การประเมินเป็นแบบ **ขับเคลื่อนด้วยเหตุการณ์** โดยจะทำงานหลังจากทุกเหตุการณ์เกมมิฟิเคชัน แต่

ช่วยให้การประเมินทำงานได้รวดเร็ว (< 5ms สำหรับเหตุการณ์ส่วนใหญ่)

## ตัวติดตามสตรีค

**ไฟล์:** `src/lib/gamification/streaks.ts`

### โมเดลข้อมูล

สตรีคจะถูกจัดเก็บไว้ในตาราง `key_value` (ตารางยูทิลิตีที่ใช้ร่วมกัน) ภายใต้คีย์ที่มีเนมสเปซ:

| คีย์                          | ค่า                              | คำอธิบาย                 |
| ----------------------------- | -------------------------------- | ------------------------ |
| `gamification:streak:{keyId}` | `{current},{longest},{lastDate}` | ข้อมูลสตรีคที่ใช้งานอยู่ |

### ตรรกะ

```typescript
export async function updateStreak(
  apiKeyId: string
): Promise<{ current: number; longest: number; milestone: boolean }>;
```

1. อ่านระเบียนสตรีคจาก `key_value`
2. แยกวิเคราะห์ `{current}`, `{longest}`, `{lastDate}` (สตริงวันที่รูปแบบ ISO)
3. หาก `lastDate === today` — ไม่มีการเปลี่ยนแปลง (นับไปแล้วในวันนี้)
4. หาก `lastDate === yesterday` — เพิ่มค่า `current` และอัปเดต `longest` หากจำเป็น
5. หาก `lastDate < yesterday` — รีเซ็ต `current = 1` (สตรีคขาด)
6. เขียนระเบียนที่อัปเดตแล้ว
7. ตรวจสอบหมุดหมาย: 7, 14, 30, 60, 90, 180, 365 วัน หากผ่านหมุดหมาย ให้ตั้งค่า
   `milestone = true` (ผู้เรียกใช้จะมอบ XP และตรวจสอบแบดจ์)

### กรณีพิเศษ

- **เขตเวลา**: สตรีคใช้วันที่ UTC (`new Date().toISOString().slice(0, 10)`)
  ซึ่งเป็นพฤติกรรมที่ตั้งใจไว้ — การใช้เขตเวลามาตรฐานเดียวช่วยป้องกันการเอาเปรียบด้วย
  การสลับเขตเวลา
- **ผู้ใช้ใหม่**: ยังไม่มีระเบียนสตรีค คำขอแรกจะสร้างระเบียนโดยกำหนดค่า
  `current=1, longest=1, lastDate=today`
- **คำขอหลายครั้งต่อวัน**: เฉพาะคำขอแรกของวันตามเวลา UTC เท่านั้น
  ที่จะเพิ่มค่าสตรีค

   ของช่วงเวลาใหม่จะทริกเกอร์การหมุนเวียน

### บัญชีแยกประเภทแบบลงบัญชีคู่

การโอนแต่ละครั้งจะสร้างสองแถวใน `token_ledger`:

| เครดิต | ผู้รับ        | ผู้ส่ง      | -จำนวน   |

เดี๋ยวก่อน — ข้อตกลงที่ใช้คือ:

| แถว | `from_key_id` | `to_key_id` | `amount` | ความหมาย             |
| --- | ------------- | ----------- | -------- | -------------------- |
| ส่ง | ผู้ส่ง        | ผู้รับ      | +จำนวน   | เงินไหลออกจากผู้ส่ง  |
| รับ | ผู้รับ        | ผู้ส่ง      | +จำนวน   | เงินไหลเข้าสู่ผู้รับ |

ยอดคงเหลือคำนวณดังนี้:

```sql
SELECT
  COALESCE(SUM(CASE WHEN to_key_id = ? THEN amount ELSE 0 END), 0)
  - COALESCE(SUM(CASE WHEN from_key_id = ? THEN amount ELSE 0 END), 0)
  AS balance
FROM token_ledger
WHERE from_key_id = ? OR to_key_id = ?
```

### ขั้นตอนการโอน

```typescript
export async function transferTokens(
  fromKeyId: string,
  toKeyId: string,
  amount: number,
  idempotencyKey: string
): Promise<{ success: boolean; balance: number }>;
```

1. **ตรวจสอบความถูกต้อง**: `amount > 0`, `fromKeyId !== toKeyId`
2. **การทำงานแบบ Idempotent**: ตรวจสอบว่า `idempotency_key` มีอยู่ในบัญชีแยกประเภทแล้วหรือไม่
   หากมี ให้ส่งคืนผลลัพธ์ที่แคชไว้
3. **ธุรกรรม** (ธุรกรรม SQLite รายการเดียว):
   a. คำนวณยอดคงเหลือของผู้ส่ง
   b. หาก `balance < amount` ให้ยกเลิก (ยอดเงินไม่เพียงพอ)
   c. เพิ่มแถวการส่ง (`from=sender,`

### การจำกัดอัตรา

- สูงสุด 10 การโอนต่อนาทีต่อ API key
- สูงสุด 10,000 โทเค็นต่อการโอนหนึ่งครั้ง
- สูงสุด 100,000 โทเค็นที่โอนต่อวันต่อ API key

## โทเค็นคำเชิญและการแลกใช้

**ไฟล์:** `src/lib/gamification/invites.ts`

### รูปแบบรหัส

- **รหัส**: อักขระตัวอักษรและตัวเลข 8 ตัว (เช่น `A3K9-X7M2`) อ่านได้โดยมนุษย์
  และแสดงให้ผู้ใช้เห็น
- **โทเค็น**: โทเค็นสุ่มขนาด 32 ไบต์ จัดเก็บเป็นแฮช SHA-256 ใช้สำหรับ
  การแลกใช้ผ่านโปรแกรม (เช่น ลิงก์ URL)

### การจัดเก็บ

| คอลัมน์      | ค่า                          |
| ------------ | ---------------------------- |
| `code`       | `A3K9X7M2` (ไม่ซ้ำ, มีดัชนี) |
| `token_hash` | SHA-256(raw_token)           |

โทเค็นดิบจะถูกส่งคืนให้ผู้ใช้เพียงครั้งเดียวในขณะที่สร้าง OmniRoute
จะไม่จัดเก็บหรือแสดงโทเค็นดังกล่าวอีก โดยจะเก็บไว้เฉพาะแฮชเท่านั้น

### การป้องกันการแนะนำตนเอง

เมื่อผู้ใช้แลกใช้รหัส ระบบจะตรวจสอบว่า:

1. รหัสดังกล่าวเป็นของ `api_key_id` อื่น
2. ผู้ใช้ที่แลกใช้ไม่เคยแลกใช้รหัสใดๆ จากผู้แนะนำคนเดียวกันมาก่อน
   (เชื่อมโยงข้อมูลจาก `invite_tokens` และบันทึกการแลกใช้)

หากการตรวจสอบข้อใดข้อหนึ่งล้มเหลว ระบบจะปฏิเสธการแลกใช้พร้อมข้อความแสดงข้อผิดพลาดที่ชัดเจน

### วันหมดอายุและขีดจำกัด

- ค่าเริ่มต้นของ `max_uses`: 10 (กำหนดค่าได้ขณะสร้าง)
- ค่าเริ่มต้นของ `expires_at`: 30 วันนับจากเวลาที่สร้าง
- รหัสที่หมดอายุหรือถูกใช้จนครบจำนวนแล้วจะส่งคืน HTTP 410 Gone

## การเชื่อมโยงเซิร์ฟเวอร์ชุมชน

**ไฟล์:** `src/lib/gamification/servers.ts`

### การเชื่อมต่อ

เซิร์ฟเวอร์ชุมชนจะได้รับการลงทะเบียนผ่านโทเค็นคำเชิญที่ออกโดยเซิร์ฟเวอร์ระยะไกล อินสแตนซ์ภายในจะดำเนินการดังนี้:

1. รับโทเค็นคำเชิญ (เช่น นำมาวางในแดชบอร์ด)
2. เรียก `POST /api/gamification/federation/leaderboard` บนเซิร์ฟเวอร์ระยะไกลเพื่อตรวจสอบโทเค็นและดึงลีดเดอร์บอร์ดปัจจุบัน
3. จัดเก็บระเบียนเซิร์ฟเวอร์โดยกำหนด `status: connected`

### รูปแบบการซิงค์

การเชื่อมโยงใช้ **การซิงค์แบบเขียนทับ** ไม่ใช่แบบเพิ่มค่า:

```
อินสแตนซ์ภายใน                 เซิร์ฟเวอร์ชุมชน
     │                              │
     ├── ส่งคะแนน ─────────────────►│  POST /federation/score
     │   { api_key_id, score }      │  (เซิร์ฟเวอร์ตรวจสอบแฮชของโทเค็น)
     │                              │
     ├── ดึงลีดเดอร์บอร์ด ─────────►│  GET /federation/leaderboard
     │◄── รายการ top-N ─────────────┤  (เขียนทับแคชภายใน)
     │                              │
     └── ตรวจสอบสถานะ ─────────────►│  GET /federation/health
         (ทุก 60 วินาที, หมดเวลาที่ 5 วินาที) │
```

### การยืนยันตัวตน

คำขอสำหรับการเชื่อมโยงประกอบด้วย:

```
Authorization: Bearer <raw_token>
X-Federation-Version: 1
```

เซิร์ฟเวอร์ระยะไกลจะแฮชโทเค็นและค้นหาแถว `community_servers` ที่ตรงกัน วิธีนี้ช่วยหลีกเลี่ยงการส่งแฮชที่จัดเก็บไว้

### การเฝ้าติดตามสถานะ

ระเบียนเซิร์ฟเวอร์แต่ละรายการจะติดตามข้อมูลต่อไปนี้:

| ฟิลด์       | คำอธิบาย                                     |
| ----------- | -------------------------------------------- |
| `status`    | `connected`, `degraded`, `unreachable`       |
| `last_sync` | การประทับเวลา ISO ของการซิงค์ที่สำเร็จล่าสุด |
| `failures`  | จำนวนครั้งที่การตรวจสอบสถานะล้มเหลวติดต่อกัน |

หลังจากล้มเหลวติดต่อกัน 5 ครั้ง สถานะจะเปลี่ยนเป็น `unreachable` และการซิงค์จะหยุดชั่วคราวจนกว่าการตรวจสอบสถานะแบบดำเนินการด้วยตนเองจะสำเร็จ

## การป้องกันการโกง

**ไฟล์:** `src/lib/gamification/antiCheat.ts`

### การคำนวณคะแนนฝั่งเซิร์ฟเวอร์

การคำนวณ XP ทั้งหมดเกิดขึ้นใน `src/lib/gamification/xp.ts` ไคลเอนต์จะไม่ส่งคะแนน แต่จะส่งการดำเนินการ จากนั้นเซิร์ฟเวอร์จะคำนวณ XP คอลัมน์ `leaderboard.score` สามารถเขียนได้โดยโค้ดฝั่งเซิร์ฟเวอร์เท่านั้น

### การจำกัดอัตรา

| ขีดจำกัด                 | ค่า     | ขอบเขต      |
| ------------------------ | ------- | ----------- |
| XP สูงสุดต่อนาที         | 1,000   | ต่อ API key |
| จำนวนการโอนสูงสุดต่อนาที | 10      | ต่อ API key |
| จำนวนสูงสุดต่อการโอน     | 10,000  | ต่อการโอน   |
| จำนวนการโอนสูงสุดต่อวัน  | 100,000 | ต่อ API key |

การจำกัดอัตราใช้หน้าต่างเลื่อนในหน่วยความจำ (รูปแบบเดียวกับ `RateLimitManager` ใน `open-sse/services/`) และจะใช้ตัวนับที่จัดเก็บใน SQLite เป็นทางเลือกสำรอง หากโปรเซสรีสตาร์ต

### การตรวจจับความผิดปกติด้วย Z-Score

สำหรับ API key แต่ละรายการ ระบบจะรักษาหน้าต่างข้อมูลแบบต่อเนื่องย้อนหลัง 7 วันของ XP ที่ได้รับต่อชั่วโมง ทุกครั้งที่มอบ XP:

1. คำนวณอัตรา XP ต่อชั่วโมงปัจจุบันของผู้ใช้
2. คำนวณค่าเฉลี่ยและส่วนเบี่ยงเบนมาตรฐานของประชากร
3. คำนวณ `z = (user_rate - mean) / stddev`
4. หาก `z > 3.0` (3 ส่วนเบี่ยงเบนมาตรฐาน) ให้ทำเครื่องหมายว่าเป็นความผิดปกติ

ความผิดปกติจะถูกบันทึกลงใน `xp_audit_log` โดยกำหนด `action = 'anomaly_detected'` และแสดงบนแดชบอร์ดผู้ดูแลระบบ

### ร่องรอยการตรวจสอบ

การมอบ XP การโอน การได้รับเหรียญตรา และการตรวจจับความผิดปกติทุกรายการจะถูกบันทึกลงใน `xp_audit_log` พร้อมข้อมูลต่อไปนี้:

| ฟิลด์        | คำอธิบาย                                              |
| ------------ | ----------------------------------------------------- |
| `api_key_id` | ผู้ดำเนินการ                                          |
| `action`     | เหตุการณ์ที่เกิดขึ้น (xp_award, transfer, anomaly, …) |
| `xp_awarded` | จำนวน (0 สำหรับเหตุการณ์ที่ไม่เกี่ยวกับ XP)           |
| `metadata`   | JSON พร้อมบริบท (ประเภทการดำเนินการ เป้าหมาย …)       |
| `created_at` | เวลา (ISO 8601)                                       |

ผู้ดูแลระบบสามารถสืบค้นร่องรอยการตรวจสอบทั้งหมดผ่าน `GET /api/gamification/anomalies`

- แถบความคืบหน้า XP พร้อมเลเวลปัจจุบันและเกณฑ์สำหรับเลเวลถัดไป
- แสดงตราฉายาอย่างโดดเด่น
- แกลเลอรีเหรียญตรา — เหรียญตราที่ได้รับพร้อมวันที่ได้รับ ส่วนเหรียญตราที่ยังไม่ได้รับจะแสดงเป็นสีเทา
  (เหรียญตราที่ซ่อนไว้จะแสดง "???" จนกว่าจะได้รับ)
- ตัวนับสถิติต่อเนื่องพร้อมไอคอนเปลวไฟ และปฏิทินสถิติต่อเนื่อง (30 วันที่ผ่านมา)
- แผนภูมิประวัติ XP (XP รายวันในช่วง 30 วันที่ผ่านมา)

### `/dashboard/tokens`

- ยอดคงเหลือโทเค็น (แสดงอย่างโดดเด่นที่ด้านบนของหน้า)
- แบบฟอร์มโอน: ผู้รับ จำนวน และกล่องโต้ตอบยืนยัน
- ตารางประวัติการโอนพร้อมตัวกรอง (ส่งแล้ว/ได้รับ/ทั้งหมด)
- ส่วนคำเชิญ: รหัสที่ใช้งานอยู่ สร้างใหม่ และลิงก์สำหรับแชร์
- เซิร์ฟเวอร์ชุมชน: รายการพร้อมสถานะความพร้อมใช้งาน และตัวเลือกเชื่อมต่อ/ยกเลิกการเชื่อมต่อ

### `/dashboard/gamification/admin`

- รายการความผิดปกติพร้อมระดับความรุนแรง ผู้ใช้ เวลาประทับ และค่า z-score
- ตัวดูบันทึกการตรวจสอบพร้อมตัวกรอง (ประเภทการดำเนินการ ผู้ใช้ และช่วงวันที่)
- สถิติระบบ: XP ทั้งหมดที่มอบให้ ผู้ใช้ที่ใช้งานอยู่ และอัตราการได้รับเหรียญตรา
- ภาพรวมความพร้อมใช้งานของเซิร์ฟเวอร์แบบสหพันธ์

## การผสานรวมกับไปป์ไลน์

### จุดผสานรวม

ระบบเกมมิฟิเคชันเชื่อมต่อเข้ากับไปป์ไลน์คำขอ ณ จุดเดียวใน
`open-sse/handlers/chatCore.ts`:

```typescript
// หลังจากส่งการตอบกลับไปยังไคลเอนต์แล้ว:
setImmediate(() => {
  emitGamificationEvent({
    type: "request.completed",
    apiKeyId,
    metadata: {
      provider: selectedProvider,
      model: selectedModel,
      comboId: resolvedCombo?.id,
      compressionUsed: compressionStats?.applied,
      skillUsed: skillExecution?.name,
    },
  }).catch(() => {
    // เรียกใช้แล้วไม่รอผล: บันทึกข้อผิดพลาด แต่ไม่ส่งต่อไปยังไคลเอนต์
  });
});
```

### ประเภทอีเวนต์

| ประเภทอีเวนต์       | เวลาที่ปล่อยอีเวนต์                               |
| ------------------- | ------------------------------------------------- |
| `request.completed` | ส่งการตอบกลับจาก LLM สำเร็จแล้ว                   |
| `provider.switch`   | มีการเปลี่ยนผู้ให้บริการ (นับรวมการสำรองของคอมโบ) |
| `combo.created`     | บันทึกการกำหนดค่าคอมโบใหม่แล้ว                    |
| `combo.used`        | เรียกใช้เป้าหมายคอมโบสำเร็จ                       |
| `badge.earned`      | การประเมินเหรียญตราพบเงื่อนไขที่ตรงกัน            |
| `streak.milestone`  | ผ่านเกณฑ์สถิติต่อเนื่อง                           |
| `transfer.sent`     | โอนโทเค็นเสร็จสมบูรณ์                             |
| `referral.redeemed` | แลกรหัสเชิญสำเร็จแล้ว                             |
| `compression.used`  | ใช้การบีบอัดพรอมต์แล้ว                            |
| `skill.executed`    | ดำเนินการทักษะเสร็จสมบูรณ์                        |
| `model.first_use`   | โมเดลไม่เคยถูกใช้งานในช่วง 7 วันที่ผ่านมา         |

### การรับประกันว่าจะไม่บล็อก

รูปแบบ `setImmediate` + `.catch(() => {})` ทำให้มั่นใจว่า:

1. การตอบกลับถูกส่งอย่างสมบูรณ์ก่อนที่ระบบเกมมิฟิเคชันจะเริ่มทำงาน
2. ข้อผิดพลาดของระบบเกมมิฟิเคชันจะไม่ปรากฏต่อไคลเอนต์
3. การประมวลผลอีเวนต์จะทำงานในไมโครทาสก์ถัดไป ไม่ใช่แบบอินไลน์

## ความปลอดภัย

### แบบจำลองภัยคุกคาม

| ภัยคุกคาม                         | มาตรการป้องกัน                                                         |
| --------------------------------- | ---------------------------------------------------------------------- |
| การเพิ่มคะแนนอย่างไม่ถูกต้อง      | คำนวณ XP ฝั่งเซิร์ฟเวอร์เท่านั้น ไคลเอนต์ส่งการกระทำ ไม่ใช่คะแนน       |
| การโจมตีแบบส่งคำขอซ้ำ             | ใช้คีย์ Idempotency ในการโอน และขจัดรายการซ้ำในบันทึกการตรวจสอบ        |
| การฉ้อโกงในการโอน                 | บัญชีแยกประเภทแบบบันทึกคู่ ธุรกรรมแบบอะตอมมิก และการจำกัดอัตรา         |
| การแนะนำตนเอง                     | ตรวจสอบ `api_key_id` ไขว้เมื่อแลกรับสิทธิ์                             |
| การบิดเบือนลีดเดอร์บอร์ด          | ตรวจจับความผิดปกติด้วย Z-score และแดชบอร์ดความผิดปกติสำหรับผู้ดูแลระบบ |
| การขโมยโทเค็นสหพันธ์              | จัดเก็บในรูปแบบแฮช SHA-256 และแสดงโทเค็นดิบเพียงครั้งเดียว             |
| การสุ่มเดารหัสเชิญแบบ Brute Force | จำกัดอัตราที่เอนด์พอยต์แลกรับสิทธิ์ และใช้เอนโทรปี 8 อักขระ            |
| XSS ในชื่อที่แสดง                 | ทำความสะอาดชื่อที่แสดง และ Escape รายการในลีดเดอร์บอร์ด                |
| การโจมตีแบบจับเวลาต่อแฮช          | ใช้ `crypto.timingSafeEqual` เพื่อเปรียบเทียบแฮชของโทเค็น              |

### ข้อกำหนดด้านการยืนยันตัวตน

- **สาธารณะ** (ไม่ต้องยืนยันตัวตน): `GET /leaderboard`, `GET /stream` (ลีดเดอร์บอร์ดแบบอ่านอย่างเดียว)
- **ต้องใช้คีย์ API**: การดำเนินการเขียนทั้งหมด โปรไฟล์ การโอน และคำเชิญ
- **เฉพาะผู้ดูแลระบบ**: แดชบอร์ดความผิดปกติและตัวดูบันทึกการตรวจสอบ
- **สหพันธ์**: ใช้เส้นทางการยืนยันตัวตนแยกต่างหาก โดยใช้โทเค็นดิบในเฮดเดอร์ `Authorization`
  และตรวจสอบกับแฮช SHA-256 ที่จัดเก็บไว้

## ข้อพิจารณาในอนาคต

- **กิจกรรมตามฤดูกาล**: ชุดเหรียญตราและฤดูกาลของกระดานผู้นำที่มีระยะเวลาจำกัด
- **กระดานผู้นำแบบทีม**: จัดกลุ่มผู้ใช้ตามองค์กรหรือคอมโบ
- **ตัวคูณ XP**: เพิ่ม XP ในช่วงระยะเวลาส่งเสริมการขาย
- **การแชร์ความสำเร็จ**: สร้างการ์ดเหรียญตราที่แชร์ได้ (รูปภาพ OpenGraph)
- **การแจ้งเตือนแบบพุชบนมือถือ**: การแจ้งเตือนผ่าน webhook สำหรับกิจกรรมเกี่ยวกับเหรียญตรา/ระดับ
- **API กระดานผู้นำ**: API สาธารณะสำหรับการผสานรวมกับบุคคลที่สาม
