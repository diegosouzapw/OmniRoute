AgentBridge คือพร็อกซี MITM (Man-in-the-Middle) ของ OmniRoute ที่ดักจับทราฟฟิก HTTPS จากเอเจนต์ AI ใน IDE และเปลี่ยนเส้นทางผ่านเอนจินการกำหนดเส้นทางแบบรวมศูนย์ของ OmniRoute โดยรองรับ **เอเจนต์ IDE 10 รายการ** ได้แก่ Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code และ Trae (อยู่ระหว่างการตรวจสอบ) ทำให้ OmniRoute เป็นพร็อกซี MITM สำหรับผู้ช่วยเขียนโค้ด AI ที่ครอบคลุมมากที่สุดในตลาด

**ตำแหน่งแดชบอร์ด:** `/dashboard/tools/agent-bridge`
**กลุ่มในแถบด้านข้าง:** เครื่องมือ (ถัดจาก Cloud Agents)
**ดูเพิ่มเติม:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — ตรวจสอบทราฟฟิกที่ถูกดักจับทั้งหมดแบบเรียลไทม์; `docs/security/MITM-TPROXY-DECRYPT.md` (git; ไม่ได้คอมไพล์ไว้ใน `/docs`) — โหมดจับทราฟฟิกแบบถอดรหัสโปร่งใสด้วย Linux TPROXY ซึ่งควบคุมผ่านเส้นทาง `/api/tools/agent-bridge/tproxy`

## §1 ภาพรวม

### AgentBridge คืออะไร?

เมื่อเอเจนต์ IDE (เช่น GitHub Copilot, Cursor, Claude Code) เรียกใช้ API เอเจนต์จะเชื่อมต่อโดยตรงกับผู้ให้บริการ AI ต้นทาง (OpenAI, Anthropic ฯลฯ) AgentBridge จะดักจับการเชื่อมต่อนั้นอย่างโปร่งใสที่ระดับ TLS — โดยไม่ต้องเปลี่ยนแปลงการกำหนดค่าใดๆ ของเอเจนต์ — และเขียนคำขอใหม่เพื่อส่งผ่าน OmniRoute

ซึ่งหมายความว่าคุณสามารถ:

- **เปลี่ยนเส้นทางเอเจนต์ใดๆ ไปยังผู้ให้บริการใดก็ได้**: Copilot กำลังสื่อสารกับ OpenAI อยู่หรือไม่? เปลี่ยนเส้นทางไปยัง Anthropic Claude, Gemini หรือผู้ให้บริการใดๆ จากทั้งหมด 352 รายของ OmniRoute
- **ใช้การแมปโมเดล**: `gemini-3-flash` → `claude-sonnet-4.7` อย่างโปร่งใสที่ระดับแฮนด์เลอร์
- **สังเกตทราฟฟิกทั้งหมดของเอเจนต์**: ทุกคำขอที่ถูกดักจับจะถูกเผยแพร่ไปยัง [Traffic Inspector](./TRAFFIC_INSPECTOR.md)
- **ใช้ความสามารถด้านความยืดหยุ่นของ OmniRoute**: การกำหนดเส้นทางแบบผสมผสาน ตัวตัดวงจร กลไกสำรอง และการติดตามต้นทุน สามารถใช้กับทราฟฟิกของเอเจนต์ IDE ได้เช่นกัน

## §2 สถาปัตยกรรม

### 2.1 ภาพรวมองค์ประกอบ

```
เอเจนต์ IDE (VS Code / Cursor / อื่นๆ)
    │  HTTPS (พอร์ต 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← เปลี่ยนเส้นทาง DNS
    │
    ▼
src/mitm/server.cjs  (พอร์ต 443, โปรเซสลูก CJS)
    │  ระบุเป้าหมายจาก SNI ของส่วนหัว Host
    │  สร้างใบรับรอง TLS สำหรับแต่ละ SNI ซึ่งลงนามโดย CA ของ AgentBridge
    ├── ตรงกับรายการข้ามหรือไม่? → ส่งผ่าน TCP (ไม่ถอดรหัส)
    ├── ตรงกับเป้าหมายหรือไม่? → fetch → เราเตอร์ OmniRoute (พอร์ต 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() กับเนื้อหาคำขอ/ส่วนหัว
    │               ├── TrafficBuffer.push() — เผยแพร่ไปยัง Traffic Inspector
    │               └── fetchRouter() → /v1/chat/completions
    └── ไม่ตรงหรือไม่? → ส่งผ่าน TCP (ไม่ถอดรหัส)
```

### 2.2 เซิร์ฟเวอร์ MITM (`src/mitm/server.cjs`)

เซิร์ฟเวอร์ MITM หลักทำงานเป็นโปรเซสลูก CJS ของ Node.js (เพื่อหลีกเลี่ยงการเขียนฐานโค้ด CJS ที่มีอยู่ใหม่) โดย:

- รับฟังบนพอร์ต 443 (ต้องใช้สิทธิ์พิเศษหรือ `authbind`/`setcap`)
- รับอุโมงค์ CONNECT จากระบบปฏิบัติการ (ผ่านการเปลี่ยนเส้นทาง DNS ด้วย `/etc/hosts`)
- สร้างใบรับรอง TLS สำหรับแต่ละ SNI ซึ่งลงนามโดย CA ของ AgentBridge (`DATA_DIR/mitm/ca.crt`)
- ระบุเอเจนต์เป้าหมายจากส่วนหัว Host ผ่านรีจิสทรี `targets/index.ts`
- ส่งต่อไปยังเลเยอร์ตัวจัดการ TypeScript ผ่าน HTTP ที่ `http://127.0.0.1:20128`

`TARGET_HOSTS` ถูกโหลดจาก `DATA_DIR/mitm/targets.json` (เขียนโดย `targets/index.ts` ขณะบูต) ทำให้อัปเดตแบบไดนามิกได้โดยไม่ต้องรีสตาร์ตเซิร์ฟเวอร์ CJS

> **โมเดล Root CA (#6684)** คำอธิบายข้างต้นเกี่ยวกับใบรับรองสำหรับแต่ละ SNI ที่ลงนามโดย CA
> คือโมเดล Root CA แบบคงอยู่ซึ่งเพิ่มเข้ามาใน #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs` โดยนำการเข้ารหัส CA/ใบรับรองปลายทางที่ได้รับการพิสูจน์แล้ว
> สำหรับ TPROXY ใน `src/mitm/tproxy/dynamicCert.ts` มาใช้ซ้ำ) — โมเดลนี้มาแทน
> ใบรับรองปลายทางแบบ self-signed คงที่เพียงใบเดียวรุ่นเก่า (`src/mitm/cert/generate.ts` ซึ่งยังคง
> จำกัดขอบเขตเฉพาะโฮสต์ antigravity) ที่ระบุด้วยคู่ `server.crt`/`server.key`
> บนดิสก์ **พฤติกรรมการย้ายระบบ**: การติดตั้งใหม่ (ไม่มี `server.crt` เดิม)
> จะได้รับโมเดล Root CA โดยอัตโนมัติ ส่วนการติดตั้งที่เชื่อถือใบรับรองปลายทางแบบคงที่รุ่นเก่าอยู่แล้ว
> จะยังคงใช้ใบรับรองดังกล่าวจนกว่าผู้ดูแลจะตั้งค่า `MITM_ROOT_CA_ENABLED=true`
> และรีสตาร์ตบริดจ์ (`src/mitm/cert/migration.ts` คือฟังก์ชันการตัดสินใจล้วน —
> CA ของ MITM ที่ได้รับความเชื่อถือและสามารถลงนามใบรับรองปลายทางสำหรับโฮสต์
> **ใดๆ** ได้นั้นมีอำนาจมากกว่าใบรับรองปลายทางแบบ fixed-SAN รุ่นเก่าอย่างมีนัยสำคัญ ดังนั้น
> การเปลี่ยนนี้จะไม่เกิดขึ้นโดยไม่มีการแจ้งเตือนสำหรับการติดตั้งที่ได้รับความเชื่อถืออยู่แล้ว) ใบรับรอง CA
> จะติดตั้งลงในช่อง trust store `omniroute-mitm.crt` เดียวกับที่ใบรับรองปลายทางรุ่นเก่าใช้
> (`cert/install.ts::installCaCert`) — ไม่จำเป็นต้องล้างรายการที่เชื่อถือซ้ำซ้อน

### 2.3 คลาสฐานของตัวจัดการ (`src/mitm/handlers/base.ts`)

ตัวจัดการเอเจนต์ทั้งหมดสืบทอดจาก `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // เมธอดช่วยเหลือแบบ protected: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

ตัวจัดการแต่ละตัวเรียก `hookBufferStart()` ก่อนพร็อกซี และเรียก `hookBufferUpdate()` เมื่อเสร็จสิ้น เมธอดเหล่านี้จะส่งรายการ `InterceptedRequest` ไปยัง `globalTrafficBuffer` (ดู [Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4)

### 2.4 รีจิสทรีเป้าหมาย (`src/mitm/targets/`)

แต่ละเอเจนต์มีไฟล์เป้าหมายแบบประกาศ:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

รีจิสทรี (`targets/index.ts`) ส่งออก `ALL_TARGETS` และสร้าง `DATA_DIR/mitm/targets.json` ขณะบูต

### 2.5 การส่งผ่านและรายการข้าม (`src/mitm/passthrough.ts`)

**รายการข้าม** (ตรวจสอบก่อน โดยมีลำดับความสำคัญเหนือการจับคู่เป้าหมาย):

- รูปแบบเริ่มต้น: โฮสต์ของธนาคาร, `.gov.`, ผู้ให้บริการ OAuth/SSO (Okta, Auth0) และอื่นๆ
- รูปแบบของผู้ใช้: จัดเก็บในตารางฐานข้อมูล `agent_bridge_bypass`
- โฮสต์ที่ถูกข้ามจะได้รับอุโมงค์ TCP แบบโปร่งใส — TLS จะ **ไม่มีวันถูกถอดรหัส**

**การส่งผ่านเริ่มต้น** (ไม่ตรงกับเป้าหมายและไม่อยู่ในรายการข้าม):

- จะได้รับอุโมงค์ TCP เช่นกัน — การเชื่อมต่อจะไม่ถูกตัด
- ป้องกันไม่ให้ AgentBridge รบกวนทราฟฟิก HTTPS ทั่วไปของระบบ

ลำดับความสำคัญในการกำหนดเส้นทาง:

```
รายการข้าม → การจับคู่เป้าหมาย → การส่งผ่าน
```

### 2.6 ใบรับรอง CA ต้นทาง (`src/mitm/upstreamTrust.ts`)

สำหรับสภาพแวดล้อมเครือข่ายองค์กรที่ใช้ CA แบบกำหนดเอง:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

เมื่อตั้งค่าแล้ว ระบบจะกำหนดค่า global dispatcher ของ `undici` ด้วยใบรับรอง CA เพิ่มเติม ทำให้ AgentBridge สามารถเข้าถึงผู้ให้บริการต้นทางผ่านพร็อกซีที่ยุติการเชื่อมต่อ TLS ขององค์กรได้

### 2.7 การปกปิดข้อมูลลับ (`src/mitm/maskSecrets.ts`)

ตัวสแกนแบบ clean-room ที่เป็นอิสระจะถูกใช้กับเนื้อหาคำขอและส่วนหัวข้อมูลรับรอง
**ก่อน** ที่ข้อมูลเหล่านั้นจะเข้าสู่บัฟเฟอร์ Traffic Inspector หรือบันทึกใดๆ โดยจะสแกนเชิงเส้นเพียงรอบเดียว:

- โทเค็นที่ขึ้นต้นด้วย `sk-` / `ak-` / `pk-` (รูปแบบ OpenAI/Anthropic)
- ข้อมูลรับรอง `Authorization: Bearer <token>` ตาม RFC 6750 โดยให้ความสำคัญกับโทเค็นทั้งชุด
- โทเค็นทึบแสงแบบทั่วไปที่มีความยาวมาก (≥40 อักขระ) รวมถึงรูปแบบที่มีจุดและมีการเติมอักขระ

`sanitizeHeaders()` จะแปลงชื่อส่วนหัวที่เก็บไว้ให้เป็นตัวพิมพ์เล็ก รวมค่าอาร์เรย์อย่างเป็นแบบแผน ตัดรายการปฏิเสธ
hop-by-hop/framing ที่ใช้ร่วมกันออก (รวมถึงการยืนยันตัวตนของพร็อกซี) ปกปิด `cookie` และ
`set-cookie` อย่างสมบูรณ์ และมอบหมายค่าข้อมูลรับรองให้ตัวสแกนจัดการ

### 3.2 เชื่อถือใบรับรอง

OS ต้องเชื่อถือใบรับรอง CA ของ AgentBridge ก่อนที่ IDE จะยอมรับการเชื่อมต่อ MITM

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

หรือใช้ปุ่ม "เชื่อถือใบรับรอง" ในแดชบอร์ด (เรียกใช้คำสั่งที่เหมาะสมกับ OS ของคุณ พร้อมพรอมต์ sudo หากจำเป็น)

#### IDE ที่ใช้ Electron จะไม่สนใจคลังใบรับรองที่เชื่อถือของ OS (`NODE_EXTRA_CA_CERTS`)

IDE บางตัว — โดยเฉพาะ **Antigravity IDE** และแอปอื่นๆ ที่พัฒนาต่อยอดจาก Electron / VS Code — มาพร้อมกับ
รันไทม์ Node.js ของตัวเอง ซึ่ง **ไม่ตรวจสอบคลังใบรับรองที่เชื่อถือของ OS** สำหรับ `fetch`/HTTPS
ขาออก การเชื่อถือ CA ในระดับ OS/NSS เพียงพอสำหรับ **แบ็กเอนด์** แบบเนทีฟของ IDE
(เช่น เซิร์ฟเวอร์ภาษาที่เขียนด้วย Go ซึ่งใช้ชุด CA ของ OS) แต่ **ฟรอนต์เอนด์ Electron** จะยังคง
เชื่อมต่อ TLS ไม่สำเร็จ — อาการที่ปรากฏคือแอปแสดงว่า _ออกจากระบบแล้ว_ หรือแสดง _"ข้อผิดพลาดในการเชื่อมต่อ"_
แม้ว่าบันทึก MITM จะแสดงว่าการเรียกบูตสแตรปของแบ็กเอนด์ส่งคืน `200` ก็ตาม จำเป็นต้องดำเนินการ
สองขั้นตอน และทั้งสองขั้นตอนมีความสำคัญ:

1. กำหนดให้รันไทม์ใช้ CA อย่างชัดเจน:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **เปิด IDE จากเชลล์นั้น** การเปิดจากไอคอนเดสก์ท็อป / Dock / เมนู Start
   จะ **ไม่** รับค่าที่ export จากเชลล์ และ `~/.config/environment.d/*.conf` จะมีผลหลังจาก
   เข้าสู่ระบบแบบกราฟิกใหม่เท่านั้น ก่อนอื่นให้ออกจาก IDE อย่างสมบูรณ์ — การล็อกแบบซิงเกิลตันของ Electron ทำให้การ
   เปิดครั้งที่สองเพียงแค่โฟกัสโปรเซสเดิม และสภาพแวดล้อมใหม่จะถูกละเว้น

ขั้นตอนการเชื่อถือในระดับ OS + NSS ข้างต้นยังคงจำเป็น (สแตกเครือข่าย Chromium ที่โฟลว์การยืนยันตัวตน
บางส่วนใช้งานจะอ่านคลัง NSS ของผู้ใช้แต่ละราย และมีการตรึงใบรับรองแบบคงที่ของตัวเองสำหรับ `*.googleapis.com` ซึ่ง
CA ที่เชื่อถือในเครื่องจะเขียนทับ) `NODE_EXTRA_CA_CERTS` ครอบคลุมพาธ `fetch` ของ Node เพิ่มเติมจากขั้นตอนดังกล่าว

### 3.3 การกำหนดเส้นทาง DNS

สำหรับแต่ละเอเจนต์ที่คุณต้องการดักรับ โฮสต์ API ของเอเจนต์นั้นต้องชี้ไปยัง `127.0.0.1` AgentBridge จะจัดการรายการใน `/etc/hosts` โดยอัตโนมัติเมื่อคุณสลับเปิดใช้ DNS สำหรับเอเจนต์ในตัวช่วยสร้างการตั้งค่า

ตัวอย่างรายการ `/etc/hosts` สำหรับ GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 การแมปโมเดล

ใช้ตารางการแมปโมเดลในการ์ดของแต่ละเอเจนต์เพื่อกำหนดการแมปต้นทาง → เป้าหมาย:

| โมเดลต้นทาง (โมเดลเนทีฟของเอเจนต์) | โมเดลเป้าหมาย (OmniRoute) |
| ---------------------------------- | ------------------------- |
| `gpt-4o`                           | `claude-sonnet-4.7`       |
| `*` (ไวลด์การ์ด)                   | `claude-haiku-4.7`        |

ไวลด์การ์ด `*` จะแมปโมเดลที่ไม่รู้จักทั้งหมดไปยังเป้าหมายที่ระบุ โดยจัดเก็บถาวรในตาราง `agent_bridge_mappings`

> **เคล็ดลับ — ค้นหา ID โมเดลจริงของเอเจนต์** IDE อาจส่งชื่อโมเดลที่แตกต่างจาก
> ป้ายกำกับใน UI และชื่อเหล่านั้นอาจเปลี่ยนแปลงระหว่างเวอร์ชันหลัก ตัวอย่างเช่น **Antigravity 2** ส่ง
> `gemini-3.1-pro-low`, `gemini-pro-agent` และ `gemini-3.1-flash-lite` ผ่านเครือข่าย — ไม่ใช่
> `gemini-2.5-pro` ที่แสดงในเอกสารรุ่นเก่า ส่งแชตหนึ่งครั้งโดยไม่มีการแมปที่ตรงกัน: MITM
> จะบันทึกค่า `model:` ขาเข้าที่แน่นอนและส่งคำขอต่อไปตามปกติ จากนั้นแมปค่าตรงตัวนั้น แล้ว
> คำขอถัดไปจะถูกดักรับและกำหนดเส้นทางไปยังเป้าหมายของคุณ

### 3.5 ประกาศความเสี่ยง

AgentBridge ดักรับข้อมูลประจำตัว (โทเค็น OAuth, คีย์ API) ที่ IDE ใช้เพื่อยืนยันตัวตนกับผู้ให้บริการต้นทาง ข้อมูลเหล่านี้จะถูก **ปกปิดก่อนบันทึกลงบันทึก** (ดู §2.7) แต่เลเยอร์ MITM ของ OmniRoute ยังคงมองเห็นข้อมูลดังกล่าว การเปิดใช้งานเอเจนต์แต่ละตัวเป็นครั้งแรกจะแสดงหน้าต่างประกาศความเสี่ยงที่สามารถปิดได้

### 3.6 การบำรุงรักษาและการวินิจฉัย

แดชบอร์ดมีการ์ด **การบำรุงรักษาและการวินิจฉัย** (`AgentBridgeMaintenanceCard` ใน `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`) ซึ่งแสดงเส้นทางการทำงานของ MITM ที่ก่อนหน้านี้ไม่มี UI คำบรรยายรองของการ์ดคือ: _"ทดสอบไปป์ไลน์การดักรับด้วยตนเอง ย้อนคืนสถานะระบบที่ตกค้าง และย้ายการตั้งค่าของคุณระหว่างเครื่อง"_ ตัวช่วยฝั่งไคลเอนต์ของการ์ดอยู่ใน `src/lib/inspector/agentBridgeMaintenanceApi.ts`

| ปุ่ม                  | เส้นทาง                                | การทำงาน                                                                                                                                                                                           |
| --------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **วินิจฉัย**          | `GET /api/tools/agent-bridge/diagnose` | เรียกใช้การทดสอบตัวเองของไปป์ไลน์การจับข้อมูลและแสดงรายงานแยกตามการตรวจสอบ (✓/✗ + คำแนะนำในการแก้ไข)                                                                                               |
| **ซ่อมแซม**           | `POST /api/tools/agent-bridge/repair`  | ย้อนคืนสถานะระบบ MITM ที่ตกค้างโดยไม่มีเจ้าของ (รายการปลอมแปลง DNS, root CA, พร็อกซีระบบ) ซึ่งเกิดจากการแครชหรือ SIGKILL เป็นแบบ idempotent — รายงานว่า "ไม่มีสิ่งที่ต้องซ่อมแซม" เมื่อสถานะสะอาด  |
| **ลบ CA**             | `DELETE /api/tools/agent-bridge/cert`  | ยกเลิกความเชื่อถือและลบ MITM root CA ออกจากคลังความเชื่อถือของ OS (ดำเนินการโดยชัดแจ้งและเป็นแบบ idempotent) แสดงเฉพาะเมื่อ CA ได้รับความเชื่อถืออยู่ในขณะนั้น และต้องยืนยันแบบอินไลน์ว่า "ลบ CA?" |
| **ส่งออกการกำหนดค่า** | `GET /api/tools/agent-bridge/config`   | ดาวน์โหลด JSON การกำหนดค่าแบบพกพา (ดู §3.7)                                                                                                                                                        |
| **นำเข้าการกำหนดค่า** | `POST /api/tools/agent-bridge/config`  | อัปโหลด JSON การกำหนดค่าที่ส่งออกไว้ก่อนหน้านี้ (ดู §3.7)                                                                                                                                          |

**การตรวจสอบวินิจฉัย** (`summarizeDiagnostics()` ใน `src/mitm/inspector/diagnostics.ts`) เส้นทางนี้จะเรียกใช้โพรบที่มีผลข้างเคียงสำหรับแต่ละรายการ แล้วส่งค่าบูลีนไปยังตัวสรุปแบบ pure โดยจะส่งคืนผลการตัดสิน `healthy` ค่าเดียว พร้อมคำแนะนำสำหรับแต่ละความล้มเหลว:

| ชื่อการตรวจสอบ     | สิ่งที่ตรวจยืนยัน                                          | คำแนะนำเมื่อเกิดความล้มเหลว                                                                                                              |
| ------------------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | กระบวนการเซิร์ฟเวอร์ MITM ทำงานอยู่                        | "เซิร์ฟเวอร์ MITM ไม่ได้ทำงาน ให้เริ่มต้นจากแท็บ AgentBridge"                                                                            |
| `server-reachable` | เซิร์ฟเวอร์ MITM ยอมรับการเชื่อมต่อบนพอร์ตของตน (โพรบ TCP) | "เซิร์ฟเวอร์ MITM ไม่ยอมรับการเชื่อมต่อบนพอร์ตของตน โปรดตรวจสอบว่าพอร์ตว่างและคุณมีสิทธิ์ในการผูกพอร์ตนั้น"                              |
| `cert-exists`      | ใบรับรอง MITM ถูกสร้างไว้บนดิสก์แล้ว                       | "ยังไม่มีการสร้างใบรับรอง MITM ให้สร้างจากแท็บ AgentBridge"                                                                              |
| `cert-trusted`     | MITM root CA อยู่ในคลังความเชื่อถือของ OS                  | "MITM root CA ไม่ได้รับความเชื่อถือจากคลังของ OS ดังนั้นการดักจับ TLS จะล้มเหลว ให้เชื่อถือใบรับรองจากแท็บ AgentBridge"                  |
| `dns-configured`   | ชื่อโฮสต์เป้าหมายถูกปลอมแปลงใน `/etc/hosts`                | "ชื่อโฮสต์เป้าหมายไม่ได้ถูกปลอมแปลงใน /etc/hosts ดังนั้นทราฟฟิกจึงไม่ไปถึงพร็อกซี ให้เปิดใช้งาน DNS สำหรับเอเจนต์ที่คุณต้องการจับข้อมูล" |

**แบนเนอร์สถานะตกค้าง:** เมื่อหน้าตรวจพบสถานะที่ตกค้างจากการแครช (การปลอมแปลง DNS / CA / พร็อกซีระบบ) การ์ดจะแสดงแบนเนอร์สีเหลืองอำพัน — _"เซสชันก่อนหน้าทิ้งสถานะระบบไว้ (การปลอมแปลง DNS, CA หรือพร็อกซีระบบ) เรียกใช้ซ่อมแซมเพื่อล้างสถานะดังกล่าว"_ — และเน้นปุ่ม **ซ่อมแซม** `Repair` เป็นสิ่งที่ทำงานในระดับแอปพลิเคชันซึ่งเทียบเท่ากับแฟล็ก `--cleanup` ของ ProxyBridge (โดยมอบหมายให้ `repairMitm()` ใน `src/mitm/manager.ts` ทำงาน)

> MITM root CA จะยังคงติดตั้งไว้ระหว่างการหยุด/เริ่มต้น เพื่อหลีกเลี่ยงพรอมต์ sudo
> ซ้ำๆ (เป็นพฤติกรรมเดียวกับ mitmproxy/Charles) ดังนั้นการลบจึงเป็นการดำเนินการ
> **ลบ CA** โดยชัดแจ้ง แทนที่จะเกิดขึ้นโดยอัตโนมัติเมื่อหยุด

### 3.7 การนำเข้า/ส่งออกการกำหนดค่าแบบพกพา

AgentBridge สามารถทำให้สถานะที่**ผู้ดำเนินการปรับแต่งได้**อยู่ในรูปแบบ JSON blob ที่มีเวอร์ชัน เพื่อให้สามารถจำลองการตั้งค่าข้ามเครื่องได้ ตัวทำซีเรียลไลซ์คือ `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) ซึ่งตรวจสอบความถูกต้องโดย `AgentBridgeConfigSchema`

ข้อมูลส่งออกประกอบด้วยสามส่วนต่อไปนี้เท่านั้น (ค่าเริ่มต้นในตัวจะ**ไม่**ถูกส่งออกโดยตั้งใจ เพื่อให้การนำเข้าไม่สร้างค่าซ้ำหรือขัดแย้งกับค่าเหล่านั้น):

| ฟิลด์            | แหล่งที่มา                                                       | หมายเหตุ                                                          |
| ---------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| `bypassPatterns` | รูปแบบการข้ามที่ผู้ใช้กำหนด (`agent_bridge_bypass`)              | ไม่รวมรูปแบบเริ่มต้นสำหรับ bank/gov/okta                          |
| `customHosts`    | โฮสต์แบบกำหนดเองของ Traffic Inspector (`inspector_custom_hosts`) | แต่ละรายการ: `{ host, kind: "llm"\|"app"\|"custom", label? }`     |
| `agentMappings`  | การแมปโมเดลแยกตามเอเจนต์ (`agent_bridge_mappings`)               | `{ [agentId]: [{ source, target }] }` สำหรับทุกเอเจนต์ที่มีการแมป |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**พฤติกรรมการนำเข้า** (`POST /api/tools/agent-bridge/config`): รูปแบบการข้ามและการแมปแยกตามเอเจนต์จะ**แทนที่ทั้งหมด** ส่วนโฮสต์แบบกำหนดเองจะถูกเพิ่มแบบ**เป็น idempotent** (`INSERT OR IGNORE`) การตอบกลับจะรายงานจำนวนรายการแต่ละประเภทที่นำไปใช้:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

สิ่งที่ **ไม่มี** อยู่ในการกำหนดค่า ได้แก่ สถานะการทำงานของเซิร์ฟเวอร์, พาธของใบรับรอง, สถานะ DNS ของแต่ละเอเจนต์, พาธของ CA ต้นทาง และการตั้งค่า TPROXY — สิ่งเหล่านี้เป็นสถานะของโฮสต์/รันไทม์ ไม่ใช่ค่ากำหนดที่นำไปใช้กับระบบอื่นได้

### รายการบายพาสสำหรับโฮสต์ที่ละเอียดอ่อน

รายการบายพาสช่วยให้มั่นใจว่าสถาบันการเงิน ผู้ให้บริการ OAuth/SSO และโฮสต์ที่ละเอียดอ่อนอื่นๆ จะ **ไม่ถูกถอดรหัสโดยเด็ดขาด** ทราฟฟิก TLS ของโฮสต์เหล่านี้จะถูกส่งผ่านในรูปแบบทันเนล TCP โปร่งใส — OmniRoute จะไม่เห็นข้อความแบบไม่เข้ารหัส

รูปแบบบายพาสเริ่มต้นประกอบด้วย:

- `*.bank.*`, `*.gov.*` (การเงิน/ภาครัฐ)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/ข้อมูลประจำตัว)
- `*.apple.com`, `*.icloud.com` (บริการระบบของ Apple)

รูปแบบบายพาสที่ผู้ใช้เพิ่มจะถูกจัดเก็บไว้ในตาราง `agent_bridge_bypass` และมีลำดับความสำคัญเหนือสิ่งอื่นทั้งหมด

### การปกปิดข้อมูลลับ

มีการใช้ `maskSecrets()` จาก `src/mitm/maskSecrets.ts`:

- กับเนื้อหาคำขอทุกรายการก่อน `TrafficBuffer.push()`
- กับส่วนหัวทุกรายการก่อนบันทึกล็อกหรือเผยแพร่

รูปแบบ: โทเค็นที่ขึ้นต้นด้วย `sk-`/`ak-`/`pk-`, โทเค็น `Bearer` และโทเค็นทั่วไปที่มีความยาว ≥40 อักขระ

### ใบรับรอง CA ต้นทาง

เมื่อตั้งค่า `AGENTBRIDGE_UPSTREAM_CA_CERT` ระบบจะอ่านไฟล์เมื่อเริ่มต้น หากพาธมีอยู่แต่ไม่สามารถอ่านไฟล์ได้ AgentBridge จะบันทึกข้อผิดพลาดที่ชัดเจนและปฏิเสธการเริ่มทำงาน (เพื่อป้องกันความล้มเหลวของ TLS แบบเงียบในสภาพแวดล้อมองค์กร)

### ข้อจำกัดที่ทราบ

- **พอร์ต 443 ต้องใช้สิทธิ์พิเศษ**: บน Linux นั้น AgentBridge ต้องใช้ `setcap 'cap_net_bind_service=+ep'` กับไบนารี Node หรือเรียกใช้ผ่าน `authbind` ตัวช่วยตั้งค่าจะแสดงคำแนะนำเฉพาะสำหรับระบบปฏิบัติการ
- **ต้องรีสตาร์ต IDE**: หลังจากเปลี่ยนเส้นทาง DNS แล้ว ต้องรีสตาร์ต IDE เพื่อให้การแปลงชื่อโฮสต์ใหม่มีผล
- **โทเค็น OAuth ที่ฝังตายตัว**: เอเจนต์บางตัว (Kiro, Antigravity) จัดเก็บโทเค็นรีเฟรช OAuth ไว้ในเครื่อง ข้อมูลเหล่านี้โปร่งใสสำหรับ AgentBridge — โดยจะเห็นโทเค็น Bearer ในแต่ละคำขอ ซึ่งจะถูกปกปิดก่อนบันทึกล็อก
- **ฟรอนต์เอนด์ Electron ต้องใช้ `NODE_EXTRA_CA_CERTS`**: IDE ที่ฟรอนต์เอนด์ทำงานบนรันไทม์ Node/Electron ที่รวมมาในตัวจะไม่สนใจ trust store ของ OS/NSS และต้องเปิดจากเชลล์ที่ตั้งค่า `NODE_EXTRA_CA_CERTS` ไว้ (ดู §3.2) อาการเมื่อขาดการตั้งค่านี้: แบ็กเอนด์ IDE ยืนยันตัวตนได้ (MITM แสดง `200`) แต่ UI ยังคงอยู่ในสถานะออกจากระบบ
- **การติดตั้ง IDE เดียวกันหลายชุดทำงานแยกจากกัน**: การติดตั้งระดับระบบ (เช่น `/usr/share/antigravity/antigravity`) และการติดตั้ง "Full" ในเครื่องของผู้ใช้ (เช่น `~/AntigravityIDE_Full/antigravity-ide`) เป็นโปรเซสแยกกันที่มีรันไทม์ของตนเอง — ต้องเปิดแต่ละชุดใหม่โดยฉีด CA เข้าไป ก่อนเปิดใหม่ ให้ระบุว่าชุดใดกำลังทำงานอยู่ด้วยพาธไบนารี
- **ข้อมูลประจำตัวถูกกำหนดโดยพรอมต์ระบบของเอเจนต์ ไม่ใช่โมเดลที่กำหนดเส้นทาง**: เมื่อแมปโมเดลของเอเจนต์ใหม่ไปยังผู้ให้บริการรายอื่น คำตอบยังคงอ้างข้อมูลประจำตัวดั้งเดิมของเอเจนต์ (เช่น Antigravity ตอบว่า "ฉันขับเคลื่อนโดย Gemini") เนื่องจาก IDE ฉีดข้อมูลดังกล่าวเข้าไปในพรอมต์ระบบ ให้ตรวจสอบแบ็กเอนด์จริงใน `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`) แทนการถามโมเดลว่าเป็นใคร

## §6 การแก้ไขปัญหา

### พอร์ต 443 ขัดแย้งกัน

หากมีกระบวนการอื่นกำลังรอรับการเชื่อมต่อบนพอร์ต 443 อยู่แล้ว (เว็บเซิร์ฟเวอร์, VPN ฯลฯ):

```bash
lsof -i :443          # ค้นหากระบวนการ
sudo fuser -k 443/tcp  # บังคับยุติกระบวนการ (ใช้อย่างระมัดระวัง)
```

อีกทางเลือกหนึ่งคือกำหนดค่าพอร์ตที่ไม่ต้องใช้สิทธิ์พิเศษในการตั้งค่าของ AgentBridge และตั้งกฎการเปลี่ยนเส้นทางด้วย `iptables` / `pf`

### ใบรับรองไม่ได้รับความเชื่อถือ

หาก IDE แสดงข้อผิดพลาด TLS หลังจากเริ่ม AgentBridge:

1. ตรวจสอบว่าได้ติดตั้งใบรับรองแล้ว: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) หรือ `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. แอปบางตัวจัดเก็บคลังความเชื่อถือของตนเอง (Firefox, Chrome บน Linux) ให้เรียกใช้ "เชื่อถือใบรับรอง" อีกครั้งและตรวจสอบคลังใบรับรองเฉพาะสำหรับ NSS/Firefox
3. รีสตาร์ต IDE หลังจากกำหนดให้เชื่อถือแล้ว — เซสชัน TLS ที่กำลังดำเนินการอยู่จะยังใช้สถานะความเชื่อถือเดิม

### IDE ออกจากระบบ / "ข้อผิดพลาดในการเชื่อมต่อ" แม้ CA จะได้รับความเชื่อถือแล้ว

อาการ: หลังจากเปลี่ยนเส้นทาง DNS และกำหนดให้เชื่อถือ CA แล้ว IDE ที่ใช้ Electron (เช่น Antigravity)
เปิดขึ้นมาในสถานะ **ออกจากระบบ** หรือแสดงข้อผิดพลาดเกี่ยวกับการยืนยันตัวตน/การเชื่อมต่อ แต่บันทึก MITM แสดงว่า
การเรียกเริ่มต้น (`loadCodeAssist`, `fetchAvailableModels`, …) ส่งคืน `200`

สาเหตุ: **รันไทม์ Node/Electron ที่รวมมากับ IDE ไม่สนใจคลังความเชื่อถือของระบบปฏิบัติการ** แบ็กเอนด์แบบเนทีฟ
(เซิร์ฟเวอร์ภาษา Go) เชื่อถือ CA ของระบบปฏิบัติการและยืนยันตัวตนได้ แต่ฟรอนต์เอนด์ Electron
ไม่เชื่อถือ — ดังนั้น UI จึงเข้าใจว่าออฟไลน์อยู่

วิธีแก้ไข (ต้องทำทั้งสองขั้นตอน): ส่งออก `NODE_EXTRA_CA_CERTS=<ca.crt>` **และเปิด IDE ใหม่จาก
เชลล์นั้น** ไม่ใช่จากไอคอนบนเดสก์ท็อป ต้องปิด IDE โดยสมบูรณ์ก่อน — ล็อกซิงเกิลตันของ Electron หมายความว่า
การเปิดครั้งที่สองจะเพียงแค่นำกระบวนการที่มีอยู่มาแสดง และสภาพแวดล้อมใหม่จะถูกละเว้น ดู §3.2
กรณีนี้สอดคล้องกับรายงานต้นทางที่ยังเปิดอยู่ ซึ่งเอเจนต์แบบสแตนด์อโลนทำงานผ่าน MITM ได้ แต่ IDE
อีกเวอร์ชันหนึ่งล้มเหลวภายใต้การตั้งค่าเดียวกัน

### DNS ยังไม่เผยแพร่

ตรวจสอบว่า `/etc/hosts` ได้รับการอัปเดตแล้ว:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

ล้างแคช DNS:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### ตรวจไม่พบ IDE

การตรวจหาอัตโนมัติใช้ตำแหน่งการติดตั้งทั่วไป หากการตรวจหาล้มเหลวแต่ติดตั้ง IDE ไว้แล้ว:

- ตรวจสอบว่าไบนารีของ IDE อยู่ในตำแหน่งที่ไม่เป็นมาตรฐานหรือไม่
- ตัวช่วยสร้างการตั้งค่ายังคงใช้งานได้ — การตรวจหาล้มเหลวหมายความเพียงว่าป้ายสถานะจะไม่แสดงพาธการติดตั้ง

### ข้อผิดพลาดของตัวจัดการ (การดึงข้อมูลจากต้นทางล้มเหลว)

หาก AgentBridge ดักรับคำขอได้ แต่คำขอทั้งหมดล้มเหลว:

1. ตรวจสอบว่ามีผู้ให้บริการเชื่อมต่ออยู่อย่างน้อยหนึ่งรายที่ `/dashboard/providers`
2. ตรวจสอบบันทึกของเซิร์ฟเวอร์ OmniRoute: `APP_LOG_LEVEL=debug` ใน `.env`
3. ตรวจสอบว่า `OMNIROUTE_BASE_URL` ชี้ไปยังปลายทางเราเตอร์ที่ถูกต้อง (ค่าเริ่มต้น: `http://127.0.0.1:20128`)

## §8 แผนงาน

### การตรวจสอบ Trae

Trae เป็นผู้ช่วยเขียนโค้ดด้วย AI ที่ค่อนข้างใหม่ ก่อนนำ handler ไปใช้งาน:

1. ระบุไบนารี/ส่วนขยายในมาร์เก็ตเพลสของ VS Code / JetBrains หรือระบุว่าเป็นแอปแบบสแตนด์อโลน
2. จับทราฟฟิกด้วย mitmproxy เพื่อค้นหาโฮสต์ API และรูปแบบของ endpoint
3. ตรวจสอบกลไกการยืนยันตัวตน
4. ประเมินว่าจะดำเนินการต่อหรือไม่ โดยพิจารณาจากข้อกำหนดการให้บริการและความสามารถในการค้นพบ API

จนกว่าการตรวจสอบจะเสร็จสมบูรณ์ การ์ด Trae ในแดชบอร์ดจะแสดงป้าย "กำลังตรวจสอบ" พร้อมลิงก์ "รายงานความเป็นไปได้" stub ของ handler ที่ `src/mitm/handlers/trae.ts` จะส่งข้อผิดพลาดแบบมีโครงสร้าง `ยังไม่ได้ใช้งาน`

### เอเจนต์ในรายการงานค้าง (ต้องใช้ MITM — ไม่รองรับ base URL แบบกำหนดเอง)

เครื่องมือต่อไปนี้ไม่รองรับ base URL แบบกำหนดเองในเวอร์ชันปัจจุบัน ทำให้ MITM เป็นช่องทางเดียวสำหรับการดักรับข้อมูล ขณะนี้ยังอยู่ระหว่างการประเมินความเป็นไปได้:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — แยกจาก Kiro IDE)
- **Cowork** (เดสก์ท็อปของ Anthropic)

หมายเหตุ: GitHub Copilot CLI ≥v1.0.19 รองรับ `COPILOT_PROVIDER_BASE_URL` — สำหรับเครื่องมือนี้ ให้ใช้การกำหนดค่าโดยตรงแทน MITM
