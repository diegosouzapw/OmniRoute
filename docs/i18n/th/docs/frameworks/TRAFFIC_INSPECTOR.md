Traffic Inspector เป็นเครื่องมือดีบักทราฟฟิก HTTPS ในตัวของ OmniRoute ซึ่งคล้ายกับ Charles Proxy / mitmweb / HTTP Toolkit แต่ **รองรับการรับรู้ LLM** และ **รองรับการรับรู้เอเจนต์** โดยอยู่ที่ `/dashboard/tools/traffic-inspector` และรับทราฟฟิกแบบสดจากแหล่งจับข้อมูลพร้อมกันได้สูงสุด 5 แหล่ง

**ตำแหน่งในแดชบอร์ด:** `/dashboard/tools/traffic-inspector`
**กลุ่มในแถบด้านข้าง:** เครื่องมือ (อยู่ถัดจาก AgentBridge)
**ดูเพิ่มเติม:** [`AGENTBRIDGE.md`](./AGENTBRIDGE.md) — AgentBridge คือโหมดการจับข้อมูลที่ 1

### สถาปัตยกรรมโดยสรุปในหนึ่งย่อหน้า

`TrafficBuffer` (`src/mitm/inspector/buffer.ts`) เป็นริงบัฟเฟอร์ร่วมในหน่วยความจำ (ค่าเริ่มต้น 1000 รายการ และกำหนดค่าได้ผ่าน `INSPECTOR_BUFFER_SIZE`) แหล่งจับข้อมูลทั้งหมดเขียนข้อมูลลงในบัฟเฟอร์นี้ผ่าน `push()` คลาสบัฟเฟอร์จะจำแนกแต่ละรายการโดยใช้ `kindDetector.ts` (ตรวจสอบว่าเป็นคำขอ LLM หรือไม่) คำนวณ `contextKey` (ลายนิ้วมือ SHA-256 ของพรอมต์ระบบ) และกระจายข้อมูลไปยังผู้สมัครรับข้อมูล WebSocket ทั้งหมดผ่าน `globalTrafficBuffer.subscribe()` แดชบอร์ดเชื่อมต่อผ่าน `GET /api/tools/traffic-inspector/ws` และจะได้รับสแนปชอตเมื่อเชื่อมต่อ จากนั้นจึงได้รับเหตุการณ์ `new`/`update`/`clear`

## §2 โหมดการจับทราฟฟิก

Traffic Inspector รองรับ **แหล่งที่มาสำหรับการจับทราฟฟิกพร้อมกัน 5 แหล่ง** โดยแต่ละแหล่งสามารถเปิดหรือปิดได้อย่างอิสระ ฟิลด์ `source` ของ `InterceptedRequest` ทุกรายการ (`src/mitm/inspector/types.ts`) จะเป็นค่าใดค่าหนึ่งจาก `"agent-bridge"`, `"custom-host"`, `"http-proxy"`, `"system-proxy"` หรือ `"tproxy"`

### โหมด 1 — AgentBridge (ค่าเริ่มต้น เปิดอยู่เสมอ)

**แหล่งที่มา:** ตัวจัดการ AgentBridge (`src/mitm/handlers/base.ts`)
**กลไก:** การเรียก `intercept()` ทุกครั้งใน `MitmHandlerBase` จะเรียก `hookBufferStart()` ก่อนส่งต่อ และเรียก `hookBufferUpdate()` เมื่อเสร็จสิ้น ไม่ต้องกำหนดค่าเพิ่มเติม — ใช้งานได้ทันทีที่ AgentBridge ทำงาน
**ขอบเขต:** เอเจนต์ IDE ทั้ง 9 รายการที่กำหนดค่าไว้ใน AgentBridge
**หมายเหตุ:** ฟิลด์ `source` ใน `InterceptedRequest` = `"agent-bridge"`

### โหมด 2 — โฮสต์แบบกำหนดเอง (การเปลี่ยนเส้นทาง DNS)

**แหล่งที่มา:** รายการโฮสต์ที่ผู้ใช้กำหนด (`inspector_custom_hosts` table)
**กลไก:** การเพิ่มโฮสต์ผ่าน UI จะเพิ่ม `127.0.0.1 <host>` ลงใน `/etc/hosts` (ต้องใช้ sudo) เซิร์ฟเวอร์ MITM ของ AgentBridge ที่มีอยู่ (พอร์ต 443) จะสร้างใบรับรอง SNI สำหรับโฮสต์ใหม่แบบไดนามิก
**ขอบเขต:** แอปพลิเคชันใดก็ตามที่ใช้โฮสต์ที่เพิ่มไว้ — ไม่จำเป็นต้องเปลี่ยนการกำหนดค่าของแอป
**หมายเหตุ:** `source` = `"custom-host"`

ตัวอย่างกรณีการใช้งาน:

- ตรวจสอบ `api.openai.com` จากสคริปต์ Python
- ดีบัก `my-internal-llm.company.com`
- จับทราฟฟิกจากอุปกรณ์เคลื่อนที่บนเครือข่ายเดียวกัน (ผ่านการปลอมแปลง ARP — ขั้นสูง)

### โหมด 3 — ตัวรับฟัง HTTP_PROXY (พอร์ต 8080)

**แหล่งที่มา:** แอปพลิเคชันที่ใช้ตัวแปรสภาพแวดล้อม `HTTP_PROXY`/`HTTPS_PROXY`
**กลไก:** ตัวรับฟังรองที่พอร์ต 8080 (`src/mitm/inspector/httpProxyServer.ts`) ซึ่งทำหน้าที่เป็นพร็อกซี HTTP/HTTPS แบบชัดแจ้งมาตรฐาน รองรับทั้งอุโมงค์ `CONNECT` (HTTPS) และคำขอ HTTP โดยตรง
**ขอบเขต:** แอปพลิเคชันใดก็ตามที่รองรับตัวแปรสภาพแวดล้อม `HTTP_PROXY` — ไม่ต้องเปลี่ยน DNS และไม่ต้องใช้ sudo
**หมายเหตุ:** `source` = `"http-proxy"`

```bash
# จับทราฟฟิกอย่างรวดเร็วสำหรับคำสั่งเดียว:
HTTPS_PROXY=http://127.0.0.1:8080 curl https://api.openai.com/v1/models

# จับทราฟฟิกอย่างต่อเนื่องในเซสชันเชลล์:
export HTTP_PROXY=http://127.0.0.1:8080
export HTTPS_PROXY=http://127.0.0.1:8080
```

**ข้อจำกัดของ TLS:** อุโมงค์ HTTPS `CONNECT` จะถูกจับเป็นข้อมูลเมตาเท่านั้น (โฮสต์ พอร์ต และเวลา) — เนื้อหา TLS จะไม่ถูกถอดรหัสโดยค่าเริ่มต้น เปิดสวิตช์ "ถอดรหัส HTTPS ในโหมดพร็อกซี" (ต้องเลือกเปิดเองและกำหนดให้เชื่อถือใบรับรอง AgentBridge) เพื่อตรวจสอบเนื้อหาทั้งหมด

**พอร์ตขัดแย้ง:** หากพอร์ต 8080 ถูกใช้งานอยู่ AgentBridge จะส่งคืน 409 พร้อมข้อผิดพลาดที่มีโครงสร้าง เปลี่ยนพอร์ตผ่านตัวแปรสภาพแวดล้อม `INSPECTOR_HTTP_PROXY_PORT`

### โหมด 4 — พร็อกซีทั่วทั้งระบบ (ขั้นสูง ต้องเลือกเปิดเอง)

**แหล่งที่มา:** การตั้งค่าพร็อกซีระดับ OS (มีผลกับทุกแอปบนเครื่อง)
**กลไก:** ใช้ API ของ OS เพื่อเปลี่ยนเส้นทางทราฟฟิก HTTP/HTTPS ทั้งหมดผ่านตัวรับฟัง HTTP_PROXY:

- **macOS:** `networksetup -setwebproxy / -setsecurewebproxy`
- **Linux:** `gsettings set org.gnome.system.proxy` + `/etc/environment`
- **Windows:** `netsh winhttp set proxy 127.0.0.1:8080`
  **ขอบเขต:** ทุกแอปพลิเคชันบนเครื่องที่รองรับการตั้งค่าพร็อกซีของระบบ
  **หมายเหตุ:** `source` = `"system-proxy"`

**กลไกด้านความปลอดภัย:**

- ตัวจับเวลาปิดใช้งานอัตโนมัติ (ค่าเริ่มต้น 30 นาที กำหนดค่าได้ผ่าน `INSPECTOR_SYSTEM_PROXY_GUARD_MINUTES`)
- สถานะพร็อกซีระบบก่อนหน้าจะถูกบันทึกไว้ใน DB และคืนค่าเมื่อย้อนกลับ
- แดชบอร์ดจะแสดงข้อความแจ้ง "กำลังย้อนกลับพร็อกซีระบบ" หากผู้ใช้ออกจากหน้าในขณะที่ยังเปิดใช้งานอยู่
- UI แสดงป้าย `⚠ ขั้นสูง` พร้อมช่องทำเครื่องหมายเพื่อยืนยันอย่างชัดเจน

### โหมด 5 — การถอดรหัสแบบโปร่งใสด้วย TPROXY (Linux, root, ต้องเลือกเปิดเอง)

**แหล่งที่มา:** TPROXY ของเคอร์เนล + การกำหนดเส้นทางตามนโยบาย (`src/mitm/tproxy/`)
**กลไก:** ทำเครื่องหมายการเชื่อมต่อ TCP ขาออกภายในเครื่องรายการใหม่ที่ไปยังพอร์ตเป้าหมาย (ค่าเริ่มต้น `443`) ใน `mangle OUTPUT` จากนั้น `ip rule` จะเปลี่ยนเส้นทางแพ็กเก็ตที่ทำเครื่องหมายไว้ให้ส่งภายในเครื่อง และเป้าหมาย `TPROXY` ของ `mangle PREROUTING` จะส่งแพ็กเก็ตเหล่านั้นไปยังตัวรับฟังแบบโปร่งใส (**IP_TRANSPARENT**) (พอร์ตเริ่มต้น `8443`) ตัวรับฟังจะยุติ TLS ด้วยใบรับรองปลายทางที่ออก **ตามชื่อโฮสต์ SNI แต่ละรายการเมื่อมีการร้องขอ** โดย CA แบบไดนามิก จับการแลกเปลี่ยนข้อมูลที่ถอดรหัสแล้ว และส่งต่อคำขอไปยังปลายทางเดิมโดยเข้ารหัสใหม่
**ขอบเขต:** โฮสต์ปลายทาง **ใดๆ** บนพอร์ตเป้าหมาย — ไม่ต้องปลอมแปลง `/etc/hosts` ไม่ต้องใช้ตัวแปรสภาพแวดล้อม `HTTP_PROXY` และไม่ต้องแก้ไขพร็อกซีทั่วทั้งระบบ กระบวนการที่ถูกสกัดกั้นไม่จำเป็นต้องเปลี่ยนการกำหนดค่า แต่ต้องเชื่อถือ CA แบบไดนามิก
**หมายเหตุ:** `source` = `"tproxy"`

**ข้อกำหนด:** รองรับเฉพาะ Linux (**IP_TRANSPARENT** ใช้ได้เฉพาะบน Linux), ต้องมีความสามารถ **CAP_NET_ADMIN** (root) และแอดออน N-API แบบเนทีฟที่ต้องสร้างด้วยชุดเครื่องมือ C (`npm run build:native:tproxy`) เมื่อไม่พร้อมใช้งาน สวิตช์บนแดชบอร์ดจะถูกปิดใช้งานพร้อมคำแนะนำเครื่องมือ "การถอดรหัส TPROXY ต้องใช้ Linux + root + แอดออนแบบเนทีฟ" กฎไฟร์วอลล์จะถูกนำไปใช้/ย้อนกลับแบบทรานแซกชัน (การแครชจะไม่ทิ้งกฎ `mangle` ไว้) และจะถูกล้างเมื่อรีบูต กลไกป้องกันลูปที่ใช้ SO_MARK จะป้องกันไม่ให้การส่งต่อที่เข้ารหัสใหม่ของพร็อกซีถูกสกัดกั้นซ้ำ

ส่วนนี้เป็นระบบย่อยขนาดใหญ่ที่มีคู่มือสำหรับผู้ปฏิบัติงานโดยเฉพาะ — ดู `docs/security/MITM-TPROXY-DECRYPT.md` (git; ไม่ได้คอมไพล์รวมใน `/docs`) สำหรับสูตรไฟร์วอลล์ฉบับเต็ม, CA แบบไดนามิกต่อ SNI + ตัวติดตั้ง trust store, เส้นทางเฉพาะภายในเครื่อง, รายละเอียดการป้องกันลูป และสคีมาการกำหนดค่า สวิตช์นี้ควบคุมโดย `GET / POST / DELETE /api/tools/agent-bridge/tproxy` (หมายเหตุ: เส้นทางอยู่ภายใต้คำนำหน้า AgentBridge ไม่ใช่คำนำหน้า Traffic Inspector)

## §4 ฟีเจอร์ที่รับรู้บริบทของ LLM

### 4.1 ตัวตรวจจับชนิด (`src/mitm/inspector/kindDetector.ts`)

จำแนกแต่ละคำขอเป็น `"llm"`, `"app"` หรือ `"unknown"` โดยใช้สัญญาณ 4 ประเภท:

1. **รีจิสทรีโฮสต์** — ชื่อโฮสต์ API ของ LLM ที่รู้จักประมาณ 18 รายการ (OpenAI, Anthropic, Gemini, Groq, Mistral, Together, Fireworks, Cohere, Perplexity, Hugging Face, OpenRouter, xAI, Moonshot เป็นต้น)
2. **รูปแบบพาธ** — `/v1/chat/completions`, `/v1/messages`, `/generateContent`, `/v1/responses` เป็นต้น
3. **โครงสร้างบอดี** — ตรวจจับฟิลด์ `messages[]` (OpenAI/Claude), `contents[]` (Gemini), `prompt`, `input`
4. **ข้อมูลบ่งชี้จาก user-agent** — `codex`, `claude`, `gemini`, `antigravity`, `kiro`, `copilot`, `cursor` ในสตริง UA

โฮสต์แบบกำหนดเองที่เพิ่มผ่านโหมด 2 จะรับค่า `kind` จากข้อมูลที่ป้อนในฟอร์ม (ค่าเริ่มต้นคือ `"custom"`)

### 4.2 ตัวรวม SSE (`src/mitm/inspector/sseMerger.ts`)

**การพัฒนาแบบ clean-room ที่เป็นอิสระ** การแยกวิเคราะห์เหตุการณ์เป็นไปตาม
[อัลกอริทึม server-sent events ของ WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)
ส่วนการประกอบข้อมูลกลับเป็นไปตามสคีมาสตรีมมิงสาธารณะของ [OpenAI](https://platform.openai.com/docs/api-reference/chat/create),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/streaming) และ
[Gemini](https://ai.google.dev/api/generate-content#method:-models.streamgeneratecontent)

ประกอบข้อความสุดท้ายของผู้ช่วยขึ้นใหม่จากเหตุการณ์เดลตา SSE ดิบ:

- **Anthropic**: สะสม `content_block_delta` ตามดัชนี รองรับ `text_delta`, `input_json_delta` (การเรียกใช้เครื่องมือ), `thinking_delta`
- **OpenAI**: สะสมตัวเลือก/การเรียกใช้เครื่องมือของ Chat Completions และรายการเอาต์พุตของ Responses API
  ตามดัชนี
- **Gemini**: สะสม `candidates[i].content.parts`
- **ไม่ทราบชนิด**: ส่งคืนเหตุการณ์ดิบตามเดิม

แท็บการตอบกลับจะแสดงตัวสลับ: **"เหตุการณ์ดิบ ↔ รวมแล้ว"**

### 4.3 ตัวปรับบทสนทนาให้เป็นมาตรฐาน (`src/mitm/inspector/conversationNormalizer.ts`)

**การพัฒนาแบบ clean-room ที่เป็นอิสระ** การปรับให้เป็นมาตรฐานถูกกำหนดโดยสัญญาแบบ black-box
ภายในระบบและสคีมาข้อความสาธารณะของ OpenAI, Anthropic และ Gemini โดยไม่มีการใช้
ซอร์สของอิมพลีเมนเทชันต้นทาง

แปลงรูปแบบข้อความของ OpenAI, Anthropic และ Gemini เป็น `NormalizedConversation` เดียวก่อนเรนเดอร์:

```ts
interface NormalizedConversation {
  request: NormalizedTurn[]; // ข้อความ / เนื้อหา / พรอมต์จากบอดีคำขอ
  response: NormalizedTurn[]; // การตอบกลับของผู้ช่วย (รวมผ่าน sseMerger)
  contextKey: string | null; // ลายนิ้วมือ SHA-256 ของพรอมต์ระบบ
}
```

ประเภทบล็อก: `text`, `tool_use`, `tool_result` แท็บบทสนทนาใช้โครงสร้างนี้โดยไม่ขึ้นกับผู้ให้บริการ

### 4.4 การกำหนดสีให้คีย์บริบท (`src/mitm/inspector/contextKey.ts`)

- คำนวณ `SHA-256` ของพรอมต์ระบบ (ข้อความแรกที่มี `role:system` หรือฟิลด์ `system` หรือ `systemInstruction` ของ Gemini)
- ส่งคืนคำนำหน้าเลขฐานสิบหก 12 อักขระ (`"a3f9c2..."`)
- ฟรอนต์เอนด์แมปคีย์เป็นสี HSL แบบกำหนดแน่นอนสำหรับแถบขอบด้านซ้าย
- **ตัวกรอง "บริบทเดียวกัน"**: การคลิกชิป `ctx #a3f` จะเพิ่มตัวกรองเพื่อแสดงเฉพาะคำขอที่มีลายนิ้วมือเดียวกัน

ฟีเจอร์นี้ช่วยให้แยกแยะ "บุคลิก" หรืองานต่างๆ ที่ทำงานอยู่ในเซสชันเอเจนต์เดียวกันได้ง่ายขึ้นด้วยสายตา

### 4.5 การแยกเมตาดาตาของ LLM

สำหรับคำขอ LLM แท็บรายละเอียด LLM จะแยกข้อมูลต่อไปนี้:

```ts
interface LlmMetadata {
  provider: string | null; // "openai" | "anthropic" | "gemini" | ...
  apiKind: string | null; // "chat.completions" | "messages" | "embeddings" | ...
  model: string | null; // จากบอดีคำขอหรือการตอบกลับ
  messages: number; // จำนวนรอบการสนทนา
  tokensIn: number | null; // usage.prompt_tokens / usage.input_tokens
  tokensOut: number | null; // usage.completion_tokens / usage.output_tokens
  streamed: boolean; // true หากเป็นการตอบกลับแบบ SSE
  mappedTo: string | null; // เฮดเดอร์ x-omniroute-mapped
  costEstimateUsd: number | null; // ค่าใช้จ่ายโดยประมาณตามราคาของ OmniRoute
}
```

### 4.6 ตัวกรองคำขอที่กำลังดำเนินการแบบสด

ฟิลด์ `status` ของคำขอคือ `number | "in-flight" | "error"` โดยรายการจะถูก
เพิ่มเป็น `"in-flight"` ทันทีที่คำขอเริ่มต้น และจะถูก **อัปเดตในตำแหน่งเดิม**
เมื่อได้รับการตอบกลับ (หรือข้อผิดพลาด) ตัวสลับ **"สด"** บนแถบเครื่องมือ
(`liveOnly`, คีย์ i18n `trafficInspector.liveOnly`) จะจำกัดรายการให้เหลือเฉพาะรายการ
ที่มี `status === "in-flight"` ทำให้คุณสามารถติดตามการเชื่อมต่อที่เปิดอยู่ได้แบบเรียลไทม์

ตัวกรองนี้เป็นเพรดิเคตฝั่งไคลเอนต์ล้วนใน
`src/lib/inspector/matchesTrafficFilter.ts`:

```ts
if (f.liveOnly && req.status !== "in-flight") return false;
```

สถานะของตัวสลับอยู่ใน `useTrafficFilters` (ฮุกของแดชบอร์ดตัวตรวจสอบ) และ
ทำงานร่วมกับตัวกรองอื่นๆ (โปรไฟล์, โฮสต์, เอเจนต์, แหล่งที่มา, สถานะ, บริบท)

### 4.7 การระบุโปรเซสต้นทาง (Linux)

บน Linux คำขอแต่ละรายการที่ถูกดักจับสามารถระบุแหล่งที่มาไปยัง **โปรเซสภายในเครื่อง
ที่เป็นต้นทาง** ได้ โดยเพิ่มฟิลด์ทางเลือกสองฟิลด์ลงใน `InterceptedRequest`:

```ts
pid?: number;          // ID ของโปรเซสต้นทาง (Linux เท่านั้น)
processName?: string;  // ชื่อโปรเซสต้นทาง (Linux เท่านั้น)
```

`src/mitm/inspector/processAttribution.ts` แมปพอร์ตชั่วคราวของ _ไคลเอนต์_
ในการเชื่อมต่อเข้ากับ PID + ชื่อ โดย:

1. อ่าน `/proc/net/tcp` และ `/proc/net/tcp6` เพื่อค้นหา socket inode สำหรับ
   พอร์ต (`parseProcNetTcpForInode` ซึ่งเป็นพาร์เซอร์แบบ pure ที่ทดสอบด้วย fixture ได้)
2. สแกน `/proc/<pid>/fd/` เพื่อค้นหา symlink ไปยัง `socket:[<inode>]`
3. อ่านชื่อโปรเซสจาก `/proc/<pid>/comm`

แคช TTL 1 วินาทีช่วยจำกัดต้นทุนการสแกน procfs ภายใต้โหลด การระบุแหล่งที่มาเป็นแบบ
**พยายามอย่างดีที่สุด** — ความล้มเหลวใดๆ จะให้ผลลัพธ์เป็น `null` และจะไม่บล็อกการจับข้อมูล บน
macOS/Windows ฟังก์ชันจะส่งคืน `null` (stub โดยการรองรับ `lsof`/`GetExtendedTcpTable`
จะเพิ่มเติมในภายหลัง)

## §5 เซสชัน

### 5.1 การบันทึกเซสชัน

1. คลิก **"● บันทึกเซสชัน"** ในแถบเครื่องมือ → ป้อนชื่อ (ไม่บังคับ)
2. Live tail จะทำงานต่อตามปกติ โดยตัวบ่งชี้สีแดงกะพริบจะแสดง `◉ REC · <name> · 00:42 · 23 คำขอ`
3. คลิก **"⏹ หยุด"** → สแนปชอตของเซสชันจะถูกบันทึกลงใน `inspector_sessions` + `inspector_session_requests`

### 5.2 การดูเซสชันที่บันทึกไว้

เมนูแบบเลื่อนลง **เซสชัน** ในแถบเครื่องมือจะแสดงรายการเซสชันที่บันทึกไว้ เมื่อเลือกเซสชันใดเซสชันหนึ่ง:

- โหลดสแนปชอตของเซสชัน (สถานะที่ถูกตรึงไว้)
- แบนเนอร์จะแสดง: `กำลังดูเซสชันที่บันทึกไว้ "<name>" — [กลับไปยังข้อมูลสด]`
- แท็บสถิติจะพร้อมใช้งานพร้อมข้อมูลสรุปรวมจาก Recharts

### 5.3 รูปแบบการส่งออก

แต่ละเซสชันสามารถส่งออกได้ในรูปแบบต่อไปนี้:

| รูปแบบ                     | การใช้งาน                                                                               |
| -------------------------- | --------------------------------------------------------------------------------------- |
| **HAR** (HTTP Archive 1.2) | ใช้งานร่วมกับ Chrome DevTools, Charles และ Fiddler ได้ — นำเข้าเพื่อวิเคราะห์แบบออฟไลน์ |
| **JSONL**                  | หนึ่ง `InterceptedRequest` ต่อบรรทัด — ใช้งานร่วมกับรูปแบบ `llm-interceptor` ได้        |

ส่งออกผ่าน `GET /api/tools/traffic-inspector/sessions/{id}/export.har` หรือปุ่ม ⬇ ในเมนูแบบเลื่อนลงเซสชัน

## §6 ความปลอดภัย

Traffic Inspector แสดง **ทราฟฟิก HTTPS ที่ถูกดักจับทั้งหมด** รวมถึงส่วนหัวการให้สิทธิ์และเนื้อหาคำขอ โดยมีมาตรการควบคุมดังต่อไปนี้:

| มาตรการควบคุม                      | รายละเอียด                                                                                                                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LOCAL_ONLY**                     | ทุกเส้นทางและปลายทาง WebSocket เข้าถึงได้จากลูปแบ็กเท่านั้น (บังคับใช้ใน `routeGuard.ts` ก่อนการยืนยันตัวตน)                                                                             |
| **การปกปิดข้อมูลลับ**              | ตัวสแกนเชิงเส้น `maskSecret()` จะปกปิดข้อมูลประจำตัว Bearer ตาม RFC 6750, คีย์ที่มีคำนำหน้าของผู้ให้บริการ และโทเค็นแบบทึบที่มีความยาวมาก ก่อน `TrafficBuffer.push()`                    |
| **ขีดจำกัดขนาดเนื้อหา**            | เนื้อหาที่มีขนาด > `INSPECTOR_MAX_BODY_KB` (ค่าเริ่มต้น 1024 KB) จะถูกตัดทอนพร้อมข้อความแจ้ง `"(ตัดทอนเพื่อประสิทธิภาพ)"`                                                                |
| **การทำให้ส่วนหัวปลอดภัย**         | ชื่อจะถูกแปลงเป็นตัวพิมพ์เล็ก ส่วนหัวที่เกี่ยวกับการจัดเฟรม/แบบ hop-by-hop และการยืนยันตัวตนของพร็อกซีจะถูกละทิ้ง คุกกี้จะถูกปกปิดทั้งหมด และค่าข้อมูลประจำตัวจะส่งต่อให้ `maskSecret()` |
| **CSP**                            | ใช้นโยบาย Content Security Policy ที่เข้มงวดบนหน้า Traffic Inspector เพื่อป้องกัน XSS ผ่านเนื้อหาการตอบกลับที่ถูกแทรก                                                                    |
| **ไม่มีการเก็บถาวรโดยค่าเริ่มต้น** | `TrafficBuffer` อยู่ในหน่วยความจำและจะสูญหายเมื่อรีสตาร์ทเซิร์ฟเวอร์ เซสชันจะถูกเก็บถาวรเฉพาะเมื่อมีการบันทึกอย่างชัดเจนเท่านั้น                                                         |

### กฎตายตัวที่ใช้

| กฎ                                | การใช้งาน                                                                           |
| --------------------------------- | ----------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`    | การตอบกลับข้อผิดพลาด HTTP ทั้งหมดจากเส้นทาง Traffic Inspector จะถูกทำให้ปลอดภัย     |
| **#15 + #17** `isLocalOnlyPath()` | `/api/tools/traffic-inspector/` เป็น LOCAL_ONLY + SPAWN_CAPABLE (คำสั่งพร็อกซีระบบ) |

### ข้อจำกัดที่ทราบ

- **โหมดพร็อกซีทั้งระบบ** มีผลต่อแอปพลิเคชันทั้งหมดบนเครื่อง รวมถึงไคลเอนต์ VPN และ SSO ควรใช้ร่วมกับตัวจับเวลาปิดใช้งานอัตโนมัติเสมอ ห้ามใช้บนเครื่องที่ใช้ร่วมกัน
- **HTTPS ผ่านอุโมงค์ CONNECT**: โหมด 3 (HTTP_PROXY) จะบันทึกเฉพาะข้อมูลเมตาของอุโมงค์สำหรับปลายทาง HTTPS เว้นแต่จะเปิดใช้การดักจับ TLS ลักษณะนี้เป็นการออกแบบโดยเจตนา เพราะการบันทึกแบบโปร่งใสโดยที่ใบรับรอง AgentBridge ไม่ได้รับความเชื่อถือจะทำให้การตรวจสอบ TLS ของแอปเหล่านั้นล้มเหลว
- **สตริงที่เขียนไว้ตายตัวในบางคอมโพเนนต์**: คอมโพเนนต์ UI บางรายการ (F7/F8) มีสตริงที่เขียนไว้ตายตัวจำนวนเล็กน้อยซึ่งยังไม่ครอบคลุมโดยคีย์ i18n รายการเหล่านี้ได้รับการบันทึกเป็นข้อจำกัดที่ทราบในรายงานช่องว่าง i18n และจะถูกย้ายในรอบติดตามผล สตริงที่ได้รับผลกระทบเป็นป้ายกำกับตกแต่ง UI ซึ่งไม่จำเป็นต้องแปลเพื่อการใช้งานเชิงฟังก์ชัน

## §7 การแก้ไขปัญหา

### การตัดการเชื่อมต่อ WebSocket

หาก live tail แสดงข้อความ "ตัดการเชื่อมต่อแล้ว":

1. ตรวจสอบว่าเซิร์ฟเวอร์ยังคงทำงานอยู่: `GET /api/tools/traffic-inspector/capture-modes`
2. โหลดหน้าใหม่ — WebSocket จะเชื่อมต่ออีกครั้งและรับ snapshot ใหม่
3. หากเซิร์ฟเวอร์ถูกรีสตาร์ต บัฟเฟอร์ในหน่วยความจำจะถูกล้าง — รายการเก่าจะหายไป เว้นแต่จะมีการบันทึกเซสชันไว้

### พอร์ต 8080 ขัดแย้งกัน

หากโหมด HTTP_PROXY ไม่สามารถเริ่มทำงานได้:

```bash
lsof -i :8080    # ค้นหาโปรเซส
```

เปลี่ยนพอร์ต:

```bash
# .env
INSPECTOR_HTTP_PROXY_PORT=8888
```

### พร็อกซีระบบไม่ได้ถูกคืนค่า

หาก OmniRoute ขัดข้องในขณะที่โหมดพร็อกซีทั่วทั้งระบบยังทำงานอยู่:

**macOS:**

```bash
networksetup -setwebproxystate Wi-Fi off
networksetup -setsecurewebproxystate Wi-Fi off
```

**Linux (GNOME):**

```bash
gsettings set org.gnome.system.proxy mode 'none'
```

**Windows:**

```cmd
netsh winhttp reset proxy
```

เมื่อโหลดครั้งถัดไป แดชบอร์ดจะแสดงตัวเลือก "คืนค่าพร็อกซีระบบ" ด้วย หากตรวจพบว่าสถานะใน DB ระบุว่าพร็อกซีเคยทำงานอยู่

### บัฟเฟอร์เต็ม

เมื่อบัฟเฟอร์มีจำนวนรายการถึง `INSPECTOR_BUFFER_SIZE` (ค่าเริ่มต้นคือ 1000) รายการใหม่จะแทนที่รายการที่เก่าที่สุด หากคำขอสำคัญสูญหาย:

- เพิ่ม `INSPECTOR_BUFFER_SIZE` (เช่น 5000) — ใช้หน่วยความจำมากขึ้นเพื่อเก็บข้อมูลได้นานขึ้น
- บันทึกเซสชันเพื่อจัดเก็บช่วงข้อมูลที่เกี่ยวข้องลงใน DB อย่างถาวร
