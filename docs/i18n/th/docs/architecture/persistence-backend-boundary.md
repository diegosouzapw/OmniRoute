- **สถานะ:** เสนอ — ต้องได้รับการอนุมัติจากผู้ดูแลก่อนเริ่มงานด้านรันไทม์
- **ปัญหาที่ใช้ติดตาม:** [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075)
- **ขอบเขต:** เฉพาะสถาปัตยกรรมการจัดเก็บข้อมูลถาวร การตัดสินใจนี้ไม่ได้เพิ่มหรือเลือกฐานข้อมูลภายนอก

## บริบท

ปัจจุบัน OmniRoute นำเสนอฟังก์ชันการจัดเก็บข้อมูลถาวรที่จัดระเบียบตามโดเมนจาก `src/lib/db/` ขณะที่การเชื่อมต่อร่วมซึ่งส่งคืนโดย `src/lib/db/core.ts` ใช้งานสัญญา `SqliteAdapter` แบบซิงโครนัสใน `src/lib/db/adapters/types.ts` อะแดปเตอร์ดังกล่าวรองรับรันไทม์ SQLite หลายรูปแบบ แต่พื้นผิวของมันยังคงมีลักษณะเฉพาะของ SQLite ได้แก่ prepared statement แบบซิงโครนัส, `pragma`, ธุรกรรมแบบ deferred และ immediate, การสำรองข้อมูลแบบเนทีฟ/คัดลอกไฟล์, checkpoint และแฮนเดิลฐานข้อมูลภายในเครื่อง

เส้นทางการเริ่มต้นและการกู้คืนในปัจจุบันยังเป็นผู้ควบคุมวงจรชีวิตของไฟล์ SQLite ด้วย `src/lib/db/core.ts` จะระบุตำแหน่งของ `storage.sqlite`, ดูแลอะแดปเตอร์ส่วนกลางหนึ่งตัวต่อโปรเซส, ทำ checkpoint ให้ WAL, เก็บรักษาตารางที่เลือกไว้ระหว่างการกู้คืน และลบไฟล์ประกอบของ SQLite เมื่อสร้างฐานข้อมูลใหม่ การเลือกไดรเวอร์ใน `src/lib/db/adapters/driverFactory.ts` เป็นการเลือกระหว่างรันไทม์ SQLite ที่รองรับ ไม่ใช่นามธรรมสำหรับแบ็กเอนด์ภายนอก

การพัฒนาสคีมาก็ผูกติดอยู่ในลักษณะเดียวกัน `src/lib/db/migrationRunner.ts` ใช้ไฟล์ SQL ที่มีหมายเลขกำกับ, ตรวจสอบ `sqlite_master` และ `PRAGMA table_info`, ตรวจหาการรองรับ FTS5 ที่เป็นทางเลือก และเรียกใช้งานการย้ายข้อมูลภายในธุรกรรม SQLite โมดูลด้านปฏิบัติการ เช่น `src/lib/db/backup.ts` และ `src/lib/db/optimizationSettings.ts` ใช้ความหมายของการสำรองข้อมูล, `PRAGMA`, WAL, ขนาดเพจ, auto-vacuum และ `VACUUM` โดยตรง

คุณสมบัติเหล่านี้เหมาะสมสำหรับการติดตั้งใช้งาน SQLite แบบฝังตัว และควรยังคงพร้อมใช้งานโดยไม่บังคับให้ PostgreSQL หรือ MySQL จำลอง API ของ SQLite

## การตัดสินใจ

ใช้ขอบเขตการจัดเก็บข้อมูลถาวรแบบสองระดับสำหรับสถานะถาวรที่พกพาได้:

1. **สัญญาของรีโพซิทอรีโดเมน** กำหนดการดำเนินการด้านการจัดเก็บข้อมูลถาวรที่โค้ดธุรกิจและโค้ดการกำหนดเส้นทางต้องใช้ ผู้เรียกใช้งานขึ้นอยู่กับพฤติกรรมและข้อมูลของโดเมน ไม่ใช่ข้อความ SQL, prepared statement, ไฟล์ฐานข้อมูล หรือออบเจ็กต์ dialect
2. **สัญญาแบ็กเอนด์แบบอะซิงโครนัสภายใน** รองรับการใช้งานรีโพซิทอรีด้วยบริบทธุรกรรม, สถานะความพร้อมใช้งาน/ความพร้อมให้บริการ, การประสานงานการย้ายข้อมูล, ความสามารถของแบ็กเอนด์ และข้อผิดพลาดที่จำแนกประเภทแล้ว พื้นผิว TypeScript ที่แน่นอนจะถูกนำเสนอพร้อม PR การใช้งานแรกและพิสูจน์ด้วยการทดสอบความสอดคล้อง ADR นี้ตั้งใจไม่ตรึง API ที่ยังเป็นเพียงการคาดการณ์

SQLite ยังคงเป็นการใช้งานเริ่มต้น ลำดับการเลือกไดรเวอร์ SQLite ที่มีอยู่และ `SqliteAdapter` แบบซิงโครนัสจะยังคงอยู่หลังการใช้งานรีโพซิทอรี SQLite ขณะที่โดเมนต่าง ๆ ถูกย้ายทีละส่วนย่อยในแนวดิ่ง ผู้ใช้ไม่จำเป็นต้องกำหนดค่าบริการภายนอก

PostgreSQL เป็นการใช้งานภายนอกรายการแรกที่เสนอ หลังจากขอบเขตของรีโพซิทอรีได้รับการพิสูจน์กับ SQLite แล้ว MySQL จะตามมาในฐานะการใช้งานระดับเดียวกันโดยใช้ชุดการทดสอบความสอดคล้องเดียวกัน แทนที่จะเป็นการแยกตรรกะทางธุรกิจเป็นสายที่สอง

## กฎของขอบเขต

### พื้นผิวรีโพซิทอรีแบบพกพา

รีโพซิทอรีแบบพกพาอาจเปิดเผย:

- การอ่านและเขียนข้อมูลโดเมน;
- การดำเนินการแบบอะตอมที่ชัดเจนและการเข้าถึงรีโพซิทอรีภายในขอบเขตธุรกรรม;
- การดำเนินการเปรียบเทียบ/อัปเดตหรือ lease ในกรณีที่ความหมายด้านภาวะพร้อมกันเป็นส่วนหนึ่งของโดเมน;
- การแบ่งหน้า, การจัดลำดับ และข้อผิดพลาดจากข้อจำกัดที่ไม่ขึ้นกับแบ็กเอนด์

สถานะความพร้อมใช้งาน, ความพร้อมให้บริการ และการประสานงานการย้ายข้อมูลของแบ็กเอนด์อยู่ในสัญญาแบ็กเอนด์/ปฏิบัติการภายใน ไม่ใช่ในรีโพซิทอรีของแต่ละโดเมน

รีโพซิทอรีแบบพกพาต้องไม่เปิดเผย:

- `prepare`, `get`, `all`, `run` หรือแฮนเดิลไดรเวอร์โดยตรง;
- `PRAGMA`, โหมด checkpoint ของ WAL, `VACUUM` หรือการปรับแต่งเพจ/แคช;
- พาธไฟล์ SQLite, ไฟล์ประกอบ หรือการสำรองข้อมูลด้วยการคัดลอกไฟล์;
- `lastInsertRowid` ในฐานะสัญญาโดเมนข้ามแบ็กเอนด์;
- ไวยากรณ์ FTS5 หรือ `sqlite-vec`;
- ช่องทางเลี่ยงผ่าน dialect แบบทั่วไปที่โค้ดธุรกิจปกติใช้งาน

### พื้นผิวความสามารถของแบ็กเอนด์

พฤติกรรมเฉพาะของแบ็กเอนด์ยังคงถูกระบุอย่างชัดเจนและค้นพบได้ การบำรุงรักษาที่มีเฉพาะ SQLite จะยังคงอยู่หลังการใช้งานและอินเทอร์เฟซด้านปฏิบัติการของตนเอง ซึ่งรวมถึง:

- การเลือกไดรเวอร์รันไทม์;
- checkpoint ของ WAL และพฤติกรรมการปิด SQLite;
- การตั้งค่าขนาดเพจ, ขนาดแคช และ auto-vacuum;
- การสำรองข้อมูล, การคืนค่า และการกู้คืนไฟล์ฐานข้อมูล;
- การตรวจสอบโครงสร้างสคีมาของ SQLite;
- การผสานรวม FTS5 และ `sqlite-vec`

แบ็กเอนด์ภายนอกไม่จำเป็นต้องเลียนแบบคุณสมบัติเหล่านั้น รีโพซิทอรีต้องเลือกอย่างใดอย่างหนึ่งระหว่างใช้ความสามารถที่พกพาได้, จัดเตรียมการใช้งานเฉพาะแบ็กเอนด์พร้อมพฤติกรรมที่มีการบันทึกไว้ หรือรายงานว่าความสามารถนั้นไม่พร้อมใช้งาน

## โมเดลธุรกรรมและการย้ายข้อมูล

API ของรีโพซิทอรีเป็นผู้กำหนดการดำเนินการทางธุรกิจแบบอะตอมมิก ผู้เรียกใช้จะไม่เป็นผู้เลือกโหมดธุรกรรม SQL
การดำเนินการแต่ละรายการต้องกำหนดการรับประกันด้านการทำงานพร้อมกันที่สังเกตได้ ได้แก่ ค่าคงที่ที่ได้รับการปกป้อง การตรวจจับข้อขัดแย้ง
การจำแนกประเภทสำหรับการลองใหม่ ความคาดหวังด้าน idempotency และการส่งต่อบริบทธุรกรรม
การนำไปใช้งานอาจใช้กลไกธุรกรรมและระดับการแยกที่แตกต่างกันได้ เฉพาะเมื่อการรับประกันที่สังเกตได้เหล่านั้น
ยังคงเทียบเท่ากัน SQLite อาจใช้พฤติกรรมธุรกรรมแบบ deferred หรือ immediate ในปัจจุบัน
ต่อไปภายในได้ หากเป็นไปตามสัญญาของการดำเนินการนั้น

แบ็กเอนด์ภายนอกจำเป็นต้องกำหนดผู้รับผิดชอบการย้ายข้อมูลอย่างชัดเจน เพื่อป้องกันไม่ให้แอปพลิเคชันหลายเรพลิกาแข่งขันกัน
เปลี่ยนแปลงสคีมาเดียวกัน ประวัติการย้ายข้อมูลของแบ็กเอนด์อาจใช้หมุดหมายเชิงตรรกะร่วมกันได้ แต่จะไม่ถือว่าไฟล์ SQL
ของ SQLite สามารถพกพาหรือนำกลับมาใช้ใหม่กับไดอะเลกต์อื่นได้

## ความหมายของการปฏิบัติตามข้อกำหนดข้ามแบ็กเอนด์

การทดสอบการปฏิบัติตามข้อกำหนดต้องครอบคลุมพฤติกรรม ไม่ใช่เพียงซิกเนเจอร์ของเมธอดในรีโพซิทอรี แต่ละโดเมนที่ย้าย
ต้องกำหนดและตรวจสอบสิ่งต่อไปนี้:

- เขตเวลา ความละเอียด และการซีเรียลไลซ์ของการประทับเวลา;
- ความคาดหวังเกี่ยวกับการเรียงลำดับ `NULL` การเทียบเรียง และความไวต่อตัวพิมพ์เล็ก-ใหญ่;
- การแสดงผลและพฤติกรรมการเปรียบเทียบ JSON;
- ความละเอียดของจำนวนเต็ม ทศนิยม และจำนวนเงิน;
- การเรียงลำดับที่คงที่และเกณฑ์ตัดสินเมื่อค่าเท่ากันแบบกำหนดแน่นอนสำหรับการแบ่งหน้า;
- การสร้าง ID โดยไม่พึ่งพา row ID ของ SQLite;
- การจำแนกประเภทการละเมิดข้อกำหนดความเป็นเอกลักษณ์และ foreign key;
- พฤติกรรมของจำนวนแถวที่ได้รับผลกระทบสำหรับการดำเนินการแบบ no-op, compare/update และ delete;
- ผลลัพธ์ของการเขียนพร้อมกัน ข้อขัดแย้งที่สามารถลองใหม่ได้ และการลองใหม่แบบ idempotent

หากโดเมนไม่สามารถระบุความหมายที่สังเกตได้ซึ่งเทียบเท่ากันได้ แสดงว่ายังไม่สามารถพกพาได้ และต้องยังคง
เป็นแบบเฉพาะแบ็กเอนด์จนกว่าจะออกแบบสัญญาดังกล่าวเสร็จ

## ข้อกำหนดด้านความเข้ากันได้

การนำไปใช้งานใดๆ ที่เป็นไปตาม ADR นี้ต้องรักษาคุณสมบัติต่อไปนี้:

- SQLite ยังคงเป็นค่าเริ่มต้นที่ไม่ต้องกำหนดค่า
- ไฟล์ SQLite และประวัติการย้ายข้อมูลที่มีอยู่ยังคงสามารถอ่านได้
- ทางเลือกสำรองของ SQLite สำหรับ npm, Electron, Docker และรันไทม์ที่มีข้อจำกัด ยังคงใช้เส้นทางเริ่มต้นระบบในปัจจุบัน
- ข้อมูลประจำตัวของผู้ให้บริการที่จัดเก็บไว้ยังคงใช้พฤติกรรมการเข้ารหัสของแอปพลิเคชันที่มีอยู่
- การย้ายรีโพซิทอรีต้องไม่เปลี่ยนความหมายของการกำหนดเส้นทาง โควตา API key หรือการตรวจสอบโดยปริยาย
- มีการจัดทำเอกสารพฤติกรรมการสำรองและกู้คืนแยกตามแบ็กเอนด์ แทนที่จะนำเสนอว่าใช้ได้เหมือนกันทั้งหมด
- การติดตั้งแบบ SQLite เท่านั้นที่สะอาดหมดจดจะไม่โหลดหรือต้องใช้ไดรเวอร์ฐานข้อมูลภายนอก

## ลำดับการส่งมอบ

1. เผยแพร่รายการองค์ประกอบที่ผูกติดกับ SQLite ซึ่งสามารถทำซ้ำได้ เป็นสิ่งส่งมอบสำหรับการตรวจสอบแยกต่างหาก
2. เพิ่มสัญญารีโพซิทอรีของโดเมนแรกและการทดสอบการปฏิบัติตามข้อกำหนด
3. ปรับการนำ SQLite ที่มีอยู่ไปใช้งานให้อยู่เบื้องหลังสัญญาเหล่านั้น โดยไม่เปลี่ยนค่าเริ่มต้น
4. ภายใต้การอนุมัติของผู้ดูแล ให้เพิ่ม PostgreSQL เป็นการนำไปใช้งานภายนอกรายการแรกสำหรับส่วนย่อย
   ของ control plane ที่มีขอบเขตชัดเจน
5. ขยายสถานะที่ใช้ร่วมกันต่อเมื่อมีการทดสอบการเขียนพร้อมกันและผู้รับผิดชอบการย้ายข้อมูลแล้วเท่านั้น
6. เพิ่มเส้นทางการย้ายจาก SQLite ไปยังระบบภายนอกแบบออฟไลน์ที่ผ่านการตรวจสอบ ก่อนประชาสัมพันธ์ความสามารถในการสลับฐานข้อมูล
7. เพิ่ม MySQL โดยอิงกับสัญญารีโพซิทอรีและแบ็กเอนด์ที่ผ่านการพิสูจน์แล้ว

แต่ละขั้นตอนของรันไทม์ต้องเป็น PR แยกต่างหากที่สามารถตรวจสอบได้ ต้องไม่นำขั้นตอนภายหลังมาใช้เป็นเหตุผลเพื่อรวม
นามธรรมที่ยังไม่ผ่านการพิสูจน์จากขั้นตอนก่อนหน้า

## ส่วนแรกของการนำไปใช้

ควรเลือกส่วนแรกของรันไทม์หลังจากตรวจสอบรายการการเชื่อมโยงแล้ว การเชื่อมต่อกับผู้ให้บริการ
คีย์ API คอมโบ และการกำหนดค่าการกำหนดเส้นทางเป็นตัวเลือกที่เป็นไปได้ เนื่องจากตารางพื้นฐานขององค์ประกอบเหล่านี้
ปรากฏอยู่ใน `src/lib/db/core.ts` แต่ ADR นี้ไม่ได้อนุมัติรายการตารางหรือ PR สำหรับการย้ายข้อมูล
ส่วนดังกล่าวต้องประกอบด้วย:

- การทดสอบการคงพฤติกรรมเดิมของ SQLite;
- การทดสอบความสอดคล้องตามสัญญาของ repository;
- ขอบเขตของ transaction ที่กำหนดไว้อย่างชัดเจน;
- การตรวจสอบการเข้ารหัสและการปกปิดข้อมูลรับรองที่จัดเก็บไว้;
- ไม่มีการเปลี่ยนแปลงการกำหนดค่าการเริ่มต้นระบบเริ่มต้น

## ทางเลือกที่พิจารณา

### เพิ่ม PostgreSQL ไว้ภายใต้ `SqliteAdapter`

ไม่เลือกใช้ `SqliteAdapter` เป็นเลเยอร์ความเข้ากันได้สำหรับรันไทม์ SQLite และเปิดเผย
การดำเนินการเฉพาะของ SQLite การจำลองอินเทอร์เฟซดังกล่าวจะทำให้สมมติฐานเกี่ยวกับการทำงานแบบซิงโครนัส
และสมมติฐานเฉพาะของภาษาถิ่น SQL รั่วไหลเข้าสู่แบ็กเอนด์ใหม่

### เปิดเผย API สำหรับ query/execute แบบทั่วไปให้กับทุกโดเมน

ไม่เลือกใช้เป็นขอบเขตหลัก แม้จะรวมศูนย์การจัดการการเชื่อมต่อ แต่ยังคงทิ้งการเชื่อมโยงกับภาษาถิ่น SQL,
transaction และตารางไว้ในโมดูลธุรกิจ primitive ระดับล่างของแบ็กเอนด์อาจมีอยู่ภายใน
การนำ repository ไปใช้ แต่ไม่ควรเป็น API การจัดเก็บข้อมูลที่แอปพลิเคชันเรียกใช้โดยตรง

### เขียนระบบจัดเก็บข้อมูลทั้งหมดใหม่ก่อนตรวจสอบความถูกต้องของส่วนใดส่วนหนึ่ง

ไม่เลือกใช้ พื้นผิวของระบบจัดเก็บข้อมูลในปัจจุบันครอบคลุมในวงกว้าง รวมถึงวงจรชีวิตของไฟล์ การกู้คืน การค้นหา
และการตั้งค่าการดำเนินงาน การแบ่งเป็นส่วนแนวตั้งช่วยให้สามารถตรวจสอบพฤติกรรมและกำหนดขอบเขตการย้อนกลับได้

### แทนที่ SQLite ในฐานะค่าเริ่มต้น

ไม่เลือกใช้ การติดตั้งใช้งานแบบฝังตัวและบนเดสก์ท็อปพึ่งพารูปแบบการเริ่มต้นระบบปัจจุบันที่ไม่ต้องใช้บริการเพิ่มเติม
แบ็กเอนด์ภายนอกเป็นตัวเลือกแบบสมัครใจ

### ใช้ Redis เป็นแหล่งข้อมูลถาวรหลัก

ไม่เลือกใช้ Redis อาจรองรับการประสานงานแบบชั่วคราว แคช หรือตัวนับที่กำหนดไว้อย่างชัดเจน
แต่ไม่สามารถแทนที่สัญญา repository สำหรับข้อมูลถาวรที่อธิบายไว้ที่นี่ได้

## ผลที่ตามมา

### ผลเชิงบวก

- โค้ดธุรกิจมีจุดเชื่อมต่อกับระบบจัดเก็บข้อมูลที่เสถียรและไม่ขึ้นกับภาษาถิ่นของฐานข้อมูล
- พฤติกรรมของ SQLite ได้รับการทดสอบก่อนที่แบ็กเอนด์ภายนอกจะเป็นตัวกำหนด abstraction
- PostgreSQL และ MySQL ใช้สัญญาและการทดสอบร่วมกัน แทนการทำตรรกะโดเมนซ้ำ
- ความสามารถเฉพาะของ SQLite ยังคงเป็นความสามารถระดับแนวหน้า แทนที่จะกลายเป็น compatibility shim ที่ทำให้รายละเอียดภายในรั่วไหล
- พฤติกรรมของการย้ายข้อมูลและ transaction แบบหลาย replica กลายเป็นข้อพิจารณาด้านการออกแบบที่ชัดเจน

### ต้นทุนและความเสี่ยง

- การแยก repository ออกมาต้องย้าย call site แบบค่อยเป็นค่อยไป
- ขอบเขตแบบ async อาจแพร่กระจายไปยังโค้ดบริการที่ปัจจุบันทำงานแบบซิงโครนัส
- ความหมายเชิงพฤติกรรมระหว่างแบ็กเอนด์ต้องใช้การทดสอบความสอดคล้องตามสัญญาที่มากกว่าความเข้ากันได้ของไวยากรณ์ SQL
- การสำรองข้อมูล การค้นหา พื้นที่จัดเก็บเวกเตอร์ และการบำรุงรักษายังคงขึ้นอยู่กับความสามารถเฉพาะ
- การใช้งานระบบจัดเก็บข้อมูลมากกว่าหนึ่ง implementation เพิ่มต้นทุนของ CI และการสนับสนุนด้านปฏิบัติการ

## สิ่งที่ไม่ใช่เป้าหมาย

ADR นี้จะไม่:

- เพิ่ม dependency ของฐานข้อมูล ตัวแปรสภาพแวดล้อม schema หรือ migration;
- เปลี่ยน singleton ของ SQLite ที่ใช้งานจริงหรือ driver cascade;
- รับประกันการรองรับ PostgreSQL หรือ MySQL ในรีลีสใดรีลีสหนึ่ง;
- ทำให้ FTS5, `sqlite-vec`, ไฟล์สำรองข้อมูล หรือการบำรุงรักษา SQLite สามารถพกพาข้ามระบบได้;
- กำหนดความพร้อมแบบ active-active ก่อนที่จะมีการทดสอบสถานะร่วมและการประสานงาน;
- อนุมัติการเขียน `src/lib/db/` ใหม่ทั้งหมดในครั้งเดียว

## คำถามที่ยังต้องรอการอนุมัติจากผู้ดูแล

1. แนวทางที่ต้องการคือการใช้ repository ร่วมกับขอบเขต backend แบบ async ภายในใช่หรือไม่ หรือควรให้การจัดเก็บข้อมูลภายนอกอยู่เบื้องหลังบริการ control-plane แยกต่างหาก?
2. PostgreSQL เป็นที่ยอมรับได้หรือไม่ในฐานะ implementation ภายนอกตัวแรกหลังจากตรวจสอบความสอดคล้องกับ SQLite แล้ว?
3. domain ใดควรเป็น repository slice แบบมีขอบเขตลำดับแรก?
4. state ใดต้องใช้ร่วมกันสำหรับ milestone แรกที่รองรับหลาย replica และ state ใดยังคงเป็นแบบเฉพาะ node?
5. จำเป็นต้องมีช่วงเวลาความเข้ากันได้แบบใดสำหรับการ migration ของ repository ที่ถูกขัดจังหวะหรือ rollback?

จนกว่าคำถามเหล่านี้จะได้รับข้อสรุป เอกสารนี้ถือเป็นข้อเสนอเท่านั้น และไม่ได้หมายความว่าจะมีการ refactor runtime ใดๆ
