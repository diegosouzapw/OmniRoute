รีเลย์ (Vercel, Deno, Cloudflare) จะยุติการเชื่อมต่อต้นทางบนแบ็กเอนด์แบบ
serverless เพื่อให้ OmniRoute ส่งทราฟฟิกขาออกจากภูมิภาคที่เสถียรได้ พร้อมกับเก็บ
คีย์ API ของผู้ให้บริการไว้ฝั่งเซิร์ฟเวอร์ เอกสารนี้อธิบายโหมดความล้มเหลวสองแบบ
ที่ผู้ดูแลระบบพบในการใช้งานจริง และแนวทางการกู้คืนที่ OmniRoute จัดเตรียมไว้
สำหรับแต่ละกรณี

## วิธีจัดเก็บข้อมูลยืนยันตัวตนของรีเลย์

เมื่อคุณปรับใช้รีเลย์จาก **การตั้งค่า → พูลพร็อกซี → ปรับใช้รีเลย์**
ขั้นตอนการปรับใช้จะจัดเก็บโทเค็นยืนยันตัวตนของรีเลย์ไว้ในฟิลด์ JSON `notes`
ของพร็อกซี:

- หากกำหนด `STORAGE_ENCRYPTION_KEY` ไว้ โทเค็นจะถูกเขียนเป็น `relayAuthEnc`
  (เข้ารหัสด้วย AES ขณะจัดเก็บ)
- มิฉะนั้น โทเค็นจะถูกเขียนเป็นข้อความธรรมดาใน `relayAuth`

ขณะส่งคำขอ `extractRelayAuth(notes)` จะคืนค่ารูปแบบใดก็ตามที่มีอยู่
ดังนั้นรีเลย์จึงยังคงทำงานได้หลังจากรีสตาร์ต

## โหมดความล้มเหลว 1 — ไม่สามารถถอดรหัสโทเค็นได้หลังหมุนเวียนคีย์

**อาการ:** รีเลย์ที่เคยทำงานได้ก่อนหน้านี้เริ่มส่งคืนข้อผิดพลาด `401`/การยืนยันตัวตน
จากต้นทาง หลังจากหมุนเวียน `STORAGE_ENCRYPTION_KEY` ในสภาพแวดล้อมหรือ
ระบบจัดการข้อมูลลับ บล็อบ `relayAuthEnc` ที่จัดเก็บไว้ไม่สามารถถอดรหัสได้อีก
ดังนั้น `extractRelayAuth` จึงคืนค่าสตริงว่าง และรีเลย์ไม่ส่งข้อมูลยืนยันตัวตน

**การกู้คืน — ซ่อมแซม ณ ตำแหน่งเดิม (ไม่ต้องปรับใช้ใหม่):**

1. เปิด **การตั้งค่า → พูลพร็อกซี**
2. แถวรีเลย์ที่ไม่มีข้อมูลยืนยันตัวตนจะแสดงป้าย `auth missing` สีเหลืองและปุ่ม
   **ซ่อมแซม**
3. คลิก **ซ่อมแซม** OmniRoute จะเรียก
   `POST /api/settings/proxies/[id]/repair-relay` ซึ่งจะ:
   - ถอดรหัส `relayAuthEnc` ด้วยคีย์ **ปัจจุบัน**
   - เขียน `relayAuth` แบบข้อความธรรมดากลับเข้าไปใน `notes`
   - คืนค่า `{ repaired: true, mode: "recovered" }`

รีเลย์จะกลับมาให้บริการต่อได้โดยไม่ต้องป้อนข้อมูลประจำตัวสำหรับการปรับใช้อีกครั้ง

วิธีนี้ใช้ได้เฉพาะเมื่อ `STORAGE_ENCRYPTION_KEY` ปัจจุบันยังสามารถถอดรหัส
บล็อบได้ หากคุณหมุนเวียนคีย์ **โดยไม่มี** การย้ายข้อมูล บล็อบดังกล่าวจะ
ไม่สามารถกู้คืนได้

## โหมดความล้มเหลว 2 — โทเค็นไม่สามารถกู้คืนได้ (คีย์เดิมถูกหมุนเวียนออกไป)

**อาการ:** คุณคลิก **ซ่อมแซม** แล้วได้รับ
`{ repaired: false, mode: "redeploy", status: 409 }`

**การกู้คืน — ปรับใช้ใหม่:**

โทเค็นที่จัดเก็บไว้ไม่สามารถกู้คืนด้วยคีย์ปัจจุบันได้ ให้ปรับใช้รีเลย์ใหม่
จากหน้าต่างเดียวกับที่คุณใช้ในตอนแรก (เมนู **ปรับใช้รีเลย์** → Vercel / Deno
/ Cloudflare) ขั้นตอนการปรับใช้จะเขียนโทเค็นใหม่ (เข้ารหัสด้วยคีย์ปัจจุบัน)
และป้าย `auth missing` ในแถวนั้นจะหายไป

ใน UI ปุ่ม **ซ่อมแซม** จะเปิดหน้าต่างปรับใช้ใหม่โดยอัตโนมัติเมื่อ
ไม่สามารถกู้คืนโทเค็นได้ คุณจึงไม่ต้องค้นหาหน้าต่างดังกล่าวด้วยตนเอง

## โหมดความล้มเหลว 3 — เข้าถึงรีเลย์ได้แต่รีเลย์ไม่สมบูรณ์

**อาการ:** การทดสอบพร็อกซี (ปุ่ม `speed`) แสดงว่ารีเลย์พร้อมใช้งาน แต่คำขอ
ยังคงล้มเหลวเป็นระยะ

ตรวจสอบส่วนหัวที่บ่งบอกสถานะของรีเลย์ซึ่งส่งคืนโดยโพรบการทดสอบอัตโนมัติ
ของ OmniRoute (ดู **การตั้งค่า → พูลพร็อกซี** และตัวนับ `relayTested` /
`relayAlive`):

- `x-relay-url` — แบ็กเอนด์รีเลย์ใดเป็นผู้ตอบกลับ
- `x-relay-mode` — `ts` | `bifrost` | `auto` สำหรับคำขอนั้น
- `x-relay-attempts` — มีการลองฮ็อปรีเลย์กี่ครั้งก่อนสำเร็จ
- `x-relay-fallback` — เป็น `true` เมื่อคำขอเปลี่ยนจากแบ็กเอนด์ที่ต้องการ
  ไปใช้รีเลย์ TypeScript สำรอง

อัตรา `x-relay-fallback` ที่สูงร่วมกับค่า `relayAlive` ที่ต่ำ หมายความว่า
แบ็กเอนด์ sidecar ไม่สมบูรณ์ และคุณควรแก้ไขหรือเปลี่ยนกลยุทธ์แบ็กเอนด์รีเลย์
เป็น `ts` (ดู `RELAY_BACKEND_STRATEGY.md`)

## เอกสารอ้างอิง API

| เมธอด  | พาธ                                       | เนื้อหาคำขอ             | สำเร็จ                                                                                                                                    | ล้มเหลว                                                                              |
| ------ | ----------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` เมื่อสร้างค่าใหม่สำเร็จ; `200 { repaired: false, mode: "noop" }` เมื่อมีข้อความธรรมดาอยู่แล้ว | `409 { mode: "redeploy" }` ไม่สามารถกู้คืนได้; `400` ไม่ใช่ประเภทรีเลย์; `404` ไม่พบ |

เส้นทางรายการ `GET /api/settings/proxies` จะแนบ
`relayInfo: { isRelay, authMissing, repairMode }` ที่ไม่มีข้อมูลลับไปกับแต่ละรายการ
เพื่อให้แดชบอร์ดสามารถแสดงตัวเลือกการซ่อมแซมได้โดยไม่เปิดเผยโทเค็นเลย
