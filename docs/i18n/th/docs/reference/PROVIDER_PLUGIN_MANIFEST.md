`open-sse/config/providerPluginManifest.ts` กำหนดสัญญาปลั๊กอินผู้ให้บริการที่ปลอดภัยสำหรับ JSON
`open-sse/config/providerPluginManifestRegistry.ts` เชื่อมโยงสัญญาดังกล่าวกับรีจิสทรี
ผู้ให้บริการปัจจุบันสำหรับ sidecar เช่น Bifrost, CLIProxyAPI หรือเราเตอร์ Go/Rust ในอนาคต
รีจิสทรี TypeScript ยังคงเป็นแหล่งข้อมูลหลัก แต่ sidecar สามารถใช้ manifest ได้โดยไม่ต้องนำเข้า
โค้ด executor, ค่าเริ่มต้น OAuth, header หรือสถานะ environment ของ process

manifest เดียวกันนี้พร้อมใช้งานผ่าน HTTP ที่
`GET /api/v1/provider-plugin-manifest` สำหรับ sidecar ที่ทำงานแยก process

OmniRoute แจ้ง URL ดังกล่าวแก่ Bifrost และ CLIProxyAPI ผ่าน request header
`X-OmniRoute-Provider-Manifest-Url` ให้ตั้งค่า
`OMNIROUTE_PROVIDER_MANIFEST_URL` เมื่อ sidecar ต้องใช้ URL สาธารณะหรือ URL บนเครือข่าย
container แทน origin ของ request ภายในเครื่อง

## การรีเฟรช Manifest

HTTP endpoint จะส่งคืน `Cache-Control: public, max-age=60` และ
`ETag` แบบ strong โดย sidecar ควรเก็บ manifest ล่าสุดที่ผ่านการตรวจสอบแล้ว และส่ง ETag
ของ manifest นั้นใน `If-None-Match` เมื่อรีเฟรช response `304 Not Modified` จะไม่มี body;
sidecar จะใช้ manifest ที่ cache ไว้ต่อไป หากไม่มี manifest ที่ผ่านการตรวจสอบและ cache ไว้
sidecar ต้องส่ง request แบบไม่มีเงื่อนไข แทนที่จะยอมรับ `304`

## เป้าหมาย

ย้าย metadata ของผู้ให้บริการไปสู่สัญญาปลั๊กอิน เพื่อให้เส้นทาง request ที่มีการใช้งานสูง
สามารถอยู่ภายใต้การดูแลของ sidecar ที่มี latency ต่ำกว่าได้ในอนาคต ขณะที่ OmniRoute ยังคงใช้
route ของ TypeScript เป็นด่านบังคับใช้นโยบายและ fallback โดย manifest เป็นเพียงส่วนเสริม:
ตัวมันเองไม่ได้เปลี่ยนแปลงการกำหนดเส้นทาง request

## สัญญา

manifest ประกอบด้วย:

- id และ alias ของผู้ให้บริการ
- รูปแบบ upstream และชื่อ executor
- ประเภท auth, auth header และ auth prefix ซึ่งเป็นค่าที่ไม่บังคับ
- metadata ของ endpoint แบบคงที่
- คุณสมบัติในการใช้งานกับ sidecar และเหตุผลที่ชัดเจนเมื่อผู้ให้บริการควรอยู่บน TS ต่อไป
- metadata ของโมเดลที่ปลอดภัยสำหรับ JSON เช่น ความยาว context, flag สำหรับ vision/reasoning และ
  param ที่ไม่รองรับ
- tag ความสามารถ ได้แก่ `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` และ `usage-supported`

manifest ตั้งใจไม่รวมสิ่งต่อไปนี้:

- client secret ของ OAuth และค่า secret เริ่มต้น
- การ resolve environment ขณะ runtime
- request header และ helper สำหรับ credential สาธารณะ
- ตัวสร้าง URL แบบ dynamic
- ฟังก์ชัน executor
- รายละเอียดภายในของ session pool

## Tag ความสามารถ

`capabilities` เป็น array ของ tag ที่เรียงลำดับแล้วและได้มาจาก entry ในรีจิสทรี ผู้ผสานรวม
ควรใช้ข้อมูลนี้เป็นคำตอบที่เครื่องอ่านได้สำหรับคำถามว่า "ผู้ให้บริการนี้ทำอะไรได้บ้าง" แทนการ
อ่าน source ของ TypeScript ซ้ำ

| Tag                  | ความหมาย                                                                    |
| -------------------- | --------------------------------------------------------------------------- |
| `apikey`             | ยอมรับ API key (`authType` เป็น `apikey` หรือ `optional`)                   |
| `oauth`              | ใช้ flow แบบ OAuth หรือ session                                             |
| `responses`          | เปิดเผย base URL ของ OpenAI Responses API                                   |
| `passthrough-models` | ให้บริการโมเดลจาก upstream โดยตรง แทน catalog แบบคงที่                      |
| `custom-executor`    | เรียกใช้ executor ที่ไม่ใช่ค่าเริ่มต้น จึงคงอยู่บนเส้นทาง TypeScript        |
| `sidecar-candidate`  | สะท้อนค่า `sidecar.eligible` — ปลอดภัยสำหรับการพิจารณานำเข้าใน sidecar      |
| `usage-fetch`        | มีตัวดึงข้อมูลการใช้งานหรือโควตาที่เชื่อมต่อไว้แล้ว (`getUsageForProvider`) |
| `usage-supported`    | usage API ยอมรับผู้ให้บริการนี้ (`isSupportedUsageConnection`)              |

`usage-fetch` ใช้สำหรับการค้นพบเท่านั้น โดยรายงานว่า OmniRoute รู้วิธีอ่านข้อมูลการใช้งานของ
ผู้ให้บริการ แต่ไม่ได้เปิดใช้งานการดึงข้อมูล เปลี่ยน semantics ของโควตา หรือบ่งชี้ว่า widget
โควตาใน Dashboard เปิดใช้งานสำหรับผู้ให้บริการ — widget ดังกล่าวถูกควบคุมแยกต่างหากด้วย
`USAGE_SUPPORTED_PROVIDERS` แหล่งข้อมูลหลักคือ `USAGE_FETCHER_PROVIDERS` ใน
`open-sse/services/usage/fetcherProviders.ts`

รายการดังกล่าวใช้ string ที่ usage dispatcher ยอมรับเป็น key จึงมีทั้ง canonical id
และ alias ปะปนกัน และมีความยาวมากกว่าจำนวนผู้ให้บริการที่ติด tag เล็กน้อย: entry ที่ไม่ใช่
ผู้ให้บริการ chat ในรีจิสทรี manifest (เช่น ผู้ให้บริการค้นหา `firecrawl`
และผู้ให้บริการ ACP `amazon-q`) จะไม่มี entry ใน manifest สำหรับติด tag

`usage-supported` ตอบว่า route การใช้งานของ server และ Dashboard ยอมรับ connection
สำหรับผู้ให้บริการหรือไม่ โดยสะท้อนค่า `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
และ `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) ซึ่งทั้งคู่ควบคุมโดย
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) ต่างจาก
`usage-fetch` ตรงที่ tag นี้ถูกสร้างจาก id ของผู้ให้บริการเท่านั้น — runtime guard ใช้
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` โดยไม่มีการ resolve alias ดังนั้น manifest
จึงใช้กฎเดียวกัน tag ทั้งสองมีขอบเขตต่างกัน: มีผู้ให้บริการ 3 รายที่มีเฉพาะ
`usage-fetch` (`opencode`, `opencode-zen`, `xai`) และ 1 รายที่มีเฉพาะ
`usage-supported` (`xiaomi-mimo-token-plan`) ดังนั้น tag หนึ่งจึงไม่ได้บ่งชี้ว่าต้องมีอีก tag หนึ่งด้วย

## การใช้งาน Sidecar

Sidecar ควรถือว่า `sidecar.eligible` เป็นสัญญาณระบุผู้สมัครแบบระมัดระวัง ไม่ใช่การตัดสินใจกำหนดเส้นทางโดยไม่มีเงื่อนไข เป้าหมายแรกสำหรับการนำเข้าควรเป็นผู้ให้บริการที่ใช้ API key และ endpoint แบบคงที่ โดยใช้ executor เริ่มต้น ส่วนผู้ให้บริการที่มี web executor แบบกำหนดเอง, โฟลว์ OAuth/เซสชัน, ตัวสร้าง URL แบบไดนามิก หรือการกำหนดค่า pool ให้ใช้เส้นทางสำรองของ TypeScript ต่อไป จนกว่า sidecar จะรองรับพฤติกรรมที่เทียบเท่ากัน และข้อมูล telemetry ยืนยันว่าทำงานได้เทียบเท่า

ระยะการย้ายระบบที่แนะนำ:

1. สร้างและตรวจสอบความถูกต้องของ manifest สำหรับปลั๊กอินผู้ให้บริการจากรีจิสทรี TS
2. ปรับให้ Bifrost หรือ CLIProxyAPI สามารถนำเข้า manifest สำหรับผู้ให้บริการที่ใช้ API key/endpoint แบบคงที่
3. กำหนดเส้นทางให้ผู้ให้บริการที่เข้าเกณฑ์ผ่าน sidecar โดยควบคุมด้วย `OMNIROUTE_RELAY_BACKEND` พร้อมเปิดใช้งานเส้นทางสำรอง TS ไว้
4. เลื่อนสถานะผู้ให้บริการเมื่ออัตราความสำเร็จ, latency p99, พฤติกรรมการสตรีม และการจัดการพารามิเตอร์ที่ไม่รองรับ ตรงกับเส้นทาง TS แล้วเท่านั้น
5. เพิ่มปลั๊กอินแบบเนทีฟสำหรับ sidecar ให้กับ executor แบบกำหนดเอง ครั้งละหนึ่งตระกูลผู้ให้บริการ

## เหตุใดจึงไม่ควรฝังผู้ให้บริการไว้ใน Next โดยตรง

Frontend ของ Next ไม่ควรรับผิดชอบการประมวลผลของผู้ให้บริการ แต่ควรเรียกผ่านขอบเขต API จากนั้น backend จึงตัดสินใจได้ว่าจะใช้ executor ของ TypeScript, Bifrost, CLIProxyAPI หรือ sidecar แบบเนทีฟในอนาคต แนวทางนี้ช่วยรวมศูนย์การลงนามคำขอ, การตรวจสอบ allowlist, นโยบาย DB และพฤติกรรมการสำรองไว้ก่อนส่งต่องานไปยัง sidecar ใดๆ
