## ภาพรวม

เส้นทาง API สำหรับการจัดการ OmniRoute ทั้งหมดจะถูกจัดประเภทให้อยู่ในระดับการป้องกัน
หนึ่งในสามระดับ การจัดประเภทนี้เป็นแบบคงที่ โดยกำหนดไว้ใน `src/server/authz/routeGuard.ts`
และได้รับการประเมินก่อนที่สาขาการตรวจสอบสิทธิ์อื่นใดจะทำงาน

## ระดับการป้องกัน

### ระดับ 1 — LOCAL_ONLY

**บังคับใช้โดย:** `isLocalOnlyPath(path)` → การตรวจสอบโฮสต์แบบลูปแบ็ก
**การข้ามข้อจำกัด:** โดยค่าเริ่มต้นไม่มีข้อยกเว้น มีข้อยกเว้นแบบจำกัดสำหรับเส้นทางใน
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` เมื่อคำขอมี API key ที่ถูกต้อง
พร้อมขอบเขต `manage` (ดู [ข้อยกเว้นสำหรับขอบเขต Manage](#manage-scope-carve-out))

เส้นทางเหล่านี้สร้างโพรเซสลูกหรือเรียกใช้โค้ดรันไทม์ การเปิดให้ทราฟฟิก
ที่ไม่ได้มาจากลูปแบ็กเข้าถึงเส้นทางเหล่านี้ จะทำให้ผู้โจมตีที่ได้รับ JWT ที่ถูกต้อง (เช่น
ผ่านทันเนล Cloudflared/Ngrok) สามารถสั่งให้สร้างโพรเซสได้ ซึ่งเป็นช่องโหว่
ประเภท CVE ที่เป็นที่รู้จัก ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))

**GHSA-fhh6-4qxv-rpqj คืออะไร (ประเภทการโจมตี):** เซิร์ฟเวอร์สำหรับการจัดการ/เอเจนต์
เปิดเผยเอนด์พอยต์ที่เรียกใช้โพรเซสย่อย (`npm install`, `node`, เบราว์เซอร์,
พร็อกซี, `git`, `tar`, …) หากเอนด์พอยต์ดังกล่าวสามารถเข้าถึงได้จากภายนอกโฮสต์
เนื่องจากผู้ดูแลนำ OmniRoute ไปไว้หลังทันเนล nginx/Cloudflare/Tailscale และ JWT
รั่วไหล หรือกำหนดค่าการตรวจสอบสิทธิ์ไม่ถูกต้อง ผู้โจมตีจะเปลี่ยนจาก "เรียก API" เป็น
"เรียกใช้คำสั่งบนโฮสต์" (การเรียกใช้โค้ดจากระยะไกล) OmniRoute ปิดช่องโหว่นี้ด้วยการบังคับใช้
**การตรวจสอบโฮสต์แบบลูปแบ็กโดยไม่มีเงื่อนไข ก่อนการตรวจสอบสิทธิ์ใดๆ** กับทุก
เส้นทางที่สามารถสร้างโพรเซสได้ ดังนั้นโทเค็นที่รั่วไหลผ่านทันเนลก็ยังไม่สามารถเข้าถึงการสร้างโพรเซสได้

**ชุด LOCAL_ONLY ทั้งหมด** แหล่งข้อมูลอ้างอิงหลักคือ
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ใน
`src/server/authz/routeGuard.ts`; ตารางด้านล่างสะท้อนสถานะปัจจุบัน เกต
`check-route-guard-membership` จะแจกแจง `route.ts` ทุกไฟล์ภายใต้
คำนำหน้าเส้นทางที่สามารถสร้างโพรเซสได้ และทำให้ CI ล้มเหลวหากมีเส้นทางใดไม่ได้รับการจัดประเภทเป็น local-only

#### ข้อยกเว้นสำหรับขอบเขต manage

เส้นทาง LOCAL_ONLY บางส่วนอาจเข้าถึงจากที่อยู่ซึ่งไม่ใช่ loopback ได้เช่นกัน ก็ต่อเมื่อ
คำขอมี `Authorization: Bearer <api-key>` ซึ่งข้อมูลเมตารวมขอบเขต
`manage` (หรือ `admin`) ข้อยกเว้นนี้ต้องเปิดใช้งานอย่างชัดเจนเป็นรายเส้นทางผ่าน
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` เพื่อให้ค่าเริ่มต้นสำหรับเส้นทาง
LOCAL_ONLY ใหม่ยังคงบังคับใช้เฉพาะ loopback อย่างเคร่งครัด คำขอที่ไม่ผ่านการยืนยันตัวตน
และคำขอที่ใช้คีย์ซึ่งไม่มีขอบเขต manage จะยังคงถูกปฏิเสธด้วย
`403 LOCAL_ONLY`

ปัจจุบัน prefix เดียวที่อนุญาตให้ข้ามข้อจำกัดได้คือ `/api/mcp/` ส่วน `/api/cli-tools/runtime/` และ
`/api/services/` ถูกยกเว้นโดยเจตนา เนื่องจากสามารถสร้าง subprocess ใดๆ ก็ได้
(`npm install`, `node`) ซึ่งตรงกับประเภท CVE ที่ระดับ
LOCAL_ONLY ถูกสร้างขึ้นมาเพื่อป้องกันโดยเฉพาะ

**#7895 — ขอบเขตแบบจำกัดของ `mcp:connect`:** ข้อยกเว้นของ `/api/mcp/` ยังยอมรับ
Bearer key ที่มีขอบเขตแบบจำกัด `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`) โดยตรวจสอบผ่าน
`hasMcpConnectOrManageScope()` ใน `src/server/authz/policies/management.ts`
ขอบเขตนี้จำกัดไว้สำหรับ `/api/mcp/` เท่านั้น — `mcp:connect` ไม่ให้สิทธิ์ใดๆ บน
เส้นทางการจัดการอื่น (รวมถึง prefix สำหรับข้ามข้อจำกัดของ LOCAL_ONLY อื่นทั้งหมด หากมีการเพิ่ม
ในอนาคต) และถูกแยกออกจาก `MANAGEMENT_API_KEY_SCOPES` โดยเจตนา
คีย์ที่มี `manage`/`admin` ยังคงผ่านข้อยกเว้นได้เหมือนเดิมทุกประการ ส่วน
`mcp:connect` เป็นทางเลือกที่มีสิทธิ์ต่ำกว่าสำหรับผู้เรียกใช้จากระยะไกลที่ใช้งานเฉพาะ MCP
ซึ่งไม่ควรต้องมีสิทธิ์การจัดการแบบกว้าง

| คำขอ                                                    | เส้นทาง                    | ผลลัพธ์          |
| ------------------------------------------------------- | -------------------------- | ---------------- |
| ไม่ใช่ loopback, ไม่มี Bearer                           | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| ไม่ใช่ loopback, Bearer ที่มีขอบเขต `manage`            | `/api/mcp/*`               | อนุญาต           |
| ไม่ใช่ loopback, Bearer ที่มีขอบเขต `mcp:connect`       | `/api/mcp/*`               | อนุญาต           |
| ไม่ใช่ loopback, Bearer ที่ไม่มี `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| ไม่ใช่ loopback, Bearer ที่มีขอบเขต `mcp:connect`       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| ไม่ใช่ loopback, Bearer ที่มีขอบเขต `manage`            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| Loopback, มี/ไม่มี Bearer ก็ได้                         | LOCAL_ONLY ใดๆ             | อนุญาต (ผ่านเกต) |

#### คำแนะนำสำหรับผู้ดูแลระบบและการตรวจสอบ

หากคุณใช้งาน OmniRoute หลัง reverse proxy หรือ tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) การตรวจสอบ loopback จะยังคงปกป้องเส้นทางที่สามารถ
สร้างโปรเซสข้างต้นได้ — คำขอที่มีที่อยู่ไคลเอนต์ซึ่งไม่ใช่ loopback จะถูกปฏิเสธด้วย
`403 LOCAL_ONLY` **ก่อนดำเนินการยืนยันตัวตน** ดังนั้น JWT ที่รั่วไหลจึงไม่สามารถ
เข้าถึงการสร้างโปรเซสได้ ผู้ดูแลระบบยังคงมีหน้าที่รับผิดชอบสองประการ:

- **อย่า "แก้ไข" 403 ด้วยการปลอม IP ของไคลเอนต์ให้เป็น loopback** การตั้งค่า
  `X-Forwarded-For: 127.0.0.1` หรือการใช้พร็อกซีที่เขียนที่อยู่ต้นทางใหม่ให้เป็น
  loopback จะเปิดช่องโหว่ประเภท RCE ที่ระดับนี้ปิดไว้ขึ้นมาอีกครั้ง ให้เปิดเผย
  แดชบอร์ด/API ผ่านพร็อกซี — ห้ามเปิดเผยเส้นทางที่สามารถสร้างโปรเซสโดยเด็ดขาด
- **รักษาข้อยกเว้นสำหรับขอบเขต manage ให้เหลือน้อยที่สุด** เฉพาะ `/api/mcp/` เท่านั้นที่ข้ามข้อจำกัดได้ และ
  ต้องใช้ API key ที่มีขอบเขต `manage` เท่านั้น `SPAWN_CAPABLE_PREFIXES` ไม่สามารถ
  เพิ่มลงในรายการข้ามข้อจำกัดได้ — สคีมา zod จะปฏิเสธ และ
  `isLocalOnlyBypassableByManageScope` จะปฏิเสธขณะรันไทม์ (การป้องกันเชิงลึก)
  ซึ่งเป็นความหมายของข้อความ "ไม่สามารถทำให้ข้ามข้อจำกัดได้" บนแดชบอร์ด เส้นทางที่สามารถ
  สร้างโปรเซสซึ่งมีเซกเมนต์แบบไดนามิกและเส้นทางแบบคงที่ภายใต้ `/api/providers/` (เช่น `/login`,
  `/refresh-cursor`) ครอบคลุมโดยคู่ประกอบที่อิง regex ได้แก่ `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ใน
  `src/shared/constants/spawnCapablePrefixes.ts` ไม่ใช่อาร์เรย์แบบแบน
  `SPAWN_CAPABLE_PREFIXES` — อาร์เรย์แบบแบนจะต้องครอบคลุม prefix
  `/api/providers/` ทั้งหมดเพื่อให้ตรวจจับเส้นทางเหล่านี้ได้ ซึ่งจะทำให้ขอบเขตของโครงสร้างเส้นทาง
  กว้างเกินไปสำหรับแดชบอร์ดระยะไกลที่ต้องใช้งาน CRUD ของผู้ให้บริการอย่างถูกต้อง

**การตรวจสอบการเข้าถึง** — เพื่อตรวจสอบว่าไม่มีสิ่งใดจากภายนอกโฮสต์เข้าถึงเส้นทางเหล่านี้:

- เปิด **Authorization Inventory** ที่ `/dashboard/settings/security`: หน้านี้จะแสดงรายการคำนำหน้า LOCAL_ONLY ที่ใช้งานอยู่แบบเรียลไทม์ คำนำหน้าใดบ้างที่สามารถข้ามการตรวจสอบได้ และชุดที่สามารถ spawn ได้ซึ่งกำหนดไว้ตอนคอมไพล์ ("ไม่สามารถทำให้ข้ามการตรวจสอบได้")
- ใช้ Grep ตรวจสอบบันทึก reverse-proxy / การเข้าถึงของคุณ เพื่อหารายการคำนำหน้าข้างต้นที่จับคู่กับที่อยู่ไคลเอนต์ซึ่งไม่ใช่ loopback หากมีรายการใดตอบกลับเป็น `200` แทนที่จะเป็น `403 LOCAL_ONLY` แสดงว่า proxy กำลังปกปิด IP จริงของไคลเอนต์ — ให้แก้ไข proxy
- `403 LOCAL_ONLY` ในบันทึกของ OmniRoute สำหรับหนึ่งในพาธเหล่านี้หมายความว่าตัวป้องกันกำลังทำงานตามที่ออกแบบไว้ ไม่ใช่ข้อผิดพลาดที่ควรระงับ

### ระดับ 2 — ALWAYS_PROTECTED

**บังคับใช้โดย:** `isAlwaysProtectedPath(path)` → ข้ามการหลีกเลี่ยงด้วย `requireLogin=false`
**การข้าม:** ไม่มีเมื่อ `requireLogin=false`; ต้องใช้ JWT เสมอ

รูตเหล่านี้มีผลทำลายหรือไม่สามารถย้อนกลับได้ การอนุญาตให้ใช้รูตเหล่านี้ในการติดตั้งแบบ "ไม่มีรหัสผ่าน"
จะหมายความว่าทุกคนบน LAN เดียวกันสามารถล้างฐานข้อมูลหรือยุติโพรเซสของ
เซิร์ฟเวอร์ได้

| พาธ                                       | เหตุผล                                                                |
| ----------------------------------------- | --------------------------------------------------------------------- |
| `/api/shutdown`                           | ยุติโพรเซสของเซิร์ฟเวอร์                                              |
| `/api/settings/database`                  | ส่งออก นำเข้า และล้างฐานข้อมูล                                        |
| `/api/db-backups`                         | เข้าถึงอาร์ไคฟ์ข้อมูลสำรองฉบับเต็มของฐานข้อมูล                        |
| `/api/settings/export-json`               | ส่งออกบล็อบการตั้งค่าทั้งหมด (รวมถึงข้อมูลลับ)                        |
| `/api/settings/import-json`               | แทนที่บล็อบการตั้งค่าทั้งหมด                                          |
| `/api/providers/health-autopilot/actions` | ดำเนินการแก้ไขโดย autopilot                                           |
| `/api/settings/obsidian`                  | ออกข้อมูลประจำตัว WebDAV ที่นำกลับมาใช้ใหม่ได้สำหรับรูทของ vault ใด ๆ |

**การตอบกลับเมื่อละเมิด:** `401 Authentication required`

`/api/settings/obsidian` ครอบคลุม `/webdav` ซึ่งเป็นพาธลูกของมัน: `POST` จะกำหนดให้บริการไฟล์ WebDAV —
ซึ่งให้บริการโดยเลเยอร์ Node แบบกำหนดเองก่อนถึง Next.js และอยู่นอก pipeline นี้ — ชี้ไปยังรูท
ที่ผู้เรียกเลือก และส่งข้อมูลประจำตัว Basic ที่เพิ่งออกใหม่กลับไป, `DELETE` จะหมุนเวียนข้อมูลประจำตัวดังกล่าว และ `POST` ของพาธแม่จะจัดเก็บ
โทเค็น Obsidian REST API โดย GHSA-62vw ปกปิดเฉพาะการเปิดเผยรหัสผ่านผ่าน `GET`; กระบวนการออกข้อมูลประจำตัว
ยังคงอยู่ในระดับที่เปิดให้ผ่านเมื่อล้มเหลว (GHSA-7pq4-8pvv-rx7r) นอกจากนี้ `enableObsidianVaultSync()`
ยังปฏิเสธ vault ที่เป็นไดเรกทอรีข้อมูล อยู่ภายในไดเรกทอรีข้อมูล หรือมีไดเรกทอรีข้อมูลอยู่ภายใน

### การบูตสแตรปของการติดตั้งใหม่จำกัดเฉพาะ loopback — พิจารณาจาก peer จริง ไม่ใช่ `Host`

เมื่อยังไม่ได้กำหนดรหัสผ่านสำหรับการจัดการ (และไม่มี `INITIAL_PASSWORD`) `isAuthRequired()` ใน
`src/shared/utils/apiAuth.ts` จะคงการบูตสแตรปแบบไม่ระบุตัวตนไว้ **เฉพาะสำหรับ loopback peer เท่านั้น**
การระบุว่าเป็น loopback จะพิจารณาจากสัญญาณ peer ที่เชื่อถือได้ตามลำดับดังนี้: TCP peer จริง
ที่ประทับโทเค็น (`PEER_IP_HEADER` + `VIA_PROXY_HEADER` ซึ่งเป็นข้อมูลที่นโยบายมองเห็น), ผลตัดสิน
`AUTHZ_HEADER_PEER_LOCALITY` ของ pipeline เอง (ซึ่งเป็นข้อมูลที่ตัวจัดการรูตมองเห็น และเชื่อถือได้เฉพาะขณะที่
ตั้งค่า `OMNIROUTE_PEER_STAMP_TOKEN` อยู่) หรือ socket peer จริงสำหรับผู้เรียกโดยตรง ระบบจะไม่ตรวจสอบ `Host` /
`nextUrl.hostname` และการตั้งรหัสผ่านครั้งแรก
(`POST /api/settings/require-login`) จะอยู่ภายใต้ข้อจำกัดเดียวกัน แทนที่จะเปิดให้ network peer ทุกตัว
(GHSA-7pq4-8pvv-rx7r) `managementPolicy` จะส่งผลตัดสิน `peerContext` ของตัวเอง
ลงไปอย่างชัดเจน ดังนั้น header ของคำขอ ORIGINAL (ก่อนการตัดออก) จะไม่มีอำนาจตัดสินเรื่องนี้

### ระดับ 3 — MANAGEMENT (ค่าเริ่มต้น)

รูตการจัดการอื่น ๆ ทั้งหมด ต้องยืนยันตัวตน เว้นแต่จะกำหนดค่า
`requireLogin=false` โทเค็น CLI สามารถใช้ยืนยันตัวตนกับรูตเหล่านี้ได้ (loopback + HMAC ที่ถูกต้อง)

## ลำดับการประเมิน

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ดำเนินการต่อ
     → non-loopback, Bearer ที่มี manage-scope
        และ isLocalOnlyBypassableByManageScope   → อนุญาต (management_key)
     → มิฉะนั้น                                  → ปฏิเสธ 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → อนุญาต (system)
  3. hasValidCliToken(headers)?
     → อนุญาต (cli) [loopback + การตรวจสอบ HMAC ด้วย timingSafeEqual]
  4. isAlwaysProtectedPath(path) หรือ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → อนุญาต (dashboard_session)
     → Bearer ที่มี manage-scope บนพาธที่ไม่สามารถข้ามได้?
        → อนุญาต (management_key)
     → ปฏิเสธ 401/403
  5. requireLogin=false?
     → อนุญาต (anonymous)
```

แขนง manage-scope ในขั้นตอนที่ 1 เป็นพาธที่ผ่านการยืนยันตัวตนเพียงพาธเดียวที่สามารถเข้าถึง
เส้นทาง LOCAL_ONLY ได้ โหมดความล้มเหลวของ auth-backend จะส่งคืน 503 (ไม่ใช่ 403) เพื่อให้
DB ที่หมดอายุไม่ลดระดับเป็น "ปฏิเสธ" โดยไม่แจ้งให้ทราบ

## การเพิ่มเส้นทางใหม่ที่สามารถ spawn ได้

1. เพิ่มคำนำหน้าพาธลงใน `LOCAL_ONLY_API_PREFIXES` ที่
   `src/server/authz/routeGuard.ts`
2. เพิ่มการทดสอบใน `tests/unit/authz/routeGuard.test.ts` เพื่อยืนยันว่า
   `isLocalOnlyPath()` ส่งคืน true สำหรับคำนำหน้าใหม่
3. **ห้ามข้ามขั้นตอนนี้โดยเด็ดขาด** — ดูกฎตายตัวข้อที่ 15 ใน `CLAUDE.md`
4. ตัดสินใจว่าเส้นทางนี้ควรอยู่ใน `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ด้วยหรือไม่?
   คำตอบเริ่มต้นคือ **ไม่** ให้เลือกใช้เฉพาะเมื่อเส้นทางนั้นปลอดภัยพอที่จะเปิดให้ผู้ถือ
   manage-scope เข้าถึงได้ (กล่าวคือ ต้องไม่ spawn โค้ดตามอำเภอใจที่ผู้ใช้ควบคุม)

## การเพิ่มพาธที่ manage-scope สามารถข้ามข้อจำกัดได้

1. ยืนยันว่าเส้นทางนี้ไม่เรียกใช้โค้ดหรือคำสั่งที่ผู้ใช้ระบุ หากมีการเรียกใช้
   ให้หยุด — ข้อยกเว้นนี้ไม่ใช่เครื่องมือที่เหมาะสม
2. เพิ่มคำนำหน้าต่อท้าย `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ใน
   `src/server/authz/routeGuard.ts`
3. เพิ่มความครอบคลุมใน `tests/unit/authz/management-policy.test.ts` สำหรับรูปแบบ
   คำขอทั้งสี่แบบ ได้แก่ ไม่มี Bearer (403), Bearer ที่มี manage-scope (อนุญาต),
   Bearer ที่ไม่มี manage-scope (403) และการทดสอบการถดถอยรายคำนำหน้าเพื่อให้
   `/api/cli-tools/runtime/*` ยังคงจำกัดเฉพาะ loopback อย่างเคร่งครัด แม้จะมี Bearer
   ที่มี manage-scope

- `scripts/check/check-openapi-coverage.mjs` — ล้มเหลวหากความครอบคลุม < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — ล้มเหลวหากคำอธิบายประกอบ
  `x-loopback-only` หรือ `x-always-protected` ไม่สอดคล้องกับค่าคงที่ ณ เวลาคอมไพล์

สคริปต์ทั้งสองทำงานใน pre-commit hook และใน CI

### กฎเกี่ยวกับผลบวกลวง

หากมีการใส่คำอธิบายประกอบ `x-always-protected` หรือ `x-loopback-only` ให้กับเส้นทางที่ไม่ได้อยู่ใน
ค่าคงที่ของ `routeGuard.ts` สคริปต์ตรวจสอบความครอบคลุมจะล้มเหลว วิธีแก้คือต้องปรับ YAML
ให้สอดคล้องกับสิ่งที่ `routeGuard.ts` บังคับใช้จริงเสมอ — ไม่ใช่เพิ่มเส้นทางลงใน `routeGuard.ts`
โดยไม่ได้ติดตั้งตรรกะการบังคับใช้ด้วย
