> **หมายเหตุเกี่ยวกับขอบเขต:** `socket.yml` กำหนดค่าการสแกนอาร์ติแฟกต์ npm หลังการเผยแพร่ที่ฝั่งรีจิสทรีของ Socket.dev (พาธที่ให้ละเว้นสำหรับเนื้อหาที่ไม่ได้รวมอยู่ในแพ็กเกจที่เผยแพร่ เช่น `tests/`, `docs/` และรายงานการบิลด์) โดยไม่ได้เชื่อมต่อเกตสำหรับการผสาน CI/PR — ไม่มีเวิร์กโฟลว์ใน `.github/workflows` ไม่มีสคริปต์ใน `package.json` และไม่มีเป้าหมายใน `Makefile` ที่เรียกใช้ Socket.dev

เอกสารนี้คือคำรับรองที่จัดทำโดยผู้ดูแล สำหรับผลการตรวจพบ
`AI-detected potential malware` ทั้งหกรายการที่รายงานต่อ `omniroute@3.8.5` และ
มาตรการลดความเสี่ยงที่นำมาใช้ใน `omniroute@3.8.6` เอกสารนี้จัดทำขึ้นเพื่อให้:

1. ผู้ดำเนินการไปป์ไลน์ด้านความปลอดภัยมีเอกสารอ้างอิงฉบับเดียวสำหรับใช้อ้างถึงเมื่อต้อง
   ประเมินผลการตรวจพบเทียบกับซอร์สจริง
2. สแกนเนอร์ AI ในอนาคตสามารถตรวจจับคำยืนยันที่ลงนามโดยผู้ดูแลว่าแต่ละ
   พาธที่ถูกแจ้งเตือนนั้นมีไว้โดยเจตนา ต้องเลือกเปิดใช้ และมีเอกสารกำกับ
3. เรามีบันทึกเป็นลายลักษณ์อักษรว่า _เหตุใด_ จุดเรียกใช้แต่ละแห่งจึงมีรูปแบบเช่นนั้น —
   เพื่อไม่ให้การปรับโครงสร้างโค้ดในอนาคตนำลักษณะเฉพาะที่ตั้งใจลบออกแล้ว
   กลับมาโดยไม่ตั้งใจ

หากคุณใช้งานสแกนเนอร์ที่แจ้งเตือนจุดเรียกใช้ใด ๆ ด้านล่างซ้ำอีกหลังจาก
เผยแพร่มาตรการลดความเสี่ยงใน v3.8.6 แล้ว โปรดเปิด issue พร้อมแนบข้อมูลการติดตามผลการสแกน และ
เราจะขยายคำรับรองไว้ที่นี่

## §1 — การติดตั้ง root CA สำหรับ MITM (`77484.js`)

**ไฟล์ต้นฉบับ**:

- `src/mitm/cert/install.ts` — `installCert()` / `uninstallCert()` แบบสาธารณะ
  และ `installCertWindows/Mac/Linux` สำหรับแต่ละแพลตฟอร์ม
- `src/mitm/systemCommands.ts` — ตัวช่วย `execFile` / `spawn` / PowerShell
  ที่ใช้ร่วมกันโดยพาธการติดตั้งต่างๆ

**ตัวกระตุ้น**: ผู้ใช้คลิก "เปิดใช้งานพร็อกซี MITM" ในแดชบอร์ดภายในที่
`/dashboard/cli-tools/mitm` route นี้เข้าถึงได้ผ่าน loopback เท่านั้น — ดูกฎเคร่งครัดข้อ #17 ใน
`CLAUDE.md` และ `src/server/authz/routeGuard.ts::isLocalOnlyPath()` JWT ที่รั่วไหล
ผ่าน tunnel **ไม่สามารถ** กระตุ้นให้มีการเรียกใช้พาธโค้ดนี้ได้

**การดำเนินการที่ต้องใช้สิทธิ์ระดับสูง (แยกตามแพลตฟอร์ม)**:

| ระบบปฏิบัติการ         | คำสั่ง                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | `certutil -addstore Root <cert>` ผ่าน UAC                                                                         |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | อัปเดตฐานข้อมูล NSS แยกตามโปรไฟล์ผ่าน `certutil -d sql:<profile>`                                                 |

คำสั่งเหล่านี้เป็นคำสั่งเดียวกับที่ `mitmproxy`, Charles Proxy, Fiddler และ
Caddy ใช้ การมีอยู่ของคำสั่งเหล่านี้ใน OmniRoute ได้รับการบันทึกไว้ที่
`docs/security/STEALTH_GUIDE.md`

**มาตรการบรรเทาใน v3.8.6**:

- `runElevatedPowerShell()` ไม่ใช้ `-EncodedCommand <base64utf16le>` อีกต่อไป
  payload ที่ต้องใช้สิทธิ์ระดับสูงจะถูกเขียนลงในไฟล์ชั่วคราว `.ps1` แยกสำหรับการเรียกแต่ละครั้ง (โหมด 0o600
  ภายในไดเรกทอรีส่วนตัวที่สร้างด้วย `mkdtempSync`) และถูกอ้างอิงผ่าน `-File`
  ไฟล์ดังกล่าวจะถูกยกเลิกการเชื่อมโยงใน `finally` วิธีนี้ช่วยลบรูปแบบลักษณะเฉพาะที่พบบ่อยของ
  การยกระดับสิทธิ์ผ่าน PowerShell โดยใช้ base64 ซึ่งถูกแจ้งเตือนโดยตัวจำแนกประเภท AI
  ของ Socket.dev
- `installCertWindows` มีบล็อก `SECURITY-AUDITOR-NOTE:` แบบ inline
  ที่ชี้มายังเอกสารนี้

**เหตุผลที่เรายังคงเก็บไว้**: พร็อกซี MITM เป็นฟีเจอร์ที่มีเอกสารกำกับและถูกใช้โดย
`docs/security/STEALTH_GUIDE.md` และ `docs/frameworks/MITM-PROXY.md` การลบ
ฟีเจอร์นี้จะทำให้ชุดฟีเจอร์ agent-bridge ใช้งานไม่ได้

## §2 — การนำเข้าข้อมูลประจำตัวจาก Zed (`app/api/providers/zed/import/route.js`)

**ไฟล์ต้นฉบับ**:

- `src/app/api/providers/zed/discover/route.ts` _(เพิ่มใหม่ใน v3.8.6)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(เพิ่มใหม่ใน v3.8.6)_

**ทริกเกอร์**: ผู้ใช้คลิก "นำเข้าจาก Zed" ในหน้า Providers ของแดชบอร์ดภายในเครื่อง เอนด์พอยต์นี้ถูกควบคุมการเข้าถึงด้วย `requireManagementAuth` ตัวแก้ไข Zed จะเขียนคีย์ API ของผู้ให้บริการลงในพวงกุญแจของระบบปฏิบัติการภายใต้ชื่อบริการที่มีการระบุไว้ในเอกสาร — ดู https://zed.dev/docs/ai/llm-providers

**พฤติกรรมของ v3.8.5 (เวอร์ชันที่ Socket.dev แจ้งเตือน)**:

`POST /import` ค้นพบข้อมูลประจำตัวและบันทึกข้อมูลเหล่านั้นลงในที่จัดเก็บ SQLite ภายในเครื่องโดยอัตโนมัติภายในการรับส่งเพียงรอบเดียว ไม่มีการยืนยันแยกเป็นรายบัญชี ไม่มีลายนิ้วมือ มีเพียงข้อความว่า "พบโทเค็น N รายการ และนำเข้าทั้งหมดแล้ว"

**การลดความเสี่ยงใน v3.8.6 — การยืนยัน 2 ขั้นตอน**:

1. **`POST /api/providers/zed/discover`** ส่งคืน
   `{ candidates: [{ provider, service, account, fingerprint }] }` โทเค็นดิบจะ **ไม่ถูก** ส่งออกไปโดยเด็ดขาด ลายนิ้วมือคือ
   `sha256(service|account|token).slice(0,16)`
2. แดชบอร์ดแสดงรายการตัวเลือก จากนั้นผู้ดูแลเลือกว่าจะนำเข้ารายการใด และโพสต์ `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   ไปยัง **`POST /api/providers/zed/import`**
3. เอนด์พอยต์สำหรับนำเข้าจะ **อ่านพวงกุญแจซ้ำบนเซิร์ฟเวอร์** และกรองด้วย
   `(service, account, fingerprint)` การตอบกลับจาก discover ที่ถูกดัดแปลงหรือนำมาเล่นซ้ำไม่สามารถหลอกให้เอนด์พอยต์สำหรับนำเข้าบันทึกโทเค็นที่ไม่เกี่ยวข้องได้ — หากโทเค็นปัจจุบันเปลี่ยนแปลงไปหลังจาก discover ลายนิ้วมือจะไม่ตรงกันอีกต่อไปและข้อมูลประจำตัวนั้นจะถูกข้าม

แฟล็กสภาพแวดล้อม `OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` ยังคงรักษาพฤติกรรมของ v3.8.5 ไว้สำหรับผู้ดูแลที่ยังไม่ได้อัปเดตระบบอัตโนมัติของตน โดยจะถูกนำออกใน v3.9

**เหตุผลที่เรายังคงเก็บไว้**: การนำเข้าจาก Zed เป็นแนวทางเริ่มต้นใช้งานที่เป็นมิตรที่สุดสำหรับผู้ใช้ที่ใช้งาน Zed อยู่แล้วและต้องการคัดลอกคีย์ของผู้ให้บริการไปยัง OmniRoute โดยไม่ต้องวางคีย์ซ้ำ

## §3 — `execFile` / `spawn` / PowerShell ที่ยกระดับสิทธิ์ (`21843.js`)

**ไฟล์ต้นฉบับ**: `src/mitm/systemCommands.ts`

**เหตุผลที่ถูกแจ้งเตือน**: ชังก์นี้ส่งออก `execFileWithPassword`, `runElevatedPowerShell` และตัวช่วย `quotePowerShell` ที่ใช้ร่วมกันอีกครั้ง ตัวจำแนกประเภทด้วย AI ของ Socket.dev มองรายการเหล่านี้เป็น "ชุดเครื่องมือทั่วไปสำหรับการเรียกใช้คำสั่งบนโฮสต์และการยกระดับสิทธิ์" ภายใน OmniRoute รายการเหล่านี้ใช้เฉพาะในเส้นทางติดตั้งใบรับรอง MITM (§1) และโดย `execFileWithPassword` สำหรับการเรียกใช้คำสั่ง `sudo` เท่านั้น

**การลดความเสี่ยงใน v3.8.6**:

- ปรับโครงสร้าง `runElevatedPowerShell` (ดู §1)
- บล็อก `SECURITY-AUDITOR-NOTE:` แบบอินไลน์ทั้งที่
  `runElevatedPowerShell` และ `execFileWithPassword` ระบุเอกสารเกี่ยวกับตัวเรียกที่อยู่ในรายการอนุญาตและรายการไฟล์ปฏิบัติการที่กำหนดตายตัว
- การเรียก `spawn()` ของ `execFileWithPassword` มีเครื่องหมาย `nosemgrep` พร้อมรายการอนุญาตของไฟล์ปฏิบัติการที่ตัวช่วยนี้สามารถรับได้ — **ไม่มีเส้นทางจากอินพุตของผู้ใช้ไปยัง `finalCommand`/`finalArgs`**

## §4 / §6 — ตัวควบคุมบริการ 9router (`api/services/9router/{start,restart}/route.js`)

**ไฟล์ต้นฉบับ**:

- `src/app/api/services/9router/_lib.ts` — แฟกทอรีตัวควบคุม
- `src/app/api/services/9router/{start,stop,restart,status,install,update,auto-start}/route.ts`
- `src/lib/services/ServiceSupervisor.ts` — การสร้างโพรเซส / การตรวจสอบสถานะความพร้อมเป็นระยะ / บัฟเฟอร์บันทึก แบบทั่วไป

**ทริกเกอร์**: ผู้ใช้คลิก "ติดตั้ง" / "เริ่ม" บนหน้าบริการแบบฝังในแดชบอร์ดภายในเครื่อง

**การป้องกันที่มีอยู่แล้ว**:

- เส้นทาง `/api/services/*` ทั้งหมดเป็น LOCAL_ONLY ตาม
  `src/server/authz/routeGuard.ts` (กฎตายตัวข้อ #17) การบังคับให้เข้าถึงผ่านลูปแบ็กจะเกิดขึ้นก่อนการตรวจสอบสิทธิ์ใดๆ — JWT ที่รั่วไหลไม่สามารถเข้าถึงเส้นทางเหล่านี้ได้
- แถวฐานข้อมูลของ 9router ถูกตั้งค่าเริ่มต้นเป็น `status='not_installed', auto_start=0` (ดู
  `src/lib/db/migrations/071_services.sql:19`) บริการนี้จะ **ไม่** เริ่มทำงานในการเปิดใช้งานครั้งแรก
- `spawn()` ถูกเรียกด้วยพาธไบนารีที่ส่งคืนโดย
  `resolveSpawnArgs(apiKey, PORT)` ใน `src/lib/services/installers/ninerouter.ts`
  ซึ่งเป็นรายการอนุญาตแบบตายตัวของไบนารีที่รองรับ
- Stdout/stderr ถูกบัฟเฟอร์ไว้ในหน่วยความจำ (จำกัดที่ 5 MB ดู `_lib.ts`) — ไม่มีการเขียนลงดิสก์ เว้นแต่ผู้ใช้จะเปิดใช้งานการบันทึกจากแดชบอร์ด

**การลดความเสี่ยงใน v3.8.6**: ไม่มีการเปลี่ยนแปลงด้านการทำงาน โปรไฟล์บิลด์ขั้นต่ำ
(`OMNIROUTE_BUILD_PROFILE=minimal`) จะแทนที่
`src/lib/services/installers/ninerouter.ts` ด้วยสตับ สำหรับผู้ใช้ที่ต้องการนำเส้นทางซึ่งใช้สิทธิ์ระดับสูงออกจากบันเดิลโดยสมบูรณ์

**เหตุผลที่เรายังคงเก็บไว้**: 9router เป็นบริการร่วมที่เลือกติดตั้งภายในเครื่องได้ (ลักษณะเดียวกับปลั๊กอินของ WordPress) — ต้องเลือกเข้าร่วมอย่างชัดเจนเท่านั้น

## §5 — การเขียนข้อมูลรับรองกลับจาก OmniRoute Cloud Sync (`api/keys/[id]/route.js`)

**ไฟล์ต้นฉบับ**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`
- `src/app/api/keys/[id]/route.ts` — เรียกใช้ `syncKeysToCloudIfEnabled()`

**ทริกเกอร์**: `isCloudEnabled()` คืนค่า `true` (ตั้งค่าจากแดชบอร์ด) **และ**
มีการกำหนดค่า `CLOUD_URL` เมื่อปิดใช้งานทั้งสองรายการ จะไม่มีการเรียกเครือข่ายขาออกไปยัง
ปลายทาง Cloud

**พฤติกรรมใน v3.8.5 (บั๊กที่ Socket.dev ตรวจพบอย่างถูกต้อง)**:

`updateLocalTokens()` เขียนทับ `accessToken`, `refreshToken` และ
`providerSpecificData` จากการตอบกลับของ Cloud เมื่อ
`cloudUpdatedAt > localUpdatedAt` โดยไม่มี HMAC ไม่มีลายเซ็น และไม่มี checksum
`CLOUD_URL` ที่กำหนดค่าผิดหรือเป็นอันตราย (หรือ MITM บนช่องทางการสื่อสาร) สามารถสับเปลี่ยน
โทเค็น OAuth ของผู้ให้บริการได้โดยไม่มีการแจ้งเตือน

**การบรรเทาปัญหาใน v3.8.6**:

1. **การตรวจสอบ HMAC**: `verifyCloudSignature(rawBody, sigHeader)` ตรวจสอบ
   ส่วนหัว `X-Cloud-Sig` (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET,
rawBody)`) ก่อนแยกวิเคราะห์ JSON หากมีการตั้งค่าความลับ จะต้องมีลายเซ็น
   หากไม่ได้ตั้งค่า (โหมดเดิม) ระบบจะบันทึกคำเตือนและยอมรับการตอบกลับ
   — ความลับจะกลายเป็นข้อบังคับใน v3.9
2. **การเลือกเปิดใช้ฟิลด์ข้อมูลลับ**: `accessToken` / `refreshToken` /
   `providerSpecificData` จะถูกเขียนทับ **เฉพาะ** เมื่อ
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true` เท่านั้น โหมดเริ่มต้นจะซิงค์เฉพาะ
   เมทาดาทาที่ไม่ใช่ข้อมูลรับรอง (`expiresAt`, `status`, `lastError*`,
   `rateLimitedUntil`, `updatedAt`) นี่เป็น **การเปลี่ยนแปลงที่ไม่เข้ากันย้อนหลัง**
   สำหรับผู้ใช้ที่พึ่งพาการซิงค์โทเค็นระยะไกล — ผู้ใช้เหล่านั้นต้องเลือกเปิดใช้อย่างชัดเจน

**เหตุผลที่เรายังคงฟีเจอร์นี้ไว้**: Cloud Sync เป็นวิธีเดียวที่ผู้เช่า OmniRoute Cloud
สามารถรวมศูนย์ข้อมูลรับรองของทีมได้ การแก้ไขนี้ทำให้แบบจำลองภัยคุกคามตรงตามความเป็นจริง:
"เซิร์ฟเวอร์ลงลายเซ็น ไคลเอนต์ตรวจสอบ และผู้ดูแลระบบเลือกเปิดใช้"

## โปรไฟล์บิลด์: `minimal`

สำหรับผู้ใช้ที่ต้องการอาร์ติแฟกต์ที่เป็นมิตรกับ Socket ให้บิลด์ด้วย:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

webpack `NormalModuleReplacementPlugin` กำหนด alias ให้โมดูลสี่รายการชี้ไปยัง stub:

| โมดูล                                       | Stub                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

แต่ละ stub ส่งออกอินเทอร์เฟซเดียวกัน แต่ทุกฟังก์ชันจะโยน
`featureDisabledError(name)` ขณะรันไทม์ Route ที่ขึ้นอยู่กับโมดูลที่ถูกปิดใช้งาน
จะส่งคืน HTTP 503 พร้อมข้อความที่ชัดเจน แทนที่จะเปิดใช้งาน
เส้นทางโค้ดที่มีความอ่อนไหว

บันเดิลที่ได้มีไว้สำหรับเผยแพร่ในชื่อ `omniroute-secure` โปรดดู
`docs/ops/PUBLISHING_SECURE.md` สำหรับขั้นตอนการเผยแพร่
