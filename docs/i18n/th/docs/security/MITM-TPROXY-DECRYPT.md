การถอดรหัสแบบโปร่งใสด้วย TPROXY คือ **โหมดการดักจับลำดับที่ 5** ของ OmniRoute สำหรับสแตก MITM ของ
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
โดยจะดักจับและ **ถอดรหัส** ทราฟฟิก HTTPS ขาออกภายในเครื่องบน Linux
ด้วย kernel TPROXY + policy routing — **โดยไม่** ปลอมแปลง `/etc/hosts` และ
**โดยไม่** เปลี่ยนแปลงการตั้งค่าพร็อกซีระบบทั่วทั้ง OS เหมาะสำหรับการทำงานแบบไม่มีส่วนติดต่อผู้ใช้
(ไม่มีการแก้ไข DNS ที่ต้องตามล้าง) และกฎไฟร์วอลล์จะถูกล้างโดยอัตโนมัติเมื่อรีบูต

TPROXY ต่างจากโหมดการดักจับอื่นตรงที่ไม่ต้องตั้งค่าแยกตามโฮสต์ โดยจะดักจับโฮสต์ปลายทาง
**ใดๆ** บนพอร์ตเป้าหมายอย่างโปร่งใส ยุติการเชื่อมต่อ TLS ด้วยใบรับรองปลายทางที่ออกให้
ทันทีตามชื่อโฮสต์ SNI แต่ละรายการ บันทึกการรับส่งข้อมูลที่ถอดรหัสแล้ว และเข้ารหัสคำขอใหม่
เพื่อส่งไปยังปลายทางเดิม

> **เฉพาะ Linux, เฉพาะ root และต้องเลือกเปิดใช้เอง** โหมดนี้ต้องใช้ Linux, native addon
> ที่สร้างด้วยชุดเครื่องมือ C และ capability **CAP_NET_ADMIN** (โดยทั่วไปคือ root) โดยถูกจำกัด
> ให้เข้าถึงผ่าน AgentBridge API ที่รับเฉพาะการเชื่อมต่อแบบ loopback และปิดใช้งานไว้ตามค่าเริ่มต้น CA
> สำหรับ MITM ที่เชื่อถือได้และสามารถลงนามให้โฮสต์ใดๆ ได้นั้นเป็น capability ที่ทรงพลัง — โปรดดู [§6 ความปลอดภัย](#6-security)

**ซอร์ส:** `src/mitm/tproxy/`
**เส้นทาง API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**สวิตช์บนแดชบอร์ด:** Traffic Inspector → แถบเครื่องมือโหมดการดักจับ → **"TPROXY Decrypt"** ⚠

## §1 คืออะไรและควรใช้เมื่อใด

โหมดการดักจับอีกสี่โหมดต่างมีข้อจำกัดดังนี้:

| โหมด              | วิธีเปลี่ยนเส้นทางทราฟฟิก                              | ข้อจำกัด                                                |
| ----------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| AgentBridge       | ปลอมแปลง DNS ผ่าน `/etc/hosts` สำหรับชุดโฮสต์แบบตายตัว | เฉพาะโฮสต์ IDE-agent ที่ลงทะเบียนไว้                    |
| Custom Hosts      | ปลอมแปลง DNS ผ่าน `/etc/hosts` แยกตามโฮสต์             | หนึ่งรายการต่อหนึ่งโฮสต์; ต้องใช้ sudo เพื่อแก้ไข hosts |
| HTTP_PROXY        | ตัวแปรสภาพแวดล้อม `HTTP_PROXY`/`HTTPS_PROXY`           | เฉพาะแอปที่รองรับตัวแปรสภาพแวดล้อมดังกล่าว              |
| System-wide proxy | การตั้งค่าพร็อกซีของ OS                                | เปลี่ยนแปลงสถานะส่วนกลาง; ต้องย้อนค่ากลับ               |

การถอดรหัสแบบโปร่งใสด้วย TPROXY จะเปลี่ยนเส้นทางทราฟฟิกที่ระดับ **kernel** แทน โดยจะ
ทำเครื่องหมายการเชื่อมต่อ TCP ขาออกภายในเครื่องรายการใหม่ที่ส่งไปยังพอร์ตเป้าหมาย (ค่าเริ่มต้นคือ `443`) ใน
เชน `mangle OUTPUT` จากนั้น `ip rule` จะเปลี่ยนเส้นทางแพ็กเก็ตที่ถูกทำเครื่องหมายให้ส่งกลับมายังเครื่อง
และเมื่อแพ็กเก็ตเข้าสู่ระบบอีกครั้ง เป้าหมาย `TPROXY` ใน `mangle PREROUTING` จะส่งต่อแพ็กเก็ตเหล่านั้นไปยัง
listener แบบ **IP_TRANSPARENT** — ซึ่งจะยุติการเชื่อมต่อ TLS และบันทึกข้อมูลข้อความธรรมดา

ใช้โหมดนี้เมื่อคุณต้องการดักจับและถอดรหัสทราฟฟิกจากโปรเซสที่:

- ติดต่อกับโฮสต์ที่ AgentBridge ไม่ได้ลงทะเบียนไว้ และ
- ไม่รองรับ `HTTP_PROXY` และ
- คุณไม่ต้องการรบกวนด้วยการเปลี่ยนแปลงพร็อกซีทั่วทั้งระบบ

เนื่องจากการดักจับเกิดขึ้นใน kernel โปรเซสต้นทางจึง **ไม่ต้องเปลี่ยนแปลง
การกำหนดค่าใดๆ** — แต่โปรเซสดังกล่าวต้องเชื่อถือ CA แบบไดนามิกที่ OmniRoute
ติดตั้งไว้ (โปรดดู [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer))

## §2 ข้อกำหนด

| ข้อกำหนด          | รายละเอียด                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**            | เฉพาะ Linux — **IP_TRANSPARENT** เป็นตัวเลือกซ็อกเก็ตที่มีเฉพาะบน Linux ตัวโหลดจะส่งคืนสถานะ "ไม่พร้อมใช้งาน" บนแพลตฟอร์มอื่นทั้งหมด            |
| **สิทธิ์**        | ต้องมีความสามารถ **CAP_NET_ADMIN** เพื่อสร้างซ็อกเก็ตแบบโปร่งใสและใช้กฎ `iptables`/`ip` — ในทางปฏิบัติให้เรียกใช้ในฐานะ root                    |
| **Native addon**  | ต้องสร้างหรือจัดส่ง N-API addon ขนาดเล็ก (`src/mitm/tproxy/native/transparent.c`) ในรูปแบบ prebuild ดู [§3](#3-the-native-ip_transparent-addon) |
| **โมดูลเคอร์เนล** | `iptables` ที่รองรับ `TPROXY`, `mangle` และการจับคู่ `mark` (ตรวจสอบกับเคอร์เนล 6.8.0 แล้ว)                                                     |

**การลดระดับการทำงานอย่างราบรื่น:** หากขาดข้อกำหนดใดก็ตาม (ไม่ใช่ Linux, ไม่มี toolchain,
ไม่ได้สร้าง addon) ตัวโหลด addon (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
จะส่งคืน `null` แทนที่จะ throw ข้อผิดพลาด จากนั้นสถานะของ capture mode จะรายงาน
`available: false` ปุ่มสลับบนแดชบอร์ดจะถูก **ปิดใช้งาน** พร้อม tooltip
"การถอดรหัส TPROXY ต้องใช้ Linux + root + native addon" และส่วนอื่นๆ ของ
OmniRoute จะยังคงทำงานต่อไป

## §3 Native IP_TRANSPARENT addon

โมดูล `net` ของ Node ไม่สามารถเรียก `setsockopt(IP_TRANSPARENT)` _ก่อน_ `bind()`
ได้ ซึ่ง TPROXY จำเป็นต้องใช้ (มิฉะนั้นเคอร์เนลจะทิ้งแพ็กเก็ตที่ถูกเปลี่ยนเส้นทาง) addon
(`src/mitm/tproxy/native/transparent.c` ซึ่งสร้างผ่าน `binding.gyp`) เป็นโมดูล N-API
ขนาดเล็กที่เปิดเผยฟังก์ชันสามรายการ ซึ่งใช้งานผ่าน `transparentSocket.ts`:

| ฟังก์ชันของ addon                     | การทำงานกับซ็อกเก็ต                                                                         | ใช้สำหรับ                                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()` และส่งคืน fd ดิบ | listener สำหรับการดักจับแบบโปร่งใส (Node รับช่วง fd ผ่าน `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | ใช้ `setsockopt` **SO_MARK** กับ fd ที่มีอยู่                                               | ป้องกันลูป (ทำเครื่องหมายซ็อกเก็ตของพร็อกซีเอง)                                   |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **ก่อน** `connect()` แบบ non-blocking และส่งคืน fd                 | การส่งต่อ upstream ที่เข้ารหัสใหม่ (SYN มีเครื่องหมายติดไปด้วย)                   |

ปลายทางเดิมจะถูกอ่านจาก `socket.localAddress`/`localPort` — TPROXY
จะเก็บค่าเหล่านี้ไว้ จึงไม่จำเป็นต้องค้นหาผ่าน **SO_ORIGINAL_DST**/NAT

### การสร้าง addon

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- ระหว่าง `npm run build` สคริปต์ `scripts/build/build-tproxy-native.mjs` จะเรียกใช้ `node-gyp
rebuild` โดยขั้นตอนนี้ทำงาน **เฉพาะบน Linux และความล้มเหลวไม่ทำให้กระบวนการหยุด** — หากไม่มี toolchain
  capture mode จะเพียงไม่พร้อมใช้งาน
- `assembleStandalone.mjs` จะคัดลอก `build/Release/transparent.node` ไปยัง
  standalone bundle ส่วน `transparentSocket.ts` สามารถค้นหาไฟล์ได้ทั้งแบบสัมพัทธ์กับโมดูลและ
  แบบสัมพัทธ์กับ cwd (`<cwd>/src/mitm/tproxy/native/...`)
- `build/` และ `prebuilds/` ถูกตั้งค่าให้ git เพิกเฉย — ไบนารีจะถูก **สร้างขึ้น แต่ไม่เคย
  commit**

ตัวโหลดจะตรวจสอบตามลำดับความสำคัญดังนี้:
`native/build/Release/transparent.node` จากนั้น `native/prebuilds/transparent.node`
(ทั้งแบบสัมพัทธ์กับโมดูลและภายใต้ `<cwd>/src/mitm/tproxy/`)

## §4 CA แบบไดนามิกต่อ SNI และตัวติดตั้ง trust store

> **อัปเดต #6684:** ขณะนี้เซิร์ฟเวอร์แบบสแตติกของ AgentBridge (`src/mitm/server.cjs`)
> ใช้รูปแบบสถาปัตยกรรม CA/leaf เดียวกันนี้แทน leaf แบบ self-signed สแตติกเพียงใบเดียว
> โดยใช้ CA คนละอินสแตนซ์อย่างชัดเจน
> (`src/mitm/cert/rootCa.ts` ซึ่งจัดเก็บถาวรไว้ที่ `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> และติดตั้งในสล็อต trust store เดิม `omniroute-mitm.crt`
> (แทนที่ leaf เดิมในสล็อตนั้น — ไม่จำเป็นต้องล้าง trust แบบคู่)
> โดยแยกออกจากสล็อต `omniroute-tproxy-ca.crt` ของ TPROXY ด้านล่างอย่างสมบูรณ์
> การติดตั้ง AgentBridge ใหม่จะใช้โมเดล CA โดยอัตโนมัติ ส่วนการติดตั้งที่
> trust leaf แบบสแตติกเดิมไว้แล้วจะยังคงใช้ leaf นั้นต่อไป จนกว่าผู้ดูแลระบบจะเลือก
> เปิดใช้งานผ่าน `MITM_ROOT_CA_ENABLED=true` (ดู `src/mitm/cert/migration.ts`) —
> MITM CA ที่ได้รับการ trust และสามารถลงนาม leaf สำหรับโฮสต์ **ใดก็ได้** นั้น
> มีอำนาจมากกว่า leaf แบบ fixed-SAN เดิมอย่างมีนัยสำคัญ ดังนั้นการเปลี่ยนนี้
> จะไม่เกิดขึ้นโดยไม่มีการแจ้งสำหรับการติดตั้งที่มีการ trust อยู่แล้ว

ในอดีต ใบรับรอง MITM แบบสแตติกของ AgentBridge ใช้งานได้เพียงเพราะ AgentBridge
ปลอมแปลง DNS สำหรับชุดโฮสต์แบบ **ตายตัว** (ซึ่งขณะนี้รวมเป็นหนึ่งเดียวกับโมเดลด้านล่างแล้ว)
TPROXY ดักรับโฮสต์ **ใดก็ได้** ดังนั้น listener ของมันต้องนำเสนอ leaf ที่ถูกต้อง
สำหรับ SNI ใดก็ตามที่ไคลเอนต์ร้องขอ — ซึ่งเป็นข้อกำหนดเดียวกับที่ AgentBridge มีในขณะนี้
สำหรับชุด `MITM_TOOL_HOSTS` ทั้งหมด (รายการเครื่องมือ 9 รายการ) แทนที่จะมีเพียง
โฮสต์ antigravity 4 รายการ

### CA แบบไดนามิก (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` รัน CA ภายในเครื่อง (สร้างบน dependency `selfsigned`) ซึ่ง:

- สร้าง CA อายุยาวผ่าน `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  อายุใช้งาน 10 ปี, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA 2048 บิต / SHA-256)
- ออก **leaf ต่อชื่อโฮสต์ SNI ตามต้องการ** ผ่าน `issueLeafCert()` (อายุใช้งาน 1 ปี,
  `subjectAltName` = โฮสต์ SNI) และแคช `tls.SecureContext` หนึ่งรายการ
  ต่อชื่อโฮสต์
- เปิดให้ใช้ `createSNICallback()` สำหรับเซิร์ฟเวอร์ที่ยุติการเชื่อมต่อ TLS (ดู [§5](#5-how-decrypt-and-capture-work))
- สามารถสร้างด้วย `existingCa` เพื่อให้ CA คงเดิมตลอดการรีสตาร์ต
  (จึงไม่จำเป็นต้องติดตั้ง trust store ใหม่)

คีย์ส่วนตัวของ CA **จะไม่ออกจากเครื่องโดยเด็ดขาด**

### ตัวติดตั้ง trust store (`src/mitm/tproxy/caTrust.ts`)

ไคลเอนต์ที่ถูกดักรับต้อง trust CA แบบไดนามิก ดังนั้นเมื่อเริ่มโหมด capture
ระบบจะติดตั้งใบรับรอง CA ลงใน trust store ของ OS ภายใต้ **สล็อตเฉพาะ** —
`omniroute-tproxy-ca.crt` (ค่าคงที่ `TPROXY_CA_CERT_NAME`) — โดยแยกออกจาก
สล็อตของใบรับรอง MITM แบบสแตติก (`omniroute-mitm.crt`) เพื่อให้ทั้งสองไม่เขียนทับกัน

`installTproxyCa(caPem, sudoPassword?)` ตรวจหาไดเรกทอรี anchor ของดิสโทร
(ตามลำดับ: รูปแบบ Debian ก่อน) และรันคำสั่งรีเฟรชที่ตรงกัน:

| ไดเรกทอรี anchor                            | คำสั่งรีเฟรช             |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

การติดตั้งจะนำ PEM ไปพักไว้ในไฟล์ชั่วคราว จากนั้นจึงรัน `mkdir -p` แบบมีสิทธิ์พิเศษ
กับไดเรกทอรี anchor ใช้ `cp` คัดลอกไฟล์ที่พักไว้เข้าไป และรันคำสั่งรีเฟรช
`uninstallTproxyCa()` จะลบเฉพาะสล็อตเฉพาะนี้ (โดยไม่แตะต้องใบรับรอง MITM แบบสแตติก)
แล้วรีเฟรช — และจะไม่ดำเนินการใดๆ บนระบบที่ไม่ใช่ Linux

คำสั่งที่ต้องใช้สิทธิ์พิเศษทั้งหมดจะรันผ่าน `execFileWithPassword` (`src/mitm/systemCommands.ts`)
— ใช้ `spawn` พร้อม **อาร์เรย์อาร์กิวเมนต์ ไม่มี shell และไม่มีการแทรกค่าในสตริง**
(กฎเคร่งครัด #13) เมื่อโปรเซสทำงานเป็น root (เช่น VPS) เป้าหมายจะทำงานโดยตรง
และไม่ต้องใช้รหัสผ่าน ส่วนบนเดสก์ท็อปที่ไม่ใช่ root ระบบจะส่ง `sudoPassword`
ผ่าน stdin ไปยัง `sudo -S`

> `sudoPassword` ของเดสก์ท็อปจะถูกส่งมาในเนื้อหา POST เพื่ออนุญาตการติดตั้ง
> trust store และจะถูกละเว้นทั้งหมดเมื่อโปรเซสทำงานเป็น root

## §5 การถอดรหัสและการบันทึกทำงานอย่างไร

ไปป์ไลน์ (ทั้งหมดอยู่ภายใต้ `src/mitm/tproxy/`):

```
แอปภายใน  ──TCP/443──▶  mangle OUTPUT ทำเครื่องหมายการเชื่อมต่อ (fwmark)
                          ip rule → ตารางเส้นทางภายใน → lo
                          mangle PREROUTING TPROXY → ตัวรับฟัง IP_TRANSPARENT (พอร์ต 8443)
                              │  captureMode.ts: อ่านปลายทางเดิมจาก socket.localAddress
                              ▼
                          tlsCapture.ts:
                            1. ยุติ TLS จาก CLIENT ด้วยใบรับรองปลายทางต่อ SNI (dynamicCert)
                            2. http.Server ภายในแยกวิเคราะห์ข้อความธรรมดาที่ถอดรหัสแล้ว
                            3. บันทึก → globalTrafficBuffer.push() โดยมี source: "tproxy"
                               (ใช้ sanitizeHeaders + maskSecret)
                            4. ส่งต่อแบบเข้ารหัสใหม่ไปยังปลายทางเดิม
                               ผ่านซ็อกเก็ตที่มีเครื่องหมายบายพาส (connectMarked, ป้องกันลูป)
                              │
                              ▼
                          อัปสตรีมต้นทาง (api.example.com)
```

- **การยุติ TLS** (`createTlsCaptureServer`): ห่อหุ้มซ็อกเก็ตดิบที่ถูกดักจับ
  ไว้ใน `tls.TLSSocket` ฝั่งเซิร์ฟเวอร์โดยใช้คอลแบ็ก SNI ของ CA แบบไดนามิก
  จากนั้นส่งสตรีมที่ถอดรหัสแล้วให้ `http.Server` ภายใน (เทคนิคมาตรฐานสำหรับการ
  ยุติการเชื่อมต่อแบบ MITM) อายุการใช้งานของซ็อกเก็ตถูกจำกัดด้วย `MITM_IDLE_TIMEOUT_MS`
  เพื่อไม่ให้ทันเนลที่ค้างอยู่ใช้ตัวระบุไฟล์จนหมด
- **การบันทึก** (`handleDecryptedRequest`): พุช `InterceptedRequest` ที่มี
  `source: "tproxy"` โดยสถานะเริ่มต้นเป็น `"in-flight"` ส่วนเฮดเดอร์จะผ่าน
  `sanitizeHeaders()` และเนื้อความจะผ่าน `maskSecret()` ก่อนเข้าสู่
  บัฟเฟอร์ จากนั้นรายการจะได้รับการอัปเดตด้วยการตอบกลับ ขนาด และเวลาแฝง
- **การส่งต่อแบบเข้ารหัสใหม่** (`createForward` / `realForward`): เข้ารหัสใหม่เพื่อส่งไปยัง
  ปลายทางเดิม โดยค่าเริ่มต้นของ `rejectUnauthorized` คือ **`true`** (ปลอดภัย
  โดยค่าเริ่มต้น) — ใบรับรองของอัปสตรีมจะได้รับการตรวจสอบกับ SNI/Host ที่ไคลเอนต์
  ร้องขอ ดังนั้นพร็อกซีจะปฏิเสธสิ่งเดียวกันกับที่ไคลเอนต์ต้นทางจะปฏิเสธ

### การป้องกันลูป (SO_MARK)

เนื่องจากกฎต่าง ๆ ทำเครื่องหมายการเชื่อมต่อขาออกภายในเครื่องที่สร้างขึ้นใหม่ การส่งต่อ
แบบเข้ารหัสใหม่ของพร็อกซี **เอง** จึงมักจะถูกดักจับซ้ำ ซึ่งทำให้เกิดลูปไม่รู้จบ
เส้นทางการส่งต่อป้องกันปัญหานี้ด้วยเครื่องหมายบายพาสของซ็อกเก็ต (**SO_MARK**):

- `realForward` เปิดซ็อกเก็ตอัปสตรีมผ่าน `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  — `DEFAULT_BYPASS_MARK = 0x539` — ซึ่งตั้งค่า **SO_MARK** **ก่อน** `connect()`
  ทำให้ SYN ของการส่งต่อมีเครื่องหมายบายพาส
- กฎ `mangle OUTPUT` จะยกเว้นการเชื่อมต่อที่มีเครื่องหมายบายพาสอยู่แล้ว
  (`-m mark ! --mark <bypassMark>`) ดังนั้นการส่งต่อของพร็อกซีจะ**ไม่**ถูกทำเครื่องหมายซ้ำ
  และจะไม่กลับเข้าสู่ TPROXY

> หมายเหตุเกี่ยวกับการนำไปใช้: ต้องติดตั้งซ็อกเก็ตที่มีเครื่องหมายบายพาสบน
> `createConnection` ของเอเจนต์ (`https.request({ createConnection })` จะถูกเพิกเฉย
> โดยไม่มีการแจ้งเตือนเมื่อมีเอเจนต์อยู่) มิฉะนั้นการส่งต่อจะเปิดซ็อกเก็ตที่ไม่มีเครื่องหมาย
> และลูปจะกลับมา นี่คือการแก้ไขการป้องกันลูปที่ผ่านการตรวจสอบแบบ e2e แล้ว

## §6 ความปลอดภัย

| มาตรการควบคุม                 | รายละเอียด                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API สำหรับลูปแบ็กเท่านั้น** | `/api/tools/agent-bridge/tproxy` ครอบคลุมอยู่ภายใต้คำนำหน้า `/api/tools/agent-bridge/` ใน `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`) การบังคับใช้ลูปแบ็กจะทำงาน **ก่อน** การยืนยันตัวตน (กฎตายตัว #15 + #17) — JWT ที่รั่วไหลผ่านทันเนลไม่สามารถเริ่มการดักจับ TPROXY ซึ่งใช้กฎ `iptables` และติดตั้ง CA สำหรับ trust store ผ่านโพรเซสลูกได้ |
| **ช่อง CA เฉพาะ**             | CA แบบไดนามิกจะติดตั้งไปยัง `omniroute-tproxy-ca.crt` โดยไม่เขียนทับใบรับรอง MITM แบบคงที่                                                                                                                                                                                                                                                                     |

| **การปกปิดข้อมูลลับ**         | `maskSecret()` สำหรับเนื้อหาคำขอ/การตอบกลับ และ `sanitizeHeaders()` สำหรับส่วนหัว จะทำงาน **ก่อน** `globalTrafficBuffer.push()`                                                                                                                                                                                                                                |
| **ไม่มีการแทรกค่าในเชลล์**    | คำสั่ง `iptables`/`ip`/trust-store ทั้งหมดทำงานผ่าน `execFile`/`execFileWithPassword` โดยใช้อาร์เรย์อาร์กิวเมนต์ (กฎตายตัว #13)                                                                                                                                                                                                                                |
| **การตรวจสอบใบรับรองต้นทาง**  | การส่งต่อต่อแบบเข้ารหัสใหม่จะตรวจสอบใบรับรองต้นทางโดยค่าเริ่มต้น (`rejectUnauthorized: true`)                                                                                                                                                                                                                                                                  |
| **การกรองข้อผิดพลาด**         | การตอบกลับข้อผิดพลาดของเส้นทางจะผ่าน `sanitizeErrorMessage()` (กฎตายตัว #12)                                                                                                                                                                                                                                                                                   |

**MITM CA เป็นความสามารถที่ทรงพลัง** CA ที่ระบบปฏิบัติการเชื่อถือและสามารถลงนามให้กับ
โฮสต์ใดก็ได้ หมายความว่าทุกสิ่งที่ OmniRoute ดักจับสามารถถอดรหัสได้ ความสามารถนี้ถูกควบคุมด้วย
โหมดการดักจับ TPROXY แบบชัดเจนสำหรับเครื่องภายในเท่านั้น ซึ่งปิดไว้โดยค่าเริ่มต้น และรายการใน trust store
จะถูกลบออกเมื่อคุณหยุดโหมดนี้

## §7 การใช้ / ย้อนคืนไฟร์วอลล์แบบธุรกรรม

การหยุดทำงานโดยไม่คาดคิดจะต้องไม่ทิ้งกฎ `mangle` หรือเส้นทางที่ค้างอยู่ไว้ ตัวสร้างคำสั่ง
(`src/mitm/tproxy/commands.ts`) และตัวเรียกใช้ (`src/mitm/tproxy/setup.ts`) รับประกันว่า
**การย้อนคืนเป็นการดำเนินการตรงกันข้ามกับการใช้ทุกประการ โดยทำตามลำดับย้อนกลับ**

`applyTproxy(cfg)` เรียกใช้คำสั่งสำหรับการใช้ตามลำดับ เมื่อเกิดความล้มเหลว **ใดๆ** ระบบจะเรียกใช้
`revertTproxy(cfg)` แบบเต็มรูปแบบโดยพยายามให้ดีที่สุด แล้วโยนข้อผิดพลาดต่อ — ดังนั้นไฟร์วอลล์จะถูก
ใช้อย่างสมบูรณ์หรือถูกย้อนคืนอย่างสมบูรณ์เท่านั้น และจะไม่ค้างอยู่ในสถานะใช้เพียงบางส่วน `revertTproxy(cfg)` เรียกใช้
คำสั่งตรงกันข้ามตามลำดับย้อนกลับและละเว้นความล้มเหลว (ทำซ้ำได้อย่างปลอดภัย — สามารถเรียกใช้
โดยไม่มีเงื่อนไข เช่น จากขั้นตอนล้างข้อมูล `repairMitm()` ของ AgentBridge)

`validateTproxyConfig(cfg)` ทำงานก่อนคำสั่งใดๆ: พอร์ตต้องอยู่ในช่วง `1–65535`,
`mark`/`routeTable`/`bypassMark` ต้องเป็นจำนวนเต็มบวก และ `bypassMark` ต้อง
แตกต่างจาก `mark` (ป้องกันลูป)

### คำสั่งสำหรับการใช้ (ตามลำดับ)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

การย้อนคืนจะลบรายการเหล่านี้ตามลำดับย้อนกลับ: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`

> วิธีนี้อิงกับ **OUTPUT** เนื่องจากกรณีใช้งาน MITM คือทราฟฟิกขาออก
> _ภายในเครื่อง_ (แอปบนโฮสต์เดียวกัน) ซึ่ง TPROXY ที่อยู่ใน `PREROUTING` เพียงอย่างเดียวจะ
> มองไม่เห็น — `PREROUTING` มองเห็นเฉพาะทราฟฟิกที่ส่งต่อเท่านั้น เชน `OUTPUT` จะทำเครื่องหมาย
> การเชื่อมต่อภายในเครื่องรายการใหม่, `ip rule` จะเปลี่ยนเส้นทางการเชื่อมต่อเหล่านั้นไปยังการส่งภายในเครื่อง (`lo`) และ
> จากนั้น `PREROUTING` จะกำหนดการเชื่อมต่อเหล่านั้นให้กับตัวรับฟังแบบโปร่งใส

## §8 การกำหนดค่า

คำขอเริ่มต้น (`POST /api/tools/agent-bridge/tproxy`) ยอมรับฟิลด์ต่อไปนี้
ซึ่งตรวจสอบโดย `StartTproxyBodySchema` (`tproxy/route.ts`) ทุกฟิลด์เป็นตัวเลือก
และจะใช้ค่าเริ่มต้นหากไม่ได้ระบุ:

| ฟิลด์            | ชนิด               | ค่าเริ่มต้น | หมายเหตุ                                                                                                                          |
| ---------------- | ------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`       | พอร์ต TCP ปลายทางที่จะดักรับอย่างโปร่งใส                                                                                          |
| **mark**         | int (≥1)           | `0x2333`    | เครื่องหมายไฟร์วอลล์ที่กำหนดบน `OUTPUT` และใช้จับคู่โดย `ip rule` + `PREROUTING`                                                  |
| **onPort**       | int (1–65535)      | `8443`      | พอร์ตที่ตัวรับฟังแบบโปร่งใส (**IP_TRANSPARENT**) ผูกอยู่                                                                          |
| **routeTable**   | int (≥1)           | `233`       | รหัสตารางการกำหนดเส้นทางตามนโยบายที่เก็บเส้นทาง `local 0.0.0.0/0`                                                                 |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`     | เครื่องหมายซ็อกเก็ตสำหรับข้าม (**SO_MARK**) ที่พร็อกซีกำหนดบนการเชื่อมต่ออัปสตรีมของตนเอง ซึ่งจะถูกยกเว้นใน `OUTPUT` (ป้องกันลูป) |
| **sudoPassword** | string             | —           | สำหรับเดสก์ท็อปที่ไม่ใช่ root เท่านั้น: ใช้อนุญาตการติดตั้ง trust store และจะถูกละเว้นเมื่อเป็น root                              |

TPROXY **ไม่มีตัวแปรสภาพแวดล้อม** — การกำหนดค่าทั้งหมดทำผ่านเนื้อหา
POST หรือใช้ค่าเริ่มต้นข้างต้น

## §9 การเปิดใช้งานจาก Traffic Inspector

1. เปิด **Traffic Inspector** (`/dashboard/tools/traffic-inspector`)
2. ในแถบเครื่องมือโหมดการดักจับ ให้ค้นหาปุ่ม **"TPROXY Decrypt"** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)
   - หากปุ่มถูก **ปิดใช้งาน** พร้อมทูลทิป "การถอดรหัส TPROXY ต้องใช้ Linux + root +
     เนทีฟแอดออน" แสดงว่าเนทีฟแอดออนไม่พร้อมใช้งานบนโฮสต์นี้ (ไม่ใช่ Linux,
     ไม่มีชุดเครื่องมือสำหรับการบิลด์ หรือยังไม่ได้บิลด์แอดออน) ดู [§2](#2-requirements) และ [§3](#3-the-native-ip_transparent-addon)
3. คลิกปุ่มดังกล่าว ระบบจะเรียก `POST /api/tools/agent-bridge/tproxy` ผ่าน
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`) ซึ่งจะ:
   สร้าง CA แบบไดนามิก เปิด transparent listener ใช้กฎไฟร์วอลล์
   และติดตั้ง CA ลงใน trust store ของระบบปฏิบัติการ
4. เมื่อทำงานอยู่ ปุ่มสลับจะเปลี่ยนเป็นสีเหลืองอำพันและแสดงจำนวนการสกัดกั้นแบบเรียลไทม์
   (`· <interceptCount>`) คำขอที่ถูกสกัดกั้นจะปรากฏในรายการคำขอพร้อม
   `source: "tproxy"`
5. คลิกอีกครั้งเพื่อหยุด — `DELETE /api/tools/agent-bridge/tproxy` ผ่าน
   `stopTproxyCaptureMode()` จะปิด listener ถอนการติดตั้ง CA และย้อนกลับ
   กฎไฟร์วอลล์

สถานะของโหมดการดักจับ (กำลังทำงาน / พร้อมใช้งาน / จำนวนการสกัดกั้น / พอร์ตของ listener) มาจาก
`GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` ใน
`src/mitm/tproxy/captureManager.ts`) โดยสามารถมีเซสชัน TPROXY ทำงานได้ครั้งละ **หนึ่ง** เซสชันเท่านั้น —
การเริ่มเซสชันที่สองจะถูกปฏิเสธพร้อมข้อความ "โหมดการดักจับ TPROXY กำลังทำงานอยู่แล้ว"

## §10 การแก้ไขปัญหา

### ปุ่มสลับถูกปิดใช้งาน

ไม่สามารถโหลดเนทีฟแอดออนได้ โปรดยืนยันว่า: คุณกำลังใช้งาน Linux, ได้บิลด์แอดออนแล้ว
(`npm run build:native:tproxy`) และโปรเซสสามารถโหลด `transparent.node` ได้
`isTransparentSocketAvailable()` เป็นตัวควบคุมการเปิดใช้งานปุ่มสลับ; `GET /api/tools/agent-bridge/tproxy`
จะส่งคืน `available: false` เมื่อไม่มีแอดออน

### ไม่มีสิ่งใดถูกดักจับ

- ยืนยันว่าโปรเซสที่ต้องการสกัดกั้นเชื่อมต่อกับ `dport` ที่กำหนดค่าไว้จริง
  (ค่าเริ่มต้นคือ `443`)
- ยืนยันว่าโปรเซสเชื่อถือ CA แบบไดนามิก โดย CA จะถูกติดตั้งภายใต้ชื่อ
  `omniroute-tproxy-ca.crt`; แอปที่มี trust store ของตนเอง (Firefox/Chrome NSS)
  อาจต้องเพิ่มใบรับรองลงในนั้นด้วย
- เรียกใช้การทดสอบตัวเอง **Diagnose** ของ AgentBridge (ดู
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) เพื่อตรวจสอบความน่าเชื่อถือของใบรับรอง / สถานะ
  ของเซิร์ฟเวอร์

### มีกฎไฟร์วอลล์ตกค้างหลังจากการขัดข้อง

`revertTproxy()` เป็นการย้อนกลับการใช้งานอย่างตรงกันและรองรับการเรียกซ้ำโดยให้ผลลัพธ์เหมือนเดิม การหยุด
โหมดจะย้อนกลับกฎต่าง ๆ; หาก OmniRoute ถูกปิดระหว่างเซสชัน ให้ใช้การดำเนินการ
**Repair** ของ AgentBridge (`POST /api/tools/agent-bridge/repair`) เพื่อย้อนกลับสถานะของระบบ
ที่ตกค้างอยู่ (การปลอมแปลง DNS, root CA, พร็อกซีระบบ) กฎ `mangle` และ route ของ TPROXY
จะถูกล้างโดยอัตโนมัติเมื่อรีบูตด้วย

### ลูปไม่สิ้นสุด / พร็อกซีสกัดกั้นการส่งต่อของตนเอง

นี่คือกรณีป้องกันลูป โปรดยืนยันว่า `bypassMark` แตกต่างจาก `mark` (การตรวจสอบความถูกต้อง
จะบังคับใช้เงื่อนไขนี้) และการส่งต่อใช้ `connectMarked` (ซึ่งใช้อยู่แล้วใน `realForward`)
ดู [§5 การป้องกันลูป](#anti-loop-so_mark)
