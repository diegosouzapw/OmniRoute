สองวิธีในการวาง Cursor ไว้หลัง OmniRoute โดยไม่ต้องมีเซสชัน IDE:

1. **ผู้ให้บริการ `cursor-api`** (การ์ด "Cursor API", นามแฝง `cua`): ผู้ให้บริการแบบ API key
   ที่จัดเก็บ Cursor user API key (`crsr_…` ซึ่งสร้างได้ที่
   `https://cursor.com/dashboard/api`) จากนั้นไคลเอ็นต์ OmniRoute ใดๆ ก็สามารถเข้าถึง
   โมเดล Cursor ผ่าน `/v1/chat/completions` ในรูปแบบ `cursor-api/<model>` หรือ
   `cua/<model>` พร้อมเลเยอร์โควตา การสำรองเมื่อเกิดข้อผิดพลาด และการบันทึกล็อกตามปกติ ส่วนผู้ให้บริการ IDE
   (`cursor`, เซสชัน OAuth/IDE) ยังคงไม่มีการเปลี่ยนแปลง
2. **การส่งผ่าน Cursor CLI**: กำหนดให้ Cursor CLI (`agent`) ชี้ไปยัง OmniRoute เพื่อให้
   ทุก RPC ที่ CLI เรียกได้รับการยืนยันตัวตนด้วย OmniRoute API key จากนั้นส่งต่อ
   ไปยัง Cursor โดยใช้ข้อมูลรับรองของการเชื่อมต่อ `cursor-api` และบันทึกไว้ใน
   หน้า Logs

## เหตุผลที่ต้องแลกเปลี่ยนคีย์

`api2.cursor.sh` ปฏิเสธคีย์ `crsr_…` แบบดิบเมื่อใช้เป็น Bearer token (401) โดย Cursor
CLI จะ POST คีย์ไปยัง `/auth/exchange_user_api_key` ก่อน และรับ JWT ของเซสชัน
ที่หมดอายุหลังจากหนึ่งชั่วโมง ส่วน `refreshToken` ที่ส่งกลับมาจะมีค่า
`exp` เดียวกัน ดังนั้นการรีเฟรชจึงหมายถึงการแลกเปลี่ยนคีย์ใหม่อีกครั้ง
`open-sse/services/cursorApiKeyAuth.ts` ทำหน้าที่แลกเปลี่ยนดังกล่าว แคชโทเค็นเซสชันหนึ่งรายการ
ต่อหนึ่งคีย์ แลกเปลี่ยนใหม่ก่อนหมดอายุห้านาที และลบโทเค็นที่แคชไว้
เมื่อ Cursor ตอบกลับด้วย 401 โดย `CursorExecutor` จะเรียกใช้ส่วนนี้ก่อนเปิด
สตรีมต้นทางสำหรับการเชื่อมต่อ `cursor-api`

## ผู้ให้บริการ `cursor-api`

รีจิสทรี: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"` โดยใช้ `format`, `baseUrl` และ
`models` เดียวกับ `cursor`) การ์ดแค็ตตาล็อก:
`src/shared/constants/providers/apikey/specialty-media.ts` แมปตัวดำเนินการ:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`)

แดชบอร์ด: Providers → Cursor API → Add API key

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

จากนั้น:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

หมายเหตุ:

- รายการโมเดลสำหรับ `cursor-api` มาจากรีจิสทรี Cursor แบบคงที่ (เป็น
  รายการเดียวกับที่ผู้ให้บริการ IDE ใช้เป็นตัวสำรอง) โดยไม่จำเป็นต้องติดตั้ง `cursor-agent`
  บนโฮสต์ OmniRoute
- `POST /api/providers/{id}/refresh-cursor` ใช้สำหรับผู้ให้บริการ `cursor` IDE
  เท่านั้น การเชื่อมต่อ `cursor-api` ไม่มีเซสชัน IDE ที่ต้องต่ออายุ

## ID โมเดลแบบเนทีฟและระดับ effort

สำหรับ `cursor` / `cu` และ `cursor-api` / `cua` ตัวปรับมาตรฐาน Claude-effort ที่ใช้ร่วมกัน
จะคง ID โมเดลที่ร้องขอไว้ตามเดิม Cursor สามารถประกาศส่วนต่อท้าย เช่น
`-low` เป็นส่วนหนึ่งของ ID โมเดลจริง แทนที่จะเป็นนามแฝง effort ของ OmniRoute
ตัวดำเนินการ Cursor จะรักษาค่าที่ตรงกับแค็ตตาล็อกแบบเรียลไทม์ทุกประการไว้ เมื่อไม่พบ
ค่าที่ตรงกัน ตัวแก้ไขโมเดลที่มีอยู่จะรับผิดชอบการแปลงส่วนต่อท้ายเป็นพารามิเตอร์สำรอง

สิ่งนี้ไม่เปลี่ยนแปลงการปรับมาตรฐาน effort สำหรับเส้นทาง Claude โดยตรง เส้นทางที่เข้ากันได้กับ Claude
หรือเส้นทาง Vertex ทั้งนี้ ความพร้อมใช้งานยังคงขึ้นอยู่กับแค็ตตาล็อกและสิทธิ์ใช้งาน
ของบัญชี Cursor ที่เลือก

## การส่งผ่าน Cursor CLI

เส้นทาง: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts` โดยคำนำหน้า `/api/cursor-cli/` ได้รับการ
ลงทะเบียนใน `src/shared/constants/publicApiRoutes.ts` เนื่องจากตัวจัดการ
บังคับใช้การยืนยันตัวตนด้วยตัวเอง:

| เส้นทาง                                                                                                                        | การยืนยันตัวตนที่คาดหวังจาก CLI   | สิ่งที่ OmniRoute ดำเนินการ                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                             | `Bearer <คีย์ API ของ OmniRoute>` | ตรวจสอบความถูกต้องของคีย์ สร้าง JWT แบบ HS256 ที่มีอายุ 1 ชั่วโมง (ลงนามด้วย `JWT_SECRET`) แล้วส่งคืน                                                                |
| เส้นทางอื่นทั้งหมด (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <JWT ดังกล่าว>`           | ตรวจสอบผู้ออก กลุ่มเป้าหมาย และวันหมดอายุ เลือกการเชื่อมต่อ `cursor-api` ที่ใช้งานอยู่ สลับส่วนหัว Authorization เป็นโทเค็น Cursor ที่แลกมา แล้วสตรีมการตอบกลับคืนไป |

CLI ถอดรหัส `exp` จากโทเค็นใดก็ตามที่ได้รับ ดังนั้นหากส่งโทเค็นแบบทึบแสง
ให้ CLI จะทำให้มีการแลกโทเค็นใหม่ก่อนคำขอเกือบทุกครั้ง JWT ที่สร้างขึ้นช่วย
หลีกเลี่ยงปัญหานี้ การตอบกลับ 401 จาก OmniRoute จะทำให้ CLI แลกโทเค็นอีกครั้ง

### การตั้งค่า

1. สร้างคีย์ API ของ OmniRoute (แดชบอร์ด → คีย์ API) และการเชื่อมต่อ `cursor-api`
2. กำหนดให้ CLI ใช้ HTTP/1.1 สำหรับสตรีมของเอเจนต์ ในไฟล์
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   หากไม่มีการตั้งค่านี้ CLI จะเปิดรอบการทำงานของเอเจนต์ผ่าน HTTP/2 ไปยัง
   โฮสต์เอเจนต์ที่กำหนดค่าแยกไว้ และมีเพียง RPC ของระนาบควบคุมเท่านั้นที่ผ่าน
   เอนด์พอยต์นี้

3. เรียกใช้ CLI กับ OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

ทุกฮอปจะปรากฏใน Logs โดยมีผู้ให้บริการเป็น `cursor-api` ประเภทคำขอเป็น
`cursor-cli` และเส้นทางเป็น `/api/cursor-cli/<rpc>` ซึ่งเชื่อมโยงกับคีย์ API
ของ OmniRoute และการเชื่อมต่อที่ให้บริการคำขอนั้น

### รูปแบบความล้มเหลว

| สถานการณ์                                          | การตอบกลับไปยัง CLI                         |
| -------------------------------------------------- | ------------------------------------------- |
| ไม่รู้จักคีย์ OmniRoute และ `REQUIRE_API_KEY=true` | 401 `unauthenticated` ระหว่างการแลกโทเค็น   |
| `REQUIRE_API_KEY=false`                            | เซสชันแบบไม่ระบุตัวตน (ทำงานเหมือน `/v1/*`) |
| JWT ของเซสชันหมดอายุ / มาจากภายนอก / ถูกแก้ไข      | 401 โดย CLI จะแลกโทเค็นใหม่                 |
| คีย์ API ของ OmniRoute ถูกเพิกถอนหลังจากแลกโทเค็น  | 401 ใน RPC ถัดไป                            |
| ไม่มีการเชื่อมต่อ `cursor-api` ที่ใช้งานอยู่       | 503 `unavailable`                           |
| Cursor ปฏิเสธคีย์ของการเชื่อมต่อ                   | 401 `unauthenticated` และลบเซสชันที่แคชไว้  |
| ไม่สามารถเข้าถึงต้นทางได้                          | 502 `unavailable` (ข้อความผ่านการกรองแล้ว)  |
| ไม่ได้ตั้งค่า `JWT_SECRET`                         | 503 ระหว่างการแลกโทเค็น                     |
