## ภาพรวม

Quota Sharing Engine กระจายโควตาตามเวลาของผู้ให้บริการ (เช่น หน้าต่างเวลา 5 ชั่วโมงของ Codex,
Kimi 1500 คำขอ/ชม.) อย่างเป็นธรรมระหว่าง API key หลายรายการที่ใช้การเชื่อมต่อ
เดียวกัน

**ปัญหาที่ระบบนี้แก้ไข:** OmniRoute ทำหน้าที่เป็นพร็อกซีให้ API key หลายรายการกับบัญชี
ผู้ให้บริการต้นทางเดียวกัน หากไม่มีตรรกะการแบ่งปัน การส่งคำขอจำนวนมากอย่างฉับพลันจากคีย์ A อาจใช้
โควตาของผู้ให้บริการสำหรับชั่วโมงนั้นจนหมด ทำให้คีย์ B และ C ถูกบล็อกจนกว่าหน้าต่างเวลาจะรีเซ็ต
เอนจินป้องกันปัญหานี้ด้วยวิธีต่อไปนี้:

1. ติดตามการใช้งานแบบต่อเนื่องของแต่ละคีย์ในแต่ละมิติ (%, คำขอ, โทเค็น, $)
2. ใช้อัลกอริทึมการแบ่งส่วนอย่างเป็นธรรมที่ไม่ปล่อยให้ทรัพยากรว่าง: คีย์สามารถยืมส่วนแบ่งที่ไม่ได้ใช้งาน
   ได้ตราบใดที่พูลส่วนกลางยังไม่อิ่มตัว
3. บังคับใช้ผลลัพธ์ในเส้นทางหลัก (`chatCore.ts`) ก่อนที่คำขอ
   จะไปถึงตัวดำเนินการต้นทาง

## อัลกอริทึม: การแบ่งส่วนอย่างเป็นธรรมที่ไม่ปล่อยให้ทรัพยากรว่าง

นำไปใช้ใน `src/lib/quota/fairShare.ts`

### โหมด

| เงื่อนไข                                   | โหมด        | ลักษณะการทำงาน                                                |
| ------------------------------------------ | ----------- | ------------------------------------------------------------- |
| `globalUsedPercent < saturationThreshold`  | **ผ่อนปรน** | คีย์สามารถยืมได้สูงสุดถึงขีดจำกัดส่วนกลางลบด้วยยอดรวมที่ใช้ไป |
| `globalUsedPercent >= saturationThreshold` | **เข้มงวด** | บังคับใช้ส่วนแบ่งที่เป็นธรรมของแต่ละคีย์อย่างเคร่งครัด        |

ค่าเริ่มต้นคือ `saturationThreshold = 0.5` (ตัวแปรสภาพแวดล้อม `QUOTA_SATURATION_THRESHOLD`)

### การตัดสินใจในแต่ละมิติ

สำหรับแต่ละมิติที่ทำงานอยู่ในพูล เอนจินจะคำนวณดังนี้:

```
fairShareAllowed = poolLimit × (allocationWeight / 100)
consumed        = ค่าการใช้งานแบบต่อเนื่องปัจจุบันของคีย์นี้ (จาก QuotaStore.peek)
remaining       = fairShareAllowed - consumed
```

จากนั้น:

- **`policy = hard`**: หาก `consumed > fairShareAllowed` และอยู่ในโหมดเข้มงวด → **บล็อก**
- **`policy = soft`**: หาก `consumed > fairShareAllowed` และอยู่ในโหมดเข้มงวด → **ลงโทษ** (ลดลำดับความสำคัญในชุดผสม และจะไม่บล็อกโดยเด็ดขาด)
- **`policy = burst`**: อนุญาตตราบใดที่ส่วนกลางยังมีความจุเหลืออยู่ โดยไม่คำนึงถึงส่วนแบ่งที่เป็นธรรม

### เพดานสูงสุดแบบสัมบูรณ์

`capValue` + `capUnit` ในการจัดสรรเป็นเพดานสูงสุดแบบตายตัว ซึ่งไม่ขึ้นอยู่กับโหมดหรือ
นโยบาย มิติใดก็ตามที่ `consumed >= capValue` จะ **บล็อก** คำขอเสมอ

### การตรวจสอบหลายมิติ

คำขอจะถูกบล็อกหากมี **มิติใดก็ตาม** ในพูลที่จะบล็อกคำขอนั้น แต่ละมิติ
เป็นอิสระต่อกัน — การใช้โควตา 5h% จนหมดจะไม่ส่งผลต่อมิติ weekly%

### การยืม

ในโหมดผ่อนปรน คีย์ที่ใช้โควตาต่ำกว่าส่วนที่ได้รับการจัดสรรสามารถใช้ส่วนเกินจาก
ส่วนแบ่งที่คีย์อื่นไม่ได้ใช้ได้ โดยมีสูตรดังนี้:

```
maxAllowed = globalLimit - consumedByOtherKeys
```

โดยที่ `consumedByOtherKeys = consumedTotal - consumedByThisKey` เพดานส่วนกลาง
(`limit` ของพูลสำหรับมิตินั้น) จะเป็นเพดานสูงสุดแบบตายตัวเสมอ

## ตัวนับแบบหน้าต่างเลื่อน

นำไปใช้ใน `src/lib/quota/sqliteQuotaStore.ts` และ `redisQuotaStore.ts`

มีสองบัคเก็ตต่อ `(apiKeyId, dimensionKey)`:

- `curr`: บัคเก็ตปัจจุบัน (`floor(nowMs / windowMs)`)
- `prev`: บัคเก็ตก่อนหน้า (`curr - 1`)

ค่าต่อเนื่องที่มีผล:

```
effectiveBucketIndex = floor(nowMs / windowMs)
bucketStartMs        = effectiveBucketIndex × windowMs
elapsed              = nowMs - bucketStartMs
weight               = 1 - elapsed / windowMs

effective = prev × weight + curr
```

**ความแม่นยำ**: แม่นยำประมาณ 99% ค่าคลาดเคลื่อนสูงสุดคือ 1% ของขนาดหน้าต่าง ณ
รอยต่อระหว่างบัคเก็ต (เป็นข้อจำกัดโดยธรรมชาติของการประมาณแบบ 2 บัคเก็ต)

### การทำงานพร้อมกัน

ไดรเวอร์ SQLite: mutex ในหน่วยความจำต่อคีย์ `(apiKeyId | dimensionKey)` ป้องกันภาวะ
การแข่งขันแบบอ่าน-แก้ไข-เขียน โดยใช้รูปแบบเดียวกับการป้องกันปัญหา anti-thundering-herd ใน `src/sse/services/auth.ts`

ไดรเวอร์ Redis: สคริปต์ Lua EVAL สำหรับการเพิ่มค่าแบบอะตอมมิก — ทำงานเป็นคำสั่ง Redis เดียว

## ไดรเวอร์

### SQLite (ค่าเริ่มต้น, ไม่ต้องติดตั้ง)

- ตาราง: `quota_consumption` (ดู migration `073_quota_pools.sql` / `074_quota_consumption.sql`)
- เหมาะที่สุดสำหรับการติดตั้งใช้งานแบบอินสแตนซ์เดียว
- ข้อมูลถาวรทั้งหมดอยู่ในฐานข้อมูล SQLite เดิมของ OmniRoute (`DATA_DIR/storage.sqlite`)

### Redis (ตัวเลือกเสริม, หลายอินสแตนซ์)

- ต้องใช้แพ็กเกจ npm `ioredis`
- ตัวนับจัดเก็บไว้ใน Redis ส่วนข้อมูลเมตา (พูล/การจัดสรร) ยังคงอยู่ใน SQLite
- เหมาะที่สุดสำหรับการติดตั้งใช้งานแบบหลายเรพลิกาที่ต้องแชร์ตัวนับร่วมกัน

### การสลับไดรเวอร์

ผ่าน UI การตั้งค่า (`/dashboard/settings` → ที่เก็บโควตา) หรือผ่านตัวแปรสภาพแวดล้อม:

```bash
QUOTA_STORE_DRIVER=redis
QUOTA_STORE_REDIS_URL=redis://localhost:6379
```

การตั้งค่าใน DB มีลำดับความสำคัญสูงกว่าตัวแปรสภาพแวดล้อม หาก `driver=redis` แต่ไม่มี URL หรือ
ไม่ได้ติดตั้ง `ioredis` แฟกทอรีจะย้อนกลับไปใช้ SQLite และบันทึกคำเตือนในล็อก

ลำดับการเลือกไดรเวอร์:

1. การตั้งค่า DB `quotaStore.driver`
2. ตัวแปรสภาพแวดล้อม `QUOTA_STORE_DRIVER`
3. ค่าเริ่มต้น: `sqlite`

พูลหนึ่งสามารถมีได้หลายมิติ โดยแต่ละมิติทำงานอย่างเป็นอิสระ:

```ts
QuotaDimension {
  unit: "percent" | "requests" | "tokens" | "usd",
  window: "5h" | "hourly" | "daily" | "weekly" | "monthly",
  limit: number,  // เพดานรวมของพูลสำหรับมิตินี้
}
```

**ตัวอย่าง: แผน Codex** (5h% + weekly%):

```json
[
  { "unit": "percent", "window": "5h", "limit": 100 },
  { "unit": "percent", "window": "weekly", "limit": 100 }
]
```

คำขอต้องเป็นไปตามทุกมิติจึงจะได้รับอนุญาต

## การผสานรวมกับไปป์ไลน์

### ฮุก PRE (`open-sse/handlers/chatCore.ts`)

ทำงานก่อนตัวดำเนินการต้นทาง หลังจากตรวจสอบการยืนยันตัวตนและนโยบายแล้ว:

```
resolveComboTargets / handleSingleModel
  → enforceQuotaShare(apiKeyId, connectionId, provider, estimatedCost)
      → getQuotaStore().peek() ต่อมิติ
      → fairShare.decideFairShare()
      → หากบล็อก → ส่งคืน 429 (buildErrorBody, กฎตายตัว #12)
      → หากอนุญาต + ลดลำดับความสำคัญ → ตั้งค่า quotaSoftPenalty=true ให้กับตัวเลือก
  → executor.execute()
```

**เปิดให้ผ่านเมื่อเกิดข้อผิดพลาด**: หาก `enforceQuotaShare` ส่งข้อผิดพลาด คำขอจะได้รับอนุญาตให้ดำเนินการต่อ
พร้อมบันทึกล็อก `pino.warn` ซึ่งช่วยป้องกันไม่ให้บั๊กของกลไกโควตาบล็อกทราฟฟิกทั้งหมด

### ฮุก POST (บันทึกการใช้งาน)

หลังจากได้รับการตอบกลับสำเร็จ:

```
ตัวดำเนินการส่งคืนผลสำเร็จ
  → spendRecorder.recordConsumption(apiKeyId, connectionId, provider, actualCost)
      → getQuotaStore().consume() ต่อมิติ
      → เปิดให้ผ่านเมื่อเกิดข้อผิดพลาด: บันทึกข้อผิดพลาดเป็น pino.warn และไม่ส่งต่อไปยังไคลเอนต์
```

**หมายเหตุเกี่ยวกับความคลาดเคลื่อน**: หาก `consume` ล้มเหลวหลังจากตอบกลับ ตัวนับแบบช่วงเวลาเลื่อนจะนับต่ำกว่าความเป็นจริง
สัญญาณความอิ่มตัวจากผู้ให้บริการ (เช่น `anthropic-ratelimit-unified-5h-utilization`)
จะแก้ไขค่าประมาณโดยรวมในคำขอถัดไป

### ค่าปรับแบบนุ่มนวลของคอมโบ (`open-sse/services/combo.ts`)

เมื่อ `decision.deprioritize === true`:

```ts
if (candidate.quotaSoftPenalty) {
  score *= QUOTA_SOFT_DEPRIORITIZE_FACTOR; // ค่าเริ่มต้น 0.7
}
```

ค่าปรับจะถูกนำไปใช้หลังจากปัจจัยการให้คะแนนอื่นทั้งหมด โดยจะลดความน่าจะเป็นที่ระบบคอมโบอัตโนมัติ
จะเลือกคีย์ที่ใช้งานถึงขีดจำกัด โดยไม่บล็อกคีย์นั้นโดยเด็ดขาด

## การแก้ไขปัญหา

### กำหนดค่า Redis แล้วแต่เชื่อมต่อไม่ได้

ตรวจสอบว่าติดตั้ง `ioredis` แล้ว (`npm ls ioredis`) และสามารถเข้าถึง
`QUOTA_STORE_REDIS_URL` ได้ หากการเชื่อมต่อล้มเหลว factory จะย้อนกลับไปใช้ SQLite (บันทึกที่ระดับ
`warn`)

### `peek` ส่งคืนข้อมูลเก่า / เปิดให้ผ่านเมื่อเกิดข้อผิดพลาด

หาก `peek` โยนข้อผิดพลาด `enforceQuotaShare` จะถือว่าผลลัพธ์เป็น "อนุญาต" (เปิดให้ผ่านเมื่อเกิดข้อผิดพลาด)
ตรวจสอบบันทึก `pino` สำหรับรายการ `quota:enforce` และ `quota:factory` เพื่อระบุ
สาเหตุที่แท้จริง

### ตัวนับการใช้งานคลาดเคลื่อน

หากการใช้งานจริงของผู้ให้บริการแตกต่างจากตัวนับ ถือว่าเป็นพฤติกรรมที่คาดไว้ — หน้าต่างเลื่อนแบบ
2 บักเก็ตมีข้อผิดพลาดประมาณ 1% ที่ขอบเขตของหน้าต่าง และ `consume` ทำงานแบบ
ส่งแล้วไม่รอผลหลังการตอบกลับ สัญญาณความอิ่มตัว (`saturationSignals.ts`)
จะอ่านอัตราการใช้งานจริงของผู้ให้บริการด้วย TTL 30 วินาที และปรับ `globalUsedPercent`
ตามนั้น

### พูลแสดง "ไม่มีข้อมูล" สำหรับอัตราการใช้

`computeBurnRate` ต้องมีตัวอย่างข้อมูลย้อนหลังอย่างน้อย 2 รายการ พูลใหม่ที่ยังไม่มีการเรียก
`consume` ก่อนหน้านี้จะแสดง `tokensPerSecond: 0` และ `timeToExhaustionMs: null`

## การย้ายข้อมูลจาก localStorage

เมื่อ `/dashboard/costs/quota-share` โหลดเป็นครั้งแรก hook `useLocalStoragePoolMigration`
จะตรวจสอบว่า:

1. `localStorage.getItem("omniroute:quota-share:pools")` ไม่ว่างเปล่า
2. `GET /api/quota/pools` ส่งคืน `[]` (DB ว่างเปล่า)

หากทั้งสองเงื่อนไขเป็นจริง ระบบจะส่งแต่ละ pool แบบเดิมไปยัง `POST /api/quota/pools` เป็นชุด
จากนั้นลบ key ใน localStorage การย้ายข้อมูลนี้เป็นแบบ idempotent: เงื่อนไขข้อ 2 ช่วยป้องกัน
การย้ายข้อมูลซ้ำ

## การจัดประเภทกลยุทธ์ภายใน

`quota-share` เป็นกลยุทธ์การกำหนดเส้นทางสำหรับ **ใช้ภายในเท่านั้น** (`INTERNAL_ROUTING_STRATEGY_VALUES` ใน

ที่ผู้ใช้เลือกได้ใน UI หรือ API

## สรุปสคีมา DB

มีการเพิ่มตารางสามตารางโดย migration `078`, `079` และ `085`:

- `quota_pools` + `quota_allocations` — นิยาม pool และการจัดสรรสำหรับแต่ละ key
- `quota_consumption` — ตัวนับแบบหมุนเวียน 2 bucket สำหรับแต่ละ `(apiKeyId, dimensionKey)`
- `provider_plans` — การกำหนดค่า provider plan แบบแทนที่ด้วยตนเอง (dimensions JSON ต่อ connectionId)

ตารางทั้งหมดเพิ่มผ่าน migration แบบ idempotent โดยใช้ `CREATE TABLE IF NOT EXISTS`
