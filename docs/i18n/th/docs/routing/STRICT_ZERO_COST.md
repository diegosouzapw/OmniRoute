> `hidePaidModels` (`open-sse/services/autoCombo/paidModelFilter.ts`, #6512) สำหรับผู้ดำเนินการ
> ที่ต้องการการรับประกันอย่างเด็ดขาดว่าจะไม่มีค่าใช้จ่ายทางการเงินส่วนเพิ่มใดๆ ไม่ใช่เพียง
> "มีการระบุไว้ว่าใช้ฟรี"

## เหตุผลที่สิ่งนี้มีอยู่ และเหตุผลที่ `hidePaidModels` เพียงอย่างเดียวยังไม่เพียงพอ

`hidePaidModels` ตอบคำถามว่า "ขณะนี้โมเดลนี้ถูกจัดประเภทว่าใช้ฟรีใน `FREE_MODEL_BUDGETS`
หรือไม่?" — ซึ่งเป็นข้อเท็จจริงจากแค็ตตาล็อก ณ เวลาใดเวลาหนึ่ง โดยตรวจสอบผ่าน
`isFreeModel()`/`providerHasFreeModels()` (`src/shared/utils/freeModels.ts`) แต่ไม่ได้กล่าวถึง
ความเสี่ยงจริงสองประการ:

1. สิทธิ์ใช้งานของระดับฟรีแบบ `recurring-*`/`one-time-initial` อาจถูกใช้จน **หมด** —
   แค็ตตาล็อกยังคงระบุว่าโมเดลนี้ใช้ฟรี แต่บัญชีที่อยู่เบื้องหลังไม่มีโควตาเหลือแล้ว
2. การใช้งานเกินระดับฟรีไม่ได้ถูกหยุดอย่างเด็ดขาดเสมอไป ผู้ให้บริการบางรายระบุไว้อย่างชัดเจนว่า
   ไม่สามารถผูกวิธีการชำระเงินได้เลย ("ไม่ต้องใช้บัตรเครดิต") ขณะที่บางรายไม่ได้ระบุไว้ และมี
   บางรายเรียกเก็บเงินโดยอัตโนมัติเมื่อใช้งานเกินสิทธิ์ฟรี

`hidePaidModels` ไม่สามารถแยกแยะกรณีเหล่านี้ได้ — และไม่เคยถูกออกแบบมาให้ทำเช่นนั้น
STRICT_ZERO_COST เพิ่มการตรวจสอบสองประการนี้โดยตรง โดยประเมินแยกตาม candidate
**ก่อน** การจัดอันดับตามหมวดหมู่/ระดับ และ **ก่อน** dispatch — ไม่ใช่หลังจากส่งคำขอออกไปแล้ว

## การจำแนก candidate

สำหรับ candidate แต่ละรายการใน pool (`open-sse/services/autoCombo/virtualFactory.ts::buildPreparedPool`
โดยอยู่ถัดจาก `filterPaidOnlyCandidates`):

1. **ไม่มีอยู่ใน `FREE_MODEL_BUDGETS` เลย** → ถูกตัดออก ซึ่งครอบคลุมทั้งโมเดลที่มีค่าใช้จ่ายจริง
   และ provider/model ใดๆ ที่ OmniRoute ยังไม่ได้จัดประเภท — candidate ใหม่จะเริ่มต้นด้วยการ
   ถูกตัดออก ไม่ใช่ถูกรวมไว้
2. **`freeType: "keyless"`** → ผ่านทันที **แต่เฉพาะ candidate ที่มาจากเส้นทางแบบไม่ต้อง
   ยืนยันตัวตนจริงๆ เท่านั้น** (`connectionId === SYNTHETIC_NOAUTH_CONNECTION_ID`,
   `open-sse/services/autoCombo/resilienceCandidateFilter.ts`) candidate ดังกล่าวไม่มี
   ข้อมูลประจำตัว ดังนั้นคำขอที่ส่งผ่าน candidate นี้จึงไม่สามารถถูกเรียกเก็บเงินได้ —
   ไม่จำเป็นและไม่สามารถตรวจสอบระหว่างรันไทม์ได้ provider/model ที่ระบุเป็น `keyless`
   ในแค็ตตาล็อกเดียวกันแต่เข้าถึงผ่านการเชื่อมต่อ DB **จริง** (`connectionId` เป็น id
   ของการเชื่อมต่อจริง หรือ candidate มี `allowedConnectionIds`) จะ **ไม่ได้** รับทางลัดนี้ —
   metadata แบบ `keyless` อธิบายเฉพาะเส้นทางแบบไม่ต้องยืนยันตัวตน ไม่ใช่ provider โดยทั่วไป
   และไม่เครอนุญาตบัญชีจริงที่ใช้ข้อมูลประจำตัว candidate ดังกล่าวจะเข้าสู่การตรวจสอบข้อ 3
   เช่นเดียวกับ candidate อื่นๆ ซึ่งจะถูกตัดออก เว้นแต่รายการในแค็ตตาล็อกจะมี
   `hardStopGuaranteed: true` แยกต่างหาก (รายการ `keyless` จริงจะไม่มีค่านี้ —
   ทางลัดดังกล่าวเป็นเส้นทางเดียวที่ทำให้รายการเหล่านั้นปลอดภัย)
3. **`freeType` อื่นๆ** (`recurring-daily`, `recurring-monthly`, `recurring-credit`,
   `recurring-uncapped`, `one-time-initial` และประเภทใดๆ ในอนาคตที่โมดูลนี้ไม่ได้
   จัดการเป็นกรณีพิเศษ) → ผ่านเฉพาะเมื่อเป็นไปตามเงื่อนไข **ทั้งหมด** ต่อไปนี้:
   - มีการตั้งค่า `hardStopGuaranteed: true` ในรายการแค็ตตาล็อก (`FreeModelBudget.hardStopGuaranteed`,
     `open-sse/config/freeModelCatalog.ts`) — เป็น **ข้อเท็จจริงที่คัดสรรและกำหนดด้วยตนเอง**
     เกี่ยวกับเงื่อนไขที่ provider เผยแพร่เอง (เช่น คำกล่าวที่ระบุอย่างชัดเจนว่า
     "ไม่ต้องใช้บัตรเครดิต") โดยไม่อนุมานจาก `freeType` หรือจากการตอบกลับ API แบบสด
     ค่าที่ยังไม่ได้ตั้ง (`undefined`) และ `false` จะถูกถือว่า "ไม่มีการรับประกัน" ทั้งคู่
   - มี usage adapter สำหรับ provider อยู่ใน `USAGE_FETCHER_PROVIDERS`
     (`open-sse/services/usage.ts`) — ซึ่งเป็น registry เดียวกับที่รองรับแดชบอร์ดโควตาและ
     `getUsageForProvider()` อยู่แล้ว หากไม่มี adapter → จะถูกตัดออกอย่างถาวรจนกว่าจะมีการเพิ่ม
   - `FreeAccessState` แบบสดที่แคชไว้สำหรับ **การเชื่อมต่อเฉพาะที่กำลังได้รับการประเมินจริง**
     มีค่า `status: "SAFE"` ได้รับการตรวจสอบภายในช่วงเวลา
     `settings.autoRefreshProviderQuotaInterval` (ค่าเริ่มต้น 180 วินาที — เป็นการตั้งค่า
     ที่มีอยู่แล้ว ไม่ใช่ตัวเลขใหม่) และรายงาน `remainingFreeAllowance` สูงกว่าค่าความปลอดภัย
     ส่วนเผื่อเล็กน้อย
4. **`freeType: "discontinued"`** → ถูกตัดออกเสมอ

## ความปลอดภัยของการเชื่อมต่อ (ตรวจสอบแยกตามการเชื่อมต่อ ไม่ใช่แยกตามตัวเลือก)

ตัวเลือกหนึ่งในพูล auto-combo ไม่ได้ผูกกับการเชื่อมต่อเดียวเสมอไป ตัวเลือกแบบ "เชิงตรรกะ"
(`connectionId: null`) จะมี allowlist ชื่อ `allowedConnectionIds` ซึ่งประกอบด้วยการเชื่อมต่อ/บัญชี
ของผู้ให้บริการจริงอย่างน้อยหนึ่งรายการ โดยรายการใดก็ได้สามารถใช้รองรับคำขอ และบัญชีที่จะใช้จริง
จะถูกตัดสินใจภายหลัง ณ เวลาส่งคำขอ โดย `open-sse/services/combo/autoStrategy.ts`
(นำ `allowedConnectionIds` ไปหาจุดร่วมกับตรรกะการเลือกการเชื่อมต่อของตัวเอง บริเวณบรรทัด 315-331)

STRICT_ZERO_COST ตรวจสอบสถานะการเข้าถึงฟรีของ **แต่ละการเชื่อมต่อใน allowlist ดังกล่าว
แยกกัน** (`evaluateCandidateConnections()` ใน `strictZeroCostFilter.ts`) และเขียน
`allowedConnectionIds` ใหม่ให้เหลือเฉพาะชุดย่อยที่ได้รับผลลัพธ์เป็น `SAFE` เท่านั้น — ไม่ใช่รายการ
ดั้งเดิมทั้งหมด และไม่ใช่สมาชิกเพียงรายการเดียวที่ถูกเลือกโดยพลการ กล่าวอย่างเป็นรูปธรรม:

- บัญชี A เป็น `SAFE` ส่วนบัญชี B เป็น `UNKNOWN`/โควตาหมด/มีค่าใช้จ่าย → เหลือเพียง A ที่เลือกใช้ได้
- ทุกบัญชีเป็น `UNKNOWN` → ตัวเลือกจะถูกตัดออกทั้งหมด (ชุดที่ปลอดภัยว่างเปล่า)
- ตัวเลือกที่มีการเชื่อมต่อเดียว (กำหนด `connectionId` โดยตรงและไม่มี allowlist) ซึ่งไม่ผ่าน
  จะถูกตัดออกทันที และจะไม่ถูกส่งคืนพร้อม `allowedConnectionIds` ที่ว่างเปล่า

เนื่องจาก `autoStrategy.ts` บังคับใช้ `allowedConnectionIds` เป็น hard allowlist อยู่แล้วก่อน
เลือกการเชื่อมต่อที่จะส่งคำขอไป การเขียนค่าใหม่ให้เหลือเฉพาะชุดย่อยที่ผ่านการตรวจสอบว่าเป็น `SAFE`
จึงเพียงพอที่จะรับประกันว่าการเชื่อมต่อที่ใช้จริง ณ เวลาส่งคำขอ จะเป็นการเชื่อมต่อที่ตัวกรองนี้ตรวจสอบแล้ว
เสมอ — ไม่ใช่บัญชีอื่นในตัวเลือกเดียวกันที่ยังไม่ได้รับการตรวจสอบ โปรดดู
`tests/unit/autoCombo/strict-zero-cost-connection-safety.test.ts` สำหรับหลักฐานการทดสอบการถดถอย
(กรณี keyless-bypass A/B/C และกรณีหลายบัญชี 1-5)

`ค้นพบโดยอัตโนมัติ`: ผู้ให้บริการ/โมเดลที่เปิดตัวในวันพรุ่งนี้และมี metadata ที่ถูกต้อง (อยู่ใน
catalog มี usage adapter และ `hardStopGuaranteed: true`) จะใช้งานได้ทันทีที่ OmniRoute รับรู้
ถึงรายการดังกล่าว — ไม่ต้องเปลี่ยนโค้ด ไม่ต้องเพิ่มรายการใน whitelist และไม่ต้องแก้ไขสิ่งใดในโมดูลนี้
รายการที่ถูกนำออกจาก catalog ก็จะหายไปในลักษณะเดียวกัน โปรดดู
`tests/unit/autoCombo/strict-zero-cost-autodiscovery.test.ts` สำหรับหลักฐานการทดสอบการถดถอย (ผ่าน
fixtures ที่ฉีดเข้าไปได้ โดยไม่แก้ไข catalog จริง)

## การแคชโควตา (`open-sse/services/autoCombo/freeAccessQuota.ts`)

นำ `getUsageForProvider()` มาใช้ซ้ำ — ไม่มีระบบโควตาชุดที่สอง มีแคชในหน่วยความจำระยะสั้น
ตลอดอายุของ process วางอยู่ด้านหน้า (มี TTL เท่ากับค่าเริ่มต้นของ
`autoRefreshProviderQuotaInterval`) เพื่อให้อัตราคำขอระดับ Telegram ไม่ก่อให้เกิดการเรียก
billing API แบบสดต่อหนึ่งตัวเลือกต่อหนึ่งคำขอ การอ่านเป็นแบบ synchronous: เมื่อไม่พบข้อมูลในแคช
จะส่งคืน `undefined` (→ ถูกคัดออก, fail-closed) และเริ่มการรีเฟรชในเบื้องหลังสำหรับการอ่าน
_ครั้งถัดไป_ — ไม่มีส่วนใดในเส้นทางการสร้างพูลตัวเลือกที่รอ network call

`invalidateFreeAccessState(provider, connectionId)` จะถูกเรียกจาก
`src/sse/services/auth.ts::markAccountUnavailable()` ทันทีที่การเชื่อมต่อล้มเหลวไม่ว่าด้วยเหตุผลใด
ดังนั้นการสร้างพูลครั้งถัดไปจะอ่านได้ผลว่าไม่พบข้อมูลในแคชที่สะอาด แทนที่จะอ่านรายการ `SAFE`
ที่ล้าสมัย — ไม่ต้องรอให้ TTL หมดอายุหลังได้รับการตอบกลับ 402/403/โควตาหมด

## ตัวป้องกัน ToS (แยกจากความปลอดภัยด้านค่าใช้จ่าย)

`excludeTosAvoid` (ค่าเริ่มต้นคือ `false`) จะตัด candidate ใดๆ ที่ผลการพิจารณา `tos` ซึ่งผ่านการคัดสรรแล้ว
(`FreeModelBudget.tos`) เป็น `"avoid"` โดยใช้ฟิลด์เดียวกับที่เอกสารข้างเคียงของ `hidePaidModels`
(`docs/reference/FREE_TIERS.md`) เติมข้อมูลไว้อยู่แล้ว ทั้งนี้จงใจแยกออกจาก
`freeAccessPolicy`: candidate อาจมีความปลอดภัยด้านค่าใช้จ่ายเป็น `SAFE` แต่ยังคงถูกตัดออกที่นี่ด้วย
เหตุผลด้านสัญญา หรือยังคงรวมอยู่เมื่อปิดตัวป้องกันนี้ แม้ว่าจะเปิด `freeAccessPolicy: "strict"` อยู่ก็ตาม

## การดูว่าตัวป้องกันตัดสิ่งใดออกบ้าง

`GET /v1/auto-combo/{channel}/candidates` แสดง candidate ทุกรายการ รวมถึงรายการที่ตัวป้องกันนี้
จะไม่อนุญาตให้ส่งต่อไปทำงาน และแต่ละรายการจะมี `freeAccessExclusion` โดยเป็น `null` เมื่อตรงตาม
เงื่อนไขของตัวป้องกัน มิฉะนั้นจะเป็นเหตุผล รายการนี้มีไว้รายงานเท่านั้นและไม่เคยบังคับใช้นโยบาย การปิด
นโยบายจะทำให้ฟิลด์นี้เป็น `null` ทุกแห่งและไม่มีค่าใช้จ่ายใดๆ

| `freeAccessExclusion`  | ความหมาย                                                                                                                          | สิ่งที่ควรทำ                                                                                                                   |
| :--------------------- | :-------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| `not-in-catalog`       | คู่ provider/model ไม่มีอยู่ใน `FREE_MODEL_BUDGETS`                                                                               | เพิ่มรายการที่ผ่านการคัดสรรแล้ว หรือยอมรับว่าคู่ใหม่จะเริ่มต้นด้วยสถานะถูกตัดออก ซึ่งเป็นไปตามการออกแบบ                        |
| `regime-not-free`      | มีอยู่ในแค็ตตาล็อก แต่ `freeType` ไม่ใช่ประเภทที่ให้สิทธิ์เข้าถึงฟรี (เช่น แพ็กเกจที่ยกเลิกให้บริการแล้ว)                         | ไม่มีสิ่งใดต้องแก้ไข โมเดลนี้มีค่าใช้จ่าย                                                                                      |
| `no-hard-stop`         | เป็นรูปแบบการใช้งานฟรี แต่ `hardStopGuaranteed` ไม่ใช่ `true` ดังนั้นการใช้งานเกินโควตาอาจเริ่มคิดค่าบริการโดยไม่มีการแจ้งเตือน   | ตรวจสอบข้อกำหนดของ provider และตั้งค่า flag พร้อมระบุแหล่งข้อมูลไว้ใน comment — ห้ามตั้งค่าเพียงเพื่อขยายแค็ตตาล็อก            |
| `contradictory-noauth` | candidate แบบไม่ต้องยืนยันตัวตนซึ่งรายการในแค็ตตาล็อกไม่ได้เป็น `keyless` ระบบจะปฏิเสธโดยค่าเริ่มต้นเมื่อ metadata ไม่สอดคล้องกัน | แก้ไขรายการในแค็ตตาล็อก เนื่องจากข้อเท็จจริงทั้งสองขัดแย้งกัน                                                                  |
| `exhausted`            | ค่าที่อ่านล่าสุดระบุว่าใช้โควตาหมดแล้ว                                                                                            | รอการรีเซ็ต กรณีนี้จะแก้ไขตัวเองได้                                                                                            |
| `state-unknown`        | ไม่มีค่าการใช้งานโควตา หรือค่าที่มีเก่าเกินกว่าจะเชื่อถือได้                                                                      | ตรวจสอบเพิ่มเติม: provider อาจไม่มี usage adapter ที่ลงทะเบียนไว้ หรือการดึงข้อมูลโควตาอาจล้มเหลว                              |
| `no-connection`        | candidate ไม่มี account ใดๆ ให้ตรวจสอบ                                                                                            | นี่ไม่ใช่ปัญหาเกี่ยวกับโควตา: candidate ถูกสร้างขึ้นโดยไม่มี connection จึงไม่เคยมีการค้นหาข้อมูลใดๆ ให้ตรวจสอบวิธีประกอบ pool |

สองรายการสุดท้ายเป็นคู่ที่ควรแยกออกจากกัน โควตาที่หมดแล้วจะรีเซ็ตได้เอง แต่ค่าที่ไม่เคยมาถึง
หมายความว่ากระบวนการค้นหาข้อมูลนั้นเสีย และก่อนหน้านี้ทั้งสองกรณีดูเหมือนกันจากภายนอก กล่าวคือ
candidate เพียงแค่หายไป

**ยังมีช่องว่างหนึ่งจุด และเป็นสิ่งที่ตั้งใจไว้** `excludeTosAvoid` ยังคงลบ candidate ก่อนสร้าง
รายการ ดังนั้นโมเดลที่ได้รับการคัดสรรให้มี `tos: "avoid"` จะไม่ปรากฏโดยไม่มีการระบุเหตุผล ซึ่งเป็น
การมองไม่เห็นแบบเดียวกับที่ส่วนนี้เพิ่งแก้ไขให้กับตัวป้องกันการใช้งานแบบไม่มีค่าใช้จ่าย การปิดช่องว่างนี้
ด้วยจำเป็นต้องตัดสินใจว่าการตัดออกด้วยเหตุผลด้าน ToS ควรรายงานอย่างไร ซึ่งเป็นคนละประเด็นกับ
ความปลอดภัยด้านค่าใช้จ่าย หน้านี้จึงระบุช่องว่างดังกล่าวแทนที่จะแสร้งทำเป็นว่าไม่มีอยู่

สำหรับการเปรียบเทียบก่อนและหลังแบบออฟไลน์ `npx tsx scripts/ad-hoc/dry-run-strict-zero-cost.ts` ยังคงใช้งานได้
กับผลลัพธ์ candidates ของ instance ที่กำลังทำงาน โดยจะอ่าน `connectionId` จริงของ candidate แต่ละรายการ ดังนั้นจึง
ทดสอบเส้นทางความปลอดภัยของ connection ด้วย candidate แบบ keyless ต้องมาพร้อมกับ
`connectionId` แบบ no-auth สังเคราะห์เท่านั้น ห้ามเป็น connection จริง ปัจจุบันเส้นทางอัตโนมัติแบบ keyless ที่มีมาให้คือ OpenCode Free ส่วนจำนวน candidate ที่แน่นอน
ยังคงขึ้นอยู่กับการค้นพบโมเดลแบบสด และควรวัดจาก deployment เป้าหมายแทนการ
คัดลอกจากการรันครั้งเก่า candidate แบบ `recurring-*` จะผ่านก็ต่อเมื่อมีทั้ง
usage adapter ที่ลงทะเบียนไว้และ `hardStopGuaranteed: true` เท่านั้น metadata ที่ไม่ครบถ้วนจะยังคงถูกปฏิเสธโดยค่าเริ่มต้น

เมื่อใช้ `excludeTosAvoid: true` candidate ทุกตัวที่ได้รับการคัดสรรให้มี `tos: "avoid"` จะถูกลบออก ปัจจุบัน OpenCode Free
มีผลการพิจารณาดังกล่าว ดังนั้นการเปิดตัวป้องกันอาจทำให้ pool แบบ keyless ที่เหลืออยู่ของ deployment
ว่างเปล่าได้ นี่เป็นผลแลกเปลี่ยนที่คาดไว้จากการเปิดตัวป้องกัน ToS ไม่ใช่ข้อบกพร่อง: ตัวป้องกันมีค่าเริ่มต้นเป็น `false`
ด้วยเหตุผลนี้โดยเฉพาะ (ดู "ตัวป้องกัน ToS" ด้านบน)

## การเปิดใช้งาน

```json
PUT /api/settings
{ "freeAccessPolicy": "strict", "excludeTosAvoid": false }
```

การตั้งค่าใหม่ทั้งสองรายการมีค่าเริ่มต้นเป็นค่าก่อนเพิ่มฟีเจอร์ (`"off"` / `false`) ดังนั้น หากไม่ได้เปิดใช้งาน
การตั้งค่าใดเลย พฤติกรรมการกำหนดเส้นทาง `auto/*` ที่มีอยู่จะไม่เปลี่ยนแปลง
