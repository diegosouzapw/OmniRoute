| สิ่งที่พบ                    | ความหมาย                                 | สิ่งที่ควรทำ                                                                                                    |
| ---------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| "เชื่อมต่อไม่ได้"            | OmniRoute ไม่ได้ทำงานอยู่                | รัน `omniroute` หรือ `docker restart omniroute`                                                                 |
| "คีย์ API ไม่ถูกต้อง"        | คีย์ของคุณไม่ถูกต้องหรือหมดอายุ          | คัดลอกคีย์จากเว็บไซต์ของผู้ให้บริการอีกครั้ง                                                                    |
| "เกินขีดจำกัดอัตราการใช้งาน" | คุณกำลังส่งคำขอมากเกินไป                 | รอ 1 นาที หรือใช้ `model: "auto"` เพื่อสลับไปใช้ตัวเลือกสำรองโดยอัตโนมัติ                                       |
| "เกินโควตา"                  | คุณใช้โควตาฟรี/แบบชำระเงินหมดแล้ว        | เชื่อมต่อผู้ให้บริการเพิ่มเติม หรือใช้ผู้ให้บริการฟรี (Kiro, Pollinations)                                      |
| "ตอบสนองช้า"                 | ผู้ให้บริการกำลังมีภาระงานสูงหรืออยู่ไกล | ใช้ `model: "auto/fast"` หรือเชื่อมต่อผู้ให้บริการที่เร็วกว่า (Groq, Cerebras)                                  |
| "ใช้ผู้ให้บริการผิดราย"      | `auto` เลือกผู้ให้บริการรายอื่น          | นี่เป็นเรื่องปกติ! `auto` จะเลือกตัวเลือกที่ดีที่สุด บังคับใช้ผู้ให้บริการเฉพาะรายด้วย `model: "openai/gpt-4o"` |
| "502 Bad Gateway"            | ผู้ให้บริการขัดข้อง                      | รอแล้วลองอีกครั้ง หรือใช้ `model: "auto"` เพื่อสลับผู้ให้บริการ                                                 |
| "401 Unauthorized"           | ข้อมูลรับรองของคุณไม่ถูกต้อง             | ตรวจสอบคีย์ API หรือยืนยันตัวตนใหม่ด้วย OAuth                                                                   |
| "ไม่รู้จักคำสั่ง omniroute"  | Windows PATH ไม่มีโมดูล node แบบส่วนกลาง | เพิ่มคำนำหน้า npm ส่วนกลางของคุณลงใน Windows PATH ค้นหาได้ด้วย `npm config get prefix`                          |
| "429 Too Many Requests"      | ถูกจำกัดอัตราการใช้งาน                   | รอ 1 นาที หรือเชื่อมต่อผู้ให้บริการเพิ่มเติม                                                                    |

## การแก้ไขปัญหาโดยละเอียด

---

### การจำกัดอัตราการใช้งานของผู้ให้บริการฟรี (429 / 400 / 401)

**อาการ**: เมื่อใช้ `model: "auto"` กับผู้ให้บริการแบบฟรี/ไม่ต้องยืนยันตัวตน (opencode, auggie เป็นต้น) คุณจะได้รับ `HTTP 429`, `400` หรือ `401` แทนคำตอบเป็นครั้งคราว คำขอจะสำเร็จเมื่อลองส่งพรอมต์เดิมอีกครั้งในอีกไม่กี่อึดใจ แต่ระบบอัตโนมัติ (งาน cron, เอเจนต์, สคริปต์) จะหยุดทำงานทันทีที่เกิดความล้มเหลวครั้งแรก

**สาเหตุหลัก**: โหมดความล้มเหลวที่เป็นอิสระต่อกันสามรูปแบบเกิดซ้อนกัน:

1. **ขีดจำกัดอัตราของผู้ให้บริการ (`429`)**: ระดับบริการฟรีอาจบังคับใช้โควตาต่อช่วงเวลา การเรียกแบบขนานจำนวนมากในคราวเดียวจะใช้โควตาจนหมด ทำให้คำขอถัดไปถูกปฏิเสธจนกว่าช่วงเวลาจะถูกรีเซ็ต
2. **โมเดลที่ใช้งานไม่ได้ในโหมดส่งผ่าน (`400`/`401`)**: พูล `auto/*` อาจมีโมเดลแบบส่งผ่านจาก `opencode` ที่ลงทะเบียนอยู่ในแค็ตตาล็อก แต่ไม่มีข้อมูลรับรองที่ใช้งานได้ (เช่น `oc/north-mini-code-free` → `401`) ตัวกำหนดเส้นทางอัตโนมัติจะลองใช้โมเดลหนึ่ง ล้มเหลว และส่งต่อข้อผิดพลาดก่อนที่กลไกสลับไปใช้ตัวเลือกสำรองจะเริ่มทำงาน
3. **การขยายผลจากการทำงานพร้อมกัน (`429` เมื่อมีภาระงานสูง)**: เมื่อเซสชันของเอเจนต์/cron หลายเซสชันเรียกใช้ `auto` พร้อมกัน อัตราคำขอรวมจะสูงเกินกว่าที่ผู้ให้บริการฟรีรองรับได้ ทำให้การเรียกที่ถูกต้องถูกระบุว่าเป็นการใช้งานในทางที่ผิด

**วิธีแก้ไขที่ผ่านการตรวจสอบแล้ว (รายงานโดยชุมชน, 2026-08-10)**: ปรับตัวแปรสภาพแวดล้อมสามตัวเพื่อให้การหมุนเวียน การทำงานพร้อมกัน และการสลับไปใช้ตัวเลือกสำรองรองรับความไม่แน่นอนของระดับบริการฟรี แทนที่จะหยุดทำงานเพราะปัญหาดังกล่าว:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # สลับไปยังโมเดล/ผู้ให้บริการอื่นเมื่อพบ 400/401 (ข้ามโมเดลแบบส่งผ่านที่ใช้งานไม่ได้)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # เพดานการรับงานหนักที่กำหนดไว้อย่างชัดเจน (ค่าเริ่มต้นคือไม่ได้ตั้งค่า: ไม่มีขีดจำกัดจำนวนคำขอ ดูหมายเหตุด้านล่าง)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # เพิ่มเวลารอแบบมีขอบเขตให้เกินค่าเริ่มต้น RATE_LIMIT_MAX_WAIT_MS สำหรับต้นทางที่ช้า
```

ตั้งค่าตัวแปรเหล่านี้ในสภาพแวดล้อมของโพรเซส OmniRoute (ดีมอน เช่น ผ่าน LaunchAgent plist หรือ `systemctl edit`) จากนั้นรีสตาร์ต OmniRoute แฟล็กการหมุนเวียนเป็นตัวช่วยที่ให้ผลลัพธ์สูงสุดเพียงตัวเดียว โดยจะเปลี่ยนความล้มเหลวโดยสมบูรณ์ให้เป็นการลองใหม่แบบโปร่งใสกับผู้ให้บริการที่พร้อมใช้งานในพูล

**หมายเหตุ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` จำกัดจำนวนคำขอที่เป็นงานหนัก — แบบบริบทยาว — ที่ทำงานพร้อมกัน ขอบเขตนี้เป็นด่านควบคุมการรับงาน ไม่ใช่ตัวจำกัดอัตราของผู้ให้บริการ **ข้อมูลอัปเดต #503-fanout:** ตัวแปรนี้จะไม่ถูกตั้งค่าเป็นค่าเริ่มต้นอีกต่อไป (ขณะนี้จะมีผลเฉพาะเมื่อกำหนดค่าไว้อย่างชัดเจนดังด้านบน) — การรับงานหนักจะถูกควบคุมโดยงบประมาณไบต์ที่คำนวณโดยอัตโนมัติ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) แทน ซึ่งจะปรับขนาดตามขีดจำกัดหน่วยความจำจริงของโฮสต์ ดังนั้นการติดตั้งใหม่ควรพบการปฏิเสธ `503 chat_admission_busy` น้อยลงอย่างมากโดยไม่ต้องตั้งค่าตัวแปรนี้เลย อย่างไรก็ตาม การตั้งค่าไว้อย่างชัดเจนที่นี่จะยังคงทำงานตรงตามเอกสารทุกประการ การแทนที่งบประมาณไบต์อย่างชัดเจนจะถูกจำกัดให้อยู่ระหว่าง 8 MiB–2 GiB ข้อผิดพลาด `413 body_exceeds_budget` ไม่ใช่ปัญหาชั่วคราว: ให้เพิ่มงบประมาณไบต์ดังกล่าว ลด `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` หรือเพิ่มขีดจำกัดหน่วยความจำของโพรเซส การสละงานแบบ `inflight_bytes_budget` เป็นความขัดแย้งในการใช้ทรัพยากรชั่วคราวและยังคงลองใหม่ได้ การจำกัดอัตรารายผู้ให้บริการ (`open-sse/services/rateLimitManager.ts`) ถูกควบคุมแยกต่างหากโดย `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` และ `RATE_LIMIT_AUTO_ENABLE` — ดู `.env.example`

**วิธีตรวจสอบว่าการแก้ไขได้ผล**: เรียกใช้เอเจนต์/cron ของคุณสองครั้งติดกันอย่างรวดเร็ว และยืนยันว่าทั้งสองครั้งสำเร็จ ก่อนแก้ไข การเรียกใช้ครั้งที่สองมักแสดงข้อผิดพลาด `429`/`401` หลังแก้ไข ความล้มเหลวต่าง ๆ (หากมี) จะถูกลองใหม่โดยอัตโนมัติโดยที่ผู้ใช้ไม่สังเกตเห็น และการเรียกจะดำเนินการจนเสร็จสมบูรณ์ นอกจากนี้ คุณยังสามารถใช้ `curl /monitoring/health` แล้วดูฟิลด์ `rateLimitedUntil` ในการเชื่อมต่อของผู้ให้บริการ รวมถึง `circuitBreakers.providerBreakers[].state` สำหรับผู้ให้บริการที่ได้รับผลกระทบ — สถานะจะเป็นค่าใดค่าหนึ่งจาก `CLOSED`, `DEGRADED`, `OPEN` หรือ `HALF_OPEN` (ดู `src/shared/utils/circuitBreaker.ts`) และผู้ให้บริการที่ยังคงล้มเหลวจะเปลี่ยนสถานะจาก `CLOSED → DEGRADED → OPEN` ก่อนที่ช่วงเวลารีเซ็ตจะอนุญาตให้ส่งคำขอทดสอบผ่านได้ (`HALF_OPEN`)

**หากคุณยังคงพบ 429**: บัญชีที่ใช้งานอยู่สำหรับผู้ให้บริการรายนั้นใช้ _โควตา_ หมดแล้วจริง ๆ (ไม่ใช่เพียงติดข้อจำกัดด้านอัตราการเรียกใช้) ให้เพิ่มบัญชีที่สองสำหรับผู้ให้บริการรายเดียวกันในแดชบอร์ด OmniRoute → Providers → Accounts หรือเพิ่มผู้ให้บริการฟรีรายอื่นเข้ามาใช้ร่วมกัน (เช่น `routeway`, `auggie`) การหมุนเวียนบัญชีช่วยได้เฉพาะข้อจำกัดด้านอัตราการเรียกใช้ชั่วคราว/400/401 เท่านั้น หากโควตาหมดโดยสมบูรณ์ จำเป็นต้องใช้ข้อมูลรับรองชุดที่สองหรือผู้ให้บริการรายอื่น

**หากคุณพบ 403 ในโมเดลด้านการมองเห็น (`auto/vision`, `bazaarlink/*`)**: บัญชีที่เชื่อมต่อไม่มีแผนแบบชำระเงินที่รองรับการมองเห็น หรือคีย์ API มีสิทธิ์ไม่เพียงพอ ตรวจสอบในแดชบอร์ดของผู้ให้บริการว่าขอบเขตสิทธิ์ของคีย์ครอบคลุมการมองเห็น/มัลติโมดัล หรือเชื่อมต่อบัญชีระดับชำระเงินและกำหนดให้เป็นเป้าหมายสำหรับงานด้านการมองเห็น

## คำเตือนจาก npm install (ERESOLVE / peer / deprecated)

เมื่อคุณเรียกใช้ `npm install -g omniroute` คุณอาจเห็นคำเตือนจำนวนมาก เช่น `npm warn ERESOLVE` การแจ้งเตือนเกี่ยวกับ peer dependency และข้อความ `deprecated` **คำเตือนเหล่านี้เป็นสิ่งที่คาดว่าจะเกิดขึ้นและไม่เป็นอันตราย** การติดตั้งของคุณสำเร็จแล้วหากเห็น `added <N> packages` ในเอาต์พุต

หากต้องการระงับคำเตือนเกี่ยวกับการแก้ไข peer dependency ให้ใช้รูปแบบการติดตั้งที่ OmniRoute รองรับ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` จะระงับเฉพาะ `ERESOLVE` และการแจ้งเตือนเกี่ยวกับ peer dependency เท่านั้น การแจ้งเตือนการเลิกใช้งานจะยังคงปรากฏอยู่ เนื่องจากมาจากแพ็กเกจของบุคคลที่สามซึ่งเป็น dependency ทางอ้อม และไม่ได้หมายความว่าการติดตั้งล้มเหลว

คำเตือนเหล่านี้เกิดจากช่วงเวอร์ชัน peer dependency ที่ล้าสมัยในแพ็กเกจของบุคคลที่สามซึ่ง OmniRoute ไม่ได้ควบคุม:

1. **`marked-terminal` ต้องการ `marked >=1 <16` แต่พบ `marked@18`** — ในทางปฏิบัติยังทำงานได้ตามปกติ เพียงแต่ช่วงเวอร์ชัน peer dependency ของต้นทางล้าสมัย
2. **`deprecated prebuild-install@7.1.3`** — เครื่องมือช่วยดาวน์โหลดไบนารีเนทีฟที่เป็น dependency ทางอ้อม เครื่องมือนี้ไม่ได้
   ถูกใช้เพื่อติดตั้ง transport binding ของ `wreq-js` ที่ตรึงเวอร์ชันไว้ และไม่ได้หมายความว่าการตั้งค่า transport
   ของผู้ให้บริการ web-cookie ล้มเหลว

**ไม่จำเป็นต้องดำเนินการใดๆ** — ไม่สามารถปิดคำเตือนเหล่านี้ได้ทั้งหมดโดยไม่ fork แพ็กเกจต้นทาง

## คำเตือน npm install-scripts ถูกบล็อก (การติดตั้งแบบ global)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

เมื่อเรียกใช้ `npm install -g omniroute` npm เวอร์ชันใหม่กว่า (v11+ และ v12+) จะบล็อกสคริปต์วงจรชีวิตของแพ็กเกจตามค่าเริ่มต้น และแสดงคำเตือนเกี่ยวกับ install-scripts:

```
npm warn install-scripts แพ็กเกจ 7 รายการมีสคริปต์ติดตั้งที่ถูกบล็อก เนื่องจากไม่ครอบคลุมอยู่ใน allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### สามารถละเว้นคำเตือนนี้ได้หรือไม่?

**ได้บางส่วน แต่ไม่แนะนำให้ทำงานโดยไม่มีสคริปต์** OmniRoute มีระบบสำรองที่ทำงานได้อย่างเหมาะสม: หากไม่สามารถโหลด binding เนทีฟของ `better-sqlite3` จากบันเดิลแบบ standalone ได้ แอปพลิเคชันจะเปลี่ยนไปใช้ไดรเวอร์ทางเลือก เช่น `node:sqlite` หรือ `sql.js` (ดู [การเลือก SQLite Runtime](../ops/SQLITE_RUNTIME.md)) เซิร์ฟเวอร์จะยังคงเริ่มทำงานได้ แต่การทำงานบนระบบสำรองแบบ WASM เช่น `sql.js` จะปิดใช้งานโหมด SQLite WAL (Write-Ahead Logging) และเพิ่มภาระด้านหน่วยความจำและการซิงค์ดิสก์

### สคริปต์ใดที่จำเป็นจริงๆ?

สคริปต์ที่ถูกบล็อกไม่ได้จำเป็นต่อการเรียกใช้ OmniRoute ทั้งหมด:

- **จำเป็น (`omniroute`, `better-sqlite3`):** OmniRoute ทำงานจากบันเดิลแอปพลิเคชัน Next.js แบบ standalone (`dist/`) ระหว่างการติดตั้ง npm จะดาวน์โหลดหรือคอมไพล์ไดรเวอร์ SQLite เนทีฟเฉพาะสำหรับโฮสต์ไว้ใน `node_modules/better-sqlite3/` ระดับบนสุด จากนั้นสคริปต์ `postinstall` ของ OmniRoute (`scripts/build/postinstall.mjs`) จะตรวจสอบและคัดลอกไบนารีเฉพาะสำหรับโฮสต์เหล่านี้ไปยัง `dist/node_modules/` เพื่อให้เซิร์ฟเวอร์แบบ standalone สามารถเข้าถึงได้ หากสคริปต์ postinstall ของ `omniroute` ถูกบล็อก ขั้นตอนการคัดลอกนี้จะถูกข้าม
- **ไม่บังคับ/ทางอ้อม (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** รายการเหล่านี้เป็นเครื่องมือช่วยในการบิลด์ เครื่องมือตรวจจับการเปลี่ยนแปลง หรือยูทิลิตีสำหรับพวงกุญแจของระบบ การอนุญาตให้ทำงานจะช่วยป้องกันคำเตือนระหว่างการบิลด์ แต่ไม่จำเป็นต่อฟังก์ชันการกำหนดเส้นทางหลัก
- **ไม่รวม (`onnxruntime-node`):** เป็น dependency ที่ไม่บังคับสำหรับ embedding ของ AI ภายในเครื่อง และ **ไม่** จำเป็นสำหรับการทำงานของ OmniRoute สคริปต์ postinstall ของแพ็กเกจนี้จะดาวน์โหลดแอสเซ็ต CUDA ขนาดประมาณ 300MB จาก NuGet อย่าเพิ่มแพ็กเกจนี้ในรายการอนุญาต เว้นแต่คุณตั้งใจจะใช้การเร่งความเร็ว ONNX ภายในเครื่องบนฮาร์ดแวร์ที่รองรับอย่างชัดเจน

### วิธีแก้ไขที่แนะนำ

หากต้องการอนุญาตสคริปต์ติดตั้งที่จำเป็นระหว่างการติดตั้งแบบ global และปิดคำเตือน ให้ส่ง `--allow-scripts` สำหรับ OmniRoute และ dependency เนทีฟของ OmniRoute:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

หรือกำหนดค่านี้อย่างถาวรสำหรับการติดตั้งแบบ global ทั้งหมดในบัญชีผู้ใช้ของคุณ:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### ตรวจสอบการติดตั้งของคุณ

หลังการติดตั้ง ให้เรียกใช้เครื่องมือวินิจฉัยในตัวเพื่อให้แน่ใจว่า binding เนทีฟและสภาพแวดล้อม runtime อยู่ในสถานะปกติ:

```bash
omniroute doctor
```

## Gemini Web และ Playwright Chromium

หากคำขอ Gemini Web ส่งคืน `503` พร้อมข้อความว่าไม่ได้ติดตั้ง Playwright Chromium แสดงว่ามีแพ็กเกจ npm อยู่แล้ว แต่ไม่มีไบนารีของเบราว์เซอร์ Playwright แยกการดาวน์โหลดเบราว์เซอร์ออกจากการติดตั้งแพ็กเกจ npm โดยเจตนา ดังนั้นการตอบกลับนี้จึงเป็นสิ่งที่คาดไว้จนกว่าจะติดตั้งเบราว์เซอร์

สำหรับการติดตั้ง npm แบบส่วนกลาง ให้ติดตั้ง Chromium จากไดเรกทอรีของแพ็กเกจ OmniRoute เพื่อให้แคชของเบราว์เซอร์อยู่ในการติดตั้ง Playwright เดียวกัน:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

รีสตาร์ต OmniRoute หลังการติดตั้ง แล้วลองส่งคำขอ Gemini Web อีกครั้ง หากคุณเรียกใช้ OmniRoute จากอิมเมจ Docker ให้ใช้อิมเมจ `-web` (หรือเป้าหมายการบิลด์ `runner-web`) ซึ่งรวม Chromium และการขึ้นต่อกันต่างๆ ไว้แล้ว ส่วนอิมเมจพื้นฐานไม่มีองค์ประกอบเหล่านี้

| Docker แสดง `curl: (56) Recv failure: Connection reset by peer` | การผูกพอร์ต Docker ของคุณอาจไปอยู่บน IPv6 ใช้ `-p 127.0.0.1:20128:20128` เพื่อบังคับใช้ IPv4 หรือทดสอบด้วย `curl -4` ดู [Docker IPv6](#docker-ipv6) ด้านล่าง         |

| Kaspersky ระบุว่าแอปเดสก์ท็อปเป็นโทรจัน                         | เป็นผลบวกลวงจากพฤติกรรมของโปรแกรมติดตั้งที่ไม่มีลายเซ็น — ดู [ผลบวกลวงจากโปรแกรมป้องกันไวรัส](#antivirus-false-positives) ด้านล่าง                                   |

## ผลบวกลวงจากโปรแกรมป้องกันไวรัส

<a name="antivirus-false-positives"></a>

### Avast/AVG กักกัน `README.md` ด้วยผลตรวจจับ `MD:HttpRequest-inf[Susp]`

**นี่เป็นผลบวกลวง ไม่มีไฟล์ใดติดไวรัสและไม่จำเป็นต้องดำเนินการใดๆ**

Avast และ AVG ใช้ฮิวริสติกที่แจ้งเตือนไฟล์ข้อความธรรมดา/Markdown ซึ่งมีลิงก์ที่ดูคล้ายคำขอ HTTP จำนวนมาก `README.md` ของ OmniRoute รวมอยู่ในแพ็กเกจ npm (ไฟล์นี้มีชื่ออยู่ใน `package.json` → `files`) ดังนั้นเมื่อติดตั้งแบบโกลบอล ไฟล์ดังกล่าวจะถูกบันทึกไว้ที่ `node_modules/omniroute/README.md` และภายในมีตัวอย่าง `http://localhost:20128/...` ประมาณ 15 รายการ (เอ็นด์พอยต์ HTTP/SSE ของ MCP, URL `.well-known` ของ A2A และตัวอย่างคำสั่ง `curl`) ความหนาแน่นของลิงก์ในระดับนี้เพียงพอที่จะกระตุ้นฮิวริสติกดังกล่าว

หากปัญหานี้เพิ่งเริ่มเกิดขึ้นเมื่อไม่นานมานี้: ลักษณะของไฟล์ไม่ได้เปลี่ยนไป แต่ README มีตารางเอ็นด์พอยต์ที่ใหญ่ขึ้น (มีการเพิ่ม MCP HTTP + SSE + A2A) และมีตัวอย่าง `curl` มากขึ้น จึงทำให้เกินเกณฑ์การตรวจจับ

ไฟล์นี้เป็นเพียงเอกสารที่ไม่มีการทำงานใดๆ และไม่มีเนื้อหาที่เรียกใช้งานได้เลย คุณสามารถกู้คืนไฟล์จากพื้นที่กักกันได้อย่างปลอดภัย

**สิ่งที่ควรทำ:**

1. **หยุดการแจ้งเตือน** — เพิ่มไดเรกทอรีติดตั้งลงในรายการยกเว้นของโปรแกรมป้องกันไวรัส
   (Avast: Settings → Exceptions) โดยเพิ่มพาธ `node_modules` แบบโกลบอล และ/หรือไดเรกทอรีข้อมูลของ
   OmniRoute (`~/.omniroute/`)
2. **รายงานผลบวกลวง** — <https://www.avast.com/false-positive-file-form.php>
   พร้อมแนบ `README.md` ที่ถูกกักกัน วิธีนี้เป็นการแก้ไขที่ช่วยผู้ใช้ทุกคน เนื่องจากสาเหตุคือฮิวริสติกของผู้ผลิตตอบสนองต่อไฟล์ข้อความมากเกินไป

**เหตุผลที่เราไม่ "แก้ไข" ปัญหานี้จากฝั่งเรา:** ตัวอย่างทั้งหมดใช้ `http://localhost` และ
localhost ไม่สามารถใช้ `https` ได้โดยไม่เกิดความยุ่งยากจากใบรับรองที่ลงนามด้วยตนเอง การบิดเบือนเอกสารเพื่อหลบเลี่ยงฮิวริสติกของผู้ผลิตเพียงรายเดียวจะทำให้ผู้อ่านทุกคนได้รับผลกระทบ เพียงเพื่อเอาใจบั๊กของสแกนเนอร์

### Kaspersky แจ้งเตือนแอปเดสก์ท็อปว่าเป็น `PDM:Trojan.Win32.Generic`

**นี่เป็นผลบวกลวงจากฮิวริสติกเชิงพฤติกรรม ไม่มีไฟล์ใดติดไวรัส** คำนำหน้า `PDM:` ของ Kaspersky หมายความว่าคำตัดสินมาจาก Proactive Defense Module (System Watcher) ซึ่งพิจารณาจากสิ่งที่โปรแกรมติดตั้ง _ทำ_ แทนที่จะเปรียบเทียบกับมัลแวร์ที่รู้จัก เมื่อระบบตรวจจับทำงาน Kaspersky จะ "ย้อนกลับ" การติดตั้งทั้งหมด โดยลบไฟล์ที่เขียนไปแล้ว ส่งผลให้แอปเสียหายหรือหายไป

ไฟล์ที่ถูกแจ้งเตือนเป็นส่วนประกอบมาตรฐานของดีเพนเดนซีโอเพนซอร์สที่มีการประกาศไว้อย่างชัดเจนและรวมมากับแอปเดสก์ท็อป ตัวอย่างเช่น:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` และ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev) ไลบรารีระบบอัตโนมัติสำหรับเบราว์เซอร์ที่ใช้ในการเข้าสู่ระบบผู้ให้บริการภายในแอปและการแชตที่ทำงานผ่านเบราว์เซอร์
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — native binding ของ `wreq-js` เวอร์ชันที่ตรึงไว้ ซึ่งใช้สำหรับ HTTP ที่จำลองลายนิ้วมือเบราว์เซอร์กับผู้ให้บริการที่ใช้เว็บคุกกี้ (`<arch>` คือ `x64` หรือ `arm64`)

**เหตุผลที่ระบบตรวจจับทำงาน:** โปรแกรมติดตั้งสำหรับ Windows **ยังไม่ได้ลงนามโค้ด** ดังนั้นโปรแกรมติดตั้ง NSIS ที่ไม่มีลายเซ็นจึงไม่มีค่าความน่าเชื่อถือ และฮิวริสติกเชิงพฤติกรรมจะทำงานอย่างเข้มงวดสูงสุด เมื่อรวมกับ DLL แบบเนทีฟที่มาพร้อมกันและไฟล์ `.js` หลายร้อยไฟล์ที่ถูกเขียนไว้ภายใต้
`%LOCALAPPDATA%\Programs\OmniRoute` (รวมถึงไดเรกทอรีแพ็กเกจที่มีแฮชต่อท้ายจากบิลด์แบบ standalone ของ Next.js) ก็เพียงพอที่จะกระตุ้นฮิวริสติกดังกล่าว เรามีแผนจะลงนามโค้ด แต่จนกว่าจะดำเนินการเสร็จ รุ่นใหม่ๆ อาจพบปัญหานี้ซ้ำได้

**สิ่งที่ควรทำ:**

1. **ตรวจสอบไฟล์ที่ดาวน์โหลดก่อน** (เพื่อตัดความเป็นไปได้ว่าไฟล์ถูกดัดแปลง) ทุกรุ่นเผยแพร่
   `latest.yml` ซึ่งฟิลด์ `sha512` (base64) ครอบคลุมไฟล์ติดตั้ง `OmniRoute.Setup.<version>.exe`
   ใน PowerShell ให้เรียกใช้คำสั่งต่อไปนี้จากโฟลเดอร์ที่มีไฟล์ติดตั้ง:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ผลลัพธ์ต้องตรงกับ `latest.yml` → `sha512` หากไม่ตรงกัน ให้ลบไฟล์และดาวน์โหลดใหม่เฉพาะจาก[หน้าเผยแพร่ของ GitHub](https://github.com/diegosouzapw/OmniRoute/releases)
2. **กู้คืน + เพิ่มข้อยกเว้น** — กู้คืนรายการที่ถูกย้อนกลับจากพื้นที่กักกัน และเพิ่มข้อยกเว้นสำหรับ
   `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions)
   จากนั้นติดตั้งใหม่
3. **รายงานผลบวกลวง** — <https://opentip.kaspersky.com/> รายงานผลบวกลวงที่ผู้ใช้ส่งเข้ามาช่วยเร่งกระบวนการเพิ่มลงในรายการที่อนุญาตได้จริง

## ความเข้ากันได้กับ Node.js

<a name="nodejs-compatibility"></a>

### หน้าเข้าสู่ระบบขัดข้องหรือแสดงข้อผิดพลาด "Module self-registration"

**สาเหตุ:** คุณกำลังใช้ Node.js เวอร์ชันที่อยู่นอกเกณฑ์ขั้นต่ำของรันไทม์ที่ปลอดภัยซึ่ง OmniRoute รับรอง กรณีที่พบบ่อยที่สุดคือการใช้ Node 22 หรือ 24 ระดับแพตช์เก่ากว่าเกณฑ์ขั้นต่ำด้านความปลอดภัยที่ OmniRoute กำหนด

**อาการ:**

- หน้าเข้าสู่ระบบแสดงหน้าจอว่างหรือข้อผิดพลาดของเซิร์ฟเวอร์
- คอนโซลแสดง `Error: Module did not self-register` หรือข้อผิดพลาดเกี่ยวกับเนทีฟไบนดิงที่คล้ายกัน
- หน้าเข้าสู่ระบบแสดง **แบนเนอร์คำเตือนสีส้ม** พร้อมเวอร์ชัน Node ของคุณ หากรันไทม์อยู่นอกนโยบายความปลอดภัยที่รองรับ

**วิธีแก้ไข:**

1. ติดตั้ง Node.js รุ่น LTS ที่รองรับ (แนะนำ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ตรวจสอบเวอร์ชันของคุณ: `node --version` ควรแสดง `v24.0.0` หรือใหม่กว่าในสาย LTS 24.x
3. ติดตั้ง OmniRoute ใหม่: `npm install -g omniroute`
4. เริ่มระบบใหม่: `omniroute`

> **เวอร์ชันที่ปลอดภัยและรองรับ:** `>=22.22.2 <23` หรือ `>=24.0.0 <27` รองรับ Node.js 24.x LTS (Krypton) และ Node.js 26 อย่างเต็มรูปแบบ

### npm v11+: ไม่ได้ติดตั้ง `better-sqlite3` (ไม่พบโมดูล)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**สาเหตุ:** npm v11 (มาพร้อมกับ Node.js 24+) บล็อกสคริปต์การติดตั้งสำหรับ
ดีเพนเดนซีที่ไม่บังคับโดยค่าเริ่มต้น เนื่องจาก `better-sqlite3` อยู่ใน `optionalDependencies`
และจำเป็นต้องคอมไพล์แบบเนทีฟ (`node-gyp rebuild`) npm จึงข้ามการติดตั้งโดยไม่แจ้งเตือน

**อาการ:**

- เซิร์ฟเวอร์ขัดข้องขณะเริ่มต้นพร้อมข้อความ `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` แสดงข้อความ "No such file or directory"
- `npm ls better-sqlite3` แสดง `(empty)`

**วิธีแก้ไข:**

1. อนุมัติสคริปต์การติดตั้งแล้วติดตั้งใหม่:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. หรือติดตั้งไบนารีที่คอมไพล์ไว้ล่วงหน้าด้วยตนเอง:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ตรวจสอบว่าสามารถใช้งานได้: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**สาเหตุ:** หลังจากเรียกใช้ `npm install -g omniroute` แบบโกลบอล ไบนารีเนทีฟของ `better-sqlite3` ภายในแพ็กเกจอาจถูกคอมไพล์มาสำหรับสถาปัตยกรรมหรือ ABI ของ Node.js ที่แตกต่างจากสภาพแวดล้อมที่กำลังทำงานอยู่ในเครื่อง ปัญหานี้พบได้บ่อยบน macOS (ทั้ง Apple Silicon และ Intel) เมื่อไบนารีที่สร้างไว้ล่วงหน้าไม่ตรงกับสภาพแวดล้อมของคุณ

**อาการ:**

- เซิร์ฟเวอร์ล้มเหลวทันทีขณะเริ่มต้นพร้อมข้อผิดพลาด `dlopen`
- ข้อผิดพลาดมีข้อความ `slice is not valid mach-o file`
- ตัวอย่างแบบเต็ม:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**วิธีแก้ไข — สร้างใหม่สำหรับสภาพแวดล้อมในเครื่องของคุณ (ไม่จำเป็นต้องดาวน์เกรด Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **หมายเหตุ:** ขั้นตอนนี้จะคอมไพล์เนทีฟไบนดิงใหม่ให้ตรงกับเวอร์ชัน Node.js และสถาปัตยกรรม CPU ในเครื่องของคุณ ซึ่งช่วยแก้ไขปัญหาไบนารีไม่ตรงกัน ช่วงรันไทม์ที่รองรับอย่างเป็นทางการคือ **`>=22.22.2 <23` หรือ `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` ใน `src/shared/utils/nodeRuntimeSupport.ts` ซึ่งสอดคล้องกับฟิลด์ `engines` ใน `package.json`) รองรับ Node.js 24.x LTS (Krypton) และ Node.js 26 อย่างเต็มรูปแบบเมื่อใช้ร่วมกับ `better-sqlite3` v12.x

## ปัญหาเกี่ยวกับพร็อกซี

<a name="proxy-issues"></a>

### การตรวจสอบผู้ให้บริการแสดงข้อผิดพลาด "fetch failed"

**สาเหตุ:** ก่อนหน้านี้ Endpoint สำหรับตรวจสอบ API key (`POST /api/providers/validate`) ไม่ได้ใช้การกำหนดค่าพร็อกซี ส่งผลให้เกิดข้อผิดพลาดในสภาพแวดล้อมที่จำเป็นต้องกำหนดเส้นทางผ่านพร็อกซี

**วิธีแก้ไข (v3.5.5+):** ปัญหานี้ได้รับการแก้ไขแล้ว ขณะนี้การตรวจสอบผู้ให้บริการจะกำหนดเส้นทางผ่าน `runWithProxyContext` โดยใช้การตั้งค่าพร็อกซีระดับผู้ให้บริการและระดับส่วนกลางโดยอัตโนมัติ

### การตรวจสอบสถานะโทเค็นล้มเหลวด้วยข้อผิดพลาด "fetch failed"

**สาเหตุ:** การรีเฟรชโทเค็น OAuth ในเบื้องหลังไม่ได้ตรวจหาการกำหนดค่าพร็อกซีแยกตามแต่ละการเชื่อมต่อ

**วิธีแก้ไข (v3.5.5+):** ขณะนี้ตัวกำหนดเวลาตรวจสอบสถานะโทเค็นจะตรวจหาการกำหนดค่าพร็อกซีแยกตามแต่ละการเชื่อมต่อก่อนพยายามรีเฟรช โปรดอัปเดตเป็น v3.5.5+

### พร็อกซี SOCKS5 แสดงข้อผิดพลาด "invalid onRequestStart method"

**สาเหตุ:** บน Node.js 22 ตัวกระจายคำขอของ undici@8 ไม่เข้ากันกับการใช้งาน `fetch()` ที่มาพร้อมกับ Node

**วิธีแก้ไข (v3.5.5+):** ขณะนี้ OmniRoute ใช้ฟังก์ชัน `fetch()` ของ undici เองเมื่อมีการเปิดใช้งานตัวกระจายคำขอของพร็อกซี เพื่อให้มั่นใจว่าการทำงานมีความสอดคล้องกัน โปรดอัปเดตเป็น v3.5.5+

### พร็อกซี MITM ภายใต้ WSL: แอปเดสก์ท็อปบนโฮสต์ Windows ไม่ถูกดักรับ

**สาเหตุ:** พร็อกซี MITM และใบรับรอง CA ของพร็อกซีจะถูกติดตั้งในสภาพแวดล้อมที่ OmniRoute ทำงานอยู่ ภายใต้ WSL สภาพแวดล้อมดังกล่าวคือระบบ Linux แบบ Guest ขณะที่แอป AI บนเดสก์ท็อป (Kiro, Trae, Copilot, Zed, …) ทำงานอยู่บนโฮสต์ Windows แอปบนโฮสต์ไม่เชื่อถือที่เก็บใบรับรองของ Guest และไม่ได้กำหนดเส้นทางผ่านพร็อกซีระบบของ Guest ดังนั้นการดักรับทราฟฟิกของแอปเดสก์ท็อปจึงไม่ทำงานในกรณีนี้

**คำแนะนำ:** เรียกใช้ OmniRoute แบบเนทีฟบน OS เดียวกับแอปเดสก์ท็อปที่คุณต้องการดักรับ (Windows สำหรับแอป Windows และเช่นเดียวกันสำหรับ macOS/Linux) หากต้องการให้ OmniRoute ทำงานภายใน WSL ขณะที่กำหนดเป้าหมายไปยังแอปบนโฮสต์ คุณต้องกำหนดให้โฮสต์ Windows เชื่อถือใบรับรอง CA ที่สร้างขึ้นด้วยตนเอง และตั้งค่าเครือข่าย/พร็อกซีของแต่ละแอปบนโฮสต์ให้ชี้ไปยัง Endpoint พร็อกซีของ WSL ซึ่งเป็นการตั้งค่าที่ไม่รองรับและมีความเปราะบาง

## ปัญหาเกี่ยวกับคลาวด์

### ข้อผิดพลาดในการซิงค์กับคลาวด์

1. ตรวจสอบว่า `BASE_URL` ชี้ไปยังอินสแตนซ์ที่กำลังทำงานอยู่ของคุณ (เช่น `http://localhost:20128`)
2. ตรวจสอบว่า `CLOUD_URL` ชี้ไปยังปลายทางคลาวด์ของคุณ (เช่น `https://omniroute.dev`)
3. กำหนดค่า `NEXT_PUBLIC_*` ให้สอดคล้องกับค่าฝั่งเซิร์ฟเวอร์

### `stream=false` บนคลาวด์ส่งคืน 500

**อาการ:** เกิดข้อผิดพลาด `Unexpected token 'd'...` ที่ปลายทางคลาวด์สำหรับการเรียกแบบไม่สตรีม

**สาเหตุ:** ต้นทางส่งคืนเพย์โหลด SSE ขณะที่ไคลเอนต์คาดว่าจะได้รับ JSON

**วิธีแก้ชั่วคราว:** ใช้ `stream=true` สำหรับการเรียกคลาวด์โดยตรง รันไทม์ภายในเครื่องมีระบบสำรองสำหรับแปลง SSE→JSON

### คลาวด์แจ้งว่าเชื่อมต่อแล้วแต่แสดง "Invalid API key"

1. สร้างคีย์ใหม่จากแดชบอร์ดภายในเครื่อง (`/api/keys`)
2. เรียกใช้การซิงค์กับคลาวด์: Enable Cloud → Sync Now
3. คีย์เก่าหรือคีย์ที่ยังไม่ได้ซิงค์อาจยังคงส่งคืน `401` บนคลาวด์

## ปัญหาเกี่ยวกับ Docker

### Docker IPv6 / การเชื่อมต่อถูกรีเซ็ต

<a name="docker-ipv6"></a>

**อาการ:** `curl http://localhost:20128/v1/models` ส่งคืน `curl: (56) Recv failure: Connection reset by peer` แดชบอร์ดและปลายทางที่ไม่ต้องยืนยันตัวตนทำงานได้ แต่ปลายทางที่ต้องยืนยันตัวตนล้มเหลว — ดูเหมือนเป็นปัญหาการยืนยันตัวตน แต่จริง ๆ แล้วไม่ใช่

**สาเหตุ:** `docker run -p 20128:20128` เปิดพอร์ตทั้งบน `0.0.0.0` (IPv4) และ `::` (IPv6) แต่โปรเซสภายในคอนเทนเนอร์รับฟังเฉพาะบน IPv4 บนโฮสต์ที่ `localhost` ถูกแปลงเป็น `::1` ก่อน การเชื่อมต่อจะไปยังพอร์ต IPv6 ที่เปิดไว้โดยไม่มีตัวรับฟังอยู่เบื้องหลัง → การเชื่อมต่อจึงถูกรีเซ็ต

**วิธีแก้ไข:**

1. **การวินิจฉัยอย่างรวดเร็ว:** เรียกใช้ `curl -4 http://localhost:20128/v1/models` หากใช้งานได้เมื่อระบุ `-4` แต่ล้มเหลวเมื่อไม่ระบุ แสดงว่ามีการผูกที่อยู่ IPv6 ไม่ตรงกัน
2. **วิธีแก้ไขถาวร:** ผูกกับ IPv4 อย่างชัดเจนโดยใช้ `-p 127.0.0.1:20128:20128` ในคำสั่ง `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   วิธีนี้บังคับให้ผูกกับ IPv4 และยังช่วยป้องกันไม่ให้พร็อกซีถูกเปิดเผยบนอินเทอร์เฟซทั้งหมดของโฮสต์

## การดีบัก

### เปิดใช้งานไฟล์บันทึก

ตั้งค่า `APP_LOG_TO_FILE=true` ในไฟล์ `.env` ของคุณ บันทึกของแอปพลิเคชันจะถูกเขียนไว้ภายใต้ `logs/`
อาร์ติแฟกต์ของคำขอจะถูกจัดเก็บไว้ภายใต้ `${DATA_DIR}/call_logs/` เมื่อเปิดใช้งานไปป์ไลน์บันทึกการเรียก
ในการตั้งค่า
เมื่อเปิดใช้งานการบันทึกข้อมูลของไปป์ไลน์ ให้ตั้งค่า `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` เพื่อไม่รวม
เพย์โหลดของชังก์สตรีม หรือปรับ `CALL_LOG_PIPELINE_MAX_SIZE_KB` เพื่อเปลี่ยนขีดจำกัดขนาดอาร์ติแฟกต์ในหน่วย KB

### ตรวจสอบสถานะของผู้ให้บริการ

```bash
# แดชบอร์ดสถานะ
http://localhost:20128/dashboard/health

# การตรวจสอบสถานะ API
curl http://localhost:20128/api/monitoring/health
```

### พื้นที่จัดเก็บของรันไทม์

- สถานะหลัก: `${DATA_DIR}/storage.sqlite` (ผู้ให้บริการ, คอมโบ, นามแฝง, คีย์, การตั้งค่า)
- การใช้งาน: ตาราง SQLite ใน `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` ซึ่งเป็นตัวเลือกเพิ่มเติม
- บันทึกของแอปพลิเคชัน: `<repo>/logs/...` (เมื่อ `APP_LOG_TO_FILE=true`)
- อาร์ติแฟกต์บันทึกการเรียก: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` เมื่อเปิดใช้งานไปป์ไลน์บันทึกการเรียก

การดำเนินการ **Clean history** ในหน้า Request Logs จะล้าง `call_logs`,
`request_detail_logs` แบบเดิม และไดเรกทอรีอาร์ติแฟกต์ `${DATA_DIR}/call_logs/` ภายในเครื่อง

## ปัญหาเกี่ยวกับ Circuit Breaker

### ผู้ให้บริการค้างอยู่ในสถานะ OPEN

เมื่อ circuit breaker ของผู้ให้บริการอยู่ในสถานะ OPEN คำขอจะถูกบล็อกจนกว่าระยะเวลาพักจะสิ้นสุดลง

**วิธีแก้ไข:**

1. ไปที่ **Dashboard → Settings → Resilience**
2. ตรวจสอบการ์ด circuit breaker ของผู้ให้บริการที่ได้รับผลกระทบ
3. คลิก **Reset All** เพื่อล้าง breaker ทั้งหมด หรือรอให้ระยะเวลาพักสิ้นสุดลง
4. ตรวจสอบให้แน่ใจว่าผู้ให้บริการพร้อมใช้งานจริงก่อนรีเซ็ต

### ผู้ให้บริการทริกเกอร์ circuit breaker อย่างต่อเนื่อง

หากผู้ให้บริการเข้าสู่สถานะ OPEN ซ้ำๆ:

1. ตรวจสอบรูปแบบความล้มเหลวที่ **Dashboard → Health → Provider Health**
2. ไปที่ **Settings → Resilience → Provider Profiles** แล้วเพิ่มเกณฑ์ความล้มเหลว
3. ตรวจสอบว่าผู้ให้บริการได้เปลี่ยนขีดจำกัด API หรือต้องมีการยืนยันตัวตนใหม่หรือไม่
4. ตรวจสอบข้อมูล telemetry ด้านเวลาแฝง — เวลาแฝงสูงอาจทำให้เกิดความล้มเหลวจากการหมดเวลา

### ปัญหารูปแบบที่พบบ่อย

- **แท็ก Thinking ไม่ปรากฏ** — ตรวจสอบว่าผู้ให้บริการเป้าหมายรองรับการคิดและการตั้งค่างบประมาณการคิดหรือไม่
- **การเรียกใช้เครื่องมือหายไป** — การแปลรูปแบบบางรายการอาจตัดฟิลด์ที่ไม่รองรับออก ให้ตรวจสอบในโหมด Playground
- **พรอมต์ระบบหายไป** — Claude และ Gemini จัดการพรอมต์ระบบต่างกัน ให้ตรวจสอบเอาต์พุตการแปล
- **SDK ส่งคืนสตริงดิบแทนออบเจ็กต์** — แก้ไขแล้วใน v1.x โดยตัวกรองการตอบกลับจะตัดฟิลด์ที่ไม่ได้เป็นมาตรฐาน (`x_groq`, `usage_breakdown` ฯลฯ) ซึ่งทำให้การตรวจสอบความถูกต้องด้วย Pydantic ของ OpenAI SDK ล้มเหลว หากยังพบปัญหานี้ใน v3.x+ โปรดแจ้งปัญหา
- **GLM/ERNIE ปฏิเสธบทบาท `system`** — แก้ไขแล้วใน v1.x โดยตัวปรับบทบาทจะรวมข้อความระบบเข้ากับข้อความผู้ใช้โดยอัตโนมัติสำหรับโมเดลที่เข้ากันไม่ได้ หากยังพบปัญหานี้ใน v3.x+ โปรดแจ้งปัญหา
- **ไม่รู้จักบทบาท `developer`** — แก้ไขแล้วใน v1.x โดยจะถูกแปลงเป็น `system` โดยอัตโนมัติสำหรับผู้ให้บริการที่ไม่ใช่ OpenAI หากยังพบปัญหานี้ใน v3.x+ โปรดแจ้งปัญหา
- **`json_schema` ใช้งานกับ Gemini ไม่ได้** — แก้ไขแล้วใน v1.x โดยขณะนี้ `response_format` จะถูกแปลงเป็น `responseMimeType` + `responseSchema` ของ Gemini หากยังพบปัญหานี้ใน v3.x+ โปรดแจ้งปัญหา

## การตั้งค่าความยืดหยุ่น

### การจำกัดอัตราอัตโนมัติไม่ทำงาน

- การจำกัดอัตราอัตโนมัติใช้กับผู้ให้บริการที่ใช้ API key เท่านั้น (ไม่รวม OAuth/การสมัครสมาชิก)
- ตรวจสอบว่าได้เปิดใช้การจำกัดอัตราอัตโนมัติใน **Settings → Resilience → Provider Profiles**
- ตรวจสอบว่าผู้ให้บริการส่งคืนรหัสสถานะ `429` หรือส่วนหัว `Retry-After` หรือไม่

### การปรับแต่ง exponential backoff

โปรไฟล์ผู้ให้บริการรองรับการตั้งค่าเหล่านี้:

- **Base delay** — ระยะเวลารอเริ่มต้นหลังจากล้มเหลวครั้งแรก (ค่าเริ่มต้น: 1s)
- **Max delay** — ขีดจำกัดสูงสุดของระยะเวลารอ (ค่าเริ่มต้น: 30s)
- **Multiplier** — อัตราการเพิ่มระยะเวลารอต่อการล้มเหลวต่อเนื่องแต่ละครั้ง (ค่าเริ่มต้น: 2x)

### การป้องกัน thundering herd

เมื่อคำขอพร้อมกันจำนวนมากเรียกใช้ผู้ให้บริการที่ถูกจำกัดอัตรา OmniRoute จะใช้ mutex ร่วมกับการจำกัดอัตราอัตโนมัติเพื่อประมวลผลคำขอตามลำดับและป้องกันความล้มเหลวที่ลุกลามเป็นลูกโซ่ กระบวนการนี้ทำงานโดยอัตโนมัติสำหรับผู้ให้บริการที่ใช้ API key

### คำขอแชทล้มเหลวด้วย 503 / chat_admission_busy

**อาการ:**

- endpoint สำหรับ chat completions ส่งคืนการตอบกลับ `503` ที่ลองใหม่ได้ โดยมีรหัสข้อผิดพลาดเป็น
  `chat_admission_busy`
- การตอบกลับมี `Retry-After` ตั้งแต่ #12135 เป็นต้นมา ค่านี้คำนวณจากปริมาณการใช้งานที่ตรวจพบ
  โดยเลือกค่าที่มากกว่าระหว่างช่วงเวลา `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ที่คำขอได้รอไปแล้ว
  กับระยะเวลาที่ heavyweight leases ปัจจุบันถูกถือครอง จากนั้นปัดขึ้นเป็นจำนวนวินาทีเต็ม
  และจำกัดสูงสุดไว้ที่ 60 สำหรับ gate ที่ว่าง ค่านี้จะยังคงใช้ค่าต่ำสุดแบบเดิม ได้แก่ 2 วินาที
  สำหรับเส้นทางแบบอิง byte และ 1 วินาทีสำหรับเส้นทางแบบอิงโครงสร้าง (ซึ่งมี
  `reason: "structure_limit"` รวมอยู่ด้วย)
- เหตุการณ์นี้อาจเกิดขึ้นขณะที่แชทแบบ heavyweight อื่นหรือการตอบกลับแบบ streaming ที่ใช้เวลานาน
  ยังคงอยู่ระหว่างการประมวลผล

เนื้อหาการตอบกลับแบบอิง byte คือ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

การตอบกลับแบบอิงโครงสร้างใช้ type และ code เดียวกัน โดยมีข้อความ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
และ `reason: "structure_limit"`
เมื่อใช้ค่า threshold เริ่มต้น คำขอจะถือว่ามีโครงสร้างแบบ heavyweight หากมีข้อความอย่างน้อย `200` รายการ
มี tools อย่างน้อย `64` รายการ หรือมีจำนวน token โดยประมาณอย่างน้อย `32,000` รายการ หรือเมื่อการประมาณ
โครงสร้างแบบมีขอบเขตใช้ขีดจำกัดจนครบ `10,000` node ที่เข้าถึง หรือความลึก `12`

**สาเหตุ:** นี่คือการลดภาระโดยเจตนาภายใน OmniRoute ไม่ใช่ความล้มเหลวของผู้ให้บริการ upstream
แต่ละ process ใช้ guard ภายใน process เพื่อสำรองความจุแบบ heavyweight ที่มีอยู่อย่างจำกัดก่อนเก็บ
และ parse เนื้อหาคำขอขนาดใหญ่ heavyweight lease จะยังคงถูกถือครองตลอดอายุของการตอบกลับ SSE

**#503-fanout:** ก่อนการแก้ไขนี้ guard จำกัด concurrency ด้วยจำนวนคำขอคงที่
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ค่าเริ่มต้น `1`) โดยไม่คำนึงถึงหน่วยความจำของ host ทำให้
fan-out ของ coding agent (subagent/CLI หลายตัว โดยเนื้อหามักมีขนาด > 256 KB) ลดเหลือ concurrency
ที่ใช้งานได้จริงประมาณ 1 และเกิด 503 ภายใต้ภาระงานปกติโดยสิ้นเชิง ขณะนี้ guard สามารถปรับแต่งตัวเองได้:
การทำงานถูกควบคุมด้วยงบประมาณ BYTE สำหรับการรับข้อมูลที่คำนวณโดยอัตโนมัติ
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ซึ่งกำหนดขนาดจากขีดจำกัดหน่วยความจำจริงของ process
และยังตรวจสอบสัญญาณแรงกดดันด้านทรัพยากรแบบสดด้วย ดังนั้นจึงลดภาระเฉพาะเมื่อ host อยู่ภายใต้
แรงกดดันด้านหน่วยความจำจริง ๆ ไม่ใช่เพียงเพราะมีคำขอแบบ heavy มากกว่าหนึ่งรายการเข้ามาพร้อมกัน
ขีดจำกัดจำนวนแบบเดิม (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ยังคงมีผล แต่เฉพาะเมื่อคุณกำหนดค่า
ไว้อย่างชัดเจนเท่านั้น

เมื่อความจุไม่ว่าง คำขอแบบ heavyweight จะรอให้ slot ว่างก่อนเป็นเวลาสูงสุด
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ค่าเริ่มต้นคือ `RATE_LIMIT_MAX_WAIT_MS`; `0` ปิดใช้งานการรอ)
ก่อนตอบกลับด้วย `503` ที่ลองใหม่ได้ การรอแบบมีขอบเขตนี้มีไว้เพื่อให้ไคลเอนต์แบบ agent
(OpenCode, Claude Code, Cursor) ที่กระจายคำขอย่อยแบบ heavy พร้อมกันสามารถจัดลำดับ burst
แทนที่จะใช้ retry budget ทั้งหมดไปกับการถูกปฏิเสธทันทีและหยุดทำงานระหว่างงาน
จำนวน heavyweight lease ที่กำลังใช้งาน งบประมาณ byte ที่คำนวณแล้ว และระดับความรุนแรงของ
แรงกดดันแบบสด จะแสดงที่ `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) โปรดตรวจสอบค่าเหล่านี้ก่อนแก้ไข env var ใด ๆ
Settings → Resilience → Request Queue → Concurrent Requests ไม่ได้ควบคุมส่วนนี้ การตั้งค่านั้น
ควบคุมกลไกคิวคำขอของผู้ให้บริการอีกระบบหนึ่งซึ่งแยกต่างหาก

**วิธีแก้ไข:**

1. ลองใหม่ก่อน ไคลเอนต์ควรปฏิบัติตาม `Retry-After` และใช้ backoff แทนการส่งคำขอซ้ำทันที
2. ตรวจสอบ `/api/monitoring/health` → `chatAdmission` ก่อนปรับแต่งสิ่งใด `countCapEnabled:
false` และค่า `maxInflightBytes` ที่เพียงพอหมายความว่างบประมาณที่คำนวณโดยอัตโนมัติกำลังทำงาน
   ตามที่ควร ส่วน `pressureSeverity` ที่มีค่า `high`/`critical` หมายความว่า host มีหน่วยความจำ
   เหลือน้อยจริง ๆ ซึ่งไม่สามารถแก้ไขได้ด้วย admission env var แต่ต้องเพิ่ม RAM หรือลด workload
3. เฉพาะเมื่อ `/api/monitoring/health` แสดงว่างบประมาณที่คำนวณโดยอัตโนมัตินั้นน้อยเกินไปจริง ๆ
   สำหรับ host ของคุณ (พบได้น้อย เนื่องจากระบบปรับขนาดตั้งแต่ container ไปจนถึง bare-metal อยู่แล้ว)
   ให้ override โดยตรงด้วย `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` แทนการย้อนกลับไปใช้ขีดจำกัดจำนวนคำขอแบบเดิม

โปรดดู[เอกสารอ้างอิงตัวแปรสภาพแวดล้อม](../reference/ENVIRONMENT.md#4-security--authentication)
สำหรับการตั้งค่า admission ที่เป็นข้อมูลอ้างอิงอย่างเป็นทางการ

## อนุกรมวิธานความล้มเหลวของ RAG / LLM ที่ใช้ได้ตามต้องการ (16 ปัญหา)

ผู้ใช้ OmniRoute บางรายวางเกตเวย์ไว้ด้านหน้าสแตก RAG หรือเอเจนต์ ในการตั้งค่าเหล่านี้ มักพบรูปแบบที่ดูแปลก: OmniRoute ดูทำงานเป็นปกติ (ผู้ให้บริการพร้อมใช้งาน โปรไฟล์การกำหนดเส้นทางไม่มีปัญหา ไม่มีการแจ้งเตือนเรื่องขีดจำกัดอัตรา) แต่คำตอบสุดท้ายยังคงผิดอยู่

ในทางปฏิบัติ เหตุการณ์เหล่านี้มักเกิดจากไปป์ไลน์ RAG ปลายทาง ไม่ใช่จากตัวเกตเวย์เอง

หากต้องการชุดคำศัพท์ร่วมกันเพื่ออธิบายความล้มเหลวเหล่านั้น คุณสามารถใช้ WFGY ProblemMap ซึ่งเป็นแหล่งข้อมูลข้อความภายนอกภายใต้สัญญาอนุญาต MIT ที่นิยามรูปแบบความล้มเหลวของ RAG / LLM ที่เกิดซ้ำ 16 รูปแบบ โดยภาพรวมครอบคลุมเรื่องต่อไปนี้:

- การเบี่ยงเบนของการดึงข้อมูลและขอบเขตบริบทที่เสียหาย
- ดัชนีและที่เก็บเวกเตอร์ที่ว่างเปล่าหรือล้าสมัย
- ความไม่ตรงกันระหว่าง embedding กับความหมายเชิงความหมาย
- ปัญหาการประกอบพรอมต์และหน้าต่างบริบท
- การพังทลายของตรรกะและคำตอบที่มั่นใจเกินจริง
- ความล้มเหลวของสายงานแบบยาวและการประสานงานของเอเจนต์
- หน่วยความจำแบบหลายเอเจนต์และการเบี่ยงเบนของบทบาท
- ปัญหาลำดับการดีพลอยและการเริ่มต้นระบบ

แนวคิดนั้นเรียบง่าย:

1. เมื่อตรวจสอบคำตอบที่ไม่ดี ให้บันทึก:
   - งานและคำขอของผู้ใช้
   - เส้นทางหรือชุดผู้ให้บริการใน OmniRoute
   - บริบท RAG ใดๆ ที่ใช้ในระบบปลายทาง (เอกสารที่ดึงมา การเรียกใช้เครื่องมือ ฯลฯ)
2. จับคู่เหตุการณ์กับหมายเลข WFGY ProblemMap หนึ่งหรือสองหมายเลข (`No.1` … `No.16`)
3. จัดเก็บหมายเลขไว้ในแดชบอร์ด คู่มือปฏิบัติงาน หรือตัวติดตามเหตุการณ์ของคุณเอง ถัดจากบันทึกของ OmniRoute
4. ใช้หน้า WFGY ที่ตรงกันเพื่อตัดสินใจว่าจำเป็นต้องเปลี่ยนสแตก RAG ตัวดึงข้อมูล หรือกลยุทธ์การกำหนดเส้นทางหรือไม่

ข้อความฉบับเต็มและแนวทางแก้ไขที่เป็นรูปธรรมอยู่ที่นี่ (สัญญาอนุญาต MIT, ข้อความเท่านั้น):

[README ของ WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

คุณสามารถข้ามส่วนนี้ได้หากไม่ได้ใช้งานไปป์ไลน์ RAG หรือเอเจนต์หลัง OmniRoute

- "ไม่พบ Devin CLI" หรือ "การยืนยันตัวตนล้มเหลว" เมื่อเรียกใช้เครื่องมือที่รองรับโดย Devin
- การตรวจสอบรันไทม์ของ CLI รายงาน `installed=false`

**สาเหตุ:**

- `CLI_DEVIN_BIN` ชี้ไปยังพาธที่ไม่มีอยู่
- ไม่ได้ติดตั้ง Devin CLI บนโฮสต์

**วิธีแก้ไข:**

1. ติดตั้ง Devin CLI สำหรับแพลตฟอร์มของคุณ
2. ตั้งค่า `CLI_DEVIN_BIN=/usr/local/bin/devin` (หรือพาธจริง) ใน `.env`
3. รีสตาร์ต OmniRoute และทดสอบอีกครั้งจาก **แดชบอร์ด → เครื่องมือ CLI**

### คูลดาวน์ของโมเดลค้างอยู่ (รีเซ็ตด้วยตนเอง)

**อาการ:**

- โมเดลยังคงแสดงว่าอยู่ในสถานะคูลดาวน์ แม้จะเลยเวลาหมดอายุแล้ว
- คำขอยังคงข้ามโมเดลในการกำหนดเส้นทางแบบผสม แม้การประทับเวลาจะเป็นเวลาในอดีต

**การรีเซ็ตด้วยตนเอง:**

- **แดชบอร์ด:** **การตั้งค่า → คูลดาวน์ของโมเดล** → คลิก **เปิดใช้งานอีกครั้ง** บนการ์ดที่ได้รับผลกระทบ
- **API:** `DELETE /api/resilience/model-cooldowns` พร้อมส่วนหัวการยืนยันตัวตนสำหรับการจัดการ

### การเชื่อมต่อผู้ให้บริการ Command Code ล้มเหลวด้วย 403

**อาการ:**

- ได้รับ 403 เมื่อทดสอบการเชื่อมต่อกับผู้ให้บริการ Command Code
- การ์ดผู้ให้บริการแสดง "ไม่ได้รับอนุญาต" หลังจากเพิ่มใหม่

**สาเหตุ:** โฟลว์ OAuth ไม่เสร็จสมบูรณ์ (ไม่ได้รับ callback หรือไม่ได้บันทึกโทเค็นไว้)

**วิธีแก้ไข:**

- เรียกใช้ `omniroute providers` จาก CLI เพื่อเริ่มโฟลว์ OAuth อีกครั้ง หรือ
- เรียกใช้ OAuth อีกครั้งจาก **แดชบอร์ด → ผู้ให้บริการ → Command Code → เชื่อมต่อใหม่**

### ModelScope ส่งคืนคูลดาวน์ 429 ที่เข้มงวด

**อาการ:**

- เกิดคูลดาวน์ที่สั้นมากหรือทันทีบน ModelScope หลังจากมีคำขอจำนวนไม่มากในช่วงเวลาสั้นๆ
- การกำหนดเส้นทางแบบผสมข้าม ModelScope เร็วกว่าที่คาดไว้

**สาเหตุ:** ModelScope ส่งส่วนหัว `Retry-After` เฉพาะของผู้ให้บริการมาให้ v3.8.0 มาพร้อมการจัดการส่วนหัวเหล่านั้นโดยเฉพาะ ดังนั้นเวอร์ชันเก่าจึงตีความส่วนหัวดังกล่าวผิดว่าเป็นคำแนะนำทั่วไปเกี่ยวกับขีดจำกัดอัตรา

**วิธีแก้ไข:**

- ตรวจสอบให้แน่ใจว่าคุณใช้ v3.8.0 หรือใหม่กว่า
- ตรวจสอบว่าเปิดใช้ตัวสลับ `useUpstream429BreakerHints` ภายใต้ **การตั้งค่า → ความยืดหยุ่นในการทำงาน**

### ไม่มี OMNIROUTE_WS_BRIDGE_SECRET ในระบบที่ใช้งานจริง

**อาการ:**

- ได้รับ 401 ในทุกคำขอไปยังบริดจ์ WebSocket ของ Codex/Responses เมื่อทำงานบนโฮสต์สำหรับใช้งานจริงจากระยะไกล
- การจับมือของบริดจ์ WebSocket ปิดทันทีหลังจากเชื่อมต่อ

**สาเหตุ:** ไม่มีตัวแปรสภาพแวดล้อม `OMNIROUTE_WS_BRIDGE_SECRET` ในสภาพแวดล้อมที่ใช้งานจริง

**วิธีแก้ไข:**

1. สร้างค่าลับแบบสุ่ม: `openssl rand -hex 32`
2. ตั้งค่า `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ในสภาพแวดล้อมของเซิร์ฟเวอร์ที่ใช้งานจริง (และในไคลเอนต์ใดๆ ที่สื่อสารกับบริดจ์)
3. รีสตาร์ต OmniRoute

### Responses API: โหมดเบื้องหลังลดระดับเป็นการทำงานแบบซิงโครนัส

**อาการ:**

- มีการบันทึกคำเตือน: `background mode degraded to synchronous`
- คำขอ `background: true` ส่งคืนการตอบกลับแบบซิงโครนัสตามปกติ แทนที่จะเป็นตัวจัดการงานเบื้องหลัง

**สาเหตุ:** v3.8.0 ตั้งใจลดระดับ `background: true` บน Responses API ให้ทำงานแบบซิงโครนัส พร้อมส่งคำเตือนออกมา การดำเนินงานเบื้องหลังแบบอะซิงโครนัสเต็มรูปแบบเป็นสิ่งที่จะส่งมอบในอนาคต

**วิธีแก้ไข:**

- ปรับไคลเอนต์ให้เรียกใช้โดยไม่มี `background` หรือ
- รอรุ่นถัดไปที่มาพร้อมโหมดเบื้องหลังแบบอะซิงโครนัสเต็มรูปแบบ (ติดตามบันทึกการเปลี่ยนแปลง)

## การเริ่มต้นช้า / หมดเวลารอความพร้อม

หาก CLI แสดง `⚠ Server did not respond within 60s` แต่เซิร์ฟเวอร์ทำงานอยู่จริง แสดงว่าระยะเวลาที่กำหนดไว้สำหรับการตรวจสอบความพร้อมสั้นเกินไปสำหรับสภาพแวดล้อมของคุณ

เหตุการณ์นี้มักเกิดขึ้นบน Windows (โปรแกรมป้องกันไวรัส ตัวเฝ้าดูระบบไฟล์) หรือคอนเทนเนอร์ที่มีภาระงานสูงระหว่างการเริ่มต้น

**วิธีแก้ไข — เพิ่มระยะเวลารอ:**

```bash
# ผ่านตัวแปรสภาพแวดล้อม (มีผลต่อเนื่องในการเริ่มต้นครั้งถัดไป):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 นาที
omniroute serve

# ผ่านแฟล็ก CLI (ใช้ครั้งเดียว):
omniroute serve --ready-timeout 180000
```

ค่าเริ่มต้นคือ 60 000 ms (60 s) คำเตือนนี้มีไว้เพื่อแจ้งข้อมูลเท่านั้น เซิร์ฟเวอร์จะเริ่มต้นต่อไปในเบื้องหลังและจะสามารถเข้าถึงได้เมื่อกระบวนการบูตเสร็จสมบูรณ์

ดูรายละเอียดทั้งหมดเกี่ยวกับ `OMNIROUTE_READY_TIMEOUT_MS` ได้ที่ [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)
