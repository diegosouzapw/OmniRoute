## ข้อมูลอ้างอิงฉบับย่อ

**เพิ่งเริ่มใช้ OmniRoute ใช่ไหม?** เริ่มที่นี่ — วิธีเหล่านี้แก้ปัญหาได้ 90%:

| สิ่งที่พบ               | ความหมาย                          | สิ่งที่ควรทำ                                                                                                   |
| ----------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| "เชื่อมต่อไม่ได้"       | OmniRoute ไม่ได้ทำงานอยู่         | เรียกใช้ `omniroute` หรือ `docker restart omniroute`                                                           |
| "คีย์ API ไม่ถูกต้อง"   | คีย์ของคุณไม่ถูกต้องหรือหมดอายุ   | คัดลอกคีย์จากเว็บไซต์ของผู้ให้บริการอีกครั้ง                                                                   |
| "เกินขีดจำกัดอัตรา"     | คุณส่งคำขอมากเกินไป               | รอ 1 นาที หรือใช้ `model: "auto"` เพื่อสลับไปใช้ตัวเลือกสำรองโดยอัตโนมัติ                                      |
| "เกินโควตา"             | คุณใช้โควตาฟรี/แบบชำระเงินหมดแล้ว | เชื่อมต่อผู้ให้บริการเพิ่มเติม หรือใช้ผู้ให้บริการฟรี (Kiro, Pollinations)                                     |
| "ตอบสนองช้า"            | ผู้ให้บริการไม่ว่างหรืออยู่ไกล    | ใช้ `model: "auto/fast"` หรือเชื่อมต่อผู้ให้บริการที่เร็วกว่า (Groq, Cerebras)                                 |
| "ใช้ผู้ให้บริการผิดราย" | `auto` เลือกผู้ให้บริการรายอื่น   | นี่เป็นเรื่องปกติ! `auto` จะเลือกตัวเลือกที่ดีที่สุด บังคับใช้ผู้ให้บริการที่ระบุด้วย `model: "openai/gpt-4o"` |
| "502 เกตเวย์ไม่ถูกต้อง" | ผู้ให้บริการหยุดทำงาน             | รอแล้วลองใหม่ หรือใช้ `model: "auto"` เพื่อสลับผู้ให้บริการ                                                    |
| "401 ไม่ได้รับอนุญาต"   | ข้อมูลรับรองของคุณไม่ถูกต้อง      | ตรวจสอบคีย์ API หรือยืนยันตัวตนด้วย OAuth อีกครั้ง                                                             |
| "429 คำขอมากเกินไป"     | ถูกจำกัดอัตราการใช้งาน            | รอ 1 นาที หรือเชื่อมต่อผู้ให้บริการเพิ่มเติม                                                                   |

### การจำกัดอัตราบนผู้ให้บริการฟรี (429 / 400 / 401)

**อาการ**: เมื่อใช้ `model: "auto"` กับผู้ให้บริการฟรี/ไม่ต้องยืนยันตัวตน (opencode, auggie ฯลฯ) คุณจะได้รับ `HTTP 429`, `400` หรือ `401` แทนคำตอบเป็นระยะ คำขอจะสำเร็จเมื่อลองส่งพรอมต์เดิมอีกครั้งในอีกไม่กี่อึดใจต่อมา แต่ระบบอัตโนมัติ (งาน cron, เอเจนต์, สคริปต์) จะหยุดทำงานเมื่อเกิดความล้มเหลวครั้งแรก

**สาเหตุหลัก**: โหมดความล้มเหลวสามรูปแบบที่แยกจากกันเกิดซ้อนทับกัน:

1. **ขีดจำกัดอัตราของผู้ให้บริการ (`429`)**: แพ็กเกจฟรีอาจกำหนดโควตาต่อช่วงเวลา การเรียกแบบขนานพร้อมกันจำนวนมากจะใช้โควตาจนหมด ดังนั้นคำขอถัดไปจึงถูกปฏิเสธจนกว่าจะเริ่มช่วงเวลาใหม่
2. **โมเดลที่ใช้งานไม่ได้ใน passthrough (`400`/`401`)**: พูล `auto/*` อาจรวมโมเดล passthrough จาก `opencode` ซึ่งลงทะเบียนอยู่ในแค็ตตาล็อก แต่ไม่มีข้อมูลรับรองที่ใช้งานได้ (เช่น `oc/north-mini-code-free` → `401`) ตัวกำหนดเส้นทางอัตโนมัติจะลองใช้โมเดลหนึ่ง เกิดความล้มเหลว และส่งต่อข้อผิดพลาดก่อนที่การสลับไปใช้ตัวเลือกสำรองจะเริ่มทำงาน
3. **การขยายผลจากการทำงานพร้อมกัน (`429` เมื่อมีโหลด)**: เมื่อเซสชันของเอเจนต์/cron หลายเซสชันเรียกใช้ `auto` พร้อมกัน อัตราคำขอรวมจะเกินระดับที่ผู้ให้บริการฟรีรองรับ ทำให้การเรียกที่ถูกต้องถูกระบุว่าเป็นการใช้งานในทางที่ผิด

**วิธีแก้ไขที่ยืนยันแล้ว (รายงานโดยชุมชน, 2026-08-10)**: ปรับตัวแปรสภาพแวดล้อมสามตัวเพื่อให้การหมุนเวียน การทำงานพร้อมกัน และการสลับไปใช้ตัวเลือกสำรองช่วยรองรับความผันผวนของแพ็กเกจฟรีแทนที่จะล้มเหลว:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ข้ามไปยังโมเดล/ผู้ให้บริการอื่นเมื่อพบ 400/401 (ข้ามโมเดล passthrough ที่ใช้งานไม่ได้)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # เพดานการรับงานหนักอย่างชัดเจน (ค่าเริ่มต้นคือไม่ได้ตั้งค่า: ไม่มีขีดจำกัดจำนวนคำขอ ดูหมายเหตุด้านล่าง)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # รอความจุสำหรับงานหนักภายในขอบเขตเวลานานขึ้น แทนการส่ง 503 ที่ลองใหม่ได้ทันที
```

ตั้งค่าเหล่านี้ในสภาพแวดล้อมของกระบวนการ OmniRoute (ดีมอน เช่น ผ่าน LaunchAgent plist หรือ `systemctl edit`) แล้วเริ่ม OmniRoute ใหม่ แฟล็กการหมุนเวียนเป็นกลไกที่ให้ผลลัพธ์สูงสุดเพียงตัวเดียว โดยจะเปลี่ยนความล้มเหลวแบบถาวรให้เป็นการลองใหม่กับผู้ให้บริการที่พร้อมใช้งานในพูลอย่างโปร่งใส

**หมายเหตุ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` จำกัดจำนวนคำขอแบบงานหนัก — ที่มีบริบทยาว — ที่ทำงานพร้อมกัน ขอบเขตนี้เป็นเกตควบคุมการรับงาน ไม่ใช่ตัวจำกัดอัตราของผู้ให้บริการ **ข้อมูลอัปเดต #503-fanout:** ตัวแปรนี้จะไม่ถูกตั้งค่าโดยค่าเริ่มต้นอีกต่อไป (ขณะนี้จะมีผลเฉพาะเมื่อตั้งค่าไว้อย่างชัดเจนดังตัวอย่างด้านบน) — การรับงานหนักจะถูกควบคุมด้วยงบประมาณไบต์ที่คำนวณอัตโนมัติ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ซึ่งปรับขนาดตัวเองตามเพดานหน่วยความจำจริงของโฮสต์ ดังนั้นการติดตั้งใหม่ควรพบการปฏิเสธ `503 chat_admission_busy` น้อยลงอย่างมากโดยไม่ต้องตั้งค่าตัวแปรนี้เลย ทั้งนี้ การตั้งค่าไว้อย่างชัดเจนตามตัวอย่างนี้ยังคงทำงานตรงตามเอกสารทุกประการ การกำหนดงบประมาณไบต์เองอย่างชัดเจนจะถูกจำกัดไว้ที่ 8 MiB–2 GiB ข้อผิดพลาด `413 body_exceeds_budget` ไม่ใช่ข้อผิดพลาดชั่วคราว: ให้เพิ่มงบประมาณไบต์ดังกล่าว ลด `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` หรือเพิ่มเพดานหน่วยความจำของกระบวนการ การลดภาระด้วย `inflight_bytes_budget` เป็นภาวะช่วงชิงทรัพยากรชั่วคราวและยังสามารถลองใหม่ได้ การจำกัดอัตราแยกตามผู้ให้บริการ (`open-sse/services/rateLimitManager.ts`) ถูกควบคุมแยกต่างหากโดย `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` และ `RATE_LIMIT_AUTO_ENABLE` — ดู `.env.example`

**วิธีตรวจสอบว่าได้ผล**: เรียกใช้เอเจนต์/cron ของคุณสองครั้งติดต่อกันอย่างรวดเร็ว และยืนยันว่าทั้งสองครั้งสำเร็จ ก่อนแก้ไข การเรียกครั้งที่สองมักจะแสดงข้อผิดพลาด `429`/`401` หลังแก้ไข ความล้มเหลว (หากมี) จะถูกลองใหม่อย่างโปร่งใส และการเรียกจะดำเนินการจนเสร็จสมบูรณ์ นอกจากนี้ คุณยังสามารถใช้ `curl /monitoring/health` แล้วตรวจดูฟิลด์ `rateLimitedUntil` ในการเชื่อมต่อของผู้ให้บริการ และ `circuitBreakers.providerBreakers[].state` สำหรับผู้ให้บริการที่ได้รับผลกระทบ — สถานะจะเป็นค่าใดค่าหนึ่งระหว่าง `CLOSED`, `DEGRADED`, `OPEN` หรือ `HALF_OPEN` (ดู `src/shared/utils/circuitBreaker.ts`) และผู้ให้บริการที่เกิดความล้มเหลวอย่างต่อเนื่องจะเปลี่ยนจาก `CLOSED → DEGRADED → OPEN` ก่อนที่ช่วงเวลารีเซ็ตจะอนุญาตให้คำขอตรวจสอบผ่านได้ (`HALF_OPEN`)

**หากคุณยังคงพบ 429**: บัญชีที่ใช้งานอยู่สำหรับผู้ให้บริการรายนั้นได้ใช้ _โควตา_ หมดแล้วจริง ๆ (ไม่ใช่แค่ติดข้อจำกัดอัตราการใช้งาน) ให้เพิ่มบัญชีที่สองสำหรับผู้ให้บริการรายเดิมในแดชบอร์ด OmniRoute → Providers → Accounts หรือใช้ผู้ให้บริการฟรีรายอื่นร่วมด้วย (เช่น `routeway`, `auggie`) การหมุนเวียนบัญชีช่วยได้เฉพาะข้อผิดพลาดชั่วคราวเกี่ยวกับข้อจำกัดอัตราการใช้งาน/400/401 เท่านั้น ส่วนการใช้โควตาจนหมดแบบถาวรจำเป็นต้องใช้ข้อมูลประจำตัวชุดที่สองหรือผู้ให้บริการรายอื่น

**หากคุณพบ 403 ในโมเดลด้านวิชัน (`auto/vision`, `bazaarlink/*`)**: บัญชีที่เชื่อมต่อไม่มีแพ็กเกจแบบชำระเงินที่รวมความสามารถด้านวิชัน หรือคีย์ API มีสิทธิ์ไม่เพียงพอ ให้ตรวจสอบในแดชบอร์ดของผู้ให้บริการว่าขอบเขตสิทธิ์ของคีย์ครอบคลุมวิชัน/มัลติโหมด หรือเชื่อมต่อบัญชีแพ็กเกจแบบชำระเงินและกำหนดให้เป็นเป้าหมายสำหรับงานด้านวิชัน

## คำเตือนจาก npm install (ERESOLVE / peer / deprecated)

เมื่อคุณเรียกใช้ `npm install -g omniroute` คุณอาจเห็นคำเตือนจำนวนมาก เช่น `npm warn ERESOLVE` การแจ้งเตือนเกี่ยวกับ peer dependency และข้อความ `deprecated` **คำเตือนเหล่านี้เป็นสิ่งที่คาดว่าจะเกิดขึ้นและไม่เป็นอันตราย** การติดตั้งสำเร็จแล้วหากคุณเห็น `added <N> packages` ในเอาต์พุต

คำเตือนเหล่านี้มาจากช่วงเวอร์ชัน peer dependency ที่ล้าสมัยในแพ็กเกจของบุคคลที่สามซึ่ง OmniRoute ไม่ได้ควบคุม:

1. **`marked-terminal` ต้องการ `marked >=1 <16` แต่พบ `marked@18`** — ในทางปฏิบัติยังทำงานได้ตามปกติ เพียงแต่ช่วงเวอร์ชัน peer ของต้นทางล้าสมัย
2. **`deprecated prebuild-install@7.1.3`** — ตัวช่วยดึงไบนารีแบบเนทีฟที่เป็น dependency ทางอ้อม โดยไม่ได้
   ถูกใช้เพื่อติดตั้ง transport binding ของ `wreq-js` เวอร์ชันที่ตรึงไว้ และไม่ได้บ่งชี้ว่าการตั้งค่า transport
   ของผู้ให้บริการ web-cookie ล้มเหลว

**ไม่จำเป็นต้องดำเนินการใดๆ** — ไม่สามารถปิดคำเตือนเหล่านี้ได้ทั้งหมดหากไม่ fork แพ็กเกจต้นทาง

## ผลบวกลวงจากโปรแกรมป้องกันไวรัส

<a name="antivirus-false-positives"></a>

### Avast/AVG กักกัน `README.md` ด้วยการตรวจจับ `MD:HttpRequest-inf[Susp]`

**นี่เป็นผลบวกลวง ไม่มีสิ่งใดติดไวรัสและไม่จำเป็นต้องดำเนินการใดๆ**

Avast และ AVG ใช้ฮิวริสติกที่ทำเครื่องหมายไฟล์ข้อความธรรมดา/Markdown ซึ่งมีลิงก์จำนวนมากที่ดูเหมือนคำขอ HTTP โดย `README.md` ของ OmniRoute รวมอยู่ในแพ็กเกจ npm (มีรายชื่ออยู่ใน `package.json` → `files`) ดังนั้นเมื่อติดตั้งแบบส่วนกลาง ไฟล์นี้จึงอยู่ที่ `node_modules/omniroute/README.md` และภายในมีตัวอย่าง `http://localhost:20128/...` ประมาณ 15 รายการ (ปลายทาง HTTP/SSE ของ MCP, URL `.well-known` ของ A2A และตัวอย่าง `curl`) ความหนาแน่นของลิงก์ในระดับนี้เพียงพอที่จะกระตุ้นฮิวริสติกดังกล่าว

หากปัญหานี้เพิ่งเริ่มเกิดขึ้นเมื่อไม่นานมานี้: ลักษณะของไฟล์ไม่ได้เปลี่ยนไป README เพียงมีตารางปลายทางเพิ่มขึ้น (เพิ่ม MCP HTTP + SSE + A2A) รวมถึงตัวอย่าง `curl` ที่มากขึ้น ซึ่งทำให้จำนวนเกินเกณฑ์

ไฟล์นี้เป็นเพียงเอกสารที่ไม่มีการทำงานใดๆ และไม่มีเนื้อหาที่เรียกใช้งานได้ คุณสามารถกู้คืนจากพื้นที่กักกันได้อย่างปลอดภัย

**สิ่งที่ควรทำ:**

1. **หยุดการแจ้งเตือน** — เพิ่มไดเรกทอรีติดตั้งเป็นข้อยกเว้นในโปรแกรมป้องกันไวรัสของคุณ
   (Avast: Settings → Exceptions) โดยเพิ่มพาธ `node_modules` ส่วนกลางของคุณ และ/หรือ
   ไดเรกทอรีข้อมูลของ OmniRoute (`~/.omniroute/`)
2. **รายงานผลบวกลวง** — <https://www.avast.com/false-positive-file-form.php>
   โดยแนบ `README.md` ที่ถูกกักกัน วิธีนี้เป็นการแก้ไขที่ช่วยทุกคน เนื่องจากปัญหาเกิดจาก
   ฮิวริสติกของผู้จำหน่ายตอบสนองต่อไฟล์ข้อความมากเกินไป

**เหตุผลที่เราไม่ "แก้ไข" เรื่องนี้จากฝั่งของเรา:** ตัวอย่างทั้งหมดใช้ `http://localhost` และ
localhost ไม่สามารถใช้ `https` ได้โดยไม่สร้างความยุ่งยากจากใบรับรองที่ลงนามด้วยตนเอง การดัดแปลงเอกสารเพื่อหลบฮิวริสติกของผู้จำหน่ายรายเดียวจะทำให้ผู้อ่านทุกคนได้รับผลกระทบ เพียงเพื่อรองรับข้อผิดพลาดของเครื่องมือสแกน

### Kaspersky ทำเครื่องหมายแอปเดสก์ท็อปเป็น `PDM:Trojan.Win32.Generic`

**นี่เป็นผลบวกลวงจากฮิวริสติกเชิงพฤติกรรม ไม่มีสิ่งใดติดไวรัส** คำนำหน้า `PDM:` ของ Kaspersky หมายความว่าผลการตัดสินมาจาก Proactive Defense Module (System Watcher) ซึ่งพิจารณาจากสิ่งที่ตัวติดตั้ง _กระทำ_ แทนการเปรียบเทียบกับมัลแวร์ที่รู้จัก เมื่อเกิดการตรวจจับ Kaspersky จะ "ย้อนกลับ" การติดตั้งทั้งหมด โดยลบไฟล์ที่เขียนไปแล้ว ส่งผลให้แอปเสียหายหรือหายไป

ไฟล์ที่ถูกทำเครื่องหมายเป็นส่วนประกอบมาตรฐานของดีเพนเดนซีโอเพนซอร์สที่มีการประกาศไว้อย่างชัดเจนและรวมมากับแอปเดสก์ท็อป ตัวอย่างเช่น:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` และ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev) ไลบรารีระบบอัตโนมัติสำหรับเบราว์เซอร์
  ที่ใช้สำหรับการเข้าสู่ระบบผู้ให้บริการภายในแอปและแชตที่ทำงานผ่านเบราว์เซอร์
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ไบนารีเนทีฟของ `wreq-js` เวอร์ชันที่กำหนดตายตัว ซึ่งใช้สำหรับ HTTP ที่มีลายนิ้วมือเหมือนเบราว์เซอร์กับผู้ให้บริการที่ใช้คุกกี้เว็บ
  (`<arch>` คือ `x64` หรือ `arm64`)

**เหตุผลที่ระบบตรวจจับ:** ตัวติดตั้ง Windows **ยังไม่ได้ลงนามโค้ด** ดังนั้นตัวติดตั้ง NSIS ที่ไม่ได้ลงนามจึงไม่มีคะแนนความน่าเชื่อถือ และฮิวริสติกเชิงพฤติกรรมจะทำงานในระดับเข้มงวดสูงสุด เมื่อประกอบกับ DLL แบบเนทีฟที่รวมมาและไฟล์ `.js` หลายร้อยไฟล์ที่ถูกเขียนลงใน
`%LOCALAPPDATA%\Programs\OmniRoute` (รวมถึงไดเรกทอรีแพ็กเกจที่มีส่วนต่อท้ายเป็นแฮชจากบิลด์แบบ standalone ของ Next.js) จึงเพียงพอที่จะกระตุ้นฮิวริสติกดังกล่าว มีแผนจะลงนามโค้ดในอนาคต แต่ก่อนที่จะดำเนินการเสร็จ รุ่นใหม่ๆ อาจพบปัญหานี้ซ้ำได้

**สิ่งที่ควรทำ:**

1. **ตรวจสอบไฟล์ดาวน์โหลดก่อน** (เพื่อยืนยันว่าไฟล์ไม่ได้ถูกแก้ไข) แต่ละรุ่นจะเผยแพร่
   `latest.yml` ซึ่งฟิลด์ `sha512` (base64) ครอบคลุมตัวติดตั้ง `OmniRoute.Setup.<version>.exe`
   ใน PowerShell ให้รันคำสั่งต่อไปนี้จากโฟลเดอร์ที่มีตัวติดตั้ง:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ผลลัพธ์ต้องตรงกับ `latest.yml` → `sha512` หากไม่ตรงกัน ให้ลบไฟล์และ
   ดาวน์โหลดใหม่จาก[หน้าเผยแพร่ของ GitHub](https://github.com/diegosouzapw/OmniRoute/releases)เท่านั้น
2. **กู้คืน + เพิ่มข้อยกเว้น** — กู้คืนรายการที่ถูกย้อนกลับจากพื้นที่กักกัน และเพิ่มข้อยกเว้น
   สำหรับ `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions)
   จากนั้นติดตั้งใหม่
3. **รายงานผลบวกลวง** — <https://opentip.kaspersky.com/> รายงานผลบวกลวงที่ผู้ใช้ส่งเข้ามา
   ช่วยเร่งกระบวนการเพิ่มลงในรายการอนุญาตได้จริง

## ความเข้ากันได้กับ Node.js

<a name="nodejs-compatibility"></a>

### หน้าเข้าสู่ระบบขัดข้องหรือแสดงข้อผิดพลาด "Module self-registration"

**สาเหตุ:** คุณกำลังใช้ Node.js เวอร์ชันที่อยู่นอกเกณฑ์ขั้นต่ำของรันไทม์ที่ปลอดภัยซึ่ง OmniRoute อนุมัติ กรณีที่พบบ่อยที่สุดคือการใช้ Node 22 หรือ 24 รุ่นแพตช์ที่เก่ากว่าเกณฑ์ขั้นต่ำด้านความปลอดภัยที่ OmniRoute กำหนด

**อาการ:**

- หน้าเข้าสู่ระบบแสดงหน้าจอว่างหรือข้อผิดพลาดของเซิร์ฟเวอร์
- คอนโซลแสดง `Error: Module did not self-register` หรือข้อผิดพลาดเกี่ยวกับ native binding ที่คล้ายกัน
- หน้าเข้าสู่ระบบแสดง **แถบคำเตือนสีส้ม** พร้อมเวอร์ชัน Node ของคุณ หากรันไทม์อยู่นอกนโยบายความปลอดภัยที่รองรับ

**วิธีแก้ไข:**

1. ติดตั้ง Node.js รุ่น LTS ที่รองรับ (แนะนำ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ตรวจสอบเวอร์ชันของคุณ: `node --version` ควรแสดง `v24.0.0` หรือใหม่กว่าในสายรุ่น LTS 24.x
3. ติดตั้ง OmniRoute ใหม่: `npm install -g omniroute`
4. เริ่มการทำงานใหม่: `omniroute`

> **เวอร์ชันที่ปลอดภัยและรองรับ:** `>=22.22.2 <23` หรือ `>=24.0.0 <27` รองรับ Node.js 24.x LTS (Krypton) และ Node.js 26 อย่างเต็มรูปแบบ

### npm v11+: ไม่ได้ติดตั้ง `better-sqlite3` (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**สาเหตุ:** โดยค่าเริ่มต้น npm v11 (ที่มาพร้อมกับ Node.js 24+) จะบล็อกสคริปต์การติดตั้งสำหรับ
dependencies แบบไม่บังคับ เนื่องจาก `better-sqlite3` อยู่ใน `optionalDependencies`
และจำเป็นต้องคอมไพล์ native code (`node-gyp rebuild`) npm จึงข้ามแพ็กเกจนี้ไปโดยไม่แจ้งเตือน

**อาการ:**

- เซิร์ฟเวอร์ขัดข้องระหว่างเริ่มต้นระบบพร้อมข้อความ `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` แสดง "No such file or directory"
- `npm ls better-sqlite3` แสดง `(empty)`

**วิธีแก้ไข:**

1. อนุมัติสคริปต์การติดตั้งแล้วติดตั้งใหม่:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. หรือติดตั้งไฟล์ที่คอมไพล์ไว้ล่วงหน้าด้วยตนเอง:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ตรวจสอบว่าสามารถทำงานได้: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**สาเหตุ:** หลังจากใช้ `npm install -g omniroute` แบบส่วนกลาง ไบนารี native ของ `better-sqlite3` ภายในแพ็กเกจอาจถูกคอมไพล์มาสำหรับสถาปัตยกรรมหรือ ABI ของ Node.js ที่แตกต่างจากสภาพแวดล้อมที่กำลังทำงานอยู่ในเครื่อง กรณีนี้พบได้บ่อยบน macOS (ทั้ง Apple Silicon และ Intel) เมื่อไบนารีที่คอมไพล์ไว้ล่วงหน้าไม่ตรงกับสภาพแวดล้อมของคุณ

**อาการ:**

- เซิร์ฟเวอร์ทำงานล้มเหลวทันทีระหว่างเริ่มต้นระบบพร้อมข้อผิดพลาด `dlopen`
- ข้อผิดพลาดมีข้อความ `slice is not valid mach-o file`
- ตัวอย่างแบบเต็ม:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**วิธีแก้ไข — คอมไพล์ใหม่สำหรับสภาพแวดล้อมในเครื่องของคุณ (ไม่จำเป็นต้องดาวน์เกรด Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **หมายเหตุ:** การดำเนินการนี้จะคอมไพล์ native binding ใหม่ให้ตรงกับเวอร์ชัน Node.js และสถาปัตยกรรม CPU ในเครื่องของคุณ ซึ่งจะช่วยแก้ปัญหาไบนารีไม่ตรงกัน ช่วงรันไทม์ที่รองรับอย่างเป็นทางการคือ **`>=22.22.2 <23` หรือ `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` ใน `src/shared/utils/nodeRuntimeSupport.ts` ซึ่งสอดคล้องกับฟิลด์ `engines` ใน `package.json`) รองรับ Node.js 24.x LTS (Krypton) และ Node.js 26 ร่วมกับ `better-sqlite3` v12.x อย่างเต็มรูปแบบ

## ปัญหาเกี่ยวกับพร็อกซี

<a name="proxy-issues"></a>

### การตรวจสอบผู้ให้บริการแสดงข้อผิดพลาด "fetch failed"

**สาเหตุ:** ก่อนหน้านี้เอนด์พอยต์สำหรับตรวจสอบ API key (`POST /api/providers/validate`) ไม่ได้ใช้การกำหนดค่าพร็อกซี ส่งผลให้เกิดความล้มเหลวในสภาพแวดล้อมที่จำเป็นต้องกำหนดเส้นทางผ่านพร็อกซี

**วิธีแก้ไข (v3.5.5+):** ปัญหานี้ได้รับการแก้ไขแล้ว ขณะนี้การตรวจสอบผู้ให้บริการจะดำเนินการผ่าน `runWithProxyContext` โดยใช้การตั้งค่าพร็อกซีระดับผู้ให้บริการและระดับส่วนกลางโดยอัตโนมัติ

### การตรวจสอบสถานะโทเค็นล้มเหลวด้วยข้อผิดพลาด "fetch failed"

**สาเหตุ:** การรีเฟรช OAuth token ในเบื้องหลังไม่ได้ค้นหาการกำหนดค่าพร็อกซีแยกตามแต่ละการเชื่อมต่อ

**วิธีแก้ไข (v3.5.5+):** ขณะนี้ตัวกำหนดเวลาตรวจสอบสถานะโทเค็นจะค้นหาการกำหนดค่าพร็อกซีแยกตามแต่ละการเชื่อมต่อก่อนพยายามรีเฟรช โปรดอัปเดตเป็น v3.5.5+

### พร็อกซี SOCKS5 ส่งคืนข้อผิดพลาด "invalid onRequestStart method"

**สาเหตุ:** บน Node.js 22 ตัวจัดส่งคำขอของ undici@8 ไม่เข้ากันกับการทำงาน `fetch()` ที่มาพร้อมกับ Node

**วิธีแก้ไข (v3.5.5+):** ขณะนี้ OmniRoute ใช้ฟังก์ชัน `fetch()` ของ undici เองเมื่อมีการใช้งานตัวจัดส่งคำขอผ่านพร็อกซี เพื่อให้มั่นใจว่าการทำงานจะสอดคล้องกัน โปรดอัปเดตเป็น v3.5.5+

### พร็อกซี MITM ภายใต้ WSL: แอปเดสก์ท็อปบนโฮสต์ Windows ไม่ถูกดักจับ

**สาเหตุ:** พร็อกซี MITM และใบรับรอง CA จะถูกติดตั้งในสภาพแวดล้อมที่ OmniRoute ทำงานอยู่ ภายใต้ WSL สภาพแวดล้อมดังกล่าวคือระบบ Linux แบบเกสต์ ขณะที่แอป AI บนเดสก์ท็อป (Kiro, Trae, Copilot, Zed, …) ทำงานอยู่บนโฮสต์ Windows แอปบนโฮสต์ไม่เชื่อถือคลังใบรับรองของระบบเกสต์และไม่กำหนดเส้นทางผ่านพร็อกซีระบบของเกสต์ ดังนั้นการดักจับทราฟฟิกของแอปเดสก์ท็อปจึงไม่ทำงานในกรณีนี้

**คำแนะนำ:** เรียกใช้ OmniRoute แบบเนทีฟบนระบบปฏิบัติการเดียวกับแอปเดสก์ท็อปที่คุณต้องการดักจับ (Windows สำหรับแอป Windows และเช่นเดียวกันสำหรับ macOS/Linux) หากต้องการเก็บ OmniRoute ไว้ภายใน WSL แต่กำหนดเป้าหมายเป็นแอปบนโฮสต์ คุณต้องกำหนดให้โฮสต์ Windows เชื่อถือใบรับรอง CA ที่สร้างขึ้นด้วยตนเอง และตั้งค่าเครือข่าย/พร็อกซีของแต่ละแอปบนโฮสต์ให้ชี้ไปยังเอนด์พอยต์พร็อกซีของ WSL ซึ่งเป็นการตั้งค่าที่ไม่รองรับและเปราะบาง

### "Language model did not provide messages"

**สาเหตุ:** โควตาของผู้ให้บริการถูกใช้หมดแล้ว

**วิธีแก้ไข:**

1. ตรวจสอบตัวติดตามโควตาในแดชบอร์ด
2. ใช้คอมโบที่มีระดับสำรอง
3. เปลี่ยนไปใช้ระดับที่ราคาถูกกว่าหรือฟรี

### การจำกัดอัตราการใช้งาน

**สาเหตุ:** โควตาของการสมัครใช้งานถูกใช้หมดแล้ว

**วิธีแก้ไข:**

- เพิ่มตัวเลือกสำรอง: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- ใช้ GLM/MiniMax เป็นตัวเลือกสำรองราคาประหยัด

### OAuth Token หมดอายุ

OmniRoute จะรีเฟรชโทเค็นโดยอัตโนมัติ หากปัญหายังคงอยู่:

1. แดชบอร์ด → ผู้ให้บริการ → เชื่อมต่อใหม่
2. ลบการเชื่อมต่อกับผู้ให้บริการแล้วเพิ่มใหม่

### Kiro แบบหลายบัญชี: บัญชีที่สองทำให้บัญชีแรกใช้งานไม่ได้

**สาเหตุ:** ระบบแบ็กเอนด์ของ Kiro บังคับให้มีเซสชันที่ใช้งานอยู่ได้เพียงเซสชันเดียวต่อการลงทะเบียน OIDC client
เมื่อสองบัญชีใช้ไคลเอนต์ที่ลงทะเบียนเดียวกันร่วมกัน (การเชื่อมต่อที่นำเข้าก่อน v3.8.0)
การรีเฟรชโทเค็นของบัญชีหนึ่งจะทำให้ refresh token ของอีกบัญชีใช้งานไม่ได้

**วิธีแก้ไข (v3.8.0+):** นำเข้าการเชื่อมต่อที่ได้รับผลกระทบอีกครั้ง
ตั้งแต่ v3.8.0 เป็นต้นไป การเชื่อมต่อ Kiro ใหม่ทุกรายการที่สร้างผ่าน **นำเข้าโทเค็น**,
**การเข้าสู่ระบบโซเชียลด้วย Google/GitHub** หรือ **นำเข้าอัตโนมัติ** จะลงทะเบียน
OIDC client เฉพาะของตนเองโดยอัตโนมัติ ดังนั้นการเชื่อมต่อจึงถูกแยกออกจากกันอย่างสมบูรณ์ และการรีเฟรชบัญชีหนึ่ง
จะไม่ส่งผลกระทบต่อบัญชีอื่น

การเชื่อมต่อที่นำเข้า _ก่อน_ v3.8.0 ไม่มีการลงทะเบียนไคลเอนต์แยกสำหรับแต่ละการเชื่อมต่อ
การเชื่อมต่อเหล่านั้นจะยังคงใช้เอนด์พอยต์สำหรับรีเฟรชการยืนยันตัวตนผ่านโซเชียลร่วมกัน
หากต้องการแยกการเชื่อมต่อออกจากกัน ให้ลบการเชื่อมต่อเก่าจากแดชบอร์ด → ผู้ให้บริการ แล้วเพิ่มใหม่
ผ่านขั้นตอนการนำเข้าวิธีใดวิธีหนึ่งจากสามวิธี

สำหรับรายละเอียดทั้งหมดและคำแนะนำแบบทีละขั้นตอนในการเพิ่มบัญชี Kiro สองบัญชีควบคู่กัน
โปรดดู [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md)

## ปัญหาเกี่ยวกับ Cloud

### ข้อผิดพลาดในการซิงค์ Cloud

1. ตรวจสอบว่า `BASE_URL` ชี้ไปยังอินสแตนซ์ที่กำลังทำงานอยู่ (เช่น `http://localhost:20128`)
2. ตรวจสอบว่า `CLOUD_URL` ชี้ไปยังปลายทาง Cloud ของคุณ (เช่น `https://omniroute.dev`)
3. กำหนดค่า `NEXT_PUBLIC_*` ให้สอดคล้องกับค่าฝั่งเซิร์ฟเวอร์

### Cloud ที่ใช้ `stream=false` ส่งคืน 500

**อาการ:** พบข้อผิดพลาด `Unexpected token 'd'...` ที่ปลายทาง Cloud สำหรับการเรียกแบบไม่สตรีม

**สาเหตุ:** ต้นทางส่งคืนเพย์โหลด SSE ขณะที่ไคลเอนต์คาดว่าจะได้รับ JSON

**วิธีแก้ชั่วคราว:** ใช้ `stream=true` สำหรับการเรียก Cloud โดยตรง รันไทม์ภายในเครื่องมีระบบสำรองสำหรับแปลง SSE→JSON

### Cloud แสดงว่าเชื่อมต่อแล้ว แต่แจ้งว่า "Invalid API key"

1. สร้างคีย์ใหม่จากแดชบอร์ดภายในเครื่อง (`/api/keys`)
2. เรียกใช้การซิงค์ Cloud: Enable Cloud → Sync Now
3. คีย์เก่าหรือคีย์ที่ยังไม่ได้ซิงค์อาจยังคงส่งคืน `401` บน Cloud

## ปัญหาเกี่ยวกับ Docker

### IPv6 ของ Docker / การเชื่อมต่อถูกรีเซ็ต

<a name="docker-ipv6"></a>

**อาการ:** `curl http://localhost:20128/v1/models` ส่งคืน `curl: (56) Recv failure: Connection reset by peer` แดชบอร์ดและปลายทางที่ไม่ต้องยืนยันตัวตนทำงานได้ แต่ปลายทางที่ต้องยืนยันตัวตนล้มเหลว — ปัญหานี้ดูเหมือนเป็นปัญหาการยืนยันตัวตน แต่จริง ๆ แล้วไม่ใช่

**สาเหตุ:** `docker run -p 20128:20128` เผยแพร่พอร์ตทั้งบน `0.0.0.0` (IPv4) และ `::` (IPv6) แต่โปรเซสภายในคอนเทนเนอร์รับฟังบน IPv4 เท่านั้น บนโฮสต์ที่ `localhost` ถูกแปลงเป็น `::1` ก่อน การเชื่อมต่อจะไปยังพอร์ต IPv6 ที่เผยแพร่ไว้โดยไม่มีตัวรับฟังอยู่เบื้องหลัง → การเชื่อมต่อจึงถูกรีเซ็ต

**วิธีแก้ไข:**

1. **การวินิจฉัยอย่างรวดเร็ว:** เรียกใช้ `curl -4 http://localhost:20128/v1/models` หากใช้ `-4` แล้วทำงานได้ แต่ไม่ใช้แล้วล้มเหลว แสดงว่ามีการผูก IPv6 ที่ไม่ตรงกัน
2. **วิธีแก้ไขถาวร:** ผูกกับ IPv4 อย่างชัดเจนโดยใช้ `-p 127.0.0.1:20128:20128` ในคำสั่ง `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   วิธีนี้บังคับให้ผูกกับ IPv4 และยังช่วยหลีกเลี่ยงการเปิดเผยพร็อกซีบนอินเทอร์เฟซทั้งหมดของโฮสต์อีกด้วย

## ปัญหา Circuit Breaker

### ผู้ให้บริการค้างอยู่ในสถานะ OPEN

เมื่อ circuit breaker ของผู้ให้บริการอยู่ในสถานะ OPEN คำขอจะถูกบล็อกจนกว่าระยะเวลาคูลดาวน์จะสิ้นสุดลง

**วิธีแก้ไข:**

1. ไปที่ **Dashboard → Settings → Resilience**
2. ตรวจสอบการ์ด circuit breaker ของผู้ให้บริการที่ได้รับผลกระทบ
3. คลิก **Reset All** เพื่อล้าง breaker ทั้งหมด หรือรอให้ระยะเวลาคูลดาวน์สิ้นสุดลง
4. ตรวจสอบว่าผู้ให้บริการพร้อมใช้งานจริงก่อนรีเซ็ต

### ผู้ให้บริการทริกเกอร์ circuit breaker อย่างต่อเนื่อง

หากผู้ให้บริการเข้าสู่สถานะ OPEN ซ้ำๆ:

1. ตรวจสอบรูปแบบความล้มเหลวที่ **Dashboard → Health → Provider Health**
2. ไปที่ **Settings → Resilience → Provider Profiles** แล้วเพิ่มเกณฑ์ความล้มเหลว
3. ตรวจสอบว่าผู้ให้บริการได้เปลี่ยนขีดจำกัด API หรือต้องมีการยืนยันตัวตนใหม่หรือไม่
4. ตรวจสอบข้อมูลเทเลเมทรีด้านเวลาแฝง — เวลาแฝงสูงอาจทำให้เกิดความล้มเหลวจากการหมดเวลา

- **ไม่รู้จักบทบาท `developer`** — แก้ไขแล้วใน v1.x โดยจะถูกแปลงเป็น `system` โดยอัตโนมัติสำหรับผู้ให้บริการที่ไม่ใช่ OpenAI หากคุณยังพบปัญหานี้ใน v3.x+ โปรดเปิด issue
- **`json_schema` ใช้งานกับ Gemini ไม่ได้** — แก้ไขแล้วใน v1.x โดยขณะนี้ `response_format` จะถูกแปลงเป็น `responseMimeType` + `responseSchema` ของ Gemini หากคุณยังพบปัญหานี้ใน v3.x+ โปรดเปิด issue

## การตั้งค่าความทนทาน

### การจำกัดอัตราอัตโนมัติไม่ทำงาน

- การจำกัดอัตราอัตโนมัติใช้ได้เฉพาะกับผู้ให้บริการที่ใช้ API key เท่านั้น (ไม่ใช้กับ OAuth/การสมัครสมาชิก)
- ตรวจสอบว่าได้เปิดใช้การจำกัดอัตราอัตโนมัติใน **Settings → Resilience → Provider Profiles**
- ตรวจสอบว่าผู้ให้บริการส่งคืนรหัสสถานะ `429` หรือส่วนหัว `Retry-After` หรือไม่

### การปรับแต่ง exponential backoff

โปรไฟล์ผู้ให้บริการรองรับการตั้งค่าต่อไปนี้:

- **Base delay** — ระยะเวลารอเริ่มต้นหลังจากล้มเหลวครั้งแรก (ค่าเริ่มต้น: 1s)
- **Max delay** — ขีดจำกัดระยะเวลารอสูงสุด (ค่าเริ่มต้น: 30s)
- **Multiplier** — อัตราการเพิ่มระยะเวลารอต่อความล้มเหลวที่เกิดขึ้นต่อเนื่องกัน (ค่าเริ่มต้น: 2x)

### การป้องกัน thundering herd

เมื่อคำขอพร้อมกันจำนวนมากเข้าถึงผู้ให้บริการที่ถูกจำกัดอัตรา OmniRoute จะใช้ mutex + การจำกัดอัตราอัตโนมัติเพื่อจัดลำดับคำขอและป้องกันความล้มเหลวที่ลุกลามเป็นทอดๆ การทำงานนี้เป็นอัตโนมัติสำหรับผู้ให้บริการที่ใช้ API key

### คำขอแชตล้มเหลวด้วย 503 / chat_admission_busy

**อาการ:**

- เอนด์พอยต์ chat completions ส่งคืนการตอบกลับ `503` ที่ลองใหม่ได้ โดยมีรหัสข้อผิดพลาดเป็น
  `chat_admission_busy`
- การตอบกลับมี `Retry-After` ตั้งแต่ #12135 เป็นต้นมา ค่านี้คำนวณจากการใช้งานที่ตรวจพบ
  โดยเลือกค่าที่มากกว่าระหว่างช่วงเวลา `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ที่คำขอได้รอไปแล้ว
  กับระยะเวลาที่ lease สำหรับงานหนักปัจจุบันถูกถือครองอยู่ จากนั้นปัดขึ้นเป็นจำนวนวินาทีเต็ม
  และจำกัดไว้สูงสุดที่ 60 สำหรับ gate ที่ไม่มีการใช้งาน ระบบจะยังคงใช้ค่าขั้นต่ำเดิม ได้แก่ 2 วินาทีสำหรับ
  เส้นทางที่อิงตามไบต์ และ 1 วินาทีสำหรับเส้นทางที่อิงตามโครงสร้าง (ซึ่งมี
  `reason: "structure_limit"` รวมอยู่ด้วย)
- เหตุการณ์นี้อาจเกิดขึ้นขณะที่แชตงานหนักอื่นหรือการตอบกลับแบบสตรีมที่ใช้เวลานานยังคง
  อยู่ระหว่างดำเนินการ

เนื้อหาการตอบกลับแบบอิงตามไบต์คือ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

การตอบกลับแบบอิงตามโครงสร้างใช้ชนิดและรหัสเดียวกัน โดยมีข้อความ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
และ `reason: "structure_limit"`
เมื่อใช้เกณฑ์เริ่มต้น คำขอจะถือว่ามีโครงสร้างขนาดใหญ่เมื่อมีข้อความอย่างน้อย `200` รายการ
มีเครื่องมืออย่างน้อย `64` รายการ หรือมีโทเค็นโดยประมาณอย่างน้อย `32,000` โทเค็น หรือเมื่อการประมาณโครงสร้างแบบมีขอบเขต
ใช้ขอบเขตจนหมดที่จำนวนโหนดที่เยี่ยมชม `10,000` โหนด หรือความลึก `12`

**สาเหตุ:** นี่คือการลดภาระโดยเจตนาภายใน OmniRoute ไม่ใช่ความล้มเหลวของผู้ให้บริการต้นทาง
แต่ละโปรเซสใช้ตัวป้องกันภายในโปรเซสเพื่อสำรองความจุที่จำกัดสำหรับงานหนัก ก่อนเก็บ
และแยกวิเคราะห์เนื้อหาคำขอขนาดใหญ่ lease สำหรับงานหนักจะยังคงถูกถือครองตลอดอายุของการตอบกลับ

**#503-fanout:** ก่อนการแก้ไขนี้ ตัวป้องกันจำกัดการทำงานพร้อมกันตามจำนวนคำขอคงที่
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ค่าเริ่มต้น `1`) โดยไม่คำนึงถึงหน่วยความจำของโฮสต์ ทำให้
fan-out ของ coding agent (subagent/CLI หลายตัว โดยทั่วไปมีเนื้อหาขนาด > 256 KB) ลดลงเหลือ
การทำงานพร้อมกันจริงประมาณ 1 รายการ และเกิด 503 ภายใต้โหลดปกติอย่างสมบูรณ์ ปัจจุบันตัวป้องกัน
ปรับแต่งตัวเองได้แล้ว โดยถูกควบคุมด้วยงบประมาณ BYTE สำหรับการรับข้อมูลที่คำนวณโดยอัตโนมัติ
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ซึ่งกำหนดขนาดจากขีดจำกัดหน่วยความจำจริงของโปรเซส
และยังตรวจสอบสัญญาณแรงกดดันต่อทรัพยากรแบบเรียลไทม์ด้วย ดังนั้นระบบจะลดภาระเฉพาะเมื่อโฮสต์
อยู่ภายใต้แรงกดดันด้านหน่วยความจำจริงๆ ไม่ใช่เพียงเพราะมีคำของานหนักมากกว่าหนึ่งรายการเข้ามาพร้อมกัน
ระบบยังคงเคารพขีดจำกัดจำนวนแบบเดิม (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) แต่เฉพาะเมื่อคุณ
ตั้งค่าไว้อย่างชัดเจนเท่านั้น

เมื่อความจุไม่ว่าง คำของานหนักจะรอสูงสุด
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ค่าเริ่มต้น `2000`; `0` ปิดใช้งานการรอ) เพื่อให้สล็อตว่าง
ก่อนตอบกลับด้วย `503` ที่ลองใหม่ได้ การรอแบบมีขอบเขตนี้มีไว้เพื่อให้ไคลเอนต์แบบ agent
(OpenCode, Claude Code, Cursor) ที่กระจายคำขอย่อยงานหนักออกไปพร้อมกัน สามารถจัดลำดับคำขอที่เข้ามาเป็นชุด
แทนที่จะใช้โควตาการลองใหม่ทั้งหมดไปกับการถูกปฏิเสธทันทีและหยุดทำงานกลางคัน
ข้อมูลการครอบครอง lease สำหรับงานหนักในปัจจุบัน งบประมาณไบต์ที่กำหนดแล้ว และระดับความรุนแรงของแรงกดดันแบบเรียลไทม์
จะแสดงที่ `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — ตรวจสอบข้อมูลเหล่านี้ก่อนแก้ไข env var ใดๆ
Settings → Resilience → Request Queue → Concurrent Requests ไม่ได้ควบคุมกลไกนี้ การตั้งค่านั้น
ควบคุมกลไกคิวคำขอของผู้ให้บริการซึ่งเป็นคนละส่วนกัน

**วิธีแก้ไข:**

1. ลองใหม่ก่อน ไคลเอนต์ควรเคารพ `Retry-After` และใช้ backoff แทนการส่งคำขอ
   ซ้ำทันที
2. ตรวจสอบ `/api/monitoring/health` → `chatAdmission` ก่อนปรับแต่งสิ่งใด `countCapEnabled:
false` และค่า `maxInflightBytes` ที่มากเพียงพอ หมายความว่างบประมาณที่คำนวณโดยอัตโนมัติกำลังทำงานตามที่ควร
   ส่วน `pressureSeverity` ที่มีค่าเป็น `high`/`critical` หมายความว่าโฮสต์มีหน่วยความจำเหลือน้อยจริงๆ —
   ปัญหานี้ไม่สามารถแก้ไขด้วย env var สำหรับการรับคำขอได้ แต่ต้องเพิ่ม RAM หรือลดขนาดเวิร์กโหลด
3. เฉพาะเมื่อ `/api/monitoring/health` แสดงว่างบประมาณที่คำนวณโดยอัตโนมัติมีขนาดเล็กเกินไปสำหรับ
   โฮสต์ของคุณจริงๆ เท่านั้น (ซึ่งเกิดขึ้นได้ยาก เพราะระบบปรับขนาดตั้งแต่คอนเทนเนอร์ไปจนถึง bare-metal อยู่แล้ว) ให้แทนที่ค่าโดยตรงด้วย
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` แทนการย้อนกลับไปใช้ขีดจำกัดจำนวนคำขอแบบเดิม

ดูการตั้งค่าการรับคำขอที่เป็นข้อมูลอ้างอิงอย่างเป็นทางการได้ที่ [เอกสารอ้างอิงตัวแปรสภาพแวดล้อม](../reference/ENVIRONMENT.md#4-security--authentication)

## อนุกรมวิธานความล้มเหลวของ RAG / LLM ที่ใช้เพิ่มเติมได้ (16 ปัญหา)

ผู้ใช้ OmniRoute บางรายวางเกตเวย์ไว้หน้า RAG หรือสแตกเอเจนต์ ในการตั้งค่าดังกล่าว มักพบรูปแบบที่แปลกประหลาด: OmniRoute ดูเหมือนทำงานเป็นปกติ (ผู้ให้บริการพร้อมใช้งาน โปรไฟล์การกำหนดเส้นทางถูกต้อง ไม่มีการแจ้งเตือนขีดจำกัดอัตรา) แต่คำตอบสุดท้ายยังคงผิดอยู่

ในทางปฏิบัติ เหตุการณ์เหล่านี้มักเกิดจากไปป์ไลน์ RAG ปลายทาง ไม่ใช่จากตัวเกตเวย์เอง

หากคุณต้องการคำศัพท์ร่วมกันเพื่ออธิบายความล้มเหลวเหล่านั้น คุณสามารถใช้ WFGY ProblemMap ซึ่งเป็นทรัพยากรข้อความภายนอกภายใต้สัญญาอนุญาต MIT ที่กำหนดรูปแบบความล้มเหลวของ RAG / LLM ที่เกิดซ้ำ 16 รูปแบบ โดยภาพรวมครอบคลุมเรื่องต่อไปนี้:

- การเบี่ยงเบนของการดึงข้อมูลและขอบเขตบริบทที่เสียหาย
- ดัชนีและที่เก็บเวกเตอร์ที่ว่างเปล่าหรือล้าสมัย
- ความไม่สอดคล้องกันระหว่าง embedding กับความหมาย
- ปัญหาการประกอบพรอมต์และหน้าต่างบริบท
- การล่มสลายของตรรกะและคำตอบที่มั่นใจเกินไป
- ความล้มเหลวของเชนที่ยาวและการประสานงานของเอเจนต์
- หน่วยความจำของหลายเอเจนต์และการเบี่ยงเบนของบทบาท
- ปัญหาลำดับการดีพลอยและการเริ่มต้นระบบ

แนวคิดนั้นเรียบง่าย:

1. เมื่อคุณตรวจสอบคำตอบที่ไม่ถูกต้อง ให้บันทึก:
   - งานและคำขอของผู้ใช้
   - เส้นทางหรือชุดผู้ให้บริการใน OmniRoute
   - บริบท RAG ใด ๆ ที่ใช้ในระบบปลายทาง (เอกสารที่ดึงมา การเรียกใช้เครื่องมือ ฯลฯ)
2. จับคู่เหตุการณ์กับหมายเลข WFGY ProblemMap หนึ่งหรือสองหมายเลข (`No.1` … `No.16`)
3. จัดเก็บหมายเลขไว้ในแดชบอร์ด คู่มือปฏิบัติงาน หรือตัวติดตามเหตุการณ์ของคุณเอง ถัดจากบันทึกของ OmniRoute
4. ใช้หน้า WFGY ที่เกี่ยวข้องเพื่อพิจารณาว่าคุณจำเป็นต้องเปลี่ยนสแตก RAG ตัวดึงข้อมูล หรือกลยุทธ์การกำหนดเส้นทางหรือไม่

ข้อความฉบับเต็มและสูตรการใช้งานที่เป็นรูปธรรมอยู่ที่นี่ (สัญญาอนุญาต MIT, ข้อความเท่านั้น):

[README ของ WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

คุณสามารถข้ามส่วนนี้ได้ หากคุณไม่ได้ใช้งานไปป์ไลน์ RAG หรือเอเจนต์เบื้องหลัง OmniRoute

## ปัญหาที่ทราบใน v3.8.0

ปัญหาเฉพาะของรุ่น v3.8.0 และวิธีแก้ปัญหาชั่วคราวในปัจจุบัน หากมีการแก้ไขในแพตช์ถัดไป รายการดังกล่าวจะได้รับการอัปเดตหรือลบออก

### การยืนยันตัวตนของ Devin CLI ล้มเหลว

**อาการ:**

- พบข้อความ "Devin CLI not found" หรือ "auth failed" เมื่อเรียกใช้เครื่องมือที่รองรับโดย Devin
- การตรวจสอบรันไทม์ของ CLI รายงาน `installed=false`

**สาเหตุ:**

- `CLI_DEVIN_BIN` ชี้ไปยังพาธที่ไม่มีอยู่
- ไม่ได้ติดตั้ง Devin CLI บนโฮสต์

**วิธีแก้ไข:**

1. ติดตั้ง Devin CLI สำหรับแพลตฟอร์มของคุณ
2. ตั้งค่า `CLI_DEVIN_BIN=/usr/local/bin/devin` (หรือพาธจริง) ใน `.env`
3. รีสตาร์ต OmniRoute และทดสอบอีกครั้งจาก **แดชบอร์ด → เครื่องมือ CLI**

### คูลดาวน์ของโมเดลค้างอยู่ (รีเซ็ตด้วยตนเอง)

**อาการ:**

- โมเดลยังคงแสดงอยู่ในสถานะคูลดาวน์ แม้เวลาหมดอายุจะผ่านไปแล้ว
- คำขอยังคงข้ามโมเดลในการกำหนดเส้นทางแบบชุด แม้การประทับเวลาจะอยู่ในอดีต

**การรีเซ็ตด้วยตนเอง:**

- **แดชบอร์ด:** **การตั้งค่า → คูลดาวน์ของโมเดล** → คลิก **เปิดใช้งานอีกครั้ง** บนการ์ดที่ได้รับผลกระทบ
- **API:** `DELETE /api/resilience/model-cooldowns` พร้อมส่วนหัวการยืนยันตัวตนสำหรับการจัดการ

### การเชื่อมต่อผู้ให้บริการ Command Code ล้มเหลวด้วย 403

**อาการ:**

- ได้รับ 403 เมื่อทดสอบการเชื่อมต่อผู้ให้บริการ Command Code
- การ์ดผู้ให้บริการแสดง "unauthorized" หลังจากเพิ่มใหม่

**สาเหตุ:** โฟลว์ OAuth ไม่เสร็จสมบูรณ์ (ไม่ได้รับ callback หรือไม่ได้จัดเก็บโทเค็น)

**วิธีแก้ไข:**

- เรียกใช้ `omniroute providers` จาก CLI เพื่อทริกเกอร์โฟลว์ OAuth อีกครั้ง หรือ
- เรียกใช้ OAuth อีกครั้งจาก **แดชบอร์ด → ผู้ให้บริการ → Command Code → เชื่อมต่ออีกครั้ง**

### ModelScope ส่งคืนคูลดาวน์ 429 ที่เข้มงวดเกินไป

**อาการ:**

- เกิดคูลดาวน์ที่สั้นมากหรือทันทีบน ModelScope หลังจากส่งคำขอเป็นชุดขนาดเล็ก
- การกำหนดเส้นทางแบบชุดข้าม ModelScope เร็วกว่าที่คาดไว้

**สาเหตุ:** ModelScope ส่งส่วนหัว `Retry-After` เฉพาะของผู้ให้บริการ v3.8.0 มาพร้อมการจัดการเฉพาะสำหรับส่วนหัวเหล่านั้น ดังนั้นเวอร์ชันเก่าจึงตีความส่วนหัวเหล่านั้นผิดว่าเป็นคำแนะนำทั่วไปเกี่ยวกับขีดจำกัดอัตรา

**วิธีแก้ไข:**

- ตรวจสอบให้แน่ใจว่าคุณใช้ v3.8.0 หรือใหม่กว่า
- ตรวจสอบว่าสวิตช์ `useUpstream429BreakerHints` เปิดใช้งานอยู่ภายใต้ **การตั้งค่า → ความยืดหยุ่น**

### ไม่มี OMNIROUTE_WS_BRIDGE_SECRET ในสภาพแวดล้อมการใช้งานจริง

**อาการ:**

- ได้รับ 401 ในทุกคำขอของบริดจ์ WebSocket สำหรับ Codex/Responses เมื่อทำงานบนโฮสต์การใช้งานจริงระยะไกล
- แฮนด์เชกของบริดจ์ WebSocket ปิดทันทีหลังจากเชื่อมต่อ

**สาเหตุ:** ไม่มีตัวแปรสภาพแวดล้อม `OMNIROUTE_WS_BRIDGE_SECRET` ในสภาพแวดล้อมการใช้งานจริง

**วิธีแก้ไข:**

1. สร้างค่าลับแบบสุ่ม: `openssl rand -hex 32`
2. ตั้งค่า `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ในสภาพแวดล้อมของเซิร์ฟเวอร์การใช้งานจริง (และไคลเอนต์ใด ๆ ที่สื่อสารกับบริดจ์)
3. รีสตาร์ต OmniRoute

### Responses API: โหมดเบื้องหลังถูกลดระดับเป็นแบบซิงโครนัส

**อาการ:**

- มีการบันทึกคำเตือน: `background mode degraded to synchronous`
- คำขอ `background: true` ส่งคืนการตอบกลับแบบซิงโครนัสปกติ แทนที่จะเป็นตัวจัดการงานเบื้องหลัง

**สาเหตุ:** v3.8.0 ตั้งใจลดระดับ `background: true` บน Responses API ให้เป็นการดำเนินการแบบซิงโครนัส พร้อมส่งคำเตือน การดำเนินการเบื้องหลังแบบอะซิงโครนัสเต็มรูปแบบเป็นฟีเจอร์ที่จะส่งมอบในอนาคต

**วิธีแก้ไข:**

- ปรับไคลเอนต์ให้เรียกใช้โดยไม่มี `background` หรือ
- รอรุ่นในภายหลังที่มาพร้อมโหมดเบื้องหลังแบบอะซิงโครนัสเต็มรูปแบบ (ติดตามบันทึกการเปลี่ยนแปลง)

## การเริ่มต้นช้า / หมดเวลารอความพร้อม

หาก CLI แสดงข้อความ `⚠ Server did not respond within 60s` แต่เซิร์ฟเวอร์
ทำงานได้ตามปกติ แสดงว่าระยะเวลาที่กำหนดให้โพรบตรวจสอบความพร้อมสั้นเกินไปสำหรับสภาพแวดล้อมของคุณ

ปัญหานี้มักเกิดขึ้นบน Windows (โปรแกรมป้องกันไวรัส ตัวเฝ้าดูระบบไฟล์) หรือคอนเทนเนอร์
ที่มีภาระงานหนักในระหว่างการเริ่มต้น

**วิธีแก้ไข — เพิ่มระยะเวลารอ:**

```bash
# ผ่านตัวแปรสภาพแวดล้อม (มีผลต่อเนื่องในการเริ่มต้นครั้งถัดไป):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 นาที
omniroute serve

# ผ่านแฟล็ก CLI (ใช้ครั้งเดียว):
omniroute serve --ready-timeout 180000
```

ค่าเริ่มต้นคือ 60 000 ms (60 s) คำเตือนนี้มีไว้เพื่อแจ้งข้อมูลเท่านั้น เซิร์ฟเวอร์
จะเริ่มต้นต่อไปในเบื้องหลังและจะสามารถเข้าถึงได้เมื่อกระบวนการบูตเสร็จสมบูรณ์

ดูรายละเอียดทั้งหมดเกี่ยวกับ `OMNIROUTE_READY_TIMEOUT_MS` ได้ที่
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)

- **เอกสารอ้างอิง API**: ดูปลายทางทั้งหมดได้ที่ [`docs/reference/API_REFERENCE.md`](../reference/API_REFERENCE.md)
