## ข้อมูลอ้างอิงฉบับย่อ

**เพิ่งเริ่มใช้ OmniRoute ใช่ไหม?** เริ่มที่นี่ — วิธีเหล่านี้แก้ปัญหาได้ 90%:

| สิ่งที่พบ                    | ความหมาย                              | สิ่งที่ควรทำ                                                                                                    |
| ---------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| "เชื่อมต่อไม่ได้"            | OmniRoute ไม่ได้ทำงานอยู่             | เรียกใช้ `omniroute` หรือ `docker restart omniroute`                                                            |
| "คีย์ API ไม่ถูกต้อง"        | คีย์ของคุณไม่ถูกต้องหรือหมดอายุ       | คัดลอกคีย์อีกครั้งจากเว็บไซต์ของผู้ให้บริการ                                                                    |
| "เกินขีดจำกัดอัตราการใช้งาน" | คุณกำลังส่งคำขอมากเกินไป              | รอ 1 นาที หรือใช้ `model: "auto"` เพื่อให้สลับไปใช้ตัวเลือกสำรองโดยอัตโนมัติ                                    |
| "เกินโควตา"                  | คุณใช้โควตาแบบฟรี/แบบชำระเงินหมดแล้ว  | เชื่อมต่อผู้ให้บริการเพิ่มเติม หรือใช้ผู้ให้บริการฟรี (Kiro, Pollinations)                                      |
| "การตอบสนองช้า"              | ผู้ให้บริการไม่ว่างหรืออยู่ไกล        | ใช้ `model: "auto/fast"` หรือเชื่อมต่อผู้ให้บริการที่เร็วกว่า (Groq, Cerebras)                                  |
| "ใช้ผู้ให้บริการผิดราย"      | `auto` เลือกผู้ให้บริการรายอื่น       | นี่เป็นเรื่องปกติ! `auto` จะเลือกตัวเลือกที่ดีที่สุด บังคับใช้ผู้ให้บริการเฉพาะรายด้วย `model: "openai/gpt-4o"` |
| "502 เกตเวย์ไม่ถูกต้อง"      | ผู้ให้บริการล่ม                       | รอแล้วลองใหม่ หรือใช้ `model: "auto"` เพื่อสลับผู้ให้บริการ                                                     |
| "401 ไม่ได้รับอนุญาต"        | ข้อมูลประจำตัวของคุณไม่ถูกต้อง        | ตรวจสอบคีย์ API หรือยืนยันตัวตนใหม่ด้วย OAuth                                                                   |
| "ไม่รู้จักคำสั่ง omniroute"  | Windows PATH ไม่มีโมดูล node ส่วนกลาง | เพิ่มคำนำหน้าส่วนกลางของ npm ลงใน Windows PATH ค้นหาได้ด้วย `npm config get prefix`                             |
| "429 คำขอมากเกินไป"          | ถูกจำกัดอัตราการใช้งาน                | รอ 1 นาที หรือเชื่อมต่อผู้ให้บริการเพิ่มเติม                                                                    |

### การจำกัดอัตราการใช้งานของผู้ให้บริการฟรี (429 / 400 / 401)

**อาการ**: เมื่อใช้ `model: "auto"` กับผู้ให้บริการแบบฟรี/ไม่ต้องยืนยันตัวตน (opencode, auggie ฯลฯ) คุณจะได้รับ `HTTP 429`, `400` หรือ `401` เป็นระยะ แทนที่จะได้รับคำตอบ คำขอจะสำเร็จเมื่อลองส่งพรอมต์เดิมอีกครั้งในอีกไม่กี่อึดใจ แต่ระบบอัตโนมัติ (งาน cron, เอเจนต์, สคริปต์) จะหยุดทำงานตั้งแต่เกิดข้อผิดพลาดครั้งแรก

**สาเหตุหลัก**: โหมดความล้มเหลวที่เป็นอิสระต่อกันสามรูปแบบเกิดซ้อนกัน:

1. **ขีดจำกัดอัตราของผู้ให้บริการ (`429`)**: แพ็กเกจฟรีอาจบังคับใช้โควตาต่อช่วงเวลา การเรียกใช้พร้อมกันจำนวนมากจะทำให้โควตาหมด ดังนั้นคำขอถัดไปจึงถูกปฏิเสธจนกว่าช่วงเวลาจะรีเซ็ต
2. **โมเดลเสียในโหมดส่งผ่าน (`400`/`401`)**: พูล `auto/*` อาจมีโมเดลแบบส่งผ่านจาก `opencode` ซึ่งลงทะเบียนไว้ในแค็ตตาล็อก แต่ไม่มีข้อมูลประจำตัวที่ใช้งานได้ (เช่น `oc/north-mini-code-free` → `401`) ตัวกำหนดเส้นทางอัตโนมัติจะลองใช้โมเดลหนึ่ง ล้มเหลว แล้วส่งต่อข้อผิดพลาดออกไปก่อนที่การสลับไปใช้ตัวเลือกสำรองจะเริ่มทำงาน
3. **การขยายผลจากการทำงานพร้อมกัน (`429` ภายใต้โหลด)**: เมื่อเซสชันของเอเจนต์/cron หลายเซสชันเรียกใช้ `auto` พร้อมกัน อัตราคำขอโดยรวมจะสูงเกินกว่าที่ผู้ให้บริการฟรีจะรองรับได้ ส่งผลให้การเรียกใช้ที่ถูกต้องถูกระบุว่าเป็นการใช้งานในทางที่ผิด

**วิธีแก้ไขที่ผ่านการตรวจสอบแล้ว (รายงานโดยชุมชน, 2026-08-10)**: ปรับตัวแปรสภาพแวดล้อมสามตัวเพื่อให้การหมุนเวียน การทำงานพร้อมกัน และการสลับไปใช้ตัวเลือกสำรองรองรับความผันผวนของแพ็กเกจฟรีแทนที่จะล้มเหลว:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # สลับไปยังโมเดล/ผู้ให้บริการอื่นเมื่อพบ 400/401 (ข้ามโมเดลแบบส่งผ่านที่เสีย)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # เพดานการรับคำขอแบบหนักที่ระบุไว้อย่างชัดเจน (โดยค่าเริ่มต้นจะไม่ตั้งค่า: ไม่มีขีดจำกัดจำนวนคำขอ ดูหมายเหตุด้านล่าง)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # รอความจุสำหรับคำขอแบบหนักภายในขอบเขตที่นานขึ้น แทนที่จะส่ง 503 ที่ลองใหม่ได้ทันที
```

ตั้งค่าเหล่านี้ในสภาพแวดล้อมของโปรเซส OmniRoute (ดีมอน เช่น ผ่าน plist ของ LaunchAgent หรือ `systemctl edit`) แล้วรีสตาร์ต OmniRoute แฟล็กการหมุนเวียนเป็นกลไกเดียวที่ให้ผลลัพธ์สูงสุด เพราะจะเปลี่ยนความล้มเหลวถาวรให้เป็นการลองใหม่อย่างโปร่งใสกับผู้ให้บริการที่พร้อมใช้งานในพูล

**หมายเหตุ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` จำกัดจำนวนคำขอแบบหนัก — คำขอที่มีบริบทยาว — ที่ทำงานพร้อมกัน ขอบเขตนี้เป็นเกตควบคุมการรับคำขอ ไม่ใช่ตัวจำกัดอัตราของผู้ให้บริการ **ข้อมูลอัปเดต #503-fanout:** ตัวแปรนี้จะไม่ถูกตั้งค่าโดยค่าเริ่มต้นอีกต่อไป (ขณะนี้จะมีผลเฉพาะเมื่อกำหนดค่าไว้อย่างชัดเจนดังข้างต้น) — แต่การรับคำขอแบบหนักจะถูกควบคุมด้วยงบประมาณไบต์ที่คำนวณโดยอัตโนมัติ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ซึ่งปรับขนาดตัวเองตามขีดจำกัดหน่วยความจำจริงของโฮสต์ ดังนั้นการติดตั้งใหม่ควรพบการปฏิเสธ `503 chat_admission_busy` น้อยลงอย่างมากโดยไม่ต้องตั้งค่าตัวแปรนี้เลย ทั้งนี้ การตั้งค่าอย่างชัดเจนตามที่แสดงไว้ที่นี่ยังคงทำงานตรงตามเอกสารทุกประการ การกำหนดค่างบประมาณไบต์ทับอย่างชัดเจนจะถูกจำกัดให้อยู่ระหว่าง 8 MiB–2 GiB ข้อผิดพลาด `413 body_exceeds_budget` ไม่ใช่เหตุการณ์ชั่วคราว: ให้เพิ่มงบประมาณไบต์ดังกล่าว ลด `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` หรือเพิ่มขีดจำกัดหน่วยความจำของโปรเซส การลดโหลดแบบ `inflight_bytes_budget` เป็นภาวะช่วงชิงทรัพยากรชั่วคราวและยังสามารถลองใหม่ได้ การจำกัดอัตราแยกตามผู้ให้บริการ (`open-sse/services/rateLimitManager.ts`) ถูกควบคุมแยกต่างหากด้วย `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` และ `RATE_LIMIT_AUTO_ENABLE` — ดู `.env.example`

**วิธีตรวจสอบว่าทำงานแล้ว**: เรียกใช้ agent/cron ของคุณสองครั้งติดกันอย่างรวดเร็วและยืนยันว่าทั้งสองครั้งสำเร็จ ก่อนแก้ไข การเรียกใช้ครั้งที่สองมักแสดงข้อผิดพลาด `429`/`401` หลังแก้ไขแล้ว ระบบจะลองใหม่โดยอัตโนมัติเมื่อเกิดความล้มเหลว (หากมี) และดำเนินการเรียกจนเสร็จสมบูรณ์ นอกจากนี้ คุณยังสามารถใช้ `curl /monitoring/health` แล้วตรวจดูฟิลด์ `rateLimitedUntil` ในการเชื่อมต่อของผู้ให้บริการ รวมถึง `circuitBreakers.providerBreakers[].state` สำหรับผู้ให้บริการที่ได้รับผลกระทบ โดยสถานะจะเป็นค่าใดค่าหนึ่งระหว่าง `CLOSED`, `DEGRADED`, `OPEN` หรือ `HALF_OPEN` (ดู `src/shared/utils/circuitBreaker.ts`) และผู้ให้บริการที่ล้มเหลวอย่างต่อเนื่องจะเปลี่ยนสถานะจาก `CLOSED → DEGRADED → OPEN` ก่อนที่ช่วงเวลาการรีเซ็ตจะอนุญาตให้ส่งคำขอทดสอบผ่านได้ (`HALF_OPEN`)

**หากคุณยังคงพบ 429**: บัญชีที่ใช้งานอยู่สำหรับผู้ให้บริการรายนั้นใช้ _โควตา_ หมดแล้วจริง ๆ (ไม่ใช่เพียงติดข้อจำกัดด้านอัตราการเรียกใช้) ให้เพิ่มบัญชีที่สองสำหรับผู้ให้บริการรายเดียวกันในแดชบอร์ด OmniRoute → Providers → Accounts หรือใช้ผู้ให้บริการฟรีรายอื่นร่วมด้วย (เช่น `routeway`, `auggie`) การหมุนเวียนบัญชีช่วยได้เฉพาะข้อผิดพลาดชั่วคราวเกี่ยวกับอัตราการเรียกใช้/400/401 เท่านั้น หากโควตาหมดโดยสมบูรณ์ จะต้องใช้ข้อมูลประจำตัวชุดที่สองหรือผู้ให้บริการรายอื่น

**หากคุณพบ 403 ในโมเดลภาพ (`auto/vision`, `bazaarlink/*`)**: บัญชีที่เชื่อมต่อไม่มีแพ็กเกจแบบชำระเงินที่รองรับการประมวลผลภาพ หรือ API key มีสิทธิ์ไม่เพียงพอ ตรวจสอบในแดชบอร์ดของผู้ให้บริการว่าขอบเขตสิทธิ์ของคีย์ครอบคลุมการประมวลผลภาพ/มัลติโหมด หรือเชื่อมต่อบัญชีระดับชำระเงินและกำหนดให้เป็นเป้าหมายสำหรับการประมวลผลภาพ

## คำเตือนจาก npm install (ERESOLVE / peer / deprecated)

เมื่อคุณเรียกใช้ `npm install -g omniroute` คุณอาจเห็นคำเตือนจำนวนมาก เช่น `npm warn ERESOLVE` ข้อความแจ้งเตือนเกี่ยวกับ peer dependency และข้อความ `deprecated` **คำเตือนเหล่านี้เป็นสิ่งที่คาดไว้และไม่เป็นอันตราย** การติดตั้งของคุณสำเร็จแล้วหากเห็น `added <N> packages` ในผลลัพธ์

หากต้องการระงับคำเตือนเกี่ยวกับการแก้ไข peer dependency ให้ใช้รูปแบบการติดตั้งที่ OmniRoute รองรับ:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` จะระงับเฉพาะข้อความแจ้งเตือน `ERESOLVE` และ peer dependency เท่านั้น ข้อความแจ้งเตือนการเลิกใช้งานจะยังคงปรากฏ เนื่องจากมาจากแพ็กเกจภายนอกแบบ transitive ซึ่งไม่ได้หมายความว่าการติดตั้งล้มเหลว

คำเตือนเหล่านี้มาจากช่วงเวอร์ชัน peer dependency ที่ล้าสมัยในแพ็กเกจภายนอกซึ่ง OmniRoute ไม่ได้ควบคุม:

1. **`marked-terminal` ต้องการ `marked >=1 <16` แต่พบ `marked@18`** — ในทางปฏิบัติยังทำงานได้ตามปกติ เพียงแต่ช่วงเวอร์ชัน peer ของ upstream ล้าสมัย
2. **`deprecated prebuild-install@7.1.3`** — ตัวช่วยดาวน์โหลดไบนารีแบบเนทีฟที่เป็น dependency แบบ transitive แพ็กเกจนี้ไม่ได้
   ใช้เพื่อติดตั้ง transport binding ของ `wreq-js` ที่ตรึงเวอร์ชันไว้ และไม่ได้หมายความว่าการตั้งค่า transport
   ของผู้ให้บริการ web-cookie ล้มเหลว

**ไม่จำเป็นต้องดำเนินการใดๆ** — ไม่สามารถปิดคำเตือนเหล่านี้ได้ทั้งหมดโดยไม่ fork แพ็กเกจ upstream

## Gemini Web และ Playwright Chromium

หากคำขอ Gemini Web ส่งคืน `503` พร้อมข้อความว่าไม่ได้ติดตั้ง Playwright Chromium
แสดงว่ามีแพ็กเกจ npm อยู่แล้ว แต่ไม่มีไบนารีของเบราว์เซอร์
Playwright แยกการดาวน์โหลดเบราว์เซอร์ออกจากการติดตั้งแพ็กเกจ npm โดยตั้งใจ
ดังนั้นการตอบกลับนี้จึงเป็นสิ่งที่คาดไว้จนกว่าจะติดตั้งเบราว์เซอร์

สำหรับการติดตั้ง npm แบบ global ให้ติดตั้ง Chromium จากไดเรกทอรีของแพ็กเกจ
OmniRoute เพื่อให้แคชของเบราว์เซอร์อยู่ในการติดตั้ง Playwright เดียวกัน:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

รีสตาร์ต OmniRoute หลังจากติดตั้ง แล้วลองส่งคำขอ Gemini Web อีกครั้ง หากคุณ
เรียกใช้ OmniRoute จากอิมเมจ Docker ให้ใช้อิมเมจ `-web` (หรือเป้าหมายการบิลด์ `runner-web`)
ซึ่งรวม Chromium และ dependency ที่เกี่ยวข้องไว้แล้ว ส่วนอิมเมจพื้นฐาน
ไม่มีองค์ประกอบเหล่านี้

## ผลบวกลวงจากโปรแกรมป้องกันไวรัส

<a name="antivirus-false-positives"></a>

### Avast/AVG กักกัน `README.md` ด้วยการตรวจพบ `MD:HttpRequest-inf[Susp]`

**นี่เป็นผลบวกลวง ไม่มีไฟล์ใดติดไวรัสและไม่จำเป็นต้องดำเนินการใดๆ**

Avast และ AVG ใช้ฮิวริสติกที่ระบุว่าไฟล์ข้อความธรรมดา/Markdown ซึ่งมีลิงก์ที่ดูคล้ายคำขอ HTTP จำนวนมากเป็นภัยคุกคาม `README.md` ของ OmniRoute รวมอยู่ภายในแพ็กเกจ npm (ไฟล์นี้อยู่ในรายการ `package.json` → `files`) ดังนั้นเมื่อติดตั้งแบบส่วนกลาง ไฟล์จะอยู่ที่ `node_modules/omniroute/README.md` และมีตัวอย่าง `http://localhost:20128/...` ประมาณ 15 รายการ (ปลายทาง HTTP/SSE ของ MCP, URL `.well-known` ของ A2A และส่วนย่อยคำสั่ง `curl`) ความหนาแน่นของลิงก์ดังกล่าวมากพอที่จะทำให้ฮิวริสติกแจ้งเตือน

หากปัญหานี้เพิ่งเริ่มเกิดขึ้นเมื่อไม่นานมานี้ ลักษณะของไฟล์ไม่ได้เปลี่ยนไป แต่ README มีตารางปลายทางเพิ่มขึ้น (มีการเพิ่ม MCP HTTP + SSE + A2A) และมีตัวอย่าง `curl` มากขึ้น ทำให้จำนวนรายการเกินเกณฑ์

ไฟล์นี้เป็นเพียงเอกสารที่ไม่สามารถทำงานได้และไม่มีเนื้อหาที่เรียกใช้ได้เลย คุณสามารถกู้คืนไฟล์นี้จากพื้นที่กักกันได้อย่างปลอดภัย

**สิ่งที่ควรทำ:**

1. **หยุดการแจ้งเตือน** — เพิ่มไดเรกทอรีติดตั้งลงในรายการยกเว้นของโปรแกรมป้องกันไวรัส
   (Avast: Settings → Exceptions) โดยเพิ่มพาธ `node_modules` ส่วนกลาง และ/หรือไดเรกทอรีข้อมูลของ
   OmniRoute (`~/.omniroute/`)
2. **รายงานผลบวกลวง** — <https://www.avast.com/false-positive-file-form.php>
   พร้อมแนบ `README.md` ที่ถูกกักกัน วิธีนี้เป็นการแก้ไขที่ช่วยทุกคน เนื่องจากต้นเหตุคือฮิวริสติกของผู้ให้บริการตอบสนองเกินควรต่อไฟล์ข้อความ

**เหตุผลที่เราไม่ "แก้ไข" ปัญหานี้จากฝั่งของเรา:** ตัวอย่างทั้งหมดใช้ `http://localhost` และ
localhost ไม่สามารถใช้ `https` ได้โดยปราศจากความยุ่งยากจากใบรับรองแบบลงนามด้วยตนเอง การบิดเบือนเอกสารเพื่อหลบเลี่ยงฮิวริสติกของผู้ให้บริการรายเดียวจะทำให้ผู้อ่านทุกคนได้รับผลกระทบ เพียงเพื่อรองรับข้อบกพร่องของสแกนเนอร์

### Kaspersky ระบุว่าแอป Desktop เป็น `PDM:Trojan.Win32.Generic`

ไฟล์ที่ถูกระบุเป็นส่วนประกอบมาตรฐานของดีเพนเดนซีโอเพนซอร์สที่ประกาศไว้อย่างชัดเจนและรวมมากับแอปเดสก์ท็อป ตัวอย่างเช่น:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` และ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev) ซึ่งเป็นไลบรารีระบบอัตโนมัติสำหรับเบราว์เซอร์ที่ใช้ในการเข้าสู่ระบบผู้ให้บริการภายในแอปและการแชตที่ทำงานผ่านเบราว์เซอร์
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ไบนดิงแบบเนทีฟ `wreq-js` เวอร์ชันที่ตรึงไว้ ซึ่งใช้สำหรับ HTTP ที่เลียนแบบลายนิ้วมือของเบราว์เซอร์กับผู้ให้บริการที่ใช้เว็บคุกกี้ (`<arch>` คือ `x64` หรือ `arm64`)

**เหตุผลที่เกิดการแจ้งเตือน:** ตัวติดตั้ง Windows **ยังไม่ได้ลงนามโค้ด** ดังนั้นตัวติดตั้ง NSIS ที่ไม่ได้ลงนามจึงไม่มีชื่อเสียงความน่าเชื่อถือ และฮิวริสติกเชิงพฤติกรรมจะทำงานในระดับเข้มงวดสูงสุด เมื่อรวมกับ DLL แบบเนทีฟที่จัดมาให้และไฟล์ `.js` หลายร้อยไฟล์ที่เขียนไว้ใต้
`%LOCALAPPDATA%\Programs\OmniRoute` (รวมถึงไดเรกทอรีแพ็กเกจที่มีแฮชต่อท้ายจากบิลด์แบบสแตนด์อโลนของ Next.js) ก็เพียงพอที่จะทำให้ฮิวริสติกแจ้งเตือน มีแผนที่จะลงนามโค้ด แต่จนกว่าจะดำเนินการเสร็จ รุ่นใหม่ๆ อาจเกิดปัญหานี้ซ้ำได้

**สิ่งที่ควรทำ:**

1. **ตรวจสอบไฟล์ที่ดาวน์โหลดก่อน** (เพื่อยืนยันว่าไฟล์ไม่ได้ถูกดัดแปลง) ทุกรุ่นจะเผยแพร่
   `latest.yml` ซึ่งฟิลด์ `sha512` (base64) ครอบคลุมตัวติดตั้ง `OmniRoute.Setup.<version>.exe`
   ใน PowerShell ให้เรียกใช้คำสั่งต่อไปนี้จากโฟลเดอร์ที่มีตัวติดตั้ง:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ผลลัพธ์ต้องตรงกับ `latest.yml` → `sha512` หากไม่ตรงกัน ให้ลบไฟล์และดาวน์โหลดใหม่จาก[หน้าเผยแพร่ของ GitHub](https://github.com/diegosouzapw/OmniRoute/releases)เท่านั้น
2. **กู้คืน + เพิ่มข้อยกเว้น** — กู้คืนรายการที่ถูกย้อนกลับจากพื้นที่กักกัน และเพิ่มข้อยกเว้นสำหรับ
   `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions)
   จากนั้นติดตั้งใหม่
3. **รายงานผลบวกลวง** — <https://opentip.kaspersky.com/> รายงานผลบวกลวงที่ผู้ใช้ส่งเข้ามาช่วยเร่งกระบวนการเพิ่มลงในรายการอนุญาตได้จริง

## ความเข้ากันได้กับ Node.js

<a name="nodejs-compatibility"></a>

### หน้าเข้าสู่ระบบขัดข้องหรือแสดงข้อผิดพลาด "Module self-registration"

**สาเหตุ:** คุณกำลังใช้งาน Node.js เวอร์ชันที่อยู่นอกเกณฑ์ขั้นต่ำของรันไทม์ที่ปลอดภัยซึ่ง OmniRoute อนุมัติ กรณีที่พบบ่อยที่สุดคือการใช้ Node 22 หรือ 24 ที่มีระดับแพตช์เก่ากว่าเกณฑ์ขั้นต่ำด้านความปลอดภัยที่ OmniRoute กำหนด

**อาการ:**

- หน้าเข้าสู่ระบบแสดงหน้าจอว่างหรือข้อผิดพลาดของเซิร์ฟเวอร์
- คอนโซลแสดง `Error: Module did not self-register` หรือข้อผิดพลาดเกี่ยวกับ native binding ที่คล้ายกัน
- หน้าเข้าสู่ระบบแสดง **แบนเนอร์คำเตือนสีส้ม** พร้อมเวอร์ชัน Node ของคุณ หากรันไทม์อยู่นอกนโยบายความปลอดภัยที่รองรับ

**วิธีแก้ไข:**

1. ติดตั้ง Node.js รุ่น LTS ที่รองรับ (แนะนำ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ตรวจสอบเวอร์ชันของคุณ: `node --version` ควรแสดง `v24.0.0` หรือใหม่กว่าในสาย LTS 24.x
3. ติดตั้ง OmniRoute ใหม่: `npm install -g omniroute`
4. เริ่มต้นใหม่: `omniroute`

> **เวอร์ชันที่ปลอดภัยและรองรับ:** `>=22.22.2 <23` หรือ `>=24.0.0 <27` โดยรองรับ Node.js 24.x LTS (Krypton) และ Node.js 26 อย่างเต็มรูปแบบ

### npm v11+: ไม่ได้ติดตั้ง `better-sqlite3` (ไม่พบโมดูล)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**สาเหตุ:** โดยค่าเริ่มต้น npm v11 (ที่มาพร้อมกับ Node.js 24+) จะบล็อกสคริปต์การติดตั้งสำหรับ
การขึ้นต่อกันแบบไม่บังคับ เนื่องจาก `better-sqlite3` อยู่ในรายการ `optionalDependencies`
และต้องมีการคอมไพล์แบบเนทีฟ (`node-gyp rebuild`) npm จึงข้ามแพ็กเกจนี้ไปโดยไม่แจ้งเตือน

**อาการ:**

- เซิร์ฟเวอร์ขัดข้องระหว่างเริ่มต้นทำงานพร้อมข้อความ `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` แสดงข้อความ "ไม่มีไฟล์หรือไดเรกทอรีดังกล่าว"
- `npm ls better-sqlite3` แสดง `(empty)`

**วิธีแก้ไข:**

1. อนุมัติสคริปต์การติดตั้งแล้วติดตั้งใหม่:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. หรือติดตั้งไบนารีที่สร้างไว้ล่วงหน้าด้วยตนเอง:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ตรวจสอบว่าสามารถใช้งานได้: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**สาเหตุ:** หลังจากเรียกใช้ `npm install -g omniroute` แบบโกลบอล ไบนารีแบบเนทีฟของ `better-sqlite3` ภายในแพ็กเกจอาจถูกคอมไพล์มาสำหรับสถาปัตยกรรมหรือ ABI ของ Node.js ที่แตกต่างจากสภาพแวดล้อมที่กำลังทำงานอยู่ในเครื่อง ปัญหานี้พบได้บ่อยบน macOS (ทั้ง Apple Silicon และ Intel) เมื่อไบนารีที่สร้างไว้ล่วงหน้าไม่ตรงกับสภาพแวดล้อมของคุณ

**อาการ:**

- เซิร์ฟเวอร์ล้มเหลวทันทีระหว่างเริ่มต้นทำงานพร้อมข้อผิดพลาด `dlopen`
- ข้อผิดพลาดมีข้อความ `slice is not valid mach-o file`
- ตัวอย่างแบบเต็ม:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**วิธีแก้ไข — สร้างใหม่สำหรับสภาพแวดล้อมภายในเครื่องของคุณ (ไม่จำเป็นต้องดาวน์เกรด Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **หมายเหตุ:** ขั้นตอนนี้จะคอมไพล์ native binding ใหม่ให้ตรงกับเวอร์ชัน Node.js และสถาปัตยกรรม CPU ภายในเครื่องของคุณ ซึ่งช่วยแก้ไขปัญหาไบนารีไม่ตรงกัน ช่วงรันไทม์ที่รองรับอย่างเป็นทางการคือ **`>=22.22.2 <23` หรือ `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` ใน `src/shared/utils/nodeRuntimeSupport.ts` ซึ่งสอดคล้องกับฟิลด์ `engines` ใน `package.json`) โดยรองรับ Node.js 24.x LTS (Krypton) และ Node.js 26 พร้อม `better-sqlite3` v12.x อย่างเต็มรูปแบบ

## ปัญหาเกี่ยวกับพร็อกซี

<a name="proxy-issues"></a>

### การตรวจสอบผู้ให้บริการแสดงข้อผิดพลาด "fetch failed"

**สาเหตุ:** ก่อนหน้านี้ endpoint สำหรับตรวจสอบ API key (`POST /api/providers/validate`) ไม่ได้ใช้การกำหนดค่าพร็อกซี ส่งผลให้เกิดข้อผิดพลาดในสภาพแวดล้อมที่จำเป็นต้องกำหนดเส้นทางผ่านพร็อกซี

**วิธีแก้ไข (v3.5.5+):** ปัญหานี้ได้รับการแก้ไขแล้ว ขณะนี้การตรวจสอบผู้ให้บริการจะกำหนดเส้นทางผ่าน `runWithProxyContext` และใช้การตั้งค่าพร็อกซีระดับผู้ให้บริการและระดับส่วนกลางโดยอัตโนมัติ

### การตรวจสอบสถานะโทเค็นล้มเหลวด้วยข้อผิดพลาด "fetch failed"

**สาเหตุ:** การรีเฟรช OAuth token ในเบื้องหลังไม่ได้ตรวจหาการกำหนดค่าพร็อกซีแยกตามแต่ละการเชื่อมต่อ

**วิธีแก้ไข (v3.5.5+):** ขณะนี้ตัวกำหนดเวลาการตรวจสอบสถานะโทเค็นจะตรวจหาการกำหนดค่าพร็อกซีแยกตามแต่ละการเชื่อมต่อก่อนพยายามรีเฟรช โปรดอัปเดตเป็น v3.5.5+

### พร็อกซี SOCKS5 ส่งคืนข้อผิดพลาด "invalid onRequestStart method"

**สาเหตุ:** บน Node.js 22 ตัว dispatcher ของ undici@8 ไม่สามารถทำงานร่วมกับ `fetch()` ที่มีมาให้ใน Node ได้

**วิธีแก้ไข (v3.5.5+):** ขณะนี้ OmniRoute ใช้ฟังก์ชัน `fetch()` ของ undici เองเมื่อมีการใช้งาน proxy dispatcher เพื่อให้แน่ใจว่าการทำงานมีความสอดคล้องกัน โปรดอัปเดตเป็น v3.5.5+

### พร็อกซี MITM ภายใต้ WSL: ไม่สามารถดักจับแอปเดสก์ท็อปบนโฮสต์ Windows ได้

**สาเหตุ:** พร็อกซี MITM และ CA certificate ของพร็อกซีจะติดตั้งลงในสภาพแวดล้อมที่ OmniRoute ทำงานอยู่ ภายใต้ WSL สภาพแวดล้อมดังกล่าวคือ guest Linux ในขณะที่แอปเดสก์ท็อป AI (Kiro, Trae, Copilot, Zed, …) ทำงานอยู่บนโฮสต์ Windows แอปบนโฮสต์ไม่เชื่อถือ certificate store ของ guest และไม่ได้กำหนดเส้นทางผ่านพร็อกซีระบบของ guest ดังนั้นการดักจับทราฟฟิกของเดสก์ท็อปจึงไม่ทำงานในกรณีนี้

**คำแนะนำ:** เรียกใช้ OmniRoute แบบเนทีฟบน OS เดียวกับแอปเดสก์ท็อปที่คุณต้องการดักจับ (Windows สำหรับแอป Windows และเช่นเดียวกันสำหรับ macOS/Linux) หากยังคงเรียกใช้ OmniRoute ภายใน WSL ขณะที่กำหนดเป้าหมายเป็นแอปบนโฮสต์ คุณต้องกำหนดให้โฮสต์ Windows เชื่อถือ CA certificate ที่สร้างขึ้นด้วยตนเอง และตั้งค่าเครือข่าย/พร็อกซีของแต่ละแอปบนโฮสต์ให้ชี้ไปยัง endpoint ของพร็อกซี WSL ซึ่งเป็นการตั้งค่าที่ไม่รองรับและเปราะบาง

## ปัญหาเกี่ยวกับผู้ให้บริการ

### "Language model did not provide messages"

**สาเหตุ:** โควตาของผู้ให้บริการหมดแล้ว

**วิธีแก้ไข:**

1. ตรวจสอบตัวติดตามโควตาในแดชบอร์ด
2. ใช้ชุดโมเดลที่มีระดับสำรอง
3. เปลี่ยนไปใช้ระดับที่ถูกกว่า/ฟรี

### การจำกัดอัตรา

**สาเหตุ:** โควตาการสมัครใช้งานหมดแล้ว

**วิธีแก้ไข:**

- เพิ่มตัวเลือกสำรอง: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- ใช้ GLM/MiniMax เป็นตัวเลือกสำรองราคาประหยัด

### OAuth Token หมดอายุ

OmniRoute จะรีเฟรชโทเค็นโดยอัตโนมัติ หากปัญหายังคงอยู่:

1. แดชบอร์ด → ผู้ให้บริการ → เชื่อมต่อใหม่
2. ลบการเชื่อมต่อของผู้ให้บริการแล้วเพิ่มใหม่

### การใช้ Kiro หลายบัญชี: บัญชีที่สองทำให้บัญชีแรกใช้การไม่ได้

**สาเหตุ:** backend ของ Kiro กำหนดให้มี active session ได้เพียงหนึ่งรายการต่อการลงทะเบียน OIDC client
เมื่อสองบัญชีใช้ registered client เดียวกัน (การเชื่อมต่อที่นำเข้าก่อน v3.8.0)
การรีเฟรชโทเค็นของบัญชีหนึ่งจะทำให้ refresh token ของอีกบัญชีใช้การไม่ได้

**วิธีแก้ไข (v3.8.0+):** นำเข้าการเชื่อมต่อที่ได้รับผลกระทบอีกครั้ง
ตั้งแต่ v3.8.0 เป็นต้นไป การเชื่อมต่อ Kiro ใหม่ทุกรายการที่สร้างผ่าน **นำเข้าโทเค็น**,
**การเข้าสู่ระบบผ่านโซเชียลด้วย Google/GitHub** หรือ **นำเข้าอัตโนมัติ** จะลงทะเบียน
OIDC client เฉพาะของตนเองโดยอัตโนมัติ ดังนั้นการเชื่อมต่อแต่ละรายการจึงแยกจากกันอย่างสมบูรณ์ และการรีเฟรช
บัญชีหนึ่งจะไม่ส่งผลกระทบต่อบัญชีอื่น

การเชื่อมต่อที่นำเข้า _ก่อน_ v3.8.0 จะไม่มีการลงทะเบียน client แยกตามการเชื่อมต่อ
การเชื่อมต่อเหล่านั้นจะยังคงใช้ endpoint สำหรับรีเฟรชการยืนยันตัวตนผ่านโซเชียลร่วมกัน
หากต้องการแยกการเชื่อมต่อออกจากกัน ให้ลบการเชื่อมต่อเก่าออกจาก แดชบอร์ด → ผู้ให้บริการ แล้วเพิ่มใหม่
ผ่านขั้นตอนการนำเข้าแบบใดก็ได้จากทั้งสามแบบ

สำหรับรายละเอียดทั้งหมดและคำแนะนำทีละขั้นตอนในการเพิ่มบัญชี Kiro สองบัญชีให้ทำงานควบคู่กัน
โปรดดู [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md)

## ปัญหาเกี่ยวกับ Cloud

### ข้อผิดพลาดในการซิงค์ Cloud

1. ตรวจสอบว่า `BASE_URL` ชี้ไปยังอินสแตนซ์ที่กำลังทำงานอยู่ (เช่น `http://localhost:20128`)
2. ตรวจสอบว่า `CLOUD_URL` ชี้ไปยังปลายทาง Cloud ของคุณ (เช่น `https://omniroute.dev`)
3. กำหนดค่า `NEXT_PUBLIC_*` ให้สอดคล้องกับค่าฝั่งเซิร์ฟเวอร์

### Cloud ที่ใช้ `stream=false` ส่งคืน 500

**อาการ:** `Unexpected token 'd'...` ที่ปลายทาง Cloud สำหรับการเรียกแบบไม่สตรีม

**สาเหตุ:** ต้นทางส่งเพย์โหลด SSE กลับมา ขณะที่ไคลเอนต์คาดว่าจะได้รับ JSON

**วิธีแก้ปัญหาชั่วคราว:** ใช้ `stream=true` สำหรับการเรียก Cloud โดยตรง รันไทม์ภายในเครื่องมีระบบสำรองสำหรับแปลง SSE→JSON

### Cloud ระบุว่าเชื่อมต่อแล้ว แต่แจ้งว่า "Invalid API key"

1. สร้างคีย์ใหม่จากแดชบอร์ดภายในเครื่อง (`/api/keys`)
2. เรียกใช้การซิงค์ Cloud: Enable Cloud → Sync Now
3. คีย์เก่าหรือคีย์ที่ยังไม่ได้ซิงค์อาจยังคงส่งคืน `401` บน Cloud

## ปัญหาเกี่ยวกับ Docker

### IPv6 ของ Docker / การเชื่อมต่อถูกรีเซ็ต

<a name="docker-ipv6"></a>

**อาการ:** `curl http://localhost:20128/v1/models` ส่งคืน `curl: (56) Recv failure: Connection reset by peer` แดชบอร์ดและปลายทางที่ไม่ต้องยืนยันตัวตนทำงานได้ แต่ปลายทางที่ต้องยืนยันตัวตนล้มเหลว — ดูเหมือนเป็นปัญหาการยืนยันตัวตน แต่จริง ๆ แล้วไม่ใช่

**สาเหตุ:** `docker run -p 20128:20128` เปิดให้บริการทั้งบน `0.0.0.0` (IPv4) และ `::` (IPv6) แต่โพรเซสภายในคอนเทนเนอร์รับฟังเฉพาะ IPv4 บนโฮสต์ที่ `localhost` ถูกแปลงเป็น `::1` ก่อน การเชื่อมต่อจะไปถึงพอร์ต IPv6 ที่เปิดไว้โดยไม่มีตัวรับฟังอยู่เบื้องหลัง → การเชื่อมต่อจึงถูกรีเซ็ต

**วิธีแก้ไข:**

1. **การวินิจฉัยอย่างรวดเร็ว:** เรียกใช้ `curl -4 http://localhost:20128/v1/models` หากทำงานได้เมื่อใช้ `-4` แต่ล้มเหลวเมื่อไม่ใช้ แสดงว่าคุณมีปัญหาการผูกพอร์ต IPv6 ที่ไม่ตรงกัน
2. **วิธีแก้ไขแบบถาวร:** ผูกกับ IPv4 อย่างชัดเจนโดยใช้ `-p 127.0.0.1:20128:20128` ในคำสั่ง `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   วิธีนี้บังคับให้ผูกกับ IPv4 และยังช่วยหลีกเลี่ยงการเปิดเผยพร็อกซีบนอินเทอร์เฟซทั้งหมดของโฮสต์ด้วย

## การดีบัก

### เปิดใช้งานไฟล์บันทึก

ตั้งค่า `APP_LOG_TO_FILE=true` ในไฟล์ `.env` ของคุณ บันทึกของแอปพลิเคชันจะถูกเขียนไว้ภายใต้ `logs/`
อาร์ติแฟกต์ของคำขอจะถูกจัดเก็บไว้ภายใต้ `${DATA_DIR}/call_logs/` เมื่อเปิดใช้งานไปป์ไลน์บันทึกการเรียกในการตั้งค่า
เมื่อเปิดใช้งานการบันทึกข้อมูลของไปป์ไลน์ ให้ตั้งค่า `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` เพื่อละเว้น
เพย์โหลดของส่วนข้อมูลสตรีม หรือปรับ `CALL_LOG_PIPELINE_MAX_SIZE_KB` เพื่อเปลี่ยนขีดจำกัดขนาดอาร์ติแฟกต์ในหน่วย KB

### ตรวจสอบสถานะของผู้ให้บริการ

```bash
# แดชบอร์ดสถานะ
http://localhost:20128/dashboard/health

# การตรวจสอบสถานะ API
curl http://localhost:20128/api/monitoring/health
```

### พื้นที่จัดเก็บของรันไทม์

- สถานะหลัก: `${DATA_DIR}/storage.sqlite` (ผู้ให้บริการ ชุดค่าผสม นามแฝง คีย์ การตั้งค่า)
- การใช้งาน: ตาราง SQLite ใน `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + `${DATA_DIR}/call_logs/` ซึ่งเป็นทางเลือก
- บันทึกของแอปพลิเคชัน: `<repo>/logs/...` (เมื่อ `APP_LOG_TO_FILE=true`)
- อาร์ติแฟกต์บันทึกการเรียก: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` เมื่อเปิดใช้งานไปป์ไลน์บันทึกการเรียก

การดำเนินการ **Clean history** ในหน้า Request Logs จะล้าง `call_logs`,
`request_detail_logs` แบบเก่า และไดเรกทอรีอาร์ติแฟกต์ `${DATA_DIR}/call_logs/` ภายในเครื่อง

## ปัญหา Circuit Breaker

### ผู้ให้บริการค้างอยู่ในสถานะ OPEN

เมื่อ circuit breaker ของผู้ให้บริการอยู่ในสถานะ OPEN คำขอจะถูกบล็อกจนกว่าระยะเวลาคูลดาวน์จะสิ้นสุดลง

**วิธีแก้ไข:**

1. ไปที่ **แดชบอร์ด → การตั้งค่า → ความยืดหยุ่น**
2. ตรวจสอบการ์ด circuit breaker ของผู้ให้บริการที่ได้รับผลกระทบ
3. คลิก **รีเซ็ตทั้งหมด** เพื่อล้าง breaker ทั้งหมด หรือรอให้ระยะเวลาคูลดาวน์สิ้นสุดลง
4. ตรวจสอบว่าผู้ให้บริการพร้อมใช้งานจริงก่อนรีเซ็ต

### ผู้ให้บริการทริกเกอร์ circuit breaker ซ้ำ ๆ

หากผู้ให้บริการเข้าสู่สถานะ OPEN ซ้ำ ๆ:

1. ตรวจสอบรูปแบบความล้มเหลวที่ **แดชบอร์ด → สถานภาพ → สถานภาพผู้ให้บริการ**
2. ไปที่ **การตั้งค่า → ความยืดหยุ่น → โปรไฟล์ผู้ให้บริการ** แล้วเพิ่มเกณฑ์ความล้มเหลว
3. ตรวจสอบว่าผู้ให้บริการได้เปลี่ยนขีดจำกัด API หรือต้องมีการยืนยันตัวตนใหม่หรือไม่
4. ตรวจสอบข้อมูลเทเลเมทรีด้านเวลาแฝง — เวลาแฝงสูงอาจทำให้เกิดความล้มเหลวจากการหมดเวลา

## การดีบักตัวแปล

ใช้ **แดชบอร์ด → ตัวแปล** เพื่อดีบักปัญหาการแปลรูปแบบ:

| โหมด                   | ควรใช้เมื่อ                                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| **พื้นที่ทดลอง**       | เปรียบเทียบรูปแบบอินพุต/เอาต์พุตแบบเคียงข้างกัน — วางคำขอที่ล้มเหลวเพื่อดูว่าคำขอนั้นถูกแปลอย่างไร |
| **เครื่องมือทดสอบแชต** | ส่งข้อความแบบสดและตรวจสอบเพย์โหลดคำขอ/การตอบกลับทั้งหมด รวมถึงส่วนหัว                              |
| **ชุดทดสอบ**           | เรียกใช้การทดสอบแบบกลุ่มกับชุดรูปแบบต่าง ๆ เพื่อค้นหาว่าการแปลใดเสียหาย                            |
| **ตัวติดตามแบบสด**     | เฝ้าดูโฟลว์คำขอแบบเรียลไทม์เพื่อตรวจจับปัญหาการแปลที่เกิดขึ้นเป็นครั้งคราว                         |

### ปัญหารูปแบบที่พบบ่อย

- **แท็กการคิดไม่ปรากฏ** — ตรวจสอบว่าผู้ให้บริการเป้าหมายรองรับการคิดและการตั้งค่างบประมาณการคิดหรือไม่
- **การเรียกใช้เครื่องมือหายไป** — การแปลรูปแบบบางแบบอาจตัดฟิลด์ที่ไม่รองรับออก โปรดตรวจสอบในโหมดพื้นที่ทดลอง
- **พรอมต์ระบบหายไป** — Claude และ Gemini จัดการพรอมต์ระบบแตกต่างกัน โปรดตรวจสอบเอาต์พุตการแปล
- **SDK ส่งคืนสตริงดิบแทนออบเจ็กต์** — แก้ไขแล้วใน v1.x โดยตัวกรองการตอบกลับจะตัดฟิลด์ที่ไม่ได้มาตรฐาน (`x_groq`, `usage_breakdown` ฯลฯ) ซึ่งทำให้การตรวจสอบความถูกต้องด้วย Pydantic ของ OpenAI SDK ล้มเหลว หากคุณยังพบปัญหานี้ใน v3.x+ โปรดเปิดรายงานปัญหา
- **GLM/ERNIE ปฏิเสธบทบาท `system`** — แก้ไขแล้วใน v1.x โดยตัวปรับบทบาทจะรวมข้อความระบบเข้ากับข้อความผู้ใช้โดยอัตโนมัติสำหรับโมเดลที่ไม่เข้ากัน หากคุณยังพบปัญหานี้ใน v3.x+ โปรดเปิดรายงานปัญหา
- **ไม่รู้จักบทบาท `developer`** — แก้ไขแล้วใน v1.x โดยจะถูกแปลงเป็น `system` โดยอัตโนมัติสำหรับผู้ให้บริการที่ไม่ใช่ OpenAI หากคุณยังพบปัญหานี้ใน v3.x+ โปรดเปิดรายงานปัญหา
- **`json_schema` ใช้งานกับ Gemini ไม่ได้** — แก้ไขแล้วใน v1.x โดยขณะนี้ `response_format` จะถูกแปลงเป็น `responseMimeType` + `responseSchema` ของ Gemini หากคุณยังพบปัญหานี้ใน v3.x+ โปรดเปิดรายงานปัญหา

## การตั้งค่าความทนทาน

### การจำกัดอัตราอัตโนมัติไม่ทำงาน

- การจำกัดอัตราอัตโนมัติใช้กับผู้ให้บริการที่ใช้ API key เท่านั้น (ไม่ใช้กับ OAuth/การสมัครสมาชิก)
- ตรวจสอบว่า **Settings → Resilience → Provider Profiles** เปิดใช้งานการจำกัดอัตราอัตโนมัติแล้ว
- ตรวจสอบว่าผู้ให้บริการส่งคืนรหัสสถานะ `429` หรือส่วนหัว `Retry-After` หรือไม่

### การปรับแต่ง exponential backoff

โปรไฟล์ผู้ให้บริการรองรับการตั้งค่าต่อไปนี้:

- **Base delay** — เวลารอเริ่มต้นหลังจากล้มเหลวครั้งแรก (ค่าเริ่มต้น: 1s)
- **Max delay** — ขีดจำกัดสูงสุดของเวลารอ (ค่าเริ่มต้น: 30s)
- **Multiplier** — อัตราการเพิ่มเวลารอต่อการล้มเหลวต่อเนื่องแต่ละครั้ง (ค่าเริ่มต้น: 2x)

### การป้องกัน thundering herd

เมื่อคำขอพร้อมกันจำนวนมากเข้าถึงผู้ให้บริการที่ถูกจำกัดอัตรา OmniRoute จะใช้ mutex + การจำกัดอัตราอัตโนมัติเพื่อจัดลำดับคำขอและป้องกันความล้มเหลวแบบลูกโซ่ กระบวนการนี้ทำงานโดยอัตโนมัติสำหรับผู้ให้บริการที่ใช้ API key

### คำขอแชทล้มเหลวด้วย 503 / chat_admission_busy

**อาการ:**

- ปลายทาง chat completions ส่งคืนการตอบกลับ `503` ที่ลองใหม่ได้ โดยมีรหัสข้อผิดพลาดเป็น
  `chat_admission_busy`
- การตอบกลับมี `Retry-After` ตั้งแต่ #12135 เป็นต้นมา ค่านี้คำนวณจากอัตราการใช้งานที่ตรวจพบ
  โดยเลือกค่าที่มากกว่าระหว่างช่วงเวลา `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ที่คำขอได้รอไปแล้ว
  กับระยะเวลาที่ lease แบบ heavyweight ปัจจุบันถูกถือครอง จากนั้นปัดขึ้นเป็นจำนวนวินาทีเต็ม
  และจำกัดไว้สูงสุดที่ 60 สำหรับ gate ที่ไม่มีการใช้งาน ระบบจะยังคงใช้ค่าต่ำสุดแบบเดิม ได้แก่ 2 วินาทีสำหรับ
  เส้นทางแบบอิงไบต์ และ 1 วินาทีสำหรับเส้นทางแบบอิงโครงสร้าง (ซึ่งมี
  `reason: "structure_limit"` รวมอยู่ด้วย)
- เหตุการณ์นี้อาจเกิดขึ้นขณะที่แชทแบบ heavyweight อื่นหรือการตอบกลับแบบ streaming ที่ใช้เวลานานยังคง
  อยู่ระหว่างดำเนินการ

เนื้อหาการตอบกลับแบบอิงไบต์คือ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

การตอบกลับแบบอิงโครงสร้างใช้ type และ code เดียวกัน โดยมีข้อความ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
และ `reason: "structure_limit"`
เมื่อใช้เกณฑ์เริ่มต้น คำขอจะถือว่ามีโครงสร้างแบบ heavyweight เมื่อมีข้อความอย่างน้อย `200` รายการ
มี tools อย่างน้อย `64` รายการ หรือมี token โดยประมาณอย่างน้อย `32,000` token หรือเมื่อการประเมินโครงสร้าง
แบบมีขอบเขตใช้ขีดจำกัดจนหมดที่โหนดที่เข้าถึง `10,000` โหนด หรือความลึก `12`

**สาเหตุ:** นี่คือการลดภาระโดยเจตนาภายใน OmniRoute ไม่ใช่ความล้มเหลวของผู้ให้บริการ upstream
แต่ละ process ใช้ guard ภายใน process เพื่อสำรองความจุแบบ heavyweight ที่มีจำกัด ก่อนเก็บไว้
และแยกวิเคราะห์เนื้อหาคำขอขนาดใหญ่ lease แบบ heavyweight จะยังคงถูกถือครองตลอดอายุการใช้งานของการตอบกลับ
แบบ SSE

**#503-fanout:** ก่อนการแก้ไขนี้ guard จำกัดการทำงานพร้อมกันด้วยจำนวนคำขอคงที่
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ค่าเริ่มต้น `1`) โดยไม่คำนึงถึงหน่วยความจำของโฮสต์ ทำให้ fan-out
ของ coding-agent (subagent/CLI หลายรายการ โดยเนื้อหามักมีขนาด > 256 KB) ลดลงเหลือ
การทำงานพร้อมกันที่มีประสิทธิผลประมาณ 1 รายการ และเกิด 503 ภายใต้ภาระงานปกติอย่างสมบูรณ์ ขณะนี้ guard สามารถปรับตัวเองได้:
โดยควบคุมด้วยงบประมาณ BYTE สำหรับ ingest ที่คำนวณโดยอัตโนมัติ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`)
ซึ่งกำหนดขนาดจากเพดานหน่วยความจำจริงของ process และยังพิจารณาสัญญาณความกดดันของทรัพยากรแบบสดด้วย ดังนั้น
ระบบจะลดภาระเฉพาะเมื่อโฮสต์อยู่ภายใต้ความกดดันด้านหน่วยความจำอย่างแท้จริง ไม่ใช่เพียงเพราะมีคำขอ
แบบ heavy มากกว่าหนึ่งรายการเข้ามาพร้อมกัน ขีดจำกัดจำนวนแบบเดิม (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ยังคง
ได้รับการปฏิบัติตาม แต่เฉพาะเมื่อคุณตั้งค่าไว้อย่างชัดเจนเท่านั้น

เมื่อความจุไม่ว่าง คำขอแบบ heavyweight จะรอก่อนเป็นเวลาสูงสุด
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ค่าเริ่มต้น `2000`, ค่า `0` จะปิดใช้งานการรอ) เพื่อให้สล็อตว่าง
ก่อนตอบกลับด้วย `503` ที่ลองใหม่ได้ การรอแบบมีขอบเขตนี้มีไว้เพื่อให้ไคลเอนต์รูปแบบ agent
(OpenCode, Claude Code, Cursor) ที่ fan out คำขอย่อยแบบ heavy พร้อมกัน สามารถจัดลำดับคำขอที่ถาโถมเข้ามา
แทนที่จะใช้โควตาการลองใหม่ทั้งหมดไปกับการปฏิเสธทันทีและหยุดทำงานระหว่างงาน
อัตราการใช้งาน lease แบบ heavyweight ปัจจุบัน งบประมาณไบต์ที่กำหนดแล้ว และระดับความรุนแรงของความกดดันแบบสด
จะแสดงที่ `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — ตรวจสอบค่าเหล่านี้ก่อนแก้ไข env var ใดๆ
Settings → Resilience → Request Queue → Concurrent Requests ไม่ได้ควบคุมส่วนนี้ การตั้งค่าดังกล่าว
ควบคุมกลไกคิวคำขอของผู้ให้บริการอีกระบบหนึ่ง

**วิธีแก้ไข:**

1. ลองใหม่ก่อน ไคลเอนต์ควรปฏิบัติตาม `Retry-After` และใช้ backoff แทนการส่ง
   คำขอเดิมซ้ำทันที
2. ตรวจสอบ `/api/monitoring/health` → `chatAdmission` ก่อนปรับแต่งสิ่งใด `countCapEnabled:
false` และ `maxInflightBytes` ที่มีค่าเพียงพอ หมายความว่างบประมาณที่คำนวณโดยอัตโนมัติกำลังทำ
   หน้าที่ของมันอยู่แล้ว ส่วน `pressureSeverity` ที่มีค่าเป็น `high`/`critical` หมายความว่าโฮสต์มีหน่วยความจำเหลือน้อยจริงๆ —
   ปัญหานี้ไม่สามารถแก้ไขได้ด้วย admission env var แต่ต้องเพิ่ม RAM หรือลดขนาดภาระงาน
3. เฉพาะเมื่อ `/api/monitoring/health` แสดงว่างบประมาณที่คำนวณโดยอัตโนมัติมีขนาดเล็กเกินไปจริงๆ สำหรับ
   โฮสต์ของคุณ (พบได้น้อย เพราะระบบปรับขนาดตั้งแต่ container ไปจนถึง bare-metal อยู่แล้ว) ให้แทนที่ค่าโดยตรงด้วย
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` แทนการย้อนกลับไปใช้ขีดจำกัดจำนวนคำขอแบบเดิม

โปรดดู[เอกสารอ้างอิงตัวแปรสภาพแวดล้อม](../reference/ENVIRONMENT.md#4-security--authentication)
สำหรับการตั้งค่า admission ที่เป็นแหล่งข้อมูลอ้างอิงอย่างเป็นทางการ

## อนุกรมวิธานความล้มเหลวของ RAG / LLM ที่ใช้เพิ่มเติมได้ (16 ปัญหา)

ผู้ใช้ OmniRoute บางรายวางเกตเวย์ไว้หน้า RAG หรือสแต็กเอเจนต์ ในการตั้งค่าเหล่านี้ มักพบรูปแบบที่แปลกประหลาด กล่าวคือ OmniRoute ดูเหมือนทำงานเป็นปกติ (ผู้ให้บริการพร้อมใช้งาน โปรไฟล์การกำหนดเส้นทางถูกต้อง ไม่มีการแจ้งเตือนขีดจำกัดอัตรา) แต่คำตอบสุดท้ายยังคงผิดอยู่

ในทางปฏิบัติ เหตุการณ์เหล่านี้มักเกิดจากไปป์ไลน์ RAG ปลายทาง ไม่ใช่จากตัวเกตเวย์เอง

หากคุณต้องการชุดคำศัพท์ร่วมกันเพื่ออธิบายความล้มเหลวเหล่านั้น คุณสามารถใช้ WFGY ProblemMap ซึ่งเป็นแหล่งข้อมูลข้อความภายนอกภายใต้สัญญาอนุญาต MIT ที่กำหนดรูปแบบความล้มเหลวของ RAG / LLM ที่เกิดซ้ำสิบหกรูปแบบ โดยภาพรวมครอบคลุมเรื่องต่อไปนี้:

- การดึงข้อมูลที่คลาดเคลื่อนและขอบเขตบริบทที่เสียหาย
- ดัชนีและที่เก็บเวกเตอร์ที่ว่างเปล่าหรือล้าสมัย
- ความไม่สอดคล้องกันระหว่าง embedding กับความหมาย
- ปัญหาในการประกอบพรอมต์และหน้าต่างบริบท
- การล่มสลายของตรรกะและคำตอบที่มั่นใจเกินจริง
- ความล้มเหลวของสายงานที่ยาวและการประสานงานของเอเจนต์
- หน่วยความจำของหลายเอเจนต์และบทบาทที่คลาดเคลื่อน
- ปัญหาลำดับการปรับใช้และการเริ่มต้นระบบ

แนวคิดนี้เรียบง่าย:

1. เมื่อคุณตรวจสอบคำตอบที่ไม่ถูกต้อง ให้บันทึก:
   - งานและคำขอของผู้ใช้
   - เส้นทางหรือชุดผู้ให้บริการใน OmniRoute
   - บริบท RAG ใดๆ ที่ใช้ในระบบปลายทาง (เอกสารที่ดึงมา การเรียกใช้เครื่องมือ ฯลฯ)
2. จับคู่เหตุการณ์กับหมายเลข WFGY ProblemMap หนึ่งหรือสองหมายเลข (`No.1` … `No.16`)
3. จัดเก็บหมายเลขดังกล่าวไว้ในแดชบอร์ด คู่มือปฏิบัติงาน หรือตัวติดตามเหตุการณ์ของคุณ ถัดจากบันทึกของ OmniRoute
4. ใช้หน้า WFGY ที่ตรงกันเพื่อตัดสินใจว่าคุณจำเป็นต้องเปลี่ยนสแต็ก RAG ตัวดึงข้อมูล หรือกลยุทธ์การกำหนดเส้นทางหรือไม่

ข้อความฉบับเต็มและสูตรการแก้ไขที่เป็นรูปธรรมอยู่ที่นี่ (สัญญาอนุญาต MIT เฉพาะข้อความ):

[README ของ WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

คุณสามารถข้ามส่วนนี้ได้หากคุณไม่ได้เรียกใช้ไปป์ไลน์ RAG หรือเอเจนต์อยู่เบื้องหลัง OmniRoute

## ปัญหาที่ทราบใน v3.8.0

ปัญหาเฉพาะของรุ่น v3.8.0 และวิธีแก้ปัญหาชั่วคราวในปัจจุบัน หากมีการแก้ไขในแพตช์ภายหลัง รายการนี้จะได้รับการอัปเดตหรือนำออก

### การยืนยันตัวตนของ Devin CLI ล้มเหลว

**อาการ:**

- "ไม่พบ Devin CLI" หรือ "การยืนยันตัวตนล้มเหลว" เมื่อเรียกใช้เครื่องมือที่ทำงานผ่าน Devin
- การตรวจสอบรันไทม์ของ CLI รายงาน `installed=false`

**สาเหตุ:**

- `CLI_DEVIN_BIN` ชี้ไปยังพาธที่ไม่มีอยู่
- ไม่ได้ติดตั้ง Devin CLI บนโฮสต์

**วิธีแก้ไข:**

1. ติดตั้ง Devin CLI สำหรับแพลตฟอร์มของคุณ
2. ตั้งค่า `CLI_DEVIN_BIN=/usr/local/bin/devin` (หรือพาธจริง) ใน `.env`
3. รีสตาร์ต OmniRoute และทดสอบอีกครั้งจาก **แดชบอร์ด → เครื่องมือ CLI**

### คูลดาวน์ของโมเดลค้าง (รีเซ็ตด้วยตนเอง)

**อาการ:**

- โมเดลยังคงแสดงอยู่ในรายการคูลดาวน์ แม้จะเลยเวลาหมดอายุแล้ว
- คำขอยังคงข้ามโมเดลดังกล่าวในการกำหนดเส้นทางแบบชุด แม้การประทับเวลาจะอยู่ในอดีตแล้ว

**การรีเซ็ตด้วยตนเอง:**

- **แดชบอร์ด:** **การตั้งค่า → คูลดาวน์ของโมเดล** → คลิก **เปิดใช้งานอีกครั้ง** บนการ์ดที่ได้รับผลกระทบ
- **API:** `DELETE /api/resilience/model-cooldowns` พร้อมส่วนหัวการยืนยันตัวตนสำหรับการจัดการ

### การเชื่อมต่อผู้ให้บริการ Command Code ล้มเหลวด้วย 403

**อาการ:**

- ได้รับ 403 เมื่อทดสอบการเชื่อมต่อผู้ให้บริการ Command Code
- การ์ดผู้ให้บริการแสดง "ไม่ได้รับอนุญาต" หลังจากเพิ่มใหม่

**สาเหตุ:** ขั้นตอน OAuth ดำเนินการไม่เสร็จสมบูรณ์ (ไม่ได้รับ callback หรือไม่ได้บันทึก token ไว้)

**วิธีแก้ไข:**

- เรียกใช้ `omniroute providers` จาก CLI เพื่อเรียกขั้นตอน OAuth อีกครั้ง หรือ
- เรียกใช้ OAuth อีกครั้งจาก **แดชบอร์ด → ผู้ให้บริการ → Command Code → เชื่อมต่อใหม่**

### ModelScope ส่งคืนคูลดาวน์ 429 ที่เข้มงวด

**อาการ:**

- เกิดคูลดาวน์ที่สั้นมากหรือทันทีบน ModelScope หลังจากมีคำขอจำนวนไม่มากในช่วงเวลาสั้นๆ
- การกำหนดเส้นทางแบบชุดข้าม ModelScope เร็วกว่าที่คาดไว้

**สาเหตุ:** ModelScope ส่งส่วนหัว `Retry-After` เฉพาะของผู้ให้บริการ โดย v3.8.0 มาพร้อมการจัดการส่วนหัวเหล่านั้นโดยเฉพาะ ดังนั้นเวอร์ชันเก่าจึงตีความส่วนหัวเหล่านั้นผิดว่าเป็นคำแนะนำขีดจำกัดอัตราทั่วไป

**วิธีแก้ไข:**

- ตรวจสอบให้แน่ใจว่าคุณใช้ v3.8.0 หรือใหม่กว่า
- ตรวจสอบว่าเปิดใช้ตัวเลือก `useUpstream429BreakerHints` ภายใต้ **การตั้งค่า → ความยืดหยุ่นของระบบ**

### ไม่มี OMNIROUTE_WS_BRIDGE_SECRET ในสภาพแวดล้อมจริง

**อาการ:**

- ได้รับ 401 ในทุกคำขอ WebSocket bridge ของ Codex/Responses เมื่อทำงานบนโฮสต์สภาพแวดล้อมจริงระยะไกล
- การจับมือของ WebSocket bridge ปิดลงทันทีหลังจากเชื่อมต่อ

**สาเหตุ:** ไม่มีตัวแปรสภาพแวดล้อม `OMNIROUTE_WS_BRIDGE_SECRET` ในสภาพแวดล้อมจริง

**วิธีแก้ไข:**

1. สร้างข้อมูลลับแบบสุ่ม: `openssl rand -hex 32`
2. ตั้งค่า `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ในสภาพแวดล้อมของเซิร์ฟเวอร์จริง (และในไคลเอนต์ใดๆ ที่สื่อสารกับ bridge)
3. รีสตาร์ต OmniRoute

### Responses API: โหมดเบื้องหลังถูกลดระดับเป็นแบบซิงโครนัส

**อาการ:**

- มีการบันทึกคำเตือน: `background mode degraded to synchronous`
- คำขอ `background: true` ส่งคืนการตอบกลับแบบซิงโครนัสตามปกติ แทนที่จะเป็นตัวอ้างอิงงานเบื้องหลัง

**สาเหตุ:** v3.8.0 ตั้งใจลดระดับ `background: true` บน Responses API ให้เป็นการดำเนินการแบบซิงโครนัส พร้อมส่งคำเตือนออกมา การดำเนินการเบื้องหลังแบบอะซิงโครนัสเต็มรูปแบบเป็นความสามารถที่จะส่งมอบในอนาคต

**วิธีแก้ไข:**

- ปรับไคลเอนต์ให้เรียกใช้โดยไม่มี `background` หรือ
- รอรุ่นถัดไปที่มาพร้อมโหมดเบื้องหลังแบบอะซิงโครนัสเต็มรูปแบบ (ติดตามบันทึกการเปลี่ยนแปลง)

## การเริ่มต้นช้า / หมดเวลารอความพร้อม

หาก CLI แสดง `⚠ Server did not respond within 60s` แต่เซิร์ฟเวอร์ยังทำงานอยู่จริง แสดงว่าระยะเวลาที่กำหนดให้โพรบตรวจสอบความพร้อมนั้นสั้นเกินไปสำหรับสภาพแวดล้อมของคุณ

ปัญหานี้มักเกิดขึ้นบน Windows (เนื่องจากโปรแกรมป้องกันไวรัสหรือตัวเฝ้าติดตามระบบไฟล์) หรือในคอนเทนเนอร์ที่มีภาระงานหนักระหว่างการเริ่มต้น

**วิธีแก้ไข — เพิ่มระยะเวลารอ:**

```bash
# ผ่านตัวแปรสภาพแวดล้อม (มีผลต่อเนื่องในการเริ่มต้นครั้งถัดไป):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 นาที
omniroute serve

# ผ่านแฟล็ก CLI (มีผลเฉพาะครั้งนี้):
omniroute serve --ready-timeout 180000
```

ค่าเริ่มต้นคือ 60 000 ms (60 s) คำเตือนนี้มีไว้เพื่อแจ้งข้อมูลเท่านั้น เซิร์ฟเวอร์จะเริ่มต้นต่อไปในเบื้องหลังและสามารถเข้าถึงได้เมื่อกระบวนการบูตเสร็จสมบูรณ์

ดูรายละเอียดทั้งหมดเกี่ยวกับ `OMNIROUTE_READY_TIMEOUT_MS` ได้ที่ [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md)
