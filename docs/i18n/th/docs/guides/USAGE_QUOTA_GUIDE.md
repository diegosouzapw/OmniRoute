> **สรุปสั้นๆ**: OmniRoute ติดตามการใช้โทเค็นของทุกคำขอ คำนวณค่าใช้จ่าย บังคับใช้โควตาต่อคีย์ API และแสดงข้อมูลวิเคราะห์ในแดชบอร์ด คู่มือนี้อธิบายว่าทั้งหมดนี้ทำงานอย่างไร

**แหล่งข้อมูล:**

- `open-sse/services/usage.ts` (~70KB) — ระบบติดตามการใช้งานหลัก
- `src/lib/usageAnalytics.ts` (~10KB) — การรวบรวมข้อมูลสำหรับแดชบอร์ด
- `src/lib/db/quotaSnapshots.ts` — ข้อมูลประวัติโควตา
- `src/lib/db/usage*.ts` — โมดูลฐานข้อมูลหลายรายการที่เกี่ยวข้องกับการใช้งาน

## ภาพรวม

ทุกคำขอที่ไหลผ่าน OmniRoute จะสร้าง **ระเบียนการใช้งาน** ซึ่งบันทึกข้อมูลต่อไปนี้:

- **ข้อมูลระบุตัวตน**: คีย์ API, ผู้ให้บริการ, โมเดล และคอมโบที่ใช้
- **โทเค็น**: โทเค็นพรอมต์ โทเค็นผลลัพธ์ โทเค็นที่แคชไว้ และจำนวนรวม
- **ค่าใช้จ่าย**: จำนวนเงิน USD (คำนวณจากข้อมูลราคา)
- **เวลา**: เวลาแฝง และเวลาประทับเริ่มต้น/สิ้นสุด
- **สถานะ**: สำเร็จ ข้อผิดพลาด ถูกจำกัดอัตรา เป็นต้น

ระเบียนเหล่านี้จะถูกรวบรวมเป็น **ข้อมูลวิเคราะห์** จัดเก็บเป็น **สแนปช็อตโควตา** และใช้บังคับใช้ **ขีดจำกัดงบประมาณต่อคีย์**

```
คำขอ ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    การวิเคราะห์ โควตา การเรียกเก็บเงิน
                    (แดชบอร์ด) (บังคับใช้) (ส่งออก)
```

## ข้อมูลที่ถูกบันทึก

บริการ `usage.ts` จะบันทึก **เหตุการณ์การใช้งาน** สำหรับทุกคำขอ:

| ฟิลด์              | ชนิด    | แหล่งที่มา                                                 |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID ที่สร้างขึ้นเมื่อบันทึก                               |
| `apiKeyId`         | string  | คีย์ API ที่เริ่มต้นคำขอ                                   |
| `provider`         | string  | ID ผู้ให้บริการ (openai, anthropic เป็นต้น)                |
| `model`            | string  | ID โมเดล (gpt-5, claude-opus-4-6 เป็นต้น)                  |
| `comboId`          | string? | ID คอมโบ หากกำหนดเส้นทางผ่านคอมโบ                          |
| `promptTokens`     | number  | จากการตอบกลับของต้นทาง                                     |
| `completionTokens` | number  | จากการตอบกลับของต้นทาง                                     |
| `cachedTokens`     | number  | โทเค็นที่พบในแคช (การแคชพรอมต์ของ Anthropic เป็นต้น)       |
| `totalTokens`      | number  | พรอมต์ + ผลลัพธ์                                           |
| `costUsd`          | number  | คำนวณจากข้อมูลราคา                                         |
| `latencyMs`        | number  | ระยะเวลาของคำขอตั้งแต่ต้นจนจบ                              |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | คลาสข้อผิดพลาดหากสถานะ != success                          |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | ข้อมูลกำหนดเองที่ปลั๊กอินแทรกเข้ามา                        |

### โทเค็นมาจากที่ใด

โทเค็นจะถูกดึงจากการตอบกลับของผู้ให้บริการต้นทางภายใน **ตัวจัดการการตอบกลับ**:

```ts
// จาก open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

สำหรับผู้ให้บริการที่ไม่ส่งข้อมูลการใช้งานกลับมา (เช่น ผู้ให้บริการบางรายที่ใช้คุกกี้เว็บ) OmniRoute จะ **ประมาณ** จำนวนโทเค็นโดยใช้หลักเกณฑ์ `~4 chars per token` (ดู `open-sse/services/autoCombo/pipelineRouter.ts`)

### โทเค็นที่แคชไว้

OmniRoute ติดตาม `cached_tokens` แยกจาก `prompt_tokens` เนื่องจาก:

- การแคชพรอมต์ของ Anthropic คิดค่าบริการสำหรับโทเค็นที่แคชไว้ในอัตราที่ลดลง (10% ของอัตราปกติ)
- ผู้ให้บริการบางรายส่งคืน `cache_read_input_tokens` ซึ่งควรคำนวณราคาด้วยอัตราที่แตกต่างกัน
- ข้อมูลวิเคราะห์สามารถแสดง **อัตราการพบข้อมูลในแคช** = `cached_tokens / prompt_tokens`

## การคำนวณค่าใช้จ่าย

ค่าใช้จ่ายคำนวณจาก **ข้อมูลราคา** ที่ซิงค์จาก LiteLLM (`src/lib/pricingSync.ts`):

| โมเดล             | อินพุต $/1M | เอาต์พุต $/1M | แคช $/1M |
| ----------------- | ----------- | ------------- | -------- |
| gpt-5             | $2.50       | $10.00        | —        |
| claude-opus-4-6   | $15.00      | $75.00        | $1.50    |
| claude-sonnet-4-5 | $3.00       | $15.00        | $0.30    |
| gemini-2.5-pro    | $1.25       | $10.00        | —        |

สูตรคำนวณค่าใช้จ่าย (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **เหตุใดจึงต้องหักแคชออกจากพรอมต์?** ส่วนที่แคชไว้มีการคิดราคาแยกต่างหาก การคิดราคาอินพุตจากพรอมต์ทั้งหมดจึงทำให้คำนวณเกินจริง

### การซิงค์ราคา

ข้อมูลราคาจะซิงค์จาก LiteLLM โดยอัตโนมัติผ่านเอนด์พอยต์ `/api/pricing/sync` (ทริกเกอร์โดยงาน cron ในตัว ไม่ใช่ตัวแปรสภาพแวดล้อมที่ผู้ใช้เข้าถึงได้):

```bash
# ทริกเกอร์ด้วยตนเอง
curl -X POST http://localhost:20128/api/pricing/sync
```

สำหรับโมเดลที่ไม่มีข้อมูลราคา OmniRoute จะใช้วิธี **ประมาณค่าใช้จ่าย** ด้วยอัตราเฉลี่ยภายในแทน (อ้างอิงจากข้อมูลราคาของ LiteLLM)

## การรวมข้อมูลตามช่วงวันที่

โมดูล `usageAnalytics.ts` คำนวณวิดเจ็ตแดชบอร์ดจากข้อมูลการใช้งานดิบ โดยรองรับช่วงเวลา 7 รูปแบบ:

| ช่วง     | กรอบเวลา                             | กรณีใช้งาน                            |
| -------- | ------------------------------------ | ------------------------------------- |
| `1d`     | 24 ชั่วโมงที่ผ่านมา                  | ตรวจจับค่าใช้จ่ายที่พุ่งสูงรายชั่วโมง |
| `7d`     | 7 วันที่ผ่านมา                       | ตรวจสอบรายสัปดาห์                     |
| `30d`    | 30 วันที่ผ่านมา                      | การเรียกเก็บเงินรายเดือน              |
| `90d`    | 90 วันที่ผ่านมา                      | การวิเคราะห์รายไตรมาส                 |
| `ytd`    | ตั้งแต่วันที่ 1 ม.ค. ของปีปัจจุบัน   | ติดตามงบประมาณรายปี                   |
| `all`    | ตลอดระยะเวลาทั้งหมด                  | สถิติตลอดอายุการใช้งาน                |
| `custom` | วันที่เริ่มต้น/สิ้นสุดที่ผู้ใช้กำหนด | การตรวจสอบและคิวรีเฉพาะกิจ            |

### วิดเจ็ตแดชบอร์ดที่คำนวณ

สำหรับทุกช่วงวันที่ เลเยอร์การวิเคราะห์จะคำนวณข้อมูลต่อไปนี้:

| วิดเจ็ต                       | คำอธิบาย                                                            |
| ----------------------------- | ------------------------------------------------------------------- |
| **การ์ดสรุป**                 | จำนวนคำขอทั้งหมด ค่าใช้จ่ายทั้งหมด โทเค็นทั้งหมด และอัตราความสำเร็จ |
| **แผนภูมิแนวโน้มรายวัน**      | ค่าใช้จ่าย + โทเค็นต่อวัน โดยวางซ้อนตามโมเดล                        |
| **ฮีตแมปกิจกรรม**             | ตารางชั่วโมงของวัน × วันในสัปดาห์ โดยสี = จำนวนคำขอ                 |
| **รายละเอียดตามโมเดล**        | แผนภูมิวงกลมแสดงค่าใช้จ่ายตามโมเดล                                  |
| **รายละเอียดตามผู้ให้บริการ** | แผนภูมิแท่งแสดงจำนวนคำขอตามผู้ให้บริการ                             |
| **คีย์ API อันดับสูงสุด**     | ตารางคีย์ 10 อันดับแรกตามค่าใช้จ่าย                                 |
| **การวิเคราะห์ข้อผิดพลาด**    | อัตราข้อผิดพลาดตามช่วงเวลาและคลาสข้อผิดพลาดที่พบบ่อยที่สุด          |

### การเข้าถึงด้วยโปรแกรม

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // ระเบียนประวัติการใช้งาน
  "7d",                 // ช่วงเวลา: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // แมปการเชื่อมต่อผู้ให้บริการ (connectionId → ชื่อบัญชี)
  {
    startDate: "2025-01-01",  // ไม่บังคับ: สำหรับช่วง "custom"
    endDate: "2025-06-01",   // ไม่บังคับ: สำหรับช่วง "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (เซนต์)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## การบังคับใช้โควตา

โควตาต่อคีย์ API ถูกบังคับใช้ในสองจุด:

1. **ขีดจำกัดแบบผ่อนปรน** (`quotaWarnAt`): แสดงคำเตือนบนแดชบอร์ดเมื่อการใช้งานเกินเกณฑ์
2. **ขีดจำกัดแบบเข้มงวด** (`quotaLimit`): ปฏิเสธคำขอด้วย HTTP 429 เมื่อเกินขีดจำกัด

### การกำหนดค่า

```ts
// ต่อคีย์ API
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — แสดงคำเตือน
  quotaLimit: 10_00,    // $10.00 — หยุดการใช้งาน
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### ลำดับการบังคับใช้

```
คำขอ ──▶ quotaCheck()
              │
              ├── อยู่ภายในขีดจำกัด?  ──▶ อนุญาต
              │
              └── เกินขีดจำกัด?  ──▶ 429 Too Many Requests
                                   พร้อมส่วนหัว Retry-After
```

### สแนปช็อตโควตา

ตาราง `quotaSnapshots` จัดเก็บ **สถานะโควตาในอดีต** สำหรับการวิเคราะห์แนวโน้ม:

| ฟิลด์ | คำอธิบาย |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | คีย์ที่กำลังติดตาม |
| `window` | "day" | "week" | "month" |
| `used` | ค่าใช้จ่ายที่ใช้ในช่วงเวลานี้ (เซนต์) |
| `limit` | ขีดจำกัด (เซนต์) |
| `resetAt` | เวลาที่ช่วงเวลาถูกรีเซ็ต |
| `createdAt` | เวลาที่บันทึกสแนปช็อต |

ระบบจะบันทึกสแนปช็อต **ในทุกคำขอ** ที่มีค่าใช้จ่าย > 0 และนำไปใช้เพื่อ:

- แสดงแถบความคืบหน้าของโควตาในแดชบอร์ด
- แสดงแผนภูมิแนวโน้มโควตาในช่วง 30 วัน
- ทริกเกอร์การแจ้งเตือนเมื่อการใช้งานใกล้ถึงขีดจำกัด

## REST API

### แสดงรายการบันทึกการใช้งาน

```bash

GET /api/usage?provider=openai&range=1d
```

### สืบค้นการวิเคราะห์การใช้งาน

ข้อมูลการใช้งานเข้าถึงได้ผ่านแดชบอร์ดหรือเครื่องมือ MCP ไม่ใช่ผ่านตำแหน่งข้อมูลสำหรับส่งออก REST โดยตรง การวิเคราะห์ที่พร้อมใช้งานมีดังนี้:

- **`/api/usage/analytics`** — เมตริกการใช้งานแบบรวม (จัดกลุ่มตามโมเดล ผู้ให้บริการ และคีย์)
- **`/api/usage/quota`** — สถานะโควตาปัจจุบันของแต่ละคีย์ API
- **`/api/usage/history`** — บันทึกประวัติคำขอ

## การเก็บรักษาและการล้างข้อมูล

ข้อมูลการใช้งานเพิ่มขึ้นประมาณ ~1-10KB ต่อคำขอ ซึ่งอาจมีขนาดมากเมื่อใช้งานในระดับใหญ่

### การตั้งค่าการเก็บรักษา

การเก็บรักษาประวัติการใช้งานสามารถกำหนดค่าได้ผ่าน Database Settings ใน UI หรือผ่าน `/api/settings/database`

ตามค่าเริ่มต้น ประวัติการใช้งานจะถูกเก็บไว้เป็นเวลา **90 วัน**

### การล้างข้อมูล

ระเบียนเก่าจะถูกล้างโดย `src/lib/db/cleanup.ts`:

- ถูกเรียกใช้โดยกระบวนการ cron เบื้องหลัง
- ลบระเบียนจาก `usage_history` ที่เก่ากว่าระยะเวลาการเก็บรักษาที่กำหนดไว้ในการตั้งค่า `usageHistory`

### การประมาณการพื้นที่จัดเก็บ

| อัตราคำขอ        | พื้นที่จัดเก็บ 30 วัน | พื้นที่จัดเก็บ 90 วัน |
| ---------------- | --------------------- | --------------------- |
| 100 คำขอ/วัน     | ~3MB                  | ~9MB                  |
| 1,000 คำขอ/วัน   | ~30MB                 | ~90MB                 |
| 10,000 คำขอ/วัน  | ~300MB                | ~900MB                |
| 100,000 คำขอ/วัน | ~3GB                  | ~9GB                  |

สำหรับปริมาณการรับส่งข้อมูลที่สูงมาก ควรพิจารณา:

- ลดระยะเวลาการเก็บรักษาผ่าน Database Settings
- ใช้ `aggregated_metrics` แทนระเบียนดิบ (สำหรับการวิเคราะห์เท่านั้น)

## เคล็ดลับการเพิ่มประสิทธิภาพด้านต้นทุน

### 1. ใช้โมเดลที่เหมาะสม

```bash
# คำตอบด่วน — ใช้โมเดลราคาถูกและรวดเร็ว
curl -d '{"model":"auto/fast","messages":[...]}'

# งานที่ซับซ้อน — ใช้โมเดลคุณภาพสูง
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. เปิดใช้งานแคช

การแคชพรอมต์ของ Anthropic ช่วยประหยัดค่าใช้จ่ายได้ **90% สำหรับบริบทที่ใช้ซ้ำ**:

```ts
// การแคชเป็นไปโดยอัตโนมัติ — เพียงใส่พรอมต์ระบบขนาดใหญ่เดิม
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // จะถูกแคชโดยอัตโนมัติ
  messages: [{ role: "user", content: "..." }],
});
```

### 3. ใช้การบีบอัด

การบีบอัดด้วย RTK + Caveman ช่วยประหยัดได้ **15-95% ในเซสชันที่ใช้เครื่องมือจำนวนมาก**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. กำหนดโควตาต่อคีย์

กำหนด `quotaLimit` เสมอเพื่อป้องกันค่าใช้จ่ายที่เพิ่มขึ้นอย่างควบคุมไม่ได้:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // จำกัดไว้ที่ $10/เดือน
```

### 5. ตรวจสอบผู้ใช้งานที่มีการใช้ทรัพยากรสูงสุด

ใช้แดชบอร์ดหรือ **`/api/usage/analytics`** เพื่อจัดกลุ่มตาม API key และเรียงลำดับตามค่าใช้จ่าย:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## การแก้ไขปัญหา

### "ค่าใช้จ่ายสูงกว่าที่คาดไว้"

1. ตรวจสอบ **`/api/usage/analytics?groupBy=model`** — ค้นหาโมเดลที่มีค่าใช้จ่ายสูง
2. ตรวจสอบ **`/api/usage/analytics?groupBy=apiKey`** — ค้นหาผู้ใช้งานที่มีการใช้งานสูง
3. ตรวจสอบว่าข้อมูลราคาปัจจุบันเป็นข้อมูลล่าสุด: `POST /api/pricing/sync`

### "ระเบียนหายไป"

- ตรวจสอบการตั้งค่าการเก็บรักษาของ DB ที่ Dashboard → Database → Cleanup — ระเบียนเก่าจะถูกลบโดยงานล้างข้อมูลตามรอบเวลา (`src/lib/db/cleanup.ts`)
- ตรวจสอบข้อผิดพลาดใน `src/lib/db/usage*.ts` — ความล้มเหลวในการเขียน DB จะถูกบันทึกในล็อก แต่จะไม่แสดงต่อผู้ใช้
- ตรวจสอบว่าคำขอไปถึง `chatCore` จริง — ตรวจสอบการกำหนดเส้นทางแบบผสมผสาน

### "ไม่มีการบังคับใช้โควตา"

- ตรวจสอบการตั้งค่า `quotaLimit` ของคีย์
- ตรวจสอบว่ากำหนด `quotaWindow` อย่างถูกต้อง
- ค้นหาระเบียน `quotaSnapshots` — ควรถูกสร้างขึ้นในทุกคำขอ
