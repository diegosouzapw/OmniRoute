OmniRoute มาพร้อมกับชุดคำสั่ง `setup-*` ที่กำหนดค่า CLI สำหรับการเขียนโค้ด
(Codex, Claude Code, OpenCode, Cline, …) ให้ใช้ OmniRoute เป็นแบ็กเอนด์ — ดังนั้น
เครื่องมือจะสื่อสารกับปลายทาง **เดียว** และ OmniRoute จะกำหนดเส้นทางไปยังผู้ให้บริการที่เหมาะสมพร้อม
การสลับไปใช้ตัวสำรองโดยอัตโนมัติ แต่ละคำสั่งจะอ่านแค็ตตาล็อกโมเดล **แบบสด** จาก OmniRoute
ที่กำลังทำงานอยู่ (ภายในเครื่องหรือระยะไกล) และเขียนไฟล์การกำหนดค่าของเครื่องมือนั้นลงในเครื่อง
**ของคุณ** คีย์ API จะถูกอ้างอิงผ่านตัวแปรสภาพแวดล้อมในทุกตำแหน่งที่เครื่องมือรองรับ
คำสั่งที่บันทึกไฟล์สภาพแวดล้อมเฉพาะของเครื่องมือไว้อย่างถาวรจะมีการระบุไว้ด้านล่าง

นอกจากนี้ยังมีตัวเรียกใช้งานแบบทั่วไป — `omniroute run <target>` — ซึ่งเรียกใช้งาน
`claude`, `codex`, `aider`, `goose`, `opencode`, `qwen` หรือ `gemini` พร้อมแทรก
ตัวแปรสภาพแวดล้อมที่ถูกต้อง โดยไม่เขียนการกำหนดค่าใดๆ เลย เป้าหมายและ
นามแฝงของเป้าหมายมาจากแมนิเฟสต์หลัก `bin/cli/cli-manifest.mjs`
(`claude-code|cc|anthropic`, `codex-cli|openai-codex|openai`, `goose-cli`,
`open-code`, `qwen-code`, `gemini-cli`) และ `omniroute completion` มีคำเป้าหมาย
ที่ได้มาจากแมนิเฟสต์เดียวกัน ตัวเรียกใช้งานแบบแยกตามเครื่องมือรุ่นเดิม —
`omniroute launch` (Claude Code) และ `omniroute launch-codex` (Codex) — ยังคง
พร้อมใช้งาน

การเริ่มต้นใช้งานผู้ให้บริการสามารถทำได้จากบริบทภายในเครื่อง/ระยะไกลเดียวกัน
คำสั่งที่เน้น API เป็นหลักด้านล่างจะแยกการยืนยันตัวตนสำหรับการจัดการออกจากข้อมูลประจำตัว
ของผู้ให้บริการ และจะไม่แสดงข้อมูลประจำตัวในเอาต์พุตแบบมีโครงสร้าง:

```bash
omniroute providers add glm --credential-env GLM_API_KEY --name work
omniroute providers import ./providers.json --dry-run --json
omniroute providers auth openai
omniroute providers edit <connection-id> --default-model glm/glm-5.2
omniroute providers remove <connection-id> --yes
```

สำหรับสคริปต์ ควรใช้ `--credential-stdin` หรือ `--credential-env` ส่วน `--credential`
ยังคงมีไว้สำหรับการใช้งานภายในเครื่องในสภาพแวดล้อมที่ควบคุมได้ `providers remove` ต้องใช้ `--yes`
บนเทอร์มินัลที่ไม่เป็นแบบโต้ตอบ และคำสั่งทั้งห้าจะใช้บริบทที่ทำงานอยู่หรือตัวเลือกส่วนกลาง
`--base-url`/`--api-key`

สำหรับการตั้งค่าพื้นฐานครั้งแรกแบบเขียนด้วยตนเองของการผสานการทำงานที่มีความสามารถครอบคลุมที่สุดสองรายการ โปรดดู
รายละเอียดเชิงลึกของแต่ละเครื่องมือ:

- [การกำหนดค่า Claude Code](./CLAUDE-CODE-CONFIGURATION.md)
- [การกำหนดค่า Codex CLI](./CODEX-CLI-CONFIGURATION.md)
- [โหมดระยะไกล](./REMOTE-MODE.md) — ควบคุม OmniRoute ระยะไกล (VPS / Tailnet) จากแล็ปท็อปของคุณ
- [VS Code Copilot Chat](./VSCODE-COPILOT.md) — ส่วนขยาย OmniCopilot ซึ่งยังสามารถเรียกใช้คำสั่ง
  `setup-*` เหล่านี้ให้คุณได้จากภายในเอดิเตอร์

## ตารางหลัก

ทุกคำสั่งจะใช้ **บริบทที่ทำงานอยู่** (ตั้งค่าด้วย `omniroute connect` โปรดดู
[โหมดระยะไกล](./REMOTE-MODE.md)) หรือแฟล็ก `--remote <url> --api-key <key>` ที่ระบุไว้อย่างชัดเจน
"ภายในเครื่องเทียบกับระยะไกล" ด้านล่างหมายถึง: หากไม่มีแฟล็ก คำสั่งจะกำหนดเป้าหมายไปที่ `http://localhost:20128`;
เมื่อใช้ `--remote` (หรือบริบทระยะไกลที่ทำงานอยู่) คำสั่งจะดึงแค็ตตาล็อกจาก
เซิร์ฟเวอร์นั้นและเขียนการกำหนดค่าลงในเครื่องภายในเครื่อง

หมายเหตุเกี่ยวกับแฟล็ก (ตรวจสอบแล้วจากซอร์สของคำสั่ง):

- `--remote <url>` — ดึงแค็ตตาล็อกจาก OmniRoute ระยะไกล (มีผลแทนที่ `--port`
  และบริบทที่ใช้งานอยู่) `--api-key <key>` ใช้ระบุข้อมูลรับรองสำหรับ
  เซิร์ฟเวอร์นั้น (ค่าเริ่มต้นคือ env var `OMNIROUTE_API_KEY` หรือโทเค็นของบริบทที่ใช้งานอยู่)
- `--only <patterns>` — สตริงย่อยที่คั่นด้วยจุลภาค; เก็บเฉพาะ ID โมเดลที่ตรงกัน
  (เช่น `--only glm,kimi`) ใช้ได้กับ `setup-codex`, `setup-claude`,
  `setup-opencode`, `setup-continue`, `setup-cursor`, `setup-crush`
- `--dry-run` — แสดงสิ่งที่จะถูกเขียนออกมาทุกประการโดยไม่แก้ไข
  ระบบไฟล์ ใช้ได้กับทุกคำสั่ง `setup-*` **ยกเว้น** `setup-cursor`
  (ซึ่งจะไม่เขียนไฟล์อยู่แล้ว)
- `--model <id>` — จำเป็นต้องระบุ (หรือเลือกแบบโต้ตอบ) สำหรับเครื่องมือที่ไม่มี
  การค้นหาโมเดลอัตโนมัติ ได้แก่ Cline, Kilo, Roo, Goose, Qwen, Aider, 5dive เครื่องมือเหล่านี้
  ยังรองรับ `--yes` สำหรับการทำงานแบบไม่โต้ตอบ (ซึ่งในกรณีนั้นจำเป็นต้องระบุ `--model`)
  `setup-opencode` รับ `--model` เพื่อตั้งค่าโมเดลระดับบนสุดเริ่มต้น
- `--model <id>` บน `omniroute run` เป็นไปตามการเชื่อมโยงรายเป้าหมายของ manifest
  (`bin/cli/cli-manifest.mjs`): **aider** จะได้รับ `--model openai/<id>` และ
  **opencode** จะได้รับ `--model omniroute/<id>` (คำนำหน้าจะถูกเพิ่มเฉพาะเมื่อ ID
  ยังไม่มีคำนำหน้าดังกล่าว); **qwen** และ **gemini** จะได้รับ ID โดยตรง;
  **claude** จะได้รับผ่าน `ANTHROPIC_MODEL`, **goose** ผ่าน `GOOSE_MODEL` และ
  **codex** ผ่านอาร์กิวเมนต์ `-c model_providers.omniroute.*` **Qwen เป็นเป้าหมายการรันเพียงตัวเดียว
  ที่บังคับว่าต้องระบุ `--model`** — `omniroute run qwen` ที่ไม่มีแฟล็กนี้จะจบการทำงานด้วย
  รหัส `2` พร้อมข้อผิดพลาดที่ระบุไว้อย่างชัดเจน
- `--port <port>` — พอร์ต OmniRoute ภายในเครื่อง (ค่าเริ่มต้นคือ `20128` และจะถูกละเว้นเมื่อตั้งค่า `--remote`)
  มีอยู่ในทุกคำสั่ง `setup-*` และตัวเรียกใช้งานทั้งสอง
- รหัสการจบการทำงานของ `omniroute run`: รหัสการจบการทำงานของ CLI ลูกจะถูกส่งต่อ
  โดยตรง; `2` = อาร์กิวเมนต์ไม่ถูกต้อง (เป้าหมายที่ไม่รองรับ, ไม่ได้ระบุ
  `--model` ที่จำเป็น, การป้องกันของคอนเทนเนอร์); `127` = ไบนารีเป้าหมายไม่ได้อยู่ใน `PATH`;
  `130`/`143`/`129` เมื่อการเรียกใช้งานสิ้นสุดโดย `SIGINT`/`SIGTERM`/`SIGHUP`;
  `1` = ความล้มเหลวอื่นขณะเรียกใช้งาน
- ตัวเรียกใช้งานทั้งสอง (`launch`, `launch-codex`) รองรับ `--profile <name>` เพื่อเลือก
  โปรไฟล์ที่เขียนโดย `setup-claude` / `setup-codex` รวมถึงส่งผ่านอาร์กิวเมนต์ไปยัง
  ไบนารี `claude` / `codex` ที่อยู่เบื้องหลัง

ตัวเลือกแบบโต้ตอบยังใช้ร่วมกันโดยสูตรการตั้งค่าต่าง ๆ:

```bash
# เลือกจากแค็ตตาล็อกโมเดลภายในเครื่องหรือระยะไกลที่ใช้งานอยู่ แล้วกำหนดค่าเป้าหมาย
omniroute configure claude
omniroute configure opencode --provider glm
omniroute configure qwen --model qwen/qwen3.8-max-preview --yes
```

ปัจจุบัน `configure` มอบหมายงานให้กับสูตรที่ผ่านการทดสอบสำหรับ `codex`, `claude`,
`opencode`, `qwen`, `aider`, `goose`, `cline`, `continue`, `kilo` และ `5dive`
รายการในแค็ตตาล็อกที่ใช้เฉพาะกับ IDE,
MITM และคู่มือเท่านั้น ยังคงต้องดำเนินการผ่าน `setup-*`/ขั้นตอนแบบกำหนดเองอย่างชัดเจน และ
จะไม่ถูกนำเสนอเป็นเป้าหมายที่เรียกใช้งานได้

> `setup-opencode` คือการผสานรวม OpenCode แบบ **น้ำหนักเบาที่เข้ากันได้กับ openai**
> นอกจากนี้ยังมีการผสานรวมผ่านปลั๊กอินที่มีความสามารถมากกว่า — `omniroute setup opencode` — ซึ่ง
> ติดตั้ง `@omniroute/opencode-plugin` ทั้งสองเป็นคนละคำสั่งกัน; ตาราง
> ด้านบนอธิบาย `setup-opencode`
>
> ปลั๊กอินมีสองแพ็กเกจ แพ็กเกจละหนึ่งเวอร์ชันหลักของ OpenCode เนื่องจาก loader ทั้งสอง
> ต้องการ entrypoint ที่แตกต่างกัน:
> `@omniroute/opencode-plugin` สำหรับ OpenCode v1 และ
> `@omniroute/opencode-plugin-v2` สำหรับ OpenCode v2 แพ็กเกจ v2 เป็นแพ็กเกจใหม่
> (`0.1.0`) และเป็นไปตามสัญญาของโฮสต์ที่ยังมีการเปลี่ยนแปลงอยู่ ดังนั้นจึงอ่าน
> รูปแบบที่ OpenCode ใส่ไว้ในฉบับร่างของแค็ตตาล็อก แทนที่จะสมมติรูปแบบขึ้นมา ติดตั้ง
> โดยเพิ่มรายการ `plugins` ลงใน `opencode.json`; `omniroute setup opencode`
> ยังคงติดตั้งแพ็กเกจ v1 ตัวเลือกและลำดับการค้นหาข้อมูลรับรองอยู่ใน
> README ของแพ็กเกจ

## การใช้งานภายในเครื่อง

เมื่อ OmniRoute ทำงานอยู่ที่ `localhost:20128` เพียงเรียกใช้คำสั่งตั้งค่าสำหรับ
เครื่องมือของคุณ แค็ตตาล็อกจะถูกดึงมาจากเซิร์ฟเวอร์ภายในเครื่อง

```bash
# Codex: เขียนโปรไฟล์สำหรับแต่ละโมเดลที่ตรงกันลงใน ~/.codex/
omniroute setup-codex
codex --profile glm52            # ใช้โปรไฟล์ที่สร้างขึ้น

# Claude Code: เขียนโปรไฟล์แยกตามโมเดล แล้วเปิดใช้งานหนึ่งโปรไฟล์
omniroute setup-claude
omniroute launch --profile glm52

# OpenCode: เขียนผู้ให้บริการที่เข้ากันได้กับ OpenAI พร้อมโมเดลทั้งหมดในแค็ตตาล็อก
omniroute setup-opencode
export OMNIROUTE_API_KEY=sk-...  # อ้างอิงผ่าน {env:OMNIROUTE_API_KEY} โดยไม่บันทึกลงดิสก์
opencode -m omniroute/glm/glm-5.2 "..."

# เครื่องมือที่ไม่มีการค้นหาอัตโนมัติจำเป็นต้องระบุโมเดลอย่างชัดเจน:
omniroute setup-aider --model glm/glm-5.2
omniroute setup-qwen --model qwen/qwen3.8-max-preview

# แสดงตัวอย่างโดยไม่เขียนข้อมูลใดๆ:
omniroute setup-continue --dry-run
```

เปิดใช้งานโดยไม่เขียนการกำหนดค่าใดๆ เลย (แทรกผ่านตัวแปรสภาพแวดล้อมเท่านั้น):

```bash
omniroute launch                 # Claude Code → OmniRoute ภายในเครื่อง
omniroute launch-codex           # Codex CLI → OmniRoute ภายในเครื่อง
omniroute launch-codex --profile glm52
omniroute run claude --model openai/gpt-5.4
omniroute run codex --model openai/gpt-5.4 --dry-run --json
omniroute run aider --model glm/glm-5.2 -- --message "reply OK"
omniroute run goose --model glm/glm-5.2
omniroute run opencode --model glm/glm-5.2 -- run "reply OK"
omniroute run qwen --model glm/glm-5.2 -- -p "reply OK"
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "reply OK"

# พาธคำสั่งแบบชัดเจน: ส่งต่อทุกอย่างที่อยู่หลัง --
omniroute run claude -- --print-system-prompt "review this diff"
```

## การใช้งานระยะไกล

กำหนดให้คำสั่งตั้งค่าใดๆ เชื่อมต่อไปยัง OmniRoute ระยะไกลด้วย `--remote` + `--api-key`
แค็ตตาล็อกจะถูกดึงมาจากระบบระยะไกล ส่วนการกำหนดค่าจะถูกเขียนลงในเครื่องของคุณ

```bash
# ใช้ OpenCode กับ VPS ระยะไกล โดยเก็บไว้เฉพาะโมเดล glm/kimi
omniroute setup-opencode --remote http://192.168.0.15:20128 --api-key oma_live_xxx \
  --only glm,kimi
opencode -m omniroute/glm/glm-5.2 "..."   # ส่งออก OMNIROUTE_API_KEY ก่อน

# โปรไฟล์ Codex จากแค็ตตาล็อกระยะไกล
omniroute setup-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx

# เปิดใช้ CLI กับระบบระยะไกลโดยตรง
omniroute launch       --remote http://192.168.0.15:20128 --api-key oma_live_xxx
omniroute launch-codex --remote http://192.168.0.15:20128 --api-key oma_live_xxx
```

แทนที่จะส่ง `--remote`/`--api-key` ทุกครั้ง ให้เข้าสู่ระบบหนึ่งครั้ง แล้วปล่อยให้
**บริบทที่ใช้งานอยู่** ระบุค่าเหล่านี้โดยอัตโนมัติ:

```bash
omniroute connect 192.168.0.15        # สร้างโทเค็นแบบจำกัดขอบเขตและจัดเก็บบริบท
omniroute setup-codex                 # ← ตอนนี้ใช้แค็ตตาล็อกระยะไกล
omniroute setup-opencode              # ← เช่นเดียวกัน
omniroute launch                      # ← Claude Code กับระบบระยะไกล
```

ดูการจัดการบริบท ขอบเขต และโทเค็นได้ที่ [โหมดระยะไกล](./REMOTE-MODE.md)

## ฝูงเอเจนต์ 5dive

[5dive](https://5dive.ai) ใช้งานฝูงเอเจนต์เขียนโค้ดที่ทำงานระยะยาว โดยแต่ละเอเจนต์เป็น
ยูนิต systemd ภายใต้ผู้ใช้ Unix ของตนเอง ตัวมันเองไม่ใช่ CLI สำหรับเขียนโค้ด ดังนั้นจึง
ไม่มีสิ่งใดให้ `omniroute run` เปิดใช้งาน — `5dive` เป็นเป้าหมายสำหรับ **การกำหนดค่าเท่านั้น**

```bash
omniroute configure 5dive --model failover-demo --yes
omniroute setup-5dive --model failover-demo --auth-profile omniroute --agent worker1
```

ทั้งสองรูปแบบจะเขียน **โปรไฟล์การยืนยันตัวตน** ของ 5dive หนึ่งโปรไฟล์ จากนั้นทุกที่นั่ง
`claude` ที่ผูกกับโปรไฟล์ดังกล่าวจะสื่อสารกับ OmniRoute เป้าหมายนี้มีลักษณะเฉพาะสามประการ:

- **ต้องทำงานบนโฮสต์ของฝูงในฐานะ root** คำสั่งย่อยของ 5dive ทำงานกับยูนิต systemd
  ภายในเครื่องและไดเรกทอรีสถานะที่ root เป็นเจ้าของ จึงไม่มีโหมดระยะไกล สูตรจะเรียกตัวเองใหม่ผ่าน
  `sudo` เมื่อยังไม่ได้ทำงานในฐานะ root (`--no-sudo` จะปิดการทำงานดังกล่าวและพิมพ์
  คำสั่งออกมาแทน)
- **ปลายทางต้องเป็น `https://` เว้นแต่ว่าจะเป็น loopback** API key ของเอเจนต์
  จะถูกส่งไปกับ URL ดังกล่าวในทุกคำขอ และ 5dive จะปฏิเสธปลายทางนอกเครื่องที่เป็นข้อความธรรมดา
  ที่อยู่ LAN ส่วนตัวก็ไม่ได้รับการยกเว้น
- **การปักหมุดโมเดลของแต่ละที่นั่งมีลำดับความสำคัญเหนือกว่าโปรไฟล์** โปรไฟล์มี
  `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` แต่ที่นั่งที่ยังคงปักหมุดไว้กับ
  model id มาตรฐานจะล้มเหลวตั้งแต่รอบแรกพร้อมข้อความ _"There's an issue with the selected model"_.
  ส่ง `--agent <name>` (ใช้ซ้ำได้) เพื่อปักหมุดที่นั่งด้วย หากไม่ส่ง สูตรจะพิมพ์
  คำสั่งออกมา

API key จะถูกส่งให้ 5dive ทาง **stdin** (`--api-key=-`) ดังนั้นจึงไม่ปรากฏใน
เอาต์พุตของ `ps`

การกำหนดให้โปรไฟล์ชี้ไปยัง **คอมโบ** ของ OmniRoute แทนที่จะเป็นโมเดลเดียว คือสิ่งที่
ทำให้ฝูงสามารถสลับผู้ให้บริการเมื่อเกิดข้อผิดพลาดได้: เมื่อปลายทางหลักหยุดทำงานโดยสิ้นเชิง
ระหว่างรอบในการทำงานที่บันทึกไว้ใน
[#11578](https://github.com/diegosouzapw/OmniRoute/issues/11578) เอเจนต์ได้ดำเนิน
ขั้นตอนที่เหลือให้เสร็จผ่านระบบสำรองโดยไม่แสดงเหตุขัดข้องให้ผู้ใช้เห็น

## การเก็บ dependency แบบเนทีฟไว้เมื่ออัปเดต: `--include=optional`

เมื่อคุณอัปเดตด้วย `omniroute update` (หลังจากยืนยัน หรือใช้ `--apply`)
OmniRoute จะเรียกใช้การติดตั้งโดยมี `--include=optional` รวมอยู่แล้ว:

```bash
npm install -g omniroute@latest --include=optional
```

นี่ **ไม่ใช่** flag ที่คุณต้องส่งให้ `omniroute update` — ตัวอัปเดตจะใช้ค่านี้
เสมอ ซึ่งรับประกันว่า `optionalDependencies` (`better-sqlite3`, `keytar`,
`tls-client`, สแตก SLM ของ LLMLingua) จะยังคงอยู่หลังการอัปเดต แม้ว่าการกำหนดค่า npm ของคุณ
จะตั้งค่า `omit=optional` ไว้ ซึ่งหากไม่มีการตั้งค่านี้จะทำให้ไดรเวอร์ SQLite แบบเนทีฟ
และ binding สำหรับพวงกุญแจของระบบปฏิบัติการถูกลบออกไปโดยไม่มีการแจ้งเตือน หากต้องการดูตัวอย่างคำสั่งที่แน่นอนโดยไม่ดำเนินการจริง:

```bash
omniroute update --dry-run
# [DRY RUN] จะเรียกใช้: npm install -g omniroute@latest --include=optional
```

flag อื่นๆ ของ `omniroute update` (ตรวจสอบแล้วจากซอร์สโค้ด): `--check` (ออกด้วยรหัส 1 หาก
ล้าสมัย), `--apply` (ติดตั้งโดยไม่ถามยืนยัน), `--changelog`, `--no-backup`,
`--yes`

## Google Gemini CLI ผ่าน `omniroute run gemini`

ข้อกำหนดการทำงานได้รับการตรวจสอบเทียบกับ `@google/gemini-cli` 0.50.0: CLI รองรับ
`GOOGLE_GEMINI_BASE_URL` และส่ง `POST /v1beta/models/<model>:generateContent`
(รวมถึง `:streamGenerateContent?alt=sse`) ไปยัง URL ดังกล่าว — ซึ่งตรงกับอินเทอร์เฟซ Gemini
แบบเนทีฟของ OmniRoute (`/v1beta`) อย่างแม่นยำ `omniroute run gemini` จะเชื่อมต่อค่าเหล่านี้ให้โดยอัตโนมัติ:

- `GOOGLE_GEMINI_BASE_URL` → Base URL ของ OmniRoute ที่ใช้งานอยู่ (รูท ไม่มี `/v1`);
- `GEMINI_API_KEY` → ข้อมูลรับรอง OmniRoute ที่ได้รับการแก้ค่าแล้ว (จากออปชัน/env/context);
- **`GEMINI_CLI_HOME` ชั่วคราวที่แยกออกจากระบบหลัก** ซึ่ง `.gemini/settings.json`
  จะเลือกการยืนยันตัวตนแบบ `gemini-api-key` เพื่อไม่ให้เซสชัน Google OAuth (Code Assist)
  ที่จัดเก็บไว้มาแทนที่การเปิดใช้งานซึ่งชี้ไปยัง OmniRoute — และจะถูกลบหลังจากออก;
- **การรักษาความสะอาดของ env**: env ของโปรเซสลูกจะถูกลบค่า `GOOGLE_API_KEY`,
  `GOOGLE_GENAI_USE_VERTEXAI` และ `GOOGLE_GENAI_USE_GCA` (ซึ่งจะเปลี่ยนเส้นทาง
  การยืนยันตัวตนไปยัง Vertex/Code Assist) และกำหนดค่า `GEMINI_DEFAULT_AUTH_TYPE=gemini-api-key`
  เป็นกลไกสำรองอีกชั้นหนึ่ง — เป้าหมาย `run` อื่นๆ จะได้รับ
  การจัดการแบบเดียวกันสำหรับตัวแปรที่ขัดแย้งกันของตน;
- การแทรก `--model <id>` จาก `--provider`/`--model`

```bash
omniroute run gemini --model glm/glm-5.2 -- --skip-trust -p "hello"
```

กลไกป้องกัน workspace-trust ของ Gemini ยังคงมีผลในโหมด headless — คุณต้องส่ง
`--skip-trust` (หรือกำหนดให้เชื่อถือไดเรกทอรีแบบโต้ตอบ) ด้วยตนเอง ตัว launcher
จงใจไม่ข้ามกลไกนี้ Launcher นี้แยกต่างหากจาก **การลงทะเบียน ACP**
(`src/lib/acp/registry.ts`, `gemini --acp`) ซึ่งยังคงเป็น
การผสานรวมโปรโตคอลเอเจนต์สำหรับ `/dashboard/acp-agents`

## การทดสอบ Smoke กับระบบจริง (ต้องเปิดใช้เอง)

การทดสอบการถดถอยของแผนการเรียกใช้แบบกำหนดผลลัพธ์แน่นอนทำงานใน CI (`tests/unit/cli/run-command.test.ts`,
`tests/unit/cli/run-execution.test.ts`) หากต้องการตรวจสอบไบนารีจริงกับเซิร์ฟเวอร์
OmniRoute จริง มีชุดทดสอบที่ต้องเปิดใช้เองอยู่ที่
`tests/integration/upstream-cli-smoke.int.test.ts` โดยจะไม่ทำงานโดยอัตโนมัติ
(การทดสอบย่อยทุกรายการจะถูกข้าม เว้นแต่กำหนด `RUN_CLI_SMOKE=1`) ส่งข้อมูลรับรองผ่านชื่อ
ตัวแปรสภาพแวดล้อม (ไม่ส่งค่าจริงโดยตรง) ปกปิดสตริงที่มีรูปแบบคล้ายคีย์จากเอาต์พุตใดๆ ที่บันทึกไว้ ข้าม
เป้าหมายที่ไม่ได้ติดตั้งไบนารี และจำแนกความล้มเหลวเป็น
การยืนยันตัวตน / อัปสตรีม / การกำหนดค่า แทนการใช้ค่าบูลีนเพียงอย่างเดียว:

```bash
RUN_CLI_SMOKE=1 \
OMNIROUTE_SMOKE_BASE_URL="http://localhost:20128" \
OMNIROUTE_SMOKE_MODEL="<provider/model>" \
OMNIROUTE_SMOKE_API_KEY_ENV="OMNIROUTE_API_KEY" \
node --import tsx/esm --test tests/integration/upstream-cli-smoke.int.test.ts
```

ตัวเลือกเพิ่มเติม: `OMNIROUTE_SMOKE_TARGETS="codex,opencode,qwen"` ใช้จำกัดเป้าหมายในการทดสอบ;
`OMNIROUTE_SMOKE_TIMEOUT_MS` ใช้แทนที่ระยะหมดเวลา 120 วินาทีต่อเป้าหมาย
