คู่มือนี้ครอบคลุมการเพิ่มบัญชี Kiro (ผู้ช่วยเขียนโค้ด AI ที่โฮสต์โดย AWS) ลงใน OmniRoute
โดยเน้นการใช้งานหลายบัญชีพร้อมกันโดยไม่ให้เกิดข้อขัดแย้งของเซสชัน

---

## ข้อมูลเบื้องต้น: เหตุใดบัญชี Kiro จึงอาจขัดแย้งกัน

แบ็กเอนด์ของ Kiro ใช้การลงทะเบียนไคลเอนต์ AWS SSO OIDC เพื่อติดตามเซสชันที่ใช้งานอยู่
ข้อจำกัดสำคัญคือ: **การลงทะเบียนไคลเอนต์ OIDC แต่ละรายการรองรับเซสชันที่ใช้งานอยู่
ได้ครั้งละหนึ่งเซสชันเท่านั้น** เมื่ออุปกรณ์หรือผู้ใช้รายที่สองยืนยันตัวตนโดยใช้
ไคลเอนต์ที่ลงทะเบียนเดียวกัน แบ็กเอนด์จะทำให้รีเฟรชโทเค็นของบัญชีแรกใช้การไม่ได้

นี่เป็นกลไกเดียวกับที่ทำให้เกิดปัญหาเมื่อเรียกใช้ `kiro-cli login` บน
เครื่องที่มีบัญชี Kiro อื่นลงชื่อเข้าใช้อยู่แล้ว กล่าวคือ การเข้าสู่ระบบครั้งใหม่จะเพิกถอน
โทเค็นของบัญชีแรก

---

## OmniRoute แก้ปัญหานี้อย่างไร (v3.8.0+)

ตั้งแต่ v3.8.0 เป็นต้นไป OmniRoute จะเรียก `registerClient()` (AWS SSO OIDC) ระหว่างการนำเข้า
การเชื่อมต่อ Kiro ทุกครั้ง ซึ่งทำให้การเชื่อมต่อ OmniRoute แต่ละรายการมีการลงทะเบียนไคลเอนต์ OIDC
เฉพาะของตนเอง เนื่องจากการลงทะเบียนไคลเอนต์แต่ละรายการแยกจากกัน การรีเฟรชหรือ
ยืนยันตัวตนใหม่สำหรับบัญชีหนึ่งจึงไม่ส่งผลต่อรีเฟรชโทเค็นของบัญชีอื่น

การแยกเซสชันนี้ใช้กับวิธีนำเข้าด้วยรีเฟรชโทเค็น ส่วนการยืนยันตัวตนด้วย API key จะหลีกเลี่ยง
เซสชันรีเฟรช OIDC โดยสิ้นเชิง:

| วิธีนำเข้า                                  | สถานะการแยกเซสชัน                                                                              |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| โฟลว์ device-code ของ AWS Builder ID / IDC  | แยกจากกันตั้งแต่เริ่มใช้โฟลว์ device-code                                                      |
| **Import Token** (วางรีเฟรชโทเค็นด้วยตนเอง) | แยกจากกันตั้งแต่ v3.8.0                                                                        |
| **การเข้าสู่ระบบด้วย Google / GitHub**      | แยกจากกันตั้งแต่ v3.8.0                                                                        |
| **Auto-Import** (SQLite ของ kiro-cli)       | แยกจากกันตั้งแต่ v3.8.0 (เส้นทาง SQLite แยกอยู่แล้ว และขณะนี้ SSO-cache สำรองก็แยกแล้วเช่นกัน) |
| **API Key** (คีย์ CodeWhisperer ระยะยาว)    | ไม่มีเซสชันรีเฟรช โดยคีย์จะได้รับการตรวจสอบและจัดเก็บเป็นข้อมูลรับรองแบบ bearer                |

## หมายเหตุการย้ายข้อมูลสำหรับการเชื่อมต่อที่สร้างก่อน v3.8.0

การเชื่อมต่อที่นำเข้าก่อน v3.8.0 ไม่มีการลงทะเบียนไคลเอนต์ OIDC เฉพาะ
จัดเก็บไว้ใน `providerSpecificData` การเชื่อมต่อเหล่านี้ยังคงทำงานต่อไปได้ แต่ใช้
เอนด์พอยต์รีเฟรชสำหรับการยืนยันตัวตนผ่านโซเชียลร่วมกัน ซึ่งหมายความว่าการเชื่อมต่อดังกล่าวสองรายการ
ยังคงทำให้โทเค็นของอีกฝ่ายใช้การไม่ได้

**เพื่อให้แยกจากกัน:** ลบการเชื่อมต่อเก่าออกจาก **Dashboard → Providers** และ
นำเข้าใหม่โดยใช้โฟลว์นำเข้าที่รองรับ การเชื่อมต่อที่สร้างขึ้นใหม่ทั้งหมดจะ
ได้รับการลงทะเบียนไคลเอนต์ของตนเองโดยอัตโนมัติ

## การเพิ่มบัญชี Kiro สองบัญชีเพื่อใช้งานควบคู่กัน

### ข้อกำหนดเบื้องต้น

- OmniRoute v3.8.0 หรือใหม่กว่า
- บัญชี Kiro ที่ใช้งานได้ (อีเมล + รหัสผ่าน หรือเข้าสู่ระบบด้วย Google หรือ GitHub)
- บัญชี Kiro บัญชีที่สอง (ไม่บังคับ)

### ขั้นตอนที่ 1: นำเข้าบัญชีแรก

1. เปิด **Dashboard → Providers → Add Provider → Kiro**
2. เลือกหนึ่งในตัวเลือกต่อไปนี้:
   - **Import Token** — วางรีเฟรชโทเค็นที่ขึ้นต้นด้วย `aorAAAAAG`
   - **API Key** — วาง API key ของ Kiro / CodeWhisperer แบบใช้งานระยะยาว
   - **การเข้าสู่ระบบด้วย Google / GitHub** — ดำเนินการตามโฟลว์ OAuth ในเบราว์เซอร์ให้เสร็จสิ้น
   - **Auto-Import** — คลิกปุ่ม แล้ว OmniRoute จะอ่านข้อมูลรับรองจาก
     ฐานข้อมูล kiro-cli ภายในเครื่องหรือ `~/.aws/sso/cache`
3. การเชื่อมต่อจะได้รับการบันทึก โฟลว์รีเฟรชโทเค็นจะลงทะเบียนไคลเอนต์
   OIDC เฉพาะโดยอัตโนมัติ ส่วนโฟลว์ API key จะตรวจสอบคีย์กับ AWS และไม่จัดเก็บรีเฟรชโทเค็น

### ขั้นตอนที่ 2: นำเข้าบัญชีที่สอง

ทำขั้นตอนที่ 1 ซ้ำสำหรับบัญชีที่สอง เนื่องจากการนำเข้าแต่ละครั้งสร้างการลงทะเบียนไคลเอนต์ OIDC
แยกต่างหาก การเชื่อมต่อทั้งสองจึงแยกจากกันอย่างสมบูรณ์

### ขั้นตอนที่ 3: ตรวจสอบว่าการเชื่อมต่อทั้งสองทำงานอยู่

1. **Dashboard → Providers** — การเชื่อมต่อ Kiro ทั้งสองควรแสดงสถานะ **Active**
2. **Dashboard → Health** — การเชื่อมต่อทั้งสองควรผ่านการตรวจสอบสถานะโทเค็น

### ขั้นตอนที่ 4: ใช้คอมโบเพื่อกำหนดเส้นทางระหว่างบัญชี

สร้างคอมโบโดยใช้การเชื่อมต่อทั้งสองเป็นปลายทาง เพื่อกระจายโหลดหรือสลับไปใช้อีกบัญชีเมื่อบัญชีหนึ่งใช้งานไม่ได้:

```
kiro/kiro-dev → kiro/kiro-pro
```

ดู [FEATURES.md](./FEATURES.md) และเอกสารประกอบการกำหนดเส้นทางสำหรับการตั้งค่าคอมโบ

## ผู้ใช้ Enterprise / IDC

สำหรับบัญชี AWS IAM Identity Center (IDC) ให้ใช้โฟลว์ **AWS Builder ID / IDC device-code**
จาก **Dashboard → Providers → Kiro → Device Code** โฟลว์ device-code
ถูกแยกออกจากกันอย่างสมบูรณ์มาโดยตลอด การเชื่อมต่อเหล่านี้ไม่จำเป็นต้องนำเข้าใหม่

ผู้ใช้ Enterprise ที่ใช้งานในรีเจียน AWS ที่ไม่ใช่ค่าเริ่มต้นสามารถระบุรีเจียนเมื่อ
นำเข้าผ่าน Import Token API:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

ฟิลด์ `region` จะมีค่าเริ่มต้นเป็น `us-east-1` หากไม่ได้ระบุ

## โฟลว์การนำเข้า API Key

การยืนยันตัวตนด้วย API key ใช้สำหรับข้อมูลรับรอง bearer ของ Kiro / AWS CodeWhisperer ที่มีอายุการใช้งานยาวนาน โดย
ไม่ใช้การรีเฟรช OAuth จึงหลีกเลี่ยงการทำให้เซสชัน OIDC ที่ใช้ร่วมกันไม่สามารถใช้งานได้

### Dashboard

1. เปิด **Dashboard -> Providers -> Kiro**
2. เลือก **API Key**
3. วาง API key และระบุรีเจียน AWS หรือไม่ก็ได้ (`us-east-1` เป็นค่าเริ่มต้น)
4. OmniRoute จะตรวจสอบความถูกต้องของคีย์และบันทึกการเชื่อมต่อ

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### สัญญาภายในระบบ

เส้นทาง API จะตรวจสอบความถูกต้องของคีย์โดยเรียก `KiroService.validateApiKey()` ซึ่ง
ใช้ `ListAvailableProfiles` กับ endpoint ของ CodeWhisperer/Amazon Q ที่ตรงกับรีเจียน
และค้นหา `profileArn`

การเชื่อมต่อที่บันทึกไว้ใช้:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

ขณะรันไทม์ `KiroExecutor.buildHeaders()` จะส่งคีย์ในรูปแบบ
`Authorization: Bearer <key>` และเพิ่ม `tokentype: API_KEY` การเรียกข้อมูลโควตา/โปรไฟล์
จะใช้ตัวระบุเดียวกัน เพื่อให้ AWS ปฏิบัติต่อ bearer ดังกล่าวเป็น API key ที่มีอายุการใช้งานยาวนาน แทนที่จะเป็น
โทเค็นการเข้าถึง OIDC หรือโทเค็นจากโซเชียล

## การหมดอายุของไคลเอ็นต์ OIDC

โดยทั่วไป ไคลเอ็นต์สาธารณะของ AWS SSO OIDC จะหมดอายุหลังจาก 90 วัน
(`clientSecretExpiresAt`) OmniRoute จะจัดเก็บการประทับเวลานี้ไว้ใน `providerSpecificData`
เพื่อให้สามารถสังเกตการณ์ได้ หากการเชื่อมต่อหยุดรีเฟรชหลังจากประมาณ 90 วัน ให้นำเข้า
การเชื่อมต่อใหม่เพื่อรับการลงทะเบียนไคลเอ็นต์ OIDC ชุดใหม่ การลงทะเบียนใหม่โดยอัตโนมัติเมื่อ
หมดอายุถูกติดตามไว้เป็นการปรับปรุงในอนาคต

การเชื่อมต่อด้วย API key ไม่มีการหมดอายุของไคลเอ็นต์ OIDC เนื่องจากไม่ได้รีเฟรช
ผ่าน AWS SSO OIDC

## การแก้ไขปัญหา

### บัญชีที่สองถูกนำออกจากระบบอยู่เรื่อยๆ

- ตรวจสอบการเชื่อมต่อทั้งสองรายการใน **Dashboard → Providers** และยืนยันว่าแต่ละรายการแสดง
  `clientId` ที่ไม่ใช่ null ใน JSON ดิบ (ดูได้ผ่านไอคอนข้อมูล) หากการเชื่อมต่อใดไม่มี
  `clientId` แสดงว่าการเชื่อมต่อนั้นถูกนำเข้าก่อน v3.8.0 — ให้นำเข้าใหม่

### การนำเข้าล้มเหลวพร้อมข้อความ "Token validation failed"

- ตรวจสอบให้แน่ใจว่า refresh token ขึ้นต้นด้วย `aorAAAAAG`
- ตรวจสอบให้แน่ใจว่า OmniRoute สามารถเข้าถึง `https://oidc.us-east-1.amazonaws.com` (หรือรีเจียน
  ที่กำหนดค่าไว้) หากคุณอยู่เบื้องหลังพร็อกซีขององค์กร ให้ตั้งค่าพร็อกซีระดับ provider ใน
  **Dashboard → Settings → Proxies**

### การนำเข้า API key ล้มเหลว

- ยืนยันว่าคีย์เป็น API key ของ Kiro / CodeWhisperer ไม่ใช่ refresh token
- ยืนยันว่ารีเจียน AWS ตรงกับคีย์/บัญชี โดย `us-east-1` เป็นค่าเริ่มต้น
- คีย์ต้องสามารถเรียก `ListAvailableProfiles` ได้ มิฉะนั้น OmniRoute จะไม่สามารถ
  ค้นหา `profileArn` ที่จำเป็นได้
