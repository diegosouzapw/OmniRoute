คู่มือฉบับสมบูรณ์สำหรับการใช้ Codex CLI โดยกำหนดให้ OmniRoute เป็นแบ็กเอนด์ที่เข้ากันได้กับ OpenAI

---

> **TOML เป็นรูปแบบเดียวที่ใช้งานได้จริง** Codex รุ่นใหม่จะอ่านเฉพาะ
> `~/.codex/config.toml` เท่านั้น (ตรวจสอบกับ codex-cli 0.147.0 แล้ว: `codex --help`
> ระบุว่า `-c/--config` ใช้แทนค่าการกำหนดค่าที่ "โหลดจาก `~/.codex/config.toml`")
> ส่วน `~/.codex/config.yaml` แบบเก่าเป็นของ npm CLI รุ่นเดิมและจะถูกละเว้นโดยไม่มีการแจ้งเตือน
> ตัวสร้างการกำหนดค่าจากแดชบอร์ด (`/api/cli-tools/apply`, เครื่องมือ `codex`) จะเขียน TOML
> ด้วยการผสานอย่างระมัดระวัง — คีย์ที่มีอยู่และบล็อกของผู้ให้บริการรายอื่นจะยังคงอยู่
> คีย์ API จะถูกเก็บไว้ใน `OMNIROUTE_API_KEY` (ไม่ถูกเขียนลงในไฟล์) และหากยังมี
> `config.yaml` รุ่นเดิมหลงเหลืออยู่ ระบบจะรายงานเป็นหมายเหตุสำหรับการย้ายข้อมูลโดยไม่แก้ไขไฟล์นั้น

## config.toml ที่พร้อมคัดลอกไปใช้

แทนที่ `<YOUR_HOST>` และ `<YOUR_KEY>` ด้วยค่าของคุณ:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ขีดจำกัดการจัดเก็บประวัติต่อการเรียกใช้เครื่องมือหนึ่งครั้ง

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc หรือ ~/.zshrc — ค่าคีย์จริง ห้ามใส่ไว้ใน config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex ที่รวมอยู่ภายในแอป ChatGPT

หากคุณติดตั้ง Codex ผ่านแอป ChatGPT บนเดสก์ท็อป ไบนารี `codex` อาจมีอยู่
เฉพาะภายในชุดแอปและยังไม่ได้อยู่ใน `PATH` ของเชลล์ ให้เพิ่มไดเรกทอรี
ทรัพยากรลงในไฟล์เริ่มต้นของเชลล์:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

เปิดเชลล์ใหม่ แล้วตรวจสอบ:

```bash
command -v codex
codex --version
```

### OmniRoute ภายในเครื่องที่ไม่ใช้การยืนยันตัวตน: ใช้คีย์ตัวแทนได้

Codex จะตรวจสอบว่าตัวแปรสภาพแวดล้อมที่ระบุโดย `env_key` มีอยู่
**ก่อนที่** คำขอแรกจะออกจาก CLI หากอินสแตนซ์ OmniRoute **ภายในเครื่อง**
ของคุณไม่ต้องใช้การยืนยันตัวตน ก็สามารถใช้ค่าตัวแทนใดๆ ที่ไม่ใช่ค่าว่างได้:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

ให้ใช้คีย์จริงแทนเมื่อเซิร์ฟเวอร์ OmniRoute ของคุณมีการป้องกันหรืออยู่บนระบบระยะไกล

> **ตัวเลือกโฮสต์ที่ใช้บ่อย**
>
> | การเข้าถึง     | URL                           |
> | -------------- | ----------------------------- |
> | เครือข่ายภายใน | `http://192.168.0.1:20128/v1` |
> | Tailscale      | `http://100.x.x.x:20128/v1`   |
> | ลูปแบ็ก        | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — เหตุใดจึงใช้ได้กับทุกรุ่นโมเดล

Codex CLI เลิกสนับสนุน `wire_api = "chat"` (Chat Completions) ในเดือนกุมภาพันธ์ 2026 และขณะนี้ **กำหนดให้ต้องใช้** `wire_api = "responses"` (OpenAI Responses API) การตั้งค่า `wire_api = "chat"` จะทำให้โปรแกรมหยุดทำงานทันทีระหว่างการเริ่มต้นตั้งแต่ v0.138 เป็นต้นไป

ผู้ให้บริการหลายราย รวมถึง GLM และ Kimi ยังคงเปิดให้ใช้งานเฉพาะเอนด์พอยต์ Chat Completions เท่านั้น ขณะนี้ DeepSeek V4 เปิดให้ใช้งาน Responses API แบบเนทีฟควบคู่กับเอนด์พอยต์ที่เข้ากันได้กับ Anthropic แล้ว โดย OmniRoute จะใช้ Responses เป็นค่าเริ่มต้น และอนุญาตให้การเชื่อมต่อ DeepSeek แต่ละรายการเลือกความเข้ากันได้กับ Anthropic ได้

**OmniRoute จัดการเรื่องนี้ให้โดยอัตโนมัติ:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute เลือกโปรโตคอลแบบเนทีฟของผู้ให้บริการและแปลงให้เมื่อจำเป็น
    → POST /responses (DeepSeek V4) หรือ /chat/completions (Mistral / GLM / Kimi / อื่นๆ)
```

เมื่อใช้ OmniRoute คุณไม่จำเป็นต้องมีพร็อกซีแปลงข้อมูลแยกต่างหาก **ทุกรุ่นโมเดลใช้ `wire_api = "responses"`** — OmniRoute จะจัดการส่วนที่เหลือให้

> **`wire_api` เป็นค่าเริ่มต้น** — ฟิลด์นี้มีค่าเริ่มต้นเป็น `"responses"` และสามารถละเว้นจาก `config.toml` ได้ทั้งหมด ให้กำหนดค่าอย่างชัดเจนเฉพาะเมื่อคุณต้องการบันทึกเจตนาของการตั้งค่าเท่านั้น

## หน้าต่างบริบทและการบีบอัด

### ฟิลด์การกำหนดค่าโทเค็น

| ฟิลด์                            | คำอธิบาย                                                                                                                                                                                                                      |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | งบประมาณโทเค็นทั้งหมดสำหรับโมเดลที่ใช้งานอยู่ ตั้งค่าให้เท่ากับขีดจำกัดที่โมเดลประกาศไว้                                                                                                                                      |
| `model_auto_compact_token_limit` | เกณฑ์ที่เรียกใช้การบีบอัดประวัติโดยอัตโนมัติ **สูงสุด: 90% ของ `model_context_window`** — ค่าที่สูงกว่า 90% จะถูกละเว้นโดยไม่มีการแจ้งเตือน                                                                                   |
| `tool_output_token_limit`        | จำกัดจำนวนโทเค็นที่จัดเก็บในประวัติต่อเอาต์พุตจากการเรียกใช้เครื่องมือหนึ่งครั้ง ป้องกันไม่ให้การตอบกลับขนาดใหญ่จากเครื่องมือเพียงครั้งเดียวเติมเต็มหน้าต่าง **นี่ไม่ใช่เอาต์พุตสูงสุด** — แต่เป็นขีดจำกัดการจัดเก็บในประวัติ |
| `compact_prompt`                 | ค่าที่กำหนดแทนพรอมต์ระบบแบบอินไลน์ซึ่งใช้ระหว่างการบีบอัด (v0.138+)                                                                                                                                                           |

> **หมายเหตุเกี่ยวกับ `model_max_output_tokens`**: ฟิลด์นี้ **ไม่ได้เป็นส่วนหนึ่งของสคีมาการกำหนดค่า Codex CLI** (ไม่มีอยู่ในฐานโค้ด Codex Rust) หากตั้งค่าไว้ ระบบจะละเว้นโดยไม่มีการแจ้งเตือน อย่าพึ่งพาฟิลด์นี้ — ให้ใช้ `tool_output_token_limit` เพื่อควบคุมปริมาณเอาต์พุตจากเครื่องมือที่จะจัดเก็บไว้ในประวัติ

| ชื่อ Codex CLI          | โมเดล OmniRoute    |
| ----------------------- | ------------------ |
| `cx/gpt-5.5`            | GPT-5.5 มาตรฐาน    |
| `cx/gpt-5.4`            | GPT-5.4 มาตรฐาน    |
| `cx/gpt-5.4-mini`       | GPT-5.4 mini       |
| `cx/gpt-5.1-codex-mini` | GPT-5.1 Codex mini |

ผู้ให้บริการรายอื่นใช้คำนำหน้าของตนเอง (`kmc/`, `glm/`, `ds/`, `ollamacloud/`, `opencode-go/`, `mistral/`) — คำนำหน้าจะตรงกับนามแฝงผู้ให้บริการใน OmniRoute

## ระดับการใช้เหตุผล

ควบคุมว่าโมเดลจะ "คิด" มากเพียงใดก่อนตอบกลับ

| ค่า      | ใช้สำหรับ                                         |
| -------- | ------------------------------------------------- |
| `none`   | ไม่ใช้เหตุผล — ตอบโดยตรง                          |
| `low`    | งานง่ายมาก (เปลี่ยนชื่อ, จัดรูปแบบ)               |
| `medium` | **ค่าเริ่มต้นของเซิร์ฟเวอร์** เมื่อไม่ได้ระบุ     |
| `high`   | งานระดับกลาง (ปรับโครงสร้างโค้ด, ดีบัก)           |
| `xhigh`  | สถาปัตยกรรม, การวิเคราะห์เชิงลึก, ปัญหาที่ซับซ้อน |

```bash
# กำหนดค่าแทนสำหรับการเรียกใช้แต่ละครั้ง
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

ตั้งค่า **สรุป** การใช้เหตุผลด้วย เพื่อให้ Desktop สามารถแสดงข้อความกระบวนการคิดได้ (ไม่ใช่เฉพาะบล็อบที่เข้ารหัส):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # หรือ ultra เมื่อรองรับ
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### งบประมาณการคิดของ OmniRoute (การตั้งค่าเซิร์ฟเวอร์)

บนโฮสต์ OmniRoute ต้องตั้งค่า **Settings → AI → Thinking Budget** เป็น **`passthrough`** เพื่อให้ระดับการใช้เหตุผล/สรุปของ Codex ถูกส่งต่อไปยังต้นทาง โหมด **`auto` จะตัด** ฟิลด์ `reasoning` / `reasoning_effort` ทั้งหมดจากไคลเอนต์ และจะทำให้แผงกระบวนการคิดว่างเปล่า แม้จะกำหนดค่า Codex ไว้อย่างถูกต้องแล้วก็ตาม

คู่มือฉบับเต็ม: [THINKING_BUDGET.md](./THINKING_BUDGET.md)

การบีบอัดและแคชพรอมต์ทำงานแยกจากกัน และยังคงทำงานภายใต้ `passthrough`

## การสร้างโปรไฟล์โดยอัตโนมัติด้วย `omniroute setup-codex`

หากคุณใช้งาน OmniRoute บน VPS คุณสามารถสร้างไฟล์โปรไฟล์โดยอัตโนมัติจากแค็ตตาล็อกโมเดลที่กำลังใช้งานอยู่ได้:

```bash
# จาก VPS (ใช้ OmniRoute ภายในเครื่องบนพอร์ต 20128)
omniroute setup-codex

# จากเครื่องใดก็ได้ — ระบุ VPS ของคุณ
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# แสดงตัวอย่างโดยไม่เขียนไฟล์
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# สร้างเฉพาะโปรไฟล์ GLM และ Kimi
omniroute setup-codex --only glm,kimi

# เขียนไปยังไดเรกทอรีที่กำหนดเอง
omniroute setup-codex --codex-home /path/to/.codex
```

คำสั่งนี้จะดึงข้อมูลจาก `/v1/models` ใช้โปรไฟล์ที่ปรับแต่งไว้สำหรับโมเดลที่รู้จัก ใช้เมทาดาทาของแค็ตตาล็อกเป็นทางเลือกสำรองสำหรับโมเดลข้อความอื่นๆ ที่เข้ากันได้ และเขียนไฟล์ `~/.codex/<name>.config.toml` สำหรับแต่ละโมเดล คำสั่งนี้เป็นแบบ Idempotent จึงสามารถเรียกใช้ซ้ำได้อย่างปลอดภัย

OmniRoute ยังสามารถ **ซิงค์อัตโนมัติ** ไฟล์โปรไฟล์เดียวกันเหล่านี้หลังจากการค้นพบ/นำเข้าโมเดลของผู้ให้บริการสำเร็จและส่งผลให้แค็ตตาล็อกที่กำลังใช้งานอยู่เปลี่ยนแปลงไปได้อีกด้วย ฟีเจอร์นี้ **ต้องเลือกเปิดใช้เองและปิดอยู่ตามค่าเริ่มต้น**: เปิดหรือปิดได้จาก **แดชบอร์ด CLI Code** ("CLI profile auto-sync" → Codex) หรือตั้งค่า `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (ฟีเจอร์นี้ยังใช้ค่าจาก `CLI_ALLOW_CONFIG_WRITES` ซึ่งเปิดอยู่ตามค่าเริ่มต้นด้วย) เมื่อเปิดใช้ ฟีเจอร์นี้จะเขียนเฉพาะไฟล์โปรไฟล์ `~/.codex/*.config.toml` ที่แยกจากกันเท่านั้น และจะไม่เปลี่ยนแปลง `~/.codex/config.toml` ที่กำลังใช้งาน/เป็นค่าเริ่มต้น การตั้งค่า Codex-lb การยืนยันตัวตน หรือการเลือกผู้ให้บริการ

## การเปิดใช้งาน Codex ด้วย `omniroute launch-codex`

ตรวจสอบสถานะการทำงานของอินสแตนซ์ OmniRoute ก่อนเปิดใช้งาน Codex:

```bash
# เปิดใช้งานโดยเชื่อมต่อกับ OmniRoute ภายในเครื่อง (พอร์ตเริ่มต้น 20128)
omniroute launch-codex

# เปิดใช้งานด้วยโปรไฟล์ที่ระบุ
omniroute launch-codex --profile kimi-k27

# เปิดใช้งานโดยเชื่อมต่อกับ VPS ระยะไกล
omniroute launch-codex --remote http://100.x.x.x:20128/v1 --api-key sk-xxx

# ส่งอาร์กิวเมนต์เพิ่มเติมไปยัง codex
omniroute launch-codex --profile glm52 -- --yolo "fix this bug"
```

Codex ยังเป็นเป้าหมายของจุดเริ่มต้นทั่วไปสองรายการที่ขับเคลื่อนด้วย manifest
(`bin/cli/cli-manifest.mjs`):

```bash
# ตัวเลือกโมเดลแบบโต้ตอบ → เขียน ~/.codex/<name>.config.toml (TOML, env_key)
omniroute configure codex

# เปิดใช้งาน codex โดยแทรกผู้ให้บริการ omniroute ผ่านแฟล็ก -c (ไม่มีการเขียนการกำหนดค่า)
omniroute run codex
```

## งานที่ใช้เวลานาน

ค่าเริ่มต้นสองรายการของ OmniRoute อาจทำให้เซสชัน Codex CLI ที่ทำงานนานหลายชั่วโมงล้มเหลวโดยไม่มีสัญญาณเตือน ทั้งสองรายการไม่ใช่การตั้งค่าของ Codex CLI แต่เป็นการตั้งค่าฝั่ง OmniRoute ผู้ใช้ที่ย้ายการกำหนดค่ามาจากพร็อกซีต้นทางซึ่งตรึงบัญชีและปิดการตัดการเชื่อมต่อเมื่อไม่มีการใช้งาน มักพบปัญหาทั้งสองอย่างและสรุปว่า OmniRoute “ไม่สามารถรักษาเซสชันระยะยาวไว้ได้”

| อาการ                                                                             | สาเหตุที่เป็นไปได้                                                                   | ตัวเลือกการตั้งค่า       |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------ |
| เซสชันสลับบัญชีอยู่เรื่อย ๆ / ความต่อเนื่องของแคชพรอมต์สูญหายไประหว่างรอบการสนทนา | TTL ของความสัมพันธ์ของเซสชันเป็น `0` (ปิดใช้งาน)                                     | `sessionAffinityTtlMs`   |
| การเชื่อมต่อขาดระหว่างการให้เหตุผลโดยไม่มีพรอมต์แสดงต่อไคลเอนต์                   | ตัวตรวจจับสตรีมที่ไม่มีความเคลื่อนไหวทำงานหลังจากไม่มีชังก์จากต้นทางเป็นเวลา 10 นาที | `STREAM_IDLE_TIMEOUT_MS` |

การอภิปรายที่เกี่ยวข้อง: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (งานระยะยาวหลุด), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (เหตุผลที่ปิดความสัมพันธ์ไว้เป็นค่าเริ่มต้น) การติดตาม: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287)

### 1. ความสัมพันธ์ของเซสชัน — ตรึงหนึ่งการสนทนาไว้กับหนึ่งบัญชี

**ค่าเริ่มต้น:** `sessionAffinityTtlMs = 0` (ปิดใช้งาน)

**ตำแหน่งที่ตั้งค่า**

- แดชบอร์ด → **การตั้งค่า → การกำหนดเส้นทาง** → **ความสัมพันธ์ของเซสชัน** → **TTL ของความสัมพันธ์ (วินาที)** (`ComboDefaultsTab`)
- หรือ PATCH การตั้งค่าด้วย `sessionAffinityTtlMs` ในหน่วย **มิลลิวินาที** (ช่วงของ Zod คือ `0`–`86_400_000` หรือสูงสุด 24 ชั่วโมง)

> เปลี่ยนชื่อใน #7274 จาก `codexSessionAffinityTtlMs` ซึ่งใช้กับ Codex เท่านั้น คีย์แบบเดิมยังคงได้รับการยอมรับในฐานะนามแฝงแบบอ่านอย่างเดียว การกำหนดค่าใหม่ควรใช้ `sessionAffinityTtlMs` ขณะนี้ความสัมพันธ์ใช้กับผู้ให้บริการ **ทุกราย** เมื่อ TTL มากกว่า `0` ไม่ใช่เฉพาะ Codex — ดู [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → ความสัมพันธ์ของเซสชัน

**สิ่งที่จะเสียหายเมื่อค่ายังคงเป็น 0**

แต่ละรอบของการสนทนา Codex แบบหลายรอบจะถูกกำหนดเส้นทางอย่างอิสระตามกลยุทธ์คอมโบที่ใช้งานอยู่ และอาจไปยัง **บัญชีที่ต่างกันในแต่ละรอบ** ซึ่งทำลายความต่อเนื่องของเซสชัน / แคชพรอมต์ฝั่งต้นทาง OmniRoute จะตรวจสอบเฉพาะส่วนหัวเซสชันของ Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) และฟิลด์ในเนื้อหาคำขอ เช่น `prompt_cache_key` / `session_id` เมื่อ TTL มากกว่า `0` เท่านั้น (`extractSessionAffinityKey` ใน `src/sse/services/auth.ts`)

**คำแนะนำสำหรับงานเดียวที่ใช้เวลาหลายชั่วโมง**

ตั้งค่า TTL ให้ **มากกว่าระยะเวลาจริงที่คาดว่างานจะใช้** (ค่าสูงสุดใน UI คือ **86400 วินาที** = 24 ชั่วโมง):

| ระยะเวลางานที่คาดไว้ | TTL ของความสัมพันธ์ (UI, วินาที) | `sessionAffinityTtlMs` |
| -------------------- | -------------------------------- | ---------------------- |
| สองสามชั่วโมง        | `14400` (4 ชม.)                  | `14400000`             |
| ข้ามคืน / ~12 ชม.    | `43200` (12 ชม.)                 | `43200000`             |
| เต็มวัน              | `86400` (24 ชม., สูงสุด)         | `86400000`             |

การเลือกเปิดใช้งานเป็นการออกแบบโดยตั้งใจ: การปิดความสัมพันธ์เอื้อต่อการกระจายโหลดระหว่างบัญชี ส่วนการเปิดใช้งานเอื้อต่อความต่อเนื่องของเซสชันเอเจนต์ระยะยาวหนึ่งเซสชัน คู่มือนี้ **ไม่ได้** เปลี่ยนค่าเริ่มต้น — ผู้ดูแลระบบที่รันงาน Codex ระยะยาวต้องเลือกเปิดใช้งานเอง

### 2. ระยะหมดเวลาของสตรีมที่ไม่มีความเคลื่อนไหว — อย่ายุติรอบการให้เหตุผลที่ไม่มีข้อมูลส่งออก

**ค่าเริ่มต้น:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 นาที) ค่านี้สืบทอดมาจาก `REQUEST_TIMEOUT_MS` เมื่อไม่ได้ตั้งค่า โดยค่าพื้นฐานร่วมคือ 600000 เช่นกัน ดู [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → ระยะหมดเวลา

**สิ่งที่จะเสียหายเมื่อใช้ค่าเริ่มต้น**

รอบการให้เหตุผล / การใช้เครื่องมือของ Codex ที่เงียบเกิน 10 นาทีโดย **ไม่มีชิ้นข้อมูลจริงจาก upstream** จะถูกบังคับปิดโดยตัวเฝ้าระวังการไม่มีการใช้งานของ SSE (`open-sse/utils/stream.ts`) ฝั่งไคลเอนต์มักเห็นเพียงการเชื่อมต่อหลุดโดยไม่มีข้อความใด ๆ ซึ่งตรงกับอาการ “หยุดเองโดยไม่มีการแจ้งเตือน”

รายละเอียดสำคัญ: **heartbeat ของ SSE ที่ OmniRoute สร้างขึ้นไม่รีเซ็ต** นาฬิกาจับเวลาการไม่มีการใช้งาน เฉพาะชิ้นข้อมูลจริงจาก body ของ upstream เท่านั้นที่อัปเดต `lastChunkTime` สำหรับตัวเฝ้าระวังแล้ว โมเดลที่ยังคง “คิด” อยู่แต่ไม่มีข้อมูลส่งออกจะดูไม่ต่างจาก upstream ที่ค้าง

การไม่มีการใช้งานของ body ใน Undici ที่เกี่ยวข้อง: `FETCH_BODY_TIMEOUT_MS` (ค่าเริ่มต้นใช้เกณฑ์พื้นฐาน 10 นาทีเดียวกัน และ `0` หมายถึงปิดใช้งาน) สำหรับการสตรีม `FETCH_TIMEOUT_MS` ครอบคลุมเฉพาะการตั้งค่าการเชื่อมต่อ / headers แรกเท่านั้น เมื่อสตรีมทำงานแล้ว การค้างจะถูกควบคุมโดย `STREAM_IDLE_TIMEOUT_MS` และ `FETCH_BODY_TIMEOUT_MS`

**คำแนะนำสำหรับงานเดียวที่ใช้เวลาหลายชั่วโมง**

ในสภาพแวดล้อมของโปรเซส OmniRoute (`.env` / compose / systemd):

```bash
# ปิดการตัดการเชื่อมต่อจากการไม่มีการใช้งานของสตรีมและ body สำหรับรอบการให้เหตุผลที่ใช้เวลานาน
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

หรือเพิ่มค่าให้สูงกว่าช่วงเวลาที่ไม่มีข้อมูลยาวนานที่สุดที่คาดไว้ (ค่าเป็นมิลลิวินาที):

```bash
# ตัวอย่าง: อนุญาตให้ไม่มีข้อมูลระหว่างชิ้นข้อมูลจาก upstream ได้นานสูงสุด 2 ชั่วโมง
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

รีสตาร์ต OmniRoute หลังจากเปลี่ยนตัวแปรสภาพแวดล้อมเหล่านี้

### ขั้นตอนที่ทำตามได้จริง — งาน Codex ที่ใช้เวลาหลายชั่วโมง

1. **ตรึงบัญชี:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 ชม.) หรือ `86400` (สูงสุด 24 ชม.)
2. **เพิ่ม / ปิดเกณฑ์ตัดเมื่อไม่มีการใช้งาน** ในสภาพแวดล้อมของ OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. ใช้ `config.toml` ตามปกติของ Codex (`wire_api = "responses"`, `base_url` ที่ถูกต้อง, `OMNIROUTE_API_KEY`) — ไม่มีตัวเลือกฝั่ง Codex สำหรับ affinity/idle ที่ควบคุมพฤติกรรมสองอย่างนี้
4. รีสตาร์ต OmniRoute แล้วจึงเริ่มงาน Codex ที่ใช้เวลานาน

### การตัดสินใจเกี่ยวกับค่าเริ่มต้น (#7287)

| ตัวเลือก                 | ค่าเริ่มต้นที่เผยแพร่ | เปลี่ยนในคู่มือนี้หรือไม่?                                                                                 |
| ------------------------ | --------------------- | ---------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (ปิด)             | **ไม่** — ยังคงเป็นตัวเลือกที่ต้องเปิดใช้เอง (การกระจายโหลดเทียบกับความต่อเนื่อง โปรดดู Discussion #5718)  |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 นาที)    | **ไม่** — ยังคงเป็น 10 นาทีสำหรับทราฟฟิกทั่วไป ผู้ดูแล Codex ที่มีงานระยะยาวสามารถเพิ่มค่าหรือปิดใช้งานได้ |

การเปลี่ยนค่าเริ่มต้นอย่างใดอย่างหนึ่งแบบทั่วทั้งระบบจะเปลี่ยนพฤติกรรมสำหรับไคลเอนต์ทุกตัวของอินสแตนซ์ ไม่ใช่เฉพาะ Codex ควรจัดทำเอกสารเกี่ยวกับตัวเลือกเหล่านี้ และคงค่าเริ่มต้นไว้จนกว่าจะมีการตัดสินใจอย่างชัดเจนจากผู้ดูแลระบบให้เปลี่ยนแปลง

### การวินิจฉัยการตัดการเชื่อมต่อเมื่อไม่มีการใช้งาน

เมื่อตัวเฝ้าระวังการไม่มีการใช้งานทำงาน OmniRoute จะบันทึกบรรทัดที่มีรูปแบบดังนี้:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

ใช้ grep ค้นหา `Idle timeout: no data from` (หรือโค้ด `stream_idle_timeout` / ชื่อข้อผิดพลาด `StreamIdleTimeoutError`) ส่วนที่ระบุ provider จะเป็นค่าที่ OmniRoute ใช้สำหรับคำขอนั้น (`codex`, id ของ provider อื่น หรือ `provider` หากไม่ทราบ) — จึงไม่ใช่สตริง `codex` เสมอไป

## การแก้ไขปัญหา

**`Error: wire_api = "chat" is no longer supported`**
นำ `wire_api = "chat"` ออกจากการกำหนดค่าของคุณ ตั้งค่า `wire_api = "responses"` หรือละฟิลด์นี้ไว้ (ค่าเริ่มต้นคือ `"responses"` ตั้งแต่ v0.138)

**`Error: model not found`**
ตรวจสอบว่าโมเดลมีอยู่ใน OmniRoute และใช้คำนำหน้าที่ถูกต้อง ใช้ `omniroute models list` หรือเปิด `/dashboard/providers/<provider>`

**`Authentication error`**
ตรวจสอบว่าได้ส่งออก `OMNIROUTE_API_KEY` แล้ว: `echo $OMNIROUTE_API_KEY`

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex จะตรวจสอบว่าตัวแปรสภาพแวดล้อมมีอยู่ก่อนส่งคำขอแรก ส่งออก
คีย์จริงสำหรับเซิร์ฟเวอร์ที่มีการป้องกัน หรือใช้ค่าตัวยึดตำแหน่งที่ไม่ว่าง เช่น
`OMNIROUTE_API_KEY=local` เมื่ออินสแตนซ์ OmniRoute **ภายในเครื่อง** ของคุณไม่
ต้องการการยืนยันตัวตน รีสตาร์ตเชลล์หากคุณเพิ่มค่าดังกล่าวลงใน `~/.bashrc` หรือ `~/.zshrc`

**`Connection refused`**
ตรวจสอบว่า OmniRoute กำลังทำงานอยู่ และโฮสต์/พอร์ตของ `base_url` ถูกต้องสำหรับเครือข่ายของคุณ (ภายในเครื่อง เทียบกับ Tailscale เทียบกับ VPS)

**เซสชันหยุดทำงานเมื่อใกล้ถึงขีดจำกัดบริบท**
กำหนด `model_context_window` และ `model_auto_compact_token_limit` อย่างชัดเจน ดูตารางหน้าต่างบริบทด้านบน

**การย่อบริบททำงานช้าเกินไป**
ลด `model_auto_compact_token_limit` ลงเหลือ 80–85% ของขนาดหน้าต่าง ห้ามตั้งค่าเกิน 90%

**โปรไฟล์ไม่ถูกโหลด (`-p <name>` ถูกละเว้นโดยไม่มีข้อความแจ้งเตือน)**
ตรวจสอบว่าไฟล์มีอยู่ที่ `~/.codex/<name>.config.toml` (ไม่มีคำนำหน้า `profile-`) เรียกใช้ `ls ~/.codex/*.config.toml`

**งาน Codex ที่ใช้เวลานานหลุดกลางคัน / สลับบัญชีระหว่างแต่ละรอบ**
ดู [งานที่ใช้เวลานาน](#long-running-tasks) เปิดใช้การผูกเซสชัน (ตั้งค่า TTL ให้นานกว่าระยะเวลาของงาน) และเพิ่มค่าหรือปิดใช้งาน `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` ค้นหาข้อความ `Idle timeout: no data from` ในบันทึกของ OmniRoute ด้วย grep
