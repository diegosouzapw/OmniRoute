> **สคีมามาตรฐาน (แหล่งข้อมูลที่ถูกต้อง):** [`open-sse/services/compression/rules/_schema.json`](../../open-sse/services/compression/rules/_schema.json) (JSON Schema draft 2020-12)
> ตัวอย่างด้านล่างมีไว้เพื่อประกอบคำอธิบายเท่านั้น — หากไม่แน่ใจ ให้ตรวจสอบความถูกต้องของแพ็กกับ `_schema.json`

## แพ็กกฎ Caveman

แพ็กกฎ Caveman อยู่ภายใต้:

```txt
open-sse/services/compression/rules/<language>/<pack>.json
```

แต่ละแพ็กประกอบด้วยรายการแทนที่ซึ่งนำไปใช้กับข้อความร้อยแก้วทั่วไป หลังจากแยกส่วนที่ได้รับการป้องกันออกแล้ว

```json
{
  "language": "en",
  "category": "filler",
  "rules": [
    {
      "name": "question_to_directive",
      "pattern": "\\b(?:Can you explain why|Could you show me how)\\b\\s*",
      "replacement": "Explain why ",
      "replacementMap": {
        "can you explain why": "Explain why ",
        "could you show me how": "Show how "
      },
      "flags": "gi",
      "context": "all",
      "category": "context",
      "minIntensity": "lite",
      "description": "Convert verbose questions into direct requests."
    }
  ]
}
```

### ฟิลด์ของ Caveman

| ฟิลด์                    | จำเป็น | คำอธิบาย                                                                                                  |
| ------------------------ | ------ | --------------------------------------------------------------------------------------------------------- |
| `language`               | ใช่    | คีย์ภาษาที่คล้าย BCP-47 เช่น `en`, `pt-BR`, `es`                                                          |
| `category`               | ใช่    | ชื่อไฟล์/หมวดหมู่ของแพ็ก เช่น `filler` หรือ `dedup`                                                       |
| `rules`                  | ใช่    | อาร์เรย์ของกฎการแทนที่ด้วย regex                                                                          |
| `rules[].name`           | ใช่    | ชื่อกฎที่คงที่                                                                                            |
| `rules[].pattern`        | ใช่    | ซอร์ส regex ของ JavaScript                                                                                |
| `rules[].flags`          | ไม่    | แฟล็ก regex ของ JavaScript; ค่าเริ่มต้นคือ `gi`                                                           |
| `rules[].replacement`    | ไม่    | สตริงแทนที่หรือค่าทดแทนเมื่อ `replacementMap` ไม่พบรายการที่ตรงกัน                                        |
| `rules[].replacementMap` | ไม่    | รายการแทนที่เฉพาะสำหรับแต่ละข้อความที่ตรงกัน โดยใช้ข้อความที่ตรงกันซึ่งปรับให้อยู่ในรูปแบบมาตรฐานเป็นคีย์ |
| `rules[].context`        | ไม่    | `all`, `user`, `assistant` หรือ `system`; ค่าเริ่มต้นคือ `all`                                            |
| `rules[].category`       | ไม่    | `filler`, `context`, `structural`, `dedup`, `terse` หรือ `ultra`                                          |
| `rules[].minIntensity`   | ไม่    | `lite`, `full` หรือ `ultra`; ค่าเริ่มต้นคือ `lite`                                                        |
| `rules[].description`    | ไม่    | สรุปกฎที่มนุษย์อ่านเข้าใจได้                                                                              |

ใช้ `flags` เมื่อการจับคู่แบบแยกตัวพิมพ์เล็กและตัวพิมพ์ใหญ่มีความสำคัญ เช่น การลบคำนำหน้านามก่อนข้อความร้อยแก้วที่เป็นตัวพิมพ์เล็ก โดยไม่ลบ `the OpenAI API` ใช้ `replacementMap` เมื่อ regex หนึ่งรายการมีหลายทางเลือกที่ต้องให้ผลลัพธ์แตกต่างกัน วิธีนี้ช่วยให้แพ็กกฎ JSON มีเฉพาะข้อมูล ขณะเดียวกันยังคงรักษาพฤติกรรมของฟังก์ชันแทนที่ TypeScript แบบในตัวที่มีความสามารถซับซ้อนกว่าไว้ได้

## แพ็กตัวกรอง RTK

ตัวกรอง RTK อยู่ภายใต้:

```txt
open-sse/services/compression/engines/rtk/filters/<filter>.json
```

ตัวกรองแต่ละตัวอธิบายวิธีตรวจจับและบีบอัดกลุ่มเอาต์พุตของคำสั่ง

```json
{
  "id": "test-vitest",
  "label": "Vitest output",
  "category": "test",
  "priority": 92,
  "match": {
    "outputTypes": ["test-vitest"],
    "commands": ["vitest", "npm test", "npm run test"],
    "patterns": ["\\bFAIL\\b", "\\bPASS\\b", "\\bTest Files\\b"]
  },
  "rules": {
    "stripAnsi": true,
    "replace": [{ "pattern": "\\s+\\[[0-9]+ms\\]", "replacement": "" }],
    "matchOutput": [
      {
        "pattern": "All tests passed",
        "message": "vitest: ok",
        "unless": "FAIL|Error:"
      }
    ],
    "includePatterns": ["FAIL", "Error:", "Test Files", "Tests"],
    "dropPatterns": ["^\\s*$", "Duration\\s+\\d+"],
    "collapsePatterns": ["^\\s+at "],
    "deduplicate": true,
    "truncateLineAt": 240,
    "maxLines": 160,
    "headLines": 24,
    "tailLines": 40,
    "onEmpty": "vitest: ok",
    "filterStderr": false
  },
  "preserve": {
    "errorPatterns": ["FAIL", "Error:", "AssertionError"],
    "summaryPatterns": ["Test Files", "Tests", "Snapshots"]
  },
  "tests": [
    {
      "name": "keeps failing tests",
      "command": "vitest",
      "input": "FAIL test/a.test.ts\\nError: boom\\nTest Files 1 failed",
      "expected": "FAIL test/a.test.ts\\nError: boom\\nTest Files 1 failed"
    }
  ]
}
```

### ฟิลด์ RTK

| ฟิลด์                      | จำเป็น | คำอธิบาย                                                                      |
| -------------------------- | ------ | ----------------------------------------------------------------------------- |
| `id`                       | ใช่    | ID ตัวกรองที่คงที่                                                            |
| `label`                    | ใช่    | ชื่อที่อ่านได้บนแดชบอร์ด                                                      |
| `category`                 | ใช่    | กลุ่มตัวกรอง: git, test, build, shell, docker, package, infra, cloud, generic |
| `priority`                 | ไม่    | ค่าลำดับความสำคัญที่สูงกว่าจะชนะเมื่อตัวกรองหลายตัวตรงกัน                     |
| `match.outputTypes`        | ไม่    | ID เอาต์พุตของตัวตรวจจับที่ใช้เลือกตัวกรองนี้                                 |
| `match.commands`           | ไม่    | โทเค็นคำสั่งที่ใช้เลือกตัวกรองนี้                                             |
| `match.patterns`           | ไม่    | รูปแบบ regex ที่ใช้เลือกตัวกรองนี้จากข้อความเอาต์พุต                          |
| `rules.stripAnsi`          | ไม่    | ลบลำดับอักขระหลีก ANSI ก่อนขั้นตอน regex                                      |
| `rules.replace`            | ไม่    | การแทนที่ด้วย regex ตามลำดับ โดยใช้ทีละบรรทัด                                 |
| `rules.matchOutput`        | ไม่    | กฎเอาต์พุตแบบลัดวงจรพร้อมเงื่อนไขป้องกัน `unless` ที่เป็นทางเลือก             |
| `rules.includePatterns`    | ไม่    | บรรทัดที่ควรเก็บรักษาไว้เป็นพิเศษ                                             |
| `rules.dropPatterns`       | ไม่    | บรรทัดที่ต้องลบออกเนื่องจากเป็นสัญญาณรบกวน                                    |
| `rules.collapsePatterns`   | ไม่    | บรรทัดที่ตรงกันซ้ำๆ ซึ่งสามารถยุบรวมได้                                       |
| `rules.deduplicate`        | ไม่    | ยุบบรรทัดที่ผ่านการทำให้เป็นมาตรฐานและซ้ำกัน                                  |
| `rules.truncateLineAt`     | ไม่    | ขีดจำกัดจำนวนอักขระต่อบรรทัดที่รองรับ Unicode อย่างปลอดภัย                    |
| `rules.maxLines`           | ไม่    | จำนวนบรรทัดสูงสุดที่เก็บไว้ก่อนการรักษาบรรทัดส่วนท้าย                         |
| `rules.headLines`          | ไม่    | บรรทัดส่วนต้นที่เก็บไว้ระหว่างการตัดทอน                                       |
| `rules.tailLines`          | ไม่    | บรรทัดส่วนท้ายที่เก็บไว้เพื่อคงบริบทล่าสุด                                    |
| `rules.onEmpty`            | ไม่    | ข้อความสำรองเมื่อการกรองลบเนื้อหาทั้งหมด                                      |
| `rules.filterStderr`       | ไม่    | ทำให้คำนำหน้า stderr ทั่วไปเป็นมาตรฐานก่อนขั้นตอนการกรองภายหลัง               |
| `preserve.errorPatterns`   | ไม่    | บรรทัดข้อผิดพลาดที่ควรคงอยู่หลังการตัดทอน                                     |
| `preserve.summaryPatterns` | ไม่    | บรรทัดสรุปที่ควรคงอยู่หลังการตัดทอน                                           |
| `tests[]`                  | ไม่    | ตัวอย่างการตรวจสอบแบบอินไลน์ที่ใช้โดยเกตตรวจสอบ RTK                           |

RTK ใช้ขั้นตอนเชิงประกาศตามลำดับนี้: `stripAnsi`, `filterStderr`, `replace`,
`matchOutput`, `dropPatterns`/`includePatterns`, `truncateLineAt`, `headLines`/`tailLines`,
`maxLines` และ `onEmpty`

สามารถโหลดตัวกรองแบบกำหนดเองได้จาก:

1. ไฟล์ `.rtk/filters.json` ของโปรเจกต์ เฉพาะหลังจากมีแฮชที่ตรงกันใน `.rtk/trust.json` หรือ
   เปิดใช้งาน `trustProjectFilters`
2. `DATA_DIR/rtk/filters.json` ส่วนกลาง
3. ตัวกรองในตัว

ไฟล์แบบกำหนดเองของโปรเจกต์/ส่วนกลางสามารถมีออบเจ็กต์ตัวกรองหนึ่งรายการหรืออาร์เรย์ของออบเจ็กต์ตัวกรอง ไฟล์
ตัวกรองแบบกำหนดเองที่ไม่ถูกต้องจะถูกข้ามพร้อมข้อมูลวินิจฉัย ส่วนตัวกรองในตัวที่ไม่ถูกต้องจะทำให้การตรวจสอบความถูกต้องล้มเหลว

ไฟล์ความเชื่อถือของโปรเจกต์:

```json
{
  "filtersSha256": "0123456789abcdef..."
}
```

การเขียนทับผ่านสภาพแวดล้อม `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` จะเชื่อถือตัวกรองของโปรเจกต์โดยไม่ต้องมี
แฮช และควรจำกัดการใช้งานไว้เฉพาะการพัฒนาในเครื่องที่มีการควบคุมเท่านั้น

## กฎด้านความปลอดภัย

- รักษากฎให้มีคุณสมบัติ idempotent: การเรียกใช้ตัวกรองเดียวกันสองครั้งต้องไม่ทำให้ผลลัพธ์เสียหาย
- รักษาข้อความแสดงข้อผิดพลาด พาธไฟล์ หมายเลขบรรทัด และสรุปคำสั่งให้ตรงตามต้นฉบับทุกประการเมื่อทำได้
- หลีกเลี่ยงกฎที่แก้ไขบล็อกโค้ด เพย์โหลด JSON, URL หรือข้อมูลลับ
- เพิ่มความครอบคลุมของ unit test สำหรับกลุ่มคำสั่งใหม่ในชุดทดสอบ detector/filter
- เพิ่มตัวอย่าง `tests[]` ให้กับตัวกรองในตัวทุกตัวและตัวกรองแบบกำหนดเองที่ใช้ร่วมกัน

## การตรวจสอบความถูกต้อง

แพ็กกฎจะได้รับการตรวจสอบความถูกต้องก่อนใช้งาน แพ็ก Caveman ในตัวและตัวกรอง RTK ในตัวจะหยุดทำงานทันที
ระหว่างการตรวจสอบความถูกต้อง เพื่อให้ตรวจพบแอสเซ็ตของรีลีสที่เสียหายก่อนจัดส่ง ส่วนตัวกรอง RTK แบบกำหนดเองจะถูก
ข้ามพร้อมข้อมูลวินิจฉัยเมื่อการแยกวิเคราะห์หรือการตรวจสอบความน่าเชื่อถือล้มเหลว

การตรวจสอบความถูกต้องแบบเจาะจง:

```bash
node --import tsx/esm --test tests/unit/compression/rule-loader.test.ts tests/unit/compression/language-packs.test.ts
node --import tsx/esm --test tests/unit/compression/rtk-verify.test.ts tests/unit/compression/rtk-dsl-pipeline.test.ts
```
