## ภาพรวม

OmniRoute ใช้ไปป์ไลน์การบีบอัดพรอมต์แบบโมดูลาร์ที่ทำงาน **เชิงรุก** ก่อนที่คำขอจะไปถึงผู้ให้บริการต้นทาง ซึ่งหมายความว่าคุณจะประหยัดโทเค็นได้อย่างโปร่งใส โดยไม่จำเป็นต้องเปลี่ยนแปลงเวิร์กโฟลว์

```
คำขอจากไคลเอนต์
  → ตัวเลือกกลยุทธ์การบีบอัด
    → มีการตั้งค่าทับด้วยคอมโบหรือไม่? → ใช้การตั้งค่าคอมโบ
    → ถึงเกณฑ์ทริกเกอร์อัตโนมัติหรือไม่? → ใช้โหมดอัตโนมัติ
    → มีโหมดเริ่มต้นหรือไม่? → ใช้การตั้งค่าส่วนกลาง
    → ปิดอยู่หรือไม่? → ข้ามการบีบอัด
  → โหมดการบีบอัดที่เลือก
    → Off: ไม่มีการบีบอัด
    → Lite: ล้างช่องว่าง/การจัดรูปแบบอย่างปลอดภัย (~15%)
    → Standard: ลบคำฟุ่มเฟือยแบบภาษามนุษย์ถ้ำ (~30%)
    → Aggressive: ลดทอนประวัติเก่า + สรุปเนื้อหา (~50%)
    → Ultra: ตัดทอนด้วยฮิวริสติก + ลดขนาดบล็อกโค้ด (~75%)
    → RTK: กรองเอาต์พุตจากเทอร์มินัล/เครื่องมือโดยพิจารณาคำสั่ง (ช่วงต้นทาง 60-90%)
    → Stacked: ไปป์ไลน์หลายเอนจินตามลำดับ โดยทั่วไปใช้ RTK แล้วตามด้วย Caveman (ช่วงที่เข้าเกณฑ์ 78-95%)
  → คำขอที่บีบอัดแล้ว → ผู้ให้บริการ
```

## โหมดการบีบอัด

### Off

ไม่มีการบีบอัด ข้อความทั้งหมดจะถูกส่งผ่านโดยไม่มีการเปลี่ยนแปลง

### โหมด Lite (ประหยัด ~15%, เวลาแฝง <1ms)

โหมดที่ปลอดภัยที่สุด — ไม่มีการเปลี่ยนแปลงความหมาย มีเพียงการล้างการจัดรูปแบบ:

| เทคนิค                   | คำอธิบาย                                          |
| ------------------------ | ------------------------------------------------- |
| `collapseWhitespace`     | รวมบรรทัดว่างที่ต่อเนื่องกันและช่องว่างท้ายบรรทัด |
| `dedupSystemPrompt`      | ลบข้อความระบบที่ซ้ำกัน                            |
| `compressToolResults`    | บีบอัดเอาต์พุตจากเครื่องมือ/ฟังก์ชันที่เยิ่นเย้อ  |
| `removeRedundantContent` | ตัดคำสั่งที่ซ้ำกันออก                             |
| `replaceImageUrls`       | ย่อ URI ข้อมูลรูปภาพแบบ base64                    |

**เหมาะที่สุดสำหรับ:** การใช้งานแบบเปิดไว้ตลอดและเวิร์กโฟลว์ที่ให้ความสำคัญกับความปลอดภัย

### โหมด Standard (ประหยัด ~30%)

ได้รับแรงบันดาลใจจาก [Caveman](https://github.com/JuliusBrussee/caveman) — ลบคำฟุ่มเฟือยและสำนวนที่เยิ่นเย้อโดยยังคงรักษาความหมาย:

- ลบคำฟุ่มเฟือย ("โปรด", "ฉันคิดว่า", "โดยพื้นฐานแล้ว", "จริง ๆ แล้ว")
- ย่อวลีที่เยิ่นเย้อ ("เพื่อที่จะ" → "เพื่อ", "อันเป็นผลมาจาก" → "เพราะ")
- ตัดถ้อยคำเกรงใจที่ไม่แน่นอน ("คุณจะรังเกียจไหม...", "หากเป็นไปได้ คุณช่วย...")
- กฎ regex มากกว่า 30 รายการที่ปรับแต่งมาสำหรับพรอมต์การเขียนโค้ด

**เหมาะที่สุดสำหรับ:** เวิร์กโฟลว์การเขียนโค้ดประจำวันและทีมที่คำนึงถึงต้นทุน

### โหมด Aggressive (ประหยัด ~50%)

การจัดการประวัติอย่างชาญฉลาดสำหรับเซสชันที่ยาวนาน:

- **การลดทอนข้อความเก่า** — ข้อความที่เก่ากว่าจะถูกบีบอัดมากขึ้นเรื่อย ๆ
- **การบีบอัดผลลัพธ์จากเครื่องมือ** — เอาต์พุตขนาดยาวจากเครื่องมือจะถูกตัดหรือย่อออก (เก็บบรรทัดแรก/สุดท้าย
  กรองบรรทัดที่ตรงกัน และย่อคีย์ JSON)
- **ตัวป้องกันความสมบูรณ์ของโครงสร้าง** — ทำให้มั่นใจว่าคู่ `tool_use` + `tool_result` ยังคงสอดคล้องกัน
- **การรับรู้ขนาดหน้าต่างบริบท** — เคารพขีดจำกัดโทเค็นของแต่ละโมเดล

**เหมาะที่สุดสำหรับ:** เซสชันการดีบักที่ยาวนานและโค้ดเบสขนาดใหญ่

### โหมด Ultra (ประหยัด ~75%)

การบีบอัดสูงสุดสำหรับสถานการณ์ที่มีข้อจำกัดด้านโทเค็นอย่างมาก:

- **การตัดทอนด้วยฮิวริสติก** — ตัดโทเค็นจากข้อความร้อยแก้วโดยอิงตามคะแนน
- **การรักษาโครงสร้าง** — บล็อกโค้ดแบบมีรั้ว โค้ดอินไลน์ URL และตัวระบุจะถูกแทนที่ชั่วคราว
  และนำกลับมาประกอบใหม่แบบตรงตามต้นฉบับโดยไม่ถูกตัดทอน
- **ระดับ SLM ที่เลือกใช้ได้** — โมเดลภายในเครื่องขนาดเล็กสามารถปรับปรุงการตัดทอนได้เมื่อกำหนดค่าไว้
- ทำงานเป็นอิสระจากโหมด Aggressive: โหมดนี้จะไม่ลดทอนข้อความเก่า บีบอัดผลลัพธ์จากเครื่องมือ
  หรือเรียกใช้ตัวสรุปสำรอง (เฉพาะความล้มเหลวในระดับ SLM เท่านั้นที่สามารถส่งผ่านขั้นตอนสำรองไปยัง
  aggressive ได้)

**เหมาะที่สุดสำหรับ:** เมื่อคุณใช้บริบทถึงขีดจำกัดซ้ำ ๆ

### โหมด RTK (ช่วงต้นทาง 60-90%)

โหมด RTK ได้รับการปรับให้เหมาะกับเอาต์พุตจากเครื่องมือที่เยิ่นเย้อซึ่งปรากฏในเซสชันของเอเจนต์เขียนโค้ด:

- ตรวจจับคลาสคำสั่ง/เอาต์พุต เช่น `git status`, `git diff`, `git log`, ตัวรันการทดสอบ,
  บิลด์ TypeScript/Vite/Webpack, ESLint/Biome/Prettier, การตรวจสอบ/ติดตั้ง npm, บันทึก Docker, เอาต์พุต
  โครงสร้างพื้นฐาน และเอาต์พุตเชลล์ทั่วไป
- ใช้ชุดตัวกรอง JSON จาก `open-sse/services/compression/engines/rtk/filters/`
- นำเข้าตัวกรองสคีมา RTK TOML v1 จากไฟล์ `filters.toml` ของโปรเจกต์หรือส่วนกลาง พร้อมการตรวจสอบ
  การทดสอบแบบอินไลน์และการควบคุมความน่าเชื่อถือสำหรับไฟล์ของโปรเจกต์
- มาพร้อมตัวกรองในตัว 55 รายการพร้อมตัวอย่างการตรวจสอบแบบอินไลน์
- ลบลำดับควบคุม ANSI แถบความคืบหน้า บรรทัดที่ซ้ำกัน และสัญญาณรบกวนที่ไม่สามารถนำไปดำเนินการได้
- เก็บรักษาความล้มเหลว ข้อผิดพลาด คำเตือน ไฟล์ที่เปลี่ยนแปลง สรุป และส่วนท้ายของเอาต์พุตขนาดยาว
- รองรับตัวกรองของโปรเจกต์ที่ควบคุมด้วยความน่าเชื่อถือ ตัวกรองส่วนกลาง และการกู้คืนเอาต์พุตดิบที่ผ่านการปกปิดข้อมูลซึ่งเลือกใช้ได้

**เหมาะที่สุดสำหรับ:** เซสชันของเอเจนต์ที่มีทรานสคริปต์จากเชลล์ บิลด์ การทดสอบ git, grep และเอาต์พุตไฟล์

### โหมด Stacked (ช่วงที่เข้าเกณฑ์ 78-95%)

โหมด Stacked เรียกใช้เอนจินการบีบอัดหลายตัวตามลำดับที่กำหนดแน่นอน ไปป์ไลน์เริ่มต้นคือ:

```txt
RTK -> Caveman
```

ลำดับนี้จะย่อเอาต์พุตจากเทอร์มินัล/เครื่องมือก่อน จากนั้นจึงใช้การย่อเชิงความหมายของ Caveman กับ
พรอมต์ภาษาธรรมชาติที่เหลืออยู่ สามารถกำหนดค่าไปป์ไลน์ Stacked แบบส่วนกลางหรือผ่าน
คอมโบการบีบอัดที่กำหนดให้กับคอมโบการกำหนดเส้นทางได้

**เหมาะที่สุดสำหรับ:** บริบทแบบผสมที่มีบันทึกจากเครื่องมือขนาดใหญ่ร่วมกับคำสั่งจากผู้ใช้หรือสรุปจากผู้ช่วย

## คณิตศาสตร์การประหยัดจากต้นน้ำ

OmniRoute บันทึกข้อมูลการประหยัดจากการบีบอัดโดยอ้างอิงจากสองแหล่ง ได้แก่ เกณฑ์มาตรฐานของโปรเจกต์ต้นน้ำและ
การประกอบเอนจินของ OmniRoute เอง

| แหล่งที่มา | ตัวเลขจาก README ต้นน้ำที่ใช้ในที่นี้                                                                                 |
| ---------- | --------------------------------------------------------------------------------------------------------------------- |
| Caveman    | โทเค็นเอาต์พุตลดลง `~75%`, ประหยัดเอาต์พุตเฉลี่ยจากเกณฑ์มาตรฐาน `65%`, ช่วง `22-87%` และเครื่องมือบีบอัดอินพุต `~46%` |
| RTK        | ประหยัดเอาต์พุตคำสั่ง `60-90%`; เซสชันตัวอย่าง `~118,000 -> ~23,900` โทเค็น หรือประหยัด `79.7%` (`~80%`)              |

สำหรับเพย์โหลดของเครื่องมือ/บริบทที่ทับซ้อนกัน คอมโบเริ่มต้นของ OmniRoute จะซ้อนเอนจินดังนี้:

```txt
RTK -> Caveman
```

การประหยัดรวมคำนวณแบบคูณ ไม่ใช่แบบบวก:

```txt
รวม    = 1 - (1 - การประหยัดของ RTK) * (1 - การประหยัดอินพุตของ Caveman)
ค่าเฉลี่ย = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
ช่วง    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ตัวเลข `78-95%` นี้ใช้ได้เมื่อทั้ง RTK และ Caveman สามารถลดเพย์โหลดอินพุต/บริบทเดียวกันได้
โหมดเอาต์พุตการตอบกลับของ Caveman เป็นส่วนแยกต่างหาก: เมื่อเปิดใช้งาน ให้ใช้ค่าการประหยัดเอาต์พุตของ Caveman เอง (`65%`
โดยเฉลี่ย, ตัวเลขพาดหัว `~75%`, ช่วง `22-87%`) การประหยัดค่าใช้จ่ายทั้งหมดขึ้นอยู่กับสัดส่วนพรอมต์/เอาต์พุตของคุณ

### ความหมายที่แท้จริงของ "เข้าเกณฑ์"

ช่วงพาดหัว 15-95% เป็นตัวเลขจริง แต่ใช้ได้เฉพาะกับเนื้อหาที่ **ซ้ำซ้อนหรือเยิ่นเย้อ** เท่านั้น — เช่น บรรทัดข้อผิดพลาดที่เกิดซ้ำ
บันทึกการบิลด์ที่แสดงคำเตือนเดิมซ้ำจำนวนมาก หรือดัมป์จาก `grep`/การอ่านไฟล์ที่มีขนาดใหญ่เกินไป ตัวเลขนี้
**ไม่ได้** หมายความว่าทุกคำขอจะประหยัดได้มากขนาดนั้น

ผ่านการตรวจสอบเชิงประจักษ์แล้ว (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): การรันแบบ
`stacked` (RTK + Caveman) กับบล็อก `tool_result` รูปแบบ Anthropic ที่มีบรรทัดข้อผิดพลาดเหมือนกัน 300 บรรทัด
ให้ผลลัพธ์เป็น **ประหยัดโทเค็น 95.93% / ประหยัดอักขระ 96.26%** — อยู่ในช่วงที่ประกาศไว้อย่างชัดเจน
แต่เมื่อใช้ไปป์ไลน์เดียวกันกับเอาต์พุตเครื่องมือปกติที่ไม่ซ้ำซ้อน (รายการผลลัพธ์ `grep` ที่สะอาด
การอ่านไฟล์สั้น ๆ หรือข้อความสนทนาทั่วไป) ระบบจะให้ผลเป็น **การประหยัดเกือบศูนย์** อย่างถูกต้อง เนื่องจาก
ไม่มีสิ่งซ้ำซ้อนให้ลบ และ `validateCompression()` (`validation.ts`) จะไม่ยอมส่ง
ข้อความที่เขียนใหม่ซึ่งทำให้บล็อกโค้ด, URL, หัวข้อ, เวอร์ชัน หรือตัวระบุค่าคงที่แบบตัวพิมพ์ใหญ่ทั้งหมดสูญหายหรือเปลี่ยนแปลงไป

นี่เป็นพฤติกรรมที่คาดไว้และปลอดภัย ไม่ใช่ข้อบกพร่อง: เซสชันการเขียนโค้ดที่ส่วนใหญ่อ่าน/ค้นหาไฟล์ที่สะอาดด้วย `grep` จะ
ประหยัดโดยรวมได้ไม่มากนัก แม้เปิดใช้งานการบีบอัดอย่างเต็มที่แล้ว ขณะที่เซสชันที่พบลูปล้มเหลว
หรือลินเตอร์ที่สร้างข้อความจำนวนมากจะประหยัดได้เต็มช่วง 78-95% สำหรับทราฟฟิกส่วนนั้น อย่าใช้เปอร์เซ็นต์
การประหยัดรวมที่ต่ำจากเซสชันเดียวเป็นหลักฐานว่าการบีบอัดถูกกำหนดค่าผิด — ให้ตรวจสอบก่อนว่า
เอาต์พุตเครื่องมือต้นทางมีความซ้ำซ้อนจริงหรือไม่

## การกำหนดค่า

### แดชบอร์ด

ไปที่ `Dashboard → Context & Cache`:

- **Caveman** — การเลือกโหมด ชุดภาษา การแสดงตัวอย่าง และค่าเริ่มต้นส่วนกลาง
- **RTK** — การแสดงตัวอย่างตัวกรองคำสั่ง การตั้งค่าความปลอดภัยของ RTK และแค็ตตาล็อกตัวกรอง
- **Compression Combos** — ไปป์ไลน์เอนจินที่มีชื่อซึ่งกำหนดให้กับคอมโบการกำหนดเส้นทาง
- **Auto-Trigger Threshold** — เริ่มใช้การบีบอัดโดยอัตโนมัติเมื่อจำนวนโทเค็นเกินเกณฑ์

### การแทนที่รายคอมโบ

ใน `Dashboard → Context & Cache → Compression Combos` ให้กำหนดคอมโบการบีบอัดแก่คอมโบการกำหนด
เส้นทาง:

```txt
คอมโบ: "free-tier-fallback"
  คอมโบการบีบอัด: "coding-agent-stack"
  ไปป์ไลน์: RTK -> Caveman
  เป้าหมาย:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

วิธีนี้ช่วยให้คุณใช้การบีบอัดแบบซ้อนกับผู้ให้บริการแบบฟรี/สำหรับการเขียนโค้ด ขณะที่ยังคงใช้โหมด lite กับการสมัครใช้บริการ
แบบชำระเงิน

การกำหนด "การแทนที่รายคอมโบ" นี้เป็นการควบคุมคนละส่วนกับการแทนที่ **โหมดการบีบอัดของคอมโบการกำหนด
เส้นทาง** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses — สคีมาของฟิลด์นี้
ยังรองรับ `rtk`, `stacked` และ `omniglyph`) — การแทนที่ดังกล่าวไม่ได้เลือกไปป์ไลน์คอมโบการบีบอัด
ที่มีชื่อ แต่เพียงตั้งค่าฟิลด์ `compressionMode` ที่ `resolveCompressionPlan` ใช้อ้างอิง
คุณสามารถตั้งค่าได้ทั้งในการ์ดคอมโบ (`Dashboard → Combos`) หรือ ตั้งแต่ #6760 เป็นต้นมา
สามารถตั้งค่าแยกตามคอมโบการกำหนดเส้นทางในรายการ "Assign to routing" ที่
`Dashboard → Context & Cache → Compression Combos` ซึ่งอยู่ถัดจากช่องทำเครื่องหมายกำหนดไปป์ไลน์
ที่อธิบายไว้ข้างต้น ทั้งสองส่วนบันทึกค่าผ่านปลายทาง `PUT /api/combos/{id}` เดียวกัน

### การแทนที่รายคำขอ

ส่งส่วนหัวคำขอ `x-omniroute-compression` เพื่อแทนที่แผนการบีบอัดสำหรับคำขอเดียว
โดยมีลำดับความสำคัญสูงสุด — เหนือกว่าการแทนที่ของคอมโบการกำหนดเส้นทาง โปรไฟล์ที่ใช้งานอยู่
การทริกเกอร์อัตโนมัติ และค่า Default ของแผงควบคุม ค่าที่ไม่รู้จักจะถูกละเว้น (คำขอจะไม่ถูกปฏิเสธ)
และสวิตช์หลักส่วนกลางยังคงควบคุมทุกอย่าง: เมื่อปิดการบีบอัดในระดับส่วนกลาง ส่วนหัวนี้จะไม่สามารถ
เปิดใช้งานได้ ค่า:

| ค่า           | ผลลัพธ์                                                                                              |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| `off`         | ไม่มีการบีบอัดสำหรับคำขอนี้                                                                          |
| `default`     | โปรไฟล์ Default ที่มาจากแผงควบคุม (ไม่สนใจโปรไฟล์ที่ใช้งานอยู่) เอนจินแบบสูญเสียข้อมูลจะยังคงปิดอยู่ |
| `safe`        | เหมือนกับการไม่ระบุส่วนหัว: ใช้เฉพาะการขจัดข้อมูลซ้ำและการยุบช่องว่าง                                |
| `allow-lossy` | คงแผนของโอเปอเรเตอร์สำหรับคำขอนี้ไว้ รวมถึงบทสรุป ตัวกรองความเกี่ยวข้อง และการปรับรูปแบบใหม่         |
| `engine:<id>` | เอนจินเดียวเมื่อเปิดใช้งาน เช่น `engine:rtk` นี่คือการเลือกใช้เอนจินนั้นเป็นรายคำขอ                  |
| `<combo>`     | คอมโบที่มีชื่อ โดยจับคู่ตามชื่อก่อน (ไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่) แล้วจึงตาม id                     |

หากไม่มี `allow-lossy`, `engine:<id>` หรือคอมโบที่มีชื่อ เอนจินแบบสูญเสียข้อมูลจะไม่ถูกนำมาใช้
คำขอยังคงได้รับการขจัดข้อมูลซ้ำของเซสชันและการยุบช่องว่างเมื่อเปิดการบีบอัด

แผนที่นำไปใช้จะถูกส่งกลับในส่วนหัวการตอบกลับ `X-OmniRoute-Compression: <mode>; source=<source>`
โดยที่ `<source>` เป็นค่าใดค่าหนึ่งใน `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` หรือ `off`

### API

```bash
# รับการตั้งค่าการบีบอัด
curl http://localhost:20128/api/settings/compression

# อัปเดตการตั้งค่าการบีบอัด
curl -X PUT http://localhost:20128/api/settings/compression \
  -H "Content-Type: application/json" \
  -d '{"defaultMode":"stacked","autoTriggerMode":"stacked","autoTriggerTokens":32000}'

# แสดงตัวอย่างเพย์โหลด RTK/stacked ที่ระบุ
curl -X POST http://localhost:20128/api/compression/preview \
  -H "Content-Type: application/json" \
  -d '{"mode":"rtk","messages":[{"role":"tool","content":"npm test output here"}]}'

# แสดงรายการชุดตัวกรอง RTK
curl http://localhost:20128/api/context/rtk/filters

# ทดสอบ RTK โดยตรงพร้อมข้อมูลเมตาของคำสั่งที่ระบุหรือไม่ก็ได้
curl -X POST http://localhost:20128/api/context/rtk/test \
  -H "Content-Type: application/json" \
  -d '{"command":"npm test","text":"FAIL tests/example.test.ts\nError: boom"}'
```

## ระบบการบีบอัดขั้นสูง

นอกเหนือจาก 7 โหมดที่อธิบายไว้ข้างต้น (ซอร์สยังรองรับโหมด `codex-responses` และ
`omniglyph` ซึ่งคู่มือนี้ไม่ครอบคลุม) ส่วนต่อไปนี้จะกล่าวถึงฟีเจอร์ที่ทำงานภายในหรือทำงานร่วมกับ
โหมดเหล่านั้น: Tool Result Compression และ Progressive Aging เป็นขั้นตอนที่ 1 และ 2
ของกลไก Aggressive (โหมด Aggressive และขั้นตอน `aggressive` ของไปป์ไลน์แบบ
ซ้อน), Stacked Pipeline คือวิธีที่โหมด Stacked ทำงาน, Cache-Aware Compression
จะลดระดับ `aggressive` และ `ultra` ลงเป็น `standard` สำหรับผู้ให้บริการที่รองรับการแคช
ขณะที่เปิดใช้การบีบอัด และ Caveman Output Mode กับ Output Styles คือคำสั่งพรอมต์ระบบ
แบบเลือกเปิดใช้ ซึ่งปิดไว้ตามค่าเริ่มต้น และกำหนดรูปแบบเอาต์พุตของโมเดลแทนการบีบอัดคำขอ

### การบีบอัดที่ตระหนักถึงแคช

ผู้ให้บริการบางราย (เช่น Anthropic ที่มีการแคชพรอมต์) รองรับ **การแคชพรอมต์**
ซึ่งช่วยให้สามารถแคชบางส่วนของพรอมต์เพื่อลดค่าใช้จ่ายและเวลาแฝง เมื่อ
เปิดใช้การแคช การบีบอัดแบบ Aggressive อาจ **ทำให้** ประสิทธิภาพแย่ลง
เพราะจะเปลี่ยนโทเค็นที่แคชไว้ ส่งผลให้แคชใช้ไม่ได้

โมดูล `cachingAware.ts` แก้ปัญหานี้โดย **ตรวจจับบริบทการแคช** และ
**ปรับกลยุทธ์การบีบอัด** ให้เหมาะสม

#### วิธีการทำงาน

1. **ตรวจจับบริบทการแคช** — สแกนเนื้อหาคำขอเพื่อหาเครื่องหมาย `cache_control`
2. **ระบุผู้ให้บริการที่รองรับการแคช** — ตรวจสอบว่าผู้ให้บริการเป้าหมายรองรับการแคชหรือไม่
3. **ปรับกลยุทธ์** — ลดระดับ `aggressive`/`ultra` ลงเป็น `standard` สำหรับผู้ให้บริการที่รองรับการแคช
4. **ข้ามพรอมต์ระบบ** — โดยปกติพรอมต์ระบบจะถูกแคช ดังนั้นจึงไม่ควรบีบอัดพรอมต์เหล่านั้น

ตัวช่วยกลยุทธ์ยังส่งคืนแฟล็ก `deterministicOnly` ด้วย แต่ตัวสร้างแผนจะใช้
เฉพาะกลยุทธ์เท่านั้น — ปัจจุบันไม่มีส่วนใดที่อยู่ถัดจากนั้นอ่านแฟล็กดังกล่าว

#### ตัวอย่างโค้ด

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← เครื่องหมายแคช
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ควรใช้เมื่อใด

การบีบอัดที่ตระหนักถึงแคช **เปิดใช้งานอยู่เสมอ** — ไม่จำเป็นต้องกำหนดค่า ฟีเจอร์นี้จะทำงานเมื่อใดก็ตามที่
เปิดใช้การบีบอัดและผู้ให้บริการเป้าหมายรองรับการแคชพรอมต์ (Anthropic, OpenAI
เป็นต้น); ไม่จำเป็นต้องมีเครื่องหมาย `cache_control` ที่ระบุอย่างชัดเจน — เพียงแค่เป็นผู้ให้บริการที่รองรับการแคช
ก็จะกระตุ้นให้มีการลดระดับ และเครื่องหมายเพียงอย่างเดียวจะไม่กระตุ้นการลดระดับ (การตรวจจับเครื่องหมายจะส่งข้อมูลไปยัง
ระบบวัดและติดตามการแคช ไม่ใช่การตัดสินใจเลือกกลยุทธ์)

### การลดรายละเอียดตามอายุแบบก้าวหน้า

การสนทนาที่ยาวนานจะสะสมข้อความหลายรอบ แต่ข้อความจากรอบเก่า ๆ จะมี
ความเกี่ยวข้องน้อยลง โมดูล `progressiveAging.ts` จะ **ลดระดับรายละเอียดของข้อความตามระยะห่างของรอบ**
(วัดระยะห่างจากส่วนท้ายของการสนทนา) เมื่อใช้ค่าเริ่มต้นที่มาพร้อมระบบ
(`verbatim: 2, light: 2, moderate: 3`):

- **2 เทิร์นล่าสุด (ระยะห่าง ≤ 2)**: คงไว้ตามต้นฉบับทุกประการ
- **ระยะห่าง 3**: การบีบอัดแบบมนุษย์ถ้ำ (ตัดคำฟุ่มเฟือย)
- **ระยะห่าง 4+**: สรุปข้อความของผู้ช่วย ส่วนข้อความของผู้ใช้ลดเหลือเพียงบรรทัดแรก
  โดยจำกัดที่ 120 อักขระ บทบาทอื่นคงไว้โดยไม่เปลี่ยนแปลง พรอมต์ระบบ ข้อความที่ผ่าน
  การลดทอนตามอายุแล้ว และข้อความล่าสุดของผู้ใช้ จะถูกคงไว้ตามต้นฉบับทุกประการเสมอ
  โดยไม่คำนึงถึงระยะห่าง ไม่มีสิ่งใดถูกตัดทิ้งทั้งหมด และแบนด์ `light`
  จะไม่มีทางถูกใช้ด้วยค่าเริ่มต้นที่จัดส่งมา (`light` เท่ากับ `verbatim`)

#### ตัวอย่างโค้ด

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... อีก 50 เทิร์น ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // 3 เทิร์นล่าสุด: คงไว้ตามต้นฉบับ
  light: 8, // ระยะห่าง <= 8: การบีบอัดแบบเบา
  moderate: 20, // ระยะห่าง <= 20: การบีบอัดแบบมนุษย์ถ้ำ
  fullSummary: 5, // ชนิดข้อมูลกำหนดให้ต้องมี แต่โค้ดแบ่งแบนด์ไม่ได้อ่านค่านี้
  // ระยะห่าง > 20: สรุป (ผู้ช่วย) / เก็บบรรทัดแรกไว้ (ผู้ใช้)
});

// saved = จำนวนโทเค็นที่ประหยัดได้
```

#### ควรใช้เมื่อใด

การลดทอนแบบต่อเนื่องจะ **เปิดใช้งานเสมอ** สำหรับโหมด `aggressive` — โดยเป็นขั้นตอนที่ 2 ของ
`compressAggressive()` โหมด Ultra จะไม่เรียกใช้กระบวนการนี้ ฟีเจอร์นี้
มีประสิทธิภาพเป็นพิเศษสำหรับ:

- เซสชันเขียนโค้ดที่ดำเนินต่อเนื่องเป็นเวลานาน
- การสนทนาที่กินเวลาหลายวัน
- เวิร์กโฟลว์แบบเอเจนต์ที่มีการเรียกใช้เครื่องมือจำนวนมาก

### โหมดเอาต์พุตแบบมนุษย์ถ้ำ

โหมดเอาต์พุตแบบมนุษย์ถ้ำเพิ่ม **คำสั่งในพรอมต์ระบบ** ซึ่งขอให้ตัวโมเดลเองสร้าง
เอาต์พุตที่กระชับ — ระดับ `lite` ขอคำตอบที่กระชับแต่ยังคงใช้ประโยคเต็ม ระดับ `full`
ขอให้โมเดล "ตอบสั้นแบบมนุษย์ถ้ำฉลาด" และระดับ `ultra` ขอเอาต์พุตแบบโทรเลข
คำสั่งเหล่านี้ทำได้เพียงร้องขอเท่านั้น ไม่สามารถรับประกันผลลัพธ์ได้ คำขอจะได้รับคำสั่งผ่าน
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`):
ก่อนอื่น `open-sse/handlers/chatCore.ts` จะแก้ไขตัวเลือกด้วยชิมความเข้ากันได้ย้อนหลัง
(`resolveOutputStyleSelection()` ใน
`open-sse/services/compression/outputStyles/backCompat.ts`) ซึ่งในขณะที่ `outputStyles`
ว่างอยู่ จะจับคู่ `cavemanOutputMode` ที่เปิดใช้งานกับสไตล์เอาต์พุต `terse-prose` ที่ระดับ
`cavemanOutputMode.intensity` (ดูส่วนความเข้ากันได้ย้อนหลังด้านล่าง) ตัวเลือก `outputStyles`
ที่ไม่ว่างจะถูกใช้ตามเดิม จากนั้น `cavemanOutputMode.enabled` และ `intensity` จะไม่มี
ผลใด ๆ ขณะที่ตัวสลับ `autoClarity` ยังคงมีผลอยู่ `outputMode.ts` เก็บ
ข้อความคำสั่ง (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`) การข้ามเนื้อหา และ
ตัวช่วยกำหนดตำแหน่งที่กระบวนการแทรกใช้ ส่วนตัวแทรก `applyCavemanOutputMode()` ของไฟล์นี้เองไม่มี
ผู้เรียกใช้ในระบบจริง

#### วิธีการทำงาน

โหมดนี้ไม่ได้บีบอัดอินพุต แต่จะเพิ่มบล็อกคำสั่งลงในพรอมต์ระบบ
(ดูวิธีการแทรกด้านล่าง) และโหมดบีบอัดอินพุตใด ๆ ที่เลือกไว้สำหรับคำขอ
จะยังคงทำงานหลังจากนั้นกับเนื้อหาที่มีบล็อกดังกล่าวแล้ว ก่อนข้อความกำหนดขอบเขตร่วม
ที่ทุกระดับลงท้ายด้วย ระดับ `full` ภาษาอังกฤษระบุว่า:

> "ตอบสั้นแบบมนุษย์ถ้ำฉลาด ตัดคำนำหน้านาม (a/an/the) คำฟุ่มเฟือย (just/really/basically/actually/simply) คำสุภาพ และถ้อยคำแสดงความไม่แน่ใจ ใช้วลีไม่เต็มประโยคได้ ใช้คำพ้องความหมายสั้น ๆ (big แทน extensive, fix แทน implement) รักษาเนื้อหาทางเทคนิค โค้ด ข้อผิดพลาด URL และตัวระบุทั้งหมดให้ตรงตามต้นฉบับ"

วิธีนี้เหมาะเป็นพิเศษสำหรับ:

- การสร้างโค้ด (เอาต์พุตกระชับขึ้น = ใช้โทเค็นน้อยลง)
- การถามตอบแบบรวดเร็ว (ไม่จำเป็นต้องอธิบายอย่างละเอียด)
- การประมวลผลแบบแบตช์ (เพิ่มปริมาณงานสูงสุด)

#### ควรใช้เมื่อใด

โหมดเอาต์พุตแบบมนุษย์ถ้ำเป็นแบบ **เลือกเปิดใช้** เมื่อเปิดการบีบอัดอยู่ (`enabled: true` ซึ่งเป็นตัวสลับหลัก
ในหน้าการตั้งค่าการบีบอัด) ให้เปิดโหมดนี้ด้วย `cavemanOutputMode.enabled` ส่วน `intensity`
ใช้เลือก `lite`, `full` หรือ `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

ตัวสลับ **โหมดเอาต์พุต** ของคอมโบการบีบอัด (`outputMode` โดยมีระดับอยู่ใน `outputModeIntensity`)
จะตั้งค่าสวิตช์เดียวกันสำหรับคำขอที่คอมโบนั้นมีผล และเครื่องมือ MCP
`omniroute_set_compression_engine` จะเขียนค่าผ่านอาร์กิวเมนต์บูลีน `outputMode`
ของเครื่องมือ ตัวเลือก `outputStyles` ที่ไม่ว่างจะมีลำดับความสำคัญเหนือสวิตช์นี้ ใน
แดชบอร์ด การเปิดใช้สไตล์เอาต์พุต **ร้อยแก้วกระชับ** จะแทรกบล็อกเดียวกัน (ดูสไตล์เอาต์พุต
ด้านล่าง)

### สไตล์เอาต์พุต (แค็ตตาล็อก)

โหมดเอาต์พุตแบบมนุษย์ถ้ำด้านบนคือ **เส้นทางสไตล์เดียวแบบเดิม** เฟส 4 ได้ขยายแนวคิดนี้
ให้เป็นแค็ตตาล็อกของสไตล์เอาต์พุตที่สามารถใช้ร่วมกันได้: `OUTPUT_STYLE_CATALOG` ใน
`open-sse/services/compression/outputStyles/catalog.ts` แต่ละสไตล์เป็นคำสั่งในพรอมต์ระบบ
ที่ขอให้ตัวโมเดลเองสร้างเอาต์พุตที่ประหยัดกว่า โดยสามารถเปิดใช้หลายสไตล์
ร่วมกันได้ และระบบจะแทรกสไตล์เหล่านั้นตามลำดับในแค็ตตาล็อก

ด้านล่าง) เป็น `zh` การซ่อนแถวจะไม่ล้างการเลือก `terse-cjk` ที่บันทึกไว้:
API การตั้งค่ายอมรับ style id ใดก็ได้ และการบันทึกสไตล์อื่นบนหน้าดังกล่าวจะคงการเลือกนี้ไว้ ณ
เวลารับคำขอ การตรวจสอบภาษาใน `applyOutputStyles()` คือข้อจำกัดตาม locale เพียงจุดเดียว

#### วิธีการทำงานของการแทรกคำสั่ง

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) resolve
การเลือกโดยเทียบกับแค็ตตาล็อก (id ที่ไม่รู้จักและสไตล์ที่ locale ไม่ตรงกันจะ
ถูกตัดออกโดยไม่ถือเป็นข้อผิดพลาด การเลือกที่ resolve แล้วไม่เหลือสไตล์จะไม่เปลี่ยนแปลง body
และข้ามด้วยสถานะ `no_styles`), เชื่อมคำสั่งที่เลือกตามลำดับในแค็ตตาล็อก,
ต่อท้ายข้อกำหนดขอบเขต **หนึ่งครั้ง** (รวมถึงข้อกำหนดด้านความปลอดภัย `SAFETY_BOUNDARIES` หรือ
คำแปลของข้อกำหนดดังกล่าว เมื่อเลือก `less-code` หรือ `ponytail`) และเริ่ม block ด้วย
เครื่องหมาย idempotency เพียงหนึ่งรายการ (`[OmniRoute Output Styles]`) ดังนั้นการนำไปใช้อีกครั้ง
จึงไม่ทำอะไร เมื่อภาษาที่ได้รับการ resolve (ดูหัวข้อการเลือกภาษาด้านล่าง) มีคำแปล ระบบจะแทรก
คำสั่งที่แปลเป็นภาษานั้นแทนภาษาอังกฤษ

สำหรับ body ที่มีอาร์เรย์ `messages` ซึ่งไม่ว่าง การตรวจสอบ idempotency จะทำงานก่อน
การข้ามตามเนื้อหา: เมื่อมีเครื่องหมาย `[OmniRoute Output Styles]` อยู่แล้วในฟิลด์
`system` ระดับบนสุด (ไม่ว่าจะเป็นสตริงหรืออาร์เรย์ content-block) หรืออยู่ใน system message ที่มี
content เป็นสตริง ระบบจะปล่อย body ไว้โดยไม่เปลี่ยนแปลงด้วยสถานะ `already_applied` และจะไม่ตรวจสอบ
คีย์เวิร์ด มิฉะนั้น การข้ามตามเนื้อหา (`shouldBypassCavemanOutputMode()` ใน
`open-sse/services/compression/outputMode.ts`) จะตรวจสอบข้อความของสาม message ล่าสุด
ไม่ว่าจะมี role ใด และข้ามสไตล์ทั้งหมดสำหรับ turn นั้นเมื่อข้อความตรงกับคีย์เวิร์ดด้านความปลอดภัย
การดำเนินการที่ย้อนกลับไม่ได้ หรือการขอคำชี้แจง หรือพบลำดับที่ขึ้นกับลำดับคำ ได้แก่ `first`,
`then`, `after that`, `before`, `rollback` หรือ `backup` ซึ่งตามด้วย `delete`, `drop`,
`migrate`, `deploy` หรือ `release` ภายใน 240 อักขระ การข้ามนี้จะทำงานขณะที่เปิดสวิตช์
**Auto-Clarity Bypass** (`cavemanOutputMode.autoClarity` ซึ่งเปิดเป็นค่าเริ่มต้น);
การปิดสวิตช์จะข้ามการตรวจสอบคีย์เวิร์ด

เมื่อการตรวจสอบการข้ามอนุญาตให้ turn ดำเนินต่อ `placeSystemInstruction()` (ไฟล์เดียวกัน) ซึ่ง
จะไม่สร้าง `messages[0]` ใหม่ จะวาง block ในตำแหน่งแรกที่พบตามลำดับต่อไปนี้:

1. system message แรกที่มี content เป็นสตริง: ต่อท้าย block หลังข้อความ
2. ฟิลด์ `system` ระดับบนสุด: ต่อท้าย block หลังข้อความของสตริง หรือ
   เพิ่มเป็น text block ใหม่ในอาร์เรย์ content-block
3. system message ถัดไปตัวแรกที่มี content เป็นสตริง: ต่อท้าย block หลังข้อความ
4. ไม่พบรายการข้างต้น: ใส่ block ใน system message ใหม่ที่ท้าย `messages`

สำหรับ body ที่ไม่มีอาร์เรย์ `messages` (หรือมีอาร์เรย์ว่าง) จะไม่มีการข้ามตามเนื้อหา และ
จะไม่ตรวจสอบฟิลด์ `system` ระดับบนสุด ระบบจะต่อท้าย block หลังข้อความของฟิลด์
`instructions` ที่เป็นสตริง เว้นแต่ฟิลด์นั้นมีเครื่องหมาย
`[OmniRoute Output Styles]` อยู่แล้ว ซึ่งในกรณีนี้ระบบจะปล่อย body ไว้โดยไม่เปลี่ยนแปลงด้วยสถานะ
`already_applied` เมื่อ body ไม่มีฟิลด์ `instructions` ที่เป็นสตริง แต่มี `input`
(เป็นสตริงหรืออาร์เรย์) block จะกลายเป็น `instructions` โดยแทนที่ค่าที่ไม่ใช่สตริงใดๆ
ซึ่งฟิลด์นั้นเคยเก็บไว้ body ที่ไม่มีทั้งฟิลด์ `instructions` ที่เป็นสตริง และ `input`
ที่เป็นสตริงหรืออาร์เรย์ จะถูกปล่อยไว้โดยไม่เปลี่ยนแปลงและข้ามด้วยสถานะ `no_messages`

#### วิธีเปิดใช้งาน

ในแดชบอร์ด: **Compression Context → Compression Settings**
(`/dashboard/context/settings`) ส่วน Output styles: หนึ่งแถวต่อหนึ่งสไตล์ พร้อมสวิตช์เปิด/ปิด
และตัวเลือกระดับ สไตล์จะถูกแทรกขณะที่การบีบอัดเปิดอยู่ (สวิตช์หลักของหน้า
`enabled`) สวิตช์ **Auto-Clarity Bypass** อยู่ในหน้า **Caveman**
(`/dashboard/context/caveman`) ภายในการ์ด **Output Mode** ในเชิงโปรแกรม
การกำหนดค่าการบีบอัดจะบันทึกตัวเลือกไว้เป็น:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ความเข้ากันได้ย้อนหลัง: ขณะที่ `outputStyles` ว่างอยู่ การตั้งค่าเดิม
`cavemanOutputMode.enabled` จะถูกแมปเป็น `terse-prose` ที่ระดับ
`cavemanOutputMode.intensity` จากนั้นบล็อกจะเริ่มต้นด้วยเครื่องหมาย
`[OmniRoute Output Styles]` ในขณะที่ตัวแทรกเดิม `applyCavemanOutputMode()`
เขียน `[OmniRoute Caveman Output Mode]` ไว้ ใต้เครื่องหมายดังกล่าว ข้อความจะตรงกับ
การแทรกแบบเดิมใน en, pt-BR, es, de, fr, it, ru, id และ vi; ส่วนใน ja และ zh จะมี
ช่องว่างเพิ่มอีกหนึ่งช่องก่อนอนุประโยคเกี่ยวกับขอบเขต `terse-prose` มีคำแปลใน pt-BR, es, de,
fr, it, ru, zh, ja, id และ vi ดังนั้นคำขอที่ภาษาซึ่งได้รับการระบุเป็น `hu` จะได้รับ
ข้อความภาษาอังกฤษ ในจุดที่ตัวแทรกเดิมใช้ข้อความภาษาฮังการี

การเลือกภาษาของสไตล์เอาต์พุต (`resolveOutputStyleLanguage()` ใน
`outputStyles/apply.ts`): เมื่อเปิด `languageConfig.enabled` แล้ว `autoDetect` จะสุ่มตัวอย่าง
ข้อความล่าสุดจากผู้ใช้ในอาร์เรย์ `messages` ของคำขอที่มีข้อความ (เนื้อหาแบบสตริง หรือ
`text` ของส่วนต่าง ๆ ในเนื้อหา) แล้วเรียกใช้ตัวตรวจจับของเอนจิน Caveman
(`detectCompressionLanguage()`) กับข้อความนั้น ตัวตรวจจับจะคืนค่า `zh` สำหรับข้อความที่มีอักขระ Han
และไม่มี kana; มิฉะนั้นจะคืนค่าภาษาที่มีจำนวนคำใบ้ตรงกันมากที่สุดจาก `it`, `pt-BR`, `es`, `de`,
`fr`, `ru`, `ja`, `hu` และ `id` และคืนค่า `en` เมื่อไม่มีรายการใดตรงกัน —
ข้อความที่ไม่สามารถจำแนกได้จะได้รับภาษาอังกฤษเสมอ ไม่ใช่ `defaultLanguage` และจะไม่มีการตรวจพบ
`vi` แม้ว่าสไตล์จะมีข้อความ `vi` ก็ตาม บอดีของ Responses API เก็บเทิร์นต่าง ๆ ไว้ใน
`input` ซึ่งจะไม่ถูกสุ่มตัวอย่าง ดังนั้นจึงใช้ `defaultLanguage` แล้วจึงใช้ภาษาอังกฤษ เมื่อไม่มี
ข้อความจากผู้ใช้ใน `messages` ที่มีข้อความ หรือเมื่อปิด `autoDetect` ระบบจะใช้
`defaultLanguage` แล้วจึงใช้ภาษาอังกฤษ เมื่อปิด `languageConfig.enabled` ภาษาจะเป็นภาษาอังกฤษ —
เว้นแต่ว่ามีคอมโบการบีบอัดที่ใช้กับคำขอ (คอมโบที่กำหนดให้กับ routing
combo ของคำขอ หรือคอมโบการบีบอัดเริ่มต้นที่ chatCore ใช้เป็นทางเลือกสำหรับ built-in stacked
pipeline): การใช้คอมโบจะเปิด `languageConfig.enabled` สำหรับคำขอนั้น และตั้งค่า
`defaultLanguage` จากแพ็กภาษาของคอมโบ (ใช้ค่าที่บันทึกไว้หากเป็นหนึ่งใน
แพ็กของคอมโบ มิฉะนั้นจะใช้แพ็กแรกของคอมโบ ซึ่งมีค่าเริ่มต้นเป็น `en`) ขณะที่ค่า
`autoDetect` ที่บันทึกไว้ (เปิดโดยค่าเริ่มต้น) ยังคงมีผล เอนจินอินพุต Caveman จะเลือก
ภาษาของชุดกฎแตกต่างออกไป — แยกตามแต่ละส่วนข้อความ และเมื่อปิดการตรวจหาอัตโนมัติ
จะถูกควบคุมโดย `enabledPacks`

เมทริกซ์สไตล์ × ภาษาถูกตรึงไว้โดย
`tests/unit/compression/output-styles-i18n-matrix.test.ts`: ทุกสไตล์ในแค็ตตาล็อกต้องมี
รายการใน `BASELINE_LANGUAGES` ของการทดสอบ; สไตล์ที่ไม่ถูกจำกัดตามโลเคลต้องมีคำแปล
pt-BR (`terse-cjk` ที่ถูกจำกัดตามโลเคลได้รับการยกเว้นจากกฎนี้) เว้นแต่จะอยู่ใน
`KNOWN_ENGLISH_ONLY` ซึ่งอนุญาตให้มีได้เฉพาะสไตล์ที่ไม่มีคำแปลเลย —
สไตล์ที่อยู่ในรายการแต่มีคำแปลใด ๆ จะทำให้การทดสอบล้มเหลว; และสไตล์จะทำให้การทดสอบล้มเหลวเมื่อ
สูญเสียภาษาที่ระบุไว้ในรายการ `BASELINE_LANGUAGES` ของตน หากต้องการเพิ่มสไตล์ โปรดดู
[EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)

### การบีบอัดผลลัพธ์จากเครื่องมือ

`compressToolResult()` ใน `open-sse/services/compression/toolResultCompressor.ts`
บีบอัดข้อความผลลัพธ์จากเครื่องมือด้วย **5 กลยุทธ์** โดยจะลองตามลำดับต่อไปนี้ และ
กลยุทธ์แรกที่เปิดใช้งานและมีเงื่อนไขตรงกับเนื้อหาจะเป็นตัวกำหนดผลลัพธ์:

1. **`fileContent`**: เนื้อหาที่มี 3 บรรทัดขึ้นไป โดยมีอย่างน้อยหนึ่งบรรทัดที่เมื่อไม่นับ
   การเยื้องนำหน้าแล้ว เริ่มต้นด้วย `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` หรือ `return ` (คีย์เวิร์ดตามด้วยช่องว่าง) หรือเริ่มต้นด้วย `if`,
   `for` หรือ `while` ตามด้วย `(` หรือ ` (` จะเก็บ 20 บรรทัดแรกและ 5 บรรทัดสุดท้ายไว้ พร้อม
   ทำเครื่องหมายส่วนกลางที่ถูกละไว้
2. **`grepSearch`**: เนื้อหาที่มีอย่างน้อยหนึ่งบรรทัดในรูปแบบ `<path>:<digits>:`
   โดยข้อความก่อนเครื่องหมายโคลอนตัวแรกต้องไม่มีช่องว่าง จะเก็บไว้เฉพาะบรรทัดเหล่านั้น
   สูงสุด 30 บรรทัด ตามด้วยจำนวนรายการที่ตรงกันเพิ่มเติมและรายชื่อไฟล์ที่ตรงกัน
   ส่วนบรรทัดอื่นทั้งหมดจะถูกทิ้ง เพียงบรรทัดเดียวในรูปแบบดังกล่าวก็เพียงพอที่จะเรียกใช้กลยุทธ์นี้
   ดังนั้นบรรทัดบันทึกที่ขึ้นต้นด้วยการประทับเวลา เช่น `12:30:45` จึงถือว่าตรงเงื่อนไขเช่นกัน
3. **`shellOutput`**: เอาต์พุตที่มีลำดับ ANSI CSI (`ESC[` ตามด้วยตัวเลขหรือ
   เครื่องหมายอัฒภาค แล้วตามด้วยตัวอักษร เช่นในรหัสสี) หรือมี `$` ตามด้วยช่องว่าง
   ที่ตำแหน่งใดก็ตามในข้อความ จะสูญเสียลำดับเหล่านั้น (ลำดับหลีกอื่น เช่น `ESC[?25l` หรือ
   ลำดับชื่อหน้าต่าง OSC จะยังคงอยู่) และเก็บ 50 บรรทัดสุดท้ายไว้ โดยยุบบรรทัดที่ซ้ำกัน
   ต่อเนื่องให้เหลือบรรทัดเดียว เนื่องจากการตรวจสอบนี้ทำงานก่อน `json` และ `errorMessage`
   เอาต์พุต JSON หรือเอาต์พุตข้อผิดพลาดที่มี `$` ดังกล่าวจึงไม่มีทางไปถึงกลยุทธ์เหล่านั้นเมื่อ
   เปิดใช้ `shellOutput`
4. **`json`**: เพย์โหลด JSON ที่ยาวเกิน 2,000 อักขระ ซึ่งเริ่มต้นด้วย `{` หรือ `[` (หลัง
   ช่องว่างที่อาจมีหรือไม่มีก็ได้) และสามารถแยกวิเคราะห์ได้ จะถูกสรุปดังนี้: อาร์เรย์ที่มีมากกว่า 7 รายการจะเก็บ
   5 รายการแรกและ 2 รายการสุดท้าย พร้อมจำนวนรายการทั้งหมด ส่วนออบเจ็กต์จะเก็บ 20
   คีย์แรก โดยแทนค่าออบเจ็กต์หรืออาร์เรย์ที่ซ้อนกันแต่ละค่าด้วยตัวยึดตำแหน่ง `{…N keys}`
   (สำหรับอาร์เรย์ N คือความยาวของอาร์เรย์) และเพิ่มเครื่องหมาย `_remaining_<N>_keys` เพื่อนับจำนวนคีย์
   ที่ถูกทิ้งหลังจาก 20 คีย์แรก ค่าสเกลาร์จะถูกคัดลอกทั้งหมด ดังนั้นออบเจ็กต์ที่มีไม่เกิน 20 คีย์
   และไม่มีค่าซ้อนกันจะเพียงแค่ถูกจัดการเยื้องใหม่ — หากเป็นแบบย่อในบรรทัดเดียว จำนวนอักขระจะเพิ่มขึ้น
   และจึงยังคงไว้โดยไม่เปลี่ยนแปลง
5. **`errorMessage`**: เอาต์พุตที่มี `error:`, `error ` (คำตามด้วยช่องว่าง เช่น
   `no error found`), `[error]`, `exception:`, `exception `, `[exception]` หรือ `traceback`
   อยู่ที่ตำแหน่งใดก็ตามและไม่ว่าจะใช้อักษรตัวพิมพ์เล็กหรือใหญ่ จะเก็บบรรทัดแรก
   10 บรรทัดถัดไป และ 3 บรรทัดสุดท้าย โดยใช้เครื่องหมาย `… [N frames elided] …` แทน
   บรรทัดที่อยู่ระหว่างนั้น เครื่องหมายนี้จะปรากฏเฉพาะเมื่อมีมากกว่า 13 บรรทัดต่อจากบรรทัดแรก
   ดังนั้นเอาต์พุตข้อผิดพลาดที่มีไม่เกิน 14 บรรทัดจะไม่ถูกย่อ (หากมี 12 หรือ 13 บรรทัด
   3 บรรทัดสุดท้ายจะซ้ำกับบรรทัดที่เก็บไว้แล้ว)

หลังจากกลยุทธ์ใดตรงเงื่อนไข แม้จะเป็นกลยุทธ์ที่ไม่ประหยัดอะไรเลย กลยุทธ์ถัดไปก็จะไม่
ถูกลองใช้ เมื่อกลยุทธ์ที่ตรงเงื่อนไขไม่ประหยัดโทเค็นโดยประมาณ (ความยาว ÷ 4 ปัดขึ้น) —
เช่น ไฟล์ที่มีลักษณะคล้ายโค้ดซึ่งมีไม่เกิน 25 บรรทัด หรืออาร์เรย์ JSON ที่ยาวเกิน 2,000
อักขระแต่มีไม่เกิน 7 รายการ — เอนจินแบบเข้มข้นจะเก็บผลลัพธ์เครื่องมือเดิมไว้:
ตัวเรียกทั้งสอง (`compressAggressive()` และ `compressAnthropicToolResultBlock()`)
จะเก็บต้นฉบับเมื่อ `saved` มีค่าเป็น 0 หรือต่ำกว่า ขณะที่ `compressToolResult()` เองยังคง
ส่งคืนเอาต์พุตของกลยุทธ์นั้น ขั้นตอนผลลัพธ์เครื่องมือไม่ใช่การตัดสินขั้นสุดท้าย:
ตัวสรุปสำรองของเอนจินยังสามารถย่อข้อความ `tool` หรือ `function` ที่ยาวกว่า
8,192 อักขระ (`maxTokensPerMessage`, 2,048, คูณ 4) ได้

#### ควรใช้เมื่อใด

การบีบอัดผลลัพธ์เครื่องมือเป็นขั้นตอนที่ 1 ของเอนจินแบบเข้มข้น (`compressAggressive()` ใน
`open-sse/services/compression/aggressive.ts`) ดังนั้นจึงทำงานในโหมด Aggressive และใน
ขั้นตอน `aggressive` ของไปป์ไลน์แบบซ้อน โดยจะบีบอัดข้อความ `tool` และ `function`
ในรูปแบบ OpenAI และข้อความภายในบล็อก `tool_result` ของ Anthropic แต่ละกลยุทธ์มี
สวิตช์ของตนเองภายใต้ `aggressive.toolStrategies` ซึ่งเปิดไว้ทั้งหมดโดยค่าเริ่มต้น ในแดชบอร์ด
สวิตช์เหล่านี้อยู่ในมุมมอง **Advanced** ของหน้า Caveman ขณะที่เปิดการบีบอัดและ
โหมดเริ่มต้นเป็น Aggressive

### ไปป์ไลน์แบบซ้อน

โหมดซ้อนจะเรียกใช้ **หลายเอนจินตามลำดับ** — โดยทั่วไปใช้ RTK ก่อน
(ประหยัดเอาต์พุตเครื่องมือได้ 60-90%) จากนั้นใช้ Caveman กับข้อความที่เหลือ (ประหยัด
อินพุตได้ประมาณ 46%) เมื่อใช้ร่วมกัน จะได้ **ช่วงที่ประหยัดได้ 78-95%** (ดูการคำนวณการประหยัดต้นทาง
ด้านบน): `1 - (1 - 0.60..0.90) × (1 - 0.46)` เฉลี่ย ≈89%

#### วิธีการทำงาน

```
อินพุต (1000 โทเค็น)
  → RTK (ตัวกรองที่รับรู้คำสั่ง) → 200 โทเค็น
    → Caveman (ลบข้อความส่วนเกิน) → 108 โทเค็น
  → เอาต์พุต (108 โทเค็น, ประหยัด ~89%)
```

#### ควรใช้เมื่อใด

ใช้โหมดซ้อนสำหรับ:

- เวิร์กโฟลว์ที่ใช้เครื่องมืออย่างเข้มข้น (การเขียนโค้ดแบบเอเจนต์, การวิจัย)
- การประมวลผลแบบแบตช์ที่คำนึงถึงต้นทุน
- เมื่อคุณต้องการประหยัดโทเค็นให้ได้มากที่สุด

ไปป์ไลน์แบบซ้อนได้รับการกำหนดค่าผ่านการตั้งค่าการบีบอัดส่วนกลาง `stackedPipeline`
หรือผ่านคอมโบการบีบอัดที่มีชื่อซึ่งกำหนดให้กับคอมโบการกำหนดเส้นทาง (ดู
การแทนที่ต่อคอมโบด้านบน) — ไม่ใช่ผ่าน `modePack` ของคอมโบอัตโนมัติ (ฟิลด์นั้นมีไว้
ปรับน้ำหนักการเลือกโมเดลของคอมโบอัตโนมัติเท่านั้น และ `stacked` ไม่ใช่ชื่อแพ็กที่ใช้ได้)

## การกำหนดค่าทับสำหรับชุดคอมโบการบีบอัด

คุณสามารถกำหนดโหมดการบีบอัดส่วนกลางทับ **เป็นรายคอมโบ** เพื่อปรับแต่งลักษณะการทำงาน
ให้เหมาะสมกับกรณีการใช้งานต่างๆ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

สิ่งนี้มีประโยชน์สำหรับ:

- **คอมโบการเขียนโค้ด**: ใช้โหมด `aggressive` สำหรับเซสชันที่ยาวนาน
- **คอมโบถาม-ตอบแบบรวดเร็ว**: ใช้โหมด `lite` เพื่อการตอบกลับที่รวดเร็ว
- **คอมโบที่ใช้เครื่องมือจำนวนมาก**: ใช้โหมด `stacked` เพื่อประหยัดสูงสุด
- **คอมโบสำหรับระบบใช้งานจริง**: ปิดการกำหนดค่าทับไว้สำหรับผู้ให้บริการที่รองรับการแคช — การปรับค่า
  โดยคำนึงถึงแคชซึ่งเปิดใช้งานอยู่เสมอ จะลดระดับ `aggressive`/`ultra` เป็น `standard` โดยอัตโนมัติ
  (ไม่มีโหมด `cache-aware` ที่สามารถเลือกได้)
