## ภาพรวม

OmniRoute ใช้ไปป์ไลน์การบีบอัดพรอมต์แบบโมดูลาร์ซึ่งทำงาน **เชิงรุก** ก่อนที่คำขอจะไปถึงผู้ให้บริการต้นทาง ซึ่งหมายความว่าคุณจะประหยัดโทเค็นได้อย่างโปร่งใส โดยไม่ต้องเปลี่ยนแปลงเวิร์กโฟลว์

```
คำขอจากไคลเอนต์
  → ตัวเลือกกลยุทธ์การบีบอัด
    → มีการแทนที่ด้วยคอมโบหรือไม่? → ใช้การตั้งค่าคอมโบ
    → ถึงเกณฑ์ทริกเกอร์อัตโนมัติหรือไม่? → ใช้โหมดอัตโนมัติ
    → มีโหมดเริ่มต้นหรือไม่? → ใช้การตั้งค่าส่วนกลาง
    → ปิดอยู่หรือไม่? → ข้ามการบีบอัด
  → โหมดการบีบอัดที่เลือก
    → ปิด: ไม่มีการบีบอัด
    → เบา: ล้างช่องว่าง/การจัดรูปแบบอย่างปลอดภัย (~15%)
    → มาตรฐาน: ตัดคำฟุ่มเฟือยแบบภาษามนุษย์ถ้ำ (~30%)
    → เข้มข้น: ลดทอนประวัติตามอายุ + สรุปเนื้อหา (~50%)
    → สูงสุด: ตัดทอนด้วยฮิวริสติก + ลดทอนบล็อกโค้ด (~75%)
    → RTK: กรองเอาต์พุตจากเทอร์มินัล/เครื่องมือโดยคำนึงถึงคำสั่ง (ช่วงต้นทาง 60-90%)
    → แบบซ้อน: ไปป์ไลน์หลายเอนจินตามลำดับ โดยทั่วไปคือ RTK แล้วตามด้วย Caveman (ช่วงที่เข้าเกณฑ์ 78-95%)
  → คำขอที่บีบอัดแล้ว → ผู้ให้บริการ
```

## โหมดการบีบอัด

### ปิด

ไม่มีการบีบอัด ข้อความทั้งหมดจะถูกส่งผ่านโดยไม่มีการเปลี่ยนแปลง

### โหมดเบา (ประหยัด ~15%, เวลาแฝง <1ms)

โหมดที่ปลอดภัยที่สุด — ไม่มีการเปลี่ยนแปลงความหมาย มีเพียงการล้างการจัดรูปแบบ:

| เทคนิค                   | คำอธิบาย                                            |
| ------------------------ | --------------------------------------------------- |
| `collapseWhitespace`     | รวมบรรทัดว่างที่ต่อเนื่องกันและลบช่องว่างท้ายบรรทัด |
| `dedupSystemPrompt`      | ลบข้อความระบบที่ซ้ำกัน                              |
| `compressToolResults`    | บีบอัดเอาต์พุตแบบละเอียดจากเครื่องมือ/ฟังก์ชัน      |
| `removeRedundantContent` | ลบคำสั่งที่ซ้ำกัน                                   |
| `replaceImageUrls`       | ย่อ URI ข้อมูลรูปภาพแบบ base64                      |

**เหมาะที่สุดสำหรับ:** การใช้งานแบบเปิดไว้ตลอดและเวิร์กโฟลว์ที่ให้ความสำคัญกับความปลอดภัย

### โหมดมาตรฐาน (ประหยัด ~30%)

ได้รับแรงบันดาลใจจาก [Caveman](https://github.com/JuliusBrussee/caveman) — ตัดคำเติมและถ้อยคำฟุ่มเฟือยโดยยังคงความหมายไว้:

- ตัดคำเติม ("please", "I think", "basically", "actually")
- ย่อวลีฟุ่มเฟือย ("in order to" → "to", "as a result of" → "because")
- ตัดถ้อยคำสุภาพที่แสดงความลังเล ("Would you mind...", "If you could possibly...")
- กฎ regex มากกว่า 30 ข้อที่ปรับแต่งมาสำหรับพรอมต์การเขียนโค้ด

**เหมาะที่สุดสำหรับ:** เวิร์กโฟลว์การเขียนโค้ดประจำวันและทีมที่คำนึงถึงต้นทุน

### โหมดเข้มข้น (ประหยัด ~50%)

การจัดการประวัติอย่างชาญฉลาดสำหรับเซสชันที่ยาวนาน:

- **การลดทอนข้อความตามอายุ** — ข้อความเก่าจะถูกบีบอัดมากขึ้นเรื่อยๆ
- **การสรุปผลลัพธ์จากเครื่องมือ** — เอาต์พุตจากเครื่องมือที่ยาวจะถูกแทนที่ด้วยบทสรุป
- **กลไกป้องกันความสมบูรณ์ของโครงสร้าง** — ทำให้แน่ใจว่าคู่ `tool_use` + `tool_result` ยังคงสอดคล้องกัน
- **การรับรู้ขนาดหน้าต่างบริบท** — เคารพขีดจำกัดโทเค็นของแต่ละโมเดล

**เหมาะที่สุดสำหรับ:** เซสชันดีบักที่ยาวนานและฐานโค้ดขนาดใหญ่

### โหมดสูงสุด (ประหยัด ~75%)

การบีบอัดสูงสุดสำหรับสถานการณ์ที่โทเค็นมีความสำคัญอย่างยิ่ง:

- **การตัดทอนด้วยฮิวริสติก** — ลบข้อความที่มีค่าต่ำกว่าเกณฑ์ความเกี่ยวข้อง
- **การลดทอนบล็อกโค้ด** — บีบอัดตัวอย่างโค้ดที่ซ้ำซาก
- **การตัดข้อความด้วยการค้นหาแบบทวิภาค** — ค้นหาจุดตัดที่เหมาะสมที่สุดสำหรับหน้าต่างบริบท
- รวมคุณสมบัติทั้งหมดของโหมดเข้มข้น

**เหมาะที่สุดสำหรับ:** เมื่อคุณชนขีดจำกัดบริบทซ้ำๆ

### โหมด RTK (ช่วงต้นทาง 60-90%)

โหมด RTK ได้รับการปรับให้เหมาะกับเอาต์พุตแบบละเอียดจากเครื่องมือที่ปรากฏในเซสชันของเอเจนต์เขียนโค้ด:

- ตรวจหาคลาสของคำสั่ง/เอาต์พุต เช่น `git status`, `git diff`, `git log`, ตัวรันทดสอบ,
  การบิลด์ด้วย TypeScript/Vite/Webpack, ESLint/Biome/Prettier, การตรวจสอบ/ติดตั้งด้วย npm, ล็อก Docker, เอาต์พุต
  โครงสร้างพื้นฐาน และเอาต์พุตเชลล์ทั่วไป
- ใช้ชุดตัวกรอง JSON จาก `open-sse/services/compression/engines/rtk/filters/`
- นำเข้าตัวกรองสคีมา RTK TOML v1 จากไฟล์ `filters.toml` ของโปรเจกต์หรือส่วนกลาง พร้อมการตรวจสอบ
  การทดสอบแบบอินไลน์และการควบคุมตามความเชื่อถือสำหรับไฟล์โปรเจกต์
- มาพร้อมตัวกรองในตัว 49 รายการพร้อมตัวอย่างการตรวจสอบแบบอินไลน์
- ลบลำดับควบคุม ANSI, แถบความคืบหน้า, บรรทัดที่ซ้ำกัน และสัญญาณรบกวนที่ไม่ก่อให้เกิดการดำเนินการ
- เก็บรักษาความล้มเหลว ข้อผิดพลาด คำเตือน ไฟล์ที่เปลี่ยนแปลง บทสรุป และส่วนท้ายของเอาต์พุตที่ยาว
- รองรับตัวกรองโปรเจกต์ที่ควบคุมตามความเชื่อถือ ตัวกรองส่วนกลาง และตัวเลือกการกู้คืนเอาต์พุตดิบที่ผ่านการปกปิดข้อมูล

**เหมาะที่สุดสำหรับ:** เซสชันของเอเจนต์ที่มีทรานสคริปต์จากเชลล์ การบิลด์ การทดสอบ git, grep และเอาต์พุตไฟล์

### โหมดแบบซ้อน (ช่วงที่เข้าเกณฑ์ 78-95%)

โหมดแบบซ้อนเรียกใช้เอนจินการบีบอัดหลายตัวตามลำดับที่กำหนดแน่นอน ไปป์ไลน์เริ่มต้นคือ:

```txt
RTK -> Caveman
```

ลำดับนี้จะทำให้เอาต์พุตจากเทอร์มินัล/เครื่องมือมีขนาดกะทัดรัดก่อน จากนั้นจึงใช้การย่อความหมายของ Caveman กับ
พรอมต์ภาษาธรรมชาติที่เหลืออยู่ ไปป์ไลน์แบบซ้อนสามารถกำหนดค่าได้ทั้งแบบส่วนกลางหรือผ่าน
คอมโบการบีบอัดที่กำหนดให้กับคอมโบการกำหนดเส้นทาง

**เหมาะที่สุดสำหรับ:** บริบทแบบผสมที่มีทั้งล็อกจากเครื่องมือขนาดใหญ่ รวมถึงคำสั่งจากมนุษย์หรือบทสรุปจากผู้ช่วย

## การคำนวณการประหยัดจากต้นทาง

OmniRoute อธิบายการประหยัดจากการบีบอัดโดยอ้างอิงจากสองแหล่ง ได้แก่ ผลการวัดประสิทธิภาพของโปรเจกต์ต้นทางและ
การทำงานร่วมกันของเอนจินภายใน OmniRoute เอง

| แหล่งที่มา | ตัวเลขจาก README ต้นทางที่ใช้ในที่นี้                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Caveman    | โทเค็นเอาต์พุตน้อยลง `~75%`, ประหยัดเอาต์พุตโดยเฉลี่ยจากการวัดประสิทธิภาพ `65%`, ช่วง `22-87%` และเครื่องมือบีบอัดอินพุต `~46%` |
| RTK        | ประหยัดเอาต์พุตคำสั่ง `60-90%`; เซสชันตัวอย่างลดจาก `~118,000 -> ~23,900` โทเค็น หรือประหยัด `79.7%` (`~80%`)                   |

สำหรับเพย์โหลดเครื่องมือ/บริบทที่ทับซ้อนกัน ชุดการทำงานร่วมกันเริ่มต้นของ OmniRoute จะเรียงเอนจินดังนี้:

```txt
RTK -> Caveman
```

การประหยัดรวมคำนวณแบบคูณ ไม่ใช่แบบบวก:

```txt
รวม       = 1 - (1 - การประหยัดของ RTK) * (1 - การประหยัดอินพุตของ Caveman)
ค่าเฉลี่ย = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
ช่วง      = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

ตัวเลข `78-95%` นี้ใช้ได้เมื่อทั้ง RTK และ Caveman สามารถลดเพย์โหลดอินพุต/บริบทเดียวกันได้
โหมดเอาต์พุตการตอบกลับของ Caveman เป็นอีกส่วนหนึ่ง: เมื่อเปิดใช้งาน ให้ใช้ตัวเลขการประหยัดเอาต์พุตของ Caveman เอง (`65%`
โดยเฉลี่ย, `~75%` ตามตัวเลขหลักที่นำเสนอ, ช่วง `22-87%`) การประหยัดค่าใช้จ่ายทั้งหมดขึ้นอยู่กับสัดส่วนพรอมต์/เอาต์พุตของคุณ

### ความหมายที่แท้จริงของคำว่า "เข้าเกณฑ์"

ช่วงตัวเลขหลัก 15-95% เป็นตัวเลขจริง แต่ใช้ได้เฉพาะกับเนื้อหาที่ **ซ้ำซ้อนหรือเยิ่นเย้อ** เท่านั้น เช่น บรรทัดข้อผิดพลาด
ที่ซ้ำกัน, บันทึกการบิลด์ที่แสดงคำเตือนเดิมซ้ำจำนวนมาก หรือผลลัพธ์จาก `grep`/การอ่านไฟล์ที่มีขนาดใหญ่เกินไป ทั้งนี้
**ไม่ได้** หมายความว่าทุกคำขอจะประหยัดได้มากขนาดนั้น

มีการยืนยันจากการทดลองแล้ว (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): การรัน
`stacked` (RTK + Caveman) กับบล็อก `tool_result` รูปแบบ Anthropic ซึ่งมีบรรทัดข้อผิดพลาดเหมือนกัน 300 บรรทัด
ให้ผลลัพธ์เป็น **การประหยัดโทเค็น 95.93% / การประหยัดอักขระ 96.26%** ซึ่งอยู่ในช่วงที่ระบุไว้อย่างชัดเจน
แต่เมื่อใช้ไปป์ไลน์เดียวกันกับเอาต์พุตเครื่องมือปกติที่ไม่ซ้ำซ้อน (รายการผลลัพธ์ `grep` ที่สะอาด,
การอ่านไฟล์ขนาดสั้น, ข้อความสนทนาทั่วไป) ระบบจะให้ผลเป็น **การประหยัดเกือบเป็นศูนย์** อย่างถูกต้อง เพราะ
ไม่มีสิ่งที่ซ้ำให้ตัดออก และ `validateCompression()` (`validation.ts`) จะปฏิเสธการส่ง
ข้อความที่เขียนใหม่ หากการเขียนใหม่นั้นทำให้บล็อกโค้ด, URL, หัวข้อ, เวอร์ชัน หรือตัวระบุค่าคงที่แบบ ALL-CAPS สูญหายหรือเปลี่ยนแปลง

นี่เป็นพฤติกรรมที่ปลอดภัยและเป็นไปตามที่คาดไว้ ไม่ใช่บั๊ก: เซสชันเขียนโค้ดที่ส่วนใหญ่เป็นการอ่าน/ค้นหาไฟล์ที่สะอาด
จะประหยัดโดยรวมได้เพียงเล็กน้อย แม้จะเปิดใช้งานการบีบอัดเต็มรูปแบบแล้วก็ตาม ขณะที่เซสชันซึ่งพบลูปที่ล้มเหลว
หรือลินเตอร์ที่แสดงข้อความจำนวนมาก จะประหยัดได้เต็มช่วง 78-95% สำหรับทราฟฟิกส่วนนั้น อย่าใช้เปอร์เซ็นต์การประหยัดรวม
ที่ต่ำจากเซสชันเดียวเป็นหลักฐานว่าการบีบอัดตั้งค่าผิด — ให้ตรวจสอบก่อนว่า
เอาต์พุตเครื่องมือต้นทางมีความซ้ำซ้อนจริงหรือไม่

## การกำหนดค่า

### แดชบอร์ด

ไปที่ `Dashboard → Context & Cache`:

- **Caveman** — การเลือกโหมด แพ็กภาษา การแสดงตัวอย่าง และค่าเริ่มต้นส่วนกลาง
- **RTK** — การแสดงตัวอย่างตัวกรองคำสั่ง การตั้งค่าความปลอดภัยของ RTK และแค็ตตาล็อกตัวกรอง
- **Compression Combos** — ไปป์ไลน์เอนจินที่มีชื่อซึ่งกำหนดให้กับคอมโบการกำหนดเส้นทาง
- **Auto-Trigger Threshold** — เริ่มใช้การบีบอัดโดยอัตโนมัติเมื่อจำนวนโทเค็นเกินเกณฑ์

### การเขียนทับรายคอมโบ

ใน `Dashboard → Context & Cache → Compression Combos` ให้กำหนดคอมโบการบีบอัดแก่คอมโบการกำหนด
เส้นทาง:

```txt
คอมโบ: "free-tier-fallback"
  คอมโบการบีบอัด: "coding-agent-stack"
  ไปป์ไลน์: RTK -> Caveman
  เป้าหมาย:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

วิธีนี้ช่วยให้คุณใช้การบีบอัดแบบซ้อนกับผู้ให้บริการแบบฟรี/สำหรับเขียนโค้ด ขณะที่ยังคงใช้โหมด lite กับการ
สมัครสมาชิกแบบชำระเงิน

การกำหนด "การเขียนทับรายคอมโบ" นี้เป็นตัวควบคุมที่แตกต่างจากการเขียนทับ **โหมดการบีบอัดของคอมโบการกำหนด
เส้นทาง** (Default/Off/Lite/Standard/Aggressive/Ultra) — การเขียนทับดังกล่าวไม่ได้เลือกไปป์ไลน์คอมโบ
การบีบอัดที่มีชื่อ แต่เพียงตั้งค่าฟิลด์ `compressionMode` ซึ่ง `resolveCompressionPlan` ใช้อ้างอิง
โดยสามารถตั้งค่าได้ทั้งบนการ์ดคอมโบ (`Dashboard → Combos`) หรือ ตั้งแต่
#6760 เป็นต้นมา สามารถตั้งค่าแยกตามคอมโบการกำหนดเส้นทางได้ในรายการ "Assign to routing" ที่
`Dashboard → Context & Cache → Compression Combos` ซึ่งอยู่ถัดจากช่องทำเครื่องหมายกำหนดไปป์ไลน์
ที่อธิบายไว้ข้างต้น ทั้งสองส่วนจะบันทึกค่าผ่านเอนด์พอยต์ `PUT /api/combos/{id}` เดียวกัน

### การเขียนทับรายคำขอ

ส่งส่วนหัวคำขอ `x-omniroute-compression` เพื่อเขียนทับแผนการบีบอัดสำหรับคำขอรายการเดียว
ส่วนหัวนี้มีลำดับความสำคัญสูงสุด — เหนือกว่าการเขียนทับของคอมโบการกำหนดเส้นทาง โปรไฟล์ที่ใช้งานอยู่
การทริกเกอร์อัตโนมัติ และค่า Default ของแผง ค่าที่ไม่รู้จักจะถูกละเว้น (คำขอจะไม่ถูกปฏิเสธ) และ
สวิตช์หลักส่วนกลางยังคงควบคุมทุกอย่าง: เมื่อปิดการบีบอัดไว้โดยรวม ส่วนหัวจะไม่สามารถ
เปิดใช้งานได้ ค่า:

| ค่า           | ผลลัพธ์                                                                                |
| ------------- | -------------------------------------------------------------------------------------- |
| `off`         | ไม่มีการบีบอัดสำหรับคำขอนี้                                                            |
| `default`     | โปรไฟล์ Default ที่ได้จากแผง (ไม่สนใจโปรไฟล์ที่ใช้งานอยู่)                             |
| `engine:<id>` | เอนจินเดียวเมื่อเปิดใช้งาน เช่น `engine:rtk`                                           |
| `<combo>`     | คอมโบที่มีชื่อ โดยจับคู่จากชื่อก่อน (ไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่) แล้วจึงจับคู่จาก id |

แผนที่นำไปใช้จะถูกส่งกลับในส่วนหัวการตอบกลับ `X-OmniRoute-Compression: <mode>; source=<source>`
โดย `<source>` จะเป็นค่าใดค่าหนึ่งจาก `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` หรือ `off`

### API

```bash

# อัปเดตการตั้งค่าการบีบอัด

# ทดสอบ RTK โดยตรงพร้อมข้อมูลเมตาของคำสั่งที่ระบุหรือไม่ก็ได้
```

## ระบบการบีบอัดขั้นสูง

นอกเหนือจากโหมดมาตรฐานทั้ง 7 โหมดแล้ว OmniRoute ยังมีระบบการบีบอัดขั้นสูงหลายระบบ
ที่ทำงานโดยอัตโนมัติตามบริบท

### การบีบอัดที่คำนึงถึงแคช

ผู้ให้บริการบางราย (เช่น Anthropic ที่มีการแคชพรอมต์) รองรับ **การแคชพรอมต์**
ซึ่งช่วยให้สามารถแคชบางส่วนของพรอมต์เพื่อลดต้นทุนและเวลาแฝงได้ เมื่อ
เปิดใช้งานการแคช การบีบอัดเชิงรุกอาจ **ทำให้** ประสิทธิภาพแย่ลง
เพราะการบีบอัดจะเปลี่ยนโทเค็นที่ถูกแคช ทำให้แคชใช้การไม่ได้

โมดูล `cachingAware.ts` แก้ปัญหานี้ด้วยการ **ตรวจจับบริบทการแคช** และ
**ปรับกลยุทธ์การบีบอัด** ให้เหมาะสม

#### วิธีการทำงาน

1. **ตรวจจับบริบทการแคช** — สแกนเนื้อหาคำขอเพื่อหาเครื่องหมาย `cache_control`
2. **ระบุผู้ให้บริการที่รองรับการแคช** — ตรวจสอบว่าผู้ให้บริการเป้าหมายรองรับการแคชหรือไม่
3. **ปรับกลยุทธ์** — ลดระดับจาก `aggressive`/`ultra` เป็น `standard` สำหรับผู้ให้บริการที่รองรับการแคช
4. **ข้ามพรอมต์ระบบ** — โดยปกติพรอมต์ระบบจะถูกแคช ดังนั้นจึงไม่ควรบีบอัด
5. **ใช้การแปลงแบบกำหนดผลลัพธ์แน่นอน** — ใช้เฉพาะการแปลงที่ให้ผลลัพธ์สม่ำเสมอ

#### ตัวอย่างโค้ด

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← เครื่องหมายแคช
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### ควรใช้เมื่อใด

การบีบอัดที่คำนึงถึงแคช **เปิดใช้งานอยู่เสมอ** — ไม่จำเป็นต้องกำหนดค่า ระบบจะเริ่มทำงานเฉพาะ
เมื่อ:

- คำขอมีเครื่องหมาย `cache_control`
- ผู้ให้บริการเป้าหมายรองรับการแคชพรอมต์ (Anthropic, OpenAI เป็นต้น)

### การลดรายละเอียดตามอายุแบบก้าวหน้า

บทสนทนาที่ยาวจะสะสมข้อความโต้ตอบหลายรอบ แต่รอบที่เก่ากว่าจะมีความเกี่ยวข้อง
น้อยลง โมดูล `progressiveAging.ts` จะ **ลดรายละเอียดของข้อความตามระยะห่างของรอบสนทนา**:

- **รอบล่าสุด (0-3)**: เก็บไว้ตามต้นฉบับ (รายละเอียดครบถ้วน)
- **รอบช่วงกลาง (4-8)**: บีบอัดแบบ Lite (ล้างช่องว่างและการจัดรูปแบบ)
- **รอบเก่า (9+)**: บีบอัดแบบ Caveman (ตัดข้อความส่วนเกินและสรุปเนื้อหา)
- **รอบที่เก่ามาก (20+)**: สรุปอย่างมากหรือลบทิ้ง

#### ตัวอย่างโค้ด

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... อีก 50 รอบ ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // 3 รอบแรก: คงไว้ตามต้นฉบับ
  light: 8, // รอบที่ 4-8: บีบอัดแบบ lite
  moderate: 20, // รอบที่ 9-20: บีบอัดแบบ caveman
  // รอบที่ 21 เป็นต้นไป: สรุปอย่างมาก
});

// saved = จำนวนโทเค็นที่ประหยัดได้
```

#### ควรใช้เมื่อใด

การทำให้เก่าลงแบบก้าวหน้าเปิดใช้งาน **ตลอดเวลา** สำหรับโหมด `aggressive` และ `ultra` โดยมีประสิทธิภาพเป็นพิเศษสำหรับ:

- เซสชันการเขียนโค้ดที่ทำงานเป็นเวลานาน
- การสนทนาที่ดำเนินต่อเนื่องหลายวัน
- เวิร์กโฟลว์แบบเอเจนต์ที่มีการเรียกใช้เครื่องมือจำนวนมาก

### โหมดเอาต์พุต Caveman

โมดูล `outputMode.ts` จะแทรก **คำสั่งพรอมต์ระบบ** เพื่อให้โมเดลสร้างเอาต์พุตที่กระชับและสั้นห้วน (สไตล์ "มนุษย์ถ้ำ") ด้วยตัวเอง

#### วิธีการทำงาน

แทนที่จะบีบอัดอินพุต โหมดนี้จะเพิ่มพรอมต์ระบบดังนี้:

> "ตอบโดยใช้คำน้อยที่สุด ข้ามคำทักทาย ใช้ประโยคสั้น"

วิธีนี้ได้ผลดีเป็นพิเศษสำหรับ:

- การสร้างโค้ด (เอาต์พุตกระชับขึ้น = ใช้โทเคนน้อยลง)
- การถามตอบอย่างรวดเร็ว (ไม่จำเป็นต้องอธิบายอย่างละเอียด)
- การประมวลผลแบบกลุ่ม (เพิ่มปริมาณงานสูงสุด)

#### ควรใช้เมื่อใด

โหมดเอาต์พุต Caveman เป็นแบบ **เลือกเปิดใช้** — ตั้งค่าผ่านการกำหนดค่าแบบ combo:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

### สไตล์เอาต์พุต (แค็ตตาล็อก)

โหมดเอาต์พุต Caveman ข้างต้นเป็น **เส้นทางสไตล์เดียวแบบเดิม** Phase 4 ได้ขยายให้เป็นแค็ตตาล็อกของสไตล์เอาต์พุตที่ประกอบร่วมกันได้: `OUTPUT_STYLE_CATALOG` ใน `open-sse/services/compression/outputStyles/catalog.ts` แต่ละสไตล์คือคำสั่งพรอมต์ระบบที่ทำให้โมเดลสร้างเอาต์พุตที่ประหยัดขึ้นด้วยตัวเอง โดยสามารถเปิดใช้หลายสไตล์ร่วมกันได้ และระบบจะแทรกตามลำดับในแค็ตตาล็อก

#### วิธีการแทรก

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) จะตรวจสอบรายการที่เลือกกับแค็ตตาล็อก (id ที่ไม่รู้จักและสไตล์ที่ไม่ตรงกับโลเคลจะถูกตัดออกโดยไม่ถือเป็นข้อผิดพลาด) เชื่อมคำสั่งที่เลือกตามลำดับในแค็ตตาล็อก เพิ่มข้อกำหนดขอบเขต **หนึ่งครั้ง** และวางผลลัพธ์ไว้ด้านหน้าพรอมต์ระบบหลังเครื่องหมายป้องกันการทำซ้ำเพียงจุดเดียว (`[OmniRoute Output Styles]`) — การนำไปใช้อีกครั้งจะไม่ทำสิ่งใด เมื่อภาษาของคำขอที่ตรวจพบมีคำแปล ระบบจะแทรกคำสั่งฉบับภาษาท้องถิ่นแทนภาษาอังกฤษ

#### วิธีเปิดใช้

ในแดชบอร์ด: **Context → Settings → Compression** — หนึ่งแถวต่อหนึ่งสไตล์ พร้อมสวิตช์เปิด/ปิดและตัวเลือกระดับ ในเชิงโปรแกรม การกำหนดค่าการบีบอัดจะบันทึกรายการที่เลือกเป็น:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

ความเข้ากันได้ย้อนหลัง: การตั้งค่า combo แบบเดิม `outputMode: "caveman"` ยังคงใช้งานได้และแมปไปยัง `terse-prose` โดยเหมือนกับการแทรกแบบเก่าทุกไบต์ในทุกภาษาเดิม

การเลือกภาษา: เมื่อเปิด `languageConfig.enabled` ค่า `autoDetect` จะเลือกภาษาของข้อความล่าสุดจากผู้ใช้ (ใช้ตัวตรวจจับเดียวกับเอนจินอินพุต) การปิด `autoDetect` จะตรึงไว้ที่ `defaultLanguage` หากปิด → ภาษาอังกฤษ

เมทริกซ์สไตล์ × ภาษาถูกตรึงโดย `tests/unit/compression/output-styles-i18n-matrix.test.ts`: สไตล์ใหม่จะเผยแพร่ไม่ได้หากไม่มีคำแปล pt-BR เป็นอย่างน้อย (หรือข้อยกเว้นที่ติดตามไว้อย่างชัดเจน) และสไตล์ที่มีอยู่จะสูญเสียโลเคลโดยไม่มีการแจ้งไม่ได้ หากต้องการเพิ่มสไตล์ โปรดดู [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style)

### การบีบอัดผลลัพธ์จากเครื่องมือ

โมดูล `toolResultCompressor.ts` มี **กลยุทธ์การบีบอัดเฉพาะทาง 5 แบบ** สำหรับผลลัพธ์จากเครื่องมือ (การเรียกฟังก์ชัน เอาต์พุตจากเอเจนต์ ผลการค้นหา เป็นต้น):

1. **การบีบอัดผลการค้นหา** — ลบผลลัพธ์ที่ซ้ำซ้อน และเก็บ top-N ไว้
2. **การบีบอัดการอ่านไฟล์** — ตัดไฟล์ขนาดใหญ่ โดยคงส่วนหัว/อิมพอร์ตไว้
3. **การบีบอัดการเรียกใช้โค้ด** — เก็บเฉพาะ stdout/stderr ที่จำเป็น
4. **การบีบอัดคำสั่งค้นฐานข้อมูล** — จำกัดจำนวนแถว และลบเมทาดาทาที่เยิ่นเย้อ
5. **การบีบอัดการตอบกลับ API** — ตัดฟิลด์ null ออก และย่ออาร์เรย์

#### ควรใช้เมื่อใด

การบีบอัดผลลัพธ์จากเครื่องมือจะเปิด **ตลอดเวลา** เมื่อมีการเรียกใช้เครื่องมือ โดยไม่จำเป็นต้องกำหนดค่า

### ไปป์ไลน์แบบซ้อน

โหมดซ้อนจะเรียกใช้ **เอนจินหลายตัวตามลำดับ** — โดยปกติจะใช้ RTK ก่อน (ประหยัด 60-90% สำหรับเอาต์พุตจากเครื่องมือ) จากนั้นใช้ Caveman (ประหยัดเพิ่มเติม 30% สำหรับข้อความที่เหลือ) ซึ่งทำให้ **ประหยัดรวม 78-95%**

#### วิธีการทำงาน

```
อินพุต (1000 โทเคน)
  → RTK (ตัวกรองที่เข้าใจคำสั่ง) → 200 โทเคน
    → Caveman (ตัดคำฟุ่มเฟือย) → 140 โทเคน
  → เอาต์พุต (140 โทเคน, ประหยัด 86%)
```

#### ควรใช้เมื่อใด

ใช้โหมดซ้อนสำหรับ:

- เวิร์กโฟลว์ที่ใช้เครื่องมืออย่างหนัก (การเขียนโค้ดแบบเอเจนต์ งานวิจัย)
- การประมวลผลแบบกลุ่มที่คำนึงถึงต้นทุน
- เมื่อคุณต้องการประหยัดโทเคนสูงสุด

กำหนดค่าผ่าน combo:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## การแทนที่การบีบอัดสำหรับแต่ละคอมโบ

คุณสามารถแทนที่โหมดการบีบอัดส่วนกลาง **สำหรับแต่ละคอมโบ** เพื่อปรับแต่งลักษณะการทำงาน
ให้เหมาะกับกรณีการใช้งานต่างๆ:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

ฟีเจอร์นี้มีประโยชน์สำหรับ:

- **คอมโบสำหรับการเขียนโค้ด**: ใช้โหมด `aggressive` สำหรับเซสชันที่ยาวนาน
- **คอมโบถาม-ตอบแบบรวดเร็ว**: ใช้โหมด `lite` เพื่อให้ตอบกลับได้รวดเร็ว
- **คอมโบที่ใช้เครื่องมือจำนวนมาก**: ใช้โหมด `stacked` เพื่อประหยัดสูงสุด
- **คอมโบสำหรับระบบที่ใช้งานจริง**: ใช้โหมด `cache-aware` สำหรับผู้ให้บริการที่รองรับการแคช
