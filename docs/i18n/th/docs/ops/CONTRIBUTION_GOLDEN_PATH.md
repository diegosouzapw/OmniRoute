ใช้คู่มือนี้เพื่อเลือกรอบการพัฒนาที่เล็กที่สุดและเชื่อถือได้สำหรับ pull request คู่มือนี้ไม่ได้
ใช้แทนเอกสารสถาปัตยกรรมและความปลอดภัยเฉพาะด้านที่ลิงก์ไว้ด้านล่าง แต่เชื่อมโยงประเภท
การเปลี่ยนแปลงทั่วไปแต่ละประเภทเข้ากับข้อกำหนด การตรวจสอบแบบเจาะจง และความครอบคลุมของ CI

## เส้นทางที่ทุกการเปลี่ยนแปลงต้องดำเนินตาม

1. **เลือกฐานก่อนแก้ไข** ค้นหา branch `release/v*` ที่ยังใช้งานอยู่และมีเวอร์ชันสูงสุด แล้วสร้าง branch จาก
   ปลาย branch ดังกล่าว กำหนดเป้าหมายไปยัง branch นั้น ไม่ใช่ `main` หากมีการระงับการเปลี่ยนแปลงก่อนออกรุ่น อย่ากำหนดเป้าหมายไปยัง branch
   ที่ถูกระงับ ให้ใช้รอบถัดไปที่ยังใช้งานอยู่ตามที่อธิบายไว้ใน
   [โมเดล Branching และ Release](BRANCHING_MODEL.md)
2. **ระบุข้อกำหนด** ระบุ catalog, schema, artifact ที่สร้างขึ้น, public API หรือส่วนติดต่อผู้ใช้
   ทุกส่วนที่ได้รับผลกระทบจากการเปลี่ยนแปลง ตารางด้านล่างระบุชุดเริ่มต้นขั้นต่ำ
3. **เขียนหรืออัปเดตการทดสอบแบบเจาะจง** การเปลี่ยนแปลง production ใน `src/`, `open-sse/`, `electron/` หรือ
   `bin/` ต้องมีการทดสอบอัตโนมัติใน PR เดียวกัน เรียกใช้ไฟล์ทดสอบชุดเล็กที่สุดที่พิสูจน์
   พฤติกรรมดังกล่าวได้ จากนั้นเรียกใช้ gate แบบเจาะจงที่ระบุไว้
4. **ปล่อยให้ CI เรียกใช้เมทริกซ์แบบครอบคลุม** unit shard ทั้งหมด, Vitest, coverage ratchet และ
   production build จะทำงานบน PR ให้เรียกใช้ชุดทดสอบแบบครอบคลุมในเครื่องเฉพาะเมื่อความล้มเหลวจากการทดสอบแบบเจาะจงบ่งชี้ว่า
   มีผลกระทบในวงกว้าง หรือเมื่อการเปลี่ยนแปลงครอบคลุมหลาย subsystem
5. **ปรับให้สอดคล้องก่อน review** Fetch ฐานที่ใช้งานอยู่ ตรวจสอบ commit ใหม่ของฐานและ diff ของคุณเมื่อเทียบกับ
   ฐานนั้น จากนั้น rebase หรือ merge ฐานตาม workflow ของผู้มีส่วนร่วม แก้ conflict ของไฟล์ที่สร้างขึ้น
   และ catalog จากแหล่งต้นทาง สร้างไฟล์เหล่านั้นใหม่ เรียกใช้รอบแบบเจาะจงอีกครั้ง และยืนยันว่า
   PR ยังคงกำหนดเป้าหมายไปยัง release branch ที่ใช้งานอยู่
6. **บันทึกหลักฐาน** ในเทมเพลต PR ให้ระบุคำสั่งที่เรียกใช้ ไฟล์ทดสอบทุกไฟล์ที่เพิ่มหรือเปลี่ยนแปลง
   migration หรือ feature flag และการตรวจสอบเฉพาะ CI ใดๆ ที่ยังรอดำเนินการ

## แนวทางมาตรฐานตามประเภทการเปลี่ยนแปลง

คำสั่งด้านล่างคือการตรวจสอบแบบเจาะจงขั้นต่ำ ไม่ใช่การอนุญาตให้ข้ามการทดสอบที่ครอบคลุม
พฤติกรรมที่คุณเปลี่ยนแปลงโดยตรง

### Provider

**ข้อกำหนด**

- นิยาม Provider ใน `src/shared/constants/providers/` และการประกอบนิยามดังกล่าวใน
  `src/shared/constants/providers.ts`
- Models และ capabilities ใน `open-sse/config/providerRegistry.ts` หรือไฟล์ registry ที่แยกออกมา
- การเลือก executor/translator, การกำหนดค่า OAuth หรือ API key, asset ของ dashboard และข้อมูลอ้างอิง
  provider ที่สร้างขึ้นเมื่อเกี่ยวข้อง
- ข้อมูลรับรองสาธารณะต้องใช้ `resolvePublicCred()` ส่วน error response ต้องใช้ helper สำหรับ
  sanitization ที่ใช้ร่วมกัน ดู `docs/security/PUBLIC_CREDS.md` (อยู่ใน git แต่ไม่ได้ compile ลงใน `/docs`) และ
  [การ Sanitization ข้อผิดพลาด](../security/ERROR_SANITIZATION.md)

**รอบแบบเจาะจง**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # เมื่อ catalog เปลี่ยนแปลง ให้ commit diff ที่สร้างขึ้น
npm run lint
```

ทดสอบทุก request family ที่ได้รับผลกระทบด้วย ได้แก่ chat, Responses, images, embeddings, audio หรือ video
ตรวจสอบ diff ของ catalog และ golden file ที่สร้างขึ้นในฐานะการเปลี่ยนแปลงข้อกำหนด อย่ายอมรับโดยไม่ตรวจสอบ

### Routing

**ข้อกำหนด**

- ค่าของ strategy สาธารณะและ metadata ของ UI ใน `src/shared/constants/routingStrategies.ts`
- การ dispatch และการจัดลำดับภายใต้ `open-sse/services/combo.ts` และ `open-sse/services/combo/`
- Combo schema, persistence, resilience state, model capabilities และตัวควบคุม API/UI
- [กลไก Auto-Combo](../routing/AUTO-COMBO.md) และเอกสาร resilience เมื่อพฤติกรรมเปลี่ยนแปลง

**รอบแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # การเปลี่ยนแปลง strategy หรือ dispatch
npm run check:known-symbols      # การเปลี่ยนแปลงการลงทะเบียน strategy
npm run lint
```

ใช้การทดสอบ mocked-upstream แบบ deterministic ในเครื่อง การทดสอบ smoke ของ combo แบบ live ต้องใช้ข้อมูลรับรองและ
ต้องดำเนินการด้วยตนเอง ไม่สามารถใช้แทน CI ได้

### UI / UX

**ข้อกำหนด**

- ขอบเขตของ route/page ของ Next.js และ shared component ภายใต้ `src/app/` และ
  `src/shared/components/`
- รูปแบบ API response, สถานะ loading/empty/error, พฤติกรรมสำหรับ keyboard และ screen reader,
  responsive layout, theming และการขยาย locale
- ข้อความต้นฉบับภาษาอังกฤษของ UI ใน `src/i18n/messages/en.json` อย่า hard-code ข้อความใหม่ที่แสดงต่อผู้ใช้

**รอบแบบเจาะจง**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

เรียกใช้แอปสำหรับการเปลี่ยนแปลงด้านการโต้ตอบหรือภาพ และตรวจสอบทั้ง viewport แบบแคบและกว้าง CI จะเรียกใช้
production build และชุดทดสอบที่ครอบคลุมกว่า แต่พฤติกรรมด้านภาพยังคงต้องมี focused component, Playwright
หรือการตรวจสอบด้วยตนเองที่เหมาะสมกับการเปลี่ยนแปลงและมีการบันทึกไว้

### i18n

**ข้อกำหนด**

- `src/i18n/messages/en.json` เป็นแหล่งต้นฉบับของ UI ส่วน `config/i18n.json` เป็นแหล่งต้นฉบับของ locale
- catalog ของ CLI แยกอยู่ภายใต้ `bin/cli/locales/`
- รักษา placeholder และ tag ของ ICU ไว้อย่างถูกต้องทุกประการ อย่าแปลชื่อ product/provider/model,
  ชื่อ protocol และ header, คำสั่ง, identifier ของ code/JSON, URL, environment variable หรือ
  คำที่ได้รับการปกป้อง เช่น `OmniRoute`, `OAuth`, `MCP` และ `A2A` รายการต้นฉบับปัจจุบันอยู่ที่
  `scripts/i18n/glossary/protected-terms.json`

**รอบแบบเจาะจง**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # เมื่อ string/catalog ของ CLI เปลี่ยนแปลง
npm run lint
```

นี่คือแนวทางสำหรับระบบที่มีอยู่ ไม่ใช่การเชิญชวนให้ขยาย tooling หรือ key model ของระบบ
ให้ patch ของ i18n มีขอบเขตเฉพาะจุดในระหว่างที่กำลังออกแบบระบบทดแทน อย่าเรียกใช้คำสั่งแปล
ที่เรียกใช้บริการภายนอก เว้นแต่งานนั้นกำหนดให้ต้องสร้างคำแปลอย่างชัดเจน และ
คุณได้ตรวจสอบ diff ที่ได้แล้ว

### CLI

**ข้อกำหนด**

- คำสั่งและแฟล็กสาธารณะใน `bin/cli/`, คำสั่ง API ที่สร้างขึ้น, รหัสการออกจากโปรแกรม, stdout/stderr และ
  รูปแบบเอาต์พุต JSON, พฤติกรรมของการกำหนดค่า/สภาพแวดล้อม และไฟล์ที่รวมอยู่ในแพ็กเกจ
- สตริงที่แสดงต่อผู้ใช้ของ CLI ต้องใช้เลเยอร์ i18n ของ CLI และทำให้แค็ตตาล็อก `en`/`pt-BR` สอดคล้องกัน
- คง Node ไว้เป็นรันไทม์ที่รองรับ และรักษาสัญญาของไบนารีที่เผยแพร่

**วงจรแบบมุ่งเน้น**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # การเปลี่ยนแปลง CLI ที่สร้างขึ้น/บันเดิล
npm run check:pack-policy     # การเปลี่ยนแปลงพื้นผิวของแพ็กเกจ
npm run lint
```

ใช้คำสั่งที่ตรงตามนี้ทุกประการในไดเรกทอรีข้อมูลชั่วคราว เมื่อพฤติกรรมขึ้นอยู่กับการแยกวิเคราะห์ ไฟล์ หรือสถานะ
การออกจากโปรแกรม CI จะดำเนินการตรวจสอบอาร์ติแฟกต์แพ็กเกจและระบบนิเวศในขอบเขตที่กว้างกว่า

### ฐานข้อมูล

**สัญญา**

- โมดูลโดเมนอยู่ภายใต้ `src/lib/db/`; ให้นำเข้าโมดูลที่ต้องการโดยตรง (เลเยอร์ re-export เดิม `localDb.ts` ถูกนำออกแล้ว)
- ไมเกรชัน SQL ที่มีหมายเลขกำกับและทำซ้ำได้อย่างปลอดภัยภายใต้ `src/lib/db/migrations/`, ความปลอดภัยของทรานแซกชัน, พฤติกรรม
  การอัปเกรด, ดัชนี และทุกส่วนที่เรียกใช้ซึ่งได้รับผลกระทบจากสคีมา
- Route และ handler ต้องไม่สั่งรัน SQL ดิบโดยตรง

**วงจรแบบมุ่งเน้น**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

เมื่อเพิ่มไมเกรชัน ให้ทดสอบทั้งฐานข้อมูลใหม่และการอัปเกรดจากสคีมาก่อนหน้า การทดสอบฐานข้อมูล
ต้องปิด handle และเรียก `resetDbInstance()` ระหว่างการล้างข้อมูล เรียกใช้ `npm run test:bun:db` เฉพาะเมื่อ
เส้นทางอะแดปเตอร์ Bun แบบ best-effort มีการเปลี่ยนแปลง โดย Node ยังคงเป็นแหล่งอ้างอิงหลัก

### การบิลด์ / การปรับใช้

**สัญญา**

- Manifest/lockfile ของรูทและ workspace, `scripts/build/`, การประกอบ Next.js แบบ standalone, เนื้อหาแพ็กเกจ `dist/`,
  เมทาดาทาแพลตฟอร์ม Electron, workflow ของ CI และ sentinel สำหรับการปรับใช้
- ช่วงเวอร์ชัน Node ที่รองรับและการใช้งาน Bun ที่อยู่ในรายการอนุญาตใน `CLAUDE.md` ต้องคงเดิม
- อาร์ติแฟกต์จากการบิลด์ต้องไม่ถูกติดตาม; ให้ใช้นโยบายเกี่ยวกับ dependency, ใบอนุญาต, workflow และแพ็กเกจ

**วงจรแบบมุ่งเน้น**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # การเปลี่ยนแปลง dependency หรือ lockfile
npm run check:pack-policy      # การเปลี่ยนแปลงพื้นผิวของแพ็กเกจที่เผยแพร่
npm run lint
```

ใช้ `npm run build` ภายในเครื่องเฉพาะเมื่อการเปลี่ยนแปลงส่งผลต่อการคอมไพล์ การประกอบแบบ standalone แอสเซ็ต
หรือการบันเดิลรันไทม์ ใช้ `npm run build:release` เฉพาะสำหรับการตรวจสอบรีลีส/การปรับใช้ การบิลด์ของ CI
เป็นสัญญาณข้ามแพลตฟอร์มขั้นสุดท้าย; การเปลี่ยนแปลง Electron ที่เฉพาะเจาะจงกับแพลตฟอร์มต้องมีผลการบิลด์แบบมุ่งเน้น
หรือหลักฐาน smoke test ที่ตรงกับแพลตฟอร์มนั้น

## ลูปภายในเครื่องเทียบกับ CI

| เรียกใช้ภายในเครื่องสำหรับแต่ละแพตช์                                               | CI ให้สัญญาณในภาพรวม                                                           |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| การทดสอบพฤติกรรมโดยตรงและเกตตามหมวดหมู่ข้างต้น                                     | ชุดการทดสอบหน่วยแบบเต็มที่แบ่งเป็นชาร์ดและการทดสอบแบบลำดับ                     |
| `npm run lint`                                                                     | ชุดทดสอบ Vitest และเกณฑ์ขั้นต่ำแบบเพิ่มระดับสำหรับ coverage/คุณภาพ             |
| ตรวจสอบชนิดหรือบิลด์เฉพาะเมื่อสัญญาที่ได้รับผลกระทบกำหนดให้ทำ                      | บิลด์สำหรับ production รวมถึงเกตด้านความปลอดภัย เอกสาร dependency และนโยบาย PR |
| ตรวจสอบการโต้ตอบ/การทำงานจริงด้วยตนเองเฉพาะเมื่อระบบอัตโนมัติพิสูจน์พฤติกรรมไม่ได้ | การตรวจสอบการผสานรวมข้าม job และแพลตฟอร์มที่กำหนดค่าโดย workflow               |

ลูปแบบเจาะจงที่ผ่านทั้งหมดเป็นหลักฐานเกี่ยวกับสัญญาที่เปลี่ยนแปลง ไม่ใช่ข้อพิสูจน์ว่าการตรวจสอบ CI อื่นที่ไม่เกี่ยวข้อง
จะผ่าน ในทางกลับกัน อย่าทำให้ทุกการแก้ไขภายในเครื่องต้องรอเมทริกซ์ทั้งหมดของ repository

## เช็กลิสต์การปรับให้สอดคล้องกัน

ก่อนส่งคำขอให้รีวิว:

- ยืนยันว่า base ของ PR ยังคงเป็น branch `release/v*` ที่ใช้งานอยู่และมีเวอร์ชันสูงสุด
- Fetch base ดังกล่าวและตรวจสอบ commit ที่ถูกรวมเข้ามานับตั้งแต่คุณสร้าง branch
- ตรวจสอบ `git diff <active-base>...HEAD` เพื่อหาการเปลี่ยนแปลงโดยไม่ตั้งใจหรือที่เกิดจากการสร้างอัตโนมัติ
- แก้ไข conflict ของ catalog และเอกสารที่สร้างขึ้นโดยอัปเดตต้นทางแล้วสร้าง output ใหม่
- เรียกใช้การทดสอบ/เกตแบบเจาะจงทุกรายการที่ระบุไว้ในคำอธิบาย PR อีกครั้งหลังจากปรับให้สอดคล้องกัน
- ห้ามลดความเข้มงวดของ assertion หรือตัดการทดสอบที่จำเป็นออกเพียงเพื่อให้ตรงกับ base ที่เปลี่ยนไป

สำหรับกฎเกี่ยวกับช่วงหยุดการเปลี่ยนแปลงก่อน release และการเปลี่ยน target โปรดดู
