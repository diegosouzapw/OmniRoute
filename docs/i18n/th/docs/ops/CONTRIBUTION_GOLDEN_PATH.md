ใช้คู่มือนี้เพื่อเลือกวงจรการพัฒนาที่เล็กที่สุดแต่เชื่อถือได้สำหรับ pull request คู่มือนี้ไม่ได้
ใช้แทนเอกสารสถาปัตยกรรมและความปลอดภัยเฉพาะด้านที่ลิงก์ไว้ด้านล่าง แต่เชื่อมโยงการเปลี่ยนแปลง
แต่ละประเภทที่พบบ่อยเข้ากับสัญญา การตรวจสอบแบบเจาะจง และขอบเขตการตรวจสอบของ CI

## เส้นทางที่ทุกการเปลี่ยนแปลงต้องดำเนินตาม

1. **เลือก base ก่อนแก้ไข** ค้นหา branch `release/v*` ที่ยังใช้งานอยู่และมีเวอร์ชันสูงสุด แล้วสร้าง branch จาก
   tip ของ branch นั้น กำหนดเป้าหมายเป็น branch ดังกล่าว ไม่ใช่ `main` หากอยู่ในช่วงหยุดการเปลี่ยนแปลงก่อนออกรุ่น อย่ากำหนดเป้าหมายเป็น branch
   ที่ถูกระงับไว้ ให้ใช้รอบถัดไปที่ยังใช้งานอยู่ตามที่อธิบายไว้ใน
   [โมเดล Branching และ Release](BRANCHING_MODEL.md)
2. **ระบุสัญญา** ระบุ catalog, schema, artifact ที่สร้างขึ้น, public API หรือ user
   interface ทุกส่วนที่ได้รับผลกระทบจากการเปลี่ยนแปลง ตารางด้านล่างระบุชุดขั้นต่ำที่ใช้เป็นจุดเริ่มต้น
3. **เขียนหรืออัปเดตการทดสอบแบบเจาะจง** การเปลี่ยนแปลงโค้ด production ใน `src/`, `open-sse/`, `electron/` หรือ
   `bin/` ต้องมีการทดสอบอัตโนมัติใน PR เดียวกัน รันไฟล์ทดสอบชุดเล็กที่สุดที่พิสูจน์
   พฤติกรรมดังกล่าวได้ จากนั้นรันด่านตรวจสอบแบบเจาะจงที่ระบุไว้
4. **ให้ CI รันเมทริกซ์แบบครอบคลุม** unit shard ทั้งหมด, Vitest, coverage ratchet และ
   production build จะทำงานบน PR รันชุดทดสอบแบบครอบคลุมภายในเครื่องเฉพาะเมื่อความล้มเหลวจากการทดสอบแบบเจาะจงบ่งชี้ว่า
   มีผลกระทบในวงกว้างขึ้น หรือเมื่อการเปลี่ยนแปลงครอบคลุมหลาย subsystem
5. **ปรับให้สอดคล้องก่อน review** Fetch base ที่ยังใช้งานอยู่ ตรวจสอบ commit ใหม่และ diff ของคุณเมื่อเทียบกับ
   base นั้น จากนั้น rebase หรือ merge base ตามขั้นตอนการทำงานของผู้มีส่วนร่วม แก้ไข conflict ของไฟล์ที่สร้างขึ้น
   และ catalog จากต้นทาง จากนั้นสร้างไฟล์เหล่านั้นใหม่ รันวงจรแบบเจาะจงอีกครั้ง และยืนยันว่า
   PR ยังคงกำหนดเป้าหมายเป็น release branch ที่ยังใช้งานอยู่
6. **บันทึกหลักฐาน** ในเทมเพลต PR ให้ระบุคำสั่งที่รัน ไฟล์ทดสอบทั้งหมดที่เพิ่มหรือเปลี่ยนแปลง
   migration หรือ feature flag และการตรวจสอบเฉพาะ CI ที่ยังรอดำเนินการ

## เส้นทางมาตรฐานแยกตามประเภทการเปลี่ยนแปลง

คำสั่งด้านล่างเป็นการตรวจสอบแบบเจาะจงขั้นต่ำ ไม่ใช่การอนุญาตให้ข้ามการทดสอบที่ครอบคลุม
พฤติกรรมที่คุณเปลี่ยนแปลงโดยตรง

### Provider

**สัญญา**

- คำจำกัดความของ provider ใน `src/shared/constants/providers/` และการประกอบเข้าด้วยกันใน
  `src/shared/constants/providers.ts`
- Model และ capability ใน `open-sse/config/providerRegistry.ts` หรือไฟล์ registry ที่แยกออกมา
- การเลือก executor/translator, การกำหนดค่า OAuth หรือ API key, asset ของ dashboard และข้อมูลอ้างอิง
  provider ที่สร้างขึ้น หากเกี่ยวข้อง
- credential สาธารณะต้องใช้ `resolvePublicCred()` ส่วน response ข้อผิดพลาดต้องใช้ helper กลางสำหรับ
  การกรองข้อมูลที่ละเอียดอ่อน ดู `docs/security/PUBLIC_CREDS.md` (อยู่ใน git; ไม่ได้คอมไพล์ลงใน `/docs`) และ
  [การกรองข้อมูลที่ละเอียดอ่อนจากข้อผิดพลาด](../security/ERROR_SANITIZATION.md)

**วงจรแบบเจาะจง**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # เมื่อ catalog เปลี่ยนแปลง ให้ commit diff ที่สร้างขึ้น
npm run lint
```

ทดสอบ request family ทุกประเภทที่ได้รับผลกระทบด้วย ได้แก่ chat, Responses, images, embeddings, audio หรือ video
ตรวจสอบ diff ของ catalog และ golden file ที่สร้างขึ้นในฐานะการเปลี่ยนแปลงสัญญา อย่ายอมรับโดยไม่ตรวจสอบ

### Routing

**สัญญา**

- ค่ากลยุทธ์สาธารณะและ metadata ของ UI ใน `src/shared/constants/routingStrategies.ts`
- การ dispatch และการจัดลำดับภายใต้ `open-sse/services/combo.ts` และ `open-sse/services/combo/`
- Schema ของ combo, persistence, สถานะ resilience, capability ของ model และส่วนควบคุม API/UI
- [กลไก Auto-Combo](../routing/AUTO-COMBO.md) และเอกสาร resilience เมื่อมีการเปลี่ยนแปลงพฤติกรรม

**วงจรแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # การเปลี่ยนแปลงกลยุทธ์หรือ dispatch
npm run check:known-symbols      # การเปลี่ยนแปลงการลงทะเบียนกลยุทธ์
npm run lint
```

ใช้การทดสอบแบบ deterministic ที่ mock upstream ภายในเครื่อง การ smoke test combo แบบ live ต้องใช้ credential และเป็น
การทดสอบด้วยตนเอง ไม่ใช่สิ่งทดแทน CI

### UI / UX

**สัญญา**

- ขอบเขต route/page ของ Next.js และ shared component ภายใต้ `src/app/` และ
  `src/shared/components/`
- รูปแบบ response ของ API, สถานะ loading/empty/error, พฤติกรรมของ keyboard และ screen reader,
  responsive layout, theming และการขยาย locale
- string ต้นฉบับภาษาอังกฤษของ UI ใน `src/i18n/messages/en.json` อย่าฝังข้อความใหม่ที่แสดงต่อผู้ใช้โดยตรงในโค้ด

**วงจรแบบเจาะจง**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

รันแอปสำหรับการเปลี่ยนแปลงด้าน interaction หรือ visual และตรวจสอบทั้ง viewport แบบแคบและกว้าง CI จะรัน
production build และชุดทดสอบที่ครอบคลุมกว่า แต่พฤติกรรมด้าน visual ยังคงต้องมีการทดสอบ component แบบเจาะจง, Playwright
หรือการตรวจสอบด้วยตนเองที่มีการบันทึกไว้และเหมาะสมกับการเปลี่ยนแปลง

### i18n

**สัญญา**

- `src/i18n/messages/en.json` เป็นแหล่งข้อมูลของ UI ส่วน `config/i18n.json` เป็นแหล่งข้อมูลของ locale
- Catalog ของ CLI แยกอยู่ภายใต้ `bin/cli/locales/`
- รักษา placeholder และ tag ของ ICU ไว้อย่างถูกต้องครบถ้วน ห้ามแปลชื่อผลิตภัณฑ์/provider/model,
  ชื่อ protocol และ header, คำสั่ง, identifier ของโค้ด/JSON, URL, environment variable หรือ
  คำที่ได้รับการคุ้มครอง เช่น `OmniRoute`, `OAuth`, `MCP` และ `A2A` รายการต้นฉบับปัจจุบันอยู่ที่
  `scripts/i18n/glossary/protected-terms.json`

**วงจรแบบเจาะจง**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # เมื่อ string/catalog ของ CLI เปลี่ยนแปลง
npm run lint
```

นี่คือคำแนะนำสำหรับระบบที่มีอยู่ ไม่ใช่การเชื้อเชิญให้ขยาย tooling หรือ key model ของระบบ
รักษา patch ของ i18n ให้เปลี่ยนแปลงเฉพาะจุดระหว่างที่ระบบทดแทนกำลังได้รับการออกแบบ อย่ารันคำสั่งแปล
ที่เรียกใช้บริการภายนอก เว้นแต่งานนั้นกำหนดให้สร้างคำแปลอย่างชัดเจน และ
คุณได้ตรวจสอบ diff ที่ได้แล้ว

### CLI

**สัญญา**

- คำสั่งและแฟล็กสาธารณะใน `bin/cli/`, คำสั่ง API ที่สร้างขึ้น, รหัสการออกจากโปรแกรม, stdout/stderr และ
  รูปแบบเอาต์พุต JSON, พฤติกรรมของการกำหนดค่า/สภาพแวดล้อม และไฟล์ที่รวมอยู่ในแพ็กเกจ
- สตริงที่แสดงต่อผู้ใช้ CLI ต้องใช้เลเยอร์ i18n ของ CLI และทำให้แค็ตตาล็อก `en`/`pt-BR` สอดคล้องกัน
- คง Node ไว้เป็นรันไทม์ที่รองรับ และรักษาสัญญาของไบนารีที่เผยแพร่

**วงรอบแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # การเปลี่ยนแปลง CLI ที่สร้างขึ้น/รวมเป็นบันเดิล
npm run check:pack-policy     # การเปลี่ยนแปลงพื้นผิวแพ็กเกจ
npm run lint
```

ใช้คำสั่งตามที่ระบุไว้ทุกประการในไดเรกทอรีข้อมูลชั่วคราว เมื่อพฤติกรรมขึ้นอยู่กับการแยกวิเคราะห์ ไฟล์ หรือ
สถานะการออกจากโปรแกรม CI จะดำเนินการตรวจสอบอาร์ติแฟกต์แพ็กเกจและระบบนิเวศในขอบเขตที่กว้างกว่า

### ฐานข้อมูล

**สัญญา**

- โมดูลโดเมนอยู่ภายใต้ `src/lib/db/`; ให้นำเข้าโมดูลที่ต้องการโดยตรง (เลเยอร์ re-export เดิม `localDb.ts` ถูกนำออกแล้ว)
- การย้ายข้อมูล SQL ที่มีหมายเลขกำกับและทำซ้ำได้อย่างปลอดภัยภายใต้ `src/lib/db/migrations/`, ความปลอดภัยของธุรกรรม, พฤติกรรม
  การอัปเกรด, ดัชนี และทุกส่วนที่เรียกใช้ซึ่งได้รับผลกระทบจากสคีมา
- เส้นทางและตัวจัดการต้องไม่เรียกใช้ SQL ดิบโดยตรง

**วงรอบแบบเจาะจง**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

เมื่อเพิ่มการย้ายข้อมูล ให้ทดสอบทั้งฐานข้อมูลใหม่และการอัปเกรดจากสคีมาก่อนหน้า การทดสอบฐานข้อมูล
ต้องปิดแฮนเดิลและเรียก `resetDbInstance()` ระหว่างการล้างข้อมูล เรียกใช้ `npm run test:bun:db` เฉพาะเมื่อ
พาธอะแดปเตอร์ Bun แบบ best-effort มีการเปลี่ยนแปลงเท่านั้น โดย Node ยังคงเป็นแหล่งอ้างอิงหลัก

### การบิลด์ / การปรับใช้

**สัญญา**

- ไฟล์ manifest/lockfile ระดับรูทและเวิร์กสเปซ, `scripts/build/`, การประกอบ Next.js แบบ standalone, เนื้อหาแพ็กเกจ
  `dist/`, เมทาดาทาแพลตฟอร์ม Electron, เวิร์กโฟลว์ CI และตัวตรวจจับสถานะการปรับใช้
- ช่วงเวอร์ชัน Node ที่รองรับและการใช้งาน Bun ที่อยู่ในรายการอนุญาตใน `CLAUDE.md` ต้องคงเดิม
- อาร์ติแฟกต์จากการบิลด์ต้องไม่ถูกติดตาม; ต้องปฏิบัติตามนโยบายเกี่ยวกับการพึ่งพา ไลเซนส์ เวิร์กโฟลว์ และแพ็กเกจ

**วงรอบแบบเจาะจง**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # การเปลี่ยนแปลงการพึ่งพาหรือ lockfile
npm run check:pack-policy      # การเปลี่ยนแปลงพื้นผิวแพ็กเกจที่เผยแพร่
npm run lint
```

ใช้ `npm run build` ภายในเครื่องเฉพาะเมื่อการเปลี่ยนแปลงส่งผลต่อการคอมไพล์ การประกอบแบบ standalone แอสเซ็ต
หรือการรวมรันไทม์เป็นบันเดิล ใช้ `npm run build:release` เฉพาะสำหรับการตรวจสอบรีลีส/การปรับใช้ การบิลด์ของ CI
เป็นสัญญาณข้ามแพลตฟอร์มขั้นสุดท้าย; การเปลี่ยนแปลง Electron ที่เฉพาะเจาะจงต่อแพลตฟอร์มต้องมีการบิลด์แบบเจาะจงที่ตรงกัน
หรือหลักฐานการทดสอบ smoke

## ลูป candidate ภายในเครื่อง

การทดสอบซอร์สไม่สามารถยืนยันได้ว่าอาร์ติแฟกต์ที่แพ็กเกจแล้วจะบูตได้ เนื่องจากรายการไฟล์สำหรับการแพ็กเกจ, dependency ที่ถูกตัดออก
และไบนารีแบบ native จะล้มเหลวก็ต่อเมื่อติดตั้งและเริ่มต้น tarball แล้วเท่านั้น `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) คือส่วนที่ทำงานภายในเครื่องของโฟลว์ build-once / validate / promote จาก
RFC #8084 โดยจะสร้าง candidate หนึ่งรายการ ตรวจสอบอาร์ติแฟกต์นั้นโดยตรง โปรโมตด้วยการ
เปลี่ยนชื่อไดเรกทอรี และย้อนกลับเมื่อสล็อตที่โปรโมตแล้วไม่ผ่านการตรวจสอบสถานะ

```bash
npm run dev:candidate -- run --dry-run --json  # แสดงแผนโดยไม่เปลี่ยนแปลงสิ่งใด
npm run dev:candidate -- run                   # สร้าง + ตรวจสอบ + โปรโมต พร้อมย้อนกลับอัตโนมัติ
npm run dev:candidate -- build                 # npm pack + ติดตั้งลงใน _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # บูตบนพอร์ตว่าง, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # สลับ current และ previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # ใช้ tarball ที่สร้างจากที่อื่น (CI) ซ้ำ
```

- **สร้างเพียงครั้งเดียว** `build` จะแพ็ก tree ปัจจุบัน (จำเป็นต้องมี `dist/server.js` ดังนั้นให้เรียกใช้
  `npm run build:release` ก่อน) หรือคัดลอก `--from-tarball` จากนั้นติดตั้ง tarball ลงใน
  npm prefix ที่แยกต่างหาก เนื่องจาก tarball ไม่มี `node_modules` รวมอยู่ด้วย id คือ `HEAD`
  sha แบบสั้น (`-dirty` เมื่อ tree มีการเปลี่ยนแปลงภายในเครื่อง) หรือ `tgz-<sha256>` สำหรับ tarball หาก
  id แบบ clean ถูกสร้างไว้แล้ว ระบบจะนำกลับมาใช้แทนการสร้างใหม่ โดยส่ง `--force` เพื่อบังคับสร้างใหม่
- **ตรวจสอบแพ็กเกจ ไม่ใช่ซอร์ส** `validate` จะเริ่มต้น CLI ที่ติดตั้งแล้ว
  (`serve --port <free port>`) ด้วย `DATA_DIR=<candidate>/data` ใหม่, secret ปลอม และนำ
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` และ `INITIAL_PASSWORD` ของผู้ดูแลออกจาก
  environment เพื่อให้ตรวจสอบการทำงานแบบ keyless loopback ของการติดตั้งใหม่ โดยจะรอให้
  `GET /api/health` ส่งคืน 200, กำหนดให้ `GET /v1/models` ส่งคืน 200, หยุดกลุ่มโปรเซส
  และบันทึกผลการตรวจสอบลงใน `validation.json` พร้อมกับแฮชของ tarball
- **โปรโมตอาร์ติแฟกต์เดียวกัน** `promote` จะปฏิเสธ candidate ที่ไม่มีผลการตรวจสอบผ่านสำหรับ
  แฮช tarball ปัจจุบัน สล็อตที่ใช้งานอยู่โดยค่าเริ่มต้นคือ `_artifacts/candidate/current`; `--target <dir>`
  ใช้เลือกไดเรกทอรีอื่นบน filesystem เดียวกัน และสล็อตก่อนหน้าของไดเรกทอรีนั้นคือ `<dir>.previous`
  การเปลี่ยนชื่อแต่ละครั้งเป็นแบบ atomic และหากเกิดความล้มเหลวระหว่างทาง ระบบจะย้อนการเปลี่ยนชื่อที่ดำเนินการไปแล้ว
- **ย้อนกลับ** `run` จะตรวจสอบสล็อตที่โปรโมตแล้วอีกครั้ง และสลับ `current` กับ `previous` กลับเมื่อ
  การตรวจสอบนั้นล้มเหลว candidate ที่ไม่ผ่านการตรวจสอบครั้งแรกจะไม่ถูกโปรโมต

ทุกอย่างจะถูกเขียนไว้ภายใต้ `_artifacts/candidate/` ซึ่งถูก gitignore ไว้ การติดตั้ง OmniRoute
และไดเรกทอรีข้อมูลที่มีอยู่จะไม่ถูกแตะต้อง CLI ที่โปรโมตแล้วคือ
`_artifacts/candidate/current/prefix/bin/omniroute`; เมื่อใช้งาน ให้เริ่มต้นด้วย `DATA_DIR` ของคุณเอง
รหัสออก: `0` สำเร็จ, `1` การตรวจสอบหรือการโปรโมตล้มเหลว, `2` การใช้งานผิดพลาดหรือไม่มี build

## ลูปในเครื่องเทียบกับ CI

| รันในเครื่องสำหรับแต่ละแพตช์                                                         | CI ให้สัญญาณในภาพรวม                                                  |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| การทดสอบพฤติกรรมโดยตรงและเกตตามหมวดหมู่ข้างต้น                                       | ชุดการทดสอบหน่วยทั้งหมดที่แบ่งเป็นชาร์ดและการทดสอบแบบลำดับ            |
| `npm run lint`                                                                       | ชุดทดสอบ Vitest และเกณฑ์ปรับเพิ่มความครอบคลุม/คุณภาพ                  |
| ตรวจสอบชนิดหรือบิลด์เฉพาะเมื่อสัญญาที่ได้รับผลกระทบกำหนดให้ทำ                        | บิลด์สำหรับโปรดักชัน เกตด้านความปลอดภัย เอกสาร การพึ่งพา และนโยบาย PR |
| การโต้ตอบด้วยตนเอง/การตรวจสอบแบบสดเฉพาะเมื่อระบบอัตโนมัติไม่สามารถพิสูจน์พฤติกรรมได้ | การตรวจสอบการผสานรวมข้ามงานและแพลตฟอร์มที่กำหนดค่าไว้โดยเวิร์กโฟลว์   |

ลูปแบบเจาะจงที่ผ่านทั้งหมดเป็นหลักฐานเกี่ยวกับสัญญาที่เปลี่ยนแปลง ไม่ใช่ข้อพิสูจน์ว่าการตรวจสอบ CI อื่นที่ไม่เกี่ยวข้อง
จะผ่าน ในทางกลับกัน อย่าทำให้การแก้ไขทุกครั้งในเครื่องต้องรอเมทริกซ์ทั้งหมดของรีโพซิทอรี

## รายการตรวจสอบการปรับให้สอดคล้อง

ก่อนขอรับการรีวิว:

- ยืนยันว่าเบสของ PR ยังคงเป็นสาขา `release/v*` ที่ใช้งานอยู่และมีเวอร์ชันสูงสุด
- ดึงข้อมูลเบสดังกล่าวและตรวจสอบคอมมิตที่รวมเข้ามาหลังจากที่คุณสร้างสาขา
- ตรวจสอบ `git diff <active-base>...HEAD` เพื่อหาการเปลี่ยนแปลงที่เกิดขึ้นโดยไม่ตั้งใจหรือเกิดจากการสร้างอัตโนมัติ
- แก้ไขข้อขัดแย้งของแค็ตตาล็อกและเอกสารที่สร้างขึ้นโดยอัปเดตต้นทางและสร้างเอาต์พุตใหม่
- รันการทดสอบ/เกตแบบเจาะจงทุกรายการที่ระบุไว้ในคำอธิบาย PR อีกครั้งหลังจากปรับให้สอดคล้อง
- ห้ามลดความเข้มงวดของการตรวจสอบหรือยกเลิกการทดสอบที่จำเป็นเพียงเพื่อให้ตรงกับเบสที่ถูกย้าย
