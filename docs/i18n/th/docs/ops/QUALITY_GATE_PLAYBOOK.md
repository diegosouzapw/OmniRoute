## ส่วนที่ 1 — ข้อสรุปและการจัดระดับวุฒิภาวะ

**เกรดโดยรวม: A− / "ขั้นสูง" อยู่ในกลุ่มบนสุดประมาณ 5–10% ของโปรเจกต์** ระบบนี้นำรูปแบบหลายอย่าง
ที่อุตสาหกรรมกำหนดชื่อไว้อย่างชัดเจนมาใช้โดยอิสระ — ซึ่งเป็นสัญญาณความสอดคล้องที่แข็งแกร่งที่สุด
(เราไม่ได้คัดลอกรายการตรวจสอบ แต่เราพัฒนาไปบรรจบกับแนวปฏิบัติที่ถูกต้อง)

| กรอบอ้างอิง                           | สถานะของเรา                                                                                                                                                                                                                                         | ระดับ                         |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| **OWASP DSOMM** (5 ระดับ, 5 มิติ)     | อยู่ที่ระดับ 3 อย่างมั่นคง และกำลังไปถึงระดับ 4 ในด้าน _ความเข้มข้นของการทดสอบ_ และ _ความลึกของการวิเคราะห์แบบสแตติก_ องค์กรส่วนใหญ่อยู่ที่ระดับ 1–2                                                                                                | **L3→L4**                     |
| **OpenSSF Scorecard** (18 การตรวจสอบ) | เราผ่าน CI-Tests, Code-Review, Dependency-Update-Tool, Fuzzing, SAST, Signed-Releases (provenance), Token-Permissions, Vulnerabilities และ Dangerous-Workflow **ช่องว่าง:** Branch-Protection บน `main` ปิดอยู่; action บางรายการไม่ได้ตรึงเวอร์ชัน | **~7–8/10**                   |
| **SLSA** (4 ระดับ)                    | `npm publish --provenance` + `id-token: write` + การ build ที่โฮสต์โดย GitHub = **L2** และกำลังเข้าใกล้ L3 ยังขาด builder ที่ผ่านการเสริมความปลอดภัย/แยกสภาพแวดล้อมอย่างสมบูรณ์สำหรับ L3+                                                           | **L2→L3**                     |
| **SonarQube "Clean as You Code"**     | ปรัชญาเหมือนกัน: ด่าน ratchet ป้องกัน_การถดถอย_ (โค้ดใหม่ต้องไม่ทำให้เมตริกแย่ลง) **จุดที่แตกต่าง:** Sonar แนะนำให้มีเงื่อนไข **เพียงไม่กี่ข้อ**; เรามีประมาณ 46 ด่าน (เสี่ยงต่อความเหนื่อยล้าจากการตรวจสอบ)                                        | **สอดคล้อง แต่มีข้อควรระวัง** |
| **รูปแบบ Quality-Ratchet**            | การนำไปใช้ที่ใช้อ้างอิงได้: ratchet + `dedicatedGate` + `tightenSlack` + `--require-tighten` + การข้ามอย่างปลอดภัยเมื่อไม่พร้อม มีความซับซ้อนและรัดกุมกว่าตัวอย่างสาธารณะส่วนใหญ่                                                                   | **เป็นแบบอย่าง**              |
| **DORA 2024**                         | แข็งแกร่งมากในแกน_เสถียรภาพ_ ความเสี่ยง: ด่านที่หนักอาจเพิ่ม_ระยะเวลานำส่ง_ — บรรเทาด้วยการแยก fast-gates แต่ยังมีช่องว่างด้าน coverage (ดูส่วนที่ 2)                                                                                               | **แข็งแกร่ง (เสถียรภาพ)**     |
| **OWASP LLM Top 10 (2025)**           | เราครอบคลุมความเสี่ยง #1 (prompt-injection) ด้วย runtime guard + promptfoo (การประเมิน) + garak (red-team) ซึ่งเป็นเครื่องมือมาตรฐานในอุตสาหกรรม                                                                                                    | **ครอบคลุมแล้ว**              |
| **Mutation testing**                  | ใช้ Stryker ทุกคืน, threshold 70/50, 8 โมดูลสำคัญ ฉันทามติของอุตสาหกรรม (60% สำหรับโค้ดเดิม / 80% สำหรับโค้ดใหม่, ทำงานทุกคืน) — **เราทำได้ดีกว่า** **ช่องว่าง:** คะแนนยังไม่ได้เป็น ratchet                                                        | **เกือบสมบูรณ์**              |

## ส่วนที่ 2 — การประเมินเชิงวิพากษ์ (จุดแข็ง + จุดอ่อนตามความเป็นจริง)

### จุดแข็ง (สิ่งที่เหนือกว่าค่าเฉลี่ย)

1. **กลไก ratchet แบบหลายเมตริก** หัวใจสำคัญของระบบ เมตริก 24 รายการใน `quality-baseline.json`
   - baseline เฉพาะทาง 4 รายการ โดยแต่ละรายการมีทิศทาง (`up`/`down`), ค่าความคลาดเคลื่อน (`eps`), ค่าผ่อนผัน
     (`tightenSlack`) และแฟล็ก `dedicatedGate` สิ่งที่แก้ไขแล้วจะ**คงสถานะ**ว่าแก้ไขแล้ว — นี่คือ
     ยาถอนพิษต่อการเสื่อมสภาพของ codebase
2. **การป้องกันเชิงลึกสำหรับ supply chain** SAST (CodeQL/Sonar) + secrets (gitleaks พร้อม
   `useDefault`) + SCA (osv/npm-audit/Trivy/Dependabot) + ใบอนุญาต + lockfile + SBOM + provenance แบบ SLSA
   - Scorecard + การเสริมความแข็งแกร่งให้ workflow (zizmor) มี codebase เพียงไม่กี่แห่งที่มี stack ครบถ้วนขนาดนี้
3. **กลไกต้านกฎของ Goodhart** การใช้ coverage เป็นเป้าหมายถือเป็น anti-pattern แบบคลาสสิก
   ("เมื่อมาตรวัดกลายเป็นเป้าหมาย มันก็จะไม่ใช่มาตรวัดที่ดีอีกต่อไป") เรามีกลไกถ่วงดุล ได้แก่
   **mutation testing** (วัดว่า test ตรวจพบบั๊กหรือไม่ ไม่ใช่เพียงตรวจว่ามีการรันบรรทัดนั้นหรือไม่),
   **`check-test-masking`** (ป้องกันการทำให้ assert อ่อนลงเพื่อให้ผ่าน),
   **ค่า coverage ขั้นต่ำต่อโมดูล** (บังคับให้ทดสอบโค้ดที่มีความเสี่ยงสูง ไม่ใช่เฉพาะส่วนที่ง่าย) และ
   **`check-pr-evidence`** (Hard Rule #18)
4. **gate ป้องกัน hallucination / ตรวจสอบความสอดคล้อง** หมวดหมู่ที่พบได้ยากและมีคุณค่า:
   `check-known-symbols`, `check-fetch-targets`, `check-openapi-routes`, `check-docs-symbols`
   ช่วยให้มั่นใจว่าเอกสาร ข้อกำหนด และ string dispatch ชี้ไปยัง symbol ที่ยังมีอยู่จริง ตรวจพบ "การผุพัง"
   ที่ lint/test ตรวจไม่พบ
5. **วงจรชีวิตจาก advisory→blocking** gate ใหม่จะเริ่มต้นเป็น advisory (ไม่ขัดขวางการ merge
   ระหว่างที่ยังพัฒนาให้มีความเสถียร) แล้วจึงเปลี่ยนเป็น blocking เมื่อสิ้นสุดรอบ ช่วยลดแรงเสียดทาน
   โดยไม่ลดเพดานคุณภาพ
6. **ข้ามอย่างเหมาะสมเมื่อไม่มีโครงสร้างพื้นฐาน** scanner (`--ratchet`) จะจบด้วย `exit 0`
   หาก binary/network ล้มเหลว — โครงสร้างพื้นฐานที่ขาดหายไปจะไม่ขัดขวาง PR ที่ถูกต้องตามหลัก
   นี่คือแนวทางวิศวกรรมที่มีวุฒิภาวะ
7. **วัฒนธรรมที่ถูกกำหนดเป็นรูปธรรม** Hard Rules + `trust-but-verify` + stale-allowlist + evidence-gate
   เปลี่ยนระเบียบวินัยให้เป็นการตรวจสอบอัตโนมัติ

### จุดอ่อนตามความเป็นจริง (ช่องว่างที่มีอยู่จริง)

1. **🔴 การแยก fast-gates ยังคงทิ้งช่องโหว่เชิงโครงสร้างไว้** `quality.yml` (PR→`release/**`)
   ขณะนี้รัน typecheck, test เชิงกำหนดที่รวดเร็ว และ production build แบบ advisory สำหรับ PR ที่แก้โค้ด
   แต่ยังไม่ได้รันพื้นผิวการตรวจสอบทั้งหมดของ release PR จาก `ci.yml` (coverage ratchet,
   package artifact, integration, E2E, SonarQube) แรงจูงใจด้านความเร็วนั้นสมเหตุสมผล แต่ gate
   ควรอยู่ตรงจุดที่เกิดการ merge (shift-left) **นี่คือการแก้ไขเชิงโครงสร้างที่ค้างอยู่และใหญ่ที่สุด**
2. **🟠 ความเสี่ยงจาก gate ที่กระจายตัวมากเกินไป/ความเหนื่อยล้าจาก gate** ~46 gate + 25 job นั้นมากมาก
   Sonar เองเตือนว่า เงื่อนไขที่มากเกินไปทำให้เกิด "gate fatigue" และข้อถกเถียงเรื่องลำดับความสำคัญ
   ซึ่งเสี่ยงที่ gate จะถูกละเลย DORA เตือนว่า gate ที่หนักหน่วงส่งผลต่อต้นทุนด้าน lead-time
   เราบรรเทาปัญหาด้วยระดับ advisory และ ratchet ที่ไม่ใช่เกณฑ์ตายตัว แต่ยังขาด
   **การทบทวน ROI เป็นระยะสำหรับแต่ละ gate** (micro-gate บางส่วนสำหรับ doc-sync สามารถรวมกันได้)
3. **🟠 คะแนน mutation ยังไม่ได้เป็น ratchet** กลไกต้านการเล่นกับ coverage ที่แข็งแกร่งที่สุดยังเป็น
   **advisory** นี่คือรายการค้างที่มีมูลค่าสูงสุด (และสร้างเสร็จแล้ว 90%)
4. **🟡 advisory ที่ควรเป็น blocking (ภายใต้ขอบเขตที่เหมาะสม)** `osv` (vulnCount) และ `oasdiff`
   เป็น advisory แม้จะตรึง baseline แล้วก็ตาม การให้ osv เป็น advisory นั้นสมเหตุสมผล (CVE ใหม่ใน dependency
   เก่าอาจขัดขวาง PR ที่ไม่เกี่ยวข้อง) — แต่ยังมีทางสายกลาง (บล็อกเฉพาะ CRITICAL+fixable เช่นเดียวกับที่เราทำ
   กับ Trivy) ส่วนการที่ oasdiff เป็น advisory หมายความว่าการเปลี่ยนแปลงที่ทำลาย contract สามารถผ่านได้
5. **🟡 ความปลอดภัยขณะ runtime ถูกตรวจเฉพาะรายคืน** schemathesis/garak/promptfoo/chaos/k6 รันในช่วงกลางคืน
   นี่เป็นการตัดสินใจที่ถูกต้อง (ทำงานช้าและต้องใช้ server ที่รันอยู่จริง) แต่ PR อาจทำให้เกิด regression
   ของ injection guard ซึ่งจะถูกตรวจพบในคืนถัดไปเท่านั้น
6. **🟡 branch protection บน `main` ถูกปิดอยู่** `BRANCH_LOCK_TOKEN` ล็อก branch สำหรับ _release_
   แต่ตัว `main` เองไม่มีการป้องกัน Scorecard/DSOMM หักคะแนนในส่วนนี้ ต้องให้ owner ดำเนินการ
7. **🟡 CodeQL ใช้ default-setup; semgrep ไม่ได้ถูกกำหนดไว้ใน repo** default-setup ใช้งานได้
   (0 alert) แต่ `codeql.yml` ที่ commit ไว้ช่วยให้ควบคุมได้มากกว่า ส่วน semgrep รันผ่านแพลตฟอร์ม cloud
   ภายนอก และไม่ได้จัดเก็บแบบมีเวอร์ชันใน repo

## ส่วนที่ 3 — แค็ตตาล็อกจุดตรวจสอบคุณภาพฉบับสมบูรณ์ (นำไปใช้ข้ามระบบได้)

12 หมวดหมู่ด้านล่างคือ "ระบบคุณภาพ" ในรูปแบบที่นำกลับมาใช้ซ้ำได้ แต่ละหมวดระบุ
**วัตถุประสงค์** (สิ่งที่ต้องปกป้อง), **เครื่องมือที่เราใช้** และ **แนวทางเทียบเท่าที่ไม่ยึดติดกับเครื่องมือ**
เพื่อให้นำไปทำซ้ำบนสแต็กใดก็ได้

### 1. สไตล์และการจัดรูปแบบ (ให้ผลลัพธ์แน่นอนและรวดเร็ว)

- **OmniRoute:** Prettier + ESLint ผ่าน lint-staged (pre-commit), 2 ช่องว่าง/อัญประกาศคู่/100 คอลัมน์
- **ทั่วไป:** ตัวจัดรูปแบบที่แก้ไขอัตโนมัติได้หนึ่งตัว + linter หนึ่งตัว โดยทำงานในขั้นตอน pre-commit กับไฟล์ที่ staged ไว้

### 2. ชนิดข้อมูล

- **OmniRoute:** `typecheck:core` (บังคับผ่าน) + `typecheck:noimplicit:core` (ให้คำแนะนำ) + ปรับเกณฑ์ `type-coverage` แบบทางเดียวที่ 92.17% + งบประมาณการใช้ any ต่อไฟล์
- **ทั่วไป:** ตรวจสอบชนิดข้อมูลแบบเข้มงวดใน CI + เมตริกความครอบคลุมของชนิดข้อมูลที่ปรับเกณฑ์ได้ทางเดียว + งบประมาณการใช้ `any`/ช่องทางเลี่ยงข้อจำกัดต่อไฟล์

### 3. การทดสอบ (ความเข้มข้น)

- **OmniRoute:** ตัวรันทดสอบ 2 ตัวที่ไม่ทับซ้อนกัน (Node native + vitest), 8 shards, ความครอบคลุมโดยรวม 60/60/60/60 + ปรับเกณฑ์แบบทางเดียวที่ ~76% + **เกณฑ์ขั้นต่ำรายโมดูล 8 รายการสำหรับโมดูลสำคัญ** + การทดสอบเชิงคุณสมบัติทุกคืน + **การทดสอบการกลายพันธุ์** ทุกคืน
- **ทั่วไป:** ตัวรันทดสอบหนึ่งตัวหรือหลายตัว + เกณฑ์ความครอบคลุมแบบ **ค่าสัมบูรณ์** (ป้องกันค่าศูนย์) + **การปรับเกณฑ์** ความครอบคลุมแบบทางเดียว (ป้องกันการถดถอย) + **เกณฑ์ขั้นต่ำรายโมดูลสำหรับโค้ดที่มีความเสี่ยงสูง** (ป้องกัน Goodhart) + การทดสอบเชิงคุณสมบัติสำหรับตรรกะบริสุทธิ์ + **การทดสอบการกลายพันธุ์** ทุกคืน เพื่อใช้เป็นมาตรวัดคุณภาพการทดสอบที่แท้จริง

### 4. นโยบายการทดสอบ (ป้องกันการเล่นกับเกณฑ์)

- **OmniRoute:** `pr-test-policy` (โค้ดโปรดักชันต้องมีการทดสอบ), `check-test-masking` (บล็อก assert ที่ถูกทำให้อ่อนลง), `pr-evidence` (การอ้างว่าทำสำเร็จต้องมีบล็อกหลักฐาน), `test-discovery` (การทดสอบทุกตัวต้องถูกรวบรวมโดยตัวรันทดสอบ)
- **ทั่วไป:** เกต "โค้ดใหม่ ⇒ การทดสอบใหม่" + ตัวตรวจจับ assert ที่ถูกลบ/เงื่อนไขที่เป็นจริงเสมอ + ข้อกำหนดด้านหลักฐาน (TDD หรือการทดสอบที่ยังใช้งานจริง) + รับประกันว่าไม่มีการทดสอบใดถูกทิ้งไว้นอก globs

### 5. ความซับซ้อนและสุขภาพของโค้ด (ปรับเกณฑ์แบบทางเดียว)

- **OmniRoute:** คำเตือน ESLint (3769↓), โค้ดซ้ำจาก jscpd (5.72%↓), ความซับซ้อนแบบ cyclomatic+max-lines (1800↓), ความซับซ้อนเชิงการรับรู้จาก sonarjs (753↓), โค้ดที่ไม่ถูกใช้/exports ที่ไม่ถูกใช้จาก knip (339↓), ขนาดไฟล์ต่อไฟล์ (ตรึงไว้และลดลงได้เท่านั้น), การพึ่งพาแบบวงจร (Tarjan แบบกำหนดเองและบังคับผ่าน)
- **ทั่วไป:** ปรับเกณฑ์เมตริกสุขภาพทุกตัวแบบทางเดียว (คำเตือน, โค้ดซ้ำ, ความซับซ้อนแบบ cyclomatic **และ** เชิงการรับรู้, โค้ดที่ไม่ถูกใช้, ขนาดไฟล์, วงจรการ import) โดยทิศทางต้องเป็น "ห้ามถดถอย" เสมอ

### 6. ความปลอดภัยแบบสแตติก (SAST + ข้อมูลลับ)

- **OmniRoute:** CodeQL (ปรับเกณฑ์การแจ้งเตือนแบบทางเดียว = 0), gitleaks (`[extend] useDefault=true` — สำคัญอย่างยิ่ง!), SonarQube, กฎความปลอดภัยแบบกำหนดเอง (public-creds, error-helper, route-guard-membership, route-validation)
- **ทั่วไป:** SAST (CodeQL/Sonar/semgrep) พร้อมการปรับเกณฑ์การแจ้งเตือนแบบทางเดียว + เครื่องมือสแกนข้อมูลลับที่มี **ชุดกฎเริ่มต้นที่สืบทอดมา** (การกำหนดค่าแบบกำหนดเองที่เขียนทับค่าเริ่มต้น = จุดบอด) + เกตความปลอดภัยตาม Hard Rule เฉพาะของโปรเจกต์

### 7. ซัพพลายเชน (การพึ่งพา)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA), license-checker (รายการอนุญาต SPDX), lockfile-lint (HTTPS+sha512+registry), `check-deps` ป้องกัน slopsquatting (รายการอนุญาต + อายุ ≥72 ชม.)
- **ทั่วไป:** SCA จากหลายแหล่ง + รายการอนุญาตด้านสัญญาอนุญาต + การตรวจสอบความสมบูรณ์ของ lockfile + รายการอนุญาตของการพึ่งพาพร้อมตรวจสอบอายุ/typosquatting + บอตอัปเดตแบบจัดกลุ่ม

### 8. ซัพพลายเชน (การบิลด์และการรีลีส)

- **OmniRoute:** SBOM (CycloneDX + syft), ที่มาของอาร์ติแฟกต์ตาม SLSA (`--provenance`), OpenSSF Scorecard (รายสัปดาห์), การเสริมความแข็งแกร่งให้เวิร์กโฟลว์ (zizmor: artipacked→`persist-credentials:false`, cache-poisoning, token-permissions)
- **ทั่วไป:** สร้าง SBOM เมื่อเผยแพร่ + ที่มาที่มีลายเซ็นรับรอง (SLSA L2+) + เรียกใช้ Scorecard ตามกำหนดเวลา + เสริมความแข็งแกร่งให้ทุกเวิร์กโฟลว์ (โทเค็นสิทธิ์ขั้นต่ำ, ไม่เก็บข้อมูลประจำตัวไว้เมื่อ checkout สำหรับงานที่ไม่ push, ตรึง actions ด้วย SHA)

### 9. สัญญาและ API

- **OmniRoute:** oasdiff (การเปลี่ยนแปลง OpenAPI ที่ทำลายความเข้ากันได้), schemathesis (contract fuzz ทุกคืน), openapi-coverage (% ของ route ที่มีเอกสารประกอบ, ปรับเกณฑ์แบบทางเดียวที่ 38.3%), openapi-security-tiers (ข้อกำหนดเทียบกับ route-guard)
- **ทั่วไป:** diff สัญญาเพื่อตรวจจับการเปลี่ยนแปลงที่ทำลายความเข้ากันได้ (oasdiff/buf) + fuzz เชิงคุณสมบัติตามข้อกำหนด (schemathesis) + ความครอบคลุมของเอกสารที่ปรับเกณฑ์แบบทางเดียว + ความสอดคล้องระหว่างข้อกำหนด↔โค้ด

### 10. เอกสารและ i18n (ป้องกันการเสื่อมสภาพ)

- **OmniRoute:** docs-sync (เวอร์ชันที่ทำสำเนาให้ตรงกัน), docs-counts-sync (ตัวเลขในเอกสารเทียบกับโค้ด), env-doc-sync, doc-links, fabricated-docs, cli-i18n, i18n-ui-coverage (`--threshold=65` + ปรับเกณฑ์แบบทางเดียวที่ 80.1%)
- **ทั่วไป:** ซิงก์เวอร์ชัน/จำนวน/env-vars ระหว่างเอกสารกับโค้ด (ใช้เกต ไม่ใช่ความไว้วางใจ) + ตรวจสอบลิงก์ภายใน + ความครอบคลุม i18n ที่ปรับเกณฑ์แบบทางเดียว

### 11. การป้องกันข้อมูลหลอน / ความสอดคล้อง (หมวดหมู่ที่พบได้ยาก)

- **OmniRoute:** known-symbols (การ dispatch ด้วยสตริง ⇒ สัญลักษณ์ที่ยังมีอยู่จริง), provider-consistency, fetch-targets (การ fetch จากไคลเอนต์ ⇒ route ที่มีอยู่จริง), docs-symbols, db-rules (Hard Rules #2/#5), migration-numbering
- **ทั่วไป:** สำหรับ "แหล่งข้อมูลจริงที่ซ้ำซ้อน" ทุกจุด (registry, การ dispatch ด้วยสตริง, การอ้างอิงข้ามเลเยอร์) ให้มีเกตที่พิสูจน์ว่าทั้งสองฝั่งตรงกัน ซึ่งช่วยตรวจจับการเสื่อมสภาพที่การตรวจสอบชนิดข้อมูล/การทดสอบตรวจไม่พบ

### 12. ความยืดหยุ่นและโดเมน (เฉพาะผลิตภัณฑ์)

- **OmniRoute:** chaos (การฉีดข้อผิดพลาด), heap-growth (การรั่วไหล), k6 (soak), promptfoo+garak (การทดสอบเชิงรุก LLM ตาม OWASP LLM Top 10), กฎความยืดหยุ่น 3 ข้อ (circuit-breaker/cooldown/lockout)
- **ทั่วไป:** ระบุรูปแบบความล้มเหลวของโดเมน **ของคุณ** และสร้างเกตสำหรับแต่ละรูปแบบ (แม้จะทำงานเพียงทุกคืนก็ตาม) สำหรับแอป AI: การทดสอบเชิงรุกด้าน injection สำหรับระบบแบบกระจาย: chaos + leak + soak

## ส่วนที่ 4 — แผนการนำไปใช้ซ้ำสำหรับทุกโปรเจกต์

สร้างเป็น **ระยะ** โดยแต่ละระยะต้องสร้างคุณค่าได้ด้วยตัวเอง อย่าพยายามทำทั้ง 12 หมวดหมู่พร้อมกัน —
เพราะจะทำให้เกิดความเหนื่อยล้าจากเกตตามที่ส่วนที่ 2 เตือนไว้อย่างแน่นอน เกตใหม่ทุกตัวต้องเริ่มต้นในสถานะ **ให้คำแนะนำ** และ
เปลี่ยนเป็น **บล็อก** เมื่อมีเสถียรภาพแล้ว

### แกนหลักที่นำกลับมาใช้ซ้ำได้: "กายวิภาคของเกตแบบ ratchet"

ทั้งระบบหมุนรอบรูปแบบไฟล์ 3 ไฟล์นี้ ให้คัดลอกรูปแบบนี้ก่อน:

1. **`baseline.json`** — ค่าเมตริกที่ตรึงไว้ + `direction` (`up`/`down`) + `eps` (ป้องกันความไม่แน่นอน) + `tightenSlack` + `dedicatedGate`
2. **`collect-metrics.<ext>`** — เรียกใช้เครื่องมือ ดึงค่าตัวเลข และเขียนลงใน `metrics.json`
3. **`check-ratchet.<ext>`** — เปรียบเทียบ `metrics.json` กับ `baseline.json`; `exit 1` **เฉพาะ** เมื่อถดถอยเกิน `eps`; `exit 0` (ข้ามอย่างราบรื่น) หากเครื่องมือ/โครงสร้างพื้นฐานไม่พร้อมใช้งาน; เมื่อใช้ `--require-tighten` ให้ `exit 1` หากค่า **ดีขึ้น** แต่ไม่มีการอัปเดต baseline (เพื่อล็อกผลลัพธ์ที่ดีขึ้นไว้)

เมื่อมีสิ่งนี้แล้ว เมตริกใหม่ **ทุกตัว** (coverage, complexity, warnings, SAST alerts, bundle size, mutation score…) ก็เป็นเพียงหนึ่งบรรทัดใน baseline

### ระยะที่ 0 — รากฐาน (สัปดาห์ที่ 1)

มี CI; formatter + linter + typecheck + ตัวรันการทดสอบ 1 ตัว + ค่า coverage ขั้นต่ำแบบ **สัมบูรณ์**
(เช่น 60%) การตรวจสอบก่อน commit เรียกใช้การตรวจสอบที่รวดเร็วและแก้ไขอัตโนมัติได้ _ผลลัพธ์: ไม่มี PR ใดทำลายพื้นฐาน_

### ระยะที่ 1 — กลไก ratchet (สัปดาห์ที่ 2) — **รากฐานของทุกสิ่ง**

นำ 3 ไฟล์ข้างต้นมาใช้ ตรึง baseline สำหรับ: warnings, coverage, complexity, duplication,
dead code, file size _ผลลัพธ์: นับจากนี้ codebase จะดีขึ้นได้เท่านั้น_

### ระยะที่ 2 — การวิเคราะห์เชิงลึกแบบ static (สัปดาห์ที่ 3)

SAST (CodeQL/Sonar/semgrep) พร้อม ratchet สำหรับการแจ้งเตือน; ตัวสแกน secrets (**สืบทอดชุดกฎเริ่มต้น**);
SCA (osv/Dependabot) + รายการอนุญาต license + lockfile-lint _ผลลัพธ์: ช่องโหว่ที่ทราบและ
secrets ที่รั่วไหลจะไม่ผ่าน_

### ระยะที่ 3 — ห่วงโซ่อุปทานของ build (สัปดาห์ที่ 4)

SBOM เมื่อ publish + provenance ที่ลงนามแล้ว (SLSA L2) + Scorecard ตามกำหนดเวลา + การเพิ่มความแข็งแกร่งให้ workflow
(zizmor: token ขั้นต่ำ, ไม่เก็บ credentials ไว้, ตรึงเวอร์ชันของ actions) _ผลลัพธ์: release ที่ตรวจสอบย้อนกลับได้และ
ป้องกันการแก้ไขดัดแปลง_

### ระยะที่ 4 — ความเข้มข้นของการทดสอบ (สัปดาห์ที่ 5–6)

ตัวรันตัวที่ 2 หากมีประโยชน์; **ค่า coverage ขั้นต่ำรายโมดูลสำหรับโมดูลที่สำคัญ** (ป้องกัน Goodhart);
property-based สำหรับตรรกะแบบ pure; **mutation testing ทุกคืน** → เมื่อได้คะแนนครั้งแรก ให้ทำให้
`mutationScore` เป็น ratchet _ผลลัพธ์: coverage ไม่ใช่เมตริกเพื่อความสวยงามอีกต่อไป; พิสูจน์ได้ว่าการทดสอบตรวจจับบั๊กได้จริง_

### ระยะที่ 5 — สัญญาและการทดสอบแบบ dynamic (สัปดาห์ที่ 7)

หากมี API สาธารณะ: oasdiff (การเปลี่ยนแปลงที่ทำให้เข้ากันไม่ได้, **บล็อก**) + schemathesis (fuzz ทุกคืน)
DAST/red-team ทุกคืนตามความเหมาะสมของโดเมน _ผลลัพธ์: สัญญาจะไม่เสียหายโดยไม่มีใครรับรู้_

### ระยะที่ 6 — ป้องกัน hallucination และเฉพาะโดเมน (สัปดาห์ที่ 8)

เกตตรวจสอบความสอดคล้องหนึ่งตัวสำหรับ "ข้อเท็จจริงที่ซ้ำซ้อน" แต่ละรายการในโปรเจกต์ เกตสำหรับโหมดความล้มเหลว
เฉพาะโดเมน (สำหรับ AI: red-team ด้าน injection) _ผลลัพธ์: ความเสื่อมโทรมเชิงโครงสร้างและความล้มเหลวเฉพาะโดเมนมีตาข่ายนิรภัย_

### ระยะที่ 7 — ธรรมาภิบาล (ต่อเนื่อง)

- วงจรให้คำแนะนำ→บล็อกสำหรับเกตใหม่ทุกตัว
- `stale-allowlist`: การยกเว้นทุกกรณีต้องมีเหตุผลประกอบ + issue; ต้องตรวจพบการยกเว้นที่ล้าสมัย
- `evidence-gate`: การกล่าวอ้างความสำเร็จใน PR ต้องมีหลักฐาน (การทดสอบหรือ living test)
- **ทบทวน ROI รายไตรมาสสำหรับแต่ละเกต** (ยกเลิก/หยุดสนับสนุนเกตที่ไม่คุ้มค่า — เพื่อลดความเหนื่อยล้า)
- ยกระดับ Hard Rules ของโปรเจกต์ให้เป็นเกตที่ดำเนินการได้

### หลักการที่ครอบคลุมทุกส่วน (ไม่สามารถต่อรองได้)

- **ใช้ ratchet ไม่ใช่ค่าตายตัว** ตรวจสอบ _การไม่ถดถอย_ ไม่ใช่ตัวเลขคงที่ (ยกเว้นค่าขั้นต่ำเพื่อป้องกันการเป็นศูนย์)
- **ใช้ค่าขั้นต่ำแบบสัมบูรณ์ร่วมกับ ratchet** ค่าขั้นต่ำป้องกันการพังทลาย; ratchet ป้องกันการเสื่อมถอยอย่างช้าๆ
- **ป้องกัน Goodhart ตั้งแต่ขั้นออกแบบ** เมตริกเป้าหมายทุกตัวต้องมีตัวถ่วงดุล (coverage ⇒ mutation + การป้องกัน masking; ค่าขั้นต่ำรายโมดูลเพื่อบังคับให้ทดสอบโค้ดส่วนที่ยาก)
- **ข้ามอย่างราบรื่น** โครงสร้างพื้นฐานที่ไม่พร้อมใช้งานจะไม่บล็อก; บล็อกเฉพาะการถดถอยที่เกิดขึ้นจริง
- **ใช้ `dedicatedGate` สำหรับเมตริกที่มีค่าใช้จ่ายสูง** เมตริกที่ต้องใช้ binary ภายนอกจะมีสคริปต์ของตัวเอง (พร้อมการข้าม) แยกออกจาก ratchet ส่วนกลางแบบ synchronous
- **วางเกตตรงจุดที่เกิดการ merge** อย่าปล่อยให้มีช่องว่างระหว่างเกตแบบรวดเร็วกับการ merge จริง (บทเรียนจากการแยก fast-gates)
- **มีเกตแบบบล็อกจำนวนน้อยและเลือกอย่างเหมาะสม** Sonar/DORA: เงื่อนไขมากเกินไป = ความเหนื่อยล้า ควรใช้การให้คำแนะนำ + ratchet แทนกำแพงเกตแบบบล็อก

## ส่วนที่ 5 — การปรับปรุงที่แนะนำ (เรียงตามลำดับความสำคัญ, ใช้งานร่วมกันได้)

**P0 — ROI สูงสุด, เกือบพร้อมใช้งาน**

1. **กลไก ratchet สำหรับ mutation score** (หลังจาก Stryker รอบ nightly ครั้งแรกสร้างค่าขึ้นมาแล้ว) ยาต้านหลักสำหรับ coverage-Goodhart; เสร็จแล้วประมาณ 90%
2. **ปิดช่องโหว่ fast-gates ที่เหลืออยู่** — ยกระดับ production build ใน `quality.yml` หลังจากช่วง advisory หนึ่งสัปดาห์
   และทยอยย้ายการตรวจสอบแบบ deterministic ที่ใช้เฉพาะ release PR ไปยังเส้นทาง PR→release
3. **Branch protection บน `main`** (การตั้งค่าโดยเจ้าของ) — เพิ่ม Scorecard และปิดช่องว่างของ DSOMM

**P1 — มีคุณค่า** 4. **osv/oasdiff → blocking ด้วยขอบเขตที่เหมาะสม** — osv เฉพาะ CRITICAL+แก้ไขได้ (สองขั้นตอนแบบเดียวกับ Trivy); oasdiff บล็อก breaking changes 5. **`require-tighten` → blocking** (เมื่อสิ้นสุดรอบ) — ล็อกผลลัพธ์การปรับปรุง metrics ไว้ 6. **การทบทวน ROI/ระยะเวลาต่อ gate** ใน `ci-summary` — ค้นหาและตัด gate ที่ช้า/ให้คุณค่าต่ำออก

**P2 — ผลตอบแทนที่ลดลง** 7. **SLSA L3** — builder แบบ hermetic/reproducible (GitHub SLSA generator) หากต้องการยกระดับจาก L2 8. **CodeQL config ที่ commit ไว้ + semgrep แบบระบุเวอร์ชัน** — ควบคุมและทำซ้ำได้มากขึ้น 9. **DAST smoke ต่อ PR** — ชุดย่อยที่รวดเร็วของ schemathesis/promptfoo บน endpoint ที่มีความเสี่ยงสูงสุด (ไม่ใช่เฉพาะ nightly) 10. **แดชบอร์ด flakiness + DORA metrics** — ตรวจสอบให้แน่ใจว่า gate ไม่ได้บั่นทอนความเร็ว

## ส่วนที่ 6 — บทเรียนที่เป็นรูปธรรมจากการ release (gate ที่ต้องเพิ่มใน Phase 9)

> ส่วนนี้บันทึกเหตุการณ์จริงจากการปิด release ซึ่ง **ขาด gate**
> พร้อมหลักฐานที่เป็นรูปธรรมและ gate ที่เสนอ แต่ละรายการเป็นตัวเลือกสำหรับส่วนที่ 5

### บทเรียนจาก v3.8.27 (2026-06-17) — "ช่องโหว่ fast-gates" ทำให้ regression แบบ deterministic หลุดไปถึงวัน release

**สิ่งที่เกิดขึ้น** ระหว่าง `/generate-release` ของ v3.8.27 นั้น release PR (`release/v3.8.27` → `main`)
เป็นการรัน matrix เต็มรูปแบบของ `ci.yml` **ครั้งแรก** ในรอบที่ผสานรวมแล้ว ผลลัพธ์คือเกิดความล้มเหลวพร้อมกัน 12 รายการ
— **การทดสอบแบบ deterministic 3 รายการ** + flake/ปัญหาจาก environment ประมาณ 9 รายการ ไม่มีรายการใดเป็น regression ของผลิตภัณฑ์ที่ใช้งานจริง
แต่ทั้งหมดไม่ถูกตรวจพบ เพราะ PR ในรอบจะเข้าสู่ `release/**` ผ่าน **Fast QG
(`quality.yml`)** ซึ่งไม่ได้รัน unit suite เต็มรูปแบบ, `pr-test-policy` (test-masking),
integration suite เต็มรูปแบบ หรือการตรวจสอบความสอดคล้องของ schema โดยรายการแบบ deterministic ทั้ง 3 รายการคือ:

1. **การทดสอบล้าสมัยเนื่องจากการเปลี่ยนแปลง UI** — `permissions modal switch buttons declare button type`:
   #4034 เพิ่ม switch ตัวที่ 4 (ยังคง a11y `type="button"` ไว้); จำนวน `=== 3` ของการทดสอบจึง
   ล้าสมัย Static analysis ควรตรวจพบปัญหานี้ใน PR #4034
2. **การทดสอบล้าสมัยเนื่องจากการเปลี่ยนแปลงด้าน packaging** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` กลายเป็น required path ที่ถูกต้อง; รายการค่าที่คาดหวังของการทดสอบจึง
   ล้าสมัย
3. **ความแตกต่างจาก modularization ที่ทำให้ข้อมูลสูญหาย (ร้ายแรงที่สุด)** — `settings schemas accept ... unprefixed
toggle`: `updateSettingsSchema` ที่ถูกทำให้เป็น **modularized** (`schemas/settings.ts`, สร้างโดย #3988) แตกต่าง
   จาก canonical source (`settingsSchemas.ts`): **45 fields เทียบกับ 85 — หายไป 40 + แตกต่างกัน 6 (qdrant\*)** โดยมันเป็น
   **dead-code** (runtime ใช้ canonical source) จึงไม่มีผลกระทบต่อระบบที่ใช้งานจริง แต่มีเพียง parity
   test ที่เขียนด้วยมือเท่านั้นที่ตรวจพบ #4030 ได้กู้คืน field ที่หายไปในลักษณะเดียวกัน 16 รายการจาก #3988/#3993 แต่รายการนี้หลุดรอดไป

**gate ที่เสนอ (Phase 9):**

- **G1 — ปิดช่องโหว่ fast-gates อย่างแท้จริง (ต่อยอด P0 #2)** ใน `quality.yml` (PR→`release/**`)
  นอกเหนือจาก typecheck + impacted tests แล้ว ให้รัน **`pr-test-policy` (test-masking) + deterministic
  unit suite เต็มรูปแบบ** (หรืออย่างน้อยไฟล์ static/parity ซึ่งรวดเร็วและไม่ flaky)
  วิธีนี้ทำให้ตรวจพบการทดสอบที่ล้าสมัยและการลบ assert ได้ใน PR ที่ก่อให้เกิดปัญหา — ไม่ใช่ใน
  วัน release แยก integration/e2e ออกไว้ (ช้า/flaky) แต่เลเยอร์ deterministic จะปล่อยให้มีอยู่เฉพาะ
  ใน PR→main ไม่ได้
- **G2 — gate ตรวจสอบความสอดคล้องของ modularization (ใหม่, ปัจจุบันยังไม่ครอบคลุม)** การตรวจสอบที่เปรียบเทียบ **shape**
  (`z.object` keys, registry entries) กับ canonical
  source สำหรับแต่ละ symbol ที่ถูก re-export โดย modularized barrel (`src/shared/validation/schemas/*`, โมดูล
  `providerRegistry` ฯลฯ) และ **ล้มเหลวเมื่อพบความแตกต่าง** (field หายไป/เกินมา) วิธีนี้น่าจะตรวจพบ field ที่หายไป 40 รายการจาก
  #3988 ได้ตั้งแต่ใน PR นั้น เป็นการทำให้ parity test ที่เขียนด้วยมือใช้ได้ในวงกว้างขึ้น (ซึ่งปัจจุบันมีเฉพาะในจุดที่มีคน
  จำได้ว่าต้องเขียน) มีต้นทุนต่ำ: import ทั้งสองฝั่งแล้ว diff `Object.keys(shape)`
- **G3 — การคัดแยก flake แบบ deterministic (สนับสนุน)** การทดสอบ LiveWS-startup และ integration-combo/breaker
  ล้มเหลวเนื่องจาก server timeout/cascade ใน CI (environment) ไม่ใช่ logic ให้ทำเครื่องหมายรายการเหล่านี้เป็น
  `known-flaky` (กักไว้พร้อม issue) เพื่อให้สถานะสีแดงของ release PR เป็น **สัญญาณจริงเท่านั้น** ไม่ใช่ noise
  ที่บดบัง regression แบบ deterministic ที่อยู่ตรงกลาง

**หลักการ:** _gate ต้องรันในจุดที่เกิดการ merge_ (มีอยู่แล้วใน "หลักการที่ใช้ร่วมกันทุกส่วน") เหตุการณ์
v3.8.27 แสดงให้เห็นว่าสิ่งนี้ใช้กับ **เลเยอร์การทดสอบแบบ deterministic** ด้วย ไม่ใช่แค่ lint/typecheck —
มิฉะนั้นหนี้จากการทดสอบที่ล้าสมัย + modularization ที่ทำให้ข้อมูลสูญหายจะปรากฏเฉพาะใน PR→main แบบรวมเป็นชุด และใน
ช่วงเวลาที่เลวร้ายที่สุด
