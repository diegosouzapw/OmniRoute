## npm Trusted Publishing (ค่าเริ่มต้นตั้งแต่ v3.8.51) — จัดเตรียมไว้เมื่อมีคำขอ และเผยแพร่โดยตรงเป็นทางเลือกสำรอง

`npm-publish.yml` เผยแพร่ผ่าน **npm Trusted Publishing (OIDC)** โดยค่าเริ่มต้น: งาน
`stage-npm` (ที่โฮสต์โดย GitHub) จะแลกเปลี่ยน id-token ของ GitHub เป็นข้อมูลรับรอง npm
แบบอายุสั้นสำหรับการทำงานครั้งนั้น — ไม่มีโทเค็น npm อายุยาวอยู่ในข้อมูลลับของรีโพซิทอรี ไม่มีพรอมต์ 2FA และแนบ provenance มาด้วย
นี่คือวิธีข้ามข้อจำกัดที่ npm อนุญาตในขณะนี้ เนื่องจากโทเค็นที่ข้าม 2FA กำลังจะถูกยกเลิก
วิธีนี้ทำให้โฟลว์อัตโนมัติเต็มรูปแบบที่โปรเจกต์เคยมีจนถึง v3.8.48 กลับมา พร้อมกับยังคง
การรับประกันของ WS1.3 (โทเค็นที่รั่วไหลไม่สามารถใช้เผยแพร่ได้โดยลำพัง — เพราะไม่มีโทเค็น)

**การตั้งค่าครั้งเดียว (เจ้าของ):** npmjs.com → แพ็กเกจ `omniroute` → Settings → _Trusted
Publisher_ → GitHub: เจ้าของ `diegosouzapw`, รีโป `OmniRoute`, เวิร์กโฟลว์ `npm-publish.yml`
(สภาพแวดล้อม: ไม่มี) จนกว่าจะตั้งค่านี้ ขั้นตอนอัตโนมัติจะล้มเหลวด้วย `ENEEDAUTH`:
ให้สั่งทำงานใหม่ด้วย `publish_mode=staged` (ด้านล่าง) หรือ `direct`

### การเผยแพร่แบบจัดเตรียมไว้ (เมื่อมีคำขอ — `publish_mode=staged`)

เวิร์กโฟลว์ npm-publish จะไม่เผยแพร่โดยตรงอีกต่อไป แต่จะบูต tarball ที่แพ็กแล้ว
(`check:pack-boot`) จากนั้นเรียกใช้ `npm stage publish` — ไบต์ชุดเดียวกันจะถูกพักไว้บน
รีจิสทรี และ **ยังติดตั้งไม่ได้** จนกว่าเจ้าของจะอนุมัติ ด่าน 2FA ที่ต้องดำเนินการโดยมนุษย์ถูกย้าย
ไปอยู่หลังการพิสูจน์ ไม่ใช่ก่อนหน้า

**โฟลว์สำหรับเจ้าของหลังจากเวิร์กโฟลว์เป็นสีเขียว:**

1. `npm stage list omniroute` — ค้นหา stage id (ซึ่งจะแสดงอยู่ในสรุปของเวิร์กโฟลว์ด้วย)
2. ตรวจสอบไบต์ที่จัดเตรียมไว้ (แนะนำ): `npm stage download <id>` จากนั้นติดตั้ง
   tarball ที่ดาวน์โหลดลงใน prefix ชั่วคราวแล้วบูต (`npm run check:pack-boot` ทำให้
   ผลการตัดสินจากลำดับ pack→install→boot แบบเดียวกันเป็นอัตโนมัติใน CI)
3. `npm stage approve <id>` — พรอมต์ 2FA คือขั้นตอนการเผยแพร่ `npm stage reject <id>` ใช้เพื่อละทิ้ง
4. ตาข่ายนิรภัยหลังเผยแพร่: ตัวตรวจสอบหลังเผยแพร่ (WS1.4 ของแผน v3.8.49) จะติดตั้ง
   เวอร์ชันที่เผยแพร่จากรีจิสทรีสาธารณะในคอนเทนเนอร์ใหม่ทั้งหมด แล้วบูตเวอร์ชันนั้น

**ทางเลือกสำรองฉุกเฉิน:** `workflow_dispatch` พร้อม `publish_mode=direct` จะคืนค่าการทำงาน
แบบเดิมที่เรียก `npm publish` ทันที (ใช้เฉพาะเมื่อการจัดเตรียมเองทำงานผิดปกติ และให้บันทึกเหตุผล)

**การเพิ่มความปลอดภัยครั้งเดียว (เจ้าของ, npmjs.com):** กำหนดค่า Trusted Publisher สำหรับ
`omniroute` เป็นโหมดจัดเตรียมเท่านั้น เพื่อไม่ให้โทเค็นอายุยาวที่รั่วไหลสามารถเรียก `npm publish`
โดยตรงจากที่ใดก็ได้ — CI ทำได้เพียงจัดเตรียม และมีเพียง 2FA ของเจ้าของเท่านั้นที่เผยแพร่ได้

**คู่มือรับมืออาร์ติแฟกต์เสียหาย (ไม่เปลี่ยนแปลง):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
เป็นการตอบสนองเริ่มต้นตามค่าเริ่มต้น (ใช้เวลาไม่กี่นาทีและย้อนกลับได้); ใช้ `npm unpublish` เฉพาะภายในกรอบเวลา
72 ชั่วโมง/ไม่มีแพ็กเกจที่พึ่งพา และห้ามใช้เป็นการดำเนินการแรก สำหรับ Docker: ห้ามเขียนทับแท็กเวอร์ชัน — การย้อนกลับคือ
การชี้ `latest` ไปยัง digest ล่าสุดที่ใช้งานได้

**Docker Hub `latest` (จำเป็นสำหรับทุกการเผยแพร่ SemVer แบบเสถียร):**
เวิร์กโฟลว์ `docker-publish` ต้องติดแท็ก **ทั้ง** `X.Y.Z` และเมื่อ
`should-promote-latest.sh` ยืนยันว่านี่คือ SemVer แบบเสถียรที่สูงที่สุด ให้ติดแท็ก `:latest`
ด้วย **digest เดียวกัน** หลังจากงานเสร็จสิ้น: digest ของ `latest` บน Hub ต้องเท่ากับ digest ของ
SemVer ใหม่ และ `last_updated` ต้องเปลี่ยนแปลง อย่าปล่อยให้ `:latest` ชี้ไปยัง
บิลด์เก่า ในขณะที่บันทึกประจำรุ่นกล่าวถึงการแก้ไขที่มีเฉพาะใน git
คู่มือเริ่มต้นอย่างรวดเร็วสำหรับ Compose ใช้ `:latest`; GitOps ควรตรึงเวอร์ชันไว้ที่ `X.Y.Z` ต่อไป ดู
[ช่องทางการเผยแพร่ Docker](../guides/DOCKER_GUIDE.md#release-channels) และ #10317

## ช่องทางด่วนสำหรับ Hotfix (ป้ายกำกับ `hotfix`)

PR ที่ติดป้ายกำกับ `hotfix` จะข้ามเมทริกซ์ CI ขนาดใหญ่ (E2E แบบ 9 ชาร์ด, coverage ratchet,
quality-gate, quality-extended) และคงเฉพาะเกตที่รวดเร็วและให้สัญญาณชัดเจน ได้แก่ build,
ชาร์ดของ unit, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
และการทดสอบ boot-smoke จาก tarball (`check:pack-boot`) เป้าหมาย: ผ่านภายใน ≤15 นาที แทนที่จะใช้เวลาประมาณ ~33 นาที

**นโยบายการเข้าใช้ — ต้องครบทั้งสี่ข้อ (อิงรูปแบบช่องทางฉุกเฉินของ Chromium/VS Code/Node):**

1. **ความรุนแรง**: ระบบ production ใช้งานไม่ได้ — อาร์ติแฟกต์ที่เผยแพร่แล้วแครชขณะบูต /
   เป็นการแก้ไขด้านความปลอดภัย / ผู้ใช้รีลีสทุกรายได้รับผลกระทบ "สำคัญ" ไม่ได้แปลว่า "ใช้งานไม่ได้"
2. **อำนาจอนุมัติ**: มีเพียงเจ้าของ repository เท่านั้นที่ติดป้ายกำกับ `hotfix` ป้ายกำกับนี้ถือเป็น
   การอนุมัติ — ห้ามเปิดใช้เองบน campaign PR
3. **หลักฐาน**: เนื้อหา PR ต้องลิงก์ไปยังการรันชุดใหญ่ครั้งก่อนที่ผ่านทั้งหมด (ชุดที่งานซึ่งถูกข้าม
   จะตรวจสอบซ้ำ) รวมถึงการทดสอบของการแก้ไขนี้เองที่แสดงผลล้มเหลวก่อนแล้วจึงผ่าน
4. **ขอบเขต**: ใช้สำหรับ cherry-pick เท่านั้น — เฉพาะการแก้ไขขั้นต่ำ ห้าม refactor และห้ามพ่วงการเปลี่ยนแปลงอื่น

ส่วน coverage/ratchet ที่ถูกข้ามจะได้รับการตรวจสอบซ้ำในการรันเต็มรูปแบบครั้งถัดไปบน
release branch (คงสถานะผ่านของรีลีสอย่างต่อเนื่อง) — ช่องทางนี้ข้ามเพียงการรอ ไม่เคยข้ามการตรวจสอบ
diff ที่เปลี่ยนเฉพาะการทดสอบ (ไฟล์ทั้งหมดอยู่ภายใต้ `tests/` และไม่มีไฟล์ใดอยู่ภายใต้ `tests/e2e/`) จะข้ามเมทริกซ์ E2E
โดยอัตโนมัติ โดยไม่ต้องใช้ป้ายกำกับใดๆ

### ก่อนเผยแพร่

- [ ] PR ทั้งหมดที่กำหนดเป้าหมายไว้สำหรับรุ่นนี้ถูกรวมเข้ากับ `release/vX.Y.0` แล้ว
- [ ] รายการ Linear/issue ที่ยังเปิดอยู่ทั้งหมดสำหรับเวอร์ชันนี้ถูกปิดหรือเลื่อนไปยังเป้าหมายสำคัญถัดไปแล้ว
- [ ] CI ผ่านทั้งหมดบนสาขา `release/vX.Y.0`
- [ ] ไม่มีเครื่องหมาย `TODO(release)` ในโค้ด: `grep -r "TODO(release)" src/ open-sse/`
- [ ] อิมเมจฐาน Docker เป็นเวอร์ชันล่าสุด (ปัจจุบันคือ `node:24.15.0-trixie-slim`)

### เวอร์ชันและบันทึกการเปลี่ยนแปลง

- [ ] เรียกใช้ `/version-bump-cc <patch|minor|major>` (สกิล Claude Code)
  - เพิ่มเวอร์ชันใน `package.json`, `electron/package.json`
  - สร้าง `CHANGELOG.md` ใหม่จากคอมมิต git นับตั้งแต่แท็กล่าสุด
  - อัปเดตป้ายสถานะใน README.md
- [ ] ตรวจสอบ CHANGELOG.md ด้วยตนเองและปรับข้อความคอมมิตให้เรียบร้อยหากจำเป็น
- [ ] ตรวจสอบให้แน่ใจว่าส่วน semver ล่าสุดใน `CHANGELOG.md` ตรงกับเวอร์ชันใน `package.json`
- [ ] คง `## [Unreleased]` ไว้เป็นส่วนแรกของบันทึกการเปลี่ยนแปลงสำหรับงานที่กำลังจะมาถึง
- [ ] อัปเดต `docs/openapi.yaml` → `info.version` ต้องตรงกับเวอร์ชันใน `package.json`

### คุณภาพโค้ด

- [ ] `npm run lint` — ข้อผิดพลาด 0 รายการ (คำเตือนมีอยู่ก่อนแล้ว)
- [ ] `npm run typecheck:core` — ผ่านโดยไม่มีปัญหา

### โครงสร้างผลลัพธ์ของบิลด์

รีพอซิทอรีใช้ไดเรกทอรีผลลัพธ์ที่แตกต่างกันสามแห่ง — ห้ามสับสนกัน:

| ไดเรกทอรี | วัตถุประสงค์                                                 | ติดตามหรือไม่    |
| --------- | ------------------------------------------------------------ | ---------------- |
| `src/`    | ซอร์สของแอปพลิเคชัน (TypeScript / TSX)                       | ใช่              |
| `.build/` | ไฟล์ระหว่างกระบวนการบิลด์ — ผลลัพธ์ `next build` (`distDir`) | ไม่ (gitignored) |
| `dist/`   | บันเดิล npm ที่พร้อมจัดส่ง — ประกอบโดย `assembleStandalone`  | ไม่ (gitignored) |

> **หมายเหตุสำหรับผู้ดำเนินการ:** ไดเรกทอรีอิมเมจบน VPS ระยะไกลยังคงเป็น `/usr/lib/node_modules/omniroute/app/`
> มีเพียงผลลัพธ์บิลด์ **ภายในรีพอซิทอรี** เท่านั้นที่ย้าย (`app/` → `dist/`) สกิลสำหรับการปรับใช้จะใช้ rsync
> เนื้อหาจาก `dist/` ไปยังไดเรกทอรี `app/` ระยะไกล — ไม่จำเป็นต้องเปลี่ยนพาธบน VPS

**โฟลว์การบิลด์ครั้งเดียว:**

```
npm run build:release
  └─ rm -rf .build dist          (ล้าง)
  └─ next build → .build/next/   (ไฟล์ระหว่างกระบวนการ)
  └─ assembleStandalone          (คัดลอก standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (ตัวตรวจสอบ HEAD)
```

ห้ามรัน `npm run build` แล้วตามด้วย `npm run build:cli` แยกต่างหากสำหรับการปรับใช้ — ให้ใช้
`npm run build:release` ซึ่งจะบิลด์ใหม่ทั้งหมดแบบสะอาดและสร้างตัวตรวจสอบในคำสั่งเดียว

`scripts/release/dry-run-lts-cut.mjs` ไม่ดำเนินการเปลี่ยนแปลงใด ๆ: สคริปต์จะอ่าน git และ `gh` แล้วพิมพ์
ลำดับขั้นตอนทั้งหมด — เงื่อนไขเบื้องต้น (สามารถ resolve ต้นทางได้, repository ต้นทางมีประวัติครบถ้วน —
shallow clone ไม่สามารถ push `stable/v3` ได้ เนื่องจากฝั่งรับจะปฏิเสธ pack เมื่อพบ grafted parent แรก
ดังนั้นให้ตัดรุ่นจาก clone แบบเต็ม หรือเรียก `git fetch --unshallow origin` ก่อน — มีแท็ก
ก่อนหน้าอยู่, `package.json` เป็นเวอร์ชันเป้าหมาย, มี issue `release-freeze` ที่เปิดอยู่, ไม่มี
issue `Release branch not green` ที่เปิดอยู่
บนสาขารีลีสที่มีอยู่ — สาขาที่ไม่มีอยู่จะรายงานเป็น `?` ซึ่งหมายถึงไม่ทราบค่า และจะไม่ถือว่า
เป็นสีเขียว — มีการกำหนดค่าคิว `release` ของ Mergify แล้ว (G11: `queue_rules`, `checks_timeout`,
ป้ายกำกับ `queue`), ruleset ของ `release/*` ยังคงป้องกันการลบและ force-push และ
`stable/v3` กับ `develop` ยังไม่มีอยู่), ขั้นตอนของทั้งสองสาขา, trigger ของ workflow ที่ยังไม่ทำงานรายการใด
และเงื่อนไข `if:` ใดที่จะกลายเป็นจริง (รวมถึงรายการที่ยังถูกกั้นด้วยตัวแปรของ repository หรือ
ถูกตรึงไว้กับ repository หลัก), dist-tag ที่คาดไว้ (`latest` → 3.9.0, `next` และ
`nightly` ว่างเปล่า) และการ rollback รหัสออก `0` = `RESULT: READY`, `1` = เงื่อนไขเบื้องต้น
ที่เป็นข้อบังคับล้มเหลว (`✗`), `2` = ข้อผิดพลาดในการใช้งาน `--advisory <id,...>` จะลดระดับ
การตรวจสอบให้เป็นคำเตือน (`!`) โดยไม่ซ่อนการตรวจสอบนั้น

เรียกใช้การทดลองรันสำหรับการตัดรุ่นจริงขณะที่ release freeze ของ 3.9.0 ยังเปิดอยู่ — สาขาต่าง ๆ

### อาร์ติแฟกต์ตัวอย่างสำหรับ PR (สร้างครั้งเดียว แล้วโปรโมตไบต์ชุดเดิม)

`scripts/release/artifact-identity.mjs`) และรับรอง tarball ใน job แยกต่างหาก การโปรโมต
เวอร์ชันตัวอย่างหมายถึงการติดตั้ง tarball นั้น: ห้าม build ใหม่จาก source

### การตัดรุ่น (3.9.0 หลังจาก GO)

   การ push ไปยัง `origin` หากต้องการนำคอมมิต develop ที่ผ่านการตรวจสอบแล้วกลับมาใช้ ให้เรียกใช้

5. เวิร์กโฟลว์ที่ยังไม่ทำงานจะเปิดใช้งานเมื่อมีสาขาอยู่: `forward-port.yml` (พุชไปยัง
   `stable/v3`), `validate-stable-pr.yml` (PR ที่ส่งไปยัง `stable/v3`) และ `nightly-v4-build.yml`
   (บิลด์ `develop`) ก่อนเปิดใช้งานจริง ให้ตั้งค่าซีเคร็ตของรีโพซิทอรี `secrets.FORWARD_PORT_TOKEN` (เพื่อให้ CI ทำงานบน
   PR สำหรับ forward-port) ส่วนการเผยแพร่ nightly จะยังคงปิดอยู่จนกว่าเจ้าของจะตั้งค่าตัวแปรของรีโพซิทอรี
   `vars.NIGHTLY_PUBLISH` เป็น `true` และ npm Trusted Publishing ยอมรับ
   `nightly-v4-build.yml` การกำหนดแชนเนลอยู่ใน `scripts/release/dist-tag.mjs` ซึ่งเป็น
   ตัวกำหนดเดียวกับที่ `npm-publish.yml` ใช้
6. ตรวจสอบแชนเนล: `npm view omniroute dist-tags --json` แสดง `latest` = 3.9.0 และไม่มี
   `next` / `nightly` จนกว่าจะเผยแพร่ v4
7. หากจำเป็น ให้ย้อนกลับด้วย: `git push origin --delete refs/heads/stable/v3 refs/heads/develop`
   และ `npm dist-tag add omniroute@3.8.59 latest`

## การย้อนกลับเวอร์ชัน

หากรีลีสมีปัญหาร้ายแรง:

1. `gh release edit vX.Y.Z --prerelease` (ทำเครื่องหมายว่าไม่ใช่เวอร์ชันล่าสุด)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (เฉพาะเมื่อผู้ใช้ยังไม่ได้นำไปใช้)
3. หรือ: ทำ hotfix บน `release/vX.Y.0` → ออก patch release `vX.Y.(Z+1)`
4. แจ้งให้ทราบใน GitHub Discussions และ Discord ทันที

## กฎที่ต้องปฏิบัติตามอย่างเคร่งครัด

- ห้าม commit ไปยัง `main` โดยตรง
- ห้ามใช้ `git push --force` กับ branch `main` หรือ `release/*`
- ห้ามข้าม Husky hooks (`--no-verify`)
- ห้าม commit secret, credential หรือไฟล์ `.env`
- Coverage ต้องคงไว้ที่ ≥60/60/60/60 (statements/lines/functions/branches)
- ต้องเพิ่มหรืออัปเดต test เสมอเมื่อเปลี่ยนแปลง production code ใน `src/`, `open-sse/`, `electron/` หรือ `bin/`

