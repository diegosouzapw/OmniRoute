Decriptarea transparentă TPROXY este **al 5-lea mod de capturare** OmniRoute pentru stiva MITM
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Aceasta interceptează și **decriptează** traficul HTTPS local de ieșire pe Linux
folosind TPROXY din kernel + rutare bazată pe politici — **fără** falsificarea `/etc/hosts` și
**fără** modificarea setărilor de proxy de sistem la nivelul întregului sistem de operare. Este adecvată pentru
utilizarea fără interfață grafică (nu există modificări DNS care trebuie eliminate), iar regulile firewallului sunt eliminate automat la repornire.

Spre deosebire de celelalte moduri de capturare, TPROXY nu necesită configurare pentru fiecare gazdă: interceptează în mod transparent
gazde de destinație **arbitrare** pe un port țintă, încheie TLS cu
un certificat de entitate finală pe care îl emite dinamic pentru fiecare nume de gazdă SNI, capturează schimbul
decriptat și recriptează cererea către destinația inițială.

> **Numai pentru Linux, numai cu privilegii root, cu activare explicită.** Acest mod necesită Linux, un modul suplimentar nativ
> construit cu un lanț de instrumente C și capabilitatea **CAP_NET_ADMIN** (de obicei root). Este protejat
> de API-ul AgentBridge accesibil numai prin loopback și este dezactivat implicit. O CA MITM de încredere,
> care poate semna pentru orice gazdă, reprezintă o capabilitate puternică — consultați [§6 Securitate](#6-security).

**Sursă:** `src/mitm/tproxy/`
**Rută API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Comutator în panoul de control:** Traffic Inspector → bara de instrumente pentru modurile de capturare → **„Decriptare TPROXY”** ⚠
**Consultați și:** [`docs/frameworks/TRAFFIC_INSPECTOR.md`](../frameworks/TRAFFIC_INSPECTOR.md),
[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Ce este și când trebuie utilizat

Fiecare dintre celelalte patru moduri de capturare are câte o limitare:

| Mod                      | Cum este direcționat traficul                                | Limitare                                             |
| ------------------------ | ------------------------------------------------------------ | ---------------------------------------------------- |
| AgentBridge              | falsificare DNS prin `/etc/hosts` pentru un set fix de gazde | numai gazdele înregistrate ale agenților IDE         |
| Gazde personalizate      | falsificare DNS prin `/etc/hosts` pentru fiecare gazdă       | câte o intrare per gazdă; sudo pentru editarea hosts |
| HTTP_PROXY               | variabilele de mediu `HTTP_PROXY`/`HTTPS_PROXY`              | numai aplicațiile care respectă variabila de mediu   |
| Proxy la nivel de sistem | setările proxy ale sistemului de operare                     | modifică starea globală; necesită revenire           |

În schimb, decriptarea transparentă TPROXY direcționează traficul la nivelul **kernelului**. Aceasta
marchează conexiunile TCP locale de ieșire noi către un port țintă (implicit `443`) în
lanțul `mangle OUTPUT`, o regulă `ip rule` redirecționează pachetele marcate către livrarea locală,
iar la reintrare, ținta `TPROXY` din `mangle PREROUTING` le transmite unui
listener **IP_TRANSPARENT** — care apoi încheie TLS și capturează textul în clar.

Utilizați acest mod atunci când doriți să capturați și să decriptați traficul unui proces care:

- comunică cu o gazdă pe care AgentBridge nu o înregistrează și
- nu respectă `HTTP_PROXY` și
- nu doriți să îl perturbați printr-o modificare a proxy-ului la nivel de sistem.

Deoarece interceptarea are loc în kernel, procesul sursă nu necesită **nicio
modificare de configurare** — însă procesul trebuie să acorde încredere CA-ului dinamic instalat de OmniRoute
(consultați [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Cerințe

| Cerință              | Detaliu                                                                                                                                                     |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SO**               | Numai Linux — **IP_TRANSPARENT** este o opțiune de socket disponibilă exclusiv pe Linux. Încărcătorul returnează „indisponibil” pe orice altă platformă.    |
| **Privilegii**       | Capabilitatea **CAP_NET_ADMIN** pentru a crea socketul transparent și a aplica regulile `iptables`/`ip` — în practică, rulați ca root.                      |
| **Addon nativ**      | Un mic addon N-API (`src/mitm/tproxy/native/transparent.c`) trebuie compilat sau furnizat ca prebuild. Consultați [§3](#3-the-native-ip_transparent-addon). |
| **Module de kernel** | `iptables` cu suport pentru potrivirile `TPROXY`, `mangle` și `mark` (validat cu kernelul 6.8.0).                                                           |

**Degradare controlată:** dacă lipsește oricare dintre cerințe (sistem non-Linux, fără toolchain,
addon necompilat), încărcătorul addonului (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
returnează `null` în loc să genereze o excepție. Starea modului de captură raportează apoi
`available: false`, comutatorul din panoul de control este **dezactivat**, cu textul explicativ
„Decriptarea TPROXY necesită Linux + root + addonul nativ”, iar restul
OmniRoute continuă să funcționeze.

## §3 Addonul nativ IP_TRANSPARENT

Modulul `net` din Node nu poate apela `setsockopt(IP_TRANSPARENT)` _înainte de_ `bind()`, ceea ce
necesită TPROXY (în caz contrar, kernelul elimină pachetele redirecționate). Addonul
(`src/mitm/tproxy/native/transparent.c`, compilat prin `binding.gyp`) este un mic modul N-API
care expune trei funcții, utilizate prin `transparentSocket.ts`:

| Funcția addonului                     | Operațiunea asupra socketului                                                                     | Utilizare                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, returnează fd-ul brut | listenerul transparent de captură (Node adoptă fd-ul prin `server.listen({ fd })`) |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** pe un fd existent                                                        | prevenirea buclelor (marchează socketurile proprii ale proxy-ului)                 |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **înaintea** unui `connect()` non-blocant, returnează fd-ul              | redirecționarea în amonte recriptată (SYN-ul conține marcajul)                     |

Destinația originală este citită din `socket.localAddress`/`localPort` — TPROXY
o păstrează, astfel încât nu este necesară nicio căutare **SO_ORIGINAL_DST**/NAT.

### Compilarea addonului

```bash
npm run build:native:tproxy      # cd src/mitm/tproxy/native && node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- În timpul `npm run build`, `scripts/build/build-tproxy-native.mjs` rulează `node-gyp
rebuild`. Acesta este **exclusiv pentru Linux și necritic** — lipsa unui toolchain doar face
  ca modul de captură să fie indisponibil.
- `assembleStandalone.mjs` copiază `build/Release/transparent.node` în pachetul
  independent; `transparentSocket.ts` îl rezolvă atât relativ la modul, cât și
  relativ la cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` și `prebuilds/` sunt ignorate de git — binarul este **compilat, niciodată
  comis**.

Încărcătorul verifică, în ordinea priorității:
`native/build/Release/transparent.node`, apoi `native/prebuilds/transparent.node`
(atât relativ la modul, cât și sub `<cwd>/src/mitm/tproxy/`).

## §4 CA dinamică per SNI și programul de instalare în depozitul de încredere

> **Actualizarea #6684:** serverul static AgentBridge (`src/mitm/server.cjs`) folosește acum
> același model arhitectural CA/certificat derivat, în locul unui singur certificat
> derivat static, autosemnat. Acesta utilizează o instanță CA **distinctă**
> (`src/mitm/cert/rootCa.ts`, păstrată în `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> și se instalează în slotul preexistent `omniroute-mitm.crt` al depozitului de încredere
> (înlocuind vechiul certificat derivat unic de acolo — nu este necesară curățarea unei încrederi duble),
> fiind menținută complet separat de propriul slot `omniroute-tproxy-ca.crt` al TPROXY
> de mai jos.
> Instalările AgentBridge noi primesc automat modelul CA; o instalare care
> avea deja încredere în vechiul certificat derivat static continuă să îl utilizeze până când operatorul
> activează explicit `MITM_ROOT_CA_ENABLED=true` (consultați `src/mitm/cert/migration.ts`) — o
> CA MITM de încredere care poate semna un certificat derivat pentru **orice** gazdă este considerabil mai
> puternică decât vechiul certificat derivat cu SAN-uri fixe, astfel încât schimbarea nu se face niciodată în mod silențios pentru o
> instalare care acordă deja încredere certificatului.

În trecut, certificatul MITM static AgentBridge funcționa numai deoarece AgentBridge
falsifică DNS-ul pentru un set **fix** de gazde (acum unificat cu modelul de mai jos). TPROXY
interceptează gazde **arbitrare**, astfel încât listenerul său trebuie să prezinte un certificat derivat valid pentru
orice SNI solicitat de client — aceeași cerință pe care AgentBridge o are acum
pentru întregul set `MITM_TOOL_HOSTS` (9 intrări de instrumente), în loc de numai cele 4
gazde antigravity.

### CA dinamică (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` rulează o CA locală (bazată pe dependența `selfsigned`) care:

- Generează o CA cu durată lungă de viață prin `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  valabilitate de 10 ani, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  RSA pe 2048 de biți / SHA-256).
- Emite **la cerere câte un certificat derivat pentru fiecare nume de gazdă SNI** prin `issueLeafCert()` (valabilitate de 1 an,
  `subjectAltName` = gazda SNI) și memorează în cache câte un `tls.SecureContext`
  pentru fiecare nume de gazdă.
- Expune `createSNICallback()` pentru serverul care termină conexiunea TLS (consultați [§5](#5-how-decrypt-and-capture-work)).
- Poate fi construit cu un `existingCa` pentru a menține CA stabilă între reporniri
  (astfel încât depozitul de încredere să nu necesite reinstalare).

Cheia privată a CA **nu părăsește niciodată sistemul**.

### Programul de instalare în depozitul de încredere (`src/mitm/tproxy/caTrust.ts`)

Clientul interceptat trebuie să acorde încredere CA dinamice, astfel încât pornirea modului de captură
instalează certificatul CA în depozitul de încredere al sistemului de operare, într-un **slot dedicat** —
`omniroute-tproxy-ca.crt` (constanta `TPROXY_CA_CERT_NAME`) — menținut separat de
slotul certificatului MITM static (`omniroute-mitm.crt`), astfel încât cele două să nu se
suprascrie niciodată reciproc.

`installTproxyCa(caPem, sudoPassword?)` detectează directorul de ancore al distribuției
(în ordine: mai întâi cel în stil Debian) și rulează comanda corespunzătoare de reîmprospătare:

| Director de ancore                          | Comandă de reîmprospătare |
| ------------------------------------------- | ------------------------- |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates`  |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`         |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`         |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates`  |

Instalarea plasează temporar PEM-ul într-un fișier temporar, apoi execută (cu privilegii) `mkdir -p` pentru directorul de
ancore, folosește `cp` pentru a copia fișierul temporar în acesta și rulează comanda de reîmprospătare. `uninstallTproxyCa()`
elimină numai slotul dedicat (lăsând neatins certificatul MITM static) și
reîmprospătează depozitul — pe sisteme non-Linux nu efectuează nicio operație.

Toate comenzile privilegiate rulează prin `execFileWithPassword` (`src/mitm/systemCommands.ts`)
— `spawn` cu **matrice de argumente, fără shell, fără interpolare de șiruri** (Regula strictă #13).
Când procesul rulează ca root (de exemplu, pe VPS), ținta rulează direct și nu este necesară nicio parolă;
pe un desktop unde procesul nu rulează ca root, `sudoPassword` este transmisă către `sudo -S` prin stdin.

> Valoarea `sudoPassword` de pe desktop este furnizată în corpul cererii POST pentru a autoriza
> instalarea în depozitul de încredere; aceasta este ignorată complet atunci când procesul rulează ca root.

## §5 Cum funcționează decriptarea și capturarea

Fluxul de procesare (integral în `src/mitm/tproxy/`):

```
aplicație locală ──TCP/443──▶ mangle OUTPUT marchează conexiunea (fwmark)
                              ip rule → tabela de rutare locală → lo
                              mangle PREROUTING TPROXY → listener IP_TRANSPARENT (portul 8443)
                                  │  captureMode.ts: citește destinația inițială din socket.localAddress
                                  ▼
                              tlsCapture.ts:
                                1. Încheie TLS cu CLIENTUL folosind un certificat per-SNI (dynamicCert)
                                2. http.Server intern analizează textul în clar decriptat
                                3. capturare → globalTrafficBuffer.push() cu source: "tproxy"
                                   (sanitizeHeaders + maskSecret aplicate)
                                4. redirecționează, RE-criptat, către destinația inițială
                                   printr-un socket marcat pentru ocolire (connectMarked, anti-buclă)
                                  │
                                  ▼
                              server upstream inițial (api.example.com)
```

- **Terminarea TLS** (`createTlsCaptureServer`): încapsulează socketul brut interceptat
  într-un `tls.TLSSocket` pe partea de server, folosind callbackul SNI al CA-ului dinamic,
  apoi transmite fluxul decriptat către un `http.Server` intern (tehnica standard de
  terminare MITM). Durata de viață a socketurilor este limitată de `MITM_IDLE_TIMEOUT_MS`,
  astfel încât un tunel blocat să nu poată epuiza descriptorii de fișiere.
- **Capturarea** (`handleDecryptedRequest`): introduce un `InterceptedRequest` cu
  `source: "tproxy"`, starea inițială `"in-flight"`, antetele procesate prin
  `sanitizeHeaders()` și corpurile prin `maskSecret()` înainte ca acestea să intre în
  buffer. Intrarea este apoi actualizată cu răspunsul, dimensiunile și latența.
- **Redirecționarea recriptată** (`createForward` / `realForward`): criptează din nou
  traficul către destinația inițială. `rejectUnauthorized` are implicit valoarea
  **`true`** (securizat în mod implicit) — certificatul serverului upstream este
  verificat în raport cu SNI/Host solicitat de client, astfel încât proxy-ul respinge
  exact ceea ce ar respinge clientul inițial.

### Anti-buclă (SO_MARK)

Deoarece regulile marchează conexiunile locale de ieșire noi, redirecționarea
recriptată a proxy-ului **însuși** ar fi în mod normal interceptată din nou — o
buclă infinită. Calea de redirecționare previne acest lucru folosind un marcaj de
ocolire al socketului (**SO_MARK**):

- `realForward` deschide socketul upstream prin `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  — `DEFAULT_BYPASS_MARK = 0x539` — care setează **SO_MARK** **înainte de** `connect()`,
  astfel încât SYN-ul redirecționării poartă marcajul de ocolire.
- Regula `mangle OUTPUT` exclude conexiunile care poartă deja marcajul de ocolire
  (`-m mark ! --mark <bypassMark>`), astfel încât redirecționarea proxy-ului **nu**
  este marcată din nou și nu reintră în TPROXY.

> Notă de implementare: socketul marcat pentru ocolire trebuie instalat în
> `createConnection` al agentului (`https.request({ createConnection })` este ignorat
> fără notificare atunci când este prezent un agent); în caz contrar, redirecționarea
> ar deschide un socket nemarcat, iar bucla ar reapărea. Aceasta a fost remedierea
> anti-buclă validată e2e.

## §6 Securitate

| Control                                   | Detaliu                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API disponibil doar pe loopback**       | `/api/tools/agent-bridge/tproxy` este acoperit de prefixul `/api/tools/agent-bridge/` din `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Restricția la loopback este aplicată **înainte de** autentificare (Regulile stricte #15 + #17) — un JWT expus printr-un tunel nu poate porni capturarea TPROXY, care aplică reguli `iptables` și instalează o CA în depozitul de încredere prin procese copil. |
| **Slot CA dedicat**                       | CA-ul dinamic este instalat în `omniroute-tproxy-ca.crt`, fără a suprascrie vreodată certificatul MITM static.                                                                                                                                                                                                                                                                                                         |
| **Cheia CA nu părăsește niciodată gazda** | `DynamicCertStore` păstrează cheia CA în memorie; aceasta nu este exportată.                                                                                                                                                                                                                                                                                                                                           |
| **Mascarea secretelor**                   | `maskSecret()` pentru corpurile cererilor/răspunsurilor și `sanitizeHeaders()` pentru anteturi rulează **înainte de** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                    |
| **Fără interpolare în shell**             | Toate comenzile `iptables`/`ip`/pentru depozitul de încredere rulează prin `execFile`/`execFileWithPassword`, cu tablouri de argumente (Regula strictă #13).                                                                                                                                                                                                                                                           |
| **Verificarea certificatului upstream**   | Redirecționarea recriptată verifică în mod implicit certificatul upstream (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                                                |
| **Igienizarea erorilor**                  | Răspunsurile de eroare ale rutei sunt procesate prin `sanitizeErrorMessage()` (Regula strictă #12).                                                                                                                                                                                                                                                                                                                    |

**CA-ul MITM oferă o capabilitate puternică.** O CA considerată de încredere de sistemul de operare și care poate semna pentru orice
gazdă înseamnă că orice interceptează OmniRoute poate fi decriptat. Aceasta este disponibilă numai prin
modul explicit de capturare TPROXY, disponibil doar local, dezactivat implicit, iar intrarea din depozitul de încredere
este eliminată atunci când opriți modul.

## §7 Aplicarea / anularea tranzacțională a firewallului

O oprire neașteptată nu trebuie să lase niciodată în urmă o regulă `mangle` sau o rută învechită. Constructorul de comenzi
(`src/mitm/tproxy/commands.ts`) și executorul (`src/mitm/tproxy/setup.ts`) garantează că
**anularea este inversul exact al aplicării, în ordine inversă**.

`applyTproxy(cfg)` execută comenzile de aplicare în ordine; la **orice** eșec, execută o
operațiune completă `revertTproxy(cfg)` în regim best-effort și retransmite eroarea — astfel, firewallul este fie
aplicat complet, fie anulat complet, niciodată aplicat parțial. `revertTproxy(cfg)` execută
comenzile inverse în ordine inversă și ignoră eșecurile (este idempotent — poate fi apelat
necondiționat în siguranță, de exemplu din operațiunea de curățare AgentBridge `repairMitm()`).

`validateTproxyConfig(cfg)` se execută înaintea oricărei comenzi: porturile trebuie să fie în intervalul `1–65535`,
`mark`/`routeTable`/`bypassMark` trebuie să fie numere întregi pozitive, iar `bypassMark` trebuie
să fie diferit de `mark` (protecție împotriva buclelor).

### Comenzi de aplicare (în ordine)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Anularea le șterge în ordine inversă: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Rețeta este bazată pe **OUTPUT** deoarece scenariul de utilizare MITM vizează traficul de ieșire
> _local_ (aplicații de pe aceeași gazdă), pe care TPROXY doar în `PREROUTING` nu îl
> vede — `PREROUTING` vede doar traficul redirecționat. Lanțul `OUTPUT` marchează noile
> conexiuni locale, regula `ip rule` le redirecționează către livrarea locală (`lo`), iar
> `PREROUTING` le atribuie apoi listenerului transparent.

## §8 Configurare

Cererea de pornire (`POST /api/tools/agent-bridge/tproxy`) acceptă următoarele
câmpuri, validate de `StartTproxyBodySchema` (`tproxy/route.ts`). Toate sunt opționale
și, dacă lipsesc, sunt utilizate valorile lor implicite:

| Câmp             | Tip                | Implicit | Note                                                                                                                                                            |
| ---------------- | ------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`    | Portul TCP de destinație care trebuie interceptat transparent                                                                                                   |
| **mark**         | int (≥1)           | `0x2333` | Marcajul firewall setat în `OUTPUT`, utilizat pentru potrivire de `ip rule` + `PREROUTING`                                                                      |
| **onPort**       | int (1–65535)      | `8443`   | Portul pe care se leagă listenerul transparent (**IP_TRANSPARENT**)                                                                                             |
| **routeTable**   | int (≥1)           | `233`    | ID-ul tabelului de rutare bazată pe politici care conține ruta `local 0.0.0.0/0`                                                                                |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`  | Marcajul de ocolire al socketului (**SO_MARK**) pe care proxy-ul îl setează pe propriile conexiuni upstream; exclus din `OUTPUT` (protecție împotriva buclelor) |
| **sudoPassword** | string             | —        | Numai pentru sisteme desktop non-root: autorizează instalarea în depozitul de încredere; ignorat când se rulează ca root                                        |

Nu există **variabile de mediu** pentru TPROXY — întreaga configurare se face prin
corpul cererii POST sau prin valorile implicite de mai sus.

## §9 Activarea din Inspectorul de trafic

1. Deschideți **Inspectorul de trafic** (`/dashboard/tools/traffic-inspector`).
2. În bara de instrumente pentru modurile de capturare, găsiți butonul **„Decriptare TPROXY”** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Dacă este **dezactivat**, cu descrierea „Decriptarea TPROXY necesită Linux + root +
     modulul suplimentar nativ”, modulul suplimentar nativ nu este disponibil pe această gazdă (sistemul
     nu este Linux, nu există un lanț de instrumente sau modulul suplimentar nu a fost compilat). Consultați [§2](#2-requirements) și [§3](#3-the-native-ip_transparent-addon).
3. Faceți clic pe buton. Acesta apelează `POST /api/tools/agent-bridge/tproxy` prin
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), care:
   generează CA-ul dinamic, deschide ascultătorul transparent, aplică regulile de firewall
   și instalează CA-ul în magazinul de încredere al sistemului de operare.
4. Când funcționează, comutatorul devine portocaliu și afișează numărul actual de interceptări
   (`· <interceptCount>`). Solicitările interceptate apar în lista de solicitări cu
   `source: "tproxy"`.
5. Faceți clic din nou pentru oprire — `DELETE /api/tools/agent-bridge/tproxy` prin
   `stopTproxyCaptureMode()` închide ascultătorul, dezinstalează CA-ul și revine asupra
   regulilor de firewall.

Starea modului de capturare (în execuție / disponibil / număr de interceptări / portul ascultătorului) provine
de la `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` din
`src/mitm/tproxy/captureManager.ts`). Poate rula o singură sesiune TPROXY la un moment dat —
încercarea de a porni o a doua sesiune este respinsă cu mesajul „Modul de capturare TPROXY rulează deja”.

## §10 Depanare

### Comutatorul este dezactivat

Modulul suplimentar nativ nu poate fi încărcat. Confirmați că utilizați Linux, că ați compilat modulul suplimentar
(`npm run build:native:tproxy`) și că procesul poate încărca `transparent.node`.
`isTransparentSocketAvailable()` controlează comutatorul; `GET /api/tools/agent-bridge/tproxy`
returnează `available: false` când modulul suplimentar lipsește.

### Nu este capturat nimic

- Confirmați că procesul interceptat se conectează efectiv la `dport` configurat
  (implicit `443`).
- Confirmați că procesul consideră CA-ul dinamic ca fiind de încredere. CA-ul este instalat sub numele
  `omniroute-tproxy-ca.crt`; aplicațiile cu propriul magazin de încredere (Firefox/Chrome NSS)
  pot necesita adăugarea certificatului și în acel magazin.
- Rulați testul automat **Diagnosticare** AgentBridge (consultați
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) pentru verificarea încrederii certificatului și a
  stării serverului.

### Reguli de firewall rămase după o blocare

`revertTproxy()` este inversul exact al operației de aplicare și este idempotent. Oprirea
modului revine asupra regulilor; dacă OmniRoute a fost închis forțat în timpul unei sesiuni, utilizați acțiunea
**Reparare** AgentBridge (`POST /api/tools/agent-bridge/repair`) pentru a anula starea de sistem
rămasă neeliminată (falsificare DNS, CA rădăcină, proxy de sistem). Regulile TPROXY `mangle` și ruta sunt, de asemenea,
eliminate automat la repornire.

### Buclă infinită / proxy-ul își interceptează propria redirecționare

Acesta este cazul prevenirii buclelor. Confirmați că `bypassMark` diferă de `mark` (validarea
impune acest lucru) și că redirecționarea utilizează `connectMarked` (așa cum se întâmplă în `realForward`).
Consultați [§5 Prevenirea buclelor](#anti-loop-so_mark).
