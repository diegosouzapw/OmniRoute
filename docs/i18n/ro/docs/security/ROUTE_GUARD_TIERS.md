## Prezentare generală

Toate rutele API de administrare OmniRoute sunt clasificate într-unul dintre cele trei niveluri de
protecție. Clasificarea este statică, definită în `src/server/authz/routeGuard.ts`
și evaluată înainte de executarea oricărei alte ramuri de autentificare.

## Niveluri

### Nivelul 1 — LOCAL_ONLY

**Aplicat prin:** `isLocalOnlyPath(path)` → verificarea gazdei loopback  
**Ocolire:** În mod implicit, niciuna. Există o excepție restrânsă pentru căile din
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` atunci când cererea conține o cheie
API validă cu domeniul de autorizare `manage` (consultați [Excepția pentru domeniul de autorizare manage](#manage-scope-carve-out)).

Aceste rute lansează procese copil sau execută cod în timpul rulării. Expunerea lor
la trafic care nu provine din interfața loopback i-ar permite unui atacator care a obținut un JWT valid (de exemplu,
printr-un tunel Cloudflared/Ngrok) să declanșeze lansarea de procese — o clasă cunoscută de
vulnerabilități CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ce reprezintă GHSA-fhh6-4qxv-rpqj (clasa de atac):** un server de administrare/agent
expune un punct final care lansează un subproces (`npm install`, `node`, un browser,
un proxy, `git`, `tar`, …). Dacă acel punct final este accesibil din afara gazdei — deoarece
operatorul a plasat OmniRoute în spatele unui tunel nginx/Cloudflare/Tailscale și s-a
scurs un JWT sau autentificarea a fost configurată greșit — atacatorul transformă „apelarea unui API” în „executarea unei
comenzi pe gazdă” (execuție de cod de la distanță). OmniRoute previne acest lucru impunând
**necondiționat verificarea gazdei loopback, înaintea oricărei verificări de autentificare**, pentru fiecare
rută capabilă să lanseze procese: un token compromis transmis printr-un tunel tot nu poate ajunge la funcția de lansare.

**Setul LOCAL_ONLY complet.** Sursa oficială este reprezentată de
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` din
`src/server/authz/routeGuard.ts`; tabelul de mai jos reflectă starea actuală. Verificarea
`check-route-guard-membership` enumeră fiecare fișier `route.ts` din
prefixurile capabile să lanseze procese și determină eșuarea CI dacă vreunul nu este clasificat ca fiind exclusiv local.

**Răspuns în caz de încălcare:** `403 LOCAL_ONLY`

#### Excepție pentru domeniul de aplicare manage

Un subset de căi LOCAL_ONLY POATE fi accesat și din afara interfeței loopback dacă și
numai dacă cererea conține un antet `Authorization: Bearer <api-key>` ale cărui
metadate includ domeniul de aplicare `manage` (sau `admin`). Excepția este activată
explicit pentru fiecare cale prin `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, astfel încât
comportamentul implicit pentru orice cale LOCAL_ONLY nouă să rămână strict limitat la loopback. Cererile
neautentificate și cererile cu chei fără domeniul de aplicare manage sunt în continuare respinse cu
`403 LOCAL_ONLY`.

În prezent, singurul prefix pentru care se poate aplica excepția este `/api/mcp/`. `/api/cli-tools/runtime/` și
`/api/services/` sunt excluse intenționat, deoarece pot iniția subprocese arbitrare
(`npm install`, `node`), adică exact clasa de vulnerabilități CVE pe care
nivelul LOCAL_ONLY este conceput să o prevină.

**#7895 — domeniul de aplicare restrâns `mcp:connect`:** excepția pentru `/api/mcp/` acceptă, DE ASEMENEA,
o cheie Bearer care deține domeniul de aplicare restrâns `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), verificat prin
`hasMcpConnectOrManageScope()` în `src/server/authz/policies/management.ts`.
Acesta este limitat EXCLUSIV la `/api/mcp/` — `mcp:connect` nu acordă nimic pentru nicio altă
rută de administrare (inclusiv pentru orice alt prefix de excepție LOCAL_ONLY, dacă va fi
adăugat vreodată) și este exclus în mod intenționat din
`MANAGEMENT_API_KEY_SCOPES`. O cheie care deține `manage`/`admin` beneficiază în continuare de
excepție exact ca înainte; `mcp:connect` este o alternativă cu privilegii mai reduse
pentru apelanții MCP exclusiv de la distanță, care nu ar trebui să aibă nevoie de acces extins de administrare.

| Cerere                                                 | Cale                       | Rezultat                       |
| ------------------------------------------------------ | -------------------------- | ------------------------------ |
| Din afara loopback, fără Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Din afara loopback, Bearer cu domeniul `manage`        | `/api/mcp/*`               | Permis                         |
| Din afara loopback, Bearer cu domeniul `mcp:connect`   | `/api/mcp/*`               | Permis                         |
| Din afara loopback, Bearer fără `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Din afara loopback, Bearer cu domeniul `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Din afara loopback, Bearer cu domeniul `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Loopback, cu orice/fără Bearer                         | orice cale LOCAL_ONLY      | Permis (controlul este trecut) |

#### Îndrumări pentru operatori și auditare

Dacă rulați OmniRoute în spatele unui proxy invers sau al unui tunel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), verificarea loopback protejează în continuare rutele de mai sus
care pot iniția procese — o cerere a cărei adresă de client nu este loopback este respinsă cu
`403 LOCAL_ONLY` **înainte de rularea autentificării**, astfel încât un JWT compromis nu poate declanșa inițierea unui proces. Rămân
două responsabilități pentru operatori:

- **Nu „remediați” o eroare 403 falsificând IP-ul clientului ca fiind loopback.** Setarea
  `X-Forwarded-For: 127.0.0.1` sau utilizarea unui proxy care rescrie adresa-sursă ca
  loopback redeschide exact clasa de vulnerabilități RCE pe care acest nivel o elimină. Expuneți
  panoul de control/API-ul prin proxy — niciodată rutele care pot iniția procese.
- **Mențineți la minimum excepția pentru domeniul manage.** Numai `/api/mcp/` permite excepția și
  numai cu o cheie API având domeniul `manage`. Elementele `SPAWN_CAPABLE_PREFIXES` nu pot fi
  adăugate niciodată în lista de excepții — schema zod le respinge, iar
  `isLocalOnlyBypassableByManageScope` le refuză în timpul rulării (apărare în profunzime),
  acesta fiind sensul expresiei „nu poate permite excepția” din panoul de control. Rutele cu segmente
  dinamice și căi statice care pot iniția procese din `/api/providers/` (de exemplu, `/login`,
  `/refresh-cursor`) sunt acoperite de mecanismul complementar bazat pe expresii regulate `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` din
  `src/shared/constants/spawnCapablePrefixes.ts`, nu de matricea simplă
  `SPAWN_CAPABLE_PREFIXES` — matricea simplă ar trebui să acopere
  întregul prefix `/api/providers/` pentru a le identifica, extinzând excesiv un arbore de rute
  pe care panourile de control de la distanță îl utilizează în mod legitim pentru operațiuni CRUD asupra furnizorilor.

**Auditarea accesului** — pentru a verifica dacă niciun sistem din afara gazdei nu accesează aceste rute:

- Deschideți **Inventarul de autorizare** la `/dashboard/settings/security`: acesta afișează
  lista activă de prefixe LOCAL_ONLY, prefixele care pot fi ocolite și setul cu
  posibilitatea de a lansa procese („nu poate fi configurat pentru ocolire”), stabilit la compilare.
- Căutați cu grep în jurnalele proxy-ului invers / de acces prefixele de mai sus asociate cu o
  adresă de client care nu este loopback. Orice astfel de acces care a returnat `200` în loc de
  `403 LOCAL_ONLY` înseamnă că proxy-ul maschează IP-ul real al clientului — remediați proxy-ul.
- Un `403 LOCAL_ONLY` în jurnalele OmniRoute pentru una dintre aceste căi indică faptul că mecanismul
  de protecție funcționează conform intenției, nu o eroare care trebuie suprimată.

### Nivelul 2 — ALWAYS_PROTECTED

**Aplicat de:** `isAlwaysProtectedPath(path)` → omite ocolirea `requireLogin=false`
**Ocolire:** Niciuna când `requireLogin=false`; JWT este necesar întotdeauna

Aceste rute sunt distructive sau ireversibile. Permiterea lor într-o instalare „fără parolă”
ar însemna că oricine din aceeași rețea LAN ar putea șterge baza de date sau opri
procesul serverului.

| Cale                                      | Motiv                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------ |
| `/api/shutdown`                           | Oprește procesul serverului                                              |
| `/api/settings/database`                  | Exportul, importul și ștergerea bazei de date                            |
| `/api/db-backups`                         | Acces la arhiva completă de backup a bazei de date                       |
| `/api/settings/export-json`               | Exportă întregul bloc de setări (inclusiv secretele)                     |
| `/api/settings/import-json`               | Înlocuiește întregul bloc de setări                                      |
| `/api/providers/health-autopilot/actions` | Execută acțiuni de remediere autopilot                                   |
| `/api/settings/obsidian`                  | Generează credențiale WebDAV reutilizabile pentru orice rădăcină de seif |

**Răspuns în caz de încălcare:** `401 Authentication required`

`/api/settings/obsidian` include ruta sa copil `/webdav`: `POST` direcționează serviciul de fișiere WebDAV —
furnizat de stratul Node personalizat înainte de Next.js, în afara acestui flux — către o rădăcină
aleasă de apelant și returnează credențiale Basic nou-generate, `DELETE` le rotește, iar ruta `POST`
părinte stochează tokenul API REST Obsidian. GHSA-62vw a mascat doar dezvăluirea parolei prin `GET`;
emiterea se afla în continuare la nivelul care permitea accesul în caz de eșec (GHSA-7pq4-8pvv-rx7r).
În plus, `enableObsidianVaultSync()` refuză un seif care este directorul de date, se află în interiorul
acestuia sau îl conține.

### Inițializarea unei instalări noi este disponibilă numai prin loopback — în funcție de peer-ul real, nu de `Host`

Când nu este configurată nicio parolă de administrare (și nu există `INITIAL_PASSWORD`),
`isAuthRequired()` din `src/shared/utils/apiAuth.ts` menține inițializarea anonimă disponibilă
**numai pentru peer-ii loopback**. Caracterul loopback este determinat din semnalele de încredere
ale peer-ului, în această ordine: peer-ul TCP real marcat cu token (`PEER_IP_HEADER` +
`VIA_PROXY_HEADER`, ceea ce vede politica), verdictul `AUTHZ_HEADER_PEER_LOCALITY` al propriului
flux (ceea ce văd gestionarii de rute, considerat de încredere numai cât timp este setat
`OMNIROUTE_PEER_STAMP_TOKEN`) sau peer-ul real al socketului pentru apelanții direcți. `Host` /
`nextUrl.hostname` nu sunt consultate niciodată, iar setarea primei parole
(`POST /api/settings/require-login`) este supusă aceleiași restricții, în loc să fie disponibilă
tuturor peer-ilor din rețea (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmite explicit propriul
verdict `peerContext`, astfel încât anteturile cererii ORIGINALE (anterioare eliminării) să nu îl
determine niciodată.

### Nivelul 3 — MANAGEMENT (implicit)

Toate celelalte rute de administrare. Autentificarea este obligatorie, cu excepția cazului în care
este configurat `requireLogin=false`. Tokenurile CLI pot autentifica aceste rute (loopback + HMAC valid).

## Ordinea evaluării

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → continuă evaluarea
     → non-loopback, Bearer cu scope-ul manage
        ȘI isLocalOnlyBypassableByManageScope    → permite (management_key)
     → în caz contrar                            → respinge cu 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → permite (system)
  3. hasValidCliToken(headers)?
     → permite (cli) [loopback + verificare HMAC cu timingSafeEqual]
  4. isAlwaysProtectedPath(path) sau requireLogin=true?
     → isDashboardSessionAuthenticated?
        → permite (dashboard_session)
     → Bearer cu scope-ul manage pe o cale care nu permite ocolirea?
        → permite (management_key)
     → respinge cu 401/403
  5. requireLogin=false?
     → permite (anonymous)
```

Ramura cu scope-ul manage de la pasul 1 este singura cale autentificată care poate satisface o
rută LOCAL_ONLY; modul de eșec al backendului de autentificare returnează 503 (nu 403), astfel încât o
bază de date expirată să nu retrogradeze în mod silențios la „refuză”.

## Adăugarea unei rute noi capabile să lanseze procese

1. Adăugați prefixul căii în `LOCAL_ONLY_API_PREFIXES` din
   `src/server/authz/routeGuard.ts`
2. Adăugați un test în `tests/unit/authz/routeGuard.test.ts` care să verifice că
   `isLocalOnlyPath()` returnează true pentru noul prefix
3. **Nu omiteți niciodată acest pas** — consultați Regula strictă #15 din `CLAUDE.md`
4. Decideți: această rută trebuie inclusă ȘI în `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Răspunsul implicit este **nu**. Includeți-o explicit numai atunci când ruta poate fi expusă în
   siguranță unui deținător al scope-ului manage (adică NU lansează cod arbitrar controlat de utilizator).

## Adăugarea unei căi care permite ocolirea prin scope-ul manage

1. Confirmați că ruta nu execută cod sau comenzi furnizate de utilizator. Dacă
   o face, opriți-vă — această excepție nu este instrumentul potrivit.
2. Adăugați prefixul în `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` din
   `src/server/authz/routeGuard.ts`
3. Adăugați acoperire în `tests/unit/authz/management-policy.test.ts` pentru toate cele patru
   tipuri de cereri: fără Bearer (403), Bearer cu scope-ul manage (permite), Bearer fără scope-ul manage
   (403) și regresia specifică prefixului, care verifică faptul că `/api/cli-tools/runtime/*` rămâne
   strict limitat la loopback chiar și cu un Bearer cu scope-ul manage.

## Documentarea nivelurilor de securitate în OpenAPI

Când adăugați o rută nouă în `docs/openapi.yaml`, aplicați extensia corespunzătoare
a furnizorului dacă ruta este clasificată de `routeGuard.ts`:

| Clasificare în routeGuard.ts               | Adnotare YAML                     | Aplicare                                                   |
| ------------------------------------------ | --------------------------------- | ---------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`           | Blocat necondiționat pentru conexiunile non-loopback       |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`        | Autentificare obligatorie chiar și cu `requireLogin=false` |
| Rută internă de administrare/depanare      | `x-internal: true`                | Ascunsă implicit din /dashboard/api-endpoints              |
| Niciuna (publică / autentificare standard) | (nu este necesară nicio adnotare) | Acces standard controlat de `requireLogin`                 |

### Validare

Două scripturi asigură consecvența dintre adnotările YAML și `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — eșuează dacă acoperirea este < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — eșuează dacă adnotările `x-loopback-only` sau
  `x-always-protected` diferă de constantele definite la compilare

Ambele scripturi rulează în hook-ul pre-commit și în CI.

### Regula privind rezultatele fals pozitive

Dacă `x-always-protected` sau `x-loopback-only` este adnotat pe o rută care NU se află în
constanta din `routeGuard.ts`, scriptul de acoperire eșuează. Soluția este întotdeauna alinierea
YAML la ceea ce aplică efectiv `routeGuard.ts` — nu adăugarea rutelor în `routeGuard.ts`
fără implementarea corespunzătoare a logicii de aplicare.
