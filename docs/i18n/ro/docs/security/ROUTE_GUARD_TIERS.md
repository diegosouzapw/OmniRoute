## Prezentare generală

Toate rutele API de administrare OmniRoute sunt clasificate într-unul dintre cele trei niveluri de
protecție. Clasificarea este statică, definită în `src/server/authz/routeGuard.ts`
și evaluată înainte de executarea oricărei alte ramuri de autentificare.

## Niveluri

### Nivelul 1 — LOCAL_ONLY

**Aplicat prin:** `isLocalOnlyPath(path)` → verificarea gazdei loopback  
**Ocolire:** Niciuna în mod implicit. Excepție restrânsă pentru căile din
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` atunci când cererea conține o cheie
API validă cu domeniul de aplicare `manage` (consultați [Excepția pentru domeniul de aplicare manage](#manage-scope-carve-out)).

Aceste rute pornesc procese copil sau execută cod în timpul rulării. Expunerea lor
la trafic non-loopback ar permite unui atacator care a obținut un JWT valid (de ex.,
printr-un tunel Cloudflared/Ngrok) să declanșeze pornirea proceselor — o clasă
cunoscută de vulnerabilități CVE
([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ce este GHSA-fhh6-4qxv-rpqj (clasa de atac):** un server de management/agent
expune un endpoint care lansează un subproces (`npm install`, `node`, un browser,
un proxy, `git`, `tar`, …). Dacă acel endpoint este accesibil din afara gazdei —
deoarece operatorul a plasat OmniRoute în spatele unui tunel nginx/Cloudflare/Tailscale și s-a
scurs un JWT sau autentificarea a fost configurată greșit — atacatorul transformă „apelarea unui API” în
„rularea unei comenzi pe gazdă” (execuție de cod de la distanță). OmniRoute împiedică acest lucru prin aplicarea
**necondiționată a unei verificări a gazdei loopback, înaintea oricărei verificări de autentificare**, pentru fiecare
rută capabilă să pornească procese: un token compromis printr-un tunel tot nu poate accesa mecanismul de pornire.

**Setul LOCAL_ONLY complet.** Sursa oficială este reprezentată de
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` din
`src/server/authz/routeGuard.ts`; tabelul de mai jos reflectă starea actuală. Mecanismul
`check-route-guard-membership` enumeră fiecare `route.ts` din prefixele
capabile să pornească procese și face ca CI să eșueze dacă vreunul nu este clasificat drept accesibil numai local.

**Răspuns în caz de încălcare:** `403 LOCAL_ONLY`

#### Excepția pentru domeniul manage

Un subset de căi LOCAL_ONLY POATE fi accesat și din afara interfeței loopback dacă și
numai dacă solicitarea conține un antet `Authorization: Bearer <api-key>` ale cărui
metadate includ domeniul `manage` (sau `admin`). Excepția este activată
explicit pentru fiecare cale prin `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, astfel încât
comportamentul implicit pentru orice cale LOCAL_ONLY nouă să rămână strict limitat la loopback. Solicitările
neautentificate și solicitările cu chei fără domeniul manage sunt respinse în continuare cu
`403 LOCAL_ONLY`.

În prezent, singurul prefix pentru care este permisă excepția este `/api/mcp/`. `/api/cli-tools/runtime/` și
`/api/services/` sunt excluse intenționat, deoarece pot porni
subprocese arbitrare (`npm install`, `node`), ceea ce reprezintă exact clasa de vulnerabilități CVE pe care
nivelul LOCAL_ONLY este conceput să o prevină.

**#7895 — domeniul restrâns `mcp:connect`:** excepția pentru `/api/mcp/` acceptă ȘI
o cheie Bearer care deține domeniul restrâns `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), verificat prin
`hasMcpConnectOrManageScope()` în `src/server/authz/policies/management.ts`.
Acesta este limitat EXCLUSIV la `/api/mcp/` — `mcp:connect` nu acordă nimic pe nicio altă
rută de administrare (inclusiv pe orice alt prefix de exceptare LOCAL_ONLY, dacă va fi
adăugat vreodată) și este exclus în mod deliberat din
`MANAGEMENT_API_KEY_SCOPES`. O cheie care deține `manage`/`admin` beneficiază în continuare de
excepție exact ca înainte; `mcp:connect` este o alternativă cu privilegii mai reduse
pentru apelanții MCP exclusiv de la distanță, care nu ar trebui să aibă nevoie de acces extins de administrare.

| Solicitare                                             | Cale                       | Rezultat                   |
| ------------------------------------------------------ | -------------------------- | -------------------------- |
| Din afara loopback, fără Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY             |
| Din afara loopback, Bearer cu domeniul `manage`        | `/api/mcp/*`               | Permis                     |
| Din afara loopback, Bearer cu domeniul `mcp:connect`   | `/api/mcp/*`               | Permis                     |
| Din afara loopback, Bearer fără `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY             |
| Din afara loopback, Bearer cu domeniul `mcp:connect`   | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY             |
| Din afara loopback, Bearer cu domeniul `manage`        | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY             |
| Loopback, cu orice Bearer/fără Bearer                  | orice rută LOCAL_ONLY      | Permis (verificarea trece) |

#### Îndrumări pentru operatori și auditare

Dacă rulați OmniRoute în spatele unui proxy invers sau al unui tunel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), verificarea loopback protejează în continuare rutele de mai sus
care pot porni procese — o solicitare a cărei adresă de client nu este loopback este respinsă cu
`403 LOCAL_ONLY` **înainte de executarea autentificării**, astfel încât un JWT compromis nu poate declanșa un proces. Rămân
două responsabilități pentru operator:

- **Nu „remediați” o eroare 403 falsificând IP-ul clientului ca fiind loopback.** Setarea
  `X-Forwarded-For: 127.0.0.1` sau utilizarea unui proxy care rescrie adresa sursă ca
  loopback redeschide exact clasa de vulnerabilități RCE pe care acest nivel o elimină. Expuneți
  panoul de control/API-ul prin proxy — niciodată rutele care pot porni procese.
- **Mențineți la minimum excepția pentru domeniul manage.** Excepția este permisă numai pentru `/api/mcp/` și
  numai cu o cheie API având domeniul `manage`. Prefixele `SPAWN_CAPABLE_PREFIXES` nu pot fi
  adăugate niciodată în lista de excepții — schema zod le respinge, iar
  `isLocalOnlyBypassableByManageScope` le refuză în timpul execuției (apărare în profunzime),
  acesta fiind sensul expresiei „nu poate permite excepții” din panoul de control. Rutele cu segmente
  dinamice și cele cu căi statice care pot porni procese, aflate sub `/api/providers/` (de exemplu, `/login`,
  `/refresh-cursor`), sunt acoperite de mecanismul complementar bazat pe expresii regulate `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` din
  `src/shared/constants/spawnCapablePrefixes.ts`, nu de matricea simplă
  `SPAWN_CAPABLE_PREFIXES` — matricea simplă ar trebui să acopere întregul prefix
  `/api/providers/` pentru a le detecta, extinzând excesiv un arbore de rute
  pe care panourile de control de la distanță îl utilizează în mod legitim pentru operațiunile CRUD asupra furnizorilor.

**Auditarea accesului** — pentru a verifica dacă niciun acces din afara gazdei nu ajunge la aceste rute:

- Deschideți **Inventarul de autorizare** la `/dashboard/settings/security`: acesta afișează lista
  activă de prefixuri LOCAL_ONLY, prefixurile pentru care protecția poate fi ocolită și setul
  cu posibilitatea de lansare stabilit la compilare („nu poate deveni ocolibil”).
- Căutați cu grep în jurnalele proxy-ului invers / de acces prefixurile de mai sus asociate cu
  o adresă de client care nu este loopback. Orice astfel de accesare care a returnat `200` în loc de
  `403 LOCAL_ONLY` înseamnă că proxy-ul maschează IP-ul real al clientului — remediați proxy-ul.
- Un `403 LOCAL_ONLY` în jurnalele OmniRoute pentru una dintre aceste căi indică faptul că protecția
  funcționează conform intenției, nu o eroare care trebuie suprimată.

### Nivelul 2 — ALWAYS_PROTECTED

**Aplicat de:** `isAlwaysProtectedPath(path)` → omite ocolirea `requireLogin=false`
**Ocolire:** Niciuna când `requireLogin=false`; JWT este necesar întotdeauna

Aceste rute sunt distructive sau ireversibile. Permiterea lor într-o instalare „fără parolă”
ar însemna că oricine din aceeași rețea LAN ar putea șterge baza de date sau opri procesul
serverului.

| Cale                                      | Motiv                                                                |
| ----------------------------------------- | -------------------------------------------------------------------- |
| `/api/shutdown`                           | Oprește procesul serverului                                          |
| `/api/settings/database`                  | Exportarea, importarea și ștergerea bazei de date                    |
| `/api/db-backups`                         | Acces la arhiva completă de backup a bazei de date                   |
| `/api/settings/export-json`               | Exportă întregul blob de setări (inclusiv secretele)                 |
| `/api/settings/import-json`               | Înlocuiește întregul blob de setări                                  |
| `/api/providers/health-autopilot/actions` | Execută acțiuni de remediere ale pilotului automat                   |
| `/api/settings/obsidian`                  | Emite credențiale WebDAV reutilizabile pentru orice rădăcină de seif |

**Răspuns în caz de încălcare:** `401 Authentication required`

`/api/settings/obsidian` include ruta sa copil `/webdav`: `POST` direcționează serviciul de fișiere WebDAV —
furnizat de stratul Node personalizat înainte de Next.js, în afara acestei conducte — către o rădăcină
aleasă de apelant și returnează credențiale Basic nou emise, `DELETE` le rotește, iar ruta părinte `POST`
stochează tokenul API REST Obsidian. GHSA-62vw a mascat doar dezvăluirea parolei prin `GET`; emiterea
se afla în continuare pe nivelul cu acces permis în caz de eroare (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()`
refuză în plus un seif care este directorul de date, se află în acesta sau îl conține.

### Inițializarea unei instalări noi este disponibilă numai prin loopback — pe baza perechii reale, nu a antetului `Host`

Când nu este configurată nicio parolă de administrare (și nu există `INITIAL_PASSWORD`), `isAuthRequired()` din
`src/shared/utils/apiAuth.ts` menține inițializarea anonimă deschisă **numai pentru perechile loopback**.
Caracterul loopback este determinat din semnalele de încredere ale perechii, în ordine: perechea TCP reală
marcată cu token (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, ceea ce vede politica), verdictul propriu al
conductei `AUTHZ_HEADER_PEER_LOCALITY` (ceea ce văd gestionarii de rute, considerat de încredere numai cât timp
este setat `OMNIROUTE_PEER_STAMP_TOKEN`) sau o pereche reală de socket pentru apelanții direcți. `Host` /
`nextUrl.hostname` nu sunt consultate niciodată, iar scrierea primei parole
(`POST /api/settings/require-login`) este supusă aceleiași restricții, în loc să fie deschisă tuturor
perechilor din rețea (GHSA-7pq4-8pvv-rx7r). `managementPolicy` transmite explicit propriul verdict
`peerContext`, astfel încât anteturile cererii ORIGINALE (înainte de eliminare) să nu îl determine niciodată.

### Nivelul 3 — MANAGEMENT (implicit)

Toate celelalte rute de administrare. Autentificarea este necesară dacă nu este
configurat `requireLogin=false`. Tokenurile CLI pot autentifica aceste rute (loopback + HMAC valid).

## Ordinea evaluării

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → continuă evaluarea
     → non-loopback, Bearer cu scope-ul manage
        ȘI isLocalOnlyBypassableByManageScope    → permite (management_key)
     → în caz contrar                            → respinge cu 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → permite (system)
  3. hasValidCliToken(headers)?
     → permite (cli) [loopback + verificare HMAC cu timingSafeEqual]
  4. isAlwaysProtectedPath(path) sau requireLogin=true?
     → isDashboardSessionAuthenticated?
        → permite (dashboard_session)
     → Bearer cu scope-ul manage pe o cale care nu permite ocolirea?
        → permite (management_key)
     → respinge cu 401/403
  5. requireLogin=false?
     → permite (anonymous)
```

Ramura cu scope-ul manage de la pasul 1 este singura cale autentificată care poate satisface o
rută LOCAL_ONLY; modul de eșec al backendului de autentificare returnează 503 (nu 403), astfel încât o
bază de date expirată să nu retrogradeze în mod silențios la „refuză”.

## Adăugarea unei rute noi capabile să lanseze procese

1. Adăugați prefixul căii în `LOCAL_ONLY_API_PREFIXES` din
   `src/server/authz/routeGuard.ts`
2. Adăugați un test în `tests/unit/authz/routeGuard.test.ts` care să verifice că
   `isLocalOnlyPath()` returnează true pentru noul prefix
3. **Nu omiteți niciodată acest pas** — consultați Regula strictă #15 din `CLAUDE.md`
4. Decideți: această rută trebuie inclusă ȘI în `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Răspunsul implicit este **nu**. Includeți-o explicit numai atunci când ruta poate fi expusă în
   siguranță unui deținător al scope-ului manage (adică NU lansează cod arbitrar controlat de utilizator).

## Adăugarea unei căi care permite ocolirea prin scope-ul manage

1. Confirmați că ruta nu execută cod sau comenzi furnizate de utilizator. Dacă
   o face, opriți-vă — această excepție nu este instrumentul potrivit.
2. Adăugați prefixul în `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` din
   `src/server/authz/routeGuard.ts`
3. Adăugați acoperire în `tests/unit/authz/management-policy.test.ts` pentru toate cele patru
   tipuri de cereri: fără Bearer (403), Bearer cu scope-ul manage (permite), Bearer fără scope-ul manage
   (403) și regresia specifică prefixului, care verifică faptul că `/api/cli-tools/runtime/*` rămâne
   strict limitat la loopback chiar și cu un Bearer cu scope-ul manage.

## Documentarea nivelurilor de securitate în OpenAPI

Când adăugați o rută nouă în `docs/openapi.yaml`, aplicați extensia corespunzătoare
a furnizorului dacă ruta este clasificată de `routeGuard.ts`:

| Clasificare în routeGuard.ts               | Adnotare YAML                     | Aplicare                                                   |
| ------------------------------------------ | --------------------------------- | ---------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`           | Blocat necondiționat pentru conexiunile non-loopback       |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`        | Autentificare obligatorie chiar și cu `requireLogin=false` |
| Rută internă de administrare/depanare      | `x-internal: true`                | Ascunsă implicit din /dashboard/api-endpoints              |
| Niciuna (publică / autentificare standard) | (nu este necesară nicio adnotare) | Acces standard controlat de `requireLogin`                 |

### Validare

Două scripturi asigură consecvența dintre adnotările YAML și `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — eșuează dacă acoperirea este < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — eșuează dacă adnotările `x-loopback-only` sau
  `x-always-protected` diferă de constantele definite la compilare

Ambele scripturi rulează în hook-ul pre-commit și în CI.

### Regula privind rezultatele fals pozitive

Dacă `x-always-protected` sau `x-loopback-only` este adnotat pe o rută care NU se află în
constanta din `routeGuard.ts`, scriptul de acoperire eșuează. Soluția este întotdeauna alinierea
YAML la ceea ce aplică efectiv `routeGuard.ts` — nu adăugarea rutelor în `routeGuard.ts`
fără implementarea corespunzătoare a logicii de aplicare.
