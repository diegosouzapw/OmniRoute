Acest document descrie procesul efectiv de implementare a OmniRoute pe Fly.io, acoperind două scenarii:

- Implementarea proiectului curent pe Fly.io pentru prima dată
- Publicarea actualizărilor ulterioare ale codului
- Proiecte noi care urmează același flux de implementare

Acest ghid se bazează pe o configurație funcțională verificată pentru proiectul curent. Numele aplicației este `omniroute`.

---

## 1. Obiectivele implementării

- Platformă: Fly.io
- Metodă de implementare: publicare locală directă cu `flyctl`
- Mediu de execuție: utilizarea fișierelor existente `Dockerfile` și `fly.toml` din depozit
- Persistența datelor: Fly Volume montat la `/data`
- URL de acces: `https://omniroute.fly.dev/`

---

## 2. Configurația-cheie a proiectului curent

S-a confirmat că fișierul `fly.toml` din depozitul curent conține următoarele elemente-cheie:

```toml
app = 'omniroute'
primary_region = 'sin'

[[mounts]]
  source = 'data'
  destination = '/data'

[processes]
  app = 'node run-standalone.mjs'

[http_service]
  internal_port = 20128

[env]
  TZ = "Asia/Shanghai"
  HOST = "0.0.0.0"
  HOSTNAME = "0.0.0.0"
  BIND = "0.0.0.0"
```

Note:

- `app = 'omniroute'` stabilește aplicația Fly vizată de implementare
- `destination = '/data'` stabilește directorul de montare al volumului persistent
- Acest proiect trebuie să seteze `DATA_DIR=/data`; în caz contrar, baza de date și cheile vor fi scrise în directorul temporar al containerului

## 3. Cerințe preliminare

### 3.1 Instalarea Fly CLI

Windows PowerShell:

```powershell
pwsh -Command "iwr https://fly.io/install.ps1 -useb | iex"
```

Dacă scriptul de instalare eșuează în mediul dvs., puteți și să descărcați manual executabilul `flyctl` și să îl adăugați în `PATH`.

### 3.2 Autentificarea în contul Fly

```powershell
flyctl auth login
```

### 3.3 Verificarea stării autentificării

```powershell
flyctl auth whoami
flyctl version
```

## 4. Prima implementare a proiectului curent

### 4.1 Clonați codul și accesați directorul

```powershell
git clone https://github.com/diegosouzapw/OmniRoute.git
cd OmniRoute
```

### 4.2 Confirmați numele aplicației

Deschideți `fly.toml` și verificați următoarea linie:

```toml
app = 'omniroute'
```

Dacă implementați în propria aplicație nouă, îl puteți schimba cu un nume unic la nivel global, de exemplu:

```toml
app = 'omniroute-yourname'
```

Notă:

- Asigurați-vă că aplicația pe care o vedeți în consolă corespunde valorii `app` din `fly.toml`
- Dacă ați folosit anterior un nume diferit, precum `oroute`, nu îl confundați cu `omniroute`

### 4.3 Creați aplicația

Dacă aplicația nu există încă:

```powershell
flyctl apps create omniroute
```

Dacă ați schimbat numele aplicației, înlocuiți `omniroute` cu numele ales.

### 4.4 Prima implementare

```powershell
flyctl deploy
```

## 5. Parametri obligatorii

Pentru acest proiect, se recomandă configurarea pe Fly.io cel puțin a următorilor parametri.

### 5.1 Parametri verificați

Acești parametri au fost utilizați în implementări reale ale aplicației curente `omniroute`:

- `API_KEY_SECRET`
- `DATA_DIR`
- `JWT_SECRET`
- `MACHINE_ID_SALT`
- `NEXT_PUBLIC_BASE_URL`
- `OMNIROUTE_WS_BRIDGE_SECRET` (obligatoriu în producție — utilizat pentru autentificarea punții WebSocket)
- `STORAGE_ENCRYPTION_KEY`

### 5.2 Despre `INITIAL_PASSWORD`

Proiectul curent nu setează `INITIAL_PASSWORD`, deoarece această implementare nu îl necesită.

Dacă nu este setat:

- Jurnalul de pornire va indica faptul că parola implicită este `CHANGEME`
- Ar trebui să schimbați parola de autentificare din setările sistemului cât mai curând posibil după implementare

Dacă doriți să inițializați parola backend-ului fără intervenție manuală, o puteți adăuga ulterior:

- `INITIAL_PASSWORD`

## 6. Parametri recomandați

### 6.1 Configurarea secretelor

Următoarele variabile sunt recomandate pentru Fly Secrets:

| Variabilă                     | Recomandare              | Descriere                                                          |
| ----------------------------- | ------------------------ | ------------------------------------------------------------------ |
| `API_KEY_SECRET`              | Obligatorie              | Utilizată pentru generarea și validarea cheilor API                |
| `JWT_SECRET`                  | Obligatorie              | Utilizată pentru sesiunile de autentificare și semnarea JWT-urilor |
| `OMNIROUTE_WS_BRIDGE_SECRET`  | Obligatorie în producție | Secret pentru autentificarea punții WebSocket                      |
| `STORAGE_ENCRYPTION_KEY`      | Recomandată insistent    | Criptează în repaus informațiile sensibile despre conexiuni        |
| `MACHINE_ID_SALT`             | Recomandată              | Generează un identificator stabil al mașinii                       |
| `INITIAL_PASSWORD`            | Opțională                | Setează parola inițială a backendului la prima implementare        |
| Credențiale private OAuth/API | După necesități          | Configurarea autentificării pentru platformele externe             |

### 6.2 Valori recomandate pentru proiectul curent

| Variabilă              | Valoare recomandată         |
| ---------------------- | --------------------------- |
| `DATA_DIR`             | `/data`                     |
| `NEXT_PUBLIC_BASE_URL` | `https://omniroute.fly.dev` |

Note:

- `DATA_DIR=/data` este esențial și trebuie să corespundă punctului de montare al volumului Fly
- `NEXT_PUBLIC_BASE_URL` este utilizat de planificator, de callback-urile frontendului și în scenarii similare

### 6.3 Configurarea URL-ului de callback OAuth

Dacă trebuie să activați furnizori bazați pe OAuth (de exemplu, Antigravity, Gemini, Cursor) în implementarea Fly.io, asigurați-vă că sunt îndeplinite următoarele două condiții:

1. **Setați `NEXT_PUBLIC_BASE_URL` la domeniul dumneavoastră HTTPS public**

   ```powershell
   flyctl secrets set NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev -a omniroute
   ```

   Dacă utilizați un domeniu personalizat, înlocuiți-l cu domeniul corespunzător (de exemplu, `https://omniroute.yourdomain.com`).

2. **Configurați URL-ul de callback în consola furnizorului**

   Toți furnizorii OAuth utilizează aceeași cale de callback `/callback` — NU există câte o rută de callback pentru fiecare furnizor:

   ```text
   <NEXT_PUBLIC_BASE_URL>/callback
   ```

   De exemplu, indiferent dacă utilizați Gemini, Antigravity, Cursor sau GitLab Duo:
   - `https://omniroute.fly.dev/callback`

   Dacă `NEXT_PUBLIC_BASE_URL` nu corespunde URL-ului de callback înregistrat la furnizor, fluxul OAuth va eșua la etapa de redirecționare în browser.

## 7. Configurarea secretelor printr-o singură comandă

Următoarele comenzi generează valori aleatorii securizate și scriu într-un singur pas toți parametrii necesari proiectului curent în Fly Secrets.

Note:

- Nu include `INITIAL_PASSWORD`
- Destinat proiectului curent `omniroute`

```powershell
$apiKeySecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$jwtSecret = [Convert]::ToHexString((1..64 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$machineIdSalt = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$storageKey = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()
$wsBridgeSecret = [Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 })).ToLower()

flyctl secrets set `
  API_KEY_SECRET=$apiKeySecret `
  JWT_SECRET=$jwtSecret `
  MACHINE_ID_SALT=$machineIdSalt `
  STORAGE_ENCRYPTION_KEY=$storageKey `
  OMNIROUTE_WS_BRIDGE_SECRET=$wsBridgeSecret `
  DATA_DIR=/data `
  NEXT_PUBLIC_BASE_URL=https://omniroute.fly.dev `
  -a omniroute
```

Pe Linux / macOS, puteți utiliza și `openssl rand -hex 32`:

```bash
flyctl secrets set OMNIROUTE_WS_BRIDGE_SECRET=$(openssl rand -hex 32) -a omniroute
```

Note:

- `OMNIROUTE_WS_BRIDGE_SECRET` este obligatoriu în producție; absența sa va împiedica negocierea conexiunii cu puntea WebSocket

Dacă doriți să setați și o parolă inițială:

```powershell
flyctl secrets set INITIAL_PASSWORD=your-strong-password -a omniroute
```

## 9. Actualizări și lansări ulterioare

După actualizarea codului, procesul de lansare este simplu:

```powershell
git pull
flyctl deploy
```

Dacă trebuie doar să actualizați parametrii fără a modifica codul:

```powershell
flyctl secrets set KEY=value -a omniroute
```

Fly va efectua automat o actualizare graduală a mașinilor.

### 9.1 Urmărirea actualizărilor depozitului upstream, păstrând fișierul `fly.toml` al fork-ului

Dacă depozitul actual este un fork și doriți să sincronizați actualizările din depozitul upstream `https://github.com/diegosouzapw/OmniRoute`, urmați fluxul de lucru de mai jos.

Mai întâi, verificați depozitele remote:

```powershell
git remote -v
```

Ar trebui să vedeți cel puțin:

- `origin` indicând spre propriul fork
- `upstream` indicând spre depozitul original

Dacă `upstream` nu este configurat, adăugați-l:

```powershell
git remote add upstream https://github.com/diegosouzapw/OmniRoute.git
```

Înainte de sincronizarea cu upstream, preluați cele mai recente commituri și etichete:

```powershell
git fetch upstream --tags
```

Verificați versiunea curentă și etichetele upstream:

```powershell
git describe --tags --always
git show --no-patch --oneline v3.4.7
```

> Notă: Versiunea curentă a proiectului este `v3.8.0`. Referințele la `v3.4.7` de mai jos sunt păstrate doar ca exemple istorice. Pentru lansările efective, utilizați `:latest` sau eticheta versiunii curente (de exemplu, `:v3.8.0`).

Dacă doriți să îmbinați cea mai recentă versiune upstream `main`, păstrând în mod forțat fișierul `fly.toml` al fork-ului, urmați acest flux de lucru:

```powershell
git merge upstream/main
git checkout HEAD~1 -- fly.toml
git add -- fly.toml
git commit -m "chore(deploy): keep fork fly.toml"
git push origin main
```

Note:

- `git merge upstream/main` sincronizează cel mai recent cod din depozitul original
- `git checkout HEAD~1 -- fly.toml` restaurează propriul fișier `fly.toml` al fork-ului din starea anterioară îmbinării
- Dacă upstream nu a modificat `fly.toml`, acest pas nu va introduce nicio diferență
- Dacă upstream a modificat `fly.toml`, acest pas asigură că numele aplicației Fly, montarea volumului, regiunea și alte configurări de implementare specifice fork-ului nu sunt suprascrise

Dacă doriți să vă aliniați la o anumită etichetă de lansare (de exemplu, `v3.4.7`), verificați mai întâi dacă eticheta este deja inclusă în `upstream/main`:

```powershell
git merge-base --is-ancestor v3.4.7 upstream/main
```

Un rezultat pozitiv înseamnă că `upstream/main` conține deja versiunea respectivă; puteți îmbina pur și simplu `upstream/main`.

### 9.2 Secvența standard de lansare după sincronizarea cu upstream

După sincronizarea cu depozitul original, urmați această ordine recomandată pentru lansare:

1. `git fetch upstream --tags`
2. `git merge upstream/main`
3. Restaurați fișierul `fly.toml` al fork-ului
4. `git push origin main`
5. `flyctl deploy`
6. `flyctl status -a omniroute`
7. `flyctl logs --no-tail -a omniroute`

Acesta este fluxul de lucru efectiv utilizat la actualizarea proiectului curent la `v3.4.7` (exemplul se referă la o versiune istorică; versiunea curentă efectivă este `v3.8.0`).

## 11. Indicatori de succes

După o implementare reușită, jurnalele ar trebui să afișeze un conținut similar cu:

```text
[bootstrap] Secrets persisted to: /data/server.env
[DB] SQLite database ready: /data/storage.sqlite
```

Aceste două aspecte sunt esențiale:

- `/data/server.env` confirmă faptul că secretele din mediul de execuție sunt scrise pe volumul persistent
- `/data/storage.sqlite` confirmă faptul că baza de date este scrisă pe volumul persistent

Dacă vedeți în schimb `/app/data/...`, `DATA_DIR` este configurat incorect și trebuie corectat imediat.

## 12. Probleme frecvente

### 12.1 Pagina `Secrets` este goală

De obicei, există două motive:

- Nu ați executat încă `flyctl secrets set`
- Vizualizați o altă aplicație (de exemplu, `oroute` în loc de `omniroute`)

### 12.2 `flyctl deploy` raportează `app not found`

Creați mai întâi aplicația:

```powershell
flyctl apps create omniroute
```

### 12.3 Analizarea fișierului `fly.toml` eșuează

Verificați următoarele:

- Dacă există caractere corupte în comentarii
- Dacă ghilimelele și indentarea TOML sunt corecte

### 12.4 Datele nu sunt păstrate

Verificați ambele condiții de mai jos:

- `fly.toml` conține `destination = '/data'`
- `DATA_DIR` este setată la `/data`

### 12.5 Poate rula fără `INITIAL_PASSWORD`?

Da, poate rula. Va utiliza implicit parola prestabilită `CHANGEME`. Se recomandă schimbarea parolei backendului cât mai curând posibil în mediul de producție.

---

## 13. Reutilizarea pentru proiecte noi

Dacă implementați un proiect nou urmând acest document, trebuie să modificați doar următoarele elemente:

1. Modificați valoarea `app` din `fly.toml`
2. Modificați `NEXT_PUBLIC_BASE_URL`
3. Păstrați `DATA_DIR=/data`
4. Regenerați `API_KEY_SECRET`, `JWT_SECRET`, `MACHINE_ID_SALT` și `STORAGE_ENCRYPTION_KEY`
5. După prima implementare, verificați dacă jurnalele sunt scrise în `/data`

Nu reutilizați cheile dintr-un proiect anterior.

2. `flyctl apps create omniroute`

5. `flyctl logs --no-tail -a omniroute`
