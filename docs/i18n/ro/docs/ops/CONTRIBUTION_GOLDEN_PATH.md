Folosiți acest ghid pentru a alege cea mai restrânsă buclă de dezvoltare fiabilă pentru un pull request. Acesta nu
înlocuiește documentele de arhitectură și securitate specifice fiecărei zone, indicate mai jos; el conectează fiecare tip
uzual de modificare la contractele, verificările focalizate și acoperirea CI aferente.

## Parcursul urmat de fiecare modificare

1. **Alegeți baza înainte de a edita.** Găsiți cea mai recentă ramură activă `release/v*` și creați ramura pornind de la
   vârful acesteia. Vizați acea ramură, nu `main`. Dacă este activă o înghețare a versiunii, nu vizați ramura
   înghețată; utilizați următorul ciclu activ descris în
   [Modelul de ramificare și lansare](BRANCHING_MODEL.md).
2. **Denumiți contractele.** Identificați fiecare catalog, schemă, artefact generat, API public sau interfață
   cu utilizatorul pe care o afectează modificarea. Tabelul de mai jos oferă setul minim de pornire.
3. **Scrieți sau actualizați testele focalizate.** Modificările de producție din `src/`, `open-sse/`, `electron/` sau
   `bin/` necesită un test automatizat în același PR. Rulați cele mai restrânse fișiere de test care demonstrează
   comportamentul, apoi verificările focalizate enumerate.
4. **Permiteți CI să ruleze matricea extinsă.** Seturile complete de teste unitare fragmentate, Vitest, pragul progresiv de acoperire și
   buildul de producție rulează în PR. Rulați local o suită extinsă numai atunci când un eșec focalizat indică
   un impact mai larg sau când modificarea acoperă mai multe subsisteme.
5. **Reconciliați înainte de revizuire.** Preluați baza activă, inspectați noile commituri ale acesteia și diferențele modificărilor dvs. față de
   aceasta, apoi efectuați rebase sau merge pentru bază conform fluxului de lucru al contributorilor. Rezolvați conflictele din fișierele
   generate și din cataloage pornind de la sursa lor, regenerați-le, reluați bucla focalizată și confirmați că
   PR-ul vizează în continuare ramura activă de lansare.
6. **Înregistrați dovezile.** În șablonul PR-ului, enumerați comenzile rulate, fiecare fișier de test adăugat sau modificat,
   migrările sau indicatoarele de funcționalitate și orice validare exclusiv CI aflată încă în așteptare.

## Parcursuri recomandate în funcție de tipul modificării

Comenzile de mai jos reprezintă verificările focalizate minime, nu permisiunea de a omite un test care acoperă direct
comportamentul pe care l-ați modificat.

### Furnizor

**Contracte**

- Definiția furnizorului din `src/shared/constants/providers/` și compunerea acesteia în
  `src/shared/constants/providers.ts`.
- Modelele și capabilitățile din `open-sse/config/providerRegistry.ts` sau din fișierele de registru extrase ale acestuia.
- Selectarea executorului/traductorului, configurarea OAuth sau a cheii API, resursele panoului de control și referința
  generată a furnizorului, după caz.
- Credențialele publice trebuie să utilizeze `resolvePublicCred()`; răspunsurile de eroare trebuie să utilizeze funcțiile ajutătoare partajate
  pentru eliminarea datelor sensibile din erori. Consultați `docs/security/PUBLIC_CREDS.md` (git; necompilat în `/docs`) și
  [Eliminarea datelor sensibile din erori](../security/ERROR_SANITIZATION.md).

**Buclă focalizată**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # când catalogul se modifică; comiteți diferențele generate
npm run lint
```

Testați, de asemenea, fiecare familie de solicitări afectată: chat, Responses, imagini, înglobări, audio sau video.
Revizuiți diferențele cataloagelor generate și ale fișierelor golden ca modificări de contract; nu le acceptați orbește.

### Rutare

**Contracte**

- Valorile publice ale strategiilor și metadatele UI din `src/shared/constants/routingStrategies.ts`.
- Expedierea și ordonarea din `open-sse/services/combo.ts` și `open-sse/services/combo/`.
- Schemele combo, persistența, starea de reziliență, capabilitățile modelelor și controalele API/UI.
- [Motorul Auto-Combo](../routing/AUTO-COMBO.md) și documentația privind reziliența atunci când comportamentul se modifică.

**Buclă focalizată**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # modificări ale strategiei sau expedierii
npm run check:known-symbols      # modificări ale înregistrării strategiei
npm run lint
```

Utilizați local teste deterministe cu servicii upstream simulate. Testele rapide combo live necesită credențiale și sunt
manuale, nu substitute pentru CI.

### UI / UX

**Contracte**

- Ruta/pagina Next.js și limitele componentelor partajate din `src/app/` și
  `src/shared/components/`.
- Formele răspunsurilor API, stările de încărcare/conținut gol/eroare, comportamentul tastaturii și al cititoarelor de ecran,
  aspectul adaptiv, temele și extinderea localizărilor.
- Șirurile-sursă în limba engleză pentru UI din `src/i18n/messages/en.json`; nu introduceți direct în cod texte noi afișate utilizatorilor.

**Buclă focalizată**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Rulați aplicația pentru modificările de interacțiune sau vizuale și verificați atât ferestrele de vizualizare înguste, cât și pe cele late. CI rulează
buildul de producție și suitele mai ample; comportamentul vizual necesită în continuare o componentă focalizată, Playwright
sau o verificare manuală documentată, adecvată modificării.

### i18n

**Contracte**

- `src/i18n/messages/en.json` este sursa UI; `config/i18n.json` este sursa localizărilor.
- Cataloagele CLI se află separat în `bin/cli/locales/`.
- Păstrați exact substituenții și etichetele ICU. Nu traduceți numele produselor/furnizorilor/modelelor,
  numele protocoalelor și antetelor, comenzile, identificatorii de cod/JSON, URL-urile, variabilele de mediu sau
  termenii protejați precum `OmniRoute`, `OAuth`, `MCP` și `A2A`. Lista-sursă actuală este
  `scripts/i18n/glossary/protected-terms.json`.

**Buclă focalizată**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # când se modifică șirurile/cataloagele CLI
npm run lint
```

Acestea sunt îndrumări pentru sistemul existent, nu o invitație de a-i extinde instrumentele sau modelul de chei.
Mențineți modificările i18n punctuale cât timp este proiectat sistemul înlocuitor. Nu rulați comenzi de traducere
care apelează servicii externe decât dacă sarcina necesită explicit traduceri generate și
ați revizuit diferențele rezultate.

### CLI

**Contracte**

- Comenzile și opțiunile publice din `bin/cli/`, comenzile API generate, codurile de ieșire, stdout/stderr și
  structurile de ieșire JSON, comportamentul configurației/al mediului și fișierele incluse în pachet.
- Șirurile CLI vizibile utilizatorului trebuie să utilizeze stratul de i18n al CLI-ului și să mențină aliniate cataloagele `en`/`pt-BR`.
- Păstrați Node drept mediul de execuție acceptat și respectați contractul binar publicat.

**Buclă focalizată**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # modificări ale CLI-ului generat/inclus în pachet
npm run check:pack-policy     # modificări ale suprafeței pachetului
npm run lint
```

Utilizați comanda exactă într-un director temporar de date atunci când comportamentul depinde de parsare, fișiere sau starea
de ieșire. CI efectuează verificările mai ample ale artefactelor pachetului și ale ecosistemului.

### Bază de date

**Contracte**

- Modulele de domeniu se află în `src/lib/db/`; importați direct modulele specifice (vechiul strat de reexportare `localDb.ts` a fost eliminat).
- Migrările SQL numerotate și idempotente se află în `src/lib/db/migrations/`; trebuie respectate siguranța tranzacțiilor, comportamentul
  actualizărilor, indecșii și fiecare apelant afectat de schemă.
- Rutele și gestionarii nu execută niciodată direct SQL brut.

**Buclă focalizată**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Când adăugați o migrare, testați atât o bază de date nouă, cât și actualizarea de la schema anterioară. Testele bazei de date
trebuie să închidă handle-urile și să apeleze `resetDbInstance()` în timpul curățării. Rulați `npm run test:bun:db` numai atunci când
se modifică traseul adaptorului Bun furnizat fără garanții; Node rămâne autoritar.

### Compilare / implementare

**Contracte**

- Manifestele/fișierul de blocare din rădăcină și din spațiile de lucru, `scripts/build/`, asamblarea autonomă Next.js, conținutul
  pachetului `dist/`, metadatele Electron specifice platformei, fluxurile de lucru CI și santinelele de implementare.
- Intervalele de versiuni Node acceptate și utilizarea Bun permisă explicit în `CLAUDE.md` trebuie să rămână intacte.
- Artefactele de compilare rămân neurmărite; se aplică politicile privind dependențele, licențele, fluxurile de lucru și pachetele.

**Buclă focalizată**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # modificări ale dependențelor sau ale fișierului de blocare
npm run check:pack-policy      # modificări ale suprafeței pachetului publicat
npm run lint
```

Utilizați local `npm run build` numai atunci când modificarea afectează compilarea, asamblarea autonomă, resursele
sau includerea în pachet pentru rulare. Utilizați `npm run build:release` numai pentru validarea lansării/implementării. Compilarea din CI este
semnalul final multiplatformă; modificările Electron specifice unei platforme necesită compilarea focalizată corespunzătoare
sau dovezi rezultate dintr-un test minimal.

## Bucla locală pentru candidați

Testele sursei nu pot demonstra că artefactul împachetat pornește: listele de împachetare, dependențele eliminate
și binarele native eșuează doar după ce arhiva tar este instalată și pornită. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) reprezintă partea locală a fluxului construire unică / validare / promovare din
RFC #8084: construiește un singur candidat, validează exact acel artefact, îl promovează prin redenumirea
directoarelor și îl readuce la versiunea anterioară atunci când slotul promovat nu trece verificarea de stare.

```bash
npm run dev:candidate -- run --dry-run --json  # afișează planul, fără a modifica nimic
npm run dev:candidate -- run                   # construiește + validează + promovează, revenire automată
npm run dev:candidate -- build                 # npm pack + instalare în _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # pornește pe un port liber, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # interschimbă current și previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # reutilizează o arhivă tar construită în altă parte (CI)
```

- **Construire unică.** `build` împachetează arborele curent (are nevoie de `dist/server.js`, așadar rulați mai întâi
  `npm run build:release`) sau copiază `--from-tarball`, apoi instalează arhiva tar într-un prefix npm
  izolat, deoarece arhiva tar nu conține `node_modules`. ID-ul este sha-ul scurt pentru `HEAD`
  (`-dirty` atunci când arborele conține modificări locale) sau `tgz-<sha256>` pentru o arhivă tar. Un ID curat
  care este deja construit este reutilizat în loc să fie reconstruit; transmiteți `--force` pentru a-l reconstrui.
- **Validați pachetul, nu sursa.** `validate` pornește CLI-ul instalat
  (`serve --port <free port>`) cu un `DATA_DIR=<candidate>/data` nou, secrete fictive și variabilele operatorului
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` și `INITIAL_PASSWORD` eliminate din
  mediu, astfel încât să verifice configurația fără cheie pentru loopback a unei instalări noi. Așteaptă ca
  `GET /api/health` să returneze 200, impune ca `GET /v1/models` să returneze 200, oprește grupul de procese
  și înregistrează verdictul în `validation.json` împreună cu hash-ul arhivei tar.
- **Promovați același artefact.** `promote` refuză un candidat fără o validare reușită pentru
  hash-ul curent al arhivei sale tar. Slotul activ implicit este `_artifacts/candidate/current`; `--target <dir>`
  selectează un alt director de pe același sistem de fișiere, iar slotul său anterior este `<dir>.previous`.
  Fiecare redenumire este atomică, iar un eșec survenit în timpul procesului inversează redenumirile deja executate.
- **Revenire la versiunea anterioară.** `run` validează din nou slotul promovat și interschimbă `current` și `previous`
  dacă acea verificare eșuează. Un candidat care nu trece prima validare nu este promovat niciodată.

Totul este scris în directorul ignorat de git `_artifacts/candidate/`; o instalare OmniRoute
existentă și directorul său de date nu sunt modificate niciodată. CLI-ul promovat este
`_artifacts/candidate/current/prefix/bin/omniroute`; porniți-l cu propriul `DATA_DIR` atunci când îl utilizați.
Coduri de ieșire: `0` succes, `1` validare sau promovare eșuată, `2` eroare de utilizare sau construire lipsă.

## Bucla locală versus CI

| Rulare locală pentru fiecare patch                                                                 | CI furnizează semnalul general                                                              |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Testele directe de comportament și verificările de categorie de mai sus                            | Suita completă de teste unitare, partiționată, și testele seriale                           |
| `npm run lint`                                                                                     | Suitele Vitest și pragurile progresive de acoperire/calitate                                |
| Verificarea tipurilor sau build-ul numai când contractul afectat o impune                          | Build-ul de producție, securitatea, documentația, dependențele și verificările politicii PR |
| Interacțiunea manuală/verificările live numai când automatizarea nu poate demonstra comportamentul | Verificările de integrare între joburi și de platformă configurate prin workflow            |

O buclă focalizată verde reprezintă o dovadă privind contractul modificat, nu o garanție că verificările CI fără legătură
vor trece. Pe de altă parte, nu faceți ca fiecare editare locală să aștepte întreaga matrice a depozitului.

## Listă de verificare pentru reconciliere

Înainte de a solicita o revizuire:

- Confirmați că baza PR-ului este în continuare cea mai recentă ramură activă `release/v*`.
- Preluați acea bază și examinați commiturile integrate după crearea ramurii.
- Examinați `git diff <active-base>...HEAD` pentru modificări accidentale sau generate.
- Rezolvați conflictele din catalog și din documentele generate actualizând sursa și regenerând rezultatul.
- Rulați din nou fiecare test/verificare focalizată menționată în descrierea PR-ului după reconciliere.
- Nu slăbiți niciodată aserțiunile și nu eliminați testele obligatorii doar pentru a vă alinia la o bază modificată.

Pentru regulile privind înghețarea versiunilor și redirecționarea, consultați
[Modelul de ramificare și lansare](BRANCHING_MODEL.md). Pentru inventarul CI complet, consultați
[Referința verificărilor de calitate](../architecture/QUALITY_GATES.md).
