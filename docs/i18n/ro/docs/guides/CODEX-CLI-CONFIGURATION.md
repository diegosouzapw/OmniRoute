> **TOML este singurul format funcțional.** Versiunile moderne Codex citesc exclusiv
> `~/.codex/config.toml` (verificat cu codex-cli 0.147.0: `codex --help`
> documentează suprascrierile `-c/--config` „încărcate din
> `~/.codex/config.toml`”). Vechiul `~/.codex/config.yaml` aparținea CLI-ului npm
> învechit și este ignorat fără notificare. Generatorul din panoul de control
> (`/api/cli-tools/apply`, instrumentul `codex`) scrie TOML folosind o îmbinare
> prudentă — cheile existente și celelalte blocuri de furnizori sunt păstrate,
> cheia API rămâne în `OMNIROUTE_API_KEY` (niciodată în fișier), iar un fișier
> `config.yaml` învechit rămas este raportat într-o notă de migrare, fără a fi modificat.

## config.toml gata de lipit

Înlocuiți `<YOUR_HOST>` și `<YOUR_KEY>` cu valorile dumneavoastră:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # limita de stocare în istoric pentru fiecare apel de instrument

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc sau ~/.zshrc — valoarea efectivă a cheii, niciodată în config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex inclus în aplicația ChatGPT

Dacă ați instalat Codex prin intermediul aplicației desktop ChatGPT, binarul `codex`
poate exista doar în pachetul aplicației și este posibil să nu se afle încă în
variabila `PATH` a shellului. Adăugați directorul de resurse în fișierul de
inițializare al shellului:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Deschideți un shell nou, apoi verificați:

```bash
command -v codex
codex --version
```

### OmniRoute local fără autentificare: este suficientă o cheie substitutivă

Codex validează existența variabilei de mediu indicate de `env_key`
**înainte** ca prima solicitare să părăsească CLI-ul. Dacă instanța dumneavoastră
OmniRoute **locală** nu necesită autentificare, este suficientă orice valoare
substitutivă care nu este goală:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Folosiți în schimb o cheie reală atunci când serverul OmniRoute este protejat sau
accesat de la distanță.

> **Opțiuni uzuale pentru gazdă**
>
> | Acces        | URL                           |
> | ------------ | ----------------------------- |
> | Rețea locală | `http://192.168.0.1:20128/v1` |
> | Tailscale    | `http://100.x.x.x:20128/v1`   |
> | Buclă locală | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — de ce funcționează pentru toate modelele

Codex CLI a declarat învechit `wire_api = "chat"` (Chat Completions) în februarie 2026 și acum **necesită** `wire_api = "responses"` (OpenAI Responses API). Setarea `wire_api = "chat"` provoacă o oprire imediată la pornire începând cu v0.138.

Mulți furnizori, inclusiv GLM și Kimi, oferă în continuare doar un endpoint Chat Completions. DeepSeek V4 oferă acum atât un API Responses nativ, cât și un endpoint compatibil Anthropic; OmniRoute folosește Responses în mod implicit și permite fiecărei conexiuni DeepSeek să selecteze compatibilitatea Anthropic.

**OmniRoute rezolvă acest lucru în mod transparent:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute selectează protocolul nativ al furnizorului și efectuează traducerea când este necesar
    → POST /responses (DeepSeek V4) sau /chat/completions (Mistral / GLM / Kimi / altele)
```

Când utilizați OmniRoute, nu aveți niciodată nevoie de un proxy separat pentru traducere. **Toate modelele folosesc `wire_api = "responses"`** — OmniRoute se ocupă de restul.

> **`wire_api` este valoarea implicită** — câmpul are valoarea implicită `"responses"` și poate fi omis complet din `config.toml`. Setați-l explicit doar dacă documentați intenția.

## Fereastra de context și compactarea

### Câmpuri de configurare a tokenurilor

| Câmp                             | Descriere                                                                                                                                                                                                                                           |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Bugetul total de tokenuri pentru modelul activ. Setați-l la limita declarată a modelului.                                                                                                                                                           |
| `model_auto_compact_token_limit` | Pragul care declanșează compactarea automată a istoricului. **Maximum: 90% din `model_context_window`** — valorile de peste 90% sunt ignorate fără avertisment.                                                                                     |
| `tool_output_token_limit`        | Limita tokenurilor stocate în istoric pentru rezultatul fiecărui apel de instrument. Împiedică un singur răspuns voluminos al instrumentului să umple fereastra. **Aceasta nu este limita maximă de ieșire** — este o limită de stocare în istoric. |
| `compact_prompt`                 | Suprascriere inline a promptului de sistem utilizat în timpul compactării (v0.138+).                                                                                                                                                                |

> **Notă privind `model_max_output_tokens`**: Acest câmp **nu face parte din schema de configurare Codex CLI** (lipsește din baza de cod Codex Rust). Este ignorat fără avertisment dacă este setat. Nu vă bazați pe el — utilizați `tool_output_token_limit` pentru a controla cât de mult din rezultatul instrumentelor este stocat în istoric.

Toate modelele Codex din OmniRoute utilizează prefixul `cx/`:

| Numele din Codex CLI    | Modelul OmniRoute  |
| ----------------------- | ------------------ |
| `cx/gpt-5.5`            | GPT-5.5 standard   |

Ceilalți furnizori utilizează propriul prefix (`kmc/`, `glm/`, `ds/`, `ollamacloud/`, `opencode-go/`, `mistral/`) — prefixul corespunde aliasului furnizorului din OmniRoute.

## Efortul de raționament

Controlează cât de mult „gândește” modelul înainte de a răspunde.

| Valoare  | Utilizare                                                    |
| -------- | ------------------------------------------------------------ |
| `none`   | Fără raționament — răspuns direct                            |
| `low`    | Sarcini triviale (redenumire, formatare)                     |
| `medium` | **Valoarea implicită a serverului** când nu este specificată |
| `high`   | Sarcini intermediare (refactorizare, depanare)               |
| `xhigh`  | Arhitectură, analiză aprofundată, probleme complexe          |

```bash
# Suprascriere pentru fiecare invocare
codex -c model_reasoning_effort=low "rename variable x to count"
codex -c model_reasoning_effort=xhigh "design the auth module"
```

Setați și un **rezumat** al raționamentului, astfel încât Desktop să poată reda textul procesului de gândire (nu doar blocuri criptate):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # sau ultra, când este acceptat
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Bugetul de gândire OmniRoute (setare de server)

Pe gazda OmniRoute, **Settings → AI → Thinking Budget** trebuie să fie **`passthrough`**, astfel încât efortul/rezumatul Codex să ajungă la serviciul din amonte. Modul **`auto` elimină** toate câmpurile clientului `reasoning` / `reasoning_effort` și va goli panourile de gândire chiar și atunci când Codex este configurat corect.

Ghid complet: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Compresia și memoria cache pentru prompturi sunt independente și continuă să funcționeze cu `passthrough`.

## Profiluri — configurații denumite pentru fiecare model/flux de lucru

Profilurile vă permit să comutați modelul + fereastra de context cu un singur indicator. Fiecare profil este un fișier plat
`~/.codex/<name>.config.toml` care se suprapune peste configurația de bază din `config.toml`.

> **Regulă de denumire (Codex CLI v0.137+):** fișierul trebuie să fie `~/.codex/<name>.config.toml` — **fără prefixul `profile-`**.
> CLI-ul rezolvă `-p kimi-k27` → `~/.codex/kimi-k27.config.toml`. Dacă fișierul nu este găsit, configurația implicită se aplică fără nicio notificare.

```bash
codex --profile kimi-k27 "analyze 10k lines of this codebase"
codex -p glm52 "architecture review"
codex --profile deepseek-flash "rename variable"   # rapid, ieftin
```

### Profiluri de efort (același model, efort diferit)

```bash
codex -p low      # cx/gpt-5.5, efort=low
codex -p medium   # cx/gpt-5.5, efort=medium
codex -p high     # cx/gpt-5.5, efort=high
codex -p xhigh    # cx/gpt-5.5, efort=xhigh (implicit)
codex -p chat     # cx/gpt-5.5, niciun efort setat (valoarea implicită a serverului)
```

## Generarea automată a profilurilor cu `omniroute setup-codex`

Dacă rulați OmniRoute pe un VPS, puteți genera automat fișierele de profil din catalogul activ de modele:

```bash
# De pe un VPS (utilizează instanța OmniRoute locală pe portul 20128)
omniroute setup-codex

# De pe orice sistem — indicați adresa VPS-ului dvs.
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Previzualizare fără a scrie fișiere
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Generează doar profilurile GLM și Kimi
omniroute setup-codex --only glm,kimi

# Scrie într-un director personalizat
omniroute setup-codex --codex-home /path/to/.codex
```

Comanda preia `/v1/models`, utilizează profiluri optimizate pentru modelele cunoscute, recurge la metadatele catalogului pentru celelalte modele de text compatibile și scrie câte un fișier `~/.codex/<name>.config.toml` pentru fiecare. Este idempotentă — poate fi rulată din nou în siguranță.

OmniRoute poate, de asemenea, să **sincronizeze automat** aceleași fișiere de profil după ce o descoperire sau un import reușit al modelelor furnizorului modifică catalogul activ. Această funcționalitate este **opțională și dezactivată implicit**: activați-o din **panoul de control CLI Code** („CLI profile auto-sync” → Codex) sau setați `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (respectă și `CLI_ALLOW_CONFIG_WRITES`, activată implicit). Când este activată, aceasta scrie doar fișiere de profil `~/.codex/*.config.toml` separate; nu modifică niciodată fișierul activ/implicit `~/.codex/config.toml`, setările Codex-lb, autentificarea sau selectarea furnizorului.

Verifică starea instanței OmniRoute înainte de a lansa Codex:

## Sarcini de lungă durată

Două valori implicite OmniRoute pot sabota în mod discret sesiunile Codex CLI care durează mai multe ore. Niciuna nu este o setare Codex CLI — ambele se află în partea OmniRoute. Utilizatorii care migrează o configurație de la proxy-uri din amonte ce fixează conturile și dezactivează limitele de inactivitate se lovesc adesea de ambele și concluzionează că OmniRoute „nu poate susține o sesiune lungă”.

| Simptom                                                                                                   | Cauză probabilă                                                                                    | Parametru                |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------ |
| Sesiunea continuă să schimbe conturile / continuitatea cache-ului promptului se pierde între interacțiuni | TTL-ul afinității sesiunii este `0` (dezactivat)                                                   | `sessionAffinityTtlMs`   |
| Conexiunea se întrerupe în timpul raționamentului, fără nicio solicitare vizibilă pentru client           | Monitorul de inactivitate al fluxului s-a declanșat după 10 minute fără niciun fragment din amonte | `STREAM_IDLE_TIMEOUT_MS` |

Discuții asociate: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (întreruperi ale sarcinilor lungi), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (de ce afinitatea este dezactivată implicit). Urmărire: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Afinitatea sesiunii — fixați o conversație la un singur cont

**Implicit:** `sessionAffinityTtlMs = 0` (dezactivat).

**Unde se configurează**

- Panou de control → **Setări → Rutare** → **Afinitatea sesiunii** → **TTL-ul afinității (secunde)** (`ComboDefaultsTab`)
- Sau actualizați setările prin PATCH folosind `sessionAffinityTtlMs` în **milisecunde** (interval Zod `0`–`86_400_000`, adică până la 24 de ore)

> Redenumit în #7274 din `codexSessionAffinityTtlMs`, care era specific exclusiv Codex. Cheia veche este acceptată în continuare ca alias doar pentru citire; configurațiile noi ar trebui să utilizeze `sessionAffinityTtlMs`. Afinitatea se aplică acum **oricărui** furnizor odată ce TTL-ul depășește `0`, nu doar Codex — consultați [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Afinitatea sesiunii.

**Ce nu mai funcționează când rămâne la 0**

Fiecare interacțiune a unei conversații Codex cu mai multe schimburi este rutată independent de strategia combinată activă și poate ajunge la un **cont diferit pentru fiecare interacțiune**. Acest lucru întrerupe continuitatea sesiunii / cache-ului promptului din amonte. OmniRoute consultă antetele de sesiune Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) și câmpurile din corp, precum `prompt_cache_key` / `session_id`, numai când TTL-ul este mai mare decât `0` (`extractSessionAffinityKey` în `src/sse/services/auth.ts`).

**Recomandare pentru o singură sarcină de mai multe ore**

Setați TTL-ul **peste durata cronologică estimată a sarcinii** (valoarea maximă în interfața cu utilizatorul este de **86400 de secunde** = 24 de ore):

| Durata estimată a sarcinii | TTL-ul afinității (interfață, secunde) | `sessionAffinityTtlMs` |
| -------------------------- | -------------------------------------- | ---------------------- |
| Câteva ore                 | `14400` (4h)                           | `14400000`             |
| Peste noapte / ~12h        | `43200` (12h)                          | `43200000`             |
| O zi întreagă              | `86400` (24h, maximum)                 | `86400000`             |

Activarea explicită este intenționată: dezactivarea afinității favorizează echilibrarea încărcării între conturi; activarea acesteia favorizează continuitatea unei sesiuni lungi a agentului. Acest ghid **nu** modifică valoarea implicită — operatorii care rulează sarcini Codex lungi trebuie să activeze explicit această opțiune.

### 2. Timpul de expirare la inactivitatea fluxului — nu întrerupeți interacțiunile de raționament silențioase

**Implicit:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 minute). Când nu este setat, moștenește valoarea din `REQUEST_TIMEOUT_MS`; valoarea de bază comună este, de asemenea, 600000. Consultați [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Timpi de expirare.

**Ce nu mai funcționează cu valoarea implicită**

Un pas de raționament / utilizare a instrumentelor Codex care rămâne silențios mai mult de 10 minute, **fără niciun fragment real din amonte**, este închis forțat de monitorul SSE pentru inactivitate (`open-sse/utils/stream.ts`). Clientul observă adesea doar întreruperea conexiunii — ceea ce corespunde situației „s-a oprit automat, fără nicio notificare”.

Detaliu esențial: semnalul de menținere în viață SSE sintetic al OmniRoute **nu resetează** cronometrul de inactivitate. Numai un fragment real din corpul răspunsului din amonte actualizează `lastChunkTime`. Din perspectiva monitorului, un model silențios care încă „gândește” arată identic cu un serviciu din amonte blocat.

Inactivitate asociată a corpului Undici: `FETCH_BODY_TIMEOUT_MS` (valoarea implicită este, de asemenea, aceeași bază de 10 minute; `0` îl dezactivează). Pentru streaming, `FETCH_TIMEOUT_MS` acoperă doar stabilirea conexiunii / primele antete — după activarea fluxului, blocajele sunt controlate de `STREAM_IDLE_TIMEOUT_MS` și `FETCH_BODY_TIMEOUT_MS`.

**Recomandare pentru o singură sarcină de mai multe ore**

În mediul procesului OmniRoute (`.env` / compose / systemd):

```bash
# Dezactivează limitele de inactivitate a fluxului și a corpului pentru pașii lungi de raționament
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Sau măriți-le peste cel mai lung interval de inactivitate anticipat (valorile sunt exprimate în milisecunde):

```bash
# Exemplu: permite până la 2 ore de inactivitate între fragmentele din amonte
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Reporniți OmniRoute după modificarea acestor variabile de mediu.

### Rețetă concretă — sarcină Codex de mai multe ore

1. **Fixați contul:** Panou de control → Setări → Rutare → Afinitatea sesiunii → TTL-ul afinității = `43200` (12h) sau `86400` (maximum 24h).
2. **Măriți / dezactivați limitele de inactivitate** în mediul OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Păstrați configurația Codex obișnuită din `config.toml` (`wire_api = "responses"`, valoarea corectă pentru `base_url`, `OMNIROUTE_API_KEY`) — în Codex nu există opțiuni pentru afinitate/inactivitate care să controleze aceste două comportamente.
4. Reporniți OmniRoute, apoi porniți sarcina Codex de lungă durată.

### Decizia privind valorile implicite (#7287)

| Opțiune                  | Valoare implicită livrată | Modificare în acest ghid?                                                                          |
| ------------------------ | ------------------------- | -------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (dezactivat)          | **Nu** — rămâne opțională (echilibrarea încărcării vs. continuitate; consultați Discuția #5718)    |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 min)         | **Nu** — rămâne la 10 minute pentru traficul general; operatorii Codex o măresc sau o dezactivează |

Schimbarea globală a oricăreia dintre valorile implicite ar modifica comportamentul pentru fiecare client al unei instanțe, nu numai pentru Codex. Documentați opțiunile; lăsați valorile implicite neschimbate până când o decizie explicită a operatorului stabilește altceva.

### Diagnosticarea întreruperilor cauzate de inactivitate

Când se declanșează monitorul de inactivitate, OmniRoute înregistrează o linie de forma:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Căutați cu grep după `Idle timeout: no data from` (sau după codul `stream_idle_timeout` / numele erorii `StreamIdleTimeoutError`). Segmentul furnizorului este cel utilizat de OmniRoute pentru cererea respectivă (`codex`, un alt ID de furnizor sau `provider` dacă este necunoscut) — nu este întotdeauna șirul literal `codex`.

## Depanare

**`Error: wire_api = "chat" nu mai este acceptat`**
Eliminați `wire_api = "chat"` din configurație. Setați `wire_api = "responses"` sau omiteți câmpul (valoarea implicită este `"responses"` începând cu v0.138).

**`Error: model not found`**
Verificați dacă modelul există în OmniRoute și are prefixul corect. Utilizați `omniroute models list` sau deschideți `/dashboard/providers/<provider>`.

**`Authentication error`**
Confirmați că `OMNIROUTE_API_KEY` este exportată: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex verifică existența variabilei de mediu înainte de a efectua prima solicitare. Exportați
o cheie reală pentru serverele protejate sau o valoare substitutivă care nu este goală, precum
`OMNIROUTE_API_KEY=local`, atunci când instanța OmniRoute **locală** nu necesită
autentificare. Reporniți shell-ul dacă ați adăugat-o în `~/.bashrc` sau `~/.zshrc`.

**`Connection refused`**
Verificați dacă OmniRoute rulează și dacă gazda/portul din `base_url` sunt corecte pentru rețeaua dvs. (locală, Tailscale sau VPS).

**Sesiunea se întrerupe în apropierea limitei de context**
Setați explicit `model_context_window` și `model_auto_compact_token_limit`. Consultați tabelul de mai sus privind fereastra de context.

**Compactarea se declanșează prea târziu**
Reduceți `model_auto_compact_token_limit` la 80–85% din fereastră. Nu setați niciodată o valoare mai mare de 90%.

**Profilul nu se încarcă (`-p <name>` este ignorat fără avertisment)**
Confirmați că fișierul există la `~/.codex/<name>.config.toml` (fără prefixul `profile-`). Rulați `ls ~/.codex/*.config.toml`.

**O sarcină Codex de lungă durată se întrerupe în timpul rulării / schimbă conturile între mesaje**
Consultați [Sarcini de lungă durată](#long-running-tasks). Activați afinitatea sesiunii (cu un TTL mai mare decât durata sarcinii) și măriți valorile pentru `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS` sau dezactivați-le. Căutați în jurnalele OmniRoute folosind grep după `Idle timeout: no data from`.
