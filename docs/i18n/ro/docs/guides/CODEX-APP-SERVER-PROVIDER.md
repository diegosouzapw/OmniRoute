---

OmniRoute oferă **două** modalități de a utiliza OpenAI Codex:

| Furnizor               | Cum comunică cu OpenAI                                                                                                                                                                                                 | Restricție de utilizare                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **`codex`**            | Retransmite tokenul dvs. OAuth ChatGPT/OpenAI direct către Responses API                                                                                                                                               | **Da** — sesiunea oficială nu este autorizată pentru utilizare prin proxy/router |
| **`codex-app-server`** | Controlează propriul **`codex app-server` al Codex CLI** prin JSON-RPC/WebSocket; CLI-ul deține și își reîmprospătează automat credențialele OAuth (`~/.codex/auth.json`), exact ca într-o sesiune interactivă `codex` | **Nu** — OmniRoute nu retransmite niciodată un token către API                   |

Deoarece `codex-app-server` nu retransmite niciodată un token, acesta nu este
supus restricției privind retransmiterea sesiunii. Totuși, necesită un **Codex CLI
accesibil la URL-ul app-server configurat**, iar acel CLI trebuie să fie
**autentificat**.

---

## 1. Arhitectură

```
┌─ Aplicația OmniRoute ────────────┐        ┌─ Sidecar codex-app-server ──────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ token de capabilitate)       │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  își gestionează singur OAuth OpenAI│
└──────────────────────────────────┘        │  (~/.codex/auth.json, reîmprospătare│
        │ partajate (volume compose)         │   automată)                         │
        ▼                                   └─────────────────────────────────────┘
  codex-appserver-token   → tokenul de capabilitate WS (montat de ambele)
  codex-appserver-home    → ~/.codex (auth.json scris de panoul de control,
                             citit de codex app-server din sidecar)
```

- Sidecar-ul ascultă **doar** în rețeaua compose internă
  (`ws://codex-app-server:1456`), în spatele unui token de capabilitate. Acesta
  nu este **niciodată** expus pe gazdă sau pe internet.
- Codex CLI este inclus în imaginea `omniroute:base`, astfel încât nu este
  necesară instalarea codex pe gazdă sau pe dispozitivul utilizatorului atunci
  când rulați sidecar-ul.

## 2. Pornire

```bash
# Porniți stiva CU profilul sidecar codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Sidecar-ul generează tokenul său de capabilitate WS la prima pornire (în volumul
partajat `codex-appserver-token`), iar aplicația citește același token prin
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Nu este necesară configurarea manuală
a tokenului.

## 3. Conectare + autentificare

1. În panoul de control, adăugați o conexiune pentru **OpenAI Codex (App-Server)**.
   Nu este necesară nicio cheie API și niciun token (este un furnizor fără
   autentificare — sidecar-ul gestionează autentificarea).
2. Dacă Codex CLI din sidecar **nu este încă autentificat**, verificarea stării
   conexiunii raportează _„rulează, dar nu este autentificat”_ (nu o eroare de
   autentificare afișată cu roșu). Utilizați **Autentificare cu ChatGPT**: aceasta
   rulează fluxul standard OAuth pentru dispozitive al Codex în browser, apoi
   scrie `~/.codex/auth.json` în volumul partajat prin **Aplicare autentificare**
   (aceeași autentificare deservește atât furnizorul `codex`, cât și
   `codex-app-server`).
3. După autentificare, verificarea stării devine verde (verifică atât `/readyz`,
   **cât și** `account/read` — adică serviciul este pornit _și_ autentificat) și
   începe să funcționeze.

Panoul de control nu suprascrie niciodată un fișier `~/.codex/auth.json` existent
și valid — scrie numai atunci când fișierul lipsește sau tokenul său este expirat
(întotdeauna se creează o copie de rezervă).

## 4. Scenarii de implementare

- **Operator cu un Codex CLI deja autentificat** — montați directorul
  `~/.codex` al gazdei în sidecar (`codex-appserver-home`) și omiteți etapa de
  autentificare.
- **Utilizator public, fără codex instalat local** — irelevant: sidecar-ul
  conține CLI-ul. Utilizatorul se autentifică doar prin panoul de control.
- **OmniRoute instalat direct pe sistem (fără sidecar, codex pe gazdă)** —
  configurați `OMNIROUTE_CODEX_APPSERVER_WS` către propriul dvs.
  `codex app-server` și asigurați-vă că instanța codex de pe gazdă este
  autentificată; sugestia „codex nu este instalat” apare dacă binarul lipsește.

## 5. Ieșire prin rețea rezidențială / UDP (opțiune suplimentară pentru operator, neinclusă)

Sidecar-ul generic de mai sus accesează internetul prin rețeaua obișnuită a
containerului. Un operator care are nevoie ca traficul Codex să iasă printr-un
**punct de ieșire rezidențial** (de exemplu, un sidecar Tailscale cu TUN care
transportă TCP + UDP/QUIC) îl rulează ca suprascriere compose separată; acesta
nu face în mod intenționat parte din profilul `codex-app-server` livrat.
Consultați ghidul intern de operațiuni pentru această configurație.
