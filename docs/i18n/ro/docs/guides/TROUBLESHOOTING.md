## Referință rapidă

**Folosiți OmniRoute pentru prima dată?** Începeți aici — acestea rezolvă 90% dintre probleme:

| Văd acest mesaj                        | Ce înseamnă                                                  | Ce trebuie să faceți                                                                                 |
| -------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| „Nu se poate conecta”                  | OmniRoute nu rulează                                         | Rulați `omniroute` sau `docker restart omniroute`                                                    |
| „Cheie API nevalidă”                   | Cheia este greșită sau a expirat                             | Copiați din nou cheia de pe site-ul furnizorului                                                     |
| „Limita de solicitări a fost depășită” | Trimiteți prea multe solicitări                              | Așteptați 1 minut sau folosiți `model: "auto"` pentru comutarea automată la o alternativă            |
| „Cota a fost depășită”                 | Ați epuizat cota gratuită/plătită                            | Conectați mai mulți furnizori sau folosiți furnizori gratuiți (Kiro, Pollinations)                   |
| „Răspunsuri lente”                     | Furnizorul este ocupat sau prea departe                      | Folosiți `model: "auto/fast"` sau conectați un furnizor mai rapid (Groq, Cerebras)                   |
| „A fost utilizat furnizorul greșit”    | `auto` a ales un alt furnizor                                | Este normal! `auto` îl alege pe cel mai bun. Impuneți un anumit furnizor cu `model: "openai/gpt-4o"` |
| „502 Gateway necorespunzător”          | Furnizorul nu este disponibil                                | Așteptați și încercați din nou sau folosiți `model: "auto"` pentru a schimba furnizorul              |
| „401 Neautorizat”                      | Acreditările sunt greșite                                    | Verificați cheia API sau autentificați-vă din nou cu OAuth                                           |
| „omniroute nu este recunoscut”         | Din variabila PATH din Windows lipsesc modulele node globale | Adăugați prefixul npm global în variabila PATH din Windows. Găsiți-l cu `npm config get prefix`.     |
| „429 Prea multe solicitări”            | A fost aplicată o limită de solicitări                       | Așteptați 1 minut sau conectați mai mulți furnizori                                                  |

**Problema persistă?** Consultați secțiunea [depanare detaliată](#detailed-troubleshooting) de mai jos sau întrebați pe [Discord](https://discord.gg/U47eFqAXCn).

### Limitarea solicitărilor la furnizorii gratuiți (429 / 400 / 401)

**Simptom**: Atunci când folosiți `model: "auto"` cu furnizori gratuiți/fără autentificare (opencode, auggie etc.), primiți intermitent `HTTP 429`, `400` sau `401` în locul răspunsurilor. Solicitările reușesc dacă încercați din nou cu același prompt câteva momente mai târziu, dar automatizarea (sarcini cron, agenți, scripturi) eșuează la prima eroare.

**Cauza principală**: Trei moduri independente de eșec se suprapun:

1. **Limitarea solicitărilor de către furnizor (`429`)**: Nivelurile gratuite pot impune o cotă per interval. O rafală de apeluri paralele o epuizează, astfel încât următoarea solicitare este refuzată până la resetarea intervalului.
2. **Model nefuncțional în passthrough (`400`/`401`)**: Grupurile `auto/*` pot include modele passthrough de la `opencode` care sunt înregistrate în catalog, dar nu au acreditări active (de exemplu, `oc/north-mini-code-free` → `401`). Routerul automat încearcă unul dintre ele, eșuează, iar eroarea este propagată înainte ca mecanismul de comutare la o alternativă să intre în funcțiune.
3. **Amplificarea concurenței (`429` sub sarcină)**: Atunci când mai multe sesiuni de agent/cron accesează simultan `auto`, rata agregată a solicitărilor depășește ceea ce tolerează furnizorii gratuiți, astfel încât apelurile legitime sunt marcate drept abuzive.

**Remediere verificată (raportată de comunitate, 2026-08-10)**: ajustați trei variabile de mediu astfel încât rotația, concurența și comutarea la alternative să absoarbă fluctuațiile nivelului gratuit, în loc să eșueze din cauza lor:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # trece la alt model/furnizor la 400/401 (omite modelele passthrough nefuncționale)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limită explicită de admitere pentru sarcini grele (implicit nesetată: fără limită a numărului de solicitări, consultați nota de mai jos)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # mărește așteptarea limitată peste valoarea implicită RATE_LIMIT_MAX_WAIT_MS pentru serviciile upstream lente
```

Setați-le în mediul procesului OmniRoute (daemonul, de exemplu prin plist-ul LaunchAgent sau `systemctl edit`), apoi reporniți OmniRoute. Indicatorul de rotație este pârghia cu cel mai mare impact: acesta transformă un eșec definitiv într-o reîncercare transparentă la un furnizor funcțional din grup.

**Notă**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limitează numărul de solicitări grele — cu un context lung — care rulează simultan; limita este o poartă de admitere, nu un mecanism de limitare a solicitărilor furnizorului. **Actualizare #503-fanout:** această variabilă nu mai este setată implicit (acum se aplică numai atunci când este configurată explicit, ca mai sus) — admiterea solicitărilor grele este controlată în schimb de un buget de octeți derivat automat (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), care se adaptează în funcție de limita reală de memorie a gazdei, astfel încât o implementare nouă ar trebui să înregistreze mult mai puține respingeri `503 chat_admission_busy` fără a seta deloc această variabilă; setarea sa explicită aici continuă să funcționeze exact conform documentației. Suprascrierile explicite ale bugetului de octeți sunt limitate la intervalul 8 MiB–2 GiB. O eroare `413 body_exceeds_budget` nu este temporară: măriți acel buget de octeți, reduceți `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` sau măriți limita de memorie a procesului. O eliminare `inflight_bytes_budget` indică o competiție temporară pentru resurse și permite în continuare reîncercarea. Limitarea solicitărilor pentru fiecare furnizor (`open-sse/services/rateLimitManager.ts`) este controlată separat prin `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` și `RATE_LIMIT_AUTO_ENABLE` — consultați `.env.example`.

**Cum verificați că a funcționat**: rulați agentul/sarcina cron de două ori în succesiune rapidă și confirmați că ambele rulări reușesc. Înainte de remediere, a doua rulare generează de obicei `429`/`401`. După remediere, eșecurile (dacă există) sunt reîncercate în mod transparent, iar apelul se finalizează. De asemenea, puteți rula `curl /monitoring/health` și urmări câmpul `rateLimitedUntil` pentru conexiunile furnizorilor și `circuitBreakers.providerBreakers[].state` pentru furnizorii afectați — starea este una dintre `CLOSED`, `DEGRADED`, `OPEN` sau `HALF_OPEN` (consultați `src/shared/utils/circuitBreaker.ts`), iar un furnizor care continuă să eșueze va trece prin `CLOSED → DEGRADED → OPEN` înainte ca intervalul de resetare să permită o solicitare de testare (`HALF_OPEN`).

**Dacă întâmpinați în continuare eroarea 429**: contul activ pentru furnizorul respectiv și-a epuizat efectiv _cota_ (nu doar limita de frecvență). Adăugați un al doilea cont pentru același furnizor în panoul de control OmniRoute → Providers → Accounts sau includeți un alt furnizor gratuit (de exemplu, `routeway`, `auggie`). Rotația ajută doar în cazul erorilor tranzitorii de limitare a frecvenței/400/401; epuizarea completă a cotei necesită un al doilea set de acreditări sau un alt furnizor.

**Dacă întâmpinați eroarea 403 la modelele de viziune (`auto/vision`, `bazaarlink/*`)**: contul conectat nu are un plan plătit care să includă funcționalități de viziune sau cheia API nu are permisiuni suficiente. Verificați în panoul de control al furnizorului dacă domeniul de acces al cheii include funcționalități de viziune/multimodale sau conectați un cont cu abonament plătit și păstrați-l ca țintă pentru funcționalitățile de viziune.

## Avertismente la npm install (ERESOLVE / peer / deprecated)

Când rulați `npm install -g omniroute`, este posibil să vedeți un număr mare de avertismente precum `npm warn ERESOLVE`, notificări privind dependențele peer și mesaje `deprecated`. **Acestea sunt normale și inofensive.** Instalarea a reușit dacă vedeți `added <N> packages` în rezultat.

Pentru a suprima avertismentele privind rezolvarea dependențelor peer, utilizați forma de instalare acceptată de OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` suprimă doar mesajele `ERESOLVE` și notificările privind dependențele peer. Notificările privind funcționalitățile învechite rămân vizibile, deoarece provin din pachete terțe tranzitive; acestea nu indică faptul că instalarea a eșuat.

Avertismentele provin din intervale învechite ale dependențelor peer din pachete terțe pe care OmniRoute nu le controlează:

1. **`marked-terminal` necesită `marked >=1 <16`, dar a fost găsit `marked@18`** — în practică funcționează fără probleme; intervalul peer din proiectul upstream este doar învechit.
2. **`deprecated prebuild-install@7.1.3`** — un utilitar tranzitiv pentru preluarea binarelor native. Acesta nu este
   utilizat pentru instalarea bindingului de transport `wreq-js` fixat la o anumită versiune și nu indică faptul că
   configurarea transportului furnizorului de cookie-uri web a eșuat.

**Nu este necesară nicio acțiune** — avertismentele nu pot fi eliminate complet fără a crea fork-uri ale pachetelor upstream.

## Avertisment privind blocarea scripturilor npm install (instalare globală)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

La rularea comenzii `npm install -g omniroute`, versiunile npm mai noi (v11+ și v12+) blochează implicit scripturile ciclului de viață al pachetelor și afișează un avertisment privind scripturile de instalare:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Poate fi ignorat acest avertisment?

**Parțial, însă rularea fără scripturi nu este recomandată.** OmniRoute include mecanisme alternative robuste: dacă bindingurile native `better-sqlite3` nu pot fi încărcate din pachetul autonom, aplicația recurge la drivere alternative precum `node:sqlite` sau `sql.js` (consultați [Rezolvarea SQLite la rulare](../ops/SQLITE_RUNTIME.md)). Serverul va porni în continuare, însă rularea cu soluții alternative WASM precum `sql.js` dezactivează modul WAL (Write-Ahead Logging) al SQLite și mărește consumul de memorie și costul sincronizării pe disc.

### Ce scripturi sunt efectiv necesare?

Nu toate scripturile blocate sunt esențiale pentru rularea OmniRoute:

- **Esențiale (`omniroute`, `better-sqlite3`):** OmniRoute rulează dintr-un pachet autonom al aplicației Next.js (`dist/`). În timpul instalării, npm descarcă sau compilează driverul SQLite nativ specific sistemului gazdă în directorul de nivel superior `node_modules/better-sqlite3/`. Scriptul `postinstall` al OmniRoute (`scripts/build/postinstall.mjs`) verifică și copiază apoi aceste binare specifice sistemului gazdă în `dist/node_modules/`, astfel încât serverul autonom să le poată accesa. Dacă scriptul postinstall al `omniroute` este blocat, acest pas de copiere este omis.
- **Opționale/tranzitive (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Acestea sunt utilitare de build, instrumente de monitorizare sau utilitare pentru gestionarea sistemului de chei. Permiterea lor previne avertismentele de build, însă nu sunt necesare pentru funcționalitatea principală de rutare.
- **Exclus (`onnxruntime-node`):** Este o dependență opțională pentru embeddinguri AI locale și **nu** este necesară pentru rularea OmniRoute. Scriptul său postinstall descarcă aproximativ 300 MB de resurse CUDA de pe NuGet; nu îl includeți în lista de permisiuni decât dacă intenționați în mod explicit să utilizați accelerarea ONNX locală pe hardware compatibil.

### Soluția recomandată

Pentru a permite scripturile de instalare necesare în timpul unei instalări globale și pentru a elimina avertismentele, specificați `--allow-scripts` pentru OmniRoute și dependențele sale native:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Alternativ, pentru a configura permanent această opțiune pentru toate instalările globale din contul dumneavoastră de utilizator:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Verificați instalarea

După instalare, rulați instrumentul de diagnosticare încorporat pentru a vă asigura că bindingurile native și mediul de rulare funcționează corect:

```bash
omniroute doctor
```

Dacă o solicitare Gemini Web returnează `503` cu un mesaj care indică faptul că Playwright Chromium
nu este instalat, pachetul npm este prezent, dar binarul browserului lipsește.
Playwright păstrează în mod intenționat descărcările browserelor separat de instalarea

Pentru o instalare globală npm, instalați Chromium din directorul pachetului
OmniRoute, astfel încât memoria cache a browserului să aparțină aceleiași instalări Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Reporniți OmniRoute după instalare, apoi reîncercați solicitarea Gemini Web. Dacă
rulați OmniRoute dintr-o imagine Docker, utilizați imaginea `-web` (sau ținta de compilare
`runner-web`), care include Chromium și dependențele sale; imaginea de bază nu
le include.

## Rezultate fals pozitive ale antivirusului

<a name="antivirus-false-positives"></a>

### Avast/AVG pune în carantină `README.md` cu `MD:HttpRequest-inf[Susp]`

**Acesta este un rezultat fals pozitiv. Nimic nu este infectat și nu este necesară nicio acțiune.**

Avast și AVG rulează o euristică ce semnalează fișierele text simplu/Markdown care conțin multe
linkuri asemănătoare solicitărilor HTTP. Fișierul `README.md` al OmniRoute este inclus în pachetul npm (este
enumerat în `package.json` → `files`), astfel că, la o instalare globală, ajunge în `node_modules/omniroute/README.md` —
și conține aproximativ 15 exemple `http://localhost:20128/...` (endpointurile HTTP/SSE MCP,
URL-ul A2A `.well-known` și fragmente `curl`). Această densitate de linkuri este
suficientă pentru a declanșa euristica.

Dacă acest lucru a început abia recent: tipul fișierului nu s-a schimbat. Tabelul cu
endpointuri din README a fost extins (au fost adăugate MCP HTTP + SSE + A2A), precum și mai multe exemple `curl`,
ceea ce a făcut ca acesta să depășească pragul.

Fișierul este documentație inertă, fără niciun conținut executabil. Îl puteți restaura în
siguranță din carantină.

**Ce trebuie să faceți:**

1. **Opriți notificările** — excludeți directorul de instalare din antivirus
   (Avast: Setări → Excepții), adăugând calea globală `node_modules` și/sau directorul de
   date OmniRoute (`~/.omniroute/`).
2. **Raportați rezultatul fals pozitiv** — <https://www.avast.com/false-positive-file-form.php>,
   atașând fișierul `README.md` aflat în carantină. Aceasta este soluția care îi ajută pe toți, deoarece
   euristica furnizorului reacționează excesiv la un fișier text.

**De ce nu „remediem” acest lucru de partea noastră:** toate exemplele folosesc `http://localhost`, iar
localhost nu poate utiliza `https` fără complicațiile certificatelor autosemnate. Modificarea forțată a documentației
pentru a evita euristica unui singur furnizor ar afecta toți cititorii doar pentru a compensa o eroare a scanerului.

### Kaspersky semnalează aplicația desktop drept `PDM:Trojan.Win32.Generic`

**Acesta este un rezultat fals pozitiv al unei euristici comportamentale. Nimic nu este infectat.** Prefixul
`PDM:` al Kaspersky înseamnă că verdictul provine de la Proactive Defense Module (System Watcher),
care evaluează ce _face_ programul de instalare, în loc să îl compare cu programe malware cunoscute. Când
se declanșează, Kaspersky „revine” asupra întregii instalări — ștergând fișierele pe care le
scrisese deja — astfel încât aplicația ajunge să fie nefuncțională sau să lipsească.

Fișierele semnalate sunt componente standard ale unor dependențe open-source declarate, incluse împreună cu
aplicația desktop, de exemplu:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` și
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteca de automatizare a browserului
  utilizată pentru autentificarea în furnizori din aplicație și pentru chatul bazat pe browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — bindingul nativ `wreq-js` cu versiune fixată, utilizat pentru solicitări HTTP cu amprentă de browser în cazul furnizorilor
  bazați pe cookie-uri web (`<arch>` este `x64` sau `arm64`).

**De ce se declanșează:** programul de instalare pentru Windows **nu este încă semnat cu un certificat de cod**, astfel încât un program de
instalare NSIS nesemnat are reputație zero, iar euristicile comportamentale rulează la agresivitate maximă. Împreună
cu un DLL nativ inclus și sute de fișiere `.js` scrise în
`%LOCALAPPDATA%\Programs\OmniRoute` (inclusiv directoare de pachete cu sufixuri hash din versiunea
autonomă Next.js), acest lucru este suficient pentru a declanșa euristica. Semnarea codului este planificată;
până la implementarea ei, problema poate reapărea la versiunile noi.

**Ce trebuie să faceți:**

1. **Verificați mai întâi fișierul descărcat** (pentru a exclude posibilitatea ca fișierul să fi fost modificat). Fiecare versiune publică
   `latest.yml`, al cărui câmp `sha512` (base64) acoperă programul de instalare
   `OmniRoute.Setup.<version>.exe`. În PowerShell, din directorul care conține programul de instalare:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Rezultatul trebuie să corespundă cu `latest.yml` → `sha512`. Dacă nu corespunde, ștergeți fișierul și
   descărcați-l din nou numai de pe [pagina de versiuni GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaurați + excludeți** — restaurați din carantină elementele eliminate prin revenire și adăugați o excludere
   pentru `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Setări → Amenințări și excluderi),
   apoi reinstalați.
3. **Raportați rezultatul fals pozitiv** — <https://opentip.kaspersky.com/>. Rapoartele FP
   trimise de utilizatori accelerează în mod real includerea pe lista de permisiuni.

## Compatibilitate cu Node.js

<a name="nodejs-compatibility"></a>

### Pagina de autentificare se blochează sau afișează eroarea „Module self-registration”

**Cauză:** Rulați o versiune Node.js care nu respectă limita minimă aprobată de OmniRoute pentru un mediu de execuție securizat. Cel mai frecvent caz este utilizarea unei versiuni patch mai vechi de Node 22 sau 24, aflată sub limita minimă de securitate impusă de OmniRoute.

**Simptome:**

- Pagina de autentificare afișează un ecran gol sau o eroare de server
- Consola afișează `Error: Module did not self-register` sau erori similare privind legăturile native
- Pagina de autentificare afișează un **banner portocaliu de avertizare** cu versiunea dvs. de Node dacă mediul de execuție nu respectă politica securizată acceptată

**Remediere:**

1. Instalați o versiune LTS Node.js acceptată (recomandat: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verificați versiunea: `node --version` trebuie să afișeze `v24.0.0` sau o versiune mai nouă din seria LTS 24.x
3. Reinstalați OmniRoute: `npm install -g omniroute`
4. Reporniți: `omniroute`

> **Versiuni securizate acceptate:** `>=22.22.2 <23` sau `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) și Node.js 26 sunt acceptate integral.

### npm v11+: `better-sqlite3` nu este instalat (modulul nu poate fi găsit)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Cauză:** npm v11 (inclus cu Node.js 24+) blochează implicit scripturile de instalare pentru dependențele
opționale. Deoarece `better-sqlite3` este inclus în `optionalDependencies`
și necesită compilare nativă (`node-gyp rebuild`), npm îl omite fără a afișa un mesaj.

**Simptome:**

- Serverul se blochează la pornire cu `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` afișează „No such file or directory”
- `npm ls better-sqlite3` afișează `(empty)`

**Remediere:**

1. Aprobați scripturile de instalare și reinstalați:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Sau instalați manual pachetul precompilat:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verificați dacă funcționează: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**Cauză:** După o instalare globală cu `npm install -g omniroute`, este posibil ca binarul nativ `better-sqlite3` din interiorul pachetului să fi fost compilat pentru o arhitectură sau un ABI Node.js diferit de cel care rulează local. Acest lucru este frecvent pe macOS (atât pe Apple Silicon, cât și pe Intel) atunci când binarul precompilat nu corespunde mediului dvs.

**Simptome:**

- Serverul eșuează imediat la pornire cu o eroare `dlopen`
- Eroarea conține `slice is not valid mach-o file`
- Exemplu complet:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Remediere — recompilați pentru mediul dvs. local (nu este necesară revenirea la o versiune mai veche de Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Notă:** Această operație recompilează legătura nativă pentru versiunea locală de Node.js și arhitectura procesorului dvs., rezolvând incompatibilitatea binară. Intervalul de versiuni acceptat oficial pentru mediul de execuție este **`>=22.22.2 <23` sau `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` în `src/shared/utils/nodeRuntimeSupport.ts`, aliniat cu câmpul `engines` din `package.json`). Node.js 24.x LTS (Krypton) și Node.js 26 sunt acceptate integral cu `better-sqlite3` v12.x.

## Probleme cu proxy-ul

<a name="proxy-issues"></a>

### Validarea furnizorului afișează „fetch failed”

**Cauză:** Endpointul de validare a cheii API (`POST /api/providers/validate`) ocolea anterior configurația proxy, provocând erori în mediile care necesită rutare prin proxy.

**Remediere (v3.5.5+):** Problema este acum remediată. Validarea furnizorului este rutată prin `runWithProxyContext`, respectând automat setările proxy globale și cele de la nivelul furnizorului.

### Verificarea stării tokenului eșuează cu „fetch failed”

**Cauză:** Reîmprospătarea în fundal a tokenului OAuth nu determina configurația proxy pentru fiecare conexiune.

**Remediere (v3.5.5+):** Planificatorul verificării stării tokenurilor determină acum configurația proxy pentru fiecare conexiune înainte de a încerca reîmprospătarea. Actualizați la v3.5.5+.

### Proxy-ul SOCKS5 returnează „invalid onRequestStart method”

**Cauză:** În Node.js 22, dispecerul undici@8 este incompatibil cu implementarea `fetch()` încorporată în Node.

**Remediere (v3.5.5+):** OmniRoute utilizează acum funcția `fetch()` proprie a undici atunci când este activ un dispecer proxy, asigurând un comportament consecvent. Actualizați la v3.5.5+.

### Proxy MITM în WSL: aplicațiile desktop de pe gazda Windows nu sunt interceptate

**Cauză:** Proxy-ul MITM și certificatul său CA sunt instalate în mediul în care rulează OmniRoute. În WSL, acel mediu este sistemul Linux invitat, în timp ce aplicațiile AI desktop (Kiro, Trae, Copilot, Zed, …) rulează pe gazda Windows. Aplicațiile de pe gazdă nu acordă încredere depozitului de certificate al sistemului invitat și nu își rutează traficul prin proxy-ul de sistem al acestuia, astfel încât interceptarea aplicațiilor desktop nu se activează acolo.

**Recomandare:** Rulați OmniRoute nativ pe același sistem de operare ca aplicațiile desktop pe care doriți să le interceptați (Windows pentru aplicațiile Windows; în mod similar pentru macOS/Linux). Păstrarea OmniRoute în WSL în timp ce vizați aplicații de pe gazdă necesită să acordați manual încredere certificatului CA generat pe gazda Windows și să configurați setările de rețea/proxy ale fiecărei aplicații de pe gazdă astfel încât să utilizeze endpointul proxy WSL — o configurație neacceptată oficial și fragilă.

## Probleme cu furnizorii

### „Language model did not provide messages”

**Cauză:** Cota furnizorului a fost epuizată.

**Remediere:**

1. Verificați indicatorul cotei din panoul de control
2. Utilizați o combinație cu niveluri de rezervă
3. Treceți la un nivel mai ieftin/gratuit

### Limitarea ratei

**Cauză:** Cota abonamentului a fost epuizată.

**Remediere:**

- Adăugați o variantă de rezervă: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Utilizați GLM/MiniMax ca alternativă de rezervă ieftină

### Token OAuth expirat

OmniRoute reîmprospătează automat tokenurile. Dacă problemele persistă:

1. Panou de control → Furnizor → Reconectați
2. Ștergeți și adăugați din nou conexiunea furnizorului

### Mai multe conturi Kiro: al doilea cont îl invalidează pe primul

**Cauză:** Backendul Kiro impune o singură sesiune activă pentru fiecare înregistrare de client OIDC.
Atunci când două conturi folosesc același client înregistrat (conexiuni importate înainte de v3.8.0),
reîmprospătarea tokenului unui cont invalidează tokenul de reîmprospătare al celuilalt.

**Remediere (v3.8.0+):** Reimportați conexiunile afectate.
Începând cu v3.8.0, fiecare conexiune Kiro nouă creată prin **Importare token**,
**autentificare socială Google/GitHub** sau **Importare automată** își înregistrează automat
propriul client OIDC dedicat. Prin urmare, conexiunea este complet izolată, iar reîmprospătarea unui
cont nu afectează niciun alt cont.

Conexiunile importate _înainte_ de v3.8.0 nu includ o înregistrare de client
specifică fiecărei conexiuni. Aceste conexiuni continuă să utilizeze endpointul partajat de reîmprospătare pentru autentificarea socială.
Pentru a beneficia de izolare, ștergeți conexiunea veche din Panou de control → Furnizori și adăugați-o din nou
prin oricare dintre cele trei fluxuri de import.

Pentru detalii complete și instrucțiuni pas cu pas privind adăugarea simultană a două conturi Kiro,
consultați [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Probleme cu serviciul cloud

### Erori de sincronizare cu serviciul cloud

1. Verificați dacă `BASE_URL` indică instanța care rulează (de ex., `http://localhost:20128`)
2. Verificați dacă `CLOUD_URL` indică endpointul cloud (de ex., `https://omniroute.dev`)
3. Mențineți valorile `NEXT_PUBLIC_*` aliniate cu valorile de pe server

### `stream=false` în cloud returnează 500

**Simptom:** `Unexpected token 'd'...` pe endpointul cloud pentru apelurile fără streaming.

**Cauză:** Serviciul upstream returnează un payload SSE, în timp ce clientul așteaptă JSON.

**Soluție temporară:** Utilizați `stream=true` pentru apelurile directe către serviciul cloud. Mediul local de execuție include o soluție de rezervă SSE→JSON.

### Serviciul cloud indică o conexiune activă, dar afișează „Invalid API key”

1. Creați o cheie nouă din panoul de control local (`/api/keys`)
2. Rulați sincronizarea cu serviciul cloud: Activați Cloud → Sincronizați acum
3. Cheile vechi/nesincronizate pot returna în continuare `401` în cloud

## Probleme cu Docker

### IPv6 Docker / Resetarea conexiunii

<a name="docker-ipv6"></a>

**Simptome:** `curl http://localhost:20128/v1/models` returnează `curl: (56) Recv failure: Connection reset by peer`. Panoul de control și endpointurile neautentificate funcționează, dar endpointurile autentificate eșuează — pare a fi o problemă de autentificare, dar nu este.

**Cauză:** `docker run -p 20128:20128` publică atât pe `0.0.0.0` (IPv4), cât și pe `::` (IPv6), dar procesul din container ascultă numai pe IPv4. Pe gazdele unde `localhost` se rezolvă mai întâi la `::1`, conexiunea ajunge la portul IPv6 publicat, fără un serviciu care să asculte în spatele acestuia → conexiunea este resetată.

**Remediere:**

1. **Diagnostic rapid:** Rulați `curl -4 http://localhost:20128/v1/models`. Dacă funcționează cu `-4`, dar eșuează fără acesta, există o nepotrivire de asociere IPv6.
2. **Remediere permanentă:** Asociați explicit adresa IPv4 utilizând `-p 127.0.0.1:20128:20128` în comanda `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Aceasta forțează asocierea IPv4 și evită, de asemenea, expunerea proxy-ului pe toate interfețele gazdei.

### Instrumentul CLI apare ca neinstalat

1. Verificați câmpurile mediului de execuție: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. Pentru modul portabil: utilizați ținta de imagine `runner-cli` (CLI-uri incluse)


## Depanarea traducătorului

Utilizați **Tablou de bord → Traducător** pentru a depana problemele de traducere între formate:

| Mod                           | Când se utilizează                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Spațiu de testare**         | Comparați alăturat formatele de intrare și ieșire — inserați o solicitare care eșuează pentru a vedea cum este tradusă |
| **Tester de chat**            | Trimiteți mesaje în timp real și inspectați conținutul complet al solicitării/răspunsului, inclusiv antetele           |
| **Banc de testare**           | Rulați teste în lot pentru diverse combinații de formate, pentru a identifica traducerile defecte                      |
| **Monitorizare în timp real** | Urmăriți fluxul solicitărilor în timp real pentru a detecta problemele de traducere intermitente                       |

### Probleme frecvente de format

- **Etichetele de raționament nu apar** — Verificați dacă furnizorul țintă acceptă raționamentul și setarea bugetului de raționament
- **Apelurile instrumentelor dispar** — Unele traduceri între formate pot elimina câmpurile neacceptate; verificați în modul Spațiu de testare
- **Promptul de sistem lipsește** — Claude și Gemini gestionează diferit prompturile de sistem; verificați rezultatul traducerii
- **SDK-ul returnează un șir brut în locul unui obiect** — Rezolvat în v1.x; mecanismul de igienizare a răspunsurilor elimină câmpurile nestandard (`x_groq`, `usage_breakdown` etc.) care provoacă eșecuri de validare Pydantic în SDK-ul OpenAI. Dacă problema persistă în v3.x+, vă rugăm să o raportați.
- **GLM/ERNIE respinge rolul `system`** — Rezolvat în v1.x; normalizatorul de roluri combină automat mesajele de sistem cu mesajele utilizatorului pentru modelele incompatibile. Dacă problema persistă în v3.x+, vă rugăm să o raportați.
- **Rolul `developer` nu este recunoscut** — Rezolvat în v1.x; este convertit automat în `system` pentru furnizorii care nu sunt OpenAI. Dacă problema persistă în v3.x+, vă rugăm să o raportați.
- **`json_schema` nu funcționează cu Gemini** — Rezolvat în v1.x; `response_format` este acum convertit în `responseMimeType` + `responseSchema` pentru Gemini. Dacă problema persistă în v3.x+, vă rugăm să o raportați.

## Setări de reziliență

### Limitarea automată a ratei nu se declanșează

- Limitarea automată a ratei se aplică numai furnizorilor cu cheie API (nu OAuth/abonament)
- Verificați dacă în **Settings → Resilience → Provider Profiles** este activată limitarea automată a ratei
- Verificați dacă furnizorul returnează coduri de stare `429` sau antete `Retry-After`

### Ajustarea revenirii exponențiale

Profilurile furnizorilor acceptă următoarele setări:

- **Întârziere de bază** — Timpul inițial de așteptare după prima eroare (implicit: 1s)
- **Întârziere maximă** — Limita maximă a timpului de așteptare (implicit: 30s)
- **Multiplicator** — Cât de mult crește întârzierea pentru fiecare eroare consecutivă (implicit: 2x)

### Prevenirea efectului de turmă

Când multe solicitări concurente ajung la un furnizor cu rata limitată, OmniRoute utilizează un mutex împreună cu limitarea automată a ratei pentru a serializa solicitările și a preveni erorile în cascadă. Acest proces este automat pentru furnizorii cu cheie API.

### Solicitările de chat eșuează cu 503 / chat_admission_busy

**Simptome:**

- Endpointul pentru completările de chat returnează un răspuns reîncercabil `503` al cărui cod de eroare este
  `chat_admission_busy`.
- Răspunsul include `Retry-After`. Începând cu #12135, valoarea este derivată din gradul de ocupare
  observat — valoarea cea mai mare dintre intervalul `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` deja
  așteptat de solicitare și durata pentru care au fost menținute alocările curente pentru sarcini grele — rotunjită în sus la
  secunde întregi și limitată la 60. Când mecanismul este inactiv, sunt păstrate valorile minime istorice: 2 secunde pe
  calea bazată pe octeți și 1 secundă pe calea bazată pe structură (care include și
  `reason: "structure_limit"`).
- Acest lucru se poate întâmpla cât timp un alt chat cu sarcină grea sau un răspuns de streaming de lungă durată este încă
  în curs.

Corpul răspunsului bazat pe octeți este:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Răspunsul bazat pe structură utilizează același tip și același cod, cu mesajul
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
și `reason: "structure_limit"`.
La pragurile implicite, o solicitare este considerată grea din punct de vedere structural atunci când are cel puțin `200` de mesaje,
cel puțin `64` de instrumente sau cel puțin `32,000` de tokenuri estimate ori când estimarea limitată a structurii
își epuizează limitele de `10,000` de noduri vizitate sau adâncimea `12`.

**Cauză:** Aceasta este o reducere deliberată a încărcării în OmniRoute, nu o eroare a furnizorului upstream.
Fiecare proces utilizează un mecanism de protecție local procesului pentru a rezerva o capacitate limitată pentru sarcini grele înainte de a păstra
și analiza corpul unei solicitări mari. O alocare pentru sarcini grele rămâne activă pe întreaga durată de viață a unui
răspuns SSE.

**Distribuirea în evantai a erorilor #503:** înainte de această remediere, mecanismul de protecție limita concurența la un NUMĂR fix de solicitări
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, implicit `1`), indiferent de memoria gazdei, astfel încât
distribuirea în evantai a agenților de programare (mai mulți subagenți/mai multe CLI-uri, corpuri în mod obișnuit > 256 KB) reducea concurența
efectivă la aproximativ 1 și genera erori 503 în condiții de încărcare complet normale. Acum mecanismul de protecție se ajustează
automat: este controlat de un buget de OCTEȚI pentru ingestie, derivat automat (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionat pe baza
limitei reale de memorie a procesului și consultă, de asemenea, un semnal în timp real privind presiunea asupra resurselor — astfel încât
reduce încărcarea numai când gazda se află cu adevărat sub presiunea memoriei, nu doar pentru că au sosit simultan mai multe
solicitări grele. Vechea limită numerică (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) este
în continuare respectată, dar numai dacă o setați explicit.

Când capacitatea este ocupată, o solicitare grea așteaptă mai întâi până la
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (implicit `RATE_LIMIT_MAX_WAIT_MS`; `0` dezactivează așteptarea) pentru eliberarea unui loc
înainte de a returna răspunsul reîncercabil `503`. Așteptarea limitată există astfel încât clienții de tip agent
(OpenCode, Claude Code, Cursor), care distribuie simultan în evantai subsolicitări grele, să serializeze rafala
în loc să își consume întregul buget de reîncercări pe respingeri imediate și să eșueze în timpul sarcinii.
Gradul curent de ocupare a alocărilor pentru sarcini grele, bugetul de octeți stabilit și severitatea presiunii în timp real sunt
expuse la `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — verificați-le înainte de a modifica orice variabilă de mediu.
Settings → Resilience → Request Queue → Concurrent Requests nu controlează acest mecanism; setarea respectivă
controlează un mecanism separat pentru coada de solicitări către furnizor.

**Remediere:**

1. Reîncercați mai întâi. Clienții trebuie să respecte `Retry-After` și să utilizeze revenirea graduală în loc să
   repete imediat solicitarea.
2. Verificați `/api/monitoring/health` → `chatAdmission` înainte de a ajusta ceva. `countCapEnabled:
false` și o valoare generoasă pentru `maxInflightBytes` înseamnă că bugetul derivat automat își îndeplinește deja
   rolul; o valoare `pressureSeverity` de `high`/`critical` înseamnă că gazda are într-adevăr puțină memorie disponibilă —
   acest lucru nu poate fi remediat printr-o variabilă de mediu pentru admitere, ci necesită mai multă memorie RAM sau o sarcină de lucru mai mică.
3. Numai dacă `/api/monitoring/health` arată că bugetul derivat automat este într-adevăr prea mic pentru
   gazda dvs. (situație rară — acesta se scalează deja de la containere la sisteme bare-metal), suprascrieți-l direct cu
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, în loc să reveniți la limita veche bazată pe numărul de solicitări.

Consultați [referința variabilelor de mediu](../reference/ENVIRONMENT.md#4-security--authentication)
pentru setările oficiale privind admiterea.

## Taxonomie opțională a erorilor RAG / LLM (16 probleme)

Unii utilizatori OmniRoute plasează gateway-ul în fața stivelor RAG sau de agenți. În aceste configurații, este frecvent întâlnit un tipar ciudat: OmniRoute pare să funcționeze corect (furnizorii sunt disponibili, profilurile de rutare sunt în regulă, nu există alerte privind limitele de solicitări), dar răspunsul final este totuși greșit.

În practică, aceste incidente provin de obicei din pipeline-ul RAG din aval, nu din gateway-ul propriu-zis.

Dacă doriți un vocabular comun pentru a descrie aceste erori, puteți utiliza WFGY ProblemMap, o resursă textuală externă cu licență MIT care definește șaisprezece tipare recurente de eroare RAG / LLM. La nivel general, aceasta acoperă:

- devierea regăsirii și limite de context defectuoase
- indexuri și baze de date vectoriale goale sau învechite
- neconcordanța dintre embeddings și semantică
- probleme privind asamblarea promptului și fereastra de context
- colaps logic și răspunsuri excesiv de încrezătoare
- erori ale lanțurilor lungi și ale coordonării agenților
- devierea memoriei și a rolurilor în sisteme multi-agent
- probleme privind ordinea de implementare și inițializare

Ideea este simplă:

1. Când investigați un răspuns necorespunzător, înregistrați:
   - sarcina și solicitarea utilizatorului
   - combinația de rute sau furnizori din OmniRoute
   - orice context RAG utilizat în aval (documente regăsite, apeluri de instrumente etc.)
2. Asociați incidentul cu unul sau două numere din WFGY ProblemMap (`No.1` … `No.16`).
3. Stocați numărul în propriul tablou de bord, ghid operațional sau sistem de urmărire a incidentelor, alături de jurnalele OmniRoute.
4. Utilizați pagina WFGY corespunzătoare pentru a decide dacă trebuie să modificați stiva RAG, mecanismul de regăsire sau strategia de rutare.

Textul complet și instrucțiunile concrete sunt disponibile aici (licență MIT, numai text):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Puteți ignora această secțiune dacă nu rulați pipeline-uri RAG sau de agenți în spatele OmniRoute.

## Probleme cunoscute în v3.8.0

Probleme specifice versiunii v3.8.0 și soluțiile lor temporare actuale. Dacă o remediere este inclusă într-un patch ulterior, înregistrarea va fi actualizată sau eliminată.

### Erori de autentificare Devin CLI

**Simptome:**

- „Devin CLI nu a fost găsit” sau „autentificarea a eșuat” la invocarea instrumentelor bazate pe Devin
- Verificarea CLI în timpul execuției raportează `installed=false`

**Cauze:**

- `CLI_DEVIN_BIN` indică o cale care nu există
- Devin CLI nu este instalat pe gazdă

**Remediere:**

1. Instalați Devin CLI pentru platforma dumneavoastră
2. Setați `CLI_DEVIN_BIN=/usr/local/bin/devin` (sau calea reală) în `.env`
3. Reporniți OmniRoute și testați din nou din **Tablou de bord → Instrumente CLI**

### Perioada de așteptare a modelului este blocată (resetare manuală)

**Simptome:**

- Un model rămâne afișat ca fiind în perioada de așteptare chiar și după expirarea acesteia
- Solicitările continuă să omită modelul în rutarea combinată, deși marcajul temporal este în trecut

**Resetare manuală:**

- **Tablou de bord:** **Setări → Perioade de așteptare ale modelelor** → faceți clic pe **Reactivați** pe cardul afectat
- **API:** `DELETE /api/resilience/model-cooldowns` cu antetele de autentificare pentru administrare

### Conexiunea la furnizorul Command Code eșuează cu 403

**Simptome:**

- Eroare 403 la testarea conexiunii cu furnizorul Command Code
- Cardul furnizorului afișează „neautorizat” după o adăugare nouă

**Cauză:** Fluxul OAuth nu s-a finalizat (callback-ul nu a fost primit sau tokenul nu a fost păstrat).

**Remediere:**

- Rulați `omniroute providers` din CLI pentru a declanșa din nou fluxul OAuth sau
- Rulați din nou OAuth din **Tablou de bord → Furnizori → Command Code → Reconectare**

### ModelScope returnează perioade de așteptare 429 agresive

**Simptome:**

- Perioade de așteptare foarte scurte sau imediate în ModelScope după un volum redus de solicitări
- Rutarea combinată omite ModelScope mai devreme decât era de așteptat

**Cauză:** ModelScope emite antete `Retry-After` specifice furnizorului. v3.8.0 include gestionare dedicată pentru aceste antete, astfel încât versiunile mai vechi le interpretează greșit drept indicii generice privind limitarea solicitărilor.

**Remediere:**

- Asigurați-vă că utilizați v3.8.0 sau o versiune ulterioară
- Verificați dacă opțiunea `useUpstream429BreakerHints` este activată în **Setări → Reziliență**

### OMNIROUTE_WS_BRIDGE_SECRET lipsește în producție

**Simptome:**

- Eroare 401 la fiecare solicitare către puntea WebSocket Codex/Responses atunci când aceasta rulează pe o gazdă de producție la distanță
- Negocierea conexiunii cu puntea WebSocket se închide imediat după conectare

**Cauză:** Variabila de mediu `OMNIROUTE_WS_BRIDGE_SECRET` lipsește din mediul de producție.

**Remediere:**

1. Generați un secret aleatoriu: `openssl rand -hex 32`
2. Setați `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` în mediul serverului de producție (și în orice client care comunică cu puntea)
3. Reporniți OmniRoute

### Responses API: modul de fundal a fost retrogradat la execuție sincronă

**Simptome:**

- Avertisment înregistrat în jurnal: `background mode degraded to synchronous`
- O solicitare `background: true` returnează un răspuns sincron obișnuit în locul unui identificator pentru o activitate de fundal

**Cauză:** v3.8.0 retrogradează intenționat `background: true` în Responses API la execuție sincronă și emite în același timp un avertisment. Execuția asincronă completă în fundal este planificată pentru viitor.

**Remediere:**

- Ajustați clientul pentru a efectua apelul fără `background` sau
- Așteptați o versiune ulterioară care include modul de fundal complet asincron (urmăriți jurnalul de modificări)

## Pornire lentă / Expirarea timpului de așteptare pentru disponibilitate

Dacă CLI-ul afișează `⚠ Server did not respond within 60s`, dar serverul
funcționează de fapt, intervalul alocat verificării disponibilității este prea scurt pentru mediul dvs.

Acest lucru se întâmplă frecvent pe Windows (antivirus, monitoare ale sistemului de fișiere) sau în containere
cu sarcini de lucru intense la pornire.

**Remediere — măriți intervalul alocat:**

```bash
# Prin variabila de mediu (se păstrează între porniri):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minute
omniroute serve

# Prin opțiunea CLI (o singură utilizare):
omniroute serve --ready-timeout 180000
```

Valoarea implicită este de 60 000 ms (60 s). Avertismentul are doar caracter informativ; serverul
continuă să pornească în fundal și va deveni accesibil după finalizarea pornirii.

Consultați [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) pentru detalii
complete despre `OMNIROUTE_READY_TIMEOUT_MS`.
