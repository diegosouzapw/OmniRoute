## Referință rapidă

**Folosiți OmniRoute pentru prima dată?** Începeți aici — acestea rezolvă 90% dintre probleme:

| Vedeți acest mesaj                     | Ce înseamnă                                    | Ce trebuie să faceți                                                                                 |
| -------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| „Nu se poate realiza conexiunea”       | OmniRoute nu rulează                           | Rulați `omniroute` sau `docker restart omniroute`                                                    |
| „Cheie API nevalidă”                   | Cheia este greșită sau a expirat               | Copiați din nou cheia de pe site-ul furnizorului                                                     |
| „Limita de solicitări a fost depășită” | Trimiteți prea multe solicitări                | Așteptați 1 minut sau folosiți `model: "auto"` pentru comutare automată                              |
| „Cota a fost depășită”                 | Ați epuizat cota gratuită/plătită              | Conectați mai mulți furnizori sau folosiți furnizori gratuiți (Kiro, Pollinations)                   |
| „Răspunsuri lente”                     | Furnizorul este ocupat sau se află la distanță | Folosiți `model: "auto/fast"` sau conectați un furnizor mai rapid (Groq, Cerebras)                   |
| „A fost utilizat furnizorul greșit”    | `auto` a ales alt furnizor                     | Este normal! `auto` îl alege pe cel mai bun. Impuneți un anumit furnizor cu `model: "openai/gpt-4o"` |
| „502 Bad Gateway”                      | Furnizorul nu este disponibil                  | Așteptați și încercați din nou sau folosiți `model: "auto"` pentru a schimba furnizorii              |
| „401 Unauthorized”                     | Datele de autentificare sunt greșite           | Verificați cheia API sau autentificați-vă din nou cu OAuth                                           |
| „omniroute nu este recunoscut”         | Din Windows PATH lipsesc modulele node globale | Adăugați prefixul npm global în Windows PATH. Aflați-l cu `npm config get prefix`.                   |
| „429 Too Many Requests”                | S-a aplicat o limită de solicitări             | Așteptați 1 minut sau conectați mai mulți furnizori                                                  |

**Problema persistă?** Consultați secțiunea de [depanare detaliată](#detailed-troubleshooting) de mai jos sau solicitați ajutor pe [Discord](https://discord.gg/U47eFqAXCn).

### Limitarea solicitărilor la furnizorii gratuiți (429 / 400 / 401)

**Simptom**: Atunci când folosiți `model: "auto"` cu furnizori gratuiți/fără autentificare (opencode, auggie etc.), primiți intermitent `HTTP 429`, `400` sau `401` în locul răspunsurilor. Solicitările reușesc când încercați din nou aceeași cerere câteva momente mai târziu, însă automatizările (sarcini cron, agenți, scripturi) se întrerup la prima eroare.

**Cauza principală**: Se cumulează trei moduri independente de producere a erorilor:

1. **Limitarea solicitărilor de către furnizor (`429`)**: Nivelurile gratuite pot impune o cotă pentru fiecare interval de timp. O rafală de apeluri paralele o epuizează, astfel încât următoarea solicitare este refuzată până la resetarea intervalului.
2. **Model nefuncțional în modul passthrough (`400`/`401`)**: Grupurile `auto/*` pot include modele passthrough de la `opencode` care sunt înregistrate în catalog, dar nu au date de autentificare active (de exemplu, `oc/north-mini-code-free` → `401`). Routerul automat încearcă unul dintre acestea, solicitarea eșuează, iar eroarea este propagată înainte de activarea mecanismului de rezervă.
3. **Amplificarea concurenței (`429` sub sarcină)**: Când mai multe sesiuni de agent/cron accesează simultan `auto`, rata cumulată a solicitărilor depășește nivelul tolerat de furnizorii gratuiți, astfel încât apelurile legitime sunt marcate drept abuzive.

**Remediere verificată (raportată de comunitate, 2026-08-10)**: configurați trei variabile de mediu, astfel încât rotația, concurența și mecanismul de rezervă să absoarbă fluctuațiile nivelului gratuit, în loc să eșueze din cauza lor:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # trece la alt model/furnizor la 400/401 (omite modelele passthrough nefuncționale)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # limită explicită de admitere pentru solicitările complexe (implicit nesetată: fără limită privind numărul solicitărilor; consultați nota de mai jos)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # așteptare limitată mai lungă pentru capacitatea solicitărilor complexe, în locul unei erori 503 imediate care permite reîncercarea
```

Setați aceste variabile în mediul procesului OmniRoute (daemonul, de exemplu prin fișierul plist LaunchAgent sau `systemctl edit`), apoi reporniți OmniRoute. Indicatorul de rotație este opțiunea cu cel mai mare impact: transformă o eroare definitivă într-o reîncercare transparentă prin intermediul unui furnizor funcțional din grup.

**Notă**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limitează numărul de solicitări complexe — cu context lung — care rulează simultan; limita reprezintă un mecanism de admitere, nu un limitator al solicitărilor furnizorului. **Actualizare #503-fanout:** această variabilă nu mai este setată implicit (acum se aplică doar când este configurată explicit, ca mai sus) — admiterea solicitărilor complexe este controlată în schimb de un buget de octeți derivat automat (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), care se ajustează în funcție de limita reală de memorie a gazdei, astfel încât o instalare nouă ar trebui să întâmpine mult mai puține respingeri `503 chat_admission_busy` fără a seta deloc această variabilă; setarea explicită prezentată aici continuă să funcționeze exact conform documentației. Suprascrierile explicite ale bugetului de octeți sunt limitate la intervalul 8 MiB–2 GiB. O eroare `413 body_exceeds_budget` nu este tranzitorie: măriți bugetul de octeți, reduceți `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` sau măriți limita de memorie a procesului. O degrevare `inflight_bytes_budget` reprezintă o concurență temporară pentru resurse și permite în continuare reîncercarea. Limitarea solicitărilor pentru fiecare furnizor (`open-sse/services/rateLimitManager.ts`) este controlată separat prin `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` și `RATE_LIMIT_AUTO_ENABLE` — consultați `.env.example`.

**Cum să verificați că a funcționat**: rulați agentul/jobul cron de două ori în succesiune rapidă și confirmați că ambele rulări reușesc. Înainte de remediere, a doua rulare generează de obicei `429`/`401`. După remediere, încercările nereușite (dacă există) sunt reluate în mod transparent, iar apelul se finalizează. De asemenea, puteți rula `curl /monitoring/health` și urmări câmpul `rateLimitedUntil` din conexiunile furnizorilor și `circuitBreakers.providerBreakers[].state` pentru furnizorii afectați — starea este una dintre `CLOSED`, `DEGRADED`, `OPEN` sau `HALF_OPEN` (consultați `src/shared/utils/circuitBreaker.ts`), iar un furnizor care continuă să eșueze va trece prin `CLOSED → DEGRADED → OPEN` înainte ca intervalul de resetare să permită trecerea unei solicitări de testare (`HALF_OPEN`).

**Dacă vedeți în continuare 429**: contul activ pentru furnizorul respectiv și-a epuizat efectiv _cota_ (nu doar limita de frecvență). Adăugați un al doilea cont pentru același furnizor în tabloul de bord OmniRoute → Providers → Accounts sau includeți un alt furnizor gratuit (de exemplu, `routeway`, `auggie`). Rotația ajută doar în cazul erorilor tranzitorii de limitare a frecvenței/400/401; epuizarea completă a cotei necesită un al doilea set de credențiale sau un alt furnizor.

**Dacă vedeți 403 pentru modelele de viziune (`auto/vision`, `bazaarlink/*`)**: contul conectat nu dispune de un plan plătit care include funcționalități de viziune sau cheia API nu are permisiuni suficiente. Verificați în tabloul de bord al furnizorului dacă domeniul de acces al cheii include funcționalități de viziune/multimodale sau conectați un cont cu abonament plătit și păstrați-l ca destinație pentru solicitările de viziune.

## Avertismente la npm install (ERESOLVE / peer / deprecated)

Când rulați `npm install -g omniroute`, este posibil să vedeți o mulțime de avertismente precum `npm warn ERESOLVE`, notificări privind dependențele peer și mesaje `deprecated`. **Acestea sunt de așteptat și nu prezintă niciun pericol.** Instalarea a reușit dacă vedeți `added <N> packages` în rezultat.

Pentru a suprima avertismentele privind rezolvarea dependențelor peer, utilizați forma de instalare acceptată de OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` suprimă doar notificările `ERESOLVE` și cele privind dependențele peer. Notificările de perimare rămân vizibile deoarece provin din pachete terțe tranzitive; acestea nu indică faptul că instalarea a eșuat.

Avertismentele provin din intervale învechite pentru dependențele peer din pachete terțe pe care OmniRoute nu le controlează:

1. **`marked-terminal` necesită `marked >=1 <16`, dar a fost găsit `marked@18`** — funcționează bine în practică; intervalul peer din proiectul sursă este pur și simplu învechit.
2. **`deprecated prebuild-install@7.1.3`** — un utilitar tranzitiv pentru preluarea fișierelor binare native. Acesta nu este
   utilizat pentru a instala binding-ul de transport `wreq-js` fixat la o anumită versiune și nu indică faptul că configurarea transportului
   pentru furnizorul de cookie-uri web a eșuat.

**Nu este necesară nicio acțiune** — avertismentele nu pot fi suprimate complet fără a crea fork-uri ale pachetelor sursă.

## Gemini Web și Playwright Chromium

Dacă o solicitare Gemini Web returnează `503` cu un mesaj conform căruia Playwright Chromium
nu este instalat, pachetul npm este prezent, dar fișierul binar al browserului lipsește.
Playwright menține în mod deliberat descărcările browserului separate de instalarea
pachetului npm, astfel că acest răspuns este de așteptat până când browserul este instalat.

Pentru o instalare npm globală, instalați Chromium din directorul pachetului
OmniRoute, astfel încât memoria cache a browserului să aparțină aceleiași instalări Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Reporniți OmniRoute după instalare, apoi reîncercați solicitarea Gemini Web. Dacă
rulați OmniRoute dintr-o imagine Docker, utilizați imaginea `-web` (sau ținta de compilare
`runner-web`), care include Chromium și dependențele sale; imaginea de bază nu
le include.

## Remedieri rapide

| Problemă                                                   | Soluție                                                                                                                                                                           |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prima autentificare nu funcționează                        | Setați `INITIAL_PASSWORD` în `.env` (fără valoare implicită codificată direct)                                                                                                    |
| Panoul de control se deschide pe portul greșit             | Setați `PORT=20128` și `NEXT_PUBLIC_BASE_URL=http://localhost:20128`                                                                                                              |
| Nu sunt scrise jurnale pe disc                             | Setați `APP_LOG_TO_FILE=true` și verificați dacă este activată capturarea jurnalului apelurilor                                                                                   |
| EACCES: permisiune refuzată                                | Setați `DATA_DIR=/path/to/writable/dir` pentru a suprascrie `~/.omniroute`                                                                                                        |
| Strategia de rutare nu este salvată                        | Actualizați la cea mai recentă versiune v3.x (remedierea schemei Zod pentru persistența setărilor a fost inclusă în versiunile anterioare)                                        |
| Blocare la autentificare / pagină goală                    | Verificați versiunea Node.js — consultați mai jos [Compatibilitatea Node.js](#nodejs-compatibility)                                                                               |

## Rezultate fals pozitive ale antivirusului

<a name="antivirus-false-positives"></a>

### Avast/AVG pune în carantină `README.md` cu `MD:HttpRequest-inf[Susp]`

**Acesta este un rezultat fals pozitiv. Nimic nu este infectat și nu este necesară nicio acțiune.**

Avast și AVG rulează o euristică ce semnalează fișiere text simplu/Markdown care conțin multe
linkuri ce par a fi cereri HTTP. Fișierul `README.md` al OmniRoute este inclus în pachetul npm (este
listat în `package.json` → `files`), astfel că, la o instalare globală, ajunge în `node_modules/omniroute/README.md`
— și conține aproximativ 15 exemple `http://localhost:20128/...` (endpointurile HTTP/SSE
MCP, URL-ul A2A `.well-known` și fragmente `curl`). Această densitate a linkurilor este
suficientă pentru a declanșa euristica.

Dacă acest lucru a început abia recent: tipul fișierului nu s-a schimbat. Tabelul de
endpointuri din README a fost extins (au fost adăugate MCP HTTP + SSE + A2A), precum și mai multe
exemple `curl`, ceea ce a făcut ca fișierul să depășească pragul.

Fișierul este o documentație inertă, fără niciun conținut executabil. Îl puteți restaura
în siguranță din carantină.

**Ce trebuie să faceți:**

1. **Opriți notificările** — excludeți directorul de instalare din antivirus
   (Avast: Settings → Exceptions), adăugând calea globală către `node_modules` și/sau
   directorul de date OmniRoute (`~/.omniroute/`).
2. **Raportați rezultatul fals pozitiv** — <https://www.avast.com/false-positive-file-form.php>,
   atașând fișierul `README.md` aflat în carantină. Aceasta este remedierea care îi ajută pe toți, deoarece
   euristica furnizorului reacționează excesiv la un fișier text.

**De ce nu „remediem” acest lucru de partea noastră:** toate exemplele folosesc `http://localhost`, iar
localhost nu poate utiliza `https` fără inconvenientele certificatelor autosemnate. Denaturarea documentației pentru
a evita euristica unui singur furnizor ar afecta fiecare cititor doar pentru a compensa o eroare a scanerului.

### Kaspersky semnalează aplicația Desktop drept `PDM:Trojan.Win32.Generic`

**Acesta este un rezultat fals pozitiv provenit de la o euristică bazată pe comportament. Nimic nu este infectat.** Prefixul
`PDM:` al Kaspersky înseamnă că verdictul provine de la Proactive Defense Module (System Watcher),
care evaluează ceea ce _face_ programul de instalare, în loc să îl compare cu programe malware cunoscute. Când
se declanșează, Kaspersky „anulează” întreaga instalare — ștergând fișierele pe care le scrisese deja
— astfel că aplicația ajunge să fie defectă sau să lipsească.

Fișierele pe care le semnalează sunt componente standard ale dependențelor open-source declarate și incluse în
aplicația desktop, de exemplu:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` și
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteca de automatizare a browserului
  utilizată pentru autentificarea în aplicație la furnizori și pentru chatul bazat pe browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — componenta nativă fixată la o versiune specifică `wreq-js`, utilizată pentru HTTP cu amprentă de browser în cazul furnizorilor
  bazați pe cookie-uri web (`<arch>` este `x64` sau `arm64`).

**De ce se declanșează:** programul de instalare pentru Windows **nu este încă semnat digital**, astfel că un program de
instalare NSIS nesemnat nu are nicio reputație, iar euristicile comportamentale rulează la agresivitate maximă. Împreună
cu un DLL nativ inclus și sute de fișiere `.js` scrise în
`%LOCALAPPDATA%\Programs\OmniRoute` (inclusiv directoare de pachete cu sufixuri hash provenite din
versiunea standalone Next.js), acest lucru este suficient pentru a declanșa euristica. Semnarea codului este planificată;
până la implementarea acesteia, problema se poate repeta la noile versiuni.

**Ce trebuie să faceți:**

1. **Verificați mai întâi fișierul descărcat** (pentru a exclude posibilitatea ca acesta să fi fost modificat). Fiecare versiune publică
   `latest.yml`, al cărui câmp `sha512` (base64) acoperă programul de instalare
   `OmniRoute.Setup.<version>.exe`. În PowerShell, din folderul care conține programul de instalare:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Rezultatul trebuie să corespundă valorii `latest.yml` → `sha512`. Dacă nu corespunde, ștergeți fișierul și
   descărcați-l din nou numai de pe [pagina de versiuni GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaurați + excludeți** — restaurați din carantină elementele eliminate prin anularea instalării și adăugați o excludere
   pentru `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Settings → Threats and Exclusions),
   apoi reinstalați.
3. **Raportați rezultatul fals pozitiv** — <https://opentip.kaspersky.com/>. Rapoartele privind rezultate fals pozitive
   trimise de utilizatori accelerează în mod real includerea pe lista de permisiuni.

## Compatibilitate cu Node.js

<a name="nodejs-compatibility"></a>

### Pagina de autentificare se blochează sau afișează eroarea „Module self-registration”

**Cauză:** Rulați o versiune Node.js care nu respectă limita minimă aprobată de OmniRoute pentru un mediu de execuție securizat. Cel mai frecvent caz este utilizarea unei versiuni de corecție Node 22 sau 24 mai vechi decât nivelul minim cu remedieri de securitate impus de OmniRoute.

**Simptome:**

- Pagina de autentificare afișează un ecran gol sau o eroare de server
- Consola afișează `Error: Module did not self-register` sau erori similare privind legăturile native
- Pagina de autentificare afișează un **banner portocaliu de avertizare** cu versiunea dvs. de Node dacă mediul de execuție nu respectă politica de securitate acceptată

**Remediere:**

1. Instalați o versiune LTS de Node.js acceptată (recomandat: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verificați versiunea: `node --version` trebuie să afișeze `v24.0.0` sau o versiune mai nouă din seria LTS 24.x
3. Reinstalați OmniRoute: `npm install -g omniroute`
4. Reporniți: `omniroute`

> **Versiuni securizate acceptate:** `>=22.22.2 <23` sau `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) și Node.js 26 sunt acceptate integral.

### npm v11+: `better-sqlite3` nu este instalat (modulul nu poate fi găsit)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Cauză:** npm v11 (inclus în Node.js 24+) blochează implicit scripturile de instalare pentru dependențele opționale. Deoarece `better-sqlite3` este listat în `optionalDependencies` și necesită compilare nativă (`node-gyp rebuild`), npm îl omite fără a afișa o eroare.

**Simptome:**

- Serverul se blochează la pornire cu mesajul `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` afișează „No such file or directory”
- `npm ls better-sqlite3` afișează `(empty)`

**Remediere:**

1. Aprobați scripturile de instalare și reinstalați:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Sau instalați manual pachetul precompilat:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verificați dacă funcționează: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**Cauză:** După o instalare globală cu `npm install -g omniroute`, este posibil ca fișierul binar nativ `better-sqlite3` din pachet să fi fost compilat pentru o arhitectură sau un ABI Node.js diferit de cel care rulează local. Acest lucru este frecvent pe macOS (atât pe Apple Silicon, cât și pe Intel) atunci când fișierul binar precompilat nu corespunde mediului dvs.

**Simptome:**

- Serverul eșuează imediat la pornire cu o eroare `dlopen`
- Eroarea conține `slice is not valid mach-o file`
- Exemplu complet:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Remediere — recompilați pentru mediul dvs. local (nu este necesară trecerea la o versiune Node.js mai veche):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Notă:** Această operațiune recompilează legătura nativă pentru versiunea dvs. locală de Node.js și arhitectura procesorului, rezolvând incompatibilitatea fișierului binar. Intervalul de versiuni acceptat oficial este **`>=22.22.2 <23` sau `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` în `src/shared/utils/nodeRuntimeSupport.ts`, aliniat cu câmpul `engines` din `package.json`). Node.js 24.x LTS (Krypton) și Node.js 26 sunt acceptate integral cu `better-sqlite3` v12.x.

## Probleme cu proxy-ul

<a name="proxy-issues"></a>

### Validarea furnizorului afișează „fetch failed”

**Cauză:** Endpointul de validare a cheii API (`POST /api/providers/validate`) ocolea anterior configurația proxy-ului, provocând erori în mediile care necesită rutarea prin proxy.

**Remediere (v3.5.5+):** Această problemă este acum rezolvată. Validarea furnizorului este rutată prin `runWithProxyContext`, respectând automat setările proxy globale și cele de la nivelul furnizorului.

### Verificarea stării tokenului eșuează cu „fetch failed”

**Cauză:** Reîmprospătarea în fundal a tokenului OAuth nu determina configurația proxy pentru fiecare conexiune.

**Remediere (v3.5.5+):** Planificatorul verificării stării tokenului determină acum configurația proxy pentru fiecare conexiune înainte de a încerca reîmprospătarea. Actualizați la v3.5.5+.

### Proxy-ul SOCKS5 returnează „invalid onRequestStart method”

**Cauză:** În Node.js 22, dispecerul undici@8 este incompatibil cu implementarea `fetch()` încorporată în Node.

**Remediere (v3.5.5+):** OmniRoute utilizează acum funcția `fetch()` proprie a undici atunci când este activ un dispecer proxy, asigurând un comportament consecvent. Actualizați la v3.5.5+.

### Proxy MITM în WSL: aplicațiile desktop de pe gazda Windows nu sunt interceptate

**Cauză:** Proxy-ul MITM și certificatul său CA sunt instalate în mediul în care rulează OmniRoute. În WSL, acel mediu este sistemul Linux invitat, în timp ce aplicațiile desktop AI (Kiro, Trae, Copilot, Zed, …) rulează pe gazda Windows. Aplicațiile de pe gazdă nu acordă încredere depozitului de certificate al sistemului invitat și nu își rutează traficul prin proxy-ul de sistem al acestuia, astfel că interceptarea aplicațiilor desktop nu funcționează acolo.

**Recomandare:** Rulați OmniRoute nativ pe același sistem de operare ca aplicațiile desktop pe care doriți să le interceptați (Windows pentru aplicațiile Windows; similar pentru macOS/Linux). Păstrarea OmniRoute în WSL în timp ce vizați aplicațiile de pe gazdă necesită să acordați manual încredere certificatului CA generat pe gazda Windows și să direcționați setările de rețea/proxy ale fiecărei aplicații de pe gazdă către endpointul proxy din WSL — o configurație nesuportată și fragilă.

## Probleme cu furnizorii

### „Language model did not provide messages”

**Cauză:** Cota furnizorului a fost epuizată.

**Remediere:**

1. Verificați monitorul cotei din panoul de control
2. Utilizați o combinație cu niveluri de rezervă
3. Treceți la un nivel mai ieftin/gratuit

### Limitarea ratei

**Cauză:** Cota abonamentului a fost epuizată.

**Remediere:**

- Adăugați o variantă de rezervă: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Utilizați GLM/MiniMax ca alternativă de rezervă ieftină

### Token OAuth expirat

OmniRoute reîmprospătează automat tokenurile. Dacă problemele persistă:

1. Panou de control → Furnizor → Reconectare
2. Ștergeți și adăugați din nou conexiunea furnizorului

### Conturi Kiro multiple: al doilea cont îl invalidează pe primul

**Cauză:** Backendul Kiro impune o singură sesiune activă pentru fiecare înregistrare de client OIDC.
Când două conturi utilizează același client înregistrat (conexiuni importate înainte de v3.8.0),
reîmprospătarea tokenului unui cont invalidează tokenul de reîmprospătare al celuilalt.

**Remediere (v3.8.0+):** Reimportați conexiunile afectate.
Începând cu v3.8.0, fiecare conexiune Kiro nouă creată prin **Importare token**,
**Autentificare socială cu Google/GitHub** sau **Importare automată** își înregistrează automat
propriul client OIDC dedicat. Prin urmare, conexiunea este complet izolată, iar reîmprospătarea unui
cont nu afectează niciun alt cont.

Conexiunile importate _înainte de_ v3.8.0 nu includ o înregistrare de client pentru fiecare
conexiune. Aceste conexiuni continuă să utilizeze endpointul comun de reîmprospătare pentru autentificarea socială.
Pentru a beneficia de izolare, ștergeți conexiunea veche din Panou de control → Furnizori și adăugați-o din nou
prin oricare dintre cele trei fluxuri de import.

Pentru detalii complete și instrucțiuni pas cu pas privind adăugarea a două conturi Kiro în paralel,
consultați [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Probleme cu serviciul cloud

### Erori de sincronizare cu serviciul cloud

1. Verificați dacă `BASE_URL` indică instanța care rulează (de exemplu, `http://localhost:20128`)
2. Verificați dacă `CLOUD_URL` indică endpointul cloud (de exemplu, `https://omniroute.dev`)
3. Mențineți valorile `NEXT_PUBLIC_*` aliniate cu valorile de pe server

### Serviciul cloud returnează 500 pentru `stream=false`

**Simptom:** `Unexpected token 'd'...` la endpointul cloud pentru apelurile fără streaming.

**Cauză:** Serviciul din amonte returnează un răspuns SSE, în timp ce clientul se așteaptă la JSON.

**Soluție temporară:** Utilizați `stream=true` pentru apelurile directe către serviciul cloud. Mediul de execuție local include o conversie de rezervă SSE→JSON.

### Serviciul cloud indică starea „Conectat”, dar afișează „Cheie API nevalidă”

1. Creați o cheie nouă din panoul de control local (`/api/keys`)
2. Rulați sincronizarea cu serviciul cloud: Activați serviciul cloud → Sincronizați acum
3. Cheile vechi/nesincronizate pot returna în continuare `401` în serviciul cloud

## Probleme Docker

### IPv6 Docker / Resetarea conexiunii

<a name="docker-ipv6"></a>

**Simptome:** `curl http://localhost:20128/v1/models` returnează `curl: (56) Recv failure: Connection reset by peer`. Panoul de control și endpointurile neautentificate funcționează, dar endpointurile autentificate eșuează — pare o problemă de autentificare, dar nu este.

**Cauză:** `docker run -p 20128:20128` publică atât pe `0.0.0.0` (IPv4), cât și pe `::` (IPv6), dar procesul din container ascultă numai pe IPv4. Pe gazdele unde `localhost` se rezolvă mai întâi la `::1`, conexiunea ajunge la portul IPv6 publicat, fără un proces care să asculte în spatele acestuia → resetarea conexiunii.

**Remediere:**

1. **Diagnostic rapid:** Rulați `curl -4 http://localhost:20128/v1/models`. Dacă funcționează cu `-4`, dar eșuează fără această opțiune, există o nepotrivire a asocierii IPv6.
2. **Remediere permanentă:** Asociați explicit la IPv4 utilizând `-p 127.0.0.1:20128:20128` în comanda `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Aceasta forțează asocierea IPv4 și evită, de asemenea, expunerea proxy-ului pe toate interfețele gazdei.

## Depanare

### Activarea fișierelor jurnal

```bash
# Panou de control al stării
http://localhost:20128/dashboard/health

# Verificarea stării API-ului
curl http://localhost:20128/api/monitoring/health
```

- Starea principală: `${DATA_DIR}/storage.sqlite` (furnizori, combinații, aliasuri, chei, setări)

- Artefactele jurnalelor de apeluri: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` când fluxul de procesare a jurnalelor de apeluri este activat

Acțiunea **Curățați istoricul** din pagina Jurnalele solicitărilor șterge `call_logs`, vechiul
`request_detail_logs` și directorul local de artefacte `${DATA_DIR}/call_logs/`.

| **Monitorizare în timp real** | Urmăriți fluxul de solicitări în timp real pentru a identifica problemele intermitente de conversie                       |

### Probleme frecvente de format

- **Etichetele de gândire nu apar** — Verificați dacă furnizorul țintă acceptă gândirea și verificați setarea bugetului de gândire
- **Apelurile instrumentelor dispar** — Unele conversii de format pot elimina câmpurile neacceptate; verificați în modul Mediu de testare
- **Promptul de sistem lipsește** — Claude și Gemini gestionează diferit prompturile de sistem; verificați rezultatul conversiei
- **SDK-ul returnează un șir brut în locul unui obiect** — Problemă rezolvată în v1.x; mecanismul de igienizare a răspunsurilor elimină câmpurile nestandard (`x_groq`, `usage_breakdown` etc.) care cauzează erori de validare Pydantic în SDK-ul OpenAI. Dacă problema persistă în v3.x+, raportați-o.
- **GLM/ERNIE respinge rolul `system`** — Problemă rezolvată în v1.x; normalizatorul de roluri combină automat mesajele de sistem cu mesajele utilizatorului pentru modelele incompatibile. Dacă problema persistă în v3.x+, raportați-o.
- **Rolul `developer` nu este recunoscut** — Problemă rezolvată în v1.x; acesta este convertit automat în `system` pentru furnizorii care nu sunt OpenAI. Dacă problema persistă în v3.x+, raportați-o.
- **`json_schema` nu funcționează cu Gemini** — Problemă rezolvată în v1.x; `response_format` este acum convertit în `responseMimeType` + `responseSchema` pentru Gemini. Dacă problema persistă în v3.x+, raportați-o.

## Setări de reziliență

### Limitarea automată a ratei nu se declanșează

- Limitarea automată a ratei se aplică numai furnizorilor cu cheie API (nu OAuth/abonament)
- Verificați dacă în **Setări → Reziliență → Profiluri de furnizor** este activată limitarea automată a ratei
- Verificați dacă furnizorul returnează coduri de stare `429` sau antete `Retry-After`

### Ajustarea temporizării exponențiale

Profilurile de furnizor acceptă următoarele setări:

- **Întârziere de bază** — Timpul inițial de așteptare după prima eroare (implicit: 1s)
- **Întârziere maximă** — Limita maximă a timpului de așteptare (implicit: 30s)
- **Multiplicator** — Factorul de creștere a întârzierii pentru fiecare eroare consecutivă (implicit: 2x)

### Prevenirea efectului de turmă

Atunci când multe solicitări concurente ajung la un furnizor cu rata limitată, OmniRoute utilizează mutex + limitarea automată a ratei pentru a serializa solicitările și a preveni erorile în cascadă. Acest lucru este automat pentru furnizorii cu cheie API.

### Solicitările de chat eșuează cu 503 / chat_admission_busy

**Simptome:**

- Endpointul pentru completările de chat returnează un răspuns reîncercabil `503`, al cărui cod de eroare este
  `chat_admission_busy`.
- Răspunsul include `Retry-After`. Începând cu #12135, valoarea este derivată din gradul de ocupare
  observat — valoarea cea mai mare dintre fereastra `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` pe care solicitarea a
  așteptat-o deja și timpul cât au fost păstrate alocările curente pentru sarcini grele — rotunjită în sus la
  secunde întregi și limitată la 60. Pentru o poartă inactivă, sunt păstrate limitele minime istorice: 2 secunde pe
  calea bazată pe octeți, 1 secundă pe calea bazată pe structură (care include și
  `reason: "structure_limit"`).
- Acest lucru se poate întâmpla cât timp un alt chat cu sarcină grea sau un răspuns de streaming de lungă durată este încă
  în curs.

Corpul răspunsului bazat pe octeți este:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Răspunsul bazat pe structură utilizează același tip și același cod, cu mesajul
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
și `reason: "structure_limit"`.
La pragurile implicite, o solicitare este considerată complexă structural atunci când are cel puțin `200` de mesaje,
cel puțin `64` de instrumente sau cel puțin `32,000` de tokenuri estimate ori când estimarea limitată a structurii
își epuizează limitele de `10,000` de noduri vizitate sau de adâncime `12`.

**Cauză:** Aceasta este o reducere deliberată a sarcinii în cadrul OmniRoute, nu o eroare a furnizorului upstream.
Fiecare proces utilizează o protecție locală procesului pentru a rezerva o capacitate limitată pentru sarcini grele înainte de a păstra
și analiza corpul unei solicitări mari. O alocare pentru sarcini grele rămâne activă pe întreaga durată de viață a unui răspuns
SSE.

**Distribuirea răspunsurilor 503:** înainte de această remediere, protecția limita concurența la un NUMĂR fix de solicitări
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, implicit `1`), indiferent de memoria gazdei, astfel încât distribuirea sarcinilor
agenților de programare (mai mulți subagenți/CLI-uri, corpuri care depășesc în mod obișnuit 256 KB) reducea concurența
efectivă la ~1 și genera răspunsuri 503 în condiții de sarcină complet normale. Protecția se ajustează acum automat: este controlată
de un buget de OCTEȚI pentru ingestie, derivat automat (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionat pe baza
limitei reale de memorie a procesului și consultă, de asemenea, un semnal în timp real privind presiunea asupra resurselor — astfel încât
reduce sarcina numai atunci când gazda se află cu adevărat sub presiune de memorie, nu doar pentru că mai multe
solicitări grele au sosit simultan. Vechea limită numerică (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) este
respectată în continuare, dar numai dacă o setați în mod explicit.

Atunci când capacitatea este ocupată, o solicitare cu sarcină grea așteaptă mai întâi până la
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (implicit `2000`, `0` dezactivează așteptarea) eliberarea unui slot,
înainte de a răspunde cu codul reîncercabil `503`. Așteptarea limitată există pentru ca aplicațiile client de tip agent
(OpenCode, Claude Code, Cursor), care distribuie simultan subsolicitări grele, să serializeze vârful de sarcină,
în loc să-și consume întregul buget de reîncercări prin respingeri imediate și să se oprească în mijlocul sarcinii.
Gradul curent de ocupare a alocărilor pentru sarcini grele, bugetul de octeți calculat și severitatea în timp real a presiunii sunt
expuse la `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — verificați-le înainte de a modifica orice variabilă de mediu.
Setări → Reziliență → Coadă de solicitări → Solicitări concurente nu controlează acest comportament; setarea respectivă
gestionează un mecanism separat pentru coada de solicitări a furnizorului.

**Remediere:**

1. Încercați din nou mai întâi. Aplicațiile client trebuie să respecte `Retry-After` și să utilizeze temporizarea progresivă, în loc să
   repete imediat solicitarea.
2. Verificați `/api/monitoring/health` → `chatAdmission` înainte de a ajusta ceva. `countCapEnabled:
false` și o valoare generoasă pentru `maxInflightBytes` înseamnă că bugetul derivat automat își îndeplinește deja
   rolul; o valoare `pressureSeverity` de `high`/`critical` înseamnă că gazda are cu adevărat puțină memorie disponibilă —
   acest lucru nu poate fi remediat printr-o variabilă de mediu pentru admitere, ci necesită mai multă memorie RAM sau un volum de lucru mai mic.
3. Numai dacă `/api/monitoring/health` arată că bugetul derivat automat este într-adevăr prea mic pentru
   gazda dvs. (situație rară — acesta se adaptează deja de la containere până la sisteme bare-metal), suprascrieți-l direct cu
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, în loc să reveniți la limita învechită bazată pe numărul de solicitări.

Consultați [referința variabilelor de mediu](../reference/ENVIRONMENT.md#4-security--authentication)
pentru setările oficiale de admitere.

## Taxonomie opțională a erorilor RAG / LLM (16 probleme)

Unii utilizatori OmniRoute plasează gateway-ul în fața stivelor RAG sau a stivelor de agenți. În aceste configurații, apare frecvent un tipar ciudat: OmniRoute pare să funcționeze corect (furnizorii sunt disponibili, profilurile de rutare sunt în regulă, nu există alerte privind limitele de rată), însă răspunsul final este totuși greșit.

În practică, aceste incidente provin de obicei din pipeline-ul RAG din aval, nu din gateway-ul propriu-zis.

Dacă doriți un vocabular comun pentru descrierea acestor erori, puteți utiliza WFGY ProblemMap, o resursă text externă cu licență MIT care definește șaisprezece tipare recurente de erori RAG / LLM. La nivel general, aceasta acoperă:

- devierea regăsirii și limite de context defectuoase
- indexuri și baze de date vectoriale goale sau învechite
- neconcordanța dintre înglobări și semantică
- probleme de asamblare a promptului și ale ferestrei de context
- colapsul logicii și răspunsurile excesiv de încrezătoare
- erori ale lanțurilor lungi și de coordonare a agenților
- devierea memoriei și a rolurilor în sistemele multi-agent
- probleme privind ordinea implementării și inițializării

Ideea este simplă:

1. Atunci când investigați un răspuns incorect, înregistrați:
   - sarcina și solicitarea utilizatorului
   - ruta sau combinația de furnizori din OmniRoute
   - orice context RAG utilizat în aval (documente regăsite, apeluri de instrumente etc.)
2. Asociați incidentul cu unul sau două numere WFGY ProblemMap (`No.1` … `No.16`).
3. Stocați numărul în propriul tablou de bord, ghid operațional sau sistem de urmărire a incidentelor, alături de jurnalele OmniRoute.
4. Utilizați pagina WFGY corespunzătoare pentru a decide dacă trebuie să modificați stiva RAG, mecanismul de regăsire sau strategia de rutare.

Textul complet și rețetele concrete sunt disponibile aici (licență MIT, exclusiv text):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Puteți ignora această secțiune dacă nu rulați pipeline-uri RAG sau de agenți în spatele OmniRoute.

## Probleme cunoscute în v3.8.0

Probleme specifice versiunii v3.8.0 și soluțiile lor alternative actuale. Dacă o remediere este inclusă într-un patch ulterior, intrarea va fi actualizată sau eliminată.

### Erori de autentificare Devin CLI

**Simptome:**

- „Devin CLI nu a fost găsit” sau „autentificarea a eșuat” la invocarea instrumentelor bazate pe Devin
- Verificarea CLI în timpul rulării raportează `installed=false`

**Cauze:**

- `CLI_DEVIN_BIN` indică o cale care nu există
- Devin CLI nu este instalat pe gazdă

**Remediere:**

1. Instalați Devin CLI pentru platforma dumneavoastră
2. Setați `CLI_DEVIN_BIN=/usr/local/bin/devin` (sau calea reală) în `.env`
3. Reporniți OmniRoute și testați din nou din **Tablou de bord → Instrumente CLI**

### Perioada de așteptare a modelului rămâne blocată (resetare manuală)

**Simptome:**

- Un model rămâne afișat ca fiind în perioada de așteptare chiar și după expirarea acesteia
- Solicitările continuă să omită modelul în rutarea combinată, deși marcajul temporal este în trecut

**Resetare manuală:**

- **Tablou de bord:** **Setări → Perioade de așteptare ale modelelor** → faceți clic pe **Reactivați** pe cardul afectat
- **API:** `DELETE /api/resilience/model-cooldowns` cu antetele de autentificare pentru administrare

### Conexiunea la furnizorul Command Code eșuează cu 403

**Simptome:**

- Eroare 403 la testarea conexiunii la furnizorul Command Code
- Cardul furnizorului afișează „neautorizat” după o adăugare nouă

**Cauză:** Fluxul OAuth nu s-a finalizat (callback-ul nu a fost primit sau tokenul nu a fost păstrat).

**Remediere:**

- Rulați `omniroute providers` din CLI pentru a declanșa din nou fluxul OAuth sau
- Rulați din nou OAuth din **Tablou de bord → Furnizori → Command Code → Reconectare**

### ModelScope returnează perioade de așteptare 429 agresive

**Simptome:**

- Perioade de așteptare foarte scurte sau imediate pe ModelScope după o rafală mică de solicitări
- Rutarea combinată omite ModelScope mai devreme decât era de așteptat

**Cauză:** ModelScope emite antete `Retry-After` specifice furnizorului. v3.8.0 include gestionare dedicată pentru aceste antete, astfel încât versiunile mai vechi le interpretează greșit drept indicii generice privind limitarea ratei.

**Remediere:**

- Asigurați-vă că utilizați v3.8.0 sau o versiune ulterioară
- Verificați dacă opțiunea `useUpstream429BreakerHints` este activată în **Setări → Reziliență**

### OMNIROUTE_WS_BRIDGE_SECRET lipsește în producție

**Simptome:**

- Eroare 401 la fiecare solicitare către puntea WebSocket Codex/Responses atunci când se rulează pe o gazdă de producție la distanță
- Negocierea conexiunii punții WebSocket se închide imediat după conectare

**Cauză:** Variabila de mediu `OMNIROUTE_WS_BRIDGE_SECRET` lipsește din mediul de producție.

**Remediere:**

1. Generați un secret aleatoriu: `openssl rand -hex 32`
2. Setați `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` în mediul serverului de producție (și în orice client care comunică cu puntea)
3. Reporniți OmniRoute

### API-ul Responses: modul de fundal este retrogradat la sincron

**Simptome:**

- Avertisment înregistrat: `background mode degraded to synchronous`
- O solicitare `background: true` returnează un răspuns sincron normal în locul unui identificator pentru sarcina de fundal

**Cauză:** v3.8.0 retrogradează intenționat `background: true` din API-ul Responses la execuție sincronă, emițând în același timp un avertisment. Execuția asincronă completă în fundal este planificată pentru viitor.

**Remediere:**

- Ajustați clientul pentru a efectua apelul fără `background` sau
- Așteptați o versiune ulterioară care include modul asincron complet în fundal (urmăriți jurnalul de modificări)

## Pornire lentă / Expirarea timpului de așteptare pentru disponibilitate

Dacă CLI-ul afișează `⚠ Server did not respond within 60s`, dar serverul
funcționează de fapt, intervalul alocat verificării disponibilității este prea scurt pentru mediul dvs.

Acest lucru se întâmplă frecvent pe Windows (din cauza antivirusului sau a instrumentelor de monitorizare a sistemului de fișiere) ori în containere
cu sarcini mari la pornire.

**Remediere — măriți intervalul alocat:**

```bash
# Prin variabila de mediu (se păstrează între porniri):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minute
omniroute serve

# Prin opțiunea CLI (pentru o singură utilizare):
omniroute serve --ready-timeout 180000
```

Valoarea implicită este de 60 000 ms (60 s). Avertismentul are doar caracter informativ; serverul
continuă să pornească în fundal și va deveni accesibil după finalizarea pornirii.

Consultați [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) pentru detalii
complete despre `OMNIROUTE_READY_TIMEOUT_MS`.
