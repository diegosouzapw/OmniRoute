## Referință rapidă

**Folosiți OmniRoute pentru prima dată?** Începeți aici — acestea rezolvă 90% dintre probleme:

| Văd acest mesaj         | Ce înseamnă                             | Ce trebuie făcut                                                                                     |
| ----------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| "Can't connect"         | OmniRoute nu rulează                    | Rulați `omniroute` sau `docker restart omniroute`                                                    |
| "Invalid API key"       | Cheia este greșită sau a expirat        | Copiați din nou cheia de pe site-ul furnizorului                                                     |
| "Rate limit exceeded"   | Trimiteți prea multe solicitări         | Așteptați 1 minut sau folosiți `model: "auto"` pentru comutarea automată la o alternativă            |
| "Quota exceeded"        | Ați epuizat cota gratuită/plătită       | Conectați mai mulți furnizori sau folosiți furnizori gratuiți (Kiro, Pollinations)                   |
| "Slow responses"        | Furnizorul este ocupat sau prea departe | Folosiți `model: "auto/fast"` sau conectați un furnizor mai rapid (Groq, Cerebras)                   |
| "Wrong provider used"   | `auto` a ales un alt furnizor           | Este normal! `auto` îl alege pe cel mai bun. Impuneți un anumit furnizor cu `model: "openai/gpt-4o"` |
| "502 Bad Gateway"       | Furnizorul nu este disponibil           | Așteptați și reîncercați sau folosiți `model: "auto"` pentru a comuta între furnizori                |
| "401 Unauthorized"      | Datele de autentificare sunt greșite    | Verificați cheia API sau autentificați-vă din nou cu OAuth                                           |
| "429 Too Many Requests" | Limita de solicitări a fost atinsă      | Așteptați 1 minut sau conectați mai mulți furnizori                                                  |

**Problema persistă?** Consultați secțiunea [depanare detaliată](#detailed-troubleshooting) de mai jos sau întrebați pe [Discord](https://discord.gg/U47eFqAXCn).

### Limitarea frecvenței solicitărilor la furnizorii gratuiți (429 / 400 / 401)

**Simptom**: Când folosiți `model: "auto"` cu furnizori gratuiți/fără autentificare (opencode, auggie etc.), primiți intermitent `HTTP 429`, `400` sau `401` în locul răspunsurilor. Solicitările reușesc atunci când retrimiteți același prompt câteva momente mai târziu, însă automatizările (sarcini cron, agenți, scripturi) se opresc la prima eroare.

**Cauză principală**: Se suprapun trei moduri independente de eșec:

1. **Limitarea frecvenței de către furnizor (`429`)**: Nivelurile gratuite pot impune o cotă pentru fiecare interval de timp. O rafală de apeluri paralele o epuizează, astfel încât următoarea solicitare este refuzată până la resetarea intervalului.
2. **Model nefuncțional în modul passthrough (`400`/`401`)**: Grupurile `auto/*` pot include modele passthrough de la `opencode` care sunt înregistrate în catalog, dar nu au date de autentificare active (de exemplu, `oc/north-mini-code-free` → `401`). Routerul automat încearcă unul, eșuează, iar eroarea este propagată înainte ca trecerea la o alternativă să intre în acțiune.
3. **Amplificarea concurenței (`429` sub sarcină)**: Când mai multe sesiuni de agent/cron accesează simultan `auto`, rata cumulată a solicitărilor depășește nivelul tolerat de furnizorii gratuiți, astfel încât apelurile legitime sunt semnalate drept abuzive.

**Soluție verificată (raportată de comunitate, 2026-08-10)**: ajustați trei variabile de mediu, astfel încât rotația, concurența și trecerea la alternative să absoarbă instabilitatea nivelului gratuit în loc să eșueze din cauza acesteia:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # trece la alt model/furnizor la 400/401 (omite modelele passthrough nefuncționale)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # plafon explicit de admitere pentru solicitările intensive (implicit nesetat: fără limită a numărului de solicitări; consultați nota de mai jos)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # așteptare limitată mai lungă pentru capacitatea necesară solicitărilor intensive, în locul unui răspuns 503 imediat, care poate fi reîncercat
```

Setați aceste variabile în mediul procesului OmniRoute (daemonul, de exemplu prin plist-ul LaunchAgent sau `systemctl edit`), apoi reporniți OmniRoute. Opțiunea de rotație are cel mai mare impact: aceasta transformă un eșec definitiv într-o reîncercare transparentă cu un furnizor funcțional din grup.

**Notă**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` limitează numărul de solicitări intensive — cu context lung — care rulează simultan; această limită este o poartă de admitere, nu un mecanism de limitare a frecvenței furnizorului. **Actualizare privind propagarea erorilor #503:** această variabilă nu mai este setată implicit (acum se aplică numai atunci când este configurată explicit, ca mai sus) — în schimb, admiterea solicitărilor intensive este controlată de un buget de octeți calculat automat (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), care se adaptează la limita reală de memorie a gazdei. Prin urmare, o instalare nouă ar trebui să întâmpine mult mai puține respingeri `503 chat_admission_busy` fără a seta deloc această variabilă; setarea sa explicită aici continuă să funcționeze exact așa cum este documentat. Suprascrierile explicite ale bugetului de octeți sunt limitate la intervalul 8 MiB–2 GiB. Un răspuns `413 body_exceeds_budget` nu este temporar: măriți bugetul de octeți, micșorați `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` sau măriți limita de memorie a procesului. O respingere `inflight_bytes_budget` reprezintă o concurență temporară pentru resurse și poate fi reîncercată. Limitarea frecvenței pentru fiecare furnizor (`open-sse/services/rateLimitManager.ts`) este controlată separat de `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` și `RATE_LIMIT_AUTO_ENABLE` — consultați `.env.example`.

**Cum verificați dacă soluția a funcționat**: rulați agentul/sarcina cron de două ori într-un interval scurt și confirmați că ambele execuții reușesc. Înainte de aplicarea soluției, a doua execuție returnează de obicei `429`/`401`. După aplicarea soluției, erorile (dacă apar) sunt reîncercate în mod transparent, iar apelul se finalizează. De asemenea, puteți rula `curl /monitoring/health` și urmări câmpul `rateLimitedUntil` pentru conexiunile furnizorilor, precum și `circuitBreakers.providerBreakers[].state` pentru furnizorii afectați — starea este una dintre valorile `CLOSED`, `DEGRADED`, `OPEN` sau `HALF_OPEN` (consultați `src/shared/utils/circuitBreaker.ts`), iar un furnizor care continuă să eșueze va trece prin stările `CLOSED → DEGRADED → OPEN` înainte ca intervalul de resetare să permită efectuarea unei solicitări de test (`HALF_OPEN`).

**Dacă vedeți în continuare 429**: contul activ pentru furnizorul respectiv și-a epuizat efectiv _cota_ (nu doar limita de rată). Adăugați un al doilea cont pentru același furnizor în panoul de control OmniRoute → Providers → Accounts sau includeți un alt furnizor gratuit (de exemplu, `routeway`, `auggie`). Rotația ajută doar în cazul erorilor temporare de rată/400/401; epuizarea completă a cotei necesită o a doua acreditare sau un furnizor diferit.

**Dacă vedeți 403 la modelele de viziune (`auto/vision`, `bazaarlink/*`)**: contul conectat nu are un plan cu plată care include funcționalitatea de viziune sau cheia API nu are permisiuni suficiente. Verificați în panoul de control al furnizorului dacă domeniul de aplicare al cheii include funcționalități de viziune/multimodale sau conectați un cont cu plan plătit și păstrați-l drept țintă pentru viziune.

## Avertismente npm install (ERESOLVE / peer / deprecated)

Când rulați `npm install -g omniroute`, este posibil să vedeți numeroase avertismente precum `npm warn ERESOLVE`, notificări privind dependențele peer și mesaje `deprecated`. **Acestea sunt de așteptat și nu prezintă niciun risc.** Instalarea a reușit dacă vedeți `added <N> packages` în rezultatul comenzii.

Pentru a suprima avertismentele privind rezolvarea dependențelor peer, utilizați forma de instalare acceptată de OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` suprimă numai `ERESOLVE` și notificările privind dependențele peer. Notificările de perimare rămân vizibile deoarece provin din pachete terțe tranzitive; acestea nu indică faptul că instalarea a eșuat.

Avertismentele provin din intervale învechite ale dependențelor peer din pachete terțe pe care OmniRoute nu le controlează:

1. **`marked-terminal` necesită `marked >=1 <16`, dar a fost găsit `marked@18`** — în practică, funcționează fără probleme; intervalul peer din pachetul upstream este pur și simplu învechit.
2. **`deprecated prebuild-install@7.1.3`** — un instrument auxiliar tranzitiv pentru preluarea binarelor native. Acesta nu este
   utilizat pentru a instala bindingul de transport `wreq-js` fixat la o anumită versiune și nu indică faptul că configurarea transportului
   furnizorului web-cookie a eșuat.

**Nu este necesară nicio acțiune** — avertismentele nu pot fi suprimate complet fără a crea fork-uri ale pachetelor upstream.

## Soluții rapide

| Problemă                                                   | Soluție                                                                                                                                                                           |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prima autentificare nu funcționează                        | Setați `INITIAL_PASSWORD` în `.env` (nu există o valoare implicită codificată direct)                                                                                             |
| Panoul de control se deschide pe portul greșit             | Setați `PORT=20128` și `NEXT_PUBLIC_BASE_URL=http://localhost:20128`                                                                                                              |
| Nu sunt scrise jurnale pe disc                             | Setați `APP_LOG_TO_FILE=true` și verificați dacă este activată capturarea jurnalului de apeluri                                                                                   |
| EACCES: permisiune refuzată                                | Setați `DATA_DIR=/path/to/writable/dir` pentru a înlocui `~/.omniroute`                                                                                                           |
| Strategia de rutare nu se salvează                         | Actualizați la cea mai recentă versiune v3.x (remedierea schemei Zod pentru persistența setărilor a fost inclusă în versiunile anterioare)                                        |
| Blocare la autentificare / pagină goală                    | Verificați versiunea Node.js — consultați [Compatibilitatea cu Node.js](#nodejs-compatibility) mai jos                                                                            |
| `dlopen` / `slice is not valid mach-o file` (macOS)        | Rulați `cd $(npm root -g)/omniroute/app && npm rebuild better-sqlite3 && omniroute` — consultați [recompilarea modulului nativ pe macOS](#macos-native-module-rebuild) mai jos    |
| „fetch failed” pentru proxy                                | Asigurați-vă că configurația proxy este setată la nivelul corect — consultați [Probleme cu proxy-ul](#proxy-issues) mai jos                                                       |
| Docker `curl: (56) Recv failure: Connection reset by peer` | Asocierea portului Docker poate ajunge pe IPv6. Utilizați `-p 127.0.0.1:20128:20128` pentru a forța IPv4 sau testați cu `curl -4`. Consultați [Docker IPv6](#docker-ipv6) mai jos |
| Antivirusul plasează `README.md` în carantină              | Rezultat fals pozitiv — consultați [Rezultate fals pozitive ale antivirusului](#antivirus-false-positives) mai jos                                                                |
| Kaspersky semnalează aplicația Desktop drept troian        | Rezultat fals pozitiv comportamental pentru programul de instalare nesemnat — consultați [Rezultate fals pozitive ale antivirusului](#antivirus-false-positives) mai jos          |

## Rezultate fals pozitive ale antivirusului

<a name="antivirus-false-positives"></a>

### Avast/AVG plasează în carantină `README.md` cu `MD:HttpRequest-inf[Susp]`

**Acesta este un rezultat fals pozitiv. Nimic nu este infectat și nu este necesară nicio acțiune.**

Avast și AVG rulează o euristică ce semnalează fișiere text simplu/Markdown care conțin multe
linkuri asemănătoare solicitărilor HTTP. Fișierul `README.md` al OmniRoute este inclus în pachetul npm (este
listat în `package.json` → `files`), așadar, la o instalare globală, ajunge în `node_modules/omniroute/README.md`
— și conține aproximativ 15 exemple `http://localhost:20128/...` (endpointurile HTTP/SSE
MCP, URL-ul A2A `.well-known` și fragmente `curl`). Această densitate a linkurilor este
suficientă pentru a declanșa euristica.

Dacă acest lucru a început abia recent: tipul fișierului nu s-a schimbat. README-ul și-a extins
tabelul de endpointuri (au fost adăugate MCP HTTP + SSE + A2A) și include mai multe exemple `curl`, ceea ce
a făcut ca acesta să depășească pragul.

Fișierul este documentație inertă, fără conținut executabil. Îl puteți restaura în siguranță
din carantină.

**Ce trebuie să faceți:**

1. **Opriți notificările** — excludeți directorul de instalare din antivirus
   (Avast: Setări → Excepții), adăugând calea globală `node_modules` și/sau directorul
   de date OmniRoute (`~/.omniroute/`).
2. **Raportați rezultatul fals pozitiv** — <https://www.avast.com/false-positive-file-form.php>,
   atașând fișierul `README.md` aflat în carantină. Aceasta este soluția care îi ajută pe toți, deoarece
   euristica furnizorului reacționează excesiv la un fișier text.

**De ce nu „remediem” acest lucru de partea noastră:** toate exemplele folosesc `http://localhost`, iar
localhost nu poate folosi `https` fără complicațiile certificatelor autosemnate. Modificarea nefirească a documentației pentru
a evita euristica unui singur furnizor ar afecta fiecare cititor doar pentru a ocoli o eroare a scanerului.

### Kaspersky semnalează aplicația Desktop drept `PDM:Trojan.Win32.Generic`

**Acesta este un rezultat fals pozitiv provenit de la o euristică bazată pe comportament. Nimic nu este infectat.** Prefixul
`PDM:` al Kaspersky înseamnă că verdictul provine de la Proactive Defense Module (System Watcher),
care evaluează ceea ce _face_ programul de instalare, în loc să-l compare cu programe malware cunoscute. Când
se declanșează, Kaspersky „revine” asupra întregii instalări — ștergând fișierele pe care le-a
scris deja — astfel încât aplicația ajunge să fie nefuncțională sau să lipsească.

Fișierele pe care le semnalează sunt componente standard ale unor dependențe open-source declarate, incluse împreună cu
aplicația desktop, de exemplu:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` și
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), biblioteca de automatizare a browserului
  utilizată pentru autentificarea la furnizori în cadrul aplicației și conversațiile susținute de browser.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — bindingul nativ `wreq-js` cu versiune fixată, utilizat pentru HTTP cu amprentă de browser în cazul furnizorilor
  bazați pe cookie-uri web (`<arch>` este `x64` sau `arm64`).

**De ce se declanșează:** programul de instalare pentru Windows **nu este încă semnat digital**, astfel încât un program de instalare NSIS
nesemnat are reputație zero, iar euristicile comportamentale rulează la nivelul maxim de agresivitate. Împreună
cu un DLL nativ inclus și sute de fișiere `.js` scrise în
`%LOCALAPPDATA%\Programs\OmniRoute` (inclusiv directoare de pachete cu sufixuri hash din compilarea
autonomă Next.js), acest lucru este suficient pentru a declanșa euristica. Semnarea codului este planificată;
până la implementarea acesteia, problema poate reapărea la versiunile noi.

**Ce trebuie să faceți:**

1. **Verificați mai întâi fișierul descărcat** (pentru a exclude posibilitatea unui fișier modificat). Fiecare versiune publică
   `latest.yml`, al cărui câmp `sha512` (base64) acoperă programul de instalare
   `OmniRoute.Setup.<version>.exe`. În PowerShell, din folderul care conține programul de instalare:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Rezultatul trebuie să corespundă valorii `latest.yml` → `sha512`. Dacă nu corespunde, ștergeți fișierul și
   descărcați-l din nou numai de pe [pagina de versiuni GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Restaurați + excludeți** — restaurați din carantină elementele eliminate prin revenire și adăugați o excludere
   pentru `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Setări → Amenințări și excluderi),
   apoi reinstalați.
3. **Raportați rezultatul fals pozitiv** — <https://opentip.kaspersky.com/>. Rapoartele FP
   trimise de utilizatori accelerează în mod real adăugarea pe lista de permisiuni.

## Compatibilitate Node.js

<a name="nodejs-compatibility"></a>

### Pagina de autentificare se blochează sau afișează eroarea „Module self-registration”

**Cauză:** Rulați o versiune Node.js care nu respectă pragul minim aprobat de OmniRoute pentru un mediu de execuție securizat. Cel mai frecvent caz este utilizarea unei versiuni de corecție mai vechi pentru Node 22 sau 24, aflată sub pragul de securitate cu remedieri impus de OmniRoute.

**Simptome:**

- Pagina de autentificare afișează un ecran gol sau o eroare de server
- Consola afișează `Error: Module did not self-register` sau erori similare privind legăturile native
- Pagina de autentificare afișează un **banner portocaliu de avertizare** cu versiunea dvs. de Node dacă mediul de execuție nu respectă politica de securitate acceptată

**Remediere:**

1. Instalați o versiune LTS Node.js acceptată (recomandat: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Verificați versiunea: `node --version` trebuie să afișeze `v24.0.0` sau o versiune mai nouă din seria LTS 24.x
3. Reinstalați OmniRoute: `npm install -g omniroute`
4. Reporniți: `omniroute`

> **Versiuni securizate acceptate:** `>=22.22.2 <23` sau `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) și Node.js 26 sunt acceptate integral.

### npm v11+: `better-sqlite3` nu este instalat (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Cauză:** npm v11 (inclus cu Node.js 24+) blochează implicit scripturile de instalare pentru dependențele
opționale. Deoarece `better-sqlite3` este inclus în `optionalDependencies`
și necesită compilare nativă (`node-gyp rebuild`), npm îl omite fără nicio notificare.

**Simptome:**

- Serverul se blochează la pornire cu mesajul `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` afișează „No such file or directory”
- `npm ls better-sqlite3` afișează `(empty)`

**Remediere:**

1. Aprobați scripturile de instalare și reinstalați:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Sau instalați manual pachetul precompilat:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Verificați dacă funcționează: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / „slice is not valid mach-o file”

<a name="macos-native-module-rebuild"></a>

**Cauză:** După o instalare globală folosind `npm install -g omniroute`, este posibil ca binarul nativ `better-sqlite3` din pachet să fi fost compilat pentru o arhitectură sau o interfață ABI Node.js diferită de cea utilizată local. Acest lucru este frecvent pe macOS (atât pe Apple Silicon, cât și pe Intel) atunci când binarul precompilat nu corespunde mediului dvs.

**Simptome:**

- Serverul eșuează imediat la pornire cu o eroare `dlopen`
- Eroarea conține `slice is not valid mach-o file`
- Exemplu complet:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Remediere — recompilați pentru mediul dvs. local (nu este necesară revenirea la o versiune anterioară de Node.js):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Notă:** Această operațiune recompilează legătura nativă pentru versiunea dvs. locală de Node.js și arhitectura procesorului, rezolvând incompatibilitatea binarului. Intervalul de versiuni acceptat oficial pentru mediul de execuție este **`>=22.22.2 <23` sau `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` în `src/shared/utils/nodeRuntimeSupport.ts`, aliniat cu câmpul `engines` din `package.json`). Node.js 24.x LTS (Krypton) și Node.js 26 sunt acceptate integral cu `better-sqlite3` v12.x.

## Probleme cu proxy-ul

<a name="proxy-issues"></a>

### Validarea furnizorului afișează „fetch failed”

**Cauză:** Endpointul de validare a cheii API (`POST /api/providers/validate`) ocolea anterior configurația proxy-ului, provocând erori în mediile care necesită rutarea prin proxy.

**Remediere (v3.5.5+):** Problema este acum remediată. Validarea furnizorului este rutată prin `runWithProxyContext`, respectând automat setările proxy la nivel de furnizor și setările proxy globale.

### Verificarea stării tokenului eșuează cu „fetch failed”

**Cauză:** Reîmprospătarea în fundal a tokenului OAuth nu determina configurația proxy pentru fiecare conexiune.

**Remediere (v3.5.5+):** Planificatorul verificării stării tokenului determină acum configurația proxy pentru fiecare conexiune înainte de a încerca reîmprospătarea. Actualizați la v3.5.5+.

### Proxy-ul SOCKS5 returnează „invalid onRequestStart method”

**Cauză:** În Node.js 22, dispecerul undici@8 este incompatibil cu implementarea `fetch()` integrată în Node.

**Remediere (v3.5.5+):** OmniRoute utilizează acum propria funcție `fetch()` a undici atunci când este activ un dispecer proxy, asigurând un comportament consecvent. Actualizați la v3.5.5+.

### Proxy MITM în WSL: aplicațiile desktop de pe gazda Windows nu sunt interceptate

**Cauză:** Proxy-ul MITM și certificatul său CA sunt instalate în mediul în care rulează OmniRoute. În WSL, acel mediu este sistemul Linux invitat, în timp ce aplicațiile desktop AI (Kiro, Trae, Copilot, Zed, …) rulează pe gazda Windows. Aplicațiile gazdă nu consideră de încredere magazinul de certificate al sistemului invitat și nu își rutează traficul prin proxy-ul de sistem al acestuia, astfel încât interceptarea aplicațiilor desktop nu este activată în acest caz.

**Recomandare:** Rulați OmniRoute nativ pe același sistem de operare ca aplicațiile desktop pe care doriți să le interceptați (Windows pentru aplicațiile Windows; în mod similar pentru macOS/Linux). Menținerea OmniRoute în WSL în timp ce vizați aplicațiile gazdă necesită acordarea manuală a încrederii certificatului CA generat pe gazda Windows și configurarea setărilor de rețea/proxy ale fiecărei aplicații gazdă către endpointul proxy WSL — o configurație fragilă și neacceptată oficial.

## Probleme cu furnizorii

### „Language model did not provide messages”

**Cauză:** Cota furnizorului a fost epuizată.

**Remediere:**

1. Verificați indicatorul de cotă din panoul de control
2. Utilizați o combinație cu niveluri de rezervă
3. Treceți la un nivel mai ieftin/gratuit

### Limitarea ratei

**Cauză:** Cota abonamentului a fost epuizată.

**Remediere:**

- Adăugați o opțiune de rezervă: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Utilizați GLM/MiniMax ca alternativă ieftină

### Token OAuth expirat

OmniRoute reîmprospătează automat tokenurile. Dacă problemele persistă:

1. Panou de control → Furnizor → Reconectare
2. Ștergeți și adăugați din nou conexiunea furnizorului

### Mai multe conturi Kiro: al doilea cont îl invalidează pe primul

**Cauză:** Backendul Kiro impune o singură sesiune activă pentru fiecare înregistrare de client OIDC.
Atunci când două conturi folosesc același client înregistrat (conexiuni importate înainte de v3.8.0),
reîmprospătarea tokenului unui cont invalidează tokenul de reîmprospătare al celuilalt.

**Remediere (v3.8.0+):** Reimportați conexiunile afectate.
Începând cu v3.8.0, fiecare conexiune Kiro nouă creată prin **Import Token**,
**autentificare socială Google/GitHub** sau **Auto-Import** își înregistrează automat propriul
client OIDC dedicat. Prin urmare, conexiunea este complet izolată, iar reîmprospătarea unui
cont nu are niciun efect asupra altui cont.

Conexiunile care au fost importate _înainte de_ v3.8.0 nu includ o înregistrare de client
specifică fiecărei conexiuni. Aceste conexiuni continuă să utilizeze endpointul comun de reîmprospătare pentru autentificarea socială.
Pentru a beneficia de izolare, ștergeți conexiunea veche din Panou de control → Furnizori și adăugați-o din nou
prin oricare dintre cele trei fluxuri de import.

Pentru detalii complete și instrucțiuni pas cu pas privind adăugarea simultană a două conturi Kiro,
consultați [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Probleme cu cloud-ul

### Erori de sincronizare cu cloud-ul

1. Verificați dacă `BASE_URL` indică instanța care rulează (de exemplu, `http://localhost:20128`)
2. Verificați dacă `CLOUD_URL` indică endpointul cloud (de exemplu, `https://omniroute.dev`)
3. Mențineți valorile `NEXT_PUBLIC_*` aliniate cu valorile de pe server

### Cloud-ul returnează 500 pentru `stream=false`

**Simptom:** `Unexpected token 'd'...` la endpointul cloud pentru apelurile fără streaming.

**Cauză:** Serviciul din amonte returnează o sarcină utilă SSE, în timp ce clientul așteaptă JSON.

**Soluție temporară:** Utilizați `stream=true` pentru apelurile directe către cloud. Mediul local de execuție include o conversie de rezervă SSE→JSON.

### Cloud-ul indică o conexiune reușită, dar afișează „Invalid API key”

1. Creați o cheie nouă din panoul de control local (`/api/keys`)
2. Rulați sincronizarea cu cloud-ul: Activați Cloud → Sincronizați acum
3. Cheile vechi/nesincronizate pot returna în continuare `401` în cloud

## Probleme cu Docker

### IPv6 Docker / Resetarea conexiunii

<a name="docker-ipv6"></a>

**Simptome:** `curl http://localhost:20128/v1/models` returnează `curl: (56) Recv failure: Connection reset by peer`. Panoul de control și endpointurile neautentificate funcționează, dar endpointurile autentificate eșuează — pare a fi o problemă de autentificare, dar nu este.

**Cauză:** `docker run -p 20128:20128` publică atât pe `0.0.0.0` (IPv4), cât și pe `::` (IPv6), dar procesul din container ascultă numai pe IPv4. Pe gazdele unde `localhost` se rezolvă mai întâi la `::1`, conexiunea ajunge la portul IPv6 publicat, fără a exista un serviciu care să asculte în spatele acestuia → conexiunea este resetată.

**Remediere:**

1. **Diagnostic rapid:** Rulați `curl -4 http://localhost:20128/v1/models`. Dacă funcționează cu `-4`, dar eșuează fără acesta, există o nepotrivire de asociere IPv6.
2. **Remediere permanentă:** Asociați explicit cu IPv4 utilizând `-p 127.0.0.1:20128:20128` în comanda `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Aceasta forțează asocierea IPv4 și evită, de asemenea, expunerea proxy-ului pe toate interfețele gazdei.

## Depanare

### Activarea fișierelor jurnal

Setați `APP_LOG_TO_FILE=true` în fișierul `.env`. Jurnalele aplicației sunt scrise în `logs/`.
Artefactele solicitărilor sunt stocate în `${DATA_DIR}/call_logs/` atunci când fluxul de procesare a jurnalelor de apeluri este
activat în setări.
Când capturarea fluxului de procesare este activată, setați `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` pentru a omite
sarcinile utile ale fragmentelor de flux sau ajustați `CALL_LOG_PIPELINE_MAX_SIZE_KB` pentru a modifica limita artefactelor în KB.

### Verificarea stării furnizorului

```bash
# Panoul de control al stării
http://localhost:20128/dashboard/health

# Verificarea stării API-ului
curl http://localhost:20128/api/monitoring/health
```

### Stocarea mediului de execuție

- Starea principală: `${DATA_DIR}/storage.sqlite` (furnizori, combinații, aliasuri, chei, setări)
- Utilizare: tabele SQLite în `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + opțional `${DATA_DIR}/call_logs/`
- Jurnalele aplicației: `<repo>/logs/...` (când `APP_LOG_TO_FILE=true`)
- Artefactele jurnalelor de apeluri: `${DATA_DIR}/call_logs/YYYY-MM-DD/...` când fluxul de procesare a jurnalelor de apeluri este activat

Acțiunea **Curățați istoricul** de pe pagina Jurnale de solicitări șterge `call_logs`, vechile
`request_detail_logs` și directorul local de artefacte `${DATA_DIR}/call_logs/`.

## Probleme cu întrerupătorul de circuit

### Furnizor blocat în starea OPEN

Când întrerupătorul de circuit al unui furnizor este în starea OPEN, solicitările sunt blocate până la expirarea perioadei de așteptare.

**Remediere:**

1. Accesați **Tablou de bord → Setări → Reziliență**
2. Verificați cardul întrerupătorului de circuit pentru furnizorul afectat
3. Faceți clic pe **Resetare totală** pentru a reseta toate întrerupătoarele sau așteptați expirarea perioadei de așteptare
4. Verificați dacă furnizorul este într-adevăr disponibil înainte de resetare

### Furnizorul declanșează în mod repetat întrerupătorul de circuit

Dacă un furnizor intră în mod repetat în starea OPEN:

1. Verificați **Tablou de bord → Stare de funcționare → Starea furnizorului** pentru a identifica tiparul defecțiunilor
2. Accesați **Setări → Reziliență → Profiluri de furnizor** și măriți pragul de defecțiuni
3. Verificați dacă furnizorul a modificat limitele API sau necesită reautentificare
4. Examinați telemetria latenței — latența ridicată poate cauza defecțiuni provocate de expirarea timpului de așteptare

## Depanarea traducătorului

Utilizați **Tablou de bord → Traducător** pentru a depana problemele de traducere între formate:

| Mod                           | Când se utilizează                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Spațiu de testare**         | Comparați alăturat formatele de intrare/ieșire — inserați o solicitare care eșuează pentru a vedea cum este tradusă |
| **Tester de chat**            | Trimiteți mesaje în timp real și inspectați întregul conținut al solicitării/răspunsului, inclusiv antetele         |
| **Banc de testare**           | Rulați teste în lot pentru diverse combinații de formate, pentru a identifica traducerile defecte                   |
| **Monitorizare în timp real** | Urmăriți fluxul de solicitări în timp real pentru a detecta problemele de traducere intermitente                    |

### Probleme frecvente legate de format

- **Etichetele de raționament nu apar** — Verificați dacă furnizorul țintă acceptă raționamentul și setarea bugetului de raționament
- **Apelurile instrumentelor sunt omise** — Unele traduceri între formate pot elimina câmpurile neacceptate; verificați în modul Spațiu de testare
- **Promptul de sistem lipsește** — Claude și Gemini gestionează diferit prompturile de sistem; verificați rezultatul traducerii
- **SDK-ul returnează un șir brut în locul unui obiect** — Problemă rezolvată în v1.x; mecanismul de curățare a răspunsurilor elimină câmpurile nestandard (`x_groq`, `usage_breakdown` etc.) care cauzează erori de validare Pydantic în SDK-ul OpenAI. Dacă problema persistă în v3.x+, vă rugăm să raportați o problemă.
- **GLM/ERNIE respinge rolul `system`** — Problemă rezolvată în v1.x; normalizatorul de roluri combină automat mesajele de sistem cu mesajele utilizatorului pentru modelele incompatibile. Dacă problema persistă în v3.x+, vă rugăm să raportați o problemă.
- **Rolul `developer` nu este recunoscut** — Problemă rezolvată în v1.x; acesta este convertit automat în `system` pentru furnizorii diferiți de OpenAI. Dacă problema persistă în v3.x+, vă rugăm să raportați o problemă.
- **`json_schema` nu funcționează cu Gemini** — Problemă rezolvată în v1.x; `response_format` este acum convertit în `responseMimeType` + `responseSchema` pentru Gemini. Dacă problema persistă în v3.x+, vă rugăm să raportați o problemă.

## Setări de reziliență

### Limitarea automată a ratei nu se declanșează

- Limitarea automată a ratei se aplică numai furnizorilor cu cheie API (nu OAuth/abonament)
- Verificați dacă în **Setări → Reziliență → Profiluri de furnizor** este activată limitarea automată a ratei
- Verificați dacă furnizorul returnează coduri de stare `429` sau antete `Retry-After`

### Ajustarea întârzierii exponențiale

Profilurile de furnizor acceptă următoarele setări:

- **Întârziere de bază** — Timpul inițial de așteptare după prima eroare (implicit: 1s)
- **Întârziere maximă** — Limita maximă a timpului de așteptare (implicit: 30s)
- **Multiplicator** — Cu cât să crească întârzierea pentru fiecare eroare consecutivă (implicit: 2x)

### Prevenirea efectului de turmă

Când mai multe solicitări concurente ajung la un furnizor cu rata limitată, OmniRoute utilizează un mutex și limitarea automată a ratei pentru a serializa solicitările și a preveni erorile în cascadă. Acest lucru este automat pentru furnizorii cu cheie API.

### Solicitările de chat eșuează cu 503 / chat_admission_busy

**Simptome:**

- Endpointul pentru completări de chat returnează un răspuns reîncercabil `503` al cărui cod de eroare este
  `chat_admission_busy`.
- Răspunsul include `Retry-After`. Începând cu #12135, valoarea este derivată din gradul de
  ocupare observat — valoarea mai mare dintre intervalul `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` pe care solicitarea l-a
  așteptat deja și timpul de când sunt deținute alocările curente pentru solicitări grele — rotunjită în sus la
  secunde întregi și limitată la 60. Pentru un mecanism de control inactiv, păstrează valorile minime istorice: 2 secunde pentru
  calea bazată pe octeți și 1 secundă pentru calea bazată pe structură (care include și
  `reason: "structure_limit"`).
- Acest lucru se poate întâmpla cât timp un alt chat greu sau un răspuns de streaming de lungă durată este încă
  în curs.

Corpul răspunsului bazat pe octeți este:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Răspunsul bazat pe structură folosește același tip și același cod, cu mesajul
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
și `reason: "structure_limit"`.
La pragurile implicite, o solicitare este grea din punct de vedere structural atunci când are cel puțin `200` de mesaje,
cel puțin `64` de instrumente sau cel puțin `32,000` de tokenuri estimate ori când estimarea limitată a structurii
își epuizează limitele de `10,000` de noduri vizitate sau adâncimea `12`.

**Cauză:** Aceasta este o reducere deliberată a sarcinii în OmniRoute, nu o eroare a furnizorului din amonte.
Fiecare proces utilizează un mecanism de protecție local procesului pentru a rezerva o capacitate limitată pentru solicitări grele înainte de a păstra
și analiza corpul unei solicitări mari. O alocare pentru solicitări grele rămâne deținută pe întreaga durată de viață a unui răspuns
SSE.

**Distribuirea erorilor #503:** înainte de această remediere, mecanismul de protecție limita concurența la un NUMĂR fix de solicitări
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, implicit `1`), indiferent de memoria gazdei, astfel încât distribuirea
agenților de programare (mai mulți subagenți/CLI-uri, corpuri care depășesc în mod obișnuit 256 KB) se reducea la o
concurență efectivă de ~1 și genera erori 503 în condiții de încărcare complet normale. Acum, mecanismul de protecție se ajustează
automat: este controlat printr-un buget de OCTEȚI pentru ingestie derivat automat (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), dimensionat pe baza
limitei reale de memorie a procesului, și consultă, de asemenea, un semnal în timp real privind presiunea asupra resurselor — astfel încât
reduce sarcina numai atunci când gazda se află cu adevărat sub presiune de memorie, nu doar pentru că au sosit simultan mai multe
solicitări grele. Vechea limită numerică (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) este
respectată în continuare, dar numai dacă o setați explicit.

Când capacitatea este ocupată, o solicitare grea așteaptă mai întâi până la
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (implicit `2000`, `0` dezactivează așteptarea) pentru eliberarea unui loc
înainte de a răspunde cu codul reîncercabil `503`. Așteptarea limitată există pentru ca aplicațiile client de tip agent
(OpenCode, Claude Code, Cursor), care distribuie simultan subsolicitări grele, să serializeze rafala
în loc să își consume întregul buget de reîncercări prin respingeri imediate și să eșueze în timpul sarcinii.
Gradul actual de ocupare al alocărilor pentru solicitări grele, bugetul de octeți calculat și severitatea în timp real a presiunii sunt
expuse la `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — verificați-le înainte de a modifica orice variabilă de mediu.
Setări → Reziliență → Coadă de solicitări → Solicitări concurente nu controlează acest lucru; setarea respectivă
gestionează un mecanism separat pentru coada de solicitări către furnizor.

**Remediere:**

1. Încercați din nou mai întâi. Aplicațiile client trebuie să respecte `Retry-After` și să utilizeze o întârziere progresivă, în loc să
   repete imediat solicitarea.
2. Verificați `/api/monitoring/health` → `chatAdmission` înainte de a ajusta ceva. `countCapEnabled:
false` și o valoare generoasă pentru `maxInflightBytes` înseamnă că bugetul derivat automat își face deja
   treaba; o valoare `pressureSeverity` de `high`/`critical` înseamnă că gazda are cu adevărat puțină memorie disponibilă —
   această problemă nu poate fi remediată printr-o variabilă de mediu pentru admitere; necesită mai multă memorie RAM sau un volum de lucru mai mic.
3. Numai dacă `/api/monitoring/health` arată că bugetul derivat automat este într-adevăr prea mic pentru
   gazda dvs. (situație rară — acesta se adaptează deja de la containere la sisteme bare-metal), suprascrieți-l direct cu
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, în loc să reveniți la vechea limită bazată pe numărul de solicitări.

Consultați [referința variabilelor de mediu](../reference/ENVIRONMENT.md#4-security--authentication)
pentru setările oficiale de admitere.

## Taxonomie opțională a erorilor RAG / LLM (16 probleme)

Unii utilizatori OmniRoute plasează gateway-ul în fața unor stive RAG sau de agenți. În aceste configurații apare frecvent un tipar ciudat: OmniRoute pare să funcționeze corect (furnizorii sunt disponibili, profilurile de rutare sunt în regulă, nu există alerte privind limitarea ratei), dar răspunsul final este totuși greșit.

În practică, aceste incidente provin de obicei din pipeline-ul RAG din aval, nu din gateway-ul propriu-zis.

Dacă doriți un vocabular comun pentru a descrie aceste erori, puteți utiliza WFGY ProblemMap, o resursă textuală externă cu licență MIT care definește șaisprezece tipare recurente de erori RAG / LLM. La nivel general, aceasta acoperă:

- devierea regăsirii și limitele defectuoase ale contextului
- indecși și depozite vectoriale goale sau neactualizate
- neconcordanța dintre înglobări și semantică
- probleme privind asamblarea prompturilor și fereastra de context
- colapsul logicii și răspunsurile excesiv de încrezătoare
- erori ale lanțurilor lungi și ale coordonării agenților
- devierea memoriei și a rolurilor în sisteme multi-agent
- probleme privind ordinea implementării și inițializării

Ideea este simplă:

1. Atunci când investigați un răspuns necorespunzător, înregistrați:
   - sarcina și solicitarea utilizatorului
   - ruta sau combinația de furnizori din OmniRoute
   - orice context RAG utilizat în aval (documente regăsite, apeluri de instrumente etc.)
2. Asociați incidentul cu unul sau două numere WFGY ProblemMap (`No.1` … `No.16`).
3. Stocați numărul în propriul tablou de bord, ghid operațional sau sistem de urmărire a incidentelor, alături de jurnalele OmniRoute.
4. Utilizați pagina WFGY corespunzătoare pentru a decide dacă trebuie să modificați stiva RAG, mecanismul de regăsire sau strategia de rutare.

Textul complet și procedurile concrete sunt disponibile aici (licență MIT, doar text):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Puteți ignora această secțiune dacă nu rulați pipeline-uri RAG sau de agenți în spatele OmniRoute.

## Probleme cunoscute în v3.8.0

Probleme specifice versiunii v3.8.0 și soluțiile temporare disponibile în prezent. Dacă o remediere este inclusă într-un patch ulterior, intrarea va fi actualizată sau eliminată.

### Erori de autentificare Devin CLI

**Simptome:**

- „Devin CLI not found” sau „auth failed” la invocarea instrumentelor bazate pe Devin
- Verificarea CLI în timpul execuției raportează `installed=false`

**Cauze:**

- `CLI_DEVIN_BIN` indică o cale care nu există
- Devin CLI nu este instalat pe gazdă

**Remediere:**

1. Instalați Devin CLI pentru platforma dvs.
2. Setați `CLI_DEVIN_BIN=/usr/local/bin/devin` (sau calea reală) în `.env`
3. Reporniți OmniRoute și retestați din **Tablou de bord → Instrumente CLI**

### Perioada de răcire a modelului rămâne blocată (resetare manuală)

**Simptome:**

- Un model rămâne afișat ca fiind în perioada de răcire chiar și după expirarea acesteia
- Solicitările continuă să omită modelul în rutarea prin combinații, deși marcajul temporal este în trecut

**Resetare manuală:**

- **Tablou de bord:** **Setări → Perioade de răcire ale modelelor** → faceți clic pe **Reactivați** pe cardul afectat
- **API:** `DELETE /api/resilience/model-cooldowns` cu antetele de autentificare pentru administrare

### Conectarea la furnizorul Command Code eșuează cu 403

**Simptome:**

- Eroare 403 la testarea conexiunii cu furnizorul Command Code
- Cardul furnizorului afișează „unauthorized” după o adăugare nouă

**Cauză:** Fluxul OAuth nu s-a finalizat (callback-ul nu a fost primit sau tokenul nu a fost salvat).

**Remediere:**

- Rulați `omniroute providers` din CLI pentru a declanșa din nou fluxul OAuth sau
- Relansați OAuth din **Tablou de bord → Furnizori → Command Code → Reconectare**

### ModelScope returnează perioade de răcire 429 agresive

**Simptome:**

- Perioade de răcire foarte scurte sau imediate pe ModelScope după un volum redus de solicitări
- Rutarea prin combinații omite ModelScope mai devreme decât era de așteptat

**Cauză:** ModelScope emite antete `Retry-After` specifice furnizorului. v3.8.0 include o gestionare dedicată a acestor antete, astfel că versiunile mai vechi le interpretează greșit drept indicii generice privind limitarea ratei.

**Remediere:**

- Asigurați-vă că utilizați v3.8.0 sau o versiune ulterioară
- Verificați dacă opțiunea `useUpstream429BreakerHints` este activată în **Setări → Reziliență**

### OMNIROUTE_WS_BRIDGE_SECRET lipsește în producție

**Simptome:**

- Eroare 401 la fiecare solicitare către puntea WebSocket Codex/Responses atunci când aceasta rulează pe o gazdă de producție la distanță
- Negocierea conexiunii cu puntea WebSocket se închide imediat după conectare

**Cauză:** Variabila de mediu `OMNIROUTE_WS_BRIDGE_SECRET` lipsește din mediul de producție.

**Remediere:**

1. Generați un secret aleatoriu: `openssl rand -hex 32`
2. Setați `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` în mediul serverului de producție (și pe orice client care comunică cu puntea)
3. Reporniți OmniRoute

### Responses API: modul de fundal este retrogradat la execuție sincronă

**Simptome:**

- Avertisment înregistrat în jurnal: `background mode degraded to synchronous`
- O solicitare `background: true` returnează un răspuns sincron obișnuit în locul unui identificator pentru o sarcină de fundal

**Cauză:** v3.8.0 retrogradează în mod intenționat `background: true` din Responses API la execuție sincronă, emițând în același timp un avertisment. Execuția asincronă completă în fundal este planificată pentru viitor.

**Remediere:**

- Ajustați clientul pentru a efectua apelul fără `background` sau
- Așteptați o versiune ulterioară care include modul asincron complet în fundal (urmăriți jurnalul modificărilor)

## Pornire lentă / Expirarea timpului de așteptare pentru disponibilitate

Dacă CLI-ul afișează `⚠ Server did not respond within 60s`, dar serverul
funcționează, intervalul alocat verificării disponibilității este prea scurt pentru mediul dvs.

Acest lucru se întâmplă frecvent pe Windows (antivirus, monitorizarea sistemului de fișiere) sau în containere
cu sarcini de lucru intensive la pornire.

**Remediere — măriți intervalul alocat:**

```bash
# Prin variabila de mediu (se păstrează între porniri):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 minute
omniroute serve

# Prin opțiunea CLI (o singură utilizare):
omniroute serve --ready-timeout 180000
```

Valoarea implicită este de 60 000 ms (60 s). Avertismentul are doar caracter informativ; serverul
continuă să pornească în fundal și va fi accesibil după finalizarea pornirii.

Consultați [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) pentru detalii
complete despre `OMNIROUTE_READY_TIMEOUT_MS`.
