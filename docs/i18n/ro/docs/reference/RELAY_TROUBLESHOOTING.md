Releele (Vercel, Deno, Cloudflare) încheie conexiunea din amonte într-un
backend serverless, astfel încât OmniRoute să poată efectua traficul de ieșire dintr-o regiune stabilă, păstrând
cheia API a furnizorului pe server. Acest document descrie cele două moduri de defectare
întâlnite de operatori în producție și procedurile de recuperare incluse în OmniRoute pentru
fiecare dintre ele.

## Cum este stocată autentificarea releului

Când implementați un releu din **Setări → Grup de proxy-uri → Implementare releu**,
fluxul de implementare stochează tokenul de autentificare al releului în câmpul JSON `notes`
al proxy-ului:

- Dacă este setată variabila `STORAGE_ENCRYPTION_KEY`, tokenul este scris ca `relayAuthEnc`
  (criptat cu AES în repaus).
- În caz contrar, este scris ca text simplu în `relayAuth`.

În momentul solicitării, `extractRelayAuth(notes)` returnează oricare dintre formele prezente,
astfel încât releul continuă să funcționeze după reporniri.

## Modul de defectare 1 — token care nu poate fi decriptat după rotirea cheii

**Simptom:** releele care funcționau anterior returnează acum erori `401`/de autentificare
din amonte după o rotire a variabilei de mediu sau în managerul de secrete pentru
`STORAGE_ENCRYPTION_KEY`. Obiectul binar `relayAuthEnc` stocat nu mai poate fi
decriptat, astfel încât `extractRelayAuth` returnează șirul gol, iar releul nu trimite
date de autentificare.

**Recuperare — remediere pe loc (fără reimplementare):**

1. Deschideți **Setări → Grup de proxy-uri**.
2. Rândurile releelor pentru care lipsește autentificarea afișează o insignă galbenă `autentificare lipsă` și un
   buton **Remediați**.
3. Faceți clic pe **Remediați**. OmniRoute apelează
   `POST /api/settings/proxies/[id]/repair-relay`, care:
   - decriptează `relayAuthEnc` folosind cheia **curentă**,
   - scrie datele `relayAuth` în text simplu înapoi în `notes`,
   - returnează `{ repaired: true, mode: "recovered" }`.

Releul reia procesarea fără a fi necesară reintroducerea datelor de autentificare pentru implementare.

Această metodă funcționează numai dacă valoarea curentă a `STORAGE_ENCRYPTION_KEY` poate încă decripta
obiectul binar. Dacă ați rotit cheia **fără** o migrare, obiectul binar nu poate fi
recuperat.

## Modul de defectare 2 — token nerecuperabil (cheia a fost înlocuită prin rotire)

**Simptom:** ați făcut clic pe **Remediați** și ați primit
`{ repaired: false, mode: "redeploy", status: 409 }`.

**Recuperare — reimplementare:**

Tokenul stocat nu poate fi recuperat folosind cheia curentă. Reimplementați releul
din aceeași fereastră modală pe care ați folosit-o inițial (meniul **Implementare releu** → Vercel / Deno
/ Cloudflare). Fluxul de implementare scrie un token nou (criptat cu cheia curentă),
iar insigna `autentificare lipsă` a rândului dispare.

În interfața cu utilizatorul, butonul **Remediați** deschide automat fereastra modală de reimplementare atunci când
tokenul nu poate fi recuperat, astfel încât nu trebuie să o căutați manual.

## Modul de defectare 3 — releul este accesibil, dar nu funcționează corect

**Simptom:** testul proxy-ului (butonul `speed`) arată că releul este activ, dar solicitările
continuă să eșueze intermitent.

Verificați antetele de identificare a releului returnate de sonda de testare automată a OmniRoute
(consultați **Setări → Grup de proxy-uri** și contoarele `relayTested` / `relayAlive`):

- `x-relay-url` — backendul releului care a răspuns.
- `x-relay-mode` — `ts` | `bifrost` | `auto` pentru solicitarea respectivă.
- `x-relay-attempts` — câte salturi între relee au fost încercate înainte de succes.
- `x-relay-fallback` — `true` atunci când solicitarea a trecut de la backendul preferat
  la releul TypeScript.

O rată ridicată pentru `x-relay-fallback`, împreună cu o valoare scăzută pentru `relayAlive`, indică faptul că backendul
sidecar nu funcționează corect și trebuie fie să îl remediați, fie să schimbați strategia backendului releului
la `ts` (consultați `RELAY_BACKEND_STRATEGY.md`).

## Referință API

| Metodă | Cale                                      | Corp                    | Succes                                                                                                                                  | Eșec                                                                                           |
| ------ | ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `POST` | `/api/settings/proxies/[id]/repair-relay` | `{ "id": "<proxyId>" }` | `200 { repaired: true, mode: "recovered" }` la rederivare; `200 { repaired: false, mode: "noop" }` când textul simplu este deja prezent | `409 { mode: "redeploy" }` nerecuperabil; `400` nu este un tip de releu; `404` nu a fost găsit |

Ruta de listare `GET /api/settings/proxies` atașează fiecărui element un obiect fără secrete
`relayInfo: { isRelay, authMissing, repairMode }`, astfel încât tabloul de bord
să poată afișa opțiunea de remediere fără a expune vreodată tokenul.
