## Rezumat

OmniRoute acceptă acum trei moduri de retransmitere pentru `/api/v1/relay/chat/completions`:

- `ts`: Utilizează retransmiterea TypeScript în cadrul procesului.
- `bifrost`: Forțează utilizarea gateway-ului Bifrost.
- `auto`: Preferă Bifrost atunci când este disponibil și revine la TypeScript în caz de eșec.

Când operezi la o rată ridicată de solicitări (număr mare de tokenuri/zi, debit aproape constant), cea mai bună strategie este să menții calea de rezervă explicită și rapidă, astfel încât calea critică să nu fie niciodată blocată de un sidecar nefuncțional.

## Comportamentul modurilor

- `ts`
  - Cea mai redusă complexitate operațională.
  - Toate operațiunile de rutare și validare rulează în Node.
  - Disponibilitatea nu depinde de un sidecar.
- `bifrost`
  - Forțează trimiterea tuturor solicitărilor prin gateway-ul sidecar.
  - Fără revenire automată la calea de rezervă.
  - Util numai atunci când starea de funcționare și latența sidecar-ului sunt garantate.
- `auto`
  - Sidecar-ul este utilizat atunci când poate fi accesat și este activat.
  - Încercările eșuate declanșează antete de revenire și redirecționează traficul către TS, astfel încât timpul până la finalizarea cu succes a solicitării să rămână limitat.
  - Acest mod este cea mai sigură alegere pentru producție atunci când disponibilitatea este mai importantă decât rutarea strictă exclusiv prin sidecar.

## 9router comparativ cu CLIPROXYAPI în prezent

9router și CLIPROXYAPI sunt integrări care au oferit în mod tradițional căi de compatibilitate pentru furnizorii din amonte.

- 9router este o cale încorporată pentru orchestrarea serviciilor din amonte și comportamentul de compatibilitate.
- CLIPROXYAPI este o punte API proxy pentru traficul de tip CLI / SDK.
- Bifrost este stabilizat drept calea externalizată atunci când ai nevoie de un salt dedicat, similar unui sidecar, și de distribuire locală cu latență redusă.

Dacă în prezent compari 9router/CLIPROXYAPI:

- Păstrează semnarea solicitărilor, verificările listelor de permisiuni și porțile de politici DB în ruta API înainte de predare.
- Dacă un flux de lucru necesită un comportament strict al sidecar-ului și o variație mai redusă per solicitare, utilizează `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Dacă ai nevoie de reziliență pentru sidecar și degradare controlată în condiții de incident, utilizează `OMNIROUTE_RELAY_BACKEND=auto`.

## Contractul limitei backend-ului

Limita stabilă a produsului este API-ul de retransmitere OmniRoute, nu implementarea panoului de control. Panoul de control Next.js poate instala, configura și supraveghea servicii locale, dar rutarea solicitărilor trebuie să intre prin API-ul de retransmitere și să fie predată în spatele acestei limite.

Opțiuni backend pe termen lung:

- Păstrează retransmiterea TypeScript drept cale în cadrul procesului pentru politici și revenire. Autentificarea, listele de permisiuni, normalizarea solicitărilor, contorizarea și verificările de siguranță rămân aici înaintea oricărei predări către backend.
- Utilizează Bifrost drept sidecar Tier-1 preferat, cu debit ridicat, atunci când implementarea necesită o variație mai redusă a rutării, rotația centralizată a furnizorilor sau scalarea pe mai multe replici OmniRoute.
- Păstrează 9router și CLIPROXYAPI drept servicii de compatibilitate încorporate. Acestea rulează ca procese locale supravegheate și sunt utile atunci când comportamentul lor specific furnizorului/CLI-ului este adaptorul dorit, dar nu ar trebui să devină motorul implicit de rutare Tier-1.
- Nu permite panoului de control să transmită URL-uri arbitrare ale serviciilor în calea critică. URL-urile furnizate de UI sunt intrări de configurare; codul de rutare trebuie să identifice backend-uri înregistrate și verificate din punctul de vedere al stării de funcționare, folosind setările de pe server și starea supervizorului.
- Preferă HTTP pe interfața loopback pentru serviciile supravegheate în prezent, deoarece procesele gestionate expun deja API-uri compatibile cu HTTP, protecția rutei poate audita limita, iar comportamentul de eșec/revenire este vizibil în jurnalele solicitărilor. Adăugarea în viitor a unui transport prin SDK sau socket merită luată în calcul numai dacă reduce în mod măsurabil latența p99 a rutării fără a slăbi izolarea sau semantica revenirii.

Prin urmare, pentru o implementare cu debit foarte ridicat, alegerea implicită este `auto` cu Bifrost activat: utilizează sidecar-ul Go pe calea critică, păstrând în același timp calea de rezervă TypeScript pentru rata de succes. Utilizează `bifrost` numai atunci când comportamentul strict exclusiv prin sidecar este mai important decât degradarea controlată.

## Recomandări pentru debit ridicat

Pentru RPM/RPS ridicat susținut și un SLO strict privind succesul:

1. Utilizează `auto` cu o perioadă de așteptare practică și telemetrie pentru eșecuri.
2. Păstrează validarea serviciilor din amonte și verificările cheilor API la limita rutei TypeScript.
3. Activează antete/contoare explicite, astfel încât sistemul de alertare să detecteze frecvența și motivele revenirilor.
4. Configurează expirările sidecar-ului pentru eșec rapid, nu pentru a aștepta la nesfârșit.
5. Menține funcționale repornirea automată a serviciului și bucla de telemetrie a stării, astfel încât revenirea să fie cu adevărat excepțională.

## Configurație de bază sugerată

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Menține activate verificările cheilor API, ale listelor de permisiuni, ale instrumentului de sanitizare și ale limitelor de rată în gestionarii de rute (acestea rulează întotdeauna înainte de redirecționarea în aval).
- Exportă metricile de revenire din proxy-ul invers și din jurnalele solicitărilor, astfel încât întreruperile sidecar-ului să fie vizibile în decurs de un minut.
