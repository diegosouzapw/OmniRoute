`open-sse/config/providerPluginManifest.ts` definește contractul JSON-safe pentru pluginurile
furnizorilor. `open-sse/config/providerPluginManifestRegistry.ts` asociază acest
contract cu registrul curent al furnizorilor pentru sidecar-uri precum Bifrost,
CLIProxyAPI sau un viitor router Go/Rust. Registrul TypeScript rămâne
sursa adevărului, însă sidecar-urile pot consuma manifestul fără a importa
codul executorului, valorile implicite OAuth, antetele sau starea mediului de proces.

Același manifest este disponibil prin HTTP la
`GET /api/v1/provider-plugin-manifest` pentru sidecar-urile care rulează în afara procesului.

OmniRoute comunică acel URL către Bifrost și CLIProxyAPI prin intermediul
antetului de solicitare `X-OmniRoute-Provider-Manifest-Url`. Setați
`OMNIROUTE_PROVIDER_MANIFEST_URL` atunci când sidecar-ul necesită un URL public sau din
rețeaua containerului în locul originii solicitării locale.

## Reîmprospătarea manifestului

Endpoint-ul HTTP returnează `Cache-Control: public, max-age=60` și un
`ETag` puternic. Un sidecar ar trebui să păstreze ultimul manifest validat și să trimită ETag-ul
acestuia în `If-None-Match` atunci când îl reîmprospătează. Un răspuns `304 Not Modified` nu are corp;
sidecar-ul își păstrează manifestul din cache. Dacă nu există niciun manifest validat în cache,
sidecar-ul trebuie să emită o solicitare necondiționată în loc să accepte un `304`.

## Obiectiv

Mutarea metadatelor furnizorilor către un contract de plugin, astfel încât traseul rapid al solicitărilor
să poată fi gestionat în cele din urmă de un sidecar cu latență mai mică, în timp ce OmniRoute păstrează
ruta TypeScript drept mecanism de control al politicilor și soluție de rezervă. Manifestul este aditiv: acesta
nu modifică singur rutarea solicitărilor.

## Contract

Manifestul conține:

- id-ul și aliasul furnizorului
- formatul upstream și numele executorului
- tipul autentificării, antetul de autentificare și prefixul opțional de autentificare
- metadatele statice ale endpoint-ului
- eligibilitatea pentru sidecar și motive explicite pentru cazurile în care un furnizor ar trebui să rămână pe TS
- metadate JSON-safe despre modele, precum lungimea contextului, indicatorii pentru vedere/raționament și
  parametrii neacceptați
- etichete de capabilități, inclusiv `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` și `usage-supported`

Manifestul exclude în mod intenționat:

- secretele clienților OAuth și valorile secrete implicite
- rezolvarea mediului în timpul rulării
- antetele solicitărilor și funcțiile ajutătoare pentru credențiale publice
- constructorii dinamici de URL-uri
- funcțiile executorului
- detaliile interne ale pool-ului de sesiuni

## Etichete de capabilități

`capabilities` este o matrice sortată de etichete derivate din intrarea registrului. Integratorii
ar trebui să o trateze drept răspunsul procesabil automat la întrebarea „ce poate face acest furnizor”, în loc
să recitească sursele TypeScript.

| Etichetă             | Semnificație                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `apikey`             | Acceptă o cheie API (`authType` este `apikey` sau `optional`).                                      |
| `oauth`              | Utilizează un flux OAuth sau de sesiune.                                                            |
| `responses`          | Expune un URL de bază pentru API-ul OpenAI Responses.                                               |
| `passthrough-models` | Servește modele direct din upstream, nu dintr-un catalog static.                                    |
| `custom-executor`    | Rulează un executor non-implicit, deci rămâne pe traseul TypeScript.                                |
| `sidecar-candidate`  | Reflectă `sidecar.eligible` — poate fi luat în considerare în siguranță pentru importul în sidecar. |
| `usage-fetch`        | Are configurat un preluator pentru utilizare sau cotă (`getUsageForProvider`).                      |
| `usage-supported`    | API-ul de utilizare acceptă acest furnizor (`isSupportedUsageConnection`).                          |

`usage-fetch` este destinat exclusiv descoperirii. Acesta indică faptul că OmniRoute știe cum să citească utilizarea pentru
furnizor; nu activează preluarea, nu modifică semantica cotelor și nu implică faptul că
widgetul pentru cote din Dashboard este activat pentru furnizor — acel widget este controlat separat prin
`USAGE_SUPPORTED_PROVIDERS`. Sursa adevărului este `USAGE_FETCHER_PROVIDERS` din
`open-sse/services/usage/fetcherProviders.ts`.

Lista respectivă este indexată după șirurile acceptate de dispecerul de utilizare, astfel încât combină id-uri canonice
cu aliasuri și este puțin mai lungă decât numărul furnizorilor etichetați: intrările care nu sunt
furnizori de chat în registrul manifestului (de exemplu, furnizorul de căutare `firecrawl`
și furnizorul ACP `amazon-q`) nu au nicio intrare în manifest care să poată fi etichetată.

`usage-supported` indică dacă rutele de utilizare ale serverului și ale Dashboard-ului acceptă o conexiune
pentru furnizor. Acesta reflectă `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
și `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), ambele controlate prin
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). Spre deosebire de
`usage-fetch`, acesta este emis exclusiv pe baza id-ului furnizorului — verificarea din timpul rulării execută
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` fără rezolvarea aliasurilor, astfel încât manifestul
păstrează aceeași regulă. Cele două etichete au domenii diferite: 3 furnizori au doar
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), iar 1 are doar
`usage-supported` (`xiaomi-mimo-token-plan`), astfel încât una nu o implică pe cealaltă.

## Utilizarea sidecar-urilor

Sidecar-urile ar trebui să trateze `sidecar.eligible` drept un semnal conservator privind eligibilitatea, nu drept o decizie necondiționată de rutare. Primii candidați pentru import ar trebui să fie furnizorii care utilizează chei API, endpointuri statice și executorul implicit. Furnizorii cu executori web personalizați, fluxuri OAuth/de sesiune, generatoare dinamice de URL-uri sau configurații de pool rămân pe calea de rezervă TypeScript până când un sidecar implementează un comportament echivalent, iar telemetria demonstrează paritatea.

Faze de migrare sugerate:

1. Generați și validați manifestul pluginurilor furnizorilor din registrul TS.
2. Configurați Bifrost sau CLIProxyAPI să importe manifestul pentru furnizorii care utilizează chei API și endpointuri statice.
3. Rutați furnizorii eligibili prin sidecar, prin intermediul `OMNIROUTE_RELAY_BACKEND`, menținând activată calea de rezervă TS.
4. Promovați furnizorii numai atunci când rata de succes, latența p99, comportamentul de streaming și gestionarea parametrilor neacceptați corespund căii TS.
5. Adăugați pluginuri native pentru sidecar în cazul executorilor personalizați, câte o familie de furnizori pe rând.

## De ce să nu integrați furnizorii direct în Next

Frontendul Next nu ar trebui să gestioneze execuția furnizorilor. Acesta ar trebui să apeleze limita API. Backendul poate decide apoi dacă utilizează executorul TypeScript, Bifrost, CLIProxyAPI sau un viitor sidecar nativ. Astfel, semnarea cererilor, verificările listei de permisiuni, politica bazei de date și comportamentul de rezervă rămân centralizate înaintea oricărui transfer către un sidecar.
