> **Pe scurt**: `open-sse/` este motorul principal de streaming care gestionează fiecare solicitare LLM din OmniRoute. Conține aproximativ 1.400 de fișiere care implementează fluxul de procesare a solicitărilor, executorii, serviciile, serverul MCP și stratul de traducere. Acest ghid explică modul în care componentele se îmbină.

**Sursă:** `open-sse/` (pachet al spațiului de lucru, aproximativ 1.440 de fișiere `.ts` care nu sunt de test)

---

## De ce un pachet separat în spațiul de lucru?

`open-sse/` este un **spațiu de lucru autonom** în monorepo-ul OmniRoute din mai multe motive:

1. **Reutilizare** — `open-sse` este publicat ca `@omniroute/open-sse` pe npm, astfel încât alte proiecte îl pot utiliza independent
2. **Delimitări clare** — motorul de streaming este decuplat de stratul UI/DB specific OmniRoute
3. **Performanță** — motorul nu are dependențe Next.js, permițând porniri la rece mai rapide în contexte CLI/serverless
4. **Versionare** — `open-sse` poate publica versiuni în propriul ritm

```json
// package.json
"workspaces": ["open-sse"]
```

## Fluxul de procesare a solicitărilor

Fiecare solicitare LLM trece printr-un **flux de procesare în 5 etape**:

```
                              ┌──────────────┐
   Solicitare HTTP             │  1. RUTARE   │   rezolvarea combinației, selectarea modelului
   (rută Next.js)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRADUCERE│   conversia formatului (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXECUȚIE │   executor furnizor, HTTP, reîncercare, întrerupător
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAMING│   transformare SSE, contrapresiune
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ÎNREGISTR│   urmărirea utilizării, jurnal apeluri, clasificarea erorilor
                              └──────┬───────┘
                                     │
                                     ▼
                              Răspuns HTTP (SSE sau JSON)
```

### Etapa 1: Rutare (services/combo.ts)

**Punct de intrare**: `handleComboChat()` din `services/combo.ts`

Rezolvă solicitarea într-un tuplu concret `(provider, model, account, credentials)`:

- Caută combinația după ID (sau construiește o combinație virtuală pentru modelele `auto/*`)
- Aplică strategia de rutare (prioritate, ponderată, round-robin etc.)
- Exclude furnizorii cu probleme (întrerupător de circuit)
- Alege următoarea destinație viabilă

Pentru modelele `auto/*`, această etapă efectuează și următoarele:

- Rulează algoritmul de **evaluare pe baza a 16 factori** (`services/autoCombo/`)
- Selectează o pereche `provider+model` pe baza stării de funcționare, costului, latenței etc.

### Etapa 2: Traducere (translator/)

Dacă formatul sursă (de exemplu, OpenAI) diferă de formatul destinație (de exemplu, Claude), solicitarea este **tradusă**:

- Prompt de sistem → mesaj de sistem
- Definițiile instrumentelor → formatul de instrumente specific furnizorului
- Parametrii de raționament/gândire → echivalente specifice furnizorului
- Normalizarea rolurilor mesajelor (`developer` → `system` pentru furnizorii diferiți de OpenAI)

Fișierul `translator/index.ts` expune:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Etapa 3: Execuție (executors/)

**Punct de intrare**: `getExecutor(providerId).execute(request, options)`

Toți furnizorii utilizează `DefaultExecutor` (`executors/default.ts`) prin mecanismul de rezervă al fabricii `getExecutor()`. Executorul:

- Construiește URL-ul upstream (`buildUrl()`)
- Adaugă antetele specifice furnizorului (`buildHeaders()`)
- Transformă corpul solicitării (`transformRequest()`)
- Trimite solicitarea HTTP cu reîncercări și temporizare exponențială
- Gestionează reîmprospătarea autentificării dacă este necesar (furnizori OAuth)

Toți executorii extind `BaseExecutor` (`executors/base.ts`, 1170 LOC), care furnizează:

- Logică comună de reîncercare
- Integrare proxy
- Integrarea întrerupătorului de circuit
- Hook-uri pentru înregistrarea utilizării

### Etapa 4: Streaming (utils/stream.ts)

Pentru răspunsurile transmise în flux, executorul returnează un **ReadableStream**. Gestionarul:

- Direcționează datele printr-o transformare SSE (`createSSETransformStreamWithLogger`)
- Aplică semnale periodice de tip heartbeat pentru a detecta conexiunile întrerupte
- Gestionează elegant deconectarea clientului (`pipeWithDisconnect`)
- Transformă SSE → JSON pentru clienții fără streaming

Pentru răspunsurile fără streaming, executorul returnează un obiect JSON analizat sintactic, care este transmis mai departe fără modificări.

### Etapa 5: Înregistrare (services/usage.ts)

După răspuns (reușit sau eșuat), utilizarea este înregistrată:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` din răspuns
- `cost_usd` calculat pe baza datelor de tarifare
- `latency_ms`, `status`, `error_class` dacă a eșuat
- Persistată în tabelul `usage_history`

Artefactele jurnalului de apeluri (dacă sunt activate) sunt scrise în `${DATA_DIR}/call_logs/`.

## Analiză aprofundată a fișierelor cheie

### chatCore.ts (5977 de linii)

**Gestionarul principal de cereri**. În ciuda dimensiunii sale, are o structură clară:

```ts
// Pseudo-structura fișierului chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autentificare + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validarea corpului
  const body = await parseRequestBody(request);

  // 3. Detectarea formatului + traducere
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Rutarea combo
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Continuă cu următoarea țintă
    }
  }

  // 5. Mecanism de rezervă de urgență
  return await emergencyFallback(body);
}
```

Deși este o singură funcție uriașă, aceasta este organizată în **secțiuni comentate** care corespund fluxului în 5 etape.

### combo.ts (4456 LOC)

**Motorul de rutare** care transformă un combo într-o listă ordonată de ținte.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Acceptă **19 strategii de rutare** (consultați `src/shared/constants/routingStrategies.ts`):

| Strategie           | Comportament                                                                           |
| ------------------- | -------------------------------------------------------------------------------------- |
| `priority`          | Listă ordonată cu prioritate pentru prima țintă                                        |
| `weighted`          | Selecție probabilistică în funcție de ponderea fiecărei ținte                          |
| `round-robin`       | Parcurge ciclic țintele, în ordine                                                     |
| `context-relay`     | Transferă contextul între ținte                                                        |
| `fill-first`        | Epuizează cota înainte de a trece la următoarea țintă                                  |
| `p2c`               | Puterea alegerii dintre două opțiuni                                                   |
| `random`            | Selecție aleatorie uniformă                                                            |
| `least-used`        | O alege pe cea cu cele mai puține utilizări recente                                    |
| `cost-optimized`    | Cea mai ieftină țintă funcțională este aleasă prima                                    |
| `reset-aware`       | Ține cont de ferestrele de resetare ale furnizorului                                   |
| `reset-window`      | Rutare bazată pe fereastra de resetare                                                 |
| `headroom`          | Mai întâi, ținta cu cea mai mare cotă disponibilă rămasă                               |
| `strict-random`     | Cu adevărat uniformă (fără ponderare în funcție de calitate)                           |
| `auto`              | Utilizează punctajul cu 16 factori (`autoCombo/`)                                      |
| `lkgp`              | Ultimul furnizor cunoscut ca fiind funcțional este ales primul                         |
| `context-optimized` | Cea mai bună opțiune pentru cererile cu un context lung                                |
| `fusion`            | Distribuie în paralel către un grup, apoi sintetizează printr-un arbitru (`fusion.ts`) |

### base.ts (1170 LOC)

**Executorul abstract** pe care îl extind toate cele 107 executări. Acesta conține:

- `buildUrl()` — construirea implicită a URL-ului (subclasele o suprascriu pentru personalizare)

- `transformRequest()` — transmitere nemodificată în mod implicit
- `execute()` — bucla HTTP principală, cu reîncercare/backoff/întrerupător

```ts

  // Gestionează toți furnizorii compatibili cu OpenAI/Anthropic
  // Furnizorii înregistrează configurații (URL, autentificare, antete), dar folosesc în comun logica executorului
}
```

Comportamentul specific furnizorului (antetele de autentificare, URL-ul de bază, antetele de versiune) este configurat prin registrul furnizorilor, nu prin clase de executori separate.

````
## Executori (peste 75 de fișiere)

Câte un fișier pentru fiecare furnizor. Toți extind `BaseExecutor` și suprascriu elementele care diferă.

### Tipare comune

Furnizorii sunt rezolvați prin `getExecutor(providerId)`, care returnează executorul configurat. Furnizorii compatibili cu OpenAI/Anthropic utilizează `DefaultExecutor` (`executors/default.ts`). Comportamentul specific furnizorului (URL-ul de bază, anteturile de autentificare, versiunea API) este configurat în `open-sse/config/providers/`, iar transformările corpului cererii sunt gestionate în `open-sse/translator/`.

**URL-ul personalizat** este stabilit prin configurația furnizorului:

```ts
// Configurația furnizorului în open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**Autentificarea personalizată** este gestionată prin configurația de autentificare din registrul furnizorilor (cheie API, OAuth, profiluri de antet).

Transformările **personalizate ale corpului cererii** (de exemplu, separarea de către Anthropic a `system` de `messages`) sunt înregistrate pentru fiecare furnizor în `open-sse/translator/`.

````

### Fabrica de executori

`executors/index.ts` exportă `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Rezolvarea se face prin `ExecutorRegistry` (`executors/registry.ts`): fiecare executor specializat este declarat în tabelul încorporat din `executors/index.ts` și înregistrat prin `registerExecutor(alias, instance)` la încărcarea modulului; `getExecutor()` consultă registrul și revine la un `DefaultExecutor` memorat pentru orice furnizor fără o intrare specializată. Maparea completă alias → executor este descrisă de testul de referință `tests/unit/executor-map-golden.test.ts`.

## Traductoare

Traduce între **3 formate**: OpenAI, Anthropic, Gemini, plus noul Responses API.

### Când are loc traducerea

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Traduceri comune:

- `OpenAI → Anthropic`: câmp `system` separat, antet `x-api-key`
- `OpenAI → Gemini`: `contents` în loc de `messages`, `systemInstruction`
- `OpenAI → Responses API`: matrice `input`, stare `previous_response_id`

### Cazuri-limită gestionate

- Rolul `developer` → `system` pentru furnizorii non-OpenAI
- Rolul `system` → îmbinat în primul mesaj al utilizatorului pentru GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` din Gemini
- `tools` → format de instrument specific furnizorului
- Parametrii de raționament (o1, Claude) → echivalenți specifici furnizorului

## Server MCP

`open-sse/mcp-server/` implementează serverul **Model Context Protocol**:

- **110 instrumente** (gestionarea furnizorilor, combinații, memorie, cache, compresie, proxy, abilități, gamificare, pluginuri, Notion, Obsidian, corpus local)
- **3 transporturi**: stdio, SSE, Streamable HTTP
- **33 de domenii de autorizare** pentru control granular

### Înregistrarea instrumentelor

Instrumentele sunt înregistrate ca fișiere independente în `open-sse/mcp-server/tools/`, fiecare exportând un nume, o schemă, un handler și un domeniu de autorizare:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Obține un instantaneu al stării sistemului",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Transporturi

```ts
// stdio (utilizare CLI)
startMcpStdio(server);

// SSE (streaming bazat pe HTTP)
startMcpSse(server, port);

// Streamable HTTP (MCP modern)
startMcpStreamable(server, port);
```

### Autorizare

Fiecare apel al unui instrument trece prin verificările domeniilor de autorizare (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Domeniu de autorizare insuficient");
}
```

## Transformatoare

`open-sse/transformer/` efectuează conversia între formatele **Chat Completions** și **Responses API**.

### De ce un transformator separat?

Responses API este noul format OpenAI, cu **conversații cu stare** (`previous_response_id`). Când un client trimite o solicitare Responses, OmniRoute:

1. Convertește intern Responses → Chat Completions
2. Trimite solicitarea furnizorului (oricărui furnizor care acceptă Chat Completions)
3. Convertește răspunsul înapoi în formatul Responses
4. Transmite răspunsul convertit către client prin streaming

Transformatorul (`transformer/responsesTransformer.ts`) furnizează:

```ts
createResponsesApiTransformStream(): TransformStream
```

Acesta gestionează:

- Evenimentele `response.output_item.added`
- Evenimentele `response.output_text.delta`
- Evenimentul `response.completed`
- Maparea apelurilor de instrumente (`function_call` ↔ `tool_calls`)

## Configurare

`open-sse/config/` conține stratul de configurare:

| Fișier                        | Scop                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| `providerRegistry.ts`         | Registru de modele de chat pentru catalogul cu 352 de furnizori |
| `providerModels.ts`           | Aliasuri de modele, maparea formatelor                          |
| `constants.ts`                | Timpi de expirare, limite, coduri de stare                      |
| `defaultThinkingSignature.ts` | Semnătura implicită de raționament Claude                       |
| `modelStrip.ts` (în servicii) | Eliminarea câmpurilor pentru fiecare furnizor                   |

### Schema registrului de furnizori

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Validarea Zod la încărcarea modulului asigură faptul că toate configurațiile furnizorilor sunt valide.

## Constrângeri de performanță

Motorul de rutare are bugete stricte de performanță:

| Operațiune                                      | Obiectiv | Măsurare                               |
| ----------------------------------------------- | -------- | -------------------------------------- |
| Rezolvarea combinației                          | <10ms    | Pentru 50 de ținte                     |
| Verificarea limitei de rată                     | <1ms     | Găleată de tokenuri în memorie         |
| Fallback pentru familia de modele               | <5ms     | Definiții de familii memorate în cache |
| Expedierea cererii pentru rutare                | <2ms     | Cale critică                           |
| **Fără I/O blocant în calea critică de rutare** | —        | Totul asincron                         |

## Anti-modele

❌ **Apeluri sincrone către baza de date în `combo.ts`** — precalculați și stocați în cache
❌ **Logică de reîncercare în gestionari** — utilizați `retry()` din serviciul de reziliență
❌ **Acces direct la configurația furnizorului** — utilizați metodele getter din `providerRegistry`
❌ **Lanțuri de fallback codificate direct** — definiți-le în `modelFamilyFallback.ts`
❌ **Modificări ale stării între cereri concurente** — utilizați doar contextul cu domeniu limitat la cerere

## Adăugarea unei componente noi

### Adăugarea unui serviciu nou

1. Creați `open-sse/services/[serviceName].ts` cu o responsabilitate bine delimitată
2. Exportați funcția principală de gestionare și eventualele constante
3. Adăugați teste unitare în `tests/unit/services/[serviceName].test.mjs`
4. Integrați-l în fluxul de procesare a cererilor din `handlers/chatCore.ts` (dacă are legătură cu rutarea)
5. Actualizați logica de rutare din `combo.ts` dacă serviciul afectează selectarea țintei
6. Documentați-l în acest fișier

### Adăugarea unui executor nou

1. Creați `open-sse/executors/[provider].ts` care extinde `BaseExecutor`
2. Înregistrați-l în `config/providerRegistry.ts`
3. Adăugați-l în fabrica din `executors/index.ts`
4. Adăugați teste unitare pentru executor
5. Documentați-l în `docs/architecture/ARCHITECTURE.md`

### Adăugarea unui instrument MCP nou

1. Creați sau actualizați `open-sse/mcp-server/tools/[category]Tools.ts`
2. Definiți schema Zod pentru datele de intrare
3. Înregistrați instrumentul în `mcp-server/index.ts`
4. Adăugați-l în matricea domeniilor de acces din `mcp-server/auth/`
5. Adăugați teste unitare
