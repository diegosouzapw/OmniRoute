AgentBridge este proxy-ul MITM (Man-in-the-Middle) al OmniRoute, care interceptează traficul HTTPS provenit de la agenții AI din IDE-uri și îl redirecționează prin motorul unificat de rutare al OmniRoute. Acesta acceptă **10 agenți IDE** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code și Trae (în curs de investigare) — ceea ce face din OmniRoute proxy-ul MITM cu cea mai extinsă acoperire pentru asistenții AI de programare de pe piață.

**Locație în panoul de control:** `/dashboard/tools/agent-bridge`
**Grup în bara laterală:** Instrumente (după Agenți cloud)
**Consultați și:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — monitorizați în timp real întregul trafic interceptat; `docs/security/MITM-TPROXY-DECRYPT.md` (git; nu este compilat în `/docs`) — modul de capturare Linux TPROXY cu decriptare transparentă, controlat prin ruta `/api/tools/agent-bridge/tproxy`.

## §1 Prezentare generală

### Ce este AgentBridge?

Atunci când un agent IDE (de exemplu, GitHub Copilot, Cursor, Claude Code) efectuează un apel API, acesta se conectează direct la furnizorul AI din amonte (OpenAI, Anthropic etc.). AgentBridge interceptează transparent conexiunea la nivel TLS — fără a necesita modificarea configurației agentului — și rescrie solicitarea prin OmniRoute.

Aceasta înseamnă că puteți:

- **Redirecționa orice agent către orice furnizor**: Copilot comunică cu OpenAI? Redirecționați-l către Anthropic Claude, Gemini sau către oricare dintre cei 352 de furnizori OmniRoute.
- **Aplica mapări de modele**: `gemini-3-flash` → `claude-sonnet-4.7` în mod transparent, la nivelul gestionarului.
- **Observa întregul trafic al agenților**: fiecare solicitare interceptată este publicată în [Inspectorul de trafic](./TRAFFIC_INSPECTOR.md).
- **Aplica mecanismele de reziliență OmniRoute**: rutarea combinată, întrerupătoarele de circuit, mecanismele de rezervă și urmărirea costurilor funcționează și pentru traficul agenților IDE.

## §2 Arhitectură

### 2.1 Prezentare generală a componentelor

```
Agent IDE (VS Code / Cursor / etc.)
    │  HTTPS (portul 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← redirecționare DNS
    │
    ▼
src/mitm/server.cjs  (portul 443, proces copil CJS)
    │  determină ținta după antetul Host și SNI
    │  generează pentru fiecare SNI un certificat TLS semnat de CA-ul AgentBridge
    ├── Corespunde listei de ocolire? → tranzit TCP (fără decriptare)
    ├── Corespunde unei ținte? → fetch → routerul OmniRoute (portul 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() pentru corpul/antetele cererii
    │               ├── TrafficBuffer.push() — publică în Inspectorul de trafic
    │               └── fetchRouter() → /v1/chat/completions
    └── Nicio potrivire? → tranzit TCP (fără decriptare)
```

### 2.2 Serverul MITM (`src/mitm/server.cjs`)

Serverul MITM principal rulează ca proces copil Node.js CJS (pentru a evita rescrierea bazei de cod CJS existente). Acesta:

- Ascultă pe portul 443 (necesită privilegii sau `authbind`/`setcap`)
- Primește tuneluri CONNECT de la sistemul de operare (prin redirecționarea DNS din `/etc/hosts`)
- Generează pentru fiecare SNI certificate TLS semnate de CA-ul AgentBridge (`DATA_DIR/mitm/ca.crt`)
- Determină agentul țintă după antetul Host prin registrul `targets/index.ts`
- Trimite către stratul de gestionare TypeScript prin HTTP la `http://127.0.0.1:20128`

`TARGET_HOSTS` este încărcat din `DATA_DIR/mitm/targets.json` (scris de `targets/index.ts` la pornire), permițând actualizări dinamice fără repornirea serverului CJS.

> **Modelul CA rădăcină (#6684).** Descrierea de mai sus, bazată pe certificate per SNI semnate de o CA,
> reprezintă modelul persistent cu CA rădăcină adăugat în #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, reutilizând criptografia CA/certificat derivat deja
> validată pentru TPROXY în `src/mitm/tproxy/dynamicCert.ts`) — acesta înlocuiește
> vechiul certificat derivat unic, static și autosemnat (`src/mitm/cert/generate.ts`, încă
> limitat doar la gazdele antigravity), indicat de simpla existență pe disc a unei perechi
> `server.crt`/`server.key`. **Comportamentul migrării**: o instalare nouă (fără un
> `server.crt` anterior) primește automat modelul cu CA rădăcină; o instalare care avea deja
> încredere în vechiul certificat derivat static continuă să îl utilizeze până când operatorul setează
> `MITM_ROOT_CA_ENABLED=true` și repornește puntea (`src/mitm/cert/migration.ts`
> este funcția pură de decizie — o CA MITM de încredere care poate semna un certificat derivat pentru
> **orice** gazdă este considerabil mai puternică decât vechiul certificat derivat cu SAN-uri fixe, astfel încât
> comutarea nu se face niciodată în mod silențios pentru o instalare care acordase deja încredere). Certificatul CA este instalat
> în același slot `omniroute-mitm.crt` din depozitul de încredere pe care îl utiliza vechiul certificat derivat
> (`cert/install.ts::installCaCert`) — nu este necesară curățarea unei încrederi duale.

### 2.3 Clasa de bază pentru gestionare (`src/mitm/handlers/base.ts`)

Toate clasele de gestionare ale agenților extind `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Metode ajutătoare protejate: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Fiecare clasă de gestionare apelează `hookBufferStart()` înainte de redirecționare și `hookBufferUpdate()` la finalizare. Acestea introduc intrări `InterceptedRequest` în `globalTrafficBuffer` (consultați [Inspectorul de trafic](./TRAFFIC_INSPECTOR.md) §4).

### 2.4 Registrul de ținte (`src/mitm/targets/`)

Fiecare agent are un fișier declarativ pentru țintă:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Registrul (`targets/index.ts`) exportă `ALL_TARGETS` și generează `DATA_DIR/mitm/targets.json` la pornire.

### 2.5 Tranzit și lista de ocolire (`src/mitm/passthrough.ts`)

**Lista de ocolire** (verificată prima, având prioritate față de potrivirea țintei):

- Modele implicite: gazde bancare, `.gov.`, furnizori OAuth/SSO (Okta, Auth0) etc.
- Modele definite de utilizator: stocate în tabelul DB `agent_bridge_bypass`
- Gazdele ocolite primesc un tunel TCP transparent — traficul TLS nu este **niciodată decriptat**

**Tranzitul implicit** (nicio potrivire cu o țintă și gazda nu se află în lista de ocolire):

- Primește, de asemenea, un tunel TCP — conexiunile nu sunt niciodată întrerupte
- Împiedică AgentBridge să afecteze traficul HTTPS general al sistemului

Ordinea de prioritate a rutării:

```
lista de ocolire → potrivire cu ținta → tranzit
```

### 2.6 Certificatul CA din amonte (`src/mitm/upstreamTrust.ts`)

Pentru mediile de rețea corporative care utilizează o CA personalizată:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Când este setată, configurează dispecerul global al `undici` cu certificatul CA suplimentar, permițând AgentBridge să acceseze furnizorii din amonte prin proxy-uri corporative de terminare TLS.

### 2.7 Mascarea secretelor (`src/mitm/maskSecrets.ts`)

Scanerul independent, implementat de la zero, este aplicat corpurilor cererilor și antetelor cu date de autentificare
**înainte** ca acestea să intre în memoria tampon a Inspectorului de trafic sau în orice jurnal. Acesta efectuează o singură parcurgere liniară:

- Tokenuri cu prefixul `sk-` / `ak-` / `pk-` (în stil OpenAI/Anthropic)
- Date de autentificare RFC 6750 `Authorization: Bearer <token>`, cu prioritate pentru întregul token
- Tokenuri opace lungi generice (≥40 de caractere), inclusiv forme cu puncte și umplutură

`sanitizeHeaders()` convertește la minuscule numele păstrate, concatenează în mod determinist valorile de tip tablou, elimină
lista comună de excludere pentru antetele hop-by-hop/încadrare (inclusiv autentificarea proxy), maschează complet `cookie` și
`set-cookie` și deleagă scanerului valorile datelor de autentificare.

### 3.2 Acordarea încrederii certificatului

Certificatul CA AgentBridge trebuie să fie considerat de încredere de către sistemul de operare înainte ca IDE-urile să accepte conexiunea MITM.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Alternativ, utilizați butonul „Acordare încredere certificatului” din panoul de control (rulează comanda corespunzătoare sistemului dvs. de operare, solicitând parola sudo dacă este necesar).

#### IDE-urile bazate pe Electron ignoră depozitul de încredere al sistemului de operare (`NODE_EXTRA_CA_CERTS`)

Unele IDE-uri — în special **Antigravity IDE** și alte aplicații derivate din Electron / VS Code — includ
propriul lor mediu de execuție Node.js, care **nu consultă depozitul de încredere al sistemului de operare** pentru cererile
`fetch`/HTTPS de ieșire. Acordarea încrederii CA la nivelul sistemului de operare/NSS este suficientă pentru **backendul** nativ
al IDE-ului (de exemplu, un server de limbaj Go, care utilizează pachetul CA al sistemului de operare), însă **frontendul Electron**
va eșua în continuare la negocierea TLS — acest lucru se manifestă prin faptul că aplicația apare ca fiind _deconectată_ sau afișează o
_„eroare de conexiune”_, chiar dacă jurnalul MITM arată că apelurile de inițializare ale backendului returnează `200`. Sunt necesari
doi pași, iar ambii sunt importanți:

1. Indicați explicit mediului de execuție certificatul CA:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Lansați IDE-ul din acel shell.** Pornirea acestuia din pictograma de pe desktop / Dock / meniul Start
   **nu** moștenește variabilele exportate din shell, iar `~/.config/environment.d/*.conf` se aplică numai după
   o nouă autentificare în mediul grafic. Închideți mai întâi complet IDE-ul — mecanismul de blocare pentru o singură instanță din Electron face ca o a doua
   lansare doar să aducă în prim-plan procesul existent, iar noul mediu să fie ignorat.

Pasul de mai sus privind încrederea la nivelul sistemului de operare + NSS rămâne necesar (stiva de rețea Chromium utilizată de unele fluxuri
de autentificare citește depozitul NSS al utilizatorului și are propriile fixări statice pentru `*.googleapis.com`, pe care un
CA considerat de încredere local le suprascrie). `NODE_EXTRA_CA_CERTS` acoperă suplimentar calea Node `fetch`.

### 3.3 Rutarea DNS

Pentru fiecare agent pe care doriți să-l interceptați, gazda sau gazdele sale API trebuie să se rezolve la `127.0.0.1`. AgentBridge gestionează automat intrările din `/etc/hosts` atunci când activați DNS pentru un agent în expertul de configurare.

Exemple de intrări `/etc/hosts` pentru GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Maparea modelelor

Utilizați tabelul de mapare a modelelor din cardul fiecărui agent pentru a defini mapările sursă → destinație:

| Model sursă (nativ agentului) | Model destinație (OmniRoute) |
| ----------------------------- | ---------------------------- |
| `gpt-4o`                      | `claude-sonnet-4.7`          |
| `*` (metacaracter)            | `claude-haiku-4.7`           |

Metacaracterul `*` mapează orice model nerecunoscut la destinația specificată. Mapările sunt păstrate în tabelul `agent_bridge_mappings`.

> **Sfat — identificați ID-urile reale ale modelelor agentului.** Un IDE poate trimite nume de modele care diferă de
> etichetele din interfața sa și care se schimbă între versiunile majore. De exemplu, **Antigravity 2** trimite
> `gemini-3.1-pro-low`, `gemini-pro-agent` și `gemini-3.1-flash-lite` prin rețea — nu
> `gemini-2.5-pro`, afișat în documentația mai veche. Trimiteți un mesaj de chat fără să existe o mapare corespunzătoare: MITM
> înregistrează valoarea exactă primită în `model:` și lasă cererea să treacă mai departe. Mapați acea valoare literală, iar
> următoarea cerere va fi interceptată și rutată către destinația dvs.

### 3.5 Notificare privind riscurile

AgentBridge interceptează acreditările (tokenuri OAuth, chei API) pe care IDE-ul le utilizează pentru autentificarea la furnizorii din amonte. Acestea sunt **mascate înainte de înregistrarea în jurnal** (consultați §2.7), dar sunt vizibile pentru nivelul MITM al OmniRoute. La prima activare a fiecărui agent este afișată o fereastră modală cu o notificare privind riscurile, care poate fi închisă.

Este afișat numai când CA-ul este considerat de încredere; necesită o confirmare în linie „Eliminați CA-ul?”. |
| **Exportare configurație** | `GET /api/tools/agent-bridge/config`   | Descarcă configurația JSON portabilă (consultați §3.7).                                                                                                                                                                                    |
| **Importare configurație** | `POST /api/tools/agent-bridge/config`  | Încarcă o configurație JSON exportată anterior (consultați §3.7).                                                                                                                                                                          |

**Verificări de diagnosticare** (`summarizeDiagnostics()` din `src/mitm/inspector/diagnostics.ts`). Ruta rulează verificarea cu efecte pentru fiecare element și transmite valorile booleene către funcția pură de sintetizare; sunt returnate un singur verdict `healthy` și o sugestie pentru fiecare eșec:

| Numele verificării | Ce verifică                                                 | Sugestie în caz de eșec                                                                                                                                                                       |
| ------------------ | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | Procesul serverului MITM este activ                         | „Serverul MITM nu rulează. Porniți-l din fila AgentBridge.”                                                                                                                                   |
| `server-reachable` | Serverul MITM acceptă conexiuni pe portul său (sondă TCP)   | „Serverul MITM nu acceptă conexiuni pe portul său. Verificați dacă portul este liber și dacă aveți privilegii pentru a-l asocia.”                                                             |
| `cert-exists`      | Certificatul MITM a fost generat pe disc                    | „Nu a fost generat încă niciun certificat MITM. Generați unul din fila AgentBridge.”                                                                                                          |
| `cert-trusted`     | CA-ul rădăcină MITM se află în depozitul de încredere al SO | „CA-ul rădăcină MITM nu este considerat de încredere de către depozitul SO, astfel încât interceptarea TLS va eșua. Acordați încredere certificatului din fila AgentBridge.”                  |
| `dns-configured`   | Numele de gazdă țintă sunt falsificate în `/etc/hosts`      | „Numele de gazdă țintă nu sunt falsificate în /etc/hosts, astfel încât traficul nu ajunge niciodată la proxy. Activați DNS pentru agentul sau agenții al căror trafic doriți să-l capturați.” |

**Banner pentru starea orfană:** când pagina detectează o stare rămasă în urma unei blocări (falsificare DNS / CA / proxy de sistem), cardul afișează un banner portocaliu — _„O sesiune anterioară a lăsat în urmă o stare de sistem (falsificare DNS, CA sau proxy de sistem). Rulați Reparare pentru a o curăța.”_ — și evidențiază butonul **Reparare**. `Repair` este echivalentul la nivelul aplicației al opțiunii `--cleanup` din ProxyBridge (delegă către `repairMitm()` din `src/mitm/manager.ts`).

> CA-ul rădăcină MITM rămâne instalat între opriri și porniri pentru a evita solicitările
> sudo repetate (același comportament ca mitmproxy/Charles), astfel încât eliminarea sa este o acțiune
> explicită **Eliminare CA**, în loc să se producă automat la oprire.

### 3.7 Importarea/exportarea configurației portabile

AgentBridge poate serializa starea **configurabilă de către operator** într-un obiect JSON cu versiune, astfel încât o configurație să poată fi reprodusă pe mai multe sisteme. Serializatorul este `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), validat de `AgentBridgeConfigSchema`.

Exportul include exact trei componente (valorile implicite integrate **NU** sunt exportate în mod intenționat, astfel încât importarea să nu le dubleze și să nu intre niciodată în conflict cu acestea):

| Câmp             | Sursă                                                            | Note                                                                       |
| ---------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `bypassPatterns` | modele de ocolire definite de utilizator (`agent_bridge_bypass`) | modelele implicite pentru bănci/administrații publice/okta sunt excluse    |
| `customHosts`    | gazde personalizate Traffic Inspector (`inspector_custom_hosts`) | fiecare: `{ host, kind: "llm"\|"app"\|"custom", label? }`                  |
| `agentMappings`  | mapări de modele pentru fiecare agent (`agent_bridge_mappings`)  | `{ [agentId]: [{ source, target }] }` pentru fiecare agent care are mapări |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Comportamentul la importare** (`POST /api/tools/agent-bridge/config`): modelele de ocolire și mapările pentru fiecare agent sunt **înlocuite integral**; gazdele personalizate sunt adăugate **idempotent** (`INSERT OR IGNORE`). Răspunsul raportează câte elemente din fiecare categorie au fost aplicate:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Ce **NU** se află în configurație: starea de funcționare a serverului, căile certificatelor, starea DNS pentru fiecare agent, calea către CA-ul din amonte și setările TPROXY — acestea reprezintă starea gazdei/a mediului de execuție, nu preferințe portabile.

## §5 Securitate

### Reguli stricte aplicate

| Regulă                              | Aplicare                                                                                                          |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`      | Toate erorile gestionarilor sunt igienizate înainte de răspuns sau de introducerea în buffer                      |
| **#13** Transmiterea mediului shell | Editările în `/etc/hosts` folosesc opțiunea `env` — fără interpolarea căilor în șiruri                            |
| **#15 + #17** `isLocalOnlyPath()`   | `/api/tools/agent-bridge/` este LOCAL_ONLY + SPAWN_CAPABLE — accesul loopback este impus înainte de autentificare |

### Lista de ocolire pentru gazde sensibile

Lista de ocolire garantează că instituțiile financiare, furnizorii OAuth/SSO și alte gazde sensibile nu sunt **niciodată decriptate**. Traficul TLS al acestora trece printr-un tunel TCP transparent — OmniRoute nu vede niciodată textul în clar.

Modelele implicite de ocolire includ:

- `*.bank.*`, `*.gov.*` (instituții financiare/guvernamentale)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/identitate)
- `*.apple.com`, `*.icloud.com` (servicii de sistem Apple)

Modelele de ocolire adăugate de utilizator sunt stocate în tabelul `agent_bridge_bypass` și au prioritate față de orice altceva.

### Mascarea secretelor

Se aplică `maskSecrets()` din `src/mitm/maskSecrets.ts`:

- Pentru fiecare corp al cererii înainte de `TrafficBuffer.push()`
- Pentru fiecare antet înainte de jurnalizare sau difuzare

Modele: tokenuri cu prefixul `sk-`/`ak-`/`pk-`, tokenuri `Bearer` și tokenuri generice cu ≥40 de caractere.

### Certificatul CA din amonte

Când este setată variabila `AGENTBRIDGE_UPSTREAM_CA_CERT`, fișierul este citit la pornire. Dacă acea cale există, dar fișierul nu poate fi citit, AgentBridge înregistrează o eroare clară și refuză să pornească (prevenind erorile TLS nedetectate în mediile corporative).

### Limitări cunoscute

- **Portul 443 necesită privilegii**: Pe Linux, AgentBridge necesită `setcap 'cap_net_bind_service=+ep'` pe binarul Node sau trebuie rulat prin `authbind`. Expertul de configurare afișează instrucțiuni specifice sistemului de operare.
- **Este necesară repornirea IDE-ului**: După redirecționarea DNS, IDE-ul trebuie repornit pentru ca noua rezoluție a gazdei să intre în vigoare.
- **Tokenuri OAuth codificate direct**: Unii agenți (Kiro, Antigravity) stochează local tokenurile OAuth de reîmprospătare. Acestea sunt transparente pentru AgentBridge — acesta vede tokenul Bearer în fiecare cerere, care este mascat înainte de jurnalizare.
- **Interfețele Electron necesită `NODE_EXTRA_CA_CERTS`**: IDE-urile a căror interfață rulează într-un mediu Node/Electron inclus ignoră depozitul de încredere al sistemului de operare/NSS și trebuie lansate dintr-un shell cu `NODE_EXTRA_CA_CERTS` setată (consultați §3.2). Simptom atunci când lipsește: backendul IDE-ului se autentifică (MITM afișează răspunsuri `200`), dar interfața rămâne deconectată.
- **Instalările multiple ale aceluiași IDE sunt independente**: o instalare de sistem (de exemplu, `/usr/share/antigravity/antigravity`) și o instalare „Full” locală a utilizatorului (de exemplu, `~/AntigravityIDE_Full/antigravity-ide`) sunt procese separate, cu propriile lor medii de execuție — fiecare trebuie relansată cu certificatul CA injectat. Identificați care dintre ele rulează după calea binarului înainte de relansare.
- **Identitatea este stabilită de promptul de sistem al agentului, nu de modelul rutat**: atunci când remapați modelul unui agent către un alt furnizor, răspunsul continuă să revendice identitatea nativă a agentului (de exemplu, Antigravity răspunde „Sunt alimentat de Gemini”), deoarece IDE-ul injectează acest lucru în promptul de sistem. Confirmați backendul real în `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), nu întrebând modelul cine este.

## §6 Depanare

### Conflict pe portul 443

Dacă un alt proces ascultă deja pe portul 443 (server web, VPN etc.):

```bash
lsof -i :443          # găsește procesul
sudo fuser -k 443/tcp  # oprește forțat procesul (utilizați cu atenție)
```

Alternativ, configurați un port neprivilegiat în setările AgentBridge și configurați reguli de redirecționare `iptables` / `pf`.

### Certificat care nu este de încredere

Dacă IDE-ul afișează erori TLS după pornirea AgentBridge:

1. Verificați dacă certificatul a fost instalat: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) sau `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Unele aplicații își gestionează propriul magazin de încredere (Firefox, Chrome pe Linux). Rulați din nou „Trust Cert” și verificați magazinul de certificate specific NSS/Firefox.
3. Reporniți IDE-ul după acordarea încrederii — sesiunile TLS aflate în desfășurare utilizează starea de încredere anterioară.

### IDE deconectat / „eroare de conexiune” în ciuda unei CA de încredere

Simptom: după redirecționarea DNS și acordarea încrederii pentru CA, un IDE bazat pe Electron (de exemplu, Antigravity)
se deschide **cu utilizatorul deconectat** sau afișează o eroare de autentificare/conexiune, deși jurnalul MITM arată că
apelurile de inițializare (`loadCodeAssist`, `fetchAvailableModels`, …) returnează `200`.

Cauză: mediul de execuție **Node/Electron inclus în IDE ignoră magazinul de încredere al sistemului de operare**. Componenta backend
nativă (un server de limbaj Go) acordă încredere CA-ului sistemului de operare și se autentifică, dar componenta frontend Electron
nu o face — astfel, interfața cu utilizatorul consideră că este offline.

Remediere (ambii pași): exportați `NODE_EXTRA_CA_CERTS=<ca.crt>` **și relansați IDE-ul din acel
shell**, nu de la pictograma de pe desktop. Închideți mai întâi complet IDE-ul — blocarea pentru instanță unică din Electron înseamnă
că o a doua lansare doar aduce în prim-plan procesul existent, iar noul mediu este ignorat. Consultați §3.2.
Aceasta reflectă un raport deschis în amonte, în care un agent independent funcționează printr-un MITM, dar varianta IDE
eșuează în aceeași configurație.

### DNS nepropagat

Verificați dacă `/etc/hosts` a fost actualizat:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Goliți memoria cache DNS:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE nedetectat

Detectarea automată utilizează căi de instalare uzuale. Dacă detectarea eșuează, dar IDE-ul este instalat:

- Verificați dacă fișierul binar al IDE-ului se află într-o locație nestandard
- Expertul de configurare funcționează în continuare — eșecul detectării înseamnă doar că insigna nu va afișa calea de instalare

### Erori ale handlerului (preluarea din amonte eșuează)

Dacă AgentBridge interceptează, dar toate solicitările eșuează:

1. Verificați dacă este conectat cel puțin un furnizor la `/dashboard/providers`
2. Verificați jurnalele serverului OmniRoute: `APP_LOG_LEVEL=debug` în `.env`
3. Verificați dacă `OMNIROUTE_BASE_URL` indică endpointul corect al routerului (implicit: `http://127.0.0.1:20128`)

## §8 Foaie de parcurs

### Investigarea Trae

Trae este un asistent de programare cu IA relativ nou. Înainte de implementarea unui handler:

1. Identificați binarul/extensia în marketplace-urile VS Code / JetBrains sau ca aplicație autonomă
2. Capturați traficul cu mitmproxy pentru a descoperi gazdele API și structura endpoint-urilor
3. Determinați mecanismul de autentificare
4. Evaluați decizia de continuare sau renunțare pe baza TOS și a posibilității de descoperire a API-ului

Până la finalizarea investigației, cardul Trae din tabloul de bord afișează o insignă „În curs de investigare” cu un link „Raportați viabilitatea”. Stub-ul handlerului din `src/mitm/handlers/trae.ts` generează o eroare structurată `Neimplementat încă`.

### Agenți din backlog (MITM obligatoriu — fără suport pentru un URL de bază personalizat)

Următoarele instrumente nu acceptă URL-uri de bază personalizate în versiunile lor actuale, ceea ce face ca MITM să fie singura metodă de interceptare. Evaluarea viabilității este în așteptare:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — separat de Kiro IDE)
- **Cowork** (aplicația desktop Anthropic)

Notă: GitHub Copilot CLI ≥v1.0.19 acceptă `COPILOT_PROVIDER_BASE_URL` — utilizați configurarea directă în locul MITM pentru acest instrument.
