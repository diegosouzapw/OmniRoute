OmniRoute ایسے فراہم کنندگان کے ساتھ انٹیگریٹ ہوتا ہے جن کے ایج سسٹمز غیر سرکاری کلائنٹس کی فعال طور پر فنگرپرنٹنگ کرتے ہیں (TLS JA3/JA4، ہیڈر کی ترتیب، JSON باڈی کی ساخت، انٹیگریٹی ٹوکنز)۔ یہ صفحہ OmniRoute کی فراہم کردہ اسٹیلتھ سطحوں اور ان کے نفاذ کے مقامات کو دستاویزی شکل دیتا ہے۔

## قانونی اور اخلاقی نوٹس

اسٹیلتھ خصوصیات اس لیے موجود ہیں تاکہ OmniRoute صارف کی ملکیت والے سرکاری اکاؤنٹس (Claude Code CLI، Codex، Antigravity، Cursor، وغیرہ) اور OmniRoute کی متحد API کے درمیان مطابقتی تہہ کے طور پر کام کر سکے۔ یہ فراڈ کی شناخت سے بچنے، اسناد کا اشتراک کرنے، یا فراہم کنندہ کی سروس کی شرائط کی خلاف ورزی کے لیے **نہیں** ہیں۔ مینٹینرز آپریٹرز سے توقع کرتے ہیں کہ وہ اکاؤنٹس بناتے وقت قبول کردہ اپ اسٹریم ToS کی پابندی کریں گے۔

## TLS فنگرپرنٹنگ تہہ

### `open-sse/utils/tlsClient.ts` — wreq-js (Chrome 124)

مستقل `wreq-js` سیشنز ہر اکاؤنٹ اسکوپ اور حل شدہ پراکسی کے لیے ضرورت پڑنے پر بنائے جاتے ہیں۔ پورے پروسیس کا `TlsClient` زیادہ سے زیادہ 128 سیشنز کو پول کرتا ہے، جو Cloudflare کے پیچھے موجود اپ اسٹریمز کے لیے **macOS پر Chrome 124** کی نقل کرتے ہیں۔ جب نیٹو رن ٹائم دستیاب نہ ہو تو `TlsClient.fetch()` محفوظ انداز میں ناکام ہو جاتا ہے؛ کالر اس ریپر کے باہر واضح طور پر کوئی فال بیک منتخب کر سکتا ہے۔

- سیشن پروفائل: `browser: "chrome_124", os: "macos"`
- پراکسی ریزولیوشن (ترجیح): `HTTPS_PROXY` → `HTTP_PROXY` → `ALL_PROXY` (چھوٹے حروف والی صورتیں بھی)
- ٹائم آؤٹ: `TLS_CLIENT_TIMEOUT_MS` (`FETCH_TIMEOUT_MS` سے وراثت میں ملتا ہے، ڈیفالٹ 600000)
- `wreq-js` Response، fetch کے ساتھ مطابقت رکھتا ہے (`headers`، `text()`، `json()`، `clone()`، `body`)۔
- فرسٹ بائٹ واچ ڈاگ (`open-sse/utils/tlsFirstByteWatchdog.ts`، #12656): اپ اسٹریم ہیڈرز پہنچتے ہی `TlsClient.fetch()`
  حل ہو جاتا ہے، اس لیے صرف `TLS_CLIENT_TIMEOUT_MS` ایسی باڈی کو محدود نہیں کر سکتا جو کبھی پہلی بائٹ فراہم نہ کرے۔
  `guardTlsFirstByte()` باڈی کے پہلے `read()` اور `TLS_FIRST_BYTE_WATCHDOG_MS` (ڈیفالٹ `10000`، `0` اسے غیر فعال کرتا ہے)
  کے درمیان ریس کرواتا ہے؛ صحت مند باڈی متاثر نہیں ہوتی، جبکہ رکی ہوئی باڈی wreq ریڈر کو منسوخ کر دیتی ہے اور
  `proxyFetch` کی موجودہ TLS فال بیک منطق کو براہ راست/پراکسی ڈسپیچر تک گرنے دیتی ہے (ری پلے کے لیے غیر محفوظ درخواست،
  مثلاً باڈی کے ساتھ POST، خاموشی سے دوبارہ آزمائے جانے کے بجائے پھر بھی ایرر دیتی ہے)۔

### ویب کوکی فراہم کنندہ ٹرانسپورٹ — wreq-js 3.2.0

`open-sse/services/tlsClientBase.ts` ذیل کے پانچ مخصوص ویب کوکی ٹرانسپورٹس کے لیے مشترکہ اڈاپٹر ہے۔ ہر مختصر فراہم کنندہ ریپر ایک براؤزر/OS پروفائل منتخب کرتا ہے۔ اڈاپٹر `open-sse/utils/tlsClient.ts` میں موجود واحد wreq رن ٹائم لوڈر اور ٹرانسپورٹ پول استعمال کرتا ہے، جس کی کلید پروفائل + OS + حل شدہ پراکسی ہوتی ہے، جبکہ ہر درخواست `cookieMode: "ephemeral"` استعمال کرتی ہے۔ لہٰذا اکاؤنٹس اور درخواستیں ٹرانسپورٹ سطح کے کنکشنز کا اشتراک کرتی ہیں، مگر کبھی بھی wreq سیشن یا کوکی جار کا نہیں۔

| فراہم کنندہ | پروفائل       | نقل کردہ OS | اسٹریم EOF پالیسی                       |
| ----------- | ------------- | ----------- | --------------------------------------- |
| Claude      | `chrome_146`  | Linux       | `[DONE]` شامل کریں                      |
| Perplexity  | `firefox_148` | macOS       | `event: end_of_stream` شامل کریں        |
| Grok        | `chrome_146`  | Linux       | `[DONE]` خارج کریں                      |
| Notion      | `chrome_146`  | Windows     | `[DONE]` شامل کریں                      |
| LMArena     | `chrome_146`  | Windows     | کوئی سینٹینل نہیں؛ نیٹو EOF پر بند کریں |

- اسٹریمنگ براہ راست نیٹو Response کے `ReadableStream` کو استعمال کرتی ہے؛ کوئی عارضی فائل یا سائیڈ کار
  نہیں بنایا جاتا۔
- اسٹریم ظاہر کرنے سے پہلے زیادہ سے زیادہ ابتدائی 256 بائٹس کا معائنہ کیا جاتا ہے۔ SSE فراہم کنندگان غیر SSE
  ایررز کو بفر کرتے ہیں؛ Grok/LMArena، Cloudflare چیلنجز کو `403` اور HTML انٹرسٹیشلز کو `502` سے میپ کرتے ہیں۔
- نیٹو درخواست کا ٹائم آؤٹ ایک مطلق JS ہارڈ ڈیڈ لائن میں لپٹا رہتا ہے۔ ہینگ ہونے کی صورت میں صرف متاثرہ
  پروفائل/OS/پراکسی ٹرانسپورٹ کو غیر مؤثر کر کے بند کیا جاتا ہے، اس سے پہلے کہ اگلی درخواست اسے دوبارہ بنائے۔
- پراکسی ریزولیوشن کی ترجیح فی کال `proxyUrl` → درخواست کے اسکوپ والا اکاؤنٹ/ڈیش بورڈ کانٹیکسٹ →
  `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (چھوٹے حروف والی صورتوں سمیت) ہے۔ ریزولیوشن ایررز براہ راست کنکشن
  لیک کرنے کے بجائے محفوظ انداز میں ناکام ہوتے ہیں۔ LMArena دانستہ طور پر `arena.ai` کے مطابق ریزولیوشن کرتا ہے۔
- `byteResponse`، UTF-8 خرابی کے بغیر مواد کی قسم پر مبنی `data:` URL واپس کرتا ہے۔
- ایررز `TlsClientUnavailableError` (پیکیج/ایڈ آن دستیاب نہیں)، `TlsClientHangError`
  (ڈیڈ لائن گزر گئی)، اور `WreqTransportCapacityError` (مشترکہ سیشن گنجائش کا ایرر کوڈ)
  ہوتے ہیں، جب تمام 128 محدود پروفائل/OS/پراکسی سلاٹس فعال ہوں یا بند ہو رہے ہوں۔

اوپر موجود عمومی `TlsClient` سیشن مستقل براؤزر کی پشت پناہی والی کوکی حالت کے لیے مخصوص رہتا ہے۔ دونوں راستے ایک ہی کیش شدہ wreq ماڈیول لوڈر اور پروسیس لائف سائیکل ہک کو دوبارہ استعمال کرتے ہیں؛ ان کے پولز الگ رہتے ہیں کیونکہ ان کی کوکی کی مدتِ حیات دانستہ طور پر مختلف ہے۔

پروفائلز کو پن شدہ پیکیج سپورٹ کرتا ہے، لیکن حقیقی WAF قبولیت مقامی کنٹریکٹ ٹیسٹس سے آزادانہ طور پر تبدیل ہو سکتی ہے۔ اپ اسٹریم براؤزر کے ساتھ یکسانیت کا دعویٰ کرنے سے پہلے، واضح طور پر مجاز لائیو اکاؤنٹ کے ذریعے فنگرپرنٹ تبدیلیوں کی توثیق کریں۔

## Claude Code اسٹیلتھ بنڈل

جب `cliCompatMode` فعال ہو، تو OmniRoute باہر جانے والی Claude درخواستوں کو اس طرح ڈھالتا ہے کہ وہ `claude-cli` ٹریفک سے ناقابلِ امتیاز ہوں۔ تین ماڈیول باہمی تعاون کرتے ہیں:

### `claudeCodeFingerprint.ts`

بلنگ ہیڈر میں شامل 3-حرفی `cc_version` فنگرپرنٹ کا حساب لگاتا ہے:

```
SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

- `FINGERPRINT_SALT = "59cf53e54c78"` (ہارڈ کوڈ شدہ؛ آفیشل کلائنٹ سے مطابقت رکھتا ہے)
- اِن پٹس: پہلے صارف کے پیغام کے متن میں انڈیکس 4، 7، 20 پر موجود حروف + ورژن اسٹرنگ
- آؤٹ پٹ: 3-حرفی ہیکس سابقہ

### `claudeCodeCCH.ts` (کلائنٹ مواد ہیش)

سرور سائیڈ سالمیت کی جانچ، جسے آفیشل Claude Code CLI، Bun/Zig کے ذریعے شمار کرتا ہے۔ OmniRoute اسے `xxhash-wasm` کے ساتھ دوبارہ نافذ کرتا ہے:

1. باڈی کو `cch=00000;` پلیس ہولڈر کے ساتھ سیریلائز کریں
2. `xxhash64(bytes, seed) & 0xFFFFF`
3. صفر سے پیڈ کردہ 5-حرفی چھوٹے حروف والا ہیکس
4. `cch=00000;` کو شمار کردہ ٹوکن سے تبدیل کریں

مستقل قدریں:

- سیڈ: `0x6e52736ac806831e`
- پیٹرن: `/\bcch=([0-9a-f]{5});/`

### `claudeCodeObfuscation.ts`

"حساس" کلائنٹ ناموں کے پہلے حرف کے بعد ایک یونیکوڈ **صفر چوڑائی جوائنر** (`U+200D`) داخل کرتا ہے، تاکہ اپ اسٹریم فلٹرز انہیں grep نہ کر سکیں۔ ڈیفالٹ الفاظ کی فہرست:

```
opencode, open-code, cline, roo-cline, roo_cline, cursor, windsurf,
aider, continue.dev, copilot, avante, codecompanion
```

اس پر لاگو ہوتا ہے: `system` بلاکس، تمام `messages[].content`، اور `tools[].description` / `tools[].function.description`۔ آپریٹر اسے `setSensitiveWords()` کے ذریعے تبدیل کر سکتا ہے۔

### `claudeCodeCompatible.ts` — `anthropic-compatible-cc-*` فراہم کنندگان

فریقِ ثالث کے ان Anthropic ریلے کے لیے جو صرف "حقیقی Claude Code" ٹریفک قبول کرتے ہیں:

- `CLAUDE_CODE_COMPATIBLE_USER_AGENT = "claude-cli/2.1.258 (external, sdk-cli)"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_PACKAGE_VERSION = "0.112.1"`
- `CLAUDE_CODE_COMPATIBLE_STAINLESS_RUNTIME_VERSION = "v26.3.0"`
- ڈیفالٹ طور پر `anthropic-beta = "claude-code-20250219,interleaved-thinking-2025-05-14,effort-2025-11-24"`
- فی کنکشن "Enable redact-thinking beta" ٹوگل، جب کسی CC Compatible اپ اسٹریم کو خاص طور پر مخفی کردہ تھنکنگ اسٹریمز درکار ہوں، تو `redact-thinking-2026-02-12` شامل کرتا ہے
- فی کنکشن "Enable summarized thinking display" ٹوگل `providerSpecificData.requestDefaults.summarizeThinking` محفوظ کرتا ہے اور ان CC Compatible تھنکنگ درخواستوں میں `display: "summarized"` شامل کرتا ہے جن میں پہلے سے ڈسپلے موڈ مقرر نہیں کیا گیا
- `CONTEXT_1M_BETA_HEADER = "context-1m-2025-08-07"` (Opus/Sonnet 4.x خاندان)
- ڈیفالٹ پاتھ: `/v1/messages?beta=true`

اسی بنڈل میں موجود متعلقہ ماڈیولز:

- `claudeCodeConstraints.ts` — درجۂ حرارت + کیش کنٹرول کے قواعد
- `claudeCodeToolRemapper.ts` — ٹول ناموں کی دوبارہ میپنگ
- `claudeCodeExtraRemap.ts` — اضافی پے لوڈ کی معمول کاری

## Antigravity اسٹیلتھ

Antigravity درخواستیں کالر کے متن کو بائٹ بہ بائٹ برقرار رکھتی ہیں۔ OmniRoute پرامپٹس میں صفر چوڑائی والے حروف داخل نہیں کرتا اور نہ ہی کسی IDE کلائنٹ کی نقل کے لیے ٹولز کے نام بدلتا یا انہیں داخل کرتا ہے۔

### `antigravityHeaderScrub.ts`

فارورڈ کرنے سے پہلے Stainless SDK مارکرز (`x-stainless-lang`، `x-stainless-package-version`، `x-stainless-os`، `x-stainless-arch`، `x-stainless-runtime`، `x-stainless-runtime-version`، `x-stainless-timeout`، `x-stainless-retry-count`، `x-stainless-helper-method`) ہٹا دیتا ہے۔

### ⚠️ خطرہ: `ANTIGRAVITY_CREDITS=always` (اکاؤنٹ پابندی کا انتہائی حساس مقام)

`ANTIGRAVITY_CREDITS=always` (جسے `open-sse/executors/antigravity.ts` استعمال کرتا ہے) **ہر** درخواست کو Google کے مفت درجے کے کوٹے کے ذریعے محدود ہونے دینے کے بجائے Antigravity AI Credit Overages (ادا شدہ Google کریڈٹس) کے ذریعے روٹ کرتا ہے۔ اسے ایک خصوصیت کے طور پر دستاویز کیا گیا ہے، لیکن یہ **ہمیں موصول ہونے والی ToS خلاف ورزی کی رپورٹوں کی واحد سب سے عام وجہ ہے** — `=always` کے ساتھ چند گھنٹے چلنے کے بعد متعدد Google Ultra اکاؤنٹس پر `403 / "service disabled for ToS violation" / insufficient_quota` کے ساتھ پابندی لگ چکی ہے۔

اپ اسٹریم نفاذ **Google کی جانب سے** ہوتا ہے، اور OmniRoute اسے روک نہیں سکتا۔ ماحول متغیر کا نام اور موجودہ دستاویزات اسے ایک محفوظ اختیار کی طرح ظاہر کرتے ہیں؛ لیکن یہ محفوظ نہیں ہے۔

**یہ صرف مفت درجے کے استعمال کی نسبت زیادہ جارحانہ انداز میں غلط استعمال کی نشاندہی کیوں متحرک کرتا ہے:**

- ایک Google اکاؤنٹ پر مسلسل خودکار اخراجات، مفت درجے کے کوٹے تک پہنچ کر رک جانے والے استعمال کی نسبت مختلف انداز میں نشان زد ہوتے ہیں۔
- کریڈٹ اووریجز پر شرح کی کوئی حد نہیں، لہٰذا غلط کنفیگر شدہ کلائنٹ چند منٹوں میں کئی سو USD خرچ کر سکتا ہے اور API کلید کی دوبارہ فروخت یا بوٹ ٹریفک جیسا نظر آ سکتا ہے۔
- ایک ہی بیرونی IP سے متعدد OmniRoute صارفین کا متوازی طور پر اووریج کریڈٹس استعمال کرنا اس سگنل کو مزید مضبوط کرتا ہے۔

**تجویز کردہ طرزِ عمل:**

1. ڈیفالٹ `ANTIGRAVITY_CREDITS=off` برقرار رکھیں، جب تک آپریٹر واضح طور پر ادا شدہ کریڈٹ اور اکاؤنٹ پر نفاذ کا خطرہ قبول نہ کرے۔ `retry` پہلے معمول کی درخواست بھیجتا ہے اور اہل کوٹا 429 کے بعد زیادہ سے زیادہ ایک مرتبہ کریڈٹس داخل کرتا ہے؛ `always` پہلی ہی درخواست میں کریڈٹس داخل کرتا ہے۔
2. کسی ایک Antigravity اکاؤنٹ کو مکمل طور پر مصروف کرنے کے بجائے **Auto-Combo کے ذریعے لوڈ کو فراہم کنندگان میں تقسیم کریں** (`model: "auto"` یا `kr/glm/etc`-combo)۔
3. Antigravity فراہم کنندہ کے ترمیمی صفحے میں **فی کنکشن RPM حدود مقرر کریں** (Dashboard → Providers → Antigravity → connection → rate limit)۔ مسلسل استعمال کے لیے 30–60 RPM ایک قابلِ دفاع بالائی حد ہے۔
4. **مستحکم، آپریٹر کے زیرِ کنٹرول اپ اسٹریم نیٹ ورکنگ استعمال کریں** اور ایک اکاؤنٹ کو غیر متعلقہ صارفین یا ورک لوڈز کے درمیان شیئر کرنے سے گریز کریں۔
5. **پابندی لگنے کی صورت میں**: Google کی بھیجی ہوئی عین `quota_exceeded` / `service disabled` رسپانس باڈی کے ساتھ `support.google.com` → "Restore Workspace/Account access" کے ذریعے اپیل کریں۔ بحالی کی ضمانت نہیں ہے۔

ماحول کا حوالہ ہر کریڈٹس موڈ کے اکاؤنٹ اور اخراجات سے متعلق مضمرات کو دستاویز کرتا ہے۔

متاثرہ مقامات:

- `open-sse/executors/antigravity.ts` — `process.env.ANTIGRAVITY_CREDITS` پڑھتا ہے
- `src/lib/oauth/providers/antigravity.ts` — اسناد کی پلمبنگ
- اصل واقعے کی رپورٹ: مباحثہ [#1183](https://github.com/diegosouzapw/OmniRoute/discussions/1183)

## CLI فنگرپرنٹ رجسٹری — `open-sse/config/cliFingerprints.ts`

ہر فراہم کنندہ کے لیے ایک جدول جو آفیشل CLIs کے mitmproxy ٹریسز سے حاصل کردہ ہیڈر کی **عین** ترتیب اور JSON باڈی فیلڈز کی ترتیب کو مقرر کرتا ہے۔ فی الحال رجسٹرڈ: `codex`، `claude`، نیز `antigravity` اور `github` کے لیے `providerHeaderProfiles.ts` میں رن ٹائم سے اخذ کردہ پروفائلز۔

```ts
interface CliFingerprint {
  headerOrder: string[]; // حروف کی ہیئت کے لحاظ سے حساس
  bodyFieldOrder: string[]; // اعلیٰ سطح کی JSON کلیدیں
  userAgent?: string | (() => string);
  extraHeaders?: Record<string, string>;
}
```

ہر فراہم کنندہ کے لیے env کے ذریعے فعال یا غیر فعال کریں (نیچے دیکھیں)۔ غیر فعال ہونے پر ہیڈرز/باڈی کلیدیں اسی ترتیب میں ظاہر ہوتی ہیں جس ترتیب میں Node/JSON نے انہیں فراہم کیا — جس سے فنگرپرنٹ بنانا آسان ہو جاتا ہے۔

## MITM پراکسی (Antigravity، Linux/macOS/Windows)

ان CLIs کے لیے جن کی بائنریز کو `OPENAI_BASE_URL` کے ذریعے ری ڈائریکٹ نہیں کیا جا سکتا، OmniRoute ایک مقامی TLS ختم کرنے والی پراکسی چلاتا ہے۔ اینڈ پوائنٹس `src/app/api/cli-tools/antigravity-mitm/` کے تحت موجود ہیں۔

| طریقہ  | اینڈ پوائنٹ                             | مقصد                                                 |
| ------ | --------------------------------------- | ---------------------------------------------------- |
| GET    | `/api/cli-tools/antigravity-mitm`       | حالت — چل رہا ہے، pid، dnsConfigured، certExists     |
| POST   | `/api/cli-tools/antigravity-mitm`       | MITM شروع کریں (`apiKey` + `sudoPassword` درکار ہیں) |
| DELETE | `/api/cli-tools/antigravity-mitm`       | MITM روکیں                                           |
| GET    | `/api/cli-tools/antigravity-mitm/alias` | ماڈل عرفیات کی فہرست                                 |
| PUT    | `/api/cli-tools/antigravity-mitm/alias` | کسی ٹول کے لیے ماڈل عرفیات محفوظ کریں                |

ہدف بنایا گیا میزبان: **`daily-cloudcode-pa.googleapis.com`** (Antigravity کا اپ اسٹریم)۔

### آغاز کی ترتیب (`src/mitm/manager.ts::startMitm`)

1. `selfsigned` کے ذریعے خود دستخط شدہ سرٹیفکیٹ بنائیں (RSA-2048، SHA-256، 1y) — `cert/generate.ts`
2. سرٹیفکیٹ کو سسٹم ٹرسٹ اسٹور میں انسٹال کریں — `cert/install.ts`
3. ہوسٹس اندراج `127.0.0.1 daily-cloudcode-pa.googleapis.com` شامل کریں — `dns/dnsConfig.ts`
4. `ROUTER_API_KEY` + `MITM_LOCAL_PORT` (ڈیفالٹ `443`) کے ساتھ `src/mitm/server.cjs` کو اسپان کریں
5. PID کو `<DATA_DIR>/mitm/.mitm.pid` میں محفوظ رکھیں

### Linux کی متحرک ٹرسٹ اسٹور شناخت — `cert/install.ts`

`getLinuxCertConfig()` ترجیحی فہرست کا جائزہ لیتا ہے اور پہلی موجود ڈائریکٹری منتخب کرتا ہے:

| ڈسٹرو خاندان             | ڈائریکٹری                                   | اپ ڈیٹ کمانڈ             |
| ------------------------ | ------------------------------------------- | ------------------------ |
| Debian / Ubuntu          | `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| Arch / CachyOS / Manjaro | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| Fedora / RHEL / CentOS   | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| openSUSE                 | `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

سرٹیفکیٹ فائل کا نام: `omniroute-mitm.crt`۔ فنگرپرنٹ کی مماثلت `getCertFingerprint()` کے ذریعے (DER کا SHA-1)۔

مزید برآں، جب `certutil` دستیاب ہو تو `updateNssDatabases()` ہر صارف کے NSS DBs میں انسٹال کرتا ہے: `~/.pki/nssdb`، `~/snap/chromium/.../nssdb`، تمام Firefox پروفائلز (بشمول snap)، عرفی نام **`OmniRoute MITM Root CA`** کے تحت۔

### macOS / Windows

- **macOS:** `security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain`
- **Windows:** اعلیٰ مراعات یافتہ PowerShell → `certutil -addstore Root`

### توثیق

تمام MITM اینڈ پوائنٹس کے لیے انتظامی توثیق (`requireCliToolsAuth`) درکار ہے۔ sudo پاس ورڈ کو ماڈیول اسکوپ میں کیش کیا جاتا ہے (کبھی بھی `globalThis` میں نہیں) اور `stopMitm()` پر صاف کر دیا جاتا ہے۔

## فراہم کنندہ کی تبدیلی پر فنگرپرنٹس اپ ڈیٹ کرنا

1. `mitmproxy` کے ذریعے آفیشل CLI ٹریفک کیپچر کریں (TLS انٹرسیپشن + ڈمپ)
2. JA3/JA4 اور ہیڈرز کی عین ترتیب اخذ کریں
3. متعلقہ `CLI_FINGERPRINTS[...]` اندراج اپ ڈیٹ کریں
4. `.env.example` میں مماثل `*_USER_AGENT` ڈیفالٹ اپ ڈیٹ کریں
5. اگر TLS ہینڈ شیک بھی تبدیل ہوا ہے، تو متعلقہ فراہم کنندہ ریپر یا wreq-js کا `browser:` آپشن اپ ڈیٹ کریں
6. فراہم کنندہ سے مخصوص TLS ٹیسٹس چلائیں اور لائیو فراہم کنندہ کے خلاف دستی کینری ٹیسٹ کریں
7. پیچ ریلیز میں جاری کریں؛ `CHANGELOG.md` میں دستاویز کریں
