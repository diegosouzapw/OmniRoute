TPROXY شفاف ڈی کرپشن، [Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md)
MITM اسٹیک کے لیے OmniRoute کا **5واں کیپچر موڈ** ہے۔ یہ Linux پر kernel TPROXY + policy routing استعمال کرتے ہوئے مقامی outbound HTTPS ٹریفک کو intercept اور **decrypt** کرتا ہے — `/etc/hosts` کو spoof کیے **بغیر** اور پورے OS کی system-proxy ترتیبات میں تبدیلی کیے **بغیر**۔ یہ headless ماحول کے لیے موزوں ہے
(صاف کرنے کے لیے کوئی DNS ترامیم نہیں) اور firewall قواعد reboot ہونے پر خودکار طور پر flush ہو جاتے ہیں۔

دوسرے کیپچر موڈز کے برعکس، TPROXY کو فی host کسی setup کی ضرورت نہیں: یہ ہدف port پر **کسی بھی** destination host کو شفاف طور پر intercept کرتا ہے، ہر SNI hostname کے لیے فوری طور پر جاری کردہ leaf certificate کے ذریعے TLS ختم کرتا ہے، decrypt شدہ تبادلے کو capture کرتا ہے، اور request کو اصل destination کے لیے دوبارہ encrypt کرتا ہے۔

> **صرف Linux، صرف root، اور opt-in۔** اس موڈ کے لیے Linux، C toolchain کے ساتھ بنایا گیا native addon، اور **CAP_NET_ADMIN** capability (عموماً root) درکار ہیں۔ یہ صرف loopback تک محدود AgentBridge API کے پیچھے محفوظ ہے اور بطور ڈیفالٹ غیر فعال ہے۔ کوئی بھی host sign کر سکنے والی قابلِ اعتماد
> MITM CA ایک طاقتور capability ہے — [§6 سیکیورٹی](#6-security) دیکھیں۔

**سورس:** `src/mitm/tproxy/`
**API روٹ:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`

## §1 یہ کیا ہے اور اسے کب استعمال کرنا چاہیے

دیگر چار کیپچر موڈز میں سے ہر ایک کی ایک حد ہے:

| موڈ               | ٹریفک کو کیسے موڑا جاتا ہے                          | حد                                                    |
| ----------------- | --------------------------------------------------- | ----------------------------------------------------- |
| AgentBridge       | hosts کے ایک مقررہ مجموعے کا `/etc/hosts` DNS spoof | صرف رجسٹرڈ IDE-agent hosts                            |
| Custom Hosts      | ہر host کے لیے `/etc/hosts` DNS spoof               | ہر host کے لیے ایک entry؛ hosts میں ترمیم کے لیے sudo |
| HTTP_PROXY        | `HTTP_PROXY`/`HTTPS_PROXY` env                      | صرف وہ apps جو env var کا لحاظ کرتی ہیں               |
| System-wide proxy | OS proxy ترتیبات                                    | global state تبدیل کرتا ہے؛ revert درکار ہے           |

TPROXY شفاف ڈی کرپشن اس کے بجائے **kernel** کی سطح پر ٹریفک کو موڑتی ہے۔ یہ
`mangle OUTPUT` chain میں ہدف port (ڈیفالٹ `443`) کے لیے نئی مقامی outbound TCP connections کو mark کرتی ہے، ایک `ip rule` نشان زدہ packets کو local delivery کی طرف reroute کرتا ہے،
اور دوبارہ داخل ہونے پر `mangle PREROUTING` کا `TPROXY` target انہیں
**IP_TRANSPARENT** listener کے حوالے کرتا ہے — جو پھر TLS ختم کرکے plaintext کو capture کرتا ہے۔

اسے اس وقت استعمال کریں جب آپ کسی ایسے process سے ٹریفک capture اور decrypt کرنا چاہتے ہوں جو:

- کسی ایسے host سے رابطہ کرتا ہو جسے AgentBridge رجسٹر نہیں کرتا، اور
- `HTTP_PROXY` کا لحاظ نہ کرتا ہو، اور
- جسے آپ system-wide proxy کی تبدیلی سے متاثر نہ کرنا چاہتے ہوں۔

چونکہ interception، kernel میں ہوتا ہے، اس لیے اصل process کو **کسی
configuration تبدیلی** کی ضرورت نہیں — تاہم process کو OmniRoute کی نصب کردہ dynamic CA پر اعتماد کرنا ضروری ہے
([§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer) دیکھیں)۔

## §2 تقاضے

| تقاضا              | تفصیل                                                                                                                                                                         |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS**             | صرف Linux — **IP_TRANSPARENT** صرف Linux پر دستیاب socket option ہے۔ دیگر تمام پلیٹ فارمز پر loader `"unavailable"` لوٹاتا ہے۔                                                |
| **استحقاق**        | transparent socket بنانے اور `iptables`/`ip` قواعد لاگو کرنے کے لیے **CAP_NET_ADMIN** capability — عملی طور پر، root کے طور پر چلائیں۔                                        |
| **Native addon**   | ایک مختصر N-API addon (`src/mitm/tproxy/native/transparent.c`) لازماً build کیا جائے یا prebuild کی صورت میں فراہم کیا جائے۔ [§3](#3-the-native-ip_transparent-addon) دیکھیں۔ |
| **Kernel modules** | `TPROXY`، `mangle`، اور `mark` match support کے ساتھ `iptables` (kernel 6.8.0 کے مقابل validate کیا گیا)۔                                                                     |

**تدریجی تنزل:** اگر کوئی تقاضا پورا نہ ہو (غیر Linux، toolchain موجود نہ ہو،
addon build نہ کیا گیا ہو)، تو addon loader (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
exception پھینکنے کے بجائے `null` لوٹاتا ہے۔ اس کے بعد capture-mode status
`available: false` رپورٹ کرتا ہے، dashboard toggle اس tooltip کے ساتھ
**غیر فعال** ہو جاتا ہے: "TPROXY decrypt کے لیے Linux + root + native addon درکار ہیں"،
اور OmniRoute کا باقی حصہ کام کرتا رہتا ہے۔

## §3 مقامی IP_TRANSPARENT addon

Node کا `net` module، `bind()` سے _پہلے_ `setsockopt(IP_TRANSPARENT)` نہیں کر سکتا،
جبکہ TPROXY کو اس کی ضرورت ہوتی ہے (بصورتِ دیگر kernel redirect کیے گئے packets
کو مسترد کر دیتا ہے)۔ یہ addon (`src/mitm/tproxy/native/transparent.c`، جسے
`binding.gyp` کے ذریعے build کیا جاتا ہے) ایک مختصر N-API module ہے جو تین
functions فراہم کرتا ہے، جنہیں `transparentSocket.ts` کے ذریعے استعمال کیا جاتا ہے:

| Addon function                        | Socket کا کام                                                                                | استعمال                                                                            |
| ------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`، raw fd لوٹاتا ہے | transparent capture listener (Node، `server.listen({ fd })` کے ذریعے fd اپناتا ہے) |
| `setSocketMark(fd, mark)`             | موجودہ fd پر `setsockopt` **SO_MARK**                                                        | anti-loop (proxy کے اپنے sockets کو mark کرنا)                                     |
| `connectMarked(ip, port, mark)`       | non-blocking `connect()` سے **پہلے** `socket()` + **SO_MARK**، fd لوٹاتا ہے                  | دوبارہ encrypted کیا گیا upstream forward (SYN اپنے ساتھ mark لے جاتا ہے)          |

اصل destination کو `socket.localAddress`/`localPort` سے پڑھا جاتا ہے — TPROXY
اسے محفوظ رکھتا ہے، اس لیے کسی **SO_ORIGINAL_DST**/NAT lookup کی ضرورت نہیں ہوتی۔

### Addon کو build کرنا

```bash
npm run build:native:tproxy      # src/mitm/tproxy/native میں جائیں اور node-gyp rebuild چلائیں
                                 # -> native/build/Release/transparent.node
```

- `npm run build` کے دوران، `scripts/build/build-tproxy-native.mjs`، `node-gyp
rebuild` چلاتا ہے۔ یہ **صرف Linux کے لیے اور non-fatal** ہے — toolchain موجود نہ
  ہونے کی صورت میں capture mode بس غیر دستیاب رہتا ہے۔
- `assembleStandalone.mjs`، `build/Release/transparent.node` کو standalone
  bundle میں copy کرتا ہے؛ `transparentSocket.ts` اسے module-relative اور
  cwd-relative (`<cwd>/src/mitm/tproxy/native/...`) دونوں طریقوں سے resolve کرتا ہے۔
- `build/` اور `prebuilds/` کو git-ignore کیا جاتا ہے — binary کو **build کیا
  جاتا ہے، کبھی commit نہیں کیا جاتا**۔

Loader ترجیحی ترتیب میں درج ذیل مقامات کو probe کرتا ہے:
`native/build/Release/transparent.node`، پھر `native/prebuilds/transparent.node`
(دونوں module-relative اور `<cwd>/src/mitm/tproxy/` کے تحت)۔

## §4 فی-SNI متحرک CA اور ٹرسٹ اسٹور انسٹالر

> **#6684 اپ ڈیٹ:** AgentBridge کا جامد سرور (`src/mitm/server.cjs`) اب
> ایک واحد جامد خود دستخط شدہ leaf کے بجائے یہی CA/leaf آرکیٹیکچر پیٹرن
> استعمال کرتا ہے۔ یہ ایک **الگ** CA انسٹینس استعمال کرتا ہے
> (`src/mitm/cert/rootCa.ts`، جو `<DATA_DIR>/mitm/ca.key`/`ca.crt` پر محفوظ رہتا ہے)
> اور پہلے سے موجود `omniroute-mitm.crt` ٹرسٹ اسٹور سلاٹ کے تحت انسٹال ہوتا ہے
> (وہاں موجود پرانے واحد leaf کی جگہ لیتا ہے — دوہری ٹرسٹ صفائی کی ضرورت نہیں)،
> اور اسے ذیل میں موجود TPROXY کے اپنے `omniroute-tproxy-ca.crt` سلاٹ سے مکمل
> طور پر الگ رکھا جاتا ہے۔ AgentBridge کی نئی تنصیبات کو CA ماڈل خودکار طور پر
> مل جاتا ہے؛ ایسی تنصیب جو پہلے ہی پرانے جامد leaf پر بھروسا کرتی ہے، اسے اس
> وقت تک استعمال کرتی رہتی ہے جب تک آپریٹر `MITM_ROOT_CA_ENABLED=true` کے ذریعے
> اسے فعال نہ کرے (`src/mitm/cert/migration.ts` دیکھیں) — ایک قابلِ اعتماد MITM
> CA جو **کسی بھی** ہوسٹ کے لیے leaf پر دستخط کر سکتا ہے، پرانے مقررہ-SAN leaf
> سے نمایاں طور پر زیادہ طاقتور ہے، اس لیے پہلے سے قابلِ اعتماد تنصیب کے لیے یہ
> تبدیلی کبھی خاموشی سے نہیں کی جاتی۔

تاریخی طور پر، جامد AgentBridge MITM سرٹیفکیٹ صرف اس لیے کام کرتا تھا کیونکہ
AgentBridge، DNS کے ذریعے ہوسٹس کے ایک **مقررہ** مجموعے کی جعل سازی کرتا ہے
(جسے اب ذیل کے ماڈل کے ساتھ یکجا کر دیا گیا ہے)۔ TPROXY **من مانے** ہوسٹس کو
انٹرسیپٹ کرتا ہے، اس لیے اس کے listener کو کلائنٹ کی طرف سے درخواست کردہ ہر
SNI کے لیے ایک درست leaf پیش کرنا ضروری ہے — یہی تقاضا اب AgentBridge کو بھی
صرف 4 antigravity ہوسٹس کے بجائے مکمل `MITM_TOOL_HOSTS` مجموعے (9 ٹول اندراجات)
کے لیے درپیش ہے۔

### متحرک CA (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` ایک مقامی CA چلاتا ہے (جو `selfsigned` dependency پر بنایا
گیا ہے) جو:

- `generateMitmCa()` کے ذریعے ایک طویل مدتی CA تیار کرتا ہے (CN `"OmniRoute MITM CA"`،
  10 سالہ مدتِ اعتبار، `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`،
  2048-bit RSA / SHA-256)۔
- `issueLeafCert()` کے ذریعے **ہر SNI ہوسٹ نیم کے لیے ضرورت کے وقت ایک leaf**
  جاری کرتا ہے (1 سالہ مدتِ اعتبار، `subjectAltName` = SNI ہوسٹ) اور ہر ہوسٹ
  نیم کے لیے ایک `tls.SecureContext` کیش کرتا ہے۔
- TLS ختم کرنے والے سرور کے لیے `createSNICallback()` فراہم کرتا ہے
  ([§5](#5-how-decrypt-and-capture-work) دیکھیں)۔
- ری اسٹارٹس کے دوران CA کو مستحکم رکھنے کے لیے اسے `existingCa` کے ساتھ
  بنایا جا سکتا ہے (تاکہ ٹرسٹ اسٹور کو دوبارہ انسٹال نہ کرنا پڑے)۔

CA کی نجی کلید **کبھی مشین سے باہر نہیں جاتی**۔

### ٹرسٹ اسٹور انسٹالر (`src/mitm/tproxy/caTrust.ts`)

انٹرسیپٹ شدہ کلائنٹ کو متحرک CA پر بھروسا کرنا ضروری ہے، اس لیے کیپچر موڈ شروع
کرنے پر CA سرٹیفکیٹ کو OS ٹرسٹ اسٹور میں ایک **مخصوص سلاٹ** —
`omniroute-tproxy-ca.crt` (مستقل `TPROXY_CA_CERT_NAME`) — کے تحت انسٹال کیا جاتا
ہے۔ اسے جامد MITM سرٹیفکیٹ کے سلاٹ (`omniroute-mitm.crt`) سے الگ رکھا جاتا ہے
تاکہ دونوں کبھی ایک دوسرے کو اوور رائٹ نہ کریں۔

`installTproxyCa(caPem, sudoPassword?)` ڈسٹری بیوشن کی anchor ڈائریکٹری کا پتہ
لگاتا ہے (ترتیب میں: پہلے Debian طرز) اور متعلقہ ریفریش کمانڈ چلاتا ہے:

| Anchor ڈائریکٹری                            | ریفریش کمانڈ             |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

تنصیب پہلے PEM کو ایک عارضی فائل میں رکھتی ہے، پھر (خصوصی مراعات کے ساتھ)
anchor ڈائریکٹری پر `mkdir -p` چلاتی ہے، staged فائل کو `cp` کے ذریعے اس میں
کاپی کرتی ہے، اور ریفریش کمانڈ چلاتی ہے۔ `uninstallTproxyCa()` صرف مخصوص سلاٹ
کو ہٹاتا ہے (جامد MITM سرٹیفکیٹ کو برقرار رکھتے ہوئے) اور ریفریش کرتا ہے —
غیر Linux نظام پر یہ کوئی کارروائی نہیں کرتا۔

تمام خصوصی مراعات والے کمانڈز `execFileWithPassword` (`src/mitm/systemCommands.ts`)
کے ذریعے چلتے ہیں — **argument arrays، shell کے بغیر، string interpolation کے
بغیر** `spawn` (سخت اصول #13)۔ جب پراسیس root ہو (مثلاً VPS)، ہدف براہِ راست
چلتا ہے اور کسی پاس ورڈ کی ضرورت نہیں ہوتی؛ غیر root ڈیسک ٹاپ پر `sudoPassword`
کو stdin پر `sudo -S` کے ذریعے بھیجا جاتا ہے۔

> ٹرسٹ اسٹور کی تنصیب کی اجازت دینے کے لیے ڈیسک ٹاپ کا `sudoPassword`، POST body
> میں فراہم کیا جاتا ہے؛ جب پراسیس root ہو تو اسے مکمل طور پر نظر انداز کر دیا
> جاتا ہے۔

## §5 ڈکرپشن اور کیپچر کیسے کام کرتے ہیں

پائپ لائن (مکمل طور پر `src/mitm/tproxy/` کے تحت):

```
مقامی ایپ  ──TCP/443──▶  mangle OUTPUT کنکشن کو نشان زد کرتا ہے (fwmark)
                          ip rule → مقامی روٹ ٹیبل → lo
                          mangle PREROUTING TPROXY → IP_TRANSPARENT لسنر (پورٹ 8443)
                              │  captureMode.ts: اصل منزل socket.localAddress سے پڑھتا ہے
                              ▼
                          tlsCapture.ts:
                            1. فی-SNI لیف (dynamicCert) کے ساتھ CLIENT کا TLS ختم کرتا ہے
                            2. اندرونی http.Server ڈکرپٹ شدہ سادہ متن کو پارس کرتا ہے
                            3. کیپچر → globalTrafficBuffer.push()، source: "tproxy" کے ساتھ
                               (sanitizeHeaders + maskSecret لاگو ہوتے ہیں)
                            4. بائی پاس مارک شدہ ساکٹ (connectMarked، اینٹی لوپ) کے ذریعے
                               اصل منزل کو دوبارہ انکرپٹ کر کے فارورڈ کرتا ہے
                              │
                              ▼
                          اصل اپ اسٹریم (api.example.com)
```

- **TLS اختتام** (`createTlsCaptureServer`): ڈائنامک CA کے SNI کال بیک کو استعمال کرتے ہوئے خام انٹرسیپٹ شدہ
  ساکٹ کو سرور سائیڈ `tls.TLSSocket` میں لپیٹتا ہے،
  پھر ڈکرپٹ شدہ اسٹریم کو ایک اندرونی `http.Server` کے حوالے کرتا ہے (معیاری MITM
  اختتامی ترکیب)۔ ساکٹ کی مدتِ حیات `MITM_IDLE_TIMEOUT_MS` کے ذریعے محدود ہوتی ہے تاکہ
  پھنسی ہوئی ٹنل فائل ڈسکرپٹرز ختم نہ کر سکے۔
- **کیپچر** (`handleDecryptedRequest`): ایک `InterceptedRequest` پش کرتا ہے جس میں
  `source: "tproxy"`، ابتدائی اسٹیٹس `"in-flight"`، ہیڈرز کو
  `sanitizeHeaders()` اور باڈیز کو `maskSecret()` سے گزارا جاتا ہے، اس سے پہلے کہ وہ
  بفر میں داخل ہوں۔ پھر اندراج کو رسپانس، سائزز اور لیٹنسی کے ساتھ اپ ڈیٹ کیا جاتا ہے۔
- **دوبارہ انکرپٹ شدہ فارورڈ** (`createForward` / `realForward`): اصل منزل کے لیے دوبارہ انکرپٹ کرتا ہے۔
  `rejectUnauthorized` کی ڈیفالٹ قدر **`true`** ہے (بطور ڈیفالٹ محفوظ)
  — اپ اسٹریم سرٹیفکیٹ کی تصدیق کلائنٹ کی درخواست کردہ SNI/Host کے مقابلے میں کی جاتی ہے،
  لہٰذا پراکسی بالکل اسی چیز کو مسترد کرتی ہے جسے اصل کلائنٹ مسترد کرتا۔

### اینٹی لوپ (SO_MARK)

چونکہ قواعد نئے مقامی آؤٹ باؤنڈ کنکشنز کو نشان زد کرتے ہیں، اس لیے پراکسی کا **اپنا**
دوبارہ انکرپٹ شدہ فارورڈ عموماً دوبارہ انٹرسیپٹ ہو جاتا — یعنی ایک لامتناہی لوپ۔ فارورڈ
پاتھ ایک بائی پاس ساکٹ مارک (**SO_MARK**) کے ذریعے اس سے دفاع کرتا ہے:

- `realForward` اپنا اپ اسٹریم ساکٹ `connectMarked(ip, port, DEFAULT_BYPASS_MARK)`
  کے ذریعے کھولتا ہے — `DEFAULT_BYPASS_MARK = 0x539` — جو `connect()` سے **پہلے**
  **SO_MARK** سیٹ کرتا ہے، اس لیے فارورڈ کا SYN بائی پاس مارک رکھتا ہے۔
- `mangle OUTPUT` قاعدہ ان کنکشنز کو خارج کر دیتا ہے جو پہلے ہی بائی پاس مارک رکھتے ہوں
  (`-m mark ! --mark <bypassMark>`)، اس لیے پراکسی کے فارورڈ کو دوبارہ نشان زد **نہیں**
  کیا جاتا اور وہ دوبارہ TPROXY میں داخل نہیں ہوتا۔

> نفاذ سے متعلق نوٹ: بائی پاس مارک شدہ ساکٹ کو ایجنٹ کے
> `createConnection` پر نصب کرنا ضروری ہے (`https.request({ createConnection })` کو ایجنٹ
> موجود ہونے پر خاموشی سے نظر انداز کر دیا جاتا ہے)، ورنہ فارورڈ ایک غیر نشان زدہ ساکٹ
> کھولے گا اور لوپ واپس آ جائے گا۔ یہ e2e سے توثیق شدہ اینٹی لوپ فکس تھا۔

## §7 ٹرانزیکشنل فائر وال اطلاق / واپسی

کسی کریش کے نتیجے میں کبھی بھی کوئی `mangle` اصول یا متروک روٹ باقی نہیں رہنا چاہیے۔ کمانڈ بلڈر
(`src/mitm/tproxy/commands.ts`) اور رنر (`src/mitm/tproxy/setup.ts`) اس بات کی ضمانت دیتے ہیں کہ
**واپسی، اطلاق کا عین الٹ اور معکوس ترتیب میں ہوتی ہے**۔

`applyTproxy(cfg)` اطلاق کی کمانڈز کو ترتیب وار چلاتا ہے؛ **کسی بھی** ناکامی پر یہ
بہترین ممکنہ کوشش کے ساتھ مکمل `revertTproxy(cfg)` چلاتا ہے اور خرابی دوبارہ پھینک دیتا ہے — لہٰذا فائر وال
یا تو مکمل طور پر لاگو ہوتا ہے یا مکمل طور پر واپس کر دیا جاتا ہے، کبھی جزوی طور پر لاگو نہیں رہتا۔ `revertTproxy(cfg)`
معکوس کمانڈز کو الٹی ترتیب میں چلاتا ہے اور ناکامیوں کو نظر انداز کرتا ہے (آئیڈیم پوٹینٹ — اسے
بلاشرط کال کرنا محفوظ ہے، مثلاً AgentBridge کی `repairMitm()` صفائی سے)۔

`validateTproxyConfig(cfg)` کسی بھی کمانڈ سے پہلے چلتا ہے: پورٹس `1–65535` ہونی چاہئیں،
`mark`/`routeTable`/`bypassMark` مثبت صحیح اعداد ہونے چاہئیں، اور `bypassMark` کو
`mark` سے مختلف ہونا چاہیے (اینٹی لوپ)۔

### اطلاق کی کمانڈز (ترتیب وار)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

واپسی کے دوران انہیں الٹی ترتیب میں حذف کیا جاتا ہے: `PREROUTING -D`، `OUTPUT -D`، `ip route del`، `ip rule del`۔

> یہ طریقۂ کار **OUTPUT پر مبنی** ہے کیونکہ MITM کا استعمال _مقامی_ آؤٹ باؤنڈ
> ٹریفک (اسی ہوسٹ پر موجود ایپس) کے لیے ہے، جسے صرف `PREROUTING` میں موجود TPROXY
> نہیں دیکھتا — `PREROUTING` صرف فارورڈ کی گئی ٹریفک دیکھتا ہے۔ `OUTPUT` چین نئے
> مقامی کنکشنز کو مارک کرتی ہے، `ip rule` انہیں مقامی ڈیلیوری (`lo`) کی طرف دوبارہ روٹ کرتا ہے، اور
> پھر `PREROUTING` انہیں ٹرانسپیرنٹ لسنر کے سپرد کرتا ہے۔

## §8 کنفیگریشن

اسٹارٹ درخواست (`POST /api/tools/agent-bridge/tproxy`) درج ذیل
فیلڈز قبول کرتی ہے، جن کی توثیق `StartTproxyBodySchema` (`tproxy/route.ts`) کرتا ہے۔ یہ سب اختیاری
ہیں اور موجود نہ ہونے پر اپنی ڈیفالٹ اقدار استعمال کرتے ہیں:

| فیلڈ             | قسم                     | ڈیفالٹ   | نوٹس                                                                                                                         |
| ---------------- | ----------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | صحیح عدد (1–65535)      | `443`    | منزل کا TCP پورٹ جسے ٹرانسپیرنٹ انداز میں انٹرسیپٹ کرنا ہے                                                                   |
| **mark**         | صحیح عدد (≥1)           | `0x2333` | `OUTPUT` پر سیٹ کیا جانے والا فائر وال مارک، جسے `ip rule` + `PREROUTING` میچ کرتے ہیں                                       |
| **onPort**       | صحیح عدد (1–65535)      | `8443`   | وہ پورٹ جس سے ٹرانسپیرنٹ (**IP_TRANSPARENT**) لسنر بائنڈ ہوتا ہے                                                             |
| **routeTable**   | صحیح عدد (≥1)           | `233`    | پالیسی روٹنگ ٹیبل کی id جس میں `local 0.0.0.0/0` روٹ موجود ہوتا ہے                                                           |
| **bypassMark**   | صحیح عدد (≥1، ≠ `mark`) | `0x539`  | بائی پاس ساکٹ مارک (**SO_MARK**) جسے پراکسی اپنے اپ اسٹریم کنکشنز پر سیٹ کرتی ہے؛ `OUTPUT` میں خارج رکھا جاتا ہے (اینٹی لوپ) |
| **sudoPassword** | اسٹرنگ                  | —        | صرف نان روٹ ڈیسک ٹاپس: ٹرسٹ اسٹور کی تنصیب کی اجازت دیتا ہے؛ روٹ ہونے پر نظر انداز کیا جاتا ہے                               |

TPROXY کے لیے **کوئی environment variables نہیں ہیں** — تمام کنفیگریشن
POST باڈی یا اوپر دی گئی ڈیفالٹ اقدار کے ذریعے ہوتی ہے۔

## §9 ٹریفک انسپکٹر سے فعال کرنا

1. **ٹریفک انسپکٹر** (`/dashboard/tools/traffic-inspector`) کھولیں۔
2. کیپچر موڈز کی ٹول بار میں **"TPROXY ڈکرپٹ"** ⚠ بٹن تلاش کریں
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`)۔
   - اگر یہ **غیرفعال** ہو اور ٹول ٹِپ میں "TPROXY ڈکرپشن کے لیے Linux + root +
     مقامی ایڈ آن درکار ہے" دکھائی دے، تو اس ہوسٹ پر مقامی ایڈ آن دستیاب نہیں ہے (Linux نہیں،
     کوئی ٹول چین نہیں، یا ایڈ آن بِلڈ نہیں ہوا)۔ [§2](#2-requirements) اور [§3](#3-the-native-ip_transparent-addon) دیکھیں۔
3. بٹن پر کلک کریں۔ یہ `startTproxyCaptureMode()` کے ذریعے
   `POST /api/tools/agent-bridge/tproxy` کو کال کرتا ہے
   (`src/lib/inspector/tproxyCaptureApi.ts`)، جو:
   ڈائنامک CA بناتا ہے، شفاف لسنر کھولتا ہے، فائر وال قواعد لاگو کرتا ہے،
   اور CA کو OS ٹرسٹ اسٹور میں انسٹال کرتا ہے۔
4. چلنے کے دوران، ٹوگل عنبری رنگ کا ہو جاتا ہے اور براہِ راست انٹرسیپٹ کی تعداد
   (`· <interceptCount>`) دکھاتا ہے۔ انٹرسیپٹ کی گئی درخواستیں درخواستوں کی فہرست میں
   `source: "tproxy"` کے ساتھ ظاہر ہوتی ہیں۔
5. روکنے کے لیے دوبارہ کلک کریں — `stopTproxyCaptureMode()` کے ذریعے
   `DELETE /api/tools/agent-bridge/tproxy` لسنر بند کرتا ہے، CA اَن انسٹال کرتا ہے، اور
   فائر وال قواعد واپس پلٹاتا ہے۔

کیپچر موڈ کی حالت (چل رہا ہے / دستیاب ہے / انٹرسیپٹ کی تعداد / لسنر پورٹ)
`GET /api/tools/agent-bridge/tproxy` سے آتی ہے (`src/mitm/tproxy/captureManager.ts` میں
`getCaptureStatus()`)۔ ایک وقت میں صرف **ایک** TPROXY سیشن چلتا ہے —
دوسرا شروع کرنے کی کوشش "TPROXY کیپچر موڈ پہلے ہی چل رہا ہے" کے ساتھ مسترد ہو جاتی ہے۔

---

## §10 خرابیوں کا ازالہ

### ٹوگل غیرفعال ہے

مقامی ایڈ آن لوڈ نہیں کیا جا سکتا۔ تصدیق کریں: آپ Linux استعمال کر رہے ہیں، آپ نے ایڈ آن
بِلڈ کیا ہے (`npm run build:native:tproxy`)، اور پراسیس `transparent.node` لوڈ کر سکتا ہے۔
`isTransparentSocketAvailable()` ٹوگل کی دستیابی کو کنٹرول کرتا ہے؛ ایڈ آن موجود نہ ہونے پر
`GET /api/tools/agent-bridge/tproxy`، `available: false` لوٹاتا ہے۔

### کچھ بھی کیپچر نہیں ہو رہا

- تصدیق کریں کہ انٹرسیپٹ کیا گیا پراسیس واقعی ترتیب کردہ `dport`
  (ڈیفالٹ `443`) سے منسلک ہوتا ہے۔
- تصدیق کریں کہ پراسیس ڈائنامک CA پر اعتماد کرتا ہے۔ CA کو
  `omniroute-tproxy-ca.crt` کے تحت انسٹال کیا جاتا ہے؛ اپنے ٹرسٹ اسٹور والی ایپس (Firefox/Chrome NSS)
  میں بھی سرٹیفکیٹ شامل کرنے کی ضرورت ہو سکتی ہے۔
- سرٹیفکیٹ پر اعتماد / سرور کی صحت کی جانچ کے لیے AgentBridge کا **تشخیصی** سیلف ٹیسٹ چلائیں
  ([`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md) دیکھیں)۔

### کریش کے بعد باقی رہ جانے والے فائر وال قواعد

`revertTproxy()`، اطلاق کے عین برعکس ہے اور idempotent ہے۔ موڈ روکنے سے
قواعد واپس پلٹ جاتے ہیں؛ اگر OmniRoute کو سیشن کے دوران بند کر دیا گیا تھا، تو تنہا رہ جانے والی
سسٹم حالت (DNS spoof، root CA، سسٹم پراکسی) کو واپس لینے کے لیے AgentBridge کی
**مرمت** کارروائی (`POST /api/tools/agent-bridge/repair`) استعمال کریں۔ TPROXY کے `mangle`
قواعد اور روٹ بھی ری بوٹ پر خودکار طور پر صاف ہو جاتے ہیں۔

### لامتناہی لوپ / پراکسی اپنی ہی فارورڈنگ کو انٹرسیپٹ کرتی ہے

یہ اینٹی لوپ صورتِ حال ہے۔ تصدیق کریں کہ `bypassMark`، `mark` سے مختلف ہے (توثیق
اسے یقینی بناتی ہے) اور فارورڈ `connectMarked` استعمال کرتا ہے (`realForward` میں ایسا ہی ہوتا ہے)۔
[§5 اینٹی لوپ](#anti-loop-so_mark) دیکھیں۔
