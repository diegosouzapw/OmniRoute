یہ دستاویز `omniroute@3.8.5` کے خلاف سامنے آنے والے چھ
`AI-detected potential malware` نتائج اور `omniroute@3.8.6` میں نافذ کی گئی
تخفیفی تدابیر کے لیے مینٹینر کی تحریر کردہ تصدیق ہے۔ اس کے مقاصد یہ ہیں:

1. سیکیورٹی پائپ لائن کے آپریٹرز کے پاس ایک واحد حوالہ موجود ہو جس کا وہ
   اصل سورس کے مقابل نتائج کا جائزہ لیتے وقت حوالہ دے سکیں۔
2. مستقبل کے AI اسکینرز مینٹینر کے دستخط شدہ اس دعوے کو شناخت کر سکیں کہ
   نشان زد کیا گیا ہر پاتھ دانستہ، اختیاری، اور دستاویزی ہے۔
3. ہمارے پاس اس بات کا تحریری ریکارڈ ہو کہ ہر کال سائٹ کو اس مخصوص انداز میں
   _کیوں_ بنایا گیا ہے — تاکہ مستقبل کی کوئی ری فیکٹرنگ نادانستہ طور پر ایسا
   فنگر پرنٹ دوبارہ متعارف نہ کر دے جسے جان بوجھ کر ہٹایا گیا تھا۔

اگر آپ ایسا اسکینر چلاتے ہیں جو v3.8.6 کی تخفیفی تدابیر جاری ہونے کے بعد ذیل
میں دی گئی کسی کال سائٹ کو دوبارہ نشان زد کرتا ہے، تو براہِ کرم اسکین ٹریس کے
ساتھ ایک مسئلہ کھولیں، اور ہم یہاں اس تصدیق میں توسیع کر دیں گے۔

## §1 — MITM روٹ-CA کی تنصیب (`77484.js`)

**سورس فائلیں**:

- `src/mitm/cert/install.ts` — عوامی `installCert()` / `uninstallCert()`،
  ہر پلیٹ فارم کے لیے `installCertWindows/Mac/Linux`۔
- `src/mitm/systemCommands.ts` — تنصیب کے پاتھز کے زیرِ استعمال مشترکہ
  `execFile` / `spawn` / PowerShell ہیلپرز۔

**ٹرگر**: صارف مقامی ڈیش بورڈ میں
`/dashboard/cli-tools/mitm` پر "MITM پراکسی فعال کریں" پر کلک کرتا ہے۔ یہ
روٹ صرف لوپ بیک تک محدود ہے — `CLAUDE.md` میں سخت اصول #17 اور
`src/server/authz/routeGuard.ts::isLocalOnlyPath()` ملاحظہ کریں۔ ٹنل کے ذریعے
سامنے آنے والا لیک شدہ JWT اس کوڈ پاتھ کو **فعال نہیں** کر سکتا۔

**انجام دیے جانے والے مراعات یافتہ آپریشنز (ہر پلیٹ فارم کے لحاظ سے)**:

| OS                     | کمانڈ (کمانڈز)                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Windows                | UAC کے ذریعے `certutil -addstore Root <cert>`                                                                     |
| macOS                  | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>`                     |
| Linux                  | `sudo cp <cert> <distro-trust-dir>` + `sudo update-ca-certificates` (Debian) / `sudo update-ca-trust` (RHEL/SUSE) |
| Linux+Firefox/Chromium | `certutil -d sql:<profile>` کے ذریعے ہر پروفائل کی NSS DB اپ ڈیٹ                                                  |

یہ وہی کمانڈز ہیں جو `mitmproxy`، Charles Proxy، Fiddler، اور
Caddy استعمال کرتے ہیں۔ OmniRoute میں ان کی موجودگی
`docs/security/STEALTH_GUIDE.md` میں دستاویز کی گئی ہے۔

**v3.8.6 کی تخفیف**:

- `runElevatedPowerShell()` اب `-EncodedCommand <base64utf16le>` استعمال نہیں
  کرتا۔ اعلیٰ مراعات والا پے لوڈ ہر کال کے لیے ایک عارضی `.ps1` فائل میں
  لکھا جاتا ہے (موڈ 0o600، نجی `mkdtempSync` ڈائریکٹری کے اندر) اور `-File`
  کے ذریعے اس کا حوالہ دیا جاتا ہے۔ فائل کو `finally` میں ان لنک کر دیا جاتا
  ہے۔ اس سے PowerShell کے ذریعے base64-اعلیٰ مراعات حاصل کرنے کا وہ معروف
  فنگر پرنٹ ختم ہو جاتا ہے جسے Socket.dev کے AI کلاسیفائر نے نشان زد کیا تھا۔
- `installCertWindows` میں ایک اِن لائن `SECURITY-AUDITOR-NOTE:` بلاک موجود
  ہے جو یہاں کی طرف اشارہ کرتا ہے۔

**ہم اسے کیوں برقرار رکھتے ہیں**: MITM پراکسی ایک دستاویزی فیچر ہے جسے
`docs/security/STEALTH_GUIDE.md` اور `docs/frameworks/MITM-PROXY.md` استعمال
کرتے ہیں۔ اسے ہٹانے سے agent-bridge فیچر سیٹ متاثر ہو جائے گا۔

## §2 — Zed اسناد کی درآمد (`app/api/providers/zed/import/route.js`)

**ماخذ فائلیں**:

- `src/app/api/providers/zed/discover/route.ts` _(v3.8.6 میں نئی)_
- `src/app/api/providers/zed/import/route.ts`
- `src/lib/zed-oauth/keychain-reader.ts`
- `src/lib/zed-oauth/credentialFingerprint.ts` _(v3.8.6 میں نئی)_

**محرک**: صارف مقامی ڈیش بورڈ کے Providers صفحے پر "Zed سے درآمد کریں" پر کلک کرتا ہے۔ Endpoint کو `requireManagementAuth` کے ذریعے محفوظ کیا گیا ہے۔ Zed ایڈیٹر خود اپنے provider API keys کو دستاویزی service ناموں کے تحت OS keychain میں لکھتا ہے — دیکھیے https://zed.dev/docs/ai/llm-providers۔

**v3.8.5 کا طرزِ عمل (جسے Socket.dev نے نشان زد کیا)**:

`POST /import` اسناد دریافت کرتا اور ایک ہی round-trip میں انہیں خودکار طور پر مقامی SQLite store میں محفوظ کر دیتا تھا۔ ہر account کے لیے کوئی تصدیق نہیں، کوئی fingerprint نہیں، صرف "N tokens ملے، سب درآمد کر دیے گئے۔"

**v3.8.6 میں تخفیف — 2-مرحلہ تصدیق**:

1. **`POST /api/providers/zed/discover`** یہ واپس کرتا ہے:
   `{ candidates: [{ provider, service, account, fingerprint }] }`۔ خام
   token **کبھی بھی** منتقل نہیں کیا جاتا۔ Fingerprint یہ ہے:
   `sha256(service|account|token).slice(0,16)`۔
2. ڈیش بورڈ candidate فہرست دکھاتا ہے، operator منتخب کرتا ہے کہ کن کو
   درآمد کرنا ہے، اور `{ confirmedAccounts: [{ service, account, fingerprint }] }`
   کو **`POST /api/providers/zed/import`** پر پوسٹ کرتا ہے۔
3. Import endpoint **سرور پر keychain دوبارہ پڑھتا ہے** اور
   `(service, account, fingerprint)` کے مطابق فلٹر کرتا ہے۔ چھیڑ چھاڑ شدہ یا دوبارہ چلایا گیا discover
   response، import endpoint کو کسی غیر متعلقہ token کو محفوظ کرنے کے لیے دھوکا نہیں دے سکتا —
   اگر discover کے بعد سے live token تبدیل ہو چکا ہو تو fingerprint مزید
   match نہیں کرتا اور credential کو چھوڑ دیا جاتا ہے۔

`OMNIROUTE_ZED_IMPORT_LEGACY_ONE_STEP=true` env flag ان operators کے لیے v3.8.5
کا طرزِ عمل برقرار رکھتا ہے جنہوں نے ابھی تک اپنی automation اپ ڈیٹ نہیں کی۔ اسے
v3.9 میں ہٹا دیا جائے گا۔

**ہم اسے کیوں برقرار رکھتے ہیں**: Zed import ان صارفین کے لیے سب سے آسان onboarding راستہ ہے
جو پہلے ہی Zed استعمال کرتے ہیں اور دوبارہ paste کیے بغیر اپنی provider keys کو OmniRoute
میں mirror کرنا چاہتے ہیں۔

## §3 — `execFile` / `spawn` / elevated PowerShell (`21843.js`)

**ماخذ فائلیں**: `src/mitm/systemCommands.ts`۔

**نشان زد کیے جانے کی وجہ**: یہ chunk `execFileWithPassword`،
`runElevatedPowerShell`، اور مشترکہ `quotePowerShell` helper کو دوبارہ export کرتا ہے۔ Socket.dev کا
AI classifier انہیں ایک عمومی "host execution + privilege elevation
toolkit" کے طور پر دیکھتا ہے۔ OmniRoute کے اندر یہ صرف MITM cert installation path
(§1) اور `sudo` command execution کے لیے `execFileWithPassword` میں استعمال ہوتے ہیں۔

**v3.8.6 میں تخفیف**:

- `runElevatedPowerShell` کی refactorization (§1 دیکھیے)۔
- `runElevatedPowerShell` اور `execFileWithPassword` دونوں پر inline
  `SECURITY-AUDITOR-NOTE:` block، allowlisted callers اور pinned executable
  list کو دستاویزی شکل دیتا ہے۔
- `execFileWithPassword` کی `spawn()` call میں executables کی اس allowlist کے ساتھ
  `nosemgrep` marker موجود ہے جنہیں یہ helper وصول کرنے کا مجاز ہے —
  user input سے `finalCommand`/`finalArgs` تک **کوئی راستہ موجود نہیں ہے**۔

**پہلے سے موجود تحفظات**:

- 9router DB row کو `status='not_installed', auto_start=0` کے ساتھ seed کیا جاتا ہے (دیکھیے
  `src/lib/db/migrations/071_services.sql:19`)۔ Service پہلی launch پر
  شروع **نہیں** ہوتی۔
- `spawn()` کو `src/lib/services/installers/ninerouter.ts` میں
  `resolveSpawnArgs(apiKey, PORT)` کے ذریعے واپس کردہ binary path کے ساتھ call کیا جاتا ہے،
  جو supported binaries کی ایک مقررہ allowlist ہے۔
- Stdout/stderr کو memory میں buffer کیا جاتا ہے (5 MB کی حد، `_lib.ts` دیکھیے) — disk پر
  اس وقت تک کوئی تحریر نہیں ہوتی جب تک صارف dashboard سے logging فعال نہ کرے۔

**v3.8.6 میں تخفیف**: کوئی functional تبدیلی نہیں۔ Minimal build profile
(`OMNIROUTE_BUILD_PROFILE=minimal`)،
`src/lib/services/installers/ninerouter.ts` کو ان صارفین کے لیے ایک stub سے بدل دیتا ہے جو
privileged paths کو bundle سے مادی طور پر ہٹانا چاہتے ہیں۔

**ہم اسے کیوں برقرار رکھتے ہیں**: 9router ایک اختیاری، مقامی طور پر install ہونے والی companion
service ہے (یعنی: WordPress طرز کا plugin) — سخت opt-in۔

## §5 — OmniRoute Cloud Sync اسناد کی رائٹ بیک (`api/keys/[id]/route.js`)

**ماخذ فائلیں**:

- `src/lib/cloudSync.ts` — `syncToCloud()` / `updateLocalTokens()`۔
- `src/app/api/keys/[id]/route.ts` — `syncKeysToCloudIfEnabled()` کو طلب کرتی ہے۔

**محرک**: `isCloudEnabled()` کی واپسی `true` ہو (جسے ڈیش بورڈ سے متعین کیا جاتا ہے) **اور**
`CLOUD_URL` کنفیگر شدہ ہو۔ دونوں بند ہونے کی صورت میں Cloud اینڈ پوائنٹ کو کوئی آؤٹ باؤنڈ نیٹ ورک کال نہیں کی جاتی۔

**v3.8.5 کا رویہ (وہ بگ جسے Socket.dev نے درست طریقے سے پکڑا)**:

جب `cloudUpdatedAt > localUpdatedAt` ہوتا تو `updateLocalTokens()`، Cloud کے جواب سے `accessToken`، `refreshToken`، اور `providerSpecificData` کو اوور رائٹ کر دیتا تھا۔ کوئی HMAC، کوئی دستخط، کوئی چیک سم نہیں تھا۔ غلط کنفیگر شدہ یا مخاصمانہ `CLOUD_URL` (یا چینل پر موجود MITM) فراہم کنندہ کے OAuth ٹوکنز کو خاموشی سے تبدیل کر سکتا تھا۔

**v3.8.6 میں تخفیف**:

1. **HMAC توثیق**: `verifyCloudSignature(rawBody, sigHeader)`، JSON کو پارس کرنے سے پہلے `X-Cloud-Sig` ہیڈر (`HMAC-SHA256(OMNIROUTE_CLOUD_SYNC_SECRET, rawBody)`) کی جانچ کرتا ہے۔ اگر سیکرٹ متعین ہو تو دستخط لازمی ہیں۔ اگر متعین نہ ہو (لیگیسی موڈ)، تو ایک انتباہ لاگ کیا جاتا ہے اور جواب قبول کر لیا جاتا ہے — v3.9 میں سیکرٹ لازمی ہوگا۔
2. **خفیہ فیلڈز کے لیے آپٹ اِن**: `accessToken` / `refreshToken` /
   `providerSpecificData` کو **صرف** اس وقت اوور رائٹ کیا جاتا ہے جب
   `OMNIROUTE_CLOUD_SYNC_SECRETS=true` ہو۔ ڈیفالٹ موڈ صرف غیر اسنادی میٹا ڈیٹا (`expiresAt`، `status`، `lastError*`،
   `rateLimitedUntil`، `updatedAt`) سنک کرتا ہے۔ یہ ان صارفین کے لیے ایک **عدم مطابقت پیدا کرنے والی تبدیلی** ہے جو ریموٹ ٹوکن سنک پر انحصار کرتے تھے — انہیں واضح طور پر آپٹ اِن کرنا ہوگا۔

**ہم اسے کیوں برقرار رکھتے ہیں**: Cloud Sync ہی وہ واحد طریقہ ہے جس سے کوئی OmniRoute Cloud ٹیننٹ ٹیم کے اسناد کو مرکزی طور پر منظم کر سکتا ہے۔ یہ اصلاح تھریٹ ماڈل کو دیانت دار بناتی ہے:
"سرور دستخط کرتا ہے، کلائنٹ تصدیق کرتا ہے، آپریٹر آپٹ اِن کرتا ہے۔"

## بلڈ پروفائل: `minimal`

جن صارفین کو Socket کے موافق آرٹی فیکٹ درکار ہو، وہ اس کے ساتھ بلڈ کریں:

```bash
OMNIROUTE_BUILD_PROFILE=minimal npm run build
```

webpack کا `NormalModuleReplacementPlugin` چار ماڈیولز کو اسٹبز سے الیاس کرتا ہے:

| ماڈیول                                      | اسٹب                                             |
| ------------------------------------------- | ------------------------------------------------ |
| `src/mitm/cert/install.ts`                  | `src/mitm/cert/install.stub.ts`                  |
| `src/lib/zed-oauth/keychain-reader.ts`      | `src/lib/zed-oauth/keychain-reader.stub.ts`      |
| `src/lib/cloudSync.ts`                      | `src/lib/cloudSync.stub.ts`                      |
| `src/lib/services/installers/ninerouter.ts` | `src/lib/services/installers/ninerouter.stub.ts` |

ہر اسٹب وہی انٹرفیس ایکسپورٹ کرتا ہے، لیکن ہر فنکشن رن ٹائم پر
`featureDisabledError(name)` تھرو کرتا ہے۔ غیر فعال کردہ ماڈیول پر منحصر روٹس، حساس کوڈ پاتھ کو فعال کرنے کے بجائے واضح پیغام کے ساتھ HTTP 503 واپس کرتے ہیں۔

نتیجتاً بننے والے بنڈل کو `omniroute-secure` کے طور پر شائع کیا جانا مقصود ہے۔ اشاعت کے طریقۂ کار کے لیے
`docs/ops/PUBLISHING_SECURE.md` دیکھیں۔
