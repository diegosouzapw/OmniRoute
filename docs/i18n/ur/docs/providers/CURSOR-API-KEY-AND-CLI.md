IDE سیشن کے بغیر Cursor کو OmniRoute کے پیچھے رکھنے کے دو طریقے:

1. **`cursor-api` پرووائیڈر** (کارڈ "Cursor API"، عرف `cua`): ایک API-key
   پرووائیڈر جو Cursor صارف کی API کلید (`crsr_…`، جو
   `https://cursor.com/dashboard/api` پر بنائی جاتی ہے) محفوظ رکھتا ہے۔ اس کے بعد کوئی بھی OmniRoute کلائنٹ
   `/v1/chat/completions` کے ذریعے `cursor-api/<model>` یا
   `cua/<model>` کے طور پر، معمول کی کوٹا، فال بیک، اور لاگنگ تہوں کے ساتھ Cursor ماڈلز تک رسائی حاصل کرتا ہے۔ IDE
   پرووائیڈر (`cursor`، OAuth/IDE سیشن) میں کوئی تبدیلی نہیں کی گئی۔
2. **Cursor CLI پاس تھرو**: Cursor CLI (`agent`) کو OmniRoute کی طرف پوائنٹ کریں تاکہ
   CLI کی جانب سے کی جانے والی ہر RPC کی توثیق OmniRoute API کلید سے ہو، اسے
   `cursor-api` کنکشن کی اسناد کے ساتھ Cursor کو فارورڈ کیا جائے، اور
   Logs صفحے میں ریکارڈ کیا جائے۔

## کلید کا تبادلہ کیوں کیا جاتا ہے

`api2.cursor.sh` ایک خام `crsr_…` کلید کو Bearer ٹوکن کے طور پر مسترد کر دیتا ہے (401)۔ Cursor
CLI پہلے کلید کو `/auth/exchange_user_api_key` پر POST کرتا ہے اور ایک سیشن
JWT وصول کرتا ہے جو ایک گھنٹے بعد زائد المیعاد ہو جاتا ہے؛ واپس ملنے والا `refreshToken` بھی وہی
`exp` رکھتا ہے، اس لیے ریفریش کرنے کا مطلب کلید کا دوبارہ تبادلہ کرنا ہے۔
`open-sse/services/cursorApiKeyAuth.ts` یہ تبادلہ انجام دیتا ہے، ہر کلید کے لیے ایک سیشن
ٹوکن کیش کرتا ہے، میعاد ختم ہونے سے پانچ منٹ پہلے دوبارہ تبادلہ کرتا ہے، اور جب Cursor
401 کے ساتھ جواب دیتا ہے تو کیش شدہ ٹوکن حذف کر دیتا ہے۔ `CursorExecutor`، `cursor-api`
کنکشنز کے لیے اپ اسٹریم اسٹریم کھولنے سے عین پہلے اسے کال کرتا ہے۔

## `cursor-api` پرووائیڈر

رجسٹری: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`، `authType: "apikey"`، وہی `format`، `baseUrl` اور
`models` جو `cursor` کے ہیں)۔ کیٹلاگ کارڈ:
`src/shared/constants/providers/apikey/specialty-media.ts`۔ ایگزیکیوٹر میپ:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`)۔

ڈیش بورڈ: Providers → Cursor API → Add API key۔

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

پھر:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

نوٹس:

- `cursor-api` کے لیے ماڈلز کی فہرست جامد Cursor رجسٹری سے آتی ہے (وہی
  فہرست جسے IDE پرووائیڈر فال بیک کے طور پر استعمال کرتا ہے)؛ OmniRoute ہوسٹ پر
  `cursor-agent` انسٹال کرنے کی ضرورت نہیں۔
- `POST /api/providers/{id}/refresh-cursor` صرف `cursor` IDE پرووائیڈر
  کے لیے ہے؛ `cursor-api` کنکشنز کے پاس تجدید کے لیے کوئی IDE سیشن نہیں ہوتا۔

## مقامی ماڈل IDs اور کوشش

`cursor` / `cu` اور `cursor-api` / `cua` کے لیے، مشترکہ Claude-effort نارملائزر
درخواست کردہ ماڈل ID کو جوں کا توں رہنے دیتا ہے۔ Cursor کسی حقیقی ماڈل ID کے حصے کے طور پر
`-low` جیسا لاحقہ مشتہر کر سکتا ہے، نہ کہ OmniRoute effort عرف کے طور پر۔
Cursor ایگزیکیوٹر لائیو کیٹلاگ میں عین مماثلت کو برقرار رکھتا ہے؛ جب کوئی
مماثلت نہ ہو تو اس کا موجودہ ماڈل ریزولوَر لاحقے کو پیرامیٹر میں تبدیل کرنے کا فال بیک سنبھالتا ہے۔

اس سے براہِ راست Claude، Claude-compatible، یا Vertex روٹس کے لیے effort normalization
میں کوئی تبدیلی نہیں آتی۔ دستیابی اب بھی منتخب کردہ Cursor اکاؤنٹ کے
کیٹلاگ اور استحقاق پر منحصر ہے۔

## Cursor CLI پاس تھرو

روٹ: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`۔ سابقہ `/api/cursor-cli/` کو
`src/shared/constants/publicApiRoutes.ts` میں رجسٹر کیا گیا ہے کیونکہ ہینڈلر
اپنی توثیق خود نافذ کرتا ہے:

| پاتھ                                                                                                                      | CLI سے متوقع توثیق           | OmniRoute کیا کرتا ہے                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                        | `Bearer <OmniRoute API key>` | کلید کی توثیق کرتا ہے، 1h کا HS256 JWT بناتا ہے (`JWT_SECRET` کے ساتھ دستخط شدہ) اور اسے واپس کرتا ہے                                                                     |
| ہر دوسرا پاتھ (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`          | جاری کنندہ/سامعین/میعاد کی تصدیق کرتا ہے، ایک فعال `cursor-api` کنکشن منتخب کرتا ہے، Authorization ہیڈر کو تبدیل شدہ Cursor ٹوکن سے بدلتا ہے اور جواب واپس اسٹریم کرتا ہے |

CLI موصول ہونے والے کسی بھی ٹوکن سے `exp` ڈی کوڈ کرتا ہے، اس لیے اسے ایک مبہم
ٹوکن دینے سے وہ تقریباً ہر درخواست سے پہلے دوبارہ تبادلہ کرتا ہے؛ بنایا گیا JWT
اس سے بچاتا ہے۔ OmniRoute کی جانب سے 401 موصول ہونے پر CLI دوبارہ تبادلہ کرتا ہے۔

### سیٹ اپ

1. ایک OmniRoute API کلید (Dashboard → API keys) اور ایک `cursor-api`
   کنکشن بنائیں۔
2. CLI کو ایجنٹ اسٹریم کے لیے HTTP/1.1 استعمال کرنے کی ہدایت دیں۔
   `~/.cursor/cli-config.json` میں:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   اس کے بغیر CLI ایک علیحدہ ترتیب دیے گئے ایجنٹ ہوسٹ پر HTTP/2 کے ذریعے ایجنٹ
   ٹرن کھولتا ہے، اور صرف کنٹرول پلین RPCs ہی اینڈ پوائنٹ سے گزرتے ہیں۔

3. CLI کو OmniRoute کے خلاف چلائیں:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

ہر ہاپ Logs میں فراہم کنندہ `cursor-api`، درخواست کی قسم `cursor-cli`،
پاتھ `/api/cursor-cli/<rpc>` کے طور پر درج ہوتی ہے، اور اسے OmniRoute API کلید
اور اسے انجام دینے والے کنکشن سے منسوب کیا جاتا ہے۔

### ناکامی کی صورتیں

| صورتِ حال                                         | CLI کو جواب                                             |
| ------------------------------------------------- | ------------------------------------------------------- |
| نامعلوم OmniRoute کلید اور `REQUIRE_API_KEY=true` | تبادلے پر 401 `unauthenticated`                         |
| `REQUIRE_API_KEY=false`                           | گمنام سیشن (`/v1/*` کے طرزِ عمل کی عکاسی کرتا ہے)       |
| میعاد ختم شدہ / غیر متعلق / تبدیل شدہ سیشن JWT    | 401، CLI دوبارہ تبادلہ کرتا ہے                          |
| تبادلے کے بعد OmniRoute API کلید منسوخ ہو جائے    | اگلے RPC پر 401                                         |
| کوئی فعال `cursor-api` کنکشن نہ ہو                | 503 `unavailable`                                       |
| Cursor کنکشن کی کلید مسترد کر دے                  | 401 `unauthenticated`، کیش کردہ سیشن حذف کر دیا جاتا ہے |
| اپ اسٹریم ناقابلِ رسائی ہو                        | 502 `unavailable` (صاف کیا گیا پیغام)                   |
| `JWT_SECRET` سیٹ نہ ہو                            | تبادلے پر 503                                           |
