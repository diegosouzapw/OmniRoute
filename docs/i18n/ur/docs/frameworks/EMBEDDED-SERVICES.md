API کلیدوں سے رسائی حاصل کی جاتی ہے) کے برعکس، ایمبیڈڈ سروسز OmniRoute والی ہی مشین پر چلتی ہیں اور لوپ بیک کے ذریعے مواصلت کرتی ہیں۔

## 1. جائزہ

### ایمبیڈڈ سروسز کیوں؟

چھ سروسز ایمبیڈ کی گئی ہیں:

| سروس            | npm پیکیج                        | ڈیفالٹ پورٹ | مقصد                                                                                                                                                                                                      |
| --------------- | -------------------------------- | :---------: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9Router**     | `9router`                        |    20130    | AI روٹر جسے OmniRoute ذیلی فراہم کنندہ کے طور پر استعمال کر سکتا ہے۔ ماڈلز `9router/{sub}/{model}` کے طور پر دستیاب کیے جاتے ہیں                                                                          |
| **CLIProxyAPI** | GitHub ریلیز بائنری (`cliproxy`) |    8317     | Anthropic CLI تصدیقی بہاؤ کے لیے مقامی پراکسی اڈاپٹر۔ OAuth ٹوکنز کی میعاد ختم ہونے پر فال بیک روٹنگ فراہم کرتا ہے                                                                                        |
| **Mux**         | `mux` (ہیڈ لیس `mux server`)     |    8322     | مقامی ایجنٹ آرکیسٹریشن ڈیمَن (coder/mux)۔ صرف لائف سائیکل کا انتظام کیا جاتا ہے — یہ روٹنگ ہدف نہیں ہے (کوئی LLM پراکسینگ نہیں)۔                                                                          |
| **Bifrost**     | `@maximhq/bifrost`               |    8080     | Go AI گیٹ وے ریلے بیک اینڈ۔ چلنے کی صورت میں، ریلے روٹ (`/v1/relay/`) اسے خودکار طور پر منتخب کرتا ہے                                                                                                     |
| **Dario**       | `@askalf/dario`                  |    3456     | Claude سبسکرپشن پراکسی — Claude-Code طرز کی ٹریفک کے لیے CLIProxyAPI کا متبادل/فیل اوور؛ انجیکٹ کردہ کلید `DARIO_ADMIN_TOKEN` بن جاتی ہے، جو اس کے `/admin/*` OAuth کنٹرول پلین تک رسائی کو محدود کرتی ہے |
| **open-wa**     | `@open-wa/wa-automate`           |    8323     | WhatsApp Web آٹومیشن (Puppeteer کے ذریعے ہیڈ لیس Chromium)۔ صرف لائف سائیکل کا انتظام کیا جاتا ہے — یہ روٹنگ ہدف نہیں ہے۔                                                                                 |

تمام چھ ایک ہی نگرانی کے ماڈل کی پیروی کرتی ہیں:

- OmniRoute انہیں `DATA_DIR/services/{name}/` کے تحت انسٹال کرتا ہے (OmniRoute کی اپنی `package.json` سے الگ تھلگ)
- OmniRoute انہیں چائلڈ پراسیسز کے طور پر چلاتا اور مانیٹر کرتا ہے
- OmniRoute چائلڈ کے ماحول میں ایک عارضی API کلید انجیکٹ کرتا ہے اور اسے بغیر کسی ڈاؤن ٹائم کے تبدیل کرتا ہے (جہاں قابل اطلاق ہو)
- تمام انتظامی روٹس (`/api/services/*`) **LOCAL_ONLY** ہیں — صرف لوپ بیک سے قابل رسائی (قطعی اصول #17)

### اہم فیصلے (ڈیزائن پلان سے)

| فیصلہ                                    | قدر                                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 9Router کے مقامی UI تک ڈیش بورڈ کی رسائی | `/dashboard/providers/services/9router/embed/*` پر ریورس پراکسی                                   |
| تنصیب کا طریقۂ کار                       | `execFile` کے ذریعے `npm install {package}` (بغیر شیل انٹرپولیشن)                                 |
| استعمال کا موڈ                           | روٹنگ انجن میں `9router/{sub}/{model}` کے طور پر رجسٹر شدہ فراہم کنندہ                            |
| API کلید کا انتظام                       | OmniRoute اسے بناتا، غیر فعال حالت میں انکرپٹ کرتا (AES-256-GCM)، اور env کے ذریعے انجیکٹ کرتا ہے |
| ڈیش بورڈ کا مقام                         | `/dashboard/providers/services` (تین ٹیبز)                                                        |
| خودکار آغاز                              | ہر سروس کے لیے الگ ٹوگل، ڈیفالٹ طور پر بند                                                        |

## 3. لائف سائیکل اسٹیٹ مشین

```
                    install()
  ┌─────────────┐ ──────────► ┌─────────────┐
  │ not_installed│             │   stopped   │◄──────────────────┐
  └─────────────┘             └──────┬──────┘                   │
                                     │ start()                   │
                                     ▼                           │ stop()
                               ┌──────────┐                      │
                               │ starting │                      │
                               └────┬─────┘                     │
           ہیلتھ پروب کامیاب   │         کریش / SIGTERM         │
                               ┌────▼─────┐  (5s میں اخراج)      │
                               │ running  │──── کریش ───────────►┤
                               └────┬─────┘                   ┌─▼────┐
                             stop() │                          │error │
                                    ▼                          └──────┘
                               ┌──────────┐
                               │ stopping │
                               └──────────┘
```

اسٹیٹس `version_manager` DB ٹیبل (`status` کالم) میں محفوظ کیے جاتے ہیں اور
`ServiceSupervisor` کی اِن میموری حالت میں ان کی عکاسی کی جاتی ہے۔ چلتے ہوئے
پروسیس کے لیے اِن میموری حالت حتمی اتھارٹی ہے؛ بوٹ کے وقت DB حالت پائیدار متبادل ہے۔

### حالت کی منتقلیاں

| از              | ایونٹ                                  | تک                     |
| --------------- | -------------------------------------- | ---------------------- |
| `not_installed` | `install()` کامیاب ہو                  | `stopped`              |
| `stopped`       | `start()` کال کیا جائے                 | `starting`             |
| `starting`      | ہیلتھ پروب 200 واپس کرے                | `running`              |
| `starting`      | صحت مند ہونے سے پہلے پروسیس ختم ہو     | `error`                |
| `running`       | `stop()` کال کیا جائے                  | `stopping` → `stopped` |
| `running`       | پروسیس غیر متوقع طور پر ختم ہو (< 5 s) | `error` (فوری کریش)    |
| `running`       | پروسیس غیر متوقع طور پر ختم ہو (> 5 s) | `error`                |
| `error`         | `start()` کال کیا جائے                 | `starting`             |
| کوئی بھی        | `stopping` کے دوران `stop()`           | کوئی کارروائی نہیں     |

### آپریشن لاک

`ServiceSupervisor` ایک async آپریشن لاک (`withLock()`) کے ذریعے لائف سائیکل
آپریشنز کو سلسلہ وار بناتا ہے۔ ایک ہی سپروائزر پر بیک وقت `start()` کالز کے نتیجے
میں بالکل ایک پروسیس spawn ہوتا ہے؛ دوسرا کالر انتظار کرتا ہے اور موجودہ اسٹیٹس
واپس حاصل کرتا ہے۔ یہ race conditions کو روکتا ہے، مثلاً جب auto-start اور UI
بٹن بیک وقت متحرک ہوں۔


یہ پراکسی:

- درخواست کو `http://127.0.0.1:{port}/{path}` پر فارورڈ کرتی ہے (صرف لوپ بیک)
- آنے والے `cookie` اور `authorization` ہیڈرز ہٹاتی ہے (OmniRoute سیشن کا کوئی اخراج نہیں)
- 9Router تصدیق کے لیے `Authorization: Bearer {apiKey}` داخل کرتی ہے
- رسپانس سے `set-cookie`، `content-security-policy`، `x-frame-options`، `cross-origin-*` ہٹاتی ہے
- `<base href>` داخل کرنے اور مطلق راستوں کو معمول پر لانے کے لیے HTML رسپانسز کو دوبارہ لکھتی ہے (`/foo` → `/dashboard/.../embed/foo`)

ایمبیڈڈ ڈیش بورڈ کے لیے WebSocket اپ گریڈز ایک
مختص پورٹ پر موجود معاون سرور سنبھالتا ہے (`src/lib/services/embedWsProxy.ts` دیکھیں)۔

**سیکیورٹی:** ایمبیڈ پراکسی روٹس کو `LOCAL_ONLY_API_PREFIXES`
کے تحت درجہ بند کیا گیا ہے اور ان تک صرف لوپ بیک سے رسائی حاصل کی جا سکتی ہے۔ ایسا حملہ آور جو
Cloudflare/Ngrok ٹنل کے ذریعے JWT حاصل کر لے، ایمبیڈڈ سروسز تک پراکسی نہیں کر سکتا۔

## 5. سیکیورٹی

### LOCAL_ONLY کا نفاذ (سخت اصول #17)

`/api/services/` اور `/dashboard/providers/services/*/embed/` کے تحت تمام روٹس کو
`src/server/authz/routeGuard.ts` میں LOCAL_ONLY کے طور پر درجہ بند کیا گیا ہے۔ لوپ بیک کی جانچ
کسی بھی تصدیقی شاخ سے پہلے غیر مشروط طور پر چلتی ہے:

```
درخواست موصول ہوتی ہے
  → isLocalOnlyPath(path)?
      → غیر لوپ بیک → 403 LOCAL_ONLY (ہمیشہ، تصدیقی جانچ سے پہلے)
      → لوپ بیک     → معمول کی تصدیق پر جاری رہیں
```

یہ کسی افشا شدہ JWT (مثلاً، ٹنل کے ذریعے) کو `npm install` متحرک کرنے یا
پراسیس شروع کرنے سے روکتا ہے۔ مکمل درجہ جاتی میٹرکس کے لیے
`docs/security/ROUTE_GUARD_TIERS.md` دیکھیں۔

### API کلید کا اندراج

9Router اور Mux کو اپنے HTTP اینڈ پوائنٹس کے لیے API کلید/بیئرر ٹوکن درکار ہوتا ہے۔
OmniRoute:

1. `crypto.randomBytes(32).toString("base64url")` کے ذریعے سروس کے لیے مخصوص
   سابقے (`nr_` برائے 9Router، `mx_` برائے Mux) کے ساتھ کلید بناتا ہے۔
2. اسے AES-256-GCM کے ذریعے محفوظ حالت میں انکرپٹ کرتا ہے (وہی سائفر جو فراہم کنندہ کی اسناد کے لیے استعمال ہوتا ہے)۔
3. پراسیس شروع کرتے وقت اسے ڈکرپٹ کرکے ایک ماحولیاتی متغیر کے طور پر داخل کرتا ہے —
   9Router کے لیے `NINEROUTER_API_KEY`، Mux کے لیے `MUX_SERVER_AUTH_TOKEN` (کبھی بھی CLI
   فلیگ کے طور پر نہیں، تاکہ ٹوکن کبھی `ps`/پراسیس فہرستوں میں ظاہر نہ ہو)۔
4. کسی بھی HTTP جواب میں سادہ متن والی کلید کبھی واپس نہیں کرتا۔

CLIProxyAPI کو پراسیس شروع کرتے وقت ایک مخصوص ڈیٹا پلین کلید دی جاتی ہے
(`needsApiKey: true` — اڈاپٹر کے خلاف ماڈل سنک کے لیے استعمال ہوتی ہے)۔

### SSRF سے دفاع

ریورس HTTP پراکسی (`/dashboard/.../embed/[...path]`) کو صرف
`http://127.0.0.1:{port}` کی طرف فارورڈ کرنے کے لیے ہارڈ کوڈ کیا گیا ہے۔ یہ کبھی بھی غیر لوپ بیک
منزلوں کی طرف ری ڈائریکٹس کی پیروی نہیں کرتی۔ `ssrf-req-filter` لائبریری ہر ایسے upstream URL کو
مسترد کرنے کے لیے استعمال ہوتی ہے جو لوپ بیک رینج سے باہر resolve ہو۔

### شیل کی حفاظت (سخت اصول #13)

`npm install` کو `execFile('npm', ['install', pkg, '--prefix', dir])` کے ذریعے چلایا جاتا ہے —
کوئی ٹیمپلیٹ لٹرلز، کوئی شیل، اور کمانڈ اسٹرنگ میں بیرونی پاتھز کی کوئی انٹرپولیشن نہیں۔
رن ٹائم اقدار (پورٹس، API کلیدیں) چائلڈ کے `env` آبجیکٹ کے ذریعے فراہم کی جاتی ہیں۔

### خرابیوں کی تطہیر (سخت اصول #12)

`/api/services/*` سے آنے والے تمام خرابی کے جوابات `buildErrorBody()` یا
`sanitizeErrorMessage()` سے گزرتے ہیں۔ خام `err.stack` اور `err.message` کبھی بھی
کال کرنے والے کو من و عن واپس نہیں کیے جاتے۔

`src/lib/services/providerPlugins/` ایک `ServiceProviderPlugin` معاہدہ متعارف کراتا ہے جو

## 7. مسائل کا حل

### سروس شروع نہیں ہوتی

**علامات:** Start بٹن 503 واپس کرتا ہے، حالت `"error"` یا `"starting"` پر برقرار رہتی ہے۔

**چیک لسٹ:**

1. `GET /api/services/{name}/logs` چیک کریں (یا dashboard میں Logs پینل)۔ ایسی سطور تلاش کریں جیسے `Error: ENOENT`، `address already in use`، یا `Cannot find module`۔
2. تصدیق کریں کہ `npm`، PATH میں موجود ہے: اسی صارف اکاؤنٹ سے `which npm` چلائیں جو OmniRoute چلاتا ہے۔
3. تصدیق کریں کہ سروس انسٹال ہے: `installedVersion` کے لیے `GET /api/services/{name}/status` چیک کریں۔ اگر یہ `null` ہو، تو پہلے انسٹالیشن چلائیں۔
4. چیک کریں کہ `DATA_DIR/services/{name}/node_modules/` موجود ہے اور خالی نہیں ہے۔
5. صاف شدہ اختتامی وجہ کے لیے status response میں `lastError` فیلڈ چیک کریں۔

---

### کولڈ اسٹارٹ سست ہے (`running` تک پہنچنے میں > 10 s)

**علامات:** حالت `"running"` یا `"error"` میں جانے سے پہلے کافی دیر تک `"starting"` پر برقرار رہتی ہے۔

**وضاحت:** 9Router کے کولڈ اسٹارٹ میں بڑے dependency trees (DNS، tunnel، MITM modules) کو import کرنا شامل ہے۔ پہلے سے طے شدہ health interval 2 s ہے اور supervisor کی جانب سے timeout قرار دیے جانے سے پہلے 3 کوششیں کی جاتی ہیں (تاہم polling جاری رہتی ہے)۔

**حل:** `healthIntervalMs` اور `waitForHealthy` timeout
(`healthIntervalMs * 3`) کو `bootstrap.ts` میں ترتیب دیا جا سکتا ہے۔ زیادہ startup وقت لینے والی سروسز کے لیے `healthIntervalMs` کو 5000 اور `stopTimeoutMs` کو 30 000 تک بڑھائیں۔

---

### پورٹ کا ٹکراؤ (`EADDRINUSE`)

**علامات:** Logs میں `address already in use :::20130` دکھائی دیتا ہے۔

**وجوہات:**

- کوئی دوسرا process پہلے ہی port 20130 استعمال کر رہا ہے۔
- پچھلا 9Router process مکمل طور پر بند نہیں ہوا تھا (zombie PID)۔

**حل:**

1. `.env` میں `NINEROUTER_PORT` environment variable کے ذریعے پہلے سے طے شدہ port تبدیل کریں۔
2. متصادم process تلاش کرکے ختم کریں: `lsof -ti :20130 | xargs kill -9`۔
3. `bootstrap.ts` میں `port` فیلڈ کے ذریعے ہر سروس کے لیے port الگ سے ترتیب دیا جا سکتا ہے۔

**نوٹ:** 9Router بطور ڈیفالٹ port 20130 استعمال کرتا ہے تاکہ خاص طور پر OmniRoute کے پہلے سے طے شدہ port 20128 سے ٹکراؤ سے بچا جا سکے۔

---

### انسٹالیشن کے دوران اجازت مسترد (`EACCES`)

**علامات:** انسٹالیشن 500 واپس کرتی ہے، logs میں `EACCES` یا `permission denied` دکھائی دیتا ہے۔

**وجوہات:**

- OmniRoute process کو `DATA_DIR` یا اس کی parent directory میں لکھنے کی اجازت نہیں ہے۔
- mapped volume تک تحریری رسائی کے بغیر rootless Docker کے اندر چلایا جا رہا ہے۔

**حل:**

1. `DATA_DIR` چیک کریں (ڈیفالٹ: `~/.omniroute/`): `ls -la ~/.omniroute/`
2. یقینی بنائیں کہ OmniRoute process کا صارف directory کا مالک ہے: `chown -R $USER ~/.omniroute/`
3. Docker میں یقینی بنائیں کہ volume mount پر container user کے لیے درست permissions موجود ہیں۔

---

### اپ ڈیٹ ناکام ہو جاتا ہے (`npm install` timeout یا network error)

**علامات:** اپ ڈیٹ `InstallError` کے ساتھ 500 واپس کرتا ہے، logs میں network timeout دکھائی دیتا ہے۔

**چیک لسٹ:**

1. تصدیق کریں کہ npm registry قابلِ رسائی ہے: `npm ping`۔
2. corporate proxy چیک کریں: `npm config get proxy`، `npm config get https-proxy`۔
3. انسٹالیشن دستی طور پر آزمائیں: `npm install {package}@latest --prefix ~/.omniroute/services/{name}/`۔
4. اگر air-gap کے پیچھے ہوں تو tarball پہلے سے download کریں اور `npm install /path/to/tarball.tgz` استعمال کریں۔

---

### سروس شروع ہونے کے فوراً بعد `"error"` حالت دکھاتی ہے (فوری کریش)

**علامات:** حالت 5 سیکنڈ سے کم وقت میں `"starting"` سے `"error"` میں تبدیل ہو جاتی ہے۔
`lastError` میں `"Fast crash (exited with code 1)"` دکھائی دیتا ہے۔

**چیک لسٹ:**

1. log کا مکمل آخری حصہ پڑھیں: `GET /api/services/{name}/logs?tail=500`۔
2. عام وجہ: سروس کو درکار environment variables موجود نہیں ہیں۔
3. 9Router کے لیے: تصدیق کریں کہ `NINEROUTER_DISABLE_MITM=true` اور
   `NINEROUTER_DISABLE_TUNNEL=true`، spawn کے وقت پاس کیے گئے env میں موجود ہیں (`installers/ninerouter.ts` میں `resolveSpawnArgs` دیکھیں)۔

## 8. اکثر پوچھے گئے سوالات

**سوال: کیا میں ایمبیڈڈ سروسز کے endpoints کو non-loopback clients کے لیے قابلِ رسائی بنا سکتا ہوں؟**

نہیں۔ LOCAL_ONLY tier دانستہ طور پر مقرر کیا گیا ہے (سخت اصول #17)۔ وہ routes جو
`npm install` چلا سکتے ہیں یا `node` processes شروع کر سکتے ہیں، non-loopback
traffic سے قابلِ رسائی نہیں ہونے چاہییں، کیونکہ بصورتِ دیگر کسی tunnel (Cloudflare، Ngrok، Tailscale) کے ذریعے
لیک ہونے والا JWT صوابدیدی processes شروع کرنے کی اجازت دے دے گا۔ اس پابندی سے دست برداری کی کوئی استثنائی گنجائش
`/api/services/` کے لیے موجود نہیں ہے — `/api/mcp/` کے برعکس، اسے manage-scope bypass
فہرست سے خارج رکھا گیا ہے۔ `docs/security/ROUTE_GUARD_TIERS.md` دیکھیں۔

---

**سوال: کیا 9Router اور CLIProxyAPI production/cloud deployments میں دستیاب ہوں گے؟**

ہاں۔ دونوں سروسز OmniRoute کی طرح اسی local-first ماڈل کی پیروی کرتی ہیں۔ وہ اسی
مشین پر چلتی ہیں اور loopback کے ذریعے رابطہ کرتی ہیں۔ یہاں "Production" سے مراد وہ VPS
یا local server ہے جہاں OmniRoute deploy کیا گیا ہے، نہ کہ کوئی remote cloud provider۔

---

**سوال: میں supervisor کو debug کیسے کروں؟**

1. SSE log stream کو tail کریں: `curl -N http://localhost:20128/api/services/9router/logs`۔
2. OmniRoute کے pino output میں structured logs کو
   `service:supervisor` namespace کے مطابق filter کر کے دیکھیں۔
3. DB row کا معائنہ کریں: `sqlite3 ~/.omniroute/omniroute.db "SELECT * FROM version_manager WHERE tool='9router'"`۔
4. موجودہ live state، PID، health،
   اور `lastError` کو ایک ہی call میں دیکھنے کے لیے `GET /api/services/9router/status` استعمال کریں۔

---

**سوال: supervisor میں `health: "degraded"` یا `health: "unknown"` دکھائی دیتا ہے، لیکن state `"running"` ہے۔ کیا یہ مسئلہ ہے؟**

`"degraded"` کا مطلب ہے کہ health probe نے non-200 response واپس کیا۔ `"unknown"` کا مطلب ہے کہ ابھی تک کوئی
probe مکمل نہیں ہوا (پہلے poll کے ساتھ race)۔ startup کے دوران دونوں حالتیں عارضی ہوتی ہیں۔
اگر `"running"` کے بعد `healthIntervalMs * 3` ms سے زیادہ وقت تک health
`"degraded"` رہے، تو ایمبیڈڈ سروس چل رہی ہے لیکن اس کا HTTP API جواب نہیں دے رہا۔ چیک کریں
کہ status response میں port درست ہے اور آیا سروس واقعی
اس port پر سن رہی ہے۔

---

**سوال: کیا میں مکمل restart کے بغیر 9Router API key تبدیل کر سکتا ہوں؟**

نہیں۔ API key کو spawn کے وقت environment variable کے ذریعے 9Router کو دیا جاتا ہے۔
چلتے ہوئے process میں environment variables تبدیل نہیں کیے جا سکتے۔ `POST .../rotate-key`
نئی key لاگو کرنے کے لیے سروس کو خودکار طور پر روکتا اور دوبارہ شروع کرتا ہے۔ key rotation
سروس کے `stopTimeoutMs` (default 15 s) اور اس کے startup
وقت کے اندر مؤثر ہو جاتی ہے۔

---

**سوال: ring buffer کی حد کیا ہے اور بھر جانے پر کیا ہوتا ہے؟**

ہر سروس کے لیے مختص 5 MB کا ring buffer ہوتا ہے۔ buffer بھر جانے پر نئی log lines کے لیے جگہ بنانے کی خاطر سب سے پرانی
log lines نکال دی جاتی ہیں۔ SSE `snapshot` event،
`tail` حد کے اندر تازہ ترین lines واپس کرتا ہے۔ logs کو disk پر برقرار نہیں رکھا جاتا، سوائے اس صورت کے جب
DB row میں `logsBufferPath` مقرر ہو۔
