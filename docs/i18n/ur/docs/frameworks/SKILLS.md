> **مستند ماخذ:** `src/lib/skills/` اور `src/app/api/skills/`
> **آخری بار اپ ڈیٹ کیا گیا:** 2026-06-28 — v3.8.40

OmniRoute ایک قابلِ توسیع Skills فریم ورک فراہم کرتا ہے جو زبان کے ماڈلز (اور آپریٹرز) کو دوبارہ قابلِ استعمال صلاحیتیں یکجا کرنے دیتا ہے — فائل سسٹم سے ڈیٹا پڑھنے اور HTTP درخواستوں سے لے کر سینڈ باکس میں کوڈ چلانے اور منتخب مارکیٹ پلیس اسکلز تک۔

ایک اسکل کام کی ایک ورژن شدہ، اسکیما کے ذریعے متعین اکائی ہوتی ہے۔ OmniRoute اسکلز کو ٹول کی تعریفوں کے طور پر بیرونی درخواستوں میں شامل کر سکتا ہے، ماڈل سے واپس آنے والی ٹول کالز کو روک کر متعلقہ ہینڈلر چلا سکتا ہے، اور نتیجہ واپس ماڈل کو دے سکتا ہے تاکہ گفتگو جاری رہ سکے۔ ماڈل کبھی نفاذ نہیں دیکھتا — صرف ٹول انٹرفیس دیکھتا ہے۔

## Agent Skills بمقابلہ Omni Skills

OmniRoute میں دو الگ مگر ایک دوسرے کی تکمیل کرنے والے اسکل سسٹمز ہیں:

| جہت                 | **Omni Skills** (یہ دستاویز)                           | **Agent Skills**                                                                           |
| :------------------ | :----------------------------------------------------- | :----------------------------------------------------------------------------------------- |
| مقصد                | LLM ٹول کا اندراج + سینڈ باکس میں عمل درآمد            | بیرونی ایجنٹس کے دریافت اور استعمال کے لیے SKILL.md کیٹلاگ                                 |
| مستند ماخذ          | `src/lib/skills/` + مارکیٹ پلیس                        | `src/lib/agentSkills/` + `skills/` ڈائریکٹری                                               |
| رن ٹائم موڈ         | بیرونی درخواستوں میں شامل، ٹول کال واقعات پر عمل درآمد | جامد markdown کیٹلاگ + REST/MCP/A2A دریافت کے اینڈ پوائنٹس                                 |
| کون استعمال کرتا ہے | خود OmniRoute (کمبو روٹنگ، آنے والی LLM کالز)          | بیرونی ایجنٹس، MCP کلائنٹس، A2A آرکیسٹریٹرز                                                |
| تعداد               | متغیر (مارکیٹ پلیس پر منحصر)                           | 45 کیٹلاگ اندراجات (23 API + 21 CLI + 1 کنفیگریشن)                                         |
| فارمیٹ              | ٹول اسکیما + ہینڈلر کے ساتھ `SkillDefinition`          | `SKILL.md` فرنٹ میٹر + markdown متن                                                        |
| دریافت              | `/api/skills/*` REST + `omniroute_skills_*` MCP ٹولز   | `/api/agent-skills/*` REST + `omniroute_agent_skills_*` MCP ٹولز + A2A `list-capabilities` |

**Omni Skills** عمل درآمد کا انجن ہیں — یہ متعین کرتے ہیں کہ جب کوئی LLM کسی ٹول کو استعمال کرے تو OmniRoute _کیا کر سکتا ہے_۔

**Agent Skills** دستاویزاتی کیٹلاگ ہیں — یہ بیرونی ایجنٹس کو وضاحت کرتے ہیں کہ OmniRoute کی REST API اور CLI کو _کیسے استعمال کیا جائے_، اور اس کے لیے منظم SKILL.md فائلیں فراہم کرتے ہیں جنہیں براہِ راست ایجنٹ پرامپٹس میں شامل کیا جا سکتا ہے۔

Agent Skills کیٹلاگ، جنریٹر، MCP ٹولز، اور A2A اسکل کے لیے [docs/frameworks/AGENT-SKILLS.md](./AGENT-SKILLS.md) دیکھیں۔

## تصورات

### اسکل کے ذرائع

اسکلز کے تین ذرائع ایک ہی رجسٹری میں بیک وقت موجود ہوتے ہیں:

1. **بلٹ اِن اسکلز** (`src/lib/skills/builtins.ts`) — OmniRoute کے ساتھ فراہم کیے جاتے ہیں۔ یہ عام استعمال کے حالات کا احاطہ کرتے ہیں:
   - `file_read`, `file_write` — `<DATA_DIR>/skills/workspaces/<hashed-key>/` کے تحت ہر API کلید کے لیے الگ سینڈ باکس ورک اسپیس
   - `http_request` — `guard: "public-only"` کے ساتھ `safeOutboundFetch` کے ذریعے بیرونی HTTP
   - `web_search` — کیشنگ کے ساتھ قابلِ تبدیل سرچ فراہم کنندہ (`executeWebSearch`)
   - `eval_code` — Docker سینڈ باکس میں `node` یا `python` کا عمل درآمد
   - `execute_command` — Docker سینڈ باکس میں شیل کمانڈ
   - `browser` — Playwright پر مبنی بنیادی ڈھانچا، بطور ڈیفالٹ غیر فعال (`builtin/browser.ts`)
2. **SkillsMP** (OmniRoute مارکیٹ پلیس) — `https://skillsmp.com/api/v1/skills/search` سے حاصل کیا جاتا ہے۔ Settings میں `skillsmpApiKey` درکار ہے۔
3. **SkillsSH** (`skills.sh` کمیونٹی کیٹلاگ) — `https://skills.sh/api/search` سے حاصل کیا جاتا ہے۔ کسی تصدیق کی ضرورت نہیں؛ SKILL.md کا مواد GitHub raw سے حاصل کیا جاتا ہے۔

ایک واحد "فعال فراہم کنندہ" یہ کنٹرول کرتا ہے کہ ڈیش بورڈ کس کیٹلاگ سے انسٹال کرے (`src/lib/skills/providerSettings.ts`)۔ اسے **Settings → Memory & Skills** کے تحت تبدیل کریں۔ ڈیفالٹ: `skillsmp`۔

### اسکل کی شناخت

درونِ میموری رجسٹری (`src/lib/skills/registry.ts`) میں اسکلز کی کلید `name@version` ہوتی ہے۔ ورژن کا semver (`^\d+\.\d+\.\d+$`) ہونا ضروری ہے۔ `resolveVersion()`، `^`، `~`، `>`، `>=`، `<`، `<=`، `==`، اور عین مماثلت کی پابندیوں کو سمجھتا ہے۔

### اسکل موڈ

ہر اسکل کا ایک رن ٹائم موڈ ہوتا ہے جو یہ کنٹرول کرتا ہے کہ اسے کب شامل کیا جائے:

| موڈ    | طرزِ عمل                                                                                                            |
| ------ | ------------------------------------------------------------------------------------------------------------------- |
| `on`   | ہمیشہ ٹول کی تعریف کے طور پر شامل کیا جاتا ہے                                                                       |
| `off`  | کبھی شامل نہیں کیا جاتا اور کبھی قابلِ عمل نہیں ہوتا                                                                |
| `auto` | آنے والی درخواست کے مقابل اسکور کیا جاتا ہے؛ صرف اس صورت میں شامل ہوتا ہے جب اسکور ≥ `AUTO_MIN_SCORE` ہو (ڈیفالٹ 3) |

مارکیٹ پلیس سے انسٹال کردہ اسکلز کے لیے `auto` ڈیفالٹ ہے۔ `enabled=true` اور `mode="off"` کا ایک ساتھ مطلب "رجسٹرڈ مگر غیر فعال" ہے — قدیم کالم کے ذریعے `enabled` کو ٹوگل کرنے سے `mode` بھی تبدیل ہوتا ہے، تاکہ پرانے کوڈ راستے ہم آہنگ رہیں (`src/app/api/skills/[id]/route.ts`)۔

### اسٹیٹس (عمل درآمد)

اسکل کے عمل درآمد کو `skill_executions` ٹیبل میں درج ذیل اسٹیٹسز کے ساتھ ٹریک کیا جاتا ہے (`src/lib/skills/types.ts`):

```ts
enum SkillStatus {
  PENDING = "pending",
  RUNNING = "running",
  SUCCESS = "success",
  ERROR = "error",
  TIMEOUT = "timeout",
}
```

### رجسٹری کیش

`SkillRegistry` ایک سنگلٹن ہے جس میں 60 سیکنڈ کا TTL کیش موجود ہے (`registry.ts:14`)۔ `loadFromDatabase()` idempotent ہے اور `pendingLoad` کے ذریعے بیک وقت ہونے والی کالز کی نقل ختم کرتا ہے۔ ہر تحریری کارروائی (`register`/`unregister`/`unregisterById`) کیش کو غیر مؤثر کر دیتی ہے۔ ورژنز تلاش کرنے کے لیے `getSkillVersions(name)` اور `resolveVersion(name, constraint)` استعمال کریں۔

### فراہم کنندہ سے آگاہ اندراج

`src/lib/skills/injection.ts` میں موجود `injectSkills()` وہ نقطۂ آغاز ہے جو رجسٹرڈ اسکلز کو فراہم کنندہ کے لیے مخصوص ٹول تعریفوں میں تبدیل کرتا ہے:

- **OpenAI** — `{ type: "function", function: { name, description, parameters } }`
- **Anthropic** — `{ name, description, input_schema }`
- **Google (Gemini)** — `{ name, description, parameters }`

ٹول کا نام `name@version` کی صورت میں انکوڈ کیا جاتا ہے تاکہ جب ماڈل اسے واپس کال کرے تو ہینڈلر درست ورژن منتخب کر سکے۔

### AUTO اسکورنگ

جب `mode="auto"` ہو، تو ہر امیدوار اسکل کو درخواست کے سیاق و سباق کے مقابل اسکور کیا جاتا ہے (`injection.ts` میں `scoreAutoSkill()`):

| اشارہ                                                         | پوائنٹس    |
| ------------------------------------------------------------- | ---------- |
| اسکل کا نام سیاق و سباق میں بعینہٖ موجود ہو                   | +6         |
| نام کا ہر ٹوکن سیاق و سباق کے کسی ٹوکن سے مماثل ہو            | +2         |
| ہر ٹیگ کا ذیلی اسٹرنگ سیاق و سباق سے مماثل ہو                 | +3         |
| وضاحت کا ہر ٹوکن سیاق و سباق سے مماثل ہو                      | +1         |
| پس منظر کی وجہ نام کے کسی ٹوکن سے مماثل ہو                    | +2 فی ٹوکن |
| پس منظر کی وجہ کسی ٹیگ سے مماثل ہو                            | +2 فی ٹوکن |
| ٹیگز میں موجود پرووائیڈر ہنٹ درخواست کے پرووائیڈر سے مماثل ہو | +2 / −2    |

`score >= AUTO_MIN_SCORE = 3` والی سرفہرست `AUTO_MAX_SKILLS = 5` اسکلز انجیکٹ کی جاتی ہیں۔ برابری کی صورت میں پہلے `installCount` (نزولی ترتیب)، اور پھر حروفِ تہجی کے مطابق نام سے فیصلہ کیا جاتا ہے (`injection.ts:225-235`)۔

### ٹول کال کی انٹرسیپشن

اپ اسٹریم کی جانب سے ٹول کال کرنے والا رسپانس واپس آنے کے بعد چیٹ ہینڈلر، `src/lib/skills/interception.ts` میں موجود `handleToolCallExecution()` کو طلب کرتا ہے:

1. `extractToolCalls()` پرووائیڈر کے لیے مخصوص ساختیں پڑھتا ہے (OpenAI کے `tool_calls` / Responses کے `function_call`، Anthropic کے `tool_use`، Gemini کے `functionCalls`)۔
2. پہلے بلٹ اِن ٹول کے عرفی نام (مثلاً `omniroute_web_search` → `web_search`) ریزولو کیے جاتے ہیں۔ بلٹ اِن ہینڈلرز اِن لائن چلتے ہیں۔
3. باقی ہر چیز کو `skillExecutor.execute(name@version, args, { apiKeyId, sessionId })` کے ذریعے روٹ کیا جاتا ہے۔
4. نتائج کو مناسب انداز میں رسپانس میں واپس شامل کر دیا جاتا ہے — `tool_results`، `function_call_output` آئٹمز، یا Anthropic کے `tool_result` بلاکس۔

ایگزیکیوشن سیاق و سباق میں `customSkillExecutionEnabled` کو `false` پر سیٹ کیا جا سکتا ہے تاکہ صرف بلٹ اِن انٹرسیپشن کی اجازت ہو (یہ ان درخواست راستوں میں استعمال ہوتا ہے جو صارف کی وضاحت کردہ ہینڈلرز کو واضح طور پر غیر فعال کرتے ہیں)۔

## Docker سینڈ باکس

غیر بلٹ اِن کوڈ پاتھز (`eval_code`, `execute_command`) کو `SandboxRunner` (`src/lib/skills/sandbox.ts`) کے ذریعے Docker کے اندر چلایا جاتا ہے۔ ہر کنٹینر درج ذیل کے ساتھ لانچ کیا جاتا ہے:

```
--rm --network none|bridge --cap-drop ALL
--security-opt no-new-privileges --pids-limit 100
--cpus <cpuLimit/1000> --memory <memoryLimit>m
--tmpfs /tmp:rw,noexec,nosuid,size=64m
--tmpfs /workspace:rw,noexec,nosuid,size=64m
--read-only (جب readOnly=true ہو)
```

ڈیفالٹس (`SandboxRunner.DEFAULT_CONFIG`):

| فیلڈ             | ڈیفالٹ          | نوٹس                                                        |
| ---------------- | --------------- | ----------------------------------------------------------- |
| `cpuLimit`       | 100 (= 0.1 CPU) | `--cpus` کو پاس کرنے سے پہلے 1000 سے تقسیم کیا جاتا ہے      |
| `memoryLimit`    | 256 MB          | قطعی حد                                                     |
| `timeout`        | 30000 ms        | `SIGTERM` + `docker kill` کے ذریعے سافٹ کِل                 |
| `networkEnabled` | `false`         | `--network none` بن جاتا ہے                                 |
| `readOnly`       | `true`          | روٹ FS صرف پڑھنے کے لیے؛ `/tmp` اور `/workspace`، tmpfs ہیں |

شٹ ڈاؤن کے لیے `SandboxRunner.kill(id)` اور `killAll()` دستیاب ہیں؛ چلتے ہوئے کنٹینرز کو `runningContainers: Map<string, ChildProcess>` میں ٹریک کیا جاتا ہے۔

### سینڈ باکس ماحولیاتی متغیرات

`src/lib/skills/builtins.ts` میں `process.env` کے ذریعے کنفیگر کیے گئے ہیں:

| ماحولیاتی متغیر                   | ڈیفالٹ           | مقصد                                                                                |
| --------------------------------- | ---------------- | ----------------------------------------------------------------------------------- |
| `SKILLS_MAX_FILE_BYTES`           | `1048576` (1 MB) | `file_read` اور `file_write` کے لیے حد                                              |
| `SKILLS_MAX_HTTP_RESPONSE_BYTES`  | `256000`         | `http_request` کے رسپانس باڈی کے لیے حد                                             |
| `SKILLS_MAX_SANDBOX_OUTPUT_CHARS` | `100000`         | کالر کو واپس کیے جانے والے stdout/stderr کے لیے حد                                  |
| `SKILLS_SANDBOX_TIMEOUT_MS`       | `10000`          | سینڈ باکس کمانڈز کے لیے ڈیفالٹ ٹائم آؤٹ؛ زیادہ سے زیادہ 60 s                        |
| `SKILLS_SANDBOX_NETWORK_ENABLED`  | `false`          | ایگریس کے لیے ماسٹر گیٹ۔ فی کال آپٹ اِن کی اجازت دینے کے لیے `1` یا `true` سیٹ کریں |
| `SKILLS_ALLOWED_SANDBOX_IMAGES`   | (ذیل میں دیکھیں) | Docker امیجز کی کوما سے علیحدہ کردہ اجازت فہرست                                     |

ڈیفالٹ مجاز امیجز: `alpine:3.20`, `node:22-alpine`, `python:3.12-alpine`۔ `SKILLS_ALLOWED_SANDBOX_IMAGES` کے ذریعے کیے گئے اضافے ڈیفالٹس کے ساتھ ضم کر دیے جاتے ہیں؛ نامعلوم امیجز کو `normalizeImage()` مسترد کر دیتا ہے۔

> نوٹ: کوئی علیحدہ `SKILLS_EXECUTION_TIMEOUT_MS` ماحولیاتی متغیر موجود نہیں ہے۔ غیر سینڈ باکس ہینڈلر کا ٹائم آؤٹ `SkillExecutor` (`executor.ts:13`) میں 30 s پر ہارڈ کوڈڈ ہے، لیکن رن ٹائم کے دوران `skillExecutor.setTimeout(ms)` کے ذریعے اسے اوور رائیڈ کیا جا سکتا ہے۔

### ورک اسپیس کی علیحدگی

`file_read` اور `file_write` ہر پاتھ کو `<DATA_DIR>/skills/workspaces/<sha256(apiKeyId).slice(0,24)>/` میں موجود فی API کلید ورک اسپیس کے لحاظ سے ریزولو کرتے ہیں۔ کسی بھی ڈسک I/O سے پہلے پاتھ ٹریورسل (`..`) اور ممنوعہ سیگمنٹس (`.env`, `.git`, `.ssh`, `.omniroute`, `.codex`, `secrets`) مسترد کر دیے جاتے ہیں۔

### HTTP کی مضبوط سیکیورٹی

`http_request` (`builtins.ts:257`):

- طریقوں کی اجازت فہرست: `GET, HEAD, POST, PUT, PATCH, DELETE`
- بلاک شدہ آؤٹ باؤنڈ ہیڈرز: `host, connection, content-length, cookie, set-cookie, authorization, proxy-authorization`
- ری ڈائریکٹس غیر فعال (`allowRedirect: false`)
- `guard: "public-only"` کے ساتھ `safeOutboundFetch` کے ذریعے روٹ کیا جاتا ہے (نجی/لوپ بیک رینجز بلاک ہیں)
- رسپانس کو `SKILLS_MAX_HTTP_RESPONSE_BYTES` پر مختصر کر دیا جاتا ہے؛ کلائنٹ کو `truncated: true` نظر آتا ہے

## عمل درآمد کا لائف سائیکل (v3.8.16+)

`SkillExecutor` (`src/lib/skills/executor.ts`) ایک **singleton** ہے جو ہر skill invocation کو منظم کرتا ہے۔ timeouts، retries، اور execution state کی debugging کے لیے اس کے lifecycle کو سمجھنا انتہائی اہم ہے۔

### 5 مراحل پر مشتمل لائف سائیکل

```
   execute() کو کال کیا گیا
        │
        ▼
  ┌─────────────┐
  │  PENDING    │  ← قطار میں، ابھی شروع نہیں ہوا (DB row تخلیق کی گئی)
  └──────┬──────┘
         │ handler شروع کریں
         ▼
  ┌─────────────┐
  │  RUNNING    │  ← handler کو timeout کے ساتھ invoke کیا گیا
  └──────┬──────┘
         │
    ┌────┴────┬──────────┬──────────┐
    │         │          │          │
    ▼         ▼          ▼          ▼
  SUCCESS   ERROR     TIMEOUT   (کوئی دوسرا راستہ نہیں — parent نے ختم کر دیا)
    │         │          │
    └────┬────┴──────────┘
         │
         ▼
   DB row کو status، output، durationMs کے ساتھ اپ ڈیٹ کیا گیا
```

### ڈیفالٹ کنفیگریشن

| ترتیب        | ڈیفالٹ        | جس کے ذریعے کنفیگر کیا جا سکتا ہے    |
| ------------ | ------------- | ------------------------------------ |
| `timeout`    | `30000` (30s) | `skillExecutor.setTimeout(ms)`       |
| `maxRetries` | `3`           | `skillExecutor.setMaxRetries(count)` |

> **اہم**: executor ایک singleton ہے — `setTimeout()` کو کال کرنے سے بعد کی تمام invocations عالمی طور پر متاثر ہوتی ہیں۔ فی skill timeouts فی الحال معاونت یافتہ نہیں ہیں؛ اگر آپ کو ہر skill کے لیے مختلف timeouts درکار ہوں تو علیحدہ processes submit کریں یا executor کو fork کریں۔

### Status کی اقدار

`src/lib/skills/types.ts` سے:

```ts
enum SkillStatus {
  PENDING = "pending", // قطار میں، ابھی شروع نہیں ہوا
  RUNNING = "running", // Handler کو invoke کیا گیا
  SUCCESS = "success", // Handler نے درست output واپس کیا
  ERROR = "error", // Handler نے exception پھینکا
  TIMEOUT = "timeout", // Executor کا timeout تجاوز کر گیا
}
```

> **نوٹ**: `TIMEOUT` status کی enum میں تعریف موجود ہے، لیکن executor کا موجودہ implementation اسے **حقیقتاً DB میں نہیں لکھتا** — timeouts، `"Skill execution timed out"` پیغام کے ساتھ `ERROR` کی صورت میں ظاہر ہوتے ہیں۔ status enum مستقبل کے استعمال کے لیے محفوظ ہے۔

### Executions کا معائنہ

```ts
import { skillExecutor } from "omniroute/skills/executor";

// ID کے ذریعے ایک مخصوص execution حاصل کریں
const exec = skillExecutor.getExecution("exec-uuid-123");
if (exec) {
  console.log(`${exec.skillName}: ${exec.status} in ${exec.durationMs}ms`);
}

// ایک API key کے لیے حالیہ executions کی فہرست حاصل کریں
const recent = skillExecutor.listExecutions("api-key-id", 50, 0);
for (const e of recent) {
  console.log(`${e.skillName} → ${e.status} (${e.durationMs}ms)`);
}

// کل executions شمار کریں
const total = skillExecutor.countExecutions("api-key-id");
```

### Retry کا طرزِ عمل

`maxRetries` ترتیب محفوظ کی جاتی ہے، لیکن executor کا `execute()` method اسے **فی الحال استعمال نہیں کرتا** — یہ صرف ایک کوشش کرتا ہے۔ `maxRetries` کی قدر مستقبل کے implementation اور اسے پڑھنے کے خواہش مند hooks کے لیے دستیاب رکھی گئی ہے۔

فی الحال retries کو خود skill handler کے اندر implement کرنا ضروری ہے۔ Built-in
skills کو executor کے ساتھ register کیا جاتا ہے (مثلاً `registerBuiltinSkills(executor)`
/ `registerBrowserSkill(executor)` در `src/lib/skills/builtin/`)؛ آپ جو بھی handler
register کریں، وہ اپنے retry loop کو wrap کر سکتا ہے:

```ts
// ایک skill handler کے اندر
async function handler(input, ctx) {
  const maxRetries = 3;
  let lastError: Error | null = null;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await fetchSomething(input);
    } catch (err) {
      lastError = err as Error;
      if (attempt < maxRetries) {
        await new Promise((r) => setTimeout(r, 1000 * attempt));
      }
    }
  }
  throw lastError;
}
```

## SkillMode کی تفصیل

`SkillMode` enum (`src/lib/skills/types.ts`) کنٹرول کرتا ہے کہ skills کو **کب اور کیسے** invoke کیا جاتا ہے:

```ts
enum SkillMode {
  AUTO = "auto", // LLM فیصلہ کرتا ہے کہ skill کو کب call کرنا ہے
  MANUAL = "manual", // صرف صارف کی واضح درخواست پر invoke کیا جاتا ہے

}
```

> **نوٹ**: codebase میں `SkillMode` (AUTO/MANUAL/HYBRID) کی تعریف موجود ہے، جبکہ `Skill.mode` فیلڈ ایک مختلف ساخت (`"on" | "off" | "auto"`) استعمال کرتی ہے۔ یہ ایک دوسرے سے متعلق ہیں لیکن یکساں نہیں — `SkillMode` executor policy کے لیے ہے، جبکہ `Skill.mode` ہر skill کو فعال کرنے کے لیے ہے۔

### ہر Mode کب استعمال کریں

| Mode     | LLM کا طرزِ عمل                                                                     | استعمال کی صورت                                       |
| -------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `AUTO`   | جب LLM ضروری سمجھے تو skill کو call کر سکتا ہے                                      | عمومی مقاصد کی skills (فائل پڑھنا، HTTP درخواستیں)    |
| `MANUAL` | LLM skill کو call نہیں کر سکتا؛ صرف واضح `executeSkill` API call اسے invoke کرتی ہے | حساس کارروائیاں (database writes، payments)           |
| `HYBRID` | LLM skill تجویز کر سکتا ہے؛ صارف کی تصدیق ضروری ہے                                  | ایسی skills جن کے ضمنی اثرات ہوں مگر وہ خطرناک نہ ہوں |

### AUTO اسکورنگ

جب `AUTO` mode فعال ہو تو ہر امیدوار skill کو درخواست کے context کے مقابل
`src/lib/skills/injection.ts` میں موجود `scoreAutoSkill()` کے ذریعے اسکور کیا جاتا ہے — یہ ایک اضافی،
صحیح عددی پوائنٹ سسٹم ہے (skill کے نام کی مماثلت، نام/tag/description کے tokens کا overlap،
background-reason کے اشارے، provider-hint bonus/penalty)۔ سب سے زیادہ اسکور والی
`AUTO_MAX_SKILLS = 5` skills جن کا `score >= AUTO_MIN_SCORE = 3` ہو، قابلِ call tools کے طور پر
inject کی جاتی ہیں، جبکہ برابر اسکور کی صورت میں پہلے `installCount` اور پھر نام کے ذریعے فیصلہ کیا جاتا ہے۔ مکمل پوائنٹ ٹیبل
اس دستاویز میں پہلے موجود [**Tool Schema Generation → AUTO اسکورنگ**](#auto-scoring) میں دیکھیں؛
یہاں float `0.6` طرز کی کوئی threshold اور `registry.ts` میں کوئی scoring موجود نہیں ہے۔

## Built-in Skills کی فہرست

OmniRoute میں `src/lib/skills/builtin/` کے اندر منتخب شدہ built-in skills کا ایک مجموعہ شامل ہے۔ سب سے عام skills یہ ہیں:

### Browser Automation Skill

browser skill (`src/lib/skills/builtin/browser.ts`) Playwright/Puppeteer کے ذریعے headless browser automation فراہم کرتی ہے۔ **یہ implement کی گئی ہے، لیکن default skills catalog میں شامل نہیں** — اسے استعمال کرنے کے لیے browser extension plugin الگ سے install کریں۔

```ts
// اپنی config میں فعال کریں
const config: SkillConfig = {
  enabled: true,
  mode: SkillMode.MANUAL, // ہمیشہ واضح invocation درکار ہو
  allowedSkills: ["browser"],
  timeout: 60000, // page loads کے لیے 60s
  maxRetries: 1,
};
```

### دیگر Built-in زمرے

| زمرہ      | Skills                                      | Mode   |
| --------- | ------------------------------------------- | ------ |
| File I/O  | `file_read`, `file_write`                   | AUTO   |
| HTTP      | `http_request`                              | AUTO   |
| تلاش      | `web_search`                                | AUTO   |
| Code Exec | `eval_code` (sandboxed JavaScript/Python)   | HYBRID |
| سسٹم      | `execute_command` (sandboxed CLI execution) | MANUAL |

plugin system کے ذریعے custom skill شامل کرنے کا طریقہ جاننے کے لیے [Plugin SDK اور Skills Integration](./PLUGIN_SDK.md) دیکھیں۔
