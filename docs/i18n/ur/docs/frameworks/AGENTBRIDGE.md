AgentBridge، OmniRoute کا MITM (Man-in-the-Middle) پراکسی ہے جو IDE کے AI ایجنٹس سے آنے والی HTTPS ٹریفک کو انٹرسیپٹ کرتا ہے اور اسے OmniRoute کے متحدہ روٹنگ انجن کے ذریعے دوبارہ روٹ کرتا ہے۔ یہ **10 IDE ایجنٹس** — Antigravity، Kiro، GitHub Copilot، GHE Copilot، OpenAI Codex، Cursor، Zed، Claude Code، Open Code، اور Trae (زیرِ تحقیق) — کو سپورٹ کرتا ہے، جس سے OmniRoute مارکیٹ میں AI کوڈنگ اسسٹنٹس کے لیے سب سے وسیع کوریج والا MITM پراکسی بن جاتا ہے۔

**ڈیش بورڈ کا مقام:** `/dashboard/tools/agent-bridge`
**سائیڈ بار گروپ:** ٹولز (Cloud Agents کے بعد)
**یہ بھی دیکھیں:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — تمام انٹرسیپٹ شدہ ٹریفک کو ریئل ٹائم میں مانیٹر کریں؛ `docs/security/MITM-TPROXY-DECRYPT.md` (git؛ `/docs` میں کمپائل نہیں کیا گیا) — Linux کا TPROXY شفاف-ڈکرپٹ کیپچر موڈ، جو `/api/tools/agent-bridge/tproxy` روٹ کے ذریعے چلتا ہے۔

## §1 جائزہ

### AgentBridge کیا ہے؟

جب کوئی IDE ایجنٹ (مثلاً GitHub Copilot، Cursor، Claude Code) API کال کرتا ہے، تو وہ براہِ راست اپ اسٹریم AI فراہم کنندہ (OpenAI، Anthropic وغیرہ) سے جڑتا ہے۔ AgentBridge کسی بھی ایجنٹ کی کنفیگریشن تبدیل کیے بغیر، TLS کی سطح پر اس کنکشن کو شفاف انداز میں انٹرسیپٹ کرتا ہے — اور درخواست کو OmniRoute کے ذریعے دوبارہ لکھتا ہے۔

اس کا مطلب ہے کہ آپ:

- **کسی بھی ایجنٹ کو کسی بھی فراہم کنندہ کی طرف دوبارہ روٹ کر سکتے ہیں**: کیا Copilot، OpenAI سے رابطہ کر رہا ہے؟ اسے Anthropic Claude، Gemini، یا OmniRoute کے 352 فراہم کنندگان میں سے کسی کی طرف ری ڈائریکٹ کریں۔
- **ماڈل میپنگز لاگو کر سکتے ہیں**: ہینڈلر کی سطح پر `gemini-3-flash` → `claude-sonnet-4.7` شفاف انداز میں۔
- **ایجنٹ کی تمام ٹریفک کا مشاہدہ کر سکتے ہیں**: ہر انٹرسیپٹ شدہ درخواست [Traffic Inspector](./TRAFFIC_INSPECTOR.md) کو شائع کی جاتی ہے۔
- **OmniRoute کی لچک پذیری لاگو کر سکتے ہیں**: کومبو روٹنگ، سرکٹ بریکرز، فال بیکس، اور لاگت کی ٹریکنگ IDE ایجنٹ ٹریفک کے لیے بھی کام کرتے ہیں۔

## §2 آرکیٹیکچر

### 2.1 اجزاء کا جائزہ

```
IDE ایجنٹ (VS Code / Cursor / وغیرہ)
    │  HTTPS (پورٹ 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← DNS ری ڈائریکٹ
    │
    ▼
src/mitm/server.cjs  (پورٹ 443، CJS چائلڈ پراسیس)
    │  Host ہیڈر SNI کے ذریعے ہدف کا تعین کرتا ہے
    │  AgentBridge CA سے دستخط شدہ فی-SNI TLS سرٹیفکیٹ تیار کرتا ہے
    ├── بائی پاس فہرست سے مطابقت؟ → TCP پاس تھرو (کوئی ڈکرپشن نہیں)
    ├── ہدف سے مطابقت؟ → fetch → OmniRoute راؤٹر (پورٹ 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── درخواست کی باڈی/ہیڈرز پر maskSecrets()
    │               ├── TrafficBuffer.push() — Traffic Inspector کو شائع کرتا ہے
    │               └── fetchRouter() → /v1/chat/completions
    └── کوئی مطابقت نہیں؟ → TCP پاس تھرو (کوئی ڈکرپشن نہیں)
```

### 2.2 MITM سرور (`src/mitm/server.cjs`)

بنیادی MITM سرور Node.js CJS چائلڈ پراسیس کے طور پر چلتا ہے (موجودہ CJS کوڈ بیس کو دوبارہ لکھنے سے بچنے کے لیے)۔ یہ:

- پورٹ 443 پر سنتا ہے (خصوصی مراعات یا `authbind`/`setcap` درکار ہیں)
- OS سے CONNECT ٹنلز وصول کرتا ہے (`/etc/hosts` کے DNS ری ڈائریکٹ کے ذریعے)
- AgentBridge CA (`DATA_DIR/mitm/ca.crt`) سے دستخط شدہ فی-SNI TLS سرٹیفکیٹس تیار کرتا ہے
- `targets/index.ts` رجسٹری کے ذریعے Host ہیڈر کی بنیاد پر ہدف ایجنٹ کا تعین کرتا ہے
- HTTP کے ذریعے `http://127.0.0.1:20128` پر موجود TypeScript ہینڈلر پرت کو درخواست بھیجتا ہے

`TARGET_HOSTS` کو `DATA_DIR/mitm/targets.json` سے لوڈ کیا جاتا ہے (جسے بوٹ کے وقت `targets/index.ts` لکھتا ہے)، جس سے CJS سرور کو دوبارہ شروع کیے بغیر متحرک اپ ڈیٹس ممکن ہوتی ہیں۔

> **روٹ-CA ماڈل (#6684)۔** اوپر بیان کردہ CA سے دستخط شدہ فی-SNI سرٹیفکیٹ
> والا طریقہ #6684 میں شامل کیا گیا مستقل روٹ-CA ماڈل ہے (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`، جو `src/mitm/tproxy/dynamicCert.ts` میں TPROXY کے لیے
> پہلے سے ثابت شدہ CA/leaf کرپٹو کو دوبارہ استعمال کرتا ہے) — یہ پرانے واحد جامد
> خود دستخط شدہ leaf (`src/mitm/cert/generate.ts`، جو اب بھی صرف antigravity ہوسٹس تک
> محدود ہے) کی جگہ لیتا ہے، جس کی موجودگی ڈسک پر محض `server.crt`/`server.key`
> جوڑے سے ظاہر ہوتی ہے۔ **مائیگریشن کا طرزِ عمل**: ایک نئی انسٹالیشن (جہاں پہلے سے
> `server.crt` موجود نہ ہو) کو روٹ-CA ماڈل خودکار طور پر ملتا ہے؛ ایسی انسٹالیشن جو
> پہلے ہی پرانے جامد leaf پر اعتماد کرتی ہو، اسے اس وقت تک استعمال کرتی رہتی ہے جب تک
> آپریٹر `MITM_ROOT_CA_ENABLED=true` مقرر کرکے برج کو دوبارہ شروع نہ کرے
> (`src/mitm/cert/migration.ts` خالص فیصلہ کرنے والا فنکشن ہے — ایک قابلِ اعتماد MITM CA
> جو **کسی بھی** ہوسٹ کے لیے leaf پر دستخط کر سکتا ہو، پرانے مقررہ-SAN leaf سے نمایاں طور پر
> زیادہ طاقتور ہے، اس لیے پہلے سے قابلِ اعتماد انسٹالیشن میں تبدیلی کبھی خاموشی سے نہیں
> ہوتی)۔ CA سرٹیفکیٹ اسی `omniroute-mitm.crt` ٹرسٹ اسٹور سلاٹ میں انسٹال ہوتا ہے جسے
> پرانا leaf استعمال کرتا تھا (`cert/install.ts::installCaCert`) — دوہری ٹرسٹ کی صفائی
> کی ضرورت نہیں ہے۔

### 2.3 ہینڈلر بیس (`src/mitm/handlers/base.ts`)

تمام ایجنٹ ہینڈلرز `MitmHandlerBase` کو وسعت دیتے ہیں:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // محفوظ ہیلپرز: fetchRouter، pipeSSE، hookBufferStart، hookBufferUpdate
}
```

ہر ہینڈلر پراکسی کرنے سے پہلے `hookBufferStart()` اور مکمل ہونے پر `hookBufferUpdate()` کو کال کرتا ہے۔ یہ `InterceptedRequest` اندراجات کو `globalTrafficBuffer` میں پُش کرتے ہیں ([Traffic Inspector](./TRAFFIC_INSPECTOR.md) §4 دیکھیں)۔

### 2.4 اہداف کی رجسٹری (`src/mitm/targets/`)

ہر ایجنٹ کی ایک اعلانیہ ہدف فائل ہوتی ہے:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

رجسٹری (`targets/index.ts`) `ALL_TARGETS` کو ایکسپورٹ کرتی ہے اور بوٹ کے وقت `DATA_DIR/mitm/targets.json` تیار کرتی ہے۔

### 2.5 پاس تھرو اور بائی پاس فہرست (`src/mitm/passthrough.ts`)

**بائی پاس فہرست** (سب سے پہلے جانچی جاتی ہے اور ہدف سے مطابقت پر فوقیت رکھتی ہے):

- ڈیفالٹ پیٹرنز: بینکنگ ہوسٹس، `.gov.`، OAuth/SSO فراہم کنندگان (Okta، Auth0)، وغیرہ
- صارف کے پیٹرنز: DB ٹیبل `agent_bridge_bypass` میں محفوظ ہوتے ہیں
- بائی پاس کیے گئے ہوسٹس کو شفاف TCP ٹنل ملتا ہے — TLS کو **کبھی ڈکرپٹ نہیں کیا جاتا**

**ڈیفالٹ پاس تھرو** (ہدف سے کوئی مطابقت نہ ہو اور بائی پاس میں بھی نہ ہو):

- اسے بھی TCP ٹنل ملتا ہے — کنکشنز کبھی منقطع نہیں کیے جاتے
- AgentBridge کو عمومی سسٹم HTTPS ٹریفک میں خلل ڈالنے سے روکتا ہے

راؤٹنگ کی ترجیح:

```
بائی پاس فہرست → ہدف سے مطابقت → پاس تھرو
```

### 2.6 اپ اسٹریم CA سرٹیفکیٹ (`src/mitm/upstreamTrust.ts`)

حسبِ ضرورت CA والے کارپوریٹ نیٹ ورک ماحول کے لیے:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

مقرر ہونے پر، یہ اضافی CA سرٹیفکیٹ کے ساتھ `undici` کے عالمی ڈسپیچر کو کنفیگر کرتا ہے، جس سے AgentBridge کارپوریٹ TLS ٹرمینیشن پراکسیز کے ذریعے اپ اسٹریم فراہم کنندگان تک رسائی حاصل کر سکتا ہے۔

### 2.7 رازوں کی ماسکنگ (`src/mitm/maskSecrets.ts`)

خودمختار کلین روم اسکینر کو درخواست کی باڈیز اور اسناد والے ہیڈرز پر اس وقت **پہلے** لاگو کیا جاتا ہے جب وہ Traffic Inspector بفر یا کسی لاگ میں داخل ہوں۔ یہ ایک ہی خطی پاس انجام دیتا ہے:

- `sk-` / `ak-` / `pk-` سابقے والے ٹوکنز (OpenAI/Anthropic طرز)
- RFC 6750 کے `Authorization: Bearer <token>` اسناد، جہاں مکمل ٹوکن کو ترجیح حاصل ہے
- عمومی طویل مبہم ٹوکنز (≥40 حروف)، بشمول نقطوں اور پیڈنگ والی صورتیں

`sanitizeHeaders()` برقرار رکھے گئے ناموں کو چھوٹے حروف میں تبدیل کرتا ہے، ارے کی اقدار کو قطعی انداز میں جوڑتا ہے، مشترکہ hop-by-hop/framing ممنوعہ فہرست (بشمول پراکسی توثیق) کو خارج کرتا ہے، `cookie` اور `set-cookie` کو مکمل طور پر چھپاتا ہے، اور اسناد کی اقدار اسکینر کے سپرد کرتا ہے۔

| سرور بند کریں           | چائلڈ پراسیس کو بحفاظت بند کرتا ہے                                               |
| سرور دوبارہ شروع کریں   | بند + شروع کرتا ہے (ہدف کی تبدیلیاں لاگو ہو جاتی ہیں)                            |
| سرٹیفکیٹ پر اعتماد کریں | `DATA_DIR/mitm/ca.crt` کو OS ٹرسٹ اسٹور میں انسٹال کرتا ہے                       |
| سرٹیفکیٹ ڈاؤن لوڈ کریں  | دستی تنصیب کے لیے `ca.crt` ڈاؤن لوڈ کرتا ہے                                      |
| سرٹیفکیٹ دوبارہ بنائیں  | نیا CA کلیدی جوڑا بناتا ہے (تمام موجودہ فی ایجنٹ سرٹیفکیٹس غیر مؤثر ہو جاتے ہیں) |

### 3.2 سرٹیفکیٹ پر اعتماد کریں

IDE کی جانب سے MITM کنکشن قبول کیے جانے سے پہلے OS کو AgentBridge CA سرٹیفکیٹ پر اعتماد کرنا ضروری ہے۔

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

یا ڈیش بورڈ میں "سرٹیفکیٹ پر اعتماد کریں" بٹن استعمال کریں (یہ آپ کے OS کے لیے موزوں کمانڈ چلاتا ہے، اور ضرورت پڑنے پر sudo پرامپٹ دکھاتا ہے)۔

#### Electron پر مبنی IDEs، OS ٹرسٹ اسٹور کو نظر انداز کرتے ہیں (`NODE_EXTRA_CA_CERTS`)

کچھ IDEs — بالخصوص **Antigravity IDE**، اور دیگر Electron / VS Code سے اخذ کردہ ایپس — اپنا
Node.js رن ٹائم ساتھ شامل کرتے ہیں جو آؤٹ باؤنڈ `fetch`/HTTPS کے لیے **OS ٹرسٹ اسٹور سے رجوع نہیں کرتا**۔
OS/NSS سطح پر CA پر اعتماد کرنا IDE کے مقامی **بیک اینڈ** کے لیے کافی ہے
(مثلاً Go لینگویج سرور، جو OS CA بنڈل استعمال کرتا ہے)، لیکن **Electron فرنٹ اینڈ** میں
پھر بھی TLS ناکام ہو گا — یہ ایپ کے _لاگ آؤٹ_ دکھائی دینے یا _"کنکشن کی خرابی"_
دکھانے کی صورت میں ظاہر ہوتا ہے، حالاں کہ MITM لاگ بیک اینڈ کی بوٹ اسٹریپ کالز کو `200` واپس کرتے دکھاتا ہے۔ دو مراحل
درکار ہیں، اور دونوں اہم ہیں:

1. رن ٹائم کو واضح طور پر CA کی جانب متوجہ کریں:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **اسی شیل سے IDE لانچ کریں۔** اسے ڈیسک ٹاپ آئیکن / Dock / Start مینو سے شروع کرنے پر
   شیل ایکسپورٹس وراثت میں **نہیں** ملتیں، اور `~/.config/environment.d/*.conf` صرف
   نئے گرافیکل لاگ اِن کے بعد لاگو ہوتا ہے۔ پہلے IDE کو مکمل طور پر بند کریں — Electron کے سنگلٹن لاک کا مطلب ہے کہ دوسری بار
   لانچ کرنے سے صرف موجودہ پراسیس فوکس ہوتا ہے اور نئے ماحول کو نظر انداز کر دیا جاتا ہے۔

مندرجہ بالا OS ٹرسٹ + NSS مرحلہ پھر بھی ضروری ہے (کچھ تصدیقی
فلوز کے زیرِ استعمال Chromium نیٹ ورک اسٹیک فی صارف NSS اسٹور پڑھتا ہے، اور `*.googleapis.com` کے لیے اس کے اپنے جامد پنز ہوتے ہیں جنہیں
مقامی طور پر قابلِ اعتماد CA اوور رائیڈ کرتا ہے)۔ اس کے علاوہ `NODE_EXTRA_CA_CERTS`، Node کے `fetch` راستے کا احاطہ کرتا ہے۔

### 3.3 DNS روٹنگ

جس بھی ایجنٹ کو آپ انٹرسیپٹ کرنا چاہتے ہیں، اس کے API ہوسٹ یا ہوسٹس کا `127.0.0.1` پر ریزولو ہونا ضروری ہے۔ جب آپ Setup Wizard میں کسی ایجنٹ کے لیے DNS ٹوگل کرتے ہیں تو AgentBridge خودکار طور پر `/etc/hosts` اندراجات کا انتظام کرتا ہے۔

GitHub Copilot کے لیے `/etc/hosts` اندراجات کی مثال:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 ماڈل میپنگ

ماخذ → ہدف میپنگز متعین کرنے کے لیے ہر ایجنٹ کارڈ میں Model Mapping Table استعمال کریں:

| ماخذ ماڈل (ایجنٹ کا مقامی) | ہدف ماڈل (OmniRoute) |
| -------------------------- | -------------------- |
| `gpt-4o`                   | `claude-sonnet-4.7`  |
| `*` (وائلڈ کارڈ)           | `claude-haiku-4.7`   |

وائلڈ کارڈ `*` کسی بھی غیر شناخت شدہ ماڈل کو مخصوص ہدف سے میپ کرتا ہے۔ یہ `agent_bridge_mappings` ٹیبل میں محفوظ رہتا ہے۔

> **مشورہ — ایجنٹ کی اصل ماڈل IDs دریافت کریں۔** کوئی IDE ایسے ماڈل نام بھیج سکتا ہے جو
> اس کے UI لیبلز سے مختلف ہوں اور بڑے ورژنز کے درمیان تبدیل ہو جائیں۔ مثال کے طور پر **Antigravity 2** وائر پر
> `gemini-3.1-pro-low`، `gemini-pro-agent`، اور `gemini-3.1-flash-lite` بھیجتا ہے — نہ کہ
> پرانی دستاویزات میں دکھایا گیا `gemini-2.5-pro`۔ کسی مماثل میپنگ کے بغیر ایک چیٹ بھیجیں: MITM
> عین موصول ہونے والے `model:` کو لاگ کرتا ہے اور درخواست کو آگے گزار دیتا ہے۔ اسی لفظی قدر کو میپ کریں، پھر
> اگلی درخواست انٹرسیپٹ ہو کر آپ کے ہدف تک روٹ کر دی جائے گی۔

### 3.5 خطرے کا نوٹس

AgentBridge ان اسناد (OAuth ٹوکنز، API کلیدیں) کو انٹرسیپٹ کرتا ہے جنہیں IDE اپ اسٹریم فراہم کنندگان کے ساتھ تصدیق کے لیے استعمال کرتا ہے۔ لاگنگ سے پہلے انہیں **ماسک کر دیا جاتا ہے** (§2.7 دیکھیں)، لیکن یہ OmniRoute کی MITM تہہ کو نظر آتی ہیں۔ ہر ایجنٹ کو پہلی بار فعال کرنے پر ایک قابلِ برخاست خطرے کے نوٹس کا موڈل دکھایا جاتا ہے۔

### 3.6 دیکھ بھال اور تشخیص

ڈیش بورڈ ایک **Maintenance & Diagnostics** کارڈ (`AgentBridgeMaintenanceCard`، `src/app/(dashboard)/dashboard/tools/agent-bridge/components/` میں) فراہم کرتا ہے، جو ان عملیاتی MITM روٹس کو ظاہر کرتا ہے جن کے لیے پہلے کوئی UI نہیں تھا۔ اس کا ذیلی عنوان ہے: _"کیپچر پائپ لائن کا خودکار ٹیسٹ کریں، بچی ہوئی سسٹم حالت کو کالعدم کریں، اور اپنا سیٹ اپ مشینوں کے درمیان منتقل کریں۔"_ کارڈ کے کلائنٹ ہیلپرز `src/lib/inspector/agentBridgeMaintenanceApi.ts` میں موجود ہیں۔

| بٹن                  | روٹ                                    | یہ کیا کرتا ہے                                                                                                                                                                                                    |
| -------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **تشخیص**            | `GET /api/tools/agent-bridge/diagnose` | کیپچر پائپ لائن کا خودکار ٹیسٹ چلاتا ہے اور ہر جانچ کی رپورٹ دکھاتا ہے (✓/✗ + تدارک کا اشارہ)۔                                                                                                                    |
| **مرمت**             | `POST /api/tools/agent-bridge/repair`  | کریش یا SIGKILL کے باعث باقی رہ جانے والی MITM سسٹم حالت (DNS اسپوف اندراجات، روٹ CA، سسٹم پراکسی) کو ختم کرتا ہے۔ یہ عمل یکساں نتیجہ دینے والا ہے — حالت صاف ہونے پر "مرمت کے لیے کچھ نہیں ہے" کی اطلاع دیتا ہے۔ |
| **CA ہٹائیں**        | `DELETE /api/tools/agent-bridge/cert`  | OS ٹرسٹ اسٹور سے MITM روٹ CA کا اعتماد ختم کر کے اسے ہٹاتا ہے (واضح، یکساں نتیجہ دینے والا عمل)۔ صرف اس وقت دکھایا جاتا ہے جب CA فی الحال قابلِ اعتماد ہو؛ اس کے لیے اسی جگہ "CA ہٹائیں؟" کی تصدیق درکار ہوتی ہے۔ |
| **کنفیگ برآمد کریں** | `GET /api/tools/agent-bridge/config`   | قابلِ منتقلی کنفیگ JSON ڈاؤن لوڈ کرتا ہے (§3.7 دیکھیں)۔                                                                                                                                                           |
| **کنفیگ درآمد کریں** | `POST /api/tools/agent-bridge/config`  | پہلے برآمد کیا گیا کنفیگ JSON اپ لوڈ کرتا ہے (§3.7 دیکھیں)۔                                                                                                                                                       |

ہر ایجنٹ کارڈ میں اپنا **ڈیفالٹ بحال کریں** بٹن بھی ہوتا ہے (`POST
/api/tools/agent-bridge/agents/{id}/reset`) — ہر ایجنٹ کے لیے ایک کلک میں سابقہ حالت بحال کرنے کا عمل، جو صرف اس
ایجنٹ کے ہوسٹس کی اسپوفنگ ختم کرتا ہے، اس کی محفوظ کردہ ماڈل میپنگز صاف کرتا ہے، اور اس کی `dns_enabled`/`setup_completed`
حالت کو ری سیٹ کرتا ہے، تاکہ IDE مکمل طور پر دوبارہ شروع ہونے کے بعد حقیقی اپ اسٹریم سے دوبارہ رابطہ کرے۔ یہ
مشترکہ MITM سرور یا روٹ CA کو **متاثر نہیں** کرتا (ممکن ہے دوسرے ایجنٹس اب بھی ان پر منحصر ہوں) — ان تک
سرور کارڈ اور اوپر دیے گئے **CA ہٹائیں** عمل کے ذریعے رسائی برقرار رہتی ہے۔ Windows پر یہ حتی الامکان
`ipconfig /flushdns` بھی چلاتا ہے، کیونکہ Windows DNS Client ہوسٹس فائل کے اندراجات کیش کرتا ہے اور بصورتِ دیگر
ابھی ہٹائی گئی اسپوفنگ کو خارج نہیں کرتا۔

**تشخیصی جانچیں** (`summarizeDiagnostics()` در `src/mitm/inspector/diagnostics.ts`)۔ روٹ ہر جانچ کے لیے اثرانداز پروب چلاتا ہے اور بولین اقدار خالص خلاصہ ساز کو فراہم کرتا ہے؛ نتیجے میں ایک واحد `healthy` فیصلہ اور ہر ناکامی کے لیے ایک اشارہ واپس کیا جاتا ہے:

| جانچ کا نام        | یہ کس چیز کی تصدیق کرتی ہے                           | ناکامی پر اشارہ                                                                                                                                            |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server-running`   | MITM سرور پراسیس فعال ہے                             | "MITM سرور نہیں چل رہا۔ اسے AgentBridge ٹیب سے شروع کریں۔"                                                                                                 |
| `server-reachable` | MITM سرور اپنی پورٹ پر کنکشن قبول کرتا ہے (TCP پروب) | "MITM سرور اپنی پورٹ پر کنکشن قبول نہیں کر رہا۔ یقینی بنائیں کہ پورٹ خالی ہے اور اسے بائنڈ کرنے کے لیے آپ کے پاس مطلوبہ مراعات ہیں۔"                       |
| `cert-exists`      | MITM سرٹیفکیٹ ڈسک پر تیار کیا جا چکا ہے              | "ابھی تک کوئی MITM سرٹیفکیٹ تیار نہیں کیا گیا۔ AgentBridge ٹیب سے ایک سرٹیفکیٹ تیار کریں۔"                                                                 |
| `cert-trusted`     | MITM روٹ CA، OS ٹرسٹ اسٹور میں موجود ہے              | "MITM روٹ CA کو OS اسٹور قابلِ اعتماد نہیں سمجھتا، اس لیے TLS انٹرسیپشن ناکام ہو جائے گی۔ AgentBridge ٹیب سے سرٹیفکیٹ کو قابلِ اعتماد بنائیں۔"             |
| `dns-configured`   | ہدف ہوسٹ ناموں کو `/etc/hosts` میں اسپوف کیا گیا ہے  | "ہدف ہوسٹ نام `/etc/hosts` میں اسپوف نہیں کیے گئے، اس لیے ٹریفک کبھی پراکسی تک نہیں پہنچتی۔ جن ایجنٹس کو آپ کیپچر کرنا چاہتے ہیں ان کے لیے DNS فعال کریں۔" |

**باقی رہ جانے والی حالت کا بینر:** جب صفحہ کسی کریش کے باعث باقی رہ جانے والی حالت (DNS اسپوف / CA / سسٹم پراکسی) کا پتہ لگاتا ہے، تو کارڈ ایک عنبری بینر دکھاتا ہے — _"پچھلے سیشن نے سسٹم کی حالت باقی چھوڑ دی ہے (DNS اسپوف، CA، یا سسٹم پراکسی)۔ اسے صاف کرنے کے لیے مرمت چلائیں۔"_ — اور **مرمت** بٹن کو نمایاں کرتا ہے۔ `Repair`، ProxyBridge کے `--cleanup` فلیگ کا اطلاقی سطح پر مماثل عمل ہے (یہ `src/mitm/manager.ts` میں `repairMitm()` کو ذمہ داری سونپتا ہے)۔

> MITM روٹ CA کو بار بار sudo
> پرامپٹس سے بچنے کے لیے اسٹاپ/اسٹارٹ کے دوران انسٹال رکھا جاتا ہے (یہی طرزِ عمل mitmproxy/Charles کا بھی ہے)، اس لیے اسے ہٹانا ایک واضح
> **CA ہٹائیں** عمل ہے، نہ کہ کوئی ایسا عمل جو رکنے پر خودکار طور پر انجام پائے۔

### 3.7 قابلِ منتقلی کنفیگ کی درآمد/برآمد

AgentBridge، **آپریٹر کی جانب سے قابلِ ترتیب** حالت کو ورژن شدہ JSON بلاک میں سیریلائز کر سکتا ہے، تاکہ کسی سیٹ اپ کو متعدد مشینوں پر نقل کیا جا سکے۔ سیریلائزر `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`) ہے، جس کی توثیق `AgentBridgeConfigSchema` کرتا ہے۔

برآمد میں عین تین اجزا شامل ہوتے ہیں (بلٹ اِن ڈیفالٹس جان بوجھ کر برآمد **نہیں** کیے جاتے، تاکہ درآمد کبھی انہیں نقل نہ کرے یا ان سے متصادم نہ ہو):

| فیلڈ             | ماخذ                                                       | نوٹس                                                                    |
| ---------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------- |
| `bypassPatterns` | صارف کی متعین کردہ بائی پاس پیٹرنز (`agent_bridge_bypass`) | ڈیفالٹ bank/gov/okta پیٹرنز شامل نہیں کیے جاتے                          |
| `customHosts`    | Traffic Inspector کے کسٹم ہوسٹس (`inspector_custom_hosts`) | ہر ایک: `{ host, kind: "llm"\|"app"\|"custom", label? }`                |
| `agentMappings`  | ہر ایجنٹ کے لیے ماڈل میپنگز (`agent_bridge_mappings`)      | میپنگز رکھنے والے ہر ایجنٹ کے لیے `{ [agentId]: [{ source, target }] }` |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**درآمد کا طرزِ عمل** (`POST /api/tools/agent-bridge/config`): بائی پاس پیٹرنز اور ہر ایجنٹ کی میپنگز کو **مکمل طور پر تبدیل** کر دیا جاتا ہے؛ کسٹم ہوسٹس **بلا تکرار** شامل کیے جاتے ہیں (`INSERT OR IGNORE`)۔ جواب میں بتایا جاتا ہے کہ ہر قسم میں سے کتنے لاگو کیے گئے:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

کنفگ میں کیا **شامل نہیں ہے**: سرور کے چلنے کی حالت، سرٹیفکیٹ پاتھز، ہر ایجنٹ کی DNS حالت، اپ اسٹریم CA پاتھ، اور TPROXY سیٹنگز — یہ ہوسٹ/رن ٹائم کی حالت ہیں، قابلِ منتقلی ترجیحات نہیں۔

### سیٹ اپ وزارڈ کے مراحل (فی ایجنٹ)

export async function detectAgent(agentId: AgentId): Promise<DetectionResult>;

دریافت میں OS کے لیے مخصوص راستے اور بائنری جانچ استعمال ہوتی ہے (مثلاً Copilot کے لیے `code --list-extensions | grep github.copilot`، اور Antigravity کے لیے `~/.config/antigravity/`)۔

### حساس ہوسٹس کے لیے بائی پاس فہرست

بائی پاس فہرست یقینی بناتی ہے کہ مالیاتی اداروں، OAuth/SSO فراہم کنندگان، اور دیگر حساس ہوسٹس کو **کبھی ڈی کرپٹ نہ کیا جائے**۔ ان کی TLS ٹریفک ایک شفاف TCP ٹنل کے طور پر گزرتی ہے — OmniRoute کبھی سادہ متن نہیں دیکھتا۔

ڈیفالٹ بائی پاس پیٹرنز میں شامل ہیں:

- `*.bank.*`، `*.gov.*` (مالیاتی/سرکاری)
- `*.okta.com`، `*.auth0.com`، `*.microsoft.com` (SSO/شناخت)
- `*.apple.com`، `*.icloud.com` (Apple سسٹم سروسز)

صارف کے شامل کردہ بائی پاس پیٹرنز `agent_bridge_bypass` جدول میں محفوظ ہوتے ہیں اور ہر چیز پر فوقیت رکھتے ہیں۔

### رازوں کی ماسکنگ

`src/mitm/maskSecrets.ts` سے `maskSecrets()` کا اطلاق ہوتا ہے:

- `TrafficBuffer.push()` سے پہلے ہر درخواست کی باڈی پر
- لاگ کرنے یا براڈکاسٹ کرنے سے پہلے ہر ہیڈر پر

پیٹرنز: `sk-`/`ak-`/`pk-` سابقے والے ٹوکنز، `Bearer` ٹوکنز، اور کم از کم 40 حروف پر مشتمل عمومی ٹوکنز۔

### اپ اسٹریم CA سرٹیفکیٹ

جب `AGENTBRIDGE_UPSTREAM_CA_CERT` سیٹ ہو، تو فائل کو آغاز کے وقت پڑھا جاتا ہے۔ اگر راستہ موجود ہو لیکن فائل قابلِ مطالعہ نہ ہو، تو AgentBridge ایک واضح خرابی لاگ کرتا ہے اور شروع ہونے سے انکار کر دیتا ہے (کارپوریٹ ماحول میں خاموش TLS ناکامیوں کو روکتا ہے)۔

### معلوم حدود

- **پورٹ 443 کے لیے استحقاق درکار ہے**: Linux پر، AgentBridge کو Node بائنری پر `setcap 'cap_net_bind_service=+ep'` درکار ہے، یا اسے `authbind` کے ذریعے چلائیں۔ سیٹ اپ وزارڈ OS کے لیے مخصوص ہدایات دکھاتا ہے۔
- **IDE کو دوبارہ شروع کرنا ضروری ہے**: DNS ری ڈائریکٹ کے بعد، نئی ہوسٹ ریزولیوشن مؤثر بنانے کے لیے IDE کو دوبارہ شروع کرنا ضروری ہے۔
- **ہارڈ کوڈ شدہ OAuth ٹوکنز**: کچھ ایجنٹس (Kiro، Antigravity) OAuth ریفریش ٹوکنز مقامی طور پر محفوظ کرتے ہیں۔ یہ AgentBridge کے لیے شفاف ہوتے ہیں — اسے ہر درخواست میں Bearer ٹوکن نظر آتا ہے، جسے لاگ کرنے سے پہلے ماسک کر دیا جاتا ہے۔
- **Electron فرنٹ اینڈز کو `NODE_EXTRA_CA_CERTS` درکار ہے**: وہ IDEs جن کا فرنٹ اینڈ بنڈل شدہ Node/Electron رن ٹائم پر چلتا ہے، OS/NSS ٹرسٹ اسٹور کو نظر انداز کرتے ہیں اور انہیں ایسے شیل سے لانچ کرنا ضروری ہے جس میں `NODE_EXTRA_CA_CERTS` سیٹ ہو (§3.2 دیکھیں)۔ اس کے نہ ہونے کی علامت: IDE بیک اینڈ تصدیق کر لیتا ہے (MITM میں `200` دکھائی دیتے ہیں) لیکن UI لاگ آؤٹ ہی رہتا ہے۔
- **ایک ہی IDE کی متعدد تنصیبات آزاد ہوتی ہیں**: سسٹم تنصیب (مثلاً `/usr/share/antigravity/antigravity`) اور صارف کی مقامی "Full" تنصیب (مثلاً `~/AntigravityIDE_Full/antigravity-ide`) اپنے الگ رن ٹائمز کے ساتھ الگ پراسیسز ہیں — ہر ایک کو CA انجیکٹ کر کے دوبارہ لانچ کرنا ضروری ہے۔ دوبارہ لانچ کرنے سے پہلے اس کے بائنری راستے سے شناخت کریں کہ کون سی تنصیب چل رہی ہے۔
- **شناخت روٹ کیے گئے ماڈل سے نہیں بلکہ ایجنٹ کے سسٹم پرامپٹ سے متعین ہوتی ہے**: جب آپ کسی ایجنٹ کے ماڈل کو کسی مختلف فراہم کنندہ پر دوبارہ میپ کرتے ہیں، تب بھی جواب ایجنٹ کی مقامی شناخت کا دعویٰ کرتا ہے (مثلاً Antigravity جواب دیتا ہے "مجھے Gemini تقویت دیتا ہے") کیونکہ IDE اسے سسٹم پرامپٹ میں شامل کرتا ہے۔ اصل بیک اینڈ کی تصدیق ماڈل سے اس کی شناخت پوچھ کر نہیں بلکہ `call_logs` / `proxy_logs` (`provider`، `model`، `target_format`) میں کریں۔

## §6 مسائل کا ازالہ

### پورٹ 443 کا ٹکراؤ

اگر کوئی دوسرا پراسیس پہلے ہی پورٹ 443 پر سن رہا ہو (ویب سرور، VPN، وغیرہ):

```bash
lsof -i :443          # پراسیس تلاش کریں
sudo fuser -k 443/tcp  # زبردستی بند کریں (احتیاط سے استعمال کریں)
```

متبادل طور پر، AgentBridge کی ترتیبات میں ایک غیر مراعات یافتہ پورٹ ترتیب دیں اور `iptables` / `pf` ری ڈائریکٹ قواعد قائم کریں۔

### سرٹیفکیٹ قابلِ اعتماد نہیں ہے

اگر AgentBridge شروع کرنے کے بعد IDE میں TLS کی خرابیاں دکھائی دیں:

1. تصدیق کریں کہ سرٹیفکیٹ انسٹال ہو چکا ہے: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) یا `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. کچھ ایپس اپنا الگ ٹرسٹ اسٹور برقرار رکھتی ہیں (Firefox، Linux پر Chrome)۔ "Trust Cert" دوبارہ چلائیں اور NSS/Firefox کے مخصوص سرٹیفکیٹ اسٹور کی جانچ کریں۔
3. اعتماد قائم کرنے کے بعد IDE دوبارہ شروع کریں — پہلے سے جاری TLS سیشنز اعتماد کی پرانی حالت استعمال کرتے ہیں۔

### قابلِ اعتماد CA کے باوجود IDE لاگ آؤٹ / "connection error"

علامت: DNS ری ڈائریکٹ کرنے اور CA پر اعتماد قائم کرنے کے بعد، Electron پر مبنی IDE (مثلاً Antigravity)
**لاگ آؤٹ شدہ** حالت میں کھلتا ہے یا توثیق/کنکشن کی خرابی دکھاتا ہے، حالانکہ MITM لاگ میں
بوٹسٹریپ کالز (`loadCodeAssist`، `fetchAvailableModels`، …) کو `200` واپس کرتے ہوئے دکھایا جاتا ہے۔

وجہ: IDE کا **بنڈل شدہ Node/Electron رن ٹائم OS کے ٹرسٹ اسٹور کو نظر انداز کرتا ہے**۔ مقامی
بیک اینڈ (ایک Go لینگویج سرور) OS کے CA پر اعتماد کرتا ہے اور توثیق کر لیتا ہے، لیکن Electron فرنٹ اینڈ
ایسا نہیں کرتا — اس لیے UI سمجھتا ہے کہ وہ آف لائن ہے۔

حل (دونوں مراحل): `NODE_EXTRA_CA_CERTS=<ca.crt>` ایکسپورٹ کریں **اور اسی
شیل سے IDE دوبارہ لانچ کریں**، ڈیسک ٹاپ آئیکن سے نہیں۔ پہلے IDE کو مکمل طور پر بند کریں — Electron کے سنگلٹن لاک کا مطلب ہے کہ
دوسری بار لانچ کرنے سے صرف موجودہ پراسیس فوکس ہوتا ہے اور نیا ماحول نظر انداز کر دیا جاتا ہے۔ §3.2 دیکھیں۔
یہ ایک کھلی اپ اسٹریم رپورٹ سے مطابقت رکھتا ہے، جہاں ایک اسٹینڈ الون ایجنٹ MITM کے ذریعے کام کرتا ہے لیکن IDE
ویریئنٹ اسی سیٹ اپ کے تحت ناکام ہو جاتا ہے۔

### DNS کی تبدیلیاں نافذ نہیں ہوئیں

جانچ کریں کہ `/etc/hosts` اپ ڈیٹ ہوا ہے:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

DNS کیش صاف کریں:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE کا پتہ نہیں چلا

خودکار شناخت عام انسٹالیشن پاتھ استعمال کرتی ہے۔ اگر شناخت ناکام ہو جائے لیکن IDE انسٹال ہو:

- جانچ کریں کہ آیا IDE بائنری کسی غیر معیاری مقام پر ہے
- Setup Wizard پھر بھی کام کرتا ہے — شناخت کی ناکامی کا صرف یہ مطلب ہے کہ بیج انسٹالیشن پاتھ نہیں دکھائے گا

### ہینڈلر کی خرابیاں (اپ اسٹریم فیچ ناکام)

اگر AgentBridge انٹرسیپٹ تو کرتا ہے لیکن تمام درخواستیں ناکام ہو جاتی ہیں:

1. تصدیق کریں کہ `/dashboard/providers` پر کم از کم ایک پرووائیڈر منسلک ہے
2. OmniRoute سرور لاگز کی جانچ کریں: `.env` میں `APP_LOG_LEVEL=debug`
3. تصدیق کریں کہ `OMNIROUTE_BASE_URL` درست روٹر اینڈ پوائنٹ کی طرف اشارہ کرتا ہے (ڈیفالٹ: `http://127.0.0.1:20128`)

## §8 روڈ میپ

### Trae کی تحقیقات

Trae نسبتاً نیا AI کوڈنگ اسسٹنٹ ہے۔ ہینڈلر نافذ کرنے سے پہلے:

1. VS Code / JetBrains مارکیٹ پلیسز یا اسٹینڈ الون ایپ میں بائنری/ایکسٹینشن کی شناخت کریں
2. API ہوسٹس اور اینڈ پوائنٹس کی ساخت دریافت کرنے کے لیے mitmproxy کے ذریعے ٹریفک کیپچر کریں
3. توثیق کے طریقۂ کار کا تعین کریں
4. شرائطِ خدمت اور API کی قابلِ دریافت ہونے کی بنیاد پر آگے بڑھنے یا نہ بڑھنے کا جائزہ لیں

تحقیقات مکمل ہونے تک، ڈیش بورڈ میں Trae کارڈ پر "زیرِ تحقیق" بیج اور "قابلِ عمل ہونے کی رپورٹ دیں" لنک دکھائی دیتا ہے۔ `src/mitm/handlers/trae.ts` میں موجود ہینڈلر اسٹب ایک منظم `ابھی نافذ نہیں کیا گیا` خرابی پھینکتا ہے۔

### بیک لاگ ایجنٹس (MITM درکار ہے — حسبِ ضرورت بنیادی URL کی معاونت موجود نہیں)

درج ذیل ٹولز کے موجودہ ورژنز حسبِ ضرورت بنیادی URLs کی معاونت نہیں کرتے، جس کی وجہ سے MITM مداخلت کا واحد راستہ ہے۔ قابلِ عمل ہونے کا جائزہ ابھی زیرِ التوا ہے:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — Kiro IDE سے الگ)
- **Cowork** (Anthropic ڈیسک ٹاپ)

نوٹ: GitHub Copilot CLI ≥v1.0.19، `COPILOT_PROVIDER_BASE_URL` کی معاونت کرتا ہے — اس ٹول کے لیے MITM کی بجائے براہِ راست کنفیگریشن استعمال کریں۔
