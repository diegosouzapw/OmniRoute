> **خلاصہ**: `open-sse/` بنیادی اسٹریمنگ انجن ہے جو OmniRoute میں ہر LLM درخواست کو چلاتا ہے۔ اس میں تقریباً 1,400 فائلیں ہیں جو درخواست پائپ لائن، ایگزیکیوٹرز، سروسز، MCP سرور، اور ترجمے کی تہہ کو نافذ کرتی ہیں۔ یہ رہنما وضاحت کرتا ہے کہ یہ اجزا کس طرح باہم مربوط ہیں۔

**ماخذ:** `open-sse/` (ورک اسپیس پیکیج، تقریباً 1,440 غیر ٹیسٹ `.ts` فائلیں)

## ایک علیحدہ ورک اسپیس پیکیج کیوں؟

`open-sse/` کئی وجوہات کی بنا پر OmniRoute monorepo کے اندر ایک **خود مختار ورک اسپیس** ہے:

1. **دوبارہ استعمال کی صلاحیت** — `open-sse` کو npm پر `@omniroute/open-sse` کے طور پر شائع کیا جاتا ہے، لہٰذا دوسرے پروجیکٹس اسے آزادانہ طور پر استعمال کر سکتے ہیں
2. **واضح حدود** — اسٹریمنگ انجن کو OmniRoute کی مخصوص UI/DB تہہ سے الگ رکھا گیا ہے
3. **کارکردگی** — انجن کا Next.js پر کوئی انحصار نہیں، جس سے CLI/serverless سیاق و سباق میں کولڈ اسٹارٹس زیادہ تیز ہوتے ہیں
4. **ورژننگ** — `open-sse` اپنے شیڈول کے مطابق ریلیز ہو سکتا ہے

```json
// package.json
"workspaces": ["open-sse"]
```

## درخواست پائپ لائن

ہر LLM درخواست ایک **5 مراحل پر مشتمل پائپ لائن** سے گزرتی ہے:

```
                              ┌──────────────┐
   HTTP درخواست               │  1. روٹنگ    │   combo ریزولیوشن، ماڈل کا انتخاب
   (Next.js روٹ)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. ترجمہ    │   فارمیٹ کی تبدیلی (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. نفاذ     │   پرووائیڈر ایگزیکیوٹر، HTTP، دوبارہ کوشش، بریکر
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. اسٹریم   │   SSE ٹرانسفارمیشن، بیک پریشر
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ریکارڈ   │   استعمال کی ٹریکنگ، کال لاگ، خرابی کی درجہ بندی
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP جواب (SSE یا JSON)
```

### مرحلہ 1: روٹنگ (services/combo.ts)

**داخلی نقطہ**: `services/combo.ts` میں `handleComboChat()`

درخواست کو ایک واضح `(provider, model, account, credentials)` ٹیپل سے منسلک کرتا ہے:

- ID کے ذریعے combo تلاش کریں (یا `auto/*` ماڈلز کے لیے ایک ورچوئل combo بنائیں)
- روٹنگ حکمت عملی لاگو کریں (ترجیح، وزنی، راؤنڈ رابن، وغیرہ)
- غیر صحت مند پرووائیڈرز کو خارج کریں (سرکٹ بریکر)
- اگلا قابل عمل ہدف منتخب کریں

`auto/*` ماڈلز کے لیے، یہ مرحلہ یہ کام بھی کرتا ہے:

- **16 عوامل پر مبنی اسکورنگ** الگورتھم چلاتا ہے (`services/autoCombo/`)
- صحت، لاگت، تاخیر، وغیرہ کی بنیاد پر ایک `provider+model` جوڑا منتخب کرتا ہے

### مرحلہ 2: ترجمہ (translator/)

اگر ماخذ فارمیٹ (مثلاً OpenAI) ہدف فارمیٹ (مثلاً Claude) سے مختلف ہو تو درخواست کا **ترجمہ** کیا جاتا ہے:

- سسٹم پرامپٹ → سسٹم پیغام
- ٹول کی تعریفیں → پرووائیڈر کے لیے مخصوص ٹول فارمیٹ
- استدلال/تفکر کے پیرامیٹرز → پرووائیڈر کے لیے مخصوص متبادلات
- پیغام کے کرداروں کو معمول پر لانا (غیر OpenAI کے لیے `developer` → `system`)

`translator/index.ts` یہ فراہم کرتا ہے:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### مرحلہ 3: نفاذ (executors/)

**داخلی نقطہ**: `getExecutor(providerId).execute(request, options)`

تمام پرووائیڈرز `getExecutor()` فیکٹری فال بیک کے ذریعے `DefaultExecutor` (`executors/default.ts`) استعمال کرتے ہیں۔ ایگزیکیوٹر:

- اپ اسٹریم URL بناتا ہے (`buildUrl()`)
- پرووائیڈر کے لیے مخصوص ہیڈرز شامل کرتا ہے (`buildHeaders()`)
- درخواست کی باڈی کو تبدیل کرتا ہے (`transformRequest()`)
- دوبارہ کوشش اور ایکسپونینشل بیک آف کے ساتھ HTTP درخواست بھیجتا ہے
- ضرورت پڑنے پر تصدیقی معلومات ریفریش کرتا ہے (OAuth پرووائیڈرز)

تمام ایگزیکیوٹرز `BaseExecutor` (`executors/base.ts`، 1170 LOC) کو توسیع دیتے ہیں، جو یہ سہولیات فراہم کرتا ہے:

- دوبارہ کوشش کی مشترکہ منطق
- پراکسی انضمام
- سرکٹ بریکر انضمام
- استعمال ریکارڈ کرنے کے ہکس

### مرحلہ 4: اسٹریم (utils/stream.ts)

اسٹریمنگ جوابات کے لیے، ایگزیکیوٹر ایک **ReadableStream** واپس کرتا ہے۔ ہینڈلر:

- SSE ٹرانسفارم سے گزارتا ہے (`createSSETransformStreamWithLogger`)
- غیر فعال کنکشنز کا پتا لگانے کے لیے ہارٹ بیٹ پنگز لاگو کرتا ہے
- کلائنٹ کے منقطع ہونے کو بخوبی سنبھالتا ہے (`pipeWithDisconnect`)
- غیر اسٹریمنگ کلائنٹس کے لیے SSE → JSON تبدیل کرتا ہے

غیر اسٹریمنگ جوابات کے لیے، ایگزیکیوٹر پارس کیا ہوا JSON آبجیکٹ واپس کرتا ہے، جسے بغیر تبدیلی کے آگے بھیج دیا جاتا ہے۔

### مرحلہ 5: ریکارڈنگ (services/usage.ts)

جواب (کامیابی یا ناکامی) کے بعد، استعمال کا ریکارڈ درج کیا جاتا ہے:

- جواب سے `prompt_tokens`، `completion_tokens`، `cached_tokens`
- قیمتوں کے ڈیٹا سے شمار کردہ `cost_usd`
- ناکامی کی صورت میں `latency_ms`، `status`، `error_class`
- `usage_history` ٹیبل میں محفوظ کیا جاتا ہے

کال لاگ کے نمونے (اگر فعال ہوں) `${DATA_DIR}/call_logs/` میں لکھے جاتے ہیں۔

## اہم فائلوں کا تفصیلی جائزہ

### chatCore.ts (5977 لائنیں)

**مرکزی درخواست ہینڈلر**۔ اپنے حجم کے باوجود، اس کی ساخت واضح ہے:

```ts
// chatCore.ts کی نمائندہ ساخت
export async function handleChat(request: NextRequest) {
  // 1. توثیق + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. باڈی کی توثیق
  const body = await parseRequestBody(request);

  // 3. فارمیٹ کی شناخت + ترجمہ
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. کومبو روٹنگ
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // اگلے ہدف پر جائیں
    }
  }

  // 5. ہنگامی متبادل راستہ
  return await emergencyFallback(body);
}
```

اگرچہ یہ ایک بہت بڑا فنکشن ہے، یہ **تبصروں والے حصوں** میں منظم ہے جو 5 مراحل کی پائپ لائن سے مطابقت رکھتے ہیں۔

### combo.ts (4456 LOC)

**روٹنگ انجن** جو کومبو کو ترتیب شدہ اہداف میں حل کرتا ہے۔

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

| `fusion`            | متوازی طور پر پینل پر تقسیم، پھر جج کے ذریعے یکجا کرنا (`fusion.ts`)             |
| `pipeline`          | مراحل کی زنجیر — ہر ہدف کا آؤٹ پٹ اگلے کو دیا جاتا ہے                            |

### base.ts (1170 LOC)

**تجریدی ایگزیکیوٹر** جسے ہر ایگزیکیوٹر کلاس بڑھاتی ہے (براہ راست یا `DefaultExecutor` اور دیگر ذیلی کلاسوں کے ذریعے)۔ اس میں شامل ہے:

- `buildUrl()` — پہلے سے طے شدہ URL کی تعمیر (ذیلی کلاسیں حسب ضرورت اسے تبدیل کرتی ہیں)
- `buildHeaders()` — پہلے سے طے شدہ ہیڈرز (توثیق، content-type)
- `transformRequest()` — پہلے سے طے شدہ طور پر بلا تبدیلی منتقل
- `execute()` — دوبارہ کوشش/بیک آف/بریکر کے ساتھ مرکزی HTTP لوپ

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // تمام OpenAI/Anthropic سے مطابقت رکھنے والے فراہم کنندگان کو ہینڈل کرتا ہے
  // فراہم کنندگان کنفیگریشنز (URL، توثیق، ہیڈرز) رجسٹر کرتے ہیں لیکن ایگزیکیوٹر منطق مشترک ہوتی ہے
}
```

فراہم کنندہ کے مخصوص طرز عمل (توثیقی ہیڈرز، بنیادی URL، ورژن ہیڈرز) کو الگ ایگزیکیوٹر کلاسوں کے بجائے فراہم کنندہ رجسٹری کے ذریعے کنفیگر کیا جاتا ہے।

## ایگزیکیوٹرز (150 ماڈیولز)

زیادہ تر فی فراہم کنندہ ایک فائل ہے۔ تمام ایگزیکیوٹر کلاسز `BaseExecutor` کو ایکسٹینڈ کرتی ہیں اور جو چیز مختلف ہو اسے اووررائیڈ کرتی ہیں؛ دیگر ماڈیولز فی فراہم کنندہ معاون ہیں (ٹول اسکیماز، fetch/TTS اڈاپٹرز، خصوصیت ہینڈلرز)۔

### عام پیٹرنز

فراہم کنندگان کو `getExecutor(providerId)` کے ذریعے ریزولو کیا جاتا ہے، جو کنفیگر شدہ ایگزیکیوٹر لوٹاتا ہے۔ OpenAI/Anthropic سے مطابقت رکھنے والے فراہم کنندگان `DefaultExecutor` (`executors/default.ts`) استعمال کرتے ہیں۔ فراہم کنندہ کے مخصوص رویّے (بیس URL، توثیقی ہیڈرز، API ورژن) کو `open-sse/config/providers/` میں کنفیگر کیا جاتا ہے، جبکہ درخواست کے باڈی کی تبدیلیاں `open-sse/translator/` میں سنبھالی جاتی ہیں۔

**حسبِ ضرورت URL** فراہم کنندہ کی کنفیگریشن کے ذریعے سیٹ کیا جاتا ہے:

```ts
// فراہم کنندہ کنفیگریشن open-sse/config/providers/ میں
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**حسبِ ضرورت توثیق** فراہم کنندہ رجسٹری کی توثیقی کنفیگریشن (API کلید، OAuth، ہیڈر پروفائلز) کے ذریعے سنبھالی جاتی ہے۔

**حسبِ ضرورت درخواست باڈی** کی تبدیلیاں (مثلاً Anthropic کا `system` کو `messages` سے الگ کرنا) فی فراہم کنندہ `open-sse/translator/` میں رجسٹر کی جاتی ہیں۔

````

### ایگزیکیوٹر فیکٹری

`executors/index.ts` سے `getExecutor(providerId)` ایکسپورٹ کیا جاتا ہے:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

ریزولوشن `ExecutorRegistry` (`executors/registry.ts`) سے گزرتی ہے: ہر مخصوص ایگزیکیوٹر `executors/index.ts` کی بلٹ اِن جدول میں بیان کیا گیا ہے اور ماڈیول لوڈ کے وقت `registerExecutor(alias, instance)` کے ذریعے رجسٹر ہوتا ہے؛ `getExecutor()` رجسٹری سے رجوع کرتا ہے اور جس فراہم کنندہ کے لیے مخصوص اندراج موجود نہ ہو وہاں میموائزڈ `DefaultExecutor` پر واپس جاتا ہے۔ مکمل alias → executor میپنگ کی خصوصیت گولڈن ٹیسٹ `tests/unit/executor-map-golden.test.ts` سے بیان ہوتی ہے۔

## مترجمین

**3 فارمیٹس** کے درمیان ترجمہ کریں: OpenAI، Anthropic، Gemini، نیز نیا Responses API۔

### ترجمہ کب ہوتا ہے

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

عام تراجم:

- `OpenAI → Anthropic`: علیحدہ `system` فیلڈ، `x-api-key` ہیڈر
- `OpenAI → Gemini`: `messages` کی بجائے `contents`، `systemInstruction`
- `OpenAI → Responses API`: `input` ارے، `previous_response_id` اسٹیٹ

### سنبھالے گئے خصوصی حالات

- `developer` رول → غیر OpenAI کے لیے `system`
- `system` رول → GLM/ERNIE کے لیے پہلے صارف کے پیغام میں ضم کیا جاتا ہے
- `json_schema` → Gemini کا `responseMimeType` + `responseSchema`
- `tools` → فراہم کنندہ کے لیے مخصوص ٹول فارمیٹ
- تھنکنگ پیرامیٹرز (o1، Claude) → فراہم کنندہ کے لیے مخصوص متبادلات

## MCP سرور

`open-sse/mcp-server/`، **Model Context Protocol** سرور نافذ کرتا ہے:

- **110 ٹولز** (فراہم کنندہ مینجمنٹ، کمبوز، میموری، کیش، کمپریشن، پراکسی، اسکلز، گیمیفیکیشن، پلگ انز، Notion، Obsidian، مقامی کارپس)
- **3 ٹرانسپورٹس**: stdio، SSE، Streamable HTTP
- باریک سطح کی اجازت دہی کے لیے **33 اسکوپس**

### ٹول رجسٹریشن

ٹولز کو `open-sse/mcp-server/tools/` میں علیحدہ فائلوں کے طور پر رجسٹر کیا جاتا ہے، جن میں سے ہر ایک نام، اسکیما، ہینڈلر اور اسکوپ ایکسپورٹ کرتی ہے:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### ٹرانسپورٹس

```ts
// stdio (CLI استعمال)
startMcpStdio(server);

// SSE (HTTP پر مبنی اسٹریمنگ)
startMcpSse(server, port);

// Streamable HTTP (جدید MCP)
startMcpStreamable(server, port);
```

### اجازت دہی

ہر ٹول کال اسکوپ چیکس (`open-sse/mcp-server/auth/`) سے گزرتی ہے:

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## ٹرانسفارمرز

`open-sse/transformer/`، **Chat Completions** اور **Responses API** فارمیٹس کے درمیان تبدیلی کرتا ہے۔

### علیحدہ ٹرانسفارمر کیوں؟

Responses API، OpenAI کا نیا فارمیٹ ہے جس میں **حالت برقرار رکھنے والی گفتگوئیں** (`previous_response_id`) شامل ہیں۔ جب کوئی کلائنٹ Responses درخواست بھیجتا ہے، تو OmniRoute:

1. اندرونی طور پر Responses → Chat Completions میں تبدیل کرتا ہے
2. فراہم کنندہ کو بھیجتا ہے (کوئی بھی فراہم کنندہ جو Chat Completions کو سپورٹ کرتا ہو)
3. جواب کو واپس Responses فارمیٹ میں تبدیل کرتا ہے
4. تبدیل شدہ جواب کو کلائنٹ تک اسٹریم کرتا ہے

ٹرانسفارمر (`transformer/responsesTransformer.ts`) یہ فراہم کرتا ہے:

```ts
createResponsesApiTransformStream(): TransformStream
```

یہ درج ذیل کو سنبھالتا ہے:

- `response.output_item.added` ایونٹس
- `response.output_text.delta` ایونٹس
- `response.completed` ایونٹ
- ٹول کال میپنگ (`function_call` ↔ `tool_calls`)

## نامناسب طریقے

❌ **`combo.ts` میں سنکرونس DB کالز** — پہلے سے کمپیوٹ کرکے کیش کریں

❌ **ہم وقت درخواستوں کے درمیان اسٹیٹ میں تبدیلیاں** — صرف درخواست کے دائرۂ کار کا کانٹیکسٹ استعمال کریں

## نیا کمپوننٹ شامل کرنا

### نئی سروس شامل کرنا

1. مخصوص ذمہ داری کے ساتھ `open-sse/services/[serviceName].ts` بنائیں
2. مرکزی ہینڈلر فنکشن اور تمام مستقل اقدار ایکسپورٹ کریں
3. `tests/unit/services/[serviceName].test.mjs` میں یونٹ ٹیسٹس شامل کریں
4. درخواست پائپ لائن میں `handlers/chatCore.ts` کے اندر انٹیگریٹ کریں (اگر راؤٹنگ سے متعلق ہو)
5. اگر سروس ہدف کے انتخاب کو متاثر کرتی ہے تو `combo.ts` میں راؤٹنگ منطق اپ ڈیٹ کریں
6. اس فائل میں دستاویز کریں

### نیا ایگزیکیوٹر شامل کرنا

1. `BaseExecutor` کو ایکسٹینڈ کرتے ہوئے `open-sse/executors/[provider].ts` بنائیں
2. `config/providerRegistry.ts` میں رجسٹر کریں
3. `executors/index.ts` فیکٹری میں شامل کریں
4. ایگزیکیوٹر کے لیے یونٹ ٹیسٹس شامل کریں
5. `docs/architecture/ARCHITECTURE.md` میں دستاویز کریں

### نیا MCP ٹول شامل کرنا

1. `open-sse/mcp-server/tools/[category]Tools.ts` بنائیں یا اپ ڈیٹ کریں
2. اِن پٹس کے لیے Zod اسکیما متعین کریں
3. ٹول کو `mcp-server/index.ts` میں رجسٹر کریں
4. `mcp-server/auth/` میں اسکوپ میٹرکس میں شامل کریں
5. یونٹ ٹیسٹس شامل کریں
