## فوری حوالہ

**OmniRoute پر نئے ہیں؟** یہاں سے شروع کریں — یہ 90% مسائل حل کر دیتے ہیں:

| مجھے یہ نظر آتا ہے            | اس کا مطلب کیا ہے                              | کیا کرنا ہے                                                                                                           |
| ----------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| "کنیکٹ نہیں ہو سکتا"          | OmniRoute چل نہیں رہا                          | `omniroute` چلائیں یا `docker restart omniroute` استعمال کریں                                                         |
| "غلط API کلید"                | آپ کی کلید غلط ہے یا اس کی میعاد ختم ہو چکی ہے | فراہم کنندہ کی ویب سائٹ سے کلید دوبارہ کاپی کریں                                                                      |
| "شرح کی حد تجاوز کر گئی"      | آپ بہت زیادہ درخواستیں بھیج رہے ہیں            | 1 منٹ انتظار کریں، یا خودکار متبادل کے لیے `model: "auto"` استعمال کریں                                               |
| "کوٹا ختم ہو گیا"             | آپ اپنا مفت/ادا شدہ کوٹا استعمال کر چکے ہیں    | مزید فراہم کنندگان منسلک کریں، یا مفت فراہم کنندگان (Kiro، Pollinations) استعمال کریں                                 |
| "سست جوابات"                  | فراہم کنندہ مصروف ہے یا بہت دور ہے             | `model: "auto/fast"` استعمال کریں یا کوئی تیز فراہم کنندہ (Groq، Cerebras) منسلک کریں                                 |
| "غلط فراہم کنندہ استعمال ہوا" | `auto` نے کوئی مختلف فراہم کنندہ منتخب کیا     | یہ معمول کی بات ہے! `auto` بہترین فراہم کنندہ منتخب کرتا ہے۔ `model: "openai/gpt-4o"` سے مخصوص فراہم کنندہ منتخب کریں |
| "502 خراب گیٹ وے"             | فراہم کنندہ دستیاب نہیں                        | انتظار کرکے دوبارہ کوشش کریں، یا فراہم کنندہ تبدیل کرنے کے لیے `model: "auto"` استعمال کریں                           |
| "401 غیر مجاز"                | آپ کی اسناد غلط ہیں                            | اپنی API کلید چیک کریں یا OAuth کے ذریعے دوبارہ توثیق کریں                                                            |
| "omniroute شناخت نہیں ہوا"    | Windows PATH میں عالمی node ماڈیولز شامل نہیں  | اپنا npm عالمی پریفکس Windows PATH میں شامل کریں۔ اسے `npm config get prefix` سے تلاش کریں۔                           |
| "429 بہت زیادہ درخواستیں"     | شرح محدود کر دی گئی ہے                         | 1 منٹ انتظار کریں، یا مزید فراہم کنندگان منسلک کریں                                                                   |

**اب بھی مسئلہ حل نہیں ہوا؟** ذیل میں [تفصیلی خرابیوں کا ازالہ](#detailed-troubleshooting) دیکھیں، یا [Discord](https://discord.gg/U47eFqAXCn) پر پوچھیں۔

## تفصیلی خرابیوں کا ازالہ

---

### مفت فراہم کنندگان پر شرح کی تحدید (429 / 400 / 401)

**علامت**: مفت/بلا توثیق فراہم کنندگان (opencode، auggie وغیرہ) کے ساتھ `model: "auto"` استعمال کرتے وقت، کبھی کبھار جوابات کے بجائے `HTTP 429`، `400`، یا `401` موصول ہوتا ہے۔ چند لمحوں بعد اسی پرامپٹ کو دوبارہ آزمانے پر درخواستیں کامیاب ہو جاتی ہیں، لیکن خودکاری (cron جابز، ایجنٹس، اسکرپٹس) پہلی ناکامی پر رک جاتی ہے۔

**بنیادی وجہ**: ناکامی کی تین آزاد صورتیں ایک ساتھ جمع ہو جاتی ہیں:

1. **فراہم کنندہ کی شرح کی حد (`429`)**: مفت درجات فی وقفہ کوٹا نافذ کر سکتے ہیں۔ متوازی کالز کا اچانک اضافہ اسے ختم کر دیتا ہے، اس لیے وقفہ ری سیٹ ہونے تک اگلی درخواست مسترد کر دی جاتی ہے۔
2. **پاس تھرو میں خراب ماڈل (`400`/`401`)**: `auto/*` پولز میں `opencode` کے ایسے پاس تھرو ماڈلز شامل ہو سکتے ہیں جو کیٹلاگ میں رجسٹرڈ ہیں لیکن ان کے پاس فعال اسناد نہیں ہیں (مثلاً `oc/north-mini-code-free` → `401`)۔ آٹو راؤٹر ایک کو آزماتا ہے، ناکام ہوتا ہے، اور متبادل فعال ہونے سے پہلے ہی خرابی آگے منتقل ہو جاتی ہے۔
3. **ہم وقتی کا بڑھتا اثر (لوڈ کے تحت `429`)**: جب متعدد ایجنٹ/cron سیشن ایک ہی وقت میں `auto` استعمال کرتے ہیں، تو درخواستوں کی مجموعی شرح مفت فراہم کنندگان کی قابل برداشت حد سے بڑھ جاتی ہے، جس کے نتیجے میں جائز کالز کو بھی غلط استعمال کے طور پر نشان زد کر دیا جاتا ہے۔

**تصدیق شدہ حل (کمیونٹی کی جانب سے رپورٹ کردہ، 2026-08-10)**: تین ماحولیاتی متغیرات کو اس طرح ترتیب دیں کہ گردش، ہم وقتی، اور متبادل نظام مفت درجے کے اتار چڑھاؤ کو ناکامی میں بدلنے کے بجائے جذب کر لیں:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 پر کسی دوسرے ماڈل/فراہم کنندہ پر جائیں (خراب پاس تھرو ماڈلز کو چھوڑ دیتا ہے)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # بھاری درخواستوں کے داخلے کی واضح بالائی حد (بطور ڈیفالٹ غیر مقرر: درخواستوں کی تعداد پر کوئی حد نہیں، ذیل کا نوٹ دیکھیں)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # فوری طور پر دوبارہ قابل کوشش 503 دینے کے بجائے بھاری گنجائش کے لیے زیادہ طویل مگر محدود انتظار
```

انہیں OmniRoute پراسیس کے ماحول میں مقرر کریں (ڈیمَن میں، مثلاً LaunchAgent plist یا `systemctl edit` کے ذریعے)، پھر OmniRoute دوبارہ شروع کریں۔ گردش کا فلیگ سب سے زیادہ مؤثر واحد ذریعہ ہے: یہ سخت ناکامی کو پول میں موجود کسی صحت مند فراہم کنندہ کے خلاف شفاف دوبارہ کوشش میں بدل دیتا ہے۔

**نوٹ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` اس بات کو محدود کرتا ہے کہ کتنی بھاری — طویل سیاق والی — درخواستیں ایک وقت میں چل سکتی ہیں؛ یہ حد داخلے کا گیٹ ہے، فراہم کنندہ کی شرح محدود کرنے والا نظام نہیں۔ **#503-fanout تازہ کاری:** یہ متغیر اب بطور ڈیفالٹ مقرر نہیں ہوتا (اب یہ صرف واضح طور پر ترتیب دیے جانے پر لاگو ہوتا ہے، جیسا کہ اوپر دکھایا گیا ہے) — اس کے بجائے بھاری درخواستوں کے داخلے کو خودکار طور پر اخذ کردہ بائٹ بجٹ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کے ذریعے کنٹرول کیا جاتا ہے، جو میزبان کی حقیقی میموری حد کے مطابق خود کو پیمانہ کرتا ہے؛ لہٰذا نئی تنصیب میں اس متغیر کو بالکل بھی مقرر کیے بغیر `503 chat_admission_busy` مستردیوں کی تعداد بہت کم ہونی چاہیے؛ اسے یہاں واضح طور پر مقرر کرنا اب بھی دستاویز کے مطابق بالکل اسی طرح کام کرتا ہے۔ واضح بائٹ بجٹ اوور رائیڈز 8 MiB–2 GiB تک محدود رہتے ہیں۔ `413 body_exceeds_budget` عارضی نہیں ہے: اس بائٹ بجٹ میں اضافہ کریں، `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` کم کریں، یا پراسیس کی میموری حد بڑھائیں۔ `inflight_bytes_budget` کی وجہ سے لوڈ کم کرنا عارضی وسائل کی مسابقت ہے اور اس پر دوبارہ کوشش کی جا سکتی ہے۔ فی فراہم کنندہ شرح کی تحدید (`open-sse/services/rateLimitManager.ts`) کو الگ سے `RATE_LIMIT_MAX_WAIT_MS`، `RATE_LIMIT_MAX_QUEUE_DEPTH`، اور `RATE_LIMIT_AUTO_ENABLE` کے ذریعے کنٹرول کیا جاتا ہے — `.env.example` دیکھیں۔

**یہ کیسے تصدیق کریں کہ اس نے کام کیا**: اپنے agent/cron کو یکے بعد دیگرے دو مرتبہ چلائیں اور تصدیق کریں کہ دونوں کامیاب ہوتے ہیں۔ اصلاح سے پہلے، دوسری بار چلانے پر عموماً `429`/`401` آتا ہے۔ اصلاح کے بعد، ناکامیوں (اگر کوئی ہوں) پر پسِ پردہ دوبارہ کوشش کی جاتی ہے اور کال مکمل ہو جاتی ہے۔ آپ `curl /monitoring/health` بھی چلا سکتے ہیں اور provider connections میں `rateLimitedUntil` فیلڈ، نیز متاثرہ providers کے لیے `circuitBreakers.providerBreakers[].state` کو دیکھ سکتے ہیں — state، `CLOSED`، `DEGRADED`، `OPEN`، یا `HALF_OPEN` میں سے ایک ہوتی ہے (`src/shared/utils/circuitBreaker.ts` دیکھیں)، اور مسلسل ناکام ہونے والا provider، reset window کے ذریعے probe کی اجازت ملنے (`HALF_OPEN`) سے پہلے `CLOSED → DEGRADED → OPEN` پر منتقل ہو جائے گا۔

**اگر آپ کو اب بھی 429 نظر آئے**: اس provider کے فعال account کا _quota_ واقعی ختم ہو چکا ہے (یہ محض rate کی حد نہیں ہے)۔ OmniRoute dashboard → Providers → Accounts میں اسی provider کے لیے دوسرا account شامل کریں، یا کسی دوسرے مفت provider کو شامل کریں (مثلاً `routeway`، `auggie`)۔ Rotation صرف عارضی rate/400/401 کی صورت میں مدد کرتی ہے؛ quota مکمل طور پر ختم ہونے کی صورت میں دوسری credential یا مختلف provider درکار ہوتا ہے۔

**اگر vision models (`auto/vision`، `bazaarlink/*`) پر 403 نظر آئے**: منسلک account کے پاس ایسا paid plan نہیں ہے جس میں vision شامل ہو، یا API key کے پاس مطلوبہ permissions نہیں ہیں۔ provider dashboard میں تصدیق کریں کہ key scope میں vision/multimodal شامل ہے، یا paid tier account منسلک کریں اور اسے vision target کے طور پر برقرار رکھیں۔

## npm install انتباہات (ERESOLVE / peer / deprecated)

جب آپ `npm install -g omniroute` چلاتے ہیں، تو آپ کو `npm warn ERESOLVE`، peer-dependency نوٹسز، اور `deprecated` پیغامات جیسے بہت سے انتباہات نظر آ سکتے ہیں۔ **یہ متوقع اور بے ضرر ہیں۔** اگر آؤٹ پٹ میں `added <N> packages` دکھائی دے تو آپ کی انسٹالیشن کامیاب ہو گئی ہے۔

peer-dependency ریزولیوشن کے انتباہات کو دبانے کے لیے، OmniRoute کا معاونت یافتہ انسٹالیشن طریقہ استعمال کریں:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` صرف `ERESOLVE` اور peer-dependency نوٹسز کو دباتا ہے۔ فرسودگی کے نوٹسز نظر آتے رہتے ہیں کیونکہ وہ بالواسطہ فریق ثالث پیکیجز سے آتے ہیں؛ ان کا مطلب یہ نہیں کہ انسٹالیشن ناکام ہو گئی ہے۔

یہ انتباہات فریق ثالث کے ان پیکیجز میں پرانی peer-dependency حدود کی وجہ سے آتے ہیں جو OmniRoute کے اختیار میں نہیں ہیں:

1. **`marked-terminal` کو `marked >=1 <16` درکار ہے، مگر `marked@18` ملا** — عملی طور پر یہ درست کام کرتا ہے؛ upstream peer حد صرف پرانی ہے۔
2. **`deprecated prebuild-install@7.1.3`** — مقامی بائنری حاصل کرنے کا ایک بالواسطہ معاون۔ اسے پن شدہ `wreq-js` ٹرانسپورٹ بائنڈنگ انسٹال کرنے کے لیے
   استعمال نہیں کیا جاتا، اور یہ اس بات کی نشاندہی نہیں کرتا کہ web-cookie
   فراہم کنندہ کی ٹرانسپورٹ سیٹ اپ ناکام ہو گئی ہے۔

**کسی کارروائی کی ضرورت نہیں** — upstream پیکیجز کو fork کیے بغیر ان انتباہات کو مکمل طور پر خاموش نہیں کیا جا سکتا۔

## Gemini Web اور Playwright Chromium

اگر Gemini Web کی کوئی درخواست `503` واپس کرتی ہے اور پیغام میں بتایا جاتا ہے کہ Playwright Chromium
انسٹال نہیں ہے، تو npm پیکیج موجود ہے مگر براؤزر بائنری غائب ہے۔
Playwright جان بوجھ کر براؤزر ڈاؤن لوڈز کو npm پیکیج
کی انسٹالیشن سے الگ رکھتا ہے، اس لیے براؤزر انسٹال ہونے تک یہ جواب متوقع ہے۔

عالمی npm انسٹالیشن کے لیے، OmniRoute پیکیج کی
ڈائریکٹری سے Chromium انسٹال کریں تاکہ براؤزر کیش اسی Playwright انسٹالیشن سے وابستہ ہو:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

انسٹالیشن کے بعد OmniRoute دوبارہ شروع کریں، پھر Gemini Web کی درخواست دوبارہ آزمائیں۔ اگر آپ
OmniRoute کو Docker امیج سے چلاتے ہیں، تو `-web` امیج (یا `runner-web`
بلڈ ٹارگٹ) استعمال کریں، جس میں Chromium اور اس کی dependencies شامل ہیں؛ بنیادی امیج میں
یہ شامل نہیں ہیں۔

## اینٹی وائرس کے غلط مثبت نتائج

<a name="antivirus-false-positives"></a>

### Avast/AVG کا `README.md` کو `MD:HttpRequest-inf[Susp]` کے ساتھ قرنطینہ کرنا

**یہ ایک غلط مثبت نتیجہ ہے۔ کچھ بھی متاثر نہیں ہے، اور کسی کارروائی کی ضرورت نہیں ہے۔**

Avast اور AVG ایک ایسا ہیورسٹک چلاتے ہیں جو ان سادہ متن/Markdown فائلوں کو نشان زد کرتا ہے جن میں
HTTP درخواستوں جیسے نظر آنے والے بہت سے لنکس موجود ہوں۔ OmniRoute کی `README.md` npm پیکیج کے اندر شامل ہوتی ہے (یہ
`package.json` → `files` میں درج ہے)، اس لیے عالمی انسٹالیشن پر یہ `node_modules/omniroute/README.md` میں
آ جاتی ہے — اور اس میں `http://localhost:20128/...` کی تقریباً 15 مثالیں موجود ہیں (MCP
HTTP/SSE اینڈ پوائنٹس، A2A `.well-known` URL، اور `curl` کے اقتباسات)۔ لنکس کی یہ کثافت
ہیورسٹک کو متحرک کرنے کے لیے کافی ہے۔

اگر یہ مسئلہ حال ہی میں شروع ہوا ہے: فائل کی نوعیت تبدیل نہیں ہوئی۔ README کی
اینڈ پوائنٹس جدول میں توسیع ہوئی (MCP HTTP + SSE + A2A شامل کیے گئے) اور مزید `curl` مثالیں شامل ہوئیں، جس کی وجہ سے
یہ حد سے تجاوز کر گئی۔

یہ فائل غیر فعال دستاویز ہے جس میں قابلِ عمل مواد بالکل نہیں ہے۔ آپ اسے محفوظ طریقے سے
قرنطینہ سے بحال کر سکتے ہیں۔

**کیا کریں:**

1. **اطلاعات روکیں** — اپنے اینٹی وائرس میں انسٹالیشن ڈائریکٹری کو مستثنیٰ قرار دیں
   (Avast: Settings → Exceptions)، اور اپنی عالمی `node_modules` پاتھ اور/یا
   OmniRoute ڈیٹا ڈائریکٹری (`~/.omniroute/`) شامل کریں۔
2. **غلط مثبت نتیجے کی اطلاع دیں** — <https://www.avast.com/false-positive-file-form.php>،
   اور قرنطینہ شدہ `README.md` منسلک کریں۔ یہی وہ حل ہے جو سب کے لیے مددگار ہے، کیونکہ یہ
   وینڈر کا ہیورسٹک ہے جو ایک متنی فائل پر ضرورت سے زیادہ ردِعمل دے رہا ہے۔

**ہم اپنی جانب سے اسے "درست" کیوں نہیں کرتے:** تمام مثالیں `http://localhost` ہیں، اور
خود دستخط شدہ سرٹیفکیٹ کی پیچیدگی کے بغیر localhost کو `https` نہیں بنایا جا سکتا۔ کسی ایک وینڈر کے ہیورسٹک سے
بچنے کے لیے دستاویزات کو بگاڑنا، اسکینر کے ایک بگ کو مطمئن کرنے کی خاطر ہر قاری کے لیے نقصان دہ ہوگا۔

### Kaspersky کا Desktop ایپ کو `PDM:Trojan.Win32.Generic` کے طور پر نشان زد کرنا

**یہ رویہ جاتی ہیورسٹک کا ایک غلط مثبت نتیجہ ہے۔ کچھ بھی متاثر نہیں ہے۔** Kaspersky کا
`PDM:` سابقہ بتاتا ہے کہ فیصلہ اس کے Proactive Defense Module (System Watcher) کی طرف سے آیا ہے،
جو معلوم میل ویئر کے ساتھ مماثلت تلاش کرنے کے بجائے یہ جانچتا ہے کہ انسٹالر _کیا کرتا ہے_۔ جب
یہ متحرک ہوتا ہے تو Kaspersky پوری انسٹالیشن کو "واپس پلٹا" دیتا ہے — اور وہ فائلیں حذف کر دیتا ہے جو پہلے ہی
لکھی جا چکی ہوں — لہٰذا ایپ خراب ہو جاتی ہے یا غائب ہو جاتی ہے۔

جن فائلوں کو یہ نشان زد کرتا ہے وہ ڈیسک ٹاپ ایپ کے ساتھ بنڈل کردہ، واضح طور پر اعلان شدہ اوپن سورس انحصارات کے
معیاری حصے ہیں، مثلاً:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` اور
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)، براؤزر آٹومیشن
  لائبریری جو ایپ کے اندر پرووائیڈر لاگ اِن اور براؤزر پر مبنی چیٹ کے لیے استعمال ہوتی ہے۔
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — مقررہ `wreq-js` مقامی بائنڈنگ جو ویب کوکی
  پرووائیڈرز پر براؤزر فنگرپرنٹ شدہ HTTP کے لیے استعمال ہوتی ہے (`<arch>` سے مراد `x64` یا `arm64` ہے)۔

**یہ کیوں متحرک ہوتا ہے:** Windows انسٹالر پر **ابھی تک کوڈ سائن نہیں کیا گیا**، اس لیے ایک غیر دستخط شدہ NSIS
انسٹالر کی کوئی ساکھ نہیں ہوتی اور رویہ جاتی ہیورسٹکس انتہائی جارحانہ انداز میں چلتے ہیں۔ اس کے ساتھ
ایک بنڈل شدہ مقامی DLL اور `%LOCALAPPDATA%\Programs\OmniRoute` کے اندر لکھی جانے والی سینکڑوں `.js` فائلیں
(بشمول Next.js اسٹینڈ الون بلڈ کی ہیش لاحقہ والی پیکیج ڈائریکٹریز)
ہیورسٹک کو متحرک کرنے کے لیے کافی ہیں۔ کوڈ سائننگ کا منصوبہ موجود ہے؛
اس کے نافذ ہونے تک نئی ریلیزز میں یہ مسئلہ دوبارہ پیش آ سکتا ہے۔

**کیا کریں:**

1. **پہلے اپنے ڈاؤن لوڈ کی تصدیق کریں** (یہ چھیڑ چھاڑ شدہ فائل کے امکان کو خارج کرتا ہے)۔ ہر ریلیز
   `latest.yml` شائع کرتی ہے، جس کا `sha512` فیلڈ (base64) `OmniRoute.Setup.<version>.exe`
   انسٹالر کا احاطہ کرتا ہے۔ PowerShell میں، انسٹالر والی ڈائریکٹری سے:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   آؤٹ پٹ کا `latest.yml` → `sha512` سے مماثل ہونا ضروری ہے۔ اگر یہ مماثل نہ ہو تو فائل حذف کریں اور
   صرف [GitHub ریلیزز صفحے](https://github.com/diegosouzapw/OmniRoute/releases) سے دوبارہ ڈاؤن لوڈ کریں۔
2. **بحال کریں + مستثنیٰ قرار دیں** — واپس پلٹائی گئی اشیا کو قرنطینہ سے بحال کریں اور
   `%LOCALAPPDATA%\Programs\OmniRoute` کے لیے ایک استثنا شامل کریں (Kaspersky → Settings → Threats and Exclusions)،
   پھر دوبارہ انسٹال کریں۔
3. **غلط مثبت نتیجے کی اطلاع دیں** — <https://opentip.kaspersky.com/>۔ صارفین کی جانب سے جمع کرائی گئی FP
   رپورٹس واقعی اجازت یافتہ فہرست میں شامل کیے جانے کے عمل کو تیز کرتی ہیں۔

## Node.js مطابقت

<a name="nodejs-compatibility"></a>

### لاگ اِن صفحہ کریش ہو جاتا ہے یا "Module self-registration" خرابی دکھاتا ہے

**وجہ:** آپ Node.js کا ایسا ورژن چلا رہے ہیں جو OmniRoute کی منظور شدہ محفوظ رَن ٹائم کی کم از کم حد سے باہر ہے۔ سب سے عام صورت یہ ہے کہ Node 22 یا 24 کا کوئی پرانا پیچ لیول چل رہا ہو، جو OmniRoute کی مطلوبہ پیچ شدہ سیکیورٹی حد سے کم ہو۔

**علامات:**

- لاگ اِن صفحہ خالی اسکرین یا سرور کی خرابی دکھاتا ہے
- کنسول میں `Error: Module did not self-register` یا اس جیسی نیٹو بائنڈنگ کی خرابیاں دکھائی دیتی ہیں
- اگر رَن ٹائم معاونت یافتہ محفوظ پالیسی سے باہر ہو تو لاگ اِن صفحہ آپ کے Node ورژن کے ساتھ ایک **نارنجی انتباہی بینر** دکھاتا ہے

**حل:**

1. Node.js کی معاونت یافتہ LTS ریلیز انسٹال کریں (تجویز کردہ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. اپنا ورژن چیک کریں: `node --version` کو 24.x LTS سلسلے میں `v24.0.0` یا اس سے نیا ورژن دکھانا چاہیے
3. OmniRoute دوبارہ انسٹال کریں: `npm install -g omniroute`
4. دوبارہ شروع کریں: `omniroute`

> **معاونت یافتہ محفوظ ورژنز:** `>=22.22.2 <23` یا `>=24.0.0 <27`۔ Node.js 24.x LTS (Krypton) اور Node.js 26 مکمل طور پر معاونت یافتہ ہیں۔

### npm v11+: `better-sqlite3` انسٹال نہیں ہوا (ماڈیول نہیں مل سکا)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**وجہ:** npm v11 (جو Node.js 24+ کے ساتھ فراہم کیا جاتا ہے) بطور ڈیفالٹ اختیاری
ڈیپینڈنسیز کی انسٹال اسکرپٹس کو بلاک کرتا ہے۔ چونکہ `better-sqlite3`، `optionalDependencies`
میں درج ہے اور اسے نیٹو کمپائلیشن (`node-gyp rebuild`) درکار ہوتی ہے، اس لیے npm خاموشی سے اسے چھوڑ دیتا ہے۔

**علامات:**

- سرور اسٹارٹ اپ پر `Cannot find module 'better-sqlite3'` کے ساتھ کریش ہو جاتا ہے
- `ls node_modules/better-sqlite3` سے "No such file or directory" دکھائی دیتا ہے
- `npm ls better-sqlite3` سے `(empty)` دکھائی دیتا ہے

**حل:**

1. انسٹال اسکرپٹس کی منظوری دیں اور دوبارہ انسٹال کریں:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. یا پہلے سے تیار شدہ پیکیج کو دستی طور پر انسٹال کریں:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. تصدیق کریں کہ یہ کام کرتا ہے: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**وجہ:** عالمی `npm install -g omniroute` کے بعد، پیکیج کے اندر موجود `better-sqlite3` نیٹو بائنری ممکن ہے کسی ایسے مختلف آرکیٹیکچر یا Node.js ABI کے لیے کمپائل ہوئی ہو جو مقامی طور پر چلنے والے ماحول سے مختلف ہو۔ یہ macOS (Apple Silicon اور Intel دونوں) پر عام ہے، جب پہلے سے تیار شدہ بائنری آپ کے ماحول سے مطابقت نہیں رکھتی۔

**علامات:**

- سرور اسٹارٹ اپ پر فوراً `dlopen` خرابی کے ساتھ ناکام ہو جاتا ہے
- خرابی میں `slice is not valid mach-o file` شامل ہوتا ہے
- مکمل مثال:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**حل — اپنے مقامی ماحول کے لیے دوبارہ بلڈ کریں (Node.js کو ڈاؤن گریڈ کرنے کی ضرورت نہیں):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **نوٹ:** یہ نیٹو بائنڈنگ کو آپ کے مقامی Node.js ورژن اور CPU آرکیٹیکچر کے مطابق دوبارہ کمپائل کرتا ہے، جس سے بائنری عدم مطابقت حل ہو جاتی ہے۔ باضابطہ طور پر معاونت یافتہ رَن ٹائم رینج **`>=22.22.2 <23` یا `>=24.0.0 <27`** ہے (`src/shared/utils/nodeRuntimeSupport.ts` میں `SUPPORTED_NODE_RANGE`، جو `package.json` کے `engines` فیلڈ کے مطابق ہے)۔ Node.js 24.x LTS (Krypton) اور Node.js 26 کو `better-sqlite3` v12.x کے ساتھ مکمل معاونت حاصل ہے۔

## پراکسی کے مسائل

<a name="proxy-issues"></a>

### فراہم کنندہ کی توثیق میں "fetch failed" دکھائی دیتا ہے

**وجہ:** API کلید کی توثیق کا اینڈ پوائنٹ (`POST /api/providers/validate`) پہلے پراکسی کنفیگریشن کو نظرانداز کر رہا تھا، جس کی وجہ سے ان ماحولوں میں ناکامی ہوتی تھی جہاں پراکسی روٹنگ درکار ہوتی ہے۔

**حل (v3.5.5+):** اب یہ مسئلہ حل ہو چکا ہے۔ فراہم کنندہ کی توثیق `runWithProxyContext` کے ذریعے روٹ ہوتی ہے اور خودکار طور پر فراہم کنندہ کی سطح اور عالمی پراکسی ترتیبات کی پابندی کرتی ہے۔

### ٹوکن کی صحت کی جانچ "fetch failed" کے ساتھ ناکام ہو جاتی ہے

**وجہ:** پس منظر میں OAuth ٹوکن ریفریش کا عمل ہر کنکشن کے لیے پراکسی کنفیگریشن کو حل نہیں کر رہا تھا۔

**حل (v3.5.5+):** ٹوکن کی صحت کی جانچ کا شیڈیولر اب ریفریش کی کوشش سے پہلے ہر کنکشن کے لیے پراکسی کنفیگ کو حل کرتا ہے۔ v3.5.5+ پر اپ ڈیٹ کریں۔

### SOCKS5 پراکسی "invalid onRequestStart method" لوٹاتی ہے

**وجہ:** Node.js 22 پر undici@8 ڈسپیچر، Node کے اندرونی `fetch()` نفاذ کے ساتھ مطابقت نہیں رکھتا۔

**حل (v3.5.5+):** جب پراکسی ڈسپیچر فعال ہو تو OmniRoute اب undici کا اپنا `fetch()` فنکشن استعمال کرتا ہے، جس سے یکساں طرزِ عمل یقینی بنتا ہے۔ v3.5.5+ پر اپ ڈیٹ کریں۔

### WSL کے تحت MITM پراکسی: Windows ہوسٹ پر ڈیسک ٹاپ ایپس انٹرسیپٹ نہیں ہوتیں

**وجہ:** MITM پراکسی اور اس کا CA سرٹیفکیٹ اس ماحول میں انسٹال ہوتے ہیں جہاں OmniRoute چلتا ہے۔ WSL کے تحت یہ ماحول Linux گیسٹ ہوتا ہے، جبکہ AI ڈیسک ٹاپ ایپس (Kiro، Trae، Copilot، Zed، …) Windows ہوسٹ پر چلتی ہیں۔ ہوسٹ ایپس گیسٹ کے سرٹیفکیٹ اسٹور پر اعتماد نہیں کرتیں اور گیسٹ کی سسٹم پراکسی کے ذریعے روٹ نہیں ہوتیں، اس لیے وہاں ڈیسک ٹاپ انٹرسیپشن فعال نہیں ہوتی۔

**تجویز:** OmniRoute کو مقامی طور پر اسی OS پر چلائیں جس پر وہ ڈیسک ٹاپ ایپس چل رہی ہیں جنہیں آپ انٹرسیپٹ کرنا چاہتے ہیں (Windows ایپس کے لیے Windows؛ اسی طرح macOS/Linux کے لیے متعلقہ OS)۔ ہوسٹ ایپس کو ہدف بناتے ہوئے OmniRoute کو WSL کے اندر رکھنے کے لیے ضروری ہے کہ بنائے گئے CA سرٹیفکیٹ کو Windows ہوسٹ پر دستی طور پر قابلِ اعتماد بنایا جائے اور ہر ہوسٹ ایپ کی نیٹ ورک/پراکسی ترتیبات کو WSL پراکسی اینڈ پوائنٹ کی طرف متعین کیا جائے — یہ ایک غیر معاون اور غیر مستحکم سیٹ اپ ہے۔

## کلاؤڈ کے مسائل

### کلاؤڈ سنک کی خرابیاں

1. تصدیق کریں کہ `BASE_URL` آپ کی چلتی ہوئی انسٹینس کی طرف اشارہ کرتا ہے (مثلاً، `http://localhost:20128`)
2. تصدیق کریں کہ `CLOUD_URL` آپ کے کلاؤڈ اینڈ پوائنٹ کی طرف اشارہ کرتا ہے (مثلاً، `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` کی قدروں کو سرور سائیڈ کی قدروں کے مطابق رکھیں

### کلاؤڈ پر `stream=false` سے 500 واپس آتا ہے

**علامت:** نان اسٹریمنگ کالز کے لیے کلاؤڈ اینڈ پوائنٹ پر `Unexpected token 'd'...`۔

**وجہ:** اپ اسٹریم SSE پے لوڈ واپس کرتا ہے جبکہ کلائنٹ JSON کی توقع کرتا ہے۔

**عارضی حل:** کلاؤڈ کو براہِ راست کالز کے لیے `stream=true` استعمال کریں۔ لوکل رن ٹائم میں SSE→JSON فال بیک شامل ہے۔

### کلاؤڈ کنیکٹڈ دکھاتا ہے لیکن "Invalid API key" کہتا ہے

1. لوکل ڈیش بورڈ (`/api/keys`) سے ایک نئی کلید بنائیں
2. کلاؤڈ سنک چلائیں: کلاؤڈ فعال کریں → ابھی سنک کریں
3. پرانی یا سنک نہ کی گئی کلیدیں اب بھی کلاؤڈ پر `401` واپس کر سکتی ہیں

## Docker کے مسائل

### Docker IPv6 / کنکشن ری سیٹ

<a name="docker-ipv6"></a>

**علامات:** `curl http://localhost:20128/v1/models` سے `curl: (56) Recv failure: Connection reset by peer` واپس آتا ہے۔ ڈیش بورڈ اور غیر توثیق شدہ اینڈ پوائنٹس کام کرتے ہیں، لیکن توثیق شدہ اینڈ پوائنٹس ناکام ہو جاتے ہیں — یہ توثیق کا مسئلہ لگتا ہے، مگر ایسا نہیں ہے۔

**وجہ:** `docker run -p 20128:20128` دونوں `0.0.0.0` (IPv4) اور `::` (IPv6) پر پورٹ شائع کرتا ہے، لیکن کنٹینر کے اندر موجود پراسیس صرف IPv4 پر سنتا ہے۔ ایسے ہوسٹس پر جہاں `localhost` پہلے `::1` میں ریزولو ہوتا ہے، کنکشن IPv6 کی شائع شدہ پورٹ پر پہنچتا ہے جس کے پیچھے کوئی لسنر موجود نہیں ہوتا → کنکشن ری سیٹ۔

**حل:**

1. **فوری تشخیص:** `curl -4 http://localhost:20128/v1/models` چلائیں۔ اگر یہ `-4` کے ساتھ کام کرتا ہے لیکن اس کے بغیر ناکام ہوتا ہے، تو آپ کو IPv6 بائنڈ کی عدم مطابقت کا مسئلہ درپیش ہے۔
2. **مستقل حل:** اپنی `docker run` کمانڈ میں `-p 127.0.0.1:20128:20128` استعمال کرکے واضح طور پر IPv4 سے بائنڈ کریں:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```

## ڈیبگنگ

### لاگ فائلیں فعال کریں

اپنی `.env` فائل میں `APP_LOG_TO_FILE=true` سیٹ کریں۔ ایپلیکیشن لاگز `logs/` کے تحت لکھے جاتے ہیں۔
جب سیٹنگز میں کال لاگ پائپ لائن فعال ہو تو درخواست کے آرٹیفیکٹس `${DATA_DIR}/call_logs/` کے تحت محفوظ کیے جاتے ہیں۔
جب پائپ لائن کیپچر فعال ہو تو اسٹریم چنک پے لوڈز کو شامل نہ کرنے کے لیے `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` سیٹ کریں، یا KB میں آرٹیفیکٹ کی حد تبدیل کرنے کے لیے `CALL_LOG_PIPELINE_MAX_SIZE_KB` کو ایڈجسٹ کریں۔

### پرووائیڈر کی صحت چیک کریں

```bash
# ہیلتھ ڈیش بورڈ
http://localhost:20128/dashboard/health

# API ہیلتھ چیک
curl http://localhost:20128/api/monitoring/health
```

### رن ٹائم اسٹوریج

- بنیادی حالت: `${DATA_DIR}/storage.sqlite` (پرووائیڈرز، کومبوز، عرف، کلیدیں، سیٹنگز)
- استعمال: `storage.sqlite` میں SQLite ٹیبلز (`usage_history`، `call_logs`، `proxy_logs`) + اختیاری `${DATA_DIR}/call_logs/`

`request_detail_logs`، اور لوکل `${DATA_DIR}/call_logs/` آرٹیفیکٹ ڈائریکٹری کو صاف کرتی ہے۔

## لچک پذیری کی ترتیبات

### خودکار شرح کی حد فعال نہیں ہو رہی

- خودکار شرح کی حد صرف API کلید فراہم کنندگان پر لاگو ہوتی ہے (OAuth/سبسکرپشن پر نہیں)
- تصدیق کریں کہ **Settings → Resilience → Provider Profiles** میں خودکار شرح کی حد فعال ہے
- چیک کریں کہ آیا فراہم کنندہ `429` اسٹیٹس کوڈز یا `Retry-After` ہیڈرز واپس کرتا ہے

### ایکسپونینشل بیک آف کی ٹیوننگ

فراہم کنندہ پروفائلز ان ترتیبات کی معاونت کرتے ہیں:

- **بنیادی تاخیر** — پہلی ناکامی کے بعد ابتدائی انتظار کا وقت (ڈیفالٹ: 1s)
- **زیادہ سے زیادہ تاخیر** — انتظار کے وقت کی زیادہ سے زیادہ حد (ڈیفالٹ: 30s)
- **ضارب** — ہر مسلسل ناکامی پر تاخیر میں کتنا اضافہ کیا جائے (ڈیفالٹ: 2x)

### تھنڈرنگ ہرڈ سے بچاؤ

جب کئی بیک وقت درخواستیں شرح کی حد والے فراہم کنندہ تک پہنچتی ہیں، تو OmniRoute درخواستوں کو سلسلہ وار کرنے اور پے در پے ناکامیوں کو روکنے کے لیے mutex + خودکار شرح کی حد استعمال کرتا ہے۔ API کلید فراہم کنندگان کے لیے یہ خودکار ہے۔

### چیٹ درخواستیں 503 / chat_admission_busy کے ساتھ ناکام ہوتی ہیں

**علامات:**

- چیٹ کمپلیشنز اینڈ پوائنٹ دوبارہ کوشش کے قابل `503` جواب واپس کرتا ہے، جس کا نقص کوڈ
  `chat_admission_busy` ہوتا ہے۔
- جواب میں `Retry-After` شامل ہوتا ہے۔ #12135 کے بعد سے اس کی قدر مشاہدہ شدہ
  مصروفیت سے اخذ ہوتی ہے — درخواست کے پہلے ہی انتظار کردہ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  وقفے اور موجودہ ہیوی ویٹ لیزز کے برقرار رہنے کے وقت میں سے بڑی قدر — جسے اوپر کی جانب قریب ترین
  مکمل سیکنڈ تک گول کیا جاتا ہے اور 60 پر محدود کیا جاتا ہے۔ غیر مصروف گیٹ پر یہ تاریخی کم از کم
  قدریں برقرار رکھتا ہے: بائٹ پر مبنی راستے پر 2 سیکنڈ، ساخت پر مبنی راستے پر 1 سیکنڈ
  (جس میں `reason: "structure_limit"` بھی شامل ہوتا ہے)۔
- یہ اس وقت ہو سکتا ہے جب کوئی دوسرا ہیوی ویٹ چیٹ یا طویل عرصے تک چلنے والا اسٹریمنگ جواب اب بھی
  زیرِ عمل ہو۔

بائٹ پر مبنی جواب کی باڈی یہ ہے:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ساخت پر مبنی جواب اسی قسم اور کوڈ کو استعمال کرتا ہے، جبکہ پیغام
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
اور `reason: "structure_limit"` ہوتا ہے۔
ڈیفالٹ حدوں پر، درخواست اس وقت ساختی طور پر بھاری ہوتی ہے جب اس میں کم از کم `200` پیغامات،
کم از کم `64` ٹولز، یا کم از کم `32,000` تخمینی ٹوکنز ہوں، یا جب محدود ساختی تخمینہ
`10,000` ملاحظہ کردہ نوڈز یا `12` گہرائی کی اپنی حدود ختم کر دے۔

**وجہ:** یہ OmniRoute کے اندر دانستہ لوڈ شیڈنگ ہے، اپ اسٹریم فراہم کنندہ کی ناکامی نہیں۔
ہر پراسیس، بڑی درخواست کی باڈی کو برقرار رکھنے اور پارس کرنے سے پہلے، محدود ہیوی ویٹ گنجائش محفوظ
کرنے کے لیے ایک پراسیس-لوکل گارڈ استعمال کرتا ہے۔ ایک ہیوی ویٹ لیز SSE جواب کی پوری مدت تک
برقرار رہتی ہے۔

**#503-fanout:** اس اصلاح سے پہلے، گارڈ میزبان کی میموری سے قطع نظر بیک وقت درخواستوں کو ایک مقررہ
تعداد (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`، ڈیفالٹ `1`) تک محدود کرتا تھا، اس لیے کوڈنگ ایجنٹ
فین آؤٹ (متعدد ذیلی ایجنٹس/CLIs، باڈیز معمول کے مطابق > 256 KB) مؤثر بیک وقتی کو تقریباً
1 تک گرا دیتا تھا اور مکمل طور پر معمول کے لوڈ میں 503 جوابات کا سبب بنتا تھا۔ اب گارڈ خود کو
ٹیون کرتا ہے: اسے پراسیس کی حقیقی میموری حد سے متعین کردہ، خودکار طور پر اخذ شدہ ان جیسٹ بائٹ
بجٹ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کے ذریعے کنٹرول کیا جاتا ہے، اور یہ براہِ راست
وسائل کے دباؤ کے سگنل کو بھی مدنظر رکھتا ہے — لہٰذا یہ صرف تب لوڈ کم کرتا ہے جب میزبان واقعی
میموری کے دباؤ میں ہو، محض اس لیے نہیں کہ ایک سے زیادہ بھاری درخواستیں بیک وقت پہنچ گئی ہیں۔
پرانی تعداد کی حد (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) کا اب بھی احترام کیا جاتا ہے، لیکن
صرف اس صورت میں جب آپ اسے واضح طور پر مقرر کریں۔

جب گنجائش مصروف ہو، تو ہیوی ویٹ درخواست دوبارہ کوشش کے قابل `503` جواب دینے سے پہلے کسی سلاٹ
کے خالی ہونے کے لیے `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ڈیفالٹ `2000`، `0` انتظار کو غیر فعال
کرتا ہے) تک انتظار کرتی ہے۔ یہ محدود انتظار اس لیے موجود ہے تاکہ ایجنٹ طرز کے کلائنٹس
(OpenCode, Claude Code, Cursor)، جو بھاری ذیلی درخواستیں بیک وقت فین آؤٹ کرتے ہیں، فوری
مستردیوں پر اپنا پورا دوبارہ کوشش کا بجٹ ضائع کرنے اور کام کے درمیان ناکام ہونے کے بجائے
درخواستوں کے اچانک اضافے کو سلسلہ وار کر سکیں۔
موجودہ ہیوی ویٹ لیز کی مصروفیت، طے شدہ بائٹ بجٹ، اور براہِ راست دباؤ کی شدت
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) پر ظاہر کی جاتی ہے — کسی بھی env var
کو تبدیل کرنے سے پہلے انہیں چیک کریں۔
Settings → Resilience → Request Queue → Concurrent Requests اسے کنٹرول نہیں کرتی؛ یہ ترتیب
ایک علیحدہ فراہم کنندہ درخواست قطار کے طریقۂ کار کو کنٹرول کرتی ہے۔

**حل:**

1. پہلے دوبارہ کوشش کریں۔ کلائنٹس کو درخواست فوری طور پر دہرانے کے بجائے `Retry-After` کا احترام
   کرنا اور بیک آف استعمال کرنا چاہیے۔
2. کچھ بھی ٹیون کرنے سے پہلے `/api/monitoring/health` → `chatAdmission` چیک کریں۔ `countCapEnabled:
false` اور فراخ `maxInflightBytes` کا مطلب ہے کہ خودکار طور پر اخذ شدہ بجٹ پہلے ہی اپنا
   کام کر رہا ہے؛ `high`/`critical` کی `pressureSeverity` کا مطلب ہے کہ میزبان کے پاس واقعی
   میموری کم ہے — اسے کسی ایڈمیشن env var سے ٹھیک نہیں کیا جا سکتا، اس کے لیے زیادہ RAM یا
   کم حجم کا ورک لوڈ درکار ہے۔
3. صرف اس صورت میں جب `/api/monitoring/health` یہ دکھائے کہ خودکار طور پر اخذ شدہ بجٹ واقعی
   آپ کے میزبان کے لیے بہت کم ہے (ایسا شاذ و نادر ہوتا ہے — یہ پہلے ہی کنٹینر سے لے کر
   بیئر میٹل تک اسکیل کرتا ہے)، پرانی درخواست-تعداد کی حد پر واپس جانے کے بجائے اسے براہِ راست
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` کے ذریعے اوور رائیڈ کریں۔

مستند ایڈمیشن ترتیبات کے لیے [ماحولیاتی متغیرات کا حوالہ](../reference/ENVIRONMENT.md#4-security--authentication)
دیکھیں۔

## اختیاری RAG / LLM ناکامیوں کی درجہ بندی (16 مسائل)

OmniRoute کے بعض صارفین گیٹ وے کو RAG یا ایجنٹ اسٹیکس کے آگے رکھتے ہیں۔ ایسی ترتیبات میں ایک عجیب صورتِ حال عام طور پر دیکھنے میں آتی ہے: OmniRoute بظاہر درست کام کر رہا ہوتا ہے (فراہم کنندگان فعال، روٹنگ پروفائلز درست، شرح کی حد کے کوئی انتباہات نہیں) لیکن حتمی جواب پھر بھی غلط ہوتا ہے۔

عملی طور پر یہ واقعات عموماً خود گیٹ وے کے بجائے ڈاؤن اسٹریم RAG پائپ لائن کی وجہ سے پیش آتے ہیں۔

اگر آپ ان ناکامیوں کی وضاحت کے لیے مشترکہ اصطلاحات استعمال کرنا چاہتے ہیں، تو آپ WFGY ProblemMap استعمال کر سکتے ہیں، جو MIT لائسنس کے تحت ایک بیرونی متنی وسیلہ ہے اور RAG / LLM کی ناکامی کے بار بار پیش آنے والے سولہ نمونوں کی وضاحت کرتا ہے۔ اعلیٰ سطح پر اس میں درج ذیل شامل ہیں:

- بازیافت میں انحراف اور سیاق کی ٹوٹی ہوئی حدود
- خالی یا فرسودہ انڈیکسز اور ویکٹر اسٹورز
- ایمبیڈنگ اور معنوی مطابقت میں عدم موافقت
- پرامپٹ کی تشکیل اور سیاقی ونڈو کے مسائل
- منطق کا انہدام اور حد سے زیادہ پراعتماد جوابات
- طویل سلسلے اور ایجنٹوں کے درمیان ہم آہنگی کی ناکامیاں
- متعدد ایجنٹوں کی میموری اور کردار میں انحراف
- تعیناتی اور بوٹسٹریپ ترتیب کے مسائل

تصور سادہ ہے:

1. کسی خراب جواب کی تفتیش کرتے وقت، درج ذیل محفوظ کریں:
   - صارف کا کام اور درخواست
   - OmniRoute میں روٹ یا فراہم کنندگان کا مجموعہ
   - ڈاؤن اسٹریم میں استعمال ہونے والا کوئی بھی RAG سیاق (بازیافت شدہ دستاویزات، ٹول کالز، وغیرہ)
2. واقعے کو WFGY ProblemMap کے ایک یا دو نمبروں (`No.1` … `No.16`) سے منسلک کریں۔
3. نمبر کو OmniRoute لاگز کے ساتھ اپنے ڈیش بورڈ، رن بُک، یا واقعہ ٹریکر میں محفوظ کریں۔
4. متعلقہ WFGY صفحے کی مدد سے فیصلہ کریں کہ آیا آپ کو اپنے RAG اسٹیک، ریٹریور، یا روٹنگ حکمتِ عملی میں تبدیلی کی ضرورت ہے۔

مکمل متن اور عملی طریقے یہاں دستیاب ہیں (MIT لائسنس، صرف متن):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

اگر آپ OmniRoute کے پیچھے RAG یا ایجنٹ پائپ لائنز نہیں چلاتے تو آپ اس حصے کو نظر انداز کر سکتے ہیں۔

## v3.8.0 کے معلوم مسائل

v3.8.0 ریلیز سے مخصوص مسائل اور ان کے موجودہ عبوری حل۔ اگر کسی بعد کے پیچ میں اصلاح شامل ہو جاتی ہے تو اندراج کو اپ ڈیٹ یا حذف کر دیا جائے گا۔

### Devin CLI کی توثیق میں ناکامیاں

**علامات:**

- Devin پر مبنی ٹولز استعمال کرتے وقت "Devin CLI not found" یا "auth failed"
- CLI رن ٹائم جانچ میں `installed=false` کی رپورٹ

**وجوہات:**

- `CLI_DEVIN_BIN` ایک ایسے پاتھ کی طرف اشارہ کرتا ہے جو موجود نہیں
- میزبان پر Devin CLI انسٹال نہیں ہے

**حل:**

1. اپنے پلیٹ فارم کے لیے Devin CLI انسٹال کریں
2. `.env` میں `CLI_DEVIN_BIN=/usr/local/bin/devin` (یا اصل پاتھ) سیٹ کریں
3. OmniRoute کو دوبارہ شروع کریں اور **Dashboard → CLI Tools** سے دوبارہ آزمائیں

### ماڈل کول ڈاؤن پھنس گیا (دستی ری سیٹ)

**علامات:**

- میعاد ختم ہونے کا وقت گزر جانے کے بعد بھی کوئی ماڈل کول ڈاؤن میں درج رہتا ہے
- ٹائم اسٹیمپ ماضی کا ہونے کے باوجود کمبو روٹنگ میں درخواستیں ماڈل کو بدستور چھوڑ دیتی ہیں

**دستی ری سیٹ:**

- **ڈیش بورڈ:** **Settings → Model Cooldowns** → متاثرہ کارڈ پر **Re-enable** پر کلک کریں
- **API:** انتظامی توثیقی ہیڈرز کے ساتھ `DELETE /api/resilience/model-cooldowns`

### Command Code فراہم کنندہ کا کنکشن 403 کے ساتھ ناکام ہوتا ہے

**علامات:**

- Command Code فراہم کنندہ کے کنکشن کی جانچ کرتے وقت 403
- نیا اضافہ کرنے کے بعد فراہم کنندہ کا کارڈ "unauthorized" دکھاتا ہے

**وجہ:** OAuth بہاؤ مکمل نہیں ہوا (کال بیک موصول نہیں ہوا یا ٹوکن مستقل طور پر محفوظ نہیں کیا گیا)۔

**حل:**

- OAuth بہاؤ کو دوبارہ شروع کرنے کے لیے CLI سے `omniroute providers` چلائیں، یا
- **Dashboard → Providers → Command Code → Reconnect** سے OAuth دوبارہ چلائیں

### ModelScope بہت سخت 429 کول ڈاؤنز واپس کرتا ہے

**علامات:**

- درخواستوں کے ایک مختصر سلسلے کے بعد ModelScope پر انتہائی مختصر یا فوری کول ڈاؤنز
- کمبو روٹنگ توقع سے پہلے ModelScope کو چھوڑ دیتی ہے

**وجہ:** ModelScope فراہم کنندہ سے مخصوص `Retry-After` ہیڈرز بھیجتا ہے۔ v3.8.0 میں ان ہیڈرز کے لیے مخصوص ہینڈلنگ شامل ہے، اس لیے پرانے ورژنز انہیں شرح کی حد کے عمومی اشاروں کے طور پر غلط سمجھتے ہیں۔

**حل:**

- یقینی بنائیں کہ آپ v3.8.0 یا اس کے بعد کا ورژن استعمال کر رہے ہیں
- تصدیق کریں کہ **Settings → Resilience** کے تحت `useUpstream429BreakerHints` ٹوگل فعال ہے

### پروڈکشن میں OMNIROUTE_WS_BRIDGE_SECRET موجود نہیں

**علامات:**

- ریموٹ پروڈکشن میزبان پر چلتے ہوئے ہر Codex/Responses WebSocket برج درخواست پر 401
- کنیکٹ ہونے کے فوراً بعد WebSocket برج ہینڈ شیک بند ہو جاتا ہے

**وجہ:** پروڈکشن ماحول میں `OMNIROUTE_WS_BRIDGE_SECRET` env var موجود نہیں ہے۔

**حل:**

1. ایک بے ترتیب سیکرٹ بنائیں: `openssl rand -hex 32`
2. پروڈکشن سرور env میں `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` سیٹ کریں (اور برج سے رابطہ کرنے والے ہر کلائنٹ میں بھی)
3. OmniRoute کو دوبارہ شروع کریں

### Responses API: پس منظر موڈ سنکرونس میں تنزل پذیر

**علامات:**

- لاگ شدہ انتباہ: `background mode degraded to synchronous`
- `background: true` درخواست، پس منظر جاب ہینڈل کے بجائے ایک عام سنکرونس جواب واپس کرتی ہے

**وجہ:** v3.8.0 میں Responses API پر `background: true` کو جان بوجھ کر سنکرونس عمل درآمد میں تبدیل کیا جاتا ہے، جبکہ ایک انتباہ بھی جاری کیا جاتا ہے۔ مکمل غیر ہم وقت پس منظر عمل درآمد مستقبل میں فراہم کیا جائے گا۔

**حل:**

- کلائنٹ کو `background` کے بغیر کال کرنے کے لیے ایڈجسٹ کریں، یا
- مکمل غیر ہم وقت پس منظر موڈ فراہم کرنے والی بعد کی ریلیز کا انتظار کریں (چینج لاگ پر نظر رکھیں)

## سست آغاز / آمادگی کا ٹائم آؤٹ

اگر CLI میں `⚠ Server did not respond within 60s` ظاہر ہو لیکن سرور حقیقت میں
کام کر رہا ہو، تو آپ کے ماحول کے لیے آمادگی کی جانچ کا مختص وقت بہت کم ہے۔

یہ عام طور پر Windows (اینٹی وائرس، فائل سسٹم واچرز) یا بھاری ابتدائی کام کے بوجھ
والے کنٹینرز میں ہوتا ہے۔

**حل — مختص وقت بڑھائیں:**

```bash
# ماحول کے متغیر کے ذریعے (ہر آغاز پر برقرار رہتا ہے):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 منٹ
omniroute serve

# CLI فلیگ کے ذریعے (صرف ایک بار کے لیے):
omniroute serve --ready-timeout 180000
```

ڈیفالٹ 60 000 ms (60 s) ہے۔ یہ تنبیہ صرف معلوماتی ہے؛ سرور پس منظر میں
شروع ہوتا رہتا ہے اور بوٹ مکمل ہونے کے بعد قابل رسائی ہوگا۔

`OMNIROUTE_READY_TIMEOUT_MS` کی مکمل تفصیلات کے لیے
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) دیکھیں۔
