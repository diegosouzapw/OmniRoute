## فوری حوالہ

**OmniRoute پر نئے ہیں؟** یہاں سے شروع کریں — یہ 90% مسائل حل کر دیتے ہیں:

| مجھے یہ نظر آتا ہے                | اس کا کیا مطلب ہے                                  | کیا کرنا ہے                                                                                                                         |
| --------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| "کنیکٹ نہیں ہو سکتا"              | OmniRoute چل نہیں رہا                              | `omniroute` یا `docker restart omniroute` چلائیں                                                                                    |
| "غلط API کلید"                    | آپ کی کلید غلط ہے یا اس کی میعاد ختم ہو چکی ہے     | فراہم کنندہ کی ویب سائٹ سے کلید دوبارہ کاپی کریں                                                                                    |
| "شرح کی حد سے تجاوز ہو گیا"       | آپ بہت زیادہ درخواستیں بھیج رہے ہیں                | 1 منٹ انتظار کریں، یا خودکار فال بیک کے لیے `model: "auto"` استعمال کریں                                                            |
| "کوٹہ ختم ہو گیا"                 | آپ اپنا مفت/ادائیگی شدہ کوٹہ استعمال کر چکے ہیں    | مزید فراہم کنندگان منسلک کریں، یا مفت فراہم کنندگان (Kiro، Pollinations) استعمال کریں                                               |
| "جوابات سست ہیں"                  | فراہم کنندہ مصروف ہے یا بہت دور ہے                 | `model: "auto/fast"` استعمال کریں یا کوئی تیز فراہم کنندہ (Groq، Cerebras) منسلک کریں                                               |
| "غلط فراہم کنندہ استعمال ہوا"     | `auto` نے کوئی دوسرا فراہم کنندہ منتخب کیا         | یہ معمول کی بات ہے! `auto` بہترین کو منتخب کرتا ہے۔ `model: "openai/gpt-4o"` کے ساتھ کسی مخصوص فراہم کنندہ کو لازمی استعمال کروائیں |
| "502 خراب گیٹ وے"                 | فراہم کنندہ دستیاب نہیں ہے                         | انتظار کرکے دوبارہ کوشش کریں، یا فراہم کنندہ بدلنے کے لیے `model: "auto"` استعمال کریں                                              |
| "401 غیر مجاز"                    | آپ کی اسناد غلط ہیں                                | اپنی API کلید چیک کریں یا OAuth کے ذریعے دوبارہ توثیق کریں                                                                          |
| "omniroute کو شناخت نہیں کیا گیا" | Windows PATH میں گلوبل node ماڈیولز موجود نہیں ہیں | اپنا npm گلوبل پریفکس Windows PATH میں شامل کریں۔ اسے `npm config get prefix` سے معلوم کریں۔                                        |
| "429 بہت زیادہ درخواستیں"         | شرح کی حد لاگو ہو گئی ہے                           | 1 منٹ انتظار کریں، یا مزید فراہم کنندگان منسلک کریں                                                                                 |

## تفصیلی مسئلہ حل کرنے کی رہنمائی

---

### مفت فراہم کنندگان پر شرح کی حد بندی (429 / 400 / 401)

**علامت**: مفت/بغیر توثیق والے فراہم کنندگان (opencode، auggie وغیرہ) کے ساتھ `model: "auto"` استعمال کرتے وقت، آپ کو کبھی کبھار جوابات کے بجائے `HTTP 429`، `400` یا `401` ملتا ہے۔ چند لمحوں بعد اسی پرامپٹ کو دوبارہ آزمانے پر درخواستیں کامیاب ہو جاتی ہیں، لیکن خودکار عمل (cron جابز، ایجنٹس، اسکرپٹس) پہلی ناکامی ہی پر رک جاتا ہے۔

**بنیادی وجہ**: ناکامی کی تین آزاد صورتیں ایک ساتھ جمع ہو جاتی ہیں:

1. **فراہم کنندہ کی شرح کی حد (`429`)**: مفت درجوں میں فی دورانیہ کوٹہ نافذ ہو سکتا ہے۔ متوازی کالز کا اچانک اضافہ اسے ختم کر دیتا ہے، اس لیے اگلی درخواست اس وقت تک مسترد کر دی جاتی ہے جب تک دورانیہ ری سیٹ نہ ہو جائے۔
2. **پاس تھرو میں خراب ماڈل (`400`/`401`)**: `auto/*` پولز میں `opencode` کے ایسے پاس تھرو ماڈلز شامل ہو سکتے ہیں جو کیٹلاگ میں رجسٹرڈ ہیں مگر ان کے پاس فعال اسناد نہیں ہیں (مثلاً `oc/north-mini-code-free` → `401`)۔ آٹو راؤٹر کسی ایک کو آزماتا ہے، ناکام ہوتا ہے، اور فال بیک فعال ہونے سے پہلے ہی خرابی آگے منتقل ہو جاتی ہے۔
3. **ہم وقتی میں اضافہ (لوڈ کے تحت `429`)**: جب متعدد ایجنٹ/cron سیشنز ایک ہی وقت میں `auto` استعمال کرتے ہیں، تو مجموعی درخواستوں کی شرح مفت فراہم کنندگان کی برداشت سے بڑھ جاتی ہے، جس کے نتیجے میں جائز کالز کو بھی بدسلوکی کے طور پر نشان زد کر دیا جاتا ہے۔

**تصدیق شدہ حل (کمیونٹی کی رپورٹ، 2026-08-10)**: تین ماحولیاتی متغیرات کو اس طرح ایڈجسٹ کریں کہ روٹیشن، ہم وقتی، اور فال بیک مفت درجے کے اتار چڑھاؤ کو سنبھال لیں، بجائے اس کے کہ اس کی وجہ سے عمل ناکام ہو جائے:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 پر کسی دوسرے ماڈل/فراہم کنندہ پر جائیں (خراب پاس تھرو ماڈلز کو چھوڑ دیتا ہے)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # بھاری درخواستوں کے داخلے کی واضح زیادہ سے زیادہ حد (بطور ڈیفالٹ غیر مقرر: درخواستوں کی تعداد پر کوئی حد نہیں، ذیل کا نوٹ دیکھیں)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # سست اپ اسٹریمز کے لیے محدود انتظار کو RATE_LIMIT_MAX_WAIT_MS کی ڈیفالٹ قدر سے آگے بڑھائیں
```

انہیں OmniRoute پراسیس کے ماحول میں مقرر کریں (ڈیمَن میں، مثلاً LaunchAgent plist یا `systemctl edit` کے ذریعے)، پھر OmniRoute کو دوبارہ شروع کریں۔ روٹیشن فلیگ سب سے زیادہ مؤثر واحد اختیار ہے: یہ ایک قطعی ناکامی کو پول میں موجود کسی صحت مند فراہم کنندہ کے خلاف شفاف دوبارہ کوشش میں بدل دیتا ہے۔

**نوٹ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` اس بات کی حد مقرر کرتا ہے کہ کتنی بھاری — طویل سیاق والی — درخواستیں ایک ہی وقت میں چل سکتی ہیں؛ یہ حد داخلے کا گیٹ ہے، فراہم کنندہ کی شرح محدود کرنے والا نظام نہیں۔ **#503-fanout اپ ڈیٹ:** یہ متغیر اب بطور ڈیفالٹ مقرر نہیں ہوتا (اب یہ صرف واضح طور پر کنفیگر کیے جانے پر لاگو ہوتا ہے، جیسا کہ اوپر دکھایا گیا ہے) — اس کے بجائے بھاری درخواستوں کے داخلے کو خودکار طور پر اخذ کردہ بائٹ بجٹ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کے ذریعے کنٹرول کیا جاتا ہے، جو میزبان کی حقیقی میموری حد کے مطابق خود کو اسکیل کرتا ہے، اس لیے نئی تعیناتی میں اس متغیر کو بالکل بھی مقرر کیے بغیر `503 chat_admission_busy` مستردیاں بہت کم نظر آنی چاہئیں؛ اسے یہاں واضح طور پر مقرر کرنا اب بھی بالکل دستاویز کے مطابق کام کرتا ہے۔ واضح بائٹ بجٹ اوور رائیڈز کو 8 MiB–2 GiB تک محدود کیا جاتا ہے۔ `413 body_exceeds_budget` عارضی نہیں ہے: اس بائٹ بجٹ کو بڑھائیں، `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` کو کم کریں، یا پراسیس کی میموری حد بڑھائیں۔ `inflight_bytes_budget` کی وجہ سے لوڈ کم کرنا عارضی تنازع ہے اور اس پر دوبارہ کوشش کی جا سکتی ہے۔ فی فراہم کنندہ شرح کی حد بندی (`open-sse/services/rateLimitManager.ts`) کو علیحدہ طور پر `RATE_LIMIT_MAX_WAIT_MS`، `RATE_LIMIT_MAX_QUEUE_DEPTH`، اور `RATE_LIMIT_AUTO_ENABLE` کنٹرول کرتے ہیں — `.env.example` دیکھیں۔

**یہ کیسے تصدیق کریں کہ یہ کام کر رہا ہے**: اپنے agent/cron کو تیزی سے لگاتار دو بار چلائیں اور تصدیق کریں کہ دونوں بار کامیابی ہوتی ہے۔ اصلاح سے پہلے، دوسری بار چلانے پر عموماً `429`/`401` کی خرابی آتی ہے۔ اصلاح کے بعد، ناکامیوں (اگر کوئی ہوں) پر پسِ پردہ خودکار طور پر دوبارہ کوشش کی جاتی ہے اور کال مکمل ہو جاتی ہے۔ آپ `curl /monitoring/health` بھی چلا سکتے ہیں اور provider کنکشنز پر `rateLimitedUntil` فیلڈ، نیز متاثرہ providers کے لیے `circuitBreakers.providerBreakers[].state` کو مانیٹر کر سکتے ہیں — حالت `CLOSED`، `DEGRADED`، `OPEN`، یا `HALF_OPEN` میں سے ایک ہوتی ہے (`src/shared/utils/circuitBreaker.ts` دیکھیں)، اور مسلسل ناکام ہونے والا provider، reset window کے probe کو گزرنے کی اجازت دینے سے پہلے، `CLOSED → DEGRADED → OPEN` میں تبدیل ہو جائے گا (`HALF_OPEN`)۔

**اگر آپ کو اب بھی 429 نظر آئے**: اس provider کے فعال account کا _quota_ واقعی ختم ہو چکا ہے (صرف rate کی حد نہیں)۔ OmniRoute dashboard → Providers → Accounts میں اسی provider کے لیے دوسرا account شامل کریں، یا کوئی دوسرا مفت provider شامل کریں (مثلاً `routeway`، `auggie`)۔ Rotation صرف عارضی rate/400/401 مسائل میں مدد دیتی ہے؛ quota مکمل طور پر ختم ہونے کی صورت میں دوسری credential یا مختلف provider درکار ہوتا ہے۔

**اگر vision models (`auto/vision`، `bazaarlink/*`) پر 403 نظر آئے**: منسلک account کے پاس ایسا paid plan نہیں ہے جس میں vision شامل ہو، یا API key کے permissions ناکافی ہیں۔ provider dashboard میں تصدیق کریں کہ key scope میں vision/multimodal شامل ہے، یا paid tier account منسلک کریں اور اسے vision target کے طور پر برقرار رکھیں۔

## npm install کی تنبیہات (ERESOLVE / peer / deprecated)

جب آپ `npm install -g omniroute` چلاتے ہیں، تو آپ کو `npm warn ERESOLVE`، peer-dependency اطلاعات، اور `deprecated` پیغامات جیسی تنبیہات کی ایک طویل فہرست نظر آ سکتی ہے۔ **یہ متوقع اور بے ضرر ہیں۔** اگر آؤٹ پٹ میں `added <N> packages` نظر آئے تو آپ کی تنصیب کامیاب ہو گئی ہے۔

peer-dependency ریزولیوشن کی تنبیہات کو دبانے کے لیے، OmniRoute کا معاونت یافتہ تنصیبی طریقہ استعمال کریں:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` صرف `ERESOLVE` اور peer-dependency اطلاعات کو دباتا ہے۔ فرسودگی کی اطلاعات نظر آتی رہتی ہیں کیونکہ وہ بالواسطہ فریق ثالث پیکیجز سے آتی ہیں؛ وہ اس بات کی نشاندہی نہیں کرتیں کہ تنصیب ناکام ہو گئی ہے۔

یہ تنبیہات ان فریق ثالث پیکیجز میں پرانی peer-dependency حدود کی وجہ سے آتی ہیں جنہیں OmniRoute کنٹرول نہیں کرتا:

1. **`marked-terminal` کو `marked >=1 <16` درکار ہے، مگر `marked@18` ملا** — عملی طور پر یہ ٹھیک کام کرتا ہے؛ upstream peer حد صرف پرانی ہے۔
2. **`deprecated prebuild-install@7.1.3`** — مقامی بائنری حاصل کرنے کے لیے ایک بالواسطہ معاون۔ اسے
   پن شدہ `wreq-js` ٹرانسپورٹ بائنڈنگ انسٹال کرنے کے لیے استعمال نہیں کیا جاتا اور یہ اس بات کی
   نشاندہی نہیں کرتا کہ web-cookie پرووائیڈر ٹرانسپورٹ سیٹ اپ ناکام ہو گیا ہے۔

**کسی کارروائی کی ضرورت نہیں** — upstream پیکیجز کو fork کیے بغیر ان تنبیہات کو مکمل طور پر خاموش نہیں کیا جا سکتا۔

## npm install-scripts بلاک ہونے کی تنبیہ (عالمی تنصیب)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

`npm install -g omniroute` چلاتے وقت، npm کے نئے ورژن (v11+ اور v12+) بطور ڈیفالٹ پیکیج lifecycle اسکرپٹس کو بلاک کرتے ہیں اور install-scripts کی تنبیہ دکھاتے ہیں:

```
npm warn install-scripts 7 پیکیجز کے install scripts بلاک کر دیے گئے کیونکہ وہ allowScripts میں شامل نہیں ہیں:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### کیا اس تنبیہ کو نظر انداز کیا جا سکتا ہے؟

**جزوی طور پر، لیکن اسکرپٹس کے بغیر چلانے کی سفارش نہیں کی جاتی۔** OmniRoute میں مناسب fallback موجود ہیں: اگر مقامی `better-sqlite3` بائنڈنگز کو standalone بنڈل سے لوڈ نہ کیا جا سکے، تو ایپلیکیشن `node:sqlite` یا `sql.js` جیسے متبادل ڈرائیورز استعمال کرتی ہے ([SQLite رن ٹائم ریزولیوشن](../ops/SQLITE_RUNTIME.md) دیکھیں)۔ سرور پھر بھی شروع ہو جائے گا، لیکن `sql.js` جیسے WASM fallbacks پر چلانے سے SQLite WAL (Write-Ahead Logging) موڈ غیر فعال ہو جاتا ہے اور میموری و disk-sync کا اضافی بوجھ بڑھ جاتا ہے۔

### درحقیقت کن اسکرپٹس کی ضرورت ہے؟

تمام بلاک شدہ اسکرپٹس OmniRoute چلانے کے لیے ضروری نہیں ہیں:

- **ضروری (`omniroute`، `better-sqlite3`):** OmniRoute ایک Next.js standalone ایپلیکیشن بنڈل (`dist/`) سے چلتا ہے۔ تنصیب کے دوران، npm اعلیٰ سطح کے `node_modules/better-sqlite3/` میں میزبان کے لیے مخصوص مقامی SQLite ڈرائیور ڈاؤن لوڈ یا کمپائل کرتا ہے۔ پھر OmniRoute کا `postinstall` اسکرپٹ (`scripts/build/postinstall.mjs`) میزبان کے لیے مخصوص ان بائنریز کی تصدیق کرتا ہے اور انہیں `dist/node_modules/` میں کاپی کرتا ہے تاکہ standalone سرور ان تک رسائی حاصل کر سکے۔ اگر `omniroute` کا postinstall اسکرپٹ بلاک ہو تو کاپی کرنے کا یہ مرحلہ چھوڑ دیا جاتا ہے۔
- **اختیاری/بالواسطہ (`keytar`، `@parcel/watcher`، `@swc/core`، `protobufjs`، `esbuild`):** یہ build معاونین، watcher ٹولز، یا سسٹم keychain یوٹیلیٹیز ہیں۔ انہیں اجازت دینے سے build تنبیہات رک جاتی ہیں، لیکن بنیادی routing فعالیت کے لیے ان کی ضرورت نہیں ہے۔
- **خارج شدہ (`onnxruntime-node`):** مقامی AI embeddings کے لیے ایک اختیاری dependency ہے اور OmniRoute چلانے کے لیے **ضروری نہیں** ہے۔ اس کا postinstall اسکرپٹ NuGet سے تقریباً 300MB کے CUDA اثاثے ڈاؤن لوڈ کرتا ہے؛ اسے allow-list میں شامل نہ کریں، الا یہ کہ آپ معاونت یافتہ ہارڈویئر پر واضح طور پر مقامی ONNX acceleration استعمال کرنا چاہتے ہوں۔

### تجویز کردہ حل

عالمی تنصیب کے دوران مطلوبہ install scripts کی اجازت دینے اور تنبیہات کو خاموش کرنے کے لیے، OmniRoute اور اس کی مقامی dependencies کے لیے `--allow-scripts` فراہم کریں:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

متبادل طور پر، اپنے صارف اکاؤنٹ پر تمام عالمی تنصیبات کے لیے اسے مستقل طور پر ترتیب دینے کے لیے:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### اپنی تنصیب کی تصدیق کریں

تنصیب کے بعد، یہ یقینی بنانے کے لیے بلٹ اِن تشخیصی ٹول چلائیں کہ مقامی بائنڈنگز اور رن ٹائم ماحول درست حالت میں ہیں:

```bash
omniroute doctor
```

## Gemini Web اور Playwright Chromium

اگر Gemini Web کی کوئی درخواست `503` واپس کرے اور پیغام دے کہ Playwright Chromium
انسٹال نہیں ہے، تو npm پیکیج موجود ہے لیکن براؤزر بائنری غائب ہے۔
Playwright جان بوجھ کر براؤزر ڈاؤن لوڈز کو npm پیکیج کی
انسٹالیشن سے الگ رکھتا ہے، اس لیے براؤزر انسٹال ہونے تک یہ جواب متوقع ہے۔

عالمی npm انسٹالیشن کے لیے، OmniRoute پیکیج کی
ڈائریکٹری سے Chromium انسٹال کریں تاکہ براؤزر کیش اسی Playwright انسٹالیشن سے منسلک ہو:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

انسٹالیشن کے بعد OmniRoute کو دوبارہ شروع کریں، پھر Gemini Web کی درخواست دوبارہ آزمائیں۔ اگر آپ
OmniRoute کو Docker امیج سے چلاتے ہیں، تو `-web` امیج (یا `runner-web`
بلڈ ٹارگٹ) استعمال کریں، جس میں Chromium اور اس کی dependencies شامل ہیں؛ بنیادی امیج میں
یہ شامل نہیں ہیں۔

## اینٹی وائرس کے غلط مثبت نتائج

<a name="antivirus-false-positives"></a>

### Avast/AVG، `README.md` کو `MD:HttpRequest-inf[Susp]` کے ساتھ قرنطینہ کر دیتا ہے

**یہ ایک غلط مثبت نتیجہ ہے۔ کوئی چیز متاثر نہیں ہے، اور کسی کارروائی کی ضرورت نہیں ہے۔**

Avast اور AVG ایک ایسا ہیورسٹک چلاتے ہیں جو ان سادہ متن/Markdown فائلوں کو نشان زد کرتا ہے جن میں
HTTP درخواستوں جیسے نظر آنے والے بہت سے لنکس موجود ہوں۔ OmniRoute کی `README.md`، npm پیکیج کے اندر شامل ہوتی ہے (یہ
`package.json` → `files` میں درج ہے)، اس لیے گلوبل انسٹالیشن پر یہ `node_modules/omniroute/README.md` میں
آتی ہے — اور اس میں تقریباً 15 `http://localhost:20128/...` مثالیں موجود ہیں (MCP کے
HTTP/SSE اینڈ پوائنٹس، A2A کا `.well-known` URL، اور `curl` کے اقتباسات)۔ لنکس کی یہ کثافت
ہیورسٹک کو متحرک کرنے کے لیے کافی ہے۔

اگر یہ مسئلہ حال ہی میں شروع ہوا ہے: تو فائل کی نوعیت تبدیل نہیں ہوئی۔ README میں
اینڈ پوائنٹس کی جدول بڑھی ہے (MCP HTTP + SSE + A2A شامل کیے گئے) اور مزید `curl` مثالیں شامل ہوئی ہیں، جس سے
یہ حد سے تجاوز کر گئی۔

یہ فائل غیر فعال دستاویزات پر مشتمل ہے اور اس میں کوئی قابلِ عمل مواد نہیں ہے۔ آپ اسے بحفاظت
قرنطینہ سے بحال کر سکتے ہیں۔

**کیا کرنا ہے:**

1. **اطلاعات روکیں** — اپنے اینٹی وائرس میں انسٹالیشن ڈائریکٹری کو خارج کر دیں
   (Avast: Settings → Exceptions)، اور اپنی گلوبل `node_modules` پاتھ اور/یا
   OmniRoute ڈیٹا ڈائریکٹری (`~/.omniroute/`) شامل کریں۔
2. **غلط مثبت نتیجے کی اطلاع دیں** — <https://www.avast.com/false-positive-file-form.php>،
   اور قرنطینہ کی گئی `README.md` منسلک کریں۔ یہی وہ حل ہے جو سب کی مدد کرتا ہے، کیونکہ یہ
   وینڈر کا ہیورسٹک ہے جو ایک ٹیکسٹ فائل پر حد سے زیادہ ردِعمل دکھا رہا ہے۔

**ہم اپنی جانب سے اسے "ٹھیک" کیوں نہیں کرتے:** تمام مثالیں `http://localhost` ہیں، اور
خود دستخط شدہ سرٹیفکیٹ کی پیچیدگی کے بغیر localhost کو `https` نہیں بنایا جا سکتا۔ صرف ایک
وینڈر کے ہیورسٹک سے بچنے کے لیے دستاویزات کو بگاڑنا، اسکینر کی خرابی کو مطمئن کرنے کی خاطر ہر قاری کے لیے مشکلات پیدا کرے گا۔

### Kaspersky، Desktop ایپ کو `PDM:Trojan.Win32.Generic` کے طور پر نشان زد کرتا ہے

**یہ طرزِ عمل پر مبنی ہیورسٹک کا ایک غلط مثبت نتیجہ ہے۔ کوئی چیز متاثر نہیں ہے۔** Kaspersky کا
`PDM:` سابقہ ظاہر کرتا ہے کہ یہ فیصلہ اس کے Proactive Defense Module (System Watcher) سے آیا ہے،
جو معروف میل ویئر سے مماثلت تلاش کرنے کے بجائے یہ جانچتا ہے کہ انسٹالر _کیا کرتا ہے_۔ جب
یہ متحرک ہوتا ہے، تو Kaspersky پوری انسٹالیشن کو "رول بیک" کر دیتا ہے — اور وہ فائلیں حذف کر دیتا ہے جو یہ پہلے ہی
لکھ چکا ہوتا ہے — لہٰذا ایپ خراب ہو جاتی ہے یا غائب ہو جاتی ہے۔

اس کی نشان زد کردہ فائلیں، Desktop ایپ کے ساتھ بنڈل کردہ، واضح طور پر درج اوپن سورس dependencies کے معیاری حصے ہیں، مثلاً:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` اور
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)، براؤزر آٹومیشن
  لائبریری جو ایپ کے اندر پرووائیڈر لاگ اِن اور براؤزر پر مبنی چیٹ کے لیے استعمال ہوتی ہے۔
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — مقررہ `wreq-js` نیٹو بائنڈنگ جو ویب کوکی
  پرووائیڈرز پر براؤزر فنگرپرنٹڈ HTTP کے لیے استعمال ہوتی ہے (`<arch>`، `x64` یا `arm64` ہوتا ہے)۔

**یہ کیوں متحرک ہوتا ہے:** Windows انسٹالر پر **ابھی تک کوڈ سائن نہیں کیا گیا**، اس لیے بغیر دستخط والے NSIS
انسٹالر کی کوئی ساکھ نہیں ہوتی اور طرزِ عمل پر مبنی ہیورسٹکس انتہائی جارحانہ انداز میں کام کرتے ہیں۔ اس کے ساتھ
بنڈل شدہ نیٹو DLL اور `%LOCALAPPDATA%\Programs\OmniRoute` کے تحت لکھی جانے والی سیکڑوں `.js` فائلیں
(جن میں Next.js standalone build سے hash-suffixed پیکیج ڈائریکٹریاں بھی شامل ہیں)،
ہیورسٹک کو متحرک کرنے کے لیے کافی ہیں۔ کوڈ سائننگ کا منصوبہ موجود ہے؛
اس کے نفاذ تک نئی ریلیزز میں یہ مسئلہ دوبارہ پیش آ سکتا ہے۔

**کیا کرنا ہے:**

1. **پہلے اپنے ڈاؤن لوڈ کی تصدیق کریں** (اس سے فائل میں چھیڑ چھاڑ کا امکان خارج ہو جاتا ہے)۔ ہر ریلیز
   `latest.yml` شائع کرتی ہے، جس کا `sha512` فیلڈ (base64)، `OmniRoute.Setup.<version>.exe`
   انسٹالر کا احاطہ کرتا ہے۔ PowerShell میں، انسٹالر والی ڈائریکٹری سے:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   آؤٹ پٹ کا `latest.yml` → `sha512` سے مماثل ہونا ضروری ہے۔ اگر مماثلت نہ ہو تو فائل حذف کریں اور
   صرف [GitHub ریلیزز کے صفحے](https://github.com/diegosouzapw/OmniRoute/releases) سے دوبارہ ڈاؤن لوڈ کریں۔
2. **بحال کریں + خارج کریں** — رول بیک کی گئی اشیا کو قرنطینہ سے بحال کریں اور
   `%LOCALAPPDATA%\Programs\OmniRoute` کے لیے ایک exclusion شامل کریں (Kaspersky → Settings → Threats and Exclusions)،
   پھر دوبارہ انسٹال کریں۔
3. **غلط مثبت نتیجے کی اطلاع دیں** — <https://opentip.kaspersky.com/>۔ صارفین کی جانب سے جمع کرائی گئی FP
   رپورٹس واقعی allowlisting کو تیز کرتی ہیں۔

## Node.js مطابقت

<a name="nodejs-compatibility"></a>

### لاگ اِن صفحہ کریش ہو جاتا ہے یا "Module self-registration" خرابی دکھاتا ہے

**وجہ:** آپ Node.js کا ایسا ورژن چلا رہے ہیں جو OmniRoute کی منظور شدہ محفوظ رن ٹائم کی کم از کم حد سے باہر ہے۔ عام ترین صورت یہ ہے کہ Node 22 یا 24 کا کوئی پرانا پیچ لیول استعمال کیا جا رہا ہو جو OmniRoute کی مطلوبہ پیچ شدہ سیکیورٹی حد سے کم ہو۔

**علامات:**

- لاگ اِن صفحہ خالی اسکرین یا سرور کی خرابی دکھاتا ہے
- کنسول میں `Error: Module did not self-register` یا اس جیسی نیٹو بائنڈنگ کی خرابیاں دکھائی دیتی ہیں
- اگر رن ٹائم معاونت یافتہ محفوظ پالیسی سے باہر ہو تو لاگ اِن صفحہ آپ کے Node ورژن کے ساتھ ایک **نارنجی انتباہی بینر** دکھاتا ہے

**حل:**

1. Node.js کی معاونت یافتہ LTS ریلیز انسٹال کریں (تجویز کردہ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. اپنے ورژن کی تصدیق کریں: `node --version` کو 24.x LTS سلسلے میں `v24.0.0` یا اس سے نیا ورژن دکھانا چاہیے
3. OmniRoute دوبارہ انسٹال کریں: `npm install -g omniroute`
4. دوبارہ شروع کریں: `omniroute`

> **معاونت یافتہ محفوظ ورژنز:** `>=22.22.2 <23` یا `>=24.0.0 <27`۔ Node.js 24.x LTS (Krypton) اور Node.js 26 مکمل طور پر معاونت یافتہ ہیں۔

### npm v11+: `better-sqlite3` انسٹال نہیں ہوا (ماڈیول نہیں مل سکا)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**وجہ:** npm v11 (جو Node.js 24+ کے ساتھ فراہم ہوتا ہے) بطور ڈیفالٹ اختیاری
انحصارات کے انسٹال اسکرپٹس کو روکتا ہے۔ چونکہ `better-sqlite3` کو `optionalDependencies`
میں درج کیا گیا ہے اور اسے نیٹو کمپائلیشن (`node-gyp rebuild`) درکار ہے، اس لیے npm اسے خاموشی سے چھوڑ دیتا ہے۔

**علامات:**

- سرور آغاز کے وقت `Cannot find module 'better-sqlite3'` کے ساتھ کریش ہو جاتا ہے
- `ls node_modules/better-sqlite3` سے "No such file or directory" دکھائی دیتا ہے
- `npm ls better-sqlite3` سے `(empty)` دکھائی دیتا ہے

**حل:**

1. انسٹال اسکرپٹس کی منظوری دیں اور دوبارہ انسٹال کریں:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. یا پہلے سے تیار شدہ پیکیج دستی طور پر انسٹال کریں:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. تصدیق کریں کہ یہ کام کرتا ہے: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**وجہ:** عالمی `npm install -g omniroute` کے بعد، پیکیج کے اندر موجود `better-sqlite3` نیٹو بائنری ممکن ہے کسی ایسے مختلف آرکیٹیکچر یا Node.js ABI کے لیے کمپائل ہوئی ہو جو مقامی طور پر چلنے والے ماحول سے مطابقت نہ رکھتا ہو۔ macOS پر (Apple Silicon اور Intel دونوں میں) یہ عام بات ہے، جب پہلے سے تیار شدہ بائنری آپ کے ماحول سے مطابقت نہ رکھتی ہو۔

**علامات:**

- سرور آغاز کے فوراً بعد `dlopen` خرابی کے ساتھ ناکام ہو جاتا ہے
- خرابی میں `slice is not valid mach-o file` شامل ہوتا ہے
- مکمل مثال:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**حل — اپنے مقامی ماحول کے لیے دوبارہ تعمیر کریں (Node.js کا ورژن گھٹانے کی ضرورت نہیں):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **نوٹ:** یہ نیٹو بائنڈنگ کو آپ کے مقامی Node.js ورژن اور CPU آرکیٹیکچر کے مطابق دوبارہ کمپائل کرتا ہے، جس سے بائنری کی عدم مطابقت حل ہو جاتی ہے۔ باضابطہ طور پر معاونت یافتہ رن ٹائم رینج **`>=22.22.2 <23` یا `>=24.0.0 <27`** ہے (`src/shared/utils/nodeRuntimeSupport.ts` میں `SUPPORTED_NODE_RANGE`، جو `package.json` کے `engines` فیلڈ سے ہم آہنگ ہے)۔ Node.js 24.x LTS (Krypton) اور Node.js 26 کو `better-sqlite3` v12.x کے ساتھ مکمل معاونت حاصل ہے۔

## پراکسی کے مسائل

<a name="proxy-issues"></a>

### فراہم کنندہ کی توثیق میں "fetch failed" دکھائی دیتا ہے

**وجہ:** API کلید کی توثیق کا اینڈ پوائنٹ (`POST /api/providers/validate`) پہلے پراکسی کنفیگریشن کو نظرانداز کر رہا تھا، جس کی وجہ سے ایسے ماحول میں ناکامیاں ہو رہی تھیں جہاں پراکسی روٹنگ درکار ہوتی ہے۔

**حل (v3.5.5+):** اب یہ مسئلہ حل ہو چکا ہے۔ فراہم کنندہ کی توثیق `runWithProxyContext` کے ذریعے روٹ ہوتی ہے اور خودکار طور پر فراہم کنندہ کی سطح اور عالمی پراکسی ترتیبات کا لحاظ رکھتی ہے۔

### ٹوکن کی صحت کی جانچ "fetch failed" کے ساتھ ناکام ہو جاتی ہے

**وجہ:** پس منظر میں OAuth ٹوکن ریفریش ہر کنکشن کے لیے پراکسی کنفیگریشن کو حل نہیں کر رہا تھا۔

**حل (v3.5.5+):** ٹوکن کی صحت کی جانچ کا شیڈیولر اب ریفریش کی کوشش سے پہلے ہر کنکشن کے لیے پراکسی کنفیگ کو حل کرتا ہے۔ v3.5.5+ پر اپ ڈیٹ کریں۔

### SOCKS5 پراکسی "invalid onRequestStart method" لوٹاتی ہے

**وجہ:** Node.js 22 پر، undici@8 ڈسپیچر Node کے بلٹ اِن `fetch()` نفاذ کے ساتھ غیر موافق ہے۔

**حل (v3.5.5+):** جب پراکسی ڈسپیچر فعال ہو تو OmniRoute اب undici کا اپنا `fetch()` فنکشن استعمال کرتا ہے، جس سے یکساں رویہ یقینی بنتا ہے۔ v3.5.5+ پر اپ ڈیٹ کریں۔

### WSL کے تحت MITM پراکسی: Windows ہوسٹ پر موجود ڈیسک ٹاپ ایپس انٹرسیپٹ نہیں ہوتیں

**وجہ:** MITM پراکسی اور اس کا CA سرٹیفکیٹ اسی ماحول میں انسٹال ہوتے ہیں جہاں OmniRoute چلتا ہے۔ WSL کے تحت یہ ماحول Linux گیسٹ ہوتا ہے، جبکہ AI ڈیسک ٹاپ ایپس (Kiro، Trae، Copilot، Zed، …) Windows ہوسٹ پر چلتی ہیں۔ ہوسٹ ایپس گیسٹ کے سرٹیفکیٹ اسٹور پر اعتماد نہیں کرتیں اور گیسٹ کی سسٹم پراکسی کے ذریعے روٹ نہیں ہوتیں، اس لیے وہاں ڈیسک ٹاپ انٹرسیپشن فعال نہیں ہوتی۔

**تجویز:** OmniRoute کو مقامی طور پر اسی OS پر چلائیں جس پر وہ ڈیسک ٹاپ ایپس چل رہی ہیں جنہیں آپ انٹرسیپٹ کرنا چاہتے ہیں (Windows ایپس کے لیے Windows؛ اسی طرح macOS/Linux کے لیے متعلقہ OS)۔ ہوسٹ ایپس کو ہدف بناتے ہوئے OmniRoute کو WSL کے اندر رکھنے کے لیے Windows ہوسٹ پر تیار کردہ CA سرٹیفکیٹ کو دستی طور پر قابلِ اعتماد بنانا اور ہر ہوسٹ ایپ کی نیٹ ورک/پراکسی ترتیبات کو WSL پراکسی اینڈ پوائنٹ کی طرف متعین کرنا ضروری ہے — یہ ایک غیر معاون اور نازک سیٹ اپ ہے۔

## فراہم کنندہ کے مسائل

### "Language model did not provide messages"

**وجہ:** فراہم کنندہ کا کوٹا ختم ہو گیا ہے۔

**حل:**

2. فال بیک درجات والا کومبو استعمال کریں
3. کم قیمت/مفت درجے پر منتقل ہوں

### شرح کی حد بندی

**وجہ:** سبسکرپشن کا کوٹا ختم ہو گیا ہے۔

**حل:**

- فال بیک شامل کریں: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- سستے بیک اپ کے طور پر GLM/MiniMax استعمال کریں

### OAuth ٹوکن کی میعاد ختم ہو گئی

OmniRoute ٹوکنز کو خودکار طور پر ریفریش کرتا ہے۔ اگر مسائل برقرار رہیں:

1. ڈیش بورڈ → فراہم کنندہ → دوبارہ منسلک کریں
2. فراہم کنندہ کا کنکشن حذف کرکے دوبارہ شامل کریں

### Kiro ملٹی اکاؤنٹ: دوسرا اکاؤنٹ پہلے کو غیر معتبر کر دیتا ہے

**وجہ:** Kiro کا بیک اینڈ ہر OIDC کلائنٹ رجسٹریشن کے لیے صرف ایک فعال سیشن نافذ کرتا ہے۔
جب دو اکاؤنٹس ایک ہی رجسٹرڈ کلائنٹ کا اشتراک کرتے ہیں (یعنی v3.8.0 سے پہلے درآمد کیے گئے کنکشنز)،
تو ایک اکاؤنٹ کے ٹوکن کو ریفریش کرنے سے دوسرے اکاؤنٹ کا ریفریش ٹوکن غیر معتبر ہو جاتا ہے۔

**حل (v3.8.0+):** متاثرہ کنکشنز کو دوبارہ درآمد کریں۔
v3.8.0 سے شروع کرتے ہوئے، **Import Token**،
**Google/GitHub social login**، یا **Auto-Import** کے ذریعے بنایا گیا ہر نیا Kiro کنکشن خودکار طور پر اپنا
مخصوص OIDC کلائنٹ رجسٹر کرتا ہے۔ اس طرح کنکشن مکمل طور پر الگ تھلگ رہتا ہے اور ایک
اکاؤنٹ کو ریفریش کرنے سے کسی دوسرے اکاؤنٹ پر کوئی اثر نہیں پڑتا۔

وہ کنکشنز جو v3.8.0 سے _پہلے_ درآمد کیے گئے تھے، فی کنکشن کلائنٹ
رجسٹریشن نہیں رکھتے۔ وہ کنکشنز مشترکہ سوشل آتھ ریفریش اینڈ پوائنٹ کا استعمال جاری رکھتے ہیں۔
الگ تھلگ کرنے کے لیے، ڈیش بورڈ → فراہم کنندگان سے پرانا کنکشن حذف کریں اور اسے

## کلاؤڈ کے مسائل

### کلاؤڈ سنک کی خرابیاں

1. تصدیق کریں کہ `BASE_URL` آپ کی چلتی ہوئی انسٹینس کی طرف اشارہ کرتا ہے (مثلاً، `http://localhost:20128`)
2. تصدیق کریں کہ `CLOUD_URL` آپ کے کلاؤڈ اینڈ پوائنٹ کی طرف اشارہ کرتا ہے (مثلاً، `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` کی قدروں کو سرور سائیڈ کی قدروں کے مطابق رکھیں

### کلاؤڈ میں `stream=false` سے 500 موصول ہوتا ہے

**علامت:** نان اسٹریمنگ کالز کے لیے کلاؤڈ اینڈ پوائنٹ پر `Unexpected token 'd'...`۔

**وجہ:** اپ اسٹریم SSE پے لوڈ واپس کرتا ہے جبکہ کلائنٹ JSON کی توقع کرتا ہے۔

**عارضی حل:** کلاؤڈ پر براہِ راست کالز کے لیے `stream=true` استعمال کریں۔ مقامی رن ٹائم میں SSE→JSON فال بیک شامل ہے۔

### کلاؤڈ منسلک دکھاتا ہے لیکن "Invalid API key"

1. مقامی ڈیش بورڈ (`/api/keys`) سے نئی کلید بنائیں
2. کلاؤڈ سنک چلائیں: کلاؤڈ فعال کریں → ابھی سنک کریں
3. پرانی یا غیر سنک شدہ کلیدیں اب بھی کلاؤڈ پر `401` واپس کر سکتی ہیں

## Docker کے مسائل

### Docker IPv6 / کنکشن ری سیٹ

<a name="docker-ipv6"></a>

**علامات:** `curl http://localhost:20128/v1/models` سے `curl: (56) Recv failure: Connection reset by peer` واپس آتا ہے۔ ڈیش بورڈ اور بغیر تصدیق والے اینڈ پوائنٹس کام کرتے ہیں، لیکن تصدیق شدہ اینڈ پوائنٹس ناکام ہو جاتے ہیں — یہ تصدیق کا مسئلہ نظر آتا ہے، مگر ایسا نہیں ہے۔

**وجہ:** `docker run -p 20128:20128` پورٹ کو `0.0.0.0` (IPv4) اور `::` (IPv6) دونوں پر شائع کرتا ہے، لیکن کنٹینر کے اندر موجود پراسیس صرف IPv4 پر سنتا ہے۔ ایسے ہوسٹس پر جہاں `localhost` پہلے `::1` میں ریزولو ہوتا ہے، کنکشن IPv6 کی شائع شدہ پورٹ پر پہنچتا ہے جس کے پیچھے کوئی لسنر موجود نہیں ہوتا → کنکشن ری سیٹ ہو جاتا ہے۔

**حل:**

1. **فوری تشخیص:** `curl -4 http://localhost:20128/v1/models` چلائیں۔ اگر یہ `-4` کے ساتھ کام کرے لیکن اس کے بغیر ناکام ہو، تو آپ کے پاس IPv6 بائنڈ کی عدم مطابقت ہے۔
2. **مستقل حل:** اپنی `docker run` کمانڈ میں `-p 127.0.0.1:20128:20128` استعمال کر کے واضح طور پر IPv4 سے بائنڈ کریں:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   اس سے IPv4 بائنڈ لازمی ہو جاتا ہے اور پراکسی کو ہوسٹ کے تمام انٹرفیسز پر ظاہر ہونے سے بھی روکا جاتا ہے۔

### CLI ٹول انسٹال شدہ نہیں دکھاتا

1. رن ٹائم فیلڈز چیک کریں: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`


## ڈی بگنگ

### لاگ فائلیں فعال کریں

اپنی `.env` فائل میں `APP_LOG_TO_FILE=true` سیٹ کریں۔ ایپلیکیشن لاگز `logs/` کے تحت لکھے جاتے ہیں۔
جب ترتیبات میں کال لاگ پائپ لائن فعال ہو تو درخواست کے آرٹی فیکٹس `${DATA_DIR}/call_logs/` کے تحت محفوظ کیے جاتے ہیں۔
جب پائپ لائن کیپچر فعال ہو تو اسٹریم چنک پے لوڈز کو شامل نہ کرنے کے لیے `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` سیٹ کریں، یا آرٹی فیکٹ کی حد KB میں تبدیل کرنے کے لیے `CALL_LOG_PIPELINE_MAX_SIZE_KB` کو ایڈجسٹ کریں۔

### فراہم کنندہ کی صحت چیک کریں

```bash
# صحت کا ڈیش بورڈ
http://localhost:20128/dashboard/health

# API صحت کی جانچ
curl http://localhost:20128/api/monitoring/health
```

### رن ٹائم اسٹوریج

- مرکزی حالت: `${DATA_DIR}/storage.sqlite` (فراہم کنندگان، کومبوز، عرف، کلیدیں، ترتیبات)
- استعمال: `storage.sqlite` میں SQLite ٹیبلز (`usage_history`، `call_logs`، `proxy_logs`) + اختیاری `${DATA_DIR}/call_logs/`
- ایپلیکیشن لاگز: `<repo>/logs/...` (جب `APP_LOG_TO_FILE=true` ہو)
- کال لاگ آرٹی فیکٹس: کال لاگ پائپ لائن فعال ہونے پر `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

درخواست لاگز کے صفحے پر **ہسٹری صاف کریں** کی کارروائی `call_logs`، سابقہ
`request_detail_logs`، اور مقامی `${DATA_DIR}/call_logs/` آرٹی فیکٹ ڈائریکٹری کو صاف کر دیتی ہے۔

## سرکٹ بریکر کے مسائل

### فراہم کنندہ OPEN حالت میں پھنسا ہوا ہے

جب کسی فراہم کنندہ کا سرکٹ بریکر OPEN ہو، تو کول ڈاؤن کی مدت ختم ہونے تک درخواستیں مسدود رہتی ہیں۔

**حل:**

1. **ڈیش بورڈ → ترتیبات → لچک پذیری** پر جائیں
2. متاثرہ فراہم کنندہ کا سرکٹ بریکر کارڈ دیکھیں
3. تمام بریکرز صاف کرنے کے لیے **سب ری سیٹ کریں** پر کلک کریں، یا کول ڈاؤن ختم ہونے کا انتظار کریں
4. ری سیٹ کرنے سے پہلے تصدیق کریں کہ فراہم کنندہ واقعی دستیاب ہے

### فراہم کنندہ بار بار سرکٹ بریکر کو ٹرپ کرتا ہے

اگر کوئی فراہم کنندہ بار بار OPEN حالت میں چلا جاتا ہے:

1. ناکامی کے پیٹرن کے لیے **ڈیش بورڈ → صحت → فراہم کنندہ کی صحت** دیکھیں
2. **ترتیبات → لچک پذیری → فراہم کنندہ پروفائلز** پر جائیں اور ناکامی کی حد بڑھائیں
3. چیک کریں کہ آیا فراہم کنندہ نے API کی حدود تبدیل کی ہیں یا دوبارہ توثیق درکار ہے
4. تاخیر کی ٹیلی میٹری کا جائزہ لیں — زیادہ تاخیر ٹائم آؤٹ پر مبنی ناکامیوں کا سبب بن سکتی ہے

### فارمیٹ کے عام مسائل

- **تھنکنگ ٹیگز ظاہر نہیں ہو رہے** — چیک کریں کہ آیا ہدف فراہم کنندہ تھنکنگ اور تھنکنگ بجٹ کی ترتیب کی معاونت کرتا ہے
- **ٹول کالز غائب ہو رہی ہیں** — بعض فارمیٹ تبدیلیاں غیر معاون فیلڈز کو ہٹا سکتی ہیں؛ پلے گراؤنڈ موڈ میں تصدیق کریں
- **سسٹم پرامپٹ غائب ہے** — Claude اور Gemini سسٹم پرامپٹس کو مختلف انداز میں سنبھالتے ہیں؛ ترجمے کا آؤٹ پٹ چیک کریں
- **SDK آبجیکٹ کے بجائے خام اسٹرنگ واپس کرتا ہے** — v1.x میں حل کر دیا گیا؛ رسپانس سینیٹائزر غیر معیاری فیلڈز (`x_groq`، `usage_breakdown` وغیرہ) کو ہٹا دیتا ہے جو OpenAI SDK کی Pydantic توثیق میں ناکامیوں کا سبب بنتی ہیں۔ اگر v3.x+ پر بھی یہ مسئلہ نظر آئے تو براہ کرم ایک ایشو درج کریں۔
- **GLM/ERNIE، `system` رول کو مسترد کرتا ہے** — v1.x میں حل کر دیا گیا؛ رول نارملائزر غیر موافق ماڈلز کے لیے سسٹم پیغامات کو خودکار طور پر صارف کے پیغامات میں ضم کر دیتا ہے۔ اگر v3.x+ پر بھی یہ مسئلہ نظر آئے تو براہ کرم ایک ایشو درج کریں۔
- **`developer` رول شناخت نہیں ہوتا** — v1.x میں حل کر دیا گیا؛ غیر OpenAI فراہم کنندگان کے لیے خودکار طور پر `system` میں تبدیل کر دیا جاتا ہے۔ اگر v3.x+ پر بھی یہ مسئلہ نظر آئے تو براہ کرم ایک ایشو درج کریں۔
- **`json_schema`، Gemini کے ساتھ کام نہیں کر رہا** — v1.x میں حل کر دیا گیا؛ اب `response_format` کو Gemini کے `responseMimeType` + `responseSchema` میں تبدیل کیا جاتا ہے۔ اگر v3.x+ پر بھی یہ مسئلہ نظر آئے تو براہ کرم ایک ایشو درج کریں۔

## لچک پذیری کی ترتیبات

### خودکار شرحِ حد فعال نہ ہونا

- خودکار شرحِ حد صرف API کلید فراہم کنندگان پر لاگو ہوتی ہے (OAuth/سبسکرپشن پر نہیں)
- تصدیق کریں کہ **Settings → Resilience → Provider Profiles** میں خودکار شرحِ حد فعال ہے
- جانچیں کہ آیا فراہم کنندہ `429` اسٹیٹس کوڈز یا `Retry-After` ہیڈرز واپس کرتا ہے

### ایکسپونینشل بیک آف کی ٹیوننگ

فراہم کنندہ پروفائلز ان ترتیبات کی معاونت کرتے ہیں:

- **بنیادی تاخیر** — پہلی ناکامی کے بعد ابتدائی انتظار کا وقت (طے شدہ: 1s)
- **زیادہ سے زیادہ تاخیر** — انتظار کے وقت کی زیادہ سے زیادہ حد (طے شدہ: 30s)
- **ضارب** — ہر مسلسل ناکامی پر تاخیر میں کتنا اضافہ کیا جائے (طے شدہ: 2x)

### تھنڈرنگ ہرڈ کی روک تھام

جب متعدد ہم وقت درخواستیں شرحِ حد کے شکار فراہم کنندہ تک پہنچتی ہیں، تو OmniRoute درخواستوں کو سلسلہ وار کرنے اور پے در پے ناکامیوں کو روکنے کے لیے mutex + خودکار شرحِ حد استعمال کرتا ہے۔ API کلید فراہم کنندگان کے لیے یہ خودکار ہے۔

### چیٹ درخواستیں 503 / chat_admission_busy کے ساتھ ناکام ہوتی ہیں

**علامات:**

- چیٹ کمپلیشنز اینڈ پوائنٹ دوبارہ کوشش کے قابل `503` جواب واپس کرتا ہے، جس کا نقص کوڈ
  `chat_admission_busy` ہوتا ہے۔
- جواب میں `Retry-After` شامل ہوتا ہے۔ #12135 کے بعد سے اس کی قدر مشاہدہ شدہ
  مصروفیت سے اخذ کی جاتی ہے — درخواست کے پہلے ہی انتظار کیے گئے `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` دورانیے
  اور موجودہ ہیوی ویٹ لیزز کے برقرار رہنے کے وقت میں سے بڑی قدر — جسے مکمل
  سیکنڈز تک اوپر کی جانب گول کیا جاتا ہے اور 60 پر محدود کیا جاتا ہے۔ غیر مصروف گیٹ پر یہ تاریخی کم از کم حدود برقرار رکھتا ہے: بائٹ پر مبنی
  راستے پر 2 سیکنڈ، اور ساخت پر مبنی راستے پر 1 سیکنڈ (جس میں
  `reason: "structure_limit"` بھی شامل ہوتا ہے)۔
- ایسا اس وقت ہو سکتا ہے جب کوئی اور ہیوی ویٹ چیٹ یا طویل عرصے تک چلنے والا اسٹریمنگ جواب اب بھی
  زیرِ عمل ہو۔

بائٹ پر مبنی جواب کی باڈی یہ ہے:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ساخت پر مبنی جواب اسی قسم اور کوڈ کو استعمال کرتا ہے، جبکہ پیغام
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
اور `reason: "structure_limit"` ہوتا ہے۔
طے شدہ حدود پر، کوئی درخواست ساختی طور پر بھاری سمجھی جاتی ہے جب اس میں کم از کم `200` پیغامات،
کم از کم `64` ٹولز، یا کم از کم `32,000` تخمینی ٹوکنز ہوں، یا جب محدود ساختی تخمینہ
`10,000` ملاحظہ کردہ نوڈز یا `12` گہرائی کی اپنی حدود ختم کر دے۔

**وجہ:** یہ OmniRoute کے اندر دانستہ لوڈ شیڈنگ ہے، نہ کہ اپ اسٹریم فراہم کنندہ کی ناکامی۔
ہر پراسیس ایک پراسیس-لوکل گارڈ استعمال کرتا ہے تاکہ بڑی درخواست کی باڈی کو برقرار رکھنے
اور پارس کرنے سے پہلے محدود ہیوی ویٹ گنجائش محفوظ کی جا سکے۔ ہیوی ویٹ لیز کسی SSE
جواب کی پوری مدت تک برقرار رہتی ہے۔

**#503-fanout:** اس اصلاح سے پہلے، گارڈ میزبان میموری سے قطع نظر ہم وقتی عمل کو درخواستوں کی ایک مقررہ تعداد
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`، طے شدہ `1`) تک محدود کرتا تھا، لہٰذا کوڈنگ ایجنٹ
فین آؤٹ (متعدد ذیلی ایجنٹس/CLIs، باڈیز معمول کے مطابق > 256 KB) مؤثر
ہم وقتی عمل کو تقریباً 1 تک گرا دیتا تھا اور مکمل طور پر معمول کے لوڈ میں 503 پیدا کرتا تھا۔ اب گارڈ خود کو ٹیون کرتا ہے: اسے
خودکار طور پر اخذ کردہ ان جیسٹ BYTE بجٹ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کے ذریعے کنٹرول کیا جاتا ہے، جس کا حجم
پراسیس کی حقیقی میموری حد سے متعین ہوتا ہے، اور یہ براہِ راست وسائل کے دباؤ کے سگنل سے بھی رجوع کرتا ہے — لہٰذا یہ
صرف تب لوڈ کم کرتا ہے جب میزبان حقیقی طور پر میموری کے دباؤ میں ہو، نہ کہ محض اس وجہ سے کہ ایک ہی وقت میں ایک سے زیادہ
بھاری درخواستیں آئیں۔ پرانی تعداد کی حد (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) کا
اب بھی احترام کیا جاتا ہے، مگر صرف اس صورت میں جب آپ اسے واضح طور پر مقرر کریں۔

جب گنجائش مصروف ہو، تو ایک ہیوی ویٹ درخواست پہلے کسی سلاٹ کے خالی ہونے کے لیے
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` تک انتظار کرتی ہے (طے شدہ قدر `RATE_LIMIT_MAX_WAIT_MS`؛ `0` انتظار غیر فعال کر دیتا ہے)
اور اس کے بعد دوبارہ کوشش کے قابل `503` جواب دیتی ہے۔ یہ محدود انتظار اس لیے موجود ہے کہ ایجنٹ طرز کے کلائنٹس
(OpenCode، Claude Code، Cursor)، جو بھاری ذیلی درخواستوں کو ہم وقت طور پر فین آؤٹ کرتے ہیں، برسٹ کو سلسلہ وار کریں
بجائے اس کے کہ فوری مسترد کیے جانے پر اپنا پورا دوبارہ کوشش کا بجٹ ختم کر دیں اور کام کے درمیان ناکام ہو جائیں۔
موجودہ ہیوی ویٹ لیز کی مصروفیت، طے شدہ بائٹ بجٹ، اور براہِ راست دباؤ کی شدت
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`، `maxInflightBytes`،
`budgetSource`، `pressureSeverity`، `countCapEnabled`) پر ظاہر کی جاتی ہیں — کسی بھی env var کو تبدیل کرنے سے پہلے انہیں جانچیں۔
Settings → Resilience → Request Queue → Concurrent Requests اسے کنٹرول نہیں کرتی؛ یہ ترتیب
فراہم کنندہ کی ایک الگ درخواست-قطار میکانزم کو کنٹرول کرتی ہے۔

**حل:**

1. پہلے دوبارہ کوشش کریں۔ کلائنٹس کو چاہیے کہ `Retry-After` کا احترام کریں اور درخواست کو فوراً
   دہرانے کے بجائے بیک آف استعمال کریں۔
2. کوئی بھی ٹیوننگ کرنے سے پہلے `/api/monitoring/health` → `chatAdmission` جانچیں۔ `countCapEnabled:
false` اور فراخ `maxInflightBytes` کا مطلب ہے کہ خودکار طور پر اخذ کردہ بجٹ پہلے ہی اپنا
   کام کر رہا ہے؛ `high`/`critical` کی `pressureSeverity` کا مطلب ہے کہ میزبان کے پاس واقعی میموری کم ہے —
   اسے کسی ایڈمیشن env var سے درست نہیں کیا جا سکتا، اس کے لیے زیادہ RAM یا کم ورک لوڈ درکار ہے۔
3. صرف اس صورت میں جب `/api/monitoring/health` دکھائے کہ خودکار طور پر اخذ کردہ بجٹ واقعی آپ کے
   میزبان کے لیے بہت کم ہے (ایسا شاذونادر ہوتا ہے — یہ پہلے ہی کنٹینر سے بیئر میٹل تک پیمانہ بندی کرتا ہے)، پرانی درخواست-تعداد کی حد کی طرف واپس جانے کے بجائے
   براہِ راست `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` کے ذریعے اسے اوور رائیڈ کریں۔

مستند ایڈمیشن ترتیبات کے لیے [ماحولیاتی متغیرات کا حوالہ](../reference/ENVIRONMENT.md#4-security--authentication)
دیکھیں۔

## اختیاری RAG / LLM ناکامیوں کی درجہ بندی (16 مسائل)

OmniRoute کے کچھ صارفین گیٹ وے کو RAG یا ایجنٹ اسٹیکس کے سامنے رکھتے ہیں۔ ایسی ترتیبات میں ایک عجیب صورتِ حال عام طور پر نظر آتی ہے: OmniRoute بظاہر درست حالت میں ہوتا ہے (فراہم کنندگان دستیاب، روٹنگ پروفائلز درست، شرح کی حد سے متعلق کوئی انتباہ نہیں) لیکن حتمی جواب پھر بھی غلط ہوتا ہے۔

عملی طور پر یہ واقعات عموماً خود گیٹ وے کے بجائے بعد کے مراحل میں موجود RAG پائپ لائن سے پیدا ہوتے ہیں۔

اگر آپ ان ناکامیوں کو بیان کرنے کے لیے مشترکہ اصطلاحات چاہتے ہیں تو WFGY ProblemMap استعمال کر سکتے ہیں، جو MIT لائسنس کے تحت ایک بیرونی متنی وسیلہ ہے اور RAG / LLM کی ناکامی کے بار بار پیش آنے والے سولہ نمونوں کی تعریف کرتا ہے۔ اعلیٰ سطح پر اس میں یہ شامل ہیں:

- بازیافت میں انحراف اور سیاق کی ٹوٹی ہوئی حدود
- خالی یا فرسودہ انڈیکسز اور ویکٹر اسٹورز
- ایمبیڈنگ اور معنوی مطابقت میں فرق
- پرامپٹ کی تشکیل اور سیاقی ونڈو کے مسائل
- منطق کا انہدام اور حد سے زیادہ پراعتماد جوابات
- طویل زنجیر اور ایجنٹ ہم آہنگی کی ناکامیاں
- متعدد ایجنٹس کی میموری اور کردار میں انحراف
- تعیناتی اور بوٹسٹریپ ترتیب کے مسائل

خیال سادہ ہے:

1. کسی خراب جواب کی تفتیش کرتے وقت یہ معلومات محفوظ کریں:
   - صارف کا کام اور درخواست
   - OmniRoute میں روٹ یا فراہم کنندگان کا مجموعہ
   - بعد کے مراحل میں استعمال ہونے والا کوئی بھی RAG سیاق (بازیافت شدہ دستاویزات، ٹول کالز وغیرہ)
2. واقعے کو WFGY ProblemMap کے ایک یا دو نمبروں (`No.1` … `No.16`) سے منسلک کریں۔
3. نمبر کو OmniRoute لاگز کے ساتھ اپنے ڈیش بورڈ، رن بُک، یا واقعہ ٹریکر میں محفوظ کریں۔
4. متعلقہ WFGY صفحہ استعمال کر کے فیصلہ کریں کہ آیا آپ کو اپنے RAG اسٹیک، ریٹریور، یا روٹنگ حکمتِ عملی میں تبدیلی کی ضرورت ہے۔

مکمل متن اور عملی ترکیبیں یہاں دستیاب ہیں (MIT لائسنس، صرف متن):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

اگر آپ OmniRoute کے پیچھے RAG یا ایجنٹ پائپ لائنز نہیں چلاتے تو اس حصے کو نظر انداز کر سکتے ہیں۔

## v3.8.0 کے معلوم مسائل

v3.8.0 ریلیز سے مخصوص مسائل اور ان کے موجودہ عارضی حل۔ اگر کسی بعد کے پیچ میں مسئلہ درست ہو جاتا ہے تو اس اندراج کو اپ ڈیٹ یا حذف کر دیا جائے گا۔

### Devin CLI کی توثیق کی ناکامیاں

**علامات:**

- Devin کی معاونت والے ٹولز استعمال کرتے وقت "Devin CLI نہیں ملا" یا "توثیق ناکام ہوئی"
- CLI رن ٹائم جانچ `installed=false` رپورٹ کرتی ہے

**وجوہات:**

- `CLI_DEVIN_BIN` ایک ایسے پاتھ کی طرف اشارہ کرتا ہے جو موجود نہیں
- میزبان پر Devin CLI انسٹال نہیں ہے

**حل:**

1. اپنے پلیٹ فارم کے لیے Devin CLI انسٹال کریں
2. `.env` میں `CLI_DEVIN_BIN=/usr/local/bin/devin` (یا حقیقی پاتھ) سیٹ کریں
3. OmniRoute دوبارہ شروع کریں اور **Dashboard → CLI Tools** سے دوبارہ جانچ کریں

### ماڈل کول ڈاؤن اٹکا ہوا ہے (دستی ری سیٹ)

**علامات:**

- اختتامی وقت گزر جانے کے بعد بھی کوئی ماڈل کول ڈاؤن میں درج رہتا ہے
- ٹائم اسٹیمپ ماضی کا ہونے کے باوجود مجموعی روٹنگ میں درخواستیں اب بھی ماڈل کو چھوڑ دیتی ہیں

**دستی ری سیٹ:**

- **ڈیش بورڈ:** **Settings → Model Cooldowns** → متاثرہ کارڈ پر **Re-enable** کلک کریں
- **API:** انتظامی توثیقی ہیڈرز کے ساتھ `DELETE /api/resilience/model-cooldowns`

### Command Code فراہم کنندہ کا کنکشن 403 کے ساتھ ناکام ہوتا ہے

**علامات:**

- Command Code فراہم کنندہ کے کنکشن کی جانچ کرتے وقت 403
- نیا شامل کرنے کے بعد فراہم کنندہ کا کارڈ "غیر مجاز" دکھاتا ہے

**وجہ:** OAuth کا عمل مکمل نہیں ہوا (کال بیک موصول نہیں ہوا یا ٹوکن محفوظ نہیں کیا گیا)۔

**حل:**

- OAuth کا عمل دوبارہ شروع کرنے کے لیے CLI سے `omniroute providers` چلائیں، یا
- **Dashboard → Providers → Command Code → Reconnect** سے OAuth دوبارہ چلائیں

### ModelScope جارحانہ 429 کول ڈاؤنز واپس کرتا ہے

**علامات:**

- درخواستوں کے مختصر سلسلے کے بعد ModelScope پر بہت مختصر یا فوری کول ڈاؤنز
- مجموعی روٹنگ توقع سے پہلے ModelScope کو چھوڑ دیتی ہے

**وجہ:** ModelScope فراہم کنندہ کے لیے مخصوص `Retry-After` ہیڈرز جاری کرتا ہے۔ v3.8.0 میں ان ہیڈرز کے لیے مخصوص ہینڈلنگ شامل ہے، اس لیے پرانے ورژنز انہیں شرح کی حد کے عمومی اشاروں کے طور پر غلط سمجھتے ہیں۔

**حل:**

- یقینی بنائیں کہ آپ v3.8.0 یا بعد کا ورژن استعمال کر رہے ہیں
- تصدیق کریں کہ **Settings → Resilience** کے تحت `useUpstream429BreakerHints` ٹوگل فعال ہے

### پروڈکشن میں OMNIROUTE_WS_BRIDGE_SECRET موجود نہیں

**علامات:**

- ریموٹ پروڈکشن میزبان پر چلتے وقت ہر Codex/Responses WebSocket برج درخواست پر 401
- کنیکٹ ہونے کے فوراً بعد WebSocket برج ہینڈ شیک بند ہو جاتا ہے

**وجہ:** پروڈکشن ماحول میں `OMNIROUTE_WS_BRIDGE_SECRET` ماحول متغیر موجود نہیں ہے۔

**حل:**

1. ایک بے ترتیب راز تیار کریں: `openssl rand -hex 32`
2. پروڈکشن سرور کے ماحول میں `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` سیٹ کریں (اور برج سے رابطہ کرنے والے ہر کلائنٹ میں بھی)
3. OmniRoute دوبارہ شروع کریں

### Responses API: پسِ منظر موڈ کو ہم وقتی بنا دیا گیا ہے

**علامات:**

- لاگ کیا گیا انتباہ: `background mode degraded to synchronous`
- `background: true` والی درخواست پسِ منظر جاب ہینڈل کے بجائے معمول کا ہم وقتی جواب واپس کرتی ہے

**وجہ:** v3.8.0 میں Responses API پر `background: true` کو دانستہ طور پر ہم وقتی عمل درآمد میں تبدیل کیا جاتا ہے اور ساتھ ایک انتباہ جاری کیا جاتا ہے۔ مکمل غیر ہم وقتی پسِ منظر عمل درآمد مستقبل میں فراہم کیا جائے گا۔

**حل:**

- کلائنٹ کو `background` کے بغیر کال کرنے کے لیے ایڈجسٹ کریں، یا
- مکمل غیر ہم وقتی پسِ منظر موڈ فراہم کرنے والی بعد کی ریلیز کا انتظار کریں (تبدیلیوں کا ریکارڈ دیکھتے رہیں)

## سست آغاز / تیاری کا ٹائم آؤٹ

اگر CLI یہ دکھائے کہ `⚠ Server did not respond within 60s` لیکن سرور حقیقت میں
کام کر رہا ہو، تو آپ کے ماحول کے لیے تیاری کی جانچ کا مقررہ وقت بہت کم ہے۔

یہ عموماً Windows (اینٹی وائرس، فائل سسٹم واچرز) یا بھاری ابتدائی ورک لوڈ والے
کنٹینرز میں ہوتا ہے۔

**حل — مقررہ وقت بڑھائیں:**

```bash
# ماحولیاتی متغیر کے ذریعے (آئندہ آغازوں میں برقرار رہتا ہے):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 منٹ
omniroute serve

# CLI فلیگ کے ذریعے (صرف ایک بار کے لیے):
omniroute serve --ready-timeout 180000
```

ڈیفالٹ 60 000 ms (60 s) ہے۔ یہ انتباہ صرف معلوماتی ہے؛ سرور پس منظر میں
شروع ہوتا رہتا ہے اور بوٹ مکمل ہونے کے بعد قابلِ رسائی ہو جائے گا۔

`OMNIROUTE_READY_TIMEOUT_MS` کی مکمل
تفصیلات کے لیے [`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) دیکھیں۔
