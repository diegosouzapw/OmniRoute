## فوری حوالہ

**OmniRoute پر نئے ہیں؟** یہاں سے شروع کریں — یہ 90% مسائل حل کر دیتے ہیں:

| مجھے یہ نظر آتا ہے            | اس کا کیا مطلب ہے                            | کیا کرنا ہے                                                                                                                        |
| ----------------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| "کنکشن قائم نہیں ہو سکا"      | OmniRoute چل نہیں رہا                        | `omniroute` یا `docker restart omniroute` چلائیں                                                                                   |
| "غلط API کلید"                | آپ کی کلید غلط ہے یا زائد المیعاد ہو چکی ہے  | فراہم کنندہ کی ویب سائٹ سے کلید دوبارہ کاپی کریں                                                                                   |
| "شرح کی حد تجاوز کر گئی"      | آپ بہت زیادہ درخواستیں بھیج رہے ہیں          | 1 منٹ انتظار کریں، یا خودکار فال بیک کے لیے `model: "auto"` استعمال کریں                                                           |
| "کوٹہ ختم ہو گیا"             | آپ اپنا مفت/بامعاوضہ کوٹہ استعمال کر چکے ہیں | مزید فراہم کنندگان منسلک کریں، یا مفت فراہم کنندگان (Kiro، Pollinations) استعمال کریں                                              |
| "سست جوابات"                  | فراہم کنندہ مصروف یا بہت دور ہے              | `model: "auto/fast"` استعمال کریں یا کوئی تیز فراہم کنندہ (Groq، Cerebras) منسلک کریں                                              |
| "غلط فراہم کنندہ استعمال ہوا" | `auto` نے کوئی مختلف فراہم کنندہ منتخب کیا   | یہ معمول کی بات ہے! `auto` بہترین فراہم کنندہ منتخب کرتا ہے۔ `model: "openai/gpt-4o"` کے ذریعے کسی مخصوص فراہم کنندہ کو لازمی کریں |
| "502 خراب گیٹ وے"             | فراہم کنندہ دستیاب نہیں                      | انتظار کرکے دوبارہ کوشش کریں، یا فراہم کنندہ تبدیل کرنے کے لیے `model: "auto"` استعمال کریں                                        |
| "401 غیر مجاز"                | آپ کی اسناد غلط ہیں                          | اپنی API کلید چیک کریں یا OAuth کے ذریعے دوبارہ توثیق کریں                                                                         |
| "429 بہت زیادہ درخواستیں"     | شرح کی حد نافذ ہو گئی ہے                     | 1 منٹ انتظار کریں، یا مزید فراہم کنندگان منسلک کریں                                                                                |

## تفصیلی ازالۂ خرابی

---

### مفت فراہم کنندگان پر شرح کی تحدید (429 / 400 / 401)

**علامت**: مفت/بغیر توثیق والے فراہم کنندگان (opencode، auggie وغیرہ) کے ساتھ `model: "auto"` استعمال کرتے وقت، کبھی کبھار جوابات کی بجائے `HTTP 429`، `400`، یا `401` موصول ہوتا ہے۔ کچھ لمحوں بعد اسی پرامپٹ کو دوبارہ آزمانے پر درخواستیں کامیاب ہو جاتی ہیں، لیکن خودکاری (cron جابز، ایجنٹس، اسکرپٹس) پہلی ناکامی پر رک جاتی ہے۔

**بنیادی وجہ**: ناکامی کی تین آزاد صورتیں ایک ساتھ جمع ہو جاتی ہیں:

1. **فراہم کنندہ کی شرح کی حد (`429`)**: مفت درجے فی وقفہ ایک کوٹہ نافذ کر سکتے ہیں۔ متوازی کالز کا اچانک اضافہ اسے ختم کر دیتا ہے، اس لیے وقفہ ری سیٹ ہونے تک اگلی درخواست مسترد کر دی جاتی ہے۔
2. **پاس تھرو میں خراب ماڈل (`400`/`401`)**: `auto/*` پولز میں `opencode` کے ایسے پاس تھرو ماڈلز شامل ہو سکتے ہیں جو کیٹلاگ میں رجسٹرڈ ہیں لیکن ان کے پاس فعال اسناد نہیں ہیں (مثلاً `oc/north-mini-code-free` → `401`)۔ آٹو راؤٹر ایک کو آزماتا ہے، ناکام ہوتا ہے، اور فال بیک فعال ہونے سے پہلے ہی خرابی آگے منتقل ہو جاتی ہے۔
3. **ہم وقتی میں اضافہ (لوڈ کے تحت `429`)**: جب متعدد ایجنٹ/cron سیشنز بیک وقت `auto` استعمال کرتے ہیں، تو مجموعی درخواستوں کی شرح مفت فراہم کنندگان کی قابل برداشت حد سے بڑھ جاتی ہے، جس کے باعث جائز کالز کو بھی ناجائز استعمال قرار دے دیا جاتا ہے۔

**تصدیق شدہ حل (کمیونٹی کی رپورٹ، 2026-08-10)**: تین ماحولیاتی متغیرات کو اس طرح ایڈجسٹ کریں کہ روٹیشن، ہم وقتی، اور فال بیک مفت درجے کے اتار چڑھاؤ کو ناکامی کا باعث بننے کی بجائے سنبھال لیں:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 پر کسی دوسرے ماڈل/فراہم کنندہ پر منتقل ہوں (خراب پاس تھرو ماڈلز کو چھوڑ دیتا ہے)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # بھاری درخواستوں کے داخلے کی واضح بالائی حد (بطور ڈیفالٹ غیر سیٹ: درخواستوں کی تعداد کی کوئی حد نہیں، ذیل کا نوٹ دیکھیں)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # فوری، دوبارہ کوشش کے قابل 503 کی بجائے بھاری گنجائش کے لیے زیادہ طویل محدود انتظار
```

انہیں OmniRoute پراسیس کے ماحول میں سیٹ کریں (ڈیمون میں، مثلاً LaunchAgent plist یا `systemctl edit` کے ذریعے)، پھر OmniRoute کو دوبارہ شروع کریں۔ روٹیشن فلیگ سب سے زیادہ مؤثر واحد اختیار ہے: یہ ایک سخت ناکامی کو پول میں موجود کسی صحت مند فراہم کنندہ کے خلاف شفاف دوبارہ کوشش میں تبدیل کر دیتا ہے۔

**نوٹ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` اس بات کی حد مقرر کرتا ہے کہ کتنی بھاری — طویل سیاق والی — درخواستیں بیک وقت چل سکتی ہیں؛ یہ حد داخلے کا دروازہ ہے، فراہم کنندہ کی شرح کی حد نہیں۔ **#503-fanout اپ ڈیٹ:** اب یہ متغیر بطور ڈیفالٹ سیٹ نہیں ہوتا (اب یہ صرف واضح طور پر کنفیگر کیے جانے پر لاگو ہوتا ہے، جیسا کہ اوپر دکھایا گیا ہے) — اس کے بجائے بھاری درخواستوں کا داخلہ خودکار طور پر اخذ کردہ بائٹ بجٹ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کے ذریعے محدود کیا جاتا ہے، جو میزبان کی حقیقی میموری حد کے مطابق خود کو ڈھالتا ہے، لہٰذا کسی نئی تعیناتی میں اس متغیر کو سیٹ کیے بغیر بھی `503 chat_admission_busy` مستردات کہیں کم ہونے چاہئیں؛ اسے یہاں واضح طور پر سیٹ کرنا اب بھی دستاویز کے عین مطابق کام کرتا ہے۔ واضح بائٹ بجٹ اوور رائیڈز 8 MiB–2 GiB تک محدود رہتے ہیں۔ `413 body_exceeds_budget` عارضی نہیں ہے: اس بائٹ بجٹ کو بڑھائیں، `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` کو کم کریں، یا پراسیس کی میموری حد بڑھائیں۔ `inflight_bytes_budget` شیڈ عارضی مسابقت ہے اور اس پر دوبارہ کوشش کی جا سکتی ہے۔ فی فراہم کنندہ شرح کی تحدید (`open-sse/services/rateLimitManager.ts`) الگ سے `RATE_LIMIT_MAX_WAIT_MS`، `RATE_LIMIT_MAX_QUEUE_DEPTH`، اور `RATE_LIMIT_AUTO_ENABLE` کے ذریعے کنٹرول ہوتی ہے — `.env.example` دیکھیں۔

**اس کے کام کرنے کی تصدیق کیسے کریں**: اپنے ایجنٹ/cron کو یکے بعد دیگرے دو بار چلائیں اور تصدیق کریں کہ دونوں کامیاب ہوں۔ حل سے پہلے، دوسری بار چلانے پر عموماً `429`/`401` آتا ہے۔ حل کے بعد، ناکامیوں (اگر کوئی ہوں) پر شفاف طور پر دوبارہ کوشش کی جاتی ہے اور کال مکمل ہو جاتی ہے۔ آپ `curl /monitoring/health` بھی چلا سکتے ہیں اور فراہم کنندہ کنکشنز پر `rateLimitedUntil` فیلڈ اور متاثرہ فراہم کنندگان کے لیے `circuitBreakers.providerBreakers[].state` دیکھ سکتے ہیں — حالت `CLOSED`، `DEGRADED`، `OPEN`، یا `HALF_OPEN` میں سے ایک ہوتی ہے (`src/shared/utils/circuitBreaker.ts` دیکھیں)، اور مسلسل ناکام ہونے والا فراہم کنندہ `CLOSED → DEGRADED → OPEN` میں تبدیل ہو جائے گا، جس کے بعد ری سیٹ وقفہ ایک آزمائشی درخواست کو گزرنے دے گا (`HALF_OPEN`)۔

**اگر آپ کو اب بھی 429 نظر آئے**: اس provider کے لیے فعال account کا _quota_ واقعی ختم ہو چکا ہے (صرف rate نہیں)۔ OmniRoute dashboard → Providers → Accounts میں اسی provider کے لیے دوسرا account شامل کریں، یا کوئی اور مفت provider شامل کریں (مثلاً `routeway`، `auggie`)۔ Rotation صرف عارضی rate/400/401 مسائل میں مدد دیتی ہے؛ quota مکمل طور پر ختم ہونے کی صورت میں دوسری credential یا مختلف provider درکار ہوتا ہے۔

**اگر vision models (`auto/vision`، `bazaarlink/*`) پر 403 نظر آئے**: منسلک account کے پاس ایسا paid plan نہیں ہے جس میں vision شامل ہو، یا API key کے permissions ناکافی ہیں۔ provider dashboard میں تصدیق کریں کہ key scope میں vision/multimodal شامل ہے، یا paid tier account منسلک کرکے اسے vision target کے طور پر برقرار رکھیں۔

## npm install انتباہات (ERESOLVE / peer / deprecated)

جب آپ `npm install -g omniroute` چلاتے ہیں، تو آپ کو `npm warn ERESOLVE`، peer-dependency نوٹسز، اور `deprecated` پیغامات جیسے بہت سے انتباہات نظر آ سکتے ہیں۔ **یہ متوقع اور بے ضرر ہیں۔** اگر آؤٹ پٹ میں `added <N> packages` نظر آئے تو آپ کی انسٹالیشن کامیاب ہو گئی ہے۔

peer-dependency ریزولیوشن کے انتباہات کو دبانے کے لیے، OmniRoute کی معاونت یافتہ انسٹالیشن کمانڈ استعمال کریں:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` صرف `ERESOLVE` اور peer-dependency نوٹسز کو دباتا ہے۔ فرسودگی کے نوٹسز بدستور نظر آتے ہیں کیونکہ وہ بالواسطہ تھرڈ پارٹی پیکیجز سے آتے ہیں؛ وہ اس بات کی نشاندہی نہیں کرتے کہ انسٹالیشن ناکام ہو گئی ہے۔

یہ انتباہات ان تھرڈ پارٹی پیکیجز میں پرانی peer-dependency حدود کی وجہ سے آتے ہیں جن پر OmniRoute کا اختیار نہیں ہے:

1. **`marked-terminal` کو `marked >=1 <16` درکار ہے، مگر `marked@18` ملا** — عملی طور پر درست کام کرتا ہے؛ upstream peer حد صرف پرانی ہے۔
2. **`deprecated prebuild-install@7.1.3`** — مقامی بائنری حاصل کرنے کے لیے ایک بالواسطہ مددگار۔ اسے پن شدہ `wreq-js` ٹرانسپورٹ بائنڈنگ انسٹال کرنے کے لیے
   استعمال نہیں کیا جاتا اور یہ اس بات کی نشاندہی نہیں کرتا کہ web-cookie
   فراہم کنندہ کی ٹرانسپورٹ سیٹ اپ ناکام ہو گئی ہے۔

**کسی اقدام کی ضرورت نہیں** — upstream پیکیجز کو fork کیے بغیر ان انتباہات کو مکمل طور پر خاموش نہیں کیا جا سکتا۔

## اینٹی وائرس کے غلط مثبت نتائج

<a name="antivirus-false-positives"></a>

### Avast/AVG، `README.md` کو `MD:HttpRequest-inf[Susp]` کے ساتھ قرنطینہ کر دیتا ہے

**یہ ایک غلط مثبت نتیجہ ہے۔ کوئی چیز متاثرہ نہیں ہے، اور کسی کارروائی کی ضرورت نہیں ہے۔**

Avast اور AVG ایک ایسا ہیورسٹک چلاتے ہیں جو بہت سے HTTP درخواست جیسے نظر آنے والے لنکس پر مشتمل سادہ متن/Markdown فائلوں کو نشان زد کرتا ہے۔ OmniRoute کی `README.md` فائل npm پیکیج کے اندر شامل ہوتی ہے (یہ `package.json` → `files` میں درج ہے)، لہٰذا عالمی انسٹالیشن پر یہ `node_modules/omniroute/README.md` میں آ جاتی ہے — اور اس میں تقریباً 15 `http://localhost:20128/...` مثالیں موجود ہیں (MCP کے HTTP/SSE اینڈ پوائنٹس، A2A کا `.well-known` URL، اور `curl` کے اسنیپٹس)۔ لنکس کی یہ کثافت ہیورسٹک کو متحرک کرنے کے لیے کافی ہے۔

اگر یہ مسئلہ حال ہی میں شروع ہوا ہے: فائل کی نوعیت تبدیل نہیں ہوئی۔ README میں اینڈ پوائنٹس کی جدول وسیع ہوئی (MCP HTTP + SSE + A2A شامل کیے گئے) اور مزید `curl` مثالیں شامل ہوئیں، جس کے باعث یہ حد سے تجاوز کر گئی۔

یہ فائل غیر فعال دستاویز ہے جس میں کوئی قابلِ اجرا مواد موجود نہیں۔ آپ اسے قرنطینہ سے محفوظ طریقے سے بحال کر سکتے ہیں۔

**کیا کریں:**

1. **اطلاعات روکیں** — اپنے اینٹی وائرس میں انسٹالیشن ڈائریکٹری کو مستثنیٰ قرار دیں
   (Avast: Settings → Exceptions)، اور اپنی عالمی `node_modules` پاتھ اور/یا
   OmniRoute ڈیٹا ڈائریکٹری (`~/.omniroute/`) شامل کریں۔
2. **غلط مثبت نتیجے کی اطلاع دیں** — <https://www.avast.com/false-positive-file-form.php>،
   اور قرنطینہ کی گئی `README.md` منسلک کریں۔ یہی وہ حل ہے جو سب کی مدد کرتا ہے، کیونکہ یہ
   وینڈر کا ہیورسٹک ہے جو ایک متنی فائل پر ضرورت سے زیادہ ردِعمل ظاہر کر رہا ہے۔

**ہم اپنی جانب سے اسے "درست" کیوں نہیں کرتے:** تمام مثالیں `http://localhost` ہیں، اور
خود دستخط شدہ سرٹیفکیٹ کی پیچیدگی کے بغیر localhost کو `https` نہیں بنایا جا سکتا۔ کسی ایک
وینڈر کے ہیورسٹک سے بچنے کے لیے دستاویزات کو بگاڑنا، اسکینر کی خرابی کی خاطر ہر قاری کو
نقصان پہنچائے گا۔

### Kaspersky ڈیسک ٹاپ ایپ کو `PDM:Trojan.Win32.Generic` کے طور پر نشان زد کرتا ہے

**یہ طرزِ عمل پر مبنی ہیورسٹک کا غلط مثبت نتیجہ ہے۔ کوئی چیز متاثرہ نہیں ہے۔** Kaspersky کا
`PDM:` سابقہ ظاہر کرتا ہے کہ یہ فیصلہ اس کے Proactive Defense Module (System Watcher) سے
آیا ہے، جو انسٹالر کو معروف میل ویئر سے مماثل کرنے کے بجائے یہ جانچتا ہے کہ وہ _کیا کرتا ہے_۔
جب یہ متحرک ہوتا ہے تو Kaspersky پوری انسٹالیشن کو "واپس پلٹ" دیتا ہے — ان فائلوں کو حذف
کر دیتا ہے جو وہ پہلے ہی لکھ چکا تھا — لہٰذا ایپ خراب یا غائب ہو جاتی ہے۔

جن فائلوں کو یہ نشان زد کرتا ہے وہ ڈیسک ٹاپ ایپ کے ساتھ شامل، واضح طور پر بیان کردہ اوپن
سورس انحصارات کے معیاری حصے ہیں، مثلاً:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` اور
  `workerProcessEntry.js` — [Playwright](https://playwright.dev)، براؤزر آٹومیشن
  لائبریری جو ایپ کے اندر فراہم کنندہ کے لاگ اِن اور براؤزر پر مبنی چیٹ کے لیے استعمال ہوتی ہے۔
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — مخصوص ورژن کی `wreq-js` مقامی بائنڈنگ، جو ویب کوکی فراہم کنندگان پر براؤزر فنگرپرنٹ والی
  HTTP درخواستوں کے لیے استعمال ہوتی ہے (`<arch>`، `x64` یا `arm64` ہوتا ہے)۔

**یہ کیوں متحرک ہوتا ہے:** Windows انسٹالر پر **ابھی تک کوڈ سائن نہیں کیا گیا**، اس لیے ایک
غیر دستخط شدہ NSIS انسٹالر کی کوئی ساکھ نہیں ہوتی اور طرزِ عمل کے ہیورسٹکس انتہائی جارحانہ
انداز میں کام کرتے ہیں۔ اس کے ساتھ شامل مقامی DLL اور `%LOCALAPPDATA%\Programs\OmniRoute`
کے تحت لکھی جانے والی سینکڑوں `.js` فائلیں (بشمول Next.js اسٹینڈ الون بلڈ کی ہیش لاحقے والی
پیکیج ڈائریکٹریاں) مل کر ہیورسٹک کو متحرک کرنے کے لیے کافی ہیں۔ کوڈ سائننگ کا منصوبہ موجود
ہے؛ جب تک یہ نافذ نہیں ہوتی، نئی ریلیزز میں یہ مسئلہ دوبارہ پیش آ سکتا ہے۔

**کیا کریں:**

1. **پہلے اپنے ڈاؤن لوڈ کی تصدیق کریں** (اس سے چھیڑ چھاڑ شدہ فائل کا امکان خارج ہو جاتا ہے)۔
   ہر ریلیز `latest.yml` شائع کرتی ہے، جس کا `sha512` فیلڈ (base64)
   `OmniRoute.Setup.<version>.exe` انسٹالر کا احاطہ کرتا ہے۔ PowerShell میں، انسٹالر والی
   ڈائریکٹری سے:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   آؤٹ پٹ لازماً `latest.yml` → `sha512` سے مماثل ہونا چاہیے۔ اگر ایسا نہ ہو تو فائل حذف
   کریں اور صرف [GitHub ریلیزز کے صفحے](https://github.com/diegosouzapw/OmniRoute/releases)
   سے دوبارہ ڈاؤن لوڈ کریں۔
2. **بحال کریں + مستثنیٰ قرار دیں** — واپس پلٹائی گئی اشیا کو قرنطینہ سے بحال کریں اور
   `%LOCALAPPDATA%\Programs\OmniRoute` کے لیے استثنا شامل کریں
   (Kaspersky → Settings → Threats and Exclusions)، پھر دوبارہ انسٹال کریں۔
3. **غلط مثبت نتیجے کی اطلاع دیں** — <https://opentip.kaspersky.com/>۔ صارفین کی جانب سے
   جمع کرائی گئی FP رپورٹس واقعی اجازت یافتہ فہرست میں شمولیت کو تیز کرتی ہیں۔

## Node.js مطابقت

<a name="nodejs-compatibility"></a>

### لاگ اِن صفحہ کریش ہو جاتا ہے یا "Module self-registration" کی خرابی دکھاتا ہے

**وجہ:** آپ Node.js کا ایسا ورژن چلا رہے ہیں جو OmniRoute کی منظور شدہ محفوظ رن ٹائم کم از کم حد سے باہر ہے۔ سب سے عام صورت یہ ہے کہ Node 22 یا 24 کا ایسا پرانا پیچ لیول چل رہا ہو جو OmniRoute کی مطلوبہ پیچ شدہ سیکیورٹی حد سے کم ہو۔

**علامات:**

- لاگ اِن صفحہ خالی اسکرین یا سرور کی خرابی دکھاتا ہے
- کنسول میں `Error: Module did not self-register` یا اس جیسی نیٹو بائنڈنگ کی خرابیاں دکھائی دیتی ہیں
- اگر رن ٹائم معاونت یافتہ محفوظ پالیسی سے باہر ہو تو لاگ اِن صفحہ آپ کے Node ورژن کے ساتھ **نارنجی انتباہی بینر** دکھاتا ہے

**حل:**

1. Node.js کا معاونت یافتہ LTS ریلیز انسٹال کریں (تجویز کردہ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. اپنے ورژن کی تصدیق کریں: `node --version` کو 24.x LTS سلسلے میں `v24.0.0` یا اس سے نیا ورژن دکھانا چاہیے
3. OmniRoute دوبارہ انسٹال کریں: `npm install -g omniroute`
4. دوبارہ شروع کریں: `omniroute`

> **معاونت یافتہ محفوظ ورژنز:** `>=22.22.2 <23` یا `>=24.0.0 <27`۔ Node.js 24.x LTS (Krypton) اور Node.js 26 مکمل طور پر معاونت یافتہ ہیں۔

### npm v11+: `better-sqlite3` انسٹال نہیں ہے (ماڈیول نہیں مل سکا)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**وجہ:** npm v11 (جو Node.js 24+ کے ساتھ فراہم کیا جاتا ہے) اختیاری
انحصارات کے لیے انسٹالیشن اسکرپٹس کو بطور ڈیفالٹ بلاک کر دیتا ہے۔ چونکہ `better-sqlite3` کو `optionalDependencies`
میں درج کیا گیا ہے اور اسے نیٹو کمپائلیشن (`node-gyp rebuild`) درکار ہے، اس لیے npm اسے خاموشی سے چھوڑ دیتا ہے۔

**علامات:**

- سرور آغاز کے وقت `Cannot find module 'better-sqlite3'` کے ساتھ کریش ہو جاتا ہے
- `ls node_modules/better-sqlite3` سے "No such file or directory" ظاہر ہوتا ہے
- `npm ls better-sqlite3` سے `(empty)` ظاہر ہوتا ہے

**حل:**

1. انسٹالیشن اسکرپٹس کی منظوری دیں اور دوبارہ انسٹال کریں:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. یا پہلے سے تیار شدہ پیکیج دستی طور پر انسٹال کریں:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. تصدیق کریں کہ یہ کام کرتا ہے: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**وجہ:** عالمی `npm install -g omniroute` کے بعد، پیکیج کے اندر موجود `better-sqlite3` نیٹو بائنری ممکن ہے کہ مقامی طور پر چلنے والے سسٹم سے مختلف آرکیٹیکچر یا Node.js ABI کے لیے کمپائل کی گئی ہو۔ macOS (Apple Silicon اور Intel دونوں) پر یہ اس وقت عام ہے جب پہلے سے تیار شدہ بائنری آپ کے ماحول سے مطابقت نہ رکھتی ہو۔

**علامات:**

- سرور آغاز کے فوراً بعد `dlopen` خرابی کے ساتھ ناکام ہو جاتا ہے
- خرابی میں `slice is not valid mach-o file` شامل ہوتا ہے
- مکمل مثال:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**حل — اپنے مقامی ماحول کے لیے دوبارہ بنائیں (Node.js کا ورژن کم کرنے کی ضرورت نہیں):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **نوٹ:** یہ نیٹو بائنڈنگ کو آپ کے مقامی Node.js ورژن اور CPU آرکیٹیکچر کے مطابق دوبارہ کمپائل کرتا ہے، جس سے بائنری کی عدم مطابقت حل ہو جاتی ہے۔ باضابطہ طور پر معاونت یافتہ رن ٹائم حد **`>=22.22.2 <23` یا `>=24.0.0 <27`** ہے (`src/shared/utils/nodeRuntimeSupport.ts` میں `SUPPORTED_NODE_RANGE`، جو `package.json` کے `engines` فیلڈ سے ہم آہنگ ہے)۔ Node.js 24.x LTS (Krypton) اور Node.js 26 کو `better-sqlite3` v12.x کے ساتھ مکمل معاونت حاصل ہے۔

## پراکسی کے مسائل

<a name="proxy-issues"></a>

### فراہم کنندہ کی توثیق میں "fetch failed" دکھائی دیتا ہے

**وجہ:** API کلید کی توثیق کا اینڈ پوائنٹ (`POST /api/providers/validate`) پہلے پراکسی کنفیگریشن کو نظر انداز کر رہا تھا، جس کی وجہ سے ان ماحولوں میں ناکامیاں ہوتی تھیں جہاں پراکسی روٹنگ درکار ہوتی ہے۔

**حل (v3.5.5+):** اب یہ مسئلہ حل ہو چکا ہے۔ فراہم کنندہ کی توثیق `runWithProxyContext` کے ذریعے روٹ ہوتی ہے اور فراہم کنندہ کی سطح اور عالمی پراکسی ترتیبات کا خودکار طور پر احترام کرتی ہے۔

### ٹوکن کی صحت کی جانچ "fetch failed" کے ساتھ ناکام ہو جاتی ہے

**وجہ:** پس منظر میں OAuth ٹوکن ریفریش ہر کنکشن کے لیے پراکسی کنفیگریشن کو حل نہیں کر رہا تھا۔

**حل (v3.5.5+):** ٹوکن کی صحت کی جانچ کا شیڈیولر اب ریفریش کی کوشش کرنے سے پہلے ہر کنکشن کے لیے پراکسی کنفیگ کو حل کرتا ہے۔ v3.5.5+ پر اپ ڈیٹ کریں۔

### SOCKS5 پراکسی "invalid onRequestStart method" واپس کرتی ہے

**وجہ:** Node.js 22 پر، undici@8 ڈسپیچر Node کے بلٹ اِن `fetch()` نفاذ کے ساتھ غیر موافق ہے۔

**حل (v3.5.5+):** جب پراکسی ڈسپیچر فعال ہو تو OmniRoute اب undici کا اپنا `fetch()` فنکشن استعمال کرتا ہے، جس سے مستقل رویہ یقینی بنتا ہے۔ v3.5.5+ پر اپ ڈیٹ کریں۔

### WSL کے تحت MITM پراکسی: Windows ہوسٹ پر ڈیسک ٹاپ ایپس انٹرسیپٹ نہیں ہوتیں

**وجہ:** MITM پراکسی اور اس کا CA سرٹیفکیٹ اسی ماحول میں انسٹال ہوتے ہیں جہاں OmniRoute چلتا ہے۔ WSL کے تحت یہ ماحول Linux گیسٹ ہوتا ہے، جبکہ AI ڈیسک ٹاپ ایپس (Kiro، Trae، Copilot، Zed، …) Windows ہوسٹ پر چلتی ہیں۔ ہوسٹ ایپس گیسٹ کے سرٹیفکیٹ اسٹور پر بھروسا نہیں کرتیں اور نہ ہی گیسٹ کے سسٹم پراکسی کے ذریعے روٹ ہوتی ہیں، اس لیے وہاں ڈیسک ٹاپ انٹرسیپشن فعال نہیں ہوتی۔

**تجویز:** OmniRoute کو مقامی طور پر اسی OS پر چلائیں جس پر وہ ڈیسک ٹاپ ایپس چلتی ہیں جنہیں آپ انٹرسیپٹ کرنا چاہتے ہیں (Windows ایپس کے لیے Windows؛ اسی طرح macOS/Linux کے لیے متعلقہ OS)۔ ہوسٹ ایپس کو ہدف بناتے ہوئے OmniRoute کو WSL کے اندر رکھنے کے لیے ضروری ہے کہ آپ بنائے گئے CA سرٹیفکیٹ کو Windows ہوسٹ پر دستی طور پر قابلِ اعتماد بنائیں اور ہر ہوسٹ ایپ کی نیٹ ورک/پراکسی ترتیبات کو WSL پراکسی اینڈ پوائنٹ کی طرف متوجہ کریں — یہ ایک غیر معاون اور نازک سیٹ اپ ہے۔

## کلاؤڈ کے مسائل

### کلاؤڈ سنک کی خرابیاں

1. تصدیق کریں کہ `BASE_URL` آپ کی چلتی ہوئی انسٹینس کی طرف اشارہ کرتا ہے (مثلاً، `http://localhost:20128`)
2. تصدیق کریں کہ `CLOUD_URL` آپ کے کلاؤڈ اینڈ پوائنٹ کی طرف اشارہ کرتا ہے (مثلاً، `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` کی قدروں کو سرور سائیڈ کی قدروں کے مطابق رکھیں

### کلاؤڈ میں `stream=false` سے 500 واپس آتا ہے

**علامت:** نان اسٹریمنگ کالز کے لیے کلاؤڈ اینڈ پوائنٹ پر `Unexpected token 'd'...`۔

**وجہ:** اپ اسٹریم SSE پے لوڈ واپس کرتا ہے جبکہ کلائنٹ JSON کی توقع کرتا ہے۔

**عارضی حل:** کلاؤڈ کو براہِ راست کالز کے لیے `stream=true` استعمال کریں۔ مقامی رن ٹائم میں SSE→JSON فال بیک شامل ہے۔

### کلاؤڈ کنیکٹڈ دکھاتا ہے لیکن "غلط API کلید"

1. مقامی ڈیش بورڈ (`/api/keys`) سے ایک نئی کلید بنائیں
2. کلاؤڈ سنک چلائیں: کلاؤڈ فعال کریں → ابھی سنک کریں
3. پرانی/غیر سنک شدہ کلیدیں اب بھی کلاؤڈ پر `401` واپس کر سکتی ہیں

## Docker کے مسائل

### Docker IPv6 / کنکشن ری سیٹ

<a name="docker-ipv6"></a>

**علامات:** `curl http://localhost:20128/v1/models` سے `curl: (56) Recv failure: Connection reset by peer` واپس آتا ہے۔ ڈیش بورڈ اور غیر تصدیق شدہ اینڈ پوائنٹس کام کرتے ہیں، لیکن تصدیق شدہ اینڈ پوائنٹس ناکام ہو جاتے ہیں — یہ تصدیق کا مسئلہ نظر آتا ہے، مگر ایسا نہیں ہے۔

**وجہ:** `docker run -p 20128:20128` دونوں `0.0.0.0` (IPv4) اور `::` (IPv6) پر پورٹ شائع کرتا ہے، لیکن کنٹینر کے اندر موجود پراسیس صرف IPv4 پر سنتا ہے۔ ان ہوسٹس پر جہاں `localhost` پہلے `::1` پر ریزولو ہوتا ہے، کنکشن IPv6 کی شائع شدہ پورٹ پر پہنچتا ہے جس کے پیچھے کوئی لسنر نہیں ہوتا → کنکشن ری سیٹ۔

**حل:**

1. **فوری تشخیص:** `curl -4 http://localhost:20128/v1/models` چلائیں۔ اگر یہ `-4` کے ساتھ کام کرتا ہے لیکن اس کے بغیر ناکام ہوتا ہے، تو آپ کو IPv6 بائنڈ عدم مطابقت کا مسئلہ درپیش ہے۔
2. **مستقل حل:** اپنی `docker run` کمانڈ میں `-p 127.0.0.1:20128:20128` استعمال کرکے واضح طور پر IPv4 سے بائنڈ کریں:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   یہ IPv4 بائنڈ کو لازمی بناتا ہے اور پراکسی کو تمام ہوسٹ انٹرفیسز پر ظاہر ہونے سے بھی روکتا ہے۔

### CLI ٹول انسٹال شدہ نہیں دکھاتا

1. رن ٹائم فیلڈز چیک کریں: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`
2. پورٹیبل موڈ کے لیے: امیج ٹارگٹ `runner-cli` استعمال کریں (بنڈل شدہ CLIs)
3. ہوسٹ ماؤنٹ موڈ کے لیے: `CLI_EXTRA_PATHS` سیٹ کریں اور ہوسٹ bin ڈائریکٹری کو صرف پڑھنے کے لیے ماؤنٹ کریں
4. اگر `installed=true` اور `runnable=false` ہو: بائنری مل گئی تھی لیکن ہیلتھ چیک میں ناکام ہوگئی


## ڈیبگنگ

### لاگ فائلیں فعال کریں

اپنی `.env` فائل میں `APP_LOG_TO_FILE=true` سیٹ کریں۔ ایپلیکیشن لاگز `logs/` کے تحت لکھے جاتے ہیں۔
جب سیٹنگز میں کال لاگ پائپ لائن فعال ہو تو درخواست کے آرٹیفیکٹس `${DATA_DIR}/call_logs/` کے تحت محفوظ کیے جاتے ہیں۔
جب پائپ لائن کیپچر فعال ہو تو اسٹریم چنک پے لوڈز شامل نہ کرنے کے لیے `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` سیٹ کریں، یا KB میں آرٹیفیکٹ کی حد تبدیل کرنے کے لیے `CALL_LOG_PIPELINE_MAX_SIZE_KB` کو ایڈجسٹ کریں۔

### فراہم کنندہ کی صحت چیک کریں

```bash
# ہیلتھ ڈیش بورڈ
http://localhost:20128/dashboard/health

# API ہیلتھ چیک
curl http://localhost:20128/api/monitoring/health
```

### رن ٹائم اسٹوریج

- بنیادی حالت: `${DATA_DIR}/storage.sqlite` (فراہم کنندگان، کومبوز، عرف، کلیدیں، سیٹنگز)
- استعمال: `storage.sqlite` میں SQLite ٹیبلز (`usage_history`، `call_logs`، `proxy_logs`) + اختیاری `${DATA_DIR}/call_logs/`
- ایپلیکیشن لاگز: `<repo>/logs/...` (جب `APP_LOG_TO_FILE=true` ہو)
- کال لاگ آرٹیفیکٹس: جب کال لاگ پائپ لائن فعال ہو تو `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

درخواست لاگز کے صفحے کی **ہسٹری صاف کریں** کارروائی `call_logs`، پرانے
`request_detail_logs`، اور مقامی `${DATA_DIR}/call_logs/` آرٹیفیکٹ ڈائریکٹری کو صاف کرتی ہے۔

## سرکٹ بریکر کے مسائل

### فراہم کنندہ OPEN حالت میں پھنسا ہوا ہے

جب کسی فراہم کنندہ کا سرکٹ بریکر OPEN ہو، تو کول ڈاؤن ختم ہونے تک درخواستیں مسدود رہتی ہیں۔

**حل:**

1. **ڈیش بورڈ → ترتیبات → لچک پذیری** پر جائیں
2. متاثرہ فراہم کنندہ کے لیے سرکٹ بریکر کارڈ چیک کریں
3. تمام بریکرز صاف کرنے کے لیے **سب ری سیٹ کریں** پر کلک کریں، یا کول ڈاؤن ختم ہونے کا انتظار کریں
4. ری سیٹ کرنے سے پہلے تصدیق کریں کہ فراہم کنندہ واقعی دستیاب ہے

### فراہم کنندہ بار بار سرکٹ بریکر کو ٹرپ کرتا ہے

اگر کوئی فراہم کنندہ بار بار OPEN حالت میں داخل ہوتا ہے:

1. ناکامی کا انداز دیکھنے کے لیے **ڈیش بورڈ → صحت → فراہم کنندہ کی صحت** چیک کریں
2. **ترتیبات → لچک پذیری → فراہم کنندہ پروفائلز** پر جائیں اور ناکامی کی حد بڑھائیں
3. چیک کریں کہ آیا فراہم کنندہ نے API کی حدود تبدیل کی ہیں یا دوبارہ توثیق درکار ہے
4. تاخیر کی ٹیلی میٹری کا جائزہ لیں — زیادہ تاخیر ٹائم آؤٹ پر مبنی ناکامیوں کا سبب بن سکتی ہے

### فارمیٹ کے عام مسائل

- **تھنکنگ ٹیگز ظاہر نہیں ہو رہے** — چیک کریں کہ آیا ہدف فراہم کنندہ تھنکنگ کی معاونت کرتا ہے اور تھنکنگ بجٹ کی ترتیب درست ہے
- **ٹول کالز غائب ہو رہی ہیں** — فارمیٹ کی بعض تبدیلیاں غیر معاون فیلڈز کو ہٹا سکتی ہیں؛ پلے گراؤنڈ موڈ میں تصدیق کریں
- **سسٹم پرامپٹ غائب ہے** — Claude اور Gemini سسٹم پرامپٹس کو مختلف طریقے سے سنبھالتے ہیں؛ تبدیلی کا آؤٹ پٹ چیک کریں
- **SDK آبجیکٹ کے بجائے خام اسٹرنگ واپس کرتا ہے** — یہ مسئلہ v1.x میں حل ہو چکا ہے؛ رسپانس سینیٹائزر غیر معیاری فیلڈز (`x_groq`, `usage_breakdown`، وغیرہ) کو ہٹا دیتا ہے جو OpenAI SDK Pydantic کی توثیقی ناکامیوں کا سبب بنتی ہیں۔ اگر آپ کو v3.x+ پر اب بھی یہ مسئلہ نظر آتا ہے، تو براہِ کرم ایک مسئلہ درج کریں۔
- **GLM/ERNIE، `system` کردار کو مسترد کرتا ہے** — یہ مسئلہ v1.x میں حل ہو چکا ہے؛ کردار نارملائزر غیر موافق ماڈلز کے لیے سسٹم پیغامات کو خودکار طور پر صارف کے پیغامات میں ضم کر دیتا ہے۔ اگر آپ کو v3.x+ پر اب بھی یہ مسئلہ نظر آتا ہے، تو براہِ کرم ایک مسئلہ درج کریں۔
- **`developer` کردار شناخت نہیں کیا جاتا** — یہ مسئلہ v1.x میں حل ہو چکا ہے؛ غیر OpenAI فراہم کنندگان کے لیے اسے خودکار طور پر `system` میں تبدیل کر دیا جاتا ہے۔ اگر آپ کو v3.x+ پر اب بھی یہ مسئلہ نظر آتا ہے، تو براہِ کرم ایک مسئلہ درج کریں۔
- **`json_schema`، Gemini کے ساتھ کام نہیں کر رہا** — یہ مسئلہ v1.x میں حل ہو چکا ہے؛ اب `response_format` کو Gemini کے `responseMimeType` + `responseSchema` میں تبدیل کیا جاتا ہے۔ اگر آپ کو v3.x+ پر اب بھی یہ مسئلہ نظر آتا ہے، تو براہِ کرم ایک مسئلہ درج کریں۔

## لچک کی ترتیبات

### خودکار شرحِ حد فعال نہیں ہو رہی

- خودکار شرحِ حد صرف API کلید فراہم کنندگان پر لاگو ہوتی ہے (OAuth/سبسکرپشن پر نہیں)
- تصدیق کریں کہ **Settings → Resilience → Provider Profiles** میں خودکار شرحِ حد فعال ہے
- چیک کریں کہ آیا فراہم کنندہ `429` اسٹیٹس کوڈز یا `Retry-After` ہیڈرز واپس کرتا ہے

### ایکسپونینشل بیک آف کی ٹیوننگ

فراہم کنندہ پروفائلز ان ترتیبات کو سپورٹ کرتے ہیں:

- **بنیادی تاخیر** — پہلی ناکامی کے بعد ابتدائی انتظار کا وقت (ڈیفالٹ: 1s)
- **زیادہ سے زیادہ تاخیر** — انتظار کے وقت کی زیادہ سے زیادہ حد (ڈیفالٹ: 30s)
- **ضارب** — ہر مسلسل ناکامی پر تاخیر میں کتنا اضافہ کیا جائے (ڈیفالٹ: 2x)

### اینٹی تھنڈرنگ ہرڈ

جب بیک وقت بہت سی درخواستیں شرحِ حد کے شکار فراہم کنندہ تک پہنچتی ہیں، تو OmniRoute درخواستوں کو سلسلہ وار کرنے اور یکے بعد دیگرے ناکامیوں کو روکنے کے لیے mutex + خودکار شرحِ حد استعمال کرتا ہے۔ API کلید فراہم کنندگان کے لیے یہ خودکار ہے۔

### چیٹ درخواستیں 503 / chat_admission_busy کے ساتھ ناکام ہوتی ہیں

**علامات:**

- چیٹ تکمیلات کا اینڈ پوائنٹ دوبارہ کوشش کے قابل `503` جواب واپس کرتا ہے، جس کا خرابی کوڈ
  `chat_admission_busy` ہوتا ہے۔
- جواب میں `Retry-After` شامل ہوتا ہے۔ #12135 کے بعد سے اس کی قدر مشاہدہ شدہ
  مصروفیت سے اخذ کی جاتی ہے — درخواست کے پہلے ہی انتظار کیے گئے `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  دورانیے اور موجودہ بھاری لیزز کے برقرار رہنے کے وقت میں سے جو بڑا ہو — اسے مکمل
  سیکنڈز تک اوپر کی طرف راؤنڈ کیا جاتا ہے اور 60 پر محدود کیا جاتا ہے۔ غیر مصروف گیٹ پر یہ
  تاریخی کم از کم حدود برقرار رکھتا ہے: بائٹ پر مبنی راستے پر 2 سیکنڈ، ساخت پر مبنی راستے پر
  1 سیکنڈ (جس میں `reason: "structure_limit"` بھی شامل ہوتا ہے)۔
- یہ اس وقت ہو سکتا ہے جب کوئی دوسری بھاری چیٹ یا طویل عرصے تک چلنے والا اسٹریمنگ جواب اب بھی
  زیرِ عمل ہو۔

بائٹ پر مبنی جواب کی باڈی یہ ہے:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ساخت پر مبنی جواب یہی قسم اور کوڈ استعمال کرتا ہے، جبکہ پیغام
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
اور `reason: "structure_limit"` ہوتا ہے۔
ڈیفالٹ حدوں پر، کوئی درخواست ساختی طور پر بھاری ہوتی ہے جب اس میں کم از کم `200` پیغامات،
کم از کم `64` ٹولز، یا کم از کم `32,000` تخمینی ٹوکنز ہوں، یا جب محدود ساختی تخمینہ
`10,000` ملاحظہ شدہ نوڈز یا گہرائی `12` کی اپنی حدود ختم کر دے۔

**وجہ:** یہ OmniRoute کے اندر دانستہ بوجھ میں کمی ہے، نہ کہ اپ اسٹریم فراہم کنندہ کی ناکامی۔
ہر پراسیس کسی بڑی درخواست کی باڈی کو برقرار رکھنے اور پارس کرنے سے پہلے محدود بھاری گنجائش
محفوظ کرنے کے لیے پراسیس-مقامی گارڈ استعمال کرتا ہے۔ ایک بھاری لیز SSE جواب کی پوری مدت تک
برقرار رہتی ہے۔

**#503-fanout:** اس اصلاح سے پہلے، گارڈ میزبان کی میموری سے قطع نظر بیک وقت عمل درآمد کو درخواستوں
کی ایک مقررہ تعداد (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`، ڈیفالٹ `1`) تک محدود کرتا تھا، لہٰذا
کوڈنگ ایجنٹ فین آؤٹ (متعدد ذیلی ایجنٹس/CLIs، باڈیز معمول کے مطابق > 256 KB) مؤثر بیک وقت عمل
درآمد کو ~1 تک گرا دیتا تھا اور بالکل معمول کے بوجھ میں بھی 503 پیدا کرتا تھا۔ اب گارڈ خود کو
ٹیون کرتا ہے: اسے پراسیس کی حقیقی میموری حد سے متعین کردہ، خودکار طور پر اخذ شدہ ان جیسٹ بائٹ
بجٹ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) کے ذریعے کنٹرول کیا جاتا ہے، اور یہ براہِ راست وسائل
کے دباؤ کے سگنل کو بھی مدِنظر رکھتا ہے — لہٰذا یہ صرف اس وقت بوجھ کم کرتا ہے جب میزبان واقعی
میموری کے دباؤ میں ہو، محض اس لیے نہیں کہ ایک سے زیادہ بھاری درخواستیں ایک ساتھ پہنچ گئیں۔
پرانے تعداد کے کیپ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) کا اب بھی احترام کیا جاتا ہے، لیکن
صرف اس صورت میں جب آپ اسے واضح طور پر سیٹ کریں۔

جب گنجائش مصروف ہو، تو بھاری درخواست دوبارہ کوشش کے قابل `503` کا جواب دینے سے پہلے کسی سلاٹ
کے خالی ہونے کے لیے `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ڈیفالٹ `2000`، `0` انتظار کو غیر فعال
کرتا ہے) تک انتظار کرتی ہے۔ یہ محدود انتظار اس لیے موجود ہے تاکہ ایجنٹ طرز کے کلائنٹس
(OpenCode، Claude Code، Cursor)، جو بھاری ذیلی درخواستیں بیک وقت فین آؤٹ کرتے ہیں، فوری
مستردگیوں پر اپنے پورے دوبارہ کوشش کے بجٹ کو ضائع کرنے اور کام کے درمیان ناکام ہونے کے بجائے
برسٹ کو سلسلہ وار کریں۔
موجودہ بھاری لیز کی مصروفیت، طے شدہ بائٹ بجٹ، اور براہِ راست دباؤ کی شدت
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`، `maxInflightBytes`،
`budgetSource`، `pressureSeverity`، `countCapEnabled`) پر ظاہر کی جاتی ہیں — کسی بھی env var کو
تبدیل کرنے سے پہلے انہیں چیک کریں۔
Settings → Resilience → Request Queue → Concurrent Requests اسے کنٹرول نہیں کرتی؛ یہ ترتیب
فراہم کنندہ کی درخواستوں کی قطار کے ایک علیحدہ طریقۂ کار کو کنٹرول کرتی ہے۔

**حل:**

1. پہلے دوبارہ کوشش کریں۔ کلائنٹس کو فوری طور پر درخواست دہرانے کے بجائے `Retry-After` کا
   احترام کرنا اور بیک آف استعمال کرنا چاہیے۔
2. کچھ بھی ٹیون کرنے سے پہلے `/api/monitoring/health` → `chatAdmission` چیک کریں۔ `countCapEnabled:
false` اور فراخ `maxInflightBytes` کا مطلب ہے کہ خودکار طور پر اخذ شدہ بجٹ پہلے ہی اپنا
   کام کر رہا ہے؛ `high`/`critical` کی `pressureSeverity` کا مطلب ہے کہ میزبان کے پاس واقعی
   میموری کم ہے — اسے کسی ایڈمیشن env var سے درست نہیں کیا جا سکتا، اس کے لیے زیادہ RAM یا
   کم کام کا بوجھ درکار ہے۔
3. صرف اس صورت میں جب `/api/monitoring/health` یہ دکھائے کہ خودکار طور پر اخذ شدہ بجٹ واقعی
   آپ کے میزبان کے لیے بہت کم ہے (جو شاذ و نادر ہوتا ہے — یہ پہلے ہی کنٹینر سے بیئر میٹل تک
   اسکیل کرتا ہے)، لیگیسی درخواست-تعداد کیپ پر واپس جانے کے بجائے اسے براہِ راست
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` کے ذریعے اوور رائیڈ کریں۔

مستند ایڈمیشن ترتیبات کے لیے [ماحولیاتی متغیرات کا حوالہ](../reference/ENVIRONMENT.md#4-security--authentication)
دیکھیں۔

## اختیاری RAG / LLM ناکامیوں کی درجہ بندی (16 مسائل)

OmniRoute کے کچھ صارفین گیٹ وے کو RAG یا ایجنٹ اسٹیکس کے سامنے رکھتے ہیں۔ ان سیٹ اپس میں ایک عجیب صورتِ حال عام طور پر دیکھنے میں آتی ہے: OmniRoute صحت مند نظر آتا ہے (فراہم کنندگان فعال، روٹنگ پروفائلز درست، شرح کی حد کے کوئی انتباہات نہیں) لیکن حتمی جواب پھر بھی غلط ہوتا ہے۔

عملی طور پر یہ واقعات عموماً خود گیٹ وے کے بجائے ڈاؤن اسٹریم RAG پائپ لائن کی وجہ سے پیش آتے ہیں۔

اگر آپ ان ناکامیوں کو بیان کرنے کے لیے مشترکہ اصطلاحات چاہتے ہیں، تو آپ WFGY ProblemMap استعمال کر سکتے ہیں، جو MIT لائسنس کے تحت ایک بیرونی متنی وسیلہ ہے اور RAG / LLM کی ناکامی کے سولہ بار بار پیش آنے والے نمونوں کی وضاحت کرتا ہے۔ اعلیٰ سطح پر یہ درج ذیل کا احاطہ کرتا ہے:

- بازیافت میں انحراف اور سیاق کی ٹوٹی ہوئی حدود
- خالی یا فرسودہ انڈیکسز اور ویکٹر اسٹورز
- ایمبیڈنگ اور معنوی مطابقت میں فرق
- پرامپٹ کی تشکیل اور سیاقی ونڈو کے مسائل
- منطق کا انہدام اور حد سے زیادہ پراعتماد جوابات
- طویل چین اور ایجنٹ کی ہم آہنگی کی ناکامیاں
- متعدد ایجنٹس کی میموری اور کردار میں انحراف
- تعیناتی اور بوٹسٹریپ کی ترتیب کے مسائل

تصور سادہ ہے:

1. کسی خراب جواب کی چھان بین کرتے وقت، یہ معلومات محفوظ کریں:
   - صارف کا کام اور درخواست
   - OmniRoute میں روٹ یا فراہم کنندگان کا مجموعہ
   - ڈاؤن اسٹریم استعمال ہونے والا کوئی بھی RAG سیاق (بازیافت شدہ دستاویزات، ٹول کالز وغیرہ)
2. واقعے کو WFGY ProblemMap کے ایک یا دو نمبروں (`No.1` … `No.16`) سے منسلک کریں۔
3. نمبر کو OmniRoute لاگز کے ساتھ اپنے ڈیش بورڈ، رن بک، یا واقعہ ٹریکر میں محفوظ کریں۔
4. متعلقہ WFGY صفحہ استعمال کرکے فیصلہ کریں کہ آیا آپ کو اپنے RAG اسٹیک، بازیافت کنندہ، یا روٹنگ حکمتِ عملی میں تبدیلی کرنے کی ضرورت ہے۔

مکمل متن اور عملی ترکیبیں یہاں دستیاب ہیں (MIT لائسنس، صرف متن):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

اگر آپ OmniRoute کے پیچھے RAG یا ایجنٹ پائپ لائنز نہیں چلاتے، تو اس حصے کو نظر انداز کر سکتے ہیں۔

## v3.8.0 کے معلوم مسائل

v3.8.0 ریلیز سے متعلق مخصوص مسائل اور ان کے موجودہ عارضی حل۔ اگر کسی بعد کے پیچ میں اصلاح شامل ہو جاتی ہے، تو اندراج کو اپ ڈیٹ یا حذف کر دیا جائے گا۔

### Devin CLI کی توثیق میں ناکامیاں

**علامات:**

- Devin پر مبنی ٹولز استعمال کرتے وقت "Devin CLI نہیں ملا" یا "توثیق ناکام ہو گئی"
- CLI رن ٹائم جانچ `installed=false` رپورٹ کرتی ہے

**وجوہات:**

- `CLI_DEVIN_BIN` ایک ایسے راستے کی طرف اشارہ کرتا ہے جو موجود نہیں
- میزبان پر Devin CLI انسٹال نہیں ہے

**حل:**

1. اپنے پلیٹ فارم کے لیے Devin CLI انسٹال کریں
2. `.env` میں `CLI_DEVIN_BIN=/usr/local/bin/devin` (یا اصل راستہ) مقرر کریں
3. OmniRoute دوبارہ شروع کریں اور **ڈیش بورڈ → CLI ٹولز** سے دوبارہ جانچ کریں

### ماڈل کول ڈاؤن پھنسا ہوا ہے (دستی ری سیٹ)

**علامات:**

- میعاد ختم ہونے کا وقت گزر جانے کے بعد بھی ماڈل کول ڈاؤن میں درج رہتا ہے
- ٹائم اسٹیمپ ماضی کا ہونے کے باوجود کومبو روٹنگ میں درخواستیں اب بھی ماڈل کو نظر انداز کرتی ہیں

**دستی ری سیٹ:**

- **ڈیش بورڈ:** **ترتیبات → ماڈل کول ڈاؤنز** → متاثرہ کارڈ پر **دوبارہ فعال کریں** پر کلک کریں
- **API:** انتظامی توثیقی ہیڈرز کے ساتھ `DELETE /api/resilience/model-cooldowns`

### Command Code فراہم کنندہ کا کنکشن 403 کے ساتھ ناکام ہوتا ہے

**علامات:**

- Command Code فراہم کنندہ کے کنکشن کی جانچ کرتے وقت 403
- نیا شامل کرنے کے بعد فراہم کنندہ کا کارڈ "غیر مجاز" دکھاتا ہے

**وجہ:** OAuth فلو مکمل نہیں ہوا (کال بیک موصول نہیں ہوا یا ٹوکن محفوظ نہیں کیا گیا)۔

**حل:**

- OAuth فلو کو دوبارہ متحرک کرنے کے لیے CLI سے `omniroute providers` چلائیں، یا
- **ڈیش بورڈ → فراہم کنندگان → Command Code → دوبارہ منسلک کریں** سے OAuth دوبارہ چلائیں

### ModelScope جارحانہ 429 کول ڈاؤنز واپس کرتا ہے

**علامات:**

- درخواستوں کے معمولی برسٹ کے بعد ModelScope پر بہت مختصر یا فوری کول ڈاؤنز
- کومبو روٹنگ توقع سے پہلے ModelScope کو نظر انداز کرتی ہے

**وجہ:** ModelScope فراہم کنندہ کے لیے مخصوص `Retry-After` ہیڈرز بھیجتا ہے۔ v3.8.0 میں ان ہیڈرز کے لیے مخصوص ہینڈلنگ شامل ہے، اس لیے پرانے ورژن انہیں عمومی شرح کی حد کے اشاروں کے طور پر غلط پڑھتے ہیں۔

**حل:**

- یقینی بنائیں کہ آپ v3.8.0 یا اس کے بعد کا ورژن استعمال کر رہے ہیں
- تصدیق کریں کہ **ترتیبات → لچک** کے تحت `useUpstream429BreakerHints` ٹوگل فعال ہے

### پروڈکشن میں OMNIROUTE_WS_BRIDGE_SECRET موجود نہیں

**علامات:**

- ریموٹ پروڈکشن میزبان پر چلتے وقت ہر Codex/Responses WebSocket برج درخواست پر 401
- منسلک ہونے کے فوراً بعد WebSocket برج ہینڈ شیک بند ہو جاتا ہے

**وجہ:** پروڈکشن ماحول میں `OMNIROUTE_WS_BRIDGE_SECRET` ماحولیاتی متغیر موجود نہیں ہے۔

**حل:**

1. ایک بے ترتیب سیکرٹ بنائیں: `openssl rand -hex 32`
2. پروڈکشن سرور کے ماحول میں `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` مقرر کریں (اور برج سے رابطہ کرنے والے کسی بھی کلائنٹ میں بھی)
3. OmniRoute دوبارہ شروع کریں

### Responses API: پسِ منظر موڈ ہم وقت عمل درآمد میں تنزلی کا شکار

**علامات:**

- لاگ شدہ انتباہ: `background mode degraded to synchronous`
- `background: true` درخواست پسِ منظر جاب ہینڈل کے بجائے ایک عام ہم وقت جواب واپس کرتی ہے

**وجہ:** v3.8.0 میں Responses API پر `background: true` کو دانستہ طور پر ہم وقت عمل درآمد میں تبدیل کیا جاتا ہے اور ساتھ ایک انتباہ جاری کیا جاتا ہے۔ مکمل غیر ہم وقت پسِ منظر عمل درآمد مستقبل میں فراہم کیا جائے گا۔

**حل:**

- کلائنٹ کو `background` کے بغیر کال کرنے کے لیے ایڈجسٹ کریں، یا
- مکمل غیر ہم وقت پسِ منظر موڈ فراہم کرنے والی بعد کی ریلیز کا انتظار کریں (چینج لاگ پر نظر رکھیں)

## سست آغاز / تیاری کا ٹائم آؤٹ

اگر CLI پر `⚠ Server did not respond within 60s` ظاہر ہو لیکن سرور
حقیقت میں کام کر رہا ہو، تو آپ کے ماحول کے لیے تیاری کی جانچ کا مقررہ وقت بہت کم ہے۔

یہ عام طور پر Windows (اینٹی وائرس، فائل سسٹم واچرز) یا زیادہ ابتدائی کام کے بوجھ
والے کنٹینرز میں ہوتا ہے۔

**حل — مقررہ وقت بڑھائیں:**

```bash
# ماحول کے متغیر کے ذریعے (آغاز کے درمیان برقرار رہتا ہے):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 منٹ
omniroute serve

# CLI فلیگ کے ذریعے (صرف ایک بار):
omniroute serve --ready-timeout 180000
```

پہلے سے طے شدہ مدت 60 000 ms (60 s) ہے۔ یہ انتباہ صرف معلوماتی ہے؛ سرور
پس منظر میں شروع ہوتا رہتا ہے اور بوٹ مکمل ہونے کے بعد قابلِ رسائی ہو جائے گا۔

`OMNIROUTE_READY_TIMEOUT_MS` کی مکمل تفصیلات کے لیے
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md) دیکھیں۔
