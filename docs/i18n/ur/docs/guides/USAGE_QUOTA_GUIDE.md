## جائزہ

OmniRoute سے گزرنے والی ہر درخواست ایک **استعمال کا ریکارڈ** بناتی ہے، جس میں درج ذیل معلومات محفوظ ہوتی ہیں:

- **شناخت**: کون سی API کلید، فراہم کنندہ، ماڈل، کومبو
- **ٹوکنز**: پرامپٹ ٹوکنز، تکمیلی ٹوکنز، کیش شدہ ٹوکنز، کل تعداد
- **لاگت**: USD رقم (قیمتوں کے ڈیٹا سے حساب کی گئی)
- **وقت**: تاخیر، آغاز/اختتام کے ٹائم اسٹیمپس
- **حالت**: کامیابی، خرابی، شرح کی حد کا اطلاق، وغیرہ

```
درخواست ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    تجزیات     کوٹا    بلنگ
                    (ڈیش بورڈ) (نفاذ)  (برآمد)
```

## کیا ریکارڈ کیا جاتا ہے

`usage.ts` سروس ہر درخواست کے لیے ایک **استعمال کا واقعہ** محفوظ کرتی ہے:

| فیلڈ               | قسم     | ماخذ                                                       |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | ریکارڈ بناتے وقت تیار کردہ UUID                            |
| `apiKeyId`         | string  | وہ API کلید جس نے درخواست شروع کی                          |
| `provider`         | string  | فراہم کنندہ کی ID (openai، anthropic، وغیرہ)               |
| `model`            | string  | ماڈل ID (gpt-5، claude-opus-4-6، وغیرہ)                    |
| `comboId`          | string? | اگر کومبو کے ذریعے روٹنگ ہوئی ہو تو کومبو ID               |
| `promptTokens`     | number  | اپ اسٹریم جواب سے                                          |
| `completionTokens` | number  | اپ اسٹریم جواب سے                                          |
| `cachedTokens`     | number  | کیش ہٹ ٹوکنز (Anthropic پرامپٹ کیشنگ، وغیرہ)               |
| `totalTokens`      | number  | پرامپٹ + تکمیل                                             |
| `costUsd`          | number  | قیمتوں کے ڈیٹا سے حساب کی گئی                              |
| `latencyMs`        | number  | درخواست کا آغاز سے اختتام تک دورانیہ                       |
| `status`           | enum    | `success`، `error`، `rate_limited`، `timeout`، `cancelled` |
| `errorClass`       | string? | اگر status != success ہو تو خرابی کی کلاس                  |
| `timestamp`        | string  | ISO 8601 UTC                                               |
| `metadata`         | object  | پلگ اِن کے ذریعے شامل کردہ حسبِ ضرورت ڈیٹا                 |

### ٹوکنز کہاں سے آتے ہیں

ٹوکنز کو **ریسپانس ہینڈلر** میں اپ اسٹریم فراہم کنندہ کے جواب سے اخذ کیا جاتا ہے:

```ts
// open-sse/handlers/chatCore.ts سے
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

ایسے فراہم کنندگان کے لیے جو استعمال کی معلومات واپس نہیں کرتے (کچھ ویب کوکی فراہم کنندگان)، OmniRoute ٹوکنز کا تخمینہ `~4 chars per token` کے اصولِ تخمینہ سے لگاتا ہے (`open-sse/services/autoCombo/pipelineRouter.ts` دیکھیں)۔

### کیش شدہ ٹوکنز

OmniRoute، `cached_tokens` کو `prompt_tokens` سے الگ ٹریک کرتا ہے کیونکہ:

- Anthropic پرامپٹ کیشنگ، کیش شدہ ٹوکنز کے لیے کم شرح وصول کرتی ہے (معمول کی شرح کا 10%)
- کچھ فراہم کنندگان `cache_read_input_tokens` واپس کرتے ہیں، جن کی قیمت مختلف طریقے سے شمار ہونی چاہیے
- تجزیات **کیش ہٹ شرح** دکھا سکتے ہیں = `cached_tokens / prompt_tokens`

## لاگت کا حساب

لاگت کا حساب LiteLLM سے ہم وقت کیے گئے **قیمتوں کے ڈیٹا** (`src/lib/pricingSync.ts`) کی بنیاد پر کیا جاتا ہے:

| ماڈل              | اِن پٹ $/1M | آؤٹ پٹ $/1M | کیش شدہ $/1M |
| ----------------- | ----------- | ----------- | ------------ |
| gpt-5             | $2.50       | $10.00      | —            |
| claude-opus-4-6   | $15.00      | $75.00      | $1.50        |
| claude-sonnet-4-5 | $3.00       | $15.00      | $0.30        |
| gemini-2.5-pro    | $1.25       | $10.00      | —            |

لاگت کا فارمولا (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **کیش شدہ ٹوکنز کو پرامپٹ سے کیوں منہا کیا جاتا ہے؟** کیش شدہ حصے کی قیمت الگ سے مقرر کی جاتی ہے؛ پورے پرامپٹ پر اِن پٹ کی قیمت عائد کرنے سے لاگت زائد شمار ہوگی۔

### قیمتوں کی ہم وقتی

قیمتوں کا ڈیٹا `/api/pricing/sync` اینڈ پوائنٹ کے ذریعے LiteLLM سے خودکار طور پر ہم وقت کیا جاتا ہے (یہ بلٹ اِن cron ٹاسک کے ذریعے متحرک ہوتا ہے، صارف کے لیے دستیاب env var کے ذریعے نہیں):

```bash
# دستی طور پر متحرک کریں
curl -X POST http://localhost:20128/api/pricing/sync
```

جن ماڈلز کے لیے قیمتوں کا ڈیٹا دستیاب نہ ہو، ان کی **تخمینی لاگت** معلوم کرنے کے لیے OmniRoute داخلی اوسط نرخ استعمال کرتا ہے (جو LiteLLM کے قیمتوں کے ڈیٹا سے حاصل کیے گئے ہیں)۔

## تاریخ کی حد کے لحاظ سے مجموعہ

`usageAnalytics.ts` ماڈیول استعمال کے خام ڈیٹا سے ڈیش بورڈ وجٹس کا حساب لگاتا ہے۔ یہ وقت کی 7 حدود کی معاونت کرتا ہے:

| حد       | دورانیہ                                   | استعمال کا مقصد                    |
| -------- | ----------------------------------------- | ---------------------------------- |
| `1d`     | گزشتہ 24 گھنٹے                            | فی گھنٹہ لاگت میں اضافے کی نشاندہی |
| `7d`     | گزشتہ 7 دن                                | ہفتہ وار جائزہ                     |
| `30d`    | گزشتہ 30 دن                               | ماہانہ بلنگ                        |
| `90d`    | گزشتہ 90 دن                               | سہ ماہی تجزیہ                      |
| `ytd`    | موجودہ سال کی 1 جنوری سے                  | سالانہ بجٹ کی نگرانی               |
| `all`    | تمام عرصہ                                 | مجموعی اعداد و شمار                |
| `custom` | صارف کی متعین کردہ آغاز/اختتام کی تاریخیں | آڈٹس، حسبِ ضرورت استفسارات         |

### حساب کیے جانے والے ڈیش بورڈ وجٹس

کسی بھی تاریخ کی حد کے لیے، تجزیاتی پرت درج ذیل کا حساب لگاتی ہے:

| وجٹ                      | تفصیل                                                     |
| ------------------------ | --------------------------------------------------------- |
| **خلاصہ کارڈز**          | کل درخواستیں، کل لاگت، کل ٹوکنز، کامیابی کی شرح           |
| **روزانہ رجحان کا چارٹ** | یومیہ لاگت + ٹوکنز، ماڈل کے لحاظ سے تہہ در تہہ            |
| **سرگرمی کا ہیٹ میپ**    | دن کے گھنٹے × ہفتے کے دن کا گرڈ، رنگ = درخواستوں کی تعداد |
| **ماڈل کی تفصیل**        | ماڈل کے لحاظ سے لاگت کا پائی چارٹ                         |
| **فراہم کنندہ کی تفصیل** | فراہم کنندہ کے لحاظ سے درخواستوں کا بار چارٹ              |
| **سرفہرست API کلیدیں**   | لاگت کے لحاظ سے سرفہرست 10 کلیدوں کی جدول                 |
| **خرابیوں کا تجزیہ**     | وقت کے ساتھ خرابی کی شرح، سرفہرست خرابی کی کلاسیں         |

### پروگرام کے ذریعے رسائی

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // استعمال کی تاریخ کے ریکارڈز
  "7d",                 // وقت کی حد: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // فراہم کنندہ کے کنکشن کا نقشہ (connectionId → اکاؤنٹ کا نام)
  {
    startDate: "2025-01-01",  // اختیاری: "custom" حد کے لیے
    endDate: "2025-06-01",   // اختیاری: "custom" حد کے لیے
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (سینٹس)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## کوٹا کا نفاذ

فی API کلید کوٹا دو جگہوں پر نافذ کیا جاتا ہے:

1. **نرم حد** (`quotaWarnAt`): استعمال کی مقررہ حد سے تجاوز ہونے پر ڈیش بورڈ میں تنبیہ
2. **سخت حد** (`quotaLimit`): حد سے تجاوز ہونے پر درخواست HTTP 429 کے ساتھ مسترد کر دی جاتی ہے

### ترتیب

```ts
// فی API کلید
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — تنبیہ دکھائیں
  quotaLimit: 10_00,    // $10.00 — مکمل پابندی
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### نفاذ کا بہاؤ

```
درخواست ──▶ quotaCheck()
              │
              ├── حد کے اندر؟  ──▶ اجازت دیں
              │
              └── حد سے تجاوز؟  ──▶ 429 بہت زیادہ درخواستیں
                                   Retry-After ہیڈر کے ساتھ
```

### کوٹا اسنیپ شاٹس

`quotaSnapshots` ٹیبل رجحانات کے تجزیے کے لیے **کوٹے کی تاریخی حالت** محفوظ کرتا ہے:

| فیلڈ | تفصیل |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | وہ کلید جس کی نگرانی کی جا رہی ہے |
| `window` | "day" | "week" | "month" |
| `used` | اس ونڈو میں استعمال ہونے والی لاگت (سینٹس) |
| `limit` | حد (سینٹس) |
| `resetAt` | ونڈو کب ری سیٹ ہوتی ہے |
| `createdAt` | اسنیپ شاٹ کب لیا گیا |

ہر ایسی درخواست پر اسنیپ شاٹس لیے جاتے ہیں جس کی لاگت > 0 ہو، اور انہیں درج ذیل مقاصد کے لیے استعمال کیا جاتا ہے:

- ڈیش بورڈ میں کوٹے کی پیش رفت کا بار دکھانا
- 30 دن کے کوٹا رجحان کے چارٹس دکھانا
- استعمال کے حد کے قریب پہنچنے پر انتباہات فعال کرنا


### استعمال کے تجزیات سے استفسار

استعمال کے ڈیٹا تک براہ راست REST برآمدی اینڈ پوائنٹس کے بجائے ڈیش بورڈ یا MCP ٹولز کے ذریعے رسائی حاصل کی جاتی ہے۔ دستیاب تجزیات:

- **`/api/usage/analytics`** — مجموعی استعمال کے میٹرکس (ماڈل، فراہم کنندہ، کلید کے لحاظ سے گروپ کریں)
- **`/api/usage/quota`** — ہر API کلید کے لیے کوٹے کی موجودہ حالت
- **`/api/usage/history`** — درخواستوں کی تاریخ کے لاگز

---

## MCP ٹولز

دو MCP ٹولز ایجنٹس کے لیے استعمال کا ڈیٹا دستیاب کرتے ہیں (`open-sse/mcp-server/tools/` دیکھیں):

| ٹول                     | تفصیل                                                |
| ----------------------- | ---------------------------------------------------- |
| `omniroute_cost_report` | دی گئی مدت کے لیے فی کلید لاگت کی رپورٹ تیار کرتا ہے |
| `omniroute_check_quota` | API کلید کے لیے کوٹے کی موجودہ حالت واپس کرتا ہے     |

ایجنٹ کی طلب کی مثال:

```json
{
  "tool": "omniroute_cost_report",
  "args": { "period": "week" }
}
```

## برقرار رکھنا اور صفائی

استعمال کا ڈیٹا ہر درخواست کے ساتھ تقریباً ~1-10KB بڑھتا ہے۔ بڑے پیمانے پر یہ مقدار قابلِ ذکر ہو سکتی ہے۔

### برقرار رکھنے کی ترتیبات

استعمال کی ہسٹری برقرار رکھنے کی مدت UI میں Database Settings کے ذریعے یا `/api/settings/database` کے ذریعے ترتیب دی جاتی ہے۔

بطور ڈیفالٹ، استعمال کی ہسٹری **90 دنوں** تک برقرار رکھی جاتی ہے۔

### صفائی

پرانے ریکارڈز کو `src/lib/db/cleanup.ts` کے ذریعے صاف کیا جاتا ہے:

- پس منظر میں چلنے والے cron پراسیس کے ذریعے متحرک ہوتا ہے
- ترتیب شدہ `usageHistory` برقرار رکھنے کی مدت سے پرانے ریکارڈز کو `usage_history` سے حذف کرتا ہے

### اسٹوریج کا تخمینہ

| درخواستوں کی شرح     | 30 دن کا اسٹوریج | 90 دن کا اسٹوریج |
| -------------------- | ---------------- | ---------------- |
| 100 درخواستیں/دن     | ~3MB             | ~9MB             |
| 1,000 درخواستیں/دن   | ~30MB            | ~90MB            |
| 10,000 درخواستیں/دن  | ~300MB           | ~900MB           |
| 100,000 درخواستیں/دن | ~3GB             | ~9GB             |

بہت زیادہ ٹریفک کی صورت میں، ان اقدامات پر غور کریں:

- Database Settings کے ذریعے برقرار رکھنے کی مدت کم کرنا
- خام ریکارڈز کے بجائے `aggregated_metrics` استعمال کرنا (صرف تجزیات کے لیے)

## لاگت بہتر بنانے کے نکات

### 1. درست ماڈل استعمال کریں

```bash
# فوری جواب — سستا + تیز استعمال کریں
curl -d '{"model":"auto/fast","messages":[...]}'

# پیچیدہ کام — اعلیٰ معیار استعمال کریں
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. کیشنگ فعال کریں

Anthropic پرامپٹ کیشنگ **دہرائے جانے والے سیاق و سباق پر 90% بچت** کرتی ہے:

```ts
// کیشنگ خودکار ہے — بس وہی بڑا سسٹم پرامپٹ شامل کریں
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // خودکار طور پر کیش ہو جائے گا
  messages: [{ role: "user", content: "..." }],
});
```

### 3. کمپریشن استعمال کریں

RTK + Caveman کمپریشن **ٹولز کے زیادہ استعمال والے سیشنز میں 15-95% بچت** کرتی ہے:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. ہر کلید کے لیے کوٹہ مقرر کریں

بے قابو اخراجات روکنے کے لیے ہمیشہ `quotaLimit` مقرر کریں:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // $10/ماہ کی حد
```

### 5. سب سے زیادہ استعمال کرنے والوں کا آڈٹ کریں

API کلید کے لحاظ سے گروپ بنانے اور لاگت کے لحاظ سے ترتیب دینے کے لیے ڈیش بورڈ یا **`/api/usage/analytics`** استعمال کریں:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## خرابیوں کا ازالہ

### "لاگت توقع سے زیادہ ہے"

1. **`/api/usage/analytics?groupBy=model`** چیک کریں — مہنگا ماڈل تلاش کریں
2. **`/api/usage/analytics?groupBy=apiKey`** چیک کریں — زیادہ استعمال کرنے والا صارف تلاش کریں
3. تصدیق کریں کہ قیمتوں کا ڈیٹا تازہ ترین ہے: `POST /api/pricing/sync`

### "ریکارڈز موجود نہیں ہیں"

- Dashboard → Database → Cleanup کے تحت DB برقرار رکھنے کی ترتیبات چیک کریں — پرانے ریکارڈز متواتر صفائی کے کام (`src/lib/db/cleanup.ts`) کے ذریعے حذف کیے جاتے ہیں
- `src/lib/db/usage*.ts` میں خرابیوں کی جانچ کریں — DB میں تحریر کی ناکامیاں لاگ کی جاتی ہیں لیکن ظاہر نہیں کی جاتیں
- تصدیق کریں کہ درخواست واقعی `chatCore` تک پہنچی تھی — combo روٹنگ چیک کریں

### "کوٹہ نافذ نہیں ہو رہا"

- کلید کی `quotaLimit` ترتیب چیک کریں
- تصدیق کریں کہ `quotaWindow` درست طور پر مقرر ہے
- `quotaSnapshots` ریکارڈز تلاش کریں — انہیں ہر درخواست پر بننا چاہیے
