RTK کمپریشن ٹرمینل اور ٹول آؤٹ پٹ کے لیے OmniRoute کا کمانڈ سے باخبر کمپریشن انجن ہے۔ اسے
کوڈنگ ایجنٹ سیشنز کے لیے ڈیزائن کیا گیا ہے، جہاں سیاق و سباق میں زیادہ تر اضافہ ٹیسٹ لاگز، بلڈ آؤٹ پٹ،
پیکیج مینیجر کے غیر ضروری پیغامات، شیل ٹرانسکرپٹس، Docker آؤٹ پٹ، git آؤٹ پٹ، اور اسٹیک ٹریسز سے ہوتا ہے۔

RTK براہ راست `defaultMode: "rtk"` کے ساتھ یا اسٹیک شدہ پائپ لائن میں پہلے مرحلے کے طور پر چل سکتا ہے، عموماً:

```txt
rtk -> caveman
```

یہ ترتیب پہلے شور سے بھرپور مشینی آؤٹ پٹ کو کمپریس کرتی ہے، پھر Caveman کو باقی نثری متن مختصر کرنے دیتی ہے۔

اپ اسٹریم RTK کمانڈ آؤٹ پٹ میں `60-90%` بچت رپورٹ کرتا ہے۔ اس کے README میں دیا گیا نمونہ سیشن
`~118,000` معیاری ٹوکنز سے کم ہو کر `~23,900` RTK ٹوکنز رہ جاتا ہے، یعنی `79.7%` بچت (`~80%`)۔ OmniRoute
Caveman ان پٹ کمپریشن کے ساتھ اسٹیک شدہ بچت کے حساب کے لیے اسی اپ اسٹریم اوسط کو استعمال کرتا ہے:

```txt
RTK اوسط:              80% بچت
Caveman ان پٹ:         46% بچت
اسٹیک شدہ:             1 - (1 - 0.80) * (1 - 0.46) = 89.2% بچت
حد:                    1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## یہ کیا کمپریس کرتا ہے

بلٹ اِن کیٹلاگ میں فی الحال ان زمروں میں 49 فلٹرز شامل ہیں:

| زمرہ      | مثالیں                                                        |
| --------- | ------------------------------------------------------------- |
| `git`     | `git status`، `git branch`، `git diff`، `git log`             |
| `test`    | Vitest، Jest، Pytest، Playwright، Go ٹیسٹس، Cargo ٹیسٹس       |
| `build`   | TypeScript، ESLint، Biome، Prettier، Vite، Webpack، Turbo، Nx |
| `package` | `npm install`، `npm audit`، `pip`، `uv sync`، Poetry، Bundler |
| `shell`   | `ls`، `find`، `grep`، عمومی شیل لاگز                          |
| `docker`  | `docker ps`، Docker لاگز                                      |
| `infra`   | Terraform، OpenTofu، `systemctl status`                       |
| `generic` | JSON آؤٹ پٹ، اسٹیک ٹریسز، عمومی آؤٹ پٹ فال بیک                |

`open-sse/services/compression/engines/rtk/commandDetector.ts` میں موجود ڈیٹیکٹر فلٹر منتخب کرنے
سے پہلے آؤٹ پٹ کی درجہ بندی کرتا ہے۔ جب کمانڈ کلاس کافی نہ ہو تو فلٹرز کمانڈ پیٹرن یا آؤٹ پٹ ریجیکس
کی بنیاد پر بھی مماثلت تلاش کر سکتے ہیں۔

## فلٹر کا تعین

RTK فلٹرز کو اس ترتیب میں لوڈ کرتا ہے:

1. `.rtk/filters.toml` اور `.rtk/filters.json` سے پروجیکٹ فلٹرز، صرف قابل اعتماد ہونے کی صورت میں۔
2. `DATA_DIR/rtk/filters.toml` اور `DATA_DIR/rtk/filters.json` سے گلوبل فلٹرز۔
3. `open-sse/services/compression/engines/rtk/filters/` سے بلٹ اِن فلٹرز۔

ایک ہی دائرۂ کار کے اندر RTK TOML schema v1 فلٹرز کو OmniRoute JSON فلٹرز پر ترجیح حاصل ہوتی ہے۔ TOML
`match_command` ایکسپریشنز کو کمانڈ ٹائپ کی مماثلت سے پہلے جانچا جاتا ہے، تاکہ امپورٹ کیا گیا کمانڈ سے مخصوص
فلٹر اسی دائرۂ کار میں زیادہ عمومی فلٹر کی جگہ لے سکے۔ فائل فارمیٹ سے قطع نظر، پروجیکٹ دائرۂ کار کو اب بھی گلوبل
دائرۂ کار پر ترجیح حاصل ہے۔

پروجیکٹ فلٹرز کو دانستہ طور پر اعتماد سے مشروط کیا گیا ہے، کیونکہ ریجیکس فلٹرز یہ تبدیل کر سکتے ہیں کہ ٹول آؤٹ پٹ
ایجنٹس کو کس طرح دکھائی جائے۔ پروجیکٹ فلٹر فائل اس وقت قبول کی جاتی ہے جب ان میں سے کوئی ایک شرط درست ہو:

- `rtkConfig.trustProjectFilters` کی قدر `true` ہو۔
- `OMNIROUTE_RTK_TRUST_PROJECT_FILTERS=1` سیٹ ہو۔
- `.rtk/trust.json` میں پروجیکٹ فلٹر فائل کے لیے مماثل SHA-256 ہیش موجود ہو۔

ٹرسٹ فائل کی مثال:

```json
{
  "filtersSha256": "0123456789abcdef...",
  "filtersTomlSha256": "fedcba9876543210..."
}
```

ہیشز الگ الگ ہیں: `filtersSha256`، `.rtk/filters.json` پر اعتماد کرتا ہے، جبکہ `filtersTomlSha256`
`.rtk/filters.toml` پر اعتماد کرتا ہے۔ دونوں میں سے کسی فائل میں ترمیم صرف اسی کی اپنی ٹرسٹ انٹری کو غیر مؤثر
کرتی ہے۔ گلوبل فائلز ایڈمنسٹریٹر کی جانب سے انسٹال کی جاتی ہیں اور موجودہ گلوبل فلٹر اعتماد کے طرزِ عمل کو استعمال کرتی ہیں۔

کسٹم فلٹرز ایک فلٹر آبجیکٹ یا فلٹر آبجیکٹس کی ایک ارے ہو سکتے ہیں۔ غیر موزوں کسٹم فلٹرز کو چھوڑ دیا جاتا ہے اور
`/api/context/rtk/filters` کی تشخیص میں رپورٹ کیا جاتا ہے۔ غیر موزوں بلٹ اِن فلٹرز فوری طور پر ناکام ہو جاتے ہیں۔

## RTK TOML اسکیما v1 مطابقت

OmniRoute، RTK TOML اسکیما v1 استعمال کرنے والی اعلانیہ فلٹر فائلوں کو پارس، توثیق، جانچ اور انسٹال کر سکتا ہے۔
معاونت یافتہ فیلڈز `description`، `match_command`، `strip_ansi`، `filter_stderr`،
`strip_lines_matching`، `keep_lines_matching`، `replace`، `match_output`، `truncate_lines_at`،
`head_lines`، `tail_lines`، `max_lines`، `on_empty`، اور `[[tests.<filter>]]` اِن لائن ٹیسٹس ہیں۔
نامعلوم فیلڈز، غلط یا غیر محفوظ ریگولر ایکسپریشنز، بیک وقت strip/keep قواعد، 1 MiB سے بڑی فائلیں،
اور نامعلوم فلٹرز کے حوالہ جات مسترد کر دیے جاتے ہیں۔ ایسی فائل جس کے اِن لائن ٹیسٹس ناکام ہوں،
معائنے کے لیے اس کی توثیق کی جا سکتی ہے، لیکن اسے انسٹال یا لوڈ نہیں کیا جا سکتا۔ حسبِ ضرورت فائل
لوڈ ہونے میں ناکامیاں بدستور fail-open رہتی ہیں: غلط فائل کو چھوڑ دیا جاتا ہے اور باقی فلٹرز کام کرتے رہتے ہیں۔

OmniRoute کو ٹول کا آؤٹ پٹ اس وقت موصول ہوتا ہے جب کلائنٹ اسے پہلے ہی کیپچر کر چکا ہوتا ہے، اس لیے `filter_stderr = true`
پروسیس کیپچر کو تبدیل نہیں کر سکتا۔ یہ فیلڈ no-op کے طور پر قبول کی جاتی ہے اور توثیق ایک انتباہ واپس کرتی ہے۔
اسے جان بوجھ کر **RTK TOML اسکیما v1 مطابقت** کے طور پر بیان کیا گیا ہے، نہ کہ RTK executable،
shell hooks، Rust کمانڈ implementations، یا اس کے trust-store layout کے ساتھ مکمل مطابقت کے طور پر۔

ڈیش بورڈ کا advanced RTK view پیسٹ یا اپ لوڈ کردہ TOML قبول کرتا ہے۔ توثیق صرف پڑھنے تک محدود ہے۔
انسٹالیشن پابندی والی اجازتوں کے ساتھ `DATA_DIR/rtk/filters.toml` کو اٹامک انداز میں لکھتی ہے اور
بغیر ری اسٹارٹ کیے فعال فلٹر کیٹلاگ کو تازہ کرتی ہے۔ موجودہ فائل کو تبدیل کرنے کے لیے واضح `overwrite`
تصدیق درکار ہوتی ہے اور پہلے `DATA_DIR/rtk/filters.toml.bak` بنائی جاتی ہے۔

## فلٹر DSL

فلٹرز [Compression Rules Format](./COMPRESSION_RULES_FORMAT.md) میں بیان کردہ JSON اسکیما استعمال کرتے ہیں۔
رن ٹائم ان مراحل کو اسی ترتیب سے لاگو کرتا ہے:

```txt
stripAnsi -> filterStderr -> replace -> matchOutput -> لائنوں کو حذف/شامل کریں
  -> truncateLineAt -> head/tail/maxLines -> onEmpty
```

اہم فیلڈز:

| فیلڈ                         | مقصد                                                            |
| ---------------------------- | --------------------------------------------------------------- |
| `rules.stripAnsi`            | میچنگ سے پہلے ٹرمینل کے رنگ/کنٹرول سیکوئنسز ہٹائیں              |
| `rules.filterStderr`         | میچنگ/فلٹرنگ سے پہلے عام stderr سابقوں کو معمول پر لائیں        |
| `rules.replace`              | ترتیب وار regex تبدیلیاں لاگو کریں                              |
| `rules.matchOutput`          | جب آؤٹ پٹ کسی معلوم حالت سے مماثل ہو تو مختصر خلاصہ واپس کریں   |
| `rules.matchOutput[].unless` | کسی error/failure پیٹرن کی موجودگی میں شارٹ کٹ چھوڑ دیں         |
| `rules.dropPatterns`         | غیر ضروری شور والی لائنیں ہٹائیں                                |
| `rules.includePatterns`      | قابلِ عمل لائنوں کو ترجیح دیں                                   |
| `rules.collapsePatterns`     | بار بار آنے والی مماثل لائنوں کو یکجا کریں                      |
| `rules.deduplicate`          | فی فلٹر اختیاری فعال کاری: مسلسل دہرائی گئی لائنوں کو یکجا کریں |
| `rules.truncateLineAt`       | Unicode-محفوظ فی لائن اختصار                                    |
| `rules.onEmpty`              | اگر تمام لائنیں فلٹر ہو جائیں تو متبادل پیغام                   |
| `tests[]`                    | verify gate کے استعمال کردہ اِن لائن نمونے                      |

بلٹ اِن فلٹرز میں اِن لائن `tests[]` نمونے شامل ہونا متوقع ہے۔ حسبِ ضرورت فلٹرز میں بھی انہیں شامل کرنا چاہیے،
خصوصاً جب وہ مختلف پروجیکٹس میں مشترکہ طور پر استعمال کیے جائیں۔

## لائن کی تکرار ختم کرنا (دو سطحیں)

RTK نقل شدہ لائنوں کو دو آزاد سطحوں پر یکجا کرتا ہے:

1. **فی فلٹر `deduplicate` (اختیاری، ڈیفالٹ `false`)۔** کوئی فلٹر `rules.deduplicate: true`
   مقرر کر سکتا ہے تاکہ تراشنے سے پہلے، _اس فلٹر کے مماثل آؤٹ پٹ کے اندر_ مسلسل نقل شدہ لائنوں کو یکجا کیا جا سکے۔
   یہ عمل `lineFilter.ts` کے اندر چلتا ہے۔ پرانے فلٹرز کے لیے، جب فلٹر
   `collapsePatterns` کی تعریف کرتا ہے تو یہ خودکار طور پر فعال ہو جاتا ہے۔ اسکیما:
   `open-sse/services/compression/engines/rtk/filterSchema.ts` میں `deduplicate: z.boolean().default(false)`۔
2. **پورے انجن پر لاگو `deduplicateThreshold` (ڈیفالٹ `3`)۔** تمام فلٹرز چلنے کے بعد، انجن پورے نتیجے میں
   `>= deduplicateThreshold` ایک جیسی مسلسل لائنوں کے ہر سلسلے کو یکجا کرتا ہے
   (`deduplicateRepeatedLines`، جو `engines/rtk/index.ts` میں لاگو ہوتا ہے)۔ نارملائزیشن کے وقت قدر کو
   2–100 تک محدود کیا جاتا ہے۔

فی فلٹر مرحلہ پہلے (فلٹر کے اندر) چلتا ہے، جبکہ پورے انجن کا مرحلہ آخر میں (جوڑے گئے
آؤٹ پٹ پر) چلتا ہے، اس لیے دونوں دگنی گنتی کے بغیر باہم کام کرتے ہیں۔

## لائنوں کی گروپ بندی (`enableGrouping`)

جب `rtkConfig.enableGrouping` کی قدر `true` ہو (ڈیفالٹ `false`)، تو RTK تکرار سے پاک نتیجے پر ایک اضافی
`groupSimilarLines` مرحلہ چلاتا ہے، جو مسلسل _تقریباً مساوی_ (بائٹ بہ بائٹ یکساں نہیں)
لائنوں کے سلسلوں کو یکجا کرتا ہے۔ `rtkConfig.groupingThreshold` (ڈیفالٹ `3`) وہ کم از کم سلسلہ لمبائی ہے جو
گروپ بندی کو فعال کرتی ہے۔ یہ `deduplicateThreshold` کا ساختی ہم منصب ہے: تکرار ختم کرنے کا عمل عین یکساں تکرار کو سنبھالتا ہے،
جبکہ گروپ بندی "چھوٹے فرق کے ساتھ ایک ہی ساخت" کو سنبھالتی ہے۔ دونوں فلیگز `key_value` ٹیبل میں برقرار رکھے گئے
`rtkConfig` JSON کا حصہ ہیں (اوپر ترتیب کاری دیکھیں)، اس لیے یہ ترتیب ری اسٹارٹس کے بعد بھی برقرار رہتی ہے۔

## کوڈ تبصرے ہٹانا (`stripCodeComments` / `preserveDocstrings`)

جب `rtkConfig.applyToCodeBlocks` فعال ہو، تو RTK فینس کیے گئے کوڈ بلاکس سے تبصرے بھی ہٹا سکتا ہے:

- `stripCodeComments` (ڈیفالٹ `false`) — اختیاری۔ `true` ہونے پر، RTK JavaScript
  اور TypeScript کے فینس کیے گئے بلاکس سے تبصرے ہٹا دیتا ہے۔ تاریخی طور پر یہ فلیگ پڑھا جاتا تھا مگر کبھی لاگو نہیں کیا گیا، اس لیے
  خاموش پیداواری تبدیلی سے بچنے کے لیے ڈیفالٹ "محفوظ رکھیں" ہی رہتا ہے۔
- `preserveDocstrings` (ڈیفالٹ `true`) — تبصرے ہٹاتے وقت، JSDoc/`/** … */` بلاک تبصرے
  محفوظ رکھے جاتے ہیں (ان میں موجود API دستاویزات کی قدر ان کے زیر استعمال بائٹس سے زیادہ ہوتی ہے)۔ انہیں بھی ہٹانے کے لیے اسے
  `false` مقرر کریں۔

تبصروں کو ہٹانے کا عمل `open-sse/services/compression/engines/rtk/codeStripper.ts` میں نافذ کیا گیا ہے۔ یہ
**TypeScript parser** استعمال کرتا ہے (regex نہیں)، تاکہ اسٹرنگ، ٹیمپلیٹ اور regex لٹرلز کو کبھی غلطی سے
تبصرے نہ سمجھا جائے، اور JSX کا پتہ چلنے پر یہ مکمل طور پر عمل روک دیتا ہے (تاکہ JSX ایکسپریشن کنٹینر کے تبصرے
کبھی خراب نہ ہوں)۔ فی الحال تبصرے ہٹانے کا اطلاق صرف **JavaScript اور TypeScript** پر ہوتا ہے — اسٹرپر کے
`CodeLanguage` مجموعے کی دیگر زبانوں (Python، Rust، Go، Ruby، Java) میں خالی لائنوں اور
وائٹ اسپیس کو یکجا کیا جاتا ہے، مگر تبصرے نہیں ہٹائے جاتے۔ اسٹرپ کیے گئے بلاک کے عمل کو
`rulesApplied` میں `rtk:code-strip` ٹیگ دیا جاتا ہے۔

> **نوٹ — GCF / جدولی انکوڈنگ ایک علیحدہ انجن ہے۔** RTK میں **"GCF"**
> (Graph Compact Format) جدولی/کالمی JSON انکوڈر شامل **نہیں** ہے۔ وہ انکوڈر — جس نے پرانے
> `omni-tabular` انکوڈر کی جگہ لی — **headroom** انجن میں موجود ہے
> (`open-sse/services/compression/engines/headroom/`، جبکہ وینڈر شدہ کوڈیک
> `headroom/gcf/` کے تحت ہے)۔ اس کا یہاں دستاویزی شکل میں بیان کردہ RTK فلٹر پائپ لائن سے کوئی تعلق نہیں ہے۔

## کنفیگریشن

عالمی ترتیبات `/api/settings/compression` کے ذریعے دستیاب ہیں۔ RTK سے مخصوص ترتیبات بھی
`/api/context/rtk/config` کے ذریعے دستیاب ہیں۔

```json
{
  "defaultMode": "stacked",
  "autoTriggerMode": "stacked",
  "autoTriggerTokens": 32000,
  "stackedPipeline": [
    { "engine": "rtk", "intensity": "standard" },
    { "engine": "caveman", "intensity": "full" }
  ],
  "rtkConfig": {
    "enabled": true,
    "intensity": "standard",
    "applyToToolResults": true,
    "applyToCodeBlocks": false,
    "applyToAssistantMessages": false,
    "enabledFilters": [],
    "disabledFilters": [],
    "maxLinesPerResult": 120,
    "maxCharsPerResult": 12000,
    "deduplicateThreshold": 3,
    "customFiltersEnabled": true,
    "trustProjectFilters": false,
    "rawOutputRetention": "never",
    "rawOutputMaxBytes": 1048576,
    "enableGrouping": false,
    "groupingThreshold": 3,
    "stripCodeComments": false,
    "preserveDocstrings": true
  }
}
```

`enabledFilters` اور `disabledFilters` فلٹر IDs استعمال کرتے ہیں، مثلاً `test-vitest` یا `git-diff`۔

`rtkConfig` کی مکمل ساخت `open-sse/services/compression/types.ts` میں `RtkConfig` /
`DEFAULT_RTK_CONFIG` کے ذریعے متعین کی گئی ہے۔ پورا آبجیکٹ SQLite کی `key_value` ٹیبل میں
`namespace = "compression"`، `key = "rtkConfig"` کے تحت ایک واحد JSON ویلیو کی صورت میں برقرار رکھا جاتا ہے
(`src/lib/db/compression.ts`)، اور پڑھتے وقت `normalizeRtkConfig` کے ذریعے معمول پر لایا جاتا ہے۔ لہٰذا ذیل کا ہر فیلڈ
— بشمول `enableGrouping`، `groupingThreshold`، `stripCodeComments`، اور `preserveDocstrings` —
اسی اسٹور کے ذریعے راؤنڈ ٹرپ کرتا ہے اور دوبارہ شروع ہونے کے بعد بھی برقرار رہتا ہے۔

| کلید                   | ڈیفالٹ  | مقصد                                                                               |
| ---------------------- | ------- | ---------------------------------------------------------------------------------- |
| `deduplicateThreshold` | `3`     | پورے انجن کے لیے: یکساں متواتر لائنوں کو سمیٹنے کی کم از کم تعداد (2–100 تک محدود) |
| `enableGrouping`       | `false` | اختیاری: تقریباً مساوی متواتر لائنوں کے سلسلوں کو سمیٹیں                           |
| `groupingThreshold`    | `3`     | متشابہ متواتر لائنوں کے سلسلے کی کم از کم تعداد جو گروپنگ کو متحرک کرتی ہے         |
| `stripCodeComments`    | `false` | اختیاری: فینس شدہ کوڈ بلاکس سے تبصرے ہٹائیں (`applyToCodeBlocks` درکار ہے)         |
| `preserveDocstrings`   | `true`  | تبصرے ہٹاتے وقت JSDoc/`/** … */` بلاکس برقرار رکھیں                                |

## API

| روٹ                                | طریقہ | مقصد                                            |
| ---------------------------------- | ----- | ----------------------------------------------- |
| `/api/context/rtk/config`          | GET   | RTK کنفیگ پڑھیں                                 |
| `/api/context/rtk/config`          | PUT   | RTK کنفیگ اپ ڈیٹ کریں                           |
| `/api/context/rtk/filters`         | GET   | فلٹر کیٹلاگ اور لوڈ تشخیصی معلومات کی فہرست     |
| `/api/context/rtk/import`          | POST  | RTK TOML اسکیما v1 فائلوں کی توثیق یا تنصیب     |
| `/api/context/rtk/test`            | POST  | ایک ٹیکسٹ پے لوڈ کے لیے RTK کمپریشن کا پیش منظر |
| `/api/context/rtk/raw-output/[id]` | GET   | برقرار رکھا گیا مخفی کردہ خام آؤٹ پٹ پڑھیں      |
| `/api/compression/preview`         | POST  | کسی بھی کمپریشن موڈ کا پیش منظر دیکھیں          |

RTK ٹیسٹ پے لوڈ:

```json
{
  "command": "npm test",
  "text": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed",
  "config": {
    "intensity": "standard"
  }
}
```

کمپریشن پیش منظر پے لوڈ:

```json
{
  "mode": "stacked",
  "messages": [
    {
      "role": "tool",
      "content": "FAIL tests/example.test.ts\nAssertionError: expected true\nTest Files 1 failed"
    }
  ],
  "config": {
    "rtkConfig": {
      "rawOutputRetention": "failures"
    }
  }
}
```

انتظامی روٹس کے لیے ڈیش بورڈ مینجمنٹ کی تصدیق یا مماثل API-key پالیسی درکار ہے۔

RTK TOML توثیقی پے لوڈ:

```json
{
  "action": "validate",
  "content": "schema_version = 1\n\n[filters.my-tool]\nmatch_command = \"^my-tool\\\\b\"\nmax_lines = 20\n"
}
```

توثیق شدہ فائل کو عالمی سطح پر نصب کرنے کے لیے `"action": "install"` استعمال کریں۔ کسی موجودہ عالمی فائل کے
متبادل کا جائزہ لینے اور اس کی تصدیق کرنے کے بعد ہی `"overwrite": true` شامل کریں۔

## خام آؤٹ پٹ کی بازیابی

RTK عام طور پر صرف کمپریس شدہ متن واپس کرتا ہے۔ ڈیبگنگ کے لیے، `rawOutputRetention` ترمیم شدہ
خام آؤٹ پٹ محفوظ رکھ سکتا ہے:

| قدر        | طرزِ عمل                                               |
| ---------- | ------------------------------------------------------ |
| `never`    | خام آؤٹ پٹ محفوظ نہ رکھیں                              |
| `failures` | صرف ممکنہ ناکامی کا آؤٹ پٹ محفوظ رکھیں                 |
| `always`   | ترمیم کے بعد، ہر کمپریس شدہ RTK خام آؤٹ پٹ محفوظ رکھیں |

محفوظ شدہ فائلیں یہاں لکھی جاتی ہیں:

```txt
DATA_DIR/rtk/raw-output/
```

محفوظ کرنے سے پہلے رازوں کی ترمیم کر دی جاتی ہے، جن میں عام بیئرر ٹوکنز، API کیز، Slack ٹوکنز،
AWS ایکسیس کیز، اور اسائنمنٹ طرز کی `token=...`، `secret=...`، `password=...` اقدار شامل ہیں۔ اینالیٹکس
صرف پوائنٹر آئی ڈی، سائز، اور ہیش میٹا ڈیٹا محفوظ کرتا ہے۔

## RTK میں توسیع کرنا

1. ایک فلٹر JSON فائل شامل یا اپ ڈیٹ کریں۔
2. کم از کم ایک `tests[]` نمونہ شامل کریں جو اہم طرزِ عمل کو ثابت کرے۔
3. نئی کمانڈ فیملیز کے لیے `tests/unit/compression/fixtures/rtk/` کے تحت ایک فکسچر شامل کریں۔
4. نئی آؤٹ پٹ کلاس متعارف کراتے وقت کمانڈ کی شناخت کی کوریج شامل کریں۔
5. تصدیقی اور وسیع RTK گیٹس چلائیں۔
6. اگر فلٹر پروجیکٹ کے لیے مقامی ہے، تو `.rtk/filters.json` کو کمٹ کریں اور صرف جائزے کے بعد `.rtk/trust.json` کو ریفریش کریں۔

## شدت کی سطحیں (v3.8.16+)

RTK **شدت کی 3 سطحوں** کو سپورٹ کرتا ہے جو **کمپریشن کی جارحیت** اور **حفاظت** کے درمیان توازن قائم کرتی ہیں۔ سطح انجن کنفگ میں `config.intensity` کے ذریعے سیٹ کی جاتی ہے۔

### 3 سطحیں

| سطح                 | تراشنے کی حد       | ٹوکن کی بچت | خطرہ    | بہترین استعمال                 |
| ------------------- | ------------------ | ----------- | ------- | ------------------------------ |
| `minimal`           | فی سیکشن 24 لائنیں | ~20-40%     | بہت کم  | اہم سیاق و سباق والی پروڈکشن   |
| `standard` (ڈیفالٹ) | فی سیکشن 24 لائنیں | ~50-70%     | کم      | روزمرہ کوڈنگ سیشنز             |
| `aggressive`        | فی سیکشن 16 لائنیں | ~70-90%     | درمیانہ | طویل سیشنز، زیادہ سے زیادہ بچت |

### تراشنا کہاں ہوتا ہے

تراشنے کی حد `lineFilter.ts` پر اثر انداز ہوتی ہے:

```ts
// open-sse/services/compression/engines/rtk/index.ts:329-330 سے
config.intensity === "aggressive" ? 16 : 24,
config.intensity === "aggressive" ? 16 : 24,
```

ہر سیکشن کا **ابتدائی** اور **آخری** دونوں حصہ محفوظ رکھا جاتا ہے؛ تراشنا فعال ہونے پر درمیانی مواد ہٹا دیا جاتا ہے۔

### کیا باقی رہتا ہے بمقابلہ کیا کاٹا جاتا ہے

| مواد                        | minimal       | standard      | aggressive    |
| --------------------------- | ------------- | ------------- | ------------- |
| ایررز / اسٹیک ٹریسز         | ✅ محفوظ      | ✅ محفوظ      | ✅ محفوظ      |
| ٹیسٹ کی ناکامیاں            | ✅ محفوظ      | ✅ محفوظ      | ✅ محفوظ      |
| بِلڈ ایررز                  | ✅ محفوظ      | ✅ محفوظ      | ✅ محفوظ      |
| کامیاب ٹیسٹس (تفصیلی)       | ✅ محفوظ      | 🟡 مختصر کردہ | 🟡 مختصر کردہ |
| معمول کا آؤٹ پٹ (انفو لاگز) | 🟡 مختصر کردہ | 🟡 مختصر کردہ | ❌ حذف شدہ    |
| پروگریس بارز                | 🟡 مختصر کردہ | ❌ حذف شدہ    | ❌ حذف شدہ    |
| بینر / ASCII آرٹ            | 🟡 مختصر کردہ | ❌ حذف شدہ    | ❌ حذف شدہ    |

## حسبِ ضرورت فلٹر کی تیاری (v3.8.16+)

`engines/rtk/filters/` ڈائریکٹری میں **49+ پہلے سے شامل فلٹر JSON فائلیں** موجود ہیں۔ آپ ایسے حسبِ ضرورت ٹولز کے آؤٹ پٹ کو مختصر کرنے کے لیے اپنا فلٹر شامل کر سکتے ہیں جو ڈیفالٹس میں شامل نہیں ہیں۔

### فلٹر اسکیما (Zod)

```ts
{
  "id": "string",                      // لازمی۔ فلٹر شناخت کنندہ (kebab-case، مثلاً "python-traceback")
  "label": "string",                   // لازمی۔ انسان کے لیے قابلِ فہم فلٹر نام
  "description": "string",             // اختیاری (ڈیفالٹ: "")۔ فلٹر کے کام کی مختصر وضاحت
  "category": "git|test|build|shell|docker|package|infra|cloud|generic",
  "priority": number,                  // اختیاری (0-100، ڈیفالٹ: 50)۔ نفاذ کی ترتیب (زیادہ قدر = پہلے)
  "match": {
    "commands": ["string"],            // مماثلت کے لیے کمانڈ نام (مثلاً "python"، "pytest")
    "patterns": ["string"],            // آؤٹ پٹ سے مماثلت کے لیے ریجیکس پیٹرنز
    "outputTypes": ["string"]          // شناخت شدہ آؤٹ پٹ کلاسز (مثلاً "test-failure")
  },
  "rules": {
    "stripAnsi": boolean,              // اختیاری (ڈیفالٹ: false)۔ ANSI رنگ کوڈز ہٹائیں
    "replace": [                       // تلاش اور تبدیلی کے قواعد (ڈیفالٹ: [])
      { "pattern": "regex", "replacement": "..." }
    ],
    "matchOutput": [                   // پیٹرن مماثلت پر فوراً اختتام کریں (ڈیفالٹ: [])
      {
        "pattern": "regex",
        "message": "short summary",
        "unless": "regex"              // اگر یہ پیٹرن مماثل ہو تو چھوڑ دیں
      }
    ],
    "includePatterns": ["string"],     // برقرار رکھنے والی لائنیں (ریجیکس پیٹرنز، ڈیفالٹ: [])
    "dropPatterns": ["string"],        // حذف کرنے والی لائنیں (ریجیکس پیٹرنز، ڈیفالٹ: [])
    "collapsePatterns": ["string"],    // ایک ہی وقوعے تک محدود کرنے والی لائنیں (ڈیفالٹ: [])
    "deduplicate": boolean,            // اختیاری (ڈیفالٹ: false)۔ نقل شدہ لائنیں ہٹائیں
    "truncateLineAt": number,          // اختیاری (ڈیفالٹ: 0)۔ لائنوں کو حروف کی زیادہ سے زیادہ حد تک مختصر کریں
    "maxLines": number,                // اختیاری (ڈیفالٹ: 0)۔ کل لائنوں کی قطعی حد
    "headLines": number,               // اختیاری (ڈیفالٹ: 20)۔ مماثل آؤٹ پٹ کی پہلی N لائنیں برقرار رکھیں
    "tailLines": number,               // اختیاری (ڈیفالٹ: 20)۔ مماثل آؤٹ پٹ کی آخری N لائنیں برقرار رکھیں
    "onEmpty": "string",               // اختیاری (ڈیفالٹ: "")۔ تمام لائنیں فلٹر ہونے کی صورت میں متبادل پیغام
    "filterStderr": boolean            // اختیاری (ڈیفالٹ: false)۔ stderr آؤٹ پٹ بھی فلٹر کریں
  },
  "preserve": {
    "errorPatterns": ["string"],       // ایسے پیٹرنز جو ہمیشہ برقرار رہنے چاہییں (ڈیفالٹ: [])
    "summaryPatterns": ["string"]      // آخری خلاصہ لائن کے پیٹرنز (ڈیفالٹ: [])
  },
  "tests": [                           // تصدیق کے لیے اِن لائن ٹیسٹس (ڈیفالٹ: [])
    {
      "name": "string",               // لازمی۔ ٹیسٹ کا نام
      "input": "sample output",        // لازمی۔ نمونہ ان پٹ متن
      "expected": "expected output",   // لازمی۔ متوقع مختصر آؤٹ پٹ
      "command": "optional command"    // اختیاری۔ کمانڈ کا سیاق
    }
  ]
}
```

```json
{
  "id": "python-traceback",
  "label": "Python Traceback Filter",
  "description": "Compresses Python tracebacks to essential file/line locations and error type",
  "category": "test",
  "priority": 60,
  "match": {
    "commands": ["python", "python3", "pytest", "uv", "poetry"],
    "patterns": ["Traceback \\(most recent call last\\)", "Error", "Exception"],
    "outputTypes": ["error-traceback"]
  },
  "rules": {
    "stripAnsi": true,
    "includePatterns": [
      "Traceback \\(most recent call last\\)",
      "^\\s*File \".+\", line \\d+",

      "^\\s*[A-Z][a-zA-Z]+Exception"
    ],
    "dropPatterns": ["site-packages/", "^\\s+[a-z_]+\\([^)]*\\)$"],
    "headLines": 5,
    "tailLines": 3,
    "maxLines": 25,
    "filterStderr": true
  },
  "preserve": {
    "errorPatterns": ["Error:", "Exception:", "Traceback"],
    "summaryPatterns": ["^[A-Z][a-zA-Z]+(?:Error|Exception):"]
  },
  "tests": [
    {
      "name": "preserves-error-type-and-location",
      "input": "Traceback (most recent call last):\n  File \"app.py\", line 42, in main\n    do_thing()\n  File \"lib/utils.py\", line 17, in helper\n    return 1 / 0\nZeroDivisionError: division by zero",
      "expected": "Traceback (most recent call last):\n  File \"app.py\", line 42, in main\n  File \"lib/utils.py\", line 17, in helper\nZeroDivisionError: division by zero",
      "command": "python app.py"
    }
  ]
}
```

### حسبِ ضرورت فلٹرز لوڈ کرنا

فائل کو کسی تسلیم شدہ مقام پر رکھیں:

```
~/.omniroute/rtk/filters/my-filter.json     # صارف کی سطح پر
<project>/.rtk/filters/my-filter.json      # پروجیکٹ کی سطح پر
```

اسٹارٹ اپ کے وقت `open-sse/services/compression/engines/rtk/filterLoader.ts` میں موجود `loadRtkFilters()` کے ذریعے فلٹرز خودکار طور پر لوڈ ہو جاتے ہیں۔ لوڈر درج ذیل مقامات سے فلٹرز دریافت کرتا ہے:

- پہلے سے شامل کیٹلاگ: `open-sse/services/compression/engines/rtk/filters/`
- صارف کی ڈائریکٹری: `~/.omniroute/rtk/filters/`
- پروجیکٹ ڈائریکٹری: `<project>/.rtk/filters/`

فلٹرز کو پروگرام کے ذریعے لوڈ کرنے کے لیے:

```ts
import { loadRtkFilters } from "@omniroute/open-sse/services/compression/engines/rtk/filterLoader";

// اختیارات: customFiltersEnabled (صارف/پروجیکٹ فلٹرز لوڈ کریں، بطور ڈیفالٹ فعال)،
// trustProjectFilters، refresh۔
const filters = loadRtkFilters({ customFiltersEnabled: true });
```

### توثیق

فلٹرز کو لوڈ کرتے وقت Zod اسکیما کے مطابق جانچا جاتا ہے۔ غلط ساخت والا فلٹر لوڈ نہیں ہوگا اور ایک خرابی لاگ کرے گا:

```
RTK_FILTER_LOADER: فلٹر "my-filter" کی توثیق ناکام ہوئی:
  - rules.replace.0.pattern: غیر درست ریجیکس
  - match.commands: خالی نہیں ہونا چاہیے
```

انسٹال شدہ تمام فلٹرز کی توثیق کے لیے `runRtkFilterTests()` کو کال کریں، جسے `open-sse/services/compression/engines/rtk/verify.ts` سے ایکسپورٹ کیا جاتا ہے۔

### بہترین طریقۂ کار

1. **ہمیشہ `tests[]` شامل کریں** — یہ ثابت کرتے ہیں کہ آپ کا فلٹر کام کرتا ہے اور ریگریشنز کو روکتے ہیں
2. **شارٹ سرکٹس کے لیے `matchOutput` استعمال کریں** — اگر ایک سطر پوری بات واضح کر دے تو پورے بلاک کو بدل دیں
3. **`strip` کے بجائے `keep` کو ترجیح دیں** — واضح "ہمیشہ محفوظ رکھیں" کے اصول "ہمیشہ ہٹا دیں" سے زیادہ محفوظ ہوتے ہیں
4. **شدت کی تینوں سطحوں پر ٹیسٹ کریں** — `minimal` کو کوئی تبدیلی نہیں کرنی چاہیے، جبکہ `aggressive` کو پھر بھی ایررز محفوظ رکھنے چاہئیں
5. **`unless` فیلڈ استعمال کریں** — شارٹ سرکٹس کو اس شرط کے ساتھ محفوظ بنائیں کہ "اگر X موجود ہو تو فعال نہ ہوں"

## خام آؤٹ پٹ کی بازیابی اور تصدیقی گیٹ

جب RTK آؤٹ پٹ کو بہت زیادہ کمپریس کرتا ہے، تو آپ ڈیبگنگ، آڈٹ، یا دوبارہ چلانے کے لیے **اصل متن بازیافت** کر سکتے ہیں۔

### خام آؤٹ پٹ کی بازیابی کیسے کام کرتی ہے

```
اصل آؤٹ پٹ (10K ٹوکنز)
        │
        ▼
RTK کمپریشن (rawOutput.enabled=true کے ساتھ)
        │
        ├─▶ کمپریس شدہ آؤٹ پٹ (2K ٹوکنز)  ──▶ LLM کو
        │
        └─▶ اصل آؤٹ پٹ (10K ٹوکنز)         ──▶ DB میں محفوظ
                                                  (request_id کے ذریعے منسلک)
```

### خام آؤٹ پٹ اسٹوریج کو فعال کرنا

**فی درخواست** (combo کنفیگریشن میں):

```json
{
  "compression": {
    "engine": "rtk",
    "intensity": "aggressive",
    "rawOutput": {
      "enabled": true,
      "maxBytes": 1048576 // 1MB کی حد
    }
  }
}
```

**ڈیفالٹ**: `rawOutput.enabled: false` (اسٹوریج بچاتا ہے)۔

### اسٹوریج کی لاگت

| فی درخواست                    | 1MB کی حد    | 10MB کی حد    |
| ----------------------------- | ------------ | ------------- |
| اوسط کمپریس شدہ آؤٹ پٹ        | ~5KB         | ~5KB          |
| محفوظ کردہ خام آؤٹ پٹ         | ~50-500KB    | ~500KB-5MB    |
| روزانہ 1000 درخواستوں کے ساتھ | 50-500MB/day | 500MB-5GB/day |

> **تجویز**: خام آؤٹ پٹ کو ہمیشہ فعال رکھنے کے بجائے صرف **ڈیبگنگ سیشنز** یا **نمونہ جاتی آڈٹنگ** کے لیے فعال کریں۔

### اصل آؤٹ پٹ کی بازیابی

```ts
import { readRtkRawOutput } from "omniroute/compression/engines/rtk/rawOutput";

const raw = readRtkRawOutput(pointerId); // کمپریشن کے اعداد و شمار سے pointerId
if (raw) {
  console.log("Original output:", raw);
}
```

کمپریشن کے بعد `pointerId`، `CompressionStats.rtkRawOutputPointers[]` میں واپس کیا جاتا ہے۔
فنکشن کے سگنیچر کے لیے `open-sse/services/compression/engines/rtk/rawOutput.ts:102` دیکھیں۔

### تصدیقی گیٹ

**RTK فلٹر کی تصدیق** (`open-sse/services/compression/engines/rtk/verify.ts`) تمام فلٹرز کو ان کے `tests[]` کے مقابل جانچتی ہے اور یقینی بناتی ہے کہ تینوں شدت کی سطحوں پر رویہ درست ہو۔

تصدیق چلانے کے لیے **`runRtkFilterTests()` کو کال کریں**:

```ts
import { runRtkFilterTests } from "open-sse/services/compression/engines/rtk/verify";

const result = runRtkFilterTests();
console.log(`Passed: ${result.outcomes.filter((o) => o.passed).length}`);
console.log(`Failed: ${result.outcomes.filter((o) => !o.passed).length}`);
if (!result.passed) {
  console.error("Filters failed verification");
  result.outcomes
    .filter((o) => !o.passed)
    .forEach((o) => {
      console.error(
        `  - ${o.filterId} / ${o.testName}: expected "${o.expected}", got "${o.actual}"`
      );
    });
}
```

**یہ کن چیزوں کی توثیق کرتی ہے**:

1. ہر فلٹر لوڈ ہوتا ہے اور اسکیما کی توثیق میں کامیاب ہوتا ہے
2. ہر `tests[]` اندراج متوقع آؤٹ پٹ پیدا کرتا ہے
3. `minimal` شدت کوئی کارروائی نہیں کرتی (اصل کو برقرار رکھتی ہے، صرف ساختی فلٹرز لاگو کرتی ہے)
4. `aggressive` شدت خرابیوں، ٹیسٹ کی ناکامیوں، اور اسٹیک ٹریسز کو برقرار رکھتی ہے
5. کمپریس شدہ آؤٹ پٹ کبھی بھی اصل ان پٹ سے بڑا نہیں ہوتا

- ماخذ: `open-sse/services/compression/engines/rtk/` (63 فائلیں، ~70KB)

- **فلٹر کی تبدیلی ضم کرنے سے پہلے** — ہمیشہ یقینی بنائیں کہ ٹیسٹس کامیاب ہوں
- **RTK انجن اپ گریڈ کرنے کے بعد** — اسکیما تبدیل ہو سکتا ہے
- **نگرانی کے دوران وقتاً فوقتاً** — ٹیسٹ فکسچرز میں انحراف سے تحفظ فراہم کرتا ہے
- **نیا ٹول/کمانڈ خاندان شامل کرتے وقت** — ثابت کرتا ہے کہ نیا فلٹر کام کرتا ہے
