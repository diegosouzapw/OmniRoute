کسی pull request کے لیے سب سے مختصر قابلِ اعتماد development loop منتخب کرنے کے لیے یہ رہنما استعمال کریں۔ یہ ذیل میں منسلک، ہر شعبے سے مخصوص architecture اور security دستاویزات کی جگہ نہیں
لیتا؛ بلکہ تبدیلی کی ہر عام قسم کو اس کے contracts، مرکوز checks، اور CI coverage سے جوڑتا ہے۔

## وہ راستہ جس پر ہر تبدیلی چلتی ہے

1. **ترمیم سے پہلے base منتخب کریں۔** سب سے بلند فعال `release/v*` branch تلاش کریں اور اس کے
   tip سے branch بنائیں۔ `main` کے بجائے اس branch کو target کریں۔ اگر release freeze فعال ہو تو منجمد
   branch کو target نہ کریں؛
   [Branching & Release Model](BRANCHING_MODEL.md) میں بیان کردہ اگلا فعال cycle استعمال کریں۔
2. **Contracts کے نام واضح کریں۔** ہر اس catalog، schema، generated artifact، public API، یا user
   interface کی شناخت کریں جسے تبدیلی متاثر کرتی ہے۔ ذیل کا جدول کم از کم ابتدائی مجموعہ فراہم کرتا ہے۔
3. **مرکوز tests لکھیں یا اپ ڈیٹ کریں۔** `src/`، `open-sse/`، `electron/`، یا
   `bin/` میں production تبدیلیوں کے لیے اسی PR میں ایک automated test درکار ہے۔ پہلے وہ مختصر ترین test files
   چلائیں جو رویے کو ثابت کرتی ہوں، پھر درج شدہ focused gates چلائیں۔
4. **وسیع matrix کو CI پر چلنے دیں۔** مکمل unit shards، Vitest، coverage ratchet، اور
   production build، PR پر چلتے ہیں۔ وسیع suite مقامی طور پر صرف اس وقت چلائیں جب کوئی focused failure
   وسیع تر اثر کی نشاندہی کرے یا تبدیلی کئی subsystems پر محیط ہو۔
5. **Review سے پہلے ہم آہنگی کریں۔** فعال base کو fetch کریں، اس کے نئے commits اور اس کے مقابلے میں اپنا diff
   دیکھیں، پھر contributor workflow کے مطابق base کو rebase یا merge کریں۔ Generated-file
   اور catalog conflicts کو ان کے source سے حل کریں، انہیں دوبارہ generate کریں، focused loop پھر چلائیں، اور تصدیق کریں کہ
   PR اب بھی فعال release branch کو target کرتا ہے۔
6. **شواہد درج کریں۔** PR template میں چلائی گئی commands، شامل یا تبدیل کی گئی ہر test file،
   migrations یا feature flags، اور کوئی بھی CI-only validation جو ابھی pending ہو، درج کریں۔

## تبدیلی کی قسم کے لحاظ سے Golden paths

ذیل کی commands کم از کم focused checks ہیں، براہِ راست اس
رویے کا احاطہ کرنے والے test کو چھوڑنے کی اجازت نہیں جسے آپ نے تبدیل کیا ہے۔

### Provider

**Contracts**

- `src/shared/constants/providers/` میں Provider definition اور
  `src/shared/constants/providers.ts` میں اس کی composition۔
- `open-sse/config/providerRegistry.ts` یا اس کی extracted registry files میں Models اور capabilities۔
- حسبِ اطلاق Executor/translator selection، OAuth یا API-key configuration، dashboard assets، اور generated
  provider reference۔
- Public credentials کے لیے `resolvePublicCred()` استعمال کرنا ضروری ہے؛ error responses کے لیے مشترکہ sanitized
  error helpers استعمال کرنا ضروری ہے۔ `docs/security/PUBLIC_CREDS.md` (git؛ `/docs` میں compile نہیں ہوتا) اور
  [Error Sanitization](../security/ERROR_SANITIZATION.md) دیکھیں۔

**Focused loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # جب catalog تبدیل ہو؛ generated diff کو commit کریں
npm run lint
```

ہر متاثرہ request family بھی test کریں: chat، Responses، images، embeddings، audio، یا video۔
Generated catalog اور golden diffs کو contract changes کے طور پر review کریں؛ انہیں بغیر جائزے کے قبول نہ کریں۔

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts` میں Public strategy values اور UI metadata۔
- `open-sse/services/combo.ts` اور `open-sse/services/combo/` کے تحت Dispatch اور ordering۔
- Combo schemas، persistence، resilience state، model capabilities، اور API/UI controls۔
- رویہ تبدیل ہونے پر [Auto-Combo Engine](../routing/AUTO-COMBO.md) اور resilience documentation۔

**Focused loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy یا dispatch کی تبدیلیاں
npm run check:known-symbols      # strategy registration کی تبدیلیاں
npm run lint
```

مقامی طور پر deterministic mocked-upstream tests استعمال کریں۔ Live combo smokes کے لیے credentials درکار ہیں اور یہ
manual ہیں، CI کے متبادل نہیں۔

### UI / UX

**Contracts**

- `src/app/` اور `src/shared/components/` کے تحت Next.js route/page اور shared component boundaries۔
- API response shapes، loading/empty/error states، keyboard اور screen-reader behavior،
  responsive layout، theming، اور locale expansion۔
- `src/i18n/messages/en.json` میں English UI source strings؛ نئی user-facing copy کو hard-code نہ کریں۔

**Focused loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction یا visual تبدیلیوں کے لیے app چلائیں اور narrow اور wide دونوں viewports کو check کریں۔ CI
production build اور وسیع تر suites چلاتا ہے؛ visual behavior کے لیے پھر بھی تبدیلی کے مطابق کوئی focused component، Playwright،
یا documented manual check درکار ہے۔

### i18n

**Contracts**

- `src/i18n/messages/en.json`، UI source ہے؛ `config/i18n.json`، locale source ہے۔
- CLI catalogs الگ سے `bin/cli/locales/` کے تحت موجود ہیں۔
- ICU placeholders اور tags کو بالکل اسی طرح محفوظ رکھیں۔ product/provider/model names،
  protocol اور header names، commands، code/JSON identifiers، URLs، environment variables، یا
  محفوظ اصطلاحات مثلاً `OmniRoute`، `OAuth`، `MCP`، اور `A2A` کا ترجمہ نہ کریں۔ موجودہ source list
  `scripts/i18n/glossary/protected-terms.json` ہے۔

**Focused loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # جب CLI strings/catalogs تبدیل ہوں
npm run lint
```

یہ موجودہ system کے لیے رہنمائی ہے، اس کی tooling یا key model کو وسعت دینے کی دعوت نہیں۔
جب تک replacement system تیار کیا جا رہا ہے، i18n patches کو محدود اور مخصوص رکھیں۔ External services کو call کرنے والی translation
commands اس وقت تک نہ چلائیں جب تک task میں generated translations واضح طور پر مطلوب نہ ہوں اور
آپ resulting diff کا review نہ کر چکے ہوں۔

### CLI

**Contracts**

- `bin/cli/` میں عوامی کمانڈز اور فلیگز، تیار کردہ API کمانڈز، ایگزٹ کوڈز، stdout/stderr اور
  JSON آؤٹ پٹ کی ساختیں، کنفیگ/انوائرمنٹ کا برتاؤ، اور پیکیج شدہ فائلیں۔
- CLI میں صارف کو دکھائی دینے والی اسٹرنگز کو لازماً CLI i18n پرت استعمال کرنی چاہیے اور `en`/`pt-BR` کیٹلاگز کو ہم آہنگ رکھنا چاہیے۔
- Node کو معاونت یافتہ رن ٹائم اور شائع شدہ بائنری معاہدے کے طور پر برقرار رکھیں۔

**مرکوز عمل**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تیار کردہ/بنڈل شدہ CLI تبدیلیاں
npm run check:pack-policy     # پیکیج کی ظاہری سطح کی تبدیلیاں
npm run lint
```

جب برتاؤ پارسنگ، فائلوں، یا ایگزٹ اسٹیٹس پر منحصر ہو تو عارضی ڈیٹا ڈائریکٹری میں عین وہی کمانڈ استعمال کریں۔
CI پیکیج آرٹیفیکٹ اور ایکوسسٹم کی زیادہ وسیع جانچیں انجام دیتا ہے۔

### ڈیٹابیس

**معاہدے**

- `src/lib/db/` کے تحت ڈومین ماڈیولز؛ مخصوص ماڈیولز براہِ راست درآمد کریں (پرانی `localDb.ts` دوبارہ ایکسپورٹ کرنے والی پرت ہٹا دی گئی تھی)۔
- `src/lib/db/migrations/` کے تحت نمبر شدہ، idempotent SQL مائیگریشنز، ٹرانزیکشن کا تحفظ، اپ گریڈ
  کا برتاؤ، انڈیکسز، اور اسکیما سے متاثر ہونے والا ہر کالر۔
- روٹس اور ہینڈلرز کبھی بھی براہِ راست خام SQL جاری نہیں کرتے۔

**مرکوز عمل**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

مائیگریشن شامل کرتے وقت تازہ ڈیٹابیس اور پچھلے اسکیما سے اپ گریڈ، دونوں کی جانچ کریں۔ ڈیٹابیس ٹیسٹس
کو کلین اپ کے دوران ہینڈلز بند کرنے اور `resetDbInstance()` کال کرنے چاہییں۔ `npm run test:bun:db` صرف اس وقت
چلائیں جب best-effort Bun اڈاپٹر کا راستہ تبدیل ہو؛ Node ہی مستند رہتا ہے۔

### بلڈ / تعیناتی

**معاہدے**

- روٹ اور ورک اسپیس مینی فیسٹس/لاک فائل، `scripts/build/`، Next.js اسٹینڈ الون اسمبلی، `dist/`
  پیکیج کے مندرجات، Electron پلیٹ فارم میٹا ڈیٹا، CI ورک فلوز، اور تعیناتی کے سینٹینلز۔
- معاونت یافتہ Node رینجز اور `CLAUDE.md` میں allow-listed Bun کا استعمال برقرار رہنا چاہیے۔
- بلڈ آرٹیفیکٹس کو ٹریک نہ کیا جائے؛ انحصارات، لائسنس، ورک فلو، اور پیکیج کی پالیسیاں لاگو ہوتی ہیں۔

**مرکوز عمل**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # انحصار یا لاک فائل کی تبدیلیاں
npm run check:pack-policy      # شائع شدہ پیکیج کی ظاہری سطح کی تبدیلیاں
npm run lint
```

`npm run build` کو مقامی طور پر صرف اس وقت استعمال کریں جب تبدیلی کمپائلیشن، اسٹینڈ الون اسمبلی، اثاثوں،
یا رن ٹائم بنڈلنگ کو متاثر کرتی ہو۔ `npm run build:release` صرف ریلیز/تعیناتی کی توثیق کے لیے استعمال کریں۔ CI کا بلڈ
آخری کراس پلیٹ فارم اشارہ ہے؛ پلیٹ فارم کے لیے مخصوص Electron تبدیلیوں کو متعلقہ مرکوز بلڈ
یا اسموک ٹیسٹ کے ثبوت کی ضرورت ہوتی ہے۔

## مقامی امیدوار کا چکر

سورس ٹیسٹس یہ ثابت نہیں کر سکتے کہ پیکیج شدہ آرٹیفیکٹ بوٹ ہوتا ہے: پیکیجنگ فہرستیں، حذف شدہ dependencies،
اور native binaries صرف tarball کے انسٹال اور شروع ہونے کے بعد ناکام ہوتے ہیں۔ `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) RFC #8084 کے build-once / validate / promote بہاؤ کا مقامی حصہ ہے:
یہ ایک امیدوار بناتا ہے، عین اسی آرٹیفیکٹ کی توثیق کرتا ہے، directory renames کے ذریعے اسے promote کرتا ہے،
اور promoted slot کے health check میں ناکام ہونے پر اسے roll back کر دیتا ہے۔

```bash
npm run dev:candidate -- run --dry-run --json  # منصوبہ دکھائیں، کچھ تبدیل نہ کریں
npm run dev:candidate -- run                   # build + validate + promote، خودکار rollback
npm run dev:candidate -- build                 # npm pack + _artifacts/candidate/<id>/ میں انسٹال کریں
npm run dev:candidate -- validate --id <id>    # خالی port پر بوٹ کریں، /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current، current → previous
npm run dev:candidate -- rollback              # current اور previous کو باہم تبدیل کریں
npm run dev:candidate -- run --from-tarball <file.tgz>  # کہیں اور (CI میں) بنایا گیا tarball دوبارہ استعمال کریں
```

- **ایک بار build کریں۔** `build` موجودہ tree کو پیک کرتا ہے (اسے `dist/server.js` درکار ہے، اس لیے پہلے
  `npm run build:release` چلائیں) یا `--from-tarball` کو کاپی کرتا ہے، پھر tarball کو ایک الگ تھلگ
  npm prefix میں انسٹال کرتا ہے، کیونکہ tarball میں `node_modules` شامل نہیں ہوتا۔ id مختصر `HEAD`
  sha ہوتا ہے (جب tree میں مقامی تبدیلیاں ہوں تو `-dirty`) یا tarball کے لیے `tgz-<sha256>`۔ پہلے
  سے build شدہ صاف id کو دوبارہ build کرنے کے بجائے دوبارہ استعمال کیا جاتا ہے؛ اسے دوبارہ build کرنے
  کے لیے `--force` دیں۔
- **سورس کی نہیں، پیکیج کی توثیق کریں۔** `validate` انسٹال شدہ CLI کو
  (`serve --port <free port>`) ایک نئے `DATA_DIR=<candidate>/data`، فرضی secrets، اور operator کے
  `OMNIROUTE_API_KEY`، `STORAGE_ENCRYPTION_KEY` اور `INITIAL_PASSWORD` کو environment سے ہٹا کر شروع
  کرتا ہے، تاکہ یہ تازہ installation کی keyless loopback posture کی جانچ کرے۔ یہ
  `GET /api/health` سے 200 واپس آنے کا انتظار کرتا ہے، `GET /v1/models` سے 200 واپس آنا لازم قرار
  دیتا ہے، process group کو روکتا ہے، اور tarball hash کے ساتھ فیصلہ `validation.json` میں ریکارڈ کرتا ہے۔
- **اسی آرٹیفیکٹ کو promote کریں۔** `promote` ایسے امیدوار کو قبول نہیں کرتا جس کے موجودہ tarball hash
  کے لیے کامیاب validation موجود نہ ہو۔ پہلے سے طے شدہ active slot `_artifacts/candidate/current` ہے؛
  `--target <dir>` اسی filesystem پر ایک دوسری directory منتخب کرتا ہے، اور اس کا previous slot
  `<dir>.previous` ہوتا ہے۔ ہر rename atomic ہے، اور درمیان میں ناکامی کی صورت میں پہلے سے مکمل شدہ
  renames کو الٹ دیا جاتا ہے۔
- **Roll back کریں۔** `run` promoted slot کی دوبارہ توثیق کرتا ہے اور وہ جانچ ناکام ہونے پر `current`
  اور `previous` کو واپس باہم تبدیل کر دیتا ہے۔ پہلی validation میں ناکام ہونے والے امیدوار کو کبھی
  promote نہیں کیا جاتا۔

ہر چیز gitignored `_artifacts/candidate/` کے تحت لکھی جاتی ہے؛ موجودہ OmniRoute installation اور اس کی
data directory کو کبھی نہیں چھیڑا جاتا۔ Promoted CLI
`_artifacts/candidate/current/prefix/bin/omniroute` ہے؛ اسے استعمال کرتے وقت اپنے `DATA_DIR` کے ساتھ
شروع کریں۔ Exit codes: کامیابی کے لیے `0`، ناکام validation یا promotion کے لیے `1`، اور usage error
یا گم شدہ build کے لیے `2`۔

## مقامی لوپ بمقابلہ CI

| ہر پیچ کے لیے مقامی طور پر چلائیں                                       | CI وسیع اشارہ فراہم کرتا ہے                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------- |
| براہِ راست رویّے کے ٹیسٹس اور اوپر دیے گئے زمرہ جاتی گیٹس               | تقسیم شدہ مکمل یونٹ سوٹ اور سلسلہ وار ٹیسٹس                         |
| `npm run lint`                                                          | Vitest سوٹس اور کوریج/معیار کے بتدریج سخت ہونے والے معیارات         |
| ٹائپ چیک یا بلڈ صرف اس وقت جب متاثرہ معاہدے کے لیے اس کی ضرورت ہو       | پروڈکشن بلڈ، سیکیورٹی، دستاویزات، انحصارات، اور PR-پالیسی گیٹس      |
| دستی تعامل/لائیو جانچ صرف اس وقت جب خودکار نظام رویّے کو ثابت نہ کر سکے | ورک فلو کے ذریعے ترتیب دی گئی کراس-جاب انٹیگریشن اور پلیٹ فارم جانچ |

ایک کامیاب مرکوز لوپ تبدیل شدہ معاہدے کے بارے میں ثبوت ہے، یہ اس بات کا ثبوت نہیں کہ غیر متعلقہ CI جانچیں
کامیاب ہوں گی۔ اس کے برعکس، ہر مقامی ترمیم کو مکمل ریپوزٹری میٹرکس کا انتظار نہ کروائیں۔

## ہم آہنگی کی چیک لسٹ

جائزے کی درخواست کرنے سے پہلے:

- تصدیق کریں کہ PR کی بیس اب بھی سب سے اعلیٰ فعال `release/v*` برانچ ہے۔
- اس بیس کو فیچ کریں اور اپنی برانچ بنانے کے بعد شامل ہونے والے کمیٹس کا جائزہ لیں۔
- غیر ارادی یا خودکار طور پر پیدا ہونے والی تبدیلیوں کے لیے `git diff <active-base>...HEAD` کا جائزہ لیں۔
- کیٹلاگ اور خودکار طور پر تیار کردہ دستاویزات کے تنازعات کو ماخذ اپ ڈیٹ کر کے اور آؤٹ پٹ دوبارہ تیار کر کے حل کریں۔
- ہم آہنگی کے بعد PR کی تفصیل میں درج ہر مرکوز ٹیسٹ/گیٹ دوبارہ چلائیں۔
- تبدیل شدہ بیس سے مطابقت پیدا کرنے کے لیے کبھی بھی assertions کمزور نہ کریں یا مطلوبہ ٹیسٹس حذف نہ کریں۔

ریلیز فریز اور دوبارہ ہدف مقرر کرنے کے قواعد کے لیے،
[برانچنگ اور ریلیز ماڈل](BRANCHING_MODEL.md) استعمال کریں۔ CI کی مکمل فہرست کے لیے،
[کوالٹی گیٹس کا حوالہ](../architecture/QUALITY_GATES.md) استعمال کریں۔
