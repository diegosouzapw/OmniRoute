اس رہنما کو استعمال کرتے ہوئے کسی pull request کے لیے سب سے مختصر قابلِ اعتماد development loop منتخب کریں۔ یہ ذیل میں منسلک
علاقہ-مخصوص architecture اور security دستاویزات کا متبادل نہیں ہے؛ یہ ہر عام
تبدیلی کی قسم کو اس کے contracts، مرکوز checks، اور CI coverage سے جوڑتا ہے۔

## ہر تبدیلی کا راستہ

1. **ترمیم سے پہلے base منتخب کریں۔** سب سے بلند فعال `release/v*` branch تلاش کریں اور اس کے
   تازہ ترین سرے سے branch بنائیں۔ اسی branch کو target کریں، `main` کو نہیں۔ اگر release freeze فعال ہو تو منجمد
   branch کو target نہ کریں؛
   [Branching & Release Model](BRANCHING_MODEL.md) میں بیان کردہ اگلا فعال cycle استعمال کریں۔
2. **Contracts کی نشان دہی کریں۔** ہر اس catalog، schema، generated artifact، public API، یا user
   interface کی شناخت کریں جسے تبدیلی متاثر کرتی ہے۔ ذیل کا جدول کم از کم ابتدائی مجموعہ فراہم کرتا ہے۔
3. **مرکوز tests لکھیں یا اپ ڈیٹ کریں۔** `src/`، `open-sse/`، `electron/`، یا
   `bin/` میں production تبدیلیوں کے لیے اسی PR میں ایک automated test درکار ہے۔ پہلے سب سے مختصر test files چلائیں جو
   رویے کو ثابت کرتی ہوں، پھر درج شدہ مرکوز gates چلائیں۔
4. **وسیع matrix کو CI پر چلنے دیں۔** مکمل unit shards، Vitest، coverage ratchet، اور
   production build PR پر چلتے ہیں۔ کوئی وسیع suite مقامی طور پر صرف اس وقت چلائیں جب کوئی مرکوز failure
   وسیع تر اثر کی نشان دہی کرے یا تبدیلی کئی subsystems تک پھیلی ہوئی ہو۔
5. **Review سے پہلے مطابقت قائم کریں۔** فعال base کو fetch کریں، اس کے نئے commits اور اس کے مقابلے میں اپنا diff
   دیکھیں، پھر contributor workflow کے مطابق base کو rebase یا merge کریں۔ Generated-file
   اور catalog conflicts کو ان کے source سے حل کریں، انہیں دوبارہ generate کریں، مرکوز loop دوبارہ چلائیں، اور تصدیق کریں کہ
   PR اب بھی فعال release branch کو target کرتا ہے۔
6. **ثبوت درج کریں۔** PR template میں چلائی گئی commands، شامل یا تبدیل کی گئی ہر test file،
   migrations یا feature flags، اور CI-only validation جو ابھی زیرِ التوا ہو، درج کریں۔

## تبدیلی کی قسم کے لحاظ سے مثالی راستے

ذیل کی commands کم از کم مرکوز checks ہیں، یہ کسی ایسے test کو چھوڑنے کی اجازت نہیں
جو آپ کے تبدیل کردہ رویے کا براہِ راست احاطہ کرتا ہو۔

### Provider

**Contracts**

- `src/shared/constants/providers/` میں Provider definition اور
  `src/shared/constants/providers.ts` میں اس کی composition۔
- `open-sse/config/providerRegistry.ts` یا اس کی الگ کی گئی registry files میں Models اور capabilities۔
- قابلِ اطلاق ہونے پر Executor/translator selection، OAuth یا API-key configuration، dashboard assets، اور generated
  provider reference۔
- Public credentials کے لیے `resolvePublicCred()` استعمال کرنا لازم ہے؛ error responses کے لیے مشترکہ sanitized
  error helpers استعمال کرنا لازم ہے۔ `docs/security/PUBLIC_CREDS.md` (git؛ `/docs` میں compile نہیں ہوتی) اور
  [Error Sanitization](../security/ERROR_SANITIZATION.md) دیکھیں۔

**مرکوز loop**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # جب catalog تبدیل ہو؛ generated diff کو commit کریں
npm run lint
```

متاثرہ ہر request family کو بھی test کریں: chat، Responses، images، embeddings، audio، یا video۔
Generated catalog اور golden diffs کا contract changes کے طور پر review کریں؛ انہیں بغیر جانچے قبول نہ کریں۔

### Routing

**Contracts**

- `src/shared/constants/routingStrategies.ts` میں Public strategy values اور UI metadata۔
- `open-sse/services/combo.ts` اور `open-sse/services/combo/` کے تحت dispatch اور ordering۔
- Combo schemas، persistence، resilience state، model capabilities، اور API/UI controls۔
- رویہ تبدیل ہونے پر [Auto-Combo Engine](../routing/AUTO-COMBO.md) اور resilience documentation۔

**مرکوز loop**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # strategy یا dispatch میں تبدیلیاں
npm run check:known-symbols      # strategy registration میں تبدیلیاں
npm run lint
```

مقامی طور پر deterministic mocked-upstream tests استعمال کریں۔ Live combo smokes کے لیے credentials درکار ہوتے ہیں اور یہ
دستی ہیں، CI کے متبادل نہیں۔

### UI / UX

**Contracts**

- `src/app/` اور `src/shared/components/` کے تحت Next.js route/page اور مشترکہ component boundaries۔
- API response shapes، loading/empty/error states، keyboard اور screen-reader behavior،
  responsive layout، theming، اور locale expansion۔
- `src/i18n/messages/en.json` میں انگریزی UI source strings؛ نیا user-facing متن hard-code نہ کریں۔

**مرکوز loop**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Interaction یا visual تبدیلیوں کے لیے app چلائیں اور تنگ و کشادہ دونوں viewports چیک کریں۔ CI
production build اور وسیع تر suites چلاتا ہے؛ visual behavior کے لیے پھر بھی تبدیلی کے مطابق کوئی مرکوز component، Playwright،
یا دستاویزی manual check درکار ہے۔

### i18n

**Contracts**

- `src/i18n/messages/en.json`، UI source ہے؛ `config/i18n.json`، locale source ہے۔
- CLI catalogs الگ سے `bin/cli/locales/` کے تحت موجود ہیں۔
- ICU placeholders اور tags کو بالکل جوں کا توں محفوظ رکھیں۔ product/provider/model names،
  protocol اور header names، commands، code/JSON identifiers، URLs، environment variables، یا
  `OmniRoute`، `OAuth`، `MCP`، اور `A2A` جیسی protected terms کا ترجمہ نہ کریں۔ موجودہ source list
  `scripts/i18n/glossary/protected-terms.json` ہے۔

**مرکوز loop**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # جب CLI strings/catalogs تبدیل ہوں
npm run lint
```

یہ موجودہ system کے لیے رہنمائی ہے، اس کے tooling یا key model کو وسیع کرنے کی دعوت نہیں۔
جب تک replacement system تیار کیا جا رہا ہے، i18n patches کو نہایت محدود رکھیں۔ ایسی translation
commands نہ چلائیں جو external services کو call کرتی ہوں، الا یہ کہ task واضح طور پر generated translations کا تقاضا کرے اور
آپ نے نتیجے میں بننے والے diff کا review کر لیا ہو۔

### CLI

**Contracts**

- `bin/cli/` میں عوامی commands اور flags، تیار کردہ API commands، exit codes، stdout/stderr اور
  JSON output کی ساختیں، config/environment کا رویہ، اور پیکیج کردہ فائلیں۔
- CLI کے صارف کو دکھائی دینے والے strings کے لیے CLI i18n layer استعمال کرنا لازم ہے اور `en`/`pt-BR` catalogs کو ہم آہنگ رکھا جائے۔
- Node کو معاونت یافتہ runtime اور شائع شدہ binary contract کے طور پر برقرار رکھیں۔

**مرکوز دور**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # تیار کردہ/بنڈل شدہ CLI تبدیلیاں
npm run check:pack-policy     # پیکیج کی سطح میں تبدیلیاں
npm run lint
```

جب رویہ parsing، فائلوں، یا exit status پر منحصر ہو تو عارضی data directory میں عین وہی command استعمال کریں۔
CI پیکیج artifacts اور ecosystem کی مزید وسیع جانچیں انجام دیتا ہے۔

### ڈیٹابیس

**معاہدے**

- `src/lib/db/` کے تحت domain modules؛ مخصوص modules کو براہِ راست import کریں (پرانا `localDb.ts` re-export layer ہٹا دیا گیا تھا)۔
- `src/lib/db/migrations/` کے تحت نمبر شدہ، idempotent SQL migrations، transaction safety، upgrade
  کا رویہ، indexes، اور schema سے متاثر ہونے والا ہر caller۔
- Routes اور handlers کبھی بھی براہِ راست raw SQL جاری نہیں کرتے۔

**مرکوز دور**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

migration شامل کرتے وقت ایک نیا database اور سابقہ schema سے upgrade، دونوں کو test کریں۔ Database tests
کو handles بند کرنے اور cleanup کے دوران `resetDbInstance()` کو call کرنے کی ضرورت ہے۔ `npm run test:bun:db` صرف اس وقت چلائیں
جب best-effort Bun adapter path تبدیل ہو؛ Node بدستور حتمی معیار ہے۔

### Build / تعیناتی

**معاہدے**

- Root اور workspace manifests/lockfile، `scripts/build/`، Next.js standalone assembly، `dist/`
  پیکیج کے مندرجات، Electron platform metadata، CI workflows، اور deployment sentinels۔
- معاونت یافتہ Node ranges اور `CLAUDE.md` میں allow-listed Bun کا استعمال برقرار رہنا چاہیے۔
- Build artifacts untracked رہیں؛ dependency، license، workflow، اور package policies لاگو ہوتی ہیں۔

**مرکوز دور**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # dependency یا lockfile میں تبدیلیاں
npm run check:pack-policy      # شائع شدہ پیکیج کی سطح میں تبدیلیاں
npm run lint
```

`npm run build` کو مقامی طور پر صرف اس وقت استعمال کریں جب تبدیلی compilation، standalone assembly، assets،
یا runtime bundling کو متاثر کرے۔ `npm run build:release` صرف release/deploy validation کے لیے استعمال کریں۔ CI کا build
حتمی cross-platform اشارہ ہے؛ platform-specific Electron تبدیلیوں کے لیے متعلقہ focused build
یا smoke evidence درکار ہے۔

## مقامی لوپ بمقابلہ CI

| ہر پیچ کے لیے مقامی طور پر چلائیں                                   | CI وسیع تر اشارہ فراہم کرتا ہے                                             |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| براہِ راست رویّے کے ٹیسٹس اور اوپر دیے گئے زمرہ جاتی گیٹس           | حصوں میں تقسیم مکمل یونٹ سوٹ اور سلسلہ وار ٹیسٹس                           |
| `npm run lint`                                                      | Vitest سوٹس اور کوریج/معیار کے بتدریج سخت ہوتے معیارات                     |
| ٹائپ چیک یا بلڈ صرف اس وقت جب متاثرہ کنٹریکٹ اس کا تقاضا کرے        | پروڈکشن بلڈ، سیکیورٹی، دستاویزات، ڈیپینڈنسی، اور PR پالیسی گیٹس            |
| دستی تعامل/لائیو جانچ صرف اس وقت جب خودکاری رویّے کو ثابت نہ کر سکے | ورک فلو کے ذریعے ترتیب دی گئی مختلف جابز کی انٹیگریشن اور پلیٹ فارم جانچیں |

ایک کامیاب مرکوز لوپ تبدیل شدہ کنٹریکٹ کے بارے میں ثبوت ہے، اس بات کا ثبوت نہیں کہ غیر متعلقہ CI جانچیں
کامیاب ہوں گی۔ اس کے برعکس، ہر مقامی ترمیم کو مکمل ریپوزٹری میٹرکس کا انتظار نہ کروائیں۔

## مطابقت پذیری کی چیک لسٹ

جائزے کی درخواست کرنے سے پہلے:

- تصدیق کریں کہ PR کی بیس اب بھی سب سے اعلیٰ فعال `release/v*` برانچ ہے۔
- اس بیس کو فیچ کریں اور اپنی برانچ بنانے کے بعد سے شامل ہونے والی کمیٹس کا جائزہ لیں۔
- غیر ارادی یا خودکار طور پر پیدا ہونے والی تبدیلیوں کے لیے `git diff <active-base>...HEAD` کا جائزہ لیں۔
- کیٹلاگ اور خودکار طور پر تیار شدہ دستاویزات کے تنازعات کو ماخذ اپ ڈیٹ کرکے اور آؤٹ پٹ دوبارہ تیار کرکے حل کریں۔
- مطابقت پذیری کے بعد PR کی تفصیل میں درج ہر مرکوز ٹیسٹ/گیٹ دوبارہ چلائیں۔
- محض تبدیل شدہ بیس سے مطابقت پیدا کرنے کے لیے کبھی بھی assertions کو کمزور نہ کریں یا مطلوبہ ٹیسٹس نہ ہٹائیں۔
