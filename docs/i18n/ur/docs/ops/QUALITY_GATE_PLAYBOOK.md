> **یہ دستاویز کیا ہے۔** OmniRoute کے quality-gate نظام کا ایک تنقیدی جائزہ،
> جس کا موازنہ صنعتی بہترین طریقوں سے کیا گیا ہے، **نیز** تمام quality
> checkpoints کی ایک جامع فہرست اور اسی نظام کو کسی بھی project پر لاگو کرنے کے لیے ایک **tool-agnostic replication plan**۔
> یہ 2026-06-16 کو repository کی حقیقی حالت کی بنیاد پر تیار کی گئی (یادداشت کی بنیاد پر نہیں)۔
>
> معیارات: OWASP DSOMM · OpenSSF Scorecard · SLSA · SonarQube "Clean as You Code" ·
> Quality-Ratchet pattern · DORA 2024 · OWASP LLM Top 10 (2025) · mutation-testing کے بہترین طریقے۔
>
> ہر gate کے مستند حوالہ کے لیے (ہر gate کیا validate کرتا ہے، CI job، ratchet بمقابلہ
> policy، blocking بمقابلہ advisory)،
> [Quality Gates Reference](../architecture/QUALITY_GATES.md) دیکھیں۔

## حصہ 1 — فیصلہ اور پختگی کی درجہ بندی

**مجموعی گریڈ: A− / "اعلیٰ درجے کا"۔ سرفہرست تقریباً 5–10% projects میں۔** یہ نظام آزادانہ طور پر
کئی ایسے patterns نافذ کرتا ہے جنہیں صنعت واضح طور پر نام دیتی ہے — اور یہی مطابقت کا سب سے مضبوط
اشارہ ہے (ہم نے کسی checklist کی نقل نہیں کی؛ ہم خود درست طریقوں تک پہنچے)۔

| حوالہ جاتی framework                     | ہماری موجودہ حیثیت                                                                                                                                                                                                                         | گریڈ                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| **OWASP DSOMM** (5 levels، 5 dimensions) | مضبوط Level 3، جبکہ _Test Intensity_ اور _Static Depth_ میں Level 4 تک پہنچ رہا ہے۔ زیادہ تر ادارے 1–2 پر ہیں۔                                                                                                                             | **L3→L4**                               |
| **OpenSSF Scorecard** (18 checks)        | ہم CI-Tests، Code-Review، Dependency-Update-Tool، Fuzzing، SAST، Signed-Releases (provenance)، Token-Permissions، Vulnerabilities، Dangerous-Workflow پاس کرتے ہیں۔ **خلا:** `main` پر Branch-Protection بند ہے؛ کچھ actions pin نہیں ہیں۔ | **~7–8/10**                             |
| **SLSA** (4 levels)                      | `npm publish --provenance` + `id-token: write` + GitHub-hosted build = **L2**، اور L3 کے قریب۔ L3+ کے لیے hardened/hermetic builder موجود نہیں۔                                                                                            | **L2→L3**                               |
| **SonarQube "Clean as You Code"**        | یکساں فلسفہ: ratchet _non-regression_ نافذ کرتا ہے (نیا code metric کو بدتر نہیں کرتا)۔ **اختلاف:** Sonar **کم** conditions تجویز کرتا ہے؛ ہمارے پاس تقریباً 46 gates ہیں (تھکن کا خطرہ)۔                                                  | **مطابقت رکھتا ہے، ایک احتیاط کے ساتھ** |
| **Quality-Ratchet pattern**              | حوالہ جاتی implementation: ratchet + `dedicatedGate` + `tightenSlack` + `--require-tighten` + graceful-skip۔ بیشتر عوامی مثالوں سے زیادہ نفیس۔                                                                                             | **مثالی**                               |
| **DORA 2024**                            | _stability_ محور پر بہت مضبوط۔ خطرہ: بھاری gates سے _lead time_ بڑھ سکتا ہے — fast-gates کی تقسیم سے اس میں کمی کی گئی ہے، مگر coverage gap موجود ہے (حصہ 2 دیکھیں)۔                                                                       | **مضبوط (استحکام)**                     |
| **OWASP LLM Top 10 (2025)**              | ہم خطرہ #1 (prompt-injection) کو runtime guard + promptfoo (eval) + garak (red-team) کے ذریعے cover کرتے ہیں۔ یہ معیاری صنعتی tools ہیں۔                                                                                                   | **احاطہ شدہ**                           |
| **Mutation testing**                     | Stryker رات کو چلتا ہے، thresholds 70/50 ہیں، اور 8 اہم modules شامل ہیں۔ صنعتی اتفاقِ رائے (موجودہ code کے لیے 60% / نئے کے لیے 80%، رات کو) — **ہم اس سے بہتر ہیں**۔ **خلا:** score ابھی ratchet نہیں ہے۔                                | **تقریباً مکمل**                        |

## حصہ 2 — تنقیدی جائزہ (خوبیاں + دیانت دارانہ کمزوریاں)

### خوبیاں (جو اوسط سے بہتر ہے)

1. **کثیر میٹرک ریچٹ انجن۔** نظام کا مرکزی حصہ۔ `quality-baseline.json` میں 24 میٹرکس
   - 4 مخصوص بیس لائنز، جن میں سے ہر ایک کے ساتھ سمت (`up`/`down`)، قابلِ برداشت حد (`eps`)، گنجائش
     (`tightenSlack`) اور `dedicatedGate` فلیگ ہے۔ جو چیزیں درست ہو جاتی ہیں، وہ **درست ہی رہتی ہیں** — یہ
     کوڈ بیس کے بتدریج انحطاط کا تریاق ہے۔
2. **سپلائی چین کے لیے دفاع کی متعدد تہیں۔** SAST (CodeQL/Sonar) + سیکرٹس (gitleaks مع
   `useDefault`) + SCA (osv/npm-audit/Trivy/Dependabot) + لائسنسز + لاک فائل + SBOM + SLSA
   پروویننس + Scorecard + ورک فلو ہارڈننگ (zizmor)۔ بہت کم کوڈ بیسز میں یہ مکمل مجموعہ موجود ہوتا ہے۔
3. **Goodhart's Law کے خلاف تریاق۔** کوریج کو ہدف بنانا ایک روایتی اینٹی پیٹرن ہے
   ("جب پیمانہ خود ہدف بن جائے تو وہ اچھا پیمانہ نہیں رہتا")۔ ہمارے پاس اس کے توازن کے لیے:
   **میوٹیشن ٹیسٹنگ** (یہ جانچتی ہے کہ آیا ٹیسٹ بگ کو پکڑتا ہے، نہ کہ صرف یہ کہ آیا وہ لائن کو
   چلاتا ہے)، **`check-test-masking`** (پاس ہونے کے لیے asserts کو کمزور کرنے سے روکتا ہے)،
   **فی ماڈیول کوریج کی کم از کم حدیں** (صرف آسان حصوں کے بجائے زیادہ خطرے والے کوڈ کی ٹیسٹنگ لازم کرتی ہیں) اور
   **`check-pr-evidence`** (سخت اصول #18)۔
4. **ہیلوسینیشن مخالف / مستقل مزاجی کے گیٹس۔** ایک نایاب اور قیمتی زمرہ: `check-known-symbols`،
   `check-fetch-targets`، `check-openapi-routes`، `check-docs-symbols` یقینی بناتے ہیں کہ دستاویزات، اسپیِکس اور
   اسٹرنگ ڈسپیچز فعال سمبلز کی طرف اشارہ کریں۔ اس "بوسیدگی" کو پکڑتے ہیں جسے lint/test نہیں پکڑتے۔
5. **مشاورتی→بلاکنگ لائف سائیکل۔** نئے گیٹس ابتدا میں مشاورتی ہوتے ہیں (پختہ ہونے کے دوران
   مرجز کو بلاک نہیں کرتے)، پھر سائیکل کے اختتام پر بلاکنگ بن جاتے ہیں۔ معیار کی بالائی حد کھوئے بغیر رکاوٹ کم ہوتی ہے۔
6. **انفرا اسٹرکچر موجود نہ ہونے پر محتاط انداز سے اسکیپ۔** اگر بائنری/نیٹ ورک
   ناکام ہو تو اسکینرز (`--ratchet`) `exit 0` کے ساتھ بند ہوتے ہیں — غائب انفرا اسٹرکچر کبھی بھی کسی جائز PR کو بلاک نہیں کرتا۔ یہ پختہ انجینئرنگ ہے۔
7. **ضابطہ بند ثقافت۔** سخت اصول + `trust-but-verify` + stale-allowlist + evidence-gate
   نظم و ضبط کو خودکار تصدیق میں تبدیل کرتے ہیں۔

### دیانت دارانہ کمزوریاں (حقیقی خلا)

1. **🔴 fast-gates کی تقسیم اب بھی ایک ساختی خلا چھوڑتی ہے۔** `quality.yml` (PR→`release/**`)
   اب کوڈ PRs کے لیے typecheck، تیز اور قطعی ٹیسٹس، اور ایک مشاورتی پروڈکشن بلڈ چلاتی ہے،
   لیکن اب بھی `ci.yml` کی مکمل release-PR سطح (کوریج ریچٹس،
   پیکیج آرٹیفیکٹ، انٹیگریشن، E2E، SonarQube) نہیں چلاتی۔ محرک (رفتار) درست ہے، لیکن گیٹ
   وہاں ہونا چاہیے جہاں مرج ہوتا ہے (shift-left)۔ **سب سے بڑی زیرِ التوا ساختی اصلاح۔**
2. **🟠 گیٹس کے پھیلاؤ/تھکن کا خطرہ۔** تقریباً 46 گیٹس + 25 جابز بہت زیادہ ہیں۔ خود Sonar خبردار کرتا ہے:
   بہت زیادہ شرائط "گیٹ تھکن" اور ترجیحات پر بحث کا باعث بنتی ہیں، جس سے کسی گیٹ کے
   نظرانداز ہونے کا خطرہ ہوتا ہے۔ DORA خبردار کرتا ہے کہ بھاری گیٹس lead-time بڑھاتے ہیں۔ ہم مشاورتی درجات اور
   غیر مطلق ریچٹس سے اس کا تدارک کرتے ہیں، لیکن **ہر گیٹ کا وقفہ وار ROI جائزہ** موجود نہیں (doc-sync کے لیے بعض مائیکرو گیٹس
   یکجا کیے جا سکتے ہیں)۔
3. **🟠 میوٹیشن اسکور ابھی ریچٹ نہیں ہے۔** کوریج سے کھیلنے کے خلاف سب سے مضبوط تریاق
   **مشاورتی** ہے۔ یہ سب سے زیادہ قدر والا زیرِ التوا آئٹم ہے (اور پہلے ہی 90% تیار ہے)۔
4. **🟡 وہ مشاورتی چیزیں جنہیں بلاک کرنا چاہیے (درست دائرۂ کار کے ساتھ)۔** `osv` (vulnCount) اور `oasdiff`
   منجمد بیس لائنز کے باوجود مشاورتی ہیں۔ osv-advisory قابلِ فہم ہے (کسی پرانی dependency میں نئی CVE کسی
   غیر متعلقہ PR کو بلاک کر دے گی) — لیکن ایک درمیانی راستہ موجود ہے (صرف CRITICAL+fixable کو بلاک کریں، جیسا کہ ہم نے
   Trivy کے ساتھ کیا)۔ oasdiff کے مشاورتی ہونے کا مطلب ہے کہ کنٹریکٹ توڑنے والی تبدیلی پاس ہو سکتی ہے۔
5. **🟡 رَن ٹائم سیکیورٹی صرف رات کو چلتی ہے۔** schemathesis/garak/promptfoo/chaos/k6 رات کو چلتے ہیں۔
   یہ درست فیصلہ ہے (سست ہیں، ایک فعال سرور درکار ہوتا ہے)، لیکن کوئی PR injection-guard میں ایسی خرابی متعارف کرا سکتا ہے
   جو اگلی رات ہی پکڑی جائے۔
6. **🟡 `main` پر برانچ پروٹیکشن بند ہے۔** `BRANCH_LOCK_TOKEN` _release_ برانچز کو لاک کرتا ہے، لیکن
   خود `main` غیر محفوظ ہے۔ Scorecard/DSOMM اس پر منفی نشان دیتے ہیں۔ مالک کی کارروائی درکار ہے۔
7. **🟡 CodeQL default-setup؛ semgrep ضابطہ بند نہیں۔** default-setup کام کرتا ہے (0 alerts)، لیکن
   کمیٹ شدہ `codeql.yml` زیادہ کنٹرول فراہم کرتی ہے؛ semgrep ایک بیرونی کلاؤڈ پلیٹ فارم کے ذریعے چلتا ہے،
   ریپو میں ورژن شدہ نہیں ہے۔

## حصہ 3 — معیار کی جانچ کے مقامات کا مکمل کیٹلاگ (قابلِ منتقلی)

ذیل کی 12 اقسام دوبارہ قابلِ استعمال شکل میں "معیار کا نظام" ہیں۔ ہر ایک میں
**مقصد** (کس چیز کی حفاظت کرنی ہے)، **ہمارے زیرِ استعمال ٹولز** اور کسی بھی اسٹیک پر اسے نقل کرنے کے لیے **ٹول سے آزاد متبادل**
درج ہیں۔

### 1. انداز اور فارمیٹنگ (قطعی، تیز)

- **OmniRoute:** lint-staged کے ذریعے Prettier + ESLint (pre-commit)، 2-spaces/double-quotes/100col۔
- **عمومی:** خودکار طور پر درست کیا جا سکنے والا ایک فارمیٹر + ایک لنٹر، جو staged فائلوں پر pre-commit میں چلیں۔

### 2. اقسام

- **OmniRoute:** `typecheck:core` (روکنے والا) + `typecheck:noimplicit:core` (مشاورتی) + `type-coverage` ریچٹ 92.17% + ہر فائل کے لیے any-budget۔
- **عمومی:** CI میں سخت typecheck + ریچٹ شدہ type-coverage میٹرک + ہر فائل کے لیے `any`/escape-hatch بجٹ۔

### 3. ٹیسٹس (شدت)

- **OmniRoute:** 2 غیر متداخل رنرز (Node native + vitest)، 8 shards، مجموعی coverage 60/60/60/60 + ریچٹ ~76% + **اہم ماڈیولز کے لیے 8 فی ماڈیول کم از کم حدیں** + راتانہ property tests + راتانہ **mutation testing**۔
- **عمومی:** ٹیسٹ رنر (یا رنرز) + coverage کی **مطلق** کم از کم حد (صفر سے بچاؤ) + coverage **ریچٹ** (تنزلی سے بچاؤ) + **زیادہ خطرے والے کوڈ کے لیے فی ماڈیول کم از کم حدیں** (Goodhart سے بچاؤ) + خالص منطق کے لیے property-based ٹیسٹنگ + ٹیسٹ کے معیار کی حقیقی پیمائش کے طور پر راتانہ **mutation testing**۔

### 4. ٹیسٹ پالیسی (ہیرا پھیری سے بچاؤ)

- **OmniRoute:** `pr-test-policy` (پروڈکشن کوڈ کے لیے ٹیسٹ لازم ہے)، `check-test-masking` (کمزور کیے گئے asserts کو روکتا ہے)، `pr-evidence` (کامیابی کے دعوے کے لیے ثبوت کا بلاک لازم ہے)، `test-discovery` (ہر ٹیسٹ کو کوئی رنر جمع کرتا ہے)۔
- **عمومی:** "نیا کوڈ ⇒ نیا ٹیسٹ" گیٹ + ہٹائے گئے assert/tautology کا کھوج کار + ثبوت کی شرط (TDD یا فعال ٹیسٹ) + یہ ضمانت کہ کوئی ٹیسٹ globs سے باہر یتیم نہ رہ جائے۔

### 5. پیچیدگی اور کوڈ کی صحت (ریچٹس)

- **OmniRoute:** ESLint-warnings (3769↓)، jscpd duplication (5.72%↓)، cyclomatic+max-lines complexity (1800↓)، cognitive complexity sonarjs (753↓)، dead-code/unused-exports knip (339↓)، ہر فائل کا file-size (منجمد، صرف کمی)، circular-deps (حسبِ ضرورت Tarjan، روکنے والا)۔
- **عمومی:** صحت کے ہر میٹرک کو ریچٹ کریں (تنبیہات، نقل، cyclomatic **اور** cognitive پیچیدگی، مردہ کوڈ، فائل کا حجم، import چکر)۔ سمت ہمیشہ "تنزلی نہ ہو" ہو۔

### 6. جامد سکیورٹی (SAST + secrets)

- **OmniRoute:** CodeQL (alerts ریچٹ = 0)، gitleaks (`[extend] useDefault=true` — انتہائی اہم!)، SonarQube، حسبِ ضرورت سکیورٹی قواعد (public-creds، error-helper، route-guard-membership، route-validation)۔
- **عمومی:** alert ریچٹ کے ساتھ SAST (CodeQL/Sonar/semgrep) + **وراثت میں ملنے والے پہلے سے طے شدہ ruleset** کے ساتھ secrets scanner (پہلے سے طے شدہ ترتیب کو override کرنے والی حسبِ ضرورت ترتیب = اندھا پن) + منصوبے کے لیے مخصوص Hard Rule سکیورٹی گیٹس۔

### 7. سپلائی چین (dependencies)

- **OmniRoute:** osv-scanner + npm-audit + Trivy + Dependabot (SCA)، license-checker (SPDX allowlist)، lockfile-lint (HTTPS+sha512+registry)، `check-deps` anti-slopsquatting (allowlist + عمر ≥72h)۔
- **عمومی:** متعدد ذرائع والا SCA + لائسنس allowlist + lockfile کی سالمیت کی جانچ + عمر/typosquatting کی جانچ کے ساتھ dependency allowlist + گروپ شدہ update bot۔

### 8. سپلائی چین (build اور release)

- **OmniRoute:** SBOM (CycloneDX + syft)، SLSA provenance (`--provenance`)، OpenSSF Scorecard (ہفتہ وار)، workflow کی مضبوطی (zizmor: artipacked→`persist-credentials:false`، cache-poisoning، token-permissions)۔
- **عمومی:** publish کرتے وقت SBOM بنائیں + دستخط شدہ provenance (SLSA L2+) + مقررہ شیڈول پر Scorecard + تمام workflows کو مضبوط بنائیں (کم از کم اختیارات والے tokens، non-pusher checkout پر کوئی محفوظ شدہ credentials نہیں، actions کو SHA کے ذریعے pin کیا گیا ہو)۔

### 9. معاہدے اور API

- **OmniRoute:** oasdiff (breaking-change OpenAPI)، schemathesis (راتانہ contract fuzz)، openapi-coverage (دستاویزی routes کا %، ریچٹ 38.3%)، openapi-security-tiers (spec بمقابلہ route-guard)۔
- **عمومی:** breaking-change contract diff (oasdiff/buf) + spec کے خلاف property-based fuzz (schemathesis) + دستاویزی coverage کا ریچٹ + spec↔code مطابقت۔

### 10. دستاویزات اور i18n (بوسیدگی سے بچاؤ)

- **OmniRoute:** docs-sync (عکس شدہ versions)، docs-counts-sync (دستاویزات کے اعداد بمقابلہ کوڈ)، env-doc-sync، doc-links، fabricated-docs، cli-i18n، i18n-ui-coverage (`--threshold=65` + ریچٹ 80.1%)۔
- **عمومی:** دستاویزات اور کوڈ کے درمیان versions/counts/env-vars کو ہم آہنگ کریں (گیٹ، محض اعتماد نہیں) + داخلی links کی توثیق کریں + i18n coverage کو ریچٹ کریں۔

### 11. واہمہ سازی سے بچاؤ / مطابقت (نایاب زمرہ)

- **OmniRoute:** known-symbols (string dispatch ⇒ فعال symbol)، provider-consistency، fetch-targets (client fetch ⇒ حقیقی route)، docs-symbols، db-rules (Hard Rules #2/#5)، migration-numbering۔
- **عمومی:** ہر "نقل شدہ واحد ماخذِ حقیقت" (registry، string dispatch، تہوں کے درمیان حوالہ جات) کے لیے ایسا گیٹ جو ثابت کرے کہ دونوں اطراف مطابقت رکھتے ہیں۔ یہ اس بوسیدگی کو پکڑتا ہے جسے typecheck/test نہیں پکڑتے۔

### 12. لچک اور ڈومین (پروڈکٹ کے لیے مخصوص)

- **OmniRoute:** chaos (fault-injection)، heap-growth (leak)، k6 (soak)، promptfoo+garak (LLM red-team OWASP LLM Top 10)، لچک کے 3 قوانین (circuit-breaker/cooldown/lockout)۔
- **عمومی:** **اپنے** ڈومین کی ناکامی کی صورتوں کی نشان دہی کریں اور ہر ایک کے لیے ایک گیٹ رکھیں (چاہے وہ راتانہ ہی کیوں نہ ہو)۔ AI ایپس کے لیے: injection red-team۔ تقسیم شدہ نظاموں کے لیے: chaos + leak + soak۔

## حصہ 4 — کسی بھی پروجیکٹ کے لیے نقل پذیری کا منصوبہ

**مراحل** میں تعمیر کریں، جن میں سے ہر مرحلہ بذاتِ خود قدر فراہم کرے۔ تمام 12 زمروں کو ایک ساتھ نافذ کرنے کی کوشش نہ کریں —
اس سے عین وہی گیٹ تھکن پیدا ہوتی ہے جس کے بارے میں حصہ 2 خبردار کرتا ہے۔ ہر نیا گیٹ پہلے **مشاورتی** ہوتا ہے اور
مستحکم ہونے پر **بلاکنگ** بن جاتا ہے۔

### دوبارہ قابلِ استعمال مرکزی جزو: "ریچٹ گیٹ کی ساخت"

پورا نظام اس 3-فائل پیٹرن کے گرد گھومتا ہے۔ پہلے اسے نقل کریں:

1. **`baseline.json`** — منجمد میٹرک قدر + `direction` (`up`/`down`) + `eps` (اتار چڑھاؤ سے تحفظ) + `tightenSlack` + `dedicatedGate`۔
2. **`collect-metrics.<ext>`** — ٹول چلاتی ہے، عدد اخذ کرتی ہے، اور `metrics.json` لکھتی ہے۔
3. **`check-ratchet.<ext>`** — `metrics.json` کا `baseline.json` سے موازنہ کرتی ہے؛ `exit 1` **صرف** اس صورت میں جب تنزلی `eps` سے تجاوز کر جائے؛ اگر ٹول/انفراسٹرکچر موجود نہ ہو تو `exit 0` (بلا رکاوٹ نظرانداز)؛ `--require-tighten` کے ساتھ، اگر بیس لائن اپ ڈیٹ کیے بغیر **بہتری** آئی ہو تو `exit 1` (حاصل شدہ بہتری کو محفوظ کر دیتا ہے)۔

اس کے نافذ ہونے کے بعد، **ہر** نیا میٹرک (کوریج، پیچیدگی، انتباہات، SAST الرٹس، بنڈل سائز، میوٹیشن اسکور…) بیس لائن میں محض ایک سطر ہے۔

### مرحلہ 0 — بنیاد (ہفتہ 1)

CI موجود ہو؛ فارمیٹر + لنٹر + ٹائپ چیک + 1 ٹیسٹ رنر + **مطلق** کوریج کی کم از کم حد
(مثلاً، 60%)۔ پری کمیٹ تیز رفتار، خودکار طور پر درست کیے جانے والے چیکس چلاتا ہے۔ _نتیجہ: کوئی PR بنیادی چیزوں کو نہیں توڑتا۔_

### مرحلہ 1 — ریچٹ انجن (ہفتہ 2) — **ہر چیز کی بنیاد**

اوپر دی گئی 3 فائلیں نافذ کریں۔ انتباہات، کوریج، پیچیدگی، نقل،
مردہ کوڈ اور فائل سائز کے لیے بیس لائنز منجمد کریں۔ _نتیجہ: یہاں سے کوڈ بیس صرف بہتر ہو سکتا ہے۔_

### مرحلہ 2 — جامد گہرائی (ہفتہ 3)

الرٹ ریچٹ کے ساتھ SAST (CodeQL/Sonar/semgrep)؛ سیکرٹس اسکینر (**پہلے سے طے شدہ رول سیٹ کو وراثت میں لیں**)؛
SCA (osv/Dependabot) + لائسنس کی اجازت فہرست + lockfile-lint۔ _نتیجہ: معلوم کمزوریاں اور
افشا شدہ راز منظور نہیں ہوتے۔_

### مرحلہ 3 — بلڈ سپلائی چین (ہفتہ 4)

اشاعت پر SBOM + دستخط شدہ ماخذ کا ثبوت (SLSA L2) + شیڈول شدہ Scorecard + ورک فلو کی سخت کاری
(zizmor: کم از کم ٹوکنز، کوئی محفوظ شدہ اسناد نہیں، پن کیے گئے ایکشنز)۔ _نتیجہ: قابلِ سراغ اور
چھیڑ چھاڑ سے محفوظ ریلیزز۔_

### مرحلہ 4 — ٹیسٹ کی شدت (ہفتہ 5–6)

اگر مفید ہو تو دوسرا رنر؛ **اہم ماڈیولز کے لیے فی ماڈیول کوریج کی کم از کم حدود** (اینٹی Goodhart)؛
خالص منطق کے لیے پراپرٹی پر مبنی ٹیسٹنگ؛ **رات کو میوٹیشن ٹیسٹنگ** → پہلا اسکور آتے ہی،
`mutationScore` کو ریچٹ بنا دیں۔ _نتیجہ: کوریج دکھاوے کا میٹرک نہیں رہتی؛ ٹیسٹس ثابت شدہ طور پر بگز پکڑتے ہیں۔_

### مرحلہ 5 — کنٹریکٹ اور ڈائنامک (ہفتہ 7)

اگر کوئی عوامی API ہو: oasdiff (توڑنے والی تبدیلی، **بلاکنگ**) + schemathesis (رات کو فزنگ)۔
ڈومین کے مطابق رات کو DAST/ریڈ ٹیم چلائیں۔ _نتیجہ: کنٹریکٹس خاموشی سے نہیں ٹوٹتے۔_

### مرحلہ 6 — اینٹی ہیلوسینیشن اور ڈومین (ہفتہ 8)

پروجیکٹ میں ہر "نقل شدہ سچائی" کے لیے ایک مطابقتی گیٹ۔ ڈومین سے مخصوص ناکامی کے طریقوں کے
گیٹس (AI کے لیے: انجیکشن ریڈ ٹیم)۔ _نتیجہ: ساختی بگاڑ اور ڈومین کی ناکامیوں کے لیے حفاظتی جال موجود ہے۔_

### مرحلہ 7 — نظم و نسق (مسلسل)

- ہر نئے گیٹ کے لیے مشاورتی→بلاکنگ چکر۔
- `stale-allowlist`: ہر استثنا کے ساتھ جواز + مسئلہ ہو؛ متروک استثنا پکڑا جائے۔
- `evidence-gate`: PR میں کامیابی کے دعوے کے لیے ثبوت درکار ہو (ٹیسٹ یا زندہ ٹیسٹ)۔
- **ہر گیٹ کا سہ ماہی ROI جائزہ** (جو فائدہ نہ دیں انہیں ختم کریں/ان کی فنڈنگ روکیں — یہ تھکن کا مقابلہ کرتا ہے)۔
- اپنے پروجیکٹ کے سخت قواعد کو قابلِ نفاذ گیٹس میں تبدیل کریں۔

### تمام مراحل پر لاگو اصول (ناقابلِ سمجھوتہ)

- **ریچٹ، مطلق نہیں۔** کسی مقررہ عدد کے بجائے _عدم تنزلی_ کو گیٹ کریں (سوائے صفر سے بچانے والی کم از کم حدود کے)۔
- **مطلق کم از کم حد + ریچٹ ایک ساتھ۔** کم از کم حد مکمل زوال روکتی ہے؛ ریچٹ بتدریج تنزلی روکتا ہے۔
- **ڈیزائن ہی سے اینٹی Goodhart۔** ہر ہدفی میٹرک کے لیے توازن پیدا کرنے والا پیمانہ ضروری ہے (کوریج ⇒ میوٹیشن + اینٹی ماسکنگ؛ مشکل کوڈ کی ٹیسٹنگ یقینی بنانے کے لیے فی ماڈیول کم از کم حدود)۔
- **بلا رکاوٹ نظرانداز۔** غائب انفراسٹرکچر کبھی بلاک نہیں کرتا؛ صرف حقیقی تنزلی بلاک کرتی ہے۔
- **مہنگے میٹرکس کے لیے `dedicatedGate`۔** جن میٹرکس کو بیرونی بائنری درکار ہو، ان کے لیے اپنی الگ اسکرپٹ ہو (نظرانداز کرنے کی سہولت کے ساتھ)، جو ہم وقت مرکزی ریچٹ سے باہر ہو۔
- **گیٹ وہیں لگائیں جہاں مرج ہوتا ہے۔** تیز رفتار گیٹ اور اصل مرج کے درمیان خلا نہ چھوڑیں (fast-gates کی تقسیم سے حاصل ہونے والا سبق)۔
- **چند، اچھی طرح منتخب بلاکنگ گیٹس۔** Sonar/DORA: بہت زیادہ شرائط = تھکن۔ بلاکنگ گیٹس کی دیوار کے بجائے مشاورتی + ریچٹ کو ترجیح دیں۔

## حصہ 5 — تجویز کردہ بہتریاں (ترجیحی، ہم آہنگ)

**P0 — سب سے زیادہ ROI، تقریباً تیار**

1. **میوٹیشن اسکور ریچٹ** (پہلی رات کی Stryker رَن سے قدریں حاصل ہونے کے بعد)۔ coverage-Goodhart کے خلاف کلیدی تریاق؛ ~90% مکمل۔
2. **باقی ماندہ fast-gates خلا کو بند کریں** — `quality.yml` کی پروڈکشن بلڈ کو اس کے
   مشاورتی ہفتے کے بعد ترقی دیں اور صرف deterministic release-PR والی جانچوں کو PR→release راستے میں منتقل کرتے رہیں۔
3. **`main` پر برانچ پروٹیکشن** (مالک کی ترتیب) — Scorecard بہتر کرتا ہے، DSOMM کا خلا بند کرتا ہے۔

**P1 — قابلِ قدر** 4. **osv/oasdiff → درست دائرۂ کار کے ساتھ بلاکنگ** — osv صرف CRITICAL+fixable (Trivy کی طرح دو مرحلہ)؛ oasdiff بریکنگ تبدیلیوں کو روکتا ہے۔ 5. **`require-tighten` → بلاکنگ** (سائیکل کے اختتام پر) — میٹرکس میں حاصل شدہ بہتریوں کو برقرار رکھتا ہے۔ 6. **`ci-summary` میں فی گیٹ ROI/ٹائمنگ جائزہ** — سست/کم قدر والے گیٹس تلاش کرکے ہٹائیں۔

**P2 — گھٹتے ہوئے فوائد** 7. **SLSA L3** — اگر آپ L2 سے آگے بڑھنا چاہتے ہیں تو hermetic/reproducible بلڈر (GitHub SLSA generator)۔ 8. **کمیٹ شدہ CodeQL کنفگ + ورژن شدہ semgrep** — زیادہ کنٹرول/اعادہ پذیری۔ 9. **فی PR DAST اسموک** — سب سے زیادہ خطرے والے endpoints پر schemathesis/promptfoo کا تیز ذیلی مجموعہ (صرف رات کو نہیں)۔ 10. **Flakiness ڈیش بورڈ + DORA میٹرکس** — یقینی بنائیں کہ گیٹس رفتار کو متاثر نہیں کر رہے۔

> ساتھ میں ٹھوس شواہد اور مجوزہ گیٹ بھی دیے گئے ہیں۔ ہر آئٹم حصہ 5 کے لیے امیدوار ہے۔

### سبق v3.8.27 (2026-06-17) — "fast-gates خلا" deterministic regressions کو ریلیز کے دن تک پہنچنے دیتا ہے

**کیا ہوا۔** v3.8.27 کی `/generate-release` کے دوران، ریلیز PR (`release/v3.8.27` → `main`)
مربوط سائیکل میں مکمل `ci.yml` میٹرکس کی **پہلی** تنفیذ تھی۔ نتیجہ: ایک ساتھ 12 ناکامیاں
— **3 deterministic ٹیسٹس** + ~9 flakes/env۔ ان میں سے کوئی بھی لائیو پروڈکٹ regression نہیں تھا، مگر
سب نظر انداز ہو گئے کیونکہ سائیکل PRs **Fast QG
(`quality.yml`)** کے ذریعے `release/**` میں داخل ہوتے ہیں، جو مکمل یونٹ سوٹ، `pr-test-policy` (ٹیسٹ ماسکنگ)،
مکمل انٹیگریشن سوٹ، یا schema parity جانچ کو نہیں چلاتا۔ 3 deterministic مسائل یہ تھے:

1. **UI تبدیلی کی وجہ سے فرسودہ ٹیسٹ** — `permissions modal switch buttons declare button type`:
   #4034 نے چوتھا switch شامل کیا (a11y `type="button"` برقرار رہا)؛ ٹیسٹ کی `=== 3` گنتی
   فرسودہ ہو گئی۔ Static analysis کو #4034 PR میں اسے پکڑ لینا چاہیے تھا۔
2. **پیکیجنگ تبدیلی کی وجہ سے فرسودہ ٹیسٹ** — `findMissingArtifactPaths ... root runtime files`:
   `dist/http-method-guard.cjs` ایک جائز required-path بن گیا؛ ٹیسٹ کی متوقع فہرست
   فرسودہ ہو گئی۔
3. **نقصان دہ modularization انحراف (سب سے سنگین)** — `settings schemas accept ... unprefixed
toggle`: **modularized** `updateSettingsSchema` (`schemas/settings.ts`، جسے #3988 نے بنایا) بنیادی
   ورژن (`settingsSchemas.ts`) سے منحرف ہو گیا: **45 fields بمقابلہ 85 — 40 حذف + 6 منحرف (qdrant\*)**۔ یہ
   **dead-code** تھا (runtime بنیادی ورژن استعمال کرتا ہے)، اس لیے لائیو اثر نہیں پڑا، مگر صرف ہاتھ سے لکھے گئے parity
   ٹیسٹ نے اسے پکڑا۔ #4030 نے #3988/#3993 سے اسی نوعیت کے 16 حذوف بحال کیے، مگر یہ رہ گیا۔

**مجوزہ گیٹس (Phase 9):**

- **G1 — واقعی fast-gates خلا بند کریں (P0 #2 کی توسیع)۔** `quality.yml` (PR→`release/**`) میں،
  typecheck + متاثرہ ٹیسٹس کے علاوہ، **`pr-test-policy` (ٹیسٹ ماسکنگ) + مکمل deterministic
  یونٹ سوٹ** چلائیں (یا کم از کم static/parity فائلیں، جو تیز اور non-flaky ہیں)۔
  اس طرح فرسودہ ٹیسٹس اور assert کا ہٹایا جانا اسی PR میں پکڑا جائے گا جو انہیں متعارف کراتا ہے — نہ کہ
  ریلیز کے دن۔ integration/e2e کو باہر رکھیں (سست/flaky)، مگر deterministic تہہ کو صرف
  PR→main میں ہرگز محدود نہیں رہنا چاہیے۔
- **G2 — Modularization parity گیٹ (نیا، آج اس کا احاطہ نہیں ہوتا)۔** ایک ایسی جانچ جو modularized barrel (`src/shared/validation/schemas/*`، `providerRegistry`
  modules، وغیرہ) سے re-export ہونے والی ہر symbol کے لیے اس کی **ساخت** (`z.object` keys، registry entries) کا بنیادی
  سورس سے موازنہ کرے اور **انحراف پر ناکام ہو** (حذف شدہ/اضافی field)۔ یہ #3988 سے ہونے والے 40-field حذف کو
  اسی PR میں پکڑ لیتا۔ یہ ہاتھ سے لکھے گئے parity ٹیسٹس کو عمومی بناتا ہے (جو صرف وہاں موجود ہیں جہاں کسی
  کو انہیں لکھنا یاد رہا)۔ کم خرچ: دونوں کو import کرکے `Object.keys(shape)` کا فرق نکالتا ہے۔
- **G3 — Deterministic flake triage (معاونت)۔** LiveWS-startup اور integration-combo/breaker
  ٹیسٹس CI میں server timeout/cascade (env) کی وجہ سے ناکام ہوتے ہیں، منطق کی وجہ سے نہیں۔ انہیں
  `known-flaky` (issue کے ساتھ قرنطینہ شدہ) کے طور پر نشان زد کریں تاکہ release-PR کی سرخ حالت میں **صرف حقیقی signals** ہوں، نہ کہ ایسا شور
  جو درمیان میں deterministic regressions کو چھپا دے۔

**اصول:** _گیٹ کو وہیں چلنا چاہیے جہاں merge ہوتا ہے_ (پہلے ہی "Cross-cutting principles" میں موجود ہے)۔
v3.8.27 کا واقعہ ظاہر کرتا ہے کہ یہ بات صرف lint/typecheck ہی نہیں بلکہ **deterministic ٹیسٹ تہہ** پر بھی لاگو ہوتی ہے —
ورنہ فرسودہ ٹیسٹس + نقصان دہ modularization کا قرض صرف PR→main میں، ایک ساتھ، بدترین
وقت پر سامنے آتا ہے۔
