## بغیر کنفیگریشن خودکار روٹنگ (`auto/` سابقہ)

> **نیا:** کومبو بنانے کی ضرورت نہیں۔ کسی بھی کلائنٹ میں براہ راست `auto/` سابقہ استعمال کریں۔

### فوری مثالیں

| ماڈل ID        | ویرینٹ  | رویہ                                                              |
| -------------- | ------- | ----------------------------------------------------------------- |
| `auto`         | ڈیفالٹ  | تمام منسلک فراہم کنندگان، LKGP حکمتِ عملی، متوازن اوزان           |
| `auto/coding`  | کوڈنگ   | معیار کو ترجیح دینے والے اوزان، کوڈ بنانے کے لیے موزوں            |
| `auto/fast`    | تیز     | کم تاخیر پر مبنی وزنی انتخاب                                      |
| `auto/cheap`   | سستا    | لاگت کے لحاظ سے بہتر بنائی گئی روٹنگ (سب سے کم لاگت پہلے)         |
| `auto/offline` | آف لائن | سب سے زیادہ کوٹا دستیابی والے فراہم کنندگان کو ترجیح دیتا ہے      |
| `auto/smart`   | اسمارٹ  | معیار کو ترجیح + بہتر ماڈل دریافت کے لیے زیادہ کھوج کی شرح (10%)  |
| `auto/lkgp`    | lkgp    | واضح LKGP (ڈیفالٹ `auto` جیسا)                                    |
| `auto/chaos`   | کیاس    | مضبوطی کی جانچ کے لیے خرابی داخل کرنے والے اوزان (کیاس انجینئرنگ) |

### زمرہ × ٹیئر کی ترکیب (`auto/<category>:<tier>`)

OpenRouter طرز کے لاحقے **کس قسم کا روٹ** (زمرہ) کو **اسے کس طرح بہتر بنانا ہے** (ٹیئر) سے الگ کرتے ہیں، تاکہ آپ انہیں آزادانہ طور پر یکجا کر سکیں (#4235 Phase B، `open-sse/services/autoCombo/suffixComposition.ts`):

- **زمرے** (صلاحیت کے لحاظ سے امیدوار پول کو فلٹر کریں): `coding` · `reasoning` · `vision` · `chat` · `multimodal`۔ `vision`/`multimodal` بصری صلاحیت رکھنے والے ماڈلز برقرار رکھتے ہیں؛ `reasoning` استدلال/تفکر والے ماڈلز برقرار رکھتا ہے۔
- **ٹیئرز** (اسکورنگ اوزان / پول فلٹر منتخب کریں): `fast` (فوری ترسیل) · `cheap` (عرف `floor`، لاگت بچانے والا) · `reliable` (سرکٹ بریکر کی صحت + تاخیر کا استحکام) · `free` / `pro` (`classifyTier` کے ذریعے ماڈل ٹیئر کے لحاظ سے پول فلٹر کریں — مفت ٹیئر بمقابلہ پریمیم)۔

| مثال                   | نتیجہ                                                               |
| ---------------------- | ------------------------------------------------------------------- |
| `auto/coding:fast`     | کوڈنگ پول، کم تاخیر والے اوزان                                      |
| `auto/coding:cheap`    | کوڈنگ پول، لاگت کے لحاظ سے بہتر بنایا گیا (عرف `auto/coding:floor`) |
| `auto/reasoning:pro`   | صرف استدلال/تفکر والے ماڈلز، پریمیم ٹیئر                            |
| `auto/vision`          | بصری صلاحیت والے ماڈلز (کوئی ٹیئر نہیں → متوازن اوزان)              |
| `auto/multimodal:free` | ملٹی موڈل صلاحیت والے ماڈلز، صرف مفت ٹیئر                           |

ہر درست `auto/<category>[:<tier>]` طلب پر حل ہو جاتا ہے؛ ایک منتخب ذیلی مجموعہ `/v1/models` اور ڈیش بورڈ میں ظاہر کیا جاتا ہے (`open-sse/services/autoCombo/builtinCatalog.ts` میں `AUTO_SUFFIX_VARIANTS`)۔ فلٹرنگ **fail-open** ہے — اگر کوئی پابندی کسی منسلک ماڈل سے مطابقت نہ رکھے تو مکمل پول استعمال کیا جاتا ہے، تاکہ روٹنگ کبھی متاثر نہ ہو۔ بنیادی اسکورر (`combo.ts`) میں کوئی تبدیلی نہیں؛ زمرہ/ٹیئر فلٹر `buildAutoCandidates` میں لاگو ہوتا ہے۔

> **لائیو ماڈل انٹیلیجنس:** جب `ARENA_ELO_SYNC_ENABLED` فلیگ فعال ہو تو خودکار روٹنگ کی موزونیت کے تعین میں لائیو **Arena ELO** درجہ بندیوں + **models.dev** کے ٹیئر ڈیٹا سے مدد لی جاتی ہے (بصورتِ دیگر جامد فٹنس میپ استعمال ہوتا ہے)۔

**استعمال کا طریقہ:**

```bash
# کوئی بھی IDE یا CLI ٹول جو OpenAI فارمیٹ کی معاونت کرتا ہو
بنیادی URL: http://localhost:20128/v1
API کلید:  <your-endpoint-key>

# اپنے کوڈ/کنفیگ میں ماڈل کو یوں سیٹ کریں:
model: "auto"                 # متوازن ڈیفالٹ
model: "auto/coding"          # کوڈنگ کے کاموں کے لیے بہترین
model: "auto/fast"            # تیز ترین دستیاب
model: "auto/cheap"           # فی ٹوکن سب سے سستا
```

**کیا ہوتا ہے:**

1. OmniRoute، `src/sse/handlers/chat.ts` میں `auto/` سابقے کا پتہ لگاتا ہے
2. ڈیٹابیس سے تمام **فعال فراہم کنندہ کنکشنز** دریافت کرتا ہے
3. انہیں فلٹر کر کے صرف درست اسناد (API کلید یا OAuth ٹوکن) رکھنے والے کنکشنز رکھتا ہے
4. ہر کنکشن کے لیے ماڈل متعین کرتا ہے (`connection.defaultModel` یا فراہم کنندہ کا پہلا ماڈل)
5. میموری میں ایک **ورچوئل کومبو** بناتا ہے (DB میں محفوظ نہیں ہوتا)
6. منتخب ویرینٹ کے وزنی پروفائل + LKGP حکمتِ عملی کے ذریعے روٹنگ کرتا ہے

**اہم خصوصیات:**

- ✅ **ہمیشہ فعال:** کسی ٹوگل، کومبو بنانے یا کنفیگریشن کی ضرورت نہیں
- ✅ **متحرک:** موجودہ منسلک فراہم کنندگان کی خودکار طور پر عکاسی کرتا ہے
- ✅ **سیشن وابستگی:** LKGP یقینی بناتا ہے کہ آخری کامیاب فراہم کنندہ کو ترجیح دی جائے
- ✅ **متعدد اکاؤنٹس سے آگاہ:** ہر فراہم کنندہ کنکشن ایک الگ امیدوار بن جاتا ہے
- ✅ **DB میں کوئی تحریر نہیں:** ورچوئل کومبو صرف درخواست کے لیے موجود رہتا ہے، مستقل ذخیرہ کاری کا کوئی اضافی بوجھ نہیں

### فی کلید امیدوار کنٹرول (#7819، سطح 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` کے بعد آنے والا لاحقہ، یا
بنیادی چینل کے لیے لفظی `auto`) ایک **صرف پڑھنے کا** اینڈپوائنٹ ہے جو کسی
`auto/*` چینل کے موجودہ امیدوار پول کو لائیو رسائی پذیری کی معلومات سمیت فہرست کرتا ہے، اور
موجودہ مضبوطی سے متعلق ریڈز کو دوبارہ استعمال کرتا ہے (کبھی بھی خام بریکر `state` نہیں):

- فراہم کنندہ سرکٹ بریکر — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- کنکشن کول ڈاؤن — حل شدہ
  `provider_connections` قطار پر `rateLimitedUntil` / `testStatus`
- ماڈل لاک آؤٹ — `isModelLocked(provider, connectionId, model)`

ہر امیدوار کے ساتھ اس API کلید کا `excluded` فلیگ بھی ہوتا ہے۔ اخراجات
فی API کلید محفوظ کیے جاتے ہیں (`auto_candidate_overrides` جدول، مائیگریشن `128`) — OmniRoute
سنگل ٹیننٹ ہے اور اس میں کوئی `users` جدول نہیں، اس لیے `apiKeyId` فی کالر حقیقی
شناخت کا قریب ترین متبادل ہے — اور انہیں
`open-sse/services/autoCombo/virtualFactory.ts` میں امیدوار پول کے مرکزی مرحلے پر خالص، یونٹ ٹیسٹ شدہ
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) کے ذریعے نافذ کیا جاتا ہے۔
فلٹر **fail-open** ہے: غیر مقرر apiKeyId/channel یا DB تلاش کی ناکامی، دونوں صورتوں میں
پول بغیر فلٹر کے رہتا ہے، اس لیے وہ آپریٹر جس کے لیے کوئی اوور رائیڈ کنفیگر نہیں کیا گیا، روٹنگ کو
اس فیچر سے پہلے کی حالت سے بائٹ بہ بائٹ یکساں دیکھتا ہے۔

**فالو اَپ ایشو تک مؤخر:** فی امیدوار weights + واضح ترتیب (Level 3
— موجودہ weighted/priority حکمتِ عملی کے راستوں میں شامل ہوتا ہے) اور ہر `auto/*` چینل کے لیے ایک مخصوص
`combo.ts` حکمتِ عملی کو pin کرنا (Level 4)۔ اس کھلے سوال کے لیے #7819 منصوبہ دیکھیں کہ آیا
single-tenant ماڈل کے پیشِ نظر overrides فی API کلید ہی رہنے چاہییں یا global بن جانے چاہییں۔

**پسِ پردہ:**

```txt
درخواست: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts سابقے کا پتہ لگاتا ہے
   ↓
createVirtualAutoCombo('coding') → فعال connections سے candidatePool
   ↓
handleComboChat (وہی انجن جو محفوظ شدہ combos کے لیے استعمال ہوتا ہے)
   ↓
Auto-scoring ہر درخواست کے لیے بہترین provider/model منتخب کرتی ہے
```

**نفاذ کی فائلیں:**

| فائل                                                      | مقصد                                            |
| --------------------------------------------------------- | ----------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | سابقہ parser (`parseAutoPrefix`)                |
| `open-sse/services/autoCombo/virtualFactory.ts`           | مجازی `AutoComboConfig` objects تخلیق کرتی ہے   |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | provider registry کو mock کرنے کے لیے ٹیسٹ hook |
| `src/sse/handlers/chat.ts`                                | انضمام: auto سابقے کا short-circuit             |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` سسٹم entry              |

## ایسے کومبو نام جو کسی حقیقی ماڈل آئی ڈی سے مماثل ہوں

ایسا کومبو جس کا `name` کسی سادہ ماڈل آئی ڈی کے عین مطابق ہو (مثلاً `gpt-5.5` نامی کومبو)، ایک **دانستہ اور معاونت یافتہ پیٹرن** ہے، بگ نہیں: یہ فی ماڈل آئی ڈی پرووائیڈر فال بیک کا طریقۂ کار ہے، جسے [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) میں دستاویزی شکل دی گئی ہے۔ چونکہ کومبو ریزولیوشن کو سادہ ماڈل آئی ڈی ریزولیوشن سے پہلے چیک کیا جاتا ہے (`src/sse/services/model.ts` میں `getComboForModel()`)، اس لیے سادہ آئی ڈی `gpt-5.5` کی درخواست براہِ راست کسی ایک پرووائیڈر کے پاس جانے کے بجائے کومبو کے اہداف (مثلاً `acme-responses/gpt-5.5`، `backup-responses/gpt-5.5`) کے ذریعے روٹ کی جاتی ہے — یہ [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) کے لیے بنائی گئی کومبو-قبل-از-ری رائٹ ترجیح کو دوبارہ استعمال کرتا ہے، اور `tests/unit/responses-combo-resolution-3227.test.ts` اور `tests/unit/combo-name-codex-responses-rewrite.test.ts` کے ذریعے اس کی ریگریشن ٹیسٹنگ کی جاتی ہے۔

کسی ایسے کومبو کو بنانا یا اس کا نام بدلنا جو کسی حقیقی ماڈل آئی ڈی کو شیڈو کرے، **کبھی مسترد نہیں کیا جاتا** — ایسا کرنے سے یہ دستاویزی ورک فلو ٹوٹ جائے گا۔ اس کے بجائے (#8530)، جب (نیا) نام کسی حقیقی ماڈل آئی ڈی سے متصادم ہو تو `POST /api/combos` اور `PUT /api/combos/[id]` ریسپانس کے ساتھ ایک غیر مسدود کرنے والی `warning` فیلڈ منسلک کرتے ہیں:

```json
{
  "warning": {
    "code": "COMBO_NAME_SHADOWS_MODEL",
    "modelId": "gpt-5.5",
    "providerId": "openai"
  }
}
```

بوٹ کے وقت، `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ایک سطر پر مشتمل `[STARTUP]` وارننگ بھی لاگ کرتا ہے، جس میں ایسے تمام موجودہ کومبوز درج ہوتے ہیں جو کسی ماڈل آئی ڈی کو شیڈو کرتے ہیں، تاکہ جن آپریٹرز کو دانستہ طور پر، بمطابق #6940، ایسا کرنے کے بجائے حادثاتی طور پر اس صورتِ حال کا سامنا ہو، انہیں ایک اشارہ مل سکے۔ ڈیٹیکشن ہیلپر `src/lib/combos/modelNameCollision.ts` میں موجود ہے۔

## کسی کلائنٹ سے کسٹم کومبو کو کال کرنا

محفوظ شدہ کومبوز (Settings → Combos) صرف اسی وقت استعمال ہوتے ہیں جب کلائنٹ `model` فیلڈ میں کومبو کا **بالکل درست نام** بھیجے — کومبو نام کی کوئی مبہم یا جزوی میچنگ نہیں ہوتی، اور نہ ہی `auto/` پریفکس شامل ہوتا ہے۔ ریزولیوشن کی ترتیب (`src/sse/services/model.ts` میں `getComboForModel()`):

1. کومبو نام سے بالکل درست میچ (`model: "my-combo"`)،
2. `combo/<name>` پریفکس (`model: "combo/my-combo"`)،
3. ماڈل→کومبو گلوب میپنگز (`/api/model-combo-mappings`)۔

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

دو عام غلط فہمیاں:

- **`auto` آپ کے کومبوز استعمال نہیں کرتا۔** `auto`/`auto/*` اپنا زیرو-کنفیگ امیدوار پول بناتا ہے اور محفوظ شدہ کومبوز سے صرف اس صورت میں رجوع کرتا ہے جب کسی کومبو کا نام حرف بہ حرف `auto` ہو (اس کی سفارش نہیں کی جاتی)۔ کسی کومبو کے ذریعے روٹ کرنے کے لیے اس کا بالکل درست نام بھیجیں — `auto` نہیں۔
- **`openrouter/auto` ایک حقیقی، بامعاوضہ OpenRouter پراڈکٹ** ("Auto Best Available") ہے، OmniRoute کا عرف نہیں۔ یہ OpenRouter رجسٹری (`open-sse/config/providers/registry/openrouter/index.ts`) کا واحد جامد ماڈل اندراج ہے اور اس کی بلنگ الگ سے ہوتی ہے۔ اسے `auto` پولز سے خارج کرنے کے لیے Settings → Routing → Hide paid models استعمال کریں۔

اس دستاویز میں بیان کردہ اصل الجھن کے لیے [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) اور [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) دیکھیں۔

| `X-OmniRoute-Effort`          | `auto` (دیگر اقدار محفوظ ہیں)                                                                                                                                                        | موافق سوچ کا بجٹ: جب درخواست میں کسی بھی شکل کی **کوئی** استدلالی فیلڈ (`reasoning_effort`، `reasoning`، `thinking`) موجود نہ ہو، تو گیٹ وے قطعی درخواست-ساخت کے اشاروں (آخری صارف پیغام کی لمبائی، آخری صارف پیغام تک سیاق کا حجم، سابقہ ٹول نتائج، ٹول-لوپ کی گہرائی) کی بنیاد پر `auto` کو `low`/`medium`/`high` میں تبدیل کرتا ہے۔ اشارے موجودہ ٹرن تک محدود ہوتے ہیں — آخری صارف پیغام کے بعد موجود ہر چیز نظر انداز کر دی جاتی ہے — لہٰذا ٹول لوپ میں ہر درخواست ایک ہی سطح پر تبدیل ہوتی ہے (فی ٹرن بے حالت پن، کوئی سیشن حالت نہیں، اور لوپ کے درمیان ایسی درجہ افزائی نہیں جو اپ اسٹریم پرامپٹ-کیش سابقوں کو خراب کرے)۔ کلائنٹ کی واضح استدلالی فیلڈ ہمیشہ ترجیح رکھتی ہے۔ یہ ان درخواستوں تک محدود ہے جن کی اپ اسٹریم ترسیل OpenAI Chat Completions ساخت (`targetFormat === FORMATS.OPENAI`) میں تبدیل ہوتی ہے — `reasoning_effort` ایک OpenAI ساخت والی فیلڈ ہے، اس لیے Claude یا Gemini کو ہدف بنانے والی درخواست پر یہ ہیڈر بے اثر ہوتا ہے (دیکھیے `open-sse/handlers/chatCore/adaptiveEffortWiring.ts`)۔ |

```bash
# تیز ترین پروفائل کو لازمی استعمال کریں، اس درخواست کی حد $0.05 مقرر کریں، اور حد سے زیادہ خرچ کرنے کے بجائے اسے سختی سے بلاک کریں
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-OmniRoute-Mode: fast" \
  -H "X-OmniRoute-Budget: 0.05" \
  -H "X-OmniRoute-Budget-Fallback: strict" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

ریزولیوشن ایک خالص فنکشن (`open-sse/services/autoCombo/requestControls.ts`) ہے؛
حل شدہ اقدار انجن کے موجودہ `config.modePack` / `config.budgetCap` /
`config.budgetFallback` اِن پٹس کو فراہم کی جاتی ہیں۔ کسی کومبو کی محفوظ شدہ `config.budgetFallback` ("strict" |
"cheapest") مستقل پالیسی متعین کرتی ہے؛ ہیڈر ایک واحد درخواست کے لیے اسے اوور رائیڈ کرتا ہے۔

## تمام روٹنگ حکمتِ عملیاں

OmniRoute کا کومبو انجن **19 روٹنگ حکمتِ عملیوں** کی معاونت کرتا ہے (جن کا اعلان `src/shared/constants/routingStrategies.ts` → `ROUTING_STRATEGY_VALUES` میں کیا گیا ہے)۔ Auto Combo انجن خود `auto` حکمتِ عملی کے تحت دستیاب ہے؛ دیگر محفوظ شدہ کومبوز کے لیے دستیاب ہیں۔

| حکمتِ عملی          | تفصیل                                                                                                                                                                                                                                     |
| :------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `priority`          | واضح ترجیح کے ساتھ پہلے ہدف کو فوقیت دینے والی مرتب فہرست                                                                                                                                                                                 |

| `fill-first`        | اگلے ہدف پر جانے سے پہلے ہر ہدف کا کوٹا مکمل استعمال کرنا                                                                                                                                                                                 |

### `weighted` کے معنوی اصول

`weighted` **ہر درخواست کے لیے تناسبی بے ترتیب انتخاب** ہے
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)، یہ برابری قائم کرنے والا طریقہ نہیں ہے:

- ہر درخواست `weight / totalWeight` احتمال کے ساتھ **ایک** مرحلہ منتخب کرتی ہے؛ باقی مراحل
  اس درخواست کے لیے متبادل سلسلے کے طور پر وزن کی نزولی ترتیب میں رکھے جاتے ہیں۔
- وہ مرحلہ جس کا وزن `0` ہو (یا موجود نہ ہو)، اس وقت تک **کبھی منتخب نہیں ہوتا** جب تک کسی دوسرے مرحلے کا
  وزن > 0 ہو — وہ صرف منتخب شدہ مرحلے کی ناکامی کے بعد بطور متبادل کام کر سکتا ہے۔ انتخاب صرف تب یکساں ہوتا ہے جب **تمام**
  اوزان 0 ہوں۔
- وہ مراحل جن کے تمام اہداف غیر دستیاب ہوں — فراہم کنندہ کا سرکٹ بریکر `OPEN`، کنکشن
  کول ڈاؤن، یا ماڈل لاک آؤٹ — انتخاب ہونے سے پہلے ہی قرعہ اندازی سے نکال دیے جاتے ہیں
  (`open-sse/services/combo/targetResolution.ts`)، لہٰذا کوئی ایک صحت مند مرحلہ عارضی طور پر
  ہر درخواست جیت سکتا ہے۔
- `stickyWeightedLimit` (کومبو کنفیگریشن، طے شدہ قدر `1` = بند) منتخب شدہ مرحلے کو دوبارہ انتخاب کرنے سے پہلے اتنی
  مسلسل کامیابیوں تک برقرار رکھتا ہے۔

سخت گردشی ترتیب کے لیے `round-robin` استعمال کریں؛ `weighted` پر برابر اوزان شماریاتی توازن دیتے ہیں — سخت
توازن نہیں۔

## فیوژن حکمتِ عملی

`fusion` وہ واحد حکمتِ عملی ہے جو کسی ایک ہدف کو منتخب **نہیں** کرتی۔ یہ پرامپٹ کو
**ہر پینل ماڈل کو متوازی طور پر** بھیجتی ہے، پھر ایک قابلِ تشکیل **جج ماڈل** پینل کے
تمام جوابات سے ایک حتمی جواب مرتب کرتا ہے۔ اسے اپ اسٹریم `decolua/9router`
(OpenRouter کے Fusion ڈیزائن) سے پورٹ کیا گیا ہے؛ نفاذ `open-sse/services/fusion.ts` میں ہے۔

یہ کیسے کام کرتی ہے:

0. **ٹول والی درخواست کا بائی پاس** — ایسی درخواست جس میں ایک غیر خالی `tools` ارے ہو اور
   `tool_choice` کو واضح طور پر `"none"` مقرر نہ کیا گیا ہو، پینل کو مکمل طور پر چھوڑ دیتی ہے:
   یہ `tools`/`tool_choice` کو بغیر تبدیلی کے براہِ راست ایک ماڈل (تشکیل کردہ جج، یا `panel[0]`)
   کی طرف بھیجی جاتی ہے۔ پینل اراکین کو ٹولز تک رسائی حاصل نہیں ہوتی اور جج کی
   ترکیبی ہدایت ٹول کال پیدا کرنے کی حوصلہ شکنی کرتی ہے، اس لیے ایجنٹ پر مبنی/ٹول کال کرنے والے کلائنٹس
   کو ترکیب شدہ نثر کے بجائے حقیقی ٹول کال کا فیصلہ ملتا ہے (#6771)۔
1. **فین آؤٹ** (صرف ٹول کے بغیر درخواستوں کے لیے) — پرامپٹ کو ایک ہی وقت میں ہر پینل
   ماڈل کو بھیجا جاتا ہے، ٹولز ہٹا کر نان اسٹریمنگ کو لازمی بنایا جاتا ہے (جج کو ترکیب کے لیے
   مکمل نثر درکار ہوتی ہے)۔
2. **کورم-گریس کلیکشن** — جیسے ہی `minPanel` جوابات موصول ہوتے ہیں، پیچھے رہ جانے والوں کے لیے
   ایک مختصر گریس ٹائمر شروع ہو جاتا ہے، پھر جو کچھ جمع ہو چکا ہو اس کے ساتھ فیوژن آگے بڑھتا ہے۔
   یہ وال ٹائم پر سب سے سست ماڈل کے جرمانے کو محدود کرتا ہے، جبکہ ایک سخت ٹائم آؤٹ حتمی حد مقرر کرتا ہے۔
3. **جج کی ترکیب** — پینل کے جوابات کو گمنام بنایا جاتا ہے (`Source 1`، `Source 2`، … — تاکہ
   جج ماڈل کے برانڈ کے بجائے مواد کی اہمیت پر غور کرے) اور جج کو دے دیا جاتا ہے، جو
   اتفاقِ رائے / تضادات / جزوی احاطے / منفرد بصیرتوں / نظر انداز پہلوؤں کا تجزیہ کرتا ہے، پھر
   **ایک** مستند جواب لکھتا ہے۔ جج کال کلائنٹ کا اصل
   `stream` فلیگ + ٹولز برقرار رکھتی ہے، اس لیے اسٹریمنگ اور ڈاؤن اسٹریم ٹول کا استعمال بدستور کام کرتے ہیں۔
4. **بتدریج تنزل** — پینل کے 0 جوابات → `503`؛ صرف 1 جواب باقی بچے → وہ جواب
   براہِ راست واپس کر دیا جاتا ہے (ترکیب کرنے کے لیے کچھ نہیں)؛ ایک ماڈل والا پینل براہِ راست جواب دیتا ہے۔

پینل کا کوئی رکن `combo-ref` مرحلہ بھی ہو سکتا ہے (`{kind: "combo-ref", comboName: "..."}`) جو
کسی دوسرے کومبو کا حوالہ دیتا ہے — اسے **ایک بلیک باکس پینل آواز** کے طور پر حل کیا جاتا ہے (حوالہ دیے گئے
کومبو میں مکمل تکراری ڈسپیچ، نہ کہ اس کومبو کے اپنے اہداف کا فین آؤٹ)، اور اس میں وہی گہرائی/چکر کا تحفظ
استعمال ہوتا ہے جو پہلے سے ہر دوسری combo-ref استعمال کرنے والی حکمتِ عملی میں موجود ہے (#6764)۔

### تشکیل

کومبو کے `config` بلاب میں تشکیل کیا جاتا ہے (کسی اسکیما مائیگریشن کی ضرورت نہیں — یہ موجودہ
`combos` ٹیبل کو دوبارہ استعمال کرتا ہے):

| فیلڈ                                     | قسم      | ڈیفالٹ         | مقصد                                                                         |
| :--------------------------------------- | :------- | :------------- | :--------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | پہلا پینل ماڈل | حتمی جواب کی ترکیب کرنے والا ماڈل                                            |
| `config.fusionTuning.minPanel`           | `number` | `2`            | گریس ٹائمر شروع ہونے سے پہلے درکار کامیاب جوابات (`[2, panelSize]` تک محدود) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`         | کورم پورا ہونے کے بعد پیچھے رہ جانے والوں کا کتنی دیر انتظار کیا جائے        |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`        | حتمی مطلق حد، تاکہ ایک معلق ماڈل درخواست کو روک نہ سکے                       |

ڈیفالٹس `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) میں موجود ہیں۔

### مثال

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

پھر اسے کسی بھی کومبو کی طرح کال کریں: `{"model":"fusion-panel","messages":[...]}`۔

## ورچوئل آٹو-کومبو فیکٹری

Auto Combo انجن کو پہلے سے متعین combos کی ضرورت نہیں ہوتی۔ اس کے بجائے، `open-sse/services/autoCombo/virtualFactory.ts` فوری طور پر امیدوار بناتا ہے:

1. `getProviderConnections({ isActive: true })` حاصل کرتا ہے (تمام فعال connections)
2. ان connections تک محدود کرتا ہے جن کے credentials درست ہوں (API key یا `hasUsableOAuthToken()` کے ذریعے غیر زائد المیعاد OAuth token)
3. ماڈل کی دستیابی + قیمتوں کے لیے `getProviderRegistry()` سے تقابل کرتا ہے
4. ہر tuple `(provider, model, connection)` کے لیے ایک `VirtualAutoComboCandidate` بناتا ہے
5. dispatch ہدف کے طور پر `connection.defaultModel` (یا registry کا پہلا ماڈل) منتخب کرتا ہے
6. 16 عوامل والے `scorePool()` اور variant کے weight pack کے ذریعے ہر امیدوار کو اسکور کرتا ہے
7. `handleComboChat()` کے لیے نتیجے میں بننے والا in-memory `AutoComboConfig` واپس کرتا ہے — اسے کبھی DB میں محفوظ نہیں کیا جاتا

اس کا مطلب ہے کہ **`auto/*` فعال رکھنے والا نیا provider شامل کرنے سے امیدواروں کا pool خودکار طور پر وسیع ہو جاتا ہے** — combo میں دستی ترمیم کی ضرورت نہیں ہوتی۔ ورچوئل combo ہر درخواست پر دوبارہ بنایا جاتا ہے، اس لیے نئے شامل کیے گئے یا دوبارہ صحت مند ہونے والے connections فوراً شامل کر لیے جاتے ہیں۔

## خودکار بحالی

- **عارضی اخراج**: اسکور < 0.2 → 5 منٹ کے لیے خارج (تدریجی backoff، زیادہ سے زیادہ 30 منٹ)
- **Circuit breaker سے آگاہی**: OPEN → خودکار طور پر خارج؛ HALF_OPEN → آزمائشی درخواستیں
- **حادثاتی صورتِ حال کا موڈ**: >50% OPEN → exploration غیر فعال، استحکام زیادہ سے زیادہ
- **Cooldown بحالی**: اخراج کے بعد پہلی درخواست کم timeout کے ساتھ ایک "probe" ہوتی ہے

## Bandit Exploration

5% درخواستیں (قابلِ ترتیب) exploration کے لیے بے ترتیب providers کو بھیجی جاتی ہیں۔ حادثاتی صورتِ حال کے موڈ میں یہ غیر فعال ہوتا ہے۔

## API

کوئی مخصوص **`POST /api/combos/auto` endpoint موجود نہیں ہے** — Auto-Combo دو طریقوں سے استعمال کیا جاتا ہے:

1. **بغیر ترتیب (تجویز کردہ):** کوئی بھی chat completion درخواست `model: "auto"` یا `model: "auto/<variant>"` کے ساتھ بھیجیں۔ ورچوئل فیکٹری ہر درخواست کے لیے combo بناتی ہے — نہ persistence درکار ہے، نہ API calls۔

2. **`strategy: "auto"` کے ساتھ محفوظ شدہ combo:** `POST /api/combos` کے ذریعے معمول کا combo بنائیں اور `strategy: "auto"` کے ساتھ `config.auto.weights` / `config.auto.candidatePool` مقرر کریں۔ وہی scoring engine استعمال ہوتا ہے؛ combo کو `combos` میں محفوظ کیا جاتا ہے اور ID کے ذریعے دوبارہ استعمال کیا جا سکتا ہے۔

دریافت کے لیے، `GET /api/combos/auto` ہر variant کو اس کے resolved candidate pool کے ساتھ، نیز `context_length` / `max_output_tokens` کے ساتھ فہرست کرتا ہے — یہ candidate pool کی windows میں سب سے بڑی قدر، یعنی MAX، ہوتی ہے۔ Clients (مثلاً opencode plugin) کو `0` کے بجائے انہی اقدار کی تشہیر کرنی چاہیے: صفر context، opencode کی auto-compaction کو مکمل طور پر غیر فعال کر دیتا ہے، جس سے sessions اس وقت تک بڑھتے رہتے ہیں جب تک gateway کی history purge سیاق و سباق کو تباہ نہ کر دے۔ MAX کی تشہیر محفوظ ہے کیونکہ auto-combo context pre-filter حد سے بڑی درخواستوں کو بڑی window والے امیدواروں کی طرف بھیجتا ہے۔

```bash
# بغیر ترتیب استعمال (combo بنائے بغیر)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# معمول کے combos endpoint کے ذریعے محفوظ شدہ auto combo
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router حکمتِ عملیاں

محفوظ شدہ `strategy: "auto"` combos، `config.routerStrategy` (یا legacy
`config.auto.routerStrategy`) کو درج ذیل میں سے کسی ایک پر مقرر کر سکتے ہیں:

- `rules` — پہلے سے طے شدہ weighted scoring
- `score` — سب سے زیادہ configured weighted score منتخب کرتا ہے۔ بالکل برابر اسکور کی صورت میں configured
  candidate order برقرار رہتا ہے؛ موجودہ `explorationRate` مکمل ranked pool سے نمونے منتخب کرتا ہے۔
- `cost` / `eco` — سب سے سستا صحت مند provider
- `latency` / `fast` — reliability penalty کے ساتھ سب سے کم p95 latency
- `sla-aware` / `sla` — ان امیدواروں کو ترجیح دیتا ہے جو p95 latency، error-rate، اور اختیاری
  cost SLOs پورے کرتے ہوں
- `lkgp` — آخری معلوم درست provider پہلے

### Router حکمتِ عملیوں کی تفصیل

Auto-combo انجن 6 pluggable **RouterStrategy** implementations فراہم کرتا ہے جنہیں
آپ `config.routerStrategy` (یا legacy `config.auto.routerStrategy`) کے ذریعے تبدیل کر سکتے ہیں۔
ہر حکمتِ عملی ایک `RoutingContext`
(task type، tool/vision hints، token estimate، اختیاری SLA policy، اختیاری
last-known-good provider) کی بنیاد پر candidate pool سے ایک provider منتخب کرتی ہے۔

#### 1. `rules` (پہلے سے طے شدہ) — 16 عوامل پر مبنی weighted scoring

موجودہ scoring engine کو wrap کرتا ہے۔ `OPEN` circuit-breaker
امیدواروں کو خارج کرتا ہے، پھر موجودہ task type اور `getTaskFitness()` کے ساتھ `scorePool()` چلاتا ہے،
اور سب سے زیادہ اسکور والے provider کو منتخب کرتا ہے۔

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: پہلے سے طے شدہ انتخاب۔ جب آپ تمام signals کے درمیان متوازن سمجھوتا چاہتے ہوں تو استعمال کریں۔

**عرف**: `rules` (کوئی عرف نہیں)

---

#### 2. `cost` / `eco` — سب سے سستا صحت مند provider

Candidate pool کو `costPer1MTokens` کے لحاظ سے (صعودی ترتیب میں) مرتب کرتا ہے اور سب سے سستا امیدوار منتخب کرتا ہے۔
پہلے `OPEN` امیدواروں کو خارج کرتا ہے۔

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: لاگت کے لحاظ سے حساس workloads، batch processing، یا background jobs۔

**عرف**: `cost`، `eco`

---

#### 3. `latency` / `fast` — reliability penalty کے ساتھ سب سے کم p95 latency

`p95LatencyMs + (errorRate * 1000)` کے لحاظ سے ترتیب دیتا ہے۔ خرابی کی شرح کا جرمانہ یقینی بناتا ہے کہ
ناقابلِ اعتماد فراہم کنندگان کو کم درجہ دیا جائے، چاہے ان کی برائے نام تاخیر کم ہو۔

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: تاخیر کے لیے حساس ورک لوڈز، جیسے ریئل ٹائم چیٹ، خودکار تکمیل، یا
انٹرایکٹو کوڈنگ معاونین۔

**عرف**: `latency`، `fast`

---

#### 4. `sla-aware` / `sla` — تاخیر/خرابی/لاگت کی SLO تعمیل

ہر امیدوار کو اس بنیاد پر اسکور دیتا ہے کہ وہ ترتیب دی گئی SLO پالیسی کو کس حد تک پورا کرتا ہے:

| عامل             | وزن | فارمولا                                           |
| ---------------- | --- | ------------------------------------------------- |
| تاخیر کا اسکور   | 35% | `threshold / max(value, ε)`                       |
| خرابی کا اسکور   | 35% | `threshold / max(value, ε)`                       |
| صحت کا اسکور     | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| لاگت کا اسکور    | 10% | `threshold / max(value, ε)` یا معکوس نارملائزڈ    |
| استحکام کا اسکور | 5%  | تاخیر کے معیاری انحراف کا معکوس نارملائزڈ اسکور   |

جب `hardConstraints: true` ہو، تو امیدواروں کو بنیادی طور پر **خلاف ورزی کے اسکور**
(وہ کسی SLO سے کتنا تجاوز کرتے ہیں) اور پھر مرکب اسکور کے لحاظ سے ترتیب دیا جاتا ہے۔ بصورتِ دیگر صرف
مرکب اسکور استعمال ہوتا ہے۔

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... ہر امیدوار کو پالیسی کے مقابل اسکور دیتا ہے: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA فیلڈز** (combo کنفیگریشن پر مقرر کریں):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**کب استعمال کریں**: سخت تاخیر، خرابی کی شرح، یا لاگت کے بجٹ والے پروڈکشن ورک لوڈز۔

**عرف**: `sla-aware`، `sla`

---

#### 5. `lkgp` — آخری معلوم اچھا فراہم کنندہ پہلے

پہلے **آخری معلوم اچھے فراہم کنندہ** (اگر مقرر ہو) کو آزماتا ہے، پھر
`rules` حکمتِ عملی استعمال کرتا ہے۔ سیشن کی وابستگی کے لیے مفید — ایک ہی فراہم کنندہ
گفتگو میں بعد کی درخواستوں کو سنبھالتا ہے۔

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // متبادل کے طور پر rules حکمتِ عملی استعمال کریں
    return getStrategy("rules").select(pool, context);
  }
}
```

**کب استعمال کریں**: کثیر باری گفتگوئیں جہاں آپ چاہتے ہیں کہ ایک ہی فراہم کنندہ
بعد کی درخواستوں کو سنبھالے (مثلاً کیشنگ، سیاق و سباق کے تسلسل، یا قیمتوں میں یکسانیت کے لیے)۔

**عرف**: `lkgp` (کوئی عرف نہیں)

### حسبِ ضرورت راؤٹر حکمتِ عملیاں

آپ عوامی API کے ذریعے اپنی `RouterStrategy` امپلیمینٹیشن رجسٹر کر سکتے ہیں:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // آپ کی راؤٹنگ منطق یہاں
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

پھر اسے استعمال کریں:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

6 ٹاسک اقسام (`coding`، `review`، `planning`، `analysis`، `debugging`، `documentation`) میں 30+ ماڈلز کو اسکور کیا گیا ہے۔ وائلڈ کارڈ پیٹرنز کی معاونت موجود ہے (مثلاً، `*-coder` → کوڈنگ کا بلند اسکور)۔

## خودکار ویریئنٹس کا خلاصہ

بنیادی `auto` (ڈیفالٹ) اور `autoPrefix.ts` میں اعلان کردہ 6 `AutoVariant` اقدار سمیت، **7 قابلِ استعمال ماڈل IDs** ہیں:

`auto`، `auto/coding`، `auto/fast`، `auto/cheap`، `auto/offline`، `auto/smart`، `auto/lkgp`

(`AutoVariant` بذاتِ خود 6 اقدار شمار کرتا ہے؛ ساتواں آپشن "کوئی ویریئنٹ نہیں" — بنیادی `auto` — ہے، جسے `parseAutoPrefix()`، `variant: undefined` کے طور پر ہینڈل کرتا ہے۔)

## ٹیئرز Auto-Combo میں کیسے شامل ہوتے ہیں

16-فیکٹر اسکورنگ فنکشن (`open-sse/services/autoCombo/scoring.ts`) ٹیئر کی
رکنیت کو دو سگنلز کے طور پر دیکھتا ہے: `tierPriority` (0.0476) اور `tierAffinity` (0.0476)۔ مکمل
`DEFAULT_WEIGHTS` سیٹ کے لیے اوپر دی گئی مستند [اسکورنگ فیکٹر جدول](#how-it-works-persisted-auto-combos) دیکھیں — ہر پیک کے اوور رائیڈز (ship-fast/cost-saver/quality-first/
offline-friendly) "ہر پیک کے لیے ویٹ پروفائلز" کی جدول میں درج ہیں۔

صرف ٹیئر، لازماً **Tier 1** کو پہلے نہیں رکھتا — اگر Tier 1 کی تاخیر خراب ہو یا
لاگت بمقابلہ معیار ناموزوں ہو، تو Tier 2 منتخب ہوتا ہے۔ ٹیئر کی ترتیب لازمی نافذ کرنے کے لیے، کومبو
حکمتِ عملی `priority` استعمال کریں اور پرووائیڈرز کو ٹیئر کے لحاظ سے ترتیب دیں۔

Tier 1 (سبسکرپشن) کو نمایاں ترجیح دینے کے لیے، `tierPriority` کا ویٹ بڑھائیں:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ٹیئر کی تعریفات اور پرووائیڈر کی درجہ بندی کے لیے `docs/marketing/TIERS.md` دیکھیں۔

### قطعی روٹنگ-فیصلہ میٹرکس (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts`، فرضی اپ اسٹریم کے ساتھ حقیقی کومبو پائپ لائن کے ذریعے تمام 19
عوامی حکمتِ عملیوں کے روٹنگ **فیصلے** کو ابتدا سے انتہا تک ثابت کرتا ہے۔
کوریج میں شامل ہیں:

- تمام 19 `ROUTING_STRATEGY_VALUES` حکمتِ عملیاں (ترتیب یافتہ، وزن دار، لاگت، سیاق، فیوژن، …)۔
- `quota-share` (اندرونی) ابتدا سے انتہا تک: حقیقی `selectQuotaShareTarget` جوڑ کے ذریعے DRR کی منصفانہ تقسیم + سچوریشن پر ترجیح میں کمی (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)۔
- اہداف کی ہر تعداد میں `context-relay` یونیورسل-ہینڈ آف کوریج۔

یہ سویٹ CI (`test:integration` جاب) میں `--test-concurrency=1` اور
`--test-force-exit` کے ساتھ چلتا ہے، لہٰذا یہ قطعی ہے اور اسے لائیو اسناد درکار نہیں ہوتیں۔

| `npm run test:combo:live:vps`          | لائیو OmniRoute سرور کے خلاف HTTP کالز (`COMBO_LIVE_BASE_URL` سیٹ کریں)                    |
| `npm run test:combo:live:vps:failover` | یہی عمل، دانستہ فیل اوور منظرناموں کے ساتھ                                                 |

یہ اسموک ٹیسٹس حقیقی وائر پاتھ (کومبو → پرووائیڈر → تکمیل) کو آزماتے ہیں۔ انہیں
جان بوجھ کر CI سے خارج رکھا گیا ہے کیونکہ انہیں لائیو اسناد اور VPS رسائی درکار ہوتی ہے۔
