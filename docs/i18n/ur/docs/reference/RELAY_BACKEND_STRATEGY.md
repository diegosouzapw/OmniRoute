## خلاصہ

OmniRoute اب `/api/v1/relay/chat/completions` کے لیے تین ریلے موڈز کو سپورٹ کرتا ہے:

- `ts`: TypeScript ریلے کو اسی پراسیس کے اندر استعمال کریں۔
- `bifrost`: Bifrost گیٹ وے کا استعمال لازمی بنائیں۔
- `auto`: دستیاب ہونے پر Bifrost کو ترجیح دیں، اور ناکامی کی صورت میں TypeScript پر واپس چلے جائیں۔

جب آپ درخواستوں کی بلند شرح پر کام کر رہے ہوں (روزانہ ٹوکنز کی بڑی تعداد، تقریباً مسلسل تھروپٹ)، تو بہترین حکمتِ عملی یہ ہے کہ fallback راستے کو واضح اور تیز رکھا جائے تاکہ فعال راستہ کبھی کسی ناکارہ sidecar کی وجہ سے بلاک نہ ہو۔

## موڈ کا طرزِ عمل

- `ts`
  - آپریشنل پیچیدگی سب سے کم۔
  - تمام روٹنگ اور توثیق Node میں انجام پاتی ہے۔
  - دستیابی کے لیے sidecar پر کوئی انحصار نہیں۔
- `bifrost`
  - تمام درخواستوں کو لازماً sidecar گیٹ وے سے گزاریں۔
  - کوئی خودکار fallback نہیں۔
  - صرف اس وقت مفید ہے جب sidecar کی صحت اور تاخیر کی ضمانت ہو۔
- `auto`
  - جب sidecar قابلِ رسائی اور فعال ہو تو اسے استعمال کیا جاتا ہے۔
  - ناکام کوششیں fallback ہیڈرز کو متحرک کرتی ہیں اور ٹریفک کو TS کی طرف واپس بھیجتی ہیں، تاکہ درخواست کی کامیابی ایک مقررہ حد میں رہے۔
  - جب اپ ٹائم، صرف sidecar کے ذریعے سخت روٹنگ سے زیادہ اہم ہو، تو پروڈکشن کے لیے یہ موڈ سب سے محفوظ انتخاب ہے۔

## آج 9router بمقابلہ CLIPROXYAPI

9router اور CLIPROXYAPI دونوں ایسے انٹیگریشنز ہیں جو تاریخی طور پر upstream فراہم کنندگان کے لیے مطابقتی راستے فراہم کرتے رہے ہیں۔

- 9router، upstream آرکیسٹریشن اور مطابقتی طرزِ عمل کے لیے ایک embedded راستہ ہے۔
- CLIPROXYAPI، CLI / SDK طرز کی ٹریفک کے لیے ایک proxy API برج ہے۔
- جب آپ کو ایک مخصوص sidecar جیسے اضافی مرحلے اور کم تاخیر والی مقامی dispatch درکار ہو، تو Bifrost کو externalized راستے کے طور پر مستحکم کیا جا رہا ہے۔

اگر آپ اس وقت 9router/CLIPROXYAPI کا موازنہ کر رہے ہیں:

- handoff سے پہلے API روٹ میں درخواست کی signing، allowlist کی جانچ، اور DB پالیسی gates برقرار رکھیں۔
- اگر کسی workflow کو sidecar کے سخت طرزِ عمل اور فی درخواست کم تغیر کی ضرورت ہو، تو `OMNIROUTE_RELAY_BACKEND=bifrost` استعمال کریں۔
- اگر آپ کو حادثاتی حالات میں بتدریج تنزلی کے ساتھ sidecar کی لچک درکار ہو، تو `OMNIROUTE_RELAY_BACKEND=auto` استعمال کریں۔

## بیک اینڈ باؤنڈری کا معاہدہ

مستحکم پروڈکٹ باؤنڈری OmniRoute relay API ہے، dashboard implementation نہیں۔ Next.js dashboard مقامی سروسز کو install، configure، اور supervise کر سکتا ہے، لیکن درخواست کی routing کو relay API کے ذریعے داخل ہونا چاہیے اور اس باؤنڈری کے پیچھے handoff ہونا چاہیے۔

طویل مدتی backend انتخاب:

- TypeScript relay کو in-process پالیسی اور fallback راستے کے طور پر برقرار رکھیں۔ کسی بھی backend handoff سے پہلے auth، allowlists، درخواست کی normalization، accounting، اور حفاظتی جانچیں یہیں رہیں گی۔
- جب deployment کو routing میں کم تغیر، مرکزی provider rotation، یا متعدد OmniRoute replicas میں scale-out کی ضرورت ہو، تو Bifrost کو ترجیحی high-throughput Tier-1 sidecar کے طور پر استعمال کریں۔
- 9router اور CLIPROXYAPI کو embedded compatibility services کے طور پر برقرار رکھیں۔ یہ supervised مقامی processes کے طور پر چلتے ہیں اور اس وقت مفید ہوتے ہیں جب ان کا provider/CLI طرزِ عمل مطلوبہ adapter ہو، لیکن انہیں ڈیفالٹ Tier-1 routing engine نہیں بننا چاہیے۔
- dashboard کو hot path میں صوابدیدی service URLs منتقل نہ کرنے دیں۔ UI سے فراہم کردہ URLs configuration inputs ہیں؛ routing code کو server-side settings اور supervisor state سے رجسٹرڈ اور health-checked backends resolve کرنے چاہییں۔
- فی الحال supervised services کے لیے loopback HTTP کو ترجیح دیں، کیونکہ managed processes پہلے ہی HTTP-compatible APIs فراہم کرتے ہیں، route guard باؤنڈری کا audit کر سکتا ہے، اور failure/fallback طرزِ عمل request logs میں نظر آتا ہے۔ مستقبل میں SDK یا socket transport صرف اسی وقت شامل کرنا مفید ہے جب وہ isolation یا fallback semantics کو کمزور کیے بغیر p99 routing latency میں قابلِ پیمائش کمی کرے۔

لہٰذا بہت زیادہ throughput والی deployment کے لیے ڈیفالٹ جواب Bifrost فعال ہونے کے ساتھ `auto` ہے: کامیابی کی شرح کے لیے TypeScript fallback برقرار رکھتے ہوئے hot path پر Go sidecar استعمال کریں۔ `bifrost` صرف اس وقت استعمال کریں جب صرف sidecar والا سخت طرزِ عمل، بتدریج تنزلی سے زیادہ اہم ہو۔

## زیادہ تھروپٹ کے لیے رہنمائی

مسلسل بلند RPM/RPS اور سخت کامیابی SLO کے لیے:

1. موزوں cooldown اور failure telemetry کے ساتھ `auto` استعمال کریں۔
2. upstream validation اور API-key checks کو TypeScript route boundary پر رکھیں۔
3. واضح headers/counters فعال کریں تاکہ آپ کا alerting نظام fallback کی تعداد اور وجوہات دیکھ سکے۔
4. sidecar timeouts کو ہمیشہ انتظار کرنے کے بجائے تیزی سے ناکام ہونے کے لیے ٹیون کریں۔
5. service auto-restart اور health telemetry loop کو صحت مند رکھیں تاکہ fallback واقعی ایک غیر معمولی واقعہ رہے۔

## تجویز کردہ بنیادی ترتیب

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- API keys، allowlist، sanitizer، اور rate-limit checks کو route handlers میں فعال رکھیں (یہ downstream forwarding سے پہلے ہمیشہ چلتے ہیں)۔
- اپنے reverse proxy اور request logs سے fallback metrics برآمد کریں تاکہ sidecar کی بندش ایک منٹ کے اندر نظر آ جائے۔
