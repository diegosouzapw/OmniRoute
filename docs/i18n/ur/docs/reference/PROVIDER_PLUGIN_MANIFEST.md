`open-sse/config/providerPluginManifest.ts` JSON-محفوظ provider
plugin معاہدے کی تعریف کرتا ہے۔ `open-sse/config/providerPluginManifestRegistry.ts` اس
معاہدے کو موجودہ provider registry کے ساتھ منسلک کرتا ہے، تاکہ Bifrost،
CLIProxyAPI، یا مستقبل کا کوئی Go/Rust router جیسا sidecar اسے استعمال کر سکے۔ TypeScript registry بدستور
حتمی ماخذ ہے، لیکن sidecars executor code،
OAuth defaults، headers، یا process environment state کو import کیے بغیر manifest استعمال کر سکتے ہیں۔

یہی manifest HTTP پر بھی
`GET /api/v1/provider-plugin-manifest` کے ذریعے ان sidecars کے لیے دستیاب ہے جو الگ process میں چلتے ہیں۔

OmniRoute اس URL کو Bifrost اور CLIProxyAPI کے سامنے
`X-OmniRoute-Provider-Manifest-Url` request header کے ذریعے ظاہر کرتا ہے۔ جب sidecar کو مقامی request origin کے بجائے کسی public یا container
network URL کی ضرورت ہو تو
`OMNIROUTE_PROVIDER_MANIFEST_URL` سیٹ کریں۔

## Manifest کو ریفریش کرنا

HTTP endpoint `Cache-Control: public, max-age=60` اور ایک مضبوط
`ETag` واپس کرتا ہے۔ sidecar کو آخری توثیق شدہ manifest محفوظ رکھنا چاہیے اور ریفریش کرتے وقت اس کا ETag
`If-None-Match` میں بھیجنا چاہیے۔ `304 Not Modified` response میں کوئی body نہیں ہوتی؛
sidecar اپنا cached manifest برقرار رکھتا ہے۔ اگر کوئی توثیق شدہ cached manifest موجود نہ ہو،
تو sidecar کو `304` قبول کرنے کے بجائے غیر مشروط request بھیجنی چاہیے۔

## مقصد

provider metadata کو plugin contract کی سمت منتقل کرنا، تاکہ hot request path
بالآخر کم latency والے sidecar کے زیرِ انتظام آ سکے، جبکہ OmniRoute
TypeScript route کو policy gate اور fallback کے طور پر برقرار رکھے۔ manifest اضافی نوعیت کا ہے:
یہ بذاتِ خود request routing کو تبدیل نہیں کرتا۔

## معاہدہ

manifest میں یہ شامل ہیں:

- provider id اور alias
- upstream format اور executor name
- auth type، auth header، اور اختیاری auth prefix
- static endpoint metadata
- sidecar اہلیت اور ان صورتوں کی واضح وجوہات جب کسی provider کو TS پر رہنا چاہیے
- JSON-محفوظ model metadata، جیسے context length، vision/reasoning flags، اور
  غیر معاون params
- capability tags، جن میں `apikey`، `oauth`، `custom-executor`،
  `passthrough-models`، `responses`، `sidecar-candidate`، `usage-fetch`، اور `usage-supported` شامل ہیں

manifest دانستہ طور پر یہ چیزیں شامل نہیں کرتا:

- OAuth client secrets اور default secret values
- runtime environment resolution
- request headers اور public credential helpers
- dynamic URL builders
- executor functions
- session pool internals

## Capability Tags

`capabilities`، registry entry سے اخذ کردہ tags کی ایک مرتب شدہ array ہے۔ Integrators
کو TypeScript sources دوبارہ پڑھنے کے بجائے اسے "یہ provider کیا کر سکتا ہے" کے
machine-readable جواب کے طور پر استعمال کرنا چاہیے۔

| Tag                  | مطلب                                                                                |
| -------------------- | ----------------------------------------------------------------------------------- |
| `apikey`             | API key قبول کرتا ہے (`authType` کی قدر `apikey` یا `optional` ہے)۔                 |
| `oauth`              | OAuth یا session flow استعمال کرتا ہے۔                                              |
| `responses`          | OpenAI Responses-API کا base URL فراہم کرتا ہے۔                                     |
| `passthrough-models` | static catalog کے بجائے models کو براہِ راست upstream سے فراہم کرتا ہے۔             |
| `custom-executor`    | non-default executor چلاتا ہے، اس لیے یہ TypeScript path پر رہتا ہے۔                |
| `sidecar-candidate`  | `sidecar.eligible` کی عکاسی کرتا ہے — sidecar import کے لیے زیرِ غور لانا محفوظ ہے۔ |
| `usage-fetch`        | منسلک usage یا quota fetcher (`getUsageForProvider`) رکھتا ہے۔                      |
| `usage-supported`    | usage API اس provider کو قبول کرتی ہے (`isSupportedUsageConnection`)۔               |

`usage-fetch` صرف دریافت کے لیے ہے۔ یہ بتاتا ہے کہ OmniRoute provider کے لیے usage پڑھنا
جانتا ہے؛ یہ fetching کو فعال نہیں کرتا، quota semantics تبدیل نہیں کرتا، اور نہ ہی یہ ظاہر کرتا ہے کہ
Dashboard quota widget اس provider کے لیے فعال ہے — اس widget کو الگ سے
`USAGE_SUPPORTED_PROVIDERS` کے ذریعے محدود کیا جاتا ہے۔ حتمی ماخذ
`open-sse/services/usage/fetcherProviders.ts` میں `USAGE_FETCHER_PROVIDERS` ہے۔

اس فہرست کی keys وہ strings ہیں جنہیں usage dispatcher قبول کرتا ہے، اس لیے اس میں canonical ids
اور aliases دونوں شامل ہیں اور یہ tagged providers کی تعداد سے قدرے طویل ہے: وہ entries جو
manifest registry میں chat providers نہیں ہیں (مثلاً `firecrawl` search provider
اور `amazon-q` ACP provider)، ان کے لیے tag کرنے کی خاطر کوئی manifest entry موجود نہیں۔

`usage-supported` بتاتا ہے کہ آیا server اور Dashboard usage routes اس provider کے لیے connection
قبول کرتے ہیں۔ یہ `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
اور `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`) کی عکاسی کرتا ہے، اور دونوں کو
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`) کے ذریعے محدود کیا جاتا ہے۔ `usage-fetch`
کے برعکس، یہ صرف provider id پر جاری ہوتا ہے — runtime guard
کسی alias resolution کے بغیر `USAGE_SUPPORTED_PROVIDERS.includes(providerId)` انجام دیتا ہے، اس لیے manifest
بھی یہی اصول برقرار رکھتا ہے۔ دونوں tags کے دائرۂ کار مختلف ہیں: 3 providers پر صرف
`usage-fetch` (`opencode`، `opencode-zen`، `xai`) موجود ہے اور 1 پر صرف
`usage-supported` (`xiaomi-mimo-token-plan`) موجود ہے، اس لیے ایک سے دوسرے کا وجود لازم نہیں آتا۔

## سائیڈ کار کا استعمال

سائیڈ کارز کو `sidecar.eligible` کو ایک محتاط امیدوار سگنل سمجھنا چاہیے، نہ کہ غیر مشروط روٹنگ کا فیصلہ۔ درآمد کا پہلا ہدف API-key، جامد اینڈ پوائنٹ والے وہ فراہم کنندگان ہونے چاہییں جو ڈیفالٹ ایگزیکیوٹر استعمال کرتے ہیں۔ حسبِ ضرورت ویب ایگزیکیوٹرز، OAuth/سیشن فلو، متحرک URL بلڈرز، یا پول کنفیگریشن والے فراہم کنندگان TypeScript کے فال بیک راستے پر رہیں، جب تک کوئی سائیڈ کار مساوی طرزِ عمل نافذ نہ کر دے اور ٹیلی میٹری یکسانیت ثابت نہ کر دے۔

تجویز کردہ منتقلی کے مراحل:

1. TS رجسٹری سے فراہم کنندہ پلگ اِن مینی فیسٹ بنائیں اور اس کی توثیق کریں۔
2. Bifrost یا CLIProxyAPI کو API-key/جامد فراہم کنندگان کے لیے مینی فیسٹ درآمد کرنا سکھائیں۔
3. TS فال بیک کو فعال رکھتے ہوئے، اہل فراہم کنندگان کو `OMNIROUTE_RELAY_BACKEND` کے پسِ پشت سائیڈ کار کے ذریعے روٹ کریں۔
4. فراہم کنندگان کو صرف اس وقت ترقی دیں جب کامیابی کی شرح، p99 لیٹنسی، اسٹریمنگ کا طرزِ عمل، اور غیر معاون پیرامیٹرز سے نمٹنے کا طریقہ TS راستے کے مساوی ہوں۔
5. حسبِ ضرورت ایگزیکیوٹرز کے لیے، ایک وقت میں ایک فراہم کنندہ فیملی کے حساب سے سائیڈ کار کے مقامی پلگ اِنز شامل کریں۔

## فراہم کنندگان کو براہِ راست Next میں کیوں شامل نہ کیا جائے

Next فرنٹ اینڈ کو فراہم کنندہ پر عمل درآمد کی ذمہ داری نہیں سنبھالنی چاہیے۔ اسے API باؤنڈری کو کال کرنا چاہیے۔ پھر بیک اینڈ یہ فیصلہ کر سکتا ہے کہ TypeScript ایگزیکیوٹر، Bifrost، CLIProxyAPI، یا مستقبل کا کوئی مقامی سائیڈ کار استعمال کرنا ہے۔ اس طرح کسی بھی سائیڈ کار کو کنٹرول منتقل کرنے سے پہلے درخواست پر دستخط، اجازت یافتہ فہرست کی جانچ، DB پالیسی، اور فال بیک کا طرزِ عمل مرکزی طور پر منظم رہتے ہیں۔
