Tumia mwongozo huu kuchagua mzunguko mdogo zaidi wa maendeleo unaotegemewa kwa pull request. Hauchukui
nafasi ya nyaraka mahususi za usanifu na usalama za kila eneo zilizounganishwa hapa chini; unaunganisha kila aina ya kawaida
ya mabadiliko na mikataba yake, ukaguzi mahususi, na ufunikaji wa CI.

## Njia inayofuatwa na kila mabadiliko

1. **Chagua msingi kabla ya kuhariri.** Tafuta tawi amilifu la juu zaidi la `release/v*` na uunde tawi kutoka
   kwenye ncha yake. Lenga tawi hilo, si `main`. Ikiwa usitishaji wa mabadiliko ya toleo unatumika, usilenge tawi
   lililositishwa; tumia mzunguko amilifu unaofuata ulioelezwa katika
   [Muundo wa Matawi na Matoleo](BRANCHING_MODEL.md).
2. **Taja mikataba.** Tambua kila katalogi, schema, artefakti iliyozalishwa, API ya umma, au kiolesura cha
   mtumiaji kinachoathiriwa na mabadiliko. Jedwali lililo hapa chini linatoa seti ya chini ya kuanzia.
3. **Andika au sasisha majaribio mahususi.** Mabadiliko ya uzalishaji katika `src/`, `open-sse/`, `electron/`, au
   `bin/` yanahitaji jaribio la kiotomatiki katika PR hiyo hiyo. Endesha faili chache zaidi za majaribio zinazothibitisha
   tabia hiyo, kisha vizuizi mahususi vilivyoorodheshwa.
4. **Ruhusu CI iendeshe matriki pana.** Sehemu kamili za majaribio ya unit, Vitest, ratchet ya ufunikaji, na
   build ya uzalishaji huendeshwa kwenye PR. Endesha seti pana ya majaribio katika mazingira ya ndani tu wakati hitilafu mahususi inaashiria
   athari pana zaidi au wakati mabadiliko yanahusisha mifumo midogo kadhaa.
5. **Sawazisha kabla ya ukaguzi.** Pakua msingi amilifu, kagua commit zake mpya na diff yako dhidi
   yake, kisha fanya rebase au merge ya msingi kulingana na mtiririko wa kazi wa wachangiaji. Tatua migogoro ya faili
   zilizozalishwa na katalogi kutoka kwenye chanzo chake, zizalishe upya, endesha tena mzunguko mahususi, na uthibitishe kuwa
   PR bado inalenga tawi amilifu la toleo.
6. **Rekodi ushahidi.** Katika kiolezo cha PR, orodhesha amri zilizoendeshwa, kila faili ya jaribio iliyoongezwa au kubadilishwa,
   uhamishaji au feature flags, na uthibitishaji wowote wa CI pekee ambao bado unasubiri.

## Njia bora kulingana na aina ya mabadiliko

Amri zilizo hapa chini ni ukaguzi wa chini unaolengwa, si ruhusa ya kuruka jaribio linaloshughulikia moja kwa moja
tabia uliyobadilisha.

### Mtoa huduma

**Mikataba**

- Ufafanuzi wa mtoa huduma katika `src/shared/constants/providers/` na utungaji wake katika
  `src/shared/constants/providers.ts`.
- Modeli na uwezo katika `open-sse/config/providerRegistry.ts` au faili zake za registry zilizotengwa.
- Uteuzi wa executor/translator, usanidi wa OAuth au API key, mali za dashboard, na rejeleo la mtoa
  huduma lililozalishwa inapohitajika.
- Vitambulisho vya umma lazima vitumie `resolvePublicCred()`; majibu ya hitilafu lazima yatumie visaidizi vya pamoja vya
  utakaso wa hitilafu. Angalia `docs/security/PUBLIC_CREDS.md` (git; haijumuishwi katika `/docs`) na
  [Utakaso wa Hitilafu](../security/ERROR_SANITIZATION.md).

**Mzunguko mahususi**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # katalogi inapobadilika; commit diff iliyozalishwa
npm run lint
```

Pia jaribu kila familia ya maombi iliyoathiriwa: chat, Responses, images, embeddings, audio, au video.
Kagua katalogi iliyozalishwa na golden diffs kama mabadiliko ya mkataba; usiyakubali bila kuyakagua.

### Uelekezaji

**Mikataba**

- Thamani za umma za strategy na metadata ya UI katika `src/shared/constants/routingStrategies.ts`.
- Dispatch na mpangilio chini ya `open-sse/services/combo.ts` na `open-sse/services/combo/`.
- Schema za combo, persistence, hali ya resilience, uwezo wa modeli, na vidhibiti vya API/UI.
- [Injini ya Auto-Combo](../routing/AUTO-COMBO.md) na nyaraka za resilience wakati tabia inabadilika.

**Mzunguko mahususi**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # mabadiliko ya strategy au dispatch
npm run check:known-symbols      # mabadiliko ya usajili wa strategy
npm run lint
```

Tumia majaribio thabiti yenye upstream iliyoigizwa katika mazingira ya ndani. Majaribio ya haraka ya live combo yanahitaji vitambulisho na ni
ya mikono, si mbadala wa CI.

### UI / UX

**Mikataba**

- Mipaka ya route/page ya Next.js na component zinazoshirikiwa chini ya `src/app/` na
  `src/shared/components/`.
- Miundo ya majibu ya API, hali za kupakia/tupu/hitilafu, tabia ya kibodi na kisoma skrini,
  mpangilio unaoitikia ukubwa wa skrini, mandhari, na upanuzi wa locale.
- Mifuatano chanzo ya UI ya Kiingereza katika `src/i18n/messages/en.json`; usiweke moja kwa moja maandishi mapya yanayoonekana kwa mtumiaji kwenye msimbo.

**Mzunguko mahususi**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Endesha programu kwa mabadiliko ya mwingiliano au mwonekano na ukague viewport nyembamba na pana. CI huendesha
build ya uzalishaji na seti pana zaidi za majaribio; tabia ya mwonekano bado inahitaji component mahususi, Playwright,
au ukaguzi wa mikono uliorekodiwa unaofaa kwa mabadiliko hayo.

### i18n

**Mikataba**

- `src/i18n/messages/en.json` ndiyo chanzo cha UI; `config/i18n.json` ndiyo chanzo cha locale.
- Katalogi za CLI zipo kando chini ya `bin/cli/locales/`.
- Hifadhi placeholder na tag za ICU bila kuzibadilisha. Usitafsiri majina ya bidhaa/mtoa huduma/modeli,
  majina ya protocol na header, amri, vitambulishi vya code/JSON, URL, environment variables, au
  istilahi zilizolindwa kama `OmniRoute`, `OAuth`, `MCP`, na `A2A`. Orodha ya sasa ya chanzo ni
  `scripts/i18n/glossary/protected-terms.json`.

**Mzunguko mahususi**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # wakati mifuatano/katalogi za CLI zinabadilika
npm run lint
```

Huu ni mwongozo wa mfumo uliopo, si mwaliko wa kupanua zana zake au modeli ya key.
Weka viraka vya i18n vikiwa mahususi wakati mfumo mbadala unaundwa. Usiendeshe amri za utafsiri
zinazotumia huduma za nje isipokuwa kazi inahitaji waziwazi tafsiri zinazozalishwa na
umekagua diff iliyotokana nazo.

### CLI

**Mikataba**

- Amri na bendera za umma katika `bin/cli/`, amri za API zinazozalishwa, misimbo ya kutoka, stdout/stderr na
  miundo ya matokeo ya JSON, tabia ya usanidi/mazingira, na faili zilizofungashwa.
- Maandishi yanayoonekana kwa mtumiaji wa CLI lazima yatumie safu ya i18n ya CLI na kudumisha ulinganifu wa katalogi za `en`/`pt-BR`.
- Dumisha Node kama mazingira ya utekelezaji yanayotumika na mkataba wa binary iliyochapishwa.

**Mzunguko mahususi**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # mabadiliko ya CLI iliyozalishwa/iliyofungamanishwa
npm run check:pack-policy     # mabadiliko ya sehemu ya kifurushi
npm run lint
```

Tumia amri halisi katika saraka ya muda ya data wakati tabia inategemea uchanganuzi, faili, au hali ya
kutoka. CI hufanya ukaguzi mpana zaidi wa artefakti za kifurushi na mfumo-ikolojia.

### Hifadhidata

**Mikataba**

- Moduli za kikoa zilizo chini ya `src/lib/db/`; leta moduli mahususi moja kwa moja (safu ya zamani ya kusafirisha upya ya `localDb.ts` iliondolewa).
- Uhamishaji wa SQL wenye nambari na unaoweza kurudiwa bila athari chini ya `src/lib/db/migrations/`, usalama wa miamala, tabia ya
  uboreshaji, faharasa, na kila kiitishi kinachoathiriwa na skimu.
- Njia na vishughulikiaji hazitoi kamwe SQL ghafi moja kwa moja.

**Mzunguko mahususi**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Jaribu hifadhidata mpya na uboreshaji kutoka skimu iliyotangulia unapoongeza uhamishaji. Majaribio ya hifadhidata
lazima yafunge vishikio na kuita `resetDbInstance()` wakati wa usafishaji. Tekeleza `npm run test:bun:db` tu wakati
njia ya adapta ya Bun ya kadiri ya uwezo wake inabadilika; Node hubaki kuwa mamlaka kuu.

### Uundaji / upelekaji

**Mikataba**

- Manifesti/lockfile za mzizi na nafasi ya kazi, `scripts/build/`, uunganishaji huru wa Next.js, maudhui ya kifurushi cha `dist/`,
  metadata ya majukwaa ya Electron, mitiririko ya kazi ya CI, na viashiria vya upelekaji.
- Masafa ya Node yanayotumika na matumizi ya Bun yaliyoruhusiwa katika `CLAUDE.md` lazima yabaki bila kubadilika.
- Artefakti za uundaji zisifuatiliwe; sera za vitegemezi, leseni, mtiririko wa kazi, na kifurushi zinatumika.

**Mzunguko mahususi**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # mabadiliko ya vitegemezi au lockfile
npm run check:pack-policy      # mabadiliko ya sehemu ya kifurushi kilichochapishwa
npm run lint
```

Tumia `npm run build` ndani ya mazingira yako tu wakati mabadiliko yanaathiri ukusanyaji, uunganishaji huru, rasilimali,
au ufungamanishaji wa wakati wa utekelezaji. Tumia `npm run build:release` tu kwa uthibitishaji wa toleo/upelekaji. Uundaji wa CI ndio
ishara ya mwisho ya majukwaa mbalimbali; mabadiliko ya Electron yanayohusu jukwaa mahususi yanahitaji uundaji mahususi unaolingana
au ushahidi wa jaribio la awali.

## Mzunguko wa ndani wa toleo teule

Majaribio ya msimbo chanzi hayawezi kuthibitisha kuwa kifurushi kilichoundwa kinaanza: orodha za ufungashaji, vitegemezi vilivyopunguzwa,
na faili asili za mfumo hushindwa tu baada ya tarball kusakinishwa na kuanzishwa. `npm run dev:candidate`
(`scripts/dev/candidate.mjs`) ni upande wa ndani wa mtiririko wa tengeneza-mara-moja / thibitisha / pandisha kutoka
RFC #8084: hutengeneza toleo moja teule, huthibitisha kifurushi hicho mahususi, hukipandisha kwa kubadilisha majina ya
saraka, na hukirejesha nyuma nafasi iliyopandishwa inaposhindwa ukaguzi wake wa afya.

```bash
npm run dev:candidate -- run --dry-run --json  # chapisha mpango, usibadilishe chochote
npm run dev:candidate -- run                   # tengeneza + thibitisha + pandisha, rejesha nyuma kiotomatiki
npm run dev:candidate -- build                 # npm pack + sakinisha katika _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # anzisha kwenye port iliyo wazi, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # badilishana current na previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # tumia tena tarball iliyotengenezwa mahali pengine (CI)
```

- **Tengeneza mara moja.** `build` hufungasha mti wa sasa (inahitaji `dist/server.js`, kwa hivyo endesha
  `npm run build:release` kwanza) au hunakili `--from-tarball`, kisha husakinisha tarball katika
  kiambishi awali cha npm kilichotengwa, kwa sababu tarball haina `node_modules`. Kitambulisho ni sha fupi ya `HEAD`
  (`-dirty` wakati mti una mabadiliko ya ndani) au `tgz-<sha256>` kwa tarball. Kitambulisho safi ambacho
  tayari kimetengenezwa hutumika tena badala ya kutengenezwa upya; tumia `--force` ili kukitengeneza upya.
- **Thibitisha kifurushi, si msimbo chanzi.** `validate` huanzisha CLI iliyosakinishwa
  (`serve --port <free port>`) kwa kutumia `DATA_DIR=<candidate>/data` mpya, siri bandia, huku
  `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` na `INITIAL_PASSWORD` za mwendeshaji zikiondolewa kwenye
  mazingira, ili ikague hali ya loopback isiyohitaji ufunguo ya usakinishaji mpya. Husubiri
  `GET /api/health` irejeshe 200, huhitaji `GET /v1/models` irejeshe 200, husimamisha kundi la michakato,
  na kurekodi uamuzi katika `validation.json` pamoja na hashi ya tarball.
- **Pandisha kifurushi kilekile.** `promote` hukataa toleo teule lisilo na uthibitishaji uliofaulu kwa
  hashi yake ya sasa ya tarball. Nafasi amilifu chaguomsingi ni `_artifacts/candidate/current`; `--target <dir>`
  huchagua saraka nyingine kwenye mfumo uleule wa faili, na nafasi yake ya awali ni `<dir>.previous`.
  Kila ubadilishaji wa jina ni atomiki, na hitilafu inayotokea katikati hubatilisha ubadilishaji wa majina ambao tayari ulitekelezwa.
- **Rejesha nyuma.** `run` huthibitisha tena nafasi iliyopandishwa na kubadilishana `current` na `previous`
  iwapo ukaguzi huo utashindwa. Toleo teule linaloshindwa uthibitishaji wa kwanza halipandishwi kamwe.

Kila kitu huandikwa chini ya `_artifacts/candidate/` iliyopuuzwa na git; usakinishaji uliopo wa OmniRoute
na saraka yake ya data haziguswi kamwe. CLI iliyopandishwa ni
`_artifacts/candidate/current/prefix/bin/omniroute`; ianzishe kwa `DATA_DIR` yako mwenyewe unapoitumia.
Misimbo ya kuondoka: `0` mafanikio, `1` uthibitishaji au upandishaji umeshindwa, `2` hitilafu ya matumizi au build inayokosekana.

## Mzunguko wa ndani dhidi ya CI

| Endesha ndani kwa kila kiraka                                                                       | CI hutoa ishara pana                                                               |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Majaribio ya moja kwa moja ya tabia na vizuizi vya kategoria vilivyo hapo juu                       | Seti kamili ya majaribio ya vipengele iliyogawanywa na majaribio ya mfululizo      |
| `npm run lint`                                                                                      | Seti za Vitest na vizingiti vya ufunikaji/ubora                                    |
| Ukaguzi wa aina au uundaji pale tu mkataba ulioathiriwa unapouhitaji                                | Uundaji wa uzalishaji, usalama, nyaraka, utegemezi, na vizuizi vya sera za PR      |
| Ukaguzi wa moja kwa moja/wa mwingiliano wa mikono pale tu otomatiki inaposhindwa kuthibitisha tabia | Ukaguzi wa ujumuishaji kati ya kazi na wa mifumo uliosanidiwa na mtiririko wa kazi |

Mzunguko lengwa uliofaulu ni ushahidi kuhusu mkataba uliobadilishwa, si uthibitisho kwamba ukaguzi wa CI usiohusiana
utafaulu. Kwa upande mwingine, usifanye kila hariri ya ndani isubiri matriki kamili ya hazina.

## Orodha hakiki ya upatanisho

Kabla ya kuomba ukaguzi:

- Thibitisha kuwa msingi wa PR bado ni tawi amilifu la juu zaidi la `release/v*`.
- Leta msingi huo na ukague commit zilizoingizwa tangu ulipounda tawi lako.
- Kagua `git diff <active-base>...HEAD` ili kubaini mabadiliko ya bahati mbaya au yaliyotengenezwa kiotomatiki.
- Tatua migogoro ya katalogi na hati zilizotengenezwa kwa kusasisha chanzo na kutengeneza upya matokeo.
- Endesha upya kila jaribio/kizuizi lengwa kilichoorodheshwa katika maelezo ya PR baada ya upatanisho.
- Kamwe usilegeze masharti ya uthibitishaji au kuondoa majaribio yanayohitajika ili tu kulingana na msingi uliohamishwa.

Kwa sheria za kusitisha toleo na kubadilisha lengo, tumia
[Muundo wa Matawi na Matoleo](BRANCHING_MODEL.md). Kwa orodha kamili ya CI, tumia
[Marejeleo ya Vizuizi vya Ubora](../architecture/QUALITY_GATES.md).
