## Uchapishaji Unaoaminika wa npm (chaguo-msingi tangu v3.8.51) — uliowekwa kwenye hatua kwa ombi, wa moja kwa moja kama mbadala

`npm-publish.yml` huchapisha kupitia **Uchapishaji Unaoaminika wa npm (OIDC)** kwa chaguo-msingi: kazi ya
`stage-npm` (inayohifadhiwa na GitHub) hubadilishana id-token ya GitHub ili kupata kitambulisho cha muda mfupi cha npm
kwa utekelezaji huo — hakuna tokeni ya muda mrefu ya npm katika siri za hazina, hakuna kidokezo cha 2FA, na asili imeambatishwa.
Huo ndio ukwepaji ambao npm inaruhusu sasa kwa kuwa tokeni zinazoruka 2FA zinaondolewa;
unarejesha mtiririko otomatiki kikamilifu ambao mradi ulikuwa nao hadi v3.8.48 huku ukidumisha
hakikisho la WS1.3 (tokeni iliyovuja haiwezi kuchapisha peke yake — hakuna tokeni).

**Usanidi wa mara moja (mmiliki):** npmjs.com → kifurushi `omniroute` → Settings → _Trusted
Publisher_ → GitHub: mmiliki `diegosouzapw`, hazina `OmniRoute`, mtiririko wa kazi `npm-publish.yml`
(mazingira: hakuna). Hadi hilo liwepo, hatua otomatiki hushindwa kwa `ENEEDAUTH`:
anzisha tena kwa `publish_mode=staged` (hapa chini) au `direct`.

### Uchapishaji wa hatua kwa hatua (kwa ombi — `publish_mode=staged`)

Mtiririko wa kazi wa npm-publish hauchapishi tena moja kwa moja: huanzisha tarball iliyofungashwa
(`check:pack-boot`) kisha huendesha `npm stage publish` — baiti halisi huwekwa kwenye
rejesta, **haziwezi kusakinishwa** hadi mmiliki aidhinishe. Kizuizi cha kibinadamu cha 2FA kimehamishwa
BAADA ya uthibitisho, si kabla yake.

**Mtiririko wa mmiliki baada ya mtiririko wa kazi kuwa katika hali nzuri:**

1. `npm stage list omniroute` — tafuta kitambulisho cha hatua (pia huchapishwa katika muhtasari wa mtiririko wa kazi).
2. Thibitisha baiti zilizowekwa kwenye hatua (inapendekezwa): `npm stage download <id>`, kisha sakinisha
   tarball iliyopakuliwa kwenye kiambishi awali cha muda na uiwashe (`npm run check:pack-boot` huendesha otomatiki
   uamuzi sawa wa kufungasha→kusakinisha→kuwasha katika CI).
3. `npm stage approve <id>` — kidokezo cha 2FA NDICHO uchapishaji. `npm stage reject <id>` hutupa.
4. Kinga ya baada ya uchapishaji: kithibitishaji cha baada ya uchapishaji (WS1.4 ya mpango wa v3.8.49) husakinisha
   toleo lililochapishwa kutoka kwenye rejesta ya umma katika kontena safi na kuliwasha.

**Mbadala wa dharura:** `workflow_dispatch` pamoja na `publish_mode=direct` hurejesha
`npm publish` ya zamani ya papo hapo (tumia tu ikiwa uwekaji kwenye hatua wenyewe unatatizika; rekodi sababu).

**Uimarishaji wa mara moja (mmiliki, npmjs.com):** sanidi Trusted Publisher kwa
`omniroute` katika hali ya hatua pekee ili tokeni ya muda mrefu iliyovuja isiweze kutumia `npm publish`
moja kwa moja kutoka popote — CI inaweza kuweka kwenye hatua pekee; ni 2FA ya mmiliki tu inayotoa.

**Mwongozo wa kushughulikia artefakti iliyoharibika (haujabadilika):** `npm deprecate omniroute@<bad> "<reason> — use <fixed>"`
kama hatua ya kawaida ya kwanza (dakika chache, inaweza kutenduliwa); `npm unpublish` tu ndani ya kipindi cha saa 72/bila vitegemezi
na kamwe isiwe hatua ya kwanza. Docker: usiwahi kuandika upya lebo ya toleo — kurejesha nyuma ni
kuelekeza upya `latest` kwenye digest ya mwisho iliyo nzuri.

**Docker Hub `latest` (inahitajika katika kila uchapishaji thabiti wa SemVer):**
mtiririko wa kazi wa `docker-publish` lazima uweke lebo kwa **zote mbili** `X.Y.Z` na, wakati
`should-promote-latest.sh` inathibitisha kuwa hii ndiyo SemVer thabiti ya juu zaidi, `:latest`
kwa **digest ileile**. Baada ya kazi: digest ya `latest` kwenye Hub inalingana na digest mpya ya
SemVer na `last_updated` imesogea. Usiache `:latest` kwenye jengo la zamani
wakati maelezo ya toleo yanazungumzia marekebisho yaliyopo kwenye git pekee. Mianzisho ya haraka ya Compose
hutumia `:latest`; GitOps inapaswa kuendelea kubandika `X.Y.Z`. Tazama
[Vituo vya matoleo ya Docker](../guides/DOCKER_GUIDE.md#release-channels) na #10317.

## Njia ya Haraka ya Marekebisho ya Dharura (lebo `hotfix`)

PR yenye lebo `hotfix` huruka matriki nzito ya CI (E2E yenye sehemu 9, coverage ratchet,
quality-gate, quality-extended) na huhifadhi ukaguzi wa haraka wenye ishara thabiti: build,
sehemu za unit, integration, vitest, lint/typecheck, docs-sync, `check:pack-artifact`
na jaribio la kuwasha kutoka tarball (`check:pack-boot`). Lengo: kuwa kijani ndani ya ≤15min badala ya ~33min.

**Sera ya kuingia — yote manne yanahitajika (imeundwa kwa kufuata njia za dharura za Chromium/VS Code/Node):**

1. **Ukali**: uzalishaji umeharibika — artifact iliyochapishwa huanguka wakati wa kuwaka /
   marekebisho ya usalama / kila mtumiaji wa toleo ameathirika. "Muhimu" si sawa na "imeharibika".
2. **Mamlaka**: ni mmiliki wa hazina pekee anayeweka lebo `hotfix`. Lebo NDIYO
   idhini — kamwe usijipe mwenyewe kwenye PR ya kampeni.
3. **Ushahidi**: maelezo ya PR yana kiungo cha utekelezaji mzito wa awali uliokuwa kijani kikamilifu (mkusanyiko ambao
   kazi zilizorukwa zingethibitisha upya) pamoja na jaribio la marekebisho lenyewe lililofeli kisha likafaulu.
4. **Upeo**: cherry-pick pekee — marekebisho madogo kabisa, bila refactors, bila mabadiliko ya ziada.

Sehemu ya coverage/ratchet iliyorukwa inathibitishwa upya na utekelezaji kamili unaofuata kwenye
tawi la toleo (release-green endelevu) — njia hii huruka KUSUBIRI, kamwe si uthibitishaji.
Tofauti za majaribio pekee (faili zote chini ya `tests/`, hakuna chini ya `tests/e2e/`) huruka matriki ya E2E
kiotomatiki, bila lebo yoyote.

### Mpangilio wa Muundo

Hazina hutumia saraka tatu tofauti za matokeo — usizichanganye kamwe:

| Saraka    | Madhumuni                                                                       | Inafuatiliwa?             |
| --------- | ------------------------------------------------------------------------------- | ------------------------- |
| `src/`    | Chanzo cha programu (TypeScript / TSX)                                          | Ndiyo                     |
| `.build/` | Vipengee vya kati vya uundaji — matokeo ya `next build` (`distDir`)             | Hapana (imepuuzwa na git) |
| `dist/`   | Kifurushi cha npm kinachoweza kusambazwa — huunganishwa na `assembleStandalone` | Hapana (imepuuzwa na git) |

> **Dokezo kwa mwendeshaji:** saraka ya picha ya VPS ya mbali inasalia `/usr/lib/node_modules/omniroute/app/`.
> Ni matokeo ya uundaji **ndani ya hazina** pekee yaliyohamishwa (`app/` → `dist/`). Ujuzi wa upelekaji husawazisha
> maudhui ya `dist/` kwa rsync hadi saraka ya mbali ya `app/` — hakuna mabadiliko ya njia ya VPS yanayohitajika.

**Mtiririko wa uundaji mmoja:**

```
npm run build:release
  └─ rm -rf .build dist          (safisha)
  └─ next build → .build/next/   (vipengee vya kati)
  └─ assembleStandalone          (hunakili standalone + static + public + natives → dist/)
  └─ writes dist/BUILD_SHA       (kiashirio cha HEAD)
```

USIENDESHE `npm run build` ikifuatiwa na `npm run build:cli` tofauti kwa ajili ya upelekaji — tumia
`npm run build:release`, ambayo hufanya uundaji upya safi + kiashirio katika amri moja.

## Kurejesha Toleo la Awali

Ikiwa toleo lina tatizo kubwa:

1. `gh release edit vX.Y.Z --prerelease` (huweka alama kuwa si toleo la hivi karibuni)
2. `git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` (ikiwa tu halijaanza kutumiwa na watumiaji)
3. Au: hotfix kwenye `release/vX.Y.0` → toleo la kiraka `vX.Y.(Z+1)`
4. Wasiliana mara moja kupitia GitHub Discussions na Discord

## Kanuni Muhimu

- Kamwe usifanye commit moja kwa moja kwenye `main`
- Kamwe usitumie `git push --force` kwenye matawi ya `main` au `release/*`
- Kamwe usiruke hooks za Husky (`--no-verify`)
- Kamwe usifanye commit ya siri, taarifa za uthibitishaji, au faili za `.env`
- Coverage lazima ibaki ≥60/60/60/60 (statements/lines/functions/branches)
- Daima jumuisha au sasisha majaribio unapobadilisha msimbo wa uzalishaji katika `src/`, `open-sse/`, `electron/`, au `bin/`
