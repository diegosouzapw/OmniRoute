`open-sse/config/providerPluginManifest.ts` визначає JSON-безпечний контракт плагіна провайдера. `open-sse/config/providerPluginManifestRegistry.ts` пов’язує цей контракт із поточним реєстром провайдерів для сайдкарів, таких як Bifrost, CLIProxyAPI або майбутній маршрутизатор на Go/Rust. Реєстр TypeScript залишається джерелом істини, але сайдкари можуть використовувати маніфест без імпорту коду виконавців, стандартних значень OAuth, заголовків або стану середовища процесу.

Той самий маніфест доступний через HTTP за адресою
`GET /api/v1/provider-plugin-manifest` для сайдкарів, що працюють поза процесом.

OmniRoute повідомляє цю URL-адресу Bifrost і CLIProxyAPI через заголовок запиту
`X-OmniRoute-Provider-Manifest-Url`. Задайте
`OMNIROUTE_PROVIDER_MANIFEST_URL`, якщо сайдкару потрібна публічна URL-адреса або адреса в мережі контейнерів замість локального джерела запиту.

## Оновлення маніфесту

HTTP-кінцева точка повертає `Cache-Control: public, max-age=60` і строгий
`ETag`. Сайдкар має зберігати останній перевірений маніфест і надсилати його ETag
в `If-None-Match` під час оновлення. Відповідь `304 Not Modified` не має тіла;
сайдкар продовжує використовувати кешований маніфест. Якщо перевіреного кешованого маніфесту немає,
сайдкар повинен виконати безумовний запит замість прийняття відповіді `304`.

## Мета

Поступово перетворити метадані провайдерів на контракт плагіна, щоб гарячий шлях запиту
зрештою міг оброблятися сайдкаром із меншою затримкою, тоді як OmniRoute зберігатиме
маршрут TypeScript як шлюз політик і резервний варіант. Маніфест є доповненням: сам по собі він
не змінює маршрутизацію запитів.

## Контракт

Маніфест містить:

- ідентифікатор і псевдонім провайдера
- формат висхідного сервісу та назву виконавця
- тип автентифікації, заголовок автентифікації та необов’язковий префікс автентифікації
- статичні метадані кінцевої точки
- придатність для сайдкара та явні причини, через які провайдер має залишатися на шляху TS
- JSON-безпечні метадані моделей, як-от довжина контексту, ознаки підтримки зору/міркувань і
  непідтримувані параметри
- теги можливостей, зокрема `apikey`, `oauth`, `custom-executor`,
  `passthrough-models`, `responses`, `sidecar-candidate`, `usage-fetch` і `usage-supported`

Маніфест навмисно не містить:

- секретів клієнта OAuth і стандартних значень секретів
- розв’язання середовища під час виконання
- заголовків запитів і публічних допоміжних засобів для облікових даних
- динамічних побудовників URL
- функцій виконавців
- внутрішніх компонентів пулу сеансів

## Теги можливостей

`capabilities` — це відсортований масив тегів, отриманих із запису реєстру. Інтеграторам
слід сприймати його як машинозчитувану відповідь на запитання «що може робити цей провайдер» замість
повторного аналізу вихідного коду TypeScript.

| Тег                  | Значення                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `apikey`             | Приймає ключ API (`authType` має значення `apikey` або `optional`).                       |
| `oauth`              | Використовує потік OAuth або сеансовий потік.                                             |
| `responses`          | Надає базову URL-адресу OpenAI Responses API.                                             |
| `passthrough-models` | Надає моделі безпосередньо з висхідного сервісу замість статичного каталогу.              |
| `custom-executor`    | Запускає нестандартний виконавець, тому залишається на шляху TypeScript.                  |
| `sidecar-candidate`  | Віддзеркалює `sidecar.eligible` — можна безпечно розглядати для імпорту в сайдкар.        |
| `usage-fetch`        | Має підключений засіб отримання даних про використання або квоту (`getUsageForProvider`). |
| `usage-supported`    | API використання приймає цього провайдера (`isSupportedUsageConnection`).                 |

`usage-fetch` призначений лише для виявлення. Він повідомляє, що OmniRoute вміє отримувати дані про використання для
провайдера; він не активує отримання, не змінює семантику квот і не означає, що
віджет квоти на панелі керування ввімкнено для провайдера — цей віджет окремо контролюється
`USAGE_SUPPORTED_PROVIDERS`. Джерелом істини є `USAGE_FETCHER_PROVIDERS` у
`open-sse/services/usage/fetcherProviders.ts`.

Цей список індексується рядками, які приймає диспетчер використання, тому він поєднує канонічні ідентифікатори
з псевдонімами та є дещо довшим за кількість позначених провайдерів: записи, які
не є чат-провайдерами в реєстрі маніфесту (наприклад, пошуковий провайдер `firecrawl`
і ACP-провайдер `amazon-q`), не мають запису в маніфесті, який можна було б позначити.

`usage-supported` указує, чи приймають серверні маршрути та маршрути панелі керування для даних про використання підключення
цього провайдера. Він віддзеркалює `isSupportedUsageConnection()` (`src/lib/usage/providerLimits.ts`)
і `supportsProviderQuota()` (`src/shared/utils/providerQuotaVisibility.ts`), обидва з яких контролюються
`USAGE_SUPPORTED_PROVIDERS` (`open-sse/services/usage/supportedProviders.ts`). На відміну від
`usage-fetch`, він додається лише на основі ідентифікатора провайдера — перевірка під час виконання виконує
`USAGE_SUPPORTED_PROVIDERS.includes(providerId)` без розв’язання псевдонімів, тому маніфест
дотримується того самого правила. Ці два теги мають різні області дії: 3 провайдери мають лише
`usage-fetch` (`opencode`, `opencode-zen`, `xai`), а 1 має лише
`usage-supported` (`xiaomi-mimo-token-plan`), тому один не передбачає наявності іншого.

## Використання сайдкара

Сайдкари мають розглядати `sidecar.eligible` як консервативний сигнал про можливість використання, а не як безумовне рішення щодо маршрутизації. Першими цілями для імпорту мають бути провайдери з API-ключами та статичними кінцевими точками, які використовують стандартний виконавець. Провайдери з власними вебвиконавцями, потоками OAuth/сеансів, динамічними конструкторами URL або конфігурацією пулу мають залишатися на резервному шляху TypeScript, доки сайдкар не реалізує еквівалентну поведінку, а телеметрія не підтвердить паритет.

Рекомендовані етапи міграції:

1. Згенерувати й перевірити маніфест плагінів провайдерів із реєстру TS.
2. Навчити Bifrost або CLIProxyAPI імпортувати маніфест для провайдерів з API-ключами та статичними кінцевими точками.
3. Маршрутизувати відповідних провайдерів через сайдкар за допомогою `OMNIROUTE_RELAY_BACKEND`, залишаючи резервний шлях TS увімкненим.
4. Переводити провайдерів лише тоді, коли частота успішних запитів, затримка p99, потокова поведінка та обробка непідтримуваних параметрів відповідають шляху TS.
5. Додавати нативні для сайдкара плагіни для власних виконавців — по одному сімейству провайдерів за раз.

## Чому не варто вбудовувати провайдерів безпосередньо в Next

Фронтенд Next не повинен відповідати за виконання запитів до провайдерів. Він має викликати межу API. Після цього бекенд може вирішити, чи використовувати виконавець TypeScript, Bifrost, CLIProxyAPI або майбутній нативний сайдкар. Це дає змогу централізовано виконувати підписання запитів, перевірки списку дозволених ресурсів, політики БД і резервну поведінку перед передаванням керування будь-якому сайдкару.
