## Підсумок

OmniRoute тепер підтримує три режими ретрансляції для `/api/v1/relay/chat/completions`:

- `ts`: використовувати ретранслятор TypeScript у межах процесу.
- `bifrost`: примусово використовувати шлюз Bifrost.
- `auto`: надавати перевагу Bifrost, коли він доступний, і повертатися до TypeScript у разі збою.

За високої частоти запитів (велика кількість токенів на день, майже безперервне навантаження) найкраща стратегія — зробити резервний шлях явним і швидким, щоб основний шлях ніколи не блокувався через непрацюючий sidecar.

## Поведінка режимів

- `ts`
  - Найнижча операційна складність.
  - Уся маршрутизація та валідація виконуються в Node.
  - Доступність не залежить від sidecar.
- `bifrost`
  - Примусово спрямовує всі запити через шлюз sidecar.
  - Без автоматичного резервного перемикання.
  - Корисний лише тоді, коли працездатність і затримка sidecar гарантовані.
- `auto`
  - Sidecar використовується, коли він доступний і ввімкнений.
  - Невдалі спроби додають заголовки резервного перемикання та повертають трафік до TS, щоб забезпечити обмежений час успішного виконання запитів.
  - Цей режим є найбезпечнішим вибором для робочого середовища, коли безперервність роботи важливіша за сувору маршрутизацію виключно через sidecar.

## 9router і CLIPROXYAPI сьогодні

9router і CLIPROXYAPI — це інтеграції, які історично надавали шляхи сумісності для upstream-провайдерів.

- 9router — це вбудований шлях для оркестрації upstream-сервісів і забезпечення сумісності.
- CLIPROXYAPI — це проксі-міст API для трафіку в стилі CLI / SDK.
- Bifrost стабілізується як зовнішній шлях для випадків, коли потрібен окремий проміжний вузол на кшталт sidecar і локальна диспетчеризація з низькою затримкою.

Якщо ви зараз порівнюєте 9router/CLIPROXYAPI:

- Зберігайте підписування запитів, перевірки списку дозволених адрес і шлюзи політик БД у маршруті API до передавання запиту.
- Якщо робочий процес потребує суворої поведінки sidecar і меншої варіативності для кожного запиту, використовуйте `OMNIROUTE_RELAY_BACKEND=bifrost`.
- Якщо потрібна стійкість sidecar із поступовою деградацією під час інцидентів, використовуйте `OMNIROUTE_RELAY_BACKEND=auto`.

## Контракт межі бекенду

Стабільною межею продукту є API ретрансляції OmniRoute, а не реалізація панелі керування. Панель керування Next.js може встановлювати, налаштовувати й контролювати локальні служби, але маршрутизація запитів має починатися через API ретрансляції та передаватися далі за цією межею.

Довгострокові варіанти бекенду:

- Зберігайте ретранслятор TypeScript як внутрішньопроцесний шлях політик і резервного перемикання. Автентифікація, списки дозволених адрес, нормалізація запитів, облік і перевірки безпеки залишаються тут до будь-якого передавання бекенду.
- Використовуйте Bifrost як бажаний високопродуктивний sidecar рівня Tier-1, коли розгортанню потрібна менша варіативність маршрутизації, централізована ротація провайдерів або горизонтальне масштабування між кількома репліками OmniRoute.
- Зберігайте 9router і CLIPROXYAPI як вбудовані служби сумісності. Вони працюють як контрольовані локальні процеси й корисні, коли потрібен адаптер із властивою їм поведінкою провайдера/CLI, але вони не повинні ставати стандартним механізмом маршрутизації рівня Tier-1.
- Не дозволяйте панелі керування передавати довільні URL-адреси служб в основний шлях. URL-адреси, надані інтерфейсом користувача, є вхідними даними конфігурації; код маршрутизації має визначати зареєстровані та перевірені на працездатність бекенди на основі серверних налаштувань і стану супервізора.
- Наразі віддавайте перевагу loopback HTTP для контрольованих служб, оскільки керовані процеси вже надають HTTP-сумісні API, захист маршруту може перевіряти цю межу, а поведінку під час збоїв і резервного перемикання видно в журналах запитів. Майбутній транспорт на основі SDK або сокетів варто додавати лише в тому разі, якщо він відчутно зменшить затримку маршрутизації p99, не послаблюючи ізоляцію чи семантику резервного перемикання.

Отже, для розгортання з дуже високою пропускною здатністю стандартною відповіддю є `auto` з увімкненим Bifrost: використовуйте sidecar на Go в основному шляху, зберігаючи резервний шлях TypeScript для забезпечення високої частки успішних запитів. Використовуйте `bifrost` лише тоді, коли сувора робота виключно через sidecar важливіша за поступову деградацію.

## Рекомендації для високої пропускної здатності

Для стабільно високих RPM/RPS і суворого SLO успішності:

1. Використовуйте `auto` з практичним періодом очікування та телеметрією збоїв.
2. Зберігайте валідацію upstream-сервісів і перевірки ключів API на межі маршруту TypeScript.
3. Увімкніть явні заголовки/лічильники, щоб ваша система сповіщень бачила частоту та причини резервних перемикань.
4. Налаштуйте тайм-аути sidecar на швидке завершення в разі збою, а не на нескінченне очікування.
5. Підтримуйте автоматичний перезапуск служби та цикл телеметрії працездатності в справному стані, щоб резервне перемикання справді було винятковою подією.

## Рекомендована базова конфігурація

- `OMNIROUTE_RELAY_BACKEND=auto`
- `BIFROST_ENABLED=1`
- Не вимикайте перевірки ключів API, списку дозволених адрес, санітизатора та обмеження частоти в обробниках маршрутів (вони завжди виконуються до подальшого переспрямування).
- Експортуйте метрики резервного перемикання зі свого зворотного проксі та журналів запитів, щоб збої sidecar ставали помітними протягом однієї хвилини.

## Контракт плагіна провайдера

Sidecar мають імпортувати метадані провайдера через JSON-безпечний маніфест плагіна провайдера, а не залежати від внутрішньої реалізації виконавців TypeScript. Контракт відповідності вимогам до sidecar та етапи міграції див. у документі
[Маніфест плагіна провайдера](./PROVIDER_PLUGIN_MANIFEST.md).
