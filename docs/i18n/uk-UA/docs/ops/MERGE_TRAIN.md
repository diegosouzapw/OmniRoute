Починаючи з v3.8.49 (WS3.2/WS3.4 плану якості/швидкості), типовим шляхом злиття
перевірених PR у `release/vX.Y.Z` є **черга злиття Mergify** (`.mergify.yml`);
описаний нижче **ручний потяг злиття** є РЕЗЕРВНИМ варіантом — він використовується під час інцидентів,
заморожування релізу або якщо план Mergify Open Source коли-небудь зміниться.

## Шлях за замовчуванням: черга Mergify

1. PR перевірено кампаніями, він отримав зелений статус і схвалений власником через ⭐
   контрольний етап перед злиттям (звіт + рішення щодо кожного елемента — див. `/merge-prs`, крок 0.75).
2. Власник (або сесія, що діє відповідно до рішення власника) застосовує мітку **`queue`**.
   Ця мітка Є схваленням злиття; Mergify лише виконує його.
3. Mergify перевіряє PR у черзі **послідовно** (по одному) за допомогою швидких
   контрольних етапів і виконує злиття (squash). Пакетна обробка + автоматичний поділ навпіл доступні
   в платному тарифі Mergify ("Cannot use Merge Queue batch" у безкоштовному тарифі, #7220),
   тому `.mergify.yml` не задає `batch_size`; пакетна обробка залишається завданням описаного нижче
   ручного конвеєра злиття. PR, перевірки якого все ще очікують на завершення після `checks_timeout`
   (240 хв = 2× виміряного p95 для `quality.yml`), видаляється з черги замість її блокування.
4. Після злиття безперервний процес перевірки готовності релізу перевіряє нову вершину під час push
   і створює issue із зазначенням причетності, якщо комбінація спричинила регресію (автоматичне скасування ніколи не виконується).

Запобіжні заходи (відповідають жорстким правилам #21/#22 у `CLAUDE.md`):

- **Відкрито заморожування релізу** → НЕ позначайте міткою PR, націлені на заморожену гілку;
  спочатку перепризначте ціль на активну `release/vX+1`.
- **PR іншої сесії, над яким триває робота** → ніколи не позначайте його міткою; лише сесія-власник
  ставить у чергу власну роботу.
- Зміни лише в тестах і PR із міткою `hotfix` уже запускають скорочений CI (див.
  `RELEASE_CHECKLIST.md` → пришвидшений процес для виправлень); умови черги приймають будь-який
  фактично запущений набір перевірок (`#check-failure=0` + `#check-pending=0`).

## Резервний варіант: ручний потяг злиття

Використовується, коли черга недоступна. Тут формалізовано практику, завдяки якій протягом
одного дня циклу v3.8.47 було оброблено 33 PR:

1. **Сформуйте пакет** (приблизно 10–30 перевірених і схвалених PR). Перевірте колізії `linked:`
   (однакові `tap.testFiles`, однакові фрагменти CHANGELOG) і обробляйте їх послідовно.
2. **Перевірте ОДИН РАЗ**: в ізольованому worktree від верхівки релізної гілки локально злийте всі
   голови пакета, а потім запустіть еквівалентний релізному набір перевірок
   (`npm run check:release-green`; перед релізом додайте `--with-build`).
   `scripts/release/merge-train.sh <base> <PR#>…` автоматизує кроки 1–2 (конфліктні
   PR вилучаються, потяг продовжує рух). Повний режим запускає `npm run test:unit` —
   оптимізований для машини засіб запуску (`--test-concurrency=20`), **а не** два послідовні CI-шарди
   на 4 ядра, через які домінантна фаза використовувала лише близько 25% ресурсів 16-ядерної машини (виправлено
   2026-07-18). `--fast` (внутрішньоденна обробка мегапотягів, схвалено власником 2026-07-18)
   зберігає всі статичні перевірки + vitest, але запускає лише файли node:test, змінені
   PR, що увійшли до потяга; ПОВНИЙ набір усе одно має запускатися щонайменше раз на день
   на накопиченій верхівці (один потяг без `--fast`).
3. **Зелений результат** → злийте PR послідовно (перед кожним повторно перевіряючи `state,headRefOid` —
   PR, голова якого змінилася, повертається на перевірку). Переконайтеся, що результуюча різниця кожного злиття
   містить лише власні зміни PR (жодних повернень через автоматичне розв'язання конфліктів: перевірте `git diff --stat`
   на наявність видалень поза межами області змін).
4. **Червоний результат** → діліть пакет навпіл (перевіряючи кожну половину), а не виконуйте повторну перевірку
   по одному PR; поверніть проблемний PR у чергу перевірки разом із доказами.
5. **Ніколи не робіть цього**: не зливайте в заморожену гілку під час заморожування релізу; не використовуйте `git stash`
   ніде; не перезапускайте CI без розбору в надії, що червоний результат зникне (правило: червоний результат — це інформація).

## Рівні перевірки (чому черга безпечна лише зі швидкими перевірками)

- **Для кожного PR** (швидкі перевірки quality.yml): тести, охоплені TIA, + повний модульний набір у 4 шардах +
  vitest + набір lint-перевірок + перевірка типів + цілісність документації/журналу змін.
- **Для кожного пакета/верхівки** (безперервна перевірка готовності релізу): ЖОРСТКІ перевірки `--quick` під час кожного push до
  релізної гілки; повні проходи `--with-build --full-ci` 3 рази на день.
- **Для кожного релізу** (ci.yml у релізному PR): повна матриця, включно з E2E ×9,
  артефактом пакета + початковою smoke-перевіркою tarball, покриттям/порогами.

Жодна перевірка не виконується рідше, ніж раніше — важкий набір просто запускається для кожного пакета/верхівки,
а не для кожного PR, що й усуває O(N) циклів очікування.

## Передумови для `merge-train.sh` у свіжому checkout

Скрипт запускає **попередню перевірку** з негайним завершенням у разі помилки в кореневому checkout (до будь-яких
операцій із worktree), тому пошкоджене встановлення ніколи не зможе маскуватися під червоний потяг:

1. `npm ci`, потім запустіть postinstall для `bun`, який блокує npm:
   `(cd node_modules/bun && node install.js)` — інакше `check:provider-consistency`
   і `check:known-symbols` (обидва `bun scripts/…`) завершаться помилкою і для потяга, І для бази
   без рядка з описом порушення.
2. Не повинно бути стороннього `node_modules/node_modules` (дубльованого дерева залежностей; React завантажується двічі,
   і набори UI-тестів vitest миттєво завершуються помилкою).
3. `node_modules/.bin/tsc` має існувати й бути виконуваним (у разі часткового встановлення його немає).

Потяг запускає блокувальну перевірку `npm run check:cycles:ratchet`; звичайна `npm run check:cycles`
має рекомендаційний характер (вона виводить список SCC і завершується з ненульовим кодом навіть на справній базі).
