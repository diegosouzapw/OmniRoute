Починаючи з v3.8.49 (WS3.2/WS3.4 плану якості/швидкості), стандартним шляхом злиття
перевірених PR у `release/vX.Y.Z` є **черга злиття Mergify** (`.mergify.yml`);
описаний нижче **ручний потяг злиття** є РЕЗЕРВНИМ варіантом — він використовується під час інцидентів,
заморожування релізу або якщо план Mergify Open Source коли-небудь зміниться.

## Стандартний шлях: черга Mergify

1. PR перевірено/позначено зеленим кампаніями та схвалено власником через шлюз ⭐
   перед злиттям (звіт + рішення щодо кожного пункту — див. `/merge-prs`, крок 0.75).
2. Власник (або сесія, що діє відповідно до рішення власника) додає мітку **`queue`**.
   Ця мітка І Є схваленням злиття; Mergify лише виконує його.
3. Mergify об’єднує в пакет до 10 PR із черги, перевіряє пакет за швидкими шлюзами
   та зливає його (squash). Червоний пакет **автоматично ділиться навпіл** — проблемний PR
   ізолюється приблизно за log2(N) повторних перевірок і видаляється з черги; решта продовжують обробку.
4. Після злиття безперервний робочий процес перевірки готовності релізу перевіряє нову вершину під час push
   і відкриває issue з атрибуцією, якщо комбінація спричинила регресію (без автоматичного відкату).

Запобіжники (відповідають жорстким правилам #21/#22 у `CLAUDE.md`):

- **Заморожування релізу активне** → НЕ додавайте мітки до PR, націлених на заморожену гілку; спершу перенаправте їх на
  активну `release/vX+1`.
- **PR іншої сесії, над яким триває робота** → ніколи не додавайте до нього мітку; лише сесія-власник ставить
  власну роботу в чергу.
- PR зі змінами лише в тестах і PR із міткою `hotfix` уже запускають скорочений CI (див.
  `RELEASE_CHECKLIST.md` → Hotfix Fast-Lane); умови черги приймають будь-який
  фактично виконаний набір перевірок (`#check-failure=0` + `#check-pending=0`).

## Резервний варіант: ручний потяг злиття

Використовується, коли черга недоступна. Це формалізує практику, за допомогою якої за
один день під час циклу v3.8.47 було оброблено 33 PR:

1. **Сформуйте пакет** (приблизно 10–30 перевірених і схвалених PR). Перевірте колізії `linked:`
   (однакові `tap.testFiles`, однакові фрагменти CHANGELOG) і обробляйте такі PR послідовно.
2. **Перевірте ОДИН РАЗ**: в ізольованому worktree від вершини релізної гілки локально злийте всі
   голови пакета, а потім запустіть еквівалентний релізному набір перевірок
   (`npm run check:release-green`; перед релізом додайте `--with-build`).
   `scripts/release/merge-train.sh <base> <PR#>…` автоматизує кроки 1–2 (PR із конфліктами
   вилучаються, потяг продовжує рух). Повний режим запускає `npm run test:unit` — оптимізований
   для цієї машини засіб запуску (`--test-concurrency=20`), **а не** два послідовні 4-ядерні
   шарди CI, через які основна фаза використовувала лише приблизно 25% ресурсів 16-ядерної машини (виправлено
   2026-07-18). `--fast` (для очищення великого потяга протягом дня, схвалено власником 2026-07-18)
   зберігає всі статичні шлюзи + vitest, але запускає лише файли node:test, змінені
   PR, що ввійшли до потяга; ПОВНИЙ набір усе одно має запускатися щонайменше раз на день на
   накопиченій вершині (один потяг без `--fast`).
3. **Зелений результат** → злийте PR послідовно (перед кожним повторно перевіряючи `state,headRefOid` —
   PR, голова якого змінилася, повертається на перевірку). Доведіть, що підсумкова різниця кожного злиття
   містить лише власні зміни PR (жодних відкатів через автоматичне розв’язання конфліктів: перевіряйте `git diff --stat`
   на наявність вилучень поза межами завдання).
4. **Червоний результат** → діліть пакет навпіл (перевіряючи кожну половину), а не повторно перевіряйте
   PR по одному; поверніть проблемний PR у чергу перевірки разом із доказами.
5. **Ніколи не робіть цього**: не зливайте зміни в заморожену гілку під час заморожування; не використовуйте `git stash`
   ніде; не перезапускайте CI без розбору в надії, що червоний результат зникне (правило: червоний результат — це інформація).

## Рівні (чому черга безпечна лише зі швидкими шлюзами)

- **Для кожного PR** (швидкі шлюзи quality.yml): тести, визначені TIA як заторкнуті, + повний модульний набір у 4 шардах +
  vitest + набір перевірок lint + перевірка типів + цілісність документації/журналу змін.
- **Для кожного пакета/вершини** (безперервна перевірка готовності релізу): ЖОРСТКІ шлюзи `--quick` під час кожного push до
  релізної гілки; повні проходи `--with-build --full-ci` 3 рази на день.
- **Для кожного релізу** (ci.yml у релізному PR): повна матриця, зокрема E2E ×9,
  артефакт пакета + базова перевірка запуску tarball, покриття/порогові обмеження.

Обсяг перевірок не став меншим, ніж раніше — ресурсомістка частина просто виконується для кожного пакета/вершини,
а не для кожного PR, що й усуває O(N) циклів очікування.
