> **Коротко**: OmniRoute постачається із вбудованим моніторингом стану, автопілотом провайдерів, відстеженням квот і хуками спостережуваності. У цьому посібнику описано інформаційну панель, сповіщення та усунення несправностей.

**Джерела:**

- `src/lib/monitoring/observability.ts` — знімок спостережуваності
- `src/lib/monitoring/comboHealthAutopilot.ts` — автопілот стану комбінацій
- `src/lib/monitoring/providerHealthAutopilot.ts` — автопілот провайдерів
- `src/lib/monitoring/providerHealthMatrix.ts` — матриця стану провайдерів
- `src/lib/localHealthCheck.ts` — локальна перевірка стану
- `src/lib/tokenHealthCheck.ts` — стан оновлення токенів
- `src/lib/proxyHealth.ts` — кеш стану проксі-сервера (описано в PROXY_GUIDE.md)

## Огляд

OmniRoute має **3 рівні моніторингу**:

```
┌──────────────────────────────────────────────────────────────┐
│  Рівень 1: Стан системи (на рівні сервера)                    │
│  ├─ localHealthCheck.ts — БД, порти, нативні залежності       │
│  ├─ db/healthCheck.ts — цілісність, зовнішні ключі,            │
│  │  осиротілі артефакти                                       │
│  └─ Інформаційна панель: /dashboard/health                    │
├──────────────────────────────────────────────────────────────┤
│  Рівень 2: Стан провайдерів (стійкість кожного провайдера)    │
│  ├─ providerHealthAutopilot.ts — запобіжник, періоди          │
│  │  відновлення                                               │
│  ├─ providerHealthMatrix.ts — оцінки стану за                 │
│  │  провайдером/моделлю                                       │
│  └─ Інформаційна панель: /dashboard/providers                 │
├──────────────────────────────────────────────────────────────┤
│  Рівень 3: Спостережуваність у реальному часі                 │
│  │  (знімки середовища виконання)                             │
│  ├─ observability.ts — запобіжники, сеанси, квота             │

└──────────────────────────────────────────────────────────────┘
```

## Сторінки інформаційної панелі

### `/dashboard/health` (Стан системи)

Інформаційна панель загального стану показує:

| Розділ                    | Що він показує                                                  |
| ------------------------- | --------------------------------------------------------------- |
| **Стан сервера**          | Час роботи, версія, порт, активні з’єднання                     |
| **База даних**            | З’єднання, цілісність, розмір WAL, останні міграції             |
| **Зведення провайдерів**  | Кількість активних і справних, кількість відкритих запобіжників |
| **Монітори квот**         | Активні сеанси, сповіщення, вичерпані квоти                     |
| **Останні помилки**       | Останні 10 помилок із трасуванням стека                         |
| **Використання ресурсів** | Пам’ять, ЦП, індикатор навантаження на купу                     |

### `/dashboard/providers` (Стан провайдерів)

Інформаційна панель для кожного провайдера:

| Стовпець   | Опис                                                             |
| ---------- | ---------------------------------------------------------------- |
| Провайдер  | Ідентифікатор провайдера + відображуване ім’я                    |
| Стан       | Зелений/жовтий/червоний стан                                     |
| Запобіжник | Відкритий/закритий/напіввідкритий стан                           |
| З’єднання  | Кількість з’єднань, останнє оновлення                            |
| Моделі     | Доступні моделі, стан кожної моделі                              |
| Вартість   | Вартість за сьогодні, тенденція за 7 днів                        |
| Помилки    | Кількість помилок за останні 24 год, найпоширеніший клас помилок |

Натисніть на провайдера, щоб переглянути:

- Останні запити з деталізацією затримки
- Оцінки стану кожного з’єднання
- Блокування для кожної моделі
- Рекомендації автопілота

### `/dashboard/quota` (Відстеження квот)

Для кожного ключа API:

- Поточне використання порівняно з лімітом (індикатор прогресу)
- Тенденція квоти (графік за 30 днів)
- Час наступного скидання
- Історія сповіщень

### `/dashboard/combos` (Стан комбінацій)

Для кожної комбінації:

- Стратегія + цільові сервіси
- Стан кожного цільового сервісу
- Останні події перемикання на резерв
- Частка успішних запитів (24 год, 7 дн., 30 дн.)

## API перевірки стану

OmniRoute надає **дві** HTTP-точки перевірки стану. Вони не є взаємозамінними для оркестраторів.

| Шлях                         | Призначення                                                                         | Навантаження                                  | Використання                                                                                   |
| ---------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `GET /healthz`               | Перевірка активності/готовності життєвого циклу (`ok` / `starting` / `stopping`)    | Мінімальне (лише прапорець фази)              | **Готовність** Kubernetes; м’яка перевірка **активності**, якщо необхідно використовувати HTTP |
| `GET /api/monitoring/health` | Поглиблене зведення системи й провайдерів (БД, купа, кількість записів каталогу, …) | Високе (синхронна робота з БД / моніторингом) | Панелі моніторингу, поглиблені blackbox-перевірки, вбудована перевірка стану Docker            |

> **Примітка:** Матриці стану провайдерів, проблеми автопілота, монітори квот, стан токенів і докладні відомості про затримку, що виходять за межі `/api/monitoring/health`, доступні через **інструмент MCP** `observability_snapshot` або сторінки **панелі моніторингу** — окремих REST-маршрутів для них немає.

Обидва маршрути виконуються в **тому самому циклі подій Node**, що й обробка запитів. Шлях із високим навантаженням на CPU (робота з великим каталогом `GET /v1/models`, стиснення довгого контексту / підрахунок токенів) може затримати **всі** HTTP-обробники, включно з `/healthz`. Зайнятий цикл подій ≠ непрацюючий процес. Краще усунути причину надмірного навантаження; налаштування проб лише зменшує кількість помилкових завершень процесу.

### Полегшена проба для оркестратора

```bash
GET /healthz
# або HEAD /healthz
```

- **200** + тіло `ok`, коли фаза життєвого циклу сервера готова
- **503** + `starting` / `stopping` під час запуску або завершення роботи
- Реалізація: `src/app/healthz/route.ts` (без перевірки зв’язку з БД)

```bash

```

#### `credentialHealth`: кеш проб і `test_status` у SQLite

`GET /api/monitoring/health` → `credentialHealth` — це **показник кешу проб у пам’яті**,
а не актуальний дамп `provider_connections.test_status`. Після #12532 шлях
обробки запиту зчитує лише `getCachedCredentialHealthSummary()`; фонові проби
оновлюють кеш поза циклом подій.

| Рівень                          | Де                                                                    | Що це означає                                                                                                                                                                                                     |
| ------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Показник кешу проб              | `credentialHealth.total` / `healthy` / `failed` / `unknown` / `stale` | Останні результати проб стану облікових даних, які досі зберігаються в пам’яті процесу. `source` завжди має значення `probe-cache`.                                                                               |
| Відомості про невдалі з’єднання | `credentialHealth.failedConnections`                                  | Наявні **лише коли `failed > 0`**. Обмежений список рядків кешу зі `status=error` (`connectionId`, `status`, очищені `lastError` / `lastErrorType`). `failedOmitted` установлюється, коли список було обмежено.   |
| Закріплений стан SQLite         | `credentialHealth.staleDbNonOkCount`                                  | Кількість **активних** (`is_active=1`) рядків з’єднань, у яких збережений `test_status` має відоме значення, відмінне від `ok` (`error`, `expired`, `credits_exhausted`, `banned`, `deactivated`, `unavailable`). |

Ці два рівні можуть навмисно не збігатися:

- Показник `failed=0`, тоді як `staleDbNonOkCount>0` — у SQLite досі зберігається
  закріплений `test_status` (наприклад, `expired` або `credits_exhausted`), який
  останній знімок кешу проб не враховує як `status=error`.
- Показник `failed>0`, тоді як SQLite указує на нормальний стан — нещодавня проба
  завершилася невдало та була кешована; рядок БД ще не оновлено або його було
  очищено пізніше.

Не створюйте сповіщення лише на основі `provider_connections.test_status` під час
збирання даних із цієї кінцевої точки. Використовуйте `failed` +
`failedConnections` для поточних невдалих проб, а `staleDbNonOkCount` — коли
потрібна кількість збережених закріплених станів.

### Рекомендації щодо проб Kubernetes

OmniRoute — це **єдиний процес Node** (один цикл подій). Стандартна перевірка Docker `HEALTHCHECK` використовує полегшений маршрут `/healthz`. `/api/monitoring/health` є **надто ресурсомістким** для інтервалів перевірки активності kubelet.

| Проба                          | Рекомендована ціль                                                                | Примітки                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Запуск**                     | HTTP `GET /healthz` із великим `failureThreshold` (або тривалим `startPeriod`)    | Холодний запуск і міграція SQLite можуть тривати понад кілька секунд                                                                                                                                                                                                                                                                                                                                               |
| **Готовність**                 | HTTP `GET /healthz`                                                               | Стан життєвого циклу `ok` / `starting` / `stopping` (200 проти 503). Перевірка все одно нестабільна, якщо цикл заблокований навантаженням на CPU. **Відповідь 200 через кілька секунд не означає справний стан** (#10303) — це означає, що цикл подій був позбавлений ресурсів ще до запуску обробника, який повертає 3 байти                                                                                      |
| **Життєздатність**             | HTTP `GET /livez` **або TCP** на основному порту сервісу (`PORT`, типово `20128`) | `/livez` перевіряє лише роботу процесу (завжди повертає 200, якщо обробник запускається). Він усе одно використовує той самий цикл подій — зайнятий ≠ мертвий, і виявляє виснаження циклу подій (#10303) не краще за TCP. Віддавайте перевагу **TCP**, якщо HTTP-проби перевищують час очікування під навантаженням каталогу/стиснення; у будь-якому разі **не** завершуйте pod через короткі затримки циклу подій |
| **Поглиблена перевірка стану** | `GET /api/monitoring/health` із зовнішнього засобу перевірки                      | Не призначено для `livenessProbe` kubelet або `readinessProbe` із жорсткими обмеженнями                                                                                                                                                                                                                                                                                                                            |

Приклад конфігурації (адаптуйте порогові значення до навантаження під час холодного запуску та стиснення):

```yaml
ports:
  - name: http
    containerPort: 20128
startupProbe:
  httpGet:
    path: /healthz
    port: http
  failureThreshold: 30
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 6
livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
  # Під час затримки циклу подій HTTP-запит до /livez усе одно може перевищити
  # час очікування. TCP — консервативна альтернатива:
  # tcpSocket:
  #   port: http
```

**Не** спрямовуйте перевірку **життєздатності** kubelet на `/api/monitoring/health`. Цей шлях виконує реальну роботу з БД і моніторингом та даватиме хибнопозитивні результати під навантаженням.

Пов’язані матеріали: [#10052](https://github.com/diegosouzapw/OmniRoute/issues/10052) (проби, коли цикл подій зайнятий), [#9685](https://github.com/diegosouzapw/OmniRoute/issues/9685) / [#10055](https://github.com/diegosouzapw/OmniRoute/pull/10055) (розрахунок цін каталогу, що захоплює ресурси), [#10117](https://github.com/diegosouzapw/OmniRoute/issues/10117) (підрахунок токенів під час стиснення, що захоплює ресурси).

### Необов’язкова робота під час обробки запитів (пам’ять, навички, оновлення токенів)

Видобування даних із пам’яті, додавання навичок і оновлення токенів OAuth використовують **основний цикл подій Node** разом із `/healthz`. Це функції, які вмикаються на панелі керування (`memoryEnabled`, `skillsEnabled`), а не пул робочих процесів. Див. [Середовище — вартість для циклу подій](../reference/ENVIRONMENT.md#event-loop-cost-of-memory-skills-and-token-refresh-10349).

## Автопілот стану провайдерів

Модуль `providerHealthAutopilot.ts` — це **система самовідновлення**, яка:

1. Виявляє проблеми провайдерів (розімкнений автоматичний вимикач, періоди очікування, блокування, попередження про квоту)
2. Формує **рекомендовані дії** для їх усунення
3. За потреби **автоматично виконує** дії з низьким рівнем ризику

### Типи виявлених проблем

| Тип проблеми                 | Серйозність  | Приклад умови                                               |
| ---------------------------- | ------------ | ----------------------------------------------------------- |
| `provider_circuit_open`      | критична     | Автоматичний вимикач розімкнений після 5 помилок            |
| `provider_circuit_half_open` | попередження | Автоматичний вимикач перевіряє відновлення                  |
| `connection_cooldown`        | попередження | З’єднання в періоді очікування після 429                    |
| `stale_connection_error`     | попередження | Останнє оновлення завершилося помилкою понад 30 хвилин тому |
| `terminal_connection_error`  | критична     | OAuth відкликано, ключ недійсний                            |
| `inactive_connection`        | інформаційна | З’єднання вимкнено в налаштуваннях                          |
| `model_lockout`              | попередження | Певна модель перебуває на карантині                         |
| `quota_monitor_warning`      | попередження | Використано понад 80% квоти                                 |

### Типи сформованих дій

| Дія                            | Ризик    | Опис                                          |
| ------------------------------ | -------- | --------------------------------------------- |
| `clear_provider_breaker`       | середній | Скинути автоматичний вимикач у замкнений стан |
| `clear_connection_cooldown`    | низький  | Зняти період очікування зі з’єднання          |
| `clear_stale_connection_error` | низький  | Очистити прапорець застарілої помилки         |
| `clear_model_lockout`          | низький  | Повторно ввімкнути модель на карантині        |
| `reactivate_connection`        | середній | Повторно ввімкнути деактивоване з’єднання     |
| `deactivate_connection`        | високий  | Вимкнути проблемне з’єднання                  |

### API

> **Кінцева точка REST відсутня.** Дані про проблеми автопілота доступні через інструмент MCP `observability_snapshot` або інформаційну панель. Автопілот працює всередині системи; його поведінка налаштовується через базу даних налаштувань (поле `autopilotMode` для кожного з’єднання), а не через змінні середовища — `grep -rn` для змінної середовища режиму автопілота не повертає жодних збігів.

### Режим автопілота

За замовчуванням автопілот працює в **ручному режимі** — він виявляє проблеми та формує рекомендовані дії, але не застосовує їх автоматично. Дії можна застосовувати через інформаційну панель.

## Автопілот стану комбінацій

`comboHealthAutopilot.ts` — це **спеціалізований для комбінацій** аналог автопілота провайдерів. Він:

- Виявляє несправні комбінації
- Рекомендує змінити порядок цілей
- Пропонує вимкнути несправні цілі
- Автоматично видаляє недоступні цілі після N помилок

### Приклади проблем із комбінаціями

```
Комбінація "always-on" (стратегія пріоритету)
├─ Ціль 1: openai/gpt-5 (справна)
├─ Ціль 2: anthropic/claude-opus-4-6 (⚠️ модель заблокована до 14:00)
└─ Ціль 3: kiro/claude-sonnet-4-5 (справна)

Рекомендована дія: змінити порядок — перемістити kiro вище за anthropic до завершення блокування
```

## Монітори квот

`observability.ts` надає **монітори квот для кожного сеансу** для провайдерів із підпискою (Claude Code, Codex, GitHub Copilot):

```ts
interface QuotaMonitorSnapshot {
  sessionId: string;
  provider: string;
  accountId: string;
  status: "starting" | "idle" | "healthy" | "warning" | "exhausted" | "error";
  lastQuotaPercent: number | null; // 0-100
  lastQuotaUsed: number | null;
  lastQuotaTotal: number | null;
  lastResetAt: string | null;
  nextPollAt: string | null;
  totalPolls: number;
  totalAlerts: number;
  consecutiveFailures: number;
}
```

### Значення статусів

| Статус      | Коли                            | Дія в інтерфейсі                                           |
| ----------- | ------------------------------- | ---------------------------------------------------------- |
| `starting`  | Триває початкове опитування     | Індикатор завантаження                                     |
| `idle`      | Немає нещодавньої активності    | Приховано з інформаційної панелі                           |
| `healthy`   | Залишилося понад 50% квоти      | Зелена крапка                                              |
| `warning`   | Залишилося менш ніж 50% квоти   | Жовте попередження                                         |
| `exhausted` | Квота = 0%                      | Червоне блокування, маршрутизація до наступного провайдера |
| `error`     | Опитування завершилося помилкою | Червона крапка, незабаром повторити спробу                 |

### API

> **Кінцева точка REST відсутня.** Дані монітора квот доступні через інструмент MCP `observability_snapshot` або інформаційну панель.

## Перевірка стану токенів

Постачальники OAuth (Claude Code, GitHub Copilot, Cursor) потребують **періодичного оновлення токенів**. `src/lib/tokenHealthCheck.ts` запускає фоновий планувальник:

- **Такт перевірки**: кожні 60 секунд (перевірка в `TICK_MS = 60 * 1000` у `src/lib/tokenHealthCheck.ts:30`)
- **Інтервал перевірки стану окремого підключення**: за замовчуванням 60 хвилин (`DEFAULT_HEALTH_CHECK_INTERVAL_MIN = 60`); налаштовується через базу даних налаштувань
- **Превентивне оновлення за кодом 401**: обробляється перехоплювачем окремого підключення

### Статус стану токена

```ts
interface TokenHealth {
  connectionId: string;
  provider: string;
  status: "valid" | "expiring_soon" | "expired" | "refresh_failed";
  expiresAt: string;
  lastRefresh: string;
  nextRefresh: string;
  consecutiveFailures: number;
}
```

### Конфігурація

Конфігурація перевірки стану токенів обробляється внутрішньо файлом `tokenHealthCheck.ts`.

### Стан токенів

> **Кінцева точка REST відсутня.** Дані про стан токенів доступні через панель керування або інструмент MCP `observability_snapshot`.

## Сповіщення

### Вбудовані канали

OmniRoute підтримує **3 канали сповіщень**:

| Канал                  | Налаштування     | Варіант використання              |
| ---------------------- | ---------------- | --------------------------------- |
| Банер панелі керування | Завжди ввімкнено | Сповіщення в застосунку           |
| Вебхук                 | Налаштувати URL  | Slack, Discord, PagerDuty         |
| Журнал                 | За замовчуванням | Для зовнішньої агрегації журналів |

### Конфігурація вебхука

> **Примітка:** Конфігурація сповіщень через вебхук виконується на сторінці налаштувань панелі керування. У користувацькому інтерфейсі налаштувань можна задати URL вебхука, фільтрацію подій і персоналізацію корисного навантаження.

### Типи сповіщень

| Сповіщення                   | Коли                                                       | Рівень серйозності за замовчуванням |
| ---------------------------- | ---------------------------------------------------------- | ----------------------------------- |
| `provider_circuit_open`      | Контур відкривається                                       | критичний                           |
| `provider_circuit_half_open` | Контур тестує відновлення                                  | інформаційний                       |
| `quota_warning`              | Використано понад 80% квоти                                | попередження                        |
| `quota_exhausted`            | Використано 100% квоти                                     | критичний                           |
| `token_refresh_failed`       | 3+ послідовні невдалі оновлення                            | попередження                        |
| `token_expired`              | Термін дії токена минув                                    | критичний                           |
| `combo_target_unhealthy`     | Комбінована ціль перебуває в режимі очікування понад 1 год | попередження                        |
| `db_integrity_warning`       | Кількість порушень FK > 0                                  | попередження                        |
| `heap_pressure`              | Використання купи > 80% порогового значення                | попередження                        |

## Рецепти налаштування сповіщень

### Slack

> **Примітка:** Сповіщення через вебхуки налаштовуються на сторінці «Налаштування» панелі керування — окремих змінних середовища для вебхуків немає (`grep -rn` не повертає жодних збігів). URL вебхука, фільтрацію подій і налаштування корисного навантаження дивіться в інтерфейсі «Налаштування».

### Discord

> Сповіщення через вебхуки налаштовуються в тому самому інтерфейсі «Налаштування», що й для Slack. Discord приймає корисне навантаження JSON тієї самої структури.

### PagerDuty

> Сповіщення через вебхуки налаштовуються в тому самому інтерфейсі «Налаштування». Ключі маршрутизації PagerDuty Events API v2 налаштовуються в інтерфейсі «Налаштування».

### Власний вебхук (JSON)

> Підійде будь-яка кінцева точка HTTP, яка приймає POST із тілом JSON. Налаштуйте URL в інтерфейсі «Налаштування».

## Усунення несправностей

### «Постачальник позначений як справний, але запити не виконуються»

1. Перевірте **проблеми автопілота** — можливо, модель заблоковано
2. Перегляньте **недавні помилки**, щоб знайти конкретний клас помилки
3. Спробуйте **перевірку підключення** в картці постачальника
4. Перевірте, чи не застосовує постачальник **обмеження частоти запитів на своєму боці** (локально цього не видно)

### «Квота позначена як доступна, але я бачу помилки 429»

- Код 429 означає, що, за даними постачальника, ви вичерпали свою квоту
- Дані відстеження квоти OmniRoute можуть бути **застарілими** — актуальні дані зберігаються на боці постачальника
- Дані квоти автоматично оновлюються внутрішнім засобом моніторингу квоти

### «Комбінація не працює, але всі цільові ресурси виглядають справними»

- Перевірте панель **стану комбінації** на наявність проблем із порядком цільових ресурсів
- Перегляньте **події резервного перемикання** — можливо, комбінація надто швидко вичерпує варіанти
- Переконайтеся, що **стратегія** відповідає вашому сценарію використання (пріоритет, циклічний перебір або автоматичний режим)

### «Перевірка стану бази даних завершується помилкою»

- Виконайте `sqlite3 ~/.omniroute/storage.sqlite "PRAGMA integrity_check;"`
- Якщо результат — «ok», це хибна тривога: перевірка стану надто сувора
- Якщо результат інший — **зупиніть OmniRoute** і дотримуйтеся [посібника з аварійного відновлення](./DATABASE_GUIDE.md#disaster-recovery)

### «Навантаження на купу пам’яті критичне»

```bash
# Перевірте поточний стан купи
node -e "console.log(process.memoryUsage())"

# Запустіть збирання сміття вручну (якщо використовується --expose-gc)
node --expose-gc -e "global.gc(); console.log(process.memoryUsage())"

# Зменште кількість одночасних запитів (налаштовується на сторінці «Налаштування» панелі керування, а не через змінну середовища)
# Змінної середовища `MAX_CONCURRENT_REQUESTS` немає — налаштуйте цей параметр у «Налаштування» → «Паралельність».
```
