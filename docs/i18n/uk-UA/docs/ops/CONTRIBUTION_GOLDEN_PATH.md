Скористайтеся цим посібником, щоб вибрати найменший надійний цикл розробки для pull request. Він не
замінює наведені нижче документи з архітектури та безпеки для окремих областей; він пов’язує кожен поширений
тип зміни з його контрактами, цільовими перевірками та покриттям CI.

## Шлях, яким проходить кожна зміна

1. **Виберіть базову гілку до початку редагування.** Знайдіть найновішу активну гілку `release/v*` і створіть гілку від
   її вершини. Спрямовуйте зміни до цієї гілки, а не до `main`. Якщо діє заморожування релізу, не спрямовуйте зміни до замороженої
   гілки; використовуйте наступний активний цикл, описаний у
   [Моделі розгалуження та релізів](BRANCHING_MODEL.md).
2. **Назвіть контракти.** Визначте кожен каталог, схему, згенерований артефакт, публічний API або користувацький
   інтерфейс, на який впливає зміна. У таблиці нижче наведено мінімальний початковий набір.
3. **Напишіть або оновіть цільові тести.** Зміни робочого коду в `src/`, `open-sse/`, `electron/` або
   `bin/` потребують автоматизованого тесту в тому самому PR. Запустіть найменший набір тестових файлів, що підтверджує
   потрібну поведінку, а потім — перелічені цільові перевірки.
4. **Дозвольте CI виконати широку матрицю.** Повні сегменти модульних тестів, Vitest, контроль порога покриття та
   робоче збирання виконуються для PR. Запускайте широкий набір тестів локально лише тоді, коли збій цільової перевірки вказує на
   ширший вплив або коли зміна охоплює кілька підсистем.
5. **Узгодьте зміни перед перевіркою.** Отримайте активну базову гілку, перегляньте її нові коміти та різницю ваших змін відносно
   неї, а потім виконайте rebase або merge базової гілки відповідно до робочого процесу для контриб’юторів. Розв’язуйте конфлікти згенерованих файлів
   і каталогів у їхньому джерелі, повторно генеруйте їх, перезапускайте цільовий цикл і переконайтеся, що
   PR усе ще спрямовано до активної релізної гілки.
6. **Зафіксуйте підтвердження.** У шаблоні PR перелічіть виконані команди, усі додані або змінені тестові файли,
   міграції чи прапорці функцій, а також усі перевірки лише в CI, які ще очікують виконання.

## Рекомендовані шляхи за типом зміни

Наведені нижче команди є мінімальними цільовими перевірками, а не дозволом пропустити тест, що безпосередньо охоплює
змінену вами поведінку.

### Провайдер

**Контракти**

- Визначення провайдера в `src/shared/constants/providers/` та його композиція в
  `src/shared/constants/providers.ts`.
- Моделі й можливості в `open-sse/config/providerRegistry.ts` або у винесених із нього файлах реєстру.
- Вибір виконавця/перетворювача, конфігурація OAuth або ключа API, ресурси панелі керування та згенерована
  довідка провайдера, коли це застосовно.
- Публічні облікові дані мають використовувати `resolvePublicCred()`; відповіді з помилками мають використовувати спільні допоміжні засоби
  санітизації помилок. Див. `docs/security/PUBLIC_CREDS.md` (git; не компілюється до `/docs`) і
  [Санітизація помилок](../security/ERROR_SANITIZATION.md).

**Цільовий цикл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # коли каталог змінюється; закомітьте згенеровану різницю
npm run lint
```

Також протестуйте кожну порушену групу запитів: чат, Responses, зображення, вбудовування, аудіо чи відео.
Розглядайте різниці у згенерованому каталозі та еталонних даних як зміни контрактів; не приймайте їх без перевірки.

### Маршрутизація

**Контракти**

- Публічні значення стратегій і метадані інтерфейсу в `src/shared/constants/routingStrategies.ts`.
- Диспетчеризація та впорядкування в `open-sse/services/combo.ts` і `open-sse/services/combo/`.
- Схеми комбінацій, збереження, стан відмовостійкості, можливості моделей і елементи керування API/інтерфейсу.
- [Рушій Auto-Combo](../routing/AUTO-COMBO.md) і документація з відмовостійкості, коли змінюється поведінка.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # зміни стратегії або диспетчеризації
npm run check:known-symbols      # зміни реєстрації стратегії
npm run lint
```

Локально використовуйте детерміновані тести з імітованими зовнішніми сервісами. Перевірки працездатності комбінацій із реальними сервісами потребують облікових даних і
виконуються вручну, а не замінюють CI.

### UI / UX

**Контракти**

- Маршрут/сторінка Next.js і межі спільних компонентів у `src/app/` та
  `src/shared/components/`.
- Форми відповідей API, стани завантаження/відсутності даних/помилок, поведінка клавіатури та засобів читання з екрана,
  адаптивне компонування, теми й розширення локалей.
- Англійські вихідні рядки інтерфейсу в `src/i18n/messages/en.json`; не додавайте новий видимий користувачам текст безпосередньо в код.

**Цільовий цикл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Запустіть застосунок для змін взаємодії або візуального оформлення та перевірте як вузькі, так і широкі області перегляду. CI запускає
робоче збирання та ширші набори тестів; візуальна поведінка все одно потребує цільової перевірки компонента, Playwright
або задокументованої ручної перевірки, що відповідає зміні.

### i18n

**Контракти**

- `src/i18n/messages/en.json` є джерелом інтерфейсу; `config/i18n.json` є джерелом локалей.
- Каталоги CLI зберігаються окремо в `bin/cli/locales/`.
- Зберігайте заповнювачі й теги ICU без змін. Не перекладайте назви продуктів/провайдерів/моделей,
  назви протоколів і заголовків, команди, ідентифікатори коду/JSON, URL-адреси, змінні середовища або
  захищені терміни, як-от `OmniRoute`, `OAuth`, `MCP` і `A2A`. Поточний вихідний список міститься в
  `scripts/i18n/glossary/protected-terms.json`.

**Цільовий цикл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # коли змінюються рядки/каталоги CLI
npm run lint
```

Це настанови для наявної системи, а не запрошення розширювати її інструментарій або модель ключів.
Зберігайте зміни i18n точковими, поки проєктується система на заміну. Не запускайте команди перекладу,
які звертаються до зовнішніх сервісів, якщо завдання явно не потребує згенерованих перекладів і
ви не переглянули отриману різницю.

### CLI

**Контракти**

- Публічні команди та прапорці в `bin/cli/`, згенеровані команди API, коди завершення, stdout/stderr і
  структури виводу JSON, поведінка конфігурації/середовища та файли пакета.
- Рядки CLI, видимі користувачеві, мають використовувати шар i18n CLI, а каталоги `en`/`pt-BR` повинні залишатися узгодженими.
- Зберігайте Node як підтримуване середовище виконання та дотримуйтеся опублікованого контракту бінарного файла.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # зміни згенерованого/зібраного CLI
npm run check:pack-policy     # зміни поверхні пакета
npm run lint
```

Використовуйте точну команду в тимчасовому каталозі даних, якщо поведінка залежить від розбору, файлів або
статусу завершення. CI виконує ширші перевірки артефактів пакета та екосистеми.

### База даних

**Контракти**

- Доменні модулі в `src/lib/db/`; імпортуйте конкретні модулі безпосередньо (старий шар повторного експорту `localDb.ts` було видалено).
- Нумеровані, ідемпотентні міграції SQL у `src/lib/db/migrations/`, безпека транзакцій, поведінка
  оновлення, індекси та кожен викликач, на який впливає схема.
- Маршрути й обробники ніколи не виконують необроблений SQL безпосередньо.

**Цільовий цикл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Під час додавання міграції тестуйте як нову базу даних, так і оновлення з попередньої схеми. Тести бази даних
мають закривати дескриптори та викликати `resetDbInstance()` під час очищення. Запускайте `npm run test:bun:db`, лише коли
змінюється експериментальний шлях адаптера Bun; Node залишається авторитетним середовищем.

### Збирання / розгортання

**Контракти**

- Кореневий маніфест і маніфести робочих просторів/файл блокування, `scripts/build/`, автономне компонування Next.js, вміст
  пакета `dist/`, метадані платформи Electron, робочі процеси CI та контрольні маркери розгортання.
- Підтримувані діапазони Node і дозволене використання Bun, зазначене в `CLAUDE.md`, мають залишатися незмінними.
- Артефакти збирання не відстежуються; застосовуються політики щодо залежностей, ліцензій, робочих процесів і пакетів.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # зміни залежностей або файла блокування
npm run check:pack-policy      # зміни поверхні опублікованого пакета
npm run lint
```

Використовуйте `npm run build` локально, лише якщо зміна впливає на компіляцію, автономне компонування, ресурси
або пакування середовища виконання. Використовуйте `npm run build:release` лише для перевірки випуску/розгортання. Збирання в CI є
остаточним кросплатформним сигналом; платформозалежні зміни Electron потребують відповідного цільового збирання
або підтвердження димового тестування.

## Локальний цикл кандидата

Тести вихідного коду не можуть довести, що запакований артефакт запускається: помилки у списках пакування, скорочених залежностях і нативних бінарних файлах проявляються лише після встановлення та запуску tarball. `npm run dev:candidate` (`scripts/dev/candidate.mjs`) — це локальна частина процесу одноразового збирання / перевірки / просування з RFC #8084: команда збирає одного кандидата, перевіряє саме цей артефакт, просуває його шляхом перейменування каталогів і відкочує, якщо перевірка працездатності просунутого слота завершується невдало.

```bash
npm run dev:candidate -- run --dry-run --json  # вивести план, нічого не змінювати
npm run dev:candidate -- run                   # зібрати + перевірити + просунути, автоматичний відкіт
npm run dev:candidate -- build                 # npm pack + встановити в _artifacts/candidate/<id>/
npm run dev:candidate -- validate --id <id>    # запустити на вільному порту, /api/health + /v1/models
npm run dev:candidate -- promote --id <id>     # <id> → current, current → previous
npm run dev:candidate -- rollback              # поміняти місцями current і previous
npm run dev:candidate -- run --from-tarball <file.tgz>  # повторно використати tarball, зібраний деінде (CI)
```

- **Збирайте один раз.** `build` пакує поточне дерево (для цього потрібен `dist/server.js`, тому спочатку виконайте `npm run build:release`) або копіює `--from-tarball`, а потім встановлює tarball в ізольований префікс npm, оскільки tarball не містить `node_modules`. Ідентифікатором є короткий sha `HEAD` (`-dirty`, якщо дерево містить локальні зміни) або `tgz-<sha256>` для tarball. Уже зібраний незмінений ідентифікатор використовується повторно замість повторного збирання; щоб перебудувати його, передайте `--force`.
- **Перевіряйте пакет, а не вихідний код.** `validate` запускає встановлений CLI (`serve --port <free port>`) із новим `DATA_DIR=<candidate>/data`, фіктивними секретами та видаленими із середовища оператора значеннями `OMNIROUTE_API_KEY`, `STORAGE_ENCRYPTION_KEY` і `INITIAL_PASSWORD`, щоб перевірити режим loopback без ключів для нового встановлення. Команда очікує, доки `GET /api/health` поверне 200, вимагає, щоб `GET /v1/models` повернув 200, зупиняє групу процесів і записує результат у `validation.json` разом із хешем tarball.
- **Просувайте той самий артефакт.** `promote` відхиляє кандидата без успішної перевірки для поточного хешу його tarball. Активний слот за замовчуванням — `_artifacts/candidate/current`; `--target <dir>` вибирає інший каталог у тій самій файловій системі, а його попереднім слотом є `<dir>.previous`. Кожне перейменування є атомарним, а в разі часткового збою вже виконані перейменування скасовуються.
- **Виконуйте відкіт.** `run` повторно перевіряє просунутий слот і в разі невдалої перевірки міняє `current` та `previous` місцями. Кандидат, який не пройшов першу перевірку, ніколи не просувається.

Усе записується в ігнорований Git каталог `_artifacts/candidate/`; наявне встановлення OmniRoute та його каталог даних ніколи не змінюються. Просунутий CLI розташований за шляхом `_artifacts/candidate/current/prefix/bin/omniroute`; під час використання запускайте його з власним `DATA_DIR`. Коди завершення: `0` — успіх, `1` — невдала перевірка або просування, `2` — помилка використання або відсутня збірка.

## Локальний цикл порівняно з CI

| Запускати локально для кожного патча                                                                 | CI надає загальну картину                                                     |
| ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Прямі тести поведінки та наведені вище перевірки категорій                                           | Розподілений повний набір модульних і послідовних тестів                      |
| `npm run lint`                                                                                       | Набори тестів Vitest і порогові перевірки покриття/якості                     |
| Перевірка типів або збірка лише тоді, коли цього вимагає відповідний контракт                        | Продакшн-збірка, перевірки безпеки, документації, залежностей і політик PR    |
| Ручні інтерактивні перевірки/перевірки наживо, лише якщо автоматизація не може підтвердити поведінку | Міжзадачні інтеграційні та платформні перевірки, налаштовані робочим процесом |

Успішний цільовий цикл є свідченням щодо зміненого контракту, а не доказом того, що непов’язані перевірки CI
будуть успішними. Водночас не змушуйте кожне локальне редагування чекати на повну матрицю репозиторію.

## Контрольний список узгодження

Перед запитом на перевірку:

- Переконайтеся, що базовою гілкою PR досі є найновіша активна гілка `release/v*`.
- Отримайте зміни з цієї базової гілки та перегляньте коміти, додані після створення вашої гілки.
- Перегляньте `git diff <active-base>...HEAD` на наявність випадкових або згенерованих змін.
- Вирішуйте конфлікти в каталогах і згенерованих документах, оновлюючи джерело та повторно генеруючи результат.
- Після узгодження повторно запустіть усі цільові тести/перевірки, зазначені в описі PR.
- Ніколи не послаблюйте перевірки тверджень і не вилучайте обов’язкові тести лише для того, щоб відповідати зміненій базовій гілці.

Правила заморожування релізу та зміни цільової гілки наведено в документі
[Модель розгалуження та випусків](BRANCHING_MODEL.md). Повний перелік перевірок CI наведено в документі
[Довідник із перевірок якості](../architecture/QUALITY_GATES.md).
