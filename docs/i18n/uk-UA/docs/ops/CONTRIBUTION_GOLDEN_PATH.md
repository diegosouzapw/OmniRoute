Скористайтеся цим посібником, щоб вибрати найменший надійний цикл розробки для pull request. Він не
замінює наведені нижче документи з архітектури та безпеки для конкретних областей; він пов’язує кожен поширений
тип зміни з його контрактами, цільовими перевірками та покриттям CI.

## Шлях, який проходить кожна зміна

1. **Виберіть базову гілку перед редагуванням.** Знайдіть найстаршу активну гілку `release/v*` і створіть свою гілку від
   її вершини. Спрямовуйте зміни до цієї гілки, а не до `main`. Якщо діє заморожування релізу, не спрямовуйте зміни до замороженої
   гілки; використовуйте наступний активний цикл, описаний у
   [Моделі розгалуження та релізів](BRANCHING_MODEL.md).
2. **Назвіть контракти.** Визначте кожен каталог, схему, згенерований артефакт, публічний API або користувацький
   інтерфейс, на який впливає зміна. У таблиці нижче наведено мінімальний початковий набір.
3. **Напишіть або оновіть цільові тести.** Зміни робочого коду в `src/`, `open-sse/`, `electron/` або
   `bin/` потребують автоматизованого тесту в тому самому PR. Запустіть найменший набір тестових файлів, які підтверджують
   поведінку, а потім — перелічені цільові перевірки.
4. **Дозвольте CI виконати широку матрицю.** Повні сегменти модульних тестів, Vitest, контрольний поріг покриття та
   робоче збирання виконуються в PR. Запускайте широкий набір локально лише тоді, коли збій цільової перевірки вказує на
   ширший вплив або коли зміна охоплює кілька підсистем.
5. **Узгодьте зміни перед перевіркою.** Отримайте активну базову гілку, перегляньте її нові коміти та різницю ваших змін
   відносно неї, а потім виконайте rebase або merge базової гілки відповідно до робочого процесу для учасників. Розв’язуйте конфлікти згенерованих файлів
   і каталогів, починаючи з їхнього джерела, повторно генеруйте їх, повторно запускайте цільовий цикл і підтвердьте, що
   PR усе ще спрямовано до активної релізної гілки.
6. **Зафіксуйте підтвердження.** У шаблоні PR перелічіть виконані команди, кожен доданий або змінений тестовий файл,
   міграції чи прапорці функцій, а також усі перевірки, що ще очікують виконання лише в CI.

## Оптимальні шляхи за типом зміни

Наведені нижче команди є мінімальними цільовими перевірками, а не дозволом пропускати тест, який безпосередньо перевіряє
змінену вами поведінку.

### Провайдер

**Контракти**

- Визначення провайдера в `src/shared/constants/providers/` та його композиція в
  `src/shared/constants/providers.ts`.
- Моделі й можливості в `open-sse/config/providerRegistry.ts` або у винесених із нього файлах реєстру.
- Вибір виконавця/транслятора, конфігурація OAuth або API-ключа, ресурси панелі керування та згенерована
  довідка провайдера, де це застосовно.
- Публічні облікові дані мають використовувати `resolvePublicCred()`; відповіді з помилками мають використовувати спільні допоміжні функції
  очищення помилок. Див. `docs/security/PUBLIC_CREDS.md` (git; не компілюється в `/docs`) і
  [Очищення помилок](../security/ERROR_SANITIZATION.md).

**Цільовий цикл**

```bash
npm run check:provider-consistency
npm run check:provider-assets
node --import tsx/esm --test tests/unit/provider-translate-path-golden.test.ts
node --import tsx/esm --test tests/unit/<provider-or-executor>.test.ts
npm run gen:provider-reference   # коли каталог змінюється; закомітьте згенеровану різницю
npm run lint
```

Також перевірте кожне сімейство запитів, якого торкнулися зміни: чат, Responses, зображення, вбудовування, аудіо або відео.
Перевіряйте різниці згенерованого каталогу та еталонних даних як зміни контрактів; не приймайте їх бездумно.

### Маршрутизація

**Контракти**

- Публічні значення стратегій і метадані UI в `src/shared/constants/routingStrategies.ts`.
- Диспетчеризація та впорядкування в `open-sse/services/combo.ts` і `open-sse/services/combo/`.
- Схеми комбінацій, збереження, стан відмовостійкості, можливості моделей та елементи керування API/UI.
- [Рушій Auto-Combo](../routing/AUTO-COMBO.md) і документація з відмовостійкості, коли змінюється поведінка.

**Цільовий цикл**

```bash
node --import tsx/esm --test tests/unit/combo-<behavior>.test.ts
npm run test:combo:matrix        # зміни стратегії або диспетчеризації
npm run check:known-symbols      # зміни реєстрації стратегії
npm run lint
```

Локально використовуйте детерміновані тести з імітацією зовнішніх сервісів. Перевірки працездатності комбінацій із реальними сервісами потребують облікових даних і
виконуються вручну, а не замість CI.

### UI / UX

**Контракти**

- Межі маршруту/сторінки Next.js і спільних компонентів у `src/app/` та
  `src/shared/components/`.
- Форми відповідей API, стани завантаження/відсутності даних/помилки, поведінка клавіатури та засобів читання з екрана,
  адаптивний макет, теми й розширення локалей.
- Англійські початкові рядки UI в `src/i18n/messages/en.json`; не вписуйте новий видимий користувачам текст безпосередньо в код.

**Цільовий цикл**

```bash
node --import tsx --test tests/unit/dashboard/<feature>.test.ts
npx vitest run --config vitest.config.ts tests/unit/ui/<component>.test.tsx
npm run check:dashboard-typecheck
npm run lint
```

Запустіть застосунок для змін взаємодії або візуальних змін і перевірте вузькі та широкі області перегляду. CI виконує
робоче збирання та ширші набори тестів; візуальна поведінка все одно потребує цільового тесту компонента, Playwright
або задокументованої ручної перевірки, що відповідає зміні.

### i18n

**Контракти**

- `src/i18n/messages/en.json` є джерелом UI; `config/i18n.json` є джерелом локалей.
- Каталоги CLI зберігаються окремо в `bin/cli/locales/`.
- Зберігайте заповнювачі й теги ICU без жодних змін. Не перекладайте назви продуктів/провайдерів/моделей,
  назви протоколів і заголовків, команди, ідентифікатори коду/JSON, URL-адреси, змінні середовища або
  захищені терміни, як-от `OmniRoute`, `OAuth`, `MCP` і `A2A`. Поточний вихідний список розташовано в
  `scripts/i18n/glossary/protected-terms.json`.

**Цільовий цикл**

```bash
npm run i18n:sync-ui:dry
npm run i18n:check-ui-coverage
npm run i18n:check-value-drift
npm run i18n:check-glossary
npm run check:cli-i18n          # коли змінюються рядки/каталоги CLI
npm run lint
```

Це настанови для наявної системи, а не запрошення розширювати її інструментарій або модель ключів.
Зберігайте зміни i18n точковими, поки проєктується система на заміну. Не запускайте команди перекладу,
які звертаються до зовнішніх сервісів, якщо завдання явно не потребує згенерованих перекладів і
ви не перевірили отриману різницю.

### CLI

**Контракти**

- Публічні команди та прапорці в `bin/cli/`, згенеровані команди API, коди завершення, stdout/stderr і
  структури виводу JSON, поведінка конфігурації/середовища та файли пакета.
- Рядки CLI, видимі користувачам, мають використовувати шар i18n CLI, а каталоги `en`/`pt-BR` мають залишатися узгодженими.
- Зберігайте Node як підтримуване середовище виконання та дотримуйтеся контракту опублікованого бінарного файла.

**Сфокусований цикл**

```bash
node --import tsx/esm --test tests/unit/cli/<command>.test.ts
npm run check:cli-i18n
npm run build:cli             # зміни згенерованого/зібраного CLI
npm run check:pack-policy     # зміни поверхні пакета
npm run lint
```

Використовуйте точну команду в тимчасовому каталозі даних, якщо поведінка залежить від синтаксичного аналізу, файлів або статусу
завершення. CI виконує ширші перевірки артефактів пакета та екосистеми.

### База даних

**Контракти**

- Доменні модулі в `src/lib/db/`; імпортуйте конкретні модулі безпосередньо (старий шар реекспорту `localDb.ts` видалено).
- Нумеровані ідемпотентні міграції SQL у `src/lib/db/migrations/`, безпечність транзакцій, поведінка під час оновлення,
  індекси та кожен викликач, на який впливає схема.
- Маршрути й обробники ніколи не виконують необроблений SQL безпосередньо.

**Сфокусований цикл**

```bash
npm run check:migration-numbering
npm run check:db-rules
node --import tsx/esm --test tests/unit/db/<domain>.test.ts
node --import tsx/esm --test tests/unit/db/migration-<number>.test.ts
npm run lint
```

Під час додавання міграції тестуйте як нову базу даних, так і оновлення з попередньої схеми. Тести бази даних
мають закривати дескриптори та викликати `resetDbInstance()` під час очищення. Запускайте `npm run test:bun:db` лише тоді, коли
змінюється експериментальний шлях адаптера Bun; Node залишається авторитетним.

### Збирання / розгортання

**Контракти**

- Кореневі маніфести, маніфести робочих просторів і lockfile, `scripts/build/`, автономне компонування Next.js, вміст пакета `dist/`,
  метадані платформ Electron, робочі процеси CI та контрольні маркери розгортання.
- Підтримувані діапазони Node та дозволене використання Bun у `CLAUDE.md` мають залишатися незмінними.
- Артефакти збирання не відстежуються; застосовуються політики залежностей, ліцензій, робочих процесів і пакетів.

**Сфокусований цикл**

```bash
node --import tsx/esm --test tests/unit/build/<behavior>.test.ts
npm run check:build-scope
npm run check:lockfile         # зміни залежностей або lockfile
npm run check:pack-policy      # зміни поверхні опублікованого пакета
npm run lint
```

Використовуйте `npm run build` локально лише тоді, коли зміна впливає на компіляцію, автономне компонування, ресурси
або формування пакета середовища виконання. Використовуйте `npm run build:release` лише для перевірки випуску/розгортання. Збирання в CI
є остаточним кросплатформним сигналом; специфічні для платформи зміни Electron потребують відповідного цільового збирання
або підтвердження за допомогою димового тестування.

## Локальний цикл і CI

| Запускати локально для кожного патча                                                         | CI забезпечує широке охоплення                                               |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Наведені вище прямі тести поведінки та перевірки категорій                                   | Розподілений на сегменти повний набір модульних і послідовних тестів         |
| `npm run lint`                                                                               | Набори тестів Vitest і порогові перевірки покриття та якості                 |
| Перевірка типів або збірка лише тоді, коли цього вимагає змінений контракт                   | Перевірки продакшн-збірки, безпеки, документації, залежностей і PR-політик   |
| Ручна перевірка взаємодії наживо лише тоді, коли автоматизація не може підтвердити поведінку | Налаштовані робочим процесом міжзадачні інтеграційні та платформні перевірки |

Успішний цільовий цикл є свідченням щодо зміненого контракту, а не доказом того, що непов’язані перевірки CI
будуть пройдені. Водночас не змушуйте кожне локальне редагування чекати на повну матрицю перевірок репозиторію.

## Контрольний список узгодження

Перш ніж запитувати перевірку:

- Переконайтеся, що базовою гілкою PR досі є найвища активна гілка `release/v*`.
- Отримайте актуальний стан цієї базової гілки та перегляньте коміти, додані після створення вашої гілки.
- Перегляньте `git diff <active-base>...HEAD` на наявність випадкових або згенерованих змін.
- Розв’язуйте конфлікти в каталогах і згенерованій документації, оновлюючи джерело та повторно генеруючи результат.
- Після узгодження повторно запустіть кожен цільовий тест і кожну перевірку, зазначені в описі PR.
- Ніколи не послаблюйте твердження перевірок і не вилучайте обов’язкові тести лише для відповідності зміненій базовій гілці.
