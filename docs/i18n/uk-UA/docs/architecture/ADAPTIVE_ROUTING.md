Цей документ описує основу адаптивної маршрутизації на основі зворотного зв’язку, додану до
OmniRoute. Вона навмисно невелика: запроваджує типізований канал результатів
маршрутизації, оперативний сигнал якості, що надходить до наявного оцінювача auto-combo,
необов’язковий експортер OpenTelemetry та ендпоінт пояснюваності. Вона **не**
замінює наявний стек стійкості (автоматичний вимикач, затримка повторного підключення,
блокування моделі, матриця стану, автопілот) — вона доповнює його.

## 1. Архітектурний контекст

OmniRoute — це площина даних зі **швидким шляхом запитів** і **площиною
керування/аналітики**. Швидкий шлях має залишатися швидким, ефективним щодо пам’яті, асинхронним, стійким і
передбачуваним. Оцінювання, визначення якості, експерименти та історичний аналіз належать
до площини керування.

```
ШІ-агент / IDE
      │
      ▼
┌─────────────────────┐
│    OmniRoute        │   площина даних (швидка, синхронна, у пам’яті)
│  маршрутизація /    │
│  перемикання після  │
│  відмови            │
│  стан / обмеження   │
│  кеш / потоковість  │
└──────────┬──────────┘
           │ RoutingEvent (без очікування відповіді, ~0.2µs)
           ▼
┌─────────────────────┐
│  Приймачі відгуків  │   площина керування (асинхронна, за можливості)
│  трекер якості      │
│  експортер OTel     │
│  сховище пояснень   │
└──────────┬──────────┘
           ▼  оцінка якості
      оцінювач auto-combo
```

### Що вже було реалізовано (перевірено, не дублюється)

| Концепція                                      | Наявна реалізація                                                                                                          |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Доступність (чи можемо ми надсилати трафік?)   | Автоматичний вимикач (CLOSED/DEGRADED/OPEN/HALF_OPEN, збережений у БД), затримка повторного підключення, блокування моделі |
| Звітування про стан                            | `providerHealthMatrix.ts`, `providerHealthAutopilot.ts`                                                                    |
| Тіньовий трафік                                | `open-sse/services/combo/shadowRouting.ts`                                                                                 |
| Обмеження                                      | `src/lib/guardrails/` (хуки до/після)                                                                                      |
| Точний кеш                                     | `src/lib/semanticCache.ts` (на основі сигнатур)                                                                            |
| Оцінювачі / маршрутизація на основі оцінювання | `src/lib/evals/`, `open-sse/services/evalRouting.ts`                                                                       |
| Пояснюваність рішень combo                     | `open-sse/services/combo/decisionTrace.ts`                                                                                 |
| Події панелі моніторингу в реальному часі      | `src/lib/events/eventBus.ts` (канал сповіщень інтерфейсу, корисні навантаження `unknown`, історія на 100 записів)          |

Рівень подій маршрутизації **не** є повторною реалізацією `eventBus`: ця шина є
каналом сповіщень панелі моніторингу в реальному часі (типізовані _назви подій_, непрозорі
корисні навантаження, споживачі інтерфейсу). `RoutingEvent` — це типізована структура _результату_
(затримка/токени/вартість/результат/причина завершення), яку споживають
приймачі зворотного зв’язку площини керування (трекер якості, експортер OTel, сховище пояснень).

### Чого бракувало (додано тут)

1. **Типізована подія результату маршрутизації та абстракція приймача** (`RoutingEvent` /
   `RoutingEventSink`). `decisionTrace` обмежений combo та працює лише в пам’яті;
   `comboMetrics` — це накопичувальні лічильники; `call_logs` — необроблене асинхронне сховище.
   Жоден із них не є типізованим каналом результатів на основі приймачів, на який можуть підписатися трекер якості, експортер OTel
   або оцінювач у стилі Future-AGI.
2. **Оперативний сигнал якості** (EWMA) для якості результатів — раніше оцінювач
   опосередковано визначав «якість» лише через статичну відповідність завданню та частоту успішного проходження необов’язкових оцінювань.
3. **Необов’язковий експортер OTel без залежностей**, що використовує семантичні конвенції GenAI.
4. **Ендпоінт пояснюваності**, який повертає фактичні рішення маршрутизації та стан якості.

## 2. Події маршрутизації (основа зворотного зв’язку)

Файли: `open-sse/services/routing/events.ts`, `.../index.ts`

`RoutingEvent` містить лише метадані маршрутизації:

```ts
interface RoutingEvent {
  requestId: string;
  provider: string;
  model: string;
  strategy: string; // "auto" | "priority" | "direct" | ...
  latencyMs: number;
  ttftMs: number | null;
  inputTokens: number | null;
  outputTokens: number | null;
  cost: number | null;
  retries: number;
  fallbackUsed: boolean;
  outcome: RoutingOutcome; // об’єднання дозволених значень
  status: number | null;
  finishReason: string | null;
  connectionId: string | null;
  ts: number;
}
```

`RoutingEventSink` — це аналог трейта `Send+Sync` у TypeScript:

```ts
interface RoutingEventSink {
  readonly name: string;
  record(event: RoutingEvent): void; // має виконуватися за O(1), без синхронного введення-виведення
}
```

Гарячий шлях викликає `emitRoutingEvent(event)` один раз для кожного завершеного запиту
(зворотний виклик завершення потокової передачі, шлях успішного виконання без потокової передачі та
шлях помилки через некоректну відповідь 200 у `handleChatCore`). Диспетчеризація виконується як синхронне розсилання
до зареєстрованих приймачів, але кожен приймач лише додає дані до черги або оновлює стан у пам’яті. **Жодних
синхронних записів до бази даних і жодного мережевого введення-виведення на гарячому шляху.**

Приймачі за замовчуванням:

- `MemoryRoutingEventStore` — обмежений (500) кільцевий буфер із найновішими записами на початку для
  кінцевої точки пояснення.
- Споживач `QualityTracker` — оновлює оцінку якості EWMA.
- `OtlpHttpsEventSink` — необов’язковий; вмикається лише тоді, коли встановлено `OMNIROUTE_OTEL_ENDPOINT`
  (або `OTEL_EXPORTER_OTLP_ENDPOINT`).

### Виміряні накладні витрати (чесне порівняння)

`npm run bench:routing-events` на цій робочій станції (100 тис. ітерацій; операції тривалістю менше мікросекунди
вимірювалися в сукупності у мкс/операцію, оскільки процентилі для окремих операцій нижчі за
роздільну здатність таймера `performance.now()`):

| Сценарій                                         | мкс/операцію | операцій/с |
| ------------------------------------------------ | ------------ | ---------- |
| базовий рівень (лише оцінювання)                 | ~0.045       | ~22 M      |
| базовий рівень + RoutingEvent (2 приймачі)       | ~0.168       | ~5.9 M     |
| базовий рівень + подія + додавання OTel до черги | ~0.163       | ~6.1 M     |
| паралельне виконання (8 перемежованих пакетів)   | ~0.18        | —          |

Різниця між диспетчеризацією подій і базовим оцінюванням становить ~0.12 мкс/запит; приймач OTel
лише додає дані до черги (додавання до буфера за O(1)), не створюючи вимірюваних накладних витрат. Ці показники
залежать від конкретної машини та є відносними — це не гарантія для промислового середовища. Показник v1 «~0.2 мкс»
був сукупною оцінкою; ця методологія відокремлює базове оцінювання
від вартості диспетчеризації подій.

## 3. Сигнал якості (стан постачальника на основі зворотного зв’язку)

Файли: `open-sse/services/routing/quality.ts`

v2 розділяє **операційну** та **семантичну** якість:

- **Операційна** — визначається з гарячого шляху маршрутизації (HTTP 4xx/5xx, помилки
  з’єднання, відповіді 429, некоректні відповіді, переривання потоків, `finish_reason=length`,
  успішні відповіді з нульовим обсягом виведення, EWMA затримки/TTFT). Відповідь 200 НЕ вважається показником семантичної
  якості.
- **Семантична** — фактична цінність згенерованого результату. Створюється ВИКЛЮЧНО
  оцінювачем через `setSemanticQuality()`. Її значення дорівнює `null`, доки оцінювач його не надасть,
  і вона ніколи не впливає на операційну оцінку.

Стан для кожної пари (постачальник, модель) (EWMA + обмежені лічильники):

- `successEwma` — EWMA (α=0.2) успішності результатів.
- `latencyEwma` / `ttftEwma` — EWMA затримки (α=0.1).
- `samples`, `anomalies`, `rateLimited`, `semantic`, `semanticConfidence`.
- `recencyMs` — час, що минув від останнього спостереження моделі.

### Урахування впевненості / кількості вибірок

`confidence = clamp01(samples / 50)`, а оцінка, повернена модулю оцінювання,
зміщується в бік нейтрального середнього значення:

```
score = 0.5 + confidence * (operational - 0.5)
```

Наслідки (підтверджені тестами):

- Холодний постачальник (0 вибірок) отримує оцінку **0.5** — без несправедливого штрафу, але
  не може переважити постачальника з тисячами надійних спостережень.
- Постачальник із 7 випадковими успішними результатами зміщується до 0.5 (і ніколи не домінує завдяки
  оптимістичній ініціалізації).
- Постачальник із 50+ вибірками наближається до своєї справжньої операційної оцінки.
- Погіршення та відновлення відбуваються поступово (EWMA), а один окремий збій
  не руйнує оцінку справного постачальника.

`ProviderQuality` надає `{ operational, semantic, confidence, samples, anomalies,
rateLimited, successEwma, latencyEwmaMs, ttftEwmaMs, recencyMs }`.

Це надходить до модуля оцінювання auto-combo як фактор оцінювання `quality`:

- `ScoringFactors.quality` / `ScoringWeights.quality` у
  `open-sse/services/autoCombo/scoring.ts`.
- `DEFAULT_WEIGHTS`: `health` 0.1905 → 0.1605, `quality` 0.03. Сума залишається рівною 1.0.
- `buildAutoCandidates` заповнює `candidate.quality` даними з трекера; для кандидатів
  без даних за замовчуванням використовується нейтральне значення **0.5** (холодний кандидат не отримує ані
  підсилення, ані штрафу).

Замкнений цикл:

```
RoutingEvent → QualityTracker → getQualityScore → фактор якості auto-combo
      ↑                                                    │
      └────── результат запиту (handleChatCore) ←──────────┘
```

### Жорстке виключення та м’який штраф

Сигнал якості — це лише **м’яка адаптивна перевага**. Жорстке виключення залишається
за наявним стеком відмовостійкості: стан автоматичного вимикача OPEN, вичерпана квота,
помилка автентифікації, блокування моделі — оцінка якості не впливає на жоден із цих випадків.
Постачальник, чия оцінка якості тимчасово знижується, отримує нижчий пріоритет, але ніколи
не вимикається примусово.

## 3b. Канонічні часові метрики потоку (TTFT / ITL)

Файли: `open-sse/utils/streamTiming.ts`

`createStreamTiming()` є єдиною точкою інструментування потокового шляху,
підключеною до `createSSEStream` (`open-sse/utils/stream.ts`):

- `markByte()` — отримано перший фрагмент від upstream-сервісу.
- `markForward()` — перший фрагмент переслано клієнту (використовується для TTFT).
- `markInterrupted()` — тайм-аут/переривання/помилка потоку до коректного завершення.
- `ttft()` = затримка до першого пересланого SSE-фрагмента. **Це НЕ TTFT на рівні токенів** —
  один SSE-фрагмент може містити нуль, один або багато токенів. Це точно задокументовано.
- `avgItlMs()` = середній інтервал між фрагментами (наближена метрика затримки фрагментів для ITL).

TTFT/ITL/стан переривання надходять до `RoutingEvent` (`ttftMs`, `itlMs`) та
експортуються як атрибути спану GenAI/OmniRoute засобом призначення OTel.

## 4. Спостережуваність OpenTelemetry / GenAI

Файли: `open-sse/services/routing/otel.ts`

- Експортер OTLP/HTTP JSON без залежностей (використовує глобальний `fetch`, без
  SDK `@opentelemetry/*`).
- Спани відповідають семантичним конвенціям GenAI (`gen_ai.provider.name`,
  `gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`,
  `gen_ai.completion.finish_reason`, `gen_ai.system`) і містять атрибути
  маршрутизації OmniRoute (результат, статус, ttft, повторні спроби, резервний маршрут).
- `record()` лише додає дані до обмеженого буфера (O(1)); фоновий таймер
  асинхронно скидає їх через `POST {endpoint}/v1/traces`. За перевантаження
  найстаріші події відкидаються (лічильник `dropped`) — зворотний тиск на площину
  даних ніколи не створюється.
- **Вимкнено, якщо не налаштовано.** Має бути задано `OMNIROUTE_OTEL_ENDPOINT` (або
  `OTEL_EXPORTER_OTLP_ENDPOINT`); інакше засіб призначення не реєструється й жоден
  код OTel не виконується.

## 5. Пояснюваність

- `GET /v1/explain/routing` повертає нещодавні `RoutingEvent` (реальні
  рішення, спочатку найновіші) та знімок якості для кожної пари постачальник/модель.
- Автентифікація відповідає `/v1/combos` (Bearer API key або сесія панелі керування;
  анонімний доступ у локальних однокористувацьких розгортаннях із `REQUIRE_API_KEY=false`).
- Трасування окремих викликів на рівні комбінацій залишається доступним через наявний
  `decisionTrace.ts` (заголовок `X-OmniRoute-Combo-Trace`).
- Безпека: події містять лише метадані маршрутизації, але ніколи не містять промптів,
  тіл запитів або облікових даних.

## 6. Інтеграція площини оцінювання (готовність до Future AGI)

OmniRoute розглядає Future AGI (або будь-який засіб оцінювання) як **потенційний
бекенд інтелектуального аналізу/оцінювання, а не залежність**. Точки інтеграції:

- `RoutingEventSink` може асинхронно пересилати події засобу оцінювання.
- `MemoryRoutingEventStore` і знімок якості надають засобу оцінювання необроблений
  потік рішень.
- Майбутній `Evaluator` (детермінований, локальна модель-суддя, HTTP, WASM) споживатиме
  події/трасування та повертатиме `QualityScore`, що надходитиме до того самого
  шляху `getQualityScore`/коефіцієнта якості.
- Наявна маршрутизація на основі оцінювання (`open-sse/services/evalRouting.ts`) уже
  змінює порядок цілей комбінації за часткою успішних результатів `eval_runs`, коли її ввімкнено.

Жодне оцінювання не виконується синхронно на шляху запиту, а шлюз повністю
працює за відсутності засобу оцінювання.

## 7. Підсумковий огляд архітектури

1. **Що залишається на синхронному гарячому шляху?** Маршрутизація/визначення оцінки,
   попередні перевірки захисних обмежень, пошук у кеші та одне розгалуження
   `emitRoutingEvent` (~0.12 мкс понад базовий час визначення оцінки) до засобів
   призначення в пам’яті.
2. **Що перенесено до асинхронного оброблення?** Експорт OTel (таймер + fetch),
   збереження `call_logs`/використання, записи до семантичного кешу; якість
   зберігається в пам’яті й обчислюється за O(1) (асинхронність не потрібна).
3. **Як результат маршрутизації перетворюється на зворотний зв’язок?**
   `handleChatCore` генерує `RoutingEvent` → `QualityTracker` оновлює стан EWMA →
   `getQualityScore` передає дані коефіцієнту `quality` автоматичної комбінації.
4. **Як якість впливає на майбутню маршрутизацію?** Низька оцінка якості зменшує
   зважену оцінку цієї пари постачальник/модель у `scoreAutoTargets`, тому моделі
   з погіршеною якістю поступово отримують нижчий пріоритет і відновлюють його зі
   зростанням їхнього показника EWMA.
5. **Як Future AGI може інтегруватися, не стаючи залежністю?** Через інтерфейс
   `RoutingEventSink` / майбутній адаптер `Evaluator` — без жорстко закодованої
   залежності.
6. **Що відбувається, коли засіб оцінювання недоступний?** Маршрутизація не зазнає
   впливу; для моделей без спостережуваного сигналу якість повертається до
   нейтрального значення (1.0).
7. **Що відбувається, коли телеметрія недоступна?** Засіб призначення OTel просто
   не реєструється; решта рівня маршрутизації працює без змін.
8. **Що відбувається за перевантаження?** Буфер OTel відкидає найстаріші події;
   розмір даних про якість і кільцевого буфера обмежений за конструкцією;
   зворотний тиск відсутній.
9. **Як відновлюється стан постачальника після погіршення?** EWMA повторно збігається
   в міру накопичення успішних результатів; прогрівання зберігає нейтральний статус
   холодних моделей; автоматичний вимикач незалежно відновлюється через пробні
   запити HALF_OPEN.
10. **Які запропоновані можливості навмисно НЕ реалізовано й чому?**
    - Тіньовий трафік / експерименти — уже реалізовано
      (`combo/shadowRouting.ts`); повторно не створювалися.
    - Захисні обмеження — уже реалізовано (`src/lib/guardrails/`); не дублювалися.
    - Семантичний кеш — уже реалізовано (`src/lib/semanticCache.ts`); не
      дублювався.
    - Повноцінна платформа керування експериментами, інструменти для наборів даних,
      платформа оптимізації промптів, векторна БД або обов’язкова зовнішня
      інфраструктура OTel — поза межами компактної площини даних.
    - Структура Rust `RoutingEvent` — площину даних реалізовано на TypeScript;
      тип TS є адаптованим еквівалентом.

## 9. Тести

- `tests/unit/routing-events.test.ts` — нормалізація подій, класифікація
  станів, обмежений кільцевий буфер, розподіл між приймачами + ізоляція.
- `tests/unit/routing-quality.test.ts` — прогрівання EWMA, відновлення після невдачі/успіху,
  штрафи за аномалії, обробка тимчасової помилки 429, знімок стану, скидання.
- `tests/unit/routing-scoring-quality.test.ts` — цілісність ваг, нейтральне
  значення за замовчуванням, ранжування за коефіцієнтом якості.
- `tests/unit/routing-otel.test.ts` — керування ввімкненням, корисне навантаження спану GenAI, асинхронне
  скидання, відкидання за перевантаження.
- `tests/unit/routing-events-concurrency.test.ts` — тисячі подій, обмеженість кільцевого
  буфера, ізоляція приймача, що викидає винятки, перемежовані асинхронні сплески,
  скидання під час вставок.
- `tests/unit/routing-adaptive-e2e.test.ts` — детермінований наскрізний цикл через
  справжній оцінювач `scoreAutoTargets`: справний стан → погіршення → відновлення → короткочасний збій, а також
  сценарії холодного старту та випадково успішного холодного провайдера.
- `tests/unit/stream-timing.test.ts` — TTFT (перший пересланий фрагмент), ITL,
  перший байт порівняно з першим пересиланням, переривання, безпечна обробка пошкоджених/порожніх фрагментів.
