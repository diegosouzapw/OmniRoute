> Практичні примітки для супровідників:
>
> - Кілька жорстко заданих hex-значень, що залишилися, є **навмисними** (завжди темний термінал консолі, обведення SVG у ReactFlow), і їх **НЕ МОЖНА** масово замінювати токенами.
> - «Більша» сітка в запущеному екземплярі означає застарілу збірку, а не проблему в коді — розмір сітки становить 32px, як і на сайті.

## 1. Призначення

Маркетинговий сайт (`viral.omniroute.online`, `why.omniroute.online`, `omniroute.online`) і дашборд продукту мають виглядати як **єдиний продукт**. Сайт уже запозичив свою палітру з дашборда — у його `css/tokens.css` навіть зазначено: _«Палітра відповідає дашборду OmniRoute (src/app/globals.css)»_. Отже, на рівні кольорів вони вже узгоджені приблизно на 80%. Чого бракує дашборду:

1. **Фон у стилі міліметрового паперу**, який сайт використовує на кожній сторінці.
2. Кілька **спільних дизайн-токенів**, які є на сайті, але відсутні в дашборді (шкала радіусів, брендовий градієнт, `surface-2`, моноширинний шрифт).
3. **Узгодженість на рівні компонентів** — низка компонентів дашборда обходить токени теми, використовуючи жорстко задані hex/rgba-значення.

Цей документ містить аналіз і план.

## 2. Принципи

- **Єдине джерело істини = `src/app/globals.css`.** Сайт наслідує дашборд, а не навпаки. Нові токени спочатку додаються до `globals.css`.
- **Токени замість літералів.** Компоненти використовують семантичні токени (`bg-surface`, `text-primary`, `border-border`), а не необроблені значення `#hex`.
- **Ненав’язливо, а не кричуще.** Сітка — це ледь помітні шпалери позаду контенту; вона ніколи не повинна знижувати контрастність тексту або конкурувати з інтерфейсом.
- **З урахуванням теми.** Усе працює як у `.dark` (фірмовому вигляді продукту), так і у світлій темі.
- **Точкове впровадження.** Спочатку випускаємо сітку й токени (низький ризик, висока помітність), а потім поетапно впорядковуємо компоненти.

### 3.3 Механіка темізації (щоб нічого не зламати)

- **Tailwind v4, підхід CSS-first** (без `tailwind.config.*`). Токени визначено в `:root`/`.dark` і надано утилітам через `@theme inline` (`globals.css:130-179`).
- **Темна тема через клас `.dark`** на `<html>` (`@custom-variant dark` у `globals.css:22`), перемикається власним сховищем Zustand (`src/store/themeStore.ts`), тема за замовчуванням = `system` (`src/shared/constants/appConfig.ts:11`). Натомість сайт використовує `html[data-theme="light"]` — **механізми відрізняються, але ніколи не перетинаються** (окремі джерела), тому конфлікту немає. Зберігаємо механізм `.dark` панелі керування.
- **Існує перевизначення основного кольору під час виконання** (`themeStore.ts:85-97`, готові варіанти в `COLOR_THEMES`) — користувачі можуть змінювати `--color-primary`. Будь-який новий токен (градієнт тощо), що посилається на `--color-primary`, автоматично успадковує ці перевизначення. ✅
- **Зарезервовані назви радіусів у Tailwind v4:** `--radius-sm/md/lg/...` є основою для утиліт `rounded-*`. Їхнє перевизначення ретроактивно змінює всі наявні `rounded-*` (наприклад, `rounded-sm` використовується у 12 файлах). Тому значення малого радіуса та перепризначення компонентів навмисно відкладено до Етапу 2, де споживачі змінюватимуться разом.

## 4. Частина A — Фон у клітинку як на міліметровому папері (головний запит) — РЕАЛІЗОВАНО (етап 1)

### 4.1 Що це таке

Точний рецепт із сайту (`_mono_repo/omnirouteSite/css/base.css`): **фіксований псевдоелемент на всю область перегляду**, який малює два градієнти з лініями завтовшки 1px і розташовується на `z-index:-1` позаду всього вмісту.

```css
body::before {
  content: "";
  position: fixed;
  inset: 0;
  z-index: -1;
  pointer-events: none;
  background-image:
    linear-gradient(to right, var(--grid-line) 1px, transparent 1px),
    linear-gradient(to bottom, var(--grid-line) 1px, transparent 1px);
  background-size: var(--grid-size) var(--grid-size);
}
```

**Чому це працює, хоча `body` має непрозорий `background-color`:** `::before` із `z-index:-1` відображається _над_ власним фоном елемента, але _під_ його вмістом у звичайному потоці. Отже, `--color-bg` є базовою заливкою, поверх неї накладається сітка, а застосунок відображається над сіткою.

### 4.2 Уже наявний у кодовій базі приклад

`src/app/landing/page.tsx:16-26` **уже реалізує таку саму сітку на рівні сторінки**, але з **червоними** лініями (`#E54D5E`, непрозорість `0.06`) із кроком **50px**, а також з анімованими сферами. Отже, цей підхід уже перевірено в продукті; ця робота перетворює його на **глобальний фон, що враховує тему**.

### 4.3 Додані токени (у `globals.css`)

```css
:root {
  /* світла тема — непрозорість сітки збільшено порівняно з 0.045 на сайті, щоб фон
     справді був помітним на щільній панелі керування (картки/обрамлення закривають більшу частину області перегляду) */
  --grid-line: rgba(0, 0, 0, 0.07);
  --grid-size: 32px;
  --section-alt: rgba(0, 0, 0, 0.022);
}
.dark {
  /* темна тема — збільшено порівняно з 0.035 з тієї самої причини */
  --grid-line: rgba(255, 255, 255, 0.06);
  --section-alt: rgba(255, 255, 255, 0.018);
}
```

### 4.4 Єдиний блокер — усунуто

Сітка за своєю будовою є глобальною (вона одночасно охоплює панель, `auth`/`login`, сторінки помилок — кожен маршрут). Усередині панелі її приховував рівно **один** елемент:

- `src/shared/components/layouts/DashboardLayout.tsx` — зовнішня обгортка мала непрозорий фон `bg-bg`. Усе під нею вже прозоре (`<main>`, контейнер прокручування, внутрішній контейнер `max-w-7xl`), тому **видалення `bg-bg`** дає змогу сітці `body` відображатися в області вмісту (властивість `--color-bg` елемента `body` залишається базовою заливкою).

  ```diff
  - <div className="flex h-dvh min-h-0 w-full overflow-hidden bg-bg">
  + <div className="flex h-dvh min-h-0 w-full overflow-hidden">
  ```

### 4.5 Взаємодія з обрамленням (бічна панель / заголовок)

- `Header` (`Header.tsx:207`, `bg-bg`) і `Sidebar` (`Sidebar.tsx:430`, `bg-sidebar`) залишаються **непрозорими** → сітка відображається **лише в області вмісту**, обрамленій суцільним інтерфейсом. Спокійний варіант за замовчуванням, що відповідає тому, як сайт відокремлює обрамлення від полотна (рішення D3 = суцільний фон).

### 4.6 Сторінки входу / автентифікації / помилок

Вони відображаються безпосередньо всередині `<body>` (без обрамлення панелі), тому глобальна сітка має автоматично з’являтися позаду них. **Етап 5 — ВИКОНАНО:** автономні повноекранні обгортки насправді були непрозорими (`min-h-screen … bg-bg`, де `bg-bg` — та сама суцільна заливка, що й у `<body>`), через що сітка була прихована на всіх екранах поза панеллю, а не лише на сторінці входу. Тепер усі вони прозорі, тож спільний фон видно крізь них: `login`, `forgot-password`, `callback`, `maintenance`, `offline`, `status`, `terms`, `privacy`, `onboarding` та `ErrorPageScaffold` (охоплює `400`/`401`). Це закриває **D4** (розширено зі сторінки входу на всі автономні екрани). Захищено тестом `tests/unit/design-grid-background.test.ts`.

### 4.7 Цільова сторінка

`landing/page.tsx` зберігає свій насиченіший анімований фон (сфери + віньєтка) — власну маркетингову заставку (рішення D5 = залишити без змін).

## 5. Частина B — Уніфікація токенів

Фаза 1 додає інертні токени ідентичності без конфліктів (`--surface-2`/`--color-surface-2`, `--grad-brand`, `--radius`). Фаза 2 підключає шкалу радіусів до Tailwind і переводить компоненти на неї; фаза 4 додає `--font-mono` та його споживачів.

| Токен                      | Навіщо                                                                | Фаза                                    |
| -------------------------- | --------------------------------------------------------------------- | --------------------------------------- |
| `--radius` / `--radius-sm` | Єдина шкала радіусів (14/9) замість довільних значень 6/8/12          | 1 (значення) / 2 (підключення + заміна) |
| `--grad-brand`             | Фірмовий градієнт для основних CTA (червоний→фіолетовий), як на сайті | 1 (токен) / 2 (Button)                  |
| `--surface-2`              | Вкладені панелі / заголовки таблиць / утоплені рядки                  | 1                                       |
| `--font-mono`              | Блоки коду, термінал, ID, кінцеві точки                               | 4                                       |
| узгодження `--text-muted`  | Вибрати одне значення для сайту й панелі (`#a1a1aa` рекомендовано)    | 2                                       |

## 7. План розгортання

- **Фаза 1 — Сітка + токени айдентики (ЦЕЙ PR).** Сітка в `globals.css` + токени `--surface-2`/`--grad-brand`/`--radius`; фонове зображення `body::before`; видалення блокувального `bg-bg`; статичний захисний тест. Низький ризик, можна відкотити одним комітом.
- **Фаза 2 — Примітиви (C1, C2, C5) — ВИКОНАНО в цьому PR.** Семантичні утиліти радіуса `rounded-card` (14px) / `rounded-control` (9px) додано через `@theme` (власні назви, тож стандартні `rounded-sm/md/lg/xl` залишаються незмінними — без масових змін у 400 файлах); Card/Modal → 14px, Button/Input/Select → 9px; основний Button → `--grad-brand` (червоний→фіолетовий) + новий варіант `accent`; рамки Card → токен `border-border` (0.08). **Відкладено:** `cn()`→tailwind-merge (C9) потребує нових залежностей; точкові входження `rounded-lg` (326 файлів) залишено без змін, оскільки примітиви охоплюють основну частину поверхонь.
- **Фаза 3 — Кольори статусів + таблиці (C3, C4) — ВИКОНАНО в цьому PR.** ✅ **C4** (`src/shared/constants/statusColors.ts` — єдине джерело `STATUS_HEX`; `flow/edgeStyles.ts` + `TokenHealthBadge` переведено на нього зі збереженням тих самих hex-кольорів). ✅ Токен **`--font-mono`**. ✅ **C3 (DataTable)** — усі вбудовані значення rgba та неактивні резервні значення `var(--bg-table-header)` / `var(--text-secondary)` замінено набором токенів `--table-*` (`--table-header-bg/-row-zebra/-row-hover/-cell-border/-row-selected`), чиї **темні значення точно відповідають старим жорстко заданим rgba** (темна тема побайтово ідентична), а світлі значення виправляють світлу тему, яка раніше завжди виглядала темною. Рамка заголовка → `--color-border`, вторинний текст → `--color-text-muted`. **Перед злиттям потрібна візуальна перевірка.** (Не змінено: `logTableStyles.ts` і застарілі правила Ant `.ant-table` — це окреме завдання з нижчим пріоритетом.)
- **Фаза 4 — Очищення (C6, C7, C9 виконано; C8 очікує).** ✅ **C9** `cn()` → `twMerge(clsx(...))` (clsx + tailwind-merge додано як залежності) — тепер `className`, переданий викликачем, коректно _замінює_ конфліктний клас примітива, а не додається поверх нього. ✅ **C7** нові примітиви `Checkbox` + `Textarea` (на основі токенів, експортовані з barrel-файлу; зміна адитивна — 32 необроблені прапорці / 41 необроблене текстове поле можна переводити поступово). ✅ **C6** узгодження кільця фокуса — елементи форми (`Input`/`Select`/`Textarea`/`Toggle`/`Checkbox`) тепер під час фокусування використовують кільце **акцентного (фіолетового)** кольору відповідно до глобального `--focus-ring`, щоб воно не конфліктувало з червоним кільцем помилки; червоний стан помилки залишився без змін. ⏳ **C8 — перевірка hex-кольорів — це НЕ сліпий пошук із заміною**: підтверджені випадки, які є _навмисними_ й мають залишитися: `ConsoleLogViewer.tsx:240` (термінал, що завжди має темну тему), спливне вікно `TokenHealthBadge`, SVG-обведення ReactFlow. Переносити лише ті hex-кольори, які справді мають залежати від теми.

Для кожної фази: `npm run lint` + `npm run typecheck:core` + візуальна перевірка.
