OmniRoute має три окремі, але взаємопов’язані механізми стійкості. Кожен із них має свою область дії та призначення. Не змішуйте їх під час налагодження поведінки маршрутизації.

## 1. Автоматичний вимикач провайдера

**Область дії:** увесь провайдер (наприклад, `glm`, `openai`, `anthropic`).

**Призначення:** припинити надсилання трафіку провайдеру, у якого регулярно виникають збої на рівні висхідного сервісу.

**Реалізація:**

- Основний клас: `src/shared/utils/circuitBreaker.ts`
- Підключення: `src/sse/handlers/chatHelpers.ts`, `src/sse/handlers/chat.ts`
- API стану: `GET /api/monitoring/health`
- API скидання: `POST /api/resilience/reset`
- Обгортки: `open-sse/services/accountFallback.ts`
- Таблиця БД: `domain_circuit_breakers`

**Стани:**

- `CLOSED` — звичайний трафік дозволено
- `DEGRADED` — трафік усе ще дозволено, але відстежується підвищена кількість збоїв провайдера
- `OPEN` — провайдера тимчасово заблоковано; комбінована маршрутизація пропускає його
- `HALF_OPEN` — час очікування перед скиданням минув; дозволено пробний запит

**Налаштовувані значення за замовчуванням (`open-sse/config/constants.ts`, доступні в Панель керування → Налаштування → Стійкість):**

| Клас      | Деградація після | Відкриття після | Час очікування перед скиданням |
| --------- | ---------------- | --------------- | ------------------------------ |
| OAuth     | 5 збоїв          | 8 збоїв         | 60s                            |
| API-ключ  | 7 збоїв          | 12 збоїв        | 30s                            |
| Локальний | обчислюється     | 2 збоїв         | 15s                            |

`degradationThreshold` визначає, коли провайдер переходить у стан `DEGRADED`; `failureThreshold` визначає, коли вимикач відкривається, а провайдер пропускається. Профілі локальних провайдерів поки що не відображаються на сторінці налаштувань стійкості.

**Коди спрацювання:** лише статуси рівня провайдера `[408, 500, 502, 503, 504]`. НЕ активуйте вимикач для помилок рівня облікового запису (більшість 401/403/429 — вони належать до механізму охолодження або блокування).

**Відкладене відновлення:** коли спливає термін стану `OPEN`, `getStatus()`, `canExecute()`, `getRetryAfterMs()` оновлюють стан до `HALF_OPEN`. Фоновий таймер не потрібен.

### Необов’язкове глобальне охолодження провайдера (віконний шлюз)

Четвертий, **необов’язковий** рівень (`PROVIDER_COOLDOWN_ENABLED`, за замовчуванням **вимкнено**) зберігає
між запитами інформацію про провайдерів зі збоями в
`open-sse/services/providerCooldownTracker.ts`; ця інформація враховується під час визначення цілей комбінованої
маршрутизації, щоб послідовні комбіновані запити не намагалися знову використовувати провайдера, у якого щойно
стався збій. Записи рівня провайдера враховують віконний шлюз `PROVIDER_PROFILES`:

| Профіль  | спрацьовує після (`providerFailureThreshold`) | упродовж (`providerFailureWindowMs`) | охолоджується протягом (`providerCooldownMs`) |
| -------- | --------------------------------------------: | -----------------------------------: | --------------------------------------------: |
| OAuth    |                                          `10` |                              `15min` |                                        `5min` |
| API-ключ |                                          `15` |                              `30min` |                                       `10min` |

Нижче порогового значення провайдер **не** вважається таким, що перебуває в стані охолодження; успішне виконання очищає
вікно. Натомість записи рівня підключення (`provider:connectionId`) зберігають
експоненційну затримку `minRetryCooldownMs → maxRetryCooldownMs`. Перевизначення:
`OMNIROUTE_PROVIDER_BREAKER_{OAUTH,API_KEY}_{FAILURE_THRESHOLD,FAILURE_WINDOW_MS,COOLDOWN_MS}`.
Захист від регресій: `tests/unit/provider-cooldown-window-gate.test.ts`.

## 2. Період очікування підключення

**Область дії:** одне підключення/обліковий запис/ключ провайдера.

**Призначення:** пропускати один несправний ключ, поки інші підключення того самого провайдера продовжують обслуговувати запити.

**Реалізація:**

- Позначення недоступним: `src/sse/services/auth.ts::markAccountUnavailable()`
- Вибір: `getProviderCredentials*` у тому самому файлі
- Обчислення періоду очікування: `open-sse/services/accountFallback.ts::checkFallbackError()`
- Налаштування: `src/lib/resilience/settings.ts`

**Поля для кожного підключення:**

- `rateLimitedUntil` — часова позначка завершення періоду очікування
- `testStatus: "unavailable"`
- `lastError`, `lastErrorType`, `errorCode`
- `backoffLevel` — лічильник експоненційної затримки

**Періоди очікування за замовчуванням:**

- Базовий для OAuth: 5 с
- Базовий для API-ключа: 3 с
- Для відповіді 429 з API-ключем: перевага надається отриманим від сервера заголовкам `Retry-After`/заголовкам скидання/тексту часу скидання, який можна розібрати
- Затримка: `baseCooldownMs * 2 ** failureIndex`

**Захист від лавиноподібного навантаження:** запобігає надмірному подовженню періоду очікування або подвійному збільшенню `backoffLevel` через одночасні збої.

**Термінальні стани (НЕ періоди очікування):**

- `banned` — установлюється в разі виявлення ключового слова блокування / блокування облікового запису (див. [BAN_DETECTION](../security/BAN_DETECTION.md)), а також після трьох послідовних відмов провайдера для окремих запитів (`request_rejected`, наприклад Anthropic OAuth 403 «Запит не дозволено» — `open-sse/services/requestRejectedStreak.ts`); одна відмова лише переводить підключення в період очікування
- `expired` (переходить у термінальний стан після обмеженої кількості повторних спроб — `EXPIRED_RETRY_MAX = 3` з експоненційною затримкою — тож тимчасові помилки OAuth можуть усунутися самі до остаточної деактивації облікового запису)
- `credits_exhausted`

Ці стани зберігаються, доки не зміняться облікові дані або оператор не скине їх. Не перезаписуйте термінальні стани тимчасовим станом періоду очікування.

**Відкладене відновлення:** коли час `rateLimitedUntil` минув, підключення знову стає придатним для використання. Після успішного використання `clearAccountError()` очищає всі поля помилок.

### Ліміт використання Claude OAuth: канал із нижчим пріоритетом + скидання ліміту сеансу

**Область дії:** одне підключення передплати Claude (OAuth). Обидві функції **вмикаються окремо для кожного
підключення** (Редагувати підключення → розділ Claude → `lowPriorityMode` / `autoLimitReset` у
`providerSpecificData`, обидві за замовчуванням вимкнені) і відтворюють команди Claude Code `/low-priority` та
`/limit-reset` (контракт обміну даними зафіксовано з Claude Code 2.1.263).

**Реалізація:**

- Машина станів + класифікація відповідей: `open-sse/services/claudeLowPriority.ts`
- Клієнт перевірки статусу/отримання скидання: `open-sse/services/claudeLimitReset.ts`
- Хук виконавця (додавання заголовка + повторна спроба з тим самим обліковим записом): `open-sse/executors/base.ts::execute()`
- Збереження згоди: `src/lib/providers/requestDefaults.ts::normalizeProviderSpecificData()`

**Умова спрацювання:** 5-годинний ліміт використання — відповідь `429`, заголовки якої містять
`anthropic-ratelimit-unified-status: rejected` і, якщо обліковий запис придатний,
`anthropic-ratelimit-unified-slow-offer: treatment`. До першої такої відповіді 429 про досягнення ліміту
нічого не надсилається; серія відповідей 429 без уніфікованих заголовків обробляється звичайним механізмом періоду очікування.

**Канал із нижчим пріоритетом** (`lowPriorityMode`):

- Після відповіді 429 про досягнення ліміту виконавець приймає пропозицію та негайно повторює запит через **той самий**
  обліковий запис із `anthropic-usage-limit: slow`; канал залишається активним до оголошеного часу
  `anthropic-ratelimit-unified-reset` (+60 с пільгового періоду), і кожен запит у цьому проміжку містить
  цей заголовок. Перехоплена відповідь 429 ніколи не потрапляє до `handleChatCore`, тому підключення
  **не** переводиться в період очікування й не замінюється іншим.
- `anthropic-ratelimit-unified-slow-status` у наступних відповідях: `active` / `not_needed`
  зберігають канал; `slot_busy` (429) або `529` очікують указаний сервером час
  `anthropic-ratelimit-unified-slow-retry-after` (за замовчуванням 20 с, обмеження 5–600 с, випадкове відхилення ±30%)
  і повторюють спробу з обмеженням `anthropic-ratelimit-unified-slow-max-wait` (за замовчуванням 20 хв, обмеження
  1 хв–6 год) — після цього канал завершується, а 10-хвилинна пауза блокує повторне прийняття. Час
  очікування додатково обмежується залишком власного тайм-ауту початку відповіді провайдера для запиту
  (`resolveFetchStartTimeout`, за замовчуванням 10 хв) мінус запас у 5 с: без цього обмеження
  стандартний максимальний час очікування у 20 хв перевищив би час життя запиту, а очікування було б перервано
  посеред процесу, що призвело б до появи `TimeoutError` замість коректного завершення `max_wait` + паузи.
- `weekly_limit` / `budget_exhausted` / `off` / `ineligible`, перехід до нового 5-годинного вікна або
  `ineligible` + `anthropic-ratelimit-unified-overage-in-use: true` (що завершує канал зі станом
  `extra_usage` за будь-якого статусу, оскільки платне перевищення тепер покриває ліміт) завершують канал;
  після цього відповідь передається звичайному механізму періоду очікування. `budget_exhausted` запам’ятовується до
  оголошеного часу скидання бюджету (≤ 8 днів).
- Перевірка ліміту виконується після внутрішніх повторних спроб виконавця, спричинених відповідями 400 (редагування
  контексту, обмеження мислення/зусиль, автоматичне визначення параметрів), тому відповідь 429 про ліміт, яка з’являється лише під час
  однієї з таких повторних спроб, усе одно перехоплюється, а не передається механізму періоду очікування.
- Стан зберігається в пам’яті окремо для кожного підключення (після перезапуску потрібна одна додаткова відповідь 429 про досягнення ліміту для повторного прийняття).

**Скидання ліміту сеансу** (`autoLimitReset`, виконується перед переходом у канал, якщо ввімкнено обидві функції):

- `GET https://api.anthropic.com/api/oauth/usage?at_wall=1&skip_spend=1` → блок `juniper_tide`;
  коли `arm: "reset"` і `available: true`,
  `POST https://api.anthropic.com/api/organizations/{orgUUID}/reset_rate_limits` із
  `{ "program": "juniper_tide" }` (UUID організації з
  `providerSpecificData.organizationUUID`, резервне початкове визначення).
- `result: reset|not_limited` → запит повторюється на повній швидкості (без заголовка повільного режиму).
  Для `already_used` / `not_offered` значення `next_available_at` запам’ятовується (за замовчуванням один тиждень);
  після будь-якого збою застосовується 15-хвилинна затримка. Скидання доступне раз на тиждень і все одно
  зараховується до тижневого ліміту.

Перевірки на регресії: `tests/unit/claude-low-priority-mode.test.ts`,
`tests/unit/claude-limit-reset.test.ts`, `tests/unit/claude-low-priority-executor.test.ts`.

### Прив’язка сеансу (#7274)

**Область дії:** один клієнтський сеанс (заголовок `X-Session-Id` / `x-codex-session-id` / `x-omniroute-session`), прив’язаний до одного підключення для **будь-якого** провайдера.

**Призначення:** утримувати багатоходового агента (Claude Code, aider, власні агенти) на тому самому обліковому записі між запитами, зменшуючи втрату контексту через перемикання між обліковими записами та повторні помилки 429 під час холодного запуску в постачальників зі станом сеансу на рівні облікового запису.

**Реалізація:**

- Визначення TTL: `src/sse/services/sessionAffinityPin.ts::resolveSessionAffinityTtlMs()`
- Вибір/створення закріплення: `src/sse/services/sessionAffinityPin.ts::selectSessionAffinityConnection()`
- Отримання заголовка (універсальне, для будь-якого постачальника): `src/sse/services/auth.ts::extractSessionAffinityKey()`
- Таблиця збережених закріплень: `sessionAccountAffinity` (`src/lib/db/sessionAccountAffinity.ts`)
- Налаштування: `sessionAffinityTtlMs` (глобальний TTL у мс, `0` вимикає) — `src/lib/db/settings.ts`. Перейменовано з орієнтованого лише на Codex параметра `codexSessionAffinityTtlMs` за допомогою міграції `124_generic_session_affinity_ttl.sql`, яка переносить будь-який раніше налаштований TTL Codex як нове значення за замовчуванням.

До #7274 `resolveSessionAffinityTtlMs()` негайно повертав `0` для всіх постачальників, крім `codex`, тому налаштування TTL (і заголовки сеансу) більше ніде не діяли, хоча механізм закріплення та отримання заголовків уже не залежали від постачальника. Виправлення прибрало це дострокове повернення; тепер TTL однаково застосовується до кожного постачальника, щойно глобально встановлено значення понад `0`.

Три заголовки спорідненості сеансу ніколи не пересилаються до висхідного сервера — виконавці формують власні висхідні заголовки з нуля, а не передають клієнтські заголовки, тому вони залишаються лише внутрішніми ідентифікаторами кореляції.

### Ексклюзивні оренди підключень керованих сеансів

**Область дії:** один активний керований HTTP-клієнт/сеанс володіє одним придатним підключенням OmniRoute.

**Призначення:** забезпечити стале ексклюзивне володіння підключенням для клієнтів, яким потрібна жорстка межа маршрутизації між запитами. Це відрізняється від спорідненості сеансу, яка є м’якою перевагою безперервності: ексклюзивна оренда зберігає стан життєвого циклу в SQLite, забезпечує глобальну унікальність активного власника й активного підключення та відхиляє застаріле покоління до передавання запиту постачальнику.

Функцію потрібно вмикати окремо для кожного ключа API. Керований ключ повинен мати область доступу `lease:exclusive` і явно заданий непорожній список `allowedConnections`. Будь-який HTTP-клієнт може використовувати кінцеву точку життєвого циклу; ім’я клієнта, user-agent, постачальник, метод OAuth або модель не потрібні. Оренда належить підключенню, а не моделі, тому зміна моделі зберігає прив’язку, доки підключення залишається придатним за звичайними правилами. Звичайні правила щодо моделі, квоти, стану, періоду відновлення та списку дозволів залишаються визначальними й можуть перевести те саме покоління на інше вільне придатне підключення.

Життєвий цикл реалізовано через `POST /api/v1/session-leases` з JSON-діями `acquire`, `renew` і `release`. Керовані запити інференсу передають непрозоре значення `X-OmniRoute-Lease-Owner` і точне значення `X-OmniRoute-Lease-Generation`. Ідентифікатор власника складається з `vlo_`, після якого йдуть 43 символи base64url; зберігається лише його хеш SHA-256. Кожна остаточна перевірка перед відправленням також прив’язує ідентифікатор автентифікованого ключа API та ідентифікатор активного підключення. Керувальні заголовки оренди вилучаються з журналів, збережених знімків запитів і заголовків висхідних виконавців.

Якщо звичайна маршрутизація має придатних керованих кандидатів, але кожен вільний кандидат зайнятий чужою активною орендою, OmniRoute повертає HTTP `429`, код lease-capacity-unavailable, стан waiting-for-capacity та обмежене значення `Retry-After`, обчислене на основі найближчого відповідного часу завершення. Звичайна відсутність придатних кандидатів не є конфліктом оренд і зберігає наявну семантику помилок маршрутизації.

Пов’язані механізми залишаються окремими:

- Зайнятість сеансів OAuth — це локальний для процесу механізм м’якого розподілу облікових записів OAuth.
- Семафори облікових записів надають дозволи на одночасне виконання запитів і завершують дію після виконання запиту.
- Ексклюзивні оренди підключень керованих сеансів — це стале володіння протягом життєвого циклу із захистом за поколінням.

## 3. Блокування моделі

**Область дії:** комбінація постачальника + підключення + моделі.

**Область ключа залежно від статусу:** статус помилки визначає, до якого ключа
буде записано блокування (`resolveLockoutScope()` у `open-sse/services/accountFallback/exactModelLock.ts`):

- `429` / `403` / `402` — сигнал квоти або права доступу — блокують **сімейство квот**:
  для codex — усю область `codex` / `spark` (кожну модель `gpt-5*` цього
  підключення), для інших постачальників — `getQuotaScopedModelForProvider()`.
- `404` блокує саму модель (`getModelLockKey()` звужує `not_found`).
- Будь-який інший статус — транспортні/серверні помилки `5xx` і власний
  синтезований OmniRoute статус `502` після перевірки якості — блокує лише **точну**
  комбінацію постачальника/підключення/моделі. Некоректний потік однієї моделі не
  є свідченням проблем із квотою облікового запису; до запровадження цього правила
  одна порожня відповідь від `codex/gpt-5.6-luna` вилучала кожну модель `gpt-5*`
  цього підключення з маршрутизації на 2–30 хв (із поступовим збільшенням), хоча
  її квота залишалася незмінною.
- Явно заданий викликачем параметр `scope` завжди має пріоритет (Antigravity передає `"exact"`).

**Мета:** уникнути вимкнення всього підключення, коли недоступна або обмежена квотою лише одна модель.

**Приклади:**

- Постачальники з квотами для окремих моделей, які повертають 429
- Локальні постачальники, які повертають 404 для однієї відсутньої моделі
- Специфічні для постачальника помилки дозволів режиму/моделі (наприклад, режими Grok)

**Реалізація:** `open-sse/services/accountFallback.ts` — `lockModel()`, `clearModelLock()`, `getAllModelLockouts()`.

### Панель періодів очікування моделей (v3.8.0)

Інтерфейс: Налаштування → Періоди очікування моделей (`src/app/(dashboard)/dashboard/settings/components/ModelCooldownsCard.tsx`)

Відображає активні блокування з такими даними: постачальник, підключення, модель, причина, expiresAt. Оператори можуть вручну повторно ввімкнути модель із картки.

**REST API:**

- `GET /api/resilience/model-cooldowns` — отримати список активних блокувань
- `DELETE /api/resilience/model-cooldowns` — повторне ввімкнення вручну. Тіло: `{provider, connection, model}`. Автентифікація: керування.

### Інтерфейс налаштувань блокування + відновлення зі зменшенням після успіху (v3.8.23)

Блокування моделей змінилося з постійно ввімкненої жорстко закодованої поведінки
на повністю налаштовувану функцію, яку потрібно явно ввімкнути, із власною
карткою налаштувань і механізмом самовідновлення.

**Картка налаштувань:** Налаштування → Блокування моделі
(`src/app/(dashboard)/dashboard/settings/components/ModelLockoutCard.tsx`).
Вона **відрізняється** від наведеної вище картки `ModelCooldownsCard`, доступної
лише для читання (яка лише _відображає_ активні блокування), — нова картка
_налаштовує параметри_. Значення за замовчуванням містяться в
`DEFAULT_MODEL_LOCKOUT_SETTINGS`
(`src/lib/resilience/modelLockoutSettings.ts`):

| Налаштування            | Значення за замовчуванням        | Значення                                                               |
| ----------------------- | -------------------------------- | ---------------------------------------------------------------------- |
| `enabled`               | `false`                          | Головний перемикач — блокування моделей **типово вимкнене**.           |
| `errorCodes`            | `[403, 404, 429, 502, 503, 504]` | Статуси висхідного сервісу, що вважаються помилкою на рівні моделі.    |
| `baseCooldownMs`        | `120_000` (120 с)                | Початкова тривалість блокування після першої помилки.                  |
| `maxCooldownMs`         | `1_800_000` (30 хв)              | Верхня межа збільшеного періоду очікування.                            |
| `maxBackoffSteps`       | `10`                             | Максимальна кількість кроків експоненційного збільшення затримки.      |
| `useExponentialBackoff` | `true`                           | Чи мають повторні помилки експоненційно збільшувати період очікування. |

Налаштування зберігаються через звичайне сховище налаштувань і перевіряються
схемою налаштувань стійкості; картка обмежує `baseCooldownMs`/`maxCooldownMs`
(з умовою `maxCooldownMs ≥ baseCooldownMs`) і `maxBackoffSteps`.

**Відновлення зі зменшенням після успіху:** відновлення відбувається **не**
лише після завершення таймера. Успішна відповідь поступово зменшує лічильник
помилок моделі, тому для моделі, яка відновилася посеред періоду, ескалація
припиняється (і блокування знімається) раніше, ніж завершиться її таймер. Після
успішного комбінованого цільового запиту `open-sse/services/combo.ts` викликає
`decayModelFailureCount()` (`open-sse/services/accountFallback.ts`), що
**вдвічі зменшує** збережене значення `failureCount`
(`Math.floor(failureCount / 2)`); коли воно досягає `0`, запис про блокування
повністю видаляється. Відповідна функція `recordModelLockoutFailure()`
збільшує лічильник (і подовжує період очікування) у разі помилок у межах
вікна ескалації. Таке зменшення після успіху доповнює звичайне завершення
таймера — модель може бути повторно ввімкнена будь-яким із цих способів.

**Стан:** блокування зберігаються **в пам’яті** (`Map` для кожного процесу
з елементами `ModelLockoutEntry`, ключами яких є `provider:connectionId:model`,
а для блокувань із точною областю — `provider:connectionId:exact:model`) і не
зберігаються в БД — вони втрачаються після перезапуску. _Налаштування_
зберігаються постійно; активний _стан_ блокування є тимчасовим.

## 4. Керування паралельністю Quota-Share (v3.8.36)

Облікові записи з підпискою (GLM, MiniMax тощо) часто приймають лише ~1–3 паралельні
запити; перевищення цього ліміту спричиняє помилки 429 і періоди очікування. Це особливо відчутно для
комбінацій **quota-share** (`qtSd/…`), де кілька ключів API спільно використовують один
висхідний обліковий запис. Три рівні захищають спільний обліковий запис від перевантаження.

### Обмеження паралельності для кожного підключення (`max_concurrent`)

Для кожного підключення провайдера можна вказати верхню межу `max_concurrent`
(`provider_connections.max_concurrent`, налаштовується в модальному вікні підключення / API / БД).
Залиште поле порожнім, щоб не застосовувати обмеження. Це єдиний параметр, який керує описаним
нижче рівнем серіалізації — установіть його відповідно до фактичної паралельності облікового запису
(наприклад, GLM ~1, MiniMax ~2).

### Серіалізація запитів Quota-share

Коли диспетчеризація quota-share спрямовується до підключення, для якого задано додатне
значення `max_concurrent`, паралельні запити до цього **облікового запису** серіалізуються через
окремий для кожного підключення семафор (ключ `qsconn:<connectionId>`): надлишкові запити **очікують у
черзі**, а не перевантажують обліковий запис. Механізм працює за принципом **fail-open** — у разі
переповнення черги або завершення часу очікування запит продовжується без слота, замість того щоб
відхиляти запит, який можна диспетчеризувати. Перемикач розташований у розділі **Налаштування → Стійкість → Паралельність
Quota-share для кожного підключення** (`resilienceSettings.quotaShareConcurrencyLimit.enabled`, початково
ввімкнено). Без обмеження `max_concurrent` поведінка не змінюється.

> Шлюз маршрутизації quota-share (`selectQuotaShareTarget`, DRR + P2C) сам
> працює за принципом fail-open і лише _знижує пріоритет_ підключення, що досягло ліміту, — якщо
> пул містить одне підключення, він не може застосувати жорстке обмеження, тому саме цей семафор фактично
> стримує потік запитів.

### Повторні спроби з урахуванням періоду очікування комбінації

Для кожної стратегії комбінації (коли її ввімкнено) запит, який призвів би до остаточного формування
помилки 429 через КОРОТКИЙ тимчасовий період очікування, чекає на його завершення та диспетчеризується повторно
замість повернення помилки 429 — це охоплює вікна TPM/RPM класу Gemini
(~60s retry-after) у багатомодельних комбінаціях, наприклад коли обидві цілі комбінації з 2 моделей
досягають обмеження частоти запитів для окремої моделі. Обмежується параметрами `comboCooldownWait`
(`enabled`, `maxWaitMs`, `maxAttempts`, `budgetMs`) у розділі **Налаштування → Стійкість**.
Очікування ніколи не застосовується для `quota_exhausted` (заблоковано до опівночі) або причин,
пов’язаних з автентифікацією чи відсутністю ресурсу.

## 5. Керування допуском до черги запитів (v3.8.49 · issue #6593)

**Область дії**: локальна черга обмеження частоти для кожної пари постачальник+з’єднання (`open-sse/services/rateLimitManager.ts`,
на базі Bottleneck), на один рівень нижче від трьох наведених вище механізмів.

**`maxWaitMs` обмежує очікування в черзі; `executionMaxWaitMs` обмежує виконання.**
Ці два обмеження навмисно відокремлені, і жодне з них не впливає на інше.

`resilienceSettings.requestQueue.maxWaitMs` — це **бюджет очікування в черзі**: він
охоплює очікування доступного слота постачальника та подальше перебування у стані QUEUED, а його таймер
скидається в момент, коли завдання залишає стан QUEUED і починає виконуватися
(`rateLimitManager.ts`, `wrappedFn`). Запит, який перевищує цей бюджет, ніколи не надходить
до зовнішнього сервісу. Значення за замовчуванням — 30000ms; воно задається через `DEFAULT_REQUEST_QUEUE_MAX_WAIT_MS`
у `src/lib/resilience/settings.ts` і зафіксоване тестом
`tests/unit/ratelimit-admission-control-6593.test.ts`, тож його зміна призведе
до падіння цього тесту, а не до непомітного застарівання цього абзацу.

`resilienceSettings.requestQueue.executionMaxWaitMs` — це значення, яке Bottleneck
отримує як параметр завдання `expiration`; його таймер запускається лише після диспетчеризації. Воно є
запобіжним обмеженням для виконавців, які не мають власного тайм-ауту зовнішнього запиту, і
збільшується до власного тайм-ауту початку отримання даних виконавця, якщо той довший, тому
воно не може перервати справну відповідь, яка вже обробляється. Значення за замовчуванням — 600000ms (10 хв).

Передавання бюджету черги до `expiration` раніше призводило до переривання неінкрементальних
шлюзів посеред виконання — вони цілком правомірно можуть працювати кілька хвилин до отримання перших байтів —
і саме тому завершення терміну дії повертається як `code:
"RATE_LIMIT_EXECUTION_TIMEOUT"` (HTTP 504), тоді як бюджет черги має
код тайм-ауту черги. Перевизначити будь-яке зі значень можна через `RATE_LIMIT_MAX_WAIT_MS` /
`RATE_LIMIT_EXECUTION_MAX_WAIT_MS` (змінні середовища) або на панелі керування
(**Налаштування → Відмовостійкість**). Під час нормалізації обидва значення обмежуються діапазоном 1ms–24h.

**Пріоритет для обох параметрів:** змінна середовища лише задає значення _за замовчуванням_. Значення,
збережене в `resilienceSettings.requestQueue` (через панель керування / API-виправлення, зберігається
в `key_value`), має вищий пріоритет, а параметр конкретного з’єднання
`rateLimitOverrides.maxWaitMs` / `.executionMaxWaitMs` має ще вищий пріоритет. Тому встановлення
змінної середовища в розгортанні, де вже є збережене значення,
нічого не змінить — натомість очистьте або оновіть збережене налаштування.

Час перебування в черзі обмежується параметром `maxWaitMs`; наведений нижче `maxQueueDepth` обмежує
кількість викликів, які можуть одночасно перебувати в черзі.

**`maxQueueDepth` — необов’язкове обмеження допуску (нове).** `resilienceSettings.requestQueue.maxQueueDepth`
обмежує кількість запитів, які можуть одночасно перебувати в черзі (ще не бути диспетчеризованими) для однієї
пари постачальник+з’єднання. Якщо в черзі вже перебуває `maxQueueDepth`
запитів, новий запит негайно відхиляється з типізованою помилкою
`code: "RATE_LIMIT_QUEUE_FULL"` **до** того, як він потрапить до `limiter.schedule()`
— тому відхилення є маловитратним і відбувається до будь-якої подальшої
роботи зі стиснення / перекладу запиту для цього звернення. Значення за замовчуванням `0` =
вимкнено, що зберігає наявну поведінку необмеженої черги; допустимий діапазон — 0–100000.
Перевизначити значення можна через `RATE_LIMIT_MAX_QUEUE_DEPTH` (змінну середовища) або
`resilienceSettings.requestQueue.maxQueueDepth` (панель керування/API-виправлення).

Сама перевірка допуску є чистою функцією
(`open-sse/services/rateLimitManager/admission.ts::checkQueueAdmission`), тому
її можна модульно тестувати без реального обмежувача Bottleneck.

> RFC, з якого почалася робота над #6593, також пропонував прапорець `bypassCompressionOnRateLimit`.
> Конвеєр `open-sse/services/compression/` у цьому репозиторії виконує
> стиснення запиту/контексту у вихідному запиті до LLM (`chatCore.ts`,
> у блоці `resolveCompressionSettings`/`selectCompressionStrategy`),
> а не стиснення HTTP-відповіді для згенерованих тіл 429 — відповідного
> шляху коду для буквального прапорця обходу не існує. Цей етап стиснення запиту
> також наразі виконується _до_ `withRateLimit()` у конвеєрі обробки запиту, тому
> зміна порядку, яка дала б змогу пропустити його в разі відхилення через переповнену чергу, є окремою та масштабнішою
> зміною, ніж передбачено областю дії цього issue; її навмисно **не** реалізовано
> тут і залишено для подальшої роботи, якщо вигода від зменшення навантаження на CPU виправдає
> ризик зміни порядку.

## 6. Сторож пропускної здатності повільного потоку (#9709)

Необов’язковий захисний механізм `resilienceSettings.streamRecovery.throughputWatchdog` виявляє
висхідний сервер, який усе ще надсилає фрагменти, але генерує виведення асистента зі швидкістю,
нижчою за налаштовану швидкість корисного виведення. Він навмисно відокремлений від тайм-ауту
простою: сигнали перевірки активності та метадані не скидають жоден із таймерів і не вважаються
прогресом. Він також відрізняється від жорсткого граничного часу спроби (#9153), який залишається
абсолютною межею безпеки незалежно від якості виведення.

Перш ніж сторож зможе перервати виконання, мають минути період прогрівання та повне рухоме вікно.
Він підраховує текстові дельти з подій виведення API Chat Completions і Responses
(консервативний приблизний показник у байтах UTF-8), ігнорує порожні події та події лише з даними
про використання й призупиняє оцінювання, поки обробляються події виклику інструментів або міркування.
За замовчуванням його вимкнено; увімкнути його можна за допомогою
`STREAM_THROUGHPUT_WATCHDOG_ENABLED=true`. Вікно, період прогрівання, мінімальна швидкість і
мінімальний вимірюваний обсяг виведення обмежуються звичайним шаром нормалізації налаштувань
стійкості.

Коли сторож увімкнено, його переривання застосовується лише до активної спроби висхідного сервера.
До надсилання будь-яких видимих клієнту байтів наявний шлях раннього відновлення в межах того самого
облікового запису може повторно відкрити спробу. Після фіксації потік ніколи не відтворюється
наосліп; додати суфікс може лише наявний безпечний контракт продовження всередині потоку.
Фіналізація, як і раніше, виконується лише один раз, тому облік використання та звільнення семафора
не дублюються.

## 7. Переформулювання статусу висхідного сервера (помилково вказані помилки квоти)

**Область застосування:** один висхідний шлюз, який повідомляє про тимчасове вичерпання квоти за допомогою неправильного статусу HTTP.

**Мета:** виправити оманливий статус ДО класифікації, щоб наступні споживачі (механізм резервного перемикання, агрегація комбінацій, відповідь для клієнта) бачили справжню повторювану природу помилки.

Деякі шлюзи сигналізують про ТИМЧАСОВЕ вичерпання квоти за допомогою HTTP-статусу,
який не передбачає повторної спроби. `agentrouter.org` повертає `403` (іноді `400`) з текстом
китайською мовою (`用户额度不足` / `额度不足`) замість стандартного `429`. Такі клієнти, як Claude
Code, вважають `403` постійною помилкою та переривають сеанс, а без виправлення
механізм резервного перемикання класифікував би її як `AUTH_ERROR`, а не як подію
квоти.

**Реалізація:**

- Реєстр і зіставник: `open-sse/config/upstreamStatusRestatement.ts` — список
  правил для кожного провайдера (`{id, fromStatuses, toStatus, textMarkers,
excludeMarkers, defaultRetryAfterMs}`), які зіставляються за допомогою `applyStatusRestatement()`.
- Місце виклику: блок `providerFailure:` у `open-sse/handlers/chatCore.ts`
  (приблизно рядок 3654), одразу після того, як `parseUpstreamError()` аналізує відповідь
  висхідного сервера зі статусом помилки HTTP (`!providerResponse.ok`), і до виконання
  будь-якої класифікації, щоб кожен наступний споживач бачив виправлений
  статус. Помилки, вбудовані в потік SSE зі статусом `200`, проходять окремим,
  пізнішим шляхом аналізу потоку й **не** охоплюються цим перехоплювачем наразі — це
  відоме обмеження, яке поки не має значення для помилкового статусу agentrouter (він
  проявляється як HTTP-статус помилки).
- Придатність до повторної спроби: `429` входить до `RETRY_AFTER_ELIGIBLE_STATUSES`
  (`open-sse/services/combo/unavailableRetryGate.ts`), тому помилка з переформульованим
  статусом містить справжнє вікно повторної спроби, а не відображається як безнадійна `403`.
- Синтетичне значення `60s` для `defaultRetryAfterMs` (`upstreamStatusRestatement.ts`)
  лише визначає, що переформульована відповідь повідомляє **клієнту**; воно саме по собі
  не є тривалістю внутрішнього періоду очікування/блокування з’єднання — вона окремо
  визначається механізмом, який фактично обробляє переформульовану помилку
  (наростальним відкладенням Connection Cooldown, §2, з базовим значенням `3s` для
  провайдерів із ключами API; або Model Lockout, §3, для провайдерів із квотою на
  окремі моделі, як-от agentrouter). Маршрутизатор може отримати право на внутрішню
  повторну спробу раніше за 60-секундне вікно, яке він оголошує клієнту, — це навмисний
  запас, а не помилка.

Постійні помилки (`无权访问模型` від agentrouter — немає доступу до цієї моделі)
НІКОЛИ не переформульовуються: `excludeMarkers` забороняє застосування правила, навіть коли
`textMarkers` збігаються, тому помилка зберігає свій початковий статус і ніщо не намагається
повторювати її безкінечно. Відповідне правило класифікації провайдера
(`agentrouter-model-access-denied` у `open-sse/config/providerErrorRules.ts`:
`reason: "auth_error"`, `scope: "model"`, оголошений базовий період очікування `6h`)
перевіряється функцією `checkFallbackError` (`open-sse/services/accountFallback.ts`)
_до_ загального раннього повернення `FORBIDDEN` для категорії apikey, за умови
`honorsRuleLockScope(provider)` (#10334 — наразі виключно для agentrouter через
список дозволених значень `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у
`providerErrorRules.ts`). Оголошений правилом 6-годинний період очікування передається далі як
`fallbackResult.baseCooldownMs`, але все одно надходить до вже наявного
шляху блокування квоти для окремої моделі (`lockModelIfPerModelQuota()` /
`recordModelLockoutFailure()`, не зміненого в #10334, за винятком джерела періоду
очікування): його верхня межа обмежується операторським значенням `mlSettings.maxCooldownMs`
(за замовчуванням `1_800_000ms` / 30 хв), як і для будь-якого іншого блокування моделі, а
_збережена причина блокування_ залишається раніше наявним жорстко закодованим значенням
`"forbidden"`, а не значенням правила `"auth_error"` — наскрізно враховується лише тривалість
періоду очікування, а не рядок причини. Саме з’єднання залишається активним;
інші моделі в тому самому з’єднанні не зазнають впливу.

Переформульовані помилки квоти (`额度不足`) у production-середовищі відповідають правилу провайдера
(`agentrouter-user-quota-exhausted`: `reason: "quota_exhausted"`, `scope:
"connection"`, без власного оголошеного періоду відновлення — застосовується
масштабоване експоненційне відкладення за замовчуванням із шару збереження).
Починаючи з #10334, `scope` у
`ProviderErrorRuleMatch` обробляється наскрізно, але **лише** для провайдерів зі
списку дозволених `HONORS_RULE_LOCK_SCOPE_PROVIDERS` (`providerErrorRules.ts` —
наразі лише `"agentrouter"`, із перевіркою через `honorsRuleLockScope()`). Для
всіх інших провайдерів `scope` залишається інформаційним, як і до #10334.
`checkFallbackError` надає область відповідного правила як
`fallbackResult.ruleScope`; `isAgentrouterConnectionQuotaScope()`
(`src/sse/services/auth.ts`) — це спільна захисна перевірка, яка підтверджує, що
`ruleScope` справді можна безпечно враховувати як самовідновлюваний сигнал на
рівні всього підключення (область `"connection"`, причина `quota_exhausted`,
ніколи не `permanent`, ніколи не `creditsExhausted` — захист від майбутнього
правила, яке поєднуватиме область `"connection"` із постійним станом
облікового запису). Її викликають два споживачі:

- **Збереження** (`markAccountUnavailable()`, `src/sse/services/auth.ts`):
  замість переходу до гілки блокування **для окремої моделі** для
  passthrough-провайдера (agentrouter має `passthroughModels: true` →
  `hasPerModelQuota()` повертає `true`) застосовується **тимчасовий період
  відновлення підключення** — `testStatus: "unavailable"` +
  `rateLimitedUntil`, без установлення термінального стану
  (`credits_exhausted`/`banned`/`expired`) — тому підключення самостійно
  відновлюється після завершення періоду відновлення, а не потребує ручного
  скидання облікових даних. Пропускається для підключень із
  `disableCooling: true` (#2997): у разі такої відмови від механізму
  виконується перехід до блокування для окремої моделі (це задокументований
  компроміс — див. коментар у коді над цією гілкою).
- **Маршрутизація комбінації в межах того самого запиту**
  (`applyComboTargetExhaustion()`,
  `open-sse/services/combo/targetExhaustion.ts`): та сама захисна перевірка
  позначає підключення в наборі `exhaustedConnections` у пам’яті з ключем
  `${provider}:${connectionId}`. Це пропускає лише решту цілей ТОГО САМОГО
  ЗАПИТУ, які _самі вже містять саме цей `connectionId`_ у власному об’єкті
  цілі (`getExhaustedTargetSkipReason()`,
  `open-sse/services/combo/comboPredicates.ts`, `if (provider &&
connectionId)` перед пошуком у `exhaustedConnections`) — звичайна комбінація
  зі списком моделей, де споріднені цілі не містять власного закріпленого
  `connectionId`, а він визначається для кожної диспетчеризації лише із
  заголовка відповіді `X-OmniRoute-Selected-Connection-Id`, ніколи не
  знаходить відповідності такому ключу. У цьому поширеному випадку реальний
  захист від повторного використання щойно вичерпаного облікового запису
  наступним етапом забезпечує НЕ цей Set, а описаний вище шар збереження
  (`rateLimitedUntil` підключення тепер указує на момент у майбутньому) у
  поєднанні з тим, що ця сама захисна перевірка не додає провайдера до
  `transientRateLimitedProviders` для цієї помилки (див. «Двоетапна
  конструкція» та коментар у коді гілки
  `isAgentrouterConnectionQuotaScope` у `targetExhaustion.ts`): оскільки цей
  Set залишається без позначки, примусовий дозвіл через
  `allowRateLimitedConnection` у `combo.ts`
  (`open-sse/services/combo.ts:1005-1013`, `:2734-2738`) НЕ активується для
  решти етапів провайдера, тому фільтр `rateLimitedUntil` під час вибору
  облікових даних (`src/sse/services/auth.ts:1238`) застосовується у звичайний
  спосіб, а наступний етап або вибирає інше, усе ще придатне підключення
  agentrouter, або завершується помилкою через відсутність доступних
  облікових даних — він не повертається примусово до підключення, для якого ця
  гілка щойно встановила період відновлення.

### Двоетапна конструкція: переформулювання статусу, потім класифікація

Переформулювання статусу (`upstreamStatusRestatement.ts`) і правила
класифікації провайдерів (`open-sse/config/providerErrorRules.ts`,
`providerRuleRegistry`) — це окремі реєстри, що обидва використовують як ключі
ідентифікатор провайдера та текстові маркери, але виконуються в різних місцях
і мають різне призначення: переформулювання завчасно переписує HTTP-статус у
`chatCore.ts`; правила класифікації вибирають резервну `reason` і `scope`
блокування (`model` / `provider` / `connection`) усередині
`checkFallbackError()` (`open-sse/services/accountFallback.ts`).

Правила класифікації бачать повний **текст** помилки (необхідний для
зіставлення з маркерами тіла на кшталт `额度不足`) лише для провайдерів,
перелічених у списку дозволених `FULL_TEXT_RULE_PROVIDERS` у
`providerErrorRules.ts` — наразі це лише `"agentrouter"`. Для кожного іншого
провайдера з **вбудованого каталогу** `checkFallbackError` передає до
`getProviderErrorRuleMatch` лише структуровану помилку (`{code, type}`), якої
достатньо для правил на основі заголовка/статусу/коду, але яка не бачить
текстових маркерів у тілі. Допоміжна функція `resolveRuleMatchBody()` виконує
цей вибір: повний текст помилки для провайдерів зі списку дозволених,
структуровану помилку — для решти. Додавання **вбудованого** провайдера до
`FULL_TEXT_RULE_PROVIDERS` є явною згодою окремо для кожного провайдера — цей
механізм існує для того, щоб стандартний шлях для кожного провайдера, якого
немає в списку, залишався незмінним байт у байт.

`scope` правила (`model` / `provider` / `connection`) — це окрема явна згода,
незалежна від `FULL_TEXT_RULE_PROVIDERS`: `checkFallbackError` лише надає її
як `fallbackResult.ruleScope`, а наступні споживачі враховують її як щось
більше за інформаційну мітку лише для провайдерів зі списку дозволених
`HONORS_RULE_LOCK_SCOPE_PROVIDERS` у тому самому файлі (`із перевіркою через
honorsRuleLockScope()` — наразі лише `"agentrouter"`). Опис того, що саме
відбувається після збігу зі `scope: "connection"`, коли провайдер перебуває в
цьому списку дозволених, наведено вище в розділі «Переформульовані помилки
квоти».

**#11104 — оголошені оператором правила обходять обидва списки дозволених.** Оператор може
оголосити правило для окремого провайдера під час виконання через `settings.providerErrorRules`
(`open-sse/config/providerErrorRules.ts::setOperatorProviderErrorRules`)
без редагування цього файлу. Обмеження операторського правила за допомогою
`FULL_TEXT_RULE_PROVIDERS`/`HONORS_RULE_LOCK_SCOPE_PROVIDERS` — списків дозволених,
призначених для захисту **типової** поведінки вбудованих правил каталогу, —
зробило б механізм налаштувань неактивним для всіх провайдерів, окрім уже
зазначених у цих списках, оскільки саме оголошення правила вже є явною
згодою оператора. `resolveRuleMatchBody()` і `honorsRuleLockScope()` спочатку
перевіряють `hasOperatorRuleForProvider()`: провайдер з операторським правилом
отримує необроблений текст помилки, а оголошений ним `scope` враховується
незалежно від того, чи присутній він також у будь-якому зі списків дозволених.

**Відома прогалина — `providerRuleRegistry` ніколи не перевіряється для HTTP 400.**
Гілка `BAD_REQUEST` у `checkFallbackError` класифікує статус 400 винятково
за допомогою власних масивів шаблонів (`MODEL_ACCESS_DENIED_PATTERNS`,
`CONTEXT_OVERFLOW_PATTERNS` тощо в `accountFallback.ts`) і повертає результат
до того, як виконання досягне розташованої вище гілки
`configuredRule`/`getProviderErrorRuleMatch`. Вбудоване правило каталогу
(або операторське правило) зі `status: 400` є синтаксично коректним, але
ніколи не спрацює. Наразі жодне наявне правило не націлене на 400,
тому це не впливає на роботу в продуктивному середовищі, але для майбутнього
правила щодо 400 спочатку доведеться змінити цю гілку. Це суттєвіша зміна,
ніж додавання правила (вона перекласифіковує 400 для кожного провайдера,
який уже покладається на поведінку масивів шаблонів), і вона виходить за
межі додавання правила для одного провайдера.

### Додавання нового шлюзу, який неправильно повідомляє про квоту

1. Зареєструйте один масив правил у `statusRestatementRegistry`
   (`open-sse/config/upstreamStatusRestatement.ts`). Зберігайте `textMarkers`
   специфічними для провайдера; ніколи не використовуйте повторно загальні
   англійські фрази, що конфліктують із `CREDITS_EXHAUSTED_SIGNALS`
   (`open-sse/services/accountFallback.ts`).
2. За потреби зареєструйте правила класифікації в
   `open-sse/config/providerErrorRules.ts` (`providerRuleRegistry`), щоб
   вибрати правильну область блокування (`connection` для квоти всього
   облікового запису, `model` для помилок окремої моделі). У продуктивному
   середовищі цей крок діє лише для провайдерів, правила яких потребують
   повного тексту помилки (маркерів у тілі): додайте ідентифікатор провайдера
   до `FULL_TEXT_RULE_PROVIDERS` у тому самому файлі — інакше
   `checkFallbackError` передаватиме правилу лише структуровану помилку
   `{code, type}`, а правило на основі тексту тіла ніколи не збігатиметься
   для реального трафіку. Правила, що зіставляються винятково за
   `status`/`headers` (як у Opencode або Minimax), не потребують цієї явної
   згоди. Окремо, якщо правило оголошує `scope: "connection"` і передбачається
   справжня пауза для всього з’єднання разом із пропуском комбінації в межах
   того самого запиту (а не лише інформаційна мітка), додайте ідентифікатор
   провайдера до `HONORS_RULE_LOCK_SCOPE_PROVIDERS` у тому самому файлі —
   саме це контролює використання в стилі
   `isAgentrouterConnectionQuotaScope()` у `markAccountUnavailable()`
   (`src/sse/services/auth.ts`) та `applyComboTargetExhaustion()`
   (`open-sse/services/combo/targetExhaustion.ts`); без цього `scope`
   усе одно передається через `fallbackResult.ruleScope`, але ніщо на нього
   не реагує.
3. Додайте модульні тести за зразком
   `tests/unit/upstream-status-restatement.test.ts` і
   `tests/unit/agentrouter-error-rules.test.ts` (включно з перевірками
   not-permanent / not-creditsExhausted, а якщо провайдер потребує списку
   дозволених — також тестом, який підтверджує, що `resolveRuleMatchBody()`
   повертає повний текст лише для цього провайдера).

Зміни до `chatCore.ts`, `classifyError` або combo не потрібні.

#### Блокування з групуванням за вихідним IP (#10880)

Провайдери в `EGRESS_BUCKETED_LOCK_PROVIDERS` (сімейство opencode)
розглядаються як висхідні сервіси, згруповані за IP-адресою (безплатний рівень
opencode згрупований за IP-адресою, а не за обліковим записом — див. #9611):
статус 429, класифікований як `quota_exhausted` **або**
`rate_limit_exceeded`, призупиняє кожне з’єднання із сімейства в списку
дозволених, остання відома вихідна IP-адреса якого збігається з IP-адресою
з’єднання, що зазнало помилки, перш ніж механізм ротації зможе їх
випробувати, — це дає змогу уникнути N-1 гарантовано невдалих викликів
висхідного сервісу (за тією самою схемою, що й #10460/#10525).
`rate_limit_exceeded` включено навмисно: у шляху `markAccountUnavailable`
специфічні для opencode правила ніколи не збігаються (заголовки й тіло не
передаються до `checkFallbackError`, а opencode відсутній у
`FULL_TEXT_RULE_PROVIDERS`), тому 429, тіло якого містить текст про квоту
підписки ("monthly usage limit reached"), класифікується як `quota_exhausted`
через резервну логіку для тексту про квоту (`buildSubscriptionQuotaFallback`,
`accountFallback.ts`; пауза на 1 годину) ще до того, як буде досягнуто правило
`status_429`, тоді як 429 без тексту про квоту (звичайне обмеження частоти)
класифікується правилом `status_429` як `rate_limit_exceeded` і все одно
призупиняє все IP-сімейство. Для провайдера зі списку дозволених обмеження
частоти, згруповане за IP-адресою, є тим самим сигналом, що й вичерпана квота.
Фактичні обмеження:

- **Найкраще можливе наближення**: блокування визначає останню відому `egress_ip`
  з'єднання з `proxy_logs` (вікно 24 год, синхронно, без кешу). Холодний кеш
  (вихідну IP-адресу ніколи не перевіряли) або відсутність рядка → гілка все одно
  переводить з'єднання, що завершилося помилкою, у режим очікування (записуючи це
  так само, як зараз), але не блокує жодне споріднене з'єднання.
- **Ніколи не є термінальним**: режим очікування — це поновлюване вікно квоти
  (`testStatus: "unavailable"`); постійний стан ніколи не визначається на основі
  сигналу рівня IP. З'єднання з `disableCooling` повністю пропускають цю гілку.
- **Змінюється гранулярність блокування для сімейства зі списку дозволених**: це
  зміна області дії, а не лише оптимізація для споріднених з'єднань. opencode є
  провайдером `passthroughModels`, тому до появи цієї гілки помилка 429
  спричиняла блокування на рівні окремої МОДЕЛІ; тепер вона переводить з'єднання
  в режим очікування — зокрема й для оператора, який використовує лише одне
  з'єднання без жодного спорідненого. Саме таку гранулярність таблиця правил
  opencode вже визначає правильно (`scope: "connection"`,
  `providerErrorRules.ts`), але досі вона ніколи не застосовувалася, оскільки
  opencode не входить до `HONORS_RULE_LOCK_SCOPE_PROVIDERS`. Ця гілка самостійно
  записує режим очікування + `backoffLevel` для з'єднання, що завершилося
  помилкою, відтворюючи поведінку гілки agentrouter з областю дії на рівні
  з'єднання, і повертається — блокування на рівні моделі та загальний шлях нижче
  ніколи не виконуються.
- **Комбінований режим включено**: як і гілка agentrouter, ця область дії
  навмисно ігнорує пониження `persistUnavailableState`/`isCombo`, яке
  комбінований викликач застосовує до помилки 429. Блокування на рівні моделі —
  це не слабша форма цієї області дії, а неправильна одиниця: воно нічого не
  повідомляє про вичерпану IP-адресу, тому комбінована ротація й надалі
  витрачала б по одному гарантовано невдалому виклику на кожне споріднене
  з'єднання.
- **Безпека споріднених з'єднань**: споріднене з'єднання, яке вже перебуває в
  термінальному стані (banned/credits_exhausted) або вже має довший режим
  очікування, ніколи не перезаписується.
- **Виключний список дозволених**: розширення `EGRESS_BUCKETED_LOCK_PROVIDERS` —
  це явне рішення власника; жодної загальної інтеграції (шаблон
  #10334/#10419). Запит споріднених з'єднань використовує прив'язку до того
  самого списку дозволених, а не повторює його як SQL-літерал, тому його
  розширення залишається зміною в один рядок.
- **Ротація вихідної IP-адреси в обох напрямках**: вікно пошуку (24 год) значно
  ширше за TTL кешу вихідної IP-адреси (5 хв), тому «остання відома IP-адреса» —
  це історичні дані, а не поточний стан. Якщо проксі з'єднання змінився в межах
  цього вікна, блокування може **не охопити** справді спільну IP-адресу
  (записана IP-адреса є новою, ще не вичерпаною) — і, симетрично, може
  **перевести в режим очікування споріднене з'єднання, яке відтоді вже
  перейшло** з вичерпаної IP-адреси на іншу. У другому випадку це коштує
  спорідненому з'єднанню одного вікна режиму очікування; обидва випадки
  вважаються прийнятними обмеженнями найкращого можливого наближення для пошуку
  на основі історичних даних.
- **Вартість**: два обмежені сканування `proxy_logs` (з фільтрацією за вікном
  через `idx_pl_timestamp`), лише з частотою виникнення помилок 429. Новий
  індекс не додається (міграція 134, YAGNI). Виміряно на копії бази даних
  помірного розміру з реальним трафіком; високонавантажений екземпляр зберігає
  пропорційно більше рядків у тому самому вікні.

## Налагодження

- Комбінація з вагами відповідає `503 all_targets_cooling_down` (задано `Retry-After`, а `diagnostics.excluded` містить усі цілі зі статусами `model_lockout` / `circuit_open` / `provider_cooldown` / `unavailable`) → пул налаштований і підключений, але кожну ціль виключено таймером механізму стійкості; попередження `[COMBO] Weighted selection: every target excluded before dispatch — …` указує причини та кількість секунд, що залишилася. Відповідь `404 no_executable_targets` від тієї самої комбінації означає, що жоден таймер механізму стійкості не був задіяний (нічого запускати або всі облікові записи не пройшли перевірку доступності). Реалізовано в `open-sse/services/combo/pinRecovery.ts` на основі виключень, зібраних у `targetResolution.ts`.
- Усі ключі постачальника пропущено → перевірте як стан автоматичного вимикача, ТАК І `rateLimitedUntil`/`testStatus` кожного підключення.
- Постачальника назавжди виключено після завершення вікна скидання → код зчитує необроблений `state` замість `getStatus()`/`canExecute()`.
- Один ключ не працює, а інші мають працювати → надавайте перевагу періоду очікування підключення перед автоматичним вимикачем.
- Не працює лише одна модель → надавайте перевагу блокуванню моделі перед періодом очікування підключення.
- Стан має відновлюватися автоматично, але цього не відбувається → перевірте наявність майбутньої часової позначки та шлях читання, який оновлює прострочений стан. Постійні статуси потребують внесення змін вручну.

## Тестування стійкості (Фаза 8 · Блок C)

Окрім модульних тестів логіки стійкості, три тести перевіряють середовище виконання за
реальних умов навантаження/відмов (усі інтеграційні/нічні — жоден не блокує PR):

| Тест        | Що перевіряється                                                                                                                                                                                                                                         | Запуск                                  |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Chaos       | Фіктивний upstream-вузол спричиняє реальні затримки/скидання/тайм-аути/503; перевіряє, що автоматичний вимикач спрацьовує/відновлюється, а `checkFallbackError` класифікує 503 як помилку, від якої можна відновитися за допомогою резервного механізму. | `RUN_CHAOS_INT=1 npm run test:chaos`    |
| Heap-growth | ~500 потоків на кожен `createSSEStream` із `--expose-gc`; завершується помилкою, якщо купа перевищує граничний розмір (захист від OOM #3069).                                                                                                            | `npm run test:heap`                     |
| k6 soak     | Тривале навантаження на `/api/monitoring/health`; порогові значення p95/помилок.                                                                                                                                                                         | `k6 run tests/load/k6-soak.js` (щоночі) |

Оркеструється за допомогою `.github/workflows/nightly-resilience.yml` (cron + dispatch). У
стандартному `test:integration` тести chaos і heap автоматично пропускаються (без `RUN_CHAOS_INT`/`--expose-gc`).
