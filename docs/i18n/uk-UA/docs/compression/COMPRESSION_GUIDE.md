> Автоматично заощаджуйте 15–95% токенів у придатному для стиснення контексті. Для швидкого огляду див. [розділ про стиснення в README](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## Огляд

OmniRoute реалізує модульний конвеєр стиснення промптів, який запускається **проактивно**, перш ніж запити потрапляють до зовнішніх провайдерів. Це означає, що економія токенів відбувається прозоро — жодних змін у робочому процесі не потрібно.

```
Запит клієнта
  → Вибір стратегії стиснення
    → Є перевизначення комбінацією? → Використати налаштування комбінації
    → Досягнуто порога автозапуску? → Використати автоматичний режим
    → Є режим за замовчуванням? → Використати глобальне налаштування
    → Вимкнено? → Пропустити стиснення
  → Вибраний режим стиснення
    → Вимкнено: без стиснення
    → Легкий: безпечне очищення пробілів/форматування (~15%)
    → Стандартний: видалення слів-паразитів у стилі Caveman (~30%)
    → Агресивний: старіння історії + узагальнення (~50%)
    → Ультра: евристичне відсікання + проріджування блоків коду (~75%)
    → RTK: фільтрування з урахуванням команд виводу термінала/інструментів (діапазон 60–90% на стороні зовнішнього провайдера)
    → Комбінований: упорядкований багатоетапний конвеєр, зазвичай RTK, а потім Caveman (78–95% у придатному для стиснення контексті)
  → Стиснений запит → Провайдер
```

## Режими стиснення

### Вимкнено

Стиснення не застосовується. Усі повідомлення передаються без змін.

### Легкий режим (економія ~15%, затримка <1ms)

Найбезпечніший режим — жодних семантичних змін, лише очищення форматування:

| Метод                    | Опис                                                 |
| ------------------------ | ---------------------------------------------------- |
| `collapseWhitespace`     | Об’єднує послідовні порожні рядки та кінцеві пробіли |
| `dedupSystemPrompt`      | Видаляє дублікати системних повідомлень              |
| `compressToolResults`    | Стискає багатослівний вивід інструментів/функцій     |
| `removeRedundantContent` | Видаляє повторювані інструкції                       |
| `replaceImageUrls`       | Скорочує URI зображень із даними base64              |

**Найкраще підходить для:** постійного використання та робочих процесів, критичних до безпеки.

### Стандартний режим (економія ~30%)

Натхнений [Caveman](https://github.com/JuliusBrussee/caveman) — видаляє слова-паразити та багатослівні формулювання, зберігаючи зміст:

- Видаляє слова-паразити ("будь ласка", "я думаю", "по суті", "насправді")
- Скорочує багатослівні фрази ("для того, щоб" → "щоб", "у результаті того, що" → "оскільки")
- Видаляє надмірно ввічливі пом’якшення ("Чи не могли б ви...", "Якщо ви могли б...")
- Понад 30 правил регулярних виразів, налаштованих для промптів із програмування

**Найкраще підходить для:** щоденних процесів розробки та команд, що прагнуть заощаджувати кошти.

### Агресивний режим (економія ~50%)

Інтелектуальне керування історією для тривалих сеансів:

- **Старіння повідомлень** — старіші повідомлення поступово стискаються
- **Узагальнення результатів інструментів** — довгий вивід інструментів замінюється стислими підсумками
- **Засоби захисту структурної цілісності** — забезпечують узгодженість пар `tool_use` + `tool_result`
- **Урахування контекстного вікна** — дотримується обмежень на кількість токенів для кожної моделі

**Найкраще підходить для:** тривалих сеансів налагодження та великих кодових баз.

### Режим Ultra (економія ~75%)

Максимальне стиснення для сценаріїв із критичними обмеженнями на кількість токенів:

- **Евристичне відсікання** — видаляє повідомлення, релевантність яких нижча за порогове значення
- **Проріджування блоків коду** — стискає повторювані приклади коду
- **Обрізання за допомогою двійкового пошуку** — знаходить оптимальну точку відсікання для контекстного вікна
- Включає всі можливості агресивного режиму

**Найкраще підходить для:** випадків, коли ви неодноразово досягаєте меж контексту.

### Режим RTK (діапазон 60–90% на стороні зовнішнього провайдера)

Режим RTK оптимізовано для багатослівного виводу інструментів, що з’являється в сеансах агентів програмування:

- Виявляє класи команд/виводу, як-от `git status`, `git diff`, `git log`, засоби запуску тестів,
  збірки TypeScript/Vite/Webpack, ESLint/Biome/Prettier, аудит/встановлення npm, журнали Docker, вивід
  інфраструктури та загальний вивід оболонки
- Застосовує набори JSON-фільтрів із `open-sse/services/compression/engines/rtk/filters/`
- Імпортує фільтри схеми RTK TOML v1 із файлів `filters.toml` проєкту або глобальних файлів із перевіркою
  вбудованих тестів і контролем довіри для файлів проєкту
- Постачається з 49 вбудованими фільтрами, що містять приклади для вбудованої перевірки
- Видаляє керівні послідовності ANSI, індикатори прогресу, повторювані рядки та шум, що не потребує дій
- Зберігає збої, помилки, попередження, змінені файли, підсумки та кінцеву частину довгого виводу
- Підтримує фільтри проєкту з контролем довіри, глобальні фільтри та необов’язкове відновлення редагованого необробленого виводу

**Найкраще підходить для:** сеансів агентів із журналами оболонки, збірок, тестів, git, grep і файлового виводу.

### Комбінований режим (78–95% у придатному для стиснення контексті)

Комбінований режим запускає кілька рушіїв стиснення в детермінованому порядку. Конвеєр за замовчуванням:

```txt
RTK -> Caveman
```

Такий порядок спершу стискає вивід термінала/інструментів, а потім застосовує семантичне стиснення Caveman до
решти промпту природною мовою. Комбіновані конвеєри можна налаштувати глобально або за допомогою
комбінацій стиснення, призначених комбінаціям маршрутизації.

**Найкраще підходить для:** змішаного контексту з великими журналами інструментів разом з інструкціями користувача або підсумками асистента.

## Математика економії вхідних даних

OmniRoute документує економію завдяки стисненню з двох джерел: бенчмарків початкових проєктів і
власної композиції рушіїв OmniRoute.

| Джерело | Число з README початкового проєкту, використане тут                                                                                                 |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | на `~75%` менше вихідних токенів, `65%` середньої економії вихідних даних у бенчмарках, діапазон `22-87%` і засіб стиснення вхідних даних на `~46%` |
| RTK     | економія `60-90%` для виводу команд; приклад сеансу: `~118,000 -> ~23,900` токенів, або `79.7%` економії (`~80%`)                                   |

Для корисного навантаження інструментів/контексту, що перекривається, стандартна комбінація OmniRoute послідовно застосовує рушії:

```txt
RTK -> Caveman
```

Сукупна економія є мультиплікативною, а не адитивною:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Показник `78-95%` застосовується, коли і RTK, і Caveman можуть скоротити те саме вхідне/контекстне корисне навантаження.
Режим вихідних відповідей Caveman є окремим: коли його ввімкнено, використовуйте власні показники економії вихідних даних Caveman (`65%`
у середньому, `~75%` у заголовку, діапазон `22-87%`). Загальна економія на оплаті залежить від співвідношення запитів і відповідей.

### Що насправді означає "придатний"

Заявлений діапазон 15-95% є реальним, але він стосується лише **надлишкового або багатослівного** вмісту — повторюваних
рядків помилок, журналу збірки, що засмічується тим самим попередженням, надмірного виводу `grep`/читання файлу. Це
**не** означає, що кожен запит заощаджує стільки.

Перевірено емпірично (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): запуск
`stacked` (RTK + Caveman) для блоку `tool_result` у форматі Anthropic, що містить 300 однакових
рядків помилок, забезпечив **95.93% економії токенів / 96.26% економії символів** — цілком у межах заявленого
діапазону. Але запуск того самого конвеєра для звичайного, ненадлишкового виводу інструмента (чистого списку збігів `grep`,
короткого читання файлу, звичайного розмовного тексту) цілком очікувано забезпечує **майже нульову економію**, оскільки
немає нічого повторюваного, що можна було б видалити, а `validateCompression()` (`validation.ts`) відмовляється надсилати
переписаний вміст, який видалив би або змінив блоки коду, URL-адреси, заголовки, версії чи ідентифікатори констант У ВЕРХНЬОМУ РЕЄСТРІ.

Це очікувана й безпечна поведінка, а не помилка: сеанс програмування, під час якого переважно читаються або перевіряються через `grep` чисті файли,
матиме помірну загальну економію навіть за повністю ввімкненого стиснення, тоді як сеанс, що стикається з циклом помилок
або надмірно балакучим лінтером, продемонструє повний діапазон 78-95% для такого трафіку. Не використовуйте низький
сукупний відсоток економії одного сеансу як доказ неправильного налаштування стиснення — спершу перевірте, чи
справді базовий вивід інструмента був надлишковим.

## Візуалізація економії токенів

```
Без стиснення:       47K токенів надіслано до LLM
З Lite:              40K токенів надіслано          (15% економії — безпечно, завжди ввімкнено)
З Standard:          33K токенів надіслано          (30% економії — правила caveman-speak)
З Aggressive:        24K токенів надіслано          (50% економії — старіння + підсумовування)
З Ultra:             12K токенів надіслано          (75% економії — евристичне відсікання)
З RTK:               19K-5K токенів надіслано       (60-90% економії на виводі команд/інструментів)
З Stacked:           10K-2.5K токенів надіслано     (78-95% для придатного діапазону RTK+Caveman)
```

## Конфігурація

### Панель керування

Перейдіть до `Dashboard → Context & Cache`:

- **Caveman** — вибір режиму, мовні пакети, попередній перегляд та глобальні налаштування за замовчуванням
- **RTK** — попередній перегляд фільтра команд, налаштування безпеки RTK та каталог фільтрів
- **Compression Combos** — іменовані конвеєри двигунів, призначені для комбінацій маршрутизації
- **Auto-Trigger Threshold** — автоматичне ввімкнення стиснення, коли кількість токенів перевищує поріг

### Перевизначення для кожної комбінації

У `Dashboard → Context & Cache → Compression Combos` призначте комбінацію стиснення комбінації маршрутизації:

```txt
Combo: "free-tier-fallback"
  Compression Combo: "coding-agent-stack"
  Pipeline: RTK -> Caveman
  Targets:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Це дозволяє використовувати стекове стиснення для безкоштовних/кодуючих провайдерів, зберігаючи полегшений режим для платних підписок.

Це призначення "Перевизначення для кожної комбінації" є іншим елементом керування, ніж перевизначення **режиму стиснення комбінації маршрутизації** (Default/Off/Lite/Standard/Aggressive/Ultra) — це перевизначення не вибирає іменований конвеєр комбінації стиснення; воно просто встановлює поле `compressionMode`, яке використовується `resolveCompressionPlan`. Його можна встановити або на картці комбінації (`Dashboard → Combos`), або, починаючи з #6760, для кожної комбінації маршрутизації у списку "Assign to routing" на `Dashboard → Context & Cache → Compression Combos`, поруч із прапорцем призначення конвеєра, описаним вище. Обидва інтерфейси зберігаються через ту саму кінцеву точку `PUT /api/combos/{id}`.

### Перевизначення для кожного запиту

Надішліть заголовок запиту `x-omniroute-compression`, щоб перевизначити план стиснення для одного запиту. Він має найвищий пріоритет — він переважає над перевизначенням комбінації маршрутизації, активним профілем, автозапуском та панеллю за замовчуванням. Невідомі значення ігноруються (запит ніколи не відхиляється), а глобальний головний перемикач все ще керує всім: коли стиснення вимкнено глобально, заголовок не може його ввімкнути. Значення:

| Значення      | Ефект                                                                                                              |
| :------------ | :----------------------------------------------------------------------------------------------------------------- |
| `off`         | Без стиснення для цього запиту.                                                                                    |
| `default`     | Профіль за замовчуванням, отриманий з панелі (ігнорує активний профіль). Втратні двигуни залишаються вимкненими.   |
| `safe`        | Те саме, що й пропуск заголовка: лише дедуплікація та згортання пробілів.                                          |
| `allow-lossy` | Зберегти план оператора цього запиту, включаючи зведення, фільтри релевантності та переписування стилів.           |
| `engine:<id>` | Один двигун, коли ввімкнено, наприклад `engine:rtk`. Це одноразове включення для цього двигуна для кожного запиту. |
| `<combo>`     | Іменована комбінація, спочатку співставляється за назвою (без урахування регістру), потім за ідентифікатором.      |

Без `allow-lossy`, `engine:<id>` або іменованої комбінації втратні двигуни не застосовуються. Запит все ще отримує дедуплікацію сесії та згортання пробілів, коли стиснення увімкнено.

Застосований план повертається у заголовку відповіді `X-OmniRoute-Compression: <mode>; source=<source>`, де `<source>` є одним з `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` або `off`.

## Подяки

Правила стиснення стандартного режиму натхненні проєктом **[Caveman](https://github.com/JuliusBrussee/caveman)** від **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) — вірусним проєктом «навіщо використовувати багато токенів, коли достатньо кількох». Caveman повідомляє про `~75%` менше токенів виводу, середню економію виводу `65%` за результатами тестів, діапазон економії виводу `22-87%` та інструмент стиснення вводу на `~46%`.

Режим RTK натхненний **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** від **[RTK AI](https://github.com/rtk-ai)** — високопродуктивним проєктом стиснення виводу команд для термінала, збирання, тестування, git і фільтрації виводу інструментів. RTK повідомляє про економію `60-90%`, а приклад сеансу в README демонструє економію `~80%`.

## Розширені системи стиснення

Окрім 7 стандартних режимів, OmniRoute включає кілька розширених систем стиснення, які працюють автоматично залежно від контексту.

### Стиснення з урахуванням кешу

Деякі провайдери (наприклад, Anthropic з кешуванням підказок) підтримують **кешування підказок**, що дозволяє їм кешувати частини підказки для зменшення витрат і затримки. Коли кешування увімкнено, агресивне стиснення може насправді **зашкодити** продуктивності, оскільки воно змінює кешовані токени, роблячи кеш недійсним.

Модуль `cachingAware.ts` вирішує цю проблему шляхом **виявлення контексту кешування** та **відповідного коригування стратегії стиснення**.

#### Як це працює

1.  **Виявлення контексту кешування** — Сканує тіло запиту на наявність маркерів `cache_control`
2.  **Визначення провайдерів кешування** — Перевіряє, чи підтримує цільовий провайдер кешування
3.  **Коригування стратегії** — Знижує рівень `aggressive`/`ultra` до `standard` для провайдерів кешування
4.  **Пропуск системної підказки** — Системні підказки зазвичай кешуються, тому не стискайте їх
5.  **Використання детермінованих перетворень** — Використовуйте лише ті перетворення, які дають послідовний результат

#### Приклад коду

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Маркер кешу
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Коли використовувати

Стиснення з урахуванням кешу **завжди увімкнено** — конфігурація не потрібна. Воно активується лише коли:

- Запит має маркери `cache_control`
- Цільовий провайдер підтримує кешування підказок (Anthropic, OpenAI тощо)

### Прогресивне старіння

Довгі розмови накопичують багато обмінів повідомленнями, але старіші обміни стають менш релевантними. Модуль `progressiveAging.ts` **знижує якість повідомлень за відстанню обміну**:

- **Останні обміни (0-3)**: Зберігаються дослівно (повна деталізація)
- **Середні обміни (4-8)**: Легке стиснення (пробіли, очищення форматування)
- **Старі обміни (9+)**: Стиснення в стилі "печерної людини" (видалення заповнювачів, узагальнення)
- **Дуже старі обміни (20+)**: Сильно узагальнені або відкинуті

#### Приклад коду

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ще 50 обмінів ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // Перші 3 обміни: дослівно
  light: 8, // Обміни 4-8: легке стиснення
  moderate: 20, // Обміни 9-20: стиснення в стилі "печерної людини"
  // Обміни 21+: сильне узагальнення
});

// saved = кількість збережених токенів
```

#### Коли використовувати

Прогресивне старіння **завжди увімкнено** для режимів `aggressive` та `ultra`. Воно особливо ефективне для:

- Тривалих сесій кодування
- Багатоденних розмов
- Агентних робочих процесів з багатьма викликами інструментів

### Режим виведення "печерної людини"

Модуль `outputMode.ts` вставляє **інструкції системної підказки**, щоб змусити саму модель створювати стислий, лаконічний вивід (у стилі "печерної людини").

#### Як це працює

Замість стиснення вхідних даних, цей режим додає системну підказку, наприклад:

> "Відповідай мінімальною кількістю слів. Пропускай люб'язності. Використовуй короткі речення."

Це особливо добре працює для:

- Генерації коду (лаконічніший вивід = менше токенів)
- Швидких запитань і відповідей (немає потреби в розгорнутих поясненнях)
- Пакетної обробки (максимізація пропускної здатності)

#### Коли використовувати

Режим виведення "печерної людини" є **опціональним** — встановіть його через комбіновану конфігурацію:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "outputMode": "caveman"
    }
  }
}
```

Фаза 4 узагальнила його в каталог компонованих стилів виведення: `OUTPUT_STYLE_CATALOG` у `open-sse/services/compression/outputStyles/catalog.ts`. Кожен стиль — це інструкція системної підказки, яка змушує саму модель створювати дешевший вивід; стилі можуть бути увімкнені разом і вставляються в порядку каталогу.

| -------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |

Кожен стиль має три рівні інтенсивності — `lite`, `full`, `ultra` — і кожен рівень завершується спільним застереженням про межі (boundaries clause), яке зберігає блоки коду, шляхи до файлів, команди, рядки помилок, URL-адреси та ідентифікатори без змін.

#### Як працює ін’єкція

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) зіставляє вибір із каталогом (невідомі ідентифікатори та стилі, що не відповідають локалі, відкидаються, це ніколи не призводить до помилки), об’єднує вибрані інструкції в порядку каталогу, додає застереження про межі **один раз** і вставляє результат на початок системного промпту після єдиного маркера ідемпотентності (`[OmniRoute Output Styles]`) — повторне застосування не виконує жодних дій. Якщо для виявленої мови запиту є переклад, замість англійської вставляється локалізована інструкція.

#### Як увімкнути

На панелі керування: **Context → Settings → Compression** — по одному рядку для кожного стилю з перемикачем увімк./вимк. та вибором рівня. Програмно конфігурація стиснення зберігає вибір як:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Зворотна сумісність: комбіноване налаштування застарілого `outputMode: "caveman"` все ще працює і відображається на `terse-prose`, що байт-в-байт ідентично старій ін’єкції для кожної застарілої мови.

Вибір мови: якщо `languageConfig.enabled` увімкнено, `autoDetect` вибирає мову останнього повідомлення користувача (той самий детектор, що й у вхідних рушіях); вимкнення `autoDetect` закріплює `defaultLanguage`. Вимкнено → English.

Матриця стиль × мова закріплена в `tests/unit/compression/output-styles-i18n-matrix.test.ts`: новий стиль не може бути випущений без принаймні перекладу на pt-BR (або явного відстежуваного винятку), а існуючий стиль не може непомітно втратити локаль. Щоб додати стиль, див. [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### Стиснення результатів інструментів

Модуль `toolResultCompressor.ts` надає **5 спеціалізованих стратегій стиснення** для результатів роботи інструментів (виклики функцій, виводи агентів, результати пошуку тощо):

1. **Стиснення результатів пошуку** — видаляє зайві результати, залишає топ-N
2. **Стиснення читання файлів** — обрізає великі файли, зберігає заголовки/імпорти
3. **Стиснення виконання коду** — зберігає лише необхідні stdout/stderr
4. **Стиснення запитів до бази даних** — обмежує кількість рядків, видаляє детальні метадані
5. **Стиснення відповідей API** — видаляє порожні поля (null), стискає масиви

#### Коли використовувати

Стиснення результатів інструментів **завжди увімкнено**, коли присутні виклики інструментів. Налаштування не потрібне.

### Каскадний конвеєр (Stacked Pipeline)

Каскадний режим запускає **кілька рушіїв послідовно** — зазвичай спочатку RTK (економія 60-90% на виводі інструментів), потім Caveman (додаткова економія 30% на залишку тексту). Це забезпечує **загальну економію 78-95%**.

#### Як це працює

```
Вхід (1000 токенів)
  → RTK (фільтр з урахуванням команд) → 200 токенів
    → Caveman (видалення зайвих слів) → 140 токенів
  → Вихід (140 токенів, 86% економії)
```

#### Коли використовувати

Використовуйте каскадний режим для:

- Робочих процесів з інтенсивним використанням інструментів (агентне програмування, дослідження)
- Пакетної обробки, чутливої до витрат
- Коли потрібна максимальна економія токенів

Налаштування через комбінацію:

```json
{
  "strategy": "auto",
  "config": {
    "auto": {
      "modePack": "stacked"
    }
  }
}
```

## Перевизначення стиснення для комбінацій

Ви можете перевизначити глобальний режим стиснення **для кожної комбінації окремо**, щоб точніше налаштувати поведінку
для різних сценаріїв використання:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "auto": {
      "weights": { "taskFit": 0.5 },
      "modePack": "quality-first"
    }
  },
  "compressionOverride": {
    "mode": "aggressive",
    "stackedPipelines": ["rtk", "caveman"],
    "preserveToolDefinitions": true
  }
}
```

Це корисно для:

- **Комбінацій для програмування**: використовуйте режим `aggressive` для тривалих сеансів
- **Комбінацій для швидких запитань і відповідей**: використовуйте режим `lite` для швидких відповідей
- **Комбінацій з інтенсивним використанням інструментів**: використовуйте режим `stacked` для максимальної економії
- **Комбінацій для робочого середовища**: використовуйте режим `cache-aware` для провайдерів із кешуванням
