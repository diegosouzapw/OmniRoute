> Автоматично заощаджуйте 15–95% токенів у придатному для стиснення контексті. Короткий огляд наведено в [розділі README про стиснення](../README.md#%EF%B8%8F-prompt-compression--save-15-95-eligible-tokens-automatically).

## Огляд

OmniRoute реалізує модульний конвеєр стиснення промптів, який запускається **проактивно**, перш ніж запити надходять до зовнішніх провайдерів. Це означає, що токени заощаджуються прозоро — жодних змін у вашому робочому процесі не потрібно.

```
Запит клієнта
  → Засіб вибору стратегії стиснення
    → Є перевизначення комбінацією? → Використати налаштування комбінації
    → Досягнуто порога автоматичного запуску? → Використати автоматичний режим
    → Режим за замовчуванням? → Використати глобальне налаштування
    → Вимкнено? → Пропустити стиснення
  → Вибраний режим стиснення
    → Вимкнено: без стиснення
    → Легкий: безпечне очищення пробілів і форматування (~15%)
    → Стандартний: видалення зайвих слів у телеграфному стилі (~30%)
    → Агресивний: ущільнення історії + узагальнення (~50%)
    → Ультра: евристичне скорочення + проріджування блоків коду (~75%)
    → RTK: фільтрування виводу термінала/інструментів з урахуванням команд (діапазон 60–90% для висхідних запитів)
    → Стековий: упорядкований багатоетапний конвеєр, зазвичай RTK, а потім Caveman (діапазон 78–95% для придатного вмісту)
  → Стиснений запит → Провайдер
```

## Режими стиснення

### Вимкнено

Стиснення не застосовується. Усі повідомлення передаються без змін.

### Легкий режим (економія ~15%, затримка <1 мс)

Найбезпечніший режим — жодних семантичних змін, лише очищення форматування:

| Метод                    | Опис                                                         |
| ------------------------ | ------------------------------------------------------------ |
| `collapseWhitespace`     | Об’єднує послідовні порожні рядки та видаляє кінцеві пробіли |
| `dedupSystemPrompt`      | Видаляє дублікати системних повідомлень                      |
| `compressToolResults`    | Стискає багатослівний вивід інструментів/функцій             |
| `removeRedundantContent` | Видаляє повторювані інструкції                               |
| `replaceImageUrls`       | Скорочує URI даних зображень у форматі base64                |

**Найкраще підходить для:** постійного використання та робочих процесів із критичними вимогами до безпеки.

### Стандартний режим (економія ~30%)

Натхнений [Caveman](https://github.com/JuliusBrussee/caveman) — видаляє слова-паразити та багатослівні формулювання, зберігаючи зміст:

- Видаляє слова-паразити («будь ласка», «я думаю», «по суті», «насправді»)
- Скорочує багатослівні фрази («для того, щоб» → «щоб», «унаслідок того, що» → «оскільки»)
- Видаляє надмірно ввічливі пом’якшувальні формулювання («Чи не могли б ви...», «Якщо ви могли б...»)
- Понад 30 правил із регулярними виразами, налаштованих для промптів, пов’язаних із програмуванням

**Найкраще підходить для:** щоденних процесів розробки та команд, які прагнуть зменшити витрати.

### Агресивний режим (економія ~50%)

Інтелектуальне керування історією для тривалих сеансів:

- **Ущільнення повідомлень із часом** — старіші повідомлення поступово стискаються
- **Стиснення результатів інструментів** — довгий вивід інструментів скорочується або опускається (перші/останні рядки,
  фільтрування рядків зі збігами, ущільнення ключів JSON)
- **Запобіжники структурної цілісності** — забезпечують узгодженість пар `tool_use` + `tool_result`
- **Урахування контекстного вікна** — дотримується обмежень на кількість токенів для кожної моделі

**Найкраще підходить для:** тривалих сеансів налагодження та великих кодових баз.

### Ультрарежим (економія ~75%)

Максимальне стиснення для сценаріїв із критичними обмеженнями на кількість токенів:

- **Евристичне скорочення** — скорочення токенів у прозі на основі оцінювання
- **Збереження структури** — відокремлені блоки коду, вбудований код, URL-адреси та ідентифікатори
  замінюються заповнювачами, а потім дослівно відновлюються без скорочення
- **Необов’язковий рівень SLM** — невелика локальна модель може уточнювати скорочення, якщо її налаштовано
- Не залежить від агресивного режиму: не запускає ущільнення історії, стиснення результатів інструментів
  або резервний узагальнювач (лише збій рівня SLM може спрямувати резервний прохід через
  агресивний режим)

**Найкраще підходить для:** ситуацій, коли ви постійно досягаєте меж контексту.

### Режим RTK (діапазон 60–90% для висхідних запитів)

Режим RTK оптимізовано для багатослівного виводу інструментів, який з’являється в сеансах агентів для програмування:

- Виявляє класи команд/виводу, як-от `git status`, `git diff`, `git log`, засоби запуску тестів,
  збірки TypeScript/Vite/Webpack, ESLint/Biome/Prettier, аудит/установлення npm, журнали Docker, вивід
  інфраструктури та загальний вивід оболонки
- Застосовує набори фільтрів JSON із `open-sse/services/compression/engines/rtk/filters/`
- Імпортує фільтри схеми RTK TOML v1 із файлів проєкту або глобальних файлів `filters.toml` із перевіркою
  вбудованих тестів і контролем довіри для файлів проєкту
- Постачається з 55 вбудованими фільтрами та вбудованими прикладами перевірки
- Видаляє керівні послідовності ANSI, індикатори перебігу, повторювані рядки та некорисний шум
- Зберігає збої, помилки, попередження, змінені файли, підсумки та кінцеву частину довгого виводу
- Підтримує проєктні фільтри з контролем довіри, глобальні фільтри та необов’язкове відновлення редагованого необробленого виводу

**Найкраще підходить для:** сеансів агентів із транскриптами команд оболонки, збірок, тестів, git, grep і файлового виводу.

### Стековий режим (діапазон 78–95% для придатного вмісту)

Стековий режим запускає кілька рушіїв стиснення в детермінованому порядку. Типовий конвеєр:

```txt
RTK -> Caveman
```

Такий порядок спочатку ущільнює вивід термінала/інструментів, а потім застосовує семантичне скорочення Caveman до
решти промпту природною мовою. Стекові конвеєри можна налаштувати глобально або через
комбінації стиснення, призначені комбінаціям маршрутизації.

**Найкраще підходить для:** змішаного контексту з великими журналами інструментів, а також інструкціями користувача чи підсумками асистента.

## Розрахунок економії від вихідних проєктів

OmniRoute документує економію завдяки стисненню з двох джерел: тестів продуктивності вихідних проєктів і
власної композиції рушіїв OmniRoute.

| Джерело | Показник із README вихідного проєкту, використаний тут                                                                                             |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caveman | на `~75%` менше вихідних токенів, у середньому `65%` економії вихідних даних у тестах, діапазон `22-87%` і засіб стиснення вхідних даних на `~46%` |
| RTK     | `60-90%` економії для виводу команд; приклад сеансу: `~118,000 -> ~23,900` токенів, або `79.7%` економії (`~80%`)                                  |

Для перекривних корисних даних інструментів/контексту стандартна комбінація OmniRoute послідовно застосовує рушії:

```txt
RTK -> Caveman
```

Сукупна економія є мультиплікативною, а не адитивною:

```txt
сукупна  = 1 - (1 - економія RTK) * (1 - економія вхідних даних Caveman)
середня  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
діапазон = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

Показник `78-95%` застосовується, коли і RTK, і Caveman можуть скоротити ті самі вхідні/контекстні корисні дані.
Режим вихідних даних відповіді Caveman є окремим: коли його ввімкнено, використовуйте власні показники економії вихідних даних Caveman (у середньому `65%`,
основний заявлений показник `~75%`, діапазон `22-87%`). Загальна економія на оплаті залежить від співвідношення запитів і вихідних даних.

### Що насправді означає "придатний"

Заявлений діапазон 15-95% є реальним, але він застосовується лише до **надлишкового або багатослівного** вмісту — повторюваних
рядків помилок, журналу збірки, що засмічується тим самим попередженням, завеликого виводу `grep`/читання файлу. Це
**не** означає, що кожен запит забезпечує таку економію.

Перевірено емпірично (`tests/unit/compression/stacked-compression-tool-result-savings.test.ts`): запуск
`stacked` (RTK + Caveman) для блока `tool_result` у форматі Anthropic, що містить 300 однакових
рядків помилок, забезпечив **95.93% економії токенів / 96.26% економії символів** — точно в межах заявленого
діапазону. Але запуск того самого конвеєра для звичайного, ненадлишкового виводу інструментів (чистого списку збігів `grep`,
короткого читання файлу, звичайного тексту розмови) цілком правильно забезпечує **майже нульову економію**, оскільки
немає нічого повторюваного, що можна було б видалити, а `validateCompression()` (`validation.ts`) не дозволяє надсилати
переписаний вміст, який вилучає або змінює блоки коду, URL-адреси, заголовки, версії чи ідентифікатори констант, записані ВЕЛИКИМИ ЛІТЕРАМИ.

Це очікувана й безпечна поведінка, а не помилка: сеанс програмування, у якому переважно читаються чисті файли або виконується `grep`,
матиме помірну загальну економію навіть із повністю ввімкненим стисненням, тоді як сеанс, що стикається з циклом помилок
або багатослівним лінтером, забезпечить повний діапазон 78-95% для такого трафіку. Не вважайте низький
сукупний відсоток економії окремого сеансу доказом неправильного налаштування стиснення — спочатку перевірте, чи
був базовий вивід інструментів справді надлишковим.

## Візуалізація економії токенів

```
Без стиснення:       47K токенів надіслано до LLM
З Lite:              40K токенів надіслано          (15% економії — безпечний, завжди ввімкнений)
З Standard:          33K токенів надіслано          (30% економії — правила caveman-speak)
З Aggressive:        24K токенів надіслано          (50% економії — старіння + узагальнення)
З Ultra:             12K токенів надіслано          (75% економії — евристичне відсікання)
З RTK:               19K-5K токенів надіслано       (60-90% економії на виводі команд/інструментів)
З Stacked:           10K-2.5K токенів надіслано     (78-95% для придатного діапазону RTK+Caveman)
```

## Конфігурація

### Панель керування

Перейдіть до `Dashboard → Context & Cache`:

- **Caveman** — вибір режиму, мовні пакети, попередній перегляд і глобальні налаштування за замовчуванням
- **RTK** — попередній перегляд фільтрації команд, налаштування безпеки RTK і каталог фільтрів
- **Compression Combos** — іменовані конвеєри рушіїв, призначені комбінаціям маршрутизації
- **Auto-Trigger Threshold** — автоматичне ввімкнення стиснення, коли кількість токенів перевищує порогове значення

### Перевизначення для окремої комбінації

У `Dashboard → Context & Cache → Compression Combos` призначте комбінацію стиснення комбінації
маршрутизації:

```txt
Комбінація: "free-tier-fallback"
  Комбінація стиснення: "coding-agent-stack"
  Конвеєр: RTK -> Caveman
  Цілі:
    1. if/kimi-k2.7-code
    2. if/qwen3.8-max-preview
```

Це дає змогу використовувати багаторівневе стиснення для безплатних постачальників або постачальників
для програмування, зберігаючи полегшений режим для платних підписок.

Це призначення «Перевизначення для окремої комбінації» є іншим елементом керування, ніж перевизначення
**режиму стиснення комбінації маршрутизації** (Default/Off/Lite/Standard/Aggressive/Ultra/Codex Responses —
схема цього поля також приймає `rtk`, `stacked` і `omniglyph`) — це перевизначення не вибирає іменований
конвеєр комбінації стиснення; воно лише задає поле `compressionMode`, яке використовує
`resolveCompressionPlan`. Його можна встановити на картці комбінації (`Dashboard → Combos`) або, починаючи
з #6760, для кожної комбінації маршрутизації в списку «Assign to routing» у
`Dashboard → Context & Cache → Compression Combos`, безпосередньо поруч із прапорцем призначення конвеєра,
описаним вище. Обидва інтерфейси зберігають зміни через той самий кінцевий пункт `PUT /api/combos/{id}`.

### Перевизначення для окремого запиту

Надішліть заголовок запиту `x-omniroute-compression`, щоб перевизначити план стиснення для окремого
запиту. Він має найвищий пріоритет — він переважає перевизначення комбінації маршрутизації, активний
профіль, автоматичне спрацьовування та значення Default на панелі. Невідомі значення ігноруються
(запит ніколи не відхиляється), а глобальний головний перемикач усе одно керує всім: якщо стиснення
глобально вимкнено, заголовок не може його ввімкнути. Значення:

| Значення      | Ефект                                                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `off`         | Не застосовувати стиснення до цього запиту.                                                                             |
| `default`     | Профіль Default, визначений панеллю (активний профіль ігнорується). Рушії з втратами вимкнено.                          |
| `safe`        | Те саме, що й відсутність заголовка: лише дедуплікація та згортання пробілів.                                           |
| `allow-lossy` | Зберегти операторський план цього запиту, включно з підсумками, фільтрами релевантності та переписуванням стилю.        |
| `engine:<id>` | Один рушій, якщо його ввімкнено, наприклад `engine:rtk`. Це явна згода на використання цього рушія для окремого запиту. |
| `<combo>`     | Іменована комбінація: спочатку зіставляється за назвою без урахування регістру, а потім за ідентифікатором.             |

Без `allow-lossy`, `engine:<id>` або іменованої комбінації рушії з втратами не застосовуються.
Коли стиснення ввімкнено, до запиту все одно застосовуються дедуплікація сеансу та згортання пробілів.

Застосований план повертається в заголовку відповіді `X-OmniRoute-Compression: <mode>; source=<source>`,
де `<source>` має одне зі значень: `request-header`, `routing-override`, `active-profile`,
`auto-trigger`, `default` або `off`.

## Подяки

Правила стиснення стандартного режиму натхненні проєктом **[Caveman](https://github.com/JuliusBrussee/caveman)** від **[JuliusBrussee](https://github.com/JuliusBrussee)** (⭐ 51K+) — вірусним проєктом «навіщо використовувати багато токенів, коли достатньо кількох». Caveman повідомляє про `~75%` менше токенів виводу, `65%` середньої економії виводу за результатами тестів, діапазон економії виводу `22-87%` та інструмент стиснення вводу на `~46%`.

Режим RTK натхненний **[RTK - Rust Token Killer](https://github.com/rtk-ai/rtk)** від **[RTK AI](https://github.com/rtk-ai)** — високопродуктивним проєктом стиснення виводу команд для фільтрації виводу термінала, збирання, тестів, git та інструментів. RTK повідомляє про економію `60-90%`, а приклад сеансу в його README демонструє економію `~80%`.

## Розширені системи стиснення

Окрім 7 режимів, описаних вище (вихідний код також підтримує режими `codex-responses` і
`omniglyph`, які не розглядаються в цьому посібнику), у наведених нижче розділах описано функції,
що працюють усередині цих режимів або разом із ними: стиснення результатів інструментів і поступове старіння
є кроками 1 і 2 агресивного рушія (агресивний режим і крок `aggressive`
стекового конвеєра), стековий конвеєр визначає роботу стекового режиму, стиснення
з урахуванням кешу знижує рівень `aggressive` і `ultra` до `standard` для провайдерів
кешування, доки стиснення ввімкнене, а режим виводу Caveman і стилі виводу — це необов'язкові інструкції системної підказки,
які за замовчуванням вимкнені та формують вивід моделі замість стиснення запиту.

### Стиснення з урахуванням кешу

Деякі провайдери (наприклад, Anthropic із кешуванням підказок) підтримують **кешування підказок**,
що дає їм змогу кешувати частини підказки для зниження витрат і затримки. Коли
кешування ввімкнено, агресивне стиснення насправді може **погіршити** продуктивність,
оскільки воно змінює кешовані токени, роблячи кеш недійсним.

Модуль `cachingAware.ts` розв’язує цю проблему шляхом **виявлення контексту кешування** та
відповідного **коригування стратегії стиснення**.

#### Як це працює

1. **Виявлення контексту кешування** — сканує тіло запиту на наявність маркерів `cache_control`
2. **Визначення провайдерів кешування** — перевіряє, чи підтримує цільовий провайдер кешування
3. **Коригування стратегії** — знижує рівень `aggressive`/`ultra` до `standard` для провайдерів кешування
4. **Пропуск системної підказки** — системні підказки зазвичай кешуються, тому їх не слід стискати

Допоміжна функція стратегії також повертає прапорець `deterministicOnly`, але конструктор плану використовує
лише стратегію — наразі жоден подальший компонент не зчитує цей прапорець.

#### Приклад коду

```ts
import {
  detectCachingContext,
  getCacheAwareStrategy,
} from "@omniroute/open-sse/services/compression/cachingAware";

const body = {
  model: "anthropic/claude-sonnet-4.5",
  messages: [{ role: "user", content: "Hello" }],
  cache_control: { type: "ephemeral" }, // ← Маркер кешу
};

const ctx = detectCachingContext(body, { provider: "anthropic" });
// → { hasCacheControl: true, provider: "anthropic", targetFormat: null, isCachingProvider: true }

const strategy = getCacheAwareStrategy("aggressive", ctx);
// → { strategy: "standard", skipSystemPrompt: true, deterministicOnly: true }
```

#### Коли використовувати

Стиснення з урахуванням кешу **завжди ввімкнене** — налаштування не потрібне. Воно активується щоразу,
коли стиснення ввімкнене й цільовий провайдер підтримує кешування підказок (Anthropic, OpenAI
тощо); явні маркери `cache_control` не потрібні — для зниження рівня достатньо самого
провайдера кешування, а самі лише маркери ніколи цього не спричиняють (виявлення маркерів забезпечує телеметрію
кешу, а не ухвалення рішення щодо стратегії).

### Поступове старіння

У довгих розмовах накопичується багато обмінів повідомленнями, але старіші обміни стають менш
релевантними. Модуль `progressiveAging.ts` **поступово спрощує повідомлення залежно від відстані в обмінах**
(відстань вимірюється від кінця розмови). З типовими параметрами постачання
(`verbatim: 2, light: 2, moderate: 3`):

- **Останні 2 репліки (відстань ≤ 2)**: зберігаються дослівно
- **Відстань 3**: примітивне стиснення (видалення слів-паразитів)
- **Відстань 4+**: повідомлення асистента підсумовуються; повідомлення користувача скорочуються до першого
  рядка з обмеженням у 120 символів; інші ролі залишаються без змін. Системні промпти, уже зістарені
  повідомлення та останнє повідомлення користувача завжди зберігаються дослівно незалежно від відстані.
  Нічого не видаляється повністю, а діапазон `light`
  недосяжний зі стандартними налаштуваннями постачання (`light` дорівнює `verbatim`).

#### Приклад коду

```ts
import { applyAging } from "@omniroute/open-sse/services/compression/progressiveAging";

const messages = [
  { role: "system", content: "You are a helpful assistant" },
  { role: "user", content: "What is 2+2?" },
  { role: "assistant", content: "4" },
  // ... ще 50 реплік ...
];

const { messages: aged, saved } = applyAging(messages, {
  verbatim: 3, // останні 3 репліки: дослівно
  light: 8, // відстань <= 8: легке стиснення
  moderate: 20, // відстань <= 20: примітивне стиснення
  fullSummary: 5, // вимагається типом, але не зчитується кодом розподілу за діапазонами
  // відстань > 20: підсумовується (асистент) / зберігається перший рядок (користувач)
});

// saved = кількість збережених токенів
```

#### Коли використовувати

Прогресивне старіння **завжди ввімкнене** для режиму `aggressive` — це крок 2 у
`compressAggressive()`. Режим Ultra його не запускає. Воно
особливо ефективне для:

- Тривалих сеансів програмування
- Розмов, що тривають кілька днів
- Агентних робочих процесів із великою кількістю викликів інструментів

### Режим примітивного виведення

Режим примітивного виведення додає **інструкції системного промпту**, які просять саму модель
відповідати стисло — рівень `lite` просить давати лаконічні відповіді повними реченнями, `full`
просить її «відповідати стисло, як розумна печерна людина», а `ultra` — давати телеграфні відповіді;
інструкції лише просять про це, але не можуть цього гарантувати. Запити отримують їх через
`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`):
`open-sse/handlers/chatCore.ts` спочатку визначає вибір за допомогою прошарку зворотної сумісності
(`resolveOutputStyleSelection()` у
`open-sse/services/compression/outputStyles/backCompat.ts`), який, коли `outputStyles`
порожній, зіставляє ввімкнений `cavemanOutputMode` зі стилем виведення `terse-prose` на рівні
`cavemanOutputMode.intensity` (див. розділ «Зворотна сумісність» нижче); непорожній вибір `outputStyles`
використовується без змін, після чого `cavemanOutputMode.enabled` та `intensity` не мають
жодного впливу, тоді як його перемикач `autoClarity` продовжує діяти. `outputMode.ts` містить
тексти інструкцій (`CAVEMAN_INSTRUCTION_BY_LANGUAGE`), обхід обробки вмісту та
допоміжну функцію розміщення, яку використовує вставлення; його власний засіб вставлення `applyCavemanOutputMode()` не має
викликів у робочому середовищі.

#### Як це працює

Цей режим не стискає вхідні дані. Він додає блок інструкцій до системного промпту
(див. розділ «Як працює вставлення» нижче), а будь-який режим стиснення вхідних даних, вибраний для запиту,
усе одно запускається після цього для тіла, яке тепер містить цей блок. Перед спільним
положенням про обмеження, яким завершується кожен рівень, англійський рівень `full` містить такий текст:

> «Відповідай стисло, як розумна печерна людина. Відкидай артиклі (a/an/the), слова-паразити (just/really/basically/actually/simply), люб’язності та невпевнені формулювання. Фрагменти дозволені. Використовуй короткі синоніми (big, а не extensive; fix, а не implement). Зберігай без змін усю технічну суть, код, помилки, URL-адреси та ідентифікатори».

Це особливо добре працює для:

- Генерування коду (стисліше виведення = менше токенів)
- Швидких запитань і відповідей (немає потреби в розлогих поясненнях)
- Пакетної обробки (максимальна пропускна здатність)

#### Коли використовувати

Режим примітивного виведення є **необов’язковим**. Коли стиснення ввімкнене (`enabled: true`, головний перемикач
на сторінці налаштувань стиснення), увімкніть його за допомогою `cavemanOutputMode.enabled`; `intensity`
вибирає `lite`, `full` або `ultra`:

```json
{
  "enabled": true,
  "cavemanOutputMode": {
    "enabled": true,
    "intensity": "full"
  }
}
```

Перемикач **Режим виведення** комбінації стиснення (`outputMode`, рівень у `outputModeIntensity`)
установлює той самий стан для запитів, до яких застосовується ця комбінація, а
MCP-інструмент `omniroute_set_compression_engine` записує його через свій булевий аргумент `outputMode`.
Непорожній вибір `outputStyles` має пріоритет над цим перемикачем. На
панелі керування ввімкнення стилю виведення **Стисла проза** вставляє той самий блок (див. розділ «Стилі
виведення» нижче).

| Лаконічна CJK (文言)                       | `terse-cjk`   | Відповідь рівня `full`/`ultra` класичною китайською мовою (文言); `lite` лише вимагає коротких відповідей без службових слів, люб’язностей або прикрас.                                                                                  | zh (обмежено локаллю, див. нижче)             |

Кожен стиль має три рівні інтенсивності — `lite`, `full`, `ultra` — і кожен рівень
завершується спільним положенням про межі (`SHARED_BOUNDARIES` у `outputMode.ts`), яке
зберігає блоки коду, шляхи до файлів, команди, помилки та URL без змін. Тексти рівнів
`terse-prose` і `terse-cjk` також додають до цього списку ідентифікатори.

`terse-cjk` обмежено локаллю `zh` у двох місцях. На сторінці налаштувань стиснення
його рядок відображається лише тоді, коли мовою інтерфейсу панелі керування є китайська
(`zh-CN` або `zh-TW`), а `applyOutputStyles()` додає його лише тоді, коли визначена мова
запиту (див. розділ «Вибір мови» нижче) — `zh`. Приховування рядка не очищає збережений
вибір `terse-cjk`: API налаштувань приймає будь-який id стилю, а збереження інших стилів
на сторінці не видаляє його. Під час запиту перевірка мови в `applyOutputStyles()` є
єдиним обмеженням за локаллю.

#### Як працює додавання

`applyOutputStyles()` (`open-sse/services/compression/outputStyles/apply.ts`) зіставляє
вибір із каталогом (невідомі id та стилі, що не відповідають локалі, відкидаються без
помилки; якщо в результаті не визначено жодного стилю, тіло залишається без змін із
пропуском як `no_styles`), об’єднує вибрані інструкції в порядку каталогу,
додає положення про межі **один раз** (разом із положенням про безпеку,
`SAFETY_BOUNDARIES` або його перекладом, коли вибрано `less-code` чи `ponytail`) і
починає блок з одного маркера ідемпотентності (`[OmniRoute Output Styles]`), тому
повторне застосування нічого не змінює. Коли для визначеної мови (див. розділ «Вибір
мови» нижче) є переклад, замість англійської інструкції додається локалізована.

Для тіла з непорожнім масивом `messages` перевірка ідемпотентності виконується перед
обходом за вмістом: якщо маркер `[OmniRoute Output Styles]` уже міститься в полі
верхнього рівня `system` (рядку або масиві блоків вмісту) чи в системному повідомленні
з рядковим вмістом, тіло залишається без змін як `already_applied`, а перевірка ключових
слів не виконується. Інакше обхід за вмістом (`shouldBypassCavemanOutputMode()` у
`open-sse/services/compression/outputMode.ts`) перевіряє текст останніх трьох
повідомлень незалежно від їхньої ролі та пропускає застосування стилів для всього ходу,
коли цей текст відповідає ключовим словам безпеки, незворотних дій або уточнення чи
залежній від порядку послідовності: `first`, `then`, `after that`, `before`, `rollback`
або `backup`, після яких у межах 240 символів іде `delete`, `drop`, `migrate`, `deploy`
або `release`. Обхід виконується, доки перемикач **Auto-Clarity Bypass**
(`cavemanOutputMode.autoClarity`, увімкнений за замовчуванням) увімкнено; вимкнення
перемикача пропускає перевірку ключових слів.

Коли обхід дозволяє обробити хід, `placeSystemInstruction()` (у тому самому файлі), яка
ніколи не створює новий `messages[0]`, розміщує блок у першому знайденому місці з
наведених нижче:

1. Початкове системне повідомлення з рядковим вмістом: блок додається після його тексту.
2. Поле верхнього рівня `system`: блок додається після тексту рядка або як новий
   текстовий блок до масиву блоків вмісту.
3. Перше наступне системне повідомлення з рядковим вмістом: блок додається після його
   тексту.
4. Нічого з наведеного вище: блок розміщується в новому системному повідомленні
   наприкінці `messages`.

Для тіла без масиву `messages` (або з порожнім масивом) обхід за вмістом не виконується,
а поле верхнього рівня `system` не перевіряється. Блок додається після тексту рядкового
поля `instructions`, якщо це поле вже не містить маркер `[OmniRoute Output Styles]`;
у такому разі тіло залишається без змін як `already_applied`. Коли тіло не має
рядкового поля `instructions`, але містить `input` (рядок або масив), блок стає
`instructions`, замінюючи будь-яке нерядкове значення, яке містило це поле. Тіло без
рядкового поля `instructions` і без рядкового чи масивного `input` залишається без змін
і пропускається як `no_messages`.

#### Як увімкнути

На панелі керування: **Контекст стиснення → Налаштування стиснення**
(`/dashboard/context/settings`), розділ стилів виведення: один рядок на кожен стиль із
перемикачем увімкнення/вимкнення та селектором рівня. Стилі додаються, коли саме
стиснення ввімкнено (головний перемикач сторінки, `enabled`). Перемикач
**Автоматичний обхід Clarity** розташований на сторінці **Caveman**
(`/dashboard/context/caveman`) у картці **Режим виведення**. Програмно конфігурація
стиснення зберігає вибір у такому вигляді:

```json
{
  "outputStyles": [
    { "id": "i-have-adhd", "level": "full" },
    { "id": "less-code", "level": "lite" }
  ]
}
```

Зворотна сумісність: доки `outputStyles` порожній, застаріле налаштування
`cavemanOutputMode.enabled` зіставляється з `terse-prose` на рівні
`cavemanOutputMode.intensity`. Тоді блок починається з маркера
`[OmniRoute Output Styles]`, тоді як застарілий інжектор `applyCavemanOutputMode()`
додавав `[OmniRoute Caveman Output Mode]`. Під маркером текст відповідає застарілій
вставці мовами en, pt-BR, es, de, fr, it, ru, id і vi; у ja та zh він містить один
додатковий пробіл перед положенням про межі. `terse-prose` перекладено мовами pt-BR,
es, de, fr, it, ru, zh, ja, id і vi, тому запит, для якого визначено мову `hu`, отримує
англійський текст, тоді як застарілий інжектор використовував угорський.

Вибір мови стилю виведення (`resolveOutputStyleLanguage()` у
`outputStyles/apply.ts`): коли `languageConfig.enabled` увімкнено, `autoDetect` бере
зразок з останнього повідомлення користувача в масиві `messages` запиту, яке містить
текст (рядковий вміст або `text` його частин вмісту), і запускає для нього детектор
рушія Caveman (`detectCompressionLanguage()`). Детектор повертає `zh` для тексту з
ієрогліфами Han без кани; інакше він повертає ту з мов `it`, `pt-BR`, `es`, `de`,
`fr`, `ru`, `ja`, `hu` та `id`, яка має найбільше збігів із підказками, а якщо збігів
немає — `en`. Текст, який він не може класифікувати, отримує англійську мову, а не
`defaultLanguage`, і `vi` ніколи не визначається, хоча стилі постачаються з текстом
мовою `vi`. Тіло Responses API зберігає свої репліки в `input`, з якого зразок не
береться, тому воно отримує `defaultLanguage`, а потім англійську. Якщо жодне
повідомлення користувача в `messages` не містить тексту або `autoDetect` вимкнено,
застосовується `defaultLanguage`, а потім англійська. Коли `languageConfig.enabled`
вимкнено, мовою є англійська — якщо тільки до запиту не застосовується комбінація
стиснення (комбінація, призначена комбінації маршрутизації запиту, або типова
комбінація стиснення, до якої chatCore повертається для вбудованого складеного
конвеєра): застосування комбінації вмикає `languageConfig.enabled` для цього запиту та
встановлює `defaultLanguage` з мовних пакетів комбінації (збережене значення, якщо
воно є одним із пакетів комбінації, інакше — перший пакет комбінації, який за
замовчуванням має значення `en`), тоді як збережене значення `autoDetect` (увімкнене
за замовчуванням) усе одно застосовується. Рушій введення Caveman вибирає мову пакета
правил інакше — окремо для кожної текстової частини, а коли автоматичне визначення
вимкнено, вибір обмежується `enabledPacks`.

Матрицю стилів і мов закріплено тестом
`tests/unit/compression/output-styles-i18n-matrix.test.ts`: кожен стиль каталогу
повинен мати запис у `BASELINE_LANGUAGES` тесту; стиль, який не обмежено локаллю,
повинен постачатися з перекладом pt-BR (стиль `terse-cjk`, обмежений локаллю,
звільняється від цієї вимоги), якщо тільки його не внесено до `KNOWN_ENGLISH_ONLY`,
де можуть міститися лише стилі без будь-яких перекладів — внесений до списку стиль,
який має хоча б один переклад, спричиняє помилку тесту; також стиль не проходить тест,
якщо втрачає мову, зазначену в його записі `BASELINE_LANGUAGES`. Щоб додати стиль,
див. [EXTENDING_COMPRESSION.md](./EXTENDING_COMPRESSION.md#adding-an-output-style).

### Стиснення результатів інструментів

`compressToolResult()` у `open-sse/services/compression/toolResultCompressor.ts`
стискає текст результату інструмента за допомогою **5 стратегій**. Вони перевіряються
в такому порядку, і результат визначає перша ввімкнена стратегія, перевірка якої
відповідає вмісту:

1. **`fileContent`**: вміст із 3 або більше рядків, у якому принаймні один рядок, без урахування
   початкових відступів, починається з `import `, `export `, `function `, `class `,
   `const `, `let `, `var ` або `return ` (ключове слово та пробіл), чи з `if`,
   `for` або `while`, після якого йде `(` або ` (`, зберігає перші 20 і останні 5 рядків,
   позначаючи пропущену середину.
2. **`grepSearch`**: вміст із принаймні одним рядком у форматі `<path>:<digits>:`,
   де текст перед першою двокрапкою не містить пробілів, зберігає лише такі рядки, не
   більше 30, після чого додає кількість решти збігів і список файлів зі збігами;
   усі інші рядки відкидаються. Одного такого рядка достатньо для запуску стратегії, тож
   рядок журналу, що починається з позначки часу на кшталт `12:30:45`, також враховується.
3. **`shellOutput`**: вивід, що містить послідовність ANSI CSI (`ESC[`, потім цифри або
   крапки з комою, а далі літера, як у кодах кольорів) чи символ `$`, після якого будь-де
   в тексті йде пробільний символ, втрачає ці послідовності (інші керівні послідовності,
   як-от `ESC[?25l` або OSC-послідовність заголовка вікна, зберігаються) і зберігає
   останні 50 рядків, об'єднуючи послідовні повторювані рядки. Оскільки ця перевірка
   виконується перед `json` і `errorMessage`, вивід JSON або помилки, що містить такий
   `$`, ніколи не доходить до них, поки `shellOutput` увімкнено.
4. **`json`**: коректні дані JSON завдовжки понад 2 000 символів, що починаються з `{`
   або `[` (після необов'язкових пробільних символів) і успішно розбираються, стискаються:
   для масиву з понад 7 елементами зберігаються перші 5 і останні 2 елементи та їхня
   загальна кількість, а для об'єкта зберігаються перші 20 ключів, при цьому значення
   кожного вкладеного об'єкта або масиву замінюється заповнювачем `{…N keys}` (для
   масиву N — це його довжина), а маркер `_remaining_<N>_keys` указує кількість ключів,
   відкинутих після перших 20. Скалярні значення копіюються повністю, тому об'єкт із
   20 або меншою кількістю ключів без вкладених значень лише отримує інші відступи —
   мінімізований об'єкт збільшується в кількості символів і залишається без змін.
5. **`errorMessage`**: вивід, що будь-де й у будь-якому регістрі містить `error:`,
   `error ` (слово, після якого йде пробіл, як у `no error found`), `[error]`,
   `exception:`, `exception `, `[exception]` або `traceback`, зберігає перший рядок,
   наступні 10 рядків і останні 3, замінюючи рядки між ними маркером
   `… [N frames elided] …`. Маркер з'являється лише тоді, коли після першого рядка
   є понад 13 рядків, тому вивід помилки з 14 або меншою кількістю рядків не
   скорочується (якщо рядків 12 або 13, останні 3 дублюють уже збережені рядки).

Після збігу зі стратегією, навіть якщо вона нічого не заощаджує, наступні стратегії не
випробовуються. Коли відповідна стратегія не заощаджує жодних оцінених токенів (довжина ÷ 4,
округлена вгору) — наприклад, для схожого на код файлу з 25 або меншою кількістю рядків
чи JSON-масиву завдовжки понад 2 000 символів із 7 або меншою кількістю елементів —
агресивний рушій зберігає початковий результат інструмента: обидва виклики
(`compressAggressive()` і `compressAnthropicToolResultBlock()`) зберігають оригінал,
коли значення `saved` дорівнює 0 або менше, тоді як сама функція `compressToolResult()`
усе одно повертає результат цієї стратегії. Етап обробки результату інструмента не є
остаточним: резервний механізм узагальнення рушія все ще може скоротити повідомлення
`tool` або `function` завдовжки понад 8 192 символи (`maxTokensPerMessage`, 2 048,
помножене на 4).

#### Коли використовувати

Стиснення результатів інструментів — це крок 1 агресивного рушія (`compressAggressive()` у
`open-sse/services/compression/aggressive.ts`), тому воно виконується в агресивному режимі
та на етапі `aggressive` складеного конвеєра. Воно стискає повідомлення `tool` і `function`
у форматі OpenAI та текст усередині блоків Anthropic `tool_result`. Кожна стратегія має
власний перемикач у `aggressive.toolStrategies`; за замовчуванням усі вони ввімкнені.
На панелі керування перемикачі розташовані в поданні **Advanced** сторінки Caveman, коли
стиснення ввімкнено, а режимом за замовчуванням є Aggressive.

### Складений конвеєр

Складений режим запускає **кілька рушіїв послідовно** — зазвичай спочатку RTK
(заощадження 60–90% на виводі інструментів), а потім Caveman для решти тексту
(заощадження ~46% вхідних даних). У поєднанні це дає **діапазон заощадження 78–95%
для придатних даних** (див. розрахунок заощаджень вище): `1 - (1 - 0.60..0.90) × (1 - 0.46)`
у середньому становить ≈89%.

#### Як це працює

```
Вхідні дані (1000 токенів)
  → RTK (фільтр з урахуванням команд) → 200 токенів
    → Caveman (видалення зайвого тексту) → 108 токенів
  → Вихідні дані (108 токенів, заощадження ~89%)
```

#### Коли використовувати

Використовуйте складений режим для:

- Робочих процесів із великою кількістю інструментів (агентне програмування, дослідження)
- Пакетної обробки, чутливої до вартості
- Випадків, коли потрібне максимальне заощадження токенів

Складені конвеєри налаштовуються через глобальний параметр стиснення `stackedPipeline`
або через іменовану комбінацію стиснення, призначену комбінації маршрутизації (див.
перевизначення для окремої комбінації вище), — а не через `modePack` автоматичної
комбінації (це поле лише змінює ваги вибору моделі автоматичною комбінацією, а `stacked`
не є допустимою назвою набору).

## Перевизначення стиснення для комбінацій

Ви можете перевизначити глобальний режим стиснення **для кожної окремої комбінації**, щоб точніше налаштувати поведінку
для різних сценаріїв використання:

```json
{
  "id": "coding-combo",
  "strategy": "priority",
  "config": {
    "weights": { "taskFit": 0.5 },
    "modePack": "quality-first"
  },
  "compressionOverride": "aggressive"
}
```

Це корисно для:

- **Комбінацій для програмування**: використовуйте режим `aggressive` для тривалих сеансів
- **Комбінацій для швидких запитань і відповідей**: використовуйте режим `lite` для швидких відповідей
- **Комбінацій з інтенсивним використанням інструментів**: використовуйте режим `stacked` для максимальної економії
- **Робочих комбінацій**: не вмикайте перевизначення для провайдерів із кешуванням — постійно активне
  коригування з урахуванням кешу автоматично знижує `aggressive`/`ultra` до `standard`
  (режим `cache-aware` не можна вибрати)
