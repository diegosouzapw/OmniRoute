AgentBridge — це проксі MITM (Man-in-the-Middle, «людина посередині») від OmniRoute, який перехоплює HTTPS-трафік від ШІ-агентів IDE та перенаправляє його через уніфікований механізм маршрутизації OmniRoute. Він підтримує **10 агентів IDE** — Antigravity, Kiro, GitHub Copilot, GHE Copilot, OpenAI Codex, Cursor, Zed, Claude Code, Open Code і Trae (досліджується) — завдяки чому OmniRoute є MITM-проксі з найширшим на ринку охопленням ШІ-помічників для програмування.

**Розташування панелі керування:** `/dashboard/tools/agent-bridge`
**Група на бічній панелі:** Інструменти (після Cloud Agents)
**Див. також:** [`TRAFFIC_INSPECTOR.md`](./TRAFFIC_INSPECTOR.md) — моніторинг усього перехопленого трафіку в реальному часі; `docs/security/MITM-TPROXY-DECRYPT.md` (git; не включено до `/docs`) — режим прозорого перехоплення та дешифрування Linux TPROXY, керований маршрутом `/api/tools/agent-bridge/tproxy`.

## §1 Огляд

### Що таке AgentBridge?

Коли агент IDE (наприклад, GitHub Copilot, Cursor або Claude Code) виконує виклик API, він підключається безпосередньо до зовнішнього постачальника ШІ (OpenAI, Anthropic тощо). AgentBridge прозоро перехоплює це з’єднання на рівні TLS — без необхідності змінювати конфігурацію агента — і перенаправляє запит через OmniRoute.

Це дає змогу:

- **Перенаправляти будь-якого агента до будь-якого постачальника**: Copilot взаємодіє з OpenAI? Перенаправте його до Anthropic Claude, Gemini або будь-якого з 352 постачальників OmniRoute.
- **Застосовувати зіставлення моделей**: `gemini-3-flash` → `claude-sonnet-4.7` прозоро на рівні обробника.
- **Спостерігати за всім трафіком агентів**: кожен перехоплений запит публікується в [Інспекторі трафіку](./TRAFFIC_INSPECTOR.md).
- **Застосовувати механізми відмовостійкості OmniRoute**: комбінована маршрутизація, автоматичні вимикачі, резервні варіанти та відстеження витрат також працюють для трафіку агентів IDE.

## §2 Архітектура

### 2.1 Огляд компонентів

```
Агент IDE (VS Code / Cursor / тощо)
    │  HTTPS (порт 443)
    ▼
/etc/hosts — 127.0.0.1 api.githubcopilot.com   ← переспрямування DNS
    │
    ▼
src/mitm/server.cjs  (порт 443, дочірній процес CJS)
    │  визначає ціль за SNI із заголовка Host
    │  генерує окремий TLS-сертифікат для кожного SNI, підписаний CA AgentBridge
    ├── Збіг зі списком обходу? → наскрізна передача TCP (без розшифрування)
    ├── Збіг із ціллю? → fetch → маршрутизатор OmniRoute (порт 20128)
    │       └── handler.intercept() — TypeScript
    │               ├── maskSecrets() для тіла/заголовків запиту
    │               ├── TrafficBuffer.push() — публікує в Інспекторі трафіку
    │               └── fetchRouter() → /v1/chat/completions
    └── Немає збігу? → наскрізна передача TCP (без розшифрування)
```

### 2.2 Сервер MITM (`src/mitm/server.cjs`)

Основний сервер MITM працює як дочірній процес Node.js CJS (щоб уникнути переписування наявної кодової бази CJS). Він:

- Прослуховує порт 443 (потребує привілеїв або `authbind`/`setcap`)
- Приймає тунелі CONNECT від ОС (через переспрямування DNS у `/etc/hosts`)
- Генерує окремі TLS-сертифікати для кожного SNI, підписані CA AgentBridge (`DATA_DIR/mitm/ca.crt`)
- Визначає цільового агента за заголовком Host через реєстр `targets/index.ts`
- Передає запити на рівень обробників TypeScript через HTTP за адресою `http://127.0.0.1:20128`

`TARGET_HOSTS` завантажується з `DATA_DIR/mitm/targets.json` (записується `targets/index.ts` під час запуску), що дає змогу виконувати динамічні оновлення без перезапуску сервера CJS.

> **Модель кореневого CA (#6684).** Описана вище модель із сертифікатом для кожного SNI, підписаним CA,
> є збережуваною моделлю кореневого CA, доданою в #6684 (`src/mitm/cert/rootCa.ts` +
> `src/mitm/_internal/rootCaShim.cjs`, із повторним використанням криптографічної реалізації CA/кінцевого сертифіката, уже
> перевіреної для TPROXY у `src/mitm/tproxy/dynamicCert.ts`) — вона замінює
> старіший єдиний статичний самопідписаний кінцевий сертифікат (`src/mitm/cert/generate.ts`, який усе ще
> обмежений лише хостами antigravity), на наявність якого вказує проста пара
> `server.crt`/`server.key` на диску. **Поведінка під час міграції**: свіже встановлення (без попереднього
> `server.crt`) автоматично отримує модель кореневого CA; встановлення, яке вже
> довіряє старому статичному кінцевому сертифікату, продовжує використовувати його, доки оператор не встановить
> `MITM_ROOT_CA_ENABLED=true` і не перезапустить міст (`src/mitm/cert/migration.ts`
> є чистою функцією прийняття рішення — довірений MITM CA, здатний підписати кінцевий сертифікат для
> **будь-якого** хоста, має суттєво ширші можливості, ніж старий кінцевий сертифікат із фіксованим SAN, тому
> перемикання ніколи не відбувається непомітно для встановлення, якому вже довіряють). Сертифікат CA встановлюється
> в той самий слот сховища довіри `omniroute-mitm.crt`, який використовував старий кінцевий сертифікат
> (`cert/install.ts::installCaCert`) — очищення подвійної довіри не потрібне.

### 2.3 Базовий обробник (`src/mitm/handlers/base.ts`)

Усі обробники агентів розширюють `MitmHandlerBase`:

```ts
export abstract class MitmHandlerBase {
  abstract readonly agentId: AgentId;

  abstract intercept(
    req: IncomingMessage,
    res: ServerResponse,
    body: Buffer,
    mappedModel: string
  ): Promise<void>;

  // Захищені допоміжні методи: fetchRouter, pipeSSE, hookBufferStart, hookBufferUpdate
}
```

Кожен обробник викликає `hookBufferStart()` перед проксіюванням і `hookBufferUpdate()` після завершення. Вони додають записи `InterceptedRequest` до `globalTrafficBuffer` (див. [Інспектор трафіку](./TRAFFIC_INSPECTOR.md), §4).

### 2.4 Реєстр цілей (`src/mitm/targets/`)

Кожен агент має декларативний файл цілі:

```ts
// src/mitm/targets/copilot.ts
export const COPILOT_TARGET: MitmTarget = {
  id: "copilot",
  name: "GitHub Copilot",
  hosts: ["api.githubcopilot.com", "copilot-proxy.githubusercontent.com"],
  port: 443,
  endpointPatterns: ["/chat/completions", "/v1/chat/completions"],
  defaultModels: [{ id: "gpt-4o", name: "GPT-4o", alias: "gpt-4o" }],
  handler: () => import("../handlers/copilot"),
  riskNoticeKey: "providers.riskNotice.oauth",
};
```

Реєстр (`targets/index.ts`) експортує `ALL_TARGETS` і створює `DATA_DIR/mitm/targets.json` під час запуску.

### 2.5 Наскрізна передача та список обходу (`src/mitm/passthrough.ts`)

**Список обходу** (перевіряється першим і має пріоритет над збігом із ціллю):

- Стандартні шаблони: хости банків, `.gov.`, постачальники OAuth/SSO (Okta, Auth0) тощо
- Користувацькі шаблони: зберігаються в таблиці БД `agent_bridge_bypass`
- Хости зі списку обходу отримують прозорий TCP-тунель — TLS **ніколи не розшифровується**

**Наскрізна передача за замовчуванням** (немає збігу з ціллю й хост не входить до списку обходу):

- Також отримує TCP-тунель — з’єднання ніколи не розриваються
- Запобігає порушенню загального системного HTTPS-трафіку з боку AgentBridge

Пріоритет маршрутизації:

```
список обходу → збіг із ціллю → наскрізна передача
```

### 2.6 Сертифікат CA висхідного з’єднання (`src/mitm/upstreamTrust.ts`)

Для корпоративних мережевих середовищ із власним CA:

```bash
AGENTBRIDGE_UPSTREAM_CA_CERT=/path/to/corporate-ca.pem
```

Якщо значення задано, воно налаштовує глобальний диспетчер `undici` із додатковим сертифікатом CA, даючи AgentBridge змогу підключатися до висхідних постачальників через корпоративні проксі-сервери термінації TLS.

### 2.7 Маскування секретів (`src/mitm/maskSecrets.ts`)

Незалежний сканер із чистою реалізацією застосовується до тіл запитів і заголовків з обліковими даними
**до того**, як вони потраплять до буфера Інспектора трафіку або будь-якого журналу. Він виконує один лінійний прохід:

- Токени з префіксами `sk-` / `ak-` / `pk-` (у стилі OpenAI/Anthropic)
- Облікові дані RFC 6750 `Authorization: Bearer <token>` із пріоритетом цілого токена
- Універсальні довгі непрозорі токени (≥40 символів), включно з формами з крапками та доповненням

`sanitizeHeaders()` перетворює збережені назви на нижній регістр, детерміновано об’єднує значення масивів, відкидає
спільний список заборонених проміжних та обрамлювальних заголовків (включно з автентифікацією проксі), повністю приховує `cookie` і
`set-cookie` та передає значення облікових даних сканеру.

## §3 Налаштування

### 3.1 Запуск/зупинка MITM-сервера

Скористайтеся карткою сервера AgentBridge за адресою `/dashboard/tools/agent-bridge`:

| Дія                          | Опис                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------ |
| Запустити сервер             | Запускає `src/mitm/server.cjs` на порту 443                                    |
| Зупинити сервер              | Коректно завершує дочірній процес                                              |
| Перезапустити сервер         | Зупиняє та запускає сервер (застосовує зміни цільових моделей)                 |
| Довіряти сертифікату         | Установлює `DATA_DIR/mitm/ca.crt` у сховище довірених сертифікатів ОС          |
| Завантажити сертифікат       | Завантажує `ca.crt` для встановлення вручну                                    |
| Повторно створити сертифікат | Створює нову пару ключів ЦС (усі наявні сертифікати агентів стають недійсними) |

### 3.2 Додайте сертифікат до довірених

Сертифікат ЦС AgentBridge має бути додано до довірених в ОС, перш ніж IDE прийматимуть MITM-з’єднання.

**Linux (NSS — Chrome/Firefox):**

```bash
certutil -A -d sql:$HOME/.pki/nssdb -n "OmniRoute AgentBridge" -t CT,, -i ~/.omniroute/mitm/ca.crt
```

**macOS (Keychain):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain ~/.omniroute/mitm/ca.crt
```

**Windows (certmgr):**

```powershell
certutil -addstore -f Root $env:USERPROFILE\.omniroute\mitm\ca.crt
```

Або скористайтеся кнопкою «Довіряти сертифікату» на панелі керування (вона запускає відповідну команду для вашої ОС із запитом sudo, якщо потрібно).

#### IDE на базі Electron ігнорують сховище довірених сертифікатів ОС (`NODE_EXTRA_CA_CERTS`)

Деякі IDE — зокрема **Antigravity IDE** та інші застосунки на основі Electron / VS Code — постачаються
із власним середовищем виконання Node.js, яке **не використовує сховище довірених сертифікатів ОС** для вихідних
`fetch`/HTTPS-запитів. Додавання ЦС до довірених на рівні ОС/NSS достатньо для нативного **бекенду**
IDE (наприклад, сервера мови Go, який використовує набір ЦС операційної системи), однак **фронтенд Electron**
все одно не зможе встановити TLS-з’єднання — це проявляється так, ніби користувача _виведено з облікового запису_,
або у вигляді _«помилки з’єднання»_, хоча журнал MITM показує, що початкові виклики бекенду повертають `200`.
Потрібно виконати два кроки, і обидва є важливими:

1. Явно вкажіть середовищу виконання шлях до ЦС:
   ```bash
   export NODE_EXTRA_CA_CERTS=/path/to/omniroute-agentbridge-ca.crt
   ```
2. **Запустіть IDE із цієї оболонки.** Запуск за допомогою піктограми на робочому столі / Dock / меню «Пуск»
   **не** успадковує експортовані змінні оболонки, а `~/.config/environment.d/*.conf` застосовується лише після
   нового входу в графічний сеанс. Спочатку повністю закрийте IDE — через блокування одного екземпляра в Electron
   повторний запуск лише переводить фокус на наявний процес, а нове середовище ігнорується.

Описаний вище крок із додаванням до сховищ ОС і NSS залишається необхідним (мережевий стек Chromium, який використовують деякі
потоки автентифікації, читає користувацьке сховище NSS і має власні статичні закріплення сертифікатів для `*.googleapis.com`,
які перевизначаються локально довіреним ЦС). `NODE_EXTRA_CA_CERTS` додатково охоплює шлях Node `fetch`.

### 3.3 Маршрутизація DNS

Для кожного агента, запити якого потрібно перехоплювати, його API-хости мають визначатися як `127.0.0.1`. AgentBridge автоматично керує записами `/etc/hosts`, коли ви перемикаєте DNS для агента в майстрі налаштування.

Приклад записів `/etc/hosts` для GitHub Copilot:

```
127.0.0.1 api.githubcopilot.com
127.0.0.1 copilot-proxy.githubusercontent.com
```

### 3.4 Зіставлення моделей

Використовуйте таблицю зіставлення моделей у картці кожного агента, щоб визначити зіставлення джерело → ціль:

| Вихідна модель (нативна для агента) | Цільова модель (OmniRoute) |
| ----------------------------------- | -------------------------- |
| `gpt-4o`                            | `claude-sonnet-4.7`        |
| `*` (символ підстановки)            | `claude-haiku-4.7`         |

Символ підстановки `*` зіставляє будь-яку нерозпізнану модель із зазначеною цільовою моделлю. Зіставлення зберігається в таблиці `agent_bridge_mappings`.

> **Порада — визначте справжні ідентифікатори моделей агента.** IDE може надсилати назви моделей, які відрізняються від
> підписів у її інтерфейсі та змінюються між основними версіями. Наприклад, **Antigravity 2** передає
> `gemini-3.1-pro-low`, `gemini-pro-agent` і `gemini-3.1-flash-lite` через мережу, а не
> `gemini-2.5-pro`, зазначену в старішій документації. Надішліть одне повідомлення в чаті без відповідного зіставлення:
> MITM реєструє точне вхідне значення `model:` і пропускає запит без змін. Зіставте це буквальне значення, після чого
> наступний запит буде перехоплено й спрямовано до вашої цільової моделі.

### 3.5 Повідомлення про ризик

AgentBridge перехоплює облікові дані (токени OAuth, ключі API), які IDE використовує для автентифікації у зовнішніх постачальників. Вони **маскуються перед записуванням до журналу** (див. §2.7), але доступні MITM-рівню OmniRoute. Під час першої активації кожного агента відображається модальне вікно з повідомленням про ризик, яке можна закрити.

### 3.6 Обслуговування та діагностика

На панелі керування є картка **Обслуговування та діагностика** (`AgentBridgeMaintenanceCard`, у `src/app/(dashboard)/dashboard/tools/agent-bridge/components/`), яка надає доступ до операційних маршрутів MITM, що раніше не мали інтерфейсу користувача. Її підзаголовок: _«Самостійно перевірте конвеєр перехоплення, скасуйте залишкові зміни стану системи та перенесіть налаштування між комп’ютерами»._ Допоміжні клієнтські функції картки містяться в `src/lib/inspector/agentBridgeMaintenanceApi.ts`.

| Кнопка                   | Маршрут                                | Що вона робить                                                                                                                                                                                          |
| ------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Діагностика**          | `GET /api/tools/agent-bridge/diagnose` | Запускає самоперевірку конвеєра перехоплення та показує звіт за кожною перевіркою (✓/✗ + підказка щодо усунення проблеми).                                                                              |
| **Відновити**            | `POST /api/tools/agent-bridge/repair`  | Скасовує залишковий системний стан MITM (записи підміни DNS, кореневий ЦС, системний проксі), що лишився після збою або SIGKILL. Ідемпотентна — повідомляє «Немає чого відновлювати», якщо стан чистий. |
| **Видалити ЦС**          | `DELETE /api/tools/agent-bridge/cert`  | Скасовує довіру до кореневого ЦС MITM і видаляє його зі сховища довіри ОС (явно, ідемпотентно). Відображається лише тоді, коли ЦС наразі довірений; потребує вбудованого підтвердження «Видалити ЦС?».  |
| **Експорт конфігурації** | `GET /api/tools/agent-bridge/config`   | Завантажує переносну конфігурацію JSON (див. §3.7).                                                                                                                                                     |
| **Імпорт конфігурації**  | `POST /api/tools/agent-bridge/config`  | Завантажує раніше експортовану конфігурацію JSON (див. §3.7).                                                                                                                                           |

**Діагностичні перевірки** (`summarizeDiagnostics()` у `src/mitm/inspector/diagnostics.ts`). Маршрут запускає перевірку з побічними ефектами для кожного пункту й передає логічні значення до чистої функції узагальнення; повертається єдиний вердикт `healthy` разом із підказкою для кожної невдалої перевірки:

| Назва перевірки    | Що вона перевіряє                                             | Підказка в разі невдачі                                                                                                                                |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `server-running`   | Процес сервера MITM активний                                  | «Сервер MITM не запущено. Запустіть його на вкладці AgentBridge.»                                                                                      |
| `server-reachable` | Сервер MITM приймає з’єднання на своєму порту (TCP-перевірка) | «Сервер MITM не приймає з’єднання на своєму порту. Переконайтеся, що порт вільний і у вас є права для прив’язування до нього.»                         |
| `cert-exists`      | Сертифікат MITM було згенеровано на диску                     | «Сертифікат MITM ще не згенеровано. Згенеруйте його на вкладці AgentBridge.»                                                                           |
| `cert-trusted`     | Кореневий ЦС MITM міститься у сховищі довіри ОС               | «ОС не довіряє кореневому ЦС MITM, тому перехоплення TLS не працюватиме. Надайте сертифікату довіру на вкладці AgentBridge.»                           |
| `dns-configured`   | Цільові імена хостів підмінено в `/etc/hosts`                 | «Цільові імена хостів не підмінено в /etc/hosts, тому трафік ніколи не досягає проксі. Увімкніть DNS для агентів, трафік яких потрібно перехоплювати.» |

**Банер залишкового стану:** коли сторінка виявляє стан, що лишився після збою (підміна DNS / ЦС / системний проксі), на картці відображається бурштиновий банер — _«Попередній сеанс залишив системний стан (підміну DNS, ЦС або системний проксі). Запустіть відновлення, щоб очистити його.»_ — і виділяється кнопка **Відновити**. `Repair` є аналогом прапорця `--cleanup` ProxyBridge на рівні застосунку (він делегує виконання `repairMitm()` у `src/mitm/manager.ts`).

> Кореневий ЦС MITM залишається встановленим між зупинками та запусками, щоб уникнути повторних
> запитів sudo (така сама поведінка, як у mitmproxy/Charles), тому його видалення є явною
> дією **Видалити ЦС**, а не чимось, що відбувається автоматично під час зупинки.

### 3.7 Імпорт/експорт переносної конфігурації

AgentBridge може серіалізувати **налаштовуваний оператором** стан у версіонований блок JSON, щоб конфігурацію можна було відтворити на різних машинах. Серіалізатор — `src/lib/inspector/configPortability.ts` (`exportConfig()` / `importConfig()`), із валідацією за допомогою `AgentBridgeConfigSchema`.

Експорт містить рівно три компоненти (вбудовані значення за замовчуванням навмисно **НЕ** експортуються, тому імпорт ніколи не дублює їх і не конфліктує з ними):

| Поле             | Джерело                                                          | Примітки                                                                     |
| ---------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `bypassPatterns` | визначені користувачем шаблони обходу (`agent_bridge_bypass`)    | стандартні шаблони bank/gov/okta виключено                                   |
| `customHosts`    | користувацькі хости Traffic Inspector (`inspector_custom_hosts`) | кожен: `{ host, kind: "llm"\|"app"\|"custom", label? }`                      |
| `agentMappings`  | зіставлення моделей для кожного агента (`agent_bridge_mappings`) | `{ [agentId]: [{ source, target }] }` для кожного агента, що має зіставлення |

```jsonc
// GET /api/tools/agent-bridge/config
{
  "version": 1,
  "bypassPatterns": ["*.internal.example.com"],
  "customHosts": [{ "host": "api.example.com", "kind": "llm", "label": null }],
  "agentMappings": {
    "copilot": [{ "source": "gpt-4o", "target": "claude-sonnet-4.7" }],
  },
}
```

**Поведінка імпорту** (`POST /api/tools/agent-bridge/config`): шаблони обходу та зіставлення для кожного агента **замінюються повністю**; користувацькі хости додаються **ідемпотентно** (`INSERT OR IGNORE`). У відповіді повідомляється, скільки елементів кожного типу було застосовано:

```jsonc
{ "ok": true, "bypassPatterns": 1, "customHosts": 1, "agents": 1 }
```

Чого **НЕМАЄ** в конфігурації: стан роботи сервера, шляхи до сертифікатів, стан DNS для кожного агента, шлях до кореневого сертифіката вищого рівня та налаштування TPROXY — це стан хоста/середовища виконання, а не переносні параметри.

### Застосовані жорсткі правила

| Правило                              | Застосування                                                                                                               |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **#12** `sanitizeErrorMessage`       | Усі помилки обробників очищаються перед надсиланням відповіді або додаванням до буфера                                     |

### Список обходу для чутливих хостів

Список обходу гарантує, що трафік фінансових установ, постачальників OAuth/SSO та інших чутливих хостів **ніколи не розшифровується**. Їхній TLS-трафік проходить через прозорий TCP-тунель — OmniRoute ніколи не бачить відкритий текст.

Стандартні шаблони обходу включають:

- `*.bank.*`, `*.gov.*` (фінансові/державні установи)
- `*.okta.com`, `*.auth0.com`, `*.microsoft.com` (SSO/ідентифікація)
- `*.apple.com`, `*.icloud.com` (системні служби Apple)

Додані користувачем шаблони обходу зберігаються в таблиці `agent_bridge_bypass` і мають найвищий пріоритет.

### Маскування секретів

Застосовується `maskSecrets()` із `src/mitm/maskSecrets.ts`:

- До тіла кожного запиту перед `TrafficBuffer.push()`
- До кожного заголовка перед журналюванням або трансляцією

Шаблони: токени з префіксами `sk-`/`ak-`/`pk-`, токени `Bearer` і загальні токени довжиною ≥40 символів.

### Сертифікат CA висхідного сервера

Коли встановлено `AGENTBRIDGE_UPSTREAM_CA_CERT`, файл зчитується під час запуску. Якщо шлях існує, але файл неможливо прочитати, AgentBridge реєструє зрозумілу помилку й відмовляється запускатися (це запобігає непомітним збоям TLS у корпоративних середовищах).

### Відомі обмеження

- **Порт 443 потребує привілеїв**: у Linux для AgentBridge потрібно виконати `setcap 'cap_net_bind_service=+ep'` для бінарного файлу Node або запускати його через `authbind`. Майстер налаштування показує інструкції для конкретної ОС.
- **Потрібен перезапуск IDE**: після перенаправлення DNS IDE необхідно перезапустити, щоб нове зіставлення хоста набуло чинності.
- **Жорстко задані токени OAuth**: деякі агенти (Kiro, Antigravity) зберігають токени оновлення OAuth локально. Для AgentBridge вони прозорі — він бачить токен Bearer у кожному запиті, який маскується перед журналюванням.
- **Для фронтендів Electron потрібен `NODE_EXTRA_CA_CERTS`**: IDE, фронтенд яких працює у вбудованому середовищі виконання Node/Electron, ігнорують сховище довіри ОС/NSS і мають запускатися з оболонки зі встановленою змінною `NODE_EXTRA_CA_CERTS` (див. §3.2). Ознака її відсутності: бекенд IDE проходить автентифікацію (MITM показує відповіді `200`), але інтерфейс залишається незалогіненим.
- **Кілька інсталяцій однієї IDE є незалежними**: системна інсталяція (наприклад, `/usr/share/antigravity/antigravity`) і локальна користувацька інсталяція «Full» (наприклад, `~/AntigravityIDE_Full/antigravity-ide`) є окремими процесами з власними середовищами виконання — кожну потрібно перезапустити з підключеним CA. Перед перезапуском визначте за шляхом до бінарного файлу, яка саме інсталяція працює.
- **Ідентичність визначається системним промптом агента, а не маршрутизованою моделлю**: коли модель агента перепризначається іншому постачальнику, відповідь усе одно вказує на нативну ідентичність агента (наприклад, Antigravity відповідає «Я працюю на базі Gemini»), оскільки IDE додає це до системного промпту. Перевіряйте фактичний бекенд у `call_logs` / `proxy_logs` (`provider`, `model`, `target_format`), а не запитуйте модель, ким вона є.

## §6 Усунення несправностей

### Конфлікт порту 443

Якщо інший процес уже прослуховує порт 443 (вебсервер, VPN тощо):

```bash
lsof -i :443          # знайти процес
sudo fuser -k 443/tcp  # примусово завершити (використовуйте обережно)
```

Або налаштуйте непривілейований порт у параметрах AgentBridge і створіть правила перенаправлення `iptables` / `pf`.

### Сертифікат не є довіреним

Якщо після запуску AgentBridge IDE показує помилки TLS:

1. Переконайтеся, що сертифікат установлено: `security find-certificate -c "OmniRoute AgentBridge"` (macOS) або `certutil -L -d sql:$HOME/.pki/nssdb` (Linux/NSS)
2. Деякі застосунки використовують власне сховище довірених сертифікатів (Firefox, Chrome у Linux). Знову виконайте «Trust Cert» і перевірте сховище сертифікатів NSS/Firefox.
3. Перезапустіть IDE після додавання сертифіката до довірених — активні сеанси TLS використовують попередній стан довіри.

### Вихід з облікового запису IDE / «помилка з’єднання» попри довірений центр сертифікації

Ознака: після перенаправлення DNS і додавання центру сертифікації до довірених IDE на основі Electron (наприклад, Antigravity)
відкривається **без входу в обліковий запис** або показує помилку автентифікації/з’єднання, хоча журнал MITM показує, що
початкові виклики (`loadCodeAssist`, `fetchAvailableModels`, …) повертають `200`.

Причина: **вбудоване середовище виконання Node/Electron в IDE ігнорує системне сховище довіри ОС**. Нативна
серверна частина (мовний сервер на Go) довіряє центру сертифікації ОС та проходить автентифікацію, але інтерфейс Electron
— ні, тому інтерфейс користувача вважає, що підключення відсутнє.

Виправлення (обидва кроки): експортуйте `NODE_EXTRA_CA_CERTS=<ca.crt>` **і перезапустіть IDE з цієї
оболонки**, а не за допомогою значка на робочому столі. Спочатку повністю закрийте IDE — через блокування єдиного екземпляра Electron
повторний запуск лише переводить фокус на наявний процес, а нове середовище ігнорується. Див. §3.2.
Це відповідає відкритому звіту в основному проєкті, де автономний агент працює через MITM, але варіант для IDE
не працює за тих самих налаштувань.

### DNS не поширився

Перевірте, чи оновлено `/etc/hosts`:

```bash
grep "omniroute\|127.0.0.1.*github\|127.0.0.1.*cursor" /etc/hosts
```

Очистьте кеш DNS:

```bash
# macOS
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Linux (systemd-resolved)
sudo systemctl restart systemd-resolved
# Windows
ipconfig /flushdns
```

### IDE не виявлено

Автоматичне виявлення використовує типові шляхи встановлення. Якщо виявлення не вдалося, але IDE встановлено:

- Перевірте, чи не розташований виконуваний файл IDE в нестандартному місці
- Майстер налаштування все одно працюватиме — помилка виявлення означає лише, що на позначці не відображатиметься шлях встановлення

### Помилки обробника (не вдалося отримати дані від вищого сервера)

Якщо AgentBridge перехоплює запити, але всі вони завершуються помилкою:

1. Переконайтеся, що за адресою `/dashboard/providers` підключено принаймні одного постачальника
2. Перевірте журнали сервера OmniRoute: `APP_LOG_LEVEL=debug` у `.env`
3. Переконайтеся, що `OMNIROUTE_BASE_URL` вказує на правильну кінцеву точку маршрутизатора (типове значення: `http://127.0.0.1:20128`)

## §7 Довідник API

Усі маршрути мають позначки `LOCAL_ONLY` (лише loopback, перевіряється перед автентифікацією) і `SPAWN_CAPABLE`. Див. `src/server/authz/routeGuard.ts`.

Базовий шлях: `/api/tools/agent-bridge/`

| Метод               | Шлях                                           | Опис                                                                                                                             |
| ------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| GET                 | `/api/tools/agent-bridge/state`                | Глобальний стан сервера + виявлення/статус для кожного агента                                                                    |
| GET                 | `/api/tools/agent-bridge/agents`               | Список зареєстрованих агентів (ідентифікатор, ім’я, хости, працездатність, стан)                                                 |
| GET                 | `/api/tools/agent-bridge/agents/{id}`          | Стан одного агента (цільова конфігурація + виявлення + збережений стан)                                                          |
| PATCH               | `/api/tools/agent-bridge/agents/{id}`          | Оновити `setup_completed` для агента                                                                                             |
| GET                 | `/api/tools/agent-bridge/agents/{id}/detect`   | Виконати перевірку виявлення агента (`installed`, `version?`, `path?`)                                                           |
| POST                | `/api/tools/agent-bridge/agents/{id}/dns`      | Увімкнути/вимкнути DNS для агента (`{enabled: boolean}`)                                                                         |
| GET                 | `/api/tools/agent-bridge/agents/{id}/mappings` | Зіставлення моделей для агента                                                                                                   |
| PUT                 | `/api/tools/agent-bridge/agents/{id}/mappings` | Замінити зіставлення моделей                                                                                                     |
| POST                | `/api/tools/agent-bridge/server`               | Запустити/зупинити/перезапустити сервер (`action: "start"\|"stop"\|"restart"\|"trust-cert"\|"regenerate-cert"`)                  |
| GET                 | `/api/tools/agent-bridge/cert`                 | Статус сертифіката (`exists`, `trusted`, `path`)                                                                                 |
| POST                | `/api/tools/agent-bridge/cert`                 | Позначити кореневий центр сертифікації MITM як довірений (установити)                                                            |
| DELETE              | `/api/tools/agent-bridge/cert`                 | Скасувати довіру до кореневого центру сертифікації MITM (видалити) — ідемпотентна операція (див. §3.6)                           |
| POST                | `/api/tools/agent-bridge/cert/regenerate`      | Повторно згенерувати самопідписаний сертифікат MITM                                                                              |

| GET                 | `/api/tools/agent-bridge/bypass`               | Список шаблонів обходу (`default` + `user`)                                                                                      |

| DELETE              | `/api/tools/agent-bridge/bypass?pattern=...`   | Видалити один визначений користувачем шаблон обходу                                                                              |
| GET                 | `/api/tools/agent-bridge/diagnose`             | Самоперевірка конвеєра перехоплення (див. §3.6)                                                                                  |
| POST                | `/api/tools/agent-bridge/repair`               | Скасувати залишковий системний стан MITM (див. §3.6)                                                                             |
| GET                 | `/api/tools/agent-bridge/config`               | Експортувати переносну конфігурацію JSON (див. §3.7)                                                                             |
| POST                | `/api/tools/agent-bridge/config`               | Імпортувати переносну конфігурацію JSON (див. §3.7)                                                                              |
| GET                 | `/api/tools/agent-bridge/upstream-ca`          | Отримати шлях до налаштованого висхідного центру сертифікації                                                                    |

## §8 Дорожня карта

### Дослідження Trae

Trae — відносно новий ШІ-асистент для програмування. Перед реалізацією обробника:

1. Знайти бінарний файл/розширення в маркетплейсах VS Code / JetBrains або окремий застосунок
2. Перехопити трафік за допомогою mitmproxy, щоб виявити хости API та структуру кінцевих точок
3. Визначити механізм автентифікації
4. Ухвалити рішення про доцільність реалізації на основі умов використання та можливості виявлення API

До завершення дослідження картка Trae на панелі керування відображає значок "Досліджується" з посиланням "Повідомити про придатність". Заглушка обробника в `src/mitm/handlers/trae.ts` видає структуровану помилку `Ще не реалізовано`.

### Агенти в беклозі (потрібен MITM — підтримки власної базової URL-адреси немає)

Наведені нижче інструменти в поточних версіях не підтримують власні базові URL-адреси, тому MITM є єдиним способом перехоплення. Оцінювання придатності ще не завершено:

- **Windsurf** (Codeium/Cognition)
- **Amp** (Sourcegraph)
- **Amazon Q / Kiro CLI** (AWS Bedrock — окремо від Kiro IDE)
- **Cowork** (настільний застосунок Anthropic)

Примітка: GitHub Copilot CLI ≥v1.0.19 підтримує `COPILOT_PROVIDER_BASE_URL` — для цього інструмента використовуйте безпосереднє налаштування замість MITM.
