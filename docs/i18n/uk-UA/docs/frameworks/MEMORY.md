> **Джерело істини:** `src/lib/memory/` і `src/app/api/memory/`
> **Останнє оновлення:** 2026-06-28 — v3.8.40 (типово вимкнено + підтримка квантування int8)

OmniRoute забезпечує постійну пам’ять розмов, прив’язану до ключа API (і,
за потреби, ідентифікатора сесії). Спогади автоматично витягуються з відповідей LLM
за допомогою легкого зіставлення за регулярними виразами та додаються до наступних
запитів як початкове системне повідомлення (або перше повідомлення користувача для
провайдерів, які не приймають системну роль).

> **Пам’ять типово ВИМКНЕНА (v3.8.30+).** `DEFAULT_MEMORY_SETTINGS.enabled`
> тепер має значення `false` (`src/lib/memory/settings.ts`). Увімкнення пам’яті додає
> до `maxTokens` (~2k) токенів отриманого контексту до **кожного** запиту чату, за що
> стягується плата — це може стати неочікуваною витратою для нових інсталяцій і клієнтів,
> які самостійно керують власним контекстом. Увімкніть її явно в розділі
> **Налаштування → Пам’ять** (`MemorySkillsTab` показує попередження про вартість
> токенів, коли пам’ять увімкнено). Клієнт може вимкнути пам’ять для окремого запиту
> за допомогою заголовка запиту `x-omniroute-no-memory` (`true`/`1`/`yes`) — див.
> таблицю заголовків запиту в [API_REFERENCE.md](../reference/API_REFERENCE.md).
> Запит без пам’яті встановлює `memoryOwnerId = null`, що вимикає **і** додавання
> пам’яті, **і** додавання навичок для цього запиту
> (`open-sse/handlers/chatCore/headers.ts::isNoMemoryRequested`).

Пам’ять **ізольована за ключем API**, а не за користувачем — усі запити,
автентифіковані тим самим ключем API, спільно використовують один пул пам’яті
з можливістю додаткової ізоляції за `sessionId`.

## Архітектура

```
Клієнт → /v1/chat/completions (apiKeyInfo визначено вище за потоком)
  → handleChatCore() [open-sse/handlers/chatCore.ts]
    → resolveMemoryOwnerId(apiKeyInfo)        # витягує id
    → getMemorySettings()                     # кешовані налаштування
    → shouldInjectMemory(body, {enabled})     # перевірка
    → retrieveMemories(apiKeyId, config)      # SQL + FTS5 + необов’язковий вектор
    → injectMemory(body, memories, provider)  # системне повідомлення або повідомлення користувача
  → виклик зовнішнього провайдера
  → після відповіді: extractFacts(text, apiKeyId, sessionId)  # неблокувально
    → setImmediate → createMemory(fact) для кожного збігу
                   → embed(content) + upsertVector(id, vec)
```

Місця виклику додавання та витягування підключено у
`open-sse/handlers/chatCore.ts` (шукайте `retrieveMemories`, `injectMemory`
і `extractFacts`).

## Архітектура рушія (3-рівневе визначення)

Рушій пам’яті визначає шлях пошуку під час виконання залежно від доступної
інфраструктури та налаштувань. Існують три рівні, які застосовуються в порядку
пріоритету:

```
  ┌─────────────────────────────────────────────────────────────┐
  │  РІВЕНЬ 0 — Ключові слова (FTS5)                            │
  │  Доступність на основі перевірки: FTS5, якщо збірка SQLite  │
  │  його підтримує (better-sqlite3 / node:sqlite / bun:sqlite);│
  │  недоступний у збірках без FTS5 (наприклад, sql.js/WASM —   │
  │  "no such module: fts5"). Використовується, коли strategy = │
  │  "exact", або як запасний варіант; стан keyword у статусі   │
  │  рушія відображає результат перевірки.                      │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ strategy = semantic|hybrid?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  РІВЕНЬ 1 — Вбудовані вектори (sqlite-vec)                  │
  │  sqlite-vec v0.1.9 завантажується через db.loadExtension(). │
  │  Повний перебір KNN для векторів Float32. Активний, коли:   │
  │   • sqlite-vec loadExtension виконується успішно             │
  │   • Доступне джерело вбудовувань (remote | static |         │
  │     transformers), здатне створити Float32Array             │
  │   • Існує таблиця vec_memories (створюється під час першого │
  │     виклику ready())                                        │
  └──────────────────────────────────┬──────────────────────────┘
                                     │ qdrant.enabled?
                                     ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  РІВЕНЬ 2 — Qdrant (зовнішня векторна БД, за згодою)        │
  │  Якщо ввімкнено, замінює sqlite-vec для semantic/hybrid.    │
  │  Потребує запущеного екземпляра Qdrant і налаштованих       │
  │  хоста/порту.                                                │
  └─────────────────────────────────────────────────────────────┘
```

Деградація відбувається автоматично й прозоро:

- Якщо sqlite-vec не вдається завантажити, рівень 1 недоступний → відбувається
  перехід до рівня 0.
- Якщо джерело вбудовувань повертає помилку, рівень 1 переходить до рівня 0.
- Якщо Qdrant не працює належним чином, рівень 2 переходить до рівня 1 (або
  рівня 0, якщо рівень 1 також недоступний).

## Джерела ембедингів

Рівень ембедингів (`src/lib/memory/embedding/`) визначає, яке джерело використовувати,
на основі `MemorySettingsExtended.embeddingSource`:

| Джерело        | Опис                                                                                                    | Потрібен ключ | Холодний запуск  |
| -------------- | ------------------------------------------------------------------------------------------------------- | ------------- | ---------------- |
| `remote`       | Використовує API ембедингів налаштованого провайдера (OpenAI, Cohere тощо)                              | Так           | Відсутній        |
| `static`       | Локальні ембединги на основі таблиці пошуку через `potion-base-8M` (WordPiece + усереднювальний пулінг) | Ні            | ~200ms           |
| `transformers` | Локальне виконання ONNX через `@huggingface/transformers` v4, `all-MiniLM-L6-v2`                        | Ні            | ~3s + ~400MB RAM |
| `auto`         | Визначення під час виконання: remote (якщо ключ існує) → static → transformers → null                   | Залежить      | Залежить         |

**Порядок визначення для `auto`:**

1. Знайти першого провайдера в `listEmbeddingProviders()` з `hasKey === true` → `remote`.
2. Якщо `settings.staticEnabled === true` → `static`.
3. Якщо `settings.transformersEnabled === true` → `transformers`.
4. Інакше → `null` (перехід до повнотекстового пошуку FTS5 за ключовими словами).

Кеш ембедингів (`src/lib/memory/embedding/cache.ts`) використовує LRU-мапу в пам’яті
з ключем `${source}:${model}:${dim}:${sha256(text)}`, обмежену
`MEMORY_EMBEDDING_CACHE_MAX` записами (за замовчуванням 1000) із TTL
`MEMORY_EMBEDDING_CACHE_TTL_MS` (за замовчуванням 5 хв). Кеш спільний для всіх
викликів протягом життєвого циклу процесу.

## Гібридний RRF (k=60)

Коли `strategy = "hybrid"` і векторне сховище доступне, для пошуку використовується
Reciprocal Rank Fusion, щоб об’єднати результати FTS5 і векторного пошуку:

```
RRF(d) = Σ  1 / (k + rank_i(d))      де k = 60 (налаштовується через MEMORY_RRF_K)
          i
```

А саме:

1. Виконати пошук FTS5 → ранжований список `R_fts` (позиції 1..N).
2. Виконати векторний пошук KNN → ранжований список `R_vec` (позиції 1..M).
3. Для кожного унікального `memoryId`:  
   `rrf_score = 1/(60 + fts_rank)` + `1/(60 + vec_rank)` (0, якщо запису немає у списку).
4. Відсортувати за `rrf_score` у порядку спадання та застосувати послідовний відбір у межах бюджету токенів.

Загальновідомо, що RRF є ефективним без необхідності нормалізації оцінок між
різнорідними системами пошуку. Значення `k=60` за замовчуванням походить з оригінальної
статті Cormack та ін. і добре працює для невеликих корпусів (<10k записів пам’яті).

## Зворотне заповнення (відкладене + переіндексація)

Коли модель ембедингів змінюється (це виявляється через `embedding_signature`),
векторне сховище перебудовується, а всі наявні записи пам’яті позначаються
`needs_reindex = 1` у таблиці `memories`.

**Відкладене зворотне заповнення**: Під час наступного пошуку будь-який запис пам’яті,
для якого відсутній векторний запис, перетворюється на ембединг і додається до
`vec_memories` до запуску пошуку. Це розподіляє витрати на зворотне заповнення між
реальними запитами, не блокуючи запуск.

**Явна переіндексація**: Вкладка Engine у `/dashboard/memory` містить кнопку
"Переіндексувати зараз", яка викликає `POST /api/memory/reindex`. Обробник викликає
`runReindexBatch()` із `src/lib/memory/reindex.ts`, що обробляє до `limit` записів,
які очікують обробки, за один запит. Стан виконання можна опитувати через
`GET /api/memory/engine-status` (`vectorStore.needsReindex`).

Таблиця `memory_vec_meta` (міграція `083_memory_vec.sql`) зберігає:

- `active_dim` — поточна розмірність вектора (null = ще не відкалібровано).
- `embedding_signature` — `${source}:${model}:${dim}`, що використовується для виявлення змін.
- `last_reset_at` — часова мітка останнього повного скидання.
- `vec_loaded` — прапорець 0/1, що вказує, чи було sqlite-vec успішно завантажено.

## Розширення налаштувань

Дев’ять полів для вбудовувань і векторів доступні в `MemorySettingsExtended` у
`src/shared/schemas/memory.ts` та зберігаються через `src/lib/db/settings.ts`:

| Поле                     | Тип                                                | Значення за замовчуванням | Опис                                                              |
| ------------------------ | -------------------------------------------------- | ------------------------- | ----------------------------------------------------------------- |
| `embeddingSource`        | `"remote" \| "static" \| "transformers" \| "auto"` | `"auto"`                  | Яке джерело вбудовувань використовувати                           |
| `embeddingProviderModel` | `string \| null`                                   | `null`                    | Провайдер/модель у форматі `provider/model`                       |
| `customBaseUrl`          | `string \| null`                                   | `null`                    | Базова URL-адреса OpenAI-сумісної кінцевої точки лише для пам’яті |
| `customModelId`          | `string \| null`                                   | `null`                    | ID моделі, що надсилається до користувацької кінцевої точки       |
| `transformersEnabled`    | `boolean`                                          | `false`                   | Згода на використання Transformers.js (MiniLM, ~400MB)            |
| `staticEnabled`          | `boolean`                                          | `false`                   | Згода на використання локальної статичної моделі potion-base-8M   |
| `rerankEnabled`          | `boolean`                                          | `false`                   | Увімкнути етап повторного ранжування (додає +200-500ms/запит)     |
| `rerankProviderModel`    | `string \| null`                                   | `null`                    | Провайдер/модель повторного ранжування у форматі `provider/model` |
| `vectorStore`            | `"sqlite-vec" \| "qdrant" \| "auto"`               | `"auto"`                  | Яке векторне сховище використовувати                              |

Вони доступні через `GET /PUT /api/settings/memory` (схема `MemorySettingsExtendedSchema`).

Для джерела `remote` Memory також приймає необов’язкові налаштування `customBaseUrl` і
`customModelId`. Разом вони визначають OpenAI-сумісну кінцеву точку `/embeddings`
і модель без зміни глобального реєстру вбудовувань. Перед використанням кінцева точка
нормалізується та перевіряється політикою вихідних URL-адрес провайдера: потрібен HTTP(S),
вбудовані облікові дані й рядки запиту відхиляються, а адреси хмарних метаданих
залишаються заблокованими. Порожні значення зберігають вибраного провайдера реєстру. Помилки,
що повертаються на панель керування, очищуються, а облікові дані кінцевої точки ніколи не журналюються.

## Рівні зберігання

### Основний: SQLite (таблиця `memories`)

Створюється міграцією `015_create_memories.sql`:

| Стовпець                    | Тип                | Примітки                                                                     |
| --------------------------- | ------------------ | ---------------------------------------------------------------------------- |
| `id`                        | `TEXT PRIMARY KEY` | UUID, згенерований через `crypto.randomUUID()`                               |
| `api_key_id`                | `TEXT NOT NULL`    | Ключ API власника                                                            |
| `session_id`                | `TEXT`             | Необов’язкова область видимості для окремої розмови                          |
| `type`                      | `TEXT NOT NULL`    | Одне зі значень: `factual`, `episodic`, `procedural`, `semantic`             |
| `key`                       | `TEXT`             | Стабільний ключ upsert, наприклад `preference:i_prefer_python`               |
| `content`                   | `TEXT NOT NULL`    | Фактичний текст факту                                                        |
| `metadata`                  | `TEXT`             | Блок JSON (категорія, extractedAt, джерело, ...)                             |
| `created_at` / `updated_at` | `TEXT`             | Рядки ISO 8601                                                               |
| `expires_at`                | `TEXT`             | Необов’язковий термін дії; `NULL` означає безстрокове зберігання             |
| `memory_id`                 | `INTEGER UNIQUE`   | Додано міграцією `023_fix_memory_fts_uuid.sql` для зв’язку UUID ↔ rowid FTS5 |

Індекси: `api_key_id`, `session_id`, `type`, `expires_at`, а також унікальний
індекс `memory_id`.

**Семантика upsert**: `createMemory()` шукає наявний рядок із таким самим
`(api_key_id, key)` і, якщо знаходить, оновлює його на місці (об’єднуючи `metadata`
через поверхневе розгортання). Це запобігає необмеженому зростанню таблиці через повторювані
твердження про вподобання.

### Повнотекстовий пошук (віртуальна таблиця `memory_fts`)

`022_add_memory_fts5.sql` створює віртуальну таблицю FTS5 для `content` і
`key`. `023_fix_memory_fts_uuid.sql` виправляє помилку, що виникала на практиці, коли первинний
ключ UUID не з’єднувався з цілочисельним rowid FTS5 — міграція додає
стовпець `memory_id`, повторно створює таблицю FTS і налаштовує тригери
(`memory_fts_ai`, `memory_fts_ad`, `memory_fts_au`), які синхронізують FTS під час
INSERT, DELETE і UPDATE.

Використовується в `retrieval.ts` для стратегій `semantic` і `hybrid` (див. нижче).
Код отримання виконує перевірку через `hasTable("memory_fts")` і повертається до
хронологічного порядку, якщо таблиця FTS відсутня або запит FTS спричиняє помилку.

### Необов’язковий: Qdrant (рівень 2 векторного сховища)

`src/lib/memory/qdrant.ts` реалізує необов’язкову інтеграцію з Qdrant як рівень 2
векторного сховища. Отримання спрямовується до Qdrant лише тоді, коли селектор рушія
`memoryVectorStore === "qdrant"` — значення за замовчуванням `"auto"` (і `"sqlite-vec"`)
**ніколи** не вибирають Qdrant. Перемикач на вкладці Engine одночасно встановлює **обидва**
параметри: `qdrantEnabled` і `memoryVectorStore`: увімкнення робить Qdrant основним сховищем, а вимкнення
скидає значення до `"auto"` (#5597 — до цього виправлення ввімкнення не мало ефекту, оскільки ніщо
не записувало значення селектора рушія). Якщо Qdrant недоступний або нічого не повертає, отримання
переходить до sqlite-vec → FTS5.

- `upsertSemanticMemoryPoint()` — створює вбудовування для `key + content` за допомогою налаштованої
  моделі вбудовування, перевіряє наявність колекції (під час першого використання
  створює вектори з косинусною відстанню) та додає або оновлює точку з корисним навантаженням `{memoryId,
apiKeyId, sessionId, key, content, metadata, createdAtUnix, expiresAtUnix}`.
- `searchSemanticMemory(query, topK, scope)` — створює вбудовування запиту, виконує пошук у
  колекції з фільтром за `kind = "omniroute_memory"` і, за потреби, за
  `apiKeyId` / `sessionId`. Обмежує `topK` діапазоном `[1, 20]`.
- `deleteSemanticMemoryPoint(id)` — видаляє одну точку. Викликається функцією
  `deleteMemory()` після видалення рядка SQLite (D15).
- `cleanupSemanticMemoryPoints({retentionDays})` — масово видаляє точки, у яких
  `expiresAtUnix` уже минув або `createdAtUnix` передує граничній даті
  зберігання. Спочатку підраховує їх, щоб на інформаційній панелі можна було показати фактичні числа.
- `checkQdrantHealth()` — перевірка працездатності через `GET /readyz` із вимірюванням затримки.

Інтерфейс налаштувань надає конфігурацію Qdrant, перевірку працездатності, тест семантичного пошуку
та очищення на вкладці **Рушій** сторінки `/dashboard/memory`. Станом на v3.8.6 усі відповідні
маршрути в `src/app/api/settings/qdrant/` підключено:

| Маршрут                                 | Метод         | Опис                                   |
| --------------------------------------- | ------------- | -------------------------------------- |
| `/api/settings/qdrant`                  | `GET` / `PUT` | Читання / оновлення налаштувань Qdrant |
| `/api/settings/qdrant/health`           | `GET`         | Перевірка доступності + затримка       |
| `/api/settings/qdrant/search`           | `POST`        | Тест семантичного пошуку               |
| `/api/settings/qdrant/cleanup`          | `POST`        | Видалення прострочених / старих точок  |
| `/api/settings/qdrant/embedding-models` | `GET`         | Перелік доступних моделей вбудовування |

**Примітки щодо поведінки (чого очікувати):**

- **Вибір рушія** — увімкнення Qdrant на вкладці «Рушій» робить його основним
  сховищем (установлює `memoryVectorStore="qdrant"`); вимкнення повертає значення `"auto"` (#5597).
- **Без заповнення попередніми даними** — до нього записуються лише спогади, створені/оновлені **після**
  ввімкнення Qdrant (подвійний запис без очікування результату). Наявні раніше спогади SQLite **не**
  переносяться; дія «Переіндексувати зараз» перебудовує лише індекс sqlite-vec, а не Qdrant.
- **Розмірність вектора визначається автоматично** на основі фактичного вбудовування під час першого використання —
  поля розмірності для заповнення немає. Зміна моделі вбудовування після створення колекції
  **не** обробляється автоматично: наявна колекція залишається без змін, а операції запису/пошуку
  з невідповідною розмірністю завершуються помилкою та перемикаються на sqlite-vec. Щоб змінити модель вбудовування,
  створіть колекцію заново (з новою назвою або видаліть її у Qdrant).
- **Метрика відстані** — завжди **косинусна** (жорстко задана під час створення колекції;
  не налаштовується).
- **Автентифікація** — лише ключ API (передається в заголовку `api-key`; необов’язковий для локального
  Docker без автентифікації). JWT/RBAC не використовуються.
- **Поля конфігурації** — в інтерфейсі доступні `host`, `port`, `collection`, `embeddingModel`,
  `apiKey`. `vectorSize` / `hnswEfConstruct` доступні лише через змінні середовища/БД, а `vectorSize` не
  використовується під час створення колекції (розмірність визначається з вбудовування).

### Квантування векторів (int8 — опціональне, для обох бекендів)

Обидва векторні бекенди підтримують **опціональне квантування int8**, щоб зменшити обсяг
пам’яті для збережених векторів (приблизно в 4 рази порівняно з Float32) ціною незначного зниження повноти пошуку.
За замовчуванням воно **вимкнене** для обох — вектори зберігають повну точність, якщо квантування
не ввімкнено явно.

| Бекенд     | Налаштування                                  | Тип                            | Значення за замовчуванням | Де зчитується                                               |
| ---------- | --------------------------------------------- | ------------------------------ | ------------------------- | ----------------------------------------------------------- |
| Qdrant     | `qdrantQuantization` (ключ БД)                | `"none" \| "int8" \| "binary"` | `"none"`                  | `src/lib/memory/qdrant.ts::normalizeQdrantConfig()`         |
| sqlite-vec | `MEMORY_VEC_QUANTIZATION` (змінна середовища) | `"none" \| "int8"`             | `"none"`                  | `src/lib/memory/vectorStore.ts::requestedVecQuantization()` |

- **Qdrant** налаштовується окремо для кожного екземпляра за допомогою ключа налаштування
  `qdrantQuantization` (доступного як поле `quantization` у `PUT /api/settings/qdrant`). За значення
  `"int8"` функція `buildQuantizationConfig()` запитує скалярне квантування
  (`always_ram`, квантиль `0.99`), а під час пошуку вмикається `rescore: true`, щоб
  вектори повної точності уточнювали набір кандидатів int8.
- Квантування **sqlite-vec** налаштовується **лише через середовище** (це не налаштування БД): задайте
  `MEMORY_VEC_QUANTIZATION=int8`, щоб зберігати локальні вектори як стовпець `int8[dim]`
  за допомогою `vec_quantize_int8(?, 'unit')`. Вибраний режим включається до
  `embedding_signature` (суфікс `:int8`), тому перемикання режимів запускає повну
  переіндексацію таблиці `vec_memories` — через той самий шлях відкладеного заповнення, що використовується,
  коли змінюється модель вбудовування.

## Типи пам’яті

`MemoryType` (`src/lib/memory/types.ts`):

| Тип          | Для чого використовується                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------- |
| `factual`    | Уподобання, сталі факти про користувача, поведінкові шаблони                                    |
| `episodic`   | Рішення, прив’язані до конкретного моменту ("Я вибрав Postgres")                                |
| `procedural` | Пам’ять про робочі процеси / інструкції (зарезервовано; наразі автоматичного екстрактора немає) |
| `semantic`   | Зарезервовано для записів векторного сховища                                                    |

Стратегія отримання `MemoryConfig` може бути `exact`, `semantic` або `hybrid`,
а область дії — `session`, `apiKey` або `global`. Стандартна область дії з
`getMemorySettings()` — `apiKey`.

## Вилучення фактів (`extraction.ts`)

Вилучення здійснюється **на основі регулярних виразів**, а не LLM — воно виконується всередині процесу за допомогою
`setImmediate()`, тому ніколи не блокує потік відповіді:

- **Шаблони вподобань** → `MemoryType.FACTUAL`
  (наприклад, `Я віддаю перевагу …`, `Мені дуже подобається …`, `мій улюблений варіант — …`, `Я ненавиджу …`)
- **Шаблони рішень** → `MemoryType.EPISODIC`
  (наприклад, `Я використаю …`, `Я вибрав …`, `Я зупинився на …`, `Я збираюся впровадити …`)
- **Шаблони поведінки** → `MemoryType.FACTUAL`
  (наприклад, `Зазвичай я …`, `Я завжди …`, `Я схильний …`)

Кожен збіг очищується (`trim`, згортання пробілів, обмеження до 500 символів),
дедуплікується в межах пакета за допомогою стабільного `factKey(category, content)` і
зберігається через `createMemory()` з метаданими
`{category, extractedAt, source: "llm_response"}`. Вхідний текст обмежується
64 KiB (`MAX_EXTRACTION_TEXT_LENGTH`) — якщо він довший, використовується **кінець** тексту,
щоб найновіший вміст відповіді асистента завжди брав участь у вилученні.

`extractFactsFromText(text)` експортується для тестів і повертає структуровані
факти без їх збереження.

## Отримання (`retrieval.ts`)

`retrieveMemories(apiKeyId, config)` — основна точка входу. Вона:

1. Нормалізує та перевіряє конфігурацію через `MemoryConfigSchema`.
2. Негайно повертає `[]`, якщо `enabled` має значення false або `maxTokens <= 0`.
3. Обмежує `maxTokens` діапазоном `[1, 8000]`.
4. Визначає, чи існує сучасна таблиця `memories` (на відміну від застарілої таблиці `memory`),
   щоб старі бази даних продовжували працювати.
5. Формує базовий запит із перевіркою терміну дії
   (`expires_at IS NULL OR datetime(expires_at) > datetime('now')`), необов’язковою
   областю дії сесії та необов’язковим обмеженням `retentionDays`.
6. Розгалужує логіку залежно від стратегії:
   - **`exact`** (стандартна): хронологічне сортування `ORDER BY created_at DESC LIMIT 100`.
   - **`semantic`**: якщо задано `config.query` та існує `memory_fts`, виконує JOIN
     `memory_fts MATCH ?` і сортує за рангом FTS; повертається до хронологічного
     порядку, якщо FTS повертає 0 рядків.
   - **`hybrid`**: об’єднання результатів FTS (вища релевантність) і
     хронологічного набору з дедуплікацією за id.
7. Обчислює оцінку релевантності за ключовими словами (`getRelevanceScore`) для
   `content`, `key` і JSON-метаданих `metadata`, якщо надано запит. Рядки з
   нульовою оцінкою відфільтровуються.
8. Сортує за спаданням оцінки, а потім за спаданням `createdAt`.
9. Проходить ранжований список і приймає записи, доки накопичуване значення
   `estimateTokens(content)` (≈ `length / 4`) не перевищує бюджет. Завжди
   повертає щонайменше один запис, якщо знайдено хоча б один збіг.

`estimateTokens` експортується та використовується під час отримання, узагальнення й у MCP-інструменті
`omniroute_memory_search`.

## Ін’єкція (`injection.ts`)

`injectMemory(request, memories, provider)`:

1. Об’єднує весь вміст пам’яті в один рядок `Memory context: …`.
2. Вибирає стратегію за назвою провайдера:
   - **Системне повідомлення** (за замовчуванням для OpenAI, Anthropic, Gemini, …) — додає
     `{role: "system", content: memoryText}` перед усіма наявними системними
     повідомленнями, щоб системні промпти користувача й надалі мали пріоритет.
   - **Повідомлення користувача** (резервний варіант) — для провайдерів у
     `PROVIDERS_WITHOUT_SYSTEM_MESSAGE`: `o1`, `o1-mini`, `o1-preview`,
     `glm`, `glmt`, `glm-cn`, `zai`, `qianfan`. Вони відхиляють системну роль,
     інакше повертаючи помилку 400 (див. проблему #1701 для GLM/Zhipu).
3. Записує в журнал кількість, стратегію та модель під ключем `memory.injection.injected`.

`providerSupportsSystemMessage(provider)` експортується для викликів, яким
потрібно ухвалювати власні рішення щодо маршрутизації. Для невідомих провайдерів
за замовчуванням повертається `true` (системну роль дозволено) задля безпеки.

## Сумаризація (`summarization.ts`)

`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)` стискає старіший
вміст, коли поточна загальна кількість токенів у спогадах ключа перевищує
ліміт. Функція перебирає рядки за спаданням `created_at`, зберігає рядки, що
вміщуються в ліміт, а для решти замінює `content` на місці першими трьома
реченнями оригіналу. `tokensSaved` — це різниця в `estimateTokens` між старим і
новим вмістом.

Ця процедура **доступна, але не викликається автоматично** в поточному
конвеєрі чату — викликайте її із cron, адміністративної дії або зв’язувального
коду `MemoryConfig.autoSummarize`, якщо потрібне постійне стиснення. Втрата
даних є незворотною: оригінальний текст перезаписується.

## REST API

Усі кінцеві точки вимагають автентифікації керування (`requireManagementAuth`).

### Основні кінцеві точки пам’яті (наявні й оновлені)

| Метод    | Шлях                 | Опис                                                                                                                                                                                           |
| -------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Інструменти MCP (`open-sse/mcp-server/tools/memoryTools.ts`)

Коли сервер MCP увімкнено, реєструються три інструменти пам’яті:

- `omniroute_memory_search` — `{apiKeyId, query?, type?, maxTokens?, limit?}`
  → обгортає `retrieveMemories()`. Починаючи з v3.8.6 (D16), `strategy` зчитується
  з `getMemorySettings()` замість жорстко заданого значення `"exact"`. Якщо
  вказано `query`, а `strategy` має значення `semantic` або `hybrid`, за
  наявності використовується векторне сховище.
- `omniroute_memory_add` — `{apiKeyId, sessionId?, type, key, content,
metadata?}` → обгортає `createMemory()`. Приймає лише 4 канонічні типи:
  `factual`, `episodic`, `procedural`, `semantic` (D17).
- `omniroute_memory_clear` — `{apiKeyId, type?, olderThan?}` → виводить список
  відповідних записів, за потреби фільтрує їх за часовою позначкою створення,
  а потім видаляє кожен через `deleteMemory()` (що також видаляє вектори зі
  sqlite-vec + Qdrant).

Докладніше про транспорт і область дії див. у [MCP-SERVER.md](./MCP-SERVER.md).

## Панель керування (Студія пам’яті)

`src/app/(dashboard)/dashboard/memory/page.tsx` тепер є **студією з 3 вкладками**:

### Вкладка: Спогади

- Картка концепції (згортане пояснення «Як це працює»).
- Список у реальному часі, пошук і пагінація (затримка 300 мс).
- Фільтр за типом (`factual` / `episodic` / `procedural` / `semantic` / усі).
- Модальне вікно додавання спогаду (ключ, вміст, тип).
- Вбудоване редагування (кнопка з олівцем → `PUT /api/memory/[id]`).
- Видалення окремого рядка (з діалоговим вікном підтвердження).
- Експорт поточної сторінки у форматі JSON; імпорт JSON через засіб вибору файлу.
- Картки статистики: `totalEntries`, `tokensUsed`, `hitRate`.
- Кнопка «Стиснути старі» → `POST /api/memory/summarize` (спочатку пробний запуск
  показує кількість кандидатів, після чого запитується підтвердження).
- Зелений/червоний індикатор стану, керований через `GET /api/memory/health`.

### Вкладка: Експериментальний майданчик

- Поле запиту + селектор стратегії (точна / семантична / гібридна) + бюджет токенів.
- «Симулювати» → `POST /api/memory/retrieve-preview` — показує ранжовані результати з
  `score`, `tier`, `tokens`, `vecScore`, `ftsScore`.
- Панель розв’язання, що показує, яке джерело вкладень / векторне сховище було
  використано та чи відбулося перемикання на резервний варіант.

### Вкладка: Рушій

- Панель стану рушія (індикатор ключових слів FTS5, індикатор вкладень,
  індикатор векторного сховища, індикатор стану Qdrant, індикатор повторного ранжування).
- Кнопка «Переіндексувати зараз» → `POST /api/memory/reindex`.
- Селектор джерела вкладень (автоматичне / віддалене / статичне / transformers + перемикачі).
- Картка конфігурації Qdrant (перемикач увімкнення, хост/порт/колекція/ключ,
  перевірка з’єднання, перевірка семантичного пошуку, очищення).
- Картка конфігурації повторного ранжування (перемикач увімкнення, селектор постачальника/моделі).

Налаштування пам’яті та Qdrant також доступні в розділі
`/dashboard/settings → Пам’ять і навички` (`MemorySkillsTab.tsx`) для
застарілого/глобального інтерфейсу налаштувань.

## Кешування

`src/lib/memory/store.ts` підтримує внутрішньопроцесний кеш, подібний до LRU
(`MEMORY_CACHE_TTL = 1 хв`, `MEMORY_MAX_CACHE_SIZE = 500`, із видаленням 20 %
найстаріших записів), для операцій читання `getMemory(id)`, а також універсальний
рівень кешування ключ/значення `memoryCache` (`src/lib/memory/cache.ts`) із
методами `get`/`set`/`invalidate`, який використовується викликачами, що потребують
власного кешу з окремою областю дії (LRU на 1 000 записів, стандартний TTL — 5 хв).

## Конфіденційність і життєвий цикл

- Власником пам’яті є ідентифікатор ключа API (`resolveMemoryOwnerId` у
  `chatCore.ts`). Без `apiKeyInfo.id` не виконуються ані пошук, ані
  вставлення, ані вилучення.
- Записи з майбутньою датою `expires_at` відфільтровуються з результатів
  пошуку; старі записи, що виходять за межі `retentionDays`, виключаються
  умовою `created_at >= cutoff` у `retrieveMemories`.
- Для безповоротного видалення використовуйте `DELETE /api/memory/[id]` або
  `omniroute_memory_clear`.
- Вилучення виконується асинхронно без очікування результату через
  `setImmediate`; помилки реєструються під ключем
  `memory.extraction.background.failed` і ніколи не повертаються викликачеві.
- Перевірочні цикли (`verifyExtractionPipeline`) видаляють власні тестові
  записи в блоці `finally`.

## Вибір постачальника вбудовувань (v3.8.16+)

Рушій пам’яті OmniRoute підтримує **чотири джерела вбудовувань** (`src/lib/memory/embedding/`). Кожне з них має різні компроміси щодо **затримки, вартості, якості моделі та складності налаштування**.

### Джерела вбудовувань

| Постачальник   | Джерело                                             | Затримка                                  | Вартість              | Якість                            | Налаштування                                           |
| -------------- | --------------------------------------------------- | ----------------------------------------- | --------------------- | --------------------------------- | ------------------------------------------------------ |
| `transformers` | Локальна модель ONNX (Xenova/all-MiniLM-L6-v2)      | ~50-150 мс (CPU)                          | Безкоштовно           | Добра                             | Лише `npm install`                                     |
| `static`       | Попередньо обчислені вектори (кешовані)             | <1 мс                                     | Безкоштовно           | Н/Д (залежить від влучання в кеш) | Не потрібне                                            |
| `remote`       | API OpenAI / Cohere / Voyage                        | ~100-300 мс                               | $0.02-0.10/1M токенів | Відмінна                          | Ключ API                                               |
| `auto`         | Вибирає найкраще доступне джерело під час виконання | Як у вибраного джерела                    | Безкоштовно           | Як у вибраного джерела            | Не потрібне                                            |
| _(cache)_      | Шар LRU в пам’яті поверх будь-якого джерела         | <1 мс (влучання), повна затримка (промах) | Безкоштовно           | Як у базового джерела             | Завжди ввімкнений (не є доступним для вибору джерелом) |

### Налаштування бази даних та API

Параметри вбудовувань пам’яті налаштовуються через API/інтерфейс налаштувань, а не через змінні середовища. Відповідні ключі бази даних налаштувань у розділі Settings (`normalizeMemorySettings` у `src/lib/memory/settings.ts`):

- `memoryEmbeddingSource`: `"transformers"` (локальне), `"remote"` (на основі API, наприклад OpenAI), `"static"` (зовнішнє сховище) або `"auto"`
- `memoryEmbeddingProviderModel`: ідентифікатор моделі для віддалених/статичних джерел (наприклад, `"text-embedding-3-small"`)
- `memoryTransformersEnabled`: `true` | `false`
- `memoryStaticEnabled`: `true` | `false`
- `memoryVectorStore`: `"sqlite-vec"`, `"qdrant"` або `"auto"`

#### Локальна модель (`transformers`)

Внутрішньо використовує transformers.js для запуску локальних моделей:

```bash
# Змінні середовища, що зчитуються в коді (src/lib/memory/embedding/index.ts):
MEMORY_TRANSFORMERS_MODEL=Xenova/all-MiniLM-L6-v2  # Репозиторій моделі HF
MEMORY_STATIC_MODEL=minishlab/potion-base-8M       # Статична модель potion HF
MEMORY_STATIC_CACHE_DIR=<DATA_DIR>/embeddings      # Каталог кешу
```

#### Кеш вбудовувань LRU

За замовчуванням кеш завжди ввімкнений і налаштовується за допомогою змінних середовища:

```bash
MEMORY_EMBEDDING_CACHE_MAX=1000                    # Максимальна кількість кешованих елементів
MEMORY_EMBEDDING_CACHE_TTL_MS=300000               # TTL (5 хв)
```

## Шаблони вилучення фактів (v3.8.16+)

Модуль `extraction.ts` (`src/lib/memory/extraction.ts`) використовує **зіставлення з шаблонами регулярних виразів** для вилучення структурованих фактів із повідомлень розмови. Розуміння цих шаблонів допоможе вам налаштувати якість вилучення для вашого сценарію використання.

### Категорії шаблонів за замовчуванням

| Категорія           | Приклад шаблону                                                          | Що вилучається                   |
| ------------------- | ------------------------------------------------------------------------ | -------------------------------- |
| PREFERENCE_PATTERNS | `"Я віддаю перевагу <X>"`, `"Мені подобається <X>"`, `"Я ненавиджу <X>"` | Уподобання користувача           |
| DECISION_PATTERNS   | `"Я використаю <X>"`, `"Я вирішив <X>"`, `"Я вибрав <X>"`                | Рішення користувача (епізодичні) |
| PATTERN_PATTERNS    | `"Я зазвичай <X>"`, `"Я завжди <X>"`, `"Я ніколи <X>"`                   | Стійкі моделі поведінки          |

### Приклади шаблонів (спрощено)

```ts
// З src/lib/memory/extraction.ts
const PREFERENCE_PATTERNS = [
  /\bI\s+(?:really\s+)?prefer\s+([^.,\n]+)/gi,
  /\bI\s+(?:really\s+)?like\s+([^.,\n]+)/gi,
  /\bI\s+(?:hate|dislike|avoid)\s+([^.,\n]+)/gi,
];
const DECISION_PATTERNS = [
  /\bI'?(?:ll|will)\s+use\s+([^.,\n]+)/gi,
  /\bI\s+(?:have\s+)?decided\s+(?:to\s+)?([^.,\n]+)/gi,
];
const PATTERN_PATTERNS = [/\bI\s+usually\s+([^.,\n]+)/gi, /\bI\s+always\s+([^.,\n]+)/gi];
```

### Що вилучається

Коли користувач каже:

> "Я віддаю перевагу TypeScript. Я використаю Postgres для цього проєкту. Я завжди роблю коміт перед надсиланням змін. Мені не подобається Python."
> У результаті вилучення створюються 4 записи пам’яті:
>
> | Ключ                                 | Категорія  | Тип      | Вміст                                |
> | ------------------------------------ | ---------- | -------- | ------------------------------------ |
> | `preference:typescript`              | preference | factual  | "TypeScript"                         |
> | `decision:postgres_for_this_project` | decision   | episodic | "Postgres для цього проєкту"         |
> | `pattern:commit_before_pushing`      | pattern    | factual  | "роблю коміт перед надсиланням змін" |
> | `preference:python`                  | preference | factual  | "Python"                             |

### Обмеження вилучення

Щоб запобігти неконтрольованому вилученню, застосовуються такі обмеження:

| Мінімальна довжина вмісту | 3 символи |
| Максимальна довжина вмісту | 500 символів |

### Коли слід вимкнути вилучення

Вилучення запускається автоматично щоразу, коли пам’ять увімкнена; окремого
перемикача лише для вилучення немає. Щоб вимкнути його, повністю вимкніть пам’ять (`enabled: false`
через `PUT /api/settings/memory`). Розгляньте цей варіант, якщо:

- У вас великий обсяг повідомлень, а витрати на вилучення є суттєвими
- Ваші розмови здебільшого тимчасові (чат, налагодження) і не мають довгострокової цінності
- Ви вже зберігаєте контекст за допомогою власних плагінів

## Налаштування гібридного RRF (v3.8.16+)

Алгоритм **Reciprocal Rank Fusion (RRF)** поєднує результати FTS5 (пошук за ключовими словами) і векторного (семантичного) пошуку. Параметр `k` визначає, яку вагу мають результати з нижчими позиціями в рейтингу.

### Формула

Для кожного кандидата в пам’яті оцінка RRF обчислюється так:

```
RRF(d) = Σ  1 / (k + rank_i(d))
```

Де:

- `k` — константа (за замовчуванням 60)
- `rank_i(d)` — позиція документа `d` в i-й системі пошуку (FTS, векторній)
- Сума обчислюється за всіма системами пошуку

### Як `k` впливає на результати

| Значення `k`                  | Ефект                                                                                                                       | Найкраще підходить для                               |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `k=0`                         | Чисте об’єднання рейтингів (без згладжування)                                                                               | Теоретичного базового рівня                          |
| `k=10-30`                     | Надає значно більшу вагу найкращим результатам, низькі позиції майже не впливають                                           | Випадків, коли перші 3 результати зазвичай правильні |
| **`k=60`** (за замовчуванням) | Збалансований варіант — усі перші 10 результатів роблять суттєвий внесок                                                    | Пошуку загального призначення                        |
| `k=100+`                      | Рівномірніший розподіл — навіть результати з низькими позиціями можуть домінувати, якщо вони з’являються в кількох системах | Випадків, коли повнота > точність є критичною        |

### Практичне налаштування `k`

```bash
# Значення за замовчуванням
MEMORY_RRF_K=60

# Агресивна точність (мала пам’ять, мало документів)
MEMORY_RRF_K=20

# Максимальна повнота (велика пам’ять, різноманітні запити)
MEMORY_RRF_K=120
```

**Приклад із `k=20`:**

- Позиція FTS 1 → внесок `1/21 = 0.048`
- Позиція FTS 10 → внесок `1/30 = 0.033`
- Позиція у векторному пошуку 1 → внесок `0.048`
- Максимальна сума: `0.096`

**Приклад із `k=60`:**

- Позиція FTS 1 → внесок `1/61 = 0.016`
- Позиція FTS 10 → внесок `1/70 = 0.014`
- Позиція у векторному пошуку 1 → внесок `0.016`
- Максимальна сума: `0.033`

За вищого `k` **відносна різниця** між першою та десятою позиціями менша, тому алгоритм більше покладається на **узгодженість між системами пошуку**, ніж на впевненість, зумовлену найвищою позицією.

### Коли змінювати `k`

| Ознака                                                              | Що спробувати                                                                                     |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Перший результат завжди перемагає, але він неправильний             | **Зменшити** k (наприклад, до 20) — впевненість, зумовлена найвищою позицією, має більше значення |
| Правильна відповідь входить до перших 5, але не посідає перше місце | **Збільшити** k (наприклад, до 100) — рівномірніше оцінювання винагороджує узгодженість           |
| Повнота висока, але точність низька                                 | **Зменшити** k — зробити ранжування чіткішим                                                      |
| Повнота низька (релевантні документи пропускаються)                 | **Збільшити** k — дати шанс документам із нижчими позиціями                                       |

### Зважування RRF

Об’єднання на основі обернених рангів використовує однакові ваги для семантичного векторного рангу та рангу повнотекстового пошуку:

```
RRF(d) = 1/(k + rank_vector) + 1/(k + rank_fts)
```

Змінних середовища для налаштування окремих ваг немає (`MEMORY_RRF_VECTOR_WEIGHT`/`MEMORY_RRF_FTS_WEIGHT` не існують).

## Стратегія узагальнення (v3.8.16+)

Модуль `summarization.ts` (`src/lib/memory/summarization.ts`) стискає давніші спогади, щоб зберігати активний набір невеликим, водночас не втрачаючи можливості відтворення.

### Коли запускається узагальнення

| Тригер                  | Порогове значення (типово) |
| ----------------------- | -------------------------- |
| Ручний запуск через API | не застосовується          |

### Що узагальнюється

З `summarization.ts` експортуються дві точки входу:

- **`summarizeMemories(apiKeyId, sessionId?, maxTokens = 4000)`** — стискає
  спогади сеансу в єдиний текст узагальнення, обмежений бюджетом токенів.
- **`summarizeMemoriesOlderThan(apiKeyId, days, dryRun)`** — вікове
  ущільнення, яке використовується API: воно вибирає кожен спогад, старіший за `days`, створює
  з них один стислий підсумковий спогад і (коли `dryRun` має значення `false`) видаляє
  оригінали. Передайте `dryRun: true`, щоб переглянути набір кандидатів і загальну кількість токенів
  без внесення змін.

Прохід кластеризації за тегами/ключами або оцінювання кожного спогаду як «основного чи придатного до узагальнення» відсутні —
вибір відбувається виключно за віковою межею, а текст узагальнення складається зі стислого
рядка з префіксом типу для кожного кандидата.

### Запуск узагальнення

Узагальнення є **ручним / за явною згодою** — параметр `autoSummarize` типово має значення `false`,
тому автоматичне ущільнення не відбувається. Запустіть його через API:

```bash
curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

Щоб залишити його вимкненим, просто збережіть для `autoSummarize` типове значення (`false`).

### Поради щодо якості узагальнення

- **Спочатку виконайте попередній перегляд за допомогою `dryRun`** — `summarizeMemoriesOlderThan(..., true)` повертає
  список кандидатів і загальну кількість токенів, щоб ви могли перевірити, що саме буде об’єднано,
  перш ніж видаляти оригінали.
- **Запускайте узагальнення в години низького навантаження**, якщо у вас великий корпус спогадів — виклик LLM є найповільнішою частиною

```bash
# У стилі Cron: узагальнювати щодня о 3-й годині ночі
0 3 * * * curl -X POST http://localhost:20128/api/memory/summarize \
  -H "Authorization: Bearer $OMNIROUTE_KEY"
```

## Шаблон провайдера MemoryBackend

> **Джерело істини:** `src/lib/memory/backend.ts`, `src/lib/memory/genericBackend.ts`, `src/lib/memory/manager.ts`
> **Тести:** `src/lib/memory/__tests__/generic-backend.test.ts`

Шаблон провайдера MemoryBackend додає **підключуваний рівень абстракції бекенду** поверх наявного механізму пам’яті. Замість прив’язки до однієї реалізації сховища система пам’яті тепер підтримує кілька бекендів (SQLite, Obsidian, Notion, власні HTTP-бекенди) з налаштовуваною маршрутизацією до основного/резервного бекенду.

### Архітектура

```
┌──────────────────────────────────────────────────────────┐
│                    Маршрути API                           │
│            (src/app/api/memory/route.ts)                  │
└──────────────────────┬───────────────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────────────┐
│                   MemoryManager                           │
│        Оркестратор-одинак (manager.ts)                    │
│                                                          │
│  Основний ──► Бекенд A  (наприклад, SQLite)              │
│  Резервний ─► Бекенд B  (наприклад, Obsidian)            │
│               Бекенд C  (наприклад, Notion через          │
│                          GenericBackend)                  │
└──────────────────────┬───────────────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌────────────┐ ┌────────────┐ ┌──────────────────┐
│ Бекенд     │ │ Бекенд     │ │ GenericMemory    │
│ SQLite     │ │ Obsidian   │ │ Backend (HTTP)   │
└────────────┘ └────────────┘ └──────────────────┘
```

#### Основний інтерфейс (`backend.ts`)

Кожен бекенд має реалізовувати інтерфейс `MemoryBackend`:

```typescript
interface MemoryBackend {
  readonly id: string;
  readonly displayName: string;

  // CRUD
  create(input: CreateMemoryInput): Promise<Memory>;
  get(id: string): Promise<Memory | null>;
  update(id: string, updates: Partial<...>): Promise<boolean>;
  delete(id: string): Promise<boolean>;
  list(filter: MemoryFilter): Promise<{ data: Memory[]; total: number; byType: Record<string, number> }>;

  // Пошук
  search(config: SearchConfig): Promise<Memory[]>;

  // Стан працездатності
  health(): Promise<HealthCheckResult>;

  // Життєвий цикл (необов’язково)
  initialize?(): Promise<void>;
  shutdown?(): Promise<void>;
}
```

#### MemoryManager (`manager.ts`)

Оркестратор-одинак, який:

- **Реєструє** бекенди через `register(backend)` — викликається під час запуску з `index.ts`
- **Налаштовує** основний і резервні бекенди через `configure(primary, fallbacks)`
- **Маршрутизує** операції CRUD/пошуку до основного бекенду з використанням ланцюжка резервних у разі збою
- **Перевіряє стан працездатності** всіх бекендів через певні проміжки часу

**Поведінка резервних бекендів:**

| Операція | Основний                        | Резервні                                   |
| -------- | ------------------------------- | ------------------------------------------ |
| `create` | ✅ Лише основний                | ❌                                         |
| `get`    | ✅ Спочатку спробувати основний | ✅ Резервний, якщо результат — null        |
| `update` | ✅ Лише основний                | ✅ Асинхронна синхронізація без очікування |
| `delete` | ✅ Лише основний                | ✅ Асинхронна синхронізація без очікування |
| `list`   | ✅ Лише основний                | ❌                                         |
| `search` | ✅ Спочатку основний            | ✅ Резервний у разі помилки                |

#### GenericMemoryBackend (`genericBackend.ts`)

Універсальний HTTP-конектор, який адаптує будь-який REST API до MemoryBackend. Корисний для:

- **Notion** — підключення через Notion API
- **Obsidian** — підключення через Obsidian Local REST API
- **Власних бекендів** — будь-якого сервісу, що надає RESTful API пам’яті

**Конфігурація:**

```typescript
interface GenericBackendConfig {
  baseUrl: string;           // Базова URL-адреса API бекенду
  apiKey?: string;           // Bearer-токен для автентифікації
  headers?: Record<string, string>;  // Власні HTTP-заголовки
  timeout?: number;          // Час очікування запиту (типово: 30000ms)
  backendType?: string;      // Для журналювання

  // Перевизначення кінцевих точок (типові значення відповідають REST-конвенціям)
  endpoints?: {
    search?: string;   // типово: "/memories/search"
    create?: string;   // типово: "/memories"
    list?: string;     // типово: "/memories"
    get?: string;      // типово: "/memories/{id}"
    update?: string;   // типово: "/memories/{id}"
    delete?: string;   // типово: "/memories/{id}"
    health?: string;   // типово: "/health"
  };

  // Зіставлення назв параметрів запиту
  queryParams?: {
    query?/apiKeyId?/limit?/offset?/strategy?/maxTokens?/type?/sessionId?/orderBy?/orderDir?/options?
  };

  // Зіставлення назв параметрів шляху
  pathParams?: {
    id?/memoryId?
  };
}
```

**Відомі бекенди** попередньо налаштовані в `KNOWN_BACKENDS`:

```typescript
createKnownBackend("obsidian"); // → GenericMemoryBackend, спрямований на localhost:27123
createKnownBackend("notion"); // → GenericMemoryBackend, спрямований на api.notion.com/v1
```

#### Вбудовані бекенди

##### SQLiteBackend (`sqliteBackend.ts`)

Основний бекенд за замовчуванням. Обгортає наявне сховище пам’яті на базі SQLite за допомогою `src/lib/memory/store.ts`. Автоматично реєструється під час запуску.

```typescript
import { sqliteBackend } from "./sqliteBackend";
memoryManager.register(sqliteBackend);
```

##### ObsidianBackend (`obsidianBackend.ts`)

Обгортає наявну інтеграцію з Obsidian (`src/lib/memory/obsidianBackend.ts`). Підключається до сховища Obsidian через Obsidian Local REST API.

### Налаштування

Налаштування бекенду пам’яті зберігаються в таблиці налаштувань застосунку та керуються через `src/lib/memory/settings.ts`:

| Налаштування          | Ключ середовища/конфігурації | Типове значення | Опис                                            |
| --------------------- | ---------------------------- | --------------- | ----------------------------------------------- |
| Основний бекенд       | `memoryPrimaryBackend`       | `"sqlite"`      | ID основного бекенду                            |
| Резервні бекенди      | `memoryFallbackBackends`     | `[]`            | Упорядковані ID резервних бекендів              |
| Конфігурації бекендів | `memoryBackendConfigs`       | `{}`            | Перевизначення конфігурації для кожного бекенду |

Налаштування нормалізуються за допомогою `normalizeMemorySettings()` і кешуються в `getMemorySettings()`.

### Процес ініціалізації

```
Початкове завантаження застосунку
  → імпорти index.ts (побічний ефект): реєструють SQLiteBackend
  → initMemoryBackends() викликається з життєвого циклу застосунку:
      1. Завантажити налаштування (getMemorySettings)
      2. Налаштувати основний і резервні бекенди
      3. Ініціалізувати всі бекенди (перевірка працездатності)
      4. Готово до обробки запитів
```

### Додавання нового бекенду

1. **Реалізуйте інтерфейс `MemoryBackend`** у `src/lib/memory/<name>Backend.ts`
2. **Експортуйте** з `src/lib/memory/index.ts`
3. **Зареєструйте** за допомогою `memoryManager.register(yourBackend)` під час запуску
4. **Налаштуйте** через параметри: установіть для `memoryPrimaryBackend` ID вашого бекенду
5. **Протестуйте**, використовуючи `src/lib/memory/__tests__/generic-backend.test.ts` як зразок
