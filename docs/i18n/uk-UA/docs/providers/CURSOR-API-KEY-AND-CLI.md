Два способи розмістити Cursor за OmniRoute без сесії IDE:

1. **Провайдер `cursor-api`** (картка «Cursor API», псевдонім `cua`): провайдер
   з API-ключем, який зберігає користувацький API-ключ Cursor (`crsr_…`,
   створений на `https://cursor.com/dashboard/api`). Після цього будь-який клієнт
   OmniRoute отримує доступ до моделей Cursor через `/v1/chat/completions` як
   `cursor-api/<model>` або `cua/<model>` зі звичайними рівнями квот,
   резервування та журналювання. Провайдер IDE (`cursor`, сесія OAuth/IDE)
   залишається без змін.
2. **Наскрізне проксування Cursor CLI**: спрямуйте Cursor CLI (`agent`) на
   OmniRoute, щоб кожен RPC-запит CLI автентифікувався за допомогою API-ключа
   OmniRoute, пересилався до Cursor з обліковими даними підключення `cursor-api`
   та записувався на сторінці журналів.

## Навіщо виконується обмін ключа

`api2.cursor.sh` відхиляє необроблений ключ `crsr_…` як Bearer-токен (401).
Cursor CLI спочатку надсилає ключ методом POST до `/auth/exchange_user_api_key`
та отримує JWT сеансу, термін дії якого спливає через одну годину; повернений
`refreshToken` має те саме значення `exp`, тому для оновлення потрібно повторно
обміняти ключ.
`open-sse/services/cursorApiKeyAuth.ts` виконує цей обмін, кешує один токен
сеансу для кожного ключа, повторно обмінює його за п’ять хвилин до завершення
терміну дії та видаляє кешований токен, коли Cursor повертає 401.
`CursorExecutor` викликає його безпосередньо перед відкриттям висхідного потоку
для підключень `cursor-api`.

## Провайдер `cursor-api`

Реєстр: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, ті самі `format`, `baseUrl` і
`models`, що й у `cursor`). Картка каталогу:
`src/shared/constants/providers/apikey/specialty-media.ts`. Мапа виконавців:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Панель керування: Провайдери → Cursor API → Додати API-ключ.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

Потім:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Примітки:

- Список моделей для `cursor-api` надходить зі статичного реєстру Cursor
  (того самого списку, до якого як резервного варіанта звертається провайдер
  IDE); установлювати `cursor-agent` на хості OmniRoute не потрібно.
- `POST /api/providers/{id}/refresh-cursor` призначений лише для провайдера
  Cursor IDE `cursor`; підключення `cursor-api` не мають сесії IDE, яку потрібно
  поновлювати.

## Нативні ідентифікатори моделей і рівень зусиль

Для `cursor` / `cu` та `cursor-api` / `cua` спільний нормалізатор рівня зусиль
Claude залишає запитаний ідентифікатор моделі без змін. Cursor може оголошувати
суфікс на кшталт `-low` як частину фактичного ідентифікатора моделі, а не як
псевдонім рівня зусиль OmniRoute. Виконавець Cursor зберігає точний збіг з
актуальним каталогом; якщо збігу немає, його наявний механізм визначення моделі
виконує резервне перетворення суфікса на параметр.

Це не змінює нормалізацію рівня зусиль для прямих маршрутів Claude,
Claude-сумісних маршрутів або маршрутів Vertex. Доступність, як і раніше,
залежить від каталогу та прав вибраного облікового запису Cursor.

## Наскрізне проксування Cursor CLI

Маршрут: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Префікс `/api/cursor-cli/`
зареєстровано в `src/shared/constants/publicApiRoutes.ts`, оскільки обробник
самостійно виконує автентифікацію:

| Шлях                                                                                                                       | Автентифікація, очікувана від CLI | Дії OmniRoute                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/exchange_user_api_key`                                                                                         | `Bearer <OmniRoute API key>`      | Перевіряє ключ, створює JWT HS256 на 1 годину (підписаний за допомогою `JWT_SECRET`) і повертає його                                                                              |
| усі інші шляхи (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`               | Перевіряє видавця, аудиторію та строк дії, вибирає активне підключення `cursor-api`, замінює заголовок Authorization на обміняний токен Cursor і потоково передає відповідь назад |

CLI декодує `exp` з будь-якого отриманого токена, тому передавання йому непрозорого
токена змушує виконувати повторний обмін майже перед кожним запитом; створений JWT
запобігає цьому. Відповідь 401 від OmniRoute змушує CLI знову виконати обмін.

### Налаштування

1. Створіть API-ключ OmniRoute (Панель керування → API-ключі) і підключення
   `cursor-api`.
2. Налаштуйте CLI на використання HTTP/1.1 для потоку агента. У
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Без цього CLI відкриває взаємодію з агентом через HTTP/2 на окремо
   налаштованому хості агента, і лише RPC площини керування проходять через
   кінцеву точку.

3. Запустіть CLI через OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Кожен перехід потрапляє до журналів із провайдером `cursor-api`, типом запиту
`cursor-cli` і шляхом `/api/cursor-cli/<rpc>` та пов’язується з API-ключем
OmniRoute і підключенням, яке його обслужило.

### Сценарії помилок

| Ситуація                                          | Відповідь CLI                                      |
| ------------------------------------------------- | -------------------------------------------------- |
| Невідомий ключ OmniRoute і `REQUIRE_API_KEY=true` | 401 `unauthenticated` під час обміну               |
| `REQUIRE_API_KEY=false`                           | анонімний сеанс (відтворює поведінку `/v1/*`)      |
| Прострочений / сторонній / підроблений JWT сеансу | 401, CLI повторно виконує обмін                    |
| API-ключ OmniRoute відкликано після обміну        | 401 під час наступного RPC                         |
| Немає активного підключення `cursor-api`          | 503 `unavailable`                                  |
| Cursor відхиляє ключ підключення                  | 401 `unauthenticated`, кешований сеанс видаляється |
| Висхідний сервер недоступний                      | 502 `unavailable` (очищене повідомлення)           |
| `JWT_SECRET` не задано                            | 503 під час обміну                                 |
