Два способи підключити Cursor через OmniRoute без сесії IDE:

1. **Провайдер `cursor-api`** (картка «Cursor API», псевдонім `cua`): провайдер
   з API-ключем, який зберігає користувацький API-ключ Cursor (`crsr_…`,
   згенерований на `https://cursor.com/dashboard/api`). Після цього будь-який
   клієнт OmniRoute може отримувати доступ до моделей Cursor через
   `/v1/chat/completions` як `cursor-api/<model>` або `cua/<model>`, зі
   звичайними рівнями квот, резервного перемикання та журналювання. Провайдер
   IDE (`cursor`, OAuth/сесія IDE) залишається без змін.
2. **Наскрізне проксіювання Cursor CLI**: налаштуйте Cursor CLI (`agent`) на
   використання OmniRoute, щоб кожен RPC-виклик CLI автентифікувався за
   допомогою API-ключа OmniRoute, пересилався до Cursor з обліковими даними
   з’єднання `cursor-api` і записувався на сторінці Logs.

## Навіщо виконується обмін ключа

`api2.cursor.sh` відхиляє необроблений ключ `crsr_…` як Bearer-токен (401).
Cursor CLI спочатку надсилає ключ методом POST до
`/auth/exchange_user_api_key` й отримує JWT сесії, термін дії якого спливає
через одну годину; повернений `refreshToken` має те саме значення `exp`, тому
для оновлення потрібно повторно обміняти ключ.
`open-sse/services/cursorApiKeyAuth.ts` виконує цей обмін, кешує один токен
сесії для кожного ключа, повторно обмінює його за п’ять хвилин до завершення
терміну дії та видаляє кешований токен, коли Cursor відповідає кодом 401.
`CursorExecutor` викликає його безпосередньо перед відкриттям висхідного потоку
для з’єднань `cursor-api`.

## Провайдер `cursor-api`

Реєстр: `open-sse/config/providers/registry/cursor/index.ts`
(`cursor_apiProvider`, `authType: "apikey"`, ті самі `format`, `baseUrl` і
`models`, що й у `cursor`). Картка каталогу:
`src/shared/constants/providers/apikey/specialty-media.ts`. Мапа виконавців:
`open-sse/executors/index.ts` (`"cursor-api"` / `cua` →
`new CursorExecutor("cursor-api")`).

Панель керування: Providers → Cursor API → Add API key.

REST:

```bash
curl -sS -X POST http://localhost:20128/api/providers \
  -H "Content-Type: application/json" \
  -d '{"provider":"cursor-api","name":"cursor-api-key","apiKey":"crsr_…","priority":1}'
```

Після цього:

```bash
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <omniroute-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"cursor-api/auto","messages":[{"role":"user","content":"say PONG"}]}'
```

Примітки:

- Список моделей для `cursor-api` береться зі статичного реєстру Cursor (це той
  самий список, який провайдер IDE використовує як резервний); інсталювати
  `cursor-agent` на хості OmniRoute не потрібно.
- `POST /api/providers/{id}/refresh-cursor` призначений лише для провайдера IDE
  `cursor`; з’єднання `cursor-api` не мають сесії IDE, яку потрібно поновлювати.

## Наскрізне проксіювання Cursor CLI

Маршрут: `src/app/api/cursor-cli/[...path]/route.ts` →
`open-sse/handlers/cursorCliProxy.ts`. Префікс `/api/cursor-cli/`
зареєстровано в `src/shared/constants/publicApiRoutes.ts`, оскільки обробник
самостійно забезпечує автентифікацію:

| Шлях                                                                                                                             | Автентифікація, очікувана від CLI | Дії OmniRoute                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/exchange_user_api_key`                                                                                               | `Bearer <OmniRoute API key>`      | Перевіряє ключ, створює JWT HS256 терміном дії 1 год (підписаний за допомогою `JWT_SECRET`) і повертає його                                                              |
| будь-який інший шлях (`/aiserver.v1.*`, `/agent.v1.AgentService/RunSSE`, `/aiserver.v1.BidiService/BidiAppend`, `/v1/traces`, …) | `Bearer <that JWT>`               | Перевіряє видавця, аудиторію й термін дії, вибирає активне з’єднання `cursor-api`, замінює заголовок Authorization на обміняний токен Cursor і передає відповідь потоком |

CLI декодує `exp` з будь-якого отриманого токена, тому передавання непрозорого
токена змушує його повторювати обмін майже перед кожним запитом; створений JWT
дає змогу цього уникнути. Відповідь 401 від OmniRoute змушує CLI повторити
обмін.

### Налаштування

1. Створіть API-ключ OmniRoute (Dashboard → API keys) і з’єднання `cursor-api`.
2. Налаштуйте CLI на використання HTTP/1.1 для потоку агента. У
   `~/.cursor/cli-config.json`:

   ```json
   { "network": { "useHttp1ForAgent": true } }
   ```

   Без цього CLI відкриває взаємодію з агентом через HTTP/2 на окремо
   налаштованому хості агента, і через кінцеву точку проходять лише RPC-виклики
   площини керування.

3. Запустіть CLI через OmniRoute:

   ```bash
   export CURSOR_API_ENDPOINT=http://localhost:20128/api/cursor-cli
   export CURSOR_API_KEY=<omniroute-api-key>
   agent -p --trust "Reply with exactly OK"
   ```

Кожен етап потрапляє до Logs із провайдером `cursor-api`, типом запиту
`cursor-cli` і шляхом `/api/cursor-cli/<rpc>`, з прив’язкою до API-ключа
OmniRoute та з’єднання, яке його обслугувало.

### Режими відмови

| Ситуація                                          | Відповідь для CLI                                  |
| ------------------------------------------------- | -------------------------------------------------- |
| Невідомий ключ OmniRoute і `REQUIRE_API_KEY=true` | 401 `unauthenticated` під час обміну               |
| `REQUIRE_API_KEY=false`                           | анонімний сеанс (повторює поведінку `/v1/*`)       |
| Прострочений / сторонній / підроблений JWT сеансу | 401, CLI повторно виконує обмін                    |
| Ключ API OmniRoute відкликано після обміну        | 401 під час наступного RPC                         |
| Немає активного підключення `cursor-api`          | 503 `unavailable`                                  |
| Cursor відхиляє ключ підключення                  | 401 `unauthenticated`, кешований сеанс видаляється |
| Висхідний сервер недоступний                      | 502 `unavailable` (очищене повідомлення)           |
| `JWT_SECRET` не задано                            | 503 під час обміну                                 |
