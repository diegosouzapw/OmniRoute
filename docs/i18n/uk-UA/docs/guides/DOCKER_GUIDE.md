## Швидкий запуск

> **Самостійне розгортання однією командою?** Див.
> [Посібник із самостійного розгортання](../getting-started/SELF_HOST_GUIDE.md) —
> `docker compose -f docker-compose.selfhost.yml up -d` (опублікований образ +
> Redis, доступ лише через loopback-інтерфейс, без вибору профілю). Наведений нижче швидкий запуск —
> це варіант з одним контейнером для користувачів, які вже запускають Redis в іншому місці.

```bash
docker run -d \
  --name omniroute \
  --restart unless-stopped \
  --stop-timeout 40 \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## З файлом змінних середовища

```bash
# Спочатку скопіюйте та відредагуйте .env

  --stop-timeout 40 \
  --env-file .env \
  -p 20128:20128 \
  -v omniroute-data:/app/data \
  diegosouzapw/omniroute:latest
```

## Docker Compose

```bash
# Базовий профіль (без CLI-інструментів)
docker compose --profile base up -d

# Профіль CLI (вбудовані Claude Code, Codex і OpenClaw)
docker compose --profile cli up -d

# Профіль хоста (насамперед для Linux; монтує CLI-бінарні файли хоста лише для читання)
docker compose --profile host up -d

# Вебпрофіль (Chromium/Playwright для провайдерів вебсеансів)
docker compose --profile web up -d

# Поєднання CLI з допоміжним контейнером CLIProxyAPI
docker compose --profile cli --profile cliproxyapi up -d
```

## Доступні профілі

OmniRoute постачається з профілями Compose для основних варіантів розгортання. Виберіть той, що відповідає вашому середовищу.

| Профіль              | Сервіс           | Коли використовувати                                                                                                                                   | Команда                                      |
| -------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| `base` (стандартний) | `omniroute-base` | Безголовий сервер / мінімальне середовище виконання, без включених CLI провайдерів                                                                     | `docker compose --profile base up -d`        |
| `cli`                | `omniroute-cli`  | Агентні робочі процеси, що викликають `omniroute providers/setup/doctor` і вбудовані CLI (Codex, Claude Code, Droid, OpenClaw)                         | `docker compose --profile cli up -d`         |
| `host`               | `omniroute-host` | Хости Linux, яким потрібен доступ до CLI хоста на кшталт `network_mode` через монтування `~/.local/bin`, `~/.codex`, `~/.claude` тощо лише для читання | `docker compose --profile host up -d`        |
| `cliproxyapi`        | `cliproxyapi`    | Запуск допоміжного контейнера [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) на порту `8317` для проксіювання до вищестоящих CLI          | `docker compose --profile cliproxyapi up -d` |
| `web`                | `omniroute-web`  | Провайдери вебсеансів, яким потрібен браузер: `gemini-web`, `claude-web`, `claude-turnstile` (збирає `runner-web`, Chromium включено)                  | `docker compose --profile web up -d`         |

> Можна поєднувати кілька профілів: `docker compose --profile cli --profile cliproxyapi up -d`.

## Налаштування CLI-інструментів хоста, коли OmniRoute працює в Docker

`omniroute setup-codex`, `setup-claude`, `config set <tool>` і кнопка
**Зберегти конфігурацію** на панелі керування записують файли на кшталт `~/.codex/*.config.toml`. Ці шляхи
мають сенс лише на машині, де фактично працює CLI. Якщо запустити ці команди всередині
контейнера, запис потрапить у власній домашній каталог контейнера (`/home/node` —
образ працює з `USER node`), звідки жоден CLI на хості ніколи його не прочитає і де його буде
видалено одразу після повторного створення контейнера.

OmniRoute виявляє це й відхиляє запис, натомість надаючи інструкції,
а не повідомляючи про успіх, яким ви не зможете скористатися: CLI завершує роботу з кодом `2`, а API відповідає `422`
з `containerEphemeralTarget: true`.

### Рекомендовано: запускайте CLI на хості, а OmniRoute — у Docker

Контейнер обслуговує API; CLI налаштовує ваші інструменти на хості.

```bash
docker compose --profile base up -d

npm install -g omniroute
omniroute connect http://localhost:20128   # спрямуйте CLI на контейнер
omniroute setup-codex                      # записує справжній ~/.codex на вашому хості
```

Це правильний вибір, коли Codex, Claude Code, Cursor або подібні інструменти працюють на вашому
ноутбуці — а це звичайна конфігурація.

### Альтернатива: підключіть каталоги конфігурації хоста через bind mount (профіль `host`)

Якщо ви хочете, щоб сам контейнер записував конфігурацію на хості, підключіть
каталоги та спрямуйте `CLI_CONFIG_HOME` на корінь точки монтування. Профіль `host`
уже робить це:

```yaml
environment:
  - CLI_CONFIG_HOME=/host-home
  - CLI_ALLOW_CONFIG_WRITES=true
volumes:
  - ~/.codex:/host-home/.codex:rw
  - ~/.claude:/host-home/.claude:rw
```

Саме bind mount робить шлях надійним: OmniRoute читає
`/proc/self/mountinfo` і дозволяє запис у змонтовані шляхи (а також у каталоги,
дочірні елементи яких є точками монтування, що точно відповідає наведеній вище структурі `/host-home`), водночас
і далі відхиляючи запис у незмонтовані шляхи.

### Обхідний шлях: налаштуйте власні CLI контейнера (використовуйте обачно)

Коли CLI справді розміщені всередині контейнера (профіль `cli`), запис
є навмисним. Передайте `--allow-container-write` будь-якій команді `setup-*` або задайте
`OMNIROUTE_ALLOW_CONTAINER_CONFIG_WRITE=true` для сервера. Запис буде виконано
з попередженням, що він не збережеться після завершення роботи контейнера.

> **Попередження щодо безпеки — профіль `cli` + монтування `docker.sock`.**
> Профіль `cli` підключає `/var/run/docker.sock` через bind mount, щоб засіб
> автоматичного оновлення всередині контейнера міг повторно створювати стек через демон хоста
> (`src/lib/system/autoUpdate.ts` перевіряє наявність цього сокета та пропускає
> шлях Docker, якщо він відсутній). Цей сокет є **межею довіри з правами root
> на хості**: усе, що може отримати до нього доступ, керує демоном Docker на хості від імені
> root — воно може створювати, перевіряти, зупиняти та видаляти будь-який контейнер на хості.
> Наслідки:
>
> 1. **Ніколи не відкривайте порт профілю `cli` у мережі.** Публікуйте
>    його на `127.0.0.1` (`ports: "127.0.0.1:${DASHBOARD_PORT:-20128}:..."`)
>    — доступний із локальної мережі профіль `cli` перетворює будь-яке виконання довільного коду на рівні панелі керування на
>    повну компрометацію хоста.
> 2. **Не підключайте жодних додаткових каталогів хоста до профілю `cli`.**
>    Сокет Docker у поєднанні з будь-яким додатковим монтуванням надає контейнеру повний
>    доступ на читання й запис до вашої файлової системи та конфігурації хоста. Якщо інструменту потрібен доступ до
>    проєкту, запускайте його локально за допомогою виконуваного файла CLI — не монтуйте проєкт
>    у контейнер `cli`.
>
> Якщо вам не потрібне автоматичне оновлення всередині контейнера, не вмикайте профіль `cli`
> (`COMPOSE_PROFILES=core,redis` або коротший варіант). Інші профілі не
> монтують сокет Docker.
>
> Пов’язану модель загроз
> для MITM див. у `docs/security/MITM-TPROXY-DECRYPT.md` (git; не включено до зібраної документації в `/docs`), а ланцюг походження бінарних файлів
> `codex`/`claude-code`/`droid`/`openclaw` — у `docs/security/SUPPLY_CHAIN.md`.

## Сайдкар Redis

OmniRoute використовує Redis як основу для розподіленого обмежувача частоти запитів і спільного кешу. Сервіс `redis` **завжди визначено** у `docker-compose.yml` (він не обмежений профілем) і запускається разом із будь-яким іншим профілем.

| Параметр                      | Значення                               |
| ----------------------------- | -------------------------------------- |
| Образ                         | `redis:7-alpine`                       |
| Назва контейнера              | `omniroute-redis`                      |
| Внутрішній порт               | `6379`                                 |
| Порт хоста (перевизначення)   | `REDIS_PORT` (типово `6379`)           |
| Адреса хоста (перевизначення) | `REDIS_BIND_HOST` (типово `127.0.0.1`) |
| Том                           | `omniroute-redis-data` → `/data`       |
| Перевірка працездатності      | `redis-cli ping` (інтервал 10 с)       |

Пов’язані змінні середовища:

- `REDIS_URL` — рядок підключення, переданий у застосунок (типово `redis://redis:6379`).
- `REDIS_PORT` — порт хоста, зіставлений із контейнером Redis.
- `REDIS_BIND_HOST` — інтерфейс хоста, на якому публікується порт. Типове значення — `127.0.0.1`.

> **Чому типово використовується loopback-інтерфейс:** сайдкар працює без `requirepass`, а контейнери
> застосунку підключаються до нього через мережу compose (`redis:6379`) — опублікований порт
> потрібен лише для інструментів на боці хоста (`redis-cli`, локального `npm run dev`). Публікація на
> `0.0.0.0` відкрила б доступ до Redis без автентифікації для кожного хоста у вашій локальній мережі. Якщо ви встановлюєте
> `REDIS_BIND_HOST=0.0.0.0`, також додайте `--requirepass` до `command:` сервісу.

**Вимикати Redis** не рекомендовано (обмежувач частоти запитів перейде на резервний варіант у пам’яті з обмеженими можливостями). Якщо це необхідно, видаліть або закоментуйте блок сервісу `redis:` у `docker-compose.yml` чи зменште кількість його екземплярів до нуля:

```bash
docker compose up -d --scale redis=0
```

## Compose для виробничого середовища

Для ізольованого знімка виробничого середовища, що працює паралельно із середовищем розробки, використовуйте `docker-compose.prod.yml`.

| Параметр                      | Значення                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| Файл                          | `docker-compose.prod.yml`                                                          |
| Типовий порт панелі керування | `PROD_DASHBOARD_PORT=20130` (зіставлено з внутрішнім `${DASHBOARD_PORT:-20128}`)   |
| Типовий порт API              | `PROD_API_PORT=20131`                                                              |
| Образ                         | `omniroute:prod` (зібрано з цілі `runner-cli`)                                     |
| Контейнер Redis               | `omniroute-redis-prod` (`redis:8.6.2`, окремий том `redis-prod-data`)              |
| Том даних                     | `omniroute-prod-data` (іменований, зберігається між повторними збірками)           |
| Перевірки працездатності      | `node healthcheck.mjs` + `redis-cli ping`, а `depends_on` залежить від стану Redis |

Використання:

```bash
# Зібрати й запустити стек виробничого середовища
docker compose -f docker-compose.prod.yml up -d --build

# Переглядати журнали в потоковому режимі
docker compose -f docker-compose.prod.yml logs -f

# Зупинити й видалити стек (зберегти томи)
docker compose -f docker-compose.prod.yml down
```

Виробничий стек працює паралельно з compose-стеком середовища розробки (використовуючи інші назви контейнерів, порти й томи), тому ви можете продовжувати локальну розробку, поки виробниче середовище залишається запущеним.

## Етапи Dockerfile

Репозиторій містить багатоетапний Dockerfile (`Dockerfile`). Доступні чотири етапи; виберіть відповідний `target` для свого сценарію використання.

| Етап          | Базовий образ         | Призначення                                                                                                                                                                                                                                                                                                                  |
| ------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`     | `node:26-trixie-slim` | Установлює залежності (`npm ci --legacy-peer-deps`) і запускає `npm run build` (типово використовується Turbopack — див. розділ «Ресурси під час збирання» нижче)                                                                                                                                                            |
| `runner-base` | `node:26-trixie-slim` | Середовище виконання для робочої експлуатації з автономним виводом Next.js. **CLI постачальників не включені.**                                                                                                                                                                                                              |
| `runner-cli`  | `runner-base`         | Додає `git`, `docker.io`, `docker-compose` і глобальні CLI: `@openai/codex`, `@anthropic-ai/claude-code`, `droid`, `openclaw`. **Виберіть цей варіант для агентних робочих процесів.**                                                                                                                                       |
| `runner-web`  | `runner-base`         | Додає Playwright і браузер Chromium (`--with-deps`) для постачальників вебсеансів: `gemini-web`, `claude-web`, `claude-turnstile`. **Виберіть цей варіант, якщо використовуєте цих постачальників** — звичайний образ без нього завершується помилкою під час запиту (див. примітку про `-web` у розділі «Канали випусків»). |

Зберіть певну ціль вручну:

```bash
docker build --target runner-base -t omniroute:base .
docker build --target runner-cli  -t omniroute:cli  .
docker build --target runner-web  -t omniroute:web  .
```

### Ресурси під час збирання

Три аргументи збирання керують ресурсомісткістю етапу `builder`. Вони застосовуються лише під час збирання —
`OMNIROUTE_MEMORY_MB` (нижче) є окремим параметром середовища виконання.

| Аргумент збирання           | Типове значення | Ефект                                                                                                             |
| --------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------- |
| `OMNIROUTE_USE_TURBOPACK`   | `0`             | `0` виконує збирання за допомогою webpack: менше пікове споживання пам’яті, але повільніше. `1` вмикає Turbopack. |
| `OMNIROUTE_BUILD_MEMORY_MB` | `6144`          | Обмеження купи V8 (`--max-old-space-size`) для запущеного процесу `next build`.                                   |
| `OMNIROUTE_BUILD_WORKERS`   | `2`             | Передає значення в `CIRCLE_NODE_TOTAL`; Next визначає `workers = N - 1` для збирання даних сторінок.              |

`OMNIROUTE_BUILD_WORKERS` — це параметр, який слід збільшувати на потужному сервері збирання та перевіряти
першим, коли збирання в обмеженому середовищі аварійно завершується **після** `✓ Compiled successfully`. Кожен
робочий процес збирання даних сторінок є окремим процесом, як і сам батьківський процес `next build`;
відтворення на реальному VPS (проблема #7518) показало, що піковий RSS кожного процесу
становить ~4,5 ГБ незалежно від прапорця купи `NODE_OPTIONS` (Turbopack компілює з використанням
нативної пам’яті/Rust поза купою V8). Типове значення `2` (→ 1 робочий процес, загалом 2
процеси) розраховане на розміщені в GitHub виконавці з 16 ГБ / 4 vCPU, які використовує
конвеєр публікації. За значення `8` (→ 7 робочих процесів) на такому виконавці закінчилася пам’ять, і
buildkit завершив етап помилкою `ResourceExhausted: ... cannot allocate memory`;
значення `3` (→ 2 робочі процеси) також не вмістилося після того, як RSS кожного процесу виміряли
безпосередньо, а не визначили опосередковано. `tests/unit/docker-build-memory-budget.test.ts`
виконує розрахунки на основі виміряного значення та завершується помилкою, якщо будь-який із параметрів
перевищує можливості виконавця.

Turbopack компілює з використанням нативної пам’яті Rust, яка розташована **поза** купою V8, тому
`OMNIROUTE_BUILD_MEMORY_MB` її не обмежує. На хості з обмеженням пам’яті
OOM killer завершує збирання сигналом SIGKILL без будь-якого тексту помилки — воно просто
зупиняється посеред `Creating an optimized production build`, що виглядає як зависання, а
не вичерпання пам’яті. Саме тому `Dockerfile` типово використовує webpack
(`OMNIROUTE_USE_TURBOPACK=0`), на відміну від `npm run dev` / `npm run build`, де
типово на рівні коду використовується Turbopack: звичайна команда `docker build .` без аргументів збирання (саме її
запускають Railway та інші хостинги з розгортанням в один клік) не повинна без повідомлення завершуватися на
сервері збирання з обмеженою пам’яттю. Для опублікованих образів
`OMNIROUTE_USE_TURBOPACK=0` уже явно передається в `docker-publish.yml`. На сервері збирання
з великим обсягом оперативної пам’яті ввімкніть Turbopack для швидшого збирання:

```bash
docker build --target runner-base \
  --build-arg OMNIROUTE_USE_TURBOPACK=1 \
  -t omniroute:base .
```

`webpackBuildWorker` увімкнено, тому `next build` запускає батьківський **і** робочий
процеси, кожен із яких окремо враховує `OMNIROUTE_BUILD_MEMORY_MB`. Установлюйте обмеження
контейнера на рівні, що приблизно вдвічі перевищує це значення, а не дорівнює йому.

Виміряно для цього дерева (`--target runner-base`, `OMNIROUTE_BUILD_MEMORY_MB=6144`):

| Пакувальник | Обмеження контейнера | Результат                                          |
| ----------- | -------------------- | -------------------------------------------------- |
| Turbopack   | 8 ГіБ / 16 ГіБ       | OOM-завершення в обох випадках, без повідомлень    |
| webpack     | 8 ГіБ                | робочий процес збирання завершено сигналом SIGKILL |
| webpack     | 12 ГіБ               | успішно, пікове споживання — 11,1 ГіБ              |

### Типові параметри середовища виконання

Типові значення, які експортує `runner-base`: `PORT=20128`, `HOSTNAME=0.0.0.0`, `OMNIROUTE_MEMORY_MB=1024`, `NODE_OPTIONS=--max-old-space-size=1024`, `DATA_DIR=/app/data`, `OMNIROUTE_MIGRATIONS_DIR=/app/migrations`.

Поведінка пам’яті в Docker:

- Образ задає `OMNIROUTE_MEMORY_MB=1024` і на його основі формує `NODE_OPTIONS=--max-old-space-size=1024`.
- Фактичний серверний процес запускається автономним засобом запуску, який зчитує `OMNIROUTE_MEMORY_MB` і додає `--max-old-space-size=<OMNIROUTE_MEMORY_MB>`.
- Node використовує останнє повторно вказане значення `--max-old-space-size`, тому налаштування `OMNIROUTE_MEMORY_MB` визначає фактичний ліміт купи в Docker.
- Оскільки образ завжди задає це значення, власний резервний механізм засобу запуску, що калібрується за обсягом оперативної пам’яті, у Docker ніколи не застосовується. Збільште його явно відповідно до робочого навантаження (див. таблицю нижче). `2048` усе ще недостатньо для `/v1/responses` агентів програмування.

### Оперативна пам’ять під час виконання для агентів програмування

Стандартний для Docker обсяг у 1 ГіБ — це мінімум для панелі керування та легких чатів, а не придатний для промислової експлуатації обсяг. Довгі тіла запитів `POST /v1/responses` (сотні повідомлень, десятки інструментів) під час стиснення утримують у пам’яті кілька графів. Два одночасні запити обсягом близько 3 МіБ / 750 тис. токенів спричиняли аварійне завершення V8 за розміру old-space **12 ГіБ** (`FATAL ERROR: Reached heap limit`), а також OOM у cgroup з лімітом 16 ГіБ. Див. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849).

Установлюйте для **cgroup `--memory` значення, вище за розмір купи** — нативні буфери, SQLite і проміжні дані стиснення розміщуються поза V8.

| Робоче навантаження                          | `OMNIROUTE_MEMORY_MB`           | Контейнер / cgroup                                | Примітки                                                                                                                                       |
| -------------------------------------------- | ------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Панель керування, один легкий чат            | `1024` (типове значення образу) | ≥2 ГіБ                                            |                                                                                                                                                |
| Один агент програмування (Claude/Codex/Grok) | `8192`                          | ≥10 ГіБ                                           | Типовий односесійний `/v1/responses`                                                                                                           |
| Два одночасні довгі `/v1/responses`          | `10240`–`12288`                 | ≥12–16 ГіБ                                        | Зафіксовано аварійне завершення V8 за розміру купи близько 12 ГіБ                                                                              |
| Три або більше одночасних довгих контекстів  | не запускайте в одному процесі  | послідовне виконання / більше оперативної пам’яті | Типово допускається 1 активний важкий запит; збільшення цього значення без додаткової оперативної пам’яті знову спричинить аварійне завершення |

`omniroute serve` на фізичному сервері калібрує приблизно 35% оперативної пам’яті (в межах `[512, 4096]`), якщо `OMNIROUTE_MEMORY_MB` **не задано**. Docker завжди задає `1024`, тому в офіційному образі це калібрування ніколи не виконується.

```bash
docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
  -e OMNIROUTE_MEMORY_MB=8192 --memory=10g \
  -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
```

## Зворотний проксі на підшляху (Traefik / nginx)

`basePath` Next.js компілюється в автономний пакет. OmniRoute записує вбудоване
значення у контрольний файл у корені застосунку (записується під час `npm run build`;
зчитується `scripts/docker/ensure-docker-base-path.mjs`) і порівнює його з
`OMNIROUTE_BASE_PATH` під час запуску контейнера. Якщо значення відрізняються, а образ
було зібрано для кореня домену, точка входу переписує автономні маніфести, вбудовані
літерали `basePath`/`assetPrefix` (Next 16 формує URL-адреси ресурсів SSR лише з
`assetPrefix` — засіб виправлення дублює в ньому підшлях), вбудовані URL-адреси
ресурсів `/_next/static` (маніфести клієнтських посилань, імпорти медіафайлів,
попередньо відрендерені сторінки помилок) і клієнтську підстановку `process.env` перед
запуском `node dev/run-standalone.mjs`.

### Збирання через Compose (рекомендовано)

Задайте обидві змінні у `.env`, а потім повторно зберіть образ, щоб налаштування
образу та середовища виконання збігалися:

```bash
# .env
OMNIROUTE_BASE_PATH=/omniroute
NEXT_PUBLIC_BASE_URL=https://myhostname.example.com/omniroute
```

```bash
docker compose --profile base up -d --build
```

`docker-compose.yml` передає `OMNIROUTE_BASE_PATH` як аргумент збирання Docker і як
змінну середовища виконання.

### Попередньо зібраний кореневий образ + підшлях під час виконання

Опубліковані образи `diegosouzapw/omniroute:*` зібрано для кореня домену. Ви все одно
можете задати `OMNIROUTE_BASE_PATH` під час виконання; контейнер одноразово виправить
пакет під час запуску. Використовуйте його разом із відповідним публічним джерелом:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    environment:
      OMNIROUTE_BASE_PATH: /omniroute
      NEXT_PUBLIC_BASE_URL: https://myhostname.example.com/omniroute
```

Налаштуйте зворотний проксі так, щоб він передавав **повний** зовнішній шлях (не
видаляйте префікс). Traefik має спрямовувати `PathPrefix(`/omniroute`)` до контейнера
без `StripPrefix`, щоб Next.js отримував `/omniroute/...` і обслуговував ресурси з
`/omniroute/_next/...`.

Перевірка працездатності Docker звертається до полегшеної кінцевої точки життєвого
циклу `/healthz` із префіксом активного `OMNIROUTE_BASE_PATH`.
`/api/monitoring/health` залишається доступною для діагностики користувачами та через
панелі моніторингу; щоб знову спрямувати на неї HEALTHCHECK контейнера (наприклад, для
поглибленого контролю працездатності), задайте
`OMNIROUTE_HEALTHCHECK_PATH=/api/monitoring/health`. Цей шлях виконує **поглиблену**
перевірку (БД + зведення моніторингу) — вона підходить для нечастого `HEALTHCHECK`
Docker, якщо ви вирішите знову її ввімкнути, але **не** для інтервалів
`livenessProbe` у Kubernetes.

Для оркестраторів (Kubernetes, Nomad тощо):

| Перевірка             | Рекомендовано                                                         | Уникайте                                                       |
| --------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| Життєздатність        | HTTP `GET /livez` або TCP на основному порту (`PORT`, типово `20128`) | `/api/monitoring/health` як перевірки життєздатності           |
| Готовність            | HTTP `GET /healthz`                                                   | Коротких тайм-аутів, що вважають зайнятий цикл подій зупиненим |
| Поглиблена / зовнішня | `/api/monitoring/health`                                              | —                                                              |

`/healthz` повідомляє про стан життєвого циклу процесу (`ok` / `starting` /
`stopping`). `/livez` перевіряє лише те, чи працює процес (повертає 200 щоразу, коли
обробник може виконатися; вона не очікує готовності). Обидві кінцеві точки все одно
працюють у тому самому циклі подій Node, що й обробка запитів, тому ресурсомісткі
операції з каталогом або стисненням можуть спричиняти затримки — зайнятий ≠
зупинений. Якщо HTTP-перевірки завершуються через тайм-аут, віддавайте перевагу
перевірці життєздатності через TCP. Повні рекомендації щодо перевірок:
[Посібник із моніторингу — рекомендації щодо перевірок Kubernetes](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations).

## Docker Compose із Caddy (автоматичний TLS для HTTPS)

OmniRoute можна безпечно опублікувати за допомогою автоматичного налаштування SSL у Caddy. Переконайтеся, що DNS-запис A вашого домену вказує на IP-адресу вашого сервера.

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:latest
    container_name: omniroute
    restart: unless-stopped
    volumes:
      - omniroute-data:/app/data
    environment:
      - PORT=20128
      # Джерело, доступне браузеру, для зворотних викликів OAuth, посилань панелі керування та згенерованих публічних URL-адрес.
      - NEXT_PUBLIC_BASE_URL=https://your-domain.com
      # Внутрішня URL-адреса між серверами для запланованих завдань / запитів до самого себе.
      - BASE_URL=http://omniroute:20128
      - AUTH_COOKIE_SECURE=true

  caddy:
    image: caddy:latest
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    command: caddy reverse-proxy --from https://your-domain.com --to http://omniroute:20128

volumes:
  omniroute-data:
```

Caddy встановлює стандартні заголовки переспрямування для висхідного контейнера. OmniRoute використовує
`NEXT_PUBLIC_BASE_URL` як канонічне публічне джерело для зворотних викликів OAuth і згенерованих публічних
посилань; автентифіковані операції запису з панелі керування використовують запити з того самого джерела та прив’язаний до сеансу захист CSRF.
Вмикайте `OMNIROUTE_TRUST_PROXY` лише для розширених розгортань, у яких ви свідомо
хочете, щоб OmniRoute визначав публічне джерело на основі довірених пересланих заголовків замість явної
конфігурації.

## Швидкий тунель Cloudflare

Підтримка панелі керування для розгортань Docker включає **швидкий тунель Cloudflare**, який можна активувати одним натисканням у `Панель керування → Кінцеві точки`. Під час першого ввімкнення `cloudflared` завантажується лише за потреби, запускається тимчасовий тунель до вашої поточної кінцевої точки `/v1`, а згенерована URL-адреса `https://*.trycloudflare.com/v1` відображається безпосередньо під вашою звичайною публічною URL-адресою.

Панелі тунелів кінцевих точок (Cloudflare, Tailscale, ngrok) можна показувати або приховувати через `Налаштування → Вигляд`, не змінюючи стан активного тунелю.

### Примітки щодо тунелів

- URL-адреси швидких тунелів є тимчасовими та змінюються після кожного перезапуску.
- Швидкі тунелі не відновлюються автоматично після перезапуску OmniRoute або контейнера. За потреби повторно ввімкніть їх із панелі керування.
- Кероване встановлення наразі підтримує Linux, macOS і Windows на `x64` / `arm64`.
- Керовані швидкі тунелі за замовчуванням використовують транспорт HTTP/2, щоб уникнути надокучливих попереджень QUIC про буфер UDP в контейнерних середовищах з обмеженими ресурсами. Установіть `CLOUDFLARED_PROTOCOL=quic` або `auto`, якщо бажаєте використовувати інший транспорт.
- Образи Docker містять системні кореневі сертифікати ЦС і передають їх керованому `cloudflared`, що запобігає помилкам довіри TLS під час ініціалізації тунелю всередині контейнера.
- Установіть `CLOUDFLARED_BIN=/absolute/path/to/cloudflared`, якщо хочете, щоб OmniRoute використовував наявний бінарний файл замість завантаження нового.

| ------------------------ | -------- | ------ | ---------------------------------------------------------------- |

### Канали випусків

OmniRoute публікує окремі канали Docker для стабільних випусків, тестування активної гілки випуску та збірок для розробки.

| Канал                           | Джерело                                          | Змінюваність                           | Рекомендоване використання                                                                                                        |
| ------------------------------- | ------------------------------------------------ | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `:<version>` / `:<version>-web` | Підписаний/версійований випуск                   | Незмінний                              | Робочі розгортання, які закріплюють точний випуск                                                                                 |
| `:latest` / `:latest-web`       | Найвища **опублікована** стабільна версія SemVer | Змінний стабільний вказівник           | Відстежує стабільні випуски **після** завдання публікації SemVer — **не** відстежує `main` або неопубліковані коміти `release/v*` |
| `:next` / `:next-web`           | Поточна стандартна гілка `release/v*`            | Змінний вказівник попереднього випуску | Тестування виправлень, які вже потрапили до активної гілки випуску, але ще не ввійшли до стабільного випуску                      |
| `:main` / `:main-web`           | Гілка `main`                                     | Змінний вказівник розробки             | Лише розробка та інтеграційне тестування                                                                                          |

#### Постачальники вебсеансів: образи `-web`

Кожен наведений вище канал також має тег `-web` (`:latest-web`, `:<version>-web`, `:next-web`, `:main-web`), зібраний з етапу `runner-web` — це той самий образ із доданими Playwright і браузером Chromium. Звичайний образ постачається **без** Chromium; він потрібен для `gemini-web`, `claude-web` і `claude-turnstile`.

Помилка виникає не під час запуску, а пізніше: ці постачальники відображають свої моделі та показуються як підключені в панелі керування, і лише перший запит завершується помилкою

```
[500]: Failed to load external module playwright: Error: Cannot find module
'/app/node_modules/playwright/node_modules/playwright-core/browsers.json'
```

Якщо ви використовуєте цих постачальників, завантажте тег `-web` каналу, який уже використовуєте — більше нічого не змінюється. Для встановлення через npm/CLI (без образу Docker) відповідним відсутнім компонентом є бінарний файл браузера: виконайте `npx playwright install chromium` на хості.

#### Використання каналу попередніх випусків

Канал `next` перебудовується після кожного push до поточної стандартної гілки `release/v*` і публікується як для AMD64, так і для ARM64. Старіші гілки супроводу не можуть його перезаписати. Канал надає доступний для завантаження образ із виправленнями, які було об’єднано з активною гілкою випуску до створення наступного стабільного тегу.

```bash
docker pull diegosouzapw/omniroute:next
docker pull diegosouzapw/omniroute:next-web
```

Для Docker Compose перевизначте тег образу, який використовує вибраний профіль, а потім завантажте образ і повторно створіть сервіс:

```yaml
services:
  omniroute:
    image: diegosouzapw/omniroute:next
```

```bash
docker compose pull
docker compose up -d
```

#### Безпека та відкат

`next` — це рухомий канал попередніх випусків. Він може змінюватися після будь-якого push до активної гілки випуску та **не підтримується для використання у виробничому середовищі**. Під час оцінювання конкретної збірки закріпіть дайджест образу:

```bash
docker pull diegosouzapw/omniroute:next
docker image inspect diegosouzapw/omniroute:next --format '{{index .RepoDigests 0}}'
```

Перед тестуванням створіть резервну копію тому даних OmniRoute або каталогу даних, підключеного через bind mount. Щоб виконати відкат, відновіть раніше використану стабільну версію або дайджест і повторно створіть контейнер:

```bash
docker pull diegosouzapw/omniroute:<stable-version>
docker compose up -d
```

Збірка з гілки випуску ніколи не може перемістити `latest`; оновити вказівник на стабільну версію може лише відповідна стабільна семантична версія. Для образів `next` зберігаються перевірка образу випуску та блокувальний бар’єр для вразливостей рівня CRITICAL.

**`latest` не гарантує актуальність щодо git.** Об’єднані виправлення в `main` або в активній гілці `release/v*` **не** потрапляють до `:latest`, доки не буде опубліковано стабільний образ SemVer і завдання публікації не оновить `:latest` (той самий дайджест, що й у відповідної версії SemVer). Якщо `latest` здається незмінним, хоча GitHub уже показує виправлення, завантажте `:next`, щоб протестувати гілку випуску, або дочекайтеся тегу SemVer.

| Ваша мета                                                                                           | Використовуйте                           |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| GitOps / виробниче середовище, де неприпустимі неочікувані зміни                                    | Закріпіть `:X.Y.Z` (або дайджест образу) |
| Стежити за опублікованими стабільними версіями та приймати повторне створення після кожного випуску | `:latest`                                |
| Тестувати невипущені коміти `release/v*`                                                            | `:next` (не для виробничого середовища)  |
| Тестувати `main`                                                                                    | `:main` (не для виробничого середовища)  |

## Доступність: стандартна SQLite підтримує лише одну репліку

Стандартне розгортання OmniRoute у Docker / Kubernetes — це **один процес Node + один записувач SQLite**. Висока доступність у такій топології **не підтримується**.

| Обмеження                                                      | Наслідок                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Один записувач                                                 | **Не** запускайте кілька реплік з одним і тим самим файлом SQLite. Це пошкоджує БД.                                                                                                                                                                                                                                                                        |
| Повторне створення / перезапуск / завершення через HEALTHCHECK | **Повна недоступність** активних SSE-з’єднань, сесій панелі керування та стану в пам’яті. Усі підключені клієнти від’єднуються. Нові запити протягом періоду без доступних кінцевих точок отримують від зворотного проксі **`502 Bad Gateway: Unknown error`**, а не JSON від OmniRoute — клієнти не можуть відрізнити це від збою постачальника (#11015). |
| Той самий цикл подій, що й `/healthz`                          | Завантажена операція з каталогом або цикл стиснення можуть затримати перевірки; короткий тайм-аут тоді спричинить перезапуск **єдиної** репліки.                                                                                                                                                                                                           |

**Матриця перевірок** (див. також [рекомендації щодо перевірок Kubernetes](../ops/MONITORING_GUIDE.md#kubernetes-probe-recommendations)):

| Перевірка              | Ціль                                                               | Не використовуйте                                                        |
| ---------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Життєздатність         | TCP на `PORT` (типово `20128`) або м’яка HTTP-перевірка `/healthz` | `/api/monitoring/health`                                                 |
| Готовність             | HTTP `GET /healthz`                                                | Короткі тайм-аути, які трактують зайнятий цикл подій як непрацездатність |
| Поглиблена / для людей | `/api/monitoring/health`                                           | Автоматизовану перевірку життєздатності kubelet                          |

**Оновлення:** очікуйте розриву кожної сесії. Якщо можливо, поступово відключіть клієнтів; стандартна SQLite не підтримує безперервне оновлення. Compose `restart: unless-stopped` разом із Docker `HEALTHCHECK` також замінить єдиний процес, коли контейнер перебуватиме в стані Unhealthy — з тим самим масштабом наслідків.

Фрагмент Kubernetes для **однієї репліки** (Recreate є обов’язковим; не збільшуйте `replicas` для одного файлу SQLite):

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: omniroute
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sleep", "15"]
          readinessProbe:
            httpGet:
              path: /healthz
              port: 20128
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 20128
            periodSeconds: 20
```

Затримка `preStop` дає kube змогу видалити кінцеві точки Service до SIGTERM, щоб **новий** трафік більше не надходив до процесу, який завершується. Активні SSE-з’єднання `/v1/responses` обслуговуються до завершення протягом максимум `SHUTDOWN_TIMEOUT_MS` (типово 30 с) за допомогою ресурсомістких оренд допуску (#11015). Нові запити, які все одно досягають процесу, отримують `503` + `Retry-After: 5`. Проміжок Recreate без доступних кінцевих точок, доки заміна не стане Ready, залишається періодом повної недоступності — це властивість топології SQLite, а не неправильна конфігурація перевірок.

Зовнішня Postgres / високодоступна топологія з кількома записувачами **не** є документованим стандартним варіантом. Якщо вам потрібна висока доступність, використовуйте одну репліку або топологію, яку проєкт протестував і задокументував окремо. Робота над Postgres/MySQL ведеться в [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075). До її завершення єдиний підтримуваний спосіб збільшити пропускну здатність для **великих** `/v1/responses` — це N незалежних процесів (наступний розділ), а не `replicas > 1` на одному томі.

## Горизонтальне масштабування: N незалежних процесів

Один процес Node — це **одна купа V8**. Два паралельні запити агента програмування `POST /v1/responses` розміром ~3 MiB / ~750 тис. токенів (RTK + Caveman) спричиняють аварійне завершення цієї купи приблизно на 12 Gi (`FATAL ERROR: Reached heap limit`) і можуть спричинити OOM у cgroup із 16 Gi. Див. [#7849](https://github.com/diegosouzapw/OmniRoute/issues/7849). Це вимірювання є попередженням щодо **бюджету пам’яті**, а не жорстким продуктовим обмеженням у два паралельні довгі запити `/v1/responses`. Допуск ресурсомістких чатів контролюється автоматично визначеним бюджетом байтів вхідних даних (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, `src/shared/middleware/admissionBudget.ts`), розрахованим на основі тієї самої межі V8/cgroup — збільшення цього значення вручну (або встановлення застарілого обмеження кількості запитів `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) у вже налаштованому за розміром процесі знову призводить до аварійного завершення. Малі чати, `/healthz`, `/v1/models` і MCP **не** підпадають під це обмеження.

### Один процес: понад два довгі запити `/v1/responses`

**Здоровий** процес (купа нижче за `OMNIROUTE_CHAT_ADMISSION_HEAP_SHED_RATIO`, типове значення `0.75`) **може** виконувати понад два паралельні довгі запити `POST /v1/responses`, якщо в загальнопроцесному бюджеті байтів активних запитів (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` / #10110) ще є місце. Тіла розміром не менше за `OMNIROUTE_CHAT_LARGE_BODY_BYTES` (типове значення 256 KiB) отримують таку саму оренду для ресурсомістких запитів, як і запити зі складною структурою, та використовують той самий механізм обходу `tryAcquireHealthyHeadroom` із [#10437](https://github.com/diegosouzapw/OmniRoute/pull/10437) (`OMNIROUTE_CHAT_ADMISSION_HEALTHY_HEADROOM`). Десятки паралельних довгих SSE-клієнтів (операторам часто потрібно 40–50) — це питання **бюджету пам’яті**: слід налаштувати розмір купи, основні/резервні слоти та `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, а не покладатися на жорстке продуктове обмеження «не більше 2». Процес із перевантаженою купою все одно відхиляє навантаження з повторюваною помилкою `503`, щоб проблема #7849 не повернулася.

Щоб **помножити кількість куп** (незалежних просторів старого покоління V8) **вже сьогодні**:

| Робіть                                                                                                                                                                                                           | Не робіть                                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Запускайте **N контейнерів/подів**, кожен зі **своїм** `DATA_DIR` / томом                                                                                                                                        | Не встановлюйте `replicas > 1` для одного файла SQLite                                |
| Розраховуйте кількість ресурсомістких активних запитів і резерв здорового стану на основі бюджету купи / байтів активних запитів; 1–2 — це консервативне типове значення для #7849, а не жорстка продуктова межа | Не надавайте одному процесу у 8 разів більше RAM із необмеженим лімітом кількості     |
| Необов’язково: `QUOTA_STORE_DRIVER=redis` + `QUOTA_STORE_REDIS_URL` для **спільних лічильників квот**                                                                                                            | Не вважайте Redis спільною SQLite — це не так                                         |
| Дублюйте секрети провайдерів у кожному екземплярі (або погодьтеся з розділеними панелями моніторингу)                                                                                                            | Не очікуйте єдиної панелі моніторингу / єдиного журналу викликів для всіх екземплярів |
| Розмістіть попереду будь-який балансувальник навантаження; достатньо прив’язки за API-ключем або сеансом                                                                                                         | Не вимагайте специфічного для постачальника проміжного ПЗ, що враховує розмір         |

Апаратні ресурси: кількість паралельних довгих запитів `/v1/responses` на один екземпляр — це питання **бюджету пам’яті** (купа + байти активних запитів / #10110). `N` незалежних `DATA_DIR` усе одно множать кількість куп: оперативної пам’яті хоста має вистачати на `N × cgroup`, а не на «один под із 16 Gi та N=8». Ніколи не використовуйте `replicas > 1` для одного файла SQLite.

Приклад Compose (дві купи, два томи — не `deploy.replicas: 2`):

```yaml
services:
  omniroute-a:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-a-data:/app/data]
    ports: ["20128:20128"]
  omniroute-b:
    image: diegosouzapw/omniroute:3.8.49
    environment:
      DATA_DIR: /app/data
      OMNIROUTE_MEMORY_MB: "12288"
      QUOTA_STORE_DRIVER: redis
      QUOTA_STORE_REDIS_URL: redis://redis:6379
    volumes: [omniroute-b-data:/app/data]
    ports: ["20138:20128"]
volumes:
  omniroute-a-data:
  omniroute-b-data:
```

Щільність усередині процесу (винесення стиснення з HTTP-ізоляту) розглядається в [#11023](https://github.com/diegosouzapw/OmniRoute/issues/11023). Єдиний логічний кластер на основі спільного постійного сховища розглядається в [#8075](https://github.com/diegosouzapw/OmniRoute/issues/8075).

## Регіональні помилки Gemini усередині Docker

Google AI Studio / Gemini API може повертати HTTP 400 із FAILED_PRECONDITION та
`User location is not supported for the API use.` Успішний запит на хості
не доводить, що контейнер використовує той самий вихідний маршрут. Порядок DNS,
підключення IPv4/IPv6, маршрутизація VPN і налаштовані проксі можуть відрізнятися. Перевірте
[регіони, які підтримує Google](https://ai.google.dev/gemini-api/docs/available-regions),
а також фактичний маршрут з'єднання; сама по собі ця помилка не вказує на недійсний ключ API.

### Надавайте перевагу проксі для окремого з'єднання

Використовуйте [налаштування проксі для окремого з'єднання](../ops/PROXY_GUIDE.md#4-level-proxy-system)
OmniRoute для відповідного з'єднання Gemini, а потім повторіть **Перевірку з'єднання** та невеликий запит
із тією самою моделлю. Так зміна маршрутизації застосовуватиметься лише до цього з'єднання. Переконайтеся,
що проксі доступний із контейнера та що з'єднання справді його вибирає.
Зміна маршруту не гарантує регіональної доступності на стороні постачальника.

### Порівняйте мережеві налаштування хоста й контейнера

Порівнюючи результати автентифікованих запитів, не змінюйте ключ, модель і запит; ніколи
не вставляйте в повідомлення про проблему облікові дані, паролі проксі або повні заголовки авторизації.
Спочатку перевірте, які сімейства адрес пропонує системний резолвер, використовуючи ту саму команду
на хості та всередині контейнера:

```bash
node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
docker compose exec omniroute node -e 'require("node:dns").lookup("generativelanguage.googleapis.com", {all: true}, (error, addresses) => { if (error) { console.error(error.code); process.exitCode = 1; return; } console.log(addresses.map(({family}) => family)); })'
```

Замініть `omniroute` на службу, яку ви запускаєте (наприклад, `omniroute-web`). Ці
команди виводять сімейства адрес без облікових даних або IP-адрес. Повернене значення `6`
лише вказує на результат DNS для IPv6: воно **не** доводить наявність працездатного маршруту IPv6 або доступу до API.
Якщо встановлено `curl`, порівняйте `curl -4 -I https://generativelanguage.googleapis.com`
із `curl -6 -I https://generativelanguage.googleapis.com` в обох середовищах.
Відповідь HTTP підтверджує наявність підключення для цієї перевірки, навіть якщо це помилка
неавтентифікованого запиту; лише автентифікований запит до моделі перевіряє доступність Gemini.

### Альтернатива на рівні хоста: працездатний IPv6 і політика резолвера

Автор повідомлення [#12762](https://github.com/diegosouzapw/OmniRoute/issues/12762) відновив
доступ у своєму середовищі, увімкнувши IPv6 для контейнера та змінивши вибір адрес у glibc.
Розглядайте це як альтернативу, специфічну для конкретного середовища. Перш ніж змінювати налаштування резолвера,
переконайтеся, що IPv6 на хості працює, вихідний трафік і маршрутизацію контейнера налаштовано, а правила брандмауера коректні.
Сама по собі приватна адреса ULA не підтверджує наявність загальнодоступного підключення IPv6.

Для служб, уже підключених до стандартної мережі Compose, цей фрагмент вмикає
IPv6 у цій мережі; збережіть решту налаштувань служби, портів, томів і конфігурації:

```yaml
networks:
  default:
    enable_ipv6: true
```

Для іменованої мережі ввімкніть його в мережі, до якої фактично підключається служба. Docker може
виділити підмережу ULA; явно вказуйте підмережу, що не перетинається з іншими, лише тоді, коли цього
потребує ваша мережа. Див. [мережеві налаштування IPv6 у Docker](https://docs.docker.com/engine/daemon/ipv6/)
та [параметри мережі Compose](https://docs.docker.com/reference/compose-file/networks/#enable_ipv6).

В **образі на основі glibc** файл `/etc/gai.conf` може змінювати вибір адрес. Поточний
Dockerfile репозиторію використовує Debian; власні образи на основі musl не підтримують цей механізм.
Описане коригування змінює мітку ULA з `label fc00::/7 6` на
`label fc00::/7 1`. Почніть із повної таблиці політик образу та збережіть усі інші
записи: додавання запису `label` або `precedence` замінює цю стандартну таблицю, тому файла,
що містить лише змінений рядок, недостатньо. У
[довіднику з конфігурації glibc](https://github.com/bminor/glibc/blob/master/posix/gai.conf)
описано цю семантику. Підключіть перевірений файл лише для читання до `/etc/gai.conf`
і повторно створіть службу, щоб застосувати його.

Це змінює вибір адрес на рівні ОС для **всього вихідного трафіку в цьому контейнері**.
Це не змушує кожну програму вибирати IPv6: порядок DNS і вибір з'єднання в Node
також мають значення. Зокрема, `--dns-result-order=ipv4first` надає перевагу IPv4 і
не усуває помилку, що виникає лише з IPv4. Див. [порядок DNS у Node](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder).

Після будь-якої зміни на рівні хоста повторно перевірте Gemini та інших постачальників. Щоб відкотити зміни,
видаліть власне монтування `gai.conf`, відновіть попередню конфігурацію мережі та
повторно створіть відповідну службу або мережу під час вікна технічного обслуговування. Повторне створення мережі
може перервати роботу інших підключених до неї контейнерів; не видаляйте том із постійними даними.

## Важливі примітки

- **Режим WAL SQLite:** команді `docker stop` слід дозволити завершити роботу, щоб OmniRoute міг виконати контрольну точку та записати останні зміни назад у `storage.sqlite`. Файли Compose, що входять до комплекту, уже задають 40-секундний пільговий період для зупинки. Якщо ви запускаєте образ безпосередньо, залиште `--stop-timeout 40`.
- **`DISABLE_SQLITE_AUTO_BACKUP`:** Установіть значення `true`, якщо регулярними резервними копіями та резервними копіями перед записом керує зовнішня система. Міграції наявної бази даних усе одно потребують окремого надійного знімка для захисту та механізму запобігання масовій міграції.
- **Збереження даних:** Завжди підключайте том до `/app/data`, щоб зберігати базу даних, ключі та конфігурації після перезапусків контейнера.
- **Налаштування порту:** Перевизначте змінну середовища `PORT`, щоб змінити стандартний порт `20128`.
