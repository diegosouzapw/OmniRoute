OmniRoute надає **два** способи використання OpenAI Codex:

| Провайдер              | Як він взаємодіє з OpenAI                                                                                                                                                               | Застереження щодо використання                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **`codex`**            | Безпосередньо повторно використовує ваш OAuth-токен ChatGPT/OpenAI для доступу до Responses API                                                                                         | **Так** — офіційна сесія не авторизована для використання через проксі/маршрутизатор |
| **`codex-app-server`** | Керує **власним `codex app-server` Codex CLI** через JSON-RPC/WebSocket; CLI самостійно керує своїм OAuth і оновлює його (`~/.codex/auth.json`) так само, як інтерактивна сесія `codex` | **Ні** — OmniRoute ніколи не передає токен API повторно                              |

Оскільки `codex-app-server` ніколи не передає токен повторно, на нього не
поширюється застереження щодо повторного використання сесії. Однак для нього
потрібен **Codex CLI, доступний за налаштованою URL-адресою app-server**, і в
цьому CLI має бути **виконано вхід**.

## 1. Архітектура

```
┌─ Застосунок OmniRoute ──────────┐        ┌─ Сайдкар codex-app-server ──────────┐
│  CodexAppServerExecutor          │  WS    │  codex app-server                   │
│  ws://codex-app-server:1456 ─────┼───────▶│  --listen ws://0.0.0.0:1456         │
│  (+ токен доступу)               │  JSON  │  --ws-auth capability-token         │
│                                  │  RPC   │  самостійно керує OAuth OpenAI      │
└──────────────────────────────────┘        │  (~/.codex/auth.json, автооновлення)│
        │ спільний доступ (томи compose)     └─────────────────────────────────────┘
        ▼
  codex-appserver-token   → токен доступу WS (підключений в обох контейнерах)
  codex-appserver-home    → ~/.codex (auth.json записується панеллю керування,
                             читається codex app-server у сайдкарі)
```

- Сайдкар прослуховує **лише** внутрішню мережу compose
  (`ws://codex-app-server:1456`) із захистом токеном доступу. Він **ніколи**
  не публікується на хості чи в інтернеті.
- Codex CLI вбудовано в `omniroute:base`, тому під час запуску сайдкара
  встановлювати codex на хості чи комп’ютері користувача не потрібно.

## 2. Запуск

```bash
# Запустіть стек З профілем сайдкара codex app-server:
docker compose --profile base --profile codex-app-server up -d
# (podman: podman compose --profile base --profile codex-app-server up -d)
```

Під час першого запуску сайдкар створює свій токен доступу WS (у спільному томі
`codex-appserver-token`), а застосунок читає той самий токен через
`OMNIROUTE_CODEX_APPSERVER_WS_TOKEN_FILE`. Налаштовувати токен вручну не
потрібно.

## 3. Підключення та вхід

1. На панелі керування додайте підключення для **OpenAI Codex (App-Server)**. API
   key або токен не потрібен (це провайдер без автентифікації — автентифікацією
   керує сайдкар).
2. Якщо в Codex CLI сайдкара **ще не виконано вхід**, перевірка справності
   підключення повідомить _«працює, але вхід не виконано»_ (а не покаже червону
   помилку автентифікації). Скористайтеся кнопкою **Увійти через ChatGPT**: вона
   запускає стандартну OAuth-автентифікацію Codex на пристрої у вашому браузері,
   а потім записує `~/.codex/auth.json` у спільний том через **Застосувати дані
   автентифікації** (один і той самий вхід обслуговує провайдери `codex` і
   `codex-app-server`).
3. Після входу перевірка справності стає зеленою (вона перевіряє як `/readyz`,
   **так і** `account/read` — тобто чи сервер працює _і_ чи виконано
   автентифікацію), після чого все починає працювати.

Панель керування ніколи не перезаписує справний наявний
`~/.codex/auth.json` — запис виконується лише тоді, коли файл відсутній або його
токен застарів (резервна копія створюється завжди).

## 4. Сценарії розгортання

- **Оператор із уже автентифікованим Codex CLI** — підключіть каталог хоста
  `~/.codex` до сайдкара (`codex-appserver-home`) і пропустіть крок входу.
- **Зовнішній користувач без локально встановленого codex** — це не має
  значення: CLI уже є в сайдкарі. Користувач проходить автентифікацію лише через
  панель керування.
- **OmniRoute на фізичному сервері (без сайдкара, codex на хості)** — задайте в
  `OMNIROUTE_CODEX_APPSERVER_WS` адресу власного `codex app-server` і
  переконайтеся, що в codex на хості виконано вхід; якщо виконуваний файл
  відсутній, з’явиться підказка «codex не встановлено».

## 5. Домашній / UDP-вихідний трафік (додатково для оператора, не постачається)

Наведений вище універсальний сайдкар спрямовує вихідний трафік через звичайну
мережу контейнера. Оператор, якому потрібно спрямовувати трафік Codex через
**домашню вихідну точку** (наприклад, TUN-сайдкар tailscale, що передає TCP +
UDP/QUIC), запускає її як окреме перевизначення compose; воно навмисно **не**
входить до профілю `codex-app-server`, що постачається. Інструкції з такого
налаштування дивіться у внутрішньому посібнику з експлуатації.
