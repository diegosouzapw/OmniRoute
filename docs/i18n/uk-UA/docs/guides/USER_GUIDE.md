## 🎯 Варіанти використання

### Випадок 1: «Я маю підписку Claude Pro»

**Проблема:** квота згорає невикористаною, а під час інтенсивного програмування спрацьовують обмеження частоти запитів

```
Комбінація: "maximize-claude"
  1. cc/claude-opus-4-7        (використовуйте підписку повністю)
  2. glm/glm-4.7               (дешевий резервний варіант після вичерпання квоти)
  3. if/qwen3.8-max-preview       (безкоштовний аварійний резервний варіант)

Щомісячна вартість: $20 (підписка) + ~$5 (резерв) = загалом $25
замість $20 + розчарування через досягнення лімітів
```

### Випадок 2: «Я хочу нульову вартість»

**Проблема:** не можу дозволити собі підписки, але потрібен надійний ШІ для програмування

```
Комбінація: "zero-cost"
  1. if/kimi-k2.7-code          (зазначено безкоштовний доступ; можуть застосовуватися обмеження частоти запитів)
  2. kr/qwen3-coder-next        (безкоштовний резервний варіант Kiro)

Щомісячна вартість: $0
Якість: перевірте модель, обмеження, конфіденційність і SLA для свого робочого навантаження
```

### Випадок 3: «Мені потрібне програмування 24/7 без перерв»

**Проблема:** стислі терміни, не можу дозволити собі простої

```
Комбінація: "always-on"
  1. cc/claude-opus-4-7        (найкраща якість)
  2. cx/gpt-5.5                (друга підписка)
  3. glm/glm-4.7               (дешево, скидання щодня)
  4. minimax/MiniMax-M2.1      (найдешевше, скидання кожні 5 год)
  5. if/deepseek-v4-flash       (зазначено безкоштовний доступ; можуть застосовуватися обмеження частоти запитів)

Результат: 5 резервних рівнів підвищують стійкість; доступність зовнішніх сервісів не гарантується
Щомісячна вартість: $20-200 (підписки) + $10-20 (резерв)
```

### Випадок 4: «Я хочу БЕЗКОШТОВНИЙ ШІ в OpenClaw»

**Проблема:** потрібен ШІ-помічник у застосунках для обміну повідомленнями, цілком безкоштовно

```
Комбінація: "openclaw-free"
  1. if/qwen3.8-max-preview     (зазначено безкоштовний доступ; можуть застосовуватися обмеження частоти запитів)
  2. if/deepseek-v4-flash       (зазначено безкоштовний доступ; можуть застосовуватися обмеження частоти запитів)
  3. if/kimi-k2.7-code          (зазначено безкоштовний доступ; можуть застосовуватися обмеження частоти запитів)

Щомісячна вартість: $0
Доступ через: WhatsApp, Telegram, Slack, Discord, iMessage, Signal...
```

## 📖 Налаштування провайдерів

Щоб масово додати підключення за API-ключами з файлу CSV або JSON, скористайтеся пунктом **Панель керування → Провайдери → Імпортувати з файлу**. Стовпці є позиційними (`provider,name,apiKey,baseUrl,priority`); `provider` має вже існувати як керований провайдер або сумісний вузол. Див. [Імпорт провайдерів із файлу CSV або JSON](../providers/CSV-IMPORT.md).

### 🔐 Провайдери за підпискою

#### Claude Code (Pro/Max)

```bash
Панель керування → Провайдери → Підключити Claude Code
→ Вхід через OAuth → Автоматичне оновлення токена
→ Відстеження 5-годинної та тижневої квоти

Моделі:
  cc/claude-opus-4-7
  cc/claude-sonnet-4-6
  cc/claude-haiku-4-5-20251001
```

**Порада:** Використовуйте Opus для складних завдань, а Sonnet — для швидкості. OmniRoute відстежує квоту для кожної моделі!

На хості OmniRoute немає браузера? Запустіть `claude setup-token` будь-де, де виконано вхід у Claude Code, і вставте токен із терміном дії один рік на вкладці **Токен налаштування**. Див. [Claude Code із токеном налаштування](../providers/CLAUDE_CODE_SETUP_TOKEN.md).

Маршрути Claude та сумісні з Claude Code зберігають рівень інтенсивності міркування `max` для моделей Opus і Sonnet. Моделі Haiku не підтримують рівень інтенсивності `max`, тому перед надсиланням запиту до зовнішнього сервісу OmniRoute знижує його до високого бюджету міркування.

**Використання:** `glm/glm-4.7` — **Порада:** Coding Plan пропонує втричі більшу квоту за 1/7 вартості! Щоденне скидання о 10:00.

**Використання:** `minimax/MiniMax-M2.1` — **Порада:** Найдешевший варіант для довгого контексту (1M токенів)!

1. Оформте підписку: [Moonshot AI](https://platform.kimi.ai?aff=omniroute)

**Використання:** `kimi/kimi-k2.5` — **Порада:** Фіксовані $9/місяць за 10M токенів = фактична вартість $0.90/1M!

#### Baidu Qianfan / ERNIE

1. Зареєструйтеся: [Baidu AI Cloud Qianfan](https://cloud.baidu.com/product/wenxinworkshop)
2. Створіть API-ключ Qianfan → Панель керування → Додати API-ключ: Провайдер: `qianfan`

## 🚀 Розгортання

### Глобальне встановлення через npm (Рекомендовано)

```bash
npm install -g omniroute

# Створіть каталог конфігурації
mkdir -p ~/.omniroute

# Створіть файл .env (див. .env.example)
cp .env.example ~/.omniroute/.env

# Запустіть сервер
omniroute
# Або з власним портом:
omniroute --port 3000
```

CLI автоматично завантажує `.env` з `~/.omniroute/.env` або `./.env`.

### Режим системного трея

Запустіть OmniRoute у системному треї:

```bash
omniroute serve --tray
```

Команда завершує роботу після того, як сервер і значок у треї будуть готові.

Сервер продовжує працювати без термінала.

Режим системного трея підтримує macOS, Windows і графічні сеанси Linux. У режимі системного трея панель керування не відкривається автоматично.

Використовуйте меню системного трея для таких дій:

- Відкрити панель керування.
- Відкрити `/dashboard/logs`.
- Змінити налаштування автоматичного запуску.
- Зупинити OmniRoute.

Не поєднуйте `--tray` із такими параметрами:

- `--daemon`
- `--log`
- `--no-recovery`

Ці режими потребують іншого керування процесами.

Увімкніть запуск під час наступного входу в систему:

```bash
omniroute autostart enable
```

Автоматичний запуск використовує режим системного трея в macOS, Windows і графічних сеансах Linux. Linux без графічного інтерфейсу використовує наявну користувацьку службу systemd.

Вимкніть запуск під час входу в систему:

```bash
omniroute autostart disable
```

### Видалення

Коли OmniRoute вам більше не потрібен, ми пропонуємо два швидкі сценарії для повного видалення:

| Команда                  | Дія                                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `npm run uninstall`      | Видаляє системний застосунок, але **зберігає вашу БД і конфігурації** в `~/.omniroute`. |
| `npm run uninstall:full` | Видаляє застосунок І назавжди **стирає всі конфігурації, ключі та бази даних**.         |

> Примітка: Щоб виконати ці команди, перейдіть до папки проєкту OmniRoute (якщо ви його клонували) і запустіть їх. Якщо застосунок установлено глобально, можна просто виконати `npm uninstall -g omniroute`.

Користувачі Void Linux можуть пакувати та встановлювати OmniRoute нативно за допомогою фреймворку кроскомпіляції `xbps-src`. Це автоматизує створення автономної збірки Node.js разом із необхідними нативними прив’язками `better-sqlite3`.

<summary><b>Переглянути шаблон xbps-src</b></summary>

```bash
# Файл шаблону для 'omniroute'
pkgname=omniroute
version=3.8.0
revision=1
hostmakedepends="nodejs python3 make"
depends="openssl"

maintainer="zenobit <zenobit@disroot.org>"

homepage="https://github.com/diegosouzapw/OmniRoute"

system_accounts="_omniroute"
omniroute_homedir="/var/lib/omniroute"
export NODE_ENV=production
export npm_config_engine_strict=false
export npm_config_loglevel=error
export npm_config_fund=false
export npm_config_audit=false

do_build() {
	# Визначення цільової архітектури ЦП для node-gyp
	local _gyp_arch
	case "$XBPS_TARGET_MACHINE" in
		aarch64*) _gyp_arch=arm64 ;;
		armv7*|armv6*) _gyp_arch=arm ;;
		i686*) _gyp_arch=ia32 ;;
		*) _gyp_arch=x64 ;;
	esac

	# 1) Установлення всіх залежностей без виконання скриптів
	NODE_ENV=development npm ci --ignore-scripts

	# 2) Створення автономної збірки Next.js
	npm run build

	# 3) Копіювання статичних ресурсів до автономної збірки
	cp -r .next/static .next/standalone/.next/static
	[ -d public ] && cp -r public .next/standalone/public || true

	# 4) Компіляція нативної прив’язки better-sqlite3
	local _node_gyp=/usr/lib/node_modules/npm/node_modules/node-gyp/bin/node-gyp.js
	(cd node_modules/better-sqlite3 && node "$_node_gyp" rebuild --arch="$_gyp_arch")

	# 5) Розміщення скомпільованої прив’язки в автономній збірці
	local _bs3_release=.next/standalone/node_modules/better-sqlite3/build/Release
	mkdir -p "$_bs3_release"
	cp node_modules/better-sqlite3/build/Release/better_sqlite3.node "$_bs3_release/"

	# 6) Видалення залежних від архітектури збірок sharp
	rm -rf .next/standalone/node_modules/@img

	# 7) Копіювання залежностей середовища виконання pino, пропущених статичним аналізом Next.js:
	for _mod in pino-abstract-transport split2 process-warning; do
		cp -r "node_modules/$_mod" .next/standalone/node_modules/
	done
}

do_check() {
	npm run test:unit
}

do_install() {
	vmkdir usr/lib/omniroute/.next
	vcopy .next/standalone/. usr/lib/omniroute/.next/standalone

	# Запобігання видаленню порожніх каталогів маршрутизатора застосунку Next.js обробником після встановлення
	for _d in \
		.next/standalone/.next/server/app/dashboard \
		.next/standalone/.next/server/app/dashboard/settings \
		.next/standalone/.next/server/app/dashboard/providers; do
		touch "${DESTDIR}/usr/lib/omniroute/${_d}/.keep"
	done

	cat > "${WRKDIR}/omniroute" <<'EOF'
#!/bin/sh
export PORT="${PORT:-20128}"
export DATA_DIR="${DATA_DIR:-${XDG_DATA_HOME:-${HOME}/.local/share}/omniroute}"
export APP_LOG_TO_FILE="${APP_LOG_TO_FILE:-false}"
mkdir -p "${DATA_DIR}"
exec node /usr/lib/omniroute/.next/standalone/server.js "$@"
EOF
	vbin "${WRKDIR}/omniroute"
}

post_install() {
	vlicense LICENSE
}
```

## 🧩 Розширені можливості

### Власні моделі

Додавайте будь-який ID моделі до будь-якого постачальника, не чекаючи оновлення застосунку:

```bash
# Через API
curl -X POST http://localhost:20128/api/provider-models \
  -H "Content-Type: application/json" \
  -d '{"provider": "openai", "modelId": "gpt-5.2", "modelName": "GPT-5.2"}'

# Список: curl http://localhost:20128/api/provider-models?provider=openai
# Видалення: curl -X DELETE "http://localhost:20128/api/provider-models?provider=openai&model=gpt-5.2"
```

Або скористайтеся панеллю керування: **Постачальники → [Постачальник] → Власні моделі**.

Примітки:

- Постачальники, сумісні з OpenRouter та OpenAI/Anthropic, керуються лише через розділ **Доступні моделі**. Ручне додавання, імпорт і автоматична синхронізація додають моделі до того самого списку доступних моделей, тому для цих постачальників немає окремого розділу «Власні моделі».
- Розділ **Власні моделі** призначений для постачальників, які не надають керованого імпорту доступних моделей.

### Власні постачальники, сумісні з OpenAI

Будь-який шлюз, що підтримує API OpenAI (самостійно розгорнутий проксі, vLLM або сторонній агрегатор),
можна додати як окремий вузол постачальника:

1. **Постачальники → Додати сумісний з OpenAI**.
2. **Назва**: відображувана назва вузла.
3. **Префікс**: назва для маршрутизації. Клієнти викликають моделі у форматі `<prefix>/<model>`, тому вузол із
   префіксом `mygw` обслуговує `mygw/gpt-4o-mini`. Обов’язковий; обмежень щодо символів немає.
4. **Тип API**: сімейство кінцевих точок, які обслуговує шлюз (Chat Completions, Responses,
   Embeddings, аудіо, зображення).
5. **Базова URL-адреса**: корінь API до `/v1` включно (наприклад,
   `https://gateway.example.com/v1`), а не повний шлях `/chat/completions`. Для шлюзів із
   нестандартними шляхами їх можна вказати в розділі **Розширені налаштування** (шлях чату, шлях моделей).
6. Поле **Ключ API (для перевірки)** лише перевіряє з’єднання. Після створення вузла
   відкрийте його та скористайтеся функцією **Додати з’єднання**, щоб зберегти ключ, який використовуватимуть запити.

Вузол отримує внутрішній ID у форматі `openai-compatible-<apiType>-<uuid>`; вам ніколи
не потрібно вводити його, оскільки префікс є публічною назвою.

#### Зарезервовані префікси

Префікс не може бути ID або псевдонімом вбудованого постачальника (наприклад, `openai`, `cf`) чи
ID вилученого постачальника. Засіб визначення моделей перевіряє вбудовані ID та псевдоніми перед
власними вузлами, тому вузол, що використовує один із таких префіксів, ніколи не отримуватиме трафік:
`<prefix>/model` буде спрямовано до вбудованого постачальника або відхилено, якщо цього постачальника
було вилучено. Створення або редагування вузла з таким префіксом відхиляється з повідомленням:

```text
prefix: "<prefix>" — це зарезервований префікс постачальника; виберіть інший префікс (зарезервовані ID/псевдоніми не можна використовувати для власних вузлів, оскільки запити на кшталт <prefix>/model спрямовуються до вбудованого постачальника або відхиляються, якщо його вилучено)
```

Виберіть унікальний префікс (`mygw`, `acme-proxy`). Якщо запити до власного вузла завершуються
помилкою, у якій згадується вбудований постачальник або його облікові дані, перевірте, чи не є префікс вузла
зарезервованим: вузли, збережені до запровадження цього правила, усе ще зберігаються, але їхній префікс спрямовує
запити до вбудованого постачальника. Відредагуйте вузол і надайте йому новий префікс.

### З’єднання шлюзів OmniRoute у ланцюжок

Інший шлюз OmniRoute можна додати як **власного постачальника, сумісного з OpenAI**. Використовуйте
базову URL-адресу `/v1` вузла-партнера та окремий ключ API з мінімальними привілеями, виданий цим вузлом.

Для взаємних або багатоланкових ланцюжків увімкніть необов’язковий захист від циклів на кожному шлюзі:

```bash
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

```bash
# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4
```

Лише запити, надіслані на URL-адресу вузла-партнера, явно внесену до списку дозволених, отримують
заголовок `X-OmniRoute-Peer-Trace`. Шлюз відхиляє повторюваний ID екземпляра або вичерпаний ліміт
переходів із відповіддю HTTP `508 Loop Detected`; звичайні зовнішні постачальники не отримують метаданих про вузли-партнери.

З’єднання вузлів у ланцюжок не є реплікацією бази даних або відмовостійкістю хоста. Кожен шлюз має незалежні
стан SQLite, кеші, лічильники обмеження частоти та сеанси. Для доступності в режимі «активний/пасивний» або
«активний/активний» використовуйте зворотний проксі з перевіркою працездатності чи перемикання клієнта після відмови
та ніколи не підключайте одну базу даних SQLite до кількох запущених екземплярів OmniRoute.

### Швидкий тунель Cloudflare

- Доступно в **Панель керування → Кінцеві точки** для Docker та інших самостійно розгорнутих середовищ
- Створює тимчасову URL-адресу `https://*.trycloudflare.com`, яка переспрямовує запити до вашої поточної OpenAI-сумісної кінцевої точки `/v1`
- Під час першого ввімкнення `cloudflared` установлюється лише за потреби; під час наступних перезапусків повторно використовується той самий керований бінарний файл
- Швидкі тунелі не відновлюються автоматично після перезапуску OmniRoute або контейнера; за потреби повторно ввімкніть їх із панелі керування
- URL-адреси тунелів є тимчасовими та змінюються щоразу, коли ви зупиняєте або запускаєте тунель
- Керовані швидкі тунелі за замовчуванням використовують транспорт HTTP/2, щоб уникнути надмірної кількості попереджень QUIC про UDP-буфер у контейнерах з обмеженими ресурсами
- Установіть `CLOUDFLARED_PROTOCOL=quic` або `auto`, якщо хочете перевизначити вибір керованого транспорту
- Установіть `CLOUDFLARED_BIN`, якщо бажаєте використовувати попередньо встановлений бінарний файл `cloudflared` замість керованого завантаження
- Панелі Cloudflare Quick Tunnel, Tailscale Funnel і ngrok Tunnel можна показувати або приховувати в **Налаштування → Вигляд**. Приховування панелі не зупиняє запущений тунель.

### Інтелектуальні функції LLM-шлюзу (етап 9)

- **Семантичний кеш** — Автоматично кешує непотокові відповіді з temperature=0 (обхід за допомогою `X-OmniRoute-No-Cache: true`)
- **Ідемпотентність запитів** — Усуває дублікати запитів у межах 5 с за допомогою заголовка `Idempotency-Key` або `X-Request-Id`
- **Відстеження прогресу** — Необов’язкові події SSE `event: progress`, які вмикаються заголовком `X-OmniRoute-Progress: true`

### Стратегії маршрутизації

Налаштовуються через **Панель керування → Налаштування → Маршрутизація**. На панелі керування представлено шість найуживаніших стратегій; комбінації та автоматичний маршрутизатор внутрішньо підтримують ширший набір.

**Стратегії, доступні на панелі керування (маршрутизація на рівні облікового запису):**

| Стратегія                         | Опис                                                                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **Почергове заповнення**          | Використовує облікові записи в порядку пріоритету — основний обліковий запис обробляє всі запити, доки не стане недоступним    |
| **Циклічний розподіл**            | Циклічно перебирає всі облікові записи з налаштовуваним лімітом закріплення (за замовчуванням: 3 виклики на обліковий запис)   |
| **P2C (вибір із двох варіантів)** | Вибирає 2 випадкові облікові записи та спрямовує запит до справнішого з них — балансує навантаження з урахуванням стану        |
| **Випадковий вибір**              | Випадково вибирає обліковий запис для кожного запиту за допомогою перемішування Фішера–Єйтса                                   |
| **Найменш використовуваний**      | Спрямовує запит до облікового запису з найдавнішою часовою позначкою `lastUsedAt`, рівномірно розподіляючи трафік              |
| **Оптимізація вартості**          | Спрямовує запит до облікового запису з найнижчим значенням пріоритету, оптимізуючи вибір на користь найдешевших постачальників |

**Розширені стратегії комбінацій та автоматичного вибору** (налаштовуються для кожної комбінації або через префікси `auto/*` — див. [AUTO-COMBO.md](../routing/AUTO-COMBO.md)):

- `priority` — суворий порядок без циклічного розподілу
- `weighted` — пропорційний розподіл трафіку за вагами окремих моделей
- `fill-first` — використовує першу модель до вичерпання її лімітів
- `round-robin` / `strict-random` / `random`
- `p2c` (вибір із двох варіантів)
- `least-used` і `cost-optimized`
- `auto` — вибір серед усіх кандидатів на основі оцінювання
- `lkgp` (останній відомий справний постачальник) — закріплює останнього успішного постачальника, а потім переходить до резервних правил
- `context-optimized` — вибирає модель із найбільшим вільним контекстним вікном
- `context-relay` — об’єднує моделі з великим контекстом у ланцюжок для наступних реплік

#### Зовнішній заголовок закріпленого сеансу

Для зовнішньої прив’язки сеансу (наприклад, для агентів Claude Code/Codex за зворотними проксі) надішліть:

```http
X-Session-Id: your-session-key
```

OmniRoute також приймає `x_session_id` і повертає фактичний ключ сеансу в `X-OmniRoute-Session-Id`.

Якщо ви використовуєте Nginx і надсилаєте заголовки з підкресленнями, увімкніть:

```nginx
underscores_in_headers on;
```

#### Псевдоніми моделей із символами узагальнення

Створюйте шаблони із символами узагальнення для перепризначення назв моделей:

```
Шаблон: claude-sonnet-*     →  Ціль: cc/claude-sonnet-4-6
Шаблон: gpt-*               →  Ціль: gh/gpt-5.3-codex
```

Символи узагальнення підтримують `*` (будь-які символи) та `?` (один символ).

#### Ланцюжки резервування

Визначайте глобальні ланцюжки резервування, які застосовуються до всіх запитів:

```
Ланцюжок: production-fallback
  1. cc/claude-opus-4-7
  2. gh/gpt-5.3-codex
  3. glm/glm-4.7
```

### Відмовостійкість і автоматичні вимикачі

Налаштовуються через **Панель керування → Налаштування → Відмовостійкість**.

OmniRoute реалізує відмовостійкість на рівні постачальника за допомогою п’яти компонентів:

1. **Черга запитів і регулювання темпу** — Керування потоком запитів на рівні системи:
   - **Запитів за хвилину (RPM)** — Максимальна кількість запитів за хвилину для кожного облікового запису
   - **Мінімальний час між запитами** — Мінімальний інтервал у мілісекундах між запитами
   - **Максимальна кількість одночасних запитів** — Максимальна кількість одночасних запитів для кожного облікового запису
2. **Пауза для з’єднання** — Конфігурація для кожного типу автентифікації окремого з’єднання після помилок, що допускають повторну спробу:
   - **Базова пауза** — Стандартний період паузи після помилок вищого сервісу, що допускають повторну спробу
   - **Використовувати підказки вищого сервісу щодо повторних спроб** — Враховує авторитетні значення `Retry-After` або підказки щодо скидання, якщо їх надано
   - **Максимальна кількість кроків відкладення** — Максимальний рівень експоненційного відкладення для повторюваних помилок

3. **Автоматичний вимикач провайдера** — Відстежує наскрізні помилки провайдера, позначає його як такого, що працює з погіршенням, після досягнення налаштованого порога попередження та розмикає вимикач після досягнення налаштованого порога помилок:
   - **Поріг погіршення** — Кількість послідовних помилок провайдера перед переходом у стан `DEGRADED`
   - **Поріг помилок** — Кількість послідовних помилок провайдера перед переходом у стан `OPEN`
   - **Час очікування до скидання** — Період часу до наступної перевірки провайдера
   - **CLOSED** (Справний) — Запити обробляються у звичайному режимі
   - **DEGRADED** — Запити продовжують оброблятися, а підвищена кількість помилок відстежується
   - **OPEN** — Провайдера тимчасово заблоковано після повторюваних помилок
   - **HALF_OPEN** — Перевіряється, чи відновився провайдер

   Обмеження частоти `429` на рівні з’єднання залишаються в стані **Пауза для з’єднання** та не враховуються автоматичним вимикачем провайдера.

   Стан автоматичного вимикача провайдера під час виконання відображається лише на сторінці **Панель керування → Стан системи**.

4. **Очікування завершення паузи** — Якщо всі доступні з’єднання вже перебувають у стані паузи, OmniRoute може дочекатися завершення найкоротшої паузи та автоматично повторити той самий клієнтський запит.

5. **Автоматичне виявлення обмежень частоти** — Коли вищі провайдери повертають явні інтервали очікування, ці підказки перевизначають локальну паузу для з’єднання, якщо відповідне налаштування ввімкнено.

**Професійна порада:** Використовуйте сторінку **Стан системи**, щоб перевіряти та скидати активні автоматичні вимикачі провайдерів після збою. Сторінка «Відмовостійкість» змінює лише конфігурацію.

### Експорт / імпорт бази даних

Керуйте резервними копіями бази даних у розділі **Панель керування → Налаштування → Система та сховище**.

| Дія                            | Опис                                                                                                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Експортувати базу даних**    | Завантажує поточну базу даних SQLite як файл `.sqlite`                                                                                                                   |
| **Експортувати все (.tar.gz)** | Завантажує повний архів резервної копії, що містить базу даних, налаштування, комбінації, з’єднання провайдерів (без облікових даних) і метадані ключів API              |
| **Імпортувати базу даних**     | Завантажує файл `.sqlite`, щоб замінити поточну базу даних. Перед імпортом автоматично створюється резервна копія, якщо не встановлено `DISABLE_SQLITE_AUTO_BACKUP=true` |

```bash
# API: Експорт бази даних
curl -o backup.sqlite http://localhost:20128/api/db-backups/export

# API: Експорт усього (повний архів)
curl -o backup.tar.gz http://localhost:20128/api/db-backups/exportAll

# API: Імпорт бази даних
curl -X POST http://localhost:20128/api/db-backups/import \
  -F "file=@backup.sqlite"
```

**Перевірка імпорту:** Імпортований файл перевіряється на цілісність (перевірка за допомогою pragma SQLite), наявність обов’язкових таблиць (`provider_connections`, `provider_nodes`, `combos`, `api_keys`) і розмір (максимум 100 МБ).

**Варіанти використання:**

- Перенесення OmniRoute між комп’ютерами
- Створення зовнішніх резервних копій для аварійного відновлення
- Обмін конфігураціями між учасниками команди (експортувати все → поділитися архівом)

### Стратегії балансування комбінацій

Налаштовуйте балансування для кожної комбінації в розділі **Панель керування → Комбінації → Створити/редагувати → Стратегія**.

| Стратегія                    | Опис                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Циклічна**                 | Послідовно перебирає моделі                                                                          |
| **Пріоритетна**              | Завжди спочатку використовує першу модель; переходить до резервної лише в разі помилки               |
| **Випадкова**                | Для кожного запиту вибирає випадкову модель із комбінації                                            |
| **Зважена**                  | Розподіляє запити пропорційно до ваг, призначених кожній моделі                                      |
| **Найменш використовувана**  | Спрямовує запит до моделі з найменшою кількістю нещодавніх запитів (використовує метрики комбінації) |
| **Оптимізована за вартістю** | Спрямовує запит до найдешевшої доступної моделі (використовує таблицю цін)                           |

Глобальні типові параметри комбінацій можна встановити в розділі **Панель керування → Налаштування → Маршрутизація → Типові параметри комбінацій**.
За замовчуванням тайм-аути цілей комбінації успадковують поточний тайм-аут запиту. Використовуйте **Тайм-аут цілі
(секунди)** у типових параметрах комбінацій або для окремої комбінації лише тоді, коли коротше обмеження для кожної цілі має
швидше активувати перехід до резервного варіанта.

Оптимізації комбінацій із нульовою затримкою потребують явного ввімкнення. Залиште **Оптимізації з нульовою затримкою** вимкненими, щоб
запобігти ситуаціям, коли ці функції зменшення затримки запускають паралельні перегони між резервними цілями, пропускають цілі на основі
історії TTFT або стискають резервні запити; увімкнення дозволяє налаштоване дублювання запитів, прогнозовані пропуски за TTFT
і проактивне стискання резервних запитів, жертвуючи точністю маршрутизації та запитів заради зменшення
затримки у гірших випадках.

Вимкніть **Буфер токенів міркування**, якщо постачальники верхнього рівня вимагають суворих обмежень
`max_tokens` / `maxOutputTokens`. Коли цю функцію ввімкнено, маршрутизація комбінацій додає резерв для моделей міркування
лише для моделей із відомим обмеженням вихідних даних і не змінює клієнтський ліміт токенів, якщо
безпечне буферизоване значення перевищуватиме це обмеження. Якщо клієнтський ліміт уже перевищує відоме обмеження,
OmniRoute зменшує його до цього обмеження перед надсиланням запиту постачальнику верхнього рівня.

## 🤖 Автоматична маршрутизація (без налаштування)

OmniRoute постачається з **автоматичним маршрутизатором на основі оцінювання**, який вибирає найкращу модель для кожного запиту серед усіх підключених провайдерів — не потрібно підтримувати жодних комбінацій. Просто надішліть запит з одним із префіксів `auto/*`, і OmniRoute динамічно сформує віртуальну комбінацію, оцінюючи кандидатів за затримкою, вартістю, частотою успішних запитів, відповідністю контексту, придатністю моделі до завдання, нещодавніми збоями, квотою та станом автоматичного вимикача.

| Префікс        | Що оптимізує                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `auto`         | Збалансований варіант за замовчуванням (затримка × вартість × частота успішних запитів)                                      |
| `auto/coding`  | Завдання програмування: надає перевагу Claude, GPT-5, GLM, Kimi, Qwen Coder, моделям DeepSeek для програмування              |
| `auto/cheap`   | Найнижча вартість за токен, допускає вищу затримку                                                                           |
| `auto/fast`    | Найнижча затримка, ігнорує вартість                                                                                          |
| `auto/offline` | Лише локальні провайдери (Ollama, vLLM, llama.cpp) — корисно для ізольованих середовищ                                       |
| `auto/smart`   | Пріоритет якості міркувань (Opus, GPT-5 xhigh, R1, GLM 5.1 reasoning)                                                        |
| `auto/lkgp`    | «Останній відомий справний провайдер» — закріплює останнього успішного провайдера, а потім переходить до правил резервування |

Приклад:

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer $OMNIROUTE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto/coding",
    "messages": [{ "role": "user", "content": "Рефакторизуй цю функцію Python" }],
    "stream": true
  }'
```

Повний опис автоматичного маршрутизатора наведено в [AUTO-COMBO.md](../routing/AUTO-COMBO.md), зокрема як налаштовувати ваги оцінювання, додавати провайдерів до чорного списку та переглядати рішення щодо маршрутизації в розділі **Панель керування → Автоматична комбінація**.

## 🔌 Інтеграція MCP та A2A

OmniRoute одночасно є **сервером MCP** (Model Context Protocol) і **сервером A2A** (Agent-to-Agent JSON-RPC 2.0). Будь-яке IDE або середовище запуску агентів, сумісне з MCP, може безпосередньо викликати інструменти OmniRoute — додаткова обгортка не потрібна.

### Транспорти MCP

- **SSE**: `http://localhost:20128/api/mcp/sse`
- **Потоковий HTTP**: `http://localhost:20128/api/mcp/stream`
- **stdio**: `omniroute --mcp` (для плагінів IDE, які віддають перевагу stdio)

### Підключення Claude Desktop

Відредагуйте `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) або відповідний файл у Windows/Linux:

```json
{
  "mcpServers": {
    "omniroute": {
      "command": "omniroute",
      "args": ["--mcp"]
    }
  }
}
```

### Підключення Cursor / Continue / VS Code MCP

Використовуйте SSE URL `http://localhost:20128/api/mcp/sse` і Bearer API-ключ, створений у розділі **Панель керування → API-ключі**.

### Області доступу

Наразі MCP визначає 32 іменовані області доступу. Кожен Bearer-ключ можна обмежити певними областями доступу — актуальний перелік областей та інструментів наведено в [MCP-SERVER.md](../frameworks/MCP-SERVER.md), а схему JSON-RPC — у [A2A-SERVER.md](../frameworks/A2A-SERVER.md).

## 🧠 Система навичок

OmniRoute надає розширюваний **фреймворк навичок** (`src/lib/skills/`), завдяки якому агенти та кінцева точка A2A можуть виконувати спеціалізовані для певної предметної області процедури (наприклад, `code-review`, `summarize`, `extract-facts`, `web-research`).

- **Інтерфейс маркетплейсу** — Переглядайте та встановлюйте навички через **Панель керування → Навички**
- **Області доступу для окремих ключів** — Обмежуйте, які ключі API можуть викликати певні навички
- **Власні навички** — Додайте файл TypeScript до `src/lib/a2a/skills/`, зареєструйте його, і він одразу стане доступним для виклику через A2A

Повна довідка: [SKILLS.md](../frameworks/SKILLS.md).

## 💾 Система пам’яті

OmniRoute зберігає **довготривалу пам’ять розмов** із гібридним пошуком:

- **SQLite FTS5** для пошуку за ключовими словами в попередніх репліках
- **Векторне сховище Qdrant** (необов’язкове) для семантичного пошуку
- **Автоматичне вилучення фактів** — сутності, уподобання та рішення узагальнюються після кожного сеансу й зберігаються в таблиці `memory_facts`
- Спогади ізольовані за ключем API та сеансом

Керуйте спогадами в розділі **Панель керування → Пам’ять** (пошук, редагування, експорт, очищення). HTTP-інтерфейс (`/api/memory/*`) дає агентам змогу програмно додавати та запитувати факти — див. [MEMORY.md](../frameworks/MEMORY.md).

## 🔔 Вебхуки

Підписуйтеся на події OmniRoute для моніторингу й автоматизації в реальному часі.

- Створіть вебхук у розділі **Панель керування → Вебхуки**, указавши цільову URL-адресу та секрет для підпису HMAC
- Доступні події: `request.completed`, `request.failed`, `provider.unavailable`, `budget.exceeded`, `combo.switched`, `circuit_breaker.opened`, `circuit_breaker.closed`
- Кожне корисне навантаження містить `X-OmniRoute-Signature` (HMAC-SHA256) для перевірки
- Повторні спроби: 3 спроби з експоненційною затримкою, після чого повідомлення надсилається до черги недоставлених повідомлень

Повна схема наведена в [WEBHOOKS.md](../frameworks/WEBHOOKS.md).

## 🛠️ Програмне керування

Ви можете керувати всіма ресурсами OmniRoute (постачальниками, комбінаціями, ключами, налаштуваннями) через HTTP за допомогою **ключа Bearer з областю доступу `manage`**.

Згенеруйте ключ у розділі **Панель керування → Ключі API → Новий ключ → Область доступу: manage**, а потім:

```bash
# Вивести список постачальників
curl http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"

# Додати підключення до постачальника
curl -X POST http://localhost:20128/api/providers \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "provider": "openai", "apiKey": "sk-...", "name": "main" }'

# Створити комбінацію
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "premium", "strategy": "priority", "models": [{ "model": "cc/claude-opus-4-7" }, { "model": "glm/glm-5.1" }] }'

# Вивести список ключів API / створити ключ API
curl http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY"
curl -X POST http://localhost:20128/api/keys -H "Authorization: Bearer $OMNIROUTE_MANAGE_KEY" \
  -d '{ "name": "ci-bot", "scopes": ["chat"] }'
```

Повний каталог кінцевих точок і схеми запитів/відповідей див. у [API_REFERENCE.md](../reference/API_REFERENCE.md).

## 💻 Внутрішній CLI

OmniRoute постачається з внутрішнім CLI (`omniroute …`) для налаштування, діагностики та керування під час виконання. Він **відрізняється від сторінки «Інструменти CLI» на панелі керування**, де налаштовуються сторонні CLI (Claude Code, Cursor, Codex, Cline, …), щоб вони могли взаємодіяти з OmniRoute.

```bash
omniroute setup                    # Інтерактивний майстер (пароль, провайдери, комбінації)
omniroute setup --non-interactive  # Підходить для CI
omniroute doctor                   # Діагностика стану (каталог даних, БД, провайдери, порти)
omniroute providers available      # Показати підтримуваних провайдерів
omniroute providers list           # Показати налаштовані підключення
omniroute providers test <id>      # Перевірити підключення до провайдера в реальному часі
omniroute combos list              # Показати комбінації
omniroute combos switch <name>     # Установити стандартну комбінацію
omniroute models                   # Показати доступні моделі (--json, --search)
omniroute keys add | list | remove # Керувати ключами API з термінала
omniroute backup                   # Створити знімок конфігурації та БД
omniroute restore [<timestamp>]    # Відновити зі знімка
omniroute health                   # Докладний стан (запобіжники, кеш, пам’ять)
omniroute quota                    # Використання квоти провайдера
omniroute mcp status               # Стан сервера MCP
omniroute a2a status               # Стан сервера A2A
omniroute tunnel list|create|stop  # Тунелі Cloudflare/Tailscale/ngrok
omniroute reset-password           # Скинути пароль адміністратора
omniroute --mcp                    # Запустити сервер MCP через stdio
omniroute --port 3000              # Запустити сервер на власному порту
```

Порада: поєднайте `omniroute doctor --json` зі своїм інструментом моніторингу, щоб отримувати сповіщення про несправні підключення до провайдерів.

## 🖥️ Настільний застосунок (Electron)

OmniRoute доступний як нативний настільний застосунок для Windows, macOS і Linux.

### Встановлення

```bash
# З каталогу electron:
cd electron
npm install

# Режим розробки (підключення до запущеного сервера розробки Next.js):
npm run dev

# Робочий режим (використовує автономну збірку):
npm start
```

### Створення інсталяторів

```bash
cd electron
npm run build          # Поточна платформа
npm run build:win      # Windows (.exe NSIS)
npm run build:mac      # macOS (.dmg universal)
npm run build:linux    # Linux (.AppImage)
```

Результат → `electron/dist-electron/`

### Основні можливості

| Можливість                  | Опис                                                             |
| --------------------------- | ---------------------------------------------------------------- |
| **Готовність сервера**      | Опитує сервер перед показом вікна (без порожнього екрана)        |
| **Системний трей**          | Згортання в трей, зміна порту та вихід із меню трея              |
| **Керування портом**        | Зміна порту сервера з трея (сервер перезапускається автоматично) |
| **Політика безпеки вмісту** | Обмежувальна CSP через заголовки сеансу                          |
| **Один екземпляр**          | Одночасно може працювати лише один екземпляр застосунку          |
| **Автономний режим**        | Вбудований сервер Next.js працює без інтернету                   |

### Змінні середовища

| Змінна                | Стандартне значення | Опис                                 |
| --------------------- | ------------------- | ------------------------------------ |
| `OMNIROUTE_PORT`      | `20128`             | Порт сервера                         |
| `OMNIROUTE_MEMORY_MB` | `512`               | Обмеження купи Node.js (64–16384 МБ) |
