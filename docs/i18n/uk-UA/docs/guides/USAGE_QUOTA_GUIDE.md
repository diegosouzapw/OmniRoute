> **Коротко**: OmniRoute відстежує використання токенів для кожного запиту, обчислює вартість, застосовує квоти для кожного API-ключа та відображає аналітику на інформаційній панелі. У цьому посібнику пояснюється, як усе це працює.

**Джерела:**

- `open-sse/services/usage.ts` (~70KB) — основна логіка відстеження використання
- `src/lib/usageAnalytics.ts` (~10KB) — агрегація даних для інформаційної панелі
- `src/lib/db/quotaSnapshots.ts` — історичні дані про квоти
- `src/lib/db/usage*.ts` — кілька модулів БД, пов’язаних із використанням

---

## Огляд

Кожен запит, що проходить через OmniRoute, створює **запис про використання**, який містить:

- **Ідентифікаційні дані**: API-ключ, провайдер, модель і комбінація
- **Токени**: токени запиту, токени відповіді, кешовані токени, загальна кількість
- **Вартість**: сума в USD (обчислена на основі даних про ціни)
- **Часові показники**: затримка, часові позначки початку та завершення
- **Статус**: успіх, помилка, обмеження частоти запитів тощо

Ці записи агрегуються в **аналітику**, зберігаються як **знімки квот** і використовуються для застосування **бюджетних обмежень для кожного ключа**.

```
Запит ──▶ chatCore ──▶ usage.record() ──▶ SQLite
                                  │
                          ┌───────┼───────┐
                          ▼       ▼       ▼
                    аналітика  квота   білінг
                    (панель)  (контроль) (експорт)
```

## Що записується

Служба `usage.ts` реєструє **подію використання** для кожного запиту:

| Поле               | Тип     | Джерело                                                    |
| ------------------ | ------- | ---------------------------------------------------------- |
| `id`               | string  | UUID, згенерований під час запису                          |
| `apiKeyId`         | string  | API-ключ, який ініціював запит                             |
| `provider`         | string  | ID провайдера (openai, anthropic тощо)                     |
| `model`            | string  | ID моделі (gpt-5, claude-opus-4-6 тощо)                    |
| `comboId`          | string? | ID комбінації, якщо маршрутизація виконувалася через неї   |
| `promptTokens`     | number  | З відповіді висхідного сервісу                             |
| `completionTokens` | number  | З відповіді висхідного сервісу                             |
| `cachedTokens`     | number  | Токени з кешу (кешування запитів Anthropic тощо)           |
| `totalTokens`      | number  | запит + відповідь                                          |
| `costUsd`          | number  | Обчислюється на основі даних про ціни                      |
| `latencyMs`        | number  | Повна тривалість обробки запиту                            |
| `status`           | enum    | `success`, `error`, `rate_limited`, `timeout`, `cancelled` |
| `errorClass`       | string? | Клас помилки, якщо status != success                       |
| `timestamp`        | string  | UTC у форматі ISO 8601                                     |
| `metadata`         | object  | Власні дані, додані плагіном                               |

### Звідки беруться токени

Токени витягуються з відповіді висхідного провайдера в **обробнику відповіді**:

```ts
// З open-sse/handlers/chatCore.ts
const response = await providerExecutor.execute(provider, request);
const usage = response.usage || {
  prompt_tokens: 0,
  completion_tokens: 0,
  cached_tokens: 0,
};
```

Для провайдерів, які не повертають дані про використання (деякі провайдери на основі веб-cookie), OmniRoute **оцінює** кількість токенів за евристикою `~4 символи на токен` (див. `open-sse/services/autoCombo/pipelineRouter.ts`).

### Кешовані токени

OmniRoute відстежує `cached_tokens` окремо від `prompt_tokens`, оскільки:

- За кешування запитів Anthropic стягується знижена плата за кешовані токени (10% від звичайної)
- Деякі провайдери повертають `cache_read_input_tokens`, для яких вартість має обчислюватися інакше
- Аналітика може показувати **частку влучень у кеш** = `cached_tokens / prompt_tokens`

## Розрахунок вартості

Вартість обчислюється на основі **даних про ціни**, синхронізованих із LiteLLM (`src/lib/pricingSync.ts`):

| Модель            | Вхідні $/1М | Вихідні $/1М | Кешовані $/1М |
| ----------------- | ----------- | ------------ | ------------- |
| gpt-5             | $2.50       | $10.00       | —             |
| claude-opus-4-6   | $15.00      | $75.00       | $1.50         |
| claude-sonnet-4-5 | $3.00       | $15.00       | $0.30         |
| gemini-2.5-pro    | $1.25       | $10.00       | —             |

Формула розрахунку вартості (`src/lib/usage/costCalculator.ts`):

```ts
cost =
  (prompt_tokens - cached_tokens) * input_price +
  cached_tokens * cached_price +
  completion_tokens * output_price;
```

> **Навіщо віднімати кешовані токени від токенів запиту?** Кешована частина тарифікується окремо; застосування ціни вхідних токенів до всього запиту призвело б до подвійного врахування.

### Синхронізація цін

Дані про ціни автоматично синхронізуються з LiteLLM через кінцеву точку `/api/pricing/sync` (запускається вбудованим завданням cron, а не доступною користувачеві змінною середовища):

```bash
# Запуск вручну
curl -X POST http://localhost:20128/api/pricing/sync
```

Для моделей, для яких немає даних про ціни, OmniRoute використовує **оцінювання вартості** за внутрішніми середніми тарифами (отриманими з даних про ціни LiteLLM).

## Агрегація за діапазоном дат

Модуль `usageAnalytics.ts` обчислює віджети інформаційної панелі на основі необроблених даних про використання. Він підтримує 7 часових діапазонів:

| Діапазон | Період                                  | Сценарій використання                  |
| -------- | --------------------------------------- | -------------------------------------- |
| `1d`     | Останні 24 години                       | Виявлення погодинних стрибків вартості |
| `7d`     | Останні 7 днів                          | Щотижневий огляд                       |
| `30d`    | Останні 30 днів                         | Щомісячне виставлення рахунків         |
| `90d`    | Останні 90 днів                         | Щоквартальний аналіз                   |
| `ytd`    | Від 1 січня поточного року              | Відстеження річного бюджету            |
| `all`    | За весь час                             | Статистика за весь період              |
| `custom` | Визначені користувачем початок і кінець | Аудити, спеціальні запити              |

### Обчислювані віджети інформаційної панелі

Для будь-якого діапазону дат аналітичний рівень обчислює:

| Віджет                       | Опис                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------- |
| **Картки зведення**          | Загальна кількість запитів, загальна вартість, загальна кількість токенів, частка успішних запитів |
| **Графік денної динаміки**   | Вартість і токени за день із групуванням за моделлю                                                |
| **Теплова карта активності** | Сітка «година доби × день тижня», колір = кількість запитів                                        |
| **Розподіл за моделями**     | Кругова діаграма вартості за моделями                                                              |
| **Розподіл за провайдерами** | Стовпчикова діаграма запитів за провайдерами                                                       |
| **Найактивніші ключі API**   | Таблиця 10 ключів із найбільшою вартістю                                                           |
| **Аналіз помилок**           | Частка помилок у часі, найпоширеніші класи помилок                                                 |

### Програмний доступ

````ts
import { computeAnalytics } from "@/lib/usageAnalytics";

const analytics = await computeAnalytics(
  history,              // записи історії використання
  "7d",                 // часовий діапазон: "1d" | "7d" | "30d" | "90d" | "ytd" | "all" | "custom"
  connectionMap,        // карта підключень провайдерів (connectionId → назва облікового запису)
  {
    startDate: "2025-01-01",  // необов’язково: для діапазону "custom"
    endDate: "2025-06-01",   // необов’язково: для діапазону "custom"
  }
);

console.log(analytics.summary.totalCost);   // 12.34 (центи)
console.log(analytics.byModel[0]);           // { model, cost, requests, promptTokens, completionTokens }

## Застосування квот

Квота для кожного API-ключа застосовується у двох місцях:

1. **М’який ліміт** (`quotaWarnAt`): попередження на інформаційній панелі, коли використання перевищує порогове значення
2. **Жорсткий ліміт** (`quotaLimit`): запит відхиляється з HTTP 429, коли ліміт перевищено

### Конфігурація

```ts
// Для кожного API-ключа
await updateApiKey(keyId, {
  quotaWarnAt: 5_00,    // $5.00 — показати попередження
  quotaLimit: 10_00,    // $10.00 — жорстка зупинка
  quotaWindow: "month", // "day" | "week" | "month" | "all"
});
````

### Процес застосування

```
Запит ──▶ quotaCheck()
             │
             ├── У межах ліміту?  ──▶ дозволити
             │
             └── Понад ліміт?  ──▶ 429 Забагато запитів
                                   із заголовком Retry-After
```

### Знімки квот

Таблиця `quotaSnapshots` зберігає **історичний стан квот** для аналізу тенденцій:

| Поле | Опис |
| ----------- | -------------------------------- | ------ | ------- |
| `apiKeyId` | Ключ, використання якого відстежується |
| `window` | "day" | "week" | "month" |
| `used` | Витрати в цьому вікні (центи) |
| `limit` | Ліміт (центи) |
| `resetAt` | Час скидання вікна |
| `createdAt` | Час створення знімка |

Знімки створюються **для кожного запиту**, вартість якого > 0, і використовуються, щоб:

- Відображати індикатор використання квоти на інформаційній панелі
- Показувати графіки тенденцій квоти за 30 днів
- Запускати сповіщення, коли використання наближається до ліміту

### Запит аналітики використання

Доступ до даних про використання здійснюється через інформаційну панель або інструменти MCP, а не через прямі кінцеві точки експорту REST. Доступна аналітика:

- **`/api/usage/analytics`** — агреговані показники використання (групування за моделлю, провайдером, ключем)
- **`/api/usage/quota`** — поточний стан квоти для кожного API-ключа
- **`/api/usage/history`** — журнали історії запитів

## Зберігання та очищення

Обсяг даних про використання зростає приблизно на 1–10 КБ на запит. У великих масштабах це може бути суттєво.

### Налаштування зберігання

Термін зберігання історії використання налаштовується через параметри бази даних в інтерфейсі користувача або через `/api/settings/database`.

За замовчуванням історія використання зберігається протягом **90 днів**.

### Очищення

Старі записи очищаються за допомогою `src/lib/db/cleanup.ts`:

- Запускається фоновим процесом cron
- Видаляє з `usage_history` записи, старіші за термін зберігання, налаштований у параметрі `usageHistory`

### Оцінка обсягу сховища

| Частота запитів      | Обсяг за 30 днів | Обсяг за 90 днів |
| -------------------- | ---------------- | ---------------- |
| 100 запитів/день     | ~3 МБ            | ~9 МБ            |
| 1 000 запитів/день   | ~30 МБ           | ~90 МБ           |
| 10 000 запитів/день  | ~300 МБ          | ~900 МБ          |
| 100 000 запитів/день | ~3 ГБ            | ~9 ГБ            |

Для дуже високого трафіку розгляньте такі варіанти:

- Скорочення терміну зберігання через налаштування бази даних
- Використання `aggregated_metrics` замість необроблених записів (лише для аналітики)

## Поради щодо оптимізації витрат

### 1. Використовуйте відповідну модель

```bash
# Швидка відповідь — використовуйте дешеву й швидку модель
curl -d '{"model":"auto/fast","messages":[...]}'

# Складне завдання — використовуйте якісну модель
curl -d '{"model":"auto/smart","messages":[...]}'
```

### 2. Увімкніть кешування

Кешування промптів Anthropic дає змогу заощадити **90% на повторюваному контексті**:

```ts
// Кешування відбувається автоматично — просто додайте той самий великий системний промпт
const response = await openai.chat({
  model: "claude-sonnet-4-5",
  system: longSystemPrompt, // Буде кешовано автоматично
  messages: [{ role: "user", content: "..." }],
});
```

### 3. Використовуйте стиснення

Стиснення RTK + Caveman дає змогу заощадити **15–95% у сеансах з інтенсивним використанням інструментів**:

```ts
const config = {
  compression: {
    engine: "rtk",
    intensity: "aggressive",
  },
};
```

### 4. Установлюйте квоти для кожного ключа

Завжди встановлюйте `quotaLimit`, щоб запобігти неконтрольованим витратам:

```ts
await updateApiKey(keyId, { quotaLimit: 10_00 }); // Ліміт $10 на місяць
```

### 5. Перевіряйте найбільших споживачів

Використовуйте панель керування або **`/api/usage/analytics`**, щоб згрупувати дані за ключем API та відсортувати їх за вартістю:

```bash
GET /api/usage/analytics?groupBy=apiKey
```

## Усунення несправностей

### «Витрати вищі, ніж очікувалося»

1. Перевірте **`/api/usage/analytics?groupBy=model`** — знайдіть дорогу модель
2. Перевірте **`/api/usage/analytics?groupBy=apiKey`** — знайдіть найбільшого споживача
3. Переконайтеся, що дані про ціни актуальні: `POST /api/pricing/sync`

### «Записи відсутні»

- Перевірте налаштування терміну зберігання БД у Панель керування → База даних → Очищення — старі записи видаляються періодичним завданням очищення (`src/lib/db/cleanup.ts`)
- Перевірте наявність помилок у `src/lib/db/usage*.ts` — помилки запису в БД реєструються в журналі, але не відображаються
- Переконайтеся, що запит дійсно досяг `chatCore` — перевірте комбіновану маршрутизацію

### «Квота не застосовується»

- Перевірте налаштування `quotaLimit` ключа
- Переконайтеся, що `quotaWindow` налаштовано правильно
- Перевірте наявність записів `quotaSnapshots` — вони мають створюватися для кожного запиту
