## Короткий довідник

**Вперше користуєтеся OmniRoute?** Почніть звідси — ці рішення усувають 90% проблем:

| Що я бачу                              | Що це означає                                    | Що робити                                                                                                                   |
| -------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| «Не вдається підключитися»             | OmniRoute не запущено                            | Виконайте `omniroute` або `docker restart omniroute`                                                                        |
| «Недійсний ключ API»                   | Ваш ключ неправильний або термін його дії минув  | Повторно скопіюйте ключ із вебсайту провайдера                                                                              |
| «Перевищено обмеження частоти запитів» | Ви надсилаєте забагато запитів                   | Зачекайте 1 хвилину або використовуйте `model: "auto"` для автоматичного перемикання                                        |
| «Перевищено квоту»                     | Ви вичерпали безкоштовну або платну квоту        | Підключіть більше провайдерів або використовуйте безкоштовних провайдерів (Kiro, Pollinations)                              |
| «Повільні відповіді»                   | Провайдер перевантажений або розташований далеко | Використовуйте `model: "auto/fast"` або підключіть швидшого провайдера (Groq, Cerebras)                                     |
| «Використано не того провайдера»       | `auto` вибрав іншого провайдера                  | Це нормально! `auto` вибирає найкращого. Щоб примусово використовувати певного провайдера, укажіть `model: "openai/gpt-4o"` |
| «502 Bad Gateway»                      | Провайдер недоступний                            | Зачекайте й повторіть спробу або використовуйте `model: "auto"` для перемикання між провайдерами                            |
| «401 Unauthorized»                     | Ваші облікові дані неправильні                   | Перевірте ключ API або повторно автентифікуйтеся через OAuth                                                                |
| «omniroute не розпізнано»              | У Windows PATH відсутні глобальні модулі node    | Додайте глобальний префікс npm до Windows PATH. Знайдіть його за допомогою `npm config get prefix`.                         |
| «429 Too Many Requests»                | Застосовано обмеження частоти запитів            | Зачекайте 1 хвилину або підключіть більше провайдерів                                                                       |

## Детальне усунення несправностей

---

### Обмеження частоти запитів у безкоштовних провайдерів (429 / 400 / 401)

**Ознака**: під час використання `model: "auto"` з безкоштовними провайдерами або провайдерами без автентифікації (opencode, auggie тощо) ви час від часу отримуєте `HTTP 429`, `400` або `401` замість відповідей. Якщо повторити той самий запит через кілька секунд, він виконується успішно, але автоматизація (завдання cron, агенти, скрипти) припиняє роботу після першої помилки.

**Основна причина**: одночасно виникають три незалежні режими відмови:

1. **Обмеження частоти запитів провайдером (`429`)**: безкоштовні рівні обслуговування можуть застосовувати квоту на певний часовий інтервал. Сплеск паралельних викликів вичерпує її, тому наступний запит відхиляється, доки інтервал не буде скинуто.
2. **Несправна модель у наскрізному режимі (`400`/`401`)**: пули `auto/*` можуть містити наскрізні моделі від `opencode`, які зареєстровані в каталозі, але не мають активних облікових даних (наприклад, `oc/north-mini-code-free` → `401`). Автоматичний маршрутизатор намагається використати одну з них, зазнає невдачі, і помилка поширюється раніше, ніж активується резервне перемикання.
3. **Посилення через конкурентність (`429` під навантаженням)**: коли кілька сеансів агентів або cron одночасно звертаються до `auto`, сукупна частота запитів перевищує рівень, який здатні витримати безкоштовні провайдери, тому коректні виклики позначаються як зловживання.

**Перевірене рішення (за повідомленням спільноти, 2026-08-10)**: налаштуйте три змінні середовища, щоб ротація, обмеження конкурентності та резервне перемикання компенсували нестабільність безкоштовного рівня замість завершення з помилкою:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # перейти до іншої моделі або провайдера після 400/401 (пропускає несправні наскрізні моделі)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # явна верхня межа допуску ресурсомістких запитів (типово не задано: кількість запитів не обмежено, див. примітку нижче)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=20000 # збільшити обмежений час очікування понад типове значення RATE_LIMIT_MAX_WAIT_MS для повільних висхідних служб
```

Установіть ці змінні в середовищі процесу OmniRoute (демона, наприклад через plist LaunchAgent або `systemctl edit`), а потім перезапустіть OmniRoute. Прапорець ротації дає найбільший ефект: він перетворює критичну помилку на непомітну повторну спробу через працездатного провайдера з пулу.

**Примітка**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` обмежує кількість ресурсомістких запитів із довгим контекстом, що виконуються одночасно; це обмеження є шлюзом допуску, а не обмежувачем частоти запитів провайдера. **Оновлення щодо розгалуження #503:** ця змінна більше не встановлюється типово (тепер вона діє лише тоді, коли її налаштовано явно, як вище) — натомість допуск ресурсомістких запитів контролюється автоматично визначеним бюджетом байтів (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), який масштабується відповідно до фактичного обмеження пам’яті хоста. Тому в новому розгортанні має виникати значно менше відхилень `503 chat_admission_busy` навіть без установлення цієї змінної; її явне встановлення тут і надалі працює саме так, як описано. Явно задані перевизначення бюджету байтів обмежуються діапазоном від 8 MiB до 2 GiB. Помилка `413 body_exceeds_budget` не є тимчасовою: збільште цей бюджет байтів, зменште `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` або збільште обмеження пам’яті процесу. Скидання навантаження `inflight_bytes_budget` є тимчасовою конкуренцією за ресурси, тому повторна спроба залишається можливою. Обмеження частоти запитів для кожного провайдера (`open-sse/services/rateLimitManager.ts`) окремо керується параметрами `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` і `RATE_LIMIT_AUTO_ENABLE` — див. `.env.example`.

**Як перевірити, що це спрацювало**: запустіть свій агент/cron двічі поспіль із коротким інтервалом і переконайтеся, що обидва запуски завершилися успішно. До виправлення другий запуск зазвичай повертав помилку `429`/`401`. Після виправлення повторні спроби в разі помилок (якщо вони виникають) виконуються прозоро, і виклик завершується успішно. Також можна виконати `curl /monitoring/health` і стежити за полем `rateLimitedUntil` у підключеннях до провайдерів та за `circuitBreakers.providerBreakers[].state` для відповідних провайдерів — стан може бути `CLOSED`, `DEGRADED`, `OPEN` або `HALF_OPEN` (див. `src/shared/utils/circuitBreaker.ts`), а провайдер, у якого помилки продовжують виникати, перейде зі стану `CLOSED → DEGRADED → OPEN`, перш ніж після завершення вікна скидання буде дозволено пробний запит (`HALF_OPEN`).

**Якщо помилка 429 усе ще виникає**: активний обліковий запис цього провайдера справді вичерпав свою _квоту_ (а не лише ліміт частоти запитів). Додайте другий обліковий запис для того самого провайдера в панелі керування OmniRoute → Providers → Accounts або додайте іншого безкоштовного провайдера (наприклад, `routeway`, `auggie`). Ротація допомагає лише з тимчасовими помилками обмеження частоти запитів/400/401; повне вичерпання квоти вимагає інших облікових даних або іншого провайдера.

**Якщо для моделей із підтримкою зображень (`auto/vision`, `bazaarlink/*`) виникає помилка 403**: підключений обліковий запис не має платного тарифного плану, що включає підтримку зображень, або ключ API має недостатні дозволи. Переконайтеся в панелі керування провайдера, що область дії ключа включає роботу із зображеннями/мультимодальними даними, або підключіть обліковий запис із платним тарифом і залиште його цільовим для запитів із зображеннями.

## Попередження npm install (ERESOLVE / peer / deprecated)

Під час виконання `npm install -g omniroute` ви можете побачити безліч попереджень, як-от `npm warn ERESOLVE`, сповіщення про peer-залежності та повідомлення `deprecated`. **Це очікувано й нешкідливо.** Встановлення завершилося успішно, якщо у виводі є `added <N> packages`.

Щоб приховати попередження про вирішення peer-залежностей, використовуйте підтримувану форму встановлення OmniRoute:

```bash
npm install -g omniroute --legacy-peer-deps
```

`--legacy-peer-deps` приховує лише `ERESOLVE` і сповіщення про peer-залежності. Сповіщення про застарілі компоненти залишаються видимими, оскільки вони надходять від транзитивних сторонніх пакетів; вони не свідчать про невдале встановлення.

Попередження спричинені застарілими діапазонами peer-залежностей у сторонніх пакетах, які OmniRoute не контролює:

1. **`marked-terminal` вимагає `marked >=1 <16`, але знайдено `marked@18`** — на практиці працює нормально; діапазон peer-залежності у вихідному пакеті просто застарів.
2. **`deprecated prebuild-install@7.1.3`** — транзитивний допоміжний компонент для отримання нативних бінарних файлів. Він не
   використовується для встановлення прив’язки транспорту `wreq-js` із зафіксованою версією та не свідчить про те, що
   налаштування транспорту провайдера вебфайлів cookie завершилося невдало.

**Жодних дій не потрібно** — ці попередження неможливо повністю приховати без створення форків вихідних пакетів.

## Попередження про заблоковані npm install-скрипти (глобальне встановлення)

<a name="npm-install-scripts-blocked-warning-global-install"></a>

Під час виконання `npm install -g omniroute` новіші версії npm (v11+ і v12+) за замовчуванням блокують скрипти життєвого циклу пакетів і показують попередження про install-скрипти:

```
npm warn install-scripts 7 packages had install scripts blocked because they are not covered by allowScripts:
  omniroute@<version> (postinstall: node scripts/build/postinstall.mjs)
  keytar, @parcel/watcher, @swc/core, protobufjs, esbuild, onnxruntime-node
```

### Чи можна ігнорувати це попередження?

**Частково, але запуск без скриптів не рекомендований.** OmniRoute передбачає надійні резервні механізми: якщо нативні прив’язки `better-sqlite3` не вдається завантажити з автономного пакета, застосунок переходить на альтернативні драйвери, як-от `node:sqlite` або `sql.js` (див. [Визначення середовища виконання SQLite](../ops/SQLITE_RUNTIME.md)). Сервер усе одно запуститься, але використання резервних реалізацій WASM, як-от `sql.js`, вимикає режим WAL (Write-Ahead Logging) SQLite та збільшує використання пам’яті й накладні витрати на синхронізацію з диском.

### Які скрипти насправді потрібні?

Не всі заблоковані скрипти є обов’язковими для роботи OmniRoute:

- **Обов’язкові (`omniroute`, `better-sqlite3`):** OmniRoute працює з автономного пакета застосунку Next.js (`dist/`). Під час встановлення npm завантажує або компілює нативний драйвер SQLite для конкретної хост-системи у верхньорівневому каталозі `node_modules/better-sqlite3/`. Потім скрипт `postinstall` OmniRoute (`scripts/build/postinstall.mjs`) перевіряє та копіює ці бінарні файли для конкретної хост-системи до `dist/node_modules/`, щоб автономний сервер міг отримати до них доступ. Якщо скрипт postinstall пакета `omniroute` заблоковано, цей етап копіювання буде пропущено.
- **Необов’язкові/транзитивні (`keytar`, `@parcel/watcher`, `@swc/core`, `protobufjs`, `esbuild`):** Це допоміжні засоби збирання, інструменти спостереження за змінами або утиліти системного сховища ключів. Їх дозвіл усуває попередження під час збирання, але вони не потрібні для основної функціональності маршрутизації.
- **Виключено (`onnxruntime-node`):** Необов’язкова залежність для локальних ШІ-вбудовувань, яка **не потрібна** для роботи OmniRoute. Її скрипт postinstall завантажує з NuGet приблизно 300 МБ ресурсів CUDA; не додавайте її до списку дозволених, якщо ви явно не плануєте використовувати локальне прискорення ONNX на підтримуваному обладнанні.

### Рекомендоване виправлення

Щоб дозволити необхідні install-скрипти під час глобального встановлення та приховати попередження, передайте `--allow-scripts` для OmniRoute і його нативних залежностей:

```bash
npm install -g omniroute --allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild
```

Або, щоб налаштувати це постійно для всіх глобальних встановлень у вашому обліковому записі користувача:

```bash
npm config set allow-scripts=omniroute,better-sqlite3,keytar,@parcel/watcher,@swc/core,protobufjs,esbuild --location=user
npm install -g omniroute
```

### Перевірте встановлення

Після встановлення запустіть вбудований засіб діагностики, щоб переконатися, що нативні прив’язки та середовище виконання працюють належним чином:

```bash
omniroute doctor
```

## Gemini Web і Playwright Chromium

Якщо запит Gemini Web повертає `503` з повідомленням, що Playwright Chromium
не встановлено, це означає, що пакет npm наявний, але бінарний файл браузера відсутній.
Playwright навмисно завантажує браузери окремо від установлення пакета npm,
тому така відповідь є очікуваною, доки браузер не буде встановлено.

Для глобального встановлення npm установіть Chromium із каталогу пакета OmniRoute,
щоб кеш браузера належав тій самій інсталяції Playwright:

```bash
cd "$(npm root -g)/omniroute"
npx playwright install chromium
```

Після встановлення перезапустіть OmniRoute, а потім повторіть запит Gemini Web. Якщо ви
запускаєте OmniRoute з образу Docker, використовуйте образ `-web` (або ціль збирання
`runner-web`), який містить Chromium і його залежності; базовий образ їх
не містить.

## Хибні спрацювання антивірусу

<a name="antivirus-false-positives"></a>

### Avast/AVG поміщає `README.md` у карантин із позначкою `MD:HttpRequest-inf[Susp]`

**Це хибне спрацювання. Нічого не заражено, і жодних дій не потрібно.**

Avast і AVG використовують евристичний алгоритм, який позначає прості текстові файли та файли Markdown, що містять багато посилань, схожих на HTTP-запити. `README.md` OmniRoute постачається всередині пакета npm (його вказано в `package.json` → `files`), тому під час глобального встановлення він потрапляє до `node_modules/omniroute/README.md` — і містить близько 15 прикладів `http://localhost:20128/...` (кінцеві точки HTTP/SSE MCP, URL-адресу `.well-known` A2A та фрагменти з `curl`). Такої щільності посилань достатньо, щоб спрацював евристичний алгоритм.

Якщо це почалося лише нещодавно: характер файлу не змінився. У README було розширено таблицю кінцевих точок (додано MCP HTTP + SSE + A2A) і додано більше прикладів із `curl`, через що було перевищено порогове значення.

Цей файл є неактивною документацією без жодного виконуваного вмісту. Ви можете безпечно відновити його з карантину.

**Що робити:**

1. **Припиніть сповіщення** — додайте каталог встановлення до винятків антивірусу (Avast: Налаштування → Винятки), указавши шлях до глобального каталогу `node_modules` та/або каталогу даних OmniRoute (`~/.omniroute/`).
2. **Повідомте про хибне спрацювання** — <https://www.avast.com/false-positive-file-form.php>, прикріпивши поміщений у карантин файл `README.md`. Це виправлення допоможе всім, оскільки проблема полягає в тому, що евристичний алгоритм постачальника надмірно реагує на текстовий файл.

**Чому ми не «виправляємо» це зі свого боку:** усі приклади використовують `http://localhost`, а для localhost неможливо використовувати `https` без ускладнень із самопідписаними сертифікатами. Спотворення документації заради обходу евристичного алгоритму одного постачальника зашкодило б усім читачам лише для того, щоб задовольнити сканер із помилкою.

### Kaspersky позначає програму для настільних комп’ютерів як `PDM:Trojan.Win32.Generic`

**Це хибне спрацювання поведінкового евристичного алгоритму. Нічого не заражено.** Префікс `PDM:` у Kaspersky означає, що вердикт винесено модулем проактивного захисту (System Watcher), який оцінює те, що _робить_ інсталятор, а не порівнює його з відомим шкідливим програмним забезпеченням. Після спрацювання Kaspersky «відкочує» все встановлення — видаляючи файли, які вже було записано, — тому програма в результаті виявляється пошкодженою або відсутньою.

Файли, які він позначає, є стандартними частинами задекларованих залежностей із відкритим вихідним кодом, що постачаються разом із програмою для настільних комп’ютерів, наприклад:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` і
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), бібліотека автоматизації браузера, яка використовується для входу до постачальників із програми та чату на основі браузера.
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — зафіксована нативна прив’язка `wreq-js`, що використовується для HTTP із відбитком браузера у постачальників, які використовують вебфайли cookie (`<arch>` — це `x64` або `arm64`).

**Чому він спрацьовує:** інсталятор Windows **ще не має цифрового підпису**, тому непідписаний інсталятор NSIS має нульову репутацію, а поведінкові евристичні алгоритми працюють із максимальною агресивністю. У поєднанні з нативною DLL у комплекті та сотнями файлів `.js`, записаних у `%LOCALAPPDATA%\Programs\OmniRoute` (включно з каталогами пакетів із суфіксами-хешами зі самодостатньої збірки Next.js), цього достатньо, щоб спрацював евристичний алгоритм. Додавання цифрового підпису заплановано; доки це не буде реалізовано, проблема може повторюватися з новими випусками.

**Що робити:**

1. **Спочатку перевірте завантажений файл** (це дає змогу виключити підміну файлу). Для кожного випуску публікується `latest.yml`, поле `sha512` якого (у форматі base64) відповідає інсталятору `OmniRoute.Setup.<version>.exe`. У PowerShell із каталогу, що містить інсталятор, виконайте:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Результат має збігатися з `latest.yml` → `sha512`. Якщо він не збігається, видаліть файл і повторно завантажте його лише зі [сторінки випусків GitHub](https://github.com/diegosouzapw/OmniRoute/releases).
2. **Відновіть і додайте до винятків** — відновіть відкочені елементи з карантину та додайте виняток для `%LOCALAPPDATA%\Programs\OmniRoute` (Kaspersky → Налаштування → Загрози та винятки), а потім перевстановіть програму.
3. **Повідомте про хибне спрацювання** — <https://opentip.kaspersky.com/>. Надіслані користувачами повідомлення про хибні спрацювання справді пришвидшують додавання до списку дозволених програм.

## Сумісність із Node.js

<a name="nodejs-compatibility"></a>

### Сторінка входу аварійно завершує роботу або показує помилку "Module self-registration"

**Причина:** Ви використовуєте версію Node.js, яка не відповідає затвердженим OmniRoute вимогам до безпечного середовища виконання. Найпоширеніший випадок — використання старішої версії виправлень Node 22 або 24, яка не досягає мінімального рівня з виправленнями безпеки, необхідного для OmniRoute.

**Симптоми:**

- Сторінка входу показує порожній екран або помилку сервера
- У консолі відображається `Error: Module did not self-register` або подібні помилки нативних прив’язок
- На сторінці входу відображається **помаранчевий банер-попередження** з вашою версією Node, якщо середовище виконання не відповідає підтримуваній політиці безпеки

**Виправлення:**

1. Установіть підтримуваний випуск Node.js LTS (рекомендовано: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. Перевірте свою версію: `node --version` має показувати `v24.0.0` або новішу версію в гілці 24.x LTS
3. Повторно встановіть OmniRoute: `npm install -g omniroute`
4. Перезапустіть: `omniroute`

> **Підтримувані безпечні версії:** `>=22.22.2 <23` або `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) і Node.js 26 повністю підтримуються.

### npm v11+: `better-sqlite3` не встановлено (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**Причина:** npm v11 (постачається з Node.js 24+) за замовчуванням блокує сценарії встановлення для необов’язкових
залежностей. Оскільки `better-sqlite3` зазначено в `optionalDependencies`
і він потребує нативної компіляції (`node-gyp rebuild`), npm непомітно пропускає його.

**Симптоми:**

- Сервер аварійно завершує роботу під час запуску з повідомленням `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` показує "No such file or directory"
- `npm ls better-sqlite3` показує `(empty)`

**Виправлення:**

1. Схваліть сценарії встановлення та виконайте повторне встановлення:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. Або встановіть попередньо зібраний пакет вручну:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. Перевірте, чи все працює: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**Причина:** Після глобального виконання `npm install -g omniroute` нативний двійковий файл `better-sqlite3` усередині пакета міг бути скомпільований для архітектури або ABI Node.js, що відрізняються від локально використовуваних. Це часто трапляється в macOS (як на Apple Silicon, так і на Intel), коли попередньо зібраний двійковий файл не відповідає вашому середовищу.

**Симптоми:**

- Сервер одразу завершує роботу під час запуску з помилкою `dlopen`
- Помилка містить `slice is not valid mach-o file`
- Повний приклад:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**Виправлення — перебудуйте для свого локального середовища (зниження версії Node.js не потрібне):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **Примітка:** Це повторно компілює нативну прив’язку для вашої локальної версії Node.js і архітектури процесора, усуваючи невідповідність двійкових файлів. Офіційно підтримуваний діапазон середовища виконання: **`>=22.22.2 <23` або `>=24.0.0 <27`** (`SUPPORTED_NODE_RANGE` у `src/shared/utils/nodeRuntimeSupport.ts`, узгоджено з полем `engines` у `package.json`). Node.js 24.x LTS (Krypton) і Node.js 26 повністю підтримуються з `better-sqlite3` v12.x.

## Проблеми з проксі

<a name="proxy-issues"></a>

### Перевірка провайдера показує "fetch failed"

**Причина:** Кінцева точка перевірки ключа API (`POST /api/providers/validate`) раніше обходила конфігурацію проксі, що спричиняло помилки в середовищах, де потрібна маршрутизація через проксі.

**Виправлення (v3.5.5+):** Тепер це виправлено. Перевірка провайдера виконується через `runWithProxyContext` з автоматичним урахуванням налаштувань проксі на рівні провайдера та глобальних налаштувань проксі.

### Перевірка стану токена завершується помилкою "fetch failed"

**Причина:** Фонове оновлення токена OAuth не визначало конфігурацію проксі окремо для кожного підключення.

**Виправлення (v3.5.5+):** Планувальник перевірки стану токенів тепер визначає конфігурацію проксі для кожного підключення перед спробою оновлення. Оновіться до v3.5.5+.

### Проксі SOCKS5 повертає "invalid onRequestStart method"

**Причина:** У Node.js 22 диспетчер undici@8 несумісний із вбудованою реалізацією `fetch()` у Node.

**Виправлення (v3.5.5+):** Тепер OmniRoute використовує власну функцію `fetch()` з undici, коли активний диспетчер проксі, що забезпечує узгоджену поведінку. Оновіться до v3.5.5+.

### Проксі MITM у WSL: перехоплення настільних застосунків на хості Windows не працює

**Причина:** Проксі MITM і його сертифікат CA установлюються в середовищі, де працює OmniRoute. У WSL цим середовищем є гостьова система Linux, тоді як настільні застосунки зі ШІ (Kiro, Trae, Copilot, Zed, …) працюють на хості Windows. Застосунки хоста не довіряють сховищу сертифікатів гостьової системи й не використовують її системний проксі, тому перехоплення настільних застосунків у такій конфігурації не працює.

**Рекомендація:** Запускайте OmniRoute безпосередньо в тій самій ОС, що й настільні застосунки, трафік яких потрібно перехоплювати (Windows для застосунків Windows; аналогічно для macOS/Linux). Якщо OmniRoute залишається всередині WSL, а цільові застосунки працюють на хості, потрібно вручну додати згенерований сертифікат CA до довірених на хості Windows і спрямувати налаштування мережі/проксі кожного застосунку хоста на кінцеву точку проксі WSL — це непідтримувана й ненадійна конфігурація.

## Проблеми з провайдерами

### "Language model did not provide messages"

**Причина:** Квоту провайдера вичерпано.

**Виправлення:**

1. Перевірте індикатор квоти на панелі керування
2. Використовуйте комбінацію з резервними рівнями
3. Перейдіть на дешевший/безкоштовний рівень

### Обмеження частоти запитів

**Причина:** Квоту підписки вичерпано.

**Виправлення:**

- Додайте резервний ланцюжок: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- Використовуйте GLM/MiniMax як дешевий резервний варіант

### Термін дії токена OAuth минув

OmniRoute автоматично оновлює токени. Якщо проблеми не зникають:

1. Панель керування → Провайдер → Повторно підключити
2. Видаліть і повторно додайте підключення провайдера

### Кілька облікових записів Kiro: другий обліковий запис робить перший недійсним

**Причина:** Серверна частина Kiro дозволяє лише один активний сеанс для кожної реєстрації клієнта OIDC.
Коли два облікові записи використовують спільний зареєстрований клієнт (підключення, імпортовані до v3.8.0),
оновлення токена одного облікового запису робить токен оновлення іншого недійсним.

**Виправлення (v3.8.0+):** Повторно імпортуйте проблемні підключення.
Починаючи з v3.8.0, для кожного нового підключення Kiro, створеного через **Імпорт токена**,
**вхід через Google/GitHub** або **Автоматичний імпорт**, автоматично реєструється власний
виділений клієнт OIDC. Тому підключення є повністю ізольованим, і оновлення одного
облікового запису не впливає на жоден інший обліковий запис.

Підключення, імпортовані _до_ v3.8.0, не мають окремої реєстрації клієнта
для кожного підключення. Ці підключення й надалі використовують спільну кінцеву точку оновлення соціальної автентифікації.
Щоб забезпечити ізоляцію, видаліть старе підключення в розділі Панель керування → Провайдери й повторно додайте його
за допомогою будь-якого з трьох способів імпорту.

Повну інформацію та покрокові інструкції з одночасного додавання двох облікових записів Kiro
див. у файлі [`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md).

## Проблеми з хмарою

### Помилки хмарної синхронізації

1. Переконайтеся, що `BASE_URL` указує на запущений екземпляр (наприклад, `http://localhost:20128`)
2. Переконайтеся, що `CLOUD_URL` указує на вашу хмарну кінцеву точку (наприклад, `https://omniroute.dev`)
3. Підтримуйте значення `NEXT_PUBLIC_*` узгодженими зі значеннями на стороні сервера

### Хмарний запит із `stream=false` повертає 500

**Ознака:** `Unexpected token 'd'...` на хмарній кінцевій точці для непотокових викликів.

**Причина:** Висхідний сервер повертає корисне навантаження SSE, тоді як клієнт очікує JSON.

**Обхідне рішення:** Використовуйте `stream=true` для прямих хмарних викликів. Локальне середовище виконання містить резервне перетворення SSE→JSON.

### Хмара повідомляє про підключення, але повертає «Invalid API key»

1. Створіть новий ключ у локальній панелі керування (`/api/keys`)
2. Запустіть хмарну синхронізацію: Увімкнути хмару → Синхронізувати зараз
3. Старі або несинхронізовані ключі все ще можуть повертати `401` у хмарі

## Проблеми з Docker

### Docker IPv6 / скидання з’єднання

<a name="docker-ipv6"></a>

**Ознаки:** `curl http://localhost:20128/v1/models` повертає `curl: (56) Recv failure: Connection reset by peer`. Панель керування та кінцеві точки без автентифікації працюють, але автентифіковані кінцеві точки завершуються помилкою — це схоже на проблему з автентифікацією, але насправді нею не є.

**Причина:** `docker run -p 20128:20128` публікує порт як на `0.0.0.0` (IPv4), так і на `::` (IPv6), але процес усередині контейнера прослуховує лише IPv4. На хостах, де `localhost` спочатку перетворюється на `::1`, з’єднання надходить на опублікований порт IPv6, за яким немає слухача → з’єднання скидається.

**Виправлення:**

1. **Швидка діагностика:** Виконайте `curl -4 http://localhost:20128/v1/models`. Якщо команда працює з `-4`, але не працює без нього, у вас є невідповідність прив’язки IPv6.
2. **Постійне виправлення:** Явно прив’яжіть порт до IPv4, використавши `-p 127.0.0.1:20128:20128` у команді `docker run`:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   Це примусово встановлює прив’язку до IPv4, а також запобігає доступу до проксі через усі інтерфейси хоста.

### Інструмент CLI відображається як невстановлений

1. Перевірте поля середовища виконання: `curl http://localhost:20128/api/cli-tools/runtime/codex | jq`

## Налагодження

### Увімкнення файлів журналу

Установіть `APP_LOG_TO_FILE=true` у файлі `.env`. Журнали застосунку записуються в каталог `logs/`.
Артефакти запитів зберігаються в `${DATA_DIR}/call_logs/`, коли в налаштуваннях
увімкнено конвеєр журналювання викликів.
Коли захоплення даних конвеєром увімкнено, установіть `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false`, щоб не зберігати
корисне навантаження потокових фрагментів, або налаштуйте `CALL_LOG_PIPELINE_MAX_SIZE_KB`, щоб змінити обмеження розміру артефактів у КБ.

### Перевірка стану постачальника

```bash
# Панель моніторингу стану
http://localhost:20128/dashboard/health

# Перевірка стану API
curl http://localhost:20128/api/monitoring/health
```

### Сховище середовища виконання

- Основний стан: `${DATA_DIR}/storage.sqlite` (постачальники, комбінації, псевдоніми, ключі, налаштування)
- Використання: таблиці SQLite у `storage.sqlite` (`usage_history`, `call_logs`, `proxy_logs`) + необов’язковий каталог `${DATA_DIR}/call_logs/`
- Журнали застосунку: `<repo>/logs/...` (коли `APP_LOG_TO_FILE=true`)
- Артефакти журналу викликів: `${DATA_DIR}/call_logs/YYYY-MM-DD/...`, коли конвеєр журналювання викликів увімкнено

Дія **Очистити історію** на сторінці журналів запитів очищає `call_logs`, застарілий
`request_detail_logs` і локальний каталог артефактів `${DATA_DIR}/call_logs/`.

## Проблеми із запобіжником

### Провайдер застряг у стані OPEN

Коли запобіжник провайдера перебуває у стані OPEN, запити блокуються до завершення періоду очікування.

**Виправлення:**

1. Перейдіть до **Панель керування → Налаштування → Відмовостійкість**
2. Перевірте картку запобіжника відповідного провайдера
3. Натисніть **Скинути все**, щоб скинути всі запобіжники, або дочекайтеся завершення періоду очікування
4. Перед скиданням переконайтеся, що провайдер справді доступний

### Провайдер постійно активує запобіжник

Якщо провайдер неодноразово переходить у стан OPEN:

1. Перевірте характер збоїв у розділі **Панель керування → Стан → Стан провайдерів**
2. Перейдіть до **Налаштування → Відмовостійкість → Профілі провайдерів** і збільште поріг збоїв
3. Перевірте, чи провайдер не змінив обмеження API або чи не потребує повторної автентифікації
4. Перегляньте телеметрію затримок — висока затримка може спричиняти збої через перевищення часу очікування

- Перевірте чинність ключа API провайдера в його картці

### Поширені проблеми з форматами

- **Теги міркування не відображаються** — перевірте, чи підтримує цільовий провайдер міркування, а також налаштування бюджету міркування
- **Виклики інструментів зникають** — деякі перетворення форматів можуть видаляти непідтримувані поля; перевірте це в режимі «Майданчик»
- **Системний запит відсутній** — Claude і Gemini по-різному обробляють системні запити; перевірте результат перетворення
- **SDK повертає необроблений рядок замість об’єкта** — вирішено у v1.x; засіб очищення відповідей видаляє нестандартні поля (`x_groq`, `usage_breakdown` тощо), які спричиняють помилки перевірки Pydantic у OpenAI SDK. Якщо ви все ще спостерігаєте це у v3.x+, повідомте про проблему.
- **GLM/ERNIE відхиляє роль `system`** — вирішено у v1.x; нормалізатор ролей автоматично об’єднує системні повідомлення з повідомленнями користувача для несумісних моделей. Якщо ви все ще спостерігаєте це у v3.x+, повідомте про проблему.
- **Роль `developer` не розпізнається** — вирішено у v1.x; автоматично перетворюється на `system` для провайдерів, відмінних від OpenAI. Якщо ви все ще спостерігаєте це у v3.x+, повідомте про проблему.
- **`json_schema` не працює з Gemini** — вирішено у v1.x; `response_format` тепер перетворюється на `responseMimeType` + `responseSchema` Gemini. Якщо ви все ще спостерігаєте це у v3.x+, повідомте про проблему.

## Налаштування стійкості

### Автоматичне обмеження частоти запитів не спрацьовує

- Автоматичне обмеження частоти запитів застосовується лише до постачальників із ключами API (не до OAuth/підписок)
- Переконайтеся, що в **Налаштування → Стійкість → Профілі постачальників** увімкнено автоматичне обмеження частоти запитів
- Перевірте, чи повертає постачальник коди стану `429` або заголовки `Retry-After`

### Налаштування експоненційної затримки

Профілі постачальників підтримують такі налаштування:

- **Базова затримка** — Початковий час очікування після першої помилки (за замовчуванням: 1s)
- **Максимальна затримка** — Максимальне обмеження часу очікування (за замовчуванням: 30s)
- **Множник** — Наскільки збільшувати затримку з кожною послідовною помилкою (за замовчуванням: 2x)

### Запобігання ефекту «гурту, що налітає»

Коли багато паралельних запитів надходять до постачальника з обмеженою частотою запитів, OmniRoute використовує м'ютекс + автоматичне обмеження частоти, щоб серіалізувати запити та запобігти каскадним збоям. Для постачальників із ключами API це відбувається автоматично.

### Запити чату завершуються помилкою 503 / chat_admission_busy

**Симптоми:**

- Кінцева точка завершень чату повертає придатну для повторної спроби відповідь `503` із кодом помилки
  `chat_admission_busy`.
- Відповідь містить `Retry-After`. Починаючи з #12135, значення визначається на основі спостережуваної
  зайнятості — береться більше з вікна `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`, протягом якого запит уже
  очікував, і часу, протягом якого утримувалися поточні великовагові оренди, — з округленням угору до цілих
  секунд і обмеженням у 60. Коли шлюз не зайнятий, зберігаються історичні мінімальні значення: 2 секунди для
  шляху на основі байтів і 1 секунда для шляху на основі структури (який також містить
  `reason: "structure_limit"`).
- Це може статися, поки інший великоваговий запит чату або довготривала потокова відповідь усе ще
  виконується.

Тіло відповіді на основі байтів:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Відповідь на основі структури використовує той самий тип і код, із повідомленням
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
і `reason: "structure_limit"`.
За порогових значень за замовчуванням запит вважається структурно великоваговим, якщо він містить щонайменше `200` повідомлень,
щонайменше `64` інструменти або щонайменше `32,000` оцінених токенів, чи якщо обмежене оцінювання структури
вичерпує свої межі в `10,000` відвіданих вузлів або глибину `12`.

**Причина:** Це навмисне скидання навантаження всередині OmniRoute, а не збій зовнішнього постачальника.
Кожен процес використовує локальний для процесу запобіжник, щоб зарезервувати обмежену пропускну здатність для великовагових запитів, перш ніж зберігати
й аналізувати велике тіло запиту. Великовагова оренда утримується протягом усього часу існування відповіді SSE.

**#503-розгалуження:** до цього виправлення запобіжник обмежував паралельність фіксованою КІЛЬКІСТЮ запитів
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, за замовчуванням `1`) незалежно від пам'яті хоста, тому розгалуження
агентів програмування (кілька субагентів/CLI, тіла зазвичай > 256 KB) знижувало ефективну
паралельність приблизно до 1 і спричиняло помилки 503 за цілком нормального навантаження. Тепер запобіжник самоналаштовується: він керується
автоматично визначеним БАЙТОВИМ бюджетом приймання (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`), розрахованим на основі
реального обмеження пам'яті процесу, а також враховує оперативний сигнал навантаження на ресурси — тому
він скидає навантаження лише тоді, коли хост справді зазнає дефіциту пам'яті, а не просто через те, що одночасно
надійшло більше одного великовагового запиту. Старе обмеження кількості (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
усе ще враховується, але лише якщо ви явно його встановите.

Коли пропускна здатність зайнята, великоваговий запит спочатку очікує до
`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (за замовчуванням `RATE_LIMIT_MAX_WAIT_MS`; `0` вимикає очікування), доки не звільниться місце,
і лише потім повертає придатну для повторної спроби відповідь `503`. Обмежене очікування потрібне, щоб клієнти агентного типу
(OpenCode, Claude Code, Cursor), які паралельно розгалужують великовагові підзапити, серіалізували сплеск,
а не витрачали весь свій бюджет повторних спроб на негайні відхилення та не завершували роботу посеред завдання.
Поточна зайнятість великовагових оренд, визначений байтовий бюджет і поточний рівень навантаження
відображаються в `GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) — перевірте їх, перш ніж змінювати будь-яку змінну середовища.
Налаштування → Стійкість → Черга запитів → Паралельні запити не керує цим; цей параметр
керує окремим механізмом черги запитів постачальника.

**Виправлення:**

1. Спочатку повторіть спробу. Клієнти мають враховувати `Retry-After` і використовувати затримку замість негайного
   повторення запиту.
2. Перевірте `/api/monitoring/health` → `chatAdmission`, перш ніж щось налаштовувати. `countCapEnabled:
false` і достатній `maxInflightBytes` означають, що автоматично визначений бюджет уже належним чином виконує свою
   функцію; значення `pressureSeverity` `high`/`critical` означає, що хост справді має мало пам'яті —
   це неможливо виправити змінною середовища керування допуском, потрібен більший обсяг RAM або менше навантаження.
3. Лише якщо `/api/monitoring/health` показує, що автоматично визначений бюджет справді замалий для
   вашого хоста (що трапляється рідко — він уже масштабується від контейнерів до фізичних серверів), перевизначте його безпосередньо за допомогою
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`, а не повертайтеся до застарілого обмеження кількості запитів.

Авторитетний перелік налаштувань допуску наведено в [довіднику змінних середовища](../reference/ENVIRONMENT.md#4-security--authentication).

## Необов’язкова таксономія збоїв RAG / LLM (16 проблем)

Деякі користувачі OmniRoute розміщують шлюз перед стеками RAG або агентів. У таких конфігураціях часто спостерігається дивна картина: OmniRoute виглядає справним (провайдери доступні, профілі маршрутизації налаштовані правильно, сповіщень про обмеження частоти запитів немає), але кінцева відповідь усе одно неправильна.

На практиці такі інциденти зазвичай спричинені подальшим конвеєром RAG, а не самим шлюзом.

Якщо вам потрібна спільна термінологія для опису таких збоїв, можна використовувати WFGY ProblemMap — зовнішній текстовий ресурс за ліцензією MIT, у якому визначено шістнадцять типових шаблонів збоїв RAG / LLM. На високому рівні він охоплює:

- відхилення пошуку та порушення меж контексту
- порожні або застарілі індекси й векторні сховища
- невідповідність між вбудовуваннями та семантикою
- проблеми зі складанням промптів і контекстним вікном
- логічні збої та надмірно впевнені відповіді
- збої в довгих ланцюжках і координації агентів
- відхилення пам’яті й ролей у багатоагентних системах
- проблеми з порядком розгортання та початкового завантаження

Ідея проста:

1. Під час розслідування неправильної відповіді зафіксуйте:
   - завдання й запит користувача
   - маршрут або комбінацію провайдерів в OmniRoute
   - будь-який контекст RAG, використаний у подальшому конвеєрі (отримані документи, виклики інструментів тощо)
2. Зіставте інцидент з одним або двома номерами WFGY ProblemMap (`No.1` … `No.16`).
3. Збережіть номер у власній панелі моніторингу, інструкції з реагування або системі відстеження інцидентів поруч із журналами OmniRoute.
4. Скористайтеся відповідною сторінкою WFGY, щоб визначити, чи потрібно змінити стек RAG, механізм пошуку або стратегію маршрутизації.

Повний текст і конкретні рецепти доступні тут (ліцензія MIT, лише текст):

[README WFGY ProblemMap](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

Ви можете пропустити цей розділ, якщо не використовуєте конвеєри RAG або агентів за OmniRoute.

## Відомі проблеми v3.8.0

Проблеми, характерні для випуску v3.8.0, і поточні способи їх обходу. Якщо виправлення з’явиться в наступному патчі, відповідний запис буде оновлено або видалено.

### Помилки автентифікації Devin CLI

**Симптоми:**

- «Devin CLI не знайдено» або «помилка автентифікації» під час виклику інструментів на основі Devin
- Перевірка середовища виконання CLI повідомляє `installed=false`

**Причини:**

- `CLI_DEVIN_BIN` указує на шлях, якого не існує
- Devin CLI не встановлено на хості

**Виправлення:**

1. Установіть Devin CLI для своєї платформи
2. Задайте `CLI_DEVIN_BIN=/usr/local/bin/devin` (або фактичний шлях) у `.env`
3. Перезапустіть OmniRoute і повторіть перевірку через **Панель керування → Інструменти CLI**

### Режим очікування моделі завис (ручне скидання)

**Симптоми:**

- Модель залишається в списку моделей у режимі очікування навіть після завершення терміну дії
- Запити і надалі пропускають модель під час комбінованої маршрутизації, хоча позначка часу вже в минулому

**Ручне скидання:**

- **Панель керування:** **Налаштування → Режими очікування моделей** → натисніть **Повторно ввімкнути** на картці відповідної моделі
- **API:** `DELETE /api/resilience/model-cooldowns` із заголовками автентифікації для керування

### Підключення до провайдера Command Code завершується помилкою 403

**Симптоми:**

- Помилка 403 під час перевірки підключення до провайдера Command Code
- Після нового додавання на картці провайдера відображається «не авторизовано»

**Причина:** Потік OAuth не завершився (зворотний виклик не отримано або токен не збережено).

**Виправлення:**

- Виконайте `omniroute providers` у CLI, щоб повторно запустити потік OAuth, або
- Повторно запустіть OAuth через **Панель керування → Провайдери → Command Code → Повторно підключити**

### ModelScope повертає агресивні режими очікування через помилки 429

**Симптоми:**

- Дуже короткі або негайні режими очікування в ModelScope після невеликої серії запитів
- Комбінована маршрутизація пропускає ModelScope раніше, ніж очікувалося

**Причина:** ModelScope надсилає специфічні для провайдера заголовки `Retry-After`. У v3.8.0 реалізовано спеціальну обробку цих заголовків, тому старіші версії неправильно інтерпретують їх як загальні підказки щодо обмеження частоти запитів.

**Виправлення:**

- Переконайтеся, що використовуєте v3.8.0 або новішу версію
- Переконайтеся, що перемикач `useUpstream429BreakerHints` увімкнено в розділі **Налаштування → Відмовостійкість**

### Відсутня OMNIROUTE_WS_BRIDGE_SECRET у робочому середовищі

**Симптоми:**

- Помилка 401 для кожного запиту до WebSocket-моста Codex/Responses під час роботи на віддаленому робочому хості
- Рукостискання WebSocket-моста завершується відразу після підключення

**Причина:** Змінна середовища `OMNIROUTE_WS_BRIDGE_SECRET` відсутня в робочому середовищі.

**Виправлення:**

1. Згенеруйте випадковий секрет: `openssl rand -hex 32`
2. Задайте `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` у середовищі робочого сервера (і в будь-якому клієнті, що взаємодіє з мостом)
3. Перезапустіть OmniRoute

### Responses API: фоновий режим понижено до синхронного

**Симптоми:**

- У журналі з’являється попередження: `background mode degraded to synchronous`
- Запит із `background: true` повертає звичайну синхронну відповідь замість дескриптора фонового завдання

**Причина:** У v3.8.0 параметр `background: true` у Responses API навмисно переводить виконання в синхронний режим із виведенням попередження. Повноцінне асинхронне фонове виконання заплановано на майбутнє.

**Виправлення:**

- Налаштуйте клієнт так, щоб він здійснював виклик без `background`, або
- Дочекайтеся пізнішого випуску з повноцінним асинхронним фоновим режимом (стежте за журналом змін)

## Повільний запуск / Перевищення часу очікування готовності

Якщо CLI виводить `⚠ Server did not respond within 60s`, але сервер насправді
працює, ліміт часу перевірки готовності замалий для вашого середовища.

Це часто трапляється у Windows (через антивірус, спостерігачі файлової системи) або в контейнерах
зі значним навантаженням під час запуску.

**Виправлення — збільште ліміт часу:**

```bash
# Через змінну середовища (зберігається між запусками):
export OMNIROUTE_READY_TIMEOUT_MS=180000   # 3 хвилини
omniroute serve

# Через прапорець CLI (одноразово):
omniroute serve --ready-timeout 180000
```

Значення за замовчуванням — 60 000 мс (60 с). Попередження має лише інформаційний характер; сервер
продовжує запускатися у фоновому режимі й стане доступним після завершення завантаження.

Повну інформацію про `OMNIROUTE_READY_TIMEOUT_MS` див. у
[`docs/reference/ENVIRONMENT.md`](../reference/ENVIRONMENT.md).
