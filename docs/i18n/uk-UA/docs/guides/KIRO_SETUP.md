Цей посібник описує додавання облікових записів Kiro (розміщеного в AWS ШІ-асистента для програмування) до OmniRoute,
з акцентом на одночасне використання кількох облікових записів без конфліктів сеансів.

---

## Передумови: чому облікові записи Kiro можуть конфліктувати

Серверна частина Kiro використовує реєстрації клієнтів AWS SSO OIDC для відстеження активних сеансів.
Критичне обмеження: **кожна реєстрація клієнта OIDC підтримує лише один активний
сеанс одночасно**. Коли другий пристрій або користувач автентифікується за допомогою того самого
зареєстрованого клієнта, серверна частина анулює токен оновлення першого облікового запису.

Це той самий механізм, який спричиняє проблеми під час виконання `kiro-cli login` на
комп’ютері, де вже виконано вхід в інший обліковий запис Kiro: новий вхід анулює
токен першого облікового запису.

---

## Як OmniRoute розв’язує цю проблему (v3.8.0+)

Починаючи з v3.8.0, OmniRoute викликає `registerClient()` (AWS SSO OIDC) під час кожного
імпорту підключення Kiro. Завдяки цьому кожне підключення OmniRoute отримує власну виділену
реєстрацію клієнта OIDC. Оскільки кожна реєстрація клієнта є незалежною, оновлення або
повторна автентифікація одного облікового запису не впливає на токен оновлення іншого облікового запису.

Ізоляція застосовується до методів імпорту токенів оновлення, а автентифікація за допомогою ключа API
взагалі не використовує сеанси оновлення OIDC:

| Метод імпорту                                          | Стан ізоляції                                                                                                 |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| AWS Builder ID / потік коду пристрою IDC               | Ізольовано від моменту впровадження потоку коду пристрою                                                      |
| **Імпорт токена** (вставлення токена оновлення вручну) | Ізольовано з v3.8.0                                                                                           |
| **Вхід через Google / GitHub**                         | Ізольовано з v3.8.0                                                                                           |
| **Автоімпорт** (SQLite kiro-cli)                       | Ізольовано з v3.8.0 (шлях SQLite уже був ізольований; резервний варіант із кешем SSO тепер також ізольований) |
| **Ключ API** (довгостроковий ключ CodeWhisperer)       | Без сеансу оновлення; ключ перевіряється та зберігається як облікові дані носія                               |

---

## Примітка щодо міграції підключень, створених до v3.8.0

Підключення, імпортовані до v3.8.0, не мають виділеної реєстрації клієнта OIDC,
збереженої в `providerSpecificData`. Ці підключення продовжують працювати, але використовують спільну
кінцеву точку оновлення соціальної автентифікації, а це означає, що два такі підключення все ще можуть анулювати
токени одне одного.

**Щоб отримати ізоляцію:** видаліть старе підключення через **Панель керування → Провайдери** та
повторно імпортуйте його за допомогою будь-якого з підтримуваних способів імпорту. Усі новостворені підключення
автоматично отримуватимуть власну реєстрацію клієнта.

## Додавання двох облікових записів Kiro паралельно

### Передумови

- OmniRoute v3.8.0 або новішої версії.
- Робочий обліковий запис Kiro (електронна пошта + пароль, вхід через Google або GitHub).
- За потреби — другий обліковий запис Kiro.

### Крок 1: імпортуйте перший обліковий запис

1. Відкрийте **Панель керування → Провайдери → Додати провайдера → Kiro**.
2. Виберіть один із варіантів:
   - **Імпорт токена** — вставте токен оновлення, що починається з `aorAAAAAG`.
   - **Ключ API** — вставте довгостроковий ключ API Kiro / CodeWhisperer.
   - **Вхід через Google / GitHub** — завершіть процес OAuth у браузері.
   - **Автоімпорт** — натисніть кнопку; OmniRoute зчитає облікові дані з
     локальної бази даних kiro-cli або `~/.aws/sso/cache`.
3. Підключення буде збережено. Потоки з токенами оновлення автоматично реєструють виділений
   клієнт OIDC. Потоки з ключами API перевіряють ключ за допомогою AWS і не зберігають токен оновлення.

### Крок 2: імпортуйте другий обліковий запис

Повторіть крок 1 для другого облікового запису. Оскільки кожен імпорт створює окрему
реєстрацію клієнта OIDC, обидва підключення є повністю ізольованими.

### Крок 3: переконайтеся, що обидва підключення активні

1. **Панель керування → Провайдери** — обидва підключення Kiro повинні мати стан **Активне**.
2. **Панель керування → Стан системи** — обидва підключення мають успішно пройти перевірку стану токена.

### Крок 4: використовуйте комбінацію для маршрутизації між обліковими записами

Створіть комбінацію з обома підключеннями як цільовими, щоб розподіляти навантаження або перемикатися між ними в разі збою:

```
kiro/kiro-dev → kiro/kiro-pro
```

Відомості про налаштування комбінацій див. у [FEATURES.md](./FEATURES.md) та документації з маршрутизації.

## Корпоративні користувачі / користувачі IDC

Для облікових записів AWS IAM Identity Center (IDC) використовуйте потік **AWS Builder ID / коду пристрою IDC** у розділі **Панель керування → Провайдери → Kiro → Код пристрою**. Потік коду пристрою завжди був повністю ізольованим. Для цих підключень повторний імпорт не потрібен.

Корпоративні користувачі, які працюють у регіоні AWS, відмінному від стандартного, можуть указати регіон під час імпорту через API імпорту токена:

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/import \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "aorAAAAAG...", "region": "eu-west-1"}'
```

Якщо поле `region` не вказано, типовим значенням є `us-east-1`.

## Потік імпорту API-ключа

Автентифікація за допомогою API-ключа призначена для довготривалих облікових даних носія Kiro / AWS CodeWhisperer. Вона не використовує оновлення OAuth, тому дає змогу уникнути недійсності спільного сеансу OIDC.

### Панель керування

1. Відкрийте **Панель керування -> Провайдери -> Kiro**.
2. Виберіть **API-ключ**.
3. Вставте API-ключ і, за потреби, регіон AWS (типово — `us-east-1`).
4. OmniRoute перевірить ключ і збереже підключення.

### API

```bash
curl -X POST http://localhost:20128/api/oauth/kiro/api-key \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "kiro_or_codewhisperer_key", "region": "us-east-1"}'
```

### Внутрішній контракт

Маршрут API перевіряє ключ, викликаючи `KiroService.validateApiKey()`, який використовує `ListAvailableProfiles` із кінцевою точкою CodeWhisperer/Amazon Q, що відповідає регіону, і визначає `profileArn`.

Збережене підключення використовує:

```json
{
  "authType": "apikey",
  "providerSpecificData": {
    "authMethod": "api_key",
    "region": "us-east-1",
    "profileArn": "arn:aws:codewhisperer:..."
  }
}
```

Під час виконання `KiroExecutor.buildHeaders()` надсилає ключ як `Authorization: Bearer <key>` і додає `tokentype: API_KEY`. Виклики квоти/профілю використовують той самий маркер, щоб AWS розглядав облікові дані носія як довготривалий API-ключ, а не як токен доступу OIDC або соціальної мережі.

## Закінчення терміну дії клієнта OIDC

Термін дії публічних клієнтів AWS SSO OIDC зазвичай закінчується через 90 днів (`clientSecretExpiresAt`). OmniRoute зберігає цю часову позначку в `providerSpecificData` для спостережуваності. Якщо підключення перестає оновлюватися приблизно через 90 днів, повторно імпортуйте його, щоб отримати нову реєстрацію клієнта OIDC. Автоматична повторна реєстрація після закінчення терміну дії запланована як майбутнє вдосконалення.

Підключення за допомогою API-ключа не мають терміну дії клієнта OIDC, оскільки вони не оновлюються через AWS SSO OIDC.

## Усунення несправностей

### Другий обліковий запис постійно виходить із системи

- Перевірте обидва підключення в розділі **Панель керування → Провайдери** та переконайтеся, що кожне з них має ненульове значення `clientId` у необробленому JSON (доступному через значок інформації). Якщо в будь-якому підключенні відсутній `clientId`, його було імпортовано до v3.8.0 — повторно імпортуйте його.

### Помилка імпорту "Не вдалося перевірити токен"

- Переконайтеся, що токен оновлення починається з `aorAAAAAG`.
- Переконайтеся, що OmniRoute має доступ до `https://oidc.us-east-1.amazonaws.com` (або налаштованого регіону). Якщо ви працюєте через корпоративний проксі-сервер, налаштуйте проксі-сервер на рівні провайдера в розділі **Панель керування → Налаштування → Проксі-сервери**.

### Не вдається імпортувати API-ключ

- Переконайтеся, що це API-ключ Kiro / CodeWhisperer, а не токен оновлення.
- Переконайтеся, що регіон AWS відповідає ключу/обліковому запису. Типовим є `us-east-1`.
- Ключ повинен мати змогу викликати `ListAvailableProfiles`; інакше OmniRoute не зможе визначити необхідний `profileArn`.

Щодо інших проблем див. основний файл [TROUBLESHOOTING.md](./TROUBLESHOOTING.md).
