Повний посібник із використання Codex CLI з OmniRoute як OpenAI-сумісним бекендом.

---

> **TOML — єдиний дієвий формат.** Сучасний Codex читає виключно
> `~/.codex/config.toml` (перевірено з codex-cli 0.147.0: у `codex --help`
> зазначено, що перевизначення `-c/--config` «завантажуються з
> `~/.codex/config.toml`»). Старий `~/.codex/config.yaml` належав застарілому
> npm CLI й мовчки ігнорується. Генератор на панелі керування
> (`/api/cli-tools/apply`, інструмент `codex`) записує TOML із консервативним
> об’єднанням — наявні ключі та блоки інших провайдерів зберігаються, API-ключ
> залишається в `OMNIROUTE_API_KEY` (і ніколи не потрапляє у файл), а про
> залишковий застарілий `config.yaml` повідомляється в примітці щодо міграції,
> без внесення змін до нього.

## Готовий до вставлення config.toml

Замініть `<YOUR_HOST>` і `<YOUR_KEY>` своїми значеннями:

```toml
# ~/.codex/config.toml
model                          = "cx/gpt-5.5"
model_provider                 = "omniroute"
model_reasoning_effort         = "xhigh"
model_context_window           = 400000
model_auto_compact_token_limit = 350000
tool_output_token_limit        = 32768    # ліміт зберігання в історії для кожного виклику інструмента

[model_providers.omniroute]
name                 = "OmniRoute"
base_url             = "http://<YOUR_HOST>:20128/v1"
env_key              = "OMNIROUTE_API_KEY"
requires_openai_auth = false
wire_api             = "responses"
```

```bash
# ~/.bashrc або ~/.zshrc — фактичне значення ключа, ніколи не зберігайте його в config.toml
export OMNIROUTE_API_KEY="<YOUR_KEY>"
```

### macOS: Codex, вбудований у застосунок ChatGPT

Якщо ви встановили Codex через настільний застосунок ChatGPT, бінарний файл
`codex` може існувати лише всередині пакета застосунку й ще не бути доступним
у `PATH` вашої оболонки. Додайте каталог ресурсів до стартового файла оболонки:

```bash
export PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH"
```

Відкрийте нову оболонку, а потім перевірте:

```bash
command -v codex
codex --version
```

### Локальний OmniRoute без автентифікації: достатньо ключа-заповнювача

Codex перевіряє наявність змінної середовища, вказаної в `env_key`,
**до того**, як перший запит залишить CLI. Якщо ваш **локальний** екземпляр
OmniRoute не потребує автентифікації, підійде будь-яке непорожнє
значення-заповнювач:

```bash
export OMNIROUTE_API_KEY="${OMNIROUTE_API_KEY:-local}"
```

Натомість використовуйте справжній ключ, якщо ваш сервер OmniRoute захищений
або віддалений.

> **Поширені варіанти адреси хоста**
>
> | Доступ          | URL                           |
> | --------------- | ----------------------------- |
> | Локальна мережа | `http://192.168.0.1:20128/v1` |
> | Tailscale       | `http://100.x.x.x:20128/v1`   |
> | Loopback        | `http://localhost:20128/v1`   |

## `wire_api = "responses"` — чому це працює для всіх моделей

Codex CLI оголосив `wire_api = "chat"` (Chat Completions) застарілим у лютому 2026 року й тепер **вимагає** `wire_api = "responses"` (OpenAI Responses API). Встановлення `wire_api = "chat"` спричиняє негайний збій під час запуску, починаючи з v0.138.

Багато провайдерів, зокрема GLM і Kimi, досі надають лише кінцеву точку Chat Completions. DeepSeek V4 тепер надає як нативний Responses API, так і Anthropic-сумісну кінцеву точку; OmniRoute типово використовує Responses і дає змогу для кожного підключення DeepSeek вибрати сумісність з Anthropic.

**OmniRoute розв’язує це прозоро:**

```
Codex CLI
  → wire_api = "responses"
  → POST /v1/responses (OmniRoute)
    → OmniRoute вибирає нативний протокол провайдера та за потреби виконує перетворення
    → POST /responses (DeepSeek V4) або /chat/completions (Mistral / GLM / Kimi / інші)
```

Під час використання OmniRoute вам ніколи не потрібен окремий проксі-сервер для перетворення. **Усі моделі використовують `wire_api = "responses"`** — про решту дбає OmniRoute.

> **`wire_api` використовується за замовчуванням** — поле має значення `"responses"` за замовчуванням, і його можна повністю опустити в `config.toml`. Вказуйте його явно лише тоді, коли потрібно задокументувати намір.

## Контекстне вікно та ущільнення

### Поля конфігурації токенів

| Поле                             | Опис                                                                                                                                                                                                                                      |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_context_window`           | Загальний бюджет токенів для активної моделі. Установіть відповідно до заявленого ліміту моделі.                                                                                                                                          |
| `model_auto_compact_token_limit` | Порогове значення, що запускає автоматичне ущільнення історії. **Максимум: 90% від `model_context_window`** — значення понад 90% без повідомлення ігноруються.                                                                            |
| `tool_output_token_limit`        | Обмеження кількості токенів, що зберігаються в історії для результату кожного виклику інструмента. Запобігає заповненню вікна однією великою відповіддю інструмента. **Це не максимальний обсяг виводу** — це ліміт збереження в історії. |
| `compact_prompt`                 | Вбудоване перевизначення системного промпту, що використовується під час ущільнення (v0.138+).                                                                                                                                            |

> **Примітка щодо `model_max_output_tokens`**: Це поле **не є частиною схеми конфігурації Codex CLI** (відсутнє в кодовій базі Codex на Rust). Якщо його встановити, воно без повідомлення ігнорується. Не покладайтеся на нього — використовуйте `tool_output_token_limit`, щоб контролювати обсяг результатів інструментів, який зберігається в історії.

## Інтенсивність міркування

Керує тим, наскільки ретельно модель «міркує» перед відповіддю.

| Значення | Для чого використовувати                                  |
| -------- | --------------------------------------------------------- |
| `none`   | Без міркування — безпосередня відповідь                   |
| `low`    | Тривіальні завдання (перейменування, форматування)        |
| `medium` | **Значення сервера за замовчуванням**, якщо не вказано    |
| `high`   | Завдання середньої складності (рефакторинг, налагодження) |
| `xhigh`  | Архітектура, глибокий аналіз, складні проблеми            |

```bash
# Перевизначення для окремого виклику
codex -c model_reasoning_effort=low "перейменуй змінну x на count"
codex -c model_reasoning_effort=xhigh "спроєктуй модуль автентифікації"
```

Також налаштуйте **підсумок** міркувань, щоб Desktop міг відображати текст міркувань (а не лише зашифровані блоки):

```toml
# ~/.codex/config.toml
model_reasoning_effort = "xhigh"   # або ultra, якщо підтримується
model_reasoning_summary = "detailed"  # auto | concise | detailed | none
```

### Бюджет міркувань OmniRoute (налаштування сервера)

На хості OmniRoute параметр **Settings → AI → Thinking Budget** має бути встановлений у значення **`passthrough`**, щоб інтенсивність/підсумок Codex передавалися до зовнішнього сервісу. Режим **`auto` видаляє** всі клієнтські поля `reasoning` / `reasoning_effort` і залишає панелі міркувань порожніми, навіть якщо Codex налаштовано правильно.

Повний посібник: [THINKING_BUDGET.md](./THINKING_BUDGET.md).

Стиснення та кеш запитів не залежать від цього й продовжують працювати в режимі `passthrough`.

## Профілі — іменовані конфігурації для кожної моделі/робочого процесу

Профілі дають змогу перемикати модель і контекстне вікно за допомогою одного прапорця. Кожен профіль — це плоский файл
`~/.codex/<name>.config.toml`, налаштування якого накладаються поверх базового `config.toml`.

> **Правило іменування (Codex CLI v0.137+):** файл має називатися `~/.codex/<name>.config.toml` — **без префікса `profile-`**.
> CLI перетворює `-p kimi-k27` на `~/.codex/kimi-k27.config.toml`. Якщо файл не знайдено, конфігурація за замовчуванням застосовується без попередження.

```bash
codex --profile kimi-k27 "проаналізуй 10 тисяч рядків цієї кодової бази"
codex -p glm52 "перевір архітектуру"
codex --profile deepseek-flash "перейменуй змінну"   # швидко й дешево
```

### Профілі інтенсивності (та сама модель, різна інтенсивність)

```bash
codex -p low      # cx/gpt-5.5, інтенсивність=low
codex -p medium   # cx/gpt-5.5, інтенсивність=medium
codex -p high     # cx/gpt-5.5, інтенсивність=high
codex -p xhigh    # cx/gpt-5.5, інтенсивність=xhigh (за замовчуванням)
codex -p chat     # cx/gpt-5.5, інтенсивність не задано (значення сервера за замовчуванням)
```

## Автоматичне генерування профілів за допомогою `omniroute setup-codex`

Якщо ви запускаєте OmniRoute на VPS, можна автоматично генерувати файли профілів з актуального каталогу моделей:

```bash
# З VPS (використовує локальний OmniRoute на порту 20128)
omniroute setup-codex

# З будь-якого комп’ютера — укажіть адресу свого VPS
omniroute setup-codex --remote http://100.x.x.x:20128 --api-key sk-xxx

# Попередній перегляд без запису файлів
omniroute setup-codex --remote http://100.x.x.x:20128 --dry-run

# Генерувати лише профілі GLM і Kimi
omniroute setup-codex --only glm,kimi

# Записати до власного каталогу
omniroute setup-codex --codex-home /path/to/.codex
```

Команда отримує `/v1/models`, використовує оптимізовані профілі для відомих моделей, а для інших сумісних текстових моделей — метадані каталогу, після чого записує `~/.codex/<name>.config.toml` для кожної з них. Команда ідемпотентна — її безпечно запускати повторно.

OmniRoute також може **автоматично синхронізувати** ці самі файли профілів після того, як успішне виявлення або імпорт моделей постачальника змінить актуальний каталог. Ця функція **вмикається явно й за замовчуванням вимкнена**: увімкніть її на панелі **CLI Code** ("CLI profile auto-sync" → Codex) або задайте `OMNIROUTE_AUTO_SYNC_CODEX_PROFILES=true` (також враховується `CLI_ALLOW_CONFIG_WRITES`, яку за замовчуванням увімкнено). Коли функцію ввімкнено, вона записує лише окремі файли профілів `~/.codex/*.config.toml`; вона ніколи не змінює активний або стандартний файл `~/.codex/config.toml`, налаштування Codex-lb, автентифікацію чи вибір постачальника.

## Довготривалі завдання

Два стандартні параметри OmniRoute можуть непомітно зірвати багатогодинні сеанси Codex CLI. Жоден із них не є налаштуванням Codex CLI — обидва належать до OmniRoute. Користувачі, які переносять конфігурацію з проксі-серверів вищого рівня, що закріплюють облікові записи та вимикають відсікання через бездіяльність, часто стикаються з обома проблемами й доходять висновку, що OmniRoute «не здатен підтримувати тривалий сеанс».

| Симптом                                                                                       | Імовірна причина                                                                                        | Параметр                 |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------ |
| Сеанс постійно перемикає облікові записи / безперервність кешу запитів між ходами втрачається | TTL прив’язки сеансу дорівнює `0` (вимкнено)                                                            | `sessionAffinityTtlMs`   |
| З’єднання обривається під час міркування без запиту, видимого клієнту                         | Сторожовий таймер бездіяльності потоку спрацював після 10 хвилин без фрагмента від сервера вищого рівня | `STREAM_IDLE_TIMEOUT_MS` |

Пов’язані обговорення: [#7126](https://github.com/diegosouzapw/OmniRoute/discussions/7126) (переривання тривалих завдань), [#5718](https://github.com/diegosouzapw/OmniRoute/discussions/5718) (чому прив’язку типово вимкнено). Відстеження: [#7287](https://github.com/diegosouzapw/OmniRoute/issues/7287).

### 1. Прив’язка сеансу — закріплення однієї розмови за одним обліковим записом

**Типове значення:** `sessionAffinityTtlMs = 0` (вимкнено).

**Де це налаштувати**

- Панель керування → **Налаштування → Маршрутизація** → **Прив’язка сеансу** → **TTL прив’язки (секунди)** (`ComboDefaultsTab`)
- Або виконайте PATCH налаштувань із `sessionAffinityTtlMs` у **мілісекундах** (діапазон Zod: `0`–`86_400_000`, тобто до 24 годин)

> Перейменовано в #7274 з орієнтованого лише на Codex параметра `codexSessionAffinityTtlMs`. Застарілий ключ усе ще приймається як псевдонім лише для читання; у нових конфігураціях слід використовувати `sessionAffinityTtlMs`. Тепер прив’язка застосовується до **будь-якого** постачальника, щойно TTL перевищує `0`, а не лише до Codex — див. [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) → Прив’язка сеансу.

**Що порушується, коли значення залишається рівним 0**

Кожен хід багатокрокової розмови Codex маршрутизується незалежно за активною комбінованою стратегією та може потрапляти до **іншого облікового запису на кожному ході**. Це порушує безперервність сеансу / кешу запитів на сервері вищого рівня. OmniRoute враховує заголовки сеансу Codex (`x-codex-session-id` / `x-session-id` / `x-omniroute-session`) і поля тіла, як-от `prompt_cache_key` / `session_id`, лише коли TTL перевищує `0` (`extractSessionAffinityKey` у `src/sse/services/auth.ts`).

**Рекомендація для одного багатогодинного завдання**

Установіть TTL **вище за очікувану астрономічну тривалість завдання** (максимум в інтерфейсі — **86400 секунд** = 24 години):

| Очікувана тривалість завдання | TTL прив’язки (інтерфейс, секунди) | `sessionAffinityTtlMs` |
| ----------------------------- | ---------------------------------- | ---------------------- |
| Кілька годин                  | `14400` (4 год)                    | `14400000`             |
| Упродовж ночі / ~12 год       | `43200` (12 год)                   | `43200000`             |
| Повна доба                    | `86400` (24 год, максимум)         | `86400000`             |

Явна згода є навмисною: вимкнення прив’язки сприяє балансуванню навантаження між обліковими записами, а її ввімкнення — безперервності одного тривалого агентного сеансу. Цей посібник **не** змінює типове значення — оператори, які виконують тривалі завдання Codex, мають увімкнути цю функцію самостійно.

### 2. Тайм-аут бездіяльності потоку — не переривайте тихі етапи міркування

**Типове значення:** `STREAM_IDLE_TIMEOUT_MS = 600000` (10 хвилин). Якщо його не задано, воно успадковується від `REQUEST_TIMEOUT_MS`; спільне базове значення також дорівнює 600000. Див. [`docs/guides/SETUP_GUIDE.md`](SETUP_GUIDE.md) → Тайм-аути.

**Що порушується за типового значення**

Хід міркування / виклику інструмента Codex, який залишається безмовним понад 10 хвилин, **не отримуючи жодного реального фрагмента від upstream**, примусово закривається сторожовим таймером бездіяльності SSE (`open-sse/utils/stream.ts`). Клієнт часто бачить лише обрив з’єднання — що відповідає опису «автоматично зупинилося без жодного сповіщення».

Критично важлива деталь: синтетичний SSE-**heartbeat OmniRoute не скидає** таймер бездіяльності. `lastChunkTime` оновлюється лише після отримання реального фрагмента тіла відповіді від upstream. З погляду сторожового таймера модель, яка мовчки продовжує «міркувати», нічим не відрізняється від завислого upstream.

Пов’язаний тайм-аут бездіяльності тіла Undici: `FETCH_BODY_TIMEOUT_MS` (також за замовчуванням використовує той самий базовий інтервал у 10 хвилин; значення `0` вимикає його). Для потокового передавання `FETCH_TIMEOUT_MS` охоплює лише встановлення з’єднання / отримання перших заголовків — після активації потоку зависання контролюються параметрами `STREAM_IDLE_TIMEOUT_MS` і `FETCH_BODY_TIMEOUT_MS`.

**Рекомендація для одного завдання тривалістю кілька годин**

У середовищі процесу OmniRoute (`.env` / compose / systemd):

```bash
# Вимкнути обмеження бездіяльності потоку й тіла для тривалих циклів міркування
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

Або збільште їх до значень, що перевищують найдовший очікуваний період бездіяльності (значення вказуються в мілісекундах):

```bash
# Приклад: дозволити до 2 годин тиші між фрагментами від upstream
STREAM_IDLE_TIMEOUT_MS=7200000
FETCH_BODY_TIMEOUT_MS=7200000
```

Після зміни цих змінних середовища перезапустіть OmniRoute.

### Конкретний рецепт — багатогодинне завдання Codex

1. **Закріпіть обліковий запис:** Dashboard → Settings → Routing → Session affinity → Affinity TTL = `43200` (12 год) або `86400` (максимум 24 год).
2. **Збільште / вимкніть тайм-аути бездіяльності** в середовищі OmniRoute:

```bash
STREAM_IDLE_TIMEOUT_MS=0
FETCH_BODY_TIMEOUT_MS=0
```

3. Збережіть звичайний `config.toml` Codex (`wire_api = "responses"`, правильний `base_url`, `OMNIROUTE_API_KEY`) — у Codex немає налаштувань прив’язки чи бездіяльності для цих двох типів поведінки.
4. Перезапустіть OmniRoute, а потім запустіть тривале завдання Codex.

### Рішення щодо значень за замовчуванням (#7287)

| Параметр                 | Значення за замовчуванням | Змінювати в цьому посібнику?                                                                                          |
| ------------------------ | ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `sessionAffinityTtlMs`   | `0` (вимкнено)            | **Ні** — залишається за вибором (балансування навантаження проти безперервності; див. Discussion #5718)               |
| `STREAM_IDLE_TIMEOUT_MS` | `600000` (10 хв)          | **Ні** — для загального трафіку залишається 10 хвилин; оператори тривалих завдань Codex збільшують або вимикають його |

Глобальна зміна будь-якого з цих значень за замовчуванням вплинула б на поведінку всіх клієнтів екземпляра, а не лише Codex. Задокументуйте параметри; не змінюйте значення за замовчуванням, доки оператор явно не ухвалить інше рішення.

### Діагностика переривань через бездіяльність

Коли спрацьовує сторожовий таймер бездіяльності, OmniRoute записує в журнал рядок такого вигляду:

```text
[STREAM] Idle timeout: no data from codex for 600000ms (model: cx/gpt-5.5)
```

Шукайте за допомогою grep рядок `Idle timeout: no data from` (або код `stream_idle_timeout` / назву помилки `StreamIdleTimeoutError`). Сегмент постачальника відповідає тому, що OmniRoute використав для цього запиту (`codex`, ідентифікатор іншого постачальника або `provider`, якщо він невідомий), — це не завжди буквальний рядок `codex`.

## Усунення несправностей

**`Error: wire_api = "chat" більше не підтримується`**
Видаліть `wire_api = "chat"` зі своєї конфігурації. Установіть `wire_api = "responses"` або пропустіть це поле (починаючи з v0.138, типовим значенням є `"responses"`).

**`Error: model not found`**
Переконайтеся, що модель існує в OmniRoute і має правильний префікс. Виконайте `omniroute models list` або відкрийте `/dashboard/providers/<provider>`.

**`Authentication error`**
Переконайтеся, що `OMNIROUTE_API_KEY` експортовано: `echo $OMNIROUTE_API_KEY`.

**`ERROR: Missing environment variable: OMNIROUTE_API_KEY`**
Codex перевіряє наявність змінної середовища перед виконанням першого запиту. Експортуйте
справжній ключ для захищених серверів або непорожнє значення-заповнювач, наприклад
`OMNIROUTE_API_KEY=local`, якщо ваш **локальний** екземпляр OmniRoute не
вимагає автентифікації. Перезапустіть оболонку, якщо ви додали змінну до `~/.bashrc` або `~/.zshrc`.

**`Connection refused`**
Переконайтеся, що OmniRoute запущено, а хост і порт у `base_url` правильні для вашої мережі (локальна мережа, Tailscale або VPS).

**Сеанс аварійно завершується поблизу межі контексту**
Явно задайте `model_context_window` і `model_auto_compact_token_limit`. Дивіться таблицю вікон контексту вище.

**Ущільнення запускається запізно**
Зменште `model_auto_compact_token_limit` до 80–85% від розміру вікна. Ніколи не встановлюйте значення вище 90%.

**Профіль не завантажується (`-p <name>` мовчки ігнорується)**
Переконайтеся, що файл існує за шляхом `~/.codex/<name>.config.toml` (без префікса `profile-`). Виконайте `ls ~/.codex/*.config.toml`.

**Тривале завдання Codex переривається під час виконання / між запитами перемикаються облікові записи**
Дивіться розділ [Тривалі завдання](#long-running-tasks). Увімкніть прив’язування сеансу (TTL має перевищувати тривалість завдання) і збільште значення або вимкніть `STREAM_IDLE_TIMEOUT_MS` / `FETCH_BODY_TIMEOUT_MS`. Знайдіть у журналах OmniRoute рядок `Idle timeout: no data from` за допомогою grep.
