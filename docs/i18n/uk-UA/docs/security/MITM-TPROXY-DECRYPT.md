Прозоре дешифрування TPROXY — це **5-й режим перехоплення** OmniRoute для MITM-стека
[Traffic Inspector](../frameworks/TRAFFIC_INSPECTOR.md) / [AgentBridge](../frameworks/AGENTBRIDGE.md).
Він перехоплює та **дешифрує** локальний вихідний HTTPS-трафік у Linux,
використовуючи ядровий TPROXY і маршрутизацію на основі політик — **без** підміни `/etc/hosts` і
**без** зміни загальносистемних налаштувань проксі ОС. Він придатний для роботи
без графічного інтерфейсу (не потрібно скасовувати зміни DNS), а правила брандмауера
автоматично очищаються після перезавантаження.

На відміну від інших режимів перехоплення, TPROXY не потребує налаштування для кожного хоста:
він прозоро перехоплює **довільні** хости призначення на цільовому порту, завершує TLS
за допомогою кінцевого сертифіката, який створюється на льоту для кожного імені хоста SNI,
перехоплює дешифрований обмін і повторно шифрує запит до початкового призначення.

> **Лише для Linux, лише з правами root, за явним вибором.** Цей режим потребує Linux,
> нативного доповнення, зібраного за допомогою набору інструментів C, і можливості
> **CAP_NET_ADMIN** (зазвичай — прав root). Доступ до нього надається лише через
> AgentBridge API, доступний виключно на loopback-інтерфейсі, і за замовчуванням його вимкнено.
> Довірений MITM-центр сертифікації, який може підписувати сертифікати для будь-якого хоста,
> є потужним засобом — див. [§6 Безпека](#6-security).

**Джерело:** `src/mitm/tproxy/`
**Маршрут API:** `GET / POST / DELETE /api/tools/agent-bridge/tproxy`
**Перемикач на панелі керування:** Traffic Inspector → панель режимів перехоплення → **"Дешифрування TPROXY"** ⚠

[`docs/frameworks/AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)

## §1 Що це таке й коли це використовувати

Кожен з інших чотирьох режимів перехоплення має певне обмеження:

| Режим                    | Як спрямовується трафік                                  | Обмеження                                               |
| ------------------------ | -------------------------------------------------------- | ------------------------------------------------------- |
| AgentBridge              | DNS-підміна фіксованого набору хостів через `/etc/hosts` | лише зареєстровані хости IDE-агентів                    |
| Власні хости             | DNS-підміна кожного хоста через `/etc/hosts`             | один запис на хост; для редагування hosts потрібен sudo |
| HTTP_PROXY               | змінні середовища `HTTP_PROXY`/`HTTPS_PROXY`             | лише застосунки, що враховують змінну середовища        |
| Загальносистемний проксі | налаштування проксі ОС                                   | змінює глобальний стан; потрібно скасувати зміни        |

Натомість прозоре дешифрування TPROXY спрямовує трафік на рівні **ядра**. Воно
позначає нові локальні вихідні TCP-з’єднання до цільового порту (за замовчуванням `443`)
у ланцюжку `mangle OUTPUT`; правило `ip rule` переспрямовує позначені пакети
для локальної доставки, а під час повторного входу ціль `TPROXY` у
`mangle PREROUTING` передає їх обробнику **IP_TRANSPARENT**, який потім
завершує TLS і перехоплює відкритий текст.

Використовуйте цей режим, якщо потрібно перехопити й дешифрувати трафік процесу, який:

- звертається до хоста, не зареєстрованого AgentBridge;
- не враховує `HTTP_PROXY`;
- не повинен зазнавати впливу через зміну загальносистемного проксі.

Оскільки перехоплення відбувається в ядрі, процес-джерело **не потребує жодних
змін конфігурації**, але він має довіряти динамічному центру сертифікації, який
встановлює OmniRoute (див. [§4](#4-the-per-sni-dynamic-ca-and-trust-store-installer)).

## §2 Вимоги

| Вимога             | Деталі                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ОС**             | Лише Linux — **IP_TRANSPARENT** є параметром сокета, доступним лише в Linux. На всіх інших платформах завантажувач повертає «недоступно».                                             |
| **Привілеї**       | Можливість **CAP_NET_ADMIN** для створення прозорого сокета та застосування правил `iptables`/`ip` — на практиці слід запускати від імені root.                                       |
| **Нативний аддон** | Невеликий аддон N-API (`src/mitm/tproxy/native/transparent.c`) має бути зібраний або постачатися як попередньо зібраний бінарний файл. Див. [§3](#3-the-native-ip_transparent-addon). |
| **Модулі ядра**    | `iptables` із підтримкою `TPROXY`, `mangle` та зіставлення `mark` (перевірено з ядром 6.8.0).                                                                                         |

**Коректна деградація:** якщо будь-яка вимога не виконана (не Linux, немає інструментарію,
аддон не зібрано), завантажувач аддона (`src/mitm/tproxy/transparentSocket.ts::loadTransparentAddon`)
повертає `null`, а не створює виняток. Після цього статус режиму перехоплення повідомляє
`available: false`, перемикач на панелі керування стає **недоступним** із підказкою
«Для розшифрування TPROXY потрібні Linux, права root і нативний аддон», а решта
OmniRoute продовжує працювати.

## §3 Нативний аддон IP_TRANSPARENT

Модуль Node `net` не може викликати `setsockopt(IP_TRANSPARENT)` _перед_ `bind()`, як
того вимагає TPROXY (інакше ядро відкидає перенаправлені пакети). Аддон
(`src/mitm/tproxy/native/transparent.c`, зібраний через `binding.gyp`) — це невеликий модуль
N-API, який надає три функції, що використовуються через `transparentSocket.ts`:

| Функція аддона                        | Робота із сокетом                                                                                    | Призначення                                                                           |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `createTransparentListener(ip, port)` | `socket()` + **SO_REUSEADDR** + **IP_TRANSPARENT** + `bind()` + `listen()`, повертає необроблений fd | прозорий прослуховувач перехоплення (Node приймає fd через `server.listen({ fd })`)   |
| `setSocketMark(fd, mark)`             | `setsockopt` **SO_MARK** для наявного fd                                                             | запобігання зацикленню (маркування власних сокетів проксі)                            |
| `connectMarked(ip, port, mark)`       | `socket()` + **SO_MARK** **перед** неблокувальним `connect()`, повертає fd                           | повторно зашифроване переспрямування до висхідного сервера (SYN передається з міткою) |

Початкове місце призначення зчитується із `socket.localAddress`/`localPort` — TPROXY
зберігає його, тому пошук через **SO_ORIGINAL_DST**/NAT не потрібен.

### Збирання аддона

```bash
npm run build:native:tproxy      # перехід до src/mitm/tproxy/native та запуск node-gyp rebuild
                                 # -> native/build/Release/transparent.node
```

- Під час `npm run build` сценарій `scripts/build/build-tproxy-native.mjs` запускає `node-gyp
rebuild`. Він призначений **лише для Linux і завершується без критичної помилки** — відсутність інструментарію просто залишає
  режим перехоплення недоступним.
- `assembleStandalone.mjs` копіює `build/Release/transparent.node` до
  автономного пакета; `transparentSocket.ts` знаходить його як відносно модуля, так і
  відносно cwd (`<cwd>/src/mitm/tproxy/native/...`).
- `build/` і `prebuilds/` ігноруються git — бінарний файл **збирається, але ніколи
  не додається до репозиторію**.

Завантажувач перевіряє в такому порядку пріоритетності:
`native/build/Release/transparent.node`, потім `native/prebuilds/transparent.node`
(обидва шляхи — відносно модуля та всередині `<cwd>/src/mitm/tproxy/`).

## §4 Динамічний ЦС для кожного SNI та інсталятор сховища довіри

> **Оновлення #6684:** статичний сервер AgentBridge (`src/mitm/server.cjs`) тепер
> використовує ту саму архітектурну модель ЦС/кінцевих сертифікатів замість одного статичного
> самопідписаного кінцевого сертифіката. Він використовує **окремий** екземпляр ЦС
> (`src/mitm/cert/rootCa.ts`, збережений у `<DATA_DIR>/mitm/ca.key`/`ca.crt`)
> та встановлює його в наявний слот сховища довіри `omniroute-mitm.crt`
> (замінюючи там старий одиночний кінцевий сертифікат — очищення подвійної довіри не потрібне),
> який залишається повністю відокремленим від власного слота TPROXY
> `omniroute-tproxy-ca.crt`, описаного нижче.
> Нові інсталяції AgentBridge автоматично використовують модель ЦС; інсталяція, яка
> вже довіряє старому статичному кінцевому сертифікату, продовжує використовувати його, доки оператор не
> ввімкне цю модель через `MITM_ROOT_CA_ENABLED=true` (див. `src/mitm/cert/migration.ts`) —
> довірений MITM-ЦС, здатний підписати кінцевий сертифікат для **будь-якого** хоста, має суттєво
> ширші повноваження, ніж старий кінцевий сертифікат із фіксованим SAN, тому для
> інсталяції, яка вже йому довіряє, перехід ніколи не відбувається непомітно.

Історично статичний MITM-сертифікат AgentBridge працював лише тому, що AgentBridge
підміняє DNS для **фіксованого** набору хостів (тепер уніфікованого з наведеною нижче моделлю). TPROXY
перехоплює **довільні** хости, тому його слухач повинен надавати дійсний кінцевий сертифікат
для будь-якого SNI, запитаного клієнтом, — така сама вимога тепер діє для AgentBridge
щодо повного набору `MITM_TOOL_HOSTS` (9 записів інструментів), а не лише 4
хостів antigravity.

### Динамічний ЦС (`src/mitm/tproxy/dynamicCert.ts`)

`DynamicCertStore` запускає локальний ЦС (побудований на основі залежності `selfsigned`), який:

- Створює довгостроковий ЦС через `generateMitmCa()` (CN `"OmniRoute MITM CA"`,
  термін дії 10 років, `basicConstraints CA=true` + `keyUsage keyCertSign,cRLSign`,
  2048-бітний RSA / SHA-256).
- **На вимогу видає кінцевий сертифікат для кожного імені хоста SNI** через `issueLeafCert()` (термін
  дії 1 рік, `subjectAltName` = хост SNI) та кешує по одному `tls.SecureContext`
  для кожного імені хоста.
- Надає `createSNICallback()` для сервера, який завершує TLS-з’єднання (див. [§5](#5-how-decrypt-and-capture-work)).
- Може бути створений з `existingCa`, щоб ЦС залишався незмінним після перезапусків
  (щоб не потрібно було повторно встановлювати сховище довіри).

Закритий ключ ЦС **ніколи не залишає машину**.

### Інсталятор сховища довіри (`src/mitm/tproxy/caTrust.ts`)

Клієнт, трафік якого перехоплюється, повинен довіряти динамічному ЦС, тому під час запуску режиму захоплення
сертифікат ЦС встановлюється у сховище довіри ОС в **окремий слот** —
`omniroute-tproxy-ca.crt` (константа `TPROXY_CA_CERT_NAME`) — відокремлений від
слота статичного MITM-сертифіката (`omniroute-mitm.crt`), щоб вони ніколи не
перезаписували один одного.

`installTproxyCa(caPem, sudoPassword?)` визначає каталог довірених сертифікатів
дистрибутива (у такому порядку: спочатку в стилі Debian) і запускає відповідну команду оновлення:

| Каталог довірених сертифікатів              | Команда оновлення        |
| ------------------------------------------- | ------------------------ |
| `/usr/local/share/ca-certificates`          | `update-ca-certificates` |
| `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust`        |
| `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust`        |
| `/etc/pki/trust/anchors`                    | `update-ca-certificates` |

Під час встановлення PEM спочатку розміщується в тимчасовому файлі, потім із підвищеними привілеями
виконується `mkdir -p` для каталогу довірених сертифікатів, `cp` копіює до нього підготовлений файл,
після чого запускається команда оновлення. `uninstallTproxyCa()` видаляє лише окремий слот
(залишаючи статичний MITM-сертифікат недоторканим) і виконує оновлення; на системах, відмінних від Linux,
нічого не відбувається.

Усі привілейовані команди виконуються через `execFileWithPassword` (`src/mitm/systemCommands.ts`)
— `spawn` із **масивами аргументів, без оболонки та без інтерполяції рядків** (жорстке правило №13).
Коли процес виконується від імені root (наприклад, на VPS), цільова команда запускається безпосередньо й пароль
не потрібен; на настільній системі без root-прав `sudoPassword` передається через `sudo -S` у stdin.

> `sudoPassword` настільного застосунку передається в тілі POST-запиту для авторизації
> встановлення у сховище довіри; якщо процес виконується від імені root, цей параметр повністю ігнорується.

## §5 Як працюють розшифрування та перехоплення

Конвеєр (увесь у `src/mitm/tproxy/`):

```
локальний застосунок  ──TCP/443──▶  mangle OUTPUT позначає з’єднання (fwmark)
                                    ip rule → локальна таблиця маршрутів → lo
                                    mangle PREROUTING TPROXY → прослуховувач IP_TRANSPARENT (порт 8443)
                                        │  captureMode.ts: зчитує початкову адресу призначення із socket.localAddress
                                        ▼
                                    tlsCapture.ts:
                                      1. Завершує TLS-з’єднання КЛІЄНТА за допомогою окремого для кожного SNI кінцевого сертифіката (dynamicCert)
                                      2. внутрішній http.Server аналізує розшифрований відкритий текст
                                      3. перехоплення → globalTrafficBuffer.push() із source: "tproxy"
                                         (застосовуються sanitizeHeaders + maskSecret)
                                      4. пересилає дані, ПОВТОРНО зашифровані, до початкової адреси призначення
                                         через сокет із позначкою обходу (connectMarked, захист від зациклення)
                                        │
                                        ▼
                                    початковий висхідний сервер (api.example.com)
```

- **Завершення TLS** (`createTlsCaptureServer`): обгортає перехоплений необроблений
  сокет у серверний `tls.TLSSocket`, використовуючи функцію зворотного виклику SNI
  динамічного ЦС, а потім передає розшифрований потік внутрішньому `http.Server`
  (стандартний прийом завершення MITM). Час життя сокетів обмежується
  `MITM_IDLE_TIMEOUT_MS`, щоб завислий тунель не міг вичерпати файлові дескриптори.
- **Перехоплення** (`handleDecryptedRequest`): додає `InterceptedRequest` із
  `source: "tproxy"`, початковим статусом `"in-flight"`, заголовками, обробленими
  через `sanitizeHeaders()`, і тілами, обробленими через `maskSecret()`, перш ніж
  вони потраплять до буфера. Потім запис оновлюється відповіддю, розмірами та
  затримкою.
- **Повторно зашифроване пересилання** (`createForward` / `realForward`): повторно
  шифрує дані для початкової адреси призначення. Значення `rejectUnauthorized`
  за замовчуванням — **`true`** (безпечне за замовчуванням): сертифікат висхідного
  сервера перевіряється щодо SNI/Host, запитаного клієнтом, тому проксі відхиляє
  саме те, що відхилив би початковий клієнт.

### Захист від зациклення (SO_MARK)

Оскільки правила позначають нові локальні вихідні з’єднання, **власне** повторно
зашифроване пересилання проксі зазвичай було б повторно перехоплене, утворюючи
нескінченний цикл. Шлях пересилання захищається від цього позначкою обходу сокета
(**SO_MARK**):

- `realForward` відкриває свій сокет висхідного з’єднання через
  `connectMarked(ip, port, DEFAULT_BYPASS_MARK)` — `DEFAULT_BYPASS_MARK = 0x539` —
  що встановлює **SO_MARK** **до** `connect()`, тож SYN-пакет пересилання містить
  позначку обходу.
- Правило `mangle OUTPUT` виключає з’єднання, які вже мають позначку обходу
  (`-m mark ! --mark <bypassMark>`), тому пересилання проксі **не** позначається
  повторно й не потрапляє знову до TPROXY.

> Примітка щодо реалізації: сокет із позначкою обходу має бути встановлений у
> `createConnection` агента (`https.request({ createConnection })` мовчки
> ігнорується за наявності агента), інакше для пересилання буде відкрито
> непозначений сокет і зациклення відновиться. Це виправлення захисту від
> зациклення було підтверджено наскрізним тестуванням.

## §6 Безпека

| Контроль                                     | Докладний опис                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **API лише для loopback**                    | `/api/tools/agent-bridge/tproxy` охоплюється префіксом `/api/tools/agent-bridge/` у `LOCAL_ONLY_API_PREFIXES` (`src/server/authz/routeGuard.ts`). Обмеження loopback застосовується **до** автентифікації (Жорсткі правила №15 і №17) — витік JWT через тунель не дасть змоги запустити перехоплення TPROXY, яке застосовує правила `iptables` і встановлює CA в сховище довіри через дочірні процеси. |
| **Окреме місце для CA**                      | Динамічний CA встановлюється як `omniroute-tproxy-ca.crt`, ніколи не перезаписуючи статичний сертифікат MITM.                                                                                                                                                                                                                                                                                          |
| **Ключ CA ніколи не залишає хост**           | `DynamicCertStore` зберігає ключ CA в пам’яті; він не експортується.                                                                                                                                                                                                                                                                                                                                   |
| **Маскування секретів**                      | `maskSecret()` для тіл запитів/відповідей і `sanitizeHeaders()` для заголовків виконуються **до** `globalTrafficBuffer.push()`.                                                                                                                                                                                                                                                                        |
| **Без інтерполяції оболонки**                | Усі команди `iptables`/`ip`/сховища довіри виконуються через `execFile`/`execFileWithPassword` із масивами аргументів (Жорстке правило №13).                                                                                                                                                                                                                                                           |
| **Перевірка сертифіката висхідного сервера** | Повторно зашифроване переспрямування типово перевіряє сертифікат висхідного сервера (`rejectUnauthorized: true`).                                                                                                                                                                                                                                                                                      |
| **Очищення помилок**                         | Відповіді маршруту з помилками проходять через `sanitizeErrorMessage()` (Жорстке правило №12).                                                                                                                                                                                                                                                                                                         |

**CA для MITM — це потужна можливість.** CA, якому довіряє ОС і який може підписувати сертифікати для будь-якого
хоста, означає, що все, що перехоплює OmniRoute, можна розшифрувати. Ця можливість доступна лише в
явно ввімкненому локальному режимі перехоплення TPROXY, типово вимкнена, а запис у сховищі довіри
видаляється після зупинення цього режиму.

## §7 Транзакційне застосування / скасування налаштувань брандмауера

Збій у жодному разі не повинен залишати після себе правило `mangle` або застарілий маршрут. Побудовник команд
(`src/mitm/tproxy/commands.ts`) і виконавець (`src/mitm/tproxy/setup.ts`) гарантують, що
**скасування є точною операцією, оберненою до застосування, виконаною у зворотному порядку**.

`applyTproxy(cfg)` виконує команди застосування по порядку; у разі **будь-якої** помилки він виконує
повне скасування через `revertTproxy(cfg)` у режимі найкращих зусиль і повторно викидає помилку — тож брандмауер або
повністю налаштований, або його налаштування повністю скасовано, але він ніколи не залишається частково налаштованим. `revertTproxy(cfg)` виконує
обернені команди у зворотному порядку та ігнорує помилки (операція ідемпотентна — її можна безпечно викликати
безумовно, наприклад, під час очищення AgentBridge у `repairMitm()`).

`validateTproxyConfig(cfg)` запускається перед будь-якою командою: порти мають бути в діапазоні `1–65535`,
`mark`/`routeTable`/`bypassMark` мають бути додатними цілими числами, а `bypassMark` має
відрізнятися від `mark` (запобігання зацикленню).

### Команди застосування (по порядку)

```bash
ip rule add fwmark <mark> lookup <routeTable>
ip route add local 0.0.0.0/0 dev lo table <routeTable>
iptables -t mangle -A OUTPUT -p tcp --dport <dport> -m mark ! --mark <bypassMark> -j MARK --set-mark <mark>
iptables -t mangle -A PREROUTING -p tcp --dport <dport> -m mark --mark <mark> -j TPROXY --on-port <onPort> --tproxy-mark <mark>
```

Під час скасування вони видаляються у зворотному порядку: `PREROUTING -D`, `OUTPUT -D`, `ip route del`, `ip rule del`.

> Ця схема базується на **OUTPUT**, оскільки сценарій використання MITM стосується _локального_ вихідного
> трафіку (застосунків на тому самому хості), якого TPROXY лише в `PREROUTING` не
> бачить — `PREROUTING` бачить лише переспрямований трафік. Ланцюжок `OUTPUT` позначає нові
> локальні з’єднання, `ip rule` переспрямовує їх на локальну доставку (`lo`), після чого
> `PREROUTING` призначає їх прозорому слухачу.

## §8 Конфігурація

Запит на запуск (`POST /api/tools/agent-bridge/tproxy`) приймає наведені нижче
поля, які перевіряє `StartTproxyBodySchema` (`tproxy/route.ts`). Усі вони необов’язкові
й у разі відсутності набувають значень за замовчуванням:

| Поле             | Тип                | Типове значення | Примітки                                                                                                                                     |
| ---------------- | ------------------ | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **dport**        | int (1–65535)      | `443`           | TCP-порт призначення для прозорого перехоплення                                                                                              |
| **mark**         | int (≥1)           | `0x2333`        | Позначка брандмауера, установлена в `OUTPUT`, за якою виконують зіставлення `ip rule` + `PREROUTING`                                         |
| **onPort**       | int (1–65535)      | `8443`          | Порт, до якого прив’язується прозорий слухач (**IP_TRANSPARENT**)                                                                            |
| **routeTable**   | int (≥1)           | `233`           | Ідентифікатор таблиці маршрутизації на основі політик, що містить маршрут `local 0.0.0.0/0`                                                  |
| **bypassMark**   | int (≥1, ≠ `mark`) | `0x539`         | Позначка обходу сокета (**SO_MARK**), яку проксі встановлює для власних висхідних з’єднань; виключається в `OUTPUT` (запобігання зацикленню) |
| **sudoPassword** | string             | —               | Лише для середовищ робочого столу без root-прав: авторизує встановлення в сховище довіри; ігнорується за наявності root-прав                 |

Для TPROXY **немає змінних середовища** — уся конфігурація передається через
тіло POST-запиту або визначається наведеними вище типовими значеннями.

## §9 Увімкнення через Інспектор трафіку

1. Відкрийте **Інспектор трафіку** (`/dashboard/tools/traffic-inspector`).
2. На панелі режимів захоплення знайдіть кнопку **«Розшифрування TPROXY»** ⚠
   (`src/app/(dashboard)/dashboard/tools/traffic-inspector/components/CaptureModesToolbar.tsx`).
   - Якщо вона **вимкнена** й має підказку «Для розшифрування TPROXY потрібні Linux + права root +
     нативний аддон», нативний аддон недоступний на цьому хості (не Linux,
     немає набору інструментів або аддон не зібрано). Див. [§2](#2-requirements) і [§3](#3-the-native-ip_transparent-addon).
3. Натисніть кнопку. Вона викликає `POST /api/tools/agent-bridge/tproxy` через
   `startTproxyCaptureMode()` (`src/lib/inspector/tproxyCaptureApi.ts`), що:
   створює динамічний ЦС, відкриває прозорий прослуховувач, застосовує правила
   брандмауера та встановлює ЦС у сховище довіри ОС.
4. Під час роботи перемикач стає бурштиновим і показує поточну кількість перехоплень
   (`· <interceptCount>`). Перехоплені запити з’являються у списку запитів із
   `source: "tproxy"`.
5. Натисніть ще раз, щоб зупинити — `DELETE /api/tools/agent-bridge/tproxy` через
   `stopTproxyCaptureMode()` закриває прослуховувач, видаляє ЦС і скасовує
   правила брандмауера.

Стан режиму захоплення (запущено / доступно / кількість перехоплень / порт прослуховувача) надходить
від `GET /api/tools/agent-bridge/tproxy` (`getCaptureStatus()` у
`src/mitm/tproxy/captureManager.ts`). Одночасно працює лише **один** сеанс TPROXY —
спроба запустити другий відхиляється з повідомленням «Режим захоплення TPROXY уже запущено».

## §10 Усунення несправностей

### Перемикач вимкнено

Нативний аддон неможливо завантажити. Переконайтеся, що ви працюєте в Linux, зібрали аддон
(`npm run build:native:tproxy`) і процес може завантажити `transparent.node`.
`isTransparentSocketAvailable()` керує доступністю перемикача; `GET /api/tools/agent-bridge/tproxy`
повертає `available: false`, коли аддон відсутній.

### Нічого не захоплюється

- Переконайтеся, що перехоплюваний процес справді підключається до налаштованого `dport`
  (типове значення — `443`).
- Переконайтеся, що процес довіряє динамічному ЦС. ЦС установлюється як
  `omniroute-tproxy-ca.crt`; для застосунків із власним сховищем довіри (Firefox/Chrome NSS)
  може також знадобитися додати сертифікат до нього.
- Запустіть самоперевірку **Діагностика** AgentBridge (див.
  [`AGENTBRIDGE.md`](../frameworks/AGENTBRIDGE.md)) для перевірки довіри до сертифіката /
  стану сервера.

### Застарілі правила брандмауера після аварійного завершення

`revertTproxy()` є точною зворотною операцією до застосування та ідемпотентною. Зупинення
режиму скасовує правила; якщо OmniRoute було аварійно завершено посеред сеансу, скористайтеся дією
**Відновлення** AgentBridge (`POST /api/tools/agent-bridge/repair`), щоб скасувати залишковий системний
стан (підміна DNS, кореневий ЦС, системний проксі). Правила TPROXY у таблиці `mangle` і маршрут також
автоматично очищуються після перезавантаження.

### Нескінченний цикл / проксі перехоплює власне пересилання

Це випадок запобігання циклу. Переконайтеся, що `bypassMark` відрізняється від `mark` (це
забезпечується перевіркою) і що для пересилання використовується `connectMarked` (саме так у `realForward`).
Див. [§5 Запобігання циклу](#anti-loop-so_mark).
