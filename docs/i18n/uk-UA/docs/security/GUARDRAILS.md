> **Останнє оновлення:** 2026-08-29 — v3.8.51 (походження транскрипту Video Bridge декларується викликачем,
> але ще не перевіряється сервером — уточнено відповідно до #11661)

Запобіжники забезпечують безпеку, дотримання політик і перетворення вмісту на межі
між OmniRoute та вищими провайдерами. Кожен запобіжник може перевіряти (і
за потреби відхиляти, перетворювати або анотувати) корисне навантаження запиту (`preCall`) і
відповіді вищих провайдерів (`postCall`).

Система **працює за принципом fail-open**: якщо запобіжник генерує виняток під час виконання, реєстр
записує помилку й переходить до наступного запобіжника, а не завершує
запит помилкою. Блокування є явним рішенням (`block: true`), а не випадковістю.

### Vision Bridge (`visionBridge.ts`) — міст модальностей PR-1

Перехоплює запити із зображеннями, спрямовані до **моделей без підтримки зору**, і або
перенаправляє весь запит до моделі з підтримкою зору, або замінює частини із
зображеннями текстовими описами, створеними налаштовуваною моделлю з підтримкою зору, перед
викликом вищого провайдера. Це дає змогу провайдерам, що працюють лише з текстом, прозоро обробляти
мультимодальне корисне навантаження.

Процес:

1. Пропустити, якщо цільова модель уже підтримує зір (якщо тільки вона не входить до
   списку примусового застосування мосту `isVisionBridgeForcedModel`).
2. Витягти частини із зображеннями через `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), який делегує роботу **уніфікованому детектору
   медіаданих** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиному
   джерелу істини, спільному з фільтром сумісності комбінацій.
   Витягування обмежено дозволеним списком частин верхнього рівня тих форм,
   які `replaceImageParts` може вставити назад (контракт extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` та Responses API `input_image`. Вкладені збіги й
   форми, що містять лише індикатори, призначені для фільтра комбінацій і ніколи не витягуються.
   Пропустити, якщо нічого не знайдено.
3. Визначити конфігурацію середовища виконання через `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*`
   мають перевагу; застарілі ключі `visionBridge*` залишаються як **резервний варіант на один цикл**
   (вікно відкочування). Якщо міст вимкнено, пропустити до будь-якого обходу медіаданих.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) визначає
   перенаправлення чи опис. Перенаправлення повертає `modifiedPayload`, у якому замінено лише `model`,
   разом із метаданими `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити кількість зображень значенням `maxImages`, скласти контекстний щодо завдання запит,
   перевірити кеш описів, викликати модель з підтримкою зору **паралельно**
   (`Promise.allSettled`) і вставити замість них текстові частини `[Image N]: <description>`.
   Невдалий опис повертає `null`, а початкова частина із зображенням
   **зберігається** (#4012) — за винятком шляху опису для комбінації, коли всі
   спроби опису завершилися невдало: у такому разі для підтвердженого вищого провайдера без підтримки зору
   натомість використовується заглушка `(unavailable — no vision-capable provider connected)` (#8430).
6. Повернути `modifiedPayload` + метадані (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | За замовчуванням | Поведінка                                                                                                                                                                                                                                                                                                                  |
| ---------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔                | Застаріла евристика без змін (#6640/#7204): моделі, що не є комбінаціями, і моделі `auto/` перенаправляються до найкращої моделі з підтримкою зору, якщо лише початкова модель уже не має придатних облікових даних (тоді використовується опис); цілі-комбінації завжди використовують опис.                              |
| `describe` |                  | Завжди описувати — блок перенаправлення повністю пропускається; відповідь завжди надає вибрана користувачем модель.                                                                                                                                                                                                        |
| `reroute`  |                  | Примусове перенаправлення: перевірка збереження моделі з обліковими даними обходиться. Перевірка облікових даних **цілі** перенаправлення все одно застосовується — якщо придатної цілі з підтримкою зору немає, запит переходить до опису, щоб необроблені зображення ніколи не потрапляли до текстового бекенду (#8430). |

Примусові режими виконують раннє завершення **до** запуску автоматичної евристики; поведінка `auto`
побайтово ідентична запобіжнику до PR-1.

#### Контекстний щодо завдання запит опису (`modalityBridgeVisionTaskAware`)

За замовчуванням — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (скорочений до 500 символів) до базового
запиту опису, спрямовуючи опис на те, про що насправді запитав користувач
(патерн codex-vision-proxy), і просить модель з підтримкою зору транскрибувати видимий
текст. Якщо прапорець вимкнено або текст користувача відсутній, базовий запит використовується без змін.

Власний OpenAI-сумісний запит циклу самоопису (`callVisionModelSingle()`
у `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного виклику/провайдера, без прив’язки до будь-якого сигналу
клієнта. Вибірка з низькою деталізацією погіршує точність OCR саме для завдання
транскрибування тексту, яке задає цей промпт, тому сам виклик опису завжди
запитує високу деталізацію незалежно від того, який рівень деталізації
використовував початковий вхідний запит. Це впливає лише на тіло внутрішнього
запиту опису; це не змінює те, як OmniRoute передає власне значення
`image_url.detail` виклику в основному запиті — це значення за замовчуванням
застосовується окремо й лише для виявлених клієнтів OpenCode у
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка
циклу самоопису у форматі передавання Anthropic не має поля `detail` і не
залежить від жодного з цих значень за замовчуванням.

#### Обмеження результату опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає **без обмеження** — опис, повернутий
`callVisionModel()`, передається без змін, зберігаючи наявну поведінку.
Будь-яке значення в діапазоні 100–50000 обрізає опис із додаванням суфікса
`…`, перш ніж він буде вставлений назад у вигляді
`[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` у
`src/lib/guardrails/visionBridge.ts`). Збільшуйте це значення для насичених
деталями завдань OCR, у яких наступній моделі потрібна повна транскрипція;
зменшуйте його, щоб обмежити використання токенів багатослівними моделями
комп’ютерного зору. Поле на панелі керування розташоване на вкладці Vision
у панелі Advanced (`modality-bridge-max-chars` у
`ModalityBridgeVisionTab.tsx`) і підвищує будь-яке значення від 1 до 99 до
мінімуму 100, водночас залишаючи явно вказаний `0` без змін — `0` сам по собі
є допустимим значенням Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не лише
значенням за замовчуванням для стану «не задано».

#### Кеш описів (`modalityBridge/bridgeCache.ts`)

Внутрішньопроцесний кеш LRU + TTL для результатів опису, спільний для всього
процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` із
префіксуванням довжини (без колізій на межах полів). Компонент моделі — це
**налаштована** модель мосту, а не модель, яка фактично надала відповідь:
`callVisionModel` може внутрішньо перемкнутися на резервний варіант, а створення
ключів для кожної спроби призвело б до фрагментації кешу. Невдалі описи ніколи
не кешуються. Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (самоопис/отримання base64)

Коли міст самостійно отримує **віддалене** зображення — для самовиклику опису
Anthropic і перетворення у base64 для формату передавання Claude
(`ensureBase64ImagesForClaudeWire`), в обох випадках через
`fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий URI даних
перед вбудовуванням у запит до моделі комп’ютерного зору передається через
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`). Завеликі зображення
зменшуються до **2048px за довгою стороною** (відповідно до обмеження зміни
розміру, яке OpenAI/Anthropic уже застосовують на сервері), що скорочує обсяг
переданих байтів і затримку, не змінюючи того, що бачить модель комп’ютерного
зору. Для зміни розміру використовується `sharp`, завантажений через динамічний
імпорт: на платформі, де його нативний бінарний файл не вдається завантажити,
`normalizeDataUri()` **ніколи не створює виняток** — натомість він передає
оригінальні байти без змін, тому шлях опису/перетворення в base64 завжди
залишається працездатним. Байти, що не є зображенням (коли отриманий вміст не
вдалося декодувати як зображення), також передаються без змін. Ця нормалізація
обмежена зображеннями, які міст отримує для власного самовиклику, і ніколи не
застосовується до необробленого транзитного корисного навантаження виклику,
відповідно до принципу внесення змін лише за явною згодою (Жорстке правило
№20).

#### Схема налаштувань і міграція

Нові ключі `modalityBridge*` перевіряються за допомогою Zod у
`updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`):
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, трійка
`modalityBridgeCache*` і група `modalityBridgeAudio*`, яку використовує Audio
Bridge. Міграція `141_modality_bridge_settings.sql` копіює наявні застарілі
значення `visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не
перезаписуючи значення `modalityBridge*`, установлене оператором); застарілі
ключі залишаються допустимим резервним варіантом для читання протягом одного
циклу випуску.

#### Заголовок прозорості та статистика

Перетворені через опис відповіді містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створюється `buildModalityBridgeHeader()` у
`modalityBridge/bridgeStats.ts`, додається `withModalityBridgeHeader()` у
`src/sse/handlers/chatHelpers.ts`). Перенаправлені запити **не** отримують
заголовка — корисне навантаження не змінювалося, а заміну моделі вже видно в
полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (автентифікація керування, той самий рівень,
що й для `GET /api/settings`) повертає внутрішньопроцесні лічильники для кожної
модальності `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` і
`video`. `averageLatencyMs` використовує як знаменник `latencySamples`, а не
всі спроби; операція без вимірювання часу не створює штучний зразок із
затримкою нуль мілісекунд. `bridged` залишається зворотно сумісним псевдонімом
для успішних перетворень; невдалі спроби не збільшують його значення.
Лічильники навмисно скидаються під час перезапуску процесу
(це телеметрія, а не облік).

#### Налаштування панелі керування

Спеціальна сторінка панелі керування розташована за адресою
`/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio`
і `Video`, доступні безпосередньо через URL, зберігають параметри запиту під час перемикання значення `tab`.
Вкладка Vision надає налаштування ввімкнення, режиму, вибору моделі (включно з автоматичним
значенням за замовчуванням), формування підказок з урахуванням завдання, розширених обмежень часу очікування, зображення, довжини опису та кешу,
лічильники середовища виконання
і захищений тестовий запит. Вкладка Audio також повністю функціональна: вона надає
налаштування ввімкнення, засіб вибору лише STT-моделей із параметром Auto, обмеження часу очікування й максимальної тривалості кліпу, лічильники
аудіо та тестовий запит `input_audio`. Вкладка Video функціональна: вона відображає
стан середовища виконання FFmpeg/ffprobe — один із чотирьох явних станів інтерфейсу (`unknown`, поки
перевірка виконується або не може завершитися, `restricted` на хості
панелі керування, що не є loopback-хостом, де перевірка пропускається на боці клієнта, `unavailable` після виконання
перевірки й підтвердження відсутності або `available` із версіями FFmpeg/ffprobe) — зберігає
налаштування ввімкнення, моделі, кадрів, відео та обмежень часу очікування, фільтрує засіб вибору моделей, залишаючи моделі
з підтримкою комп’ютерного зору, і надає лічильники відео.

Колишня картка Vision Bridge в налаштуваннях ШІ тепер є посиланням для сумісності на
нову сторінку; вона більше не містить другої копії форми. Media Providers також
пов’язує робочі процеси Image-to-Text і Speech-to-Text із відповідними вкладками Modality
Bridge, не видаляючи наявний інтерактивний майданчик Speech-to-Text.

**Обхід контролю допуску для self-loop:** коли виклик опису спрямовується через
власний self-loop OmniRoute `/v1` (нестандартну модель постачальника), підзапит надсилає
`x-omniroute-admission-bypass: internal` і автентифікується за допомогою визначених
облікових даних self-loop — локального маркера `sk_omniroute` в локальному режимі або
налаштованого оператором ключа середовища `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб
розгортання з `REQUIRE_API_KEY=true` усе ще могли виконувати виклик опису. Обхід
дозволяється лише для цих точних облікових даних, тому зовнішні клієнти не можуть використовувати
цей заголовок для пропуску контролю допуску.

Застарілі значення за замовчуванням містяться в `src/shared/constants/visionBridgeDefaults.ts`;
нові значення за замовчуванням для режиму, урахування завдання й кешу, а також засіб визначення налаштувань містяться в
`src/shared/constants/modalityBridgeDefaults.ts`. Запобіжник надає параметр конструктора
`deps`, щоб тести могли підставляти фіктивні реалізації `getSettings` і
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює запити чату, що містять аудіо, до того, як вони досягнуть цільового сервісу, про який
невідомо, чи приймає він аудіовхід. Він ніколи не перенаправляє запит чату: аудіочастини
транскрибуються через наявну OpenAI-сумісну multipart-кінцеву точку, а
вибрана модель чату продовжує роботу з текстовими транскриптами.

Послідовність:

1. Визначити `supportsAudio` через `getResolvedModelCapabilities()`. Явні
   метадані реєстру постачальників мають пріоритет, потім ідуть статичні метадані моделі, а далі —
   синхронізоване значення `modalities_input`. Оголошений список вхідних даних без `audio` дає `false`; за
   відсутності даних про можливості залишається `null`. І `false`, і `null` активують
   консервативний міст, тоді як `true` обходить його.
2. Визначити налаштування `modalityBridgeAudio*` і витягти придатні до заміни аудіочастини верхнього рівня
   з кожного повідомлення за допомогою спільного детектора `detectMediaParts()`.
   Підтримувані формати передавання: OpenAI `input_audio`, `audio_url` і
   `source.media_type: "audio/*"`. Вкладене аудіо виявляється для маршрутизації, але не
   видаляється під час заміни. Обсяг роботи обмежується `modalityBridgeAudioMaxClips`;
   наступні частини залишаються без змін.
3. Використати налаштовану пару `provider/model` або дозволити `selectAudioBridgeModel()` пройти
   `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу й вибрати першу
   модель із придатними активними обліковими даними постачальника.
4. `callAudioTranscription()` перетворює аудіо у форматі base64/data URI на multipart-файл
   `file` або завантажує віддалений `audio_url` через захист вихідних з’єднань лише з публічними адресами,
   із закріпленням DNS і обмеженням у 25 МБ. Потім він POST-запитом надсилає файл і вибрану
   модель до локального self-loop `/v1/audio/transcriptions`, автентифікуючись за допомогою
   `resolveSelfLoopBearer()`. Наявний маршрут транскрибування виконує звичайний
   пошук облікових даних, обробку періодів очікування/обмежень частоти запитів і диспетчеризацію постачальника.
5. Успішні виклики замінюють відповідні частини на `[Audio N]: <transcript>`. Виклики
   виконуються через `Promise.allSettled`: окрема помилка зберігає початкову
   аудіочастину (контракт #4012). Якщо всі виклики завершуються невдало, а для цільового сервісу доведено
   `supportsAudio === false`, частини перетворюються на
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   невідомого цільового сервісу (`null`) результат, у якому всі виклики завершилися невдало, залишається без змін. Цільовий сервіс із підтвердженою
   підтримкою лише тексту та без придатних облікових даних STT отримує таку саму явну
   заглушку без виконання мережевого виклику.

Успішні транскрипти використовують спільний для всього процесу LRU/TTL-кеш Modality Bridge.
Ключ поєднує посилання на аудіо, стабільну мітку операції `audio-transcription`
і вибрану STT-модель; невдалі результати ніколи не кешуються. Спроби обробки аудіо оновлюють
спільні лічильники `bridged`, `cacheHits`, `failures` і `lastUsedAt`.
Перетворені відповіді містять
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені
запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                          | За замовчуванням | Діапазон        |
| ----------------------------- | ---------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`           | —               |
| `modalityBridgeAudioModel`    | `""`             | Auto або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`          | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`              | 1–10            |

Спільний кеш, як і раніше, контролюється параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` і `modalityBridgeCacheMaxEntries`.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює відеочастини верхнього рівня в `messages` Chat Completions і `input`
Responses API до виклику цільової системи без відомої нативної підтримки відео.
Підтримувані форми: `input_video`, `video_url`, `video_source`, URL-адреси HTTPS
і URI даних `data:video/*;base64,...`. Звичайні імена файлів у тексті не
вважаються відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запиту,
перевірку можливостей/політик, агрегацію на рівні окремого запиту та корисне
навантаження відповіді. Обробка окремого відео — отримання, кешування повного
результату, опис послідовності кадрів (з об’єднанням будь-якої заявленої
викликачем транскрипції аудіо), а також метрики/переривання/очищення для кожної
спроби — прихована за `processVideoPart` у `videoBridgePipeline.ts`, яка
викликається один раз для кожної відеочастини в циклі `preCall`. Цей модуль
також визначає явні межі портів `VideoMediaBrokerPort` (отримання байтів і
вилучення вибіркових кадрів), `VideoAudioTranscriptionPort` (об’єднання
заявленої викликачем транскрипції аудіо з підписами вибіркових кадрів) і
`VideoDrilldownPort` (межа збереження деталізації кадрів; ще не підключена до
`processVideoPart` — наразі записи деталізації створює лише окремий маршрут
`/api/modality-bridge/video/drilldown`).

Публічний шлях запиту `/v1` ніколи не імпортує й не викликає підпроцес.
Віддалені відео завантажуються з обмеженням 50 MiB; вбудовані відео base64
мають консервативне обмеження 36 MiB декодованих даних на відео, щоб оболонка
моделі/повідомлень/фреймінгу залишалася в межах публічного ліміту приймання
JSON-запитів у 50 MiB. Довжина вбудованих даних і оцінка декодованого розміру
перевіряються до виділення пам’яті. HTTPS є обов’язковим для початкової
віддаленої URL-адреси та кожного перенаправлення із застосуванням наявного
захисту для лише публічних вихідних з’єднань із фіксацією DNS. Потім байти
перетинають точну внутрішню межу брокера
`POST /api/modality-bridge/video/extract`. Цей маршрут має позначки
`LOCAL_ONLY` і `SPAWN_CAPABLE`, приймає лише автентифікований на рівні процесу
запит через довірений loopback-інтерфейс і ніколи не приймає URL-адресу, шлях
файлової системи, виконуваний файл або список аргументів. Конвеєр обмеження
розміру тіла API та інкрементальний зчитувач тіла обробника незалежно
застосовують обмеження вхідних даних брокера у 50 MiB. Його обмежена черга
виконує одне вилучення за раз, допускає чотири завдання в очікуванні та обмежує
їхні вхідні дані 100 MiB.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований список
дозволених форматів виключає формати списків відтворення та маніфестів. Для
дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV типово
залишаються вимкненими, а фіксована команда не вмикає їх. І `ffprobe`, і
`ffmpeg` використовують список дозволених протоколів, що містить лише `file`,
один потік, фіксовані масиви аргументів, не використовують оболонку, а
виконувані файли визначаються через `PATH`. Потоки обкладинок із прикріпленими
зображеннями не вважаються кандидатами для відтворення. Усі потоки, придатні
для відтворення, мають відповідати обмеженням; перед детермінованим резервним
вибором потоку з найменшим індексом перевага надається явно визначеному потоку
за замовчуванням. Відео обмежені тривалістю 600 секунд, 8 192 пікселями на
вимір і 33 554 432 пікселями джерела. FFmpeg вибирає 1–16 JPEG-кадрів у
середніх точках, зменшує довгу сторону щонайбільше до 1 024 пікселів без
збільшення менших вхідних даних і ніколи не отримує URL-адресу. Типовою
політикою вибірки є `uniform`. Необов’язкові політики `scene_aware` та
експериментальна `segment_aware` виконують один додатковий фіксований прохід
FFmpeg над уже перевіреним локальним потоком, вибирають обмежені часові позначки
сцен `showinfo` і детерміновано повертаються до тих самих рівномірних середніх
точок у разі збою детектора, тайм-ауту, некоректного виводу або порожнього
набору кандидатів. Режим з урахуванням сегментів розподіляє вибірки середніх
точок пропорційно перевіреним інтервалам сцен; докладні відомості про докази
для режиму з урахуванням сегментів і резервну поведінку наведено нижче. Жорстке
обмеження у 16 кадрів застосовується після вибору в кожній політиці. Якщо запит
з урахуванням сцен має бюджет лише в один кадр, використовується рівномірна
середня точка активного повного відео або вікна фокусування, а у звіті
вказується `policyEffective: uniform`: один вибраний кадр сцени не може
зберегти обидві часові межі. Викликач може необов’язково надати скінченне вікно
фокусування (`start`/`end` у секундах); межі обмежуються тривалістю медіа,
обернені або нескінченні вікна відхиляються, а всі політики вибірки
застосовуються лише в межах нормалізованого інтервалу. Отримане вікно
включається до метаданих вибірки та до префікса ненадійного опису, щоб подальші
моделі могли відрізнити сфокусований уривок від повної часової шкали.

Семантичний фокус підписів є окремим явним налаштуванням. Типовий режим аналізу
`full` зберігає наявну підказку для кадрів і ніколи не передає текст запиту
моделі підписів. У режимі `focused` міст зчитує лише останній непорожній
створений користувачем `text`/`input_text` із того самого контейнера Chat або
Responses, нормалізує його до NFC, згортає керівні символи та пробіли й обмежує
до 500 кодових точок Unicode. Порожній результат спричиняє повернення до точної
підказки `full`. Придатна підказка серіалізується як JSON у спеціальному блоці
ненадійного користувацького контексту й може лише визначати пріоритет
спостережуваних деталей; вона не може перевизначити окреме попередження про
заборону виконувати інструкції, видимі або чутні в медіа. Текстовий фокус ніколи
не виводить `start`/`end` і не змінює часовий семплер.

#### FU-07 структурні докази сегментів

`segment_aware` використовує один обмежений прохід попереднього аналізу вже
перевіреного локального відеопотоку. Фіксований ланцюжок фільтрів спочатку
масштабує відео до щонайбільше 320 пікселів завширшки, виявляє зміни сцен і
завмерлі інтервали, а потім відбирає 1 кадр на секунду для визначення розмиття,
середньої яскравості та просторової/часової інформації. Прохід обмежений 600
структурними вибірками, одним потоком FFmpeg/фільтра, тими самими списками
дозволених лише `file` протоколів і контейнерів, обмеженням виводу процесу в
1 MiB і щонайбільше 30 секундами в межах спільного механізму
переривання/кінцевого терміну брокера. Він ніколи не приймає команду, фільтр,
шлях або URL-адресу із запиту.

Структурні значення є детермінованими свідченнями вибірки, а не семантичним розумінням відео. Вони не визначають об’єкти, дії, субтитри, мовлення чи наміри користувача. Межі сцен і завмирань утворюють сегменти; покриття завмирань, розмиття, експозиція, просторова деталізація та часові зміни впливають лише на розподіл наявного бюджету в 1–16 кадрів. Повністю завмерлий сегмент обмежується одним кадром, тоді як незавмерлі сегменти конкурують за решту бюджету. Коли кількість меж перевищує кількість кадрів, зберігається рівномірне покриття часової шкали, щоб швидкі ранні монтажні склейки не могли приховати довгий кінцевий сегмент. Межі сцен, що потрапляють у межі 1-секундної роздільної здатності аналізу відносно межі завмирання, об’єднуються.

Відсутні фільтри, некоректні або порожні свідчення, помилка детектора чи завершення обмеженого часу очікування попереднього аналізу призводять до безпечного переходу до точної політики рівномірного вибору середніх точок. Переривання з боку викликувача чи спливання граничного терміну брокера не призводить до такого переходу: воно завершує активний підпроцес, запобігає подальшому вилученню кадрів, а приватне тимчасове дерево видаляється у `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні тестові дані FFmpeg для оцінювання скорочення кількості викликів створення підписів після дедуплікації, розподілу бюджету за щільного руху, свідчень розмиття/експозиції/SI-TI, швидких монтажних склейок із довгим кінцевим сегментом і хибнопозитивних спрацьовувань під час поступового згасання. Він реєструє фактичний час попереднього аналізу, а за наявності `/usr/bin/time` — процесорний час дочірнього процесу та піковий RSS. Його перевірки якості є лише структурними оракулами. Якість реальної моделі створення підписів залишається в стані `HOLD`, оскільки цей тестовий стенд не має авторизованої кінцевої точки чи зафіксованого оцінювача. Грошова економія також залишається в стані `HOLD`, якщо `--caption-cost-per-call-usd` не надає явну додатну оцінку вартості одного виклику; скрипт ніколи не вигадує жоден із цих результатів.

Розмір кожного кадру обмежено 4 MiB, сукупний розмір усіх необроблених кадрів — 23 MiB, а серіалізованої відповіді брокера — 32 MiB. Приватний тимчасовий каталог видаляється у `finally`. OmniRoute не постачає FFmpeg у комплекті та не приймає користувацький шлях до виконуваного файла. Перед створенням підписів міст застосовує консервативний прохід візуальної дедуплікації: кожне зображення JPEG зменшується до буфера відтінків сірого 16×16 і порівнюється лише з останнім збереженим кадром. Якщо запитаний бюджет підписів перевищує один кадр, вилучення надає обмежений пул кандидатів, розмір якого не перевищує подвоєний бюджет і в жодному разі не перевищує 16 кадрів. Запитане обмеження застосовується лише після дедуплікації, причому під час остаточного проріджування зберігаються перший і останній вибрані кандидати, якщо бюджет становить щонайменше два кадри. Версіонована політика `grayscale-16x16-mean-cells-v2` використовує більше зі значень: середню зміну яскравості або частку комірок мініатюри, нормалізована зміна яких становить щонайменше 0.05. Порогом дублювання є стала 0.04, вибрана заради передбачуваності, а не надана як параметр виконання. Цей вторинний сигнал високої контрастності зберігає невеликі рухи та зміни видимого тексту, які може приховати порівняння лише за середнім значенням. Помилки компаратора чи декодера призводять до безпечного збереження покриття. Вихідні метадані окремо відображають вилучених кандидатів, успішно використані кадри та відкинуті візуальні дублікати.

Явно позначена частина відео може запитувати контактний аркуш із часовими мітками. Міст створює JPEG-сітку щонайбільше з 4 стовпців і 16 кадрів. У кожній 512-піксельній комірці часова мітка джерела вбудовується у висококонтрастну нижню смугу, а ті самі часові мітки залишаються в текстових метаданих для подальшого зіставлення й аудиту. Розмір повного JPEG залишається обмеженим 32 MiB. Якщо `sharp` не може декодувати чи скомпонувати сітку, міст повертається до окремих кадрів JPEG; переривання клієнта все одно поширюється на операцію з аркушем.

Свідчення для просування навмисно відокремлені від синтетичного мікротесту продуктивності компонування. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає версіонований за схемою A/B-тестовий стенд для реальних моделей комп’ютерного зору, сумісних з OpenAI. Він вимірює повідомлену постачальником кількість токенів, наскрізну фактичну затримку (включно з компонуванням аркуша), кількість викликів моделі та збереження фактів, визначених у маніфесті. Необроблені відповіді моделі не записуються у звіт; зберігаються лише SHA-256-дайджести та ідентифікатори зіставлених фактів. Тестовий стенд не виконує мережевих чи платних викликів моделі, якщо не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без такого явного реального запуску його машинозчитуваний вердикт залишається `HOLD`; самі лише синтетичні вимірювання корисного навантаження та кількості викликів не є свідченням для просування.

Викликувачі можуть додати необов’язковий масив `transcript.cues` до підтримуваної частини відео, якщо вони вже мають синхронізований текст. Кожна репліка повинна містити `text`, скінченний інтервал `start`/`end` у межах визначеної тривалості та значення `source` з білого списку (`client`, `embedded` або `audio-bridge`); значення `confidence` за замовчуванням дорівнює `1` і повинно залишатися в межах від `0` до `1`. Точні дублікати реплік згортаються. OmniRoute ніколи не запускає транскрибування на основі цих метаданих: перевірені репліки копіюються до описаного результату разом із джерелом, рівнем упевненості та інтервалом і відображаються як ненадійні спостереження поряд із підписами кадрів. Некоректний текст, текст поза допустимим діапазоном або текст без походження відхиляється, а не змішується з потоком підписів. Поле `source` наразі декларується викликувачем, а не перевіряється сервером: OmniRoute забезпечує належність значення до одного з трьох дозволених рядків, але поки що криптографічно не підтверджує, що мітка `embedded` або `audio-bridge` справді походить від вилучення, виконаного під керуванням сервера. Вважайте `source` ненадійною підказкою, доки таку перевірку не буде реалізовано; не ґрунтуйте на ньому рішення щодо авторизації.

Досвідчений викликач може надати вже авторизовану доріжку `audioTranscript`
для того самого відео. Рівень об’єднання виконує візуальні й аудіоспостереження в межах
єдиного крайнього терміну та сигналу переривання, упорядковує їх на спільній часовій шкалі, згортає
точні дублікати й повертає частковий результат, якщо успішною є лише одна сторона.
Недійсний `audioTranscript` призводить до такого часткового результату — візуальний
опис зберігається, а аудіогілка записує санітизований код помилки —
замість збою обробки всього відео. Доступність кожної гілки, ознака часткового результату
та санітизовані коди помилок зберігаються в описаному результаті, у метаданих
захисних обмежень (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), у метаданих кешу результатів і в лічильниках
об’єднання мосту. Стандартний шлях Video Bridge не викликає перетворення мовлення на текст
і не завантажує другу копію медіафайлу; без цієї явно наданої доріжки він залишається
лише відеорежимом.

**Зберігання транскрипту (#12150 P1).** Це застосовується автоматично щоразу, коли
Video Bridge (який сам потребує явного ввімкнення) відтворює репліку транскрипту — окремої
ознаки зберігання немає. Коли запит відтворює будь-яку репліку транскрипту (оголошений викликачем
`transcript` або об’єднаний `audioTranscript`), захисне обмеження позначає його як
`videoBridgeObserved` і створює редаговану тінь відеоопису —
ідентичне відтворення, у якому довільний текст тіла кожної репліки замінено на
`[redacted-video-transcript]`; вона створюється шляхом підстановки структурованого поля репліки
до складання рядка (а не шляхом аналізу сплощеного тексту, тому жоден вміст репліки —
зловмисний або звичайний, зокрема тіла, що містять `]`, як-от
`[inaudible]`/`[music]`, — не може зберегтися). У збереженому тілі запиту журналу викликів
кожна похідна від відео текстова частина замінюється цією редагованою тінню за збігом
вмісту; прив’язка `fullText` повторно зчитується із завершеного корисного навантаження
захисного обмеження перед викликом, тому зіставлення залишається успішним після того, як подальші
ланцюгові захисні обмеження (маскувальники PII та облікових даних із пріоритетами 10/95)
перезапишуть текст опису на місці, а також після того, як упровадження системного
промпту/передавання/пам’яті змінить форму масиву повідомлень. Тіло, надіслане вище за потоком
до моделі, не змінюється. Спостережуваний запит також не заповнює довготривалу Memory
(вилучення як із запиту, так і з відповіді пропускається), тому власна відповідь моделі
не може відтворити текст транскрипту в Memory.

Поверхні зберігання, що досі залишаються відкритими й відстежуються для подальшої роботи
(**P2**, #12430): необроблений знімок клієнтського запиту до застосування захисних обмежень
в артефакті докладного журналу; продовження `previous_response_id` із відмовою за замовчуванням;
внутрішні пересилання похідних промптів, які вбудовують транскрипт у синтезований рядковий промпт
(етапи конвеєра, передавання контексту); а також тіло відповіді / копія семантичного кешу
відповіді моделі, яка цитує транскрипт. Це поверхні класу необроблених даних/відповідей або
поверхні з явним увімкненням поза межами P1, що охоплює збережене тіло запиту + Memory.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою,
автентифікованою через loopback/токен кеш-підсистемою. Кожна операція також потребує
канонічного непрозорого ID суб’єкта. Перш ніж увімкнути робочий викликач, він має
виводити цей ID з автентифікованого орендаря й ніколи не пересилати значення,
вибране клієнтом. Ключі кешу пов’язують цього суб’єкта з канонічними ID сеансу та
посилання на відео, зберігають лише похідні від SHA-256 ключі й обмежують як читання,
так і видалення тим самим суб’єктом. Кеш зберігає щонайбільше 16 похідних кадрів JPEG
на запис, вилучає їх через десять хвилин і підтримує обмежене читання `start`/`end`
або явне видалення сеансу.

Для кожного суб’єкта встановлено обмеження в 16 записів і 64 MiB канонічних даних JPEG.
Ці обмеження незалежні від глобальної межі у 64 записи/256 MiB: тиск на квоту суб’єкта
витісняє лише найдавніше використані записи цього суб’єкта, перш ніж розглядатиметься
глобальне витіснення LRU. Прострочені записи вилучаються з обліку як суб’єкта, так і
глобального обліку під час активності кешу, тоді як скасування та помилка валідації не
фіксують часткову заміну.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, дані не у форматі JPEG, пошкоджені або
усічені JPEG, а також JPEG, що спричиняють попередження під час обмеженого повного декодування
зображення за допомогою `sharp`. Кожне прийняте зображення перекодовується в канонічний JPEG,
ширина й висота визначаються з декодованих байтів без довіри до полів викликача, а всі кінцеві
поліглотні байти відкидаються, а не зберігаються. До обох квот зараховується лише обмежений
канонічний стиснений буфер. Обмеження передавання JSON включає накладні витрати Base64 для
верхньої межі декодованих вхідних даних у 32 MiB. Кожна
збережена похідна сутність фіксує перевірений формат/роздільну здатність JPEG, політику
вибірки, версію формування, час створення, обчислений сервером хеш вмісту, хешоване батьківське
посилання та хеш батьківського вмісту від довіреного викликача. Скасування перевіряється
між асинхронними фазами декодування/хешування до атомарної фіксації в кеші.

Ця частина ще не підключає робочого виробника до маршруту й не
забезпечує вибір варіантів із різною роздільною здатністю. Тому прозорий шлях запиту
Video Bridge не створює додаткового навантаження, тоді як прив’язане до орендаря виведення
суб’єкта та повний життєвий цикл FU-08 із кількома роздільними здатностями залишаються
явно визначеною подальшою роботою, а не задокументованою завершеною функціональністю.

Кадри послідовно отримують описи за допомогою налаштованої моделі Video. Порожнє
перевизначення Video успадковує налаштування Vision; якщо обидва значення порожні, автоматичний
маршрутизатор Vision вибирає ефективну модель із підтримкою зору. Успішні описи
замінюють оригінальну частину стабільним префіксом `[Video description:`, який також
позначає текст як ненадійне спостереження, отримане з медіаданих, і вказує подальшим
моделям не виконувати інструкції, знайдені в медіа. Ключі кешу описів кадрів
містять байти JPEG, підказку, позначку часу та ефективну модель; кешуються лише успішні
описи. Записи кешу зберігають фактичну модель-виробника успішного результату,
зокрема резервну модель; міст повідомляє `mixed`, коли різні кадри
були оброблені різними моделями. У разі влучання в кеш повторно використовується ідентичність цього виробника,
а не перепризначається відповідно до запитаного плану маршрутизації. Кеш результатів
для всього відео має ключ, сформований з усіх вхідних даних, що змінюють результат, — підказки, ефективної
моделі, політики вибірки, кількості кадрів, режиму семантичного аналізу, відбитка SHA-256
нормалізованої підказки щодо фокуса, вікна фокуса, `transcript`,
`audioTranscript` і прапорця контактного аркуша, — тому зміна будь-якого з цих
параметрів призводить до промаху кешу, а не повторного використання застарілих даних. Версія політики
візуальної дедуплікації, порогове значення та обмежена кількість кадрів-кандидатів також явно вказуються в
ключі й метаданих кешу результатів; отже, зміна політики не може повторно використати застарілий
опис усього відео. Метадані кешу результатів v4 зберігають режим і
відбиток, але ніколи не зберігають необроблене завдання користувача. Метадані захисного механізму повідомляють як
запитаний, так і ефективний режими аналізу; запитаний режим `focused` без
придатного тексту користувача позначається як фактично `full`.

Захисний механізм витягує кожну підтримувану відеочастину, але описує не більше ніж
`modalityBridgeVideoMaxVideos`. Для цільової моделі, щодо якої підтверджено
`supportsVideo === false`, невдалі відео та відео понад ліміт перетворюються на явні безпечні
текстові маркери, щоб необроблене відео не зберігалося. Коли можливості невідомі, ці частини
залишаються без змін. Цільові моделі з `supportsVideo === true` оминають міст.
Сигнал переривання клієнтського запиту поширюється на завантаження, чергу брокера,
підпроцеси та виклики створення описів; переривання зупиняють обробку між відео й ніколи не допускають
аварійного пропускання необроблених медіаданих.

| `modalityBridgeVideoSamplingPolicy` | `"uniform"`     | `uniform`, `scene_aware` або пропорційний `segment_aware`; у разі збою детектора використовується `uniform`              |
| `modalityBridgeVideoMaxVideos`      | `1`             | 1–4                                                                                                                      |
| `modalityBridgeVideoTimeout`        | `120000`        | 1000–120000 мс                                                                                                           |

Збережені застарілі значення тайм-ауту Video понад 120 секунд обмежуються
кінцевим терміном брокера; нові спроби записати налаштування понад цей ліміт відхиляються.
`GET /api/modality-bridge/video/runtime` вимагає надійно засвідченої локальності loopback
до автентифікації або перевірки середовища виконання, а потім вимагає автентифікації
керування. Він повертає лише `available`, санітизовані версії FFmpeg/ffprobe та фіксовану
причину недоступності середовища виконання. Внутрішня кінцева точка видобування не є
публічним API для завантаження: переповнення черги повертає `503` разом із `Retry-After`, від’єднання
викликувачем повертає `499`, а фіксований кінцевий термін брокера — `504`. Перетворені відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до центрального заголовка
`x-omniroute-modality-bridge`, не видаляючи сегменти Vision або Audio.

### Маскувальник PII (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує корисне навантаження, обходить `system`, `messages`, `input` і
  `prompt` (включно з елементами у вигляді звичайних рядків) та застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII редагуються у вихідному
  корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою щодо ін’єкцій у підказки). Коли редагування вимкнено, виклик записує кількість
  виявлень без переписування вмісту.
- **`postCall`** виконує глибоке клонування відповіді, запускає `sanitizePIIResponse()` разом із
  маскувальником структури Responses API (`maskResponsesOutput` — охоплює
  `output_text` і `output[].content[].text`). Якщо відбувається будь-яке редагування,
  змінена відповідь замінює оригінальну.

Захисний механізм ніколи не блокує; він лише додає анотації (`meta.detections`,
`meta.redacted`) або переписує дані.

### Ін’єкція в підказку (`promptInjection.ts`)

Виявляє зловмисні структури у вмісті, наданому користувачем, і застосовує
налаштовану політику. Поведінка визначається змінними середовища та параметрами
конструктора:

| Налаштування     | Змінна середовища                                                                                           | Типове значення | Ефект                                                                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`          | Якщо `false`, захисний механізм завершує роботу достроково.                                                                                                                                                                      |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`          | Політика щодо ін’єкцій: `block`, `warn` або `log`. (`redact` підтримується для зворотної сумісності, але **не** видаляє текст ін’єкції; перезапис персональних даних у запиті контролюється параметром `PII_REDACTION_ENABLED`.) |
| Поріг блокування | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`          | Мінімальний рівень серйозності, необхідний для блокування. За типових налаштувань рівень Medium призначений лише для спостереження.                                                                                              |

**Пріоритет режимів** (`getMode`): `options.mode`, переданий викликачем →
**перевизначення прапорця функції в БД** `INJECTION_GUARD_MODE` (Панель керування → Налаштування →
Прапорці функцій) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Отже, перевизначення з панелі керування має пріоритет над змінними середовища, тому інтерфейс
Прапорців функцій керує активним захисним механізмом у реальному часі (без перезапуску). Читання з БД є відмовостійким:
якщо виникає помилка, захисний механізм повертається до поведінки на основі змінних середовища, а якщо
перевизначення не задано, поведінка ідентична визначенню лише за змінними середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір детекторів,
   що використовується в інших частинах конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` і
   `markdown_system_block`, обидва з рівнем серйозності `high`).
3. Необов’язкові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази
   або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Request rejected:
suspicious content detected" }`. У режимах `warn`/`log` захисний механізм записує подію в журнал, але
дозволяє виклик. Спільна допоміжна функція `evaluatePromptInjection()` також експортується
для викликачів, яким потрібно оцінювати промпти без використання реєстру.

**Обмеження сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об’єднаного тексту промпту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у
`src/shared/utils/inputSanitizer.ts`. І `detectInjection()`, і
`evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
циклу перевірки шаблонів. Директиви ін’єкцій розташовуються ближче до початку вхідних даних, тому це
обмежує навантаження регулярних виразів на ЦП/GC для корисних навантажень обсягом у сотні КБ без послаблення виявлення (див.
#3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Працює на **обох** етапах, останнім у типовому ланцюжку (пріоритет `95`). Редагує
відомі шаблони API-ключів / секретних токенів у вихідному корисному навантаженні (вмісті
повідомлень, аргументах викликів інструментів, результатах інструментів) **і** у відповіді постачальника, щоб
облікові дані, вставлені в промпт (або повернуті результатом інструмента), не потрапили
до зовнішнього постачальника або назад до клієнта.

- **Лише за явної згоди**, відповідно до тієї ж домовленості, що й для редагування персональних даних (поруч із Жорстким правилом №20):
  вимкнено, якщо `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true` не задано. Коли функцію вимкнено, захисний механізм нічого не робить —
  він ніколи не блокує й не перезаписує дані.
- `redactCredentials()` обходить усе дерево корисного навантаження/відповіді (`walkValue()`,
  із захистом від забруднення прототипу та циклів за допомогою `WeakSet`) і замінює збіги
  заповнювачем `[REDACTED:<type>]`, клонуючи лише ті гілки, які
  фактично змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі постачальників LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), хмарні
  ключі (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення, що містять облікові дані (`mongodb://user:pass@...` тощо), а також
  універсальний шаблон значення заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі у формі заголовків (`authorization`, `x-api-key`, `api-key`,
  `apikey`) редагуються структурно (лише значення, зі збереженням префікса схеми на кшталт
  `Bearer `/`Basic `), а не за допомогою універсального текстового регулярного виразу.
- Захисний механізм ніколи не блокує; він лише перезаписує (`modifiedPayload` /
  `modifiedResponse`) і додає анотації (`meta.credentialsRedacted`, `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true негайно зупиняє ланцюжок
  message?: string; // відображається в разі блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається методом preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається методом postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Захисний механізм сигналізує про «відсутність змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, яке передається ланцюжком наступним захисним механізмам.
`signal?: AbortSignal` передає життєвий цикл виклику до захисних механізмів. Переривання запиту є навмисним винятком із поведінки fail-open: медіамости припиняють роботу та очищують ресурси, не відновлюючи необроблені медіадані для цільової системи, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає захисний механізм (або замінює його за нормалізованим ім’ям) і
  повторно сортує механізми за зростанням `priority`.
- `clear()` / `list()` — адміністративні допоміжні методи.
- `runPreCallHooks(payload, context)` — перебирає активні захисні механізми, послідовно
  передає корисне навантаження через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — такий самий процес на боці відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищує стан і за потреби
  повторно реєструє механізми за замовчуванням для надійної ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`,
де `results` — це масив записів `GuardrailExecutionResult`, які містять
поля `blocked`, `skipped`, `modified`, `error` і `meta` для кожного захисного механізму,
що корисно для трасування.

### Вимкнення захисних механізмів для окремого запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` збирає
дедуплікований список імен захисних механізмів, які слід пропустити для поточного
запиту. Джерела (усі необов’язкові та об’єднуються):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` у тілі запиту (на верхньому рівні)
- `metadata.disabledGuardrails` у тілі запиту
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий
  `x-disabled-guardrails`)

Значеннями можуть бути масиви рядків або рядки, розділені комами; імена
нормалізуються до kebab-case у нижньому регістрі (`pii_masker` → `pii-masker`). Результат
передається через `context.disabledGuardrails` до реєстру, який пропускає
відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` і
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` формує список пропусків на основі ключа API, тіла запиту
   та заголовків.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускає запобіжники в порядку
   зростання пріоритету:
   - Вимкнені запобіжники позначаються як `skipped`.
   - `preCall` кожного запобіжника може змінити корисне навантаження через `modifiedPayload`.
   - Перший результат із `block: true` достроково припиняє ланцюжок, і обробник повертає
     відповідь про відхилення запиту запобіжником.
3. Корисне навантаження (можливо, змінене) надходить до комбінованої маршрутизації та
   передається до зовнішнього сервісу.
4. Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
   запускає той самий ланцюжок для відповіді. `block: true` на цьому етапі відкидає відповідь
   зовнішнього сервісу.

Запобіжники, що породжують винятки, реєструються з `error: <message>`, а подія журналюється через
`logger.warn`, але ланцюжок продовжує виконання — це передбачена архітектурою відкрита відмова.

## Конфігурація

Змінні середовища, які зчитують вбудовані запобіжники:

| Змінна                                | Використовується в         | Ефект                                                                                                         |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | Установіть `false`, щоб повністю вимкнути виявлення.                                                          |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | Політика щодо ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не змінює текст ін'єкції.      |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | Режим захисту від ін'єкцій; також прапорець функції в БД, який **перевизначає** змінні середовища (БД > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | Мінімальний рівень серйозності, який відхиляє `MODE=block`: `high` (типово), `medium` або `low`.              |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                   |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | Якщо встановлено `true`, персональні дані в запиті редагуються (незалежно від режиму ін'єкцій).               |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (у відповіді) | Керує поведінкою маскувальника на боці відповіді.                                                             |

Запобіжники Modality Bridge зчитують конфігурацію під час виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища. Основними ключами для Vision є
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` і
`modalityBridgeCacheMaxEntries`. Застарілі ключі
`visionBridge*` підтримуються лише як задокументований резервний варіант читання
протягом одного циклу; панель керування записує основні ключі. Значення за замовчуванням і механізм
резервного визначення містяться в `src/shared/constants/modalityBridgeDefaults.ts`, а застарілі
константи збережено в `src/shared/constants/visionBridgeDefaults.ts`.

Для Audio використовуються `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` і `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Для Audio немає резервного використання застарілих ключів, оскільки ці
ключі були додані разом зі схемою Modality Bridge.

Для Video використовуються `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` і
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
За замовчуванням цю функцію вимкнено, оскільки FFmpeg/ffprobe є необов'язковими операційними
залежностями, а створення описів кадрів збільшує затримку та вартість використання моделі.

## Власні захисні механізми

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1. Створіть `src/lib/guardrails/myGuardrail.ts`, розширивши `BaseGuardrail`.
2. Реалізуйте `preCall` та/або `postCall`.
3. Або зареєструйте під час імпорту (додайте через `registerDefaultGuardrails`), або
   викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
   будь-який попередній захисний механізм із такою самою нормалізованою назвою.
4. Додайте тести до `tests/unit/` (наявні приклади:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб починати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише захисні механізми, які тестуються. Vision Bridge підтримує впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
аналогічні точки підміни для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних і транскрибування. Завдяки цьому тести можуть перевіряти обидва потоки
без доступу до БД або мережі.

## Дивіться також

- `src/lib/guardrails/` — реалізація
- `src/shared/utils/inputSanitizer.ts` — спільний детектор, що забезпечує
  виявлення ін’єкцій у промпти та маскування PII
- `src/shared/constants/visionBridgeDefaults.ts` — типові налаштування Vision Bridge і
  список моделей із примусовим використанням моста
- `src/shared/constants/modalityBridgeDefaults.ts` — спільні типові налаштування виконання Vision/Audio
- `docs/architecture/RESILIENCE_GUIDE.md` — ортогональний рівень (автоматичний вимикач, періоди очікування)
- `docs/reference/ENVIRONMENT.md` — повний довідник змінних середовища

## Покриття маршрутів захистом від ін’єкцій і red-team-тестування (Етап 8 · Блок D)

Захист від ін’єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
що приймають промпти користувачів. Він враховує `INJECTION_GUARD_MODE` (типове значення `warn` = лише журналювання;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип            | Маршрути                                                                                                                                             | Типовий режим |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| Текст (наявні) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| Генеративні    | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| Дані           | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

Видобування тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team-тестування (щонічне, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає проби (пропускаються без секрету).
`moderations` включено для узгодженості — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Щонічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокувальне)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен змагальний тестовий випадок (наприклад, «ігноруй усі
  попередні інструкції…», джейлбрейки в стилі DAN) перевіряє, що відповідь містить
  `error.code === "SECURITY_001"`, тобто захисний механізм справді відхилив запит.
- **`garak` (рекомендаційне)** — запускає garak із `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Виконання залежить від наявності
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); без нього завдання коректно пропускається та має суфікс
  `|| true`, тому воно надає звіт, не спричиняючи збій CI.

Покриття допоміжного засобу захисту (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що приймає промпти; текст промпту видобувається з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
