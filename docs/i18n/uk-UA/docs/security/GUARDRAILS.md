> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

## Вбудовані захисні механізми

Реєстр автоматично завантажує шість захисних механізмів у порядку пріоритету під час імпорту (див. `registry.ts` → `registerDefaultGuardrails()`):

| Пріоритет | Назва               | Етап(и)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Менші номери пріоритету виконуються **першими**.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Перехоплює запити, що містять зображення, призначені для **моделей без підтримки зору**, і або перенаправляє весь запит до моделі з підтримкою зору, або замінює частини зображення текстовими описами, створеними настроюваною моделлю зору, перед викликом вищестоящої системи. Це дозволяє провайдерам, що працюють лише з текстом, прозоро обробляти мультимодальні корисні навантаження.

Послідовність:

1.  Пропустити, якщо цільова модель вже підтримує зір (якщо вона не вказана у списку примусового мосту `isVisionBridgeForcedModel`).
2.  Витягти частини зображення за допомогою `extractImageParts(messages)` (`visionBridgeHelpers.ts`), який делегує до **уніфікованого детектора медіа** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиного джерела істини, спільного з фільтром сумісності комбінацій. Витяг дозволено для частин верхнього рівня форм, які `replaceImageParts` може вставити назад (контракт витягнення↔заміни): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"`, та Responses API `input_image`. Вкладені збіги та форми лише для індикаторів є матеріалом для комбінованого фільтра і ніколи не витягуються. Пропустити, якщо нічого не знайдено.
3.  Вирішити конфігурацію часу виконання за допомогою `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*` мають пріоритет; застарілі ключі `visionBridge*` залишаються **одноцикловим резервом** (вікно відкату). Пропустити перед будь-яким обходом медіа, коли міст вимкнено.
4.  Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) вирішує перенаправляти чи описувати. Перенаправлення повертає `modifiedPayload` лише зі зміненою `model`, плюс мета `{ rerouted, fromModel, toModel, imagesKept }`.
5.  Шлях опису: обмежити зображення до `maxImages`, скласти підказку, що враховує завдання, звернутися до кешу описів, викликати модель зору **паралельно** (`Promise.allSettled`), та вставити текстові частини `[Image N]: <description>` на їх місце. Невдалий опис дає `null`, а оригінальна частина зображення **зберігається** (#4012) — за винятком шляху комбінованого опису, коли кожен опис не вдався, де підтверджений вищестоящий провайдер без підтримки зору отримує заглушку `(unavailable — no vision-capable provider connected)` замість цього (#8430).
6.  Повернути `modifiedPayload` + мета (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | За замовчуванням | Поведінка                                                                                                                                                                                                                                                                             |
| ---------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔                | Застаріла евристика, без змін (#6640/#7204): моделі без комбінації/`auto/` перенаправляються до найкращої моделі зору, якщо оригінальна модель вже не має придатних облікових даних (тоді описується); комбіновані цілі завжди описуються.                                            |
| `describe` |                  | Завжди описувати — блок перенаправлення повністю пропускається; обрана користувачем модель завжди відповідає.                                                                                                                                                                         |
| `reroute`  |                  | Примусове перенаправлення: захист моделі з обліковими даними обходиться. Захист облікових даних **цілі** перенаправлення все ще застосовується — якщо немає придатної цілі зору, запит переходить до опису, щоб необроблені зображення ніколи не досягали текстового бекенду (#8430). |

Примусові режими спрацьовують **до** запуску евристики `auto`; поведінка `auto` є байт-ідентичною до захисного механізму до PR-1.

#### Підказка для опису, що враховує завдання (`modalityBridgeVisionTaskAware`)

За замовчуванням **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає текст **останнього повідомлення користувача** (обрізаного до 500 символів) до базової підказки опису, спрямовуючи опис до того, що користувач насправді запитав (шаблон codex-vision-proxy) і просячи модель зору транскрибувати видимий текст. Якщо прапорець вимкнено — або немає тексту користувача — використовується базова підказка без змін.

Власний OpenAI-сумісний запит самоциклу опису (`callVisionModelSingle()` у `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` — безумовно, для кожного абонента/провайдера, не залежно від будь-якого клієнтського сигналу. Вибірка з низькою деталізацією погіршує точність OCR саме для завдання транскрипції тексту, яке вимагає цей запит, тому сам виклик опису завжди запитує високу деталізацію, незалежно від рівня деталізації, використаного в оригінальному вхідному запиті. Це впливає лише на внутрішнє тіло запиту опису; це не змінює того, як OmniRoute пересилає власний `image_url.detail` абонента в основному запиті — це значення за замовчуванням застосовується окремо і лише для виявлених клієнтів OpenCode, у `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка самоциклу опису у форматі Anthropic wire-format не має поля `detail` і не залежить від жодного з цих значень за замовчуванням.

#### Обмеження виводу опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| :----------------------------- | :--------------- | :---------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає **без обмежень** — опис, повернений `callVisionModel()`, передається без змін, зберігаючи існуючу поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис суфіксом `…` перед тим, як він буде вставлений назад як `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`). Збільшуйте це значення для завдань OCR, що вимагають високої деталізації, де нижній моделі потрібна повна транскрипція; зменшуйте його, щоб обмежити використання токенів у багатослівних візуальних моделях. Поле на панелі керування знаходиться на вкладці Vision, у розширеній панелі (`modality-bridge-max-chars` у `ModalityBridgeVisionTab.tsx`) і обмежує будь-яке значення від 1 до 99 до нижньої межі 100, залишаючи явне `0` без змін — `0` є дійсним значенням Zod сам по собі (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто "не встановленим" значенням за замовчуванням.

#### Кеш опису (`modalityBridge/bridgeCache.ts`)

LRU + TTL кеш у пам'яті для виводів опису, спільний для всього процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` з префіксом довжини (без колізій меж полів). Компонент моделі — це **налаштована** модель мосту, а не модель, яка фактично відповіла — `callVisionModel` може внутрішньо використовувати резервні варіанти, і створення ключа для кожної спроби фрагментувало б кеш. Невдалі описи ніколи не кешуються. Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| :------------------------------ | :--------------- | :------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (самоцикл опису/отримання base64)

Коли міст сам отримує **віддалене** зображення — самовиклик опису Anthropic та перетворення base64 у форматі claude-wire-format (`ensureBase64ImagesForClaudeWire`), обидва через `fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий URI даних передається через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед вбудовуванням у запит візуальної моделі. Зображення великого розміру зменшуються до **довгої сторони 2048px** (відповідає обмеженню розміру, яке OpenAI/Anthropic вже застосовують на стороні сервера), що зменшує кількість завантажених байтів/затримку без зміни того, що бачить візуальна модель. Зміна розміру використовує `sharp`, завантажений через динамічний імпорт: на платформі, де його нативний бінарний файл не завантажується, `normalizeDataUri()` **ніколи не видає помилок** — він повертається до передачі оригінальних байтів, тому шлях опису/перетворення base64 завжди працює. Байти, що не є зображеннями (отримання, яке не повернуло зображення, що піддається декодуванню), також передаються без змін. Ця нормалізація стосується зображень, які міст отримує для власного самовиклику — вона ніколи не застосовується до необробленого корисного навантаження абонента, що відповідає принципу мутації лише за згодою (Жорстке правило №20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` перевіряються Zod у `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, тріо `modalityBridgeCache*` та група `modalityBridgeAudio*`, що використовується Audio Bridge. Міграція `141_modality_bridge_settings.sql` копіює існуючі застарілі значення `visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не перезаписує встановлене оператором значення `modalityBridge*`); застарілі ключі залишаються прийнятими як резервний варіант для читання протягом одного циклу випуску.

#### Заголовок прозорості + статистика

Відповіді, перетворені описом, містять `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (створений `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`, позначений `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`). Перенаправлені запити **не отримують** заголовка — корисне навантаження залишилося незмінним, а зміна моделі вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (авторизація управління, той самий рівень, що й `GET /api/settings`) повертає лічильники в пам'яті для кожної модальності `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та `video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як свій знаменник; операція без вимірювання часу не створює зразок з нульовою мілісекундою. `bridged` залишається зворотно сумісним псевдонімом для успішних перетворень; невдалі спроби не збільшують його. Лічильники скидаються при перезапуску процесу за задумом (телеметрія, а не облік).

#### Конфігурація панелі керування

Виділена сторінка панелі керування — це
`/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio`
та `Video`, що доступні за URL-адресою, зберігають параметри запиту під час зміни
значення `tab`. Вкладка Vision надає доступ до параметрів увімкнення, режиму, вибору моделі (включно
з автоматичним значенням за замовчуванням), промптів з урахуванням завдань, розширених лімітів таймаутів/зображень/довжини опису/кешу,
лімітів виконання
та захищеного запиту для прикладу. Вкладка Audio також працює: на ній доступні параметри
увімкнення, вибору моделі лише для STT (з варіантом Auto), ліміти таймауту/максимальної тривалості кліпу, ліміти аудіо
та тестовий запит `input_audio`. Вкладка Video є функціональною: вона відображає
стан виконання FFmpeg/ffprobe — один із чотирьох явних станів інтерфейсу (`unknown`, доки перевірка
виконується або не може завершитися; `restricted` на не-loopback хості панелі керування, де перевірка
пропускається на боці клієнта; `unavailable`, якщо перевірку виконано і підтверджено відсутність;
або `available` з версіями FFmpeg/ffprobe) — зберігає ліміти
увімкнення/моделі/кадрів/відео/таймауту, фільтрує вибір моделі лише до моделей, здатних працювати з візуальними даними,
та надає лічильники відео.

Колишня картка Vision Bridge у налаштуваннях AI є посиланням сумісності на
нову сторінку; вона більше не містить другу копію форми. Media Providers також
посилається на робочі процеси Image-to-Text та Speech-to-Text у відповідних вкладках Modality
Bridge, не видаляючи наявний майданчик (playground) Speech-to-Text.

**Обхід допуску self-loop:** коли виклик опису спрямовується через власний self-loop
`/v1` у OmniRoute (нестандартна модель провайдера), підзапит надсилає
`x-omniroute-admission-bypass: internal` та автентифікується за допомогою вирішеного
облікового запису self-loop — локального вартового `sk_omniroute` в локальному режимі або
сконфігурованого оператором ключа середовища `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), тож
розгортання з `REQUIRE_API_KEY=true` все одно можуть виконувати виклик опису. Обхід
застосовується лише для цих конкретних облікових даних, тому зовнішні клієнти не можуть використовувати
заголовок для пропускання допуску.

Застарілі значення за замовчуванням містяться у `src/shared/constants/visionBridgeDefaults.ts`; нові
значення за замовчуванням для режиму/завдань/кешу та резолвер налаштувань містяться у
`src/shared/constants/modalityBridgeDefaults.ts`. Захисний механізм (guardrail) надає
варіант конструктора `deps`, щоб тести могли впроваджувати фейкові реалізації `getSettings` та
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює чат-запити, що містять аудіо, до того, як вони досягнуть цілі, яка
не підтримує аудіовхід. Він ніколи не перенаправляє чат-запит: аудіочастини
транскрибуються через наявний сумісний з OpenAI multipart-ендпоінт, а обрана
модель чату продовжує роботу з текстовими транскриптами.

Послідовність:

1. Визначити `supportsAudio` за допомогою `getResolvedModelCapabilities()`. Метадані явного
   реєстру провайдерів мають пріоритет, потім статичні метадані моделі та синхронізовані
   `modalities_input`. Оголошений список вхідних даних без `audio` стає `false`; відсутність
   доказів можливостей залишається `null`. І `false`, і `null` активують консервативний міст,
   тоді як `true` обходить його.
2. Визначити налаштування `modalityBridgeAudio*` та витягти аудіочастини верхнього рівня,
   які можна обрізати, з кожного повідомлення за допомогою спільного детектора `detectMediaParts()`.
   Підтримувані формати: OpenAI `input_audio`, `audio_url` та `source.media_type: "audio/*"`.
   Вкладене аудіо визначається для маршрутизації, але не видаляється шляхом обрізання.
   Робота обмежується значенням `modalityBridgeAudioMaxClips`; подальші частини залишаються незмінними.
3. Використати налаштовані `provider/model` або дозволити `selectAudioBridgeModel()` переглянути
   `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та вибрати першу
   модель із працездатними активними обліковими даними провайдера.
4. `callAudioTranscription()` перетворює аудіо base64/data-URI на multipart `file`
   або завантажує віддалений `audio_url` через загальнодоступний вихідний захисний механізм
   із прив'язкою DNS та обмеженням 25 МБ. Потім він надсилає POST-запит із файлом та вибраною
   моделлю на локальний self-loop `/v1/audio/transcriptions`, автентифікований за допомогою
   `resolveSelfLoopBearer()`. Наявний маршрут транскрипції виконує звичайний пошук облікових даних,
   обробку періодів очікування (cooldown) / обмеження частоти запитів та диспетчеризацію провайдера.
5. Успішні виклики замінюють свої частини на `[Audio N]: <transcript>`. Виклики
   виконуються за допомогою `Promise.allSettled`: окрема помилка зберігає цю оригінальну
   аудіочастину (контракт #4012). Якщо всі виклики зазнають невдачі, а ціль точно
   має значення `supportsAudio === false`, частини перетворюються на
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   невідомої цілі (`null`) результат у разі всіх невдач залишається незмінним. Доведена
   текстова ціль без жодних робочих облікових даних STT отримує таку саму явну заглушку
   без здійснення мережевого виклику.

Успішні транскрипти використовують процесний LRU/TTL кеш Modality Bridge. Ключ
поєднує аудіопосилання, стабільну мітку операції `audio-transcription`
та вибрану STT-модель; невдачі ніколи не кешуються. Спроби роботи з аудіо оновлюють спільні
лічильники `bridged`, `cacheHits`, `failures` та `lastUsedAt`.
Зtransformed відповіді містять
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені
запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання зберігаються в БД та перевіряються за допомогою Zod:

| Ключ                          | За замовчуванням | Діапазон        |
| ----------------------------- | ---------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`           | —               |
| `modalityBridgeAudioModel`    | `""`             | Auto або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`          | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`              | 1–10            |

Спільний кеш продовжує контролюватися параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює відеочастини верхнього рівня в `messages` Chat Completions та `input` API Responses перед викликом цілі без відомої нативної підтримки відео.
Підтримувані форми: `input_video`, `video_url`, `video_source`, HTTPS URL-адреси та `data:video/*;base64,...` URI даних. Звичайні імена файлів у тексті не розглядаються як відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запитів, перевірку можливостей/політики, агрегацію за запитом та корисне навантаження відповіді.
Робота з кожним відео — отримання, кеш повного результату, опис послідовності кадрів (яка об'єднує будь-яку аудіорозшифровку, оголошену викликаючою стороною), а також метрики/переривання/очищення за спробу — прихована за `processVideoPart` у `videoBridgePipeline.ts`, яка викликається один раз для кожної відеочастини всередині циклу `preCall`.
Цей модуль також визначає явні межі портів `VideoMediaBrokerPort` (отримання байтів та вилучення вибіркових кадрів), `VideoAudioTranscriptionPort` (об'єднання аудіорозшифровки, оголошеної викликаючою стороною, з вибірковими субтитрами) та `VideoDrilldownPort` (межа збереження деталізації кадрів; ще не підключена до `processVideoPart` — лише окремий маршрут `/api/modality-bridge/video/drilldown` сьогодні записує записи деталізації).

Публічний шлях запиту `/v1` ніколи не імпортує та не викликає підпроцес. Віддалені відео завантажуються з обмеженням 50 МіБ; вбудовані base64 відео мають консервативне обмеження 36 МіБ декодованого розміру на відео, щоб модель/повідомлення/оболонка кадрування могли залишатися в межах публічного ліміту прийому JSON-запитів у 50 МіБ. Оцінки довжини та декодованого розміру вбудованих даних перевіряються перед виділенням. HTTPS вимагається для початкової віддаленої URL-адреси та кожного перенаправлення, використовуючи існуючий публічний вихідний захист з прив'язкою DNS. Потім байти перетинають точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`. Цей маршрут є як `LOCAL_ONLY`, так і `SPAWN_CAPABLE`, приймає лише автентифікований, довірений запит зворотного зв'язку для кожного процесу, і ніколи не приймає URL-адресу, шлях до файлової системи, виконуваний файл або список аргументів. Конвеєр розміру тіла API та інкрементний зчитувач тіла обробника незалежно забезпечують обмеження вхідних даних брокера в 50 МіБ. Його обмежена черга виконує одне вилучення за раз, дозволяє чотири очікувані завдання та обмежує очікувані вхідні дані до 100 МіБ.

Всередині брокера `ffprobe` читає приватний локальний файл; фіксований список дозволених форматів виключає формати списків відтворення та маніфестів. Для дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV залишаються вимкненими за замовчуванням, і фіксована команда не дозволяє їх. Як `ffprobe`, так і `ffmpeg` використовують білий список протоколів лише для `file`, один потік, фіксовані масиви аргументів, без оболонки та виконувані файли, розв'язані з `PATH`. Потоки обкладинок з прикріпленими зображеннями не є придатними кандидатами для відтворення. Усі відтворювані потоки повинні задовольняти обмеженням, і явний потік за замовчуванням є кращим перед детермінованим найнижчим індексом резервного варіанту. Відео обмежені 600 секундами, 8192 пікселями на вимір та 33 554 432 вихідними пікселями. FFmpeg вибирає 1–16 проміжних кадрів JPEG, зменшує довгу сторону до максимум 1024 пікселів без збільшення менших вхідних даних і ніколи не отримує URL-адресу. Вибірка за замовчуванням є `uniform`. Додаткові політики `scene_aware` та експериментальні `segment_aware` виконують один додатковий фіксований прохід FFmpeg над вже перевіреним локальним потоком, вибирають обмежені часові мітки сцени `showinfo` та детерміновано повертаються до тих самих рівномірних проміжних точок у разі збою детектора, тайм-ауту, неправильного виводу або порожнього набору кандидатів. Режим з урахуванням сегментів розподіляє проміжні зразки пропорційно до перевірених інтервалів сцени; докази та поведінка резервного варіанту з урахуванням сегментів детально описані нижче. Жорстке обмеження в 16 кадрів застосовується після вибору в кожній політиці. Коли запит з урахуванням сцени має бюджет лише на один кадр, він використовує рівномірну проміжну точку активного повного відео або вікна фокусування та повідомляє `policyEffective: uniform`: один вибраний кадр сцени не може зберегти обидва часові кінці. Викликаюча сторона може за бажанням надати кінцеве вікно фокусування (`start`/`end` секунди); межі обмежуються тривалістю медіа, відхиляються зворотні або нескінченні вікна, і всі політики вибірки виконуються лише всередині нормалізованого інтервалу. Отримане вікно включається в метадані вибірки та в неперевірений префікс опису, щоб подальші моделі могли відрізнити сфокусований уривок від повної часової шкали.

Фокус семантичних субтитрів є окремим, явним налаштуванням. Режим аналізу `full` за замовчуванням зберігає існуючий запит кадру і ніколи не пересилає текст запиту до моделі субтитрів. У режимі `focused` міст читає лише останній непорожній `text`/`input_text`, створений користувачем, з того ж контейнера Chat або Responses, нормалізує його до NFC, згортає керуючі символи та пробіли та обмежує його 500 кодовими точками Unicode. Порожній результат повертається до точного запиту `full`. Використана підказка серіалізується як JSON у спеціальному блоці неперевіреного користувацького контексту і може лише пріоритезувати помітні деталі; вона не може скасувати окреме попередження проти дотримання інструкцій, видимих або чутних у медіа. Текстовий фокус ніколи не виводить `start`/`end` або не змінює часовий семплер.

#### FU-07 докази структурного сегмента

`segment_aware` використовує один обмежений прохід попереднього аналізу над вже перевіреним локальним відеопотоком. Фіксований ланцюжок фільтрів спочатку масштабує до максимум 320 пікселів завширшки, виявляє зміни сцени та заморожені інтервали, потім вибирає 1 кадр на секунду для розмиття, середньої яскравості та просторової/часової інформації. Прохід обмежений 600 структурними зразками, одним потоком FFmpeg/фільтра, тим самим протоколом лише для `file` та білими списками контейнерів, обмеженням виводу процесу в 1 МіБ та максимум 30 секундами всередині спільного переривання/дедлайну брокера. Він ніколи не приймає команду, фільтр, шлях або URL-адресу із запиту.

Структурні значення є детермінованими доказами вибірки, а не семантичним розумінням відео. Вони не виводять суб'єктів, дії, підписи, мовлення чи наміри користувача. Межі сцен та стоп-кадрів формують сегменти; покриття стоп-кадрів, розмиття, експозиція, просторова деталізація та часові зміни лише впливають на те, як розподіляється наявний бюджет у 1–16 кадрів. Повністю заморожений сегмент обмежений одним кадром, тоді як незаморожені сегменти конкурують за решту бюджету. Коли кількість меж перевищує кількість кадрів, зберігається рівномірне покриття часової шкали, щоб швидкі ранні вирізки не могли приховати довгий кінцевий сегмент. Межі сцен в межах 1-секундної роздільної здатності аналізу межі стоп-кадру об'єднуються.

Відсутні фільтри, неправильно сформовані/порожні докази, помилка детектора або обмежений тайм-аут попереднього аналізу призводять до відкритого збою за політикою точної рівномірної середньої точки. Переривання виклику або дедлайн брокера не призводить до відкритого збою: це припиняє поточний підпроцес, запобігає подальшому вилученню кадрів, а приватне тимчасове дерево видаляється у `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні фікстури FFmpeg для економії викликів підписів після дедуплікації, розподілу бюджету щільного руху, доказів розмиття/експозиції/SI-TI, швидких вирізок з довгим хвостом та хибних спрацьовувань поступового згасання. Він записує реальний час попереднього аналізу та, якщо доступний `/usr/bin/time`, CPU дочірнього процесу та піковий RSS. Його перевірки якості є лише структурними оракулами. Реальна якість моделі підписів залишається `HOLD`, оскільки цей тестовий стенд не має авторизованої кінцевої точки або замороженого судді. Грошова економія також залишається `HOLD`, якщо `--caption-cost-per-call-usd` не надає явну позитивну оцінку вартості за виклик; скрипт ніколи не фабрикує жодного з цих результатів.

Кожен кадр обмежений 4 МіБ, всі необроблені кадри разом — 23 МіБ, а серіалізована відповідь брокера — 32 МіБ. Приватний тимчасовий каталог видаляється у `finally`. OmniRoute не включає FFmpeg і не приймає користувацький шлях до виконуваного файлу. Перед створенням підписів, міст застосовує консервативний візуальний прохід дедуплікації: кожен JPEG зменшується до буфера 16×16 у відтінках сірого і порівнюється лише з останнім збереженим кадром. Для запитуваного бюджету підписів понад один кадр, вилучення надає обмежений пул кандидатів до подвійного розміру цього бюджету і ніколи не більше 16 кадрів. Запитуване обмеження застосовується лише після дедуплікації, при цьому перший і останній вибрані кандидати зберігаються під час остаточного проріджування, коли бюджет становить щонайменше два. Версіонована політика `grayscale-16x16-mean-cells-v2` використовує більше значення з середньої дельти яскравості та співвідношення комірок мініатюр, нормалізована дельта яких становить щонайменше 0.05. Поріг дублікатів є константою 0.04, обраною для передбачуваності, а не виставленою як налаштування під час виконання. Цей вторинний висококонтрастний сигнал зберігає невеликі рухи та зміни видимого тексту, які може приховати порівняння лише за середнім значенням. Помилки компаратора або декодера призводять до відкритого збою та зберігають покриття. Вихідні метадані розділяють вилучені кандидати, успішно використані кадри та відкинуті візуальні дублікати.

Явно позначена частина відео може запитувати контактний лист з мітками часу. Міст створює максимум 4-колонкову, 16-кадрову JPEG-сітку. Кожна 512-піксельна комірка вбудовує свою вихідну мітку часу у висококонтрастну нижню смугу, тоді як ті ж мітки часу залишаються в текстових метаданих для подальшої асоціації та аудиту. Повний JPEG залишається обмеженим 32 МіБ. Якщо `sharp` не може декодувати або скомпонувати сітку, міст повертається до окремих JPEG-кадрів; переривання клієнтом все ще поширюється через операцію з листом.

Докази просування навмисно відокремлені від синтетичного мікробенчмарку композиції. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає версіонований за схемою A/B тестовий стенд для реальних моделей зору, сумісних з OpenAI. Він вимірює токени, надані провайдером, наскрізну реальну затримку (включаючи композицію листа), кількість викликів моделі та збереження фактів, визначених у маніфесті. Необроблені відповіді моделі не записуються до звіту; зберігаються лише дайджести SHA-256 та ідентифікатори відповідних фактів. Тестовий стенд не здійснює мережевих або платних викликів моделі, якщо не передано `--execute-real` та не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без цього явного реального запуску, його машинозчитуваний вердикт залишається `HOLD`; лише синтетичні вимірювання навантаження/кількості викликів не є доказами просування.

Викликаючі сторони можуть прикріпити необов'язковий масив `transcript.cues` до підтримуваної частини відео, якщо вони вже мають вирівняний текст. Кожна підказка повинна містити `text`, кінцевий інтервал `start`/`end` всередині досліджуваної тривалості та дозволений `source` (`client`, `embedded` або `audio-bridge`); `confidence` за замовчуванням дорівнює `1` і має залишатися між `0` та `1`. Точні дублікати підказок згортаються. OmniRoute ніколи не починає транскрипцію з цих метаданих: перевірені підказки копіюються в описаний результат з джерелом, достовірністю та інтервалом, і відображаються як ненадійні спостереження поряд з підписами кадрів. Недійсний, поза діапазоном або текст без походження відхиляється, а не змішується в потік підписів. Поле `source` наразі оголошується викликаючою стороною, а не перевіряється сервером: OmniRoute забезпечує, щоб значення було одним з трьох дозволених рядків, але ще не підтверджує криптографічно, що мітка `embedded` або `audio-bridge` дійсно походить від вилучення, що належить серверу. Розглядайте `source` як ненадійну підказку, доки ця перевірка не буде реалізована; не будуйте на ній рішення щодо авторизації.

Досвідчений абонент може надати вже авторизовану доріжку `audioTranscript` для того ж відео. Шов злиття обробляє візуальні та аудіоспостереження за одним дедлайном та сигналом переривання, упорядковує їх на спільній часовій шкалі, об'єднує точні дублікати та повідомляє про частковий результат, якщо успішною є лише одна сторона. Недійсний `audioTranscript` деградує до цього часткового результату — візуальний опис зберігається, а аудіогілка записує очищений код помилки — замість того, щоб призвести до збою всього відео. Доступність для кожної гілки, прапорець частковості та очищені коди помилок зберігаються в описаному результаті, у метаданих захисту (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), у метаданих кешу результатів та в лічильниках злиття мосту. Шлях за замовчуванням Video Bridge не викликає перетворення мови в текст і не завантажує другу копію медіа; без цієї явно заданої доріжки він залишається лише відео.

**Збереження стенограми (#12150 P1).** Це застосовується автоматично щоразу, коли Video Bridge (який сам є опціональним) відтворює підказку стенограми — окремого прапорця збереження немає. Коли запит відтворює будь-яку підказку стенограми (оголошену абонентом `transcript` або об'єднану `audioTranscript`), захист позначає її як `videoBridgeObserved` і створює відредаговану тінь опису відео — ідентичне відтворення, в якому вільний текстовий вміст кожної підказки замінюється на `[redacted-video-transcript]`, що створюється шляхом заміни структурованого поля підказки до того, як рядок буде зібраний (ніколи не шляхом розбору згладженого тексту, тому жоден вміст підказки — ворожий чи звичайний, включаючи тіла, що містять `]` такі як `[inaudible]`/`[music]` — не може зберегтися). Тіло запиту журналу викликів, що зберігається, замінює кожну текстову частину, отриману з відео, на цю відредаговану тінь, зіставлену за рівністю вмісту; якір `fullText` повторно зчитується з готового корисного навантаження захисту перед викликом, тому збіг все ще успішний після того, як пізніші ланцюгові захисти (маскувальники PII та облікових даних, пріоритети 10/95) переписують текст опису на місці та після того, як впровадження системних підказок/передачі/пам'яті змінює масив повідомлень. Тіло, надіслане вгору за течією до моделі, залишається незмінним. Спостережуваний запит також не заповнює постійну Пам'ять (пропускається як вилучення, отримане із запиту, так і з відповіді), тому власна відповідь моделі не може відлунювати текст стенограми в Пам'ять.

Додаткові збережені копії використовують той самий сигнал спостережуваного запиту. Необроблений знімок клієнтського запиту до захисту, запит, що очікує в пам'яті, та ранній журнал відхилених запитів структурно замінюють поля стенограми у відеочастинах; рядкові підказки, синтезовані етапами конвеєра та передачею контексту, редагуються в сховищі тіла збереженого запиту. Збережений маркер `video_content_removed` призводить до того, що продовження `previous_response_id` завершується збоєм, а не відновлює текст, який був навмисно відкинутий. Якщо спостережуваний запит втрачає свою тінь редагування для кожної частини до логування, або навіть одна з кількох тіней відео не збігається після пізніших мутацій запиту, збережене тіло запиту повністю пропускається замість збереження частково відредагованої стенограми.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину стенограми без структурованої межі підказки. Його збережене `responseBody` журналу викликів тому замінюється маркером пропуску; детальний артефакт конвеєра (який може включати тіла вищестоящих/клієнтів та фрагменти потоку) не зберігається. Кеші семантики, ідемпотентності та відтворення міркувань обходять операції читання та запису для цього запиту. Запит провайдера та видима клієнту відповідь залишаються незмінними. Ранні байти keepalive вивантажуються з тимчасового буфера, коли детальний артефакт пропускається. Попередження Kiro про некоректний EventStream повідомляє лише кількість байтів корисного навантаження, ніколи його вміст або необроблену помилку JSON-парсера. Це не означає, що кожен непов'язаний діагностичний засіб провайдера/плагіна був перевірений; ширше очищення збережених сховищ відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремим, кешованим субстратом з аутентифікацією за зворотним зв'язком/токеном. Кожна операція також вимагає канонічного непрозорого principal ID. Перш ніж виробничий абонент буде увімкнений, він повинен отримати цей ID з автентифікованого орендаря і ніколи не повинен передавати значення, обране клієнтом. Ключі кешу прив'язують цей principal до канонічних ідентифікаторів сесії та відео-посилань, зберігають лише їхні ключі, отримані за допомогою SHA-256, і обмежують як читання, так і видалення тим самим principal. Кеш зберігає щонайбільше 16 отриманих JPEG-кадрів на запис, термін їх дії закінчується через десять хвилин, і він підтримує обмежені операції читання `start`/`end` або явне видалення сесії.

Кожен principal обмежений 16 записами та 64 MiB канонічних JPEG-даних. Ці обмеження не залежать від глобальної межі в 64 записи/256 MiB: тиск квоти principal витісняє лише найменш використовувані записи цього principal до того, як буде розглянуто глобальне витіснення за LRU. Записи з вичерпаним терміном дії видаляються як з обліку principal, так і з глобального обліку при активності кешу, тоді як скасування та збій валідації не призводять до часткової заміни.

Кеш відхиляє неканонічний Base64, надмірне заповнення, не-JPEG медіа, некоректні або обрізані JPEG, а також JPEG, які викликають попередження під час обмеженого декодування повного зображення за допомогою `sharp`. Він перекодовує кожне прийняте зображення як канонічний JPEG, виводить ширину та висоту з декодованих байтів замість того, щоб довіряти полям абонента, і відкидає будь-які кінцеві поліглотні байти замість їх збереження. Лише обмежений канонічний стиснутий буфер зараховується до обох квот. Ліміт JSON-протоколу включає накладні витрати Base64 для стелі декодованого входу в 32 MiB. Кожне збережене похідне значення записує свій перевірений формат/роздільну здатність JPEG, політику вибірки, версію похідного значення, час створення, обчислений сервером хеш вмісту та хешоване батьківське посилання, а також хеш батьківського вмісту довіреного абонента. Скасування перевіряється між асинхронними фазами декодування/хешування перед атомарним фіксацією кешу.

Цей транш ще не підключає виробничий продюсер до маршруту і не
забезпечує вибір варіантів з кількома роздільними здатностями. Прозорий шлях
запиту Video Bridge, таким чином, не несе додаткового навантаження, тоді як
виведення основних даних, прив'язаних до орендаря, та повний життєвий цикл
FU-08 з кількома роздільними здатностями залишаються явним подальшим завданням,
а не документуються як завершена поведінка.

Кадри послідовно підписуються налаштованою моделлю Video. Порожнє
перевизначення Video успадковує налаштування Vision; якщо обидва порожні,
автоматичний маршрутизатор Vision вибирає ефективну модель, здатну до зору.
Успішні підписи замінюють оригінальну частину стабільним префіксом
`[Video description:`, який також позначає текст як ненадійне спостереження,
отримане з медіа, і вказує наступним моделям не слідувати інструкціям,
знайденим у медіа. Ключі кешу підписів кадрів включають байти JPEG, підказку,
мітку часу та ефективну модель; кешуються лише успішні підписи. Записи кешу
зберігають фактичну успішну модель продюсера, включаючи резервну модель;
міст повідомляє `mixed`, коли різні кадри були створені різними моделями.
Збіг у кеші повторно використовує цю ідентичність продюсера замість того, щоб
перемарковувати її як запитуваний план маршрутизації. Кеш результатів
цілого відео кешується за кожним вхідним параметром, який змінює вихід —
підказка, ефективна модель, політика вибірки, кількість кадрів, режим
семантичного аналізу, SHA-256 відбиток нормалізованої підказки фокусу,
вікно фокусу, `transcript`, `audioTranscript` та прапорець контактного
листа — тому зміна будь-якого з цих вимірів призводить до промаху кешу,
ніколи не до застарілого повторного використання. Версія політики візуальної
дедуплікації, поріг та обмежена кількість кандидатів-кадрів також є явними
в ключі кешу результатів та метаданих; тому зміна політики не може повторно
використовувати застарілий опис цілого відео. Метадані кешу результатів v4
зберігають режим та відбиток, ніколи не сире завдання користувача. Метадані
Guardrail повідомляють як запитувані, так і ефективні режими аналізу;
запитуваний режим `focused` без придатного тексту користувача повідомляється
як ефективно `full`.

Guardrail витягує кожну підтримувану частину відео, але описує не більше, ніж
`modalityBridgeVideoMaxVideos`. Для цілі, яка, як доведено, має
`supportsVideo === false`, невдалі та перевищені відео стають явними
безпечними текстовими маркерами, тому жодне сире відео не зберігається.
Коли можливості невідомі, ці частини залишаються недоторканими. Цілі з
`supportsVideo === true` обходять міст. Сигнал переривання запиту клієнта
поширюється через завантаження, чергу брокера, підпроцеси та виклики
підписів; переривання зупиняються між відео і ніколи не відкриваються до
сирих медіа.

Налаштування часу виконання зберігаються в БД та перевіряються Zod:

| Key                                 | Default     | Range / behavior                                                                                               |
| :---------------------------------- | :---------- | :------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | Додатковий час виконання, за згодою                                                                            |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` зберігає загальні підписи; `focused` використовує обмежений, ненадійний контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`        | Успадковує модель Vision Bridge                                                                                |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware` або пропорційний `segment_aware`; збій детектора повертається до `uniform`            |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 мс                                                                                                 |

Застарілі збережені значення тайм-ауту Video понад 120 секунд обмежуються
дедлайном брокера; нові записи налаштувань понад цей ліміт відхиляються.
`GET /api/modality-bridge/video/runtime` вимагає довіреної штампованої
локальності зворотного зв'язку перед автентифікацією або зондуванням часу
виконання, потім вимагає автентифікації управління. Він повертає лише
`available`, санітизовані версії FFmpeg/ffprobe та фіксовану причину,
коли час виконання недоступний. Внутрішня кінцева точка вилучення не є
публічним API завантаження: насичення черги повертає `503` плюс `Retry-After`,
відключення абонента повертає `499`, а фіксований дедлайн брокера повертає `504`.
Перетворені відповіді додають `video->text;model=<visionModel>;parts=<videos>`
до центрального заголовка `x-omniroute-modality-bridge` без видалення сегментів
Vision або Audio.

### Маскувальник PII (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує корисне навантаження, проходить `system`, `messages`,
  `input` та `prompt` (включаючи прості рядкові елементи) і застосовує
  `processPII()` (з `@/shared/utils/inputSanitizer`) до рядкових полів
  `content`/`text`. Коли `PII_REDACTION_ENABLED=true`, виявлена PII
  редагується у вихідному корисному навантаженні. Це не залежить від
  `INPUT_SANITIZER_MODE` (який контролює лише політику ін'єкції підказок).
  Коли редагування вимкнено, виклик записує кількість виявлень без
  перезапису вмісту.
- **`postCall`** глибоко клонує відповідь, запускає `sanitizePIIResponse()`
  плюс маскувальник форми Responses-API (`maskResponsesOutput` — охоплює
  `output_text` та `output[].content[].text`). Якщо відбувається будь-яке
  редагування, змінена відповідь замінює оригінальну.

Guardrail ніколи не блокує; він лише анотує (`meta.detections`,
`meta.redacted`) або переписує.

### Ін'єкція підказок (`promptInjection.ts`)

Виявляє ворожі структури у наданому користувачем вмісті та забезпечує
виконання налаштованої політики. Поведінка визначається змінними середовища
та параметрами конструктора:

| Налаштування    | Змінна середовища                                                                                     | За замовчуванням | Ефект                                                                                                                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`           | Якщо `false`, захисний механізм вимикається.                                                                                                                                                    |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`           | Політика ін'єкцій: `block`, `warn` або `log`. (`redact` приймається для зворотної сумісності, але **не** видаляє текст ін'єкції; запит на перезапис PII контролюється `PII_REDACTION_ENABLED`.) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальна серйозність, необхідна для блокування. Середній рівень за замовчуванням лише для спостереження.                                                                                      |

**Пріоритет режиму** (`getMode`): викликаючий `options.mode` →
`INJECTION_GUARD_MODE` **Перевизначення прапорця функції БД** (Панель керування → Налаштування →
Прапорці функцій) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Перевизначення з панелі керування має пріоритет над змінними середовища, тому інтерфейс користувача Feature Flags контролює роботу захисного механізму в реальному часі (без перезапуску). Зчитування з БД є відмовостійким: якщо виникає помилка, захисний механізм повертається до поведінки, заснованої на змінних середовища, а якщо перевизначення не встановлено, поведінка ідентична вирішенню лише на основі змінних середовища.

Джерела виявлення:

1.  `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір детекторів, що використовується в інших частинах конвеєра).
2.  Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` та
    `markdown_system_block`, обидва з `high` серйозністю).
3.  Додаткові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази
    або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Request rejected:
suspicious content detected" }`. У режимах `warn`/`log` захисний механізм реєструє подію, але
дозволяє виклик. Спільний допоміжний метод `evaluatePromptInjection()` також експортується
для викликаючих сторін, яким потрібно оцінювати підказки без проходження через реєстр.

**Межа сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об'єднаного тексту підказки — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у
`src/shared/utils/inputSanitizer.ts`. Обидва `detectInjection()` та
`evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
циклу шаблонів. Директиви ін'єкцій знаходяться близько до початку вхідних даних, тому це
обмежує використання ЦП/збирання сміття регулярними виразами для корисних навантажень розміром у сотні КБ без послаблення виявлення (див. #3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Працює на **обох** етапах, останній у стандартному ланцюжку (пріоритет `95`). Видаляє
відомі шаблони ключів API / секретних токенів з вихідного корисного навантаження (вміст
повідомлення, аргументи виклику інструменту, результати інструменту) **та** відповіді
провайдера, щоб облікові дані, вставлені в підказку (або повернені результатом інструменту),
не витікали до вихідного провайдера або назад до клієнта.

- **Лише за згодою**, та сама конвенція, що й для редагування PII (Суворе правило #20-суміжне):
  вимкнено, якщо `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true`. Якщо вимкнено, захисний механізм не виконує жодних операцій —
  він ніколи не блокує і ніколи не перезаписує.
- `redactCredentials()` обходить повне дерево корисного навантаження/відповіді (`walkValue()`,
  безпечний від забруднення прототипу, безпечний від циклів через `WeakSet`) і замінює збіги на
  заповнювач `[REDACTED:<type>]`, клонуючи лише ті гілки, які фактично змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі провайдерів LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square),
  хмарні ключі (AWS access key, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення, що містять облікові дані (`mongodb://user:pass@...`, тощо), а також
  загальний шаблон значення заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі у формі заголовків (`authorization`, `x-api-key`, `api-key`, `apikey`)
  редагуються структурно (лише значення, префікс схеми, такий як
  `Bearer `/`Basic `, зберігається), а не за допомогою загального текстового регулярного виразу.
- Захисний механізм ніколи не блокує; він лише перезаписує (`modifiedPayload` /
  `modifiedResponse`) та анотує (`meta.credentialsRedacted`, `meta.count`).

Захист від регресії: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true short-circuits the chain
  message?: string; // surfaced when blocking
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // returned by preCall to rewrite the request
  modifiedResponse?: TValue; // returned by postCall to rewrite the response
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Захисний механізм (guardrail) сигналізує про "відсутність змін", повертаючи `void`, `{}`, або `{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює значення, що проходить через ланцюжок, для подальших захисних механізмів. `signal?: AbortSignal` передає життєвий цикл викликаючої сторони до захисних механізмів. Переривання запиту є навмисним винятком "відкриття при збої": медіа-мости припиняють роботу та очищення, не відновлюючи необроблені медіа-дані до цілі, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
