## Огляд

Усі маршрути API керування OmniRoute належать до одного з трьох рівнів захисту. Класифікація є статичною, визначається у `src/server/authz/routeGuard.ts` і перевіряється до виконання будь-якої іншої гілки автентифікації.

## Рівні

### Рівень 1 — LOCAL_ONLY

**Забезпечується через:** `isLocalOnlyPath(path)` → перевірка loopback-хоста  
**Обхід:** За замовчуванням відсутній. Вузький виняток для шляхів у `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, коли запит містить дійсний ключ API з областю доступу `manage` (див. [Виняток для області доступу manage](#manage-scope-carve-out)).

Ці маршрути запускають дочірні процеси або виконують код під час роботи. Надання доступу до них для трафіку не з loopback-інтерфейсу дало б змогу зловмиснику, який отримав дійсний JWT (наприклад, через тунель Cloudflared/Ngrok), ініціювати запуск процесів — це відомий клас CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Що таке GHSA-fhh6-4qxv-rpqj (клас атаки):** сервер керування/агентський сервер надає кінцеву точку, яка запускає підпроцес (`npm install`, `node`, браузер, проксі, `git`, `tar`, …). Якщо ця кінцева точка доступна з-поза хоста — через те, що оператор розмістив OmniRoute за тунелем nginx/Cloudflare/Tailscale і стався витік JWT або автентифікацію було налаштовано неправильно, — зловмисник перетворює «виклик API» на «виконання команди на хості» (віддалене виконання коду). OmniRoute запобігає цьому, **безумовно виконуючи перевірку loopback-хоста до будь-якої перевірки автентифікації** для кожного маршруту, здатного запускати процеси: навіть витік токена через тунель не дасть змоги дістатися до функції запуску.

**Повний набір LOCAL_ONLY.** Авторитетним джерелом є `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` у `src/server/authz/routeGuard.ts`; наведена нижче таблиця відображає поточний стан. Перевірка `check-route-guard-membership` перераховує кожен `route.ts` у префіксах, здатних запускати процеси, і спричиняє збій CI, якщо будь-який із них не класифіковано як доступний лише локально.

#### Виняток для області керування

До підмножини шляхів LOCAL_ONLY ТАКОЖ МОЖНА звертатися не з loopback-адреси тоді й
лише тоді, коли запит містить `Authorization: Bearer <api-key>`, метадані якого
включають область `manage` (або `admin`). Виняток явно вмикається окремо для
кожного шляху через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, тому типовою
поведінкою для будь-якого нового шляху LOCAL_ONLY залишається сувора вимога
loopback. Неавтентифіковані запити та запити з ключами без області `manage`
і надалі відхиляються з `403 LOCAL_ONLY`.

Наразі єдиним префіксом, для якого дозволено виняток, є `/api/mcp/`.
`/api/cli-tools/runtime/` і `/api/services/` навмисно виключено, оскільки вони
можуть запускати довільні підпроцеси (`npm install`, `node`), а це саме той
клас CVE, якому має запобігати рівень LOCAL_ONLY.

**#7895 — вузька область `mcp:connect`:** виняток для `/api/mcp/` ТАКОЖ приймає
Bearer-ключ із вузькою областю `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), що перевіряється
через `hasMcpConnectOrManageScope()` у `src/server/authz/policies/management.ts`.
Це обмежено ВИКЛЮЧНО `/api/mcp/` — `mcp:connect` не надає жодних дозволів для
будь-якого іншого маршруту керування (включно з усіма іншими префіксами винятків
LOCAL_ONLY, якщо такі колись буде додано) і навмисно не включено до
`MANAGEMENT_API_KEY_SCOPES`. Ключ з областю `manage`/`admin` і надалі проходить
цей виняток так само, як і раніше; `mcp:connect` є альтернативою з нижчими
привілеями для віддалених клієнтів, що використовують лише MCP і не повинні
потребувати широкого доступу до керування.

| Запит                                            | Шлях                       | Результат                      |
| ------------------------------------------------ | -------------------------- | ------------------------------ |
| Не з loopback, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не з loopback, Bearer з областю `manage`         | `/api/mcp/*`               | Дозволено                      |
| Не з loopback, Bearer з областю `mcp:connect`    | `/api/mcp/*`               | Дозволено                      |
| Не з loopback, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не з loopback, Bearer з областю `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Не з loopback, Bearer з областю `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Loopback, із будь-яким Bearer або без нього      | будь-який LOCAL_ONLY       | Дозволено (перевірку пройдено) |

#### Рекомендації операторам і аудит

Якщо ви запускаєте OmniRoute за зворотним проксі або тунелем (nginx, Caddy,
Cloudflare Tunnel, Tailscale, Ngrok), перевірка loopback і надалі захищає
наведені вище маршрути, здатні запускати процеси, — запит, адреса клієнта якого
не є loopback-адресою, відхиляється з `403 LOCAL_ONLY` **до виконання
автентифікації**, тому витік JWT не дасть змоги запустити процес. В операторів
залишаються два обов’язки:

- **Не «виправляйте» 403, підробляючи IP-адресу клієнта як loopback.**
  Установлення `X-Forwarded-For: 127.0.0.1` або використання проксі, який
  переписує адресу джерела на loopback, знову відкриває саме той клас RCE, який
  цей рівень блокує. Надавайте доступ через проксі до панелі керування/API —
  але ніколи до маршрутів, здатних запускати процеси.
- **Зберігайте виняток для області керування мінімальним.** Виняток можливий
  лише для `/api/mcp/` і лише з API-ключем, що має область `manage`.
  `SPAWN_CAPABLE_PREFIXES` ніколи не можна додавати до списку винятків — схема
  zod відхиляє їх, а `isLocalOnlyBypassableByManageScope` забороняє їх під час
  виконання (ешелонований захист); саме це означає повідомлення панелі керування
  «не можна зробити доступним через виняток». Маршрути з динамічними сегментами
  та статичними шляхами, здатні запускати процеси, у `/api/providers/`
  (наприклад, `/login`, `/refresh-cursor`) охоплюються супровідними
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` на основі
  регулярних виразів у `src/shared/constants/spawnCapablePrefixes.ts`, а не
  плоским масивом `SPAWN_CAPABLE_PREFIXES` — для їх охоплення плоский масив мав
  би включати весь префікс `/api/providers/`, що надмірно розширило б охоплення
  дерева маршрутів, яке віддалені панелі керування правомірно використовують
  для CRUD-операцій із постачальниками.

**Аудит доступу** — щоб перевірити, що жодні зовнішні запити не досягають цих маршрутів:

- Відкрийте **Інвентаризацію авторизації** на `/dashboard/settings/security`: там відображається
  актуальний список префіксів LOCAL_ONLY, префікси, для яких можна дозволити обхід, і визначений
  під час компіляції набір із можливістю запуску процесів («для нього не можна дозволити обхід»).
- Перевірте за допомогою grep журнали зворотного проксі / доступу на наявність наведених вище
  префіксів у поєднанні з адресою клієнта, що не належить до loopback. Будь-яке таке звернення,
  яке отримало `200` замість `403 LOCAL_ONLY`, означає, що проксі маскує справжню IP-адресу
  клієнта — виправте конфігурацію проксі.
- Запис `403 LOCAL_ONLY` у журналах OmniRoute для одного з цих шляхів означає, що захисний
  механізм працює належним чином, а не помилку, яку слід приховати.

### Рівень 2 — ALWAYS_PROTECTED

**Забезпечується через:** `isAlwaysProtectedPath(path)` → пропуск обходу `requireLogin=false`
**Обхід:** відсутній, коли `requireLogin=false`; JWT потрібен завжди

Ці маршрути виконують руйнівні або незворотні дії. Якби вони були дозволені
в інсталяції «без пароля», будь-хто в тій самій LAN міг би стерти базу даних
або завершити серверний процес.

| Шлях                                      | Причина                                                       |
| ----------------------------------------- | ------------------------------------------------------------- |
| `/api/shutdown`                           | Завершує серверний процес                                     |
| `/api/settings/database`                  | Експорт, імпорт і стирання бази даних                         |
| `/api/db-backups`                         | Доступ до повного архіву резервної копії бази даних           |
| `/api/settings/export-json`               | Експортує повний набір налаштувань (включно із секретами)     |
| `/api/settings/import-json`               | Замінює повний набір налаштувань                              |
| `/api/providers/health-autopilot/actions` | Виконує дії автоматичного виправлення за допомогою автопілота |
| `/api/settings/obsidian`                  | Створює багаторазові облікові дані WebDAV для кореня сховища  |

**Відповідь у разі порушення:** `401 Authentication required`

`/api/settings/obsidian` охоплює свій дочірній шлях `/webdav`: `POST` спрямовує файлову службу WebDAV —
яка обслуговується спеціальним шаром Node перед Next.js, поза цим конвеєром — на кореневий каталог,
вибраний викликачем, і повертає щойно створені облікові дані Basic, `DELETE` змінює їх, а батьківський
`POST` зберігає токен REST API Obsidian. GHSA-62vw лише приховав розкриття пароля через `GET`;
створення облікових даних усе ще залишалося на рівні з дозволом у разі збою (GHSA-7pq4-8pvv-rx7r).
`enableObsidianVaultSync()` додатково відхиляє сховище, яке є каталогом даних, розташоване всередині
нього або містить його.

### Початкове налаштування нової інсталяції доступне лише через loopback — за реальною адресою вузла, а не за `Host`

Якщо пароль керування не налаштовано (і `INITIAL_PASSWORD` не задано), `isAuthRequired()` у
`src/shared/utils/apiAuth.ts` залишає анонімне початкове налаштування доступним **лише для loopback-вузлів**.
Належність до loopback визначається за довіреними сигналами вузла в такому порядку: позначена токеном
реальна адреса TCP-вузла (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, яку бачить політика), власний вердикт
конвеєра `AUTHZ_HEADER_PEER_LOCALITY` (який бачать обробники маршрутів і якому довіряють лише тоді, коли
задано `OMNIROUTE_PEER_STAMP_TOKEN`) або реальна адреса сокета вузла для прямих викликів. `Host` /
`nextUrl.hostname` ніколи не враховуються, а початкове встановлення пароля
(`POST /api/settings/require-login`) підпорядковується тому самому обмеженню, а не є відкритим для кожного
вузла мережі (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передає далі власний вердикт `peerContext`,
тож заголовки ОРИГІНАЛЬНОГО запиту (до їх видалення) ніколи не впливають на це рішення.

### Рівень 3 — MANAGEMENT (за замовчуванням)

Усі інші маршрути керування. Автентифікація потрібна, якщо не налаштовано
`requireLogin=false`. Токени CLI можуть автентифікуватися для цих маршрутів (loopback + дійсний HMAC).

## Порядок перевірки

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → fall through
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → allow (management_key)
     → otherwise                                  → reject 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → allow (system)
  3. hasValidCliToken(headers)?
     → allow (cli) [loopback + timingSafeEqual HMAC check]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → allow (dashboard_session)
     → manage-scope Bearer on a non-bypassable path?
        → allow (management_key)
     → reject 401/403
  5. requireLogin=false?
     → allow (anonymous)
```

Гілка manage-scope на кроці 1 — єдиний автентифікований шлях, який може надати доступ до маршруту
LOCAL_ONLY; у разі помилки auth-backend повертається 503 (а не 403), щоб
прострочена БД непомітно не спричинила перехід до режиму «відхилити».

## Додавання нового маршруту, здатного запускати процеси

1. Додайте префікс шляху до `LOCAL_ONLY_API_PREFIXES` у
   `src/server/authz/routeGuard.ts`
2. Додайте тест до `tests/unit/authz/routeGuard.test.ts`, який перевіряє, що
   `isLocalOnlyPath()` повертає true для нового префікса
3. **Ніколи не пропускайте цей крок** — див. жорстке правило №15 у `CLAUDE.md`
4. Вирішіть: чи має цей маршрут ТАКОЖ входити до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Типова відповідь — **ні**. Додавайте його лише тоді, коли маршрут безпечно надавати
   власнику manage-scope (тобто він НЕ запускає довільний код, керований користувачем).

## Додавання шляху, який можна обійти за допомогою manage-scope

1. Переконайтеся, що маршрут не виконує наданий користувачем код або команди. Якщо
   виконує, зупиніться — цей виняток тут не підходить.
2. Додайте префікс до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` у
   `src/server/authz/routeGuard.ts`
3. Додайте покриття в `tests/unit/authz/management-policy.test.ts` для всіх чотирьох
   варіантів запиту: без Bearer (403), manage Bearer (дозволити), не-manage Bearer
   (403), а також окрему регресійну перевірку для кожного префікса, щоб
   `/api/cli-tools/runtime/*` залишався доступним лише через loopback навіть із manage Bearer.

## Документування рівнів безпеки в OpenAPI

Під час додавання нового маршруту до `docs/openapi.yaml` застосуйте відповідне
розширення постачальника, якщо маршрут класифіковано в `routeGuard.ts`:

| Класифікація routeGuard.ts                      | YAML-анотація              | Застосування правил                                       |
| ----------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                       | `x-loopback-only: true`    | Безумовно блокується для з’єднань не через loopback       |
| `ALWAYS_PROTECTED_API_PATHS`                    | `x-always-protected: true` | Автентифікація обов’язкова навіть за `requireLogin=false` |
| Внутрішній маршрут адміністрування/налагодження | `x-internal: true`         | Типово прихований у /dashboard/api-endpoints              |
| Немає (публічний / стандартна автентифікація)   | (анотація не потрібна)     | Стандартний доступ, керований `requireLogin`              |

### Валідація

Два скрипти забезпечують узгодженість між YAML-анотаціями та `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершується помилкою, якщо покриття < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершується помилкою, якщо анотації `x-loopback-only` або
  `x-always-protected` не відповідають константам часу компіляції

Обидва скрипти запускаються в pre-commit hook і в CI.

### Правило щодо хибнопозитивних результатів

Якщо `x-always-protected` або `x-loopback-only` додано до маршруту, якого НЕМАЄ у
відповідній константі `routeGuard.ts`, скрипт перевірки покриття завершується помилкою. Правильне виправлення — завжди узгодити
YAML із тим, що фактично забезпечує `routeGuard.ts`, а не додавати маршрути до `routeGuard.ts`
без одночасної реалізації логіки застосування відповідних правил.
