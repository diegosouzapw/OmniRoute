- **fix(conversations):** parallel agents on one API key no longer re-insert their whole history as a new conversation on most requests. Reconnect candidates were the 20 most recently seen conversations in a bucket every agent on the key shared, so with more than 20 active agents a session's own conversation fell out of the window and its next request copied hundreds of turn nodes again (about 1.3M rows, ~1 GB a day, on one deployment). Candidates are now the bucket's conversations that already hold some of the request's turns, and when the client sends a session id (`x-claude-code-session-id`, Codex `session_id`, opencode `x-opencode-session`, or Claude's `metadata.user_id` session) the bucket is that session; the old bucket is still searched so existing conversations keep continuing. Migration 206 recreates the `(conversation_id, content_hash)` turn-node index (dropped by migration 201) that the new candidate lookup probes, so it stays a fast indexed search instead of a ~0.3–0.4 s row-by-row scan per request on busy installs.
